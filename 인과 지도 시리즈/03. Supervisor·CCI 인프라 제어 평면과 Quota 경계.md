# 03. Supervisor·CCI 인프라 제어 평면과 Quota 경계 — 원하는 Node 수는 어떤 자원 조건을 통과해야 실제 Worker가 되는가?

## 문서의 목적

이 문서는 DKS-C에서 Worker 수를 늘리겠다는 선언이 실제 Node 증가로 이어지기까지 무엇이 더 필요한지 설명합니다. MachineDeployment의 원하는 수와 VM 한 대의 사양, Supervisor Namespace·Zone·Region의 Quota와 실제 Capacity, CCI·Supervisor·User Cluster의 서로 다른 상태, 기존 Namespace Quota 변경 경로, 그리고 마지막으로 Node Ready까지 확인하는 과정을 하나의 흐름으로 연결합니다.

핵심은 원하는 Node 수를 선언한 상태, 그 Node를 만들 자원 사용이 허용된 상태, 실제 VM이 만들어진 상태, Kubernetes Node가 준비된 상태를 하나의 “증설”로 뭉치지 않는 것입니다. 내부 자료의 SupervisorNamespace update/patch 미지원과 vCenter API 변경 경로는 해당 자료가 기록한 환경의 제약이며 다른 VCF/VCFA 버전이나 현재 설치 환경에 자동으로 확대하지 않습니다.

## 전체 인과 지도

Worker를 늘리고 싶으면 먼저 MachineDeployment가 더 많은 Worker를 원하도록 바뀌어야 합니다. 하지만 원하는 수가 늘었다고 새 VM을 만들 자원까지 생기는 것은 아닙니다. 추가 Worker 한 대가 요구하는 CPU·Memory·Disk·Network를 계산하고 Supervisor Namespace의 허용량과 Zone·Region의 실제 Capacity가 이를 받아줄 수 있는지 따로 봐야 합니다. 자원 조건이 맞아도 어디를 조회하느냐에 따라 보이는 상태가 다릅니다. CCI는 Organization 범위의 자원 허가를, Supervisor는 Machine과 VirtualMachine의 Lifecycle을, User Cluster는 실제 Node 상태를 보여주기 때문에 한 계층의 Ready를 다음 계층의 완료로 사용할 수 없습니다. 부족한 Quota를 늘렸다면 그 변경이 반영된 것에서 끝나지 않습니다. 추가 Machine과 VM이 생기고 Bootstrap을 거쳐 kubelet이 Join하고 Node가 Ready가 될 때까지 이어져야 실제 Worker 증설이 끝납니다.

이 문서는 공장 증설을 하나의 비유 세계로 사용합니다. 설비 대수 계획은 원하는 Worker 수, 설비 한 대의 사양표는 VirtualMachineClass, 공장의 계약 한도와 실제 여유는 Quota와 Capacity, 실제 설비 설치와 가동은 VM 생성과 Node Ready에 대응합니다. 비유는 관계를 잡는 보조 수단이며 실제 증설 가능 여부와 완료 판단은 Resource·Condition·Event와 현재 인프라 상태를 기준으로 합니다.

### 원하는 Worker 수와 인프라 허용량

#### 왜 필요한가

Worker를 더 운영하려면 시스템이 실제로 더 많은 Node를 원해야 하고, 동시에 그 Node를 만들 자원도 허용되어 있어야 합니다. 원하는 수와 인프라 허용량은 서로 다른 조건이므로 한쪽만 바뀌어서는 실제 증설이 성립하지 않습니다.

#### 핵심 용어

- MachineDeployment: CAPI가 유지하려는 Worker Machine 집합과 원하는 개수를 나타내는 Resource
- replicas: MachineDeployment가 유지하려는 Worker 수
- Machine: Kubernetes Node 한 대의 생성·교체 Lifecycle을 표현하는 CAPI Resource
- Quota: 특정 Namespace나 인프라 범위에서 사용할 수 있도록 허용한 자원 한도
- Capacity: 실제 인프라에 남아 있는 배치 가능한 물리·논리 자원

#### 비유

생산 설비를 세 대에서 다섯 대로 늘리겠다는 계획이 MachineDeployment replicas라면, 공장의 전력·공간 계약은 Quota에 해당합니다. 설비 대수 계획을 늘려도 전력 계약이 자동으로 늘지 않고, 전력 계약만 늘려도 새 설비를 들이라는 주문이 생기지 않습니다.

#### 본문

MachineDeployment.replicas가 증가하면 CAPI는 추가 Worker를 위한 Machine을 만들 이유를 갖습니다. 예를 들어 replicas를 3에서 5로 바꾸면 CAPI는 추가 Worker 두 대를 만들도록 조정합니다. 그러나 이 선언이 Supervisor Namespace Quota를 자동으로 늘리지는 않습니다.

반대로 Quota만 늘리고 replicas를 그대로 두면 CAPI가 새 Machine을 만들 요구도 생기지 않습니다. 따라서 Worker 증설은 항상 두 질문으로 나눠야 합니다. 원하는 Node 수가 실제로 바뀌었는가, 그리고 그 Node를 만들 자원과 설정이 준비됐는가입니다.

```text
원하는 Worker 수 증가                 인프라 허용량 증가
MachineDeployment replicas ↑          Quota / Capacity ↑
          │                                   │
          ▼                                   ▼
추가 Machine 요구                    추가 VM 생성 가능성
          └──────────────┬────────────────────┘
                         ▼
                 실제 Worker 생성 후보

한쪽만 충족돼서는 충분하지 않음
```

MachineDeployment가 더 많은 Worker를 원하도록 바뀌었다고 바로 Node가 생기는 것도 아닙니다. Machine이 참조하는 Infrastructure·Bootstrap 설정이 유효해야 하고, Supervisor Namespace Quota와 실제 Zone·Storage·Network 자원이 준비되어야 VirtualMachine을 만들 수 있습니다. VM이 부팅된 뒤에는 Bootstrap이 적용되고 kubelet이 User Cluster API에 Join해야 하며, 마지막으로 Node Ready까지 확인해야 합니다.

```text
MachineDeployment desired replicas 증가
        ↓
추가 Machine 생성
        ↓
Infrastructure·Bootstrap 설정 유효
        ↓
Supervisor Namespace Quota 허용
        ↓
Zone·Storage·Network 실제 자원 준비
        ↓
VirtualMachine 생성·부팅
        ↓
kubelet Join
        ↓
Node Ready
```

각 화살표는 앞 상태가 뒤 상태의 충분조건이라는 뜻이 아닙니다. Machine이 있어도 VM 생성이 실패할 수 있고, VM이 Power On이어도 Bootstrap이 실패할 수 있습니다. kubelet이 등록돼도 CNI·CSI 문제로 Node가 Ready가 아닐 수 있으며, Node가 Ready라고 사용자 Application까지 정상이라는 뜻도 아닙니다.

### VM Class·Quota·Capacity

#### 왜 필요한가

추가 Worker 한 대의 크기를 안다고 해서 그 Worker를 실제로 놓을 자리가 남았다는 뜻은 아닙니다. Worker 증설 가능 여부를 판단하려면 VM 한 대의 단위 요구량과 Namespace·Zone·Region·Network의 전체 허용량과 실제 여유를 구별해야 합니다.

#### 핵심 용어

- VirtualMachineClass: VM 한 대의 CPU·Memory 사양을 정하는 클래스
- SupervisorNamespaceClassConfig: 새 Supervisor Namespace를 만들 때 적용할 기본 Quota와 VM Class 설정
- SupervisorNamespace: 현재 Namespace에 허용된 Compute·Storage 한도와 VM Class 연결을 나타내는 Resource
- RegionStorageClassQuota: Region 범위의 StorageClass별 한도와 소비량을 나타내는 Resource
- StorageQuota·StoragePolicyQuota·StoragePolicyUsage: Namespace와 Storage Policy 수준의 한도와 사용량을 확인하는 Resource
- Limit·IPBlock·LimitState: External IP 할당 정책·주소 Pool·소비 집계를 나타내는 Resource

#### 비유

VirtualMachineClass는 설비 한 대의 사양표이고, Supervisor Namespace Quota는 공장 전체가 사용할 수 있는 계약 한도입니다. 설비 한 대가 필요한 전력량을 안다고 해서 공장에 그만큼의 여유가 남았다는 뜻은 아닙니다. 계약 한도와 실제 전력 공급, 창고와 물류 공간을 각각 확인해야 실제 설비를 놓을 수 있습니다.

#### 본문

VirtualMachineClass는 VM 한 대의 CPU·Memory 사양을 정합니다. Supervisor Namespace Quota는 해당 Namespace에 허용된 CPU·Memory·Storage의 전체 범위입니다. 따라서 VM Class가 8 vCPU·16 GiB라는 사실은 같은 VM을 하나 더 만들 Quota와 실제 Compute 여유가 남았다는 뜻이 아닙니다.

User Cluster 하나에는 Supervisor Namespace 하나와 VPC 하나가 연결됩니다. Supervisor Namespace는 얼마까지 사용할 수 있는지와 어떤 VM Class를 요청할 수 있는지를 정하고, VPC는 Node VM이 사용할 Private IP와 Network 범위를 제공합니다. External IP가 필요한 작업에는 VPC가 참조하는 Limit과 IPBlock이 별도로 관여합니다.

| Resource | 실제로 정하는 것 | Worker 증설과의 관계 |
|---|---|---|
| VirtualMachineClass | VM 한 대의 CPU·Memory 사양 | 추가 Worker 한 대의 단위 요구량 |
| SupervisorNamespaceClassConfig | 새 Namespace의 기본 Quota와 VM Class | 생성 시 기본값 |
| SupervisorNamespace | 현재 Namespace의 Compute·Storage 한도와 VM Class 연결 | 추가 VM·Disk 요청 허용 범위 |
| VPC | VM이 연결될 Network 범위 | 추가 VM의 Network 접점 |
| Limit·IPBlock | External IP 할당 정책과 주소 Pool | External IP가 필요한 요청의 별도 Gate |
| MachineDeployment | 유지할 Worker Machine 수 | CAPI가 추가 Machine을 만들 이유 |

SupervisorNamespaceClassConfig의 기본값을 바꾸는 것과 이미 생성된 Supervisor Namespace의 Quota를 바꾸는 것은 같은 작업이 아닙니다. 전자는 이후 생성되는 Namespace의 기본 설정이고, 후자는 현재 운영 중인 인프라 범위를 바꾸는 작업입니다.

Quota는 자원 사용을 허용하는 한도입니다. Quota를 늘린다고 물리 CPU·Memory·Disk가 새로 생기지는 않습니다.

```text
새 Worker 한 대의 단위 요구량
├─ VM Class CPU / Memory
├─ OS Disk / Storage Policy
└─ Network / IP
        │
        ▼
통과해야 할 자원 범위
├─ Supervisor Namespace Quota
├─ Zone Compute Capacity
├─ Region / StorageClass Capacity
└─ VPC / Limit / IPBlock
        │
        ▼
VirtualMachine 생성 가능성
```

내부 자료에서 자원 종류별 확인 범위는 다음처럼 나뉩니다.

| 확인하려는 자원 | 주요 Resource | 확인되는 내용 |
|---|---|---|
| Namespace CPU·Memory·Storage 한도 | SupervisorNamespace | Zone별 CPU·Memory Limit, StorageClass별 Limit |
| Zone CPU·Memory | CCI Zone | Zone 범위의 Limit과 Used |
| Region Storage | RegionStorageClassQuota | StorageClass별 Region Limit과 Consumed |
| Namespace Storage 세부 | StorageQuota, StoragePolicyQuota, StoragePolicyUsage | VM·Snapshot·PVC 사용량과 Policy별 한도 |
| External IP | IPBlock, Limit, LimitState | 주소 Pool, 허용량, 소비 집계 |

내부 CCI 자료는 Node OS Disk 참고값으로 Control Plane 한 대당 136 GiB, Worker 한 대당 116 GiB를 기록합니다. 이 값이 적용되는 환경에서는 Worker 수 증가가 CPU·Memory뿐 아니라 OS Disk 수요도 늘립니다. 다만 실제 계산에는 대상 Cluster의 현재 VM·Disk 사양을 사용해야 하며 이 참고값을 모든 환경의 고정값으로 사용하지 않습니다.

External IP도 별도의 Gate입니다. 기존 VPC에 Worker만 추가하는 작업이 항상 새 External IP를 요구한다고 볼 수 없습니다. 반대로 LoadBalancer VIP나 External IP 추가 요청이라면 CPU Quota를 늘려도 IP 부족은 해결되지 않습니다. 따라서 증설이 멈췄다면 실패한 요청이 VM, Disk, External IP, Bootstrap 중 무엇인지 먼저 구분해야 합니다.

### CCI·Supervisor·User Cluster Context

#### 왜 필요한가

같은 User Cluster를 다뤄도 자원 허가, VM Lifecycle, 실제 Kubernetes 실행 상태는 서로 다른 API Context에서 보입니다. 한 Context에서 준비가 끝났다는 상태를 다음 Context의 완료로 사용하면 어디까지 실제로 진행됐는지 구분할 수 없습니다.

#### 핵심 용어

- CCI: Project·Region·Zone·Supervisor Namespace·VPC처럼 Organization 범위의 인프라 자원과 한도를 요청·조회하는 계층
- Supervisor: CAPI Resource와 VirtualMachine을 통해 Cluster와 VM Lifecycle을 관리하는 Kubernetes Cluster
- User Cluster: 실제 Node·Pod·Service·Application이 실행되는 Kubernetes Cluster
- API Context: kubectl이나 API 요청이 어느 Cluster·인증·Resource Group을 대상으로 하는지 정하는 실행 맥락
- VM Operator: Supervisor의 VirtualMachine Resource를 읽어 vSphere VM 작업으로 연결하는 Controller

#### 비유

본사 자산팀을 CCI, 시설팀을 Supervisor, 생산팀을 User Cluster에 대응시킬 수 있습니다. 자산팀은 공장 전체의 허가와 한도를 보고, 시설팀은 설비 설치 상태를 보고, 생산팀은 실제 가동 상태를 봅니다. 같은 공장을 다뤄도 각 팀이 확인하는 대상이 다릅니다.

#### 본문

User Cluster 안에서 Deployment와 Pod를 운영하는 작업과 User Cluster 자체를 실행할 VM·Network·Storage를 준비하는 작업은 서로 다른 API를 대상으로 합니다.

| 역할·Context | 주로 다루는 대상 | 이 Context만으로는 알 수 없는 것 |
|---|---|---|
| Organization Admin / CCI | Project, Region, Zone, Supervisor Namespace Class, Supervisor Namespace, VPC, Limit, IPBlock | 개별 User Cluster Pod의 현재 상태 |
| Organization User / Supervisor | CAPI Cluster·MachineDeployment·Machine, VirtualMachine | Application 요청의 최종 정상 여부 |
| Cluster User / User Cluster | Node, Deployment, Pod, Service 등 Application Resource | Region·Zone 전체 Quota와 vCenter Namespace 설정 |

Supervisor는 VM·Storage·VPC 같은 인프라 요청을 Kubernetes Resource로 관리하는 Kubernetes Cluster입니다. VirtualMachine Resource를 VM Operator가 읽어 vSphere VM 작업으로 연결합니다. CCI는 여러 Supervisor에 걸친 인프라 범위를 통합 API로 요청·조회합니다.

같은 Zone이라는 이름도 CCI의 topology.cci.vmware.com Resource와 Supervisor의 topology.tanzu.vmware.com Resource가 다를 수 있습니다. 이름이 같다고 같은 상태를 조회한다고 보면 안 됩니다.

```text
CCI Context
Project / Region / Zone / Supervisor Namespace / VPC
                 │ 자원 허가·범위
                 ▼
Supervisor Context
Cluster / MachineDeployment / Machine / VirtualMachine
                 │ VM Lifecycle
                 ▼
User Cluster Context
Node / Pod / Service / Application
                 │ 실제 Kubernetes 사용 상태
                 ▼
운영 결과

한 Context의 Ready ≠ 다음 Context의 Ready
```

이 구분 때문에 User Cluster에서 Node를 조회할 수 있다는 사실만으로 Region Quota를 변경할 수 있다고 말할 수 없습니다. CCI에서 Supervisor Namespace를 조회했다고 실제 Pod가 Ready인 것도 아니고, vCenter에 VM이 보인다고 Kubernetes Node가 등록된 것도 아닙니다. 각 상태를 서로 다른 관측점으로 이어서 사용해야 합니다.

### Quota 변경과 실제 증설 완료

#### 왜 필요한가

부족한 Quota를 늘리는 것은 추가 Worker를 만들 수 있는 한 조건을 바꾸는 일일 뿐입니다. 변경 요청이 성공한 뒤에도 실제 설정 반영, Machine·VM 생성, Bootstrap, kubelet Join, Node Ready가 이어져야 증설 완료라고 말할 수 있습니다.

#### 핵심 용어

- update/patch 지원: 기존 Resource의 설정을 같은 Resource API로 변경할 수 있는지 여부
- vCenter Namespace API: 일부 환경에서 기존 vSphere Namespace 설정을 변경하는 API
- Bootstrap: VM을 Kubernetes Node로 초기화하기 위한 설정과 명령
- kubelet Join: Worker의 kubelet이 User Cluster API에 자신을 Node로 등록하는 과정
- Condition·Event: Resource가 현재 어떤 상태이며 왜 그 상태인지 판단할 때 사용하는 Kubernetes 상태와 사건 기록

#### 비유

전력 계약을 늘리는 것이 Quota 변경이라면, 설비를 실제로 들여와 설치하는 것은 Machine·VM 생성이고 생산 라인에 참여해 가동되는 것은 kubelet Join과 Node Ready입니다. 전력 계약만 늘었다고 공장 증설이 끝난 것은 아닙니다.

#### 본문

내부 CCI 가이드는 해당 환경의 SupervisorNamespace가 create/destroy만 지원하고 update/patch를 지원하지 않으며 기존 Namespace Quota 변경에는 vSphere Automation API, 즉 vCenter API와 vCenter 권한이 필요하다고 기록합니다. 이 제약은 해당 자료가 기록한 환경의 근거이며 다른 버전이나 현재 설치 환경으로 자동 확대하지 않습니다.

Broadcom Namespace 변경 자료는 일부 버전에서 다음 PATCH 경로를 제공합니다.

```http
PATCH https://<vcenter>/api/vcenter/namespaces/instances/<namespace_id>
```

여기서는 세 상태를 구별해야 합니다.

| 상태 | 의미 |
|---|---|
| vCenter API가 Namespace 변경 기능을 제공 | 특정 vCenter 버전·권한에서 변경 API가 존재 |
| CCI SupervisorNamespace가 update를 지원 | CCI Resource 자체를 patch할 수 있음 |
| 실제 DKS-C 설치 환경에서 운영 절차로 지원 | 제품 버전·권한·운영 승인까지 확인됨 |

첫 번째가 확인됐다고 두 번째와 세 번째까지 자동으로 성립하지 않습니다. 내부 자료의 “향후 버전 적용 예정”도 현재 설치 환경의 지원 증거가 아닙니다. 변경 대상 Namespace ID도 Cluster 이름만으로 만들어내지 않고, CCI에서 실제 Supervisor Namespace와 대상 Supervisor를 확인한 뒤 vCenter Namespace와 대조해야 합니다.

Storage Policy 제거·교체는 단순 용량 증설보다 영향 범위가 큽니다. 기존 PVC나 User Cluster가 사용하는 Policy 변경을 필요한 CPU·Memory 증설과 한 작업으로 묶지 않습니다.

Quota 변경 요청이 성공했더라도 먼저 대상 Namespace 설정을 다시 조회해 바꾸려던 값이 실제 반영됐는지 확인합니다. CCI 값도 대조할 수 있지만 vCenter 변경과 CCI 상태 반영의 시점·조정 관계는 실제 환경에서 확인해야 합니다. 이 재조회는 운영자의 확인 절차이지, 사람이 조회해야 Controller가 다음 reconcile을 시작한다는 뜻은 아닙니다.

이미 Worker 증설을 요청했다면 마지막으로 확인된 상태와 다음 질문을 이어봅니다.

| 마지막으로 확인된 상태 | 다음 질문 | 주요 확인 대상 |
|---|---|---|
| MachineDeployment replicas가 바뀌지 않음 | 원하는 Node 수 선언이 실제 적용됐는가? | Git/ArgoCD, MachineDeployment spec |
| replicas는 증가했으나 Machine 없음 | CAPI Controller가 왜 추가 Machine을 만들지 못했는가? | MachineDeployment condition/event |
| Machine은 있으나 VirtualMachine 없음 | 어떤 인프라 Gate가 막혔는가? | Supervisor Namespace, Zone, Storage, VPC, Bootstrap 참조 |
| VirtualMachine 생성 실패 | Compute·Disk·Network 중 무엇이 부족한가? | VM condition, Event, Quota·Capacity |
| VM은 Power On이나 Node 미등록 | Bootstrap·API Join 조건이 충족됐는가? | cloud-init, kubelet, API endpoint, Token/Certificate |
| Node는 등록됐으나 NotReady | CNI·CSI·Node condition 중 무엇이 남았는가? | Node condition, kube-system Addon |
| Node Ready이나 Workload 미배치 | Scheduler·Affinity·Resource 조건이 맞는가? | Pod event, taint/toleration, request |

```text
Quota 변경 반영 확인
        ↓
MachineDeployment desired 확인
        ↓
추가 Machine
        ↓
VirtualMachine / Disk / Network
        ↓
Boot / Bootstrap
        ↓
kubelet Join
        ↓
Node Ready

Quota 반영 완료 ≠ Worker 증설 완료
```

Quota 문제를 해소했는데도 Node가 생기지 않으면 Quota 변경 실패로 되돌아가기 전에 새로 드러난 Condition과 Event를 확인합니다. Image·Storage·Network·Bootstrap 같은 경쟁 설명이 남아 있을 수 있습니다.

##### 어느 API에서 무엇을 조회하는가

조회할 Resource의 Context를 먼저 고정합니다. 아래 명령은 내부 가이드에 기록된 읽기 형태를 정리한 예시이며 이 문서 작성 과정에서 실제 환경에 실행한 결과가 아닙니다.

```bash
# CCI: Supervisor Namespace와 상위 Quota·Network
kubectl --context="$CCI_CONTEXT" get svns "$SVNS" -n "$PROJECT" -o yaml
kubectl --context="$CCI_CONTEXT" get zones.topology.cci.vmware.com "$ZONE" -o yaml
kubectl --context="$CCI_CONTEXT" get regionstorageclassquota -o yaml
kubectl --context="$CCI_CONTEXT" get vpc "$VPC" -o yaml
kubectl --context="$CCI_CONTEXT" get limit "$LIMIT" -o yaml

# Supervisor: CAPI와 VM lifecycle
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get machinedeployments,machines
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get virtualmachines
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get events

# User Cluster: 실제 등록된 Node
kubectl --context="$USER_CONTEXT" get nodes -o wide
```

배열의 첫 항목이 대상 Zone·StorageClass라고 가정하지 않고 실제 이름을 맞춰 조회합니다. Event는 과거 기록이 남아 있을 수 있으므로 현재 Condition, 대상 UID, 발생 시각을 연결해서 봅니다.
