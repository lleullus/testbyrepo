# 03. Supervisor·CCI 인프라 제어 평면과 Quota 경계 — Worker를 늘렸는데 왜 Node가 생기지 않는가?

## 문서의 목적

공장에 설비 두 대를 더 놓겠다고 결정해도 전력 계약과 설치 공간이 부족하면 증설하지 못합니다. 반대로 전력 계약만 늘리고 설비 발주를 하지 않으면 생산 라인은 그대로입니다. 발주, 사용 허가, 실제 설치, 가동 참여는 서로 다른 일입니다.

이 문서는 DKS-C의 Worker 증설을 **공장 증설**에 비유해 설명합니다. MachineDeployment는 유지할 설비 수량 계획, Machine은 개별 설비의 관리대장, VM은 실제 설치 대상, Quota는 허용된 자원 계약, Node 참여는 가동 체계 편입에 대응합니다. CCI·Supervisor·User Cluster에서 각각 무엇을 확인해야 하는지, Quota 변경 지원과 실제 증설 완료를 어떻게 구분하는지가 중심 질문입니다.

> 자료 범위: 지정된 03번 원문과 그 원문에 인용된 CCI·인프라·Namespace API 자료입니다. API 지원 제약과 Disk 수치는 기록된 환경의 값이며 현재 모든 제품 버전의 보장이 아닙니다. 예시와 명령은 실제 실행 결과가 아닙니다. [S1–S3]

## 전체 인과 지도

설비 수량을 세 대에서 다섯 대로 늘린다는 계획은 두 대를 더 필요로 한다는 뜻입니다. 그러나 그 계획 자체가 전력 계약을 바꾸거나 설치 공간을 만들어 주지는 않습니다.

MachineDeployment의 `replicas`를 3에서 5로 변경하면 원하는 Worker Machine 수가 증가합니다. Controller가 이를 반영하려면 Supervisor Namespace의 자원 한도, Zone의 가용량, Storage와 Network, VM 초기화 조건이 맞아야 합니다. 원하는 수량과 이를 수용하는 자원 조건은 별도로 관리됩니다.

본사 자산팀은 사용 허가를, 시설팀은 설치 상태를, 생산팀은 실제 가동을 봅니다. 한 팀의 장부만으로 다른 팀의 완료 상태나 변경 권한을 알 수는 없습니다.

CCI는 Project·Region·Zone·Supervisor Namespace·VPC의 자원 범위를, Supervisor는 CAPI와 VirtualMachine의 수명주기를, User Cluster는 Node·Pod·Service 실행 상태를 보여 줍니다. 같은 ‘Zone’이라는 이름도 API Group과 Context가 다르면 다른 객체일 수 있습니다.

전력 계약을 바꿀 수 있는 창구가 있다는 사실과 담당자에게 변경 권한이 있다는 사실은 다릅니다. 변경이 성공해도 설비가 설치되고 가동에 참여했는지까지 확인해야 증설을 닫을 수 있습니다.

기존 Namespace의 변경 API 지원, 대상 식별과 권한, 실제 Quota 반영을 먼저 구분합니다. 그 뒤 Machine·VirtualMachine·Bootstrap·kubelet Join·Node 상태를 연결합니다. 조회는 운영자의 확인 행위이며 Controller를 실행시키는 버튼이 아닙니다.

### 원하는 Worker 수와 실제 자원 수요

공장 설비 수량을 늘리는 계획과 설비 한 대의 사양은 다른 정보입니다. 수량만 늘려도 필요한 총전력과 공간은 증가하지만, 각 설비의 규격이 바뀌는 것은 아닙니다.

MachineDeployment의 `spec.replicas`는 원하는 Worker Machine 집합의 수를 나타냅니다. 원문의 설명처럼 3에서 5로 늘리는 경우 추가 수요는 2대입니다. VirtualMachineClass가 한 대당 8 vCPU·16 GiB라는 예시 조건이라면 두 대의 추가 Compute 수요는 16 vCPU·32 GiB입니다. 이는 개념 비교용 계산이며 실제 적용에는 대상 VM Class와 이미 소비 중인 자원, Quota 계산 기준을 사용해야 합니다. [S1]

```text
예시 조건: Worker 3대 → 5대, 한 대당 8 vCPU / 16 GiB
추가 Worker: 5 − 3 = 2대
추가 Compute 수요: 2 × 8 = 16 vCPU, 2 × 16 = 32 GiB

이 계산은 기존 사용량·Control Plane·Disk·Network를 합친
전체 Namespace 요구량이나 현재 가용 Capacity를 대신하지 않는다.
```

전력 계약에 여유를 추가해도 설비 발주 수량이 그대로라면 실제 설비는 늘지 않습니다. 반대로 발주 수량을 늘렸다고 계약상 허용량이 자동으로 따라 올라가지는 않습니다.

Quota 변경은 추가 자원을 사용할 수 있는 조건을 바꾸는 작업입니다. MachineDeployment의 desired 수량을 자동으로 증가시키는 작업이 아닙니다. `replicas` 변경 역시 Supervisor Namespace Quota를 자동으로 늘린다는 뜻이 아닙니다. 그래서 ‘Quota는 충분한가’와 ‘원하는 Node 수가 실제 선언됐는가’를 같은 질문으로 합치지 않습니다.

새 공장을 개설할 때 쓰는 표준 전력 계약과 이미 운영 중인 공장의 계약 변경은 적용 시점이 다릅니다. 표준값을 바꿨다고 과거 계약이 모두 자동 수정되는 것은 아닙니다.

`SupervisorNamespaceClassConfig`의 기본 Quota·VM Class 설정은 Supervisor Namespace 초기 구성에 사용할 수 있는 기준입니다. 이미 존재하는 Supervisor Namespace의 실제 한도 변경과는 구분해야 합니다. 기존 Namespace의 값을 바꾸려면 그 환경에서 지원하는 변경 경로와 현재 객체의 상태를 기준으로 판단합니다. [S1]

### 허용 한도와 실제 Capacity

공장에 사용할 수 있도록 허가된 전력량이 남아 있어도 해당 지역 공급망에 실제 여유가 없으면 설비를 설치하지 못합니다. 창고 용량과 외부 반출 주소도 전력 계약만으로 해결되지 않습니다.

Worker 추가에는 Namespace Quota뿐 아니라 Zone의 CPU·Memory 한도와 Used, Region의 Storage 한도와 Consumed, Storage Policy별 사용량, Network·주소 할당 조건이 함께 관계됩니다. Quota는 허용 상한이고 Capacity는 실제 제공 여유이므로 어느 범위의 자원을 보고 있는지 먼저 맞춰야 합니다. [S1, S2]

| 확인하려는 자원 | 주요 Resource | 읽을 내용 |
|---|---|---|
| Namespace CPU·Memory·Storage | SupervisorNamespace | Zone별 CPU·Memory Limit, StorageClass별 Limit |
| Zone CPU·Memory | CCI Zone | Zone 범위의 Limit과 Used |
| Region Storage | RegionStorageClassQuota | StorageClass별 Region Limit과 Consumed |
| Namespace Storage 세부 | StorageQuota, StoragePolicyQuota, StoragePolicyUsage | VM·Snapshot·PVC 사용량과 Policy별 한도 |
| External IP | IPBlock, Limit, LimitState | 주소 풀, 허용량, 소비 집계 |

설비가 차지하는 전력만 계산하고 설치 기반과 저장 공간을 빼면 발주는 맞아도 설치가 실패할 수 있습니다. 실제 규격서의 저장 공간을 전체 수요에 포함해야 합니다.

내부 CCI 자료는 Node OS Disk 참고값으로 **Control Plane 한 대당 136 GiB, Worker 한 대당 116 GiB**를 기록합니다. 해당 값이 적용되는 조건에서 Worker 2대를 추가하면 OS Disk만 232 GiB가 추가되는 예시가 됩니다. 실제 계산에서는 현재 VM·Disk 사양과 StorageClass·Policy, Snapshot·PVC 사용량을 사용합니다. 기록의 참고값을 모든 환경의 고정값으로 쓰지 않습니다. [S1]

같은 공장 구역 안에 설비를 더 놓는다고 외부 출입구를 매번 새로 발급받아야 하는 것은 아닙니다. 반대로 새로운 외부 출입구가 필요한 작업은 전력을 늘려도 해결되지 않습니다.

기존 VPC에 Worker만 추가하는 작업이 항상 새 External IP를 요구하는 것은 아닙니다. LoadBalancer VIP나 별도의 External IP 요청이 실패한 상황이면 CPU Quota 증설이 해결책이 아닙니다. 실패한 요청이 VM, Disk, External IP, Bootstrap 중 무엇인지 구분해야 합니다. VPC·SNAT의 관계는 [02번 문서](02.%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC%20%EA%B2%A9%EB%A6%AC%EC%99%80%201-1-1%20%ED%85%8C%EB%84%8C%EC%8B%9C%20%EA%B2%BD%EA%B3%84.md)와 연결됩니다.

### CCI·Supervisor·User Cluster Context

본사 자산팀의 화면에서는 공장 전체 계약을 볼 수 있고, 시설팀의 화면에서는 설비 설치 상태를 볼 수 있습니다. 생산팀이 설비의 가동 상태를 볼 수 있다는 이유만으로 본사의 계약을 바꿀 권한이 생기지는 않습니다.

API Context는 요청이 어느 Cluster·인증·리소스 범위를 향하는지 정하는 실행 맥락입니다. CCI, Supervisor, User Cluster는 같은 최종 User Cluster를 다루더라도 관측 대상과 권한이 다릅니다. CCI는 여러 Supervisor에 걸친 인프라 범위를 통합 API로 요청·조회하고, Supervisor의 VM Operator는 VirtualMachine을 읽어 vSphere VM 작업으로 연결합니다. [S1, S2]

| 역할·Context | 주로 다루는 대상 | 이 Context만으로 확인되지 않는 것 |
|---|---|---|
| Organization Admin / CCI | Project, Region, Zone, Supervisor Namespace Class, Supervisor Namespace, VPC, Limit, IPBlock | 개별 User Cluster Pod의 현재 동작 |
| Organization User / Supervisor | CAPI Cluster·MachineDeployment·Machine, VirtualMachine | 사용자 Application 요청의 최종 성공 |
| Cluster User / User Cluster | Node, Deployment, Pod, Service | Region·Zone 전체 Quota와 vCenter Namespace 변경 권한 |

두 부서가 모두 ‘구역’이라는 이름의 장부를 써도 같은 장부라고 볼 수는 없습니다. 장부를 발행한 부서와 적용 범위를 함께 읽어야 합니다.

CCI의 `topology.cci.vmware.com` Zone과 Supervisor의 `topology.tanzu.vmware.com` Zone은 API Group이 다를 수 있습니다. 이름만 보고 같은 자원 상태를 조회했다고 판단하지 않습니다. CCI에서 Supervisor Namespace가 준비됐다는 사실, vCenter에서 VM이 보인다는 사실, User Cluster에서 Node가 등록됐다는 사실도 각각 다른 관측입니다.

```text
같은 User Cluster를 바라보는 서로 다른 관측 범위
CCI Context         : 자원 허가·한도·VPC 범위
Supervisor Context  : Cluster / Machine / VirtualMachine 수명주기
User Cluster Context: Node / Pod / Service 실행 상태

한 Context의 준비 상태나 조회 권한이 다른 Context의
준비 상태·변경 권한을 자동으로 뜻하지 않는다.
```

### 기존 Quota 변경과 증설 완료

공장 계약을 바꾸는 창구가 따로 있다면 설비 관리 화면에서 계약을 수정하려 해서는 안 됩니다. 변경 API가 있다는 사실, 그 API를 사용할 권한, 운영 절차에서 허용한다는 사실도 각각 구분해야 합니다.

원문의 내부 CCI 가이드는 해당 환경의 SupervisorNamespace가 create/destroy만 지원하고 update/patch를 지원하지 않으며, 기존 Namespace Quota 변경에는 vSphere Automation API와 vCenter 권한이 필요하다고 기록합니다. 이는 그 자료가 기록한 환경의 제약입니다. 다른 버전이나 현재 설치 환경으로 자동 확대하지 않습니다. [S1]

일부 버전에 제공되는 창구의 주소를 안다고 올바른 공장 계약을 선택한 것은 아닙니다. 실제 대상 식별자와 변경 권한을 대조한 뒤에야 변경할 수 있습니다.

원문이 인용한 Broadcom Namespace 변경 자료에는 다음 경로가 제시되어 있습니다. 이는 **API 경로를 설명하는 표기**이며 이번 문서가 대상 환경에 실행하도록 승인하는 명령은 아닙니다. [S3]

```http
PATCH https://<vcenter>/api/vcenter/namespaces/instances/<namespace_id>
```

| 구분 | 확인해야 할 사실 |
|---|---|
| vCenter API에 변경 기능이 있음 | 해당 vCenter 버전과 필요한 권한에서 기능 제공 |
| CCI Resource 자체가 update 지원 | CCI SupervisorNamespace API에서 수정 가능 |
| 실제 DKS-C 운영 절차로 지원 | 설치 버전·연결 관계·권한·승인이 모두 맞음 |

첫 번째 사실만으로 나머지 둘을 확정하지 않습니다. 원자료의 ‘향후 버전 적용 예정’도 현재 지원 증거가 아닙니다. Namespace ID를 Cluster 이름으로 만들어내지 않고 CCI의 실제 Supervisor Namespace와 대상 Supervisor를 확인한 뒤 vCenter Namespace와 대조해야 합니다.

전력 계약을 늘리는 작업에 기존 배관과 저장 설비를 다른 규격으로 바꾸는 작업까지 섞으면 영향이 달라집니다. 필요한 증설과 별도 구조 변경을 한 번에 처리하지 않아야 어느 변경이 무엇을 바꾸는지 알 수 있습니다.

Storage Policy 제거·교체는 단순 CPU·Memory Quota 증설보다 영향 범위가 큽니다. 기존 PVC와 User Cluster가 사용하는 Policy를 변경하는 작업을 필요한 자원 증설과 무심코 묶지 않습니다. 허용되는 변경 대상과 실제 보존해야 하는 Storage 관계를 나누어 관리합니다.

계약 변경 접수가 성공해도 계약서에 값이 반영됐는지 읽어야 합니다. 그 확인 행위가 설비 설치팀의 작업 시작 버튼인 것은 아닙니다.

Quota 변경 후에는 대상 Namespace 설정을 재조회하여 변경하려던 값이 실제 반영됐는지 확인합니다. vCenter 변경과 CCI 상태 반영은 시점과 조정 관계가 다를 수 있으므로 두 값을 대조하되 동일 시점의 즉시 일치를 전제하지 않습니다. 이 재조회는 운영자의 검증이며 Controller가 다음 reconcile을 하려면 사람이 GET을 해야 한다는 뜻은 아닙니다.

```text
실제 조정 경로
Worker desired 증가 + 자원·인프라 조건 충족
    → CAPI·인프라 Controller 조정
    → Machine / VirtualMachine / Disk / Network 준비
    → Boot·Bootstrap → kubelet Join → Node 상태 보고

운영자 확인 경로
Quota 설정 읽기 / desired 읽기 / 각 Resource condition·event 읽기
    → 마지막 확인 상태와 남은 조건을 판단

운영자의 조회를 실제 생성 경로 가운데 실행 조건으로 넣지 않는다.
```

전력 계약 문제가 해결돼도 설비 운송이나 초기 가동에서 새 문제가 드러날 수 있습니다. 설치가 안 끝났다는 이유만으로 이미 반영된 계약 변경을 다시 실패로 돌려서는 안 됩니다.

Quota 반영 완료와 Worker 증설 완료는 다릅니다. 다음 상태를 따라가며 새로 확인된 Condition·Event로 판단을 갱신합니다. Image·Storage·Network·Bootstrap 문제는 Quota와 별도의 실패 지점일 수 있습니다.

| 현재 상태 | 다음 질문 | 주요 확인 대상 |
|---|---|---|
| MachineDeployment replicas가 그대로임 | 원하는 수량 선언이 실제 적용됐는가? | Git/ArgoCD, MachineDeployment spec |
| replicas 증가, 추가 Machine 없음 | CAPI가 추가 Machine을 만들지 못한 이유는 무엇인가? | MachineDeployment condition/event |
| Machine 존재, VirtualMachine 없음 | 인프라 요청의 어떤 조건이 막혔는가? | Namespace, Zone, Storage, VPC, Bootstrap 참조 |
| VirtualMachine 생성 실패 | Compute·Disk·Network 중 무엇이 실패했는가? | VM condition/event, Quota·Capacity |
| VM Power On, Node 미등록 | 초기화와 API 가입 조건이 맞는가? | cloud-init, kubelet, API endpoint, Token·Certificate |
| Node 등록, NotReady | 실행 준비 조건이 무엇인가? | Node condition, CNI·CSI·kube-system Addon |
| Node Ready, Workload 미배치 | Scheduler가 해당 Pod를 배치할 수 있는가? | Pod event, affinity, taint/toleration, request |

#### 어느 API에서 무엇을 읽는가

부서가 다른 장부를 볼 때는 먼저 어느 부서의 화면인지 확인해야 합니다. 잘못된 화면에서 ‘없음’을 보고 실제 설비가 없다고 판단하지 않도록 대상을 명시합니다.

다음은 원문의 조회 의도를 보존한 읽기 전용 명령 예시입니다. 변수는 실제 Context와 대상 이름으로 확인한 뒤 사용하며 이번 재작성에서 실행하지 않았습니다. 조회 결과의 Secret·인증 자료는 보고서에 원문으로 붙이지 않습니다.

```bash
# CCI: 허가·한도·연결 범위
kubectl --context="$CCI_CONTEXT" get svns "$SVNS" -n "$PROJECT" -o yaml
kubectl --context="$CCI_CONTEXT" get zones.topology.cci.vmware.com "$ZONE" -o yaml
kubectl --context="$CCI_CONTEXT" get regionstorageclassquota -o yaml
kubectl --context="$CCI_CONTEXT" get vpc "$VPC" -o yaml
kubectl --context="$CCI_CONTEXT" get limit "$LIMIT" -o yaml

# Supervisor: 실제 Cluster·VM 수명주기
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get machinedeployments,machines
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get virtualmachines
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get events

# User Cluster: 실행 기반의 참여 상태
kubectl --context="$USER_CONTEXT" get nodes -o wide
```

Condition은 배열의 첫 항목을 임의로 Ready로 보지 않고 `type`으로 식별합니다. 이름과 함께 UID·참조·현재 세대 및 시각을 대조하여, 다른 객체나 이전 변경의 상태를 이번 증설 결과로 섞지 않습니다.
