# 06. 통합 신원·인증과 무인 서비스 토큰 — 발급된 Token은 언제 실제 권한이 되는가?

## 문서의 목적

출입증 발급소가 신원을 확인하고 출입증을 만들어도 모든 문이 열리는 것은 아닙니다. 출입구는 발급기관과 유효기간을 확인하고, 해당 출입증으로 그 방에 들어갈 권한이 있는지도 판단합니다. 자동 설비가 출입증을 보관해 사용하는 경우에는 새 출입증 발급뿐 아니라 설비가 실제로 교체해 썼는지도 중요합니다.

이 문서는 DKS-C의 Keycloak·ADFS·OIDC와 장기 Token을 **회사 출입증의 발급·검사·권한·교체**라는 하나의 비유로 설명합니다. 사용자의 로그인, Token 종류와 Claim, Kubernetes 권한, 무인 서비스 Token, 교체 후 실제 소비까지 연결합니다.

> 자료 범위: 지정된 06번 원문의 Keycloak·Token·SW 설정 기록과 그 원문에 인용된 Kubernetes 설명입니다. 아래 Client 수명은 기록된 구성·관측을 구분해 보존한 것이며 현재 Realm을 조회한 결과가 아닙니다. 실제 Token·Client Secret·개인정보는 문서에 포함하지 않습니다. [S1–S4]

## 전체 인과 지도

중앙 발급소와 건물 안내창구는 같은 곳에 있어도 역할이 다릅니다. 안내창구는 방문자를 목적지로 보내고, 발급소는 신원을 확인해 출입증을 발급합니다.

DKS-C Gateway의 APISIX는 요청을 라우팅하고 Keycloak은 Realm·Client·User·Token과 ADFS 연동을 관리합니다. 모든 Route가 같은 인증 절차를 사용한다고 가정하지 않고 실제 Client와 수신 서비스의 설정을 연결해야 합니다.

출입증에는 발급기관, 소지자, 사용할 대상, 유효기간이 들어갑니다. 내용을 읽을 수 있다는 사실은 발급기관의 서명이 진짜라는 뜻과 다릅니다.

Token의 `iss`, `sub`, `aud`, `exp` 같은 Claim을 읽는 일과 서명·issuer·audience·만료를 검증하는 일을 구분합니다. ID Token과 Access Token은 목적이 다르며 Kubernetes의 실제 인증 경로가 어떤 Token을 사용하는지는 소비자 설정으로 확인해야 합니다.

자동 장비용 출입증을 길게 발급해도 장비가 예전 것을 계속 들고 있으면 교체는 끝나지 않습니다. 새 증명서 발급, 장비의 채택, 보호된 문 통과, 옛 증명서 처리까지 나누어 보아야 합니다.

무인 서비스의 장기 Token도 발급·저장·프로세스 반영·보호 API 검증·이전 자격의 종료를 구분합니다. 수명 설정값을 실제 Token 만료와 같다고 가정하거나, Secret 갱신을 소비자 교체 완료로 읽지 않습니다.

### 중앙 신원과 Client별 계약

회사의 중앙 출입증 체계 안에서도 직원용, 방문자용, 자동 설비용 신청 창구는 서로 다른 정책을 사용할 수 있습니다. 같은 발급소를 사용한다는 사실만으로 유효기간과 방문 대상이 같아지지는 않습니다.

Keycloak의 Realm은 사용자와 인증 정책을 묶는 범위이고 Client는 해당 Realm과 연동하는 애플리케이션의 계약 단위입니다. Client에는 로그인 흐름, redirect 조건, Credential, Scope·Audience, 세션과 Token 수명 등이 관계됩니다. DKS-C 원문은 Gateway의 Keycloak과 ADFS SSO 연동을 기록합니다. APISIX의 요청 중계와 Keycloak의 신원 처리는 구분하며 실제 Route·Plugin·Backend 설정에 맞춰 연결합니다. [S1, S2]

발급 규칙 표와 실제 출입증의 만료일이 다르면 ‘규칙 표가 있으니 실제 증명서도 그 값’이라고 결론내릴 수 없습니다. 기본값, 개별 창구 설정, 실제 발급 결과를 나누어 보아야 합니다.

원문의 Realm 기록에는 SSO Session Idle 8시간, SSO Session Max 24시간, Access Token 10분이 있습니다. 다음 Client별 설정과 관측을 함께 읽되, 이를 Keycloak의 보편 기본값이나 현재 모든 Token의 보장 수명으로 사용하지 않습니다. [S1]

| Client | 기록된 용도·대상 | 원문에 기록된 수명·조건 |
|---|---|---|
| `dkssol-console` | Console 로그인 | 30분 |
| `grafana-oauth` | Grafana 연동 | Realm 기본값 |
| `opensearch-dashboard-oauth` | OpenSearch Dashboards 연동 | Realm 기본값 |
| `kube-login` | 사용자 Kubernetes 로그인 관련 | Access / Offline Idle 8시간, Client Session Max 28,900초 |
| `k8s-client` | Kubernetes API OIDC 관련 | Realm 기본값 |
| `dks-cluster-mgmt` | console-vcfa → Console API | Realm 기본값 |
| `k8s-cluster-admin` | 관리자 시스템 연동 | Realm 기본값 |
| `dkssol-console-longterm-client` | Console·Monitoring·OpenSearch 장기 연동 | 365일 |
| `k8s-longterm-client` | Kubernetes 장기 연동 | 365일 |
| `k8s-longterm-client-30` | 기간별 장기 Client | 설정 30일, 실제 365일 발급 예외 기록 |
| `k8s-longterm-client-90` | 기간별 장기 Client | 설정 90일, 실제 365일 발급 예외 기록 |
| `k8s-longterm-client-120` | 기간별 장기 Client | 설정 120일, 실제 365일 발급 예외 기록 |
| `k8s-longterm-client-180` | 기간별 장기 Client | 설정 180일, 실제 365일 발급 예외 기록 |

8시간과 28,900초는 같은 숫자로 쓰지 않습니다. 서로 다른 필드에 기록된 값이며, 설정과 실제 발급 수명도 별개입니다. 특히 30·90·120·180일 Client에서 365일 발급이 기록된 예외는 그대로 남깁니다. Client 이름만으로 유효기간을 결정하지 않습니다.

### 로그인과 Token의 역할

신원 확인을 마친 사람이 발급 창구로 가져가는 일회용 접수표와 실제 문에서 제시하는 출입증은 다릅니다. 접수표를 받았다고 보호 구역을 통과한 것은 아닙니다.

원문의 OIDC 흐름에서는 ADFS 로그인과 Keycloak 세션을 거친 뒤 Authorization Code가 발급되고, Client가 Code를 교환하여 Token을 얻습니다. Code는 일회용 교환 자료이며 원문은 수명을 1분으로 기록합니다. Code 발급, Token 교환, 수신 서비스의 Token 검증, 작업 권한 확인을 각각 다른 단계로 봅니다. [S1, S2]

```text
사용자 로그인 / ADFS 연동
      → Keycloak의 로그인·Client 조건 충족
      → Authorization Code
      → Client의 Token 교환
      → 수신 서비스의 Token 검증
      → 해당 작업의 Authorization

Code 수명 1분은 원문 설정 기록이다.
로그인·발급 성공은 마지막 두 단계의 성공을 보장하지 않는다.
```

신분 확인서와 특정 업무에 사용할 출입증은 목적이 다릅니다. 같은 발급소에서 나왔고 모양이 비슷해도 아무 문에서나 서로 바꾸어 제시할 수는 없습니다.

ID Token은 Client에 사용자 인증 결과를 전달하는 용도이고, Access Token은 API 등 Resource Server 접근에 사용됩니다. Kubernetes의 전통적인 OIDC 인증 경로는 ID Token을 Bearer로 사용하는 형태가 있으므로 ‘Access Token이라는 이름이면 Kubernetes에 맞다’고 단정하지 않습니다. 반대로 `kube-login` 문서에 Access Token 수명이 기록되어 있다는 것만으로 kubectl이 실제 어떤 필드의 Token을 쓰는지도 확정할 수 없습니다. kubeconfig·인증 Plugin과 API Server의 OIDC 설정을 실제로 연결해야 합니다. [S3]

출입증에 쓰인 소지자와 발급기관, 사용처, 만료일은 각각 다른 질문에 답합니다. 글씨를 읽었다는 사실만으로 위조 여부가 확인되지는 않습니다.

JWT는 구조화된 Claim을 담는 Token 형식입니다. 다음 항목은 Token의 의미를 읽는 데 도움이 되지만, payload 디코딩은 서명 검증이 아닙니다. 실제 수신자는 서명·신뢰 issuer·audience·시간 조건 등을 자신의 설정에 따라 검증해야 합니다.

| Claim | 읽을 의미 | 주의할 점 |
|---|---|---|
| `iss` | 발급자 | 수신자가 신뢰하도록 설정한 issuer와 맞아야 함 |
| `sub` | 발급 체계 안의 주체 식별자 | 이름처럼 보이는 다른 Claim과 동일하지 않을 수 있음 |
| `aud` | Token의 대상 | 요청한 API·Client의 기대 Audience와 대조 |
| `azp` | 발급·인가된 Client 관련 식별 | 모든 권한을 직접 뜻하는 값으로 사용하지 않음 |
| `preferred_username` | 표시·매핑할 사용자 이름 정보 | 실제 인증 주체·권한 매핑 설정과 대조 |
| `groups` | 그룹 정보 | 포함됐다는 사실만으로 Role이 자동 부여되는 것은 아님 |
| `exp` | 만료 시각 | 디코딩값은 읽을 수 있어도 서명·수신자 검증을 대신하지 않음 |

### 신원 인증과 Kubernetes 권한

출입증이 진짜이고 유효해도 직원에게 약품 보관실 반출 권한이 없으면 문은 열리지 않습니다. ‘누구인가’와 ‘무엇을 할 수 있는가’는 다른 판단입니다.

Kubernetes API는 Token을 신뢰할 수 있는지 인증한 뒤, 그 Identity가 해당 작업을 할 권한이 있는지 판단합니다. OIDC의 issuer·Client/Audience 및 사용자·그룹 매핑과 Role·ClusterRole·RoleBinding·ClusterRoleBinding을 나누어 봅니다. Token 발급 성공은 RBAC 권한 성공이 아닙니다. [S3]

같은 이름이 붙은 출입증이라도 실제 문이 확인하는 식별자가 다르면 기대한 권한을 못 받을 수 있습니다. 명찰 이름만 보고 권한을 추정하면 발급과 소비의 연결을 놓치게 됩니다.

API Server의 `--oidc-issuer-url`, Client ID와 관련된 Audience 설정, 사용자·그룹 매핑을 실제 Token의 Claim과 대조해야 합니다. `preferred_username`이나 `groups`가 보인다는 사실만으로 기대한 Kubernetes 사용자·그룹이 생성된다고 가정하지 않습니다. `401`과 `403`은 인증과 권한 문제를 구분하는 단서이지만, Proxy나 Backend가 응답했을 가능성까지 보아야 정확한 거절 주체를 알 수 있습니다.

### 무인 서비스의 장기 Token

야간 자동 설비가 사람의 로그인 없이 동작하려면 미리 발급한 출입 수단이 필요합니다. 그러나 자동 설비용이라는 이유만으로 누구의 권한을 갖고 어떤 발급 과정을 거쳤는지 생략할 수는 없습니다.

원문은 사용자 로그인과 Code를 통해 얻은 단기 Access Token을 입력으로, Client Credential을 사용하는 Token Exchange 경로에서 장기 Access Token을 발급받는 흐름을 기록합니다. 이 흐름은 Kubernetes ServiceAccount Token, Client Credentials Grant만으로 발급한 Token, 일반적인 Refresh Token 갱신과 구분해야 합니다. 발급 결과의 실제 주체와 권한은 Claim 및 소비자 검증으로 확인합니다. [S2]

```text
원문에 기록된 장기 발급 관계
사용자 로그인 → Code → 단기 Access Token
                             │ Token Exchange의 입력
Client Credential ──────────┘
                             ▼
                     장기 Access Token
                             ▼
                    무인 서비스가 보호 API에 사용

Client Credential 사용 = 모든 경우 Client Credentials Grant라는 뜻이 아님
장기 Access Token = Kubernetes ServiceAccount Token이라는 뜻이 아님
```

발급 창구에서 ‘30일용’이라고 부르는 출입증도 실제 인쇄된 만료일을 보아야 합니다. 이름과 설정만으로 실제 발급 결과를 대신하지 않습니다.

기간별 Client의 설정과 365일 발급 예외가 원문에 함께 있으므로 실제 `exp`를 읽어 발급 결과의 만료를 확인해야 합니다. 다음은 현재 프로세스 환경의 Token을 디코딩해 만료 시각만 표시하는 예시입니다. Token 원문이나 전체 Claim을 출력하지 않으며, **서명·issuer·audience·권한을 검증하는 코드는 아닙니다.** 이번 재작성에서 실제 Token으로 실행하지 않았습니다.

```python
import os
import json
import base64
from datetime import datetime, timezone

raw = os.environ.get("LONG_TERM_TOKEN", "")
parts = raw.split(".")
if len(parts) != 3:
    raise SystemExit("JWT 형식의 Token이 필요합니다. 원문은 출력하지 않습니다.")
try:
    payload = parts[1] + "=" * (-len(parts[1]) % 4)
    claims = json.loads(base64.urlsafe_b64decode(payload).decode("utf-8"))
    if not isinstance(claims, dict):
        raise ValueError("payload must be an object")
    exp = claims.get("exp")
    if isinstance(exp, bool) or not isinstance(exp, (int, float)):
        raise ValueError("exp missing")
    expires = datetime.fromtimestamp(exp, tz=timezone.utc)
except (ValueError, TypeError, UnicodeError, OverflowError):
    raise SystemExit("만료 Claim을 읽을 수 없습니다. Token 원문은 출력하지 않습니다.")
print("expires_at_utc:", expires.isoformat())
```

### 새 Token을 실제로 사용하게 만드는 과정

새 출입증을 서랍에 넣었다고 자동 설비가 손에 들고 있는 옛 출입증까지 바뀌지는 않습니다. 설비가 어디에서 증명서를 읽고 언제 다시 읽는지에 따라 교체 방법이 달라집니다.

Kubernetes Secret 갱신과 소비 프로세스의 Credential 채택은 다릅니다. 환경변수로 받은 값은 이미 실행 중인 프로세스에서 자동으로 바뀌지 않으므로 재시작 등 반영 절차가 관계됩니다. Secret Volume은 갱신 전파와 애플리케이션 재읽기 조건을 함께 보아야 하고, `subPath` 마운트는 자동 갱신을 기대할 수 없는 경우로 구분합니다. Config reload·외부 Credential cache도 실제 소비 경로에 포함됩니다. [S4]

| 단계 | 확인할 것 | 그 단계만으로 끝나지 않는 이유 |
|---|---|---|
| 발급 | 새 Token의 실제 만료·대상·주체 | 소비자가 사용한 증거가 아님 |
| 저장 | 의도한 Secret·설정에 반영 | 실행 프로세스의 값과 다를 수 있음 |
| 채택 | 재시작·재읽기·reload 등 소비 경로 반영 | 보호 API 권한과 기능을 아직 확인하지 않음 |
| 기능 검증 | 새 Credential로 의도한 보호 API 성공 | 공개 health 응답으로 대체할 수 없음 |
| 이전 자격 처리 | 옛 Token의 실제 허용·만료·종료 조건 | 파일 삭제나 Secret 교체만으로 무효화되지 않을 수 있음 |

새 출입증으로 보안문을 통과했는지 확인해야 하는데 누구나 드나드는 로비 문만 열어 보면 교체 성공을 알 수 없습니다.

교체 검증은 실제로 인증이 필요한 경로에서 수행합니다. 공개 health URL의 `200`은 새 Token 사용을 입증하지 않습니다. 어떤 소비자가 새 Credential을 채택했는지와 해당 보호 API의 기대 작업을 수행했는지를 연결해야 합니다. 검사 과정에서 Raw Token·Client Secret을 로그나 보고서에 남기지 않습니다.

옛 출입증을 서랍에서 버렸어도 문이 그 출입증을 유효하다고 판단하면 권한은 남아 있습니다. 보관 위치에서 지우는 것과 검사 체계가 거절하는 것은 다릅니다.

이전 JWT는 수신 서비스가 로컬 서명·만료 검증으로 허용하는 동안 계속 유효할 수 있습니다. Secret 삭제, Client Secret 교체, 로그인 세션 종료를 모든 소비자에서 즉시 Token 무효화되는 보장으로 쓰지 않습니다. 실제 검증 방식과 폐기·만료 정책에 따라 종료 여부를 판단합니다. Kubernetes Secret의 base64 표기도 암호화와 같지 않으므로 접근 권한과 보관·전달 범위를 별도로 통제해야 합니다. [S2–S4]

### 어느 경계에서 실패했는가

출입증 문제가 생기면 발급소, 증명서 내용, 문 앞 검사기, 방별 권한, 자동 설비의 보관함을 한꺼번에 바꾸기보다 마지막으로 통과한 경계를 찾는 편이 명확합니다.

아래 표는 발급·검증·소비를 구분하는 조사 기준입니다. 새로운 Token을 무조건 재발급하거나 모든 소비자를 재시작하는 절차가 아닙니다.

| 관측 증상 | 구분할 질문 | 주요 확인 대상 |
|---|---|---|
| ADFS 로그인 실패 | 상위 신원 확인이 끝났는가? | ADFS·Keycloak 연동과 오류 주체 |
| 로그인 뒤 Code 처리 실패 | Client·redirect·교환 조건이 맞는가? | Client와 Code 수명·일회성 |
| Token 교환 실패 | 의도한 발급 흐름과 Credential인가? | Grant/Exchange 요청·Client 설정 |
| 예상 수명과 실제 만료 불일치 | 설정이 실제 발급에 어떻게 적용됐는가? | Client 수명, `exp`, 예외 기록 |
| Token은 있으나 수신 거부 | 서명·issuer·audience·만료가 맞는가? | 소비자 인증 설정과 Claim |
| 신원은 확인되나 작업 거부 | 해당 Identity에 권한이 있는가? | Role·Binding·사용자/그룹 매핑 |
| Secret은 변경됐으나 옛 값 사용 | 프로세스가 새 값을 읽었는가? | env·Volume·subPath·reload·cache |
| health는 성공하나 실제 기능 실패 | 검증한 경로가 보호된 실제 작업인가? | API 경로·응답·작업 결과 |
| 교체 뒤에도 옛 Token 허용 | 수신자의 종료·검증 조건은 무엇인가? | 만료·검증 방식·실제 거절 결과 |
| Credential 정보가 로그에 노출 | 관측 범위가 과도했는가? | 로그·환경 출력·접근 권한·보관 범위 |
