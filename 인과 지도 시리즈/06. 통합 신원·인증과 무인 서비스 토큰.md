# 06. 통합 신원·인증과 무인 서비스 Token — 누구의 신원을 어떤 Client가 어떤 Credential로 전달하고 언제 권한이 실제로 성립하는가?

## 문서의 목적

이 문서는 DKS-C에서 사람이 Console·Grafana·kubectl에 접속하는 흐름과 Monitoring·CI/CD 같은 자동 프로그램이 API를 호출하는 흐름을 함께 설명합니다. ADFS·Keycloak Realm·OIDC Client·Authorization Code·Token·Kubernetes RBAC가 각각 무엇을 맡는지, Short-Lived User Token이 Long-Term Token으로 이어질 때 무엇이 유지되는지, 그리고 새 Credential을 발급한 뒤 실제 소비자 반영과 옛 Credential 폐기까지 어디를 확인해야 교체가 끝났다고 말할 수 있는지를 하나의 인과 흐름으로 연결합니다.

핵심은 Login 성공, Code 발급, Token 발급, Token 검증, Identity 확인, Authorization 허용, 실제 API 기능 성공을 하나의 “인증 성공”으로 뭉치지 않는 것입니다. Long-Term Token도 발급, 소비자 반영, 실제 사용, 옛 Token 폐기를 각각 구별합니다. DKS-C 내부 자료의 Client 이름·Lifetime·Token Exchange 흐름은 기록된 환경에 대한 근거이며 현재 Keycloak Version·Client Policy·Kubernetes OIDC 설정·P-DEP 연동 Credential은 실제 설정에서 재확인해야 합니다.

## 전체 인과 지도

사람이 DKS-C 서비스에 들어오려면 먼저 사내 Identity가 확인되고, 그 결과가 대상 Application에 맞는 OIDC Client 흐름으로 이어져야 합니다. 같은 Keycloak Realm을 사용해도 Console·Grafana·kubectl은 Redirect URI·Audience·Lifetime이 다를 수 있기 때문에 하나의 Token 규칙으로 묶을 수 없습니다. Browser Login이 끝나도 API 호출용 Credential은 아직 준비되지 않았습니다. Authorization Code를 Token Endpoint에서 교환해 Token을 받고, Resource Server가 Signature·Issuer·Audience·Expiration을 검증해야 비로소 신뢰할 Identity를 만들 수 있습니다. Identity가 확인돼도 그 사용자가 원하는 API 작업을 할 수 있다는 뜻은 아니므로 RBAC나 Application Policy가 권한을 별도로 판단해야 합니다. 자동 프로그램은 매번 Browser Login을 할 수 없기 때문에 별도의 장기 Credential이 필요해지고, DKS-C 자료는 User Token에서 Long-Term Token으로 이어지는 Token Exchange 흐름을 기록합니다. 그러나 새 Token을 발급했다고 실제 서비스가 그 값을 쓰기 시작한 것은 아닙니다. Secret·Environment·Config 같은 소비자 저장 위치를 갱신하고 Process가 새 값을 읽고 Protected API 호출까지 성공한 뒤, 옛 Token이 더 이상 사용되지 않고 필요한 경우 실제로 거부되는지 확인해야 Credential 교체가 끝납니다.

이 문서는 사내 출입증 발급소와 건물 출입 통제를 하나의 비유 세계로 사용합니다. 회사의 신원 체계는 Realm, 건물별 출입증 발급 등록은 Client, 일회용 교환표는 Authorization Code, 출입증은 Token, 입구의 출입증 검사는 Authentication, 출입문 권한표는 Authorization, 장기 출입증의 배포와 회수는 Long-Term Token 수명주기에 대응합니다. 비유는 관계를 잡는 보조 수단이며 실제 인증·권한 판단은 현재 Client 설정·Token Claim·Server 검증 결과·RBAC·API 결과를 기준으로 합니다.

### Realm과 OIDC Client

#### 왜 필요한가

같은 사용자가 같은 Keycloak Realm에서 인증되더라도 Console·Grafana·kubectl·자동 호출은 서로 다른 Application이며 필요한 Redirect URI·Audience·Flow·Lifetime이 다를 수 있습니다. 서비스별 인증 흐름을 구별하려면 공통 Realm과 개별 Client의 역할을 먼저 나눠야 합니다.

#### 핵심 용어

- ADFS: 사내 User Identity를 확인하는 외부 Identity Provider로 Keycloak과 Federation될 수 있는 시스템
- Keycloak Realm: User·Group·Client·Session·Token Policy를 묶는 관리 범위
- OIDC Client: Keycloak과 Login·Token 교환을 수행하도록 등록된 Application 또는 Service
- Redirect URI: Login 뒤 Authorization Code나 결과를 돌려보낼 Client 주소
- Audience: Token을 어느 Resource Server가 받아야 하는지 나타내는 대상 정보
- Session Lifetime: Login Session이 유지되는 시간 범위
- Token Lifetime: 개별 Token 자체가 유효한 시간 범위

#### 비유

회사의 공통 인사 체계를 Realm, 본사·연구동·데이터센터마다 따로 등록한 출입증 발급 창구를 OIDC Client로 볼 수 있습니다. 같은 직원이 같은 회사에 속해도 건물마다 출입증의 용도와 만료 규칙은 다를 수 있습니다.

#### 본문

내부 SW 자료는 Gateway Cluster의 Keycloak을 사내 ADFS SSO와 연동된 OIDC 중앙 인증 Component로 기록합니다. APISIX는 Routing을, Keycloak은 Identity와 Token을 담당하므로 둘을 같은 “Gateway 인증” 기능으로 합치지 않습니다.

Keycloak의 Realm은 User·Group·Client·Session·Token Policy를 분리하는 관리 범위이고, DKS-C 자료는 DKS Realm을 기록합니다. Client는 Keycloak과 인증을 주고받는 Application 또는 Service 등록입니다. Client마다 Redirect URI, Public/Confidential 여부와 인증 방식, Access Token Lifetime, Session 설정, Allowed Flow·Scope, Audience·Protocol Mapper가 달라질 수 있습니다.

내부 자료에 기록된 Client와 수명 설정은 다음과 같습니다.

| Client | 기록된 목적 | 기록된 주요 수명 설정 |
|---|---|---|
| dkssol-console | DKS-C Console OIDC Login | Access Token 30분 |
| grafana-oauth | Grafana Login | Realm 기본값 |
| opensearch-dashboard-oauth | OpenSearch Dashboards Login | Realm 기본값 |
| kube-login | kubectl OIDC Login | Access Token·Offline Session Idle 8시간, Client Session Max 28,900초 |
| k8s-client | kube-apiserver OIDC 설정 | Realm 기본값 |
| dks-cluster-mgmt | console-vcfa → Console API 시스템 호출 | Realm 기본값 |
| k8s-cluster-admin | 관리자 기능용 시스템 계정 | Realm 기본값 |
| dkssol-console-longterm-client | Console·Monitoring·OpenSearch 계열 장기 호출 | 365일 기록 |
| k8s-longterm-client | Cluster 접속 장기 Token | 365일 기록 |
| k8s-longterm-client-30/-90/-120/-180 | 기간별 장기 Token 의도 | 30/90/120/180일 설정, 실제 365일 발급 예외 기록 |

Realm 기본값은 내부 자료에 SSO Session Idle 8시간, SSO Session Max 24시간, Access Token Lifespan 10분으로 기록되어 있습니다. 이 값은 기록된 환경의 설정이며 현재 값을 판단할 때는 실제 Realm·Client Policy와 발급 Token을 다시 봐야 합니다.

Session Lifetime과 Token Lifetime도 같은 상태가 아닙니다.

```text
SSO Session이 유효
        ≠
기존 Access Token이 아직 유효

Access Token 만료
        ≠
User Session이 끝남
        ≠
Client가 Refresh·재발급할 수 없음
```

따라서 ADFS Login 성공은 사내 Identity 확인의 한 단계일 뿐 대상 서비스의 Client Flow 성공을 보장하지 않습니다. 같은 Realm을 쓴다는 사실만으로 모든 서비스가 같은 Token·Audience·Lifetime을 사용한다고 결론내리지 않습니다.

### Authorization Code와 Token 검증

#### 왜 필요한가

Browser Login이 성공해도 그 결과를 API에서 바로 사용할 수 있는 것은 아닙니다. Client는 일회용 Authorization Code를 Token으로 교환해야 하고, Token을 받은 뒤에도 Resource Server가 그 Token을 신뢰할 수 있는지 검증해야 실제 인증에 사용할 수 있습니다.

#### 핵심 용어

- Authorization Code: Browser Login 뒤 Client가 Token Endpoint에서 Token으로 교환하는 일회용 값
- Token Endpoint: Code와 Client 정보를 검증하고 Token을 발급하는 Endpoint
- JWT: Claim을 담고 서명할 수 있는 Token 형식
- Signature: Token이 신뢰할 수 있는 발급자에 의해 만들어졌는지 검증할 때 사용하는 서명
- iss: Token을 발급한 Issuer
- aud: Token을 받아야 하는 Audience
- exp: Token 만료 시각
- Resource Server: Token을 받아 실제 API Resource를 제공하는 Server

#### 비유

본인 확인 뒤 받은 일회용 교환표가 Authorization Code이고, 교환 창구에서 받은 정식 출입증이 Token에 해당합니다. 교환표를 받았다고 출입증 발급이 끝난 것은 아니며 출입증을 받았다고 어떤 건물에서든 자동으로 받아주는 것도 아닙니다. 실제 건물 입구에서 출입증을 검증해야 합니다.

#### 본문

Authorization Code Flow에서는 User가 Browser Login을 완료한 뒤 Client Redirect URI로 Authorization Code를 돌려받습니다. Code는 API 호출용 장기 Credential이 아니라 Token Endpoint에서 Token을 받기 위한 일회용 값입니다. 내부 Long-Term Token 가이드는 Console Client의 Login 흐름을 다음처럼 기록합니다.

```text
User Browser
   ↓
Keycloak Authorization Endpoint
   ↓ ADFS 연동 Login
Client Redirect URI
   ↓ Authorization Code
Keycloak Token Endpoint
   ↓ Client·Code 검증
Short-Lived Token
```

원자료는 Code를 1회용, 1분 만료로 기록합니다. 이것은 해당 DKS-C 설정에 대한 근거이며 모든 OIDC 환경의 고정값으로 일반화하지 않습니다.

각 단계의 성공은 다음 단계를 보장하지 않습니다.

| 확인 상태 | 확인되는 것 | 아직 남은 조건 |
|---|---|---|
| ADFS Login 성공 | 사내 Identity Provider가 User를 인증 | Keycloak Federation·Client 흐름 |
| Keycloak Session 생성 | Realm Login 상태 존재 | Client Redirect·Code 발급 |
| Authorization Code 발급 | Client로 돌아갈 일회용 교환값 생성 | Token Endpoint 교환 성공 |
| Token 발급 | Keycloak이 Credential 발행 | Resource Server의 검증·권한 |
| Browser가 Token 보유 | Client가 Token을 받음 | Backend 전달·저장·재발급 방식 |

Code 교환이 성공했다고 Console Frontend·Backend가 Token을 어디에 저장하고 어느 Header에 넣는지까지 알 수 있는 것은 아닙니다. 실제 Application 구현을 확인해야 합니다.

Token을 받은 Resource Server는 Signature, iss, aud, exp와 필요한 Claim Mapping을 검증해야 합니다. JWT Payload를 Decode할 수 있다는 사실은 Signature가 유효하다는 뜻이 아니고, Token 발급 성공은 현재 Resource Server가 그 Token을 수용한다는 뜻도 아닙니다.

JWT에는 다음과 같은 Claim이 들어갈 수 있습니다.

| Claim | 의미 |
|---|---|
| iss | Token Issuer |
| sub | Subject/User 식별자 |
| aud | Token 대상 Audience |
| azp | 발급에 참여한 Authorized Party/Client |
| preferred_username | User 이름 |
| groups | Group 정보 |
| exp | 만료 시각 |

OIDC의 ID Token은 Authentication 결과로 User Identity를 Client에 전달하는 Token이고, OAuth Access Token은 Resource Server/API 호출을 위한 Authorization Credential입니다. 둘 다 JWT 형식일 수 있기 때문에 Payload 모양만으로 목적을 판단하면 안 됩니다.

Kubernetes의 전통적인 OIDC 사용자 인증 문서는 ID Token을 Bearer Token으로 API Server에 제시하는 흐름을 설명합니다. 내부 Keycloak 자료에 kube-login의 Access Token Lifespan이 기록되어 있다는 사실만으로 kube-login Plugin이 Access Token을 API Server에 보낸다고 확정하지 않습니다. 실제 kubectl·API Server 흐름에서는 Plugin이 어느 Token Field를 Kubeconfig Credential로 반환하는지, API Server의 --oidc-issuer-url과 Client ID/Audience, Username·Group Claim, Token aud, Refresh·Offline Session 사용 방식을 확인합니다.

### Authentication과 Authorization

#### 왜 필요한가

Token이 유효하고 누구를 나타내는지 확인됐다고 그 Identity가 원하는 API 작업을 수행할 권한까지 생기는 것은 아닙니다. 신원 확인과 작업 허용을 분리해야 401·403·기능 실패가 어디에서 생긴 문제인지 구분할 수 있습니다.

#### 핵심 용어

- Authentication: Token이나 Certificate를 검증해 신뢰할 수 있는 Identity를 확인하는 과정
- Authorization: 확인된 Identity가 특정 Resource·Verb·기능을 수행할 수 있는지 판단하는 과정
- Claim Mapping: Token Claim을 User 이름이나 Group 정보로 해석하는 설정
- Role·ClusterRole: Kubernetes API 작업 권한 Rule을 정의하는 Resource
- RoleBinding·ClusterRoleBinding: Role·ClusterRole을 User·Group·ServiceAccount에 연결하는 Resource
- 401·403: 각각 Authentication·Authorization 문제의 후보가 될 수 있지만 실제 응답 주체를 확인해야 하는 HTTP 상태

#### 비유

출입증의 진위를 확인하는 검사가 Authentication이고, 유효한 직원이 특정 서버실 문을 열 수 있는지 권한표를 확인하는 것이 Authorization입니다. 유효한 사원증이 있어도 서버실 권한이 없으면 들어갈 수 없습니다.

#### 본문

Authentication은 Token을 신뢰할 수 있고 어느 User·Group을 나타내는지 판단합니다. Kubernetes에서는 OIDC Issuer·Audience·Username·Group Claim Mapping이 이 과정에 관여합니다. Signature가 신뢰 Key로 검증되는지, iss가 기대 Issuer인지, aud가 현재 Resource Server에 맞는지, exp가 지나지 않았는지, Username·Group Mapping이 기대한 형태인지 확인합니다.

Authorization은 인증된 User·Group·ServiceAccount가 요청한 Resource와 Verb를 수행할 수 있는지 Role·ClusterRole과 Binding 또는 Application Policy로 판단합니다.

```text
JWT 구조를 Decode할 수 있음
        ≠
Signature / Issuer / Audience 유효
        ↓
Authentication
        ↓
User / Group Identity
        ↓
RBAC / Application Policy
        ↓
Authorization
        ↓
실제 API 처리

Authentication 성공 ≠ Authorization 성공 ≠ 기능 성공
```

401과 403도 하나의 “인증 실패”로 합치지 않습니다. 일반적으로 401은 Authentication 실패 후보이고 403은 인증된 Identity의 Authorization 실패 후보이지만, 앞단 Proxy나 Application이 자체 Status를 반환할 수도 있으므로 실제 응답 주체와 Log를 확인해야 합니다.

### Long-Term Token과 실제 Lifetime

#### 왜 필요한가

자동 프로그램은 매 요청마다 사람처럼 Browser Login을 수행하기 어렵습니다. 장기간 사용할 Credential이 필요하지만, 그것이 사람의 User Token에서 파생된 것인지 독립 Machine Identity인지에 따라 Identity와 권한 의미가 달라지므로 발급 경로와 Claim을 구별해야 합니다.

#### 핵심 용어

- Short-Lived User Access Token: 사람의 Login Flow에서 발급되는 상대적으로 짧은 수명의 User Credential
- Long-Term Token: 자동 호출에 사용할 목적으로 더 긴 수명으로 발급되는 Access Token
- Token Exchange: 이미 가진 Token과 Client Credential 등을 이용해 다른 Token을 발급받는 흐름
- Client Credentials Grant: User Login 없이 Client 자체의 Credential로 Token을 받는 OAuth 방식
- Kubernetes ServiceAccount Token: Kubernetes ServiceAccount Identity를 나타내는 Token
- azp: Token 발급에 참여한 Authorized Party/Client를 나타낼 수 있는 Claim

#### 비유

직원의 일반 출입증을 Short-Lived User Token, 반복 로그인 없이 오래 사용할 장기 출입증을 Long-Term Token으로 볼 수 있습니다. 장기 출입증이 자동문에서 사용된다고 해서 그 출입증이 기계 자체의 신원으로 바뀌는 것은 아닙니다. 누구의 신원에서 시작했는지를 봐야 합니다.

#### 본문

DKS-C 내부 자료는 Monitoring·OpenSearch 등 자동 호출에 사용할 Long-Term Access Token 발급 경로를 별도로 기록합니다.

```text
User Login
   ↓
Authorization Code
   ↓
Short-Lived User Access Token
   ↓
Token Exchange + Long-Term Client Credential
   ↓
Long-Term Access Token
   ↓
자동 프로그램의 Bearer Credential
```

이 경로의 출발점은 User Authentication입니다. 따라서 Kubernetes ServiceAccount Token 발급, 독립 Machine Identity의 Client Credentials Grant, 임의의 Refresh Token 연장, Client Secret 자체를 API Bearer Token으로 사용하는 것과 같은 것으로 취급하지 않습니다.

Long-Term Token의 Claim에는 Keycloak Realm Issuer, User Subject, 발급에 참여한 Long-Term Client, Audience가 함께 나타날 수 있습니다.

| Claim | Long-Term Token에서 구별할 대상 |
|---|---|
| iss | Token을 발급한 Keycloak Realm |
| sub·preferred_username | Token이 나타내는 User |
| azp | Exchange에 참여한 Client |
| aud | 수신 대상으로 지정된 API·Client |

Long-Term Client로 Exchange했다고 Issuer가 Client로 바뀌는 것이 아니고 자동 프로그램이 사용한다고 User Token이 ServiceAccount Token으로 바뀌는 것도 아닙니다. 한 발급 예시만으로 모든 Token에서 Subject·Audience·Group이 같은 방식으로 유지된다고 일반화하지 않습니다.

설정된 Lifetime과 실제 발급 결과도 구별합니다. 내부 Client 목록은 k8s-longterm-client-30/-90/-120/-180에 각각 30/90/120/180일 설정을 기록하지만 같은 자료의 예외 항목은 실제 Access Token이 365일로 발급된다고 기록합니다. 현재 자료만으로 Client Override가 Exchange Token에 적용되지 않는지, Realm·Exchange Policy가 365일을 강제하는지, Version·Extension 동작 차이인지, 기록 시점이나 대상 Client가 다른지를 확정할 수 없습니다.

따라서 Client 이름과 설정표는 의도 또는 설정 기록으로, 실제 발급 Token의 exp는 그 Token에 기록된 만료 시각으로, Resource Server의 응답은 현재 시점에 실제로 Token을 수용·거부한 결과로 구분합니다.

JWT Payload를 Base64url Decode하는 것은 Claim을 읽는 작업일 뿐 Signature 검증이 아닙니다. 예를 들어 exp 확인은 다음처럼 할 수 있지만 Token 원문·Client Secret은 Log나 문서에 출력하지 않습니다.

```python
import base64
import json
import os
from datetime import datetime, timezone

payload = os.environ["LONG_TERM_TOKEN"].split(".")[1]
payload += "=" * (-len(payload) % 4)
claims = json.loads(base64.urlsafe_b64decode(payload))
print(datetime.fromtimestamp(claims["exp"], timezone.utc).isoformat())
```

### Credential 배포·사용·폐기

#### 왜 필요한가

새 Token을 발급하는 것은 교체의 시작일 뿐입니다. 실제 프로그램이 새 값을 읽고 보호된 API에서 인증·권한·기능까지 성공해야 새 Credential이 사용되고 있다고 말할 수 있으며, 옛 Token이 저장소에서 사라졌다는 사실과 실제로 더 이상 사용할 수 없다는 사실도 구별해야 합니다.

#### 핵심 용어

- Bearer Token: 문자열을 가진 주체가 제시해 사용할 수 있는 Credential
- Secret·Environment·Config·External Store: Application이 Credential을 읽을 수 있는 대표 저장·전달 위치
- Reload·Restart·Re-read: 실행 중인 Process가 변경된 Credential을 다시 읽게 하는 방식
- Protected API: 실제 Authentication·Authorization을 요구하는 API
- Revocation: 이미 발급된 Credential을 더 이상 사용할 수 없도록 만드는 처리
- Local Validation: Resource Server가 Keycloak에 매 요청을 묻지 않고 Public Key 등으로 Token을 자체 검증하는 방식

#### 비유

새 출입증을 발급했다고 직원이 바로 새 카드를 들고 다니는 것은 아닙니다. 새 카드를 실제 사용자에게 전달하고 출입 시스템에서 사용되는지 확인해야 합니다. 예전 카드를 책상에서 치운 것과 중앙 출입 시스템이 그 카드를 즉시 거부하는 것도 별개입니다.

#### 본문

새 Token을 발급한 뒤에는 실제 프로그램이 읽는 Credential 저장 위치를 찾아 갱신해야 합니다.

```text
새 Token 발급
   ↓
Secret / Environment / Config / External Store 갱신
   ↓
Process Reload / Restart / Re-read
   ↓
새 Token으로 Protected API 호출
   ↓
Authentication + Authorization + 기능 성공
```

전달 방식마다 반영 조건이 다릅니다.

| 전달 방식 | Resource 변경 후 남는 조건 |
|---|---|
| Environment Variable | 기존 Process는 자동 갱신되지 않으므로 재기동 필요 가능 |
| Secret Volume File | kubelet 갱신 후 Application이 File을 다시 읽어야 함 |
| subPath Mount | 일반 Secret Volume과 갱신 동작이 다름 |
| Application Config File | Reload 기능이나 재기동 필요 가능 |
| External Secret Store | Fetch·Cache·Rotation 주기를 확인 |

Health Endpoint가 인증 없이 200을 반환하면 그 응답은 Token 유효성을 구분하지 못합니다. 실제 인증과 권한이 필요한 Protected API를 호출해 기대 Identity와 작업 결과를 확인해야 합니다.

Bearer Token은 문자열을 가진 주체가 제시할 수 있는 Credential입니다. Kubernetes Secret의 Base64 Encoding도 암호화가 아닙니다. 새 Token을 소비자에 반영하고 저장소에서 옛 문자열을 지워도 다른 Secret·Config, Process Memory, CI/CD Credential Store, Backup·Artifact, Log·Shell History 등에 복사본이 남을 수 있습니다.

또한 Resource Server가 JWT를 Public Key로 Local Validation한다면 Keycloak Logout·Client Secret 변경·원본 저장소 삭제가 이미 발급된 Token을 exp 전에 즉시 거부하는지 별도로 확인해야 합니다.

```text
옛 Token 저장소에서 제거
        ≠
모든 소비자가 새 Token 사용
        ≠
옛 Token이 더 이상 어디에도 존재하지 않음
        ≠
Resource Server가 옛 Token을 즉시 거부
```

즉시 폐기가 요구되면 Keycloak과 수신 서비스의 Revocation·Session·Policy 동작을 확인합니다.

인증 문제는 마지막으로 확인된 상태부터 다음 질문을 이어가면 범위를 줄일 수 있습니다.

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 증거 |
|---|---|---|
| ADFS Login 성공 | Keycloak Realm Session과 Client Flow가 생성됐는가? | Keycloak Event, Browser Redirect |
| Keycloak Login 성공 | 올바른 Client·Redirect URI로 Code가 발급됐는가? | Authorization Request·Redirect |
| Code 발급 | Token Endpoint 교환이 성공했는가? | Token Endpoint Status·Error |
| Token 발급 | Signature·Issuer·Audience·Expiration이 수신 서비스 기대와 맞는가? | Resource Server Auth Log, Token Metadata |
| Identity 확인 | 필요한 Group·Username Mapping이 맞는가? | Claim과 Server Mapping 설정 |
| Authentication 성공 | 요청 작업 권한이 있는가? | RBAC can-i, Authorization Log, 403 주체 |
| 새 Long-Term Token 발급 | 소비자가 실제 새 값을 읽는가? | Pod Spec·Secret Version·Process Reload |
| 새 Token으로 Health 200 | 인증이 필요한 API도 성공하는가? | Protected API Request와 Audit Log |
| 새 Token 사용 확인 | 옛 Token이 실제로 거부되는가? | Revocation/Session 정책과 별도 검증 |
| Client 설정표와 exp 불일치 | 어느 Policy·Version이 실제 Lifetime을 결정하는가? | Current Client/Realm/Exchange 설정, 발급 Token 비교 |

이 표는 “인증이 안 된다”는 하나의 증상을 Login·발급·검증·Mapping·권한·소비자 반영으로 분해하는 조사 순서입니다. 한 단계의 성공을 뒤 단계의 증거로 사용하지 않습니다.
