# 07. 운영 수명주기와 Certificate·Token·Node 교체 — 새 Resource는 언제 실제 기능을 인계받는가?

## 문서의 목적

이 문서는 DKS-C에서 Certificate·Long-Term Token·Control Plane Node·Worker Node를 교체할 때 새 Resource가 생성된 상태와 실제 통신·합의·Workload 기능을 인계한 상태를 구별하고, 기존 상태를 언제 제거할 수 있는지 설명합니다. 대상마다 구현은 다르지만 공통적으로 새 상태 준비, 소비자 반영, 실제 기능 검증, 기존 상태 제거라는 수명주기를 따릅니다.

핵심은 새 Secret 존재, 새 Token 발급, 새 VM Power On, 새 Node Ready 같은 중간 상태를 교체 완료와 동일시하지 않는 것입니다. 실제 완료는 새 상태가 기존 기능을 수행하고, 옛 상태를 제거한 뒤에도 필요한 기능이 유지되는지까지 확인한 결과로 판단합니다.

## 전체 인과 지도

운영 변경은 새 Resource를 만드는 것에서 시작하지만 거기서 끝나지 않습니다. 새 Certificate가 Secret에 저장돼도 Server가 Reload하지 않으면 실제 TLS는 옛 Certificate를 계속 제시할 수 있고, 새 Token이 발급돼도 소비자가 옛 값을 읽고 있으면 API 호출은 바뀌지 않습니다. 새 Control Plane VM과 Worker VM도 마찬가지입니다. VM이 생겼다는 사실만으로 etcd Quorum이나 Workload가 새 Node로 넘어간 것은 아닙니다. 그래서 새 상태가 실제 소비자에게 반영되고 그 상태로 TLS·Protected API·Quorum·사용자 Service가 정상 동작하는지 확인해야 합니다. 그 기능이 새 상태에서 안정적으로 이어진 뒤에야 옛 Certificate·Token·etcd Member·Worker Node를 제거할 수 있습니다. 이 문서는 이 공통 인수인계 구조를 먼저 잡고 Certificate, Token, Control Plane, Worker가 각각 어떤 증거로 기능 인계를 완료하는지 따라갑니다.

이 문서는 대형 운영센터의 교대 인수인계를 하나의 비유 세계로 사용합니다. 새 직원의 출근은 새 Resource 생성, 업무 시스템 로그인은 소비자 반영, 실제 업무 수행은 기능 인계, 이전 근무자의 퇴근은 기존 상태 제거에 대응합니다. 비유는 공통 수명주기를 이해하기 위한 보조 수단이며 실제 완료 판정은 TLS·API·etcd·Pod·Volume·Service 증거를 기준으로 합니다.

### 공통 기능 인계 수명주기

#### 왜 필요한가

운영 변경 대상마다 생성 방식은 다르지만 “새 것이 생겼다”와 “기존 기능이 새 것으로 넘어갔다”는 항상 다른 상태입니다. 이 둘을 분리해야 기존 상태를 너무 일찍 제거하거나 아직 옛 상태를 쓰는 소비자를 놓치는 위험을 줄일 수 있습니다.

#### 핵심 용어

- 생성: 새 Certificate·Token·VM·Machine 같은 Resource가 존재하는 상태
- 소비자 반영: 실제 Server·Process·Cluster가 새 값을 읽거나 새 Member·Node를 인식하는 상태
- 기능 인계: 새 상태가 TLS·API·Quorum·Workload 같은 요구 기능을 실제로 수행하는 상태
- 기존 상태 제거: 옛 Credential·Member·Node 없이도 기능이 유지됨을 확인한 뒤 옛 상태를 폐기하는 단계
- 완료 조건: 교체 작업을 끝났다고 판단하기 위해 실제로 확인해야 하는 기능적 증거

#### 비유

새 직원이 출근했다고 인수인계가 끝난 것은 아닙니다. 시스템에 로그인하고 실제 업무를 처리해 본 뒤, 이전 직원이 빠져도 업무가 유지돼야 교대가 완료됩니다.

#### 본문

운영 변경은 공통적으로 다음 네 층으로 나눌 수 있습니다.

| 층 | 공통 질문 | Certificate 예 | Token 예 | Node 예 |
|---|---|---|---|---|
| 생성 | 새 Resource가 존재하는가? | 새 Secret | 새 Token | 새 VM·Machine |
| 소비자 반영 | 실제 사용 주체가 새 값을 읽는가? | Server Reload | Process Credential 갱신 | kubelet·etcd·Scheduler 인식 |
| 기능 확인 | 새 상태가 요구 기능을 수행하는가? | TLS Handshake | Protected API 호출 | API Quorum·Pod Service |
| 기존 상태 제거 | 옛 상태가 없어도 기능이 유지되는가? | 옛 Cert·CA 제거 | 옛 Token 거부 | 기존 Member·Node 삭제 |

```text
새 Resource 존재
      ↓
소비자가 새 상태를 읽음
      ↓
새 상태로 실제 기능 수행
      ↓
기존 상태 제거 후에도 기능 유지

생성 성공 ≠ 기능 인계 완료
```

앞 층의 성공은 뒤 층의 충분조건이 아닙니다. 변경 계획에는 새 Resource를 만드는 작업뿐 아니라 누가 새 상태를 소비하는지, 어떤 실제 기능으로 인계를 검증할지, 기존 상태를 제거해도 되는 조건을 함께 적어야 합니다.

변경 대상별 완료 증거도 다릅니다.

| 변경 대상              | 새 상태 준비 증거                    | 기존 상태 제거 전 확인할 기능                       |
| ------------------ | ----------------------------- | --------------------------------------- |
| Server Certificate | 새 Certificate·Key가 Secret에 저장 | 실제 Client TLS에서 새 Certificate·Trust 확인  |
| Client Certificate | 새 Credential이 소비자에 반영         | Server가 새 Client Identity 수용            |
| Long-Term Token    | 새 Token과 exp 확인               | 소비자가 Protected API를 새 Token으로 호출        |
| Control Plane Node | 새 VM·Node 생성                  | etcd Member·Quorum과 API Health          |
| Worker Node        | 새 VM·Node Ready               | Pod Eviction·대체 Pod·Volume·Service Path |

공통 완료 기준은 새 Resource 존재가 아니라 기능 인계입니다.

### Certificate 교체

#### 왜 필요한가

Certificate가 새로 발급됐다고 실제 TLS Endpoint가 그 Certificate를 사용하고 있는 것은 아닙니다. Server가 새 Secret을 읽고 Client가 Chain·Hostname·CA를 신뢰하는지까지 확인해야 새 Credential이 실제 통신을 인계했다고 볼 수 있습니다.

#### 핵심 용어

- cert-manager Certificate: DNS/SAN·Secret·Issuer·Duration·renewBefore 등을 선언하는 Resource
- CertificateRequest: cert-manager가 Issuer에 실제 발급을 요청하는 Resource
- Secret: 발급된 Certificate와 Private Key를 저장하는 Kubernetes Resource
- Server Certificate: Client가 Server Identity를 확인하는 TLS Certificate
- Client Certificate: Server가 Client Identity를 검증할 때 사용하는 Certificate
- Root CA·Trust Store: Certificate Chain을 신뢰할지 판단하는 Root와 Client 측 신뢰 저장소
- Reload: 실행 중인 Process가 갱신된 Certificate Material을 다시 읽는 동작

#### 비유

새 출입증을 발급하는 것과 실제 출입문에서 그 출입증을 사용하는 것은 다릅니다. 출입문 장비가 새 목록을 읽고, 상대방도 새 발급기관을 신뢰해야 새 출입증이 실제 기능을 인계합니다.

#### 본문

Certificate는 TLS에서 Server·Client Identity와 Trust를 확인하는 데 사용됩니다. 어느 Certificate가 만료·불일치·미신뢰 상태인지에 따라 실패하는 연결도 다릅니다.

| Certificate·통신 | 역할 | 실패 시 영향을 받을 수 있는 연결 |
|---|---|---|
| API Server Server Certificate | Client가 kube-apiserver Identity 확인 | kubectl·kubelet·Controller API 접속 |
| API Server → etcd Client Certificate | API Server가 etcd에 Client로 인증 | Cluster State Read/Write |
| etcd Server·Peer Certificate | etcd Client·Member 간 TLS | etcd Query·Replication |
| API Server → kubelet Client Certificate | API Server가 kubelet API에 접속 | logs·exec 등 |
| front-proxy Client Certificate | Aggregated API Request 인증 | Extension API |
| kubelet Client Certificate | kubelet이 API Server에 Node Identity로 인증 | Node Status·Lease |
| kubelet Server Certificate | Client가 kubelet Server Identity 확인 | kubelet HTTPS |

Certificate 하나가 만료되면 Kubernetes 전체 Process가 즉시 정지한다고 일반화하지 않습니다. API Server Server Certificate와 etcd Peer Certificate는 서로 다른 연결을 끊을 수 있고, kubelet이 API Server에 상태를 보고하지 못한다고 이미 실행 중인 Container가 같은 순간 모두 종료되는 것도 아닙니다. DKS-C User Cluster가 실제로 어떤 방식으로 Certificate를 생성·회전하는지는 대상 관리형 VKS Version과 운영 절차를 확인해야 합니다.

내부 Certificate 현황에는 다음 설정이 기록되어 있습니다.

| 영역·예시 | Issuer | 기록된 Duration | Renew Window |
|---|---|---:|---:|
| Metric Root CA | selfsigned-root | 365일 | 3일 |
| Metric vmauth-server-cert | monitoring-hub-issuer | 90일 | 10일 |
| Log Root CA | logs-selfsigned-issuer | 365일 | 3일 |
| OpenSearch API/Admin/Node | logs-issuer | 90일 | 15일 |
| OpenTelemetry Gateway | logs-issuer | 90일 | 15일 |
| DKS Log/Metric/Event Agent | 영역별 Issuer | 90일 | 10일 |
| vm-operator-root-ca | vm-operator-root | 2658일 | 표에는 - |
| vm-operator-validation | vm-operator-issuer | 1908일 | 표에는 - |

OpenSearch Node 간 Certificate는 Coordinator 2, Master 3, Hot 2, Warm 1로 총 8개가 기록되어 있습니다. 같은 Renew Window에 들어간다고 갱신 시점이 겹칠 가능성은 있지만 Application Restart나 서비스 영향이 반드시 동시에 발생한다는 증거는 아닙니다. 내부 자료에는 Created/Renewal Time 누락, 계산 날짜 불일치, Renew -와 기본 Renew 설명의 충돌도 있으므로 표의 계산값만으로 현재 만료·자동 갱신 상태를 확정하지 않습니다.

cert-manager Certificate가 Ready가 되고 새 Certificate와 Private Key가 Secret에 저장되면 새 Certificate Material이 준비된 상태입니다. 그 뒤 실제 소비자가 새 값을 읽어야 합니다.

| 전달 방식 | Secret 변경 뒤 남는 조건 |
|---|---|
| Secret Volume File | kubelet이 갱신해도 Application이 File을 다시 읽어야 함 |
| subPath Mount | 일반 Secret Volume과 갱신 방식이 다름 |
| Environment Variable | 실행 중 Process에 자동 반영되지 않음 |
| Controller 자동 Reload | Watch·Reload가 실제 성공했는지 확인 |
| Manual Reload/Restart | 새 Process가 새 Secret을 읽는지 확인 |

따라서 Certificate Ready=True와 실제 Server가 새 Certificate를 제시하는 것은 별도 상태입니다. Root CA 교체에서는 Server Secret뿐 아니라 Client Trust Store가 중요합니다.

```text
새 Root CA
  ├─ 새 Server Certificate 서명
  └─ Client Trust Store에 새 CA 추가 필요

Server만 교체
  + Client가 새 CA를 신뢰하지 않음
  → TLS 실패 가능
```

Certificate 발급 경로와 실제 Endpoint 사용 상태도 나눠 확인합니다. 아래는 읽기 확인 예시이며 Private Key 원문은 출력하지 않습니다.

```bash
kubectl --context="$CLUSTER_CONTEXT" -n "$CERT_NAMESPACE" get certificate "$CERT_NAME" -o yaml
kubectl --context="$CLUSTER_CONTEXT" -n "$CERT_NAMESPACE" get certificaterequests -o wide
kubectl --context="$CLUSTER_CONTEXT" -n "$CERT_NAMESPACE" get events
```

status.notAfter, status.renewalTime, Ready Condition, CertificateRequest 상태를 확인하며 Condition 배열 첫 항목이 항상 Ready라고 가정하지 않습니다.

실제 Endpoint가 제시하는 Certificate는 다음과 같이 확인할 수 있습니다.

```bash
openssl s_client -connect "$TLS_HOST:$TLS_PORT" -servername "$TLS_HOST" </dev/null 2>/dev/null | openssl x509 -noout -dates -serial -fingerprint -sha256
```

이 출력은 해당 연결에서 받은 Certificate를 보여주지만 Hostname Validation 전체 성공, 전체 Trust Chain 검증, Application Request 성공, LB 뒤 모든 Endpoint가 동일 Certificate를 사용하는 것까지 자동으로 증명하지는 않습니다.

Issuer가 Ready하지 않거나 webhook/API 통신이 실패하면 CertificateRequest가 진행되지 않을 수 있습니다. Secret은 새 값인데 Endpoint가 옛 Certificate를 제시하면 Issuer보다 소비자 Reload와 Replica별 반영 상태를 조사합니다.

### Long-Term Token 교체

#### 왜 필요한가

Token도 새 문자열이 발급됐다고 실제 자동 프로그램이 그 값을 사용하는 것은 아닙니다. 소비자 저장소와 Process에 새 값을 반영하고 실제 Protected API를 새 Token으로 호출한 뒤, 옛 Token의 잔존과 수용 여부까지 확인해야 교체가 완료됩니다.

#### 핵심 용어

- Long-Term Token: 장기간 자동 호출에 사용할 목적으로 발급되는 Bearer Credential
- Token Exchange: 기존 User Token과 Long-Term Client 등을 이용해 장기 Token을 발급받는 흐름
- exp: Token Payload에 기록된 만료 시각
- Protected API: Authentication과 Authorization이 실제 필요한 API
- Revocation·Session Policy: 옛 Token의 유효성을 종료하는 방식에 영향을 줄 수 있는 정책
- Local Validation: Resource Server가 Public Key 등으로 Token을 자체 검증하는 방식

#### 비유

새 출입증을 발급해도 직원이 실제로 새 카드를 들고 다니기 전까지 업무는 옛 카드에 의존할 수 있습니다. 옛 카드를 서랍에서 없앴다고 중앙 출입 시스템이 그 카드를 즉시 거부하는 것도 아닙니다.

#### 본문

Certificate와 Long-Term Token은 발급 메커니즘은 다르지만 교체 수명주기는 비슷합니다.

```text
새 Credential 생성
   ↓
소비자 저장소 반영
   ↓
Process가 새 Credential 사용
   ↓
실제 보호 기능 호출 성공
   ↓
옛 Credential 폐기
```

Certificate는 cert-manager·Issuer가 Certificate/Key를 Secret에 저장하지만 Long-Term Token은 User Login·단기 Token·Long-Term Client Token Exchange 흐름으로 발급됩니다. 내부 Long-Term Token 흐름은 User Login → Authorization Code → Short-Lived Access Token → Long-Term Client Token Exchange → 발급 Token exp 확인 → 소비자 저장소 반영 → Protected API 새 Token 사용 확인으로 기록되어 있습니다.

Client 이름·설정 기간과 실제 365일 발급 기록이 충돌하므로 교체 일정은 이름이 아니라 실제 exp와 Current Policy를 기준으로 정합니다. JWT Payload Decode는 Claim 확인일 뿐 Signature·Audience·Authorization 검증이 아닙니다.

새 Token을 Secret에 저장해도 Environment Variable을 읽는 Process는 재기동 전 옛 값을 계속 사용할 수 있습니다. File Mount라도 Application이 다시 읽지 않으면 실제 Request는 옛 Token을 사용할 수 있습니다.

옛 Token 저장소에서 문자열을 삭제했다고 이미 복사된 Bearer JWT가 exp 전에 반드시 무효화되는 것은 아닙니다. 즉시 거부가 필요하면 Keycloak과 Resource Server의 Revocation·Session·Local Validation 동작을 확인합니다.

```text
새 Token 발급
   ↓
소비자 반영
   ↓
실제 Authentication·Authorization API 성공
   ↓
옛 Token 사용처·복사본 확인
   ↓
Revocation·Session Policy에 따라 폐기
```

Token의 발급·Claim·소비자 반영에 대한 세부는 [06. 통합 신원·인증과 무인 서비스 Token](06.%20통합%20신원%C2%B7인증과%20무인%20서비스%20토큰.md)에서 이어집니다.

### Control Plane 교체

#### 왜 필요한가

새 Control Plane VM이 생겼다고 Cluster의 합의와 API 기능을 인계한 것은 아닙니다. 새 etcd Member가 실제 상태를 따라잡고 Voting Member로 참여한 뒤, 기존 Member를 제거해도 Quorum과 Kubernetes API가 유지되는지 확인해야 합니다.

#### 핵심 용어

- etcd Member: etcd Cluster에 참여하는 Server
- Voter: etcd 합의에 Vote하는 정식 Voting Member
- Learner: Replication을 따라잡지만 아직 Vote하지 않는 Member
- Quorum: 합의를 진행하는 데 필요한 Voting Member의 최소 과반수
- Replication: 새 Member가 기존 etcd Data를 따라잡는 과정
- Endpoint Health: etcd Endpoint가 요청에 정상 응답하는 상태
- CAPI: Cluster와 Machine Lifecycle을 Controller로 조정하는 Cluster API

#### 비유

관제실의 의사결정 멤버가 etcd Voter이고, 필요한 과반수가 Quorum입니다. 새 직원이 관제실에 들어왔다고 즉시 투표권을 갖는 것은 아닙니다. 기록을 따라잡고 정식 멤버가 된 뒤 이전 멤버가 빠져도 과반수와 관제 기능이 유지돼야 합니다.

#### 본문

CAPI Rolling Update나 Machine 교체는 새 Machine·VM을 생성하고 기존 Machine을 제거하는 흐름을 사용할 수 있습니다. 그러나 새 VM 존재는 기존 Node의 기능 인계 증거가 아닙니다.

Control Plane이 인계해야 할 핵심 기능은 kube-apiserver·Controller·Scheduler와 etcd Membership·Quorum입니다. etcd는 Voting Member의 과반수가 정상적으로 통신해야 합의를 진행합니다.

```text
quorum = floor(voting_members / 2) + 1
```

| etcd 구성 | 필요한 Quorum | 판단 |
|---|---:|---|
| Voter 3 | 2 | 2개 이상 정상이어야 합의 가능 |
| Voter 4 | 3 | 3개 이상 정상이어야 합의 가능 |
| Voter 3 + Learner 1 | 2 | Learner는 Vote하지 않으므로 3 Voter 기준 |

새 Control Plane VM이 생겨 총 VM이 네 대가 돼도 새 etcd Member가 Learner이거나 Member 자체가 아니라면 Voting Member 수가 네 개가 된 것이 아닙니다.

```text
새 Control Plane VM / Node
        ↓
etcd Member 추가
        ↓
Learner Replication
        ↓
Voter Promotion
        ↓
Voting Member 과반수 유지
        ↓
Kubernetes API Health
        ↓
기존 Member 제거 가능 판단

VM 수 증가 ≠ Voting Member 수 증가
```

승인된 Endpoint와 Credential로 Member와 Endpoint 상태를 읽는 예시는 다음과 같습니다.

```bash
etcdctl --endpoints="$ETCD_ENDPOINTS" --cacert="$ETCD_CA"   --cert="$ETCD_CLIENT_CERT" --key="$ETCD_CLIENT_KEY" member list -w table

etcdctl --endpoints="$ETCD_ENDPOINTS" --cacert="$ETCD_CA"   --cert="$ETCD_CLIENT_CERT" --key="$ETCD_CLIENT_KEY" endpoint status -w table
```

이 명령은 읽기 확인 예시이며 CAPI가 관리하는 Member를 사람이 임의로 Add/Remove하라는 절차가 아닙니다. VM 개수만으로 Quorum Risk를 설명하지 않고 Member ID, Voter/Learner, Replication, Endpoint Health, API 응답을 연결해서 봅니다.

### Worker 교체

#### 왜 필요한가

새 Worker가 Node Ready라고 보고해도 기존 Workload 기능이 이미 새 Worker로 넘어갔다는 뜻은 아닙니다. 기존 Node의 Pod를 안전하게 Eviction하고, 대체 Pod와 Volume·Service Endpoint가 새 위치에서 준비되고, 실제 사용자 Request까지 성공해야 기존 Worker를 제거할 수 있습니다.

#### 핵심 용어

- Cordon: 기존 Node에 새 Pod가 Scheduling되지 않도록 막는 상태
- Drain: 기존 Node의 Pod Eviction을 요청해 Workload를 다른 Node로 이동시키는 과정
- PDB(PodDisruptionBudget): 자발적 중단 중 유지해야 할 Available Pod 수를 보호하는 정책
- Eviction: Kubernetes가 Pod를 안전하게 종료·이동하도록 요청하는 작업
- Volume Detach·Attach·Mount: Persistent Volume을 기존 Node에서 떼고 새 Node에서 사용할 수 있게 연결하는 과정
- Service Endpoint: Service가 Traffic을 전달할 Ready Pod 목록
- Leader Lease: Application Leader Election에서 현재 Leader가 역할 소유권을 나타낼 때 사용할 수 있는 Lease

#### 비유

새 작업자가 현장에 도착하는 것이 Node Ready라면, 장비와 작업물 이동은 Pod·Volume 인계이고 고객 업무가 새 작업자를 통해 정상 처리되는 것은 Service Endpoint와 실제 Request 성공에 해당합니다. 새 작업자가 출근한 것만으로 이전 작업자를 바로 철수시킬 수 없습니다.

#### 본문

Machine 삭제 과정은 설정과 Version에 따라 Node Drain, Volume Detach 대기, Infrastructure Resource 삭제를 수행할 수 있습니다. Drain은 기존 Node에 새 Pod가 배치되지 않게 하고 실행 중 Pod의 Eviction을 요청합니다. PDB는 자발적 중단에서 유지해야 할 Available Pod 수를 보호합니다.

disruptionsAllowed=0을 곧바로 잘못된 설정이라고 결론내리지 않습니다. 현재 Replica·Ready 상태에서 더 Eviction하면 가용성 조건을 깨기 때문에 정상적으로 차단하는 것일 수 있습니다.

Worker 교체 상태는 다음처럼 나뉩니다.

| 상태 | 실제 의미 | 아직 남은 조건 |
|---|---|---|
| 새 Worker VM 생성 | 인프라 VM 존재 | Node 등록·Ready |
| 새 Node Ready | kubelet이 Cluster에 참여 | Workload 인계 |
| 기존 Node Drain 시작 | Eviction 요청 진행 | PDB·종료·Volume 처리 |
| 기존 Pod 종료 | Process 종료 | 대체 Pod 생성·Ready |
| Volume Detach 완료 | 기존 Node 연결 정리 | 새 Node Attach·Mount |
| 대체 Pod Ready | Pod Ready Condition 만족 | Service Endpoint·기능 |
| Endpoint 반영 | Traffic 대상에 포함 | 실제 사용자 Request 성공 |

```text
새 Worker VM / Node Ready
        ↓
기존 Node Cordon / Drain
        ↓
Pod Eviction 허용
        ↓
대체 Pod Scheduling / Ready
        ↓
Volume Detach / Attach / Mount
        ↓
Service Endpoint 반영
        ↓
실제 사용자 Request 성공
        ↓
기존 Node 제거 가능 판단
```

따라서 Node 수를 N→N+1→N으로 맞추거나 Eviction이 끝났다는 사실만으로 교체 완료와 Service 복구를 선언하지 않습니다.

읽기 확인 예시는 다음과 같습니다.

```bash
kubectl --context="$MANAGEMENT_CONTEXT" -n "$MACHINE_NAMESPACE" get machines,machinedeployments -o wide
kubectl --context="$MANAGEMENT_CONTEXT" -n "$MACHINE_NAMESPACE" get machine "$MACHINE_NAME" -o yaml
kubectl --context="$USER_CONTEXT" get pods -A --field-selector="spec.nodeName=$NODE_NAME"
kubectl --context="$USER_CONTEXT" get pdb -A
```

CAPI Controller의 Drain을 kubectl drain CLI와 동일한 Flag로 실행한다고 가정하지 않습니다. Machine Condition·Event에서 Eviction, Pre-drain Hook, Volume Detach 가운데 무엇을 기다리는지 확인합니다.

별도 Xi'an 운영 자료의 Tower 사례는 Application Leader Election과 Rolling Update 조건이 서로 기다리는 교착을 기록합니다.

```text
기존 Pod
  └─ Leader Lease를 계속 갱신

새 Pod
  └─ Leader Lease를 얻어야 Ready

Deployment Rolling Update
  └─ 새 Pod가 Ready여야 기존 Pod 종료

결과
기존 Pod가 살아 있어 Lease 유지
→ 새 Pod는 Lease를 못 얻어 NotReady
→ Controller는 기존 Pod를 내리지 않음
```

이 사례의 일반 교훈은 새 Pod가 존재하는 것과 기존 역할을 인계한 것은 다르며, Application Leader Election 조건과 Kubernetes Rollout 조건이 교착할 수 있다는 것입니다. 그러나 모든 Lease 기반 Workload에 같은 교착이 생긴다는 근거도 아니고, CAPI Worker Drain에서 같은 순서로 재현된다는 근거도 아니며, Replica 0→1 복구안을 다른 DKS-C Component에 적용할 근거도 아닙니다. 원자료의 시간·업무 영향 수치를 다른 환경에 보장하지도 않습니다. 실제 Application의 Lease 소유권, Readiness 조건, Rollout Strategy, 중단 허용, 복구 승인부터 확인합니다.

### 변경 문제를 마지막 상태에서 좁히기

Certificate·Token·Node 교체는 대상이 다르지만 장애 조사는 마지막으로 확인된 상태와 아직 확인되지 않은 다음 기능을 이어가는 방식으로 공통화할 수 있습니다.

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 증거 |
|---|---|---|
| Certificate Ready 아님 | Issuer·CertificateRequest 중 어디서 막혔는가? | Condition, Request, Event |
| Secret은 새 Certificate 보유 | 소비자가 새 File을 읽었는가? | Pod Mount·Reload·Process Start Time |
| 일부 TLS 연결만 새 Certificate | Replica·LB Endpoint별 반영이 다른가? | 반복 연결, Backend 식별, Fingerprint |
| 새 Token 발급 | 실제 소비자 저장소와 Process가 새 값을 읽는가? | Secret Version, Env/Volume 방식, Restart |
| 새 Token으로 Health 200 | Protected API에서 Authn·Authz가 성공하는가? | 인증 필수 API·Audit Log |
| 옛 Token 저장소 제거 | Resource Server가 옛 Token을 거부하는가? | Revocation·Session·실제 호출 |
| 새 Control Plane VM 생성 | etcd Member인가, Learner인가, Voter인가? | Member List·Endpoint Status |
| 새 Voter 정상 | 기존 Member 제거 후 Quorum이 유지되는가? | Quorum 계산·API Health |
| 새 Worker Node Ready | 기존 Workload를 인계했는가? | Drain·Pod·Volume·Endpoint |
| 대체 Pod Ready | 사용자 Service Path가 정상인가? | 실제 Request·Response |
| Rollout이 멈춤 | Infra 부족인가 PDB인가 App Leader 조건인가? | Event·PDB·Lease·Readiness |

이 표는 변경 종류를 하나의 절차로 강제하는 것이 아니라, 각 대상에서 “새 상태 준비”와 “실제 기능 인계” 사이의 미확인 구간을 찾기 위한 조사 도구입니다.
