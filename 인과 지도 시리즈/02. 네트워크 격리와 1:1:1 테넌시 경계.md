# 02. 네트워크 격리와 1:1:1 테넌시 경계 — 주소가 나뉘면 통신도 분리되는가?

## 문서의 목적

도시에서 구역마다 도로와 주소를 따로 배정해도 그 구역의 차량이 어디로든 갈 수 있는 것은 아닙니다. 목적지까지 도로가 이어져야 하고, 검문 규칙이 통행을 허용해야 하며, 돌아오는 길도 맞아야 합니다. 주소 배정표만으로 실제 통행을 판정하면 ‘길이 있다’와 ‘지나갔다’를 혼동하게 됩니다.

이 문서는 DKS-C의 User Cluster·Supervisor Namespace·VPC 대응에서 출발해 SNAT, 동일 VPC와 VPC 사이의 통신, 구성 상태와 실제 패킷 관측을 연결합니다. 비유는 **도시의 도로·주소·검문소**로 통일합니다. 주소는 IP, 연결 도로는 Route, 통행 규칙은 정책, 출입구의 출발지 표기 변경은 NAT에 대응시키되, 비유의 도로가 있다는 이유만으로 실제 네트워크 통신을 보장하지 않습니다.

> 자료 범위: 지정된 02번 원문과 그 안에 인용된 DKS-C 운영·CCI·인프라 기록입니다. 1:1:1 배치와 SNAT 주소 수는 해당 자료의 구성 기록이며, 이번에 새로 측정한 모든 Cluster의 상태나 보편적인 VPC 규칙은 아닙니다. [S1–S3]

## 전체 인과 지도

구역을 구분하면 주소의 소속을 관리할 수 있습니다. 그러나 구역 이름만으로 그 안의 건물에 어떤 전력과 도로가 배정됐는지까지 정해지는 것은 아닙니다.

DKS-C는 User Cluster의 실행 경계를 Supervisor Namespace의 자원 범위와 VPC의 네트워크 범위에 연결합니다. 기록의 User Cluster : Supervisor Namespace : VPC = 1:1:1은 이 대응을 나타냅니다. Project와 Transit Gateway는 여러 VPC를 연결·관리하는 별도의 상위 관계입니다.

구역 안의 차량이 외부로 나갈 때 내부 주소 대신 출구에서 부여한 주소로 식별될 수 있습니다. 출구 주소를 받았다는 사실과 실제 그 주소로 통행했다는 사실은 다릅니다.

SNAT은 외부로 향하는 패킷의 출발지 주소를 변환합니다. `networkInfos`에 기록된 SNAT IP는 할당 정보이며, 특정 통신에 실제 적용됐는지는 NAT 세션과 전후 패킷으로 확인합니다. 상대가 응답하더라도 반환 경로와 변환 상태가 맞아야 출발지까지 응답이 돌아옵니다.

같은 구역 안의 이동과 구역 사이의 이동은 지나가는 도로와 검문 조건이 다릅니다. 구역 사이 연결 시설이 있어도 실제 목적지 도로가 빠져 있으면 통행하지 못합니다.

동일 VPC의 VM 사이 통신과 Transit Gateway 등을 통한 VPC 간 통신을 구분해야 합니다. VPC 연결 객체, Route, 정책, NAT 조건을 읽고 실제 패킷의 출발·전달·도착·반환을 대조해야 격리와 통신 성공을 판단할 수 있습니다.

### VPC와 테넌트의 대응

하나의 건물에 도로·주소 구역 하나와 자원 허가 하나를 연결하면 그 건물이 사용하는 범위를 찾기 쉬워집니다. 하지만 그 상위 행정구역에는 다른 건물과 도로 구역도 함께 속할 수 있습니다.

DKS-C의 CCI 기록은 User Cluster마다 Supervisor Namespace와 VPC를 하나씩 대응시킵니다. Supervisor Namespace는 VM 자원 사용 범위이고, VPC는 Private IP와 가상 Network의 범위입니다. Project는 여러 Supervisor Namespace와 권한을 묶는 상위 관리 단위이므로 User Cluster와 같은 개수라고 가정하지 않습니다. [S1, S2]

구역의 내부 주소, 다른 구역으로 나갈 연결 도로의 주소, 외부에 드러나는 출입구 주소는 쓰임이 다릅니다. 주소를 모두 ‘외부 IP’라고 부르면 어느 경계에서 문제가 생겼는지 구분할 수 없습니다.

원문에는 **Private, Private TGW, External IPBlock**이 구분되어 있습니다. IPBlock은 주소 풀이고 Limit은 할당에 관련된 한도·정책입니다. VM의 내부 주소, Transit Gateway 연결용 주소 범위, 외부에 사용할 주소를 같은 값으로 취급하지 않습니다. VPC가 어느 풀과 정책을 참조하는지는 해당 객체의 실제 연결에서 읽습니다. [S2, S3]

| 대상 | 나타내는 범위 | 자동으로 증명하지 않는 것 |
|---|---|---|
| User Cluster | Kubernetes 실행·수명주기 단위 | 특정 목적지까지의 통신 |
| Supervisor Namespace | VM·Storage와 허용 자원 범위 | VPC Route 설치와 패킷 전달 |
| VPC | IP와 가상 Network의 소속 | 모든 VM·Pod·포트 사이의 통신 |
| Project | 여러 자원 범위의 상위 관리 | User Cluster와의 1:1 대응 |
| Transit Gateway | 여러 VPC의 연결을 맡는 경계 | 필요한 Route·정책·반환 경로의 완성 |
| IPBlock·Limit | 주소 풀과 할당 조건 | 실제 NAT 세션과 목적지 도착 |

한 행정구역의 여러 도로 구역이 공동 연결 허브를 사용할 수 있습니다. 건물마다 도로 구역을 하나씩 준다는 규칙과 연결 허브가 여러 도로 구역을 받는다는 관계는 모순이 아닙니다.

원문에는 **Project : Transit Gateway : VPC = 1:1:N**도 기록되어 있습니다. User Cluster : Supervisor Namespace : VPC = 1:1:1은 개별 Cluster의 대응이고, 1:1:N은 상위 Project와 Transit Gateway가 여러 VPC를 연결하는 관계입니다. 어느 관계의 개수인지 먼저 구분해야 합니다. [S2]

```text
구성 기록의 대응 관계 — 패킷 경로 또는 생성 순서가 아님
Project
└─ Transit Gateway
   ├─ VPC A ↔ User Cluster A / Supervisor Namespace A
   ├─ VPC B ↔ User Cluster B / Supervisor Namespace B
   └─ VPC N ↔ User Cluster N / Supervisor Namespace N

개별 Cluster의 대응: User Cluster : Supervisor Namespace : VPC = 1:1:1
상위 연결 관계:      Project : Transit Gateway : VPC = 1:1:N
```

### SNAT과 실제 외부 통신

구역의 차량이 외부로 나갈 때 출입구에서 내부 차량 번호 대신 외부용 표기를 붙일 수 있습니다. 목적지에서 본 번호는 원래 내부 번호와 다르므로 양쪽 기록을 연결할 때 표기 변경 내역이 필요합니다.

SNAT은 통신 패킷의 출발지 주소를 변환하는 기능입니다. 원문은 VM의 외부 통신에 대해 **VPC : SNAT External IP = 1:1** 구성을 기록합니다. 이 기록을 ‘Pod 하나마다 External IP 하나’, ‘모든 종류의 트래픽이 반드시 같은 NAT를 사용한다’ 또는 ‘Worker를 늘릴 때마다 SNAT IP도 하나씩 추가된다’로 확대하지 않습니다. [S1, S2]

출입구 주소가 허가서에 적혀 있어도 그 순간 차량이 출입구를 지나간 것은 아닙니다. 주소 배정, 출입 기록, 다음 검문소의 통과 기록, 목적지 도착 기록은 서로 다른 증거입니다.

`networkInfos`의 SNAT IP는 오케스트레이션이 조회·전달한 주소 정보입니다. 특정 연결에서 그 주소가 실제 사용됐는지는 NAT 세션이나 패킷 관측이 필요합니다. 아래 단계는 관측할 증거의 구분이지 각 자료가 다음 자료의 존재를 보장한다는 뜻은 아닙니다.

| 관측 | 확인되는 것 | 아직 남는 것 |
|---|---|---|
| SNAT IP 할당·`networkInfos` | 사용하도록 배정된 주소 | 실제 연결에서의 적용 |
| NAT 세션·변환 전후 패킷 | 해당 연결의 주소·포트 변환 | 다음 경계의 허용과 목적지 도착 |
| 방화벽 허용 기록 | 관측된 정책 경계에서 허용됨 | 목적지 Listener·애플리케이션 처리 |
| 목적지 수신·응답 기록 | 목적지까지 도달하고 처리됨 | 원래 출발지까지의 정상 반환 |

외부로 나가는 차량과 돌아오는 차량을 맞추려면 차량 번호뿐 아니라 어느 출구에서 언제 어디로 갔는지도 알아야 합니다. 시간대와 목적지가 다르면 비슷한 기록을 같은 이동으로 잘못 연결할 수 있습니다.

패킷을 연결할 때는 **출발지 IP·포트, 목적지 IP·포트, 프로토콜의 5-tuple과 시각**을 함께 사용합니다. NAT 전후에는 출발지 주소나 포트가 달라질 수 있으므로 변환 내역을 함께 봅니다. 목적지 응답이 변환 상태와 맞는 경로로 돌아와야 연결이 완료됩니다. 송신만 관측한 상태를 왕복 성공으로 쓰지 않습니다.

```text
하나의 연결에서 비교할 관측 지점
VM 내부 출발지:포트 → NAT 경계 → 변환된 출발지:포트 → 목적지:포트
                         │
                   변환·세션 기록

돌아오는 응답도 해당 세션과 반환 경로에 연결되어야 한다.
각 지점에서 시간과 변환 전후 tuple을 맞춰 비교한다.
```

검문 기록에서 차량이 안 보인다고 곧바로 그 검문소가 차량을 막았다고 할 수는 없습니다. 다른 출구를 이용했거나 기록 시간·번호를 잘못 찾았거나 차량이 아직 출발하지 않았을 수도 있습니다.

NAT 세션이 보이지 않는 경우에도 바로 ‘NAT 장애’로 확정하지 않습니다. 실제 트래픽 발생 여부, 관측 시간, 필터에 사용한 변환 전후 주소, 다른 경로 사용 가능성, 세션 보존 시간 등을 구분해야 합니다. 이 구분은 후보를 무한히 늘리기 위한 것이 아니라 ‘미관측’을 특정 장비의 실패와 동일시하지 않기 위한 것입니다.

### 동일 VPC와 VPC 사이의 통신

같은 도로 구역에 별도의 건물 간 검문소가 없다고 해서 모든 방의 문까지 열려 있는 것은 아닙니다. 도로 경계의 정책과 건물 내부 출입 규칙은 다른 수준입니다.

원문에는 동일 VPC의 VM 간에 VM Security Group 기반 분리가 없다는 설명이 있습니다. 이 범위의 기록을 ‘모든 통신이 무조건 가능하다’로 바꾸면 안 됩니다. Pod 수준의 CNI 정책, OS 방화벽, Listener와 애플리케이션 인증 등 다른 조건은 별도입니다. 동일 VPC라는 소속은 해당 통신의 모든 정책과 포트 상태를 설명하지 않습니다. [S3]

구역 사이를 연결하려면 연결 허브에 구역을 붙이고 목적지 방향을 가리키는 도로 표지가 필요합니다. 연결 신청서가 접수된 것과 표지가 실제 현장에 설치된 것은 다릅니다.

VPC 간 통신에서는 `VPCConnectivityProfile`, `VPCAttachment`, Transit Gateway 등의 연결 관계를 확인합니다. ConnectivityProfile은 연결에 사용할 구성을, Attachment는 대상 연결의 부착 관계를 표현하는 자료로 읽습니다. Private TGW 주소 풀과 Route Table의 목적지·Next Hop을 함께 대조해야 실제 전달 경로를 설명할 수 있습니다. 특정 객체가 존재한다는 사실만으로 필요한 Route가 모두 설치됐다고 판단하지 않습니다. [S2, S3]

```text
VPC A의 출발지
   │ 실제 Route·정책·연결 상태에 따른 전달
   ▼
VPC 연결 경계 / Transit Gateway
   │ 실제 Route·정책·연결 상태에 따른 전달
   ▼
VPC B의 목적지

응답: VPC B에서 A로 돌아가는 Route와 정책도 별도로 성립해야 함
설정 객체의 존재와 실제 패킷 전달은 다른 관측이다.
```

공용 도로와 도시 밖 도로가 만나는 큰 교차로가 있어도 모든 차량이 반드시 그 교차로를 지나지는 않습니다. 길의 이름을 나열하기보다 실제 목적지에 대해 선택된 길을 보아야 합니다.

상위 NSX 경계의 Tier-0 같은 라우팅 계층도 해당 배치의 연결 구조 안에서 해석합니다. Transit Gateway, Tier-0, NAT가 문서에 등장한다는 이유만으로 모든 트래픽에 동일한 직렬 경로를 강제하지 않습니다. 출발지와 목적지에 맞는 실제 Route·Next Hop·정책을 기준으로 필요한 경계를 연결합니다.

### 구성 상태와 실제 관측

행정 시스템의 ‘배정 완료’와 현장의 ‘통행 가능’ 표시는 서로 다른 질문에 답합니다. 장부 두 개의 숫자가 다르면 하나를 임의로 정답으로 고르기보다 무엇을 언제 집계했는지부터 맞춰야 합니다.

VPC와 연결 객체의 준비 상태는 구성 제어 평면의 결과입니다. 실제 송수신은 데이터 경로에서 확인해야 합니다. 원문에는 `VPCLimitState`의 consumed와 `VPCIPAddressUsage`의 allocated가 일치하지 않는 사례도 기록되어 있습니다. 서로 다른 범위·의미·갱신 시각을 가진 수치를 이름이 비슷하다는 이유로 같은 값으로 취급하거나, 한쪽만으로 장애와 사용량을 확정하지 않습니다. [S2]

목적지에서 차량이 보이지 않을 때는 출발지, 출입구, 중간 검문소, 목적지, 반환 경로 가운데 마지막으로 확인된 지점을 찾아야 합니다. 이 점검 순서는 도로를 새로 여는 작업 순서와는 다릅니다.

통신 조사에서도 아래 표를 관측 분기로 사용합니다. 사용자가 조회를 끝내야 네트워크가 다음 동작을 하는 것은 아닙니다. 동일 연결의 시각·주소 변환을 맞추면서 누락된 구간만 좁히는 것이 목적입니다.

| 관측된 상태 | 먼저 구분할 질문 | 필요한 증거 |
|---|---|---|
| 이름으로만 접속 실패 | 원하는 주소로 해석됐는가? | DNS 결과, FQDN, 실제 VIP/IP |
| 출발지 송신이 불명확 | 요청이 실제 발생했는가? | 출발지 요청 시각·목적지·송신 기록 |
| SNAT IP 정보만 있음 | 그 연결에 실제 SNAT이 적용됐는가? | 변환 전후 패킷·NAT 세션 |
| 출발했으나 다음 경계에서 보이지 않음 | Route·Next Hop·필터가 같은 연결을 가리키는가? | Route Table, 경계별 tuple·시각 |
