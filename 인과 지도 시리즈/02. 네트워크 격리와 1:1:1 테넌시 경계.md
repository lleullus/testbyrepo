# 02. 네트워크 격리와 1:1:1 테넌시 경계 — 어떤 주소가 바뀌고 어떤 조건이 있어야 경로가 열리는가?

## 문서의 목적

이 문서는 DKS-C에서 User Cluster마다 VPC를 나누는 이유부터 시작해, VPC가 어떤 주소와 Network 범위를 정하는지, 외부 통신에서 SNAT이 무엇을 바꾸는지, 같은 VPC와 다른 VPC의 경로가 왜 달라지는지, 마지막으로 설정 Resource와 실제 Packet 흐름을 어떻게 구별해 통신 성공과 장애 지점을 판단하는지 설명합니다.

핵심은 VPC·SNAT·Transit Gateway 같은 설정이 존재한다는 사실과 특정 Packet이 실제로 NAT·Routing·정책 허용을 거쳐 목적지와 왕복했다는 사실을 같은 것으로 보지 않는 것입니다.

## 전체 인과 지도

User Cluster를 따로 만들면 Kubernetes 실행 경계는 나뉘지만 Network 경계까지 자동으로 정해지는 것은 아닙니다. 각 Cluster의 VM이 사용할 주소와 Route 범위를 구별하려면 VPC가 필요합니다. VPC 안에서 Private IP를 받은 VM이 외부 Network와 통신하려면 다음 문제가 생깁니다. 내부 주소를 외부가 그대로 식별할 수 없기 때문에 경계에서 사용할 Source 주소가 필요하고, DKS-C에서는 VPC별 SNAT External IP가 그 역할을 맡습니다. 그렇다고 주소가 변환됐다는 사실만으로 목적지에 도달한 것은 아닙니다. Packet이 같은 VPC 안에 머무는지, 다른 VPC나 외부 Network로 나가는지에 따라 필요한 연결 구조와 Route가 달라지고, 정책과 반환 경로까지 맞아야 왕복 통신이 성립합니다. 마지막으로 VPC나 Attachment가 Ready라는 설정 상태만으로 실제 Packet 경로를 확정할 수는 없습니다. 그래서 Control Plane의 설정과 Data Plane의 Session·Flow·Log를 함께 보면서 마지막으로 확인된 지점과 다음 미확인 지점을 연결해야 합니다.

이 문서는 도시 도로망과 검문소를 하나의 비유 세계로 사용합니다. 각 절에서는 필요한 핵심 대응만 먼저 밝히고, 이후에는 실제 Network Resource와 Packet 흐름을 중심으로 설명합니다. 비유는 구조를 잡기 위한 보조 수단이며 실제 경로와 통신 성공 여부는 Route·NAT·Session·Log 같은 증거를 기준으로 판단합니다.

### VPC와 1:1:1 경계

#### 왜 필요한가

User Cluster가 별도의 Control Plane과 Worker를 가진다고 해도 그 VM이 어떤 Private IP와 가상 Network 범위를 사용할지는 아직 정해지지 않습니다. 테넌트마다 Network 주소와 Route 범위를 구별하려면 Cluster의 실행 경계를 실제 Network 경계에 연결해야 합니다.

#### 핵심 용어

- VPC: User Cluster VM이 사용할 Private IP와 가상 Network 범위를 제공하는 네트워크 경계
- Supervisor Namespace: User Cluster VM의 Compute·Storage Quota와 VM Class 범위를 연결하는 자원 경계
- Private IP: VPC 내부에서 VM을 식별하는 주소
- Project: 여러 Supervisor Namespace와 관련 권한을 묶는 상위 관리 범위
- Transit Gateway: 여러 VPC를 상위에서 연결할 때 사용하는 구성요소
- IPBlock: Private·Private TGW·External 같은 용도의 주소 Pool
- Limit: External IP 사용량이나 CIDR 관련 할당 정책을 관리하는 Resource

#### 비유

사업장을 User Cluster, 사업장이 속한 도로 구역을 VPC, 구역 안의 주소를 Private IP라고 생각할 수 있습니다. 사업장마다 다른 도로 구역을 배정하면 내부 주소와 진입 경로를 따로 관리할 수 있습니다. 그렇다고 도시 전체의 간선도로와 교량까지 사업장마다 전용이 되는 것은 아닙니다.

#### 본문

DKS-C CCI 자료는 VPC와 Supervisor Namespace를 1:1로, Supervisor Namespace와 VKS를 1:1로 대응시키며 이를 Supervisor Namespace : VPC : Cluster = 1:1:1 관계로 설명합니다. 세 대상은 같은 경계를 다른 이름으로 부르는 것이 아닙니다.

| 대상 | 실제로 정하는 것 | 이 대상만으로는 알 수 없는 것 |
|---|---|---|
| Supervisor Namespace | User Cluster VM에 허용할 CPU·Memory·Storage Quota와 VM Class | Packet의 실제 Route와 NAT 결과 |
| VPC | User Cluster VM의 Private IP와 가상 Network 범위 | 특정 목적지까지의 도달 가능 여부 |
| User Cluster | 별도 Kubernetes Control Plane과 Worker Node 집합 | 물리 Host·Storage·상위 Network의 전용 여부 |
| Limit | External IP 사용량·CIDR 관련 할당 정책 | 특정 Session에 쓰인 주소와 NAT 성공 |
| IPBlock | Private·Private TGW·External 주소 Pool | 현재 Packet이 통과한 경로 |

CCI 자료는 IPBlock을 용도에 따라 구분합니다. Private은 VPC 내부 주소, Private TGW는 Multiple-VPC 통신에 쓰는 Private Subnet, External은 VPC 외부에서 식별되는 주소 범위입니다. 이 셋을 모두 단순히 “Cluster IP”라고 부르면 VM 내부 주소인지 Transit 연결용인지 외부 NAT·VIP 용도인지 구별할 수 없습니다.

```text
User Cluster A ─ Supervisor Namespace A ─ VPC A
User Cluster B ─ Supervisor Namespace B ─ VPC B

VPC별로 구별되는 것
├─ VM Private IP
└─ 가상 Network / Route 범위
```

더 상위에서는 Project : Transit Gateway : VPC = 1:1:N 관계가 기록되어 있습니다. User Cluster마다 VPC가 하나씩 나뉘어도 여러 VPC가 같은 Project와 Transit Gateway를 사용할 수 있습니다. 따라서 User VPC가 분리된다는 사실과 상위 연결 인프라가 공유될 수 있다는 사실은 동시에 성립합니다.

```text
User Cluster별 VPC 분리
        ↓
VM 주소와 VPC 경계는 구별됨

하지만

VPC 분리
        ≠
Transit Gateway / 상위 Gateway / 물리 Network까지 전용
```

### SNAT과 외부 통신

#### 왜 필요한가

VPC 내부 VM은 Private IP로 식별되지만 외부 Network가 그 주소를 그대로 반환 경로로 사용할 수 있는 것은 아닙니다. 외부로 나가는 Traffic에는 외부에서 식별할 Source 주소가 필요하고, 주소 변환 뒤에도 Route·정책·반환 경로가 이어져야 실제 통신이 완성됩니다.

#### 핵심 용어

- SNAT: Packet의 Source Address를 다른 주소로 바꾸는 Network Address Translation
- SNAT External IP: VPC 내부 VM의 Outbound Traffic이 외부에서 Source로 보일 수 있는 VPC별 주소
- NAT Session: 특정 통신에서 변환 전후 주소와 Port의 대응을 추적하는 상태
- Forward Path: Source에서 Destination으로 가는 경로
- Return Path: Destination의 응답이 Source로 돌아오는 경로
- 5-tuple: Source IP·Source Port·Destination IP·Destination Port·Protocol로 한 흐름을 식별하는 조합

#### 비유

구역 내부 주소를 Private IP, 외부 도로에서 사용하는 공용 출입 표식을 SNAT External IP라고 볼 수 있습니다. 차량이 구역을 나갈 때 표식이 바뀌더라도 목적지까지 갈 도로와 통행 허가가 없으면 도착하지 못합니다. 돌아올 때도 변환 기록과 반환 경로가 이어져야 같은 통신으로 되돌아올 수 있습니다.

#### 본문

VCFA 인프라 자료는 VPC : SNAT External IP = 1:1 관계를 기록하고, VPC 내부 VM의 Outbound Traffic에 해당 VPC의 SNAT External IP가 적용되는 구조를 설명합니다. SNAT이 적용되면 목적지에서 보는 Source Address는 VM의 Private IP가 아니라 해당 VPC의 SNAT External IP가 될 수 있습니다.

```text
VPC VM Private IP
      │ Outbound Packet
      ▼
SNAT
      │ Source = SNAT External IP
      ▼
외부 Network
```

여기서 VPC에 SNAT External IP가 할당되어 있다는 상태와 특정 Session에서 실제로 SNAT이 적용됐다는 상태는 다릅니다. networkInfos에 SNAT IP가 보이는 것도 관리 평면이 그 주소를 알고 있다는 뜻이지, 특정 Packet이 그 주소로 변환되어 목적지와 왕복했다는 증거는 아닙니다.

| 상태 | 확인되는 것 | 아직 별도로 확인할 것 |
|---|---|---|
| VPC에 SNAT External IP가 할당됨 | 사용 가능한 외부 Source 주소가 Control Plane에 기록됨 | 실제 Packet이 그 주소로 변환됐는가 |
| NAT/Flow에서 변환 Session 확인 | 특정 Packet의 Source가 변환됨 | 목적지 Route·정책 허용 |
| Firewall Allow/Session 확인 | 해당 정책 장비가 흐름을 허용함 | 목적지 Application 수신·응답 |
| 목적지에서 Request 수신 | Forward Path가 목적지까지 도달 | 응답의 반환 Route와 최종 기능 성공 |

따라서 왕복 통신에는 NAT Session뿐 아니라 목적지로 향하는 Route, Firewall·ACL 허용, Destination 수신, 반환 Route가 함께 이어져야 합니다.

```text
Private Source
    ↓
SNAT 적용 확인
    ↓
목적지 Route
    ↓
Firewall / ACL
    ↓
Destination 수신
    ↓
반환 Route + NAT Session
    ↓
왕복 통신 성공

SNAT IP 할당 ≠ 실제 Session 성공
```

Pod Traffic은 한 단계 더 구별해야 합니다. 현재 자료가 직접 확정하는 것은 VPC 내부 VM의 Outbound NAT입니다. Pod IP가 CNI나 Node에서 먼저 어떤 주소로 바뀌는지, Service나 별도 egress 경로를 거치는지는 대상 User Cluster의 CNI·Routing 설정을 확인해야 합니다. 따라서 모든 Pod가 VPC Gateway에서 직접 같은 방식으로 SNAT된다고 단정하거나, SNAT IP가 있다는 이유로 모든 외부 목적지와 통신 가능하다고 확대하지 않습니다.

### 같은 VPC와 다른 VPC

#### 왜 필요한가

VPC 경계가 생기면 모든 Packet이 같은 경로를 쓰는 것이 아닙니다. 같은 VPC 안에서 이동하는 Traffic과 다른 VPC로 넘어가는 Traffic은 필요한 연결 구조와 Route가 다르므로, 통신 대상을 먼저 구분해야 실제 경로를 판단할 수 있습니다.

#### 핵심 용어

- VPCConnectivityProfile: VPC가 사용할 연결 Topology를 정의하는 Resource
- VPCAttachment: 특정 VPC를 ConnectivityProfile에 연결하는 Resource
- Private TGW IPBlock: Multiple-VPC 통신에 사용하는 Private Subnet 주소 Pool
- Route Table: 목적지 Prefix에 대해 어떤 Next Hop을 선택할지 기록한 경로 정보
- Next Hop: Packet이 다음으로 전달될 Gateway나 Interface
- Tier-0 Gateway: 상위 Routing과 외부 연결에 관여할 수 있는 Gateway 계층

#### 비유

같은 도로 구역 안의 이동은 동일 VPC 통신, 다른 구역으로 넘어가는 이동은 VPC 간 통신에 대응합니다. 같은 구역 안에서는 내부 도로만으로 목적지에 갈 수 있지만 다른 구역으로 가려면 두 구역을 잇는 연결로와 그 경로에 맞는 Route가 필요합니다.

#### 본문

같은 VPC의 VM은 같은 가상 Network 범위에 속합니다. VCFA 자료는 동일 VPC의 VM 간 통신을 별도 Security Group으로 세분화하지 않는다고 기록합니다. 이 말은 해당 VPC 구현에서 같은 VPC VM 사이를 Security Group으로 나누지 않는다는 범위에서만 사용합니다.

이 사실만으로 Kubernetes NetworkPolicy가 없거나 CNI Policy가 없거나 Application Authentication이 없거나 상위 Router·Firewall Policy가 없다고 결론 내릴 수는 없습니다. 모든 Port가 실제로 열려 있다는 뜻도 아닙니다.

다른 VPC로 가는 Packet에는 별도의 연결 Topology와 Route가 필요합니다.

| Resource | 자료에서 확인되는 역할 |
|---|---|
| VPCConnectivityProfile | VPC가 사용할 연결 Topology 정의 |
| VPCAttachment | 특정 VPC를 ConnectivityProfile에 연결 |
| TransitGateway | 여러 VPC 연결에 사용하는 구성요소 |
| Private TGW IPBlock | Multiple-VPC 통신용 Private Subnet |

```text
같은 VPC
VM A ───── VPC 내부 경로 ─────> VM B

다른 VPC
VPC A
  └─ VPCAttachment
       └─ ConnectivityProfile / TransitGateway
            └─ VPCAttachment
                 └─ VPC B
```

이 Resource들이 존재하면 VPC 간 연결을 어떤 객체로 구성하는지는 설명할 수 있습니다. 하지만 특정 A VPC의 Subnet에서 B VPC의 특정 목적지로 현재 Route가 설치됐는지, 어느 Gateway가 Next Hop인지, 정책이 실제로 허용하는지는 별도의 현재 상태를 확인해야 합니다.

Private TGW라는 이름이나 “중앙 Firewall이 있다”는 아키텍처 설명도 특정 Packet이 그 장비를 경유했다는 증거는 아닙니다. 특정 장비를 실제 경로라고 판단하려면 Source·Destination·Protocol·Port·시각을 고정하고 Route Table의 Next Hop, Gateway·Firewall Interface와 Session, ACL·Policy Hit, 다음 Hop과 Destination 수신을 연결해야 합니다.

```text
Source / Destination / Protocol / Port / Time
        ↓
Source VPC Route Table의 Next Hop
        ↓
Gateway·Firewall Interface와 Session
        ↓
ACL / Policy Hit
        ↓
다음 Hop과 Destination 수신
```

Route가 Tier-0이나 Firewall을 선택하고 같은 흐름과 시각의 Session과 ACL Hit가 확인되면 해당 Packet이 그 장비를 경유했다고 강하게 판단할 수 있습니다. 반대로 장비에 Session이 없다는 사실만으로 그 장비 앞에서 차단됐다고 단정하지 않습니다. Route가 다른 경로를 선택했거나 Source에서 Packet이 나오지 않았거나 NAT 뒤 주소가 달라졌거나 관측 시각이 어긋났을 수 있습니다.

### Control Plane과 Data Plane 증거

#### 왜 필요한가

Network 설정이 정상으로 보인다고 실제 Packet이 같은 경로를 사용하고 목적지와 왕복했다는 보장은 없습니다. 통신 성공과 장애 위치를 판단하려면 원하는 설정을 보여주는 Control Plane 정보와 실제 실행을 보여주는 Data Plane 증거를 구별해 이어봐야 합니다.

#### 핵심 용어

- Control Plane 정보: VPC·Limit·IPBlock·ConnectivityProfile처럼 원하는 설정과 할당 상태를 나타내는 Resource
- Data Plane 증거: Packet Capture·NAT/Flow Session·Firewall Log·Destination Log처럼 실제 Packet 처리 결과를 보여주는 관측
- Route Table: 설정된 Next Hop을 보여주는 정보로, Packet이 실제 그 경로를 사용했다는 사실까지 단독으로 증명하지는 않음
- Session·Flow: 특정 통신 흐름이 Network 장비에서 실제로 처리된 상태나 기록
- LimitState.consumed: 특정 집계 Resource가 보고하는 소비량 값
- VPCIPAddressUsage.allocated: VPC 주소 할당 상태를 나타내는 별도 집계 값

#### 비유

도로 지도와 통행증은 Control Plane 상태, 실제 차량의 이동 기록은 Data Plane 증거에 대응시킬 수 있습니다. 지도에 길이 있고 통행증이 발급됐다고 차량이 목적지에 도착한 것은 아닙니다. 출발지와 경유지, 검문소, 목적지의 관측을 연결해야 실제 이동이 어디까지 진행됐는지 알 수 있습니다.

#### 본문

VPC·Limit·IPBlock·ConnectivityProfile 같은 Resource는 원하는 설정과 할당 상태를 보여줍니다. Packet Capture·Flow·NAT Session·Firewall Log·Destination Log는 실제 Packet 처리를 보여줍니다.

| 증거 | 강하게 말할 수 있는 것 | 그것만으로는 말할 수 없는 것 |
|---|---|---|
| VPC Ready | VPC Resource가 준비 상태로 보고됨 | 특정 목적지와 왕복 통신 성공 |
| networkInfos의 SNAT IP | 관리 평면이 알고 있는 SNAT 주소 | 특정 Session에서 실제 사용된 Source |
| LimitState.consumed | 해당 집계 Resource가 보고한 소비량 | 전체 실제 할당과 정확한 잔여량 |
| Route Table | 설정된 Next Hop | Packet이 실제 그 Route를 사용했는가 |
| Firewall Allow Log | 해당 장비가 특정 흐름을 허용 | 목적지 Application 정상 처리 |
| Destination Log | Request가 목적지에 도달 | 반환 Packet과 Client 기능 성공 |

CCI 자료에는 VPCLimitState의 consumed 값과 VPCIPAddressUsage의 allocated 값이 일치하지 않은 사례도 기록되어 있습니다. 따라서 하나의 집계값만 보고 External IP의 전체 실제 가용량을 확정하지 않습니다.

특정 Packet을 재구성할 때는 NAT 전후 주소가 달라질 수 있습니다. 최초의 5-tuple만 모든 구간에서 그대로 검색하지 않고 NAT·Session 정보에서 변환 전후 주소를 연결해야 합니다.

장애 조사도 장비 이름을 미리 원인으로 정하는 방식보다 마지막으로 확인된 상태와 아직 확인되지 않은 다음 상태를 이어가는 편이 구분력이 높습니다.

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 증거 |
|---|---|---|
| Source에서 DNS·Destination을 확정하지 못함 | 실제 목적지 IP·Port는 무엇인가? | DNS 응답, Application 설정, 호출 Log |
| Source가 Packet을 생성함 | 어느 Interface·Route로 나가는가? | Local Route, Packet Capture |
| VPC SNAT 정보는 존재함 | 실제 Session에 NAT가 적용됐는가? | NAT/Flow Table, 변환 전후 5-tuple |
| NAT는 확인됐으나 목적지 도달 안 함 | Route와 정책 중 어디까지 통과했는가? | Route Table, Gateway·Firewall Session/ACL |
| Firewall은 Allow함 | Destination Listener·Application이 받았는가? | Destination Packet·Socket·Application Log |
| Destination은 Request를 받음 | 응답이 어떤 Route로 돌아오는가? | Return Route, Reverse Flow, Client Capture |
| VPC A/B 연결 Resource가 존재함 | 실제 A→B Route가 설치됐는가? | Attachment 상태, Route Advertisement/Table |
| 같은 VPC인데 통신 실패 | VPC 외 어느 계층이 차단하는가? | CNI/NetworkPolicy, Host Route, Application Auth |

```text
Source에서 Packet 생성 확인
        ↓
Source VPC / 주소 확인
        ↓
NAT 필요 여부와 실제 변환 확인
        ↓
Route 선택 확인
        ↓
정책 장비 Session / ACL 확인
        ↓
Destination 수신·응답 확인
        ↓
반환 Packet 확인

이 순서는 장비의 실행 순서가 아니라
경쟁 설명을 줄이기 위한 조사 순서
```

운영자가 이 순서로 조회해야 Network Controller가 다음 상태를 만드는 것은 아닙니다. 이 표와 도식은 실제 실행 순서를 정의하는 것이 아니라 관측된 사실을 이용해 실패 범위를 좁히는 조사 방법입니다.
