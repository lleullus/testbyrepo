# 01. 멀티클러스터 테넌시와 자동 프로비저닝 — 무엇이 분리되고 생성 완료는 어디까지인가?

## 문서의 목적

이 문서는 DKS-C에서 User Cluster가 왜 필요한지부터 시작해, Kubernetes 실행 경계를 어떻게 나누고, 그 경계를 어떤 인프라 범위에 연결하며, 선언한 구성이 실제 VM·Node로 어떻게 수렴하고, 마지막으로 어디까지 확인해야 실제 사용 가능한 Cluster라고 볼 수 있는지를 하나의 인과 흐름으로 설명합니다.

## 전체 인과 지도

처음에는 여러 팀을 하나의 Kubernetes Cluster 안에서 나누면 충분해 보입니다. Namespace만 있어도 리소스와 권한을 나눌 수 있기 때문입니다. 하지만 Cluster 업그레이드나 Worker 장애처럼 Cluster 자체에서 일어나는 변화는 여러 팀에 함께 영향을 줄 수 있습니다. 이 문제를 피하려면 실행 환경 자체를 나눠야 하고, 그때 User Cluster가 필요합니다. User Cluster로 실행 경계를 나누면 다음 문제가 남습니다. 각 Cluster가 어떤 Compute·Storage·Network를 사용할지는 아직 정해지지 않았습니다. 그래서 Supervisor Namespace와 VPC로 실제 인프라 사용 범위를 붙입니다. 여기까지 정해도 구성은 아직 선언일 뿐입니다. 실제 VM과 Node를 만들고 이후에도 그 상태를 유지하려면 ArgoCD·CAPI·Supervisor가 현재 상태를 계속 확인하고 원하는 상태로 맞춰야 합니다. 그렇게 VM과 Node가 준비되어도 끝은 아닙니다. Kubernetes API가 응답하고 Worker가 참여하고 필요한 Addon과 접속 정보까지 준비되어야 사용자가 실제로 쓸 수 있는 User Cluster가 됩니다. 이 문서는 이처럼 앞 문제를 해결할 때마다 남는 다음 문제를 따라가면서 User Cluster가 완성되는 과정을 설명합니다.

이 문서는 신도시 개발 사업을 하나의 비유 세계로 사용합니다. 각 절에서는 필요한 핵심 대응만 먼저 밝히고, 이후에는 실제 기술 용어와 작동을 중심으로 설명합니다. 비유는 관계를 잡기 위한 보조 수단이며 실제 판단은 기술 본문과 확인 가능한 상태를 기준으로 합니다.

### Namespace와 User Cluster

#### 왜 필요한가

여러 조직이나 팀이 같은 Kubernetes 실행 환경을 공유하면 한쪽의 Cluster 수준 변경이나 장애가 다른 쪽의 운영에도 영향을 줄 수 있습니다. 그래서 각 운영 단위를 어느 수준까지 서로 독립시킬 것인지 먼저 정해야 합니다.

#### 핵심 용어

- 테넌트: 다른 조직·팀·서비스와 구분해 독립적으로 관리하려는 운영 단위
- Kubernetes Cluster: 하나의 Control Plane과 하나 이상의 Worker가 함께 동작하는 Kubernetes 실행 단위
- Namespace: 하나의 Kubernetes Cluster 안에서 리소스를 논리적으로 나누는 구획
- User Cluster: 자체 Control Plane과 Worker 집합을 가진 별도의 Kubernetes Cluster
- Control Plane: Cluster의 상태를 저장하고 API와 전체 동작을 제어하는 영역
- Worker: 실제 애플리케이션 Pod가 실행되는 Node

#### 비유

![비유: 사무실(Namespace) 분리와 독립 건물(User Cluster)](assets/block1-analogy-tenancy-building.png)

하나의 건물(Kubernetes Cluster)을 여러 회사가 함께 쓴다고 생각할 수 있습니다. 회사마다 사무실(Namespace)을 따로 주면 공간은 나눌 수 있지만 건물의 관리실과 주요 설비는 함께 사용합니다. 반면 회사마다 별도 건물(User Cluster)을 주면 각 건물이 자체 관리실(Control Plane)과 작업 공간(Worker)을 가질 수 있습니다.

#### 본문

Namespace는 하나의 Kubernetes Cluster 안에서 Pod·Service 같은 namespaced Resource가 어느 구획에 속하는지를 나눕니다. 같은 종류와 같은 이름의 리소스라도 Namespace가 다르면 서로 별개의 리소스로 관리할 수 있으므로, 여러 팀이나 환경이 하나의 Cluster를 함께 사용할 때 기본적인 논리적 구분을 만들 수 있습니다.

다만 Namespace를 만든다고 CPU·Memory 한도나 API 권한이 자동으로 생기는 것은 아닙니다. ResourceQuota를 해당 Namespace에 적용하면 Pod의 CPU·Memory request/limit 합계나 특정 Resource 개수 등에 한도를 둘 수 있습니다. Role에는 “Pod 조회”, “Deployment 변경”처럼 허용할 API 작업을 정의하고, RoleBinding으로 그 Role을 사용자·Group·ServiceAccount에 연결합니다.

이렇게 리소스·사용량·권한을 나눌 수 있어도 Kubernetes 실행 기반 자체가 Namespace별로 새로 생기지는 않습니다. 여러 Namespace는 같은 API Server와 etcd를 사용할 수 있고, 서로 다른 Namespace의 Pod가 같은 Worker Node에서 실행될 수도 있습니다.

```text
하나의 Kubernetes Cluster
├─ Control Plane
│  ├─ API Server
│  └─ etcd
├─ Worker Node
│  ├─ Namespace A의 Pod
│  └─ Namespace B의 Pod
├─ Namespace A
└─ Namespace B
```

따라서 Namespace A와 Namespace B가 논리적으로 분리되어 있어도 Cluster 자체의 업그레이드, 공통 Worker 장애, Control Plane 문제처럼 Cluster 수준에서 일어나는 변화에는 함께 영향을 받을 수 있습니다.

DKS-C의 User Cluster는 이보다 큰 경계입니다. User Cluster마다 별도의 Control Plane과 Worker VM 집합이 있으므로 각 Cluster의 Kubernetes 상태, Node 수, Machine 교체, 업그레이드 같은 수명주기를 다른 User Cluster와 별도로 관리할 수 있습니다. 한 User Cluster의 Machine이나 Node를 조정한다고 해서 다른 User Cluster의 같은 Resource를 직접 변경하는 구조는 아닙니다.

```text
User Cluster A                 User Cluster B
├─ Control Plane A             ├─ Control Plane B
└─ Worker A                    └─ Worker B

Namespace
→ 하나의 Kubernetes Cluster 안을 나눔

User Cluster
→ Kubernetes Cluster 자체를 나눔
```

여기서 주의할 점은 Kubernetes Cluster 경계와 물리 인프라 경계가 같은 말은 아니라는 것입니다. User Cluster의 VM은 vSphere Workload Domain의 서버와 Storage를 사용할 수 있습니다. 실제 ESXi 배치와 상위 Network를 확인하지 않고 “User Cluster가 분리됐으니 ESXi·Storage·Network까지 모두 전용이다”라고 확대할 수 없습니다.

```text
User Cluster 분리
        ↓
Kubernetes 실행 경계는 분리됨

하지만

User Cluster 분리
        ≠
ESXi / Storage / 상위 Network까지 전용이라는 보장
```

### Supervisor Namespace와 VPC

#### 왜 필요한가

Kubernetes 실행 환경을 서로 분리해도 각 Cluster가 실제 인프라에서 얼마만큼의 자원을 쓰고 어떤 네트워크 범위에 놓일지는 아직 정해지지 않습니다. 독립된 운영 단위를 실제 인프라 사용 범위까지 연결하려면 Compute·Storage·Network 경계를 따로 정해야 합니다.

#### 핵심 용어

- Supervisor Namespace: User Cluster VM이 사용할 수 있는 CPU·Memory·Storage와 VM Class 범위를 연결하는 Supervisor 측 자원 경계
- VPC: User Cluster VM이 사용할 Private IP와 가상 Network 범위를 제공하는 네트워크 경계
- Quota: 특정 범위가 사용할 수 있도록 허용한 자원의 총량
- VirtualMachineClass: VM 한 대의 CPU·Memory 사양을 나타내는 클래스
- Project: 여러 Supervisor Namespace와 권한을 묶는 상위 관리 범위
- Limit·IPBlock: VPC가 사용할 External IP 할당 정책과 주소 풀을 관리하는 대상

#### 비유

![비유: 건물(User Cluster)의 자원 허가(Supervisor Namespace)와 도로 구역(VPC)](assets/block2-analogy-quota-zoning.png)

별도 건물(User Cluster)을 지었다고 해서 그 건물이 얼마만큼의 전력·면적·창고를 사용할 수 있는지, 어느 도로와 주소 구역을 사용할지가 자동으로 정해지는 것은 아닙니다. 자원 허가(Supervisor Namespace)와 도로·주소 구역(VPC)을 함께 정해야 실제 운영 범위가 생깁니다.

#### 본문

DKS-C의 CCI 자료는 User Cluster마다 Supervisor Namespace와 VPC를 하나씩 대응시키는 구성을 기록합니다.

```text
User Cluster A
├─ Supervisor Namespace A
│  ├─ CPU / Memory Quota
│  ├─ Storage Quota
│  └─ 허용 VM Class
└─ VPC A
   ├─ Private IP 범위
   └─ 가상 Network 범위

User Cluster : Supervisor Namespace : VPC
             = 1 : 1 : 1
```

이 관계에서 Supervisor Namespace는 User Cluster VM이 사용할 자원 허용 범위를, VPC는 VM이 속할 IP와 가상 Network 범위를 정합니다. 따라서 User Cluster의 논리적 실행 경계를 실제 인프라 사용 범위에 연결할 수 있습니다.

각 대상이 정하는 범위와 그 대상만으로는 알 수 없는 범위를 구분해야 합니다.

| 대상 | 실제로 정하는 것 | 이 대상만으로는 알 수 없는 것 |
|---|---|---|
| Project | 여러 Supervisor Namespace와 Project 권한을 묶는 상위 관리 범위 | User Cluster와 1:1이라는 보장 |
| Supervisor Namespace | User Cluster VM에 허용할 CPU·Memory·Storage Quota와 VM Class | Zone·Region의 실제 남은 물리 용량 |
| VPC | User Cluster VM이 사용할 IP 대역과 가상 Network 범위 | 특정 목적지의 Route·정책 허용 |
| Limit·IPBlock | VPC가 사용할 External IP의 할당 정책과 주소 풀 | 특정 패킷의 실제 NAT 성공 |
| User Cluster | 별도 Kubernetes Control Plane과 Worker Node 집합 | ESXi·Storage·상위 Network의 전용 배치 |

Supervisor Namespace를 처음 만들 때는 SupervisorNamespaceClassConfig에 정의된 기본 Quota와 VM Class 설정을 사용할 수 있습니다. 여기서 VirtualMachineClass와 Supervisor Namespace Quota는 같은 개념이 아닙니다. VirtualMachineClass는 VM 한 대의 CPU·Memory 사양이고, Quota는 여러 VM이 함께 사용할 수 있는 전체 허용량입니다.

```text
VirtualMachineClass
→ VM 1대의 크기

Supervisor Namespace Quota
→ 해당 Namespace가 사용할 수 있는 전체 자원 한도
```

Quota가 충분해 보여도 실제 VM이 반드시 생성되는 것은 아닙니다. CPU·Memory는 배치 대상 Zone의 한도와 실제 가용 자원에 영향을 받고, Storage는 Region·Storage Policy의 한도와 사용량에 영향을 받을 수 있습니다. VPC의 External IP도 별도의 Limit·IPBlock 할당 조건을 사용합니다.

VPC가 존재한다고 통신 성공까지 보장되는 것도 아닙니다. VPC가 IP와 가상 Network 범위를 제공해도 특정 목적지까지 Route가 존재하는지, 정책이 허용하는지, 실제 SNAT이 성공하는지는 별도로 확인해야 합니다.

```text
1 : 1 : 1 대응
→ 테넌트와 인프라 사용 범위를 연결함

하지만 별도 확인 필요
├─ Zone / Region의 실제 Capacity
├─ Storage 여유
├─ External IP 할당
└─ Route / Policy / 실제 통신
```

Supervisor Namespace의 Quota 변경과 증설 여유는 [03. Supervisor·CCI 인프라 제어 평면과 Quota 경계](03.%20Supervisor%C2%B7CCI%20인프라%20제어%20평면과%20Quota%20경계.md)에서 확대하고, VPC·SNAT·VPC 간 경로 조건은 [02. 네트워크 격리와 1:1:1 테넌시 경계](02.%20네트워크%20격리와%201:1:1%20테넌시%20경계.md)에서 자세히 다룹니다.

### Git·ArgoCD·CAPI·Supervisor

#### 왜 필요한가

원하는 Cluster 구성을 선언하는 것과 실제 인프라가 그 상태로 존재하는 것은 다른 문제입니다. 생성·확장·교체·장애 과정에서 선언과 현실이 계속 달라질 수 있으므로, 현재 상태를 관찰하고 원하는 상태로 되돌리는 조정 구조가 필요합니다.

#### 핵심 용어

- 원하는 상태(Desired State): 운영자가 시스템이 최종적으로 가져야 한다고 선언한 상태
- reconcile: 현재 상태와 원하는 상태를 비교해 차이를 줄이는 작업을 반복하는 조정 방식
- ArgoCD: Git에 선언한 구성을 관리 대상 API Resource에 반영하고 동기화 상태를 확인하는 구성 관리 계층
- CAPI(Cluster API): Kubernetes Cluster와 Machine의 생성·확장·교체 같은 수명주기를 Kubernetes Resource로 관리하는 계층
- Machine: Kubernetes Node 한 대의 생성·교체 수명주기를 표현하는 CAPI Resource
- Supervisor: VM·Storage·Network 같은 인프라 요청을 Kubernetes Resource로 받아 실제 vSphere 작업으로 이어주는 계층

#### 비유

![비유: 설계도(Git)에서 실제 건물(VM·Node)까지 이어지는 조정](assets/block3-analogy-reconcile-construction.png)

Git은 건물 설계도, ArgoCD는 최신 설계도를 관리 시스템에 반영하는 담당, CAPI는 필요한 건물과 설비의 생성·교체를 조정하는 공정 관리자, Supervisor·vSphere는 실제 VM·Storage·Network를 준비하는 시공 영역에 대응시킬 수 있습니다. 설계도가 반영됐다는 사실과 실제 건물이 완성됐다는 사실은 서로 다른 상태입니다.

#### 본문

DKS-C 운영 현황은 User Cluster 프로비저닝을 VCF Cluster API + ArgoCD 기반으로 기록합니다. SW 아키텍처에는 사용자 Cluster 배포를 맡는 argocd-vks-instance가 Supervisor Service로 기록되어 있습니다.

운영자가 Git에 Node 수·VM 사양·Network·Addon 같은 원하는 구성을 기록하면 ArgoCD가 관리 대상 API의 Resource를 그 정의에 맞춥니다. ArgoCD의 `Synced`는 Git에 기록된 원하는 정의와 관리 대상 Resource가 동기화됐다는 뜻입니다. 실제 VM이나 Kubernetes Node가 준비됐다는 뜻은 아닙니다.

CAPI에서는 Resource마다 담당 범위가 다릅니다.

| CAPI Resource | 이 문서에서 필요한 역할 |
|---|---|
| ClusterClass | 유사한 Cluster를 만들 때 사용할 공통 구성 틀 |
| Cluster | 생성할 Cluster의 원하는 상태와 참조 |
| MachineDeployment | Worker Machine 집합의 수와 교체를 조정 |
| Machine | Node 한 대의 생성·교체 상태를 표현 |
| BootstrapData | VM을 Kubernetes Node로 초기화할 설정과 명령 |

CAPI Controller는 Cluster·MachineDeployment·Machine 같은 Resource를 읽고, 현재 상태가 원하는 Cluster와 Node 수에 가까워지도록 계속 조정합니다. Machine은 “Node가 하나 필요하다”는 선언만 표현하는 것이 아니라 해당 Node 한 대가 생성되고 교체되는 수명주기를 추적하는 단위입니다.

Machine이 존재한다고 실제 VM이 즉시 존재하는 것은 아닙니다. Machine과 연결된 Infrastructure·Bootstrap 설정을 바탕으로 Supervisor 쪽 Controller가 VirtualMachine·Storage·Network 요청을 만들고, VM Operator 같은 Controller가 이를 실제 vSphere 작업으로 이어갑니다. VM이 생성된 뒤에도 Bootstrap 설정이 적용되고 kubelet이 동작해 Kubernetes Node로 등록되어야 합니다.

```text
Git의 원하는 정의
        ↓
ArgoCD
→ 관리 API Resource를 Git과 맞춤
        ↓
CAPI
→ Cluster / MachineDeployment / Machine 조정
        ↓
Supervisor Controller
→ VirtualMachine / Storage / Network 준비
        ↓
VM Boot / Bootstrap
        ↓
kubelet Node 등록
```

따라서 다음 상태는 서로 같은 뜻이 아닙니다.

```text
ArgoCD Synced
      ≠
CAPI Machine Ready
      ≠
VM Ready
      ≠
Kubernetes Node Ready
```

이 과정을 고정된 직렬 워터폴로 이해하면 안 됩니다. ArgoCD·CAPI·Supervisor·kubelet·Addon Controller는 서로 다른 Resource를 지속적으로 reconcile하며, 앞 단계가 완전히 멈춰야 다음 단계가 시작되는 식으로 움직이지 않을 수 있습니다.

DKS 오케스트레이터가 특정 순서로 “요청하고 확인한다”는 사실도 Controller들의 내부 실행 순서와 같지 않습니다. 오케스트레이터가 Cluster health를 polling하는 동안에도 CAPI와 인프라 Controller는 계속 reconcile할 수 있습니다. 따라서 장애를 볼 때는 “몇 번째 단계인가”보다 마지막으로 실제 확인된 Resource 상태와 다음에 필요한 상태를 연결해야 합니다.

### 사용 가능한 User Cluster

#### 왜 필요한가

인프라 리소스가 생성됐다는 사실과 사용자가 실제 Kubernetes 서비스를 사용할 수 있다는 사실은 다릅니다. 생성 완료를 신뢰하려면 Control Plane·Worker·Addon·접속 정보가 각각 어떤 상태인지 구분해서 확인해야 합니다.

#### 핵심 용어

- Control Plane API 응답: API Server가 기동되어 Kubernetes API 요청을 받을 수 있는 상태
- Node 등록: Worker의 kubelet이 Control Plane에 자신을 Kubernetes Node로 등록한 상태
- Node Ready: kubelet이 현재 Node가 Kubernetes Workload를 실행할 준비가 되었다고 보고하는 상태
- Addon: CNI·CSI·cert-manager처럼 Cluster의 Network·Storage·운영 기능을 추가하는 구성요소
- kubeconfig: 사용자가 Kubernetes API에 접속할 때 사용하는 Cluster 접속·인증 설정
- networkInfos: DKS-C 오케스트레이션에서 Cluster의 네트워크 결과 정보를 전달하는 데이터
- SNAT IP: Cluster 내부 트래픽이 외부로 나갈 때 출발지 주소로 사용될 수 있는 변환 IP
- Portal·Console 후처리: 생성된 Cluster를 사용자에게 노출하고 운영 시스템과 연결하기 위한 후속 작업

#### 비유

![비유: 건물(VM) 완공 뒤 실제 입주 가능 상태(User Cluster)를 확인](assets/block4-analogy-readiness-inspection.png)

건물 골조(VM)가 완성됐다고 바로 입주할 수 있는 것은 아닙니다. 관리실(Control Plane)이 동작하고, 실제 작업 공간과 인력(Worker Node)이 준비되고, 전기·배관 같은 기본 설비(Addon)가 갖춰지고, 입주자가 사용할 출입 수단과 안내 정보(kubeconfig·networkInfos·Portal)까지 전달되어야 실제 사용 가능한 건물이라고 볼 수 있습니다.

#### 본문

Control Plane VM에서는 etcd가 Cluster 상태를 저장하고 API Server가 Kubernetes API를 제공해야 합니다. API Server가 접속 가능한 상태가 되면 Worker VM의 kubelet은 가입 정보와 API 주소를 사용해 같은 Cluster에 Node로 등록되고, 이후 자신의 상태를 API Server에 계속 보고합니다.

VM이 존재하는 것, API Server가 응답하는 것, Worker가 등록되는 것, Node가 Ready인 것은 서로 다른 확인 지점입니다.

| 확인 상태 | 확인되는 것 | 아직 별도로 확인할 것 |
|---|---|---|
| VM 존재·전원 ON | 인프라 VM이 생성되어 실행 중 | API Server·kubelet 동작 |
| Control Plane API 응답 | Kubernetes API에 접속 가능 | 모든 Worker·Addon 준비 |
| Worker Node 등록 | kubelet이 Cluster에 Node로 등록 | Pod Network·Storage 기능 |
| Node Ready | kubelet이 현재 Node 준비 상태를 보고 | 사용자 애플리케이션 정상 |
| Addon health | 해당 Addon의 배포 상태 | 외부 시스템을 포함한 전체 서비스 경로 |

Addon도 별도의 완료 조건입니다. DKS-C SW 자료는 기본 Addon 13개를 기록하며 Carvel 또는 Helm으로 관리되는 항목이 섞여 있습니다. CNI는 Pod Network를 만들고, CSI 계열은 Kubernetes Storage 요청을 인프라 Storage 작업으로 연결합니다. cert-manager, Monitoring Agent, Logging Agent, Policy, Backup 기능도 대상 Cluster API를 사용합니다.

이 순서를 단순한 직렬 단계로 고정하면 오해가 생깁니다. 예를 들어 어떤 환경에서는 CNI가 먼저 준비되어야 Node가 Ready가 될 수 있으므로 “Worker Ready가 끝난 뒤 CNI를 설치한다”라고 단정하면 실제 의존관계를 뒤집게 됩니다. Machine 조정과 Addon 배포도 서로 다른 Controller가 동시에 진행할 수 있습니다.

##### DKS 오케스트레이터가 완료를 닫는 방식

내부 CCI 가이드는 DKS 오케스트레이션에서 RoleBinding 생성, ArgoCD Application 배포, Carvel Addon 배포, Cluster health polling, kubeconfig 조회, ArgoCD 대상 Cluster 등록, etcd Secret 조회, Helm Addon 배포, networkInfos의 SNAT IP 조회, Console 전달 등을 수행한다고 기록합니다.

이 목록은 오케스트레이터가 무엇을 요청하고 무엇을 확인하는지를 보여주는 것이지, CAPI·Supervisor·vSphere·kubelet·Addon Controller가 정확히 같은 순서로 한 단계씩 멈춰 기다린다는 뜻은 아닙니다. 원자료는 이 절을 “11단계”라고 부르지만 보이는 표에는 1~10의 작업이 있으므로, 숫자를 고정된 아키텍처 state machine으로 사용하지 않고 각 작업이 실제로 무엇을 수행·확인하는지를 기준으로 읽는 편이 안전합니다.

Console에 Cluster 정보가 전달된 뒤에도 Portal DB 권한, APISIX Upstream·Route, Cluster Role·RoleBinding, 최초 Harbor Registry 같은 후처리가 기록되어 있습니다. 이 후처리가 끝났다는 사실과 사용자가 배포한 애플리케이션까지 정상이라는 사실도 같은 상태가 아닙니다.

```text
원하는 Resource 적용
        ↓
CAPI Machine 상태
        ↓
실제 VM 준비
        ↓
Control Plane API 응답
        ↓
Worker Node 등록 / Ready
        ↓
CNI·CSI 등 필요한 Addon
        ↓
kubeconfig / networkInfos / Portal 후처리
        ↓
사용 가능한 User Cluster

※ 각 화살표는 다음 상태의 충분조건이라는 뜻이 아님
※ 일부 Controller 작업은 서로 겹쳐 진행될 수 있음
```

##### 프로비저닝이 멈췄을 때는 마지막 확인 상태를 찾는다

장애를 “몇 번째 단계가 실패했는가”로만 찾기보다, 마지막으로 확인된 상태와 아직 만들어지지 않은 다음 상태를 연결하면 실패 범위를 더 직접적으로 좁힐 수 있습니다.

| 마지막으로 확인된 상태 | 다음 질문 | 주요 확인 대상 |
|---|---|---|
| ArgoCD가 원하는 revision을 적용하지 못함 | Git 정의가 관리 API에 적용됐는가? | revision, Application sync/health, 적용 오류 |
| CAPI Cluster/Machine은 있으나 Machine이 준비되지 않음 | 어떤 condition에서 Node 생성이 막혔는가? | Cluster·MachineDeployment·Machine condition/event |
| Machine은 있으나 VM·Disk가 준비되지 않음 | 어떤 인프라 조건이 부족한가? | Supervisor Namespace, VirtualMachine, Storage, VPC, Quota |
| VM은 있으나 Control Plane API가 응답하지 않음 | Bootstrap과 API Server·etcd가 어디까지 기동했는가? | BootstrapData 적용, VM 초기화, API endpoint |
| Control Plane API는 응답하나 Worker가 등록되지 않음 | Worker가 API에 접속하고 가입할 조건을 갖췄는가? | Worker Machine, kubelet, API 연결·가입 상태 |
| Worker가 등록됐으나 Ready/Addon이 불안정함 | Pod Network·Storage·필수 Addon 중 무엇이 남았는가? | Node condition, CNI·CSI·Addon Resource와 Pod |
| Cluster는 동작하나 Portal 결과가 완성되지 않음 | 오케스트레이터 후처리와 접속 정보가 준비됐는가? | kubeconfig, networkInfos, ArgoCD 등록, Console 후처리 |

이 표는 Controller의 실행 순서를 정의하는 표가 아니라, 관측된 사실을 기준으로 다음 확인 지점을 선택하기 위한 조사 순서입니다.
