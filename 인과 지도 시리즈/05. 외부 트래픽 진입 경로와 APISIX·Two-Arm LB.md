# 05. 외부 트래픽 진입 경로와 APISIX·Two-Arm LB — 요청과 원래 Client IP는 어디로 가는가?

## 문서의 목적

물류 터미널에 물건이 도착하면 안내 주소, 접수 창구, 분류 규칙, 실제 배송지가 차례로 관계됩니다. 접수 창구에 도달했다고 배송이 끝난 것은 아니며, 중계 직원이 다시 보낸 물건에는 원래 발송인과 중계자의 정보가 함께 남을 수 있습니다.

이 문서는 DKS-C의 외부 진입을 **물류 터미널의 접수·분류·중계**로 설명합니다. FQDN·VIP·Listener·Service·APISIX Route·Upstream의 관계, Two-Arm LB의 앞·뒤 경로, Client IP 보존과 인증의 차이를 연결합니다. 비유에서 발송인 표기가 유지된다고 실제 네트워크 Source IP가 유지된다고 추론하지 않고 각 계층의 실제 값을 구분합니다.

> 자료 범위: 지정된 05번 원문과 그 원문에 연결된 DKS-C 배치·네트워크 및 APISIX·Kubernetes·NGINX 설명입니다. 실제 Listener·Route·NAT·TLS 설정은 대상 환경에서 결정되며, 이번 재작성에서 새 연결을 실행하거나 패킷을 수집하지 않았습니다. [S1–S4]

## 전체 인과 지도

터미널의 대표 주소와 특정 화물 접수 창구, 차량이 외부로 나갈 때 쓰는 출구 번호는 같은 주소가 아닙니다. 먼저 어떤 업무를 위한 주소인지 알아야 경로를 따라갈 수 있습니다.

User Cluster의 Kubernetes API, Application Ingress, 외부 통신용 SNAT IP를 구분합니다. 요청은 대상 FQDN이 해석한 주소와 포트로 들어오며, LB의 Virtual Service·Pool과 Kubernetes Service·Endpoint, APISIX Listener·Route·Upstream의 실제 연결에 따라 Backend로 전달됩니다.

터미널에 앞쪽 반입로와 뒤쪽 배송로가 있다고 발송인 표기가 자동으로 유지되지는 않습니다. 도로 배치와 주소를 바꾸는 규칙은 별개의 결정입니다.

Two-Arm LB는 앞·뒤 Network 배치와 관련된 구조입니다. SNAT, Source IP 보존, Proxy Protocol, HTTP 전달 Header, 반환 Route는 그 위의 별도 설정입니다. APISIX가 Client 연결을 받고 Backend에 새 연결을 만들면 두 연결의 네트워크 상대 주소도 달라질 수 있습니다.

화물에 발송인 이름이 적혀 있어도 접수 권한과 배송 승인을 얻었다는 뜻은 아닙니다. 봉인된 화물의 내부 서류는 봉인을 열 수 있는 지점에서만 읽을 수 있습니다.

Client IP 관측, TLS 종료, Token 검증, Backend 권한 확인을 구분해야 합니다. IP를 알아도 Identity가 인증된 것은 아니고, Token이 유효해도 작업 권한이 없을 수 있습니다. 각 단계의 설정과 동일 요청의 실제 응답을 연결해야 최종 통신을 설명할 수 있습니다.

### 진입 주소와 요청 경로

같은 터미널에도 관리 사무실, 화물 접수장, 외부 반출구의 주소가 따로 있습니다. ‘터미널 주소’라는 한 이름으로 합치면 엉뚱한 창구의 상태를 보고 배송 경로가 정상이라고 판단할 수 있습니다.

Kubernetes API External 주소는 Cluster API를 위한 진입이고, Application Ingress 주소는 애플리케이션 요청을 위한 진입입니다. SNAT IP는 내부에서 외부로 나갈 때 출발지로 사용될 수 있는 주소입니다. Gateway Cluster 자체의 API VIP와 APISIX가 User Cluster API를 중계하는 Listener 역시 같은 주소라고 가정하지 않습니다. DKS-C 원문은 일부 User API 경로의 중계·접근 제한을 설명하지만 이를 모든 인터넷 요청의 보편 경로로 확대하지 않습니다. [S1, S2]

안내 주소를 찾은 뒤에는 실제 접수 창구가 열려 있어야 하고, 접수된 물건을 어느 배송지로 보낼지 규칙이 있어야 합니다. 각 단계는 다음 단계가 사용할 대상을 선택합니다.

FQDN은 DNS를 통해 IP로 해석됩니다. Client는 그 IP의 특정 포트로 연결하고, LB의 Virtual Service는 수신 규칙에 맞는 Backend Pool로 전달합니다. Kubernetes Service와 Endpoint는 실제 수신 Pod로 이어지는 대상을 제공하고, APISIX는 Listener에서 받은 요청을 Route 조건에 맞춰 Upstream으로 중계합니다. 이들은 같은 말의 반복이 아니라 주소 해석·수신·대상 선택·실제 전달의 서로 다른 역할입니다. [S1–S3]

| 대상 | 결정하는 것 | 그 상태만으로 보장하지 않는 것 |
|---|---|---|
| FQDN·DNS | 요청 이름이 가리키는 IP | 해당 포트의 연결과 서비스 준비 |
| VIP·Virtual Service | LB가 받는 주소·포트와 수신 규칙 | 모든 Pool member의 정상 |
| Pool | 전달 대상으로 선택할 서버 집합 | Kubernetes의 실제 Endpoint와 일치 |
| Kubernetes Service·EndpointSlice | Cluster 내부 전달 대상 | APISIX Route·Backend 기능 |
| APISIX Listener·Route | 어떤 요청을 받아 어느 Upstream으로 보낼지 | Upstream 연결·인증·응답 성공 |
| Upstream·Backend | 실제 요청 처리 대상 | 원래 Client가 최종 응답을 수신 |

```text
대상 구성에 맞춰 대조할 전달 관계
Client → FQDN의 실제 DNS 결과 → VIP:port / Virtual Service
       → Pool → 해당 Kubernetes Service·Endpoint / APISIX Listener
       → Route가 선택한 Upstream → Backend

모든 배치가 같은 중간 계층을 갖는다는 뜻은 아니다.
같은 이름·비슷한 포트가 아니라 실제 참조와 관측된 연결을 대조한다.
```

터미널 내부의 접수 장부와 배송 장부가 같은 화물을 가리키는지 보려면 시간과 접수 번호를 맞춰야 합니다. 겉모양이 비슷한 다른 배송 기록을 연결하면 경로가 맞아 보이는 착시가 생깁니다.

조사에서도 FQDN·VIP·포트·Virtual Service·Pool member·Service·Pod·Route·Upstream을 같은 요청 시각으로 연결합니다. Backend에서 관측한 접속이 Client에서 시작한 TCP 연결과 반드시 동일한 연결은 아니므로, 중계 구간을 나누어 읽어야 합니다.

### Two-Arm과 주소 변환

터미널의 반입로와 배송로를 분리하는 것은 차량 동선을 나누는 일입니다. 그 구조만으로 차량 번호를 그대로 보낼지, 터미널 번호로 바꿀지까지 정해지지는 않습니다.

Two-Arm LB의 앞·뒤 Network 배치는 수신 측과 Backend 측의 연결 구조입니다. **Two-Arm이라는 이름만으로 SNAT 사용 여부나 Client Source IP 보존을 확정하지 않습니다.** 실제 SNAT 설정, Server 측 반환 Route, 전달 프로토콜이 결과를 결정합니다. [S1, S2]

출고 시 차량 번호를 터미널 번호로 바꾸면 목적지는 터미널을 상대방으로 보게 됩니다. 번호를 유지한다면 목적지가 원래 발송 측으로 응답할 길을 알고 있어야 합니다.

LB가 SNAT을 적용하면 Backend가 보는 네트워크 출발지는 LB 측 변환 주소일 수 있습니다. Source IP를 보존하는 경우에는 Backend의 반환 Route와 비대칭 경로 처리 조건이 맞아야 합니다. 헤더나 별도의 프록시 메타데이터로 원래 주소를 전달하는 방식은 IP 패킷의 출발지를 그대로 보존하는 것과 다릅니다.

| 방식 | Backend에 전달되는 주소 정보 | 필요한 조건 |
|---|---|---|
| LB SNAT | 변환된 네트워크 출발지 | 변환 세션·반환 경로 |
| 네트워크 Source IP 보존 | 원래 Client IP가 출발지로 남는 경로 | LB·Service 전달 방식과 올바른 반환 Route |
| Proxy Protocol | 연결 앞부분의 별도 프록시 메타데이터 | 송신·수신 양쪽의 동일 프로토콜 지원·설정 |
| HTTP 전달 Header | `X-Forwarded-For` 등 애플리케이션 Header | HTTP를 볼 수 있는 프록시와 신뢰 설정 |

터미널의 중간 분류장이 가까운 작업자에게만 물건을 넘기도록 바꾸더라도, 앞 접수창구에서 이미 발송인 표기를 바꿨다면 원래 표기가 저절로 복구되지는 않습니다.

Kubernetes Service의 `externalTrafficPolicy: Local`은 로컬 Endpoint를 이용하는 전달과 Source IP 보존에 관련되지만, 앞단 LB가 이미 SNAT한 원래 주소를 되살리지는 않습니다. Local 설정에서는 트래픽을 받는 Node에 유효한 로컬 Endpoint가 있는지와 LB health check가 그 상태를 반영하는지가 중요합니다. Cluster 설정의 전달·NAT 가능성과 Local 설정의 대상 선택을 실제 네트워크 경로 안에서 구분합니다. [S4]

### APISIX가 받는 연결과 보내는 연결

중계 직원이 발송인의 물건을 받아 배송지에 다시 보내면, 접수 기록의 상대는 발송인이지만 배송지에서 직접 상대하는 사람은 중계 직원입니다. 두 배송 기록을 연결하려면 원래 발송인 정보가 어떤 방식으로 전달됐는지 알아야 합니다.

APISIX에는 **Client→APISIX 수신 연결**과 **APISIX→Backend 송신 연결**이 있습니다. Backend의 TCP peer가 APISIX인 것은 중계 구조에서 자연스러운 결과일 수 있습니다. 원래 Client IP가 필요하면 HTTP Header나 Proxy Protocol 등 해당 경로에서 지원하는 방법을 통해 전달·검증해야 합니다. 두 구간의 5-tuple은 다를 수 있습니다. [S3]

```text
연결 1: Client ── TCP/TLS/HTTP ──> APISIX
연결 2: APISIX ── 별도 연결 ─────> Backend

Backend의 네트워크 peer와 원래 Client는 같지 않을 수 있다.
전달 Header / Proxy Protocol / 요청 식별자는 연결을 설명하는 보조 정보다.
```

상자에 발송인이 적어 둔 이름을 아무 검증 없이 공식 발송인으로 기록하면 누구나 다른 이름을 적을 수 있습니다. 신뢰하는 접수창구가 확인한 표기와 임의로 붙인 메모를 구별해야 합니다.

`X-Forwarded-For`는 값이 존재한다는 사실만으로 신뢰할 수 없습니다. 신뢰하는 Proxy가 덧붙이거나 정리한 값인지 확인해야 합니다. APISIX real-ip의 `source`, `trusted_addresses`, `recursive` 같은 설정은 어느 정보와 어느 Proxy 경계를 신뢰하여 주소를 해석하는지와 관계됩니다. 설정된 값과 신뢰 체인에 따라 결과가 달라지므로 예제만으로 현재 배포의 실제 Client IP 판정을 단정하지 않습니다. [S3]

로그의 ‘발송인’ 칸이 원래 운송 차량 번호인지 접수창구에서 다시 해석한 정보인지 알아야 기록을 비교할 수 있습니다.

NGINX 계열의 `$remote_addr`도 real-ip 처리 설정에 따라 해석된 주소일 수 있습니다. 이를 항상 가공 전 TCP peer라고 전제하지 않습니다. 패킷에서 본 peer, 프록시가 전달한 주소, 애플리케이션이 신뢰한 Client IP, 로그에 표시된 필드를 나누어 설명해야 합니다. [S4]

### TLS와 전달 가능한 정보

봉인된 화물을 그대로 중계하는 창구는 상자 안의 서류를 고칠 수 없습니다. 봉인을 열어 다시 포장하는 창구라면 내부 배송 지시서를 읽고 추가할 수 있지만, 그 뒤의 배송에는 새로운 봉인이 필요할 수 있습니다.

TLS passthrough와 termination은 HTTP Header를 처리할 수 있는 위치를 바꿉니다. 앞단이 TLS를 그대로 통과시키는 경우 HTTP 내용을 읽고 `X-Forwarded-For`를 추가할 수 없으며, TLS를 종료하면 HTTP 정책과 Header 처리에 참여할 수 있습니다. Backend로 다시 TLS를 연결하는 재암호화는 별도의 연결·인증서 검증 조건을 갖습니다.

| TLS 배치 | 해당 중계 지점의 처리 범위 | 구분할 조건 |
|---|---|---|
| Termination | TLS를 종료하고 HTTP 내용 처리 가능 | Client→중계 인증서와 이후 전달 방식 |
| 종료 후 재암호화 | HTTP 처리 뒤 Backend로 별도 TLS 연결 | 두 TLS 구간의 신뢰·SNI·인증서 조건 |
| Passthrough | 암호화된 흐름을 전달 | HTTP Header 삽입 불가, 실제 종료 지점의 처리 |

별도 봉투에 운송 메타데이터를 붙이는 약속은 받는 창구도 그 약속을 알아야 작동합니다. 보내는 쪽만 사용하면 받는 쪽은 잘못된 내용으로 받아들일 수 있습니다.

Proxy Protocol은 송신·수신 양쪽이 지원하고 해당 Listener에 맞게 설정되어야 합니다. Backend 포트가 HTTPS라는 사실이나 Kubernetes API라는 사실만으로 이를 지원한다고 가정하지 않습니다. HTTP Header, Proxy Protocol, TLS, IP SNAT은 서로 다른 계층의 기능이므로 하나의 설정으로 나머지까지 자동 해결되는 것처럼 설명하지 않습니다.

### IP·인증·권한·최종 응답

발송인의 출발 주소를 알아도 그 사람이 어떤 업무를 요청할 자격이 있는지는 별도입니다. 출입증을 발급받았다고 모든 보관실의 물품을 반출할 권한이 생기는 것도 아닙니다.

Client IP 관측은 신원 인증과 같지 않습니다. Keycloak Token 발급, 수신 측 Token 검증, Backend Authorization, 실제 처리 응답을 나눠야 합니다. APISIX의 인증 Plugin이나 Backend 인증을 사용하는 Route에만 해당 인증 흐름을 연결하며, 공개 Route까지 동일하게 가정하지 않습니다. `401`·`403`은 구분에 도움이 되지만 코드 하나만으로 어느 구성요소가 어떤 이유로 거절했는지 확정하지 않습니다. [S1, S3]

배송지에서 접수 확인을 보냈어도 원래 발송인이 정상 결과를 받았는지 봐야 배송을 닫을 수 있습니다. 중간 창구의 응답을 최종 업무 완료로 바꾸지 않습니다.

최종 판단은 Client가 의도한 보호 경로를 호출하여 기대한 응답 코드·본문·기능을 받았는지로 합니다. VIP 연결, Route Match, Token 발급만으로 이를 대신하지 않습니다. 동일 요청을 경계별로 연결할 때는 시각·요청 식별자와 변환 전후 주소를 함께 사용하며, 모든 구간에 동일 TCP 연결 ID가 남아 있다고 전제하지 않습니다.

| 증상 | 먼저 구분할 경계 | 대조할 정보 |
|---|---|---|
| FQDN 접속 실패 | DNS와 목적 진입 주소 | 실제 해석 IP·포트·환경 |
| VIP 연결 실패 | LB Listener·정책·반환 경로 | Virtual Service, 연결 관측 |
| 일부 Node에서만 실패 | Pool 대상·Local Endpoint | health check, Service 정책, EndpointSlice |
| APISIX에 도달하나 잘못된 경로 | Listener·Route Match | host/path/method·Route·Upstream |
| Backend peer가 예상과 다름 | SNAT와 별도 프록시 연결 | 변환 전후 tuple·전달 정보 |
| X-Forwarded-For 값이 신뢰되지 않음 | Header 작성자와 trusted proxy | real-ip 설정, 원래 Header·peer |
| 인증·권한 오류 | TLS·Token 검증·Authorization | 해당 요청의 오류 주체와 보호 경로 |
| Backend는 응답하나 Client 실패 | 반환 경로·중계·응답 처리 | 양방향 패킷·동일 요청 응답 |

#### 제한된 조회 예시

터미널의 특정 배송 건을 조사할 때 전체 화물을 열어 보는 대신 해당 시간·목적지의 장부부터 좁혀 읽어야 합니다.

아래는 원문의 조회 의도를 보존한 예시입니다. 변수는 실제 대상에 맞춰 확인해야 하며 이번에 실행하지 않았습니다. 패킷 수집은 권한이 있는 관측 지점에서 승인된 범위와 보관 정책을 따릅니다. 암호화되지 않은 Credential이나 Header가 수집·노출될 가능성도 고려합니다.

```bash
kubectl --context="$GATEWAY_CONTEXT" -n "$APISIX_NAMESPACE" get service "$APISIX_SERVICE" -o yaml
kubectl --context="$GATEWAY_CONTEXT" -n "$APISIX_NAMESPACE" get endpointslices \
  -l "kubernetes.io/service-name=$APISIX_SERVICE" -o yaml

# 해당 관측 호스트에서 반환 경로를 확인하는 예시
ip route get "$CLIENT_IP"

# 해당 지점에서 실제로 보일 주소로 필터를 정한 제한적 수집 예시
tcpdump -nn -i "$IFACE" -c 20 "host $CLIENT_IP and tcp port $PORT"
```

SNAT 뒤의 지점에서 NAT 전 주소만 필터링하면 해당 패킷이 안 보일 수 있습니다. 따라서 ‘수집 결과 없음’을 경로 단절로 읽기 전에 지점·시각·변환 후 주소와 필터가 맞는지 확인합니다.
