# 서비스 노출 - Ingress 구성

VKS 사용자 클러스터는 클러스터가 생성될 때 외부의 트래픽을 받아서 운영할 수 있는 `envoy` 와 `contour` GatewayClass 까지만 생성됩니다. VKS 사용자 클러스터에 대한 외부 접근을 허용하기 위해서는 정식 도메인 발급과 TLS 인증서 등을 사용해서 Ingress 설정을 직접 수행하셔야 합니다.

※ Ingress 흐름도 (원문 이미지, 붙여넣기에 없음)

## 사전 준비

사전 작업(도메인 신청, 방화벽 오픈)은 [[15. 서비스 노출 - Gateway 구성]]의 "사전 준비"와 동일하다. 원문도 같은 문구를 반복한다.

### 1. 사전 작업: 도메인 신청이 완료 되어야 합니다.

※ 도메인(Wildcard Domain) 신청이 완료 되어야 합니다. 도메인 신청은 **Ingress IP**로 신청해야 합니다.

### 2. 사전 작업: 방화벽 오픈

※ 외부 시스템에서 DKS-C 서비스 접근이 필요할 때는 방화벽 오픈이 필요합니다.
※ Ingress IP (LB)는 **80, 443 port만** 열려 있습니다. Cluster 별로 IP를 분리하여 제공하기 때문에 할당 받으신 Ingress IP를 dest로 방화벽 신청해야 합니다.

| Source | Destination |
|---|---|
| 외부시스템, local 등 | DKS Pod (Ingress IP) |

※ DKS-C 서비스에서 외부 시스템 접근이 필요할 때는 방화벽 오픈이 필요합니다. Cluster 별로 IP를 분리하여 제공하기 때문에 할당 받으신 Egress IP를 source로 방화벽 신청해야 합니다.

| Source | Destination |
|---|---|
| DKS Pod (Egress IP) | 외부시스템 |

## Ingress 생성 하기

참고문서: https://projectcontour.io/docs/1.33/config/annotations/

어노테이션은 Kubernetes Ingress API에서 다루지 않는 기능을 구성하기 위해 Ingress 컨트롤러에서 사용됩니다. Contour의 HTTPProxy API 는 기존에 어노테이션을 통해 구성되던 일부 기능을 기본 기능으로 지원하며, 어노테이션보다 더욱 강력한 구성 인터페이스를 제공합니다.

※ Contour HTTPProxy를 통한 고도화된 라우팅 활용 안내: 기존 쿠버네티스의 기본 Ingress 환경에서는 복잡한 라우팅을 처리하기 위해 수많은 annotation(주석)을 복잡하게 추가해야 했습니다. 이는 가독성이 떨어지고 관리가 어렵다는 단점이 있습니다. HTTPProxy CRD를 사용하면, 복잡한 주석 없이 쿠버네티스 고유의 설정 방식으로 정교한 라우팅을 안전하고 직관적으로 구현할 수 있습니다. → [[16. 서비스 노출 - HTTPProxy 구성]]

- VKS 클러스터의 외부 트래픽을 분기 하기 위한 Kubernetes Ingress API 입니다.

> [!warning]
> Ingress와 Gateway API 병행 시, 동일 도메인(Host)에 대한 설정 중복으로 인한 트래픽 경로 누락 및 라우팅 간섭 주의

> [!warning] 한계점 안내
> standard Ingress 구조에서 헤더 변경(Header Manipulation) 및 쿠키 기반 스티키 세션(Sticky Session) 기능은 Contour 어노테이션으로 지원되지 않습니다. 해당 기능들이 필수라면 반드시 앞서 안내해 드린 `HTTPProxy` CRD를 사용해야 합니다.

### Contour 전용 고급 설정 주석(Annotations) 가이드

#### 1. Ingress 전용 주석 (Ingress Annotations)

인그레스 레벨에 적용되어 트래픽의 라우팅 정책, 보안 규격, 프로토콜 업그레이드를 통제합니다.

| 주석(Annotation) 이름 | 설명 및 사용 방법 | 입력 값 예시 |
|---|---|---|
| `projectcontour.io/num-retries` | [재시도 횟수] 백엔드 서버 요청 실패 시, 최대 몇 번까지 다시 요청을 보낼지(Retry) 지정합니다. (retry-on 주석과 함께 쓰여야 활성화됩니다.) | `"3"` |
| `projectcontour.io/per-try-timeout` | [개별 재시도 제한 시간] 재시도를 진행할 때마다 적용할 개별 타임아웃입니다. 이 시간 동안 서버 응답이 없으면 해당 회차는 실패로 간주하고 다음 회차로 넘어갑니다. | `"10s"`, `"1m"` |
| `projectcontour.io/response-timeout` | [전체 응답 대기 시간] 프록시가 백엔드 서버의 최종 응답을 기다리는 총시간입니다. (기본값: 15초). 대용량 다운로드나 장시간 연산이 필요한 서비스는 필수 연장이 필요합니다. 무제한은 "infinity"입니다. | `"120s"`, `"infinity"` |
| `projectcontour.io/retry-on` | [재시도 트리거 조건] 백엔드에서 어떤 에러 상태 코드가 반환되었을 때 재시도를 수행할지 결정합니다. 콤마(,)로 여러 조건을 연결할 수 있습니다. | `"5xx,gateway-error"` |
| `projectcontour.io/tls-minimum-protocol-version` | [최소 TLS 보안 버전] 안전한 HTTPS 통신을 위해 허용할 최소 TLS 프로토콜 버전을 제한합니다. 취약점이 발견된 1.1 이하 버전을 차단하기 위해 "1.2" 이상 설정을 강력히 권장합니다. | `"1.2"`, `"1.3"` |
| `projectcontour.io/tls-maximum-protocol-version` | [최대 TLS 보안 버전] 프록시가 허용할 최대 TLS 프로토콜 버전을 제한합니다. 특정 구형 클라이언트와의 암호화 호환성 유지가 필요한 예외적인 상황에만 제한적으로 사용합니다. | `"1.3"` |
| `projectcontour.io/websocket-routes` | [웹소켓 전용 경로 지정] 실시간 양방향 통신(WebSocket) 프로토콜 업그레이드를 허용할 특정 경로(Path)들을 명시합니다. 하단의 `spec.rules.http.paths`에 정의된 경로와 완벽히 일치해야 작동합니다. | `"/echo-ws,/chat"` |
| `projectcontour.io/tls-cert-namespace` | [인증서 네임스페이스 지정] TLS 인증서(Secret)가 인그레스와 다른 네임스페이스에 존재할 때, 해당 시크릿이 위치한 네임스페이스 이름을 명시하여 공유 인증서를 참조할 수 있게 합니다. | `"shared-cert-ns"` |

#### 2. Service 전용 주석 (Service Annotations)

쿠버네티스 서비스(Service) 오브젝트 레벨에 적용되어, 특정 백엔드로 향하는 트래픽의 임계치(과부하 방지) 및 프로토콜 규격을 상세 제어합니다.

| 주석(Annotation) 이름 | 설명 및 사용 방법 | 입력 값 예시 |
|---|---|---|
| `projectcontour.io/max-connections` | [최대 동시 연결 수] Contour(Envoy) 프록시가 해당 서비스의 백엔드 파드들로 연결할 수 있는 총 동시 HTTP/1.1 커넥션의 최대 개수를 제한합니다. (서버 과부하 방지 서킷 브레이커 기능) | `"1024"` |
| `projectcontour.io/max-pending-requests` | [최대 대기 요청 수] 백엔드 파드가 모든 연결을 처리 중일 때, 프록시 단에서 연결을 맺지 못하고 큐(Queue)에 쌓여 대기할 수 있는 최대 요청 수를 제한합니다. 초과 시 즉시 에러가 반환됩니다. | `"100"` |
| `projectcontour.io/max-requests` | [최대 동시 처리 요청 수] 대용량 고성능 처리가 가능한 HTTP/2 프로토콜 환경에서, 해당 서비스로 동시에 보낼 수 있는 활성화된 총 요청(Requests)의 최대 개수를 제한합니다. | `"2048"` |
| `projectcontour.io/max-retries` | [클러스터 총 재시도 허용 수] 해당 서비스의 전체 백엔드 파드들을 대상으로, 프록시가 동시에 진행할 수 있는 총 재시도(Retry)의 합계 횟수를 제한합니다. 시스템 장애 시 재시도 폭풍(Retry Storm)으로 인한 2차 장애를 막습니다. | `"3"` |
| `projectcontour.io/per-host-max-connections` | [호스트별 최대 연결 수] 개별 백엔드 파드(Pod) 하나당 연결할 수 있는 최대 커넥션 수를 지정합니다. 서비스 전체가 아닌 개별 컨테이너 단위의 정밀한 부하 제어가 필요할 때 사용합니다. | `"256"` |
| `projectcontour.io/upstream-protocol.{protocol}` | [백엔드 통신 프로토콜 정의] Contour 프록시가 서비스(백엔드 파드)와 내부적으로 통신할 때 사용할 프로토콜을 강제 지정합니다. 주석 명 뒤의 {protocol} 자리에 서비스 포트 이름을 매칭하여 선언합니다. | 주석명: `projectcontour.io/upstream-protocol.h2`, 값: `"h2c"` (암호화 없는 HTTP/2) |

> [!note]
> 원문 표의 마지막 행 주석명은 `..upstream-protocol.h2`로 앞부분이 생략돼 있다. 위 표는 같은 표의 다른 행 접두어(`projectcontour.io/`)를 보고 채웠으니 원문 확인이 필요하다.

### Ingress 설정 요약

- `ingressClassName`: 시스템에서 자동 생성한 contour controller 사용 (고정값)
- `tls`: 도메인 인증서
- `host`: 사용자 서비스 연결 도메인
- `backend`: 사용자 서비스 연결

참고: https://github.com/traefik/whoami

#### 방법 1) yaml을 통한 인증서 secret 생성

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: test-cert
  namespace: test-user
type: kubernetes.io/tls
data:
  tls.crt: |
    MIIC2DCCAcCgAwIBAgIBATANBgkqhkiG9w0BAQsFADAD...   # Base64 인코딩된 인증서 데이터
  tls.key: |
    MIIEogIBAAKCAQEAw3z9R4L2o9X...                     # Base64 인코딩된 개인키 데이터
```

#### 방법 2) kubectl 을 통해서도 가능합니다.

이때 인증서 파일 내용은 base64 encoding 된 것이 아니라 원본이면 됩니다.

```bash
kubectl -n test-user create secret tls public-cert \
  --cert=./tls.crt \
  --key=./tls.key
```

#### 테스트 백엔드 및 Ingress

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: whoami-test
  namespace: test-contour
spec:
  replicas: 2   # 스티키 세션 테스트를 위해 파드를 2개 띄웁니다.
  selector:
    matchLabels:
      app: whoami
  template:
    metadata:
      labels:
        app: whoami
    spec:
      containers:
      - name: whoami
        image: packages-dev.dks.samsungds.net/docker.io/traefik/whoami:latest
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: whoami-service
  namespace: test-contour
spec:
  ports:
  - port: 80
    targetPort: 80
  selector:
    app: whoami
```

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: contour-ingress
  namespace: test-contour
  annotations:
    # -----------------------------------------------------------------
    # [1] 트래픽 보안 및 SSL 제어 (우선순위 및 동작 방식 주의)
    # -----------------------------------------------------------------
    # 방법 A: HTTP 접근 원천 차단 (HTTP 라우트 자체를 생성하지 않음)
    # http:// 접속 시 https://로 자동 전환되지 않고 접속 실패(404 등) 처리됩니다.
    kubernetes.io/ingress.allow-http: "false"

    # 방법 B: HTTPS 자동 리다이렉트 (HTTP 요청을 HTTPS로 강제 이동)
    # http:// 접속 시 브라우저 주소를 https://로 자동 전환해 줍니다.
    # 주의: 하나의 파일에 'kubernetes.io/ingress.allow-http' 주석이 포함되어 있으면 'force-ssl-redirect'가 우선권을 가집니다.
    ingress.kubernetes.io/force-ssl-redirect: "true"

    # 사용할 최소 TLS 프로토콜 버전을 지정합니다. (값: "1.2" 또는 "1.3") (기본값: "1.2")
    projectcontour.io/tls-minimum-protocol-version: "1.2"

    # 사용할 최대 TLS 프로토콜 버전을 지정합니다. (값: "1.2" 또는 "1.3") (기본값: "1.3")
    projectcontour.io/tls-minimum-protocol-version: "1.2"

    # -----------------------------------------------------------------
    # [2] 타임아웃 및 업로드 용량 제한
    # -----------------------------------------------------------------
    # 서버(백엔드)가 응답을 마칠 때까지 기다리는 최대 시간입니다. (기본값 15초)
    # Go 언어 시간 형식(s, m, h)을 따릅니다. 무제한은 "infinity"로 설정합니다.
    projectcontour.io/response-timeout: "120s"

    # -----------------------------------------------------------------
    # [3] 요청 실패 시 재시도(Retry) 정책
    # -----------------------------------------------------------------
    # 어떤 에러 조건 발생 시 백엔드 서버에 재시도할지 결정합니다.
    # 주요 값: 5xx, gateway-error, connect-failure, retriable-4xx 등
    projectcontour.io/retry-on: "5xx,gateway-error"

    # 요청이 실패했을 때 최대 몇 번까지 다시 시도할지 횟수를 지정합니다.
    projectcontour.io/num-retries: "3"

    # -----------------------------------------------------------------
    # [4] 웹소켓(WebSocket) 활성화
    # -----------------------------------------------------------------
    # 웹소켓 프로토콜 통신을 허용할 특정 경로(Path)들을 콤마(,)로 구분하여 명시합니다.
    # 하단의 spec.rules.http.paths에 정의된 경로와 반드시 일치해야 작동합니다.
    projectcontour.io/websocket-routes: "/"

    # -----------------------------------------------------------------
    # [5] TLS Secret 네임스페이스 지정
    # -----------------------------------------------------------------
    # 웹소켓 프로토콜 통신을 허용할 특정 경로(Path)들을 콤마(,)로 구분하여 명시합니다.
    # 하단의 spec.rules.http.paths에 정의된 경로와 반드시 일치해야 작동합니다.
    projectcontour.io/websocket-routes: "/"
spec:
  ingressClassName: contour   # 시스템 자동 설치된 contour controller 사용 (고정값)
  tls:
  - hosts:
    - app.example.com
    secretName: public-cert   # HTTPS 통신을 위한 인증서 Secret 이름
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: whoami-service
            port:
              number: 80
```

> [!warning] 원문 불일치
> 위 YAML은 원문 그대로이며 다음이 어긋나 있다.
> - "최대 TLS 버전" 설명 아래 키가 `tls-maximum-protocol-version`이 아니라 `tls-minimum-protocol-version`으로 중복돼 있다.
> - [5] "TLS Secret 네임스페이스 지정" 설명 아래 키가 `tls-cert-namespace`가 아니라 `websocket-routes`로 중복돼 있다.
> - `allow-http: "false"`와 `force-ssl-redirect: "true"`를 동시에 적었는데, 원문 주석은 둘이 함께 있으면 `force-ssl-redirect`가 우선한다고 설명한다.
> - 검증의 웹소켓 테스트는 `/echo` 경로를 쓰지만 `websocket-routes`는 `/`만 허용한다.
