# (DKS-C 콘솔) HA 구성을 위한 podAntiAffinity 적용 가이드

## 개요

podAntiAffinity는 동일한 라벨을 가진 Pod가 같은 노드에 함께 배치되지 않도록 제한하여, 장애 전파를 최소화하고 고가용성을 확보하기 위한 핵심 스케줄링 기능입니다.

## 적용 목표

하나의 노드가 죽더라도 동일한 application의 다른 인스턴스가 다른 노드에 살아있도록 함

## 적용 예시

### Deployment에 적용하는 예 (hostname 기준 분산)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: webapp
  template:
    metadata:
      labels:
        app: webapp
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - webapp
              topologyKey: "kubernetes.io/hostname"
```

설명

- `replicas`: 2개 이상으로 설정하여 다중화 구성
- `requiredDuringSchedulingIgnoredDuringExecution`: 스케줄링 시 반드시 지켜야 하는 규칙
- `labelSelector`: 대상 Pod 라벨 (자기 자신 포함)
- `topologyKey: kubernetes.io/hostname`: hostname 이 다른 곳에 배치되도록 분산

### preferredDuringSchedulingIgnoredDuringExecution 예시

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: webapp
  template:
    metadata:
      labels:
        app: webapp
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - webapp
              topologyKey: "kubernetes.io/hostname"
```

> [!warning] 원문 불일치
> 위 예시는 제목이 `preferred...`인데 원문 YAML은 `requiredDuringSchedulingIgnoredDuringExecution`이다. 원문 그대로 옮겼다. `preferred`로 쓰려면 `preferredDuringSchedulingIgnoredDuringExecution` 아래에 `weight`와 `podAffinityTerm`을 둬야 하는데 원문에는 없다.

언제 쓰나? HA는 중요하지만, 노드 수나 자원이 부족할 경우엔 조건을 만족하지 않더라도 스케줄링될 수 있음

## 규칙 기준별 정리 표

| 규칙 | 필수 여부 | 시점 | 설명 |
|---|---|---|---|
| requiredDuringScheduling | O | 스케줄링 시 | 이 조건을 만족하지 않으면 스케줄 자체가 실패함. |
| preferredDuringScheduling | X (선호사항) | 스케줄링 시 | 만족하면 좋지만, 만족하지 않아도 스케줄은 됨. |
| requiredDuringExecution | O | 실행 중 (런타임) | 실행 도중에도 항상 만족해야 함. 만족하지 않으면 파드 중단 가능. (현재는 거의 사용 안 함) |
| preferredDuringExecution | X (선호사항) | 실행 중 (런타임) | 실행 중 만족하면 좋지만, 필수는 아님. (K8s에서 직접 쓰이지는 않음) |

## 검증 방법

- `kubectl get pods -o wide` → Pod들이 서로 다른 노드에 배포되었는지 확인
- `kubectl describe pod <pod-name>` → Events에서 "Found existing pod with same label in topology..." 등 로그 확인 가능

## 기타 참고 사항

DaemonSet에는 적용하지 않음 (노드당 1개 Pod 필수라 의미 없음)

## 결론

podAntiAffinity는 고가용성을 위한 기본적인 보장 메커니즘입니다. 적절한 topologyKey 선택과 함께 required/preferred 사용 전략을 잘 설계하면 복제된 애플리케이션들이 장애 전파 없이 안전하게 분산 배치될 수 있습니다.
