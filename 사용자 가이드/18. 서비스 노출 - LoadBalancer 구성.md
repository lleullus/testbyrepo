# 서비스 노출 - LoadBalancer 구성

VKS 사용자 클러스터는 클러스터가 생성될 때 외부의 트래픽을 받아서 운영할 수 있는 LoadBalancer IP 수는 **2개** 입니다. VKS 사용자 클러스터에 대한 외부 접근을 허용하기 위해서는 정식 도메인 발급과 TLS 인증서 등을 사용해서 `LoadBalancer` 처리를 직접 수행하셔야 합니다.

※ Kubernetes Service LoadBalancer 흐름도 (원문 이미지, 붙여넣기에 없음)

## LoadBalancer 생성 하기

- VKS 클러스터의 외부 트래픽을 분기 하기 위한 Kubernetes Service 입니다.
- 쿠버네티스의 LoadBalancer 타입 서비스는 외부 사용자가 클러스터 내부의 애플리케이션(예: DB, 웹 서비스)에 접근할 수 있도록 고유한 가상 IP(VIP)를 발급하고, 외부 트래픽을 안전하게 인입하여 여러 워커 노드로 균등하게 분산하는 '단일 진입점' 역할을 수행합니다.

※ LoadBalancer type으로 서비스를 생성하면 외부 IP를 할당 받습니다.

```yaml
# 외부 노출용 서비스
apiVersion: v1
kind: Service
metadata:
  name: postgres-test-svc
  namespace: test-contour
spec:
  type: LoadBalancer
  ports:
  - port: 5432
    targetPort: 5432
    nodePort: 30432
    protocol: TCP
  selector:
    app: postgresql
```

> [!warning] 정책 충돌 가능성
> 위 예제는 `nodePort`를 지정했지만, [[14. (DKS-C 콘솔) Service 배포]]는 "서비스의 External IP와 NodePort는 정책상 사용이 불가"라고 안내한다. 원문 그대로 옮겼으며 적용 전 확인이 필요하다.

## 예제 1. MySQL (StatefulSet + LoadBalancer)

작업 순서(원문 스크린샷 캡션): ▣ 스테이트풀셋 생성 → ▣ 서비스 생성 → ▣ 서비스 외부 IP 확인 → ▣ mysql 파드 확인 → ▣ 외부에서 접속 확인 - DBeaver Connection 확인

테스트를 위해 윈도우 hosts 파일에 도메인 추가

- 경로: `C:\Windows\System32\drivers\etc\hosts`
- 테스트 도메인 추가: `10.169.63.137 mysql.example.com`

※ DBeaver(디비버) `Public Key Retrieval is not allowed` 에러 발생시 Driver properties 탭에 들어가서 `allowPublicKeyRetrieval`의 값을 `TRUE`로 변경합니다.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql-test
  namespace: test-contour
spec:
  serviceName: mysql-headless
  replicas: 2
  selector:
    matchLabels:
      app: mysql-test
  template:
    metadata:
      labels:
        app: mysql-test
    spec:
      containers:
      - name: mysql-test
        image: kh-dev-wda-harbor.samsungds.net/docker.io/library/mysql:8.3.0
        env:
        - name: MYSQL_ROOT_PASSWORD
          value: "securepassword"
        - name: MYSQL_USER
          value: "test"
        - name: MYSQL_PASSWORD
          value: "test"
        - name: MYSQL_DATABASE
          value: "test"
        ports:
        - containerPort: 3306
          name: mysql-test
        volumeMounts:
        - name: mysql-data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:
  - metadata:
      name: mysql-data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "netapp-nfs"   # StorageClass 이름 매핑
      resources:
        requests:
          storage: 3Gi
```

```yaml

  name: mysql-test-svc

    nodePort: 30306
    protocol: TCP

```

```yaml
    app: mysql-test
```

## 예제 2. PostgreSQL + TLS (mTLS)

작업 순서(원문 스크린샷 캡션): ▣ 시크릿 생성 → ▣ 컨피그맵 생성 → ▣ 스테이트풀셋 생성 → ▣ 외부 노출용 서비스 생성 → ▣ StatefulSet 내부 관리를 위한 Headless 서비스 생성

### 사설 CA 및 서버 인증서 생성 스크립트

```bash
#!/bin/bash

# 에러 발생 시 스크립트 중단
set -e

# ==========================================
# 사용자 정의 변수 (환경에 맞게 수정 가능)
# ==========================================
DOMAIN="://example.com"
DAYS=365

echo "=================================================="
echo "사설 CA 및 [$DOMAIN] 서버 인증서 생성을 시작합니다."
echo "=================================================="

# --------------------------------------------------
# 1단계: 사설 Root CA 생성 (가상의 인증기관 설립)
# --------------------------------------------------
echo "[1/4] 사설 Root CA 개인키 및 인증서 생성 중..."
openssl genrsa -out ca.key 4096
openssl req -new -x509 -days "$DAYS" -key ca.key -out ca.crt \
  -subj "/CN=MyCompany-Test-Root-CA"

# --------------------------------------------------
# 2단계: 서버(DB)용 개인키 및 CSR(인증요청서) 생성
# --------------------------------------------------
echo "[2/4] 서버용 개인키 및 인증요청서(CSR) 생성 중..."
openssl genrsa -out tls.key 2048
openssl req -new -key tls.key -out server.csr \
  -subj "/CN=$DOMAIN"

# --------------------------------------------------
# 3단계: 사설 CA의 비밀키로 서버 인증서 승인 및 발급
# --------------------------------------------------
echo "[3/4] 사설 CA 도장으로 서버 인증서 발급 중..."
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -out tls.crt -days "$DAYS" -sha256

# 임시 생성된 CSR 및 시리얼 파일 삭제
rm -f server.csr ca.srl

# --------------------------------------------------
# 4단계: 파일 권한 조정 (보안 가이드 준수)
# --------------------------------------------------
echo "[4/4] 파일 권한 안전하게 조정 중..."
chmod 600 ca.key tls.key
chmod 644 ca.crt tls.crt

echo "=================================================="
echo "모든 인증서 파일 생성이 완료되었습니다!"
echo "--------------------------------------------------"
echo "생성된 파일 핵심 3종 세트:"
echo " 1. ca.crt  -> 클라이언트(사용자 PC/DB 툴) 신뢰 등록용 인증서"
echo " 2. tls.crt -> K8s 포드(DB) 탑재용 서버 인증서"
echo " 3. tls.key -> K8s 포드(DB) 탑재용 서버 개인키"
echo "=================================================="
```

> [!note]
> 원문 `DOMAIN="://example.com"`은 `*.example.com` 또는 `example.com`이 잘못 붙여넣어진 값으로 보인다. 원문 그대로 옮겼다.

### Secret (TLS)

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: postgresql-tls-secret
  namespace: test-contour
  labels:
    app: postgresql
type: kubernetes.io/tls
data:
  ca.crt: <Base64 인코딩된 CA 인증서>
  tls.crt: <Base64 인코딩된 서버 인증서>
  tls.key: <Base64 인코딩된 서버 개인키>
```

> [!note] 생략한 내용
> 원문에는 샘플 `ca.crt`, `tls.crt`, `tls.key`의 실제 Base64 값이 들어 있다. 개인키가 포함돼 있고 값 길이가 길어 재타이핑 중 오염될 위험이 있어, 이 노트에서는 자리표시자로 바꿨다. 값이 필요하면 위 스크립트로 새로 생성한다.

### ConfigMap (pg_hba.conf)

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: postgresql-tls-config
  namespace: test-contour
  labels:
    app: postgresql
data:
  # 1. 수정할 hba 설정
  pg_hba.conf: |
    # 내부 로컬 접속은 비밀번호 요구
    local   all   all                   md5
    host    all   all   127.0.0.1/32    md5
    host    all   all   ::1/128         md5

    # 외부 원격 접속은 '오직 SSL 암호화 통신'만 허용하고, 강력한 암호 인증 사용
    # 옵션: 서버에서 강제 하려면 clientcert=verify-ca 옵션 추가 - mTLS (상호 TLS, Mutual TLS) 통신을 의미합니다.
    hostssl all   all   0.0.0.0/0       scram-sha-256 clientcert=verify-ca
    # hostssl all all 0.0.0.0/0 scram-sha-256
```

### StatefulSet

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgresql-test
  namespace: test-contour
  labels:
    app: postgresql
spec:
  serviceName: postgresql-headless   # StatefulSet의 고유 네트워크 식별자를 위한 헤드리스 서비스
  replicas: 2                        # 2개의 파드 생성
  selector:
    matchLabels:
      app: postgresql
  template:
    metadata:
      labels:
        app: postgresql
    spec:
      securityContext:
        fsGroup: 1001
        runAsUser: 1001
      # 1. 초기화 컨테이너: Secret 파일을 emptyDir로 복사 후 권한 세팅 (root 권한으로 실행)
      initContainers:
      - name: init-chmod-certs
        image: kh-dev-wda-harbor.samsungds.net/docker.io/library/alpine:3.23.2
        # image: kh-dev-wda-harbor.samsungds.net/docker.io/bitnamilegacy/postgresql:17.6.0-debian-12-r4
        command:
        - sh
        - -c
        - |
          cp /tmp/certs/* /certs
          chmod 600 /certs/tls.key
        volumeMounts:
        - name: secret-certs
          mountPath: /tmp/certs
        - name: postgres-certs
          mountPath: /certs
      containers:
      - name: postgres
        image: kh-dev-wda-harbor.samsungds.net/docker.io/bitnamilegacy/postgresql:17.6.0-debian-12-r4
        env:
        # Bitnami 전용 초기 환경 변수 세팅
        # 최고 관리자의 비밀번호
        - name: POSTGRESQL_POSTGRES_PASSWORD
          value: "AdminPassword"
        - name: POSTGRESQL_PASSWORD
          value: "test"
        - name: POSTGRESQL_DATABASE
          value: "test"
        - name: POSTGRESQL_USERNAME
          value: "test"
        - name: POSTGRESQL_ENABLE_TLS
          value: "yes"                 # TLS 기능 활성화
        - name: POSTGRESQL_TLS_CERT_FILE
          value: "/opt/bitnami/postgresql/certs/tls.crt"
        - name: POSTGRESQL_TLS_KEY_FILE
          value: "/opt/bitnami/postgresql/certs/tls.key"
        - name: POSTGRESQL_TLS_CA_FILE
          value: "/opt/bitnami/postgresql/certs/ca.crt"
        ports:
        - containerPort: 5432
        volumeMounts:
        - name: postgres-certs
          mountPath: /opt/bitnami/postgresql/certs
          readOnly: true
        - name: pgdata
          mountPath: /bitnami/postgresql
        - name: config-hba
          mountPath: /bitnami/postgresql/conf/pg_hba.conf   # 여기로 마운트해야 적용됨 (고정값)
          subPath: pg_hba.conf
      volumes:
      - name: secret-certs
        secret:
          secretName: postgresql-tls-secret   # TLS 인증서 Secret 매핑
      - name: config-hba
        configMap:
          name: postgresql-tls-config         # 외부 원격 접속 ssl 설정
      # 권한 수정 후 Bitnami가 안전하게 읽어갈 임시 볼륨
      - name: postgres-certs
        emptyDir: {}
  volumeClaimTemplates:
  - metadata:
      name: pgdata
    spec:
      storageClassName: netapp-nfs
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 1Gi
```

### 확인 방법

▣ 파드 확인 ▣ 서비스 확인 ▣ 외부 접속 확인 (원문 스크린샷 캡션) ※ Use SSL 모드를 활성화 합니다.

내 눈으로 직접 SSL 접속 확인하기: DBeaver에서 해당 연결의 SQL 편집기를 열고 아래 쿼리를 실행해 보세요. 출력 결과 예시: `ssl` 컬럼이 `t` (True)로 나오고, `cipher`에 `TLS_AES_256_GCM_SHA384` 같은 암호화 알고리즘명이 명시된다면 현재 SSL 접속이 완벽히 활성화된 것입니다.

```sql
SELECT ssl, version, cipher, bits FROM pg_stat_ssl WHERE pid = pg_backend_pid();
```

```text
ssl |version|cipher                |bits|
----+-------+----------------------+----+
true|TLSv1.3|TLS_AES_256_GCM_SHA384| 256|
```

## 도메인 신청 및 방화벽 오픈

### 1. 도메인 신청

- ※ 도메인 신청은 K8s service의 LoadBalancer type 으로 생성한 서비스의 외부 IP로 신청해야 합니다.
- ※ K8s service의 LoadBalancer 생성은 위 예제를 참고 하시기 바랍니다.
- ※ 도메인 신청은 DS IAM 에서 진행합니다.

### 2. 방화벽 오픈

- ※ 외부 시스템에서 DKS-C 서비스 접근이 필요할 때는 방화벽 오픈이 필요합니다.
- ※ LoadBalancer의 포트 번호를 방화벽 오픈 신청해야 합니다. Cluster 별로 IP를 분리하여 제공하기 때문에 할당 받으신 K8s service의 LoadBalancer 외부 IP를 dest로 방화벽 신청해야 합니다.

| Source | Destination |
|---|---|
| 외부시스템, local 등 | DKS Pod (Ingress IP) |

- ※ DKS-C 서비스에서 외부 시스템 접근이 필요할 때는 방화벽 오픈이 필요합니다. Cluster 별로 IP를 분리하여 제공하기 때문에 할당 받으신 Egress IP를 source로 방화벽 신청해야 합니다.

| Source | Destination |
|---|---|
| DKS Pod (Egress IP) | 외부시스템 |
