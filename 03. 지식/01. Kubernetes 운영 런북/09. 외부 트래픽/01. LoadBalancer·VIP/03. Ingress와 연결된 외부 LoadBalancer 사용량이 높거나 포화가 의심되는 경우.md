# Ingress와 연결된 외부 LoadBalancer 사용량이 높거나 포화가 의심되는 경우

## 지금 결정

**기본 상태: 관찰**

외부 LB의 `사용량 높음` 알람만으로 Kubernetes 리소스를 변경하지 않는다. 먼저 알람이 가리키는 정확한 provider LB/listener와 Kubernetes의 `Ingress → Ingress controller → LoadBalancer Service` 관계를 확인하고, 같은 UTC 시간창의 실제 서비스 영향과 사용량 차원을 대조한다.

상황 모델은 `외부 client → VIP/listener → Ingress controller → Service/EndpointSlice → backend Pod → application`이다. 외부 LB 알람의 resource ID는 Kubernetes Service나 Ingress 이름이 아니므로 직접 매핑되기 전에는 `kubectl` selector나 resource 이름으로 사용하지 않는다.

## 진입 판단과 경계

| 구분 | 판단 기준 |
|---|---|
| 사용 | 외부 LB provider가 bandwidth, active connection, new connection/sec, packet/sec, LB CPU/queue 또는 quota 사용량 증가를 알리고 대상 LB/listener가 식별된다. |
| 적용 | provider LB resource/listener와 Ingress controller Service UID를 같은 계정·리전·address·port·시간으로 연결할 수 있다. |
| 제외 | EXTERNAL-IP 미할당은 [[01. LoadBalancer Service의 EXTERNAL-IP가 Pending이거나 할당되지 않는 경우]], VIP 연결 실패는 [[02. VIP·External IP가 할당됐지만 외부에서 연결되지 않는 경우]], L7 502/503은 [[08. 인그레스·게이트웨이/03. L7 라우팅·Backend·TLS/02. Ingress·Gateway 요청이 502·503을 반환하는 경우]]로 이동한다. |

알람의 `usage`가 무엇인지 모르면 포화로 확정하지 않는다. bandwidth, active connection, connection rate(CPS), packet rate(PPS), request rate(RPS), latency, LB CPU/queue는 서로 다른 신호다.

## 최초 입력과 증거

| 종류 | 값 | 등록 기준 |
|---|---|---|
| 알람 원문 | provider, account/project, region, LB resource ID, listener/VIP, metric, threshold, UTC window | 알람 화면 또는 provider read-only API 원문에서 exact하게 기록한다. |
| Kubernetes 대상 | context, Ingress namespace/name 또는 host, IngressClass, controller namespace/workload, controller Service namespace/name | inventory·IngressClass·Service 관계로 확인한다. 알람 ID만으로 추정하지 않는다. |
| 비교 기준 | baseline window, 현재 window, RPS, bytes/sec, active/new connections, 4xx/5xx, latency, healthy backend 수 | 같은 timezone·aggregation·listener 범위로 비교한다. |
| 서비스 영향 | 승인된 외부 probe/SLO, 기대 status·latency, 실제 기능 결과 | body·credential 없이 승인된 endpoint만 사용한다. |

알람 원문에 account, region, LB resource ID, listener, metric dimension이 없으면 provider/observability owner에게 먼저 요청한다. 공통 환경·발생 시각·비슷한 이름만으로 매핑을 확정하지 않는다.

## 5분 병렬 확인

세 확인은 같은 판단을 반복하지 않는다. provider 지표는 승인된 provider console/API의 **read-only** 화면으로 확인하고, 아래 Kubernetes 명령은 승인된 kubeconfig가 있는 작업 PC 또는 bastion의 같은 Bash에서 실행한다.

### 1. 범위와 매핑

알람이 특정 listener인지 LB 전체인지, 어느 Ingress controller Service까지 연결되는지 가른다.

Ingress namespace/name 또는 host가 알람에 이미 있으면 `-A` 전체 조회 대신 해당 namespace와 exact 대상만 조회한다. 클러스터가 과부하 상태라면 전체 목록 수집을 반복하지 않는다.

`CONTEXT='PASTE_CONTEXT_HERE'; kubectl --context "$CONTEXT" get ingress -A -o json | jq -r '.items[] | [.metadata.namespace,.metadata.name,(.spec.ingressClassName // "-"),([.status.loadBalancer.ingress[]? | (.ip // .hostname)] | join(",")),([.spec.rules[]?.host] | join(","))] | @tsv'`

`kubectl --context "$CONTEXT" get svc -A -o json | jq -r '.items[] | select(.spec.type=="LoadBalancer") | [.metadata.namespace,.metadata.name,.metadata.uid,.metadata.resourceVersion,([.status.loadBalancer.ingress[]? | (.ip // .hostname)] | join(",")),([.spec.ports[]? | "\(.port)/\(.protocol)\u2192\(.targetPort)"] | join(",")),(.spec.externalTrafficPolicy // "-")] | @tsv'`

알람의 address/listener/port와 일치하는 Service를 찾았으면 `LB_NS`, `LB_SERVICE`를 exact하게 등록하고 다음 관계를 확인한다.

`LB_NS='PASTE_CONTROLLER_SERVICE_NAMESPACE_HERE'; LB_SERVICE='PASTE_CONTROLLER_LOADBALANCER_SERVICE_HERE'; kubectl --context "$CONTEXT" get service "$LB_SERVICE" -n "$LB_NS" -o json | jq '{uid:.metadata.uid,resourceVersion:.metadata.resourceVersion,generation:.metadata.generation,type:.spec.type,ingress:.status.loadBalancer.ingress,ports:.spec.ports,externalTrafficPolicy:(.spec.externalTrafficPolicy // "Cluster"),selector:.spec.selector}'`

Service UID·address·listener port·provider LB resource ID 중 하나라도 매핑되지 않으면 범위를 확정하지 말고 `차단·에스컬레이션`으로 전환한다.

### 2. 실제 서비스 영향

사용량 증가가 고객 요청 실패인지 단순 트래픽 증가인지 가른다. 승인된 외부 probe의 host/path/status 계약이 있을 때만 실행한다.

`PUBLIC_URL='https://PASTE_APPROVED_HOST_AND_PATH_HERE'; EXPECTED_HOST='PASTE_APPROVED_HOST_HERE'; curl -sS -o /dev/null -w 'time=%{time_total} code=%{http_code} remote=%{remote_ip}\n' --connect-timeout 5 --max-time 15 -H "Host: $EXPECTED_HOST" "$PUBLIC_URL"`

HTTPS 인증서 검증을 우회하는 `-k`를 사용하지 않는다. `000`, timeout, DNS/TLS 오류는 HTTP status가 아니므로 별도로 기록한다. probe가 없으면 SLO dashboard에서 같은 UTC window의 error rate, p95/p99 latency, request rate를 확인한다.

현재 backend 경계는 다음처럼 확인한다.

`kubectl --context "$CONTEXT" get endpointslice -n "$LB_NS" -l "kubernetes.io/service-name=$LB_SERVICE" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,PORTS:.ports[*].port,READY:.endpoints[*].conditions.ready,SERVING:.endpoints[*].conditions.serving,TERMINATING:.endpoints[*].conditions.terminating,TARGET-UIDS:.endpoints[*].targetRef.uid'`

ready EndpointSlice 감소, 외부 error/latency 상승, 또는 실제 기능 실패가 같은 시간에 있으면 서비스 영향이 있는 상태다. `Running` Pod나 LB health 하나만으로 정상화를 선언하지 않는다.

### 3. 사용량 차원과 병목 계층

provider에서 다음을 **같은 listener·aggregation·UTC window**로 baseline과 현재값을 비교한다.

| provider 관측 | 우선 가설 | 다음 확인 |
|---|---|---|
| bytes/sec만 증가, error·latency 정상 | 정상적인 payload/응답량 증가 | traffic source·상위 consumer·provider capacity owner |
| active connection 증가, RPS는 평소와 유사 | keep-alive 장기화, 느린 client, connection leak 후보 | connection age/idle timeout, client 분포, listener별 connection |
| new connection/sec(CPS) 증가, RPS 대비 과도 | connection churn, retry 또는 health/probe 폭주 후보 | client/retry 분포, TLS handshake rate, probe rate |
| PPS·LB CPU·queue 증가, backend 지표는 안정 | LB dataplane 또는 listener capacity 후보 | provider LB tier/quota/partition, shared LB 여부 |
| LB 사용량과 controller CPU·request latency가 함께 증가 | Ingress controller 병목 후보 | controller Pod별 CPU/memory/restart, replica/ready, request/error |
| LB 사용량 증가와 EndpointSlice 감소·5xx 증가가 동시 발생 | backend/Service 경로의 downstream 증상 또는 원인 후보 | [[08. 인그레스·게이트웨이/03. L7 라우팅·Backend·TLS/02. Ingress·Gateway 요청이 502·503을 반환하는 경우]] |
| LB 알람만 증가하고 서비스 지표 정상 | 임계치·baseline·공유 LB 집계 범위 문제 후보 | alert rule, tenant/listener dimension, provider owner |

Ingress controller가 NGINX이고 해당 metric이 실제 수집되는 환경에서만 다음을 참고한다. metric 이름·label은 구현과 배포판에 따라 다르므로 빈 결과를 0 또는 정상으로 해석하지 않는다.

`CTRL_NS='PASTE_CONTROLLER_NAMESPACE_HERE'; CTRL_SELECTOR='PASTE_APPROVED_CONTROLLER_SELECTOR_HERE'; kubectl --context "$CONTEXT" get pods -n "$CTRL_NS" -l "$CTRL_SELECTOR" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,READY:.status.containerStatuses[*].ready,RESTARTS:.status.containerStatuses[*].restartCount,NODE:.spec.nodeName'`

`kubectl --context "$CONTEXT" top pod -n "$CTRL_NS" -l "$CTRL_SELECTOR" --containers`

Prometheus에서는 실제 label을 먼저 확인한 뒤, controller 구현에 맞는 `request rate`, `4xx/5xx rate`, `latency`, `connection` query를 사용한다. `up=1`, Pod Ready, `kubectl top`의 단일 snapshot은 capacity 여유나 정상 요청을 증명하지 않는다.

## 결과 합류와 주 판단

| 합류 결과 | 주 판단 | 운영 경계 |
|---|---|---|
| provider usage 상승 + 실제 서비스 정상 + capacity 여유 확인 | 관찰 유지 | 10~15분 같은 차원으로 재평가하고 baseline·alert owner에 전달한다. |
| provider usage 상승 + 실제 서비스 영향 + provider capacity/queue 또는 quota 직접 증거 | 제한적 조치 검토 | provider/LB owner가 exact listener·scope를 가진 승인된 증설·분산·rate-control 절차를 수행한다. |
| provider usage 상승 + controller CPU/latency/restart 또는 ready 감소 | 최소 확인 후 조치 | controller owner가 current Pod/replica/PDB와 변경 승인·rollback을 먼저 확인한다. LB 증설만으로 controller 병목이 해결된다고 보장하지 않는다. |
| provider usage 상승 + backend/EndpointSlice/5xx 이상 | 관찰 후 해당 L7/Service 런북으로 이관 | LB를 원인으로 확정하지 않고 route→Service→EndpointSlice→Pod 관계를 새 시간창으로 확인한다. |
| provider LB와 Kubernetes Service/Ingress 매핑 불가 | 차단·에스컬레이션 | provider/observability owner에게 resource ID, listener, account/region, UTC window와 mapping evidence를 요청한다. |

## 변경 금지와 제한적 조치 계약

이 문서에는 `kubectl scale`, Pod 삭제, Ingress controller 무조건 restart, Service 재생성, `externalTrafficPolicy` 변경, 임의 HPA/annotation patch, firewall 전면 허용 명령을 두지 않는다. LB 사용량 알람은 그 변경들의 안전성을 증명하지 않는다.

실제 서비스 영향이 있고 provider capacity 또는 listener queue가 직접 확인된 경우에만 provider owner의 승인된 변경 경로를 검토한다. 실행 전 최소 조건은 다음과 같다.

- exact provider LB resource ID, account/region, listener/VIP/port와 Kubernetes Service UID/RV 관계가 확인됐다.
- 사용량 차원, 현재값·threshold·baseline, 영향 서비스와 고객 증거가 같은 UTC window에 있다.
- 변경 범위가 한 LB/listener 또는 승인된 bounded scope이며, 공유 LB의 다른 tenant 영향이 확인됐다.
- 승인 ID, 변경 창, 멱등성, provider rollback/resource revision, 중단 조건과 담당자가 있다.
- 변경 후 provider usage/queue, healthy backend, 외부 실제 기능, error rate/latency를 timebox 안에 재확인할 수 있다.

기대 효과는 지정된 LB/listener의 용량 여유 또는 연결 압력 완화뿐이다. backend application 오류, 잘못된 route, client retry 폭주, shared LB의 다른 listener 영향까지 해결한다고 보장하지 않는다.

## 정상화와 재평가

정상화는 `provider capacity/queue → listener health/backend membership → Ingress controller ready·request/error·latency → Service/EndpointSlice serving → 승인된 외부 실제 기능` 순서로 같은 조건에서 확인한다. 알람 소멸, 단일 2xx, 단일 `kubectl top`, Pod `Running`만으로 닫지 않는다.

재평가는 다음 중 먼저 도달하는 시점에 한다.

- 기본 관찰: 10분 후, 동일 provider aggregation과 listener 범위.
- 제한적 변경 후: provider가 제시한 반영 시간 후 또는 최대 5분 내, 둘 중 짧은 시간부터 확인.
- 즉시 중단·에스컬레이션: error/latency 증가, healthy backend 감소, queue 지속 증가, 사용량이 다른 listener/tenant로 확장, mapping·권한·provider evidence 충돌.

## 보존할 증거와 운영 보고

보존 대상은 알람 ID, provider/account/region/LB resource ID/listener, metric·threshold·aggregation, canonical UTC window, baseline/current 값, Service UID/RV/address/port/policy, Ingress/IngressClass/controller 관계, EndpointSlice serving 수, controller Pod UID·ready·restart·usage, 외부 probe/SLO status·latency, 승인·변경·rollback·정상화 결과다.

Secret data, token, kubeconfig, private key, request/response body, cookie, 전체 provider 로그·firewall ruleset은 저장하지 않는다. 내부 address는 필요한 운영 기록 범위에서만 마스킹한다.

운영자 업데이트 문장:

> 현재 외부 LB `[resource/listener]`의 `[metric]`가 `[current]/[threshold]`로 증가했으며, Kubernetes `[Service UID]`와의 매핑은 `[확인/미확인]`입니다. `[외부 기능·error rate·latency·EndpointSlice]` 기준 서비스 영향은 `[확인/미확인]`이고, 현재는 `[관찰/최소 확인 후 조치/제한적 조치/차단·에스컬레이션]` 상태입니다. 선행 가설은 `[LB capacity/controller/backend/alert 범위]`이며 근본 원인은 미확정입니다. `[재평가 시각]`에 같은 listener와 UTC window로 갱신합니다.
