# 알람이 평가되지 않거나 통지가 전달되지 않는 경우

## 입력값과 빠른 수집

| 구분 | 값 | 출처와 gate |
|---|---|---|
| 최초 입력 | `INPUT_ALERT`, `INPUT_SYSTEM` | 사건 기록의 정확한 알람 이름과 관측 시스템 식별자 |
| API 확인 자동값 | `RULE_ID`, `RULE_UID`, `RULE_RV`, `RULE_REV`, `RULE_OWNER`, `ALERT_FINGERPRINT` | 승인된 read-only API에서 exact name으로 한 건 확인 |
| 계산 후보값 | `ALERT_RE` | 알람 이름을 정규식 literal로 escape한 값이며 출력 대조 전 미확정 |
| 운영자 선택값 | `START_RFC3339`, `END_RFC3339` | 사건 전후의 UTC 조사 창, canonical round-trip과 `start < end` 통과 |

명령은 승인된 작업 PC 또는 bastion의 같은 Bash에서 실행한다. 경로는 `local/bastion의 client -> 관측 시스템 read-only API -> rule evaluator -> state store -> routing -> notification connector -> 외부 수신 설비`다. Kubernetes Pod·node는 rule 원본이 그 대상을 지목할 때만 별도 관계로 등록한다. 내부 URL, 실제 수신자, payload, token과 credential은 입력하거나 저장하지 않는다.

**도구 확인**

`TOOLS_READY=false; MISSING=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: Bash가 아니다.' >&2; else for T in curl jq sed date; do command -v "$T" >/dev/null 2>&1 || MISSING="$MISSING $T"; done; if [ -z "$MISSING" ]; then TOOLS_READY=true; printf '%s\n' 'TOOLS_READY=true'; else printf '중단: 없는 도구=%s\n' "$MISSING" >&2; fi; fi`

**최초 입력과 모든 파생 상태 폐기**

`unset INPUT_READY AUTO_READY CANDIDATE_READY SELECTION_READY AUTH_READY EVIDENCE_READY MUTATION_READY ROLLBACK_READY NORMALIZATION_READY RULE_ID RULE_UID RULE_RV RULE_REV RULE_OWNER ALERT_FINGERPRINT CURRENT_NODE APPROVED_HOST CONTAINER_IDS RELATIONS START_RFC3339 END_RFC3339 START_EPOCH END_EPOCH ARGV_RE ALERT_RE; INPUT_ALERT='PASTE_EXACT_ALERT_NAME_HERE'; INPUT_SYSTEM='PASTE_APPROVED_OBSERVABILITY_SYSTEM_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: TOOLS_READY가 아니다.' >&2; elif [ -z "$INPUT_ALERT" ] || [ -z "$INPUT_SYSTEM" ]; then printf '%s\n' '중단: 최초 입력이 비었다.' >&2; else INPUT_READY=true; export INPUT_ALERT INPUT_SYSTEM; printf 'INPUT_READY=true alert=%s system=%s\n' "$INPUT_ALERT" "$INPUT_SYSTEM"; fi`

`INPUT_SYSTEM`은 endpoint나 credential이 아니라 승인 inventory의 시스템 별칭이다. 실제 API helper는 관측성 owner가 제공한 read-only 명령을 사용하며 이 문서가 URL·인증 방식을 발명하지 않는다.

**조사 시간 선택과 strict UTC 검증**

`START_INPUT='PASTE_START_UTC_RFC3339_HERE'; END_INPUT='PASTE_END_UTC_RFC3339_HERE'; unset START_RFC3339 END_RFC3339 START_EPOCH END_EPOCH; SELECTION_READY=false; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif ! [[ "$START_INPUT" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] || ! [[ "$END_INPUT" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then printf '%s\n' '중단: 시각 형식은 UTC YYYY-MM-DDTHH:MM:SSZ여야 한다.' >&2; elif START_CANON="$(date -u -d "$START_INPUT" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" && END_CANON="$(date -u -d "$END_INPUT" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" && [ "$START_INPUT" = "$START_CANON" ] && [ "$END_INPUT" = "$END_CANON" ] && START_TMP="$(date -u -d "$START_CANON" '+%s')" && END_TMP="$(date -u -d "$END_CANON" '+%s')" && [ "$START_TMP" -lt "$END_TMP" ]; then START_RFC3339="$START_CANON"; END_RFC3339="$END_CANON"; START_EPOCH="$START_TMP"; END_EPOCH="$END_TMP"; SELECTION_READY=true; export START_RFC3339 END_RFC3339; printf 'SELECTION_READY=true start=%s end=%s\n' "$START_RFC3339" "$END_RFC3339"; else printf '%s\n' '중단: canonical UTC round-trip 또는 start<end 검증 실패' >&2; fi; unset START_INPUT END_INPUT START_CANON END_CANON START_TMP END_TMP`

### 자동값 refresh 계약

refresh 직전 현재 ID·UID·resourceVersion·revision·owner·container ID·node·승인 host·관계·시간·argv/regex와 selection/auth/evidence/mutation/rollback/normalization gate를 모두 폐기한다. 아래 helper 계약은 조직의 read-only API가 exact rule 한 건을 JSON으로 반환할 때 적용한다. 실패하면 임시값을 승격하지 않는다.

`refresh_rule(){ unset AUTO_READY CANDIDATE_READY AUTH_READY EVIDENCE_READY MUTATION_READY ROLLBACK_READY NORMALIZATION_READY RULE_ID RULE_UID RULE_RV RULE_REV RULE_OWNER ALERT_FINGERPRINT CURRENT_NODE APPROVED_HOST CONTAINER_IDS RELATIONS ARGV_RE ALERT_RE; AUTO_READY=false; CANDIDATE_READY=false; [ "$INPUT_READY" = true ] && [ "$SELECTION_READY" = true ] || { printf '%s\n' '중단: 입력·시간 gate가 준비되지 않았다.' >&2; return 1; }; local data count id uid rv rev owner fp re; data="$(approved_alert_rule_get --system "$INPUT_SYSTEM" --exact-name "$INPUT_ALERT" --start "$START_RFC3339" --end "$END_RFC3339" --output json)" || { printf '%s\n' 'producer 실패: 승인된 rule API 호출 실패' >&2; return 1; }; count="$(jq -r '.items|length' <<<"$data")" || { printf '%s\n' 'filter 오류: rule JSON 해석 실패' >&2; return 1; }; [ "$count" = 1 ] || { printf 'no match: exact rule count=%s\n' "$count" >&2; return 1; }; id="$(jq -r '.items[0].id // empty' <<<"$data")"; uid="$(jq -r '.items[0].uid // empty' <<<"$data")"; rv="$(jq -r '.items[0].resourceVersion // empty' <<<"$data")"; rev="$(jq -r '.items[0].revision // empty' <<<"$data")"; owner="$(jq -r '.items[0].owner // empty' <<<"$data")"; fp="$(jq -r '.items[0].fingerprint // empty' <<<"$data")"; [ -n "$id" ] && [ -n "$rev" ] && [ -n "$owner" ] || { printf '%s\n' '중단: identity/revision/owner가 불완전하다.' >&2; return 1; }; re="$(printf '%s' "$INPUT_ALERT" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" || return 1; RULE_ID="$id"; RULE_UID="$uid"; RULE_RV="$rv"; RULE_REV="$rev"; RULE_OWNER="$owner"; ALERT_FINGERPRINT="$fp"; ALERT_RE="^${re}$"; RELATIONS="rule:$RULE_ID@revision:$RULE_REV"; AUTO_READY=true; CANDIDATE_READY=true; printf 'AUTO_READY=true id=%s uid=%s rv=%s revision=%s owner=%s relation=%s regex=%s\n' "$RULE_ID" "${RULE_UID:--}" "${RULE_RV:--}" "$RULE_REV" "$RULE_OWNER" "$RELATIONS" "$ALERT_RE"; }`

`refresh_current_rule(){ refresh_rule || return 1; if [ -z "$RULE_UID" ] || [ -z "$RULE_RV" ]; then unset RULE_ID RULE_UID RULE_RV RULE_REV RULE_OWNER ALERT_FINGERPRINT RELATIONS ALERT_RE; AUTO_READY=false; CANDIDATE_READY=false; printf '%s\n' '중단: rule UID/resourceVersion이 불완전하다.' >&2; return 1; fi; RELATIONS="rule:$RULE_ID@$RULE_UID/rv:$RULE_RV/revision:$RULE_REV"; printf 'CURRENT_RULE_READY=true relation=%s\n' "$RELATIONS"; }`

`refresh_current_rule`

`approved_alert_rule_get`은 예시 이름이 아니라 조직이 제공해야 하는 승인 helper 계약이다. 없으면 실행하지 않고 UI에서 같은 필드를 확인해 owner에게 이관한다. raw JSON은 저장하지 않는다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 조건이 충족됐는데 state가 없거나, state는 `firing/active`인데 통지 audit이 없는 경우 |
| 적용 | 같은 rule ID·revision·시간 창에서 load, evaluation, state, route, delivery를 연결할 수 있는 경우 |
| 제외 | source metric 누락은 [[14. 관측성/01. 메트릭/02. Prometheus 수집 대상의 메트릭이 누락되는 경우]], workload 장애는 해당 workload 런북, API 인증 실패는 [[12. 보안/01. API 접근·권한/01. API 서버 인증이 실패하거나 Unauthorized가 반환되는 경우]]로 이동 |

검색 문자열: `parse error`, `evaluation`, `no data`, `stale`, `pending`, `firing`, `silence`, `inhibit`, `route`, `notification`, `retry`, `timeout`.

## 최초 확인

각 read-only 조회는 직접 `AUTO_READY`, `SELECTION_READY`를 검사하고 `RULE_ID`, `RULE_REV`, 시간 범위를 인자로 전달해야 한다.

`if [ "$AUTO_READY" != true ] || [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: fresh rule/time state가 아니다.' >&2; else approved_alert_rule_status --system "$INPUT_SYSTEM" --rule-id "$RULE_ID" --revision "$RULE_REV" --start "$START_RFC3339" --end "$END_RFC3339" --fields 'loaded_at,last_evaluation,evaluation_error,no_data,state,last_transition' || printf '%s\n' 'producer 실패: status 조회 실패' >&2; fi`

`if [ "$AUTO_READY" != true ] || [ -z "$ALERT_FINGERPRINT" ]; then printf '%s\n' '중단: fresh fingerprint가 없다.' >&2; else approved_alert_route_status --system "$INPUT_SYSTEM" --fingerprint "$ALERT_FINGERPRINT" --start "$START_RFC3339" --end "$END_RFC3339" --redact-destination || printf '%s\n' 'producer 실패: route 조회 실패' >&2; fi`

성공 출력이 비면 `no match`다. 명령 non-zero/API 오류는 producer 실패, JSON·query parser 오류는 filter 오류다. 셋을 정상 또는 `0`으로 합치지 않는다.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| rule 없음·load error | exact ID·revision과 parse 오류 | rule 배포·evaluator 호환성 | [[#1. load와 evaluation]] |
| evaluation 중단·no data | last evaluation과 source freshness | evaluator queue 또는 source producer | [[#1. load와 evaluation]] |
| `firing`인데 통지 없음 | fingerprint의 route·silence·inhibition | delivery queue | [[#2. routing과 delivery]] |
| test·silence 해제·resend 필요 | 승인·격리·중복 side effect | 별도 mutation | [[#3. 변경 gate와 정상화]] |

### 1. load와 evaluation

`loaded=true`는 evaluation 성공을 보장하지 않는다. 같은 revision에서 `last_evaluation`, interval, duration, query error, no-data 정책과 source freshness를 확인한다. source query 성공 결과 0건은 조건 불충족 후보이고, source producer 오류는 결과 0건이 아니다. evaluator query parser 오류도 별도 filter 오류다. raw series·로그·label의 개인정보를 저장하지 않고 count, freshness, 오류 분류만 보존한다.

### 2. routing과 delivery

`firing`은 route match나 전달을 보장하지 않는다. fingerprint가 같은 state transition에 대해 route revision, group wait, silence ID·유효기간, inhibition source fingerprint, queue enqueue 시각과 destination alias만 연결한다. `2xx`는 connector 인계 성공이지 최종 수신자 확인이 아니다. `4xx`는 인증·정책, `5xx`·timeout은 connector·외부 설비, queue 증가·retry는 rate/capacity 경계다. 실제 주소·메일·전화·webhook URL·token을 audit에 남기지 않는다.

RBAC 경계: Kubernetes rule CRD를 실제 사용하는 경우 현재 주체의 `get` 권한을 `kubectl auth can-i get RESOURCE -n NAMESPACE`로 먼저 확인하되 `yes`는 실제 요청 성공을 보장하지 않는다. `list/watch`, Secret `.data`, rule payload 전체, cluster-wide audit는 요구하지 않는다. 실제 요청의 `Forbidden`은 권한 경계이며 rule 부재가 아니다. audit는 관측성 시스템의 승인된 rule/fingerprint/time 범위와 비민감 필드만 owner가 제공한다.

### 3. 변경 gate와 정상화

test alert, rule reload, silence 해제와 resend는 읽기 전용 진단과 분리한다. 다음이 모두 fresh해야 `MUTATION_READY=true`로 승인할 수 있다.

- exact rule ID·revision·owner와 fingerprint를 mutation 직전 refresh했다.
- evidence ID, 승인 ID, 변경 창, 실행 주체, 격리된 test destination과 예상 통지량이 기록됐다.
- 운영 route/quorum·관측 시스템 HA 영향과 중복·외부 호출의 멱등성 또는 보상 방법을 확인했다.
- rollback은 이전 rule/route/silence revision과 복원 owner를 가리키며, 이미 전달된 통지는 회수할 수 없음을 승인했다.
- 예상 밖 실제 수신자, queue 증가, 중복 통지, evaluation 오류가 stop 조건이다.

변경 명령은 구현체별 공식 절차에만 둔다. 실행 후 기존 identity를 재사용하지 말고 refresh하여 새 rule revision·fingerprint·route 관계를 재등록한다. 이전 관계가 남으면 정상화하지 않는다.

정상화는 `source freshness -> 반복 evaluation 성공 -> 실제 pending/firing/resolved 전이 -> 의도한 route/silence/inhibition -> delivery audit -> 승인된 수신 확인 -> 실제 workload 증상·핵심 기능`을 역순으로 같은 시간 창에서 확인한다. `NORMALIZATION_READY=true`는 실제 증상과 기능이 회복되고 재발 관찰 창이 통과한 뒤에만 기록한다.

## Prometheus 빠른 관측

Prometheus가 실제 producer이고 self-metric이 exposition에 존재할 때만 쿼리를 생성한다. exact label은 escape하고 regex로 확대하지 않는다.

`if [ "$AUTO_READY" != true ] || [ "$CANDIDATE_READY" != true ]; then printf '%s\n' '중단: fresh identity/escape가 없다.' >&2; else PROM_ALERT="$(printf '%s' "$INPUT_ALERT" | sed 's/\\/\\\\/g; s/"/\\"/g')"; printf 'ALERTS{alertname="%s",alertstate=~"pending|firing"}\n' "$PROM_ALERT"; unset PROM_ALERT; fi`

결과 없음은 조건 불충족, series stale, label 불일치, retention·조회 시간 오류, metric 미노출 후보를 뜻한다. `up`/scrape 실패는 producer 실패이며 별도 확인한다. PromQL/API parser 오류는 filter 오류다. 어느 경우도 알람 정상으로 해석하지 않는다.

## 증거·근거와 미검증

rule ID·UID·resourceVersion·revision·owner, canonical UTC 창, 비민감 evaluation/state/route/delivery 분류, 승인·rollback·재등록 관계와 실제 증상/기능 결과만 보존한다. Secret, token, 내부 URL, 실제 수신자와 payload는 보존하지 않는다.
