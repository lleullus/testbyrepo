# scheduler queue가 정체되거나 Pod binding이 진행되지 않는 경우

## 입력값과 빠른 수집

진단 경로는 `영향 Pod 집합의 schedulerName·UID·RV·PodScheduled → scheduler queue → 현재 scheduler Pod/container log → API pods/binding request·audit → Pod nodeName/condition → workload 기능`이다. scheduler metric에는 Pod UID가 없으므로 API identity와 로그를 연결하지 않으면 개별 binding 근거가 아니다.

| 입력 종류 | 변수 | 출처와 gate |
|---|---|---|
| 최초 입력 | `NS`, `SELECTOR`, 대표 `POD` | 승인된 namespace/selector와 exact representative Pod |
| API 확인 자동값 | 대표 Pod UID·RV·owner·schedulerName·node lifecycle, 영향 집합 | 현재 API에서만 등록 |
| 계산 후보값 | escaped `POD_RE`, `SCHEDULER_RE`, selector 출력용 값 | bounded 확인 뒤 사용 |
| 운영자 선택값 | scheduler Pod/container, audit subject, UTC 창, Prometheus job, host/unit | inventory·로그·audit로 확인 |

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 같은 schedulerName의 다수 Pod에서 nodeName·PodScheduled가 진행하지 않고 queue/log/API 증거가 같은 창에 있음 |
| 적용 | 대표 UID/RV와 scheduler process identity, queue, bind request/audit를 연결 가능 |
| 제외 | Event가 resource·taint·affinity·topology·PVC 원인을 직접 설명하면 [[18. Pod 이벤트에 FailedScheduling이 기록된 경우]]로 한 번 이관 |

검색 문자열: `scheduler_pending_pods`, `scheduler_queue_incoming_pods_total`, `scheduler_schedule_attempts_total`, `Failed to bind pod`, `PodScheduled`, `pods/binding`, `forbidden`, `429`, `context deadline exceeded`.

### 1. 영향 집합과 Event 관계

`SET_READY=false; unset EVENT_READY QUEUE_READY LOG_READY API_READY RBAC_READY NORMALIZE_READY; if [ "$AUTO_READY" != true ] || [ "$TIME_READY" != true ]; then printf '%s\n' '중단: auto/time gate 실패.' >&2; elif J="$(kubectl get pod "$POD" -n "$NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$J")" = "$POD_UID" ] && L="$(kubectl get pods -n "$NS" -l "$SELECTOR" -o json)"; then COUNT="$(jq --arg s "$SCHEDULER_NAME" '[.items[]|select(.spec.schedulerName==$s and ((.spec.nodeName//"")=="") and ([.status.conditions[]?|select(.type=="PodScheduled" and .status!="True")]|length>0))]|length' <<<"$L")"; if [ "$COUNT" -ge 2 ]; then SET_READY=true; jq -r --arg s "$SCHEDULER_NAME" '.items[]|select(.spec.schedulerName==$s)|"=== Pod: \(.metadata.name) ===\nUID/RV: \(.metadata.uid)/\(.metadata.resourceVersion)\nOwner: \([.metadata.ownerReferences[]?|(.kind+"/"+.name+"/"+.uid)]|join(","))\nNode: \(.spec.nodeName//"-")\nCreated: \(.metadata.creationTimestamp)\nPodScheduled: \([.status.conditions[]?|select(.type=="PodScheduled")|(.status+"/"+(.reason//"-")+" at="+(.lastTransitionTime//"-"))]|join(","))"' <<<"$L"; printf 'SET_READY=true stalled=%s\n' "$COUNT"; else printf '중단: 동일 schedulerName의 직접 정체 Pod가 2개 미만 count=%s\n' "$COUNT" >&2; fi; else printf '%s\n' '중단: representative 교체 또는 selector API 실패.' >&2; fi`

이미 nodeName이 있으면 binding 후 kubelet 경계이므로 집합에서 제외한다. 생성/condition 시각이 canonical 창 밖이면 같은 incident로 묶지 않는다.

`EVENT_READY=false; unset NORMALIZE_READY; if [ "$SET_READY" != true ]; then printf '%s\n' '중단: SET_READY가 아니다.' >&2; elif EJ="$(kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID" -o json)"; then EVENT_READY=true; jq -r '"EVENT_READY=true count=\(.items|length)",(.items[]?|"uid=\(.involvedObject.uid) time=\(.eventTime//.lastTimestamp//.metadata.creationTimestamp) type=\(.type) reason=\(.reason) count=\(.count//1)")' <<<"$EJ"; else printf '%s\n' 'event-producer-failure' >&2; fi`

0 events는 정상 의미가 아니다. message에 placement 원인이 있는지는 승인된 UI에서 확인하고, 문서 증거에는 UID·time·reason·count와 비민감 분류만 남긴다.

### 2. queue·로그·journal

PromQL은 확인된 job을 escape해 완성본을 생성한다.

`QUEUE_READY=false; unset NORMALIZE_READY; if [ "$SET_READY" != true ] || [ "$SELECTION_READY" != true ] || [ -z "$PROM_JOB" ]; then printf '%s\n' '중단: set/scheduler/job gate 실패.' >&2; elif SJ="$(kubectl get pod "$SCHED_POD" -n "$SCHED_NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$SJ")" = "$SCHED_POD_UID" ] && [ "$(jq -r --arg c "$SCHED_CONTAINER" '.status.containerStatuses[]?|select(.name==$c)|.containerID' <<<"$SJ")" = "$SCHED_CONTAINER_ID" ]; then PJ="${PROM_JOB//\\/\\\\}"; PJ="${PJ//\"/\\\"}"; PN="${SCHED_POD//\\/\\\\}"; PN="${PN//\"/\\\"}"; NN="${SCHED_NS//\\/\\\\}"; NN="${NN//\"/\\\"}"; printf 'sum by(instance,queue)(scheduler_pending_pods{job="%s",namespace="%s",pod="%s"})\nsum by(instance,profile,result)(rate(scheduler_schedule_attempts_total{job="%s",namespace="%s",pod="%s"}[5m]))\nsum by(instance,queue,event)(rate(scheduler_queue_incoming_pods_total{job="%s",namespace="%s",pod="%s"}[5m]))\n' "$PJ" "$NN" "$PN" "$PJ" "$NN" "$PN" "$PJ" "$NN" "$PN"; QUEUE_READY=true; else printf '%s\n' '중단: current scheduler identity 불일치.' >&2; fi`

Kubernetes 1.26 build에서 metric/label이 unsupported이거나 query가 empty면 0으로 해석하지 않는다. target·scrape/TLS/RBAC·time range·label mismatch를 구분한다. `unschedulable` 증가는 scheduler 장애가 아니라 placement 조건일 수 있다.

`LOG_READY=false; unset API_READY RBAC_READY NORMALIZE_READY; TMP=''; if [ "$SELECTION_READY" != true ] || [ "$TIME_READY" != true ] || [ "$SET_READY" != true ]; then printf '%s\n' '중단: scheduler log gate 실패.' >&2; elif SJ="$(kubectl get pod "$SCHED_POD" -n "$SCHED_NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$SJ")" = "$SCHED_POD_UID" ] && [ "$(jq -r '.spec.nodeName' <<<"$SJ")" = "$SCHED_NODE" ] && [ "$(jq -r --arg c "$SCHED_CONTAINER" '.status.containerStatuses[]?|select(.name==$c)|.containerID' <<<"$SJ")" = "$SCHED_CONTAINER_ID" ]; then LOG_READY=true; TMP="$(mktemp)" || exit 1; if kubectl logs "$SCHED_POD" -n "$SCHED_NS" -c "$SCHED_CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=500 >"$TMP"; then grep -Eic "$POD_RE|queue|enqueue|schedule|bind|binding|assum|forbidden|denied|429|timeout|deadline|failed" "$TMP" >/dev/null; FRC=$?; case "$FRC" in 0) printf 'LOG_READY=true filter=matched count=%s\n' "$(grep -Eic "$POD_RE|queue|enqueue|schedule|bind|binding|assum|forbidden|denied|429|timeout|deadline|failed" "$TMP")";; 1) printf '%s\n' 'LOG_READY=true filter=no-match; watch/queue 정상 증거가 아니다.';; *) printf 'filter-error rc=%s\n' "$FRC" >&2; LOG_READY=false;; esac; else printf 'log-producer-failure rc=%s\n' "$?" >&2; LOG_READY=false; fi; rm -f "$TMP"; else printf '%s\n' '중단: scheduler Pod/node/containerID 변경.' >&2; fi`

systemd 경로만 아래를 사용한다. positional args, remote machine-id, producer/filter status를 각각 검증하며 `eval`하지 않는다.

`HOST_READY=false; unset NORMALIZE_READY; if [ "$TIME_READY" != true ]; then printf '%s\n' '중단: TIME_READY가 아니다.' >&2; else ssh -- "$SSH_HOST" bash -c 'expected=$1; unit=$2; start=$3; end=$4; podre=$5; [ "$(cat /etc/machine-id 2>/dev/null)" = "$expected" ] || exit 41; out=$(journalctl -u "$unit" --since "$start" --until "$end" --no-pager -n 500); prc=$?; [ "$prc" -eq 0 ] || { printf "journal-producer-failure rc=%s\n" "$prc" >&2; exit 42; }; grep -Eic "$podre|queue|schedule|bind|forbidden|429|timeout|deadline|failed" <<<"$out" >/dev/null; frc=$?; case "$frc" in 0) printf "HOST_READY=true filter=matched count=%s\n" "$(grep -Eic "$podre|queue|schedule|bind|forbidden|429|timeout|deadline|failed" <<<"$out")";; 1) printf "%s\n" "HOST_READY=true filter=no-match";; *) exit 43;; esac' bash "$EXPECTED_MACHINE_ID" "$UNIT" "$START_RFC3339" "$END_RFC3339" "$POD_RE"; RC=$?; [ "$RC" -eq 0 ] && HOST_READY=true || printf 'SSH/journal 실패 rc=%s\n' "$RC" >&2; fi`

### 3. API binding·RBAC 경계

`API_READY=false; unset RBAC_READY NORMALIZE_READY; if [ "$LOG_READY" != true ]; then printf '%s\n' '중단: LOG_READY가 아니다.' >&2; elif J="$(kubectl get pod "$POD" -n "$NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$J")" = "$POD_UID" ]; then API_READY=true; jq -r '"API_READY=true uid=\(.metadata.uid) rv=\(.metadata.resourceVersion) scheduler=\(.spec.schedulerName) node=\(.spec.nodeName//"-") PodScheduled=\([.status.conditions[]?|select(.type=="PodScheduled")|(.status+"/"+(.reason//"-")+" at="+(.lastTransitionTime//"-"))]|join(","))"' <<<"$J"; else printf '%s\n' '중단: representative 교체/조회 실패.' >&2; fi`

bind log 시각과 Pod RV/condition 시각, API audit를 연결한다. `readyz` 성공은 해당 pods/binding write, authorization, admission과 etcd commit 성공을 보장하지 않는다.

`RBAC_READY=false; unset NORMALIZE_READY; if [ "$API_READY" != true ] || [ -z "$CLIENT_SUBJECT" ]; then printf '%s\n' '중단: API/audit subject 미확정.' >&2; elif J="$(kubectl get pod "$POD" -n "$NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$J")" = "$POD_UID" ]; then R="$(kubectl auth can-i create pods/binding -n "$NS" --as="$CLIENT_SUBJECT" 2>&1)"; RC=$?; printf 'subject=%s verb=create resource=pods subresource=binding namespace=%s name=%s result=%s rc=%s\n' "$CLIENT_SUBJECT" "$NS" "$POD" "$R" "$RC"; [ "$RC" -eq 0 ] && [ "$R" = yes ] && RBAC_READY=true; else printf '%s\n' '중단: current Pod identity 불일치.' >&2; fi; printf 'RBAC_READY=%s\n' "$RBAC_READY"`

audit에서 `user.username`, verb `create`, objectRef resource `pods`, subresource `binding`, namespace/name, response code와 auditID가 같은 창에 정확히 일치해야 한다. `can-i=yes`는 actual request 성공을 보장하지 않는다. `429/5xx/timeout`과 같은 audit/apiserver 증거가 있으면 API priority/flow control 또는 etcd owner로 이관하고 quorum 조작은 하지 않는다.

## 변경 gate와 정상화

진단은 읽기 전용이다. queue 조작, 강제 binding, scheduler restart/config/RBAC 변경, Pod 대량 삭제를 제시하지 않는다. 별도 변경 전에 current 영향 Pod와 scheduler UID/RV/owner/node/containerID, direct queue/log/audit evidence, 승인 ID·실행자·window, API/etcd quorum·capacity, tenant blast radius, 외부 side effect와 멱등성, stop·rollback을 fresh 확인한다. rollback도 독립 fresh gate가 필요하다.

변경 후 교체된 scheduler와 workload Pod를 새 UID로 다시 등록한다. `queue 정상 유입/감소 → scheduler bind → API nodeName·PodScheduled=True → kubelet Ready → EndpointSlice/실제 요청·핵심 기능`을 관찰 창에서 확인하고 동일 binding 오류·API Warning이 없어야 `NORMALIZE_READY=true`다. 기존 Pod UID, queue 감소, Running 하나만 재사용해 정상화하지 않는다.

## 증거와 미검증

canonical UTC 창, selector, 대표 및 영향 Pod UID·RV·owner·schedulerName·nodeName·condition, scheduler UID·RV·owner·node·containerID, metric/process 원점, producer/filter 결과, exact audit/RBAC tuple, 승인·rollback·새 identity·기능 결과만 보존한다. raw log/audit/message/config와 credential은 보존하지 않는다.

queue 정상 범위, scheduler profile/plugin, metrics endpoint, host/unit, API priority/flow control, audit와 etcd 운영은 환경별 미검증이다. 실제 인프라 실행과 상태 변경은 수행하지 않았다.
