# etcd 요청·WAL fsync·backend commit 지연이 증가한 경우

## 입력값과 빠른 수집

실행 경로는 `작업 PC/bastion Bash -> Kubernetes API의 current static Pod -> node와 일치하는 SSH host -> etcd client endpoint/data filesystem`이다. Pod API 관측, 원격 etcdctl, node filesystem/latency와 Prometheus는 각각 다른 hop이며 하나의 성공이 다음 hop을 보장하지 않는다.

| 종류 | 값 | gate |
|---|---|---|
| 최초 입력 | `NS`, `ETCD_POD` | 승인 inventory exact name |
| API 확인 자동값 | Pod UID/RV/owner/creation, node UID/systemUUID, containerID | 전체 API 성공과 lifecycle 단일 관계 |
| 계산 후보값 | etcd container, endpoint/TLS/data-dir, argv hash/regex | argv strict extraction, endpoint는 아직 후보 |
| 운영자 선택값 | SSH host, exact endpoint, UTC 창, Prometheus job | inventory·현재 출력·사건 시각 대조 |

API 실패·재등록 전에는 UID/RV/owner/containerID/node/host/relations/time/argv-regex와 모든 downstream `READY`를 폐기한다.

`TOOLS_READY=false; MISSING=''; for T in kubectl jq grep sed date mktemp sha256sum ssh awk; do command -v "$T" >/dev/null 2>&1 || MISSING="$MISSING $T"; done; if [ -n "${BASH_VERSION:-}" ] && [ -z "$MISSING" ]; then TOOLS_READY=true; else printf '중단: Bash 또는 도구 없음:%s\n' "$MISSING" >&2; fi`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | endpoint `took`·API storage latency와 WAL fsync/backend commit 지연이 같은 창에서 증가 |
| 적용 | current member identity, leader/raft, histogram rate, 실제 data filesystem device를 연결 가능 |
| 제외 | no leader/quorum은 [[02. etcd cluster에 leader가 없거나 quorum을 잃은 경우]], NOSPACE/CORRUPT는 각 alarm 문서, API-only 지연은 API server 경로 |

검색 문자열: `request timed out`, `slow apply`, `slow read index`, `fsync`, `backend commit`, `heartbeat`, `peer round trip`, `proposals pending`.

## 보안·권한·runtime 경계

`fresh_target && kubectl auth can-i get pods -n "$NS" && kubectl auth can-i get pods/log -n "$NS" && kubectl auth can-i get nodes`

`Forbidden`·TLS path unreadable·SSH 실패는 latency 증거가 아니다. RBAC 확대, TLS 검증 해제, Secret/private key/token/audit body 출력은 금지한다. 원격 명령은 검증 host의 고정 script에 positional args로 전달하며 `eval`을 쓰지 않는다.

CRI는 직접 사용하지 않는다. container lifecycle이 먼저 실패한 경우 runtime 런북에서 active kubelet endpoint strict single extraction, exact match, runtime socket owner/type/permission을 확인한다.

## request·member baseline

`ETCD_READY=false; if [ "$HOST_READY" = true ] && fresh_remote; then ssh -T -- "$HOST" 'set -eu; e=$1; ca=$2; crt=$3; key=$4; command -v etcdctl >/dev/null; sudo -- test -r "$ca"; sudo -- test -r "$crt"; sudo -- test -r "$key"; sudo -- env ETCDCTL_API=3 etcdctl version' sh "$ENDPOINT" "$CA_FILE" "$CERT_FILE" "$KEY_FILE"; RC=$?; if [ "$RC" -eq 0 ]; then ETCD_READY=true; else printf '중단: preflight rc=%s\n' "$RC" >&2; fi; fi`

`if [ "$ETCD_READY" = true ] && fresh_remote; then ssh -T -- "$HOST" 'set -eu; e=$1; ca=$2; crt=$3; key=$4; sudo -- env ETCDCTL_API=3 etcdctl --endpoints="$e" --cacert="$ca" --cert="$crt" --key="$key" endpoint health --cluster; sudo -- env ETCDCTL_API=3 etcdctl --endpoints="$e" --cacert="$ca" --cert="$crt" --key="$key" endpoint status --cluster -w table; sudo -- env ETCDCTL_API=3 etcdctl --endpoints="$e" --cacert="$ca" --cert="$crt" --key="$key" member list -w table; sudo -- env ETCDCTL_API=3 etcdctl --endpoints="$e" --cacert="$ca" --cert="$crt" --key="$key" alarm list' sh "$ENDPOINT" "$CA_FILE" "$CERT_FILE" "$KEY_FILE"; fi`

endpoint `took`, member ID, leader, raft index/applied, DB size를 같은 시각에 기록한다. `NOSPACE`/`CORRUPT`, leader 없음, endpoint 실패가 먼저면 latency 유지보수를 중단하고 해당 문서로 이동한다. 빈/실패 출력은 정상 baseline이 아니다.

## data filesystem 직접 gate

현재 data-dir와 remote identity가 fresh일 때만 mount/device를 확인한다. 이 명령은 data file을 읽지 않는다.

`if [ "$HOST_READY" = true ] && fresh_remote; then ssh -T -- "$HOST" 'set -eu; d=$1; sudo -- findmnt -T "$d" -o TARGET,SOURCE,FSTYPE,OPTIONS; sudo -- df -h "$d"; sudo -- df -i "$d"; if command -v iostat >/dev/null 2>&1; then sudo -- iostat -xz 1 5; else printf "%s\n" "iostat 없음: device latency 미확정" >&2; fi' sh "$DATA_DIR"; fi`

WAL fsync tail과 같은 device의 await/util이 같은 창에서 증가하면 storage 후보가 강해진다. backend commit만 증가하면 backend file/device·CPU·DB size를 본다. filesystem `ro`, block/inode 부족은 latency 완화가 아니라 node/storage 사건이다. `iostat` 부재를 정상으로 해석하지 않는다.

## UTC 증거 창과 로그 rc

`START_RFC3339='PASTE_START_UTC_RFC3339_HERE'; END_RFC3339='PASTE_END_UTC_RFC3339_HERE'; TIME_READY=false; R='^[0-9]{4}-(0[1-9]|1[0-2])-([0-2][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9]Z$'; if [[ "$START_RFC3339" =~ $R ]] && [[ "$END_RFC3339" =~ $R ]]; then S="$(date -u -d "$START_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)"; SRC=$?; E="$(date -u -d "$END_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)"; ERC=$?; SE="$(date -u -d "$START_RFC3339" +%s 2>/dev/null)"; EE="$(date -u -d "$END_RFC3339" +%s 2>/dev/null)"; if [ "$SRC" -eq 0 ] && [ "$ERC" -eq 0 ] && [ "$S" = "$START_RFC3339" ] && [ "$E" = "$END_RFC3339" ] && [ "$SE" -lt "$EE" ]; then TIME_READY=true; export START_RFC3339 END_RFC3339; else printf '%s\n' '중단: UTC round-trip/start<end 실패' >&2; fi; else printf '%s\n' '중단: canonical UTC RFC3339 아님' >&2; fi`

`if [ "$TIME_READY" = true ] && fresh_target; then RAW="$(mktemp)"; WIN="$(mktemp)"; kubectl logs "$ETCD_POD" -n "$NS" -c "$ETCD_CONTAINER" --timestamps --since-time="$START_RFC3339" >"$RAW"; PRODUCER_RC=$?; if [ "$PRODUCER_RC" -eq 0 ]; then awk -v start="$START_RFC3339" -v end="$END_RFC3339" '$1>=start && $1<=end' "$RAW" >"$WIN"; WINDOW_RC=$?; if [ "$WINDOW_RC" -eq 0 ]; then grep -E -i -C 3 'slow apply|slow read index|fsync|backend|request took|heartbeat|leader|peer|timeout|deadline|proposals pending' "$WIN"; FILTER_RC=$?; printf 'producer_rc=%s window_rc=%s filter_rc=%s evidence=%s..%s\n' "$PRODUCER_RC" "$WINDOW_RC" "$FILTER_RC" "$START_RFC3339" "$END_RFC3339"; else printf '중단: window filter rc=%s\n' "$WINDOW_RC" >&2; fi; else printf '중단: log producer rc=%s\n' "$PRODUCER_RC" >&2; fi; rm -f "$RAW" "$WIN"; fi`

producer/filter rc를 분리한다. filter rc `1`은 오류 부재가 아니며 raw 전체를 저장하지 않는다.

## 실행 가능한 Prometheus 쿼리

`JOB='PASTE_PROMETHEUS_ETCD_JOB_HERE'; INSTANCE='PASTE_PROMETHEUS_INSTANCE_FOR_SELECTED_ENDPOINT_HERE'; QUERY_READY=false; if [ "$ETCD_READY" = true ] && fresh_remote && [ -n "$JOB" ] && [ -n "$INSTANCE" ] && [[ "$JOB" != *$'\n'* ]] && [[ "$INSTANCE" != *$'\n'* ]]; then JOB_RE="$(printf '%s' "$JOB"|sed 's/[][\\.^$*+?(){}|]/\\&/g')"; INSTANCE_RE="$(printf '%s' "$INSTANCE"|sed 's/[][\\.^$*+?(){}|]/\\&/g')"; QUERY_READY=true; export JOB_RE INSTANCE_RE; printf 'QUERY_READY=true job=^%s$ instance=^%s$ endpoint=%s\n' "$JOB_RE" "$INSTANCE_RE" "$ENDPOINT"; else printf '%s\n' '중단: endpoint와 대조한 target label 미등록' >&2; fi`

`[ "$ETCD_READY" = true ] && fresh_remote && [ "$QUERY_READY" = true ] && printf 'histogram_quantile(0.99,sum by(le,instance)(rate(etcd_disk_wal_fsync_duration_seconds_bucket{job=~"^%s$",instance=~"^%s$"}[5m])))\n' "$JOB_RE" "$INSTANCE_RE"`

`[ "$ETCD_READY" = true ] && fresh_remote && [ "$QUERY_READY" = true ] && printf 'histogram_quantile(0.99,sum by(le,instance)(rate(etcd_disk_backend_commit_duration_seconds_bucket{job=~"^%s$",instance=~"^%s$"}[5m])))\n' "$JOB_RE" "$INSTANCE_RE"`

`[ "$ETCD_READY" = true ] && fresh_remote && [ "$QUERY_READY" = true ] && printf 'max by(instance)(etcd_server_proposals_pending{job=~"^%s$",instance=~"^%s$"})\n' "$JOB_RE" "$INSTANCE_RE"`

완성 출력만 사용한다. API HTTP status, `status=success`, non-empty series를 각각 gate한다. 빈 metric은 성공/0이 아니다. process restart 원점이 다른 counter는 raw 비교하지 않고 같은 창의 rate/increase를 사용한다. instance를 member ID/node/device와 연결하지 못하면 원인 확정에 쓰지 않는다.

## 원인 판정

| 직접 관계 | 판정 |
|---|---|
| WAL p99 + device latency + heartbeat 지연 | WAL filesystem/storage |
| backend p99 + pending/slow apply + DB/device/CPU | backend commit/apply |
| disk 정상 + peer RTT/leader change | peer/network 또는 quorum 경계 |
| etcd 정상 + API request만 지연 | API server request/admission/watch 경로 |

## 상태 변경·replacement·정상화

이 문서는 defrag, compaction, restart, member 변경, data-dir 조작을 제공하지 않는다. 별도 mutation은 매 실행 직전 fresh target/evidence, 승인 ID/window, leader·voting quorum, 검증된 backup, idempotence, 영향, 중단 조건, 실제 검증된 rollback을 재확인한다. latency 수치 하나는 mutation trigger가 아니다.

controller replacement는 selector+owner UID+controller UID+변경 이후 creation time+단일 후보로 선택한다. static mirror/member는 이 selector를 억지 적용하지 않고 exact member/mirror identity를 사용한다. replacement 후 모든 값을 폐기하고 전체 재등록한다.

정상화는 endpoint/member/leader -> WAL/backend p99와 pending -> 실제 device latency/pressure -> API readyz -> 승인된 실제 기능 순으로 같은 관찰 창에서 확인한다. baseline 또는 승인 SLO로 돌아오고 slow apply/read index/heartbeat/leader churn이 재발하지 않아야 한다. Pod Running, 단일 health 성공, 빈 query만으로 닫지 않는다.
