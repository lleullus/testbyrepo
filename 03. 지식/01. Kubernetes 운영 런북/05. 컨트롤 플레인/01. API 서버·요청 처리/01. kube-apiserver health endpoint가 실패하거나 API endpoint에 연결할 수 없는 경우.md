# kube-apiserver health endpoint가 실패하거나 API endpoint에 연결할 수 없는 경우

## 입력값과 빠른 수집

Kubernetes/API 명령은 승인된 작업 PC 또는 bastion의 같은 Bash에서 실행한다. 연결 경로는 `작업 host의 client → DNS/TCP/TLS → VIP/LB → control-plane backend → kube-apiserver → ready dependency`다. 한 hop 성공은 다음 hop 성공을 보장하지 않는다.

| 종류 | 변수 | 출처와 gate |
|---|---|---|
| 최초 입력 | `OBSERVED_FAILURE` | 원래 client가 본 비식별화 오류 한 줄 |
| 로컬 자동값 | `API_URL`, `OBSERVED_UTC` | minified kubeconfig의 server URL과 현재 UTC. credential data는 읽지 않음 |
| API 자동값 | `APISERVER_POD`, `APISERVER_UID`, `APISERVER_RV`, `CP_NODE`, `CP_NODE_UID`, `CP_NODE_RV`, `POD_NODE`, `CONTAINER_IDS` | API가 응답하고 후보가 exact할 때만 등록 |
| 계산값 | `API_HOST`, `API_PORT`, `JOB_RE`, `ARGV_RE` | URL/PromQL/active process 검사 후보이며 bounded 출력 후 사용 |
| 운영자 선택값 | `DEPLOYMENT_MODE`, `SSH_TARGET`, `EXPECTED_HOST`, `EXPECTED_MACHINE_ID`, `START_UTC`, `END_UTC`, `PROM_JOB` | 설치 inventory와 최초 실패 시각을 보고 선택 |

### 2. API가 응답할 때만 component identity 등록

재조회 전 identity/RV/owner/containerID/node/host/relation/time/argv-regex와 downstream READY를 전부 폐기한다. API 실패 뒤 과거 component 값을 사용하지 않는다.

`unset API_READY SELECTION_READY HOST_READY TIME_READY KUBELET_READY CRI_READY RELATION_READY HEALTH_READY DEPENDENCY_READY DOWNSTREAM_READY APISERVER_POD APISERVER_UID APISERVER_RV CP_NODE CP_NODE_UID CP_NODE_RV POD_NODE CONTAINER_IDS OWNER_KIND OWNER_UID CONTAINER_ID SSH_TARGET EXPECTED_HOST HOST_ID HOST_RELATION START_UTC END_UTC START_EPOCH END_EPOCH KUBELET_PID KUBELET_ARGV CRI_ENDPOINT RUNTIME_UNIT PROM_JOB JOB_RE ARGV_RE; API_READY=false; if [ "$LOCAL_READY" != true ]; then printf '%s\n' '중단: LOCAL_READY가 아니다.' >&2; elif PODS_JSON="$(kubectl get pods -n kube-system -l component=kube-apiserver -o json)" && NODES_JSON="$(kubectl get nodes -l node-role.kubernetes.io/control-plane -o json)" && [ "$(jq '.items|length' <<<"$PODS_JSON")" -ge 1 ] && [ "$(jq '.items|length' <<<"$NODES_JSON")" -ge 1 ]; then jq -r '.items[]|"=== API server Pod ===\n이름: \(.metadata.name)\nUID: \(.metadata.uid)\nRV: \(.metadata.resourceVersion)\nNode: \(.spec.nodeName)\nPhase: \(.status.phase)\nReady: \([.status.containerStatuses[]?.ready]|join(","))\nContainer/ID: \([.status.containerStatuses[]?|"\(.name)=\(.containerID//"-")"]|join(";"))"' <<<"$PODS_JSON"; jq -r '.items[]|"=== control-plane Node ===\n이름: \(.metadata.name)\nUID: \(.metadata.uid)\nRV: \(.metadata.resourceVersion)\nReady: \([.status.conditions[]|select(.type=="Ready")|.status][0]//"-")\nRuntime: \(.status.nodeInfo.containerRuntimeVersion)"' <<<"$NODES_JSON"; API_READY=true; ARGV_RE='(^|[[:space:]])(--config|--container-runtime-endpoint|--etcd-servers)(=|[[:space:]])'; export ARGV_RE; printf 'API_READY=true ARGV_RE=%s\n' "$ARGV_RE"; else printf '%s\n' 'API component 자동 등록 불가: selector/label/권한/연결을 미검증으로 남기고 transport 또는 provider 경로 사용' >&2; fi`

`unset EXPECTED_MACHINE_ID CP_MACHINE_ID HOST_RELATION_READY CRI_PROVIDER_READY PROM_READY`

selector 결과는 설치 방식별 후보다. 0건이면 kube-apiserver가 없다고 결론내리지 않는다. 여러 건 중 첫 항목을 자동 선택하지 않는다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | `connection refused`, DNS/timeout/TLS 오류, `/livez`·`/readyz` non-2xx 또는 verbose check 실패 |
| 적용 | 원래 endpoint와 실행 host를 고정하고 transport·LB·backend·process·dependency를 분리할 수 있음 |
| 제외 | 연결된 특정 요청만 500/503이면 [[02. API 요청에 500·503 오류가 반환되는 경우]], 429면 [[04. API 요청에 429 Too Many Requests가 반환되는 경우]] |

검색 문자열: `Could not resolve host`, `Connection refused`, `Operation timed out`, `SSL certificate problem`, `[-]etcd`, `[-]poststarthook`, `failed to connect to etcd`.

## 최초 확인과 직접 gate

`TRANSPORT_READY=false; if [ "$LOCAL_READY" != true ]; then printf '%s\n' '중단: LOCAL_READY가 아니다.' >&2; else CODE="$(curl -sS -o /dev/null -w '%{http_code}' --connect-timeout 5 --max-time 10 "$API_URL/version")"; CURL_RC=$?; if [ "$CURL_RC" -eq 0 ] && [ "$CODE" != 000 ]; then TRANSPORT_READY=true; fi; printf 'curl_rc=%s http=%s TRANSPORT_READY=%s endpoint=%s\n' "$CURL_RC" "${CODE:-000}" "$TRANSPORT_READY" "$API_URL"; fi`

unauthenticated `401`·`403`도 DNS/TCP/TLS/HTTP hop이 응답했다는 뜻이다. application authorization이나 health 성공은 아니다. `curl -k`, token, cookie, Authorization header를 추가하지 않는다.

`HEALTH_READY=false; if [ "$TRANSPORT_READY" != true ]; then printf '%s\n' '중단: transport 응답이 없어 health를 별도 증거로 중복 실행하지 않는다.' >&2; elif LIVE="$(kubectl get --raw='/livez?verbose')" && READY="$(kubectl get --raw='/readyz?verbose')"; then printf '%s\n%s\n' "$LIVE" "$READY"; if ! grep -Fq '[-]' <<<"$LIVE" && ! grep -Fq '[-]' <<<"$READY"; then HEALTH_READY=true; fi; printf 'HEALTH_READY=%s\n' "$HEALTH_READY"; else printf '%s\n' 'health API 실패: 인증/RBAC/API status를 원 transport와 분리' >&2; fi`

| 지금 보이는 것 | 먼저 볼 것 | 다음 경계 |
|---|---|---|
| curl rc 6 | 작업 host DNS | resolver/VIP inventory |
| rc 7/refused 또는 rc 28/timeout | route·listener·firewall·LB backend | network/LB owner |
| rc 35/60 | SNI·CA·만료 | 인증서 owner, 검증 우회 금지 |
| `/livez` 실패 | process lifecycle | kubelet/runtime/provider |
| `/livez` 성공, `/readyz` `[-]...` | 실패 check 이름 | etcd/post-start/해당 dependency |
| VIP만 실패, 승인 backend는 성공 | listener/backend pool | LB owner, 우회 금지 |

## control-plane host·kubelet·CRI 분기

managed control plane은 SSH/CRI를 실행하지 않고 provider incident, backend health와 같은 UTC 창의 로그를 요청한다. self-managed 환경은 승인된 inventory로 `CP_NODE_UID ↔ POD_NODE ↔ SSH host` 관계를 확인한다.

`KUBELET_UNIT='PASTE_CONFIRMED_KUBELET_UNIT_HERE'; CRI_ENDPOINT='PASTE_EXACT_ACTIVE_CRI_ENDPOINT_HERE'; RUNTIME_UNIT='PASTE_CONFIRMED_RUNTIME_UNIT_HERE'; CONTAINER_ID='PASTE_EXACT_APISERVER_CONTAINER_ID_HERE'`

`CRI_READY=false; if [ "$SELECTION_READY" != true ] || [ "$HOST_READY" != true ] || [ "$TIME_READY" != true ] || [ "$DEPLOYMENT_MODE" = managed ]; then printf '%s\n' '중단: self-managed identity/host/time gate가 아니다.' >&2; elif ! [[ "$CRI_ENDPOINT" =~ ^unix:///[^[:space:]]+$ ]] || ! [[ "$CONTAINER_ID" =~ ^[a-f0-9]{12,64}$ ]]; then printf '%s\n' '중단: active CRI endpoint 또는 exact container ID가 유효하지 않다.' >&2; elif grep -Fq "$CONTAINER_ID" <<<"$CONTAINER_IDS"; then CRI_READY=true; printf 'CRI_READY=true endpoint=%s container=%s\n' "$CRI_ENDPOINT" "$CONTAINER_ID"; else printf '%s\n' '중단: API containerID와 선택 ID가 일치하지 않는다.' >&2; fi`

`CRI_PROVIDER_READY=false; if [ "$CRI_READY" != true ] || [ "$HOST_RELATION_READY" != true ] || ! CURRENT_AP_JSON="$(kubectl get pod "$APISERVER_POD" -n kube-system -o json)" || [ "$(jq -r '.metadata.uid' <<<"$CURRENT_AP_JSON")" != "$APISERVER_UID" ] || [ "$(jq -r '.metadata.resourceVersion' <<<"$CURRENT_AP_JSON")" != "$APISERVER_RV" ] || ! CURRENT_NODE_JSON="$(kubectl get node "$CP_NODE" -o json)" || [ "$(jq -r '.metadata.uid' <<<"$CURRENT_NODE_JSON")" != "$CP_NODE_UID" ]; then CRI_READY=false; printf '%s\n' '중단: current Pod/Node/host/CRI gate가 아니다.' >&2; elif ssh -- "$SSH_TARGET" bash -c 'set -u; expected=$1; expected_machine=$2; kubelet_unit=$3; endpoint=$4; runtime_unit=$5; actual=$(hostname -f 2>/dev/null || hostname); [ "$actual" = "$expected" ] && [ "$(cat /etc/machine-id)" = "$expected_machine" ] || exit 1; kpid=$(systemctl show "$kubelet_unit" -p MainPID --value) || exit 1; rpid=$(systemctl show "$runtime_unit" -p MainPID --value) || exit 1; [[ "$kpid" =~ ^[1-9][0-9]*$ ]] && [[ "$rpid" =~ ^[1-9][0-9]*$ ]] || exit 1; mapfile -t lines < <(grep -E "^[[:space:]]*containerRuntimeEndpoint:[[:space:]]*[^[:space:]].*$" "$config"); [ "${#lines[@]}" -eq 1 ] || exit 1; active=${lines[0]#*:}; active=${active# }; active=${active%$'\r'}; active=${active#\"}; active=${active%\"}; fi; [[ "$active" =~ ^unix:///[^[:space:]]+$ ]] && [ "$active" = "$endpoint" ] || exit 1; socket=${endpoint#unix://}; [ -S "$socket" ] || exit 1; tmp=$(mktemp) || exit 1; sudo ss -xlpn >"$tmp" || { rc=$?; rm -f "$tmp"; exit "$rc"; }; found=false; while IFS= read -r line; do if [[ "$line" == *"$socket"* && "$line" == *"pid=$rpid,"* ]]; then found=true; break; fi; done <"$tmp"; rm -f "$tmp"; [ "$found" = true ]' _ "$EXPECTED_HOST" "$EXPECTED_MACHINE_ID" "$KUBELET_UNIT" "$CRI_ENDPOINT" "$RUNTIME_UNIT"; then CRI_PROVIDER_READY=true; printf 'CRI_PROVIDER_READY=true endpoint=%s runtime_unit=%s\n' "$CRI_ENDPOINT" "$RUNTIME_UNIT"; else CRI_READY=false; printf '%s\n' '중단: active kubelet endpoint/runtime PID/socket provider relation 실패' >&2; fi`

`CRI_PROVIDER_READY=true`가 아니면 뒤의 `crictl`·journal 명령을 실행하지 않는다. fallback config는 active kubelet argv가 가리킨 absolute regular readable file, key 정확히 하나, nonempty `unix:///...` endpoint일 때만 허용한다.

`if [ "$CRI_READY" != true ] || [ "$CRI_PROVIDER_READY" != true ] || ! CURRENT_AP_JSON="$(kubectl get pod "$APISERVER_POD" -n kube-system -o json)" || [ "$(jq -r '.metadata.uid' <<<"$CURRENT_AP_JSON")" != "$APISERVER_UID" ] || [ "$(jq -r '.metadata.resourceVersion' <<<"$CURRENT_AP_JSON")" != "$APISERVER_RV" ] || ! set -u
expected=$1
expected_machine=$2
unit=$3
endpoint=$4
cid=$5
start=$6
end=$7

sudo crictl --runtime-endpoint "$endpoint" inspect "$cid" >/dev/null || { printf '%s\n' '중단: exact container inspect 실패' >&2; exit 1; }
tmp=$(mktemp) || exit 1
if sudo journalctl -u "$unit" --since "$start" --until "$end" --no-pager >"$tmp"; then producer_rc=0; else producer_rc=$?; fi
if [ "$producer_rc" -ne 0 ]; then rm -f "$tmp"; exit "$producer_rc"; fi
if grep -E -i -C 3 'kube-apiserver|static pod|sandbox|container|back-off|failed to start|x509|etcd|poststarthook' "$tmp"; then filter_rc=0; else filter_rc=$?; fi
printf 'producer_rc=%s filter_rc=%s\n' "$producer_rc" "$filter_rc"
[ "$filter_rc" -le 1 ] || { rm -f "$tmp"; exit "$filter_rc"; }
rm -f "$tmp"

fi`

CRI endpoint는 active kubelet argv 또는 그 argv가 가리킨 실제 config source에서 exact 하나를 확인한다. runtime provider 문자열로 socket을 추측하지 않는다. inspect 원문은 env/mount를 노출할 수 있어 저장하지 않고 exact ID·Pod UID·state relation만 기록한다.

## dependency·보안 경계

`[-]etcd`가 직접 보일 때만 API server가 사용하는 실제 etcd endpoint/TLS identity를 control-plane owner에게 요청한다. endpoint·CA·client cert/key 경로를 추측하거나 private key를 출력하지 않고, etcd health와 quorum은 etcd 전용 절차에서 확인한다.

`kubectl auth can-i get --raw=/readyz`가 `yes`여도 실제 요청 성공을 보장하지 않는다. `no`/Forbidden이면 RBAC를 넓히지 않고 현재 subject·verb·non-resource URL만 RBAC owner에게 전달한다. audit는 승인된 owner가 requestURI path, verb, responseStatus, stageTimestamp, apiserver audit ID만 최소 공개하고 user/token/request·response body는 redaction한다.

## 상태 변경 경계와 정상화

이 문서에서 static manifest edit/delete, process·kubelet/runtime/etcd restart, LB backend 제거, 인증서 교체를 실행하지 않는다. 별도 변경에는 fresh endpoint/backend/Pod/Node UID·RV, source revision/hash, exact 증거 창, 영향·quorum, 승인 ID·작업 창·2인 확인, idempotence, 중단 조건과 rollback target이 필요하다. rollback 직전에도 target identity를 재조회하고 교체 Pod/container는 새 UID/ID로 재등록한다.

정상화는 원래 endpoint의 DNS/TCP/TLS/HTTP, `/livez`·`/readyz`, 실패 dependency, LB backend, 새 kube-apiserver UID/containerID와 restart 안정, 승인된 핵심 read API 기능이 모두 정상이고 관찰 창 동안 동일 오류가 없는 경우다. health 200 하나로 닫지 않는다.

## Prometheus 빠른 관측

`if [ "$SELECTION_READY" = true ] && [ "$PROM_READY" = true ] && [ "$TIME_READY" = true ]; then printf 'up{job="%s"} == 0\n' "$JOB_RE"; printf 'sum by(instance,code) (rate(apiserver_request_total{job="%s",code=~"5.."}[5m])) > 0\n' "$JOB_RE"; printf 'sum by(instance,request_kind) (apiserver_current_inflight_requests{job="%s"})\n' "$JOB_RE"; else printf '%s\n' '중단: current selection/prom/time gate가 아니다.' >&2; fi`

빈 결과는 정상/0이 아니다. target 미수집, job label 불일치, metric 이름/권한, query 시간 범위, Prometheus API 실패를 분리한다. `up=0`은 Prometheus→target scrape 실패이며 client→VIP 장애와 동일하지 않다.

## 증거와 미검증

실행 host, endpoint, curl rc/status, UTC 창, health check 이름, Pod/Node UID·RV, exact containerID/CRI provider relation, kubelet argv, producer/filter rc, 최소 RBAC/audit 필드, 승인/rollback과 실제 기능 결과를 보존한다. credential·내부 주소 목록·raw inspect·전체 logs는 저장하지 않는다.

Kubernetes 1.26 health endpoint와 static Pod 동작을 기준으로 했다. LB/provider, selector/label, unit/config, CRI endpoint/runtime, etcd topology, audit/metrics는 환경 미검증이다.
