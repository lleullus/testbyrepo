# API 요청 지연이 증가하거나 timeout이 발생하는 경우

## 입력값과 빠른 수집

실행 hop은 `원 client → client-side rate limiter → DNS/TCP/TLS → VIP/LB → kube-apiserver → APF queue → admission(write만) → storage/etcd → response`다. 실행 host와 path가 달라지면 timing을 같은 증거로 합치지 않는다.

| 종류 | 변수 | 출처와 gate |
|---|---|---|
| 최초 입력 | `REQ_METHOD`, `REQ_PATH` | 원 client의 method와 redacted API path |
| 로컬 자동값 | `API_URL`, `COLLECTED_UTC`, `READ_ONLY` | kubeconfig server, 현재 UTC, GET/HEAD 여부 |
| API 자동값 | `APISERVER_UIDS`, `APISERVER_RVS`, `APISERVER_NODES` | component selector가 유효하고 API가 응답할 때만 |
| 계산값 | `PATH_RE`, `JOB_RE`, `LOCAL_PROXY_URL` | escaped log/PromQL 값과 작업 host local URL |
| 운영자 선택값 | `START_UTC`, `END_UTC`, `LOCAL_PORT`, `PROM_JOB`, APF UID/name, exact Pod/container | 원 timing/header/inventory 확인 뒤 선택 |

### 2. API identity·선택값·UTC

재조회 전 identity/RV/owner/containerID/node/host/relation/time/argv-regex와 downstream READY를 모두 폐기한다. API나 filter 실패 뒤 stale timing·mapping을 사용하지 않는다.

`unset API_READY TIME_READY PROXY_READY REQUEST_READY HEADER_READY APF_READY RELATION_READY LOG_READY METRIC_READY DOWNSTREAM_READY APISERVER_UIDS APISERVER_RVS APISERVER_NODES APISERVER_POD APISERVER_UID APISERVER_RV APISERVER_CONTAINER POD_NODE NODE_UID NODE_RV OWNER_KIND OWNER_UID CONTAINER_IDS CONTAINER_ID HOST_ID HOST_RELATION CRI_ENDPOINT RUNTIME_UNIT FLOW_UID PL_UID FLOW_NAME PL_NAME FLOW_RV PL_RV SERVICE_UID SERVICE_RV ENDPOINTSLICE_UIDS START_UTC END_UTC START_EPOCH END_EPOCH PROM_JOB JOB_RE LOCAL_PORT LOCAL_PROXY_URL PROXY_PID PROXY_LOG ARGV_RE; API_READY=false; if [ "$LOCAL_READY" != true ]; then printf '%s\n' '중단: LOCAL_READY가 아니다.' >&2; elif PODS_JSON="$(kubectl get pods -n kube-system -l component=kube-apiserver -o json)"; then APISERVER_UIDS="$(jq -r '[.items[].metadata.uid]|join(",")' <<<"$PODS_JSON")"; APISERVER_RVS="$(jq -r '[.items[].metadata.resourceVersion]|join(",")' <<<"$PODS_JSON")"; APISERVER_NODES="$(jq -r '[.items[].spec.nodeName]|join(",")' <<<"$PODS_JSON")"; jq -r '.items[]|"Pod=\(.metadata.name) UID=\(.metadata.uid) RV=\(.metadata.resourceVersion) Node=\(.spec.nodeName) Ready=\([.status.containerStatuses[]?.ready]|join(",")) ContainerID=\([.status.containerStatuses[]?.containerID]|join(","))"' <<<"$PODS_JSON"; API_READY=true; export APISERVER_UIDS APISERVER_RVS APISERVER_NODES; printf 'API_READY=true candidates=%s\n' "$(jq '.items|length' <<<"$PODS_JSON")"; else printf '%s\n' 'API component 조회 실패: managed/selector/권한/API 상태 분리, stale 값 폐기됨' >&2; fi`

`if [ "$API_READY" = true ] && [ "$(jq '.items|length' <<<"$PODS_JSON")" -lt 1 ]; then API_READY=false; unset APISERVER_UIDS APISERVER_RVS APISERVER_NODES; printf '%s\n' '중단: kube-apiserver 후보 0건; selector/managed 환경을 분리' >&2; fi`

`START_UTC='PASTE_START_UTC_RFC3339_HERE'; END_UTC='PASTE_END_UTC_RFC3339_HERE'; LOCAL_PORT='PASTE_UNUSED_LOCAL_PROXY_PORT_HERE'; PROM_JOB='PASTE_PROMETHEUS_JOB_LABEL_HERE'`

`TIME_READY=false; unset START_EPOCH END_EPOCH JOB_RE LOCAL_PROXY_URL PROXY_READY REQUEST_READY HEADER_READY APF_READY LOG_READY METRIC_READY DOWNSTREAM_READY; if [[ "$START_UTC" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] && [[ "$END_UTC" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] && [ "$(date -u -d "$START_UTC" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" = "$START_UTC" ] && [ "$(date -u -d "$END_UTC" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" = "$END_UTC" ]; then START_EPOCH="$(date -u -d "$START_UTC" +%s)"; END_EPOCH="$(date -u -d "$END_UTC" +%s)"; [ "$START_EPOCH" -lt "$END_EPOCH" ] && TIME_READY=true; fi; if ! [[ "$LOCAL_PORT" =~ ^[0-9]+$ ]] || (( LOCAL_PORT < 1024 || LOCAL_PORT > 65535 )); then printf '%s\n' '중단: local port 범위 오류' >&2; TIME_READY=false; fi; JOB_RE="$(printf '%s' "$PROM_JOB" | sed 's/\\/\\\\/g; s/"/\\"/g')"; LOCAL_PROXY_URL="http://127.0.0.1:$LOCAL_PORT$REQ_PATH"; export START_UTC END_UTC LOCAL_PORT PROM_JOB JOB_RE LOCAL_PROXY_URL; printf 'TIME_READY=%s start=%s end=%s local_url=%s JOB_RE=%s\n' "$TIME_READY" "$START_UTC" "$END_UTC" "$LOCAL_PROXY_URL" "$JOB_RE"`

`PROM_READY=false; [ "$TIME_READY" = true ] && [ -n "$PROM_JOB" ] && PROM_READY=true; printf 'PROM_READY=%s\n' "$PROM_READY"`

`127.0.0.1`은 Pod나 API server가 아니라 `kubectl proxy`를 실행한 작업 host의 loopback이다. curl도 같은 host에서 실행한다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 같은 method/path에서 평소보다 느린 응답, client/gateway timeout, request duration 증가가 직접 관측됨 |
| 적용 | client wait, transport, APF, admission, audit, storage를 같은 UTC 창으로 분리 가능 |
| 제외 | HTTP 429는 [[04. API 요청에 429 Too Many Requests가 반환되는 경우]], 500/503은 [[02. API 요청에 500·503 오류가 반환되는 경우]], transport 단절은 [[01. kube-apiserver health endpoint가 실패하거나 API endpoint에 연결할 수 없는 경우]] |

검색 문자열: `client-side throttling`, `X-Kubernetes-PF-FlowSchema-UID`, `X-Kubernetes-PF-PriorityLevel-UID`, `request timed out`, `failed calling webhook`, `Failed to write audit event`, `etcdserver: request timed out`.

## 최초 확인: 읽기 요청과 proxy lifecycle

POST/PUT/PATCH/DELETE를 재현하지 않는다. GET/HEAD만 local proxy로 한 번 측정한다.

`if [ "$READ_ONLY" != true ] || [ "$TIME_READY" != true ]; then printf '%s\n' '중단: read-only/time gate가 아니다.' >&2; elif [ -n "${PROXY_PID:-}" ] && kill -0 "$PROXY_PID" 2>/dev/null; then printf '중단: 이전 proxy가 살아 있음 pid=%s\n' "$PROXY_PID" >&2; else unset PROXY_PID PROXY_LOG; PROXY_READY=false; PROXY_LOG="$(mktemp)" || exit 1; kubectl proxy --port="$LOCAL_PORT" --api-prefix=/ --accept-hosts='^localhost$,^127\.0\.0\.1$' --reject-methods='POST,PUT,PATCH,DELETE' >"$PROXY_LOG" 2>&1 & PROXY_PID=$!; for WAIT in 1 2 3 4 5; do if grep -Fq "Starting to serve on 127.0.0.1:$LOCAL_PORT" "$PROXY_LOG"; then PROXY_READY=true; break; fi; kill -0 "$PROXY_PID" 2>/dev/null || break; sleep 1; done; printf 'PROXY_READY=%s pid=%s log=%s\n' "$PROXY_READY" "$PROXY_PID" "$PROXY_LOG"; fi`

`HEADER_READY=false; if [ "$PROXY_READY" != true ]; then printf '%s\n' '중단: PROXY_READY가 아니다.' >&2; else HEADER_FILE="$(mktemp)" || exit 1; START_NS="$(date -u +%s%N)"; CODE="$(curl -sS -X "$REQ_METHOD" -D "$HEADER_FILE" -o /dev/null -w '%{http_code}' --max-time 20 "$LOCAL_PROXY_URL")"; CURL_RC=$?; END_NS="$(date -u +%s%N)"; ELAPSED_MS=$(( (END_NS-START_NS)/1000000 )); if [ "$CURL_RC" -eq 0 ] && [ "$CODE" != 000 ]; then HEADER_READY=true; fi; if grep -E -i '^(HTTP/|Retry-After:|X-Kubernetes-PF-FlowSchema-UID:|X-Kubernetes-PF-PriorityLevel-UID:)' "$HEADER_FILE"; then FILTER_RC=0; else FILTER_RC=$?; fi; printf 'curl_rc=%s http=%s elapsed_ms=%s header_filter_rc=%s HEADER_READY=%s\n' "$CURL_RC" "${CODE:-000}" "$ELAPSED_MS" "$FILTER_RC" "$HEADER_READY"; rm -f "$HEADER_FILE"; [ "$CURL_RC" -eq 0 ] && [ "$FILTER_RC" -le 1 ]; fi`

`if [ -n "${PROXY_PID:-}" ] && kill -0 "$PROXY_PID" 2>/dev/null; then kill "$PROXY_PID" 2>/dev/null; wait "$PROXY_PID" 2>/dev/null || true; fi; if [ -n "${PROXY_PID:-}" ] && kill -0 "$PROXY_PID" 2>/dev/null; then printf '중단: proxy 종료 실패 pid=%s\n' "$PROXY_PID" >&2; else rm -f "${PROXY_LOG:-}"; unset PROXY_PID PROXY_LOG LOCAL_PROXY_URL; PROXY_READY=false; HEADER_READY=false; printf '%s\n' 'proxy 종료 및 cycle 변수 무효화'; fi`

proxy process 생존은 listener 또는 API 응답 성공을 보장하지 않는다. external path와 local proxy의 실행 host·TLS·LB hop이 다르므로 timing 차이만 비교하고 결과를 동일 요청으로 간주하지 않는다.

## 관측별 진단 경로

| 지금 보이는 것 | 직접 증거 | 다음 경계 |
|---|---|---|
| HTTP 전 `client-side throttling` | 실제 request 시작 전 대기 | client QPS/Burst·fan-out owner |
| APF UID header와 queue 증가 | exact FlowSchema/PL UID·rule | APF queue/concurrency |
| external만 느림 | DNS/connect/starttransfer 차이 | LB/network owner |
| write와 webhook duration | matching rule/service UID | webhook backend |
| storage/etcd timeout | same request/time API log | etcd storage owner |
| audit write 오류 | blocking backend와 same time | audit owner |

## APF identity·RBAC gate

APF header의 UID를 원 transcript에서 선택한다. 이름은 승인된 UID mapping으로 확인하며 목록 첫 항목을 자동 선택하지 않는다.

`FLOW_UID='PASTE_FLOWSCHEMA_UID_FROM_HEADER_HERE'; PL_UID='PASTE_PRIORITYLEVEL_UID_FROM_HEADER_HERE'; FLOW_NAME='PASTE_CONFIRMED_FLOWSCHEMA_NAME_HERE'; PL_NAME='PASTE_CONFIRMED_PRIORITYLEVEL_NAME_HERE'`

`APF_READY=false; unset FLOW_RV PL_RV DOWNSTREAM_READY; if [ "$TIME_READY" != true ]; then printf '%s\n' '중단: TIME_READY가 아니다.' >&2; elif [ "$(kubectl auth can-i get flowschemas.flowcontrol.apiserver.k8s.io)" != yes ] || [ "$(kubectl auth can-i get prioritylevelconfigurations.flowcontrol.apiserver.k8s.io)" != yes ]; then printf '%s\n' '중단: 현재 subject의 exact read 권한 없음; RBAC 확대 금지' >&2; elif FLOW_JSON="$(kubectl get flowschema "$FLOW_NAME" -o json)" && PL_JSON="$(kubectl get prioritylevelconfiguration "$PL_NAME" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$FLOW_JSON")" = "$FLOW_UID" ] && [ "$(jq -r '.metadata.uid' <<<"$PL_JSON")" = "$PL_UID" ]; then FLOW_RV="$(jq -r '.metadata.resourceVersion' <<<"$FLOW_JSON")"; PL_RV="$(jq -r '.metadata.resourceVersion' <<<"$PL_JSON")"; APF_READY=true; jq -r '"FlowSchema=\(.metadata.name) UID=\(.metadata.uid) RV=\(.metadata.resourceVersion) precedence=\(.spec.matchingPrecedence) PL=\(.spec.priorityLevelConfiguration.name)"' <<<"$FLOW_JSON"; jq -r '"PriorityLevel=\(.metadata.name) UID=\(.metadata.uid) RV=\(.metadata.resourceVersion) type=\(.spec.type) shares=\(.spec.limited.nominalConcurrencyShares//"-") response=\(.spec.limited.limitResponse.type//"-") queues=\(.spec.limited.limitResponse.queuing.queues//"-") length=\(.spec.limited.limitResponse.queuing.queueLengthLimit//"-")"' <<<"$PL_JSON"; else printf '%s\n' '중단: APF header UID↔exact object relation 실패' >&2; fi`

`auth can-i=yes`는 실제 request subject/rule match나 성공을 보장하지 않는다. FlowSchema subjects·verb·group·resource·namespace가 원 요청과 일치해야 한다. `Queue`와 queue 증가면 APF 지연 후보, `Reject`/queue-full과 429면 429 런북으로 이동한다.

## API server log·pipeline rc

`APISERVER_POD='PASTE_EXACT_APISERVER_POD_HERE'; APISERVER_CONTAINER='PASTE_EXACT_APISERVER_CONTAINER_HERE'`

`LOG_READY=false; unset APISERVER_UID APISERVER_RV POD_NODE CONTAINER_IDS CONTAINER_ID DOWNSTREAM_READY; if [ "$API_READY" != true ] || [ "$TIME_READY" != true ]; then printf '%s\n' '중단: API/time gate가 아니다.' >&2; elif AP_JSON="$(kubectl get pod "$APISERVER_POD" -n kube-system -o json)" && CONTAINER_ID_TMP="$(jq -er --arg c "$APISERVER_CONTAINER" '[.status.containerStatuses[]?|select(.name==$c)|.containerID]|if length==1 and .[0]!="" then .[0] else error("current containerID") end' <<<"$AP_JSON")"; then APISERVER_UID="$(jq -r '.metadata.uid' <<<"$AP_JSON")"; APISERVER_RV="$(jq -r '.metadata.resourceVersion' <<<"$AP_JSON")"; POD_NODE="$(jq -r '.spec.nodeName' <<<"$AP_JSON")"; CONTAINER_ID="$CONTAINER_ID_TMP"; LOG_READY=true; export APISERVER_UID APISERVER_RV POD_NODE APISERVER_CONTAINER CONTAINER_ID; printf 'LOG_READY=true pod=%s uid=%s rv=%s node=%s container=%s current_id=%s\n' "$APISERVER_POD" "$APISERVER_UID" "$APISERVER_RV" "$POD_NODE" "$APISERVER_CONTAINER" "$CONTAINER_ID"; else printf '%s\n' '중단: current Pod/container relation 실패' >&2; fi`

`if [ "$LOG_READY" != true ]; then printf '%s\n' '중단: LOG_READY가 아니다.' >&2; elif CURRENT_AP_JSON="$(kubectl get pod "$APISERVER_POD" -n kube-system -o json)" && [ "$(jq -r '.metadata.uid' <<<"$CURRENT_AP_JSON")" = "$APISERVER_UID" ] && [ "$(jq -r '.metadata.resourceVersion' <<<"$CURRENT_AP_JSON")" = "$APISERVER_RV" ] && [ "$(jq -r --arg c "$APISERVER_CONTAINER" '.status.containerStatuses[]?|select(.name==$c)|.containerID' <<<"$CURRENT_AP_JSON")" = "$CONTAINER_ID" ]; then TMP="$(mktemp)" || exit 1; if kubectl logs "$APISERVER_POD" -n kube-system -c "$APISERVER_CONTAINER" --timestamps --since-time="$START_UTC" --tail=400 >"$TMP"; then PRODUCER_RC=0; else PRODUCER_RC=$?; fi; if [ "$PRODUCER_RC" -eq 0 ]; then if grep -E -i -C 3 "$PATH_RE|client-side throttling|flowcontrol|queue|failed calling webhook|Failed to write audit event|etcdserver: request timed out|context deadline exceeded|timeout" "$TMP"; then FILTER_RC=0; else FILTER_RC=$?; fi; else FILTER_RC=125; fi; printf 'producer_rc=%s filter_rc=%s pod_uid=%s current_container_id=%s\n' "$PRODUCER_RC" "$FILTER_RC" "$APISERVER_UID" "$CONTAINER_ID"; rm -f "$TMP"; [ "$PRODUCER_RC" -eq 0 ] && [ "$FILTER_RC" -le 1 ]; else LOG_READY=false; printf '%s\n' '중단: Pod UID/RV/current containerID 변경; 재등록 필요' >&2; fi`

filter rc 1은 해당 bounded 창/identity에서 무일치이며 정상 증거가 아니다. audit는 승인된 owner가 audit ID, verb, redacted requestURI, objectRef UID, responseStatus, requestReceived/stage timestamps만 최소 공개한다. 사용자·source IP·request/response body는 redaction한다.

audit 상관은 단일 auditID의 requestReceivedTimestamp와 stageTimestamp가 `START_UTC..END_UTC` 안에 있고, verb·resource/subresource·namespace/name·redacted requestURI 및 현재 lifecycle UID가 원 요청과 모두 맞을 때만 사용한다.

## 상태 변경 경계

진단은 read-only다. APF patch, client QPS/Burst 일괄 상향, webhook/audit 비활성화, API server/etcd restart, 폭주 workload scale을 실행하지 않는다. 변경에는 fresh APF UID/RV와 matching evidence, Pod/container identity, 대상/영향, approval/window/quorum, idempotence/side effect, 다른 priority level 보호, rollback target/source revision과 중단 조건이 필요하다. rollback 직전 재조회하고 replacement identity를 재등록한다.

## 정상화 검증

같은 실행 host·method·path의 status/latency가 승인 기준에 들어오고, client wait와 server timing이 분리되며, APF queue/reject, webhook, audit, storage 오류가 관찰 창 동안 안정돼야 한다. external 실제 API 기능과 control-plane critical client 영향도 확인한다. `/readyz`, 단일 2xx, queue 한 번 감소는 단독 정상화 근거가 아니다.

## Prometheus 빠른 관측

`if [ "$TIME_READY" = true ] && [ "$PROM_READY" = true ]; then printf 'histogram_quantile(0.99, sum by(le,instance,verb,resource,subresource) (rate(apiserver_request_duration_seconds_bucket{job="%s"}[5m])))\n' "$JOB_RE"; printf 'sum by(instance,flow_schema,priority_level) (apiserver_flowcontrol_current_inqueue_requests{job="%s"})\n' "$JOB_RE"; printf 'sum by(instance,flow_schema,priority_level) (apiserver_flowcontrol_current_executing_requests{job="%s"})\n' "$JOB_RE"; printf 'histogram_quantile(0.99, sum by(le,instance) (rate(etcd_request_duration_seconds_bucket{job="%s"}[5m])))\n' "$JOB_RE"; else printf '%s\n' '중단: current TIME_READY/PROM_READY가 아니다.' >&2; fi`

빈 결과는 0/정상이 아니다. bucket/label 미수집, 잘못된 job, query 범위, Prometheus 권한/API 실패를 분리한다. histogram p99는 단일 요청의 정확한 latency가 아니며 client/LB/admission/audit 원인을 단독 확정하지 않는다.

## 증거와 미검증

실행 host, method/path, strict UTC 창, client/proxy/external timing, APF header UID↔object UID/RV, API server Pod/Node/container relation, producer/filter rc, 최소 RBAC/audit 필드, 승인/rollback·실제 기능을 보존한다. token·body·전체 audit/log/metrics는 저장하지 않는다.
