# VolumeAttachment가 수렴하지 않거나 Multi-Attach가 발생하는 경우

## 입력값과 빠른 수집

identity chain은 `exact VolumeAttachment UID → PV name/UID·CSI driver → PVC namespace/name/UID → 같은 PV의 attachment UID/node set → consumer Pod UID/owner/node`다. Multi-Attach Event만 있다면 storage inventory에서 exact VolumeAttachment 이름을 확인한 뒤 시작한다. 이름 fragment로 cluster 전체에서 추측하지 않는다.

| 종류 | 변수 | 등록 기준 |
|---|---|---|
| 최초 입력 | context, exact VolumeAttachment | exact API 조회 |
| API 자동값 | attachment/PV/PVC/SC/target Node identity, same-PV attachment set, consumer 후보 | 모든 relation 성공 뒤 등록 |
| 계산 후보 | consumer mapping, 완성 PromQL | API 출력이며 임의 선택 금지 |
| 운영자 선택값 | 관련 consumer Pod, CSI controller Pod·regular container, UTC 창 | 증거와 inventory에서 선택 |

volume handle은 존재 여부만 출력한다. Secret, token, private key와 backend credential은 출력하지 않는다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | current attachment가 attached=false/error이거나 same-PV attachment가 여러 node에 존재함 |
| 적용 | PV/PVC/access mode, consumer, controller publish/unpublish를 연결 가능 |
| 제외 | attached=true 이후 mount는 [[25. Pod 이벤트에 FailedMount·FailedAttachVolume이 기록된 경우]], StatefulSet identity는 [[04. StatefulSet Pod 이름·ordinal과 PVC identity가 맞지 않는 경우]] |

검색 문자열: `Multi-Attach`, `already exclusively attached`, `ControllerPublishVolume`, `ControllerUnpublishVolume`, `attachError`, `detachError`, `attached=false`, `deadline exceeded`.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 다음 경로 |
|---|---|---|
| old attachment attached=true | old consumer UID/node 실제 사용 | unpublish·data owner |
| target attached=false | attacher/driver와 current node | CSI controller log |
| attached=true인데 mount 실패 | node stage/mount | mount 전용 런북 |
| RWO consumer가 두 node | process/mount와 quorum | split-brain 대응 |

### 1. attachment·consumer mapping

**실행:** `refresh_va && refresh_consumer_va && jq -r --arg pv "$PV" '.items[] | select(.spec.source.persistentVolumeName==$pv) | "Attachment=\(.metadata.name) UID=\(.metadata.uid) RV=\(.metadata.resourceVersion) node=\(.spec.nodeName) attacher=\(.spec.attacher) attached=\(.status.attached // false) attachError=\(.status.attachError.message // \"-\") detachError=\(.status.detachError.message // \"-\")"' <<<"$ALL_VA_JSON" && kubectl --context "$CONTEXT" get pv "$PV" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,RV:.metadata.resourceVersion,PHASE:.status.phase,CLAIM-NS:.spec.claimRef.namespace,CLAIM:.spec.claimRef.name,CLAIM-UID:.spec.claimRef.uid,ACCESS:.spec.accessModes,DRIVER:.spec.csi.driver' && kubectl --context "$CONTEXT" get pvc "$PVC" -n "$PVC_NS" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,RV:.metadata.resourceVersion,PHASE:.status.phase,VOLUME:.spec.volumeName,ACCESS:.spec.accessModes'`

`attached=true`는 controller publish 상태이며 process 종료, node unstage, mount와 data integrity를 보장하지 않는다. old Pod 삭제 상태만으로 old mount 종료를 확정하지 않는다. RWO 계열이 두 node에서 실제 사용 중이면 split-brain 위험으로 즉시 data/workload/storage owner에게 이관한다.

**direct fresh log gate·pipeline 분리:** `if ! refresh_va || ! refresh_csi_va || [ "$WINDOW_READY" != true ]; then printf '%s\n' '중단: fresh volume/CSI/window gate 실패' >&2; elif kubectl --context "$CONTEXT" auth can-i get pods/log -n "$CSI_NS" --quiet; then RAW="$(mktemp)"; CUT="$(mktemp)"; if kubectl --context "$CONTEXT" logs "$CSI_POD" -n "$CSI_NS" -c "$CSI_CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=500 >"$RAW"; then if awk -v end="$END_RFC3339" '$1 <= end' "$RAW" >"$CUT"; then if grep -E -i -C 3 "$VA_RE|$PV_RE|$PVC_RE|ControllerPublishVolume|ControllerUnpublishVolume|multi-attach|already exclusively attached|timeout|deadline|permission|denied|not found|error" "$CUT"; then :; elif [ "$?" -eq 1 ]; then printf '%s\n' 'filter no-match: 오류 부재가 아님' >&2; else printf '%s\n' 'regex filter 오류' >&2; fi; else printf '%s\n' '시간 filter 오류' >&2; fi; else printf '%s\n' 'log producer 실패' >&2; fi; rm -f "$RAW" "$CUT"; else printf '%s\n' '중단: pods/log RBAC current gate 실패' >&2; fi`

controller namespace·Pod·container를 CSI driver 이름에서 추측하지 않는다. `not found`는 redacted storage inventory와 대조하며 volume handle 원문을 log filter에 넣지 않는다.

## 변경 경계·정상화·PromQL

VolumeAttachment 강제 삭제, force detach, Pod/PVC/PV 삭제, controller restart 명령은 제공하지 않는다. 별도 변경은 fresh attachment set·PV/PVC·consumer/controller UID, storage의 실제 publish/mount 증거, 승인 ID, RWO/quorum/data 영향, 멱등성, 중단 조건이 필요하다. detach·삭제는 일반 rollback이 아니며 복구 절차를 사전 검증해야 한다. 새 attachment가 생기면 새 UID/node set으로 처음부터 재등록한다.

**정상화 gate:** `refresh_va && kubectl --context "$CONTEXT" get volumeattachment "$VA" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,RV:.metadata.resourceVersion,NODE:.spec.nodeName,ATTACHER:.spec.attacher,PV:.spec.source.persistentVolumeName,ATTACHED:.status.attached,ATTACH-ERROR:.status.attachError.message,DETACH-ERROR:.status.detachError.message' && kubectl --context "$CONTEXT" get pvc "$PVC" -n "$PVC_NS" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,VOLUME:.spec.volumeName,ACCESS:.spec.accessModes'`

정상화는 `old process/mount 종료 → storage unpublish → controller publish → current attachment → PV/PVC/access mode → new consumer mount → 실제 data read/write·replication·서비스` 순서다. attached=true나 새 Pod Running만으로 닫지 않고 승인된 관찰 창에 Multi-Attach·timeout 재발이 없어야 한다.

**완성 PromQL 생성:** `QUERY_READY=false; if ! refresh_va; then printf '%s\n' '중단: fresh gate 실패' >&2; else VA_Q="$(printf '%s' "$VA" | sed 's/\\/\\\\/g; s/"/\\"/g')"; QUERY_READY=true; printf 'kube_volumeattachment_info{volumeattachment="%s"}\n' "$VA_Q"; printf 'kube_volumeattachment_status_attached{volumeattachment="%s"} == 0\n' "$VA_Q"; printf 'time() - kube_volumeattachment_created{volumeattachment="%s"}\n' "$VA_Q"; fi`

metric 미지원·opt-in, empty vector, label·권한/query 실패와 조회 범위를 분리한다. PromQL은 storage session·mount·error message를 증명하지 않는다. 보존 항목은 attachment/PV/PVC/SC/node/consumer/controller UID·RV·owner, canonical 창, redacted backend mapping, 승인·중단·기능 결과다. 실제 Kubernetes·CSI·storage·Prometheus 환경은 미검증이다.
