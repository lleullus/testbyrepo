# PV·PVC의 phase·claimRef·reclaim 상태가 맞지 않는 경우

## 입력값과 빠른 수집

identity chain은 `PVC namespace/name/UID → spec.volumeName → PV name/UID → claimRef namespace/name/UID → CSI driver → current VolumeAttachment/node`다. phase와 reclaim policy는 이 identity가 맞은 뒤 해석한다. PV만 관찰했더라도 claimRef가 가리키는 exact PVC를 최초 입력으로 사용한다.

| 종류 | 변수 | 등록 기준 |
|---|---|---|
| 최초 입력 | context, namespace, PVC | exact PVC 조회 |
| API 자동값 | PVC/PV UID·RV·phase·owner·claimRef·policy, StorageClass, CSI, attachment set | 전체 relation 성공 뒤 등록 |
| 계산 후보 | 완성 PromQL | exact identity로 생성 |
| 운영자 선택값 | CSI controller Pod·regular container와 UTC 창 | inventory·결정적 오류에서 선택 |

**실행 위치·도구 확인:** `TOOLS_READY=false; MISSING=''; for T in kubectl jq sed date mktemp grep awk; do command -v "$T" >/dev/null 2>&1 || MISSING="$MISSING $T"; done; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: Bash에서 실행한다.' >&2; elif [ -n "$MISSING" ]; then printf '중단: 없는 도구=%s\n' "$MISSING" >&2; else TOOLS_READY=true; printf 'TOOLS_READY=true bash=%s\n' "$BASH_VERSION"; fi`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | current PVC/PV에서 phase, volumeName, claimRef UID 또는 reclaim 상태가 모순됨 |
| 적용 | object identity와 data lifecycle 경계를 정해야 함 |
| 제외 | PVC에 volumeName이 없으면 [[01. PVC가 Pending에서 Bound로 수렴하지 않는 경우]], Multi-Attach는 [[03. VolumeAttachment가 수렴하지 않거나 Multi-Attach가 발생하는 경우]] |

검색 문자열: `Bound`, `Released`, `Failed`, `Lost`, `claimRef`, `reclaimPolicy`, `Retain`, `Delete`, `finalizer`, `DeleteVolume`.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 다음 경로 |
|---|---|---|
| PVC Bound, claimRef UID 다름 | 두 UID·생성 시각 | binding controller·data owner |
| PV Released | 마지막 claim UID·Retain/Delete | data lifecycle owner |
| PV Failed/PVC Lost | finalizer·CSI error | [[#2. CSI lifecycle log|2]] |
| policy만 다름 | PV 실제 policy와 생성 이력 | 정책 owner |

### 1. current object·attachment 관계

**실행:** `refresh_binding && kubectl --context "$CONTEXT" get pvc "$PVC" -n "$NS" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,RV:.metadata.resourceVersion,PHASE:.status.phase,VOLUME:.spec.volumeName,STORAGE-CLASS:.spec.storageClassName,CREATED:.metadata.creationTimestamp' && kubectl --context "$CONTEXT" get pv "$PV" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,RV:.metadata.resourceVersion,PHASE:.status.phase,CLAIM-NS:.spec.claimRef.namespace,CLAIM:.spec.claimRef.name,CLAIM-UID:.spec.claimRef.uid,RECLAIM:.spec.persistentVolumeReclaimPolicy,DELETION:.metadata.deletionTimestamp,FINALIZERS:.metadata.finalizers,DRIVER:.spec.csi.driver,CREATED:.metadata.creationTimestamp'`

**attachment 실행:** `refresh_binding && jq -r --arg pv "$PV" '.items[] | select(.spec.source.persistentVolumeName==$pv) | "Attachment=\(.metadata.name) UID=\(.metadata.uid) RV=\(.metadata.resourceVersion) node=\(.spec.nodeName) attacher=\(.spec.attacher) attached=\(.status.attached // false) attachError=\(.status.attachError.message // \"-\") detachError=\(.status.detachError.message // \"-\")"' <<<"$VA_JSON"`

정상 binding은 PVC Bound·volumeName 일치, PV Bound, claimRef namespace/name/UID 일치다. attachment가 없다는 사실은 mount 정상이나 오류를 뜻하지 않는다. `Released+Retain`의 claimRef를 stale로 보고 삭제하지 않는다. `Delete` 성공 status도 backend data 삭제를 단독 보장하지 않는다.

**PVC UID Event 실행:** `refresh_binding && kubectl --context "$CONTEXT" get events -n "$NS" --field-selector "involvedObject.kind=PersistentVolumeClaim,involvedObject.name=$PVC,involvedObject.uid=$PVC_UID" --sort-by=.metadata.creationTimestamp -o custom-columns='CREATED:.metadata.creationTimestamp,FIRST:.firstTimestamp,LAST:.lastTimestamp,EVENT-TIME:.eventTime,SERIES-LAST:.series.lastObservedTime,TYPE:.type,REASON:.reason,COUNT:.count,MESSAGE:.message'`

API 실패와 성공한 빈 Event를 구분한다. 현재 PVC 생성 전 Event를 같은 lifecycle 증거로 사용하지 않는다.

CSI controller inventory가 확인된 경우에만 실행한다.

## 변경 경계·정상화·PromQL

PVC/PV 삭제, claimRef patch, 강제 bind/rebind, Released PV 재사용 명령은 제공하지 않는다. 별도 lifecycle 변경은 fresh UID·claimRef·attachment set·controller containerID, backup/data owner, 승인 ID, Retain/Delete 영향, 멱등성, 중단 조건과 실제 rollback이 필요하다. 삭제·backend detach는 일반 rollback이 아니다.

**정상화 gate:** `refresh_binding && kubectl --context "$CONTEXT" get pvc "$PVC" -n "$NS" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,RV:.metadata.resourceVersion,PHASE:.status.phase,VOLUME:.spec.volumeName' && kubectl --context "$CONTEXT" get pv "$PV" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,RV:.metadata.resourceVersion,PHASE:.status.phase,CLAIM-NS:.spec.claimRef.namespace,CLAIM:.spec.claimRef.name,CLAIM-UID:.spec.claimRef.uid,RECLAIM:.spec.persistentVolumeReclaimPolicy'`

정상화는 `backend lifecycle → CSI controller → attachment → PV policy·claimRef → PVC volumeName·phase → mount → 실제 data read/write·replication` 순서다. phase 하나를 바꾼 것으로 닫지 않는다.

**완성 PromQL 생성:** `QUERY_READY=false; if ! refresh_binding; then printf '%s\n' '중단: fresh gate 실패' >&2; else NS_Q="$(printf '%s' "$NS" | sed 's/\\/\\\\/g; s/"/\\"/g')"; PVC_Q="$(printf '%s' "$PVC" | sed 's/\\/\\\\/g; s/"/\\"/g')"; PV_Q="$(printf '%s' "$PV" | sed 's/\\/\\\\/g; s/"/\\"/g')"; QUERY_READY=true; printf 'kube_persistentvolumeclaim_status_phase{namespace="%s",persistentvolumeclaim="%s"} == 1\n' "$NS_Q" "$PVC_Q"; printf 'kube_persistentvolume_status_phase{persistentvolume="%s"} == 1\n' "$PV_Q"; printf 'kube_persistentvolumeclaim_info{namespace="%s",persistentvolumeclaim="%s",volumename="%s"}\n' "$NS_Q" "$PVC_Q" "$PV_Q"; fi`

empty vector와 metric·label·권한/query 실패를 분리한다. PromQL은 claimRef UID·reclaim 진행을 증명하지 않는다. 보존 항목은 PVC/PV/SC/attachment/controller UID·RV·owner, canonical 창, redacted backend identity, 승인·rollback·기능 결과다. 실제 인프라는 미검증이다.
