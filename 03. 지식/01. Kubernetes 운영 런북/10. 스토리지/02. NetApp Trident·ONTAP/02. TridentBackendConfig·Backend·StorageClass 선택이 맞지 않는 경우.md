# TridentBackendConfig·Backend·StorageClass 선택이 맞지 않는 경우

## 입력값과 빠른 수집

StorageClass 선언은 후보 집합이고, 실제 Backend 선택 결과는 PVC/PV와 Trident의 지원 interface에서 별도로 확인해야 한다. Backend 수가 여러 개라는 사실은 균등 분산을 보장하지 않는다.

| 입력 종류 | 변수 | 출처와 gate |
|---|---|---|
| 최초 입력 | `SC` | 문제가 관측된 exact StorageClass 이름 |
| API 확인 자동값 | SC UID·RV·provisioner, 조건부 PVC/PV UID·RV·claim relation | current API 성공 뒤에만 등록 |
| 계산 후보값 | `SC_RE` | SC 이름을 regex escape한 값. bounded 출력 확인 뒤 query/filter에 사용 |
| 운영자 선택값 | PVC, Trident namespace/controller container, TBC/Backend resource·scope, UTC 창 | current inventory·discovery 확인 후 선택 |

### 1. 실행 위치·도구·StorageClass identity

`TOOLS_READY=false; MISSING=''; for T in kubectl jq sed grep awk date; do command -v "$T" >/dev/null 2>&1 || MISSING="$MISSING $T"; done; if [ -n "${BASH_VERSION:-}" ] && [ -z "$MISSING" ]; then TOOLS_READY=true; else printf '중단: Bash 또는 도구 누락:%s\n' "$MISSING" >&2; fi`

`kubectl config view --minify -o json | jq -r '. as $x | "context=\($x["current-context"]|@sh) user-key=\($x.contexts[0].context.user|@sh) cluster-key=\($x.contexts[0].context.cluster|@sh)"'`

`unset INPUT_READY IDENTITY_READY RELATION_READY OWNER_READY CONTAINER_READY NODE_READY HOST_READY TIME_READY ARGUMENT_READY SELECTION_READY AUTH_READY EVIDENCE_READY MUTATION_READY ROLLBACK_READY NORMALIZATION_READY SC_UID SC_RV PROVISIONER SC_RE; SC='PASTE_TRIDENT_STORAGECLASS_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" = true ] && S0="$(kubectl get storageclass "$SC" -o json)"; then EXPECTED_SC_UID="$(jq -r '.metadata.uid' <<<"$S0")"; INPUT_READY=true; export SC EXPECTED_SC_UID; printf 'INPUT_READY=true sc=%s uid=%s\n' "$SC" "$EXPECTED_SC_UID"; else printf '%s\n' '중단: StorageClass exact 조회 실패' >&2; fi`

`refresh_sc(){ unset IDENTITY_READY RELATION_READY OWNER_READY CONTAINER_READY NODE_READY HOST_READY TIME_READY ARGUMENT_READY SELECTION_READY AUTH_READY EVIDENCE_READY MUTATION_READY ROLLBACK_READY NORMALIZATION_READY SC_UID SC_RV PROVISIONER SC_RE; IDENTITY_READY=false; RELATION_READY=false; ARGUMENT_READY=false; [ "$INPUT_READY" = true ] || return 1; local s; s="$(kubectl get storageclass "$SC" -o json)" || return 1; [ "$(jq -r '.metadata.uid' <<<"$s")" = "$EXPECTED_SC_UID" ] || { printf '%s\n' '중단: StorageClass UID 교체' >&2; return 1; }; SC_UID="$EXPECTED_SC_UID"; SC_RV="$(jq -r '.metadata.resourceVersion' <<<"$s")"; PROVISIONER="$(jq -r '.provisioner // empty' <<<"$s")"; SC_RE="$(printf '%s' "$SC" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; [ -n "$PROVISIONER" ] || return 1; IDENTITY_READY=true; RELATION_READY=true; ARGUMENT_READY=true; export SC_UID SC_RV PROVISIONER SC_RE; printf 'IDENTITY_READY=true sc=%s uid=%s rv=%s provisioner=%s regex=%s\n' "$SC" "$SC_UID" "$SC_RV" "$PROVISIONER" "$SC_RE"; }`

`if refresh_sc; then kubectl get storageclass "$SC" -o json | jq '{name:.metadata.name,uid:.metadata.uid,resourceVersion:.metadata.resourceVersion,provisioner:.provisioner,reclaimPolicy:.reclaimPolicy,volumeBindingMode:.volumeBindingMode,allowVolumeExpansion:.allowVolumeExpansion,selectionParameters:{backendType:.parameters.backendType,storagePools:.parameters.storagePools}}'; fi`

selection parameter는 운영 terminal에서만 확인하고 내부 Backend/SVM/aggregate 이름을 티켓·채팅·문서에 복사하지 않는다. Secret reference가 parameter에 있는 설치라면 이름과 type만 별도 확인하고 data는 읽지 않는다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | PVC/PV가 의도한 Backend/SVM 집합과 다르거나 `no suitable backend`, `no matching backend`가 발생한다. |
| 적용 | SC→PVC→PV→CSI driver와 실제 Trident Backend mapping을 current identity로 연결할 수 있다. |
| 제외 | Trident component·CRD 수렴은 [[01. Trident controller·node 또는 CRD 상태가 수렴하지 않는 경우]], ONTAP create API는 [[03. ONTAP API·SVM·LIF·aggregate 문제로 provisioning이 실패하는 경우]], NFS data path는 [[04. ONTAP NFS volume의 mount·export policy·Data LIF 접근이 실패하는 경우]]로 이동한다. |

검색 문자열: `backendType`, `storagePools`, `storageDriverName`, `backendName`, `no suitable backend`, `no matching backend`, `offline`, `ProvisioningFailed`.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| PVC가 다른 SC 사용 | PVC `storageClassName` | workload/admission 선택 owner | [[#1. PVC·PV 실제 선택]] |
| SC provisioner와 PV driver 다름 | current claimRef·driver | CSI registration owner | [[#1. PVC·PV 실제 선택]] |
| storagePools 교집합 없음 | current TBC/Backend status와 redacted mapping | Trident config owner | [[#2. TBC·Backend discovery]] |
| 선택은 맞지만 API/quota/mount 실패 | 최초 제품 오류 단계 | ONTAP provisioning/NFS 런북 | [[#3. controller evidence]] |

### 1. PVC·PV 실제 선택

`NS='PASTE_BACKEND_PVC_NAMESPACE_HERE'; PVC='PASTE_BACKEND_PVC_NAME_HERE'`

`refresh_claim(){ unset IDENTITY_READY RELATION_READY ARGUMENT_READY SELECTION_READY PVC_UID PVC_RV PV PV_UID PV_RV DRIVER; IDENTITY_READY=false; RELATION_READY=false; ARGUMENT_READY=false; SELECTION_READY=false; refresh_sc || return 1; local p v; p="$(kubectl get pvc "$PVC" -n "$NS" -o json)" || return 1; [ "$(jq -r '.spec.storageClassName // empty' <<<"$p")" = "$SC" ] || { printf '%s\n' '중단: PVC가 대상 StorageClass를 사용하지 않음' >&2; return 1; }; PV="$(jq -r '.spec.volumeName // empty' <<<"$p")"; [ -n "$PV" ] || { printf '%s\n' '미확정: 아직 PV 없음. Event/controller 경로만 사용' >&2; return 1; }; v="$(kubectl get pv "$PV" -o json)" || return 1; PVC_UID="$(jq -r '.metadata.uid' <<<"$p")"; PVC_RV="$(jq -r '.metadata.resourceVersion' <<<"$p")"; [ "$(jq -r '.spec.claimRef.uid // empty' <<<"$v")" = "$PVC_UID" ] && [ "$(jq -r '.spec.claimRef.namespace // empty' <<<"$v")" = "$NS" ] && [ "$(jq -r '.spec.claimRef.name // empty' <<<"$v")" = "$PVC" ] || { printf '%s\n' '중단: PV claimRef relation 불일치' >&2; return 1; }; DRIVER="$(jq -r '.spec.csi.driver // empty' <<<"$v")"; [ "$DRIVER" = "$PROVISIONER" ] || { printf '%s\n' '중단: SC provisioner/PV driver 불일치' >&2; return 1; }; PV_UID="$(jq -r '.metadata.uid' <<<"$v")"; PV_RV="$(jq -r '.metadata.resourceVersion' <<<"$v")"; IDENTITY_READY=true; RELATION_READY=true; ARGUMENT_READY=true; SELECTION_READY=true; export PVC_UID PVC_RV PV PV_UID PV_RV DRIVER; printf 'SELECTION_READY=true pvc=%s/%s pv=%s uid=%s rv=%s sc=%s driver=%s volumeHandle=REDACTED\n' "$PVC_UID" "$PVC_RV" "$PV" "$PV_UID" "$PV_RV" "$SC" "$DRIVER"; }`

`if refresh_claim; then kubectl get pvc "$PVC" -n "$NS" -o custom-columns='PVC:.metadata.name,UID:.metadata.uid,RV:.metadata.resourceVersion,SC:.spec.storageClassName,PHASE:.status.phase,PV:.spec.volumeName,REQUEST:.spec.resources.requests.storage,CAPACITY:.status.capacity.storage' && kubectl get pv "$PV" -o go-template='pv={{.metadata.name}} uid={{.metadata.uid}} rv={{.metadata.resourceVersion}} claim={{.spec.claimRef.namespace}}/{{.spec.claimRef.name}} claim-uid={{.spec.claimRef.uid}} sc={{.spec.storageClassName}} driver={{.spec.csi.driver}} volume-handle-present={{if .spec.csi.volumeHandle}}true{{else}}false{{end}}{{"\n"}}'; fi`

`Bound`와 volume handle 존재는 올바른 Backend/SVM 선택을 보장하지 않는다. handle 원문에서 Backend 이름을 추측하지 않고 승인된 Trident inventory의 redacted correlation으로만 연결한다.

### 2. TBC·Backend discovery

현재 discovery에 실제 resource가 있는 경우에만 사용한다. scope를 추측하지 않는다.

`TRIDENT_NS='PASTE_BACKEND_TRIDENT_NAMESPACE_HERE'; API_RESOURCE='PASTE_BACKEND_API_RESOURCE_HERE'; API_OBJECT='PASTE_BACKEND_API_OBJECT_HERE'; API_SCOPE='PASTE_BACKEND_API_SCOPE_HERE'`

`refresh_backend_api(){ unset IDENTITY_READY RELATION_READY OWNER_READY CONTAINER_READY NODE_READY HOST_READY TIME_READY ARGUMENT_READY SELECTION_READY AUTH_READY EVIDENCE_READY MUTATION_READY ROLLBACK_READY NORMALIZATION_READY API_UID API_RV API_VERSION API_KIND; IDENTITY_READY=false; RELATION_READY=false; ARGUMENT_READY=false; SELECTION_READY=false; [[ "$API_RESOURCE" =~ ^[a-z0-9.]+$ ]] || return 1; [ "$API_SCOPE" = Namespaced ] || [ "$API_SCOPE" = Cluster ] || return 1; kubectl api-resources --api-group=trident.netapp.io -o name | grep -Fx -- "$API_RESOURCE" >/dev/null || { printf '%s\n' '중단: discovery에 resource 없음' >&2; return 1; }; local a; if [ "$API_SCOPE" = Namespaced ]; then a="$(kubectl get "$API_RESOURCE" "$API_OBJECT" -n "$TRIDENT_NS" -o json)" || return 1; else a="$(kubectl get "$API_RESOURCE" "$API_OBJECT" -o json)" || return 1; fi; API_UID="$(jq -r '.metadata.uid' <<<"$a")"; API_RV="$(jq -r '.metadata.resourceVersion' <<<"$a")"; API_VERSION="$(jq -r '.apiVersion' <<<"$a")"; API_KIND="$(jq -r '.kind' <<<"$a")"; IDENTITY_READY=true; RELATION_READY=true; ARGUMENT_READY=true; SELECTION_READY=true; export API_UID API_RV API_VERSION API_KIND; printf 'SELECTION_READY=true resource=%s object=%s uid=%s rv=%s api=%s kind=%s scope=%s\n' "$API_RESOURCE" "$API_OBJECT" "$API_UID" "$API_RV" "$API_VERSION" "$API_KIND" "$API_SCOPE"; }`

`if refresh_backend_api; then if [ "$API_SCOPE" = Namespaced ]; then API_JSON="$(kubectl get "$API_RESOURCE" "$API_OBJECT" -n "$TRIDENT_NS" -o json)"; else API_JSON="$(kubectl get "$API_RESOURCE" "$API_OBJECT" -o json)"; fi && jq '{apiVersion,kind,metadata:{name:.metadata.name,uid:.metadata.uid,resourceVersion:.metadata.resourceVersion,generation:.metadata.generation},status:{status:.status.status,message:.status.message,conditions:.status.conditions,observedGeneration:.status.observedGeneration}}' <<<"$API_JSON"; fi`

schema에 없는 `null`을 Online으로 해석하지 않는다. 실제 backendName/SVM/aggregate/storageDriverName/credential reference의 검증은 현재 release의 schema 또는 승인 inventory에서 한다. credential은 Secret 이름·namespace·type만 확인한다.

`SECRET_NAME='PASTE_BACKEND_SECRET_NAME_HERE'; if refresh_backend_api && [ "$API_SCOPE" = Namespaced ] && [ "$(kubectl auth can-i get "secrets/$SECRET_NAME" -n "$TRIDENT_NS")" = yes ]; then kubectl get secret "$SECRET_NAME" -n "$TRIDENT_NS" -o custom-columns='NAME:.metadata.name,NAMESPACE:.metadata.namespace,UID:.metadata.uid,RV:.metadata.resourceVersion,TYPE:.type'; else printf '%s\n' '중단: namespaced API relation 또는 exact Secret metadata RBAC gate 실패' >&2; fi`

Secret metadata 조회 성공은 credential 값·ONTAP role·유효성을 보장하지 않는다. `data`, `stringData`, token, password, certificate는 출력하지 않는다.

### 3. controller evidence

`CTRL_POD='PASTE_BACKEND_CONTROLLER_POD_HERE'; CTRL_CONTAINER='PASTE_BACKEND_CONTROLLER_CONTAINER_HERE'; START_INPUT='PASTE_BACKEND_START_RFC3339_HERE'; END_INPUT='PASTE_BACKEND_END_RFC3339_HERE'`

`refresh_controller(){ unset OWNER_READY CONTAINER_READY NODE_READY TIME_READY ARGUMENT_READY SELECTION_READY AUTH_READY EVIDENCE_READY CTRL_UID CTRL_RV CTRL_NODE CTRL_CONTAINER_ID START_RFC3339 END_RFC3339 COLLECTED_AT; OWNER_READY=false; CONTAINER_READY=false; NODE_READY=false; TIME_READY=false; ARGUMENT_READY=false; SELECTION_READY=false; local j se ee; j="$(kubectl get pod "$CTRL_POD" -n "$TRIDENT_NS" -o json)" || return 1; jq -e --arg c "$CTRL_CONTAINER" 'any(.spec.containers[]?; .name==$c)' <<<"$j" >/dev/null || return 1; CTRL_UID="$(jq -r '.metadata.uid' <<<"$j")"; CTRL_RV="$(jq -r '.metadata.resourceVersion' <<<"$j")"; CTRL_NODE="$(jq -r '.spec.nodeName // empty' <<<"$j")"; CTRL_CONTAINER_ID="$(jq -r --arg c "$CTRL_CONTAINER" '[.status.containerStatuses[]? | select(.name==$c)][0].containerID // empty' <<<"$j")"; [ -n "$CTRL_CONTAINER_ID" ] || return 1; se="$(date -u -d "$START_INPUT" +%s 2>/dev/null)" || return 1; ee="$(date -u -d "$END_INPUT" +%s 2>/dev/null)" || return 1; START_RFC3339="$(date -u -d "@$se" '+%Y-%m-%dT%H:%M:%SZ')"; END_RFC3339="$(date -u -d "@$ee" '+%Y-%m-%dT%H:%M:%SZ')"; [ "$START_RFC3339" = "$START_INPUT" ] && [ "$END_RFC3339" = "$END_INPUT" ] && [ "$se" -lt "$ee" ] || return 1; COLLECTED_AT="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; OWNER_READY=true; CONTAINER_READY=true; NODE_READY=true; TIME_READY=true; ARGUMENT_READY=true; SELECTION_READY=true; export CTRL_UID CTRL_RV CTRL_NODE CTRL_CONTAINER_ID START_RFC3339 END_RFC3339 COLLECTED_AT; }`

위 함수의 시간 입력은 다음 exact gate까지 통과해야 한다. 입력 형식이 다르면 `TIME_READY`를 폐기한다.

`validate_controller_owner_time(){ unset OWNER_READY TIME_READY CTRL_OWNER_KIND CTRL_OWNER_NAME CTRL_OWNER_UID; OWNER_READY=false; TIME_READY=false; [ "$SELECTION_READY" = true ] || return 1; [[ "$START_INPUT" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] && [[ "$END_INPUT" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] || return 1; local p ref owner; p="$(kubectl get pod "$CTRL_POD" -n "$TRIDENT_NS" -o json)" || return 1; [ "$(jq -r '.metadata.uid' <<<"$p")" = "$CTRL_UID" ] || { printf '%s\n' '중단: controller Pod UID 교체' >&2; return 1; }; ref="$(jq -c '[.metadata.ownerReferences[]? | select(.controller==true)][0] // empty' <<<"$p")"; [ -n "$ref" ] || return 1; CTRL_OWNER_KIND="$(jq -r '.kind' <<<"$ref")"; CTRL_OWNER_NAME="$(jq -r '.name' <<<"$ref")"; CTRL_OWNER_UID="$(jq -r '.uid' <<<"$ref")"; owner="$(kubectl get "$CTRL_OWNER_KIND" "$CTRL_OWNER_NAME" -n "$TRIDENT_NS" -o json)" || return 1; [ "$(jq -r '.metadata.uid' <<<"$owner")" = "$CTRL_OWNER_UID" ] || return 1; OWNER_READY=true; TIME_READY=true; export CTRL_OWNER_KIND CTRL_OWNER_NAME CTRL_OWNER_UID; printf 'OWNER_READY=true owner=%s/%s/%s TIME_READY=true start=%s end=%s\n' "$CTRL_OWNER_KIND" "$CTRL_OWNER_NAME" "$CTRL_OWNER_UID" "$START_RFC3339" "$END_RFC3339"; }`

`refresh_auth(){ AUTH_READY=false; [ "$(kubectl auth can-i get "storageclasses.storage.k8s.io/$SC")" = yes ] && [ "$(kubectl auth can-i get "pods/$CTRL_POD" -n "$TRIDENT_NS")" = yes ] && [ "$(kubectl auth can-i get "pods/$CTRL_POD" --subresource=log -n "$TRIDENT_NS")" = yes ] || return 1; AUTH_READY=true; }`

`if refresh_sc && refresh_controller && validate_controller_owner_time && refresh_auth; then kubectl logs "$CTRL_POD" -n "$TRIDENT_NS" -c "$CTRL_CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=300 | awk -v end="$END_RFC3339" '$1 < end' | grep -E -i -C 3 "$SC_RE|storagePool|backend|provision|no suitable|no matching|online|offline|failed|error|timeout"; RC=("${PIPESTATUS[@]}"); if [ "${RC[0]}" -ne 0 ]; then EVIDENCE_READY=false; printf '중단: producer rc=%s\n' "${RC[0]}" >&2; elif [ "${RC[1]}" -ne 0 ]; then EVIDENCE_READY=false; printf '중단: 시간 filter rc=%s\n' "${RC[1]}" >&2; elif [ "${RC[2]}" -eq 1 ]; then EVIDENCE_READY=false; printf '%s\n' '미확정: filter 일치 없음' >&2; elif [ "${RC[2]}" -ne 0 ]; then EVIDENCE_READY=false; printf '중단: 증상 filter rc=%s\n' "${RC[2]}" >&2; else EVIDENCE_READY=true; printf 'EVIDENCE_READY=true sc_uid=%s controller_uid=%s owner_uid=%s containerID=%s collected=%s\n' "$SC_UID" "$CTRL_UID" "$CTRL_OWNER_UID" "$CTRL_CONTAINER_ID" "$COLLECTED_AT"; fi; fi`

`no suitable/no matching backend`는 후보 교집합 또는 live availability 문제다. quota/API 400은 provisioning/resize 제품 경로, NFS mount 오류는 data path 경로다. filter 없음은 정상 증거가 아니며 raw 전체 로그를 자동 출력하지 않는다.

## 원인 확정 기준

- SC 선택 오류: current PVC `storageClassName`이 승인 선언과 다르다.
- driver mapping 오류: current SC provisioner와 bound PV driver가 다르다.
- Backend 교집합 오류: current SC parameter와 current API/inventory의 Online·available Backend 집합이 겹치지 않고 controller 오류가 같은 PVC UID·시각에 일치한다.
- 분산 미확정: 일부 표본 수만 다르고 eligibility, capacity, creation order와 실제 mapping이 확인되지 않았다.

## 정확한 authorization·audit

`auth can-i=yes`는 해당 current context 요청의 authorization check일 뿐 실제 audit subject나 요청 성공을 보장하지 않는다. control-plane owner가 제공한 audit record의 `user.username`, impersonation, `verb`, `objectRef.resource/namespace/name`, `responseStatus.code`, canonical UTC 시각을 exact 대조한다. request/response body와 Secret은 저장하지 않는다.

## 상태 변경 분리

기존 SC/TBC/Backend 수정·삭제, PVC 재생성, 신규 manifest apply 명령을 이 런북에 두지 않는다. 별도 변경은 fresh SC/API/PVC/PV/controller identity·evidence, exact RBAC/audit, storage·Trident·workload·data owner 승인, 변경 창, 연결된 PVC/PV/volume 수와 quorum, 신규 provisioning 멱등성·중복 volume 방지, 중단 조건, 검증된 rollback manifest와 restore rehearsal을 요구한다. `reclaimPolicy: Delete` 가능성이 있으면 PVC 삭제를 rollback으로 사용하지 않는다.

## 정상화 검증

`NORMALIZATION_READY=false; if refresh_sc; then kubectl get storageclass "$SC" -o json | jq '{name:.metadata.name,uid:.metadata.uid,resourceVersion:.metadata.resourceVersion,provisioner:.provisioner,selectionParameters:{backendType:.parameters.backendType,storagePools:.parameters.storagePools}}'; printf 'StorageClass identity gate passed at=%s; backend mapping과 신규 PVC 기능 gate는 아직 필요\n' "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; fi`

PVC/PV가 있으면 `refresh_claim`, API object가 있으면 `refresh_backend_api`, controller evidence가 필요하면 `refresh_controller`를 다시 실행한다. replacement controller는 이름이 아니라 current workload owner relation으로 다시 식별해 UID/containerID를 갱신한다. 승인 SC→eligible Backend 집합→신규 PVC→PV driver→redacted actual Backend mapping이 일치하고 새 선택 오류가 없으며 실제 mount/read/write가 성공해야 최종 정상화한다. `Bound` 또는 metric 한 번의 성공만으로 닫지 않는다. metric 부재는 정상으로 취급하지 않는다.
