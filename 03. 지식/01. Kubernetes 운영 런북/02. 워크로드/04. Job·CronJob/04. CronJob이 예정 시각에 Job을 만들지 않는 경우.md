# CronJob이 예정 시각에 Job을 만들지 않는 경우

## 입력값과 빠른 수집

실행 경로는 `작업 PC Bash·kubectl → API server → CronJob UID·schedule → CronJob UID를 controller owner로 가진 Job UID → Job owner Pod`다. 최초 입력은 namespace와 CronJob 이름, API 자동값은 object identity·저장 schedule·status·owner Job, 계산 후보는 승인된 parser가 낸 기대 시각, 운영자 선택값은 parser evidence·관측 창·변경 승인이다. 작업 PC의 local timezone으로 schedule을 다시 계산하지 않는다.

**도구 확인**

`TOOLS_READY=false; MISSING=''; for T in kubectl jq date sha256sum cut; do command -v "$T" >/dev/null 2>&1 || MISSING="$MISSING $T"; done; if [ -n "${BASH_VERSION:-}" ] && [ -z "$MISSING" ]; then TOOLS_READY=true; printf '%s\n' 'TOOLS_READY=true'; else printf '중단: Bash 또는 도구 없음:%s\n' "$MISSING" >&2; fi`

재실행, 조회 실패 또는 외부 변경 뒤에는 위 명령부터 실행해 UID, resourceVersion, schedule·시간 계산, owner Job과 모든 READY를 폐기한다.

**CronJob identity·자동값 등록**

**현재 CronJob lifecycle 재검증 함수**

`fresh_cron(){ local d u digest; d="$(kubectl get cronjob "$CRONJOB" -n "$NS" -o json)" || { CRON_READY=false; WINDOW_READY=false; JOBS_READY=false; CHANGE_READY=false; REPLACEMENT_READY=false; NORMAL_READY=false; return 1; }; u="$(jq -r '.metadata.uid // empty' <<<"$d")"; digest="$(jq -cS '.spec' <<<"$d" | sha256sum | cut -d' ' -f1)"; if [ "$CRON_READY" != true ] || [ "$u" != "$CRON_UID" ] || [ "$digest" != "$CRON_SPEC_DIGEST" ]; then unset CRON_JSON JOBS_JSON; CRON_READY=false; WINDOW_READY=false; JOBS_READY=false; CHANGE_READY=false; REPLACEMENT_READY=false; NORMAL_READY=false; printf '%s\n' '중단: CronJob lifecycle 또는 spec이 바뀌었다. 처음부터 재등록한다.' >&2; return 1; fi; CRON_JSON="$d"; CRON_RV="$(jq -r '.metadata.resourceVersion' <<<"$d")"; return 0; }`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 승인된 schedule parser의 기대 시각이 지났는데 `lastScheduleTime` 또는 현재 CronJob UID owner Job이 없는 경우 |
| 적용 | 저장 schedule·timezone basis·기대/관측 시각과 CronJob UID를 함께 보존할 수 있는 경우 |
| 제외 | `Forbid`·`Replace` 동시성은 [[05. CronJob의 concurrencyPolicy 때문에 실행이 건너뛰거나 교체되는 경우]], 생성된 Job의 실패는 [[01. Job completion이 수렴하지 않는 경우]]로 이동한다. |

검색 문자열: `schedule`, `timeZone`, `lastScheduleTime`, `startingDeadlineSeconds`, `suspend`, `UnknownTimeZone`, `Too many missed start time`, `FailedCreate`, `AlreadyExists`, `Forbidden`, `timeout`.

## schedule 계산·증거 창 등록

`EXPECTED_RFC3339='PASTE_EXPECTED_SCHEDULE_RFC3339_HERE'; OBSERVED_RFC3339='PASTE_OBSERVED_RFC3339_HERE'; SCHEDULE_EVIDENCE_ID='PASTE_SCHEDULE_EVIDENCE_ID_HERE'; CONTROLLER_TIME_BASIS='PASTE_CONTROLLER_TIMEZONE_OR_IANA_HERE'; WINDOW_READY=false; JOBS_READY=false; CHANGE_READY=false; REPLACEMENT_READY=false; NORMAL_READY=false; if [ "$CRON_READY" != true ] || ! fresh_cron; then printf '%s\n' '중단: 최신 CRON_READY가 필요하다.' >&2; elif ! [[ "$EXPECTED_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ && "$OBSERVED_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] || [ "$(date -u -d "$EXPECTED_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" != "$EXPECTED_RFC3339" ] || [ "$(date -u -d "$OBSERVED_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" != "$OBSERVED_RFC3339" ] || [ "$(date -u -d "$EXPECTED_RFC3339" +%s)" -ge "$(date -u -d "$OBSERVED_RFC3339" +%s)" ] || [ -z "$SCHEDULE_EVIDENCE_ID" ] || [ -z "$CONTROLLER_TIME_BASIS" ]; then printf '%s\n' '중단: canonical UTC expected<observed와 승인 parser evidence가 필요하다.' >&2; elif [ -n "$TIME_ZONE" ] && [ "$CONTROLLER_TIME_BASIS" != "$TIME_ZONE" ]; then printf '중단: 저장 timeZone과 계산 basis가 다름 stored=%s basis=%s\n' "$TIME_ZONE" "$CONTROLLER_TIME_BASIS" >&2; else WINDOW_READY=true; printf 'WINDOW_READY=true expected=%s observed=%s evidence=%s basis=%s delaySeconds=%s deadline=%s\n' "$EXPECTED_RFC3339" "$OBSERVED_RFC3339" "$SCHEDULE_EVIDENCE_ID" "$CONTROLLER_TIME_BASIS" "$(( $(date -u -d "$OBSERVED_RFC3339" +%s)-$(date -u -d "$EXPECTED_RFC3339" +%s) ))" "${DEADLINE_SECONDS:--}"; fi`

`.spec.timeZone`은 Kubernetes 1.26의 `CronJobTimeZone` feature gate·API server/controller-manager version skew가 확인된 경우에만 controller 적용을 확정한다. 값이 비면 승인된 controller timezone을 사용하며 작업 PC timezone을 대신 넣지 않는다. DST 경계와 macro schedule은 승인 parser evidence가 없으면 기대 시각을 확정하지 않는다.

**현재 CronJob owner Job 등록**

`JOBS_READY=false; CHANGE_READY=false; REPLACEMENT_READY=false; NORMAL_READY=false; unset JOBS_JSON; if [ "$WINDOW_READY" != true ] || ! fresh_cron; then printf '%s\n' '중단: 최신 WINDOW_READY가 필요하다.' >&2; elif A="$(kubectl get jobs -n "$NS" -o json)" && J="$(jq -c --arg uid "$CRON_UID" '[.items[] | select(any(.metadata.ownerReferences[]?; .controller==true and .kind=="CronJob" and .uid==$uid))] | sort_by(.metadata.creationTimestamp)' <<<"$A")"; then JOBS_JSON="$J"; JOBS_READY=true; jq -r '.[] | "=== Job \(.metadata.name) ===\nuid=\(.metadata.uid) rv=\(.metadata.resourceVersion) created=\(.metadata.creationTimestamp) owner=" + ([.metadata.ownerReferences[]? | select(.controller==true) | "\(.kind)/\(.name) uid=\(.uid)"] | join(",")) + "\nactive=\(.status.active // 0) succeeded=\(.status.succeeded // 0) failed=\(.status.failed // 0) completion=\(.status.completionTime // "-")"' <<<"$JOBS_JSON"; printf 'JOBS_READY=true ownerJobCount=%s observed=%s\n' "$(jq 'length' <<<"$JOBS_JSON")" "$OBSERVED_RFC3339"; else printf '%s\n' '중단: Job API producer 실패.' >&2; fi`

빈 배열은 현재 owner Job이 없다는 직접 관측이며 create 실패를 단독 확정하지 않는다. 이름·예상 suffix·creation time만 비슷한 Job은 연결하지 않는다.

| 기대 시각이 deadline 밖 | expected/observed 차이와 deadline | 의도된 skip 또는 controller 지연 | [[#suspend·deadline·timezone 판정\|deadline 판정]] |

## suspend·deadline·timezone 판정

`SUSPEND=true`이면 subsequent execution이 생성되지 않는 것은 spec에 따른 동작이다. 해제 시 missed execution이 생성될 수 있으므로 임의로 patch하지 않는다. deadline이 있으면 `observed-expected`가 이를 넘었는지 계산하되, controller가 실제 reconcile한 시각은 Event·controller evidence로 별도 확인한다. 10초보다 작은 deadline은 약 10초 reconcile 간격으로 누락될 수 있다.

`lastScheduleTime`은 마지막 schedule 시각, `lastSuccessfulTime`은 마지막 성공 Job 완료 시각이다. 둘을 대체하지 않는다. `Forbid` active Job 때문에 건너뛴 경우는 동시성 런북으로 이동한다. missed schedule 100회 초과, controller clock skew와 hosted control-plane 로그 source는 platform owner가 확인한다.

## CronJob UID 제한 Event와 create 경로

`if [ "$JOBS_READY" != true ] || ! fresh_cron; then printf '%s\n' '중단: 최신 JOBS_READY가 필요하다.' >&2; elif ! kubectl get events -n "$NS" --field-selector "involvedObject.kind=CronJob,involvedObject.name=$CRONJOB,involvedObject.uid=$CRON_UID" --sort-by=.metadata.creationTimestamp -o custom-columns='CREATED:.metadata.creationTimestamp,EVENT_TIME:.eventTime,SERIES_LAST:.series.lastObservedTime,FIRST:.firstTimestamp,LAST:.lastTimestamp,TYPE:.type,REASON:.reason,COUNT:.count,MESSAGE:.message'; then printf '%s\n' '중단: Event producer 실패. 빈 결과와 다르다.' >&2; fi`

Event의 채워진 시각이 `EXPECTED_RFC3339..OBSERVED_RFC3339`에 있는지 대조한다. `FailedCreate`, `AlreadyExists`, `Forbidden`, admission 오류, API timeout은 message와 같은 시각의 승인된 controller evidence가 맞을 때만 해당 계층으로 이관한다. 작업자 `kubectl auth can-i` 결과는 controller service account의 실제 create 권한을 증명하지 않는다. Event가 비면 TTL·집계·권한·controller 재시작을 열어 두며 성공으로 해석하지 않는다.

control-plane host·unit·machine identity가 이 문서에서 자동 확정되지 않으므로 임의 SSH나 `journalctl -u kube-controller-manager` 명령을 실행하지 않는다. platform owner에게 CronJob UID, 기대/관측 시각, schedule evidence ID와 비민감 오류 문자열만 전달한다.

## Job이 생성된 뒤의 경계

JOBS 출력에서 기대 시각 이후 단일 Job이 있더라도 owner kind/name/UID와 Job UID·creation time을 보존한다. 생성됐다는 사실은 Pod 생성, Job completion 또는 외부 업무 성공을 보장하지 않는다. Job은 [[01. Job completion이 수렴하지 않는 경우]], Indexed Job은 [[03. Indexed Job의 completion index가 수렴하지 않는 경우]]로 새 identity를 전달한다.

## 상태 변경 경계

이 문서는 schedule·timezone·deadline 변경, `suspend` 전환, CronJob 삭제·재생성, 수동 `kubectl create job` 명령을 제공하지 않는다. 별도 절차는 실행 직전에 CronJob UID·resourceVersion·spec digest·저장 schedule, 기대/관측 시각과 parser evidence, current active owner Job, concurrencyPolicy, 누락 입력 범위, 외부 idempotency·부분 결과·중복 write, 승인 ID·창·rollback/보상 절차를 직접 재검증해야 한다.

**승인된 외부 변경 뒤 새 owner Job 후보 등록**

`APPROVAL_ID='PASTE_APPROVAL_ID_HERE'; WINDOW_ID='PASTE_WINDOW_ID_HERE'; CHANGE_RFC3339='PASTE_CHANGE_RFC3339_HERE'; CHANGE_READY=false; REPLACEMENT_READY=false; NORMAL_READY=false; if [ "$JOBS_READY" != true ] || ! fresh_cron; then printf '%s\n' '중단: 최신 CronJob·Job gate가 필요하다.' >&2; elif ! [[ "$CHANGE_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] || [ "$(date -u -d "$CHANGE_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" != "$CHANGE_RFC3339" ] || [ -z "$APPROVAL_ID" ] || [ -z "$WINDOW_ID" ]; then printf '%s\n' '중단: canonical UTC·승인·변경 창이 필요하다.' >&2; else CHANGE_READY=true; printf 'CHANGE_READY=true cronUID=%s cronRV=%s approval=%s window=%s change=%s\n' "$CRON_UID" "$CRON_RV" "$APPROVAL_ID" "$WINDOW_ID" "$CHANGE_RFC3339"; fi`

위 gate는 mutation 승인이 아니라 외부 승인 기록 등록이다. 실제 변경 전에 spec·active Job·업무 결과가 바뀌면 폐기한다.

`REPLACEMENT_READY=false; NORMAL_READY=false; unset NEW_JOB NEW_JOB_UID NEW_JOB_RV NEW_JOB_CREATED; if [ "$CHANGE_READY" != true ] || ! fresh_cron; then printf '%s\n' '중단: 최신 CHANGE_READY가 필요하다.' >&2; elif A="$(kubectl get jobs -n "$NS" -o json)" && C="$(jq -c --arg uid "$CRON_UID" --arg t "$CHANGE_RFC3339" '[.items[] | select(.metadata.creationTimestamp>$t and any(.metadata.ownerReferences[]?; .controller==true and .kind=="CronJob" and .uid==$uid))]' <<<"$A")" && [ "$(jq 'length' <<<"$C")" -eq 1 ]; then NEW_JOB="$(jq -r '.[0].metadata.name' <<<"$C")"; NEW_JOB_UID="$(jq -r '.[0].metadata.uid' <<<"$C")"; NEW_JOB_RV="$(jq -r '.[0].metadata.resourceVersion' <<<"$C")"; NEW_JOB_CREATED="$(jq -r '.[0].metadata.creationTimestamp' <<<"$C")"; REPLACEMENT_READY=true; printf 'REPLACEMENT_READY=true job=%s uid=%s rv=%s created=%s cronUID=%s\n' "$NEW_JOB" "$NEW_JOB_UID" "$NEW_JOB_RV" "$NEW_JOB_CREATED" "$CRON_UID"; else printf '%s\n' '중단: 변경 뒤 current CronJob UID owner Job 후보가 정확히 하나가 아니다.' >&2; fi`

## 정상화와 역순 검증

`NORMAL_READY=false; if [ "$REPLACEMENT_READY" != true ] || ! fresh_cron; then printf '%s\n' '중단: 최신 replacement·CronJob gate가 필요하다.' >&2; elif D="$(kubectl get job "$NEW_JOB" -n "$NS" -o json)" && jq -e --arg j "$NEW_JOB_UID" --arg c "$CRON_UID" '.metadata.uid==$j and any(.metadata.ownerReferences[]?; .controller==true and .kind=="CronJob" and .uid==$c)' <<<"$D" >/dev/null; then jq -r '"job=\(.metadata.name) uid=\(.metadata.uid) rv=\(.metadata.resourceVersion) created=\(.metadata.creationTimestamp) active=\(.status.active // 0) succeeded=\(.status.succeeded // 0) failed=\(.status.failed // 0) completion=\(.status.completionTime // "-")", (.status.conditions[]? | "condition=\(.type) status=\(.status) reason=\(.reason // "-") transition=\(.lastTransitionTime // "-")")' <<<"$D"; NORMAL_READY=true; else REPLACEMENT_READY=false; printf '%s\n' '중단: 새 Job identity가 바뀌었다.' >&2; fi`

정상화는 CronJob UID·spec·다음 schedule 계산, 새 Job UID·owner·creation, 새 Job owner Pod UID·container 결과, Warning·동일 create 실패 중단을 확인한다. 이어 실제 commit·ack·checksum·watermark와 누락/중복 부재를 관찰 창 동안 확인한다. `lastScheduleTime` 갱신이나 Job 생성만으로 정상화하지 않는다.

**PromQL 완성본 생성**

`if [ "$CRON_READY" != true ] || ! fresh_cron; then printf '%s\n' '중단: 최신 CRON_READY가 필요하다.' >&2; else printf 'time()-kube_cronjob_status_last_schedule_time{namespace=%s,cronjob=%s}\n' "$(jq -Rn --arg v "$NS" '$v')" "$(jq -Rn --arg v "$CRONJOB" '$v')"; fi`

metric·label 미지원과 빈 결과를 정상으로 해석하지 않는다. 이 쿼리는 CronJob UID, timezone, expected schedule, create failure와 외부 업무 결과를 증명하지 못한다.

보존 대상은 CronJob·Job·Pod UID/resourceVersion/owner/creation, spec digest, 저장 schedule·timezone·suspend·deadline·policy, expected/observed/Event 시각, parser evidence와 비민감 외부 결과다. Secret·token·개인키·전체 YAML·민감 Event 원문은 저장하지 않는다.
