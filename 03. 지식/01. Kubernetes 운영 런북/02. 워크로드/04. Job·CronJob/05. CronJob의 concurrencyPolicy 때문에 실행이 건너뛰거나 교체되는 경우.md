# CronJob의 concurrencyPolicy 때문에 실행이 건너뛰거나 교체되는 경우

## 입력값과 빠른 수집

실행 위치는 승인된 `kubectl` context가 있는 작업 PC 또는 bastion의 **같은 Bash**다. CronJob controller와 API server를 거쳐 Job 객체를 조회한다. `Running` Job이나 `status.active` 참조 하나만으로 실제 업무 입력의 처리 여부를 확정하지 않는다.

| 구분 | 값 | 등록·검증 |
|---|---|---|
| 최초 입력 | `NS`, `CJ` | namespace와 CronJob exact name을 한 번 입력한다. |
| API 자동값 | `CJ_UID`, `CJ_RV`, `CJ_GENERATION`, `CJ_POLICY`, `CJ_SCHEDULE` | 현재 CronJob에서 등록한다. UID가 바뀌면 전부 폐기한다. |
| 계산 후보 | owner UID가 일치하는 Job 집합과 schedule 시간 창 | API 결과와 승인된 schedule 계산으로 만들며 자동 원인 확정은 하지 않는다. |
| 운영자 선택 | `WINDOW_START`, `WINDOW_END` | 조사할 UTC 구간을 canonical RFC3339로 선택한다. |

**도구 확인**

`TOOLS_READY=false; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: Bash에서 실행한다.' >&2; else MISSING=''; for T in kubectl jq date sha256sum cut; do command -v "$T" >/dev/null 2>&1 || MISSING="$MISSING $T"; done; if [ -z "$MISSING" ]; then TOOLS_READY=true; printf '%s\n' 'TOOLS_READY=true'; else printf '중단: 없는 도구=%s\n' "$MISSING" >&2; fi; fi`

**최초 입력과 stale 상태 폐기**

`unset INPUT_READY AUTO_READY WINDOW_READY SNAPSHOT_READY MUTATION_READY REPLACEMENT_READY NORMALIZED_READY CJ_UID CJ_RV CJ_GENERATION CJ_POLICY CJ_SCHEDULE CJ_CREATED WINDOW_START WINDOW_END SNAPSHOT_AT SNAPSHOT_JSON APPROVAL_ID EVIDENCE_ID CHANGE_START CHANGE_END PRE_SPEC_DIGEST REPLACEMENT_JOB REPLACEMENT_JOB_UID REPLACEMENT_JOB_RV; NS='PASTE_NAMESPACE_HERE'; CJ='PASTE_CRONJOB_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: TOOLS_READY가 아니다.' >&2; elif [ -z "$NS" ] || [ -z "$CJ" ]; then printf '%s\n' '중단: NS와 CJ가 비어 있다.' >&2; elif CJ_INPUT_JSON="$(kubectl get cronjob "$CJ" -n "$NS" -o json)"; then INPUT_UID="$(jq -r '.metadata.uid // empty' <<<"$CJ_INPUT_JSON")"; if [ -n "$INPUT_UID" ]; then INPUT_READY=true; printf 'INPUT_READY=true namespace=%s cronjob=%s uid=%s\n' "$NS" "$CJ" "$INPUT_UID"; else printf '%s\n' '중단: UID가 비어 있다.' >&2; fi; else printf '%s\n' '중단: CronJob exact-name 조회 실패' >&2; fi`

**API identity 자동 등록**

`unset AUTO_READY WINDOW_READY SNAPSHOT_READY MUTATION_READY REPLACEMENT_READY NORMALIZED_READY CJ_UID CJ_RV CJ_GENERATION CJ_POLICY CJ_SCHEDULE CJ_CREATED WINDOW_START WINDOW_END SNAPSHOT_AT SNAPSHOT_JSON APPROVAL_ID EVIDENCE_ID CHANGE_START CHANGE_END PRE_SPEC_DIGEST REPLACEMENT_JOB REPLACEMENT_JOB_UID REPLACEMENT_JOB_RV; AUTO_READY=false; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif CJ_JSON="$(kubectl get cronjob "$CJ" -n "$NS" -o json)"; then CJ_UID="$(jq -r '.metadata.uid // empty' <<<"$CJ_JSON")"; CJ_RV="$(jq -r '.metadata.resourceVersion // empty' <<<"$CJ_JSON")"; CJ_GENERATION="$(jq -r '.metadata.generation // empty' <<<"$CJ_JSON")"; CJ_POLICY="$(jq -r '.spec.concurrencyPolicy // empty' <<<"$CJ_JSON")"; CJ_SCHEDULE="$(jq -r '.spec.schedule // empty' <<<"$CJ_JSON")"; CJ_CREATED="$(jq -r '.metadata.creationTimestamp // empty' <<<"$CJ_JSON")"; if [ -n "$CJ_UID" ] && [ -n "$CJ_RV" ] && [ -n "$CJ_GENERATION" ] && [[ "$CJ_POLICY" =~ ^(Allow|Forbid|Replace)$ ]] && [ -n "$CJ_SCHEDULE" ]; then AUTO_READY=true; printf 'AUTO_READY=true\nUID=%s\nresourceVersion=%s\ngeneration=%s\npolicy=%s\nschedule=%s\ncreated=%s\n' "$CJ_UID" "$CJ_RV" "$CJ_GENERATION" "$CJ_POLICY" "$CJ_SCHEDULE" "$CJ_CREATED"; else unset CJ_UID CJ_RV CJ_GENERATION CJ_POLICY CJ_SCHEDULE CJ_CREATED; printf '%s\n' '중단: 필수 자동값 등록 실패' >&2; fi; else printf '%s\n' '중단: 자동 등록 API 조회 실패' >&2; fi`

재등록 전에는 UID·resourceVersion·owner 관계·시간 창과 모든 downstream `READY`를 폐기한다. 이후 모든 조회는 현재 CronJob UID를 API에서 다시 확인한다. 같은 이름의 재생성 객체에는 이전 Job·Event·시간 증거를 연결하지 않는다.

**운영자 시간 창 선택**

`WINDOW_START='PASTE_WINDOW_START_RFC3339_HERE'; WINDOW_END='PASTE_WINDOW_END_RFC3339_HERE'`

**시간 창 검증**

`WINDOW_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif [[ ! "$WINDOW_START" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] || [[ ! "$WINDOW_END" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then printf '%s\n' '중단: canonical UTC RFC3339가 아니다.' >&2; elif ! START_EPOCH="$(date -u -d "$WINDOW_START" +%s)" || ! END_EPOCH="$(date -u -d "$WINDOW_END" +%s)" || [ "$(date -u -d "@$START_EPOCH" +%Y-%m-%dT%H:%M:%SZ)" != "$WINDOW_START" ] || [ "$(date -u -d "@$END_EPOCH" +%Y-%m-%dT%H:%M:%SZ)" != "$WINDOW_END" ] || [ "$START_EPOCH" -ge "$END_EPOCH" ]; then printf '%s\n' '중단: 시간 round-trip 또는 start<end 검증 실패' >&2; else WINDOW_READY=true; printf 'WINDOW_READY=true start=%s end=%s\n' "$WINDOW_START" "$WINDOW_END"; fi`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 예정 실행이 겹친 시각에 Job이 건너뛰었거나 기존 Job이 종료되고 새 Job이 생긴 것으로 보인다. |
| 적용 | 현재 CronJob UID·policy와 child Job owner UID·생성/시작/완료/삭제 시각을 같은 창에서 대조할 수 있다. |
| 제외 | schedule 자체가 계산되지 않으면 [[04. CronJob이 예정 시각에 Job을 만들지 않는 경우]], Job completion은 [[01. Job completion이 수렴하지 않는 경우]]로 이동한다. |

검색 문자열: `concurrencyPolicy`, `JobAlreadyActive`, `SuccessfulCreate`, `SuccessfulDelete`, `FailedCreate`, `FailedDelete`, `lastScheduleTime`, `lastSuccessfulTime`.

## 현재 snapshot 등록

아래 명령은 producer인 CronJob/Job API 실패, `jq` filter 오류, owner UID 필터 결과 0건을 서로 다르게 보고한다. 빈 Job 집합은 정상으로 바꾸지 않는다.

`unset SNAPSHOT_READY SNAPSHOT_JSON SNAPSHOT_AT; SNAPSHOT_READY=false; if [ "$AUTO_READY" != true ] || [ "$WINDOW_READY" != true ]; then printf '%s\n' '중단: AUTO_READY와 WINDOW_READY가 필요하다.' >&2; elif CUR_CJ="$(kubectl get cronjob "$CJ" -n "$NS" -o json)"; then CUR_UID="$(jq -r '.metadata.uid // empty' <<<"$CUR_CJ")"; if [ "$CUR_UID" != "$CJ_UID" ]; then AUTO_READY=false; WINDOW_READY=false; printf '중단: CronJob UID 변경 old=%s current=%s\n' "$CJ_UID" "$CUR_UID" >&2; elif JOBS_JSON="$(kubectl get jobs -n "$NS" -o json)"; then if ! FILTERED="$(jq -c --arg uid "$CJ_UID" '[.items[] | select(any(.metadata.ownerReferences[]?; .controller==true and .kind=="CronJob" and .uid==$uid)) | {name:.metadata.name,uid:.metadata.uid,rv:.metadata.resourceVersion,owner:[.metadata.ownerReferences[]|select(.controller==true)][0],created:.metadata.creationTimestamp,start:.status.startTime,complete:.status.completionTime,deletion:.metadata.deletionTimestamp,active:(.status.active//0),succeeded:(.status.succeeded//0),failed:(.status.failed//0),conditions:(.status.conditions//[])}]' <<<"$JOBS_JSON")"; then printf '%s\n' '중단: Job filter 오류' >&2; elif [ "$(jq 'length' <<<"$FILTERED")" -eq 0 ]; then printf '%s\n' '중단: 현재 UID의 child Job이 0건이다. API 성공과 대상 없음은 구분한다.' >&2; else SNAPSHOT_AT="$(date -u +%Y-%m-%dT%H:%M:%SZ)"; SNAPSHOT_JSON="$(jq -n --argjson cj "$CUR_CJ" --argjson jobs "$FILTERED" --arg at "$SNAPSHOT_AT" '{observedAt:$at,cronjob:{name:$cj.metadata.name,uid:$cj.metadata.uid,rv:$cj.metadata.resourceVersion,generation:$cj.metadata.generation,policy:$cj.spec.concurrencyPolicy,schedule:$cj.spec.schedule,suspend:$cj.spec.suspend,lastSchedule:$cj.status.lastScheduleTime,lastSuccess:$cj.status.lastSuccessfulTime,active:($cj.status.active//[])},jobs:$jobs}')"; SNAPSHOT_READY=true; jq -r '"SNAPSHOT_READY=true observedAt=\(.observedAt)\nCronJob UID=\(.cronjob.uid) policy=\(.cronjob.policy) active=\([.cronjob.active[]?|"\(.name)/\(.uid)"]|join(","))",(.jobs[]|"=== Job: \(.name) ===\nUID: \(.uid)\nowner: \(.owner.kind)/\(.owner.name)/\(.owner.uid)\ncreated: \(.created) start: \(.start) complete: \(.complete) deletion: \(.deletion)\nactive/succeeded/failed: \(.active)/\(.succeeded)/\(.failed)")' <<<"$SNAPSHOT_JSON"; fi; else printf '%s\n' '중단: Job API producer 실패' >&2; fi; else printf '%s\n' '중단: CronJob API producer 실패' >&2; fi`

## 관측별 진단 경로

| 지금 보이는 것 | 직접 판정 | 다음 행동 |
|---|---|---|
| `Forbid`와 active Job | active 참조 UID가 실제 현재 owner Job UID이고 schedule 시각에 미완료 | skip 후보. 입력이 처리됐다는 뜻은 아니다. |
| `Replace`와 삭제 중 Job·새 Job | 이전 Job deletion이 새 Job creation보다 이르고 둘 다 owner UID 일치 | 교체 후보. 이전 side effect는 취소되지 않는다. |
| `Allow`와 겹친 Job | owner UID가 같은 둘 이상의 Job 실행 시간이 겹침 | 업무 입력 범위·idempotency를 확인한다. |
| active 참조 불일치 | name이 아니라 UID 또는 owner UID가 불일치 | stale status/controller 조정 경로로 이관한다. |

**정책 관계 판정**

`if [ "$SNAPSHOT_READY" != true ]; then printf '%s\n' '중단: 최신 SNAPSHOT_READY가 아니다.' >&2; elif CUR="$(kubectl get cronjob "$CJ" -n "$NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$CUR")" = "$CJ_UID" ]; then jq -r --arg ws "$WINDOW_START" --arg we "$WINDOW_END" '.cronjob as $c | "policy=\($c.policy) window=\($ws)..\($we)",($c.active[]? | "active-ref=\(.name)/\(.uid)"),(.jobs[] | select(.created >= $ws and .created < $we) | "window-job=\(.name) uid=\(.uid) owner=\(.owner.uid) created=\(.created) deletion=\(.deletion)")' <<<"$SNAPSHOT_JSON"; else SNAPSHOT_READY=false; printf '%s\n' '중단: 최신 CronJob identity 재검사 실패' >&2; fi`

- `Forbid`: `status.active[*].uid == Job.metadata.uid`, Job controller owner UID가 `CJ_UID`, schedule 시각에 terminal condition과 deletion이 없고 `JobAlreadyActive`가 같은 lifecycle에 있어야 skip으로 확정한다.
- `Replace`: 이전 Job deletionTimestamp, `SuccessfulDelete`/`FailedDelete`, 새 Job UID·creationTimestamp가 window 안에서 순서대로 연결돼야 한다. 새 Job 성공은 이전 입력의 commit·ack·watermark 취소를 보장하지 않는다.
- `Allow`: 각 Job UID별 입력 범위와 idempotency key의 **비식별 요약**을 업무 시스템에서 확인한다. Secret·token·개인정보·원문 payload를 출력하지 않는다.
- Event가 필요하면 현재 요청 identity, CronJob UID와 시간 창을 보존해 audit/controller owner에게 요청한다. Event TTL 또는 RBAC 실패를 Event 없음으로 해석하지 않는다.

## 변경 전 안전 gate

진단과 변경은 분리한다. policy·suspend 변경, Job 삭제·수동 생성은 이 런북에서 실행하지 않는다. 승인된 GitOps/선언 경로로 변경하기 직전에 다음 값을 등록한다.

`APPROVAL_ID='PASTE_APPROVAL_ID_HERE'; EVIDENCE_ID='PASTE_EVIDENCE_ID_HERE'; CHANGE_START='PASTE_CHANGE_START_RFC3339_HERE'; CHANGE_END='PASTE_CHANGE_END_RFC3339_HERE'`

`unset MUTATION_READY PRE_SPEC_DIGEST REPLACEMENT_READY NORMALIZED_READY; MUTATION_READY=false; if [ "$SNAPSHOT_READY" != true ]; then printf '%s\n' '중단: 최신 SNAPSHOT_READY가 아니다.' >&2; elif [ -z "$APPROVAL_ID" ] || [ -z "$EVIDENCE_ID" ]; then printf '%s\n' '중단: 승인과 비식별 evidence가 필요하다.' >&2; elif [[ ! "$CHANGE_START" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] || [[ ! "$CHANGE_END" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then printf '%s\n' '중단: 변경 창 형식 오류' >&2; elif ! CS="$(date -u -d "$CHANGE_START" +%s)" || ! CE="$(date -u -d "$CHANGE_END" +%s)" || [ "$(date -u -d "@$CS" +%Y-%m-%dT%H:%M:%SZ)" != "$CHANGE_START" ] || [ "$(date -u -d "@$CE" +%Y-%m-%dT%H:%M:%SZ)" != "$CHANGE_END" ] || [ "$CS" -ge "$CE" ]; then printf '%s\n' '중단: 변경 창 round-trip/start<end 실패' >&2; elif CUR="$(kubectl get cronjob "$CJ" -n "$NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$CUR")" = "$CJ_UID" ] && [ "$(jq -r '.metadata.resourceVersion' <<<"$CUR")" = "$CJ_RV" ]; then PRE_SPEC_DIGEST="$(jq -S '.spec' <<<"$CUR" | sha256sum | cut -d' ' -f1)"; MUTATION_READY=true; printf 'MUTATION_READY=true uid=%s rv=%s generation=%s digest=%s approval=%s evidence=%s window=%s..%s\n' "$CJ_UID" "$CJ_RV" "$CJ_GENERATION" "$PRE_SPEC_DIGEST" "$APPROVAL_ID" "$EVIDENCE_ID" "$CHANGE_START" "$CHANGE_END"; else SNAPSHOT_READY=false; printf '%s\n' '중단: UID/resourceVersion drift. 재등록한다.' >&2; fi`

변경 기록에는 새 policy/spec digest, 입력 watermark, 외부 호출·중복·부분 처리, quorum 해당 여부, 멱등성, 영향 범위와 rollback 선언을 적는다. rollback도 현재 UID·새 resourceVersion·현재 spec digest·승인·window·업무 보상 가능성을 다시 검사한 뒤 승인된 선언 경로에서 수행한다. Kubernetes rollback은 이미 발생한 side effect를 되돌리지 않는다.

## replacement 재등록과 정상화

변경 후 기존 Job 이름·UID와 snapshot을 버린다. 현재 CronJob UID가 같고, 현재 owner UID가 일치하며, change window 안에 생성된 non-deleting Job 후보가 **정확히 하나**일 때만 replacement로 등록한다. 0건은 아직 생성되지 않음, 복수는 범위가 넓거나 여러 schedule이 포함됨이므로 중단한다.

`unset REPLACEMENT_READY NORMALIZED_READY REPLACEMENT_JOB REPLACEMENT_JOB_UID REPLACEMENT_JOB_RV; REPLACEMENT_READY=false; SNAPSHOT_READY=false; if [ "$MUTATION_READY" != true ]; then printf '%s\n' '중단: MUTATION_READY가 아니다.' >&2; elif CUR="$(kubectl get cronjob "$CJ" -n "$NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$CUR")" = "$CJ_UID" ] && JOBS="$(kubectl get jobs -n "$NS" -o json)"; then if CANDIDATES="$(jq -c --arg uid "$CJ_UID" --arg s "$CHANGE_START" --arg e "$CHANGE_END" '[.items[] | select(any(.metadata.ownerReferences[]?; .controller==true and .kind=="CronJob" and .uid==$uid)) | select(.metadata.creationTimestamp >= $s and .metadata.creationTimestamp < $e and .metadata.deletionTimestamp==null)]' <<<"$JOBS")"; then COUNT="$(jq 'length' <<<"$CANDIDATES")"; if [ "$COUNT" -eq 1 ]; then REPLACEMENT_JOB="$(jq -r '.[0].metadata.name' <<<"$CANDIDATES")"; REPLACEMENT_JOB_UID="$(jq -r '.[0].metadata.uid' <<<"$CANDIDATES")"; REPLACEMENT_JOB_RV="$(jq -r '.[0].metadata.resourceVersion' <<<"$CANDIDATES")"; REPLACEMENT_READY=true; printf 'REPLACEMENT_READY=true job=%s uid=%s rv=%s owner=%s\n' "$REPLACEMENT_JOB" "$REPLACEMENT_JOB_UID" "$REPLACEMENT_JOB_RV" "$CJ_UID"; else printf '중단: replacement 후보 수=%s\n' "$COUNT" >&2; fi; else printf '%s\n' '중단: replacement filter 오류' >&2; fi; else printf '%s\n' '중단: replacement API/identity 검사 실패' >&2; fi`

`NORMALIZED_READY=false; if [ "$REPLACEMENT_READY" != true ]; then printf '%s\n' '중단: 최신 REPLACEMENT_READY가 아니다.' >&2; elif CUR_CJ="$(kubectl get cronjob "$CJ" -n "$NS" -o json)" && CUR_JOB="$(kubectl get job "$REPLACEMENT_JOB" -n "$NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$CUR_CJ")" = "$CJ_UID" ] && [ "$(jq -r '.metadata.uid' <<<"$CUR_JOB")" = "$REPLACEMENT_JOB_UID" ] && [ "$(jq -r '[.metadata.ownerReferences[]?|select(.controller==true and .uid==$uid)]|length' --arg uid "$CJ_UID" <<<"$CUR_JOB")" -eq 1 ]; then TERMINAL="$(jq -r '[.status.conditions[]?|select((.type=="Complete" or .type=="Failed") and .status=="True")]|length' <<<"$CUR_JOB")"; printf 'replacement=%s uid=%s active=%s succeeded=%s failed=%s terminalConditions=%s\n' "$REPLACEMENT_JOB" "$REPLACEMENT_JOB_UID" "$(jq -r '.status.active//0' <<<"$CUR_JOB")" "$(jq -r '.status.succeeded//0' <<<"$CUR_JOB")" "$(jq -r '.status.failed//0' <<<"$CUR_JOB")" "$TERMINAL"; NORMALIZED_READY=true; printf '%s\n' 'NORMALIZED_READY=true API identity/owner 확인 완료; 업무 기능 gate는 별도 확인'; else REPLACEMENT_READY=false; printf '%s\n' '중단: replacement UID/owner 최신 검사 실패' >&2; fi`

최종 정상화는 현재 policy·generation, active UID와 Job owner UID, schedule/creation/start/completion 순서, Warning 재발 부재를 확인한 뒤 업무 입력 범위·commit·ack·watermark·산출물과 실제 기능을 승인된 비민감 절차로 확인해야 한다. `NORMALIZED_READY=true`만으로 업무 성공을 선언하지 않는다.

## Prometheus 보조 관측

kube-state-metrics metric과 label이 실제 존재할 때만 현재 identity로 완성 쿼리를 만든다. UID가 없는 CronJob metric은 API UID 증거를 대체하지 않으며 빈 결과는 성공이 아니다.

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: 최신 AUTO_READY가 아니다.' >&2; elif CUR="$(kubectl get cronjob "$CJ" -n "$NS" -o json)" && [ "$(jq -r '.metadata.uid' <<<"$CUR")" = "$CJ_UID" ]; then NS_Q="$(jq -Rn --arg v "$NS" '$v|@json')"; CJ_Q="$(jq -Rn --arg v "$CJ" '$v|@json')"; printf 'kube_cronjob_status_active{namespace=%s,cronjob=%s}\n' "$NS_Q" "$CJ_Q"; printf 'kube_cronjob_next_schedule_time{namespace=%s,cronjob=%s}\n' "$NS_Q" "$CJ_Q"; else AUTO_READY=false; printf '%s\n' '중단: 현재 CronJob identity 불일치' >&2; fi`

## 증거와 경계

CronJob/Job UID·resourceVersion·owner UID, policy/spec digest, canonical 시간 창, 상태·Event의 비민감 요약, 승인과 실제 업무 결과만 보존한다. Secret·token·payload·개인정보·전체 YAML/로그는 출력하거나 저장하지 않는다. Kubernetes 1.26 동작을 기준으로 정적 검토했으며 controller clock, Event/audit 보존, RBAC, 업무 멱등성과 실제 클러스터 결과는 환경별 미검증이다.
