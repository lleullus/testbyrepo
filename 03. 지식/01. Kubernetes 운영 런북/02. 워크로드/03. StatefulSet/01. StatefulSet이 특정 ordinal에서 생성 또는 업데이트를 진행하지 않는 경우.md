# StatefulSet이 특정 ordinal에서 생성 또는 업데이트를 진행하지 않는 경우

## 입력값과 빠른 수집

승인된 작업 PC의 같은 Bash에서 `API server -> StatefulSet UID/spec -> expected ordinal -> Pod UID/owner/revision -> 조건부 PVC/PV/CSI attachment`를 확인한다. node SSH·CRI·Pod exec는 사용하지 않는다.

| 구분 | 값 | 계약 |
|---|---|---|
| 최초 입력 | namespace, StatefulSet, UTC 관측 창 | 한 번만 입력하고 canonical 검증한다. |
| API 자동값 | UID/resourceVersion/generation/spec digest/selector, policy·strategy·revision·ordinal 범위 | 조회가 모두 성공한 뒤 등록한다. |
| 계산 후보 | expected ordinal과 Pod 이름 | start ordinal과 replicas에서 계산하며 API 결과와 대조한다. |
| 운영자 선택값 | 문제 ordinal, 1.26 alpha gate 확인, 조건부 PVC | inventory를 확인한 뒤 등록한다. |

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | expected ordinal Pod가 없거나, 존재하지만 update 대상인데 새 revision으로 진행하지 않는다. |
| 적용 | StatefulSet UID/spec, ordinal 범위, Pod owner·UID·revision, 필요 시 PVC→PV→CSI 관계를 연결한다. |
| 제외 | partition·OnDelete로 의도된 old revision은 [[03. StatefulSet rolling update partition 또는 OnDelete 전략 때문에 일부 Pod가 이전 revision인 경우]], revision 전체 불일치는 [[02. StatefulSet currentRevision과 updateRevision이 수렴하지 않는 경우]]로 이동한다. |

검색 문자열: `OrderedReady`, `Parallel`, `currentRevision`, `updateRevision`, `controller-revision-hash`, `partition`, `OnDelete`, `FailedCreate`, `FailedMount`.

## 최초 확인

```bash
INVENTORY_READY=false
if ! fresh_statefulset; then printf '%s\n' '중단: 최신 StatefulSet gate 실패' >&2
elif ! P="$(kubectl get pods -n "$NS" -l "$SELECTOR" -o json --request-timeout=15s)" || ! C="$(kubectl get controllerrevisions -n "$NS" -o json --request-timeout=15s)"; then printf '%s\n' '중단: Pod/ControllerRevision producer 실패' >&2
else jq -r '"=== StatefulSet ===\nUID/RV: \(.metadata.uid)/\(.metadata.resourceVersion)\ngeneration/observed: \(.metadata.generation)/\(.status.observedGeneration//0)\nreplicas actual/current/ready/updated: \(.status.replicas//0)/\(.status.currentReplicas//0)/\(.status.readyReplicas//0)/\(.status.updatedReplicas//0)\npolicy/strategy/partition: \(.spec.podManagementPolicy)/\(.spec.updateStrategy.type)/\(.spec.updateStrategy.rollingUpdate.partition//0)\ncurrent/update: \(.status.currentRevision//"-")/\(.status.updateRevision//"-")"' <<<"$S_LIVE"; jq -r --arg u "$STS_UID" '.items[]|select(any(.metadata.ownerReferences[]?;.controller==true and .kind=="StatefulSet" and .uid==$u))|"\n=== Pod \(.metadata.name) ===\nUID/RV: \(.metadata.uid)/\(.metadata.resourceVersion)\nowner: StatefulSet/\([.metadata.ownerReferences[]|select(.controller==true)][0].name) uid=\($u)\npod-name label/revision: \(.metadata.labels["statefulset.kubernetes.io/pod-name"]//"-")/\(.metadata.labels["controller-revision-hash"]//"-")\ncreated/deletion: \(.metadata.creationTimestamp)/\(.metadata.deletionTimestamp//"-")\nnode/phase/Ready: \(.spec.nodeName//"-")/\(.status.phase//"-")/\([.status.conditions[]?|select(.type=="Ready")][0].status//"-")\nclaims: \([.spec.volumes[]?|select(.persistentVolumeClaim!=null)|.persistentVolumeClaim.claimName]|join(","))\ncontainers: \((([.status.initContainerStatuses[]?|"init/\(.name):\(.containerID//"-")"])+([.status.containerStatuses[]?|"regular/\(.name):\(.containerID//"-")"]))|join(";"))"' <<<"$P"; jq -r --arg u "$STS_UID" '.items[]|select(any(.metadata.ownerReferences[]?;.controller==true and .kind=="StatefulSet" and .uid==$u))|"ControllerRevision \(.metadata.name) uid=\(.metadata.uid) rv=\(.metadata.resourceVersion) numericRevision=\(.revision) ownerUID="+$u+" hash=\(.metadata.labels["controller.kubernetes.io/hash"]//"-") created=\(.metadata.creationTimestamp)"' <<<"$C"; INVENTORY_READY=true; fi
```

`Parallel`은 scale 순서만 완화하며 RollingUpdate 순서를 병렬화하지 않는다. ControllerRevision `metadata.name`을 Pod의 `controller-revision-hash`와 비교하고 `controller.kubernetes.io/hash`를 Pod label과 직접 비교하지 않는다.

|---|---|---|---|
| expected ordinal Pod가 없다 | ordinal 범위, OrderedReady의 더 낮은 Pod, owner UID | controller 진행 또는 낮은 Pod 원인 | [[#문제 ordinal 등록]] |
| Pod는 있지만 update revision이 아니다 | strategy·partition·높은 ordinal Ready | 의도된 old revision 또는 update 정체 | [[#UID·시간 제한 Event와 판정]] |

| 교체 뒤 Pod가 생겼다 | 새 Pod UID·revision·containerID·PVC identity | 실제 기능과 재발 관찰 | [[#상태 변경 경계와 정상화]] |

## 문제 ordinal 등록

```bash
ORDINAL_INPUT='PASTE_PROBLEM_ORDINAL_HERE'
START_ORDINAL_GATE_INPUT='PASTE_STATEFULSET_START_ORDINAL_GATE_VERIFIED_TRUE_OR_FALSE_HERE'
PVC_INPUT='PASTE_PVC_NAME_OR_DASH_HERE'
```

```bash
ORDINAL_READY=false; STORAGE_READY=false; EVENT_READY=false; NORMAL_READY=false; PROMQL_READY=false
unset TARGET_ORDINAL TARGET_POD POD_PRESENT POD_UID POD_RV POD_REV POD_NODE NODE_UID MACHINE_ID CONTAINER_ROWS PVC PVC_UID PV PV_UID CSI_DRIVER ATTACHMENT_ROWS
if [ "$INVENTORY_READY" != true ] || ! fresh_statefulset; then printf '%s\n' '중단: 최신 inventory/StatefulSet 필요' >&2
elif ! [[ "$ORDINAL_INPUT" =~ ^[0-9]+$ ]]; then printf '%s\n' '중단: ordinal은 0 이상의 정수여야 한다.' >&2
elif [ "$ORDINAL_START" -ne 0 ] && [ "$START_ORDINAL_GATE_INPUT" != true ]; then printf '%s\n' '중단: Kubernetes 1.26 alpha StatefulSetStartOrdinal feature gate와 API 적용 확인 필요' >&2
elif (( ORDINAL_INPUT < ORDINAL_START || ORDINAL_INPUT >= ORDINAL_START + REPLICAS )); then printf '%s\n' '중단: ordinal이 현재 expected 범위 밖이다.' >&2
else TARGET_ORDINAL="$ORDINAL_INPUT"; TARGET_POD="${STS}-${TARGET_ORDINAL}"; if POD_JSON="$(kubectl get pod "$TARGET_POD" -n "$NS" -o json --request-timeout=15s 2>/dev/null)"; then POD_PRESENT=true; if ! jq -e --arg u "$STS_UID" --arg n "$STS" 'any(.metadata.ownerReferences[]?;.controller==true and .kind=="StatefulSet" and .name==$n and .uid==$u)' <<<"$POD_JSON" >/dev/null || [ "$(jq -r '.metadata.labels["statefulset.kubernetes.io/pod-name"]//empty' <<<"$POD_JSON")" != "$TARGET_POD" ]; then printf '%s\n' '중단: Pod owner/pod-name identity 불일치' >&2; else POD_UID="$(jq -r '.metadata.uid' <<<"$POD_JSON")"; POD_RV="$(jq -r '.metadata.resourceVersion' <<<"$POD_JSON")"; POD_REV="$(jq -r '.metadata.labels["controller-revision-hash"]//"-"' <<<"$POD_JSON")"; POD_NODE="$(jq -r '.spec.nodeName//"-"' <<<"$POD_JSON")"; CONTAINER_ROWS="$(jq -c '([.status.initContainerStatuses[]?|{kind:"init",name,containerID:(.containerID//"-")}]+[.status.containerStatuses[]?|{kind:"regular",name,containerID:(.containerID//"-")}])' <<<"$POD_JSON")"; if [ "$POD_NODE" != - ] && N="$(kubectl get node "$POD_NODE" -o json --request-timeout=15s)"; then NODE_UID="$(jq -r '.metadata.uid' <<<"$N")"; MACHINE_ID="$(jq -r '.status.nodeInfo.machineID//"-"' <<<"$N")"; elif [ "$POD_NODE" != - ]; then printf '%s\n' '중단: node identity 조회 실패' >&2; POD_PRESENT=error; fi; fi; else POD_PRESENT=false; POD_UID='-'; POD_RV='-'; POD_REV='-'; POD_NODE='-'; NODE_UID='-'; MACHINE_ID='-'; CONTAINER_ROWS='[]'; fi; if [ "$POD_PRESENT" != error ]; then ORDINAL_READY=true; printf 'ORDINAL_READY=true ordinal=%s pod=%s present=%s uid=%s rv=%s revision=%s\nnode=%s nodeUID=%s machineID=%s containers=%s\n' "$TARGET_ORDINAL" "$TARGET_POD" "$POD_PRESENT" "$POD_UID" "$POD_RV" "$POD_REV" "$POD_NODE" "$NODE_UID" "$MACHINE_ID" "$CONTAINER_ROWS"; fi; fi
```

Pod가 없으면 `POD_PRESENT=false` 자체가 성공적인 조회 결과다. `OrderedReady` create/scale 경로에서는 더 낮은 ordinal의 Ready·deletion을 먼저 보고, update 경로에서는 높은 ordinal부터 막힌 Pod를 본다. `OnDelete` 또는 `ordinal < partition`의 old revision은 자동 진행 대상이 아니다.

```bash
fresh_ordinal(){ [ "$ORDINAL_READY" = true ] || return 1; fresh_statefulset || return 1; if [ "$POD_PRESENT" = true ]; then P_NOW="$(kubectl get pod "$TARGET_POD" -n "$NS" -o json --request-timeout=15s)" || return 1; [ "$(jq -r '.metadata.uid' <<<"$P_NOW")" = "$POD_UID" ] || { printf '%s\n' '중단: Pod UID 교체, ordinal 재등록 필요' >&2; return 1; }; jq -e --arg u "$STS_UID" 'any(.metadata.ownerReferences[]?;.controller==true and .uid==$u)' <<<"$P_NOW" >/dev/null || return 1; else ! kubectl get pod "$TARGET_POD" -n "$NS" --request-timeout=15s >/dev/null 2>&1 || { printf '%s\n' '중단: 없던 Pod가 생성됨, ordinal 재등록 필요' >&2; return 1; }; fi; }
```

## 조건부 storage identity

`PVC_INPUT`은 inventory의 대상 Pod claim 중 조사할 PVC 하나이거나 storage 조사가 불필요한 경우 `-`다. PVC 이름을 ordinal 규칙으로 추측하지 않는다.

```bash
STORAGE_READY=false
if ! fresh_ordinal; then printf '%s\n' '중단: 최신 ordinal/StatefulSet 필요' >&2
elif [ "$PVC_INPUT" = - ]; then STORAGE_READY=true; printf '%s\n' 'STORAGE_READY=true storage=not-selected'
elif [ "$POD_PRESENT" != true ]; then printf '%s\n' '중단: Pod가 없으므로 실제 claimName을 확정할 수 없다.' >&2
elif ! jq -e --arg p "$PVC_INPUT" 'any(.spec.volumes[]?;.persistentVolumeClaim.claimName==$p)' <<<"$POD_JSON" >/dev/null; then printf '%s\n' '중단: 선택 PVC가 현재 Pod claim이 아니다.' >&2
elif ! PVC_JSON="$(kubectl get pvc "$PVC_INPUT" -n "$NS" -o json --request-timeout=15s)"; then printf '%s\n' '중단: PVC producer 실패' >&2
elif [ -z "$(jq -r '.spec.volumeName//empty' <<<"$PVC_JSON")" ] || ! PV_JSON="$(kubectl get pv "$(jq -r '.spec.volumeName' <<<"$PVC_JSON")" -o json --request-timeout=15s)"; then printf '%s\n' '중단: PVC가 Bound PV를 제공하지 않거나 PV 조회 실패' >&2
elif ! jq -e --arg n "$NS" --arg p "$PVC_INPUT" --arg u "$(jq -r '.metadata.uid' <<<"$PVC_JSON")" '.spec.claimRef.namespace==$n and .spec.claimRef.name==$p and .spec.claimRef.uid==$u' <<<"$PV_JSON" >/dev/null; then printf '%s\n' '중단: PV claimRef namespace/name/UID 불일치' >&2
elif ! VA_JSON="$(kubectl get volumeattachments.storage.k8s.io -o json --request-timeout=15s)"; then printf '%s\n' '중단: VolumeAttachment producer 실패' >&2
else PVC="$PVC_INPUT"; PVC_UID="$(jq -r '.metadata.uid' <<<"$PVC_JSON")"; PV="$(jq -r '.metadata.name' <<<"$PV_JSON")"; PV_UID="$(jq -r '.metadata.uid' <<<"$PV_JSON")"; CSI_DRIVER="$(jq -r '.spec.csi.driver//"non-CSI"' <<<"$PV_JSON")"; ATTACHMENT_ROWS="$(jq -c --arg p "$PV" '[.items[]|select(.spec.source.persistentVolumeName==$p)|{name:.metadata.name,uid:.metadata.uid,rv:.metadata.resourceVersion,attacher:.spec.attacher,node:.spec.nodeName,attached:(.status.attached//false)}]' <<<"$VA_JSON")"; STORAGE_READY=true; printf 'STORAGE_READY=true pod=%s uid=%s PVC=%s uid=%s PV=%s uid=%s driver=%s attachments=%s\n' "$TARGET_POD" "$POD_UID" "$PVC" "$PVC_UID" "$PV" "$PV_UID" "$CSI_DRIVER" "$ATTACHMENT_ROWS"; fi
```

attachment no-match는 오류 없음이 아니라 driver가 attach를 사용하지 않거나 아직 생성되지 않았거나 조회 범위가 다른 분기다. attach가 있으면 node가 현재 Pod node와 맞는지 확인한다. `Bound`·`attached=true`는 mount와 제품 데이터 정상을 보장하지 않는다.

## UID·시간 제한 Event와 판정

```bash
EVENT_READY=false
if ! fresh_ordinal; then printf '%s\n' '중단: 최신 ordinal identity 실패' >&2
elif ! E="$(kubectl get events -n "$NS" -o json --request-timeout=15s)"; then printf '%s\n' '중단: Event producer 실패' >&2
elif ! ROWS="$(jq -er --arg su "$STS_UID" --arg pu "$POD_UID" --arg s "$OBS_START" --arg e "$OBS_END" '[.items[]|select(.involvedObject.uid==$su or ($pu!="-" and .involvedObject.uid==$pu))|(.eventTime//.series.lastObservedTime//.lastTimestamp//.firstTimestamp//.metadata.creationTimestamp) as $t|select($t>=$s and $t<=$e)|{uid:.metadata.uid,involvedUID:.involvedObject.uid,time:$t,type,reason,count:(.count//.series.count//1),message}]' <<<"$E")"; then printf '%s\n' '중단: Event filter 오류' >&2
else jq -r 'if length==0 then "no-match: 현재 UID·시간 범위 Event 없음" else .[]|"event uid=\(.uid) involvedUID=\(.involvedUID) time=\(.time) type=\(.type) reason=\(.reason) count=\(.count) message=\(.message)" end' <<<"$ROWS"; EVENT_READY=true; fi
```

- `OrderedReady` create/scale에서 더 낮은 ordinal이 NotReady·deleting이면 해당 Pod UID/container reason으로 이관한다.
- update 대상 높은 ordinal이 Ready가 아니면 다음 ordinal 진행은 보장되지 않는다. image·mount·probe·OOM 원인을 해당 Pod 런북으로 넘긴다.
- `observedGeneration < generation`, expected Pod 부재, owner·revision이 모두 정상인데 진행이 없으면 StatefulSet controller/control-plane owner에게 이관한다.
- audit을 쓰면 단일 auditID의 timestamp, verb, resource/subresource, namespace/name, requestURI, status와 현재 StatefulSet lifecycle UID만 보존한다. actor 상세·token은 남기지 않는다.

## 상태 변경 경계와 정상화

이 문서에는 delete, scale, partition·strategy patch, PVC/PV 변경 명령이 없다. StatefulSet 변경은 quorum·leader·replication, PVC identity, 현재 UID/resourceVersion/spec digest, 승인 ID·UTC 창·가용성·멱등성·되돌림을 직접 재검사하는 제품별 절차로만 수행한다. 승인된 외부 변경으로 spec이 바뀌면 모든 READY와 자동값을 폐기하고 처음부터 재등록한다.

```bash
NORMAL_READY=false
if ! fresh_statefulset; then printf '%s\n' '중단: 최신 StatefulSet identity 실패' >&2
elif ! P2="$(kubectl get pods -n "$NS" -l "$SELECTOR" -o json --request-timeout=15s)"; then printf '%s\n' '중단: 정상화 Pod producer 실패' >&2
elif ! NEW_POD="$(jq -cer --arg n "$TARGET_POD" --arg u "$STS_UID" '[.items[]|select(.metadata.name==$n and any(.metadata.ownerReferences[]?;.controller==true and .uid==$u))]|if length==1 then .[0] else error("target candidate count") end' <<<"$P2")"; then printf '%s\n' '미정상: target ordinal current Pod 단일 재등록 실패' >&2
else NEW_POD_UID="$(jq -r '.metadata.uid' <<<"$NEW_POD")"; NEW_POD_REV="$(jq -r '.metadata.labels["controller-revision-hash"]//"-"' <<<"$NEW_POD")"; NEW_CONTAINERS="$(jq -c '([.status.initContainerStatuses[]?|{kind:"init",name,containerID:(.containerID//"-")}]+[.status.containerStatuses[]?|{kind:"regular",name,containerID:(.containerID//"-")}])' <<<"$NEW_POD")"; if [ "$(jq -r '([.status.conditions[]?|select(.type=="Ready")][0].status//"False")' <<<"$NEW_POD")" != True ] || [ "$(jq '[.[]|select(.containerID=="-")]|length' <<<"$NEW_CONTAINERS")" -ne 0 ]; then printf '%s\n' '미정상: current target Pod Ready/containerID 불충족' >&2; elif [ "$UPDATE_TYPE" = RollingUpdate ] && (( TARGET_ORDINAL >= PARTITION )) && [ "$NEW_POD_REV" != "$UPDATE_REV" ]; then printf '%s\n' '미정상: update 대상 ordinal revision 불일치' >&2; else NORMAL_READY=true; printf 'NORMAL_READY=true statefulSetUID=%s pod=%s oldUID=%s currentUID=%s revision=%s containers=%s observedAt=%s\n' "$STS_UID" "$TARGET_POD" "$POD_UID" "$NEW_POD_UID" "$NEW_POD_REV" "$NEW_CONTAINERS" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; fi; fi
```

새 UID를 얻은 뒤 claimName→PVC UID→PV UID/claimRef→CSI driver/attachment node를 다시 등록한다. 전체 expected ordinal 수, desired/actual/ready/updated, 같은 Warning·restart·deletion 재발 없음, Service를 쓰는 경우 endpoint targetRef Pod UID, 승인된 실제 read/write·핵심 기능과 quorum 상태가 관찰 창 동안 안정적이어야 정상화한다.

## Prometheus 빠른 관측

```bash
PROMQL_READY=false
if ! fresh_ordinal; then printf '%s\n' '중단: 최신 ordinal identity 실패' >&2
else printf 'kube_statefulset_replicas{namespace="%s",statefulset="%s"}-kube_statefulset_status_replicas_ready{namespace="%s",statefulset="%s"}\n' "$NS" "$STS" "$NS" "$STS"; if [ "$POD_PRESENT" = true ]; then printf 'kube_pod_status_ready{namespace="%s",pod="%s",uid="%s",condition="true"}\n' "$NS" "$TARGET_POD" "$POD_UID"; fi; PROMQL_READY=true; fi
```

metric·label 미지원, 빈 결과, stale series를 정상으로 해석하지 않는다. PromQL은 ordinal 순서, ControllerRevision owner UID, PVC identity, 제품 기능을 증명하지 않는다.
