# Pod restartCount가 계속 증가하는 경우

## 입력값과 빠른 수집

실행 host는 승인된 context가 설정된 작업 PC 또는 bastion이며 모든 명령은 같은 Bash에서 실행한다. 기본 진단은 Kubernetes API의 `pods/get`, `pods/list`, `events/list`와 `logs` subresource 권한이 필요하다. node·kubelet·kernel·CRI 분기는 승인된 `NODE_HOST` 매핑, remote node identity가 Kubernetes Node 이름과 일치하는 SSH gate, remote `sudo` 권한, 실제 journal unit과 CRI endpoint가 확인된 뒤에만 진입한다. 작업 PC에서 node journal·CRI에 직접 `sudo`하지 않는다. 기본 도구 확인이 실패하면 다음 단계로 진행하지 않는다.

| 종류 | 값 | 출처와 사용 시점 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 namespace와 정확한 Pod 이름을 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `NODE`, `NODE_UID`, `NODE_MACHINE_ID`, `PHASE`, `POD_READY`, `OWNER_KIND`, `OWNER_NAME`, `OWNER_UID`, kubelet에서 읽은 `CRI_ENDPOINT`, `CONTAINER_CANDIDATES`, 선택 container의 `RESTART_COUNT`, `CONTAINER_ID`, current/last state·시각·reason·exit code, `POD_RE` | 같은 Pod·Node API와 승인된 node에서 읽어 현재 Bash에 등록한다. 선택 container의 restartCount와 controller owner kind/name/UID를 bounded 출력하고 이후 분기에서 같은 identity를 재검증한다. CRI endpoint와 Node machine ID는 운영자가 입력하지 않는다. |
| 계산 후보 | `POD_RE`, `JOB_SELECTOR`, `START_JOURNAL`, `END_JOURNAL`, runtime log filter | 등록값·관측 시각으로 만들며 원인 확정 전에 후보로만 사용한다. |
| 운영자 선택값 | `CONTAINER`, `START_RFC3339`, 승인된 `NODE_HOST`, dependency service, service, `RUNTIME_SERVICE` | 출력·승인된 node 매핑·권한·실제 구현을 확인한 뒤 해당 절 직전에 선택한다. 복수 container·runtime unit을 첫 번째로 고르지 않는다. |

Pod UID가 바뀌면 이전 counter·Event·로그를 새 Pod에 재사용하지 않는다. 현재 `CrashLoopBackOff`는 kubelet backoff 상태이고 종료 원인 자체가 아니므로 [[06. Pod STATUS가 CrashLoopBackOff인 경우]]와 역할을 나눈다. `Running`과 `Ready`도 별개이며 readiness probe 실패만으로 restart를 확정하지 않는다.

**Bash·필수 도구·권한 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date ssh; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 같은 Pod UID의 특정 container에서 두 관찰 시각 사이 `restartCount`가 증가한 경우 |
| 적용 | Pod UID와 대상 container를 고정하고 current/lastState, 종료 시각, UID 제한 Event·로그를 같은 시간축에서 비교한다. |
| 제외 | 현재 `CrashLoopBackOff`만 있고 증가 구간을 확인하지 못하면 [[06. Pod STATUS가 CrashLoopBackOff인 경우]], Pending·FailedScheduling은 [[02. Pod STATUS가 Pending인 경우]], image pull은 [[07. Pod STATUS가 ImagePullBackOff·ErrImagePull인 경우]], volume mount는 [[25. Pod 이벤트에 FailedMount·FailedAttachVolume이 기록된 경우]], sandbox는 [[24. Pod 이벤트에 FailedCreatePodSandBox가 기록된 경우]]로 이동한다. restart를 낮추기 위한 무조건 Pod 삭제·rollout restart는 실행하지 않는다. |

검색 문자열: `restartCount`, `CrashLoopBackOff`, `Back-off restarting failed container`, `Last State`, `Exit Code`, `Signal`, `OOMKilled`, `Liveness probe failed`, `Startup probe failed`, `Killing`, `Completed`, `OCI`, `cgroup`, `kernel OOM`

## 최초 확인

`OBS_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o wide && kubectl describe pod "$POD" -n "$NS"; then OBS_READY=true; printf 'OBS_READY=true uid=%s observed_at=%s\n' "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '%s\n' '중단: Pod 최초 확인 실패' >&2; fi`

`get`에서 phase·Ready·restarts·node·age·UID를, `describe`와 자동 수집에서 container별 current State, Last State, reason, exitCode, signal, started/finished 시각, restartCount, Conditions와 첫 실패 Event message를 본다. `CrashLoopBackOff`는 현재 backoff 결과이지 종료 원인이 아니다. 이 명령 성공은 실제 application 정상과 재시작 중단을 보장하지 않는다.

`EVENTS_READ_READY=false; EVENT_JSON=''; if [ "$OBS_READY" != true ]; then printf '%s\n' '중단: OBS_READY가 아니다.' >&2; elif EVENT_JSON="$(kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID" --sort-by=.metadata.creationTimestamp -o json)"; then EVENTS_READ_READY=true; jq -r 'if (.items|length)==0 then "Event: 없음 (정상·원인 없음으로 해석하지 않음)" else .items[] | "=== Event ===\n생성: \(.metadata.creationTimestamp // "-")\nFirst: \(.firstTimestamp // "-")\nLast: \(.lastTimestamp // "-")\nEvent time: \(.eventTime // "-")\nSeries last: \(.series.lastObservedTime // "-")\nType/Reason: \(.type // "-")/\(.reason // "-")\nCount: \(.count // "-")\nMessage: \(.message // "-")" end' <<<"$EVENT_JSON"; else printf '%s\n' '중단: UID 제한 Event API 조회 실패' >&2; fi`

Event는 집계되므로 채워진 시각과 count를 current/lastState 종료 시각·로그 시각과 대조한다. Pod 이름만으로 다른 UID의 Event를 섞지 않으며, 빈 Event는 보존·범위·selector 문제와 실제 미존재를 구분한다.

| `Startup probe failed` | 초기화 로그와 startup 유예 | app dependency·kubelet | [[#3. Startup probe 실패|3]] |
| `reason=Error` 또는 non-zero exit | command/args와 종료 직전 오류 | current/previous 로그·설정·dependency | [[#4. 애플리케이션 또는 command 종료|4]] |
| exit code `0`, `restartPolicy=Always` | owner와 장기 실행 계약 | command/args·Job 완료 여부 | [[#5. exit code 0과 restartPolicy=Always|5]] |
| Last State는 정상인데 runtime Event | 생성·정리 경로 | kubelet·CRI·Linux | [[#6. Last State는 정상인데 runtime 경로가 실패|6]] |

표는 길 안내일 뿐 원인을 확정하지 않는다. 각 상세 절의 직접 evidence와 gate를 통과하지 못하면 다음 명령을 실행하지 않고 해당 owner로 이관한다.

## 공통 로그와 stream 경계

로그 진입 증거는 자동 수집된 대상 container의 `restartCount`·current/last state가 확정된 경우다. 종료 시각보다 조금 앞선 UTC `$START_RFC3339`가 필요하며, 같은 Pod UID·container ID를 함께 기록한다.

## 상세 분기

### 1. OOMKilled 또는 메모리 종료

진입 증거는 같은 UID·container의 `reason=OOMKilled` 또는 종료 code `137`이다. `137`만으로 OOM을 확정하지 않고 resource·node evidence와 kernel 시각을 연결한다.

`if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .spec.containers[*]}container={.name} requests={.resources.requests} limits={.resources.limits}{"\n"}{end}' && kubectl top pod "$POD" -n "$NS" --containers && kubectl describe node "$NODE"; then printf '성공 gate: 선택 container limit/top 결과와 node MemoryPressure/Eviction/OOM 시각을 비교\n'; else printf '%s\n' '실패 또는 빈 top: metrics-server 부재·지연·권한·node 조회 실패 후보이며 OOM 부재로 해석하지 않음' >&2; fi`

`kubectl top`의 사용량은 peak를 보장하지 않는다. 여러 Pod가 동시에 종료되거나 `MemoryPressure`가 있으면 단일 limit 변경으로 닫지 않고 kubelet eviction·node owner로 이동한다. 볼 것은 해당 container의 memory limit, 관찰 사용량, node `MemoryPressure`, `EvictionThresholdMet`, 같은 시각 다른 Pod 종료와 OOMKilled 시각이다.

kernel의 `Out of memory: Killed process`와 대상 cgroup·종료 시각이 맞으면 kernel OOM, kubelet `eviction manager` 또는 `Evicted`가 맞으면 node pressure 경로다. cgroup path가 확인되지 않으면 `/sys/fs/cgroup` 임의 파일을 container 증거로 사용하지 않고 node 담당자에게 이관한다. 대상 `reason=OOMKilled` 세부 소유권은 [[11. Pod STATUS가 OOMKilled인 경우]], 현재 waiting `CrashLoopBackOff`는 [[06. Pod STATUS가 CrashLoopBackOff인 경우]]다.

### 2. Liveness probe가 container를 종료한 경우

진입 증거는 같은 Event 시간축에서 `Liveness probe failed` 뒤 `Killing`이 있고 종료 시각이 맞는 경우다. readiness 실패만 있고 `Killing`이 없으면 이 절로 오지 않는다.

### 3. Startup probe 실패

진입 증거는 `Startup probe failed`와 초기화 중 종료 시각이 연결된 경우다. startup 성공 전 liveness가 실행되지 않는다는 1.26 동작 전제를 유지하되 scheduling·timeout·실행 지연은 별도다.

### 4. 애플리케이션 또는 command 종료

진입 증거는 `reason=Error` 또는 non-zero exit가 있고 probe·OOM·runtime 직접 근거가 없는 경우다. command/args와 종료 직전 current/previous log를 먼저 연결한다.

`DEPENDENCY_SERVICE='PASTE_DEPENDENCY_SERVICE_HERE'; DEPENDENCY_READY=false; if [ "$AUTO_READY" != true ] || [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: AUTO_READY와 container SELECTION_READY가 아니다.' >&2; elif [ -n "$DEPENDENCY_SERVICE" ]; then DEPENDENCY_READY=true; export DEPENDENCY_SERVICE; printf 'DEPENDENCY_READY=true dependency=%s\n' "$DEPENDENCY_SERVICE"; else printf '%s\n' '중단: dependency service를 선택하지 않음' >&2; fi`

### 5. exit code 0과 restartPolicy=Always

진입 증거는 `lastState.terminated.exitCode=0`, `Completed`와 `restartPolicy=Always`가 같은 container에서 확인된 경우다. 먼저 owner를 자동값으로 확인한다.

### 6. Last State는 정상인데 runtime 경로가 실패

## 영향 범위와 제한된 복구

서비스 workload는 Ready replica와 EndpointSlice를, Job/CronJob owner는 Complete·succeeded·산출물·외부 side effect를 별도로 판단한다. 서비스 이름을 자동 추측하지 않는다.

`SERVICE='PASTE_SERVICE_HERE'; APP_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif SERVICE_JSON="$(kubectl get service "$SERVICE" -n "$NS" -o json)"; then SERVICE_PRODUCER_RC=0; if ENDPOINT_JSON="$(kubectl get endpointslice -n "$NS" -l "kubernetes.io/service-name=$SERVICE" -o json)"; then ENDPOINT_PRODUCER_RC=0; APP_READY=true; export SERVICE; jq -r 'if (.items|length)==0 then "EndpointSlice: 없음 (정상 endpoint로 해석하지 않음)" else .items[] | "EndpointSlice: \(.metadata.name) endpoints=\((.endpoints // [])|length)" end' <<<"$ENDPOINT_JSON"; printf 'APP_READY=true service=%s observed_at=%s\n' "$SERVICE" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else ENDPOINT_PRODUCER_RC=$?; printf '중단: EndpointSlice producer rc=%s; endpoint 영향 판단 불가\n' "$ENDPOINT_PRODUCER_RC" >&2; fi; else SERVICE_PRODUCER_RC=$?; printf '중단: Service producer rc=%s; endpoint 영향 판단 불가\n' "$SERVICE_PRODUCER_RC" >&2; fi`

### 복구 전 안전 gate와 상태 변경 경계

원인 하나 이상을 직접 입증하고 owner·영향·승인·되돌림·관찰 시간을 정한 뒤에만 선언 변경을 별도 승인 절차로 이관한다. 삭제·rollout·scale·patch를 기본 진단으로 실행하지 않는다.

- Trigger: 종료 reason·exitCode 또는 OOM·probe·application·runtime 직접 근거가 있다.
- Scope: Deployment/StatefulSet replica·PDB·quorum, Job 중복 실행·산출물·외부 side effect를 평가했다.
- Authority: workload·node·runtime·dependency owner와 변경 승인자가 확인됐다.
- Stop/Rollback: 같은 Last State·Event 재발, Ready/endpoint 감소, 새 Warning, 오류율 증가, Job 산출물 이상이면 즉시 중단하고 승인된 rollback·이관을 실행한다.
- Verification: 새 Pod가 생기면 이전 UID 증거를 재사용하지 않고 새 UID·container·시각부터 다시 수집한다.

## 정상화 검증

서비스 workload는 다음으로 Pod identity와 endpoint를 다시 확인한다. 명령 성공은 실제 요청 성공을 보장하지 않는다.

`NORMALIZATION_READY=false; unset NORMALIZATION_JSON NORMALIZATION_UID; if [ "$APP_READY" != true ] && [ "$OWNER_KIND" != Job ] && [ "$OWNER_KIND" != CronJob ]; then printf '%s\n' '중단: 서비스 workload는 APP_READY가 아니다.' >&2; elif NORMALIZATION_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && NORMALIZATION_UID="$(jq -r '.metadata.uid // empty' <<<"$NORMALIZATION_JSON")" && [ "$NORMALIZATION_UID" = "$POD_UID" ]; then NORMALIZATION_READY=true; printf 'NORMALIZATION_READY=true uid=%s owner=%s/%s/%s observed_at=%s\n' "$NORMALIZATION_UID" "$OWNER_KIND" "$OWNER_NAME" "${OWNER_UID:--}" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '중단: 정상화 직전 Pod UID mismatch stored_uid=%s current_uid=%s; 기존 evidence를 폐기하고 자동 수집부터 재실행한다.\n' "$POD_UID" "${NORMALIZATION_UID:--}" >&2; APP_READY=false; fi`

`NORMALIZATION_OWNER_READY=false; NORMALIZATION_OWNER_KIND=''; NORMALIZATION_OWNER_NAME=''; NORMALIZATION_OWNER_UID=''; NORMALIZATION_CURRENT_OWNER_UID=''; NORMALIZATION_OWNER_JSON=''; CURRENT_OWNER_REF_JSON=''; if [ "$NORMALIZATION_READY" != true ] || [ "$OWNER_REFERENCE_READY" != true ]; then printf '%s\n' '중단: NORMALIZATION_READY 또는 OWNER_REFERENCE_READY가 아니다.' >&2; elif CURRENT_OWNER_REF_JSON="$(jq -c '[.metadata.ownerReferences[]? | select(.controller==true)][0] // {}' <<<"$NORMALIZATION_JSON")" && NORMALIZATION_OWNER_KIND="$(jq -r '.kind // "-"' <<<"$CURRENT_OWNER_REF_JSON")" && NORMALIZATION_OWNER_NAME="$(jq -r '.name // "-"' <<<"$CURRENT_OWNER_REF_JSON")" && NORMALIZATION_OWNER_UID="$(jq -r '.uid // "-"' <<<"$CURRENT_OWNER_REF_JSON")" && [ "$NORMALIZATION_OWNER_KIND" = "$OWNER_KIND" ] && [ "$NORMALIZATION_OWNER_NAME" = "$OWNER_NAME" ] && [ "$NORMALIZATION_OWNER_UID" = "${OWNER_UID:--}" ]; then if [ "$OWNER_KIND" = Job ] || [ "$OWNER_KIND" = CronJob ]; then if [ "$OWNER_KIND" = Job ]; then OWNER_RESOURCE='job'; else OWNER_RESOURCE='cronjob'; fi; if NORMALIZATION_OWNER_JSON="$(kubectl get "$OWNER_RESOURCE" "$OWNER_NAME" -n "$NS" -o json)" && NORMALIZATION_CURRENT_OWNER_UID="$(jq -r '.metadata.uid // empty' <<<"$NORMALIZATION_OWNER_JSON")" && [ "$NORMALIZATION_CURRENT_OWNER_UID" = "$OWNER_UID" ]; then NORMALIZATION_OWNER_READY=true; NORMALIZATION_OWNER_KIND="$OWNER_KIND"; NORMALIZATION_OWNER_NAME="$OWNER_NAME"; export NORMALIZATION_OWNER_KIND NORMALIZATION_OWNER_NAME NORMALIZATION_CURRENT_OWNER_UID; printf 'NORMALIZATION_OWNER_READY=true owner=%s/%s owner_uid=%s current_owner_uid=%s pod_uid=%s observed_at=%s\n' "$OWNER_KIND" "$OWNER_NAME" "$OWNER_UID" "$NORMALIZATION_CURRENT_OWNER_UID" "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else NORMALIZATION_READY=false; printf '중단: 같은 이름의 현재 %s UID가 저장 owner UID와 다름 owner=%s/%s stored_owner_uid=%s current_owner_uid=%s\n' "$OWNER_KIND" "$OWNER_NAME" "$OWNER_UID" "${NORMALIZATION_CURRENT_OWNER_UID:--}" >&2; fi; else NORMALIZATION_OWNER_READY=true; printf 'NORMALIZATION_OWNER_READY=true owner=%s/%s owner_uid=%s pod_uid=%s observed_at=%s\n' "$OWNER_KIND" "$OWNER_NAME" "${OWNER_UID:--}" "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; fi; else NORMALIZATION_READY=false; printf '중단: 정상화 Pod의 현재 owner kind/name/UID가 초기 저장 identity와 다름 stored=%s/%s/%s current=%s/%s/%s\n' "$OWNER_KIND" "$OWNER_NAME" "${OWNER_UID:--}" "$NORMALIZATION_OWNER_KIND" "$NORMALIZATION_OWNER_NAME" "$NORMALIZATION_OWNER_UID" >&2; fi`

`if [ "$NORMALIZATION_OWNER_READY" != true ]; then printf '%s\n' '중단: 현재 owner UID 검증이 아니다.' >&2; elif [ "$NORMALIZATION_OWNER_KIND" = Job ]; then kubectl get job "$NORMALIZATION_OWNER_NAME" -n "$NS" -o jsonpath='{range .status.conditions[*]}condition={.type} status={.status} reason={.reason}{"\n"}{end}succeeded={.status.succeeded} failed={.status.failed}{"\n"}'; elif [ "$NORMALIZATION_OWNER_KIND" = CronJob ]; then kubectl get cronjob "$NORMALIZATION_OWNER_NAME" -n "$NS" -o wide; fi`

`if [ "$APP_READY" != true ]; then printf '%s\n' '중단: APP_READY가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o wide && kubectl get endpointslice -n "$NS" -l "kubernetes.io/service-name=$SERVICE" -o wide; fi`

`Running/Ready`, 원하는 replica·Ready 수, EndpointSlice, 승인된 client/monitor 실제 요청 또는 synthetic transaction, 핵심 기능이 정상이고 관찰 창 동안 같은 reason·exitCode·probe 실패·OOM·application 오류·restart 증가·새 Warning이 없어야 한다. `restartCount=0`은 정상화 조건이 아니다. EndpointSlice가 정상이어도 실제 요청을 생략하지 않는다.

Job/CronJob owner는 정상화 직전에 Pod의 현재 owner kind/name/UID와 저장된 `$OWNER_UID`를 대조하고, 같은 이름으로 재생성된 현재 owner의 API UID까지 대조한 `NORMALIZATION_OWNER_READY=true` 결과만 사용한다. 산출물·commit/ack·중복 여부를 승인된 읽기 전용 절차로 확인할 수 없으면 정상화·재실행을 선언하지 않는다.

## 증거 보존과 미검증

UTC 시각, namespace·Pod UID·node, container 이름·ID·restartCount, current/Last State·reason·exitCode·signal·started/finished 시각, restartPolicy, probe 선언, resource limit·top 결과, Event UID·시각·message, current/previous/CRI 로그의 bounded 시간 범위, kubelet·runtime·kernel 증거, dependency·Service 응답, owner kind/name/UID와 정상화 직전 현재 owner UID, runtime service·kubelet CRI endpoint·socket owner 관계, 승인·정상화 관찰 시각을 보존한다. Secret·token·개인키·개인정보·raw systemd ExecStart는 저장하지 않는다.

container runtime, CRI endpoint와 권한, cgroup 버전·경로, kubelet journal unit, Linux 보안 모듈, metrics-server와 외부 dependency는 환경별 미검증이다. Kubernetes Server와 `kubectl` 기준은 `1.26.x`이다.

## Prometheus 빠른 관측

PromQL은 등록된 `$NS`, `$POD_RE`, `$POD_UID`와 선택된 `$CONTAINER`로 완성 문자열을 생성한다. 출력 한 줄만 Prometheus/Grafana에 붙여 넣으며 metric 부재·label 불일치·조회 범위와 API/권한 실패를 구분한다.

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else printf '%s\n' "sum by(namespace,pod,uid,container)(increase(kube_pod_container_status_restarts_total{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\"}[15m]))>0"; fi`

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else printf '%s\n' "kube_pod_container_status_waiting_reason{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\"}==1"; printf '%s\n' "kube_pod_container_status_last_terminated_reason{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\"}==1"; fi`

`CONTAINER` label을 사용하는 중앙 metric이 실제로 수집될 때만 container별 결과를 해석한다. Counter reset·Pod UID 재생성·scrape 간격 때문에 increase 결과만으로 종료 원인을 확정하지 않으며 previous 로그와 `lastState`로 닫는다.
