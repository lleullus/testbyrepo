# Pod exec 대상 컨테이너를 찾을 수 없는 경우

## 입력값과 빠른 수집

이 문서는 Pod 이름은 맞지만 `container not found`, 기본 container 선택 실패, `not running`, 완료된 Pod 차단처럼 exec 대상의 identity·종류·상태를 확정할 수 없는 경우를 다룬다. 실행 명령은 승인된 비파괴 read-only command 하나로 제한하며 운영 image·Pod 선언·command/args를 바꾸지 않는다.

| 값 종류 | 이 문서에서 쓰는 값 | 출처와 처리 |
|---|---|---|
| 최초 입력 | `CONTEXT`, `NS`, `POD` | 운영자가 승인된 context, namespace, 정확한 Pod 이름을 처음 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `NODE`, `PHASE`, `POD_START`, `DELETION_TIMESTAMP`, regular·init·ephemeral의 spec/status, `CONTAINER_ID` | Kubernetes API에서 현재 Pod를 읽어 등록한다. UID·node·phase·시각과 container 종류·상태·ID를 사람이 선택할 수 있게 출력한다. |
| 계산 후보값 | `OBSERVED_AT`, `POD_RE`, `CONTAINER_RE`, 생성된 PromQL | 수집 시각과 escaped selector를 만들지만 사용 전 bounded 출력과 metric 존재를 확인한다. |
| 운영자 선택값 | `CONTAINER_KIND`, `CONTAINER`, `READ_ONLY_COMMAND`, `APPROVED_DEBUG_IMAGE` | API 출력·image 계약·승인 기록을 확인한 뒤 해당 분기에서 선택한다. debug image는 변경 gate에서만 사용한다. |

모든 shell 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. 터미널을 바꾸거나 새 Bash를 열면 등록값·gate가 사라지므로 이 절부터 다시 실행한다. `CONTEXT`는 kubeconfig의 API server 대상을 뜻하고, namespace와 Pod 이름은 exact-name 조회 범위를 제한한다. API 조회가 실패하거나 후보·필수값이 비면 다음 단계로 진행하지 않는다.

**실행 host와 필수 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: Bash에서 실행한다.' >&2; else MISSING_TOOLS=''; for TOOL in kubectl jq sed grep date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true shell=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 아래 명령을 실행하지 않는다. 이 gate는 도구 부재를 Kubernetes 오류로 오해하지 않게 한다.

**최초 입력과 이전 파생값 초기화 — 같은 Bash에서 한 번 실행**

`INPUT_READY=true`가 아니면 namespace·Pod 이름·context·API 권한을 확인하고 중단한다. 이 문서 전체의 `PASTE_..._HERE` 문자열은 각각 한 번만 입력하며 이후 값은 Bash 변수로 재사용한다.

**공통 auth·UID gate 등록 — 이후 모든 재조회에서 같은 Bash로 재사용**

`unset AUTH_OUTPUT AUTH_RAW_OUTPUT AUTH_RC AUTH_DECISION POD_SNAPSHOT POD_UID_GATE; auth_can_i(){ local raw output rc; raw="$(kubectl "$@" 2>&1; rc=$?; printf '\036%s' "$rc"; exit "$rc")"; rc="${raw##*$'\036'}"; output="${raw%$'\036'*}"; AUTH_RAW_OUTPUT="$output"; case "$output" in *$'\n') output="${output%$'\n'}";; esac; AUTH_OUTPUT="$output"; AUTH_RESULT="$output"; AUTH_RC="$rc"; AUTH_DECISION=error; if [ "$rc" -eq 0 ] && [ "$output" = yes ]; then AUTH_DECISION=yes; elif [ "$rc" -eq 1 ]; then case "$output" in no) AUTH_DECISION=no;; no\ -*) case "$output" in *$'\n'*|*$'\r'*) ;; *) AUTH_DECISION=no;; esac;; esac; fi; return 0; }; pod_uid_gate(){ local snapshot uid; POD_UID_GATE=false; unset POD_SNAPSHOT; if snapshot="$(kubectl --context "$CONTEXT" get pod "$POD" -n "$NS" -o json)" && uid="$(jq -r '.metadata.uid // empty' <<<"$snapshot")" && [ "$uid" = "$POD_UID" ]; then POD_SNAPSHOT="$snapshot"; POD_UID_GATE=true; export POD_SNAPSHOT POD_UID_GATE; printf 'POD_UID_GATE=true expected=%s observed=%s\n' "$POD_UID" "$uid"; return 0; else AUTO_READY=false; AUTH_READY=false; SELECTION_READY=false; COMMAND_READY=false; DEBUG_READY=false; QUERY_READY=false; CONTAINER_ID_READY=false; unset POD_SNAPSHOT CONTAINER_ID POD_RE CONTAINER_RE; printf 'UID_MISMATCH 또는 Pod API 실패 expected=%s observed=%s; 파생 gate를 폐기한다.\n' "$POD_UID" "${uid:--}" >&2; return 1; fi; }`

`auth_can_i`는 `AUTH_OUTPUT`, `AUTH_RC`, `AUTH_DECISION`을 별도로 등록한다. `AUTH_DECISION=yes`는 rc=0이고 출력이 정확히 한 줄 `yes`인 경우뿐이다. rc=1이고 출력이 정확히 한 줄 `no` 또는 한 줄 `no - ...`이면 정상적인 RBAC 거부로 `34번`으로 이관하며, multiline·blank extra line을 포함한 그 밖의 rc/output 조합은 API·인증 진단으로 이동한다. `pod_uid_gate`가 실패하면 최초 `$POD_UID`는 보존하고 `AUTO_READY`, `SELECTION_READY`, `CONTAINER_ID_READY` 등 파생 gate만 폐기한다.

**exec identity gate helper — 모든 exec 직전에 아래 helper를 통과**

`exec_identity_gate(){ local kind="$1" c="$2" expected="$3" expected_uid="${POD_UID:-}"; EXEC_IDENTITY_READY=false; if [ -z "$kind" ] || [ -z "$c" ] || [ -z "$expected" ] || [ -z "$expected_uid" ] || ! pod_uid_gate; then printf '%s\n' '중단: exec 직전 Pod UID·container 선택·containerID 재검증 실패.' >&2; return 1; elif ! jq -e --arg kind "$kind" --arg c "$c" --arg expected "$expected" --arg uid "$expected_uid" '(.metadata.uid == $uid) and (.metadata.deletionTimestamp == null) and (if $kind == "regular" then any(.spec.containers[]?; .name == $c) and any(.status.containerStatuses[]?; .name == $c and .state.running != null and .containerID == $expected) elif $kind == "init" then any(.spec.initContainers[]?; .name == $c) and any(.status.initContainerStatuses[]?; .name == $c and .state.running != null and .containerID == $expected) elif $kind == "ephemeral" then any(.spec.ephemeralContainers[]?; .name == $c) and any(.status.ephemeralContainerStatuses[]?; .name == $c and .state.running != null and .containerID == $expected) else false end)' <<<"$POD_SNAPSHOT" >/dev/null; then printf '중단: exec 직전 UID·deletionTimestamp·container kind/state/current containerID gate 실패 pod_uid=%s kind=%s container=%s container_id=%s\n' "$expected_uid" "$kind" "$c" "$expected" >&2; return 1; else EXEC_IDENTITY_READY=true; export EXEC_IDENTITY_READY; printf 'EXEC_IDENTITY_READY=true pod_uid=%s kind=%s container=%s container_id=%s\n' "$expected_uid" "$kind" "$c" "$expected"; return 0; fi; }`

**Pod API 자동 수집과 등록 — 같은 Bash에서 한 번 실행**

as $c | ([.status.ephemeralContainerStatuses[]? | select(.name == $c.name)] | first) as $s | ($s.state // {}) as $state | "  이름: \($c.name) / status: " + (if $state.running then "Running 시작=" + ($state.running.startedAt // "-") elif $state.waiting then "Waiting reason=" + ($state.waiting.reason // "-") elif $state.terminated then "Terminated reason=" + ($state.terminated.reason // "-") + " exitCode=" + (($state.terminated.exitCode // "-") | tostring) else "미보고" end) + " / containerID: " + ($s.containerID // "-") + " / restartCount: " + (($s.restartCount // "-") | tostring))] | join("\n"))' <<<"$POD_JSON"; fi; else printf '%s\n' '중단: Pod API 또는 자동값 파싱 실패. 이전 값은 유효하지 않다.' >&2; fi`

성공 출력은 대상 Pod의 UID·node·phase·시각과 regular·init·ephemeral 각각의 선언 이름, port 후보, 대응 status, state, containerID, restartCount를 포함해야 한다. 빈 status는 `Running`이 아니며 정상·오류 없음으로 해석하지 않는다. `containerID`는 runtime 식별자이고 Pod UID가 아니다. 이 명령이 실패하면 부분 등록을 남기지 않고 context·권한·API 응답을 확인한다.

재수집·재등록은 같은 이름의 새 Pod를 포함하므로 기존 선택값, 권한 결과, argv, containerID, debug/evidence gate, regex selector를 모두 폐기한다. 새 `AUTO_READY=true`만으로 진행하지 말고 `CONTAINER_KIND`·`CONTAINER`·command·승인 image를 다시 입력한 뒤 selection/auth/command gate를 다시 통과한다.

검색 문자열: `container not found`, `container name must be specified`, `Defaulted container`, `not running`, `cannot exec into a container in a completed pod`, `unable to upgrade connection`, `Upgrade request required`, `Forbidden`.

`kubectl logs`의 `pods/log` 권한과 `kubectl exec`의 `pods/exec` 권한·stream 경로는 별개다. `Running`, `Ready`, `auth can-i=yes`는 각각 container process·application·실제 exec stream 성공을 보장하지 않는다.

## 최초 확인

`AUTO_READY=true`인 같은 Bash에서 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r '"UID=" + (.metadata.uid // "-") + "\tPHASE=" + (.status.phase // "-") + "\tREADY=" + ([.status.containerStatuses[]?.ready] | map(tostring) | join(",")) + "\tRESTARTS=" + ([.status.containerStatuses[]?.restartCount] | map(tostring) | join(",")) + "\tNODE=" + (.spec.nodeName // "-")' <<<"$POD_SNAPSHOT"; fi`를 실행한다. 출력에는 현재 UID·phase·READY·RESTARTS·NODE가 있어야 하며, 명령 실패·`NotFound`는 namespace·Pod 이름·context를 다시 확인하는 gate다. `Forbidden`이면 오류의 subject·resource·subresource를 보존하고 34번 런북으로 이관한다.

같은 조건에서 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else kubectl --context "$CONTEXT" describe pod "$POD" -n "$NS"; fi`를 실행한다. `State`, `Last State`, `Reason`, `Exit Code`, `Restart Count`, 대상 container의 `containerID`, Conditions와 첫 실패 message만 비민감 범위로 기록한다. Secret·token·개인정보가 포함된 Event 원문은 저장하지 않는다. `describe` 실패는 진단 진행이 아니라 API·권한 실패 분기다.

현재 UID와 상태를 확인한 뒤에만 등록된 `auth_can_i --context "$CONTEXT" auth can-i create pods/"$POD" --subresource=exec -n "$NS"`를 실행한다. rc=1과 `no` 또는 `no - ...`는 정상적인 권한 거부로 RBAC 런북으로 이동하고, rc=0의 `yes`만 실행 gate를 통과한다. 그 밖의 non-zero/output 조합인 `Unauthorized`, DNS, timeout, `connection refused`는 권한 판정이 아니라 API 연결 런북으로 이동한다.

| `Succeeded`·`Failed` 또는 대상 state가 `Waiting`·`Terminated` | 완료 phase와 대상 state | exec 반복을 중단하고 상태·로그 런북 | [[#1. Pod UID와 phase를 먼저 고정|phase]] · [[#2. container 종류와 state를 분리|state]] |
| init이 `Terminated` | finished 시각과 exit code | 종료된 init에 exec하지 않고 init 런북 | [[#2. container 종류와 state를 분리|init state]] |
| ephemeral이 `Waiting`·`Terminated` | debug 승인과 세션 상태 | 상태 변경 없이 담당자 재평가 | [[#2. container 종류와 state를 분리|ephemeral state]] · [[#4. 승인된 ephemeral debug 경계|debug gate]] |
| 이름·UID·containerID와 `Running`이 모두 일치 | API upgrade 오류 | API server→kubelet stream 런북 | [[02. 워크로드/01. Pod/33. Pod exec 연결이 실패하는 경우|Pod exec 연결이 실패하는 경우]] |

표는 길 안내이며 annotation이나 Pod phase만으로 exec 대상을 확정하지 않는다. Kubernetes 1.26 `kubectl exec`에서 `-c`는 선택 사항일 수 있지만, 이 문서에서는 자동 선택을 배제하기 위해 실제 이름을 항상 명시한다.

## 1. Pod UID와 phase를 먼저 고정

진입 증거는 Pod 이름은 같지만 수집 시각의 UID·phase·deletionTimestamp 또는 node가 이전 오류 증거와 다를 때다. 필요한 값은 API 자동값 `POD_UID`, `NODE`, `PHASE`, `DELETION_TIMESTAMP`이며 위 자동 수집의 출처를 재사용한다.

exec 직전에 UID gate가 포함된 읽기 명령 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r '"uid=" + (.metadata.uid // "-") + "\tphase=" + (.status.phase // "-") + "\tdeletionTimestamp=" + (.metadata.deletionTimestamp // "-") + "\tnode=" + (.spec.nodeName // "-")' <<<"$POD_SNAPSHOT"; fi`을 실행한다. 성공 gate는 UID·phase·node가 빈 값이 아니고 자동 수집 UID와 일치하는 것이다. UID가 다르면 재생성 race이므로 새 목록을 다시 수집하고 이전 containerID·오류와 섞지 않는다.

`NotFound`는 다른 namespace를 추측하지 말고 대상 identity를 다시 고정하는 의미다. `Succeeded`·`Failed`는 1.26 completed Pod 차단 경로이므로 exec를 반복하지 않는다. `Unknown` 또는 deletion timestamp가 있으면 상태가 불명확하므로 중단한다. `Pending`은 자동으로 exec 불가가 아니며 init이 실제 `Running`인지 2절에서 대조한다. 이 명령의 성공은 API object identity만 보장하고 kubelet stream이나 application 정상은 보장하지 않는다.

## 2. container 종류와 state를 분리

진입 증거는 오류의 container 이름이 spec에 없거나, regular·init·ephemeral 중 다른 종류에만 있거나, state가 `Waiting`·`Terminated`인 경우다. 이 절의 운영자 선택값은 API 출력과 승인된 진단 목적을 확인한 뒤 `CONTAINER_KIND`, `CONTAINER`, `READ_ONLY_COMMAND`에 한 번 입력한다. `READ_ONLY_COMMAND`는 image 계약으로 비파괴 동작이 확인된 argv여야 한다.

**선택값 입력 — 확인한 후보를 같은 Bash에 한 번 등록**

`CONTAINER_KIND='PASTE_CONTAINER_KIND_HERE'; CONTAINER='PASTE_CONTAINER_HERE'; READ_ONLY_COMMAND='PASTE_READ_ONLY_COMMAND_HERE'`

`regular`, `init`, `ephemeral` 이외의 종류, 빈 이름 또는 승인되지 않은 command이면 중단한다. 선택값을 검증하고 실제 주체의 권한을 같은 단계에서 확인한다.

**선택·권한 gate — 아래 한 줄 전체를 복사**

`unset SELECTION_READY AUTH_READY AUTH_RESULT AUTH_OUTPUT AUTH_RC AUTH_DECISION COMMAND_READY EXEC_ARGV; SELECTION_READY=false; AUTH_READY=false; COMMAND_READY=false; EXEC_ARGV=(); if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif [ "$CONTAINER_KIND" != regular ] && [ "$CONTAINER_KIND" != init ] && [ "$CONTAINER_KIND" != ephemeral ]; then printf '중단: container 종류가 regular|init|ephemeral이 아님 kind=%s\n' "$CONTAINER_KIND" >&2; elif [ -z "$CONTAINER" ] || [ -z "$READ_ONLY_COMMAND" ]; then printf '%s\n' '중단: container와 read-only command를 확인한다.' >&2; elif pod_uid_gate && jq -e --arg kind "$CONTAINER_KIND" --arg c "$CONTAINER" 'if $kind == "regular" then any(.spec.containers[]?; .name == $c) and any(.status.containerStatuses[]?; .name == $c and .state.running != null and (.containerID // "") != "") elif $kind == "init" then any(.spec.initContainers[]?; .name == $c) and any(.status.initContainerStatuses[]?; .name == $c and .state.running != null and (.containerID // "") != "") elif $kind == "ephemeral" then any(.spec.ephemeralContainers[]?; .name == $c) and any(.status.ephemeralContainerStatuses[]?; .name == $c and .state.running != null and (.containerID // "") != "") else false end' <<<"$POD_SNAPSHOT" >/dev/null && auth_can_i --context "$CONTEXT" auth can-i create pods/"$POD" --subresource=exec -n "$NS"; then AUTH_RESULT="$AUTH_OUTPUT"; if [ "$AUTH_DECISION" = yes ]; then read -r -a EXEC_ARGV <<<"$READ_ONLY_COMMAND"; if [ "${#EXEC_ARGV[@]}" -gt 0 ]; then AUTH_READY=true; COMMAND_READY=true; SELECTION_READY=true; export CONTAINER_KIND CONTAINER READ_ONLY_COMMAND AUTH_RESULT; printf 'SELECTION_READY=true AUTH_READY=true kind=%s container=%s command_argv_count=%s\n' "$CONTAINER_KIND" "$CONTAINER" "${#EXEC_ARGV[@]}"; else printf '%s\n' '중단: command argv가 비어 있다.' >&2; fi; elif [ "$AUTH_DECISION" = no ]; then printf '중단: pods/exec 권한 거부 RBAC로 이관 rc=%s output=%s\n' "$AUTH_RC" "$AUTH_OUTPUT" >&2; else printf '중단: auth API 호출 실패 rc=%s output=%s\n' "$AUTH_RC" "${AUTH_OUTPUT:--}" >&2; fi; else printf '%s\n' '중단: 현재 UID·spec/status 대조 또는 auth API 호출 실패. 부분 선택을 남기지 않는다.' >&2; fi`

성공 gate는 선택한 이름이 해당 종류의 spec와 status에 동시에 있고 `state.running`·containerID가 있으며 같은 API context의 `auth can-i`가 `yes`인 것이다. `yes`는 RBAC 판단만 보장하고 실제 API upgrade·kubelet·runtime·application 성공을 보장하지 않는다. 이름이 없으면 `container not found`, status가 없거나 `Running`이 아니면 lifecycle 문제로 분기한다.

**선택 container ID 등록 — debug action gate가 재사용**

`unset CONTAINER_ID; CONTAINER_ID_READY=false; if [ "$SELECTION_READY" != true ] || ! pod_uid_gate; then printf '%s\n' '중단: SELECTION_READY 또는 UID gate가 아니다.' >&2; elif CONTAINER_ID="$(jq -r --arg kind "$CONTAINER_KIND" --arg c "$CONTAINER" 'if $kind == "regular" then [.status.containerStatuses[]? | select(.name==$c) | .containerID][0] // empty elif $kind == "init" then [.status.initContainerStatuses[]? | select(.name==$c) | .containerID][0] // empty elif $kind == "ephemeral" then [.status.ephemeralContainerStatuses[]? | select(.name==$c) | .containerID][0] // empty else empty end' <<<"$POD_SNAPSHOT")" && [ -n "$CONTAINER_ID" ]; then CONTAINER_ID_READY=true; export CONTAINER_ID; printf 'CONTAINER_ID_READY=true pod_uid=%s kind=%s container=%s container_id=%s\n' "$POD_UID" "$CONTAINER_KIND" "$CONTAINER" "$CONTAINER_ID"; else printf '%s\n' '중단: 선택 container의 현재 containerID 조회 실패.' >&2; fi`

연결 경로는 **같은 실행 host의 Bash → kubectl client → kubeconfig가 지정한 API server HTTPS endpoint와 HTTP upgrade → 대상 node의 kubelet HTTPS streaming endpoint → node-local CRI runtime socket → 선택한 container process**다. API 주소와 port는 kubeconfig·node 설정의 실제 값을 뜻하고, runtime socket은 확인된 kubelet 설정을 뜻한다. 어느 한 hop의 성공도 다음 hop이나 application 정상을 보장하지 않는다.

선택한 regular 또는 실제 `Running` init·ephemeral의 이름·Pod UID·containerID가 직전 확인과 일치하고 `COMMAND_READY=true`일 때만 비파괴 exec를 한 번 시도한다. 실행 명령은 `if [ "$SELECTION_READY" != true ] || [ "$AUTH_READY" != true ] || [ "$COMMAND_READY" != true ] || ! exec_identity_gate "$CONTAINER_KIND" "$CONTAINER" "$CONTAINER_ID"; then printf '%s\n' '중단: selection/auth/command/UID/container kind/state/containerID gate가 준비되지 않았다.' >&2; else kubectl --context "$CONTEXT" exec "$POD" -n "$NS" -c "$CONTAINER" -- "${EXEC_ARGV[@]}"; fi`이다.

성공 gate는 command가 exit 0이고 출력이 비민감 범위인 것이다. `executable file not found`·`not found`는 대상 container 부재로 단정하지 말고 [[02. 워크로드/01. Pod/32. Pod exec 명령을 찾을 수 없는 경우|Pod exec 명령을 찾을 수 없는 경우]]로 이동한다. `Forbidden`은 34번 런북, 현재 spec/status와 모순되는 `container not found` 또는 `unable to upgrade connection`은 33번 런북으로 이동한다. Secret·token·개인정보가 출력되면 즉시 중단한다.

`regular` container는 `.spec.containers`와 `.status.containerStatuses`에 있고 Running이어야 한다. `init`은 별도 spec/status를 사용하며 Pod phase가 `Pending`이어도 실제 init이 Running이고 containerID가 있을 때만 승인된 read-only exec를 검토한다. Waiting·Terminated·exit code 0으로 끝난 init에는 exec하지 않고 [[02. 워크로드/01. Pod/05. Pod가 Init 단계에서 진행되지 않는 경우|Pod가 Init 단계에서 진행되지 않는 경우]]로 이동한다. `ephemeral`은 별도 status가 Running이고 containerID가 있어야 하며, 그렇지 않으면 상태 변경 없이 debug 담당자와 재평가한다.

## 3. 대상이 맞는데 upgrade가 실패하는 경우

진입 증거는 UID·container 이름·종류·containerID·`state.running`이 유지되는데 `unable to upgrade connection`, `Upgrade request required` 또는 현재 spec/status와 모순되는 `container not found`가 반복되는 경우다. 최초 필요값은 자동 등록된 identity와 직전 command 결과이며 다시 입력하지 않는다.

범위를 제한한 재확인 명령은 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r --arg c "$CONTAINER" '[ (.metadata.uid + "\t" + (.status.phase // "-")), (.status.containerStatuses[]? | select(.name==$c) | "regular=" + .name + " running=" + (.state.running.startedAt // "-") + " containerID=" + (.containerID // "-")), (.status.initContainerStatuses[]? | select(.name==$c) | "init=" + .name + " running=" + (.state.running.startedAt // "-") + " containerID=" + (.containerID // "-")), (.status.ephemeralContainerStatuses[]? | select(.name==$c) | "ephemeral=" + .name + " running=" + (.state.running.startedAt // "-") + " containerID=" + (.containerID // "-")) ] | .[]' <<<"$POD_SNAPSHOT"; fi`이다. 성공 gate는 이전 UID·phase·containerID와 일치하는 한 종류의 Running 행이다. 빈 출력은 status 부재 또는 query 조건 불일치이지 stream 정상의 증거가 아니다.

identity가 바뀌었으면 1절 race로 돌아간다. 모두 유지되고 upgrade 오류가 반복되면 API server→kubelet 인증, kubelet 도달성, runtime stream을 [[02. 워크로드/01. Pod/33. Pod exec 연결이 실패하는 경우|Pod exec 연결이 실패하는 경우]]로 이관한다. `Forbidden`이면 권한 런북으로 이동하며 TLS 검증 우회나 무조건 재시도는 하지 않는다.

## 4. 승인된 ephemeral debug 경계

진입 증거는 regular exec로 필요한 비민감 증거를 얻을 수 없고, 구체적인 도구가 원인 판정에 필수인 경우다. Pod phase가 `Running`이고 대상 container가 Running일 때만 검토한다. 이 절에서 처음 쓰는 운영자 선택값은 담당자 승인과 digest를 확인한 뒤 입력한다.

**승인된 debug image 입력 — digest를 확인한 뒤 한 번 등록**

`APPROVED_DEBUG_IMAGE='PASTE_APPROVED_DEBUG_IMAGE_HERE'`

실행 전 trigger와 직접 근거, context·namespace·Pod UID·대상 container의 Running state, image digest, `patch pods/$POD --subresource=ephemeralcontainers`와 `create pods/$POD --subresource=attach` 권한, quota·NetworkPolicy·node 자원·민감정보 비노출 계획, 담당자·승인자·incident/change ID, 중단 조건과 종료·정리 계획을 기록한다.

**debug 권한 gate — 아래 한 줄 전체를 복사**

**debug action gate 등록 — 상태 변경 직전에 재사용**

`debug_action_gate(){ local kind="$1" c="$2" expected="$3" patch_decision attach_decision; DEBUG_ACTION_READY=false; if [ -z "$expected" ] || ! pod_uid_gate; then DEBUG_READY=false; AUTH_READY=false; SELECTION_READY=false; COMMAND_READY=false; CONTAINER_ID_READY=false; printf '%s\n' '중단: debug action 직전 current UID 또는 containerID가 없다.' >&2; elif ! jq -e --arg kind "$kind" --arg c "$c" --arg expected "$expected" '(.status.phase == "Running") and ((.metadata.deletionTimestamp // "") == "") and (if $kind == "regular" then any(.status.containerStatuses[]?; .name == $c and .state.running != null and .containerID == $expected) elif $kind == "init" then any(.status.initContainerStatuses[]?; .name == $c and .state.running != null and .containerID == $expected) elif $kind == "ephemeral" then any(.status.ephemeralContainerStatuses[]?; .name == $c and .state.running != null and .containerID == $expected) else false end)' <<<"$POD_SNAPSHOT" >/dev/null; then DEBUG_READY=false; AUTH_READY=false; SELECTION_READY=false; COMMAND_READY=false; CONTAINER_ID_READY=false; printf '%s\n' '중단: debug action 직전 phase/deletionTimestamp/container Running·containerID gate 실패.' >&2; else auth_can_i --context "$CONTEXT" auth can-i patch pods/"$POD" --subresource=ephemeralcontainers -n "$NS"; patch_decision="$AUTH_DECISION"; DEBUG_ACTION_PATCH_RESULT="$AUTH_OUTPUT"; DEBUG_ACTION_PATCH_RC="$AUTH_RC"; DEBUG_ACTION_PATCH_DECISION="$patch_decision"; if [ "$patch_decision" = yes ]; then auth_can_i --context "$CONTEXT" auth can-i create pods/"$POD" --subresource=attach -n "$NS"; attach_decision="$AUTH_DECISION"; DEBUG_ACTION_ATTACH_RESULT="$AUTH_OUTPUT"; DEBUG_ACTION_ATTACH_RC="$AUTH_RC"; DEBUG_ACTION_ATTACH_DECISION="$attach_decision"; fi; if [ "$patch_decision" = yes ] && [ "$attach_decision" = yes ]; then DEBUG_ACTION_READY=true; return 0; elif [ "$patch_decision" = no ] || [ "$attach_decision" = no ]; then DEBUG_READY=false; printf '중단: debug action 직전 RBAC 거부 patch=%s attach=%s\n' "${DEBUG_ACTION_PATCH_RESULT:--}" "${DEBUG_ACTION_ATTACH_RESULT:--}" >&2; else DEBUG_READY=false; printf '중단: debug action 직전 auth/API 확인 실패 patch=%s attach=%s\n' "${DEBUG_ACTION_PATCH_RESULT:--}" "${DEBUG_ACTION_ATTACH_RESULT:--}" >&2; fi; fi; return 1; }`

`unset DEBUG_READY DEBUG_PATCH_RESULT DEBUG_PATCH_RC DEBUG_PATCH_DECISION DEBUG_ATTACH_RESULT DEBUG_ATTACH_RC DEBUG_ATTACH_DECISION; DEBUG_READY=false; if [ "$SELECTION_READY" != true ] || [ "$AUTO_READY" != true ] || [ "$PHASE" != Running ] || ! pod_uid_gate; then printf '%s\n' '중단: Running identity와 selection gate가 준비되지 않았다.' >&2; elif ! printf '%s' "$APPROVED_DEBUG_IMAGE" | grep -Eq '@sha256:[0-9a-fA-F]{64}$'; then printf '%s\n' '중단: 승인된 immutable digest가 아니다.' >&2; elif auth_can_i --context "$CONTEXT" auth can-i patch pods/"$POD" --subresource=ephemeralcontainers -n "$NS"; then DEBUG_PATCH_RESULT="$AUTH_OUTPUT"; DEBUG_PATCH_RC="$AUTH_RC"; DEBUG_PATCH_DECISION="$AUTH_DECISION"; if [ "$DEBUG_PATCH_DECISION" = yes ]; then auth_can_i --context "$CONTEXT" auth can-i create pods/"$POD" --subresource=attach -n "$NS"; DEBUG_ATTACH_RESULT="$AUTH_OUTPUT"; DEBUG_ATTACH_RC="$AUTH_RC"; DEBUG_ATTACH_DECISION="$AUTH_DECISION"; fi; if [ "$DEBUG_PATCH_DECISION" = yes ] && [ "$DEBUG_ATTACH_DECISION" = yes ]; then DEBUG_READY=true; export APPROVED_DEBUG_IMAGE; printf 'DEBUG_READY=true patch=%s attach=%s image_digest=verified\n' "$DEBUG_PATCH_RESULT" "$DEBUG_ATTACH_RESULT"; elif [ "$DEBUG_PATCH_DECISION" = no ] || [ "$DEBUG_ATTACH_DECISION" = no ]; then printf '중단: debug RBAC 권한 거부 patch=%s patch_rc=%s attach=%s attach_rc=%s\n' "${DEBUG_PATCH_RESULT:--}" "${DEBUG_PATCH_RC:--}" "${DEBUG_ATTACH_RESULT:--}" "${DEBUG_ATTACH_RC:--}" >&2; else printf '중단: debug auth/API 확인 실패 patch=%s patch_rc=%s attach=%s attach_rc=%s\n' "${DEBUG_PATCH_RESULT:--}" "${DEBUG_PATCH_RC:--}" "${DEBUG_ATTACH_RESULT:--}" "${DEBUG_ATTACH_RC:--}" >&2; fi; fi`

`DEBUG_READY=true`와 별도 승인 기록이 모두 있어야 실행한다. 승인된 경우의 상태 변경 명령은 `if [ "$DEBUG_READY" != true ] || ! exec_identity_gate "$CONTAINER_KIND" "$CONTAINER" "$CONTAINER_ID" || ! debug_action_gate "$CONTAINER_KIND" "$CONTAINER" "$CONTAINER_ID"; then printf '%s\n' '중단: DEBUG_READY 또는 debug action 직전 UID/phase/container/RBAC gate가 아니다.' >&2; else kubectl --context "$CONTEXT" debug "pod/$POD" -n "$NS" --target="$CONTAINER" --image="$APPROVED_DEBUG_IMAGE" --profile=legacy -it -- sh; fi`이다. `--target`은 기존 process namespace target이고 `-c` exec 대상과 같은 의미가 아니다. ephemeral container 추가는 기존 Pod의 상태 변경이며 Pod UID는 유지될 수 있지만 resourceVersion·spec/status·자원 사용은 바뀐다. ephemeral container는 기존 Pod에서 제거할 수 없으므로 rollback은 추가하지 않는 것이며, 이미 추가했다면 session 종료·정리 결과·서비스 영향 관찰을 rollback 기록으로 남긴다.

`no` 또는 API·인증·연결 오류면 실행하지 않고 34번 런북 또는 담당자에게 이관한다. `yes`도 승인·digest·정리 계획을 대신하지 않는다. 민감정보 노출, 자원 압박, UID 변화, 서비스 영향이 보이면 즉시 중단하고 생성·종료·정리 증거를 보존한다. 종료된 init을 대신하기 위해 ephemeral debug를 붙이지 않는다.

## 정상화와 증거 보존

정상화는 원인 경로를 역순으로 확인한다. 선택한 Pod UID·container 종류·이름·containerID와 Running state, auth 결과, 비파괴 exec의 exit 0을 확인한 뒤 실제 서비스 요청·핵심 기능·원래 regular container의 Ready와 restart 증가 중단을 별도로 확인한다. `Running`, `Ready`, `can-i=yes` 또는 ephemeral container의 Running만으로 정상화하지 않는다.

동일 대상 확인 명령은 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r '"POD=" + (.metadata.name // "-") + "\tUID=" + (.metadata.uid // "-") + "\tPHASE=" + (.status.phase // "-") + "\tREADY=" + ([.status.containerStatuses[]?.ready] | map(tostring) | join(",")) + "\tRESTARTS=" + ([.status.containerStatuses[]?.restartCount] | map(tostring) | join(",")) + "\tNODE=" + (.spec.nodeName // "-")' <<<"$POD_SNAPSHOT"; fi`이며 UID·관측 시각을 먼저 비교한다. Event를 확인해야 할 때만 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else kubectl --context "$CONTEXT" get events -n "$NS" --field-selector involvedObject.kind=Pod,involvedObject.name="$POD",involvedObject.uid="$POD_UID",type=Warning --sort-by=.metadata.creationTimestamp -o custom-columns='CREATED:.metadata.creationTimestamp,FIRST:.firstTimestamp,LAST:.lastTimestamp,EVENT-TIME:.eventTime,REASON:.reason,MESSAGE:.message'; fi`를 한 번 실행한다. 명령 실패는 조회 실패이고 빈 결과는 Warning 부재를 단독 보장하지 않는다. 새 Warning·restart 증가·기능 실패가 있으면 해당 계층 런북으로 이동한다.

보존 항목은 UTC 관측 시각, context, namespace, Pod UID·phase·node, container 종류·이름·state·containerID·restartCount, 오류 문자열, auth 결과, 비파괴 command, debug 승인·image digest·정리 결과다. Secret·token·환경 변수 전체·인증서 개인키·민감 출력은 보존하지 않는다.

## Prometheus 빠른 관측

아래 PromQL은 문서에서 직접 고치지 않는다. 같은 Bash에서 등록된 `NS`, `POD_RE`, 필요 시 `CONTAINER_RE`로 완성 문자열을 생성하고 출력된 한 줄만 Prometheus 또는 Grafana에 붙여 넣는다. `POD_RE`와 `CONTAINER_RE`는 이름의 `.`, `+`, `[` 같은 문자를 escaped한 계산 후보이며 bounded 출력으로 확인한다.

**Pod·container regex 등록 — 아래 한 줄 전체를 복사**

`unset QUERY_READY POD_RE CONTAINER_RE; QUERY_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else POD_RE_TMP="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; if [ -z "$POD_RE_TMP" ]; then printf '%s\n' '중단: Pod regex 생성 실패' >&2; else POD_RE="^${POD_RE_TMP}$"; if [ "$SELECTION_READY" = true ]; then CONTAINER_RE_TMP="$(printf '%s' "$CONTAINER" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; if [ -z "$CONTAINER_RE_TMP" ]; then printf '%s\n' '중단: container regex 생성 실패' >&2; else CONTAINER_RE="^${CONTAINER_RE_TMP}$"; QUERY_READY=true; export POD_RE CONTAINER_RE; printf 'QUERY_READY=true POD_RE=%s CONTAINER_RE=%s\n' "${POD_RE:0:256}" "${CONTAINER_RE:0:256}"; fi; else QUERY_READY=true; export POD_RE; printf 'QUERY_READY=true POD_RE=%s container=selection_required\n' "${POD_RE:0:256}"; fi; fi; fi`

`QUERY_READY=true`가 아니면 쿼리를 생성하지 않는다. metric 이름·label이 중앙 관측에 실제 존재하는지 확인하지 않은 빈 결과는 정상이나 0이 아니다. query API 자체의 권한·transport 오류, metric 미수집, label 불일치, 조회 범위 문제를 분리한다.

**regular·init·ephemeral 후보 PromQL 생성**

`if [ "$QUERY_READY" != true ]; then printf '%s\n' '중단: QUERY_READY가 아니다.' >&2; elif [ -z "${CONTAINER_RE:-}" ]; then printf 'kube_pod_container_info{namespace="%s",pod=~"%s",uid="%s"}\n' "$NS" "$POD_RE" "$POD_UID"; else printf 'kube_pod_container_info{namespace="%s",pod=~"%s",container=~"%s",uid="%s"}\nkube_pod_container_status_running{namespace="%s",pod=~"%s",container=~"%s",uid="%s"}==1\nkube_pod_container_status_ready{namespace="%s",pod=~"%s",container=~"%s",uid="%s"}==1\n' "$NS" "$POD_RE" "$CONTAINER_RE" "$POD_UID" "$NS" "$POD_RE" "$CONTAINER_RE" "$POD_UID" "$NS" "$POD_RE" "$CONTAINER_RE" "$POD_UID"; fi`

`Running`·`Ready` metric은 regular container와 수집 label 범위만 보여 줄 수 있으며 init·ephemeral 구분, `pods/exec` 인가, API server→kubelet stream 성공을 증명하지 않는다. Prometheus query가 실패하면 API/권한 문제로 이동하고, 성공했지만 series가 없으면 metric 부재·label 불일치·scrape 범위를 확인한다.
