# Pod STATUS가 CreateContainerConfigError인 경우

## 입력값과 빠른 수집

Secret 값, token, 인증서, password와 literal env 원문은 입력·출력·기록하지 않는다. 모든 값은 다음 네 종류로 구분한다.

| 종류 | 값 | 출처와 사용 시점 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 승인된 namespace와 Pod 이름을 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `NODE`, `PHASE`, `OBSERVED_AT`, `SERVICE_ACCOUNT`, `OWNER_CANDIDATES`, `CONTAINER_CANDIDATES`, `REF_CANDIDATES`, `CONTAINER_ID`, `WORKLOAD_SELECTOR` | Pod·owner API에서 현재 identity와 참조 관계를 등록한다. `WORKLOAD_SELECTOR`는 owner의 실제 selector를 canonical registration한다. |
| 계산 후보값 | `VERIFY_POD` | 최초에는 `POD`, 변경 뒤에는 API로 확인한 새 Pod를 가리킨다. 자동 선택이 아니라 변경 전후 identity gate를 통과해야 한다. |
| 운영자 선택값 | `CONTAINER_KIND`, `CONTAINER`, `SECRET_NAME`, `SECRET_KEY`, `CONFIGMAP_NAME`, `CONFIGMAP_KEY`, `OWNER_KIND`, `OWNER_NAME`, `ROLLBACK_REVISION`, `ROLLBACK_IMAGE_DIGEST`, `APPROVAL_ID`, `NEW_POD` | 출력·Event·승인 원본을 확인한 뒤 해당 분기 직전에 한 번 입력한다. rollback revision과 image digest는 별도 승인값이다. 복수 후보를 첫 번째로 선택하지 않는다. Secret/ConfigMap key는 선택 container의 실제 ref와 일치시킨다. |

### 1. 실행 위치·도구·최초 입력

local 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. `kubectl`은 실행 host → Kubernetes API server HTTPS → Pod object 경로를 사용한다. `kubectl get/describe/events` read 권한이 없으면 다음 단계로 진행하지 않는다. `describe`와 Event 성공은 kubelet의 volume/config 해석, container 생성, application 정상까지 보장하지 않는다. `sh`, PowerShell, CMD에서는 실행하지 않는다.

**Bash와 필수 local 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep date head; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 local 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 다음 단계로 진행하지 않는다. API 호출이 실패하면 이전 참조 목록이나 stale Pod 값을 사용하지 않는다.

**최초 입력과 이전 상태 초기화 — 같은 Bash에서 한 번 실행**

`INPUT_READY=true`가 아니면 namespace·Pod 이름·context·조회 권한을 확인한다. namespace를 모를 때만 승인된 범위에서 Pod를 탐색하고 정확한 NS와 POD로 초기화 명령을 다시 실행한다.

표는 길 안내다. `valueFrom`은 한 key를 한 env에, `envFrom`은 key 집합을, volume은 파일을 주입하며 projected volume은 여러 source를 합친다. 이름·key·optional·items·path를 서로 다른 참조 방식으로 바꿔 판단하지 않는다.

### Secret 참조 오류

진입 증거: Event에 `secret "NAME" not found`, `couldn't find key KEY in Secret NAME`, `could not find key`가 있고 Pod spec의 Secret ref와 같은 namespace에서 확인될 때다.

필수값: `$NS`, `$POD`, `$POD_UID`, `$REF_CANDIDATES`를 먼저 확인하고 Event와 Pod spec에 실제로 나타난 Secret 이름을 선택한다. Secret data value는 필요하지 않다.

**Secret 이름·type·key metadata 확인 — 아래 한 줄 전체를 복사**

`SECRET_NAME='PASTE_SECRET_NAME_HERE'; SECRET_KEY='PASTE_SECRET_KEY_HERE'; SECRET_READY=false; POD_JSON=''; SECRET_TYPE_TMP=''; SECRET_KEYS_TMP=''; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && pod_uid_guard "$POD_JSON" "$POD_UID" && jq -e --arg c "$CONTAINER" --arg ck "$CONTAINER_KIND" --arg n "$SECRET_NAME" --arg k "$SECRET_KEY" '. as $pod | (if $ck == "regular" then ($pod.spec.containers // []) else ($pod.spec.initContainers // []) end | map(select(.name == $c))[0] // {}) as $container | (any($container.env[]?; .valueFrom.secretKeyRef? | .name == $n and .key == $k) or any($container.envFrom[]?; .secretRef? | .name == $n and $k == "NONE") or any($container.volumeMounts[]?; .name as $mount_name | any($pod.spec.volumes[]?; .name == $mount_name and ((.secret? != null and .secret.secretName == $n and ($k == "NONE" or any(.secret.items[]?; .key == $k))) or (.projected? != null and any(.projected.sources[]?; .secret? != null and .secret.name == $n and ($k == "NONE" or any(.secret.items[]?; .key == $k))))))))' <<<"$POD_JSON" >/dev/null && SECRET_TYPE_TMP="$(kubectl get secret "$SECRET_NAME" -n "$NS" -o jsonpath='{.type}')" && SECRET_KEYS_TMP="$(kubectl get secret "$SECRET_NAME" -n "$NS" -o go-template='{{range $key, $value := .data}}{{$key}} {{end}}')"; then if [ "$SECRET_KEY" = NONE ] || [[ " $SECRET_KEYS_TMP " == *" $SECRET_KEY "* ]]; then SECRET_READY=true; export SECRET_NAME SECRET_KEY; printf 'Secret 이름=%s key=%s namespace=%s type=%s key 목록=%s\n' "$SECRET_NAME" "$SECRET_KEY" "$NS" "$SECRET_TYPE_TMP" "${SECRET_KEYS_TMP:--}"; else printf '중단: Secret object에 선택 key가 없다.\n' >&2; fi; else printf '중단: 선택 container의 실제 Secret ref/envFrom/volume key와 일치하지 않거나 Secret 조회 실패.\n' >&2; fi`

성공 gate는 동일 namespace의 Secret 존재, type, key 이름을 실제 Pod의 `secretKeyRef`, `envFrom`, volume/projected source와 대조하는 것이다. `not found`는 같은 namespace의 부재·이름 불일치, `Forbidden`은 현재 주체의 RBAC 거부일 수 있다. key 없음은 Secret은 있으나 선언 key가 없는 것이다. `optional=true` 참조 하나의 부재는 필수 실패 원인이 아닐 수 있으므로 다른 필수 참조를 계속 확인한다.

실패·빈 결과 의미: 빈 key 목록은 key 없음 또는 조회 field 문제이며 값이 비어 있다는 뜻이 아니다. 다음 행동은 Secret 관리 owner·[[26. Pod가 ConfigMap·Secret을 찾지 못하는 경우]]의 RBAC/API audit 경계로 이관하는 것이다. Secret 값·token·certificate는 기록하지 않는다.

### ConfigMap 참조 오류

진입 증거: Event에 `configmap "NAME" not found` 또는 `couldn't find key KEY in ConfigMap NAME`가 있을 때다.

필수값: `$NS`, `$POD`, `$REF_CANDIDATES`와 Event·Pod spec에서 확인한 ConfigMap 이름을 사용한다. `data`와 `binaryData`의 key 이름만 필요하다.

**ConfigMap key metadata 확인 — 아래 한 줄 전체를 복사**

`CONFIGMAP_NAME='PASTE_CONFIGMAP_NAME_HERE'; CONFIGMAP_KEY='PASTE_CONFIGMAP_KEY_HERE'; CONFIGMAP_READY=false; POD_JSON=''; CONFIGMAP_DATA_KEYS_TMP=''; CONFIGMAP_BINARY_KEYS_TMP=''; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && pod_uid_guard "$POD_JSON" "$POD_UID" && jq -e --arg c "$CONTAINER" --arg ck "$CONTAINER_KIND" --arg n "$CONFIGMAP_NAME" --arg k "$CONFIGMAP_KEY" '. as $pod | (if $ck == "regular" then ($pod.spec.containers // []) else ($pod.spec.initContainers // []) end | map(select(.name == $c))[0] // {}) as $container | (any($container.env[]?; .valueFrom.configMapKeyRef? | .name == $n and .key == $k) or any($container.envFrom[]?; .configMapRef? | .name == $n and $k == "NONE") or any($container.volumeMounts[]?; .name as $mount_name | any($pod.spec.volumes[]?; .name == $mount_name and ((.configMap? != null and .configMap.name == $n and ($k == "NONE" or any(.configMap.items[]?; .key == $k))) or (.projected? != null and any(.projected.sources[]?; .configMap? != null and .configMap.name == $n and ($k == "NONE" or any(.configMap.items[]?; .key == $k))))))))' <<<"$POD_JSON" >/dev/null && CONFIGMAP_DATA_KEYS_TMP="$(kubectl get configmap "$CONFIGMAP_NAME" -n "$NS" -o go-template='{{range $key, $value := .data}}{{$key}} {{end}}')" && CONFIGMAP_BINARY_KEYS_TMP="$(kubectl get configmap "$CONFIGMAP_NAME" -n "$NS" -o go-template='{{range $key, $value := .binaryData}}{{$key}} {{end}}')"; then if [ "$CONFIGMAP_KEY" = NONE ] || [[ " $CONFIGMAP_DATA_KEYS_TMP $CONFIGMAP_BINARY_KEYS_TMP " == *" $CONFIGMAP_KEY "* ]]; then CONFIGMAP_READY=true; export CONFIGMAP_NAME CONFIGMAP_KEY; printf 'ConfigMap 이름=%s key=%s namespace=%s data key=%s binaryData key=%s\n' "$CONFIGMAP_NAME" "$CONFIGMAP_KEY" "$NS" "${CONFIGMAP_DATA_KEYS_TMP:--}" "${CONFIGMAP_BINARY_KEYS_TMP:--}"; else printf '중단: ConfigMap object에 선택 key가 없다.\n' >&2; fi; else printf '중단: 선택 container의 실제 ConfigMap ref/envFrom/volume key와 일치하지 않거나 ConfigMap 조회 실패.\n' >&2; fi`

성공 gate는 선언 방식에 맞는 key가 `data` 또는 `binaryData`에 있는지, 이름·namespace·optional·items가 일치하는지 확인하는 것이다. `optional=true` 부재는 그 참조 하나의 필수 실패가 아닐 수 있다. `binaryData` key를 env text 계약으로 재사용하지 않고 volume/projected source 계약으로 대조한다. key가 맞아도 애플리케이션이 기대하는 텍스트·바이너리 형식까지 보장하지 않는다.

### 일반 env, envFrom과 namespace 확인

진입 증거: Event가 `envFrom`, `secretKeyRef`, `configMapKeyRef` 또는 이름·key·prefix 불일치를 가리킬 때다.

필수값: `$REF_CANDIDATES`와 최초 API 출력의 일반 container·init container별 참조를 재사용한다. 모든 참조는 Pod namespace에서 해석된다.

**Pod의 env 참조 범위 재확인 — 아래 한 줄 전체를 복사**

성공 gate는 실제 Pod spec과 선언 원본의 이름·key·optional·prefix가 일치하는 것이다. literal env는 Secret/ConfigMap ref가 아니지만 자격 증명이 포함될 수 있으므로 출력하지 않는다. `Forbidden`·빈 결과는 object 부재나 오류 없음으로 해석하지 않고 RBAC/API audit 또는 owner template로 이동한다.

### projected volume 전체 source 확인

진입 증거: Event가 `MountVolume.SetUp`, `projected`, `secret`, `configmap` 또는 token projection을 가리킬 때다.

필수값: `$POD`, `$NS`, `$POD_UID`와 초기 `REF_CANDIDATES`다. 첫 source만 보지 않고 모든 projected source를 확인한다.

연결 경로: 작업 PC → API server HTTPS → Pod volume spec → kubelet volume manager → Secret/ConfigMap/Token source → container filesystem. API object 조회 성공은 kubelet mount와 process config 주입 성공을 보장하지 않는다.

**전체 volume·projected source·mount 관계 — 아래 한 줄 전체를 복사**

성공 gate는 모든 source의 이름·key·optional·items key/path가 metadata 조회와 일치하고 mount가 어느 container에 연결되는지 보이는 것이다. optional이 true인 source가 없으면 다른 필수 source를 찾는다. source 전부가 맞는데 `MountVolume.SetUp`이 지속되면 config 해석만으로 확정하지 말고 volume mount 런북과 kubelet 계층으로 이관한다.

### ServiceAccount token projection

진입 증거: Event에 `service account token`, `token projection`, `MountVolume.SetUp`가 있거나 projected source가 ServiceAccount token일 때다.

필수값: `$SERVICE_ACCOUNT`는 Pod API에서 자동 등록했다. Pod의 실제 service account가 namespace의 `default`인지도 확인한다.

**Pod와 ServiceAccount metadata 대조 — 아래 한 줄 전체를 복사**

`if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && pod_uid_guard "$POD_JSON" "$POD_UID" && jq -r '"serviceAccount=" + (.spec.serviceAccountName // "default") + " automount=" + ((.spec.automountServiceAccountToken // false)|tostring) + " imagePullSecrets=" + ([.spec.imagePullSecrets[]?.name] | join(","))' <<<"$POD_JSON" && kubectl get serviceaccount "$SERVICE_ACCOUNT" -n "$NS" -o go-template='name={{.metadata.name}}{{" automount="}}{{.automountServiceAccountToken}}{{" imagePullSecrets="}}{{range .imagePullSecrets}}{{.name}} {{end}}{{"\n"}}'; then printf 'ServiceAccount gate=true name=%s namespace=%s pod_uid=%s\n' "$SERVICE_ACCOUNT" "$NS" "$POD_UID"; else printf '%s\n' '중단: Pod UID 검증 또는 Pod/ServiceAccount metadata 조회 실패.' >&2; fi`

`serviceAccountName`이 비어 있으면 실제 Pod에서 `default`가 사용될 수 있다. imagePullSecrets는 image pull 인증 이름일 뿐 RBAC, 자동 token mount, projected token, env/volume Secret ref를 대신하지 않는다. ## 복구 전 안전 gate와 제한적 상태 변경

원인 확정 전 Pod 삭제, 무조건 restart, patch, edit, rollout을 실행하지 않는다. Secret/ConfigMap 관리 원본 또는 owner template을 승인된 변경 시스템에서 수정한다. Secret 값은 문서·터미널에 남기지 않는다. Job/CronJob은 외부 재호출과 중복 실행 여부가 확인되지 않으면 재실행하지 않는다.

return 0; fi; printf '중단: target revision ReplicaSet·Deployment owner UID·선택 container·image digest exact gate 실패 count=%s rs_uid=%s owner_uid=%s container_count=%s image_digest=%s expected_digest=%s\n' "$ROLLBACK_TARGET_COUNT" "${ROLLBACK_TARGET_RS_UID:--}" "${ROLLBACK_TARGET_OWNER_UID:--}" "$ROLLBACK_TARGET_CONTAINER_COUNT" "${ROLLBACK_TARGET_IMAGE_DIGEST:--}" "$ROLLBACK_IMAGE_DIGEST" >&2; return 1; }; if [ "$CHANGE_READY" != true ] || [ "$OWNER_CHAIN_KIND" != Deployment ] || [ "$SELECTION_READY" != true ] || [ "$CONTAINER_KIND" != regular ] && [ "$CONTAINER_KIND" != init ] || [ -z "$CONTAINER" ]; then ROLLBACK_TARGET_READY=false; printf '%s\n' '중단: CHANGE_READY·Deployment owner·SELECTION_READY·regular/init container gate가 아니다.' >&2; elif rollback_target_guard; then CHANGE_READY=true; export CHANGE_READY; else CHANGE_READY=false; ROLLBACK_TARGET_READY=false; printf '%s\n' '중단: rollback target exact gate 실패. CHANGE_READY=false를 유지한다.' >&2; fi`

**Deployment rollback — rollback trigger와 gate 뒤 아래 한 줄 전체를 복사**

`ROLLBACK_READY=false; EXPECTED_NEW_POD_REVISION=''; EXPECTED_NEW_POD_DIGEST=''; CHANGE_WINDOW_START=''; if [ "$ROLLBACK_TARGET_READY" != true ] || [ "$CHANGE_READY" != true ] || [ "$OWNER_CHAIN_KIND" != Deployment ] || [ "$SELECTION_READY" != true ] || [ "$CONTAINER_KIND" != regular ] && [ "$CONTAINER_KIND" != init ] || [ -z "$CONTAINER" ] || ! [[ "$ROLLBACK_REVISION" =~ ^[0-9]+$ ]] || ! [[ "$ROLLBACK_IMAGE_DIGEST" =~ ^sha256:[0-9a-f]{64}$ ]]; then printf '%s\n' '중단: ROLLBACK_TARGET_READY·CHANGE_READY·Deployment·SELECTION_READY·regular/init container·rollback revision/digest exact gate가 아니다.' >&2; elif kubectl rollout history "deployment/$OWNER_CHAIN_NAME" -n "$NS" && rollback_target_guard && [ "$ROLLBACK_TARGET_READY" = true ]; then CHANGE_WINDOW_START="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; if kubectl rollout undo "deployment/$OWNER_CHAIN_NAME" -n "$NS" --to-revision="$ROLLBACK_REVISION" && kubectl rollout status "deployment/$OWNER_CHAIN_NAME" -n "$NS" --timeout=5m; then ROLLBACK_READY=true; EXPECTED_NEW_POD_REVISION="$ROLLBACK_REVISION"; EXPECTED_NEW_POD_DIGEST="$ROLLBACK_IMAGE_DIGEST"; export ROLLBACK_READY EXPECTED_NEW_POD_REVISION EXPECTED_NEW_POD_DIGEST CHANGE_WINDOW_START; printf 'ROLLBACK_READY=true owner=Deployment/%s revision=%s digest=%s approval=%s window_start=%s\n' "$OWNER_CHAIN_NAME" "$ROLLBACK_REVISION" "$ROLLBACK_IMAGE_DIGEST" "$APPROVAL_ID" "$CHANGE_WINDOW_START"; else ROLLBACK_READY=false; EXPECTED_NEW_POD_REVISION=''; EXPECTED_NEW_POD_DIGEST=''; CHANGE_WINDOW_START=''; printf '%s\n' 'rollback 또는 rollout 실패: ROLLBACK_READY=false이며 new Pod 검증을 실행하지 않는다.' >&2; fi; else ROLLBACK_READY=false; EXPECTED_NEW_POD_REVISION=''; EXPECTED_NEW_POD_DIGEST=''; CHANGE_WINDOW_START=''; printf '%s\n' '중단: mutation 직전 Deployment·target ReplicaSet identity mismatch 또는 rollback target gate 실패. undo를 실행하지 않는다.' >&2; fi`

rollout status 성공은 config 참조 정상화, 원하는 Ready replica, application 기능을 단독 보장하지 않는다. `ROLLBACK_TARGET_READY=true`와 mutation 직전 identity 재검증이 통과한 경우에도 실제 기능을 별도로 확인한다. StatefulSet·DaemonSet·Job/CronJob은 각 owner의 승인된 rollback 절차로 이관한다.

**변경 후 새 Pod 선택·UID 등록 — 아래 한 줄 전체를 복사**

`NEW_POD='PASTE_NEW_POD_HERE'; CANDIDATES_JSON=''; NEW_POD_JSON=''; if [ "$ROLLBACK_READY" != true ] || [ "$OWNER_CHAIN_KIND" != Deployment ] || [ -z "$EXPECTED_NEW_POD_REVISION" ] || [ -z "$EXPECTED_NEW_POD_DIGEST" ]; then printf '%s\n' '중단: ROLLBACK_READY·Deployment owner chain·expected revision/digest gate가 아니다. rollback 실패 후에는 new Pod를 검증하지 않는다.' >&2; elif CANDIDATES_JSON="$(kubectl get pods -n "$NS" -l "$WORKLOAD_SELECTOR" -o json)" && NEW_POD_JSON="$(kubectl get pod "$NEW_POD" -n "$NS" -o json)" && jq -r '.items[]? | "Pod=" + .metadata.name + " UID=" + .metadata.uid + " controller=" + (([.metadata.ownerReferences[]? | select(.controller == true)][0].name // "-")|tostring) + " created=" + .metadata.creationTimestamp' <<<"$CANDIDATES_JSON" | head -c 3000 && register_new_pod "$CANDIDATES_JSON" "$NEW_POD_JSON" "$OWNER_CHAIN_UID" "$EXPECTED_NEW_POD_REVISION" "$EXPECTED_NEW_POD_DIGEST" "${CHANGE_WINDOW_START:--}"; then printf '새 후보 Pod=%s UID=%s가 selector·controller UID·생성 시각·revision=%s·digest=%s gate를 통과했다.\n' "$VERIFY_POD" "$NEW_POD_UID" "$EXPECTED_NEW_POD_REVISION" "$EXPECTED_NEW_POD_DIGEST"; else ROLLBACK_READY=false; unset NEW_POD_UID; printf '%s\n' '중단: NEW_POD 후보 membership·controller chain·생성 시각·expected revision/image digest 검증 실패.' >&2; fi`

기존 `$POD`와 `$POD_UID`를 변경 후 검증에 재사용하지 않는다. 생성 시각·owner·revision이 승인 범위와 맞는 후보만 선택한다.

## 정상화와 증거 보존

정상화는 진단 경로를 역순으로 확인한다. 참조 object·key·optional·namespace → Pod spec과 owner template → kubelet/volume source → 새 Pod identity·condition → regular는 Ready=true, init은 terminated.reason=Completed·exitCode=0 → 원하는 Ready 수와 새 Warning 부재 → 실제 요청·핵심 기능 또는 Job 산출물 → 관찰 창 동안 재발 없음 순서다.

**검증 Pod 상태 — 아래 한 줄 전체를 복사**

`unset FUNCTION_READY`

실제 기능 계약과 요청/핵심 기능 결과를 owner가 확인해 `FUNCTION_READY=true`를 직접 등록하기 전에는 정상화하지 않는다. 자동화할 기능 계약 정보가 없으면 `FUNCTION_READY=false`인 채로 owner에게 이관한다.

`normalization_evidence_guard(){ local pod_json="$1" expected_uid="$2" expected_revision="$3" expected_digest="$4" c="$5" ck="$6" direct_kind direct_name direct_uid owner_json rs_json; direct_kind="$(jq -r '[.metadata.ownerReferences[]? | select(.controller == true)][0].kind // empty' <<<"$pod_json")" || return 1; direct_name="$(jq -r '[.metadata.ownerReferences[]? | select(.controller == true)][0].name // empty' <<<"$pod_json")" || return 1; direct_uid="$(jq -r '[.metadata.ownerReferences[]? | select(.controller == true)][0].uid // empty' <<<"$pod_json")" || return 1; [ "$OWNER_CHAIN_KIND" = Deployment ] && [ "$direct_kind" = ReplicaSet ] && [ -n "$direct_name" ] && [ -n "$direct_uid" ] || return 1; owner_json="$(kubectl get deployment "$OWNER_CHAIN_NAME" -n "$NS" -o json)" || return 1; rs_json="$(kubectl get replicaset "$direct_name" -n "$NS" -o json)" || return 1; jq -e --arg uid "$expected_uid" --arg c "$c" --arg ck "$ck" --arg digest "$expected_digest" '(if $ck == "init" then (.status.initContainerStatuses // []) else (.status.containerStatuses // []) end) as $statuses | [$statuses[] | select(.name == $c)] as $selected | (.metadata.uid == $uid) and (($selected | length) == 1) and (if $ck == "init" then (($selected[0].state.terminated.reason // "") == "Completed" and ($selected[0].state.terminated.exitCode // -1) == 0) else (($selected[0].ready == true) and (($selected[0].state.waiting.reason // "") == "")) end) and (((($selected[0].imageID // "") | if contains("@") then split("@")[ -1] else . end) == $digest))' <<<"$pod_json" >/dev/null && jq -e --arg uid "$OWNER_CHAIN_UID" '(.metadata.uid == $uid) and ((.status.observedGeneration // -1) == (.metadata.generation // -2)) and ((.spec.replicas // 1) == (.status.replicas // -1)) and ((.spec.replicas // 1) == (.status.updatedReplicas // -1)) and ((.spec.replicas // 1) == (.status.availableReplicas // -1)) and ((.spec.replicas // 1) == (.status.readyReplicas // -1))' <<<"$owner_json" >/dev/null && jq -e --arg direct "$direct_uid" --arg owner "$OWNER_CHAIN_UID" --arg revision "$expected_revision" '(.metadata.uid == $direct) and (.metadata.annotations["deployment.kubernetes.io/revision"] == $revision) and any(.metadata.ownerReferences[]?; .controller == true and .kind == "Deployment" and .uid == $owner)' <<<"$rs_json" >/dev/null; }`

`if [ -n "${NEW_POD:-}" ] && [ -n "${NEW_POD_UID:-}" ]; then VERIFY_POD="$NEW_POD"; fi`

`NORMALIZATION_READY=false; FUNCTION_READY="${FUNCTION_READY:-false}"; EXPECTED_POD_UID="${NEW_POD_UID:-$POD_UID}"; EXPECTED_POD_REVISION="${EXPECTED_NEW_POD_REVISION:-}"; EXPECTED_POD_DIGEST="${EXPECTED_NEW_POD_DIGEST:-}"; VERIFY_JSON=''; if [ "$SELECTION_READY" != true ] || [ -z "$EXPECTED_POD_UID" ] || [ -z "$EXPECTED_POD_REVISION" ] || [ -z "$EXPECTED_POD_DIGEST" ]; then printf '%s\n' '중단: SELECTION_READY 또는 expected new Pod UID/revision/image gate가 아니다.' >&2; elif VERIFY_JSON="$(kubectl get pod "$VERIFY_POD" -n "$NS" -o json)" && pod_uid_guard "$VERIFY_JSON" "$EXPECTED_POD_UID" && normalization_evidence_guard "$VERIFY_JSON" "$EXPECTED_POD_UID" "$EXPECTED_POD_REVISION" "$EXPECTED_POD_DIGEST" "$CONTAINER" "$CONTAINER_KIND"; then if [ "$FUNCTION_READY" = true ] && kubectl describe pod "$VERIFY_POD" -n "$NS"; then NORMALIZATION_READY=true; printf 'NORMALIZATION_READY=true function_ready=true pod=%s uid=%s revision=%s digest=%s observed=%s\n' "$VERIFY_POD" "$EXPECTED_POD_UID" "$EXPECTED_POD_REVISION" "$EXPECTED_POD_DIGEST" "$OBSERVED_AT"; else NORMALIZATION_READY=false; printf '%s\n' '중단: FUNCTION_READY=true인 실제 기능 계약 증거가 없다. owner 확인으로 이관하고 정상화 미완료를 유지한다.' >&2; fi; else NORMALIZATION_READY=false; printf '%s\n' '중단: expected Pod UID/revision/image, Ready·waiting/config error 소멸 또는 owner replicas 수렴 검증 실패.' >&2; fi`

같은 `CreateContainerConfigError`, Secret·ConfigMap 참조 오류와 restart 증가가 관찰 창에 없어야 한다. regular는 `Ready=true`, init은 `terminated.reason=Completed`와 `exitCode=0`을 각각 확인한다. `Running`, `Ready`, rollout status 하나는 service 기능이나 config source 정상화를 보장하지 않는다.

기록 항목: 확인 시각, context, namespace·기존/새 Pod·container/node UID, Event message와 시각, 참조 이름·key·optional·namespace, ConfigMap `data`/`binaryData` key 존재 여부, projected 전체 source, ServiceAccount token projection, owner/template 대조, selector, 검증된 rollback revision, 승인·승인자·rollout 결과, 실제 정상화 결과. Secret 값·token·인증서 원문·개인정보는 기록하지 않는다.

## Prometheus 빠른 관측

메트릭이 실제로 수집되는 환경에서만 사용한다. PromQL은 등록 변수로 완성하고 출력된 한 줄만 Prometheus 또는 Grafana에 붙여 넣는다. 빈 결과는 정상·0·오류 없음이 아니라 metric 미수집, label 불일치, 조회 범위, 권한 또는 API 실패 후보다.

**config waiting·ready 상태 PromQL 생성 — 아래 한 줄 전체를 복사**

`PROMQL_READY=false; PROMQL_WAITING=''; PROMQL_READY_CONDITION=''; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif [ "$CONTAINER_KIND" = regular ]; then PROMQL_WAITING="$(printf 'kube_pod_container_status_waiting_reason{namespace="%s",pod="%s",uid="%s",container="%s",reason="CreateContainerConfigError"}==1' "$NS" "$POD" "$POD_UID" "$CONTAINER")"; PROMQL_READY_CONDITION="$(printf 'kube_pod_container_status_ready{namespace="%s",pod="%s",uid="%s",container="%s"}==0' "$NS" "$POD" "$POD_UID" "$CONTAINER")"; if [ -n "$PROMQL_WAITING" ] && [ -n "$PROMQL_READY_CONDITION" ]; then PROMQL_READY=true; printf 'WAITING: %s\nREADY_FALSE: %s\n' "$PROMQL_WAITING" "$PROMQL_READY_CONDITION" | head -c 800; printf '\n'; else printf '%s\n' '중단: regular PromQL 생성 결과가 비어 있다.' >&2; fi; elif [ "$CONTAINER_KIND" = init ]; then PROMQL_WAITING="$(printf 'kube_pod_init_container_status_waiting_reason{namespace="%s",pod="%s",uid="%s",container="%s",reason="CreateContainerConfigError"}==1' "$NS" "$POD" "$POD_UID" "$CONTAINER")"; if [ -n "$PROMQL_WAITING" ]; then PROMQL_READY=true; printf 'WAITING: %s\nINIT_NORMALIZATION: Pod API에서 terminated.reason=Completed 및 exitCode=0을 확인한다. init ready metric은 생성하지 않는다.\n' "$PROMQL_WAITING" | head -c 800; printf '\n'; else printf '%s\n' '중단: init PromQL 생성 결과가 비어 있다.' >&2; fi; else printf '중단: 지원하지 않는 CONTAINER_KIND=%s; PromQL을 생성하지 않는다.\n' "$CONTAINER_KIND" >&2; fi`

`PROMQL_READY=true` 뒤 출력된 각 완성 한 줄을 사용한다. regular는 `kube_pod_container_status_*`, init은 `kube_pod_init_container_status_*` 계열만 생성한다. init에는 일반 container의 `kube_pod_container_status_ready` 대응 metric을 만들지 않고, `terminated.reason=Completed`·`exitCode=0`은 Pod API 정상화 gate에서 확인한다. ConfigMap·Secret 이름/key, ServiceAccount와 projected volume의 실패 source는 PromQL로 확정할 수 없으므로 Pod spec과 UID 제한 Event를 기준으로 분기한다.
