# Pod가 Running이지만 Ready가 아닌 경우

## 입력값과 빠른 수집

이 문서의 실행 host는 승인된 context가 설정된 작업 PC 또는 bastion이다. 모든 명령은 도중에 터미널을 바꾸지 않는 같은 Bash에서 실행한다. Kubernetes API 읽기 권한과 대상 namespace의 `pods/get`, `pods/list`, `events/list`가 필요하며, `logs`·`exec` 분기는 각각 해당 subresource 권한과 실행 중인 client Pod를 추가로 요구한다. 도구 확인이 실패하면 다음 단계로 진행하지 않는다.

| 종류 | 값 | 출처와 사용 시점 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 대상 namespace와 Pod 이름을 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `POD_IP`, `NODE`, `PHASE`, `POD_READY`, `CONTAINERS_READY`, `CONTAINER_CANDIDATES`, 선택 container의 `CONTAINER_ID`, client/dependency의 `*_UID`·`*_CONTAINER_ID`, `POD_RE` | 대상·client·dependency API에서 현재 identity·상태·container 관계를 읽어 같은 Bash에 등록한다. |
| 계산 후보 | `POD_RE`, EndpointSlice label selector, 관측 시작 시각 | 등록값에서 생성하며 출력 후 escape와 범위를 확인한다. 시작 시각은 로그 분기에서 운영자가 고른다. |
| 운영자 선택값 | `CONTAINER`, `START_RFC3339`, Service·client·dependency 이름·namespace 값 | 자동 출력과 실제 계약을 확인한 뒤 해당 상세 절 직전에 선택한다. dependency protocol·port·path는 이 분기에서 사용하지 않으므로 입력받지 않는다. |

입력 실패나 API 후보 수 불일치가 있으면 이전 파생값을 사용하지 않는다. `Running`은 process가 존재한다는 뜻이지 application listener, readiness, Service traffic 수신을 보장하지 않는다.

**Bash·필수 도구·권한 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 입력·API 수집·분기를 실행하지 않는다. `kubectl` 권한 오류는 도구 부재가 아니라 API/RBAC 실패로 기록하고 승인된 주체로 이관한다.

**최초 입력·이전 상태 초기화 — 같은 Bash에서 한 번 실행**

`unset CLIENT_READY CLIENT_UID CLIENT_CONTAINER_ID DEP_CLIENT_UID DEP_CLIENT_CONTAINER_ID CONTAINER_ID START_READY LOG_TARGET_READY START_CANONICAL START_EPOCH NOW_EPOCH POD_RECHECK_JSON POD_RECHECK_UID POD_RECHECK_CONTAINER_ID LOG_PRODUCER_RC FILTER_RC`

`unset NORMALIZATION_READY NORMALIZATION_JSON CURRENT_UID`

`unset INPUT_READY AUTO_READY OBS_READY EVENTS_READ_READY SELECTION_READY SERVICE_READY ENDPOINT_READ_READY REQUEST_READY DEPENDENCY_READY POD_JSON POD_UID POD_IP NODE PHASE POD_READY CONTAINERS_READY CONTAINER_CANDIDATES CONTAINER_COUNT POD_RE CONTAINER START_RFC3339 SERVICE CLIENT_POD CLIENT_NS CLIENT_CONTAINER SERVICE_SCHEME SERVICE_PORT SERVICE_PATH DEP_SERVICE DEP_NS DEP_CLIENT_POD DEP_CLIENT_NS DEP_CLIENT_CONTAINER LOG_RAW EVENT_JSON; NS='PASTE_NAMESPACE_HERE'; POD='PASTE_POD_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: 도구 확인을 먼저 통과한다.' >&2; elif [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: NS와 POD를 입력한다.' >&2; elif POD_JSON_TMP="$(kubectl get pod "$POD" -n "$NS" -o json)" && jq -e --arg pod "$POD" '.metadata.name==$pod and (.metadata.uid|length)>0' <<<"$POD_JSON_TMP" >/dev/null; then POD_JSON="$POD_JSON_TMP"; INPUT_READY=true; export NS POD; printf 'INPUT_READY=true namespace=%s pod=%s\n' "$NS" "$POD"; else printf '중단: exact-name Pod API 조회 실패 또는 이름 불일치 namespace=%s pod=%s\n' "$NS" "$POD" >&2; fi`

`INPUT_READY=true`가 아니면 다음 명령을 실행하지 않는다. 이 입력칸의 두 입력 문자열만 직접 바꾸며 문서 다른 곳에 namespace·Pod 이름을 다시 입력하지 않는다.

입력 API 응답은 exact-name 확인에만 사용하고 snapshot으로 보존하지 않는다.

`unset POD_JSON`

**API 자동 수집·등록 — 같은 Bash에서 한 번 실행**

입력 단계의 `POD_JSON`은 exact-name 확인 전용이며 snapshot으로 재사용하지 않는다. 자동수집 시작 시 이전 snapshot과 downstream 값을 먼저 무효화한다.

`unset POD_JSON POD_JSON_TMP POD_UID_TMP POD_IP_TMP NODE_TMP PHASE_TMP POD_READY_TMP CONTAINERS_READY_TMP CONTAINER_COUNT_TMP CONTAINER_CANDIDATES_TMP POD_RE_TMP POD_UID POD_IP NODE PHASE POD_READY CONTAINERS_READY CONTAINER_CANDIDATES CONTAINER_COUNT POD_RE CONTAINER CONTAINER_ID SELECTION_READY START_READY LOG_TARGET_READY SERVICE_READY ENDPOINT_READ_READY REQUEST_READY DEPENDENCY_READY SERVICE_JSON CLIENT_JSON ENDPOINT_JSON DEP_JSON DEP_CLIENT_JSON DEP_LOG_RAW SNAPSHOT_READY; AUTO_READY=false`

`unset AUTO_READY POD_UID POD_IP NODE PHASE POD_READY CONTAINERS_READY CONTAINER_CANDIDATES CONTAINER_COUNT POD_RE; AUTO_READY=false; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif POD_JSON_TMP="$(kubectl get pod "$POD" -n "$NS" -o json)" && POD_UID_TMP="$(jq -r '.metadata.uid // empty' <<<"$POD_JSON_TMP")" && POD_IP_TMP="$(jq -r '.status.podIP // "-"' <<<"$POD_JSON_TMP")" && NODE_TMP="$(jq -r '.spec.nodeName // "-"' <<<"$POD_JSON_TMP")" && PHASE_TMP="$(jq -r '.status.phase // "-"' <<<"$POD_JSON_TMP")" && POD_READY_TMP="$(jq -r '[.status.conditions[]? | select(.type=="Ready") | .status][0] // "Unknown"' <<<"$POD_JSON_TMP")" && CONTAINERS_READY_TMP="$(jq -r '[.status.conditions[]? | select(.type=="ContainersReady") | .status][0] // "Unknown"' <<<"$POD_JSON_TMP")" && CONTAINER_COUNT_TMP="$(jq '[.spec.containers[]?] | length' <<<"$POD_JSON_TMP")" && CONTAINER_CANDIDATES_TMP="$(jq -r '[.spec.containers[]? | .name + "=" + ([.ports[]? | ((.name // "unnamed") + ":" + (.containerPort|tostring))] | join(","))] | join("; ")' <<<"$POD_JSON_TMP")"; then if [ -z "$POD_UID_TMP" ] || [ "$CONTAINER_COUNT_TMP" -lt 1 ]; then printf '중단: UID 또는 container 후보가 없음 uid=%s count=%s\n' "${POD_UID_TMP:--}" "$CONTAINER_COUNT_TMP" >&2; else POD_RE_TMP="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; POD_UID="$POD_UID_TMP"; POD_IP="$POD_IP_TMP"; NODE="$NODE_TMP"; PHASE="$PHASE_TMP"; POD_READY="$POD_READY_TMP"; CONTAINERS_READY="$CONTAINERS_READY_TMP"; CONTAINER_CANDIDATES="$CONTAINER_CANDIDATES_TMP"; CONTAINER_COUNT="$CONTAINER_COUNT_TMP"; POD_RE="^${POD_RE_TMP}$"; AUTO_READY=true; export POD_UID POD_IP NODE PHASE POD_READY CONTAINERS_READY CONTAINER_CANDIDATES CONTAINER_COUNT POD_RE; printf '=== 대상 Pod ===\n이름: %s\nUID: %s\nNode: %s\nPhase: %s\nPod Ready: %s\nContainersReady: %s\nPod IP: %s\nContainer/Port 후보: %s\n관측 시각(UTC): %s\nPOD_RE: %s\n' "$POD" "$POD_UID" "$NODE" "$PHASE" "$POD_READY" "$CONTAINERS_READY" "$POD_IP" "$CONTAINER_CANDIDATES" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" "$POD_RE"; fi; else printf '%s\n' '중단: Pod 자동 수집 API 또는 JSON 처리 실패' >&2; fi`

`AUTO_READY=false; SNAPSHOT_READY=false; if [ -z "${POD_UID_TMP:-}" ]; then printf '%s\n' '중단: fresh Pod UID가 없다.' >&2; elif [ "$POD_UID" = "$POD_UID_TMP" ] && jq -e --arg pod "$POD" --arg uid "$POD_UID_TMP" '.metadata.name==$pod and (.metadata.uid|length)>0 and .metadata.uid==$uid' <<<"$POD_JSON_TMP" >/dev/null; then POD_JSON="$POD_JSON_TMP"; AUTO_READY=true; SNAPSHOT_READY=true; printf 'SNAPSHOT_READY=true name=%s uid=%s observed_at=%s\n' "$POD" "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else unset POD_JSON POD_JSON_TMP POD_UID POD_IP NODE PHASE POD_READY CONTAINERS_READY CONTAINER_CANDIDATES CONTAINER_COUNT POD_RE; printf '중단: fresh Pod snapshot name/UID exact match 실패 requested_name=%s current_uid=%s\n' "$POD" "${POD_UID:--}" >&2; fi`

`AUTO_READY=true`이고 `POD_UID`, phase, condition, container/port 후보가 함께 출력돼야 다음 단계로 간다. 출력이 비면 대상 없음·field 부재·권한/API 오류·도구 실패를 구분해 이관하며 정상이나 container 0으로 해석하지 않는다. `POD_RE`는 생성 후 bounded 출력으로 확인한 계산 후보이지 원인 확정값이 아니다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 같은 Pod UID의 phase가 `Running`인데 Pod `Ready=False`, `ContainersReady=False`, 하나 이상의 container `ready=false`, 또는 관련 EndpointSlice에서 대상 Pod가 준비 endpoint로 포함되지 않은 경우 |
| 적용 | Pod aggregate condition과 container ready의 차이, `readinessGates`, sidecar, Service/EndpointSlice 포함 여부, application·dependency·실제 요청의 불일치를 진단한다. |
| 제외 | `Pending`, image·mount·sandbox 생성 실패는 해당 Pod 런북으로 이동한다. 같은 UID의 `Readiness probe failed`는 [[19. Pod readiness probe가 실패하는 경우#1. probe 유형과 정확한 target|명시적 readiness probe 실패 진단]]으로, `Liveness probe failed`, `Startup probe failed`, 종료·OOM·restart 증가는 각각 [[20. Pod liveness probe가 실패하는 경우]], [[21. Pod startup probe가 실패하는 경우]], [[17. Pod restartCount가 계속 증가하는 경우]]로 이동한다. |

검색 문자열: `Ready=False`, `ContainersReady=False`, `ready=false`, `readinessGates`, `Unhealthy`, `Readiness probe failed`, `EndpointSlice`, `connection refused`, `timeout`, `no healthy upstream`

`Ready=False`는 aggregate 결과이고 probe 실패는 가능한 원인 중 하나다. 이 문서는 aggregate Ready와 실제 traffic 경계를 소유하며, 같은 UID의 probe Event가 없으면 probe 실패를 확정하지 않는다.

## 최초 확인

**Pod 상태와 Event — API server까지 확인하는 읽기 전용 명령**

`OBS_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o wide && kubectl describe pod "$POD" -n "$NS"; then OBS_READY=true; printf 'OBS_READY=true uid=%s observed_at=%s\n' "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '%s\n' '중단: Pod 최초 확인 실패' >&2; fi`

`get`에서 phase·Ready·ContainersReady·restart·node·age·UID를, `describe`에서 custom condition·container별 ready/state/lastState/reason·`Unhealthy` suffix·Event 시각을 본다. 이 명령 성공은 application listener나 실제 요청 성공을 보장하지 않는다. 실패하면 API/RBAC 또는 현재 대상 identity를 재확인하고 진단을 중단한다.

Event 시각·UID 연결이 `describe`에서 불명확할 때만 다음을 실행한다. 빈 Event는 오류 없음이 아니라 해당 범위의 Event 미존재 또는 보존·selector 문제다.

`EVENTS_READ_READY=false; EVENT_JSON=''; if [ "$OBS_READY" != true ]; then printf '%s\n' '중단: OBS_READY가 아니다.' >&2; elif EVENT_JSON="$(kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID" --sort-by=.metadata.creationTimestamp -o json)"; then EVENTS_READ_READY=true; jq -r 'if (.items|length)==0 then "이벤트: 없음 (정상·오류 없음으로 해석하지 않음)" else .items[] | "=== Event ===\n생성: \(.metadata.creationTimestamp // "-")\nFirst: \(.firstTimestamp // "-")\nLast: \(.lastTimestamp // "-")\nEvent time: \(.eventTime // "-")\nSeries last: \(.series.lastObservedTime // "-")\nType/Reason: \(.type // "-")/\(.reason // "-")\nCount: \(.count // "-")\nMessage: \(.message // "-")" end' <<<"$EVENT_JSON"; else printf '%s\n' '중단: UID 제한 Event API 조회 실패' >&2; fi`

Event는 집계될 수 있으므로 채워진 `eventTime`, `series.lastObservedTime`, `firstTimestamp`, `lastTimestamp`, `count`를 container 상태·로그 시각과 대조한다. command/header가 message에 있으면 Secret·token·개인정보를 저장하지 않는다.

표는 원인을 확정하거나 변경을 승인하지 않는다. 상세 절의 진입 증거·필수값·범위 제한 명령·성공 gate·실패 의미·다음 행동을 모두 통과해야 다음 계층으로 이동한다.

### 1. Pod Ready aggregate와 readinessGates

진입 증거는 `ContainersReady=True`인데 `Ready=False`이거나 custom condition이 aggregate를 막는 경우다. 최초 필요값은 자동 수집한 `$POD_UID`, readiness gate condition type/status/reason이며 source는 같은 Pod API와 관측 UTC 시각이다.

**Gate와 condition 확인 — API server에서 같은 UID를 읽는 명령**

`READINESS_GATE_READY=false; READINESS_JSON=''; READINESS_UID=''; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif READINESS_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && READINESS_UID="$(jq -r '.metadata.uid // empty' <<<"$READINESS_JSON")" && jq -e --arg uid "$POD_UID" '.metadata.uid==$uid and (.metadata.uid|length)>0' <<<"$READINESS_JSON" >/dev/null; then READINESS_GATE_READY=true; jq -r '{uid:.metadata.uid,readinessGates:[.spec.readinessGates[]?.conditionType],conditions:[.status.conditions[]? | {type,status,reason,lastTransitionTime}]}' <<<"$READINESS_JSON"; printf '성공 gate: readiness 조회 UID=%s가 저장 UID=%s와 equality 일치\n' "$READINESS_UID" "$POD_UID"; else printf '실패: readiness 조회 UID mismatch 또는 API 권한 오류 stored_uid=%s current_uid=%s; gate 정상으로 진행하지 않음\n' "$POD_UID" "${READINESS_UID:--}" >&2; fi`

`READINESS_GATE_READY=true`가 아니면 readinessGate 판정을 진행하지 않는다. gate condition이 없거나 `False`면 condition을 갱신하는 승인된 controller·CRD·mesh health owner와 외부 health 결과로 이동한다. 빈 gate는 gate 없음일 수 있지만, `Ready=False`의 원인을 설명하지 않는다. 이 명령 성공은 controller 갱신과 실제 요청을 보장하지 않으며, `Ready`를 patch해 성공으로 만들지 않는다.

### 2. container ready와 명시적 probe 실패의 소유권

진입 증거는 `ContainersReady=False` 또는 자동 출력의 container 후보 중 `ready=false`다. 실제 로그·probe를 읽을 container가 여러 개면 임의로 고르지 말고 다음 선택 gate를 실행한다.

**container 선택 — 자동 후보 확인 후 한 번만 입력**

`CONTAINER='PASTE_CONTAINER_HERE'; SELECTION_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif jq -e --arg c "$CONTAINER" 'any(.spec.containers[]?; .name==$c)' <<<"$POD_JSON" >/dev/null; then CONTAINER_ID="$(jq -r --arg c "$CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID // empty][0] // empty' <<<"$POD_JSON")"; if [ -n "$CONTAINER_ID" ]; then SELECTION_READY=true; export CONTAINER CONTAINER_ID; printf 'SELECTION_READY=true container=%s container_id=%s pod_uid=%s observed_at=%s\n' "$CONTAINER" "$CONTAINER_ID" "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '중단: 선택 container의 container ID가 없음; logs/stream 대상을 확정하지 않음\n' >&2; fi; else printf '중단: 선택한 container가 자동 후보에 없음; 후보를 임의 선택하지 않음\n' >&2; fi`

`SELECTION_READY=true`가 아니면 logs·probe 분기를 실행하지 않는다. `Waiting`·`Terminated`·non-zero·`OOMKilled`와 restart 증가는 [[17. Pod restartCount가 계속 증가하는 경우]] 또는 해당 원인으로 이동한다. `Liveness probe failed`, `Killing`, `Startup probe failed`는 각각 [[20. Pod liveness probe가 실패하는 경우]], [[21. Pod startup probe가 실패하는 경우]]로, 같은 UID의 `Readiness probe failed`는 [[19. Pod readiness probe가 실패하는 경우#1. probe 유형과 정확한 target|probe owner]]로 이동한다.

로그 연결 경로는 `실행 host → API server → 대상 node의 kubelet → runtime → 대상 Pod의 container → application log stream`이다. API server까지 성공해도 kubelet·runtime·container log stream 준비를 보장하지 않으며, container ID와 UTC 시각을 함께 기록한다.

`START_RFC3339='PASTE_START_RFC3339_HERE'; START_READY=false; LOG_TARGET_READY=false; LOG_RAW=''; unset START_CANONICAL START_EPOCH NOW_EPOCH POD_RECHECK_JSON POD_RECHECK_UID POD_RECHECK_CONTAINER_ID; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif ! [[ "$START_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then printf '%s\n' '중단: START_RFC3339가 UTC RFC3339 형식이 아님' >&2; elif START_CANONICAL="$(date -u -d "$START_RFC3339" '+%Y-%m-%dT%H:%M:%SZ')" && [ "$START_CANONICAL" = "$START_RFC3339" ] && START_EPOCH="$(date -u -d "$START_RFC3339" '+%s')" && NOW_EPOCH="$(date -u '+%s')" && [ "$START_EPOCH" -le "$NOW_EPOCH" ] && POD_RECHECK_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && POD_RECHECK_UID="$(jq -r '.metadata.uid // empty' <<<"$POD_RECHECK_JSON")" && POD_RECHECK_CONTAINER_ID="$(jq -r --arg c "$CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID // empty][0] // empty' <<<"$POD_RECHECK_JSON")" && [ "$POD_RECHECK_UID" = "$POD_UID" ] && [ "$POD_RECHECK_CONTAINER_ID" = "$CONTAINER_ID" ]; then START_READY=true; LOG_TARGET_READY=true; export START_RFC3339 START_READY LOG_TARGET_READY; printf 'START_READY=true LOG_TARGET_READY=true start=%s pod_uid=%s container_id=%s observed_at=%s\n' "$START_RFC3339" "$POD_RECHECK_UID" "$POD_RECHECK_CONTAINER_ID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; if LOG_RAW="$(kubectl logs "$POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=200)"; then LOG_PRODUCER_RC=0; if grep -E -i -C 3 'ready|health|listen|bind|initializ|timeout|refused|denied|tls|upstream|dependency|dns|error|exception|probe|killing' <<<"$LOG_RAW"; then FILTER_RC=0; else FILTER_RC=$?; fi; if [ "$FILTER_RC" -eq 1 ]; then printf '%s\n' '필터 결과 없음: 오류 없음으로 해석하지 않고 같은 시간 범위 tail로 재확인'; elif [ "$FILTER_RC" -ne 0 ]; then printf '실패: log filter rc=%s\n' "$FILTER_RC" >&2; fi; else LOG_PRODUCER_RC=$?; printf '실패: logs producer rc=%s; API/RBAC/대상 lifecycle 오류; [[27. Pod 로그를 가져올 수 없는 경우]]로 이관\n' "$LOG_PRODUCER_RC" >&2; fi; else printf '%s\n' '중단: 시간 형식/순서가 유효하지 않거나 Pod UID/container ID 재조회가 현재 선택과 불일치' >&2; fi`

성공 gate는 같은 Pod UID·container와 시간 범위의 상태 및 로그 시각이 연결되는 것이다. 필터 또는 tail이 비면 오류 부재가 아니라 보존·범위·도구 문제일 수 있다. Secret·token·개인정보가 보이면 출력·저장을 중단하고 오류 문자열만 보존한다. `Ready=False`만으로 probe 실패를 확정하지 않는다.

### 3. Service·EndpointSlice 포함 여부와 실제 요청

진입 증거는 container가 ready인데 endpoint에서 대상 Pod가 빠지거나 실제 Service 요청이 실패하는 경우다. 연결 경로는 `실행 host → API server → Service/EndpointSlice controller가 기록한 address·port → 승인된 client Pod의 node/kubelet/runtime → client container → DNS → Service port → targetPort/EndpointSlice port → 대상 process listener → application protocol`이다. Service port, targetPort, endpoint port, listener port와 HTTP/HTTPS protocol은 같은 값으로 취급하지 않는다.

**Service·client 선택 — 자동 후보를 본 뒤 한 번만 입력**

`SERVICE='PASTE_SERVICE_HERE'; CLIENT_POD='PASTE_CLIENT_POD_HERE'; CLIENT_NS='PASTE_CLIENT_NAMESPACE_HERE'; CLIENT_CONTAINER='PASTE_CLIENT_CONTAINER_HERE'; SERVICE_SCHEME='PASTE_SERVICE_SCHEME_HERE'; SERVICE_PORT='PASTE_SERVICE_PORT_HERE'; SERVICE_PATH='PASTE_SERVICE_PATH_HERE'; SERVICE_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif ! [[ "$SERVICE_PORT" =~ ^[0-9]+$ ]] || (( SERVICE_PORT < 1 || SERVICE_PORT > 65535 )); then printf '%s\n' '중단: SERVICE_PORT가 유효한 숫자가 아님' >&2; elif [ "$SERVICE_SCHEME" != http ] && [ "$SERVICE_SCHEME" != https ]; then printf '%s\n' '중단: HTTP 또는 HTTPS만 이 문서의 실제 요청에 사용' >&2; elif SERVICE_JSON="$(kubectl get service "$SERVICE" -n "$NS" -o json)" && CLIENT_JSON="$(kubectl get pod "$CLIENT_POD" -n "$CLIENT_NS" -o json)" && jq -e --arg c "$CLIENT_CONTAINER" 'any(.spec.containers[]?; .name==$c)' <<<"$CLIENT_JSON" >/dev/null; then SERVICE_READY=true; export SERVICE CLIENT_POD CLIENT_NS CLIENT_CONTAINER SERVICE_SCHEME SERVICE_PORT SERVICE_PATH; printf 'SERVICE_READY=true service=%s client=%s/%s container=%s port=%s scheme=%s path=%s\n' "$SERVICE" "$CLIENT_NS" "$CLIENT_POD" "$CLIENT_CONTAINER" "$SERVICE_PORT" "$SERVICE_SCHEME" "$SERVICE_PATH"; else printf '%s\n' '중단: Service·client Pod·container exact API 조회 또는 선택값 검증 실패' >&2; fi`

`SERVICE_READY=true`가 아니면 endpoint·exec를 실행하지 않는다. Service API 성공은 selector가 endpoint를 만들었다는 뜻이 아니고, client container 존재는 DNS·network·application 성공을 보장하지 않는다.

`CLIENT_READY=false; if [ "$SERVICE_READY" != true ]; then printf '%s\n' '중단: SERVICE_READY가 아니다.' >&2; elif CLIENT_UID="$(jq -r '.metadata.uid // empty' <<<"$CLIENT_JSON")" && CLIENT_CONTAINER_ID="$(jq -r --arg c "$CLIENT_CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID // empty][0] // empty' <<<"$CLIENT_JSON")" && [ -n "$CLIENT_UID" ] && [ -n "$CLIENT_CONTAINER_ID" ]; then CLIENT_READY=true; export CLIENT_UID CLIENT_CONTAINER_ID; printf 'CLIENT_READY=true client_uid=%s client_container_id=%s observed_at=%s\n' "$CLIENT_UID" "$CLIENT_CONTAINER_ID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else SERVICE_READY=false; printf '%s\n' '중단: client Pod UID 또는 container ID가 없음; exec stream 대상을 확정하지 않음' >&2; fi`

`ENDPOINT_READ_READY=false; if [ "$SERVICE_READY" != true ] || [ "$CLIENT_READY" != true ]; then printf '%s\n' '중단: SERVICE_READY 또는 CLIENT_READY가 아니다.' >&2; elif ENDPOINT_JSON="$(kubectl get endpointslice -n "$NS" -l "kubernetes.io/service-name=$SERVICE" -o json)"; then ENDPOINT_READ_READY=true; jq -r --arg poduid "$POD_UID" 'if (.items|length)==0 then "EndpointSlice: 없음 (selector 불일치·controller 지연·API 범위 오류 후보)" else .items[] | "=== EndpointSlice ===\n이름: \(.metadata.name)\n관측 시각: \(.metadata.creationTimestamp // "-")\n" + ([.endpoints[]? | "주소/상태: \((.addresses // [])|join(",")) / ready=\(.conditions.ready // "-") serving=\(.conditions.serving // "-") terminating=\(.conditions.terminating // "-")\ntargetRef: \(.targetRef.kind // "-")/\(.targetRef.name // "-")/\(.targetRef.uid // "-")"] | join("\n")) end' <<<"$ENDPOINT_JSON"; else printf '%s\n' '실패: EndpointSlice API 조회 실패; 빈 endpoint와 구분하고 selector/controller owner로 이관' >&2; fi`

대상 Pod IP와 `targetRef.uid`가 `$POD_UID`와 일치하고 `ready=true`인지 확인한다. `ready=false` 또는 address 없음은 not-ready 효과의 직접 근거다. `serving`·`terminating`은 `ready=true`와 같은 뜻이 아니다. EndpointSlice가 비거나 UID가 다르면 정상화하지 않고 selector·targetPort·controller 지연·재생성 identity를 확인한다.

**Service port·targetPort·EndpointSlice port 관계 — Service 선택값과 대상 Pod UID를 같은 관계로 검증**

Service의 `.spec.ports[].port`는 client가 호출하는 `$SERVICE_PORT`, `targetPort`는 backend로 해석할 값이다. `targetPort`가 숫자면 그 숫자를 그대로, 이름이면 현재 `$POD`의 같은 이름 `containerPort`를 하나만 찾아 숫자로 해석한다. `targetPort`가 생략된 경우에는 Service `port`가 기본 target 값이다. EndpointSlice port는 이 해석 결과와 대상 `$POD_UID`가 포함된 Slice에서 일치해야 하며, 선언된 `containerPort`나 EndpointSlice 일치만으로 process listener를 확정하지 않는다.

`SERVICE_PORT_RELATION_READY=false; SERVICE_PORT_RECORD=''; SERVICE_TARGET_PORT=''; SERVICE_TARGET_PORT_KIND=''; TARGET_PORT_NUMBER=''; POD_TARGET_PORT_JSON=''; ENDPOINT_PORT_JSON=''; if [ "$SERVICE_READY" != true ] || [ "$ENDPOINT_READ_READY" != true ]; then printf '%s\n' '중단: SERVICE_READY 또는 ENDPOINT_READ_READY가 아니다.' >&2; elif SERVICE_PORT_RECORD="$(jq -c --argjson service_port "$SERVICE_PORT" '[.spec.ports[]? | select(.port==$service_port)]' <<<"$SERVICE_JSON")" && [ "$(jq 'length' <<<"$SERVICE_PORT_RECORD")" -eq 1 ] && SERVICE_TARGET_PORT="$(jq -r '.[0].targetPort // .[0].port' <<<"$SERVICE_PORT_RECORD")" && SERVICE_TARGET_PORT_KIND="$(jq -r 'if .[0].targetPort == null then "default" elif (.[0].targetPort|type)=="number" then "numeric" elif (.[0].targetPort|type)=="string" then "named" else "invalid" end' <<<"$SERVICE_PORT_RECORD")"; then if [ "$SERVICE_TARGET_PORT_KIND" = named ]; then POD_TARGET_PORT_JSON="$(jq -c --arg port_name "$SERVICE_TARGET_PORT" '[.spec.containers[]? | .ports[]? | select(.name==$port_name)]' <<<"$POD_JSON")"; if [ "$(jq 'length' <<<"$POD_TARGET_PORT_JSON")" -eq 1 ]; then TARGET_PORT_NUMBER="$(jq -r '.[0].containerPort' <<<"$POD_TARGET_PORT_JSON")"; else printf '중단: named targetPort=%s에 대응하는 대상 Pod containerPort 후보 수가 1이 아님 count=%s\n' "$SERVICE_TARGET_PORT" "$(jq 'length' <<<"$POD_TARGET_PORT_JSON")" >&2; fi; else TARGET_PORT_NUMBER="$SERVICE_TARGET_PORT"; fi; if [[ "$TARGET_PORT_NUMBER" =~ ^[0-9]+$ ]] && (( TARGET_PORT_NUMBER >= 1 && TARGET_PORT_NUMBER <= 65535 )); then ENDPOINT_PORT_JSON="$(jq -c --arg uid "$POD_UID" --argjson target_port "$TARGET_PORT_NUMBER" '[.items[]? | select(any(.endpoints[]?; .targetRef.uid == $uid)) | .ports[]? | select(.port==$target_port)]' <<<"$ENDPOINT_JSON")"; if [ "$(jq 'length' <<<"$ENDPOINT_PORT_JSON")" -ge 1 ]; then SERVICE_PORT_RELATION_READY=true; printf 'SERVICE_PORT_RELATION_READY=true service_port=%s targetPort=%s targetPort_kind=%s resolved_target_port=%s endpoint_port_matches=%s pod_uid=%s\n' "$SERVICE_PORT" "$SERVICE_TARGET_PORT" "$SERVICE_TARGET_PORT_KIND" "$TARGET_PORT_NUMBER" "$(jq 'length' <<<"$ENDPOINT_PORT_JSON")" "$POD_UID"; else printf '중단: EndpointSlice port가 Service targetPort 해석값과 일치하지 않음 expected=%s pod_uid=%s\n' "$TARGET_PORT_NUMBER" "$POD_UID" >&2; fi; else printf '중단: targetPort 해석 결과가 유효한 숫자 port가 아님 value=%s kind=%s\n' "$TARGET_PORT_NUMBER" "$SERVICE_TARGET_PORT_KIND" >&2; fi; else printf '중단: Service port=%s 후보가 정확히 하나가 아니거나 Service JSON 처리 실패\n' "$SERVICE_PORT" >&2; fi`

`SERVICE_PORT_RELATION_READY=true`가 아니면 Service 요청을 실행하지 않는다. 실패는 Service port 없음·중복, named targetPort와 Pod `containerPort` 불일치, EndpointSlice controller 지연·selector 불일치·재생성 identity 후보로 기록한다. 성공은 `port → targetPort(숫자 또는 이름 해석) → EndpointSlice port`와 대상 Pod UID의 관계만 보장하며 listener·protocol·HTTP application 성공은 다음 gate에서 별도로 확인한다.

`if [ "$SERVICE_PORT_RELATION_READY" != true ]; then ENDPOINT_READ_READY=false; fi`

`CLIENT_EXEC_READY=false; unset FRESH_CLIENT_JSON FRESH_CLIENT_UID FRESH_CLIENT_CONTAINER_ID; if [ "$CLIENT_READY" != true ]; then printf '%s\n' '중단: CLIENT_READY가 아니다.' >&2; elif FRESH_CLIENT_JSON="$(kubectl get pod "$CLIENT_POD" -n "$CLIENT_NS" -o json)" && FRESH_CLIENT_UID="$(jq -r '.metadata.uid // empty' <<<"$FRESH_CLIENT_JSON")" && FRESH_CLIENT_CONTAINER_ID="$(jq -r --arg c "$CLIENT_CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID // empty][0] // empty' <<<"$FRESH_CLIENT_JSON")" && [ "$FRESH_CLIENT_UID" = "$CLIENT_UID" ] && [ "$FRESH_CLIENT_CONTAINER_ID" = "$CLIENT_CONTAINER_ID" ]; then CLIENT_EXEC_READY=true; printf 'CLIENT_EXEC_READY=true client_uid=%s client_container_id=%s observed_at=%s\n' "$FRESH_CLIENT_UID" "$FRESH_CLIENT_CONTAINER_ID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else CLIENT_READY=false; printf '중단: client exec 직전 UID 또는 containerID가 바뀌었으므로 exec를 실행하지 않는다.\n' >&2; fi`

`REQUEST_READY=false; REQUEST_OUT=''; if [ "$ENDPOINT_READ_READY" != true ] || [ "$CLIENT_READY" != true ] || [ "$CLIENT_EXEC_READY" != true ]; then printf '%s\n' '중단: EndpointSlice·CLIENT_READY 또는 CLIENT_EXEC_READY gate가 아니다.' >&2; elif REQUEST_OUT="$(kubectl exec "$CLIENT_POD" -n "$CLIENT_NS" -c "$CLIENT_CONTAINER" -- sh -c 'service="$1"; ns="$2"; scheme="$3"; port="$4"; path="$5"; if command -v curl >/dev/null 2>&1; then curl -sS -o /dev/null -w "transport=connected http_code=%{http_code} time_total=%{time_total}\n" --connect-timeout 3 --max-time 5 "$scheme://$service.$ns.svc.cluster.local:$port$path"; elif command -v wget >/dev/null 2>&1; then wget -qO /dev/null -T 5 "$scheme://$service.$ns.svc.cluster.local:$port$path" && printf "%s\n" "transport=connected http_code=unreported"; else printf "%s\n" "request_tool_missing=curl,wget" >&2; exit 127; fi' sh "$SERVICE" "$NS" "$SERVICE_SCHEME" "$SERVICE_PORT" "$SERVICE_PATH")"; then REQUEST_READY=true; printf 'REQUEST_READY=true client=%s/%s client_uid=%s client_container_id=%s result=%s observed_at=%s\n' "$CLIENT_NS" "$CLIENT_POD" "$CLIENT_UID" "$CLIENT_CONTAINER_ID" "$REQUEST_OUT" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '%s\n' '실패: exec stream·DNS·Service 전달·listener·HTTP transport 중 하나; 결과를 정상 요청으로 해석하지 않음' >&2; fi`

`REQUEST_READY=true`는 exec가 결과를 반환한 transport 관측일 뿐 HTTP 성공·application success/data를 뜻하지 않는다. `http_code`와 latency를 별도로 기록하고 예상 application 계약과 비교한다.

HTTP transport, HTTP status, application success/data를 분리한다. `HTTP 401/403`은 연결 후 인증·인가 실패, `404`는 path·port·endpoint 후보, `5xx`는 backend/application 오류다. TLS 검증을 `-k`로 우회하지 않는다. 실제 요청 성공, Pod `Ready=True`, EndpointSlice `ready=true`는 서로 다른 증거이며 예상 application 계약을 확인하기 전 정상화하지 않는다.

### 4. Application·DNS·Service dependency

진입 증거는 같은 UID의 logs에 `timeout`, `refused`, DNS·upstream·dependency 오류가 있거나 Service 요청이 transport/API gate에서 실패한 경우다. 로그 시작 시각은 `$START_RFC3339`의 source를 재사용하고, dependency 값은 승인된 client에서 선택한다.

**dependency 선택 — 실제 대상과 protocol을 확인한 뒤 한 번만 입력**

`DEP_SERVICE='PASTE_DEPENDENCY_SERVICE_HERE'; DEP_NS='PASTE_DEPENDENCY_NAMESPACE_HERE'; DEP_CLIENT_POD='PASTE_DEPENDENCY_CLIENT_POD_HERE'; DEP_CLIENT_NS='PASTE_DEPENDENCY_CLIENT_NAMESPACE_HERE'; DEP_CLIENT_CONTAINER='PASTE_DEPENDENCY_CLIENT_CONTAINER_HERE'; DEPENDENCY_READY=false; if [ "$AUTO_READY" != true ] || [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: AUTO_READY와 SELECTION_READY가 아니다.' >&2; elif DEP_JSON="$(kubectl get service "$DEP_SERVICE" -n "$DEP_NS" -o json)" && DEP_CLIENT_JSON="$(kubectl get pod "$DEP_CLIENT_POD" -n "$DEP_CLIENT_NS" -o json)" && jq -e --arg c "$DEP_CLIENT_CONTAINER" 'any(.spec.containers[]?; .name==$c)' <<<"$DEP_CLIENT_JSON" >/dev/null; then DEPENDENCY_READY=true; export DEP_SERVICE DEP_NS DEP_CLIENT_POD DEP_CLIENT_NS DEP_CLIENT_CONTAINER; printf 'DEPENDENCY_READY=true service=%s/%s client=%s/%s container=%s\n' "$DEP_NS" "$DEP_SERVICE" "$DEP_CLIENT_NS" "$DEP_CLIENT_POD" "$DEP_CLIENT_CONTAINER"; else printf '%s\n' '중단: dependency Service·client Pod·container API 확인 실패' >&2; fi`

`DEPENDENCY_READY=true`가 아니면 DNS·dependency endpoint 확인을 실행하지 않는다. 연결 경로는 `실행 host → API server → dependency client node/kubelet/runtime → client container → cluster DNS → dependency Service → EndpointSlice/backend listener → dependency application`이다. `get` 성공은 다음 hop을 보장하지 않는다.

`if [ "$DEPENDENCY_READY" != true ]; then printf '%s\n' '중단: DEPENDENCY_READY가 아니다.' >&2; elif DEP_CLIENT_UID="$(jq -r '.metadata.uid // empty' <<<"$DEP_CLIENT_JSON")" && DEP_CLIENT_CONTAINER_ID="$(jq -r --arg c "$DEP_CLIENT_CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID // empty][0] // empty' <<<"$DEP_CLIENT_JSON")" && [ -n "$DEP_CLIENT_UID" ] && [ -n "$DEP_CLIENT_CONTAINER_ID" ]; then export DEP_CLIENT_UID DEP_CLIENT_CONTAINER_ID; printf 'dependency client identity: uid=%s container_id=%s observed_at=%s\n' "$DEP_CLIENT_UID" "$DEP_CLIENT_CONTAINER_ID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else DEPENDENCY_READY=false; printf '%s\n' '중단: dependency client UID 또는 container ID가 없음; exec stream 대상을 확정하지 않음' >&2; fi`

`DEP_LOG_RAW=''; if [ "$DEPENDENCY_READY" != true ] || [ "$START_READY" != true ] || [ "$LOG_TARGET_READY" != true ]; then printf '%s\n' '중단: DEPENDENCY_READY·START_READY·LOG_TARGET_READY가 아니다.' >&2; elif DEP_LOG_RAW="$(kubectl logs "$POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=200)"; then if grep -E -i -C 3 'ready|health|listen|bind|initializ|timeout|refused|denied|tls|upstream|dependency|dns|error|exception' <<<"$DEP_LOG_RAW"; then FILTER_RC=0; else FILTER_RC=$?; fi; if [ "$FILTER_RC" -eq 1 ]; then printf '%s\n' '필터 빈 결과: 오류 부재로 해석하지 않음'; elif [ "$FILTER_RC" -ne 0 ]; then printf '실패: dependency log filter rc=%s\n' "$FILTER_RC" >&2; fi; else LOG_PRODUCER_RC=$?; printf '실패: application logs producer rc=%s; 빈 필터와 분리하고 [[27. Pod 로그를 가져올 수 없는 경우]]로 이관\n' "$LOG_PRODUCER_RC" >&2; fi`

`DEPENDENCY_EXEC_READY=false; unset FRESH_DEP_CLIENT_JSON FRESH_DEP_CLIENT_UID FRESH_DEP_CLIENT_CONTAINER_ID; if [ "$DEPENDENCY_READY" != true ]; then printf '%s\n' '중단: DEPENDENCY_READY가 아니다.' >&2; elif FRESH_DEP_CLIENT_JSON="$(kubectl get pod "$DEP_CLIENT_POD" -n "$DEP_CLIENT_NS" -o json)" && FRESH_DEP_CLIENT_UID="$(jq -r '.metadata.uid // empty' <<<"$FRESH_DEP_CLIENT_JSON")" && FRESH_DEP_CLIENT_CONTAINER_ID="$(jq -r --arg c "$DEP_CLIENT_CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID // empty][0] // empty' <<<"$FRESH_DEP_CLIENT_JSON")" && [ "$FRESH_DEP_CLIENT_UID" = "$DEP_CLIENT_UID" ] && [ "$FRESH_DEP_CLIENT_CONTAINER_ID" = "$DEP_CLIENT_CONTAINER_ID" ]; then DEPENDENCY_EXEC_READY=true; printf 'DEPENDENCY_EXEC_READY=true client_uid=%s client_container_id=%s observed_at=%s\n' "$FRESH_DEP_CLIENT_UID" "$FRESH_DEP_CLIENT_CONTAINER_ID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else DEPENDENCY_READY=false; printf '중단: dependency exec 직전 UID 또는 containerID가 바뀌었으므로 exec를 실행하지 않는다.\n' >&2; fi`

`if [ "$DEPENDENCY_READY" != true ] || [ "$DEPENDENCY_EXEC_READY" != true ]; then printf '%s\n' '중단: DEPENDENCY_READY 또는 DEPENDENCY_EXEC_READY가 아니다.' >&2; elif kubectl exec "$DEP_CLIENT_POD" -n "$DEP_CLIENT_NS" -c "$DEP_CLIENT_CONTAINER" -- sh -c 'name="$1"; ns="$2"; if command -v getent >/dev/null 2>&1; then getent hosts "$name.$ns.svc.cluster.local"; elif command -v nslookup >/dev/null 2>&1; then nslookup "$name.$ns.svc.cluster.local"; else printf "%s\n" "dns_tool_missing=getent,nslookup" >&2; exit 127; fi' sh "$DEP_SERVICE" "$DEP_NS"; then printf '%s\n' '성공 gate: DNS 응답을 얻음; listener·HTTP·dependency application 정상은 아직 비보장'; else printf '%s\n' '실패: client container DNS 도구·CoreDNS·NetworkPolicy 또는 exec stream 계층; 정상 DNS로 해석하지 않음' >&2; fi`

`kubectl get service "$DEP_SERVICE" -n "$DEP_NS" -o custom-columns='SERVICE:.metadata.name,SELECTOR:.spec.selector,PORTS:.spec.ports'`와 `kubectl get endpointslice -n "$DEP_NS" -l "kubernetes.io/service-name=$DEP_SERVICE" -o wide`는 DNS 성공 뒤에도 endpoint address·port·ready를 확인할 때만 실행한다. 빈 결과는 정상이나 dependency 없음으로 해석하지 않고 selector·API 범위·controller·workload owner로 이관한다. 이 문서는 dependency application protocol·status를 임의로 가정하지 않으며 승인된 owner health check로 이관한다.

### 5. Sidecar 패턴

진입 증거는 application container가 ready인데 sidecar가 `ready=false`인 경우다. `$CONTAINER_CANDIDATES`에서 실제 sidecar 이름과 port 관계를 선택하고, `SELECTION_READY=true`일 때만 sidecar 상태를 읽는다. `kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .status.containerStatuses[*]}container={.name} ready={.ready} state={.state} last={.lastState}{"\n"}{end}'`의 성공 gate는 대상 UID와 sidecar 상태가 같은 관측 시각에 연결되는 것이다.

Sidecar가 일반 container로 포함되므로 application container가 ready여도 sidecar가 `ready=false`이면 `ContainersReady=False`와 `Ready=False`가 될 수 있다. probe Event가 있으면 [[19. Pod readiness probe가 실패하는 경우#1. probe 유형과 정확한 target|probe 진단]], 없으면 bootstrap·route·upstream·TLS/mTLS·dependency를 owner와 대조한다. `no healthy upstream`, route 부재·certificate 오류는 proxy와 upstream EndpointSlice로, 종료·OOM·restart는 [[17. Pod restartCount가 계속 증가하는 경우]]로 이동한다. sidecar 제거·재시작·condition patch는 진단이 아니다.

## 제한된 상태 변경과 안전 gate

probe·readinessGate·workload 설정 변경, rollout, Pod 삭제·재시작은 진단 명령에 섞지 않는다. 위험 변경을 별도로 검토할 때는 다음을 모두 닫는다.

- Trigger: 같은 Pod UID의 condition·Event·application·dependency·EndpointSlice 또는 실제 요청에 직접 근거가 있다.
- Authority: workload owner와 probe/gate/mesh/dependency 담당자 및 변경 승인자가 확인됐다.
- Scope: 단일 Pod인지 rollout인지, endpoint 감소·오류율·quorum·다른 tenant 영향이 계산됐다.
- Stop/Rollback: 새 Warning, restart 증가, endpoint 감소, gate 미갱신, dependency·요청 오류 또는 latency 증가 시 즉시 중단하고 승인된 rollback·owner 이관을 실행한다.
- Verification: 새 Pod가 생기면 이름·UID·node·시각을 다시 수집하고 container ready·gate·EndpointSlice·실제 요청·핵심 기능·재발 관찰을 새 identity로 검증한다.

## 정상화 검증

`NORMALIZATION_READY=false; NORMALIZATION_JSON=''; CURRENT_UID=''; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif NORMALIZATION_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && CURRENT_UID="$(jq -r '.metadata.uid // empty' <<<"$NORMALIZATION_JSON")"; then if [ -n "$CURRENT_UID" ] && [ "$CURRENT_UID" = "$POD_UID" ]; then NORMALIZATION_READY=true; jq -r '"POD: \(.metadata.name)\nUID: \(.metadata.uid)\nPhase: \(.status.phase // "-")\nPod Ready: \([.status.conditions[]? | select(.type=="Ready") | .status][0] // "Unknown")\nContainersReady: \([.status.conditions[]? | select(.type=="ContainersReady") | .status][0] // "Unknown")\nNode: \(.spec.nodeName // "-")\nObserved at: " + (now|todateiso8601)' <<<"$NORMALIZATION_JSON"; printf 'NORMALIZATION_READY=true uid=%s observed_at=%s\n' "$CURRENT_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '중단: Pod UID mismatch stored_uid=%s current_uid=%s; 모든 정상화를 중단하고 현재 identity를 처음부터 재수집\n' "$POD_UID" "${CURRENT_UID:--}" >&2; NORMALIZATION_READY=false; unset AUTO_READY POD_UID POD_IP NODE PHASE POD_READY CONTAINERS_READY CONTAINER_CANDIDATES CONTAINER_COUNT POD_RE CONTAINER CONTAINER_ID SELECTION_READY START_READY LOG_TARGET_READY; fi; else printf '%s\n' '중단: 정상화용 Pod API 조회 또는 UID 추출 실패; 정상화하지 않음' >&2; fi`

정상화는 `application 기능 → 실제 요청·핵심 기능 → listener/remote endpoint → EndpointSlice ready → readinessGate → Pod Ready → container ready` 순서로 역검증한다. `Running`, 한 번의 `Ready=True`, `endpoint ready=true`, HTTP 200은 각각 단독 정상화 근거가 아니다. 완화 성공과 근본 원인 해결을 별도로 기록한다.

## 증거 보존과 미검증

UTC 관측 시각, namespace, Pod UID·IP·node·phase, `Ready`·`ContainersReady`·custom condition·readinessGate, container별 ready/state/restart와 container ID, Event의 UID·시각·suffix, application·dependency logs 결과, Service selector·port·targetPort, EndpointSlice address·conditions·targetRef UID, client 위치·protocol·HTTP status·latency, 승인·변경·검증 결과를 보존한다. Secret·token·개인키·개인정보·전체 YAML·응답 body는 저장하지 않는다.

Pod 내부 도구, kubelet journal 접근, CNI·NetworkPolicy 구현, Service mesh, CoreDNS, 외부 DB/API/queue health 계약과 서비스 지표는 환경별 미검증이다. Kubernetes Server와 `kubectl` 기준은 `1.26.x`다.

## Prometheus 빠른 관측

PromQL은 문서에서 직접 수정하지 않는다. 같은 Bash에서 등록된 `$NS`, `$POD_RE`, `$POD_UID`와 선택된 `$CONTAINER`로 완성 문자열을 생성하고 bounded 출력만 Prometheus/Grafana에 붙여 넣는다. metric 부재·label 불일치·조회 범위 문제와 권한/API 조회 실패를 구분하며 빈 결과를 정상·0으로 해석하지 않는다.

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else printf '%s\n' "kube_pod_status_ready{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\",condition=\"false\"}==1"; fi`

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: CONTAINER 선택이 없다.' >&2; else CONTAINER_RE="$(printf '%s' "$CONTAINER" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; printf '%s\n' "kube_pod_container_status_ready{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\",container=~\"^${CONTAINER_RE}$\"}==0"; unset CONTAINER_RE; fi`

이 metric은 상태 시계열이 실제로 수집된 경우에만 보조 증거다. PromQL만으로 probe 실패·EndpointSlice 포함·실제 요청 성공을 확정하지 않는다.
