# Pod STATUS가 ImagePullBackOff·ErrImagePull인 경우

## 입력값과 빠른 수집

처음부터 Secret 원문, token, password, private key를 입력하거나 출력하지 않는다. 모든 값은 다음 네 종류로 관리한다.

| 종류 | 값 | 출처와 사용 시점 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 승인된 namespace와 Pod 이름을 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `NODE`, `PHASE`, `OBSERVED_AT`, `OWNER_CANDIDATES`, `CONTAINER_CANDIDATES`, `IMAGE_REFERENCE`, `IMAGE_PULL_POLICY`, `WAITING_REASON`, `WAITING_MESSAGE`, `CONTAINER_ID`, `SERVICE_ACCOUNT`, `WORKLOAD_SELECTOR` | 같은 Pod·owner API 응답에서 등록한다. UID와 관측 시각은 이름과 명령 성공보다 우선한다. `WORKLOAD_SELECTOR`는 owner의 실제 selector를 canonical registration한다. |
| 계산 후보값 | `POD_UID_RE`, `IMAGE_REFERENCE_RE` | Pod UID와 image reference를 로그 필터용 정규식으로 escape해 만든다. 생성 후 bounded 출력으로 확인한다. |
| 운영자 선택값 | `CONTAINER`, `OWNER_KIND`, `OWNER_NAME`, `SECRET_NAME`, `NODE_HOST`, `START_JOURNAL`, `END_JOURNAL`, `RUNTIME_KIND`, `REGISTRY_HOST`, `REGISTRY_IP`, `CRI_ENDPOINT`, `APPROVED_MANIFEST`, `APPROVED_REVISION`, `APPROVED_IMAGE_DIGEST`, `ROLLBACK_REVISION`, `ROLLBACK_IMAGE_DIGEST`, `APPROVAL_ID`, `NEW_POD` | API 출력과 승인 기록을 본 뒤 해당 상세 절 직전에 한 번 입력한다. `NODE_HOST`는 Kubernetes Node와 별도로 승인된 SSH 주소다. forward와 rollback의 revision/digest를 별도로 승인한다. 복수 후보를 첫 번째로 고르지 않는다. |

### 1. 실행 위치·도구·최초 입력

모든 local 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. `kubectl`은 실행 host에서 API server로 HTTPS 요청을 보내고, node 확인은 그 host에서 SSH로 node에 연결한다. `kubectl get/describe/events` read 권한과 승인된 node SSH·sudo journal/runtime 권한이 없으면 해당 분기에서 멈춘다. 새 Bash를 열면 변수와 gate가 사라지므로 이 절부터 다시 실행한다. `sh`, PowerShell, CMD에서는 실행하지 않는다.

**Bash와 필수 local 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed ssh curl date head tr; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 local 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 다음 단계로 진행하지 않는다. node에서 쓰는 `journalctl`, `systemctl`, `getent`, `ip`, `timedatectl`, `curl`, `crictl`은 해당 node의 별도 도구 gate를 통과하기 전까지 존재한다고 가정하지 않는다.

**최초 입력과 이전 파생값 초기화 — 같은 Bash에서 한 번 실행**

### 2. 기본값 자동 수집·등록

다음 명령은 Pod API 호출과 필수 field·container 후보 계산이 모두 성공한 경우에만 값을 등록한다. API 실패, UID·node·phase 누락, regular container 후보 0개이면 이전 값과 부분 결과를 남기지 않고 중단한다.

**Pod 상태·describe — 아래 한 줄 전체를 복사**

`FIRST_READY=false; CURRENT_POD_JSON=''; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif CURRENT_POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && pod_uid_guard "$CURRENT_POD_JSON" "$POD_UID" && jq -r '"Pod=" + .metadata.name + " UID=" + .metadata.uid + " Node=" + (.spec.nodeName // "-") + " Phase=" + (.status.phase // "-")' <<<"$CURRENT_POD_JSON" && kubectl describe pod "$POD" -n "$NS"; then FIRST_READY=true; printf 'FIRST_READY=true pod=%s uid=%s observed=%s\n' "$POD" "$POD_UID" "$OBSERVED_AT"; else FIRST_READY=false; printf '%s\n' '중단: Pod 상태 조회 또는 UID 검증 실패.' >&2; fi`

성공 gate는 `STATUS`, `READY`, `RESTARTS`, `NODE`, `AGE`, Pod UID와 실제 `Image`, `ImagePullPolicy`, waiting `Reason`, 최초 pull message가 같은 identity로 대조되는 것이다. `Running`이나 `Ready`는 image pull 이후 application 정상까지 보장하지 않는다.

**UID 제한 Event — 아래 한 줄 전체를 복사**

`EVENT_READY=false; if [ "$FIRST_READY" != true ]; then printf '%s\n' '중단: FIRST_READY가 아니다.' >&2; elif kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID" --sort-by=.metadata.creationTimestamp -o custom-columns='CREATED:.metadata.creationTimestamp,FIRST:.firstTimestamp,LAST:.lastTimestamp,EVENT:.eventTime,SERIES-LAST:.series.lastObservedTime,TYPE:.type,REASON:.reason,COUNT:.count,MESSAGE:.message'; then EVENT_READY=true; printf 'EVENT_READY=true uid=%s\n' "$POD_UID"; else printf '%s\n' '중단: UID 제한 Event 조회 실패. 빈 결과와 조회 실패를 구분하지 못한 채 진행하지 않는다.' >&2; fi`

Event의 `FIRST`, `LAST`, `EVENT`, `SERIES-LAST` 중 채워진 시각과 `COUNT`를 보존하고 최초 `Failed to pull image`를 `Back-off pulling image`보다 우선한다. Event가 보존되지 않았거나 빈 결과이면 오류 없음이 아니라 보존 기간·권한·조회 범위 문제 후보다. application current/previous log는 process가 시작되지 않았으므로 pull 원인 증거로 사용하지 않는다.

표는 길 안내이며 Secret 공개, 무조건 pull 재현 또는 상태 변경을 승인하지 않는다. 한 hop 성공은 다음 hop 또는 application 정상의 증거가 아니다.

### 1. image reference 또는 manifest 불일치

진입 증거: 최초 Event 또는 waiting message에 `manifest unknown`, `not found`가 있거나 Pod image와 승인 원본이 다를 때다. `invalid reference format`·`InvalidImageName`이면 registry 명령을 중단하고 [[08. Pod STATUS가 InvalidImageName·ErrImageNeverPull인 경우]]로 이동한다.

필수값: `$POD`, `$POD_UID`, `$CONTAINER`, `$IMAGE_REFERENCE`, `$IMAGE_PULL_POLICY`는 API와 최초 확인에서 등록했다. owner template 비교가 필요하면 `OWNER_READY=true`여야 한다.

연결 경로: 작업 PC/Bash → Kubernetes API server HTTPS → Pod와 controller template → registry HTTPS manifest/auth. API 조회 성공은 registry 도달·manifest 존재·pull 성공을 보장하지 않는다.

**Deployment owner template 읽기 — Deployment인 경우 아래 한 줄 전체를 복사**

`if [ "$OWNER_CHAIN_READY" != true ] || [ "$OWNER_CHAIN_KIND" != Deployment ]; then printf '%s\n' '중단: Deployment owner chain gate가 아니다. 실제 owner kind의 template과 승인 원본으로 이관한다.' >&2; elif kubectl get deployment "$OWNER_CHAIN_NAME" -n "$NS" -o jsonpath='{range .spec.template.spec.containers[?(@.name=="'$CONTAINER'")]}container={.name} image={.image} policy={.imagePullPolicy}{"\n"}{end}'; then printf 'template gate: Deployment UID=%s, Pod UID=%s의 image=%s policy=%s와 승인 원본을 대조한다.\n' "$OWNER_CHAIN_UID" "$POD_UID" "$IMAGE_REFERENCE" "$IMAGE_PULL_POLICY"; else printf '%s\n' '중단: owner template 조회 실패.' >&2; fi`

성공 gate는 Pod effective image/policy, owner template, 승인 원본의 registry host/repository/tag/digest가 같은 범위로 대조되는 것이다. `manifest unknown`·`not found`는 registry에 도달했지만 reference가 없거나 권한 없는 경로일 수 있다. `Always`·`IfNotPresent`는 원인 후보일 뿐 단독 원인이 아니다.

실패·빈 결과 의미: template 빈 출력은 해당 container가 없거나 owner kind/권한/field가 맞지 않다는 뜻이며 정상으로 해석하지 않는다. image나 policy를 임의로 바꾸지 말고 workload owner와 registry owner에게 원본·manifest·repository permission 확인을 이관한다.

### 2. Secret 이름과 ServiceAccount 연결

진입 증거: 최초 message가 `unauthorized` 또는 `denied`일 때만 이 절을 연다. Secret data·auth·username·password는 읽지 않는다.

필수값: `$SERVICE_ACCOUNT`는 Pod API에서 자동 등록했고, 참조 후보를 출력한 뒤 실제 이름을 선택한다.

**참조 Secret 선택과 metadata 확인 — 아래 한 줄 전체를 복사**

`SECRET_NAME='PASTE_IMAGE_PULL_SECRET_HERE'; AUTH_READY=false; SECRET_TYPE_TMP=''; POD_PULLS_TMP=''; SA_PULLS_TMP=''; POD_JSON=''; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && pod_uid_guard "$POD_JSON" "$POD_UID" && POD_PULLS_TMP="$(jq -r '.spec.imagePullSecrets[]?.name // empty' <<<"$POD_JSON")" && SA_PULLS_TMP="$(kubectl get serviceaccount "$SERVICE_ACCOUNT" -n "$NS" -o jsonpath='{.imagePullSecrets[*].name}')" && SECRET_TYPE_TMP="$(kubectl get secret "$SECRET_NAME" -n "$NS" -o jsonpath='{.type}')"; then if printf '%s\n' "$POD_PULLS_TMP $SA_PULLS_TMP" | tr ' ' '\n' | grep -Fxq "$SECRET_NAME" && [ "$SECRET_TYPE_TMP" = kubernetes.io/dockerconfigjson ]; then AUTH_READY=true; printf 'AUTH_READY=true serviceAccount=%s secret=%s type=%s\nPod imagePullSecrets: %s\nServiceAccount imagePullSecrets: %s\n' "$SERVICE_ACCOUNT" "$SECRET_NAME" "$SECRET_TYPE_TMP" "${POD_PULLS_TMP:--}" "${SA_PULLS_TMP:--}"; else printf '중단: 선택 Secret이 Pod 또는 ServiceAccount 참조와 type gate를 통과하지 못함 secret=%s type=%s\n' "$SECRET_NAME" "${SECRET_TYPE_TMP:--}" >&2; fi; else printf '%s\n' '중단: Pod UID 검증 또는 Pod·ServiceAccount·Secret metadata 조회 실패. 부분 결과를 사용하지 않는다.' >&2; fi`

성공 gate는 같은 namespace의 이름·참조 연결·Secret type만 확인하는 것이다. 이름과 type이 맞아도 registry 계정의 repository permission·만료·registry audit 성공은 보장하지 않는다. `Forbidden`은 Secret 부재가 아니라 현재 주체의 RBAC 거부일 수 있으므로 권한을 넓히지 말고 [[26. Pod가 ConfigMap·Secret을 찾지 못하는 경우]]의 API audit/RBAC owner로 이관한다.

### 3. 실패 node 범위

진입 증거: 한 node에서만 실패하거나 동일 image의 다른 Pod 결과가 필요한 경우다. node별 차이는 node-local DNS, proxy, CA, runtime cache 후보를 가르는 직접 증거다.

자동값: `$WORKLOAD_SELECTOR`는 owner API의 `matchLabels`·`matchExpressions`를 canonical selector로 등록한다. `matchExpressions`를 임의로 평탄화하거나 Pod label에서 추측하지 않는다.

**selector 등록과 bounded 범위 조회 — 아래 한 줄 전체를 복사**

### 5. node DNS·route·시간·TLS·proxy

진입 증거: runtime 오류가 특정 node와 registry endpoint로 좁혀졌을 때다. registry credential 없이 endpoint와 TLS만 확인한다.

필수값: `$REGISTRY_HOST`는 `$IMAGE_REFERENCE`에서 확인한 registry host, `$REGISTRY_IP`는 DNS 결과에서 선택한 실제 IP다. 둘을 임의로 만들지 않는다.

**registry endpoint 선택·node 경계 확인 — 아래 한 줄 전체를 복사**

`REGISTRY_HOST='PASTE_REGISTRY_HOST_HERE'; REGISTRY_IP='PASTE_REGISTRY_IP_HERE'; NODE_NETWORK_READY=false; DNS_OUT=''; ROUTE_OUT=''; TIME_OUT=''; HTTP_OUT=''; if [ "$RUNTIME_READY" != true ] || [ "$NODE_IDENTITY_READY" != true ]; then printf '%s\n' '중단: 확인된 runtime·Node identity gate가 아니다.' >&2; elif printf -v REGISTRY_HOST_Q '%q' "$REGISTRY_HOST" && printf -v REGISTRY_IP_Q '%q' "$REGISTRY_IP" && DNS_OUT="$(ssh -- "$NODE_HOST" "getent hosts $REGISTRY_HOST_Q")" && ROUTE_OUT="$(ssh -- "$NODE_HOST" "ip route get $REGISTRY_IP_Q")" && TIME_OUT="$(ssh -- "$NODE_HOST" 'timedatectl status')" && HTTP_OUT="$(ssh -- "$NODE_HOST" "curl -sS -o /dev/null -w 'HTTP_STATUS=%{http_code}\\n' --max-time 10 https://$REGISTRY_HOST_Q/v2/")"; then printf '=== DNS ===\n%s\n=== route ===\n%s\n=== time ===\n%s\n=== registry HTTPS ===\n%s\n' "$DNS_OUT" "$ROUTE_OUT" "$TIME_OUT" "$HTTP_OUT" | head -c 1800; printf '\n'; NODE_NETWORK_READY=true; else printf '%s\n' '중단: DNS·route·time·TLS transport 중 하나를 확인하지 못함. 비어 있는 결과를 정상으로 해석하지 않는다.' >&2; fi`

성공 gate에서 SSH transport, HTTPS/TLS transport, HTTP status를 분리한다. `SERVFAIL`·주소 미반환은 DNS 후보, route 부재는 node network 후보, `System clock synchronized: no`는 시간 후보, TLS certificate 오류는 CA/TLS 후보, timeout/refused는 route·firewall·proxy 후보다. `/v2/`의 `200`은 anonymous endpoint 접근, `401`은 인증 필요, `403`은 권한 거부, `429`는 rate limit 후보일 뿐 pull permission 성공을 보장하지 않는다. `-k`로 TLS 검증을 우회하지 않는다.

proxy endpoint, `NO_PROXY`, CA 경로만 읽고 credential·private key가 출력되면 저장하지 않는다. CRI-O 설정 경로는 배포판별로 미검증이면 node owner에게 확인받는다.

### 6. registry 인증·권한·rate limit·mirror

진입 증거: node DNS·route·TLS가 정상인데 runtime의 최초 message가 인증, manifest, quota 또는 mirror 문제를 가리킬 때다.

필수값: 앞 절의 `$HTTP_OUT`, `$WAITING_MESSAGE`, `$IMAGE_REFERENCE`와 registry owner에게 전달할 `$SECRET_NAME` metadata를 재사용한다.

반복 pull이나 동일 endpoint 재조회로 rate limit을 악화시키지 않는다. `200`은 endpoint 접근, `401`은 인증 필요, `403`은 권한 거부, `429`는 quota/rate limit 후보, `manifest unknown`은 reference 또는 mirror manifest 후보다. `WWW-Authenticate` header를 보존할 때 credential은 redaction한다.

다음 행동: registry owner에게 repository pull permission·credential 만료·`401/403` audit·`429` quota와 `Retry-After`·mirror upstream sync·manifest·TLS trust를 이관한다. node 오류면 node owner, Pod image/policy drift면 workload owner로 분리 이관한다. 이 절의 성공은 application 기능과 새 Pod Ready를 보장하지 않는다.

## 승인된 pull 재현의 별도 gate

`crictl pull`은 기본 진단 명령이 아니다. 다음 조건이 모두 충족될 때만 한 번 실행한다.

- 실제 kubelet의 CRI endpoint와 runtime, 실행 node와 권한이 확인됐다.
- `$CRI_ENDPOINT`가 kubelet 설정의 endpoint와 문자열 단위로 일치한다.
- 최초 Event·waiting message·image reference·policy·Secret 연결과 영향 범위가 기록됐다.
- 무인증 조회와 journal만으로 확정할 수 없고 registry owner와 workload owner가 재현을 승인했다.
- node cache 변경, registry quota 소비, 중단 기준과 rollback 방향이 승인 기록에 있다.

**kubelet 실제 CRI endpoint exact-match gate — 아래 한 줄 전체를 복사**

## 복구 전 안전 gate와 제한적 상태 변경

진단과 상태 변경을 분리한다. `kubectl set image`, `patch`, `edit`, Pod 직접 수정·삭제와 무조건 반복 pull로 승인된 원본을 우회하지 않는다.

위험 변경의 trigger는 image reference/policy 또는 auth 경로의 직접 근거가 확보되고 owner가 승인된 원본을 준비한 경우다. authority/approval, 대상 Deployment·selector·Pod UID, 영향, 중단 조건, rollback revision, 변경 전후 digest를 사건 기록에 남긴다. `Running`, `Ready`, rollout 완료는 registry와 실제 기능 정상을 보장하지 않는다.

**변경 후 새 Pod 선택과 UID 등록 — 아래 한 줄 전체를 복사**

`NEW_POD='PASTE_NEW_POD_HERE'; CANDIDATES_JSON=''; NEW_POD_JSON=''; VERIFY_POD="$POD"; if [ "$APPLY_READY" != true ] || [ "$OWNER_CHAIN_KIND" != Deployment ] || [ -z "$EXPECTED_NEW_POD_REVISION" ] || [ -z "$EXPECTED_NEW_POD_DIGEST" ]; then printf '%s\n' '중단: APPLY_READY·Deployment owner chain·expected revision/digest gate가 아니다. rollback 실패 후에는 new Pod를 검증하지 않는다.' >&2; elif CANDIDATES_JSON="$(kubectl get pods -n "$NS" -l "$WORKLOAD_SELECTOR" -o json)" && NEW_POD_JSON="$(kubectl get pod "$NEW_POD" -n "$NS" -o json)" && jq -r '.items[]? | "Pod=" + .metadata.name + " UID=" + .metadata.uid + " controller=" + (([.metadata.ownerReferences[]? | select(.controller == true)][0].name // "-")|tostring) + " created=" + .metadata.creationTimestamp' <<<"$CANDIDATES_JSON" | head -c 3000 && jq -e --arg n "$NEW_POD" --arg d "$EXPECTED_NEW_POD_DIGEST" 'any(.items[]?; .metadata.name == $n and any(.status.containerStatuses[]?; (((.imageID // "") | split("@")[ -1]) == $d)))' <<<"$CANDIDATES_JSON" >/dev/null && register_new_pod "$CANDIDATES_JSON" "$NEW_POD_JSON" "$OWNER_CHAIN_UID" "$EXPECTED_NEW_POD_REVISION" "$EXPECTED_NEW_POD_DIGEST" "$CHANGE_WINDOW_START"; then printf '새 후보 Pod=%s UID=%s가 selector·controller UID·생성 시각·revision=%s·digest=%s exact gate를 통과했다.\n' "$VERIFY_POD" "$NEW_POD_UID" "$EXPECTED_NEW_POD_REVISION" "$EXPECTED_NEW_POD_DIGEST"; else APPLY_READY=false; unset NEW_POD_UID; printf '%s\n' '중단: NEW_POD 후보 membership·controller chain·expected revision/image digest exact 검증 실패.' >&2; fi`

생성 시각, owner UID, revision, 승인 image/digest에 맞는 후보만 `NEW_POD`로 선택한다. 기존 `$POD`와 `$POD_UID`를 변경 후 검증에 재사용하지 않는다.

## 정상화 검증과 증거

정상화는 원인 파이프라인을 역순으로 확인한다. runtime pull 성공 → kubelet 새 Warning 중단 → 같은 node와 다른 node의 실패 범위 해소 → registry auth/permission/rate-limit/mirror 해결 → 원하는 Ready replica와 endpoint → 실제 요청 또는 핵심 기능 → 재발 관찰 순서다.

**검증 Pod 상태 — 아래 한 줄 전체를 복사**

`unset FUNCTION_READY`

실제 기능 계약과 요청/핵심 기능 결과를 owner가 확인해 `FUNCTION_READY=true`를 직접 등록하기 전에는 정상화하지 않는다. 자동화할 기능 계약 정보가 없으면 `FUNCTION_READY=false`인 채로 owner에게 이관한다.

`normalization_evidence_guard(){ local pod_json="$1" expected_uid="$2" expected_revision="$3" expected_digest="$4" c="$5" ck="$6" direct_kind direct_name direct_uid owner_json rs_json; direct_kind="$(jq -r '[.metadata.ownerReferences[]? | select(.controller == true)][0].kind // empty' <<<"$pod_json")" || return 1; direct_name="$(jq -r '[.metadata.ownerReferences[]? | select(.controller == true)][0].name // empty' <<<"$pod_json")" || return 1; direct_uid="$(jq -r '[.metadata.ownerReferences[]? | select(.controller == true)][0].uid // empty' <<<"$pod_json")" || return 1; [ "$OWNER_CHAIN_KIND" = Deployment ] && [ "$direct_kind" = ReplicaSet ] && [ -n "$direct_name" ] && [ -n "$direct_uid" ] || return 1; owner_json="$(kubectl get deployment "$OWNER_CHAIN_NAME" -n "$NS" -o json)" || return 1; rs_json="$(kubectl get replicaset "$direct_name" -n "$NS" -o json)" || return 1; jq -e --arg uid "$expected_uid" --arg c "$c" --arg ck "$ck" --arg digest "$expected_digest" '(if $ck == "init" then (.status.initContainerStatuses // []) else (.status.containerStatuses // []) end) as $statuses | [$statuses[] | select(.name == $c)] as $selected | (.metadata.uid == $uid) and (($selected | length) == 1) and ($selected[0].ready == true) and (($selected[0].state.waiting.reason // "") == "") and (((($selected[0].imageID // "") | if contains("@") then split("@")[ -1] else . end) == $digest))' <<<"$pod_json" >/dev/null && jq -e --arg uid "$OWNER_CHAIN_UID" '(.metadata.uid == $uid) and ((.status.observedGeneration // -1) == (.metadata.generation // -2)) and ((.spec.replicas // 1) == (.status.replicas // -1)) and ((.spec.replicas // 1) == (.status.updatedReplicas // -1)) and ((.spec.replicas // 1) == (.status.availableReplicas // -1)) and ((.spec.replicas // 1) == (.status.readyReplicas // -1))' <<<"$owner_json" >/dev/null && jq -e --arg direct "$direct_uid" --arg owner "$OWNER_CHAIN_UID" --arg revision "$expected_revision" '(.metadata.uid == $direct) and (.metadata.annotations["deployment.kubernetes.io/revision"] == $revision) and any(.metadata.ownerReferences[]?; .controller == true and .kind == "Deployment" and .uid == $owner)' <<<"$rs_json" >/dev/null; }`

`if [ -n "${NEW_POD:-}" ] && [ -n "${NEW_POD_UID:-}" ]; then VERIFY_POD="$NEW_POD"; fi`

`NORMALIZATION_READY=false; FUNCTION_READY="${FUNCTION_READY:-false}"; EXPECTED_POD_UID="${NEW_POD_UID:-$POD_UID}"; EXPECTED_POD_REVISION="${EXPECTED_NEW_POD_REVISION:-}"; EXPECTED_POD_DIGEST="${EXPECTED_NEW_POD_DIGEST:-}"; VERIFY_JSON=''; if [ "$SELECTION_READY" != true ] || [ -z "$EXPECTED_POD_UID" ] || [ -z "$EXPECTED_POD_REVISION" ] || [ -z "$EXPECTED_POD_DIGEST" ]; then printf '%s\n' '중단: SELECTION_READY 또는 expected new Pod UID/revision/image gate가 아니다.' >&2; elif VERIFY_JSON="$(kubectl get pod "$VERIFY_POD" -n "$NS" -o json)" && pod_uid_guard "$VERIFY_JSON" "$EXPECTED_POD_UID" && normalization_evidence_guard "$VERIFY_JSON" "$EXPECTED_POD_UID" "$EXPECTED_POD_REVISION" "$EXPECTED_POD_DIGEST" "$CONTAINER" regular; then if [ "$FUNCTION_READY" = true ] && kubectl describe pod "$VERIFY_POD" -n "$NS"; then NORMALIZATION_READY=true; printf 'NORMALIZATION_READY=true function_ready=true pod=%s uid=%s revision=%s digest=%s observed=%s\n' "$VERIFY_POD" "$EXPECTED_POD_UID" "$EXPECTED_POD_REVISION" "$EXPECTED_POD_DIGEST" "$OBSERVED_AT"; else NORMALIZATION_READY=false; printf '%s\n' '중단: FUNCTION_READY=true인 실제 기능 계약 증거가 없다. owner 확인으로 이관하고 정상화 미완료를 유지한다.' >&2; fi; else NORMALIZATION_READY=false; printf '%s\n' '중단: expected Pod UID/revision/image, Ready·waiting error 소멸 또는 owner replicas 수렴 검증 실패.' >&2; fi`

`Running` 하나, `Ready=true` 하나, `crictl pull` 성공 하나만으로 정상화하지 않는다. `describe`에 새 `Failed to pull image`·`Back-off pulling image`가 없어야 하고, 실제 기능과 관찰 창 동안 재발이 없어야 한다.

보존할 것: 수집 시각, context 식별자, namespace·Pod UID·node, container ID, image reference와 policy, 최초 Event의 채워진 시각·message, Secret 이름·namespace·type, kubelet/runtime의 비식별 오류 문자열, DNS/route/time/TLS와 HTTP status, 승인 ID, 변경 전후 digest, 원하는 Ready와 실제 기능 검증 결과. Secret data·credential 원문은 보존하지 않는다.

## Prometheus 빠른 관측

메트릭이 실제로 수집되는 경우에만 사용한다. PromQL을 문서에서 직접 수정하지 않고 등록된 변수로 완성본을 생성한다. 출력이 비어 있으면 정상·0·오류 없음이 아니라 metric 미수집, label 불일치, 조회 범위, 권한 또는 API 오류 후보다.

**waiting reason·image·node 범위 PromQL 생성 — 아래 한 줄 전체를 복사**

`PROMQL_READY=false; PROMQL_WAITING=''; PROMQL_INFO=''; PROMQL_NODE=''; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; else PROMQL_WAITING="$(printf 'kube_pod_container_status_waiting_reason{namespace="%s",pod="%s",uid="%s",reason=~"ImagePullBackOff|ErrImagePull"}==1' "$NS" "$POD" "$POD_UID")"; PROMQL_INFO="$(printf 'kube_pod_container_info{namespace="%s",pod="%s",uid="%s"}' "$NS" "$POD" "$POD_UID")"; PROMQL_NODE="$(printf 'count by(node)((kube_pod_container_status_waiting_reason{namespace="%s",pod="%s",uid="%s",reason=~"ImagePullBackOff|ErrImagePull"}==1)*on(namespace,pod,uid)group_left(node)kube_pod_info{namespace="%s",pod="%s",uid="%s"})' "$NS" "$POD" "$POD_UID" "$NS" "$POD" "$POD_UID")"; if [ -n "$PROMQL_WAITING" ] && [ -n "$PROMQL_INFO" ] && [ -n "$PROMQL_NODE" ]; then PROMQL_READY=true; printf 'WAITING: %s\nINFO: %s\nNODE: %s\n' "$PROMQL_WAITING" "$PROMQL_INFO" "$PROMQL_NODE" | head -c 1200; printf '\n'; else printf '%s\n' '중단: PromQL 생성 결과가 비어 있다.' >&2; fi; fi`

`PROMQL_READY=true` 뒤 출력된 각 완성 한 줄만 Prometheus 또는 Grafana에 붙여 넣는다. `kube_pod_container_info`의 image/image_id와 node join을 확인하되 metric 부재는 API 조회 실패와 구분하고 `$POD_UID`·UTC 관측 시각을 함께 기록한다.
