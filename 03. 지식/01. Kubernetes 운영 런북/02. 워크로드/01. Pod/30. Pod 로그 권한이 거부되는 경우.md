# Pod 로그 권한이 거부되는 경우

## 입력값과 빠른 수집

| 종류 | 값 | 출처와 사용 시점 |
|---|---|---|
| 최초 입력 | `CTX`, `NS`, `POD` | 운영자가 승인된 context·namespace·Pod를 처음 한 번 입력한다. |
| API 자동값 | `POD_UID`, `NODE`, `PHASE`, `OBSERVED_AT`, `ACTUAL_USER`, `ACTUAL_GROUPS`, `CAN_POD`, `CAN_LOG`, `ROLE_REF_KIND`, `ROLE_REF_NAME` | Pod API·허용된 SelfSubjectReview·동일 대상 `can-i`·확인된 RoleBinding에서 자동 수집한다. whoami 거부 시 actor 값은 비워 두고 audit에서 확인한다. |
| 계산 후보값 | `SUBJECT_NAME`, `SUBJECT_NAMESPACE`, `NS_RE`, `POD_RE`, `POD_UID_RE`, `LOG_URL`, API query 문자열 | 오류 주체와 등록값으로 만들며 subject·regex·URL·query를 bounded 출력 뒤 사용한다. 해석할 수 없는 주체 형식은 RBAC owner에게 이관한다. |
| 운영자 선택값 | 오류에서 확인한 `SUBJECT`, `SUBJECT_KIND`, `CONTAINER`, `START_RFC3339`, `END_RFC3339`, `ROLEBINDING`, 승인된 `APPROVED_GROUP`, 필요 시 `CLUSTERROLEBINDING` | 오류 원문의 `User`·`Group`·`ServiceAccount` kind와 주체 값을 함께 확인하고, 자동 출력·RBAC owner·승인 문서에서 출처를 확인한 뒤 선택한다. token·Secret은 값으로 받지 않는다. |
| canonical audit fallback 값 | `AUDIT_RECORD_FILE`, `AUDIT_REQUEST_UID`, `AUDIT_REQUEST_TIME`, `AUDIT_REQUEST_URI`, `AUDIT_START_RFC3339`, `AUDIT_END_RFC3339`, `AUDIT_USER`, `AUDIT_GROUPS`, `AUDIT_RESPONSE_CODE` | whoami 실패 때 audit owner가 전달한 단일 metadata event와 timestamp window, 별도 current Pod API 재검증에서 strict relation으로 등록한다. user 값은 exact 비교에만 사용하고 출력하지 않는다. |
| feature gate 선택값 | `APISelfSubjectReview` | cluster owner가 확인한 단일 `true`/`false`만 받는다. `true`일 때만 `kubectl alpha auth whoami`를 시도하고, `false`·미확정은 실행하지 않고 canonical audit fallback으로 이동한다. |

### 1. 실행 위치·도구·최초 입력

모든 일반 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. 경로는 `실행 host → kubectl client → API server HTTPS → authorization/admission → Pod log subresource → node/kubelet/runtime → container log`다. `pods` 조회 권한, `pods/log`의 `get` 판정, API audit 접근은 서로 다른 전제다. API server 도달은 authorization·kubelet·application 정상의 증거가 아니며 TLS 검증을 끄지 않는다.

**필수 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date mktemp head wc; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 다음 단계로 진행하지 않는다. kubeconfig raw credential, token, Secret data, 인증서 개인키는 출력하지 않는다.

**입력·이전 상태 초기화 — 같은 Bash에서 한 번 실행**

`unset INPUT_READY AUTO_READY ACTOR_READY ACTOR_SUBJECT_READY SELECTION_READY SUBJECT_PARSE_READY AUTHZ_READY UID_READY START_READY START_CANONICAL END_CANONICAL RAW_READY AUDIT_READY AUDIT_RANGE_READY RBAC_BINDING_READY RBAC_READY CLUSTER_RBAC_READY CRB_INPUT_READY CRB_SUBJECT_READY CRB_ROLE_REF_READY CRB_RULE_READY QUERY_READY APISelfSubjectReview APISelfSubjectReview_READY CTX NS POD POD_UID NODE PHASE OBSERVED_AT POD_JSON ACTUAL_USER ACTUAL_GROUPS SUBJECT SUBJECT_KIND SUBJECT_NAME SUBJECT_NAMESPACE CONTAINER START_RFC3339 END_RFC3339 ROLEBINDING APPROVED_GROUP CLUSTERROLEBINDING NS_RE POD_RE POD_UID_RE CONTAINER_RE LOG_URL CAN_POD CAN_LOG ROLE_REF_KIND ROLE_REF_NAME RB_JSON; APISelfSubjectReview_READY=false; CTX='PASTE_CONTEXT_HERE'; NS='PASTE_NAMESPACE_HERE'; POD='PASTE_POD_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: 도구 확인을 먼저 통과한다.' >&2; elif [ -z "$CTX" ] || [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: CTX, NS, POD를 입력한다.' >&2; elif kubectl --context "$CTX" get pod "$POD" -n "$NS" >/dev/null 2>&1; then INPUT_READY=true; export CTX NS POD; printf 'INPUT_READY=true context=%s namespace=%s pod=%s\n' "$CTX" "$NS" "$POD"; else printf '중단: context·namespace·Pod 조회 실패\n' >&2; fi`

`INPUT_READY=true`가 아니면 context·namespace·Pod 이름·API 권한을 확인하고 멈춘다. `--all-namespaces`, wildcard resource/verb, 다른 namespace broad query를 권한 진단의 기본값으로 사용하지 않는다.

### 2. API 자동 수집과 actor 경계

**Pod identity 자동 등록 — 아래 한 줄 전체를 복사**

`unset AUTO_READY APISelfSubjectReview APISelfSubjectReview_READY POD_UID NODE PHASE OBSERVED_AT; APISelfSubjectReview_READY=false; AUTO_READY=false; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif POD_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && POD_UID_TMP="$(jq -r '.metadata.uid // empty' <<<"$POD_JSON")" && NODE_TMP="$(jq -r '.spec.nodeName // "-"' <<<"$POD_JSON")" && PHASE_TMP="$(jq -r '.status.phase // "-"' <<<"$POD_JSON")" && OBSERVED_AT_TMP="$(date -u '+%Y-%m-%dT%H:%M:%SZ')" && [ -n "$POD_UID_TMP" ]; then printf '%s\n' '=== Pod 대상 ==='; jq -r --arg observed "$OBSERVED_AT_TMP" '"이름: \(.metadata.name)\nUID: \(.metadata.uid)\nNode: \(.spec.nodeName // "-")\nPhase: \(.status.phase // "-")\nPod 생성 시각(UTC): \(.metadata.creationTimestamp // "-")\n관측 시각(UTC): \($observed)\nContainer: \([.spec.containers[]?.name] | join(", "))"' <<<"$POD_JSON"; POD_UID="$POD_UID_TMP"; NODE="$NODE_TMP"; PHASE="$PHASE_TMP"; OBSERVED_AT="$OBSERVED_AT_TMP"; AUTO_READY=true; export POD_UID NODE PHASE OBSERVED_AT; printf 'AUTO_READY=true 관측시각(UTC)=%s\n' "$OBSERVED_AT"; else printf '%s\n' '중단: Pod API 조회 실패 또는 UID 없음; 자동값을 무효화한다.' >&2; unset POD_JSON POD_UID NODE PHASE OBSERVED_AT; fi`

성공 gate는 대상 Pod의 UID·node·phase·생성 시각·UTC 관측 시각이 함께 보이는 것이다. `Running`은 application readiness나 `pods/log` 허용을 보장하지 않는다. `AUTO_READY=true`가 아니면 다음 단계로 진행하지 않는다.

SelfSubjectReview feature는 cluster owner의 확인값을 단일 입력으로 받는다. 확인되지 않은 feature를 client capability나 `whoami` 오류만으로 true로 추정하지 않는다.

**SelfSubjectReview feature gate — whoami 전에 같은 Bash에서 한 번 실행**

`APISelfSubjectReview='PASTE_APISelfSubjectReview_HERE'; APISelfSubjectReview_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif [ "$APISelfSubjectReview" = true ] || [ "$APISelfSubjectReview" = false ]; then APISelfSubjectReview_READY=true; export APISelfSubjectReview APISelfSubjectReview_READY; printf 'APISelfSubjectReview_READY=true value=%s source=cluster-owner-confirmation\n' "$APISelfSubjectReview"; else printf '%s\n' 'APISelfSubjectReview_READY=false; cluster owner의 true/false 단일 확인이 없어 whoami를 실행하지 않고 canonical audit fallback으로 이동한다.' >&2; unset APISelfSubjectReview; fi`

`APISelfSubjectReview_READY=true`이고 값이 `true`인 경우에만 `whoami`를 시도한다. `false` 또는 미확정은 인증 실패로 해석하지 않고 바로 audit fallback으로 이동한다.

**현재 actor 확인 — 아래 한 줄 전체를 복사**

`unset ACTOR_READY ACTUAL_USER ACTUAL_GROUPS; ACTOR_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif [ "$APISelfSubjectReview_READY" != true ] || [ "$APISelfSubjectReview" != true ]; then printf '%s\n' 'APISelfSubjectReview가 cluster owner에 의해 true로 확인되지 않아 whoami를 실행하지 않고 canonical audit fallback으로 이동한다.' >&2; unset WHOAMI_JSON ACTUAL_USER ACTUAL_GROUPS; elif WHOAMI_JSON="$(kubectl --context "$CTX" alpha auth whoami -o json 2>/dev/null)" && ACTUAL_USER_TMP="$(jq -r '.status.userInfo.username // empty' <<<"$WHOAMI_JSON")" && [ -n "$ACTUAL_USER_TMP" ]; then ACTUAL_GROUPS_TMP="$(jq -r '.status.userInfo.groups[]? // empty' <<<"$WHOAMI_JSON")"; ACTUAL_USER="$ACTUAL_USER_TMP"; ACTUAL_GROUPS="$ACTUAL_GROUPS_TMP"; ACTOR_READY=true; export ACTUAL_USER ACTUAL_GROUPS; printf '%s\n' 'ACTOR_READY=true source=SelfSubjectReview user/groups=registered-not-printed'; else printf '%s\n' 'ACTOR_READY=false; whoami가 거부·미지원이면 canonical audit fallback을 실행한다.' >&2; unset WHOAMI_JSON ACTUAL_USER ACTUAL_GROUPS; fi`

whoami 실패는 권한 허용의 증거도 오류 actor 부재의 증거도 아니다. 반복 호출하거나 credential을 확인하지 말고, audit 담당자가 제공한 raw log가 아닌 **단일 canonical metadata audit record**에서 같은 요청의 identity를 등록한다. `user.username`·`user.groups`는 exact relation 판정용 Bash 변수에만 넣고 출력하지 않는다.

**Kubernetes 1.26 whoami 실패용 canonical audit fallback — `can-i` 전에 같은 Bash에서 실행**

`AUDIT_RECORD_FILE`에는 audit owner가 필터링해 전달한 단일 `audit.k8s.io/v1` metadata record만 둔다. `auditID`(요청 UID), `requestReceivedTimestamp`, `verb=get`, core API `objectRef.apiGroup`/`apiVersion`, `resource=pods`, `subresource=log`, namespace/name, optional `uid`, exact `requestURI`, `user.username`, `user.groups`, `responseStatus.code=403`이 있어야 하며 raw source IP·인증정보·로그 원문은 넣지 않는다. `objectRef.uid`가 비어 있거나 없을 수 있으므로 current Pod UID와 `metadata.creationTimestamp`는 별도 API GET으로 재검증한다.

```bash

then AUDIT_REQUEST_UID="$(printf '%s\n' "$AUDIT_RECORD_JSON" | jq -r '.auditID')"; AUDIT_REQUEST_TIME="$(printf '%s\n' "$AUDIT_RECORD_JSON" | jq -r '.requestReceivedTimestamp')"; AUDIT_REQUEST_URI="$(printf '%s\n' "$AUDIT_RECORD_JSON" | jq -r '.requestURI')"; ```

`if [ "$ACTOR_READY" = true ] && [ "$AUDIT_FALLBACK_READY" != true ]; then unset AUDIT_START_RFC3339 AUDIT_END_RFC3339; fi`

성공 gate는 `auditID` 단일 event의 `requestReceivedTimestamp`가 strict window 안에 있고, `objectRef`·`requestURI`가 현재 context의 namespace·Pod name·core `v1`·`pods/log`·`get` 요청과 정확히 맞으며, 별도 current Pod API GET의 UID/name/namespace equality와 strict `metadata.creationTimestamp` epoch `<= requestReceivedTimestamp`가 함께 성립하는 것이다. fallback은 identity를 추측하거나 credential을 재현하지 않으며, canonical record의 request UID/time/resource/lifecycle relation을 보존한 채 값은 출력하지 않는다. `ACTOR_READY=true`가 되기 전에는 subject relation과 `can-i`를 실행하지 않는다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | `kubectl logs` 또는 Pod log subresource 요청이 `Forbidden`, `is forbidden`, `cannot get resource "pods/log"`로 거부된 경우 |
| 적용 | context·namespace·Pod UID·resource/subresource·verb·실제 요청 주체를 대조할 수 있는 경우 |
| 제외 | 인증·API 연결·kubelet·node log 접근은 [[27. Pod 로그를 가져올 수 없는 경우]], container 선택은 [[29. 멀티 컨테이너 Pod의 로그 대상을 특정할 수 없는 경우]]로 이동한다. |

검색 문자열: `User ... cannot get resource "pods/log"`, `User ... cannot get resource "pods"`, `is forbidden`, `Forbidden`, `authorization.k8s.io/decision`, `responseStatus.code=403`.

오류의 `pods/log` `get`과 일반 `pods` `get`은 별도 권한이다. RoleBinding을 임의로 만들거나 수정하지 않고, `cluster-admin`, wildcard, 전 namespace 허용, 승인되지 않은 `--as`, TLS 우회, token·Secret·로그 원문 저장을 복구 방법으로 제시하지 않는다.

오류 원문에서 확인한 요청 주체만 운영자 선택값으로 기록한다.

**오류 주체·container 선택 — 아래 한 줄 전체를 복사**

`SUBJECT='PASTE_SUBJECT_HERE'; SUBJECT_KIND='PASTE_SUBJECT_KIND_HERE'; CONTAINER='PASTE_CONTAINER_HERE'; SELECTION_READY=false; SUBJECT_PARSE_READY=false; SUBJECT_NAME=''; SUBJECT_NAMESPACE=''; SA_PART=''; if [ "$AUTO_READY" != true ] || [ -z "$SUBJECT" ] || [ -z "$SUBJECT_KIND" ] || [ -z "$CONTAINER" ]; then printf '%s\n' '중단: Pod 자동값과 오류 원문의 SUBJECT·SUBJECT_KIND·선택 container가 필요하다.' >&2; elif [ "$SUBJECT_KIND" != User ] && [ "$SUBJECT_KIND" != Group ] && [ "$SUBJECT_KIND" != ServiceAccount ]; then printf '중단: SUBJECT_KIND는 User, Group, ServiceAccount 중 하나여야 한다.\n' >&2; elif jq -e --arg c "$CONTAINER" '([.spec.containers[]? | select(.name==$c)] | length)==1' <<<"$POD_JSON" >/dev/null; then case "$SUBJECT_KIND" in ServiceAccount) case "$SUBJECT" in system:serviceaccount:*:*) SA_PART="${SUBJECT#system:serviceaccount:}"; SUBJECT_NAMESPACE="${SA_PART%%:*}"; SUBJECT_NAME="${SA_PART#*:}"; if [ -n "$SUBJECT_NAMESPACE" ] && [ -n "$SUBJECT_NAME" ] && [[ "$SUBJECT_NAMESPACE" != *:* ]] && [[ "$SUBJECT_NAME" != *:* ]]; then SUBJECT_PARSE_READY=true; fi;; *) printf '중단: ServiceAccount SUBJECT는 system:serviceaccount:namespace:name 형식이어야 한다.\n' >&2;; esac;; User|Group) SUBJECT_NAME="$SUBJECT"; SUBJECT_NAMESPACE=''; if [ -n "$SUBJECT_NAME" ]; then SUBJECT_PARSE_READY=true; fi;; esac; if [ "$SUBJECT_PARSE_READY" = true ]; then SELECTION_READY=true; export SUBJECT SUBJECT_KIND CONTAINER SUBJECT_NAME SUBJECT_NAMESPACE SUBJECT_PARSE_READY SELECTION_READY; printf 'SELECTION_READY=true subject=%s expected-kind=%s expected-name=%s expected-namespace=%s container=%s\n' "$SUBJECT" "$SUBJECT_KIND" "$SUBJECT_NAME" "${SUBJECT_NAMESPACE:--}" "$CONTAINER"; else printf '중단: 오류 SUBJECT에서 kind/name/namespace를 안전하게 해석하지 못함 subject=%s kind=%s; 사용자의 Bash는 종료하지 않는다.\n' "$SUBJECT" "$SUBJECT_KIND" >&2; fi; else printf '중단: container가 Pod spec에 정확히 하나로 존재하지 않음\n' >&2; fi`

`SELECTION_READY=true`는 이름과 오류 주체를 등록한 것뿐이며 권한을 증명하지 않는다. container가 없거나 오류가 `Defaulted container`이면 [[29. 멀티 컨테이너 Pod의 로그 대상을 특정할 수 없는 경우]]로 반환한다.

**actual user/groups와 selected SUBJECT exact relation — 아래 한 줄 전체를 복사**

`unset ACTOR_SUBJECT_READY; ACTOR_SUBJECT_READY=false; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif [ "$ACTOR_READY" != true ]; then printf '%s\n' '중단: actual user/groups를 SelfSubjectReview 또는 동일 audit record에서 확인하지 못했다; SUBJECT와 권한을 연결하지 않는다.' >&2; elif [ "$SUBJECT_KIND" = Group ] && printf '%s\n' "$ACTUAL_GROUPS" | grep -Fqx -- "$SUBJECT_NAME"; then ACTOR_SUBJECT_READY=true; export ACTOR_SUBJECT_READY; printf 'ACTOR_SUBJECT_READY=true relation=Group exact-match=true identity=redacted\n'; elif [ "$SUBJECT_KIND" != Group ] && [ "$ACTUAL_USER" = "$SUBJECT" ]; then ACTOR_SUBJECT_READY=true; export ACTOR_SUBJECT_READY; printf 'ACTOR_SUBJECT_READY=true relation=%s exact-match=true identity=redacted\n' "$SUBJECT_KIND"; else printf '중단: actual user/groups와 selected SUBJECT exact relation 불일치 kind=%s identity=redacted\n' "$SUBJECT_KIND" >&2; fi`

User와 ServiceAccount는 selected `SUBJECT`가 `ACTUAL_USER`와 정확히 같아야 한다. Group은 selected `SUBJECT_NAME`이 `ACTUAL_GROUPS`의 한 줄과 정확히 같아야 하며 substring·부분 group 이름을 허용하지 않는다. whoami가 거부되면 audit의 동일 request `user.username`·`user.groups`가 이 exact relation을 대체 증명해야 하며, 확인 전에는 `ACTOR_SUBJECT_READY`를 열지 않는다.

## 최초 확인

**named 권한 최초 확인 — 아래 한 줄 전체를 복사**

`unset AUTHZ_READY UID_READY CAN_POD CAN_LOG; AUTHZ_READY=false; UID_READY=false; if [ "$SELECTION_READY" != true ] || [ "$ACTOR_SUBJECT_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY와 actual user/groups·SUBJECT exact relation gate가 필요하다.' >&2; elif CHECK_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && CHECK_UID="$(jq -r '.metadata.uid // empty' <<<"$CHECK_JSON")" && [ "$CHECK_UID" = "$POD_UID" ] && CAN_POD="$(kubectl --context "$CTX" auth can-i get "pods/$POD" -n "$NS")" && CAN_LOG="$(kubectl --context "$CTX" auth can-i get "pods/$POD" --subresource=log -n "$NS")"; then if [ "$CAN_POD" = yes ] || [ "$CAN_POD" = no ]; then if [ "$CAN_LOG" = yes ] || [ "$CAN_LOG" = no ]; then AUTHZ_READY=true; UID_READY=true; export CAN_POD CAN_LOG AUTHZ_READY UID_READY; printf 'AUTHZ_READY=true UID_READY=true named-pods=%s named-pods/log=%s subject-kind=%s subject=%s actor=verified-redacted\n' "$CAN_POD" "$CAN_LOG" "$SUBJECT_KIND" "$SUBJECT"; else printf '중단: pods/log can-i의 yes/no가 아닌 출력=%s\n' "$CAN_LOG" >&2; fi; else printf '중단: pods can-i의 yes/no가 아닌 출력=%s\n' "$CAN_POD" >&2; fi; else printf '중단: 현재 UID 재확인 또는 can-i 호출 실패; 권한 허용으로 단정하지 않는다.\n' >&2; unset CHECK_JSON CHECK_UID CAN_POD CAN_LOG; fi`

성공 gate는 같은 context·namespace·Pod의 named `pods`와 `pods/log` 결과가 각각 `yes` 또는 `no`로 분리된 것이다. `pods=yes`만으로 logs 권한을 판단하지 않는다. `AUTHZ_READY=true`는 can-i의 yes/no 판정이 준비됐다는 뜻이지 API log 호출 성공이 아니다. can-i 호출 자체가 실패하면 `AUTHZ_READY=false`로 멈추고, can-i가 `yes/no`를 반환한 뒤 log API가 실패하면 2절의 API transport·HTTP status 경로로 분리한다. `pods/log=no`이면 4절로 이동한다. `AUTHZ_READY=true`가 아니면 다음 명령을 실행하지 않는다.

## 관측별 진단 경로

### 1. resource·verb·주체 고정

진입 증거: 오류 원문에 `User`·`Group`·ServiceAccount identity, namespace, resource/subresource와 `Forbidden`이 있다. 최초 입력은 오류에서 확인한 `SUBJECT_KIND`와 `SUBJECT`이며 출처는 오류 원문이다. `ACTUAL_USER`·`ACTUAL_GROUPS`는 whoami 또는 동일 audit record에서 확인하며 오류 주체와 다르면 합치지 않는다.

성공 gate는 `pods`와 `pods/log` named `get`을 같은 context·namespace·Pod UID에 대해 비교한 것이다. `pods/log` `no`는 현재 actor의 subresource 권한 부족 범위의 증거다. `pods get=yes`는 log subresource 허용이나 실제 log stream 성공을 보장하지 않는다.

실패·빈 결과: `can-i` 실패는 권한 허용이 아니라 API·인증·client 실패 후보다. `SUBJECT`가 비어 있으면 오류 원문과 audit를 다시 확인하고 승인되지 않은 impersonation으로 채우지 않는다. 다음은 4절의 Role/Binding 범위 또는 3절 audit다.

### 2. kubectl logs와 log API 분리

진입 증거: named can-i 결과와 일반 `kubectl logs` 결과가 다르거나 raw log endpoint도 확인해야 한다. 최초 필요값은 API 자동 `POD_UID`와 운영자 선택 `CONTAINER`, `START_RFC3339`다.

**로그 시작 시각 등록 — 같은 Bash에서 한 번 실행**

`START_RFC3339="${AUDIT_START_RFC3339:-PASTE_START_RFC3339_HERE}"; START_READY=false; unset START_CANONICAL; if [[ ! "$START_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then printf '중단: START_RFC3339는 strict UTC Z 형식이어야 함 %s\n' "$START_RFC3339" >&2; elif START_CANONICAL="$(date -u -d "$START_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" && [ "$START_CANONICAL" = "$START_RFC3339" ]; then START_READY=true; export START_RFC3339 START_CANONICAL START_READY; printf 'START_READY=true strict_utc=true start=%s\n' "$START_RFC3339"; else printf '중단: START_RFC3339 canonical round-trip 실패 %s\n' "$START_RFC3339" >&2; fi`

`START_READY=true`가 아니면 로그 요청을 실행하지 않는다. 연결 경로는 `작업 PC/Bash → kubectl client → API server HTTPS → authorization/admission → pods/log → node/kubelet/runtime → container`다. API server 주소·port는 kubeconfig/API 앞단, kubelet·runtime 주소·socket은 클러스터 구성에서 결정한다.

**kubectl logs 제한 조회 — 아래 한 줄 전체를 복사**

`if [ "$AUTHZ_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$UID_READY" != true ] || [ "$START_READY" != true ]; then printf '%s\n' '중단: AUTHZ_READY, selection·UID·start gate가 필요하다.' >&2; else kubectl --context "$CTX" -n "$NS" logs "$POD" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=50 | grep -E -i -C 3 'error|exception|timeout|refused|denied|permission|fatal'; rc=${PIPESTATUS[0]}; if [ "$rc" -ne 0 ]; then printf 'kubectl logs API call 실패 rc=%s; can-i 결과와 분리해 HTTP/API 계층을 확인한다.\n' "$rc" >&2; else printf '%s\n' 'kubectl logs API call 성공; filter 무출력은 오류 부재가 아니다.'; fi; fi`

`Forbidden`이면 HTTP/API authorization이 거부된 것이며 4절로 이동한다. `connection refused`, `i/o timeout`, `x509`는 인증인가 증거가 아니라 API/kubelet 경로 문제로 [[27. Pod 로그를 가져올 수 없는 경우]]에 넘긴다. filter 무출력은 오류 없음이 아니며 민감정보가 보이면 출력·저장을 중단한다.

raw log endpoint를 확인할 때도 TLS 검증을 우회하지 않는다. URL은 등록값으로 만들고 원문 로그를 출력하지 않는다.

**raw log API URL 생성·요청 — 아래 한 줄 전체를 복사**

`RAW_READY=false; if [ "$AUTHZ_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$UID_READY" != true ] || [ "$START_READY" != true ]; then printf '%s\n' '중단: AUTHZ_READY, selection·UID·start gate가 필요하다.' >&2; else LOG_URL="/api/v1/namespaces/$NS/pods/$POD/log?container=$CONTAINER&sinceTime=$START_RFC3339&tailLines=20&timestamps=true"; RAW_BODY="$(mktemp)"; RAW_TRACE="$(mktemp)"; if kubectl --context "$CTX" get --raw "$LOG_URL" -v=6 >"$RAW_BODY" 2>"$RAW_TRACE"; then HTTP_STATUS="$(grep -Eo 'Response Status: [0-9]{3}' "$RAW_TRACE" | head -n 1 | grep -Eo '[0-9]{3}' || true)"; RAW_BYTES="$(wc -c <"$RAW_BODY")"; if [ "$HTTP_STATUS" = 200 ]; then RAW_READY=true; printf 'RAW_READY=true transport=success HTTP=%s API=data-stream bytes=%s\n' "$HTTP_STATUS" "$RAW_BYTES"; else printf 'RAW_READY=false transport=success HTTP status evidence missing or unexpected=%s\n' "${HTTP_STATUS:--}" >&2; fi; else rc=$?; HTTP_STATUS="$(grep -Eo 'Response Status: [0-9]{3}' "$RAW_TRACE" | head -n 1 | grep -Eo '[0-9]{3}' || true)"; printf 'RAW_READY=false transport-or-API failure rc=%s HTTP=%s\n' "$rc" "${HTTP_STATUS:--}" >&2; head -c 500 "$RAW_TRACE" >&2; printf '\n'; fi; rm -f "$RAW_BODY" "$RAW_TRACE"; export LOG_URL RAW_READY; fi`

transport 실패, API HTTP status 오류(`403`, `404`, `5xx`)와 data stream 빈 결과를 분리한다. raw 요청 성공은 log endpoint transport와 API 응답 전달만 보장하며 application 오류 부재나 로그 pipeline 전체 정상은 보장하지 않는다. HTTP 403이면 4절, 404/NotFound면 Pod UID·이름·namespace·container를 다시 대조하고, 연결 오류면 [[27. Pod 로그를 가져올 수 없는 경우]]로 이동한다.

### 3. can-i와 API audit 대조

진입 증거: `CAN_LOG=yes`인데 실제 log 호출이 403이거나, `CAN_LOG=no`인데 오류에 표시된 subject·context가 다르다. 최초 필요값은 `POD_UID`, `SUBJECT`, `START_RFC3339`, `END_RFC3339`이며 각각 API·오류·운영자 시간 선택값이다.

**audit 시간 범위 등록 — 같은 Bash에서 한 번 실행**

`END_RFC3339="${AUDIT_END_RFC3339:-PASTE_END_RFC3339_HERE}"; AUDIT_READY=false; AUDIT_RANGE_READY=false; unset START_CANONICAL_TMP END_CANONICAL_TMP START_EPOCH_TMP END_EPOCH_TMP; if [ "$START_READY" != true ] || [ -z "${START_RFC3339:-}" ] || [ -z "$END_RFC3339" ]; then printf '중단: START_RFC3339와 END_RFC3339를 먼저 유효한 UTC 값으로 등록한다. end=%s\n' "$END_RFC3339" >&2; elif [[ ! "$START_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] || [[ ! "$END_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then printf '중단: START/END는 strict UTC Z 형식이어야 함 start=%s end=%s\n' "$START_RFC3339" "$END_RFC3339" >&2; elif START_CANONICAL_TMP="$(date -u -d "$START_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" && END_CANONICAL_TMP="$(date -u -d "$END_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" && [ "$START_CANONICAL_TMP" = "$START_RFC3339" ] && [ "$END_CANONICAL_TMP" = "$END_RFC3339" ] && START_EPOCH_TMP="$(date -u -d "$START_RFC3339" '+%s' 2>/dev/null)" && END_EPOCH_TMP="$(date -u -d "$END_RFC3339" '+%s' 2>/dev/null)"; then if [ "$END_EPOCH_TMP" -ge "$START_EPOCH_TMP" ]; then AUDIT_READY=true; AUDIT_RANGE_READY=true; export END_RFC3339 AUDIT_READY AUDIT_RANGE_READY; printf 'AUDIT_READY=true AUDIT_RANGE_READY=true strict_utc=true start=%s end=%s start_epoch=%s end_epoch=%s\n' "$START_RFC3339" "$END_RFC3339" "$START_EPOCH_TMP" "$END_EPOCH_TMP"; else printf '중단: END가 START보다 빠름 start=%s end=%s\n' "$START_RFC3339" "$END_RFC3339" >&2; fi; else printf '중단: START/END canonical round-trip 실패 start=%s end=%s\n' "$START_RFC3339" "$END_RFC3339" >&2; fi`

`AUDIT_READY=true`와 `AUDIT_RANGE_READY=true`가 아니면 audit 결과를 추정하지 않는다. 로그·audit 시간은 strict `YYYY-MM-DDTHH:MM:SSZ`만 허용하며 자연어·offset·비정규 timestamp는 거부한다. API audit 담당자에게 다음 bounded 필드를 요청한다.

```text
시간: AUDIT_START_RFC3339부터 AUDIT_END_RFC3339(UTC), requestReceivedTimestamp가 window 안인지 확인
user.username: 실제 audit user.username을 `ACTUAL_USER`로 등록하고 selected `SUBJECT`와 exact 비교
user.groups: 실제 audit user.groups를 `ACTUAL_GROUPS`로 등록하고 selected Group `SUBJECT_NAME`과 exact line 비교
subject relation: User/ServiceAccount는 `SUBJECT == ACTUAL_USER`, Group은 `SUBJECT_NAME`이 `ACTUAL_GROUPS`에 exact member인지 기록
objectRef.namespace: NS
objectRef.name: POD
objectRef.uid: 있으면 POD_UID와 exact equality, 없거나 빈 값이면 requestURI·namespace/name·current Pod API UID equality로 대체하지 않고 결합 증명
requestURI: /api/v1/namespaces/NS/pods/POD/log 또는 같은 path의 query suffix만 허용
current Pod API: 같은 context·namespace·name을 별도 GET하고 metadata.uid == 저장된 POD_UID인지 재검증
objectRef.apiGroup: 비어 있거나 생략된 core group
objectRef.apiVersion: v1
objectRef.resource: pods
objectRef.subresource: log
verb: get
responseStatus.code: 403
authorization decision: allow 또는 forbid
admission webhook/policy 거부 증거가 있으면 같은 request ID로 포함
```

성공 gate는 같은 request의 actual `user.username`·`user.groups`, selected `SUBJECT` kind/name/namespace, namespace·Pod UID·subresource·verb·HTTP status가 하나의 audit record에 맞는 것이다. User/ServiceAccount는 `SUBJECT == user.username`, Group은 selected group이 `user.groups`의 exact member인지 확인한다. `403`과 `decision=forbid`면 RBAC subject와 대조한다. decision이 allow인데 response가 403이면 RBAC를 넓히지 말고 admission/policy controller와 request audit를 확인한다. audit가 `200`인데 client가 실패하면 API response 이후 client/proxy/context를 [[27. Pod 로그를 가져올 수 없는 경우]]에서 확인한다. record가 없으면 audit 보존 실패이며 권한 허용으로 단정하지 않는다.

`responseStatus.code=200`은 actor identity fallback의 성공 조건이 아니다. 필요하면 같은 request의 사후 관찰 결과로만 설명하고, Forbidden incident의 `ACTOR_READY`를 열지 않는다.

### 4. Role과 RoleBinding 확인

진입 증거: 같은 실제 subject의 `pods/log` `can-i=no` 또는 audit 403이 RBAC authorization으로 확인됐다. 최초 필요값 `ROLEBINDING`은 RBAC owner가 오류 namespace와 subject에 연결된 binding으로 확인한 운영자 선택값이다. 전체 RBAC를 broad query하지 않는다.

**RoleBinding 선택 — 아래 한 줄 전체를 복사**

`ROLEBINDING='PASTE_ROLEBINDING_HERE'; RBAC_BINDING_READY=false; RBAC_READY=false; unset ROLE_REF_KIND ROLE_REF_NAME ROLE_REF_KIND_TMP ROLE_REF_NAME_TMP SUBJECT_MATCH_COUNT; if [ "$AUTHZ_READY" != true ] || [ "$UID_READY" != true ] || [ "$CAN_LOG" != no ] || [ "$SELECTION_READY" != true ] || [ -z "$ROLEBINDING" ]; then printf '%s\n' '중단: UID·named pods/log=no·subject 선택·승인된 RoleBinding 이름이 필요하다.' >&2; elif RB_JSON="$(kubectl --context "$CTX" -n "$NS" get rolebinding "$ROLEBINDING" -o json)" && ROLE_REF_KIND_TMP="$(jq -r '.roleRef.kind // empty' <<<"$RB_JSON")" && ROLE_REF_NAME_TMP="$(jq -r '.roleRef.name // empty' <<<"$RB_JSON")" && SUBJECT_MATCH_COUNT="$(jq --arg kind "$SUBJECT_KIND" --arg name "$SUBJECT_NAME" --arg namespace "$SUBJECT_NAMESPACE" '[.subjects[]? | select(.kind==$kind and .name==$name and ((.namespace // "")==$namespace))] | length' <<<"$RB_JSON")" && [ "$ROLE_REF_KIND_TMP" = Role -o "$ROLE_REF_KIND_TMP" = ClusterRole ] && [ -n "$ROLE_REF_NAME_TMP" ] && [ "$SUBJECT_MATCH_COUNT" = 1 ]; then ROLE_REF_KIND="$ROLE_REF_KIND_TMP"; ROLE_REF_NAME="$ROLE_REF_NAME_TMP"; RBAC_BINDING_READY=true; export ROLE_REF_KIND ROLE_REF_NAME RBAC_BINDING_READY; printf '%s\n' '=== RoleBinding subject match ==='; jq -r --arg kind "$SUBJECT_KIND" --arg name "$SUBJECT_NAME" --arg namespace "$SUBJECT_NAMESPACE" '"이름: \(.metadata.name)\nNamespace: \(.metadata.namespace)\n오류 subject 기대값: \($kind)/\($namespace // "-")/\($name)\n일치 subject 수: \([.subjects[]? | select(.kind==$kind and .name==$name and ((.namespace // "")==$namespace))] | length)\nroleRef kind: \(.roleRef.kind)\nroleRef name: \(.roleRef.name)"' <<<"$RB_JSON"; printf 'RBAC_BINDING_READY=true subject=%s/%s/%s roleRef=%s/%s\n' "$SUBJECT_KIND" "${SUBJECT_NAMESPACE:--}" "$SUBJECT_NAME" "$ROLE_REF_KIND" "$ROLE_REF_NAME"; else printf '중단: RoleBinding subject가 오류 SUBJECT kind/name/namespace와 일치하지 않거나 roleRef가 유효하지 않음 match-count=%s roleRef=%s/%s; RBAC_BINDING_READY=false\n' "${SUBJECT_MATCH_COUNT:--}" "${ROLE_REF_KIND_TMP:--}" "${ROLE_REF_NAME_TMP:--}" >&2; unset RB_JSON ROLE_REF_KIND ROLE_REF_NAME ROLE_REF_KIND_TMP ROLE_REF_NAME_TMP SUBJECT_MATCH_COUNT; fi`

성공 gate는 먼저 `RBAC_BINDING_READY=true`로 binding의 subject kind·name·namespace가 오류 `SUBJECT`의 kind/name/namespace와 정확히 일치하고 `roleRef.kind/name`이 유효하게 확인되는 것이다. 그 `roleRef` 대상 Role 또는 ClusterRole을 실제로 조회해 rules schema와 core `apiGroups: [""]`, `resources: ["pods/log"]`, `verbs: ["get"]` rule을 확인한 뒤에만 `RBAC_READY=true`로 올린다. subject가 다르거나 namespace가 다르면 이 binding으로 권한을 설명하지 말고 RBAC owner에게 이관한다. rule이 비어 있거나 다른 resource·verb만 있으면 `RBAC_READY=false`로 유지한다.

`roleRef.kind=Role`일 때만 같은 namespace의 Role을 조회한다.

**Role rule 확인 — 아래 한 줄 전체를 복사**

`RBAC_READY=false; unset ROLE_JSON; if [ "$RBAC_BINDING_READY" != true ] || [ "$ROLE_REF_KIND" != Role ]; then printf '%s\n' '중단: RBAC_BINDING_READY 또는 Role roleRef가 아니다. ClusterRole 분기로 이동한다.' >&2; elif ROLE_JSON="$(kubectl --context "$CTX" -n "$NS" get role "$ROLE_REF_NAME" -o json)" && jq -e 'if (.rules|type)!="array" then false else any(.rules[]?; ((.apiGroups|type)=="array") and ((.resources|type)=="array") and ((.verbs|type)=="array") and ((.apiGroups|index("")) != null) and ((.resources|index("pods/log")) != null) and ((.verbs|index("get")) != null)) end' <<<"$ROLE_JSON" >/dev/null; then jq -c '{kind,metadata:{name:.metadata.name,namespace:.metadata.namespace,uid:.metadata.uid},rules}' <<<"$ROLE_JSON"; RBAC_READY=true; export RBAC_READY; printf 'RBAC_READY=true roleRef=Role/%s rule=core/pods/log/get\n' "$ROLE_REF_NAME"; else printf '중단: roleRef가 가리키는 Role 조회 또는 exact core/pods/log/get rule 검증 실패; RBAC_READY=false\n' >&2; fi`

**ClusterRole rule 확인 — 아래 한 줄 전체를 복사**

`RBAC_READY=false; unset CLUSTERROLE_JSON; if [ "$RBAC_BINDING_READY" != true ] || [ "$ROLE_REF_KIND" != ClusterRole ]; then printf '%s\n' '중단: RBAC_BINDING_READY 또는 ClusterRole roleRef가 아니다. Role 분기로 이동한다.' >&2; elif CLUSTERROLE_JSON="$(kubectl --context "$CTX" get clusterrole "$ROLE_REF_NAME" -o json)" && jq -e 'if (.rules|type)!="array" then false else any(.rules[]?; ((.apiGroups|type)=="array") and ((.resources|type)=="array") and ((.verbs|type)=="array") and ((.apiGroups|index("")) != null) and ((.resources|index("pods/log")) != null) and ((.verbs|index("get")) != null)) end' <<<"$CLUSTERROLE_JSON" >/dev/null; then jq -c '{kind,metadata:{name:.metadata.name,uid:.metadata.uid},rules}' <<<"$CLUSTERROLE_JSON"; RBAC_READY=true; export RBAC_READY; printf 'RBAC_READY=true roleRef=ClusterRole/%s rule=core/pods/log/get\n' "$ROLE_REF_NAME"; else printf '중단: roleRef가 가리키는 ClusterRole 조회 또는 exact core/pods/log/get rule 검증 실패; RBAC_READY=false\n' >&2; fi`

`RBAC_READY=true`는 binding subject exact match와 대상 Role/ClusterRole의 core `apiGroups: [""]`, `resources: ["pods/log"]`, `verbs: ["get"]` rule이 함께 확인된 경우뿐이다. 실제 `kubectl logs`의 사전 Pod 조회가 필요한 환경이면 `pods` `get`은 별도 rule로 확인한다. `pods`, `pods/exec`, `pods/attach`는 `pods/log`를 대신하지 않는다. binding·rule 조회 성공은 현재 actor가 해당 rule을 실제로 사용했다는 증거가 아니며 actual user/groups audit과 다시 대조한다.

ClusterRoleBinding이 audit 또는 RBAC owner에 의해 후보로 식별된 경우에만 이름을 운영자에게 받는다. 이 경로는 namespace RoleBinding의 `RBAC_READY`를 선행 조건으로 삼지 않지만, actual user/groups와 selected `SUBJECT` exact relation은 선행 조건이다. ClusterRoleBinding 입력, 오류 subject kind/name/namespace exact match, `roleRef.kind=ClusterRole`·비어 있지 않은 exact name, 그 이름의 ClusterRole rule에서 `apiGroups: [""]`, `resources: ["pods/log"]`, `verbs: ["get"]`를 각각 확인한 뒤에만 `CLUSTER_RBAC_READY=true`를 연다.

**확인된 ClusterRoleBinding 조회 — 아래 한 줄 전체를 복사**

`CLUSTER_RBAC_READY=false; CRB_INPUT_READY=false; CRB_SUBJECT_READY=false; CRB_ROLE_REF_READY=false; CRB_RULE_READY=false; CLUSTERROLEBINDING='PASTE_CLUSTERROLEBINDING_HERE'; unset CRB_JSON CLUSTERROLE_JSON CRB_ROLE_KIND CRB_ROLE_NAME CRB_SUBJECT_MATCH_COUNT; if [ "$SELECTION_READY" != true ] || [ "$ACTOR_SUBJECT_READY" != true ] || [ -z "${SUBJECT_KIND:-}" ] || [ -z "${SUBJECT_NAME:-}" ] || [ -z "$CLUSTERROLEBINDING" ]; then printf '%s\n' '중단: SELECTION_READY, actual user/groups·SUBJECT exact relation과 승인된 ClusterRoleBinding 후보가 필요하다.' >&2; else CRB_INPUT_READY=true; if CRB_JSON="$(kubectl --context "$CTX" get clusterrolebinding "$CLUSTERROLEBINDING" -o json)"; then CRB_ROLE_KIND="$(jq -r '.roleRef.kind // empty' <<<"$CRB_JSON")"; CRB_ROLE_NAME="$(jq -r '.roleRef.name // empty' <<<"$CRB_JSON")"; CRB_SUBJECT_MATCH_COUNT="$(jq --arg kind "$SUBJECT_KIND" --arg name "$SUBJECT_NAME" --arg namespace "$SUBJECT_NAMESPACE" '[.subjects[]? | select(.kind==$kind and .name==$name and ((.namespace // "")==$namespace))] | length' <<<"$CRB_JSON")"; [ "$CRB_SUBJECT_MATCH_COUNT" = 1 ] && CRB_SUBJECT_READY=true; [ "$CRB_ROLE_KIND" = ClusterRole ] && [ -n "$CRB_ROLE_NAME" ] && CRB_ROLE_REF_READY=true; printf 'CRB_INPUT_READY=true subject-match=%s roleRef=%s/%s\n' "$CRB_SUBJECT_MATCH_COUNT" "${CRB_ROLE_KIND:--}" "${CRB_ROLE_NAME:--}"; if [ "$CRB_SUBJECT_READY" = true ] && [ "$CRB_ROLE_REF_READY" = true ] && CLUSTERROLE_JSON="$(kubectl --context "$CTX" get clusterrole "$CRB_ROLE_NAME" -o json)" && jq -e 'if (.rules|type)!="array" then false else any(.rules[]?; ((.apiGroups|type)=="array") and ((.resources|type)=="array") and ((.verbs|type)=="array") and ((.apiGroups|index("")) != null) and ((.resources|index("pods/log")) != null) and ((.verbs|index("get")) != null)) end' <<<"$CLUSTERROLE_JSON" >/dev/null; then CRB_RULE_READY=true; CLUSTER_RBAC_READY=true; export CRB_INPUT_READY CRB_SUBJECT_READY CRB_ROLE_REF_READY CRB_RULE_READY CLUSTER_RBAC_READY; jq -c '{kind,metadata:{name:.metadata.name,uid:.metadata.uid},rules}' <<<"$CLUSTERROLE_JSON"; printf 'CLUSTER_RBAC_READY=true CRB_INPUT_READY=true CRB_SUBJECT_READY=true CRB_ROLE_REF_READY=true CRB_RULE_READY=true subject=%s/%s/%s roleRef=ClusterRole/%s\n' "$SUBJECT_KIND" "${SUBJECT_NAMESPACE:--}" "$SUBJECT_NAME" "$CRB_ROLE_NAME"; else export CRB_INPUT_READY CRB_SUBJECT_READY CRB_ROLE_REF_READY CRB_RULE_READY; printf '중단: ClusterRole 조회 실패 또는 exact pods/log get rule 없음 subject-ready=%s roleRef-ready=%s rule-ready=%s roleRef=%s/%s; CLUSTER_RBAC_READY=false\n' "$CRB_SUBJECT_READY" "$CRB_ROLE_REF_READY" "$CRB_RULE_READY" "${CRB_ROLE_KIND:--}" "${CRB_ROLE_NAME:--}" >&2; fi; else export CRB_INPUT_READY; printf '%s\n' '중단: ClusterRoleBinding API 조회 실패; CRB_INPUT_READY=true 나머지 gate=false' >&2; fi; fi`

### 5. 승인된 복구 gate

진입 증거: 업무상 로그가 필요하고, 정확한 오류·현재 실제 subject와 audit identity 일치·현재 실제 subject의 named `pods/log` `can-i=no`가 직접 근거다. 이 절은 일반 복구가 아니라 승인된 변경 절차다. Role·RoleBinding 변경 또는 impersonation은 승인 전 실행하지 않는다.

변경 trigger, 대상 namespace·Pod UID·subject, 최소 권한, 승인자·incident/change ID, 만료 시각, rollback diff·방법, 중단 조건과 영향을 변경 기록에 남긴다. 대상 namespace에 한정된 Role·RoleBinding, 대상 subject, `pods/log` `get`만 우선한다. `pods get`은 실제 사전 조회에 필요한 경우에만 별도 허용한다. cluster-admin·wildcard·cluster-wide binding·TLS 우회는 제외한다.

승인된 impersonation에 필요한 group만 운영자 선택값으로 등록한다.

**승인 group 등록 — 아래 한 줄 전체를 복사**

`APPROVED_GROUP='PASTE_APPROVED_GROUP_HERE'; if [ -z "$APPROVED_GROUP" ] || [ "$AUDIT_READY" != true ] || [ "$AUDIT_RANGE_READY" != true ]; then printf '%s\n' '중단: 승인 문서와 순서가 검증된 audit 범위가 필요하다.' >&2; else printf 'APPROVED_GROUP_READY=true group=%s; 승인 문서에 명시된 경우에만 impersonation을 실행한다.\n' "$APPROVED_GROUP"; fi`

**승인된 impersonation 판정 — 아래 한 줄 전체를 복사**

`if [ -n "${APPROVED_GROUP:-}" ] && [ "$AUDIT_READY" = true ] && [ "$AUDIT_RANGE_READY" = true ]; then kubectl --context "$CTX" auth can-i get "pods/$POD" --subresource=log -n "$NS" --as="$SUBJECT" --as-group="$APPROVED_GROUP"; else printf '%s\n' '중단: 승인된 impersonation, group 또는 순서가 검증된 audit 범위가 없다.' >&2; fi`

`cannot impersonate` 또는 예상 밖 group이면 즉시 중단하고 인증·RBAC 담당자로 이관한다. 이 결과는 현재 실제 actor의 판정과 분리한다. 위험 변경은 진단과 섞지 않으며, 변경 뒤 같은 실제 subject의 `can-i`, 제한된 log 요청, audit record를 재검증한다. subject·namespace·roleRef가 다르거나 권한 범위가 넓어지면 rollback을 요청한다.

## Prometheus 빠른 관측

API server metric이 실제로 수집될 때만 사용한다. 먼저 metric query transport/API success를 확인하고, 성공 후 빈 series는 metric 미수집·label 불일치·시간 범위 문제로 분리한다.

**API metric용 변수·PromQL 생성 — 아래 한 줄 전체를 복사**

`QUERY_READY=false; API_RESOURCE='pods'; API_SUBRESOURCE='log'; API_CODE='403'; if [ "$AUTO_READY" != true ] || [ "$UID_READY" != true ] || [ -z "$POD_UID" ]; then printf '%s\n' '중단: AUTO_READY, UID_READY와 Pod UID가 필요하다.' >&2; else NS_RE="$(printf '%s' "$NS" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; POD_RE="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; POD_UID_RE="$(printf '%s' "$POD_UID" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; printf 'sum by(code,resource,subresource)(increase(apiserver_request_total{resource="%s",subresource="%s",code="%s"}[15m]))>0\n' "$API_RESOURCE" "$API_SUBRESOURCE" "$API_CODE"; printf 'kube_pod_info{namespace=~"%s",pod=~"%s",uid=~"%s"}\n' "$NS_RE" "$POD_RE" "$POD_UID_RE"; QUERY_READY=true; export NS_RE POD_RE POD_UID_RE QUERY_READY; printf 'QUERY_READY=true matcher는 namespace·pod·uid bounded 출력만 사용한다.\n'; fi`

`QUERY_READY=true`는 완성 query 생성 성공일 뿐 API metric 존재나 특정 subject·Pod의 403을 증명하지 않는다. metric query 자체의 transport/API 실패와 빈 result를 구분하고, 실제 authorization 원인은 `can-i`·오류·audit으로 닫는다.

## 정상화와 증거 보존

정상화는 역순으로 `실제 log 요청과 필요한 application 기능 → API HTTP status·log data → authorization/admission audit → RoleBinding·rule → context·Pod UID·actor`를 확인한다. `can-i=yes`, HTTP 200, log stream 성공은 서로 다른 hop이며 application 정상이나 민감정보 안전을 보장하지 않는다. 같은 실제 subject로 named `pods/log`가 의도한 범위에서 허용되고, 제한된 로그 요청이 성공하며, 새 403과 실제 서비스 오류가 재발하지 않는 관찰 창을 둔다.

보존 항목은 UTC 관측 시간, context, namespace, Pod UID·node, 오류 subject와 actual user/groups, resource/verb/subresource, 두 can-i 결과, transport·HTTP status·data 유무, audit filter/result, 승인 ID·rollback ID다. token·Secret data·개인키·민감한 로그 원문은 저장하지 않는다.

이 문서의 상태 변경은 승인된 RBAC 변경 검토뿐이며, 실행 명령은 제공하지 않는다. 변경의 trigger·authority·대상/영향·중단·rollback·검증을 기록하지 못하면 실행하지 않는다.
