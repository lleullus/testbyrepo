# Pod exec 명령을 찾을 수 없는 경우

## 입력값과 빠른 수집

이 문서는 대상 Pod와 Running regular container가 고정됐지만 `executable file not found in $PATH`, `command not found`, shell·interpreter 부재, 권한·architecture·runtime exec 오류가 보이는 경우를 다룬다. local shell에서 난 `kubectl: command not found`, kubeconfig 오류와 원격 container executable 오류를 섞지 않는다.

| 값 종류 | 이 문서에서 쓰는 값 | 출처와 처리 |
|---|---|---|
| 최초 입력 | `CONTEXT`, `NS`, `POD` | 운영자가 승인된 context, namespace, 정확한 Pod 이름을 처음 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `NODE`, `PHASE`, `POD_START`, `CONTAINER_ID`, image·command·args·securityContext·port 후보와 status | Kubernetes API에서 현재 Pod를 읽어 대상 identity와 실행 환경을 세로 블록으로 등록한다. |
| 계산 후보값 | `OBSERVED_AT`, `POD_RE`, `CONTAINER_RE`, runtime 로그 필터, 생성된 PromQL | 수집 시각·escaped selector·bounded filter를 만들지만 실제 image 계약·node 로그·metric 존재를 확인하기 전에는 확정하지 않는다. |
| 운영자 선택값 | `CONTAINER`, `COMMAND_NAME`, `KNOWN_ABSOLUTE_COMMAND`, `NODE_HOST`, `KUBELET_UNIT`, `RUNTIME_UNIT`, `START_JOURNAL`, `END_JOURNAL`, `APPROVED_DEBUG_IMAGE` | container 후보, image 계약, 승인된 remote node·실제 systemd unit·journal 범위와 변경 승인을 확인한 뒤 해당 분기에서 선택한다. |

모든 kubectl 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. 변수·배열을 재사용하므로 `sh`, PowerShell, CMD 또는 새 Bash로 복사하지 않는다. 32번에서는 local `journalctl`을 실행하지 않으며 승인된 `NODE_HOST`로만 safe-quoted SSH remote journal을 실행한다. API·도구·권한·remote identity 확인이 실패하면 다음 단계로 진행하지 않는다.

**실행 host와 필수 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: Bash에서 실행한다.' >&2; else MISSING_TOOLS=''; for TOOL in kubectl jq sed grep date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true shell=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

**공통 auth·UID gate 등록 — 이후 모든 재조회에서 같은 Bash로 재사용**

`unset AUTH_OUTPUT AUTH_RAW_OUTPUT AUTH_RC AUTH_DECISION POD_SNAPSHOT POD_UID_GATE NODE_IDENTITY_GATE; auth_can_i(){ local raw output rc; raw="$(kubectl "$@" 2>&1; rc=$?; printf '\036%s' "$rc"; exit "$rc")"; `auth_can_i`는 `AUTH_OUTPUT`, `AUTH_RC`, `AUTH_DECISION`을 별도로 등록한다. `AUTH_DECISION=yes`는 rc=0이고 출력이 정확히 한 줄 `yes`인 경우뿐이다. rc=1이고 출력이 정확히 한 줄 `no` 또는 한 줄 `no - ...`이면 정상적인 RBAC 거부로 `34번`으로 이관하며, multiline·blank extra line을 포함한 그 밖의 rc/output 조합은 API·인증 진단으로 이동한다. `pod_uid_gate`가 실패하면 최초 `$POD_UID`는 보존하고 `AUTO_READY`, `SELECTION_READY`, `CONTAINER_ID_READY` 등 파생 gate만 폐기한다.

**exec identity gate helper — 모든 exec 직전에 아래 helper를 통과**

`exec_identity_gate(){ local kind="$1" c="$2" expected="$3" expected_uid="${POD_UID:-}"; EXEC_IDENTITY_READY=false; if [ "$kind" != regular ] || [ -z "$c" ] || [ -z "$expected" ] || [ -z "$expected_uid" ] || ! pod_uid_gate; then printf '%s\n' '중단: exec 직전 Pod UID·regular container·containerID 재검증 실패.' >&2; return 1; elif ! jq -e --arg c "$c" --arg expected "$expected" --arg uid "$expected_uid" '(.metadata.uid == $uid) and (.metadata.deletionTimestamp == null) and any(.spec.containers[]?; .name == $c) and any(.status.containerStatuses[]?; .name == $c and .state.running != null and .containerID == $expected)' <<<"$POD_SNAPSHOT" >/dev/null; then printf '중단: exec 직전 UID·deletionTimestamp·regular Running/current containerID gate 실패 pod_uid=%s container=%s container_id=%s\n' "$expected_uid" "$c" "$expected" >&2; return 1; else EXEC_IDENTITY_READY=true; export EXEC_IDENTITY_READY; printf 'EXEC_IDENTITY_READY=true pod_uid=%s kind=regular container=%s container_id=%s\n' "$expected_uid" "$c" "$expected"; return 0; fi; }`

성공 출력은 UID·node·phase·Pod 시작 시각·관측 시각과 regular container별 image, port 후보, status, containerID, restartCount를 대상별 세로 블록으로 보여 줘야 한다. 명령·args 원문은 출력하지 않으며 image contract가 확인된 선택값으로만 사용한다. `containerPort`는 후보 선언값이며 process listener·protocol·application 정상은 보장하지 않는다. 빈 출력은 대상 없음, API 권한, schema·조회 오류 중 하나일 수 있으므로 정상으로 기록하지 않는다.

재수집·재등록은 같은 이름의 새 Pod를 포함하므로 기존 container 선택, auth 결과, command/known argv, containerID, node/journal 입력, debug/evidence gate, regex selector를 모두 폐기한다. 새 `AUTO_READY=true`만으로 PATH 분기나 로그 수집을 진행하지 말고 선택·auth·command·known argv를 다시 등록하고 각 gate를 다시 통과한다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | Pod UID와 Running regular container가 고정됐는데 `kubectl exec`가 실행 파일·shell·interpreter를 찾지 못하는 경우 |
| 적용 | Pod UID, container ID, image·command/args, securityContext와 node를 대조할 수 있는 경우 |
| 제외 | 대상 container 선택·UID race는 [[31. Pod exec 대상 컨테이너를 찾을 수 없는 경우|31번 대상 컨테이너 런북]], `Forbidden`은 [[34. Pod exec 권한이 거부되는 경우|34번 RBAC 런북]], API·stream 오류는 [[33. Pod exec 연결이 실패하는 경우#3. API server에서 kubelet으로의 streaming upgrade|33번 API streaming 절]]로 이동 |

검색 문자열: `executable file not found in $PATH`, `command not found`, `sh: not found`, `stat /bin/sh: no such file or directory`, `permission denied`, `operation not permitted`, `no such file or directory`, `exec format error`, `OCI runtime`, `runc`, `containerd`, `failed to exec`.

대상 Pod UID와 container가 맞고 해당 container가 Running인 상태에서 명령·image·실행 환경을 구분한다. 운영 image에 shell·PATH·package를 임의로 추가하지 않는다. `-c`와 kubectl 옵션은 `--` 앞에 두며 `--` 뒤 token은 원격 argv다. API 도달 전 local shell 오류와 API 이후의 원격 실행 오류를 분리한다.

## 최초 확인

`AUTO_READY=true`인 같은 Bash에서 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r '"UID=" + (.metadata.uid // "-") + "\tPHASE=" + (.status.phase // "-") + "\tREADY=" + ([.status.containerStatuses[]?.ready] | map(tostring) | join(",")) + "\tRESTARTS=" + ([.status.containerStatuses[]?.restartCount] | map(tostring) | join(",")) + "\tNODE=" + (.spec.nodeName // "-") + "\tAGE=" + (.metadata.creationTimestamp // "-")' <<<"$POD_SNAPSHOT"; fi`를 실행한다. `STATUS`, `READY`, `RESTARTS`, `NODE`, `AGE`, 현재 UID를 본다. 명령 실패·`NotFound`면 target identity를 다시 입력하는 것이 아니라 `INPUT_READY`부터 재확인한다.

같은 조건에서 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else kubectl --context "$CONTEXT" describe pod "$POD" -n "$NS"; fi`를 실행한다. 대상 container의 `State`, `Last State`, `Reason`, `Exit Code`, `Restart Count`, Conditions와 exec 시각에 가까운 첫 실패 message만 기록한다. 자동 수집의 spec 이름·status 이름·Running 시각·현재 UID가 맞지 않으면 명령 부재로 판정하지 않고 [[31. Pod exec 대상 컨테이너를 찾을 수 없는 경우#1. Pod UID와 phase를 먼저 고정|31번 UID·phase 절]]로 이동한다.

표는 원인과 변경을 승인하지 않는다. `Running`은 process가 현재 존재할 가능성만 보여 주며 PATH·binary·listener·application 정상은 보장하지 않는다.

## 1. PATH 문제와 image의 명령 부재

진입 증거는 원격 실행에서 `executable file not found in $PATH` 또는 `command not found`가 보이는 경우다. 필요한 운영자 선택값은 image 문서·manifest·애플리케이션 계약으로 확인한 `COMMAND_NAME`과 비파괴 `KNOWN_ABSOLUTE_COMMAND`이며 이 절에서 한 번만 입력한다. 원래 실패한 명령이 상태 변경·서버 기동·무기한 대기라면 재실행하지 않는다.

**image 계약값 입력 — 확인한 argv를 같은 Bash에 한 번 등록**

`COMMAND_NAME='PASTE_COMMAND_NAME_HERE'; KNOWN_ABSOLUTE_COMMAND='PASTE_KNOWN_ABSOLUTE_COMMAND_HERE'`

`COMMAND_NAME`은 하나의 실행 파일 이름이어야 하고 `KNOWN_ABSOLUTE_COMMAND`는 image 계약에서 확인된 비파괴 argv여야 한다. 둘 중 하나가 비어 있거나 계약 출처가 없으면 exec하지 않고 image 담당자에게 reference·digest·entrypoint·command/args를 요청한다.

**대상 identity·argv 준비 gate — 아래 한 줄 전체를 복사**

`unset SELECTION_READY AUTH_READY AUTH_RESULT AUTH_OUTPUT AUTH_RC AUTH_DECISION COMMAND_READY COMMAND_ARGV KNOWN_ARGV KNOWN_EXEC_READY KNOWN_EXEC_RC; SELECTION_READY=false; AUTH_READY=false; COMMAND_READY=false; COMMAND_ARGV=(); KNOWN_ARGV=(); KNOWN_EXEC_READY=false; KNOWN_EXEC_RC=0; if [ "$AUTO_READY" != true ] || [ -z "$CONTAINER" ]; then printf '%s\n' '중단: AUTO_READY와 container 선택이 필요하다.' >&2; elif pod_uid_gate && jq -e --arg c "$CONTAINER" 'any(.spec.containers[]?; .name == $c) and any(.status.containerStatuses[]?; .name == $c and .state.running != null and (.containerID // "") != "")' <<<"$POD_SNAPSHOT" >/dev/null && auth_can_i --context "$CONTEXT" auth can-i create pods/"$POD" --subresource=exec -n "$NS"; then AUTH_RESULT="$AUTH_OUTPUT"; if [ "$AUTH_DECISION" = yes ]; then read -r -a COMMAND_ARGV <<<"$COMMAND_NAME"; read -r -a KNOWN_ARGV <<<"$KNOWN_ABSOLUTE_COMMAND"; if [ "${#COMMAND_ARGV[@]}" -eq 1 ] && [ "${#KNOWN_ARGV[@]}" -gt 0 ]; then SELECTION_READY=true; AUTH_READY=true; COMMAND_READY=true; export CONTAINER COMMAND_NAME KNOWN_ABSOLUTE_COMMAND AUTH_RESULT; printf 'SELECTION_READY=true AUTH_READY=true container=%s command_ready=true\n' "$CONTAINER"; else printf '%s\n' '중단: command argv 검증 실패' >&2; fi; elif [ "$AUTH_DECISION" = no ]; then printf '중단: pods/exec 권한 거부 RBAC로 이관 rc=%s output=%s\n' "$AUTH_RC" "$AUTH_OUTPUT" >&2; else printf '중단: auth API 호출 실패 rc=%s output=%s\n' "$AUTH_RC" "${AUTH_OUTPUT:--}" >&2; fi; else printf '%s\n' '중단: 현재 UID·container state·auth 조회 실패. 부분 등록하지 않는다.' >&2; fi`

성공 gate는 현재 Pod UID와 선택 container가 spec/status에서 일치하고 Running·containerID이며, same-subject `auth can-i`가 `yes`이고 argv가 준비된 것이다. `yes`는 실제 exec stream이나 image 실행 가능성을 보장하지 않는다. 빈 JSON 출력은 상태 정상이나 명령 부재로 해석하지 않는다.

**선택 container ID 등록 — runtime 분기에서 재입력하지 않도록 한 번 확정**

`unset CONTAINER_ID; CONTAINER_ID_READY=false; if [ "$SELECTION_READY" != true ] || ! pod_uid_gate; then printf '%s\n' '중단: SELECTION_READY 또는 UID gate가 아니다.' >&2; elif CONTAINER_ID="$(jq -r --arg c "$CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID][0] // empty' <<<"$POD_SNAPSHOT")" && [ -n "$CONTAINER_ID" ]; then CONTAINER_ID_READY=true; export CONTAINER_ID; printf 'CONTAINER_ID_READY=true pod_uid=%s container=%s container_id=%s\n' "$POD_UID" "$CONTAINER" "$CONTAINER_ID"; else printf '%s\n' '중단: 선택 container의 현재 containerID 조회 실패. runtime 로그를 실행하지 않는다.' >&2; fi`

`CONTAINER_ID_READY=true`가 아니면 runtime log 명령으로 내려가지 않는다. containerID는 Pod UID와 다른 runtime 식별자이며, 재생성되면 이전 runtime log와 섞지 않는다.

연결 경로는 **같은 실행 host의 Bash → kubectl client → API server HTTPS endpoint와 exec 요청 → 대상 node kubelet streaming endpoint → CRI runtime → container process와 PATH resolver**다. API address·port, kubelet address·port, runtime socket, 원격 argv는 서로 다른 역할이다. 한 hop의 성공은 다음 hop이나 application 정상의 증거가 아니다.

API server·kubelet TLS 검증은 유지한다. `--insecure-skip-tls-verify`, 인증서 검증 비활성화, 확인되지 않은 trust 변경으로 image·runtime 오류를 시험하지 않는다.

exec 직전 identity를 한 번 재확인한 뒤, 실행 명령은 `if [ "$SELECTION_READY" != true ] || [ "$AUTH_READY" != true ] || [ "$COMMAND_READY" != true ] || ! exec_identity_gate regular "$CONTAINER" "$CONTAINER_ID"; then printf '%s\n' '중단: selection/auth/command/UID/container state/containerID gate가 준비되지 않았다.' >&2; else kubectl --context "$CONTEXT" exec "$POD" -n "$NS" -c "$CONTAINER" -- "${COMMAND_ARGV[@]}"; fi`이다. 명령 이름만 실패하고 image 계약의 절대 argv가 성공하면 remote PATH 문제다. 이름과 절대 argv가 모두 `not found`면 실제 배포 image의 경로·digest와 entrypoint를 확인한다. `no such file or directory`는 4절, `permission denied`는 3절로 간다.

**KNOWN_ARGV 실제 실행 gate — fresh identity 성공 뒤에만 PATH 분기 허용**

`KNOWN_EXEC_READY=false; KNOWN_EXEC_RC=0; if [ "$SELECTION_READY" != true ] || [ "$AUTH_READY" != true ] || [ "$COMMAND_READY" != true ] || [ "$CONTAINER_ID_READY" != true ] || ! exec_identity_gate regular "$CONTAINER" "$CONTAINER_ID"; then printf '%s\n' '중단: KNOWN_ARGV 실행 전 selection/auth/command/current identity gate가 준비되지 않았다.' >&2; else kubectl --context "$CONTEXT" exec "$POD" -n "$NS" -c "$CONTAINER" -- "${KNOWN_ARGV[@]}"; KNOWN_EXEC_RC=$?; if [ "$KNOWN_EXEC_RC" -eq 0 ]; then KNOWN_EXEC_READY=true; printf 'KNOWN_EXEC_READY=true pod_uid=%s container=%s container_id=%s argv_count=%s\n' "$POD_UID" "$CONTAINER" "$CONTAINER_ID" "${#KNOWN_ARGV[@]}"; else printf 'KNOWN_ARGV 실행 실패 rc=%s; PATH 분기를 허용하지 않는다.\n' "$KNOWN_EXEC_RC" >&2; fi; fi`

절대 argv가 fresh identity gate 뒤 실제로 exit 0을 반환하고 image 계약이 `/bin/sh`를 실제 보장하며 `sh`가 비파괴 PATH 출력에 적합할 때만 `if [ "$KNOWN_EXEC_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$AUTH_READY" != true ] || ! exec_identity_gate regular "$CONTAINER" "$CONTAINER_ID"; then printf '%s\n' '중단: KNOWN_ARGV 성공·selection/auth/current identity gate가 아니다.' >&2; else kubectl --context "$CONTEXT" exec "$POD" -n "$NS" -c "$CONTAINER" -- /bin/sh -c 'printf "%s\\n" "$PATH"'; fi`를 실행한다. `/bin/sh`를 가정할 수 없으면 이 명령을 건너뛰고 image contract를 확인한다. PATH 출력은 원하는 directory가 없는지만 판단하고, 운영 container 안에서 PATH export·package 설치·image 변경은 복구로 제시하지 않는다.

## 2. shell 부재와 최소 image

진입 증거는 `/bin/sh: not found` 또는 `stat /bin/sh: no such file or directory`다. shell 경로를 `/bin/bash`, `/bin/sh` 순서로 추측하지 않는다. 필요한 값은 API 자동 수집의 image·command/args와 image manifest의 application executable이며, manifest에서 확인되지 않으면 이 절을 중단한다.

범위를 제한한 image identity 명령은 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r --arg c "$CONTAINER" '.metadata.uid + "\t" + (([.spec.containers[]? | select(.name==$c) | "image=" + (.image // "-")] + [.status.containerStatuses[]? | select(.name==$c) | "imageID=" + (.imageID // "-")]) | join("\n"))' <<<"$POD_SNAPSHOT"; fi`이다. 성공 gate는 선택 container의 현재 image reference·status imageID가 image manifest의 대상과 일치하는 것이다. 빈 출력은 container 선택·API 실패이며 shell 부재가 확인됐다는 뜻이 아니다.

distroless·scratch처럼 shell이 없는 image에서는 shell 문법을 바꾸거나 shell·package를 설치하지 않는다. 승인된 image contract의 application executable을 직접 실행할 수 있는지만 1절의 gate로 확인한다. application 경로가 현재 image와 맞지 않으면 image reference·digest·entrypoint·command/args를 image 담당자에게 이관한다.

성공 gate는 shell 부재가 image 설계와 일치하고, 별도의 승인된 absolute application argv가 존재하며, 그 argv의 실행 결과를 원격 stream과 혼동하지 않는 것이다. shell이 없다는 결과는 application binary 부재나 API stream 실패를 보장하지 않는다. image contract가 없거나 절대 argv도 실패하면 4절 또는 image 담당자로 이동한다.

일반 exec로 필요한 증거를 얻을 수 없고 승인된 도구가 꼭 필요한 경우에만 제한적 debug gate를 검토한다. 원래 image에 shell·package·binary를 추가하지 않는다.

## 3. permission과 operation not permitted

진입 증거는 원격 실행에서 `permission denied` 또는 `operation not permitted`가 보이며 파일 위치·image contract만으로 설명되지 않는 경우다. 최초 필요값은 API 자동 수집의 image·command/args·securityContext·volumeMount와 선택 container이며 raw Secret·환경 변수는 수집하지 않는다.

범위를 제한한 읽기 명령은 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r --arg c "$CONTAINER" '.spec.containers[]? | select(.name==$c) | "image=" + (.image // "-") + " command_count=" + ((.command // []) | length | tostring) + " args_count=" + ((.args // []) | length | tostring) + " securityContext=" + ((.securityContext // {}) | tostring) + " mounts=" + ([.volumeMounts[]?.mountPath] | join(",") // "-")' <<<"$POD_SNAPSHOT"; fi`이다. 성공 gate는 선택 container의 image·command/args 개수·securityContext·mount path가 비민감 범위로 출력되는 것이다. 빈 출력은 container 이름 불일치 또는 API 조회 실패이지 권한 문제가 해결됐다는 뜻이 아니다.

특정 mount 경로에서만 실패하면 node 담당자가 `noexec`, read-only와 보안 정책을 확인한다. 전역 실행 실패나 `operation not permitted`면 `runAsUser`, `runAsNonRoot`, capabilities, seccomp, AppArmor/SELinux와 runtime 오류를 함께 본다. `chmod`, remount, privileged 변경, securityContext 완화는 원인 확인과 별도 승인 없이 실행하지 않는다.

## 4. file, shebang, ELF interpreter

진입 증거는 image contract에 파일이 있다고 확인했는데 `no such file or directory`가 나오는 경우다. 먼저 실행 파일 자체가 아니라 `#!/bin/bash`·`/usr/bin/env` 부재, 동적 ELF loader 부재, image 경로·실제 배포 digest 불일치를 구분한다.

필요한 증거는 image build 결과, base image의 interpreter 경로, 실제 Pod의 image reference·status imageID다. `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r --arg c "$CONTAINER" '.metadata.uid + "\t" + (([.spec.containers[]? | select(.name==$c) | "image=" + (.image // "-")] + [.status.containerStatuses[]? | select(.name==$c) | "imageID=" + (.imageID // "-")]) | join("\n"))' <<<"$POD_SNAPSHOT"; fi`로 현재 digest를 다시 확인한다. 성공 gate는 same image digest의 build manifest와 오류의 interpreter 경로가 일치하는 것이다. 빈 출력은 image 원인이 아니라 API·container identity 실패다. Kubernetes API의 `Running`은 interpreter 존재를 보장하지 않는다. 운영 container에 interpreter를 복사하지 않고 image build·base image 담당자에게 이관한다. `exec format error`는 5절로, API `unable to upgrade connection`은 [[33. Pod exec 연결이 실패하는 경우#3. API server에서 kubelet으로의 streaming upgrade|33번 API streaming 절]]로 이동한다.

성공 gate는 `POD_UID_GATE=true` 상태에서 선택 container의 spec image와 status `imageID`가 같은 digest 관측으로 연결되고, same image digest의 build manifest와 오류의 interpreter 경로가 일치하는 것이다. API·runtime에서 나온 `not found`와 image 내부 path 부재를 로그 시각·Pod UID·containerID로 연결하지 못하면 원인을 확정하지 않는다.

## 5. architecture와 image manifest

진입 증거는 `exec format error`이며 실행 파일·image manifest와 배치 node architecture를 비교해야 하는 경우다. API 자동값 `NODE`와 image reference·imageID를 다시 입력하지 않는다.

대상 image/node 확인 명령은 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r --arg c "$CONTAINER" '.metadata.uid + "\t" + (.spec.nodeName // "-") + "\t" + (([.spec.containers[]? | select(.name==$c) | "image=" + (.image // "-")] + [.status.containerStatuses[]? | select(.name==$c) | "imageID=" + (.imageID // "-")]) | join("\n"))' <<<"$POD_SNAPSHOT"; fi`와 `if ! node_identity_gate; then printf '%s\n' '중단: current Pod UID와 spec.nodeName이 NODE와 일치하지 않는다.' >&2; else kubectl --context "$CONTEXT" get node "$NODE" -o jsonpath='{.metadata.name}{"\t"}{.status.nodeInfo.architecture}{"\t"}{.status.nodeInfo.operatingSystem}{"\n"}'; fi`이다. 성공 gate는 current Pod UID·`spec.nodeName==$NODE`와 node architecture, image manifest의 `amd64`·`arm64` 또는 실제 platform이 같은 관측 시각으로 기록되는 것이다.

불일치가 확인되면 image build·registry·scheduling 담당자에게 이관한다. node architecture만으로 binary 오류를 확정하지 않으며, image manifest가 맞아도 잘못 빌드된 binary·shebang·interpreter는 남을 수 있다. 명령 성공은 application 기능 정상이나 재배포 안전성을 보장하지 않는다.

## 6. kubelet과 runtime으로 내려가는 조건

진입 증거는 여러 Pod·image가 같은 node와 시각에 실패하거나, 오류에 `OCI runtime`, `runc`, `containerd`, `failed to exec`, `failed to start`가 포함되거나, Pod spec와 image contract로 설명되지 않는 경우다. 필요한 값은 자동값 `POD_UID`, `NODE`, `CONTAINER_ID`, `CONTAINER`이며 remote node host·실제 kubelet/runtime systemd unit은 운영자가 승인된 host에서 확인한다.

**승인된 remote node·systemd unit 입력 — API/SSH preflight 전에 한 번 등록**

`NODE_HOST='PASTE_NODE_HOST_HERE'; KUBELET_UNIT='PASTE_KUBELET_UNIT_HERE'; RUNTIME_UNIT='PASTE_RUNTIME_UNIT_HERE'`

`NODE_HOST`는 SSH 목적지일 뿐 journal 명령에 문자열로 삽입하지 않는다. `KUBELET_UNIT`과 `RUNTIME_UNIT`은 remote host에서 실제로 확인한 unit 이름이어야 하며, 아래 preflight가 API node name·machineID, remote hostname·machine-id, 두 unit의 loaded/active 상태를 모두 대조한다.

먼저 `if ! systemd_unit_allowlist_gate "$KUBELET_UNIT" || ! systemd_unit_allowlist_gate "$RUNTIME_UNIT" || ! node_remote_preflight; then printf '%s\n' '중단: current Pod UID·spec.nodeName·API/SSH node identity·unit allowlist·실제 unit gate가 준비되지 않았다.' >&2; else kubectl --context "$CONTEXT" get node "$NODE" -o jsonpath='{.metadata.name}{"\t"}{.status.nodeInfo.containerRuntimeVersion}{"\t"}{.status.nodeInfo.kubeletVersion}{"\n"}'; fi`를 실행한다. 성공 gate는 node 이름과 runtime version이 비어 있지 않고 API node와 remote hostname·machineID, allowlist를 통과한 kubelet/runtime unit이 일치하는 것이다. 빈 출력·API·SSH·systemd 실패는 runtime down의 증거가 아니라 preflight 실패다.

remote `NODE_HOST`에서 `journalctl` 명령과 대상 node journal 접근 권한이 확인된 경우에만 아래 값을 해당 오류 시각에 맞춰 한 번 입력한다. local `journalctl`은 실행하지 않으며 remote 명령은 `sudo -n`으로 password prompt를 금지한다.

**node journal 시간 선택값 입력 — 승인된 범위를 확인한 뒤 한 번 등록**

`START_JOURNAL='PASTE_START_JOURNAL_HERE'; END_JOURNAL='PASTE_END_JOURNAL_HERE'`

시간은 공백을 포함한 정확한 `YYYY-MM-DD HH:MM:SS UTC` 형식으로 입력한다. 예: `2026-07-29 12:00:00 UTC`.

**node journal 도구 gate — 아래 한 줄 전체를 복사**

`NODE_TOOLS_READY=false; if [ "$AUTO_READY" != true ] || [ -z "$NODE" ] || [ -z "$START_JOURNAL" ] || [ -z "$END_JOURNAL" ]; then printf '%s\n' '중단: identity와 journal 시간값이 준비되지 않았다.' >&2; elif command -v ssh >/dev/null 2>&1; then NODE_TOOLS_READY=true; printf 'NODE_TOOLS_READY=true remote_node=%s start=%s end=%s\n' "$NODE_HOST" "$START_JOURNAL" "$END_JOURNAL"; else printf '%s\n' '중단: ssh가 없어 remote node log를 수집하지 않는다.' >&2; fi`

성공 gate는 kubelet 로그의 시간 범위·Pod UID·container 이름과 오류 layer가 맞는 것이다. 로그가 비거나 필터 결과가 없으면 오류 없음으로 닫지 않고 같은 범위의 승인된 runtime 증거를 요청한다. kubelet unit·systemd가 확인되지 않으면 명령을 발명하지 않는다.

runtime version에 `containerd`가 포함되고 실제 unit·접근 권한이 확인된 경우에만 `if [ "$NODE_TOOLS_READY" != true ] || [ "$CONTAINER_ID_READY" != true ] || ! journal_window_gate || ! systemd_unit_allowlist_gate "$KUBELET_UNIT" || ! systemd_unit_allowlist_gate "$RUNTIME_UNIT" || ! exec_identity_gate regular "$CONTAINER" "$CONTAINER_ID" || ! node_remote_preflight; then printf '%s\n' '중단: node tools·remote identity·UID/container state/containerID·journal window·unit gate가 준비되지 않았다.' >&2; else printf -v REMOTE_JOURNAL_CMD 'bash -s -- %q %q %q %q %q %q' "$START_JOURNAL" "$END_JOURNAL" "$CONTAINER_ID" "$POD_UID" "$CONTAINER" "$RUNTIME_UNIT"; ssh -- "$NODE_HOST" "$REMOTE_JOURNAL_CMD" <<< 'start="$1"; end="$2"; container_id="$3"; pod_uid="$4"; container="$5"; unit="$6"; sudo -n journalctl -u "$unit" --since "$start" --until "$end" --no-pager | grep -E -i -C 3 "$container_id|$pod_uid|$container|shim|exec|not found|permission|format|failed"; runtime_producer_rc="${PIPESTATUS[0]}"; runtime_filter_rc="${PIPESTATUS[1]}"; printf "runtime_journal_producer_rc=%s filter_rc=%s\\n" "$runtime_producer_rc" "$runtime_filter_rc"; if [ "$runtime_producer_rc" -ne 0 ] || [ "$runtime_filter_rc" -gt 1 ]; then exit 1; fi'; REMOTE_JOURNAL_RC=$?; if [ "$REMOTE_JOURNAL_RC" -ne 0 ]; then printf '중단: remote containerd journal 실행 실패 rc=%s\n' "$REMOTE_JOURNAL_RC" >&2; fi; fi`를 실행한다. `%q`로 만든 하나의 remote command가 공백 포함 시간을 단일 원격 Bash 인수로 보존하고, runtime 인수 순서는 `container_id`, `pod_uid`, `container`, `unit`이다. `runc exec failed`, `failed to create task`, `no such file or directory`, `permission denied`가 같은 ID·시각이면 runtime/OCI·rootfs·mount·security policy 담당자로 이관한다. CRI-O 등 다른 runtime이면 실제 service unit과 로그 위치를 확인한 뒤 동일한 시간·필터 범위를 사용한다. CRI endpoint를 확인하지 않은 상태에서 `crictl`을 실행하지 않는다.

## 제한적 debug gate

진입 증거는 일반 exec와 읽기 전용 node/runtime 증거로 원인을 좁힐 수 없고 승인된 도구가 꼭 필요한 경우다. ephemeral container 추가는 Pod 상태 변경이며 원래 image의 shell·PATH·binary·package를 고치지 않는다. 실행 trigger와 직접 근거, current Pod UID·Running state, 승인된 immutable image digest, RBAC·quota·NetworkPolicy·node 자원, 민감정보 비노출 계획, 담당자·승인자·incident/change ID, 종료·정리·중단 조건을 action contract에 기록한다.

**승인된 debug image 입력 — digest와 승인을 확인한 뒤 한 번 등록**

`APPROVED_DEBUG_IMAGE='PASTE_APPROVED_DEBUG_IMAGE_HERE'`

**debug 권한 gate — 아래 한 줄 전체를 복사**

**debug action gate 등록 — 상태 변경 직전에 재사용**

## 정상화와 증거

정상화는 명령 하나의 성공이나 shell 연결로 닫지 않는다. 원인 경로를 역순으로 확인해 image contract·runtime/OCI·kubelet 증거가 해소됐고, 원래 Pod UID·Ready·restart 증가 중단·새 Warning 부재·실제 서비스 기능이 정상인지 확인한다. ephemeral container의 Running은 원래 application 정상의 증거가 아니다.

대상 상태는 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r '"POD=" + (.metadata.name // "-") + "\tUID=" + (.metadata.uid // "-") + "\tPHASE=" + (.status.phase // "-") + "\tREADY=" + ([.status.containerStatuses[]?.ready] | map(tostring) | join(",")) + "\tRESTARTS=" + ([.status.containerStatuses[]?.restartCount] | map(tostring) | join(",")) + "\tNODE=" + (.spec.nodeName // "-") + "\tIMAGE-ID=" + ([.status.containerStatuses[]?.imageID // "-"] | join(","))' <<<"$POD_SNAPSHOT"; fi`로 확인한다. 실패는 API·권한·도구 수집 실패로 분기하고 빈 출력은 정상으로 기록하지 않는다. 실제 기능·image digest·containerID·node 로그 시간 범위를 함께 기록한다.

증거에는 UTC 시각, 원본 오류와 정확한 remote argv, image reference·digest, Pod UID, container state·ID, node architecture·runtime, securityContext·mount path, kubelet/runtime 로그의 시간·필터·식별자, debug 승인·정리와 이관 시각을 남긴다. Secret·token·환경 변수 전체·인증서 개인키는 저장하지 않는다.

## Prometheus 빠른 관측

PromQL은 문서에서 직접 수정하지 않는다. 같은 Bash에서 자동 등록된 `NS`, `POD_RE`와 선택된 `CONTAINER_RE`로 완성 문자열을 생성하고 출력된 한 줄만 Prometheus 또는 Grafana에 붙여 넣는다. metric query 자체의 transport·HTTP/API 오류와 성공 후 빈 series를 분리한다.

**Pod·container regex 등록 — 아래 한 줄 전체를 복사**

`unset QUERY_READY POD_RE CONTAINER_RE; QUERY_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else POD_RE_TMP="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; if [ -z "$POD_RE_TMP" ]; then printf '%s\n' '중단: Pod regex 생성 실패' >&2; else POD_RE="^${POD_RE_TMP}$"; if [ "$SELECTION_READY" = true ]; then CONTAINER_RE_TMP="$(printf '%s' "$CONTAINER" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; if [ -z "$CONTAINER_RE_TMP" ]; then printf '%s\n' '중단: container regex 생성 실패' >&2; else CONTAINER_RE="^${CONTAINER_RE_TMP}$"; QUERY_READY=true; export POD_RE CONTAINER_RE; printf 'QUERY_READY=true POD_RE=%s CONTAINER_RE=%s\n' "${POD_RE:0:256}" "${CONTAINER_RE:0:256}"; fi; else QUERY_READY=true; export POD_RE; printf 'QUERY_READY=true POD_RE=%s container=selection_required\n' "${POD_RE:0:256}"; fi; fi; fi`

`QUERY_READY=true`가 아니면 query를 생성하지 않는다. 결과가 비면 metric 미수집, label 불일치, 조회 범위 오류 또는 대상 없음일 수 있고 query API 실패·권한 부족과 구분해야 한다.

**대상 image·container 상태 PromQL 생성**

`if [ "$QUERY_READY" != true ]; then printf '%s\n' '중단: QUERY_READY가 아니다.' >&2; elif [ -z "${CONTAINER_RE:-}" ]; then printf 'kube_pod_container_info{namespace="%s",pod=~"%s",uid="%s"}\n' "$NS" "$POD_RE" "$POD_UID"; else printf 'kube_pod_container_info{namespace="%s",pod=~"%s",container=~"%s",uid="%s"}\nkube_pod_container_status_running{namespace="%s",pod=~"%s",container=~"%s",uid="%s"}==1\nsum by(namespace,pod,uid,container)(increase(kube_pod_container_status_restarts_total{namespace="%s",pod=~"%s",container=~"%s",uid="%s"}[15m]))\n' "$NS" "$POD_RE" "$CONTAINER_RE" "$POD_UID" "$NS" "$POD_RE" "$CONTAINER_RE" "$POD_UID" "$NS" "$POD_RE" "$CONTAINER_RE" "$POD_UID"; fi`

image·image_id와 Running 상태를 확인하는 metric은 binary·shell·PATH·interpreter 존재, `pods/exec` 인가, kubelet/runtime stream을 보장하지 않는다. metric이 없으면 0으로 만들지 않고 중앙 scrape·label·범위를 확인하며, API query 자체가 실패하면 query 권한·transport 계층으로 이동한다.
