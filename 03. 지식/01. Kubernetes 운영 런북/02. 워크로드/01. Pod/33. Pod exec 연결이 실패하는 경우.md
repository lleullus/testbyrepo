# Pod exec 연결이 실패하는 경우

## 입력값과 빠른 수집

이 문서는 Pod와 container를 지정했지만 `kubectl exec`가 stream을 열지 못하거나 연결 중 끊기는 경우를 다룬다. 대상 선택·image 명령 부재·RBAC를 API server→kubelet→runtime stream 문제와 섞지 않는다.

| 값 종류 | 이 문서에서 쓰는 값 | 출처와 처리 |
|---|---|---|
| 최초 입력 | `CONTEXT`, `NS`, `POD` | 운영자가 승인된 context, namespace, 정확한 Pod 이름을 처음 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `NODE`, `PHASE`, `POD_START`, `CONTAINER_ID`, container status·시작 시각, node runtime 후보 | Kubernetes API에서 현재 Pod·node identity를 읽고 시각과 관계를 보존한다. |
| 계산 후보값 | `OBSERVED_AT`, `POD_RE`, `CONTAINER_RE`, journal filter, 생성된 PromQL | 수집 시각·escaped selector·bounded filter를 생성하지만 실제 protocol·endpoint·metric 존재 전에는 확정하지 않는다. |
| 운영자 선택값 | `CONTAINER`, `READ_ONLY_COMMAND`, `NODE_HOST`, `KUBELET_UNIT`, `RUNTIME_UNIT`, `START_JOURNAL`, `END_JOURNAL` | 자동 출력과 image 계약·승인된 remote node·실제 systemd unit·journal 범위를 확인한 뒤 해당 분기에서 선택한다. |

모든 kubectl 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. `CONTEXT`는 kubeconfig의 API server 대상이고, namespace·Pod·container identity는 이후 모든 명령에 그대로 재사용한다. 33번에서는 local `journalctl`을 실행하지 않으며 승인된 `NODE_HOST`로만 safe-quoted SSH remote journal을 실행한다. 새 shell로 이동하면 변수와 gate를 잃으므로 이 문서의 첫 절부터 다시 시작한다.

**실행 host와 필수 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: Bash에서 실행한다.' >&2; else MISSING_TOOLS=''; for TOOL in kubectl jq sed grep date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true shell=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`auth_can_i`는 `AUTH_OUTPUT`, `AUTH_RC`, `AUTH_DECISION`을 별도로 등록한다. `AUTH_DECISION=yes`는 rc=0이고 출력이 정확히 한 줄 `yes`인 경우뿐이다. rc=1이고 출력이 정확히 한 줄 `no` 또는 한 줄 `no - ...`이면 정상적인 RBAC 거부로 `34번`으로 이관하며, multiline·blank extra line을 포함한 그 밖의 rc/output 조합은 API·인증 진단으로 이동한다. `pod_uid_gate`가 실패하면 최초 `$POD_UID`는 보존하고 `AUTO_READY`, `SELECTION_READY`, `CONTAINER_ID_READY` 등 파생 gate만 폐기한다.

**exec identity gate helper — 모든 exec 직전에 아래 helper를 통과**

성공 출력에는 UID·node·phase·Pod 시작 시각·관측 시각과 container별 port 후보, status, containerID, restartCount가 있어야 한다. `containerPort`는 선언값일 뿐 실제 listener·protocol·application 정상은 보장하지 않는다. 빈 출력은 대상 없음·schema·권한·조회 범위 중 하나일 수 있고 정상·오류 없음이 아니다.

재수집·재등록은 같은 이름의 새 Pod를 포함하므로 기존 container 선택, auth 결과, argv, containerID, node/journal 입력, debug/evidence gate, regex selector를 모두 폐기한다. 새 `AUTO_READY=true`만으로 stream 재시도나 정상화 검증을 진행하지 말고 container·command·auth를 다시 등록하고 각 gate를 다시 통과한다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | Pod와 container를 지정했지만 `kubectl exec`가 stream을 열지 못하거나 연결 중 끊기는 경우 |
| 적용 | 단일 context·namespace·Pod UID·node와 Running regular container를 고정할 수 있는 경우 |
| 제외 | image 명령 부재는 [[32. Pod exec 명령을 찾을 수 없는 경우#1. PATH 문제와 image의 명령 부재|32번 명령·image 절]], 대상 선택·not running은 [[31. Pod exec 대상 컨테이너를 찾을 수 없는 경우#1. Pod UID와 phase를 먼저 고정|31번 UID·phase 절]], RBAC 거부는 [[34. Pod exec 권한이 거부되는 경우#오류에서 권한 판정까지|34번 RBAC 절]]로 이동 |

검색 문자열: `unable to upgrade connection`, `error dialing backend`, `Upgrade request required`, `proxy error`, `connection refused`, `i/o timeout`, `TLS handshake timeout`, `context deadline exceeded`, `connection reset by peer`, `Forbidden`, `Unauthorized`.

이 문서의 기본 hop은 **실행 host의 Bash·local network → kubectl client → API server HTTPS endpoint와 API 인증·HTTP upgrade → API server가 선택한 대상 node의 kubelet HTTPS streaming endpoint → kubelet이 연결하는 node-local CRI runtime socket → container process**다. API endpoint port, kubelet address·port, runtime socket, remote argv와 stream protocol은 각각 다른 역할이다. 한 hop의 성공은 다음 hop 또는 application 정상의 증거가 아니다.

다음은 해결책으로 사용하지 않는다.

- `--insecure-skip-tls-verify`, 인증서 검증 비활성화, TLS 오류 무시
- cluster-admin 또는 광범위한 RBAC 부여
- 영향 범위 확인 없는 kubelet·runtime 재시작
- `delete`, rollout, scale, 재실행으로 종료 race를 재현하는 행위
- 확인되지 않은 proxy·CRI·cloud gateway 구현을 원인으로 단정하는 행위

## 최초 확인

`AUTO_READY=true`인 같은 Bash에서 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r '"UID=" + (.metadata.uid // "-") + "\tPHASE=" + (.status.phase // "-") + "\tREADY=" + ([.status.containerStatuses[]?.ready] | map(tostring) | join(",")) + "\tRESTARTS=" + ([.status.containerStatuses[]?.restartCount] | map(tostring) | join(",")) + "\tNODE=" + (.spec.nodeName // "-") + "\tAGE=" + (.metadata.creationTimestamp // "-")' <<<"$POD_SNAPSHOT"; fi`를 실행한다. `STATUS`, `READY`, `RESTARTS`, `NODE`, `AGE`, 현재 UID를 확인한다. 명령 성공은 API object 조회와 transport 도달 범위만 보장하고 kubelet stream·container process는 보장하지 않는다.

같은 조건에서 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else kubectl --context "$CONTEXT" describe pod "$POD" -n "$NS"; fi`를 실행한다. 대상 container의 `State`, `Last State`, `Reason`, `Exit Code`, `Restart Count`, Conditions와 첫 실패 message를 비민감 범위로 기록한다. `describe` 실패는 연결 원인 확정이 아니라 API·권한·도구 실패다.

`kubectl --context "$CONTEXT" get --raw='/readyz?verbose'`도 한 번 실행한다. kubectl client가 API endpoint에 요청을 보냈는지, 명령 exit와 error에 나타난 HTTP status·API response body를 분리해 기록한다. `readyz` 성공은 API server health 응답 범위만 확인하며 API server→kubelet streaming을 보장하지 않는다. `Forbidden`은 non-resource URL 권한 부족일 수 있으므로 Pod 조회·auth 결과와 분리하고, TLS 검증을 우회하지 않는다.

대상 주체의 권한은 등록된 `auth_can_i --context "$CONTEXT" auth can-i create pods/"$POD" --subresource=exec -n "$NS"`로 확인한다. rc=1과 `no` 또는 `no - ...`는 정상적인 권한 거부로 [[02. 워크로드/01. Pod/34. Pod exec 권한이 거부되는 경우|34번 RBAC 런북]]으로 이동하고, rc=0의 `yes`만 실행 gate를 통과한다. 그 밖의 non-zero/output 조합인 `Unauthorized`, DNS, `connection refused`, `i/o timeout`은 권한 판정이 아니라 인증·API 도달성 분기다.

| `Unauthorized` 또는 `You must be logged in` | kubeconfig 인증과 API endpoint | 인증 담당자, token·TLS 비노출 | [[#1. RBAC와 API 인증|1]] |

표는 길 안내이며 원인·상태 변경을 승인하지 않는다. 모든 단계에서 UID·관측 시각·`Running` state가 유지되는지 먼저 확인한다.

## 1. RBAC와 API 인증

진입 증거는 `Forbidden`, `cannot create resource pods/exec`, `Unauthorized`, `You must be logged in`이 API 요청과 함께 보이는 경우다. 필요한 값은 자동 등록된 context·namespace·Pod UID와 현재 kubeconfig 주체이며 token·kubeconfig secret·인증서 개인키는 출력하지 않는다.

등록된 `auth_can_i --context "$CONTEXT" auth can-i create pods/"$POD" --subresource=exec -n "$NS"`가 rc=1과 `no` 또는 `no - ...`를 반환하면 34번 RBAC 런북으로 이관한다. rc=0의 `yes`만 다음 stream gate로 전달하며, 그 밖의 non-zero/output 조합인 `Unauthorized`, DNS, `connection refused`, `i/o timeout`이면 권한 판정이 아니라 2절 또는 인증 담당자 분기다.

`yes`인데 실제 exec 요청이 `Forbidden`이면 오류의 subject, context, namespace, resource, subresource와 API server 감사 증거가 같은지 대조한다. `auth can-i=yes`는 실제 요청의 subject·context가 같고 stream이 성공한다는 보장이 아니다. 다른 namespace에서 `yes`를 만드는 것으로 해결하지 않으며 TLS 우회·cluster-admin 부여는 권한 복구 방법이 아니다.

`Unauthorized`, `the server has asked for the client to provide credentials`, `You must be logged in`이면 `kubectl --context "$CONTEXT" cluster-info`를 실행해 endpoint 대상과 client credential 발급·만료 상태를 인증 담당자에게 확인한다. command exit 실패와 API error status를 분리하고 token·secret·개인키를 출력하거나 저장하지 않는다.

성공 gate는 동일 context·namespace·Pod에 대해 API가 인증되고 `auth can-i` 결과가 직접 기록되는 것이다. 이것은 HTTP upgrade·kubelet·runtime·application 성공을 보장하지 않는다. 실패 시 subject·resource·subresource·UTC 시각·Pod UID를 보존해 RBAC 또는 인증 담당자로 이관한다.

## 2. client에서 API server까지의 도달성

진입 증거는 `Unable to connect to the server`, DNS 오류, `connection refused`, `i/o timeout`이 API endpoint 요청에서 보이는 경우다. 아직 kubelet streaming 단계가 아니며 remote executable이나 container runtime으로 내려가지 않는다.

범위를 제한한 확인 명령은 `kubectl --context "$CONTEXT" cluster-info`와 `kubectl --context "$CONTEXT" get --raw='/readyz?verbose'`다. 첫 명령은 client→API endpoint의 transport·대상 cluster를, 두 번째는 API server의 ready 응답을 확인한다. 명령 exit·kubectl error에 표시된 HTTP status·응답 body를 분리해 기록한다. `readyz`의 HTTP/API 성공은 API server→kubelet backend 연결을 보장하지 않는다.

성공 gate는 정확한 API endpoint에 transport가 도달하고 API 응답이 돌아오는 것이다. DNS·route·firewall·proxy·CONNECT 문제는 client와 network 담당자가 현재 endpoint의 주소·port·시간을 기준으로 확인한다. `connection refused`는 해당 주소까지 거부 응답을 받은 범위만 의미하며 listener 부재·잘못된 port·firewall을 단독 확정하지 않는다. `i/o timeout`도 network·policy·backend 지연을 단독 구분하지 않는다.

회사 proxy를 사용하는 환경에서는 proxy가 client→API인지 API→kubelet인지와 CONNECT 결과를 확인한 뒤에만 설정을 변경한다. `--insecure-skip-tls-verify`로 성공 여부를 시험하지 않는다. client→API가 정상이고 실제 오류가 `upgrade`·`backend` 계층일 때만 3절로 이동한다.

## 3. API server에서 kubelet으로의 streaming upgrade

진입 증거는 UID·node·containerID·Running state가 유지되는데 `unable to upgrade connection`, `Upgrade request required`, `error dialing backend`, `proxy error`, `connection reset by peer`가 반복되는 경우다. 이 절에서 처음 필요한 운영자 선택값은 image contract에서 확인한 비파괴 `READ_ONLY_COMMAND`이며 command 자체에 side effect나 무기한 대기가 있으면 입력하지 않는다.

**read-only argv 입력 — image contract와 승인을 확인한 뒤 한 번 등록**

`READ_ONLY_COMMAND='PASTE_READ_ONLY_COMMAND_HERE'`

실제 container 이름은 API 자동 출력의 후보를 보고 한 번만 선택해야 하며, 복수 후보에서 첫 번째를 자동 선택하지 않는다.

**container 선택값 입력 — 후보 확인 후 한 번 등록**

`CONTAINER='PASTE_CONTAINER_HERE'`

**선택·권한·argv 등록 — 아래 한 줄 전체를 복사**

`unset SELECTION_READY AUTH_READY COMMAND_READY AUTH_RESULT AUTH_OUTPUT AUTH_RC AUTH_DECISION EXEC_ARGV; SELECTION_READY=false; AUTH_READY=false; COMMAND_READY=false; EXEC_ARGV=(); if [ "$AUTO_READY" != true ] || [ -z "$CONTAINER" ] || [ -z "$READ_ONLY_COMMAND" ]; then printf '%s\n' '중단: AUTO_READY, CONTAINER, read-only command가 필요하다.' >&2; elif pod_uid_gate && jq -e --arg c "$CONTAINER" 'any(.spec.containers[]?; .name == $c) and any(.status.containerStatuses[]?; .name == $c and .state.running != null and (.containerID // "") != "")' <<<"$POD_SNAPSHOT" >/dev/null && auth_can_i --context "$CONTEXT" auth can-i create pods/"$POD" --subresource=exec -n "$NS"; then AUTH_RESULT="$AUTH_OUTPUT"; if [ "$AUTH_DECISION" = yes ]; then read -r -a EXEC_ARGV <<<"$READ_ONLY_COMMAND"; if [ "${#EXEC_ARGV[@]}" -gt 0 ]; then SELECTION_READY=true; AUTH_READY=true; COMMAND_READY=true; export CONTAINER READ_ONLY_COMMAND AUTH_RESULT; printf 'SELECTION_READY=true AUTH_READY=true container=%s argv_count=%s\n' "$CONTAINER" "${#EXEC_ARGV[@]}"; else printf '%s\n' '중단: read-only argv가 비어 있다.' >&2; fi; elif [ "$AUTH_DECISION" = no ]; then printf '중단: pods/exec 권한 거부 RBAC로 이관 rc=%s output=%s\n' "$AUTH_RC" "$AUTH_OUTPUT" >&2; else printf '중단: auth API 호출 실패 rc=%s output=%s\n' "$AUTH_RC" "${AUTH_OUTPUT:--}" >&2; fi; else printf '%s\n' '중단: 현재 UID·container state·auth 조회 실패. 부분 등록하지 않는다.' >&2; fi`

성공 gate는 선택 container가 현재 spec/status에 있고 Running·containerID이며, same-subject `auth can-i`가 `yes`이고 argv가 준비된 것이다. 이 gate는 API server→kubelet stream을 보장하지 않는다. 빈 status는 container lifecycle 문제이고, `Forbidden`은 RBAC로 이동한다.

**선택 container ID 등록 — runtime·Event 분기에서 재입력하지 않도록 한 번 확정**

`unset CONTAINER_ID; CONTAINER_ID_READY=false; if [ "$SELECTION_READY" != true ] || ! pod_uid_gate; then printf '%s\n' '중단: SELECTION_READY 또는 UID gate가 아니다.' >&2; elif CONTAINER_ID="$(jq -r --arg c "$CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID][0] // empty' <<<"$POD_SNAPSHOT")" && [ -n "$CONTAINER_ID" ]; then CONTAINER_ID_READY=true; export CONTAINER_ID; printf 'CONTAINER_ID_READY=true pod_uid=%s container=%s container_id=%s\n' "$POD_UID" "$CONTAINER" "$CONTAINER_ID"; else printf '%s\n' '중단: 선택 container의 현재 containerID 조회 실패. kubelet/runtime log를 실행하지 않는다.' >&2; fi`

`CONTAINER_ID_READY=true`가 아니면 kubelet/runtime log 분기로 내려가지 않는다. containerID는 Pod UID와 다른 runtime 식별자이며, 재생성되면 이전 log와 섞지 않는다.

exec 직전 확인 명령은 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r --arg c "$CONTAINER" '(.metadata.uid + "\t" + (.status.phase // "-") + "\t" + (.spec.nodeName // "-")), ([.status.containerStatuses[]? | select(.name==$c) | "name=" + .name + " running=" + (.state.running.startedAt // "-") + " containerID=" + (.containerID // "-")] | .[])' <<<"$POD_SNAPSHOT"; fi`이다. 성공 gate는 자동 수집 UID·node·containerID와 일치하는 Running 행이다. 빈 출력이나 UID 변경은 stream 문제로 해석하지 않고 [[31. Pod exec 대상 컨테이너를 찾을 수 없는 경우#1. Pod UID와 phase를 먼저 고정|31번 UID·phase 절]]로 이동한다.

재확인 뒤 실제 테스트 명령은 `if [ "$SELECTION_READY" != true ] || [ "$AUTH_READY" != true ] || [ "$COMMAND_READY" != true ] || ! exec_identity_gate regular "$CONTAINER" "$CONTAINER_ID"; then printf '%s\n' '중단: selection/auth/command/UID/container state/containerID gate가 준비되지 않았다.' >&2; else kubectl --context "$CONTEXT" exec "$POD" -n "$NS" -c "$CONTAINER" -- "${EXEC_ARGV[@]}"; fi`이다. `executable file not found`, `sh: ... not found`, `permission denied`이면 API streaming 장애로 닫지 말고 [[32. Pod exec 명령을 찾을 수 없는 경우#1. PATH 문제와 image의 명령 부재|32번 명령·image 절]]로 이동한다. UID·node·Running이 유지되고 upgrade/backend 오류가 반복될 때만 API server 로그로 내려간다.

API server 운영자는 실제 배포판의 승인된 로그 조회 방법으로 같은 UTC 시간 범위·Pod UID·node를 검색한다. 구현·로그 수집기가 미확정이면 명령을 발명하지 않는다. 보존할 필터 후보는 `POD_UID`, `NODE`, `upgrade`, `proxy`, `backend`, `dial`, `stream`, `x509`, `refused`, `timeout`이다.

예상 분기: backend dial의 `connection refused`·`i/o timeout`은 API server→kubelet route·firewall 후보이고, `x509`는 kubelet TLS 기간·SAN·신뢰 체인 후보다. upgrade·proxy 오류만 있고 backend dial이 없으면 API streaming/proxy 구현과 kubelet 응답 시각을 대조한다. 어느 경우도 오류 한 줄만으로 firewall·proxy 구현·protocol을 확정하지 않는다. API server 로그의 endpoint·시각이 맞으면 4절로 이동하고, backend 요청 생성 자체가 실패하면 network/TLS 담당자에게 이관한다.

## 4. kubelet streaming과 runtime

진입 증거는 API server→kubelet network·TLS가 확인됐고 backend stream이 실패하거나, API upgrade 뒤 stream이 끊기며 kubelet/runtime 오류가 같은 시각에 보이는 경우다. 필요한 값은 API 자동값 `POD_UID`, `NODE`, `CONTAINER_ID`, `CONTAINER`와 API server 로그의 UTC 시각이며 remote node host·실제 kubelet/runtime systemd unit은 운영자가 승인된 host에서 확인한다.

**승인된 remote node·systemd unit 입력 — API/SSH preflight 전에 한 번 등록**

`NODE_HOST='PASTE_NODE_HOST_HERE'; KUBELET_UNIT='PASTE_KUBELET_UNIT_HERE'; RUNTIME_UNIT='PASTE_RUNTIME_UNIT_HERE'`

`NODE_HOST`는 SSH 목적지일 뿐 journal 명령에 문자열로 삽입하지 않는다. `KUBELET_UNIT`과 `RUNTIME_UNIT`은 remote host에서 실제로 확인한 unit 이름이어야 하며, 아래 preflight가 API node name·machineID, remote hostname·machine-id, 두 unit의 loaded/active 상태를 모두 대조한다.

**remote node·unit preflight helper 등록**

`journal_window_gate(){ local start_epoch end_epoch; JOURNAL_WINDOW_READY=false; if start_epoch="$(date -u -d "$START_JOURNAL" +%s 2>/dev/null)" && end_epoch="$(date -u -d "$END_JOURNAL" +%s 2>/dev/null)" && [ "$start_epoch" -lt "$end_epoch" ]; then JOURNAL_WINDOW_READY=true; export JOURNAL_WINDOW_READY; printf 'JOURNAL_WINDOW_READY=true start=%s end=%s\n' "$START_JOURNAL" "$END_JOURNAL"; return 0; else printf '중단: START_JOURNAL < END_JOURNAL 시간 순서 또는 형식이 유효하지 않다.\n' >&2; return 1; fi; }; node_remote_preflight(){ local node_api node_api_name node_machine remote remote_host remote_machine unit_check ssh_rc; NODE_REMOTE_READY=false; if [ -z "$NODE_HOST" ] || [ -z "$KUBELET_UNIT" ] || [ -z "$RUNTIME_UNIT" ] || ! command -v ssh >/dev/null 2>&1 || ! node_identity_gate; then printf '%s\n' '중단: NODE_HOST·unit·ssh·current UID/node gate가 준비되지 않았다.' >&2; return 1; elif node_api="$(kubectl --context "$CONTEXT" get node "$NODE" -o jsonpath='{.metadata.name}{"\t"}{.status.nodeInfo.machineID}{"\n"}')" && node_api_name="${node_api%%$'\t'*}" && node_machine="${node_api#*$'\t'}" && [ "$node_api_name" = "$NODE" ] && [ -n "$node_machine" ]; remote_machine="${remote#*$'\n'}"; remote_machine="${remote_machine%%$'\n'*}"; if [ "$remote_host" != "$node_api_name" ] || [ "$remote_machine" != "$node_machine" ]; then printf '중단: API node와 remote hostname/machineID 불일치 api_node=%s remote_host=%s api_machine=%s remote_machine=%s\n' "$node_api_name" "$remote_host" "$node_machine" "$remote_machine" >&2; return 1; fi; NODE_API_NAME="$node_api_name"; NODE_API_MACHINE_ID="$node_machine"; REMOTE_HOSTNAME="$remote_host"; REMOTE_MACHINE_ID="$remote_machine"; NODE_UNIT_CHECK="$unit_check"; NODE_REMOTE_READY=true; return 0; else printf '중단: Node API name 또는 machineID 조회 실패 node=%s output=%s\n' "$NODE" "${node_api:--}" >&2; return 1; fi; }`

**strict UTC·systemd unit gate — 위 preflight helper 등록 뒤 같은 Bash에서 한 번 등록**

`systemd_unit_allowlist_gate(){ local unit="$1"; if [[ "$unit" =~ ^[A-Za-z0-9_.@-]+(\.service)?$ ]]; then return 0; else printf '중단: systemd unit allowlist 불일치 unit=%s\n' "$unit" >&2; return 1; fi; }; journal_window_gate(){ local start_epoch end_epoch start_canonical end_canonical; JOURNAL_WINDOW_READY=false; if ! 먼저 `if ! systemd_unit_allowlist_gate "$KUBELET_UNIT" || ! systemd_unit_allowlist_gate "$RUNTIME_UNIT" || ! node_remote_preflight; then printf '%s\n' '중단: current Pod UID·spec.nodeName·API/SSH node identity·unit allowlist·실제 unit gate가 준비되지 않았다.' >&2; else kubectl --context "$CONTEXT" get node "$NODE" -o jsonpath='{.metadata.name}{"\t"}{.status.nodeInfo.containerRuntimeVersion}{"\t"}{.status.nodeInfo.kubeletVersion}{"\n"}'; fi`를 실행한다. 성공 gate는 node와 runtime version이 확인되고 API node와 remote hostname·machineID, allowlist를 통과한 kubelet/runtime unit이 일치하는 것이다. 빈 출력·API·SSH·systemd 실패는 runtime down의 증거가 아니며 preflight 실패로 중단한다.

API server와 kubelet 로그를 좁힐 실제 시간 범위를 확인한 뒤 아래 값을 한 번 입력한다. local journal은 사용하지 않으며 너무 넓은 범위나 다른 Pod의 시간을 사용하지 않는다.

**kubelet/runtime journal 시간 선택값 입력 — 같은 Bash에서 한 번 등록**

`START_JOURNAL='PASTE_START_JOURNAL_HERE'; END_JOURNAL='PASTE_END_JOURNAL_HERE'`

시간은 공백을 포함한 정확한 `YYYY-MM-DD HH:MM:SS UTC` 형식으로 입력한다. 예: `2026-07-29 12:00:00 UTC`.

**node journal 도구·host gate — 아래 한 줄 전체를 복사**

`NODE_TOOLS_READY=false; if [ "$AUTO_READY" != true ] || [ -z "$NODE" ] || [ -z "$START_JOURNAL" ] || [ -z "$END_JOURNAL" ]; then printf '%s\n' '중단: identity와 journal 시간값이 준비되지 않았다.' >&2; elif command -v ssh >/dev/null 2>&1; then NODE_TOOLS_READY=true; printf 'NODE_TOOLS_READY=true remote_node=%s start=%s end=%s\n' "$NODE_HOST" "$START_JOURNAL" "$END_JOURNAL"; else printf '%s\n' '중단: ssh가 없어 remote node log를 수집하지 않는다.' >&2; fi`

현재 host가 target node journal을 읽는 대신 승인된 `NODE_HOST`의 remote journal만 사용하고 `NODE_TOOLS_READY=true`일 때 같은 Pod UID·containerID·`spec.nodeName==$NODE`의 remote identity를 유지한다. 실제 실행 직전에는 strict `START_JOURNAL < END_JOURNAL`, API/SSH remote identity·loaded/active unit gate도 필요하며, gate가 통과하면 `if [ "$NODE_TOOLS_READY" != true ] || [ "$CONTAINER_ID_READY" != true ] || ! journal_window_gate || ! systemd_unit_allowlist_gate "$KUBELET_UNIT" || ! systemd_unit_allowlist_gate "$RUNTIME_UNIT" || ! exec_identity_gate regular "$CONTAINER" "$CONTAINER_ID" || ! node_remote_preflight; then printf '%s\n' '중단: node tools·remote identity·UID/container state/containerID·journal window·unit gate가 준비되지 않았다.' >&2; else printf -v REMOTE_JOURNAL_CMD 'bash -s -- %q %q %q %q %q' "$START_JOURNAL" "$END_JOURNAL" "$POD_UID" "$CONTAINER" "$KUBELET_UNIT"; ssh -- "$NODE_HOST" "$REMOTE_JOURNAL_CMD" <<< 'start="$1"; end="$2"; pod_uid="$3"; container="$4"; unit="$5"; sudo -n journalctl -u "$unit" --since "$start" --until "$end" --no-pager | grep -E -i -C 3 "$pod_uid|$container|stream|exec|runtime|failed|certificate|authentication|authorization|not running|not found"; journal_producer_rc="${PIPESTATUS[0]}"; journal_filter_rc="${PIPESTATUS[1]}"; printf "journal_producer_rc=%s filter_rc=%s\\n" "$journal_producer_rc" "$journal_filter_rc"; if [ "$journal_producer_rc" -ne 0 ] || [ "$journal_filter_rc" -gt 1 ]; then exit 1; fi'; REMOTE_JOURNAL_RC=$?; if [ "$REMOTE_JOURNAL_RC" -ne 0 ]; then printf '중단: remote kubelet journal 실행 실패 rc=%s\n' "$REMOTE_JOURNAL_RC" >&2; fi; fi`를 실행한다. `%q`로 만든 하나의 remote command가 시간·UID·container·unit을 원격 Bash positional argument로 전달하므로 공백 포함 시간도 단일 인수로 유지된다. `sudo -n`, SSH, unit, journal 접근 실패는 remote node 수집 실패이며, 필터가 비어도 오류 없음으로 닫지 않는다. `failed to serve`, `streaming connection`, authentication·authorization은 kubelet listener·인증·인가 후보이고, `container runtime is down`, `failed to get container status`, `PLEG`는 runtime·container lifecycle 후보다.

runtime 구현이 `containerd`이고 실제 unit·권한이 확인된 경우에만 `if [ "$NODE_TOOLS_READY" != true ] || [ "$CONTAINER_ID_READY" != true ] || ! journal_window_gate || ! systemd_unit_allowlist_gate "$KUBELET_UNIT" || ! systemd_unit_allowlist_gate "$RUNTIME_UNIT" || ! exec_identity_gate regular "$CONTAINER" "$CONTAINER_ID" || ! node_remote_preflight; then printf '%s\n' '중단: node tools·remote identity·UID/container state/containerID·journal window·unit gate가 준비되지 않았다.' >&2; else printf -v REMOTE_JOURNAL_CMD 'bash -s -- %q %q %q %q %q %q' "$START_JOURNAL" "$END_JOURNAL" "$CONTAINER_ID" "$POD_UID" "$CONTAINER" "$RUNTIME_UNIT"; ssh -- "$NODE_HOST" "$REMOTE_JOURNAL_CMD" <<< 'start="$1"; end="$2"; container_id="$3"; pod_uid="$4"; container="$5"; unit="$6"; sudo -n journalctl -u "$unit" --since "$start" --until "$end" --no-pager | grep -E -i -C 3 "$container_id|$pod_uid|$container|shim|stream|exec|not found|deadline|failed|runtime"; runtime_producer_rc="${PIPESTATUS[0]}"; runtime_filter_rc="${PIPESTATUS[1]}"; printf "runtime_journal_producer_rc=%s filter_rc=%s\\n" "$runtime_producer_rc" "$runtime_filter_rc"; if [ "$runtime_producer_rc" -ne 0 ] || [ "$runtime_filter_rc" -gt 1 ]; then exit 1; fi'; REMOTE_JOURNAL_RC=$?; if [ "$REMOTE_JOURNAL_RC" -ne 0 ]; then printf '중단: remote containerd journal 실행 실패 rc=%s\n' "$REMOTE_JOURNAL_RC" >&2; fi; fi`를 실행한다. `%q`로 만든 하나의 remote command가 공백 포함 시간을 단일 원격 Bash 인수로 보존하고, runtime 인수 순서는 `container_id`, `pod_uid`, `container`, `unit`이다. `sudo -n`, SSH, unit, journal 접근 실패는 remote node 수집 실패이며, 필터가 비어도 오류 없음으로 닫지 않는다. `failed to create shim task`, `runc exec failed`, `stream copy error`, `context deadline exceeded`가 같은 containerID·시각이면 CRI/OCI streaming과 runtime 상태 담당자로 이관한다. runtime이 container를 제거했거나 ID가 바뀌면 새 exec를 반복하지 않고 5절 lifecycle을 먼저 확인한다. CRI-O 등 다른 runtime은 실제 service unit과 로그 위치를 확인한 뒤 동일한 시간·필터 범위를 사용하고, endpoint·권한을 확인하지 않은 `crictl`은 실행하지 않는다.

성공 gate는 kubelet·runtime 로그의 identity·시각·stream layer가 API server 오류와 일치하는 것이다. kubelet log 성공은 runtime·container application 정상 또는 API client 정상까지 보장하지 않는다.

## 5. container running과 종료 race

진입 증거는 API server·kubelet·runtime 경로를 확인하는 동안 `not running`, `container not found`, `Killing`, `OOMKilled`, `Error`, `context deadline exceeded`와 종료 시각이 exec 요청 시각에 겹치는 경우다. 필요한 값은 자동 등록된 Pod UID·containerID·phase·restartCount다.

범위를 제한한 확인 명령은 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else jq -r --arg c "$CONTAINER" '[ (.metadata.uid + "\t" + (.status.phase // "-")), (.status.containerStatuses[]? | select(.name==$c) | "name=" + .name + "\tid=" + (.containerID // "-") + "\trunning=" + (.state.running.startedAt // "-") + "\twaiting=" + (.state.waiting.reason // "-") + "\tterminated=" + (.state.terminated.reason // "-") + "\tfinished=" + (.state.terminated.finishedAt // "-") + "\tlastFinished=" + (.lastState.terminated.finishedAt // "-") + "\trestarts=" + ((.restartCount // "-") | tostring)) ] | .[]' <<<"$POD_SNAPSHOT"; fi`이다. 성공 gate는 현재 UID와 선택 container의 current state·last state·ID·restartCount를 같은 시각으로 기록하는 것이다. `Terminated`, `Killing`, `OOMKilled`, `Error`가 맞으면 lifecycle로 분류한다. Pod가 `Pending`, `Succeeded`, `Failed`, `Unknown`이면 exec를 반복하지 않는다.

`finishedAt`, exit code, restartCount, Pod UID와 runtime 로그의 containerID를 보존하고 [[31. Pod exec 대상 컨테이너를 찾을 수 없는 경우#1. Pod UID와 phase를 먼저 고정|31번 UID·phase 절]] 또는 workload 상태 런북으로 이동한다. 확인 명령의 성공은 과거 stream이 정상이었다는 뜻이 아니며 빈 status는 오류 없음이 아니다.

## Pod Event는 UID를 확인한 뒤 한 번만

진입 증거는 현재 Pod lifecycle과 kubelet/runtime 시각을 대조할 bounded Event가 필요할 때다. 현재 `POD_UID`를 자동값으로 확인한 뒤 `if ! pod_uid_gate; then printf '%s\n' '중단: UID gate 실패' >&2; else kubectl --context "$CONTEXT" get events -n "$NS" --field-selector involvedObject.kind=Pod,involvedObject.name="$POD",involvedObject.uid="$POD_UID" --sort-by=.metadata.creationTimestamp -o custom-columns='CREATED:.metadata.creationTimestamp,FIRST-SEEN:.firstTimestamp,LAST-SEEN:.lastTimestamp,EVENT-TIME:.eventTime,SERIES-LAST:.series.lastObservedTime,TYPE:.type,REASON:.reason,COUNT:.count,MESSAGE:.message'; fi`를 한 번만 실행한다.

성공 gate는 같은 UID의 필요한 Event와 실제로 채워진 FIRST·LAST·EVENT·series 시각을 exec·container 종료 시각과 비교하는 것이다. `Killing`, `BackOff`, `Failed`, `FailedCreatePodSandbox`가 같은 UID·시각이면 lifecycle·kubelet/runtime 분기로 이동한다. Event가 없거나 집계 시각만 다르면 오류가 없다고 결론내리지 않는다. API 오류·Forbidden·빈 결과를 서로 구분하고 민감한 message 원문은 저장하지 않는다.

## 제한적 변경의 경계

network rule, certificate, proxy, kubelet, runtime 또는 host 설정 변경이 필요하면 진단과 별도 action contract로 분리한다. 정확한 오류·UTC 시각·context·namespace·Pod UID·node·실패 layer, 대상과 영향, 실행자·승인자·incident/change ID, 정확한 변경값·사전 백업·검증, 기대 효과와 비보장, 중단·rollback 조건, 실행 후 `readyz`·UID·state·로그·실제 서비스 지표 검증을 기록한다.

TLS 검증 비활성화, cluster-admin 부여, 원인·영향 범위 없는 서비스 재시작은 승인 가능한 action이 아니다. 이 문서에는 상태 변경 명령을 진단 명령과 섞지 않는다.

## 정상화와 증거 보존

승인된 변경 뒤에는 원인 경로를 역순으로 확인한다. 먼저 application의 실제 기능 또는 비파괴 exec 결과, 그 다음 container process·runtime ID, kubelet stream, API server→kubelet upgrade, API auth/reachability와 client endpoint를 확인한다. Pod UID·node·containerID·Running state가 유지되고 새 Warning·restart 증가·동일 오류가 관찰 창에서 없으며 실제 요청·핵심 기능 지표가 정상이어야 한다.

정상화 검증 명령은 `if [ "$SELECTION_READY" != true ] || [ "$AUTH_READY" != true ] || [ "$COMMAND_READY" != true ] || ! exec_identity_gate regular "$CONTAINER" "$CONTAINER_ID"; then printf '%s\n' '중단: selection/auth/command/UID/container state/containerID gate가 준비되지 않았다.' >&2; else kubectl --context "$CONTEXT" exec "$POD" -n "$NS" -c "$CONTAINER" -- "${EXEC_ARGV[@]}"; EXEC_RC=$?; jq -r '"POD=" + (.metadata.name // "-") + "\tUID=" + (.metadata.uid // "-") + "\tPHASE=" + (.status.phase // "-") + "\tREADY=" + ([.status.containerStatuses[]?.ready] | map(tostring) | join(",")) + "\tRESTARTS=" + ([.status.containerStatuses[]?.restartCount] | map(tostring) | join(",")) + "\tNODE=" + (.spec.nodeName // "-") + "\tIMAGE-ID=" + ([.status.containerStatuses[]?.imageID // "-"] | join(","))' <<<"$POD_SNAPSHOT"; printf 'exec_rc=%s\n' "$EXEC_RC"; fi`다. command exit 0은 선택한 remote process와 stream 범위만 확인하고 application 기능·API server log·재발 부재를 보장하지 않는다.

증거에는 UTC 시각, context·namespace, Pod UID·node, container ID, 원문 오류, kubectl exit와 HTTP/API error status가 있으면 함께 기록하고, `readyz` 요약, Pod state·Event, API server·kubelet·runtime 로그의 시간·필터·식별자, action ID를 남긴다. Secret·token·인증서 개인키·개인정보는 보존하지 않는다.

## Prometheus 빠른 관측

PromQL은 문서에서 직접 수정하지 않는다. 같은 Bash의 `NS`, `POD_RE`, `CONTAINER_RE`로 완성 문자열을 생성해 출력된 한 줄만 Prometheus 또는 Grafana에 붙여 넣는다. query transport/API 오류, metric 부재, label 불일치, 조회 범위 문제를 구분한다.

**Pod·container regex 등록 — 아래 한 줄 전체를 복사**

`unset QUERY_READY POD_RE CONTAINER_RE; QUERY_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else POD_RE_TMP="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; if [ -z "$POD_RE_TMP" ]; then printf '%s\n' '중단: Pod regex 생성 실패' >&2; else POD_RE="^${POD_RE_TMP}$"; if [ "$SELECTION_READY" = true ]; then CONTAINER_RE_TMP="$(printf '%s' "$CONTAINER" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; if [ -z "$CONTAINER_RE_TMP" ]; then printf '%s\n' '중단: container regex 생성 실패' >&2; else CONTAINER_RE="^${CONTAINER_RE_TMP}$"; QUERY_READY=true; export POD_RE CONTAINER_RE; printf 'QUERY_READY=true POD_RE=%s CONTAINER_RE=%s\n' "${POD_RE:0:256}" "${CONTAINER_RE:0:256}"; fi; else printf '%s\n' '중단: container 선택 전에는 query를 생성하지 않는다.' >&2; fi; fi; fi`

`QUERY_READY=true`가 아니면 PromQL을 생성하지 않는다. label·metric이 실제 수집되는지 확인하기 전 빈 결과를 정상·0·오류 없음으로 해석하지 않는다.

**대상 Pod·Running container PromQL 생성**

`if [ "$QUERY_READY" != true ]; then printf '%s\n' '중단: QUERY_READY가 아니다.' >&2; else printf 'kube_pod_info{namespace="%s",pod=~"%s",uid="%s"}\nkube_pod_container_status_running{namespace="%s",pod=~"%s",container=~"%s",uid="%s"}==1\nsum by(code,resource,subresource)(increase(apiserver_request_total{resource="pods",subresource="exec",code=~"5.."}[15m]))>0\n' "$NS" "$POD_RE" "$POD_UID" "$NS" "$POD_RE" "$CONTAINER_RE" "$POD_UID"; fi`

`kube_pod_info`와 `Running`은 object·container 상태의 수집 범위만 보여 주며 API server→kubelet→runtime stream과 application 정상은 보장하지 않는다. API server metric의 label 구성이 실제 확인된 환경에서만 세 번째 query를 사용하고, metric이 없으면 미수집·label 불일치·범위 문제를 확인한다. Prometheus API 자체의 transport·HTTP status·query error는 결과가 빈 것과 분리한다.
