# Pod STATUS가 Completed·Succeeded인데 비정상인 경우

## 입력값과 빠른 수집

이 런북은 `kubectl` printer의 `Completed`, Pod API의 `phase=Succeeded`, 컨테이너 `exitCode=0`이 업무 성공을 보장하지 않는 경우를 다룬다. Job·CronJob의 산출물과 외부 side effect, sidecar 종료 순서, 장기 실행 workload의 예상치 못한 정상 종료를 분리한다. 세 상태가 모두 성공처럼 보여도 외부 DB/API/queue commit·ack, 부분 처리, 중복 실행은 별도로 확인한다.

| 분류 | 이 문서에서 쓰는 값 | 출처와 처리 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 승인된 namespace와 Pod 이름을 한 번 입력한다. |
| API 자동값 | `POD_UID`, `NODE`, `PHASE`, `RESTART_POLICY`, `OWNER_KIND`, `OWNER_NAME`, `OWNER_UID`, `POD_CREATED`, container/status 후보 | 대상 Pod API에서 읽어 현재 Bash에 등록한다. UID·owner·container 상태가 비거나 API가 실패하면 중단한다. |
| 계산 후보 | `NS_RE`, `POD_RE`, `UID_RE`, `PROMQL_READY` | PromQL 생성용으로 이름을 escape한다. 생성된 한 줄을 확인하기 전에는 쿼리로 사용하지 않는다. |
| 운영자 선택값 | `CONTAINER`, `START_RFC3339`, `START_JOURNAL`, `END_JOURNAL` | 자동 출력과 장애 시각을 확인한 뒤 한 번 입력한다. 시간 형식·대상 container 검증 전에는 로그에 사용하지 않는다. |
| 상세 분기 선택값 | `SIDE_CAR`, `WORKLOAD_KIND`, `WORKLOAD_NAME`, `NODE_HOST`, `RUNTIME_SERVICE` | 해당 분기에만 실제 구현·접속 경계를 확인한 뒤 입력한다. 추측한 node SSH 이름이나 runtime unit은 사용하지 않는다. |
| 변경 선택값 | `APPROVAL_ID`, `NEW_JOB` | CronJob 보완 실행을 승인받은 경우에만 입력한다. 진단 단계에서는 사용하지 않는다. |

### 1. 실행 host·도구·최초 입력

모든 기본 명령은 승인된 context가 설정된 **작업 PC 또는 bastion의 같은 Bash 터미널**에서 실행한다. `NS`, `POD`와 자동값은 이 Bash에서 계속 재사용한다. PowerShell, CMD, 별도 shell로 바꾸면 gate와 변수 상태가 사라지므로 처음부터 다시 시작한다. `kubectl`은 API server로, logs는 API server에서 대상 node의 kubelet/runtime을 거쳐 container stream으로 연결된다. API 응답 성공은 node·container·애플리케이션 성공을 보장하지 않는다.

필수 도구는 `kubectl`, `jq`, `grep`, `sed`, `date`다. 확인 실패 시 아래 초기화·수집을 포함한 다음 단계로 진행하지 않는다.

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash 터미널에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 namespace·Pod 권한과 도구를 먼저 복구한다. `jq` 없이 raw Pod JSON을 저장하거나 Secret·token이 섞인 원문을 출력하지 않는다.

### 2. 이전 상태 초기화와 대상 입력

재실행 시작 시 이전 UID·owner·선택값·분기 gate를 지운다. 이전 Pod와 같은 이름으로 새 Pod가 생성됐을 수 있으므로 이름만 재사용하지 않는다.

`unset INPUT_READY AUTO_READY SELECTION_READY TIME_READY FIRST_CHECK_READY PROMQL_READY POD_UID NODE PHASE RESTART_POLICY OWNER_KIND OWNER_NAME OWNER_UID POD_CREATED CONTAINER POD_JSON POD_CHECK_JSON NS_RE POD_RE UID_RE JOB_READY JOB_UID JOB_OWNER_KIND JOB_OWNER_NAME JOB_OWNER_UID CRI_ENDPOINT CRON_READY CRONJOB CRONJOB_UID ATTEMPTS_READY ATTEMPT_LIST ATTEMPT_COUNT SIDE_CAR SIDECAR_READY WORKLOAD_KIND WORKLOAD_NAME WORKLOAD_READY NODE_HOST NODE_HOST_READY NODE_IDENTITY_READY NODE_API_JSON NODE_MACHINE_ID NODE_HOSTNAME REMOTE_IDENTITY_OUT REMOTE_MACHINE_ID REMOTE_HOSTNAME REMOTE_FQDN NODE_TOOLS_READY RUNTIME_SERVICE NODE_RUNTIME_READY APPROVAL_ID APPROVAL_READY NEW_JOB; NS='PASTE_NAMESPACE_HERE'; POD='PASTE_POD_HERE'; CONTAINER='PASTE_CONTAINER_HERE'; START_RFC3339='PASTE_START_RFC3339_HERE'; START_JOURNAL='PASTE_START_JOURNAL_HERE'; END_JOURNAL='PASTE_END_JOURNAL_HERE'; INPUT_READY=false; AUTO_READY=false; SELECTION_READY=false; TIME_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: TOOLS_READY가 아니다.' >&2; elif [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: NS와 POD를 입력한다.' >&2; elif kubectl get pod "$POD" -n "$NS" >/dev/null 2>&1; then INPUT_READY=true; export NS POD; printf 'INPUT_READY=true NS=%s POD=%s\n' "$NS" "$POD"; else printf '중단: 대상 Pod 조회 실패 NS=%s POD=%s\n' "$NS" "$POD" >&2; fi`

`INPUT_READY=true`가 아니면 namespace·Pod 이름·API 권한을 고친 뒤 이 초기화 명령부터 다시 실행한다. namespace를 모를 때의 broad query는 승인된 범위에서만 사용하고, 확인된 namespace를 얻으면 즉시 namespaced 명령으로 돌아간다.

공통 로그 helper는 모든 진단 분기보다 먼저 등록한다. 등록 gate가 통과하지 않으면 helper 호출도 중단한다.

`FILTER_READY=false; FILTER_RESULT='not-run'; FILTER_MATCHED=false; scoped_filter() { FILTER_RESULT='producer-failure'; FILTER_MATCHED=false; if [ "$FILTER_READY" != true ]; then printf '%s\n' '중단: FILTER_READY가 아니다.' >&2; return 1; fi; FILTER_LABEL="$1"; FILTER_PATTERN="$2"; shift 2; "$@" 2>&1 | grep -E -i -C 3 "$FILTER_PATTERN"; FILTER_PIPE_STATUS=("${PIPESTATUS[@]}"); if [ "${FILTER_PIPE_STATUS[0]}" -ne 0 ]; then printf '로그 producer 실패 label=%s rc=%s\n' "$FILTER_LABEL" "${FILTER_PIPE_STATUS[0]}" >&2; return 1; elif [ "${FILTER_PIPE_STATUS[1]}" -eq 0 ]; then FILTER_RESULT='match'; FILTER_MATCHED=true; elif [ "${FILTER_PIPE_STATUS[1]}" -eq 1 ]; then FILTER_RESULT='no-match'; FILTER_MATCHED=false; printf '필터 결과 없음 label=%s; 오류 부재로 해석하지 않는다.\n' "$FILTER_LABEL"; else FILTER_RESULT='filter-failure'; printf '필터 실행 실패 label=%s rc=%s\n' "$FILTER_LABEL" "${FILTER_PIPE_STATUS[1]}" >&2; return 1; fi; }; if [ "$(type -t scoped_filter 2>/dev/null)" = function ]; then FILTER_READY=true; printf 'FILTER_READY=true\n'; else printf '%s\n' '중단: scoped_filter helper 등록 실패' >&2; fi`

### 3. 기본값 자동 수집·등록

다음 명령은 API가 반환한 선택 필드만 메모리에서 처리하고 전체 Pod JSON을 저장하거나 출력하지 않는다. 출력은 대상 identity·시각과 container/status 관계를 세로로 보여 준다. direct owner가 없으면 `none`으로 표시하며 standalone 경로에서만 사용한다.




`AUTO_READY=false; unset POD_UID NODE PHASE RESTART_POLICY OWNER_KIND OWNER_NAME OWNER_UID POD_CREATED; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && POD_UID_TMP="$(printf '%s' "$POD_JSON" | jq -er '.metadata.uid')" && NODE_TMP="$(printf '%s' "$POD_JSON" | jq -r '.spec.nodeName // "-"')" && PHASE_TMP="$(printf '%s' "$POD_JSON" | jq -er '.status.phase')" && RESTART_POLICY_TMP="$(printf '%s' "$POD_JSON" | jq -r '.spec.restartPolicy // "-"')" && OWNER_KIND_TMP="$(printf '%s' "$POD_JSON" | jq -r '([.metadata.ownerReferences[]? | select(.controller==true)][0].kind // "none")')" && OWNER_NAME_TMP="$(printf '%s' "$POD_JSON" | jq -r '([.metadata.ownerReferences[]? | select(.controller==true)][0].name // "-")')" && OWNER_UID_TMP="$(printf '%s' "$POD_JSON" | jq -r '([.metadata.ownerReferences[]? | select(.controller==true)][0].uid // "-")')" && POD_CREATED_TMP="$(printf '%s' "$POD_JSON" | jq -r '.metadata.creationTimestamp // "-"')" && CONTAINER_BLOCK_TMP="$(printf '%s' "$POD_JSON" | jq -r '.status.containerStatuses[]? | ["컨테이너: " + .name, "ready=" + ((.ready // "-") | tostring), "id=" + (.containerID // "-"), "current=" + (((.state // {}) | keys | join(","))), "last=" + (((.lastState // {}) | keys | join(","))), "restart=" + ((.restartCount // "-") | tostring)] | join(" ")')" && OBSERVED_AT_TMP="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; then POD_UID="$POD_UID_TMP"; NODE="$NODE_TMP"; PHASE="$PHASE_TMP"; RESTART_POLICY="$RESTART_POLICY_TMP"; OWNER_KIND="$OWNER_KIND_TMP"; OWNER_NAME="$OWNER_NAME_TMP"; OWNER_UID="$OWNER_UID_TMP"; POD_CREATED="$POD_CREATED_TMP"; printf '=== Pod: %s ===\nUID: %s\nNode: %s\nPhase: %s\nRestart policy: %s\nOwner: %s/%s UID=%s\nPod 생성 시각: %s\n컨테이너 | 상태 | ID\n%s\n관측 시각(UTC): %s\n' "$POD" "$POD_UID" "$NODE" "$PHASE" "$RESTART_POLICY" "$OWNER_KIND" "$OWNER_NAME" "$OWNER_UID" "$POD_CREATED" "$CONTAINER_BLOCK_TMP" "$OBSERVED_AT_TMP"; AUTO_READY=true; export POD_UID NODE PHASE RESTART_POLICY OWNER_KIND OWNER_NAME OWNER_UID POD_CREATED; else printf '%s\n' '중단: Pod API 또는 필수 필드 수집 실패. 부분 등록값을 사용하지 않는다.' >&2; unset POD_UID NODE PHASE RESTART_POLICY OWNER_KIND OWNER_NAME OWNER_UID POD_CREATED; fi`

`AUTO_READY=true`이고 출력에 대상 UID·phase·owner·container/status·관측 시각이 모두 있어야 다음 단계로 간다. Pod가 없거나 필드가 비어 있으면 정상·종료 성공으로 해석하지 않는다. UID가 바뀌면 이전 로그·Event·외부 결과와 섞지 않고 이 수집부터 다시 실행한다.

### 4. 운영자 선택값 검증

`CONTAINER`는 자동 출력의 container 후보에서 업무 주 컨테이너를 고른 값이다. sidecar 분기에서는 별도의 `SIDE_CAR`를 선택한다. `START_RFC3339`는 관련 종료 시각과 첫 Event보다 조금 앞선 UTC 시각이며, journal 값은 node의 현지 journal 표시 형식에 맞춘다.

`SELECTION_READY=false; unset POD_CHECK_JSON CURRENT_POD_UID; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif POD_CHECK_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && CURRENT_POD_UID="$(printf '%s' "$POD_CHECK_JSON" | jq -er '.metadata.uid')" && [ "$CURRENT_POD_UID" = "$POD_UID" ] && printf '%s' "$POD_CHECK_JSON" | jq -e --arg container "$CONTAINER" 'any(.spec.containers[]?; .name==$container)' >/dev/null; then SELECTION_READY=true; export CONTAINER; printf 'SELECTION_READY=true pod=%s uid=%s container=%s\n' "$POD" "$POD_UID" "$CONTAINER"; else printf '중단: 현재 Pod UID가 바뀌었거나 container 후보가 아님 container=%s\n' "$CONTAINER" >&2; fi`

`TIME_READY=false; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif [[ "$START_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] && [ -n "$START_JOURNAL" ] && [ -n "$END_JOURNAL" ]; then TIME_READY=true; export START_RFC3339 START_JOURNAL END_JOURNAL; printf 'TIME_READY=true start=%s journal=%s..%s\n' "$START_RFC3339" "$START_JOURNAL" "$END_JOURNAL"; else printf '%s\n' '중단: START_RFC3339 또는 journal 시간 범위가 비어 있거나 형식이 맞지 않는다.' >&2; fi`

### 5. PromQL 생성값 등록

PromQL은 문서 안의 값을 직접 고치는 방식으로 사용하지 않는다. 등록된 namespace·Pod·UID를 regex 특수문자 escape한 뒤 완성된 한 줄을 생성한다. 생성 명령은 쿼리 문자열만 bounded하게 출력하며, 외부 Prometheus UI의 transport·HTTP status·query API success/data는 별도로 확인한다.

`PROMQL_READY=false; unset NS_RE POD_RE UID_RE; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif NS_RE="$(printf '%s' "$NS" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" && POD_RE="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" && UID_RE="$(printf '%s' "$POD_UID" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" && [ -n "$NS_RE" ] && [ -n "$POD_RE" ] && [ -n "$UID_RE" ]; then PROMQL_READY=true; printf 'PROMQL_READY=true namespace=%.120s pod=%.120s uid=%.120s\n' "$NS_RE" "$POD_RE" "$UID_RE"; else printf '%s\n' '중단: PromQL selector 생성 실패' >&2; fi`

`PROMQL_READY=true`가 아니면 아래 쿼리 생성 명령을 실행하지 않는다. `printf 'kube_pod_status_phase{namespace=~"%s",pod=~"%s",uid=~"%s",phase="Succeeded"}==1\n' "$NS_RE" "$POD_RE" "$UID_RE"`을 실행해 출력된 한 줄만 Prometheus 또는 Grafana에 넣는다. `printf 'time()-kube_pod_completion_time{namespace=~"%s",pod=~"%s",uid=~"%s"}\n' "$NS_RE" "$POD_RE" "$UID_RE"`도 같은 방식으로 생성한다. `printf 'kube_pod_container_status_terminated_reason{namespace=~"%s",pod=~"%s",uid=~"%s"}==1\n' "$NS_RE" "$POD_RE" "$UID_RE"`도 같은 방식으로 생성한다. 빈 결과는 정상·0·오류 없음이 아니라 metric 미수집, label 불일치, 조회 범위 문제의 후보다. PromQL 조회 실패와 metric 부재를 구분하고, 업무 결과는 API·로그·외부 시스템으로 확인한다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | `STATUS=Completed`, Pod `phase=Succeeded` 또는 container `exitCode=0`인데 Job 산출물·처리 건수·외부 반영이 없거나 장기 실행 workload가 예기치 않게 종료된 경우 |
| 적용 | Job·CronJob·standalone 일회성 Pod, 주 컨테이너와 sidecar의 종료 순서, 장기 실행 controller의 정상 종료와 실제 서비스 기능을 분리해야 하는 경우 |
| 제외 | 최초 관측이 `CrashLoopBackOff`, `OOMKilled`, `Unknown`, `ContainerStatusUnknown`이면 [[01. Pod STATUS가 Error인 경우]], [[11. Pod STATUS가 OOMKilled인 경우]], [[14. Pod STATUS가 Unknown·ContainerStatusUnknown인 경우]]로 이동한다. Job completion 자체가 수렴하지 않으면 [[01. Job completion이 수렴하지 않는 경우]], 재실행 정책 판단은 [[02. BackoffLimitExceeded 또는 DeadlineExceeded 뒤 재실행 판단이 필요한 경우]]로 이관한다. |

검색 문자열: `Completed`, `Succeeded`, `phase=Succeeded`, `exitCode=0`, `reason=Completed`, `Complete=True`, `Failed=True`, `backoffLimit`, `activeDeadlineSeconds`, `DeadlineExceeded`, `BackoffLimitExceeded`, `CronJob`, `sidecar`, `commit`, `ack`, `checksum`, `watermark`, `unexpected exit 0`.

`STATUS=Completed`는 printer 요약이고 `phase=Succeeded`는 Pod lifecycle 관측이다. 둘 다 Job controller 완료, 외부 commit·ack, 전체 입력 처리, 데이터 중복 부재를 보장하지 않는다.

## 최초 확인

`FIRST_CHECK_READY=false; if [ "$SELECTION_READY" != true ] || [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: 자동 수집·container 선택 gate를 통과하지 못했다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o wide && kubectl describe pod "$POD" -n "$NS" && kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID" --sort-by=.metadata.creationTimestamp -o custom-columns='EVENT-UID:.metadata.uid,CREATED:.metadata.creationTimestamp,FIRST-SEEN:.firstTimestamp,LAST-SEEN:.lastTimestamp,EVENT-TIME:.eventTime,SERIES-LAST:.series.lastObservedTime,TYPE:.type,REASON:.reason,COUNT:.count,MESSAGE:.message'; then FIRST_CHECK_READY=true; printf 'FIRST_CHECK_READY=true pod=%s uid=%s\n' "$POD" "$POD_UID"; else printf '%s\n' '중단: 최초 Pod·describe·Event API 조회 중 하나가 실패했다.' >&2; fi`

`FIRST_CHECK_READY=true`이면 `get`에서 `STATUS`, `PHASE`, `READY`, `RESTARTS`, `NODE`, `AGE`, owner를, `describe`에서 container별 `State`, `Last State`, `Reason`, `Exit Code`, 종료 시각과 첫 Warning을 본다. Event는 이 절에서 한 번만 UID로 제한한다. 빈 Event 출력은 오류 없음이 아니며, Event 보존·권한·시간 범위 문제를 구분한다. `FIRST_CHECK_READY=true`는 API 객체 조회 성공만 보장하고 업무 성공·node 정상·container 로그 보존은 보장하지 않는다.

### 1. Job·CronJob 완료와 업무 결과

진입 증거는 direct owner가 `Job`이고 Pod/Job에 `Complete=True`가 보이지만 산출물·처리 결과가 불명확한 경우다. 최초 필요값은 API 자동값 `OWNER_NAME`, `OWNER_UID`, `POD_UID`, 운영자 선택값 `CONTAINER`, `START_RFC3339`다. Pod direct owner가 Job이 아니면 이 절의 Job·CronJob 명령을 실행하지 않는다.

로그 filter는 producer의 rc와 filter 무일치를 분리한다. 아래 helper는 producer 실패를 필터 결과 없음으로 바꾸지 않는다.


`JOB_READY=false; CRON_READY=false; ATTEMPTS_READY=false; unset JOB JOB_JSON JOB_UID JOB_OWNER_KIND JOB_OWNER_NAME JOB_OWNER_UID CRONJOB CRONJOB_UID ATTEMPT_LIST ATTEMPT_COUNT; ATTEMPT_PODS=(); if [ "$FIRST_CHECK_READY" != true ] || [ "$OWNER_KIND" != Job ] || [ "$OWNER_NAME" = "-" ]; then printf '%s\n' '중단: direct owner가 확인된 Job이 아니다.' >&2; elif JOB_JSON="$(kubectl get job "$OWNER_NAME" -n "$NS" -o json)" && JOB_UID_TMP="$(printf '%s' "$JOB_JSON" | jq -er '.metadata.uid')" && JOB_OWNER_KIND_TMP="$(printf '%s' "$JOB_JSON" | jq -r '([.metadata.ownerReferences[]? | select(.controller==true)][0].kind // "none")')" && JOB_OWNER_NAME_TMP="$(printf '%s' "$JOB_JSON" | jq -r '([.metadata.ownerReferences[]? | select(.controller==true)][0].name // "-")')" && JOB_OWNER_UID_TMP="$(printf '%s' "$JOB_JSON" | jq -r '([.metadata.ownerReferences[]? | select(.controller==true)][0].uid // "-")')" && [ "$JOB_UID_TMP" = "$OWNER_UID" ]; then JOB="$OWNER_NAME"; JOB_UID="$JOB_UID_TMP"; JOB_OWNER_KIND="$JOB_OWNER_KIND_TMP"; JOB_OWNER_NAME="$JOB_OWNER_NAME_TMP"; JOB_OWNER_UID="$JOB_OWNER_UID_TMP"; JOB_READY=true; printf 'JOB_READY=true job=%s uid=%s owner=%s/%s owner_uid=%s\n' "$JOB" "$JOB_UID" "$JOB_OWNER_KIND" "$JOB_OWNER_NAME" "$JOB_OWNER_UID"; else printf '중단: Job API 조회 실패 또는 Pod owner UID mismatch job=%s owner_uid=%s\n' "$OWNER_NAME" "$OWNER_UID" >&2; fi`

`JOB_READY=true`이면 Job UID·condition의 `Complete`/`Failed`, `active`, `succeeded`, `failed`, `backoffLimit`, `activeDeadlineSeconds`를 확인한다. Job API 실패나 필드 빈 값은 완료 성공이 아니며 [[01. Job completion이 수렴하지 않는 경우]]로 이관한다.

`JOB_READY=false; if [ -n "${JOB_UID:-}" ] && [ "$JOB_UID" = "$OWNER_UID" ]; then JOB_READY=true; else printf '중단: Job UID가 Pod owner UID와 다르므로 Job gate와 파생값을 폐기한다. job_uid=%s owner_uid=%s\n' "${JOB_UID:--}" "${OWNER_UID:--}" >&2; unset JOB JOB_JSON JOB_UID JOB_OWNER_KIND JOB_OWNER_NAME JOB_OWNER_UID; CRON_READY=false; unset CRONJOB CRONJOB_UID; fi`

Job UID가 Pod의 `OWNER_UID`와 다르면 `JOB_READY`를 true로 두지 않는다. mismatch 뒤에는 Job·CronJob·시도 Pod의 파생값을 재사용하지 않고 이 절의 Job API 수집부터 다시 실행한다.

`if [ "$JOB_READY" != true ]; then printf '%s\n' '중단: JOB_READY가 아니다.' >&2; elif [ "$JOB_OWNER_KIND" = CronJob ] && [ "$JOB_OWNER_NAME" != "-" ]; then unset CRON_JSON CRON_UID_TMP; if [ "$JOB_OWNER_UID" = "-" ]; then printf '중단: Job의 CronJob owner UID가 없어 현재 CronJob을 검증하지 않는다. cronjob=%s\n' "$JOB_OWNER_NAME" >&2; elif CRON_JSON="$(kubectl get cronjob "$JOB_OWNER_NAME" -n "$NS" -o json)" && CRON_UID_TMP="$(printf '%s' "$CRON_JSON" | jq -er '.metadata.uid')" && [ "$JOB_OWNER_UID" = "$CRON_UID_TMP" ]; then CRONJOB="$JOB_OWNER_NAME"; CRONJOB_UID="$CRON_UID_TMP"; CRON_READY=true; printf 'CRON_READY=true cronjob=%s uid=%s job_owner_uid=%s\n' "$CRONJOB" "$CRONJOB_UID" "$JOB_OWNER_UID"; else printf '중단: CronJob API 조회 실패 또는 Job→CronJob owner UID mismatch cronjob=%s job_owner_uid=%s current_cronjob_uid=%s\n' "$JOB_OWNER_NAME" "$JOB_OWNER_UID" "${CRON_UID_TMP:--}" >&2; fi; else CRON_READY=true; printf '%s\n' 'CRON_READY=true CronJob owner 없음 또는 standalone Job'; fi`

`CRON_READY=true`는 CronJob이 없다는 뜻일 수도 있다. CronJob이면 `concurrencyPolicy`, `suspend`, `lastScheduleTime`, `lastSuccessfulTime`, active Job 이름·UID를 확인한다. Job owner가 CronJob이 아니면 CronJob 명령을 실행하지 않으며, 빈 active 목록을 일정 누락이나 성공으로 해석하지 않는다.

`ATTEMPTS_READY=false; ATTEMPT_PODS=(); unset ATTEMPT_LIST ATTEMPT_COUNT; if [ "$JOB_READY" != true ]; then printf '%s\n' '중단: JOB_READY가 아니다.' >&2; elif PODS_JSON="$(kubectl get pods -n "$NS" -o json)" && ATTEMPT_COUNT_TMP="$(printf '%s' "$PODS_JSON" | jq -r --arg job "$JOB" --arg uid "$JOB_UID" '[.items[] | select(any(.metadata.ownerReferences[]?; .kind=="Job" and .name==$job and .uid==$uid and .controller==true))] | length')" && [[ "$ATTEMPT_COUNT_TMP" =~ ^[1-9][0-9]*$ ]] && ATTEMPT_LIST="$(printf '%s' "$PODS_JSON" | jq -r --arg job "$JOB" --arg uid "$JOB_UID" '.items[] | select(any(.metadata.ownerReferences[]?; .kind=="Job" and .name==$job and .uid==$uid and .controller==true)) | .metadata.name' | sort)"; then mapfile -t ATTEMPT_PODS < <(printf '%s\n' "$ATTEMPT_LIST"); ATTEMPT_COUNT="$ATTEMPT_COUNT_TMP"; printf '%s\n' "$PODS_JSON" | jq -r --arg job "$JOB" --arg uid "$JOB_UID" '.items[] | select(any(.metadata.ownerReferences[]?; .kind=="Job" and .name==$job and .uid==$uid and .controller==true)) | "=== 시도 Pod: \(.metadata.name) ===\nUID: \(.metadata.uid)\nNode: \(.spec.nodeName // "-")\nPhase: \(.status.phase // "-")\n시작 시각: \(.status.startTime // "-")\nContainer: \([.status.containerStatuses[]? | "\(.name) id=\(.containerID // "-") exit=\(.state.terminated.exitCode // "-") reason=\(.state.terminated.reason // "-")"] | join("; "))"'; ATTEMPTS_READY=true; else printf '중단: Job UID와 직접 연결된 시도 Pod가 없거나 후보 수 확인 실패 job=%s uid=%s\n' "$JOB" "$JOB_UID" >&2; fi`

`ATTEMPTS_READY=true`이고 각 시도 블록에 Pod UID·node·phase·container ID·exit/reason·시각이 있어야 로그를 읽는다. broad label 결과라도 owner UID가 Job UID와 맞지 않는 Pod는 시도로 사용하지 않는다. 후보가 없거나 API가 실패하면 정상 시도 0으로 해석하지 않고 controller·API 보존 경로로 이관한다.

`verify_attempt_job_owner() { ATTEMPT_LOG_JSON="$(kubectl get pod "$ATTEMPT_POD" -n "$NS" -o json)" && ATTEMPT_LOG_POD_UID="$(printf '%s' "$ATTEMPT_LOG_JSON" | jq -er '.metadata.uid')" && ATTEMPT_LOG_JOB_UID="$(printf '%s' "$ATTEMPT_LOG_JSON" | jq -er '([.metadata.ownerReferences[]? | select(.controller==true)][0].uid // empty)')" && [ "$ATTEMPT_LOG_JOB_UID" = "$JOB_UID" ] && printf '%s' "$ATTEMPT_LOG_JSON" | jq -e --arg job "$JOB" --arg uid "$JOB_UID" 'any(.metadata.ownerReferences[]?; .kind=="Job" and .name==$job and .uid==$uid and .controller==true)' >/dev/null; }`

`ATTEMPT_LOG_READY=false; if [ "$ATTEMPTS_READY" != true ] || [ "$TIME_READY" != true ]; then ATTEMPTS_READY=false; else ATTEMPT_LOG_READY=true; for ATTEMPT_POD in "${ATTEMPT_PODS[@]}"; do if ! verify_attempt_job_owner; then ATTEMPT_LOG_READY=false; ATTEMPTS_READY=false; printf '중단: 실패 시도 로그 직전 controller Job UID 재검증 실패 pod=%s expected_job_uid=%s\n' "$ATTEMPT_POD" "$JOB_UID" >&2; break; fi; done; fi`


`if [ "$ATTEMPTS_READY" != true ] || [ "$TIME_READY" != true ]; then printf '%s\n' '중단: ATTEMPTS_READY 또는 TIME_READY가 아니다.' >&2; else for ATTEMPT_POD in "${ATTEMPT_PODS[@]}"; do if ATTEMPT_JSON="$(kubectl get pod "$ATTEMPT_POD" -n "$NS" -o json)" && ATTEMPT_POD_UID="$(printf '%s' "$ATTEMPT_JSON" | jq -er '.metadata.uid')" && ATTEMPT_NODE="$(printf '%s' "$ATTEMPT_JSON" | jq -r '.spec.nodeName // "-"')" && ATTEMPT_CONTAINER_ID="$(printf '%s' "$ATTEMPT_JSON" | jq -r --arg container "$CONTAINER" '.status.containerStatuses[]? | select(.name==$container) | .containerID // "-"' )" && printf '%s' "$ATTEMPT_JSON" | jq -e --arg job "$JOB" --arg uid "$JOB_UID" 'any(.metadata.ownerReferences[]?; .kind=="Job" and .name==$job and .uid==$uid and .controller==true)' >/dev/null; then printf '로그 대상 확인 pod=%s uid=%s node=%s container=%s id=%s\n' "$ATTEMPT_POD" "$ATTEMPT_POD_UID" "$ATTEMPT_NODE" "$CONTAINER" "$ATTEMPT_CONTAINER_ID"; scoped_filter "attempt/$ATTEMPT_POD" 'start|complete|done|commit|ack|checksum|watermark|timeout|retry|error|failed|duplicate|already' kubectl logs "$ATTEMPT_POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=300; if [ "$FILTER_RESULT" = 'no-match' ]; then kubectl logs "$ATTEMPT_POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=50; fi; else printf '중단: 시도 Pod 재조회·owner UID 검증 실패 pod=%s\n' "$ATTEMPT_POD" >&2; break; fi; done; fi`

예상 예시가 `processed=100 commit=100 checksum=...`이면 산출물 checksum/watermark와 DB/API/queue 최종 상태를 대조한다. `timeout`, `commit unknown`, `ack failed`, `partial batch`가 보이면 외부 시스템의 실제 반영·중복 여부로 이동한다. 로그 stream 준비 성공은 container가 업무를 성공했다는 뜻이 아니며, 필터와 tail이 모두 비면 로그 보존·시간 범위·권한을 구분한다. Secret·token·개인정보가 보이면 출력·저장을 중단하고 오류 유형·시각만 기록한다.

### 2. 실패 시도와 side effect

진입 증거는 Job에 `Failed=True`, `BackoffLimitExceeded` 또는 `DeadlineExceeded`가 있거나 일부 시도는 실패하고 마지막 시도만 `exitCode=0`인 경우다. 최초 필요값과 출처는 1절에서 자동 등록한 Job UID·시도 Pod UID와 `CONTAINER`, `START_RFC3339`다. 1절의 `JOB_READY`·`ATTEMPTS_READY`가 없으면 먼저 그 절의 등록 gate를 통과한다.

`ATTEMPT_LOG_READY=false; if [ "$JOB_READY" != true ] || [ "$ATTEMPTS_READY" != true ] || [ "$TIME_READY" != true ]; then ATTEMPTS_READY=false; else ATTEMPT_LOG_READY=true; for ATTEMPT_POD in "${ATTEMPT_PODS[@]}"; do if ! verify_attempt_job_owner; then ATTEMPT_LOG_READY=false; ATTEMPTS_READY=false; printf '중단: 실패 시도 로그 직전 controller Job UID 재검증 실패 pod=%s expected_job_uid=%s\n' "$ATTEMPT_POD" "$JOB_UID" >&2; break; fi; done; fi`


`if [ "$JOB_READY" != true ] || [ "$ATTEMPTS_READY" != true ] || [ "$TIME_READY" != true ]; then printf '%s\n' '중단: Job·시도 UID·시간 gate를 먼저 통과한다.' >&2; elif kubectl get job "$JOB" -n "$NS" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,CONDITION:.status.conditions[*].type,REASON:.status.conditions[*].reason,ACTIVE:.status.active,SUCCEEDED:.status.succeeded,FAILED:.status.failed,BACKOFF:.spec.backoffLimit,DEADLINE:.spec.activeDeadlineSeconds'; then for ATTEMPT_POD in "${ATTEMPT_PODS[@]}"; do if ATTEMPT_JSON="$(kubectl get pod "$ATTEMPT_POD" -n "$NS" -o json)" && ATTEMPT_POD_UID="$(printf '%s' "$ATTEMPT_JSON" | jq -er '.metadata.uid')" && ATTEMPT_CONTAINER_ID="$(printf '%s' "$ATTEMPT_JSON" | jq -r --arg container "$CONTAINER" '.status.containerStatuses[]? | select(.name==$container) | .containerID // "-"' )" && verify_attempt_job_owner; then printf '실패 시도 로그 대상 pod=%s uid=%s container=%s id=%s\n' "$ATTEMPT_POD" "$ATTEMPT_POD_UID" "$CONTAINER" "$ATTEMPT_CONTAINER_ID"; scoped_filter "failed-attempt/$ATTEMPT_POD" 'commit|ack|timeout|retry|error|failed|duplicate|already|watermark|checkpoint|response code' kubectl logs "$ATTEMPT_POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=300; if [ "$FILTER_RESULT" = 'no-match' ]; then kubectl logs "$ATTEMPT_POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=50; fi; else printf '중단: 실패 시도 Pod 재조회·controller Job UID 검증 실패 pod=%s\n' "$ATTEMPT_POD" >&2; break; fi; done; else printf '%s\n' '중단: Job condition 조회 실패' >&2; fi`

non-zero exit은 한 시도의 실패 신호일 뿐 Job 최종 실패의 증거가 아니다. `restartPolicy=Never`의 시도는 서로 다른 Pod이므로 `--previous`를 사용하지 않는다. `restartPolicy=OnFailure`이고 동일 Pod의 대상 container `restartCount>0` 및 이전 종료 상태가 확인된 경우에만 현재 Pod UID의 previous 로그를 같은 시간 범위로 조회한다. 외부 DB transaction/unique key, API HTTP 응답·retry key·비동기 최종 상태, queue publish·ack/visibility·offset, 파일 rename·checksum을 각각 확인한다. `unknown`·timeout·부분 산출물은 성공으로 닫지 않고 업무 owner에게 이관한다.

### 3. sidecar와 주 컨테이너 결과 분리

진입 증거는 sidecar만 `exitCode=0`이거나 sidecar의 종료 시각이 주 컨테이너의 marker·commit·ack보다 앞선 경우다. `SIDE_CAR`는 자동 후보 출력과 Pod spec에서 확인한 sidecar 이름을 선택한다. 일반 sidecar는 Kubernetes 1.26에서 주 컨테이너 업무 완료 계약을 자동으로 만들지 않는다.

`SIDE_CAR='PASTE_SIDE_CAR_HERE'; SIDECAR_READY=false; unset SIDECAR_RESTARTS; if [ "$FIRST_CHECK_READY" != true ]; then printf '%s\n' '중단: FIRST_CHECK_READY가 아니다.' >&2; elif SIDE_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && printf '%s' "$SIDE_JSON" | jq -e --arg sidecar "$SIDE_CAR" 'any(.spec.containers[]?; .name==$sidecar)' >/dev/null && SIDECAR_RESTARTS_TMP="$(printf '%s' "$SIDE_JSON" | jq -r --arg sidecar "$SIDE_CAR" '[.status.containerStatuses[]? | select(.name==$sidecar)][0].restartCount // 0')"; then SIDECAR_RESTARTS="$SIDECAR_RESTARTS_TMP"; SIDECAR_READY=true; printf 'SIDECAR_READY=true pod=%s uid=%s sidecar=%s restart=%s\n' "$POD" "$POD_UID" "$SIDE_CAR" "$SIDECAR_RESTARTS"; else printf '중단: sidecar가 현재 Pod에 없거나 Pod 조회 실패 sidecar=%s\n' "$SIDE_CAR" >&2; fi`

`SIDECAR_READY=true`이면 다음 명령으로 주 컨테이너와 sidecar의 `startedAt`, `finishedAt`, current/last state, restart count를 UID와 함께 비교한다. `kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .status.containerStatuses[*]}container={.name} ready={.ready} currentReason={.state.terminated.reason} currentExit={.state.terminated.exitCode} lastReason={.lastState.terminated.reason} lastExit={.lastState.terminated.exitCode} started={.state.terminated.startedAt} finished={.state.terminated.finishedAt} restarts={.restartCount}{"\n"}{end}'`를 실행한다. 이 명령 성공은 status snapshot만 보장하고 flush·proxy drain·queue ack·실제 산출물을 보장하지 않는다.

sidecar 로그를 읽기 직전에 현재 Pod를 다시 읽어 최초 `POD_UID`와 일치하는지 확인한다. mismatch·NotFound·sidecar 부재이면 `SIDECAR_READY=false`로 만들고 로그·previous 로그를 실행하지 않는다.

`if [ "$SIDECAR_READY" = true ] && [ "$TIME_READY" = true ]; then if SIDECAR_CHECK_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && SIDECAR_CURRENT_UID="$(printf '%s' "$SIDECAR_CHECK_JSON" | jq -er '.metadata.uid')" && [ "$SIDECAR_CURRENT_UID" = "$POD_UID" ] && printf '%s' "$SIDECAR_CHECK_JSON" | jq -e --arg sidecar "$SIDE_CAR" 'any(.spec.containers[]?; .name==$sidecar)' >/dev/null; then :; else SIDECAR_READY=false; printf '중단: sidecar 로그 직전 Pod UID 또는 sidecar identity 재검증 실패 pod=%s expected_uid=%s\n' "$POD" "$POD_UID" >&2; fi; fi`

`if [ "$SIDECAR_READY" != true ] || [ "$TIME_READY" != true ]; then printf '%s\n' '중단: SIDECAR_READY 또는 TIME_READY가 아니다.' >&2; else scoped_filter "sidecar/$POD" 'flush|drain|proxy|telemetry|queue|ack|commit|timeout|error|failed|duplicate|already' kubectl logs "$POD" -n "$NS" -c "$SIDE_CAR" --timestamps --since-time="$START_RFC3339" --tail=300; if [ "$FILTER_RESULT" = 'no-match' ]; then kubectl logs "$POD" -n "$NS" -c "$SIDE_CAR" --timestamps --since-time="$START_RFC3339" --tail=50; fi; fi`

`SIDECAR_RESTARTS`가 0보다 크고 previous 인스턴스의 종료 순서·flush·ack가 필요할 때만 다음 명령을 실행한다. `if [ "$SIDECAR_READY" = true ] && [ "$SIDECAR_RESTARTS" -gt 0 ] && [ "$TIME_READY" = true ]; then scoped_filter "sidecar-previous/$POD" 'flush|drain|proxy|telemetry|queue|ack|commit|timeout|error|failed|duplicate|already' kubectl logs "$POD" -n "$NS" -c "$SIDE_CAR" --previous --timestamps --since-time="$START_RFC3339" --tail=200; else printf '%s\n' '중단: previous 로그 조건을 충족하지 않는다.'; fi`

previous 로그도 실행 직전에 같은 UID 재검증 gate를 통과해야 한다. 로그 producer가 실패한 경우에는 filter 무일치로 기록하지 않고 조회 실패와 rc를 기록한다.

`if [ "$SIDECAR_READY" = true ] && [ "$SIDECAR_RESTARTS" -gt 0 ] && [ "$TIME_READY" = true ]; then if SIDECAR_CHECK_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && SIDECAR_CURRENT_UID="$(printf '%s' "$SIDECAR_CHECK_JSON" | jq -er '.metadata.uid')" && [ "$SIDECAR_CURRENT_UID" = "$POD_UID" ] && printf '%s' "$SIDECAR_CHECK_JSON" | jq -e --arg sidecar "$SIDE_CAR" 'any(.spec.containers[]?; .name==$sidecar)' >/dev/null; then :; else SIDECAR_READY=false; printf '중단: previous 로그 직전 Pod UID 또는 sidecar identity 재검증 실패 pod=%s expected_uid=%s\n' "$POD" "$POD_UID" >&2; fi; fi`

필터·tail·previous가 모두 비면 로그 rotation/GC·보존 기간·권한을 구분하며 오류 부재로 해석하지 않는다. sidecar가 먼저 종료됐다는 사실은 주 컨테이너의 업무 성공을 보장하지 않는다. marker·commit·ack와 sidecar flush/drain 시각이 맞지 않으면 외부 결과 검증으로 이동한다.

### 4. 장기 실행 workload의 예상치 못한 exit 0

진입 증거는 owner가 Deployment·StatefulSet·DaemonSet 등 장기 서비스 계약인데 process가 `exitCode=0`으로 끝난 경우다. 실행 경로는 작업 host의 `kubectl` → API server → 대상 node의 kubelet/runtime → container log stream → application이다. node journal은 승인된 SSH 대상 host에서 systemd/kubelet/runtime를 조회한다. 한 hop의 성공은 다음 hop이나 application 정상의 증거가 아니다.

이 분기에서 처음 쓰는 값은 운영자가 owner chain·접속 기록과 대조해 선택한다. workload kind/name은 API owner와 일치해야 하고 `NODE_HOST`는 Kubernetes node 이름으로 자동 추정하지 않는다. runtime unit은 node에서 실제 확인한 이름만 입력한다.

`WORKLOAD_KIND='PASTE_WORKLOAD_KIND_HERE'; WORKLOAD_NAME='PASTE_WORKLOAD_NAME_HERE'; NODE_HOST='PASTE_NODE_HOST_HERE'; RUNTIME_SERVICE='PASTE_RUNTIME_SERVICE_HERE'; WORKLOAD_READY=false; if [ "$FIRST_CHECK_READY" != true ] || [ "$TIME_READY" != true ]; then printf '%s\n' '중단: 최초 확인·시간 gate를 통과한다.' >&2; elif [ "$OWNER_KIND" != Deployment ] && [ "$OWNER_KIND" != StatefulSet ] && [ "$OWNER_KIND" != DaemonSet ]; then printf '중단: 장기 실행 owner가 아님 owner=%s/%s\n' "$OWNER_KIND" "$OWNER_NAME" >&2; elif [ "$WORKLOAD_KIND" != "$OWNER_KIND" ] || [ "$WORKLOAD_NAME" != "$OWNER_NAME" ]; then printf '중단: workload 입력이 Pod owner와 일치하지 않음\n' >&2; elif kubectl get "$WORKLOAD_KIND" "$WORKLOAD_NAME" -n "$NS" -o custom-columns='NAME:.metadata.name,GENERATION:.metadata.generation,OBSERVED:.status.observedGeneration,REPLICAS:.status.replicas,READY:.status.readyReplicas,AVAILABLE:.status.availableReplicas,UPDATED:.status.updatedReplicas,DESIRED-SCHEDULED:.status.desiredNumberScheduled,NUMBER-READY:.status.numberReady,UPDATED-SCHEDULED:.status.updatedNumberScheduled'; then WORKLOAD_READY=true; printf 'WORKLOAD_READY=true kind=%s name=%s node=%s\n' "$WORKLOAD_KIND" "$WORKLOAD_NAME" "$NODE"; else printf '%s\n' '중단: workload status 조회 실패' >&2; fi`

### 5. 재실행 판단과 실제 결과

진입 증거는 Pod가 `Succeeded`, Job이 `Complete=True`인데 산출물이 누락됐거나 외부 결과가 `unknown`인 경우다. 먼저 외부 시스템을 읽기 전용으로 확인한다. 입력 watermark, idempotency key, transaction/commit, API retry key와 최종 상태, queue ack/offset, 부분 산출물, 원본 Job deadline/backoff, CronJob concurrencyPolicy와 업무 owner 승인을 모두 기록한다.

DB의 commit·unique key·부분 batch, API의 HTTP 응답·timeout·비동기 최종 상태, queue의 publish·ack·visibility timeout·offset, 파일의 임시 경로·최종 rename·checksum을 각각 확인한다. Pod·Job 상태나 마지막 exit 0만으로 외부 성공을 확정하지 않는다. `committed`, `acknowledged`, checksum 일치와 실제 최종 상태가 승인된 절차로 입증되면 재실행하지 않는다. timeout, 부분 산출물, watermark 불일치, 멱등성 불명확 또는 검증 절차 부재면 재실행하지 않고 업무 owner로 이관한다.

## 조건부 상태 변경

진단 단계에는 `delete`, `rollout`, Job 재실행을 섞지 않는다. CronJob 보완 실행은 외부 산출물 누락이 읽기 전용 조회로 확인되고, 입력 범위·멱등성·외부 side effect·동시 실행 정책·owner 승인·실제 결과 검증 절차가 모두 닫힌 경우에만 검토한다. 원본 Pod·Job UID를 재사용하지 않는다.

`APPROVAL_ID='PASTE_APPROVAL_ID_HERE'; NEW_JOB='PASTE_NEW_JOB_HERE'; APPROVAL_READY=false; if [ "$CRON_READY" != true ] || [ -z "${CRONJOB:-}" ] || [ "$TIME_READY" != true ]; then printf '%s\n' '중단: 확인된 CronJob과 시간 gate가 없다.' >&2; elif [ -z "$APPROVAL_ID" ] || [ -z "$NEW_JOB" ]; then printf '%s\n' '중단: 승인 ID와 새 Job 이름을 입력하지 않았다.' >&2; elif [ "$NEW_JOB" = "$JOB" ]; then printf '%s\n' '중단: 새 Job 이름이 원본과 같다.' >&2; else APPROVAL_READY=true; printf 'APPROVAL_READY=true approval=%s original_job=%s original_uid=%s new_job=%s\n' "$APPROVAL_ID" "$JOB" "$JOB_UID" "$NEW_JOB"; fi`

`APPROVAL_READY=true` 외에도 변경 기록에 namespace, 원본 Job/CronJob UID, 입력 범위, 권한 주체, 영향·중복 위험, 중단 조건, 보상 절차와 검증 시각을 남긴 경우에만 실행한다. 기대 효과는 누락 산출물 보완뿐이며 이미 실행된 DB/API write·queue ack·파일 write를 rollback하지 못한다. timeout·중복 징후·checksum 불일치가 다시 보이면 추가 실행을 중단한다.

`CRON_CREATE_READY=false; unset CRONJOB_CHECK_JSON CRONJOB_CHECK_UID; if [ "$APPROVAL_READY" != true ] || [ "$CRON_READY" != true ]; then printf '%s\n' '중단: 승인·확인된 CronJob gate가 아니다.' >&2; elif CRONJOB_CHECK_JSON="$(kubectl get cronjob "$CRONJOB" -n "$NS" -o json)" && CRONJOB_CHECK_UID="$(printf '%s' "$CRONJOB_CHECK_JSON" | jq -er '.metadata.uid')" && [ "$CRONJOB_CHECK_UID" = "$CRONJOB_UID" ]; then CRON_CREATE_READY=true; printf 'CRON_CREATE_READY=true cronjob=%s uid=%s new_job=%s approval=%s\n' "$CRONJOB" "$CRONJOB_CHECK_UID" "$NEW_JOB" "$APPROVAL_ID"; else printf '중단: 생성 직전 CronJob UID 재검증 실패 expected_uid=%s current_uid=%s\n' "$CRONJOB_UID" "${CRONJOB_CHECK_UID:--}" >&2; fi`

`CRON_CREATE_READY=true`는 owner에게 생성 요청을 이관할 수 있는 CronJob identity·승인 gate일 뿐이다. 이 런북은 Job 생성 CLI를 실행하지 않는다. 외부 side effect의 멱등성·중복 여부를 이 런북에서 검증할 수 없으므로 namespace, CronJob UID, 원본 Job UID, 입력 범위, 승인 ID, 새 Job 이름과 검증 절차를 업무 owner에게 이관한다. owner가 별도 절차로 생성한 뒤 새 Job UID·Pod owner·condition과 산출물 checksum/watermark·DB/API/queue 중복 여부를 확인한다. rollback은 자동 제공하지 않으며 외부 side effect 보상은 업무 owner의 별도 절차다.

장기 workload 교체는 이 문서의 `exit 0`만으로 실행하지 않는다. owner가 승인한 revision 절차로 이관하고 PDB, replica 여유, StatefulSet/quorum, graceful shutdown, 외부 side effect와 증거 보존을 확인한다. Ready 감소, error 증가, queue lag 악화 또는 quorum 위험이면 추가 변경을 중단한다.

## 정상화와 증거

정상화는 원인 경로를 역순으로 확인한다. Job·CronJob은 외부 기능·최종 상태 → 산출물 checksum/watermark·DB commit/API 최종 상태/queue ack → container stream의 성공 시도와 UID → Job condition·owner chain 순으로 본다. `Complete=True`와 `exitCode=0`만으로 정상화하지 않는다. sidecar는 flush/drain/proxy/telemetry/queue ack가 업무 marker·commit보다 먼저 끊기지 않았는지 포함한다.

장기 workload는 application의 실제 요청·핵심 기능과 원하는 Ready/Available 수가 관찰 창 동안 정상이고, 같은 exit 0·restart·Warning·probe 오류가 반복되지 않아야 한다. kubelet/runtime 오류가 원인이면 runtime 종료 경계와 node journal의 오류가 사라졌는지, replacement가 있다면 새 Pod UID·owner·Ready가 실제 서비스 지표와 함께 수렴했는지 확인한다. 완화 성공과 근본 원인 해소를 별도로 기록한다.

보존할 것은 관측 UTC 시각, namespace, Pod·container·owner·Job/CronJob UID, phase/restartPolicy, container ID와 termination 시각, UID로 제한한 Event의 시각·reason·message·Event UID, 시간 필터 로그/journal, 외부 검증값, 승인·명령·전후 revision이다. 전체 Pod YAML, Secret·token·개인키·개인정보는 저장하지 않는다.
