# Pod STATUS가 InvalidImageName·ErrImageNeverPull인 경우

## 입력값과 빠른 수집

Secret data, token, password, private key는 입력·출력·기록하지 않는다. 모든 값은 아래처럼 분류하고, API만으로 복수 후보를 확정할 수 없으면 운영자가 첫 번째를 임의 선택하지 않는다.

| 종류 | 값 | 출처와 사용 시점 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 승인된 namespace와 Pod 이름을 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `NODE`, `PHASE`, `OBSERVED_AT`, `OWNER_CANDIDATES`, `CONTAINER_CANDIDATES`, `IMAGE_REFERENCE`, `IMAGE_PULL_POLICY`, `WAITING_REASON`, `WAITING_MESSAGE`, `CONTAINER_ID`, `WORKLOAD_SELECTOR` | Pod·owner API에서 같은 identity로 등록한다. `WORKLOAD_SELECTOR`는 owner의 실제 selector를 canonical registration한다. |
| 계산 후보값 | `POD_UID_RE`, `IMAGE_REFERENCE_RE` | runtime journal용 regex로 escape해 만들고 bounded 출력으로 확인한다. |
| 운영자 선택값 | `CONTAINER_KIND`, `CONTAINER`, `OWNER_KIND`, `OWNER_NAME`, `NODE_HOST`, `RUNTIME_KIND`, `START_JOURNAL`, `END_JOURNAL`, `CRI_ENDPOINT`, `APPROVED_MANIFEST`, `APPROVED_REVISION`, `APPROVED_IMAGE_DIGEST`, `APPROVED_ROLLBACK_MANIFEST`, `ROLLBACK_REVISION`, `ROLLBACK_IMAGE_DIGEST`, `APPROVAL_ID`, `NEW_POD` | 관측 후보와 승인 원본을 확인한 뒤 해당 분기 직전에 한 번 입력한다. `NODE_HOST`는 Kubernetes Node와 별도로 승인된 SSH 주소다. forward와 rollback의 revision/digest를 별도로 승인한다. |

### 1. 실행 위치·도구·최초 입력

local 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash**에서 실행한다. `kubectl`은 실행 host → API server HTTPS 경로를 사용하고, runtime 확인은 실행 host → SSH → node → kubelet/runtime 경로를 사용한다. `kubectl get/describe/events` read 권한과 승인된 node SSH·sudo runtime 권한이 없으면 해당 분기에서 멈춘다. 터미널을 바꾸면 변수와 gate가 사라지므로 이 절부터 다시 실행한다. `sh`, PowerShell, CMD에서는 실행하지 않는다.

**Bash와 필수 local 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed ssh date head; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 local 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 다음 단계로 진행하지 않는다. `journalctl`, `systemctl`, `crictl` 등 node 도구는 node별 원격 도구 gate를 통과하기 전까지 있다고 가정하지 않는다.

**최초 입력과 이전 상태 초기화 — 같은 Bash에서 한 번 실행**

## 최초 확인

`SELECTION_READY=true`인 뒤에만 아래 명령을 실행한다. Event 조회는 같은 이름으로 재생성된 Pod가 섞이지 않게 UID를 제한해 문서 전체에서 한 번 실행한다.

**Pod 상태·describe — 아래 한 줄 전체를 복사**

`FIRST_READY=false; CURRENT_POD_JSON=''; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif CURRENT_POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && pod_uid_guard "$CURRENT_POD_JSON" "$POD_UID" && jq -r '"Pod=" + .metadata.name + " UID=" + .metadata.uid + " Node=" + (.spec.nodeName // "-") + " Phase=" + (.status.phase // "-")' <<<"$CURRENT_POD_JSON" && kubectl describe pod "$POD" -n "$NS"; then FIRST_READY=true; printf 'FIRST_READY=true pod=%s uid=%s observed=%s\n' "$POD" "$POD_UID" "$OBSERVED_AT"; else FIRST_READY=false; printf '%s\n' '중단: Pod 상태 조회 또는 UID 검증 실패.' >&2; fi`

`get`에서 `STATUS`, `READY`, `RESTARTS`, `NODE`, `AGE`와 UID를 본다. `describe`의 effective `Image`, `ImagePullPolicy`, waiting `Reason`, `Service Account`, 최초 local-image 또는 parser message를 자동 수집값과 대조한다. `Running`·`Ready`는 image reference 해석 또는 local image 존재를 보장하지 않는다.

**UID 제한 Event — 아래 한 줄 전체를 복사**

`EVENT_READY=false; if [ "$FIRST_READY" != true ]; then printf '%s\n' '중단: FIRST_READY가 아니다.' >&2; elif kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID" --sort-by=.metadata.creationTimestamp -o custom-columns='CREATED:.metadata.creationTimestamp,FIRST:.firstTimestamp,LAST:.lastTimestamp,EVENT:.eventTime,TYPE:.type,REASON:.reason,COUNT:.count,MESSAGE:.message'; then EVENT_READY=true; printf 'EVENT_READY=true uid=%s\n' "$POD_UID"; else printf '%s\n' '중단: Event 조회 실패. 빈 결과를 정상으로 해석하지 않는다.' >&2; fi`

Event의 최초 결정적 message와 채워진 시각을 보존한다. Event가 없으면 보존 기간, 권한, UID·namespace 범위 오류를 구분하고 reason만으로 원인을 확정하지 않는다.

|---|---|---|---|

표는 길 안내이며 image, policy, Pod 삭제·preload 변경을 승인하지 않는다. 한 hop의 성공은 다음 hop 또는 application 성공을 보장하지 않는다.

## 첫 분기: effective image와 policy

진입 증거: `$WAITING_REASON`, `$IMAGE_REFERENCE`, `$IMAGE_PULL_POLICY`가 같은 Pod UID에서 확인된 경우다.

`InvalidImageName`이면 parser와 owner 원본 경로로 간다. `ErrImageNeverPull`이고 policy가 `Never`이면 local image 경로로 간다. reason과 policy가 맞지 않으면 admission 변환·stale Pod·다른 container를 확인하고 변경하지 않는다.

**effective 값 bounded 확인 — 아래 한 줄 전체를 복사**

`if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; elif [ "$WAITING_REASON" = InvalidImageName ]; then printf '문법 경로 Pod UID=%s image=%s policy=%s reason=%s\n' "$POD_UID" "$IMAGE_REFERENCE" "$IMAGE_PULL_POLICY" "$WAITING_REASON"; elif [ "$WAITING_REASON" = ErrImageNeverPull ] && [ "$IMAGE_PULL_POLICY" = Never ]; then printf 'local image 경로 Pod UID=%s node=%s image=%s policy=%s reason=%s\n' "$POD_UID" "$NODE" "$IMAGE_REFERENCE" "$IMAGE_PULL_POLICY" "$WAITING_REASON"; else printf '중단: reason/policy 불일치 reason=%s policy=%s. 성공 gate는 두 reason을 같은 pull 장애로 묶지 않는 것이다. 실패하면 API·Pod identity와 owner 원본을 다시 대조하고 정책 변경 없이 담당 owner에게 이관한다.

## A. InvalidImageName 문법 경로

### A-1. reference 원문과 배포 원본 대조

진입 증거: `WAITING_REASON=InvalidImageName` 또는 `invalid reference format`가 같은 UID의 Event/message에 있다.

필수값: `$IMAGE_REFERENCE`, `$IMAGE_PULL_POLICY`, `$CONTAINER`, `$OWNER_KIND`, `$OWNER_NAME`는 API·선택값에서 왔다. registry host, Secret, node network, `crictl pull`은 이 절의 최초 필요값이 아니다.

연결 경로: 작업 PC → API server HTTPS → Pod spec/parser → owner template·승인 원본. parser 성공은 registry DNS, TLS, auth 또는 manifest 존재를 보장하지 않는다.

볼 문자열: 빈 image, 공백, 미치환 shell variable, 대문자 repository, 잘못된 registry 구분자, 빈 tag/digest, `@` 뒤 digest 형식 오류, 승인 원본과 다른 path를 대조한다. Pod에 적용된 문자열이 원본에서 어떻게 만들어졌는지만 확인한다.

**Deployment template 읽기 — Deployment owner일 때 아래 한 줄 전체를 복사**

`if [ "$OWNER_CHAIN_READY" != true ] || [ "$OWNER_CHAIN_KIND" != Deployment ]; then printf '%s\n' '중단: Deployment owner chain gate가 아니다. 실제 controller의 template과 승인 원본으로 이관한다.' >&2; elif kubectl get deployment "$OWNER_CHAIN_NAME" -n "$NS" -o jsonpath='{range .spec.template.spec.containers[?(@.name=="'$CONTAINER'")]}container={.name} image={.image} policy={.imagePullPolicy}{"\n"}{end}' && kubectl rollout history "deployment/$OWNER_CHAIN_NAME" -n "$NS"; then printf 'template gate: Deployment UID=%s, Pod UID=%s의 image=%s policy=%s와 revision·승인 원본을 대조한다.\n' "$OWNER_CHAIN_UID" "$POD_UID" "$IMAGE_REFERENCE" "$IMAGE_PULL_POLICY"; else printf '%s\n' '중단: owner template 또는 revision 조회 실패.' >&2; fi`

성공 gate는 Pod image/policy, template, 승인된 registry/path와 tag/digest가 일치하는 것이다. 빈 출력은 container·owner·권한·API 범위가 틀렸다는 뜻일 수 있고 정상으로 해석하지 않는다. parser 오류가 확인된 동안 registry login, imagePullSecrets, DNS·route·TLS·proxy, `crictl pull`을 실행하지 않는다. 원본 owner에게 교정과 영향 범위를 이관한다.

## B. ErrImageNeverPull local image 경로

### B-1. policy=Never 전제 확인

진입 증거: `$WAITING_REASON=ErrImageNeverPull`이고 `$IMAGE_PULL_POLICY=Never`가 같은 Pod UID에서 확인된 경우다.

필수값: `$NODE`, `$IMAGE_REFERENCE`, `$CONTAINER_ID`와 node 시간 범위가 필요하다. `Never`에서는 registry auth, DNS, TLS, proxy를 최초 원인으로 분류하지 않는다. policy가 `IfNotPresent` 또는 `Always`이면 [[07. Pod STATUS가 ImagePullBackOff·ErrImagePull인 경우]]로 이동한다.

`Never`는 registry에서 pull하지 않고 대상 node local image만 사용한다. exact repository·tag/digest와 대상 node가 일치하는지 확인하기 전 preload나 Pod 삭제를 실행하지 않는다.

### B-2. runtime 구현체와 image inventory

연결 경로: 작업 PC/Bash → API server HTTPS → SSH → node kubelet → 실제 CRI endpoint/socket → runtime image service. `containerRuntimeVersion` 또는 SSH 성공 하나만으로 image service·endpoint·local image 존재를 보장하지 않는다.

### B-3. node 범위와 local preload

진입 증거: 특정 node의 local inventory 차이 또는 여러 node의 preload 전제를 비교할 때다.

자동값: `$WORKLOAD_SELECTOR`는 owner API의 `matchLabels`·`matchExpressions`를 canonical selector로 등록한다. `matchExpressions`를 임의 평탄화하거나 Pod label에서 추측하지 않는다.

**workload selector 등록·Pod 범위 조회 — 아래 한 줄 전체를 복사**

성공 gate는 동일 workload가 어느 node에서 `ErrImageNeverPull`이고 exact image가 어느 범위에 존재하는지 UID·생성 시각과 함께 보이는 것이다. 특정 node만 실패하면 node inventory 차이, 여러 node가 실패하면 preload 배포 전제 또는 image reference drift를 workload owner와 확인한다. image가 없는 node에 임의 preload하거나 Pod를 delete하지 않는다.

## 관측별 종착점

- `InvalidImageName`: reference 문자열·원본 변수 치환을 owner가 승인된 registry/path와 tag/digest로 교정한다. registry auth/네트워크로 우회하지 않는다.
- `Never` + inventory empty: local preload가 승인된 방식인지, policy 변경이 허용되는지 결정한다. policy를 바꾸면 [[07. Pod STATUS가 ImagePullBackOff·ErrImagePull인 경우]]의 registry/auth pipeline을 새로 적용한다.
- `Never` + 다른 tag/digest: 배포 원본과 local inventory 중 승인된 기준을 확인하고 exact reference를 일치시킨다.
- `Never` + exact inventory 존재: CRI endpoint, runtime image service, 실제 node와 container reason을 재확인하고 kubelet/runtime owner로 이관한다.
- 여러 node에서 local image 부재: image preload 전략 또는 registry 기반 배포 전략을 workload owner와 재설계한다.

## 복구 전 안전 gate와 제한적 상태 변경

진단과 변경을 섞지 않는다. `kubectl set image`, `patch`, `edit`, Pod 직접 수정·삭제, `crictl pull`로 parser 오류나 `Never` 정책을 우회하지 않는다.

변경 trigger는 parser 오류 또는 exact local inventory 불일치의 직접 근거, 올바른 owner 원본, policy 결정, 실제 selector, 승인된 apply와 별도 rollback manifest, 대상 node 범위, 영향·rollback 계획, 권한자 승인이 모두 기록된 경우다. 기대 효과는 올바른 reference 해석 또는 `Never` 전제 충족이며 registry 가용성과 credential 정상화를 보장하지 않는다.

## 정상화 검증과 증거

문법 경로는 effective image가 승인 원본과 일치하고 waiting reason/Event가 사라지는지 역순으로 확인한다. local 경로는 runtime inventory의 exact reference·digest가 있고 kubelet이 그 local image로 container를 시작하는지 확인한다. 이후 같은 node와 다른 node 범위, 원하는 Ready replica, endpoint와 실제 요청 또는 핵심 기능, 관찰 창의 재발 여부를 확인한다.

## Prometheus 빠른 관측

메트릭이 실제 수집될 때만 사용한다. PromQL은 등록값으로 완성본을 생성하고 출력 한 줄만 UI에 붙여 넣는다. 빈 결과는 정상·0·오류 없음이 아니라 metric 미수집, label 불일치, 범위·권한·API 실패 후보다.

**waiting reason·image 정보 PromQL 생성 — 아래 한 줄 전체를 복사**

`PROMQL_READY=false; PROMQL_WAITING=''; PROMQL_INFO=''; if [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: SELECTION_READY가 아니다.' >&2; else PROMQL_WAITING="$(printf 'kube_pod_container_status_waiting_reason{namespace="%s",pod="%s",uid="%s",reason=~"InvalidImageName|ErrImageNeverPull"}==1' "$NS" "$POD" "$POD_UID")"; PROMQL_INFO="$(printf 'kube_pod_container_info{namespace="%s",pod="%s",uid="%s"}' "$NS" "$POD" "$POD_UID")"; if [ -n "$PROMQL_WAITING" ] && [ -n "$PROMQL_INFO" ]; then PROMQL_READY=true; printf 'WAITING: %s\nINFO: %s\n' "$PROMQL_WAITING" "$PROMQL_INFO" | head -c 800; printf '\n'; else printf '%s\n' '중단: PromQL 생성 결과가 비어 있다.' >&2; fi; fi`

`PROMQL_READY=true` 뒤 출력된 각 완성 한 줄만 Prometheus 또는 Grafana에 붙여 넣는다. `kube_pod_container_info`가 없을 수 있으므로 image·policy·UID는 Pod API와 Event로 대조한다. PromQL은 image parser 문법이나 local image inventory를 직접 증명하지 않는다.
