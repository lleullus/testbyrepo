# Pod STATUS가 Unknown·ContainerStatusUnknown인 경우

## 입력값과 빠른 수집

Pod phase `Unknown`은 API가 전체 상태를 현재 확정하지 못한 관측이고, `ContainerStatusUnknown`은 kubelet 또는 runtime이 특정 컨테이너 상태를 확정하지 못한 관측이다. 둘을 같은 장애로 단정하지 않고 API server·network → node heartbeat·Lease → kubelet → runtime → Linux host/VM 순으로 내린다. stale UID와 현재 서비스 영향을 별도로 판정한다.

| 분류 | 이 문서에서 쓰는 값 | 출처와 처리 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 승인된 namespace와 Pod 이름을 한 번 입력한다. |
| API 자동값 | `POD_UID`, `RESOURCE_VERSION`, `NODE`, `PHASE`, `REASON`, `OWNER_KIND`, `OWNER_NAME`, `OWNER_UID`, `POD_CREATED`, `DELETION`, `END_RFC3339`, container/status/ID 후보 | API snapshot과 UTC 시각에서 등록한다. UID·resourceVersion·phase를 확인하지 못하면 중단한다. |
| 계산 후보 | `NS_RE`, `POD_RE`, `UID_RE`, `PROMQL_READY`, `WATCH_RC` | PromQL selector와 bounded watch 결과용이다. regex는 escape하고 watch 종료 코드는 성공으로 임의 변환하지 않는다. |
| 운영자 선택값 | `CONTAINER`, `START_RFC3339`, `START_JOURNAL`, `END_JOURNAL`, `NODE_HOST` | 자동 후보·장애 시각·node 접근 기록을 확인한 뒤 선택한다. Kubernetes node 이름을 SSH host로 추정하지 않는다. |
| runtime 선택값 | `RUNTIME_SERVICE`, `CRI_ENDPOINT` | 실제 node unit과 kubelet 설정에서 확인한 뒤 입력한다. 기본 socket이나 runtime unit을 발명하지 않는다. |
| 변경 선택값 | `APPROVAL_ID` | API/node evidence, owner·PDB·quorum·외부 side effect를 확인한 뒤 승인 기록을 연결한다. |

### 1. 실행 host·도구·최초 입력

기본 명령은 승인된 context가 설정된 **작업 PC 또는 bastion의 같은 Bash 터미널**에서 실행한다. `kubectl`의 API 경로는 실행 host → kubectl client → API server이며, node 명령은 승인된 SSH host → systemd/kubelet/runtime → container/host로 이어진다. `127.0.0.1`이나 API 접근 성공은 대상 node·runtime·container 정상의 증거가 아니다. PowerShell, CMD, 새 Bash로 바꾸면 gate와 변수가 사라진다.

필수 도구는 `kubectl`, `jq`, `grep`, `sed`, `date`, `timeout`이다. 확인 실패 시 초기화·API 수집을 포함한 다음 단계로 진행하지 않는다. SSH·sudo·journalctl·systemctl·crictl은 해당 node 분기의 별도 권한 gate에서 확인한다.

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash 터미널에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date timeout; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 도구·권한을 먼저 복구한다. raw Pod JSON, Secret·token·개인키·개인정보가 포함될 수 있는 원문은 저장하거나 출력하지 않는다.

### 2. 이전 상태 초기화와 대상 입력

재실행할 때 이전 Pod UID, container ID, runtime endpoint, watch·host gate를 모두 무효화한다. 같은 이름의 replacement가 생겼을 수 있으므로 이름으로 이전 관측을 재사용하지 않는다.

### 4. 운영자 선택값과 시간 gate

검색 문자열: `Unknown`, `phase=Unknown`, `ContainerStatusUnknown`, `NodeNotReady`, `Lease`, `kubelet stopped posting`, `PLEG`, `runtime`, `stale UID`, `resourceVersion`, `connection refused`, `timeout`, `failed to update status`.

`Unknown`만으로 node 장애, VM 손실, container 사망을 확정하지 않는다. `Running`, `Ready`, 최신 Lease, `HTTP 200` 또는 API read 성공도 다음 kubelet/runtime/host hop과 실제 서비스 기능을 보장하지 않는다.

### 1. Pod phase=Unknown: API 관측부터 확인

진입 증거는 phase가 Unknown이거나 API read/watch가 함께 불안정한 경우다. 필수값은 자동 등록한 `NS`, `POD`, `POD_UID`, `RESOURCE_VERSION`이며 API snapshot에서 출처를 남긴다. 실행 경로는 작업 host → kubectl → API server이며, 이 경로의 성공은 node heartbeat나 container 상태를 보장하지 않는다.

`API_READY=false; WATCH_RC=0; if [ "$FIRST_CHECK_READY" != true ]; then printf '%s\n' '중단: FIRST_CHECK_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,RESOURCE-VERSION:.metadata.resourceVersion,PHASE:.status.phase,NODE:.spec.nodeName' && kubectl get pods -n "$NS" -o wide && kubectl get --raw='/readyz?verbose'; then timeout 35s kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,RESOURCE-VERSION:.metadata.resourceVersion,PHASE:.status.phase,NODE:.spec.nodeName' --watch-only --request-timeout=30s || WATCH_RC=$?; API_READY=true; printf 'API_READY=true watch_rc=%s pod=%s uid=%s\n' "$WATCH_RC" "$POD" "$POD_UID"; else printf '%s\n' '중단: 대상 Pod·namespace 또는 readyz API 조회 실패' >&2; fi`

`API_READY=true`는 대상 API read와 namespace 범위 read, readyz 요청이 성공한 범위만 보장한다. `WATCH_RC=124`는 bounded watch가 시간 제한으로 끝난 것이므로 최초 snapshot이 있었다면 watch 지속 실패 후보로 기록하고 API 전체 장애로 단정하지 않는다. namespace 조회·readyz가 실패하면 node 장애로 내리지 말고 API server·auth·network 담당으로 이관한다. API가 현재 UID를 읽지 못하거나 `NotFound`이면 stale UID 절로 이동한다.

### 2. phase=Unknown: Node Ready와 Lease

진입 증거는 API는 응답하지만 Pod 상태가 오래됐거나 node condition/Lease가 오래된 경우다. 필수값은 자동값 `NODE`, `POD_UID`, `END_RFC3339`다. `NODE`가 `-`면 node 명령을 실행하지 않고 API/owner path로 이관한다.

`NODE_READY_CHECK=false; if [ "$API_READY" != true ] || [ -z "$NODE" ] || [ "$NODE" = "-" ]; then printf '%s\n' '중단: API_READY 또는 NODE gate가 아니다.' >&2; elif kubectl get node "$NODE" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,READY:.status.conditions[?(@.type=="Ready")].status,REASON:.status.conditions[?(@.type=="Ready")].reason,LAST-HEARTBEAT:.status.conditions[?(@.type=="Ready")].lastHeartbeatTime,LAST-TRANSITION:.status.conditions[?(@.type=="Ready")].lastTransitionTime,TAINTS:.spec.taints[*].effect' && kubectl get lease "$NODE" -n kube-node-lease -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,RENEW-TIME:.spec.renewTime,HOLDER:.spec.holderIdentity,RESOURCE-VERSION:.metadata.resourceVersion,LEASE-DURATION:.spec.leaseDurationSeconds' && kubectl describe node "$NODE"; then NODE_READY_CHECK=true; printf 'NODE_READY_CHECK=true node=%s observed=%s\n' "$NODE" "$END_RFC3339"; else printf '중단: Node 또는 Lease API 조회 실패 node=%s\n' "$NODE" >&2; fi`

볼 것은 Ready status/reason/message, last heartbeat/transition, pressure·taint, Lease `renewTime`·holder·resourceVersion다. Ready와 Lease가 최신이면 API가 heartbeat를 최근 봤다는 뜻이지 process·host liveness 증명이 아니며 kubelet/runtime 또는 특정 Pod로 내린다. Ready `Unknown/False`와 오래된 Lease가 함께 있으면 kubelet↔API 단절 후보지만 Linux/VM 증거 전에는 node 장애로 확정하지 않는다. Lease가 최신인데 한 Pod만 stale이면 전체 heartbeat partition보다 Pod worker·runtime을 먼저 본다.

### 3. kubelet 경로

진입 증거는 Node가 stale이거나 API는 정상인데 Pod 상태 report가 멈춘 경우다. 실행 경로는 작업 host → SSH host `NODE_HOST` → systemd/kubelet → API server 또는 Pod worker다. `NODE_HOST`는 자동값 `NODE`와 별개이며 승인된 접속 mapping 없이는 사용하지 않는다.

`NODE_TOOLS_READY=false; if [ "$NODE_HOST_READY" != true ] || [ "$NODE_IDENTITY_READY" != true ]; then printf '%s\n' '중단: NODE_HOST_READY·NODE_IDENTITY_READY가 아니다.' >&2; elif [ "$NODE_READY_CHECK" != true ] && [ "$API_READY" != true ]; then printf '%s\n' '중단: API 또는 Node gate가 없다.' >&2; elif command -v ssh >/dev/null 2>&1 && ssh -- "$NODE_HOST" 'command -v journalctl >/dev/null 2>&1 && sudo -n command -v journalctl >/dev/null 2>&1 && sudo -n command -v systemctl >/dev/null 2>&1'; then NODE_TOOLS_READY=true; printf 'NODE_TOOLS_READY=true host=%s node=%s\n' "$NODE_HOST" "$NODE"; else printf '중단: SSH·sudo·journalctl·systemctl 또는 NODE_HOST 확인 실패 host=%s\n' "$NODE_HOST" >&2; fi`

`if [ "$NODE_TOOLS_READY" != true ] || [ "$TIME_READY" != true ] || [ "$NODE_HOST_READY" != true ] || [ "$NODE_IDENTITY_READY" != true ]; then printf '%s\n' '중단: NODE_TOOLS_READY·NODE_HOST_READY·NODE_IDENTITY_READY 또는 TIME_READY가 아니다.' >&2; else scoped_filter "kubelet/$POD" "$POD_UID|$POD|failed to update status|timeout|tls|auth|PLEG|cgroup|runtime" ssh -- "$NODE_HOST" "sudo -n systemctl is-active kubelet; sudo -n journalctl -u kubelet --since $START_JOURNAL_Q --until $END_JOURNAL_Q --no-pager"; if [ "$FILTER_RESULT" = 'no-match' ]; then ssh -- "$NODE_HOST" "sudo -n journalctl -u kubelet --since $START_JOURNAL_Q --until $END_JOURNAL_Q --no-pager | tail -n 50"; fi; fi` `failed to update status ... context deadline exceeded`는 kubelet status report/API network 경로, `PLEG is not healthy`는 Pod worker/runtime 경로로 이동한다. producer가 성공하고 필터가 비면 같은 시간 범위의 비식별화된 마지막 50행만 확인한다. 빈 journal은 kubelet 정상의 증거가 아니다.

`systemctl is-active kubelet`가 inactive여도 해당 명령 자체가 API·host 장애를 확정하지는 않는다. SSH 실패는 kubelet 중단으로 단정하지 말고 host/network/VM 담당으로 이관한다. 확인할 것은 Pod UID·node·journal 시각과 PLEG/API timeout이며, kubelet restart/reboot는 이 문서의 자동 복구가 아니다.

### 4. ContainerStatusUnknown: container runtime 경로

진입 증거는 Pod phase와 별개로 선택한 container가 `ContainerStatusUnknown`이거나 current/last state와 container ID가 일치하지 않는 경우다. 실행 경로는 작업 host → API server → node kubelet/runtime → CRI endpoint/socket → container ID다. 선언된 `containerRuntimeVersion`은 runtime 정체성 후보일 뿐 unit·socket·CRI endpoint·container 생존을 보장하지 않는다.

`RUNTIME_SERVICE='PASTE_RUNTIME_SERVICE_HERE'; CRI_ENDPOINT='PASTE_CRI_ENDPOINT_HERE'; CONTAINER_ID_RAW=''; RUNTIME_READY=false; if [ "$NODE_HOST_READY" != true ] || [ "$NODE_IDENTITY_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$NODE" = "-" ] || [ "$CONTAINER_ID" = "-" ] || [ -z "$CONTAINER_ID" ]; then printf '%s\n' '중단: NODE_HOST·NODE_IDENTITY·container 선택·node·container ID gate가 없다.' >&2; elif [ "$CONTAINER_ID" != "-" ]; then CONTAINER_ID_RAW="${CONTAINER_ID#*://}"; if [ -n "$CONTAINER_ID_RAW" ]; then RUNTIME_READY=false; if command -v ssh >/dev/null 2>&1 && ssh -- "$NODE_HOST" 'command -v journalctl >/dev/null 2>&1 && sudo -n command -v journalctl >/dev/null 2>&1 && sudo -n command -v systemctl >/dev/null 2>&1'; then NODE_TOOLS_READY=true; printf 'NODE_TOOLS_READY=true host=%s\n' "$NODE_HOST"; else printf '중단: runtime node 도구·권한·host 확인 실패 host=%s\n' "$NODE_HOST" >&2; fi; else printf '%s\n' '중단: scheme을 제거한 container ID가 비어 있다.' >&2; fi; fi`

`NODE_TOOLS_READY=true`일 때 확인된 node 범위의 다른 Pod와 runtime 정체성을 조회한다. `kubectl get pods -A --field-selector "spec.nodeName=$NODE" -o custom-columns='NAMESPACE:.metadata.namespace,POD:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,NODE:.spec.nodeName'`와 `kubectl get node "$NODE" -o jsonpath='{.status.nodeInfo.containerRuntimeVersion}{"\n"}'`을 실행한다. 첫 명령의 다른 Unknown 후보 수로 단일 container와 node 범위를 분리한다. 빈 목록은 node에 Pod가 없다는 뜻일 수도 있고 selector/API 권한 문제일 수도 있으므로 정상으로 해석하지 않는다.

`ssh -- "$NODE_HOST" 'sudo -n systemctl list-units --type=service --state=running --no-legend | grep -E -i "containerd|crio|cri-o|docker|runtime"'`와 `ssh -- "$NODE_HOST" 'sudo -n systemctl show kubelet --property=ExecStart --value | grep -Eo -- "--container-runtime-endpoint(=| )[^ ]+|--config(=| )[^ ]+"'`를 실행한다. active `ExecStart`에 `--container-runtime-endpoint`가 없으면 그 `ExecStart`에서 확인한 절대 `--config` 경로의 유일한 `containerRuntimeEndpoint` key를 읽어 fallback으로 삼는다. config 경로가 절대경로·regular file이 아니거나 key가 0개·여러 개이거나 값이 비면 endpoint를 확정하지 않는다. `containerRuntimeVersion`·실제 running unit·kubelet endpoint가 같은 runtime 경계를 가리킬 때만 입력한 `RUNTIME_SERVICE`·`CRI_ENDPOINT`를 사용한다.

### 5. Linux host·network·VM 경로

진입 증거는 kubelet/runtime 오류, Ready·Lease 지연, SSH reachability 또는 host pressure 증거가 있는 경우다. 실행 경로는 작업 host → 승인된 `NODE_HOST` → Linux network/kernel/systemd → VM/hypervisor와 API endpoint다. host 명령 성공은 API server·VM·애플리케이션 정상의 증거가 아니다.

`HOST_READY=false; if [ "$NODE_TOOLS_READY" != true ] || [ "$NODE_HOST_READY" != true ] || [ "$NODE_IDENTITY_READY" != true ]; then printf '%s\n' '중단: NODE_TOOLS_READY·NODE_HOST_READY·NODE_IDENTITY_READY가 아니다.' >&2; elif ssh -- "$NODE_HOST" 'sudo -n command -v ip >/dev/null 2>&1 && sudo -n command -v ss >/dev/null 2>&1 && sudo -n command -v journalctl >/dev/null 2>&1'; then HOST_READY=true; printf 'HOST_READY=true host=%s node=%s\n' "$NODE_HOST" "$NODE"; else printf '%s\n' '중단: host 도구·sudo·SSH gate가 아니다.' >&2; fi`

`if [ "$HOST_READY" != true ] || [ "$TIME_READY" != true ] || [ "$NODE_HOST_READY" != true ] || [ "$NODE_IDENTITY_READY" != true ]; then printf '%s\n' '중단: HOST_READY·NODE_HOST_READY·NODE_IDENTITY 또는 TIME_READY가 아니다.' >&2; else scoped_filter "host/$NODE_HOST" 'oom|out of memory|i/o|filesystem|read-only|nic|link|reset|panic|conntrack|socket' ssh -- "$NODE_HOST" "sudo -n ip addr show; sudo -n ip route show; sudo -n ss -tanp; sudo -n journalctl -k --since $START_JOURNAL_Q --until $END_JOURNAL_Q --no-pager"; fi`

볼 것은 API server endpoint로 가는 route·NIC/link, conntrack·socket 고갈, filesystem read-only/full, kernel OOM, clock drift다. `Out of memory: Killed process`는 Linux pressure, `I/O error`·`link is not ready`는 storage/NIC 경로로 이동한다. 필터가 비면 host 정상의 증거가 아니므로 VM/network 담당에게 같은 시간 범위의 플랫폼 이벤트를 요청한다. process argument·token이 섞일 수 있는 `ss` 출력은 저장 전 마스킹한다. VM stop/reboot, node fencing, network rule 변경은 자동 복구가 아니다.

## stale UID와 현재 서비스 영향

stale 판정은 이름이 아니라 UID·resourceVersion·실제 시각으로 한다. `resourceVersion`의 크기는 timestamp나 단조 증가하는 원인 순서가 아니다. `creationTimestamp`, `deletionTimestamp`, condition·container 시각, Event의 실제 `eventTime`·`series.lastObservedTime`·legacy timestamp와 replacement 생성 시각을 함께 비교한다.

`kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,RESOURCE-VERSION:.metadata.resourceVersion,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,NODE:.spec.nodeName,OWNER-KIND:.metadata.ownerReferences[?(@.controller==true)].kind,OWNER:.metadata.ownerReferences[?(@.controller==true)].name,OWNER-UID:.metadata.ownerReferences[?(@.controller==true)].uid,CREATED:.metadata.creationTimestamp,DELETED:.metadata.deletionTimestamp'`

현재 UID가 최초 `POD_UID`와 다르면 이전 Unknown 관측을 현재 상태로 재사용하지 않는다. 현재 UID가 없거나 새 UID가 Ready여도 당시 서비스 오류·queue lag·처리 중단·중복 실행을 별도로 확인한다. Job/CronJob owner는 Unknown Pod를 재실행 근거로 삼지 않고 active/succeeded/failed, 입력 key와 산출물을 확인한 뒤 업무 owner가 결정한다. Deployment·StatefulSet·DaemonSet은 desired/Ready, Endpoint/실제 요청, PDB·quorum을 확인한다.

## 정상화와 증거

정상화는 객체 상태 하나가 좋아진 것으로 닫지 않는다. API snapshot·UID/resourceVersion → Node Ready·Lease → kubelet status/report → runtime inspect·CRI → host/network/VM → replacement process/listener → 실제 요청·queue lag·Job 산출물 순으로 역검증한다. 대상 UID가 현재 관측과 같고, 원하는 Ready 수와 실제 기능이 관찰 창 동안 정상이며, 같은 Unknown·ContainerStatusUnknown·Warning이 반복되지 않아야 한다.

Job/CronJob은 산출물·DB/API/queue 중복 여부까지 확인한다. replacement가 생성됐거나 `Running`·`Ready`가 됐다는 사실만으로 old process 종료·volume 정리·서비스 정상화를 선언하지 않는다. 완화 성공과 근본 원인 해소를 분리해 기록한다.

보존할 것은 관측 UTC 시각, namespace, Pod UID/resourceVersion, phase·container ID·reason, node UID/condition·Lease renewTime, UID 제한 Event/watch/readyz, kubelet/runtime/host/VM의 시간 범위 증거, 승인·전후 UID와 서비스 지표다. 전체 Pod YAML, Secret·token·개인키·개인정보는 저장하지 않는다.

## PromQL 생성

`PROMQL_READY=false; unset NS_RE POD_RE UID_RE; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif NS_RE="$(printf '%s' "$NS" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" && POD_RE="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" && UID_RE="$(printf '%s' "$POD_UID" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" && [ -n "$NS_RE" ] && [ -n "$POD_RE" ] && [ -n "$UID_RE" ]; then PROMQL_READY=true; printf 'PROMQL_READY=true namespace=%.120s pod=%.120s uid=%.120s\n' "$NS_RE" "$POD_RE" "$UID_RE"; else printf '%s\n' '중단: PromQL selector 생성 실패' >&2; fi`

`PROMQL_READY=true`일 때만 `printf 'sum by(namespace,pod,uid)(kube_pod_status_phase{namespace=~"%s",pod=~"%s",uid=~"%s",phase="Unknown"}) or (count by(namespace,pod,uid)(kube_pod_deletion_timestamp{namespace=~"%s",pod=~"%s",uid=~"%s"}) * sum by(namespace,pod,uid)(kube_pod_status_reason{namespace=~"%s",pod=~"%s",uid=~"%s",reason="NodeLost"}))\n' "$NS_RE" "$POD_RE" "$UID_RE" "$NS_RE" "$POD_RE" "$UID_RE" "$NS_RE" "$POD_RE" "$UID_RE"`을 실행해 완성된 한 줄을 외부 UI에 넣는다. `printf 'kube_pod_info{namespace=~"%s",pod=~"%s",uid=~"%s"}\n' "$NS_RE" "$POD_RE" "$UID_RE"`와 `printf 'time()-timestamp(kube_pod_info{namespace=~"%s",pod=~"%s",uid=~"%s"})\n' "$NS_RE" "$POD_RE" "$UID_RE"`도 생성 명령의 출력만 사용한다. Prometheus transport·HTTP status·query API success/data를 분리한다. 빈 series는 정상·0이 아니라 metric 미수집·라벨 불일치·scrape lag·범위 문제이며, PromQL 조회 실패와 metric 부재를 구분한다. 반환 UID·node·sample 시각은 현재 API·Event·Lease와 대조한다.
