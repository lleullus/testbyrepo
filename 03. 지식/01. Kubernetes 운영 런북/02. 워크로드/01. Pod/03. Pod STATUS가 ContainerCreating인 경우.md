# Pod STATUS가 ContainerCreating인 경우

## 입력값과 빠른 수집

모든 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. `kubectl`은 실행 host → client/API server → 대상 node의 kubelet/runtime → container/application으로 이어진다. logs stream, kubelet journal, CSI/CNI log는 각각 다른 hop과 권한을 확인하며, 한 hop 성공은 다음 hop·listener·application 정상의 증거가 아니다.

| 종류 | 값 | 출처와 사용 범위 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 승인된 namespace와 정확한 Pod 이름을 한 번 입력한다. |
| API 자동값 | `POD_UID`, `NODE`, `PHASE`, `CREATED_AT`, `OWNER_KIND`, `OWNER_NAME`, `OWNER_UID`, `SERVICE_ACCOUNT`, `POD_JSON`, `POD_RE`, `EVENT_SELECTOR` | 현재 Pod API에서 UID·node·phase·시각·owner·container/init·port·PVC 관계를 등록한다. controller owner kind/name/UID를 함께 등록한다. |
| 계산 후보 | `PVC_RE` | API에서 확인된 이름을 escape한 후보이며 실제 selector가 맞는지 확인하기 전에는 확정하지 않는다. |
| 운영자 선택값 | `INIT_CONTAINER`, `CONTAINER`, `START_RFC3339`, `START_JOURNAL`, `END_JOURNAL`, `RUNTIME_SERVICE`, `NODE_HOST`, `PVC`, `PV`, `MOUNT_PATH`, `CNI_NAMESPACE`, `CNI_POD`, `CNI_CONTAINER`, `CONFIGMAP`, `SECRET`, `DEPLOYMENT`, `ROLLBACK_REVISION`, `WORKLOAD_SELECTOR`, `APPROVAL_ID`, `DATA_QUORUM_CONFIRM`, `SERVICE` | 해당 상세 분기의 후보 출력·실제 구현·승인 후 선택한다. `NODE_HOST`는 API의 `NODE`에서 자동 추론하지 않고 승인된 SSH 대상 host를 직접 선택한다. 복수 후보를 임의로 첫 번째 선택하지 않는다. CSI plugin Pod/container는 generic API로 driver 귀속을 확정할 수 없어 선택하지 않는다. |

**Bash와 필수 도구 확인**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 이 문서의 명령은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true shell=%s\n' "$BASH_VERSION"; else printf '중단: 없는 필수 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`AUTO_READY=true`이고 현재 UID·node·phase·생성 시각·container/init 상태·port/PVC 관계가 출력되어야 다음으로 간다. `containerPort`는 선언 후보일 뿐 실제 process listener·protocol·TLS·Service 연결을 보장하지 않는다. API 실패·빈 후보·복수 후보는 정상으로 해석하지 않는다.

**owner identity·UID 재조회·pipeline 상태 helper**

## 최초 확인

`kubectl get pod "$POD" -n "$NS" -o wide`

성공 gate는 자동 수집 UID·node·phase와 `STATUS`, `READY`, `RESTARTS`, `NODE`, `AGE`가 일치하는 것이다. 빈 출력은 container 생성 성공·오류 없음이 아니다.

`kubectl describe pod "$POD" -n "$NS"`

`State`, `Last State`, `Reason`, `Conditions`, volume과 마지막 Event의 첫 실패 message·시각을 본다. `describe` 성공은 image pull·volume mount·sandbox·application listener 정상의 증거가 아니다.

`kubectl get pod "$POD" -n "$NS" -o jsonpath='{.status.phase}{" nodeName="}{.spec.nodeName}{"\n"}{range .status.initContainerStatuses[*]}init/{.name}{" waiting="}{.state.waiting.reason}{" running="}{.state.running.startedAt}{" terminated="}{.state.terminated.reason}{" exit="}{.state.terminated.exitCode}{" last="}{.lastState.terminated.reason}{" restart="}{.restartCount}{"\n"}{end}{range .status.containerStatuses[*]}container/{.name}{" waiting="}{.state.waiting.reason}{" running="}{.state.running.startedAt}{" terminated="}{.state.terminated.reason}{" exit="}{.state.terminated.exitCode}{" last="}{.lastState.terminated.reason}{" restart="}{.restartCount}{"\n"}{end}'`

현재 waiting reason, 실행 시각, 종료 reason·exit, restart를 확인한다. status field가 비면 field 부재·권한·API 오류를 구분하지 못한 것이므로 Event와 `describe`를 보존한다.

`if ! refresh_pod; then printf '%s\n' '중단: Event 조회 직전 Pod UID 재조회 실패' >&2; else kubectl get events -n "$NS" --field-selector "$EVENT_SELECTOR" --sort-by=.metadata.creationTimestamp -o custom-columns='EVENT-UID:.metadata.uid,CREATED:.metadata.creationTimestamp,FIRST-SEEN:.firstTimestamp,LAST-SEEN:.lastTimestamp,EVENT-TIME:.eventTime,SERIES-LAST:.series.lastObservedTime,TYPE:.type,REASON:.reason,COUNT:.count,MESSAGE:.message'; fi`

UID 제한 Event를 한 번만 조회한다. Event가 비면 TTL 만료·selector 불일치·권한·API 실패를 구분하며 오류 없음으로 해석하지 않는다. `FIRST-SEEN`, `LAST-SEEN`, `EVENT-TIME`, `SERIES-LAST` 중 채워진 시각을 Pod 생성 시각·logs와 대조한다. token·인증서·개인정보가 보이면 저장하지 않는다.

**container log 공통 선택값**

image·node log·CNI log 절은 이 선택 block을 먼저 실행하고 `SELECTION_READY=true`를 확인한다. CSI plugin Pod/container 로그는 authoritative driver 귀속 API가 없어 직접 실행하지 않고 CSI owner handoff로 이관한다. init log는 별도의 init 이름을 선택하되 같은 UTC 시작 시각을 재사용한다. `containerPort` 선언은 실제 listener·protocol·TLS·application readiness를 보장하지 않는다.

### 1. init 미완료

진입 증거는 첫 미완료 init이 `Waiting`·`PodInitializing`이거나 `Terminated` 후 restart·non-zero reason이 있는 경우다. 연결 경로는 `실행 host → API server → kubelet/runtime → init container stream → ConfigMap·Secret·PVC·DNS·DB/API`다. init 성공 전 일반 container의 `Running`·`Ready`는 application 정상의 증거가 아니다.

`INIT_CONTAINER='PASTE_INIT_CONTAINER_HERE'; INIT_READY=false; if [ "$SELECTION_READY" != true ] || ! refresh_pod || [ -z "$INIT_CONTAINER" ]; then printf '%s\n' '중단: SELECTION_READY·Pod UID 재조회와 현재 Pod의 init 후보가 필요하다.' >&2; elif jq -e --arg c "$INIT_CONTAINER" 'any(.spec.initContainers[]?; .name==$c)' <<<"$POD_JSON" >/dev/null; then INIT_READY=true; export INIT_CONTAINER; printf 'INIT_READY=true init=%s uid=%s start=%s\n' "$INIT_CONTAINER" "$POD_UID" "$START_RFC3339"; else printf '중단: 선택한 init container가 현재 Pod에 없음 %s\n' "$INIT_CONTAINER" >&2; fi`

`INIT_READY=true`이고 init이 실제 `running|terminated` 또는 실행 이력이 있을 때만 `if ! refresh_pod || [ "$INIT_READY" != true ]; then printf '%s\n' '중단: init log 직전 Pod UID 재조회 또는 INIT_READY 확인 실패' >&2; else filter_stream 'panic|fatal|error|exception|timeout|refused|denied|permission|not found|migration|lock|oom|killed' kubectl logs "$POD" -n "$NS" -c "$INIT_CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=200; fi`를 실행한다. init이 Waiting이면 logs·exec를 강행하지 않고 [[04. Pod STATUS가 PodInitializing인 경우]] 또는 [[05. Pod가 Init 단계에서 진행되지 않는 경우]]로 이관한다.

필터가 비면 같은 시간 범위의 마지막 50행을 `if ! refresh_pod || [ "$INIT_READY" != true ]; then printf '%s\n' '중단: 제한 tail 직전 Pod UID 재조회 또는 INIT_READY 확인 실패' >&2; else kubectl logs "$POD" -n "$NS" -c "$INIT_CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=50; fi`로 확인하되 오류 부재로 닫지 않는다. `connection refused`는 DNS·Service·DB/API 후보, permission/not found는 mount·projection·security 후보, `OOMKilled`는 Error 런북의 resource/node 경로다.

### 2. image 준비

진입 증거는 `Failed to pull image`, `ErrImagePull`, `ImagePullBackOff`, `pull access denied`, `manifest unknown`, `no such host`, `x509`, `429`, `unauthorized`다. 연결 경로는 `실행 host → API server → node kubelet → CRI runtime → node DNS·route·proxy·TLS → registry`다. `ServiceAccount` 조회 성공은 image pull credential 유효성·unpack·container start를 보장하지 않는다.

`kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .spec.containers[*]}{.name}{" image="}{.image}{" pullPolicy="}{.imagePullPolicy}{"\n"}{end}{range .spec.initContainers[*]}init/{.name}{" image="}{.image}{" pullPolicy="}{.imagePullPolicy}{"\n"}{end}{"serviceAccount="}{.spec.serviceAccountName}{"\n"}{range .spec.imagePullSecrets[*]}imagePullSecret={.name}{"\n"}{end}'`

성공 gate는 image reference·pull policy와 Secret·ServiceAccount 이름만 확인되는 것이다. Secret 값·token·인증서는 출력하지 않는다. image 선언이 맞아도 node 로그로 내려가며 API 빈 출력은 registry 정상의 증거가 아니다.

### 3. volume 준비

진입 증거는 `FailedAttachVolume`, `FailedMount`, `MountVolume.SetUp failed`, timeout, `Multi-Attach`, device/filesystem, permission 오류다. 연결 경로는 `실행 host → API server → PVC/PV/StorageClass → VolumeAttachment → CSI controller/node plugin → kubelet volume manager → Linux mount`다.

`kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .spec.volumes[*]}{.name}{" pvc="}{.persistentVolumeClaim.claimName}{" configmap="}{.configMap.name}{" secret="}{.secret.secretName}{" emptyDir="}{.emptyDir.medium}{"\n"}{end}{range .spec.containers[*].volumeMounts[*]}mount={.name}{" path="}{.mountPath}{"\n"}{end}'`

출력에서 volume·PVC·mount path 관계를 확인한다. 복수 PVC 후보면 첫 번째를 고르지 않는다.

### 4. sandbox 준비

진입 증거는 `FailedCreatePodSandBox`, `CreatePodSandboxError`, `network plugin`, `CNI`, `failed to setup network`, `no IP addresses available`, `failed to allocate`다. 연결 경로는 `실행 host → API server → kubelet → CRI sandbox → CNI/IPAM → network namespace/interface/route → Linux firewall/underlay`다.

`kubectl get pods -A -o wide --field-selector "spec.nodeName=$NODE"`

성공 gate는 같은 node의 Pod UID·phase·생성 시각과 공통 실패 범위를 확인하는 것이다. CNI Pod `Running`이나 Pod `Pending`은 IP pool·route·runtime sandbox 성공을 보장하지 않는다.

`CNI_NAMESPACE='PASTE_CNI_NAMESPACE_HERE'; CNI_POD='PASTE_CNI_POD_HERE'; CNI_CONTAINER='PASTE_CNI_CONTAINER_HERE'; CNI_READY=false; if [ -z "$CNI_NAMESPACE" ] || [ -z "$CNI_POD" ] || [ -z "$CNI_CONTAINER" ] || ! refresh_pod; then printf '%s\n' '중단: UID 재조회와 CNI 후보가 필요하다.' >&2; elif CNI_JSON="$(kubectl get pod "$CNI_POD" -n "$CNI_NAMESPACE" -o json)" && CNI_NODE_TMP="$(jq -r '.spec.nodeName // empty' <<<"$CNI_JSON")" && [ "$CNI_NODE_TMP" = "$NODE" ] && jq -e --arg c "$CNI_CONTAINER" 'any(.spec.containers[]?; .name==$c)' <<<"$CNI_JSON" >/dev/null; then CNI_READY=true; export CNI_NAMESPACE CNI_POD CNI_CONTAINER; printf 'CNI_READY=true cni=%s/%s node=%s container=%s\n' "$CNI_NAMESPACE" "$CNI_POD" "$CNI_NODE_TMP" "$CNI_CONTAINER"; else CNI_JSON=''; printf '중단: CNI Pod producer/schema, node=%s 또는 container=%s 검증 실패\n' "$NODE" "$CNI_CONTAINER" >&2; fi`

`CNI_READY=true`와 `SELECTION_READY=true`이고 CNI Pod가 현재 `$NODE`의 실제 plugin container임을 확인한 경우에만 `if ! refresh_pod || [ "$CNI_READY" != true ] || [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: CNI log 직전 Pod UID 재조회·CNI·container 확인 실패' >&2; else filter_stream "$POD_UID|add|del|ipam|allocate|address|route|veth|permission|timeout|error" kubectl logs "$CNI_POD" -n "$CNI_NAMESPACE" -c "$CNI_CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=300; fi`를 실행한다. `IPAM pool exhausted`·address allocation은 IPAM, veth·namespace·permission은 CNI/Linux network로 이동한다. 같은 node의 여러 Pod가 실패하면 delete/restart를 반복하지 않는다.

### 5. 설정 projection

진입 증거는 Event가 `configmap`, `secret`, `not found`, `references non-existent`, `couldn't find key`, `MountVolume.SetUp failed`를 가리키는 경우다. 연결 경로는 `실행 host → API server → Pod volume/env 참조 → ConfigMap·Secret object → kubelet projected volume/atomic writer → container mount/env → application`이다. object 조회 성공은 key·mount·application config 정상의 증거가 아니다.

`kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .spec.volumes[*]}{.name}{" configmap="}{.configMap.name}{" secret="}{.secret.secretName}{"\n"}{end}{range .spec.containers[*]}{.name}{" envFrom="}{.envFrom[*].configMapRef.name}{" "}{.envFrom[*].secretRef.name}{"\n"}{range .env[*]}env={.name}{" configmap="}{.valueFrom.configMapKeyRef.name}{":"}{.valueFrom.configMapKeyRef.key}{" secret="}{.valueFrom.secretKeyRef.name}{":"}{.valueFrom.secretKeyRef.key}{"\n"}{end}{end}{range .spec.initContainers[*]}{.name}{" init-envFrom="}{.envFrom[*].configMapRef.name}{" "}{.envFrom[*].secretRef.name}{"\n"}{end}'`

참조 이름·key·주입 위치를 확인한 뒤 복수 후보를 임의 선택하지 않는다.

`CONFIGMAP='PASTE_CONFIGMAP_HERE'; SECRET='PASTE_SECRET_HERE'; CONFIG_READY=false; if ! refresh_pod || { [ -z "$CONFIGMAP" ] && [ -z "$SECRET" ]; }; then printf '%s\n' '중단: 현재 Pod UID 재조회 또는 실제 참조 object 이름 선택 실패' >&2; elif { [ -z "$CONFIGMAP" ] || kubectl get configmap "$CONFIGMAP" -n "$NS" -o go-template='{{.metadata.name}} keys={{range $key, $_ := .data}}{{$key}} {{end}}'; } && { [ -z "$SECRET" ] || kubectl get secret "$SECRET" -n "$NS" -o go-template='{{.metadata.name}} type={{.type}} keys={{range $key, $_ := .data}}{{$key}} {{end}}'; }; then CONFIG_READY=true; export CONFIGMAP SECRET; printf 'CONFIG_READY=true configmap=%s secret=%s\n' "${CONFIGMAP:--}" "${SECRET:--}"; else printf '%s\n' '중단: ConfigMap·Secret object 조회 실패. 값과 token은 출력하지 않는다.' >&2; fi`

`CONFIG_READY=true`일 때만 object 이름·key를 선언 원본과 대조한다. Secret data·환경 변수 값은 출력하지 않는다. `couldn't find key`는 key/선언 owner, projection·mount·permission은 kubelet으로 이관한다. 일반 container가 아직 생성되지 않았으면 `exec`하지 않는다. node log는 `printf -v REMOTE_CMD 'journalctl -u kubelet --since %q --until %q --no-pager' "$START_JOURNAL" "$END_JOURNAL"; if ! refresh_pod || [ "$NODE_INPUT_READY" != true ]; then printf '%s\n' '중단: projection log 직전 Pod UID 재조회 또는 NODE_INPUT_READY 확인 실패' >&2; else filter_stream "$POD_UID|project|atomic|mount|permission|watch|key|not found|error" node_exec "$REMOTE_CMD"; fi`로 범위를 제한하며 producer 실패·필터 무일치를 구분한다.

### 6. suffix 없음

진입 증거는 별도 Warning이 없거나 여러 suffix가 함께 보이는 경우다. 원인은 진행 중, Event TTL, Pod 교체, 권한 부족 중 하나다. 연결 경로는 `실행 host → API server → kubelet → image·volume·sandbox·projection 단계 → runtime`이다.

`kubectl get pod "$POD" -n "$NS" -o jsonpath='{.metadata.creationTimestamp}{" uid="}{.metadata.uid}{" phase="}{.status.phase}{" node="}{.spec.nodeName}{" conditions="}{range .status.conditions[*]}{.type}:{.status}{" "}{end}{"\n"}'`

성공 gate는 현재 UID·생성 시각·node가 자동값과 일치하는 것이다. node가 없으면 Pending 전용 scheduler 경로로 이동하고, node가 있으면 공통 node log 선택값을 먼저 통과시킨다.

`NODE_INPUT_READY=true`인 경우에만 `printf -v REMOTE_CMD 'journalctl -u kubelet --since %q --until %q --no-pager' "$START_JOURNAL" "$END_JOURNAL"; if ! refresh_pod || [ "$NODE_INPUT_READY" != true ]; then printf '%s\n' '중단: 미확정 log 직전 Pod UID 재조회 또는 NODE_INPUT_READY 확인 실패' >&2; else filter_stream "$POD_UID|$CONTAINER|pull|image|volume|mount|attach|sandbox|cni|configmap|secret|timeout|error" node_exec "$REMOTE_CMD"; fi`를 실행한다. `pull|image`, `volume|mount`, `sandbox|cni`, `configmap|secret` 각각의 전용 절로 이동하며, producer 실패·필터 무일치·필터 오류를 구분하고 broad node 조회와 무조건 delete/restart는 하지 않는다.

## 복구 전 gate와 조건부 복구

상태 변경 전에는 직접 원인·마지막 확인 지점, Pod/owner·Ready replica·Service 영향, 권한·승인, data·quorum·외부 호출 위험, rollback·중단 조건, 관찰 시간을 기록한다. PVC 삭제, lease 삭제, IP pool 확장, privileged 추가, 보안 정책 완화, runtime/CNI/CSI 재시작은 이 문서에서 제시하지 않는다.

`DEPLOYMENT='PASTE_DEPLOYMENT_HERE'; ROLLBACK_REVISION='PASTE_ROLLBACK_REVISION_HERE'; WORKLOAD_SELECTOR='PASTE_WORKLOAD_SELECTOR_HERE'; APPROVAL_ID='PASTE_APPROVAL_ID_HERE'; DATA_QUORUM_CONFIRM='PASTE_DATA_QUORUM_CONFIRM_HERE'; CHANGE_READY=false; if [ "$AUTO_READY" != true ] || [ "$OWNER_READY" != true ] || [ -z "$DEPLOYMENT" ] || [ -z "$ROLLBACK_REVISION" ] || [ -z "$WORKLOAD_SELECTOR" ] || [ -z "$APPROVAL_ID" ] || [ "$DATA_QUORUM_CONFIRM" != yes ]; then printf '%s\n' '중단: AUTO_READY·OWNER_READY·Deployment·revision·selector·승인 ID·data/quorum 확인이 필요하다.' >&2; elif validate_controller_change; then export DEPLOYMENT ROLLBACK_REVISION WORKLOAD_SELECTOR APPROVAL_ID DATA_QUORUM_CONFIRM; else printf '%s\n' '중단: API owner chain·selector·revision·replica 검증 실패' >&2; fi`

controller 관리 장기 실행 Pod, 원인 해소, 외부 호출·data·quorum 영향 없음, 대체 Ready replica, 승인된 owner와 selector가 모두 확인된 경우에만 `if ! validate_controller_change; then printf '%s\n' '중단: 삭제 직전 owner chain·selector·승인·replica 재검증 실패' >&2; else OLD_POD="$POD"; OLD_POD_UID="$POD_UID"; OLD_POD_CREATED_AT="$CREATED_AT"; if kubectl delete pod "$POD" -n "$NS" --wait=false; then DEPLOYMENT_UID="$(kubectl get deployment "$DEPLOYMENT" -n "$NS" -o jsonpath='{.metadata.uid}')" && reacquire_deployment_pod "$OLD_POD" "$OLD_POD_UID" "$OLD_POD_CREATED_AT"; else printf '%s\n' '중단: delete producer 실패; 새 Pod identity를 등록하지 않는다.' >&2; fi; fi`를 고려한다. 삭제 뒤에는 기존 `$POD` 조회로 이어가지 않고 새 생성 시각·UID가 하나인 후보만 승인된 Deployment owner UID chain으로 검증·등록한다. 기대 효과는 새 image pull·mount·sandbox 시도뿐이며 원인 제거를 보장하지 않는다. 같은 suffix 재발·Ready 감소·영향 확대·새 Warning이면 반복하지 않는다.

삭제 후 기존 Pod/UID를 재사용하지 않는다. `reacquire_deployment_pod`가 승인된 selector에서 더 최근 생성 시각·새 UID가 하나인 후보를 고르고 Pod→ReplicaSet→Deployment owner UID chain과 Deployment selector·revision·replica를 재검증한 뒤 `POD`, `POD_UID`, `OWNER_UID`, `SERVICE_ACCOUNT`, `POD_JSON`, `POD_RE`, `EVENT_SELECTOR`와 `AUTO_READY=true`를 등록한다. 0개·복수 후보·owner 불일치면 임의 선택하지 않는다.

## 정상화 검증

정상화는 `container/application → config projection → sandbox/IP → volume mount → image/runtime start → kubelet → API object identity`의 역순으로 확인한다. 삭제 후 `reacquire_deployment_pod`가 새 `POD`, `POD_UID`, `OWNER_UID`, `SERVICE_ACCOUNT`, `POD_JSON`, `POD_RE`, `EVENT_SELECTOR`를 다시 등록하고 `AUTO_READY=true` 및 승인된 Deployment owner chain을 재검증한다. `if [ "$CHANGE_READY" != true ] || [ "$AUTO_READY" != true ] || [ "$OWNER_CHAIN_READY" != true ] || [ "$POD_RECHECK_READY" != true ]; then printf '%s\n' '중단: 새 Pod identity·owner UID chain·자동 수집 gate가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,OWNER-KIND:.metadata.ownerReferences[?(@.controller==true)].kind,OWNER:.metadata.ownerReferences[?(@.controller==true)].name,OWNER-UID:.metadata.ownerReferences[?(@.controller==true)].uid,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,NODE:.spec.nodeName,CREATED:.metadata.creationTimestamp'; fi`의 UID·owner UID가 등록된 새 값과 같아야 한다. 이전 Event·로그와 새 Pod를 섞지 않는다.

`kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,NODE:.spec.nodeName,CREATED:.metadata.creationTimestamp'`

`kubectl get pod "$POD" -n "$NS" -o jsonpath='{.status.phase}{" "}{range .status.conditions[*]}{.type}={.status}{" "}{end}{range .status.containerStatuses[*]}{.name}{" ready="}{.ready}{" state="}{.state}{" restarts="}{.restartCount}{"\n"}{end}'`

성공 gate는 의도한 UID가 image pull·runtime start, CSI publish·kubelet mount, sandbox·IP allocation, ConfigMap/Secret projection, init 성공과 container `Running`·`Ready`를 통과하고 같은 시간의 새 Warning·restart 증가가 없는 것이다. `Running`, `Ready`, PVC `Bound`, 권한 `yes`, Endpoint `ready=true`, HTTP 200만으로 process listener·protocol·실제 요청·핵심 기능을 보장하지 않는다.

`SERVICE='PASTE_SERVICE_HERE'; SERVICE_READY=false; if [ -z "$SERVICE" ]; then printf '%s\n' '서비스가 실제 영향 대상이면 Service 이름을 선택한다.' >&2; elif kubectl get service "$SERVICE" -n "$NS" -o wide >/dev/null 2>&1; then SERVICE_READY=true; export SERVICE; printf 'SERVICE_READY=true service=%s\n' "$SERVICE"; else printf '중단: Service 조회 실패 service=%s\n' "$SERVICE" >&2; fi`

`SERVICE_READY=true`일 때만 `kubectl get endpointslice -n "$NS" -l "kubernetes.io/service-name=$SERVICE" -o wide`를 실행한다. Endpoint `ready=true`는 모든 address·port에서 process가 listen함을 보장하지 않는다. 승인된 실제 요청·핵심 기능과 재발 관찰 창이 통과하지 못하면 정상화를 선언하지 않는다.

## Prometheus 빠른 관측

### PromQL 생성

kube-state-metrics가 실제로 수집되고 `namespace`, `pod`, `uid`, `phase`, `reason` 라벨이 존재할 때만 사용한다. 아래 생성 명령의 출력 한 줄만 Prometheus/Grafana에 붙여 넣는다. metric 부재, label 불일치, query 실패, 빈 결과를 정상으로 해석하지 않는다.

`if ! refresh_pod || [ "$AUTO_READY" != true ] || [ -z "$POD_UID" ]; then printf '%s\n' '중단: PromQL 직전 Pod UID 재조회 또는 AUTO_READY가 아니다.' >&2; else QUERY="$(printf 'kube_pod_status_phase{namespace="%s",pod=~"%s",uid="%s",phase="Pending"}==1' "$NS" "$POD_RE" "$POD_UID")"; printf '%s\n' "$QUERY"; fi`

`if ! refresh_pod || [ "$AUTO_READY" != true ] || [ -z "$POD_UID" ]; then printf '%s\n' '중단: PromQL 직전 Pod UID 재조회 또는 AUTO_READY가 아니다.' >&2; else QUERY="$(printf 'kube_pod_container_status_waiting_reason{namespace="%s",pod=~"%s",uid="%s",reason="ContainerCreating"}==1' "$NS" "$POD_RE" "$POD_UID")"; printf '%s\n' "$QUERY"; fi`

`if ! refresh_pod || [ "$AUTO_READY" != true ] || [ -z "$POD_UID" ]; then printf '%s\n' '중단: PromQL 직전 Pod UID 재조회 또는 AUTO_READY가 아니다.' >&2; else QUERY="$(printf 'time()-kube_pod_status_scheduled_time{namespace="%s",pod=~"%s",uid="%s"}' "$NS" "$POD_RE" "$POD_UID")"; printf '%s\n' "$QUERY"; fi`

`ContainerCreating=1`은 현재 waiting reason의 보조 시계열이며 직접 원인을 확정하지 않는다. `kube_pod_status_scheduled_time` 미수집은 scheduled time이 0이라는 뜻이 아니다. 빈 결과는 scrape·metric·label·조회 시간 문제일 수 있고 현재 `POD_UID`와 uid label을 대조한다.
