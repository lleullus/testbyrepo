# Pod STATUS가 Error인 경우

## 입력값과 빠른 수집

모든 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. 실행 host의 `kubectl`은 API server까지, `logs`·`exec` stream은 API server에서 대상 node의 kubelet·runtime을 거쳐 대상 container까지 간다. node journal·CRI·Linux 명령은 대상 node shell에서만 실행하며, 한 hop 성공은 다음 hop이나 application 정상의 증거가 아니다.

| 종류 | 값 | 출처와 사용 범위 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 승인된 namespace와 정확한 Pod 이름을 한 번 입력한다. |
| API 자동값 | `POD_UID`, `NODE`, `PHASE`, `CREATED_AT`, `OWNER_KIND`, `OWNER_NAME`, `OWNER_UID`, `POD_JSON` | 현재 Pod API 응답에서 등록한다. UID·node·phase·시각과 controller owner kind/name/UID를 함께 보존한다. |
| 계산 후보 | `POD_RE`, `EVENT_SELECTOR` | Pod 이름을 정규식에 안전하게 escape하고 UID 제한 Event selector를 만든다. 후보를 확정된 원인으로 해석하지 않는다. |
| 운영자 선택값 | `CONTAINER`, `INIT_CONTAINER`, `START_RFC3339`, `START_JOURNAL`, `END_JOURNAL`, `KUBELET_ROOT`, `RUNTIME_SERVICE`, `CRI_ENDPOINT`, `START_AUDIT`, `END_AUDIT`, `NODE_HOST`, `DEPLOYMENT`, `ROLLBACK_REVISION`, `WORKLOAD_SELECTOR`, `APPROVAL_ID`, `DATA_QUORUM_CONFIRM`, `SERVICE` | 해당 상세 분기에서 출력된 후보와 실제 구현·승인을 확인한 뒤 선택한다. `NODE_HOST`는 API의 `NODE`에서 자동 추론하지 않고 승인된 SSH 대상 host를 직접 선택한다. 복수 후보를 첫 번째로 고르지 않는다. |

**Bash와 필수 도구 확인**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 이 문서의 명령은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true shell=%s\n' "$BASH_VERSION"; else printf '중단: 없는 필수 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 다음 단계로 진행하지 않는다. `jq`·`kubectl`·`grep`이 없으면 raw JSON이나 전체 로그를 저장해 우회하지 말고 승인된 UI 또는 담당 owner에게 같은 필드 확인을 요청한다.

**최초 입력과 이전 파생값 초기화**

`if [ -n "${PF_PID:-}" ] && kill -0 "$PF_PID" 2>/dev/null; then kill "$PF_PID" 2>/dev/null; wait "$PF_PID" 2>/dev/null || true; fi; unset INPUT_READY AUTO_READY SELECTION_READY NODE_INPUT_READY NODE_HOST NODE_HOST_READY NODE_IDENTITY_READY NODE_API_JSON K8S_MACHINE_ID REMOTE_IDENTITY REMOTE_MACHINE_ID REMOTE_HOSTNAME REMOTE_FQDN INIT_READY MOUNT_READY CHANGE_READY SERVICE_READY POD_UID NODE PHASE CREATED_AT OWNER POD_JSON POD_RE EVENT_SELECTOR CONTAINER INIT_CONTAINER START_RFC3339 START_JOURNAL END_JOURNAL KUBELET_ROOT RUNTIME_SERVICE CRI_ENDPOINT START_AUDIT END_AUDIT DEPLOYMENT ROLLBACK_REVISION WORKLOAD_SELECTOR SERVICE PF_PID; NS='PASTE_NAMESPACE_HERE'; POD='PASTE_POD_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: 도구 확인을 먼저 통과한다.' >&2; elif [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: NS와 POD를 입력한다.' >&2; elif kubectl get pod "$POD" -n "$NS" >/dev/null 2>&1; then INPUT_READY=true; export NS POD; printf 'INPUT_READY=true namespace=%s pod=%s\n' "$NS" "$POD"; else printf '중단: 정확한 Pod를 찾지 못했거나 API 권한이 없음 namespace=%s pod=%s\n' "$NS" "$POD" >&2; fi`

`INPUT_READY=true`가 아니면 모든 후속 명령을 중단한다. namespace를 모르면 `kubectl get pods -A --field-selector "metadata.name=$POD" -o custom-columns='NAMESPACE:.metadata.namespace,POD:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,NODE:.spec.nodeName' --no-headers`를 실행해 후보를 확인한다. 출력이 0개 또는 복수 namespace면 임의 선택하지 말고 정확한 namespace를 확인한 뒤 최초 입력을 다시 한다.

**API 자동 수집과 등록**

`POD_JSON`은 한 번의 정확한 Pod API 응답이며, API 호출·UID·시각 검증이 모두 성공하기 전에는 이전 값을 남기지 않는다. 성공 출력은 대상별 세로 블록으로 사람이 바로 비교할 수 있게 한다.

`unset POD_UID NODE PHASE CREATED_AT OWNER POD_RE EVENT_SELECTOR; AUTO_READY=false; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && POD_UID_TMP="$(jq -r '.metadata.uid // empty' <<<"$POD_JSON")" && PHASE_TMP="$(jq -r '.status.phase // empty' <<<"$POD_JSON")" && CREATED_AT_TMP="$(jq -r '.metadata.creationTimestamp // empty' <<<"$POD_JSON")" && [ -n "$POD_UID_TMP" ] && [ -n "$PHASE_TMP" ] && [ -n "$CREATED_AT_TMP" ]; then NODE_TMP="$(jq -r '.spec.nodeName // empty' <<<"$POD_JSON")"; OWNER_TMP="$(jq -r '[.metadata.ownerReferences[]? | "\(.kind)/\(.name)"] | join(",")' <<<"$POD_JSON")"; POD_RE_TMP="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; EVENT_SELECTOR_TMP="involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID_TMP"; POD_UID="$POD_UID_TMP"; NODE="$NODE_TMP"; PHASE="$PHASE_TMP"; CREATED_AT="$CREATED_AT_TMP"; OWNER="$OWNER_TMP"; POD_RE="^${POD_RE_TMP}$"; EVENT_SELECTOR="$EVENT_SELECTOR_TMP"; AUTO_READY=true; export POD_UID NODE PHASE CREATED_AT OWNER POD_RE EVENT_SELECTOR; jq -r '"=== 대상 Pod ===\n이름: \(.metadata.name)\nUID: \(.metadata.uid)\nNode: \(.spec.nodeName // "미배정")\nPhase: \(.status.phase // "미확인")\n생성 시각: \(.metadata.creationTimestamp // "미확인")\nOwner: \([.metadata.ownerReferences[]? | "\(.kind)/\(.name)"] | join(",") // "없음")\nContainer/Port 후보: " + ([.spec.containers[]? | "\(.name)=\([.ports[]? | ((.name // "unnamed") + ":" + (.containerPort|tostring))] | join(",") // "port 미선언")"] | join("; ")) + "\nContainer 상태: " + ([.status.containerStatuses[]? | "\(.name) state=\(.state|tojson) last=\(.lastState|tojson) reason=\(.state.terminated.reason // .state.waiting.reason // "-") exit=\(.state.terminated.exitCode // "-") restart=\(.restartCount // 0)"] | join("; ")) + "\nInit 상태: " + ([.status.initContainerStatuses[]? | "\(.name) state=\(.state|tojson) last=\(.lastState|tojson) reason=\(.state.terminated.reason // .state.waiting.reason // "-") exit=\(.state.terminated.exitCode // "-") restart=\(.restartCount // 0)"] | join("; "))' <<<"$POD_JSON"; printf 'AUTO_READY=true pod_uid=%s node=%s phase=%s created=%s owner=%s pod_regex=%s\n' "$POD_UID" "${NODE:--}" "$PHASE" "$CREATED_AT" "${OWNER:--}" "$POD_RE"; else POD_JSON=''; printf '%s\n' '중단: Pod API 실패 또는 UID·phase·생성 시각 누락. 이전 자동값은 무효다.' >&2; fi`

`AUTO_READY=true`이고 출력에 현재 UID·node·phase·생성 시각·container/init 상태가 모두 있어야 최초 확인으로 간다. API 호출 실패, 빈 출력, 후보가 복수인 경우 `AUTO_READY`를 유효하게 남기지 않는다. `Running`, `Ready`, `phase=Failed`는 application 기능 정상·원인 확정·다음 hop 성공을 보장하지 않는다.

**owner identity·UID 재조회·pipeline 상태 helper**

`invalidate_derived(){ AUTO_READY=false; OWNER_READY=false; POD_RECHECK_READY=false; SELECTION_READY=false; INIT_READY=false; NODE_INPUT_READY=false; MOUNT_READY=false; CHANGE_READY=false; SERVICE_READY=false; } ; refresh_pod(){ local latest='' latest_uid=''; POD_RECHECK_READY=false; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; return 1; elif ! latest="$(kubectl get pod "$POD" -n "$NS" -o json)"; then invalidate_derived; POD_JSON=''; printf '%s\n' 'Pod 재조회 producer 실패: API 응답이 없다.' >&2; return 1; elif ! latest_uid="$(jq -r '.metadata.uid // empty' <<<"$latest")" || [ -z "$latest_uid" ]; then invalidate_derived; POD_JSON=''; printf '%s\n' 'Pod 재조회 schema 실패: UID가 없다.' >&2; return 1; elif [ "$latest_uid" != "$POD_UID" ]; then invalidate_derived; POD_JSON=''; printf '중단: Pod UID 변경 old=%s new=%s\n' "$POD_UID" "$latest_uid" >&2; return 1; else POD_JSON="$latest"; POD_RECHECK_READY=true; export POD_JSON; printf 'POD_RECHECK_READY=true uid=%s\n' "$POD_UID"; return 0; fi; }; filter_stream(){ local pattern="$1"; shift; local producer_rc=0 filter_rc=0; set +e; "$@" | grep -E -i -C 3 "$pattern"; producer_rc=${PIPESTATUS[0]}; filter_rc=${PIPESTATUS[1]}; if [ "$producer_rc" -ne 0 ]; then printf 'PIPELINE_PRODUCER_FAILED rc=%s\n' "$producer_rc" >&2; return 1; elif [ "$filter_rc" -eq 1 ]; then printf 'FILTER_NO_MATCH pattern=%s\n' "$pattern" >&2; return 3; elif [ "$filter_rc" -ne 0 ]; then printf 'FILTER_FAILED rc=%s pattern=%s\n' "$filter_rc" "$pattern" >&2; return 2; else printf 'FILTER_MATCHED pattern=%s\n' "$pattern"; return 0; fi; } ; inspect_cri(){ local container_id="$1" body='' inspect_rc=0; if [ "$NODE_INPUT_READY" != true ]; then printf '%s\n' 'CRICTL_PRODUCER_FAILED: crictl 도구 없음' >&2; return 1; elif [ -z "$container_id" ] || [ -z "$CRI_ENDPOINT" ]; then printf '%s\n' 'CRICTL_PRODUCER_FAILED: container ID 또는 CRI endpoint 없음' >&2; return 1; else printf -v REMOTE_CRI_CMD "crictl --runtime-endpoint=%q inspect %q" "$CRI_ENDPOINT" "$container_id"; body="$(node_exec "$REMOTE_CRI_CMD")"; inspect_rc=$?; if [ "$inspect_rc" -ne 0 ]; then printf 'CRICTL_PRODUCER_FAILED rc=%s\n' "$inspect_rc" >&2; return 1; elif [ -z "$body" ]; then printf '%s\n' 'CRICTL_EMPTY_JSON: inspect 출력이 비었다.' >&2; return 2; elif ! jq -e '.status | type == "object" and (.id | type == "string" and length > 0)' <<<"$body" >/dev/null 2>&1; then printf '%s\n' 'CRICTL_SCHEMA_FAILED: status.id schema가 없다.' >&2; return 3; else jq -c '{id:.status.id,state:.status.state,exitCode:.status.exitCode,reason:.status.reason,message:.status.message,createdAt:.status.createdAt,startedAt:.status.startedAt,finishedAt:.status.finishedAt,logPath:.status.logPath}' <<<"$body"; return $?; fi; fi; }`

`OWNER_READY=true`와 `POD_RECHECK_READY=true`가 아니면 owner·logs·runtime·변경 의존 gate를 열지 않는다. `filter_stream`은 producer 실패, 필터 무일치, 필터 자체 오류를 서로 다른 결과로 남긴다. `inspect_cri`는 `crictl` producer 실패·빈 JSON·schema 실패를 각각 중단한다.

`OWNER_READY=false; if [ "$AUTO_READY" != true ] || ! OWNER_COUNT="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true)] | length' <<<"$POD_JSON")" || ! [[ "$OWNER_COUNT" =~ ^1$ ]]; then POD_JSON=''; AUTO_READY=false; printf '중단: controller owner가 정확히 하나가 아님 count=%s\n' "${OWNER_COUNT:--}" >&2; else OWNER_KIND_TMP="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true)][0].kind // empty' <<<"$POD_JSON")"; OWNER_NAME_TMP="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true)][0].name // empty' <<<"$POD_JSON")"; OWNER_UID_TMP="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true)][0].uid // empty' <<<"$POD_JSON")"; if [ -z "$OWNER_KIND_TMP" ] || [ -z "$OWNER_NAME_TMP" ] || [ -z "$OWNER_UID_TMP" ]; then POD_JSON=''; AUTO_READY=false; printf '%s\n' '중단: owner kind/name/UID가 모두 필요하다.' >&2; else OWNER_KIND="$OWNER_KIND_TMP"; OWNER_NAME="$OWNER_NAME_TMP"; OWNER_UID="$OWNER_UID_TMP"; OWNER="$OWNER_KIND/$OWNER_NAME"; OWNER_READY=true; export OWNER_KIND OWNER_NAME OWNER_UID OWNER; printf 'OWNER_READY=true kind=%s name=%s uid=%s\n' "$OWNER_KIND" "$OWNER_NAME" "$OWNER_UID"; fi; fi`

owner가 없거나 복수이면 `OWNER_READY=false`로 남겨 owner chain·Job/CronJob·변경 gate를 닫는다. 문자열 owner 이름만으로 controller를 추정하지 않는다.

## 최초 확인

`kubectl get pod "$POD" -n "$NS" -o wide`

성공 gate는 대상 이름·UID가 자동 수집한 값과 같고 `STATUS`, `READY`, `RESTARTS`, `NODE`, `AGE`가 출력되는 것이다. 실패·빈 출력은 Pod 삭제나 새 Pod 선택의 근거가 아니며 API 권한·현재 context를 확인한다.

`kubectl get pod "$POD" -n "$NS" -o jsonpath='{.status.phase}{"\n"}{range .status.initContainerStatuses[*]}init/{.name}{" state="}{.state}{" last="}{.lastState}{" restart="}{.restartCount}{"\n"}{end}{range .status.containerStatuses[*]}container/{.name}{" state="}{.state}{" last="}{.lastState}{" restart="}{.restartCount}{"\n"}{end}'`

성공 gate는 실패한 init/container의 `waiting|running|terminated`, `lastState.terminated.reason`, `exitCode`, `finishedAt`, `restartCount`가 UID와 함께 확인되는 것이다. JSONPath가 비면 field 부재·권한·API 실패를 구분하지 못한 것이므로 `describe`로 이관한다.

`kubectl describe pod "$POD" -n "$NS"`

`Conditions`와 `Events`의 첫 실패 `reason`, message, 관측 시각을 보존한다. `describe` 성공은 container process·node·runtime·application 정상이나 원인 확정을 보장하지 않는다.

`if ! refresh_pod; then printf '%s\n' '중단: Event 조회 직전 Pod UID 재조회 실패' >&2; else kubectl get events -n "$NS" --field-selector "$EVENT_SELECTOR" --sort-by=.metadata.creationTimestamp -o custom-columns='CREATED:.metadata.creationTimestamp,FIRST-SEEN:.firstTimestamp,LAST-SEEN:.lastTimestamp,EVENT-TIME:.eventTime,SERIES-LAST:.series.lastObservedTime,TYPE:.type,REASON:.reason,COUNT:.count,MESSAGE:.message'; fi`

UID 제한 Event가 비면 Event TTL 만료, selector 불일치, 권한 부족, API 조회 실패를 재확인한다. `CREATED` 순서만으로 최초 원인을 확정하지 말고 실제로 채워진 시각을 종료 시각·로그와 대조한다. 민감정보는 저장하지 않는다.

표는 경로 선택용이며 원인 확정·상태 변경 승인·정상화를 의미하지 않는다.

**container 로그 공통 선택값**

`CONTAINER='PASTE_CONTAINER_HERE'; START_RFC3339='PASTE_START_RFC3339_HERE'; SELECTION_READY=false; if [ "$AUTO_READY" != true ] || ! refresh_pod; then printf '%s\n' '중단: 현재 Pod UID 재조회 gate가 아니다.' >&2; elif [ -z "$CONTAINER" ] || ! logs 또는 runtime container ID가 필요한 모든 절은 먼저 `SELECTION_READY=true`를 확인한다. init 절은 별도의 `INIT_CONTAINER`를 선택하지만 공통 UTC 시작 시각은 이 값을 재사용한다.

### 1. 애플리케이션 종료

진입 증거는 `reason`이 application 고유 문자열이거나 종료 code가 `1`, `2`, `126`, `127`, `143`이고 OOM·eviction 근거가 없는 같은 UID의 관측이다. 연결 경로는 `실행 host → kubectl/API server → kubelet/runtime → container log stream → process/application → Service·DB·외부 API`다. 로그 stream 준비 성공은 application 오류 부재나 외부 endpoint 정상의 증거가 아니다.

선택값은 출력된 container 후보에서 고른다. 복수 후보를 임의로 선택하지 않으며 `SELECTION_READY=true`가 아니면 logs를 실행하지 않는다.

`if ! refresh_pod || [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: current Pod UID 재조회 또는 SELECTION_READY 실패' >&2; else filter_stream 'panic|fatal|error|exception|timeout|refused|denied|permission|not found|killed|signal' kubectl logs "$POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=200; fi`

필터된 결정적 오류가 있으면 process·설정·외부 dependency 중 해당 다음 계층으로 이동한다. transport/stream 실패는 로그 내용이 아니라 API 권한·대상 UID·kubelet/runtime 계층의 실패다. 빈 결과는 오류 없음이 아니므로 같은 범위의 제한 tail을 확인한다. Secret·token·개인정보가 보이면 저장을 중단한다.

`if ! refresh_pod || [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: current Pod UID 재조회 또는 SELECTION_READY 실패' >&2; else kubectl logs "$POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=50; rc=$?; if [ "$rc" -ne 0 ]; then printf 'LOG_PRODUCER_FAILED rc=%s\n' "$rc" >&2; else printf '%s\n' 'LOG_PRODUCER_OK; 출력 빈도와 내용은 오류 부재를 보장하지 않는다.'; fi; fi`

`restartCount`가 1 이상인 경우에만 `--previous`를 확인한다. `--previous`가 비면 직전 container가 없거나 로그 보존·runtime stream이 실패한 것이며 종료 원인을 부정하지 않는다.

`if ! refresh_pod || [ "$SELECTION_READY" != true ]; then printf '%s\n' '중단: current Pod UID 재조회 또는 SELECTION_READY 실패' >&2; else filter_stream 'panic|fatal|error|exception|timeout|refused|denied|permission|not found|killed|signal' kubectl logs "$POD" -n "$NS" -c "$CONTAINER" --previous --timestamps --since-time="$START_RFC3339" --tail=200; fi`

`connection refused`는 주소 도달 후 listener·port·firewall·backend 중 하나가 거부한 범위이지 단일 원인 확정이 아니다. `exitCode=126`은 실행 파일 권한·형식, command/args, securityContext, `noexec` mount를 확인한다. `127`은 entrypoint·PATH·파일 존재, `143`은 rollout·scale·delete·eviction·preStop 시각과 대조하며 application 장애로 단정하지 않는다. ConfigMap·Secret 값은 출력하지 않고 참조 이름·key만 다음 owner에게 이관한다.

### 2. OOMKilled 또는 메모리 종료

진입 증거는 같은 UID의 `reason=OOMKilled` 또는 `exitCode=137`이다. `137`만으로 OOM을 확정하지 않는다. 연결 경로는 `실행 host → API server → Pod status → node kubelet → Linux kernel/cgroup → workload`이며 API status 성공은 node pressure나 kernel OOM 정상의 증거가 아니다.

`kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .spec.containers[*]}{.name}{" requests="}{.resources.requests}{" limits="}{.resources.limits}{"\n"}{end}'`

성공 gate는 대상 container의 memory request/limit과 종료 시각이 확인되는 것이다. 빈 resource는 무제한·정상이라는 뜻이 아니며 선언 원본과 admission 결과를 확인한다.

`kubectl describe node "$NODE"`

`MemoryPressure`, `EvictionThresholdMet`, `Evicted`, allocatable과 같은 시각의 공통 실패를 본다. node가 비어 있거나 조회가 실패하면 node 원인을 확정하지 않고 플랫폼 owner에게 Pod UID·시각을 이관한다.

### 3. Evicted와 node pressure

진입 증거는 Pod status reason `Evicted`, `MemoryPressure`, `DiskPressure`, `PIDPressure` 또는 같은 node의 복수 workload 실패다. `kubectl get pod` 성공은 node filesystem·PID·runtime 정상의 증거가 아니다.

### 4. container start 실패

진입 증거는 `CreateContainerError`, `RunContainerError`, `OCI runtime create failed`, `permission denied`, `no such file or directory`, `read-only file system`, `failed to create task`다. 연결 경로는 `실행 host → API server → node kubelet → CRI endpoint → OCI runtime → Linux filesystem/security → container process`다. API 조회 성공이나 `containerID` 존재는 process start·application listener를 보장하지 않는다.

### 5. init container 실패

진입 증거는 첫 미완료 init의 `Waiting`·`Terminated`, non-zero exit, init reason 또는 init Event다. init 성공 전에는 일반 container의 `Running`·`Ready`를 정상화 근거로 보지 않는다. 연결 경로는 `실행 host → API server → kubelet/runtime → init container log stream → ConfigMap·Secret·PVC·DNS·DB/API`다.

`INIT_CONTAINER='PASTE_INIT_CONTAINER_HERE'; INIT_READY=false; if [ "$AUTO_READY" != true ] || ! refresh_pod; then printf '%s\n' '중단: AUTO_READY 또는 current Pod UID 재조회가 아니다.' >&2; elif [ -z "$INIT_CONTAINER" ] || ! jq -e --arg c "$INIT_CONTAINER" 'any(.spec.initContainers[]?; .name==$c)' <<<"$POD_JSON" >/dev/null; then printf '중단: 현재 Pod의 init container가 아님 %s\n' "$INIT_CONTAINER" >&2; else INIT_READY=true; export INIT_CONTAINER; printf 'INIT_READY=true init=%s uid=%s\n' "$INIT_CONTAINER" "$POD_UID"; fi`

`INIT_READY=true`이고 init process가 `running|terminated` 또는 실행 이력이 확인된 경우에만 `if ! refresh_pod || [ "$INIT_READY" != true ]; then printf '%s\n' '중단: 실행 직전 Pod UID 재조회 또는 INIT_READY 확인 실패' >&2; else filter_stream 'panic|fatal|error|exception|timeout|refused|denied|permission|not found|migration|lock|oom|killed' kubectl logs "$POD" -n "$NS" -c "$INIT_CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=200; fi`를 실행한다. init이 Waiting이면 logs·exec를 강행하지 않고 [[04. Pod STATUS가 PodInitializing인 경우]] 또는 [[05. Pod가 Init 단계에서 진행되지 않는 경우]]로 이관한다.

필터가 비면 같은 시간의 제한 tail을 확인하되 오류 부재로 해석하지 않는다. `permission denied`·`not found`는 volume·projection·securityContext, `OOMKilled`·`137`은 resource·node pressure, DB connection 오류는 Service/DNS/DB owner로 내린다. Secret·token·개인정보는 기록하지 않는다.

### 6. Job과 CronJob

진입 증거는 owner와 같은 UID의 `BackoffLimitExceeded` 또는 `DeadlineExceeded`다. API server에서 owner kind/name을 확인하고, 복수 실패 Pod의 공통 reason·exit code와 산출물·외부 side effect를 비교한다.

`if [ "$AUTO_READY" != true ] || [ "$OWNER_READY" != true ] || ! refresh_pod; then printf '%s\n' '중단: OWNER_READY 또는 현재 UID 재조회 gate가 아니다.' >&2; elif [ "$OWNER_KIND" = Job ] || [ "$OWNER_KIND" = CronJob ]; then OWNER_JSON="$(kubectl get "$OWNER_KIND" "$OWNER_NAME" -n "$NS" -o json)"; OWNER_OBJECT_UID="$(jq -r '.metadata.uid // empty' <<<"$OWNER_JSON")"; if [ -z "$OWNER_JSON" ] || [ -z "$OWNER_OBJECT_UID" ] || [ "$OWNER_OBJECT_UID" != "$OWNER_UID" ]; then printf '중단: owner API UID 불일치 expected=%s actual=%s\n' "$OWNER_UID" "${OWNER_OBJECT_UID:--}" >&2; else kubectl get "$OWNER_KIND" "$OWNER_NAME" -n "$NS" -o wide && kubectl describe "$OWNER_KIND" "$OWNER_NAME" -n "$NS"; fi; else printf '이 Pod controller owner는 Job/CronJob이 아님 owner=%s\n' "$OWNER"; fi`

성공 gate는 owner status와 실패 Pod count·산출물이 현재 UID·시각과 연결되는 것이다. Job/CronJob 조회 성공은 외부 side effect의 멱등성·중복 없음·재실행 안전을 보장하지 않는다. 결제·메시지·배치 재실행은 담당자 승인과 멱등성 확인 없이는 제시하지 않고 owner에게 이관한다.

## 복구 전 gate와 조건부 복구

진단과 상태 변경을 분리한다. 변경 전 trigger, 직접 근거, 대상 UID·owner·replica 영향, 권한·승인, 데이터·quorum·외부 호출 위험, rollback, 중단 조건, 관찰 시간을 기록한다.

**Deployment rollback 입력과 검증**

`DEPLOYMENT='PASTE_DEPLOYMENT_HERE'; ROLLBACK_REVISION='PASTE_ROLLBACK_REVISION_HERE'; WORKLOAD_SELECTOR='PASTE_WORKLOAD_SELECTOR_HERE'; APPROVAL_ID='PASTE_APPROVAL_ID_HERE'; DATA_QUORUM_CONFIRM='PASTE_DATA_QUORUM_CONFIRM_HERE'; CHANGE_READY=false; if [ "$AUTO_READY" != true ] || [ "$OWNER_READY" != true ] || [ -z "$DEPLOYMENT" ] || [ -z "$ROLLBACK_REVISION" ] || [ -z "$WORKLOAD_SELECTOR" ] || [ -z "$APPROVAL_ID" ] || [ "$DATA_QUORUM_CONFIRM" != yes ]; then printf '%s\n' '중단: AUTO_READY·OWNER_READY·Deployment·revision·selector·승인 ID·data/quorum 확인이 필요하다.' >&2; elif validate_controller_change; then export DEPLOYMENT ROLLBACK_REVISION WORKLOAD_SELECTOR APPROVAL_ID DATA_QUORUM_CONFIRM; else printf '%s\n' '중단: API owner chain·selector·revision·replica 검증 실패' >&2; fi`

직전 rollout 직후부터 동일 오류가 시작됐고 이전 revision 정상·현재 변경 원인이 같은 UID와 Event/log에 연결되며 Deployment owner가 승인한 경우에만 `if ! validate_controller_change; then printf '%s\n' '중단: 실행 직전 owner chain·selector·승인·replica 재검증 실패' >&2; else OLD_POD="$POD"; OLD_POD_UID="$POD_UID"; OLD_POD_CREATED_AT="$CREATED_AT"; if kubectl rollout undo "deployment/$DEPLOYMENT" -n "$NS" --to-revision="$ROLLBACK_REVISION" && kubectl rollout status "deployment/$DEPLOYMENT" -n "$NS" --timeout=5m; then DEPLOYMENT_UID="$(kubectl get deployment "$DEPLOYMENT" -n "$NS" -o jsonpath='{.metadata.uid}')" && reacquire_deployment_pod "$OLD_POD" "$OLD_POD_UID" "$OLD_POD_CREATED_AT"; else printf '%s\n' '중단: rollback producer/status 실패; 새 Pod identity를 등록하지 않는다.' >&2; fi; fi`를 실행한다. rollback 뒤에는 기존 `$POD` 조회로 이어가지 않고 새 생성 시각·UID가 하나인 후보만 승인된 Deployment owner UID chain으로 검증·등록한다. 영향은 검증된 Deployment의 새 replica 전체이며 node·runtime·외부 dependency를 되돌리지 않는다. Ready 감소·같은 reason 재발·새 Warning·서비스 지표 악화 시 중단하고 rollback 담당자에게 이관한다. rollout status 성공은 application 기능 정상이나 목표 revision의 근본 원인 제거를 보장하지 않는다.

controller 관리 장기 실행 Pod이고 대체 Ready replica·데이터/세션 안전·일시 원인·승인이 모두 확인된 경우에만 `if ! validate_controller_change; then printf '%s\n' '중단: 삭제 직전 owner chain·selector·승인·replica 재검증 실패' >&2; else OLD_POD="$POD"; OLD_POD_UID="$POD_UID"; OLD_POD_CREATED_AT="$CREATED_AT"; if kubectl delete pod "$POD" -n "$NS" --wait=false; then DEPLOYMENT_UID="$(kubectl get deployment "$DEPLOYMENT" -n "$NS" -o jsonpath='{.metadata.uid}')" && reacquire_deployment_pod "$OLD_POD" "$OLD_POD_UID" "$OLD_POD_CREATED_AT"; else printf '%s\n' '중단: delete producer 실패; 새 Pod identity를 등록하지 않는다.' >&2; fi; fi`를 고려한다. 삭제 뒤에는 기존 `$POD` 조회로 이어가지 않고 새 생성 시각·UID가 하나인 후보만 승인된 Deployment owner UID chain으로 검증·등록한다. standalone, StatefulSet quorum, Job/CronJob, PVC 데이터 위험 Pod에는 적용하지 않는다. 새 Pod가 같은 reason으로 실패하거나 Ready replica가 줄면 반복 삭제하지 않는다.

## 정상화 검증

정상화는 원인 경로를 역순으로 확인한다. rollback/delete 후 `reacquire_deployment_pod`가 새 `POD`, `POD_UID`, `OWNER_UID`, `POD_JSON`, `POD_RE`, `EVENT_SELECTOR`를 다시 등록하고 `AUTO_READY=true` 및 승인된 Deployment owner chain을 재검증한다. `CHANGE_READY=true`인 변경 뒤에만 `if [ "$CHANGE_READY" != true ] || [ "$AUTO_READY" != true ] || [ "$OWNER_CHAIN_READY" != true ] || [ "$POD_RECHECK_READY" != true ]; then printf '%s\n' '중단: 새 Pod identity·owner UID chain·자동 수집 gate가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,OWNER-KIND:.metadata.ownerReferences[?(@.controller==true)].kind,OWNER:.metadata.ownerReferences[?(@.controller==true)].name,OWNER-UID:.metadata.ownerReferences[?(@.controller==true)].uid,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,RESTARTS:.status.containerStatuses[*].restartCount,CREATED:.metadata.creationTimestamp'; fi`로 새 identity를 확인한다. selector 조회가 0개·복수 후보·권한 실패면 임의 선택하지 않는다.

`kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,RESTARTS:.status.containerStatuses[*].restartCount,NODE:.spec.nodeName,CREATED:.metadata.creationTimestamp'`

`SERVICE='PASTE_SERVICE_HERE'; SERVICE_READY=false; if [ -z "$SERVICE" ]; then printf '%s\n' '서비스 기능 확인을 생략하려면 이 gate를 통과시키지 않는다.' >&2; elif kubectl get service "$SERVICE" -n "$NS" -o wide >/dev/null 2>&1; then SERVICE_READY=true; export SERVICE; printf 'SERVICE_READY=true service=%s\n' "$SERVICE"; else printf '중단: Service 조회 실패 service=%s\n' "$SERVICE" >&2; fi`

`if [ "$SERVICE_READY" != true ]; then printf '%s\n' '중단: SERVICE_READY가 아니다.' >&2; else kubectl get endpointslice -n "$NS" -l "kubernetes.io/service-name=$SERVICE" -o wide; fi`

보존·검증할 것은 의도한 새 UID, 원하는 Ready replica, 동일 reason·exit code·restart 증가 중단, 새 Warning 부재, image pull/start·volume·sandbox 성공, 해당 EndpointSlice, 승인된 실제 요청·핵심 기능과 재발 관찰 창이다. `Running`, `Ready`, PVC `Bound`, 권한 `yes`, Endpoint `ready=true`, HTTP 200은 각각 다음 hop·listener·인증·application data 정상까지 보장하지 않는다. 승인된 health check·synthetic transaction·지표 절차가 없거나 실패하면 정상화를 선언하지 않는다.

## Prometheus 빠른 관측

### PromQL 생성

Prometheus와 kube-state-metrics가 실제로 수집되고 `namespace`, `pod`, `uid`, `container`, `reason`, `phase` 라벨이 존재할 때만 사용한다. 아래 명령이 출력한 **한 줄**만 Prometheus/Grafana에 붙여 넣는다. query 실패, metric 부재, label 불일치, 빈 결과를 서로 구분한다.

`if ! refresh_pod || [ "$AUTO_READY" != true ] || [ -z "$POD_UID" ]; then printf '%s\n' '중단: PromQL 직전 Pod UID 재조회 또는 AUTO_READY가 아니다.' >&2; else QUERY="$(printf 'kube_pod_status_phase{namespace="%s",pod=~"%s",uid="%s",phase="Failed"}==1' "$NS" "$POD_RE" "$POD_UID")"; printf '%s\n' "$QUERY"; fi`

`if ! refresh_pod || [ "$AUTO_READY" != true ] || [ -z "$POD_UID" ]; then printf '%s\n' '중단: PromQL 직전 Pod UID 재조회 또는 AUTO_READY가 아니다.' >&2; else QUERY="$(printf 'kube_pod_container_status_waiting_reason{namespace="%s",pod=~"%s",uid="%s",reason=~"CrashLoopBackOff|CreateContainerConfigError|CreateContainerError|RunContainerError"}==1' "$NS" "$POD_RE" "$POD_UID")"; printf '%s\n' "$QUERY"; fi`

`if ! refresh_pod || [ "$AUTO_READY" != true ] || [ -z "$POD_UID" ]; then printf '%s\n' '중단: PromQL 직전 Pod UID 재조회 또는 AUTO_READY가 아니다.' >&2; else QUERY="$(printf 'sum by(namespace,pod,uid,container)(increase(kube_pod_container_status_restarts_total{namespace="%s",pod=~"%s",uid="%s"}[15m]))>0' "$NS" "$POD_RE" "$POD_UID")"; printf '%s\n' "$QUERY"; fi`

`Failed=1`은 API phase가 Failed인 시계열만 뜻하며 printer `STATUS=Error`를 부정하지 않는다. waiting reason은 현재 상태만 보여 주고 이미 종료된 실패를 누락할 수 있다. restart 증가가 비어도 scrape 실패·metric 미수집·UID 불일치일 수 있다. PromQL은 원인 확정·상태 변경 승인·정상화의 단독 근거가 아니다.
