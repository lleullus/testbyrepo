# Pod 이벤트에 Killing이 반복되는 경우

## 입력값과 빠른 수집

이 런북의 모든 값은 다음처럼 분류한다. 처음에는 namespace와 Pod만 운영자가 넣고, API가 반환한 현재 객체의 UID·node·phase·owner를 같은 Bash에 등록한다. `NS_RE`와 `POD_RE`는 PromQL용으로 이름을 escape한 계산 후보이며, container와 시간·배포 승인 정보는 관측 결과를 본 뒤 운영자가 선택한다. 빈 값, API 실패, 후보 수 불일치가 있으면 해당 gate를 열지 않고 이전 파생값도 유효하게 두지 않는다.

| 종류 | 값 | 출처와 사용 범위 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 승인된 namespace와 현재 조사할 Pod 이름. 문서 전체에서 한 번만 입력한다. |
| API 자동값 | `POD_UID`, `NODE`, `PHASE`, `OWNER_KIND`, `OWNER_NAME`, `OWNER_UID`, `KILLING_EVENT_UID`, `KILLING_EVENT_MESSAGE`, `KILLING_TIME`, `KILLING_EPOCH`, `NS_RE`, `POD_RE`, `OBSERVED_AT` | Pod API와 같은 UID의 정확히 하나인 canonical Killing Event에서 등록한다. `NODE`가 비어 있으면 node 계층 분기를 열지 않는다. |
| 계산 후보 | `NS_RE`, `POD_RE` | PromQL matcher 후보. escape된 문자열을 출력으로 확인한 뒤 사용한다. |
| 운영자 선택값 | `CONTAINER`, `START_RFC3339`, `START_JOURNAL`, `END_JOURNAL`, `KUBELET_SERVICE`, `NODE_HOST`, `DEPLOYMENT` | Event·Pod·실제 node 환경·승인 기록을 확인한 뒤 필요한 상세 분기에서 한 번 선택한다. `NODE_HOST`는 승인된 remote host다. `CONTAINER`는 canonical Event message 관계가 맞을 때만 `KILLING_EVENT_CONTAINER`로 등록한다. rollout approval artifact와 immutable change ID는 이 런북의 자동 입력값으로 받지 않고 owner/audit handoff로만 남긴다. |

### 실행 위치·도구·권한 전제

모든 kubectl·logs·journal 명령은 승인된 context에 연결된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. `POD_UID`, `NODE`, 로그 시간과 gate가 shell 변수로 이어지므로 터미널을 닫거나 다른 shell로 바꾸면 초기화 절부터 다시 실행한다. `kubectl`은 API 읽기 권한과 필요한 경우 `pods/log`, node 조회 권한이 있어야 하며, node journal은 실제 node shell 접근과 승인된 `sudo` 권한이 있어야 한다. Secret·token·인증서 개인키·개인정보 원문은 출력하거나 저장하지 않는다.

**Bash·필수 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else MISSING_TOOLS=''; for TOOL in kubectl jq grep sed date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 다음 단계로 진행하지 않는다. `journalctl`과 `sudo`는 node journal 분기에 들어갈 때 별도로 확인하며, 그 확인이나 권한 검증이 실패하면 journal을 실행하지 않고 node owner에게 이관한다.

### 대상 지정·이전 상태 초기화·API 자동 등록

재실행 시작 시 이전 Pod·UID·owner·시간·선택값을 모두 무효화한다. API 호출과 필수 field 파싱이 모두 성공한 경우에만 `AUTO_READY=true`가 된다.

**최초 입력과 상태 초기화 — 같은 Bash에서 한 번 실행**

`POD_API_GATE_ENABLED=false`

`unset INPUT_READY AUTO_READY NODE_READY OWNER_READY FIRST_CHECK_READY EVENT_API_OK EVENT_READY SELECTION_READY LOG_TIME_READY JOURNAL_TIME_READY ROLLOUT_READY DEPLOYMENT_READY POD_JSON EVENT_JSON POD_UID NODE PHASE OWNER_KIND OWNER_NAME OWNER_UID NS_RE POD_RE OBSERVED_AT CONTAINER START_RFC3339 START_JOURNAL END_JOURNAL KUBELET_SERVICE ROLLOUT_APPROVED_AT DEPLOYMENT; NS='PASTE_NAMESPACE_HERE'; POD='PASTE_POD_HERE'; INPUT_READY=false; AUTO_READY=false; NODE_READY=false; OWNER_READY=false; FIRST_CHECK_READY=false; EVENT_API_OK=false; EVENT_READY=false; SELECTION_READY=false; LOG_TIME_READY=false; JOURNAL_TIME_READY=false; ROLLOUT_READY=false; DEPLOYMENT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: 도구 확인을 먼저 통과한다.' >&2; elif [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: NS와 POD를 입력한다.' >&2; elif POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && POD_UID_TMP="$(jq -er '.metadata.uid' <<<"$POD_JSON")" && PHASE_TMP="$(jq -r '.status.phase // "-"' <<<"$POD_JSON")" && NODE_TMP="$(jq -r '.spec.nodeName // empty' <<<"$POD_JSON")" && OWNER_KIND_TMP="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true)][0].kind // empty' <<<"$POD_JSON")" && OWNER_NAME_TMP="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true)][0].name // empty' <<<"$POD_JSON")" && OWNER_UID_TMP="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true)][0].uid // empty' <<<"$POD_JSON")" && NS_RE_TMP="$(printf '%s' "$NS" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" && POD_RE_TMP="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')" && OBSERVED_AT_TMP="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; then INPUT_READY=true; POD_UID="$POD_UID_TMP"; PHASE="$PHASE_TMP"; NODE="$NODE_TMP"; OWNER_KIND="$OWNER_KIND_TMP"; OWNER_NAME="$OWNER_NAME_TMP"; OWNER_UID="$OWNER_UID_TMP"; NS_RE="$NS_RE_TMP"; POD_RE="$POD_RE_TMP"; OBSERVED_AT="$OBSERVED_AT_TMP"; AUTO_READY=true; [ -n "$NODE" ] && NODE_READY=true; if [ -n "$OWNER_KIND" ] && [ -n "$OWNER_NAME" ] && [ -n "$OWNER_UID" ]; then OWNER_READY=true; fi; jq -r --arg observed "$OBSERVED_AT" '"=== 대상 Pod ===\nNamespace: \(.metadata.namespace)\nPod: \(.metadata.name)\nUID: \(.metadata.uid)\nPhase: \(.status.phase // "-")\nNode: \(.spec.nodeName // "-")\nPod 시작: \(.status.startTime // "-")\nOwner: " + (([.metadata.ownerReferences[]? | select(.controller==true) | "\(.kind)/\(.name) UID=\(.uid)"] | if length==0 then "-" else join(", ") end)) + "\nContainer/Port 후보:\n" + ([.spec.containers[]? | "  \(.name): " + ([.ports[]? | ((.name // "unnamed") + ":" + (.containerPort|tostring))] | if length==0 then "선언된 port 없음" else join(", ") end)] | if length==0 then "  없음" else join("\n") end) + "\n관측 시각: " + $observed' <<<"$POD_JSON"; printf 'AUTO_READY=true NS_RE=%s POD_RE=%s NODE_READY=%s OWNER_READY=%s\n' "$NS_RE" "$POD_RE" "$NODE_READY" "$OWNER_READY"; else printf '중단: Pod API 조회 또는 필수 field 파싱 실패. 이전 값은 유효하지 않다.\n' >&2; unset POD_JSON POD_UID NODE PHASE OWNER_KIND OWNER_NAME OWNER_UID NS_RE POD_RE OBSERVED_AT; fi`

`AUTO_READY=true`와 대상 Pod 블록이 함께 출력되어야 한다. API가 실패하거나 UID가 없으면 Pod 이름을 다른 명령에 재입력하지 말고 namespace·권한·현재 Pod를 확인한 뒤 초기화 명령부터 다시 실행한다. `Running`이나 `Ready`가 출력돼도 application listener·기능 정상은 보장하지 않는다.

**container 상태·port 관계 확인 — 아래 한 줄 전체를 복사**

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else jq -r --arg observed "$OBSERVED_AT" '"=== 자동 수집: Pod 관계 ===\n네임스페이스: \(.metadata.namespace)\n파드: \(.metadata.name)\n파드 UID: \(.metadata.uid)\n파드 상태: \(.status.phase // "-")\n노드: \(.spec.nodeName // "-")\n관측 시각: " + $observed + "\n컨테이너 상태/포트:\n" + ([.spec.containers[]? as $c | ([.status.containerStatuses[]? | select(.name==$c.name)][0] // {}) as $s | "  \($c.name): ready=\($s.ready // false), restart=\($s.restartCount // 0), state=" + (($s.state // {}) | keys | join(",")) + ", ports=" + ([$c.ports[]? | ((.name // "unnamed") + ":" + (.containerPort|tostring))] | if length==0 then "-" else join(",") end)] | if length==0 then "없음" else join("\n") end)' <<<"$POD_JSON"; fi`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 같은 Pod UID의 Event에서 `reason=Killing` 또는 message의 `Killing`이 반복되거나 컨테이너 종료·재시작과 함께 보이는 경우 |
| 적용 | `AUTO_READY=true`, Event의 관련 Pod UID, container 종료 시각과 Event 시각을 비교할 수 있는 경우 |
| 제외 | `reason=Evicted`가 직접 확인되면 [[12. Pod STATUS가 Evicted인 경우]], probe가 선행하면 [[19. Pod readiness probe가 실패하는 경우]], [[20. Pod liveness probe가 실패하는 경우]], [[21. Pod startup probe가 실패하는 경우]]로 이동한다. Terminating 자체가 멈춘 경우는 [[15. Pod가 Terminating에서 멈춘 경우]]로 이관한다. |

검색 문자열: `Killing`, `Killing container`, `Unhealthy`, `Container failed liveness probe`, `Startup probe failed`, `OOMKilled`, `Evicted`, `deletionTimestamp`, `rollout`, `preStop`, `FailedPreStopHook`, `SIGTERM`, `SIGKILL`, `terminationGracePeriodSeconds`.

`Killing`은 원인이 아니라 kubelet이 종료를 수행했다는 결과다. `readiness` 실패만으로 kill을 설명하지 않으며, `Last State.reason`·exit code·signal은 Event reason과 별도로 판정한다. StatefulSet quorum, DaemonSet node maintenance, Job 재실행은 owner별 승인 절차로 판단한다. 상위 경로는 [[00. Kubernetes 운영 런북 허브]], 기준은 [[01. Kubernetes 1.26 런북 작성 기준]]이다.

## 최초 확인

`AUTO_READY=true`일 때만 아래 읽기 명령을 같은 Bash에서 실행한다. `get`과 `describe`의 성공은 API가 객체를 읽었다는 범위만 보장하며, 원인·현재 listener·실제 서비스 정상은 보장하지 않는다.

**Pod 상태 확인 — 아래 한 줄 전체를 복사**

`FIRST_CHECK_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o wide && kubectl describe pod "$POD" -n "$NS"; then FIRST_CHECK_READY=true; printf 'FIRST_CHECK_READY=true pod=%s uid=%s observed=%s\n' "$POD" "$POD_UID" "$OBSERVED_AT"; else printf '%s\n' '중단: Pod get 또는 describe 실패. Event와 상세 분기를 사용하지 않는다.' >&2; fi`

볼 것: `get`의 `STATUS`, `READY`, `RESTARTS`, `NODE`, `AGE`, UID. `describe`의 container별 `State`, `Last State`, `Reason`, `Exit Code`, `Signal`, `Restart Count`, Conditions와 첫 `Killing`·`Unhealthy` message. 이름이 같은 다른 Pod의 결과와 섞지 않는다.

**현재 Pod UID의 Event 한 번 수집 — 아래 한 줄 전체를 복사**

`EVENT_API_OK=false; EVENT_READY=false; unset EVENT_JSON; if [ "$FIRST_CHECK_READY" != true ]; then printf '%s\n' '중단: FIRST_CHECK_READY가 아니다.' >&2; elif EVENT_JSON="$(kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID" --sort-by=.metadata.creationTimestamp -o json)"; then if jq -e '.items | type == "array"' <<<"$EVENT_JSON" >/dev/null; then EVENT_API_OK=true; if jq -e '.items | length > 0' <<<"$EVENT_JSON" >/dev/null; then jq -r '.items[] | "=== Pod Event ===\nEvent UID: \(.metadata.uid)\n관련 Pod UID: \(.involvedObject.uid)\n생성 시각: \(.metadata.creationTimestamp // "-")\n최초 시각: \(.firstTimestamp // "-")\n마지막 시각: \(.lastTimestamp // "-")\nEvent 시각: \(.eventTime // "-")\nSeries 마지막 시각: \(.series.lastObservedTime // "-")\nType: \(.type // "-")\nReason: \(.reason // "-")\nCount: \(.count // 0)\nMessage: \(.message // "-")\n"' <<<"$EVENT_JSON"; EVENT_READY=true; printf 'EVENT_READY=true pod_uid=%s\n' "$POD_UID"; else printf '중단: 현재 Pod UID의 Event가 비어 있다. 정상·오류 없음으로 해석하지 말고 Event TTL·권한·관측 범위를 확인한다.\n' >&2; unset EVENT_JSON; fi; else printf '%s\n' '중단: Events API data가 배열이 아니다.' >&2; unset EVENT_JSON; fi; else printf '%s\n' '중단: Event API 조회 실패. Event 부재와 조회 실패를 구분하고 다음 단계로 진행하지 않는다.' >&2; unset EVENT_JSON; fi`

`EVENT_READY=true`인 출력에서 `EVENT UID`, 관련 Pod UID, 실제로 채워진 시각과 `Killing`·`Unhealthy` message를 보존한다. 원인 시각은 `eventTime`, 없으면 `series.lastObservedTime`, `lastTimestamp`, `firstTimestamp` 순으로 선택하고 `creationTimestamp`는 정렬용으로만 쓴다. Event가 비어 있으면 `Killing`이 없다고 결론내리지 않는다.

**같은 UID·시각의 Killing 직접 증거 gate — 아래 한 줄 전체를 복사**

`KILLING_READY=false; KILLING_TIME_READY=false; KILLING_EVENT_CANDIDATE_COUNT=0; unset KILLING_EVENT_UID KILLING_EVENT_MESSAGE KILLING_TIME KILLING_EPOCH KILLING_EVENT_CANDIDATES; if [ "$EVENT_READY" != true ]; then printf '%s\n' '중단: EVENT_READY가 아니다.' >&2; elif KILLING_EVENT_CANDIDATES="$(jq -c --arg uid "$POD_UID" '[.items[] | select(.involvedObject.uid==$uid and (.reason=="Killing" or ((.message // "") | test("(^|[^A-Za-z])Killing([^A-Za-z]|$)"; "i")))) | select((.message // "") | (type == "string" and length > 0)) | ([.eventTime,.series.lastObservedTime,.lastTimestamp,.firstTimestamp] | map(select(type=="string" and length>0)) | .[0]) as $time | select($time != null) | {event_uid:.metadata.uid,message:.message,killing_time:$time}]' <<<"$EVENT_JSON")" && KILLING_EVENT_CANDIDATE_COUNT="$(jq -er 'length' <<<"$KILLING_EVENT_CANDIDATES")" && [ "$KILLING_EVENT_CANDIDATE_COUNT" -eq 1 ] && KILLING_EVENT_UID="$(jq -er '.[0].event_uid' <<<"$KILLING_EVENT_CANDIDATES")" && KILLING_EVENT_MESSAGE="$(jq -er '.[0].message' <<<"$KILLING_EVENT_CANDIDATES")" && KILLING_TIME="$(jq -er '.[0].killing_time' <<<"$KILLING_EVENT_CANDIDATES")" && KILLING_EPOCH="$(date -u -d "$KILLING_TIME" +%s 2>/dev/null)"; then KILLING_READY=true; KILLING_TIME_READY=true; printf 'KILLING_READY=true KILLING_TIME_READY=true canonical_event_count=%s killing_event_uid=%s pod_uid=%s killing_time=%s killing_epoch=%s message=%s\n' "$KILLING_EVENT_CANDIDATE_COUNT" "$KILLING_EVENT_UID" "$POD_UID" "$KILLING_TIME" "$KILLING_EPOCH" "$KILLING_EVENT_MESSAGE"; else printf '중단: 같은 Pod UID의 canonical Killing Event 후보가 정확히 하나가 아니거나 UID/message/time/epoch 파싱에 실패했다 count=%s. 다른 Event를 혼합하지 않는다.\n' "$KILLING_EVENT_CANDIDATE_COUNT" >&2; unset KILLING_EVENT_UID KILLING_EVENT_MESSAGE KILLING_TIME KILLING_EPOCH; fi`

`KILLING_READY=true`는 Event의 관련 UID가 현재 `$POD_UID`와 같고 `reason=Killing` 또는 message에 직접 `Killing`이 있으며 선택 가능한 Event 시각이 있다는 뜻이다. 다른 UID·동명 Pod·시각 없는 Event는 원인 근거로 사용하지 않는다.

**Killing 시각 형식 gate — 아래 한 줄 전체를 복사**

`if [ "$KILLING_READY" != true ] || [ "$KILLING_TIME_READY" != true ] || [ -z "${KILLING_EPOCH:-}" ]; then KILLING_READY=false; KILLING_TIME_READY=false; printf '중단: KILLING_TIME canonical epoch가 등록되지 않았다 value=%s\n' "${KILLING_TIME:--}" >&2; else printf 'KILLING_TIME_READY=true killing_time=%s canonical_event_epoch=%s\n' "$KILLING_TIME" "$KILLING_EPOCH"; fi`

`if [ "$KILLING_READY" = true ] && [ "$KILLING_TIME_READY" = true ] && [ -n "${KILLING_EPOCH:-}" ]; then POD_API_GATE_ENABLED=true; else POD_API_GATE_ENABLED=false; fi`

### container·시간·node journal 값 등록

Event와 대상별 출력에서 선택한 값만 다음 명령으로 한 번 등록한다. `CONTAINER`는 여러 container 후보 중 실제 종료 상태를 가진 이름이며 임의로 첫 후보를 고르지 않는다. `START_RFC3339`는 canonical Killing Event보다 앞선 UTC 시각, journal 시간은 실제 node 시간 형식이다. rollout evidence의 허용 관측창은 `max(START_RFC3339, START_JOURNAL) <= Killing Event <= END_JOURNAL`이고 승인 시각은 Killing Event보다 늦을 수 없다. 이 시간축이 맞지 않으면 별도 owner 증거로 이관한다.

**운영자 선택값 설정 — 필요한 분기에 들어가기 전에 같은 Bash에서 한 번 실행**

`CONTAINER='PASTE_CONTAINER_HERE'; START_RFC3339='PASTE_START_RFC3339_HERE'; START_JOURNAL='PASTE_START_JOURNAL_HERE'; END_JOURNAL='PASTE_END_JOURNAL_HERE'; KUBELET_SERVICE='PASTE_KUBELET_SERVICE_HERE'; SELECTION_READY=false; CONTAINER_RELATION_READY=false; LOG_TIME_READY=false; JOURNAL_TIME_READY=false; if [ "$KILLING_READY" != true ]; then printf '%s\n' '중단: KILLING_READY가 아니다.' >&2; elif [ -z "$CONTAINER" ]; then printf '%s\n' '중단: CONTAINER를 선택한다.' >&2; elif ! `NODE_REMOTE_READY=true`는 승인된 `NODE_HOST`에서 원격 `hostname` 또는 short hostname이 Kubernetes `$NODE`와 일치하고, non-interactive sudo와 실제 kubelet systemd unit이 확인됐다는 뜻이다. node journal 명령은 이 gate가 아니면 실행하지 않는다. `NODE_HOST`는 Pod 주소·API server 주소·container runtime socket이 아니다.

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| `Unhealthy`와 liveness/startup 실패가 `Killing`보다 앞섬 | probe 종류·target과 Last State 시각 | application 로그 → kubelet/runtime | [[#1. Probe kill\|probe kill 진단]] |
| `OOMKilled` 또는 종료 코드 `137` | container memory limit과 종료 시각 | cgroup OOM → node pressure·kernel | [[#2. Container cgroup OOM\|container OOM 진단]] |
| `Evicted`, `MemoryPressure`, `DiskPressure`, `PIDPressure` | Pod reason/message와 node condition | kubelet eviction → Linux 자원 | [[#3. Node-pressure eviction\|node pressure 진단]] |
| 승인된 revision 변경과 `Killing` | owner revision·rollout 시각 | controller → SIGTERM drain | [[#4. Rollout·명시적 삭제 시간축\|rollout 시간축]] |
| `deletionTimestamp`만 있고 승인된 rollout이 없음 | 삭제 근거와 controller/audit 기록 | 삭제 주체 → SIGTERM 처리 | [[#4. Rollout·명시적 삭제 시간축\|삭제 시간축]] |
| `preStop`, `FailedPreStopHook`, grace 만료 뒤 `Killing` | lifecycle·grace와 shutdown 로그 | kubelet → runtime → PID 1 | [[#6. preStop 또는 grace expiry\|preStop·grace 진단]] |
| 선행 원인이 없거나 UID·시간이 맞지 않음 | Event 보존과 Last State 시각 | kubelet/runtime/Linux/controller 이관 | [[#7. 시간축 또는 UID가 맞지 않는 경우\|증거 불일치 진단]] |

이 표는 경로 선택용이며 상태 변경을 승인하지 않는다. `OOMKilled`와 node eviction은 서로 다른 원인 계층으로 분리하고, 어느 한 상태가 `Running`, `Ready`, HTTP 200 또는 실제 기능 정상임을 보장하지 않는다는 점을 유지한다.

## 관측 이후 장애 파이프라인

### 1. Probe kill

진입 증거는 같은 Pod UID의 `Killing`보다 앞선 `Unhealthy`가 liveness 또는 startup 실패를 가리키고 Last State 종료 시각과 맞는 경우다. readiness 실패만 있으면 kill 원인이 아니다. startup 성공 전이면 [[21. Pod startup probe가 실패하는 경우]]로 연결한다.

연결 경로: `실행 host → kubectl client/API server → node kubelet → container runtime log stream → container process/application`. 로그 stream이 준비됐다는 것은 대상 Pod UID·container의 로그 전달만 확인하며 probe target의 실제 listener·protocol·외부 dependency 정상은 보장하지 않는다.

**probe 설정 확인 — 아래 한 줄 전체를 복사**

`if [ "$KILLING_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$POD_IDENTITY_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, SELECTION_READY 또는 POD_IDENTITY_READY가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .spec.containers[*]}{.name}{" startup="}{.startupProbe}{" liveness="}{.livenessProbe}{" readiness="}{.readinessProbe}{"\n"}{end}'; fi`

성공 gate는 선택한 container의 probe 종류·path 또는 command·port·scheme이 `describe`와 승인 manifest에서 확인되는 것이다. 이 출력은 probe 선언만 확인하며 실제 process listener, network path, application 의존성 정상은 보장하지 않는다.

**application 로그 확인 — 아래 한 줄 전체를 복사**

`if [ "$KILLING_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$LOG_TIME_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, SELECTION_READY 또는 LOG_TIME_READY가 아니다.' >&2; else run_logs_filter probe "$POD" "$NS" "$CONTAINER" "$START_RFC3339" false 200 'panic|fatal|error|timeout|refused|health|probe|deadlock|overload'; fi`

예상 예: `ERROR health endpoint timeout` 또는 `panic`이 probe 실패 직전에 보이면 app 초기화·부하·의존성 경로다. 필터가 비어도 오류 부재가 아니므로 같은 시간 범위의 비식별화된 tail만 재확인한다. `restartCount>=1` 또는 `Last State.terminated`가 확인된 경우에만 다음 previous 로그를 실행한다.

`if [ "$KILLING_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$LOG_TIME_READY" != true ] || [ "$PREVIOUS_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, SELECTION_READY, LOG_TIME_READY 또는 PREVIOUS_READY가 아니다.' >&2; else run_logs_filter probe-previous "$POD" "$NS" "$CONTAINER" "$START_RFC3339" true 200 'panic|fatal|error|timeout|refused|health|probe|deadlock|overload'; fi`

`previous` 인스턴스가 없다는 오류는 probe 원인을 뜻하지 않는다. 결정적 application 오류가 없으면 kubelet의 probe 실행 지연·timeout 증거로 이동한다.

**kubelet journal 확인 — node 권한과 unit 확인 후 아래 한 줄 전체를 복사**

`if [ "$KILLING_READY" != true ] || [ "$JOURNAL_TIME_READY" != true ] || [ "$NODE_REMOTE_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, JOURNAL_TIME_READY 또는 NODE_REMOTE_READY가 아니다.' >&2; else run_remote_journal unit "$KUBELET_SERVICE" "$START_JOURNAL" "$END_JOURNAL" "$POD_UID|$POD|probe|unhealthy|killing|timeout|refused"; fi`

`failed liveness probe` 뒤 `Killing container`가 같은 Pod UID·시각이면 kubelet이 probe 결과를 실행한 경로를 지지한다. kubelet에 probe 오류가 없고 runtime 종료만 있으면 CRI/runtime owner로, 여러 Pod가 같은 node에서 같은 시각 실패하면 node CPU·network namespace owner로 이관한다. target path·port·scheme이 틀려도 probe를 무조건 완화하지 말고 승인 manifest의 변경으로 닫는다.

### 2. Container cgroup OOM

진입 증거는 동일 container의 `Last State.reason=OOMKilled`와 종료 시각이며, 종료 코드 `137`만으로 OOM을 확정하지 않는다. 아래 명령은 resource field와 node condition을 분리해 읽는다.

연결 경로: `실행 host → kubectl client/API server → node kubelet/runtime → container cgroup·previous log → kernel OOM 기록`. API 또는 log stream 한 hop의 성공은 cgroup kill 원인과 application 정상의 증거가 아니다.

**container·node 자원 확인 — 아래 한 줄 전체를 복사**

`if [ "$KILLING_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$NODE_READY" != true ] || [ "$POD_IDENTITY_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, SELECTION_READY, NODE_READY 또는 POD_IDENTITY_READY가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o jsonpath='{range .spec.containers[*]}{.name}{" requests="}{.resources.requests}{" limits="}{.resources.limits}{"\n"}{end}{range .status.containerStatuses[*]}{.name}{" lastReason="}{.lastState.terminated.reason}{" exit="}{.lastState.terminated.exitCode}{" finished="}{.lastState.terminated.finishedAt}{" restart="}{.restartCount}{"\n"}{end}' && kubectl get node "$NODE" -o jsonpath='{range .status.conditions[?(@.type=="MemoryPressure")]}MemoryPressure={.status} reason={.reason} message={.message}{"\n"}{end}'; fi`

성공 gate는 선택한 container의 `limits.memory`, Last State와 종료 시각, node `MemoryPressure`가 한 사건의 시간축에 놓이는 것이다. `MemoryPressure=True`나 여러 Pod 종료·kubelet eviction이 맞으면 node pressure 경로로 이동하며 단일 limit만 올리지 않는다. node condition 현재값 `False`는 과거 원인이 사라졌다는 보장이 아니다.

**previous 로그 확인 — 아래 한 줄 전체를 복사**

`if [ "$KILLING_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$LOG_TIME_READY" != true ] || [ "$PREVIOUS_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, SELECTION_READY, LOG_TIME_READY 또는 PREVIOUS_READY가 아니다.' >&2; else run_logs_filter oom-previous "$POD" "$NS" "$CONTAINER" "$START_RFC3339" true 200 'oom|out of memory|killed|memory|allocation'; fi`

로그가 비어도 OOM 부재가 아니다. Last State·cgroup·kernel evidence가 맞지 않으면 `Killing`만 확정하고 runtime/Linux owner에게 이관한다.

**kernel·kubelet journal 확인 — 권한 전제 후 아래 한 줄 전체를 복사**

`KERNEL_JOURNAL_RC=0; KUBELET_JOURNAL_RC=0; JOURNAL_EVIDENCE_READY=false; if [ "$KILLING_READY" != true ] || [ "$JOURNAL_TIME_READY" != true ] || [ "$NODE_REMOTE_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, JOURNAL_TIME_READY 또는 NODE_REMOTE_READY가 아니다.' >&2; false; else run_remote_journal kernel - "$START_JOURNAL" "$END_JOURNAL" "$POD_UID|$POD|out of memory|killed process|oom|memcg|memory cgroup"; KERNEL_JOURNAL_RC=$?; run_remote_journal unit "$KUBELET_SERVICE" "$START_JOURNAL" "$END_JOURNAL" "$POD_UID|oom|memory|evict|pressure"; KUBELET_JOURNAL_RC=$?; if [ "$KERNEL_JOURNAL_RC" -ne 0 ] || [ "$KUBELET_JOURNAL_RC" -ne 0 ]; then printf '중단: 연속 remote journal 실패 kernel_rc=%s kubelet_rc=%s\n' "$KERNEL_JOURNAL_RC" "$KUBELET_JOURNAL_RC" >&2; false; else JOURNAL_EVIDENCE_READY=true; printf 'JOURNAL_EVIDENCE_READY=true kernel_rc=%s kubelet_rc=%s\n' "$KERNEL_JOURNAL_RC" "$KUBELET_JOURNAL_RC"; true; fi; fi`

`Out of memory: Killed process`는 kernel 범위, `task_memcg` 또는 대상 cgroup과 종료 시각의 일치는 container 범위를 지지한다. cgroup이 확인되지 않으면 실제 cgroup 경로를 Linux 담당자에게 이관하고 무근거 재시작을 하지 않는다.

### 3. Node-pressure eviction

진입 증거는 `status.reason=Evicted`, eviction message 또는 `MemoryPressure`·`DiskPressure`·`PIDPressure`가 `Killing`보다 앞선 경우다. Pod cgroup OOM과 node-level eviction을 합치지 않는다.

연결 경로: `실행 host → kubectl client/API server → 대상 node kubelet eviction manager → Linux resource/filesystem/PID 계층`. 현재 node condition 조회 성공은 과거 eviction 시각이나 Pod replacement 기능을 보장하지 않는다.

**Pod·node·kubelet evidence 확인 — 권한 전제 후 아래 한 줄 전체를 복사**

`if [ "$KILLING_READY" != true ] || [ "$JOURNAL_TIME_READY" != true ] || [ "$NODE_REMOTE_READY" != true ] || [ "$POD_IDENTITY_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, JOURNAL_TIME_READY, NODE_REMOTE_READY 또는 POD_IDENTITY_READY가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o jsonpath='{.status.reason}{" message="}{.status.message}{" node="}{.spec.nodeName}{" qos="}{.status.qosClass}{"\n"}' && kubectl describe node "$NODE" && run_remote_journal unit "$KUBELET_SERVICE" "$START_JOURNAL" "$END_JOURNAL" "$POD_UID|evict|eviction|memory.available|nodefs|imagefs|pid.available|pressure"; fi`

예상 예: `eviction manager: must evict pod(s)`와 `nodefs.available`가 Pod message와 같은 시각이면 kubelet eviction 경로다. `nodefs/imagefs`는 filesystem·runtime log/image, `pid.available`는 PID 고갈, `memory.available`는 node memory로 이동한다. 출력이 비거나 현재 pressure가 `False`여도 과거 원인 부재로 단정하지 않는다.

### 4. Rollout·명시적 삭제 시간축

진입 증거는 `deletionTimestamp`가 `KillingTime`보다 먼저이거나 같은 시간 정밀도에서 먼저이며, rollout 승인·owner revision 또는 삭제 기록과 같은 시간축을 갖는 경우다. Event 시간이 비어 있거나 정밀도가 맞지 않으면 순서를 확정하지 않는다. 4·5 분기는 아래 Pod·owner 정보를 한 번 수집해 재사용한다.

연결 경로: `실행 host → kubectl client/API server → Pod metadata → controller/audit record → kubelet termination path → container process`. API에서 `deletionTimestamp`를 읽어도 삭제 주체·승인·SIGTERM 처리 완료는 보장하지 않는다.

**Pod 삭제·owner 확인 — 아래 한 줄 전체를 복사**

`if [ "$FIRST_CHECK_READY" != true ] || [ "$POD_IDENTITY_READY" != true ]; then printf '%s\n' '중단: FIRST_CHECK_READY 또는 POD_IDENTITY_READY가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o jsonpath='uid={.metadata.uid}{" deletionTimestamp="}{.metadata.deletionTimestamp}{" created="}{.metadata.creationTimestamp}{" owner="}{.metadata.ownerReferences[*].kind}{"/"}{.metadata.ownerReferences[*].name}{" labels="}{.metadata.labels}{"\n"}'; fi`

**controller owner 확인 — owner UID·kind·name이 모두 있을 때 아래 한 줄 전체를 복사**

`if [ "$OWNER_READY" != true ]; then printf '%s\n' 'owner가 없어 standalone Pod 경로로 이관한다.' >&2; else kubectl get "$OWNER_KIND" "$OWNER_NAME" -n "$NS" -o jsonpath='kind={.kind}{" name="}{.metadata.name}{" uid="}{.metadata.uid}{" created="}{.metadata.creationTimestamp}{" generation="}{.metadata.generation}{" observed="}{.status.observedGeneration}{" deployment-revision="}{.metadata.annotations.deployment\.kubernetes\.io/revision}{" current-revision="}{.status.currentRevision}{" update-revision="}{.status.updateRevision}{"\n"}{range .status.conditions[*]}condition={.type}{" last-update="}{.lastUpdateTime}{" last-transition="}{.lastTransitionTime}{"\n"}{end}'; fi`

owner API 성공은 owner object를 읽었다는 뜻이지 승인된 rollout이나 삭제 주체를 확인했다는 뜻이 아니다. owner kind가 revision field를 제공하지 않으면 빈 출력은 revision evidence가 아니다.

#### 4-1. Approved rollout

운영자가 승인된 변경·배포·감사 기록에서 확인한 시각을 선택한다. owner `creationTimestamp`나 condition 시각을 승인 시각으로 대신하지 않는다.

`ROLLOUT_READY=false; ROLLOUT_TIME_READY=false; ROLLOUT_CHAIN_READY=false; ROLLOUT_EVIDENCE_READY=false; printf '%s\n' 'ROLLOUT_READY=false ROLLOUT_TIME_READY=false ROLLOUT_CHAIN_READY=false ROLLOUT_EVIDENCE_READY=false; approval artifact·immutable change ID 조회 계약이 없어 문자열 승인 ID/annotation으로 rollout 원인을 확정하지 않는다. revision/change record와 같은 immutable ID, Pod/Event 시간축은 owner/audit에서 외부 이관한다.' >&2; false`

이 런북은 실제 approval artifact와 Deployment revision을 동일 immutable ID로 조회·검증할 API/문서 계약이 없으므로 rollout 원인을 자동 확정하지 않는다. 문자열 승인 ID, Deployment annotation, Pod/Event 시간축만으로 `ROLLOUT_EVIDENCE_READY`를 true로 만들지 않고 `ROLLOUT_*` state gate를 false로 유지한다. owner/audit가 동일 immutable ID의 revision/change record와 직접 시간축을 외부 evidence로 이관한 경우에만 별도 판단한다.

`ROLLOUT_EVIDENCE_READY=false; printf '%s\n' '중단: approval artifact·immutable change ID 외부 evidence가 없어 rollout application log로 원인을 확정하지 않는다. owner/audit로 이관한다.' >&2; false`

`received SIGTERM` 뒤 drain·flush 완료면 승인된 rollout의 app 종료 경로다. 로그가 없거나 drain timeout이면 6절로 이동한다. rollout이 직접 근거인 경우에도 새 Pod UID·revision·replica·endpoint를 확인하고 개별 Pod 삭제로 가속하지 않는다.

#### 4-2. Explicit deletion

`deletionTimestamp`가 `KillingTime`보다 먼저인데 owner revision 변경이나 승인된 rollout이 없으면 명시적 삭제 경로다. controller 기록·배포 기록·감사 pipeline에서 삭제 근거와 실행자를 확인하고 Event message만으로 실행자를 특정하지 않는다. 근거가 없으면 controller/audit owner로 이관하며 Pod를 다시 삭제하거나 rollout하지 않는다. SIGTERM 이후 drain이 끝나지 않으면 6절로 이동한다.

### 5. Owner별 영향 확인

진입 증거는 owner chain과 승인된 revision이 확인된 경우다. Pod의 직접 owner가 ReplicaSet이면 Deployment 이름을 추측하지 않고 owner chain·승인 기록에서 확인한다.

연결 경로: `실행 host → kubectl client/API server → owner controller → replacement Pod → Service endpoint → 실제 요청/application`. rollout status 성공은 실제 요청과 핵심 기능 정상, 다른 owner·quorum·Job 산출물을 보장하지 않는다.

**Deployment 확인값 설정 — Deployment owner chain을 확인한 경우에만 아래 한 줄 전체를 복사**

`DEPLOYMENT=''; DEPLOYMENT_READY=false; printf '%s\n' 'DEPLOYMENT_READY=false; immutable approval/revision external evidence 계약이 없어 Deployment rollout 원인·normalization 경로를 자동으로 열지 않는다. owner/audit에게 실제 Deployment revision/change record와 동일 immutable ID를 요청한다.' >&2; false`

**Pod→ReplicaSet→Deployment kind/name/UID/selector chain gate — 아래 한 줄 전체를 복사**

`ROLLOUT_CHAIN_READY=false; RS_UID=''; RS_OWNER_KIND=''; RS_OWNER_NAME=''; RS_OWNER_UID=''; DEPLOYMENT_UID=''; unset RS_JSON DEPLOYMENT_JSON; if [ "$POD_IDENTITY_READY" != true ] || [ "$OWNER_READY" != true ] || [ "$ROLLOUT_READY" != true ]; then printf '%s\n' '중단: POD_IDENTITY_READY, OWNER_READY 또는 strict rollout approval gate가 아니다.' >&2; false; elif [ "$OWNER_KIND" != ReplicaSet ]; then printf '중단: Pod direct owner가 ReplicaSet이 아니다 kind=%s\n' "$OWNER_KIND" >&2; false; elif RS_JSON="$(kubectl get replicaset "$OWNER_NAME" -n "$NS" -o json)" && RS_UID="$(jq -er '.metadata.uid' <<<"$RS_JSON")" && RS_OWNER_KIND="$(jq -er '[.metadata.ownerReferences[]? | select(.controller==true)][0].kind' <<<"$RS_JSON")" && RS_OWNER_NAME="$(jq -er '[.metadata.ownerReferences[]? | select(.controller==true)][0].name' <<<"$RS_JSON")" && RS_OWNER_UID="$(jq -er '[.metadata.ownerReferences[]? | select(.controller==true)][0].uid' <<<"$RS_JSON")" && [ "$RS_UID" = "$OWNER_UID" ] && [ "$RS_OWNER_KIND" = Deployment ] && [ "$RS_OWNER_NAME" = "$DEPLOYMENT" ] && DEPLOYMENT_JSON="$(kubectl get deployment "$DEPLOYMENT" -n "$NS" -o json)" && DEPLOYMENT_UID="$(jq -er '.metadata.uid' <<<"$DEPLOYMENT_JSON")" && jq -e -n --arg pod_uid "$POD_UID" --arg owner_kind "$OWNER_KIND" --arg owner_name "$OWNER_NAME" --arg owner_uid "$OWNER_UID" --arg deployment "$DEPLOYMENT" --arg rs_owner_uid "$RS_OWNER_UID" --argjson pod "$POD_JSON" --argjson rs "$RS_JSON" --argjson dep "$DEPLOYMENT_JSON" 'def normalize_selector($s): {matchLabels:($s.matchLabels // {}),matchExpressions:(($s.matchExpressions // []) | sort_by([.key,.operator,((.values // []) | join(","))]))}; def selector_matches($labels;$s): (([($s.matchLabels // {}) | to_entries[] | ($labels[.key] == .value)] | all) and ([($s.matchExpressions // [])[] | if .operator == "In" then (($labels[.key] // null) as $v | ($v != null and ((.values // []) | index($v) != null))) elif .operator == "NotIn" then (($labels[.key] // null) as $v | ($v == null or ((.values // []) | index($v) == null))) elif .operator == "Exists" then ($labels[.key] != null) elif .operator == "DoesNotExist" then ($labels[.key] == null) else false end] | all)); ([ $rs.metadata.ownerReferences[]? | select(.controller==true) ][0]) as $rs_owner | ($pod.kind == "Pod" and $rs.kind == "ReplicaSet" and $dep.kind == "Deployment" and $pod_uid == $pod.metadata.uid and $owner_kind == "ReplicaSet" and $rs.metadata.name == $owner_name and $rs.metadata.uid == $owner_uid and $rs_owner.kind == "Deployment" and $rs_owner.name == $deployment and $rs_owner.uid == $rs_owner_uid and $dep.metadata.name == $deployment and $dep.metadata.uid == $rs_owner_uid and normalize_selector($rs.spec.selector) == normalize_selector($dep.spec.selector) and selector_matches(($pod.metadata.labels // {}); $rs.spec.selector))' >/dev/null; then DEPLOYMENT_READY=true; ROLLOUT_CHAIN_READY=true; printf 'ROLLOUT_CHAIN_READY=true pod=%s/%s pod_uid=%s rs=%s/%s rs_uid=%s deployment=%s/%s deployment_uid=%s selector_chain=true approval_id=%s\n' "$NS" "$POD" "$POD_UID" "$NS" "$OWNER_NAME" "$RS_UID" "$NS" "$DEPLOYMENT" "$DEPLOYMENT_UID" "$ROLLOUT_APPROVAL_ID"; true; else printf '중단: Pod→ReplicaSet→Deployment kind/name/UID/selector chain mismatch 또는 API/jq 검증 실패. rollout evidence와 normalization을 열지 않는다.\n' >&2; false; fi`

**Deployment revision/change annotation·Pod creation/deletion·Event 시간축 직접 근거 gate — 아래 한 줄 전체를 복사**

`ROLLOUT_EVIDENCE_READY=false; printf '%s\n' '중단: 실제 approval artifact와 Deployment revision을 동일 immutable ID로 연결하는 API/문서 계약이 없다. annotation·Pod/Event 시간축·문자열 ID만으로 rollout 원인을 확정하지 않고 owner/audit 외부 evidence로 이관한다.' >&2; false`

`NORMALIZATION_READY=false; printf '%s\n' '중단: immutable approval/revision external evidence 계약이 없어 rollout normalization을 자동 실행하지 않는다. owner/audit evidence로 이관한다.' >&2; false`

`rollout status` timeout 또는 non-zero는 rollout 성공이 아니다. StatefulSet은 ordinal별 UID·Ready·PVC·quorum·leader·`controller-revision-hash`를 확인하고 일반 Deployment rollout을 적용하지 않는다. DaemonSet은 node별 desired/current/ready와 maintenance를 비교한다. Job/CronJob은 completion, failed, active, 외부 side effect와 산출물을 확인하며 멱등성이 입증되지 않으면 재실행·삭제하지 않는다. `Running`이나 `Ready`만으로 서비스 기능 정상은 보장되지 않는다.

### 6. preStop 또는 grace expiry

진입 증거는 `deletionTimestamp`가 있고 `preStop`, `FailedPreStopHook`, grace 만료 또는 `SIGKILL` 단서가 종료 순서에 있는 경우다. preStop은 삭제를 시작한 주체가 아니라 종료 중 실행되는 hook이다. 유효 grace는 삭제 시점의 `deletionGracePeriodSeconds`가 있으면 그것을, 없으면 Pod spec의 `terminationGracePeriodSeconds`를 기준으로 계산하되 계산만으로 원인을 확정하지 않는다.

연결 경로: `실행 host → API server의 Pod metadata → node kubelet → runtime termination stream → PID 1/preStop → application dependency`. kubelet Event나 application log 한 hop의 성공은 hook 완료·grace 내 종료·data flush를 보장하지 않는다.

**lifecycle·shutdown 확인 — 아래 한 줄 전체를 복사**

`if [ "$KILLING_READY" != true ] || [ "$SELECTION_READY" != true ] || [ "$LOG_TIME_READY" != true ] || [ "$POD_IDENTITY_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, SELECTION_READY, LOG_TIME_READY 또는 POD_IDENTITY_READY가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o jsonpath='{.metadata.deletionTimestamp}{" grace="}{.spec.terminationGracePeriodSeconds}{" graceAtDelete="}{.metadata.deletionGracePeriodSeconds}{"\n"}{range .spec.containers[*]}{.name}{" lifecycle="}{.lifecycle}{"\n"}{end}' && run_logs_filter termination "$POD" "$NS" "$CONTAINER" "$START_RFC3339" false 200 'shutdown|sigterm|sigkill|drain|flush|prestop|hook|timeout|stuck'; fi`

`if [ "$KILLING_READY" != true ] || [ "$JOURNAL_TIME_READY" != true ] || [ "$NODE_REMOTE_READY" != true ]; then printf '%s\n' '중단: KILLING_READY, JOURNAL_TIME_READY 또는 NODE_REMOTE_READY가 아니다.' >&2; else run_remote_journal unit "$KUBELET_SERVICE" "$START_JOURNAL" "$END_JOURNAL" "$POD_UID|prestop|grace|termination|killing|kill|timeout"; fi`

`FailedPreStopHook`, hook timeout 또는 `Killing` 뒤 `SIGKILL`이 같은 Pod UID·시간이면 kubelet grace countdown과 hook·runtime·PID 1 signal 처리를 대조한다. app이 외부 DB·queue drain을 기다리면 dependency owner로, runtime이 TERM 후 KILL을 기록하면 runtime/Linux owner로 이관한다. grace를 무조건 늘리거나 force delete하지 않는다.

### 7. 시간축 또는 UID가 맞지 않는 경우

Event와 Last State가 다른 UID를 가리키거나 probe·OOM·eviction·rollout/deletion·preStop 중 선행 원인이 없으면 `Killing`만 확정하고 원인을 미확정으로 남긴다. Event 보존 한계와 kubelet/runtime/Linux/controller evidence를 담당자별로 수집하며 상태 변경을 보류한다. 빈 Event는 오류 없음이 아니며, 현재 `Running`은 과거 종료 원인을 지우지 않는다.

**UID·현재 상태 재확인 — 아래 한 줄 전체를 복사**

`if [ "$FIRST_CHECK_READY" != true ] || [ "$POD_IDENTITY_READY" != true ]; then printf '%s\n' '중단: FIRST_CHECK_READY 또는 POD_IDENTITY_READY가 아니다.' >&2; else kubectl get pod "$POD" -n "$NS" -o jsonpath='uid={.metadata.uid}{" phase="}{.status.phase}{" reason="}{.status.reason}{" node="}{.spec.nodeName}{" deletion="}{.metadata.deletionTimestamp}{" lastState="}{.status.containerStatuses[*].lastState.terminated.reason}{" finished="}{.status.containerStatuses[*].lastState.terminated.finishedAt}{"\n"}'; fi`

성공 gate는 현재 UID가 `$POD_UID`와 같고 현재 상태·Last State 시각이 보존되는 것이다. 출력이 비거나 UID가 다르면 현재 이름의 새 Pod와 과거 Event가 섞인 것이므로 원인을 확정하지 않고 controller·kubelet/runtime/Linux 담당자에게 같은 UID·UTC 시각 evidence를 이관한다.

## 복구 gate와 상태 변경 계약

상태 변경은 진단 명령과 분리한다. 변경 전 승인된 namespace, Pod UID, node, owner kind/name/UID, `KillingTime`, 직접 원인, replica·traffic·data 영향, 실행 권한, 증거 보존을 다시 대조한다.

- **Trigger:** probe, cgroup OOM, node eviction, 승인 rollout, 명시적 삭제, preStop/grace 중 하나가 같은 UID·시각의 직접 evidence로 연결됐다.
- **권한·영향:** probe와 workload manifest는 owner, node·runtime는 플랫폼 관리자, 서비스·Job·quorum·data 영향은 해당 owner 승인이다. 다른 namespace와 tenant의 영향도 평가한다.
- **기대 효과·비보장:** 승인된 manifest rollout은 변경된 probe 또는 resource 정책을 적용할 뿐 node pressure·runtime 장애·외부 dependency 정상과 실제 기능 성공을 보장하지 않는다.
- **중단·rollback:** 새 probe 실패, restart 증가, Ready 감소, error rate 상승, 반복 `Killing`, quorum 위험 또는 data loss 위험이면 중단하고 이전 revision 또는 controller 경로 rollback을 승인자와 결정한다.
- **금지:** 원인 미확정 Pod 삭제, force delete, `kubectl patch`로 finalizer·grace 변경, 임의 scale·rollout·재시작을 진단 명령으로 실행하지 않는다. StatefulSet·PVC/RWO·quorum·leader가 관련되면 ordinal별 UID와 PVC consumer·attach evidence가 모두 확인될 때까지 중단한다.
- **검증:** 변경 후 owner desired/Ready, replacement UID, 동일 `Killing`·원인 Event와 restart 증가의 비반복, 새 Warning 부재, Service endpoint와 실제 요청·핵심 기능·Job 산출물을 즉시와 재평가 시각에 확인한다.

## 정상화와 증거 보존

정상화는 원인 경로를 역순으로 확인한다. application 기능과 실제 요청 또는 Job 산출물 → process·probe listener → kubelet/runtime 종료 오류 중단 → node pressure·kernel/cgroup 해소 → owner desired/Ready와 replacement identity 순서다. 새 Pod가 `Running`이거나 `Ready`인 것, HTTP 200 한 번, `Killing` Event가 잠시 없는 것만으로 정상화를 선언하지 않는다. 관찰 창 동안 같은 오류·restart·Warning이 반복되지 않아야 한다.

Pod UID·owner/revision·node·`KillingTime`, get/describe/Event의 실제 시각과 count, Last State, 선택한 로그·journal의 시간 범위와 필터·결정적 행, resource·pressure·cgroup evidence, 승인·manifest diff·이관 결과를 보존한다. Secret·token·개인키·개인정보와 전체 원문 로그는 보존하지 않는다.

## Prometheus 빠른 관측

아래 metric이 실제로 수집될 때만 사용한다. PromQL을 문서에서 직접 수정하지 않고 등록된 `$NS_RE`, `$POD_RE`, 현재 `$POD_UID`로 완성 문자열을 생성한다. UID matcher가 없는 metric 계약이면 query를 사용하지 않고 Event·API evidence로 이관한다. 출력된 한 줄만 Prometheus 또는 Grafana에 붙여 넣는다. transport/API 조회 실패는 metric 부재와 다르며, 빈 결과는 정상·0·오류 없음이 아니라 metric 미수집·label 불일치·시간 범위 오류 후보다.

**재시작 상관관계 PromQL 생성 — 아래 한 줄 전체를 복사**

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else printf 'sum by(namespace,pod,uid,container)(increase(kube_pod_container_status_restarts_total{namespace=~"%s",pod=~"%s",uid="%s"}[15m]))>0\n' "$NS_RE" "$POD_RE" "$POD_UID"; fi`

**probe 실패 상관관계 PromQL 생성 — 아래 한 줄 전체를 복사**

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else printf 'sum by(namespace,pod,pod_uid,container,probe_type)(increase(prober_probe_total{namespace=~"%s",pod=~"%s",pod_uid="%s",probe_type=~"Liveness|Startup",result!="successful"}[15m]))>0\n' "$NS_RE" "$POD_RE" "$POD_UID"; fi`

**마지막 종료 reason PromQL 생성 — 아래 한 줄 전체를 복사**

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else printf 'kube_pod_container_status_last_terminated_reason{namespace=~"%s",pod=~"%s",uid="%s"}==1\n' "$NS_RE" "$POD_RE" "$POD_UID"; fi`

Killing Event 자체는 kube-state-metrics의 공통 Pod metric으로 직접 표현되지 않는다. restart 증가·probe 실패·마지막 종료 reason을 같은 UTC 시간축에 맞추되 rollout·scale·eviction·operator 삭제는 Event와 audit·controller 기록으로 구분한다. metric query가 실패하면 Prometheus 접근·권한·API 상태를 먼저 확인하고, query가 성공했지만 series가 없으면 metric 부재와 label·시간 범위를 분리한다.
