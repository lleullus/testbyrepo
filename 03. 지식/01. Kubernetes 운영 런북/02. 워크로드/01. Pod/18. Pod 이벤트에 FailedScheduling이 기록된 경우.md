# Pod 이벤트에 FailedScheduling이 기록된 경우

## 입력값과 빠른 수집

실행 host는 승인된 context가 설정된 작업 PC 또는 bastion이며 모든 명령은 같은 Bash에서 실행한다. 기본 진단은 API server의 `pods/get`, `pods/list`, `events/list`, `nodes/get`, `resourcequotas/get`, `limitranges/list` 읽기 권한이 필요하다. scheduler log 분기는 control-plane 접근과 `pods/log` 권한을 별도로 확인한다. 도구 확인 또는 필수 API 수집이 실패하면 다음 단계로 진행하지 않는다.

| 종류 | 값 | 출처와 사용 시점 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 운영자가 namespace와 정확한 Pending Pod 이름을 한 번 입력한다. |
| API 확인 자동값 | `POD_UID`, `PHASE`, `POD_READY`, `NODE_ASSIGNED`, `OWNER_KIND`, `OWNER_NAME`, `OWNER_UID`, `PVC_CANDIDATES`, 선택 scheduler의 `SCHEDULER_UID`·current `SCHEDULER_CONTAINER_ID`, `POD_RE`, `EVENT_SELECTOR` | Pod API에서 현재 identity·phase·owner kind/name/UID·volume 후보를 읽어 등록하고 scheduler log 직전 fresh identity와 대조한다. |
| 계산 후보 | `POD_RE`, `EVENT_SELECTOR`, request 합계·init 최대값·overhead 계산, `JOB_SELECTOR` | 등록값과 API 출력으로 만들며 실제 scheduler message와 대조 전에는 확정하지 않는다. |
| 운영자 선택값 | Event가 지목한 `NODE`, `QUOTA`, `PVC`, scheduler Pod/container·`START_RFC3339`, Service | 복수 후보를 출력으로 확인한 뒤 해당 분기 직전에 선택한다. Job은 Pod owner kind/name/UID에서 자동 확정하며 첫 번째 후보를 임의 선택하지 않는다. |

Pending은 아직 스케줄되지 않았다는 상태이고 항상 scheduler 실패라는 뜻은 아니다. `FailedScheduling` Event는 과거 집계일 수 있으므로 같은 Pod UID·Event 시각·count와 현재 phase/node를 함께 본다. Pod 이름만으로 다른 UID의 Event를 섞지 않는다.

**Bash·필수 도구·권한 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 입력·Pod API·Event 수집을 실행하지 않는다. scheduler log의 `journalctl`·control-plane 접근은 별도 owner gate이며, 접근이 없다고 scheduler 원인으로 확정하지 않는다.

**최초 입력·이전 상태 초기화 — 같은 Bash에서 한 번 실행**

`unset SCHEDULER_UID PVC_UID PVC_STORAGE_CLASS PVC_READY PV_READY PVC_EVENT_READY STORAGECLASS_READY PVC_DIAG_READY START_CANONICAL START_EPOCH NOW_EPOCH SCHEDULER_CANDIDATE_UID SCHEDULER_MEMBER_COUNT SCHEDULER_NAMESPACE_MATCH SCHEDULER_MEMBER_MATCH SCHEDULER_PRODUCER_RC SCHEDULER_LOG_FILTER_RC`

`unset SCHEDULER_CONTAINER_ID SCHEDULER_FRESH_CONTAINER_ID SCHEDULER_FRESH_UID OWNER_UID OWNER_REFERENCE_READY JOB_OWNER_READY CURRENT_OWNER_REF_JSON CURRENT_OWNER_KIND CURRENT_OWNER_NAME CURRENT_OWNER_UID CURRENT_JOB_UID JOB_JSON NORMALIZATION_CHECK_JSON NORMALIZATION_CURRENT_UID`

`unset INPUT_READY AUTO_READY OBS_READY EVENT_READY NODE_READY QUOTA_READY PVC_READY SCHEDULER_READY NORMALIZATION_READY POD_JSON POD_UID PHASE POD_READY NODE_ASSIGNED OWNER_KIND OWNER_NAME OWNER_UID PVC_CANDIDATES POD_RE EVENT_SELECTOR EVENT_JSON NODE QUOTA PVC PV SCHEDULER_POD SCHEDULER_CONTAINER START_RFC3339 SERVICE JOB JOB_SELECTOR; NS='PASTE_NAMESPACE_HERE'; POD='PASTE_POD_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: 도구 확인을 먼저 통과한다.' >&2; elif [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: NS와 POD를 입력한다.' >&2; elif POD_JSON_TMP="$(kubectl get pod "$POD" -n "$NS" -o json)" && jq -e --arg pod "$POD" '.metadata.name==$pod and (.metadata.uid|length)>0' <<<"$POD_JSON_TMP" >/dev/null; then POD_JSON="$POD_JSON_TMP"; INPUT_READY=true; export NS POD; printf 'INPUT_READY=true namespace=%s pod=%s\n' "$NS" "$POD"; else printf '중단: exact-name Pod API 조회 실패 또는 이름 불일치 namespace=%s pod=%s\n' "$NS" "$POD" >&2; fi`

`INPUT_READY=true`가 아니면 다음 명령을 실행하지 않는다. 이 입력칸의 두 입력값만 바꾸며 이후 명령에는 `$NS`, `$POD`를 재사용한다.

입력 API 응답은 exact-name 확인에만 사용하고 snapshot으로 보존하지 않는다.

`unset POD_JSON`

**API 자동 수집·등록 — 같은 Bash에서 한 번 실행**

입력 단계의 `POD_JSON`은 exact-name 확인 전용이며 snapshot으로 재사용하지 않는다. 자동수집 시작 시 이전 snapshot과 downstream 값을 먼저 무효화한다.

`unset POD_JSON POD_JSON_TMP POD_UID_TMP PHASE_TMP POD_READY_TMP NODE_ASSIGNED_TMP OWNER_TMP OWNER_UID_TMP PVC_CANDIDATES_TMP POD_RE_TMP POD_UID PHASE POD_READY NODE_ASSIGNED OWNER_KIND OWNER_NAME OWNER_UID OWNER_REFERENCE_READY PVC_CANDIDATES POD_RE EVENT_SELECTOR EVENT_READY NODE_READY QUOTA_READY PVC_READY SCHEDULER_READY NORMALIZATION_READY SERVICE_JSON JOB_JSON JOB JOB_SELECTOR SNAPSHOT_READY; AUTO_READY=false`

`unset AUTO_READY POD_UID PHASE POD_READY NODE_ASSIGNED OWNER_KIND OWNER_NAME PVC_CANDIDATES POD_RE EVENT_SELECTOR; AUTO_READY=false; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif POD_JSON_TMP="$(kubectl get pod "$POD" -n "$NS" -o json)" && POD_UID_TMP="$(jq -r '.metadata.uid // empty' <<<"$POD_JSON_TMP")" && PHASE_TMP="$(jq -r '.status.phase // "-"' <<<"$POD_JSON_TMP")" && POD_READY_TMP="$(jq -r '[.status.conditions[]? | select(.type=="Ready") | .status][0] // "Unknown"' <<<"$POD_JSON_TMP")" && NODE_ASSIGNED_TMP="$(jq -r '.spec.nodeName // "-"' <<<"$POD_JSON_TMP")" && OWNER_TMP="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true)][0] | if .==null then "-/-" else (.kind+"/"+.name) end' <<<"$POD_JSON_TMP")" && PVC_CANDIDATES_TMP="$(jq -r '[.spec.volumes[]? | select(.persistentVolumeClaim!=null) | .persistentVolumeClaim.claimName] | join(",")' <<<"$POD_JSON_TMP")"; then if [ -z "$POD_UID_TMP" ]; then printf '%s\n' '중단: Pod UID가 비어 있음; 부분 등록하지 않음' >&2; else POD_RE_TMP="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; POD_UID="$POD_UID_TMP"; PHASE="$PHASE_TMP"; POD_READY="$POD_READY_TMP"; NODE_ASSIGNED="$NODE_ASSIGNED_TMP"; OWNER_KIND="${OWNER_TMP%%/*}"; OWNER_NAME="${OWNER_TMP#*/}"; PVC_CANDIDATES="$PVC_CANDIDATES_TMP"; POD_RE="^${POD_RE_TMP}$"; EVENT_SELECTOR="involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID,reason=FailedScheduling"; AUTO_READY=true; export POD_UID PHASE POD_READY NODE_ASSIGNED OWNER_KIND OWNER_NAME PVC_CANDIDATES POD_RE EVENT_SELECTOR; printf '=== 대상 Pod ===\n이름: %s\nUID: %s\nPhase: %s\nReady: %s\n할당 Node: %s\nOwner: %s\nPVC 후보: %s\n관측 시각(UTC): %s\nPOD_RE: %s\nEvent selector: %s\n' "$POD" "$POD_UID" "$PHASE" "$POD_READY" "$NODE_ASSIGNED" "$OWNER_TMP" "${PVC_CANDIDATES:--}" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" "$POD_RE" "$EVENT_SELECTOR"; fi; else printf '%s\n' '중단: Pod 자동 수집 API 또는 JSON 처리 실패; stale 값을 사용하지 않음' >&2; fi`

`AUTO_READY=false; SNAPSHOT_READY=false; if [ -z "${POD_UID_TMP:-}" ]; then printf '%s\n' '중단: fresh Pod UID가 없다.' >&2; elif [ "$POD_UID" = "$POD_UID_TMP" ] && jq -e --arg pod "$POD" --arg uid "$POD_UID_TMP" '.metadata.name==$pod and (.metadata.uid|length)>0 and .metadata.uid==$uid' <<<"$POD_JSON_TMP" >/dev/null; then POD_JSON="$POD_JSON_TMP"; AUTO_READY=true; SNAPSHOT_READY=true; printf 'SNAPSHOT_READY=true name=%s uid=%s observed_at=%s\n' "$POD" "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else unset POD_JSON POD_JSON_TMP POD_UID PHASE POD_READY NODE_ASSIGNED OWNER_KIND OWNER_NAME OWNER_UID OWNER_REFERENCE_READY PVC_CANDIDATES POD_RE EVENT_SELECTOR; printf '중단: fresh Pod snapshot name/UID exact match 실패 requested_name=%s current_uid=%s\n' "$POD" "${POD_UID:--}" >&2; fi`

`AUTO_READY=true`이고 Pod UID·phase·ready·현재 node·owner·PVC 후보가 출력돼야 다음 단계로 이동한다. PVC 후보가 비어 있는 것은 PVC 없음·field 부재·API 오류를 먼저 구분할 신호이며 storage 원인 없음이나 정상으로 해석하지 않는다.

`OWNER_REFERENCE_READY=false; OWNER_UID=''; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif [ "$OWNER_KIND" = "-" ] && [ "$OWNER_NAME" = "-" ]; then OWNER_REFERENCE_READY=true; printf 'OWNER_REFERENCE_READY=true owner=none owner_uid=- pod_uid=%s\n' "$POD_UID"; elif OWNER_UID="$(jq -r --arg kind "$OWNER_KIND" --arg name "$OWNER_NAME" '[.metadata.ownerReferences[]? | select(.controller==true and .kind==$kind and .name==$name) | .uid][0] // empty' <<<"$POD_JSON")" && [ -n "$OWNER_UID" ]; then OWNER_REFERENCE_READY=true; export OWNER_UID; printf 'OWNER_REFERENCE_READY=true owner=%s/%s owner_uid=%s pod_uid=%s\n' "$OWNER_KIND" "$OWNER_NAME" "$OWNER_UID" "$POD_UID"; else AUTO_READY=false; printf '중단: Pod controller owner kind/name에 대응하는 UID가 없음; owner identity를 등록하지 않음\n' >&2; fi`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | Pod가 `Pending`이고 같은 Pod UID의 Event `Reason=FailedScheduling` 원문이 후보 node 배제 이유를 설명하는 경우 |
| 적용 | 일반·init container request, Pod overhead, LimitRange·ResourceQuota, node allocatable·Pod capacity, taint·affinity·topology, PVC binding·volume topology를 동일 UID·시각으로 확인한다. |
| 제외 | `FailedMount`·`FailedAttachVolume`은 [[25. Pod 이벤트에 FailedMount·FailedAttachVolume이 기록된 경우]], image pull은 [[07. Pod STATUS가 ImagePullBackOff·ErrImagePull인 경우]], sandbox는 [[24. Pod 이벤트에 FailedCreatePodSandBox가 기록된 경우]], 현재 `Pending`만 있고 같은 UID의 `FailedScheduling`이 없으면 [[02. Pod STATUS가 Pending인 경우]]로 이관한다. Node `NotReady`·pressure 자체는 주 분기가 아니다. taint 제거·affinity 삭제·무조건 scale·노드 증설·Pod 삭제는 이 문서의 조치가 아니다. |

검색 문자열: `FailedScheduling`, `0/5 nodes are available`, `Insufficient cpu`, `Insufficient memory`, `Insufficient ephemeral-storage`, `pod has unbound immediate PersistentVolumeClaims`, `had taint`, `untolerated taint`, `didn't match Pod's node affinity/selector`, `topology spread constraints`, `exceeded quota`, `Too many pods`, `volume node affinity conflict`, `preemption is not helpful`

Event message 전체를 먼저 보존한 뒤 request → quota/LimitRange → allocatable → placement → PVC topology 순으로 분기한다. scheduler plugin 내부 원인은 표준 Event만으로 추측하지 않는다.

## 최초 확인

`OBS_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o wide && kubectl describe pod "$POD" -n "$NS"; then OBS_READY=true; printf 'OBS_READY=true uid=%s observed_at=%s\n' "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '%s\n' '중단: Pod 최초 확인 실패' >&2; fi`

`get`에서 phase·ready·node·age·UID를, `describe`에서 `Controlled By`와 Event를 본다. 이미 node가 있거나 phase가 바뀌었다면 과거 FailedScheduling과 현재 상태를 분리한다. 명령 성공은 스케줄 성공·container 시작·서비스 정상화를 보장하지 않는다.

**동일 UID FailedScheduling Event 한 번 수집 — API server에서 bounded 출력**

`EVENT_READY=false; EVENT_JSON=''; if [ "$OBS_READY" != true ]; then printf '%s\n' '중단: OBS_READY가 아니다.' >&2; elif EVENT_JSON="$(kubectl get events -n "$NS" --field-selector "$EVENT_SELECTOR" --sort-by=.metadata.creationTimestamp -o json)"; then if jq -e '(.items|length)>0' <<<"$EVENT_JSON" >/dev/null; then EVENT_READY=true; jq -r '.items[] | "=== FailedScheduling Event ===\nUID: \(.involvedObject.uid // "-")\nReason: \(.reason // "-")\nCount: \(.count // "-")\nFirst: \(.firstTimestamp // "-")\nLast: \(.lastTimestamp // "-")\nEvent time: \(.eventTime // "-")\nSeries last: \(.series.lastObservedTime // "-")\nMessage: \(.message // "-")"' <<<"$EVENT_JSON"; else printf '%s\n' '중단: 같은 UID FailedScheduling Event가 없음; Pending 상위 런북 또는 다른 Event 분기로 이관' >&2; fi; else printf '%s\n' '중단: UID·Reason 제한 Event API 조회 실패' >&2; fi`

`EVENT_READY=true`가 아니면 상세 scheduling 분기를 실행하지 않는다. 빈 결과는 scheduler가 정상이라는 뜻이 아니라 Event 보존·selector·API 범위·identity 문제 또는 실제 Event 미존재다. Event 원문의 `count`, `firstTimestamp`, `lastTimestamp`, `eventTime`, `series.lastObservedTime`과 현재 Pod 관측 시각을 함께 기록한다.

표는 원인을 확정하지 않는다. message가 여러 절을 가리키면 원문을 절별로 보존하고 각 상세 절의 gate를 독립적으로 통과한다.

### 1. request와 Pod overhead

진입 증거는 `Insufficient cpu`, `Insufficient memory`, `Insufficient ephemeral-storage`다. 최초 필요값은 같은 Pod UID의 일반 container request, init container request, `.spec.overhead`, RuntimeClass이며 source는 Pod API다.

`if [ "$EVENT_READY" != true ]; then printf '%s\n' '중단: EVENT_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o jsonpath='uid={.metadata.uid}{"\n"}overhead={.spec.overhead}{"\n"}runtimeClass={.spec.runtimeClassName}{"\n"}containers:{range .spec.containers[*]}{.name} requests={.resources.requests}{"\n"}{end}initContainers:{range .spec.initContainers[*]}{.name} requests={.resources.requests}{"\n"}{end}'; then printf '%s\n' '성공 gate: 일반 request 합·init request별 자원 최대·overhead를 Event message와 계산'; else printf '%s\n' '실패: Pod spec/API 조회 실패; request 원인으로 확정하지 않음' >&2; fi`

일반 container request의 합과 init container request의 자원별 최대값을 비교한 뒤 Pod overhead를 더한다. 일반 container 하나만 보거나 init을 빼지 않는다. overhead가 비면 없음으로 기록하되 RuntimeClass·admission이 없는 것으로 단정하지 않는다. 계산이 message와 맞으면 allocatable로, 맞지 않으면 LimitRange·admission이 실제 spec을 바꿨는지로 이동한다. 이 성공은 node 여유·스케줄 가능성을 보장하지 않는다.

### 2. quota와 LimitRange

진입 증거는 `exceeded quota`, `must be less than or equal to`, `minimum resources`, `maximum cpu/memory`다. quota 이름은 Event·namespace 정책에서 확인하고 복수 후보를 임의 선택하지 않는다.

`QUOTA='PASTE_QUOTA_HERE'; QUOTA_READY=false; if [ "$EVENT_READY" != true ]; then printf '%s\n' '중단: EVENT_READY가 아니다.' >&2; elif QUOTA_JSON="$(kubectl get resourcequota "$QUOTA" -n "$NS" -o json)" && kubectl get limitrange -n "$NS" -o wide && jq -e --arg q "$QUOTA" '.metadata.name==$q' <<<"$QUOTA_JSON" >/dev/null; then QUOTA_READY=true; export QUOTA; kubectl get resourcequota "$QUOTA" -n "$NS" -o custom-columns='NAME:.metadata.name,UID:.metadata.uid,HARD:.status.hard,USED:.status.used'; printf 'QUOTA_READY=true quota=%s\n' "$QUOTA"; else printf '%s\n' '중단: quota exact API 또는 LimitRange 조회 실패; 정책 원인으로 확정하지 않음' >&2; fi`

`hard`·`used`의 `requests.cpu`, `requests.memory`, `requests.ephemeral-storage`, `pods`와 LimitRange의 default/min/max를 실제 admission 후 Pod spec과 비교한다. quota가 가득 찼으면 node 조사보다 quota owner로 이관한다. quota message가 없고 request만 큰 경우에는 1번으로 돌아간다. 빈 quota·LimitRange는 정책 없음·selector 범위·API 실패를 구분하며 quota 여유로 해석하지 않는다.

### 3. node allocatable과 Pod capacity

진입 증거는 `Insufficient ...`, `Too many pods`, `Insufficient pods`다. Pending Pod에는 node가 배정되지 않았을 수 있으므로 Event message에 이름이 있거나 승인된 후보 목록에서 운영자가 고른 경우만 특정 node를 조사한다.

`NODE='PASTE_NODE_HERE'; NODE_READY=false; if [ "$EVENT_READY" != true ]; then printf '%s\n' '중단: EVENT_READY가 아니다.' >&2; elif NODE_JSON="$(kubectl get node "$NODE" -o json)" && jq -e --arg n "$NODE" '.metadata.name==$n' <<<"$NODE_JSON" >/dev/null; then NODE_READY=true; export NODE; printf 'NODE_READY=true node=%s\n' "$NODE"; else printf '%s\n' '중단: 선택 node exact API 조회 실패; 첫 번째 후보를 자동 선택하지 않음' >&2; fi`

`if [ "$NODE_READY" != true ]; then printf '%s\n' '중단: NODE_READY가 아니다.' >&2; elif kubectl get nodes -o custom-columns='NAME:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory,EPHEMERAL:.status.allocatable.ephemeral-storage,PODS:.status.allocatable.pods' && kubectl describe node "$NODE" && kubectl get pods -A --field-selector "spec.nodeName=$NODE" -o wide; then printf '성공 gate: node allocatable과 Pod capacity·현재 Pod 목록을 같은 관측 시각으로 확보\n'; else printf '%s\n' '실패: node API 또는 Pod 목록 조회 실패; resource 여유·Too many pods를 확정하지 않음' >&2; fi`

CPU·memory·ephemeral-storage request 여유, `.status.allocatable.pods`, 실제 Pod 수와 DaemonSet 점유를 대조한다. `MemoryPressure`, `DiskPressure`, `PIDPressure`, `NotReady`는 scheduler 자원 계산과 별개인 node/runtime 경로다. 특정 node 후보가 없으면 전체 후보를 이 명령으로 비교하되 첫 번째 여유 node를 원인 해결로 선택하지 않는다.

### 4. taint·affinity·selector·topology

진입 증거는 `had taint`, `untolerated taint`, `didn't match Pod's node affinity/selector`, `topology spread constraints`다. 3번에서 `$NODE`를 선택하지 않았다면 Event message와 정책을 먼저 확인하고 특정 node 명령을 실행하지 않는다.

`if [ "$EVENT_READY" != true ]; then printf '%s\n' '중단: EVENT_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o jsonpath='{.spec.nodeSelector}{"\n"}{.spec.affinity}{"\n"}{.spec.tolerations}{"\n"}{.spec.topologySpreadConstraints}{"\n"}' && kubectl get nodes --show-labels; then if [ "$NODE_READY" = true ]; then kubectl describe node "$NODE"; fi; printf '%s\n' '성공 gate: selector·required affinity·toleration·topology와 후보 node label/taint를 대조'; else printf '%s\n' '실패: placement 선언 또는 node label 조회 실패; 정책 변경으로 진행하지 않음' >&2; fi`

taint key/value/effect와 toleration key/operator/effect, selector·required affinity, topology key·`maxSkew`·`whenUnsatisfiable`, zone/hostname 분포를 함께 본다. `NoSchedule`은 신규 배치를 막고 `PreferNoSchedule`은 선호 조건이며 `NoExecute`는 실행 중 축출과 관련된다. label 공급·배치 정책이 확인되지 않으면 taint 제거·affinity 삭제·`ScheduleAnyway` 전환을 하지 않고 owner로 이관한다. 이 출력 성공은 해당 node에 안전하게 배치할 권한이나 workload 정책을 승인하지 않는다.

### 5. PVC binding과 volume topology

진입 증거는 `pod has unbound immediate PersistentVolumeClaims`, `persistentvolumeclaim ... is not bound`, `volume node affinity conflict`다. 자동 출력의 PVC 후보가 여러 개면 Pod volume 관계를 보고 하나만 선택한다.

`PVC='PASTE_PVC_HERE'; PVC_READY=false; PV_READY=false; PVC_EVENT_READY=false; STORAGECLASS_READY=false; PVC_DIAG_READY=false; PVC_UID=''; PVC_STORAGE_CLASS=''; PV=''; if [ "$EVENT_READY" != true ]; then printf '%s\n' '중단: EVENT_READY가 아니다.' >&2; elif jq -e --arg pvc "$PVC" 'any(.spec.volumes[]?; .persistentVolumeClaim.claimName==$pvc)' <<<"$POD_JSON" >/dev/null && PVC_JSON="$(kubectl get pvc "$PVC" -n "$NS" -o json)" && PVC_NAME_TMP="$(jq -r '.metadata.name // empty' <<<"$PVC_JSON")" && PVC_UID_TMP="$(jq -r '.metadata.uid // empty' <<<"$PVC_JSON")" && PVC_STORAGE_CLASS_TMP="$(jq -r '.spec.storageClassName // empty' <<<"$PVC_JSON")"; then if [ -z "$PVC_NAME_TMP" ] || [ -z "$PVC_UID_TMP" ]; then printf '%s\n' '중단: PVC name 또는 UID가 없음; Pod-volume 관계를 유효하게 등록하지 않음' >&2; elif kubectl get pvc "$PVC" -n "$NS" -o jsonpath='name={.metadata.name}{"\n"}uid={.metadata.uid}{"\n"}phase={.status.phase}{"\n"}volume={.spec.volumeName}{"\n"}storageClass={.spec.storageClassName}{"\n"}'; then PVC_READY=true; PVC="$PVC_NAME_TMP"; PVC_UID="$PVC_UID_TMP"; PVC_STORAGE_CLASS="$PVC_STORAGE_CLASS_TMP"; PV_TMP="$(jq -r '.spec.volumeName // empty' <<<"$PVC_JSON")"; if [ -n "$PV_TMP" ]; then PV_READY=true; PV="$PV_TMP"; fi; export PVC PVC_UID PVC_STORAGE_CLASS PV; printf 'PVC_READY=true pvc=%s pvc_uid=%s pod_uid=%s pod_volume_relation=true pv=%s pv_ready=%s observed_at=%s\n' "$PVC" "$PVC_UID" "$POD_UID" "${PV:--}" "$PV_READY" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '%s\n' '중단: PVC 출력 producer 실패; PVC identity를 유효하게 등록하지 않음' >&2; fi; else printf '%s\n' '중단: PVC가 이 Pod volume에 없거나 PVC API 조회 실패' >&2; fi`

`PVC_EVENT_JSON=''; STORAGECLASS_JSON=''; if [ "$PVC_READY" != true ]; then printf '%s\n' '중단: PVC_READY가 아니다.' >&2; elif PVC_EVENT_JSON="$(kubectl get events -n "$NS" --field-selector "involvedObject.kind=PersistentVolumeClaim,involvedObject.name=$PVC,involvedObject.uid=$PVC_UID" --sort-by=.metadata.creationTimestamp -o json)"; then PVC_EVENT_READY=true; if jq -r 'if (.items|length)==0 then "PVC Event: 없음 (binding 정상·오류 없음으로 해석하지 않음)" else .items[] | "=== PVC Event ===\nReason: \(.reason // "-")\nCount: \(.count // "-")\nFirst: \(.firstTimestamp // "-")\nLast: \(.lastTimestamp // "-")\nMessage: \(.message // "-")" end' <<<"$PVC_EVENT_JSON"; then :; else PVC_EVENT_READY=false; printf '%s\n' '실패: PVC Event JSON 처리 실패' >&2; fi; if [ -z "$PVC_STORAGE_CLASS" ]; then STORAGECLASS_READY=true; printf '%s\n' 'StorageClass: 없음 (default 주입·binding mode를 별도 정책에서 확인)'; elif STORAGECLASS_JSON="$(kubectl get storageclass "$PVC_STORAGE_CLASS" -o json)"; then STORAGECLASS_READY=true; jq -r '"=== StorageClass ===\n이름: \(.metadata.name)\nUID: \(.metadata.uid // "-")\nvolumeBindingMode: \(.volumeBindingMode // "-")\nprovisioner: \(.provisioner // "-")"' <<<"$STORAGECLASS_JSON"; else printf '%s\n' '실패: StorageClass producer 조회 실패' >&2; fi; if [ "$PVC_EVENT_READY" = true ] && [ "$STORAGECLASS_READY" = true ]; then PVC_DIAG_READY=true; if [ "$PV_READY" = true ]; then if kubectl get pv "$PV" -o custom-columns='PV:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,CLAIM:.spec.claimRef,CLASS:.spec.storageClassName,NODE-AFFINITY:.spec.nodeAffinity'; then printf 'PV_READY=true pv=%s observed_at=%s\n' "$PV" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else PV_READY=false; printf '%s\n' '실패: PV 조회 producer 실패' >&2; fi; else printf '%s\n' 'PV: 없음 (PVC가 아직 Bound되지 않음; PVC Event·StorageClass·volumeBindingMode 진단을 계속함)'; fi; else printf '%s\n' '중단: PVC Event 또는 StorageClass 진단 producer 실패' >&2; fi; fi`

PVC가 `Pending`이고 `PV`가 비어 있어도 `PVC_READY=true`와 Pod-volume 관계가 확인되면 이 절을 중단하지 않는다. `waiting for first consumer`, `no persistent volumes available`, `WaitForFirstConsumer`와 StorageClass `volumeBindingMode`를 함께 대조한다. 빈 PVC Event는 정상 binding의 증거가 아니며, PV 이름을 추측하거나 PVC를 삭제·재생성하지 않는다.

명시적 `storageClassName`이 비어 있으면 default StorageClass 후보도 확인해야 한다. `if [ "$PVC_READY" != true ]; then printf '%s\n' '중단: PVC_READY가 아니다.' >&2; elif [ -n "$PVC_STORAGE_CLASS" ]; then printf 'StorageClass 선택값=%s는 앞선 volumeBindingMode 출력으로 대조\n' "$PVC_STORAGE_CLASS"; elif kubectl get storageclass -o custom-columns='NAME:.metadata.name,DEFAULT:.metadata.annotations["storageclass.kubernetes.io/is-default-class"],VOLUME-BINDING-MODE:.volumeBindingMode,PROVISIONER:.provisioner'; then printf '%s\n' '성공 gate: default StorageClass 후보와 volumeBindingMode를 출력; 후보가 복수면 임의 선택하지 않음'; else printf '%s\n' '실패: default StorageClass 조회 producer 실패' >&2; fi`

`WaitForFirstConsumer`는 Pod topology와 함께 binding되므로 PVC 삭제·재생성이나 StorageClass 변경을 하지 않는다. binding 뒤 `FailedMount`가 보이면 [[25. Pod 이벤트에 FailedMount·FailedAttachVolume이 기록된 경우]]로 이관한다. CSI 구현·backend 상태는 Kubernetes 객체만으로 확정하지 않는다.

### 6. scheduler plugin·log

진입 증거는 표준 message가 resource·placement 원인을 설명하지 못하거나 plugin 결과가 충돌하는 경우다. 연결 경로는 `실행 host → API server/proxy → control-plane scheduler Pod 또는 managed control plane log endpoint → scheduler process → Pod UID 기록`이다. API server·scheduler Pod 조회 성공은 log stream과 plugin 원인 확인을 보장하지 않는다.

`SCHEDULER_POD='PASTE_SCHEDULER_POD_HERE'; SCHEDULER_CONTAINER='PASTE_SCHEDULER_CONTAINER_HERE'; START_RFC3339='PASTE_START_RFC3339_HERE'; SCHEDULER_READY=false; if [ "$EVENT_READY" != true ]; then printf '%s\n' '중단: EVENT_READY가 아니다.' >&2; elif ! | select(.metadata.namespace=="kube-system" and .metadata.name==$pod)] | length' <<<"$SCHEDULER_LIST")" && [ "$SCHEDULER_MEMBER_COUNT" -eq 1 ] && SCHEDULER_CANDIDATE_UID="$(jq -r --arg pod "$SCHEDULER_POD" '[.items[]? | select(.metadata.namespace=="kube-system" and .metadata.name==$pod) | .metadata.uid][0] // empty' <<<"$SCHEDULER_LIST")" && SCHEDULER_UID="$(jq -r '.metadata.uid // empty' <<<"$SCHEDULER_JSON")" && [ -n "$SCHEDULER_CANDIDATE_UID" ] && [ "$SCHEDULER_UID" = "$SCHEDULER_CANDIDATE_UID" ] && jq -e --arg pod "$SCHEDULER_POD" --arg c "$SCHEDULER_CONTAINER" --arg uid "$SCHEDULER_UID" '.metadata.namespace=="kube-system" and .metadata.name==$pod and .metadata.uid==$uid and any(.spec.containers[]?; .name==$c)' <<<"$SCHEDULER_JSON" >/dev/null; then SCHEDULER_READY=true; export SCHEDULER_POD SCHEDULER_CONTAINER START_RFC3339 SCHEDULER_UID; jq -r '.items[] | "=== Scheduler 후보 ===\nNamespace: \(.metadata.namespace)\nPod: \(.metadata.name)\nUID: \(.metadata.uid)\nNode: \(.spec.nodeName // "-")\nContainer: \([.spec.containers[]?.name]|join(","))"' <<<"$SCHEDULER_LIST"; printf 'SCHEDULER_READY=true namespace=kube-system pod=%s container=%s uid=%s member_count=%s start=%s target_uid=%s observed_at=%s\n' "$SCHEDULER_POD" "$SCHEDULER_CONTAINER" "$SCHEDULER_UID" "$SCHEDULER_MEMBER_COUNT" "$START_RFC3339" "$POD_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '%s\n' '중단: scheduler 후보의 namespace/name/UID/member 또는 container/time exact 검증 실패; 첫 후보를 자동 선택하지 않음' >&2; fi`

`SCHEDULER_READY=true`가 아니면 scheduler logs를 실행하지 않고 control-plane owner에게 Pod UID·Event 시각·message만 이관한다. scheduler Pod와 log 접근이 있는 경우에만 다음을 실행한다.

`if [ "$SCHEDULER_READY" = true ]; then SCHEDULER_CONTAINER_ID="$(jq -r --arg c "$SCHEDULER_CONTAINER" '[.status.containerStatuses[]? | select(.name==$c) | .containerID // empty][0] // empty' <<<"$SCHEDULER_JSON")"; if [ -n "$SCHEDULER_CONTAINER_ID" ]; then export SCHEDULER_CONTAINER_ID; printf 'SCHEDULER_CONTAINER_ID_READY=true pod=%s uid=%s container=%s container_id=%s observed_at=%s\n' "$SCHEDULER_POD" "$SCHEDULER_UID" "$SCHEDULER_CONTAINER" "$SCHEDULER_CONTAINER_ID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else SCHEDULER_READY=false; printf '%s\n' '중단: scheduler 선택 container의 current containerID가 없음; log stream 대상을 확정하지 않음' >&2; fi; fi`

`if [ "$SCHEDULER_READY" != true ] || ! refresh_scheduler_identity; then SCHEDULER_READY=false; printf '%s\n' '중단: scheduler log 직전 Pod UID 또는 containerID 재검증 실패; restart면 stale gate=false' >&2; fi`

`Failed to schedule`, `Preemption is not helpful for scheduling`, 특정 Filter/Permit plugin이 같은 Pod UID·시간으로 맞으면 해당 정책 owner로 이동한다. UID가 다르거나 log가 없으면 scheduler 원인으로 확정하지 않는다. 필터가 비면 같은 범위의 tail 50행을 확인하되 개인정보·token·Secret을 저장하지 않는다. 실제 scheduler profile/plugin 변경은 control-plane owner의 별도 변경이다.

## 복구 전 안전 gate와 action contract

Event 원문, 동일 Pod UID·owner, request·init·overhead 계산, LimitRange·Quota, node allocatable·Pod capacity, taint·label·affinity·topology, PVC/PV 상태와 서비스·Job 영향이 보존돼야 한다. 상태 변경은 GitOps 또는 승인된 관리 경로에서만 수행하며 이 문서의 진단 명령에 섞지 않는다.

- Trigger: Event message와 위 계층 중 하나의 직접 근거가 같은 UID·관측 시각으로 연결됐다.
- Scope: replica·PDB·quorum·node pool, quota tenant, PVC 데이터·CSI 영향과 Job 외부 side effect를 평가했다.
- Authority: workload·quota·node pool·storage·control-plane owner와 변경 승인자가 확인됐다.
- Action: 측정된 request·사용량·SLO·quota 여유가 있을 때만 resource 계획, 정책 owner가 확인된 경우에만 quota/LimitRange·taint/affinity/topology 변경을 검토한다. PVC 삭제·재생성·StorageClass 변경, 모든 taint 허용, affinity 삭제, scheduler plugin 변경은 금지한다.
- Stop/Rollback: 새 FailedScheduling, 잘못된 node/zone 배치, OOM·eviction·SLO 악화, 데이터/산출물 이상이면 즉시 중단하고 승인된 이전 선언·정책으로 rollback한다.
- Job: `Complete=True`·`succeeded`만으로 재실행하지 않는다. 승인된 읽기 전용 checksum/watermark·commit/ack·중복 확인이 없거나 불명확하면 Job owner에게 이관한다.

## 정상화 검증

상태 변경 후 새 Pod가 스케줄됐다는 사실만으로 정상화하지 않는다. 새 Pod면 이전 UID의 Event를 재사용하지 않고 입력 수집부터 새 UID·시각을 확정한다.

`NORMALIZATION_READY=false; NORMALIZATION_CANDIDATE_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,NODE:.spec.nodeName,START:.status.startTime'; then NORMALIZATION_CANDIDATE_READY=true; printf 'NORMALIZATION_CANDIDATE_READY=true observed_at=%s\n' "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '%s\n' '중단: 새 Pod 상태 확인 실패' >&2; fi`

`if [ "$NORMALIZATION_CANDIDATE_READY" = true ]; then if NORMALIZATION_CHECK_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && NORMALIZATION_CURRENT_UID="$(jq -r '.metadata.uid // empty' <<<"$NORMALIZATION_CHECK_JSON")" && [ "$NORMALIZATION_CURRENT_UID" = "$POD_UID" ]; then NORMALIZATION_READY=true; printf 'NORMALIZATION_UID_READY=true uid=%s observed_at=%s\n' "$NORMALIZATION_CURRENT_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '중단: 정상화 직전 Pod UID mismatch stored_uid=%s current_uid=%s; 기존 evidence를 폐기하고 입력·자동 수집부터 재실행한다.\n' "$POD_UID" "${NORMALIZATION_CURRENT_UID:--}" >&2; NORMALIZATION_READY=false; unset AUTO_READY POD_JSON POD_UID PHASE POD_READY NODE_ASSIGNED OWNER_KIND OWNER_NAME PVC_CANDIDATES POD_RE EVENT_SELECTOR EVENT_JSON; fi; fi`

`JOB_OWNER_READY=false; CURRENT_OWNER_REF_JSON=''; CURRENT_OWNER_KIND=''; CURRENT_OWNER_NAME=''; CURRENT_OWNER_UID=''; CURRENT_JOB_UID=''; JOB_JSON=''; JOB=''; JOB_SELECTOR=''; if [ "$NORMALIZATION_READY" != true ] || [ "$OWNER_REFERENCE_READY" != true ]; then printf '%s\n' '중단: NORMALIZATION_READY 또는 OWNER_REFERENCE_READY가 아니다.' >&2; elif [ "$OWNER_KIND" != Job ]; then printf '중단: 대상 Pod owner kind가 Job이 아님 kind=%s; Job 정상화를 선언하지 않음\n' "$OWNER_KIND" >&2; elif CURRENT_OWNER_REF_JSON="$(jq -c '[.metadata.ownerReferences[]? | select(.controller==true)][0] // {}' <<<"$NORMALIZATION_CHECK_JSON")" && CURRENT_OWNER_KIND="$(jq -r '.kind // empty' <<<"$CURRENT_OWNER_REF_JSON")" && CURRENT_OWNER_NAME="$(jq -r '.name // empty' <<<"$CURRENT_OWNER_REF_JSON")" && CURRENT_OWNER_UID="$(jq -r '.uid // empty' <<<"$CURRENT_OWNER_REF_JSON")" && [ "$CURRENT_OWNER_KIND" = "$OWNER_KIND" ] && [ "$CURRENT_OWNER_NAME" = "$OWNER_NAME" ] && [ "$CURRENT_OWNER_UID" = "$OWNER_UID" ] && JOB_JSON="$(kubectl get job "$OWNER_NAME" -n "$NS" -o json)" && CURRENT_JOB_UID="$(jq -r '.metadata.uid // empty' <<<"$JOB_JSON")" && [ "$CURRENT_JOB_UID" = "$OWNER_UID" ]; then JOB_OWNER_READY=true; JOB="$OWNER_NAME"; JOB_SELECTOR="job-name=$JOB"; export JOB JOB_SELECTOR CURRENT_JOB_UID; printf 'JOB_OWNER_READY=true pod_uid=%s pod_owner=%s/%s pod_owner_uid=%s current_job_uid=%s observed_at=%s\n' "$POD_UID" "$CURRENT_OWNER_KIND" "$CURRENT_OWNER_NAME" "$CURRENT_OWNER_UID" "$CURRENT_JOB_UID" "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; else printf '중단: Pod owner kind/name/UID 또는 현재 Job UID가 저장 identity와 일치하지 않음 stored_owner=%s/%s/%s current_owner=%s/%s/%s current_job_uid=%s\n' "$OWNER_KIND" "$OWNER_NAME" "$OWNER_UID" "${CURRENT_OWNER_KIND:--}" "${CURRENT_OWNER_NAME:--}" "${CURRENT_OWNER_UID:--}" "${CURRENT_JOB_UID:--}" >&2; fi`

서비스 workload인 경우 실제 Service 이름을 확인한 뒤에만 endpoint와 기능을 확인한다.

`SERVICE='PASTE_SERVICE_HERE'; if [ "$NORMALIZATION_READY" != true ]; then printf '%s\n' '중단: NORMALIZATION_READY가 아니다.' >&2; elif SERVICE_JSON="$(kubectl get service "$SERVICE" -n "$NS" -o json)" && kubectl get endpointslice -n "$NS" -l "kubernetes.io/service-name=$SERVICE" -o wide; then export SERVICE; printf 'service evidence ready service=%s\n' "$SERVICE"; else printf '%s\n' '실패: Service/EndpointSlice API 조회 실패; 실제 기능 정상화로 해석하지 않음' >&2; fi`

서비스 workload의 정상화 조건은 의도한 node와 `Running/Ready`, desired replica·Ready 수, EndpointSlice address·conditions·targetRef UID, 승인된 실제 요청·핵심 기능, 관찰 구간의 새 `FailedScheduling` Warning과 동일 message count 증가 없음이다. `Running`, `Ready`, EndpointSlice 존재만으로 application 기능을 보장하지 않는다.

Job 정상화는 이전 분기에서 남은 `$JOB`이나 사용자가 다시 입력한 이름을 사용하지 않고, `JOB_OWNER_READY=true`인 현재 Pod owner와 현재 Job UID만 사용한다.

`if [ "$JOB_OWNER_READY" != true ]; then printf '%s\n' '중단: 현재 Pod owner UID와 Job UID가 대조된 Job 정상화 gate가 아니다.' >&2; else kubectl get job "$CURRENT_OWNER_NAME" -n "$NS" -o jsonpath='{range .status.conditions[*]}condition={.type} status={.status} reason={.reason}{"\n"}{end}succeeded={.status.succeeded} failed={.status.failed}{"\n"}' && kubectl get pods -n "$NS" -l "job-name=$CURRENT_OWNER_NAME" -o wide; fi`

`Complete=True`와 기대 `succeeded`는 첫 조건일 뿐이다. 환경에서 승인된 읽기 전용 산출물 checksum/watermark, DB/API/queue commit/ack, 동일 입력·idempotency 기준 중복 여부를 실제 확인해야 한다. 어느 하나라도 실패·불명확·재현 불가하면 정상화를 선언하거나 Job을 재실행하지 않고 owner에게 이관한다. Job Pod가 `Running/Ready`가 된 것만으로 성공을 선언하지 않는다.

정상화는 `application 기능 → 실제 요청·Job 산출물 → Endpoint/remote dependency → Pod phase/condition → scheduler Event count` 순서로 역검증한다. 원인이 해소되고 재발 관찰 창을 통과했는지와 완화 성공·근본 원인 해결을 별도로 기록한다.

## 증거 보존과 1.26 경계

UTC 시각, namespace, 현재·이전 Pod UID, owner kind/name/UID와 현재 Job UID, Event reason·전체 message·count·first/last/event/series timestamp, request·init request·overhead 계산, LimitRange·Quota, node allocatable·Pod capacity·taint·label, affinity·topology, PVC/PV UID·phase·nodeAffinity, scheduler log의 UID·시간·plugin 식별자, 승인·변경 revision과 정상화 결과를 보존한다. Secret·token·개인키·개인정보는 저장하지 않는다.

Kubernetes Server와 `kubectl` 기준은 `1.26.x`다. scheduler profile·plugin 설정, managed control plane log 접근, autoscaler·admission webhook의 request 변경, CSI 구현과 배포판별 Event message는 환경별 미검증이다. feature gate가 필요한 동작은 활성화 여부를 확인하기 전 기본 동작으로 취급하지 않는다.

## Prometheus 빠른 관측

PromQL은 등록된 `$NS`, `$POD_RE`, `$POD_UID`로 완성 문자열을 생성한다. 출력된 원라인만 Prometheus/Grafana에 붙여 넣고, metric 부재·label 불일치·조회 시간 범위·권한/API 실패를 분리한다. Pod 이름을 regex에 넣을 때 자동 생성한 escaped `$POD_RE`를 사용한다.

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else printf '%s\n' "kube_pod_status_scheduled{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\",condition=\"false\"}==1"; fi`

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else printf '%s\n' "kube_pod_status_unschedulable{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\"}==1"; printf '%s\n' "time()-kube_pod_created{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\"}"; fi`

해당 metric에 `uid` label이 실제로 있으면 결과의 UID를 `$POD_UID`와 대조한다. `scheduled=false`, `unschedulable=1`, 생성 후 경과 시간은 현재 상태의 보조 증거일 뿐이며 Insufficient resource·taint·affinity·PVC topology·quota 원인은 동일 UID Event message와 scheduler 관측으로 확정한다. 빈 결과를 스케줄 성공이나 원인 없음으로 해석하지 않는다.
