# Pod 이벤트에 FailedMount·FailedAttachVolume이 기록된 경우

## 입력값과 빠른 수집

이 문서의 값은 다음처럼 분류한다. 최초 입력은 namespace와 Pod뿐이다. UID, node, phase, owner, volume source, PVC·PV·StorageClass와 관측 시각은 Kubernetes API 자동값이다. Pod volume 정규식과 PVC 정규식은 자동 계산 후보이며, 어떤 volume과 실제 CSI·kubelet 대상을 볼지는 출력 확인 뒤 운영자가 선택한다. PVC가 아닌 source에는 PVC·CSI 값을 만들지 않는다.

| 구분 | 값 | 출처와 유효성 gate |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 승인된 namespace와 정확한 Pod 이름을 한 번 입력하고 exact-name API 조회가 성공해야 한다. |
| API 자동값 | `POD_UID`, `NODE`, `PHASE`, `OWNER`, `POD_JSON`, `EVENTS_JSON`, `PVC`, `PV`, `STORAGE_CLASS`, `VOLUME_HANDLE`, `OBSERVED_AT` | 대상 UID와 API 조회가 모두 성공해야 등록한다. 빈 node·event는 정상이나 오류 없음으로 해석하지 않는다. |
| 계산 후보 | `POD_RE`, `PVC_RE`, `POD_IDENTITY_READY` | 등록된 이름을 regex escape한 bounded 문자열이며 실제 조회 결과와 현재 UID를 확인하기 전에는 확정하지 않는다. |
| 운영자 선택값 | `VOLUME`, `VOLUMEATTACHMENT`, CSI controller/node DaemonSet·Pod·container, `START_RFC3339`, journal 시간·unit, `MOUNT_TARGET`, `DEVICE_OR_SOURCE` | Event·inventory·node에서 대상을 확인한 뒤 해당 분기 직전에 한 번만 입력한다. 복수 후보를 첫 번째로 고르지 않는다. |

### 1. 실행 위치·도구·대상 지정

kubectl 명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. `sh`, PowerShell, CMD로 바꾸거나 중간에 새 Bash를 열면 gate와 변수 상태가 사라지므로 처음부터 다시 시작한다. Kubernetes API에는 Pod·Event·PVC·PV·StorageClass·VolumeAttachment·CSIDriver·CSINode를 읽을 권한이 필요하다. node 명령은 작업 PC 변수에 의존하지 않는 승인된 SSH 원격 Bash에서 UID·Node machine identity·gate를 다시 검증한 뒤에만 실행한다.

**Bash·필수 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; MISSING_TOOLS=''; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else for TOOL in kubectl jq grep sed date mktemp ssh; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 다음 명령을 실행하지 않는다. jq가 없으면 raw JSON을 저장하거나 임의로 값을 추출하지 말고 플랫폼 owner에게 같은 필드 확인을 이관한다.

**최초 입력·이전 상태 초기화 — 같은 Bash에서 한 번 실행**

`unset INPUT_READY AUTO_READY VOLUME_READY PVC_READY ATTACHMENT_READY CSI_DRIVER_READY CSI_ATTACH_REQUIRED CSI_DRIVER CSI_CONTROLLER_READY CSI_NODE_READY NODE_READY NODE_REMOTE_READY MOUNT_READY PROMQL_READY POD_UID NODE PHASE OWNER POD_JSON EVENTS_JSON CSI_NODE_CANDIDATES VOLUME VOLUME_SOURCE PVC PV STORAGE_CLASS VOLUME_HANDLE VOLUMEATTACHMENT CSI_NAMESPACE CSI_CONTROLLER_POD CSI_CONTROLLER_POD_UID CSI_CONTROLLER_CONTAINER CSI_CONTROLLER_CONTAINER_ID CSI_NODE_NAMESPACE CSI_NODE_POD CSI_NODE_POD_UID CSI_NODE_CONTAINER CSI_NODE_CONTAINER_ID START_RFC3339 START_JOURNAL END_JOURNAL KUBELET_SERVICE MOUNT_TARGET DEVICE_OR_SOURCE POD_RE PVC_RE OBSERVED_AT; NS='PASTE_NAMESPACE_HERE'; POD='PASTE_POD_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: 도구 확인을 먼저 통과한다.' >&2; elif [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: NS와 POD를 입력한다.' >&2; elif kubectl get pod "$POD" -n "$NS" -o name >/dev/null 2>&1; then INPUT_READY=true; export NS POD; printf 'INPUT_READY=true namespace=%s pod=%s\n' "$NS" "$POD"; else printf '중단: 정확한 Pod 조회 실패 namespace=%s pod=%s\n' "$NS" "$POD" >&2; fi`

`unset POD_IDENTITY_READY NODE_API_READY NODE_API_JSON NODE_HOST NODE_HOST_READY ACTUAL_NODE_HOST NODE_REMOTE_READY NODE_MACHINE_ID NODE_REMOTE_MACHINE_ID CSI_DAEMONSET_JSON CSI_SELECTOR CSI_NODE_DAEMONSET_UID CSI_NODE_OWNER_UID CSI_NODE_JSON CSI_NODE_CONTAINER_ID`

`unset START_READY START_EPOCH START_CANONICAL JOURNAL_TIME_READY JOURNAL_START_EPOCH JOURNAL_END_EPOCH JOURNAL_START_CANONICAL JOURNAL_END_CANONICAL CSI_EVIDENCE_READY CSI_NODE_EVIDENCE_READY`

`INPUT_READY=true`가 아니면 context·namespace·Pod 이름·권한을 확인하고 이후 단계로 진행하지 않는다.

### 2. API 자동 수집

**Pod·Event 자동 수집 — 아래 한 줄 전체를 복사**

`unset AUTO_READY POD_UID NODE PHASE OWNER POD_JSON EVENTS_JSON OBSERVED_AT; AUTO_READY=false; if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif POD_JSON="$(kubectl get pod "$POD" -n "$NS" -o json)" && POD_UID_TMP="$(jq -r '.metadata.uid // empty' <<<"$POD_JSON")" && [ -n "$POD_UID_TMP" ] && EVENTS_JSON="$(kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID_TMP" -o json)" && NODE_TMP="$(jq -r '.spec.nodeName // "-"' <<<"$POD_JSON")" && PHASE_TMP="$(jq -r '.status.phase // "-"' <<<"$POD_JSON")" && OBSERVED_AT_TMP="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; then OWNER_TMP="$(jq -r '[.metadata.ownerReferences[]? | select(.controller==true) | (.kind+"/"+.name)] | join(",") // "-"' <<<"$POD_JSON")"; POD_UID="$POD_UID_TMP"; NODE="$NODE_TMP"; PHASE="$PHASE_TMP"; OWNER="$OWNER_TMP"; OBSERVED_AT="$OBSERVED_AT_TMP"; AUTO_READY=true; export POD_UID NODE PHASE OWNER OBSERVED_AT; jq -r '"=== Pod ===\n이름: \(.metadata.name)\nUID: \(.metadata.uid)\n노드: \(.spec.nodeName // "미할당")\n상태: \(.status.phase // "-")\n시작 시각: \(.status.startTime // .metadata.creationTimestamp // "-")\n소유자: \(([.metadata.ownerReferences[]? | select(.controller==true) | (.kind+"/"+.name)] | join(",")) // "-")\n" + ([.spec.volumes[]? | "볼륨: \(.name)\n소스: (if .persistentVolumeClaim then "PVC/"+.persistentVolumeClaim.claimName elif .csi then "CSI/"+.csi.driver elif .configMap then "ConfigMap/"+.configMap.name elif .secret then "Secret/"+.secret.secretName elif .projected then "Projected" elif .emptyDir then "emptyDir" elif .hostPath then "hostPath" else "기타" end)"] | join("\n"))' <<<"$POD_JSON"; if [ "$(jq '.items|length' <<<"$EVENTS_JSON")" -eq 0 ]; then printf '%s\n' '=== Event ===' '결과: 없음 (정상·오류 없음으로 해석하지 않음)'; else jq -r '.items | sort_by(.eventTime // .lastTimestamp // .firstTimestamp // .metadata.creationTimestamp)[] | "=== Event ===\n이벤트 UID: \(.metadata.uid // "-")\n대상 UID: \(.involvedObject.uid // "-")\n시각: \(.eventTime // .lastTimestamp // .firstTimestamp // .metadata.creationTimestamp // "-")\n유형/사유: \(.type // "-")/\(.reason // "-")\n횟수: \(.count // 1)\n메시지: \(.message // "-")\n"' <<<"$EVENTS_JSON"; fi; printf 'AUTO_READY=true 관측 시각=%s\n' "$OBSERVED_AT"; else unset POD_UID NODE PHASE OWNER POD_JSON EVENTS_JSON OBSERVED_AT; printf '%s\n' '중단: Pod 또는 Event API 조회와 필수 identity 추출 실패' >&2; fi`

예상 출력은 대상별 UID·node·phase·시각·volume source와 Event의 대상 UID·시각·reason·message를 보존해야 한다.

```text
=== Pod ===
이름: api-0
UID: 11111111-2222-3333-4444-555555555555
Node: worker-a
Phase: Pending
Volume: data
Source: PVC/api-data
=== Event ===
대상 UID: 11111111-2222-3333-4444-555555555555
시각: 2026-07-29T09:01:00Z
유형/Reason: Warning/FailedMount
```

`AUTO_READY=true`와 Pod UID가 확인돼야 다음으로 간다. Event가 없거나 빈 message인 것은 정상화 증거가 아니다. 이 문서의 Event 조회는 최초 수집에서 한 번만 하고, 이후에는 `EVENTS_JSON`의 같은 UID·시각을 재사용한다.

**Pod UID 재조회 gate — 파생값 사용 전에 아래 한 줄 전체를 복사**

`refresh_pod_identity(){ local current; POD_IDENTITY_READY=false; CURRENT_POD_UID="$(kubectl get pod "$POD" -n "$NS" -o jsonpath='{.metadata.uid}' 2>/dev/null)"; if [ "$AUTO_READY" = true ] && [ -n "$CURRENT_POD_UID" ] && [ "$CURRENT_POD_UID" = "$POD_UID" ]; then POD_IDENTITY_READY=true; printf 'POD_IDENTITY_READY=true uid=%s\n' "$CURRENT_POD_UID"; return 0; else unset AUTO_READY VOLUME_READY PVC_READY ATTACHMENT_READY CSI_DRIVER_READY CSI_ATTACH_REQUIRED CSI_DRIVER CSI_EVIDENCE_READY CSI_CONTROLLER_READY CSI_NODE_READY CSI_NODE_EVIDENCE_READY CSI_NODE_DAEMONSET_UID CSI_NODE_POD_UID CSI_NODE_OWNER_UID PROMQL_READY; printf '중단: Pod UID mismatch 또는 재조회 실패 expected=%s actual=%s\n' "$POD_UID" "${CURRENT_POD_UID:--}" >&2; return 1; fi; }; refresh_pod_identity`

### 3. Event volume 선택

Event message의 volume 이름과 Pod 출력의 source를 대조한 뒤에만 다음을 실행한다. 같은 Bash에서 자동 수집 결과와 선택값을 연결한다.

`refresh_pod_identity`

`refresh_pod_identity`가 실패하거나 `POD_IDENTITY_READY=true`가 아니면 다음 명령을 실행하지 않는다. 이 helper는 각 파생 경로 직전에 current Pod UID를 재조회한다.

`unset VOLUME_SOURCE PVC VOLUME_READY; VOLUME_READY=false; VOLUME='PASTE_VOLUME_HERE'; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif jq -e --arg volume "$VOLUME" 'any(.spec.volumes[]?; .name==$volume)' <<<"$POD_JSON" >/dev/null; then VOLUME_SOURCE="$(jq -r --arg volume "$VOLUME" '.spec.volumes[] | select(.name==$volume) | if .persistentVolumeClaim then "pvc" elif .csi then "csi" elif .configMap then "configmap" elif .secret then "secret" elif .projected then "projected" elif .emptyDir then "emptyDir" elif .hostPath then "hostPath" else "other" end' <<<"$POD_JSON")"; PVC="$(jq -r --arg volume "$VOLUME" '.spec.volumes[] | select(.name==$volume) | .persistentVolumeClaim.claimName // empty' <<<"$POD_JSON")"; VOLUME_READY=true; export VOLUME VOLUME_SOURCE PVC; printf 'VOLUME_READY=true volume=%s source=%s pvc=%s\n' "$VOLUME" "$VOLUME_SOURCE" "${PVC:--}"; else printf '중단: Pod에 없는 volume이거나 이름 선택 실패 volume=%s\n' "$VOLUME" >&2; fi`

**volume source 추출 gate — 아래 한 줄 전체를 복사**

`refresh_pod_identity`

`if [ "$VOLUME_READY" = true ] && [ -n "$VOLUME_SOURCE" ]; then printf 'VOLUME_SOURCE_READY=true volume=%s source=%s pvc=%s\n' "$VOLUME" "$VOLUME_SOURCE" "${PVC:--}"; else unset VOLUME_READY PVC VOLUME_SOURCE; printf '%s\n' '중단: 선택 volume source 추출 실패' >&2; fi`

선택한 volume이 여러 후보 중 실제 Event의 volume과 일치하지 않거나 source가 비어 있으면 `VOLUME_READY`를 만들지 않는다. PVC가 아닌 source면 PVC·CSI 명령을 실행하지 않고 [[26. Pod가 ConfigMap·Secret을 찾지 못하는 경우]] 또는 해당 source owner로 이동한다. `emptyDir`·`hostPath`도 이 문서의 persistent volume 경로가 아니다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 같은 Pod UID의 Event에 `FailedAttachVolume`, `FailedMount`, `Unable to attach or mount volumes`, `MountVolume.SetUp failed` 또는 `Multi-Attach`가 보이는 경우 |
| 적용 | Pod UID·node·volume 이름·source와 Event의 실제 시각을 확인할 수 있는 경우 |
| 제외 | `FailedScheduling`이면 [[18. Pod 이벤트에 FailedScheduling이 기록된 경우]], `FailedCreatePodSandBox`이면 [[24. Pod 이벤트에 FailedCreatePodSandBox가 기록된 경우]], ConfigMap·Secret source 오류면 [[26. Pod가 ConfigMap·Secret을 찾지 못하는 경우]]로 이동한다. PVC·PV·CSI가 최초 원인이 아니면 해당 owner에게 이관한다. |

검색 문자열: `FailedAttachVolume`, `FailedMount`, `Unable to attach or mount volumes`, `MountVolume.SetUp failed`, `Multi-Attach`, `attach`, `mount`, `staging`, `publish`, `VolumeAttachment`, `CSI`, `timed out`, `already exclusively attached`, `filesystem`, `device`, `permission`.

## 최초 확인

진입 판단을 통과하고 `AUTO_READY=true`일 때만 실행한다. `kubectl describe`와 이미 등록된 Event 결과는 대상 UID와 실제 Event 시각을 확인하는 범위의 읽기다. 다른 UID의 Event, 집계된 LAST 시각만으로 원인을 확정하지 않는다.

**Pod 상세 확인 — 아래 한 줄 전체를 복사**

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; else kubectl describe pod "$POD" -n "$NS"; fi`

`describe`에서 volume 이름·PVC source·Conditions와 첫 `FailedAttachVolume`·`FailedMount` message를 본다. 명령 성공은 object 상태 출력만 보장하며 mount 성공이나 application 정상은 보장하지 않는다.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| PVC가 `Pending`이거나 PV 연결이 없음 | 선택한 volume과 PVC/PV identity | StorageClass·provisioning owner | [[#1. Pod volume → PVC/PV/StorageClass\|1]] |
| `FailedAttachVolume`, `Multi-Attach`, attach timeout | PV·VolumeAttachment의 node·attacher·오류 | CSI controller·storage API | [[#2. FailedAttachVolume → VolumeAttachment → CSI controller\|2]] |
| attach 성공 뒤 `FailedMount`, staging/path 오류 | CSI node Pod와 kubelet의 같은 시각 오류 | device·filesystem·mount target | [[#3. FailedMount → CSI node plugin → kubelet\|3]], [[#4. kubelet → OS device/filesystem/mount\|4]] |
| device는 있으나 source·fstype·permission이 다름 | 실제 device와 mount target | Linux filesystem·multipath·node owner | [[#4. kubelet → OS device/filesystem/mount\|4]] |

진단 순서는 `Pod volume → PVC/PV/StorageClass → VolumeAttachment → CSI controller/node → kubelet → OS device/filesystem/mount`다. 앞 계층의 identity가 확인되기 전에는 뒤 계층의 상태 변경이나 복구를 실행하지 않는다.

## 1. Pod volume → PVC/PV/StorageClass

진입 증거는 `VOLUME_SOURCE=pvc`와 Event의 volume 이름 일치다. 최초 필요값은 `PVC`이며 선택한 Pod volume의 API source에서 자동 등록된다. `PVC_READY`가 아니면 PV·VolumeAttachment를 조회하지 않는다.

**PVC·PV·StorageClass 자동 연결 — 아래 한 줄 전체를 복사**

`refresh_pod_identity`

`unset PVC_READY PV STORAGE_CLASS VOLUME_HANDLE PVC_JSON PV_JSON SC_JSON; PVC_READY=false; if [ "$VOLUME_READY" != true ] || [ "$VOLUME_SOURCE" != pvc ]; then printf '%s\n' '중단: 선택 volume이 PVC source가 아니다.' >&2; elif [ -z "$PVC" ]; then printf '%s\n' '중단: PVC claim name이 비어 있다.' >&2; elif PVC_JSON="$(kubectl get pvc "$PVC" -n "$NS" -o json)" && PV="$(jq -r '.spec.volumeName // empty' <<<"$PVC_JSON")" && [ -n "$PV" ] && PV_JSON="$(kubectl get pv "$PV" -o json)" && STORAGE_CLASS="$(jq -r '.spec.storageClassName // empty' <<<"$PVC_JSON")" && VOLUME_HANDLE="$(jq -r '.spec.csi.volumeHandle // empty' <<<"$PV_JSON")" && { [ -z "$STORAGE_CLASS" ] || SC_JSON="$(kubectl get storageclass "$STORAGE_CLASS" -o json)"; }; then PVC_READY=true; export PVC PV STORAGE_CLASS VOLUME_HANDLE; jq -r '"=== PVC ===\n이름: \(.metadata.name)\nUID: \(.metadata.uid)\n생성 시각: \(.metadata.creationTimestamp)\nPhase: \(.status.phase // "-")\nPV: \(.spec.volumeName // "-")\nAccess mode: (\(.spec.accessModes // [])|join(","))\nStorageClass: \(.spec.storageClassName // "-")"' <<<"$PVC_JSON"; jq -r '"=== PV ===\n이름: \(.metadata.name)\nUID: \(.metadata.uid)\n생성 시각: \(.metadata.creationTimestamp)\nPhase: \(.status.phase // "-")\nClaim: \(.spec.claimRef.namespace // "-")/\(.spec.claimRef.name // "-")\nCSI driver: \(.spec.csi.driver // "-")\nVolume handle: \(.spec.csi.volumeHandle // "-")"' <<<"$PV_JSON"; if [ -n "$STORAGE_CLASS" ]; then jq -r '"=== StorageClass ===\n이름: \(.metadata.name)\nUID: \(.metadata.uid)\nProvisioner: \(.provisioner)\nBinding: \(.volumeBindingMode // "-")\nReclaim: \(.reclaimPolicy // "-")"' <<<"$SC_JSON"; else printf '%s\n' 'StorageClass: 명시되지 않음'; fi; else unset PVC_READY PV STORAGE_CLASS VOLUME_HANDLE PVC_JSON PV_JSON SC_JSON; printf '중단: PVC→PV identity 또는 API 조회 실패 pvc=%s\n' "$PVC" >&2; fi`

성공 gate는 `PVC namespace/name → PVC UID → PVC.spec.volumeName → PV UID/claimRef`가 정확히 이어지는 것이다. `Bound`는 binding 상태만 보장하며 attach·stage·publish·OS mount를 보장하지 않는다. `Pending`이면 [[01. PVC가 Pending에서 Bound로 수렴하지 않는 경우]], claimRef·reclaim 문제가 있으면 [[02. PV·PVC의 phase·claimRef·reclaim 상태가 맞지 않는 경우]]로 이관한다. 연결이 비어 있거나 PVC/PV namespace·claimRef가 다르면 다음 계층을 중단하고 storage owner에게 UID와 Event 시각을 전달한다.

**PV→CSI driver·CSIDriver attach requirement gate — 같은 Bash에서 아래 한 줄 전체를 복사**

`refresh_pod_identity`

## 2. FailedAttachVolume → VolumeAttachment (attachRequired=true) → CSI controller

진입 증거는 `FailedAttachVolume`, `Multi-Attach` 또는 attach timeout과 `PVC_READY=true`다. `CSI_ATTACH_REQUIRED=true`이면 연결 경로는 **작업 PC의 kubectl client → API server HTTPS endpoint → VolumeAttachment·CSI controller Pod → external-attacher → storage API**다. `CSI_ATTACH_REQUIRED=false`이면 VolumeAttachment 후보 수집을 건너뛰고 **PV → CSI driver → CSINode → kubelet** 경로로 이동한다. API server에 도달한 성공은 controller·storage API의 성공을 보장하지 않으며, attach가 필요한 경우 VolumeAttachment의 node·PV·attacher를 먼저 확정한다.

**VolumeAttachment 후보 수집 — 아래 한 줄 전체를 복사**

후보가 복수일 때는 위의 PV·node·attacher·시각을 대조한 뒤에만 선택한다. `attachRequired=false`에서 `ATTACHMENT_READY=true`는 VolumeAttachment object가 확인됐다는 뜻이 아니라, 해당 hop이 적용되지 않는다는 gate다.

`if [ "$CSI_ATTACH_REQUIRED" = true ] && [ "$AUTO_READY" = true ] && [ "$PVC_READY" = true ] && [ "${VA_COUNT:-0}" -gt 1 ]; then ATTACHMENT_READY=false; VOLUMEATTACHMENT='PASTE_VOLUMEATTACHMENT_HERE'; if jq -e --arg name "$VOLUMEATTACHMENT" --arg pv "$PV" --arg node "$NODE" 'any(.items[]?; .metadata.name==$name and .spec.source.persistentVolumeName==$pv and .spec.nodeName==$node)' <<<"$VA_JSON" >/dev/null; then ATTACHMENT_READY=true; export VOLUMEATTACHMENT; printf 'ATTACHMENT_READY=true selected=%s\n' "$VOLUMEATTACHMENT"; else printf '중단: 선택한 VolumeAttachment가 PV·node 후보와 일치하지 않음 name=%s\n' "$VOLUMEATTACHMENT" >&2; fi; else printf '%s\n' '복수 후보 선택 단계가 아니거나 attachRequired=false이다.'; fi`

선택한 이름이 실제 후보가 아니거나 PV·node가 Pod mapping과 다르면 `ATTACHMENT_READY`를 만들지 않는다. `attachRequired=false`에서는 VolumeAttachment 이름을 만들지 않고 `ATTACHMENT_READY=true`만 hop 제외 gate로 기록한다. `attached=false`와 attach error는 CSI controller·storage API·권한·node 대상 분기로, `attached=true`인데 `FailedMount`가 계속되면 3절로 이동한다. `Multi-Attach`는 기존 consumer·access mode를 확인하고 [[03. VolumeAttachment가 수렴하지 않거나 Multi-Attach가 발생하는 경우]]로 이관하며 강제 detach나 VolumeAttachment 삭제를 하지 않는다.

CSI controller Pod·container 이름은 platform inventory에서 attacher와 PV의 CSI driver에 연결해 확인한다. `attachRequired=false`에서는 controller publish/VolumeAttachment 후보를 만들지 않는다. inventory 확인 전 cluster 전체 Pod 목록을 CSI controller 후보로 사용하지 않는다.

`NODE_HOST='PASTE_NODE_HOST_HERE'`

`NODE_API_READY=false; NODE_API_JSON=''; if [ "$POD_IDENTITY_READY" != true ] || [ "$NODE" = - ] || [ -z "$NODE_HOST" ]; then printf '%s\n' '중단: Pod UID·API node·승인 NODE_HOST가 필요하다.' >&2; elif NODE_API_JSON="$(kubectl get node "$NODE" -o json 2>/dev/null)" && jq -e --arg host "$NODE_HOST" '[.metadata.name] + [.status.addresses[]?.address] | any(.==$host)' <<<"$NODE_API_JSON" >/dev/null; then NODE_API_READY=true; printf 'NODE_API_READY=true api_node=%s approved_node_host=%s addresses=%s\n' "$NODE" "$NODE_HOST" "$(jq -r '[.status.addresses[]?.address] | join(",")' <<<"$NODE_API_JSON")"; else printf '중단: 승인 NODE_HOST가 API node name/address와 일치하지 않음 node=%s host=%s\n' "$NODE" "$NODE_HOST" >&2; fi`

**node handoff 값 등록 — 작업 PC의 같은 Bash에서 확인된 unit·시간·target·device를 한 번 입력**

node shell에 작업 PC의 `NODE_READY`, `POD_IDENTITY_READY`, `START_READY`를 복사하지 않는다. 아래 SSH command가 원격에서 Pod UID·`spec.nodeName`, CSI node Pod UID·node, Node API machine ID·remote `/etc/machine-id`, host mapping, 도구·sudo·unit·시간 gate를 모두 다시 확인한다. remote `kubectl` 또는 machine identity 확인이 불가능하면 journal·mount를 실행하지 않고 node owner에게 handoff한다.

**node journal 선택값 등록 — 실제 node의 systemd unit과 Event 전후 시간을 확인한 뒤 작업 PC에서 한 번 실행**

`KUBELET_SERVICE='PASTE_KUBELET_SERVICE_HERE'; START_JOURNAL='PASTE_START_JOURNAL_HERE'; END_JOURNAL='PASTE_END_JOURNAL_HERE'; MOUNT_TARGET='PASTE_MOUNT_TARGET_HERE'; DEVICE_OR_SOURCE='PASTE_DEVICE_OR_SOURCE_HERE'`

`JOURNAL_TIME_READY=false; JOURNAL_START_EPOCH=''; JOURNAL_END_EPOCH=''; JOURNAL_START_CANONICAL=''; JOURNAL_END_CANONICAL=''; if [[ "$START_JOURNAL" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}\ [0-9]{2}:[0-9]{2}:[0-9]{2}\ UTC$ ]] && [[ "$END_JOURNAL" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}\ [0-9]{2}:[0-9]{2}:[0-9]{2}\ UTC$ ]] && JOURNAL_START_EPOCH="$(date -u -d "$START_JOURNAL" +%s 2>/dev/null)" && JOURNAL_END_EPOCH="$(date -u -d "$END_JOURNAL" +%s 2>/dev/null)" && JOURNAL_START_CANONICAL="$(date -u -d "$START_JOURNAL" '+%Y-%m-%d %H:%M:%S UTC' 2>/dev/null)" && JOURNAL_END_CANONICAL="$(date -u -d "$END_JOURNAL" '+%Y-%m-%d %H:%M:%S UTC' 2>/dev/null)" && [ "$JOURNAL_START_CANONICAL" = "$START_JOURNAL" ] && [ "$JOURNAL_END_CANONICAL" = "$END_JOURNAL" ] && [ "$JOURNAL_START_EPOCH" -lt "$JOURNAL_END_EPOCH" ]; then JOURNAL_TIME_READY=true; printf 'JOURNAL_TIME_READY=true start=%s end=%s\n' "$START_JOURNAL" "$END_JOURNAL"; else printf '중단: FailedMount journal은 strict UTC canonical 형식과 시작 시각이 종료 시각보다 앞서야 한다 start=%s end=%s\n' "$START_JOURNAL" "$END_JOURNAL" >&2; fi`

**원격 UID·Node identity·journal·mount read-only handoff — 작업 PC의 같은 Bash에서 아래 한 줄 전체를 복사**

`NODE_REMOTE_READY=false; if [ "$NODE_API_READY" != true ] || [ "$POD_IDENTITY_READY" != true ] || [ "$JOURNAL_TIME_READY" != true ] || [ "$START_READY" != true ] || [ "$CSI_NODE_EVIDENCE_READY" != true ] || [ -z "$PV" ] || [ -z "$VOLUME" ]; then printf '%s\n' '중단: 작업 PC의 API mapping은 handoff일 뿐이며 현재 Pod·CSI node·시간·PV·volume gate가 필요하다.' >&2; elif ssh -- "$NODE_HOST" bash -s -- "$NS" "$POD" "$POD_UID" "$NODE" "$NODE_HOST" "$KUBELET_SERVICE" "$START_JOURNAL" "$END_JOURNAL" "$START_RFC3339" "$PV" "$VOLUME" "$CSI_NODE_NAMESPACE" "$CSI_NODE_POD" "$CSI_NODE_POD_UID" "$MOUNT_TARGET" "$DEVICE_OR_SOURCE" <<< 'set -u; ns="$1"; pod="$2"; pod_uid="$3"; node="$4"; expected_host="$5"; unit="$6"; start="$7"; end="$8"; start_rfc="$9"; pv="${10}"; volume="${11}"; csi_ns="${12}"; csi_pod="${13}"; csi_pod_uid="${14}"; target="${15}"; device="${16}"; missing=""; for tool in kubectl journalctl systemctl findmnt mount lsblk blkid df mountpoint date hostname cat grep; do command -v "$tool" >/dev/null 2>&1 || missing="$missing $tool"; done; if [ -n "$missing" ] || ! sudo -n -v >/dev/null 2>&1; then printf "중단: remote 도구·sudo read gate 실패 missing=%s\\n" "$missing" >&2; exit 1; fi; actual_host="$(hostname -f 2>/dev/null || hostname)"; short_host="$(hostname 2>/dev/null || true)"; api_node="$(kubectl get node "$node" -o "jsonpath={.metadata.name}" 2>/dev/null)"; api_machine="$(kubectl get node "$node" -o "jsonpath={.status.nodeInfo.machineID}" 2>/dev/null)"; current_csi_uid="$(kubectl get pod "$csi_pod" -n "$csi_ns" -o "jsonpath={.metadata.uid}" 2>/dev/null)"; current_csi_node="$(kubectl get pod "$csi_pod" -n "$csi_ns" -o "jsonpath={.spec.nodeName}" 2>/dev/null)"; rfc_epoch="$(date -u -d "$start_rfc" +%s 2>/dev/null)"; rfc_canonical="$(date -u -d "$start_rfc" "+%Y-%m-%dT%H:%M:%SZ" 2>/dev/null)"; if [[ "$start" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}\ [0-9]{2}:[0-9]{2}:[0-9]{2}\ UTC$ ]] && [[ "$end" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}\ [0-9]{2}:[0-9]{2}:[0-9]{2}\ UTC$ ]] && [ "$start_canonical" = "$start" ] && [ "$end_canonical" = "$end" ] && [ -n "$start_epoch" ] && [ -n "$end_epoch" ] && [ "$start_epoch" -lt "$end_epoch" ] && [[ "$start_rfc" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] && [ "$rfc_canonical" = "$start_rfc" ] && [ -n "$rfc_epoch" ] && [ "$api_node" = "$node" ] && [ "$current_uid" = "$pod_uid" ] && [ "$current_node" = "$node" ] && [ "$current_csi_uid" = "$csi_pod_uid" ] && [ "$current_csi_node" = "$node" ] && [ "$api_machine" = "$local_machine" ] && { [ "$actual_host" = "$expected_host" ] || [ "$short_host" = "$expected_host" ]; exit 1; fi' ; then NODE_REMOTE_READY=true; printf 'NODE_REMOTE_READY=true remote_host=%s pod_uid=%s node=%s csi_node_pod_uid=%s journal=%s mount=%s\\n' "$NODE_HOST" "$POD_UID" "$NODE" "$CSI_NODE_POD_UID" "$JOURNAL_TIME_READY" "$NODE_REMOTE_READY"; else printf '중단: self-contained SSH node handoff 실패; journal·mount를 실행하지 않음\\n' >&2; fi`

`MountVolume.SetUp failed`와 CSI node의 같은 volume·시각 오류가 성공 gate다. journal이 비거나 unit 조회가 실패하면 오류 없음이 아니라 시간·unit·권한·node 접근 문제 후보다. kubelet 재시작이나 인증서 변경을 하지 말고 node owner에게 이관한다.

SSH handoff의 read-only 출력에서 `findmnt`의 source·target·fstype·options, 실제 device/filesystem, target 사용량·mount 여부를 비교한다. target source/fstype 불일치·device 부재는 CSI stage/publish로 돌아간다. wrong fs type, read-only, inode/space 부족, permission·multipath는 Linux filesystem·node owner로 이관한다. filesystem 검사·repair·mkfs·수동 mount·device 삭제는 이 문서에서 실행하지 않는다. SSH가 실패하거나 gate가 닫히면 빈 journal·mount 결과를 정상으로 기록하지 않는다.

## 상태 변경 gate와 정상화

이 런북의 기본 action은 원인 계층을 확정해 application·CSI·storage·node owner에게 이관하는 것이다. 진단 명령에는 상태 변경을 섞지 않는다. 별도 변경이 필요하면 다음을 모두 기록한다.

- **Trigger:** Pod volume과 PVC/PV/StorageClass, VolumeAttachment node·attacher·오류, CSI·kubelet·OS의 같은 시각 증거가 연결됐다.
- **Authority/approval:** 대상 cluster·namespace·Pod UID·consumer·node·StatefulSet/quorum·서비스 영향·변경 창·담당 owner·승인을 대조했다.
- **대상·rollback:** 확인된 선언과 consumer만 대상으로 하고 변경 전 원본과 복구 절차를 보존한다.
- **금지·중단:** force detach, VolumeAttachment 강제 삭제, filesystem repair/format, 수동 mount, 원인 미확정 Pod 삭제·CSI/kubelet 재시작을 하지 않는다. 다른 consumer 영향, Warning 증가, device/filesystem 오류 확대 또는 Ready 감소 시 중단한다.
- **검증 한계:** 재시도 성공은 attach/mount 재시도만 의미하며 CSI·storage·node 근본 원인이나 data integrity를 보장하지 않는다.

정상화는 `OS device/mount → kubelet → CSI node → CSI controller/VolumeAttachment (attachRequired=true일 때) → PV/PVC/StorageClass → Pod` 역순으로 확인한다. 기대한 device·fstype·target mount, CSI stage/publish 성공, 새 Warning 중단, attach가 필요한 경우 VolumeAttachment 상태, PVC/PV 연결과 desired/Ready replica, 동일 Pod UID의 restart 증가 중단을 확인한 뒤 실제 요청·핵심 기능과 재발 관찰 창을 통과시킨다. `attachRequired=false`의 VolumeAttachment 부재는 실패가 아니지만 PV→driver→CSINode→kubelet identity와 stage/publish evidence가 필요하다. `Bound`, `Running`, `Ready`는 각각 binding·phase·condition의 범위만 보장하고 실제 mount·application 기능을 보장하지 않는다.

## Prometheus 빠른 관측

Prometheus metric과 `namespace`, `pod`, `persistentvolumeclaim` label이 실제 수집될 때만 사용한다. API 조회 실패, metric 부재, label 불일치, selector 범위 오류를 구분한다. 아래 query는 사용자가 내부 값을 고치지 않고 등록된 변수로 완성한다.

**PromQL selector 계산 — 같은 Bash에서 아래 한 줄 전체를 복사**

`refresh_pod_identity`

`unset POD_RE PVC_RE PROMQL_READY; POD_RE="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; PVC_RE=''; if [ -n "${PVC:-}" ]; then PVC_RE="$(printf '%s' "$PVC" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; fi; if [ -n "$POD_RE" ]; then PROMQL_READY=true; printf 'PROMQL_READY=true pod_re=%s pvc_re=%s\n' "$POD_RE" "${PVC_RE:--}"; else printf '%s\n' '중단: PromQL selector 계산 실패' >&2; fi`

**Pod phase PromQL 생성 — 아래 한 줄 전체를 복사**

`if [ "$PROMQL_READY" != true ] || [ "$POD_IDENTITY_READY" != true ]; then printf '%s\n' '중단: PROMQL_READY와 Pod UID gate가 아니다.' >&2; else printf 'kube_pod_status_phase{namespace="%s",pod=~"%s",uid="%s",phase="Pending"}==1\n' "$NS" "$POD_RE" "$POD_UID"; fi`

**PVC phase PromQL 생성 — PVC source일 때 아래 한 줄 전체를 복사**

`if [ "$PROMQL_READY" != true ] || [ -z "$PVC_RE" ]; then printf '%s\n' '중단: PVC selector가 없어 PVC query를 만들지 않는다.' >&2; else printf 'kube_persistentvolumeclaim_status_phase{namespace="%s",persistentvolumeclaim=~"%s",phase!="Bound"}==1\n' "$NS" "$PVC_RE"; fi`

query 출력이 비면 정상·0·오류 없음으로 해석하지 않는다. Prometheus transport/API 조회 실패인지, metric 미수집인지, label 불일치인지, 실제 series 부재인지 확인하고 Event·VolumeAttachment·CSI·kubelet을 우선 증거로 사용한다.

## 증거 보존과 1.26 경계

namespace, Pod UID·node·owner·phase, volume source, PVC/PV/StorageClass UID·생성 시각·claim 연결, Event UID·대상 UID·첫 message와 실제 시각, VolumeAttachment UID·PV·node·attacher·error, CSI Pod/container UID, kubelet·CSI·OS의 결정적 오류 행, 영향 범위·승인·이관·정상화 결과를 보존한다. Secret·token·인증서 개인키·개인정보와 불필요한 전체 로그는 보존하지 않는다.

Kubernetes Server와 kubectl은 `1.26.x` 기준이다. CSI driver, controller/node Pod label·container, kubelet unit, cloud storage API, device path, Linux filesystem·multipath와 로그 위치는 환경별 미검증이다. 구현체 확인 전 특정 unit·DaemonSet·driver·socket을 기본값으로 사용하지 않는다.
