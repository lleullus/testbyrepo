# Pod exec 권한이 거부되는 경우

## 입력값과 빠른 수집

이 문서는 `pods/exec` API 인가 거부와 exec 이후 container 내부 권한 오류를 구분한다. 자동으로 확정되는 Pod identity와 운영자가 오류 원문·승인 기록을 보고 고르는 값은 섞지 않는다. 다음 값은 최초 입력, API 확인 자동값, 계산 후보, 운영자 선택값으로 분류한다.

| 종류 | 값 | 출처와 사용 범위 |
|---|---|---|
| 최초 입력 | `CTX`, `NS`, `POD` | 승인된 작업 context와 namespace·Pod 이름. 같은 Bash에서 한 번만 입력한다. |
| API 확인 자동값 | `POD_UID`, `NODE`, `PHASE`, `RESOURCE_VERSION`, `OBSERVED_AT`, `ACTUAL_USER`, `ACTUAL_GROUP`, `ROLE_REF_KIND`, `ROLE_REF_NAME` | Pod API snapshot, 허용된 SelfSubjectReview와 RoleBinding의 `roleRef`에서 등록한다. UID와 UTC 시각을 이름보다 우선한다. whoami가 거부되면 audit의 user identity를 사용한다. |
| 계산 후보 | `POD_RE`, `PROM_WINDOW` | Pod 이름을 정규식에 넣을 때 escape한 값과 기본 PromQL 관측 창. 후보 출력 뒤에만 사용한다. |
| 운영자 선택값 | `CONTAINER`, `EXEC_COMMAND`, `TARGET_PATH`, `START_RFC3339`, `ROLEBINDING`, `SUBJECT`, `AS_GROUP` | 오류 원문, Pod 출력, 승인된 allowlist·RBAC evidence를 확인한 뒤 해당 분기에서만 입력한다. `ROLE_REF_KIND/NAME`과 Role·ClusterRole 대상은 RoleBinding API에서 자동 확정하며 token·Secret·개인키는 값으로 사용하지 않는다. |

### 실행 계약과 도구 gate

명령은 승인된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. `kubectl`은 Kubernetes Server와 client가 1.26.x이고 입력한 context를 사용할 수 있어야 한다. API 조회 권한, 대상 Pod 조회 권한, 진단 명령별 `pods/exec`, `pods/log` 또는 RBAC 조회 권한은 서로 다르다. 도구 gate가 실패하면 다음 단계로 진행하지 않는다.

`TOOLS_READY=false; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else MISSING_TOOLS=''; for TOOL in kubectl jq grep sed date mktemp; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true shell=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 입력·API 수집·exec를 실행하지 않는다. 필요한 RBAC나 audit 권한이 없으면 권한을 넓히지 말고 같은 범위의 출력과 오류 원문을 담당자에게 요청한다.

### 최초 입력과 이전 상태 초기화

재실행 전에 이전 Pod UID, 계산 정규식, 단계 gate와 stream 관련 값을 지운다. 아래 세 값만 직접 바꾸며 각각 문서 전체에서 한 번만 나타난다.

`reset_pod34_downstream(){ unset AUTO_READY POD_UID NODE PHASE RESOURCE_VERSION OBSERVED_AT POD_RE PROM_WINDOW CONTAINER EXEC_COMMAND TARGET_PATH START_RFC3339 START_CANONICAL START_EPOCH EXEC_CONTAINER_ID EXEC_TARGET_READY ROLEBINDING SUBJECT AS_GROUP ROLE_REF_KIND ROLE_REF_NAME AUTH_READY AUTH_EXEC_RESULT AUTH_RECHECK_READY LOG_AUTH_READY LOG_SELECTION_READY INTERNAL_SELECTION_READY PATH_SELECTION_READY RBAC_SELECTION_READY IMPERSONATION_READY WHOAMI_READY ACTUAL_USER ACTUAL_GROUP AUTH_GET_RESULT AUTH_RECHECK_RESULT LOG_GET_RESULT LOG_SUBRESOURCE_RESULT AUTH_CAN_I_STDOUT AUTH_CAN_I_STDERR AUTH_CAN_I_RC WHOAMI_JSON POD_JSON POD_CHECK_JSON POD_LOG_CHECK_JSON POD_EXEC_JSON ROLEBINDING_JSON ROLE_REF_KIND_TMP ROLE_REF_NAME_TMP ROLE_JSON CLUSTERROLE_JSON CURRENT_EXEC_CONTAINER_ID; AUTO_READY=false; AUTH_READY=false; AUTH_RECHECK_READY=false; LOG_AUTH_READY=false; LOG_SELECTION_READY=false; INTERNAL_SELECTION_READY=false; PATH_SELECTION_READY=false; RBAC_SELECTION_READY=false; IMPERSONATION_READY=false; WHOAMI_READY=false; ROLE_READY=false; CLUSTERROLE_READY=false; EXEC_TARGET_READY=false; }; reset_pod34_downstream; unset INPUT_READY; CTX='PASTE_CONTEXT_HERE'; NS='PASTE_NAMESPACE_HERE'; POD='PASTE_POD_HERE'; INPUT_READY=false; if [ "$TOOLS_READY" != true ]; then printf '%s\n' '중단: TOOLS_READY가 아니다.' >&2; elif [ -z "$CTX" ] || [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: CTX·NS·POD를 입력한다.' >&2; elif kubectl --context "$CTX" get pod "$POD" -n "$NS" -o name >/dev/null 2>&1; then INPUT_READY=true; export CTX NS POD; printf 'INPUT_READY=true context=%s namespace=%s pod=%s\n' "$CTX" "$NS" "$POD"; else printf '중단: exact-name Pod 조회 실패 context=%s namespace=%s pod=%s\n' "$CTX" "$NS" "$POD" >&2; fi`

`INPUT_READY=true`가 아니면 다음 단계로 가지 않는다. namespace를 모르면 broad query로 임의 선택하지 말고 승인된 namespace를 확인한 뒤 위 입력 절을 다시 실행한다.

`unset AUTH_READY AUTH_EXEC_RESULT AUTH_RECHECK_READY LOG_AUTH_READY AUTH_CAN_I_STDOUT AUTH_CAN_I_STDERR AUTH_CAN_I_RC`

### API 자동 수집과 등록

자동 출력은 한 대상 Pod의 UID·node·phase·관측 시각과 container별 상태·ID·port 후보 관계를 세로 블록으로 보여 준다. `containerPort`는 선언 후보이지 실제 listener나 exec 가능성을 보장하지 않는다. API 호출이 실패하거나 필수 값이 비면 이전 값을 남기지 않는다.

`if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif POD_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)"; then jq -r '"=== 대상 Pod ===\n네임스페이스: \(.metadata.namespace)\nPod: \(.metadata.name)\nUID: \(.metadata.uid)\nNode: \(.spec.nodeName // "-")\nPhase: \(.status.phase // "-")\nResourceVersion: \(.metadata.resourceVersion // "-")\n생성 시각: \(.metadata.creationTimestamp // "-")\n\n=== Container별 후보 ===\n" + ([.spec.containers[]? as $c | (first(.status.containerStatuses[]? | select(.name==$c.name)) // {}) as $s | "컨테이너: \($c.name)\n  Port 후보: \([ $c.ports[]? | ((.name // "unnamed") + ":" + (.containerPort|tostring)) ] | join(", ") | if .=="" then "-" else . end)\n  Ready: \($s.ready // "-")\n  Container ID: \($s.containerID // "-")\n  State: \($s.state | tostring)\n  Last State: \($s.lastState | tostring)\n  Restart: \($s.restartCount // "-")"] | join("\n\n"))' <<<"$POD_JSON"; else printf '%s\n' '중단: Pod API snapshot 조회 실패' >&2; fi`

출력에서 대상 Pod의 UID·node·phase와 각 container의 이름·status·ID·port 후보를 확인한다. container 목록이 비거나 UID가 없으면 정상·권한 허용으로 해석하지 않고 context·namespace·API 권한을 확인한다.

`reset_pod34_downstream && if [ "$INPUT_READY" != true ]; then printf '%s\n' '중단: INPUT_READY가 아니다.' >&2; elif POD_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && OBSERVED_AT="$(date -u '+%Y-%m-%dT%H:%M:%SZ')" && POD_UID_TMP="$(jq -r '.metadata.uid // empty' <<<"$POD_JSON")" && NODE_TMP="$(jq -r '.spec.nodeName // empty' <<<"$POD_JSON")" && PHASE_TMP="$(jq -r '.status.phase // empty' <<<"$POD_JSON")" && RESOURCE_VERSION_TMP="$(jq -r '.metadata.resourceVersion // empty' <<<"$POD_JSON")"; then POD_RE_ESCAPED="$(printf '%s' "$POD" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; if [ -z "$POD_UID_TMP" ] || [ -z "$PHASE_TMP" ] || [ -z "$RESOURCE_VERSION_TMP" ] || [ -z "$POD_RE_ESCAPED" ]; then printf '%s\n' '중단: 자동값이 비어 있어 부분 등록을 폐기함' >&2; else POD_UID="$POD_UID_TMP"; NODE="$NODE_TMP"; PHASE="$PHASE_TMP"; RESOURCE_VERSION="$RESOURCE_VERSION_TMP"; POD_RE="^${POD_RE_ESCAPED}$"; PROM_WINDOW='15m'; AUTO_READY=true; export POD_UID NODE PHASE RESOURCE_VERSION OBSERVED_AT POD_RE PROM_WINDOW; printf 'AUTO_READY=true 관측시각=%s UID=%s Node=%s Phase=%s ResourceVersion=%s POD_RE=%s PROM_WINDOW=%s\n' "$OBSERVED_AT" "$POD_UID" "${NODE:--}" "$PHASE" "$RESOURCE_VERSION" "$POD_RE" "$PROM_WINDOW"; fi; unset POD_UID_TMP NODE_TMP PHASE_TMP RESOURCE_VERSION_TMP POD_RE_ESCAPED; else printf '%s\n' '중단: API 자동값 수집 실패; 이전 파생값을 사용하지 않음' >&2; fi`

후속 Pod snapshot은 최초 자동값의 `$POD_UID`와 대조한다. 함수가 `jq` 실패 또는 UID mismatch를 반환하면 호출한 분기의 gate를 열지 않고 stale container·node·status를 사용하지 않는다.

`pod_uid_matches(){ local pod_json="$1" current_uid; current_uid="$(jq -r '.metadata.uid // empty' <<<"$pod_json")" || { AUTO_READY=false; AUTH_READY=false; AUTH_RECHECK_READY=false; LOG_AUTH_READY=false; LOG_SELECTION_READY=false; INTERNAL_SELECTION_READY=false; PATH_SELECTION_READY=false; RBAC_SELECTION_READY=false; IMPERSONATION_READY=false; WHOAMI_READY=false; ROLE_READY=false; CLUSTERROLE_READY=false; EXEC_TARGET_READY=false; return 1; }; if [ -n "$current_uid" ] && [ "$current_uid" = "$POD_UID" ]; then return 0; else AUTO_READY=false; AUTH_READY=false; AUTH_RECHECK_READY=false; LOG_AUTH_READY=false; LOG_SELECTION_READY=false; INTERNAL_SELECTION_READY=false; PATH_SELECTION_READY=false; RBAC_SELECTION_READY=false; IMPERSONATION_READY=false; WHOAMI_READY=false; ROLE_READY=false; CLUSTERROLE_READY=false; EXEC_TARGET_READY=false; return 1; fi; }`

`auth_can_i_result(){ local stdout_file='' stderr_file='' stdout_raw='' stderr_raw='' stdout='' stderr='' rc; if ! stdout_file="$(mktemp)" || ! stderr_file="$(mktemp)"; then [ -z "$stdout_file" ] || rm -f -- "$stdout_file"; [ -z "$stderr_file" ] || rm -f -- "$stderr_file"; printf '%s\n' '중단: auth can-i stdout/stderr 임시 파일 생성 실패' >&2; return 1; fi; if kubectl --context "$CTX" auth can-i "$@" >"$stdout_file" 2>"$stderr_file"; then rc=0; else rc=$?; fi; if IFS= read -r -d '' stdout_raw <"$stdout_file"; then :; fi; if IFS= read -r -d '' stderr_raw <"$stderr_file"; then :; fi; rm -f -- "$stdout_file" "$stderr_file"; AUTH_CAN_I_STDOUT="$stdout_raw"; AUTH_CAN_I_STDERR="$stderr_raw"; AUTH_CAN_I_RC="$rc"; stdout="$stdout_raw"; if [[ "$stdout" == *$'\n' ]]; then stdout="${stdout%$'\n'}"; fi; stderr="$stderr_raw"; if [ "$rc" -eq 0 ] && [ -z "$stderr" ] && [ "$stdout" = yes ] && [[ "$stdout_raw" != *$'\n'*$'\n'* ]]; then printf '%s\n' yes; return 0; elif [ "$rc" -eq 1 ] && [ -z "$stderr" ] && [[ "$stdout" != *$'\n'* ]] && { [ "$stdout" = no ] || { [[ "$stdout" == 'no - '* ]] && [ "${#stdout}" -gt 5 ]; }; }; then printf '%s\n' no; return 0; else printf '중단: auth can-i 실패 또는 예상하지 않은 출력 rc=%s stdout=%q stderr=%q\n' "$rc" "$stdout_raw" "$stderr_raw" >&2; return 1; fi; }`

`running_container_id(){ jq -r --arg c "$CONTAINER" 'first(.status.containerStatuses[]? | select(.name==$c) | select(.state.running != null) | .containerID // empty)' <<<"$1"; }`

`unset WHOAMI_READY ACTUAL_USER ACTUAL_GROUP; WHOAMI_READY=false; if [ "$AUTO_READY" != true ]; then printf '%s\n' 'whoami 중단: AUTO_READY가 아니다.' >&2; elif WHOAMI_JSON="$(kubectl --context "$CTX" alpha auth whoami -o json)" && ACTUAL_USER_TMP="$(jq -r '.status.userInfo.username // empty' <<<"$WHOAMI_JSON")" && ACTUAL_GROUP_TMP="$(jq -r '[.status.userInfo.groups[]?] | join(",")' <<<"$WHOAMI_JSON")"; then if [ -n "$ACTUAL_USER_TMP" ]; then ACTUAL_USER="$ACTUAL_USER_TMP"; ACTUAL_GROUP="$ACTUAL_GROUP_TMP"; WHOAMI_READY=true; export ACTUAL_USER ACTUAL_GROUP; printf 'WHOAMI_READY=true actual-user=%s groups=%s UID=%s\n' "$ACTUAL_USER" "${ACTUAL_GROUP:--}" "$POD_UID"; else printf '%s\n' 'whoami 중단: username이 비어 있음; audit identity를 사용함' >&2; fi; unset WHOAMI_JSON ACTUAL_USER_TMP ACTUAL_GROUP_TMP; else printf '%s\n' 'whoami 조회 거부 또는 실패; 반복하지 말고 audit identity를 사용함' >&2; fi`

`WHOAMI_READY=true`가 아니면 현재 주체를 오류 subject와 같다고 쓰지 않는다. SelfSubjectReview가 비활성화·거부된 경우 token이나 kubeconfig raw credential을 출력하지 말고 audit의 `user.username`, `user.groups`를 사용한다.

`AUTO_READY=true`이고 UID·phase·resourceVersion·bounded `POD_RE`가 출력된 경우에만 최초 확인으로 이동한다. `Running` 또는 `Ready`는 `pods/exec` 인가, stream 준비, container 명령 실행을 보장하지 않는다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | `kubectl exec`가 `Forbidden`, `cannot create resource "pods/exec"`, `User cannot create pods/exec`를 반환하거나 exec 후 container 내부에서 `permission denied`가 보이는 경우 |
| 적용 | 같은 context·namespace·Pod UID와 오류의 subject, resource, subresource, verb를 대조할 수 있는 경우 |
| 제외 | API server 도달 실패·HTTP upgrade·stream timeout은 [[33. Pod exec 연결이 실패하는 경우]], 대상 container 선택은 [[31. Pod exec 대상 컨테이너를 찾을 수 없는 경우]]로 이동한다. |

검색 문자열: `Forbidden`, `cannot create resource "pods/exec"`, `User cannot create pods/exec`, `pods/exec is forbidden`, `permission denied`, `Operation not permitted`, `authorization`, `impersonate`, `RBAC`.

오류 원문의 `User`, namespace, resource, subresource, verb와 UTC 관측 시각을 보존한다. token·Secret·인증서 개인키와 개인정보는 저장하지 않는다.

## 최초 확인

`AUTO_READY=true`일 때만 다음 읽기 명령을 실행한다. 명령은 모두 같은 context와 namespace를 사용한다.

`if [ "$AUTO_READY" = true ] && POD_CHECK_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && pod_uid_matches "$POD_CHECK_JSON"; then jq -r '"Pod=" + .metadata.name + " UID=" + .metadata.uid + " Node=" + (.spec.nodeName // "-") + " Phase=" + (.status.phase // "-") + " ResourceVersion=" + (.metadata.resourceVersion // "-")' <<<"$POD_CHECK_JSON"; else printf '%s\n' '중단: AUTO_READY, Pod API 또는 최초 UID 검증 실패' >&2; fi`

성공 gate는 출력의 UID가 `$POD_UID`, 관측 시각이 현재 조사 창과 일치하는 것이다. `get` 성공은 API 조회 성공만 보장하며 exec 권한이나 application 정상을 보장하지 않는다. 실패·빈 대상이면 이후 `can-i`를 다른 Pod로 실행하지 않고 identity를 다시 확정한다.

`if [ "$AUTO_READY" = true ] && POD_CHECK_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && pod_uid_matches "$POD_CHECK_JSON"; then kubectl --context "$CTX" describe pod "$POD" -n "$NS"; else printf '%s\n' '중단: 최초 UID와 Pod describe 대상이 일치하지 않음' >&2; fi`

`describe`에서 Conditions, container State·Last State·Reason·Exit Code·Restart Count와 container 이름을 확인한다. `describe`가 성공해도 `pods/exec` subresource 권한은 별도다.

`AUTH_READY=false; if [ "$AUTO_READY" = true ] && AUTH_GET_RESULT="$(auth_can_i_result get pods/"$POD" -n "$NS")" && AUTH_EXEC_RESULT="$(auth_can_i_result create pods/"$POD" --subresource=exec -n "$NS")"; then AUTH_READY=true; printf 'AUTH_READY=true pod-get=%s pods-exec-create=%s UID=%s\n' "$AUTH_GET_RESULT" "$AUTH_EXEC_RESULT" "$POD_UID"; else printf '%s\n' '중단: auth can-i API 실패; partial 권한 결과를 사용하지 않음' >&2; fi`

첫 결과는 일반 Pod `get`, 둘째 결과는 named `pods/exec`의 `create`다. `AUTH_READY=true`이고 결과가 `no`이면 유효한 RBAC 거부 결과이며 API 실패가 아니다. `yes`인 resource-scoped `can-i`는 현재 kubeconfig 주체가 그 권한을 평가받았다는 뜻일 뿐 실제 요청의 subject·context·stream·container command 성공을 보장하지 않는다. `AUTH_READY`가 아니면 partial 권한 결과를 기록하지 않고 API/auth 담당자에게 이관한다.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| `Forbidden`과 `pods/exec`가 함께 보임 | 오류의 subject·namespace·verb와 현재 UID | 현재 주체의 `create pods/exec` 및 audit | [[#오류에서 권한 판정까지]] |
| `can-i create pods/exec`가 `no` | resource/subresource/verb와 Role·Binding | 최소 권한 및 승인 gate | [[#Role·RoleBinding 확인 파이프라인]] |
| `can-i`는 `yes`인데 `permission denied` | stream 통과 뒤 container 실행 사용자·mount | container 내부 POSIX·security 정책 | [[#Container 내부 permission]] |
| `can-i`는 `yes`인데 upgrade·timeout | API server→kubelet→runtime stream | 연결 런북 | [[33. Pod exec 연결이 실패하는 경우]] |
| Pod `get` 또는 `pods/log`만 `yes` | subresource별 verb | 해당 로그 또는 대상 선택 런북 | [[30. Pod 로그 권한이 거부되는 경우]] |

진단 범위를 넓히려고 다른 namespace, wildcard resource/verb, `--all-namespaces`를 사용하지 않는다. TLS 검증 우회, cluster-admin, wildcard binding, root·privileged·추가 capability 권한 완화는 이 문서의 해결책이 아니다.

## 오류에서 권한 판정까지

**진입 증거:** 오류에 `pods/exec`, `create`, `Forbidden`이 함께 있고 오류의 namespace·Pod가 자동 수집한 UID와 맞을 때다. 오류의 `User`와 현재 kubeconfig 주체는 같은 값이라고 추정하지 않는다.

**연결 경계:** `실행 host → kubectl client → API server HTTPS endpoint → API authorization/admission → API server의 streaming proxy → 대상 node/kubelet → container runtime → container process`다. 주소·port는 API server의 HTTPS endpoint와 kubelet/runtime 내부 endpoint가 서로 다르며, exec는 일반 application HTTP 요청이 아니다. API authorization 성공은 kubelet 연결, runtime attach, process 실행을 보장하지 않는다.

**필수값과 출처:** `POD_UID`, `PHASE`, `OBSERVED_AT`은 API 자동값이다. `User`, groups, resource, subresource, verb는 오류 원문과 API audit에서 선택·대조한다. audit 시간은 오류 전후의 실제 UTC 시간 범위로 기록한다.

`AUTH_RECHECK_READY=false; if [ "$AUTO_READY" = true ] && AUTH_RECHECK_RESULT="$(auth_can_i_result create pods/"$POD" --subresource=exec -n "$NS")"; then AUTH_RECHECK_READY=true; printf 'AUTH_RECHECK_READY=true pods-exec-create=%s UID=%s\n' "$AUTH_RECHECK_RESULT" "$POD_UID"; else printf '%s\n' '중단: auth can-i 재평가 API 실패' >&2; fi`

**성공 gate:** 현재 주체의 결과가 `no`이고 audit의 `user.username`, `user.groups`, `objectRef.namespace`, `objectRef.name`, `objectRef.resource=pods`, `objectRef.subresource=exec`, `verb=create`와 `responseStatus.code=403`이 같은 요청을 가리킬 때만 API 인가 거부로 닫는다.

감사 backend에 전달할 범위는 오류 전후의 실제 UTC 시간, `user.username`·`user.groups`, `objectRef.namespace`·`objectRef.name`, `resource=pods`, `subresource=exec`, `verb=create`, `responseStatus.code`·`reason`, `requestURI`, `annotations.authorization.k8s.io/decision`, `impersonatedUser`다. `decision=allow`인데 response가 403이면 admission webhook·policy controller·proxy와 같은 request evidence를 확인하며 RBAC를 넓히지 않는다.

**실패·빈 결과 의미:** `can-i=yes`인데 실제 오류가 있으면 현재 주체와 오류 subject 불일치, stale Pod, admission 거부, 다른 context 또는 stream 계층을 분리한다. audit Event가 없다는 것은 허용이나 오류 없음이 아니며 backend·TTL·필터·권한을 확인한다. `authorization.k8s.io/decision=allow`인데 response가 403이면 RBAC를 넓히지 말고 admission/proxy evidence를 확인한다.

**다음 행동:** 현재 주체와 오류 subject가 다르면 `--as`로 재현하지 않고 인증·proxy·API audit 담당자에게 오류 원문·UID·UTC 시각을 이관한다. `no`와 audit 일치일 때만 Role pipeline으로 이동한다. `yes`와 stream 실패면 [[33. Pod exec 연결이 실패하는 경우]]로 이동한다.

## Pod 조회·logs 권한과 분리

**진입 증거:** 일반 Pod 조회 또는 로그는 되지만 exec만 거부되거나 exec 원인을 로그로 보조 확인해야 할 때다. 이 절에서는 오류 원문의 container와 오류 전후 시각을 운영자가 고른다.

`CONTAINER='PASTE_CONTAINER_HERE'; START_RFC3339='PASTE_START_RFC3339_HERE'; LOG_SELECTION_READY=false; START_CANONICAL=''; START_EPOCH=''; if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; elif [[ ! "$START_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then printf '중단: START_RFC3339 형식 오류=%s\n' "$START_RFC3339" >&2; elif ! START_CANONICAL="$(date -u -d "$START_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" || [ "$START_CANONICAL" != "$START_RFC3339" ] || ! START_EPOCH="$(date -u -d "$START_RFC3339" '+%s' 2>/dev/null)"; then printf '중단: START_RFC3339 canonical calendar round-trip 실패=%s\n' "$START_RFC3339" >&2; elif POD_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && pod_uid_matches "$POD_JSON" && jq -e --arg c "$CONTAINER" 'any(.spec.containers[]?; .name==$c)' <<<"$POD_JSON" >/dev/null; then LOG_SELECTION_READY=true; export CONTAINER START_RFC3339 START_CANONICAL START_EPOCH; printf 'LOG_SELECTION_READY=true container=%s start=%s canonical=%s epoch=%s UID=%s\n' "$CONTAINER" "$START_RFC3339" "$START_CANONICAL" "$START_EPOCH" "$POD_UID"; else printf '중단: container, API 또는 최초 UID 검증 실패\n' >&2; fi`

선택한 container가 현재 Pod spec에 정확히 하나 있어야 다음 명령으로 간다. 복수 후보를 첫 번째로 고르지 않는다.

`logs_filtered(){ local pod_json api_rc grep_rc pipeline_status; if ! pod_json="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" || ! pod_uid_matches "$pod_json"; then printf '%s\n' '중단: logs 실행 직전 Pod API 또는 최초 UID 검증 실패' >&2; return 1; fi; kubectl --context "$CTX" logs "$POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=200 | grep -E -i -C 3 'permission|denied|forbidden|operation not permitted|exec|shell|command|error|timeout|not found'; pipeline_status=("${PIPESTATUS[@]}"); api_rc="${pipeline_status[0]}"; grep_rc="${pipeline_status[1]}"; if [ "$api_rc" -ne 0 ]; then printf '중단: logs API/stream 실패 rc=%s UID=%s\n' "$api_rc" "$POD_UID" >&2; return "$api_rc"; elif [ "$grep_rc" -gt 1 ]; then printf '중단: logs 필터 도구 실패 rc=%s UID=%s\n' "$grep_rc" "$POD_UID" >&2; return "$grep_rc"; else return 0; fi; }`

`logs_filtered`는 grep의 `no match`와 kubectl logs API/stream 실패를 `PIPESTATUS`로 분리한다. producer rc가 0이 아니면 로그 증거 gate를 열지 않는다.

`LOG_AUTH_READY=false; if [ "$LOG_SELECTION_READY" = true ] && LOG_GET_RESULT="$(auth_can_i_result get pods/"$POD" -n "$NS")" && LOG_SUBRESOURCE_RESULT="$(auth_can_i_result get pods/"$POD" --subresource=log -n "$NS")"; then LOG_AUTH_READY=true; printf 'LOG_AUTH_READY=true pod-get=%s pods-log-get=%s UID=%s\n' "$LOG_GET_RESULT" "$LOG_SUBRESOURCE_RESULT" "$POD_UID"; else printf '%s\n' '중단: logs auth API 실패; partial 권한 결과를 사용하지 않음' >&2; fi`

일반 Pod `get=yes`는 metadata/status 읽기일 뿐이고 `pods/log get=yes`는 `pods/exec create`와 무관하다. `Forbidden`이면 [[30. Pod 로그 권한이 거부되는 경우]]로 이동한다.

**연결 경계:** `실행 host → kubectl/API server HTTPS → API server streaming proxy → node/kubelet/runtime → 선택한 container stdout/stderr`다. logs의 transport 성공은 exec stream 성공이나 로그 내용의 원인 확정을 보장하지 않는다.

`if [ "$LOG_SELECTION_READY" = true ] && [ "$LOG_AUTH_READY" = true ]; then logs_filtered; else printf '%s\n' '중단: container 선택 또는 logs auth gate가 아니다.' >&2; fi`

`permission denied`가 보여도 로그 읽기가 성공한 것뿐이며 exec 인가의 증거는 아니다. 필터가 비면 오류 부재로 해석하지 않는다.

`if [ "$LOG_SELECTION_READY" = true ] && [ "$LOG_AUTH_READY" = true ] && POD_LOG_CHECK_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && pod_uid_matches "$POD_LOG_CHECK_JSON"; then if kubectl --context "$CTX" logs "$POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=50; then :; else printf '중단: logs tail API/stream 실패 UID=%s\n' "$POD_UID" >&2; fi; else printf '%s\n' '중단: container 선택, logs auth 또는 실행 직전 UID gate가 아니다.' >&2; fi`

tail도 비면 보존·재생성·조회 권한 한계와 현재 container state를 기록한다. Secret·token·개인정보가 출력되면 저장을 중단하고 필요한 오류 문자열만 남긴다. 로그가 정상인데 exec stream이 실패하면 [[33. Pod exec 연결이 실패하는 경우]]로 돌아간다.

## Container 내부 permission

**진입 증거:** audit와 현재 주체의 `pods/exec create`가 허용되고, 승인된 비파괴 exec가 `permission denied`, `Operation not permitted`, `not readable`, `not executable`을 반환할 때다. `pods/exec create`는 stream을 여는 권리이지 container의 POSIX 권한을 부여하지 않는다.

**필수값:** `CONTAINER`는 앞의 Pod 출력에서 고른 값이며, `EXEC_COMMAND`는 allowlist에 있는 비파괴 명령, `TARGET_PATH`는 승인된 고정 절대 경로다. 이 절에 직접 들어오면 먼저 `CONTAINER` 등록·검증을 완료하고, `EXEC_COMMAND`와 `TARGET_PATH`를 바꾼다.

`EXEC_COMMAND='PASTE_EXEC_COMMAND_HERE'; INTERNAL_SELECTION_READY=false; EXEC_CONTAINER_ID=''; if [ "$AUTO_READY" != true ] || [ -z "${CONTAINER:-}" ]; then printf '%s\n' '중단: AUTO_READY와 CONTAINER가 필요하다.' >&2; elif [ "$EXEC_COMMAND" != id ]; then printf '중단: 승인된 identity 확인 명령은 id여야 함=%s\n' "$EXEC_COMMAND" >&2; elif POD_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && pod_uid_matches "$POD_JSON" && jq -e --arg c "$CONTAINER" 'any(.spec.containers[]?; .name==$c)' <<<"$POD_JSON" >/dev/null && EXEC_CONTAINER_ID="$(running_container_id "$POD_JSON")" && [ -n "$EXEC_CONTAINER_ID" ]; then INTERNAL_SELECTION_READY=true; export EXEC_COMMAND EXEC_CONTAINER_ID; printf 'INTERNAL_SELECTION_READY=true container=%s identity-command=%s containerID=%s UID=%s\n' "$CONTAINER" "$EXEC_COMMAND" "$EXEC_CONTAINER_ID" "$POD_UID"; else printf '%s\n' '중단: 선택 container가 Running이 아니거나 containerID가 없어 identity exec를 승인하지 않음' >&2; fi`

고정 identity 확인은 `id`만 허용하며 path 검사와 독립된 gate다. path 검사는 명령 문자열을 선택하지 않고 고정된 `sh -c` 검사만 사용한다.

`TARGET_PATH='PASTE_TARGET_PATH_HERE'; PATH_SELECTION_READY=false; EXEC_CONTAINER_ID=''; if [ "$AUTO_READY" != true ] || [ -z "${CONTAINER:-}" ]; then printf '%s\n' '중단: AUTO_READY와 CONTAINER가 필요하다.' >&2; elif [[ ! "$TARGET_PATH" = /* ]] || [[ "$TARGET_PATH" == *[!A-Za-z0-9_./-]* ]]; then printf '중단: TARGET_PATH는 allowlist의 고정 절대 경로여야 한다.\n' >&2; elif POD_JSON="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)" && pod_uid_matches "$POD_JSON" && jq -e --arg c "$CONTAINER" 'any(.spec.containers[]?; .name==$c)' <<<"$POD_JSON" >/dev/null && EXEC_CONTAINER_ID="$(running_container_id "$POD_JSON")" && [ -n "$EXEC_CONTAINER_ID" ]; then PATH_SELECTION_READY=true; export TARGET_PATH EXEC_CONTAINER_ID; printf 'PATH_SELECTION_READY=true container=%s path=%s containerID=%s UID=%s\n' "$CONTAINER" "$TARGET_PATH" "$EXEC_CONTAINER_ID" "$POD_UID"; else printf '%s\n' '중단: 선택 container가 Running이 아니거나 containerID가 없어 path exec를 승인하지 않음' >&2; fi`

명령 문자열은 오류 원문이나 임의 shell 코드를 재사용하지 않는다. image에 `sh`와 `test`가 확인되지 않았으면 shell을 추가하거나 image를 변경하지 않고 명령·image 런북으로 이관한다.

`fresh_exec_target(){ local pod_json current_container_id deletion_timestamp; EXEC_TARGET_READY=false; POD_EXEC_JSON=''; CURRENT_EXEC_CONTAINER_ID=''; if ! pod_json="$(kubectl --context "$CTX" get pod "$POD" -n "$NS" -o json)"; then printf '%s\n' '중단: exec 직전 fresh Pod API 조회 실패; exec/evidence를 실행하지 않음' >&2; return 1; elif ! jq -e --arg uid "$POD_UID" --arg c "$CONTAINER" '(.metadata.uid == $uid) and (.metadata.deletionTimestamp == null) and any(.spec.containers[]?; .name == $c) and any(.status.containerStatuses[]?; .name == $c and .state.running != null and ((.containerID // "") != ""))' <<<"$pod_json" >/dev/null; then deletion_timestamp="$(jq -r '.metadata.deletionTimestamp // empty' <<<"$pod_json")"; if [ -n "$deletion_timestamp" ]; then printf '중단: exec 직전 fresh target Pod가 삭제 중임 deletionTimestamp=%s; exec/evidence를 실행하지 않음\n' "$deletion_timestamp" >&2; else printf '%s\n' '중단: exec 직전 fresh target의 Pod UID·container Running·containerID 검증 실패; exec/evidence를 실행하지 않음' >&2; fi; return 1; fi; current_container_id="$(running_container_id "$pod_json")"; if [ -z "$current_container_id" ] || [ "$current_container_id" != "${EXEC_CONTAINER_ID:-}" ]; then printf '%s\n' '중단: exec 직전 fresh target의 current containerID가 승인된 ID와 다름; exec/evidence를 실행하지 않음' >&2; return 1; fi; POD_EXEC_JSON="$pod_json"; CURRENT_EXEC_CONTAINER_ID="$current_container_id"; EXEC_TARGET_READY=true; return 0; }`

**연결 경계:** `실행 host → API server HTTPS/stream upgrade → kubelet → runtime exec → container PID/파일시스템`이다. API stream 준비는 내부 파일·mount·capability·seccomp 정책을 보장하지 않는다.

`if [ "$INTERNAL_SELECTION_READY" = true ] && [ "${AUTH_EXEC_RESULT:-}" = yes ] && fresh_exec_target; then jq -r --arg c "$CONTAINER" 'first(.spec.containers[]? | select(.name==$c) | "컨테이너: \(.name)\nSecurityContext: \(.securityContext // {})\nVolumeMounts: \(.volumeMounts // [])") // empty' <<<"$POD_EXEC_JSON" && kubectl --context "$CTX" exec "$POD" -n "$NS" -c "$CONTAINER" -- "$EXEC_COMMAND"; else printf '%s\n' '중단: AUTH_EXEC_RESULT=yes, fresh target 또는 동일 containerID 검증 실패; identity exec를 실행하지 않음' >&2; fi`

**성공 gate:** `id`의 UID/GID와 명령 성공은 stream과 해당 명령 실행만 확인한다. `runAsUser`, `runAsGroup`, `fsGroup`, `readOnlyRootFilesystem`, capability·seccomp, 대상 mount의 readOnly와 실행 사용자를 대조한다. `command not found`, exit 126·127이면 [[32. Pod exec 명령을 찾을 수 없는 경우]]로 이동한다.

`permission denied` 또는 `not readable`은 image mode·mount owner/mode·실행 사용자 불일치 후보다. `Operation not permitted`는 capability·seccomp·LSM·mount 정책 후보다. root·privileged·capability 완화로 닫지 말고 동일 Pod UID와 오류 UTC를 image/mount/node 보안 담당자에게 이관한다.

`if [ "$PATH_SELECTION_READY" = true ] && [ "${AUTH_EXEC_RESULT:-}" = yes ] && fresh_exec_target; then kubectl --context "$CTX" exec "$POD" -n "$NS" -c "$CONTAINER" -- sh -c 'id; test -r "$1" && echo readable || echo not-readable; test -x "$1" && echo executable || echo not-executable' sh "$TARGET_PATH"; else printf '%s\n' '중단: AUTH_EXEC_RESULT=yes, fresh target 또는 동일 containerID 검증 실패; path exec를 실행하지 않음' >&2; fi`

빈 결과나 비정상 종료는 오류 없음이 아니다. container image의 shell·test 존재, mount와 보안 정책을 확인하고, 직접 증거가 없으면 미확정으로 남긴다.

## Role·RoleBinding 확인 파이프라인

**진입 증거:** 현재 실제 주체의 named `pods/exec create`가 `no`이고 audit의 namespace·Pod·subresource·verb·subject가 오류와 일치할 때다. Role 조회 권한이 없으면 RBAC 관리자에게 같은 범위의 출력만 요청한다.

**필수값:** `ROLEBINDING`과 오류·audit의 `SUBJECT`는 승인된 RBAC evidence에서 운영자가 선택한다. `roleRef.kind`와 `roleRef.name`은 RoleBinding API에서 읽으며, 이름을 추측하거나 첫 번째 binding을 자동 선택하지 않는다.

`ROLEBINDING='PASTE_ROLEBINDING_HERE'; SUBJECT='PASTE_ERROR_SUBJECT_HERE'; RBAC_SELECTION_READY=false; if [ "$AUTO_READY" != true ] || [ "$AUTH_READY" != true ] || [ "${AUTH_EXEC_RESULT:-}" != no ] || [ -z "$ROLEBINDING" ] || [ -z "$SUBJECT" ]; then printf '%s\n' '중단: AUTO_READY·AUTH_READY·pods/exec create=no·RoleBinding·오류 subject가 필요하다.' >&2; elif ROLEBINDING_JSON="$(kubectl --context "$CTX" get rolebinding "$ROLEBINDING" -n "$NS" -o json)" && ROLE_REF_KIND_TMP="$(jq -r '.roleRef.kind // empty' <<<"$ROLEBINDING_JSON")" && ROLE_REF_NAME_TMP="$(jq -r '.roleRef.name // empty' <<<"$ROLEBINDING_JSON")" && [ -n "$ROLE_REF_NAME_TMP" ] && jq -e --arg subject "$SUBJECT" --arg ns "$NS" 'any(.subjects[]?; (.kind=="User" and .name==$subject) or (.kind=="Group" and .name==$subject) or (.kind=="ServiceAccount" and ("system:serviceaccount:" + (.namespace // $ns) + ":" + .name)==$subject))' <<<"$ROLEBINDING_JSON" >/dev/null; then if [ "$ROLE_REF_KIND_TMP" = Role ] || [ "$ROLE_REF_KIND_TMP" = ClusterRole ]; then ROLE_REF_KIND="$ROLE_REF_KIND_TMP"; ROLE_REF_NAME="$ROLE_REF_NAME_TMP"; RBAC_SELECTION_READY=true; export ROLEBINDING SUBJECT ROLE_REF_KIND ROLE_REF_NAME; printf 'RBAC_SELECTION_READY=true namespace=%s rolebinding=%s roleRef=%s/%s subject=%s\n' "$NS" "$ROLEBINDING" "$ROLE_REF_KIND" "$ROLE_REF_NAME" "$SUBJECT"; else printf '중단: 지원하지 않는 roleRef.kind=%s\n' "$ROLE_REF_KIND_TMP" >&2; fi; unset ROLEBINDING_JSON ROLE_REF_KIND_TMP ROLE_REF_NAME_TMP; else printf '%s\n' '중단: RoleBinding API 실패, roleRef 누락 또는 실제 subject 불일치; stale RBAC 값을 사용하지 않음' >&2; fi`

RoleBinding `subjects`의 kind·name·namespace가 오류·audit의 `SUBJECT`와 일치해야 한다. ServiceAccount는 namespace를 포함한 `system:serviceaccount:namespace:name` identity로 비교한다. `roleRef.kind=Role`이면 대상 namespace Role만, `roleRef.kind=ClusterRole`이면 ClusterRole만 조회한다. RoleBinding이 이미 ClusterRole을 참조하는데 별도 ClusterRoleBinding 입력을 요구하지 않는다.

`ROLE_READY=false; if [ "$RBAC_SELECTION_READY" = true ] && [ "$ROLE_REF_KIND" = Role ] && ROLE_JSON="$(kubectl --context "$CTX" get role "$ROLE_REF_NAME" -n "$NS" -o json)"; then if jq -e '.rules[]? | select((.apiGroups // []) | index("")) | select((.resources // []) | index("pods/exec")) | select((.verbs // []) | index("create"))' <<<"$ROLE_JSON" >/dev/null; then ROLE_READY=true; printf 'ROLE_READY=true namespace=%s role=%s subject=%s\n' "$NS" "$ROLE_REF_NAME" "$SUBJECT"; else printf '%s\n' '중단: namespace Role에 core apiGroup의 pods/exec create가 없음' >&2; fi; else printf '%s\n' '중단: RoleBinding gate 또는 Role API 조회 실패' >&2; fi`

`ROLE_READY=true`는 대상 namespace Role의 `apiGroups: [""]`, `resources: ["pods/exec"]`, `verbs`의 `create` rule과 RoleBinding subject 일치만 보장한다. `pods`, `pods/log`, `pods/attach`는 `pods/exec`를 대신하지 않는다. 출력이 비거나 권한이 없으면 권한 없음과 조회 실패를 구분하지 못한 상태로 이관한다.

`CLUSTERROLE_READY=false; if [ "$RBAC_SELECTION_READY" = true ] && [ "$ROLE_REF_KIND" = ClusterRole ] && CLUSTERROLE_JSON="$(kubectl --context "$CTX" get clusterrole "$ROLE_REF_NAME" -o json)"; then if jq -e '.rules[]? | select((.apiGroups // []) | index("")) | select((.resources // []) | index("pods/exec")) | select((.verbs // []) | index("create"))' <<<"$CLUSTERROLE_JSON" >/dev/null; then CLUSTERROLE_READY=true; printf 'CLUSTERROLE_READY=true clusterrole=%s subject=%s namespace=%s\n' "$ROLE_REF_NAME" "$SUBJECT" "$NS"; else printf '%s\n' '중단: ClusterRole에 core apiGroup의 pods/exec create가 없음' >&2; fi; else printf '%s\n' '중단: RoleBinding gate 또는 ClusterRole API 조회 실패' >&2; fi`

`CLUSTERROLE_READY=true`는 이 namespace RoleBinding이 참조하는 ClusterRole의 `apiGroups: [""]`, `resources: ["pods/exec"]`, `verbs`의 `create` rule과 실제 subject 일치만 보장한다. ClusterRoleBinding은 별도 audit·RBAC evidence가 있고 cluster-scoped 권한 경로를 조사해야 할 때에만 그 담당자 절차로 이관하며, 이 문서의 입력값이나 기본 진단 명령으로 강제하지 않는다. 전 namespace binding은 최소 권한의 기본값이 아니며 대상 namespace Role·RoleBinding이 가능한지 먼저 판단한다.

## 승인된 최소 권한과 action contract

현재 주체의 직접적인 `no`와 audit 대조가 있을 때만 RBAC 관리자와 다음 최소 범위를 검토한다.

- 대상 namespace에만 적용되는 Role·RoleBinding
- `resources: [pods/exec]`, `verbs: [create]`
- 오류의 동일 subject만 포함
- 진단 목적, 승인자, incident/change ID, 만료·회수 시각 기록

**안전 gate:** 변경을 실행하는 운영자가 임의로 Role·RoleBinding을 만들거나 `--as`를 사용하지 않는다. action contract에는 trigger와 오류·UID·UTC audit, 대상·영향 namespace, 실행 권한·승인자, 정확한 diff, 기대 효과와 비보장, 중단 조건, rollback diff, 실행 후 동일 subject `can-i`·비파괴 exec·audit 검증, 관찰 창을 적는다. API 인가 회복은 kubelet 연결, 명령 존재, container 실행과 서비스 정상화를 보장하지 않는다.

변경 trigger가 사라졌거나 subject·namespace·roleRef가 다르면 실행을 중단한다. 적용 범위가 namespace보다 넓어지면 사전 승인된 원복 diff만 사용하고, 회수 후 `can-i=no`가 기대한 동일 주체에 적용되는지 확인한다.

## 승인된 impersonation과 동일 subject 검증

**진입 증거:** RBAC 변경 또는 impersonation이 보안·업무 승인으로 명시된 경우뿐이다. 현재 kubeconfig 주체의 결과와 target subject의 보조 결과를 섞지 않는다.

`AS_GROUP='PASTE_APPROVED_GROUP_HERE'; IMPERSONATION_READY=false; if [ "$AUTO_READY" != true ] || [ -z "${SUBJECT:-}" ] || [ -z "$AS_GROUP" ]; then printf '%s\n' '중단: RoleBinding 절에서 검증한 subject와 승인된 group이 필요하다.' >&2; else IMPERSONATION_READY=true; export SUBJECT AS_GROUP; printf 'IMPERSONATION_READY=true subject=%s group=%s UID=%s\n' "$SUBJECT" "$AS_GROUP" "$POD_UID"; fi`

`--as`는 기본 진단이 아니다. 승인서에 subject와 group이 정확히 명시되고 audit의 `user.username`, `user.groups`, `impersonatedUser`와 대조된 뒤에만 보조 검증으로 사용한다.

`if [ "$IMPERSONATION_READY" = true ]; then auth_can_i_result create pods/"$POD" --subresource=exec -n "$NS" --as="$SUBJECT" --as-group="$AS_GROUP"; else printf '%s\n' '중단: IMPERSONATION_READY가 아니다.' >&2; fi`

보조 결과가 `yes`여도 실제 kubeconfig 주체의 기본 결과를 대체하지 않는다. 승인된 `CONTAINER`와 비파괴 `EXEC_COMMAND`로 현재 실제 주체의 exec를 별도 검증한다. group이 여러 개면 승인된 각 group을 별도 확인하고, 오류의 subject와 현재 실제 주체가 다르면 인증·RBAC 담당자에게 이관한다.

## 제한적 복구와 정상화

이 문서는 진단 중 권한 변경 명령을 제공하지 않는다. 승인된 Role 변경의 trigger는 같은 UID·namespace·subject에 대한 `403` audit와 현재 주체의 `can-i=no`다. 대상은 해당 namespace와 subject뿐이며, cluster-admin·wildcard·TLS 우회는 제외한다. 변경 전 승인·rollback·만료를 기록하고, subject·namespace·roleRef가 달라지거나 범위가 넓어지면 중단한다.

정상화는 원인 경로의 역순으로 확인한다.

1. API server의 동일 subject·namespace·Pod에 대한 `pods/exec create`가 승인된 범위에서 기대한 결과인지 확인한다.
2. API audit의 UID·resource·subresource·verb와 response가 기대한 요청을 가리키는지 확인한다.
3. kubelet/runtime stream이 준비되고 확인된 container에서 승인된 비파괴 command가 실행되는지 확인한다.
4. Pod `Ready`와 실제 Service 요청·핵심 기능을 별도로 확인하고 권한 회복만으로 정상화하지 않는다.
5. 임시 권한은 승인된 rollback으로 회수하고 회수 뒤 현재 주체 `can-i`와 audit를 확인한다.
6. 관찰 창 동안 같은 오류와 불필요한 권한 재사용이 재발하지 않는지 확인한다.

보존할 증거는 context, namespace, Pod UID, node, UTC 관측 시각, 오류 원문, 오류 subject와 실제 subject, `can-i` 결과, Role·Binding 식별자, authorization/admission audit, 승인·rollback ID다. token·Secret·인증서 개인키·개인정보는 보존하지 않는다.

## Prometheus 빠른 관측

메트릭이 실제 수집되고 라벨이 일치할 때만 사용한다. `POD_RE`는 자동 escape된 bounded 값이며, PromQL은 아래 생성 명령의 출력만 Prometheus/Grafana에 붙여 넣는다. metric 부재, label 불일치, 조회 실패와 빈 결과를 구분한다.

API server request metric은 특정 Pod UID를 제공하지 않는 경우가 있으므로 이 문서의 권한 판정에는 사용하지 않는다. `kube-state-metrics`의 `kube_pod_info`가 `namespace`, `pod`, `uid` label을 실제로 제공하는지 먼저 확인하고, 세 label 계약이 없거나 series가 1개가 아니면 PromQL gate를 닫는다.

`if [ "$AUTO_READY" = true ]; then printf '%s\n' "count by(namespace,pod,uid)(kube_pod_info{namespace=\"$NS\",pod=~\"$POD_RE\",uid=\"$POD_UID\"})"; else printf '%s\n' '중단: AUTO_READY가 아니다.' >&2; fi`

출력된 query는 현재 namespace·Pod 이름 regex·최초 UID를 모두 포함한다. 결과가 1인 series로 확인되면 해당 Pod identity의 KSM label 계약만 통과한 것이며, 권한 `403`의 원인은 API audit와 동일 subject `can-i`로 판정한다.

series가 없으면 정상이나 0으로 기록하지 말고 metric 미수집·라벨 불일치·조회 범위·권한을 확인한다. PromQL은 RBAC 변경 승인 근거가 아니다.
