# Pod가 Preempted된 경우

## 입력값과 빠른 수집

처음에는 victim namespace와 Pod만 입력한다. Pod API가 현재 victim UID·node·phase·priority·preemption policy·nominated node·controller owner를 자동 등록하고, namespace와 Pod 이름은 PromQL용 escape 후보로 계산한다. Event가 식별한 preemptor, 실제 scheduler 배포 정보, node journal 시간과 Job 이름은 관측 결과를 본 뒤 운영자가 선택한다. API 호출 실패, 빈 후보, 후보 수 불일치가 있으면 이전 값이나 부분 등록값을 사용하지 않는다.

| 종류 | 값 | 출처와 사용 범위 |
|---|---|---|
| 최초 입력 | `NS`, `POD` | 승인된 victim namespace와 Pod 이름. 문서 전체에서 한 번만 입력한다. |
| API 자동값 | `VICTIM_UID`, `VICTIM_EVENT_UID`, `VICTIM_EVENT_MESSAGE`, `PREEMPTION_TIME`, `PREEMPTION_EPOCH`, `PREEMPTOR_NS`, `PREEMPTOR_POD`, `CURRENT_POD_UID`, `NODE`, `PHASE`, `STATUS_REASON`, `PRIORITY_CLASS`, `PRIORITY`, `PREEMPTION_POLICY`, `NOMINATED_NODE`, `OWNER_KIND`, `OWNER_NAME`, `OWNER_UID`, `NS_RE`, `POD_RE`, `OBSERVED_AT` | 단일 canonical victim Event item과 현재 Pod API에서 같은 Bash에 등록한다. 현재 Pod가 없어도 victim Event identity는 유지한다. preemptor namespace/name은 Event message에서만 파생한다. |
| 계산 후보 | `NS_RE`, `POD_RE` | PromQL label matcher 후보이며 생성 문자열을 bounded 출력으로 확인한다. |
| 운영자 선택값 | `VICTIM_UID`(복수 Event 후보일 때만), `SCHEDULER_NAMESPACE`, `SCHEDULER_SELECTOR`, `SCHEDULER_MODE`, `SCHEDULER_POD`, `SCHEDULER_CONTAINER`, `START_RFC3339`, `NODE_HOST`, `KUBELET_SERVICE`, `START_JOURNAL`, `END_JOURNAL`, `JOB` | Event·실제 control-plane 배포·node 권한·owner chain을 확인한 뒤 필요한 분기에서 한 번 선택한다. `PREEMPTOR_NS`·`PREEMPTOR_POD`는 수동 입력하지 않고 canonical Event message에서만 파생한다. `NODE_HOST`는 승인된 remote host다. |

### 실행 위치·도구·권한 전제

kubectl과 로그 명령은 승인된 context에 연결된 작업 PC 또는 bastion의 **같은 Bash 터미널**에서 실행한다. 이 문서의 변수와 gate는 shell에 남아 있으므로 터미널을 바꾸면 초기화 절부터 다시 실행한다. API 조회에는 Pod·Event·Node·PriorityClass 및 필요한 owner 읽기 권한이 필요하다. scheduler 로그는 control-plane 접근과 `pods/log` 권한이 확인된 경우에만 사용하며 managed control plane이면 로그를 추측하지 않는다. node journal은 실제 node shell 접근과 승인된 `sudo` 권한이 필요하다. Secret·token·인증서 개인키·개인정보는 출력하거나 저장하지 않는다.

**Bash·필수 도구 확인 — 아래 한 줄 전체를 복사**

`TOOLS_READY=false; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: 같은 Bash에서 실행한다.' >&2; else MISSING_TOOLS=''; for TOOL in kubectl jq grep sed date; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true Bash=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

`TOOLS_READY=true`가 아니면 다음 단계로 진행하지 않는다. `journalctl`·`sudo`는 node 분기에서 별도로 확인하고 실패하면 journal을 실행하지 않고 node owner에게 이관한다.

### 대상 지정·이전 상태 초기화·API 자동 등록

재실행할 때 이전 victim·preemptor·scheduler·시간·owner 값을 먼저 무효화한다. Pod API와 필수 field 파싱, 이름 escape가 모두 성공한 경우에만 `AUTO_READY=true`가 된다.

### Event-first victim 확정

일반 사후 선점에서는 victim Pod가 이미 삭제됐거나 같은 이름의 replacement가 존재할 수 있다. 따라서 먼저 namespace·Pod 이름으로 Event를 조회하고, Event의 관련 Pod UID를 victim identity로 확정한다. 현재 Pod API가 존재하면 `CURRENT_POD_UID`·status는 보조 대조만 하며, 동명 replacement를 victim으로 사용하지 않는다.

**Event-first 수집과 직접 선점 후보 출력 — 아래 한 줄 전체를 복사**

`EVENT_FIRST_READY=false; PREEMPTION_READY=false; EVENT_READY=false; EVIDENCE_READY=false; CURRENT_POD_UID="${POD_UID:-}"; unset EVENT_JSON VICTIM_UID VICTIM_EVENT_UID; if [ "$TOOLS_READY" != true ] || [ -z "$NS" ] || [ -z "$POD" ]; then printf '%s\n' '중단: 도구·NS·POD 전제가 아니다.' >&2; elif EVENT_JSON="$(kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD" --sort-by=.metadata.creationTimestamp -o json)" && jq -e '.items | type == "array" and length > 0' <<<"$EVENT_JSON" >/dev/null; then jq -r '.items[] | "=== Event 후보 ===\nEvent UID: \(.metadata.uid)\n관련 Pod UID: \(.involvedObject.uid // "-")\nReason: \(.reason // "-")\nEvent 시각: \(.eventTime // "-")\nSeries 마지막 시각: \(.series.lastObservedTime // "-")\n마지막 시각: \(.lastTimestamp // "-")\nMessage: \(.message // "-")\n"' <<<"$EVENT_JSON"; mapfile -t PREEMPTION_UIDS < <(jq -r '[.items[] | select(.reason=="Preempted" or ((.message // "") | test("(^|[^A-Za-z])Preempted([^A-Za-z]|$)"; "i"))) | .involvedObject.uid // empty] | unique[]' <<<"$EVENT_JSON"); if [ "${#PREEMPTION_UIDS[@]}" -eq 1 ]; then VICTIM_UID="${PREEMPTION_UIDS[0]}"; VICTIM_EVENT_UID="$(jq -er --arg uid "$VICTIM_UID" '[.items[] | select(.involvedObject.uid==$uid and (.reason=="Preempted" or ((.message // "") | test("(^|[^A-Za-z])Preempted([^A-Za-z]|$)"; "i")))) | .metadata.uid] | sort | .[0]' <<<"$EVENT_JSON")"; POD_UID="$VICTIM_UID"; EVENT_FIRST_READY=true; PREEMPTION_READY=true; EVENT_READY=true; EVIDENCE_READY=true; printf 'PREEMPTION_READY=true victim_uid=%s event_uid=%s current_pod_uid=%s\n' "$VICTIM_UID" "$VICTIM_EVENT_UID" "${CURRENT_POD_UID:--}"; elif [ "${#PREEMPTION_UIDS[@]}" -gt 1 ]; then printf '중단: 직접 Preempted Event의 victim UID 후보가 여러 개다. 첫 번째를 선택하지 않는다 candidates=%s\n' "${PREEMPTION_UIDS[*]}" >&2; else printf '중단: reason=Preempted 또는 직접 Preempted message Event가 없다. Event를 선점 근거로 사용하지 않는다.\n' >&2; fi; else printf '중단: Event-first API 조회 실패 또는 빈 결과. Pod 부재·정상·선점 없음으로 해석하지 않는다.\n' >&2; unset EVENT_JSON; fi`

`PREEMPTION_READY=true`는 Event의 `reason=Preempted` 또는 직접 `Preempted` message와 관련 victim UID가 확정됐다는 뜻이다. Event API가 실패하거나 직접 후보가 0개 또는 여러 개면 다음 단계로 진행하지 않는다. 여러 후보일 때만 아래 선택 command를 실행한다.

**복수 victim UID 후보 선택 — 위 출력이 복수 후보라고 명시한 경우에만 아래 한 줄 전체를 복사**

`VICTIM_UID='PASTE_VICTIM_UID_HERE'; VICTIM_SELECTION_READY=false; unset VICTIM_EVENT_UID; if [ "$EVENT_FIRST_READY" = true ]; then printf '%s\n' '중단: 이미 단일 victim이 자동 확정됐다.' >&2; elif [ -z "$VICTIM_UID" ]; then printf '%s\n' '중단: Event 후보에서 승인된 victim UID를 입력한다.' >&2; elif jq -e --arg uid "$VICTIM_UID" 'any(.items[]; .involvedObject.uid==$uid and (.reason=="Preempted" or ((.message // "") | test("(^|[^A-Za-z])Preempted([^A-Za-z]|$)"; "i"))))' <<<"$EVENT_JSON" >/dev/null && VICTIM_EVENT_UID="$(jq -er --arg uid "$VICTIM_UID" '[.items[] | select(.involvedObject.uid==$uid and (.reason=="Preempted" or ((.message // "") | test("(^|[^A-Za-z])Preempted([^A-Za-z]|$)"; "i")))) | .metadata.uid] | sort | .[0]' <<<"$EVENT_JSON")"; then POD_UID="$VICTIM_UID"; VICTIM_SELECTION_READY=true; EVENT_FIRST_READY=true; PREEMPTION_READY=true; EVENT_READY=true; EVIDENCE_READY=true; printf 'PREEMPTION_READY=true victim_uid=%s event_uid=%s\n' "$VICTIM_UID" "$VICTIM_EVENT_UID"; else printf '중단: 선택 UID가 직접 Preempted Event 후보와 일치하지 않는다. stale 또는 동명 replacement를 사용하지 않는다.\n' >&2; unset VICTIM_EVENT_UID; fi`

**단일 canonical victim Event 등록 — 아래 한 줄 전체를 복사**

`VICTIM_EVENT_READY=false; EVENT_FIRST_READY=false; PREEMPTION_READY=false; EVENT_READY=false; EVIDENCE_READY=false; unset VICTIM_EVENT_JSON VICTIM_EVENT_UID VICTIM_EVENT_MESSAGE PREEMPTION_TIME PREEMPTION_EPOCH PREEMPTOR_NS PREEMPTOR_POD; if [ -z "${VICTIM_UID:-}" ] || [ -z "${EVENT_JSON:-}" ]; then printf '%s\n' '중단: victim UID 또는 Event JSON이 없다.' >&2; false; else VICTIM_EVENT_CANDIDATES="$(jq -c --arg uid "$VICTIM_UID" '[.items[] | select(.involvedObject.uid==$uid and (.reason=="Preempted" or ((.message // "") | test("(^|[^A-Za-z])Preempted([^A-Za-z]|$)"; "i")))) | ([.eventTime,.series.lastObservedTime,.lastTimestamp,.firstTimestamp] | map(select(type=="string" and length>0)) | .[0]) as $time | select($time != null) | select((.message // "") | test("Preempted by [A-Za-z0-9][A-Za-z0-9._-]*/[A-Za-z0-9][A-Za-z0-9._-]*")) | ((.message // "") | capture("Preempted by (?<ref>[A-Za-z0-9][A-Za-z0-9._-]*/[A-Za-z0-9][A-Za-z0-9._-]*)").ref) as $ref | ($ref | split("/")) as $parts | {event_uid:.metadata.uid,message:.message,event_time:$time,preemptor_namespace:$parts[0],preemptor_pod:$parts[1]}]' <<<"$EVENT_JSON")"; false; elif VICTIM_EVENT_JSON="$(jq -c '.[0]' <<<"$VICTIM_EVENT_CANDIDATES")" && VICTIM_EVENT_UID="$(jq -er '.event_uid' <<<"$VICTIM_EVENT_JSON")" && VICTIM_EVENT_MESSAGE="$(jq -er '.message' <<<"$VICTIM_EVENT_JSON")" && PREEMPTION_TIME="$(jq -er '.event_time' <<<"$VICTIM_EVENT_JSON")" && PREEMPTION_EPOCH="$(date -u -d "$PREEMPTION_TIME" +%s 2>/dev/null)" && PREEMPTOR_NS="$(jq -er '.preemptor_namespace' <<<"$VICTIM_EVENT_JSON")" && PREEMPTOR_POD="$(jq -er '.preemptor_pod' <<<"$VICTIM_EVENT_JSON")"; then POD_UID="$VICTIM_UID"; VICTIM_EVENT_READY=true; EVENT_FIRST_READY=true; PREEMPTION_READY=true; EVENT_READY=true; EVIDENCE_READY=true; printf 'VICTIM_EVENT_READY=true PREEMPTION_READY=true victim_uid=%s victim_event_uid=%s event_time=%s preemption_epoch=%s preemptor=%s/%s message=%s\n' "$VICTIM_UID" "$VICTIM_EVENT_UID" "$PREEMPTION_TIME" "$PREEMPTION_EPOCH" "$PREEMPTOR_NS" "$PREEMPTOR_POD" "$VICTIM_EVENT_MESSAGE"; true; else printf '중단: 단일 canonical victim Event item에서 UID/message/time/preemptor 파생에 실패했다. 다른 Event를 혼합하지 않고 scheduler evidence로 이관한다.\n' >&2; false; fi; fi`

`VICTIM_EVENT_READY=true`는 하나의 Event item에서 `VICTIM_EVENT_UID`, message, canonical event time/`PREEMPTION_EPOCH`, preemptor namespace/name을 함께 파생했다는 뜻이다. 후보가 0개 또는 2개 이상이거나 preemptor fixed relation이 없으면 `PREEMPTION_READY=false`로 유지한다.

현재 Pod가 존재해 `CURRENT_POD_UID`가 있더라도 `CURRENT_POD_UID != VICTIM_UID`이면 replacement로 보고 victim 증거에 섞지 않는다. victim Pod가 없어도 Event-first gate가 열릴 수 있지만 priority·node·owner 상태는 Event와 별도 control-plane evidence가 없으면 미확정이다.

**replacement Pod 상태 무효화 gate — 아래 한 줄 전체를 복사**

`VICTIM_STATE_READY=false; if [ "$PREEMPTION_READY" != true ]; then printf '%s\n' '중단: PREEMPTION_READY가 아니다.' >&2; false; elif [ -n "${CURRENT_POD_UID:-}" ] && [ "$CURRENT_POD_UID" = "$VICTIM_UID" ]; then VICTIM_STATE_READY=true; printf 'VICTIM_STATE_READY=true victim_uid=%s current_pod_uid=%s\n' "$VICTIM_UID" "$CURRENT_POD_UID"; true; else VICTIM_STATE_READY=false; AUTO_READY=false; FIRST_CHECK_READY=false; NODE_READY=false; OWNER_READY=false; PRIORITY_READY=false; PREEMPTOR_READY=false; NODE_SNAPSHOT_READY=false; SCHEDULER_CANDIDATES_READY=false; SCHEDULER_SELECTION_READY=false; SCHEDULER_LOG_READY=false; JOURNAL_READY=false; JOB_READY=false; unset POD_JSON NODE PHASE STATUS_REASON PRIORITY_CLASS PRIORITY PREEMPTION_POLICY NOMINATED_NODE OWNER_KIND OWNER_NAME OWNER_UID PREEMPTOR_JSON PREEMPTOR_UID PREEMPTOR_PHASE PREEMPTOR_NODE; printf 'VICTIM_STATE_READY=false replacement_or_absent=true current_pod_uid=%s victim_uid=%s; replacement Pod의 node/priority/owner와 관련 READY를 비웠다. historical Event 또는 scheduler evidence 없는 분기는 중단한다.\n' "${CURRENT_POD_UID:--}" "$VICTIM_UID" >&2; true; fi`

**Event 시각 형식 gate — 아래 한 줄 전체를 복사**

`PREEMPTION_TIME_READY=false; if [ "$PREEMPTION_READY" != true ] || [ "$VICTIM_EVENT_READY" != true ] || [ -z "${PREEMPTION_TIME:-}" ] || [ -z "${PREEMPTION_EPOCH:-}" ]; then PREEMPTION_READY=false; PREEMPTION_TIME_READY=false; EVIDENCE_READY=false; printf '중단: 단일 canonical victim Event의 PREEMPTION_TIME/PREEMPTION_EPOCH가 등록되지 않았다.\n' >&2; false; else PREEMPTION_TIME_READY=true; printf 'PREEMPTION_TIME_READY=true victim_uid=%s victim_event_uid=%s event_time=%s epoch=%s preemptor=%s/%s\n' "$POD_UID" "$VICTIM_EVENT_UID" "$PREEMPTION_TIME" "$PREEMPTION_EPOCH" "$PREEMPTOR_NS" "$PREEMPTOR_POD"; true; fi`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 같은 victim Pod UID의 Event 또는 Pod `status.reason`이 `Preempted`이고 priority·scheduler 시간축을 조사해야 하는 경우 |
| 적용 | `PREEMPTION_READY=true`, `PREEMPTION_TIME_READY=true`, victim UID와 Event 시각을 확인할 수 있는 경우. 현재 Pod API는 있으면 보조 대조로 사용한다. |
| 제외 | 최초 reason이 `Evicted`이면 [[12. Pod STATUS가 Evicted인 경우]], `OOMKilled`이면 [[11. Pod STATUS가 OOMKilled인 경우]], preemption과 무관한 `FailedScheduling`이면 [[18. Pod 이벤트에 FailedScheduling이 기록된 경우]]로 이동한다. `NodeLost`·application 종료가 최초 원인이거나 오래된 Event만 있으면 해당 계층의 과거 사건으로 이관한다. |

검색 문자열: `Preempted`, `PreemptLowerPriority`, `Preemptor`, `victim`, `priorityClassName`, `priority`, `preemptionPolicy`, `nominatedNodeName`, `FailedScheduling`, `Insufficient cpu`, `Insufficient memory`, `Preemption is not helpful`, `No preemption victims found`, `taint`, `affinity`, `topology`, `quota`.

`Preempted`는 victim이 종료된 결과이지 replacement가 배치됐다는 뜻이 아니다. 선점을 node 장애나 일반 eviction으로 바꾸어 해석하지 않는다.

볼 것: `PHASE`, `READY`, `RESTARTS`, `NODE`, priority 관련 field와 `nominatedNodeName`. `describe`에서 `Priority`, `Preemption Policy`, owner, Conditions와 첫 `Preempted`·`FailedScheduling` message를 본다.

**Event-first 결과 재사용 — 아래 한 줄 전체를 복사**

`EVENT_API_OK=false; if [ "$PREEMPTION_READY" != true ] || [ "$EVENT_FIRST_READY" != true ]; then printf '%s\n' '중단: Event-first direct Preempted gate가 아니다.' >&2; else EVENT_API_OK=true; EVENT_READY=true; EVIDENCE_READY=true; printf 'EVENT_READY=true EVIDENCE_READY=true victim_uid=%s event_uid=%s\n' "$POD_UID" "$VICTIM_EVENT_UID"; fi`

Event-first 결과에서는 `EVENT UID`, victim UID, preemptor가 언급된 message, 실제로 채워진 시각과 count를 보존한다. 시각은 `eventTime`, 없으면 `series.lastObservedTime`, `lastTimestamp`, `firstTimestamp` 순으로 선택하고 `creationTimestamp`는 정렬용으로만 쓴다. Event가 비어 있거나 reason/message 직접 근거가 없으면 status만으로 선점을 확정하지 않는다.

### preemptor 선택값 등록

Event message에서 victim과 같은 UID의 직접 `Preempted` Event 안에 고정 문자열 `namespace/pod`가 실제로 확인된 경우에만 선택한다. 문자열·name·API UID가 직접 연결되지 않으면 수동 Pod를 preemptor로 등록하지 않고 scheduler evidence로 이관한다. 복수 후보가 있으면 첫 번째를 고르지 않는다.

**운영자 선택값 설정·API 재확인 — 아래 한 줄 전체를 복사**

`PREEMPTOR_READY=false; unset PREEMPTOR_JSON PREEMPTOR_UID PREEMPTOR_PHASE PREEMPTOR_NODE PREEMPTOR_CREATED_AT PREEMPTOR_START_AT PREEMPTOR_CREATED_EPOCH PREEMPTOR_START_EPOCH; if [ "$EVIDENCE_READY" != true ] || [ "$VICTIM_EVENT_READY" != true ] || [ "$PREEMPTION_TIME_READY" != true ] || [ -z "${PREEMPTOR_NS:-}" ] || [ -z "${PREEMPTOR_POD:-}" ]; then printf '%s\n' '중단: 단일 victim Event에서 파생된 preemptor 또는 시간 gate가 아니다.' >&2; false; elif PREEMPTOR_JSON="$(kubectl get pod "$PREEMPTOR_POD" -n "$PREEMPTOR_NS" -o json)" && PREEMPTOR_UID_TMP="$(jq -er '.metadata.uid' <<<"$PREEMPTOR_JSON")" && PREEMPTOR_PHASE_TMP="$(jq -r '.status.phase // "-"' <<<"$PREEMPTOR_JSON")" && PREEMPTOR_NODE_TMP="$(jq -r '.spec.nodeName // empty' <<<"$PREEMPTOR_JSON")" && PREEMPTOR_CREATED_AT_TMP="$(jq -er '.metadata.creationTimestamp' <<<"$PREEMPTOR_JSON")" && PREEMPTOR_START_AT_TMP="$(jq -er '.status.startTime' <<<"$PREEMPTOR_JSON")" && PREEMPTOR_CREATED_EPOCH_TMP="$(date -u -d "$PREEMPTOR_CREATED_AT_TMP" +%s 2>/dev/null)" && PREEMPTOR_START_EPOCH_TMP="$(date -u -d "$PREEMPTOR_START_AT_TMP" +%s 2>/dev/null)"; then PREEMPTOR_UID="$PREEMPTOR_UID_TMP"; PREEMPTOR_PHASE="$PREEMPTOR_PHASE_TMP"; PREEMPTOR_NODE="$PREEMPTOR_NODE_TMP"; PREEMPTOR_CREATED_AT="$PREEMPTOR_CREATED_AT_TMP"; PREEMPTOR_START_AT="$PREEMPTOR_START_AT_TMP"; PREEMPTOR_CREATED_EPOCH="$PREEMPTOR_CREATED_EPOCH_TMP"; PREEMPTOR_START_EPOCH="$PREEMPTOR_START_EPOCH_TMP"; if [ "$PREEMPTOR_CREATED_EPOCH" -le "$PREEMPTION_EPOCH" ] && [ "$PREEMPTOR_START_EPOCH" -le "$PREEMPTION_EPOCH" ]; then PREEMPTOR_READY=false; jq -r '"=== Preemptor Pod ===\nNamespace: \(.metadata.namespace)\nPod: \(.metadata.name)\nUID: \(.metadata.uid)\nPhase: \(.status.phase // "-")\nReady: \([.status.containerStatuses[]? | .ready] | if length==0 then "-" else join(",") end)\nNode: \(.spec.nodeName // "-")\nCreated: \(.metadata.creationTimestamp // "-")\nStarted: \(.status.startTime // "-")\nPriorityClass: \(.spec.priorityClassName // "-")\nPriority: \(.spec.priority // "-")\nPreemption policy: \(.spec.preemptionPolicy // "-")\nNominated node: \(.status.nominatedNodeName // "-")"' <<<"$PREEMPTOR_JSON"; printf 'PREEMPTOR_READY=false victim_event_uid=%s preemptor=%s/%s preemptor_uid=%s created=%s created_epoch=%s started=%s start_epoch=%s preemption_epoch=%s\n' "$VICTIM_EVENT_UID" "$PREEMPTOR_NS" "$PREEMPTOR_POD" "$PREEMPTOR_UID" "$PREEMPTOR_CREATED_AT" "$PREEMPTOR_CREATED_EPOCH" "$PREEMPTOR_START_AT" "$PREEMPTOR_START_EPOCH" "$PREEMPTION_EPOCH"; true; else PREEMPTOR_READY=false; printf '중단: preemptor Pod의 creationTimestamp 또는 startTime이 PREEMPTION_EPOCH 이후다. same-name Pod를 사용하지 않고 scheduler evidence로 이관한다.\n' >&2; false; fi; else PREEMPTOR_READY=false; printf '중단: 파생 preemptor의 API/UID/timestamp 파싱 실패. 선택값을 유효하게 남기지 않고 scheduler evidence로 이관한다.\n' >&2; unset PREEMPTOR_JSON PREEMPTOR_UID PREEMPTOR_PHASE PREEMPTOR_NODE PREEMPTOR_CREATED_AT PREEMPTOR_START_AT PREEMPTOR_CREATED_EPOCH PREEMPTOR_START_EPOCH; false; fi`

`PREEMPTOR_READY=false; PREEMPTOR_START_OBSERVATION_READY=false; PREEMPTOR_START_POST_EVENT=false`

위 API 조회 단계가 계산한 `PREEMPTOR_READY`는 bounded observation으로 재검증하기 전에는 사용하지 않는다. 다음 줄이 재검증을 통과한 경우에만 다시 true로 연다.

`PREEMPTOR_START_OBSERVATION_READY=false; PREEMPTOR_START_POST_EVENT=false; PREEMPTOR_OBSERVED_EPOCH="$(date -u +%s)"; if [ "$EVIDENCE_READY" = true ] && [ "$VICTIM_EVENT_READY" = true ] && [ -n "${PREEMPTOR_UID:-}" ] && [[ "${PREEMPTOR_CREATED_EPOCH:-}" =~ ^[0-9]+$ ]] && [[ "${PREEMPTOR_START_EPOCH:-}" =~ ^[0-9]+$ ]] && [ "$PREEMPTOR_CREATED_EPOCH" -le "$PREEMPTION_EPOCH" ] && [ "$PREEMPTOR_CREATED_EPOCH" -le "$PREEMPTOR_START_EPOCH" ] && [ "$PREEMPTOR_START_EPOCH" -le "$PREEMPTOR_OBSERVED_EPOCH" ]; then PREEMPTOR_START_OBSERVATION_READY=true; if [ "$PREEMPTOR_START_EPOCH" -gt "$PREEMPTION_EPOCH" ]; then PREEMPTOR_START_POST_EVENT=true; fi; PREEMPTOR_READY=true; printf 'PREEMPTOR_START_OBSERVATION_READY=true post_event=%s created_epoch=%s start_epoch=%s event_epoch=%s observed_epoch=%s\n' "$PREEMPTOR_START_POST_EVENT" "$PREEMPTOR_CREATED_EPOCH" "$PREEMPTOR_START_EPOCH" "$PREEMPTION_EPOCH" "$PREEMPTOR_OBSERVED_EPOCH"; else PREEMPTOR_READY=false; printf '중단: preemptor creation/startTime 관계 또는 bounded observation window가 닫히지 않았다. created=%s start=%s event_epoch=%s observed_epoch=%s\n' "${PREEMPTOR_CREATED_EPOCH:--}" "${PREEMPTOR_START_EPOCH:--}" "${PREEMPTION_EPOCH:--}" "$PREEMPTOR_OBSERVED_EPOCH" >&2; fi`

`PREEMPTOR_START_POST_EVENT=true`인 경우 `startTime`은 선점 Event 이전 evidence로 사용하지 않고, canonical Event 이후 bounded observation으로만 기록한다. `creationTimestamp <= PREEMPTION_EPOCH`와 `startTime <= 관측 시각`을 만족하지 않으면 preemptor 관계를 확정하지 않는다.

`PREEMPTOR_READY=true`는 같은 victim UID의 직접 `Preempted` Event message가 고정 문자열 `namespace/pod`를 포함하고, 그 name을 API에서 읽은 UID·시각과 연결했으며 bounded `PREEMPTOR_START_OBSERVATION_READY=true`를 통과했다는 뜻이다. `nominatedNodeName`과 실제 `spec.nodeName`, Ready는 별도로 대조한다. preemptor가 사라졌거나 fixed-string/name/UID 연결이 없으면 수동 등록을 취소하고 scheduler evidence로 이동한다.

|---|---|---|---|

| preemptor가 `Pending`이고 nominated node가 있음 | 지명 node와 실제 `node` 여부 | scheduler 판단 → 용량·배치 조건 | [[#2. Preemptor와 nominated node\|2]] |
| `Insufficient cpu/memory`, `Too many pods` | node allocatable과 Pod requests | capacity → replacement 재스케줄 | [[#3. 용량 부족과 replacement 재스케줄 가능성\|3]] |
| `taint`, affinity, topology, quota 또는 `Preemption is not helpful` | placement 조건과 scheduler message | scheduler policy/plugin → owner | [[#4. Scheduler 판단과 배치 제약\|4]] |
| victim owner에 대체 Pod가 없거나 대체 Pod도 Pending | controller와 desired/Ready | controller·capacity·서비스 영향 | [[#5. Controller와 서비스·Job 영향\|5]] |

## 진단 파이프라인

### 1. Preempted victim의 priority와 정책

진입 증거는 같은 victim UID의 `Preempted` message와 priority field가 함께 확인된 경우다. victim의 `preemptionPolicy`가 `Never`라는 사실은 victim이 다른 Pod를 선점하지 않는다는 뜻이지 victim이 절대 선점되지 않는다는 뜻이 아니다.

연결 경로: `실행 host → kubectl client/API server → PriorityClass·victim Pod API → scheduler policy → victim termination`. API field가 정상이어도 scheduler decision·victim 종료 시각·replacement application 정상은 보장하지 않는다.

**PriorityClass 확인 — class 이름이 API 자동값으로 비어 있지 않을 때 아래 한 줄 전체를 복사**

`PRIORITY_READY=false; if [ "$EVIDENCE_READY" != true ] || [ "$VICTIM_STATE_READY" != true ]; then printf '%s\n' '중단: historical Event evidence만 있고 현재 victim Pod priority state가 없어 priority 분기를 열지 않는다.' >&2; false; elif [ -z "$PRIORITY_CLASS" ]; then printf 'PriorityClass 없음: spec.priority=%s와 cluster 기본 정책을 확인한다.\n' "${PRIORITY:--}"; PRIORITY_READY=true; true; elif kubectl get priorityclass "$PRIORITY_CLASS" -o custom-columns='NAME:.metadata.name,VALUE:.value,PREEMPTION:.preemptionPolicy,GLOBAL_DEFAULT:.globalDefault'; then PRIORITY_READY=true; printf 'PRIORITY_READY=true class=%s pod_priority=%s\n' "$PRIORITY_CLASS" "${PRIORITY:--}"; true; else printf '중단: PriorityClass 조회 실패. priority policy drift로 해석하지 않는다.\n' >&2; false; fi`

성공 gate는 PriorityClass value와 Pod `spec.priority`, preemption policy, Event 시각이 같은 정책 revision에 맞는 것이다. class API 실패나 값 불일치는 policy drift·변경 이력으로 이관하며 priority를 즉시 수정하지 않는다.

### 2. Preemptor와 nominated node

진입 증거는 bounded `PREEMPTOR_START_OBSERVATION_READY=true`를 포함한 `PREEMPTOR_READY=true` 또는 Event message에 preemptor가 있지만 현재 Pod가 사라져 별도 scheduler 확인이 필요한 경우다. 연결 경로는 `실행 host → kubectl client → API server → scheduler 판단 → nominated node의 kubelet/runtime → preemptor Pod/application`이다. API server 연결 성공은 scheduler가 배치를 완료했거나 application이 Ready라는 뜻이 아니다.

**victim과 preemptor 상태 비교 — 아래 한 줄 전체를 복사**

`if [ "$PREEMPTOR_READY" != true ] || [ "$PREEMPTOR_START_OBSERVATION_READY" != true ] || [ "$VICTIM_STATE_READY" != true ]; then printf '%s\n' '중단: PREEMPTOR_READY, PREEMPTOR_START_OBSERVATION_READY 또는 VICTIM_STATE_READY가 아니다.' >&2; false; else kubectl get pod "$POD" -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,NODE:.spec.nodeName,NOMINATED:.status.nominatedNodeName,READY:.status.containerStatuses[*].ready' && kubectl get pod "$PREEMPTOR_POD" -n "$PREEMPTOR_NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,NODE:.spec.nodeName,NOMINATED:.status.nominatedNodeName,READY:.status.containerStatuses[*].ready'; fi`

`Pending`이고 `nominatedNodeName=$NODE`이면 scheduler가 후보 node를 지명했지만 victim 제거 뒤에도 resource·taint·affinity·topology·quota를 만족하지 못할 수 있다. `spec.nodeName`이 채워지고 Ready인 것은 배치의 보조 evidence일 뿐 실제 service 기능을 보장하지 않는다. preemptor가 사라지면 Event 시각과 scheduler record로 이관한다.

### 3. 용량 부족과 replacement 재스케줄 가능성

진입 증거는 preemptor 또는 victim replacement의 `Insufficient cpu`, `Insufficient memory`, `Too many pods`다. 선점 실행과 새 Pod 배치 여유는 별도 사실이다.

연결 경로: `실행 host → kubectl client/API server → node allocatable·Pod requests → scheduler capacity decision → replacement kubelet/runtime → application`. node 자원 조회 성공은 scheduler가 replacement를 배치했거나 실제 요청이 성공한다는 보장이 아니다.

**관측 node 자원·Pod 범위 확인 — 아래 한 줄 전체를 복사**

`NODE_SNAPSHOT_READY=false; if [ "$NODE_READY" != true ]; then printf '%s\n' '중단: NODE_READY가 아니다.' >&2; elif kubectl describe node "$NODE" && kubectl get node "$NODE" -o jsonpath='{.status.allocatable}{"\n"}{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}' && kubectl get pods -A --field-selector "spec.nodeName=$NODE" -o custom-columns='NAMESPACE:.metadata.namespace,POD:.metadata.name,UID:.metadata.uid,PHASE:.status.phase,PRIORITY_CLASS:.spec.priorityClassName,PRIORITY:.spec.priority,OWNER_KIND:.metadata.ownerReferences[?(@.controller==true)].kind,OWNER_NAME:.metadata.ownerReferences[?(@.controller==true)].name,DELETION:.metadata.deletionTimestamp,REQUESTS:.spec.containers[*].resources.requests'; then NODE_SNAPSHOT_READY=true; printf 'NODE_SNAPSHOT_READY=true node=%s observed=%s\n' "$NODE" "$OBSERVED_AT"; else printf '중단: node 자원 또는 범위 조회 실패. 빈 목록을 여유 자원으로 해석하지 않는다.\n' >&2; fi`

`Allocatable`, `Allocated resources`, Pod requests, `Non-terminated Pods`, taints, `MemoryPressure`, `DiskPressure`, `PIDPressure`, `Ready`를 본다. CPU·memory·ephemeral-storage·Pod 수 request가 실제로 부족하면 capacity 경로다. node가 `NotReady` 또는 pressure이면 node 문제의 별도 evidence로 보존하되 `Preempted` 원인을 대체하지 않는다. 목록에 남은 낮은 priority Pod를 임의로 victim으로 표시하거나 삭제하지 않는다.

controller victim의 replacement 가능성은 owner desired replica, replacement request·placement, 사용 가능한 node capacity에 달려 있다. standalone Pod는 controller가 없으면 자동 replacement를 기대하지 않는다. replacement가 Pending이면 선점 복구가 아니라 현재 capacity 또는 배치 정책 문제다.

### 4. Scheduler 판단과 배치 제약

진입 증거는 preemptor Event 또는 scheduler evidence에 `taint`, affinity, topology, quota, `Preemption is not helpful`, `No preemption victims found` 또는 resource failure가 있는 경우다. 실제 scheduler 배포 방식·namespace·selector·Pod·container가 확인된 경우에만 로그를 조회한다. 기본 control-plane namespace, label selector, Pod·container 이름을 가정하지 않는다.

연결 경로는 `실행 host → kubectl client → API server → scheduler Pod 또는 managed control plane → kubelet/runtime → preemptor Pod`다. scheduler Pod 목록이 보였다는 사실은 scheduler 판단 로그가 완전하거나 preemptor가 배치됐다는 것을 보장하지 않는다.

**scheduler 후보 조회값 설정·후보 출력 — 실제 control-plane 배포가 확인된 경우에만 아래 한 줄 전체를 복사**

`SCHEDULER_MODE='PASTE_SCHEDULER_MODE_HERE'; SCHEDULER_NAMESPACE='PASTE_SCHEDULER_NAMESPACE_HERE'; SCHEDULER_SELECTOR='PASTE_SCHEDULER_SELECTOR_HERE'; SCHEDULER_CANDIDATES_READY=false; unset SCHEDULER_CANDIDATE_JSON; if [ "$EVIDENCE_READY" != true ]; then printf '%s\n' '중단: EVIDENCE_READY가 아니다.' >&2; elif [ "$SCHEDULER_MODE" = managed_control_plane ]; then printf '중단: managed_control_plane scheduler는 Pod·container·journal을 추측하지 않고 control-plane owner에게 이관한다.\n' >&2; elif [ "$SCHEDULER_MODE" != pod ]; then printf '중단: SCHEDULER_MODE는 pod 또는 managed_control_plane이어야 한다 value=%s\n' "$SCHEDULER_MODE" >&2; elif [ -z "$SCHEDULER_NAMESPACE" ] || [ -z "$SCHEDULER_SELECTOR" ]; then printf '%s\n' '중단: 확인된 scheduler namespace와 selector를 입력한다.' >&2; elif SCHEDULER_CANDIDATE_JSON="$(kubectl get pods -n "$SCHEDULER_NAMESPACE" -l "$SCHEDULER_SELECTOR" -o json)" && jq -e '.items | type == "array" and length > 0' <<<"$SCHEDULER_CANDIDATE_JSON" >/dev/null; then jq -r '.items[] | "=== Scheduler 후보 ===\nNamespace: \(.metadata.namespace)\nPod: \(.metadata.name)\nUID: \(.metadata.uid)\nPhase: \(.status.phase // "-")\nReady: \([.status.containerStatuses[]? | .ready] | if length==0 then "-" else join(",") end)\nNode: \(.spec.nodeName // "-")\nContainer 후보: " + ([.spec.containers[]?.name] | join(", "))' <<<"$SCHEDULER_CANDIDATE_JSON"; SCHEDULER_CANDIDATES_READY=true; printf 'SCHEDULER_CANDIDATES_READY=true mode=%s namespace=%s selector=%s\n' "$SCHEDULER_MODE" "$SCHEDULER_NAMESPACE" "$SCHEDULER_SELECTOR"; else printf '중단: scheduler 후보 API 실패 또는 빈 결과. managed control plane·selector·권한을 확인하고 로그를 추측하지 않는다.\n' >&2; unset SCHEDULER_CANDIDATE_JSON; fi`

selector는 API 호출에 quoted 값으로 전달하고, 후보 출력은 namespace·Pod·UID·phase·Ready·container 관계를 보존한다. 빈 결과는 scheduler가 없다는 뜻이 아니라 selector 불일치·권한·API 실패 가능성을 포함한다.

**scheduler 대상·시간 선택값 설정 — 후보 출력에서 하나를 확인한 경우에만 아래 한 줄 전체를 복사**

`SCHEDULER_POD='PASTE_SCHEDULER_POD_HERE'; SCHEDULER_CONTAINER='PASTE_SCHEDULER_CONTAINER_HERE'; START_RFC3339='PASTE_START_RFC3339_HERE'; SCHEDULER_SELECTION_READY=false; SCHEDULER_LOG_READY=false; unset SCHEDULER_POD_UID; if [ "$SCHEDULER_MODE" != pod ] || [ "$SCHEDULER_CANDIDATES_READY" != true ]; then printf '중단: scheduler mode가 pod가 아니거나 후보 gate가 아니다 mode=%s\n' "$SCHEDULER_MODE" >&2; elif [ -z "$SCHEDULER_POD" ] || [ -z "$SCHEDULER_CONTAINER" ] || ! [[ "$START_RFC3339" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]] || ! `SCHEDULER_SELECTION_READY=true`는 선택한 scheduler Pod·container가 후보 목록에 있다는 뜻만 가진다. managed control plane이면 이 선택을 하지 않고 Event·priority·node 자원 evidence를 control-plane owner에게 이관한다.

**scheduler evidence window gate — scheduler logs 직전에 아래 한 줄 전체를 복사**

`PREEMPTION_WINDOW_READY=false; PREEMPTION_WINDOW_END_EPOCH="$(date -u +%s)"; if [ "$PREEMPTION_TIME_READY" != true ] || [ -z "${PREEMPTION_EPOCH:-}" ] || [ -z "${START_EPOCH:-}" ] || [ "$START_EPOCH" -gt "$PREEMPTION_EPOCH" ] || [ "$PREEMPTION_EPOCH" -gt "$PREEMPTION_WINDOW_END_EPOCH" ]; then SCHEDULER_SELECTION_READY=false; SCHEDULER_LOG_READY=false; printf '중단: scheduler evidence window가 canonical PREEMPTION_EPOCH를 포함하지 않는다 start_epoch=%s preemption_epoch=%s end_epoch=%s\n' "${START_EPOCH:--}" "${PREEMPTION_EPOCH:--}" "${PREEMPTION_WINDOW_END_EPOCH:--}" >&2; false; else PREEMPTION_WINDOW_READY=true; printf 'PREEMPTION_WINDOW_READY=true source=scheduler start_epoch=%s preemption_epoch=%s end_epoch=%s victim_event_uid=%s\n' "$START_EPOCH" "$PREEMPTION_EPOCH" "$PREEMPTION_WINDOW_END_EPOCH" "$VICTIM_EVENT_UID"; true; fi`

**scheduler logs producer/grep 결과 분리 helper 등록 — 같은 Bash에서 한 번 실행**

`run_logs_filter(){ local label="$1" pod="$2" ns="$3" container="$4" since="$5" tail_count="$6" pattern="$7" output producer_rc grep_rc; command -v mktemp >/dev/null 2>&1 || { printf '%s\n' '중단: mktemp가 없다.' >&2; return 2; }; output="$(mktemp)" || return 2; kubectl logs "$pod" -n "$ns" -c "$container" --timestamps --since-time="$since" --tail="$tail_count" >"$output"; producer_rc=$?; if [ "$producer_rc" -ne 0 ]; then printf 'LOG_PRODUCER_FAILED label=%s rc=%s pod=%s pod_uid=%s container=%s\n' "$label" "$producer_rc" "$pod" "$SCHEDULER_POD_UID" "$container" >&2; rm -f "$output"; return "$producer_rc"; fi; grep -E -i -C 3 "$pattern" "$output"; grep_rc=$?; if [ "$grep_rc" -eq 1 ]; then printf 'LOG_FILTER_NO_MATCH label=%s pod=%s pod_uid=%s container=%s\n' "$label" "$pod" "$SCHEDULER_POD_UID" "$container" >&2; elif [ "$grep_rc" -ne 0 ]; then printf 'LOG_FILTER_FAILED label=%s rc=%s pod=%s pod_uid=%s container=%s\n' "$label" "$grep_rc" "$pod" "$SCHEDULER_POD_UID" "$container" >&2; fi; rm -f "$output"; return "$grep_rc"; }`

최종 scheduler log helper도 `PREEMPTION_WINDOW_READY=true`를 직접 요구한다. window가 아니면 producer를 호출하지 않는다.

`run_logs_filter(){ if [ "$PREEMPTION_WINDOW_READY" != true ] || [ "$PREEMPTION_TIME_READY" != true ] || [ "$SCHEDULER_LOG_READY" != true ]; then printf '중단: scheduler logs 직접 preemption window gate가 아니다 PREEMPTION_WINDOW_READY=%s PREEMPTION_TIME_READY=%s SCHEDULER_LOG_READY=%s\n' "$PREEMPTION_WINDOW_READY" "$PREEMPTION_TIME_READY" "$SCHEDULER_LOG_READY" >&2; return 2; fi; local label="$1" pod="$2" ns="$3" container="$4" since="$5" tail_count="$6" pattern="$7" output producer_rc grep_rc; command -v mktemp >/dev/null 2>&1 || return 2; output="$(mktemp)" || return 2; kubectl logs "$pod" -n "$ns" -c "$container" --timestamps --since-time="$since" --tail="$tail_count" >"$output"; producer_rc=$?; if [ "$producer_rc" -ne 0 ]; then rm -f "$output"; return "$producer_rc"; fi; grep -E -i -C 3 "$pattern" "$output"; grep_rc=$?; rm -f "$output"; return "$grep_rc"; }`

**scheduler 로그 직전 Pod UID 재조회 gate — 아래 한 줄 전체를 복사**

`SCHEDULER_LOG_READY=false; CURRENT_SCHEDULER_UID=''; if [ "$PREEMPTION_READY" != true ] || [ "$SCHEDULER_SELECTION_READY" != true ]; then printf '%s\n' '중단: PREEMPTION_READY 또는 SCHEDULER_SELECTION_READY가 아니다.' >&2; elif CURRENT_SCHEDULER_UID="$(kubectl get pod "$SCHEDULER_POD" -n "$SCHEDULER_NAMESPACE" -o jsonpath='{.metadata.uid}')" && [ "$CURRENT_SCHEDULER_UID" = "$SCHEDULER_POD_UID" ]; then SCHEDULER_LOG_READY=true; printf 'SCHEDULER_LOG_READY=true pod=%s uid=%s start=%s\n' "$SCHEDULER_POD" "$CURRENT_SCHEDULER_UID" "$START_RFC3339"; else SCHEDULER_SELECTION_READY=false; printf '중단: scheduler 로그 직전 Pod UID mismatch 또는 재조회 실패 expected=%s actual=%s\n' "$SCHEDULER_POD_UID" "${CURRENT_SCHEDULER_UID:--}" >&2; fi`

**scheduler 로그 확인 — 대상과 권한 확인 후 아래 한 줄 전체를 복사**

`if [ "$PREEMPTION_READY" != true ] || [ "$SCHEDULER_SELECTION_READY" != true ] || [ "$SCHEDULER_LOG_READY" != true ]; then printf '%s\n' '중단: PREEMPTION_READY, SCHEDULER_SELECTION_READY 또는 SCHEDULER_LOG_READY가 아니다.' >&2; else run_logs_filter scheduler "$SCHEDULER_POD" "$SCHEDULER_NAMESPACE" "$SCHEDULER_CONTAINER" "$START_RFC3339" 300 "$POD_UID|$PREEMPTOR_POD|FailedScheduling|Preempted|preemption|nominated|Insufficient cpu|Insufficient memory|Too many pods|taint|affinity|selector|topology|quota|victim|not helpful|No preemption victims"; fi`

예상 예: `Insufficient cpu`·`Insufficient memory`는 request와 allocatable을 다시 계산하는 capacity 분기다. `had untolerated taint`, affinity/selector, topology 또는 quota는 자원만 늘려도 해결되지 않을 수 있는 placement policy 분기다. `Preemption is not helpful` 또는 `No preemption victims found`는 victim을 내보내도 preemptor가 배치되지 않는다는 scheduler 판단이므로 priority를 무조건 올리거나 victim을 반복 삭제하지 않는다. 필터가 비면 오류 부재가 아니다. 같은 Pod·시간 범위의 제한된 tail을 재확인하고, selector·namespace·권한이 맞지 않으면 control-plane owner로 이관한다.

### 5. Controller와 서비스·Job 영향

진입 증거는 victim owner의 desired/Ready와 replacement가 없거나 Pending인 경우다. PDB는 preemption에서도 best effort이며 보호를 보장하지 않는다.

연결 경로: `실행 host → kubectl client/API server → owner controller/PDB → replacement Pod → Service endpoint 또는 Job 산출물 → 실제 기능`. controller object가 읽혀도 PDB 보호·replacement Ready·서비스 기능·Job 외부 호출의 멱등성은 보장하지 않는다.

**owner·PDB·replacement 범위 확인 — 아래 한 줄 전체를 복사**

`if [ "$PREEMPTION_READY" != true ] || [ "$VICTIM_STATE_READY" != true ]; then printf '%s\n' '중단: historical victim Event만 있고 현재 victim owner/controller 상태가 없어 영향 분기를 열지 않는다.' >&2; false; else kubectl get pdb -n "$NS" -o custom-columns='NAME:.metadata.name,SELECTOR:.spec.selector,MIN_AVAILABLE:.spec.minAvailable,MAX_UNAVAILABLE:.spec.maxUnavailable,CURRENT_HEALTHY:.status.currentHealthy,DESIRED_HEALTHY:.status.desiredHealthy,DISRUPTIONS_ALLOWED:.status.disruptionsAllowed,EXPECTED_PODS:.status.expectedPods,DISRUPTED_PODS:.status.disruptedPods' && kubectl get deploy,rs,sts,ds,job -n "$NS" -o wide && kubectl get pods -n "$NS" -o custom-columns='POD:.metadata.name,UID:.metadata.uid,OWNER_KIND:.metadata.ownerReferences[?(@.controller==true)].kind,OWNER_NAME:.metadata.ownerReferences[?(@.controller==true)].name,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,RESTARTS:.status.containerStatuses[*].restartCount,NODE:.spec.nodeName'; fi`

PDB label selector와 victim labels가 실제로 일치하는지 확인하고 `disruptionsAllowed`, `currentHealthy`, `desiredHealthy`, `disruptedPods`와 Event 시각을 보존한다. Deployment/DaemonSet은 desired·Ready와 replacement UID·node, Service endpoint와 실제 요청 지표를 확인한다. StatefulSet은 quorum·leader·순서·PVC와 data consistency를 먼저 확인한다. 이 명령의 성공은 controller replacement와 서비스 기능을 보장하지 않는다.

**Job owner인 경우에만 Job 이름을 선택하고 확인 — 아래 한 줄 전체를 복사**

`JOB='PASTE_JOB_HERE'; JOB_READY=false; if [ "$OWNER_KIND" != Job ]; then printf '%s\n' 'owner가 Job이 아니므로 Job 명령을 건너뛴다.'; else if [ -z "$JOB" ]; then printf '%s\n' '중단: owner chain에서 확인한 Job 이름을 입력한다.' >&2; elif kubectl get job "$JOB" -n "$NS" -o jsonpath='{.metadata.uid}{" succeeded="}{.status.succeeded}{" failed="}{.status.failed}{" active="}{.status.active}{" completions="}{.spec.completions}{"\n"}'; then JOB_READY=true; printf 'JOB_READY=true job=%s\n' "$JOB"; else printf '중단: Job API 조회 실패. 산출물·외부 호출을 추측하지 않는다.\n' >&2; fi; fi`

Job은 `completions`, `succeeded`, `failed`, `active`, 산출물과 외부 호출을 확인하며 멱등성·중복 실행이 입증되지 않으면 재실행하지 않는다. 새 Pod가 `Running`이어도 Ready·요청 성공·Job 산출물이 없으면 정상화가 아니다.

### 6. Node 장애와 선점의 분리

진입 증거는 `NodeNotReady`, `NetworkUnavailable`, pressure 또는 kubelet 오류가 victim/preemptor 시간과 겹치는 경우다. 연결 경로는 `실행 host → kubectl client → API server → node kubelet → runtime → Pod sandbox/container`이며, node 상태 성공은 선점 원인이나 application 정상의 증거가 아니다.

**node journal 선택값 설정 — 실제 node shell·systemd·unit을 확인한 경우에만 아래 한 줄 전체를 복사**

**remote journal producer/grep 결과 분리 helper 등록 — `NODE_REMOTE_READY=true` 이후 같은 Bash에서 한 번 실행**

`run_remote_journal(){ local service="$1" start="$2" end="$3" pattern="$4" output remote_cmd producer_rc grep_rc; [ "$NODE_REMOTE_READY" = true ] || { printf '중단: NODE_REMOTE_READY가 아니다 node=%s host=%s\n' "$NODE" "$NODE_HOST" >&2; return 2; }; output="$(mktemp)" || return 2; printf -v remote_cmd 'sudo -n journalctl -u %q --since %q --until %q --no-pager' "$service" "$start" "$end"; ssh -o BatchMode=yes -o ConnectTimeout=10 -- "$NODE_HOST" "$remote_cmd" >"$output"; producer_rc=$?; if [ "$producer_rc" -ne 0 ]; then printf 'JOURNAL_PRODUCER_FAILED service=%s rc=%s node=%s host=%s\n' "$service" "$producer_rc" "$NODE" "$NODE_HOST" >&2; rm -f "$output"; return "$producer_rc"; fi; grep -E -i -C 3 "$pattern" "$output"; grep_rc=$?; if [ "$grep_rc" -eq 1 ]; then printf 'JOURNAL_FILTER_NO_MATCH service=%s node=%s host=%s\n' "$service" "$NODE" "$NODE_HOST" >&2; elif [ "$grep_rc" -ne 0 ]; then printf 'JOURNAL_FILTER_FAILED service=%s rc=%s node=%s host=%s\n' "$service" "$grep_rc" "$NODE" "$NODE_HOST" >&2; fi; rm -f "$output"; return "$grep_rc"; }`

`run_remote_journal(){ if [ "$PREEMPTION_WINDOW_READY" != true ] || [ "$PREEMPTION_TIME_READY" != true ]; then printf '중단: node journal 직접 preemption window gate가 아니다 PREEMPTION_WINDOW_READY=%s PREEMPTION_TIME_READY=%s\n' "$PREEMPTION_WINDOW_READY" "$PREEMPTION_TIME_READY" >&2; return 2; fi; local service="$1" start="$2" end="$3" pattern="$4" output remote_cmd producer_rc grep_rc; [ "$NODE_REMOTE_READY" = true ] || return 2; output="$(mktemp)" || return 2; printf -v remote_cmd 'sudo -n journalctl -u %q --since %q --until %q --no-pager' "$service" "$start" "$end"; ssh -o BatchMode=yes -o ConnectTimeout=10 -- "$NODE_HOST" "$remote_cmd" >"$output"; producer_rc=$?; if [ "$producer_rc" -ne 0 ]; then rm -f "$output"; return "$producer_rc"; fi; grep -E -i -C 3 "$pattern" "$output"; grep_rc=$?; rm -f "$output"; return "$grep_rc"; }`

**node condition·kubelet evidence 확인 — 아래 한 줄 전체를 복사**

`if [ "$PREEMPTION_READY" != true ] || [ "$JOURNAL_READY" != true ] || [ "$NODE_REMOTE_READY" != true ]; then printf '%s\n' '중단: PREEMPTION_READY, JOURNAL_READY 또는 NODE_REMOTE_READY가 아니다.' >&2; else kubectl get node "$NODE" -o jsonpath='{.metadata.uid}{" node="}{.metadata.name}{"\n"}{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{" message="}{.message}{"\n"}{end}' && run_remote_journal "$KUBELET_SERVICE" "$START_JOURNAL" "$END_JOURNAL" "$NODE|$POD_UID|notready|networkunavailable|pressure|runtime|evict|failed"; fi`

예상 예: `KubeletNotReady`, `container runtime is down`, `MemoryPressure`가 같은 시각이면 node·runtime 계층으로 이관한다. `Preempted` Event가 victim UID와 preemptor priority를 지지하면 node 장애가 선점 Event를 대신하지 않도록 두 사건을 분리 보존한다. 실제 node shell·systemd·unit이 확인되지 않으면 journal 명령을 추측하지 않는다.

## 복구 전 권한·영향 gate

victim·preemptor namespace, Pod UID, node, Event 시각과 priority policy를 승인된 대상과 다시 대조한다. PriorityClass·resource request·quota·PDB·owner 변경은 해당 owner와 플랫폼 관리자의 승인 범위를 확인한다. 서비스 replica·Ready·endpoint, StatefulSet quorum, Job 중복 호출·산출물, 다른 tenant의 preemptor 영향 범위를 기록한다.

- 선점을 node 장애로 간주해 `cordon`·`drain`하지 않는다. node condition·pressure가 별도로 입증될 때만 node 운영 절차로 이관한다.
- 기본 조치는 controller가 victim replacement를 만들도록 두고 scheduler·서비스 지표를 관찰하는 것이다. PriorityClass, priority, preemptionPolicy, resource request, scale, node policy 변경은 별도 변경으로 수행한다.
- **Trigger:** `Preempted` Event·victim policy·preemptor 또는 scheduler decision·node resource/condition·서비스 또는 Job 영향이 같은 시간축에 맞는다.
- **권한·영향:** workload는 owner, PriorityClass·scheduler·node는 플랫폼 관리자, 서비스·Job은 서비스 owner가 승인한다. 다른 namespace와 고우선 Pod의 배치 변화를 사전 평가한다.
- **기대 효과·비보장:** controller 재생성은 replica 회복을 기대하지만 capacity 부족·placement 제약·재선점을 해결하거나 application Ready를 보장하지 않는다. priority 변경도 선점 방지를 보장하지 않는다.
- **중단·rollback:** 고우선 Pod Pending, victim 반복 선점, Ready 감소, quorum 위험, Job 중복 위험 또는 새 Warning 증가 시 중단하고 이전 정책으로 돌아갈지 승인자와 결정한다.
- **검증:** scheduler 배치, replacement Ready, resource 여유·node condition, 실제 서비스 요청 또는 Job 산출물을 즉시와 재평가 시각에 확인한다.

## 정상화와 증거 보존

정상화는 연결·스케줄링 경로를 역순으로 확인한다. application 기능과 실제 요청 또는 Job 산출물 → preemptor process·Ready → kubelet/runtime sandbox와 node condition → scheduler placement·resource 여유 → victim owner desired/Ready와 replacement UID 순서다. preemptor가 의도한 node에 실제 배치되고 scheduler의 capacity·조건이 안정적이어야 하며, 관찰 창 동안 같은 `Preempted`·`FailedScheduling`·Warning이 반복되지 않아야 한다. replacement 성공과 선점 원인 해결은 별도로 기록한다.

victim/preemptor namespace·Pod UID·node, Event UID·원문에서 필요한 message·시간·count, PriorityClass·priority·preemptionPolicy·nominated node, owner, PDB selector/status, node resource/condition, scheduler 로그 시간·필터·결정적 행, 서비스 지표와 Job 상태를 보존한다. Secret 원문·token·개인키·개인정보는 저장하지 않는다.

## Prometheus 관측 적용성

일반 kube-state-metrics 계약에는 역사적으로 삭제된 victim의 `Preempted` Event와 preemptor·priority 관계를 확정하는 표준 condition metric이 없다. 따라서 존재를 확인하지 않은 `kube_pod_status_reason{reason="PreemptionByScheduler"}`나 유사한 status reason query를 제공하지 않는다. 이 런북에서 선점의 canonical evidence는 같은 victim UID·시각의 Kubernetes Event이며, PromQL은 **비적용**이다.

별도 exporter가 직접 수집하는 Event metric 또는 condition metric의 이름·label·보존 기간·UID 계약이 운영 문서에서 확인된 경우에만 해당 exporter owner가 완성 query를 제공한다. 계약이 확인되기 전에는 빈 series를 선점 부재나 정상으로 해석하지 않고 Event API·scheduler evidence로 돌아간다.
