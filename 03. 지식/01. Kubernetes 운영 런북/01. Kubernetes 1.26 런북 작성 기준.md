# Kubernetes 1.26 런북 작성 기준

여러 에이전트가 병렬로 작성하더라도 같은 진단 깊이와 안전 경계를 유지하기 위한 공통 계약이다. 런북의 본문은 명령 사용법이 아니라 **관측 결과 이후의 장애 파이프라인**을 설명해야 한다.

> [!danger] 금지하는 문서 형태
> `목적 | 명령 | 정상 관측 | 이상 관측 | 다음 단계 | 위험도 | 적용 조건` 표를 반복하지 않는다. context·API server·버전 확인을 모든 문서에서 장황하게 되풀이하지 않는다. `get → describe → events → logs`를 무조건 전부 실행하는 직선형 목록도 만들지 않는다.

## 버전 계약

- Kubernetes Server 기준: `1.26.x`
- `kubectl` 기준: `1.26.x`
- Kubernetes 1.26에서 제공되는 API와 CLI 동작만 기본값으로 사용한다.
- alpha·beta 기능은 활성화 여부와 feature gate를 적용 조건에 명시하지 않으면 사용하지 않는다.
- 1.27 이상에서 추가되거나 바뀐 동작을 1.26의 기본 동작처럼 작성하지 않는다.
- 배포판, CNI, 런타임, Ingress·Gateway, 스토리지와 OS 차이는 확인된 범위만 작성하고 나머지는 `미검증`으로 표시한다.

> [!warning] 지원 종료 버전
> Kubernetes 1.26은 현재 upstream 지원이 종료된 버전이다. 이 문서는 현행 클러스터 운용 기준을 맞추기 위한 것이며, 보안 패치와 업그레이드 계획은 별도로 관리해야 한다.

기준 버전은 frontmatter와 이 공통 문서에서 관리한다. 개별 런북에서는 버전 차이가 실제 분기를 바꿀 때만 설명한다. 모든 문서에 `kubectl version` 확인 절차를 반복하지 않는다.

## 파일과 frontmatter

하나의 런북은 최초 증상과 가장 가까운 카테고리 한 곳에만 둔다. 다른 계층은 문서 안의 분기 또는 wikilink로 연결한다.

파일명 형식:

```text
NN. 운영자가 보는 증상 또는 오류 문자열.md
```

예:

```text
02. 워크로드/01. Pod/01. Pod STATUS가 Error인 경우.md
```

```yaml
---
title: 런북 제목
type: runbook
status: draft
created: YYYY-MM-DD
updated: YYYY-MM-DD
parent: "[[00. Kubernetes 운영 런북 허브]]"
category: 워크로드/Pod
kubernetes_server: 1.26.x
kubectl: 1.26.x
review_needed: true
---
```

실제 1.26 클러스터에서 명령과 분기를 검증하기 전에는 `status: draft`, `review_needed: true`를 유지한다.

## 입력값과 빠른 수집

모든 런북은 **H1 제목 바로 아래**에 `## 입력값과 빠른 수집`을 둔다. 이 블록은 처음부터 모든 값을 요구하는 목록이 아니라 `대상 지정 → 기본값 자동 수집`의 실제 운영 순서를 보여 준다.

- `### 1. 대상 지정`: 운영자가 처음 입력할 최소 식별자만 둔다. Pod 런북은 보통 `<namespace>`, `<pod>`이며 controller 런북은 `<namespace>`, controller 이름이다.
- `### 2. 기본값 자동 수집`: UID, node, container, owner, selector처럼 명령 결과로 얻는 값을 분리한다.
- 특정 runtime, journal, audit, dependency, rollback 분기에서만 쓰는 값은 상단에 한꺼번에 나열하지 않고 **해당 상세 절의 첫 사용 직전**에 예시 형식과 함께 선언한다.
- 자동 수집 또는 분기별 입력을 운영자가 처음부터 채워야 하는 값처럼 표현하지 않는다.

자리표시자는 문서의 이후 명령 또는 설명에서 실제로 쓰이는 값만 둔다. Pod 문서라고 해서 `<container>`, `<node>`, `<service>`, `<pvc>`, 시간값을 전부 나열하지 않는다. 예를 들어 PVC를 보지 않는 문서에는 `<pvc>`를, node 로그가 없는 문서에는 `<start-journal>`을 넣지 않는다.

각 값에는 실제 형식을 한 줄로 붙인다. 대상 지정과 자동 수집값은 상단에서 다음처럼 구분한다.

```text
<namespace>       예: payments
<pod>             예: api-6d79f9d7cc-x4k9p
<container>       예: api
<pod-uid>         예: 2d6a7b1c-4f7e-4db2-8c71-4d9e8ef1a234
```

로그·journal·audit 시간은 실제로 해당 분기에 들어간 경우에만 그 절의 입력 블록에서 다음 형식으로 선언한다.

```text
<start-rfc3339>   예: 2026-07-26T09:00:00Z
<start-journal>   예: 2026-07-26 09:00:00 UTC
<start-audit>     예: 07/26/2026 09:00:00
```

입력값 바로 아래에는 **그 문서에 나열한 값만 출력하는** 읽기 전용 수집 명령을 둔다. 일반 Pod 진단이라면 다음처럼 Pod UID·node·container 이름을 한 번에 모은다. 문서가 이 값 중 일부를 쓰지 않으면 출력과 입력 목록에서 함께 뺀다.

```bash
kubectl get pod <pod> -n <namespace> -o custom-columns='NAMESPACE:.metadata.namespace,POD:.metadata.name,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,RESTARTS:.status.containerStatuses[*].restartCount,NODE:.spec.nodeName,AGE:.metadata.creationTimestamp'
kubectl get pod <pod> -n <namespace> -o jsonpath='uid={.metadata.uid}{"\n"}{range .spec.containers[*]}container={.name}{"\n"}{end}{range .spec.initContainers[*]}init-container={.name}{"\n"}{end}'
date -u '+%Y-%m-%dT%H:%M:%SZ'
```

Pod 이름은 알지만 namespace를 모를 때에만 다음 탐색 명령을 쓴다. `<pod>`를 그대로 넣어 namespace를 확정한 뒤, 이후에는 즉시 namespaced 명령으로 돌아간다. 이 탐색 명령을 쓴다고 별도 `<pod-fragment>` 입력값을 만들지 않는다.

```bash
kubectl get pods -A -o custom-columns='NAMESPACE:.metadata.namespace,POD:.metadata.name,PHASE:.status.phase,READY:.status.containerStatuses[*].ready,NODE:.spec.nodeName' --no-headers | grep -F -- '<pod>'
```

`kubectl config current-context`는 입력값 수집이나 진단 명령으로 넣지 않는다. broad query는 namespace를 찾는 이 예외에만 사용하고, `grep` 패턴에는 토큰·개인정보를 넣지 않는다.

## 문서의 무게 중심

문서 앞부분은 짧게 끝낸다.

1. 제목 바로 아래의 입력값과 빠른 수집
2. `## 진입 판단`의 사용·적용·제외 표
3. 반드시 존재하는 `검색 문자열:` 한 줄
4. 최초 확인 명령 2~4개와 각 명령에서 반드시 볼 필드·문자열

`언제 사용하는가`, `검색 문자열`, `검색 키워드`, `적용·제외 조건`을 여러 H2로 흩어 놓지 않는다. `## 진입 판단` 하나로 통합하고 다음 형식을 사용한다.

```markdown
## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 운영자가 이 런북에 들어오는 직접 관측 |
| 적용 | 이 문서가 책임지는 범위와 필요한 식별자 |
| 제외 | 다른 런북으로 넘길 조건과 정확한 wikilink |

검색 문자열: `대표 STATUS`, `Event reason`, `condition`, `핵심 오류 문자열`.
```

검색 문자열은 모든 런북에 필수다. 제목 문자열만 반복하지 말고 운영자가 화면, Event, condition, 로그에서 실제로 검색할 대표 동의어와 오류 문자열을 포함한다. 근거 없는 구현체 전용 문자열은 추가하지 않는다.

문서의 절반 이상은 다음 내용이어야 한다.

1. 관측 결과별 분기
2. 분기별 실제 동작 파이프라인
3. Kubernetes 밖으로 내려가는 점검
4. 원인이 확인된 뒤의 제한적 복구
5. 동일 파이프라인을 거슬러 올라가는 정상화 검증

## 최초 확인 작성법

`kubectl get pod`와 `kubectl describe pod`는 필요한 만큼 사용할 수 있다. 다만 명령 자체를 설명하지 말고 출력에서 볼 곳만 적는다.

```bash
kubectl get pod <pod> -n <namespace> -o wide
kubectl describe pod <pod> -n <namespace>
```

바로 아래에는 다음처럼 쓴다.

```text
get에서 볼 것: STATUS, READY, RESTARTS, NODE, AGE
describe에서 볼 것: State, Last State, Reason, Exit Code, Restart Count, Conditions, Events의 첫 실패 message
```

이벤트는 `describe`만으로 분기가 어려울 때 한 번만 별도 조회한다. 같은 Event 명령을 분기마다 반복하지 않는다.

```bash
kubectl get events -n <namespace> --field-selector involvedObject.kind=Pod,involvedObject.name=<pod> --sort-by=.metadata.creationTimestamp
```

`kubectl config current-context`와 API server·버전 확인 표는 런북에 넣지 않는다. 대상 namespace, Pod와 승인된 변경 범위는 입력값·변경 기록으로 관리한다.

## 로그·journal 증거 선별

로그 명령은 출력량만 늘리는 관측이 아니다. 로그·journal을 사용하는 모든 분기는 **시간 범위, container 또는 node, 증상에 맞춘 필터, 예상 메시지 예시와 다음 분기**를 함께 제시한다. `kubectl logs`와 `journalctl` 원문 전체를 던지고 운영자에게 결정적 문자열을 찾게 하지 않는다.

Pod 로그는 기본적으로 `<start-rfc3339>`와 `--timestamps`를 사용한다. 결정적 오류를 좁힐 때는 `grep -E -i -C 3`을 사용해 앞뒤 문맥 세 줄을 남긴다.

```bash
kubectl logs <pod> -n <namespace> -c <container> --timestamps --since-time=<start-rfc3339> --tail=200 | grep -E -i -C 3 'panic|fatal|error|exception|timeout|refused|denied|permission|oom|killed'
```

예상 관측은 명령 바로 뒤에 한 줄 이상으로 쓴다.

```text
예상 예: 2026-07-26T09:03:11Z ERROR dial tcp 10.0.4.18:5432: connect: connection refused
의미: process는 시작됐지만 외부 DB 연결이 거부됐다. Service/endpoint 또는 DB·방화벽 분기로 이동한다.
```

필터가 아무것도 반환하지 않으면 오류가 없다는 뜻이 아니다. 해당 문서는 다음 한 줄로 같은 시간 범위의 비식별화된 tail을 제한해 재확인하도록 쓴다. Secret·token·개인정보가 보이면 출력·저장을 중단하고 필요한 오류 문자열만 기록한다.

```bash
kubectl logs <pod> -n <namespace> -c <container> --timestamps --since-time=<start-rfc3339> --tail=50
```

노드 로그는 node 접근 권한, 실제 unit 이름, systemd 사용 여부가 확인된 경우에만 사용한다. `<start-journal>`과 `<end-journal>`은 반드시 해당 node/journal 분기의 첫 명령 앞에 예시 형식까지 둔다.

```bash
sudo journalctl -u kubelet --since "<start-journal>" --until "<end-journal>" --no-pager | grep -E -i -C 3 '<pod-uid>|<pod>|failed|error|oom|evict|mount|sandbox|cni|runtime'
```

```text
예상 예: failed to create pod sandbox: rpc error: code = Unknown desc = failed to setup network
의미: application 로그가 아니라 sandbox/CNI 또는 runtime 경로다. CNI·IPAM 분기로 이동한다.
```

필터 키워드는 증상에 맞게 줄인다. 예를 들어 image pull은 `pull|resolve|unauthorized|denied|429|x509|timeout`, mount는 `mount|attach|volume|device|filesystem|permission`, OOM은 `oom|out of memory|killed process|evict`, probe는 `probe|unhealthy|killing|timeout|refused`를 쓴다. `grep`·`journalctl`의 환경별 동작이 미확정이면 조건을 적고 담당 계층으로 이관한다.

## 분기 작성법

분기는 관측 가능한 문자열이나 필드에서 시작한다.

상세 분기 앞에는 문서당 한 번만 `## 관측별 진단 경로`를 둔다. `쉬운 말 요약`, `쉬운 요약표`, `쉬운 분기 요약`, `빠른 길잡이`, `관측 결과 요약`처럼 문서마다 다른 제목을 만들지 않는다. 운영자가 아래로 모두 내리지 않고 현재 경로를 고를 수 있게 `지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절`만 쓴다. `CRI`, `cgroup`, `EndpointSlice`처럼 이해에 필요한 용어는 표에서 먼저 풀어 쓰고, 정확한 기술 용어는 상세 절에서 사용한다.

```text
지금 보이는 것: OOMKilled 또는 종료 코드 137
먼저 볼 것: 이 컨테이너의 메모리 제한과 노드의 메모리 부족 표시
그다음 어디를 볼지: kubelet 로그, Linux OOM 기록, workload 메모리 설정
상세 절: 2
```

이 표는 길 안내일 뿐 원인을 확정하거나 상태 변경을 승인하지 않는다. `목적 | 명령 | 정상 | 이상` 같은 반복 명령 표로 바꾸지 않는다.

| 관측 | 1차 판단 | 다음 파이프라인 |
|---|---|---|
| `reason=OOMKilled` | 컨테이너 cgroup 한도 또는 노드 메모리 압박 | 컨테이너 limit → 사용량 → node pressure → kernel OOM |
| `FailedMount` | volume 준비 경로 실패 | Pod volume → PVC/PV → VolumeAttachment → CSI → kubelet → OS mount |

각 분기에는 다음 흐름을 실제 명령과 함께 쓴다.

```text
관측 문자열
-> 지금 가장 가능성 높은 실패 지점
-> 다음 명령
-> 그 출력에서 볼 필드·오류 문자열
-> 결과 A/B에 따른 다음 레이어
-> 안전한 종착점 또는 담당 계층 이관
```

`원인 가능`에서 끝내지 않는다. 다음에 무엇을 실행하고 무엇이 나오면 어느 레이어로 내려갈지 연결한다.

## 파이프라인 깊이

증상과 관련된 경로만 사용하되, Kubernetes 객체 조회에서 멈추지 않는다.

### 이미지·레지스트리

```text
Pod waiting reason·Event
-> 실제 image reference와 imagePullPolicy
-> imagePullSecrets 이름·ServiceAccount 연결
-> 같은 node와 다른 node의 재현 범위
-> kubelet 로그
-> container runtime 로그와 CRI image pull
-> node의 DNS·route·proxy·TLS 시간
-> registry 인증·권한·rate limit·mirror
```

### 컨테이너 시작·재시작

```text
State·Last State·exitCode
-> image entrypoint·command·args·securityContext
-> current/previous log
-> probe·resource limit
-> kubelet
-> container runtime·OCI error
-> cgroup·kernel OOM·filesystem·host dependency
```

### 스케줄링

```text
FailedScheduling message
-> 일반·init container request와 Pod overhead
-> ResourceQuota·LimitRange
-> node allocatable·pod capacity
-> taint/toleration·selector/affinity·topology
-> PVC binding·volume topology
-> scheduler 정책·플러그인 로그
```

### 스토리지

```text
FailedAttachVolume·FailedMount
-> Pod volume source
-> PVC·PV·StorageClass
-> VolumeAttachment
-> CSI controller·node plugin
-> kubelet volume manager
-> Linux block device·mount·filesystem·multipath
```

### 네트워크·sandbox

```text
FailedCreatePodSandBox message
-> 실패 node 범위
-> CNI·IPAM 또는 runtime sandbox 구분
-> CNI DaemonSet·node plugin 로그
-> container runtime·kubelet
-> Linux network namespace·interface·route·iptables/nftables
-> IP pool·external network dependency
```

### 설정·외부 의존성

```text
Event·application log
-> ConfigMap·Secret 참조 이름과 key
-> 실제 mount/env 주입 경로
-> application endpoint·timeout
-> Pod DNS·Service·NetworkPolicy
-> 외부 DB·API·queue·certificate·firewall
```

환경별 명령은 구현체를 확인한 뒤 조건부로 제시한다. 예를 들어 containerd가 확인됐을 때만 `journalctl -u containerd`, CRI endpoint와 권한이 확인됐을 때만 `crictl`을 사용한다. 구현체가 미확정이면 명령을 발명하지 말고 확인할 서비스·로그 위치와 이관 정보를 적는다.

## 명령 규칙

- 모든 명령은 복사 가능한 원라인으로 작성한다.
- 줄바꿈 연결용 `\`를 사용하지 않는다.
- `<namespace>`, `<pod>`, `<node>`처럼 교체할 값은 명시적인 자리표시자로 쓴다.
- namespaced 리소스 명령에는 `-n <namespace>`를 넣는다.
- 상태 변경 전에는 대상 namespace, Pod 또는 owner와 승인된 변경 범위를 변경 기록에서 다시 대조한다.
- broad query보다 확인된 namespace, workload, Pod 또는 node 범위를 우선한다.
- Secret 원문, 토큰, 인증서 개인키와 개인정보를 출력하거나 문서에 저장하도록 안내하지 않는다.
- 1.26에서 지원되지 않는 `kubectl` 옵션을 사용하지 않는다.

명령 뒤에는 긴 메타데이터 표 대신 `볼 것:` 한 줄을 둔다. 명령을 실행해도 다음 분기가 바뀌지 않으면 삭제한다.

## 상태 변경 규칙

`delete`, `rollout`, `scale`, `patch`, `edit`, `cordon`, `drain`과 재실행 명령은 진단 목록에 섞지 않는다.

상태 변경에는 반드시 다음을 적는다.

- 실행 trigger와 직접 근거
- 남아 있는 안전 gate
- 대상과 예상 영향 범위
- 실행 권한과 승인 조건
- 기대 효과와 보장하지 않는 것
- 되돌림 또는 중단 조건
- 실행 후 검증 명령과 재평가 시간

Job·CronJob 재실행은 멱등성, 외부 시스템 재호출과 데이터 중복 여부가 확인되지 않으면 제시하지 않는다. StatefulSet과 quorum 워크로드는 일반 Deployment 복구 절차를 그대로 적용하지 않는다.

## 복구와 정상화

새 Pod가 생성됐거나 `Running`이 됐다는 사실만으로 정상화를 선언하지 않는다.

- 원하는 replica와 Ready 수가 일치한다.
- 같은 오류, 종료 reason과 재시작 증가가 관찰 시간 동안 반복되지 않는다.
- 새 Warning 이벤트가 발생하지 않는다.
- 실제 요청, 핵심 기능, Job 산출물 또는 서비스 지표가 정상이다.
- 완화 성공과 근본 원인 상태를 별도로 기록한다.

정상화는 진단 파이프라인을 역순으로 확인한다. 예를 들어 registry 장애라면 새 Pod의 `Running`만 보지 말고 runtime pull 성공, kubelet Warning 중단, registry 오류·rate limit 해소, 실제 서비스 Ready까지 확인한다.

## 병렬 작성 규칙

- 에이전트 하나는 할당된 파일만 작성한다.
- 에이전트가 임의로 새 카테고리나 공통 템플릿을 만들지 않는다.
- 개별 에이전트는 공유 허브를 동시에 수정하지 않는다.
- 같은 증상의 동의어와 대표 오류 문자열은 해당 런북의 검색 키워드에 모은다.
- 통합 담당자가 중복, 끊어진 분기, 위험한 복구 명령과 wikilink를 최종 검수하고 허브 링크를 갱신한다.

## 완료 점검

- [ ] Kubernetes Server와 `kubectl` `1.26.x` 기준인가?
- [ ] `STATUS`, Pod phase와 container state를 혼동하지 않았는가?
- [ ] 앞부분이 짧고 `get`·`describe`에서 볼 항목만 짚는가?
- [ ] `입력값과 빠른 수집`이 H1 바로 아래에 있고, 최초 수동 입력·자동 수집·분기별 조건부 입력이 구분되는가?
- [ ] `## 진입 판단`에 사용·적용·제외가 있고 `검색 문자열:`이 빠짐없이 존재하는가?
- [ ] 분기표 제목이 정확히 `## 관측별 진단 경로`이며 문서당 한 번만 존재하는가?
- [ ] 목적/정상/이상/위험도 표를 반복하지 않는가?
- [ ] 모든 명령이 실제 다음 분기를 바꾸는가?
- [ ] 로그·journal 명령에 시간 범위·범위·증상별 필터와 예상 메시지 예시·의미·다음 분기가 있는가?
- [ ] 분기 이후 Kubernetes 객체에서 런타임·Linux·외부 의존성까지 필요한 깊이로 이어지는가?
- [ ] 각 레이어에서 실행할 명령과 볼 출력이 연결되어 있는가?
- [ ] 읽기 전용 진단과 상태 변경이 분리됐는가?
- [ ] 상태 변경에 trigger, 영향, 승인, 검증과 중단 조건이 있는가?
- [ ] 정상화가 실제 서비스 또는 작업 결과까지 확인하는가?
- [ ] 환경 의존 내용과 미검증 내용을 구분했는가?
- [ ] 민감정보 저장을 방지하는가?
- [ ] 상위 허브와 관련 런북으로 이동할 수 있는가?
