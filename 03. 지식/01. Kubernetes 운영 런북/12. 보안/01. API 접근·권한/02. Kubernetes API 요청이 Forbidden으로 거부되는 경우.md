# Kubernetes API 요청이 Forbidden으로 거부되는 경우

## 입력값과 빠른 수집

요청 identity는 `authenticated subject + verb + API group/resource/subresource + resourceName + namespace + auditID + UTC 창`이다. `can-i=yes`는 이 identity가 같을 때의 authorization 판정일 뿐 실제 요청·admission·서비스 성공을 보장하지 않는다.

| 종류 | 변수 | 출처 |
|---|---|---|
| 최초 입력 | `VERB`, `API_GROUP`, `RESOURCE`, `SUBRESOURCE`, `RESOURCE_NAME`, `NS` | 원래 403의 exact 요청 범위, 해당 없음은 `-` |
| API 자동값 | `CONFIG_FINGERPRINT`, `RESOURCE_TOKEN`, `REQUEST_KEY`, 조건부 `BIND_UID/RV`, `ROLE_UID/RV` | client config와 exact RBAC 객체 API |
| 계산 후보값 | `SUBJECT_RE`, `AUDIT_RE` | redacted audit filter용 escape |
| 운영자 선택값 | `SUBJECT`, `AUDIT_ID`, UTC 창, exact binding/role, 승인 manifest | 원래 response·audit·승인 inventory 확인 뒤 선택 |

workload owner/container/node/runtime/service/storage/Linux identity는 이 authorization 요청에 직접 적용되지 않는다. 변경 뒤 workload replacement가 생기면 해당 런북에서 새 UID·owner 관계를 별도 등록한다.

refresh는 UID/RV·owner/containerID/node/host/relation/time/argv-regex에 해당하는 request·RBAC·audit 상태와 모든 downstream `READY`를 먼저 지운다. 실패한 API·pipeline은 이전 `true`를 보존하지 않는다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 인증 후 HTTP `403`, `User ... cannot ...`, `is forbidden` |
| 적용 | exact current subject와 요청 scope, binding→roleRef→rule, audit 판정을 연결 가능 |
| 제외 | `401`은 [[01. API 서버 인증이 실패하거나 Unauthorized가 반환되는 경우]], `violates PodSecurity`·webhook deny는 admission 런북 |

검색 문자열: `Forbidden`, `User`, `cannot`, `resourceNames`, `pods/log`, `pods/exec`, `status`, `scale`, `impersonate`.

## 현재 subject와 exact can-i

원래 403과 redacted audit에서 subject와 auditID를 확인한다. kubeconfig user label을 subject로 추정하지 않는다.

`SUBJECT='PASTE_REDACTED_EXACT_SUBJECT_HERE'; AUDIT_ID='PASTE_AUDIT_ID_HERE'; SUBJECT_READY=false; if [ "$AUTO_READY" != true ] || ! current_request; then AUTO_READY=false; printf '%s\n' '중단: 현재 request identity가 아니다.' >&2; elif [ -z "$SUBJECT" ] || ! [[ "$AUDIT_ID" =~ ^[A-Za-z0-9-]+$ ]]; then printf '%s\n' '중단: subject/auditID 확인값 오류' >&2; else SUBJECT_RE="$(printf '%s' "$SUBJECT" | sed 's/[][\\.^$*+?(){}|]/\\&/g')"; AUDIT_RE="$AUDIT_ID|$SUBJECT_RE|403|forbidden|authorization"; SUBJECT_READY=true; export SUBJECT AUDIT_ID SUBJECT_RE AUDIT_RE; printf 'SUBJECT_READY=true subject=%s auditID=%s requestKey=%s\n' "$SUBJECT" "$AUDIT_ID" "$REQUEST_KEY"; fi`

**현재 credential의 complete scope SelfSubjectAccessReview**

`if [ "$SUBJECT_READY" != true ] || ! current_request; then AUTO_READY=false; EVIDENCE_READY=false; printf '%s\n' '중단: 현재 subject/request identity가 아니다.' >&2; elif ! command -v mktemp >/dev/null 2>&1; then EVIDENCE_READY=false; printf '%s\n' '중단: mktemp 없음' >&2; else REVIEW_FILE="$(mktemp)" || { EVIDENCE_READY=false; printf '%s\n' '중단: 임시 파일 생성 실패' >&2; }; GROUP="$API_GROUP"; [ "$GROUP" = core ] && GROUP=''; REVIEW_NS="$NS"; [ "$REVIEW_NS" = '-' ] && REVIEW_NS=''; REVIEW_SUB="$SUBRESOURCE"; [ "$REVIEW_SUB" = '-' ] && REVIEW_SUB=''; REVIEW_NAME="$RESOURCE_NAME"; [ "$REVIEW_NAME" = '-' ] && REVIEW_NAME=''; if [ -n "${REVIEW_FILE:-}" ] && jq -n --arg verb "$VERB" --arg group "$GROUP" --arg resource "$RESOURCE" --arg subresource "$REVIEW_SUB" --arg name "$REVIEW_NAME" --arg namespace "$REVIEW_NS" '{apiVersion:"authorization.k8s.io/v1",kind:"SelfSubjectAccessReview",spec:{resourceAttributes:{verb:$verb,group:$group,resource:$resource,subresource:$subresource,name:$name,namespace:$namespace}}}' >"$REVIEW_FILE"; then if REVIEW_JSON="$(kubectl create -f "$REVIEW_FILE" -o json)"; then EVIDENCE_READY=true; jq -c '{allowed:.status.allowed,denied:(.status.denied // false),reason:(.status.reason // "-"),evaluationError:(.status.evaluationError // "-")}' <<<"$REVIEW_JSON"; else EVIDENCE_READY=false; printf '%s\n' '중단: SelfSubjectAccessReview API 실패' >&2; fi; else EVIDENCE_READY=false; printf '%s\n' '중단: review JSON 생성 실패' >&2; fi; [ -z "${REVIEW_FILE:-}" ] || rm -f "$REVIEW_FILE"; fi`

이 review에는 `--as`를 쓰지 않으며 현재 kubeconfig subject만 판정한다. 원래 403 audit의 `$SUBJECT`와 current credential subject가 exact match한다는 별도 audit 증거가 필요하다. `allowed=true`도 admission이나 실제 요청 성공을 보장하지 않고, `list/watch`와 object `get`, resource와 subresource를 바꾸어 해석하지 않는다.

## UTC와 audit 계약

`START_RFC3339='PASTE_START_RFC3339_HERE'; END_RFC3339='PASTE_END_RFC3339_HERE'; TIME_READY=false; RFC3339_RE='^[0-9]{4}-(0[1-9]|1[0-2])-([0-2][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9]Z$'; if ! [[ "$START_RFC3339" =~ $RFC3339_RE ]] || ! [[ "$END_RFC3339" =~ $RFC3339_RE ]]; then printf '%s\n' '중단: canonical UTC RFC3339 형식 오류' >&2; elif [ "$(date -u -d "$START_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" != "$START_RFC3339" ] || [ "$(date -u -d "$END_RFC3339" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)" != "$END_RFC3339" ]; then printf '%s\n' '중단: date round-trip 실패' >&2; elif [ "$(date -u -d "$START_RFC3339" +%s)" -ge "$(date -u -d "$END_RFC3339" +%s)" ]; then printf '%s\n' '중단: 시간 순서 오류' >&2; elif [ "$SUBJECT_READY" != true ] || ! current_request; then AUTO_READY=false; printf '%s\n' '중단: 현재 subject/request identity가 아니다.' >&2; else TIME_READY=true; export START_RFC3339 END_RFC3339; printf 'TIME_READY=true start=%s end=%s auditID=%s\n' "$START_RFC3339" "$END_RFC3339" "$AUDIT_ID"; fi`

audit owner에게 exact `auditID` 한 건을 요청한다. 필수 필드는 `stage`, `requestReceivedTimestamp`, `stageTimestamp`, `verb`, redacted `requestURI`, `user.username/groups`, `objectRef.apiGroup/resource/subresource/namespace/name`, `responseStatus.code/reason`이다. `RequestReceived -> ResponseComplete/Panic` 순서, request scope와 `$SUBJECT`가 모두 같아야 한다. token, Authorization header, source IP, request/response body와 개인정보는 저장하지 않는다. audit query 자체가 실패하거나 한 건이 아니면 `EVIDENCE_READY=false`다.

승인된 redacted audit JSON은 완결 stage 한 건만 담은 regular file로 전달받는다. actor는 exact match에만 쓰고 출력에는 subject hash만 남긴다.

`AUDIT_RECORD_PATH='PASTE_REDACTED_AUDIT_RECORD_PATH_HERE'; AUDIT_READY=false; EVIDENCE_READY=false; if [ "$TIME_READY" != true ] || [ "$SUBJECT_READY" != true ] || ! current_request; then AUTO_READY=false; then IFS=$'\t' read -r AID ATS ASTAGE ACODE AREASON <<<"$AUDIT_TSV"; ATS_CANON="$(date -u -d "$ATS" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null)"; SUBJECT_HASH="$(printf '%s' "$SUBJECT" | sha256sum | cut -c1-16)"; if [ -z "$ATS_CANON" ] || [ "$(date -u -d "$ATS_CANON" +%s)" -lt "$(date -u -d "$START_RFC3339" +%s)" ] || [ "$(date -u -d "$ATS_CANON" +%s)" -gt "$(date -u -d "$END_RFC3339" +%s)" ]; then printf '%s\n' '중단: audit timestamp가 증거 창 밖임' >&2; else AUDIT_READY=true; EVIDENCE_READY=true; export AUDIT_RECORD_PATH SUBJECT_HASH; printf 'AUDIT_READY=true auditID=%s timestamp=%s stage=%s status=%s reason=%s subjectHash=%s\n' "$AID" "$ATS_CANON" "$ASTAGE" "$ACODE" "$AREASON" "$SUBJECT_HASH"; fi; else printf '%s\n' '중단: 단일 audit record와 request identity 불일치' >&2; fi; fi`

## exact RBAC 객체

전체 RoleBinding·ClusterRoleBinding subject dump를 하지 않는다. 승인 inventory 또는 audit owner가 확인한 exact binding만 선택한다.

`BIND_KIND='PASTE_ROLEBINDING_OR_CLUSTERROLEBINDING_HERE'; BIND_NS='PASTE_BINDING_NAMESPACE_OR_DASH_HERE'; BIND_NAME='PASTE_BINDING_NAME_HERE'; RBAC_READY=false; if [ "$TIME_READY" != true ] || ! current_request; then AUTO_READY=false; printf '%s\n' '중단: 현재 TIME/request identity가 아니다.' >&2; elif [ "$BIND_KIND" != RoleBinding ] && [ "$BIND_KIND" != ClusterRoleBinding ]; then printf '%s\n' '중단: binding kind 오류' >&2; elif ! [[ "$BIND_NS" =~ ^(-|[-a-z0-9.]+)$ ]] || ! [[ "$BIND_NAME" =~ ^[-a-z0-9.]+$ ]]; then printf '%s\n' '중단: binding identity 형식 오류' >&2; elif [ "$BIND_KIND" = RoleBinding ] && BJ="$(kubectl get rolebinding "$BIND_NAME" -n "$BIND_NS" -o json)" || [ "$BIND_KIND" = ClusterRoleBinding ] && BJ="$(kubectl get clusterrolebinding "$BIND_NAME" -o json)"; then VALS="$(jq -er --arg s "$SUBJECT" '[.metadata.uid,.metadata.resourceVersion,.roleRef.kind,.roleRef.name,([.subjects[]? | select((.kind=="ServiceAccount" and ("system:serviceaccount:" + .namespace + ":" + .name)==$s) or (.kind=="User" and .name==$s) or (.kind=="Group" and .name==$s))] | length | tostring)] | @tsv' <<<"$BJ")" && IFS=$'\t' read -r BIND_UID BIND_RV ROLE_KIND ROLE_NAME SUBJECT_MATCHES <<<"$VALS"; if [ "${SUBJECT_MATCHES:-0}" -ne 1 ]; then printf '중단: exact subject match count=%s\n' "${SUBJECT_MATCHES:-0}" >&2; else if [ "$ROLE_KIND" = Role ]; then RJ="$(kubectl get role "$ROLE_NAME" -n "$BIND_NS" -o json)"; else RJ="$(kubectl get clusterrole "$ROLE_NAME" -o json)"; fi; if ROLE_VALS="$(jq -er '[.metadata.uid,.metadata.resourceVersion] | @tsv' <<<"$RJ")"; then IFS=$'\t' read -r ROLE_UID ROLE_RV <<<"$ROLE_VALS"; RBAC_READY=true; export BIND_KIND BIND_NS BIND_NAME BIND_UID BIND_RV ROLE_KIND ROLE_NAME ROLE_UID ROLE_RV; jq -c '{binding:{kind:.kind,name:.metadata.name,uid:.metadata.uid,rv:.metadata.resourceVersion,roleRef:.roleRef},matchedSubjects:[.subjects[]? | {kind,namespace,name}]}' <<<"$BJ"; jq -c '{role:{kind:.kind,name:.metadata.name,uid:.metadata.uid,rv:.metadata.resourceVersion},aggregationRule,rules}' <<<"$RJ"; else printf '%s\n' '중단: roleRef API 실패' >&2; fi; fi; else printf '%s\n' '중단: binding API 실패' >&2; fi`

`current_rbac(){ local bj rj matches; [ "$RBAC_READY" = true ] || return 1; if [ "$BIND_KIND" = RoleBinding ]; then bj="$(kubectl get rolebinding "$BIND_NAME" -n "$BIND_NS" -o json)" || return 1; else bj="$(kubectl get clusterrolebinding "$BIND_NAME" -o json)" || return 1; fi; jq -e --arg uid "$BIND_UID" --arg rv "$BIND_RV" --arg rk "$ROLE_KIND" --arg rn "$ROLE_NAME" '.metadata.uid==$uid and .metadata.resourceVersion==$rv and .roleRef.kind==$rk and .roleRef.name==$rn' <<<"$bj" >/dev/null || return 1; matches="$(jq -r --arg s "$SUBJECT" '[.subjects[]? | select((.kind=="ServiceAccount" and ("system:serviceaccount:" + .namespace + ":" + .name)==$s) or (.kind=="User" and .name==$s) or (.kind=="Group" and .name==$s))] | length' <<<"$bj")" || return 1; [ "$matches" -eq 1 ] || return 1; if [ "$ROLE_KIND" = Role ]; then rj="$(kubectl get role "$ROLE_NAME" -n "$BIND_NS" -o json)" || return 1; else rj="$(kubectl get clusterrole "$ROLE_NAME" -o json)" || return 1; fi; jq -e --arg uid "$ROLE_UID" --arg rv "$ROLE_RV" '.metadata.uid==$uid and .metadata.resourceVersion==$rv' <<<"$rj" >/dev/null; }`

**exact rule gate**

`RULE_READY=false; if [ "$AUDIT_READY" != true ] || ! current_request || ! current_rbac; then AUTO_READY=false; RBAC_READY=false; printf '%s\n' '중단: 현재 audit/request/RBAC identity가 아니다.' >&2; else if [ "$ROLE_KIND" = Role ]; then RJ="$(kubectl get role "$ROLE_NAME" -n "$BIND_NS" -o json)"; else RJ="$(kubectl get clusterrole "$ROLE_NAME" -o json)"; fi; GROUP="$API_GROUP"; [ "$GROUP" = core ] && GROUP=''; RULE_RESOURCE="$RESOURCE"; [ "$SUBRESOURCE" = '-' ] || RULE_RESOURCE="$RESOURCE/$SUBRESOURCE"; RULE_NAME="$RESOURCE_NAME"; [ "$RULE_NAME" = '-' ] && RULE_NAME=''; MATCHES="$(jq -r --arg g "$GROUP" --arg r "$RULE_RESOURCE" --arg v "$VERB" --arg n "$RULE_NAME" '[.rules[]? | select(any(.apiGroups[]?; .==$g or .=="*") and any(.resources[]?; .==$r or .=="*") and any(.verbs[]?; .==$v or .=="*") and (((.resourceNames // [])|length)==0 or ($n!="" and any(.resourceNames[]?; .==$n))))] | length' <<<"$RJ")"; if [ "$MATCHES" -gt 0 ]; then RULE_READY=true; else RULE_READY=false; fi; printf 'RULE_READY=%s exactRuleMatches=%s requestKey=%s\n' "$RULE_READY" "$MATCHES" "$REQUEST_KEY"; fi`

rule에서 exact `apiGroups`, `resources`, `verbs`, `resourceNames`, `nonResourceURLs`를 요청과 대조한다. aggregated ClusterRole이면 generated rule을 직접 수정하지 않는다. `*`, cluster-admin 또는 broad group이 보이면 최소 권한 증거가 아니다.

## 변경·rollback·정상화

진단은 읽기 전용이다. 이 문서는 RBAC mutation·rollback 명령을 제공하지 않는다. 변경은 fresh `current_request`·`current_rbac`, 단일 auditID의 직접 근거, 최소 rule, namespace/workload/RBAC owner 승인 ID, 실행 주체·변경 창·HA 조건, 자동화 재시도의 idempotence, 승인 manifest digest와 이전 manifest digest를 배포 시스템이 mutation 직전에 다시 확인할 때만 수행한다.

배포 시스템이 binding 또는 role을 바꾸면 현재 UID/RV와 모든 `READY`를 즉시 폐기한다. 같은 이름을 재사용하지 않고 새 UID/RV, exact subject→binding→roleRef→role relation과 rule을 이 문서 처음부터 재등록한다. rollback도 별도 승인과 이전 digest를 fresh object에 대조한 뒤 같은 배포 시스템에서 수행한다.

정상화는 `RBAC object UID/RV -> exact subject binding -> exact rule -> can-i -> 원래 비변경 요청 -> workload/service 기능 -> 관찰 창` 순으로 확인한다. rollback도 이 경로로 실제 검증한다. `can-i=yes`, apply 성공, Pod `Running`, 403 metric 감소만으로 정상화하지 않는다.
