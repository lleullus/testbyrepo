# Kubernetes 업그레이드가 API 호환성·버전 차이로 진행되지 않는 경우

## 입력값과 빠른 수집

| 구분 | 값 | 출처와 gate |
|---|---|---|
| 최초 입력 | `UPGRADE_RECORD` | 승인된 change record의 exact ID |
| API 확인 자동값 | `CLUSTER_UID`, `PLAN_RV`, `UPGRADE_OWNER`, `CURRENT_SERVER`, `TARGET_VERSION`, `EXECUTION_STATE` | record와 현재 API에서 교차 확인 |
| 계산 후보값 | `TARGET_RE`, `API_GV_RE` | literal escape 결과이며 bounded 출력 전 미확정 |
| 운영자 선택값 | `START_RFC3339`, `END_RFC3339`, 조건부 `API_GV` | preflight/audit의 실제 오류에서 선택 |

경로는 `작업 PC/bastion의 kubectl -> API endpoint/LB -> kube-apiserver -> admission/conversion webhook -> CRD/add-on controller -> node kubelet`이다. provider 장비나 node shell은 승인된 provider 절차에서만 접근한다. 업그레이드 record만으로 kubeadm/provider 구현을 추측하지 않는다.

`refresh_upgrade`

`approved_change_get`은 조직의 승인 read-only helper 계약이다. 없으면 record owner가 동일 필드를 제공할 때까지 중단한다. refresh는 현재 ID/RV/owner/container ID/node·host/relations/time 파생값/argv-regex와 selection 이후 gate를 먼저 비우며 어떤 실패에도 stale 값을 승격하지 않는다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 승인 upgrade가 removed API, skew, webhook, CRD 또는 add-on preflight 때문에 중단된 경우 |
| 적용 | exact plan revision·cluster UID·target과 현재 상태가 연결된 경우 |
| 제외 | 일반 API endpoint 장애는 API server 런북, 승인 없는 계획 수립은 upgrade owner 절차로 이동 |

검색 문자열: `deprecated`, `removed API`, `no matches for kind`, `version skew`, `unsupported version`, `webhook timeout`, `conversion`, `preflight`, `rollback`.

## 최초 확인

`if [ "$AUTO_READY" != true ]; then printf '%s\n' '중단: fresh upgrade state가 아니다.' >&2; elif kubectl auth can-i get nodes >/dev/null 2>&1; then AUTH_READY=true; kubectl get nodes -o custom-columns='NODE:.metadata.name,UID:.metadata.uid,READY:.status.conditions[?(@.type=="Ready")].status,KUBELET:.status.nodeInfo.kubeletVersion,RUNTIME:.status.nodeInfo.containerRuntimeVersion' || { AUTH_READY=false; printf '%s\n' 'producer 실패: node 조회 실패' >&2; }; else AUTH_READY=false; printf '%s\n' '권한 경계: nodes get 확인 실패' >&2; fi`

`if [ "$AUTO_READY" != true ] || [ "$AUTH_READY" != true ]; then printf '%s\n' '중단: fresh identity/auth가 아니다.' >&2; else kubectl api-resources -o wide || printf '%s\n' 'producer 실패: discovery 실패' >&2; fi`

`auth can-i=yes`는 실제 요청 성공·동일 impersonation·admission 통과를 보장하지 않는다. `Forbidden`은 리소스 부재가 아니다. cluster-wide audit 원문, Secret, webhook `caBundle`, token과 kubeconfig는 수집하지 않는다.

### 1. API와 CRD

preflight 또는 승인 audit가 실제 GVR을 지목한 경우에만 선택한다.

`API_GV_INPUT='PASTE_EXACT_API_GROUP_VERSION_HERE'; unset API_GV API_GV_RE; EVIDENCE_READY=false; if [ "$AUTO_READY" != true ] || ! [[ "$API_GV_INPUT" =~ ^[A-Za-z0-9.-]+/[A-Za-z0-9.-]+$ ]]; then printf '%s\n' '중단: fresh plan 또는 G/V 형식 오류' >&2; else API_GV="$API_GV_INPUT"; API_GV_RE="^$(printf '%s' "$API_GV" | sed 's/[][\\.^$*+?(){}|]/\\&/g')$"; if ! API_VERSIONS="$(kubectl api-versions)"; then printf '%s\n' 'producer 실패: API discovery 조회 실패' >&2; elif grep -Fxq "$API_GV" <<<"$API_VERSIONS"; then EVIDENCE_READY=true; printf 'EVIDENCE_READY=true served=%s regex=%s\n' "$API_GV" "$API_GV_RE"; else RC=$?; if [ "$RC" -eq 1 ]; then printf 'no match: current server가 %s를 discovery에서 반환하지 않음\n' "$API_GV" >&2; else printf 'filter 오류: G/V 필터 실패 rc=%s\n' "$RC" >&2; fi; fi; unset API_VERSIONS; fi; unset API_GV_INPUT`

no match는 과거 caller·저장 객체가 없다는 뜻이 아니다. 승인 audit의 caller, timestamp, GVR과 manifest inventory를 target release 제거 목록에 대조한다. CRD라면 exact CRD name을 owner에게 받아 UID/RV, served/storage version, conversion strategy만 조회한다. schema 변경, stored object rewrite와 conversion 비활성화는 하지 않는다.

### 2. skew·webhook·add-on

skew는 현재 server/kubelet/kubectl 값을 target release의 공식 matrix와 대조한다. 문자열 정렬로 버전 순서를 판정하지 않는다. webhook은 오류에 나온 exact configuration UID/RV와 Service namespace/name/port, EndpointSlice UID·address/port·ready 관계를 확인한다. 설정 존재는 endpoint TLS/application 성공을 보장하지 않는다. `failurePolicy=Fail`을 `Ignore`로 바꾸지 않는다.

add-on은 승인 inventory의 actual kind/namespace/name/UID/imageID와 vendor release matrix를 사용한다. Deployment라고 추측하지 않는다. no object, API producer 실패, selector no match와 JSON/filter 오류를 분리한다.

### 3. 변경 gate와 정상화

upgrade 진행·rollback은 진단과 분리한다. mutation 직전 plan과 cluster를 refresh하고 다음을 모두 확인한다.

- exact target, plan RV, cluster UID, 실행 단계, evidence ID와 승인 ID가 fresh하다.
- API write 영향, maintenance window, node 순서, PDB·control-plane/workload quorum과 대체 capacity가 승인됐다.
- removed API caller·CRD/webhook/add-on compatibility 미해결 항목이 없거나 명시적 예외가 있다.
- etcd backup/managed provider 보호 증거와 restore 가능성이 확인됐다.
- 각 provider/kubeadm 단계의 재실행 멱등성과 package/API 외부 side effect를 owner가 확인했다.
- rollback은 현재 단계에서 실제 지원되는 공식 절차, 이전 artifact와 중단 기준을 가리킨다.

Ready/API 오류, webhook timeout, quorum 감소, plan drift가 stop 조건이다. 변경 후 기존 node/component ID와 relation을 버리고 새 UID/RV·server/kubelet version·webhook endpoint·add-on imageID를 refresh로 재등록한다. 정상화는 승인 target, API discovery뿐 아니라 실제 CRD conversion/admission, add-on 기능, workload desired/Ready, 실제 요청과 재발 관찰을 통과해야 한다.

## 메트릭 사용 경계

표준 `kube_node_info`에는 cluster UID나 승인 plan revision을 직접 연결하는 공통 label 계약이 없다. 따라서 이 문서는 범용 PromQL을 만들지 않는다. 환경별 external label이 승인 inventory의 `CLUSTER_UID`와 exact match한다고 증명된 경우에만 monitoring owner가 현재 node UID 목록과 함께 완성 query를 제공하며, 빈 결과를 호환성 통과로 해석하지 않는다.
