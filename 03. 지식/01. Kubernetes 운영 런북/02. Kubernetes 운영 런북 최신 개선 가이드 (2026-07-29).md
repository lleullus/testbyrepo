# Kubernetes 운영 런북 최신 개선 가이드 (2026-07-29)

## 문서 지위와 목적

이 문서는 2026-07-29 현재의 [[01. Kubernetes 1.26 런북 작성 기준]]을 보완하기 위한 초안이다. **작성 방식의 레퍼런스 구현체는 [[14. 관측성/01. 메트릭/03. Prometheus StatefulSet replica별 PVC 사용률이 다른 경우]]다.** 다른 런북은 기술 주제와 명령이 달라도, 입력값 등록·자동값 전달·가독성 있는 출력·쿼리 생성·연결 준비·실패 분기·정상화 검증 방식은 이 레퍼런스를 따라 작성한다.

이 가이드는 기존 작성 기준을 자동으로 대체하지 않는다. 검토가 끝나기 전에는 신규·기존 런북을 3번 문서와 같은 실사용 수준으로 끌어올리는 검수 기준과 기준 개정 후보로 사용한다.

핵심 결론은 다음과 같다.

> [!important] 핵심 결론
> 좋은 런북은 설명이 많은 문서가 아니라, 운영자가 값을 한 번만 입력하고 이후 결과가 다음 단계로 안전하게 연결되는 문서다. [[14. 관측성/01. 메트릭/03. Prometheus StatefulSet replica별 PVC 사용률이 다른 경우]]처럼 **실행 위치·도구 확인 → 최초 입력 → 읽기 쉬운 자동 수집 → 자동값과 선택값 분리 → 쿼리 생성 → 성공 gate → 실패 의미 → 다음 분기 → 정상화 검증**이 닫혀 있어야 한다.

## 레퍼런스 구현체에서 그대로 가져올 패턴

[[14. 관측성/01. 메트릭/03. Prometheus StatefulSet replica별 PVC 사용률이 다른 경우]]는 Prometheus 전용 진단 내용뿐 아니라 **런북을 실제로 사용하는 방법**까지 포함한 레퍼런스다. 다른 런북은 아래 패턴을 기술 주제에 맞게 치환한다.

| 3번 문서의 패턴 | 다른 런북에 적용하는 방법 |
|---|---|
| 입력값 종류 표 | 최초 입력, API 자동값, 계산 후보값, 운영자 선택값을 문서 앞에서 구분한다. |
| `PASTE_..._HERE` 입력칸 | 사용자가 직접 바꿀 문자열은 문서 전체에서 각각 한 번만 둔다. 실행용 자리표시자에 `< >`를 사용하지 않는다. |
| 같은 Bash에서 변수 재사용 | 자동 수집 결과를 `$NS`, `$POD`, `$PVC`처럼 후속 명령에 전달한다. 실행 host와 shell 유지 조건을 먼저 적는다. |
| 시작 시 이전 변수·tunnel 정리 | 재실행 전에 파생 변수와 이전 연결을 비우고, 단계별 `..._READY=true`가 확인된 경우에만 다음 단계로 이동한다. |
| Pod별 세로 출력 | 긴 `key=value` 한 줄 대신 대상별 구분선과 한국어 항목명으로 출력한다. container와 port, Pod와 PVC처럼 관계가 있는 값은 같은 항목에 묶는다. |
| 자동값과 선택값 분리 | API로 확정 가능한 UID·owner·PV는 자동 등록하고, high 대상·container·protocol·장애 시각은 출력 근거를 본 뒤 고른다. |
| 정규식·selector 자동 생성 | 이름을 그대로 regex에 붙이지 않고 특수문자를 escape하며, 생성된 값을 bounded 출력으로 확인한다. |
| PromQL 생성 명령 | PromQL, LogQL, MetricsQL, SQL, JSON body, URL query 등 외부 UI에 붙여 넣을 문자열은 등록된 변수로 완성본을 생성한다. 사용자가 쿼리 안의 여러 자리표시자를 직접 수정하게 하지 않는다. |
| port-forward 완결 cycle | 대상 UID 확인 → local/remote port 구분 → forwarding 준비 → readiness → HTTP/API success → 증거 수집 → 종료 확인 → cycle 변수 무효화 순서로 반복한다. |
| HTTP/API helper | 반복되는 요청은 공통 helper로 HTTP status, JSON 여부, API success field와 필요한 data를 검사한다. |
| 원인 확정·안전 gate·정상화 | 관측 결과를 원인 범주로 닫고, 위험한 변경은 진단과 분리하며, 실제 기능과 재발 관찰까지 역순 검증한다. |

> [!important] 레퍼런스 사용 원칙
> 3번 문서의 Prometheus 명령을 다른 주제에 그대로 복사하라는 뜻이 아니다. **입력 횟수, 값 전달, 출력 형태, 성공·실패 gate, 쿼리 생성, 연결 lifecycle과 검증 구조**를 그대로 가져오라는 뜻이다.

## 반드시 달라져야 하는 것

### 0. 실사용 입력칸과 Markdown 표시 방식을 먼저 정한다

3번 문서처럼 운영자가 실제로 바꿔야 하는 값과 문서 설명용 단어를 분리한다.

- 실행용 입력칸에는 꺾쇠괄호로 감싼 자리표시자를 사용하지 않는다.
- 직접 입력이 필요한 값은 `PASTE_..._HERE` 형태의 검색·더블클릭이 쉬운 문자열로 둔다.
- 각 `PASTE_..._HERE` 문자열은 문서 전체에서 한 번만 나타나야 한다.
- 같은 값이 다시 필요하면 문서에서 재입력하지 않고 `$NS`, `$TARGET` 같은 shell 변수를 사용한다.
- 사용자는 문서 전체의 찾아 바꾸기·모두 바꾸기를 사용하지 않아도 되어야 한다.
- 한 줄 실행 명령은 fenced code block이 아니라 인라인 코드 한 줄로 제공한다. 그래야 명령만 바로 선택·복사할 수 있다.
- fenced code block은 예상 출력, 연결 경로, 데이터 형식, 비실행용 Markdown 템플릿 또는 실제 다중 행 스크립트에만 사용한다.
- 설명·예상 출력·실행 명령을 하나의 코드 블록 안에 섞지 않는다.

### 1. 입력값을 네 종류로 분리한다

기존의 `대상 지정 → 기본값 자동 수집` 구조는 유지하되 모든 값은 다음 네 종류 중 하나로 표시한다.

| 종류 | 의미 | 예 | 작성 규칙 |
|---|---|---|---|
| 최초 입력 | API만으로 찾을 수 없는 최소 대상 식별자 | namespace, Pod, StatefulSet | 처음에 한 번만 입력 |
| API 확인 자동값 | 대상 객체에서 직접 읽어 확정할 수 있는 값 | UID, node, owner, PVC의 PV | 명령이 현재 shell에 등록하거나 바로 다음 명령에 전달 |
| 계산 후보값 | 규칙·기본값으로 만들지만 실제 사용 가능성을 검증해야 하는 값 | local port 기본값, regex, selector 문자열 | `확정`이 아니라 `후보`로 표시하고 대조 gate 제공 |
| 운영자 선택값 | 관측·정책·실제 구현을 확인해야 정할 수 있는 값 | high replica, 장애 시작 시각, 본체 container, protocol | 출력 확인 뒤 해당 분기 직전에 선택 |

자동 수집한 값을 다시 여러 자리표시자에 옮겨 적게 하지 않는다. 단, 복수 후보 중 어느 것이 실제 대상인지 API만으로 확정할 수 없으면 자동 선택하지 않는다.

### 2. 변수 사용 전에 등록 계약을 닫는다

shell 변수를 사용하는 런북은 첫 사용 전에 다음을 모두 보여 준다.

- 변수 이름과 의미
- 값의 출처
- 자동 등록인지 운영자 선택인지
- 같은 shell·실행 host를 유지해야 하는지
- 값이 비었거나 후보 수가 예상과 다를 때 중단하는 조건
- 재실행 시 이전 값이 남지 않도록 초기화하는 방법
- 후속 명령에서 실제 등록값을 확인하는 bounded 출력

등록되지 않은 `$LOCAL_PORT`, `$REMOTE_PORT`, `$CONTAINER`, `$START_RFC3339`를 후속 명령에서 처음 등장시키지 않는다. 배열은 일반 환경변수로 export되지 않으므로 `Bash 배열`인지 `export된 scalar`인지 구분한다.

3번 문서처럼 `INPUT_READY`, `AUTO_READY`, `SELECTION_READY`, `APP_READY` 등 단계별 유효 상태를 두고, 이전 단계가 준비되지 않았으면 후속 명령을 중단한다.

> [!warning] 부분 등록 금지
> 긴 명령의 중간 API 호출이 실패했는데 일부 변수만 이전 값으로 남으면 다른 Pod·PVC·cluster를 조회할 수 있다. 자동 등록 시작 전에 파생값을 비우고, 필수 호출과 후보 수 검증이 모두 성공했을 때만 후속 변수 세트를 유효하게 만든다.

### 3. 복사 가능한 원라인과 거대 one-liner를 구분한다

`모든 명령은 복사 가능한 원라인`이라는 규칙은 유지한다. 그러나 여러 단계가 섞인 하나의 거대 명령을 만들라는 뜻은 아니다.

- 대상 수집, 변수 등록, 연결 시작, readiness 확인, 실제 조회, 종료는 각각 독립적으로 검증 가능한 한 줄로 나눈다.
- 하나의 명령 안에서 여러 API를 호출하면 각 호출의 실패를 확인하고 부분 성공 상태를 후속 단계에 넘기지 않는다.
- 명령 바로 아래에 성공 출력, 실패 출력과 중단 조건을 적는다.
- `jq`, `curl`, `grep`, `ss`, `du`, `journalctl` 등 필수 도구가 없을 때의 대체 경로나 이관 조건을 둔다.
- 빈 출력은 `0`, `정상`, `오류 없음`으로 해석하지 않는다.

#### 3.1 자동 수집 출력은 사람이 바로 비교할 수 있게 만든다

자동 수집은 단순히 값을 많이 뽑는 명령이 아니다. 3번 문서처럼 다음 선택을 바로 할 수 있는 출력이어야 한다.

- 대상 리소스 또는 Pod마다 `=== 대상 ===` 구분선을 둔다.
- 항목명은 운영자가 이해할 수 있는 한국어로 적는다.
- UID, node, revision, phase, 시작 시각처럼 identity와 시각을 함께 보여 준다.
- container와 port, Pod와 PVC, PVC와 PV처럼 관계가 있는 값은 같은 줄 또는 같은 블록에 묶는다.
- 긴 map·JSON 원문·한 줄짜리 `key=value` 덩어리를 그대로 보여 주지 않는다.
- 출력 바로 아래에 무엇을 선택하는지, 왜 필요한지, 비어 있으면 어디서 중단하는지 설명한다.
- 복수 후보를 API만으로 확정할 수 없으면 임의로 첫 번째 값을 선택하지 않는다.

#### 3.2 외부 UI용 쿼리는 완성본을 생성한다

PromQL이 있는 문서뿐 아니라 LogQL, MetricsQL, SQL, Elasticsearch query, JSON request body, URL query를 제공하는 모든 문서에 적용한다.

- 쿼리 안의 namespace·Pod·PVC·label 값을 여러 번 직접 수정하게 하지 않는다.
- shell에 등록된 변수로 최종 쿼리 한 줄을 생성하는 명령을 제공한다.
- 사용자는 생성 명령의 출력만 Prometheus, Grafana, Loki, Kibana 또는 DB UI에 붙여 넣는다.
- resource 이름을 regex에 넣을 때는 `.`·`+`·`[` 같은 특수문자를 escape한다.
- 생성한 regex·selector·query를 bounded 출력으로 확인한 뒤 사용한다.
- 쿼리 결과가 비었을 때 metric 부재, label 불일치, 조회 범위 오류와 권한·API 실패를 구분한다.

3번 문서의 PromQL 생성 방식이 기본 예다. 다른 문서에서도 쿼리 언어만 바꾸고 **변수 등록 → 완성 쿼리 생성 → 출력만 복사** 흐름은 유지한다.

### 4. 연결형 런북은 hop을 먼저 그린다

네트워크, API, exec, logs, port-forward, storage backend와 runtime 연결을 다루는 런북은 명령보다 먼저 실제 hop을 한 줄로 적는다.

```text
실행 host → local socket 또는 client → API server·proxy → 대상 node·Pod → remote port·socket → process listener → application endpoint
```

각 hop에서 다음을 구분한다.

| 구분 | 확인 질문 |
|---|---|
| 실행 위치 | 명령이 작업 PC, bastion, node, Pod 중 어디에서 실행되는가? |
| 주소 의미 | `127.0.0.1`은 어느 network namespace의 loopback인가? |
| local endpoint | 작업 host에서 실제 listen 중인 port·socket은 무엇인가? |
| 전달 대상 | 어떤 Pod UID·node·remote port·socket으로 전달되는가? |
| listener | 선언된 `containerPort`가 아니라 실제 process가 해당 주소·port에 listen하는가? |
| protocol | TCP 위의 HTTP·HTTPS·gRPC 등 실제 protocol은 무엇인가? |
| application 성공 | readiness, API success field 또는 고유 metric으로 올바른 process임을 확인했는가? |

한 hop의 성공은 다음 hop의 성공 증거가 아니다. Pod `Running`, Endpoint `ready`, port-forward 프로세스 생존, TCP connect, HTTP 200과 application 정상은 각각 보장 범위가 다르다.

### 5. port와 socket은 역할별로 이름을 분리한다

`PORT` 하나로 Service port, local port와 container port를 함께 표현하지 않는다.

```text
LOCAL_PORT       작업 host에서 port-forward가 여는 listen port
SERVICE_PORT     client가 Service로 호출하는 port
TARGET_PORT      Service가 backend로 전달하도록 선언한 값
ENDPOINT_PORT    EndpointSlice에 materialize된 backend port
REMOTE_PORT      port-forward가 Pod에서 연결할 port
CONTAINER_PORT   Pod spec의 선언값이며 실제 listener 보장은 아님
LISTENER_PORT    process가 실제 bind한 port
```

socket도 `CRI_ENDPOINT`, `CRI_SOCKET`, `PROXY_SOCKET`처럼 역할을 이름에 포함한다. local 값과 remote 값을 같은 숫자로 맞추더라도 동일한 endpoint로 설명하지 않는다.

### 6. container와 port의 관계를 보존한다

멀티 container Pod에서 container 이름 목록과 전체 port 목록을 별도 열로 출력하면 대응 관계가 사라진다. 다음처럼 container별 port를 한 항목으로 묶는다.

```text
prometheus=http:9090; config-reloader=metrics:8080
```

`containerPort`는 후보 선언값이다. 다음 사실을 자동으로 보장하지 않는다.

- 해당 process가 실제 listen 중임
- `0.0.0.0`, Pod IP 또는 loopback 중 어느 주소에 bind했는지
- HTTP인지 HTTPS인지
- 인증 없이 호출할 수 있는지
- Service·EndpointSlice가 같은 port를 가리키는지

실제 listener 또는 application 고유 endpoint 확인 전에는 선택한 port를 확정 원인이나 정상화 근거로 사용하지 않는다.

### 7. port-forward는 하나의 완결된 cycle로 쓴다

각 대상 Pod마다 다음 순서를 독립적으로 반복한다.

```text
Pod name·UID 확인 → local port 후보 확인 → port-forward 시작 → forwarding 준비 확인 → protocol 확인 → readiness·API 확인 → 증거 수집 → port-forward 종료 → 변수 무효화
```

필수 규칙:

- `127.0.0.1`은 Pod 주소가 아니라 port-forward를 실행한 host의 loopback이라고 명시한다.
- `curl`은 같은 실행 host에서 수행한다. 다른 bastion·container의 `127.0.0.1`과 혼동하지 않는다.
- process가 살아 있다는 `kill -0`만으로 준비 완료로 판단하지 않는다.
- `Forwarding from ...` 또는 동등한 listen 증거와 application readiness를 모두 확인한다.
- local port 충돌이면 local port만 바꾸고 remote port를 임의 변경하지 않는다.
- 다음 replica로 바꿀 때 이전 `PF_PID`, URL, readiness 값을 재사용하지 않는다.
- 종료 뒤 tunnel process가 실제로 끝났는지 확인한다.

port-forward 오류는 최소 다음처럼 분기한다.

| 오류 | 의미 범위 | 다음 행동 |
|---|---|---|
| `address already in use` | 작업 host의 local port 충돌 | `LOCAL_PORT` 후보만 변경 |
| `pod is not running`·`container not found` | 대상 lifecycle 또는 identity 문제 | Pod UID·phase·container status 재확인 |
| `Forbidden` | `pods/portforward` 권한 문제 | 현재 주체·namespace·subresource 권한 경로로 이동 |
| `unable to forward port`·`error forwarding port` | API server→kubelet/runtime→Pod port 경계 | Pod UID·node·kubelet/runtime 증거 확인 |
| `lost connection to pod` | tunnel 유지 실패 또는 대상 lifecycle 변화 | 같은 시각의 Pod restart·node·runtime 상태 대조 |

### 8. HTTP와 API 성공을 transport 성공과 분리한다

HTTP 명령은 다음 세 단계를 분리한다.

```text
TCP·TLS 연결 → HTTP status → API/application success와 필요한 data
```

- `curl: (7)`과 `HTTP 000`은 application metric 부재가 아니다.
- `401`·`403`은 연결 성공 후 인증·인가 실패다.
- `404`는 endpoint·path·port 선택 문제 후보이며 값이 없는 정상 응답이 아니다.
- `5xx`는 API data를 해석하지 않고 server·backend 오류로 분기한다.
- JSON API는 HTTP 성공 뒤 `.status=="success"` 같은 실제 성공 필드를 확인하고 `.data`를 읽는다.
- `jq`에 오류 HTML·인증 응답을 넘겨 나온 `null`을 정상값으로 기록하지 않는다.
- TLS 검증 실패를 `-k` 또는 검증 비활성화로 우회하지 않는다.

### 9. 관측별 진단 경로에는 판별력을 넣는다

3번 문서처럼 본문의 길 안내 표는 `지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절`의 네 열로 간결하게 유지할 수 있다. 표를 일곱 열로 늘려 읽기 어렵게 만들 필요는 없다.

다만 표와 연결된 상세 절을 합쳤을 때 다음 질문에 모두 답해야 한다.

| 항목 | 필수 내용 |
|---|---|
| 지금 보이는 것 | 실제 status, condition, metric 관계 또는 오류 문자열 |
| 먼저 볼 것 | 이 분기를 다른 원인과 가르는 직접 증거 |
| 성공이 보장하는 범위 | 해당 관측으로 확인된 hop·상태 |
| 성공이 보장하지 않는 범위 | 다음 계층에서 여전히 실패할 수 있는 것 |
| 다음 gate | 다음 명령을 실행해도 되는 조건 |
| 실패 시 이동 | 담당 계층, 관련 런북 또는 이관 정보 |

즉, 길 안내 표는 짧게 쓰고 성공 gate·비보장·실패 의미는 상세 절에서 닫아도 된다. 중요한 것은 열의 수가 아니라 **표를 따라간 운영자가 다음 명령을 실행해도 되는지 판단할 수 있는가**다.

좋은 설명은 `무엇을 본다`에서 끝나지 않는다. 예를 들어 `connection refused`는 보통 대상 주소까지의 경로가 즉시 거부 응답을 받았다는 범위의 증거이며, firewall·listener 부재·잘못된 port 중 하나를 단독 확정하지 않는다. `timeout`도 network, policy, backend 지연과 host pressure를 직접 구분하지 못한다.

### 10. 상세 절은 여섯 요소를 갖춘다

각 상세 절은 최소 다음 순서로 닫는다.

1. 진입 증거: 어떤 관측일 때 이 절을 사용하는가.
2. 필수 입력: 이 절에서 처음 필요한 값과 그 출처는 무엇인가.
3. 실행 명령: 범위가 제한된 읽기 전용 명령은 무엇인가.
4. 성공 gate: 어떤 출력이어야 다음 단계로 갈 수 있는가.
5. 실패 의미: 대표 오류·빈 결과가 무엇을 의미하고 무엇을 의미하지 않는가.
6. 다음 행동: 다음 절, 관련 런북, 담당 owner와 보존할 증거는 무엇인가.

여섯 요소를 매번 고정된 소제목으로 반복할 필요는 없다. 3번 문서처럼 짧은 설명, 명령, 판정 bullet과 다음 링크로 자연스럽게 구성해도 된다. 다만 어느 요소도 빠져서는 안 된다.

명령이 성공해도 다음 분기가 달라지지 않거나 판단 기준이 없다면 그 명령은 삭제한다.

### 11. 상태값의 비보장 범위를 반드시 적는다

대표 런북의 좋은 문장을 공통 방식으로 확장한다.

- PVC `Pending`는 아직 binding되지 않았다는 뜻이지 항상 provisioning 실패는 아니다.
- Pod `Running`은 application readiness나 listener 정상을 보장하지 않는다.
- Endpoint `ready=true`는 모든 주소·port에서 process가 listen함을 보장하지 않는다.
- `containerPort` 선언은 실제 bind 상태를 보장하지 않는다.
- `auth can-i=yes`는 실제 요청의 context·subject·resource가 같거나 요청 자체가 성공함을 보장하지 않는다.
- port-forward process 생존은 local listen과 remote application 응답을 보장하지 않는다.
- HTTP 200은 기대한 replica·application·data가 맞음을 단독 보장하지 않는다.

### 12. 빈 결과와 수집 실패를 분리한다

모든 빈 출력에는 최소 다음 후보를 구분할 다음 확인을 둔다.

```text
대상 없음 | field가 해당 kind에 원래 없음 | selector 불일치 | metric 미수집 | 조회 범위 오류 | 권한 부족 | 도구 실패 | API 오류
```

Service와 Pod처럼 schema가 다른 resource를 하나의 범용 JSONPath로 조회하지 않는다. resource kind별로 존재하는 field만 출력하고, 조건부 resource는 실제 API resource 존재와 적용 방식을 확인한 뒤 조회한다.

### 13. identity와 시각을 명령 성공보다 우선한다

Pod·PVC·PV·EndpointSlice·VolumeAttachment·controller는 이름만 저장하지 않고 필요한 범위에서 UID와 관측 시각을 함께 기록한다. 다음 대상 또는 다음 replica로 넘어갈 때 UID가 바뀌면 이전 결과와 섞지 않는다.

누적 counter 비교는 process start·restart 원점이 같을 때만 직접 수행한다. 원점이 다르면 같은 시간 간격의 rate·delta로 비교한다. 로그는 최초 결정적 이벤트보다 조금 앞선 bounded 시간부터 확인한다.

### 14. 정상화는 연결 경로를 역순으로 검증한다

정상화는 객체 상태 한 개가 좋아진 것으로 닫지 않는다.

```text
application 기능 → API·metric 결과 → process listener → remote endpoint → 전달 경로 → local client → 객체 identity·condition
```

Pod `Running`, PVC `Bound`, port-forward 성공, HTTP 200, 사용률 한 번 하락과 오류 counter 정지는 각각 단독 정상화 근거가 아니다. 원인에 해당한 증거가 해소되고 실제 서비스 기능과 재발 관찰 창이 통과해야 한다.

## 신규 런북 작성 템플릿

새 런북은 기존 기준의 전체 구조를 따르되, [[14. 관측성/01. 메트릭/03. Prometheus StatefulSet replica별 PVC 사용률이 다른 경우]]의 실사용 흐름을 기본 골격으로 사용한다.

### 입력값과 빠른 수집 골격

| 구분 | 값 예시 | 출처·선택 기준 | 유효성 gate |
|---|---|---|---|
| 최초 입력 | `NS`, `TARGET` | 운영자가 승인된 namespace와 대상 이름을 한 번 입력 | exact-name API 조회 성공 |
| API 자동값 | `TARGET_UID`, `NODE`, `OWNER`, `BOUND_RESOURCE` | Kubernetes API에서 읽어 현재 Bash에 등록 | 비어 있거나 후보 수가 예상과 다르면 중단 |
| 계산 후보 | `LOCAL_PORT`, `TARGET_RE`, selector | 기본값 또는 등록값으로 생성 | 충돌·regex escaping·실제 조회 결과 검증 전 미확정 |
| 운영자 선택 | `CONTAINER`, `REMOTE_PORT`, `SCHEME`, `START_RFC3339` | 관계가 보존된 후보 출력과 실제 구현을 확인 | 선택값 검증과 application 응답 성공 |

실행용 입력칸은 아래처럼 문서 전체에서 한 번만 제공한다.

**실행 위치·도구 확인**

`TOOLS_READY=false; if [ -z "${BASH_VERSION:-}" ]; then printf '%s\n' '중단: Bash에서 실행한다.' >&2; else MISSING_TOOLS=''; for TOOL in kubectl jq curl grep; do command -v "$TOOL" >/dev/null 2>&1 || MISSING_TOOLS="$MISSING_TOOLS $TOOL"; done; if [ -z "$MISSING_TOOLS" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true shell=%s\n' "$BASH_VERSION"; else printf '중단: 없는 도구=%s\n' "$MISSING_TOOLS" >&2; fi; fi`

**최초 입력·이전 상태 초기화**

`unset INPUT_READY AUTO_READY SELECTION_READY TARGET_UID NODE OWNER BOUND_RESOURCE LOCAL_PORT TARGET_RE CONTAINER REMOTE_PORT SCHEME START_RFC3339; NS='PASTE_NAMESPACE_HERE'; TARGET='PASTE_TARGET_HERE'; INPUT_READY=false`

위 예시를 실제 런북에 사용할 때는 두 입력칸이 각각 문서 전체에서 한 번만 나타나게 한다. 대상 kind의 exact-name 조회가 성공한 경우에만 `INPUT_READY=true`로 만든다.

### 자동 수집 출력 골격

자동 수집 출력은 다음처럼 사람이 바로 비교할 수 있는 형태로 만든다. 이 블록은 예상 출력 예시이며 실행 명령이 아니다.

```text
=== 대상: sample-0 ===
UID: 11111111-2222-3333-4444-555555555555
Node: worker-01
상태: Running
Container/Port 후보: main=http:9090; sidecar=metrics:8080
연결 리소스: data-sample-0
관측 시각: 2026-07-29T12:00:00Z
```

출력 뒤에는 다음을 바로 설명한다.

- 어떤 값이 API 자동값인지
- 어떤 값은 후보이며 아직 확정이 아닌지
- 운영자가 무엇을 골라야 하는지
- 왜 그 값이 필요한지
- 값이 비거나 후보가 여러 개면 어느 단계에서 중단하는지

### 운영자 선택과 검증 골격

**운영자 선택값 입력**

`CONTAINER='PASTE_CONTAINER_HERE'; REMOTE_PORT='PASTE_REMOTE_PORT_HERE'; SCHEME='PASTE_HTTP_OR_HTTPS_HERE'`

실제 런북에서는 container 존재 여부, port 숫자 범위, 선언된 container-port 관계와 scheme 허용값을 검사한 뒤에만 `SELECTION_READY=true`로 만든다. 선언된 `containerPort`가 없더라도 실제 설정에서 확인된 값이면 다음 application gate에서 검증할 수 있지만, 실패 시 임의 port 변경은 금지한다.

### PromQL·외부 쿼리 생성 골격

다른 문서에도 PromQL이 있으므로 쿼리 안의 값을 직접 고치게 하지 않는다. shell 변수가 들어간 완성본을 생성한다.

**PromQL 생성 예시**

`printf 'metric_name{namespace="%s",pod="%s"}\n' "$NS" "$TARGET"`

정규식 matcher가 필요하면 대상 이름을 escape해 등록한 `TARGET_RE`를 사용한다.

`printf 'metric_name{namespace="%s",pod=~"%s"}\n' "$NS" "$TARGET_RE"`

사용자는 위 생성 명령의 **출력 한 줄만** Prometheus 또는 Grafana에 붙여 넣는다. LogQL·MetricsQL·SQL·JSON body도 같은 방식으로 완성본을 생성한다.

### 관측별 진단 경로 골격

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| 실제 상태·metric 관계 또는 오류 문자열 | 다른 원인과 가르는 직접 증거 | 다음 계층·담당 owner·관련 런북 | 해당 상세 절 링크 |

### 상세 절 골격

#### N. 관측 분기 이름

진입 증거: 실제 오류 문자열 또는 상태 관계가 같은 대상 UID·관측 시각에서 확인된 경우다.

연결 경로: 실행 host → 중간 hop → remote endpoint → application.

필수값: 이 절에서 처음 쓰는 값, 값의 출처, 자동값인지 운영자 선택값인지 설명한다. 비어 있으면 중단한다.

**실행 명령 — 아래 한 줄 전체를 복사**

`범위가 제한된 읽기 전용 원라인 명령`

성공 gate: 다음 단계로 이동할 수 있는 직접 출력을 적는다.

실패 분기: 대표 오류·빈 출력의 의미 범위와 다음 절·관련 런북·담당 owner를 적는다.

비보장: 이 성공만으로 다음 hop 또는 실제 서비스 기능 정상을 확정하지 않는다고 적는다.

다음 행동: 다음 명령, 이관 정보, 보존할 UID·시각·출력을 명시한다.

## 기존 런북 재검수 우선순위

### P0: 실제 명령 실패나 오진으로 직결

- 등록되지 않은 변수 사용
- local·remote 주소 또는 port 혼동
- container와 port 대응 관계 소실
- HTTP·HTTPS·인증 전제의 무조건 가정
- port-forward, proxy, exec, logs streaming 준비 확인 누락
- API·도구 실패 뒤 stale 변수나 부분 등록값 사용
- 상태 변경 명령에 승인·중단·rollback gate 없음

### P1: 원인 계층 오분류 가능

- `Running`, `Ready`, `Bound`, HTTP 200 같은 상태의 비보장 범위 누락
- 오류 문자열별 의미와 다음 분기 부족
- resource kind에 없는 field를 범용 명령에 혼합
- 빈 결과를 정상·0·오류 없음으로 해석
- UID·시각·counter 원점 없이 replica 또는 재생성 객체 비교
- broad query를 목적·범위 없이 실행

### P2: 운영 비용과 문서 일관성 문제

- 실행용 자리표시자에 `< >`를 사용하거나 문서 전체 찾아 바꾸기를 요구
- 같은 입력값 또는 자동 수집값을 여러 명령에 반복 입력
- 한 줄 실행 명령을 fenced code block에 넣어 명령만 바로 선택하기 어려움
- 자동 수집 출력이 긴 `key=value` 한 줄이라 대상별 비교와 선택이 어려움
- container와 port, Pod와 PVC처럼 연결된 값이 따로 출력돼 관계가 소실
- PromQL·LogQL 등 외부 쿼리 안의 여러 값을 사용자가 직접 수정
- regex·selector를 escape 없이 문자열 결합
- 동일 조회·설명이 여러 절에 반복
- 긴 one-liner가 여러 책임을 수행
- 도구 부재 대체 경로의 형식 불일치
- 정상화와 증거 보존 항목이 실제 원인 경로와 연결되지 않음

재검수 순서는 연결형 런북, 변수·자동화가 많은 런북, 상태 변경을 포함한 런북, 단순 조회형 런북 순으로 한다.
