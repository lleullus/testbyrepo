# Pending Pod가 있는데 node scale-up이 시작되지 않는 경우

## 입력값과 빠른 수집

`Pending`만으로 scale-up 필요나 autoscaler 고장을 확정하지 않는다. 같은 Pod UID의 순수 node 공급 부족 Event와 실제 autoscaler 입력 인식·decision 부재를 같은 시간 창에서 연결한다.

| 구분 | 값 | gate |
|---|---|---|
| 최초 입력 | `NS`, `POD` | exact-name API 조회 |
| API 자동값 | Pod UID·resourceVersion, owner·selector, containerID, node/unbound, request 원문 | owner relation과 현재 Pending identity |
| 계산 후보 | resource 요구량, escaped Pod regex, log argv-regex | init max·overhead와 regex 검증 전 미확정 |
| 운영자 선택 | autoscaler mode/Pod/container, UTC window, 실제 구현체 검색식 | 승인된 설치 인벤토리와 로그 schema 확인 후 선택 |

실행 host는 승인된 kubeconfig를 가진 작업 PC/bastion의 같은 Bash다. Kubernetes hop은 `작업 host → API server → Pending Pod/Event → autoscaler Pod logs`다. external mode의 provider 로그는 별도 승인 host/감사 경로이며 여기서 endpoint·CLI를 발명하지 않는다. SSH가 필요한 외부 절차는 값을 command string으로 만들거나 `eval`하지 말고 positional argument 또는 안전한 quoting으로 전달하고 원격 `hostname -f`·계정·scope를 재확인해야 한다.

`TOOLS_READY=false; MISSING=''; for T in kubectl jq date hostname sed tr grep awk; do command -v "$T" >/dev/null 2>&1 || MISSING="$MISSING $T"; done; if [ -n "${BASH_VERSION:-}" ] && [ -z "$MISSING" ]; then TOOLS_READY=true; printf 'TOOLS_READY=true host=%s\n' "$(hostname -f)"; else printf '중단: Bash 또는 도구 누락:%s\n' "$MISSING" >&2; fi`

### 시간·argv regex gate

`START_RFC3339='PASTE_SCALEUP_START_UTC_HERE'; END_RFC3339='PASTE_SCALEUP_END_UTC_HERE'; ARGV_RE='PASTE_SCALEUP_VERIFIED_LOG_REGEX_HERE'; WINDOW_READY=false; RFC3339_RE='^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$'; grep -E "$ARGV_RE" </dev/null >/dev/null 2>&1; REGEX_RC=$?; if [ "$AS_READY" != true ] || ! fresh_all; then printf '%s\n' '중단: fresh identity gate 실패' >&2; elif [[ ! "$START_RFC3339" =~ $RFC3339_RE ]] || [[ ! "$END_RFC3339" =~ $RFC3339_RE ]] || [ "$REGEX_RC" -eq 2 ] || [ -z "$ARGV_RE" ]; then printf '%s\n' '중단: canonical time 또는 검증된 regex 필요' >&2; elif START_EPOCH="$(date -u -d "$START_RFC3339" +%s 2>/dev/null)" && END_EPOCH="$(date -u -d "$END_RFC3339" +%s 2>/dev/null)" && [ "$(date -u -d "@$START_EPOCH" '+%Y-%m-%dT%H:%M:%SZ')" = "$START_RFC3339" ] && [ "$(date -u -d "@$END_EPOCH" '+%Y-%m-%dT%H:%M:%SZ')" = "$END_RFC3339" ] && [ "$START_EPOCH" -lt "$END_EPOCH" ] && [ "$END_EPOCH" -le "$(date -u +%s)" ]; then WINDOW_READY=true; export START_RFC3339 END_RFC3339 START_EPOCH END_EPOCH ARGV_RE; printf 'WINDOW_READY=true %s..%s regex=%s\n' "$START_RFC3339" "$END_RFC3339" "$ARGV_RE"; else printf '%s\n' '중단: round-trip/start<end/미래 상한 실패' >&2; fi`

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 같은 Pod UID의 Event가 순수 `Insufficient cpu/memory/ephemeral-storage` 또는 `Too many pods`이고 scale-up decision이 없음 |
| 적용 | current Pod·owner와 autoscaler Pod/container/Node identity, UTC Event·log window를 연결할 수 있음 |
| 제외 | taint·affinity·topology·PVC 조건은 [[18. Pod 이벤트에 FailedScheduling이 기록된 경우]], max/quota/capacity 직접 증거는 [[02. node group 최대 크기·인프라 quota 때문에 scale-up이 중단된 경우]] |

검색 문자열: `FailedScheduling`, `Insufficient cpu`, `Insufficient memory`, `Too many pods`, `scale-up`, `no expansion options`.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| 순수 공급 부족 Event, autoscaler 입력 없음 | Pod UID·request와 watch 범위 | autoscaler 입력 인식 | [[#읽기 전용 진단|읽기 전용 진단]] |
| 입력 인식, decision 없음 | current autoscaler container log와 group 후보 | template·policy owner | [[03. scale-from-zero node group template이 Pod 요구 조건과 맞지 않는 경우]] |
| max/quota/capacity 거부 | group·scope·provider evidence | 공급 한계 owner | [[02. node group 최대 크기·인프라 quota 때문에 scale-up이 중단된 경우]] |

## 읽기 전용 진단

`EVENT_READY=false; if [ "$WINDOW_READY" != true ] || ! fresh_all; then printf '%s\n' '중단: 최신 window/identity gate 실패' >&2; elif EVENTS_JSON="$(kubectl get events -n "$NS" --field-selector "involvedObject.kind=Pod,involvedObject.name=$POD,involvedObject.uid=$POD_UID,reason=FailedScheduling" -o json)"; then EVENT_ROWS="$(jq -r --argjson s "$START_EPOCH" --argjson e "$END_EPOCH" '.items[]|(.eventTime//.series.lastObservedTime//.lastTimestamp//.firstTimestamp) as $raw|($raw|strings|sub("\\.[0-9]+Z$";"Z")|fromdateiso8601?) as $t|select($t!=null and $t>=$s and $t<=$e)|[.metadata.uid,(.count//1),$raw,.message]|@tsv' <<<"$EVENTS_JSON")"; FILTER_RC=$?; if [ "$FILTER_RC" -eq 0 ] && [ -n "$EVENT_ROWS" ]; then EVENT_READY=true; printf '%s\n' "$EVENT_ROWS"; printf 'EVENT_READY=true window=%s..%s\n' "$START_RFC3339" "$END_RFC3339"; else printf '%s\n' '중단: window 안 FailedScheduling 없음; 빈 결과를 정상으로 해석 금지' >&2; fi; else printf '%s\n' '중단: Event producer 실패; filter 미실행' >&2; fi`

Event message에 placement·PVC 원인이 섞이면 순수 공급 부족으로 확정하지 않는다.

**autoscaler 로그 producer/filter 분리**

`LOG_READY=false; if [ "$EVENT_READY" != true ] || ! fresh_all; then printf '%s\n' '중단: 최신 event/identity gate 실패' >&2; elif RAW_LOG="$(kubectl logs "$AS_POD" -n "$AS_NS" -c "$AS_CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=500)"; then WINDOW_LOG="$(awk -v s="$START_RFC3339" -v e="$END_RFC3339" '$1>=s && $1<=e' <<<"$RAW_LOG")"; AWK_RC=$?; if [ "$AWK_RC" -ne 0 ]; then printf '중단: time filter rc=%s\n' "$AWK_RC" >&2; else MATCHED="$(grep -E -i -C 3 -- "$ARGV_RE" <<<"$WINDOW_LOG")"; GREP_RC=$?; if [ "$GREP_RC" -eq 0 ]; then LOG_READY=true; printf '%s\n' "$MATCHED"; printf 'LOG_READY=true pod_uid=%s autoscaler_uid=%s\n' "$POD_UID" "$AS_UID"; elif [ "$GREP_RC" -eq 1 ]; then printf '%s\n' '필터 결과 없음: watch 범위·schema·시간을 재확인; 고장으로 단정 금지' >&2; else printf '중단: grep filter rc=%s\n' "$GREP_RC" >&2; fi; fi; else PRODUCER_RC=$?; printf '중단: kubectl logs producer rc=%s\n' "$PRODUCER_RC" >&2; fi`

`kubectl logs` 권한은 대상 namespace의 `pods/log get`이며 Pod 조회 `pods get`, Event 조회 `events list`와 구분한다. 권한을 늘리지 말고 정확한 RBAC 주체·namespace·subresource를 audit 기록과 대조한다. Secret·token이 보이면 출력을 중단한다.

로그에 입력 인식은 있으나 max/quota/capacity면 02번으로, template mismatch면 03번으로 이동한다. decision/handoff가 있으면 "시작되지 않음"이 아니라 Node 등록/Ready 경로다. 로그가 없으면 autoscaler 고장으로 단정하지 않는다.

CRI·journal·Linux host 점검은 이 증상에 직접 필요하지 않다. 향후 runtime 경로로 내려갈 경우 active kubelet `ExecStart` 또는 엄격 검증된 kubelet config의 단일 CRI endpoint와 runtime socket provider 관계가 exact match되기 전 `crictl`을 실행하지 않는다.

## 상태 변경 경계

node pool min/max, autoscaler 설정, provider capacity, Pod request, HPA/KEDA, Pod 삭제를 이 문서에서 실행하지 않는다. fresh target/evidence, approval/window/quorum, 비용·tenant 영향, 변경 멱등성, 검증된 rollback이 모두 있어야 승인된 관리 경로로 이관한다.

`APPROVAL_ID='PASTE_SCALEUP_APPROVAL_ID_HERE'; CHANGE_READY=false; if [ "$LOG_READY" != true ] || ! fresh_all; then printf '%s\n' '중단: fresh log evidence가 아니다.' >&2; elif [ -z "$APPROVAL_ID" ]; then printf '%s\n' '중단: 승인 ID 필요' >&2; else CHANGE_READY=true; export APPROVAL_ID; printf 'CHANGE_READY=true pod=%s uid=%s autoscaler=%s approval=%s window=%s..%s\n' "$POD" "$POD_UID" "$AS_UID" "$APPROVAL_ID" "$START_RFC3339" "$END_RFC3339"; fi`

이 gate는 mutation을 실행하지 않는다. 실제 mutation·rollback은 실행 직전 fresh identity와 승인 범위를 다시 검사하는 외부 절차에서 수행한다. 새 FailedScheduling, 잘못된 group/zone, Ready 감소, 비용 한도·서비스 오류면 중단한다. 승인 ID는 변경 시도마다 고유해야 한다.

`CHANGE_RFC3339='PASTE_SCALEUP_CHANGE_UTC_HERE'; unset CHANGE_TIME_READY CHANGE_EPOCH CHANGE_GATE_APPROVAL REPLACEMENT_READY NORMAL_READY; CHANGE_TIME_READY=false; RFC3339_RE='^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$'; if [ "$CHANGE_READY" != true ] || ! fresh_all; then printf '%s\n' '중단: fresh change gate 실패' >&2; elif [[ ! "$CHANGE_RFC3339" =~ $RFC3339_RE ]] || ! CHANGE_EPOCH="$(date -u -d "$CHANGE_RFC3339" +%s 2>/dev/null)" || [ "$(date -u -d "@$CHANGE_EPOCH" '+%Y-%m-%dT%H:%M:%SZ')" != "$CHANGE_RFC3339" ] || [ "$CHANGE_EPOCH" -lt "$END_EPOCH" ] || [ "$CHANGE_EPOCH" -gt "$(date -u +%s)" ]; then printf '%s\n' '중단: 변경 시각 canonical/round-trip/evidence 이후 조건 실패' >&2; else CHANGE_GATE_APPROVAL="$APPROVAL_ID"; CHANGE_TIME_READY=true; export CHANGE_RFC3339 CHANGE_EPOCH CHANGE_GATE_APPROVAL; printf 'CHANGE_TIME_READY=true approval=%s change=%s\n' "$CHANGE_GATE_APPROVAL" "$CHANGE_RFC3339"; fi`

## 교체 후 재등록과 정상화

기존 Pending Pod가 그대로 bind됐다면 `NEW_POD`에 같은 이름을 넣고 current UID가 기존 `POD_UID`와 같은지 확인한다. controller가 실제 교체했다면 새 이름을 넣으며, 이때만 변경 시각 이후 creation과 새 UID를 요구한다. `NEW_NODE`는 capacity owner가 확인한 실제 Node 이름이다.

`NEW_POD='PASTE_SCALEUP_REPLACEMENT_POD_HERE'; NEW_NODE='PASTE_SCALEUP_REGISTERED_NODE_HERE'; unset REPLACEMENT_READY NORMAL_READY NEW_POD_UID NEW_NODE_UID NEW_CREATED; REPLACEMENT_READY=false; printf 'replacement 입력 등록 pod=%s node=%s; 최종 gate 전 READY 아님\n' "$NEW_POD" "$NEW_NODE"`

위 command는 이름만 입력하고 READY를 만들지 않는다. 다음 current owner·변경 시각 gate가 최종값을 다시 등록한다.

`REPLACEMENT_READY=false; if [ "$CHANGE_TIME_READY" != true ] || [ "$CHANGE_GATE_APPROVAL" != "$APPROVAL_ID" ]; then printf '%s\n' '중단: current change-time/approval gate 실패' >&2; elif CANDIDATES="$(kubectl get pods -n "$NS" -l "$OWNER_SELECTOR" -o json)" && OJSON="$(kubectl get "$OWNER_RESOURCE" "$OWNER_NAME" -n "$NS" -o json)" && NJSON="$(kubectl get node "$NEW_NODE" -o json)" && [ "$(jq --arg p "$NEW_POD" '[.items[]|select(.metadata.name==$p)]|length' <<<"$CANDIDATES")" -eq 1 ]; then NP="$(jq -c --arg p "$NEW_POD" '.items[]|select(.metadata.name==$p)' <<<"$CANDIDATES")"; NEW_POD_UID="$(jq -r '.metadata.uid' <<<"$NP")"; NEW_NODE_UID="$(jq -r '.metadata.uid' <<<"$NJSON")"; NEW_CREATED="$(jq -r '.metadata.creationTimestamp' <<<"$NP")"; POST_LIFECYCLE=''; if [ "$NEW_POD" = "$POD" ] && [ "$NEW_POD_UID" = "$POD_UID" ]; then POST_LIFECYCLE='same-pod'; elif [ "$NEW_POD_UID" != "$POD_UID" ] && [ "$(date -u -d "$NEW_CREATED" +%s)" -ge "$CHANGE_EPOCH" ]; then POST_LIFECYCLE='replacement'; fi; if [ "$(jq -r '.metadata.uid' <<<"$OJSON")" = "$OWNER_UID" ] && [ "$(jq -r '[.metadata.ownerReferences[]?|select(.controller==true)][0].uid//empty' <<<"$NP")" = "$OWNER_UID" ] && [ "$(jq -r '.spec.nodeName//empty' <<<"$NP")" = "$NEW_NODE" ] && [ -n "$POST_LIFECYCLE" ]; then REPLACEMENT_READY=true; export NEW_POD NEW_POD_UID NEW_NODE NEW_NODE_UID NEW_CREATED POST_LIFECYCLE; printf 'REPLACEMENT_READY=true lifecycle=%s pod=%s[%s] node=%s[%s] created=%s\n' "$POST_LIFECYCLE" "$NEW_POD" "$NEW_POD_UID" "$NEW_NODE" "$NEW_NODE_UID" "$NEW_CREATED"; else printf '%s\n' '중단: current owner/node/lifecycle/change-time relation 불일치' >&2; fi; else printf '%s\n' '중단: post-change Pod/current owner/Node producer 실패' >&2; fi`

`NORMAL_READY=false; if [ "$REPLACEMENT_READY" != true ] || ! NP="$(kubectl get pod "$NEW_POD" -n "$NS" -o json)" || ! NN="$(kubectl get node "$NEW_NODE" -o json)" || ! OO="$(kubectl get "$OWNER_RESOURCE" "$OWNER_NAME" -n "$NS" -o json)"; then printf '%s\n' '중단: 정상화 producer 실패' >&2; elif [ "$(jq -r '.metadata.uid' <<<"$NP")" != "$NEW_POD_UID" ] || [ "$(jq -r '.metadata.uid' <<<"$NN")" != "$NEW_NODE_UID" ] || [ "$(jq -r '.metadata.uid' <<<"$OO")" != "$OWNER_UID" ] || [ "$(jq -r '[.metadata.ownerReferences[]?|select(.controller==true)][0].uid//empty' <<<"$NP")" != "$OWNER_UID" ]; then printf '%s\n' '중단: replacement current identity 불일치' >&2; elif [ "$(jq -r '[.status.conditions[]?|select(.type=="Ready")][0].status//""' <<<"$NN")" = True ] && [ "$(jq -r '.status.phase' <<<"$NP")" = Running ] && jq -e '(.status.containerStatuses|length)>0 and all(.status.containerStatuses[];.ready==true and (.containerID//"")!="")' <<<"$NP" >/dev/null; then NORMAL_READY=true; printf 'NORMAL_READY=true pod=%s[%s] node=%s[%s] containerIDs=%s\n' "$NEW_POD" "$NEW_POD_UID" "$NEW_NODE" "$NEW_NODE_UID" "$(jq -r '[.status.containerStatuses[].containerID]|sort|join(",")' <<<"$NP")"; else printf '%s\n' '중단: Node Ready 또는 Pod/container Running/Ready 미수렴' >&2; fi`

정상화는 새 Node allocatable/taint/zone, 새 Pod의 owner·selector·Ready, 같은 오류 Event 중단, owner desired/Ready, 조건부 Service→EndpointSlice→새 Pod UID 관계와 실제 요청/Job 결과를 관찰 창 동안 확인한다. Node 수 증가나 Pod `Running`만으로 닫지 않는다.

## Prometheus 빠른 관측

`if [ "$EVENT_READY" != true ] || ! fresh_all; then printf '%s\n' '중단: 최신 event gate 실패' >&2; else printf 'kube_pod_status_scheduled{namespace="%s",pod="%s",condition="false"} == 1\n' "$NS" "$POD"; printf 'kube_pod_status_unschedulable{namespace="%s",pod="%s"} == 1\n' "$NS" "$POD"; fi`

완성 질의가 비면 metric 부재, label 불일치, scrape/cluster 범위 오류를 구분한다. 이 질의는 특정 node group, autoscaler decision, quota를 증명하지 않는다.

## 증거 보존과 환경별 미검증

host, UTC window, Pod/owner/autoscaler/Node UID·resourceVersion·containerID·관계·시각, request 계산, Event, producer/filter rc, 비식별 로그, 정확한 RBAC/audit 주체, 승인·rollback, replacement와 실제 기능을 보존한다. credential·token·개인키·전체 로그는 저장하지 않는다.

autoscaler 제품·watch 범위·log schema, provider capacity object, HPA/KEDA, 서비스 endpoint와 실제 Kubernetes 1.26 결과는 환경별 미검증이다. 실제 인프라 명령은 실행하지 않았다.
