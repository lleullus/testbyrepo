# capability 부족으로 operation not permitted가 발생한 경우

## 입력값과 빠른 수집

`EPERM`은 capability 부족 외에도 seccomp, LSM, read-only mount, namespace와 syscall argument 검증에서 반환된다. 이 문서는 `현재 Kubernetes container identity -> runtime이 확인한 host PID/start -> 해당 process capability set -> 같은 syscall·시각의 반대 증거`가 연결될 때만 capability 원인으로 판정한다.

| 종류 | 변수 | 출처 |
|---|---|---|
| 최초 입력 | `NS`, `POD`, `CONTAINER` | 운영자 |
| API 자동값 | Pod UID/resourceVersion, owner tuple, current container ID, Node UID/machineID | API |
| 계산 후보 | 없음 | syscall이나 필요 capability를 오류 문자열에서 추측하지 않음 |
| 운영자 선택 | 실제 operation, 확인된 syscall·필요 capability, 승인 host, runtime PID/start, UTC window, 조건부 host path | application·runtime·보안 owner evidence |

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 실제 operation·syscall에서 `EPERM`이 발생하고 target process를 고정할 수 있음 |
| 적용 | current container ID와 runtime PID/start, 오류 window가 연결됨 |
| 제외 | `SECCOMP` 직접 record는 [[05. seccomp가 syscall을 거부한 경우]], AVC/AppArmor record는 [[06. SELinux·AppArmor가 작업을 거부한 경우]] |

검색 문자열: `operation not permitted`, `EPERM`, `CapEff`, `CapPrm`, `CapBnd`, `CapAmb`, `Seccomp`, `AVC`, `apparmor="DENIED"`, `read-only filesystem`.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| operation/syscall 미확정 | bounded application log | code/runtime owner | [[#1. 오류 operation과 시각]] |
| `CapEff`에 필요 capability 없음 | permitted/bounding/ambient | capability 후보 확정 | [[#2. process capability set]] |
| capability는 있으나 EPERM | Seccomp/LSM/mount | 다른 보안 경계 | [[#3. 반대 증거 분리]] |
| PID/container가 바뀜 | current guard | 전체 재등록 | [[#2. process capability set]] |

## 1. 오류 operation과 시각

**API server가 반환한 effective securityContext**

`if ! fresh_identity; then printf '%s\n' '중단: current API gate 실패' >&2; elif P="$(kubectl get pod "$POD" -n "$NS" -o json)"; then jq -r --arg c "$CONTAINER" '{uid:.metadata.uid,resourceVersion:.metadata.resourceVersion,podSecurityContext:.spec.securityContext,container:([(.spec.containers[]?,.spec.initContainers[]?)|select(.name==$c)|{name,securityContext:.securityContext}][0])}' <<<"$P"; else printf '%s\n' 'producer_error: Pod 조회 실패' >&2; fi`

API 선언은 target process의 실제 capability set을 보장하지 않는다. `capabilities.add/drop`, `privileged`, `allowPrivilegeEscalation`, `runAsUser`, seccomp 선언만 제한해 비교한다.

`if [ "$SELECTION_READY" != true ] || ! fresh_identity; then printf '%s\n' '중단: current selection gate 실패' >&2; else F="$(mktemp)" || exit 1; B="${F}.bounded"; if kubectl logs "$POD" -n "$NS" -c "$CONTAINER" --timestamps --since-time="$START_RFC3339" --tail=300 >"$F"; then if awk -v end="$END_RFC3339" '$1 <= end' "$F" >"$B"; then if grep -E -i -C 3 'operation not permitted|permission denied|EPERM|seccomp|apparmor|selinux|read-only' "$B"; then printf '%s\n' 'filter_match=true'; else RC=$?; [ "$RC" -eq 1 ] && printf '%s\n' 'filter_match=false; bounded window의 오류 부재로 해석하지 않음' || printf 'symptom_filter_error rc=%s\n' "$RC" >&2; fi; else RC=$?; printf 'time_filter_error rc=%s\n' "$RC" >&2; fi; else RC=$?; printf 'producer_error rc=%s\n' "$RC" >&2; fi; rm -f "$F" "$B"; fi`

민감 payload·argument·token은 저장하지 않고 timestamp, operation, resource 유형, errno, 확인된 syscall만 보존한다.

## 2. process capability set

`if [ "$SELECTION_READY" != true ] || ! fresh_identity; then printf '%s\n' '중단: current selection gate 실패' >&2; elif ssh -o BatchMode=yes -- "$SSH_HOST" bash -c 'set -eu; mid=$1; pid=$2; start=$3; [ "$(cat /etc/machine-id)" = "$mid" ]; s=$(cat "/proc/$pid/stat"); r=${s##*) }; set -- $r; [ "${20}" = "$start" ]; grep -E "^(Name|Pid|NSpid|CapInh|CapPrm|CapEff|CapBnd|CapAmb|NoNewPrivs|Seccomp|Seccomp_filters):" "/proc/$pid/status"' bash "$HOST_MACHINE_ID" "$HOST_PID" "$PID_START_TICKS"; then EVIDENCE_READY=true; else RC=$?; printf 'capability producer/filter 실패 rc=%s\n' "$RC" >&2; fi`

`CapEff`는 현재 effective set, `CapPrm`은 permitted, `CapBnd`는 exec/file capability 획득 상한, `CapAmb`는 ambient set이다. 승인된 `capsh --decode`가 node에 이미 있으면 hex를 이름으로 해석할 수 있지만 도구 설치는 하지 않는다. syscall의 kernel manual·제품 요구사항에서 `REQUIRED_CAP`을 확인하고, 해당 bit가 `CapEff`에 없으며 같은 시각의 seccomp/LSM/filesystem 반대 증거가 없을 때만 capability 부족으로 확정한다.

## 3. 반대 증거 분리

**bounded kernel journal, producer와 filter 상태 분리**

`if [ "$SELECTION_READY" != true ] || ! fresh_identity; then printf '%s\n' '중단: current selection gate 실패' >&2; elif ssh -o BatchMode=yes -- "$SSH_HOST" bash -c 'set -eu; mid=$1; pid=$2; starttick=$3; since=$4; until=$5; [ "$(cat /etc/machine-id)" = "$mid" ]; s=$(cat "/proc/$pid/stat"); r=${s##*) }; set -- $r; [ "${20}" = "$starttick" ]; f=$(mktemp); trap '\''rm -f "$f"'\'' EXIT; if journalctl -k --since "$since" --until "$until" --no-pager >"$f"; then if grep -E -i -C 3 "seccomp|apparmor|avc|selinux|audit|denied|EPERM|read-only" "$f"; then exit 0; else rc=$?; [ "$rc" -eq 1 ] && { printf "%s\n" "filter_match=false"; exit 3; }; exit "$rc"; fi; else exit 2; fi' bash "$HOST_MACHINE_ID" "$HOST_PID" "$PID_START_TICKS" "$START_RFC3339" "$END_RFC3339"; then printf '%s\n' 'filter_match=true'; else RC=$?; [ "$RC" -eq 3 ] && printf '%s\n' 'filter_match=false; audit 미보존/미수집 가능' || printf 'journal producer/filter_error rc=%s\n' "$RC" >&2; fi`

`SECCOMP`+syscall/arch/code, `avc: denied`, `apparmor="DENIED"`, `EROFS`·read-only mount가 같은 PID·시각·operation에 맞으면 capability 원인에서 이관한다.

**조건부 filesystem 확인**

`if [ "$HOST_PATH" = - ]; then printf '%s\n' 'skip: path 없는 operation'; elif [ "$SELECTION_READY" != true ] || ! fresh_identity; then printf '%s\n' '중단: current selection gate 실패' >&2; else ssh -o BatchMode=yes -- "$SSH_HOST" bash -c 'set -eu; mid=$1; pid=$2; start=$3; path=$4; [ "$(cat /etc/machine-id)" = "$mid" ]; s=$(cat "/proc/$pid/stat"); r=${s##*) }; set -- $r; [ "${20}" = "$start" ]; stat -Lc "owner=%u:%g mode=%a type=%F" -- "$path"; findmnt -rn -T "$path" -o TARGET,SOURCE,FSTYPE,OPTIONS' bash "$HOST_MACHINE_ID" "$HOST_PID" "$PID_START_TICKS" "$HOST_PATH"; fi`

## 변경 경계와 정상화

이 문서는 capability 추가, `privileged`, `allowPrivilegeEscalation`, `setcap`, `chmod/chown`, seccomp·LSM 완화, runtime restart를 실행하지 않는다. 별도 mutation은 current controller UID/revision/selector/image digest, 승인 artifact·새 값·approval ID·변경 시간·availability, 최소 권한과 rollback revision을 mutation 명령 자체에서 재검증해야 한다. 이 gate를 생략한 예시 명령은 제공하지 않는다.

replacement가 생기면 기존 Pod 이름/UID를 재사용하지 않는다. owner selector, owner UID, creation time과 단일 후보 관계로 새 Pod를 다시 선택하고 모든 READY를 재등록한다. 정상화는 새 process capability set만이 아니라 동일 syscall·operation 성공, seccomp/LSM/filesystem 거부 부재, Ready와 실제 기능, 관찰 창의 재발 부재까지 확인한다.
