# user namespace의 UID·GID mapping이 예상과 다른 경우

## 입력값과 빠른 수집

실행 경로는 `작업 PC/Bastion -> Kubernetes API`와 `작업 PC/Bastion -> 승인된 target node -> runtime이 확인한 host PID -> /proc/PID/{uid_map,gid_map}`다. Kubernetes 1.26의 `hostUsers`는 `UserNamespacesSupport` feature gate가 필요한 alpha 기능이다. API schema에 필드가 있거나 runtime 버전이 알려졌다는 사실만으로 gate 활성화나 실제 mapping을 확정하지 않는다.

| 종류 | 변수 | 출처 |
|---|---|---|
| 최초 입력 | `NS`, `POD`, `CONTAINER` | 운영자 |
| API 자동값 | Pod UID/resourceVersion, owner kind/name/UID, current container ID, Node UID/machineID | API |
| 계산 후보 | 없음 | UID/GID range를 추측하지 않음 |
| 운영자 선택 | 승인 SSH host, host machine-id, runtime 확인 PID/start tick, 확인된 host path, UTC window | runtime·filesystem evidence |

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | container identity와 host owner가 예상 mapping으로 연결되지 않거나 `uid_map`·`gid_map`이 예상 범위와 다름 |
| 적용 | current container ID와 runtime PID/start/user namespace inode가 같은 시각에 연결됨 |
| 제외 | capability EPERM은 [[04. capability 부족으로 operation not permitted가 발생한 경우]], LSM 거부는 [[06. SELinux·AppArmor가 작업을 거부한 경우]] |

검색 문자열: `uid_map`, `gid_map`, `setgroups`, `user namespace`, `hostUsers`, `permission denied`, `operation not permitted`.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 그다음 어디를 볼지 | 상세 절 |
|---|---|---|---|
| API 선언이 기대와 다름 | effective securityContext·hostUsers | admission/workload owner | [[#1. 선언과 mapping 분리]] |
| map range가 예상과 다름 | namespace inode와 세 열 | runtime/userns owner | [[#2. 현재 PID mapping 수집]] |
| map은 맞고 파일 접근 실패 | host numeric owner·mount | ACL/LSM/filesystem | [[#3. 같은 경로 ownership 대조]] |
| PID 또는 inode가 바뀜 | fresh identity·PID start | lifecycle 재등록 | [[#2. 현재 PID mapping 수집]] |

## 1. 선언과 mapping 분리

`if ! fresh_identity; then printf '%s\n' '중단: current API gate 실패' >&2; elif P="$(kubectl get pod "$POD" -n "$NS" -o json)"; then jq -r --arg c "$CONTAINER" '{uid:.metadata.uid,resourceVersion:.metadata.resourceVersion,hostUsers:.spec.hostUsers,podSecurityContext:.spec.securityContext,containerSecurityContext:([(.spec.containers[]?,.spec.initContainers[]?)|select(.name==$c)|.securityContext][0])}' <<<"$P"; else printf '%s\n' 'producer_error: Pod 조회 실패' >&2; fi`

`runAsUser`, `runAsGroup`, `fsGroup`은 container 내부 identity 선언이지 host numeric ID의 직접 증거가 아니다. `hostUsers`가 사용된 경우 API server feature gate, kubelet/runtime 지원과 실제 map을 별도로 확인한다.

## 2. 현재 PID mapping 수집

`if [ "$SELECTION_READY" != true ] || ! fresh_identity; then printf '%s\n' '중단: current selection gate 실패' >&2; elif ssh -o BatchMode=yes -- "$SSH_HOST" bash -c 'set -eu; mid=$1; pid=$2; start=$3; inode=$4; [ "$(cat /etc/machine-id)" = "$mid" ]; s=$(cat "/proc/$pid/stat"); r=${s##*) }; set -- $r; [ "${20}" = "$start" ]; [ "$(stat -Lc %i "/proc/$pid/ns/user")" = "$inode" ]; printf "userns="; readlink "/proc/$pid/ns/user"; printf "%s\n" "uid_map:"; cat "/proc/$pid/uid_map"; printf "%s\n" "gid_map:"; cat "/proc/$pid/gid_map"; printf "setgroups="; cat "/proc/$pid/setgroups"' bash "$HOST_MACHINE_ID" "$HOST_PID" "$PID_START_TICKS" "$USER_NS_INODE"; then EVIDENCE_READY=true; else RC=$?; printf 'mapping producer_error rc=%s\n' "$RC" >&2; fi`

map은 `inside-ID outside-ID length` 세 열이다. range overlap·길이·경계를 계산해 실제 container UID/GID가 어느 host ID에 대응하는지 확인한다. `0 100000 65536`은 모든 process가 UID 100000이라는 뜻이 아니다. `setgroups=deny`는 supplementary group 동작을 별도로 제한한다.

## 3. 같은 경로 ownership 대조

`if [ "$SELECTION_READY" != true ] || ! fresh_identity; then printf '%s\n' '중단: current selection gate 실패' >&2; elif ssh -o BatchMode=yes -- "$SSH_HOST" bash -c 'set -eu; mid=$1; pid=$2; start=$3; inode=$4; path=$5; [ "$(cat /etc/machine-id)" = "$mid" ]; s=$(cat "/proc/$pid/stat"); r=${s##*) }; set -- $r; [ "${20}" = "$start" ]; [ "$(stat -Lc %i "/proc/$pid/ns/user")" = "$inode" ]; stat -Lc "owner=%u:%g mode=%a inode=%i type=%F" -- "$path"; findmnt -rn -T "$path" -o TARGET,SOURCE,FSTYPE,OPTIONS' bash "$HOST_MACHINE_ID" "$HOST_PID" "$PID_START_TICKS" "$USER_NS_INODE" "$CONFIRMED_HOST_PATH"; then EVIDENCE_READY=true; else RC=$?; printf 'ownership producer_error rc=%s\n' "$RC" >&2; fi`

host path는 확인된 mount source만 사용한다. owner가 mapping과 맞아도 mode, ACL, read-only mount, SELinux/AppArmor가 남아 있다. 민감 path 원문은 증거에 저장하지 않고 path 유형과 numeric owner만 redaction해 남긴다.

## 원인 확정·변경 경계·정상화

원인 확정에는 current Pod/container tuple, PID/start/userns inode, map 세 열, 실제 inside identity, 같은 host path의 numeric owner/mount가 한 window에 연결돼야 한다. PID나 inode가 바뀌면 과거 READY와 evidence를 폐기한다.

이 문서는 `uid_map`, `gid_map`, `setgroups`, `chown`, `chmod`, `setcap`, runtime 설정, Pod securityContext를 변경하지 않는다. 별도 변경은 승인 ID, exact owner revision/UID, 현재 image digest와 selector, 영향 volume·다른 workload, 원본 artifact, rollback owner를 fresh하게 검증한 절차에서만 수행한다.

정상화는 다음을 모두 만족해야 한다.

1. replacement가 있으면 controller selector·owner UID·creation time으로 단일 새 Pod를 다시 선택하고 전체 자동값을 재등록한다.
2. 현재 container ID와 PID/start/userns inode/map이 승인 상태와 일치한다.
3. 동일 host path owner/mount와 container 내부 identity 대응이 맞는다.
4. 최초 파일/group 동작과 실제 제품 기능이 성공한다.
5. UTC 관찰 창 동안 같은 EPERM, restart, Warning이 재발하지 않는다.

`Running`, 새 PID 또는 map 출력 성공만으로 정상화하지 않는다. `/proc/PID/environ`, cmdline, 전체 runtime inspect, token·Secret은 수집하지 않는다.
