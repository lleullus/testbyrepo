# container cgroup에 OOM event가 증가한 경우

## 입력값과 빠른 수집

| 구분 | 값 | 출처와 gate |
|---|---|---|
| 최초 입력 | `APPROVED_HOST`, `START_RFC3339`, `END_RFC3339` | 승인 SSH host와 사건 창 |
| 시스템 자동값 | machine/boot/kernel, cgroup fs, host namespace inode | 원격 host에서 fresh 등록 |
| 계산 후보값 | epoch, `OOM_RE` | UTC roundtrip·bounded 출력 뒤 사용 |
| 운영자 선택값 | `CONTAINER_ID` | runtime 후보에서 exact full ID를 선택한다. CRI endpoint와 cgroup path는 active kubelet·runtime·PID에서 자동 확정한다. |

경로는 `operator Bash -> SSH -> host PID/mount namespace -> active runtime 또는 kernel task_memcg -> exact container cgroup`이다. `/sys/fs/cgroup` 관행 경로를 조합하지 않는다. kubelet 관리 container라면 활성 kubelet의 effective argv/config에서 endpoint를 확인하고, endpoint의 `crictl version`이 반환한 exact runtime provider를 기록한다. 기본 socket 추측은 금지한다.

## 진입 판단

| 구분 | 판단 기준 |
|---|---|
| 사용 | 정확한 container cgroup에서 v2 OOM counter delta 또는 v1 limit failure와 kernel 문맥을 대조할 때 |
| 적용 | cgroup version/path/container lifecycle와 사건 창이 연결됨 |
| 제외 | `CONSTRAINT_NONE` global OOM은 [[02. kernel system OOM에 Killed process가 기록된 경우]]로 이동 |

검색 문자열: `memory.events.local`, `oom_kill`, `memory.failcnt`, `CONSTRAINT_MEMCG`, `task_memcg`, `memory.max`.

## 관측별 진단 경로

| 지금 보이는 것 | 먼저 볼 것 | 다음 판단 | 상세 절 |
|---|---|---|---|
| v2 `oom_kill` delta | local vs hierarchical, path lifecycle | memcg kill 후보 | [[#2. exact cgroup sample]] |
| v2 `oom`만 delta | `max`, `high`, kernel victim | OOM 진입과 kill 분리 | [[#2. exact cgroup sample]] |

| path가 사라짐 | container PID/start·runtime state | replacement 또는 evidence gap | [[#1. runtime과 target identity]] |

## 1. runtime과 target identity

이 절의 CRI 경로는 active kubelet이 관리하는 container에만 적용한다. kubelet이 없으면 socket을 추측하지 않고 kernel journal의 exact `task_memcg`와 해당 runtime owner 절차로 이관한다. endpoint는 active process argv의 단일 값, 또는 argv의 단일 `--config`가 가리키는 절대경로 regular readable file의 단일 nonempty `containerRuntimeEndpoint` key에서만 자동 등록한다.

## 2. exact cgroup sample

```bash

v2 `memory.events.local`은 target 자체, `memory.events`는 descendant 포함 가능성이 있다. `oom_kill`은 누적 kill, `oom`은 OOM 경로 진입, `max`·`high`는 각 limit event다. v1 `failcnt`는 kill 횟수가 아니다. 동일 lifecycle에서 두 sample delta가 있어야 증가를 말할 수 있다.

bounded kernel journal은 current target relation과 입력 창을 직접 gate하고 producer와 filter를 분리한다.

tmp=$(mktemp); trap 'rm -f "$tmp"' EXIT
journalctl -k --since "${13}" --until "${14}" --utc --no-pager >"$tmp"
if grep -E -i -C 5 "${15}" "$tmp"; then printf '%s\n' 'FILTER_MATCH=found'; else grc=$?; [ "$grc" -eq 1 ] || exit "$grc"; printf '%s\n' 'FILTER_MATCH=none; producer 성공, memcg OOM 문자열 없음'; tail -n 50 "$tmp"; fi
REMOTE
rc=$?; if [ "$rc" -eq 0 ]; then JOURNAL_READY=true; printf '%s\n' 'JOURNAL_READY=true'; else JOURNAL_READY=false; printf '중단: journal producer/filter 실패 rc=%s\n' "$rc" >&2; fi; fi
```

`CONSTRAINT_MEMCG`·exact `task_memcg`·victim timestamp가 sample interval에 포함될 때만 memcg OOM을 확인한다. no-match와 journal 실패는 성공이 아니다.

## 변경 분리·정상화·증거

이 문서는 cgroup 쓰기, counter reset, limit 변경, kill/restart를 하지 않는다. 별도 변경마다 fresh host/container/cgroup lifecycle, direct evidence, 승인 ID, UTC window, quorum·대체 capacity, idempotence, 중단·rollback을 독립 확인한다.

replacement면 새 container ID·created/startedAt·PID start·namespace·cgroup path·CRI provider를 완전히 등록하고 old->new 관계를 남긴다. 새 path의 0 counter는 과거 문제 해소 증거가 아니다. bounded 창에서 같은 lifecycle의 event delta가 멈추고 kernel memcg OOM이 재발하지 않으며 실제 서비스 read/write·request·Job 결과가 회복되어야 한다.

보존: machine/boot/kernel/namespaces, cgroup fs, active kubelet PID/start와 endpoint 출처, exact runtime provider, container ID/lifecycle/PID start/cgroup path, sample 시각·raw bounded counters, journal 관계, 승인·rollback·기능 결과. 민감한 raw inspect와 전체 journal은 저장하지 않는다. 환경별 runtime JSON·cgroup layout은 미검증이며 infrastructure 명령은 작성 중 실행하지 않았다.
