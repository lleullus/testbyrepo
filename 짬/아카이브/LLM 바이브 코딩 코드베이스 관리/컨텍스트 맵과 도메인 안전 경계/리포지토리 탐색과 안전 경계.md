10만 줄 이상 코드베이스에서 LLM에게 중요한 것은 기능을 잘 짜는 능력보다, **어디를 읽고 어디를 건드리고 어디를 건드리면 안 되는지**를 아는 것이다.

```text

├── 목적
├── 핵심 원칙
```

## 목적

이 문서는 LLM이 변경 요청을 받았을 때 다음을 판단하게 한다.

- 어떤 컨텍스트를 읽어야 하는가
- 어떤 모듈을 수정할 수 있는가
- 어떤 모듈은 건드리면 안 되는가
- 어떤 도메인 규칙을 반드시 확인해야 하는가
- 어떤 변경은 고위험 변경으로 승격해야 하는가

## 핵심 원칙

- 어디든 import 가능한 코드베이스는 LLM에게 위험하다.
- module boundary는 폴더 설명이 아니라 의미적 소유권 지도다.
- context map은 LLM용 retrieval routing 문서다.
- 모든 도메인 경계 규칙은 가능한 한 lint, test, contract, typecheck로 검증되어야 한다.
- 실행 가능한 결과가 없는 DDD 산출물은 만들지 않는다.
- Obsidian 위키는 코드베이스의 진실의 원천이 아니라, 코드·테스트·스키마·빌드 설정을 LLM이 활용하기 쉬운 의미 계층으로 편집한 것이다.
- context map은 구조 문서이면서 동시에 LLM 작업을 위한 retrieval routing 문서이고, 기능별 context index는 그 라우팅의 실행 단위다.

## 별도 제공 체크리스트 반영

체크리스트 원문(a-1~e-4)과 역할 매핑은 [[01. 기준과 0순위 체크리스트]]가 canonical source다. 이 문서의 역할은 해당 체크리스트 항목들의 **boundary owner와 의미 경계**를 정의하는 것이다.

### boundary 의미 요약

- a-1: 구현보다 먼저 touched context, touched modules, allowed dependencies, forbidden dependencies를 정한다.
- a-3: 공용 helper/type/shape는 canonical owner를 먼저 정하고 SSOT 충돌을 확인한다.
- a-4: 디렉터리는 의존 방향을 보이게 하는 장치다.
- b-1: 에러는 boundary/handler에서만 의미 있게 처리하고 호출부에서 삼키지 않는다.
- b-4: side effect와 write path를 먼저 확인하고 mutation boundary를 테스트와 함께 고정한다.
- b-5: 새 function/helper/shape 생성 전 기존 owner와 SSOT를 먼저 찾는다.
- c-2~c-5: swallowed error, hidden coupling, public surface, fan-in/fan-out의 의미 판단은 이 문서가 owner다.
- d-1~d-2: 암묵 계약, 순환 의존성, 경계 위반은 의미 경계 차원에서 해석한다.
- e-2~e-4: mock boundary, edge case ownership, defensive code boundary를 정의한다.

구조적 evidence는 [[02. 하네스와 구조적 Evidence 계층]], finding 처리 프로토콜은 [[04. 도입과 운영 프로토콜]]을 참조한다.

## 위키 컨텍스트 인덱스 전략

컨텍스트 맵은 LLM에게 전체 코드베이스를 설명하기 위한 문서가 아니라, 변경 요청마다 필요한 구조 정보를 선택하기 위한 retrieval routing 문서다.

자세한 운영 전략은 [[옵시디언 위키 컨텍스트 인덱스 전략|옵시디언 위키 컨텍스트 인덱스 전략]]을 따른다.

핵심 원칙은 다음과 같다.

- LLM에게 전체 코드베이스 기억을 기대하지 않는다.
- Obsidian 위키는 설계 의도, 도메인 의미, 금지사항, 예외 정책을 압축한 의미 계층이다.
- 코드, 테스트, 스키마, 빌드 설정, 배포 설정이 최종 진실의 원천이다.
- 기능 구현 전에는 관련 context map, module boundary, invariant, 테스트, 금지 영역을 기능별 context index로 묶는다.
- 작업 후에는 사용한 링크가 충분했는지, 누락된 컨텍스트가 있었는지, 새로 발견한 구조 지식이 문서화됐는지 감사한다.

## 컨텍스트 맵

각 컨텍스트마다 다음을 정의한다.

- owns
- does not own
- reads from
- writes to
- allowed dependencies
- forbidden dependencies
- relevant docs
- wiki index links
- behavioral rules
- related ADRs
- relevant tests
- high-risk changes
- last verified source
- drift risk

예:

```md
## Billing Context

Owns:
- invoice lifecycle
- payment status
- refund policy

Does not own:
- user authentication
- product catalog pricing source

Allowed dependencies:
- user read model
- payment gateway adapter

Forbidden:
- direct mutation of order state
- direct access to auth session internals

Required checks:
- pnpm test billing
- pnpm contract billing
- pnpm test invariants
```

## 모듈 경계

각 레이어의 허용/금지 책임을 정의한다.

```text
domain
- 순수 비즈니스 로직
- value object
- policy
- validation

application
- use case orchestration
- transaction boundary
- repository interface 호출

infrastructure
- ORM, API client, queue, file system

ui / interface
- request/response, forms, controllers, views
```

## 도메인 언어

공통 언어를 단순 용어집이 아니라 LLM용 의미 타입 시스템으로 정의한다.

각 용어는 다음을 포함한다.

- canonical name
- forbidden aliases
- confused terms
- valid states
- invalid transitions
- owning context
- related invariant tests

## 불변식

각 도메인 규칙은 다음을 명시한다.

- invariant
- owning context
- allowed mutation path
- forbidden mutation path
- enforcing test
- related contract
- failure meaning

## 고위험 변경

다음 변경은 자동으로 고위험 변경으로 본다.

- aggregate boundary 변경
- 도메인 상태 전이 변경
- 결제 / 환불 / 정산 / 권한 / 재고 규칙 변경
- 이벤트 의미 변경
- repository contract 변경
- context dependency direction 변경
- 금지 import 예외 추가
- 핵심 테이블 migration
- domain invariant test 수정 또는 삭제

## 작업 라우팅

LLM은 변경 전에 다음을 선언해야 한다.

- touched context
- touched modules
- selected wiki index
- related behavior rules
- owned invariant
- affected contracts
- required checks
- forbidden areas
- missing context risk
- wiki update required 여부
- escalation 여부

## DDD-lite 적용 기준

이 repo는 full DDD를 목표로 하지 않는다.

사용한다:

- ubiquitous language
- bounded context
- context map
- invariant ownership
- domain event 의미 정의, 필요한 경우만
- aggregate boundary, 필요한 경우만

남발하지 않는다:

- 전역 aggregate catalog
- 모든 모델의 entity/value object화
- repository pattern 일괄 적용
- domain service 남발
- 패턴 중심 폴더 구조
