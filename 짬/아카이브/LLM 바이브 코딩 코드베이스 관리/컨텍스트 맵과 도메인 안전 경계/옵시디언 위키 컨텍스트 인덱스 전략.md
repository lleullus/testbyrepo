> [!summary] 요약
> 10만 줄 이상 코드베이스에서 LLM에게 컨텍스트 기억을 기대하지 않고, 옵시디언 위키로 프로젝트 구조를 전량 문서화한 후 특정 기능 구현 시 필요한 구조적 정보만 인덱스로 연결하여 스킬 기반 기능 부착을 수행하는 전략이다.

## 배경

LLM은 긴 세션에서도 전체 코드베이스의 의미망을 안정적으로 유지하지 못한다. 10만 줄 이상에서는 프롬프트에 컨텍스트를 주입하는 방식이 한계에 도달한다.

## 전략

LLM이 컨텍스트를 기억해주길 기대하는 것을 포기한다. 대신:

1. 프로젝트의 전체 구조를 옵시디언 위키로 싹 정리한다.
2. 특정 기능을 붙일 때, 그 기능에 필요한 구조적 정보만 위키 인덱스로 연결한다.
3. 연결된 인덱스를 기반으로 스킬을 호출하여 기능을 부착한다.

## 결과

- 코드가 10만 줄 이상이지만 과설계나 오버엔지니어링이 발생하지 않고 있다.
- 각 기능은 필요한 컨텍스트만 가져오므로, LLM의 작업 범위가 명확하고 제한적이다.
- 프로젝트 구조는 위키에 영구적으로 저장되어 세션 종료 후에도 유지된다.

## Oracle Browser 인사이트

> [!insight] 핵심 평가
> 이 전략은 단순한 노트 정리법이 아니라, **LLM 시대의 소프트웨어 작업기억 아키텍처**에 가깝다. 잘 되는 이유는 LLM의 기억 한계를 부정하지 않고, 외부화·압축·인덱싱·스코프 제한으로 바꾸기 때문이다.

### 왜 작동하는가

**컨텍스트를 기억 문제가 아니라 인덱싱 문제로 재정의**한다. 사람의 작업기억도 제한적이고, LLM의 attention 메커니즘도 프로젝트 전체의 원인-결과, 레이어 규칙, 예외 정책, 과거 설계 결정을 장기적으로 보존하지 못한다. Obsidian 인덱스는 LLM에게 "많은 코드"가 아니라 "작업에 필요한 의미 압축본"을 제공한다.

핵심은 **컨텍스트 압축과 작업 범위 제한**이다. 10만 줄 전체를 넣는 대신, 기능 구현에 필요한 모듈, 데이터 흐름, 호출 경계, 기존 패턴, 금지사항만 링크한다. LLM을 "전지적 설계자"가 아니라 "제한된 작업공간을 가진 실행자"로 다룬다.

LLM을 설계자가 아니라 **"스킬 실행자"로 낮추는 것**이 또 하나의 강점이다. Obsidian 위키는 설계 지식의 저장소이고, 스킬은 반복 가능한 작업 절차이다. 이 조합은 과설계를 줄인다. LLM이 모르는 부분을 메우려고 새 추상화, 새 레이어, 새 헬퍼를 만들 가능성이 줄어들기 때문이다.

### 위험과 실패 모드

1. **위키-코드 드리프트** — 코드는 바뀌고 위키는 늦게 갱신되면, LLM은 "정돈된 거짓말"을 본다. 산만한 코드보다 더 위험한 것은 오래되었지만 그럴듯하게 정리된 문서이다.
2. **컨텍스트 누락** — "필요한 구조 정보만 링크한다"는 판단 자체가 병목이 된다. UI 기능처럼 보여도 권한, 캐시, 이벤트 소싱, 결제 상태, 마이그레이션, 관측성, 배포 플래그가 얽혀 있을 수 있다. 사람이 잘못된 인덱스를 주면 LLM은 매우 자신 있게 국소 최적해를 낸다.
3. **구조 문서가 행동 의미를 대체하지 못함** — 폴더 구조, 모듈 책임, 호출 관계는 알려줄 수 있지만, "이 값은 언제 null이 되는가", "이 API는 왜 idempotent해야 하는가", "이 큐는 순서를 보장하지 않는다" 같은 행동적 지식은 구조 인덱스에 담기기 어렵다.
4. **위키가 새로운 과설계의 장소가 됨** — 코드에 추상화를 만들지 않는 대신, Obsidian에 너무 많은 카테고리, 규칙, 템플릿, 링크, 레이어 정의를 만들 수 있다. 과설계가 코드에서 문서 시스템으로 이동한다.
5. **LLM이 위키를 권위로 오인** — "현재 사실"인지 "과거 설계 의도"인지 "할 일"인지 "실험 메모"인지 구분되지 않으면, 초안·폐기안·아이디어를 현재 규칙처럼 적용할 수 있다.
6. **AI 생성 코드의 장기 유지보수 품질** — "기능이 붙는다"와 "장기적으로 진화 가능한 구조가 유지된다"는 다르다. 2026년 연구에 따르면 AI IDE가 기능적으로는 높은 점수를 내도, 생성 프로젝트에 코드 중복, 높은 복잡도, 큰 메서드, 프레임워크 베스트프랙티스 위반, 예외 처리 문제 등이 많이 발견된다.

### 기존 전략과의 비교

| 전략 | 강점 | 이 전략과의 관계 |
|------|------|------------------|
| AGENTS.md | "항상 적용되는 작업 규칙" | 보완재. AGENTS.md는 전역 규칙, 위키 인덱스는 기능별 구조 선택 |
| Aider repo map | 코드에서 자동 추출, 최신성 | 의미와 의도, 암묵지는 담기 어려움. 위키는 그 반대 |
| Context map | bounded context, 도메인 경계 | 이 전략은 수동 context map + 실행 프로토콜 |
| Repomix | 전체 저장소 패킹, 리뷰용 강함 | 기능 단위 반복 작업에서는 노이즈. 이 전략은 "필요한 구조만 꺼내기" |
| RepoAgent | 자동 문서 생성·갱신 | 가장 강한 조합: "자동 생성 구조 문서 + 인간 검증 설계 의도 + 기능별 인덱스" |
| Repository Intelligence Graph | 결정론적 아키텍처 맵, 스케일 친화적 | 200k~500k 라인으로 커질 때 반드시 흡수해야 할 방향 |

### 200k, 500k 라인, 멀티레포에서 무엇이 깨지는가

- **200k 라인**: 수동 위키의 최신성이 먼저 깨짐. 파일 이동, 모듈 분리, API deprecation, 테스트 위치 변경, 환경 변수 변경이 코드리뷰에서는 보이지만 위키에는 늦게 반영됨.
- **500k 라인**: 분류 체계가 깨질 가능성 큼. 같은 개념이 여러 이름으로 생기고, 한 문서가 너무 많은 링크의 허브가 되고, "어떤 인덱스를 붙여야 하는지"를 찾는 데 또 다른 LLM 세션이 필요해짐. 이 시점부터 위키는 단순 문서가 아니라 **검색 시스템, 그래프 시스템, 검증 시스템**이 되어야 함.
- **멀티레포**: 경계 정보가 깨짐. API 계약, 이벤트 스키마, 버전 호환성, 배포 순서, feature flag, 데이터 마이그레이션, 소유 팀이 더 중요해짐.
- **스킬 간 충돌**: 스킬이 많아질수록 필요한 것은 개별 스킬 설명이 아니라 **스킬 오케스트레이션 규칙**.
- **은닉된 전역 불변식**: 500k 라인과 멀티레포에서는 "이 enum 값은 외부 파트너와 계약되어 있다", "이 컬럼은 삭제하면 과거 정산이 깨진다" 같은 지식이 흩어짐. 단순 구조 인덱스가 아니라 **불변식 인덱스**가 필요.

### 강화 방안

1. **문서 3분리**: 구조 문서(모듈·파일·책임·의존성), 행동 문서(런타임 규칙·예외·상태 전이·데이터 생명주기), 결정 문서(ADR, "왜 이렇게 했는가")로 분리. 장기적으로 행동 문서와 결정 문서가 없을 때 LLM이 위험한 변경을 함.
2. **기계 판독 가능 frontmatter**: `status`, `source_files`, `owners`, `last_verified_commit`, `related_tests`, `invariants`, `deprecated_by`, `safe_to_use_for_llm` 등. 핵심은 사람이 읽기 좋은 문서가 아니라, **LLM 세션 시작 시 안전하게 필터링 가능한 문서**.
3. **기능 추가용 인덱스 템플릿 표준화**: "목표", "수정 가능 파일", "수정 금지 파일", "관련 구조 링크", "관련 행동 규칙", "관련 테스트", "필수 불변식", "예상 사이드이펙트", "작업 후 검증 명령".
4. **위키-코드 양방향 링크 강제**: 코드에도 주석 또는 메타 파일 형태로 "이 모듈의 설계 문서"를 가리키는 역링크. 코드리뷰에서 "코드는 바뀌었는데 문서는 안 바뀜"을 감지 가능.
5. **자동 repo map + 수동 위키 결합**: import graph, symbol graph, route map, DB schema map, API schema, test coverage map, package dependency graph는 자동 생성. Obsidian은 그 위에 의미·의도·금지사항을 얹는 구조.
6. **컨텍스트 누락 체크리스트**: 데이터 모델 변경?, 권한 변경?, 외부 API 계약 변경?, 캐시 무효화?, 마이그레이션?, 테스트 fixture 변경?, 로그·메트릭·알림?, rollback 경로?
7. **스킬 계약화**: 각 스킬에 입력 문서, 허용 작업, 금지 작업, 생성 산출물, 검증 명령, 실패 시 중단 조건 명시.
8. **컨텍스트 감사 단계**: LLM 작업 후 사용한 위키 링크가 충분했는지, 누락된 링크가 있었는지, 새로 발견한 구조 지식이 문서화됐는지 확인. 이 루프가 있어야 위키가 점점 좋아짐.
9. **Obsidian을 "진실의 원천"으로 두지 않음**: 진실의 원천은 코드, 테스트, 스키마, 빌드 설정, 배포 설정. Obsidian은 그 진실을 사람이 이해하고 LLM이 활용하기 쉬운 형태로 편집한 **의미 계층**. 위키는 authoritative explanation일 수는 있지만, authoritative fact는 가능하면 자동 추출물.
10. **최종 형태 조합**:
    - `AGENTS.md`: 전역 작업 규칙
    - 자동 repo map: 최신 코드 구조
    - Obsidian 위키: 설계 의도와 도메인 의미
    - 기능별 context index: 이번 작업의 범위
    - 스킬: 반복 가능한 변경 절차
    - 테스트·정적분석·리뷰 체크리스트: 결과 검증
