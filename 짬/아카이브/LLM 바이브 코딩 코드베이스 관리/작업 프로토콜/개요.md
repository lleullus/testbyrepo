> [!note] 문서 경계
> 01이 "구조 정보를 어떻게 조직하는지(what)"를 정의한다면, 이 문서는 "그 정보를 어떻게 작업 흐름에 끼워 넣는지(how)"를 다룬다. 03은 "검증 시스템을 어떻게 연결하고 운영하는지(how to verify)"를 다룬다.

바이브 코딩은 속도가 장점인데, 10만 줄 이상에서는 속도만 믿으면 망가진다.

## 필수 루프

```text
Research → Plan → Small diff → Run checks → Review → Merge
```

## Research 단계의 컨텍스트 선택

작업을 시작하기 전에 먼저 [[리포지토리 탐색과 안전 경계|리포지토리 탐색과 안전 경계]]에서 touched context, touched modules, forbidden areas, required checks를 확인한다.

대형 코드베이스에서 필요한 구조 정보만 선별해야 하는 경우 [[옵시디언 위키 컨텍스트 인덱스 전략|옵시디언 위키 컨텍스트 인덱스 전략]]에 따라 기능별 context index를 구성한다.

요구가 크거나 모호해서 바로 `Plan`으로 넘기기 어렵다면 [[Obsidian MCP 경량 라이프사이클 엔진 - 초안|Obsidian MCP 경량 라이프사이클 엔진 - 초안]]을 먼저 사용한다. 이 노트는 Obsidian project note/context를 검토 가능한 최소 slice와 구현 handoff seed로 줄이는 임시 골격이다.

## LLM에게 지시하는 방식

```text
1. 먼저 관련 파일과 기존 패턴만 조사해.
2. 아직 코드는 수정하지 마.
3. 변경 계획을 5단계 이하로 제안해.
4. 위험한 부분과 필요한 테스트를 먼저 말해.
5. 내가 승인한 범위 안에서만 수정해.
6. 수정 후 관련 테스트를 실행하고 결과를 요약해.
```

이건 답답해 보이지만, 10만 줄 이상에서는 오히려 빠르다. "한 번에 크게 시키기"는 초반엔 빨라 보여도 나중에 diff 해석과 버그 추적 비용이 폭발한다.
