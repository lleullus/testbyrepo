## Part A. Harness Runtime

LLM이 안전하게 작업할 수 있는 하네스 구조입니다.

```text
[ Harness Core (Orchestration & Policy) ]
  │
  ├─ Context Builder (Context Budgeting)
  │    └─ 구조적 evidence: manifest, topology, symbols
  │
  ├─ Pre-Write Guard (Safety Check)
  │    └─ 구조적 위험 감지
  │
  ├─ Patch Executor (Implementation)
  │
  └─ Verification Router (Validation)
       ├─ Traditional: Tests, Typecheck, Lint
       └─ Structural: post-write audit
```

### 각 계층의 역할과 입출력

**Context Builder (Context Budgeting)**
- **입력**: task, changed files, repo root
- **출력**: context pack (manifest, topology, symbols, boundary notes)
- LLM이 작업에 필요한 최소 컨텍스트를 수집합니다. lumin-repo-lens의 manifest, topology, symbols artifact를 통해 코드베이스의 지형 정보를 제공합니다.

**Pre-Write Guard (Safety Check)**
- **입력**: intended change, target files, evidence artifacts
- **출력**: advisory (block / warning / review cue)
- 코드 작성 전 예상 구조적 위험을 평가합니다. lumin-repo-lens의 pre-write advisory를 통해 변경 전 상태를 분석합니다.

**Patch Executor (Implementation)**
- **입력**: approved plan
- **출력**: small diff
- 승인된 범위 내에서 코드 변경을 실행합니다. 작은 diff 원칙을 유지합니다.

**Verification Router (Validation)**
- **입력**: diff
- **출력**: test/type/lint result + structural audit result
- 변경 후 검증을 라우팅합니다. Traditional (Tests, Typecheck, Lint) 과 Structural (lumin-repo-lens post-write / audit) 을 병행합니다.

### pre-write / post-write 실제 흐름

```text
pre-write advisory
  → 위험 감지 시 plan 수정
  → 승인 후 patch
  → post-write audit
  → structural duplicate 발견 시 allowlist 기록 또는 수정
```

## Part B. Core Evidence Provider: lumin-repo-lens

> AI에게 차가운 evidence를 제공하고 판단은 AI가 한다.

`lumin-repo-lens`는 하네스의 **핵심 엔진(Kernel)**이 아닙니다. 하네스에 정교한 지형 정보를 제공하는 **핵심 증거 제공자(Core Evidence Provider)**입니다.

- **성격**: Supporting Utility (High Leverage)
- **핵심 가치**: LLM의 할루시네이션(존재하지 않는 함수 호출, 중복 생성 등)을 방지하는 **구조적 근거(Grounded Evidence)** 제공

### 3대 역할

**Change Hygiene Gate (변경 위생 게이트)**: 테스트/타입/린트처럼 최종 결론을 내리는 것이 아니라, "수정 전후의 구조적 위험"을 감지하는 센서 역할입니다. 자체적으로 모든 검증을 완료하는 '완성형 면역계'는 아니며, 반드시 전통적인 검증 도구와 병행되어야 합니다.

**Code Map Generator (코드 맵 생성기)**: 코드의 토폴로지(Topology), 모듈 경계, 중복 패턴, 공개 API 표면 등을 LLM이 읽기 쉬운 형태(`JSON`, `Markdown`)로 추출합니다. LLM에게 "추측"하게 하지 않고, `lumin-repo-lens`가 생성한 **"객관적 증거"**를 기반으로 판단하게 만듭니다.

**Protocol Hooks (작업 프로토콜 후크)**: `pre-write`, `post-write`, `refactor-plan` 등의 커맨드 구조가 이미 설계되어 있어, 에이전트의 작업 루프에 즉시 삽입 가능합니다.

### 통합 위치

```text
[ Harness Core ]
  │
  ├─ Context Builder
  │    └─ [ lumin-repo-lens artifacts: manifest, topology, symbols ]
  │
  ├─ Pre-Write Guard
  │    └─ [ lumin-repo-lens pre-write advisory ]
  │
  ├─ Patch Executor
  │
  └─ Verification Router
       ├─ Traditional: Tests, Typecheck, Lint
       └─ Structural: [ lumin-repo-lens post-write / audit ]
```

### 한계

- 테스트/타입/린트의 대체물이 아닙니다
- 구조적 센서이지 최종 검증자가 아닙니다
- evidence confidence를 명시해야 합니다

### Evidence Artifact Glossary

| 용어 | 정의 |
| --- | --- |
| `manifest` | repo의 파일/모듈/패키지 목록과 메타데이터 |
| `topology` | 모듈 간 의존성 그래프, 경계 정보 |
| `symbols` | export된 함수, 클래스, 인터페이스, 타입 목록 |
| `review pack` | 변경 영향 범위 + 관련 evidence를 모은 패키지 |
| `advisory` | pre-write 시 구조적 위험에 대한 조언 (block/warning/cue) |
| `audit` | post-write 시 변경 결과에 대한 구조적 검증 |

## Part C. 중복 판단 모델

finding 처리 프로토콜은 [[04. 도입과 운영 프로토콜]]을 참조합니다.

`lumin-repo-lens`는 중복을 삭제하지 않습니다. 중복의 성격을 분류해 자동 가드와 LLM 검토를 분기합니다.

### 원칙

- 구조적으로 증명 가능한 중복은 pre-write 또는 post-write에서 차단합니다.
- 도메인 소유권, 라이프사이클, 계약이 다르면 자동 통합하지 않습니다.
- `partial` evidence 또는 blind zone이 있으면 review cue로만 노출합니다.
- 중복 발견의 목적은 제거 자체가 아니라 reuse, merge, keep separate, rename, allow 중 적절한 결정을 돕는 것입니다.

### 판단 매트릭스

| 유형 | 신호 | 처리 |
| --- | --- | --- |
| Exact structural duplicate | 같은 symbol, path, route, command, migration id, export surface | Auto-guard / block |
| Boundary bypass duplicate | 기존 owner를 우회하는 새 구현 | Auto-guard 후보 |
| Contract shape duplicate | 거의 같은 DTO, schema, event payload | confidence 기반 가드 또는 review cue |
| Semantic overlap | 의도는 비슷하지만 owner, lifecycle, invariant가 다름 | LLM review |
| Allowed duplicate | adapter, generated code, fixture, v1/v2 병행 | allow with reason |
| Low-confidence duplicate | dynamic language, macro, framework registration blind zone | review cue only |

### 중복 Finding 결론 vocabulary

finding이 떴을 때 LLM은 다음 중 하나로 결론을 남깁니다.

| 결론 | 의미 |
| --- | --- |
| `reuse-existing` | 기존 구현을 재사용 |
| `remove-new-duplicate` | 새로 만든 중복 제거 |
| `merge` | 둘을 통합 |
| `keep-separate` | 도메인/책임이 달라 분리 유지 |
| `rename` | 명명 충돌만 해결 |
| `add-test` | 불변식 테스트 추가 후 유지 |
| `add-allowlist-entry` | 허용 중복으로 등록 |

### 예외와 허용 중복

- 허용 중복은 reason, owner, expiry 또는 review condition을 남겨야 합니다.
- confidence가 낮으면 block이 아니라 review cue로 둡니다.
- structural duplicate는 merge 전에 해소하거나 재사용 근거를 남겨야 합니다.

### allowlist schema

```json
{
  "id": "allow-001",
  "kind": "allowed-duplicate",
  "reason": "anti-corruption layer between payment v1 and v2",
  "owner": "team-billing",
  "files": ["src/adapter/payment_v1.ts", "src/adapter/payment_v2.ts"],
  "expiry": "2027-01-01",
  "reviewCondition": "v1 migration 완료 후 재검토"
}
```

## Part D. Canonical Evidence IR

> 언어별 extractor는 늘리되, 산출물은 하나의 Canonical Evidence IR로 수렴시킨다.

완전히 언어별 파이프라인으로 쪼개면 Shape Index, Call Graph, Topology 같은 기존 장점이 언어마다 중복 구현됩니다. 반대로 공통 추상화만 강제하면 Python의 `__all__`, Go의 package/export 규칙, Rust의 `pub use`/macro, Java의 package/class visibility 같은 의미론을 잃습니다.

### 구조

```text
Repository Scanner
  → Project/Build Context Detector
  → Language Router
  → Language-specific Extractors
  → Canonical Evidence IR
  → Shared Producers
      - Shape / Contract Index
      - Symbol Graph
      - Call Graph
      - Public Surface Discipline
      - Topology / Dependency Boundaries
      - Pre-write / Post-write Gate
  → JSON Artifacts + Summary + Review Pack
```

### LanguageExtractor IR

```ts
interface LanguageExtractor {
  id: "typescript" | "javascript" | "python" | "go" | "rust" | "java";
  fileExtensions: string[];
  detectProject(root): ProjectContext[];
  extractFile(file, context): CanonicalFileFacts;
  resolveImports?(facts, context): ResolutionFacts;
  extractCalls?(file, context): CallFacts;
  extractShapes?(file, context): ShapeFacts;
  capabilities: {
    symbols: "stable" | "partial" | "experimental";
    imports: "stable" | "partial" | "experimental";
    calls: "stable" | "partial" | "experimental";
    types: "stable" | "partial" | "none";
    publicSurface: "stable" | "partial" | "none";
  };
}
```

### 핵심 규칙

- 모든 extractor가 같은 수준의 정확도를 낸다고 가정하지 않습니다
- 각 artifact에 `language`, `confidence`, `blindZones`, `sourceKind`를 반드시 붙입니다
- `partial` evidence를 `stable` evidence처럼 다루지 않습니다
- `syntax-only`, `semantic-full`, `build-required` 모드를 구분합니다

### DuplicateFinding IR

중복 판단도 하나의 evidence artifact로 다룹니다. `suggestedAction`은 Part C의 결론 vocabulary와 동일합니다.

```ts
interface DuplicateFinding {
  id: string;
  kind:
    | 'exact-structural'
    | 'boundary-bypass'
    | 'contract-shape'
    | 'semantic-overlap'
    | 'allowed-duplicate'
    | 'low-confidence';
  decisionMode: 'auto-guard' | 'review-cue' | 'allow';
  confidence: 'stable' | 'partial' | 'experimental';
  severity: 'blocking' | 'warning' | 'info';
  evidenceRefs: EvidenceRef[];
  structuralKeys: string[];
  semanticHints?: string[];
  sourceKind: 'syntax-only' | 'semantic-full' | 'build-required';
  blindZones?: string[];
  suggestedAction:
    | 'reuse-existing'
    | 'remove-new-duplicate'
    | 'merge'
    | 'keep-separate'
    | 'rename'
    | 'add-test'
    | 'add-allowlist-entry';
}
```

`partial` 또는 `experimental` evidence는 자동 차단보다 review cue에 가깝게 다룹니다.

### 기존 TS/JS 기능의 다국어 일반화

- **Shape Index** → **Contract Shape Index**: TS interface/type alias뿐 아니라 Python dataclass/Pydantic, Go struct/interface, Rust struct/enum/trait, Java class/record를 정규화
- **Call Graph** → **Resolution-confidence Call Graph**: edge를 `static-exact`, `static-heuristic`, `framework-registered`, `dynamic-blind-zone`으로 분류
- **Barrel Discipline** → **Public Surface Discipline**: TS `index.ts`, Python `__init__.py`/`__all__`, Go package export, Rust `pub use`, Java package visibility를 일반화
- **Topology**: 파일/모듈/패키지/crate 간 edge만 정규화하면 언어 독립적으로 동작

## Part E. Language Adapter Roadmap

### 언어별 지원 우선순위

| 우선순위 | 언어 | 전략 |
| ---: | ----- | ---- |
| 1 | **Python** | 이미 `extract-py.mjs` seam 있음, `ast.parse` 기반 안정화 |
| 2 | **Go** | 이미 `extract-go.mjs` 있음, `go/packages` + `go/types` 기반 semantic enhancer |
| 3 | **Rust** | syntax-first, `cargo metadata` + rust-analyzer 기반 확장 |
| 4 | **Java** | JavaParser/JDT 기반 class/package topology |
| 5 | Kotlin/C#/C++ | LSP/compiler integration 전략 표준화 후 진입 |

### 권장 확장 단계

**단계 1**: IR 안정화 — 현재 canonical shape를 공식 schema로 고정, TS/JS extractor를 registry 기반 adapter로 이동

**단계 2**: Python/Go partial을 정식 experimental로 승격

**단계 3**: shared producer hardening — Shape Index, Symbol Graph, Topology는 다국어 입력 수용, Call Graph/Dead Export/Public Surface는 capability-aware

**단계 4**: Rust/Java syntax-first 지원

**단계 5**: semantic enhancer plugin — 각 언어에 compiler/LSP 기반 enhancer를 optional로 부착

### 기술적 리스크

- **정확도 불균형**: artifact별 `confidence` 강제, low-confidence evidence는 자동 finding이 아닌 review cue로만 노출
- **dynamic language blind zone**: blind-zone artifact 분리, "분석하지 못한 영역" summary에 노출
- **성능과 설치 복잡도**: `quick`, `full`, `semantic-full` profile 분리
- **build-system 의존성**: "build-required mode"와 "syntax-only fallback mode" 분리
- **공통 IR 과잉 추상화**: core field 작게 유지, `languageMetadata` 열어두기

성공 조건은 언어 수를 빨리 늘리는 것이 아니라, **언어별 extractor가 만든 증거의 신뢰도를 명시하고, 공통 producer가 그 신뢰도를 존중하도록 만드는 것**입니다.

### a-3 보조 Evidence: SSOT / Public Surface / Shape 충돌

a-3의 구조적 evidence를 제공합니다. 규칙 owner는 [[리포지토리 탐색과 안전 경계]]입니다.

- 새 public surface가 기존 SSOT를 우회하는 경우
- 유사한 DTO / schema / event payload shape
- 기존 canonical helper/type/shape와 충돌하는 신규 구현

이 evidence는 자동 삭제를 위한 것이 아니라, 재사용·통합·분리·명명 개선 여부를 판단하게 하는 입력입니다.

module boundary 위반 후보, forbidden dependency edge, circular dependency, directory topology와 실제 import graph의 불일치는 [[리포지토리 탐색과 안전 경계]]의 책임을 따른다.

### b-5 보조 Evidence: 새 function/helper/shape 생성 전 확인

b-5의 구조적 evidence를 제공합니다. 규칙 owner는 [[리포지토리 탐색과 안전 경계]]이고, finding protocol은 [[04. 도입과 운영 프로토콜]]입니다.

- 같은 책임의 existing symbol이 이미 있는가
- 새 helper가 기존 SSOT를 우회하는가
- 새 shape가 기존 public surface와 충돌하는가
- duplicate finding이 생기면 재사용/통합/분리/명명 개선 중 무엇인지 먼저 판단하는가

### 별도 제공 체크리스트 반영 (c-1~c-5)

리뷰 시점 체크를 위한 구조적 evidence를 제공합니다. 정책 owner는 [[리포지토리 탐색과 안전 경계]]와 [[04. 도입과 운영 프로토콜]]입니다.

- c-1: duplicate implementation, dead code, commented-out code, orphaned symbol
- c-2: swallowed error, empty catch, silent fallback, suppressed failure
- c-3: hidden coupling, implicit contract, init-order dependency, shared global state, side-effect edge
- c-4: re-export cleanup, dead export, unused barrel, public surface drift
- c-5: fan-in / fan-out concentration, topology hotspot, dependency hub

이 evidence는 판단 자체가 아니라, [[04. 도입과 운영 프로토콜]]과 boundary owner가 결론을 내리도록 돕는 입력입니다.

### 별도 제공 체크리스트 반영 (d-1~d-3)

- d-1: strict type 여부, `as any` / `as unknown as` 우회 여부, JSDoc contract 필요 여부
- d-2: circular dependency, boundary violation, forbidden dependency edge
- d-3: complexity, max-depth, max-lines-per-function, nested/god-function hot path

이 evidence는 lint/typecheck/CI gate의 실패 근거를 제공합니다.

### 별도 제공 체크리스트 반영 (e-1~e-4)

- e-1: string assertion-only test, coverage-only growth, output behavior mismatch
- e-2: internal implementation mocking, boundary violation mock, over-mocking
- e-3: missing empty-input/null/boundary/failure-path tests
- e-4: defensive code added only to satisfy tests

이 evidence는 테스트 품질 검토를 위한 입력이며, 정책 owner는 [[리포지토리 탐색과 안전 경계]]와 [[04. 도입과 운영 프로토콜]]입니다.
