## 도입 순서

```text
1. AGENTS.md 작성 (초기 도입 단계: [[01. 기준과 0순위 체크리스트#AGENTS.md 최소 템플릿]] 참조)
2. 필수 검증 명령 고정
3. 핵심 도메인 테스트 20개 작성
4. lumin-repo-lens로 구조적 evidence 생성 ([[02. 하네스와 구조적 Evidence 계층]] 참조)
5. pre-write/post-write 프로토콜 연결
6. 도메인 안전 계층과 연결 ([[짬/아카이브/LLM 바이브 코딩 코드베이스 관리/컨텍스트 맵과 도메인 안전 경계/DDD 영감 도메인 안전 계층/DDD-lite 도메인 안전 계층|DDD-lite 도메인 안전 계층]] 참조)
7. 반복 실수를 문서/테스트/자동화로 흡수
```

## pre-write / post-write 운영 방식

- **pre-write**: lumin-repo-lens advisory로 구조적 위험 감지. Context Builder가 manifest, topology, symbols artifact를 수집해 LLM에게 지형 정보를 제공
- **post-write**: lumin-repo-lens audit으로 새 structural duplicate 생성 여부 확인. Verification Router가 Traditional 검증과 Structural 검증을 병행

### 실제 명령 흐름

```text
lumin-repo-lens pre-write --target src/module/
  → advisory: blocking struct duplicate found in src/shared/
  → plan 수정: 기존 src/shared/ 재사용으로 변경
  → patch 실행
  → lumin-repo-lens post-write --diff patch.diff
  → audit: no new structural duplicates
  → CI 통과
```

## 중복 Finding 처리 프로토콜

판단 기준은 [[02. 하네스와 구조적 Evidence 계층#Part C. 중복 판단 모델]]을 참조합니다.

1. Structural duplicate finding이면 먼저 기존 구현을 재사용할 수 있는지 확인합니다.
2. 새 코드가 기존 public surface를 우회했다면 새 코드를 제거하거나 기존 API를 확장합니다.
3. Semantic duplicate finding이면 자동 통합하지 않습니다.
4. LLM은 owner, boundary, invariant, call site, lifecycle 차이를 비교합니다.
5. 결론은 다음 중 하나로 남깁니다.
   - `reuse-existing`: 기존 구현 재사용
   - `remove-new-duplicate`: 새로 만든 중복 제거
   - `merge`: 둘 통합
   - `keep-separate`: 도메인/책임이 달라 분리 유지
   - `rename`: 명명 충돌만 해결
   - `add-test`: 불변식 테스트 추가 후 유지
   - `add-allowlist-entry`: 허용 중복으로 등록 (reason, owner, expiry 기록)
6. 허용 중복이면 allowlist에 reason, owner, expiry 또는 review condition을 기록합니다.

## 별도 제공 체크리스트 반영 (b-5)

- b-5. 새 function/helper/shape를 만들기 전에 기존 owner, SSOT, symbol, public surface를 먼저 확인한다.
- 새로 만들 이유가 있으면 중복 finding과 함께 재사용/통합/분리/명명 개선 중 무엇인지 먼저 남긴다.
- 상세 판단은 [[02. 하네스와 구조적 Evidence 계층]]과 [[리포지토리 탐색과 안전 경계]]를 따른다.

## 에이전트에게 바로 맡기기 어려운 작업

고위험 변경 분류는 [[DDD-lite 도메인 안전 계층|DDD-lite 도메인 안전 계층]]의 고위험 변경 정의를 참조한다. 02의 작업 프로토콜 개요에서도 이 항목을 참조한다.

- 넓은 범위의 리팩터링
- 깊은 도메인 지식이 필요한 작업
- 보안/인증/개인정보/프로덕션 크리티컬 작업
- 모호한 작업

### 발견 시 에스컬레이션 기준

| 상황 | 조치 |
| --- | --- |
| 고위험 변경 감지 | 계획만 작성, human approval 필요 |
| 도메인 불변식 충돌 | read-only 조사만 허용, 테스트 추가까지만 허용 |
| multiple context 영향 | context owner 확인 후 작업 범위 재정의 |
| blind zone 진입 | LLM 추론 중단, human review 요청 |

## 별도 제공 체크리스트 반영 (c-1~c-5)

1. c-1 finding이면 duplicate implementation, dead code, commented-out code를 먼저 제거합니다.
2. c-2 finding이면 swallowed error를 boundary/handler로 이동하거나 failure를 명시합니다.
3. c-3 finding이면 hidden coupling, implicit contract, init order, shared global state, side-effect edge를 분리합니다.
4. c-4 finding이면 re-export / barrel / public surface 정리를 먼저 합니다.
5. c-5 finding이면 hotspot의 허용 여부와 분할 필요성을 먼저 판단합니다.
6. 결론은 `remove-dead-code`, `fix-error-boundary`, `make-contract-explicit`, `cleanup-reexport`, `split-hotspot`, `allow-with-owner` 중 하나로 남깁니다.
7. 자세한 증거는 [[02. 하네스와 구조적 Evidence 계층]], 의미 판단은 [[리포지토리 탐색과 안전 경계]]를 따릅니다.

## CI rollout 정책

- **Phase 1 (advisory)**: lumin-repo-lens finding을 warning으로 노출. CI는 통과하지만 PR comment로 알림
- **Phase 2 (blocking candidate)**: exact structural duplicate, boundary bypass는 blocking. semantic overlap, low-confidence는 advisory 유지
- **Phase 3 (full gate)**: confidence가 `stable`인 **exact structural duplicate / boundary bypass / blocking contract-shape finding**은 blocking. semantic overlap과 allowed duplicate는 [[02. 하네스와 구조적 Evidence 계층#Part C. 중복 판단 모델]]의 결론 vocabulary에 따라 review 또는 allow 처리. `partial`/`experimental`는 advisory 유지
- 전환 시기는 팀이 finding의 정확도를 신뢰할 수 있을 때 진행. false-positive가 많으면 Phase 1을 연장

## 반복 실수 흡수 원칙

LLM이 같은 실수를 반복할 때마다:

1. 프롬프트로 때우지 않습니다
2. AGENTS.md에 금지 규칙으로 추가합니다
3. 테스트로 불변식을 고정합니다
4. lint/import boundary rule로 자동으로 검출하게 합니다
5. lumin-repo-lens evidence로 구조적 근거를 제공합니다

> 레포의 영구 자산으로 흡수하는 것이 핵심입니다.

## e-4 finding 처리: test-appeasement defensive code 감지

- e-4. 테스트를 통과시키려고 production code에 방어 코드를 더했는지 먼저 확인한다.
- boundary/handler가 아닌 곳에 추가된 null guard, fallback, default return, special-case branch는 test-appeasement defensive code 후보로 본다.
- 정당한 boundary validation인지 확인한 뒤, 아니면 테스트를 수정하거나 boundary policy를 올린다.
- 상세 boundary 의미는 [[리포지토리 탐색과 안전 경계]]를 따른다.
