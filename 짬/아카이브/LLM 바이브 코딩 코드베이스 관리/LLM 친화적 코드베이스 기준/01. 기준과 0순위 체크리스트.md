## 핵심 결론

> LLM에게 많이 맡기는 용기보다, LLM이 틀릴 수밖에 없다는 전제 위에 세운 검증 시스템입니다.

그 검증 시스템의 일부로, 구조적으로 증명 가능한 중복은 자동 가드하고 의미론적 중복은 LLM이 판단해야 합니다.

처음부터 완벽한 문서화를 할 필요는 없습니다. 중요한 건 **LLM이 같은 실수를 반복할 때마다 프롬프트로 때우지 말고, 레포의 영구 자산으로 흡수하는 것**입니다.

## LLM 친화적 코드베이스의 기준

```text
- 모듈 경계가 명확하다.
- 한 파일이 너무 많은 책임을 갖지 않는다.
- 구조적으로 같은 코드가 여러 곳에 반복되지 않는다.
- 비즈니스 규칙이 테스트로 고정되어 있다.
- 의미적으로 비슷해 보여도 도메인이 다르면 자동 통합하지 않는다.
- 타입이 도메인 의미를 표현한다.
- 빌드/테스트가 로컬과 CI에서 일관되게 돈다.
- 변경 영향 범위를 찾기 쉽다.
- "하지 말아야 할 것"이 문서와 자동화로 박혀 있다.
- PR 크기가 작다.
- 실패했을 때 어디가 깨졌는지 빠르게 알 수 있다.
```

## 시니어 개발자의 암묵지를 영구 자산으로 끌어내리기

LLM 시대에 필요한 건 "개발자 없이 코딩하기"가 아닙니다.

**시니어 개발자의 암묵지를 코드, 테스트, 문서, 자동화로 끌어내리는 작업**이 먼저입니다.

```text
"이 모듈은 건드리면 위험해."
"이 API는 외부 파트너가 물고 있어서 함부로 바꾸면 안 돼."
"이 테스트는 느리지만 배포 전에는 꼭 돌려야 해."
"이 테이블은 soft delete라서 unique constraint를 조심해야 해."
"이 함수는 이름은 이상하지만 결제 정산 로직 때문에 바꾸면 안 돼."
```

이걸 LLM이 읽고, 실행하고, 위반하면 실패하게 만들어야 합니다.

## 0순위 체크리스트

> **`AGENTS.md` + 자동 검증 명령 + 핵심 도메인 테스트 20개**를 먼저 만드세요.

```text
1. 레포 루트에 AGENTS.md 작성
2. Core 검증 명령 3~5개 정의
3. 핵심 비즈니스 불변식 테스트 작성
4. 모듈 경계 문서화
5. LLM 작업 프로토콜 고정 ([[04. 도입과 운영 프로토콜]] 참조)
6. 같은 실수가 반복될 때마다 AGENTS.md와 테스트에 반영
7. 구조적 중복 가드 규칙을 문서화하고, 새 public surface를 만들기 전에 기존 구조 재사용 가능성을 먼저 확인
```

## 별도 제공 체크리스트 반영 (a-1~a-4)

아래 항목들은 외부에서 별도 제공된 설계 시점 체크리스트의 **canonical source**다. 원문 수정은 이 문서에서만 한다.

- a-1. 모듈/레이어 경계를 먼저 작성한다.
  - 원문: 구현보다 먼저 touched context, touched modules, allowed dependencies, forbidden dependencies를 정한다. 경계가 불명확하면 코드를 먼저 작성하지 않는다.
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
- a-2. lint로 의존성을 기계적으로 관리한다.
  - 원문: forbidden import, circular dependency, boundary rule 위반은 lint 또는 CI에서 실패해야 한다. 예외 의존성은 owner, reason, expiry 또는 review condition 없이 추가하지 않는다.
- a-3. 공용 유틸/타입/shape를 단일 출처(SSOT)로 미리 지정한다.
  - 원문: 공용 helper, type, shape, public surface는 재사용 가능한 canonical owner를 먼저 정한다. 새 shape를 만들기 전에 기존 SSOT와 충돌하는지 확인한다.
  - 규칙 owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
  - evidence / harness support: [[02. 하네스와 구조적 Evidence 계층]]
- a-4. 디렉터리를 위계대로 구성한다.
  - 원문: 디렉터리는 단순 정리가 아니라 의존 방향을 보이게 하는 장치다. domain, application, infrastructure, ui/interface가 폴더 이름과 import graph에서 동시에 드러나야 한다.
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]

## 별도 제공 체크리스트 반영 (b-1~b-5)

아래 항목들은 외부에서 별도 제공된 지시 시점 체크리스트의 **canonical source**다.

- b-1. 에러를 삼키지 않는다.
  - 원문: 빈 try/catch, 무의미한 fallback, 호출부 방어코드 남발을 금지하고 boundary/handler에서만 의미 있게 처리한다.
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
- b-2. 과한 중첩은 guard clause / early return으로 평탄화한다.
  - 원문: 과한 중첩은 early return / guard clause로 먼저 평탄화한다.
- b-3. 함수/파일 크기 상한을 둔다.
  - 원문: 함수/파일 크기 상한을 넘기지 않는다. 큰 함수나 큰 파일은 spec의 검증 기준을 먼저 확인한다.
- b-4. 코드 작성 전 edge case와 side effect를 먼저 고정한다.
  - 원문: 코드 작성 전 빈 입력, null, 경계값, 동시성, 실패 경로, side effect를 먼저 확인한다.
  - side-effect boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
- b-5. 새 function/helper/shape를 만들기 전에 기존 owner/SSOT/symbol을 확인한다.
  - 원문: 새 function/helper/shape를 만들기 전에 기존 owner, SSOT, symbol, public surface를 먼저 찾는다.
  - SSOT owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
  - evidence support: [[02. 하네스와 구조적 Evidence 계층]]
  - finding protocol: [[04. 도입과 운영 프로토콜]]

## 별도 제공 체크리스트 반영 (c-1~c-5)

아래 항목들은 외부에서 별도 제공된 리뷰 시점 체크리스트의 **canonical source**다.

- c-1. 기존 코드를 대체해야 할 자리에 중복이 생겼는가. 죽은 코드, 주석 처리 코드가 남지 않았는가.
  - 원문: 기존 코드를 대체하는 변경이라면 dead code, commented-out code, duplicate implementation이 남지 않아야 한다.
  - duplicate / dead code evidence: [[02. 하네스와 구조적 Evidence 계층]]
  - replacement / cleanup protocol: [[04. 도입과 운영 프로토콜]]
- c-2. 조용히 삼킨 에러가 있는가.
  - 원문: catch / fallback / suppression이 에러를 조용히 삼키지 않는지 확인한다.
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
- c-3. 숨은 결합, 암묵 계약, 초기화 순서 의존, 전역 상태 공유, side effect 로 연결된 모듈은 없는가.
  - 원문: hidden coupling, implicit contract, init order dependency, shared global state, side-effect-linked module을 리뷰한다.
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
  - evidence support: [[02. 하네스와 구조적 Evidence 계층]]
- c-4. re-export 는 잘 정리되었는가.
  - 원문: re-export / barrel / public surface 변경이 정리되어 있는지 확인한다.
  - public surface evidence: [[02. 하네스와 구조적 Evidence 계층]]
  - boundary / owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
- c-5. fan-in, fan-out이 한 군데로 과하게 몰려 있지는 않은가.
  - 원문: fan-in / fan-out이 한 모듈에 과도하게 집중되면 evidence와 함께 escalation 여부를 판단한다.
  - topology / call graph evidence: [[02. 하네스와 구조적 Evidence 계층]]
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]

## 별도 제공 체크리스트 반영 (d-1~d-3)

아래 항목들은 외부에서 별도 제공된 강제 시점 체크리스트의 **canonical source**다.

- d-1. 타입을 strict으로. `as any`, `as unknown as` 금지.
  - 원문: 타입을 strict으로 유지하고, `as any`와 `as unknown as`를 쓰지 않는다. JS는 JSDoc으로 계약을 드러낸다. 암묵 계약을 타입이 드러낼 수 있도록 한다.
  - meaning owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
  - evidence support: [[02. 하네스와 구조적 Evidence 계층]]
- d-2. 순환 의존성, 경계 위반 시 CI 실패하도록 한다.
  - 원문: 순환 의존성과 경계 위반은 CI 실패로 취급한다.
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
  - evidence support: [[02. 하네스와 구조적 Evidence 계층]]
- d-3. eslint complexity / max-depth / max-lines-per-function 등으로 중첩·갓펑션을 lint가 거부하도록 한다.
  - 원문: complexity / max-depth / max-lines-per-function 규칙을 넘는 중첩과 갓펑션은 허용하지 않는다.
  - evidence support: [[02. 하네스와 구조적 Evidence 계층]]

## 별도 제공 체크리스트 반영 (e-1~e-4)

아래 항목들은 외부에서 별도 제공된 테스트 시점 체크리스트의 **canonical source**다.

- e-1. 문자열이 아니라 출력 행동을 검증한다. 커버리지만 늘려서는 의미가 없다.
  - 원문: coverage만 늘리는 테스트는 충분하지 않다. 반환값, 상태 변화, side effect, contract, error semantics, domain invariant를 검증해야 한다.
  - evidence support: [[02. 하네스와 구조적 Evidence 계층]]
- e-2. mock는 외부 경계에서만. 내부 구현 세부를 mocking 금지.
  - 원문: 내부 구현 세부를 mocking하지 않고, 외부 경계의 계약만 mock/stub/fixture로 다룬다.
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
  - evidence support: [[02. 하네스와 구조적 Evidence 계층]]
- e-3. edgecase를 테스트로 고정한다. 빈 입력, 경계값, null, 실패 경로를 테스트 케이스로 둔다.
  - 원문: 빈 입력, 경계값, null, 실패 경로, invalid transition, 동시성, side effect 경계를 테스트 케이스로 먼저 고정한다.
  - invariant owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]
- e-4. 테스트를 통과시키려고 production code에 방어 코드를 더했는지 확인한다.
  - 원문: 테스트를 만족시키기 위한 임시 방어코드가 아니라 boundary / handler / invariant로 올라가야 한다. 테스트만 통과하면 끝이 아니라, production code가 테스트를 핑계로 의미 없는 fallback을 얻지 않았는지 확인한다.
  - finding protocol: [[04. 도입과 운영 프로토콜]]
  - boundary owner: [[리포지토리 탐색과 안전 경계|01. 컨텍스트 맵과 도메인 안전 경계]]

## AGENTS.md 최소 템플릿

```md
# AGENTS.md

## 프로젝트 개요
- 기술 스택, 빌드/테스트 명령

## 필수 검증 명령
- 수정 후 무조건 통과해야 하는 명령

## 모듈 경계
- 수정 가능 영역, 수정 금지 영역

## 금지 규칙
- 절대 해서는 안 되는 변경

## Risky Area
- 건드리면 위험한 모듈, 이유, 소유자

## PR Protocol
- PR 크기 제한, 필수 리뷰 항목

## 반복 실수 흡수
- LLM이 반복한 실수를 금지 규칙이나 테스트로 영구화
```

## 중복 판단 기본 원칙

구조적으로 증명 가능한 중복은 자동 가드하고, 의미적으로 유사한 중복은 owner, boundary, invariant, lifecycle을 근거로 LLM이 판단합니다. 자세한 판단 모델과 매트릭스는 [[02. 하네스와 구조적 Evidence 계층#Part C. 중복 판단 모델]]을 참조합니다.
