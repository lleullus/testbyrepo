## Oracle 분석 요약

Anthropic의 `Agentic coding and persistent returns to expertise`는 Claude Code 사용 세션을 분석하여, 에이전틱 코딩에서 실제로 어떤 분업이 일어나는지와 사용자의 전문성이 성공률에 어떤 영향을 주는지를 다룬 연구다.

이 노트에서 중요한 점은 "Claude Code가 얼마나 똑똑한가"가 아니다.

프로젝트 99 관점의 핵심은 다음이다.

> 에이전트가 execution을 많이 맡을수록, 인간은 더 적게 코드를 직접 쓰는 대신 더 정확하게 문제를 정의하고, 완료 조건을 정하고, 검증 신호를 요구하고, 실패 시 방향을 회복시켜야 한다.

즉, 이 자료는 프로젝트 99의 기존 thesis를 강화한다.

프로젝트 99는 workflow를 보여주는 문서 세트가 아니라, LLM이 대형 코드베이스를 다룰 때 인간 전문가의 판단 구조를 외부화하고, 초보자도 그 판단 구조를 따라가게 만드는 시스템이다.

## 이 연구가 실제로 말하는 것

### 1. 에이전틱 코딩의 기본 분업은 planning과 execution의 분리다

Anthropic 연구는 Claude Code 세션에서 의미 있는 의사결정을 크게 두 종류로 나눈다.

- planning decision
  - 무엇을 할 것인가
  - 어떤 접근을 택할 것인가
  - 무엇을 완료로 볼 것인가
- execution decision
  - 어떤 파일을 바꿀 것인가
  - 어떤 코드를 쓸 것인가
  - 어떤 명령을 실행할 것인가
  - 어떤 구현 세부를 선택할 것인가

관찰된 전형적 패턴은 사람이 planning decision의 대부분을 맡고, Claude가 execution decision의 대부분을 맡는 구조다.

프로젝트 99 관점에서는 이 구분이 매우 중요하다.

LLM에게 맡겨도 되는 것은 "실행의 세부"이지, 프로젝트의 안전 기준, 완료 조건, 도메인 불변식, 변경 허용 범위 전체가 아니다.

따라서 좋은 LLM 코딩 시스템은 다음을 먼저 고정해야 한다.

- 사람이 정해야 하는 planning 기준
- agent에게 위임해도 되는 execution 범위
- execution 결과를 판정할 검증 계약
- 실패했을 때 되돌아오는 recovery loop

### 2. 전문성은 코드를 직접 쓰는 능력보다 agent를 조종하는 능력으로 나타난다

연구에서 말하는 expertise는 직업명이나 일반 지능이 아니라 task-specific expertise다.

즉, 소프트웨어 엔지니어인지 아닌지가 핵심이 아니다.

중요한 것은 사용자가 해당 문제를 얼마나 정확히 이해하고 있는가다.

전문성은 다음 행동으로 드러난다.

- 지시를 구체적으로 프레이밍한다.
- 무엇을 검증해야 하는지 명시한다.
- Claude의 산출물을 그대로 수용하지 않고 수정 방향을 제시한다.
- 실패나 오해가 생겼을 때 문제의 본질로 다시 끌고 온다.
- 도메인 규칙과 edge case를 알고 있다.

프로젝트 99에서 레포 루트 `AGENTS.md`, 모듈 경계 문서, 작업 프로토콜, 검증 체크리스트는 이 전문성을 문서화한 외부 기억 장치다.

초보자가 전문가처럼 행동하게 하려면 "좋은 프롬프트를 써라"가 아니라 다음을 제공해야 한다.

- 어떤 정보를 먼저 조사해야 하는가
- 어떤 계획을 먼저 세워야 하는가
- 어떤 변경은 작게 쪼개야 하는가
- 어떤 테스트는 무조건 통과해야 하는가
- 어떤 도메인 불변식은 절대 깨면 안 되는가
- 실패하면 어떤 순서로 원인을 좁혀야 하는가

### 3. 성공은 모델 능력만이 아니라 검증 가능한 완료 신호와 연결된다

Anthropic 연구에서 성공은 단순한 주관적 만족이 아니라, 테스트 통과, 커밋, PR, 사용자 확인 같은 hard signal과 연결되어 측정된다.

LLM 기반 코드 변경에서 중요한 질문은 "Claude가 그럴듯하게 답했는가"가 아니다.

중요한 질문은 다음이다.

- 테스트가 통과했는가
- 타입 검사가 통과했는가
- 린트가 통과했는가
- 빌드가 통과했는가
- 핵심 비즈니스 invariant가 깨지지 않았는가
- 변경 의도와 실제 diff가 일치하는가
- 검증 명령이 재현 가능한가

따라서 project 99의 0순위 체크리스트 중 다음 항목은 이 연구와 강하게 연결된다.

```text
2. "무조건 통과해야 하는 명령" 3~5개 정의
3. 핵심 비즈니스 불변식 테스트 작성
5. LLM 작업 프로토콜 고정: 조사 -> 계획 -> 작은 수정 -> 테스트 -> 리뷰
6. 같은 실수가 반복될 때마다 AGENTS.md와 테스트에 반영
```

검증 가능한 신호가 없으면 agent의 긴 실행 사슬은 생산성이 아니라 위험 증폭기가 된다.

### 4. trouble 이후의 recovery가 expertise의 핵심 차이다

연구에서 특히 프로젝트 99에 중요한 부분은 trouble을 만났을 때의 차이다.

초보자는 실패 신호가 생기면 세션을 포기하거나 문제를 더 흐리게 만들 가능성이 높다.

반대로 expert-like user는 실패를 다음 판단으로 바꾼다.

- 어떤 실패인지 분류한다.
- 실패한 명령과 로그를 보존한다.
- 변경 범위를 줄인다.
- 가설을 세운다.
- 더 작은 diff로 재시도한다.
- 불변식과 완료 조건을 다시 확인한다.
- agent의 방향을 수정한다.

이것은 `02. 작업 프로토콜`의 핵심 근거가 된다.

프로젝트 99의 작업 프로토콜은 단순한 절차표가 아니라, 실패 상황에서 novice-like collapse를 막는 recovery scaffold다.

따라서 `Research -> Plan -> Small diff -> Run checks -> Review -> Merge` 구조는 다음처럼 해석해야 한다.

- Research: agent가 손대기 전에 현재 구조와 위험 범위를 확인한다.
- Plan: planning decision을 사람이 통제 가능한 형태로 만든다.
- Small diff: 실패했을 때 원인을 추적할 수 있게 변경 단위를 제한한다.
- Run checks: 성공 여부를 감각이 아니라 hard signal로 판정한다.
- Review: agent 실행 결과와 인간 planning 기준의 일치 여부를 확인한다.
- Merge: 검증 가능한 완료 신호가 있을 때만 변경을 흡수한다.

### 5. 작업의 중심은 디버깅에서 end-to-end 운영으로 넓어지고 있다

Anthropic 연구는 Claude Code 사용이 단순한 버그 수정에서 벗어나, software operation, writing, data analysis, end-to-end work로 확장되고 있음을 보여준다.

프로젝트 99에서는 이 점을 다음처럼 받아들여야 한다.

LLM 친화적 코드베이스는 "코드 수정에만 좋은 구조"가 아니어야 한다.

앞으로 agent는 다음 작업까지 함께 수행한다.

- 기존 시스템 이해
- 변경 계획 작성
- 코드 수정
- 테스트 작성 또는 수정
- 명령 실행
- 로그 확인
- 배포 또는 운영 절차 수행
- 데이터 분석
- 문서 작성
- 변경 이유 설명
- 후속 작업 정리

따라서 `03. LLM 친화적 코드베이스 기준`은 단순한 파일 구조 기준이 아니라, agent가 더 긴 작업 사슬을 수행해도 망가지지 않는 시스템 조건을 정의해야 한다.

## 프로젝트 99에 가져올 인사이트

### 4.1 검증 가능한 완료 신호에 대한 시사점

Anthropic 연구의 verified success 개념은 프로젝트 99에서 왜 hard signal 중심 검증 체계가 먼저 와야 하는지를 설명해준다.

반영 원칙:

- 테스트, 타입, 린트, 빌드는 agent 결과의 기본 판정 장치다.
- 핵심 비즈니스 invariant는 사람이 매번 읽는 대신 테스트로 고정해야 한다.
- "성공한 것 같다"는 표현은 금지하고, "어떤 명령이 통과했는가"로 바꿔야 한다.
- trouble이 반복되면 문서 설명보다 먼저 테스트나 계약으로 승격할 수 있는지 본다.

문서에 연결할 문장 후보:

> 에이전틱 코딩의 성공은 모델 응답 품질이 아니라 hard verifiable signal로 판정해야 한다. 따라서 검증 가능한 완료 신호는 LLM 작업의 사후 보조물이 아니라, agent autonomy를 허용하기 위한 선행 조건이다.

### 4.2 `AGENTS.md`에 대한 시사점

레포 루트 `AGENTS.md`는 인간 전문가의 steering 방식을 agent가 반복해서 읽을 수 있게 만드는 운영 매뉴얼이다.

전문 사용자는 매번 긴 설명을 하지 않아도 다음을 알고 있다.

- 무엇을 먼저 확인해야 하는가
- 어떤 변경은 피해야 하는가
- 어떤 명령은 반드시 실행해야 하는가
- 어떤 실패는 즉시 멈춤 조건인가
- 어떤 도메인 규칙은 구현보다 우선하는가

초보 사용자는 이 판단을 매번 즉흥적으로 떠올리기 어렵다.

따라서 AGENTS.md는 초보자를 전문가처럼 보이게 하는 프롬프트 트릭이 아니라, 전문가 판단 구조를 agent-facing rule로 고정하는 문서다.

반영 원칙:

- AGENTS.md에는 "좋은 답변 방식"보다 "이 레포에서 틀리면 안 되는 판단 기준"을 적는다.
- 반복 실수는 AGENTS.md와 테스트 중 더 적합한 위치에 반영한다.
- agent에게 planning까지 넘기지 않도록, 조사·계획·수정·검증의 역할 경계를 명확히 한다.
- agent가 긴 action chain을 수행하기 전에 반드시 읽어야 하는 경계와 명령을 둔다.

문서에 연결할 문장 후보:

> AGENTS.md의 목적은 agent를 더 자유롭게 만드는 것이 아니라, 사람이 유지해야 할 planning judgment를 agent가 매 세션 재사용할 수 있는 외부 기억으로 고정하는 것이다.

### 4.3 `01. 컨텍스트 맵과 도메인 안전 경계`에 대한 시사점

Anthropic 연구는 task-specific domain expertise가 성공과 강하게 연결된다고 본다.

프로젝트 99에서 도메인 전문성은 개인 머릿속에만 있으면 안 된다.

대형 코드베이스에서는 다음이 문서화되어야 한다.

- 어떤 모듈이 어떤 의미적 책임을 갖는가
- 어떤 변경이 어떤 downstream behavior를 건드리는가
- 어떤 데이터나 상태가 안전 경계인가
- 어떤 파일은 단순 구현체가 아니라 도메인 계약의 일부인가
- 어떤 변경은 고위험 라우팅이 필요한가

이것이 `01. 컨텍스트 맵과 도메인 안전 경계`의 역할이다.

반영 원칙:

- 컨텍스트 맵은 폴더 설명이 아니라 도메인 판단 지도여야 한다.
- 모듈 경계는 agent가 변경 범위를 줄이는 데 사용되어야 한다.
- 안전 경계는 "주의"가 아니라 변경 전 확인 조건과 검증 조건으로 연결되어야 한다.
- 도메인 owner가 불분명한 변경은 agent가 임의로 결정하지 못하게 해야 한다.

문서에 연결할 문장 후보:

> task-specific expertise가 agentic coding 성공의 핵심이라면, 컨텍스트 맵은 코드베이스 안의 도메인 전문성을 agent가 참조할 수 있는 형태로 외부화하는 장치다.

### 4.4 `02. 작업 프로토콜`에 대한 시사점

`02` 문서는 agent 세션의 decision choreography를 정의한다.

Anthropic 연구의 planning/execution 분업은 이 문서의 중심 근거가 된다.

사람은 무엇을 할지, 왜 하는지, 완료를 무엇으로 볼지 결정한다.

agent는 정해진 범위 안에서 조사하고, 수정하고, 명령을 실행하고, 결과를 보고한다.

반영 원칙:

- 작업 시작 전 Research를 생략하지 않는다.
- Plan은 agent의 자유 발상이 아니라 사람의 판단을 검토 가능한 형태로 만든 것이다.
- Small diff는 review 비용을 낮추기 위한 장치이자 recovery 가능성을 높이는 장치다.
- Run checks는 성공 판정의 핵심이다.
- Review는 코드 스타일 검토가 아니라 planning 기준과 execution 결과의 일치 여부 검토다.

문서에 연결할 문장 후보:

> agentic coding에서 사람이 유지해야 할 핵심 권한은 execution micro-control이 아니라 planning decision, done criteria, recovery direction이다.

### 4.5 `03. LLM 친화적 코드베이스 기준`에 대한 시사점

전문 사용자는 한 번의 지시로 agent가 더 많은 action을 하게 만든다.

이것은 좋은 일이기도 하지만 위험이기도 하다.

코드베이스가 LLM 친화적이지 않으면 긴 action chain은 다음 문제를 만든다.

- agent가 잘못된 모듈을 읽는다.
- 변경 범위가 커진다.
- 검증 명령을 놓친다.
- 실패 로그가 정리되지 않는다.
- 사람이 review할 수 없는 diff가 나온다.
- 같은 실수가 반복된다.

따라서 `03` 문서는 agent가 더 많은 일을 하도록 허용하기 위한 환경 조건을 정의해야 한다.

반영 원칙:

- agent가 읽어야 할 entry point가 명확해야 한다.
- 테스트 하니스가 빠르고 재현 가능해야 한다.
- 변경 범위와 owner가 문서로 드러나야 한다.
- evidence layer가 있어야 한다.
- agent 산출물도 검토 가능한 형태로 남아야 한다.
- 긴 작업 사슬을 허용하려면 중간 checkpoint와 rollback 기준이 있어야 한다.

문서에 연결할 문장 후보:

> LLM 친화적 코드베이스란 agent가 오래 실행되어도 안전한 코드베이스다. 이를 위해서는 구조, 검증, 경계, evidence, recovery loop가 함께 설계되어야 한다.

## 해석 한계

이 자료를 프로젝트 99에 적용할 때 다음 한계를 유지해야 한다.

### 1. Claude Code 연구이지 모든 LLM 도구의 보편 법칙은 아니다

분석 대상은 Claude Code 세션이다.

따라서 결과를 Codex, Copilot, Cursor, aider, custom agent system에 그대로 일반화하면 안 된다.

다만 planning/execution 분업, verified success, domain expertise, recovery loop라는 관찰은 프로젝트 99의 원칙을 보강하는 근거로 사용할 수 있다.

### 2. 성공 측정은 실제 운영 성과가 아니라 세션 내 신호에 기반한다

연구의 success는 transcript와 hard signal을 바탕으로 추정된다.

실제 배포 후 장기 품질, 유지보수성, 장애 감소, 제품 성과까지 직접 측정한 것은 아니다.

따라서 프로젝트 99에서는 이 자료를 "성공 측정의 최종 답"이 아니라 "검증 가능한 신호를 중시해야 한다는 외부 근거"로 사용해야 한다.

### 3. 전문성은 대체되지 않았지만, 도구 변화에 따라 분업은 바뀔 수 있다

연구는 현재 시점에서 domain expertise의 수익률이 지속된다고 본다.

하지만 모델과 사용 방식이 바뀌면 planning과 execution의 경계도 변할 수 있다.

따라서 프로젝트 99는 특정 도구 사용법에 고정되기보다 다음 추상 원칙을 유지해야 한다.

- planning ownership
- verification contract
- domain boundary
- recovery protocol
- evidence-based review

### 4. 외부 레퍼런스는 본문 원칙을 대체하지 않는다

이 노트는 외부 근거다.

프로젝트 99의 source of truth는 여전히 다음 문서들이다.

- `레포 루트 AGENTS.md`
- `00. LLM 바이브 코딩 코드베이스 관리 홈`
- `01. 컨텍스트 맵과 도메인 안전 경계`
- `02. 작업 프로토콜`
- `03. LLM 친화적 코드베이스 기준`

이 노트는 그 문서들이 왜 필요한지를 설명하는 증거로만 사용한다.

## 배치 원칙

이 노트는 `04. 외부 레퍼런스`에 둔다.

본문 문서로 승격하지 않는다.

이유는 다음과 같다.

- Anthropic 글은 프로젝트 내부 규칙이 아니라 외부 연구다.
- 프로젝트 99의 thesis를 바꾸지 않고 보강한다.
- 구체 규칙은 이미 `AGENTS.md`, `01`, `02`, `03` 문서가 담당한다.
- 이 노트의 역할은 본문 원칙에 대한 외부 증거와 해석을 보존하는 것이다.
- 필요한 문장만 본문 문서의 "관련 외부 근거" 또는 "참고"로 연결하면 충분하다.

## 최종 판단

Anthropic의 Claude Code expertise 연구는 프로젝트 99에 매우 적합한 외부 레퍼런스다.

하지만 이 자료가 말하는 결론은 "agent에게 더 많이 맡겨라"가 아니다.

프로젝트 99 관점의 결론은 다음이다.

> 에이전트가 execution을 더 많이 맡을수록, 프로젝트는 planning judgment, domain boundary, verification contract, recovery protocol을 더 명시적으로 갖춰야 한다.

따라서 이 노트는 다음 판단을 보강하는 증거로 사용한다.

- `AGENTS.md`는 전문가 판단을 agent-facing memory로 고정하는 장치다.
- `01`은 task-specific domain expertise를 코드베이스 구조에 연결하는 장치다.
- `02`는 planning과 execution의 분업 및 recovery loop를 운영하는 장치다.
- `03`은 더 긴 agent action chain을 안전하게 허용하기 위한 코드베이스 조건이다.

이 자료는 프로젝트 99의 기존 thesis를 대체하지 않는다.

오히려 그 thesis를 더 강하게 만든다.

LLM 바이브 코딩의 핵심은 workflow를 예쁘게 보여주는 것이 아니라, 전문가의 판단 구조를 재구성하여 초보자도 senior-like steering을 수행하게 만드는 것이다.
