> [!summary] Phase 1 목적
> Phase 0에서 분할된 MVP를 순차적으로 실행한다. 각 MVP는 Scope Packet → Lumin Evidence → 구현 → 검증 → 분기의 사이클을 따른다.

## 전체 사이클

```text
Step 0: DDD Scope Packet 준비 (DDD-Lumin 대상 시)
  → Step 0.5: Lumin Pre-write Evidence (required 시)
    → Step 1: Implementation Subagent 실행
      → Step 1.5: Lumin Post-write Drift Check (pre-write 사용 시)
        → Step 2: Verification Subagent(s)
          → Step 3: 분기 판정 (통과 / 수정 / blocked)
```

## Step 0 — DDD Scope Packet

> DDD-Lumin 대상 MVP만 실행. 비대상 MVP는 건너뜀.

### 최소 구조

```yaml
scope_packet:
  mvp_id: MVP1
  mode: minimal | strict
  allowed_files: []
  excluded_scope: []

  authority_check:
    active_authority_confirmed: true | false

  ssot_check:
    creates_or_changes_covered_artifact: true | false
    searched_existing: true | false
    decision: reuse_existing | create_local_only | create_ssot_candidate | blocked_duplicate

  module_boundary_check:
    layers_touched: []
    public_surface_changed: true | false
    dependency_direction_changed: true | false

  evidence_profile:
    lumin:
      available: true | false
      prewrite_required: true | false
      postwrite_required: true | false
```

### strict 패킷 추가 필드

```
intended_change
allowed_files/paths (정확한 경로 목록)
ssot_check (Lumin evidence 기반)
module_boundary_check (의존성/export 변경)
evidence_profile.lumin
post_task_audit placeholder
```

> [!warning] required evidence 부족 시
> Lumin pre-write required인데 evidence도 없고 manual equivalent도 없으면 **blocked 처리**. 구현 서브에이전트에 할당하지 않는다.

## Step 0.5 — Lumin Pre-write

pre-write가 필요한 MVP는 구현 전에 intentJson을 구성하고 Lumin pre-write를 실행한다.

### intentJson 구조

```json
{
  "mode": "pre-write",
  "root": ".",
  "output": ".audit",
  "intentJson": "{\"names\":[\"새Symbol\"],\"shapes\":[{\"name\":\"새Shape\",\"fields\":[\"field1\"]}],\"files\":[\"src/foo.py\"],\"dependencies\":[{\"from\":\"src/foo.py\",\"specifier\":\"src.bar\"}],\"plannedTypeEscapes\":[]}"
}
```

### pre-write 실행 전 검증 체크리스트

1. 모든 `files`가 `allowed_files` 내에 있는가
2. `dependencies`가 `specifier`(파일경로 아님)를 사용하는가
3. `shapes`의 concrete type에 fields가 포함되었는가
4. excluded_scope의 경로가 누출되지 않았는가

### blocked 조건

- exact duplicate 발견, 기본 결정이 `reuse_existing` 또는 `blocked_duplicate`
- Lumin evidence가 stale/partial/unsupported인데 absence claim 필요
- planned file이 Scope Packet `allowed_files` 밖
- new shared/common/utils/lib/helper/type home이 scope에 미승인

## Step 1 — Implementation Subagent

할당받은 MVP에 대해 구현 서브에이전트가 내부적으로 계획을 세우고 곧바로 구현까지 완료한다.

> 별도 사전 계획 보고서는 요구하지 않는다. 할당 후 결과를 기다리면 된다.

### 구현 완료 보고 필수 항목

```md
## Implementation Completion Report
1. Initial Plan Summary (MVP ID, Plan depth, Goal, Excluded scope)
2. Reuse and Duplicate Check (inspected, matched candidates, decision)
3. R1-R12 Rule Map (12개 규칙 각각 active/n-a/blocked-risk)
4. Actual Changes (files changed, summary)
5. Deviations from Initial Plan
6. Tests Run (command, result)
7. DDD-Lumin Delta (Scope Packet ref, pre-write/post-write handling)
8. Blocked Issues
```

> [!tip] DDD-Lumin 추가 구현 제약
> - `allowed_files` 밖 파일 수정 금지
> - 새 covered artifact/helper/type/shape 생성 금지 (미승인 시)
> - 새 import boundary 변경 금지
> - public surface/barrel/re-export 변경 금지
> - Lumin exact match를 무시한 중복 구현 금지
> - 위반 시 **blocked 보고** 후 중단

## Step 1.5 — Lumin Post-write

pre-write를 사용한 MVP는 구현 직후, 검증 전에 오케스트레이터가 post-write drift check를 수행한다.

### drift blocker 조건

- unexpected files outside intent
- silent new type escapes
- public surface drift
- forbidden dependency drift
- unmapped new structural home

### Post-write Remediation Routing

1. **continue_to_verification** — blocker가 아니거나 기록만으로 충분
2. **blocked_or_rescope** — Scope Packet/MVP 범위 재정의 필요
3. **clean_implementation_reassignment** — 공식 파일 변경이 필요한 remediation

## Step 2 — Verification Subagent(s)

### 단일 검증 (기본값)

1명의 검증 서브에이전트가 할당받아 검증 수행.

### 다중 검증 전략

| 전략 | 방식 | 적합 상황 |
|------|------|----------|
| **Blind Double** | 2명 독립 검증, 상호 cross-check 없음 | 고위험 MVP, correctness 우선 |
| **Split-Lens** | 각자 다른 렌즈 (범위/동작/아키텍처) | 복합 MVP, coverage-to-noise 최고 |
| **Adversarial** | Primary 검증 + Challenger 반증 | 하나의 가정이 전체를 무효화할 수 있는 변경 |
| **Quorum** | 3명+ 독립 검증, 증거 기반 판정 | 주관적 판단 영역, 해석 차이 큰 작업 |

> 최종 산출물은 **Verification Bundle**이다: 각 검증자 결과 + 상충/중첩 + Orchestrator 종합

## Step 3 — 분기 판정

오케스트레이터가 Verification Bundle을 검토하여 다음 중 하나로 판정:

| 판정 | 조건 | 후속 조치 |
|------|------|----------|
| **통과** | 모든 검증 통과, blocker 없음 | 다음 MVP 진행 또는 Phase 2 |
| **수정 필요** | valid material finding 존재 | clean session으로 재할당 |
| **blocked** | Scope Packet/MVP 범위 자체가 잘못됨 | Phase 0 재진입 또는 사용자 문의 |

> Hard Rule: 수정 재할당 시 반드시 **새로운 clean subagent session** 사용.

## Oracle Code Mode (선택)

구현 서브에이전트가 `oracle-plus code`를 통해 구현을 수행하도록 지정 가능.

- greenfield/신규 파일 생성에 적합
- 기존 파일 증분 수정은 일반 subagent 우선
- 생성된 ZIP에서 PLAN.md는 advisory plan record
- DDD-Lumin 대상 시: Scope Packet `allowed_files`와 ZIP 대조 필수, post-write 필수
