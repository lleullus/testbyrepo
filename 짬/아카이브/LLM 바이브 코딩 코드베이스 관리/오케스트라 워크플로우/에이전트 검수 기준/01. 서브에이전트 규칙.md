> 구현/검증 서브에이전트가 반드시 준수해야 할 코딩 규칙과 검수 기준. 모든 서브에이전트는 작업 전 `/home/user01/서브에이전트-검수.txt`를 읽고 적용한다.

## R1-R12 Rule Map

| # | 규칙 | 적용 대상 | 위반 시 |
|---|------|----------|--------|
| **R1** | Silent error swallowing 금지 | 예외/에러를 조용히 삼키지 않음 | 수정 필요 |
| **R2** | 중첩 3단계 초과 금지 | 조건문/루프 중첩 3-depth 제한 | 수정 필요 |
| **R3** | 함수/파일 과대 금지 | 함수는 50줄, 파일은 300줄 권장 | 수정 필요 |
| **R4** | 새 helper/type 생성 전 재사용 확인 | 기존 구현 검색 후 결정 | 수정 필요 |
| **R5** | 중복/데드코드 금지 | 동일 기능 중복 구현 금지 | 수정 필요 |
| **R6** | Hidden coupling 금지 | 암시적 결합, 전역 상태 공유 금지 | 수정 필요 |
| **R7** | Strict types 사용 | `any`/`as unknown as` 우회 금지 | 수정 필요 |
| **R8** | 순환/레이어 의존성 금지 | layer 위반 import 금지 | 수정 필요 |
| **R9** | Behavior over snapshot | 스냅샷보다 동작 검증 테스트 우선 | 수정 필요 |
| **R10** | Mock only external boundary | 외부 경계만 mock, 내부 mock 금지 | 수정 필요 |
| **R11** | Edge case coverage | 빈 입력/null/boundary/실패 경로 테스트 | 수정 필요 |
| **R12** | No test-only production guard | 테스트 통과용 방어 코드 금지 | 수정 필요 |

### Rule Map 작성 규칙

구현 완료 보고서의 R1-R12 Rule Map은 반드시:

1. 모든 12개 규칙에 상태가 기록되어야 함 (빈 칸/생략 금지)
2. `n-a`로 표시한 규칙은 타당한 이유가 있어야 함
3. 새 helper 생성했는데 R4=n-a → 위반
4. 새 boundary import 있는데 R8=n-a → 위반
5. behavior 변경 있는데 R9/R11=n-a → 위반

> 검증 서브에이전트는 Rule Map의 완전성과 타당성을 반드시 확인한다.

## 구현 서브에이전트 실행 규칙

1. `/home/user01/서브에이전트-검수.txt`를 먼저 읽는다.
2. MVP 범위를 분석하고 내부적으로 계획을 세운 뒤 곧바로 구현.
3. **MVP 범위가 불명확하거나 범위 밖 변경이 필요하면 blocked 보고.**
4. DDD-Lumin evidence가 부족해도 Lumin 직접 실행 금지. blocked 보고.
5. 계획 변경이 필요하면 자체 판단 후 변경, 완료 보고서에 사유 기록.
6. 구현 완료 보고서(R1-R12 포함)를 제출하고 종료.

### DDD-Lumin 추가 제약

- `allowed_files` 밖 파일 수정 → blocked
- 새 covered artifact 생성 (미승인 시) → blocked
- 새 helper/type/shape 생성 (미승인 시) → blocked
- import boundary 변경 (미승인 시) → blocked
- public surface/barrel/re-export 변경 → blocked
- Lumin exact match 무시 중복 구현 → blocked

## 검증 서브에이전트 실행 규칙

1. `/home/user01/서브에이전트-검수.txt`를 먼저 읽는다.
2. 할당된 verification assignment packet 기준으로 검증 계획 수립 후 바로 실행.
3. 확인 항목:
   - 실제 변경이 MVP 범위 내인가
   - MVP 범위를 벗어난 변경이 없는가
   - 구현 완료 보고서가 완전한가 (Plan Summary, Reuse Check, R1-R12, Actual Changes, Deviations)
   - R1-R12가 모두 채워져 있고 타당한가
   - DDD-Lumin evidence가 올바르게 처리되었는가
   - post-write blocker가 통과 처리되지 않았는가
4. Lumin 직접 실행 금지. evidence gap은 blocked 보고.
5. 결과는 "통과" 또는 "수정 필요"로 시작.

### 검증 결과 형식

```
통과
- (근거 나열)
- DDD-Lumin Evidence: (Scope Packet mode, Lumin 상태, SSOT 일관성)

또는

수정 필요
1. (구체적 finding)
- 이유:
- 권장:
```
