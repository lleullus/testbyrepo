1. 설계 시점에서 체크해야 할 것들

a-1. 모듈/레이어 경계를 먼저 작성한다. 

a-2.. lint로 의존성을 기계적으로 관리한다. 

a-3. 공용 유틸/타입/shape를 단일 출처(SSOT)로 미리 지정한다. 

a-4. 디렉터리를 위계대로 구성한다. 도메인/레이어별로 나눠 의존 방향을 눈으로 볼 수 있도록 한다.

2. 지시 시점에서 체크해야 할 것들

b-1. 에러를 삼키게 하지 마라. 빈 try/catch, 무의미한 fallback, 호출부마다 방어코드 금지. 실제는 경계/핸들러에서만 처리할 것.

b-2. 과한 중첩은 하지 마라. 3단계 이상은 그 중첩이 꼭 필요한지 확인하라. 만약 그렇지 않다면 early return, guard clause 로 평탄화하라.

b-3. 함수, 파일 크기 상한을 둬라. 

b-4. 테스트에서 엣지케이스부터 먼저 확인하도록 하라. side-effect 를 항상 확인하라. 다시 말해 코드 작성 전 빈 입력, null, 경계값, 동시성, 실패 경로를 먼저 작성하게 하라.

b-5. 새 function, helper, shape를 만들기 전에 먼저 확인하라.

3. 리뷰 시점에서 체크해야 할 것들. 

c-1. 기존 코드를 대체해야 할 자리에 중복이 생겼는가. 죽은 코드, 주석 처리 코드가 남지 않았는가.

c-2. 조용히 삼킨 에러가 있는가.

c-3. 숨은 결합, 암묵 계약, 초기화 순서 의존, 전역 상태 공유, side effect 로 연결된 모듈은 없는가.

c-4. re-export 는 잘 정리되었는가.

c-5. fan-in, fan-out이 한 군데로 과하게 몰려 있지는않은가.

4. 강제해야 할 것들

d-1. 타입을 strict으로. as any, as unknown as 금지. 암묵 게약을 타입이 드러낼 수 있도록(js 등 타입이 없는 것들은 js doc으로)

d-2. 순환 의존성, 경계 위반 시 CI 실패하도록 

d-3. eslint complexity / max-depth / max-lines-per-function 등으로 중첩·갓펑션을 lint가 거부하도록 한다.

5. 테스트 시 체크해야 할 것들 

e-1. 문자열이 아니라 출력 행동을 검증하도록 한다. 커버리지만 늘려서는 의미가 없다.

e-2. mock는 외부 경게에서만. 내부 구현 세부를 mocking 금지. 

e-3. edgecase 를 테스트로 고정. 빈 입력, 경계값, null, 실패 경로를 테스트 케이스로.

e-4. 테스트를 통과시키려고 프로덕션 코드에 방어 코드를 더했는지 확인한다.
