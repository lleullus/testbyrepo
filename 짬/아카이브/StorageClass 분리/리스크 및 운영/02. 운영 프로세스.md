# 운영 프로세스

> [!summary] 운영 프로세스
> 신규 SVM 추가 후 Monitoring 지표, Communication 기준, 운영 절차.
> 출처: Oracle #10 (Monitoring), Oracle #11 (Communication)

## Monitoring

지표 기준이 없으면 운영 효과를 객관적으로 평가할 수 없다. PVC 생성 성공만으로 SVM 부하 경감이나 사용자 영향을 판단할 수 없다.

| 관점 | 지표 |
|------|------|
| **Kubernetes** | 신규 PVC 생성 수, StorageClass별 PVC/PV 수, PVC Pending/Bound 상태, Pod mount 실패 이벤트, volume expansion/delete 성공 여부 |
| **Trident** | Backend 상태, Backend별 volume 수, provisioning 실패 이벤트, Trident controller 로그 |
| **NetApp** | SVM별 세션 수, SVM별 CPU Util, volume 생성 위치, capacity 사용률, latency/IOPS/throughput, export-policy/ACL 관련 실패 여부 |
| **운영** | 기존 SC 선택 사례, Console 필터링 우회 사례, 신규 SC 관련 문의/장애 티켓, 운영 반영 후 사용자 영향 여부 |

* 적용 전 baseline과 적용 후 비교 지표를 사전에 정의한다.
* Kubernetes 관점과 NetApp 관점을 함께 본다.
* 테스트 결과 문서에 수치 기반 관찰 결과를 남긴다.
* 운영 전환 후 일정 기간 집중 모니터링 기간을 둔다.

## Communication

SC가 두 개면 사용자가 혼동할 수 있다. 운영자도 기존 SC 유지, 신규 SC 사용, 롤백 기준을 동일하게 이해해야 한다.

* 신규 PVC는 신규 SC를 사용한다는 기준을 명확히 공지한다.
* 기존 SC는 기존 PVC 유지 목적이며 신규 PVC 생성에는 사용하지 않는다는 기준을 문서화한다.
* Console 필터링 또는 정책 차단이 완료되기 전까지 수동 검토 절차를 둔다.
* 운영자용 체크리스트와 사용자 안내 문구를 별도로 준비한다.

* 확인: 사용자 안내 완료 여부, 운영자 변경 절차 공유 여부, 신규 PVC 요청 시 SC 선택 검토 여부, 예외 요청 처리 절차 존재 여부
