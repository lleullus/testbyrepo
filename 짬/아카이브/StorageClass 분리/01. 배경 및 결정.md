# 왜 이 작업을 하는가

> [!summary] 결정 요약  
> 기존 `dks`, `dks-common` SVM의 세션 수와 CPU Util 증가를 완화하기 위해 신규 SVM `dks-1AZ-A` 전용 Trident Backend와 StorageClass를 추가한다.
> 
> 기존 StorageClass는 기존 PVC 유지 경로로 남긴다. 대신 신규 PVC 생성 경로에서는 제외한다.
> 
> 이번 작업의 목적은 기존 PVC를 옮기는 것이 아니다. 신규 PVC 증가분이 기존 SVM으로 계속 유입되는 것을 차단하고, 신규 SVM으로 분산시키는 것이다.
> 
> 상태: 설계 결정 완료, 운영 테스트 전. Console 필터링 가능 여부 확인이 선행 과제다.

## 이 문서가 다루는 것

신규 SVM `dks-1AZ-A`를 추가하는 이유와 StorageClass 분리 결정을 정리한다.

상세 구성은 [[02. 설계 및 구성]]에서 다룬다.  
테스트 절차와 Done Criteria는 [[03. 테스트 및 검증]]에서 다룬다.  
운영 리스크, 모니터링, 롤백 기준은 [[리스크 및 운영/01. Risk Register]]에서 관리한다.  
NFS mount option 검토는 [[05. NFS mount option 최적화]]에서 별도로 다룬다.

## 배경

현재 `dks`, `dks-common` Vserver의 세션 수가 많고 CPU Util(%)이 높다. mccC에서는 추가 PVC 프로비저닝이 제한될 정도로 여유가 부족하다.

문제는 기존 부하만이 아니다. 기존 StorageClass를 통해 신규 PVC가 계속 생성되면, 기존 SVM에는 신규 volume, NFS client, 세션 증가분이 계속 누적된다.

신규 SVM 추가만으로는 부족하다. 프로비저닝 경로 자체를 분리해야 신규 PVC가 기존 SVM으로 생성되지 않는다.

## 해결해야 하는 문제

조건:

1. 기존 `dks`, `dks-common` SVM에 신규 PVC 증가분이 계속 유입되지 않아야 한다.
    
2. 기존 PVC와 기존 워크로드의 mount 경로는 유지되어야 한다.
    
3. 신규 PVC는 명시적으로 신규 SVM `dks-1AZ-A` 경로에 생성되어야 한다.
    
4. 사용자가 Console 또는 배포 절차에서 기존 StorageClass를 계속 선택할 수 없도록 통제해야 한다.
    

PV/PVC 마이그레이션이 아니다. 기존 PVC 재바인딩이나 데이터 복사 절차는 범위에 포함하지 않는다.

## 결정 사항

### D-01. 기존 StorageClass를 재지정하지 않는다

기존 StorageClass의 Backend나 SVM 연결을 직접 변경하지 않는다.

기존 SC를 그대로 두고 Backend/SVM만 바꾸면 PVC-SVM 추적이 어렵고 롤백 기준도 모호해진다.

기존 SC는 기존 PVC 유지 경로로 남긴다.

### D-02. 신규 SVM 전용 StorageClass를 추가한다

신규 SVM `dks-1AZ-A`에 연결되는 별도 Trident Backend와 별도 StorageClass를 추가한다.

|구분|결정|
|---|---|
|기존 PVC|기존 StorageClass / 기존 Backend / 기존 SVM 유지|
|신규 PVC|신규 StorageClass / 신규 Backend / `dks-1AZ-A` SVM 사용|
|기존 SVM 부하 제어|기존 StorageClass 신규 사용 차단|
|추적성|StorageClass 이름으로 기존 경로와 신규 경로 구분|
|롤백|신규 StorageClass 노출 또는 사용 중단으로 시작|

^decision-table

기존 PVC 경로는 그대로, 신규 PVC 증가분만 분리한다.

### D-03. 기존 StorageClass는 기존 PVC 유지용으로 격리한다

기존 `dks`, `dks-common` SVM에 연결된 StorageClass는 삭제하지 않는다. 즉시 변경하지도 않는다.

다만 운영 기준상 신규 PVC 생성에는 사용하지 않는다.

운영 반영 전 통제 방안 (하나 이상):

- Console에서 기존 StorageClass가 신규 PVC 생성 화면에 노출되지 않도록 필터링
    
- `metadata.annotations` 기반 필터링 가능 여부 확인
    
- annotation 방식이 불가능할 경우 Console UI 변경, Admission Policy, RBAC, 운영 검토 절차 등 대체 통제 적용
    

세부 통제안과 리스크는 [[리스크 및 운영/01. Risk Register]]에서 관리한다.

### D-04. NFS mount option 최적화는 보조 검증 항목으로 둔다

NFS mount option 조정은 이번 작업의 주된 해결책이 아니다.

1차 효과는 다음 구조에서 나온다.

- 신규 PVC가 기존 SVM으로 생성되지 않는다.
    
- 신규 PVC 증가분이 `dks-1AZ-A` SVM으로 분산된다.
    
- 기존 StorageClass와 신규 StorageClass가 명확히 분리된다.
    

mount option 관련 검토와 적용 가능성은 [[05. NFS mount option 최적화]]에서 별도로 관리한다.

## 기존 StorageClass를 직접 바꾸지 않는 이유

초기에는 기존 SC 이름을 유지하고 Backend/SVM만 바꾸는 방식을 검토했다. 문서 수와 Console 노출 항목이 적다는 장점이 있다.

운영 관점에서는 위험하다. SC 의미가 바뀌면 기존 PVC 영향 범위가 불명확해진다. 동일 SC 이름 아래 다른 SVM 경로가 섞일 수 있고, 장애 시 영향 받은 PVC를 특정하기 어렵다.

그래서 이번 작업은 기존 StorageClass를 바꾸는 방식이 아니라, ==신규 StorageClass를 추가하는 방식(2안)==으로 결정한다.

|항목|1안: 기존 SC 유지, 뒤쪽 SVM/Backend 변경|2안: 기존 SC 유지 + 신규 SC 추가|
|---|---|---|---|
|영향 범위|기존 SC 사용자 전체에 영향 가능|신규 SC 선택 대상 중심으로 제한|
|신규 PVC 분산|동일 SC 내부 라우팅에 의존|신규 SC로 명시적 분산 가능|
|기존 PVC 영향|Backend, Data LIF, export policy 변경 방식에 따라 영향 가능|기존 PVC 경로 유지|
|추적성|동일 SC 이름 아래 경로가 섞일 수 있음|SC 이름으로 기존/신규 경로 구분 가능|
|롤백|기준이 모호해질 수 있음|신규 SC 사용 중단으로 시작 가능|
|운영 통제|기존 SC의 의미가 바뀜|기존 SC는 유지용, 신규 SC는 신규 PVC용으로 역할 분리|

^alternative-table

상세 비교와 검증 절차는 [[03. 테스트 및 검증]]에서 다룬다.

## 완료 후 기대 상태

작업 완료 후 상태:

- `dks`, `dks-common` SVM으로 신규 PVC 증가분이 유입되지 않는다.
    
- 신규 PVC는 `dks-1AZ-A` SVM으로 명시적으로 분산된다.
    
- 기존 PVC와 기존 Pod의 mount 경로 및 동작은 유지된다.
    
- 신규 StorageClass 사용 여부를 Console 또는 정책으로 통제할 수 있다.
    

단, Console 필터링 가능 여부는 아직 테스트 전이다. 불가능할 경우 Admission Policy, RBAC, 운영 절차 통제를 대안으로 적용한다.
