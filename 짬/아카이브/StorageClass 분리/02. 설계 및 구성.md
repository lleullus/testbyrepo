# 설계 및 구성

> [!summary] 설계 요약  
> 기존 `dks`, `dks-common` 경로는 기존 PVC 유지용으로 보존한다.  
> 신규 PVC는 신규 StorageClass를 통해 신규 SVM `dks-1AZ-A`로만 생성되도록 분리한다.
> 
> 이 설계의 핵심은 StorageClass를 하나 더 만드는 것이 아니다. PVC 생성 경로를 기존 SVM과 신규 SVM으로 명확히 분리하고, 기존 경로의 신규 사용을 통제하는 것이다.

## 문서 역할

StorageClass 분리 프로젝트의 설계 계약.

상위 결정과 범위는 [[01. 배경 및 결정]]에서 관리한다.  
테스트 절차와 명령은 [[03. 테스트 및 검증]]에서 관리한다.  
운영 리스크와 롤백 기준은 [[리스크 및 운영/01. Risk Register]]에서 관리한다.  
mount option 검토 결과는 [[05. NFS mount option 최적화]]에서 관리한다.

## 설계 원칙

### P-01. 기존 경로는 재지정하지 않는다

기존 StorageClass와 기존 Trident Backend를 직접 변경하여 SVM을 바꾸지 않는다.

기존 경로는 기존 PVC와 워크로드 안정성을 위해 보존한다. 이 경로는 신규 프로비저닝 경로가 아닌 기존 PVC 유지 경로다.

### P-02. 신규 경로는 명시적으로 분리한다

신규 PVC는 별도 StorageClass와 별도 Trident Backend를 통해 `dks-1AZ-A` SVM에 생성한다.

StorageClass/Backend/SVM 이름이 서로 추적 가능해야 한다. 신규 PVC 생성 후 실제 NetApp volume이 어느 SVM에 생성되었는지도 확인 가능해야 한다.

### P-03. 선택 통제는 사용자 기억에 의존하지 않는다

신규 경로 분리 효과를 얻으려면 사용자가 기존 SC를 선택하지 못하도록 통제해야 한다.

운영 반영 전 통제 방안 (하나 이상):

- Console 필터링
    
- annotation 기반 노출 제어
    
- Admission Policy
    
- RBAC
    
- 운영 검토 절차
    

상세 통제안은 [[리스크 및 운영/01. Risk Register]]에서 관리한다.

### P-04. 테스트 값과 운영 값은 분리한다

현재 값은 테스트 클러스터 `dev-ds-upgrade-member` 기준이다.

운영 환경에서는 SVM, StorageClass, Backend, node CIDR, export-policy, Console 노출 정책이 달라질 수 있다. 운영 반영 전에는 운영용 값을 별도로 확정한다.

### P-05. mount option은 신규 경로 한정 검증 항목으로 둔다

mount option은 이 설계의 핵심 통제 수단이 아니다.

필요할 경우 신규 `dks-1AZ-A` 전용 StorageClass에 한정해 적용하고 검증한다. 관련 상세는 [[05. NFS mount option 최적화]]를 따른다.

## 리소스별 설계 계약

### 신규 Trident Backend

신규 Backend는 `dks-1AZ-A` SVM에 연결되는 전용 Backend로 구성한다.

- 역할: 신규 StorageClass가 사용할 전용 provisioning Backend
    
- 상태 조건: Trident에서 `Online` 상태
    
- 접근 조건: worker node에서 Data LIF 접근 가능
    
- NetApp 조건: export-policy, ACL, client CIDR 반영
    
- 검증 조건: 신규 PVC 생성 후 NetApp 측 volume이 `dks-1AZ-A`에 생성됨
    

manifest 작성 시 검토 항목:

- Management LIF
    
- Data LIF
    
- SVM 이름
    
- storage pool 또는 aggregate 선택 기준
    
- export-policy 적용 범위
    
- 기존 Backend와의 selector 충돌 가능성
    

### 신규 StorageClass

신규 StorageClass는 신규 Backend만 선택해야 한다.

- 이름: `netapp-economy-dev-nfs-sc-100t-1aza`
    
- 대상 Backend: `ontap-nas-economy_1AZ_test`
    
- 대상 SVM: `dks-1AZ-A`
    
- 역할: 신규 PVC 생성 표준 경로
    
- 관계: 기존 StorageClass 대체가 아니라 신규 경로 추가
    

기존 SC와 비교할 항목:

- `reclaimPolicy`
    
- `allowVolumeExpansion`
    
- `volumeBindingMode`
    
- `mountOptions`
    
- backend selector / parameters
    
- annotation / label
    

의도적으로 변경한 값과 동일 유지해야 하는 값을 구분한다.

## 선택 및 통제 메커니즘

|계층|통제 목적|확인 방법|
|---|---|---|
|StorageClass 이름|사용자가 기존/신규 경로를 구분|PVC `storageClassName` 확인|
|Trident Backend 선택|신규 StorageClass가 신규 Backend만 선택|`tridentctl get storageclass`, Backend 매핑 확인|
|NetApp SVM|실제 volume이 `dks-1AZ-A`에 생성|NetApp 측 volume 생성 위치 확인|
|Console/정책 통제|기존 StorageClass 신규 선택 방지|화면 노출 또는 정책 적용 여부 확인|
|Monitoring|적용 후 유입 경로 감시|StorageClass별 PVC 수, SVM별 session/CPU 확인|

Console 필터링 또는 대체 통제가 확정되지 않은 상태에서는 설계가 완료된 것으로 보지 않는다.

## 설계 불변 조건

상세 절차는 [[03. 테스트 및 검증]]을 따른다. 불변 조건:

- 신규 PVC는 신규 StorageClass를 사용한다.
    
- 신규 StorageClass는 신규 Backend를 선택한다.
    
- 신규 Backend는 `dks-1AZ-A` SVM에 연결된다.
    
- 기존 PVC는 기존 경로에서 계속 동작한다.
    
- 기존 StorageClass의 신규 사용은 차단하거나 통제한다.
    
- 신규 경로에서 mount, read/write, 확장, 삭제가 기대한 방식으로 동작한다.
    

## 운영 반영 전 확인 항목

운영 반영 전 확정 항목:

- 운영 환경의 최종 SVM / Backend / StorageClass 이름
    
- 운영 worker node CIDR과 export-policy 적용 범위
    
- Console에서 기존 StorageClass를 숨기거나 제한하는 방식
    
- 신규 StorageClass에 mount option을 포함할지 여부
    
- 신규 StorageClass 사용 중단 기준
    
- 운영 전환 조건
    

운영 전환 순서, 롤백 절차, 모니터링 상세는 [[리스크 및 운영/01. Risk Register]]에서 관리한다.
