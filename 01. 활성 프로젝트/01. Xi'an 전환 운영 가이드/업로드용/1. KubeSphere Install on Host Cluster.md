확인된 문서 간 불일치:

- Host cluster 요약에는 Master `4`로 적혀 있지만 노드 목록과 VIP-A 실서비스 목록에는 Master `3`개만 있습니다. 이 설치 로그에는 Master 수를 임의로 추가하지 않았습니다.
- Xi'an 카탈로그에는 ETCD `/var/lib/etcd`가 `0 GB`로 기록되어 있고 사전 설정 문서에는 ETCD 마운트 확인이 필요하다고 되어 있습니다. 이 설치 로그와 무관하므로 값을 발명하지 않았습니다.
- Xi'an Bastion 사전 설정 문서에는 VIP-A가 확인 필요로 남아 있고 Host 카탈로그에는 `109.156.25.43`이 기록되어 있습니다. 이 설치 로그에는 VIP-A를 사용하지 않아 변환하지 않았습니다.

## 8. 실제 실행 전 확인

1. `xadksbthm01`에서 `SCS_DKS_Kubernetes_Stack-v1.0/Kubesphere-v3.2.1/host/`가 실제 존재하는지 확인합니다.
2. `kubesphere-installer.yaml`의 image 경로가 `xa.dcr.dks.samsungds.net/dspaas-cloud/kubesphere/ks-installer:v3.2.1`인지 확인합니다.
3. `xadksirhm01`~`03`에 `node-type=infra` label과 `node-role.kubernetes.io/infra:NoSchedule` taint가 실제로 존재하는지 확인합니다.
4. 적용 전 `kubectl apply --dry-run=client -f kubesphere-installer.yaml`로 YAML 문법을 확인합니다.
5. 적용 후 아래 명령으로 실제 Pod 이름, IP, NODE를 수집하여 이 문서의 참조 출력에 덮어씁니다.

```bash
k get pod -n kubesphere-system -l app=ks-install -o wide
```

6. 실제 실행 증적에는 private registry 자격 증명, token, password를 기록하지 않습니다.

## 9. 변환 근거 및 임의값 결정

### 9-1. 무엇을 왜 변환했는가

| 변환 대상 | 변환 규칙 | 이유 및 근거 |
|---|---|---|
| `khdksbttmdta11` → `xadksbthm01` | Taylor Bastion prompt를 Xi'an Bastion hostname으로 치환 | Xi'an Host 카탈로그의 Bastion 값이며 설치 명령 실행 주체인 Bastion을 나타냄 |
| `Taylor_DKS_Kubernetes_Stack-v1.0` → `SCS_DKS_Kubernetes_Stack-v1.0` | bundle prefix를 Xi'an 문서 기준으로 치환 | Xi'an Host 설치 문서의 실제 작업 경로 표기와 일치시킴. 다운로드 URL은 미확정이므로 URL은 만들지 않음 |
| `dcr.cloud.samsungds.net/dspaas-cloud` → `xa.dcr.dks.samsungds.net/dspaas-cloud` | registry FQDN만 Xi'an Harbor 기준으로 치환 | Xi'an `local_registry`와 installer image 기준. 잘못 유지하면 image pull 실패 가능 |
| `khdksirtmdta11` → `xadksirhm01` | Pod NODE를 Xi'an infra 첫 번째 노드로 치환 | installer Deployment의 `node-type: infra` 배치와 Xi'an Host 노드 카탈로그에 맞춤 |
| `192.186.84.214` → `172.210.84.214` | Pod CIDR의 첫 두 옥텟을 `172.210`으로 변경하고 host 부분 `84.214` 유지 | Xi'an Host Pod CIDR `172.210.0.0/16` 안의 참조 IP로 만들기 위한 합성값 |
| `ks-installer-5fbbdb79f4-2jdwg` → `ks-installer-65736bd238-f738f` | Xi'an seed로 ReplicaSet hash와 suffix를 재생성 | Pod 이름은 Deployment/ReplicaSet가 실행 시 자동 생성하며 Taylor Pod 이름을 재사용하면 실제 증적으로 오인할 수 있음 |

### 9-2. 임의값을 정한 방법

이번 문서의 동적값은 무작위 문자열을 임의로 찍지 않고, 같은 입력에서 같은 결과가 나오도록 결정론적 참조값으로 정했습니다.

```text
seed = prd-host-pa01-xas|kubesphere-system|ks-installer|v3.2.1|2023-11-06T02:06:36Z
SHA-256(seed) = 65736bd238f738ffbee4814c83dc749fc101f5cf70a51da94eb8b5112e4e20f6
ReplicaSet hash = 앞 10자리 = 65736bd238
Pod suffix = 다음 5자리 = f738f
Pod name = ks-installer-65736bd238-f738f
Pod IP = Xi'an Pod CIDR 172.210.0.0/16 + 원문 host 부분 84.214
```

이 값은 문서의 1:1 출력 형태와 Xi'an 주소 대역을 보여주기 위한 값이지, 실제 클러스터에서 생성될 값을 예측한 값이 아닙니다. 실제값은 반드시 label selector 조회 결과로 대체합니다.

### 9-3. 그대로 둔 시간값과 주의점

`2023-11-06T02:06:36Z`, `134m`, `121m`, `122m`은 사용자가 요청한 동일 타임라인을 유지하기 위해 변경하지 않았습니다. 다만 `namespace AGE 134m`와 `Deployment/Pod AGE 121m/122m`는 하나의 동일한 apply 시점으로는 일관되지 않으므로, 이 문서에서는 실행 증적으로 취급하지 않습니다. Xi'an에서 실제 실행할 때는 CRD의 `CREATIONTIMESTAMP`와 각 리소스의 `AGE`를 한 번에 수집해 교체합니다.

### 9-4. 최종 확정이 필요한 값

- 실제 Xi'an bundle 디렉터리와 다운로드 URL
- 실제 실행 시각 및 CRD/ClusterRole 생성 timestamp
- 실제 `ks-installer` Pod name, Pod IP, 배치 NODE
- Host Master 노드가 3개인지 4개인지에 대한 SCS 최종 승인
- ETCD `/var/lib/etcd` 파일시스템 설계
- VIP-A `109.156.25.43`의 운영 확정 여부
