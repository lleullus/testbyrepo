> [!summary] 요약
> KubeSphere 클러스터에서 API Server 인증서를 포함한 kubeadm 관리 Control Plane 인증서를 갱신하는 절차. Master 노드를 one-by-one 순차적으로 진행 (ma01 → ma02 → ma03)

> [!warning] 주의사항
> - **반드시 one-by-one 순차 진행**: Master 01 정상 확인 후 Master 02, 그 후 Master 03 진행
> - **백업 필수**: 갱신 전 모든 Master 노드의 SSL 디렉토리 및 conf 파일 백업
> - **KubeSphere 재연결 필요**: 인증서 갱신 후 Member Cluster Unbind → Import 재수행

## 이 절차에서 수행하는 작업

이 절차는 Kubernetes Control Plane 구성 요소가 사용하는 인증서를 갱신하고, 갱신된 Client Certificate가 포함된 kubeconfig 파일을 업데이트한다. API Server, Scheduler, Controller Manager는 Static Pod로 실행되므로 인증서 파일만 갱신해서는 실행 중인 프로세스에 새 인증서가 반영되지 않는다. 따라서 인증서 갱신 후 Static Pod를 재생성하여 각 프로세스가 새 인증서를 다시 읽도록 해야 한다.

Control Plane 가용성을 유지하기 위해 Master 노드를 한 대씩 순차적으로 작업한다. 각 노드에서 인증서 갱신, Static Pod 재시작, 상태 및 API Server Health 확인을 완료한 뒤 다음 노드로 진행한다. 모든 Master 노드 작업이 끝나면 Bastion Node의 kubeconfig를 업데이트하고, 갱신된 인증 정보로 KubeSphere Member Cluster를 다시 연결한다.

## 체크리스트

- [ ] **1. Backup Old Certificate Directory** — 모든 Master 노드 백업 완료
- [ ] **2. Renew Master Node 01 Certificates** — ma01 갱신 + 정상 확인
- [ ] **3. Renew Master Node 02 Certificates** — ma02 갱신 + 정상 확인
- [ ] **4. Renew Master Node 03 Certificates** — ma03 갱신 + 정상 확인
- [ ] **5. Update kubeconfig file (Bastion)** — root + dspaas 계정 업데이트
- [ ] **6. Re-join KubeSphere** — Unbind → Import → System pods restart

## 1. Backup Old Certificate Directory

변경 작업 전에 현재 인증서와 kubeconfig 파일의 롤백 사본을 만든다. 갱신 실패 시 원본 파일을 복구하거나 원인 분석에 사용할 수 있도록 모든 Master 노드에서 백업을 완료해야 한다.

### 1-1. SSL 디렉토리 백업 (모든 Master 노드)

모든 Master 노드의 `/etc/kubernetes/ssl` 디렉토리를 백업한다. 이 디렉토리에는 갱신 명령으로 교체되거나 업데이트되는 인증서와 Key 파일이 들어 있다.

**BASTION NODE**:

```bash
for host in ma01 ma02 ma03; do
  ssh $host mkdir -p /tmp/$(date +%Y%m%d)-apibackup
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/ssl /tmp/$(date +%Y%m%d)-apibackup/
done
```

**Verify**:

```bash
for host in ma01 ma02 ma03; do
  ssh $host sudo ls -al /tmp/$(date +%Y%m%d)-apibackup/ssl
done
```

### 1-2. Conf 파일 백업 (모든 Master 노드)

Client Certificate가 포함된 Control Plane kubeconfig 파일을 백업한다. 이 파일들은 갱신 과정에서 다시 생성될 수 있으며 관리자, Scheduler, Controller Manager가 API Server에 연결할 때 사용한다.

**BASTION NODE**:

```bash
for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/admin.conf /tmp/$(date +%Y%m%d)-apibackup/
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/scheduler.conf /tmp/$(date +%Y%m%d)-apibackup/
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/controller-manager.conf /tmp/$(date +%Y%m%d)-apibackup/
done
```

**Verify**:

```bash
for host in ma01 ma02 ma03; do
  ssh $host ls -al /tmp/$(date +%Y%m%d)-apibackup/
done
```

## 2. Renew Master Node 01 Certificates

첫 번째로 Master Node 01만 갱신하고 재시작 및 Health 확인을 모두 완료한다. 한 번에 하나의 Control Plane 노드만 변경함으로써 나머지 Master 노드가 서비스를 계속 제공하도록 한다.

### 2-1. Master Node 01 인증서 갱신

`ma01`에서 kubeadm 관리 인증서 전체를 갱신한다. 이 명령에는 API Server 인증서도 포함된다. 이 단계에서는 디스크의 인증서 파일만 갱신되며, 실행 중인 Static Pod에는 아직 새 인증서가 반영되지 않는다.

**BASTION NODE**:

```bash
ssh ma01 sudo /usr/local/bin/kubeadm certs renew all
```

**Verify**:

```bash
ssh ma01 sudo /usr/local/bin/kubeadm certs check-expiration
```

### 2-2. Static Pods 재시작 (master01)

`ma01`의 기존 Control Plane Pod Sandbox를 제거한다. kubelet이 API Server, Scheduler, Controller Manager Static Pod를 다시 생성하면서 갱신된 인증서 파일을 읽는다.

**BASTION NODE**:

```bash
ssh ma01 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)" | awk "{print \$1}" | xargs -r sudo /usr/local/bin/crictl rmp -f'
```

**Verify**:

```bash
ssh ma01 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)"'
```

### 2-3. Master Node 01 kubeconfig 업데이트

`ma01`의 root 계정 kubeconfig를 갱신된 `admin.conf`로 교체한다. 이후 해당 노드에서 실행하는 관리 명령이 이전 Client Certificate가 아니라 갱신된 인증서를 사용하게 된다.

**BASTION NODE**:

```bash
ssh ma01 sudo cp /etc/kubernetes/admin.conf /root/.kube/config
```

**Verify**:

```bash
ssh ma01 sudo cat /root/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

### 2-4. Static Pod Status 확인 (master01)

재생성된 모든 Control Plane Pod가 Running 상태인지 확인하고, 로컬 API Server의 Ready 및 Live 상태를 점검한다. `ma01`이 정상 상태로 복구되기 전에는 Master Node 02로 진행하지 않는다.

**각 Pod 상태 확인**:

```bash
kubectl get pod -n kube-system | grep api | grep 01
kubectl get pod -n kube-system | grep controller-manager | grep 01
kubectl get pod -n kube-system | grep scheduler | grep 01
```

**Events 확인**:

```bash
POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-apiserver-" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-controller-manager" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-scheduler" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10
```

**API Server Health 확인**:

```bash
# readyz
ssh ma01 curl -k https://localhost:6443/readyz?verbose

# livez
ssh ma01 curl -k https://localhost:6443/livez?verbose
```

> [!note] 다음 단계 전 확인
> Master 01의 모든 Pod이 Running 상태이고 API Server health check가 성공한 후 Master 02 진행

## 3. Renew Master Node 02 Certificates

Master Node 01이 정상임을 확인한 후 Master Node 02에서 동일한 갱신 순서를 수행한다. `ma02`를 재시작하는 동안 나머지 Master 노드가 Control Plane 요청을 처리한다.

### 3-1. Master Node 02 인증서 갱신

`ma02`에서 kubeadm 관리 인증서 전체를 갱신한다. 갱신된 파일은 다음 단계에서 Control Plane Static Pod를 재생성하기 전까지 디스크에만 반영되어 있다.

**BASTION NODE**:

```bash
ssh ma02 sudo /usr/local/bin/kubeadm certs renew all
```

**Verify**:

```bash
ssh ma02 sudo /usr/local/bin/kubeadm certs check-expiration
```

### 3-2. Static Pods 재시작 (master02)

`ma02`의 기존 Control Plane Pod Sandbox를 제거하여 kubelet이 Static Pod를 다시 만들고 갱신된 인증서로 구성 요소를 시작하도록 한다.

**BASTION NODE**:

```bash
ssh ma02 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)" | awk "{print \$1}" | xargs -r sudo /usr/local/bin/crictl rmp -f'
```

**Verify**:

```bash
ssh ma02 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)"'
```

### 3-3. Master Node 02 kubeconfig 업데이트

`ma02`의 root 계정 kubeconfig를 갱신된 `admin.conf`로 교체하여 로컬 관리 작업이 새 Client Certificate를 사용하도록 한다.

**BASTION NODE**:

```bash

```

**Verify**:

```bash
ssh ma02 sudo cat /root/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

### 3-4. Static Pod Status 확인 (master02)

재생성된 Static Pod가 Running 상태인지 확인하고 로컬 API Server Health Endpoint가 정상인지 점검한다. `ma02`가 정상 상태로 복구된 후에만 Master Node 03으로 진행한다.

**각 Pod 상태 확인**:

```bash
kubectl get pod -n kube-system | grep api | grep 02
kubectl get pod -n kube-system | grep controller-manager | grep 02
kubectl get pod -n kube-system | grep scheduler | grep 02
```

**Events 확인**:

```bash

  | grep "^pod/kube-apiserver-" \
  | grep "02$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-controller-manager" \

POD=$(kubectl get pods -n kube-system -o name \
```

## 4. Renew Master Node 03 Certificates

Master Node 01과 02가 모두 정상으로 복구된 후 마지막 Master 노드를 갱신한다. `ma03`에서도 동일한 검증을 완료하면 모든 Control Plane 노드의 인증서 갱신이 끝난다.

### 4-1. Master Node 03 인증서 갱신

`ma03`에서 kubeadm 관리 인증서 전체를 갱신한다. 이전 노드와 마찬가지로 Static Pod를 다시 생성하기 전까지 실행 중인 구성 요소는 기존 인증서를 계속 사용한다.

**BASTION NODE**:

```bash
ssh ma03 sudo /usr/local/bin/kubeadm certs renew all
```

**Verify**:


`ma03`의 기존 Control Plane Pod Sandbox를 제거하여 kubelet이 Static Pod를 다시 생성하고 갱신된 인증서를 로드하도록 한다.

**BASTION NODE**:


`ma03`의 root 계정 kubeconfig를 갱신된 `admin.conf`로 교체하여 해당 노드의 관리 명령이 갱신된 Client Certificate로 인증하도록 한다.

## 5. Update kubeconfig file (Bastion Node)

Bastion Node의 기존 kubeconfig에는 갱신 전 Client Certificate가 포함되어 있다. 정상 상태인 Master 노드의 갱신된 `admin.conf`로 root 및 `dspaas` 계정의 kubeconfig를 교체하여 Bastion에서 실행하는 `kubectl` 명령이 계속 정상 인증되도록 한다.

### 5-1. Bastion Node Root 계정 kubeconfig 업데이트

`ma01`의 갱신된 `admin.conf`를 Bastion Node root 계정의 kubeconfig 경로로 복사한다. Verify 명령으로 kubeconfig에 포함된 Client Certificate의 만료일이 갱신되었는지 확인한다.

**BASTION NODE**:

```bash
ssh ma01 'sudo cp /etc/kubernetes/admin.conf /tmp/admin.conf && sudo chown $(whoami):$(whoami) /tmp/admin.conf'
scp ma01:/tmp/admin.conf /tmp/config
sudo cp /tmp/config /root/.kube/config
sudo ls -al /root/.kube/config
```

**Verify**:

```bash
sudo cat /root/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

### 5-2. Bastion Node dspaas 계정 kubeconfig 업데이트

`dspaas` 계정의 kubeconfig도 동일한 갱신된 `admin.conf`로 업데이트한다. `dspaas` 계정으로 실행하는 자동화 및 운영 명령이 새 클러스터 인증 정보와 일치하도록 한다.

**BASTION NODE**:

```bash
ssh ma01 sudo cat /etc/kubernetes/admin.conf > /app/dspaas/.kube/config
```

**Verify**:

```bash
cat /app/dspaas/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

## 6. Re-join KubeSphere

Kubernetes 인증서와 Bastion kubeconfig를 갱신한 후 KubeSphere에도 새 클러스터 인증 정보를 반영해야 한다. 기존 Member Cluster 연결을 해제하고 갱신된 kubeconfig로 다시 Import한 뒤, KubeSphere System 구성 요소를 재시작하여 새 인증 정보로 연결을 초기화한다.

### 6-1. Member Cluster Unbind

이전 인증 정보를 참조하는 기존 Member Cluster 등록을 KubeSphere에서 해제한다. Import 단계에서 동일한 클러스터 Identity를 사용해야 하므로 Cluster Name과 Tag를 정확히 기록한다.

1. KubeSphere Console에 로그인
2. **Platform** → **Cluster Management** → Unbind할 Member Cluster 선택
3. 좌측 메뉴에서 **Cluster Settings** → **Basic Information** → **Unbind Cluster** 메뉴에서 **Unbind** 클릭
4. **Note**: Exact name과 tag를 기록 (다음 단계에서 필요)
5. **"I understand the risks of this operation"** 체크 후 Unbind 실행

### 6-2. Member Cluster Import

기록한 Cluster Name과 Tag, 갱신된 kubeconfig를 사용하여 Member Cluster를 다시 Import한다. 이 작업으로 KubeSphere의 클러스터 연결 정보에 새 Client Certificate가 등록된다.

1. **Cluster Management** → **Add Cluster** 클릭
2. Unbind 시 기록한 Cluster name과 tag 사용
3. kubeconfig 파일 내용 복사 & 붙여넣기
4. **Create** 클릭

### 6-3. KubeSphere System Pods 재시작

각 Member Cluster의 KubeSphere System Deployment를 재시작하여 Import 이후 연결을 다시 초기화한다. 재시작된 모든 Pod가 정상 상태로 복구되는지 확인한다.

**BASTION NODE** (각 Member Cluster에서 실행):

```bash
kubectl rollout restart deploy -n kubesphere-system ks-apiserver ks-console ks-controller-manager
```

**Verify**:

```bash
kubectl get po -n kubesphere-system
```
