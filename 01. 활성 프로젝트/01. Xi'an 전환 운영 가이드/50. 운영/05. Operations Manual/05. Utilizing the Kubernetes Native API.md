> [!summary] 요약
> Kubernetes API 서버를 Ingress를 통해 외부로 노출하고, ServiceAccount 기반 인증으로 API 접근을 제어하는 절차

> [!note] 운영 선례
> DKS 운영 환경에는 Prometheus를 Kubernetes Native API로 노출한 선례가 있다. 이 문서의 `Service -> Ingress -> kube-apiserver -> RBAC` 패턴과 `인증 없이 호출 시 403` 검증 방식은 그 운영 사례와 동일한 성격이다. 다만 이 선례는 `Native API 진입 경로와 권한 제공 방식`의 운영 근거일 뿐, 특정 소비 시스템의 전체 기능 대체 범위를 입증하는 근거는 아니다.

|-------|-----|------|-----------|------|

## 1. kube-apiserver Service 생성

Kubernetes Native API는 Kubernetes의 핵심 구성 요소로, 애플리케이션을 정의 및 배포하고 원하는 상태를 유지하는 역할을 담당한다. 표준 HTTP 동사(POST, PUT, PATCH, GET 등)를 통해 리소스 조회, 생성, 갱신을 수행할 수 있다.

외부에서 특정 Kubernetes 클러스터 API에 접근하려면 Ingress 리소스를 사용하여 kube-apiserver를 노출할 수 있다.

kube-apiserver static Pod를 Service로 노출해야 Ingress 리소스가 참조 가능.

### 1-1. Service 리소스 정의

**service.yaml**:

```yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    component: kube-apiserver
    tier: control-plane
  name: kube-apiserver
  namespace: kube-system
spec:
  ipFamilyPolicy: SingleStack
  ports:
    - port: 443
      protocol: TCP
      targetPort: 6443
  selector:
    component: kube-apiserver
    tier: control-plane
  type: ClusterIP
```

**핵심**:
- 라벨 `component: kube-apiserver`, `tier: control-plane` — static Pod 라벨과 일치해야 함
- `port: 443` (HTTPS), `targetPort: 6443` (kube-apiserver 포트)
- `type: ClusterIP`

### 1-2. static Pod 라벨 확인

```bash
kubectl get po -n kube-system kube-apiserver-xadksmamp01 -o yaml | grep labels: -A2
```

```
labels:
  component: kube-apiserver
  tier: control-plane
```

### 1-3. Service 생성 및 확인

```bash
kubectl get service -n kube-system kube-apiserver
```

```
NAME            TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
kube-apiserver  ClusterIP   10.102.90.13   <none>        443/TCP   4s
```

```bash
kubectl describe service -n kube-system kube-apiserver
```

```
Name:              kube-apiserver
Namespace:         kube-system
Labels:            component=kube-apiserver
                   tier=control-plane

Session Affinity:  None
```

> [!note] 확인 사항
> Endpoints는 kube-apiserver Pod IP와 일치해야 함

## 2. Ingress로 kube-apiserver对外 노출

Ingress 리소스를 생성하여 외부 도메인으로 API 서버 접근 가능.

### 2-1. Ingress 리소스 정의

**ingress.yaml**:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    kubernetes.io/ingress.class: nginx
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
    nginx.ingress.kubernetes.io/ssl-passthrough: "true"
  labels:
    component: kube-apiserver
    tier: control-plane
  name: kube-apiserver-ingress
  namespace: kube-system
spec:
  rules:
    - host: nativeapi.xaprdpa01.apps.dks.samsungds.net
      http:
        paths:
          - backend:
              service:
                name: kube-apiserver
                port:
                  number: 443
            path: /
            pathType: Prefix
```

**핵심**:
- `ssl-passthrough: "true"` — SSL 종료 없이 백엔드로 전달
- `force-ssl-redirect: "true"` — HTTP를 HTTPS로 리다이렉트
- 호스트명: `nativeapi.xaprdpa01.apps.dks.samsungds.net`

### 2-2. Source IP/CIDR 제한

Native API를 외부로 노출하는 경우 접근 통제는 필수다. 최소한 호출 주체가 위치한 Source IP/CIDR만 허용해야 한다.

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/whitelist-source-range: "10.0.0.0/24,10.10.0.0/24"
```

호출 주체 CIDR이 확정되지 않았다면 Ingress 생성 완료로 간주하지 않는다.

### 2-3. Ingress 생성 및 확인

```bash

```

```

```

```bash

```


## 3. API 접근 (인증)

Ingress 도메인으로 API 접근 시 ServiceAccount 기반 인증 토큰 필요.

> [!warning] 적용 경계
> Prometheus 운영 선례처럼 이 절차는 `Native API 경로와 권한 기반 제공`까지만 다룬다. 특정 시스템이 어떤 리소스를 어떤 순서로 호출할지, 어떤 기본값을 쓸지, 어떤 응답 구조를 유지할지는 이 문서 범위를 벗어난다.

> [!warning] RBAC 설계 원칙
> 어떤 시스템의 RBAC을 설계할 때는 `현재 눈에 보이는 호출 몇 개에 대한 최소 권한`부터 확정하면 안 된다. 먼저 그 시스템이 기존 중간 계층 없이도 완전하게 대체되어야 하는 기능 범위를 식별하고, 그 범위 안에서 필요한 권한을 산정한 뒤 least privilege로 줄여야 한다.

### 3-1. 인증 없이 접근 시도 (실패)

```bash
curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
```

```json
{
  "kind": "Status",
  "apiVersion": "v1",
  "status": "Failure",
  "message": "pods is forbidden: User \"system:anonymous\" cannot list resource \"pods\" in API group \"\" at the cluster scope",
  "reason": "Forbidden",
  "code": 403
}
```

### 3-2. ServiceAccount 및 Role 생성

**token.yaml**:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: test-role
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: test-rb
  namespace: default
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: test-role
subjects:
  - kind: ServiceAccount
    name: test-sa
    namespace: default
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: test-sa
  namespace: default
```
