# Kubernetes Native API 접속 및 권한 오류

## Index

Xi'an Native API 호출이 안 되면 **DNS/VIP-B → Ingress → kube-apiserver Service/Endpoint → Token → RBAC** 순서로 확인한다.

대표 예시는 `prd-apps-pa01-xas`를 사용한다.

```text
nativeapi.xaprdpa01.apps.dks.samsungds.net
→ VIP-B 109.156.25.60
→ Router 109.156.22.61 / 109.156.22.62 / 109.156.22.63
→ kube-system/kube-apiserver Service :443
→ Master 109.156.22.58 / 109.156.22.59 / 109.156.22.60 :6443
→ ServiceAccount test-sa + RBAC
```

기존 Native API 운영 문서에서 `test-sa`, `test-role`, `test-rb`, `default` Namespace로 Pod `get/list`를 검증한 기록을 기준으로 한다. FQDN, Router/Master IP, Service/Ingress 이름은 기존 Xi'an 기록값을 사용하고, Pod/Secret suffix와 AGE 같은 동적 값은 화면 형태를 보여주기 위한 참조값이다. Token 원문은 문서에 기록하지 않는다.

## 1. FQDN이 안 풀리거나 TCP 443이 연결되지 않는 경우

먼저 사용자 위치에서 DNS와 VIP-B `443`을 확인한다.

```console
[user@api-client ~]$ getent hosts nativeapi.xaprdpa01.apps.dks.samsungds.net
109.156.25.60   nativeapi.xaprdpa01.apps.dks.samsungds.net

[user@api-client ~]$ nc -vz -w 3 109.156.25.60 443
Ncat: Version 7.92 ( https://nmap.org/ncat )
Ncat: Connected to 109.156.25.60:443.
Ncat: 0 bytes sent, 0 bytes received in 0.01 seconds.
```

### DNS가 다른 IP를 반환하는 경우 조치

`prd-apps-pa01-xas` Native API는 Ingress VIP-B `109.156.25.60` 경로를 사용한다. DNS가 다른 Cluster VIP나 과거 주소를 가리키면 Native API DNS를 `109.156.25.60` 경로로 수정한다.

### TCP 443이 timeout인 경우 조치

DNS가 맞는데 `109.156.25.60:443`이 timeout이면 Kubernetes RBAC을 바꾸지 않는다. 먼저 **API Client Source IP → VIP-B 109.156.25.60:443** 방화벽/LB 경로와 승인된 source IP 제한을 확인한다.

```text
DNS 실패
→ DNS 수정

DNS 정상 + 443 timeout
→ 방화벽 / LB / source IP 제한 확인

443 Connected
→ Ingress와 kube-apiserver Service 확인
```

## 2. TCP 443은 열리는데 API 응답이 없거나 502/503이 발생하는 경우

Bastion `xadksbtmp01`에서 Ingress를 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl get ingress -n kube-system kube-apiserver-ingress
NAME                     CLASS    HOSTS                                           ADDRESS                                   PORTS   AGE
kube-apiserver-ingress   <none>   nativeapi.xaprdpa01.apps.dks.samsungds.net     109.156.22.61,109.156.22.62,109.156.22.63   80      5m
```

Host는 `nativeapi.xaprdpa01.apps.dks.samsungds.net`, Address는 `xadksrtmp01~03`의 `109.156.22.61~63`이어야 한다.

Service Backend도 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl describe service -n kube-system kube-apiserver
Name:              kube-apiserver
Namespace:         kube-system
Selector:          component=kube-apiserver,tier=control-plane
Port:              <unset>  443/TCP
TargetPort:        6443/TCP
Endpoints:         109.156.22.58:6443,109.156.22.59:6443,109.156.22.60:6443
```

### Service Endpoint가 비어 있는 경우 조치

kube-apiserver Pod label을 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl get pod -n kube-system -l component=kube-apiserver -o wide
NAME                           READY   STATUS    RESTARTS   AGE   IP              NODE
kube-apiserver-xadksmamp01     1/1     Running   0          30d   109.156.22.58   xadksmamp01
kube-apiserver-xadksmamp02     1/1     Running   0          30d   109.156.22.59   xadksmamp02
kube-apiserver-xadksmamp03     1/1     Running   0          30d   109.156.22.60   xadksmamp03
```

Pod는 있는데 Service Endpoint가 없으면 Service selector를 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl edit service kube-apiserver -n kube-system
```

Service selector는 kube-apiserver Pod label과 맞아야 한다.

```yaml
selector:
  component: kube-apiserver
  tier: control-plane
```

저장 후 다시 `kubectl describe service -n kube-system kube-apiserver`에서 `109.156.22.58~60:6443` Endpoint가 생겼는지 확인한다.

### Ingress Backend가 다른 Service/Port를 가리키는 경우 조치

```console
[dspaas@xadksbtmp01 ~]$ kubectl describe ingress -n kube-system kube-apiserver-ingress
Name:             kube-apiserver-ingress
Namespace:        kube-system
Address:          109.156.22.61,109.156.22.62,109.156.22.63
Rules:
  Host                                           Path  Backends
  ----                                           ----  --------
  nativeapi.xaprdpa01.apps.dks.samsungds.net    /     kube-apiserver:443 (109.156.22.58:6443,109.156.22.59:6443,109.156.22.60:6443)
Annotations:
  nginx.ingress.kubernetes.io/force-ssl-redirect: true
  nginx.ingress.kubernetes.io/ssl-passthrough: true
```

Host, Service, Port가 다르면 Ingress를 수정한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl edit ingress kube-apiserver-ingress -n kube-system
```

정상 기준은 다음 세 값이다.

```text
Host    nativeapi.xaprdpa01.apps.dks.samsungds.net
Service kube-apiserver
Port    443
```

## 3. Token 없이 호출했을 때 `403 system:anonymous`가 나오는 경우

다음 응답은 **정상적인 무인증 차단**이다.

```console
[user@api-client ~]$ curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
{
  "kind": "Status",
  "apiVersion": "v1",
  "status": "Failure",
  "message": "pods is forbidden: User \"system:anonymous\" cannot list resource \"pods\" in API group \"\" at the cluster scope",
  "reason": "Forbidden",
  "code": 403
}
```

이 경우 Ingress나 RBAC을 고칠 필요가 없다. 승인된 ServiceAccount Token으로 다시 호출한다.

환경에 따라 무인증 요청은 `401 Unauthorized`로 거부될 수도 있다. **무인증 요청이 정상 데이터를 반환하는 경우가 문제**다.

## 4. Token을 넣었는데 `401 Unauthorized`가 발생하는 경우

ServiceAccount와 연결된 Token Secret을 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl get serviceaccount test-sa -n default
NAME      SECRETS   AGE
test-sa   1         30d

[dspaas@xadksbtmp01 ~]$ kubectl get secret -n default | grep test-sa-token
test-sa-token-hbtb5   kubernetes.io/service-account-token   3   30d
```

Secret 존재와 Token 필드만 확인한다. Token 값은 화면이나 문서에 남기지 않는다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl describe secret test-sa-token-hbtb5 -n default
Name:         test-sa-token-hbtb5
Namespace:    default
Type:         kubernetes.io/service-account-token

Data
====
ca.crt:     1099 bytes
namespace:  7 bytes
token:      <token omitted>
```

Pod suffix와 마찬가지로 Token Secret suffix는 실행 시점에 달라질 수 있으므로 현재 `kubectl get secret`에 나온 이름을 사용한다.

### `test-sa`에 Token Secret이 없는 경우 조치

Xi'an Kubernetes `v1.22.10` 기준으로 새 ServiceAccount Token Secret을 생성할 수 있다.

```console
[dspaas@xadksbtmp01 ~]$ cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Secret
metadata:
  name: test-sa-token-new
  namespace: default
  annotations:
    kubernetes.io/service-account.name: test-sa
type: kubernetes.io/service-account-token
EOF
secret/test-sa-token-new created

[dspaas@xadksbtmp01 ~]$ kubectl get secret test-sa-token-new -n default
NAME                TYPE                                  DATA   AGE
test-sa-token-new   kubernetes.io/service-account-token   3      8s
```

새 Token은 승인된 비밀 전달 경로로 사용자 또는 연동 시스템에 전달한다. 채팅이나 문서에 Token 원문을 넣지 않는다.

## 5. Token 인증은 되지만 `403 Forbidden`이 발생하는 경우

이 경우는 **인증 실패가 아니라 RBAC 권한 부족**이다.

기존 `test-role`의 권한은 Pod `get/list`다. Role과 RoleBinding을 같이 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl describe role test-role -n default
Name:         test-role
PolicyRule:
  Resources  Non-Resource URLs  Resource Names  Verbs
  ---------  -----------------  --------------  -----
  pods       []                 []              [get list]

[dspaas@xadksbtmp01 ~]$ kubectl describe rolebinding test-rb -n default
Name:         test-rb
Role:
  Kind:  Role
  Name:  test-role
Subjects:
  Kind            Name       Namespace
  ----            ----       ---------
  ServiceAccount  test-sa    default

[dspaas@xadksbtmp01 ~]$ kubectl auth can-i --as=system:serviceaccount:default:test-sa list pods -n default
yes

[dspaas@xadksbtmp01 ~]$ kubectl auth can-i --as=system:serviceaccount:default:test-sa create deployments -n default
no
```

Role은 맞는데 `test-rb`의 Subject가 다른 ServiceAccount를 가리키면 `kubectl edit rolebinding test-rb -n default`로 `test-sa / default`를 연결한다. Pod 조회는 성공하고 Deployment 생성이 `403`인 것은 현재 Role 기준으로 정상이다.

### 업무상 필요한 API가 `403`인 경우 조치

먼저 필요한 **Resource + Verb + Namespace**를 확정한다. 그다음 기존 Role에 승인된 권한만 추가한다.

예를 들어 Deployment 조회만 승인된 경우:

```console
[dspaas@xadksbtmp01 ~]$ kubectl edit role test-role -n default
```

```yaml
- apiGroups:
    - apps
  resources:
    - deployments
  verbs:
    - get
    - list
```

저장 후 실제 권한을 다시 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl auth can-i --as=system:serviceaccount:default:test-sa list deployments -n default
yes
```

`cluster-admin`을 부여하거나 필요하지 않은 `delete`, `create`, `patch` 권한을 한꺼번에 추가하지 않는다.

## 6. 허용된 Source IP인데 Native API에 들어오지 못하는 경우

Native API Ingress는 TLS passthrough를 사용한다.

```text
nginx.ingress.kubernetes.io/ssl-passthrough: true
```

이 구조에서는 `whitelist-source-range` annotation이 실제 차단 지점으로 동작하는지 **현장 검증 없이 가정하지 않는다.** 기존 Native API 설계 문서도 SSL passthrough에서는 source IP 제한의 실제 강제 지점을 확인하도록 규정한다.

허용된 Source IP가 차단되거나 허용하지 않은 Source IP가 통과하면 다음 순서로 처리한다.

```text
1. 승인된 호출 Source CIDR 확인
2. Ingress의 실제 source 제한 동작 확인
3. Ingress에서 강제되지 않으면 LB/방화벽 등 상위 네트워크 제어에서 제한
4. 동일 Source에서 다시 TCP 443 / API 호출 검증
```

승인된 CIDR이 확정되지 않은 상태에서 `0.0.0.0/0`으로 열거나 임의 대역을 추가하지 않는다.

## 7. 조치 후 정상 확인

경로부터 권한까지 다시 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl describe service -n kube-system kube-apiserver
Endpoints:         109.156.22.58:6443,109.156.22.59:6443,109.156.22.60:6443

[dspaas@xadksbtmp01 ~]$ kubectl get ingress -n kube-system kube-apiserver-ingress
NAME                     CLASS    HOSTS                                           ADDRESS
kube-apiserver-ingress   <none>   nativeapi.xaprdpa01.apps.dks.samsungds.net     109.156.22.61,109.156.22.62,109.156.22.63
```

사용자 위치에서는 무인증 차단과 Token 호출을 각각 확인한다.

```console
[user@api-client ~]$ curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
...
"reason": "Forbidden",
"code": 403

[user@api-client ~]$ curl -k -H "Authorization: Bearer $(cat nativeapi.token)" https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
{
  "kind": "PodList",
  "apiVersion": "v1",
  "items": [
    {
      "metadata": {
        "name": "ing-test-686849b47f-qvks4",
        "namespace": "default"
      }
    }
  ]
}
```

마지막으로 허용/비허용 권한을 같이 확인한다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl auth can-i --as=system:serviceaccount:default:test-sa list pods -n default
yes
[dspaas@xadksbtmp01 ~]$ kubectl auth can-i --as=system:serviceaccount:default:test-sa delete pods -n default
no
```

## 결과별 조치

| 확인 결과 | 조치 |
|---|---|
| FQDN이 잘못된 IP로 해석 | 대상 Cluster VIP-B로 DNS 수정 |
| VIP-B `443` timeout | Source IP → VIP-B 방화벽/LB/source 제한 확인 |
| Service Endpoint 없음 | kube-apiserver Pod label과 Service selector 수정 |
| Ingress Host/Backend 오류 | Native API FQDN + `kube-apiserver:443`으로 수정 |
| 무인증 `401/403` | 정상 차단. Token으로 재호출 |
| Token 사용 시 `401` | ServiceAccount/Token Secret 재확인, 필요 시 새 Token Secret 생성 |
| Token 사용 시 `403` | 필요한 Resource/Verb/Namespace만 RBAC 추가 |
| Source 제한이 의도대로 동작하지 않음 | 실제 강제 지점을 검증하고 LB/방화벽 등 승인된 제어점에서 제한 |

## 정상 확인

```text
FQDN → 대상 VIP-B
→ TCP 443 Connected
→ Ingress Address = 대상 Router 3대
→ kube-apiserver Service Endpoint = Master 3대 :6443
→ 무인증 요청 차단
→ Token 요청 성공
→ 허용 권한 yes / 비허용 권한 no
```
