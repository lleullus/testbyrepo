# When a NetApp NFS PVC Is Bound but Pod Mount Fails

## Index

Use this procedure when a `scs-netapp-qtree-nfs-sc-delete` PVC in Xi'an is `Bound`, but a Pod using the PVC remains in `ContainerCreating` and the Events show `FailedMount`, `error mounting NFS volume`, or `exit status 32`.

## 1. Confirm that the PVC is Bound and only the Pod has `FailedMount`

If the status is as follows, PVC provisioning is complete. Do not recreate the PVC or StorageClass.

```console
[dspaas@xadksbthm01 ~]$ kubectl get pvc qtree-volume
NAME           STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS                    AGE
qtree-volume   Bound    pvc-c3c5421e-b6b0-4a7e-beb5-29679a65a511   2Gi        RWX            scs-netapp-qtree-nfs-sc-delete  5m

[dspaas@xadksbthm01 ~]$ kubectl get pod -o wide | grep tomcat-deployment3
tomcat-deployment3-59b6769d74-2znvv   0/1   ContainerCreating   0   4m   <none>   xadkswkmp01

[dspaas@xadksbthm01 ~]$ kubectl describe pod tomcat-deployment3-59b6769d74-2znvv
Events:
  Type     Reason       Age   From     Message
  ----     ------       ----  ----     -------
  Warning  FailedMount  42s   kubelet  MountVolume.SetUp failed for volume "pvc-c3c5421e-b6b0-4a7e-beb5-29679a65a511": mount failed: exit status 32
  Warning  FailedMount  42s   kubelet  error mounting NFS volume 109.156.24.25:/trident_qtree_pool_k8s_XBHSYSSFEN/k8s_pvc_c3c5421e_b6b0_4a7e_beb5_29679a65a511 on mountpoint ...
```

## 2. Confirm that the Trident backend completed volume creation

If `STATE=online` and the PVC is already `Bound`, treat the Trident volume/qtree creation stage as complete. If the backend is `offline`, restore the backend connection before checking Node mount behavior.

```console
[dspaas@xadksbthm01 ~]$ tridentctl get backend -n trident
+-----------+-------------------+--------------------------------------+--------+---------+
| NAME      | STORAGE DRIVER    | UUID                                 | STATE  | VOLUMES |
+-----------+-------------------+--------------------------------------+--------+---------+
| DKS_QTREE | ontap-nas-economy | 2ef6f3c3-48a1-44b4-95bb-db47dc001f75 | online | 4       |
+-----------+-------------------+--------------------------------------+--------+---------+
```

## 3. Check the Data LIF route and TCP 2049 from the Node running the Pod

Check which source IP is actually selected when traffic goes to the Data LIF.

```console
[root@xadkswkmp01 ~]# ip route get 109.156.24.25
109.156.24.25 via 109.156.24.1 dev ens224 src 109.156.24.67 uid 0

[root@xadkswkmp01 ~]# ip route get 109.156.24.26
109.156.24.26 via 109.156.24.1 dev ens224 src 109.156.24.67 uid 0
```

`src` must be the storage NIC address.

```text
Normal
109.156.24.25/26 → storage NIC → 109.156.24.67

Abnormal
109.156.24.25/26 → management NIC → 109.156.22.67
```

If `src` is a management NIC address such as `109.156.22.67`, this is a Node routing issue. Correct the route/default metric so Data LIF traffic leaves through the storage NIC, then verify again with `ip route get`.

If the route is correct, check the NFS port.

```console
[root@xadkswkmp01 ~]# nc -vz -w 3 109.156.24.25 2049
Ncat: Version 7.92 ( https://nmap.org/ncat )
Ncat: Connected to 109.156.24.25:2049.
Ncat: 0 bytes sent, 0 bytes received in 0.01 seconds.

[root@xadkswkmp01 ~]# nc -vz -w 3 109.156.24.26 2049
Ncat: Version 7.92 ( https://nmap.org/ncat )
Ncat: Connected to 109.156.24.26:2049.
Ncat: 0 bytes sent, 0 bytes received in 0.01 seconds.
```

```text
Route abnormal
→ Correct Node routing

Route normal + TCP 2049 timeout
→ Check Storage Network / firewall / Data LIF path

Route normal + TCP 2049 Connected
→ Mount the same NFS export path directly on the Node
```

## 4. Mount the same NFS export path directly on the Node

Check whether the Node itself can mount the same NFS export path.

```console
[root@xadkswkmp01 ~]# mkdir -p /mnt/nfs-test
[root@xadkswkmp01 ~]# mount -t nfs 109.156.24.25:/trident_qtree_pool_k8s_XBHSYSSFEN/k8s_pvc_c3c5421e_b6b0_4a7e_beb5_29679a65a511 /mnt/nfs-test
```

If the mount succeeds, verify it immediately.

```console
[root@xadkswkmp01 ~]# df -h /mnt/nfs-test
Filesystem                                                                                           Size  Used Avail Use% Mounted on
109.156.24.25:/trident_qtree_pool_k8s_XBHSYSSFEN/k8s_pvc_c3c5421e_b6b0_4a7e_beb5_29679a65a511       2.0G     0  2.0G   0% /mnt/nfs-test

[root@xadkswkmp01 ~]# touch /mnt/nfs-test/nfs-node-check
[root@xadkswkmp01 ~]# ls -l /mnt/nfs-test/nfs-node-check
-rw-r--r--. 1 root root 0 Aug 13 17:20 /mnt/nfs-test/nfs-node-check
```

If the direct mount succeeds, Node → Data LIF → export path → read/write has passed. Storage Network and NFS export access are therefore working. If the Pod still shows `FailedMount`, check kubelet errors again.

```console
[root@xadkswkmp01 ~]# journalctl -u kubelet --since "10 min ago" | grep pvc-c3c5421e-b6b0-4a7e-beb5-29679a65a511
```

Return to the Bastion and check Trident Node information as well.

```console
[dspaas@xadksbthm01 ~]$ kubectl get nodes -o wide
NAME          STATUS   ROLES    AGE   VERSION    INTERNAL-IP
xadkswkmp01   Ready    <none>   ...   v1.22.10   109.156.22.67

[dspaas@xadksbthm01 ~]$ tridentctl get nodes -n trident -o yaml
```

If the direct mount fails, use the original error to narrow the scope.

```text
Connection timed out / No route to host
→ Check Node route / Storage Network / Data LIF path

access denied by server
→ Ask Storage to verify that the actual NFS source IP is allowed by the export policy

No such file or directory
→ Ask to verify that the export path in the Event matches the actual qtree/export path

Other mount.nfs errors
→ Check together with the Storage owner
```

## 5. Recheck Pod Mount and Read/Write after the fix

Kubelet retries the mount, so first check the Pod status and Events again.

```console
[dspaas@xadksbthm01 ~]$ kubectl get pod -o wide | grep tomcat-deployment3
tomcat-deployment3-59b6769d74-2znvv   1/1   Running   0   12m   172.211.3.5   xadkswkmp01

[dspaas@xadksbthm01 ~]$ kubectl describe pod tomcat-deployment3-59b6769d74-2znvv
```

If no new `FailedMount` occurs and the Pod is `Running`, verify the actual mount inside the container.

```console
[dspaas@xadksbthm01 ~]$ kubectl exec -it tomcat-deployment3-59b6769d74-2znvv -- df -h /test
Filesystem                                                                                           Size  Used Avail Use% Mounted on
109.156.24.25:/trident_qtree_pool_k8s_XBHSYSSFEN/k8s_pvc_c3c5421e_b6b0_4a7e_beb5_29679a65a511       2.0G     0  2.0G   0% /test

[dspaas@xadksbthm01 ~]$ kubectl exec -it tomcat-deployment3-59b6769d74-2znvv -- touch /test/nfs-mount-check
[dspaas@xadksbthm01 ~]$ kubectl exec -it tomcat-deployment3-59b6769d74-2znvv -- ls -l /test/nfs-mount-check
-rw-r--r--. 1 root root 0 Aug 13 17:20 /test/nfs-mount-check
```
