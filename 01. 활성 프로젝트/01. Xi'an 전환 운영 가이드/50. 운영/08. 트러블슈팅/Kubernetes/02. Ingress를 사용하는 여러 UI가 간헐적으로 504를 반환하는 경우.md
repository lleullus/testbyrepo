# Ingress를 사용하는 여러 UI가 간헐적으로 504를 반환하는 경우

## Index

Xi'an `prd-host-pa01-xas`에서 KubeSphere Console, Prometheus, Alertmanager, Grafana가 완전히 Down되지는 않지만 간헐적으로 `504 Gateway Timeout`을 반환하면 개별 Pod보다 공통 Ingress 경로부터 확인한다.

```text
사용자
→ VIP-B 109.156.25.46:80/443
→ Router xadksrthm01 / xadksrthm02 / xadksrthm03
→ ingress-nginx-controller
→ Service
→ Backend Pod
```

Router IP는 `xadksrthm01=109.156.22.47`, `xadksrthm02=109.156.22.48`, `xadksrthm03=109.156.22.49`다. Ingress Controller Service는 `80:30080`, `443:30443` NodePort를 사용한다.

이 문서는 [[60. 이슈 및 결정/장애/prd-host-pa01-xas Host UI 간헐 504 진단 핸드오프|prd-host-pa01-xas Host UI 간헐 504 진단 핸드오프]]의 실제 확인 결과를 기준으로 한다. 당시 `ingress-nginx` 로그에서 504가 확인됐고 특정 controller 하나에서만 발생했으며, 해당 controller Pod를 재생성한 뒤에도 증상이 남았다. 당시 504 원문 로그는 보존돼 있지 않으므로 아래 출력에서 **Pod suffix, Pod IP, Service ClusterIP, Backend Endpoint IP, 시간, request ID, route 상세는 화면 형태를 보여주기 위한 참조값**이다. FQDN, Namespace, Service 이름, Service Port, Router, VIP는 Xi'an 기준값을 사용한다.

## 1. Ingress와 Service 상태 확인

```console
[dspaas@xadksbthm01 ~]$ kubectl get ingress -A
NAMESPACE                       NAME                        CLASS    HOSTS                                                   ADDRESS   PORTS   AGE
kubesphere-system               ks-console-ingress          <none>   ks-console.xaprdpa01.mgmt.dks.samsungds.net                      80      32d
kubesphere-monitoring-system    alertmanager-main-ingress   <none>   alertmanager.xaprdpa01.mgmt.dks.samsungds.net                     80      32d
kubesphere-monitoring-system    prometheus-ingress          <none>   prometheus.xaprdpa01.mgmt.dks.samsungds.net                       80      32d

[dspaas@xadksbthm01 ~]$ kubectl get svc -n ingress-nginx ingress-nginx-controller
NAME                       TYPE       CLUSTER-IP      EXTERNAL-IP   PORT(S)                      AGE
ingress-nginx-controller   NodePort   192.210.12.31   <none>        80:30080/TCP,443:30443/TCP   32d
```

Console, Prometheus, Alertmanager Ingress가 있고 `ingress-nginx-controller`가 `30080/30443`으로 열려 있으면 다음 단계로 간다. `CLUSTER-IP`, `AGE`는 실행 시점 값이 달라도 된다. Grafana는 기존 Host Ingress manifest에 포함되지 않았으므로 위 세 경로를 우선 기준으로 사용한다.

## 2. Router 3대의 ingress-controller 위치 확인

```console
[dspaas@xadksbthm01 ~]$ kubectl get pod -n ingress-nginx -o wide
NAME                                        READY   STATUS    RESTARTS   AGE   IP               NODE
ingress-nginx-controller-7b9c9b8f6d-7j2xq   1/1     Running   0          12d   172.210.227.65   xadksrthm01
ingress-nginx-controller-7b9c9b8f6d-b8m4k   1/1     Running   0          12d   172.210.69.194   xadksrthm02
ingress-nginx-controller-7b9c9b8f6d-q6p9n   1/1     Running   0          12d   172.210.203.2    xadksrthm03
```

Pod suffix와 Pod IP는 실행 시점에 달라진다. `NODE` 열에서 controller가 `xadksrthm01`, `xadksrthm02`, `xadksrthm03`에 각각 하나씩 있는지만 확인한다.

## 3. 504가 찍히는 controller 로그 확인

먼저 위 출력의 controller Pod 이름으로 `504`만 확인한다.

```console
[dspaas@xadksbthm01 ~]$ kubectl logs -n ingress-nginx ingress-nginx-controller-7b9c9b8f6d-q6p9n --tail=200 | grep 504
109.156.22.100 - - [13/Aug/2026:15:22:11 +0800] "GET /graph HTTP/2.0" 504 160 "-" "Mozilla/5.0" 431 60.001 [kubesphere-monitoring-system-prometheus-k8s-9090] [] 172.210.84.214:9090 0 60.000 504 8f0b1a2c7d3e4f5a
```

504가 보이면 같은 Pod 로그에서 `upstream timed out`도 확인한다.

```console
[dspaas@xadksbthm01 ~]$ kubectl logs -n ingress-nginx ingress-nginx-controller-7b9c9b8f6d-q6p9n --tail=200 | grep "upstream timed out"
2026/08/13 15:22:11 [error] 1421#1421: *88421 upstream timed out (110: Connection timed out) while connecting to upstream, client: 109.156.22.100, server: prometheus.xaprdpa01.mgmt.dks.samsungds.net, request: "GET /graph HTTP/2.0", upstream: "http://172.210.84.214:9090/graph", host: "prometheus.xaprdpa01.mgmt.dks.samsungds.net"
```

위 참조 출력처럼 `while connecting to upstream`이 보이면 해당 Router에서 Backend Pod IP:Port까지 TCP 연결을 확인한다. `while reading response header from upstream`이면 연결은 됐지만 Backend 응답이 늦은 쪽을 본다.

실제 사건에서는 **특정 controller 하나에서만 504가 확인됐다.** 따라서 다른 두 controller도 같은 방식으로 `grep 504`해서 어느 Router에서만 발생하는지 확인한다.

## 4. Backend Endpoint 확인

504 예시에서 Backend는 Prometheus `172.210.84.214:9090`이다. 실제 장애에서는 현재 Endpoint 값을 먼저 확인한다.

```console
[dspaas@xadksbthm01 ~]$ kubectl get endpoints -n kubesphere-monitoring-system prometheus-k8s
NAME             ENDPOINTS                                         AGE
prometheus-k8s   172.210.84.214:9090,172.210.96.129:9090           32d
```

Console과 Alertmanager도 같은 방식으로 확인한다.

```console
[dspaas@xadksbthm01 ~]$ kubectl get endpoints -n kubesphere-system ks-console
[dspaas@xadksbthm01 ~]$ kubectl get endpoints -n kubesphere-monitoring-system alertmanager-main
```

Prometheus는 `9090`, Alertmanager는 `9093`, KubeSphere Console은 `80`을 사용한다.

## 5. 정상 Router와 문제 Router에서 같은 Endpoint 비교

예시 504의 Backend `172.210.84.214:9090`을 그대로 비교한다. 먼저 504가 발생한 `xadksrthm03`에서 확인한다.

```console
[dspaas@xadksbthm01 ~]$ ssh xadksrthm03
[root@xadksrthm03 ~]# ip route get 172.210.84.214
172.210.84.214 dev tunl0 src 109.156.22.49

[root@xadksrthm03 ~]# nc -vz -w 3 172.210.84.214 9090
Ncat: Version 7.92 ( https://nmap.org/ncat )
Ncat: Connection timed out.
[root@xadksrthm03 ~]# exit
```

같은 Endpoint를 정상 Router에서도 확인한다.

```console
[dspaas@xadksbthm01 ~]$ ssh xadksrthm01
[root@xadksrthm01 ~]# ip route get 172.210.84.214
172.210.84.214 dev tunl0 src 109.156.22.47

[root@xadksrthm01 ~]# nc -vz -w 3 172.210.84.214 9090
Ncat: Version 7.92 ( https://nmap.org/ncat )
Ncat: Connected to 172.210.84.214:9090.
Ncat: 0 bytes sent, 0 bytes received in 0.01 seconds.
[root@xadksrthm01 ~]# exit
```

위와 같이 같은 Backend가 `xadksrthm01`에서는 연결되는데 `xadksrthm03`에서만 timeout이면 `xadksrthm03`의 Backend Pod 경로로 범위를 좁힌다. 두 Router 모두 연결되면 지속적인 단순 route 단절로 보지 않는다.

실제 Endpoint IP가 `172.210.84.214`가 아니면 `kubectl get endpoints`에 나온 현재 IP를 그대로 사용한다.

## 6. xadksrthm03의 default route 확인

실제 사건에서 `xadksrthm03`은 과거 Main/Data default route metric이 역전된 이력이 있었다. 현재도 다시 바뀌었는지만 세 Router에서 비교한다.

```console
[dspaas@xadksbthm01 ~]$ ssh xadksrthm01 ip route
[dspaas@xadksbthm01 ~]$ ssh xadksrthm02 ip route
[dspaas@xadksbthm01 ~]$ ssh xadksrthm03 ip route
```

`xadksrthm03`의 default 경로만 다른 경우 승인된 Node 네트워크 기준과 비교해 route를 복구한다. 세 Router route가 같은데 특정 Router만 Endpoint 연결이 실패하면 route만 반복 수정하지 않고 해당 Node의 네트워크 구간을 추가 확인한다.

## 7. Bastion에서 controller Pod IP가 timeout인 경우

`xadksbthm01`에서 controller Pod IP를 직접 `curl`해서 timeout이 나오는 것은 이 사건의 장애 판정에 사용하지 않는다. 실제 사건에서는 Bastion에 Host Pod CIDR `172.210.0.0/16` 라우팅이 없어 Pod IP 직접 접근이 되지 않았다.

```text
xadksbthm01 → controller Pod IP 직접 접근
≠
사용자 → 109.156.25.46 → Router → ingress-nginx-controller → Backend
```

## 8. 바로 하지 않는 조치

실제 사건에서는 문제 controller Pod를 재생성해도 증상이 동일했다. 따라서 아래 조치를 먼저 하지 않는다.

```text
controller Pod 반복 삭제
Ingress timeout annotation 일괄 상향
전체 ingress-nginx 또는 KubeSphere 재설치
증거 없이 VIP/LB timeout 변경
Router 노드 재부팅
```

## 9. 정상 확인

조치 후 각 URL을 여러 번 직접 확인한다.

```console
[dspaas@xadksbthm01 ~]$ curl -sk -o /dev/null -w '%{http_code}\n' https://ks-console.xaprdpa01.mgmt.dks.samsungds.net/
200
[dspaas@xadksbthm01 ~]$ curl -sk -o /dev/null -w '%{http_code}\n' https://prometheus.xaprdpa01.mgmt.dks.samsungds.net/
200
[dspaas@xadksbthm01 ~]$ curl -sk -o /dev/null -w '%{http_code}\n' https://alertmanager.xaprdpa01.mgmt.dks.samsungds.net/
200
```

위 명령을 몇 차례 반복했을 때 `504`가 다시 나오지 않고, Router별 Endpoint 연결 결과가 같으며 실제 UI 기능과 데이터 조회가 정상이어야 종료한다.
