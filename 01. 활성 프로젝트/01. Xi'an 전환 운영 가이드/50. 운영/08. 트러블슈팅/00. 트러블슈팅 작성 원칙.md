# 트러블슈팅 작성 원칙

> [!summary] 요약
> 트러블슈팅 문서는 AI가 설명을 채워 넣는 문서가 아니라, 운영자가 실제 터미널에서 문제를 확인하고 다음 명령으로 범위를 좁혀 조치와 재확인까지 이어갈 수 있는 작업 문서로 작성한다. 사용자가 직접 정리한 문장·명령·로그가 있으면 그것을 우선 기준으로 삼고 불필요하게 다시 쓰지 않는다.

## 문서 채택 기준

Harbor 문서를 살릴 수 있었던 이유는 이미 검증된 User Guide의 실제 작업 흐름이 뼈대로 있었기 때문이다. 불필요한 설명을 걷어내도 `접속 → CA 인증서 → 로그인 → Repository/Tag → Pull/Push → 권한 확인`이라는 실제 운영 절차와 구체적인 입력값·명령·출력이 남았다.

반대로 뼈대가 약한 상태에서 먼저 트러블슈팅 주제를 정하고, 그럴듯한 진단 명령·오류 메시지·출력을 만들어 채운 문서는 채택하지 않는다. 설명을 걷어냈을 때 실제 작업 흐름과 검증된 판단 기준이 남지 않는다면 문서 자체를 만들지 않거나 삭제한다.

트러블슈팅 문서 생성 전에는 다음 세 가지를 먼저 확인한다.

- **검증된 작업 흐름이 있는가:** 실제 User Guide, 운영 절차, 장애 기록 중 하나에 시작점부터 조치·확인까지 이어지는 흐름이 있어야 한다.
- **군더더기를 걷어내도 핵심이 남는가:** AI 해설, 일반론, 예시 출력을 삭제해도 실제 환경값·명령·판정 기준만으로 문서가 성립해야 한다.
- **별도 문서로 만들 가치가 있는가:** 기존 User Guide나 사건 기록을 다시 풀어쓴 수준이 아니라, 실제 장애 시 더 빠르게 판단하고 조치할 수 있어야 한다.

이 기준을 충족하지 못하면 폴더를 채우기 위해 문서를 만들지 않는다.

## 작성 원칙

1. **Harbor, KubeSphere처럼 제품 단위로 폴더를 나누고 관련 트러블슈팅을 함께 관리한다.**
2. **한 문서는 하나의 작업 흐름을 기준으로 하고, 서로 이어지는 증상은 같은 문서에 묶는다.**
3. **실제 Xi'an 사건·오적용·현장 확인값이 있으면 그 사례와 현재 Xi'an 값을 기준으로 쓴다.** 다른 환경의 값이나 일반적인 Kubernetes 사례를 빈칸 채우기 용도로 섞지 않는다.
4. **사용자가 직접 정리해 준 문장·명령·로그·순서는 현재 작업의 우선 원문으로 취급한다.** `그대로 적용`, `이 형식으로 반영` 요청이 있으면 Markdown escape, 링크, 코드블록, frontmatter 같은 서식 정리 외에는 임의로 요약·재구성·미화하지 않는다.
5. **터미널 예시는 실제 작업 세션처럼 연속해서 작성한다.** `명령 → 출력 → 다음 확인 명령 → 출력 → 조치 → 재확인` 흐름을 한 블록 또는 자연스럽게 이어지는 소수의 블록으로 보여준다. 명령 하나마다 2~3줄짜리 짧은 예시를 기계적으로 붙이지 않는다.
6. **터미널 출력은 운영자가 화면에서 실제로 볼 법한 밀도와 문맥을 유지한다.** prompt, host/user, 리소스명, Status, Event, 오류 전후 문맥 등 판정에 필요한 줄은 충분히 포함한다. 반대로 판정과 관계없는 장황한 로그는 붙이지 않는다.
7. **현재 확인된 Xi'an 값은 가능한 한 실제 값을 쓴다.** Cluster, Node, VIP, IP, Namespace, StorageClass, Registry, Repository처럼 이미 확정된 값까지 `<placeholder>`로 과도하게 가리지 않는다. 실행 시 생성되는 Pod suffix, UID, 동적 IP처럼 고정할 수 없는 값만 필요한 범위에서 마스킹한다.
8. **로그나 출력 사이를 AI식 해설로 과도하게 끊지 않는다.** `Xi'an 기준 예시 출력`, `실제 사건과 같은 판정 예시`, `정상 예시` 같은 반복 라벨을 남발하지 않는다. 출력 뒤 설명은 그 출력에서 무엇이 확인됐고 다음에 무엇을 볼지만 짧게 쓴다.
9. **문서를 그럴듯하게 보이게 하려고 원인 후보·오류 메시지·진단 명령을 추가하지 않는다.** 현재 문제 흐름과 직접 연결되지 않는 generic 오류 모음, 예방 팁, 대체 방법, 사전 체크리스트는 넣지 않는다.
10. **정상 사용 가이드 전체를 트러블슈팅 문서에 다시 풀어 쓰지 않는다.** 장애 확인에 필요한 정상 기준과 비교 지점만 가져오고, 일반 사용 절차는 기존 User Guide 또는 운영 문서로 연결한다.
11. **Harbor User Guide의 명령·출력 배치 방식을 기본 참고 형식으로 사용한다.** 여러 명령과 출력이 한 실행 흐름 안에서 이어지도록 하고, Pull/Push처럼 판정에 필요한 출력은 중간 layer와 마지막 상태까지 충분히 보여준다.
12. **사용자가 제공한 터미널 로그 안의 값이나 불일치를 임의로 정상화하지 않는다.** Repository, Tag, 계정, 경로, digest 등 원문에 있는 값을 다른 값으로 바꾸거나 앞뒤를 맞추기 위해 고쳐 쓰지 않는다. 수정이 필요한 경우에만 별도 설명으로 구분한다.
13. **번역본은 원문 구조와 기술 내용을 그대로 보존한다.** 명령어와 터미널 출력은 원칙적으로 변경하지 않고, 제목·설명 문장·코드 안의 설명용 주석만 대상 언어로 번역한다. 번역하면서 명령, IP, Repository, Tag, 오류 메시지를 새로 만들거나 바꾸지 않는다.
14. **민감정보는 길고 자세한 터미널 형식을 이유로 노출하지 않는다.** 비밀번호, token, private key, kubeconfig 인증정보, JWT 원문은 출력하지 않는다. 필요한 경우 존재 여부나 hash 등 안전한 방법으로 확인한다.
15. **해결에 직접 필요한 확인과 조치만 작성한다.** 기본 흐름으로 해결되지 않으면 문서를 백과사전처럼 확장하지 않고 담당자 확인 또는 별도 심화 Runbook으로 넘긴다.
16. **명령은 운영자가 바로 읽고 칠 수 있는 가장 단순한 형태를 우선한다.** `kubectl get`, `kubectl describe`, `kubectl logs`, `curl`, `nc`, `ip route`처럼 익숙한 기본 명령으로 해결되면 그것을 사용한다. `custom-columns`, 긴 `jsonpath`, `awk`, `xargs`, 중첩 command substitution, 복잡한 정규식 grep으로 한 줄 자동화하지 않는다. 동적으로 바뀌는 Pod 이름이나 Endpoint IP는 먼저 `get`으로 확인한 뒤 다음 짧은 명령에 그대로 넣는 방식을 우선한다. 약간의 수동 복사가 생기더라도 명령 난이도를 낮추는 쪽을 선택한다.
17. **판정에 중요한 명령은 Harbor 문서처럼 화면 출력까지 보여준다.** `get`, `logs`, `describe`, `curl`, `nc`를 실행한 뒤 운영자가 무엇을 봐야 하는지 알 수 있도록 실제 로그가 있으면 그대로 붙이고, 실제 원문이 보존되지 않았으면 **참조 출력임을 한 번 명확히 밝힌 뒤** 화면에서 보일 법한 밀도의 출력 예시를 제공한다. 이때 Cluster, Node, VIP, FQDN, Namespace, Service, Port처럼 확정된 Xi'an 값은 실제값을 사용하고, Pod suffix·Pod IP·시간·request ID처럼 동적인 값만 예시값을 사용할 수 있다. 참조 출력을 실제 장애 원문이라고 표현하지 않는다.

## 금지 사항

- 사용자가 완성해 준 문장을 더 친절하게 보이게 하려고 다시 쓰기
- 짧은 명령/짧은 출력/설명을 동일한 패턴으로 반복해 문서를 채우기
- 실제 Xi'an 값이 있는데 generic placeholder로 바꾸기
- 단순한 `get`, `logs`, `describe`로 가능한 작업을 `custom-columns`, 긴 `jsonpath`, `awk`, `xargs`, 복잡한 grep 조합으로 자동화하기
- 동적 값 몇 개를 자동 추출하려고 환경변수나 command substitution을 여러 단계로 이어 붙이기
- 판정에 중요한 명령을 출력 예시 없이 명령만 나열하기
- 참조 출력을 실제 사건에서 확보한 원문 로그인 것처럼 쓰기
- 문서 분량을 늘리기 위해 일반적인 Kubernetes 오류나 원인 후보 추가하기
- 터미널 출력보다 AI의 해설 문장을 더 길게 쓰기
- 번역 과정에서 명령·출력·Repository·Tag·IP를 임의 변경하기
