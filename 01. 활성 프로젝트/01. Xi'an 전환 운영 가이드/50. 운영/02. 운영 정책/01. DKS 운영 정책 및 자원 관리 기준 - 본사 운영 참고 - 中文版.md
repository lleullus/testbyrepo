# DKS 运营政策及资源管理标准 - 韩国总部运营参考

> [!summary] 摘要
> 整理韩国总部 DKS 使用的资源申请·扩容·缩容、KubeSphere Quota 与权限、Naming、Harbor Quota、外部暴露及 Firewall 运营标准。

---

## 1. 资源申请 / 扩容 / 缩容

DKS 资源以 Namespace(Project) 为单位申请并运营。

### 1.1 申请项目

| 区分 | 申请项目 | 备注 |
|---|---|---|
| 用户信息 | Department | 使用部门 |
| Application 区域 | Namespace / Project | KubeSphere Project = Kubernetes Namespace |
| Compute | CPU | 以 Core 为单位 |
| Compute | Memory | Memory 容量 |
| Storage | NAS Storage | PVC 使用的 Storage 容量 |

除新资源申请外，现有 Namespace 的 CPU、Memory、Storage 扩容·缩容也同样向运维团队提出申请后处理。

```text
资源申请
→ 确认 Namespace(Project)
→ 确认 CPU / Memory / NAS Storage
→ 设置 Quota
```

### 1.2 扩容 / 缩容

需要变更现有分配量时，向运维团队申请扩容或缩容。

- CPU 扩容 / 缩容
- Memory 扩容 / 缩容
- Storage 扩容 / 缩容
- 变更申请以目标 Namespace 和需要变更的资源值为准进行处理

## 2. Quota 运营政策

### 2.1 Workspace 与 Namespace 的关系

KubeSphere 支持在一个 Workspace 下配置多个 Project 的 1:N 结构，但韩国总部 DKS 为简化运营和权限管理，采用**一个 Workspace 只分配一个 Namespace(Project) 的 1:1 结构**进行运营。

```text
Workspace 1
    ↓
Project 1
    ↓
Kubernetes Namespace 1
```

### 2.2 Project(Namespace) Quota

分配给 Application 的实际资源通过 Project(Namespace) Quota 管理。

| Resource | 管理标准 |
|---|---|
| CPU | Project(Namespace) Quota |
| Memory | Project(Namespace) Quota |
| Storage | Namespace Storage Quota |

根据用户申请的 CPU、Memory、Storage 值，为各 Namespace 分配 Quota。

### 2.3 Workspace Quota

使用 Workspace Quota 时，与 Project(Namespace) Quota **按 1:1 设置为相同的值**。

```text
Workspace Quota
      =
Project Quota
```

如果 Workspace 与 Project 始终保持 1:1，并按相同比例管理 Quota，则仅使用 Project Quota 也可以实现实际资源限制，因此可以不单独设置 Workspace Quota。

---

## 3. Workspace / Project 权限政策

Workspace 与 Project 的权限分开运营。

### 3.1 Workspace 权限

除运维人员外，普通用户在 Workspace 中**仅授予 Viewer 权限**。

```text
运维人员
→ 管理 Workspace

普通用户
→ Workspace Viewer
```

限制普通用户在 Workspace 中自行新增 Project 或修改 Workspace 级设置。

### 3.2 Project 权限

实际 Application 运营权限在 Project(Namespace) 内按用户分别授予。

| Role | 用途 |
|---|---|
| Admin | Project 管理 |
| Developer | Workload 及 Application Resource 运营 |
| Viewer | 查看 Project Resource |

用户在 Workspace 中保持 Viewer 权限，所需操作权限则在 Project 级分别授予 Admin / Developer / Viewer。

---

## 4. Naming 政策

为了通过名称区分 Workspace、Project(Namespace)、Harbor Project 之间的关系，使用以下 Naming 标准。

### 4.1 Project / Namespace

```text
{namespaceName}
```

KubeSphere Project 名称与 Kubernetes Namespace 名称保持一致。

### 4.2 Workspace

```text
ws_{namespaceName}
```

通过名称识别 Workspace 与 Namespace 的 1:1 关系。

### 4.3 Harbor Project

```text
{clusterName}_{projectName}
```

Harbor Project 名称中包含目标 Cluster 和 Project 名称。

## 5. Harbor Quota 政策

创建 Harbor Project 时，分配**默认 Storage Quota 10Gi**。

```text
创建 Harbor Project
       ↓
默认 Quota 10Gi
```

10Gi 作为固定默认值运营，如需额外容量，由用户提出扩容申请。

收到扩容申请后，可经运维团队协商增加 Harbor Project 的 Quota。

```text
默认 10Gi
   ↓
扩容申请
   ↓
运维团队协商
   ↓
Quota 扩容
```

---

## 6. Storage 运营政策

Application Storage 以 NAS 为基准接受申请，并分配到 Namespace。

```text
用户申请 Storage
        ↓
确认 NAS Storage 容量
        ↓
分配 Namespace Storage Quota
        ↓
使用 PVC
```

需要对 Storage 扩容或缩容时，同样以 Namespace 和变更容量为基准向运维团队提出申请。

---

## 7. 外部暴露 / NodePort 运营原则

Application 对外暴露所使用的 IP 和 NodePort 由运维团队统一管理。

- 用户不得自行指定用于外部暴露的 IP 或 NodePort。
- 需要外部暴露时向运维团队提出申请。
- NodePort 的创建及变更由运维人员控制。
- 服务需要特定 Port 时，由运维团队确认暴露方式后进行配置。

```text
Application 外部暴露申请
        ↓
运维团队确认
        ↓
配置外部暴露 IP / Port
        ↓
由运维人员控制 NodePort
```

---

## 8. Firewall / Network 处理原则

DKS 服务或 Application 通信需要开放 Firewall 时，根据通信所需的 Network 信息申请 Firewall 放行。

| 项目 | 内容 |
|---|---|
| Source | 通信源 IP 或 Network 网段 |
| Destination | 目标 IP 或 Network 网段 |
| Port | 服务 Port |
| Protocol | TCP / UDP |
| 目的 | 服务使用或 Application 联动事由 |

Firewall 根据所需网段和 Port 进行放行处理，DKS 运维团队负责管理 Application 的外部暴露以及 Cluster 侧 Network 配置。

```text
确认通信需求
→ 确认 Source / Destination 网段
→ 确认 Port / Protocol
→ 申请 Firewall 放行
→ 确认通信
```
