# DKS 운영 정책 및 자원 관리 기준 - 본사 운영 참고

> [!summary] 요약
> 본사 DKS에서 사용하는 자원 신청·증설·감축, KubeSphere Quota와 권한, Naming, Harbor Quota, 외부 노출 및 Firewall 운영 기준을 정리한다.

---

## 1. 자원 신청 / 증설 / 감축

DKS 자원은 Namespace(Project)를 기준으로 신청받아 운영한다.

### 1.1 신청 항목

| 구분 | 신청 항목 | 비고 |
|---|---|---|
| 사용자 정보 | Department | 사용 부서 |
| Application 영역 | Namespace / Project | KubeSphere Project = Kubernetes Namespace |
| Compute | CPU | Core 기준 |
| Compute | Memory | Memory 용량 |
| Storage | NAS Storage | PVC에서 사용할 Storage 용량 |

신규 자원 신청뿐 아니라 기존 Namespace의 CPU, Memory, Storage 증설·감축도 동일하게 운영팀에 요청하여 처리한다.

```text
자원 신청
→ Namespace(Project) 확인
→ CPU / Memory / NAS Storage 확인
→ Quota 설정
```

### 1.2 증설 / 감축

기존 할당량을 변경해야 하는 경우 운영팀에 증설 또는 감축을 요청한다.

- CPU 증설 / 감축
- Memory 증설 / 감축
- Storage 증설 / 감축
- 변경 요청은 대상 Namespace와 변경할 자원 값을 기준으로 처리

---

## 2. Quota 운영 정책

### 2.1 Workspace와 Namespace 관계

KubeSphere는 하나의 Workspace 아래 여러 Project를 구성하는 1:N 구조를 지원하지만, 본사 DKS에서는 운영 및 권한 관리를 단순화하기 위해 **Workspace 하나에 Namespace(Project) 하나만 부여하는 1:1 구조**로 운영한다.

```text
Workspace 1
    ↓
Project 1
    ↓
Kubernetes Namespace 1
```

### 2.2 Project(Namespace) Quota

Application에 할당되는 실제 자원은 Project(Namespace) Quota로 관리한다.

| Resource | 관리 기준 |
|---|---|
| CPU | Project(Namespace) Quota |
| Memory | Project(Namespace) Quota |
| Storage | Namespace Storage Quota |

사용자가 신청한 CPU, Memory, Storage 값을 기준으로 Namespace별 Quota를 부여한다.

### 2.3 Workspace Quota

Workspace Quota를 사용하는 경우 Project(Namespace) Quota와 **1:1로 동일한 값**을 부여한다.

```text
Workspace Quota
      =
Project Quota
```

Workspace와 Project를 항상 1:1로 유지하고 동일한 비율로 Quota를 관리하는 경우에는 Project Quota만으로도 실제 자원 제한이 가능하므로 Workspace Quota를 별도로 설정하지 않을 수 있다.

---

## 3. Workspace / Project 권한 정책

Workspace와 Project의 권한을 분리하여 운영한다.

### 3.1 Workspace 권한

운영자를 제외한 일반 사용자에게는 Workspace에서 **Viewer 권한만 부여**한다.

```text
운영자
→ Workspace 관리

일반 사용자
→ Workspace Viewer
```

일반 사용자가 Workspace에서 Project를 추가 생성하거나 Workspace 단위 설정을 변경하지 못하도록 제한한다.

### 3.2 Project 권한

실제 Application 운영 권한은 Project(Namespace) 안에서 사용자별로 부여한다.

| Role | 용도 |
|---|---|
| Admin | Project 관리 |
| Developer | Workload 및 Application Resource 운영 |
| Viewer | Project Resource 조회 |

사용자는 Workspace에서는 Viewer로 유지하고, 필요한 작업 권한은 Project 단위에서 Admin / Developer / Viewer로 개별 부여한다.

---

## 4. Naming 정책

Workspace, Project(Namespace), Harbor Project의 관계를 이름으로 구분할 수 있도록 다음 Naming 기준을 사용한다.

### 4.1 Project / Namespace

```text
{namespaceName}
```

KubeSphere Project 이름과 Kubernetes Namespace 이름을 동일하게 사용한다.

### 4.2 Workspace

```text
ws_{namespaceName}
```

Workspace와 Namespace의 1:1 관계를 이름으로 식별한다.

### 4.3 Harbor Project

```text
{clusterName}_{projectName}
```

Harbor Project 이름에 대상 Cluster와 Project 이름을 포함한다.

## 5. Harbor Quota 정책

Harbor Project는 생성 시 **기본 Storage Quota 10Gi**를 부여한다.

```text
Harbor Project 생성
       ↓
기본 Quota 10Gi
```

10Gi는 기본값으로 고정하여 운영하고, 추가 용량이 필요한 경우 사용자가 증설을 요청한다.

증설 요청이 접수되면 운영팀 협의를 통해 Harbor Project의 Quota를 증설할 수 있다.

```text
기본 10Gi
   ↓
증설 요청
   ↓
운영팀 협의
   ↓
Quota 증설
```

---

## 6. Storage 운영 정책

Application Storage는 NAS를 기준으로 신청받고 Namespace에 할당한다.

```text
사용자 Storage 신청
        ↓
NAS Storage 용량 확인
        ↓
Namespace Storage Quota 부여
        ↓
PVC 사용
```

Storage 증설 또는 감축이 필요한 경우에도 Namespace와 변경 용량을 기준으로 운영팀에 요청한다.

---

## 7. 외부 노출 / NodePort 운영 원칙

Application 외부 노출에 사용하는 IP와 NodePort는 운영팀 관리 영역으로 둔다.

- 사용자가 외부 노출용 IP 또는 NodePort를 임의로 지정하지 않는다.
- 외부 노출이 필요한 경우 운영팀에 요청한다.
- NodePort 생성 및 변경은 운영자가 제어한다.
- 서비스에 필요한 Port가 있는 경우 운영팀에서 노출 방식을 확인한 뒤 적용한다.

```text
Application 외부 노출 요청
        ↓
운영팀 확인
        ↓
외부 노출 IP / Port 구성
        ↓
NodePort 운영자 제어
```

---

## 8. Firewall / Network 처리 원칙

DKS 서비스 또는 Application 통신을 위해 방화벽 허용이 필요한 경우 통신에 필요한 Network 정보를 기준으로 방화벽을 신청한다.

| 항목 | 내용 |
|---|---|
| Source | 통신 출발지 IP 또는 Network 대역 |
| Destination | 대상 IP 또는 Network 대역 |
| Port | 서비스 Port |
| Protocol | TCP / UDP |
| 목적 | 서비스 사용 또는 Application 연계 사유 |

방화벽은 필요한 대역과 Port를 기준으로 허용 처리하며, DKS 운영팀은 Application의 외부 노출 및 Cluster 측 Network 구성을 관리한다.

```text
통신 요구사항 확인
→ Source / Destination 대역 확인
→ Port / Protocol 확인
→ 방화벽 허용 요청
→ 통신 확인
```
