> [!summary] Summary
> Xi'an DKS is a service for operating Kubernetes application resources in KubeSphere and managing container images in Harbor. Users work in their assigned Project, and a Project is equivalent to a Kubernetes Namespace.

> [!warning] Draft Status
> This document is a Xi'an-based draft that replaces the Taylor environment values. The cluster and network values reflect the current catalog, but the SCS AD integration information and the final FQDN for the KubeSphere Dashboard have not yet been finalized.

---

## 1. Service Architecture

| Component | Xi'an Reference | Role from the User's Perspective |
|---|---|---|
| KubeSphere Host | `prd-host-pa01-xas` | User login and Workspace, Project, and permission management |
| Production Member | `prd-apps-pa01-xas` | Production application deployment and execution |
| Development Member | `dev-apps-pa01-xas` | Development application deployment and execution |
| Harbor | `prd-harbor-xas` | Container image storage, Push, and Pull |

KubeSphere's management area and application execution area are separated. Users select their assigned Project from the Host web console, while actual workloads are deployed to the Production or Development Member Cluster.

## 3. Workspace, Project, and Namespace

- Under DKS policy, **one Workspace and one Project are configured in a 1:1 relationship**.
- A KubeSphere **Project is equivalent to a Kubernetes Namespace**.
- Users may view or manage only the permitted application resources within their assigned Project.
- CPU and Memory are limited by Workspace and Project Quotas, while Storage is limited by Namespace-wide and StorageClass-specific Quotas.

An `Admin` request in the application form is mapped by default to the KubeSphere `project-operator`, while a `User` request is mapped to `project-viewer`. `project-operator` can manage resources such as workloads and storage, but cannot manage Project members or roles. `project-admin`, which has member management permissions, is subject to a separate operational policy.

---

## 4. Usage Flow

1. Request firewall access for the KubeSphere Dashboard, Harbor, and the Member Cluster Ingress to be used.
2. Following the operations team's guidance, log in to KubeSphere for the first time to create an account access record.
3. Submit an application form specifying the Project name, target environment, CPU, Memory, Storage, users, and requested permissions.
4. The operations team creates the Workspace and Project, invites users, and assigns Project roles and Quotas.
5. Users added as Harbor Project members Push images, then deploy workloads in KubeSphere using those images. Private images require an Image Secret.
6. Expose the application through the Ingress domain of the target Member Cluster.

`kubectl` is not the default user access path. It may be used only through a separate operational procedure when the Bastion account, firewall access, CyberArk permissions, and a user-specific kubeconfig have been approved.
