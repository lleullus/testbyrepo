## 3. Managing Permissions

Assign users a role in the Project, which is equivalent to a Namespace. Request-form permission `Admin` maps to `project-operator`, and `User` maps to `project-viewer`. The member-management role `project-admin` follows a separate operations policy.

| Role | Description |
|------|------|
| **project-admin** | Manages project resources, settings, and members. Granted only under a separate operations policy |
| **project-operator** | Creates, updates, and deletes resources but cannot manage users, roles, or project settings. Maps to request-form `Admin` |
| **project-viewer** | Read-only access to project resources. Maps to request-form `User` |

### Procedure for Granting Operator Permissions

1. Log in with an account that has `project-admin` permissions.
2. **Projects** -> Select the project -> **Project Settings** -> **Project Members**
3. Click **Invite** or **+User** -> Add a member who has already been invited to the Workspace.
4. Select **project-operator** as the role -> **OK**

## 5. Deploying an Image Secret (UI)

1. In the same project as the Deployment, click **Configuration** -> **Secrets** -> **Create**.
2. Enter the Secret Name in **Basic Information** -> Next.
3. Configure the Secret options in **Data Settings**.
4. **Type**: Select Image registry information.
5. **Registry Address**: Enter `xa.dcr.dks.samsungds.net`.
6. **Username**: Enter the registry account.
7. **Password**: Enter the registry password.
8. Click **Create**.

Creating the Secret does not apply it automatically. Explicitly select it as the Deployment's Image Pull Secret, and never record the password in documentation or YAML.

## 9. YAML-Based Deployment

### 9-1. PVC YAML

1. KubeSphere Dashboard -> **Storage** -> **Volumes** -> **Create** -> **Edit YAML**

Replace `example-project`, resource names, and capacity below with approved actual values.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  namespace: example-project
  name: nginx-test
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 10Gi
  storageClassName: scs-netapp-qtree-nfs-sc-delete
  volumeMode: Filesystem
```

### 9-2. Deployment YAML

1. KubeSphere Dashboard -> Select the project -> **Application Workloads** -> **Workloads** -> **Deployments** -> **Create** -> **Edit YAML**

Replace `image` and `imagePullSecrets.name` with actual values verified in the same Project.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  namespace: example-project
  name: nginx-test
  labels:
    app: nginx-test
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-test
  template:
    metadata:
      labels:
        app: nginx-test
    spec:
      imagePullSecrets:
        - name: harbor-registry-secret
      containers:
        - image: xa.dcr.dks.samsungds.net/example-project/nginx:latest
          imagePullPolicy: IfNotPresent
          name: nginx
          ports:
            - containerPort: 80
              name: http-test
              protocol: TCP
          volumeMounts:
            - mountPath: /data
              name: nginx-data
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
      volumes:
        - name: nginx-data
          persistentVolumeClaim:
            claimName: nginx-test
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25%
      maxSurge: 25%
```

### 9-3. Service YAML

1. KubeSphere Dashboard -> Select the project -> **Application Workloads** -> **Services** -> **Create** -> **Specify Workload** -> **Edit YAML**

```yaml
apiVersion: v1
kind: Service
metadata:
  namespace: example-project
  name: nginx-test
  labels:
    app: nginx-test
spec:
  sessionAffinity: None
  ports:
    - name: http-test
      port: 80
      protocol: TCP
      targetPort: 80
  selector:
    app: nginx-test
```

### 9-4. Route YAML

1. KubeSphere Dashboard -> Select the project -> **Application Workloads** -> **Routes** -> **Create** -> **Edit YAML**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  namespace: example-project
  name: nginx-test
spec:
  rules:
    - host: nginx-test.xadevpa01.apps.dks.samsungds.net
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-test
                port:
                  number: 80
```

## 10. Configuring Autoscaling

1. Select the project -> **Application Workloads** -> **Workloads** -> Select the Deployment.
2. Click **More** -> **Edit Autoscaling**.
3. Confirm that the Metrics API is healthy and that CPU/Memory `requests` are configured for the target container. Then configure the options -> Click **OK**.

| Item | Description |
|------|------|
| Target CPU Usage (%) | Average container CPU usage as a percentage of `resources.requests.cpu` |
| Target Memory Usage (MiB) | Absolute average memory usage per Pod. This is different from a percentage of the memory request |
| Minimum Replicas | Minimum number of Pods |
| Maximum Replicas | Maximum number of Pods. Set it to at least Minimum Replicas |

## 11. Using the Kubectl CLI

`kubectl` is not the default user access path. Use it only when the Bastion account, firewall, CyberArk permissions, and per-user kubeconfig for the target Cluster have all been approved.

- Request a Bastion account from the T-DKS team (same as the AD account name).
- After receiving notification that the Bastion account has been created, request **CyberArk permissions** separately.
- Treat kubeconfig as sensitive because it may contain a private key, and restrict the per-user file permissions to `0600`.
- Verify access read-only in the approved Project, for example with `kubectl auth can-i get pods -n <project>`.

For detailed procedures, see [[50. 운영/영어 번역/04. Kubesphere Operation/06. Enable users using kubectl CLI|Enable users using kubectl CLI]].
