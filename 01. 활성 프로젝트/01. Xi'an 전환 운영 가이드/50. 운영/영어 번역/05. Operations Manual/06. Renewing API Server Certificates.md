> [!summary] Summary
> Procedure for renewing kubeadm-managed control-plane certificates, including the API Server certificates, in a KubeSphere cluster. Process the Master nodes one by one in sequence (ma01 → ma02 → ma03).

> [!warning] Important Notes
> - **Must proceed one by one in sequence**: confirm that Master 01 is operating normally before proceeding to Master 02, then proceed to Master 03.
> - **Backup is required**: back up the SSL directory and configuration files on all Master nodes before renewal.
> - **KubeSphere reconnection is required**: after certificate renewal, perform Member Cluster Unbind → Import again.

## About This Procedure

This procedure renews the certificates used by the Kubernetes control-plane components and updates the kubeconfig files that contain the renewed client certificate. Because the API Server, scheduler, and controller manager run as static Pods, renewing certificate files alone is not enough; the static Pods must also be recreated so that the running processes load the new certificates.

The work is performed on one Master node at a time to preserve control-plane availability. After each node is renewed, confirm that its static Pods and API Server health checks are normal before continuing to the next node. When all Master nodes are complete, update the Bastion Node kubeconfig files and reconnect the Member Cluster in KubeSphere using the renewed credentials.

---

## Checklist

- [ ] **1. Backup Old Certificate Directory** — Confirm backups are complete on all Master nodes.
- [ ] **2. Renew Master Node 01 Certificates** — ma01 renewed and operating normally.
- [ ] **3. Renew Master Node 02 Certificates** — ma02 renewed and operating normally.
- [ ] **4. Renew Master Node 03 Certificates** — ma03 renewed and operating normally.
- [ ] **5. Update the Bastion kubeconfig** — Update kubeconfig for the root and dspaas accounts.
- [ ] **6. Re-join KubeSphere** — Unbind → Import → restart system pods.

## 1. Backup Old Certificate Directory

Create a rollback copy of the current certificates and kubeconfig files before making any changes. These backups provide the original files needed to investigate or recover from a failed renewal.

### 1-1. Back Up the SSL Directory (All Master Nodes)

Back up `/etc/kubernetes/ssl` on every Master node. This directory contains the certificate and key files that will be replaced or updated by the renewal command.

**BASTION NODE**:

```bash
for host in ma01 ma02 ma03; do
  ssh $host mkdir -p /tmp/$(date +%Y%m%d)-apibackup
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/ssl /tmp/$(date +%Y%m%d)-apibackup/
done
```

**Verify**:

```bash
for host in ma01 ma02 ma03; do
  ssh $host sudo ls -al /tmp/$(date +%Y%m%d)-apibackup/ssl
done
```

### 1-2. Back Up the Configuration Files (All Master Nodes)

Back up the control-plane kubeconfig files that embed client certificates. These files may be regenerated during renewal and are required by administrators, the scheduler, and the controller manager when connecting to the API Server.

**BASTION NODE**:

```bash
for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/admin.conf /tmp/$(date +%Y%m%d)-apibackup/
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/scheduler.conf /tmp/$(date +%Y%m%d)-apibackup/
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/controller-manager.conf /tmp/$(date +%Y%m%d)-apibackup/
done
```

**Verify**:

```bash
for host in ma01 ma02 ma03; do
  ssh $host ls -al /tmp/$(date +%Y%m%d)-apibackup/
done
```

## 2. Renew Master Node 01 Certificates

Renew Master Node 01 first and complete all restart and health checks before touching another Master node. This limits the change to one control-plane member and keeps the remaining nodes available.

### 2-1. Renew the Master Node 01 Certificates

Run kubeadm on `ma01` to renew all kubeadm-managed certificates on that node, including the API Server certificate. This updates the certificate files on disk but does not yet reload them into the running static Pods.

**BASTION NODE**:

```bash
ssh ma01 sudo /usr/local/bin/kubeadm certs renew all
```

**Verify**:

```bash
ssh ma01 sudo /usr/local/bin/kubeadm certs check-expiration
```

### 2-2. Restart Static Pods (master01)

Remove the existing control-plane Pod sandboxes on `ma01` so that kubelet recreates the API Server, scheduler, and controller manager static Pods. The recreated processes load the renewed certificate files.

**BASTION NODE**:

```bash
ssh ma01 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)" | awk "{print \$1}" | xargs -r sudo /usr/local/bin/crictl rmp -f'
```

**Verify**:

```bash
ssh ma01 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)"'
```

### 2-3. Update the Master Node 01 kubeconfig

Replace the root account kubeconfig on `ma01` with the renewed `admin.conf`. This ensures that local administrative commands use the new embedded client certificate rather than the previous one.

**BASTION NODE**:

```bash
ssh ma01 sudo cp /etc/kubernetes/admin.conf /root/.kube/config
```

**Verify**:

```bash
ssh ma01 sudo cat /root/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

### 2-4. Check Static Pod Status (master01)

Confirm that all recreated control-plane Pods are running and that the local API Server is ready and live. Do not continue to Master Node 02 until this node has returned to a healthy state.

**Check each Pod status**:

```bash
kubectl get pod -n kube-system | grep api | grep 01
kubectl get pod -n kube-system | grep controller-manager | grep 01
kubectl get pod -n kube-system | grep scheduler | grep 01
```

**Check Events**:

```bash
POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-apiserver-" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-controller-manager" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-scheduler" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10
```

**Check API Server Health**:

```bash
# readyz
ssh ma01 curl -k https://localhost:6443/readyz?verbose

# livez
ssh ma01 curl -k https://localhost:6443/livez?verbose
```

> [!note] Confirm Before Proceeding
> Proceed to Master 02 only after all Pods on Master 01 are in the Running state and the API Server health check succeeds.

## 5. Update kubeconfig file (Bastion Node)

The Bastion Node still contains kubeconfig files with the previous embedded client certificate. Replace both operational copies with the renewed `admin.conf` from a healthy Master node so that Bastion-based `kubectl` commands continue to authenticate successfully.

### 5-1. Update the Bastion Node Root Account kubeconfig

Copy the renewed `admin.conf` from `ma01` to the root account's kubeconfig path on the Bastion Node. The verification command confirms the expiration date of the embedded client certificate.

**BASTION NODE**:

```bash
ssh ma01 'sudo cp /etc/kubernetes/admin.conf /tmp/admin.conf && sudo chown $(whoami):$(whoami) /tmp/admin.conf'
scp ma01:/tmp/admin.conf /tmp/config
sudo cp /tmp/config /root/.kube/config
sudo ls -al /root/.kube/config
```

**Verify**:

```bash
sudo cat /root/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

### 5-2. Update the Bastion Node dspaas Account kubeconfig

Update the `dspaas` account kubeconfig with the same renewed `admin.conf`. This keeps automation and operational commands executed by the `dspaas` account aligned with the renewed cluster credentials.

**BASTION NODE**:

```bash
ssh ma01 sudo cat /etc/kubernetes/admin.conf > /app/dspaas/.kube/config
```

**Verify**:

```bash
cat /app/dspaas/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

## 6. Re-join KubeSphere

KubeSphere must be given the renewed cluster credential after the Kubernetes certificates and Bastion kubeconfig files are updated. Remove the existing Member Cluster registration, import it again with the renewed kubeconfig, and restart the KubeSphere system components so that they reconnect using the new credential.

### 6-1. Member Cluster Unbind

Unbind the Member Cluster from KubeSphere to remove the existing registration that references the previous credential. Record the cluster name and tag exactly because the same identity is required during import.

1. Log in to the KubeSphere Console.
2. **Platform** → **Cluster Management** → select the Member Cluster to unbind.
3. In the left menu, go to **Cluster Settings** → **Basic Information** → **Unbind Cluster**, then click **Unbind**.
4. **Note**: Record the exact name and tag (they are required in the next step).
5. Check **"I understand the risks of this operation"** and execute Unbind.

### 6-2. Member Cluster Import

Import the Member Cluster again using the recorded name and tag together with the renewed kubeconfig. This registers the cluster connection with the new embedded client certificate.

1. Click **Cluster Management** → **Add Cluster**.
2. Use the Cluster name and tag recorded during Unbind.
3. Copy and paste the contents of the kubeconfig file.
4. Click **Create**.

### 6-3. Restart KubeSphere System Pods

Restart the KubeSphere system deployments on each Member Cluster so that the components reinitialize their connections after the cluster is imported. Verify that all restarted Pods return to a healthy state.

**BASTION NODE** (run on each Member Cluster):

```bash
kubectl rollout restart deploy -n kubesphere-system ks-apiserver ks-console ks-controller-manager
```

**Verify**:

```bash
kubectl get po -n kubesphere-system
```
