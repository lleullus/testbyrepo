> [!summary] Summary
> Procedure for exposing the Kubernetes API server externally through Ingress and controlling API access using ServiceAccount-based authentication.

> [!note] Operational Precedent
> The DKS operations environment has a precedent for exposing Prometheus through the Kubernetes Native API. The `Service -> Ingress -> kube-apiserver -> RBAC` pattern in this document and the validation method of receiving `403` when calling without authentication have the same nature as that operational case. However, this precedent is operational evidence for the `Native API entry path and permission provisioning method` only; it does not establish the scope for replacing all functions of a specific consumer system.

## 1. Create the kube-apiserver Service

The Kubernetes Native API is a core component of Kubernetes. It defines and deploys applications and maintains the desired state. Resources can be queried, created, and updated through standard HTTP verbs such as POST, PUT, PATCH, and GET.

To access a specific Kubernetes cluster API from outside, expose the kube-apiserver using an Ingress resource.

The kube-apiserver static Pod must be exposed as a Service so that the Ingress resource can reference it.

### 1-1. Define the Service resource

**service.yaml**:

```yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    component: kube-apiserver
    tier: control-plane
  name: kube-apiserver
  namespace: kube-system
spec:
  ipFamilyPolicy: SingleStack
  ports:
    - port: 443
      protocol: TCP
      targetPort: 6443
  selector:
    component: kube-apiserver
    tier: control-plane
  type: ClusterIP
```

**Key points**:
- Labels `component: kube-apiserver` and `tier: control-plane` — must match the static Pod labels
- `port: 443` (HTTPS), `targetPort: 6443` (kube-apiserver port)
- `type: ClusterIP`

### 1-2. Check the static Pod labels

```bash
kubectl get po -n kube-system kube-apiserver-xadksmamp01 -o yaml | grep labels: -A2
```

```
labels:
  component: kube-apiserver
  tier: control-plane
```

### 1-3. Create and verify the Service

```bash
kubectl get service -n kube-system kube-apiserver
```

```

```


## 2. Expose kube-apiserver via Ingress

Create an Ingress resource to make the API server accessible through an external domain.

### 2-1. Define the Ingress resource

**ingress.yaml**:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    kubernetes.io/ingress.class: nginx
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
    nginx.ingress.kubernetes.io/ssl-passthrough: "true"
  labels:
    component: kube-apiserver
    tier: control-plane
  name: kube-apiserver-ingress
  namespace: kube-system
spec:
  rules:
    - host: nativeapi.xaprdpa01.apps.dks.samsungds.net
      http:
        paths:
          - backend:
              service:
                name: kube-apiserver
                port:
                  number: 443
            path: /
            pathType: Prefix
```

**Key points**:
- `ssl-passthrough: "true"` — forward to the backend without SSL termination
- `force-ssl-redirect: "true"` — redirect HTTP to HTTPS
- Hostname: `nativeapi.xaprdpa01.apps.dks.samsungds.net`

### 2-2. Source IP/CIDR restrictions

When exposing the Native API externally, access control is mandatory. At a minimum, allow only the caller's source IP/CIDR.

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/whitelist-source-range: "10.0.0.0/24,10.10.0.0/24"
```

If the caller's CIDR has not been finalized, do not consider Ingress creation complete.

### 2-3. Create and verify the Ingress




## 3. API Access (Authentication)

Accessing the API through the Ingress domain requires a ServiceAccount-based authentication token.

> [!warning] Scope Boundary
> As with the Prometheus operational precedent, this procedure covers only the `Native API access path and permission model`. Which resources a specific system calls and in what order, which defaults it uses, and which response structure it maintains are outside the scope of this document.

> [!warning] RBAC Design Principle
> When designing RBAC for a system, do not begin by defining the minimum permissions for only the few calls currently visible. First identify the complete functional scope that the system must replace without the existing intermediary layer, calculate the permissions required within that scope, and then reduce them according to least privilege.

### 3-1. Attempt access without authentication (failure)

```bash
curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
```

```json
{
  "kind": "Status",
  "apiVersion": "v1",
  "status": "Failure",
  "message": "pods is forbidden: User \"system:anonymous\" cannot list resource \"pods\" in API group \"\" at the cluster scope",
  "reason": "Forbidden",
  "code": 403
}
```

### 3-2. Create the ServiceAccount and Role

**token.yaml**:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: test-role
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: test-rb
  namespace: default
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: test-role
subjects:
  - kind: ServiceAccount
    name: test-sa
    namespace: default
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: test-sa
  namespace: default
```
