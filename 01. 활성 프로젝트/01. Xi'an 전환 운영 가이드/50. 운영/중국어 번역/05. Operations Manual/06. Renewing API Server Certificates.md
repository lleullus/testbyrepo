> [!summary] 摘要
> 在 KubeSphere 集群中更新由 kubeadm 管理的控制平面证书（包括 API Server 证书）的操作流程。按顺序逐个处理 Master 节点（ma01 → ma02 → ma03）。

> [!warning] 注意事项
> - **必须按顺序逐个进行**：确认 Master 01 运行正常后再处理 Master 02，然后处理 Master 03。
> - **必须备份**：更新前备份所有 Master 节点的 SSL 目录和配置文件。
> - **需要重新连接 KubeSphere**：证书更新后，再次执行 Member Cluster Unbind → Import。

## 关于本流程

本流程用于更新 Kubernetes 控制平面组件使用的证书，并更新包含新客户端证书的 kubeconfig 文件。由于 API Server、scheduler 和 controller manager 以静态 Pod 方式运行，仅更新证书文件并不足够；还必须重新创建静态 Pod，使运行中的进程加载新证书。

为保持控制平面的可用性，每次仅处理一个 Master 节点。每个节点更新后，必须确认其静态 Pod 和 API Server 健康检查均正常，才能继续处理下一个节点。所有 Master 节点处理完成后，更新 Bastion Node 上的 kubeconfig 文件，并使用更新后的凭据在 KubeSphere 中重新连接 Member Cluster。

---

## 检查清单

- [ ] **1. 备份旧证书目录** — 确认所有 Master 节点均已完成备份。
- [ ] **2. 更新 Master Node 01 证书** — ma01 已更新且运行正常。
- [ ] **3. 更新 Master Node 02 证书** — ma02 已更新且运行正常。
- [ ] **4. 更新 Master Node 03 证书** — ma03 已更新且运行正常。
- [ ] **5. 更新 Bastion kubeconfig** — 更新 root 和 dspaas 账号的 kubeconfig。
- [ ] **6. 重新加入 KubeSphere** — Unbind → Import → 重启系统 Pod。

---

## 1. 备份旧证书目录

进行任何更改前，先创建当前证书和 kubeconfig 文件的回滚副本。更新失败时，可使用这些备份的原始文件进行问题调查或恢复。

### 1-1. 备份 SSL 目录（所有 Master 节点）

备份每个 Master 节点上的 `/etc/kubernetes/ssl`。该目录包含将由更新命令替换或更新的证书和密钥文件。

**BASTION NODE**：

```bash
for host in ma01 ma02 ma03; do
  ssh $host mkdir -p /tmp/$(date +%Y%m%d)-apibackup
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/ssl /tmp/$(date +%Y%m%d)-apibackup/
done
```

**验证**：

```bash
for host in ma01 ma02 ma03; do
  ssh $host sudo ls -al /tmp/$(date +%Y%m%d)-apibackup/ssl
done
```

### 1-2. 备份配置文件（所有 Master 节点）

备份嵌入了客户端证书的控制平面 kubeconfig 文件。这些文件可能会在更新期间重新生成，是管理员、scheduler 和 controller manager 连接 API Server 时所必需的。

**BASTION NODE**：

```bash
for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/admin.conf /tmp/$(date +%Y%m%d)-apibackup/
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/scheduler.conf /tmp/$(date +%Y%m%d)-apibackup/
done

for host in ma01 ma02 ma03; do
  ssh $host sudo cp -rp /etc/kubernetes/controller-manager.conf /tmp/$(date +%Y%m%d)-apibackup/
done
```

**验证**：

```bash
for host in ma01 ma02 ma03; do
  ssh $host ls -al /tmp/$(date +%Y%m%d)-apibackup/
done
```

## 2. 更新 Master Node 01 证书

首先更新 Master Node 01，并在处理其他 Master 节点前完成所有重启和健康检查。这样可将变更范围限制在一个控制平面成员，同时保持其余节点可用。

### 2-1. 更新 Master Node 01 证书

在 `ma01` 上运行 kubeadm，更新该节点上由 kubeadm 管理的所有证书，包括 API Server 证书。此操作会更新磁盘上的证书文件，但运行中的静态 Pod 尚不会重新加载这些文件。

**BASTION NODE**：

```bash
ssh ma01 sudo /usr/local/bin/kubeadm certs renew all
```

**验证**：

```bash
ssh ma01 sudo /usr/local/bin/kubeadm certs check-expiration
```

### 2-2. 重启静态 Pod（master01）

删除 `ma01` 上现有的控制平面 Pod sandbox，使 kubelet 重新创建 API Server、scheduler 和 controller manager 静态 Pod。重新创建的进程将加载更新后的证书文件。

**BASTION NODE**：

```bash
ssh ma01 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)" | awk "{print \$1}" | xargs -r sudo /usr/local/bin/crictl rmp -f'
```

**验证**：

```bash
ssh ma01 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)"'
```

### 2-3. 更新 Master Node 01 kubeconfig

使用更新后的 `admin.conf` 替换 `ma01` 上 root 账号的 kubeconfig。这样可确保本地管理命令使用新嵌入的客户端证书，而非原有证书。

**BASTION NODE**：

```bash
ssh ma01 sudo cp /etc/kubernetes/admin.conf /root/.kube/config
```

**验证**：

```bash
ssh ma01 sudo cat /root/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

### 2-4. 检查静态 Pod 状态（master01）

确认所有重新创建的控制平面 Pod 均在运行，并且本地 API Server 已就绪且存活。在该节点恢复健康状态前，不得继续处理 Master Node 02。

**检查各 Pod 状态**：

```bash
kubectl get pod -n kube-system | grep api | grep 01
kubectl get pod -n kube-system | grep controller-manager | grep 01
kubectl get pod -n kube-system | grep scheduler | grep 01
```

**检查 Events**：

```bash
POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-apiserver-" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-controller-manager" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-scheduler" \
  | grep "01$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10
```

**检查 API Server 健康状态**：

```bash
# readyz
ssh ma01 curl -k https://localhost:6443/readyz?verbose

# livez
ssh ma01 curl -k https://localhost:6443/livez?verbose
```

> [!note] 继续操作前确认
> 仅当 Master 01 上的所有 Pod 均处于 Running 状态且 API Server 健康检查成功后，才能继续处理 Master 02。

## 3. 更新 Master Node 02 证书

仅在确认 Master Node 01 健康后，才在 Master Node 02 上重复相同的更新流程。重启 `ma02` 期间，其余 Master 节点将继续提供控制平面服务。

### 3-1. 更新 Master Node 02 证书

在 `ma02` 上运行 kubeadm，更新该节点上由 kubeadm 管理的所有证书。更新后的文件将保留在磁盘上，直到下一步重新创建控制平面静态 Pod 后才会被加载。

**BASTION NODE**：

```bash
ssh ma02 sudo /usr/local/bin/kubeadm certs renew all
```

**验证**：

```bash
ssh ma02 sudo /usr/local/bin/kubeadm certs check-expiration
```

### 3-2. 重启静态 Pod（master02）

删除 `ma02` 上现有的控制平面 Pod sandbox，使 kubelet 重新创建静态 Pod，并使用更新后的证书启动各组件。

**BASTION NODE**：

```bash
ssh ma02 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)" | awk "{print \$1}" | xargs -r sudo /usr/local/bin/crictl rmp -f'
```

**验证**：

```bash
ssh ma02 'sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)"'
```

### 3-3. 更新 Master Node 02 kubeconfig

使用更新后的 `admin.conf` 替换 `ma02` 上 root 账号的 kubeconfig，使本地管理访问使用新的客户端证书。

**BASTION NODE**：

```bash
ssh ma02 sudo cp /etc/kubernetes/admin.conf /root/.kube/config
```

**验证**：

```bash
ssh ma02 sudo cat /root/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

### 3-4. 检查静态 Pod 状态（master02）

确认重新创建的静态 Pod 均在运行，并且本地 API Server 健康端点检查成功。仅在 `ma02` 健康后，才能继续处理 Master Node 03。

**检查各 Pod 状态**：

```bash
kubectl get pod -n kube-system | grep api | grep 02
kubectl get pod -n kube-system | grep controller-manager | grep 02
kubectl get pod -n kube-system | grep scheduler | grep 02
```

**检查 Events**：

```bash

  | grep "^pod/kube-apiserver-" \
  | grep "02$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-controller-manager" \
  | grep "02$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10

POD=$(kubectl get pods -n kube-system -o name \
  | grep "^pod/kube-scheduler" \
  | grep "02$" \
  | head -n1); kubectl describe po -n kube-system "${POD#pod/}" | grep Events: -A10
```

**检查 API Server 健康状态**：

```bash
# readyz
ssh ma02 curl -k https://localhost:6443/readyz?verbose

# livez
ssh ma02 curl -k https://localhost:6443/livez?verbose
```

> [!note] 继续操作前确认
> 仅当 Master 02 上的所有 Pod 均处于 Running 状态且 API Server 健康检查成功后，才能继续处理 Master 03。

## 4. 更新 Master Node 03 证书

在 Master Node 01 和 02 均恢复正常运行后，再更新最后一个 Master 节点。在 `ma03` 上完成相同检查，即可确认所有控制平面成员均已使用更新后的证书。

### 4-1. 更新 Master Node 03 证书

在 `ma03` 上运行 kubeadm，更新该节点上由 kubeadm 管理的所有证书。与前面的节点相同，运行中的组件将继续使用旧证书，直到重新创建其静态 Pod。

## 5. 更新 kubeconfig 文件（Bastion Node）

Bastion Node 上的 kubeconfig 文件仍包含原有的嵌入式客户端证书。使用健康 Master 节点上更新后的 `admin.conf` 替换两份运维副本，确保从 Bastion 执行的 `kubectl` 命令可继续成功进行身份验证。

### 5-1. 更新 Bastion Node root 账号的 kubeconfig

将 `ma01` 上更新后的 `admin.conf` 复制到 Bastion Node 上 root 账号的 kubeconfig 路径。验证命令用于确认嵌入式客户端证书的到期日期。

**BASTION NODE**：

```bash
ssh ma01 'sudo cp /etc/kubernetes/admin.conf /tmp/admin.conf && sudo chown $(whoami):$(whoami) /tmp/admin.conf'
scp ma01:/tmp/admin.conf /tmp/config
sudo cp /tmp/config /root/.kube/config
sudo ls -al /root/.kube/config
```

**验证**：

```bash
sudo cat /root/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

### 5-2. 更新 Bastion Node dspaas 账号的 kubeconfig

使用相同的更新后 `admin.conf` 更新 `dspaas` 账号的 kubeconfig。这样可确保由 `dspaas` 账号执行的自动化任务和运维命令使用更新后的集群凭据。

**BASTION NODE**：

```bash
ssh ma01 sudo cat /etc/kubernetes/admin.conf > /app/dspaas/.kube/config
```

**验证**：

```bash
cat /app/dspaas/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -text | grep -i 'after'
```

## 6. 重新加入 KubeSphere

更新 Kubernetes 证书和 Bastion kubeconfig 文件后，必须向 KubeSphere 提供更新后的集群凭据。移除现有的 Member Cluster 注册，使用更新后的 kubeconfig 重新导入，然后重启 KubeSphere 系统组件，使其使用新凭据重新连接。

### 6-1. Member Cluster Unbind

从 KubeSphere 解绑 Member Cluster，以移除引用原有凭据的现有注册。请准确记录集群名称和 tag，因为导入时必须使用相同的标识。

1. 登录 KubeSphere Console。
2. 进入 **Platform** → **Cluster Management** → 选择要解绑的 Member Cluster。
3. 在左侧菜单中进入 **Cluster Settings** → **Basic Information** → **Unbind Cluster**，然后点击 **Unbind**。
4. **注意**：准确记录名称和 tag（下一步需要使用）。
5. 勾选 **"I understand the risks of this operation"**，然后执行 Unbind。

### 6-2. Member Cluster Import

使用已记录的名称和 tag，以及更新后的 kubeconfig，再次导入 Member Cluster。此操作会使用新的嵌入式客户端证书注册集群连接。

1. 点击 **Cluster Management** → **Add Cluster**。
2. 使用 Unbind 时记录的 Cluster name 和 tag。
3. 复制并粘贴 kubeconfig 文件内容。
4. 点击 **Create**。

### 6-3. 重启 KubeSphere 系统 Pod

在每个 Member Cluster 上重启 KubeSphere 系统 deployment，使各组件在集群导入后重新初始化连接。确认所有重启的 Pod 均恢复健康状态。

**BASTION NODE**（在每个 Member Cluster 上执行）：

```bash
kubectl rollout restart deploy -n kubesphere-system ks-apiserver ks-console ks-controller-manager
```

**验证**：

```bash
kubectl get po -n kubesphere-system
```
