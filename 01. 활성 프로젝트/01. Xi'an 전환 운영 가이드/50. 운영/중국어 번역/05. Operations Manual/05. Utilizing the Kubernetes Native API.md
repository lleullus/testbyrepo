> [!summary] 摘要
> 通过 Ingress 将 Kubernetes API 服务器暴露到外部，并通过基于 ServiceAccount 的认证控制 API 访问的步骤

> [!note] 运营先例
> DKS 运营环境中有通过 Kubernetes Native API 暴露 Prometheus 的先例。本文档的 `Service -> Ingress -> kube-apiserver -> RBAC` 模式以及 `无认证调用时返回 403` 的验证方式，与该运营案例具有相同性质。但该先例仅是 `Native API 入口路径和权限提供方式` 的运营依据，并不能证明可以完全替代特定消费系统的全部功能范围。

## 1. 创建 kube-apiserver Service

Kubernetes Native API 是 Kubernetes 的核心组件，负责定义和部署应用并维持期望状态。通过标准 HTTP 动词（POST、PUT、PATCH、GET 等），可以查询、创建和更新资源。

要从外部访问特定 Kubernetes 集群的 API，可以使用 Ingress 资源暴露 kube-apiserver。

必须将 kube-apiserver static Pod 暴露为 Service，Ingress 资源才能引用。

### 1-1. 定义 Service 资源

**service.yaml**：

```yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    component: kube-apiserver
    tier: control-plane
  name: kube-apiserver
  namespace: kube-system
spec:
  ipFamilyPolicy: SingleStack
  ports:
    - port: 443
      protocol: TCP
      targetPort: 6443
  selector:
    component: kube-apiserver
    tier: control-plane
  type: ClusterIP
```

**核心**：
- 标签 `component: kube-apiserver`、`tier: control-plane` — 必须与 static Pod 标签一致
- `port: 443`（HTTPS），`targetPort: 6443`（kube-apiserver 端口）
- `type: ClusterIP`

### 1-2. 确认 static Pod 标签

```bash
kubectl get po -n kube-system kube-apiserver-xadksmamp01 -o yaml | grep labels: -A2
```

```
labels:
  component: kube-apiserver
  tier: control-plane
```

### 1-3. 创建并确认 Service

```bash
kubectl get service -n kube-system kube-apiserver
```

```
NAME            TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
kube-apiserver  ClusterIP   10.102.90.13   <none>        443/TCP   4s
```

```bash
kubectl describe service -n kube-system kube-apiserver
```

```
Name:              kube-apiserver
Namespace:         kube-system
Labels:            component=kube-apiserver
                   tier=control-plane
Selector:          component=kube-apiserver,tier=control-plane
Type:              ClusterIP
IP Family Policy:  SingleStack
IP:                10.102.90.13
Port:              <unset>  443/TCP
TargetPort:        6443/TCP
Endpoints:         109.156.22.58:6443,109.156.22.59:6443,109.156.22.60:6443
Session Affinity:  None
```

> [!note] 确认事项
> Endpoints 必须与 kube-apiserver Pod IP 一致

## 2. 通过 Ingress 对外暴露 kube-apiserver

创建 Ingress 资源后，可以通过外部域名访问 API 服务器。

### 2-1. 定义 Ingress 资源

**ingress.yaml**：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    kubernetes.io/ingress.class: nginx
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
    nginx.ingress.kubernetes.io/ssl-passthrough: "true"
  labels:
    component: kube-apiserver
    tier: control-plane
  name: kube-apiserver-ingress
  namespace: kube-system
spec:
  rules:
    - host: nativeapi.xaprdpa01.apps.dks.samsungds.net
      http:
        paths:
          - backend:
              service:
                name: kube-apiserver
                port:
                  number: 443
            path: /
            pathType: Prefix
```

**核心**：
- `ssl-passthrough: "true"` — 不终止 SSL，直接转发到后端
- `force-ssl-redirect: "true"` — 将 HTTP 重定向到 HTTPS
- 主机名：`nativeapi.xaprdpa01.apps.dks.samsungds.net`

### 2-2. Source IP/CIDR 限制

将 Native API 暴露到外部时，访问控制是必需的。至少应仅允许调用方所在的 Source IP/CIDR。

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/whitelist-source-range: "10.0.0.0/24,10.10.0.0/24"
```

如果调用方 CIDR 尚未确定，则不能视为 Ingress 创建完成。

### 2-3. 创建并确认 Ingress

```bash
kubectl get ing -n kube-system kube-apiserver-ingress
```

```

kube-apiserver-ingress    <none>  nativeapi.xaprdpa01.apps.dks.samsungds.net  109.156.22.61,109.156.22.62,109.156.22.63   80    5s
```

```bash
kubectl describe ing -n kube-system kube-apiserver-ingress
```

```

Labels:           component=kube-apiserver
                  tier=control-plane
Namespace:        kube-system
Address:          109.156.22.61,109.156.22.62,109.156.22.63
```

> - Ingress 地址必须与 Ingress Controller 地址一致
> - Backend 必须与 kube-apiserver Pod 地址一致

## 3. API 访问（认证）

通过 Ingress 域名访问 API 时，需要基于 ServiceAccount 的认证 Token。

> [!warning] 适用边界
> 如同 Prometheus 运营先例，本步骤仅涉及 `Native API 入口路径和权限提供方式`。特定系统将以何种顺序调用哪些资源、使用哪些默认值、维持何种响应结构，均超出本文档范围。

> [!warning] RBAC 设计原则
> 设计某个系统的 RBAC 时，不应先从 `当前可见的几个调用所需的最小权限` 开始确定。应先识别该系统在没有现有中间层的情况下也必须完整替代的功能范围，在该范围内估算所需权限后，再依据最小权限原则收敛权限。

### 3-1. 尝试无认证访问（失败）

```bash
curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
```

```json
{
  "kind": "Status",
  "apiVersion": "v1",
  "status": "Failure",
  "message": "pods is forbidden: User \"system:anonymous\" cannot list resource \"pods\" in API group \"\" at the cluster scope",
  "reason": "Forbidden",
  "code": 403
}
```

### 3-2. 创建 ServiceAccount 和 Role

**token.yaml**：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: test-role
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: test-rb
  namespace: default
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: test-role
subjects:
  - kind: ServiceAccount
    name: test-sa
    namespace: default
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: test-sa
  namespace: default
```

### 3-3. 确认 Role/RoleBinding/ServiceAccount

```bash
kubectl describe role test-role
```

```
Name:         test-role
Labels:       <none>
Annotations:  <none>
PolicyRule:
  Resources  Non-Resource URLs  Resource Names  Verbs
  ---------  -----------------  --------------  -----
  pods       []                 []              [get list]
```

```bash
kubectl describe rolebinding test-rb
```

```
Name:         test-rb
Labels:       <none>
Annotations:  <none>
Role:
  Kind:  Role
  Name:  test-role
Subjects:
  Kind          Name    Namespace
  ----          ----    ---------
  ServiceAccount  test-sa  default
```

```bash
kubectl describe sa test-sa
```

```
Name:                test-sa
Namespace:           default
Labels:              <none>
Annotations:         <none>
Image pull secrets:  <none>
Mountable secrets:   test-sa-token-hbtb5
Tokens:              test-sa-token-hbtb5
```

### 3-4. 确认并设置 Token

```bash
kubectl describe secret test-sa-token-czlnb
```

```
Name:         test-sa-token-czlnb
Namespace:    default
Labels:       <none>
Annotations:  kubernetes.io/service-account.name: test-sa
              kubernetes.io/service-account.uid: 5d3c9d64-d2f1-41f8-8ffc-6ebc11f180c6
Type:         kubernetes.io/service-account-token
Data
====
ca.crt:     1099 bytes
namespace:  7 bytes
token:      eyJhbGc...
```

```bash
export TOKEN=eyJhbGc...
echo $TOKEN
```

### 3-5. 使用 Token 访问 API（成功）

```bash
curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods \
  -H "Authorization: Bearer $TOKEN"
```
