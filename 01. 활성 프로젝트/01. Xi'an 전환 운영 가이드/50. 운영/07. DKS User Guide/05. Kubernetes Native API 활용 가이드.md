# Kubernetes Native API 활용 가이드

> [!summary] 요약
> Xi'an Kubernetes Native API는 `nativeapi` FQDN을 통해 kube-apiserver에 접근하고 ServiceAccount Bearer Token과 RBAC으로 API 권한을 제한한다. 사용자는 운영팀이 제공한 FQDN·Token·Namespace·허용 API 범위를 확인한 뒤 `curl`로 호출한다.

> [!warning] 적용 경계
> 이 문서는 **이미 Native API 경로와 RBAC이 구성된 환경에서 API를 사용하는 방법**을 설명한다. kube-apiserver Service, Ingress, source IP 제한, ServiceAccount/RBAC 생성은 운영자 작업이며 상세 구성은 [[50. 운영/05. Operations Manual/05. Utilizing the Kubernetes Native API|Utilizing the Kubernetes Native API]]를 따른다.

## 1. Xi'an Native API 주소

| Cluster | Native API FQDN | Ingress VIP-B |
|---|---|---:|
| `prd-host-pa01-xas` | `nativeapi.xaprdpa01.mgmt.dks.samsungds.net` | `109.156.25.46` |
| `prd-apps-pa01-xas` | `nativeapi.xaprdpa01.apps.dks.samsungds.net` | `109.156.25.60` |
| `dev-apps-pa01-xas` | `nativeapi.xadevpa01.apps.dks.samsungds.net` | `109.156.25.75` |

대표 예시는 기존 Native API 운영 문서에 Service/Ingress 검증값이 남아 있는 `prd-apps-pa01-xas`를 사용한다.

```text
API Client
→ nativeapi.xaprdpa01.apps.dks.samsungds.net
→ VIP-B 109.156.25.60
→ Router 109.156.22.61 / 109.156.22.62 / 109.156.22.63
→ kube-system/kube-apiserver Service :443
→ Master 109.156.22.58 / 109.156.22.59 / 109.156.22.60 :6443
→ ServiceAccount + RBAC
```

## 2. 사용 전에 확인할 항목

운영팀으로부터 다음 네 가지를 확인한다.

```text
1. Native API FQDN
2. 승인된 Source IP/CIDR
3. ServiceAccount Token
4. 사용할 Namespace와 허용된 API 범위
```

Token은 문서, 메일 본문, 채팅, shell history에 직접 기록하지 않는다. 승인된 비밀 전달 경로로 받은 Token은 작업용 파일에 저장하고 권한을 제한한다.

```console
[user@api-client ~]$ chmod 600 nativeapi.token
[user@api-client ~]$ ls -l nativeapi.token
-rw-------. 1 user user 1167 Aug 13 17:10 nativeapi.token
```

`nativeapi.token`의 내용 자체는 화면에 출력하지 않는다.

## 3. Native API 경로가 열려 있는지 확인

`prd-apps-pa01-xas` 예시다.

```console
[user@api-client ~]$ getent hosts nativeapi.xaprdpa01.apps.dks.samsungds.net
109.156.25.60   nativeapi.xaprdpa01.apps.dks.samsungds.net

[user@api-client ~]$ nc -vz -w 3 109.156.25.60 443
Ncat: Version 7.92 ( https://nmap.org/ncat )
Ncat: Connected to 109.156.25.60:443.
Ncat: 0 bytes sent, 0 bytes received in 0.01 seconds.
```

DNS가 `109.156.25.60`으로 해석되고 TCP `443`이 연결되면 Native API 진입 경로까지는 도달한 것이다.

## 4. Token 없이 호출하면 거부되는지 확인

인증 없이 Pod 목록을 조회한다.

```console
[user@api-client ~]$ curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
{
  "kind": "Status",
  "apiVersion": "v1",
  "status": "Failure",
  "message": "pods is forbidden: User \"system:anonymous\" cannot list resource \"pods\" in API group \"\" at the cluster scope",
  "reason": "Forbidden",
  "code": 403
}
```

기존 Xi'an Native API 검증에서는 무인증 요청이 위와 같이 `403 Forbidden`으로 거부됐다. 환경 설정에 따라 `401 Unauthorized`로 거부될 수도 있으며, 핵심은 **Token 없는 요청이 정상 데이터에 접근하지 못하는 것**이다.

아래 예시는 기존 Xi'an Native API 검증 기록과 동일하게 `curl -k`를 사용한다. `-k`는 인증서 검증을 생략하므로 상시 연동 시스템에서는 승인된 kube-apiserver 인증서/CA 검증 방식을 별도로 적용한다.

## 5. ServiceAccount Token으로 Pod 목록 조회

기존 운영 예시는 `default` Namespace의 `test-sa`에 `pods`의 `get`, `list` 권한을 부여했다.

Token 파일을 사용해 Pod 목록을 호출한다.

```console
[user@api-client ~]$ curl -k -H "Authorization: Bearer $(cat nativeapi.token)" https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
{
  "kind": "PodList",
  "apiVersion": "v1",
  "metadata": {
    "resourceVersion": "33931470"
  },
  "items": [
    {
      "metadata": {
        "name": "ing-test-686849b47f-qvks4",
        "namespace": "default",
        "labels": {
          "app": "ing-test"
        }
      }
    }
  ]
}
```

`kind: PodList`와 `items`가 반환되면 Token 인증과 `list pods` 권한이 정상이다.

## 6. 특정 Pod 한 개 조회

앞에서 확인한 Pod 이름을 그대로 사용한다.

```console
[user@api-client ~]$ curl -k -H "Authorization: Bearer $(cat nativeapi.token)" https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods/ing-test-686849b47f-qvks4
{
  "kind": "Pod",
  "apiVersion": "v1",
  "metadata": {
    "name": "ing-test-686849b47f-qvks4",
    "namespace": "default"
  },
  "status": {
    "phase": "Running"
  }
}
```

Pod suffix와 resourceVersion 같은 동적 값은 실행 시점마다 달라질 수 있다. 현재 API 응답에 나온 이름을 사용한다.

## 7. API URL 구성 방법

Kubernetes Native API는 리소스 종류에 따라 URL이 달라진다.

### Core API

Pod, Service, Secret, Namespace 등은 `/api/v1`을 사용한다.

```text
Pod 목록
/api/v1/namespaces/default/pods

Pod 1개
/api/v1/namespaces/default/pods/ing-test-686849b47f-qvks4

Service 목록
/api/v1/namespaces/default/services
```

### API Group

Deployment, StatefulSet 등은 `/apis` 아래의 API Group을 사용한다.

```text
Deployment 목록
/apis/apps/v1/namespaces/default/deployments
```

단, URL을 알고 있어도 ServiceAccount에 해당 리소스 권한이 없으면 `403 Forbidden`이 정상이다. 필요한 API가 추가되면 운영팀이 업무 범위를 확인한 뒤 RBAC을 조정한다.

## 8. 현재 권한 범위 확인

기존 Native API 검증용 `test-sa`는 `default` Namespace의 Pod `get`, `list`만 허용하는 예시다.

운영자는 다음처럼 실제 권한을 확인할 수 있다.

```console
[dspaas@xadksbtmp01 ~]$ kubectl auth can-i --as=system:serviceaccount:default:test-sa list pods -n default
yes

[dspaas@xadksbtmp01 ~]$ kubectl auth can-i --as=system:serviceaccount:default:test-sa create deployments -n default
no
```

사용자는 `no`가 나오는 API를 임의로 우회하지 않는다. 필요한 업무 동작을 운영팀에 전달하고 승인된 범위만 추가한다.

## 9. 작업 후 Token 파일 정리

일회성 검증이라면 Token 파일을 남겨두지 않는다.

```console
[user@api-client ~]$ rm -f nativeapi.token
[user@api-client ~]$ ls nativeapi.token
ls: cannot access 'nativeapi.token': No such file or directory
```

상시 연동 시스템은 파일 수동 배포가 아니라 승인된 Secret 관리 방식으로 Token을 관리한다.

## 정상 확인

```text
Native API FQDN이 대상 Cluster VIP-B로 해석됨
→ TCP 443 연결
→ 무인증 요청 거부
→ 승인된 ServiceAccount Token 요청 성공
→ 허용된 API는 정상 응답
→ 허용하지 않은 API는 403으로 차단
```
