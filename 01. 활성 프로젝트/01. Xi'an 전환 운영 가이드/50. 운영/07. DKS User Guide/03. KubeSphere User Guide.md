## 1. AD 계정 등록

KubeSphere 사용자 신청은 AD 계정을 기준으로 처리한다. SCS AD 도메인, 그룹 경로, 보안그룹과 최종 로그인 방식은 확정 전이므로 운영팀 확인 없이 기존 Taylor 값을 사용하지 않는다.

### AD 보안그룹 정보

| 항목 | 값 |
|------|------|
| 도메인 | 운영팀 확인 필요 |
| 위치 | 운영팀 확인 필요 |
| 보안그룹 | 운영팀 확인 필요 |

## 3. 권한 관리

Namespace와 동일한 Project에서 사용자에게 역할을 부여한다. 신청서의 `Admin`은 `project-operator`, `User`는 `project-viewer`에 매핑하며, 멤버 관리가 가능한 `project-admin`은 별도 운영 정책에 따른다.

| 역할 | 설명 |
|------|------|
| **project-admin** | 프로젝트 리소스·설정·멤버 관리. 별도 운영 정책으로 부여 |
| **project-operator** | 사용자·역할·프로젝트 설정을 제외한 리소스 생성·수정·삭제. 신청서 `Admin` 매핑 |
| **project-viewer** | 프로젝트 리소스 조회 전용. 신청서 `User` 매핑 |

### Operator 권한 부여 절차

1. `project-admin` 권한 계정으로 로그인
2. **Projects** → 프로젝트 선택 → **Project Settings** → **Project Members**
3. **Invite** 또는 **+User** 클릭 → Workspace에 초대된 멤버 계정 추가
4. 역할에서 **project-operator** 선택 → **OK**

## 4. PVC 배포 (UI)

### 4-1. PVC 생성

1. KubeSphere Dashboard → 대상 프로젝트 선택 → **Storage** → **Volumes** → **Create**

### 4-2. 기본 정보

| 항목 | 입력 | 비고 |
|------|------|------|
| Name | `<pvc-name>` | 필수 |
| Alias | — | 선택 |
| Description | — | 선택 |

### 4-3. PVC 옵션 설정

| 항목 | 선택 | 비고 |
|------|------|------|
| Storage Class | `scs-netapp-qtree-nfs-sc-delete` | Xi'an NetApp NFS. 실제 UI 목록 또는 `kubectl get sc`로 재확인 |
| Access Mode | RWX | 공유 마운트가 필요하고 StorageClass가 지원하는 경우만 선택 |
| Volume Capacity | 승인된 Quota 이내의 용량 입력 | — |

### 4-4. 생성

**Advanced Settings** → **Create**

## 5. Image Secret 배포 (UI)

1. Deployment와 같은 프로젝트에서 **Configuration** → **Secrets** → **Create** 클릭
2. **Basic Information**에서 Secret Name 입력 → Next
3. **Data Settings**에서 Secret 옵션 설정
4. **Type**: Image registry information 선택
5. **Registry Address**: `xa.dcr.dks.samsungds.net` 입력
6. **Username**: 저장소 계정 입력
7. **Password**: 저장소 비밀번호 입력
8. **Create** 클릭

Secret은 생성만으로 적용되지 않는다. Deployment의 Image Pull Secret에서 이 Secret을 명시적으로 선택하고, 비밀번호를 문서나 YAML에 기록하지 않는다.

## 6. Deployment 배포 (UI)

### 6-1. Deployment 생성

1. KubeSphere Dashboard → 프로젝트 선택 → **Application Workloads** → **Workloads** → **Deployments** → **Create**

### 6-2. 기본 정보

| 항목 | 입력 | 비고 |
|------|------|------|
| Name | `<deployment-name>` | 필수 |
| Alias | — | 선택 |
| Description | — | 선택 |

### 6-3. 옵션 설정

| 항목 | 입력 | 비고 |
|------|------|------|
| Pod Replicas | 복제 수 입력 | — |
| Container Image | `xa.dcr.dks.samsungds.net/<harbor-project>/<image>:<tag>` | 실제 Harbor Project·Repository·Tag로 교체 |

Pod Label과 Deployment Selector를 일치시키고 컨테이너의 CPU·Memory `requests`와 `limits`를 설정한다. Private 이미지는 같은 프로젝트의 Image Pull Secret을 연결한다.

### 6-4. PVC 마운트

1. **Volume Settings** → **Mount Volume** → **Existing Volume** 선택
2. 볼륨 선택 → PVC 이름 선택
3. 마운트 경로에 컨테이너 내부 절대 경로 입력(예: `/data`)

### 6-5. 생성

**Advanced Settings** → **Create**

## 8. Route 배포 (Ingress)

KubeSphere Route는 Kubernetes Ingress이다. HostName은 대상 환경의 도메인 패턴을 사용한다: 운영 `*.xaprdpa01.apps.dks.samsungds.net`, 개발 `*.xadevpa01.apps.dks.samsungds.net`.

### 8-1. Route 생성

1. KubeSphere Dashboard → 프로젝트 선택 → **Application Workloads** → **Routes** 또는 **Routers** → **Create**

### 8-2. Route 이름

| 항목 | 입력 | 비고 |
|------|------|------|
| Name | `<route-name>` | 필수 |
| Alias | — | 선택 |
| Description | — | 선택 |

### 8-3. Route 옵션 설정

| 항목 | 입력 | 비고 |
|------|------|------|
| Add Route Rule | Specify Domain 선택 | — |
| HostName | 대상 환경의 승인된 FQDN 입력 | 운영·개발 도메인 혼용 금지 |
| Protocol | HTTP/HTTPS 선택 | — |
| Paths | path, 연결 서비스, 포트 입력 | — |

### 8-4. 생성

**Advanced Settings** → **Create**

## 9. YAML 기반 배포

### 9-1. PVC YAML

1. KubeSphere Dashboard → **Storage** → **Volumes** → **Create** → **Edit YAML**

아래 예시의 `example-project`, 리소스명, 용량은 승인된 실제 값으로 교체한다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  namespace: example-project
  name: nginx-test
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 10Gi
  storageClassName: scs-netapp-qtree-nfs-sc-delete
  volumeMode: Filesystem
```

### 9-2. Deployment YAML

1. KubeSphere Dashboard → 프로젝트 선택 → **Application Workloads** → **Workloads** → **Deployments** → **Create** → **Edit YAML**

`image`와 `imagePullSecrets.name`은 같은 Project에서 확인한 실제 값으로 교체한다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  namespace: example-project
  name: nginx-test
  labels:
    app: nginx-test
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-test
  template:
    metadata:
      labels:
        app: nginx-test
    spec:
      imagePullSecrets:
        - name: harbor-registry-secret
      containers:
        - image: xa.dcr.dks.samsungds.net/example-project/nginx:latest
          imagePullPolicy: IfNotPresent
          name: nginx
          ports:
            - containerPort: 80
              name: http-test
              protocol: TCP
          volumeMounts:
            - mountPath: /data
              name: nginx-data
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
      volumes:
        - name: nginx-data
          persistentVolumeClaim:
            claimName: nginx-test
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25%
      maxSurge: 25%
```

### 9-3. Service YAML

1. KubeSphere Dashboard → 프로젝트 선택 → **Application Workloads** → **Services** → **Create** → **Specify Workload** → **Edit YAML**

```yaml
apiVersion: v1
kind: Service
metadata:
  namespace: example-project
  name: nginx-test
  labels:
    app: nginx-test
spec:
  sessionAffinity: None
  ports:
    - name: http-test
      port: 80
      protocol: TCP
      targetPort: 80
  selector:
    app: nginx-test
```

### 9-4. Route YAML

1. KubeSphere Dashboard → 프로젝트 선택 → **Application Workloads** → **Routes** → **Create** → **Edit YAML**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  namespace: example-project
  name: nginx-test
spec:
  rules:
    - host: nginx-test.xadevpa01.apps.dks.samsungds.net
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-test
                port:
                  number: 80
```

## 10. Autoscaling 설정

1. 프로젝트 선택 → **Application Workloads** → **Workloads** → Deployment 선택
2. **More** → **Edit Autoscaling** 클릭
3. Metrics API가 정상이고 대상 컨테이너에 CPU·Memory `requests`가 설정되었는지 확인한 뒤 옵션 설정 후 **OK** 클릭

| 항목 | 설명 |
|------|------|
| Target CPU Usage (%) | 컨테이너의 평균 CPU 사용량을 `resources.requests.cpu` 대비 백분율로 계산 |
| Target Memory Usage (MiB) | Pod당 평균 메모리 사용량의 절대값. 메모리 요청량 대비 백분율과 구분 |
| Minimum Replicas | 최소 Pod 수 |
| Maximum Replicas | 최대 Pod 수. Minimum Replicas 이상으로 설정 |

## 11. Kubectl CLI 사용

`kubectl`은 기본 사용자 접속 경로가 아니다. 각 Cluster의 Bastion 계정, 방화벽, CyberArk 권한과 사용자별 kubeconfig가 모두 승인된 경우에만 사용한다.

- T-DKS팀에 Bastion 계정 생성 요청 필요 (AD 계정명과 동일)
- Bastion 계정 생성 통보 후 **CyberArk 권한** 별도 요청 필요
- kubeconfig는 개인키가 포함될 수 있는 민감정보로 취급하며 사용자별 파일 권한을 `0600`으로 제한
- 접근 확인은 승인된 Project에서 `kubectl auth can-i get pods -n <project>`처럼 읽기 전용으로 수행

자세한 절차는 [[50. 운영/04. Kubesphere Operation/06. Enable users using kubectl CLI|Enable users using kubectl CLI]] 참고.
