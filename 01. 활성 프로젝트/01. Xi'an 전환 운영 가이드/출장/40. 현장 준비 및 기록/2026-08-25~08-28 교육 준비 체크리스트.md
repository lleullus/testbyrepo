# 4. 8/26 — KubeSphere Operation

## 4.1 준비 목적

하나의 사용자 신청이 실제 KubeSphere / Kubernetes의 어떤 객체와 권한으로 반영되는지 연결한다.

```text
신청
→ 대상 Member Cluster
→ Workspace
→ Project / Namespace
→ Workspace Member
→ Project Member / Role
→ Quota
→ 필요 시 kubectl
→ 필요 시 CA ConfigMap
```

## 4.2 반드시 정할 기준 대상

가능하면 기존 정상 대상 하나를 정한다.

```text
대상 Cluster: ______________________________
Workspace: __________________________________
Project / Namespace: _________________________
확인할 사용자 또는 Role: _____________________
```

- [ ] 대상 Member Cluster 결정
- [ ] Workspace 결정
- [ ] Project / Namespace 결정
- [ ] Member / Role 확인 대상 결정

대상이 없거나 접근할 수 없다고 해서 교육용 객체를 새로 만들지 않는다. 기준 Manual로 전환한다.

## 4.3 한 번만 확인할 화면

- [ ] Workspace 위치
- [ ] Project 위치
- [ ] Workspace Members 위치
- [ ] Project Members / Role 위치
- [ ] Workspace / Project Quota 위치
- [ ] 실제 Namespace / ResourceQuota 확인 위치
- [ ] 필요 시 `current-context` 확인 방법
- [ ] CA ConfigMap / `ks-apiserver` Mount 확인 위치 또는 Manual 위치

## 4.4 반드시 구분할 것

```text
Workspace ≠ Project / Namespace
Workspace Member ≠ Project 권한
신청 Admin ≠ project-admin 자동 부여
권한 부족 ≠ Quota 부족
kubeconfig 존재 ≠ 올바른 Cluster 사용
ConfigMap 존재 ≠ ks-apiserver Mount 완료
```

## 4.5 내가 미리 학습해둘 것

8/26 대비 학습은 KubeSphere 메뉴를 전부 외우는 것이 아니라, **화면에 나오는 객체들이 어떤 관계인지 설명할 수 있는 상태**를 만드는 데 집중한다.

### 1. Workspace / Project / Namespace

- [ ] Workspace가 상위 관리 범위라는 것을 설명할 수 있음
- [ ] Project가 Kubernetes Namespace와 연결된다는 것을 설명할 수 있음
- [ ] `Workspace Member ≠ Project 권한`을 설명할 수 있음

### 2. Member / Role / RBAC

- [ ] Workspace Member와 Project Member 차이를 설명할 수 있음
- [ ] `project-viewer`, `project-operator`, `project-admin` 차이를 설명할 수 있음
- [ ] 신청 `Admin → project-operator`, `User → project-viewer` 기본 매핑을 이해함
- [ ] Platform → Workspace → Project 권한 계층을 설명할 수 있음

### 3. Quota

- [ ] CPU / Memory Request와 Limit의 차이를 이해함
- [ ] Workspace Quota와 Project Quota가 무엇을 제한하는지 이해함
- [ ] Storage 총량과 StorageClass별 Quota를 구분함
- [ ] `권한 부족 ≠ Quota 부족`을 설명할 수 있음

### 4. kubectl 접근 구조

명령어 암기보다 다음 흐름을 이해한다.

```text
Bastion
→ kubeconfig
→ context
→ Kubernetes API
→ Project RBAC
```

- [ ] KubeSphere Web 로그인과 kubectl 접근이 별도라는 것을 이해함
- [ ] `current-context`가 왜 중요한지 설명할 수 있음

### 5. CA ConfigMap / x509

다음 흐름의 의미를 이해한다.

```text
Harbor 인증서
→ CA 신뢰 필요
→ ConfigMap
→ ks-apiserver Mount
→ Pod 재생성
→ 기능 재확인
```

- [ ] `x509: certificate signed by unknown authority`가 CA 신뢰 문제라는 것을 이해함
- [ ] `ConfigMap 존재 ≠ 실제 적용 완료`를 설명할 수 있음

### 학습 확인 질문

아래 질문에 흐름으로 답할 수 있으면 핵심 학습은 완료로 본다.

> 사용자가 DEV 환경을 신청하고 Admin 권한과 CPU / Memory / Storage를 요청했다면, 그 요청이 KubeSphere와 Kubernetes에 어떤 순서로 반영되는가?

```text
DEV Member
→ Workspace
→ Project / Namespace
→ Workspace Member
→ Project Member
→ project-operator
→ CPU / Memory / Storage Quota
→ 필요 시 kubectl
→ Harbor x509가 있으면 CA 설정
```

## 4.6 이번 교육을 위해 하지 않을 것

- 신규 Workspace / Project 생성
- 교육용 사용자 초대
- Role 변경

- 신규 kubeconfig 발급
- 새 CA ConfigMap 생성

## 5.6 오전에 내가 미리 학습해둘 것 — Operations Manual 2.1~2.5

27일 오전은 다섯 Manual을 같은 깊이로 외우지 않는다. **Worker 추가와 배치 원리를 우선 이해하고, Native API와 인증서 갱신은 전체 구조와 중단 기준을 잡는 수준으로 준비한다.**

### 1. Worker 추가 흐름 — 가장 중요

다음 전체 흐름을 설명할 수 있어야 한다.

```text
신규 VM
→ Node Pre-setting
→ Kubespray Inventory
→ scale.yml
→ Node Ready
→ System Pod
→ Workload 배치
→ PVC Mount / Read / Write
→ Inventory 기준본 정리
```

- [ ] Node Pre-setting이 왜 필요한지 설명할 수 있음
- [ ] Inventory가 Node의 IP·Group·Role·label·taint·scale 대상을 결정한다는 것을 이해함
- [ ] `scale.yml 성공 ≠ Worker 추가 완료`를 설명할 수 있음
- [ ] Node Ready 이후 CNI·CSI·kube-proxy·Workload·Storage까지 확인해야 한다는 것을 이해함

### 2. label / taint / nodeSelector / toleration

다음 네 요소의 역할과 관계를 설명할 수 있어야 한다.

```text
label        = Node의 속성·분류
+ nodeSelector / affinity = Pod가 원하는 Node 선택

taint        = 허용되지 않은 Pod의 배치 제한
+ toleration = Pod가 해당 taint를 허용
```

- [ ] label만으로 다른 Pod의 접근이 차단되지 않는다는 것을 이해함

ProjectAdmin

= Developer 기능
