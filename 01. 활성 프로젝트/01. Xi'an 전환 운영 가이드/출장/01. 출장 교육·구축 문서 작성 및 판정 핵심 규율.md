# Xi'an 출장 교육·구축 문서 작성 및 판정 핵심 규율

> [!important] 이 문서의 역할
> 이 문서는 특정 제품의 명령, Manifest, 현재 IP·VIP·CIDR·Version, 일정별 Gate를 제공하는 기술 Source of Truth가 아니다. **출장 문서가 특정 독자에게 어떤 변화를 만들어야 하는지 먼저 확정하고, 그 변화에 필요한 사실·설명·절차·증거를 어떤 순서와 경계로 배치할지를 정하는 작성·리뷰 Governance**다.
>
> 기술 사실과 실행값은 현재 승인 설계, 해당 Manual·Runbook, 현재 대상의 관찰 결과를 따른다.

> [!success] 최상위 한 문장
> **좋은 문서는 자료의 목차를 정리한 문서가 아니라, 독자의 실제 시작 상태에서 출발해 하나의 중심 질문을 해결하는 인과 경로를 만들고, 필요한 기술 이름·현장값·절차·증거를 그 경로의 정확한 자리에 놓아 의도한 이해·조회·판단·실행을 가능하게 하는 문서다.**

> [!warning] 모범문서를 옮기는 방식
> 모범문서의 제목, 번호, `하지만`·`그래서`의 표면 빈도, 표·Callout 형식을 복제하지 않는다. **복제할 것은 `문제 → 필요한 역할 → 기술 이름 → 현장 구현 → 실제 사용 → 완료 증거 → 첫 실패 경계 → 전체 복원`을 만드는 생성 원리**다.

# 1. 모범문서의 구조를 해체하면 무엇이 보이는가

모범문서인 [[출장/20. 교육/2026-08-27/오후/02. Harbor 강사용 전체 대본|Harbor 강사용 전체 대본]]은 Harbor 지식을 많이 나열해서 모범이 된 것이 아니다. **독자가 모르는 상태에서 시작해 기술이 왜 필요한지를 필연적으로 느끼게 하고, 실제 업무와 완료·장애 판단까지 같은 지도 위에 연결했기 때문에 모범**이다.

## 1.1 표면 목차 아래에는 세 번의 같은 이야기가 있다

| 층 | 모범문서에서 한 일 | 전용할 원리 |
|---|---|---|
| 시작 압축 | 설명 공식과 `오늘 전체 한 줄`로 전체 길을 먼저 보여줌 | 독자가 세부 설명을 놓쳐도 돌아올 수 있는 짧은 방향 지도를 먼저 제공 |
| 인과 확장 | Image의 필요에서 Registry, Harbor, Project, Member·Role, Push·Pull, Kubernetes 사용으로 필요가 연쇄됨 | 항목 순서가 아니라 **앞 문제 때문에 다음 역할이 필요해지는 순서**로 본문 구성 |
| 현장 연결 | 일반 역할을 이해한 직후 Xi'an의 실제 제품·주소·운영 요청과 연결 | 개념과 현장값을 분리하지 말고, 의미를 이해한 자리에 실제 구현을 붙임 |
| 경계 설정 | 설치 기반, 반복 운영, 다음 교육 범위, 조회와 변경을 구분 | 언제 하는 일인지와 이번 문서에서 어디까지 하는지를 명확히 함 |
| 증거 상승 | Container Running에서 Web·API·Login·Push·Pull·재시작 후 유지까지 증거를 확장 | 중간 성공을 최종 사용 성공으로 확대하지 않음 |
| 장애 역전 | 정상 사용 경로를 반대로 따라 첫 단절 지점을 찾음 | Troubleshooting을 별도 원인 백과사전이 아니라 정상 지도의 역방향 판독으로 설계 |
| 마무리 재압축 | 처음의 전체 흐름을 더 정확한 말로 다시 연결 | 마무리에서 새 사실을 추가하지 않고 전체 지도를 복원 |
| Teach-back | 용어 정의보다 문제·역할·구분·완료 판단을 질문 | 기억한 항목 수가 아니라 스스로 전체 흐름을 재구성하고 판단할 수 있는지 확인 |

이 반복은 중복이 아니다.

```text
시작
→ 방향을 잃지 않게 압축해서 보여줌

본문
→ 각 연결의 이유·한계·현장 의미를 확장함

마무리
→ 세부사항을 다시 하나의 복원 가능한 지도로 압축함
```

## 1.2 각 절은 하나의 질문을 갚고 다음 질문을 남긴다

모범문서의 절은 독립 Topic이 아니다.

```text
Application 실행 원본이 왜 필요한가?
→ Image

Worker가 여러 대면 Image를 어떻게 함께 쓰는가?
→ Registry

Xi'an에서 Registry 역할은 누가 하는가?
→ Harbor

여러 Team의 Image와 권한을 어떻게 나누는가?
→ Project

사람이 그 공간에서 무엇을 할 수 있게 하는가?
→ Member·Role

실제 사용 가능 여부는 무엇으로 확인하는가?
→ Push·Pull과 최종 사용 경로
```

각 절은 다음 계약을 가진다.

```text
현재 남은 질문 하나를 받는다
→ 필요한 답을 준다
→ 기술 이름과 사실을 그 답에 종속시킨다
→ 흔한 오판이나 적용 한계를 막는다
→ 아직 해결되지 않은 다음 질문을 남긴다
```

앞 절과 다음 절 사이에 이런 필요 관계가 없으면, 문서는 논리적인 설명이 아니라 관련 항목 목록이 되기 쉽다.

## 1.3 기술 이름은 답으로 등장한다

모범문서는 먼저 `Harbor`, `Project`, `Role`을 정의하지 않는다.

```text
문제
→ 필요한 기능이나 역할을 쉬운 말로 설명
→ 그 역할의 기술 이름을 붙임
→ 실제 Xi'an 구현과 연결
```

기술 이름이 먼저 나오면 독자는 정의를 외운다. 역할이 먼저 나오면 독자는 **그 기술이 왜 존재하고 언제 필요한지**를 이해한다.

## 1.4 정상 설명·완료 검증·장애 판단이 같은 지도다

모범문서에서 교육, 검증, Troubleshooting은 세 개의 별도 체계가 아니다.

```text
정상 경로를 이해한다
→ 교육

같은 경로의 끝까지 실제 성공을 확인한다
→ 완료 검증

같은 경로에서 마지막 성공과 첫 실패를 찾는다
→ Troubleshooting
```

이 원리는 강사용 대본뿐 아니라 Runbook, 검증 문서, 장애 가이드에도 전용된다. 단, 각 문서의 본문 형식과 정보 밀도는 역할에 맞게 달라져야 한다.

# 2. 복제할 깊은 구조와 복제하지 않을 표면을 구분한다

## 2.1 모든 문서에 전용할 깊은 구조

역할에 필요한 부분만 선택해 다음 구조를 사용한다.

```text
독자의 실제 시작 상태
→ 지금 해결해야 하는 문제·판단
→ 필요한 역할 또는 상태 변화
→ 그 역할의 기술 이름·대상
→ Xi'an의 현재 구현·승인값·관찰값
→ 실제 업무 Trigger와 행위자
→ 설명·조회·실습·변경의 경계
→ 완료를 증명하는 끝단 증거
→ 실패 시 첫 단절 지점
→ 전체 복원·판정·Handoff
```

모든 문서가 이 항목을 모두 가져야 한다는 뜻이 아니다. **현재 역할의 사용자 결과를 만드는 데 필요한 연결만 남긴다.**

## 2.2 복제하지 않을 것

다음은 모범문서의 상황별 표현이지 공통 Template가 아니다.

- `0. 강사가 머릿속에 들고 갈 설명 공식` 같은 제목
- 절마다 동일한 수의 인용문과 `하지만`·`그래서`
- Harbor의 제품명·FQDN·Role·설치 순서
- 시작 한 줄, 완료 기준, 장애 절을 모든 문서에 같은 위치로 두는 방식
- 강사용 발화체를 Runbook·Reference·검증 문서에 그대로 쓰는 방식

> **표면이 비슷한 문서가 아니라, 독자의 진행 과정이 같은 원리로 설계된 문서를 만든다.**

# 3. 본문 전에 작성 설계 기록을 먼저 만든다

이 기록은 사고를 위한 내부 작업물이다. 최종 문서의 고정 목차로 노출할 필요는 없다.

| 결정 항목 | 먼저 확정할 질문 |
|---|---|
| 문서 역할 | 이 문서는 교육 설계, 교육생 교재, 강사용 대본, 강사용 메모, Runbook, Troubleshooting, 검증·인수, Reference, Lab 중 무엇인가? |
| 독자와 사용 순간 | 누가 어떤 상황에서 이 문서를 열어 무엇을 하려는가? |
| 독자의 시작 상태 | 무엇을 알고 있고, 무엇을 잊었거나 잘못 이해할 가능성이 큰가? |
| 목표 변화 | 문서를 사용한 뒤 어떤 이해·조회·판단·행동이 가능해져야 하는가? |
| 중심 질문 | 문서 전체가 끝까지 답해야 하는 질문 하나는 무엇인가? |
| 인과 뼈대 | 앞 문제 때문에 다음 요소가 왜 필요해지는가를 한 줄로 어떻게 연결할 것인가? |
| 행위자와 경로 | User, Developer·CI, Browser, Client, Worker, 운영자 등 서로 다른 주체의 경로를 나눠야 하는가? |
| Source와 불확실성 | 어떤 승인 문서·Manual·관찰 결과가 사실을 지지하며 무엇은 아직 확정되지 않았는가? |
| 범위와 경계 | 이번 문서에서 설명·조회·실습·실제 변경 중 어디까지 하는가? 다른 문서로 보내야 할 것은 무엇인가? |
| 완료와 Handoff | 무엇을 보면 목적 달성인가? 다음 문서나 담당자가 무엇을 이어받는가? |

## 3.1 가장 먼저 고정할 세 문장

최소한 다음 세 문장은 본문보다 먼저 완성한다.

```text
이 문서는 [누가] [언제] 열어 [무엇을 하기 위한] 문서다.

이 문서 때문에 독자는 [하나의 이해·판단·행동 변화]를 얻어야 한다.

그 결과를 만들기 위해 본문은 [하나의 인과·상태·실패·증거·탐색 원리]로 조직한다.
```

세 문장이 서로 다른 목적을 가리키면 문서를 나누거나 하나를 주목적으로 종속시킨다.

## 3.2 독자의 시작 상태는 선수지식 목록보다 구체적이어야 한다

나쁜 작성 전제:

```text
Kubernetes 기본 지식 보유
```

더 좋은 작성 전제:

```text
Pod라는 이름은 들어봤지만 Image가 Worker에 전달되는 경로는 연결하지 못함
앞 교육을 들었으나 실제 업무 Trigger와 완료 증거는 아직 구분하지 못함
운영 절차는 알지만 승인값과 현재 관찰값을 혼용할 가능성이 있음
```

문서는 독자가 실제로 가진 빈칸과 오판 가능성을 메워야 한다.

# 4. Source를 해체한 뒤 독자 순서로 다시 조립한다

좋은 문서는 원본 목차를 예쁘게 요약하지 않는다. 먼저 Source를 작은 의미 단위로 해체하고, 각 단위가 최종 문서에서 어떤 일을 해야 하는지 결정한다.

## 4.1 Source를 일곱 종류로 나눈다

```text
확정 사실
→ 제품·대상·관계·현재 승인 내용

인과 관계
→ 왜 다음 요소가 필요한지 설명하는 연결

절차·상태 변화
→ 실제로 무엇을 읽고 바꾸는지

판단 기준
→ 어떤 조건에서 다음 행동이 달라지는지

증거
→ 무엇을 관찰하면 어떤 성공·실패를 말할 수 있는지

경계·금지
→ 이번 문서에서 하지 않는 일과 실행 금지 조건

미확정 사항
→ Source가 확정하지 않은 값·매핑·정책
```

같은 문장이 여러 종류를 포함하면 분리한다. 특히 사실, 추론, 권고를 한 문장에 섞지 않는다.

## 4.2 각 Source 단위에 문서 안의 역할을 부여한다

| 배치 판정 | 의미 |
|---|---|
| `KEEP` | 현재 문서의 사용자 결과를 만드는 데 반드시 필요 |
| `LINK` | 필요하지만 상세 내용의 Source of Truth는 다른 Manual·Runbook이므로 의미와 연결만 남김 |
| `MOVE` | 유용하지만 다른 문서 역할에 속함 |
| `DELETE` | 없어도 이해·판단·실행·안전·증거가 달라지지 않음 |
| `HOLD` | 필요한 내용이지만 근거가 없어 확정 문장으로 쓸 수 없음 |

정확한 정보라는 이유만으로 `KEEP`하지 않는다. **현재 문서에서 해야 할 일이 있을 때만 남긴다.**

## 4.3 원본 순서와 최종 순서를 분리한다

```text
원본 Manual 순서
≠ 독자가 이해하는 순서
≠ 운영자가 실행하는 순서
≠ 장애를 좁히는 순서
≠ 인수 증거를 판정하는 순서
```

원본의 모든 핵심 내용을 보존하되, 최종 문서의 순서는 문서 역할이 결정한다.

- 강사용 대본은 필요가 생기는 학습 순서로 재배열한다.
- Runbook은 안전한 상태 변화 순서로 재배열한다.
- Troubleshooting은 관찰 가능한 실패 경계 순서로 재배열한다.
- 검증·인수 문서는 주장과 증거의 판정 순서로 재배열한다.
- Reference는 사용자가 찾는 항목과 검색 경로로 재배열한다.

## 4.4 재배열 뒤에는 Coverage를 확인한다

내부 검토용으로 다음 표를 만든다.

| Source 단위 | 근거 | 최종 위치 | 처리 | 빠졌을 때 영향 |
|---|---|---|---|---|

다음 두 종류의 누락을 구분한다.

```text
의도적 제외
→ 현재 Purpose에 불필요해 LINK·MOVE·DELETE함

비의도적 누락
→ 재배열 과정에서 필요한 사실·경계·증거가 사라짐
```

모범문서처럼 원본 목차를 바꾸려면, 오히려 Coverage 추적은 더 엄격해야 한다.

# 5. 한 줄 인과 뼈대와 절 단위 계약을 만든다

## 5.1 중심 질문 하나를 정한다

중심 질문은 제목을 바꿔 말한 문장이 아니다. 독자가 실제로 해결해야 할 문제여야 한다.

예:

```text
Harbor란 무엇인가?
보다
여러 Worker가 동일한 Private Image를 안전하게 저장하고 사용하려면 무엇이 필요한가?
```

```text
Storage 구성 방법은 무엇인가?
보다
Application이 요청한 저장공간이 실제 Pod의 Mount·Write·Read까지 이어졌음을 어떻게 안전하게 만들고 증명하는가?
```

각 절은 중심 질문의 일부 답이어야 한다.

## 5.2 전체 인과 뼈대를 한 번에 말할 수 있어야 한다

```text
처음 문제
→ 필요한 역할 1
→ 아직 남은 문제
→ 필요한 역할 2
→ 실제 업무 적용
→ 완료 증거
→ 실패 시 첫 확인
→ 다음 Handoff
```

한 줄로 연결할 수 없으면 다음 중 하나다.

- 서로 다른 문서 역할이 섞였다.
- 원본 Topic을 아직 독자 질문으로 바꾸지 못했다.
- 중심 질문과 관계없는 정보가 본문을 지배한다.
- 실제로는 병렬 경로인데 억지로 선형화하고 있다.

## 5.3 각 절은 다섯 항목만 설계한다

```text
현재 미해결 질문:
이번 절이 주는 답:
반드시 필요한 사실·예시·증거:
막아야 할 대표 오판:
다음 절에 남길 미해결 질문:
```

이 다섯 항목은 설계 카드다. 최종 문서에 같은 제목으로 반복하지 않는다.

## 5.4 절의 끝은 다음 절의 필요를 만든다

좋은 전환은 단순한 예고가 아니다.

```text
이제 다음으로 Project를 보겠습니다.
```

보다:

```text
Harbor가 동작해도 여러 팀의 Image와 권한은 아직 구분되지 않습니다.
그래서 팀별 경계인 Project가 필요합니다.
```

가 낫다.

앞 절의 한계가 다음 절의 존재 이유가 되어야 한다.

## 5.5 `그래서`, `하지만`, `따라서`, `결국`은 의미 기능으로 쓴다

```text
그래서
→ 앞 문제 때문에 필요한 역할·조치가 생김

하지만
→ 현재 답의 한계 또는 아직 남은 문제를 드러냄

따라서
→ 근거와 조건을 바탕으로 판단·행동을 선택함

결국
→ 여러 연결을 하나의 결론이나 전체 지도로 다시 압축함
```

같은 단어를 반복하는 것이 목표가 아니다. 접속사를 지워도 인과 관계가 남아 있어야 한다.

# 6. 본문 작성 문법

## 6.1 문제와 역할을 먼저, 이름은 나중에 둔다

```text
기술 이름
→ 정의
→ 기능 목록
```

보다:

```text
독자가 느끼는 문제
→ 필요한 역할을 쉬운 말로 설명
→ 기술 이름
→ 실제 시스템에서의 구현
```

을 우선한다.

단, Reference Manual처럼 사용자가 이미 이름을 알고 빠르게 찾는 것이 Purpose라면 항목 이름을 먼저 보여도 된다.

## 6.2 한 문단은 한 번만 움직인다

한 문단의 주된 기능은 다음 중 하나로 제한한다.

- 문제를 구체화한다.
- 필요한 역할을 설명한다.
- 기술 이름을 붙인다.
- 현재 환경과 연결한다.
- 오판을 구분한다.
- 행동 경계를 정한다.
- 증거의 의미를 해석한다.
- 다음 문제로 전환한다.

한 문단에 정의, 절차, 예외, 장애 조치, 인계를 모두 넣지 않는다.

## 6.3 일반 개념과 Xi'an 구현은 붙이되 섞지 않는다

권장 순서:

```text
일반적으로 필요한 역할
→ 그 역할의 기술 이름
→ Xi'an에서 그 역할을 담당하는 실제 대상·값
→ 값의 Source와 현재성
```

예시값, 과거값, 다른 Cluster 값은 현재 실행값처럼 쓰지 않는다.

## 6.4 기술 사실의 상태를 문장 안에서 드러낸다

| 상태 | 문장 의미 |
|---|---|
| 일반 개념 | 제품·환경과 무관한 역할이나 관계 |
| 승인값 | 설계·결정·승인으로 정해진 목표 |
| 관찰값 | 현재 대상에서 실제로 읽은 상태 |
| 실행값 | 승인값과 관찰값을 대조해 이번 변경에 쓰기로 확정한 값 |
| 결과값 | 실행 후 시스템이 실제로 만든 상태 |
| 예시값 | 형식·개념 설명을 위한 비실행 값 |
| 미확정 | Source가 최종 매핑·정책·값을 지원하지 않음 |

모호한 `현재값`, `실제값`, `문서값` 표현만으로 상태를 덮지 않는다.

## 6.5 오판은 발생할 자리에서 바로 막는다

다음과 같은 구분은 별도 부록보다 오판이 생기는 문맥에 둔다.

```text
Login 성공
≠ 특정 Project Authorization 성공
```

```text
Harbor Project
≠ KubeSphere Project
```

```text
Container Running
≠ 사용자 Push·Pull 가능
```

구분식이 서사를 대신하지 않게 한다. 왜 다른지와 다음 확인까지 설명할 때만 사용한다.

## 6.6 서로 다른 행위자의 정상 경로를 억지로 합치지 않는다

같은 시스템도 행위자와 행동이 다르면 경로가 다르다.

```text
Browser 사용자의 Web 접근
Docker·CLI 사용자의 Login·Push·Pull
Kubernetes Worker의 Private Image Pull
운영자의 Project·Member·Role 변경
```

공통 기반은 공유하되, 실제 성공 조건과 첫 실패 경계는 경로별로 나눈다.

## 6.7 업무의 시간축을 연결한다

기술 설명에는 가능한 한 다음을 구분한다.

```text
플랫폼 기반을 한 번 구축하는 일
반복되는 운영 요청마다 수행하는 일
장애가 있을 때만 수행하는 일
다음 교육·구축 단계가 이어받는 일
```

이 구분이 없으면 독자는 모든 절차를 매 요청마다 반복하거나, 반복 업무를 일회성 구축으로 오해할 수 있다.

## 6.8 설명·조회·실습·실제 변경을 구분한다

| 구분 | 의미 |
|---|---|
| 설명 | 개념·관계·절차를 이해 |
| 조회 | 현재 운영 상태를 읽기 전용으로 확인 |
| 실습 | 승인된 Test 대상에서 제한적으로 실행 |
| 실제 변경 | 승인된 운영 요청과 Runbook에 따라 상태 변경 |

교육 목적 때문에 운영 변경을 만들지 않는다. 조회 화면을 보여준다는 이유로 Create·Save·Delete를 허용하지 않는다.

## 6.9 상세 정보는 Purpose에 맞는 자리로 보낸다

강사용 대본에서 상세 명령이 전체 이야기의 흐름을 끊는다면 Manual·Runbook으로 `LINK`한다.

반대로 Runbook에서 정확한 명령·옵션·경로가 안전한 실행에 필요하다면 본문에 `KEEP`한다.

> **정보의 양이 아니라 정보의 자리가 품질을 결정한다.**

## 6.10 반복은 방향 복원을 위해 사용한다

같은 핵심 흐름을 시작, 본문 전환, 마무리에서 다시 말할 수 있다. 다만 매번 역할이 달라야 한다.

```text
시작 반복
→ 전체 방향 제시

중간 반복
→ 지금까지의 위치와 다음 필요 연결

마지막 반복
→ 전체를 자기 말로 복원
```

같은 문장을 그대로 복사하거나 새 내용을 마무리에 추가하지 않는다.

# 7. 강사용 전체 대본에 적용할 특별 규율

이 절은 모범문서의 핵심 작성 인사이트를 강사용 전체 대본에 직접 전용한다. 다른 문서 역할에 기계적으로 적용하지 않는다.

## 7.1 최종 목적은 수강생의 판단·행동 변화다

강사가 많이 말하는 것, 기술 용어를 모두 다루는 것, 표를 완성하는 것이 목적이 아니다.

수업 뒤 수강생은 최소한 다음을 할 수 있어야 한다.

```text
처음 문제가 무엇인지 설명한다
→ 필요한 역할과 기술이 왜 이어지는지 자기 말로 복원한다
→ 실제 업무에서 언제 사용하는지 구분한다
→ 무엇을 보면 완료인지 판단한다
→ 실패 시 어디부터 확인할지 선택한다
```

## 7.2 독자의 기억을 가정하지 말고 필요한 만큼 복원한다

연속 교육이라도 앞 내용을 모두 기억한다고 가정하지 않는다. 그렇다고 매번 전체 기초를 처음부터 재강의하지도 않는다.

```text
현재 중심 이야기에 필요한 앞 개념
+ 앞에서 이미 만든 핵심 지도
+ 이번 블록에서 새로 달라지는 부분
```

만 복원한다.

## 7.3 시작에는 두 개의 압축 지도를 준비한다

```text
강사용 설명 알고리즘
→ 어떤 순서와 태도로 설명할지

수강생용 전체 한 줄
→ 오늘 이야기가 어디서 시작해 어디까지 가는지
```

최종 문서의 제목은 자유롭다. 중요한 것은 강사와 수강생이 서로 다른 방향 지도를 갖는 것이다.

## 7.4 본문의 대부분은 실제 발화여야 한다

강사가 그대로 말하거나 조금 조정해 말할 수 있는 문장이 본체여야 한다.

다음이 본문 대부분이면 전체 대본이 아니다.

```text
Framework
표
Checklist
A ≠ B 목록
Gate
인계표
명령 모음
```

### 발화 연속성 Test

표·Callout·Checklist를 가리고 본문만 읽는다.

- 첫 문제에서 마지막 결론까지 말로 이어지는가?
- 각 절의 첫 문장이 앞 절에서 생긴 필요를 받는가?
- 전문용어를 지워도 역할을 쉬운 말로 설명할 수 있는가?
- 한 문장이 지나치게 길거나 여러 판단을 한꺼번에 요구하지 않는가?
- 강사가 다음 문장을 찾기 위해 목차를 다시 읽어야 하지 않는가?

하나라도 중심 흐름을 끊으면 발화 문장을 먼저 고친다.

## 7.5 원본 Manual과 실제 업무의 관계를 먼저 해석한다

원본 절을 순서대로 읽는 것만으로는 교육이 되지 않는다.

먼저 각 절이 실제 업무에서 무엇인지 구분한다.

```text
플랫폼 기반 구축
반복 운영 요청
사용자 자기서비스
장애 시 절차
검증·인수
다음 교육으로 넘길 범위
```

이 해석이 있어야 수강생이 `무엇인지`뿐 아니라 `언제 하는지`를 알 수 있다.

## 7.6 실제값은 개념을 이해한 직후 연결한다

가능하면 다음 순서를 유지한다.

```text
필요
→ 역할
→ 기술 이름
→ Xi'an 실제 대상·값
→ 현재 승인 Source 또는 재확인 필요성
```

실제값 수집·대조 자체가 교육 목적이면 별도의 Inventory 흐름으로 설계할 수 있다.

## 7.7 완료는 사용 경로의 끝에서 설명한다

중간 상태를 완료로 가르치지 않는다.

```text
설치 명령 성공
→ 설치 단계 증거

Process·Container Running
→ 실행 단계 증거

Web·API 응답
→ 접근·서비스 단계 증거

실제 사용자·Workload 행동 성공
→ 사용 기능 증거

재시작·후속 변경 뒤 유지
→ 지속성과 현재성 증거
```

문서 목적이 요구하는 가장 끝단의 증거까지 올라간다.

## 7.8 장애 설명은 정상 지도를 역으로 사용한다

장애 절을 가능한 원인 목록으로 만들지 않는다.

```text
사용자가 하려던 행동
→ 해당 정상 경로 선택
→ 실제 오류·Event
→ 마지막 성공
→ 첫 실패
→ 다음 판단을 바꾸는 최소 조회
→ 관련 범위만 조치
→ 같은 사용자·대상·경로로 복구 확인
```

과거 장애 사례는 후보를 줄이는 참고일 뿐 현재 원인이 아니다.

## 7.9 마무리는 처음의 이야기를 다시 복원한다

마무리에서 새로운 기술 사실이나 예외를 추가하지 않는다.

```text
처음 문제
→ 필요한 역할
→ 기술 이름
→ Xi'an 실제 구현
→ 실제 업무
→ 완료 증거
→ 장애 시 첫 확인
→ 다음 Handoff
```

를 더 짧고 정확하게 다시 연결한다.

## 7.10 Teach-back은 용어 암기가 아니라 복원과 판단을 확인한다

우선 다음을 묻는다.

1. 처음 해결하려던 문제와 전체 흐름을 자기 말로 설명할 수 있는가?
2. 가장 중요한 두 상태나 두 객체가 왜 다른가?
3. 실제 업무에서 누가 언제 이 절차를 사용하는가?
4. 무엇을 보면 완료라고 말할 수 있는가?
5. 대표 실패가 발생하면 정상 경로의 어디부터 확인할 것인가?

질문 순서는 본문의 인과 순서를 따라야 한다.

# 8. 다른 문서 역할에 전용하는 방법

모범문서의 깊은 구조는 유지하되, 독자가 진행하는 단위와 완료 방식은 역할별로 바꾼다.

| 문서 역할 | 사용자 결과 | 지배적인 진행 단위 | 문서가 닫혀야 하는 지점 |
|---|---|---|---|
| 교육 설계·안내 | 교육 블록의 목표·순서·시간·자료·실습 경계 확정 | 학습 변화 → 블록 순서 → 자료·시간 → 실행 경계 | 강사가 실제 교육 운영을 결정할 수 있음 |
| 교육생 교재 | 개념·관계·절차를 이해하고 다시 찾음 | 학습 질문 → 설명·예시 → 핵심 요약 → 참조 | 강사 없이도 핵심 흐름과 참조 위치를 복원 |
| 강사용 전체 대본 | 실제 발화로 수강생의 판단·행동 변화 유도 | 문제 → 필요 → 역할 → 이름 → 현장 → 사용·증거 | 강사가 처음부터 끝까지 말로 수업을 진행하고 Teach-back 가능 |
| 강사용 메모 | 현장에서 전체 대본을 빠르게 복원 | 핵심 Cue → 주의점 → 전환 문장 → 시간·범위 | 짧게 보면서 다음 이야기와 경계를 즉시 찾음 |
| Runbook / Change Procedure | 안전하고 재현 가능한 상태 변경 | 대상 Identity → 선행조건 → 읽기 → 승인값 대조 → 변경 → 검증 → Rollback | 의도한 기능 성공 또는 명확한 중단·복구 |
| Troubleshooting Guide | 첫 실패 경계를 좁히고 복구 확인 | 사용자 행동 → 정상 경로 → 오류 → 마지막 성공 → 첫 실패 → 최소 확인 → 조치 | 같은 경로에서 복구 또는 명확한 Escalation 근거 확보 |
| 검증·인수 문서 | 증거에 따라 완료 여부 판정 | 의도한 결과 → 주장별 증거 → 한계·회귀 → 잔여 영향 → 판정 | 판정과 남은 책임·기한·Handoff가 모호하지 않음 |
| Reference Manual | 정확한 현재 정보를 빠르게 조회 | 검색 항목 → 현재 사실·값·제약 → 관련 절차 링크 | 필요한 답과 Source에 빠르게 도달 |
| Lab Guide | 통제된 차이를 직접 관찰 | 정상 Baseline → 한 변화 → 비교 → 해석 → 원상복구 | 차이를 설명하고 환경을 원래 상태로 복구 |

## 8.1 Runbook에는 서사보다 상태 전환이 지배한다

Runbook의 상세 명령·옵션·파일 경로는 안전한 실행에 필요하면 본문 핵심이다.

```text
대상 Identity
→ 선행조건
→ 현재 상태 읽기
→ 승인값과 대조
→ 영향·Backup·Rollback
→ 변경
→ 즉시 상태 확인
→ 실제 기능 확인
→ 실패 시 중단·복구
```

강사용 대본처럼 긴 문제 서사를 넣지 않는다. 다만 **왜 이 확인이 다음 행동을 바꾸는지**는 짧게 설명한다.

## 8.2 Troubleshooting은 원인 목록보다 분기 기준이 지배한다

```text
큰 증상
→ 사용자가 하려던 구체 행동으로 분해
→ 실제 Error·Event 확인
→ 마지막 성공과 첫 실패 결정
→ 다음 판단을 바꾸는 최소 조회
```

상태 이름을 원인으로 쓰지 않는다. 정상 대상은 비교 자료이지 실패 대상의 성공 증거가 아니다.

## 8.3 검증·인수는 실행 목록보다 주장과 증거가 지배한다

각 항목을 다음 구조로 쓴다.

```text
판정할 주장
→ 사용한 증거
→ 그 증거가 증명하는 범위
→ 증명하지 못하는 범위
→ 잔여 영향
→ 최종 판정
```

최종 상태 이름은 해당 검증 기준 문서가 정한다. 이 Governance 문서가 별도의 일정·Gate Source of Truth가 되지 않는다.

## 8.4 Reference는 이야기보다 탐색성이 지배한다

사용자가 이미 찾을 이름을 알고 있다면 항목명을 먼저 노출한다.

- 현재값과 예시값을 분리한다.
- 값의 Source와 갱신 시점을 찾을 수 있게 한다.
- 상세 실행은 관련 Runbook으로 연결한다.
- 교육 서사를 억지로 삽입하지 않는다.

# 9. Source·값·증거의 공통 규율

## 9.1 Source의 역할을 분리한다

```text
현재 작업 요청
→ 산출물 역할·범위·금지사항·출력 형식 결정

현재 승인 설계·정책·Manual
→ 기술 사실·목표값·허용 절차 결정

현재 대상의 읽기 결과
→ 지금 시스템이 실제로 보이는 상태 결정

과거 문서·Screenshot·성공 사례
→ 형식·맥락·비교 참고
```

과거 성공값이나 모범문서의 실제값을 현재 실행값으로 전용하지 않는다.

## 9.2 사실과 해석을 분리한다

문서의 중요한 판단은 다음 순서로 추적 가능해야 한다.

```text
관찰된 사실
→ 그 사실이 의미하는 범위
→ 아직 확정하지 못한 것
→ 다음 판단에 필요한 증거
```

예:

```text
PVC Bound
→ Provisioning 단계 성공
→ Pod Mount·Write·Read는 아직 미확정
→ Pod Event와 실제 Mount·Write·Read가 다음 증거
```

## 9.3 같은 주체·대상·경로·시점의 증거를 사용한다

가능한 한 다음 Identity를 유지한다.

```text
같은 사용자·Account
같은 Cluster·Context
같은 Namespace·Project
같은 Node·Role 범위
같은 Image·Tag
같은 PVC·StorageClass
같은 FQDN·접속 경로
현재 작업과 연결되는 시각
```

다른 환경이나 다른 주체의 성공은 비교 자료일 수는 있어도 현재 경로의 완료 증거가 아니다.

## 9.4 증거의 의미·한계·다음 증거를 함께 쓴다

```text
증거:
의미:
한계:
다음 증거:
```

`Running`, `Ready`, `Bound`, `Login`, `apply 성공`, `Return Code 0` 같은 중간 상태 하나로 뒤 단계까지 완료 처리하지 않는다.

## 9.5 미확정값은 조용히 확정값으로 변하지 않는다

자료가 항목의 존재만 확인하고 값을 주지 않으면 필요한 경우에만 Placeholder를 사용한다.

```text
미확정 값
+ 확인 Source
+ 확인 담당자
+ 사용 금지 조건
```

을 함께 남긴다.

## 9.6 보호정보는 값이 아니라 사용 가능성을 증명한다

다음 원문을 교육자료·증적·화면 공유에 남기지 않는다.

```text
Password
Token·JWT
Secret Data
Private Key
kubeconfig 원문
Registry Credential
Join 보호값
```

필요한 경우에는 Object 이름, Key 존재 여부, 관리 위치, 사용 성공 여부, Rotation·폐기 필요 여부만 기록한다.

# 10. 완료·중단·Handoff를 역할에 맞게 닫는다

## 10.1 완료 기준은 관찰 가능한 결과여야 한다

나쁜 표현:

```text
정상 확인
설치 완료
문제 없어 보임
교육 완료
```

더 좋은 표현:

```text
승인된 사용자로 대상 Project Login·허용 작업 성공
실제 Pod가 대상 PVC를 Mount하고 Write·Read 성공
강사가 표 없이 전체 인과 흐름을 말로 진행하고 수강생 Teach-back에서 핵심 구분을 설명
미해결 FAILED·UNREACHABLE 없음
```

문서 역할이 요구하는 실제 결과를 쓴다.

## 10.2 Gate는 다음 행동을 실제로 바꿀 때만 만든다

```text
조건 충족
→ 다음 행동 허용

조건 미충족
→ 다음 행동 금지 또는 현재 범위에서 중단
```

결과에 따라 아무 행동도 달라지지 않으면 Gate가 아니라 확인 항목이다.

## 10.3 Handoff는 의미가 이어져야 한다

좋은 Handoff에는 필요한 경우 다음이 포함된다.

```text
대상 Identity
사용한 Source
현재 판정과 증거 범위
어디까지 실제 기능을 확인했는지
미확정 사항과 영향
다음 단계가 사용할 Input
담당자·기한·금지 조건
```

앞 문서의 Output과 다음 문서의 Input이 같은 의미와 상태 이름으로 이어져야 한다.

# 11. 문서 리뷰 판정

이 절의 판정은 **문서 품질과 작성 진행 상태**를 위한 것이다. 각 구축·검증 문서 내부의 운영 Gate 상태를 대체하지 않는다.

## 11.1 공통 Kill Questions

1. 누가 언제 왜 이 문서를 열며, 어떤 결과를 얻어야 하는지 한 문장으로 말할 수 있는가?
2. 독자의 실제 시작 상태와 대표 오판을 반영했는가?
3. 문서 전체가 답하는 중심 질문 하나가 있는가?
4. 역할에 맞는 하나의 조직 원리가 본문을 지배하는가?
5. 각 주요 절이 앞의 미해결 문제·상태·증거 때문에 필요한가?
6. 기술 이름과 세부사항이 Purpose를 돕는 자리에 있는가?
7. 원본 순서를 바꾼 경우 필요한 사실·경계·증거의 Coverage가 유지되는가?
8. 일반 개념, 승인값, 관찰값, 실행값, 결과값, 예시값, 미확정값이 섞이지 않는가?
9. 중간 성공을 최종 성공으로 확대하지 않는가?
10. 설명·조회·실습·실제 변경과 다른 문서로 보낼 범위가 명확한가?
11. 문서 역할에 맞는 실제 완료·복구·판정·조회 결과로 닫히는가?
12. 표·Checklist·Framework를 가려도 핵심 이야기나 행동 경로가 유지되는가?

## 11.2 역할별 마지막 Test

```text
강사용 전체 대본
→ 강사가 처음부터 끝까지 실제 발화로 이어갈 수 있고, 수강생이 전체 흐름을 자기 말로 복원하는가?

교육생 교재
→ 강사 대본 없이도 핵심 개념·관계·참조 위치를 다시 찾을 수 있는가?

강사용 메모
→ 짧게 보면서 중심 이야기·주의점·다음 전환을 즉시 복원할 수 있는가?

Runbook
→ 변경 전후 상태, 영향, Rollback, 실제 기능 검증이 닫혀 있는가?

Troubleshooting
→ 실제 오류에서 첫 실패 경계를 좁히고 같은 경로로 복구를 확인할 수 있는가?

검증·인수
→ 주장별 증거 범위와 잔여 영향에 따라 모호하지 않은 판정이 가능한가?

Reference
→ 사용자가 필요한 현재 사실과 Source를 빠르게 찾을 수 있는가?
```

## 11.3 판정 상태

| 판정 | 의미 | 다음 행동 |
|---|---|---|
| `PASS` | Purpose, 조직 원리, Source, 경계, 역할별 완료가 닫힘 | 사용·배포 가능 |
| `REVISE` | 중심 구조는 유효하며 국소 누락·표현·증거 연결만 보완하면 됨 | 해당 부분만 최소 수정 |
| `REBUILD` | 역할, 중심 질문, 인과 뼈대, 문서 분리가 잘못됨 | 문장 수정이 아니라 구조부터 재작성 |
| `SOURCE-BLOCKED` | 목적 달성에 필요한 핵심 사실·승인값·정책이 Source에서 확인되지 않음 | 추측하지 말고 필요한 Source를 확보할 때까지 해당 주장·실행 보류 |

`REVISE`와 `REBUILD`를 문장량으로 구분하지 않는다. **중심 구조를 유지할 수 있으면 REVISE, 유지할 수 없으면 REBUILD**다.

# 12. 반복해서 발생하는 치명적 실패

## 12.1 모범의 표면을 Template로 복제한다

제목, 절 수, Callout, 접속사 빈도를 복제하면 다른 문서의 Purpose가 사라진다.

## 12.2 기술 이름과 원본 목차부터 시작한다

독자는 정의 목록을 얻지만 왜 필요한지와 언제 사용하는지는 연결하지 못한다.

## 12.3 앞뒤 절이 관련만 있고 필요로 연결되지 않는다

각 절은 정확하지만 전체는 Checklist가 된다.

## 12.4 원본 순서를 바꾸면서 Coverage도 잃는다

교육 흐름은 좋아졌지만 승인값, 금지 경계, 완료 증거가 빠지면 사용할 수 없는 문서가 된다.

## 12.5 강사용 대본을 판정 Framework로 만든다

표, `A ≠ B`, Gate, Checklist가 실제 발화를 집어삼키면 강사용 전체 대본이 아니다.

## 12.6 모든 정상 흐름을 하나의 긴 화살표로 만든다

행위자와 행동이 다른 경로를 합치면 완료 기준과 장애 시작점이 흐려진다.

## 12.7 현재값·예시값·과거값을 섞는다

정확한 예시도 현재 실행값으로 오해되면 위험한 문서가 된다.

## 12.8 중간 성공을 끝단 성공으로 확대한다

프로세스 시작, Object 생성, Login 성공 하나로 실제 사용자·Workload 기능까지 완료 처리한다.

## 12.9 교육 목적과 운영 변경 목적을 섞는다

설명이나 조회에 불필요한 Create·Save·Delete를 교육 중 실행한다.

## 12.10 마무리에서 새 내용을 추가한다

독자가 전체를 복원해야 할 때 새로운 예외와 절차를 넣어 다시 방향을 잃게 한다.

# 13. 규율 위반 문서를 고치는 순서

문장이 어색하다고 문장부터 고치지 않는다.

```text
1. 문서 역할·독자·사용 순간 확정
→ 왜 존재하는 문서인지 고정

2. 독자의 시작 상태와 목표 변화 확정
→ 무엇이 달라져야 하는지 고정

3. 중심 질문과 한 줄 인과 뼈대 재구성
→ Topic 목록을 진행 경로로 전환

4. Source 해체와 Coverage 대조
→ 필요한 사실·경계·증거를 보존하고 불필요한 내용을 배치 변경

5. 절 단위 질문·답·오판·다음 질문 연결
→ 앞뒤 절의 필요 관계 복원

6. 역할별 본체 복원
→ 대본은 실제 발화, Runbook은 상태 전환, Troubleshooting은 첫 실패, 검증은 주장·증거가 지배

7. 실제값·증거·실행 경계·Handoff 확인
→ 과장과 무근거 실행을 제거

8. 표·문장·표현 다듬기
→ 마지막에 수행
```

Purpose와 조직 원리가 틀린 문서에서 표현만 다듬지 않는다.

---

# 14. 실제 작성의 최소 절차

```text
1. 설계 기록 작성
→ 역할·독자·시작 상태·목표 변화·중심 질문·Source·경계·완료

2. Source 해체
→ 사실·관계·절차·판단·증거·경계·미확정으로 분리

3. 한 줄 인과 뼈대 작성
→ 처음 문제에서 최종 결과와 Handoff까지 연결

4. 절 설계 카드 작성
→ 질문·답·필수 근거·오판·다음 질문

5. 역할에 맞는 본문 작성
→ 원본 목차가 아니라 독자의 진행 순서로 조립

6. Coverage·값 상태·증거 범위 확인
→ 누락과 과장을 제거

7. 역할별 사용 Test
→ 발화·실행·조회·복구·판정이 실제로 가능한지 확인

8. PASS / REVISE / REBUILD / SOURCE-BLOCKED 판정
→ 다음 행동을 명확히 결정
```

이보다 많은 절차가 목적 달성에 필요하지 않다면 추가하지 않는다.

> **모범문서의 진짜 작성 인사이트는 내용을 많이 설명하는 기술이 아니다. 독자의 현재 빈칸에서 시작해, 앞 문제 때문에 다음 역할이 필요해지는 인과를 만들고, 기술 이름·Xi'an 실제 구현·업무 Trigger·실행 경계·끝단 증거·첫 실패 지점을 같은 지도 위에 정확히 배치한 뒤, 마지막에 그 지도를 다시 복원하게 하는 기술이다.**
