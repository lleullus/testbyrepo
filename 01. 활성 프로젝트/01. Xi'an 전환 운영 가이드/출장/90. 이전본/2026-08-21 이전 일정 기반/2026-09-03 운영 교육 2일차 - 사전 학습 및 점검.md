# 2026-09-03 운영 교육 2일차 - 사전 학습 및 점검

> [!important] 이 문서의 역할
> 이 문서는 장애 발생 시 그대로 수행할 종합 Runbook이 아니다. **정상 운영 상태를 어떤 증거로 확인하는지 익히고, 문제가 들어왔을 때 원인을 바로 떠올리지 않고 문제·사실·차이·선후·정보 신뢰성·다음 분기를 순서대로 판단하는 능력을 가르칠 수 있도록 준비하는 학습 노트**다.

## 1. 9/3 확정 범위

- Cluster·Workload·ETCD·Certificate·Prometheus·Grafana 등 Daily Monitoring
- 정상 기준과 확인 순서 정리
- NFS PVC Mount 실패 사례
- Monitoring 오적용 사례
- Ingress/UI 504 사례
- Harbor 오류 사례
- ImagePull 사례
- 증상 확인 → 범위 축소 → 담당 영역 구분 → 에스컬레이션
- 조회 + 사례 기반 실습

이날의 핵심 질문:

> **지금 보이는 증상에서 무엇이 확인된 사실이고, 다음 행동을 실제로 갈라놓는 확인 하나는 무엇인가?**

## 2. 문제를 받을 때 사용할 고정 사고 순서

```text
문제 이해
→ 확인된 사실
→ 차이
→ 선후와 반응
→ 정보 신뢰성
→ 다음 판단을 가를 확인 하나
→ 답변
```

### 1. 문제 이해

```text
무슨 일이 벌어졌는가?
지금 무엇을 답하거나 결정해야 하는가?
```

### 2. 확인된 사실

```text
직접 확인된 사실
전해 들은 내용
누군가의 해석
아직 모르는 것
```

### 3. 차이

```text
문제 있는 것 ↔ 정상인 것
문제 전 ↔ 문제 후
발생하는 경우 ↔ 발생하지 않는 경우
```

### 4. 선후와 반응

```text
무엇이 먼저 변했는가?
어떤 조치 뒤 결과가 달라졌는가?
어떤 조치를 했는데도 그대로였는가?
```

### 5. 정보 신뢰성

```text
이 값은 실제 현재 상태인가?
어디에서 언제 확인했는가?
다른 Cluster / 과거 로그 / 참조 출력은 아닌가?
```

### 6. 다음 판단을 가를 확인 하나

```text
A이면 이쪽
B이면 저쪽
```

### 7. 답변

```text
확인된 사실
→ 현재 판단
→ 지금 할 확인 또는 행동
```

## 3. Daily Monitoring을 “명령 모음”이 아니라 정상 기준선으로 이해한다

Daily Monitoring의 목적은 명령을 많이 실행하는 것이 아니다.

> **평소 정상 상태를 알고 있어야 문제가 생겼을 때 무엇이 달라졌는지 볼 수 있다.**

확인 범주를 다음처럼 묶는다.

### 대상 확인

- Cluster / context
- Namespace / Project
- 확인 시각

### Kubernetes 기반

- Node 상태
- Control Plane / System Pod
- 주요 Workload
- 최근 Event

### ETCD

- Member / endpoint status
- Monitoring Target
- 해당 Cluster의 실제 ETCD인지

### Certificate

- API Server 인증서 만료 상태
- 대상 Master / 현재 시간 기준

### Storage

- StorageClass
- PVC
- 실제 Mount 이상 신호

### Monitoring

- Prometheus Pod
- Target
- Alert / Rule load
- Grafana datasource / Dashboard

### Service 경로

- Service / Endpoint
- Ingress
- 최종 HTTP

모든 항목을 매번 같은 깊이로 보라는 뜻이 아니라 **정상 기준을 어디에서 확인하는지 알고 있어야 한다.**

## 4. Daily Monitoring에서 반드시 피할 과잉 판정

```text
Node Ready
≠ Cluster 모든 기능 정상

Pod Running
≠ 서비스 정상

PVC Bound
≠ Mount 정상

Prometheus Pod Running
≠ Target 정상

Grafana UI 접속
≠ Datasource 정상

Ingress 존재
≠ 사용자 HTTP 정상
```

이 다섯 가지를 문서 없이 설명할 수 있어야 한다.

## 5. 사례 1 — NFS PVC Bound인데 Pod Mount 실패

관련:
[[50. 운영/08. 트러블슈팅/Kubernetes/03. NetApp NFS PVC는 Bound인데 Pod Mount가 실패하는 경우|NetApp NFS PVC Mount 실패]]

### 문제 구조

```text
PVC = Bound
Trident volume = 생성
Pod = ContainerCreating
Event = FailedMount / exit status 32
```

### 여기서 확정할 수 있는 것

Provisioning 단계와 Node Mount 단계는 다르다.

### 비교할 것

- 정상 Node와 문제 Node의 route
- Data LIF로 갈 때 실제 source IP
- TCP 2049
- 동일 export path의 Node direct mount

### 다음 판단을 가를 확인 예

```text
Node에서 같은 NFS export를 직접 mount할 수 있는가?

성공
→ Storage Network/export 접근은 통과. kubelet/CSI 쪽으로 좁힘

실패
→ route / network / export policy / path 쪽으로 좁힘
```

이것이 **결과에 따라 다음 행동이 바뀌는 확인**의 좋은 예다.

## 7. 사례 3 — Ingress를 사용하는 여러 UI가 간헐적 504

관련:
[[50. 운영/08. 트러블슈팅/Kubernetes/02. Ingress를 사용하는 여러 UI가 간헐적으로 504를 반환하는 경우|Ingress UI 504]]

### 정상 요청 경로

```text
User
→ VIP-B
→ Router
→ ingress-nginx-controller
→ Service
→ Backend Pod
```

### 중요한 관찰

여러 UI가 동시에 간헐적 504를 보이면 개별 애플리케이션보다 **공통 경로**를 먼저 본다.

실제 사건에서는 특정 ingress-controller에서만 504가 보였고 controller Pod 재생성 후에도 증상이 유지됐다.

이것은 중요한 반응 정보다.

```text
controller 재생성
→ 증상 동일
→ 단순 Pod 자체 문제 가설의 우선순위가 낮아짐
```

### 비교할 것

```text
정상 Router ↔ 문제 Router
같은 Backend Endpoint 접근 결과
```

### 바로 하지 않을 것

- timeout 일괄 상향
- 전체 ingress-nginx 재설치
- 근거 없는 LB 변경
- Router 재부팅

## 8. 사례 4 — Harbor 접속·로그인·Push/Pull 오류

관련:
[[50. 운영/08. 트러블슈팅/Harbor/01. Harbor 접속, 로그인 및 Image Push-Pull 오류|Harbor 접속·Push/Pull 오류]]

Harbor는 한 가지 “접속 문제”로 묶지 않는다.

### 웹은 되는데 Docker x509

```text
Network/Harbor 응답
vs
사용자 시스템 CA trust
```

### 웹과 Docker 인증 실패

```text
Registry 응답
vs
계정/권한
```

### Login 성공, Pull 실패

```text
Repository / Tag
vs
Private Project 권한
```

### Push 실패

```text
Local Image
→ Tag
→ Project write 권한
→ Artifact 생성
```

## 9. 사례 5 — Private Image `ImagePullBackOff`

관련:
[[50. 운영/08. 트러블슈팅/KubeSphere/02. Private Image 배포 시 ImagePullBackOff가 발생하는 경우|Private Image ImagePullBackOff]]

확인 흐름:

```text
Pod Event
→ Deployment Image 경로 / Tag
→ 같은 Namespace의 Image Registry Secret
→ Deployment imagePullSecrets 연결
→ Harbor 계정/Project 권한
```

### 오류 메시지에 따라 분기

```text
manifest unknown
→ Tag / Artifact 존재 여부

pull access denied
→ Secret / Harbor Project 권한

x509
→ Registry CA trust
```

문자열 하나만 보고 결론내리지 않고 **실제 Image 경로·Secret·권한과 대조**한다.

## 10. 사례를 가르칠 때 원인 정답을 먼저 주지 않는다

교육용으로는 다음 순서가 좋다.

```text

→ 다음 분기 확인 선택

```

강사가 원인과 명령을 먼저 말하면 절차는 전달되지만 판단 훈련이 약해진다.
