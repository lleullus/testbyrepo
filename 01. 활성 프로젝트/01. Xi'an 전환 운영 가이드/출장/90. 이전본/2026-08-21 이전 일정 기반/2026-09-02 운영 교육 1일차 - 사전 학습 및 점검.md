# 2026-09-02 운영 교육 1일차 - 사전 학습 및 점검

> [!important] 이 문서의 역할
> 이 문서는 사용자 계정을 만들고 Workload를 배포하는 현장 실행계획서가 아니다. **신청이 Workspace·Project·Role·Quota·Harbor 권한으로 바뀌고, Image·PVC·Deployment·Service·Ingress를 거쳐 실제 사용자 HTTP 응답까지 이어지는 전체 운영 흐름을 내가 이해·설명·시연할 수 있도록 준비하는 학습 노트**다.

## 1. 9/2 확정 범위

- Workspace·Project 생성
- 사용자 초대
- Role·RBAC
- Quota
- kubectl 접근
- Harbor Project·User·Role
- Harbor Image·Image Secret
- Deployment·Pod
- PVC·Mount
- Service·Endpoint
- Ingress·VIP
- 최종 HTTP 응답 확인
- 설명 + 직접/조회 실습

이날의 핵심 질문:

> **사용자의 “DKS를 쓰고 싶다”는 요청이 어떤 권한·자원 경계를 거쳐 실제 애플리케이션 HTTP 응답이 되는가?**

## 2. 전체 운영 흐름을 하나의 이야기로 설명한다

```text
사용자 신청
→ 대상 PRD / DEV 결정
→ Workspace
→ Project = Namespace
→ Workspace Member
→ Project Role
→ CPU / Memory / Storage Quota
→ 필요 시 kubectl 접근
→ Harbor Private Project / Member Role
→ Image Push / Pull
→ Image Secret
→ PVC
→ Deployment / Pod
→ Service / Endpoint
→ Ingress / VIP-B
→ 사용자 HTTP 응답
```

이 흐름에서 관리축과 운영축이 연결된다.

```text
관리축
사용자·신청 → 권한·Quota·작업 경계

운영축
Image·Storage → Workload → Network → 사용자 응답
```

## 3. Workspace와 Project를 구분한다

근거:
[[50. 운영/04. Kubesphere Operation/01. Creating Workspaces&projects|Creating Workspaces&projects]]

### Project

KubeSphere Project는 Kubernetes Namespace와 연결되는 실제 작업 경계다.

### Workspace

여러 Project와 멤버를 관리하는 상위 논리 관리 범위다.

DKS 운영 정책에서는 Workspace와 Project를 1:1로 운영한다.

### 반드시 구분할 문장

```text
Workspace에 초대됐다
≠ Project 안에서 Workload를 변경할 권한이 있다

Project가 존재한다
≠ 사용자에게 권한이 부여됐다
```

## 4. 신청서가 실제 설정으로 바뀌는 과정을 이해한다

신청에서 최소 다음 정보를 읽어야 한다.

- 사용자 / 담당자
- Admin / User 요청
- PRD / DEV Project
- CPU
- Memory
- Storage
- 애플리케이션 정보

그리고 다음으로 변환한다.

```text
Project 접미사
→ 대상 Member Cluster

Permission
→ Project Role

CPU / Memory
→ Workspace / Project Quota

Storage
→ Storage ResourceQuota

Harbor 사용
→ Private Project + Member Role
```

핵심은 UI를 누르는 것보다 **신청값을 실제 플랫폼 경계로 변환하는 판단**이다.

## 5. Workspace 초대와 Project Role을 구분한다

관련:
[[50. 운영/04. Kubesphere Operation/02. Inviting a new member|Inviting a new member]]
[[50. 운영/04. Kubesphere Operation/03. Assigning project roles to users|Assigning project roles to users]]

### Project Role

- `project-admin`
- `project-operator`
- `project-viewer`

DKS 정책의 핵심:

```text
신청서 Admin
→ project-operator

신청서 User
→ project-viewer
```

`Admin`이라는 단어만 보고 `project-admin`을 주지 않는다.

`project-admin`은 멤버 관리까지 가능한 더 강한 권한이므로 별도 운영 정책으로 본다.

## 6. KubeSphere RBAC 3계층을 이해한다

근거:
[[50. 운영/04. Kubesphere Operation/05. Kubesphere Role-Based Access Control|KubeSphere RBAC]]

```text
Platform
→ Workspace

```

### 내가 설명할 질문

- Platform Admin은 어디까지 관리하는가?
- Workspace Role은 무엇을 관리하는가?
- Project Role은 실제 Workload·Storage·Secret에 어떤 권한을 주는가?
- 멤버 관리 권한은 operator/viewer와 어떻게 다른가?

세부 권한표 전체를 암기하지 않는다. **권한 범위의 계층과 최소 권한 원칙**을 먼저 체화한다.

## 7. Quota를 자원 경계로 이해한다

근거:
[[50. 운영/04. Kubesphere Operation/04. Setting quotas|Setting quotas]]

### CPU / Memory

- Requests = 예약·스케줄링의 기준이 되는 요구량
- Limits = 사용 상한

### DKS의 Workspace / Project Quota

1:1 운영 정책 때문에 신청값을 양쪽에 일관되게 반영한다.

### Storage Quota

- Namespace 전체 Storage 요청 총량
- 특정 StorageClass별 요청 총량

### 중요한 원칙

StorageClass 이름은 문서 예시를 그대로 믿지 않고 **대상 Cluster의 실제 StorageClass를 확인한 뒤** ResourceQuota에 반영한다.

## 8. kubectl 사용자 접근을 어떤 경계로 볼 것인가

근거:
[[50. 운영/04. Kubesphere Operation/06. Enable users using kubectl CLI|Enable users using kubectl CLI]]

kubectl은 기본 KubeSphere Web UI와 별도의 우회/CLI 접근 경로다.

큰 흐름:

```text
Bastion 계정
→ 접근 승인 / CyberArk 등 외부 조건
→ 사용자 kubeconfig
→ 대상 Cluster VIP-A
→ context
→ Project 권한 범위
```

### 절대 학습 노트에 옮기지 않을 것

- kubeconfig 인증 데이터
- client private key
- token
- 비밀번호
- JWT Secret

내가 숙지할 것은 **kubeconfig가 어떤 Cluster·사용자·context를 결정하는가**이다.

## 9. Harbor Project와 KubeSphere Project를 구분한다

근거:
[[50. 운영/06. Harbor Manual/02. Create a project|Create a Harbor Project]]
[[50. 운영/06. Harbor Manual/03. Managing Users|Managing Harbor Users]]

### Harbor Project

Private Image 공급 경계다.

기본 원칙:

- Private
- Project member만 Pull
- 승인된 사용자에게 Role 부여

### Harbor 역할

- ProjectAdmin
- Developer

Developer도 Image 읽기/쓰기가 가능하지만 멤버 관리는 할 수 없다.

### 반드시 구분

```text
KubeSphere Project
= Kubernetes Namespace / Workload 작업 경계

Harbor Project
= Private Container Image 공급·권한 경계
```

## 10. Harbor Image 흐름을 이해한다

근거:
[[50. 운영/07. DKS User Guide/02. Harbor User Guide|Harbor User Guide]]

```text
사용자 시스템
→ Harbor CA trust
→ Registry login
→ Image pull / local image
→ Tag
→ Push
→ Harbor Repository / Artifact
→ Kubernetes Image Secret
→ Deployment image pull
```

### 오류를 미리 구분한다

- CA 신뢰 오류
- 로그인/계정 오류
- Repository/Tag 오류
- Project 권한 오류

Harbor 웹 접속 성공과 Docker CLI 성공도 같은 증거가 아니다.

## 11. Image Secret을 이해한다

근거:
[[50. 운영/07. DKS User Guide/03. KubeSphere User Guide|KubeSphere User Guide]]

- Deployment와 같은 Project/Namespace에 존재해야 함
- Registry 주소와 계정 정보를 담는 Secret
- Secret을 만들었다고 자동 적용되는 것이 아니라 Deployment의 `imagePullSecrets`에 연결되어야 함
- Secret data는 출력·기록하지 않음

### 반드시 구분

```text
Secret 존재
≠ Deployment가 Secret을 사용

Harbor login 성공
≠ 해당 Project Image를 Pull할 권한 보장
```

## 12. 정상 애플리케이션 경로를 하나로 묶는다

### 배포 경로

```text
Harbor Image
+ Image Secret
→ Deployment
→ Pod
```

### Storage 경로

```text
StorageClass
→ PVC Bound
→ Pod Mount
→ 실제 사용
```

### 사용자 요청 경로

```text
User
→ DNS / VIP-B
→ Ingress
→ Service
→ Endpoint
→ Pod
→ HTTP 응답
```

### 관리 경로

```text
관리자 / kubectl
→ VIP-A
→ Kubernetes API
```

VIP-A를 사용자 HTTP 경로에 넣지 않는다.

## 13. Service와 Endpoint를 반드시 분리한다

Service 객체가 있다고 실제 Pod에 연결되는 것은 아니다.

```text
Service selector
↔ Pod label
→ Endpoint 생성
```

Selector가 틀리면 Service는 존재해도 Endpoint가 비어 있을 수 있다.

이 관계는 9/3 장애 판단의 핵심이 된다.

## 14. Ingress와 VIP-B를 이해한다

```text
Ingress Host / Path
→ Service / Port
→ Endpoint / Pod
```

외부에서는:

```text
DNS / FQDN
→ VIP-B
→ Router / ingress-nginx
→ Ingress rule
```

PRD와 DEV Domain을 혼용하지 않는다.

## 15. 최종 정상은 HTTP 응답까지 본다

```text
Pod Running
≠ Service 정상
≠ Endpoint 정상
≠ Ingress 정상
≠ 사용자 HTTP 정상
```

따라서 9/2의 정상 시나리오는 **최종 사용자 응답**까지 가야 한다.
