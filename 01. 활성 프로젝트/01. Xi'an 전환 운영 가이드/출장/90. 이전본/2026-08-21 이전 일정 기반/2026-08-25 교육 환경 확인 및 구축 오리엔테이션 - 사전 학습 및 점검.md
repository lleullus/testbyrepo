## 2. 이날 설명하기 위해 머릿속에 있어야 할 전체 구조

### 2.1 Xi'an DKS 구성요소의 역할

최소 다음 구성을 한 장의 그림으로 그릴 수 있어야 한다.

```text
                       ┌─────────────────────┐
                       │ Host Cluster        │
                       │ prd-host-pa01-xas   │
                       │ 중앙 KubeSphere 관리 │
                       └─────────┬───────────┘
                                 │ Multi-Cluster
                   ┌─────────────┴─────────────┐
                   │                           │
        ┌──────────▼──────────┐     ┌──────────▼──────────┐
        │ PRD Member          │     │ DEV Member          │
        │ prd-apps-pa01-xas   │     │ dev-apps-pa01-xas   │
        │ 사용자 Workload     │     │ 사용자 Workload     │
        └─────────────────────┘     └─────────────────────┘

Harbor
→ Kubernetes가 사용할 Private Image 공급

Storage / NetApp Trident
→ PVC가 실제 Volume을 할당받고 Pod가 Mount할 수 있게 함

Monitoring
→ Cluster·Workload·ETCD 상태를 관측

Bastion
→ 구축·관리 명령을 실행하는 기준점

VIP-A
→ Kubernetes API

VIP-B
→ Application / UI Ingress
```

### 2.2 문서 없이 설명할 핵심 관계

```text
Host = 중앙 KubeSphere 관리
Member = 사용자 Workload 실행
Harbor = Private Image 공급
Storage = Workload의 영속 Volume 제공
Monitoring = 상태 관측
Bastion = 구축·관리 실행 거점
VIP-A = Kubernetes API
VIP-B = Ingress / 사용자 접속
```

이 관계는 정확한 IP를 외우는 것보다 먼저 체화해야 한다.

## 4. 신규 VM 실습환경에서 새로 확인해야 할 값

기존 완성환경의 값과 별도로 아래 항목을 신규 VM 기준으로 확보해야 8/26 Inventory 준비가 가능하다.

| 항목 | 왜 필요한가 | 8/25 학습 포인트 |
|---|---|---|
| VM hostname / IP | Inventory의 직접 입력 | 어떤 노드를 어느 역할에 넣는지 설명 가능해야 함 |
| Node role | Master·ETCD·Router·Infra·Worker 구분 | 역할별 Pod 배치와 구축 결과에 미치는 영향 이해 |
| Bastion | Kubespray와 관리 명령 실행점 | 왜 Bastion이 필요한지 설명 |
| VIP-A | Kubernetes API endpoint | VIP-B와 혼동하지 않기 |
| VIP-B | Ingress / UI / Application traffic | API 경로와 사용자 경로 분리 |
| Pod CIDR | Pod Network | 다른 Cluster와 중복되면 안 되는 이유 이해 |
| Service CIDR | Cluster Service Network | Pod CIDR과 역할 구분 |
| Domain | Ingress·서비스 접근 | Host와 Member domain 역할 구분 |
| Registry | Offline/Private image 공급 | Harbor와 Kubespray/KubeSphere image 관계 이해 |
| Storage | Trident·StorageClass·PVC | Kubernetes 이후 왜 선행되는지 이해 |
| ETCD 정보 | Cluster state 및 Member Monitoring | Kubernetes ETCD와 Monitoring 대상 관계 이해 |
| 계정·sudo·SSH | 실제 구축 실행 가능성 | 연결 실패와 Kubernetes 실패를 구분 |

## 9. 과거 환경 준비 문서를 읽을 때 주의할 점

[[20. 환경 준비/환경 준비 및 의존성|환경 준비 및 의존성]]에는 Xi'an 구축 당시 VM·L4·방화벽·Harbor·Storage·AD 협의 이력이 있다. 이 문서는 **“무엇이 외부 의존성이었는가”를 배우는 자료**로 사용한다.

다만 문서에 남아 있는 `요청중`, `미구성` 등의 과거 상태를 현재 시스템의 미완료로 해석하지 않는다. 현재 Xi'an 구축은 완료 상태다.

이 문서에서 학습할 포인트:

- VM과 L4는 Kubernetes보다 먼저 준비되는 외부 조건이다.
- SCS VM에서 Nexus/JFrog/Harbor 등 외부 repository 접근이 구축에 영향을 줄 수 있다.
- Harbor FQDN·인증서는 image 공급 경로의 선행조건이다.
- NetApp Storage는 Kubernetes만의 내부 문제가 아니라 Storage 측 SVM·Data LIF·정책과 연결된다.
- 구축 문제를 볼 때 Kubernetes 내부와 외부 인프라 경계를 구분해야 한다.

### 연습 1 — Xi'an 전체 구조를 5분 동안 설명

```text

- Monitoring을 서비스 요청 경로 자체로 설명하지 않는다.

Service CIDR
```

### 연습 4 — 실제 완성환경 조회 연습

kubectl get nodes -L node-type

kubectl get pod -A

명령을 외우는 것이 아니라 **어떤 질문에 답하기 위해 쓰는지** 설명할 수 있어야 한다.

### 사례 1 — “kubectl은 되는데 내가 보려던 Cluster가 아니다”

```text
문제 이해
→ 명령이 성공했는지가 아니라 올바른 대상을 보고 있는지 판단해야 한다.

확인된 사실
→ kubectl 명령은 성공했다.

차이
→ 기대 Cluster와 current-context가 같은가?

선후와 반응
→ context를 확인하기 전에 다른 상태를 해석하지 않는다.

정보 신뢰성
→ 화면에 보이는 Node 이름이 어느 Cluster 카탈로그와 일치하는지 대조한다.

다음 판단을 가를 확인 하나
→ kubectl config current-context
```

### 사례 2 — “신규 VM Inventory에 기존 Xi'an IP가 들어가 있다”

```text
문제 이해
→ 기존 정상값을 참고한 것인지, 실습환경 실제값을 잘못 복사한 것인지 구분해야 한다.

확인된 사실
→ Inventory 값과 신규 VM 배정표가 다르다.

차이
→ 어떤 필드가 기존 Xi'an 카탈로그 값과 일치하는지 본다.

다음 판단을 가를 확인 하나
→ 신규 VM 배정표와 실제 hostname/IP를 직접 대조한다.
```

### 사례 3 — “VIP로 접속이 안 된다”

원인부터 LB라고 단정하지 않는다.

```text
먼저 묻기
→ VIP-A인가 VIP-B인가?

VIP-A라면
→ Kubernetes API 경로를 확인

VIP-B라면
→ Ingress / Router 경로를 확인
```

이 한 구분만으로 조사 방향이 달라진다는 것을 설명할 수 있어야 한다.
