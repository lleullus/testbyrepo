## 3. Host installer 완료를 어떻게 볼 것인가

근거: [[30. 구축 및 전환/공통 구축/Xi'an/한국어/05-1|5-1. KubeSphere Host 클러스터 설치 및 운영 구성]]

### installer Pod 상태

먼저 `ks-installer` 자체가 정상 기동했는지 본다.

하지만 다음을 구분한다.

```text
ks-installer Pod Running
≠ 내부 설치 task 모두 성공
```

내가 설명할 수 있어야 할 task 범주:

- monitoring
- multicluster
- openpitrix
- network
- devops

설치 로그에서 각 task가 successful인지 보고, 실패했으면 **어떤 선행 CRD/구성이 없는지**를 먼저 판단한다.

## 4. DKS 표준 workload 재배치를 이해하기

KubeSphere installer가 생성한 모든 workload가 자동으로 DKS의 원하는 node role에 배치되는 것은 아니다.

Host 환경에서는 KubeSphere·Monitoring 관련 주요 workload를 Infra 계층에 배치한다.

### 내가 이해해야 할 두 요소

#### nodeSelector

```text
어느 Node에 배치될 수 있는가
```

#### toleration

```text
그 Node의 taint를 허용하고 실제로 스케줄될 수 있는가
```

둘 중 하나만 보고 완료라고 하지 않는다.

### 검증은 manifest가 아니라 실제 Pod NODE까지

```text
spec에 nodeSelector가 있다
+ toleration이 있다
+ 실제 새 Pod가 대상 infra Node에 배치됐다
```

이 세 단계를 연결해서 설명한다.

## 5. `ks-installer` 종료 상태를 이해한다

Host 설치 완료 후 installer가 계속 동작하면 이미 적용한 설정이 다시 설치 기본 방향으로 영향을 받을 수 있다.

따라서 문서에서는 설치 완료 뒤 `ks-installer` replica를 `0`으로 유지하는 흐름이 있다.

여기서 외울 것은 `scale` 명령 자체가 아니라:

> **installer는 영구 운영 컴포넌트가 아니라 설치를 수행하는 컴포넌트이고, 설치 후 운영 상태와 구분해야 한다.**

## 6. Workspace RoleBase가 왜 Host 구축에 들어가는가

Host는 중앙 KubeSphere 관리 Cluster이므로 Workspace 수준 권한 모델도 준비한다.

근거:
[[30. 구축 및 전환/Host 클러스터/05.1.1.6 Deploying Custom Role Base (Workspace)|Workspace RoleBase]]

알아야 할 큰 범주:

- viewer
- self-provisioner
- regular
- admin

8/31에는 이것을 단순 YAML apply로 보지 않고 **9/2 사용자 관리 교육을 가능하게 하는 관리축의 기반**으로 이해한다.

## 7. Prometheus 운영 구성을 설명하기

### retention

얼마 동안 metric을 보관하는가.

기존 Xi'an Host 정상 기준에서는 `30d`가 사용된다.

### external label

Metric이 어느 Cluster / Stage에서 온 것인지 식별한다.

기존 Host 정상 기준 예:

```text
cluster = prd-host-pa01-xas
stage = Prd
```

신규 VM 실습 Host에서는 실제 실습 Cluster identity에 맞춰 확인한다.

### Alert / Recording Rule

- Recording Rule: 자주 쓰는 계산 결과를 미리 기록
- Alert Rule: 조건이 만족되면 이상 상태를 판단

문서에서 DKS 표준은 기존 rule의 성격을 구분하고 custom Sensor alert를 반영하는 흐름이 있다.

정확한 rule YAML 암기보다 다음을 설명할 수 있어야 한다.

> **Metric 수집이 정상인 것과, 그 metric을 어떤 이름·보관기간·alert 정책으로 운영할지는 별도의 운영 구성이다.**

## 8. Alertmanager를 큰 구조로 이해하기

```text
Prometheus Alert Rule 조건 충족
→ Alertmanager
→ route / receiver
→ 승인된 알림 대상
```

Secret 내용이나 webhook 인증값은 학습 문서에 기록하지 않는다.

알아야 할 것은:

- Secret이 어느 Namespace에 있어야 하는가
- Alertmanager가 설정을 읽었는가
- Pod가 정상인가
- 실제 알림 수신 테스트는 승인 범위에 따라 별도라는 점
