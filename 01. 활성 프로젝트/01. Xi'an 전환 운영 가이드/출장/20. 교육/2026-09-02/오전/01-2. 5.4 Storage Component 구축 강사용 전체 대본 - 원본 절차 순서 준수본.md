# 5.4 Storage Component 구축 강사용 전체 대본 - 원본 절차 순서 준수본

> [!important] 사용 방법
> 이 대본은 **원본 `04.md`의 `4-0 → 4-1 → 4-2 → 4-3` 순서와 그 안의 작업 행위를 그대로 따라가면서 설명하기 위한 강사용 대본**입니다.
>
> 설명하기 편하다는 이유로 원본의 `apply`, `cd`, `ls`, `cat`, 상태 조회, 재조회 같은 중간 행위를 합치거나 순서를 바꾸지 않습니다. 원본에 같은 명령이 앞뒤로 반복되면 그 반복도 남겨 두고, 왜 같은 명령을 다시 보는지만 설명합니다.
>
> 다만 **실제 신규 Member의 적용 여부와 실행값은 [[출장/30. 구축/2026-09-02 Member 구축 3일차 - Storage 구성 및 사용 검증|9/2 Member 구축 Source of Truth]]를 우선**합니다. 원본에 남아 있는 Host/Taylor의 hostname·IP·Credential·PowerFlex MDM·systemID·NetApp LIF·Backend·StorageClass 값을 신규 Member 실행값으로 복사하지 않습니다.
>
> 강사는 큰 단계에 들어갈 때 먼저 **“그래서 이 단계에서 결국 무엇을 만드는가?”**를 한 문장으로 잡습니다. 그다음 그 문장을 이해시키는 핵심 설명만 하고 바로 원본 절차로 들어갑니다. 세부 개념은 실제 관련 명령이 나오는 자리에서 설명합니다.
>
> Credential·Secret·Token·Private Key 원문은 화면·녹화·증적에 남기지 않습니다. 원본에 Credential을 직접 출력하는 확인 단계가 있더라도 그 단계의 목적과 위치는 보존하되 현재 교육에서는 비민감 방식으로 정합성을 확인합니다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
오늘 목적: Kubernetes의 PVC 요청이 실제 Storage까지 갈 수 있는 공급 경로를 만든다

원본 4-0  어느 Cluster에 어떤 Storage를 붙일지 기준을 고정한다
→ 4-1       Snapshot 요청을 Kubernetes가 이해하고 관리할 공통 기반을 만든다
→ 4-2       필요하면 PVC를 PowerFlex Block Volume까지 연결하는 경로를 만든다
→ 4-3       PVC를 실제 NetApp Storage까지 연결하는 Trident 경로를 만든다
   → Trident 설치
   → 실제 NetApp Backend 연결
   → StorageClass로 사용자가 선택할 공급 정책을 노출
→ 오후 4-4  실제 PVC → PV → Pod Mount → Write/Read로 기능을 증명한다
```

## 0-1. 오늘 전체 한 줄

> **오늘 오전은 Storage를 실제 사용해 보는 시간이 아니라, Kubernetes가 Storage 요청을 받아 실제 Storage까지 전달할 수 있는 공급 경로를 원본 순서대로 준비하는 시간입니다.**

---

# 1. 시작 — Kubernetes Cluster 다음에는 Storage 공급 경로가 필요하다

> 어제까지는 Kubernetes Cluster 자체를 만들고 기본 기능을 확인했습니다.
>
> 하지만 Cluster가 정상이라고 Application이 Persistent Storage를 바로 사용할 수 있는 것은 아닙니다. Application은 PVC를 만들 뿐이고, 그 요청을 실제 Storage Volume으로 바꾸는 CSI, 실제 Storage를 가리키는 Backend, 사용자가 선택하는 StorageClass가 별도로 필요합니다.
>
> 그래서 오늘 오전은 `StorageClass가 보인다`를 목표로 하지 않습니다. **Snapshot 공통 기반과 Storage Driver, 실제 Storage 연결, StorageClass까지 이어지는 공급 경로를 준비하는 것**이 목표입니다.
>
> 그리고 이 오전 성공도 최종 Storage 성공은 아닙니다. 오후 원본 `4-4`에서 실제 PVC를 만들고 `PVC → PV → Pod Mount → Write/Read → Cleanup`까지 닫아야 기능이 증명됩니다.

---

# 2. 원본 4-0 — 어느 Cluster에 어떤 Storage를 붙일지 기준을 고정한다

> **이 단계의 핵심은 “어디에 무엇을 붙이는 작업인지 먼저 고정한다”입니다.**
>
> 뒤에서 실행할 Snapshotter·PowerFlex·Trident·Backend·StorageClass 작업은 실제 Kubernetes Resource와 Storage 연결을 만듭니다. 따라서 여기서 대상 Cluster나 Storage 기준을 잘못 잡으면 뒤 명령이 전부 성공해도 잘못된 환경을 정상적으로 변경한 것입니다.
>
> 원본 `4-0`에는 Xi'an Host 기준의 Storage Index와 확인값이 남아 있습니다. 신규 Member에서는 그 과거 값을 실행값으로 사용하지 않고, 현재 현장 Source of Truth와 live Cluster 결과를 기준으로 다시 고정합니다.

## 2.1. 먼저 작업 대상을 고정한다

```bash
kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide
```

> `current-context`는 지금 `kubectl`이 어느 Cluster를 향하는지, `cluster-info`는 실제 API Endpoint가 어디인지, `get nodes`는 그 Cluster에 어떤 Node가 등록돼 있는지를 확인합니다.
>
> 원본 Host의 Cluster 이름이나 `xadks*hm*` Hostname이 보이는 것이 정답이 아닙니다. **지금 구축 중인 신규 Member의 Context와 Node가 보여야** 합니다.

그다음 실제 Role을 확인합니다.

```bash
kubectl get nodes -L node-type
kubectl get nodes -l node-type=infra -o wide
```

> Snapshot Controller와 Trident Controller의 배치 기준을 뒤에서 판단하려면 현재 Infra Node가 누구인지 알아야 합니다. 이 결과는 뒤의 Replica·NodeSelector·Toleration을 해석하는 기준이 됩니다.

## 2.2. 오늘 사용할 Storage 기준을 세 묶음으로 고정한다

| 구분 | 확인할 값 | 현재 기준 |
|---|---|---|
| 어디에 작업하나 | Cluster / Context | 현재 신규 Member |
| 어디에 작업하나 | Bastion / Node / Role | 현재 신규 Member 실제 Host |
| 무엇을 설치하나 | Registry / Bundle | 현재 승인 Registry·SCS Stack |
| 무엇을 설치하나 | Storage 방식 | 9/2 실행 범위는 Snapshotter·NetApp Trident·Backend·StorageClass |
| 어느 Storage에 연결하나 | StorageClass | `scs-netapp-qtree-nfs-sc-delete`를 현재 Source of Truth 기준으로 검증 |
| 어느 Storage에 연결하나 | SVM | 현재 승인값 |
| 어느 Storage에 연결하나 | Management LIF | 현재 Backend 관리 경로 |
| 어느 Storage에 연결하나 | Data LIF | 실제 NFS Data 경로 |
| 어느 Storage에 연결하나 | Credential Source | 승인된 Secret/보관소, 원문 기록 금지 |

> 현재 확인되지 않은 SVM·LIF·Bundle Version·Backend 값은 Host/Taylor 값으로 채우지 않습니다. 확인 전에는 미확정으로 남기고, 실제 승인값이 확보된 뒤 해당 원본 명령을 실행합니다.

### 여기까지 성공한 범위

> **이제 어느 Cluster에 어떤 Storage 경로를 만들 것인지 기준이 고정됐습니다.** 아직 Snapshotter도 Trident도 설치한 것이 아니고 Storage 기능도 증명하지 않았습니다.
>
> 원본 다음 단계는 `4-1 External Snapshotter`입니다.

# 3. 원본 4-1 — Snapshot 요청을 Kubernetes가 이해하고 관리할 기반을 만든다

> **External Snapshotter를 한 줄로 말하면 “Kubernetes가 Volume Snapshot 요청을 이해하고 상태를 관리할 공통 기반”입니다.**
>
> `VolumeSnapshot`은 PVC/PV가 사용하는 Volume의 특정 시점 상태를 남기기 위한 Kubernetes 요청입니다. Snapshot Controller는 그 요청과 상태를 관리하고, 실제 Storage에서 Snapshot을 만드는 작업은 해당 CSI Driver가 담당합니다.
>
> 따라서 이 절의 목표는 **실제 NetApp Snapshot 생성 성공이 아니라 Snapshot API와 Controller 기반을 준비하는 것**입니다.

```text
VolumeSnapshot 요청
→ Snapshot CRD
→ Snapshot Controller가 요청과 상태를 관리
→ Storage CSI Snapshot 기능
→ 실제 Storage Snapshot
```

원본 `4-1-1`의 명령 순서를 그대로 따라갑니다.

## 3.1. 원본 첫 번째 — External Snapshotter Manifest 전체를 먼저 적용한다

```bash
kubectl apply -f /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/external-snapshotter/
```

> 원본은 파일을 먼저 펼쳐 보는 순서가 아니라 **Directory 전체를 먼저 적용하는 순서**입니다. Snapshot CRD, ServiceAccount/RBAC, Snapshot Controller Deployment가 생성되거나 갱신됩니다.
>
> 결과에서 `created`, `configured`, `unchanged`를 구분해서 봅니다. 오류가 있으면 뒤 검증 명령이 정상처럼 보이더라도 완료 처리하지 않습니다.

## 3.2. 원본 두 번째 — 방금 적용한 Manifest 파일을 확인한다

```bash
ls -al /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/external-snapshotter
```

원본 기준 주요 파일은 다음과 같습니다.

```text
1.snapshot.storage.k8s.io_volumesnapshotclasses.yaml
2.snapshot.storage.k8s.io_volumesnapshotcontents.yaml
3.snapshot.storage.k8s.io_volumesnapshots.yaml
4.rbac-snapshot-controller.yaml
5.setup-snapshot-controller.yaml
```

> 여기서 세 Snapshot 객체의 역할을 연결합니다.
>
> `VolumeSnapshotClass`는 **어떤 CSI와 정책으로 Snapshot을 처리할지 정하는 기준**, `VolumeSnapshot`은 **사용자가 만드는 Snapshot 요청**, `VolumeSnapshotContent`는 **Kubernetes 요청과 실제 Storage Snapshot 결과를 연결하는 Cluster 범위 객체**입니다.
>
> 뒤의 RBAC과 Controller Manifest는 그 객체를 실제로 감시하고 상태를 갱신할 Snapshot Controller를 준비합니다.

## 3.3. 원본 세 번째 — Snapshot Controller Replica 수를 확인한다

```bash
cat /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/external-snapshotter/5.setup-snapshot-controller.yaml | grep -e replicas:
```

> 원본 Host 참조 출력은 `replicas: 3`이지만 숫자 `3` 자체가 신규 Member의 정답은 아닙니다. **현재 승인된 Infra 구성에 맞는 Replica인지**를 확인합니다.

## 3.4. 원본 네 번째 — 같은 External Snapshotter Manifest를 다시 적용한다

```bash
kubectl apply -f /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/external-snapshotter/
```

> 여기서 두 번째 `apply`를 하는 이유를 **`검수한 Manifest를 기준으로 Cluster 상태를 다시 원하는 상태에 맞추는 것`**이라고 이해하면 됩니다.
>
> 첫 번째 `apply`에서는 External Snapshotter Resource를 일단 Cluster에 생성·반영합니다. 그다음 원본은 실제 설치 Directory와 `snapshot-controller`의 `replicas` 값을 확인합니다. 즉 **방금 적용한 Package가 우리가 의도한 구성인지 Manifest 기준으로 다시 검수**하는 단계가 중간에 들어갑니다.
>
> 그 검수가 끝난 뒤 같은 Directory를 다시 `apply`하면, `kubectl apply`가 Manifest에 선언된 상태와 현재 Cluster 상태를 다시 비교해 차이가 있으면 맞추고, 이미 같으면 `unchanged`로 둡니다. 따라서 두 번째 `apply`는 별도의 새 설치라기보다 **`확인한 Manifest를 최종 기준으로 다시 수렴시키는 재적용`**에 가깝습니다.
>
> 원본에는 이 사이에 Replica를 수정하는 명령이 따로 기록되어 있지는 않습니다. 그래서 **`Replica를 바꿨기 때문에 다시 적용한다`고 설명하면 안 되고**, `첫 적용 → Manifest/Replica 검수 → 검수한 동일 Manifest 재적용 → 실제 CRD/RBAC/Pod 검증`이라는 흐름으로 설명합니다.

## 3.5. 원본 다섯 번째 — Snapshot CRD 3종을 확인한다

```bash
kubectl get crd | grep volumesnapshot
```

확인 대상:

```text
volumesnapshotclasses.snapshot.storage.k8s.io
volumesnapshotcontents.snapshot.storage.k8s.io
volumesnapshots.snapshot.storage.k8s.io
```

> CRD는 Kubernetes API가 `VolumeSnapshot*`이라는 새로운 종류의 객체를 이해하게 만드는 정의입니다. `apply` 명령이 성공했다는 사실과 실제 API에 CRD가 등록됐다는 사실은 구분해서 봅니다.

## 3.6. 원본 여섯 번째 — Snapshot Controller ServiceAccount를 확인한다

```bash
kubectl get sa -A | grep snapshot
```

> Controller가 어느 Kubernetes Identity로 동작할지 확인합니다.

## 3.7. 원본 일곱 번째 — Role을 확인한다

```bash
kubectl get Role -A | grep snapshot
```

> Namespace 범위에서 Snapshot Controller가 필요한 작업을 할 권한이 만들어졌는지 봅니다.

## 3.8. 원본 여덟 번째 — RoleBinding을 확인한다

```bash
kubectl get RoleBinding -A | grep snapshot
```

> Role이 존재하는 것과 그 Role이 실제 ServiceAccount에 연결된 것은 별개입니다. 여기서는 Binding을 확인합니다.

## 3.9. 원본 아홉 번째 — ClusterRole을 확인한다

```bash
kubectl get ClusterRole | grep snapshot
```

> Snapshot CRD는 Cluster 범위 객체도 포함하므로 Controller가 Cluster 범위에서 필요한 권한을 갖는지 확인합니다.

## 3.10. 원본 열 번째 — ClusterRoleBinding을 확인한다

```bash
kubectl get ClusterRoleBinding | grep snapshot
```

> ClusterRole이 실제 Snapshot Controller의 ServiceAccount와 연결됐는지 확인합니다.

## 3.11. 원본 열한 번째 — Snapshot Controller Pod를 확인한다

```bash
kubectl get pod -n kube-system -o wide | grep snapshot
```

> 마지막에는 정의와 권한이 아니라 **실제로 Snapshot Controller Process가 동작하는지** 봅니다. `Running/Ready`, 비정상 Restart 여부, 실제 배치 Node가 현재 신규 Member의 승인 기준과 맞는지를 확인합니다.

### 여기까지 성공한 범위

> **Kubernetes가 Snapshot 요청을 이해하고 관리할 공통 기반이 준비됐습니다.** 실제 NetApp이나 PowerFlex Storage에서 Snapshot이 생성된 것까지 증명한 것은 아닙니다.
>
> 원본 다음 단계는 `4-2 PowerFlex 스토리지 컴포넌트 설치(필요 시)`입니다.

# 4. 원본 4-2 — 필요하면 PVC를 PowerFlex Block Volume까지 연결한다

> **PowerFlex 절차의 핵심은 “Kubernetes 요청 경로와 Node의 Block Data Path를 둘 다 만든다”입니다.**
>
> CSI는 PVC 요청을 PowerFlex Volume 생성·삭제 같은 Storage 작업으로 연결하고, SDC/`scini`는 실제 PowerFlex Volume을 Kubernetes Node에서 Block Device로 사용할 수 있게 합니다. 둘 중 하나만 정상이어서는 공급 경로가 완성되지 않습니다.

```text
PVC
→ StorageClass
→ PowerFlex CSI
→ PowerFlex Volume
→ SDC / scini
→ Kubernetes Node
```

> 현재 9/2 Source of Truth의 실행 범위는 Snapshotter·NetApp Trident·Backend·StorageClass이고 PowerFlex는 확정 실행 범위가 아닙니다. 따라서 **현재 신규 Member가 PowerFlex 미적용이면 아래 원본 절차는 전부 설명하되 변경 명령은 실행하지 않습니다.**
>
> 적용 여부 때문에 원본 `4-2-1 → 4-2-2 → PowerFlex StorageClass` 순서를 줄이지 않습니다. 또한 원본의 MDM IP·SDC Version·endpoint·systemID·Storage Pool·Credential을 현재 실행값으로 사용하지 않습니다.

## 4.1. 원본 4-2-1 — Kubernetes Node에 SDC를 준비한다

> **SDC는 실제 PowerFlex Volume을 사용할 Node의 Data Client입니다.** CSI가 Kubernetes 요청을 처리해도 Node에 SDC Data Path가 없으면 그 Block Volume을 실제 Node에서 사용할 수 없습니다.

원본은 먼저 핵심 두 명령을 제시합니다.

```bash
ansible k8s -i inventory -m copy \
  -a "src=/app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/EMC-sdc-v3.6/EMC-ScaleIO-sdc-<현재-승인-SDC-Version>.rpm dest=/app/dspaas/EMC-ScaleIO-sdc-<현재-승인-SDC-Version>.rpm mode=755"
```

```bash
ansible k8s -i inventory -m shell \
```

# 5. 원본 4-3 — PVC를 실제 NetApp Storage까지 연결한다

> **Trident를 한 줄로 말하면 “Kubernetes의 PVC 요청을 실제 NetApp Storage 작업으로 연결하는 CSI Storage Orchestrator”입니다.**
>
> Kubernetes는 NetApp의 SVM·Management LIF·Data LIF를 직접 알지 못합니다. 먼저 Trident를 Kubernetes에 설치하고, Backend로 **실제로 어느 NetApp Storage를 사용할지** 연결한 뒤, StorageClass를 만들어 Application이 그 경로를 PVC에서 선택할 수 있게 합니다.
>
> 따라서 `Trident Pod가 Running`이 목표가 아닙니다. **Trident 실행 구성요소 → 실제 NetApp Backend → StorageClass**가 이어져야 오전 공급 경로가 완성됩니다.

```text
PVC
→ StorageClass
→ Trident CSI
→ Backend
→ 실제 NetApp Storage
→ PV
→ Node Mount
```

원본은 `4-3-1 Download Installation Files → 4-3-2 Namespace/CRD → 4-3-3 Operator → 4-3-4 Backend → 4-3-5 StorageClass` 순서입니다. 아래에서도 그 순서를 그대로 유지합니다.

> 같은 조회가 반복돼도 원본 순서입니다. CR 적용 후에도 TridentOrchestrator CRD가 정상 등록 상태인지 다시 확인합니다.

### 원본 4-3-2 완료 범위

> **Kubernetes가 TridentOrchestrator를 이해하고 실제 Trident 설치 요청을 받을 기반이 준비됐습니다.** 아직 Operator와 CSI Component의 실제 Running 상태는 다음 단계에서 확인합니다.

## 5.3. 원본 4-3-3 — 실제 Trident Operator와 CSI 구성요소를 올린다

> **여기서 실제 Trident 실행 구성요소가 Kubernetes에 올라옵니다.**
>
> Operator는 Trident 설치와 구성을 관리하고, Trident Controller는 PVC 요청에 따른 Volume Provisioning을 처리하며, Node Plugin은 Pod가 배치된 Node에서 실제 Volume Mount 경로에 참여합니다.
>
> 따라서 **Operator 하나 Running = Trident 완료**가 아닙니다.

```text
Operator
→ Trident Controller
→ Node Plugin
```

원본은 먼저 Operator Bundle 적용 명령을 제시합니다.

```bash
kubectl apply -f deploy/bundle.yaml
```

그다음 Bundle Manifest를 확인합니다.

```bash
cat deploy/bundle.yaml
```

> 원본 Bundle에는 ServiceAccount, 권한, Operator Deployment와 Image/NodeSelector/Toleration 등이 포함돼 있습니다. 현재 Bundle에서는 실제 Kubernetes Version에 맞는 Resource API와 Registry·배치 정책을 확인합니다.

다시 원본 순서대로 Bundle을 적용합니다.

```bash
kubectl apply -f deploy/bundle.yaml
```

> 이 두 번째 `apply`도 원본의 독립된 행위입니다.

먼저 Operator Pod가 Infra Node에 배치됐는지 확인합니다.

```bash
kubectl get pods -n trident -o wide | grep trident-operator
```

> `Running/Ready`뿐 아니라 실제 NODE가 승인된 Infra 배치 정책과 맞는지 봅니다.

원본은 잠시 뒤 전체 Trident Pod를 다시 확인합니다.

```bash
kubectl get pods -n trident
```

> 여기서 Trident Controller Pod와 Node Plugin Pod가 준비되는지 확인합니다. Controller가 기대 Container 수로 Ready인지, Node Plugin이 필요한 Node에 수렴했는지, Pending·ImagePullBackOff·CrashLoopBackOff가 없는지 봅니다.

### 원본 4-3-3 완료 범위

> **Trident CSI 실행 구성요소가 Kubernetes에 준비됐습니다.** 하지만 아직 Trident가 실제 어느 NetApp Storage를 사용할지는 연결하지 않았습니다. 그 연결이 다음 Backend입니다.

## 5.4. 원본 4-3-4 — Trident에게 실제 어느 NetApp Storage를 사용할지 연결한다

> **Backend를 한 줄로 말하면 “Trident에게 실제 어느 NetApp Storage를 사용할지 알려주는 연결 정보”입니다.**
>
> Trident Pod가 모두 정상이어도 Backend가 없으면 어느 SVM과 Storage를 관리해야 하는지 모릅니다.
>
> 여기서 특히 두 LIF를 구분합니다.

```text
Management LIF
→ Trident가 NetApp Storage를 관리하는 경로

Data LIF
→ Kubernetes Node가 실제 NFS Volume을 Mount할 때 사용하는 Data 경로
```

> 따라서 Backend `online`은 **Trident가 Storage 관리 경로와 통신한다는 증거**이지, 오후 Node NFS Mount까지 성공했다는 증거는 아닙니다.

```bash

```

```bash

```

> 원본은 Qtree용 `ontap-nas-economy`와 일반 `ontap-nas` 두 경로를 모두 설명합니다. **현재 신규 Member에서는 승인된 Backend 방식만 실제 실행**하고 다른 경로도 원본 순서대로 교육합니다. 현재 Source of Truth의 StorageClass는 `scs-netapp-qtree-nfs-sc-delete`이므로 Qtree 경로를 우선 대조하되 live Backend와 승인 Storage 설계로 최종 확정합니다.

## 5.5. 원본 4-3-5 — 사용자가 PVC에서 선택할 StorageClass를 만든다

> **Backend까지 연결했으면 이제 사용자가 그 Storage 공급 경로를 PVC에서 선택할 이름과 정책을 노출합니다. 그게 StorageClass입니다.**
>
> Application은 Backend 이름을 직접 지정하지 않습니다. PVC는 StorageClass를 선택하고, StorageClass가 Trident Provisioner와 Backend/Pool 정책을 연결합니다.

```text
PVC
→ StorageClass
→ Trident
→ Backend
→ NetApp Storage
```

> 현재 Source of Truth의 승인 StorageClass 기준은 `scs-netapp-qtree-nfs-sc-delete`입니다. 원본 Resource 이름의 대소문자와 과거 Backend/Pool 값은 현재 정답으로 사용하지 않고 live/승인 Manifest를 우선합니다.

# 6. 오전 완료 범위를 한 번에 정리한다

> 오늘 오전의 핵심을 다시 한 줄로 말하면 **“Kubernetes가 Storage 요청을 받을 공급 경로를 준비했다”**입니다.

```text
4-0
작업 대상 Cluster와 Storage 기준 고정

4-1
Snapshot 요청을 이해·관리할 CRD / Controller 기반 준비

4-2
PowerFlex 적용 환경이라면 SDC / CSI / StorageClass 경로 준비
현재 신규 Member 미적용이면 전체 절차 설명 후 실제 변경 제외

4-3
Trident 설치
→ 실제 NetApp Backend 연결
→ StorageClass 준비
```

> 현재 9/2 신규 Member 실행 범위에서 오전 완료 기준은 **External Snapshotter 준비 + Trident 실행 구성요소 정상 + 승인 NetApp Backend online + 승인 StorageClass 준비**입니다.
>
> 하지만 `StorageClass 존재`와 `Storage 기능 정상`은 같은 뜻이 아닙니다.

```text
StorageClass 존재
≠ Backend online

Backend online
≠ PVC Bound

PVC Bound
≠ Pod Mount

Pod Mount
≠ Container Write / Read 성공
```

# 7. 문제가 생기면 원본에서 처음 실패한 단계로 돌아간다

> 뒤 단계의 성공으로 앞 단계 실패를 덮지 않습니다.
>
> `4-1`에서 Snapshot CRD가 없으면 Trident Backend부터 만지지 않습니다. 첫 `apply`, Manifest 목록, Replica, 두 번째 `apply`, CRD/RBAC/Pod 순서에서 처음 틀어진 곳을 찾습니다.
>
> PowerFlex 적용 환경에서 SDC나 `scini`가 정상하지 않으면 CSI Installer Warning을 무시하고 계속 진행하지 않습니다. `4-2-1`의 RPM·MDM·GUID·`scini`부터 확인합니다.
>
> Trident `4-3-2`에서 Namespace나 TridentOrchestrator CRD/CR이 정상하지 않으면 Operator 단계로 넘어가지 않습니다.
>
> Operator는 Running인데 Controller나 Node Plugin이 준비되지 않으면 Backend JSON을 먼저 수정하지 않습니다. `4-3-3`의 Operator/CSI Pod 상태와 Image·RBAC·Scheduling을 먼저 봅니다.
>
> Backend가 `offline`이면 StorageClass를 새로 만들기보다 Management LIF·SVM·Credential Source·Network·Backend JSON을 먼저 확인합니다.
>
> StorageClass가 잘못된 Provisioner나 과거 Backend/Pool을 가리키면 오후 Test PVC로 넘어가지 않습니다.

# 9. 마무리

> 오늘 오전에는 Storage를 실제로 사용한 것이 아니라 **Storage 요청이 실제 Storage까지 갈 수 있는 공급 경로를 원본 순서대로 준비**했습니다.
>
> 먼저 어느 Cluster와 Storage를 대상으로 하는지 고정했습니다. 그다음 Snapshot 요청을 Kubernetes가 이해하고 관리할 기반을 준비했습니다. PowerFlex는 현재 적용 여부와 실제 실행을 구분하되 원본 SDC·CSI·StorageClass 절차를 전부 설명했습니다. 그리고 현재 신규 Member의 실제 경로인 Trident는 설치 구성요소를 준비하고 Backend로 실제 NetApp Storage를 연결한 뒤 StorageClass까지 만들었습니다.
>
> **오전 성공의 의미는 “PVC 요청을 받을 준비가 됐다”입니다. 실제 Storage 기능 성공은 오후에 PVC Bound, PV, Node Mount, Container Write/Read까지 확인해야 합니다.**
