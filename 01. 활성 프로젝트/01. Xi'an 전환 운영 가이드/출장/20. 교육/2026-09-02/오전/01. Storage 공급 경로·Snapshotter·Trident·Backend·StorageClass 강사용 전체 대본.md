# Storage 공급 경로·Snapshotter·Trident·Backend·StorageClass 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 9월 1일 `KUBERNETES BASE PASS`를 입력으로 받아 **Kubernetes의 PVC 요청이 실제 NetApp Storage 공급 경로까지 이어질 준비가 됐는지 판단하는 법**을 가르친다. Snapshotter·Trident·Backend·StorageClass의 정확한 설치 Manifest와 변경 명령은 Storage Runbook에서 수행한다. 여기서는 **구성요소가 존재하는 것과 공급 경로가 실제로 준비된 것을 구분하고, 오후 PVC·Mount·Write/Read 검증을 시작해도 되는지 판정하는 것**이 목적이다.

## 0. 9월 1일에서 이어받는 것

```text
Cluster Name·Stage·Context
KUBERNETES BASE PASS / BLOCKED
API·Node·Control Plane 정상 증거
External ETCD 기본 상태
Node별 Runtime 기준
Pod CIDR·CNI·Cluster DNS 실제 기능
Ingress·VIP-B 기본 경로
Storage 작업에서 사용할 Node Role·Network 전제
미해결 Event·외부 확인 항목
```

> `BLOCKED`라면 Storage 설치를 시작하지 않습니다. Kubernetes 기반 문제 위에 Storage 오류를 겹치지 않습니다.

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> Snapshotter, Trident Controller·Node Plugin, Backend와 StorageClass를 하나의 공급 경로로 설명하고, **각 구성요소의 존재가 어디까지를 증명하며 무엇은 아직 증명하지 못하는지** 구분해 오후 실제 사용 검증 진입 여부를 판단할 수 있어야 한다.

오늘의 중심 질문:

> **Kubernetes가 PVC를 요청했을 때 승인된 Storage 정책과 실제 NetApp Backend를 통해 Volume을 공급할 준비가 됐는가?**

---

# 1. 시작 — StorageClass가 보인다고 Storage가 준비된 것은 아니다

> 어제까지 Kubernetes 자체가 Pod를 실행하고 Network와 DNS를 사용하는 기반을 확인했습니다.
>
> 오늘은 Pod가 데이터를 저장할 공간을 요청했을 때 그 요청을 실제 Storage로 연결하는 경로를 만듭니다.

전체 공급 경로를 먼저 본다.

```text
Snapshot API·Controller
→ CSI Snapshot 기능의 선행 API

Trident Operator·Controller
→ Kubernetes PVC 요청을 NetApp Storage 작업으로 연결

Trident Node Plugin
→ 각 Node에서 Volume Attach·Mount 경로에 참여

Backend
→ Trident가 실제 NetApp SVM·Data LIF·정책과 연결되는 대상

StorageClass
→ 사용자가 PVC에서 선택하는 Storage 공급 정책
```

그리고 오후에야 다음이 이어진다.

```text
PVC
→ PV
→ Pod Mount
→ Write·Read
```

> 오전은 **Storage를 공급할 준비**를 닫는 시간이고, 오후는 **실제로 소비할 수 있는지**를 증명하는 시간입니다.

---

# 2. 먼저 현재 Member와 Storage 실제값 Source를 고정한다

```text
current-context: _________________________________________
Cluster Name·Stage: _____________________________________
KUBERNETES BASE PASS 증거: ______________________________
Storage 담당자·승인 근거: _______________________________
승인 StorageClass 이름: _________________________________
승인 Trident Version·Bundle: _____________________________
승인 Backend Name: ______________________________________
승인 SVM: ________________________________________________
승인 Data LIF: ___________________________________________
승인 Driver·Protocol: ____________________________________
9/3 Monitoring 대상 Node Role: ___________________________
```

> Credential·Password·Secret Data는 기록하지 않습니다. Backend 연결에 필요한 값은 승인된 관리체계와 Runbook에서 사용하고 교육 문서에는 구조와 판정만 남깁니다.

## 2.1 과거 Xi'an 값은 구조 비교 자료다

```text
기존 Backend 이름이 보임
≠ 신규 Member Backend

기존 StorageClass가 동작함
≠ 신규 Member에서 승인된 정책
```

> 이름이 같더라도 승인 근거와 현재 Backend 연결을 다시 확인합니다.

---

# 3. Snapshotter — Trident와 다른 선행 기능이다

> CSI Snapshotter는 Volume Snapshot API와 Controller 역할을 제공합니다. Trident와 함께 Storage 기능에서 사용될 수 있지만 같은 Component가 아닙니다.

구분:

```text
Snapshot CRD 존재
≠ Snapshot Controller 정상

Controller Running
≠ Trident Backend 정상
```

확인할 최소 질문:

```text
현재 Bundle이 요구하는 Snapshot CRD가 있는가
API에서 CRD가 Established 상태인가
Controller가 승인 Namespace·Replica로 정상인가
반복 Restart·ImagePull·권한 오류가 없는가
```

정확한 CRD·Controller 설치는 Storage Runbook을 따른다.

## 3.1 CRD Apply 성공과 API 사용 가능을 분리한다

```text
kubectl apply 성공
≠ CRD Established
```

> `Established=True`까지 확인해야 Kubernetes API가 해당 Resource Kind를 안정적으로 사용할 준비가 됐다고 판단합니다.

---

# 4. Trident — Controller와 Node 경로를 분리한다

> Trident는 Kubernetes CSI 요청과 NetApp Storage를 연결합니다. 하나의 Pod만 보는 것이 아니라 Controller 역할과 Node 역할을 구분해야 합니다.

```text
Operator
→ Trident 설치·구성 관리

Controller
→ Provisioning 등 Cluster 단위 Storage 작업

Node Plugin
→ Pod가 배치된 Node의 Mount 경로 참여
```

## 4.1 Controller 정상과 전체 Node 정상은 다르다

```text
Trident Controller Running
≠ 모든 대상 Node Plugin 정상
```

확인할 최소 범위:

```text
Operator 상태
Controller Ready·Restart
Node DaemonSet Desired·Ready·Available
대상 Kubernetes Node 누락 여부
9/3 Monitoring이 배치될 Infra Node에 Node Plugin 존재
Critical Event 없음
```

> Worker에서만 Node Plugin이 정상이라고 9월 3일 Monitoring용 Infra Node Mount 경로까지 성공한 것으로 보지 않습니다.

## 4.2 Image와 권한 실패는 Event에서 먼저 분리한다

| 증상 | 첫 확인 |
|---|---|
| ImagePullBackOff | Image 주소·Registry·Tag·CA·Secret |
| Pending | Label·Taint·Resource·Scheduler Event |
| CrashLoopBackOff | Container Log·Config·권한 |
| 특정 Node Plugin 누락 | Node Selector·Taint·DaemonSet 대상 조건 |

> Storage 문제라는 큰 이름으로 묶기 전에 현재 Component가 어느 단계에서 시작되지 못했는지 봅니다.

---

# 5. Backend — `online`은 실제 Storage 연결의 중요한 중간 증거다

> Trident Controller가 떠 있어도 어떤 NetApp Storage를 사용할지 연결되지 않으면 PVC를 실제 Volume으로 공급할 수 없습니다.

Backend는 다음 역할을 한다.

```text
Trident
→ Backend
→ 승인 SVM·Management/Data LIF·Storage 정책
→ 실제 Volume 공급
```

확인할 질문:

```text
현재 신규 Member용 Backend인가
Backend state가 online인가
승인 SVM과 Data LIF를 가리키는가
승인 Driver·Protocol과 맞는가
Credential이 승인된 관리 경로를 사용하는가
```

정확한 Backend 생성·Credential 입력은 Storage Runbook을 따른다.

## 5.1 `online`의 증거 범위

```text
Backend online
→ Trident와 Backend의 기본 관리 연결이 성립
```

하지만:

```text
Backend online
≠ StorageClass 정책 정상
≠ PVC Provisioning 성공
≠ Pod Node에서 NFS Mount 가능
≠ Container Write·Read 가능
```

> `online`을 오후 전체 Storage 성공으로 확대하지 않습니다.

## 5.2 Backend가 offline이면 오후로 넘어가지 않는다

첫 확인 범위:

```text
Backend 대상 SVM·LIF
Network 접근
승인 Credential 경로
Driver·Protocol
Trident Log·Backend 오류
```

> Pod를 만들어 실패를 더 쌓지 않습니다. 공급 경로가 아직 성립하지 않은 상태입니다.

---

# 6. StorageClass — 사용자가 선택할 정책을 실제 Backend와 연결한다

> StorageClass는 Storage 자체가 아니라 PVC가 어떤 공급 방식을 사용할지 정하는 Kubernetes 정책 객체입니다.

확인할 핵심값:

```text
이름
provisioner
Backend·Driver와 연결되는 parameter
reclaimPolicy
volumeBindingMode
allowVolumeExpansion 등 현재 정책
```

정확한 값은 현재 승인 설계와 Storage Runbook을 따른다.

## 6.1 존재와 정책 정상은 다르다

```text
StorageClass 존재
≠ 승인 Provisioner

기본 StorageClass 표시
≠ 이번 Monitoring·Application이 사용해야 할 정책

이름이 기존 Cluster와 같음
≠ 현재 Backend와 같은 정책
```

> YAML이 문법상 맞다는 것보다 **9월 3일 Monitoring이 실제로 이 StorageClass를 사용해도 되는가**가 중요합니다.

## 6.2 reclaimPolicy는 정리 동작과 연결된다

> 오후 Test PVC 삭제 후 PV와 Backend Volume이 어떻게 정리되는지는 StorageClass의 `reclaimPolicy`와 연결됩니다.

따라서 오전에 정책 의미를 알고 오후 Cleanup에서 실제 결과를 확인한다.

```text
reclaimPolicy 값 확인
≠ 실제 Cleanup 동작 검증 완료
```

---

# 7. 공급 경로를 한 장으로 연결한다

이제 구성요소를 따로 보지 않고 한 경로로 읽는다.

```text
Kubernetes API
→ Snapshot 선행 API 준비
→ Trident Controller
→ Trident Node Plugin
→ 승인 Backend online
→ 승인 StorageClass
→ 오후 PVC 요청을 받을 준비
```

대조표:

```text
단계 | 기대 대상 | 실제 상태 | 증거 | 판정
Snapshot CRD | | | |
Snapshot Controller | | | |
Trident Operator | | | |
Trident Controller | | | |
Trident Node Plugin 전체 | | | |
Infra Node Plugin | | | |
Backend | | | |
StorageClass | | | |
```

> 각 행이 초록색처럼 보이는 것이 아니라 **같은 신규 Member와 같은 승인 Storage 설계**를 가리켜야 합니다.

---

# 8. 오전에는 PVC를 성공 증거로 미리 만들지 않는다

> 오전의 목적은 공급 경로 준비입니다. 실제 PVC·PV·Pod Mount·Write/Read는 오후 대본에서 하나의 통제된 Test Scenario로 수행합니다.

이렇게 분리하는 이유:

```text
공급 구성 오류
vs
PVC Provisioning 오류
vs
Node Mount 오류
vs
Container 사용 오류
```

를 섞지 않기 위해서다.

> 오전 Component가 불완전한데 Test PVC부터 만들면 Pending과 Event가 추가되어 어디가 원래 첫 실패인지 흐려질 수 있습니다.

---

# 9. STORAGE SUPPLY PASS를 판정한다

오전 종료는 두 상태만 사용한다.

## 9.1 STORAGE SUPPLY PASS

```text
KUBERNETES BASE PASS
+ 필요한 Snapshot CRD Established
+ Snapshot Controller 정상
+ Trident Operator·Controller 정상
+ Trident Node Plugin이 필요한 전체 Kubernetes Node에서 정상
+ 9/3 대상 Infra Node의 Node Plugin 정상
+ 승인 Backend online·현재 Member 실제값과 일치
+ 승인 StorageClass의 provisioner·정책 일치
+ Credential 원문 노출 없음
+ Critical Event 없음
```

> 이 판정은 **PVC Test를 시작할 공급 경로가 준비됐다**는 뜻입니다.

아직 증명하지 않은 것:

```text
PVC Bound
PV 생성
Node Mount
NFS 접근
Write·Read
Cleanup
```

## 9.2 BLOCKED

```text
KUBERNETES BASE가 BLOCKED
Snapshot 필수 CRD·Controller 비정상
Trident Controller 비정상
필요 Node의 Trident Plugin 누락·비정상
Backend offline 또는 실제 연결 대상 미확정
StorageClass 실제값·정책 미확정
9/3 Infra Node Storage 경로 선행조건 미확정
Critical Event 원인 미확정
```

> 오후 Test PVC로 확인해 보자는 이유로 BLOCKED를 넘기지 않습니다.

---

# 10. 오후 실제 사용 검증으로 넘길 것

```text
Cluster Name·Stage·Context
STORAGE SUPPLY PASS / BLOCKED
Snapshot CRD·Controller 상태
Trident Operator·Controller 상태
Node Plugin 대상·Ready 결과
Backend Name·State·SVM·Data LIF의 비민감 확인 정보
승인 StorageClass 이름·Provisioner·reclaimPolicy·volumeBindingMode
9/3 Monitoring 대상 Node Role
Test PVC에 사용할 Namespace·용량 승인 기준
Test Pod 배치 대상·정리 계획
미해결 항목·담당자
```

> 오후에는 이 공급 경로를 전제로 **PVC → PV → Pod Mount → Write·Read → Cleanup**을 실제로 검증합니다.

---

# 11. 마무리 — 오전 Storage를 한 문장으로 다시 말한다

> Storage는 StorageClass 하나를 만드는 일이 아닙니다.
>
> Kubernetes의 Storage API가 준비되고, Trident Controller와 Node Plugin이 역할을 수행하며, Trident가 현재 신규 Member의 실제 NetApp Backend에 연결되고, 사용자가 선택할 승인 StorageClass가 그 공급 경로를 표현해야 합니다.
>
> **결국 오전의 성공은 Storage 객체가 많이 보이는 상태가 아니라, 오후 PVC 요청이 실제 승인 Backend로 갈 수 있는 공급 경로가 같은 신규 Member에서 증거로 연결된 상태입니다.**
