# Storage 공급 경로·Snapshotter·Trident·Backend·StorageClass 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 9월 1일에는 Kubernetes의 실제 실행·통신 경로를 확인했다. 이번 블록은 **PVC 요청을 NetApp Storage로 전달할 Trident·Backend·StorageClass를 준비하는 과정**이다.
>
> Snapshotter는 기본 PVC Provisioning의 필수 원인이 아니라 현재 Xi'an Bundle이 함께 요구하는 별도 기능으로 구분한다. Manifest·Backend·StorageClass 적용은 승인된 Storage Runbook을 따르고 Credential·Secret 원문은 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
Kubernetes가 Pod를 실행할 수 있다
→ 하지만 Pod가 사라져도 남을 데이터 공간은 별도다
→ 그래서 PVC 요청을 Storage 동작으로 바꿀 CSI가 필요하다
→ Xi'an에서는 Trident가 그 역할을 한다
→ Backend가 실제 NetApp Storage를 지정한다
→ StorageClass가 사용자가 선택할 공급 정책을 제공한다
→ 실제 요청은 PVC → StorageClass → Trident → Backend → PV로 흐른다
→ 현재 Bundle이 요구하는 Snapshot 기능도 별도로 확인한다
→ 공급 준비가 끝나면 오후에 실제 PVC·Mount를 시험한다
```

## 0-1. 오늘 전체 한 줄

> 오전에는 PVC를 바로 만들지 않습니다. **Trident·Backend·StorageClass를 연결해 Storage 요청을 처리할 준비가 됐는지 확인하는 시간**입니다.

---

# 1. 시작 — Pod가 실행돼도 데이터가 남는 것은 아니다

> 어제 Test Pod가 실행되고 Service·DNS·Ingress를 사용할 수 있는 것을 확인했습니다.
>
> **하지만 Pod 안에만 저장한 데이터는 Pod가 다시 만들어질 때 사라질 수 있습니다.** Prometheus Metric이나 Application 데이터는 Pod 수명과 분리된 공간이 필요합니다.
>
> Kubernetes 사용자는 Storage Array에 직접 Volume 생성 명령을 보내지 않습니다. PVC로 필요한 용량과 정책을 요청합니다.
>
> 그래서 그 요청을 실제 Storage 작업으로 바꾸는 CSI가 필요합니다. Xi'an에서는 NetApp Trident가 이 역할을 담당합니다.

---

# 2. Snapshotter — 기본 Provisioning과 별도로 본다

> 현재 Xi'an Storage Bundle에는 Volume Snapshot 관련 CRD와 Controller가 포함될 수 있습니다.
>
> Snapshotter는 이미 사용 중인 Volume의 특정 시점을 Snapshot으로 관리하기 위한 Kubernetes 확장 기능입니다. 그래서 PVC를 처음 만들고 Volume을 공급하는 기본 Provisioning 경로와 Snapshot 요청을 처리하는 경로를 구분해서 봐야 합니다.
>
> **하지만 기본 PVC를 Provisioning하기 위해 Snapshotter가 반드시 필요한 것은 아닙니다.** 기본 공급 경로의 중심은 실제 Storage를 연결하는 CSI·Backend·StorageClass이고, Snapshotter는 그 위에서 Snapshot 기능을 사용할 수 있도록 API와 Control Loop를 준비합니다.

## 2-1. VolumeSnapshot 관련 CRD 3종의 역할을 먼저 구분한다

> 먼저 Kubernetes가 Snapshot 요청을 객체로 이해하려면 Snapshot API Resource가 필요합니다.
>
> Cluster Setup에서는 `VolumeSnapshotClass`, `VolumeSnapshotContent`, `VolumeSnapshot` 세 종류의 CRD를 설치합니다.
>
> `VolumeSnapshotClass`는 어떤 CSI Driver와 정책으로 Snapshot을 처리할지 정의합니다. StorageClass가 Volume 공급 정책을 표현한다면, VolumeSnapshotClass는 Snapshot 요청에 사용할 Driver와 Snapshot 정책을 표현합니다.
>
> `VolumeSnapshot`은 Namespace 안에서 사용자가 특정 PVC의 Snapshot을 요청하는 객체입니다.
>
> 그다음 `VolumeSnapshotContent`는 실제 Snapshot과 Kubernetes의 Snapshot 요청을 연결하는 Cluster 범위 객체입니다.
>
> 그래서 세 CRD 중 하나만 존재하는 것으로 Snapshot API가 준비됐다고 판단하지 않습니다. 현재 Bundle이 요구하는 CRD가 모두 등록되고 Kubernetes API에서 정상적으로 제공되는지 확인해야 합니다.

## 2-2. CRD Apply와 실제 API 사용 가능을 구분한다

> Manifest를 Apply했다는 것은 Kubernetes API Server에 CRD 등록을 요청했다는 의미입니다.
>
> 하지만 Apply 명령이 성공했다고 바로 Snapshot Resource를 안정적으로 사용할 수 있다는 뜻은 아닙니다.
>
> CRD가 실제로 등록되고 `Established` 상태가 된 뒤에야 Kubernetes가 해당 Resource Kind를 정상적으로 제공할 준비가 됐다고 볼 수 있습니다.
>
> 따라서 Snapshotter 구성에서는 파일이 존재하는지보다 현재 Cluster의 CRD 상태를 확인합니다. 기존 Cluster에서 사용한 CRD Version을 그대로 가정하지 않고 현재 Bundle과 Kubernetes Version에 맞는 Resource가 등록됐는지도 같이 봅니다.

## 2-3. Snapshot Controller는 Snapshot 요청의 Control Loop를 담당한다

> CRD가 Snapshot 객체의 형태를 정의했다면 그다음 실제 Snapshot 요청 상태를 계속 확인하고 처리할 Controller가 필요합니다.
>
> Cluster Setup의 Snapshot Controller는 Kubernetes에서 생성되는 Snapshot Resource를 감시하고 CSI Snapshot 동작이 이어질 수 있도록 Control Loop를 수행합니다.
>
> 그래서 CRD만 정상이어도 Controller가 없거나 정상적으로 동작하지 않으면 Snapshot 요청은 처리되지 않습니다.
>
> 반대로 Snapshot Controller Pod가 Running이어도 CRD가 잘못됐거나 필요한 권한이 없으면 Snapshot Resource를 정상적으로 처리할 수 없습니다.
>
> 따라서 Controller Pod 하나의 상태만 보는 것이 아니라 ServiceAccount, Role·RoleBinding, ClusterRole·ClusterRoleBinding과 Controller Deployment가 같이 준비됐는지 봅니다.

## 2-4. Replica와 배치 위치도 현재 Cluster 기준으로 본다

> Cluster Setup에서는 Snapshot Controller Replica 수를 Kubernetes Cluster의 Infra Node 수와 연결해서 확인하는 절차가 있습니다.
>
> 그래서 Manifest에 `replicas` 값이 들어 있다는 사실만 보지 않고, 현재 신규 Member의 Infra 구성과 배치 정책에 맞는지 확인해야 합니다.
>
> 그다음 실제 Controller Pod가 어느 Node에서 실행되는지 보고, 승인된 Role에 배치됐는지 확인합니다.
>
> Controller가 모두 Running이어도 특정 Pod가 반복 Restart 중이거나 Image Pull·권한·Scheduling 문제가 남아 있으면 정상 상태로 넘기지 않습니다.
>
> 따라서 Replica 수, Ready 상태, 실제 Node 배치, Restart와 Event를 함께 봅니다. 과거 Cluster의 Pod 이름·Pod IP·Node 이름은 현재 신규 Member의 증거로 사용하지 않습니다.

## 2-5. Snapshotter와 CSI Driver의 책임을 구분한다

> Snapshotter가 준비되면 Kubernetes는 Snapshot API를 이해하고 Snapshot 요청을 제어할 수 있습니다.
>
> 하지만 실제 Storage에서 Snapshot을 생성할 수 있는지는 사용하는 CSI Driver와 Storage System의 Snapshot 지원까지 연결돼야 합니다.
>
> 그래서 Snapshot Controller가 정상이라고 PowerFlex나 Trident의 Storage 연결이 정상이라고 판단하지 않습니다.
>
> 반대로 Trident나 PowerFlex CSI가 정상적으로 Volume을 공급한다고 Snapshot 기능까지 자동으로 검증된 것도 아닙니다.
>
> 따라서 오늘 오전에는 현재 Bundle이 요구하는 Snapshot CRD와 Controller가 준비됐는지 확인하고, 실제 Storage 공급 경로는 PowerFlex와 Trident 단계에서 별도로 확인합니다.

## 2-6. 오전에는 Snapshot 생성 자체를 성공 기준으로 사용하지 않는다

> 이번 블록의 목적은 오후 PVC 사용 검증을 시작할 Storage 공급 기반을 준비하는 것입니다.
>
> 그래서 Snapshot 기능을 설명한다고 오전에 운영 PVC나 임의의 Test PVC를 대상으로 Snapshot 생성 시험부터 수행하지 않습니다.
>
> 먼저 CRD, RBAC, Controller, Replica와 배치 상태가 현재 Bundle 기준으로 준비됐는지 확인합니다.
>
> 그리고 실제 Snapshot 생성·복구가 별도 검증 범위로 승인된 경우에는 사용하는 CSI Driver와 Storage 정책을 확인한 뒤 별도 Test Scenario로 수행합니다.
>
> **결국 오전 Snapshotter 확인은 Snapshot 객체가 실제로 하나 생성됐다는 것을 증명하는 시간이 아니라, 현재 Cluster가 승인된 CSI Snapshot 기능을 처리할 API와 Controller 기반을 갖췄는지 확인하는 시간입니다.**

# 3. PowerFlex — Block Storage 공급 경로를 이해한다

> Cluster Setup의 Storage Component 구성에는 NetApp Trident뿐 아니라 PowerFlex 구성도 포함되어 있습니다.
>
> PowerFlex는 Kubernetes에 Persistent Storage를 제공한다는 목적은 같지만 NetApp NFS와 실제 Storage가 Node까지 연결되는 방식은 다릅니다. PowerFlex에서는 Kubernetes의 요청을 CSI Driver가 받아 PowerFlex Volume 작업으로 연결하고, Volume을 사용하는 Node에서는 SDC가 Block Data Path에 참여합니다.
>
> 그래서 PowerFlex는 CSI Driver 하나만 보는 것이 아니라 PowerFlex System, MDM, SDC, CSI Driver와 StorageClass가 같은 Storage 환경을 가리키는지 함께 이해해야 합니다.

## 3-1. SDC·SDS·MDM의 역할을 먼저 구분한다

> 먼저 PowerFlex를 구성하는 기본 역할을 구분합니다.
>
> SDC는 Storage Data Client입니다. PowerFlex Volume을 사용하는 Server에 설치되고, PowerFlex가 제공한 Volume을 해당 Server에서 Block Device로 사용할 수 있도록 연결합니다.
>
> SDS는 Storage Data Server입니다. PowerFlex System에 Storage Capacity를 제공하는 역할입니다. Kubernetes Node에서 Volume을 사용하는 SDC와는 역할이 다릅니다.
>
> MDM은 Metadata Manager입니다. PowerFlex System의 Resource와 구성을 관리하고 SDC가 연결할 Storage System 정보를 제공합니다.
>
> 따라서 Kubernetes Cluster에서 PowerFlex를 사용할 때는 대상 Node의 SDC가 올바른 PowerFlex System과 연결돼 있어야 하고, 그 위에서 CSI Driver가 Kubernetes의 Storage 요청을 처리해야 합니다.

## 3-2. SDC는 Node의 실제 Block Data Path를 준비한다

> Cluster Setup에서는 PowerFlex를 사용하는 경우 Master, Infra, Router, Worker Node에 SDC를 설치하는 구조를 사용합니다.
>
> 먼저 현재 PowerFlex Storage Pool과 호환되는 SDC Version을 확인합니다. SDC Package가 있다고 바로 설치하는 것이 아니라 현재 Storage 환경에서 승인된 Version인지 확인해야 합니다.
>
> 그다음 SDC가 연결할 MDM 정보를 사용해 Node를 PowerFlex System에 연결합니다. SDC가 설치되면 Node를 식별하는 GUID와 MDM 정보가 Driver Configuration에 반영됩니다.
>
> 그리고 `scini`가 정상적으로 기동하는지 확인합니다. RHEL 계열에서는 SELinux나 Kernel Driver 조건 때문에 Package 설치는 성공했지만 `scini`가 정상적으로 올라오지 않을 수도 있습니다.
>
> 따라서 SDC는 RPM 설치 여부만 보는 것이 아니라 `scini` 상태, Node별 GUID와 MDM 연결까지 같이 봐야 합니다.
>
> Node별 GUID는 서로 고유해야 하고, MDM은 현재 사용할 PowerFlex System을 가리켜야 합니다. 기존 Cluster에서 사용한 GUID나 MDM 값을 신규 Member의 실제값으로 그대로 사용하지 않습니다.

## 3-3. 그다음 PowerFlex CSI Driver가 Kubernetes 요청을 받는다

> Node의 Block Data Path가 준비되면 Kubernetes의 PVC 요청을 PowerFlex Volume 작업으로 바꿀 CSI Driver가 필요합니다.
>
> Cluster Setup에서는 PowerFlex CSI용 Namespace를 준비하고, PowerFlex 환경에 맞는 Configuration을 만든 뒤 Secret으로 연결하고, CSI Controller와 Node Component를 설치하는 구조를 사용합니다.
>
> CSI Configuration에는 어느 PowerFlex System을 사용할지 판단할 수 있도록 Endpoint, systemID, MDM과 Credential 정보가 필요합니다.
>
> 하지만 Endpoint, systemID와 MDM은 Cluster마다 달라질 수 있는 환경값입니다. 기존 Cluster Setup에 남아 있는 값을 신규 Member 값으로 복사하지 않고 현재 Storage 담당자가 승인한 실제값을 사용해야 합니다.
>
> Credential도 같은 기준입니다. CSI Driver가 사용할 Secret은 필요하지만 Password나 Secret Data 원문을 교육 문서와 검증 증적에 남기지 않습니다. Secret이 존재하고 올바른 Configuration Source를 사용한다는 범위까지만 확인합니다.

## 3-4. CSI Controller와 Node Component의 역할을 나눠서 본다

> PowerFlex CSI에는 Cluster 단위 Volume 작업을 처리하는 Controller와 실제 Kubernetes Node의 Volume 연결에 참여하는 Node Component가 있습니다.
>
> 먼저 Controller는 PVC 요청에 따라 PowerFlex Volume을 생성하거나 삭제하는 Provisioning 작업을 처리합니다.
>
> 그다음 Node Component는 Pod가 배치된 Node에서 Volume을 사용할 수 있도록 Node 쪽 연결 과정에 참여합니다.
>
> 그래서 Controller가 Running이어도 필요한 Node에 CSI Node Component가 없으면 실제 Volume 사용은 실패할 수 있습니다.
>
> 또한 CSI Node Component가 정상이어도 해당 Node의 SDC와 `scini`가 준비되지 않았다면 PowerFlex Block Data Path가 완성된 것은 아닙니다.
>
> 반대로 SDC가 정상이어도 CSI Controller·Node Component나 PowerFlex Configuration이 잘못돼 있으면 Kubernetes의 PVC 요청은 정상적으로 처리되지 않습니다.
>
> 따라서 PowerFlex에서는 CSI와 SDC를 같은 Component로 보지 않고, Kubernetes 요청 경로와 Node Data Path를 각각 담당하는 구성요소로 구분합니다.

## 3-5. StorageClass가 실제 PowerFlex System과 Storage Pool을 선택한다

> CSI Driver가 준비되면 사용자가 PVC에서 PowerFlex Storage를 선택할 수 있도록 StorageClass가 필요합니다.
>
> Cluster Setup의 PowerFlex StorageClass는 `csi-vxflexos.dellemc.com` Provisioner를 사용하고, 실제 Volume을 생성할 PowerFlex `systemID`와 `storagepool`을 Parameter로 연결하는 구조입니다.
>
> 그리고 Filesystem Type, `reclaimPolicy`, `volumeBindingMode`, `allowVolumeExpansion`과 Topology 조건도 StorageClass 정책에 포함될 수 있습니다.
>
> 그래서 StorageClass 이름이 존재하는지만 보지 않습니다. Provisioner가 PowerFlex CSI를 가리키는지, systemID와 Storage Pool이 CSI Configuration에서 사용하는 PowerFlex System과 같은지, Filesystem과 Reclaim·Binding 정책이 현재 승인 설계와 맞는지 확인해야 합니다.
>
> Cluster Setup 예시에서는 XFS, `Delete` Reclaim Policy, Volume Expansion과 `Immediate` Binding Mode를 사용하지만, 신규 Member에서는 예시값 자체보다 현재 승인된 StorageClass 정책을 기준으로 봅니다.

## 3-6. PowerFlex 공급 준비와 실제 사용 검증을 구분한다

> 여기까지 준비됐다고 바로 PowerFlex Storage 기능 전체가 검증된 것은 아닙니다.
>
> SDC와 `scini`가 정상이라는 것은 Node의 PowerFlex Data Path가 준비됐다는 의미이고, CSI Controller와 Node Component가 정상이라는 것은 Kubernetes가 PowerFlex Volume 작업을 수행할 구성요소가 준비됐다는 의미입니다.
>
> 그리고 CSI Configuration과 StorageClass가 현재 PowerFlex System·Storage Pool을 가리켜야 실제 PVC 요청을 받을 공급 정책이 완성됩니다.
>
> 하지만 실제 PVC가 Bound되는지, PowerFlex Volume이 생성되는지, Pod가 배치된 Node에서 Block Device와 Filesystem이 정상적으로 연결되는지, Container가 데이터를 쓰고 읽을 수 있는지는 실제 PVC·Pod 시험에서 별도로 확인해야 합니다.
>
> 따라서 오전에는 PowerFlex를 사용하는 환경이라면 실제 PVC 시험을 시작할 수 있는 공급 경로가 준비됐는지까지 구분하고, 실제 Provisioning·Mount·Write/Read는 오후 사용 검증 단계에서 확인합니다.

## 3-7. NetApp Trident와 확인 기준을 섞지 않는다

> PowerFlex와 NetApp Trident는 모두 Kubernetes Persistent Storage를 제공하지만 실제 Data Path는 다릅니다.
>
> PowerFlex에서는 SDC, `scini`, MDM, PowerFlex CSI와 Block Device 연결이 중요합니다.
>
> 반면 NetApp NFS에서는 Trident Backend, Data LIF, NFS Export와 Node의 NFS Mount 경로가 중요합니다.
>
> 그래서 Storage 문제가 발생하면 먼저 PVC가 사용하는 StorageClass와 Provisioner를 확인하고 PowerFlex 경로인지 NetApp 경로인지 구분해야 합니다. PowerFlex 문제를 Data LIF·NFS 2049·Export Policy 기준으로 확인하거나, NetApp NFS 문제를 SDC·MDM 기준으로 확인하지 않습니다.

## 3-8. 현재 신규 Member의 PowerFlex 적용 여부는 별도로 확인한다

> Cluster Setup에 PowerFlex 절차가 포함돼 있다는 이유만으로 현재 신규 Member에도 PowerFlex를 반드시 설치한다고 판단하지 않습니다.
>
> 먼저 현재 신규 Member의 승인 Storage 설계와 사용할 StorageClass를 확인합니다.
>
> PowerFlex 사용이 승인된 환경이라면 현재 Storage Pool과 호환되는 SDC Version, MDM, Endpoint, systemID, Storage Pool, CSI Version과 StorageClass 정책을 현재 환경값으로 확보해야 합니다.
>
> 반대로 현재 신규 Member가 NetApp Trident 경로만 사용한다면 과거 PowerFlex 환경값을 가져와 SDC나 CSI Driver를 신규 설치하지 않습니다.
>
> 따라서 이 시간에는 Cluster Setup에 포함된 PowerFlex의 구성 구조와 각 Component의 역할을 이해하고, 실제 적용 여부와 환경값은 현재 신규 Member의 승인 Storage 설계를 기준으로 판단합니다.
>
> 결국 PowerFlex는 CSI Pod 하나가 Running인 상태로 판단하지 않습니다. **Node의 SDC와 PowerFlex System 연결, CSI Controller·Node Component, CSI Configuration과 StorageClass가 같은 PowerFlex 환경으로 이어져 PVC 요청을 받을 준비가 됐는지를 하나의 공급 경로로 이해해야 합니다.**

# 4. Trident — PVC 요청을 NetApp 작업으로 바꾼다

> Trident는 Kubernetes의 CSI 요청을 NetApp Storage 작업으로 연결하는 Storage Orchestrator입니다.
>
> Kubernetes 사용자는 NetApp Storage에 직접 Volume을 만들지 않고 PVC와 StorageClass로 필요한 Storage를 요청합니다. Trident는 그 요청을 받아 현재 연결된 NetApp Backend의 실제 Volume 공급 작업으로 바꿉니다.
>
> 그래서 Trident를 확인할 때는 하나의 Pod만 보는 것이 아니라 설치를 관리하는 Operator, Cluster 단위 Storage 요청을 처리하는 Controller, 각 Node의 Mount 경로에 참여하는 Node Plugin과 실제 NetApp Storage를 지정하는 Backend의 역할을 구분해야 합니다.

## 4-1. 먼저 Trident Bundle과 설치 방식을 이해한다

> Cluster Setup에서는 승인된 SCS Kubernetes Stack 안의 Trident Bundle을 사용합니다.
>
> Bundle에는 Namespace와 CRD Manifest, TridentOrchestrator 설정, Operator 배포 Resource, 환경별 Configuration과 `tridentctl` 같은 관리 도구가 포함됩니다.
>
> 먼저 현재 신규 Member에서 사용할 Trident Version과 Bundle이 무엇인지 확인합니다. 디렉터리 이름이나 과거 Cluster의 설치 기록만 보고 현재 Version을 확정하지 않습니다.
>
> 그리고 Bundle 안의 Image Registry, Namespace, Node Selector와 Toleration 같은 환경 의존값이 현재 신규 Member 기준과 맞는지 확인합니다.
>
> 특히 Xi'an처럼 Private Registry를 사용하는 환경에서는 Manifest가 현재 승인된 Registry와 Image를 가리키는지가 중요합니다. Bundle은 있어도 Image 경로가 과거 환경을 가리키면 실제 Component는 정상적으로 기동하지 못할 수 있습니다.

## 4-2. Namespace와 TridentOrchestrator CRD가 설치 기반을 만든다

> 그다음 Trident가 자신의 설치 상태를 Kubernetes Resource로 관리할 수 있도록 Namespace와 `TridentOrchestrator` CRD를 준비합니다.
>
> Namespace는 Trident Operator와 CSI Component가 실행될 공간을 제공합니다.
>
> `TridentOrchestrator` CRD는 Kubernetes API가 Trident 설치 구성을 Custom Resource로 이해할 수 있게 합니다. 그리고 실제 `TridentOrchestrator` Resource에는 Trident가 어느 Namespace에 설치될지, 어떤 Registry를 사용할지, Controller를 어느 Role의 Node에 배치할지 같은 설치 정책이 들어갑니다.
>
> 그래서 CRD가 존재한다는 사실과 실제 Trident 설치 구성이 정상이라는 것은 같은 의미가 아닙니다. CRD가 등록된 뒤 현재 `TridentOrchestrator` Resource가 어떤 값을 사용하고 있는지도 확인해야 합니다.
>
> Cluster Setup에서는 Controller를 Infra Node에 배치하기 위한 Node Selector와 Toleration을 사용합니다. 따라서 현재 신규 Member에서도 실제 Infra Node Label과 Taint 정책이 TridentOrchestrator 설정과 맞는지 확인합니다.

## 4-3. Operator는 Trident CSI 구성요소의 설치와 상태를 관리한다

> Trident Operator는 `TridentOrchestrator` Resource를 읽고 필요한 Trident CSI 구성요소를 배포하고 관리합니다.
>
> 그래서 Operator 자체가 Running이라는 것은 설치를 관리할 Controller가 동작하고 있다는 의미입니다.
>
> 하지만 Operator Pod가 정상이라고 Trident CSI 전체가 준비됐다는 뜻은 아닙니다. Operator가 만든 Controller와 Node Plugin이 실제로 원하는 수만큼 기동하고 대상 Node에 배치돼야 합니다.
>
> Operator에는 Kubernetes Resource를 조회하고 생성하기 위한 ServiceAccount와 RBAC 권한도 필요합니다. 따라서 Pod가 뜨지 않거나 반복 Restart하면 Image뿐 아니라 ServiceAccount·권한·CR 상태와 Event를 같이 확인합니다.
>
> 그리고 기존 Cluster에서 이미 정상 설치된 Trident를 확인하는 경우에는 무조건 Manifest를 다시 Apply하지 않습니다. 먼저 현재 Resource와 Pod 상태를 확인하고 신규 구축이나 승인된 재구축일 때만 실제 변경 절차로 넘어갑니다.

## 4-4. Controller와 Node Plugin의 역할을 나눠서 본다

> Trident CSI에서는 Cluster 전체의 Storage 요청을 처리하는 Controller와 각 Kubernetes Node의 Volume 사용에 참여하는 Node Plugin의 역할이 나뉩니다.
>
> 먼저 Controller는 PVC 요청에 따라 Backend를 선택하고 Volume Provisioning·삭제 같은 Cluster 단위 Storage 작업을 처리합니다.
>
> 그다음 Node Plugin은 Pod가 배치된 Node에서 kubelet과 함께 실제 Volume Mount 경로에 참여합니다.
>
> 그래서 Controller가 Running이어도 Node Plugin이 없는 Node에서는 PVC가 이미 Bound됐더라도 Pod Mount 단계에서 실패할 수 있습니다.
>
> 반대로 Node Plugin이 모든 Node에서 Running이어도 Controller가 Backend와 정상적으로 연결되지 않으면 새로운 PVC를 실제 NetApp Volume으로 Provisioning할 수 없습니다.
>
> 따라서 Controller와 Node Plugin은 한쪽의 성공으로 다른 쪽을 대신하지 않습니다. Controller Ready, Node DaemonSet의 Desired·Ready·Available, 대상 Node 누락 여부와 실제 Node 배치를 각각 확인합니다.

## 4-5. Node Plugin은 실제 Volume을 사용할 Node 범위로 확인한다

> Node Plugin은 DaemonSet 형태로 필요한 Kubernetes Node에 배치됩니다.
>
> 그래서 Pod 숫자만 맞는지 보는 것보다 실제로 어떤 Node에 배치됐는지 확인하는 것이 중요합니다.
>
> 특히 다음 날 Monitoring이 Infra Node에 배치될 예정이라면 Worker의 Node Plugin이 정상이라는 결과로 Infra Node의 Mount 경로까지 정상이라고 판단하지 않습니다.
>
> 그다음 특정 Role Node에 Plugin이 없으면 바로 Backend나 StorageClass를 수정하지 않고 DaemonSet의 Node Selector, Taint·Toleration, Node 상태와 Scheduling Event를 먼저 봅니다.
>
> ImagePullBackOff가 발생하면 Registry·Image·Tag·CA·Image Pull 조건을 확인하고, CrashLoopBackOff가 발생하면 Config·권한·Container Log를 확인합니다.
>
> 따라서 Node Plugin 확인은 단순한 Pod Count가 아니라 실제 Storage를 사용할 Node가 CSI Mount 경로에 참여할 준비가 됐는지를 확인하는 과정입니다.

## 4-6. `tridentctl`은 Trident의 실제 상태와 Backend를 확인하는 관리 도구다

> Cluster Setup에는 `tridentctl`을 사용해 Trident Version과 Backend 상태를 확인하는 절차가 포함되어 있습니다.
>
> 먼저 Client와 Server Version을 확인하면 현재 사용 중인 Trident가 Bundle 이름에서 예상한 Version과 실제로 일치하는지 확인할 수 있습니다.
>
> 그리고 `tridentctl`은 Trident가 현재 어떤 Backend를 알고 있고 그 Backend가 어떤 상태인지 확인하는 데 사용합니다.
>
> 하지만 `tridentctl` 파일이 존재하거나 Client 명령이 실행된다고 Trident Server와 Backend가 정상이라는 뜻은 아닙니다. 실제 Server Version과 Backend 조회 결과까지 확인해야 합니다.
>
> 따라서 Bundle 디렉터리의 Version 표기와 live 결과가 다르면 현재 Cluster에서 조회한 실제 Trident 상태를 우선합니다.

## 4-7. Trident가 정상이어도 실제 Storage 대상은 Backend가 결정한다

> Operator, Controller와 Node Plugin이 모두 정상이어도 Trident는 아직 어떤 NetApp Storage를 사용할지 별도로 알아야 합니다.
>
> 그래서 Backend가 필요합니다.
>
> Backend에는 실제 NetApp SVM, Management LIF, Data LIF, Storage Driver와 공급 정책이 연결됩니다. Trident Controller는 이 Backend 정보를 이용해 PVC 요청을 어느 NetApp Storage에서 처리할지 결정합니다.
>
> 하지만 Trident Component가 Running이라는 사실만으로 Backend가 현재 신규 Member의 올바른 NetApp Storage를 가리킨다고 판단하지 않습니다.
>
> 반대로 Backend가 `online`이어도 모든 대상 Node에서 실제 NFS Mount와 Write·Read가 성공한다는 뜻은 아닙니다.
>
> 따라서 Trident Component 확인이 끝나면 다음 Backend 단계에서 현재 SVM·Management LIF·Data LIF·Driver와 Credential Source가 승인된 Storage 환경과 맞는지 별도로 확인합니다.

## 4-8. Trident 공급 준비와 실제 PVC 사용 검증을 구분한다

> Trident Operator와 Controller가 정상이고 필요한 Node Plugin이 대상 Node에 배치됐으며 Backend까지 정상적으로 연결되면 Kubernetes의 PVC 요청을 NetApp Storage로 전달할 공급 경로가 준비됩니다.
>
> 하지만 여기까지는 실제 PVC가 Bound되고 Pod가 NFS Volume을 Mount했다는 것을 증명한 것이 아닙니다.
>
> 실제 Provisioning에서는 StorageClass가 올바른 Trident Provisioner와 Backend 정책을 선택해야 하고, 실제 Mount에서는 Pod가 배치된 Node에서 Data LIF와 NFS Export 경로를 사용할 수 있어야 합니다.
>
> 그래서 오전에는 Trident의 설치·Controller·Node Plugin과 Backend 연결까지 공급 준비 상태를 확인하고, PVC·PV·Node Mount·Container Write/Read는 오후 Test Scenario에서 별도로 확인합니다.
>
> **결국 Trident가 준비됐다는 것은 Trident Pod 몇 개가 Running인 상태가 아니라, 현재 신규 Member의 Kubernetes 요청을 받아 승인된 NetApp Backend로 전달하고 필요한 Node가 그 Volume을 사용할 수 있는 CSI 경로가 준비된 상태입니다.**

---

# 5. Backend — Trident가 사용할 실제 Storage를 지정한다

> Backend는 Trident와 실제 NetApp Storage를 연결합니다.
>
> 현재 SVM, Management LIF, Data LIF, Protocol과 공급 정책을 Trident에 알려줍니다.
>
> 다른 Cluster의 SVM·LIF·Credential 참조가 남아 있지 않은지 확인합니다.
>
> Backend 이름과 Driver가 현재 승인 설계와 맞는지도 봅니다.
>
> Management LIF는 Trident가 Storage를 관리하는 경로입니다. Data LIF는 이후 Kubernetes Node가 NFS Volume을 Mount할 때 사용하는 데이터 경로입니다.
>
> Backend가 `online`이면 Trident가 관리 경로로 해당 Storage를 사용할 수 있다는 뜻입니다.
>
> **하지만 online은 PVC Provisioning·Node Mount·Write/Read까지 증명하지 않습니다.** 그 기능은 오후에 확인합니다.
>
> Backend가 offline이면 PVC를 만들지 않고 SVM·Management LIF·Credential·Network와 Backend 오류를 먼저 확인합니다.

---

# 6. StorageClass — 사용자가 선택하는 공급 정책이다

> Backend가 연결돼도 사용자가 어떤 정책으로 Storage를 요청할지 지정해야 합니다.
>
> 이 역할이 StorageClass입니다.
>
> StorageClass는 Volume 자체가 아니라 Provisioner, Backend 선택 Parameter, `reclaimPolicy`, `volumeBindingMode` 같은 정책을 정의합니다.
>
> 현재 신규 Member에서 사용할 StorageClass 이름과 Provisioner가 Trident와 연결되는지 확인합니다.
>
> Backend 또는 Storage Pool Parameter, 기본 StorageClass 여부도 승인 설계와 대조합니다.
>
> `reclaimPolicy`는 PVC 삭제 뒤 PV와 Backend Volume 처리 방식에 영향을 줍니다.
>
> `volumeBindingMode`는 PVC Binding과 Pod Scheduling 순서에 영향을 줄 수 있습니다.
>
> 따라서 오후 시험 전에 이 두 정책이 어떤 결과를 만드는지 확인합니다.
>
> 실제 사용자의 요청은 `PVC → StorageClass → Trident → Backend → PV·Backend Volume` 순서로 이어집니다. 이 경로의 모든 값이 같은 신규 Member와 같은 NetApp Storage를 가리켜야 합니다.
>
> Backend `online`은 관리 경로가 정상이라는 뜻이고 실제 Pod Mount는 오후에 선택된 Node에서 Data LIF·NFS Export 경로로 따로 확인합니다.

---

# 7. 문제가 생기면 공급 순서대로 확인한다

> Snapshot CRD가 없으면 Backend부터 고치지 않고 CRD Version과 Established 상태를 봅니다.
>
> Operator는 Running인데 Trident Controller가 준비되지 않으면 CR 상태·Image·권한을 확인합니다.
>
> 특정 Node Plugin만 없으면 StorageClass보다 DaemonSet Scheduling·Label·Taint·Host 조건을 봅니다.
>
> Backend가 offline이면 SVM·Management LIF·Credential·Network를 확인합니다.
>
> Backend는 online인데 StorageClass가 없거나 과거 Parameter를 사용하면 StorageClass와 Provisioner 설정을 봅니다.
>
> 확인 순서는 `Bundle 선행 기능 → Trident Controller·Node Plugin → Backend → StorageClass`입니다.

---

# 8. 오전 완료는 STORAGE SUPPLY PASS다

> 현재 Bundle이 요구하는 Snapshot 기반이 준비돼야 합니다.
>
> Trident Controller와 필요한 Node Plugin이 정상이어야 합니다.
>
> Backend가 승인된 NetApp Storage에 online으로 연결되고, StorageClass가 현재 Provisioner와 Backend 정책을 사용해야 합니다.
>
> 오후 시험에 사용할 Namespace·StorageClass·Node Role과 Cleanup 기준도 확인합니다.
>
> 이 상태를 `STORAGE SUPPLY PASS`라고 합니다.
>
> **하지만 아직 Storage 기능 전체 PASS는 아닙니다.** PVC Provisioning, Node Mount, Container Write·Read와 삭제 후 Lifecycle은 오후에 확인합니다.
>
> Trident 핵심 Component, Backend 또는 StorageClass가 미확정이면 `BLOCKED`입니다.

---

# 9. 오후에는 공급 기준을 넘긴다

> 오후에는 Cluster·Context와 `STORAGE SUPPLY PASS / BLOCKED` 결과를 넘깁니다.
>
> Snapshot CRD·Controller, Trident Controller·Node Plugin 상태를 전달합니다.
>
> Backend 이름·online 상태·SVM·Management/Data 경로의 근거도 이어갑니다.
>
> StorageClass 이름·Provisioner·주요 Parameter·Reclaim·Binding 기준과 Test PVC Namespace·용량·대상 Node Role을 넘깁니다.
>
> Credential 원문은 제외합니다.

---

# 10. 마무리

> Kubernetes가 Pod를 실행해도 Persistent Storage 공급은 별도였습니다.
>
> 그래서 PVC 요청을 NetApp 작업으로 바꿀 Trident를 준비하고, Backend로 실제 Storage를 연결했습니다.
>
> 그다음 StorageClass로 사용자가 선택할 정책을 제공했습니다.
>
> Snapshotter는 기본 Provisioning과 구분해 현재 Bundle의 별도 기능으로 확인했습니다.
>
> **결국 STORAGE SUPPLY PASS는 StorageClass 이름이 보이는 상태가 아니라, 현재 신규 Member의 PVC 요청을 올바른 Trident와 NetApp Backend로 전달할 준비가 된 상태입니다.**
