# 5.4 Storage Component 실제 사용 검증 강사용 전체 대본 - 원본 절차 순서 준수본

> [!important] 사용 방법
> 이 문서는 원본 `04.md`의 `4-4. 스토리지 컴포넌트 설치 검증`을 처음부터 끝까지 그대로 따라간다.
>
> **실제 신규 Member 환경값·실행 조건·PASS/BLOCKED 판정은 [[출장/30. 구축/2026-09-02 Member 구축 3일차 - Storage 구성 및 사용 검증|9/2 Member 구축 Source of Truth]]를 우선한다.** `04.md`는 원본 검증 순서와 기술 확인 항목의 기준으로 사용한다.
>
> 원본 `04.md`는 Xi'an Host Cluster용이므로 Host hostname·StorageClass·Image·PowerFlex 적용 결론을 신규 Member 실행값으로 그대로 복사하지 않는다. **작업 순서와 검증 논리는 유지하고, 현재 신규 Member의 승인값을 사용한다.**
>
> 오후의 핵심은 `PVC Bound` 한 줄을 얻는 것이 아니다. 원본 순서대로 PVC와 PV의 관계를 확인하고, Test Pod가 실제 대상 Node에서 Volume을 Mount하며, Container가 데이터를 쓰고 다른 Replica에서 읽고, Trident Volume과 Backend까지 연결한 뒤 Cleanup까지 완료한다.
>
> 운영 PVC를 시험 대상으로 사용하지 않는다. Test Resource를 만들기 전 이름·Namespace·StorageClass·대상 Role·Cleanup 기준을 확인한다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
오전에는 Storage 공급 경로를 준비했다
→ 4-4에서 실제 Storage 기능을 시험한다
→ PowerFlex 적용 여부를 먼저 확인한다
→ NetApp Test Namespace를 준비한다
→ PVC를 만들어 Provisioning을 확인한다
→ PV와 CSI Driver를 연결한다
→ Test Deployment를 배치한다
→ 실제 Node와 Mount를 확인한다
→ 첫 Pod가 쓰고 다른 Pod가 읽는다
→ Trident Volume과 Backend까지 연결한다
→ 완료 판정표를 채운다
→ Test Resource를 정리하고 증적을 보존한다
```

## 0-1. 오늘 전체 한 줄

> 오후에는 **현재 신규 Member의 승인 StorageClass가 실제 Volume을 공급하고, Pod가 그 Volume을 Mount하여 데이터를 사용하며, Lifecycle까지 원본 4-4 기준으로 정상인지 확인합니다.**

---

# 1. 시작 — 공급 준비가 끝났다면 이제 실제 사용자 요청으로 검증한다

> 오전에는 Snapshotter, PowerFlex 적용 여부, Trident, Backend, StorageClass까지 준비했습니다.
>
> 하지만 Backend가 `online`이고 StorageClass가 존재해도 Application이 실제로 Storage를 사용할 수 있다는 뜻은 아닙니다.
>
> 그래서 원본 `4-4`에서는 실제 Test PVC와 Pod를 사용합니다. 여기서 중요한 것은 앞 단계가 성공하기 전에는 뒤 단계를 성공으로 판단하지 않는 것입니다.
>
> PVC가 아직 Pending이면 NFS Mount부터 고치지 않습니다. Pod가 아직 Scheduling되지 않았다면 `FailedMount` 장애라고 부르지 않습니다. Pod가 Running이어도 실제 PVC가 Mount됐는지 확인하기 전에는 Write 시험을 시작하지 않습니다.

먼저 오전에 넘겨받은 값을 확인합니다.

```text
Current Cluster / Context
PowerFlex 적용 여부
현재 승인 StorageClass
Provisioner
Trident Backend / State
reclaimPolicy
volumeBindingMode
Test Namespace
Test PVC 용량 / Access Mode
Test Pod 대상 Role
```

현재 Context를 다시 확인합니다.

```bash
kubectl config current-context
kubectl get nodes -o wide
kubectl get storageclass
```

> 오전과 오후 사이에 Shell이나 kubeconfig가 바뀔 수 있기 때문에 실제 변경 명령 전에 Context를 다시 확인합니다.

---

# 2. 원본 4-4 — StorageClass가 보이는 것만으로 설치 검증을 끝내지 않는다

> 원본의 완료 흐름은 명확합니다. StorageClass 존재 다음에 실제 PVC Provisioning, Pod Scheduling, kubelet/CSI Mount, Container Filesystem, Write/Read가 이어져야 합니다.
>
> 오후에는 이 순서를 그대로 실제 Test Resource로 확인합니다.

---

# 3. 원본 4-4-1 — PowerFlex 테스트 PVC 적용 여부를 먼저 판정한다

> 원본에는 PowerFlex Test 항목이 먼저 있습니다. 현재 신규 Member가 PowerFlex 미적용이라도 이 항목을 삭제하지 않습니다. **적용 여부를 확인하고 `해당 없음`을 근거와 함께 기록한 뒤 다음 원본 4-4-2로 넘어갑니다.**

읽기 전용으로 현재 상태를 확인합니다.

```bash
kubectl get csidriver
kubectl get storageclass
kubectl get ns vxflexos 2>/dev/null || true
```

판정 예:

```text
PowerFlex 적용 여부: <적용 / 적용 제외 / 별도 확인>
PowerFlex CSI Driver: <실제 출력 또는 없음>
PowerFlex StorageClass: <실제 출력 또는 없음>
Test PVC 실행 여부: <실행 / 미실행>
```

> 현재 신규 Member가 NetApp Trident 전용으로 승인됐다면 PowerFlex Test PVC나 Pod를 만들지 않습니다.
>
> PowerFlex가 실제 적용 대상이라면 승인된 PowerFlex StorageClass와 Test Manifest를 별도 기준으로 사용해야 하며, 과거 Taylor의 endpoint·systemID·MDM·StorageClass를 재사용하지 않습니다.

원본 다음 단계는 `4-4-2 NetApp 테스트 PVC로 StorageClass 테스트`입니다.

# 4. 원본 4-4-2 — NetApp Test PVC로 StorageClass를 실제 검증한다

> 여기서부터 현재 신규 Member의 실제 NetApp Storage 기능 시험을 진행합니다.
>
> 원본 순서는 `Namespace → PVC → PV/CSI → Deployment → Pod/NODE → Used By → Mount → Write/Read → Trident Volume → 완료 판정 → Cleanup`입니다.

## 4.1 원본 4-4-2 1번 — Test Namespace 생성 여부를 결정한다

운영 Namespace와 섞이지 않도록 승인된 Test Namespace를 사용합니다.

예:

```text
<CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

먼저 존재 여부를 확인합니다.

```bash
kubectl get ns <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

없고 생성이 승인됐을 때만 만듭니다.

```bash
kubectl create namespace <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

생성 후 확인합니다.

```bash
kubectl get ns <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

강사 설명:

> Test Namespace를 별도로 쓰는 이유는 운영 Resource와 시험 Resource를 명확히 구분하고 마지막 Cleanup 범위를 안전하게 고정하기 위해서입니다.
>
> 이미 존재하는 Namespace를 사용한다면 이 테스트가 만든 Resource만 나중에 삭제해야 합니다. Namespace 전체를 삭제해도 되는지는 별도 판단입니다.

---

## 4.2 원본 4-4-2 2번 — Test PVC를 작성하고 실제 Provisioning을 확인한다

원본 구조를 유지하되 현재 신규 Member 승인값으로 작성합니다.

`member-netapp-pvc.yaml` 예:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: member-netapp-pvc
  namespace: <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
spec:
  accessModes:
    - ReadWriteMany
  volumeMode: Filesystem
  resources:
    requests:
      storage: 2Gi
  storageClassName: <CURRENT_MEMBER_STORAGECLASS>
```

> 원본 Host 예시의 `scs-netapp-qtree-nfs-sc-delete`를 신규 Member의 현재값으로 자동 가정하지 않습니다. 오전에 확정한 StorageClass를 사용합니다.
>
> 요청 용량과 Access Mode도 실제 시험 목적과 StorageClass 지원 조건을 확인합니다.

적용 전 dry-run합니다.

```bash
kubectl apply --dry-run=client -f member-netapp-pvc.yaml
```

문제가 없으면 실제 적용합니다.

```bash
kubectl apply -f member-netapp-pvc.yaml
```

PVC 상태를 확인합니다.

```bash
kubectl get pvc member-netapp-pvc \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> -o wide
```

정상적으로 동적 Provisioning이 완료됐다면 다음을 확인합니다.

```text
STATUS = Bound
STORAGECLASS = 현재 승인 StorageClass
VOLUME = 실제 생성 PV
CAPACITY = 요청값 또는 승인 결과
ACCESS MODES = 시험 의도와 일치
```

강사 설명:

> PVC Apply 성공은 Kubernetes API에 요청 객체를 만들었다는 뜻입니다. 실제 Volume이 만들어졌다는 뜻은 아닙니다.
>
> PVC가 `Bound`가 되면 PVC와 PV가 연결됐고 Provisioning 단계가 성공했다는 증거가 됩니다. 하지만 아직 Pod가 그 Volume을 Mount한 것은 아닙니다.

### PVC가 Pending이면 여기서 멈춘다

```bash
kubectl describe pvc member-netapp-pvc \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

먼저 다음을 봅니다.

- Event의 Provisioning 오류
- StorageClass 이름과 Provisioner
- Backend 상태
- StorageClass Parameter
- `volumeBindingMode`

> `WaitForFirstConsumer`라면 Pod가 생기기 전 Pending이 정상일 수 있습니다. `Immediate`인데 Provisioning 실패 Event가 반복된다면 아직 Node NFS Mount 단계로 갈 이유가 없습니다.

PVC가 원본 의도대로 Provisioning된 뒤 다음 단계로 넘어갑니다.

## 4.3 원본 4-4-2 3번 — PV와 CSI 관계를 확인한다

PVC가 연결한 PV 이름을 가져옵니다.

```bash
PV_NAME="$(kubectl get pvc member-netapp-pvc \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  -o jsonpath='{.spec.volumeName}')"
echo "$PV_NAME"
```

PV를 확인합니다.

```bash
kubectl get pv "$PV_NAME" -o wide
```

CSI Driver와 VolumeHandle을 확인합니다.

```bash
kubectl get pv "$PV_NAME" \
  -o jsonpath='{.spec.csi.driver}{"\n"}{.spec.csi.volumeHandle}{"\n"}'
```

NetApp Trident 경로라면 기대하는 Driver는 현재 Trident CSI입니다.

```text
driver = csi.trident.netapp.io
volumeHandle = <실제 생성값>
```

강사 설명:

> 여기서는 PVC가 어떤 PV와 연결됐는지, 그 PV가 어느 CSI Driver가 만든 것인지, Storage 쪽 실제 Volume을 식별할 VolumeHandle이 무엇인지 확인합니다.
>
> `Bound`는 여기까지의 Provisioning 성공을 말합니다. 이 상태에서 Pod가 `FailedMount`일 수 있으므로 Mount 성공으로 확대 해석하지 않습니다.

`reclaimPolicy`도 현재 PV 또는 StorageClass 기준으로 다시 확인해 뒤 Cleanup과 연결합니다.

```bash
kubectl get pv "$PV_NAME" -o jsonpath='{.spec.persistentVolumeReclaimPolicy}{"\n"}'
```

## 4.4 원본 4-4-2 4번 — Test Deployment를 작성한다

원본은 여러 Replica가 같은 RWX PVC를 사용하는 Deployment로 기능을 검증합니다.

`member-netapp-deploy.yaml` 예:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: member-netapp-test
  namespace: <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
spec:
  replicas: 3
  selector:
    matchLabels:
      app: member-netapp-test
  template:
    metadata:
      labels:
        app: member-netapp-test
    spec:
      nodeSelector:
        node-type: infra
      tolerations:
        - key: node-role.kubernetes.io/infra
          effect: NoSchedule
      containers:
        - name: nginx
          image: <CURRENT_APPROVED_TEST_IMAGE>
          imagePullPolicy: IfNotPresent
          volumeMounts:
            - name: netapp-volume
              mountPath: /pvc-test
      volumes:
        - name: netapp-volume
          persistentVolumeClaim:
            claimName: member-netapp-pvc
```

> [!warning] 신규 Member 값
> 원본 Host Infra hostname, 과거 Registry Image, Taylor/Member 다른 Cluster Node 이름을 그대로 사용하지 않습니다. 현재 신규 Member의 실제 Infra Label/Taint와 승인 Test Image를 사용합니다.

강사 설명:

> 여기서 중요한 필드는 세 가지입니다. 첫째, Pod가 실제 시험하려는 Node Role에 배치돼야 합니다. 둘째, `claimName`이 방금 만든 PVC를 가리켜야 합니다. 셋째, Container의 `/pvc-test`가 그 PVC Volume을 Mount하도록 연결돼야 합니다.
>
> 다음 날 실제 Workload가 Infra에서 Storage를 사용할 예정이라면 Infra에서 시험하는 것이 특히 중요합니다. Worker 성공 결과로 Infra의 NFS Data Path를 대신하지 않습니다.

적용 전 dry-run합니다.

```bash
kubectl apply --dry-run=client -f member-netapp-deploy.yaml
```

승인 후 적용합니다.

```bash
kubectl apply -f member-netapp-deploy.yaml
```

## 4.5 원본 4-4-2 5번 — Pod Ready와 실제 NODE를 확인한다

Deployment 수렴을 확인합니다.

```bash
kubectl rollout status deployment/member-netapp-test \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

Pod를 확인합니다.

```bash
kubectl get pod \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  -l app=member-netapp-test -o wide
```

확인할 것:

```text
Replica 3개 Ready
STATUS = Running
실제 NODE = 승인된 현재 신규 Member Infra
비정상 Restart 없음
```

강사 설명:

> Volume Mount는 Pod가 배치된 Node에서 일어납니다. 그래서 Storage 장애를 볼 때 실제 Pod NODE를 먼저 알아야 합니다.
>
> 아직 Pod가 Scheduling되지 않았다면 Mount 장애라고 부르지 않습니다. Selector, Taint/Toleration, Resource와 Scheduler Event를 먼저 확인합니다.

### `ContainerCreating` 또는 `FailedMount`라면

Pod Event를 확인합니다.

```bash
kubectl describe pod \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  -l app=member-netapp-test
```

이 시점부터 실제 Mount Data Path를 봅니다.

- Pod가 배치된 Node
- PV가 사용하는 NFS Server / Export
- 현재 Data LIF
- Node에서 Data LIF까지 Route
- TCP 2049
- NFS Client Package
- Export Policy
- Trident Node Plugin

> [!note] 장애 시 교육 보강 — Data LIF 2049 확인
> 원본 `4-4`의 필수 정상 흐름을 대체하는 단계가 아니라, `FailedMount`가 발생했을 때 Node Data Path를 좁히기 위한 추가 확인입니다.

```bash
nc -zvw3 <CURRENT_DATA_LIF> 2049
```

> Backend `online`은 Trident 관리 경로가 정상이라는 뜻입니다. 실제 Pod Mount는 Node에서 Data LIF와 NFS Export를 사용하는 별도 경로입니다.
>
> 따라서 `FailedMount`가 나왔을 때 PVC를 이유 없이 다시 만드는 대신 이미 성공한 Provisioning 결과를 보존하고 Node의 실제 Data Path를 확인합니다.

## 4.6 원본 4-4-2 6번 — PVC의 Used By 관계를 확인한다

```bash
kubectl describe pvc member-netapp-pvc \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  | grep -i 'Used By'
```

강사 설명:

> 이 단계는 방금 만든 PVC가 실제 Test Pod와 연결돼 사용되고 있는지 Kubernetes 관점에서 확인합니다.
>
> `Used By`가 기대 Pod를 가리키는지 보고, 다른 오래된 Test Pod나 예상하지 않은 Workload가 연결돼 있지 않은지도 확인합니다.

## 4.7 원본 4-4-2 7번 — Container 내부에서 실제 Mount를 확인한다

먼저 Pod 하나를 선택합니다.

```bash
TEST_POD="$(kubectl get pod \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  -l app=member-netapp-test \
  -o jsonpath='{.items[0].metadata.name}')"
echo "$TEST_POD"
```

Container 내부에서 Mount를 확인합니다.

```bash
kubectl exec \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  "$TEST_POD" -- df -h /pvc-test
```

```bash
kubectl exec \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  "$TEST_POD" -- mount | grep '/pvc-test'
```

확인할 것:

```text
/pvc-test가 실제 별도 Filesystem으로 보임
Size가 PV 요청과 합리적으로 연결됨
Mount Source가 현재 Storage Data Path와 연결됨
NFS Export가 과거 Cluster 값이 아님
```

강사 설명:

> Pod가 Running이라고 실제 PVC가 Mount됐다고 단정하지 않습니다. 잘못된 Local Directory나 다른 Volume을 사용해도 Container는 실행될 수 있습니다.
>
> 그래서 Pod Spec의 PVC 연결과 Container 안의 실제 Filesystem을 함께 봅니다.

> [!warning] NFS Export Path
> NFS Export 이름과 경로는 Trident가 동적으로 만든 값일 수 있습니다. 과거 Cluster의 Export Path를 신규 Member 이름으로 바꿔 적지 않습니다. 실제 PV·Pod Mount 출력에서 나온 값을 사용합니다.

## 4.8 원본 4-4-2 8번 — 첫 Pod가 쓰고 다른 Replica가 읽는지 확인한다

첫 Pod에서 실제 Persistent Mount Path에 Test Data를 씁니다.

```bash
kubectl exec \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  "$TEST_POD" -- \
  sh -c 'date -u > /pvc-test/member-storage-check && cat /pvc-test/member-storage-check'
```

Pod 목록을 확인합니다.

```bash
kubectl get pod \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  -l app=member-netapp-test -o name
```

다른 Replica에서 같은 파일을 읽습니다.

```bash
kubectl exec \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  <OTHER_POD_NAME> -- \
  cat /pvc-test/member-storage-check
```

강사 설명:

> 첫 Pod의 Write 성공은 그 Container가 Mount된 Filesystem에 데이터를 기록할 수 있다는 뜻입니다.
>
> 다른 Replica에서 같은 파일을 읽는 것은 여러 Pod가 동일한 RWX Persistent Volume을 보고 있다는 더 강한 증거입니다. 단순히 같은 Pod에서 Write 직후 Read하는 것보다 원본 시험 의도에 더 가깝습니다.

완료 기준:

```text
Replica 3개 Ready
승인 Node Role에 배치
모든 Pod의 /pvc-test Mount 확인
첫 Pod Write 성공
다른 Pod에서 동일 파일 Read 성공
```

> [!note] 교육 보강 — Persistence 재연결
> 원본 `4-4`의 필수 순서는 다른 Replica Read까지입니다. Pod 재생성 후 데이터 유지까지 추가 검증해야 한다면 **별도 승인된 교육 보강**으로 수행합니다. 이때 PVC는 삭제하지 않고 Pod만 재생성하거나 Reader Pod를 사용합니다.

## 4.9 원본 4-4-2 9번 — Trident Backend와 Volume까지 연결한다

오전에 사용한 Trident Bundle Directory에서 확인합니다.

```bash
./tridentctl -n trident get backend
./tridentctl -n trident get volume
```

강사 설명:

> 이제 Kubernetes 쪽 PVC/PV만 본 것이 아니라 Trident가 실제 어떤 Volume을 알고 있는지까지 연결합니다.
>
> 앞에서 확인한 PV의 `volumeHandle`과 Trident Volume을 대조하면 Kubernetes의 PV가 어느 Trident Volume과 연결되는지 설명할 수 있습니다.
>
> 그리고 그 Volume이 어느 Backend에서 공급됐는지 확인하면 오전에 만든 Backend와 오후 실제 PVC 요청이 같은 Storage 경로를 사용했다는 근거가 됩니다.

보존할 값:

```text
PVC Name
PV Name
PV CSI Driver
PV VolumeHandle
Trident Volume 식별값
Backend Name
Backend State
실제 NFS Source / Export Path
```

민감정보는 보존하지 않습니다.

| 검증 항목 | 신규 Member 실제 결과 | 판정 |

하나라도 FAIL이면 어느 원본 단계에서 처음 실패했는지 기록하고 뒤의 성공 항목으로 덮지 않습니다.

## 4.11 원본 4-4-2 11번 — Test Resource를 정리한다

> Cleanup은 단순한 뒷정리가 아니라 오전 StorageClass에서 확인한 `reclaimPolicy`가 실제로 어떻게 동작하는지 확인하는 마지막 단계입니다.

먼저 삭제 대상이 이번 시험 Resource인지 확인합니다.

```bash
kubectl get deploy,pod,pvc \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

PV 이름과 현재 상태를 삭제 전에 기록합니다.

```bash
echo "$PV_NAME"
kubectl get pv "$PV_NAME" -o wide
```

먼저 Deployment를 삭제합니다.

```bash
kubectl delete -f member-netapp-deploy.yaml
```

Pod가 정리됐는지 확인합니다.

```bash
kubectl get pod \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE> \
  -l app=member-netapp-test
```

그다음 PVC를 삭제합니다.

```bash
kubectl delete -f member-netapp-pvc.yaml
```

PV 상태를 확인합니다.

```bash
kubectl get pv "$PV_NAME"
```

Trident Volume도 다시 봅니다.

```bash
./tridentctl -n trident get volume
```

강사 설명:

> `reclaimPolicy: Delete`라면 PVC 삭제 뒤 Test PV와 Backend Volume이 의도대로 정리되는지 확인합니다.
>
> `Retain`이라면 Volume이 남는 것이 정상일 수 있습니다. 이 경우 잔여 Volume을 실패로 처리하지 않고 후속 정리 책임을 명확히 기록합니다.
>
> 삭제 명령이 성공했다고 Backend Volume까지 정리됐다고 단정하지 않습니다. Kubernetes PV와 Trident Volume 상태를 함께 봅니다.

Resource가 `Terminating`에 오래 머문다고 Finalizer를 바로 제거하지 않습니다. 어떤 Controller가 정리를 완료하지 못했는지와 실제 Backend 상태를 먼저 확인합니다.

Test 전용으로 새로 만든 Namespace이고 다른 Resource가 없는 경우에만 마지막에 삭제합니다.

```bash
kubectl get all,pvc \
  -n <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

```bash
kubectl delete namespace <CURRENT_MEMBER_STORAGE_TEST_NAMESPACE>
```

> 공유 Test Namespace라면 Namespace 자체는 삭제하지 않습니다.

# 6. 문제가 생기면 원본 4-4의 처음 실패 단계부터 확인한다

> PVC가 `Pending`이면 `describe pvc`의 Event와 StorageClass·Provisioner·Backend·Binding Mode를 봅니다. 아직 Pod Node가 정해지지 않았다면 NFS 2049를 먼저 수정하지 않습니다.
>
> PVC가 Bound됐는데 Pod가 Pending이면 Node Selector, Taint/Toleration, Resource, Scheduler Event를 먼저 봅니다.
>
> PVC가 Bound되고 Node도 정해졌는데 `ContainerCreating` 또는 `FailedMount`라면 그때 Data LIF, Route, TCP 2049, NFS Client, Export Policy와 Trident Node Plugin을 확인합니다.
>
> Pod가 Running인데 `/pvc-test`가 실제 Persistent Volume이 아니라면 Write 시험을 하지 않습니다. Pod Spec과 `df`, `mount` 결과를 다시 확인합니다.
>
> Mount는 정상인데 Write가 실패하면 Provisioning부터 다시 만들지 않습니다. Permission, UID/GID, Read-only, Filesystem과 Mount Option을 먼저 확인합니다.
>
> 첫 Pod Write는 성공했는데 다른 Replica에서 파일이 보이지 않으면 모든 Pod가 같은 PVC와 MountPath를 사용하고 있는지 확인합니다.
>
> Cleanup 뒤 PV 또는 Trident Volume이 예상과 다르게 남으면 `reclaimPolicy`, Finalizer와 Controller 정리 상태를 확인합니다.
