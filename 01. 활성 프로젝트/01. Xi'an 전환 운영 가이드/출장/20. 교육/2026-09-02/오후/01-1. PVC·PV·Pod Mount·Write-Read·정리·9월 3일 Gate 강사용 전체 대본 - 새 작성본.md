# PVC·PV·Pod Mount·Write-Read·정리·9월 3일 Gate 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 오전에는 Trident·Backend·StorageClass를 준비해 `STORAGE SUPPLY PASS`를 확인했다. 이번 블록은 **PVC 요청이 실제 Volume·Node Mount·Container Write/Read로 이어지는지 확인하는 과정**이다.
>
> Test PVC·Pod와 삭제 명령은 승인된 Storage Runbook을 따른다. 운영 PVC를 시험 대상으로 사용하지 않고 Credential·Secret 원문을 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
Storage 공급 준비가 끝났다
→ 하지만 실제 Volume 사용은 아직 확인하지 않았다
→ PVC가 StorageClass를 선택해 요청한다
→ PVC Bound 뒤 PV와 Backend Volume을 확인한다
→ Pod가 배치된 Node에서 Mount가 성공해야 한다
→ Pod Running 뒤 실제 PVC Mount인지 확인한다
→ Container에서 Write·Read를 확인한다
→ 필요하면 Pod 재생성 뒤 데이터 유지도 확인한다
→ 다음 Application이 사용할 Infra Node 조건을 확인한다
→ reclaimPolicy에 맞게 정리한다
```

## 0-1. 오늘 전체 한 줄

> 오후 Storage 검증은 PVC의 STATUS를 보는 시간이 아닙니다. **요청한 Storage가 실제 Pod에 Mount되고 데이터를 쓰고 읽으며, 정리 정책까지 정상인지 확인하는 시간**입니다.

---

# 1. 시작 — 공급 준비와 실제 사용은 다르다

> 오전에는 Trident Controller와 Node Plugin, Backend online, StorageClass 정책을 확인했습니다.
>
> **하지만 실제 PVC 요청이 PV로 만들어지는지, Pod가 선택된 Node에서 Mount할 수 있는지, Container가 데이터를 쓸 수 있는지는 아직 모릅니다.**
>
> 그래서 사용자의 Storage 요청이 실제 Filesystem이 되는 과정을 확인합니다.
>
> 먼저 오후 검증에서 사용할 Storage 경로를 고정합니다. 현재 신규 Member의 실제 검증은 승인된 StorageClass와 CSI 경로를 기준으로 진행하고, NetApp Trident/NFS가 승인된 경로라면 PVC Provisioning부터 Data LIF·NFS Export·Node Mount까지 같은 경로를 따라갑니다.
>
> 오전에 설명한 PowerFlex가 실제 적용 대상으로 승인된 경우에도 PVC·PV·Pod 사용이라는 검증 원칙은 같지만, Node Data Path는 NFS가 아니라 PowerFlex CSI·SDC·Block Device 기준으로 확인해야 합니다.
>
> 따라서 오후에는 서로 다른 Storage 방식을 섞지 않고, 현재 Test PVC가 선택한 StorageClass와 Provisioner가 가리키는 실제 경로를 끝까지 따라갑니다.

---

# 2. PVC — 사용자가 필요한 Storage를 요청한다

> PVC는 Application이 용량·Access Mode·StorageClass를 지정해 Persistent Storage를 요청하는 객체입니다.
>
> 먼저 현재 승인된 Test Namespace와 StorageClass, 의미 있는 용량을 사용합니다. 과거 Cluster의 StorageClass 이름이나 임의의 큰 용량을 사용하지 않습니다.
>
> PVC의 요청 용량은 실제 검증에 필요한 크기로 잡고, Access Mode는 이후 Pod가 Volume을 어떤 방식으로 사용할지와 연결해서 봅니다. StorageClass는 이 요청을 어느 Provisioner와 Storage 정책으로 보낼지 결정합니다.
>
> 그래서 PVC를 만들기 전에 Namespace, StorageClass 이름, 요청 용량과 Access Mode가 이번 시험 의도와 맞는지 먼저 확인합니다.
>
> Apply 성공은 요청 객체가 Kubernetes API에 생성됐다는 뜻입니다. **하지만 실제 Volume이 공급됐다는 뜻은 아닙니다.**
>
> 그다음 PVC의 Pending·Bound 상태와 Event를 확인하고 어떤 Provisioner가 요청을 처리하는지 봅니다.
>
> PVC가 `Pending`이면 같은 상태라도 원인이 다를 수 있습니다. `volumeBindingMode`가 `WaitForFirstConsumer`라면 Pod Scheduling 전까지 기다리는 것이 정상일 수 있고, `Immediate`인데 계속 Pending이면 Provisioner·Backend·Parameter나 실제 Storage 연결 문제일 수 있습니다.
>
> 그래서 Pending 상태 자체만 보고 실패라고 단정하지 않고 StorageClass의 Binding Mode와 Event를 같이 읽습니다.
>
> 반대로 Event에 Provisioning 실패가 명확히 보이는데 Node Network나 NFS Mount부터 확인하면 아직 도달하지 않은 단계를 보는 것입니다.
>
> 따라서 PVC가 Pending이면 Node Mount를 확인하지 않고 StorageClass·Provisioner·Backend·요청 Parameter와 Event를 먼저 봅니다.

---

# 3. PVC Bound — Provisioning 성공이지 Mount 성공은 아니다

> PVC가 `Bound`이면 요청한 PVC와 하나의 PV가 연결됐다는 뜻입니다.
>
> 동적 Provisioning이라면 Trident가 StorageClass와 Backend 정책을 사용해 실제 NetApp Volume을 만들고 Kubernetes에 PV를 연결했을 수 있습니다.
>
> 그래서 연결된 PV의 StorageClass·Capacity·Access Mode·CSI Driver·VolumeHandle을 확인합니다.
>
> 먼저 PVC에서 요청한 Capacity와 Access Mode가 PV에 의도대로 반영됐는지 봅니다. 그다음 PV의 CSI Driver와 VolumeHandle을 확인해 실제 어느 CSI가 만든 Volume인지 연결합니다.
>
> VolumeHandle은 Kubernetes의 PV와 Storage 쪽 실제 Volume을 연결하는 중요한 식별값이므로 Test PVC·PV 증적에 같이 남깁니다.
>
> 그리고 `reclaimPolicy`가 오전 StorageClass에서 확인한 정책과 같은지도 봅니다. 이 값은 시험이 끝난 뒤 PVC를 삭제했을 때 PV와 Backend Volume을 어떻게 처리할지 결정하므로 Cleanup 단계와 직접 연결됩니다.
>
> **하지만 Bound는 Volume 할당까지의 성공입니다. Pod가 실제로 Volume을 Mount한 것은 아닙니다.**
>
> 그래서 PVC가 Bound됐다는 이유로 바로 Write 시험으로 넘어가지 않습니다. 아직 Pod가 어느 Node에 배치될지, 그 Node에서 실제 Data Path를 사용할 수 있는지는 확인하지 않았습니다.
>
> 반대로 PVC가 `Bound`인데 Pod가 `ContainerCreating`이나 `FailedMount`라면 Provisioning 자체를 다시 의심하기보다 다음 Mount 단계의 실패 경계를 봐야 합니다.
>
> 따라서 `Bound`는 Provisioning 단계가 통과했다는 증거로 사용하고, 그다음부터는 Pod Scheduling과 선택된 Node의 Mount 경로를 확인합니다.

---

# 4. Pod Scheduling — 어느 Node가 Mount를 수행하는지 확인한다

> Volume Mount는 Pod가 배치된 Node에서 일어납니다.
>
> 그래서 Mount 문제를 확인하기 전에 Pod의 실제 Node를 봅니다.
>
> 먼저 Test Pod가 승인된 Role에 배치됐는지 확인합니다. 같은 Cluster 안에서도 Worker와 Infra는 Label·Taint·Network 조건이 다를 수 있으므로 다른 Role의 성공 결과를 그대로 대신 사용하지 않습니다.
>
> 그다음 Node Selector와 Taint·Toleration이 시험 의도와 맞는지 봅니다. Pod가 특정 Role에서 실제 Storage를 사용할 예정이라면 Test Pod도 가능한 한 같은 배치 조건을 사용해야 합니다.
>
> `volumeBindingMode`가 `WaitForFirstConsumer`이면 Pod Scheduling 정보가 Storage Provisioning과 연결될 수 있습니다. 그래서 PVC와 Pod가 동시에 Pending일 때는 어느 쪽이 먼저 막힌 것인지 Event를 순서대로 읽어야 합니다.
>
> 반대로 `Immediate` 방식에서 PVC가 이미 Bound됐다면 그다음 Pod Pending은 Storage Provisioning보다 Selector·Taint·Resource·Scheduler 조건을 먼저 봅니다.
>
> 그리고 실제 Pod가 배치된 Node에 Trident Node Plugin과 필요한 NFS Client Package가 있는지도 확인합니다. 다음 날 Monitoring이 Infra Node에서 Storage를 사용할 예정이라면 Infra Node의 Plugin과 NFS 조건을 별도로 확인해야 합니다.
>
> 따라서 Pod가 아직 어느 Node에도 배치되지 않았다면 Mount 장애라고 부르지 않습니다. 먼저 PVC Binding 조건과 Scheduling 조건을 구분하고, Node가 결정된 뒤에야 실제 Data Path를 확인합니다.

---

# 5. Node Mount — 관리 경로와 데이터 경로를 구분한다

> Backend `online`은 Trident가 NetApp Storage의 관리 경로를 사용할 수 있다는 뜻입니다.
>
> 먼저 이 관리 경로와 실제 Pod가 Volume을 사용하는 데이터 경로를 구분합니다. Trident Controller는 Management LIF를 통해 Storage를 관리하지만, 실제 NFS Mount는 Pod가 배치된 Node에서 Data LIF와 NFS Export로 접근해야 합니다.
>
> **하지만 Backend가 online이라는 사실만으로 선택된 Node에서 NFS Mount가 성공한다고 판단하지 않습니다.**
>
> 그래서 Pod Event에서 실제로 사용하려는 NFS Server와 Export Path, Mount 오류 원문을 확인합니다.
>
> 그다음 그 값이 PV와 VolumeHandle, 현재 Backend에서 기대한 Data LIF·Export 경로와 연결되는지 봅니다. 다른 Cluster의 Export Path나 과거 Data LIF가 섞여 있으면 Bound 이후 Mount 단계에서 실패할 수 있습니다.
>
> 실제 Node 쪽에서는 Source IP와 Data LIF까지의 Route, TCP 2049 접근, NFS Client Package와 Storage Export Policy가 모두 Mount 경로에 영향을 줍니다.
>
> 그래서 Network 연결을 볼 때 단순히 Data LIF가 Ping되는지만 보지 않습니다. NFS에 필요한 Port와 실제 Export 접근 조건이 현재 Pod Node 기준으로 허용되는지 확인해야 합니다.
>
> 그리고 Export Policy는 어느 Node Source가 해당 Export를 Mount할 수 있는지와 연결됩니다. 다른 Node에서 Mount가 성공했다는 결과로 현재 Pod Node의 Export 허용까지 대신하지 않습니다.
>
> 반대로 PVC가 아직 Pending인데 NFS Route나 2049부터 확인하면 아직 Provisioning 단계가 통과하지 않은 상태에서 다음 단계의 증거를 보는 것입니다.
>
> 따라서 PVC가 Bound되기 전에는 Provisioning 경로를 먼저 보고, Bound 뒤 `FailedMount`가 발생하면 Provisioning을 다시 만들기보다 선택된 Node의 Data LIF·Route·2049·NFS Client·Export Policy 경계를 확인합니다.

---

# 6. Pod Running — 실제 PVC가 Mount됐는지 확인한다

> Pod가 Running이면 Container가 시작됐다는 뜻입니다.
>
> **하지만 잘못된 `emptyDir`나 Container 내부 Local Path를 사용해도 Pod는 Running일 수 있습니다.**
>
> 그래서 먼저 Pod Spec에서 PVC Claim이 어떤 `volume`에 연결되고, 그 Volume이 Container의 어떤 `volumeMount`와 MountPath에 연결되는지 확인합니다.
>
> 그다음 Container 안에서 실제 Mount Source·Path·Filesystem·Capacity를 봅니다. Test Data를 쓸 경로가 Pod Spec에서 지정한 Persistent Volume MountPath와 같은지 확인해야 합니다.
>
> 같은 이름의 디렉터리가 Container Image 안에 원래 존재하거나 Local Filesystem으로 보이는 경우도 있으므로 경로가 보인다는 사실만으로 PVC Mount 성공이라고 판단하지 않습니다.
>
> 그래서 Filesystem과 Capacity, Mount Source를 같이 보고 현재 경로가 실제 Persistent Volume인지 확인합니다.
>
> 반대로 Pod가 Running인데 PVC Volume이 Pod Spec에 연결되지 않았거나 다른 MountPath를 보고 있다면 그 상태에서 Write 시험을 해도 Storage 검증 증거가 되지 않습니다.
>
> 따라서 Pod Running은 Container 기동 성공으로만 보고, 실제 PVC가 Container의 의도한 경로에 Mount됐다는 것을 확인한 뒤 Write 시험으로 넘어갑니다.

---

# 7. Write와 Read — Mount된 Filesystem을 실제로 사용한다

> Volume이 Container에 Mount돼 있어도 실제 Application이 그 Filesystem을 정상적으로 사용할 수 있다는 것은 아직 확인하지 않았습니다.
>
> 먼저 Mount Path의 Permission과 Read-only 여부를 확인하고, 실제 Test Data를 쓸 수 있는 조건인지 봅니다.
>
> Mount돼 있어도 UID/GID, Directory Permission, Read-only 설정이나 Filesystem 문제 때문에 쓰기가 실패할 수 있습니다.
>
> 그래서 실제 Persistent Volume Mount 경로에 현재 Cluster와 시험 시점을 구분할 수 있는 Test Data를 씁니다. 민감정보나 운영 데이터를 Test Data로 사용하지 않습니다.
>
> Write가 성공하면 Container가 해당 Filesystem에 실제 데이터를 기록할 수 있다는 것을 확인한 것입니다.
>
> **하지만 Write 명령의 Return Code가 0이라는 사실만으로 저장된 내용이 기대한 값과 같은지는 알 수 없습니다.**
>
> 그다음 같은 경로에서 다시 읽고 작성한 내용과 같은지 확인합니다. 필요하면 파일 크기와 Checksum도 같이 봅니다.
>
> 반대로 Read는 되지만 새 Write가 실패한다면 Provisioning이나 Mount 자체보다 Read-only 설정, Permission과 UID/GID 같은 사용 권한 경계를 먼저 봅니다.
>
> 따라서 Write와 Read를 하나의 명령 성공으로 묶지 않고, 기록 가능 여부와 기록한 데이터의 재확인을 각각 증적으로 남깁니다.

## 7-1. 즉시 Read와 Persistence 확인은 증거 범위가 다르다

> 같은 Pod에서 Write 직후 Read하는 것은 현재 Mount된 Filesystem에서 데이터를 쓰고 다시 읽을 수 있다는 것을 증명합니다.
>
> 하지만 같은 Container와 같은 Mount Session 안에서 읽은 결과만으로 Pod가 다시 만들어진 뒤에도 데이터가 유지된다고 판단하지 않습니다.
>
> 그래서 승인된 시험 범위가 Persistence 확인을 포함한다면 Test Pod를 안전하게 재생성하거나 별도의 Reader Pod에서 같은 PVC를 Mount한 뒤 이전 데이터를 다시 읽습니다.
>
> 그다음 이전에 기록한 내용과 파일 크기 또는 Checksum이 같은지 확인합니다.
>
> 이 과정에서 PVC와 PV를 삭제하지 않고 Pod만 재생성해야 합니다. PVC까지 삭제하면 `reclaimPolicy`에 따라 실제 Backend Volume이 삭제될 수 있으므로 Persistence 시험과 Cleanup을 섞지 않습니다.
>
> 따라서 즉시 Write·Read는 현재 Filesystem 사용 가능성을 확인하고, 재연결 후 Read는 Pod 수명과 분리된 Persistent Storage의 데이터 유지까지 한 단계 더 확인합니다.

---

# 8. Cleanup — 삭제 요청과 실제 정리 결과는 다르다

> 시험이 끝나면 Test Pod·PVC와 Namespace를 승인된 순서로 정리합니다.
>
> 먼저 삭제 대상이 이번 시험에서 만든 Resource가 맞는지 다시 확인합니다. 이름이 비슷하거나 운영 PVC일 가능성이 있으면 Cleanup을 진행하지 않습니다.
>
> 그다음 Test Pod를 정리하고 PVC 삭제 전 현재 PVC·PV·VolumeHandle과 `reclaimPolicy`를 다시 확인합니다. 삭제 전 상태를 남겨야 이후 어떤 Backend Volume이 정리 대상이었는지 연결할 수 있습니다.
>
> PVC를 삭제하면 Kubernetes에서는 Claim이 사라지지만 실제 PV와 Backend Volume의 처리는 `reclaimPolicy`에 따라 달라집니다.
>
> `Delete` 정책이면 PVC 삭제 뒤 PV와 의도한 Test Backend Volume이 정상적으로 정리되는지 확인합니다.
>
> **하지만 PVC 삭제 명령이 성공했다는 것만으로 Backend Volume까지 제거됐다고 판단하지 않습니다.** PV 상태와 Trident 또는 Storage 쪽 실제 Volume 결과를 이어서 확인해야 합니다.
>
> 반대로 `Retain`이면 PV나 Backend Volume이 남는 것이 정상일 수 있습니다. 이 경우 잔여 Resource를 실패로 처리하지 않고 담당자와 후속 정리 책임을 기록합니다.
>
> Finalizer가 남아 Resource가 Terminating 상태라고 바로 강제 제거하지 않습니다. 먼저 어떤 Controller가 정리 작업을 끝내지 못했는지와 실제 Backend Volume 상태를 확인합니다.
>
> 그리고 Namespace는 그 안의 Test Resource 정리가 끝난 뒤 마지막에 정리합니다. Namespace부터 삭제해 내부 Resource 상태를 보기 어렵게 만들지 않습니다.
>
> 따라서 Cleanup은 단순한 환경 정리가 아니라 StorageClass에서 확인한 Lifecycle 정책이 PVC·PV·Backend Volume에 실제로 적용되는지 확인하는 마지막 기능 검증입니다.

---

# 9. 문제가 생기면 Storage 사용 순서대로 확인한다

> Storage 검증에서 가장 먼저 지켜야 하는 원칙은 첫 실패 단계보다 뒤쪽을 먼저 고치지 않는 것입니다.
>
> 먼저 PVC가 `Pending`이면 StorageClass·Provisioner·Backend와 PVC Event를 봅니다. 이 단계에서는 아직 실제 Node Mount가 시작되지 않았을 수 있으므로 NFS Route나 Export Policy부터 수정하지 않습니다.
>
> 그다음 PVC가 `Bound`인데 Pod가 아직 Scheduling되지 않았다면 Selector·Taint·Resource·Binding Mode와 Scheduler Event를 봅니다. Node가 정해지지 않은 상태는 Mount 실패와 구분해야 합니다.
>
> PVC는 Bound이고 Pod Node도 정해졌는데 `ContainerCreating`이나 `FailedMount`가 발생하면 Pod Event의 NFS Source와 Export Path를 기준으로 Node Source IP·Route·TCP 2049·NFS Client·Export Policy를 확인합니다.
>
> 그래서 이 단계에서는 PVC를 다시 만들기보다 이미 성공한 Provisioning 결과를 보존하고 실제 Mount Data Path를 따라갑니다.
>
> 반대로 Pod가 Running인데 Persistent Volume이 의도한 MountPath에 보이지 않는다면 Write 시험을 시작하지 않습니다. Pod Spec의 PVC·Volume·`volumeMount`와 Container 안의 실제 Mount Source를 다시 확인합니다.
>
> Mount는 정상인데 Write가 실패하면 Provisioning이나 Backend부터 다시 확인하지 않고 Permission·UID/GID·Read-only·Filesystem·Mount Option을 봅니다.
>
> Write와 즉시 Read는 성공했는데 재연결 후 이전 데이터가 보이지 않는다면 같은 PVC를 다시 사용했는지와 실제 Persistent Volume 연결을 먼저 확인합니다.
>
> 그리고 Cleanup 뒤 Volume이 기대와 다르게 남거나 사라지지 않으면 `reclaimPolicy`, PV 상태, Finalizer와 Backend Volume 정리 결과를 확인합니다.
>
> 따라서 확인 순서는 `PVC → PV → Scheduling → Node Mount → Container Mount → Write·Read → Persistence → Cleanup`을 유지하고, 이미 통과한 앞 단계를 이유 없이 다시 변경하지 않습니다.

---

# 10. 9월 3일 Monitoring 진입 Gate를 판정한다

> 9월 2일 Storage 검증은 Test PVC 하나를 성공시키는 것으로 끝나지 않습니다. 다음 날 Monitoring Workload가 같은 신규 Member에서 실제 Persistent Storage를 사용할 수 있는지 판단할 수 있어야 합니다.
>
> 먼저 `STORAGE PASS`는 Backend와 StorageClass가 승인된 기준으로 준비되고 Test PVC가 실제 PV로 Provisioning된 상태에서 시작합니다.
>
> 그다음 선택된 Node에서 Volume이 Mount되고 Container Write·Read가 성공해야 합니다. 승인 범위에 Persistence 확인이 포함됐다면 Pod 재생성 또는 Reader Pod에서도 같은 데이터를 다시 읽을 수 있어야 합니다.
>
> 그리고 Cleanup 결과가 `reclaimPolicy`와 일치해야 합니다. Test Resource를 남긴 채 성공으로 넘기거나, 실제 Backend Volume 정리 여부를 확인하지 않은 상태로 다음 날 작업을 시작하지 않습니다.
>
> 다음 날 Monitoring이 Infra Node에 배치될 예정이라면 Infra Node의 Trident Node Plugin, NFS Client, Data LIF Route와 Export 조건도 확인해야 합니다.
>
> **하지만 Worker Node에서 Test Pod가 성공했다는 사실만으로 Infra Node의 Storage Data Path까지 성공했다고 판단하지 않습니다.** Node Role과 Network 조건이 다를 수 있기 때문입니다.
>
> 그래서 Monitoring이 사용할 Namespace·StorageClass·PVC 용량·예상 Node Role을 다음 날 시작 전에 확정합니다.
>
> 반대로 Backend offline, PVC Pending, FailedMount, 실제 PVC Mount 미확인, Write·Read 실패, Persistence 미확인 항목, Infra Node Data Path 미확정이나 Cleanup 위험이 남아 있으면 `BLOCKED`입니다.
>
> 따라서 `STORAGE PASS`는 하나의 Kubernetes Status가 아니라 Provisioning·Scheduling·Mount·Container 사용·Persistence·Lifecycle이 현재 신규 Member의 실제 조건에서 연결됐다는 판정입니다.

---

# 11. Monitoring에는 실제 Storage 결과를 넘긴다

> 다음 날에는 Cluster·Context와 `STORAGE PASS / BLOCKED` 결과를 넘깁니다.
>
> Trident·Backend·StorageClass 기준과 Test PVC·PV·VolumeHandle·NFS Source를 전달합니다.
>
> 배치 Node, 실제 Mount Path, Write·Read와 Persistence 결과도 이어갑니다.
>
> Worker에서만 시험했다면 그 결과로 Infra Node 성공을 대신하지 않고, Monitoring이 사용할 Infra Node의 Node Plugin·NFS Package·Route·Export 조건을 별도로 확인해 함께 남깁니다.
>
> Infra Node 조건과 Cleanup 결과, Monitoring Namespace·StorageClass·PVC 용량·예상 Role도 함께 남깁니다.
>
> Credential과 Secret 원문은 제외합니다.

---

# 12. 마무리

> 오전에는 Storage 공급 준비를 확인했지만 실제 사용은 별도였습니다.
>
> 그래서 PVC로 요청하고 PV와 Backend Volume을 확인했습니다.
>
> 그다음 Pod가 배치된 Node에서 NFS Mount를 확인하고, Container 안의 실제 Persistent Path에 데이터를 쓰고 읽었습니다.
>
> 마지막으로 필요한 Persistence와 `reclaimPolicy`에 맞는 Cleanup을 확인했습니다.
>
> **결국 STORAGE PASS는 PVC가 Bound인 화면이 아니라, 현재 신규 Member의 Application이 실제 Persistent Volume을 사용하고 그 Lifecycle이 정상인 상태입니다.**
