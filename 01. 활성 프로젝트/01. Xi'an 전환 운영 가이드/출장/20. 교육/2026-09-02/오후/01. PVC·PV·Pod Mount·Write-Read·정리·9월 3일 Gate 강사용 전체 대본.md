# PVC·PV·Pod Mount·Write-Read·정리·9월 3일 Gate 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 오전의 `STORAGE SUPPLY PASS`를 입력으로 받아 **실제 PVC 요청이 PV로 Provisioning되고, 9월 3일 Monitoring이 배치될 Node에서 Pod가 Volume을 Mount하며, Container가 데이터를 쓰고 다시 읽고, 테스트 삭제 후 정리 동작까지 기대대로 일어나는지 증명하는 법**을 가르친다. 정확한 PVC·Pod Manifest와 Storage 변경 명령은 원본 Storage Runbook을 따른다.

## 0. 오전에서 이어받는 것

```text
Cluster Name·Stage·Context
STORAGE SUPPLY PASS / BLOCKED
Snapshotter·Trident 상태
Node Plugin 대상·Ready
Backend Name·State·SVM·Data LIF
StorageClass 이름·Provisioner·reclaimPolicy·volumeBindingMode
9/3 Monitoring 대상 Node Role
Test Namespace·PVC 용량 승인 기준
정리 계획
```

> 오전이 `BLOCKED`라면 오후 Test PVC를 만들지 않습니다.

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> `PVC Bound`를 Storage 완료로 확대하지 않고, **PVC → PV·VolumeHandle → Pod Scheduling Node → Node Mount → Container Filesystem → Write → Read-back → 재읽기 → Cleanup**의 각 성공 단계를 별도 증거로 연결할 수 있어야 한다.

오늘의 중심 질문:

> **실제 Pod가 이 Storage를 Mount하고 데이터를 쓰고 다시 읽으며, 기대한 정리 동작까지 수행할 수 있는가?**

---

# 1. 시작 — `Bound`는 공급 성공이지 사용 성공이 아니다

오늘 가장 중요한 구분:

```text
PVC Bound
→ Kubernetes·CSI가 요청을 실제 Volume과 연결하는 단계까지 성공

Pod Mount 성공
→ 선택된 Node가 실제 Storage 경로를 Container에 붙이는 단계까지 성공

Write·Read 성공
→ Application이 그 Filesystem을 실제로 사용할 수 있음
```

따라서:

```text
PVC Bound
≠ Pod Mount

Pod Running
≠ 의도한 Volume이 실제 경로에 Mount

Mount 성공
≠ Write 가능
```

> 이 세 경계를 끝까지 분리하는 것이 9월 2일의 핵심입니다.

---

# 2. Test Scenario는 9월 3일 실제 사용 조건과 연결한다

> 편한 Worker 한 대에서만 성공시키는 Test는 9월 3일 Monitoring Storage의 충분한 선행조건이 아닐 수 있습니다.

Test 조건을 먼저 고정한다.

```text
Test Namespace: _________________________________________
StorageClass: ____________________________________________
PVC 요청 용량: __________________________________________
AccessMode: ______________________________________________
Test Pod Image: __________________________________________
Test Pod 배치 Role: ______________________________________
9/3 Monitoring 배치 Role과 관계: _________________________
Write할 고유 Test File: __________________________________
Cleanup 시 기대 reclaim 동작: ____________________________
승인자·실행자: __________________________________________
```

원칙:

```text
9/3 Monitoring이 Infra Node에 배치된다면
→ Infra Storage 경로를 실제로 검증
```

> Role별 NFS Route·Firewall·Export Policy가 다를 수 있으므로 다른 Role의 성공을 자동 확대하지 않습니다.

---

# 3. PVC — 요청과 Event를 함께 본다

승인된 Runbook의 Test PVC Manifest를 적용한다.

먼저 확인할 질문:

```text
의도한 Namespace인가
의도한 StorageClass인가
의도한 요청 용량인가
AccessMode가 승인 용도와 맞는가
```

대표 조회:

```bash
kubectl -n <test-namespace> get pvc -o wide
kubectl -n <test-namespace> describe pvc <test-pvc>
```

## 3.1 PVC Pending이면 아직 Mount 문제가 아니다

```text
PVC Pending
→ Provisioning 경로에서 아직 Volume 할당이 완료되지 않음
```

첫 확인:

```text
StorageClass 이름·Provisioner
PVC Event
Trident Controller 상태
Backend state
Quota·요청 조건
volumeBindingMode와 Scheduling 선행조건
```

> Pending인데 Worker Route나 NFS Export Policy부터 보지 않습니다. 아직 Node Mount 단계에 도달하지 않았을 수 있습니다.

---

# 4. PVC Bound — 대응 PV와 실제 Volume Identity를 연결한다

PVC가 Bound되면 다음을 확인한다.

```text
PVC 이름
→ 연결된 PV 이름
→ StorageClass
→ Capacity·AccessMode
→ CSI Driver
→ VolumeHandle
→ 실제 Storage Volume·Export를 식별할 근거
```

대표 조회:

```bash
kubectl -n <test-namespace> get pvc <test-pvc> -o yaml
kubectl get pv <bound-pv> -o yaml
```

> Secret Data나 Credential은 출력·증적에서 마스킹합니다.

## 4.1 Bound의 증거 범위

```text
PVC Bound
→ Provisioning 성공
→ PVC와 PV 연결
```

하지만:

```text
PVC Bound
≠ 어느 Node에서도 NFS Mount 가능
```

> 이제부터 실패 경계가 공급 경로에서 실제 소비 Node 경로로 이동합니다.

---

# 5. Test Pod — 어느 Node에서 Mount를 시도하는지 먼저 고정한다

승인된 Test Pod Manifest는 PVC를 실제 Container 경로에 Mount하고, 9월 3일 사용 조건과 가능한 한 같은 Role에 배치한다.

확인:

```bash
kubectl -n <test-namespace> get pod <test-pod> -o wide
kubectl -n <test-namespace> describe pod <test-pod>
```

먼저 기록한다.

```text
Pod: _____________________________________________________
Scheduled Node: __________________________________________
Node Role: _______________________________________________
PVC: _____________________________________________________
Container MountPath: _____________________________________
Pod Status: ______________________________________________
Event의 Storage 관련 문장: _______________________________
```

> Mount 실패를 조사할 때 **어느 Node가 Source가 되어 어느 NFS 경로를 붙이려 했는지**가 핵심입니다.

---

# 6. `Bound + FailedMount`는 모순이 아니다

```text
PVC Bound
→ Volume 준비 성공

Pod FailedMount
→ 선택된 Node의 실제 Mount 경로 실패
```

따라서 다음 질문으로 이동한다.

```text
Event가 요청한 Server·Path는 무엇인가
PV·CSI 정의와 같은가
Pod가 어느 Node에 배치됐는가
그 Node Source IP에서 Data LIF까지 Route가 있는가
TCP 2049 경로가 가능한가
Export Policy가 실제 Source를 허용하는가
```

## 6.1 Kubernetes·Network·ONTAP 책임 경계를 분리한다

| 관찰 | 다음 확인 영역 |
|---|---|
| PVC Pending | Kubernetes·Trident Provisioning |
| Server·Path 정의 불일치 | Kubernetes Object·Trident |
| Route 없음·Timeout | Node Network |
| TCP 2049 불가 | Network·Firewall |
| `access denied by server` | 실제 Source IP·Export Policy |
| Mount option 오류 | PV·StorageClass·Node Mount 조건 |

> 원본 6.3 Troubleshooting Guide와 연결하되, 과거 사례의 원인을 현재 장애의 확정 원인으로 복사하지 않습니다.

---

# 7. Pod Running 뒤에 실제 Mount를 확인한다

> Pod가 Running이면 좋지만 Volume이 의도한 경로에 실제 Mount됐는지 별도 확인합니다.

Container 내부에서 현재 Runbook이 승인한 명령으로 확인한다.

예:

```text
Filesystem·MountPath 확인
→ 기대 Volume이 해당 경로에 연결됐는가
```

대표적인 확인 도구는 `df`, `mount`, `findmnt` 등이지만 현재 Image에 존재하는 승인 Tool을 사용한다.

구분:

```text
Pod Running
≠ MountPath가 기대 Volume
```

> Application이 Volume 없이도 시작될 수 있는 구조라면 특히 이 확인이 중요합니다.

---

# 8. Write·Read-back — Application 사용 가능성을 실제로 증명한다

> Mount만 됐다고 데이터 사용이 가능한 것은 아닙니다. Filesystem 권한, Export 정책, Mount option 등의 문제로 쓰기가 실패할 수 있습니다.

승인된 고유 Test File 하나만 사용한다.

원칙:

```text
고유 파일명
기존 파일 덮어쓰기 금지
작은 Test Data
비민감 내용
정리 계획
```

검증 흐름:

```text
MountPath에 Test File Write
→ 즉시 Read-back
→ 내용 일치 확인
```

증거:

```text
Write 성공
+ Read-back 내용 일치
```

하지만:

```text
한 번의 Write·Read
≠ 재시작 뒤에도 같은 Storage 사용을 완전히 증명
```

---

# 9. 가능하면 재읽기로 영속 경계를 확인한다

> 테스트 영향과 일정이 허용되면 승인된 방식으로 Pod를 재생성하거나 별도 Reader Pod를 사용해 같은 PVC를 다시 Mount하고 기존 Test File을 읽습니다.

이 단계가 답하는 질문:

```text
Container Process의 로컬 파일이 아니라
실제 Persistent Volume에 기록됐는가
```

구분:

```text
같은 Container에서 즉시 Read 성공
≠ 새 Pod에서도 데이터 유지
```

> 재생성 방식과 영향은 Runbook을 따른다. 운영 Workload를 임의 재시작하지 않습니다.

---

# 10. 한 Node 성공을 전체 Role 성공으로 확대하지 않는다

9월 3일 Monitoring Pod가 특정 Infra Node군에 배치될 수 있다면 필요한 범위를 판단한다.

```text
Worker Test 성공
≠ Infra Node NFS 경로 성공
```

가능한 검증 방식:

```text
9/3 실제 배치 대상 Role의 대표 Node에서 Test
또는
모든 잠재 배치 Node의 Route·2049·Trident Node Plugin 조건을 별도 확인
```

> 어떤 범위를 실제 Pod Mount로 검증해야 하는지는 현재 배치 정책과 Replica 수를 기준으로 정합니다.

---

# 11. Test PVC 성공과 9월 3일 Monitoring PVC 성공을 구분한다

같은 StorageClass를 써도 다음 조건이 다를 수 있다.

```text
Namespace
PVC 요청 용량
Quota
AccessMode
volumeBindingMode
Pod Node Selector·Taint
실제 배치 Node
```

따라서:

```text
Test PVC·Pod 성공
→ Storage 기반 기능 증거
```

하지만:

```text
Test 성공
≠ 모든 Monitoring PVC 자동 성공
```

9월 3일용으로 별도 확정할 것:

```text
Monitoring Namespace
Prometheus PVC 용량
Alertmanager PVC 용량
Grafana PVC 필요 여부·용량
사용 StorageClass
배치 Node Role
Quota·정책
```

---

# 12. Cleanup — 삭제 요청과 실제 정리를 구분한다

> Test 성공 뒤 Resource를 삭제할 때도 Storage 동작을 검증할 기회입니다.

정리 전에 증거를 보존한다.

```text
PVC·PV 이름
VolumeHandle
Pod·Node
NFS source/export path
Write·Read 결과
Test File 이름
```

그다음 승인된 Runbook으로 Test Pod와 PVC를 삭제한다.

확인:

```text
Pod 제거
PVC 제거
PV 상태 변화
Backend Volume 상태
reclaimPolicy 기대 동작
잔여 Test Resource 없음
```

## 12.1 reclaimPolicy와 실제 결과

```text
reclaimPolicy=Delete 등 승인 정책
≠ Delete 요청 즉시 Backend Volume 정리 완료
```

> 실제 PV·Backend Volume이 기대 상태로 전환됐는지 확인합니다.

## 12.2 정리 위험이 보이면 강제 삭제하지 않는다

```text
예상과 다른 PV가 연결됨
기존 데이터 Volume으로 보임
삭제 대상 식별 불명확
Backend Volume 잔여 원인 미확정
```

이면 추가 삭제를 멈춘다.

---

# 13. STORAGE PASS를 판정한다

9월 2일 종료는 두 상태만 사용한다.

## 13.1 STORAGE PASS

```text
STORAGE SUPPLY PASS
+ Test PVC가 승인 StorageClass로 Bound
+ 대응 PV·CSI Driver·VolumeHandle 확인
+ Test Pod가 9/3 사용 조건과 관련된 Node에 배치
+ Pod Event에 미해결 FailedMount 없음
+ 실제 Volume Mount 확인
+ Container Write 성공
+ Read-back 내용 일치
+ 승인 범위에서 영속 재읽기 확인
+ 필요한 Monitoring 배치 Role의 Storage 경로 확인
+ Cleanup·reclaim 동작 기대대로 확인
+ 9/3 Monitoring StorageClass·Namespace·용량 확정
+ Critical Storage Error 없음
```

> 이 판정은 **9월 3일 Monitoring·KubeSphere가 사용할 Storage 기반을 시작할 수 있음**을 뜻합니다.

## 13.2 BLOCKED

```text
PVC Pending 원인 미해결
PV·VolumeHandle 실제값 불일치
Pod FailedMount 미해결
9/3 대상 Node에서 NFS 경로 미검증·실패
MountPath 실제 Volume 확인 실패
Write 또는 Read-back 실패
필요한 영속성 확인 실패
Cleanup·reclaim 동작 위험 미확정
Monitoring StorageClass·Namespace·용량 미확정
Kubernetes·Network·ONTAP 중 담당 경계 미확정으로 핵심 기능 차단
```

> BLOCKED 상태에서 9월 3일 Monitoring Stack을 올려 실패 원인을 더 복잡하게 만들지 않습니다.


> 9월 3일 첫 블록은 이 결과를 입력으로 받아 Monitoring Storage를 구성합니다.

---

# 15. 마무리 — Storage 완료를 한 문장으로 다시 말한다

> StorageClass가 보이고 PVC가 Bound되는 것은 중요한 중간 성공입니다.
>
> 하지만 실제 Application이 Storage를 사용하려면 Pod가 배치된 Node에서 CSI와 NFS 경로가 성립하고, Container의 MountPath에 실제 Filesystem이 붙으며, 데이터를 쓰고 다시 읽을 수 있어야 합니다.
>
> 테스트가 끝난 뒤에는 PVC·PV와 Backend Volume의 정리 동작도 승인 정책과 맞아야 합니다.
>
> **결국 9월 2일 완료는 PVC 상태가 Bound인 화면이 아니라, 9월 3일 실제 플랫폼 Workload와 같은 조건에서 Storage를 Mount·Write·Read하고 안전하게 정리할 수 있음을 증명한 상태입니다.**

# 16. 마지막 Teach-back

1. PVC `Bound`는 정확히 어디까지의 성공을 뜻하는가?
2. `Bound + FailedMount`가 동시에 가능한 이유는 무엇인가?
3. Pod가 어느 Node에 배치됐는지를 Mount 장애에서 먼저 확인해야 하는 이유는 무엇인가?
4. NFS Mount 실패에서 Route·TCP 2049·Source IP·Export Policy는 어떻게 연결되는가?
5. Pod Running 뒤에도 실제 MountPath를 확인해야 하는 이유는 무엇인가?
6. Write와 Read-back을 별도로 확인해야 하는 이유는 무엇인가?
7. Test PVC 성공을 Monitoring PVC 성공으로 자동 확대하면 안 되는 이유는 무엇인가?
8. Worker의 성공을 Infra Node 성공으로 확대하면 안 되는 경우는 언제인가?
9. Cleanup과 reclaim 결과가 Storage 검증의 일부인 이유는 무엇인가?
10. 어떤 조건이 남으면 9월 3일을 BLOCKED해야 하는가?
