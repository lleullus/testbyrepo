# 기존 Host Join·Multi-Cluster 기능 검증 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 오전 `MEMBER SELF PASS`를 입력으로 받아 **기존 Xi'an Host Cluster가 신규 Member를 실제로 관리·관측할 수 있는 Multi-Cluster 연결이 성립했는지 증명하는 법**을 가르친다. 기존 Host를 재설치하거나 공통 설정을 불필요하게 바꾸지 않는다. Join의 정확한 UI·Manifest·보호값 처리 절차는 현재 Host/Member Runbook을 따른다.

## 0. 오전에서 이어받는 것

```text
Cluster Name·Stage·Context
MEMBER SELF PASS / BLOCKED
KUBERNETES BASE PASS
STORAGE PASS
MONITORING PASS
KubeSphere Console·API 정상
clusterRole=member
External Monitoring 정상
Platform Workload 배치 정상
Member VIP-A·VIP-B·Domain
Join에 필요한 보호값 종류·전달 절차
```

> `MEMBER SELF PASS`가 아니면 Join하지 않습니다. Member 자체 장애를 Host 연결 문제로 보이게 만들지 않습니다.

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> Host Console에 Cluster 이름이 보이는 것만으로 Join 성공을 선언하지 않고, **기존 Host 자체 정상 → Join Identity·보호정보 → Agent·연결 Component → Host Console 상태 → Member Resource 조회 → Monitoring 관측 → 기존 Member 회귀 없음**을 독립 증거로 확인할 수 있어야 한다.

오늘의 중심 질문:

> **Host가 신규 Member를 목록에 추가한 것이 아니라 실제로 관리·관측할 수 있으며, 기존 Multi-Cluster 환경에 회귀를 만들지 않았다는 것을 무엇으로 증명할 것인가?**

---

# 1. 시작 — Join은 UI 목록 추가가 아니다

정상 의미:

```text
신규 Member 자체 정상
+ 기존 Host 자체 정상
+ 현재 Member Identity로 Join
+ Host↔Member Network·DNS·TLS·인증
+ 연결 Agent·Component 정상
= Host가 Member를 실제로 관리·관측
```

반드시 구분한다.

```text
Host Console에 Cluster 이름 표시
≠ Multi-Cluster 기능 정상

Cluster Status 정상
≠ Resource 조회·관리 정상

Resource 조회 가능
≠ Monitoring 관측 정상

신규 Member Join 성공
≠ 기존 Member 영향 없음
```

---

# 2. Join 전에 기존 Host는 읽기 전용으로 정상 기준을 고정한다

> 이번 출장에서 기존 Host는 신규 구축 대상이 아닙니다. Join 전 기준 상태를 기록해 Join 후 회귀를 비교할 수 있게 합니다.

확인할 최소 항목:

```text
Host Cluster Identity
Host KubeSphere Console·API 접근
clusterRole=host
기존 PRD·DEV Member 목록·Status
기존 Member 주요 Resource 조회 가능
기존 Multi-Cluster Component 상태
신규 Member Name 중복 여부
Join 수행 권한·승인자
Host↔신규 Member Network·DNS 전제
```

## 2.1 기존 Host의 성공을 신규 Member 증거로 쓰지 않는다

```text
기존 PRD Member Status 정상
≠ 신규 Member Join 가능
```

반대로:

```text
기존 Host 자체 비정상
≠ 신규 Member Join 문제
```

> Join 전 Host 문제가 있으면 먼저 영향 범위를 분리합니다.

---

# 3. Join Identity를 고정한다

```text
신규 Member Cluster Name: ________________________________
Stage: ___________________________________________________
Member clusterRole: member
Host Cluster Name: _______________________________________
Host clusterRole: host
Join 경로·방식: __________________________________________
Join 승인자: _____________________________________________
실행 시각: _______________________________________________
```

확인 규율:

```text
Cluster Name이 기존 Cluster와 중복되지 않음
Stage·Tag가 현재 Member와 일치
과거 PRD·DEV Member 이름을 재사용하지 않음
```

> 이름이 잘못되면 나중에 Monitoring Label과 운영 대상 선택까지 혼동됩니다.

---

# 4. 보호된 Join 정보는 값보다 전달 경계를 관리한다

보호 대상 예:

```text
Join Secret
JWT
kubeconfig
Token
Private Key
Password
```

교육·증적에 기록할 수 있는 것:

```text
값의 종류
발급·확인 시각
전달자·수신자 역할
승인된 전달 방식
사용 성공 여부
폐기·Rotation 필요 여부
```

기록하지 않을 것:

```text
실제 Secret Data
Token·JWT 원문
kubeconfig 원문
Private Key
Password
```

> 보호값을 화면 공유·채팅·Shell History에 남기지 않습니다.

## 4.1 값 이름이 같아도 현재 Member 값인지 별도 확인한다

```text
Secret 이름 동일
≠ 현재 Member Join 정보
```

> 과거 Member의 Join 값을 재사용하지 않습니다.

---

# 5. Join 전 Network는 양방향 필요한 경로를 확인한다

Multi-Cluster 연결에는 환경에 따라 여러 방향 통신이 필요할 수 있다.

확인 질문:

```text
Host가 Member API·필요 Endpoint에 접근 가능한가
Member가 Host 연결 Endpoint에 접근 가능한가
DNS가 양쪽에서 승인 주소를 반환하는가
TLS Certificate가 현재 FQDN과 맞는가
필요 Port·Firewall 정책이 승인됐는가
Proxy 영향이 없는가
```

구분:

```text
Ping 또는 TCP 한 Port 성공
≠ Join 전체 통신 정상
```

> 실제 Join 방식이 사용하는 Endpoint·Port만 Runbook 기준으로 확인합니다. 필요하지 않은 방화벽을 넓히지 않습니다.

---

# 6. Join 적용 뒤 먼저 연결 Component를 본다

실제 Join 방식에 따라 Member Agent와 Host 측 Multi-Cluster Component가 생성·갱신될 수 있다.

확인:

```text
Member 측 연결 Agent Pod·Deployment
Host 측 관련 Component
Ready·Restart
Event
Log의 최초 오류
현재 Member Identity
```

구분:

```text
Agent Pod Running
≠ Registration 완료

Registration 완료
≠ Host에서 Member Resource 조회 가능
```

## 6.1 Agent가 Pending이면

```text
Node Selector·Taint
PVC 필요 여부
Image Pull
Resource Request
Scheduler Event
```

## 6.2 Agent가 Running이지만 연결 실패면

```text
Host Endpoint
DNS·Network·TLS
보호된 Join 정보 유효성
Cluster Identity
Log의 최초 연결 오류
```

> Member KubeSphere 전체를 재설치하지 않습니다.

---

# 7. Host Console 등록 상태는 첫 번째 UI 증거일 뿐이다

확인:

```text
신규 Member 이름이 한 번만 표시
Stage·Identity 정확
Status 정상 또는 현재 Runbook의 기대 상태
등록 시각과 Join 시각 연결
```

하지만:

```text
목록 표시
≠ Node·Namespace·Workload 조회 정상
```

> 다음 실제 관리 경로를 확인해야 합니다.

---

# 8. Host에서 Member Resource를 실제로 조회한다

검증할 최소 Resource:

```text
Node 수·Role
Namespace·Project
대표 Workload 상태
필요한 KubeSphere Resource
```

대조:

```text
Host에서 본 Member Node 수·Role
↔ Member 자체 kubectl 결과
```

```text
Host에서 본 Workload
↔ Member 자체 KubeSphere·kubectl 결과
```

> Host에서 다른 Member를 선택한 결과를 신규 Member 증거로 사용하지 않습니다.

## 8.1 조회 성공과 관리 권한을 구분한다

```text
조회 가능
≠ 모든 변경 권한 정상
```

현재 인수 범위에서 필요한 승인된 관리 기능만 확인한다. 불필요한 운영 Resource 변경을 Test로 만들지 않는다.

---

# 9. Host에서 Member Monitoring을 실제로 관측한다

Monitoring은 오늘 오전 이미 Member 자체에서 `MONITORING PASS`를 받았다.

Host 측에서 추가로 확인할 것은:

```text
현재 신규 Member를 선택했을 때 Metric이 보이는가
Cluster Label이 신규 Member인가
Node·Workload Metric이 Member 실제 상태와 대략 일치하는가
최근 데이터가 있는가
기존 PRD·DEV Metric과 섞이지 않는가
```

구분:

```text
Host에서 Resource 조회 성공
≠ Monitoring 관측 성공
```

## 9.1 Monitoring이 안 보이면 Storage부터 재설치하지 않는다

첫 분기:

```text
Member 자체 Prometheus Query 정상인가
Host가 참조하는 Metric Endpoint는 무엇인가
Cluster External Label이 맞는가
Multi-Cluster Monitoring Component가 정상인가
```

> Member 자체 Monitoring PASS가 유지되면 Host↔Monitoring 통합 경계를 먼저 봅니다.

---

# 10. Host와 Member 양쪽 Console·API를 구분한다

```text
Member 자체 Console·API
→ Member Platform 자체 정상

Host Console에서 Member 관리
→ Multi-Cluster 연결 정상
```

둘 다 필요하다.

```text
Host에서 Member 보임
≠ Member 자체 KubeSphere 정상

Member 자체 Console 정상
≠ Host Join 정상
```

> 오전 `MEMBER SELF PASS` 증거와 오후 Host 결과를 같이 인수 자료에 남깁니다.

---

# 11. 기존 Member 회귀를 반드시 확인한다

> Host Join은 기존 Host의 Multi-Cluster 공통 영역과 연결됩니다. 신규 Member가 정상이어도 기존 PRD·DEV Member에 영향을 주면 최종 성공이 아닙니다.

Join 전후 대조:

```text
기존 Member 목록·Status
기존 Member Resource 조회
기존 Member Monitoring 관측
Host 공통 Component Restart·Error
```

구분:

```text
신규 Member 정상
≠ 기존 Member 회귀 없음
```

## 11.1 기존 Member 영향이 보이면

즉시 추가 Join·Host 공통 변경을 멈춘다.

확인:

```text
Join 과정에서 Host 공통 Config 변경이 있었는가
Multi-Cluster Component가 Restart·Error 상태인가
기존 Member 인증·Endpoint에 공통 영향이 있는가
```

> 기존 Member까지 동시에 수정하지 않습니다. 신규 Join과 영향 관계를 먼저 고정합니다.

---

# 12. Join 실패는 마지막 성공으로 분기한다

| 증상 | 첫 확인 |
|---|---|
| Host Console에 신규 Member 없음 | Join 요청·Identity·권한·보호값·Host Component |
| 이름은 보이나 Status 비정상 | Member 자체 상태·Agent·Host→Member Network·TLS |
| Resource 조회 실패 | 권한·API·Agent·Cluster 선택 |
| Resource는 보이나 Monitoring 없음 | Member Monitoring·Endpoint·Label·통합 Component |
| 기존 Member 영향 | Host 공통 Component·Config 변경·회귀 범위 |

> `Join 실패` 하나로 묶지 않고 어디까지 성공했는지 먼저 말합니다.

---

# 13. MULTI-CLUSTER PASS를 판정한다

## 13.1 MULTI-CLUSTER PASS

```text
MEMBER SELF PASS 유지
+ 기존 Host 자체 정상 기준 확인
+ Host clusterRole=host
+ 신규 Member Identity·Name 중복 없음
+ 보호값 안전한 전달·사용
+ 필요한 Host↔Member Network·DNS·TLS 정상
+ Member Agent·연결 Component 정상
+ Host Console 등록·Status 정상
+ Host에서 Member Node·Namespace·Workload 조회 가능
+ 필요한 관리 권한 경계 정상
+ Host에서 Member Monitoring 관측 가능
+ Metric Cluster Label이 현재 Member
+ 기존 PRD·DEV Member 회귀 없음
+ Host 공통 Component Critical Error 없음
```

> 이 상태가 최종 인수 블록의 입력입니다.

## 13.2 BLOCKED

```text
MEMBER SELF PASS 회귀
Host 자체 핵심 장애
Join Identity·보호값 유효성 미확정
필요 Network·DNS·TLS 실패
Agent·Registration 실패
Host Console Status 비정상
Member Resource 조회 불가
Member Monitoring 관측 실패 원인 미확정
기존 Member 회귀 발생
보호된 값 노출·통제 문제
```

> 최종 인수에서 PASS로 숨기지 않습니다.

---

# 14. 최종 인수 블록으로 넘길 증거

```text
Member Cluster Name·Stage
MEMBER SELF PASS
Host Cluster Identity·Role
Join 방식·실행 시각·승인자
보호값 종류·안전한 전달 결과
Member Agent·연결 Component 상태
Host Console 신규 Member Status
Host에서 Member Resource 조회 결과
Host에서 Member Monitoring 관측 결과
Cluster Label 대조
기존 Member Join 전·후 회귀 결과
Host 공통 Component 상태
MULTI-CLUSTER PASS / BLOCKED
미해결 Join·회귀 항목
```

> 최종 인수는 이 증거를 8월 31일부터의 전체 Gate와 연결합니다.

---

# 15. 마무리 — Host Join 완료를 한 문장으로 다시 말한다

> Host Join은 Cluster 이름을 Console 목록에 추가하는 작업이 아닙니다.
>
> 정상인 Member와 정상인 Host가 현재 Member Identity와 보호된 연결정보로 통신하고, 연결 Agent와 Component가 정상이며, Host가 Member의 Resource를 실제로 조회·관리하고 Monitoring을 관측할 수 있어야 합니다.
>
> 동시에 기존 PRD·DEV Member와 Host 공통 기능에 회귀가 없어야 합니다.
>
> **결국 Multi-Cluster PASS는 신규 Member가 기존 Xi'an Host의 운영 가능한 구성원으로 실제 연결됐고, 그 연결이 기존 환경을 깨뜨리지 않았다는 증거입니다.**

# 16. 마지막 Teach-back

1. Host Console에 Cluster 이름이 보이는 것과 Multi-Cluster 정상은 무엇이 다른가?
2. Join 전에 기존 Host 정상 기준을 읽기 전용으로 기록해야 하는 이유는 무엇인가?
3. 보호된 Join 값에서 문서화할 수 있는 정보와 기록하면 안 되는 정보는 무엇인가?
4. Agent Pod Running과 Registration 완료는 왜 다른가?
5. Host에서 Member Resource 조회와 Monitoring 관측을 별도로 확인해야 하는 이유는 무엇인가?
6. Member 자체 Console 정상과 Host Join 정상은 어떻게 다른가?
7. 기존 Member 회귀 확인이 신규 Member Join 검증의 일부인 이유는 무엇인가?
8. Resource는 보이지만 Monitoring이 없을 때 어느 경계부터 확인해야 하는가?
9. 기존 Member까지 이상해지면 왜 추가 변경을 멈춰야 하는가?
10. `MULTI-CLUSTER PASS`가 증명하는 범위는 어디까지인가?
