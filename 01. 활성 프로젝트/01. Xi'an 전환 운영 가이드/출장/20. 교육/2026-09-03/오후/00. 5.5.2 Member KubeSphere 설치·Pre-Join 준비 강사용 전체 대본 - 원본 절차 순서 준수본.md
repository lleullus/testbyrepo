# 5.5.2 Member KubeSphere 설치·Pre-Join 준비 강사용 전체 대본 - 원본 절차 순서 준수본

> [!important] 사용 방법
> 이 문서는 `05-2.md`의 확정 순서인 `5-2-2-1 → 5-2-2-2 → 5-2-2-3 → 5-2-2-4 → 5-2-2-5 → 5-2-2-6 → 5-2-2 완료 확인`을 그대로 따라간다.
>
> **실제 신규 Member 환경값·적용 여부·MEMBER SELF PASS/BLOCKED 판정은 [[출장/30. 구축/2026-09-03 Member 구축 4일차 - Monitoring KubeSphere Host Join 및 최종 인수|9/3 Member 구축 Source of Truth]]를 우선한다.** `05-2.md`와 `Member 클러스터/05.2.2 Install KubeSphere on Member Cluster.md`는 작업 순서·Manifest·원본 기술 절차의 기준으로 사용한다.
>
> 이 문서의 마지막 범위는 **Host Join 준비까지**다. 실제 Host Console Add/Import/Join과 Multi-Cluster 성공 판정은 이 문서에서 수행하지 않는다.
>
> JWT Secret, kubeconfig, Token, Password, Private Key는 화면·문서·증적에 원문을 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
오전 MONITORING PASS를 확인한다
→ 5-2-2-1에서 Member용 installer bundle과 manifest를 검수·적용한다
→ 5-2-2-2에서 Storage·Registry·ETCD·external Monitoring·member Role 입력을 ClusterConfiguration에 연결한다
→ 5-2-2-3에서 installer 5개 Task와 실제 KubeSphere 기본 상태를 확인한다
→ 5-2-2-4에서 DKS 표준대로 KubeSphere workload를 Infra Node로 재배치한다
→ 설치가 끝난 ks-installer를 replicas=0으로 내린다
→ 5-2-2-5에서 member-role.yaml의 project-admin RoleBase를 적용한다
→ 5-2-2-6에서 보호된 Join 정보와 kubeconfig 전달 준비를 확인한다
→ 5-2-2 완료 Checklist로 MEMBER SELF PASS / BLOCKED를 판정한다
```

## 0-1. 오늘 전체 한 줄

> 오후에는 KubeSphere Console 하나를 여는 것이 목적이 아닙니다. **현재 신규 Member의 Storage·Registry·External Monitoring을 사용하도록 KubeSphere를 `member` 역할로 설치하고, DKS 표준 Infra 배치와 권한·Join 준비까지 끝내 Host 없이도 정상인 Member 상태를 증명하는 시간입니다.**

# 1. 시작 — Monitoring이 정상이어도 KubeSphere Member Platform은 별도다

> 오전에는 현재 DEV Member의 Prometheus·Alertmanager·Grafana와 External ETCD Target, Dashboard, Ingress까지 `MONITORING PASS`로 확인했습니다.
>
> 하지만 Monitoring이 정상이라고 KubeSphere Member Platform이 자동으로 생기는 것은 아닙니다.
>
> 이번 블록에서는 먼저 KubeSphere Installer를 올리고, ClusterConfiguration에 현재 Member의 StorageClass·Registry·ETCD·External Monitoring·Multi-Cluster Role을 연결합니다.
>
> 그다음 Installer Log의 실제 Task 성공을 확인하고, 생성된 KubeSphere Workload를 DKS 표준대로 Infra Node에 재배치합니다. 설치 실행기인 `ks-installer`는 설치 완료 후 `0`으로 내리고, `member-role.yaml`을 적용한 뒤 Host Join에 필요한 보호정보 전달 준비까지만 확인합니다.
>
> Host Join은 비정상 Member를 정상으로 만드는 단계가 아닙니다. 그래서 이 문서가 끝날 때 먼저 `MEMBER SELF PASS`가 되어 있어야 합니다.

# 2. 원본 5-2-2-1 — Bundle 및 installer manifest 확인·적용

먼저 오전 결과와 현재 Context를 확인합니다.

```bash
kubectl config current-context
kubectl get pod -n monitoring -o wide
kubectl get svc -n monitoring prometheus-operated
kubectl get storageclass scs-netapp-qtree-nfs-sc-delete
kubectl get nodes -l node-type=infra -o wide
```

> `MONITORING PASS`가 아닌 상태라면 KubeSphere 설치를 시작하지 않습니다. 특히 KubeSphere는 external Monitoring Endpoint와 StorageClass를 사용하므로 선행 실패를 뒤 단계 설치로 덮지 않습니다.

## 2.1 Member Bundle을 확인한다

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/Kubesphere-v3.2.1/member
ls -al
```

필수 파일:

```text
cluster-configuration.yaml
kubesphere-installer.yaml
member-role.yaml
```

현재 Bundle에서 과거 Taylor/PRD 값이 남아 있는지도 확인합니다.

```bash
grep -nE 'dcr\.cloud\.samsungds|powerflexos|10\.166\.202|tmtest|tmdev|dev-ds-kstest|khdks' \
  kubesphere-installer.yaml \
  cluster-configuration.yaml || true
```

강사 설명:

> 세 파일은 역할이 다릅니다. `kubesphere-installer.yaml`은 설치를 수행할 CRD·권한·Deployment를 준비합니다. `cluster-configuration.yaml`은 무엇을 어떤 환경값으로 설치할지 결정합니다. `member-role.yaml`은 설치가 끝난 뒤 Member의 Project/Namespace 권한 모델을 보강합니다.
>
> 기존 Host Manifest에서 `clusterRole` 한 줄만 바꿔 사용하면 안 됩니다. StorageClass·ETCD·Registry·Monitoring Endpoint·Node 배치와 보호된 JWT 기준이 현재 Member와 모두 맞아야 합니다.

## 2.2 Installer Manifest의 핵심 필드를 확인한다

```bash
grep -nE 'nodeSelector|tolerations|node-type|image:|imagePullPolicy' kubesphere-installer.yaml
```

현재 기준:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        kubernetes.io/os: linux
        node-type: infra
      tolerations:
        - key: node-role.kubernetes.io/infra
          effect: NoSchedule
      containers:
        - name: installer
          image: xa.dcr.dks.samsungds.net/dspaas-cloud/kubesphere/ks-installer:v3.2.1
          imagePullPolicy: Always
```

Installer Manifest가 만드는 핵심 Resource:

| 종류 | 이름 | Namespace |
|---|---|---|
| CRD | `clusterconfigurations.installer.kubesphere.io` | Cluster Scope |
| Namespace | `kubesphere-system` | - |
| ServiceAccount | `ks-installer` | `kubesphere-system` |
| ClusterRole | `ks-installer` | Cluster Scope |
| ClusterRoleBinding | `ks-installer` | Cluster Scope |
| Deployment | `ks-installer` | `kubesphere-system` |

> Installer Pod 자체가 Infra Node에 배치돼야 합니다. 하지만 이 Selector가 설치 후 만들어지는 모든 KubeSphere Workload에 자동 전파되는 것은 아닙니다. 그래서 뒤의 원본 `5-2-2-4`에서 실제 Platform Workload를 다시 Infra로 재배치합니다.

## 2.3 적용 전 정적 검증을 한다

원본 순서대로 `diff`와 dry-run을 확인합니다.

```bash
kubectl diff -f kubesphere-installer.yaml
kubectl apply --dry-run=client -f kubesphere-installer.yaml
```

> 최초 설치에서는 대상 CRD가 아직 없어서 `kubectl diff`가 오류를 반환할 수 있습니다. 이 경우 `--dry-run=client` 결과로 Manifest 문법을 확인합니다.

## 2.4 Installer Manifest를 적용한다

```bash
kubectl apply -f kubesphere-installer.yaml
```

정상 적용 시 다음 종류의 Resource가 생성됩니다.

```text
clusterconfigurations.installer.kubesphere.io
kubesphere-system Namespace
ks-installer ServiceAccount
ks-installer ClusterRole
ks-installer ClusterRoleBinding
ks-installer Deployment
```

실제 생성 상태를 확인합니다.

```bash
kubectl get crd | grep installer
kubectl get ns | grep kubesphere
kubectl get clusterrole | grep '^ks-installer$'
kubectl get clusterrolebinding | grep '^ks-installer$'
kubectl get deploy -n kubesphere-system ks-installer
kubectl get pod -n kubesphere-system -l app=ks-install -o wide
```

완료 기준:

```text
clusterconfigurations.installer.kubesphere.io 존재
kubesphere-system Active
ks-installer Deployment 1/1 Available
ks-installer Pod Running
Pod NODE = xadksirmd01~03 중 하나
ImagePullBackOff 없음
```

강사 설명:

> Apply 성공은 객체 생성 요청이 받아들여졌다는 뜻입니다. Installer Pod가 `Running`이어야 설치 실행기가 실제로 시작된 것입니다.
>
> 그렇지만 아직 KubeSphere 설치 Task가 완료된 것은 아닙니다. 다음 원본 단계에서 ClusterConfiguration을 적용해야 무엇을 설치할지 결정됩니다.

# 3. 원본 5-2-2-2 — ClusterConfiguration 확인 및 적용

이 단계가 KubeSphere Member 설치 입력의 핵심입니다. 전체 Bundle YAML을 이 대본의 일부 Fragment로 새로 만들지 않고 **현재 Bundle 파일을 기준으로 검수**합니다.

## 3.1 현재 Member 필수값을 확인한다

```bash
grep -nE 'storageClass|endpointIps|local_registry|jwtSecret|clusterRole|endpoint:' cluster-configuration.yaml
```

현재 확정 기준:

```yaml
apiVersion: installer.kubesphere.io/v1alpha1
kind: ClusterConfiguration
metadata:
  name: ks-installer
  namespace: kubesphere-system
  labels:
    version: v3.2.1
spec:
  persistence:
    storageClass: scs-netapp-qtree-nfs-sc-delete
  authentication:
    jwtSecret: <HOST_JWT_SECRET>
  local_registry: xa.dcr.dks.samsungds.net/dspaas-cloud
  etcd:
    monitoring: false
    endpointIps: 109.156.22.70,109.156.22.71,109.156.22.72
    port: 2379
    tlsEnable: true
  common:
    core:
      console:
        enableMultiLogin: true
        port: 30880
        type: NodePort
    monitoring:
      type: external
      endpoint: http://prometheus-operated.monitoring.svc:9090
    devops:
      enabled: true
      jenkinsMemoryLim: 2Gi
      jenkinsMemoryReq: 1500Mi
      jenkinsVolumeSize: 8Gi
  monitoring:
    storageClass: scs-netapp-qtree-nfs-sc-delete
  multicluster:
    clusterRole: member
```

### StorageClass

> `persistence.storageClass`와 `monitoring.storageClass`는 9/2에 검증하고 오늘 오전 Monitoring에서도 실제 사용한 `scs-netapp-qtree-nfs-sc-delete`를 사용합니다.
>
> 과거 PowerFlex StorageClass가 남아 있으면 적용하지 않습니다.

### Registry

> `local_registry`는 현재 Xi'an Registry `xa.dcr.dks.samsungds.net/dspaas-cloud`를 사용합니다. Image Tag는 현재 Bundle과 실제 Registry 기준을 확인합니다.

### External ETCD

> `endpointIps`는 현재 DEV Member ETCD `109.156.22.70~72`입니다. Host ETCD나 다른 Member ETCD가 들어가 있지 않은지 다시 확인합니다.

### External Monitoring

KubeSphere가 사용하는 Endpoint:

```text
http://prometheus-operated.monitoring.svc:9090
```

Grafana Datasource:

```text
http://prometheus-k8s.monitoring.svc:9090
```

강사 설명:

> 두 URL은 의도적으로 다릅니다. 오전 Grafana는 `prometheus-k8s` Service를 Datasource로 사용하고, KubeSphere external Monitoring은 `prometheus-operated` Service를 통해 Metric을 읽습니다.
>
> 같은 Prometheus Backend와 연결되더라도 소비자가 사용하는 Service가 다르기 때문에 기억으로 하나를 복사하지 않습니다.

실제 Service를 확인합니다.

```bash
kubectl get svc -n monitoring prometheus-operated
kubectl get svc -n monitoring prometheus-k8s
```

### Multi-Cluster Role

```yaml
multicluster:
  clusterRole: member
```

> 이 `member`는 뒤의 `member-role.yaml`이 만드는 `project-admin RoleBase`와 전혀 다른 개념입니다.
>
> `clusterRole=member`는 이 Cluster가 Multi-Cluster 구조에서 Member라는 역할을 결정하고, `project-admin RoleBase`는 Project/Namespace 권한 모델입니다.

## 3.2 JWT Secret을 안전하게 취급한다

`jwtSecret`은 Host와 Member의 Multi-Cluster 신뢰에 필요한 보호정보입니다.

```yaml
authentication:
  jwtSecret: <HOST_JWT_SECRET>
```

> [!danger] 보호정보
> 실제 값을 문서, 티켓, Chat, Screenshot, Shell History에 남기지 않습니다. Host에서 승인된 방식으로 전달받고 현재 Member ClusterConfiguration에 필요한 방식으로 반영합니다.
>
> 이 문서에서는 값 자체를 보여 주거나 복사하지 않습니다.

## 3.3 다른 환경값 잔존 여부를 확인한다

```bash
grep -nE 'powerflexos|dcr\.cloud\.samsungds|10\.166\.202|tmdev|tmtest' \
  cluster-configuration.yaml || echo "OK - no Taylor/PRD values found"
```

> 이 grep은 과거 환경값 혼입을 찾기 위한 안전장치입니다. 아무 출력이 없다는 사실이 모든 현재값이 맞다는 뜻은 아니므로 앞에서 확인한 DEV 기준과 개별 필드를 다시 대조합니다.

## 3.4 적용 전 dry-run 후 ClusterConfiguration을 적용한다

```bash
kubectl apply --dry-run=client -f cluster-configuration.yaml
kubectl apply -f cluster-configuration.yaml
kubectl get clusterconfiguration -n kubesphere-system
```

필요하면 현재 CR 존재 여부를 확인합니다.

```bash
kubectl get cc -n kubesphere-system
```

> ClusterConfiguration 생성 성공은 설치 입력이 API에 등록됐다는 뜻입니다. 실제 KubeSphere 기능이 모두 설치됐다는 뜻은 아닙니다.
>
> 다음 원본 단계에서 Installer가 이 설정을 읽고 실제 Task를 수행하는지 확인합니다.

# 4. 원본 5-2-2-3 — Installer 로그와 기본 설치 상태 확인

## 4.1 Installer 로그를 추적한다

```bash
kubectl logs -n kubesphere-system \
  "$(kubectl get pod -n kubesphere-system -l app=ks-install -o jsonpath='{.items[0].metadata.name}')" \
  -f
```

원본 핵심 Task는 다음 다섯 개입니다.

```text
network
openpitrix
multicluster
monitoring
devops
```

정상 완료 기준:

```text
task network status is successful
task openpitrix status is successful
task multicluster status is successful
task monitoring status is successful
task devops status is successful
```

강사 설명:

> `ks-installer` Pod가 Running이라는 것과 내부 다섯 Task가 성공한 것은 다릅니다.
>
> 설치 로그 마지막 줄만 보는 것이 아니라 최초 실패 Task와 오류 원문을 찾습니다. 앞 단계 Storage·Monitoring·Registry·CRD 오류가 뒤 Task 실패로 이어질 수 있기 때문입니다.
>
> 모든 Task가 `successful`이어야 설치 완료로 판단합니다.

### 최초 실패 분기

- `ImagePullBackOff`: 현재 Registry, Image Tag, CA, Pull Secret
- `ClusterConfiguration` NotFound/Pending: installer CRD와 CR 상태
- Monitoring Task 실패: 오전 `MONITORING PASS`, `prometheus-operated` Service
- PVC Pending/FailedMount: StorageClass와 실제 Pod Node Data Path
- Resource 부족: Scheduler Event와 Infra Node Resource

> 상세 Runbook에는 실패 시 Installer Pod 재생성 예시가 있지만 무조건 재시작하지 않습니다. 먼저 최초 실패 원인을 확인하고 현재 상태에서 재시도가 안전한지 판단합니다.

## 4.2 KubeSphere Namespace와 기본 Pod를 확인한다

```bash
kubectl get ns | grep kubesphere
kubectl get pod -n kubesphere-controls-system -o wide
kubectl get pod -n kubesphere-devops-system -o wide
kubectl get pod -n kubesphere-system -o wide
kubectl get pod -n kubesphere-monitoring-system -o wide
```

원본 정상 Namespace 예:

```text
kubesphere-controls-system
kubesphere-devops-system
kubesphere-devops-worker
kubesphere-monitoring-federated
kubesphere-monitoring-system
kubesphere-system
```

중요한 판정:

> Member는 `monitoring.type=external`을 사용합니다. 따라서 `kubesphere-monitoring-system` Namespace가 존재하더라도 KubeSphere 자체 Monitoring Pod가 없는 것이 정상일 수 있습니다.
>
> 이를 Monitoring 설치 실패로 오해해 KubeSphere 기본 Monitoring Stack을 추가로 설치하면 안 됩니다. 실제 Monitoring은 오전에 구성한 `monitoring` Namespace의 DKS custom Prometheus가 담당합니다.

## 4.3 Console Endpoint는 현재 승인 경로로 확인한다

ClusterConfiguration의 Console NodePort는 `30880`입니다.

```bash
kubectl get svc -n kubesphere-system ks-console -o wide
```

> [!warning] Console/API VIP 실제값
> 상세 참고 문서에는 DEV Console/API VIP 예시가 있으나 현재 9/3 Source of Truth는 API VIP·Console 노출 경로를 현장 확인 항목으로 남기고 있습니다. 따라서 과거/참고 IP를 실행값으로 고정하지 않고 현재 Service·L4·Firewall 승인 경로를 확인합니다.

> Console이 열린다고 설치가 완료된 것은 아닙니다. Console은 Frontend와 일부 API 경로가 응답한다는 증거이고, 실제 Platform Workload·Storage·External Monitoring·Role·Infra 배치는 뒤에서 별도로 확인합니다.

### 5-2-2-3 완료 기준

```text
Installer 5개 Task 모두 successful
```

# 5. 원본 5-2-2-4 — DKS 표준 Infra 재배치

KubeSphere Installer에 지정한 `nodeSelector`가 설치 후 생성되는 모든 Workload에 자동 전파되지 않습니다. 그래서 원본은 설치 완료 후 KubeSphere Platform Workload를 Infra Node에 명시적으로 재배치합니다.

> [!important] 재배치 전 원칙
> Patch부터 실행하지 않습니다. 각 Workload의 현재 `nodeSelector`와 `tolerations`를 먼저 확인합니다. 기존 값이 있으면 덮어쓰지 않도록 현재 Template을 검토하고 현장 기준으로 병합합니다.

## 5.1 Infra Node Label과 Taint를 다시 확인한다

```bash
kubectl get nodes -l node-type=infra --show-labels
kubectl describe node xadksirmd01 | grep Taints
```

기대 기준:

```text
Infra Node = xadksirmd01~03
node-type=infra
node-role.kubernetes.io/infra:NoSchedule
```

대표 Workload의 현재 Template도 확인합니다.

```bash
kubectl get deployment -n kubesphere-controls-system default-http-backend \
  -o jsonpath='{.spec.template.spec.nodeSelector}{"\n"}{.spec.template.spec.tolerations}{"\n"}'

kubectl get deployment -n kubesphere-devops-system devops-apiserver \
  -o jsonpath='{.spec.template.spec.nodeSelector}{"\n"}{.spec.template.spec.tolerations}{"\n"}'

kubectl get deployment -n kubesphere-system ks-apiserver \
  -o jsonpath='{.spec.template.spec.nodeSelector}{"\n"}{.spec.template.spec.tolerations}{"\n"}'
```

> 아래 Patch 예시는 현재 Template에 보존해야 할 다른 Toleration이 없다고 확인된 경우에만 그대로 실행합니다. 기존 Toleration이 존재하면 기계적으로 복사하지 않고 현재 값을 보존하도록 병합합니다. 원본 의도는 `node-type=infra`와 Infra NoSchedule Taint를 수용하도록 만드는 것이며, 기존 필수 Toleration을 삭제하는 것이 아닙니다.

대상:

# 7. 원본 5-2-2-6 — Host Join 준비

이제 실제 Join을 하기 전에 Member 쪽 준비를 확인합니다. **Host Join 실행 자체는 이 문서 범위가 아닙니다.**

## 7.1 보호된 JWT 기준을 확인한다

Host와 Member가 사용하는 JWT Secret 일치 여부는 승인된 비밀 전달 절차로 확인합니다.

Member에서는 JWT 값 원문을 출력하지 않고 설정 키 존재 여부만 확인합니다.

```bash
kubectl -n kubesphere-system get cm kubesphere-config -o yaml \
  | grep 'jwtSecret' \
  | sed 's/:.*/: <보호된 값>/'
```

강사 설명:

> JWT Secret은 Join 정보의 핵심 보호값입니다. 값·Prefix·Hash를 교육 문서나 증적에 남겨 비교하지 않습니다.
>
> 승인된 비밀 관리체계에서 Host와 Member의 일치 여부를 확인하고, 여기에는 “일치 확인 완료”라는 판정만 남깁니다.

## 7.2 `accessTokenMaxAge` 기준을 확인한다

현재 권위 기준은 `0`입니다. JWT와 달리 이 설정값은 별도로 직접 확인합니다.

```bash
kubectl -n kubesphere-system get cm kubesphere-config -o yaml \
  | grep 'accessTokenMaxAge'
```

정상 기준:

```text
accessTokenMaxAge: 0
```

> 전체 ConfigMap이나 JWT Secret을 함께 출력하지 않고 필요한 비민감 설정값만 확인합니다.

## 7.3 KubeSphere Config의 비민감 구조를 확인한다

확인 대상:

```text
multipleLogin / enableMultiLogin 관련 설정
kubectl image Registry
Member Role 관련 설정
External Monitoring 참조
```

민감 필드는 출력에서 제외합니다.

> 현재 Bundle과 설치 후 Config의 Registry가 Xi'an DEV 기준과 맞는지 확인합니다. Taylor Registry가 남아 있으면 Host Join으로 넘어가지 않습니다.

## 7.4 Member kubeconfig 전달 준비를 확인한다

Host Web UI Import 방식에서 kubeconfig가 필요할 수 있습니다.

확인할 것:

```text
Member kubeconfig 원본 보관 위치
파일 Permission
암호화된 전달 경로
수신 담당자
전달 후 임시 사본 정리 기준
현재 server Endpoint가 승인된 DEV Member API 경로인지
```

> [!danger] kubeconfig 보호
> kubeconfig에는 Cluster 인증정보가 포함될 수 있습니다. 대본·Ticket·Chat·Screenshot에 원문을 붙이지 않습니다.

> [!warning] API Endpoint 실제값
> 참고 문서의 DEV API VIP 표기는 다른 현장 문서와 일치 여부를 최종 확인해야 합니다. kubeconfig의 `server` 값을 과거 예시로 수정하지 않고 현재 신규 Member의 승인 API Endpoint를 기준으로 확인합니다.

## 7.5 Host Console Import 책임과 접근 준비를 확인한다

```text

```

```text
kubeconfig 안전 전달 경로 미확정
```

---

# 9. 문제가 생기면 원본 순서의 마지막 성공과 첫 실패를 찾는다

> Installer Pod가 생성되지 않았다면 ClusterConfiguration이나 Console부터 보지 않습니다. `5-2-2-1`의 CRD·RBAC·Deployment·Image를 봅니다.
>
> Installer는 Running인데 ClusterConfiguration이 적용되지 않으면 현재 CRD와 Manifest 입력을 확인합니다.
>
> Installer Task가 실패하면 최초 실패 Task와 그 Task가 사용하는 Storage·Monitoring·Registry·CRD를 확인합니다.
>
> Task는 성공했지만 Platform Pod가 Pending이면 전체 설치를 반복하지 않고 Node Selector·Taint/Toleration·Resource·PVC를 봅니다.
>
> PVC가 FailedMount면 Installer를 재시작하지 않고 실제 Pod Node와 Storage Data Path를 확인합니다.
>
> KubeSphere Monitoring 화면만 비어 있으면 오전 Prometheus 자체가 여전히 정상인지 확인한 뒤 `prometheus-operated` Endpoint와 KubeSphere 설정을 봅니다.
>
> Infra 재배치 중 Patch가 실패하면 현재 Pod Template의 Selector/Toleration 구조를 먼저 읽고 기존 값을 보존하는 방식으로 병합합니다.
>
> `ks-installer=0` 상태를 장애로 보고 다시 올리지 않습니다.
>
> Host Join 준비에서 JWT나 kubeconfig 문제가 있으면 실제 Join을 강행하지 않고 보호된 전달 기준을 먼저 확정합니다.

---

# 10. Host Join 블록에 넘길 것

다음 정보만 전달합니다.

```text
MEMBER SELF PASS / BLOCKED
Member Cluster Name / Stage / Context
Kubernetes / Storage Gate 유지 여부
MONITORING PASS 결과
KubeSphere Version
Installer 5개 Task 결과
Platform 주요 Workload 상태
Infra 배치 결과
StorageClass / PVC / Mount 결과
External Monitoring Endpoint 정상 여부
clusterRole = member
project-admin RoleBase 결과
ks-installer replicas = 0
Host Join 보호정보 준비 완료 여부
kubeconfig 안전 전달 준비 여부
남은 제한 / Blocker
```

다음은 전달하지 않습니다.

```text
JWT Secret 원문
kubeconfig 원문
Token
Password
Private Key
Secret Data
```

> 다음 블록의 목적은 기존 Host를 새로 설치하는 것이 아니라, **이미 `MEMBER SELF PASS`인 Member를 정상인 기존 Host에 연결하고 실제 Resource·Monitoring 관리가 되는지 확인하는 것**입니다.

# 11. 마무리

> 오후에는 먼저 원본 `5-2-2-1`에서 Member용 Installer Bundle을 확인하고 설치 실행기 CRD·권한·Deployment를 실제 Infra Node에 올렸습니다.
>
> `5-2-2-2`에서는 9/2 Storage와 오전 Monitoring 결과를 KubeSphere ClusterConfiguration의 StorageClass·Registry·ETCD·external Monitoring·`clusterRole=member`에 연결했습니다.
>
> `5-2-2-3`에서 Installer의 5개 핵심 Task를 확인한 뒤, `5-2-2-4`에서는 설치된 KubeSphere Workload를 DKS 표준 Infra Node로 재배치하고 Installer를 `replicas=0`으로 내렸습니다.
>
> `5-2-2-5`에서는 `member-role.yaml`의 `project-admin` RoleBase를 적용했고, 마지막 `5-2-2-6`에서는 Host Join에 필요한 보호정보와 kubeconfig 전달 준비만 완료했습니다.
>
> **결국 MEMBER SELF PASS는 Console이 열린 상태가 아니라, Storage·Monitoring·KubeSphere 내부 Task·실제 Platform Workload·Infra 배치·Role·Join 준비가 모두 현재 신규 Member 기준으로 정상인 상태입니다.**
