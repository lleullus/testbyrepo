# 기존 Host Join·Multi-Cluster 기능 검증 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 오전에는 신규 Member 자체의 Kubernetes·Storage·Monitoring·KubeSphere를 확인해 `MEMBER SELF PASS`를 판정했다. 이번 블록은 **정상인 Member를 기존 Host에 연결하고, Host에서 실제 Resource와 Monitoring을 사용할 수 있는지 확인하는 과정**이다.
>
> Add·Import·Join 방식과 Endpoint는 현재 KubeSphere Version과 승인된 Runbook을 따른다. 기존 Host를 재설치하거나 불필요한 공통 설정을 변경하지 않는다. Join Secret·JWT·kubeconfig·Token·Password·Private Key 원문은 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
신규 Member 자체가 정상이다
→ 하지만 기존 Host가 그 Member를 관리할 수 있는 것은 아니다
→ 먼저 기존 Host와 기존 Member의 현재 상태를 확인한다
→ Host와 Member의 이름·Stage·Role을 맞춘다
→ 현재 Join 방식에 필요한 DNS·Network·TLS를 확인한다
→ 보호된 Join 정보를 승인된 방법으로 사용한다
→ Join 요청 뒤 Agent와 Host Component를 확인한다
→ Host의 Cluster Status를 확인한다
→ 실제 Member Resource와 Monitoring을 확인한다
→ 기존 Host와 기존 Member에 영향이 없는지 확인한다
→ 모두 정상이어야 MULTI-CLUSTER PASS다
```

## 0-1. 오늘 전체 한 줄

> Join 완료는 Host 화면에 Cluster 이름이 보이는 상태가 아닙니다. **Host에서 신규 Member의 실제 Resource와 Monitoring을 확인할 수 있고 기존 환경도 정상인 상태**입니다.

---

# 1. 시작 — Member 자체 정상과 Multi-Cluster 정상은 다르다

> 오전에는 신규 Member가 Host 없이도 정상적으로 동작하는지 확인했습니다.
>
> **하지만 기존 Host가 이 Member를 알고 실제 Resource와 Monitoring을 사용할 수 있는지는 별도입니다.**
>
> Host Join은 Member 내부 장애를 해결하는 작업이 아닙니다. `MEMBER SELF PASS`가 아닌 상태에서 Join하면 Member 내부 문제와 연결 문제를 구분하기 어려워집니다.
>
> 따라서 정상인 Member와 정상인 Host 사이에 필요한 연결만 추가합니다.
>
> 먼저 기존 Host와 기존 Member의 현재 상태를 확인합니다.

---

# 2. 기존 Host는 변경 전에 현재 상태를 확인한다

> 기존 Host는 이미 운영 중인 시스템입니다.
>
> 그래서 Join 전에 Host Console·API와 실제 `clusterRole=host`, 주요 Multi-Cluster Component 상태를 읽기 전용으로 확인합니다.
>
> 먼저 기존 PRD·DEV Member의 이름·Stage·Status를 확인하고, 대표 Resource와 Monitoring이 현재 정상인지 봅니다.
>
> 그다음 Host 자체의 Multi-Cluster Component가 Ready인지, 반복 Restart나 Error가 없는지도 확인합니다.
>
> 이 결과는 신규 Member Join 뒤 기존 환경에 변화가 생겼는지 비교하는 기준이 됩니다. Join 뒤 이상이 발생했을 때 원래 있던 문제인지 신규 작업 이후 생긴 문제인지 구분하려면 변경 전 상태가 필요합니다.
>
> 그래서 Join 전에 신규 Member 이름이 기존 Cluster와 중복되지 않는지와 현재 작업자가 Join 대상 Workspace·Cluster를 관리할 권한이 있는지도 확인합니다.
>
> **하지만 Host Console이 열리고 기존 Member 이름이 보인다는 사실만으로 기존 Multi-Cluster 기능이 정상이라고 판단하지 않습니다.** 기존 Member의 Status·대표 Resource·Monitoring까지 실제로 조회돼야 기준 상태로 사용할 수 있습니다.
>
> 반대로 사전 확인에서 기존 Host나 기존 Member에 중대한 이상이 있다면 신규 Member Join부터 진행하지 않습니다. 기존 문제와 신규 작업의 범위를 구분하고 영향과 담당자를 정합니다.
>
> 따라서 변경 전 확인은 단순한 사전 점검이 아니라 Join 이후 회귀 여부를 판단하기 위한 기준선을 만드는 과정입니다.
>
> 기존 Host 상태를 확인했으면 다음으로 Host와 신규 Member의 Identity를 맞춥니다.

---

# 3. Host와 Member의 이름·Stage·Role을 맞춘다

> 신규 Member의 Cluster Name·Stage와 실제 `clusterRole=member`를 확인합니다.
>
> 먼저 기존 중앙 Cluster가 실제 `host` 역할인지 다시 봅니다.
>
> 그다음 Host Console에 등록할 신규 Member 이름이 기존 Cluster와 중복되지 않는지 확인합니다.
>
> Cluster Name은 화면 표시만을 위한 값이 아닙니다. 운영자가 선택할 관리 대상, Monitoring의 Cluster Label과 Join Identity를 구분하는 기준으로 사용될 수 있습니다.
>
> 그래서 Host에 등록할 이름, Member가 자체적으로 사용하는 이름, Monitoring Query에서 확인한 Cluster·Stage Label이 같은 신규 Member를 가리켜야 합니다.
>
> **하지만 이름 문자열이 같다고 같은 Cluster라는 뜻은 아닙니다.** Stage·Role·Endpoint와 실제 Node 구성이 현재 신규 Member와 일치하는지도 같이 확인해야 합니다.
>
> 반대로 `clusterRole`이 잘못됐거나 기존 Cluster와 이름이 충돌하면 통신이 정상이어도 Host가 의도하지 않은 방식으로 등록하거나 운영자가 잘못된 Cluster를 선택할 수 있습니다.
>
> 따라서 이름·Stage·Role이 맞지 않으면 Network 시험이나 Join 요청으로 넘어가지 않습니다.
>
> Identity가 맞으면 현재 Join 방식에 필요한 통신 경로를 확인합니다.

---

# 4. DNS·Network·TLS는 현재 Join 방식의 실제 방향으로 확인한다

> Multi-Cluster 연결에는 Host와 Member 사이의 API·Agent 통신이 필요합니다.
>
> **하지만 통신 방향과 Port는 KubeSphere Version과 Join 방식에 따라 달라질 수 있습니다.** 과거 Diagram이나 기억으로 규칙을 정하지 않습니다.
>
> 먼저 현재 Runbook에서 Host가 Member API나 Endpoint에 접근해야 하는지, Member Agent가 어떤 Host Endpoint로 연결해야 하는지 실제 방향을 확인합니다.
>
> 그다음 각 방향별 FQDN·IP·Port·Protocol을 현재 승인값과 대조합니다.
>
> DNS에서는 이름이 해석된다는 사실보다 현재 Host 또는 Member가 접근해야 할 승인 IP로 해석되는지 확인합니다.
>
> 그래서 DNS가 맞으면 실제 Source에서 대상 Port까지 Network·Firewall 경로가 열려 있는지 봅니다.
>
> 그다음 TLS를 사용하는 Endpoint라면 Certificate Trust와 이름 검증 조건이 현재 FQDN·Endpoint와 맞는지도 확인합니다.
>
> Port 연결 성공은 인증 성공과 다릅니다. TCP 연결은 되지만 TLS Handshake나 Application 인증에서 실패할 수 있습니다.
>
> 반대로 인증 오류가 실제 Server 응답으로 반환된다면 DNS와 Network, TLS의 일부 구간은 이미 통과했을 수 있습니다.
>
> 따라서 DNS·Network·TLS·인증을 한 문제로 묶지 않고 어느 단계까지 성공했고 처음 실패한 지점이 어디인지 구분합니다.
>
> 통신 경로가 준비돼도 Join에는 보호된 연결정보가 필요합니다.

---

# 5. Join 정보는 승인된 방법으로만 사용한다

> Join 방식에 따라 Token·JWT·kubeconfig·Secret 또는 다른 연결정보가 필요할 수 있습니다.
>
> 이 값은 Host와 Member의 신뢰를 연결하므로 일반 설정값처럼 문서·채팅·Screenshot·Shell History에 남기지 않습니다.
>
> 먼저 어떤 종류의 값이 필요한지 확인합니다.
>
> 그다음 누가 발급하고 누가 사용할 수 있는지, 전달 방법과 유효시간이 무엇인지 확인합니다.
>
> 사용 후 Rotation이나 폐기가 필요한지도 봅니다.
>
> 과거 Member의 Join 값을 재사용하지 않습니다. 현재 Host와 신규 Member를 위해 발급된 값인지 승인된 관리체계에서 확인합니다.
>
> 증적에는 원문 대신 발급·사용 시각, 전달자·수신자 역할, 사용 결과와 정리 상태를 남깁니다.
>
> 필요한 값이 준비되면 Join 요청을 시작합니다.

---

# 6. Join 요청 생성과 실제 연결은 다르다

> 현재 Version에 맞는 Add·Import·Join 절차를 승인된 Runbook에 따라 수행합니다.
>
> 먼저 실행 전에 대상 Host와 Member, Cluster Name·Stage·Endpoint를 다시 확인합니다. 보호된 Join 정보가 현재 Host와 신규 Member용인지도 마지막으로 확인합니다.
>
> Submit이나 Apply가 성공하면 Join 요청 객체가 생성된 것입니다.
>
> **하지만 Agent가 설치되고 Host와 연결됐다는 뜻은 아닙니다.**
>
> 그래서 현재 방식에서 Host와 Member에 어떤 Registration 객체·Namespace·ServiceAccount·Deployment가 생성되는지 확인합니다.
>
> 그다음 Join 요청의 상태가 실제로 다음 단계로 진행되는지 보고, 필요한 Agent나 연결 Workload가 신규 Member에 생성되는지 확인합니다.
>
> 요청은 있는데 Agent가 생성되지 않으면 Network부터 바꾸지 않습니다. 요청 처리 상태, 권한, Cluster Identity, Join 정보와 Host Component Log를 먼저 확인합니다.
>
> 반대로 Agent가 생성됐다는 사실만으로 요청이 정상 완료됐다고 판단하지 않습니다. Agent가 실제 Host Endpoint와 통신하고 Registration 상태를 갱신해야 합니다.
>
> 따라서 Join 요청 단계에서는 “요청이 생성됐는가”와 “연결 Component가 생성됐는가”를 구분하고, 다음으로 실제 Agent와 Host Component 상태를 봅니다.

---

# 7. Agent Running과 정상 Registration은 다르다

> Member Agent Pod가 Running이면 Agent Process가 시작됐다는 뜻입니다.
>
> **하지만 Host에 정상 등록되고 상태를 주고받는다는 뜻은 아닙니다.**
>
> 먼저 Agent가 현재 신규 Member에 생성됐는지와 Image·Version이 현재 Host-Member 조합에 맞는지 확인합니다.
>
> 그다음 ServiceAccount와 권한, 필요한 Config·Secret 참조가 현재 Join 방식에 맞는지도 봅니다. 보호된 값의 원문은 출력하지 않습니다.
>
> 그래서 Restart·Event·Log에서 DNS·Network·TLS·인증 오류를 확인합니다.
>
> Agent가 Host Endpoint에 도달하지 못한다면 Network와 DNS를 보고, TLS 오류가 있다면 Certificate Trust와 Endpoint 이름을 확인합니다. 인증 오류가 있다면 현재 Join 정보와 Cluster Identity를 다시 확인합니다.
>
> 반대로 Agent Pod가 Running이고 Restart도 없더라도 Host에서 Registration 상태가 갱신되지 않는다면 Process 기동 성공과 실제 연결 성공을 구분해야 합니다.
>
> 그리고 Host 측 Multi-Cluster Component가 Join 전 정상 상태를 유지하는지도 같이 봅니다. Member Agent만 보고 Host 쪽 연결 처리 상태를 생략하지 않습니다.
>
> 따라서 Agent 인증 오류나 Registration 미완료가 있으면 Join 요청을 반복하지 않고, 처음 실패한 Endpoint·TLS·인증·Identity 경계를 확인합니다.
>
> Agent가 실제로 연결되면 Host Console의 Cluster 상태를 확인합니다.

---

# 8. Host Console의 이름 표시와 정상 Status는 다르다

> Host Console에 신규 Member 이름이 보이면 Host가 Cluster 등록 객체를 알고 있다는 뜻입니다.
>
> **하지만 실제 연결이 정상이라는 뜻은 아닙니다.**
>
> 먼저 등록된 이름과 Stage가 승인값과 같은지 확인합니다.
>
> 그다음 Status가 정상으로 전환되는지와 반복 Error·Unknown 상태가 없는지 봅니다.
>
> 목록에는 보이지만 Status가 Error 또는 Unknown일 수 있습니다. 이 경우 등록 객체는 생성됐지만 Agent 통신, Member API 접근이나 상태 수집 중 하나가 완료되지 않은 것입니다.
>
> 그래서 Status 오류가 남아 있는데 이름이 보인다는 이유로 Resource 검증을 정상으로 넘기지 않습니다.
>
> 반대로 Status가 정상이라고 실제 Resource와 Monitoring까지 자동으로 통과한 것도 아닙니다. Status는 연결 상태의 한 단계이고 실제 관리·관측 기능은 다음 단계에서 확인해야 합니다.
>
> 따라서 `목록 표시 → 정상 Status → 실제 Resource 접근 → Monitoring 관측` 순서로 증거 범위를 넓혀갑니다.

---

# 9. Host에서 실제 Member Resource를 확인한다

> Status가 정상이라면 Host에서 신규 Member를 선택하고 Node·Namespace·Workload를 조회합니다.
>
> 먼저 Node 수와 Role·이름이 오전 `MEMBER SELF PASS`에서 확인한 신규 Member와 같은지 봅니다.
>
> 그다음 대표 Namespace와 Workload가 실제 Member 자체 Console·API에서 확인한 상태와 일치하는지 확인합니다.
>
> 그래서 Host에서 보이는 Resource가 단순히 조회된다는 것보다 “현재 선택한 Cluster가 실제 신규 Member인가”를 교차 확인하는 것이 중요합니다.
>
> 다른 Cluster Resource가 섞이거나 결과가 비어 있지 않아야 하고, 최근에 생성한 대표 Workload 상태도 같은 Member에서 일치해야 합니다.
>
> 그리고 승인된 Role의 조회·관리 기능과 권한 경계도 확인합니다. 조회 권한만 있는 사용자에게 변경 기능이 보이지 않는 것은 장애가 아닐 수 있으므로 기대 권한과 실제 권한을 구분합니다.
>
> **하지만 Resource 목록이 보인다는 사실만으로 Host-Member 기능 전체가 정상이라는 뜻은 아닙니다.** Resource API 경로와 Monitoring 데이터 경로는 별도로 동작할 수 있습니다.
>
> 따라서 Host Console과 Member 자체 Console·API가 같은 Cluster 상태를 보여 주는지 확인한 뒤 Monitoring 관측으로 넘어갑니다.

---

# 10. Resource 조회와 Monitoring 관측은 따로 확인한다

> Member 자체 Monitoring은 오전에 정상임을 확인했습니다.
>
> 이제 Host에서 신규 Member의 Node·Workload Metric이 최근 시각으로 보이는지 확인합니다.
>
> 먼저 Host에서 선택한 Cluster가 신규 Member인지 확인하고, Metric의 Cluster·Stage Label도 같은 Member를 가리키는지 봅니다.
>
> 그다음 최근 Metric 시각과 실제 Node·Workload 상태를 Member 자체 Prometheus·Grafana 결과와 대조합니다.
>
> 그래서 Resource는 보이지만 Monitoring이 비어 있다면 Join 전체를 반복하지 않습니다.
>
> 먼저 Member 자체 Prometheus와 Target·Query가 여전히 정상인지 확인합니다.
>
> 그다음 External Label·Prometheus Endpoint와 Host의 Multi-Cluster Monitoring 설정이 현재 Member를 가리키는지 봅니다.
>
> **하지만 Host에서 Metric이 보인다는 사실만으로 Resource 관리 기능까지 정상인 것은 아닙니다.** Monitoring 데이터는 별도 Endpoint를 통해 들어올 수 있기 때문입니다.
>
> 반대로 Resource는 정상인데 Monitoring만 없다면 Agent나 Join 요청을 다시 만들기보다 Monitoring 연결 경로를 먼저 확인합니다.
>
> 따라서 Resource 관리와 Monitoring 관측은 각각 실제 기능으로 확인하고, 둘 다 같은 신규 Member를 가리킬 때 Multi-Cluster 기능으로 연결합니다.

---

# 11. 신규 Member 확인 뒤에는 기존 환경의 회귀를 본다

> 신규 Member의 Status·Resource·Monitoring이 정상이어도 기존 환경 무영향은 별도 조건입니다.
>
> 먼저 Join 전에 기록한 Host 기준 상태와 비교해 주요 Multi-Cluster Component가 계속 정상인지 확인합니다.
>
> 그다음 기존 PRD·DEV Member의 Status와 대표 Resource·Monitoring도 같은 상태를 유지하는지 봅니다.
>
> 그래서 신규 Member를 추가하는 과정에서 Shared Config·Datasource·Cluster Label·Endpoint가 신규 Member 값으로 덮이지 않았는지도 확인합니다.
>
> **하지만 신규 Member 기능이 정상이라는 결과로 기존 Member의 이상을 허용하지 않습니다.** Multi-Cluster 환경에서는 한 Cluster를 추가하면서 공통 설정에 영향을 주면 전체 운영 범위가 넓어질 수 있습니다.
>
> 반대로 기존 Member가 Error로 바뀌었다면 원래 문제였다고 추측하지 않습니다. Join 전 기준 상태와 비교해 신규 변경과 영향 관계를 확인합니다.
>
> 따라서 기존 환경 이상이 발견되면 추가 변경을 멈추고 Host 공통 Component·Config와 Identity 충돌의 영향 범위를 먼저 확인합니다.
>
> 결국 신규 Join 성공과 기존 Host·Member 무영향이 모두 확인돼야 Multi-Cluster 기능을 정상으로 판단할 수 있습니다.

---

# 12. 문제가 생기면 Join 순서대로 확인한다

> Join 문제도 처음 실패한 단계보다 뒤쪽을 먼저 고치지 않습니다.
>
> 먼저 Cluster가 Host에 전혀 보이지 않으면 Join 요청이 실제 생성됐는지, 이름·권한·보호된 값과 Host 처리 상태를 확인합니다.
>
> 그다음 이름은 보이지만 Status가 Error·Unknown이면 Agent·Endpoint·DNS·Network·TLS와 인증을 봅니다.
>
> 그래서 이 단계에서는 Join 요청을 반복 생성하기보다 이미 생성된 Registration과 Agent가 어디까지 진행됐는지 확인합니다.
>
> 반대로 Status는 정상인데 Resource가 보이지 않으면 DNS·TLS부터 다시 바꾸지 않습니다. Member API 접근·권한·동기화와 Host Component의 Resource 경로를 확인합니다.
>
> Resource는 보이는데 Monitoring이 없으면 Member 자체 Monitoring·Cluster Label·Prometheus Endpoint와 Host Monitoring 설정을 봅니다.
>
> 그리고 신규 Join 뒤 기존 Member까지 이상해지면 신규 Member만 계속 수정하지 않고 추가 변경을 멈춘 뒤 Host 공통 영향을 먼저 확인합니다.
>
> 따라서 확인 순서는 `Host 기준 상태 → Identity → DNS·Network·TLS → Join 정보 → 요청 → Agent → Status → Resource → Monitoring → 회귀`를 유지합니다.
>
> 이미 통과한 앞 단계를 근거 없이 다시 변경하지 않고, 마지막 성공과 첫 실패 지점을 기준으로 다음 확인을 정합니다.

---

# 13. MULTI-CLUSTER PASS를 판정한다

> `MULTI-CLUSTER PASS`는 Join 요청 성공에서 시작하지 않습니다. Join 전 신규 Member가 `MEMBER SELF PASS`이고 기존 Host와 기존 Member의 기준 상태가 정상인 것에서 시작합니다.
>
> 먼저 Host·Member Identity와 현재 Join 방식의 DNS·Network·TLS가 승인 기준으로 맞아야 합니다.
>
> 그다음 보호된 Join 정보가 현재 Host와 신규 Member를 위해 승인된 방식으로 사용되고 원문이 노출되지 않아야 합니다.
>
> 그리고 Member Agent와 Host Multi-Cluster Component가 정상이며 신규 Member Status가 Error나 Unknown 없이 정상이어야 합니다.
>
> **하지만 정상 Status만으로 통과시키지 않습니다.** Host에서 실제 Member Node·Namespace·Workload를 조회할 수 있고, Monitoring도 현재 신규 Member의 최신 Metric을 보여야 합니다.
>
> 그다음 Join 후에도 Member 자체 Kubernetes·Storage·Monitoring·KubeSphere 기능이 유지되고 기존 Host·PRD·DEV Member가 Join 전 상태를 유지해야 합니다.
>
> 반대로 목록만 표시되거나 Status·Resource·Monitoring 중 하나가 실패한 경우, 기존 환경 영향이나 보호정보 통제가 미확정인 경우는 `BLOCKED`입니다.
>
> 따라서 `MULTI-CLUSTER PASS`는 **정상 Member와 정상 Host가 실제 Resource 관리와 Monitoring 관측으로 연결되고, 그 과정에서 기존 환경에 회귀가 없는 상태**입니다.

# 14. 최종 인수에는 기능과 영향 결과를 넘긴다

> 다음 블록에는 Host·Member Cluster Name·Stage·Role과 Join 전 기존 환경 상태를 넘깁니다.
>
> 사용한 Join 방식과 Endpoint·DNS·Network·TLS 결과를 전달합니다.
>
> Agent·Host Component, 신규 Member Status와 실제 Resource·Monitoring 결과도 이어갑니다.
>
> Join 후 Member 자체 기능과 기존 Host·PRD·DEV Member의 회귀 확인 결과도 남깁니다.
>
> 보호된 값은 원문을 제외하고 종류·사용·정리 상태만 전달합니다.
>
> 미해결 항목은 마지막 성공, 첫 실패·미확인 지점, 영향과 담당자를 기록합니다.

# 15. 마무리

> Member 자체가 정상이어도 기존 Host의 관리·관측 기능은 별도로 확인해야 했습니다.
>
> 그래서 먼저 기존 Host와 Member의 상태를 확인하고, Host·신규 Member Identity와 DNS·Network·TLS를 점검했습니다.
>
> 그다음 승인된 Join 정보를 사용해 요청을 생성하고 Agent·Status·Resource·Monitoring을 확인했습니다.
>
> 마지막으로 기존 Host와 기존 Member에 영향이 없는지 확인했습니다.
>
> **결국 MULTI-CLUSTER PASS는 Host 화면에 이름이 보이는 상태가 아니라, Host에서 신규 Member를 실제로 관리·관측할 수 있고 기존 환경도 정상인 상태입니다.**
