# 전체 구축 최종 인수·증적·잔여 항목 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 이번 블록은 8월 31일부터 9월 3일까지의 실제 결과를 확인하고 최종 상태를 판정하는 과정이다. 마지막 화면만 보지 않고 **입력·Kubernetes·Storage·Monitoring·KubeSphere·Host Join과 기존 환경 영향, 보호정보 정리까지 확인한다.**
>
> 최종 상태는 `PASS / PARTIAL / BLOCKED`로 구분한다. Password·Token·JWT·kubeconfig·Secret Data·Private Key와 Certificate Key 원문은 증적에 포함하지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
각 단계의 PASS 또는 BLOCKED 결과가 있다
→ 먼저 모든 결과가 같은 신규 Member인지 확인한다
→ 8/31 입력부터 9/3 Host Join까지 순서대로 검토한다
→ 한 기능의 성공으로 다른 기능을 대신하지 않는다
→ 기존 환경 회귀와 보호정보·임시 Resource 정리를 확인한다
→ 남은 항목을 실제 영향으로 구분한다
→ PASS·PARTIAL·BLOCKED를 판정한다
→ 원본 증거와 판단 결과를 함께 인계한다
→ 9/4에는 문서·접근권한·임시 항목을 정리하고 철수한다
```

## 0-1. 오늘 전체 한 줄

> 최종 인수는 성공 화면을 모으는 작업이 아닙니다. **같은 신규 Member의 실제 기능과 남은 문제를 근거로 확인하고, 다음 담당자가 그대로 이어받을 수 있게 정리하는 작업**입니다.

---

# 1. 시작 — 현재 결과를 그대로 확인한다

> 앞 블록까지 `GO`, `KUBERNETES BASE PASS`, `STORAGE PASS`, `MONITORING PASS`, `MEMBER SELF PASS`, `MULTI-CLUSTER PASS`를 사용했습니다.
>
> 실제 현장에서는 모든 단계가 PASS일 수도 있고 중간에 BLOCKED가 남을 수도 있습니다.
>
> **하지만 최종 인수는 BLOCKED를 없었던 일로 만드는 절차가 아닙니다.** 마지막 Host Join이 성공했다고 앞 단계 증거가 자동으로 완성되는 것도 아닙니다.
>
> 따라서 어디까지 실제로 성공했고 처음 미완료인 단계가 어디인지 확인합니다.
>
> 그 전에 현재 Cluster Name·Stage·Context와 API Endpoint, Node Role·Hostname·IP, VIP-A·VIP-B, CIDR·Domain이 같은 신규 Member를 가리키는지 확인합니다. Storage Backend·StorageClass, Monitoring External Label, KubeSphere `clusterRole=member`와 Host Console 등록 이름도 같은 대상이어야 합니다.
>
> 각 증적에는 대상 Cluster·Stage, 확인 시각과 필요한 Context 또는 Endpoint가 드러나야 하며 과거 Reference Output은 현재 실행 증거로 사용하지 않습니다.
>
> 그리고 그 상태가 운영을 막는지, 안전과 인계에 어떤 영향을 주는지 판단합니다.

---

# 2. 8월 31일 — 검증된 설치 입력이 준비됐는지 확인한다

> 8월 31일에는 실제 VM·LB·Bastion·Node를 확인하고 Inventory와 변수 파일, Ansible Preflight를 준비했습니다.
>
> 최종 인수에서는 Role·Hostname·IP·Disk·VIP·CIDR·Domain이 근거 있는 신규 Member 값이었는지 확인합니다.
>
> Bastion과 Node의 SSH·sudo·Repository·Registry Trust·Filesystem 상태가 확인됐는지도 봅니다.
>
> 또한 Inventory Graph·Host Variable·Ping·원격 Identity·Become·Syntax 결과가 같은 Member를 가리켰는지 확인합니다.
>
> 이 결과가 정상이고 실행 승인 조건이 준비됐을 때 8월 31일의 `GO`가 성립합니다.
>
> `GO`는 실제 Kubernetes 기능 성공이 아니라 **검증된 입력으로 실행할 준비가 됐다는 결과**입니다.

---

# 3. 9월 1일 — 실제 Kubernetes 기능이 확인됐는지 본다

> 9월 1일에는 먼저 Kubespray 실행 결과를 확인합니다.
>
> Return Code와 PLAY RECAP, 최초 실패와 재실행이 있었다면 조치·재검증 결과를 봅니다.
>
> **하지만 Return Code 0만으로 Kubernetes 전체 기능을 통과시키지 않습니다.**
>
> 승인 VIP-A에서 API가 응답하고 실제 Version·CIDR·Domain이 입력값과 같은지 확인합니다.
>
> 예상 Node가 올바른 Name·IP·Role·Ready 상태로 등록되고 Control Plane이 정상인지 봅니다.
>
> 그다음 External ETCD Health, Runtime의 실제 Container 실행, CNI의 Pod IP와 통신, Service·Endpoint, DNS와 Ingress·VIP-B를 확인합니다.
>
> 이 범위가 실제 기능으로 확인됐을 때 `KUBERNETES BASE PASS`가 성립합니다.

---

# 4. 9월 2일 — Storage가 실제 사용까지 확인됐는지 본다

> Trident·Backend·StorageClass가 존재하는 것만으로 Storage를 통과시키지 않습니다.
>
> 먼저 Backend가 승인된 NetApp Storage에 online으로 연결됐는지 확인합니다.
>
> 그다음 Test PVC가 실제 PV와 Backend Volume으로 Provisioning됐는지 봅니다.
>
> Pod가 선택된 Node에서 Volume을 Mount하고, Container가 실제 Persistent Path에 데이터를 쓰고 읽었는지 확인합니다.
>
> 필요한 경우 Pod 재생성 뒤 데이터 유지와 Infra Node 조건도 봅니다.
>
> 마지막으로 `reclaimPolicy`에 따라 Test PVC·PV·Backend Volume이 정상적으로 정리됐는지 확인합니다.
>
> **PVC Bound는 Provisioning 성공일 뿐 Mount·Write/Read·Lifecycle을 대신하지 않습니다.**
>
> 이 전체 결과가 확인됐을 때 `STORAGE PASS`가 성립합니다.

---

# 5. 9월 3일 — Monitoring과 Member KubeSphere를 확인한다

> Monitoring에서는 Prometheus와 Grafana Pod가 Running인지만 보지 않습니다.
>
> CRD·PVC·Infra 배치가 정상이고 ServiceMonitor가 실제 Service·Endpoint를 발견하는지 확인합니다.
>
> 주요 Target과 External ETCD Target이 UP인지 보고, 실제 Query가 최근 현재 Member Metric과 올바른 Cluster Label을 반환하는지 봅니다.
>
> Grafana Datasource·Dashboard와 Monitoring Ingress도 같은 Member 데이터를 보여야 합니다.
>
> 이 결과가 `MONITORING PASS`입니다.
>
> 그다음 Member KubeSphere에서는 Installer Pod보다 내부 Task와 실제 Workload를 확인합니다.
>
> Infra 배치, KubeSphere PVC Mount, External Monitoring 사용, Console·API와 실제 `clusterRole=member`를 봅니다.
>
> Host가 없어도 Member 자체가 정상일 때 `MEMBER SELF PASS`가 성립합니다.

---

# 6. Host Join — 등록이 아니라 실제 관리·관측을 확인한다

> Host Join에서는 Join 전 기존 Host와 기존 Member 상태가 기록돼 있는지 먼저 확인합니다.
>
> Host·Member의 이름·Stage·Role과 현재 Join 방식의 DNS·Network·TLS, 보호된 Join 정보 사용이 정상이어야 합니다.
>
> Join 요청 뒤 Agent와 Host Component, 신규 Member Status를 확인합니다.
>
> **하지만 Host 목록에 이름이 보이는 것만으로 Multi-Cluster 기능을 통과시키지 않습니다.**
>
> Host에서 실제 Member Node·Namespace·Workload를 조회할 수 있어야 합니다.
>
> 현재 Member Monitoring도 Host에서 확인할 수 있어야 합니다.
>
> Join 후 Member 자체 기능이 유지되고 기존 Host·PRD·DEV Member에 영향이 없어야 합니다.
>
> 이 결과가 `MULTI-CLUSTER PASS`입니다.

---

# 7. 증적은 원본 결과와 판단을 함께 남긴다

> 최종 인수에서는 원본 결과와 판단을 분리해서 생각하되 둘을 함께 남겨야 합니다.
>
> 먼저 원본 출력은 실제로 어떤 명령·UI·Event·Log·Target·Query·기능 시험 결과가 있었는지를 보여 줍니다.
>
> 그다음 판단 문장은 그 결과가 어떤 대상을 확인했고 어디까지를 증명하는지 설명합니다.
>
> 그래서 원본 출력만 있으면 다음 담당자가 다시 해석해야 하고, 판단 문장만 있으면 실제 근거를 검증할 수 없습니다.
>
> **하지만 성공 화면 한 장이 전체 기능을 증명하지는 않습니다.** 예를 들어 PVC Bound 출력은 Provisioning을 보여 주지만 Mount·Write/Read를 대신하지 않고, Target UP 화면은 Scrape 성공을 보여 주지만 올바른 Member Query까지 대신하지 않습니다.
>
> 따라서 각 증적에는 대상 Cluster·Stage·확인 시각과 필요한 Context 또는 Endpoint가 드러나야 하고, 그 결과가 증명하는 범위를 함께 적습니다.
>
> 실패나 미확정이 있다면 먼저 마지막으로 성공한 단계와 처음 실패하거나 확인하지 못한 지점을 기록합니다.
>
> 그다음 운영 영향, 다음 읽기 전용 확인, 변경이 필요한 경우 승인 조건과 담당자를 연결합니다.
>
> Screenshot은 필요한 부분만 사용하고 보호정보를 Masking합니다.
>
> 반대로 원본 로그를 성공 문장으로 바꾸거나 과거 Reference Output과 현재 실행 결과를 섞으면 현재 상태를 다시 검증할 수 없으므로 인수 증거로 사용하지 않습니다.
>
> 결국 좋은 증적은 출력의 양이 많은 것이 아니라 **현재 신규 Member에서 무엇이 실제로 확인됐고 무엇이 아직 확인되지 않았는지를 다시 추적할 수 있는 증거**입니다.

---

# 8. 기존 환경 회귀와 보호정보·임시 Resource 정리를 확인한다

> 신규 Member가 정상이어도 기존 Host나 기존 Member가 영향을 받으면 최종 PASS가 아닙니다.
>
> 먼저 Join 전 결과와 비교해 기존 Host Component, PRD·DEV Member Status, 대표 Resource와 Monitoring이 유지되는지 확인합니다.
>
> 그다음 Shared Config·Datasource·Cluster Label·Endpoint가 신규 Member 값으로 변경되지 않았는지도 봅니다.
>
> 그래서 신규 Member의 성공 결과와 기존 환경 무영향 결과를 서로 다른 인수 조건으로 확인합니다.
>
> **하지만 기존 환경에 이상이 생겼는데 신규 Member가 정상이라는 이유로 최종 PASS를 선언하지 않습니다.** 공통 Host 설정이나 Multi-Cluster Component 영향은 여러 Member로 확대될 수 있습니다.
>
> 반대로 기존 환경 이상이 신규 작업 때문인지 불명확하면 원래 문제라고 추측하지 않습니다. Join 전 기준 상태와 현재 상태를 비교해 영향 범위를 확인하고 추가 변경을 멈춥니다.
>
> 그리고 기능 회귀와 별도로 보호정보 정리도 확인합니다.
>
> 문서·Screenshot·Shell History·Clipboard·임시 파일에 Password·Token·JWT·kubeconfig·Private Key·Secret Data가 남아 있지 않은지 확인합니다.
>
> Join 정보가 일회성 또는 제한된 유효기간을 갖는다면 Rotation이나 폐기 여부도 봅니다.
>
> 그다음 Test Pod·Service·Ingress·PVC·PV·Backend Volume과 임시 Manifest·Credential 파일이 정책대로 정리됐는지 확인합니다.
>
> **삭제 명령 실행과 실제 정리 결과는 다릅니다.** PVC 삭제 후 PV·Backend Volume, 임시 Secret 삭제 후 참조 Resource처럼 실제 잔여 상태를 다시 확인해야 합니다.
>
> 따라서 최종 정리는 단순한 청소가 아니라 기존 환경 무영향, 보호정보 통제와 테스트 자원 Lifecycle까지 인수 범위 안에서 닫는 과정입니다.

---

# 9. 남은 항목은 실제 영향으로 구분한다

> 최종 인수에서는 남아 있는 항목의 개수보다 실제 운영 영향이 중요합니다.
>
> 먼저 각 단계는 그 단계의 실제 사용 결과로 판단하며, 한 단계의 성공으로 다른 단계의 성공을 대신하지 않습니다.
>
> 확인이 끝난 기능은 `완료`로 남깁니다.
>
> 그다음 합의된 범위 안에서 남은 문서 보완·추가 Dashboard·교육 산출물이 핵심 운영을 막지 않는다면 `비차단 잔여`로 구분할 수 있습니다.
>
> **하지만 비차단 잔여라고 쓰려면 왜 운영을 막지 않는지 설명할 수 있어야 합니다.** 영향이 불명확한 항목을 일정 때문에 비차단으로 분류하지 않습니다.
>
> Kubernetes 기본 기능, Storage Mount·Write/Read, Monitoring Target·Query, KubeSphere 핵심 기능, Host Resource·Monitoring과 기존 환경 회귀 문제는 `차단`입니다.
>
> 현재 팀에 값이나 권한이 없어 다른 담당자의 확인이 필요한 항목은 `외부 확인`으로 남길 수 있습니다.
>
> 반대로 외부 담당자가 확인해야 한다는 이유만으로 자동으로 비차단이 되는 것은 아닙니다. 그 미확정 항목이 현재 운영 시작을 막는지 별도로 판정해야 합니다.
>
> 따라서 각 잔여 항목에는 마지막 성공, 첫 실패·미확인 지점, 운영 영향, 다음 확인, 담당자와 기한을 기록합니다.
>
> `확인 필요`만 적고 완료 처리하지 않고, 다음 담당자가 무엇을 확인해야 상태가 바뀌는지까지 남깁니다.

---

# 10. PASS·PARTIAL·BLOCKED를 구분한다

## 10.1 PASS

> `PASS`는 단순히 핵심 Pod가 Running인 상태가 아니라 합의된 인수 범위의 핵심 기능과 필수 산출물이 모두 완료된 상태입니다.
>
> 먼저 Kubernetes·Storage·Monitoring·Member KubeSphere·Multi-Cluster가 실제 기능 검증으로 정상이어야 합니다.
>
> 그다음 기존 환경 회귀가 없고 보호정보·임시 Resource 정리까지 확인돼야 합니다.
>
> 그리고 인수 범위 안에 아직 완료해야 할 항목이 없을 때 `PASS`입니다.

## 10.2 PARTIAL

> `PARTIAL`은 핵심 운영 기능과 안전 조건은 정상하지만 인수 범위 안의 비핵심 산출물이 명시적으로 남아 있는 상태입니다.
>
> 먼저 남은 항목이 Kubernetes·Storage·Monitoring·KubeSphere·Host 관리 기능이나 기존 환경 안전을 막지 않는지 확인합니다.
>
> 그다음 왜 운영을 막지 않는지, 현재 영향과 담당자, 완료 기한이 확정돼야 합니다.
>
> **하지만 핵심 기능이나 안전 조건이 미확정인데 일정만 남았다는 이유로 PARTIAL을 사용하지 않습니다.**
>
> 따라서 `PASS`는 인수 범위의 미완료가 없고, `PARTIAL`은 운영을 막지 않는 비핵심 미완료만 추적 가능하게 남은 상태입니다.

## 10.3 BLOCKED

> `BLOCKED`는 핵심 기능, 기존 환경 회귀, 보호정보 통제 또는 핵심 증거 중 하나라도 미해결인 상태입니다.
>
> Kubernetes 기본 기능, Storage Mount·Write/Read, External ETCD Target과 현재 Member Query, KubeSphere 핵심 Task·Role, Host Resource·Monitoring 실패가 여기에 포함됩니다.
>
> 그리고 기존 Host·Member 영향이 발생했거나 보호된 값 노출·정리 상태가 미확정인 경우도 최종 완료로 넘기지 않습니다.
>
> 반대로 화면상 일부 기능이 정상이어도 처음 미완료인 핵심 단계가 남아 있다면 그 뒤의 성공으로 덮지 않습니다.
>
> 따라서 핵심 기능 실패나 안전 미확정을 일정 때문에 `PARTIAL`로 낮춰 기록하지 않고 `BLOCKED`로 남긴 뒤 마지막 성공·첫 실패·영향과 다음 조치를 인계합니다.

---

# 11. 문제가 생기면 처음 미완료인 단계만 확인한다

> Kubernetes 증거가 부족하면 Storage를 다시 만들지 않습니다. 어떤 API·Node·ETCD·Runtime·CNI·DNS·Ingress 증거가 빠졌는지 확인합니다.
>
> Storage는 정상인데 Monitoring PVC Mount 증거가 없다면 Trident 전체를 재설치하지 않고 현재 Monitoring PVC와 Pod Mount를 봅니다.
>
> Target은 UP인데 Grafana가 비어 있다면 Endpoint를 다시 만들지 않고 Datasource·Query·Label을 확인합니다.
>
> Console은 정상인데 Member Role 증거가 없다면 Host Join을 반복하지 않고 실제 `clusterRole`을 봅니다.
>
> Host에 이름은 보이지만 Resource가 없다면 Join 요청을 다시 만들기보다 API·Agent·권한을 확인합니다.
>
> 확인 순서는 `8/31 입력 → 9/1 Kubernetes → 9/2 Storage → 9/3 Monitoring → Member KubeSphere → Host Join → 회귀·보안`입니다.

# 12. 최종 증적 패킷과 현지 인계를 완성한다

> 최종 증적에는 현재 Member Identity와 8월 31일 실제값·Inventory·Preflight 근거를 포함합니다.
>
> 9월 1일 Kubespray·API·Node·ETCD·Runtime·CNI·DNS·Ingress 결과를 연결합니다.
>
> 9월 2일 Storage Provisioning·Mount·Write/Read·Cleanup 결과도 포함합니다.
>
> 9월 3일 Monitoring Target·Query·Grafana, Member KubeSphere Workload·PVC·Monitoring·Role과 Host Join·Resource·Monitoring·회귀 결과를 함께 남깁니다.
>
> 최종 판정, 잔여 항목, 판정 시각과 담당자도 기록합니다.
>
> 보호정보 원문은 포함하지 않습니다.
>
> 현지 담당자에게 문서 위치만 전달하지 않습니다. 정상 기준, 문제가 생겼을 때 확인 순서, 잔여 항목의 영향과 다음 행동을 설명합니다.
>
> 다음 담당자가 현재 상태를 이해하고 운영 판단을 이어갈 수 있을 때 인계가 완료됩니다.
>
> 9월 3일 종료 시점에 기술 상태를 확정하고, 해결하지 못한 핵심 기능은 `BLOCKED`로 마지막 성공·첫 실패·영향·다음 조치를 인계합니다.
>
> 9월 4일에는 증적·문서·보호정보·임시 파일·Test Resource와 접근 권한을 정리하고 현지 담당자 확인 뒤 철수합니다. 9월 4일 작업을 이유로 9월 3일 기술 판정을 미루지 않습니다.
