# Member KubeSphere 설치·기능·Pre-Join Gate 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 `MONITORING PASS`를 입력으로 받아 **검증된 Storage와 Monitoring을 실제 Member KubeSphere가 사용하고, `clusterRole=member`와 Platform Workload 배치·Console·API가 의도대로 성립했는지 판정하는 법**을 가르친다. `kubesphere-installer.yaml`, ClusterConfiguration과 세부 Module의 정확한 적용 절차는 Member KubeSphere Runbook에서 수행한다.

## 0. Monitoring 블록에서 이어받는 것

```text
Cluster Name·Stage·Context
MONITORING PASS / BLOCKED
StorageClass·Monitoring PVC 실제 사용 증거
Prometheus Service·Endpoint
External ETCD Target UP
Grafana Datasource·Query 결과
Monitoring Ingress·VIP-B
Infra Node 배치 기준
Registry·Image 기준
KubeSphere external Monitoring Endpoint 후보·근거
```

> Monitoring이 BLOCKED라면 KubeSphere 설치로 넘어가지 않습니다. Installer 내부 Monitoring Task에서 같은 실패를 다시 만들지 않습니다.

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> `ks-installer` Pod Running을 설치 완료로 보지 않고, **Installer 실행기 → ClusterConfiguration 실제값 → 내부 Task → Platform Workload → Storage·Monitoring 연동 → Console·API → member Role**을 독립 증거로 확인해 Host Join 전 Member 자체 정상 여부를 판정할 수 있어야 한다.

오늘의 중심 질문:

> **KubeSphere Installer가 실행된 것이 아니라, 검증된 Storage와 Monitoring을 사용하는 실제 Member Platform이 준비됐는가?**

---

# 1. 시작 — installer와 ClusterConfiguration은 역할이 다르다

```text
kubesphere-installer.yaml
→ KubeSphere 설치를 수행할 실행기·CRD·RBAC·Deployment 준비

ClusterConfiguration
→ 이 Member에 어떤 기능·Role·Storage·Monitoring·Registry를 구성할지 정의
```

따라서:

```text
Installer Pod Running
≠ ClusterConfiguration의 모든 Task 성공
```

> Host용 Manifest를 복사해 `clusterRole`만 member로 바꾸는 방식은 금지합니다. StorageClass, Monitoring Endpoint, ETCD, Registry, Node 배치와 Domain이 모두 Cluster별 실제값입니다.

---

# 2. 적용 전 Member 핵심값을 한 장에 고정한다

```text
current-context: _________________________________________
Cluster Name·Stage: _____________________________________
clusterRole 기대값: member
StorageClass: ____________________________________________
Registry·Project·Tag: ____________________________________
External ETCD: ___________________________________________
Monitoring Type: _________________________________________
External Prometheus Endpoint: _____________________________
Console·Ingress Domain: __________________________________
Infra Node Selector·Toleration: ___________________________
Module Enable·Disable 기준: ______________________________
```

보호된 값은 구조만 확인한다.

```text
Join 관련 Secret·JWT·kubeconfig
ETCD Certificate Secret
Registry Credential
Private Key·Password
```

> 원문은 문서·로그·화면에 남기지 않습니다.

## 2.1 현재 Member 값 대조가 Apply보다 먼저다

```text
Manifest 문법 정상
≠ 현재 Member 설정 정상

과거 Host에서 성공한 ClusterConfiguration
≠ 신규 Member에서 사용 가능
```

---

# 3. Installer Pod 자체와 내부 Task를 분리한다

먼저 두 실패를 구분한다.

```text
Installer Pod 자체가 Pending·ImagePullBackOff·Crash
vs
Installer는 Running이지만 내부 Task 실패
```

## 3.1 Installer Pod 자체가 시작되지 않는 경우

첫 확인:

| 증상 | 먼저 볼 것 |
|---|---|
| Pending | Node Selector·Taint·PVC·Resource |
| ImagePullBackOff | Registry·Tag·CA·Secret |
| CrashLoopBackOff | Pod Log·Config·권한 |

> 내부 Monitoring·Multicluster Task를 보기 전에 실행기 자체가 정상적으로 동작해야 합니다.

## 3.2 Installer Running은 시작점이다

```text
ks-installer Running
→ 설치 Task를 수행할 실행기가 준비됨
```

하지만:

```text
ks-installer Running
≠ KubeSphere 설치 완료
```

정확한 완료는 Installer Log와 생성된 Workload·기능으로 확인한다.

---

# 4. Installer 로그 — 실패 Task 범위를 먼저 고정한다

Installer Log에서 먼저 확인할 것:

```text
어느 Task 범주인가
최초 실패는 무엇인가
Monitoring·Multicluster·Network·Common 중 어디인가
오류 원문은 무엇인가
앞에서 이미 PASS한 기능과 충돌하는가
```

대표 Task 범주:

```text
common
monitoring
multicluster
network
logging·events·alerting 등 현재 Bundle Module
```

> 정확한 Task 이름은 현재 로그를 기준으로 합니다.

## 4.1 Monitoring Task 실패

먼저 9월 3일 첫 블록 증거와 연결한다.

```text
External Prometheus Endpoint
Prometheus Service·Endpoint
Monitoring PVC
CRD
현재 Member Label
```

> Monitoring PASS가 있는데 Installer가 다른 Endpoint를 참조하면 KubeSphere 설정 문제입니다. Storage·Monitoring을 재설치하지 않습니다.

## 4.2 CRD not found

```text
CRD 실제 존재·Established
→ Installer가 기대하는 Version·Kind
```

을 비교한다.

## 4.3 Multicluster Task 실패

```text
clusterRole=member
Join 관련 설정 구조
Host 연결 전제
보호된 값의 현재 Member 대응 여부
```

를 먼저 확인한다.

---

# 5. ClusterConfiguration의 핵심은 Member 역할과 외부 의존성이다

KubeSphere에서 반드시 대조할 연결:

```text
Storage
→ 9/2 검증 StorageClass

Monitoring
→ 오늘 MONITORING PASS한 Prometheus Endpoint

Registry
→ 현재 Member 승인 Registry·Image

External ETCD
→ 현재 Member Endpoint·Secret 참조

Multi-Cluster Role
→ member

Platform 배치
→ 승인 Infra Node 정책
```

## 5.1 `clusterRole=member`의 의미

```text
member
→ 중앙 Host가 아닌 관리 대상 Member Cluster 역할
```

구분:

```text
YAML에 member 문자열 존재
≠ 실제 Member Platform 전체 정상
```

> Role은 Join 전제 중 하나일 뿐입니다.

---

# 6. Platform Workload — Manifest 배치 조건과 실제 Pod 배치를 분리한다

확인할 것:

```text
Node Label
Node Taint
Workload nodeSelector
Toleration
Replica 수
실제 Pod NODE
```

증거:

```text
Manifest에 Infra Selector 있음
+ 실제 Pod가 승인 Infra Node에 배치
+ 필요한 Replica 분산
= 배치 정책 반영
```

하지만:

```text
Pod Running
≠ 올바른 Node 배치
```

## 6.1 Pending이면 KubeSphere 자체 오류로 단정하지 않는다

```text
nodeSelector와 실제 Label
Taint·Toleration
PVC Binding
Resource Request
Scheduler Event
```

순으로 본다.

---

# 7. KubeSphere가 실제 Storage를 사용하는가

> 9월 2일 Storage PASS와 Monitoring PVC 성공 뒤에도 KubeSphere 자체 PVC는 별도 요청일 수 있습니다.

확인:

```text
KubeSphere 관련 PVC가 승인 StorageClass 사용
Bound
실제 Pod Mount
FailedMount 없음
필요한 데이터 경로 사용
```

구분:

```text
9/2 Test PVC 성공
≠ KubeSphere PVC 자동 성공

Monitoring PVC 성공
≠ KubeSphere PVC 자동 성공
```

> Namespace·용량·배치 Node가 다를 수 있습니다.

---

# 8. External Monitoring — Endpoint 기재와 실제 사용을 구분한다

KubeSphere는 외부 Monitoring을 사용하도록 설정될 수 있다.

정상 경로:

```text
KubeSphere
→ External Monitoring Endpoint
→ 오늘 검증한 Prometheus Service
→ 실제 Query
→ 현재 Member Metric 표시
```

확인:

```text
Endpoint가 현재 Monitoring Service인가
Port·Scheme이 실제 서비스와 맞는가
KubeSphere UI/API에서 Monitoring 데이터가 보이는가
Cluster Identity가 현재 Member인가
```

구분:

```text
Endpoint 문자열 존재
≠ KubeSphere Monitoring 기능 정상
```

---

# 9. Console·API — 화면이 열리는 것과 Platform 정상은 다르다

확인 경로:

```text
DNS·VIP-B·Ingress
→ KubeSphere Console Service
→ Console 응답
→ API
→ Platform 기능
```

반드시 구분한다.

```text
Console 열림
≠ API 정상

Console·API 정상
≠ Storage·Monitoring·Role·Workload 배치 정상
```

> 화면 하나를 최종 증거로 사용하지 않습니다.

---

# 10. 주요 Workload는 개수가 아니라 역할과 기능으로 본다

현재 Bundle의 핵심 Platform Workload를 확인한다.

최소 질문:

```text
필수 Deployment·StatefulSet이 Ready인가
반복 Restart가 없는가
실제 Infra 배치가 맞는가
Service·Endpoint가 연결되는가
Critical Event가 없는가
```

> 정확한 Component 이름과 Replica 수는 현재 Bundle을 기준으로 합니다. 과거 Host·Member의 Pod 수를 신규 Member 기대값으로 사용하지 않습니다.

---

# 11. Installer 완료와 Member 기능 완료를 분리한다

```text
Installer Task 성공
→ 설치 자동화 완료
```

하지만 최종 Member 자체 성공은 다음을 추가로 요구한다.

```text
Console·API
Storage PVC·Mount
External Monitoring
clusterRole=member
Platform Workload 배치
Ingress·Network
Critical Event 없음
```

즉:

```text
INSTALLER PASS
≠ MEMBER SELF PASS
```

---

# 12. Member 자체 Pre-Join 검증을 다시 묶는다

Host Join 전에 Member는 독립적으로 정상이어야 한다.

## 12.1 Kubernetes

```text
9/1 KUBERNETES BASE PASS 유지
API·Node·CNI·DNS·Ingress Critical Error 없음
```

## 12.2 Storage

```text
9/2 STORAGE PASS 유지
KubeSphere·Monitoring PVC Mount 정상
```

## 12.3 Monitoring

```text
MONITORING PASS
External ETCD Target UP
Grafana Query 정상
```

## 12.4 KubeSphere

```text
Installer 핵심 Task 성공
Console·API 정상
clusterRole=member
External Monitoring 실제 사용
Platform Workload 배치 정상
```

## 12.5 Identity·Network

```text
Cluster Name·Stage
VIP-A·VIP-B
Domain
Host Join에 필요한 DNS·Network·TLS 전제
```

> Member 자체 장애를 Host Join으로 덮지 않습니다.

---

# 13. MEMBER SELF PASS를 판정한다

## 13.1 MEMBER SELF PASS

```text
KUBERNETES BASE PASS 유지
+ STORAGE PASS 유지
+ MONITORING PASS
+ installer 핵심 Task 성공
+ KubeSphere 주요 Workload Ready
+ Console·API 실제 접근 정상
+ clusterRole=member
+ External Monitoring 실제 기능 정상
+ KubeSphere PVC·Mount 정상
+ Infra 배치 정책 정상
+ Registry·Image 오류 없음
+ Critical Event 없음
+ Join에 필요한 Network·Identity 전제 확인
```

> 이 판정이 Host Join의 입력입니다.

## 13.2 BLOCKED

```text
Kubernetes·Storage·Monitoring 기존 Gate 회귀
Installer 핵심 Task 실패
KubeSphere PVC Mount 실패
Console·API 핵심 기능 실패
clusterRole 오류
External Monitoring 연결 실패
Platform Workload 핵심 Pod 비정상
잘못된 Cluster Identity·Domain·Registry 혼입
Host Join 전제 Network·DNS·TLS 미확정
```

> BLOCKED Member를 Host에 Join해 상태를 더 복잡하게 만들지 않습니다.

---

# 14. Host Join 블록으로 넘길 증거

```text
Cluster Name·Stage·Context
MEMBER SELF PASS / BLOCKED
Kubernetes·Storage·Monitoring 기존 Gate 결과
Installer Log·핵심 Task 결과
KubeSphere Console·API
clusterRole=member 증거
External Monitoring Endpoint·실제 기능
KubeSphere PVC·Mount 결과
Platform Workload·실제 Infra 배치
Member VIP-A·VIP-B·Domain
Join에 필요한 보호값 종류·전달 절차
미해결 Member 자체 항목
```

> Join 정보의 원문은 넘기지 않고 승인된 전달 경로와 값의 종류만 문서화합니다.

---

# 15. 마무리 — Member KubeSphere 완료를 한 문장으로 다시 말한다

> Member KubeSphere 설치는 `ks-installer` Pod를 띄우는 일이 아닙니다.
>
> 검증된 Storage와 Monitoring, Registry와 ETCD를 현재 Member 실제값으로 연결하고, Installer 내부 Task가 성공하며, Platform Workload가 승인된 Infra Node에 배치되고, Console·API와 external Monitoring이 실제로 기능하며, `clusterRole=member`가 의도대로 적용되어야 합니다.
>
> **결국 Host Join 전에 신규 Member는 Host 도움 없이도 Kubernetes·Storage·Monitoring·KubeSphere 자체 기능이 정상인 독립된 Member여야 합니다.**
