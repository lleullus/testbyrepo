# Member Monitoring 전체 경로·Target·Grafana 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> Kubernetes와 Storage가 정상이어도 Cluster 상태를 지속적으로 관측할 수 있는 것은 아니다. 이번 블록은 **현재 신규 Member의 Metric이 실제 Target에서 수집되고, Query·Grafana·Ingress까지 이어지는지 확인하는 과정**이다.
>
> Manifest·CRD·Secret·ServiceMonitor·Ingress 적용은 승인된 Monitoring Runbook을 따른다. 다른 Cluster의 Endpoint·Domain·StorageClass·Label을 사용하지 않고 ETCD Certificate·Private Key·Token·Secret Data 원문을 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
Kubernetes와 Storage가 준비됐다
→ 하지만 지속적인 관측 기능은 별도다
→ 먼저 현재 Member와 실행 조건을 확인한다
→ API가 Monitoring 객체를 이해하도록 CRD를 준비한다
→ Prometheus·Alertmanager·Grafana를 설치한다
→ 실제 Pod 배치와 PVC Mount를 확인한다
→ ServiceMonitor가 Service·Endpoint를 발견해야 한다
→ External ETCD는 Endpoint·Service로 연결한다
→ Target UP과 실제 Query를 확인한다
→ Grafana와 외부 Ingress에서 현재 Member 데이터를 확인한다
```

## 0-1. 오늘 전체 한 줄

> Monitoring 완료는 Pod가 Running인 상태가 아닙니다. **현재 신규 Member의 Metric이 수집·저장·질의되고, Grafana와 외부 경로에서 실제로 보이는 상태**입니다.

---

# 1. 시작 — Cluster가 정상이어도 계속 관측할 수 있는 것은 아니다

> 9월 2일까지 Kubernetes가 Pod를 실행하고 Persistent Storage를 사용할 수 있는 것을 확인했습니다.
>
> **하지만 운영자가 매번 Node와 Pod에 들어가 CPU·Memory와 상태 변화를 확인할 수는 없습니다.**
>
> 그래서 Metric을 수집하고 저장하는 Prometheus, Alert를 처리하는 Alertmanager, 화면으로 보여 주는 Grafana가 필요합니다.
>
> 다만 Component를 설치하는 것만으로 Monitoring이 완료되지는 않습니다.
>
> 현재 Member의 Target을 실제로 발견하고 Scrape해야 하며, 올바른 Label로 Query되고 사용자 화면과 외부 경로까지 연결돼야 합니다.

---

# 2. Monitoring Stack을 올리기 전에 기본 조건을 준비한다

> 먼저 현재 Context와 Cluster Name·Stage를 확인합니다. 9월 2일에 통과한 StorageClass, 현재 Registry·Image Tag, Monitoring Domain·VIP-B와 External ETCD Endpoint도 현재 신규 Member 값인지 확인합니다.
>
> 기존 Host Manifest에서 이름만 바꾸지 않고 현재 승인값을 사용합니다.
>
> 그다음 Monitoring Resource가 들어갈 Namespace를 확인합니다.
>
> External ETCD를 HTTPS로 Scrape한다면 현재 Member Certificate와 대응하는 Secret 참조를 준비합니다.
>
> Secret 이름이 같다고 같은 Certificate는 아닙니다. Namespace·Type·필요 Key 구조를 확인하되 Data 원문은 출력하지 않습니다.
>
> 그다음 Prometheus·Alertmanager·Grafana가 사용할 StorageClass와 PVC 조건을 `STORAGE PASS` 결과에서 이어받습니다.
>
> 또한 현재 Registry·Image Tag와 Infra Node의 Label·Taint가 Monitoring Workload 실행 조건과 맞는지 확인합니다.
>
> 이 조건을 먼저 확인해야 Pending·Image Pull·Mount 문제를 Prometheus 설정 문제와 구분할 수 있습니다.

---

# 3. Prometheus Operator CRD — API가 Monitoring 객체를 알아야 한다

> Prometheus Operator는 `Prometheus`, `ServiceMonitor`, `PrometheusRule` 같은 Custom Resource를 사용합니다.
>
> 그래서 Kubernetes API가 이 객체를 이해하도록 CRD를 먼저 준비합니다.
>
> 먼저 `Prometheus` Resource는 Prometheus Server의 Replica, Storage, Selector와 같은 실행 구성을 선언하는 객체입니다.
>
> 그다음 `ServiceMonitor`는 어떤 Service를 어떤 Port와 Path로 Scrape할지 선언하고, `PrometheusRule`은 Recording Rule과 Alert Rule을 Kubernetes Resource로 관리할 수 있게 합니다.
>
> 그래서 CRD는 단순히 추가 Resource 이름을 만드는 파일이 아니라 Operator가 Monitoring 구성을 Kubernetes API 객체로 읽고 관리할 수 있게 하는 기반입니다.
>
> Apply 성공은 CRD 생성 요청이 API Server에 받아들여졌다는 뜻입니다.
>
> **하지만 실제 사용 가능 상태는 필요한 CRD가 현재 Version으로 존재하고 `Established=True`인지 확인해야 합니다.**
>
> 그다음 현재 Stack이 사용하는 API Version과 CRD Schema가 맞는지도 봅니다. 과거 Bundle의 CRD가 남아 있거나 Version·Schema가 맞지 않으면 Manifest는 있어도 Operator가 Resource를 정상적으로 처리하지 못할 수 있습니다.
>
> 반대로 CRD가 모두 정상이어도 Operator가 없거나 권한이 없으면 `Prometheus`와 `ServiceMonitor` 객체를 실제 Pod와 Scrape 설정으로 바꾸지 못합니다.
>
> 따라서 CRD 단계에서는 Resource 정의가 준비됐는지까지만 확인하고, 실제 Monitoring Component 생성과 동작은 다음 Stack 단계에서 별도로 확인합니다.
>
> CRD가 없거나 Established되지 않았다면 Grafana나 Storage를 수정하지 않고 API 객체 정의부터 확인합니다.

---

# 4. Monitoring Stack — 실제 수집·저장·표시 Component를 설치한다

> CRD가 준비되면 현재 승인된 Stack Manifest를 확인합니다.
>
> 먼저 Monitoring Stack 안의 역할을 구분합니다. Prometheus Operator는 Custom Resource를 읽어 필요한 Monitoring Resource를 관리하고, Prometheus는 Target에서 Metric을 수집하고 저장하며 Query를 처리합니다.
>
> 그다음 Alertmanager는 Prometheus가 만든 Alert를 받아 Grouping·Routing·Silence 같은 알림 처리를 담당하고, Grafana는 Prometheus 같은 Datasource를 Query해 사용자가 볼 Dashboard를 제공합니다.
>
> 필요한 Exporter는 Node나 Application의 상태를 Prometheus가 Scrape할 수 있는 Metric Endpoint로 노출합니다.
>
> 그래서 Stack을 설치한다는 것은 Pod 몇 개를 띄우는 것이 아니라 수집·저장·알림·표시 역할을 각각 현재 Member 조건으로 연결하는 과정입니다.
>
> 그다음 Cluster·Stage External Label, Registry·Tag, StorageClass·PVC와 Node Selector·Toleration이 현재 Member 값인지 봅니다.
>
> External Label은 여러 Cluster의 Metric이 합쳐지거나 외부 시스템과 연동될 때 현재 Metric이 어느 Cluster·Stage에서 온 것인지 식별하는 기준이 될 수 있습니다.
>
> 그래서 다른 Cluster의 External Label을 사용해도 Prometheus Pod 자체는 정상적으로 Running일 수 있지만, Query와 Dashboard에서는 현재 Member가 아닌 것처럼 보이거나 다른 Cluster와 구분하기 어려울 수 있습니다.
>
> StorageClass도 같은 기준입니다. 잘못된 StorageClass를 사용하면 Prometheus나 Grafana PVC가 다른 Backend 정책으로 생성되거나 Pending 상태가 될 수 있습니다.
>
> 그리고 Registry·Image Tag가 현재 Xi'an Registry와 맞지 않으면 Pod가 생성돼도 Image Pull 단계에서 멈출 수 있습니다.
>
> 따라서 Manifest 문법이 맞는지만 보지 않고 External Label·Registry·StorageClass·Node 배치 조건이 모두 현재 신규 Member 값인지 먼저 확인합니다.
>
> 적용 후 Operator·Prometheus·Alertmanager·Grafana와 필요한 Exporter의 Ready·Restart·Event·Log를 확인합니다.
>
> **하지만 Pod Running은 Process 시작을 보여 줄 뿐 실제 Metric 수집 성공을 의미하지 않습니다.**
>
> 그래서 Stack Component가 정상적으로 기동한 뒤 실제 Pod 배치와 PVC, Discovery와 Target 단계로 이어서 확인합니다.

---

# 5. Pod 배치와 PVC — Manifest 설정이 실제 상태로 반영됐는지 본다

> Monitoring Manifest가 올바르더라도 실제 Pod가 의도한 Node에서 실행되고 Storage를 사용할 수 있어야 합니다.
>
> 먼저 주요 Monitoring Pod가 승인된 Infra Node에 배치됐는지 확인합니다.
>
> Selector와 Toleration이 실제 Node Label·Taint와 연결되는지도 봅니다. Infra Node에 배치할 의도인데 Worker에 실행되거나 Pending이라면 Monitoring 기능보다 배치 조건부터 확인해야 합니다.
>
> 그다음 Pending이면 Selector·Taint·Resource·PVC 중 어디에서 막혔는지 Scheduler Event를 확인합니다.
>
> 그래서 Pod Pending을 모두 Scheduling 문제로 보지 않습니다. PVC가 Pending이라 Pod가 기다리는 것인지, Node 조건이 맞지 않아 Scheduler가 배치하지 못하는 것인지 첫 실패 단계를 구분합니다.
>
> Monitoring PVC는 9월 2일 `STORAGE PASS`에서 확인한 승인 StorageClass를 사용해야 합니다.
>
> 먼저 PVC가 Bound됐는지 보고, 그다음 실제 Prometheus·Grafana Pod에 Volume이 Mount됐는지 확인합니다.
>
> **PVC Bound는 Pod Mount와 데이터 기록까지 증명하지 않습니다.**
>
> 그래서 Pod Spec의 PVC·Volume·`volumeMount`와 Container의 실제 MountPath를 대조합니다. `emptyDir`나 Container Local Path를 사용하고 있어도 Pod는 Running일 수 있으므로 실제 Persistent Volume인지 확인해야 합니다.
>
> 반대로 9월 2일 Worker Node에서 Test PVC가 성공했다는 사실만으로 Infra Node의 Monitoring Mount 경로까지 성공했다고 판단하지 않습니다. Monitoring Pod가 실제 배치된 Infra Node의 Trident Node Plugin·NFS Client·Data LIF 경로가 정상이어야 합니다.
>
> 따라서 Pod 배치와 PVC 단계에서는 Manifest의 의도가 실제 Infra Node·PVC·Mount 상태로 반영됐는지 확인하고, 실제 Metric 수집은 그다음 Discovery 단계에서 확인합니다.

---

# 6. ServiceMonitor — 수집 설정과 실제 Target을 연결한다

> Prometheus는 Cluster 안의 모든 Pod와 Service를 자동으로 Scrape하지 않습니다.
>
> 그래서 ServiceMonitor나 PodMonitor가 어떤 대상을 어떤 조건으로 수집할지 알려줘야 합니다.
>
> 먼저 ServiceMonitor는 Label Selector를 사용해 수집할 Service를 선택합니다. 그리고 해당 Service의 어느 Port 이름을 사용할지, 어떤 Scheme과 Path로 Metric을 요청할지 정의합니다.
>
> 그다음 Prometheus Resource 자체가 어떤 ServiceMonitor를 선택하도록 구성돼 있는지도 확인해야 합니다. ServiceMonitor가 정상이어도 Prometheus의 Selector 범위 밖이면 실제 Scrape Configuration에 들어가지 않을 수 있습니다.
>
> 그래서 ServiceMonitor가 존재한다는 사실만으로 실제 Target이 만들어졌다고 판단하지 않습니다.
>
> 먼저 Namespace와 Label Selector가 의도한 Service를 선택하는지 확인하고, 그다음 Service의 Port 이름이 ServiceMonitor의 Endpoint 설정과 정확히 연결되는지 봅니다.
>
> Service가 선택되면 실제 Endpoint 또는 EndpointSlice에 수집할 Address와 Port가 존재해야 합니다.
>
> **하지만 Endpoint가 존재한다는 사실만으로 Scrape 성공을 의미하지 않습니다.** Prometheus Pod에서 해당 Address까지 Network가 연결되고, HTTP·HTTPS Scheme, Path, TLS와 인증 조건까지 맞아야 합니다.
>
> 반대로 Prometheus Target 목록에 대상 자체가 나타나지 않는다면 Network나 TLS부터 확인하지 않습니다. 이 경우에는 Prometheus Selector → ServiceMonitor → Service Label → Port → Endpoint Discovery 순서로 먼저 봅니다.
>
> 따라서 ServiceMonitor 검증은 객체 존재를 확인하는 것이 아니라, 선언한 Discovery 조건이 실제 Service와 Endpoint를 지나 Prometheus Target으로 만들어졌는지 확인하는 과정입니다.

# 7. External ETCD Monitoring — 외부 대상을 Endpoint와 Service로 표현한다

> External ETCD는 Kubernetes Pod가 아니므로 Pod Selector만으로 발견할 수 없습니다.
>
> 그래서 Kubernetes 안에 실제 ETCD 대상을 표현하는 Resource를 별도로 만들어 Prometheus Discovery 경로에 연결합니다.
>
> 먼저 현재 신규 Member의 ETCD Address와 Metric Port를 Endpoint 또는 EndpointSlice로 표현합니다.
>
> 그다음 Service가 이 외부 Endpoint를 Kubernetes 내부의 하나의 Monitoring 대상으로 표현하고, ServiceMonitor는 해당 Service를 선택합니다.
>
> 그래서 External ETCD의 수집 경로는 실제 ETCD와 Kubernetes Discovery Resource를 구분해서 이해해야 합니다. Endpoint는 실제 외부 Address를 담고, Service는 Prometheus가 선택할 논리적 대상을 제공하며, ServiceMonitor는 그 Service의 Scrape 조건을 정의합니다.
>
> Endpoint 객체가 존재해도 내부 Address가 현재 신규 Member ETCD라는 뜻은 아닙니다. 먼저 Address·Port를 9월 1일에 검증한 ETCD 결과와 대조합니다.
>
> 그다음 Service의 Port와 ServiceMonitor의 Port 이름·Scheme·Path가 같은 수집 경로를 가리키는지 확인합니다.
>
> External ETCD가 HTTPS와 Client Certificate를 요구한다면 TLS 조건도 별도로 확인합니다.
>
> 먼저 CA는 Prometheus가 ETCD Server Certificate를 신뢰할 수 있는지와 연결되고, Client Certificate와 Private Key는 ETCD가 Prometheus Client를 인증하는 데 사용될 수 있습니다.
>
> 그리고 Server Name 검증이 필요한 환경에서는 접속 Address와 Certificate의 이름 조건이 맞아야 합니다.
>
> **하지만 Secret 이름이 존재한다는 사실만으로 올바른 CA·Certificate가 연결됐다고 판단하지 않습니다.** 현재 Member용 Secret 참조와 필요한 Key 구조를 확인하되 Secret Data 원문은 출력하지 않습니다.
>
> 반대로 Target이 아예 생성되지 않았다면 TLS Certificate부터 교체하지 않습니다. 먼저 Endpoint·Service·ServiceMonitor Discovery가 실제 Target을 만들었는지 확인합니다.
>
> 따라서 External ETCD는 `대상 표현 → Service 연결 → ServiceMonitor 선택 → Target 생성 → TLS·Network Scrape → Query` 순서로 확인합니다.
>
> 결국 이 단계의 완료 기준은 ETCD 관련 Kubernetes 객체가 존재하는 것이 아니라, **현재 신규 Member ETCD가 Prometheus Target으로 발견되고 실제 ETCD Metric을 반환할 준비가 된 상태**입니다.

---

# 8. Target UP 뒤에는 실제 Metric과 Label을 확인한다

> Target `UP`은 Prometheus가 해당 Endpoint에 Scrape 요청을 보내고 응답을 받아 Metric을 수집했다는 뜻입니다.
>
> 그래서 Target Health는 Discovery 다음 단계가 실제 Network·Protocol·TLS 조건까지 통과했는지 보여 주는 중요한 증거입니다.
>
> **하지만 Target이 UP이라는 사실만으로 현재 신규 Member의 올바른 대상에서 Metric을 받고 있다는 뜻은 아닙니다.** 다른 Cluster Endpoint를 가리키거나 잘못된 External Label을 사용해도 Scrape 자체는 성공할 수 있습니다.
>
> 먼저 Target 화면에서 Job·Instance·Endpoint와 Last Scrape, Scrape Duration과 오류 여부를 확인합니다.
>
> 그다음 실제 Query로 현재 Member의 Node·Pod·ETCD Metric을 확인합니다.
>
> 그래서 단순히 Metric 이름이 반환되는지만 보지 않고 결과의 Cluster·Stage·Instance Label이 현재 신규 Member를 나타내는지 확인합니다.
>
> 그리고 Metric의 최근 시각과 실제 Node 수, ETCD Member 상태 같은 현재 Cluster 사실과 결과를 대조합니다. 오래된 Series나 다른 Cluster의 Label이 섞여 있으면 Target UP만으로 정상이라고 판단하지 않습니다.
>
> 반대로 Target이 UP인데 Query 결과가 없으면 Discovery나 Network부터 다시 수정하지 않습니다. Scrape된 Metric 이름, Label Filter, Query 범위와 실제 Series 존재 여부를 먼저 확인합니다.
>
> `PrometheusRule`도 객체 존재 여부만 보지 않고 Prometheus가 실제 Rule을 Load했는지 확인합니다. Rule Syntax나 Selector가 잘못되면 Resource는 있어도 기대한 Recording·Alert 결과가 만들어지지 않을 수 있습니다.
>
> Alertmanager의 실제 알림 전달 시험은 승인된 범위에 따라 수행합니다.
>
> 따라서 Target 단계의 완료 기준은 녹색 `UP` 표시 하나가 아니라, **현재 신규 Member의 실제 Metric이 최신 값과 올바른 Label로 Query되는 상태**입니다.

---

# 9. Grafana — 화면 접속과 올바른 Datasource 사용은 다르다

> Grafana 화면이 열리면 Grafana Process와 Service, 현재 접근 경로 일부가 정상이라는 뜻입니다.
>
> **하지만 현재 Member Prometheus를 Query한다는 뜻은 아닙니다.**
>
> 먼저 Grafana가 사용하는 Datasource를 확인합니다. Datasource URL의 Service·Namespace·Port가 현재 Member의 Prometheus Service를 가리키는지 봅니다.
>
> 그다음 Datasource 연결 시험과 간단한 Query를 수행합니다.
>
> 그래서 `Save & Test` 같은 연결 성공만으로 끝내지 않고 실제 Metric Query 결과가 반환되는지 확인합니다.
>
> 그리고 Query 결과의 Cluster·Stage Label이 현재 Member인지 봅니다. 다른 Prometheus에 연결돼 있어도 Datasource 연결 자체는 성공할 수 있기 때문입니다.
>
> Dashboard도 같은 기준입니다. Dashboard 화면이 열리는지만 보지 않고 올바른 Datasource를 참조하고 최근 Metric을 표시하는지 확인합니다.
>
> 특정 Panel만 `No data`라면 Grafana 전체 장애라고 판단하지 않고 해당 Panel Query·Variable·Label 조건과 실제 Prometheus Series를 먼저 확인합니다.
>
> 반대로 Prometheus Query에서는 현재 Member Metric이 정상인데 Grafana에서만 값이 없다면 Target이나 ServiceMonitor부터 수정하지 않습니다. Datasource, Dashboard Query와 Variable 범위를 먼저 봅니다.
>
> 또한 Grafana Datasource와 다음 KubeSphere 블록의 External Monitoring Endpoint는 목적과 Service가 다를 수 있으므로 같은 URL로 가정하지 않습니다.
>
> 따라서 Grafana 확인은 화면 접속에서 끝나는 것이 아니라, 현재 Member Prometheus를 Datasource로 사용해 실제 최신 Metric을 Dashboard까지 표시하는지 확인하는 과정입니다.

---

# 10. Monitoring Ingress — 내부 화면을 외부 접근 경로로 연결한다

> Cluster 내부에서 Grafana Service가 정상이어도 외부 Domain·VIP-B·Ingress는 별도 경로입니다.
>
> 먼저 현재 Monitoring FQDN이 무엇인지 확인하고 DNS 조회 결과가 승인된 VIP-B를 가리키는지 봅니다.
>
> 그다음 VIP-B에서 Router 또는 Ingress 진입 경로가 9월 1일에 확인한 Network 설계와 같은지 연결합니다.
>
> Cluster 안에서는 Ingress Host·Path·Class와 Backend Service·Port가 현재 승인값인지 확인합니다.
>
> 그래서 외부 접근 경로는 DNS 이름만 맞는지 보는 것이 아니라 요청이 어느 VIP로 들어와 어느 Ingress Rule과 Service를 지나 Grafana Pod까지 전달되는지 순서대로 봐야 합니다.
>
> Ingress가 올바른 Service를 가리켜도 Service Endpoint가 없으면 실제 Backend Pod로 요청을 전달할 수 없습니다.
>
> **하지만 Ingress 객체가 존재한다는 사실만으로 외부 접근 성공을 판단하지 않습니다.**
>
> 먼저 내부 Service와 Endpoint가 정상인지 확인하고, 그다음 승인된 외부 위치에서 HTTP·HTTPS 요청을 확인합니다.
>
> HTTPS에서는 Network 연결 성공과 Certificate Trust를 구분합니다. 응답은 오지만 Certificate Trust 오류가 발생한다면 Ingress Routing 자체와 Client Trust 문제를 같은 장애로 처리하지 않습니다.
>
> 반대로 내부 Grafana Service가 정상인데 외부 Domain만 실패한다면 Grafana Pod나 Datasource부터 수정하지 않습니다. DNS·VIP-B·Router·Ingress Host·Backend 연결 순서로 확인합니다.
>
> 따라서 Monitoring Ingress의 완료 기준은 Ingress Resource가 생성된 상태가 아니라, **승인된 외부 경로에서 현재 Monitoring FQDN으로 접속했을 때 실제 Grafana Service까지 요청이 이어지는 상태**입니다.

---

# 11. 문제가 생기면 Monitoring 순서대로 확인한다

> Monitoring 문제도 첫 실패 단계보다 뒤쪽을 먼저 고치지 않습니다.
>
> 먼저 CRD가 없거나 Established되지 않았다면 Stack 뒤쪽을 확인하지 않습니다. Kubernetes API가 Monitoring Resource를 정상적으로 이해하지 못하는 상태에서는 Operator·Grafana 설정을 바꿔도 앞 단계가 해결되지 않습니다.
>
> 그다음 Prometheus Pod가 Pending이면 Scheduler Event를 기준으로 Node Selector·Taint·Resource·PVC 중 어디에서 막혔는지 확인합니다.
>
> PVC도 Pending이라면 Target보다 StorageClass·Provisioner·Mount 선행조건을 먼저 봅니다.
>
> `ImagePullBackOff`면 Monitoring 설정이나 ServiceMonitor를 수정하지 않고 Registry·Image Tag·CA·Pull Secret을 확인합니다.
>
> 그래서 Component가 아직 정상적으로 기동하지 못한 상태와 Metric Discovery 실패를 구분합니다.
>
> Pod는 Running인데 Target 자체가 없다면 ServiceMonitor Selector, Prometheus의 ServiceMonitor 선택 범위, Service Label·Port와 Endpoint Discovery를 순서대로 봅니다.
>
> 반대로 Target은 만들어졌는데 `Down`이면 Discovery를 다시 만들기보다 Target 오류를 기준으로 Endpoint Listener·Network·Scheme·Path·TLS·인증 조건을 확인합니다.
>
> Target은 `UP`인데 Query 결과가 없거나 현재 Member Label이 아니면 Network보다 Metric 이름·Query·Label과 실제 Endpoint가 현재 Member인지 확인합니다.
>
> Prometheus Query는 정상인데 Grafana Data가 없으면 ServiceMonitor나 Target부터 바꾸지 않고 Datasource·Dashboard Query·Variable·Label을 봅니다.
>
> 그리고 내부 Grafana UI는 정상인데 외부 Domain만 실패하면 DNS·VIP-B·Router·Ingress Host·Service Backend 경로를 확인합니다.
>
> 따라서 확인 순서는 `대상·선행조건 → CRD → Stack·Pod·PVC → Discovery → Target → Query → Grafana → Ingress`를 유지하고, 이미 통과한 앞 단계를 근거 없이 다시 변경하지 않습니다.

---

# 12. Member KubeSphere 진입 Gate를 판정한다

> 오전 Monitoring 검증은 화면 하나가 열리는 것으로 끝나지 않습니다. 다음 KubeSphere 구성에서 현재 Member의 Monitoring 결과를 신뢰하고 사용할 수 있어야 합니다.
>
> 먼저 `MONITORING PASS`는 현재 Member의 CRD와 Monitoring Stack이 정상이고 주요 Pod가 승인된 Infra Node에서 필요한 PVC를 실제로 Mount한 상태에서 시작합니다.
>
> 그다음 주요 Kubernetes Target과 External ETCD Target이 실제로 발견되고 `UP`이어야 합니다.
>
> **하지만 Target UP만으로 통과시키지 않습니다.** 실제 Query가 현재 Member의 최신 Metric과 올바른 Cluster·Stage Label을 반환해야 합니다.
>
> 그리고 Grafana Datasource가 현재 Member Prometheus를 가리키고 Dashboard에서 실제 Metric을 표시해야 합니다.
>
> Monitoring Ingress도 승인된 Domain·VIP-B 경로에서 실제 Grafana Service까지 연결돼야 합니다.
>
> 그래서 다음 블록에 넘길 External Monitoring Service·Namespace·Port도 현재 동작한 Monitoring 경로를 기준으로 확정합니다.
>
> 반대로 ETCD Target Down, 잘못된 Cluster·Stage Label, 잘못된 Datasource, PVC Mount 실패, CRD 충돌, 핵심 Pod 반복 Restart, Discovery 미완료나 다른 Domain·VIP 사용이 남으면 `BLOCKED`입니다.
>
> 따라서 `MONITORING PASS`는 Pod 수나 Target 화면 하나가 아니라 **수집 대상 발견·Scrape·Storage·Query·Grafana 표시·외부 접근이 모두 같은 신규 Member로 연결됐다는 판정**입니다.

---

# 13. 다음 블록에는 Monitoring 결과를 넘긴다

> 다음에는 Cluster·Stage·Context와 `MONITORING PASS / BLOCKED` 결과를 넘깁니다.
>
> CRD·Stack Version, 주요 Component·PVC·Infra 배치 결과를 전달합니다.
>
> 주요 Target과 External ETCD Endpoint·Health, 실제 Query·Cluster Label도 이어갑니다.
>
> Grafana Datasource·Dashboard와 Ingress 결과, KubeSphere가 사용할 External Monitoring Service·Namespace·Port를 넘깁니다.
>
> Secret·Certificate·Token 원문은 제외합니다.

---

# 14. 마무리

> Kubernetes와 Storage가 정상이어도 지속적인 Monitoring은 별도였습니다.
>
> 그래서 현재 Member 입력과 CRD를 확인하고 Monitoring Stack을 설치했습니다.
>
> 그다음 실제 Pod·PVC·Infra 배치와 ServiceMonitor·Service·Endpoint를 확인했습니다.
>
> External ETCD Target과 실제 Query를 검증하고, Grafana와 Ingress에서 현재 Member 데이터가 보이는지 확인했습니다.
>
> **결국 MONITORING PASS는 Prometheus와 Grafana가 떠 있는 상태가 아니라, 현재 신규 Member의 Metric이 올바른 Target에서 수집되고 Query·화면·외부 경로까지 이어지는 상태입니다.**
