# Member KubeSphere 설치·기능·Pre-Join Gate 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 앞 블록에서 현재 신규 Member의 Monitoring을 `MONITORING PASS`까지 확인했다. 이번 블록은 **Kubernetes·Storage·Monitoring 위에 독립적으로 운영 가능한 KubeSphere Member를 구성하고 확인하는 과정**이다.
>
> Manifest·ClusterConfiguration·Module 설정과 검증 명령은 승인된 Member KubeSphere Runbook을 따른다. 기존 Host Manifest에서 `clusterRole`만 바꿔 사용하지 않고 Join Secret·JWT·kubeconfig·Token·Password·Private Key 원문을 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
Kubernetes·Storage·Monitoring이 준비됐다
→ 하지만 KubeSphere Member Platform은 별도다
→ Installer는 설치를 수행할 실행기다
→ ClusterConfiguration은 설치할 기능과 환경값을 정한다
→ 현재 Member의 Role·Storage·Registry·Monitoring·배치를 연결한다
→ Installer Pod와 내부 Task를 확인한다
→ 실제 Workload·PVC·배치를 확인한다
→ KubeSphere가 External Monitoring을 실제로 사용하는지 본다
→ Console·API와 member Role을 확인한다
→ Member 자체가 정상이어야 Host Join으로 넘어간다
```

## 0-1. 오늘 전체 한 줄

> 이번 블록은 Console을 여는 시간이 아닙니다. **현재 신규 Member의 기반 위에서 KubeSphere가 실제로 동작하고 `member` 역할로 준비됐는지 확인하는 시간**입니다.

---

# 1. 시작 — Monitoring이 정상이어도 KubeSphere Member는 별도다

> 신규 Member에는 Kubernetes가 있고 Persistent Storage와 Monitoring도 동작합니다.
>
> **하지만 기존 Host에 연결할 KubeSphere Member Platform이 자동으로 생긴 것은 아닙니다.**
>
> 이 Cluster가 `member` 역할이어야 하고, Platform Image·Storage·External Monitoring·배치 기준도 현재 Member 값으로 연결돼야 합니다.
>
> Host Join은 비정상 Member를 정상으로 만드는 복구 절차가 아닙니다.
>
> 따라서 Member 자체 기능을 먼저 확인해야 Join 뒤 문제를 Member 내부와 Host 연결 문제로 구분할 수 있습니다.

---

# 2. Installer와 ClusterConfiguration은 역할이 다르다

> KubeSphere 설치에는 Installer Manifest와 ClusterConfiguration이 사용됩니다.
>
> Installer는 CRD·권한·Deployment 등 **설치 작업을 수행할 실행기**를 준비합니다.
>
> ClusterConfiguration은 Module·Storage·Registry·Monitoring·Multi-Cluster Role 등 **무엇을 어떤 값으로 설치할지** 정합니다.
>
> Installer Pod가 떠도 ClusterConfiguration이 틀리면 잘못된 Platform을 만들 수 있습니다.
>
> 반대로 구성값이 맞아도 Installer가 실행되지 않으면 설치 Task는 진행되지 않습니다.
>
> 그래서 두 파일은 서로 대신할 수 없습니다.

---

# 3. Installer Apply — 객체 생성과 실제 실행은 다르다

> 승인된 Installer Manifest를 현재 Member Context에 적용합니다.
>
> `created`나 `configured` 출력은 객체 생성 요청이 받아들여졌다는 뜻입니다.
>
> **하지만 Installer가 실제로 실행됐다는 뜻은 아닙니다.**
>
> Deployment와 Pod가 생성됐는지, 어느 Node에 배치됐는지, 현재 Registry에서 Image를 Pull하는지 확인합니다.
>
> ServiceAccount·권한·CRD 오류와 반복 Restart도 봅니다.
>
> Pod가 Pending이면 내부 Task를 보지 않고 Selector·Taint·Resource·Image Pull과 Scheduler Event를 확인합니다.
>
> Installer Pod가 Running이면 실행기가 시작된 것입니다. 이제 ClusterConfiguration으로 설치 내용을 정합니다.

---

# 4. ClusterConfiguration — 현재 Member의 설치값을 정한다

> 먼저 현재 Context와 Cluster Name·Stage를 확인합니다. 9월 1일 Kubernetes 기능 결과, 9월 2일 StorageClass·Mount·Write/Read 결과와 앞 블록의 `MONITORING PASS`를 이어받습니다.
>
> 현재 Registry·Image Tag, Prometheus Service·Endpoint, External ETCD, Console Domain·VIP-B와 Infra Node Label·Taint도 현재 신규 Member 값인지 확인합니다.
>
> 그다음 Multi-Cluster Role을 확인합니다. 신규 Cluster는 `member`, 기존 중앙 Cluster는 `host`입니다.
>
> 이 값은 화면에 표시할 이름이 아니라 Join 방향과 Multi-Cluster Component 동작을 결정합니다.
>
> Storage는 검증된 StorageClass를 사용합니다.
>
> Registry는 현재 Bundle과 Image Tag를 사용하고, External Monitoring은 앞 블록에서 확인한 Prometheus Endpoint를 사용합니다.
>
> 필요한 ETCD 참조와 Console·Ingress Domain도 현재 Member 값으로 연결합니다.
>
> Node Selector와 Toleration은 Platform Workload가 승인 Infra Node에 배치되도록 설정합니다.
>
> Module은 예시에 켜져 있다는 이유로 자동 활성화하지 않습니다. 추가 Image·CRD·Storage·Network·Resource가 필요할 수 있으므로 승인 범위를 따릅니다.
>
> **따라서 기존 Host Manifest에서 `clusterRole: member`만 바꿔 사용하면 안 됩니다.** Host와 Member의 역할과 연결값이 다를 수 있습니다.

---

# 5. Installer Log — Pod Running보다 내부 Task를 확인한다

> ClusterConfiguration을 적용하면 Installer가 여러 Task를 실행합니다.
>
> 마지막 오류만 원인으로 보지 않습니다. 앞의 Storage·Monitoring·Registry·CRD 실패가 뒤 Task를 연쇄적으로 실패시킬 수 있습니다.
>
> 그래서 Installer Pod 자체 문제인지, 내부 어느 Task가 처음 실패했는지 구분합니다.
>
> 직전 성공 Task와 오류 원문, 해당 Task가 사용하는 현재 Member 값을 함께 봅니다.
>
> `CRD not found`라면 StorageClass나 Registry부터 바꾸지 않습니다.
>
> Monitoring Task가 실패하면 앞 블록의 Prometheus Endpoint·Service·PVC가 유지되는지 확인합니다.
>
> 조치 뒤에는 관련 기능을 먼저 확인하고 승인된 방식으로 Installer를 이어갑니다.
>
> 모든 핵심 Task가 끝나도 실제 Platform 기능은 별도로 확인해야 합니다.

---

# 6. 실제 Workload·배치·PVC를 확인한다

> Installer Task가 성공하면 KubeSphere Deployment·StatefulSet·Service·Pod가 생성됩니다.
>
> 객체가 존재한다고 Pod가 Ready이고 필요한 Endpoint를 제공하는 것은 아닙니다.
>
> 현재 활성 Module에 필요한 주요 Workload의 Ready·Restart·Event·Log와 Service·Endpoint를 확인합니다.
>
> 그다음 실제 Pod가 승인 Infra Node에 배치됐는지 봅니다.
>
> Manifest에 Selector가 있어도 실제 배치는 Label·Taint·Toleration·Resource 조건에 따라 달라질 수 있습니다.
>
> KubeSphere PVC가 실제 StorageClass를 사용해 Bound됐는지, Platform Pod에 Mount됐는지도 확인합니다.
>
> **9월 2일 Test PVC 성공은 KubeSphere PVC 성공을 대신하지 않습니다.** Namespace·용량·배치 Node가 다를 수 있습니다.

---

# 7. External Monitoring — URL 설정과 실제 사용은 다르다

> ClusterConfiguration에 Prometheus Endpoint가 있어도 KubeSphere가 Metric을 실제로 사용하는 것은 아닙니다.
>
> Endpoint가 앞 블록에서 확인한 Service·Namespace·Port와 같은지 확인합니다.
>
> Grafana Datasource URL을 기억해서 그대로 사용하지 않습니다. 같은 Prometheus 기반을 사용해도 소비 목적과 Service가 다를 수 있습니다.
>
> KubeSphere Monitoring 화면이나 API에서 현재 Member의 Node·Workload Metric이 최근 시각으로 보이는지 확인합니다.
>
> Cluster Identity와 반복 Timeout도 봅니다.
>
> 화면이 비면 Prometheus 전체를 재설치하기 전에 앞 블록 Query가 여전히 성공하는지 확인하고, 그다음 KubeSphere Endpoint·Service·Network 설정을 봅니다.

---

# 8. Console·API와 실제 member Role을 확인한다

> Console이 승인 Domain과 VIP-B 경로에서 열리면 Frontend와 외부 접근 일부가 정상이라는 뜻입니다.
>
> **하지만 Backend API·Storage·Monitoring·Role까지 모두 정상이라는 뜻은 아닙니다.**
>
> 승인 Account로 접근하고 KubeSphere API가 응답하는지 확인합니다.
>
> 현재 Cluster의 Node·Namespace·Workload를 조회할 수 있는지도 봅니다.
>
> Storage와 Monitoring 화면이 앞에서 확인한 기반과 연결되는지 확인합니다.
>
> 마지막으로 실제 설치 결과에서 `clusterRole=member`인지 봅니다. 구성 파일에 적혀 있다는 사실만으로 대신하지 않습니다.
>
> Console은 열리는데 Role이 틀리거나 API 오류가 반복되면 Host Join으로 넘어가지 않습니다.

---

# 9. 문제가 생기면 설치 순서대로 확인한다

> Installer Pod가 Pending이면 내부 Task보다 Scheduling·Image·권한을 봅니다.
>
> `ImagePullBackOff`면 Monitoring Endpoint보다 Registry·Tag·CA·Pull Secret을 확인합니다.
>
> Installer는 Running인데 CRD 오류가 나면 필요한 Kind와 Established 상태를 봅니다.
>
> Platform Pod가 Pending이면 전체 재설치보다 Selector·Taint·PVC·Resource를 확인합니다.
>
> Console은 열리는데 Metric이 없으면 Console 경로는 통과했습니다. KubeSphere Monitoring Endpoint와 Prometheus Query를 봅니다.
>
> PVC가 FailedMount이면 Installer를 반복하지 않고 현재 Pod Node와 Storage 데이터 경로를 확인합니다.
>
> 확인 순서는 `현재값 → Installer → ClusterConfiguration → 내부 Task → Workload·배치·PVC → Monitoring → Console·API → member Role`입니다.

---

# 10. Host Join 전 MEMBER SELF PASS를 판정한다

> `MEMBER SELF PASS`는 Kubernetes·Storage·Monitoring Gate가 유지되는 것에서 시작합니다.
>
> Installer 핵심 Task가 완료되고 주요 Platform Workload가 Ready여야 합니다.
>
> 실제 Infra 배치, KubeSphere PVC Mount와 External Monitoring 사용이 정상이어야 합니다.
>
> Console·API와 `clusterRole=member`도 현재 Member 값으로 확인돼야 합니다.
>
> Installer 실패, 주요 Pod 반복 Restart, PVC Pending·FailedMount, Monitoring 미연결, API 비정상, Role 오류나 다른 Cluster 값이 남으면 `BLOCKED`입니다.
>
> MEMBER SELF PASS는 Host가 없어도 신규 Member 자체가 운영 가능한 상태를 뜻합니다.

---

# 11. Host Join에는 Member 자체 결과를 넘긴다

> 오후에는 Cluster Name·Stage·Context와 `MEMBER SELF PASS / BLOCKED` 결과를 넘깁니다.
>
> Kubernetes·Storage·Monitoring 결과와 Installer Task를 전달합니다.
>
> 주요 Workload·Infra 배치·PVC Mount, Console·API와 실제 `member` Role도 이어갑니다.
>
> Join에 필요한 보호정보는 원문으로 넘기지 않습니다. 값의 종류, 승인된 전달 방식, 유효시간과 사용 후 정리 기준만 전달합니다.
>
> 다음 블록은 기존 Host를 재설치하는 작업이 아니라 정상인 Member와 정상인 Host를 연결하는 작업입니다.

---

# 12. 마무리

> Kubernetes·Storage·Monitoring이 준비돼도 KubeSphere Member Platform은 별도였습니다.
>
> 그래서 Installer와 ClusterConfiguration의 역할을 구분하고 현재 Member의 Role·Storage·Registry·Monitoring·배치값을 연결했습니다.
>
> 그다음 Installer 내부 Task와 실제 Workload·PVC·Infra 배치를 확인했습니다.
>
> 마지막으로 Console·API, External Monitoring과 실제 `clusterRole=member`를 확인했습니다.
>
> **결국 MEMBER SELF PASS는 Installer Pod와 Console이 보이는 상태가 아니라, Host 없이도 현재 신규 Member의 KubeSphere Platform이 정상인 상태입니다.**

---

4. Installer Apply·Pod Running·내부 Task 성공은 각각 무엇이 다른가?
5. Installer Log에서 최초 실패를 먼저 보는 이유는 무엇인가?
6. Task 성공 뒤에도 실제 Workload를 확인해야 하는 이유는 무엇인가?
7. Manifest의 배치 조건과 실제 Infra Node 배치는 왜 다른가?
8. 이전 Storage PASS가 KubeSphere PVC 성공을 대신하지 못하는 이유는 무엇인가?

10. Console 접속이 API·Storage·Monitoring·Role까지 증명하지 못하는 이유는 무엇인가?
