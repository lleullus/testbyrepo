# Member Monitoring 전체 경로·Target·Grafana 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 9월 2일 `STORAGE PASS`를 입력으로 받아 **현재 신규 Member의 Metric이 실제로 수집·저장·조회·표시되고, External ETCD와 Monitoring Ingress까지 기능으로 연결되는지 증명하는 법**을 가르친다. Prometheus Operator CRD, custom Stack Manifest, Secret 생성·적용의 정확한 절차는 Member Monitoring Runbook에서 수행한다. 이 대본은 리소스가 많이 Running인지를 세는 문서가 아니라 **각 Endpoint·Label·Storage·Target이 같은 신규 Member를 가리키는지 판정하는 문서**다.

## 0. 9월 2일에서 이어받는 것

```text
Cluster Name·Stage·Context
STORAGE PASS / BLOCKED
StorageClass 이름·정책
Backend·Trident 정상 증거
Monitoring Namespace 기준
Prometheus·Alertmanager·Grafana PVC 용량 기준
Monitoring 배치 Node Role
9/3 대상 Node의 Storage Mount 경로 증거
Registry·Image 공급 기준
External ETCD Endpoint 기준
VIP-B·Domain
```

> `STORAGE PASS`가 아니면 Monitoring Stack을 적용하지 않습니다. Storage 실패를 Monitoring 설치 실패로 보이게 만들지 않습니다.

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> Prometheus Operator CRD, Monitoring Pod, PVC, Service, External ETCD ServiceMonitor와 Grafana가 **각각 무엇을 증명하고 무엇은 증명하지 못하는지** 구분하고, `Pod Running`이 아니라 **Target UP·Query·현재 Member Label·Ingress 실제 기능**으로 Monitoring 완료를 판정할 수 있어야 한다.

오늘의 중심 질문:

> **현재 신규 Member의 Metric이 실제로 수집·저장·조회·표시되고 있으며, 그 Metric이 다른 Cluster가 아니라 바로 이 Member 것이라는 것을 무엇으로 증명할 것인가?**

---

# 1. 시작 — Monitoring은 Pod를 띄우는 일이 아니라 관측 경로를 만드는 일이다

전체 흐름을 먼저 본다.

```text
현재 Member Kubernetes·Storage
→ monitoring Namespace
→ ETCD 인증정보의 안전한 참조
→ Monitoring PVC
→ Prometheus Operator CRD
→ Prometheus Operator
→ Prometheus·Alertmanager·Grafana 등 Stack
→ Service·Endpoint
→ ServiceMonitor·Target
→ Prometheus Query
→ Grafana Datasource·Dashboard
→ Monitoring Ingress·VIP-B
```

> 여기서 핵심은 한 단계의 존재를 뒤 단계의 성공으로 확대하지 않는 것입니다.

반드시 구분한다.

```text
CRD Apply 성공
≠ Established

Prometheus Pod Running
≠ Target UP

PVC Bound
≠ Monitoring Pod Mount·데이터 기록

Grafana UI 열림
≠ Datasource·Query 정상

Ingress 존재
≠ VIP-B 사용자 경로 정상
```

---

# 2. 현재 Member Identity를 Monitoring 값 전체의 기준으로 고정한다

먼저 한 장에 적는다.

```text
current-context: _________________________________________
Cluster Name: ____________________________________________
Stage: ___________________________________________________
Monitoring Namespace: ___________________________________
StorageClass: ____________________________________________
Registry·Project·Tag 기준: _______________________________
External ETCD Endpoint: _________________________________
External Label cluster: _________________________________
External Label stage: ___________________________________
VIP-B·Monitoring FQDN: __________________________________
Infra Node Role·Label: ___________________________________
```

> Secret Data, ETCD Client Key, Password, Token은 기록하지 않습니다.

## 2.1 Monitoring 복붙 오적용을 막는 가장 강한 규율

```text
Manifest가 Apply 됨
≠ 현재 Member 값으로 Apply 됨
```

반드시 현재 Member와 대조할 값:

```text
externalLabels.cluster
externalLabels.stage
ETCD Endpoints
StorageClass
Ingress Host
Grafana Datasource
Registry·Image Tag
Node Selector·Toleration
KubeSphere가 나중에 참조할 Prometheus Endpoint
```

> 과거 Host·PRD·DEV Member의 값이 하나라도 실행값으로 남아 있다면 적용 전에 멈춥니다.

---

# 3. Preliminary — Namespace·Secret·PVC는 Stack보다 먼저 닫는다

## 3.1 monitoring Namespace

```text
Namespace Active
≠ 이후 Resource가 모두 올바른 Namespace에 있음
```

> 이후 Secret, PVC, ServiceMonitor, Grafana 설정이 현재 `monitoring` Namespace를 사용해야 합니다.

## 3.2 ETCD Certificate Secret

> External ETCD Metric을 HTTPS로 Scrape하려면 Prometheus가 승인된 인증 재료를 참조할 수 있어야 합니다.

확인할 것은 내용이 아니라 구조다.

```text
Secret 존재
Namespace = monitoring
Type 확인
필요 Key 이름 존재
현재 Member ETCD Certificate와 대응하는 승인 근거
Pod가 참조할 수 있는 경로
```

반드시 구분한다.

```text
Secret 이름 동일
≠ 현재 Member Certificate
```

> Secret Data를 Base64 Decode해 교육 화면에 출력하지 않습니다.

## 3.3 Monitoring PVC 선행조건

Prometheus·Alertmanager·Grafana가 사용하는 PVC는 9월 2일 Storage 결과를 이어받는다.

확인:

```text
StorageClass
요청 용량
Namespace Quota
AccessMode
실제 PVC Bound
Pod가 배치될 Infra Node의 Mount 경로
```

구분:

```text
Grafana PVC 성공
≠ Prometheus·Alertmanager PVC 자동 성공
```

> 각각의 요청 용량·Pod 배치·Mount 결과를 확인합니다.

---

# 4. Prometheus Operator CRD — Apply보다 Established가 중요하다

> Prometheus, ServiceMonitor, PrometheusRule 같은 객체는 Kubernetes 기본 Kind가 아닙니다. 먼저 API가 그 종류를 이해해야 합니다.

흐름:

```text
CRD Apply
→ Names Accepted
→ Established=True
→ API Discovery 가능
→ Custom Resource 적용 가능
```

확인할 질문:

```text
현재 Bundle이 요구하는 CRD인가
Established=True인가
Served·Storage Version이 현재 Manifest와 맞는가
과거 Version 충돌이 없는가
```

반드시 구분한다.

```text
kubectl apply 성공
≠ CRD Established
```

> CRD가 불완전한데 Operator·Stack을 먼저 올려 반복 오류를 쌓지 않습니다.

---

# 5. Monitoring Stack — Running 개수가 아니라 실제 기능 경로를 본다

현재 Bundle의 정확한 Component 목록은 Runbook을 따른다.

대표 역할:

```text
Prometheus Operator
→ Prometheus 계열 Custom Resource를 실제 Workload로 조정

Prometheus
→ Metric Scrape·저장·Query

Alertmanager
→ Alert 수신·Grouping·Routing

Grafana
→ Prometheus 등을 Datasource로 Query해 Dashboard 표시

kube-state-metrics·Node Exporter 등
→ Kubernetes·Node Metric 제공
```

## 5.1 Cluster Identity Label

Monitoring의 가장 중요한 실제값 중 하나:

```text
externalLabels.cluster = 현재 Member Cluster
externalLabels.stage = 현재 Stage
```

구분:

```text
Prometheus 정상 실행
≠ Metric Label이 현재 Member
```

> 다른 Cluster Label을 복사하면 Pod는 정상이어도 Multi-Cluster Query와 Dashboard가 잘못된 Cluster로 보입니다.

---

# 6. Storage와 Node 배치는 실제 Pod에서 확인한다

## 6.1 PVC Bound 뒤 실제 Mount

```text
Monitoring PVC Bound
≠ Prometheus·Grafana가 실제 Volume 사용
```

확인:

```text
Pod가 실제 어느 Infra Node에 배치됐는가
PVC와 PV는 무엇인가
Event에 FailedMount가 없는가
Container의 Storage 경로가 실제 Volume인가
Restart 후에도 Storage 관련 오류가 없는가
```

> 9월 2일 Test 성공을 Monitoring PVC 자동 성공으로 확대하지 않습니다.

## 6.2 Node Selector·Taint·Toleration

```text
Manifest에 nodeSelector 존재
≠ 실제 Pod가 Infra Node 배치
```

실제 Pod의 `NODE`를 확인하고, Taint·Toleration과 Replica 배치가 승인 정책에 맞는지 본다.

> Platform Workload가 Worker로 잘못 배치돼도 Running일 수 있습니다. 배치 정책은 별도 증거입니다.

---

# 7. Registry와 Image — Pull 실패를 Monitoring 설정 문제로 만들지 않는다

확인 경로:

```text
Manifest Image 주소
→ Registry FQDN·Project·Repository·Tag
→ Node CA Trust·Network
→ 필요한 Secret
→ Pod Event의 실제 Pull 결과
```

구분:

```text
ImagePullBackOff
≠ Monitoring Logic 실패
```

> Image Pull 단계에서 실패하면 Prometheus Rule이나 Datasource부터 바꾸지 않습니다.

---

# 8. Service·Endpoint — Pod Running 뒤 실제 연결점을 만든다

각 주요 Component에서 최소 다음을 확인한다.

```text
Service 존재
Port·Selector
Endpoint 또는 EndpointSlice
Ready Pod IP와 일치
```

구분:

```text
Service 존재
≠ Endpoint 존재

Endpoint 존재
≠ Prometheus Scrape·Grafana Query 정상
```

> 뒤의 ServiceMonitor와 Datasource는 이 Service·Endpoint 위에 올라갑니다.

---

# 9. External ETCD Monitoring — 최종 증거는 Target UP이다

External ETCD는 Kubernetes Pod Selector로 자동 발견되지 않을 수 있다.

정상 경로:

```text
현재 Member ETCD IP:Port
→ Kubernetes Endpoint 표현
→ Service
→ ServiceMonitor
→ Prometheus
→ HTTPS /metrics
→ Target UP
```

각 단계에서 볼 것:

### Endpoint

```text
현재 Member ETCD IP인가
승인 Port인가
다른 Cluster IP 혼입 없음
```

### Service

```text
Endpoint와 연결되는가
Port Name이 ServiceMonitor와 일치하는가
Namespace가 맞는가
```

### ServiceMonitor

```text
Selector가 정확한 Service를 선택하는가
Port Name·Scheme·Path가 실제 ETCD와 맞는가
TLS Config가 현재 Secret을 참조하는가
```

### Target

최종적으로:

```text
Health = UP
Last Scrape 정상
Error 없음
현재 Member Endpoint
실제 Metric Query 가능
```

## 9.1 존재와 기능의 차이

```text
Service·Endpoint 존재
≠ Target UP

Target UP
≠ 다른 Cluster ETCD가 아닌 현재 Member라는 뜻까지 자동 증명
```

> Endpoint IP와 Cluster Label을 같이 대조합니다.

## 9.2 Target Down 첫 분기

| 증상 | 첫 확인 |
|---|---|
| No Endpoint | Endpoint·Service Selector |
| Connection refused | ETCD Metric Listen·Port |
| Timeout | Network·Route·Firewall |
| x509 | CA·Client Certificate·Server Name |
| 401/403 | ETCD Auth·Certificate |
| Metric은 오지만 다른 Cluster | Endpoint IP·External Label |

> Target Down인데 Prometheus 전체를 재설치하지 않습니다.

---

# 10. Prometheus 자체 기능 — Pod Running 뒤 Query까지 본다

확인 범위:

```text
Prometheus Pod Ready
→ Service·Endpoint
→ Prometheus Web/API
→ Target 목록
→ Rule Load
→ 간단 Query 결과
```

구분:

```text
Prometheus Pod Running
≠ Target UP

Rule Object 존재
≠ Prometheus가 Rule Load
```

간단 Query는 현재 Member에서 실제로 존재하는 Metric을 사용한다. 결과에 현재 Cluster Label이 있는지 함께 본다.

> 복잡한 Dashboard보다 낮은 단계의 Prometheus Query가 먼저입니다.

---

# 11. Grafana — UI 접속보다 Datasource·Query가 중요하다

Grafana 흐름:

```text
Grafana Pod
→ Service
→ Datasource
→ Prometheus Endpoint
→ Query
→ Dashboard Panel
```

반드시 구분한다.

```text
Grafana UI 열림
≠ Datasource 정상

Datasource Save & Test 성공
≠ 모든 Dashboard Variable·Panel 정상

Panel에 숫자 있음
≠ 현재 Member Metric
```

확인할 것:

```text
Datasource URL이 현재 Monitoring Service인가
Save & Test 성공
간단 Query 성공
Cluster Label이 현재 Member
Dashboard 최근 데이터 존재
Panel Error 없음
다른 Cluster Metric 혼입 없음
```

> Grafana Datasource와 이후 KubeSphere external Monitoring Endpoint는 목적이 다를 수 있으므로 이름이 비슷하다고 같은 Endpoint로 추측하지 않습니다.

---

# 12. Monitoring Ingress — UI가 실제 VIP-B 경로에서 열리는가

전체 경로:

```text
운영자
→ Monitoring FQDN
→ DNS
→ Member VIP-B
→ Router Ingress Controller
→ Monitoring Ingress
→ Service
→ Endpoint
→ Prometheus·Grafana·Alertmanager
```

확인:

```text
FQDN이 현재 Member Domain인가
DNS가 현재 VIP-B를 반환하는가
Ingress Host·Path·Class가 맞는가
Service·Port가 실제 Component와 맞는가
Backend Endpoint가 존재하는가
실제 HTTP·HTTPS 응답이 기대 상태인가
```

구분:

```text
Ingress 객체 존재
≠ 외부 기능 정상
```

> 다른 Member Domain이나 VIP-B가 들어간 Manifest는 Apply 성공해도 현재 Member 성공이 아닙니다.

---

# 13. Monitoring 전체에서 첫 단절을 찾는다

| 증상 | 먼저 볼 경계 |
|---|---|
| CRD 관련 오류 | CRD 존재·Established·Version |
| Pod Pending | PVC·Node Selector·Taint·Resource |
| ImagePullBackOff | Registry·Tag·CA·Secret |
| PVC Bound + Pod FailedMount | 9/2 Storage 경로·실제 Node |
| Prometheus Running + Target Down | ServiceMonitor·Service·Endpoint·TLS·Network |
| Grafana UI + Query 실패 | Datasource·Prometheus Service·Query |
| Ingress 존재 + UI 실패 | DNS·VIP-B·Ingress·Service·Endpoint |
| Metric은 보이지만 Cluster가 틀림 | External Label·Endpoint·Datasource |

> 리소스 수를 세지 않고 마지막 성공과 첫 실패 사이를 봅니다.

---

# 14. MONITORING PASS를 판정한다

## 14.1 MONITORING PASS

```text
STORAGE PASS
+ 현재 Member Identity 값 검토 완료
+ monitoring Namespace 정상
+ ETCD Secret 구조·참조 정상, 원문 미노출
+ Monitoring PVC 실제 Mount·사용 정상
+ 필요한 Prometheus Operator CRD Established
+ Operator·Prometheus·Alertmanager·Grafana 등 핵심 Component 정상
+ 실제 Infra 배치 정책 정상
+ Service·Endpoint 정상
+ 주요 Kubernetes·Node Target 정상
+ External ETCD Target UP·현재 Member 확인
+ Rule Load 정상
+ Prometheus 간단 Query 정상
+ Grafana Datasource·Query·현재 Member Dashboard 정상
+ Monitoring Ingress·VIP-B 실제 기능 정상
+ Cluster·Stage Label 정확
+ Critical Event·반복 Restart 없음
```

> 이 상태가 돼야 Member KubeSphere 설치로 넘어갑니다.

## 14.2 BLOCKED

```text
STORAGE가 BLOCKED
Monitoring PVC Mount 실패
CRD Established 실패·Version 충돌
핵심 Monitoring Pod 반복 실패
External ETCD Target Down 원인 미확정
Grafana가 다른 Cluster Prometheus 참조
External Label 잘못 적용
Registry Image Pull 실패
Ingress가 다른 Domain·VIP 사용
현재 Member Metric임을 증명할 수 없음
```

> KubeSphere를 먼저 올려 문제를 덮지 않습니다.

# 16. 마무리 — Monitoring 완료를 한 문장으로 다시 말한다

> Monitoring은 Prometheus와 Grafana Pod를 띄우는 작업이 아닙니다.
>
> 현재 Member의 Storage와 배치 조건 위에서 Prometheus가 실제 Target을 Scrape하고, External ETCD를 현재 Member Endpoint로 관측하며, Query 결과에 올바른 Cluster Identity가 붙고, Grafana가 그 Datasource를 실제로 조회하며, 외부 운영자가 현재 Member VIP-B를 통해 접근할 수 있어야 합니다.
>
> **결국 Monitoring 완료는 Running Pod 개수가 아니라, 현재 신규 Member의 Metric이 끝까지 올바른 Identity로 수집·저장·조회·표시되는 것을 증명한 상태입니다.**
