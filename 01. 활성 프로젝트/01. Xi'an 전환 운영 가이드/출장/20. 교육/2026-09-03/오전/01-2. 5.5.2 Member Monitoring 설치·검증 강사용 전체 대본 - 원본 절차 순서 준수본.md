# 5.5.2 Member Monitoring 설치·검증 강사용 전체 대본 - 원본 절차 순서 준수본

## 0-1. 오늘 전체 한 줄

> 오전에는 Prometheus와 Grafana Pod를 단순히 띄우는 것이 아닙니다. **현재 신규 Member의 Metric이 올바른 Target에서 수집되고, External ETCD까지 `UP`이며, Grafana와 외부 Ingress에서 현재 Member 데이터가 실제로 보이는 상태를 완성하는 시간입니다.**

# 1. 시작 — 9월 2일에는 Storage를 증명했고, 오늘은 지속적인 관측 경로를 만든다

> 어제는 StorageClass가 존재하는지만 본 것이 아니라 실제 PVC·PV·Pod Mount·Write/Read·Cleanup까지 확인했습니다.
>
> 오늘 Monitoring은 그 Storage를 실제로 사용합니다. Grafana·Prometheus·Alertmanager가 PVC를 만들기 때문에 어제의 Storage Gate가 깨진 상태에서 Monitoring을 시작하면 Storage 문제를 Monitoring 문제로 오해할 수 있습니다.
>
> 그래서 오늘은 원본 `5-2-0`부터 시작합니다. Context와 Node, StorageClass, Registry, Domain, External ETCD를 현재 신규 Member 값으로 고정한 뒤에만 Manifest를 적용합니다.
>
> 그리고 Monitoring이 끝났다고 판단하는 기준도 Pod 수가 아닙니다. 현재 Member Target이 실제로 발견되고 Scrape되며, Query와 Grafana Dashboard, 외부 Ingress까지 같은 Member를 가리켜야 합니다.

## 1.1. 오늘 만드는 Monitoring 전체 경로를 먼저 본다

> 오늘 설치하는 Component 이름부터 외우지 않습니다. 먼저 **Metric이 어디에서 나오고, 누가 수집 대상을 정의하고, 누가 실제로 수집·저장하며, 사람이 어디에서 확인하는지** 전체 경로를 잡습니다.

```text
[Metric을 만드는 쪽]

Kubernetes Node
 └─ node-exporter
      └─ CPU / Memory / Disk / Network Metric

Kubernetes API의 Object 상태
 └─ kube-state-metrics
      └─ Node / Pod / Deployment 등 상태 Metric

External ETCD
 └─ ETCD Metrics Endpoint

                 ↓

[무엇을 수집할지 선언]

ServiceMonitor / PodMonitor 등

                 ↓

[실제 수집·저장]

Prometheus
 ├─ Target Discovery
 ├─ Scrape
 ├─ Metric 저장
 └─ PromQL Query
      │
      ├────────→ Alertmanager
      │           Alert 처리
      │
      └────────→ Grafana
                  Dashboard 표시
                       │
                       ↓
                    Ingress
                       │
                       ↓
                   외부 사용자
```

> 여기서 **Prometheus Operator와 Prometheus는 같은 Component가 아닙니다.**
>
> Prometheus는 실제 Metric을 발견하고 Scrape하고 저장·질의합니다. 반면 Prometheus Operator는 `Prometheus`, `Alertmanager`, `ServiceMonitor`, `PrometheusRule` 같은 Custom Resource를 보고 실제 Monitoring 구성이 원하는 상태가 되도록 관리하는 Controller입니다.

```text
Prometheus / Alertmanager / ServiceMonitor Custom Resource
                       ↓
               Prometheus Operator
                       ↓
          실제 Prometheus·Alertmanager 구성 관리
```

> 이 관계를 먼저 이해한 뒤 원본 순서대로 갑니다. 원본 순서를 교육 편의상 재배치하지 않습니다.

# B. Monitoring 본체가 올라갈 Kubernetes 기반을 준비한다

> 이제부터 실제 Monitoring 구축으로 들어갑니다. 하지만 아직 Prometheus나 Grafana 본체부터 올리지 않습니다.
>
> 원본은 먼저 `Namespace → ETCD Secret → Grafana PVC → Prometheus Operator CRD`를 준비합니다. 이 네 가지는 뒤 Monitoring Stack이 시작되기 전에 있어야 하는 **작업 경계·인증자료·Persistent Storage·API Schema**입니다.
>
> 따라서 이 구간의 질문은 **"Monitoring이 동작하는가?"가 아니라 "Monitoring 본체를 올릴 기반이 준비됐는가?"**입니다.

# 3. 원본 5-2-1-1 — Preliminary Components 배포

> 원본은 `monitoring Namespace → ETCD Secret → Grafana PVC` 순서입니다. 이 순서를 바꾸지 않습니다.
>
> 세 Resource는 서로 역할이 다릅니다.
>
> - `monitoring` Namespace는 이후 Monitoring Resource를 모을 Kubernetes 작업 경계입니다.
> - `etcd-certs` Secret은 지금 바로 쓰기 위한 것이 아니라 뒤 `5-2-1-4`에서 Prometheus가 External ETCD를 HTTPS로 Scrape할 때 사용할 인증자료입니다.
> - `grafana-pvc`는 뒤 Stack이 Grafana를 시작할 때 필요한 Persistent Storage를 먼저 확보하는 것입니다.
>
> 즉 이 단계는 **Monitoring 본체를 설치하는 단계가 아니라, 본체가 시작되자마자 참조할 선행 Resource를 원본 순서대로 준비하는 단계**입니다.

먼저 Preliminary Directory로 이동합니다.

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/1.preliminary
ls -al
grep -nE '^(metadata:|  name:|  namespace:)' 1.namespace.yaml
grep -nE 'namespace|etcd|pem|crt|kubectl' 2.secret.sh
grep -nE 'name:|namespace:|storage:|storageClassName:|accessModes:' 3.grafana-pvc.yaml
```

필수 파일은 다음 세 개입니다.

```text
1.namespace.yaml
2.secret.sh
3.grafana-pvc.yaml
```

## 3.1 `monitoring` Namespace를 준비한다

Manifest의 Namespace가 현재 기준과 같은지 확인합니다.

```yaml
metadata:
  name: monitoring
```

적용합니다.

```bash
kubectl apply -f 1.namespace.yaml
kubectl get ns monitoring
```

> Namespace는 단순한 폴더가 아닙니다. 앞으로 Prometheus·Grafana·Alertmanager·Secret·ServiceMonitor·Ingress를 현재 Monitoring 범위로 묶는 Kubernetes 작업 경계입니다.
>
> 여기서 `Active`를 확인한 뒤 다음 단계로 갑니다.

## 3.2 External ETCD Certificate Secret을 준비한다

Secret Script를 실행하기 전 현재 Member용 인증서 자료를 사용하고 있는지 확인합니다. 다른 Cluster 인증서를 이름만 바꿔 사용하지 않습니다.

Secret 전문을 출력하지 않고 생성합니다.

```bash
./2.secret.sh
kubectl get secret etcd-certs -n monitoring
kubectl describe secret etcd-certs -n monitoring | grep -A3 -E 'ca\.pem|node-'
```

강사 설명:

> Secret 이름이 `etcd-certs`라는 사실만으로 현재 DEV Member ETCD용 Secret이라고 볼 수 없습니다.
>
> 지금은 값 자체를 출력하지 않고 Namespace, Type, Key 이름이 필요한 구조인지 확인합니다. 실제 Key 이름은 뒤의 `5-2-1-4 External ETCD ServiceMonitor`에서 `certFile`과 `keyFile` 참조에 사용합니다.
>
> Secret Data, Certificate 본문, Private Key는 강의 화면과 증적에 남기지 않습니다.

## 3.3 Grafana PVC를 준비한다

Manifest를 확인합니다.

```yaml
metadata:
  name: grafana-pvc
  namespace: monitoring
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 16Gi
  storageClassName: scs-netapp-qtree-nfs-sc-delete
```

적용합니다.

```bash
kubectl apply -f 3.grafana-pvc.yaml
kubectl get pvc grafana-pvc -n monitoring -o wide
kubectl describe pvc grafana-pvc -n monitoring
```

> 여기에서 `Bound`를 확인합니다. 다만 9/2에서 배운 것처럼 PVC Bound는 실제 Grafana Pod Mount까지 증명하지 않습니다.
>
> 현재 단계에서는 Grafana가 사용할 Persistent Volume을 Provisioning할 선행조건이 준비됐다는 것만 확인하고 실제 Pod Mount는 Stack 배포 뒤 다시 봅니다.

# 4. 원본 5-2-1-2 — Prometheus Operator CRD 배포

> Preliminary Resource를 준비했지만 Kubernetes API가 아직 Prometheus Operator 전용 객체를 이해할 준비가 됐는지는 별도입니다.
>
> Kubernetes 기본 API에는 `Prometheus`, `Alertmanager`, `ServiceMonitor`, `PrometheusRule` 같은 객체가 원래 들어 있지 않습니다. 그래서 실제 Stack을 배포하기 전에 CRD를 등록해 **"이 Cluster에서 이런 종류의 Monitoring 객체를 사용할 수 있다"**는 API Schema부터 준비합니다.

```text
CRD
= Kubernetes API에 새로운 Resource 종류를 등록
        ↓
Prometheus / Alertmanager / ServiceMonitor 같은 Custom Resource
= 원하는 Monitoring 상태를 선언
        ↓
Prometheus Operator
= 그 선언을 읽고 실제 Monitoring 구성을 관리
```

> 여기서 CRD 이름 8개를 암기하는 것이 목적은 아닙니다. **뒤 Bundle이 사용하는 `monitoring.coreos.com` API가 실제로 등록되고 사용할 수 있는 상태인지**를 확인하는 것이 목적입니다.

Setup Directory로 이동합니다.

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/2.kube-prometheus-0.11.0/manifests/setup
ls -al
kubectl get crd | grep -E 'alertmanager|podmonitor|probe|prometheus|servicemonitor|thanosruler'
kubectl api-resources | grep monitoring.coreos.com
```

확인 대상 CRD는 다음 8개입니다.

```text
alertmanagerconfigs.monitoring.coreos.com
alertmanagers.monitoring.coreos.com
podmonitors.monitoring.coreos.com
probes.monitoring.coreos.com
prometheuses.monitoring.coreos.com
prometheusrules.monitoring.coreos.com
servicemonitors.monitoring.coreos.com
thanosrulers.monitoring.coreos.com
```

기존 CRD를 삭제하지 않습니다. 원본대로 Server-Side Apply를 수행합니다.

```bash
kubectl apply \
  --server-side \
  --field-manager=prometheus-crd-installer \
  -f .
```

강사 설명:

> 기존 CRD가 있다고 삭제 후 재생성하지 않습니다. 다른 Component가 같은 CRD를 사용하고 있을 수 있기 때문입니다.
>
> Server-Side Apply는 API Server가 Field Ownership을 관리하게 합니다. 다른 Field Manager와 충돌한다고 `--force-conflicts`를 바로 사용하지 않습니다. 먼저 어떤 소비자와 Bundle이 CRD를 관리하고 있는지 확인합니다.

그다음 각 CRD가 실제 API에서 사용 가능한 상태인지 기다립니다.

```bash
for crd in \
  alertmanagerconfigs.monitoring.coreos.com \
  alertmanagers.monitoring.coreos.com \
  podmonitors.monitoring.coreos.com \
  probes.monitoring.coreos.com \
  prometheuses.monitoring.coreos.com \
  prometheusrules.monitoring.coreos.com \
  servicemonitors.monitoring.coreos.com \
  thanosrulers.monitoring.coreos.com; do
  kubectl wait --for=condition=Established "crd/$crd" --timeout=60s
done
```

API Schema도 확인합니다.

```bash
kubectl explain prometheus.spec --api-version=monitoring.coreos.com/v1
kubectl explain servicemonitor.spec --api-version=monitoring.coreos.com/v1
```

> `kubectl apply` 성공은 CRD 생성 요청이 받아들여졌다는 뜻입니다. `Established`는 Kubernetes API가 실제 Custom Resource를 제공할 준비가 됐다는 더 강한 증거입니다.
>
> 하지만 CRD가 정상이라고 Prometheus Pod나 실제 Target이 정상이라는 뜻은 아닙니다. 이 단계의 성공 범위는 Monitoring 객체 정의가 준비됐다는 것까지입니다.

## 6.1 Monitoring Ingress를 구성한다

## 6.2 External ETCD Service와 Endpoints를 준비한다

> External ETCD는 Kubernetes Pod가 아니기 때문에 일반 Service Selector만으로 발견할 수 없습니다. 그래서 Kubernetes 밖의 실제 ETCD 주소를 `Endpoints`로 표현하고, 그것을 `Service`와 연결한 뒤 `ServiceMonitor`가 Prometheus Scrape 대상으로 선택하게 만듭니다.

```text
External ETCD
109.156.22.70~72:2379
        ↓
Endpoints
= Kubernetes 밖의 실제 주소를 표현
        ↓
Headless Service etcd-k8s
= Prometheus Discovery가 사용할 Service 형태 제공
        ↓
ServiceMonitor
= 어느 Port / Scheme / TLS로 Scrape할지 선언
        ↓
Prometheus
= Secret을 Mount해 HTTPS Client 인증 후 실제 Metric Scrape
```

> 따라서 `Service`, `Endpoints`, `ServiceMonitor`, `etcd-certs`, Prometheus `spec.secrets`는 따로 외울 객체가 아니라 **External ETCD 하나를 Prometheus Target으로 연결하기 위한 한 경로의 구성요소**입니다.

이제 원본 순서대로 ETCD Monitoring을 구성합니다.

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/3.servicemonitor_etcd
ls -al
grep -nE 'name:|namespace:|ip:|port:' 1.service.yaml 2.endpoints.yaml
kubectl describe secret -n monitoring etcd-certs | grep -A3 -E 'ca\.pem|node-'
```

Service 구조:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: etcd-k8s
  namespace: monitoring
  labels:
    k8s-app: etcd-k8s
spec:
  type: ClusterIP
  clusterIP: None
  ports:
    - name: metrics
      port: 2379
      targetPort: 2379
  selector: null
```

Endpoints 구조:

```yaml
apiVersion: v1
kind: Endpoints
metadata:
  name: etcd-k8s
  namespace: monitoring
  labels:
    k8s-app: etcd-k8s
subsets:
  - addresses:
      - ip: 109.156.22.70
      - ip: 109.156.22.71
      - ip: 109.156.22.72
    ports:
      - name: metrics
        port: 2379
        protocol: TCP
```

강사 설명:

> External ETCD는 Kubernetes Pod가 아니므로 일반 Pod Selector로 발견할 수 없습니다.
>
> 그래서 Kubernetes 안에 Headless Service와 실제 외부 Address를 가진 Endpoints를 만들어 Prometheus Discovery 대상처럼 표현합니다.
>
> 여기서 가장 중요한 것은 IP가 현재 DEV Member ETCD 세 대라는 점입니다. Host ETCD 주소가 들어가도 객체 생성은 성공할 수 있기 때문에 반드시 실제값을 대조합니다.

## 6.3 ServiceMonitor TLS 참조를 완성한다

Preliminary 단계에서 확인한 실제 Secret Key 이름을 사용합니다.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: etcd-k8s
  namespace: monitoring
  labels:
    k8s-app: etcd-k8s
spec:
  jobLabel: k8s-app
  endpoints:
    - port: metrics
      interval: 30s
      scheme: https
      tlsConfig:
        caFile: /etc/prometheus/secrets/etcd-certs/ca.pem
        certFile: /etc/prometheus/secrets/etcd-certs/<확인한-dev-node-cert>.pem
        keyFile: /etc/prometheus/secrets/etcd-certs/<확인한-dev-node-cert>-key.pem
        serverName: etcd-cluster
        insecureSkipVerify: true
  selector:
    matchLabels:
      k8s-app: etcd-k8s
```

강사 설명:

> ServiceMonitor가 Service를 선택하고 `metrics` Port로 HTTPS Scrape를 수행합니다.
>
> CA는 Server Certificate Trust와 관련되고 Client Certificate/Key는 ETCD가 Prometheus Client를 인증하는 데 사용됩니다.
>
> Secret 이름이 있다고 TLS가 올바른 것은 아닙니다. 현재 Member 인증서 Key 구조와 실제 참조가 맞아야 합니다.

> [!warning] 원본 TLS 정책
> `insecureSkipVerify: true`는 원본 DKS Procedure의 값입니다. 현장에서 임의로 보안정책을 변경하지 않고, SAN 검증 전환은 ETCD 인증서 운영 담당자의 승인 후 별도 처리합니다.

```text
반복 TLS / timeout / scrape error 없음
```

강사 설명:

> `Target 존재`와 `Target UP`은 다른 단계입니다.
>
> `Target 존재`는 Prometheus Discovery가 ServiceMonitor·Service·Endpoints 연결을 따라 대상 자체를 만들었다는 뜻입니다. `Target UP`은 그 대상에 실제로 접근해 HTTPS/TLS를 통과하고 Metric 응답을 받았다는 뜻입니다.
>
> 따라서 Target `UP`은 Discovery, Network, HTTPS, TLS 인증과 Metric 응답까지 통과했다는 중요한 증거입니다.
>
> 하지만 다른 Cluster ETCD를 가리켜도 `UP`일 수 있습니다. 그래서 **상태가 UP인지와 주소가 현재 DEV Member `109.156.22.70~72:2379`인지 둘 다** 대조합니다.

> [!note] 교육 보강 — 실제 Query와 Label 확인
> 원본 Target 확인 뒤 교육 보강으로 현재 Member의 ETCD Metric을 Query하고 `cluster=dev-apps-pa01-xas`, `stage=Dev`가 기대대로 붙는지 확인할 수 있습니다. 이 보강은 원본 순서를 대체하지 않습니다.

# 9. 문제가 생기면 원본 순서에서 처음 실패한 지점부터 본다

> 장애 때는 Monitoring Component 이름을 무작위로 돌아다니지 않습니다. **앞에서 만든 경로의 어느 계층까지 성공했는지**를 먼저 자릅니다.

```text
현재 Member 환경값
        ↓
Kubernetes 선행 Resource / Storage
        ↓
CRD / Monitoring API
        ↓
Scheduling / Runtime
        ↓
ServiceMonitor Discovery
        ↓
Network / TLS / Scrape
        ↓
Prometheus Query
        ↓
Grafana Datasource / Dashboard
        ↓
DNS / VIP / Ingress 외부 접근
```

강사는 장애를 다음 순서로 좁힙니다.

> `5-2-0`에서 현재 Cluster·Storage·Registry 값이 틀렸다면 Manifest 세부 설정부터 고치지 않습니다.
>
> Preliminary에서 Grafana PVC가 Pending이면 CRD나 ServiceMonitor를 수정하지 않습니다. StorageClass·Provisioner·PVC Event부터 봅니다.
>
> CRD가 Established되지 않았다면 Stack 뒤쪽을 보지 않습니다.
>
> Stack Pod가 Pending이면 Selector·Taint·Resource·PVC를 확인하고, `ImagePullBackOff`면 Registry·Tag·CA·Pull Secret을 봅니다.
>
> Pod는 정상인데 ETCD Target 자체가 없다면 ServiceMonitor Selector, Service Label·Port, Endpoints를 봅니다.
>
> Target은 있는데 `Down`이면 Endpoint Network·HTTPS·TLS·Secret 참조를 봅니다.
>
> Target은 `UP`인데 Grafana에 데이터가 없으면 Prometheus Query와 Datasource·Dashboard Query를 봅니다.
>
> 내부 Grafana는 정상인데 외부 접근만 실패하면 DNS·VIP-B·Router·Ingress·Backend Service 경로를 봅니다.

이미 통과한 앞 단계를 근거 없이 재설치하거나 삭제하지 않습니다.
