# 4.3 KubeSphere User Guide 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 **수강생이 KubeSphere에서 처음 Application Resource를 배포한다는 전제**로 작성했다. 메뉴 이름부터 외우게 하지 않는다. Application에 필요한 저장공간, Private Image 인증, 실행 단위, 내부 연결과 외부 주소를 먼저 설명한 뒤 PVC·Secret·Deployment·Service·Route라는 이름과 UI 절차를 연결한다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
Application에 필요한 역할을 먼저 설명한다
→ 역할의 Kubernetes 이름을 붙인다
→ 앞 단계가 다음 단계에 주는 값을 보여준다
→ Xi'an UI의 입력 위치와 실제 값을 연결한다
→ 같은 Resource를 YAML에서 다시 확인한다
```

## 0-1. 오늘 전체 한 줄

```text
AD 계정과 Network를 준비한다
→ Project 역할을 받는다
→ PVC로 Storage를 요청한다
→ Image Secret에 Harbor 인증정보를 둔다
→ Deployment가 Image·Secret·PVC를 사용한다
→ Service가 Pod를 선택한다
→ Route가 Service를 Domain에 연결한다
→ 같은 구조를 YAML로 확인한다
→ 필요하면 Autoscaling을 설정한다
→ kubectl은 별도 승인 경로로 사용한다
```

---

# 1. 시작 — Deployment 화면부터 열지 않는다

> 오늘은 KubeSphere에서 Application Resource를 배포하는 흐름을 보겠습니다.
>
> **하지만**, Deployment 화면부터 열면 Image, Storage, Network와 권한이 왜 필요한지 연결하기 어렵습니다.
>
> Application을 실행하려면 먼저 로그인할 사용자와 Project 권한이 필요합니다. Private Harbor Image를 가져올 인증정보와 데이터를 저장할 공간도 준비해야 합니다.
>
> Container를 실행한 뒤에는 여러 Pod를 하나의 Service로 연결하고, 외부 사용자가 접근할 Domain을 Route에 지정해야 합니다.

```text
사용자와 접속 경로
→ Project 권한
→ Storage
→ Private Image 인증
→ Container 실행
→ 내부 Service
→ 외부 Route
```

## 1.1 UI에서 만드는 Resource의 관계

```text
PVC
→ Deployment가 Mount

Image Secret
→ Deployment가 Image Pull에 사용

Deployment
→ Pod 생성

Service
→ Pod Label로 대상 선택

Route·Ingress
→ Domain과 Path를 Service에 연결
```

> 이 관계를 이해하면 UI 메뉴와 YAML은 서로 다른 작업이 아니라 같은 Kubernetes Resource를 입력하는 두 방식이라는 점을 알 수 있습니다.

## 1.2 현재 적용 상태

> 이 Guide의 설치 기준은 KubeSphere `v3.2.1`입니다.
>
> 화면 명칭이 다르면 실제 Xi'an Console을 우선합니다.
>
> Cluster, Network, Harbor와 StorageClass는 Xi'an 기준으로 갱신됐습니다.
>
> **하지만**, SCS AD 연동 정보와 KubeSphere Dashboard 최종 FQDN은 아직 확정되지 않았습니다. 이 두 값은 기존 환경을 복사하지 않고 Xi'an 운영팀과 현재 카탈로그에서 다시 확인합니다.

# 2. Application을 만들기 전에 사용자와 접속 경로를 준비한다

## 2.1 AD 계정

> KubeSphere 사용자 신청은 AD 계정을 기준으로 처리합니다.
>
> 현재 SCS AD Domain, Group Path, 보안그룹과 최종 로그인 방식은 확인이 필요합니다.

| 항목 | 현재 상태 |
|---|---|
| Domain | 운영팀 확인 필요 |
| 위치 | 운영팀 확인 필요 |
| 보안그룹 | 운영팀 확인 필요 |

> **따라서**, 운영팀 확인 없이 기존 Taylor 값을 사용하지 않습니다.

## 2.2 세 종류의 방화벽 목적지

> 사용자가 KubeSphere를 이용할 때는 목적이 다른 세 경로가 필요할 수 있습니다.
>
> Dashboard는 Resource를 관리하는 화면, Member Cluster Ingress는 실제 Application 접속 경로, Harbor는 Image 접속 경로입니다.

### KubeSphere Dashboard

| 서비스 | IP | Port |
|---|---:|---:|
| KubeSphere Dashboard | `109.156.25.46` | `80`, `443` |

> 이 IP는 `prd-host-pa01-xas`의 Host Ingress VIP입니다. 최종 Dashboard FQDN은 확인이 필요합니다.

### Member Cluster Ingress

| 환경 | IP | Port | 용도 |
|---|---:|---:|---|
| 운영 `prd-apps-pa01-xas` | `109.156.25.60` | `80`, `443` | 운영 Application 접속 |
| 개발 `dev-apps-pa01-xas` | `109.156.25.75` | `80`, `443` | 개발 Application 접속 |

### Harbor

| 서비스 | FQDN | IP | Port |
|---|---|---:|---:|
| Harbor | `xa.dcr.dks.samsungds.net` | `109.156.22.53` | `80`, `443` |

> 사용자 Source IP에서 실제로 사용할 목적지의 `80`, `443` Port로 방화벽이 열려 있어야 합니다.
>
> Dashboard가 열린다고 Harbor와 Application Ingress까지 자동으로 열린 것은 아닙니다.

# 3. Project 안에서 할 수 있는 일을 Role로 나눈다

> KubeSphere에서 사용자가 작업하는 경계는 Project입니다.
>
> 이 Project는 Kubernetes Namespace와 같은 대상입니다.
>
> **하지만**, Project가 보인다고 모든 사용자가 Resource를 만들거나 Member를 관리할 수 있는 것은 아닙니다. Role에 따라 허용 범위가 달라집니다.

| Role | 허용 범위 | 적용 기준 |
|---|---|---|
| `project-admin` | Project Resource·설정·Member 관리 | 별도 운영 정책으로 부여 |
| `project-operator` | 사용자·Role·Project 설정을 제외한 Resource 생성·수정·삭제 | 신청서 `Admin` 매핑 |
| `project-viewer` | Project Resource 조회 | 신청서 `User` 매핑 |

## 3.1 Operator 권한을 부여하는 순서

> Member와 Role을 관리할 수 있는 `project-admin` 계정으로 진행합니다.

```text
Projects
→ 대상 Project
→ Project Settings
→ Project Members
→ Invite 또는 +User
→ Workspace에 초대된 Member 선택
→ project-operator
→ OK
```

> 신청서의 `Admin`이라는 이름과 KubeSphere의 `project-admin`은 같은 뜻이 아닙니다.
>
> 신청서 `Admin`은 기본적으로 `project-operator`에 매핑하고, Member 관리 권한이 있는 `project-admin`은 별도 운영 정책에 따릅니다.

# 4. Application 데이터를 저장할 PVC를 만든다

> Container와 Pod는 다시 만들어질 수 있습니다.
>
> Application 데이터가 Pod 수명과 함께 사라지지 않게 하려면 별도의 Storage 요청이 필요합니다.
>
> Kubernetes에서 사용자가 Storage를 요청하는 Resource를 **PersistentVolumeClaim**, 줄여서 **PVC**라고 합니다.

## 4.1 PVC 생성 메뉴

```text
KubeSphere Dashboard
→ 대상 Project
→ Storage
→ Volumes
→ Create
```

## 4.2 기본 정보

| 항목 | 입력 | 설명 |
|---|---|---|
| Name | `<pvc-name>` | 필수 |
| Alias | 필요할 때 입력 | 선택 |
| Description | 필요할 때 입력 | 선택 |

## 4.3 Storage 옵션

| 항목 | 입력 기준 |
|---|---|
| Storage Class | `scs-netapp-qtree-nfs-sc-delete` |
| Access Mode | 공유 Mount가 필요하고 StorageClass가 지원하면 `RWX` |
| Volume Capacity | 승인된 Quota 이내의 용량 |

> StorageClass는 Xi'an NetApp NFS 기준값입니다.
>
> **하지만**, 화면 목록이나 승인된 환경값과 다를 수 있으므로 실제 UI 또는 승인된 `kubectl get sc` 결과에서 다시 확인합니다.
>
> `RWX`도 무조건 선택하는 값이 아닙니다. 여러 Pod의 공유 Mount가 필요하고 해당 StorageClass가 지원할 때 선택합니다.

## 4.4 생성

```text
Advanced Settings
→ Create
```

> PVC를 만들면 다음 Deployment 단계에서 이 이름을 선택해 Container 경로에 Mount합니다.

# 5. Private Harbor Image를 위한 Secret을 만든다

> Private Harbor Image는 Registry 인증정보 없이 가져올 수 없습니다.
>
> **그래서**, KubeSphere Project 안에 Harbor Registry Address와 계정정보를 담은 Image Secret을 만듭니다.

## 5.1 Secret 생성 순서

```text
Deployment와 같은 Project
→ Configuration
→ Secrets
→ Create
→ Basic Information
→ Secret Name
→ Next
→ Data Settings
```

## 5.2 입력값

| 항목 | 입력 기준 |
|---|---|
| Type | `Image registry information` |
| Registry Address | `xa.dcr.dks.samsungds.net` |
| Username | 승인된 저장소 계정 |
| Password | 저장소 비밀번호 |

> Password는 문서나 YAML에 기록하지 않습니다.

## 5.3 Secret을 Deployment에 연결해야 한다

> Secret은 `Create`를 눌렀다고 자동으로 모든 Deployment에 적용되지 않습니다.
>
> Deployment를 만들 때 같은 Project의 Image Pull Secret으로 이 Secret을 명시적으로 선택해야 합니다.

```text
Image Secret 생성
≠
Deployment 적용 완료

Deployment의 Image Pull Secret에서 선택
→ Private Image 인증에 사용
```

# 6. Deployment로 Container 실행 조건을 정의한다

> 이제 Storage와 Private Image 인증정보가 준비됐습니다.
>
> **Deployment**는 어떤 Image로 몇 개의 Pod를 실행하고, 어떤 Resource와 Volume을 사용할지 정의합니다.

## 6.1 Deployment 생성 메뉴

```text
KubeSphere Dashboard
→ 대상 Project
→ Application Workloads
→ Workloads
→ Deployments
→ Create
```

## 6.2 기본 정보

| 항목 | 입력 | 설명 |
|---|---|---|
| Name | `<deployment-name>` | 필수 |
| Alias | 필요할 때 입력 | 선택 |
| Description | 필요할 때 입력 | 선택 |

## 6.3 Pod와 Image

| 항목 | 입력 기준 |
|---|---|
| Pod Replicas | 필요한 복제 수 |
| Container Image | `xa.dcr.dks.samsungds.net/<harbor-project>/<image>:<tag>` |

> Image 주소의 Harbor Project, Repository와 Tag를 실제 승인값으로 바꿉니다.
>
> Private Image라면 앞에서 만든 같은 Project의 Image Pull Secret을 선택합니다.

## 6.4 Label과 Selector

> Deployment Selector와 Pod Template Label은 같은 값을 사용해야 합니다.

```text
Deployment Selector
=
Pod Template Label
```

> 이 값은 뒤에서 Service가 Pod를 선택할 때도 사용합니다.

## 6.5 CPU·Memory Requests와 Limits

> 각 Container에는 CPU와 Memory의 `requests`와 `limits`를 설정합니다.
>
> `requests`는 Resource 배치와 Autoscaling 계산의 기준이 됩니다.
>
> `limits`는 Container가 사용할 수 있는 상한을 정합니다.

## 6.6 PVC Mount

```text
Volume Settings
→ Mount Volume
→ Existing Volume
→ 앞에서 만든 PVC 선택
→ Container 내부 절대 경로 입력
```

예시 Mount 경로:

```text
/data
```

## 6.7 생성

```text
Advanced Settings
→ Create
```

> Deployment가 만들어지면 다음 단계에서 이 Deployment의 Pod를 찾아갈 Service를 만듭니다.

# 7. Service가 Pod를 하나의 접속 대상으로 묶는다

> Deployment의 Pod는 여러 개일 수 있습니다.
>
> **그래서**, Service가 Label을 기준으로 대상 Pod를 선택하고 Application Port를 하나의 접속 대상으로 제공합니다.

## 7.1 Service 생성 메뉴

```text
KubeSphere Dashboard
→ 대상 Project
→ Application Workloads
→ Services
→ Create
→ Specify Workloads
```

## 7.2 기본 정보

| 항목 | 입력 | 설명 |
|---|---|---|
| Name | `<service-name>` | 필수 |
| Alias | 필요할 때 입력 | 선택 |
| Description | 필요할 때 입력 | 선택 |

## 7.3 Label Selector

> Service의 Label Selector는 Deployment의 Pod Template Label과 정확히 같아야 합니다.

```text
Service Selector
=
Pod Template Label
```

> 일치하지 않으면 Service Endpoint가 생성되지 않습니다.

## 7.4 Port

| 항목 | 의미 |
|---|---|
| Protocol | Application 통신 Protocol |
| Name | Port 이름 |
| Container Port | Container Application이 실제로 Listen하는 Port |
| Service Port | Service가 제공하는 Port |

> Container Port는 Application의 실제 Listen Port와 일치해야 합니다.

## 7.5 생성

```text
Advanced Settings
→ Create
```

> Service는 Project 내부의 Application 접속 대상을 준비합니다. 외부 사용자에게 Domain으로 공개하려면 Route를 연결합니다.

# 8. Route가 외부 Domain을 Service에 연결한다

> KubeSphere의 **Route**는 Kubernetes **Ingress**입니다.
>
> 사용자가 접속할 HostName과 Path를 내부 Service와 Port에 연결합니다.

## 8.1 환경별 Domain Pattern

```text
운영
*.xaprdpa01.apps.dks.samsungds.net

개발
*.xadevpa01.apps.dks.samsungds.net
```

> 운영과 개발 Domain을 혼용하지 않습니다.

## 8.2 Route 생성 메뉴

```text
KubeSphere Dashboard
→ 대상 Project
→ Application Workloads
→ Routes 또는 Routers
→ Create
```

## 8.3 기본 정보

| 항목 | 입력 | 설명 |
|---|---|---|
| Name | `<route-name>` | 필수 |
| Alias | 필요할 때 입력 | 선택 |
| Description | 필요할 때 입력 | 선택 |

## 8.4 Route 옵션

| 항목 | 입력 기준 |
|---|---|
| Add Route Rule | `Specify Domain` |
| HostName | 대상 환경의 승인된 FQDN |
| Protocol | `HTTP` 또는 `HTTPS` |
| Paths | Path, 연결 Service와 Port |

## 8.5 생성

```text
Advanced Settings
→ Create
```

> Route가 참조하는 Service 이름과 Port가 실제 앞 단계 값과 일치해야 합니다.

# 9. UI에서 만든 관계를 YAML로 다시 본다

> 지금까지는 UI에서 PVC, Deployment, Service와 Route를 만들었습니다.
>
> YAML도 같은 Resource를 정의합니다. 중요한 것은 YAML 문법을 외우는 것이 아니라 Resource 사이의 이름과 Label이 정확히 연결되는지 보는 것입니다.

## 9.1 PVC YAML

경로:

```text
Storage
→ Volumes
→ Create
→ Edit YAML
```

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  namespace: example-project
  name: nginx-test
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 10Gi
  storageClassName: scs-netapp-qtree-nfs-sc-delete
  volumeMode: Filesystem
```

> `example-project`, Resource 이름과 용량은 실제 승인값으로 바꿉니다.
>
> `storageClassName`, Access Mode와 용량은 UI에서 선택한 값과 같은 의미입니다.

## 9.2 Deployment YAML

경로:

```text
Application Workloads
→ Workloads
→ Deployments
→ Create
→ Edit YAML
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  namespace: example-project
  name: nginx-test
  labels:
    app: nginx-test
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-test
  template:
    metadata:
      labels:
        app: nginx-test
    spec:
      imagePullSecrets:
        - name: harbor-registry-secret
      containers:
        - image: xa.dcr.dks.samsungds.net/example-project/nginx:latest
          imagePullPolicy: IfNotPresent
          name: nginx
          ports:
            - containerPort: 80
              name: http-test
              protocol: TCP
          volumeMounts:
            - mountPath: /data
              name: nginx-data
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
      volumes:
        - name: nginx-data
          persistentVolumeClaim:
            claimName: nginx-test
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25%
      maxSurge: 25%
```

> `metadata.namespace`는 대상 Project와 일치해야 합니다.
>
> `selector.matchLabels.app`과 Pod Template의 `labels.app`은 같은 값입니다.
>
> `imagePullSecrets.name`은 같은 Project에 만든 실제 Secret 이름으로 바꿉니다.
>
> `image`는 실제 Harbor Project·Repository·Tag를 사용합니다.
>
> `claimName`은 앞에서 만든 PVC 이름과 같아야 합니다.

## 9.3 Service YAML

경로:

```text
Application Workloads
→ Services
→ Create
→ Specify Workload
→ Edit YAML
```

```yaml
apiVersion: v1
kind: Service
metadata:
  namespace: example-project
  name: nginx-test
  labels:
    app: nginx-test
spec:
  sessionAffinity: None
  ports:
    - name: http-test
      port: 80
      protocol: TCP
      targetPort: 80
  selector:
    app: nginx-test
```

> `spec.selector.app`은 Deployment의 Pod Label과 같아야 합니다.
>
> `targetPort`는 Container가 실제로 Listen하는 Port와 연결됩니다.

## 9.4 Route YAML

경로:

```text
Application Workloads
→ Routes
→ Create
→ Edit YAML
```

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  namespace: example-project
  name: nginx-test
spec:
  rules:
    - host: nginx-test.xadevpa01.apps.dks.samsungds.net
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-test
                port:
                  number: 80
```

> 이 예시는 개발 Domain을 사용합니다.
>
> `backend.service.name`과 Port는 앞에서 만든 실제 Service와 일치해야 합니다.

## 9.5 YAML에서 이어지는 값

```text
모든 metadata.namespace
→ 같은 Project

Deployment imagePullSecrets.name
→ Image Secret 이름

Deployment claimName
→ PVC 이름

Deployment Pod Label
→ Service Selector

Container Port
→ Service targetPort

Route Backend Name·Port
→ Service Name·Port
```

# 10. 필요하면 Autoscaling을 설정한다

> 기본 Deployment를 만든 뒤에는 부하에 따라 Replica 수를 조정하는 Autoscaling을 설정할 수 있습니다.

## 10.1 메뉴 순서

```text
대상 Project
→ Application Workloads
→ Workloads
→ Deployment 선택
→ More
→ Edit Autoscaling
```

## 10.2 선행조건

> Metrics API가 정상이어야 합니다.
>
> 대상 Container에는 CPU·Memory `requests`가 설정돼 있어야 합니다.

## 10.3 설정 항목

| 항목 | 의미 |
|---|---|
| Target CPU Usage (%) | 평균 CPU 사용량을 `resources.requests.cpu` 대비 백분율로 계산 |
| Target Memory Usage (MiB) | Pod당 평균 Memory 사용량의 절대값 |
| Minimum Replicas | 최소 Pod 수 |
| Maximum Replicas | 최대 Pod 수이며 Minimum 이상으로 설정 |

> CPU 백분율과 Memory 절대값의 기준을 섞지 않습니다.
>
> 값을 입력한 뒤 **OK**를 선택합니다.

# 11. kubectl은 별도 승인된 사용자만 사용한다

> 기본 KubeSphere 사용자는 UI를 사용합니다.
>
> `kubectl`은 KubeSphere Project Role만 있다고 바로 사용할 수 있는 경로가 아닙니다.

```text
T-DKS팀 Bastion 계정
+
필요한 방화벽
+
CyberArk 권한
+
사용자별 kubeconfig
```

> Bastion 계정은 AD 계정명과 동일하게 생성 요청합니다.
>
> 계정 생성 통보를 받은 뒤 CyberArk 권한을 별도로 요청합니다.
>
> kubeconfig에는 Client 인증서와 개인키가 포함될 수 있으므로 민감정보로 취급하고 파일 권한을 `0600`으로 제한합니다.

읽기 전용 접근 확인 예시:

```bash
kubectl auth can-i get pods -n <project>
```

> 승인된 Project를 대상으로 권한을 확인합니다. 상세 사용 절차는 별도 `Enable users using kubectl CLI` 문서를 따릅니다.

# 12. 전체 흐름을 다시 연결한다

> KubeSphere 사용자는 먼저 승인된 AD 계정과 필요한 Network를 준비합니다.
>
> 자신의 Project에서 수행할 작업에 맞는 Role을 받습니다.
>
> Application 데이터가 필요하면 PVC를 만들고, Private Harbor Image를 사용하면 같은 Project에 Image Secret을 만듭니다.
>
> Deployment에는 실제 Harbor Image, Image Pull Secret, Pod Label, CPU·Memory와 PVC Mount를 연결합니다.
>
> Service는 Deployment Pod Label을 Selector로 사용하고, Route는 승인된 환경 Domain과 Path를 Service에 연결합니다.
>
> UI에서 만든 값은 YAML에서도 Namespace, Secret, PVC, Label, Port와 Backend 이름으로 이어집니다.
>
> Autoscaling은 Metrics API와 Resource Requests가 준비된 뒤 설정합니다.
>
> `kubectl`은 Bastion, 방화벽, CyberArk와 사용자별 kubeconfig가 모두 승인된 경우에만 사용합니다.

```text
AD·방화벽
→ Project Role
→ PVC·Image Secret
→ Deployment
→ Service
→ Route
→ YAML 관계 확인
→ Autoscaling
→ 별도 승인 kubectl
```
