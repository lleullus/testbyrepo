# 4.1 DS Kubernetes Service Overview 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 **수강생이 Xi'an DKS의 구조를 처음 본다는 전제**로 작성했다. 제품명과 주소를 먼저 외우게 하지 않는다. 사용자가 Image를 준비하고 Application을 배포하는 흐름부터 설명한 뒤 KubeSphere, Harbor, Host·Member Cluster, Workspace·Project·Namespace라는 실제 이름을 붙인다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
사용자가 하려는 일을 먼저 말한다
→ 그 일을 나누어 맡는 역할을 설명한다
→ 역할의 기술 이름을 붙인다
→ Xi'an 실제 구성과 주소를 보여준다
→ 사용자가 작업할 경계와 권한을 설명한다
→ 실제 이용 순서로 연결한다
```

## 0-1. 오늘 전체 한 줄

```text
Application을 실행하려 한다
→ 실행 원본 Image는 Harbor에 보관한다
→ KubeSphere에서 배포를 관리한다
→ 실제 Application은 Member Cluster에서 실행한다
→ Workspace·Project로 사용 범위를 나눈다
→ Project는 Kubernetes Namespace와 같다
→ 방화벽·계정·권한·Quota를 준비한다
→ Image를 연결하고 Application을 외부에 공개한다
```

---

# 1. 시작 — DKS 구성도부터 외우지 않는다

> 오늘은 DS Kubernetes Service, 줄여서 DKS의 전체 구조를 보겠습니다.
>
> **하지만**, 서버 이름과 IP부터 외우면 각 구성 요소가 왜 필요한지 연결하기 어렵습니다.
>
> 먼저 사용자가 하려는 일을 생각하겠습니다. 사용자는 Application을 실행할 공간이 필요하고, 실행에 사용할 Container Image를 보관해야 하며, 허용된 범위 안에서 배포와 설정을 관리해야 합니다.
>
> **그래서**, Xi'an DKS는 Image 보관, 사용자 관리, Application 실행을 서로 다른 역할로 나눕니다.

## 1.1 사용자 관점에서 두 도구를 먼저 구분한다

> 사용자는 주로 **Harbor**와 **KubeSphere**를 사용합니다.
>
> Harbor는 Container Image를 저장하고 Push·Pull하는 곳입니다.
>
> KubeSphere는 Kubernetes Application Resource를 화면에서 만들고 관리하는 곳입니다.
>
> **하지만**, KubeSphere 화면에서 배포를 눌렀다고 Application이 그 화면 안에서 실행되는 것은 아닙니다. KubeSphere는 관리 화면이고, 실제 Container는 Kubernetes Cluster에서 실행됩니다.

```text
Harbor
→ Container Image 저장·Push·Pull

KubeSphere
→ 사용자·Project·권한 관리
→ Kubernetes Resource 생성·관리

Member Cluster
→ 실제 Application Pod 실행
```

---

# 2. Xi'an DKS의 네 구성 요소를 역할로 이해한다

> Xi'an DKS에는 관리 역할을 담당하는 Host, 운영과 개발 Application을 실행하는 두 Member Cluster, Image를 보관하는 Harbor가 있습니다.

| 구성 요소 | Xi'an 이름 | 사용자 관점의 역할 |
|---|---|---|
| KubeSphere Host | `prd-host-pa01-xas` | 로그인, Workspace·Project와 권한 관리 |
| Production Member | `prd-apps-pa01-xas` | 운영 Application 배포·실행 |
| Development Member | `dev-apps-pa01-xas` | 개발 Application 배포·실행 |
| Harbor | `prd-harbor-xas` | Container Image 저장·Push·Pull |

## 2.1 Host는 관리하고 Member Cluster는 실행한다

> 사용자는 KubeSphere Host의 웹 화면에 로그인합니다. 여기에서 자신에게 할당된 Workspace와 Project를 보고 Kubernetes Resource를 만듭니다.
>
> **하지만**, 실제 Workload는 Host가 아니라 대상 Member Cluster에 배포됩니다.
>
> 운영 Application은 `prd-apps-pa01-xas`, 개발 Application은 `dev-apps-pa01-xas`에서 실행됩니다.
>
> **그래서**, 화면에 로그인한 위치와 실제 Application이 실행되는 위치를 구분해야 합니다.

```text
사용자
→ KubeSphere Host에서 로그인·관리
→ 운영 또는 개발 Project 선택
→ 대상 Member Cluster에 Workload 배포
```

## 2.2 Harbor는 실행 원본을 보관한다

> Application Container를 실행하려면 Container Image가 필요합니다.
>
> Xi'an에서는 `prd-harbor-xas`가 이 Image를 중앙에 보관합니다.
>
> 사용자는 Harbor에 Image를 Push하고, KubeSphere에서 그 Image 주소를 지정해 Workload를 배포합니다.
>
> Private Image를 사용할 때는 KubeSphere Project 안에 Image Secret도 필요합니다. 이 절차는 뒤의 Harbor와 KubeSphere User Guide에서 자세히 보겠습니다.

---

# 3. 서비스에 도달하려면 주소와 방화벽이 필요하다

> 구성 요소가 준비돼 있어도 사용자 PC에서 그 서비스까지 통신할 길이 없으면 접속할 수 없습니다.
>
> **그래서**, Dashboard, 운영·개발 Application, Harbor는 각각 다른 주소와 접속 IP를 가집니다.

| 대상 | Domain 또는 Pattern | 접속 IP | Port |
|---|---|---:|---:|
| KubeSphere Dashboard | 최종 FQDN 확인 필요 | `109.156.25.46` | `80`, `443` |
| Host Ingress | `*.xaprdpa01.mgmt.dks.samsungds.net` | `109.156.25.46` | `80`, `443` |
| Production Ingress | `*.xaprdpa01.apps.dks.samsungds.net` | `109.156.25.60` | `80`, `443` |
| Development Ingress | `*.xadevpa01.apps.dks.samsungds.net` | `109.156.25.75` | `80`, `443` |
| Harbor | `xa.dcr.dks.samsungds.net` | `109.156.22.53` | `80`, `443` |

## 3.1 Dashboard와 Application 주소를 구분한다

> KubeSphere Dashboard는 Resource를 관리하는 화면입니다. 현재 접속 IP는 `109.156.25.46`이고 최종 Dashboard FQDN은 확인이 필요합니다.
>
> Application 접속 주소는 대상 환경에 따라 달라집니다.
>
> 운영 Application은 `*.xaprdpa01.apps.dks.samsungds.net`, 개발 Application은 `*.xadevpa01.apps.dks.samsungds.net` Pattern을 사용합니다.
>
> **따라서**, Dashboard 접속과 실제 Application 접속은 같은 방화벽 목적지가 아닙니다.

## 3.2 Harbor 주소도 별도다

> Harbor는 `xa.dcr.dks.samsungds.net`, 접속 IP는 `109.156.22.53`입니다.
>
> Image를 Push·Pull할 사용자는 자신의 Source IP에서 Harbor의 `80`, `443` Port까지 통신할 수 있어야 합니다.

## 3.3 외부 요청이 Cluster 안으로 들어가는 경로

> 사용자는 외부에서 각 Ingress VIP의 `80`, `443` Port로 접속합니다.
>
> 이 요청은 Cluster 안에서 Router Node의 `30080`, `30443` Port로 전달됩니다.

```text
사용자 Source IP
→ Ingress VIP 80·443
→ Router Node 30080·30443
→ 대상 Service와 Pod
```

> 사용자가 신청할 때는 먼저 자신이 어느 화면과 어느 Application 환경에 접속할지 구분해야 합니다. 그에 맞는 Destination IP와 Port로 방화벽을 요청합니다.

## 3.4 계정 정보는 아직 확정 전이다

> 사용자 신청은 AD 계정을 기준으로 처리합니다.
>
> **하지만**, SCS AD Domain과 KubeSphere 연동 정보, 최종 로그인 방식과 계정 활성화 절차는 현재 확정 전입니다.
>
> **따라서**, 기존 환경의 값을 그대로 사용하지 않고 Xi'an 운영팀의 최종 안내를 확인합니다.

# 4. 사용자가 작업할 공간을 나눈다

> 여러 팀이 하나의 Kubernetes 환경을 함께 사용하면 각 팀의 Resource와 권한을 구분해야 합니다.
>
> **그래서**, KubeSphere에서는 Workspace와 Project로 사용 범위를 나눕니다.

## 4.1 Workspace와 Project는 1:1이다

> Xi'an DKS 정책에서는 Workspace 한 개와 Project 한 개를 1:1로 구성합니다.
>
> 사용자는 자신에게 할당된 Project 안에서만 허용된 Application Resource를 조회하거나 관리합니다.

```text
Workspace 1개
↕ 1:1
Project 1개
```

## 4.2 KubeSphere Project는 Kubernetes Namespace다

> KubeSphere 화면에서는 작업 공간을 Project라고 부릅니다.
>
> Kubernetes에서는 같은 경계를 Namespace라고 부릅니다.
>
> **결국**, KubeSphere Project와 Kubernetes Namespace는 같은 대상을 서로 다른 화면과 API에서 부르는 이름입니다.

```text
KubeSphere Project
=
Kubernetes Namespace
```

## 4.3 Resource 사용량은 Quota로 제한한다

> Project가 있다고 CPU, Memory와 Storage를 제한 없이 사용할 수 있는 것은 아닙니다.
>
> CPU와 Memory는 Workspace·Project Quota로 제한합니다.
>
> Storage는 Namespace 전체 Quota와 StorageClass별 Quota로 제한합니다.
>
> **그래서**, 이용 신청서에는 필요한 CPU·Memory·Storage 용량을 함께 기재해야 합니다.

## 4.4 역할에 따라 할 수 있는 일이 다르다

| 요청 또는 역할 | 의미 |
|---|---|
| 신청서 `Admin` | 기본적으로 KubeSphere `project-operator`에 매핑 |
| 신청서 `User` | `project-viewer`에 매핑 |
| `project-admin` | 별도 운영 정책에 따라 부여 |

> `project-operator`는 Workload와 Storage 같은 Resource를 생성·수정·삭제할 수 있습니다.
>
> **하지만**, Project Member와 Role은 관리할 수 없습니다.
>
> `project-viewer`는 Project Resource를 조회하는 역할입니다.
>
> Member 관리 권한이 있는 `project-admin`은 별도 운영 정책에 따라 부여합니다.

# 5. 실제 이용 흐름으로 연결한다

> 이제 구성 요소, 주소, 작업 공간과 권한을 실제 사용자 이용 순서로 연결하겠습니다.

## 5.1 먼저 필요한 접속 경로를 연다

> 사용자는 KubeSphere Dashboard, Harbor, 사용할 Member Cluster Ingress를 구분하고 필요한 방화벽을 요청합니다.

```text
Dashboard 관리
→ 109.156.25.46

운영 Application
→ 109.156.25.60

개발 Application
→ 109.156.25.75

Harbor
→ 109.156.22.53
```

## 5.2 최초 로그인으로 계정 접근을 준비한다

> 운영팀 안내에 따라 KubeSphere에 최초 로그인해 계정 접근 이력을 생성합니다.
>
> AD 연동과 최종 로그인 방법은 Xi'an 운영팀의 확정 안내를 따릅니다.

## 5.3 이용 신청서를 제출한다

> 이용 신청서에는 Project 이름만 적는 것이 아닙니다.
>
> 대상 환경이 운영인지 개발인지, 필요한 CPU·Memory·Storage는 얼마인지, 어떤 사용자가 어떤 권한을 요청하는지 함께 적습니다.

```text
Project Name
+
운영·개발 환경
+
CPU·Memory·Storage
+
사용자
+
요청 권한
```

## 5.4 운영팀이 작업 공간과 권한을 준비한다

> 운영팀은 Workspace와 Project를 만들고 사용자를 초대합니다.
>
> 그다음 Project Role과 Quota를 승인 내용에 맞게 부여합니다.

## 5.5 Image를 준비하고 Workload를 배포한다

> Harbor Project Member로 추가된 사용자는 Container Image를 Harbor에 Push합니다.
>
> KubeSphere에서는 그 Image 주소를 사용해 Workload를 배포합니다.
>
> Harbor Image가 Private이면 같은 KubeSphere Project에 Image Secret을 만들고 Deployment에 연결합니다.

```text
사용자 또는 CI
→ Harbor에 Image Push
→ KubeSphere Project에서 Image 주소 지정
→ Private Image Secret 연결
→ Member Cluster에 Workload 배포
```

## 5.6 Application을 외부에 공개한다

> 실행된 Application은 대상 Member Cluster의 Ingress Domain으로 노출합니다.
>
> 운영과 개발의 Domain Pattern을 혼용하지 않습니다.

## 5.7 kubectl은 기본 사용자 경로가 아니다

> 기본 사용자는 KubeSphere UI를 사용합니다.
>
> `kubectl`은 Bastion 계정, 방화벽, CyberArk 권한과 사용자별 kubeconfig가 모두 승인된 경우에만 별도 절차로 사용합니다.
>
> **따라서**, KubeSphere 사용 권한이 있다고 `kubectl` 접근까지 자동으로 허용되는 것은 아닙니다.

# 6. 전체 구조를 한 번에 다시 말한다

> Xi'an DKS에서 사용자는 KubeSphere Host에 로그인해 자신의 Workspace와 Project를 관리합니다.
>
> KubeSphere Project는 Kubernetes Namespace와 같으며 사용자는 그 경계 안에서 허용된 Resource만 다룹니다.
>
> Application Image는 Harbor에 저장하고, 실제 Workload는 운영 또는 개발 Member Cluster에서 실행합니다.
>
> **하지만**, 서비스가 준비돼 있다는 사실만으로 사용자가 접속할 수 있는 것은 아닙니다. Dashboard, Harbor와 대상 Ingress의 주소가 서로 다르므로 필요한 방화벽 경로를 각각 준비해야 합니다.
>
> **그래서**, `방화벽 → 계정 접근 → 이용 신청 → Workspace·Project·Role·Quota 준비 → Harbor Image → KubeSphere Workload → Member Ingress 공개` 순서로 이용합니다.

```text
사용자
→ KubeSphere Host에서 관리
→ Project·Namespace 안에서 Resource 생성
→ Harbor Image 연결
→ 운영·개발 Member Cluster에서 실행
→ Ingress Domain으로 Application 공개
```

3. 운영 Application과 개발 Application은 각각 어느 Member Cluster에서 실행되는가?
4. KubeSphere Dashboard, 운영 Ingress, 개발 Ingress와 Harbor의 접속 IP는 각각 무엇인가?
5. KubeSphere Dashboard 접속과 Application 접속의 방화벽 목적지가 다른 이유는 무엇인가?
6. KubeSphere Project와 Kubernetes Namespace는 어떤 관계인가?
7. Workspace와 Project는 Xi'an 정책에서 어떻게 구성하는가?
8. CPU·Memory와 Storage는 각각 어떤 Quota로 제한하는가?
9. `project-operator`, `project-viewer`, `project-admin`은 무엇이 다른가?
10. DKS 이용 신청서에는 Project 이름 외에 무엇을 적어야 하는가?
11. Private Harbor Image를 KubeSphere Workload에서 사용하려면 무엇이 추가로 필요한가?
12. `kubectl`이 기본 사용자 접속 경로가 아닌 이유는 무엇인가?
