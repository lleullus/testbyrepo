# 6.2 Kubernetes Dashboard 접속 및 Token 로그인 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 **수강생이 Kubernetes Dashboard, ServiceAccount와 Token을 거의 모른다는 전제**로 작성했다. 오전 교육이나 앞 절을 기억한다고 가정하지 않는다. Token 재생성 명령부터 보여주지 말고, 사용자가 어느 Cluster의 무엇을 보려는지와 정상 접속 경로를 먼저 설명한다. Token 원문은 화면, 교육자료, 명령 이력과 장애 기록에 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
사용자가 어느 Cluster의 Dashboard를 사용하려는지 먼저 말한다
→ 화면을 열고 사용자를 확인하는 역할을 쉬운 말로 설명한다
→ Dashboard·ServiceAccount·Secret·Token·RBAC이라는 이름을 붙인다
→ Xi'an Cluster별 URL을 보여준다
→ 원본 Guide의 확인과 Token 교체 절차로 들어간다
→ URL·인증·권한 중 마지막 성공과 첫 실패를 구분한다
→ 같은 Cluster URL과 승인 범위 조회로 복구를 확인한다
```

## 0-1. 오늘 전체 한 줄

```text
사용자는 특정 Kubernetes Cluster의 상태를 Dashboard에서 보려 한다
→ 대상 Cluster와 URL을 먼저 고른다
→ 브라우저가 Dashboard까지 도달해야 한다
→ admin-user라는 ServiceAccount가 있어야 한다
→ 그 계정과 연결된 Token Secret이 있어야 한다
→ Token으로 사용자 신원을 확인한다
→ RBAC이 허용한 Resource를 조회한다
→ 실패하면 URL·Token·권한 중 처음 끊긴 곳을 찾는다
```

# 1. 시작 — Token부터 다시 만들지 않는다

> 오늘은 Kubernetes Dashboard 화면이 열리지 않거나 Token Login이 실패할 때 무엇부터 확인해야 하는지 보겠습니다.
>
> 그런데 `Token이 안 됩니다`라는 말만 듣고 기존 Secret을 지우거나 새 Token부터 만들지는 않겠습니다. Dashboard URL 자체가 틀린 경우, 다른 Cluster의 Token을 사용한 경우, Token은 맞지만 RBAC 권한이 없는 경우는 서로 다른 문제입니다.
>
> 먼저 사용자가 어느 Cluster에서 무엇을 보려는지부터 확인하겠습니다.

## 1.1 사용자가 하려는 일

> Kubernetes Cluster에는 Node, Namespace와 Workload 같은 Resource가 있습니다.
>
> 사용자가 이 상태를 브라우저 화면에서 조회하고 관리할 수 있도록 보여주는 도구가 **Kubernetes Dashboard**입니다.
>
> Xi'an에는 Cluster가 하나만 있는 것이 아닙니다. 중앙 관리용 Host Cluster, 운영 Application용 Member Cluster, 개발 Application용 Member Cluster가 각각 있으며 Dashboard 주소도 서로 다릅니다.

## 1.2 KubeSphere 화면과 Kubernetes Dashboard를 섞지 않는다

> KubeSphere Dashboard와 Kubernetes Dashboard는 같은 화면이 아닙니다.
>
> KubeSphere는 Workspace와 Project를 중심으로 DKS Resource를 관리하는 사용자 화면입니다. 이번 6.2의 Kubernetes Dashboard는 특정 Kubernetes Cluster의 Resource를 보는 별도 화면입니다.
>
> **따라서**, 사용자가 `Dashboard가 안 됩니다`라고 말하면 먼저 어떤 제품의 어떤 Cluster URL을 열었는지 확인해야 합니다.

```text
KubeSphere Dashboard 문제인가
Kubernetes Dashboard 문제인가
대상은 Host인가 PRD Member인가 DEV Member인가
화면이 안 열리는가
화면은 열리지만 Token이 거부되는가
Login은 되지만 일부 Resource가 보이지 않는가
```

## 1.3 화면, Login과 권한은 서로 다른 단계다

> 브라우저에 Login 화면이 나타났다는 것은 Dashboard 서비스까지 도달했다는 뜻입니다.
>
> **하지만**, 아직 Token이 유효하다는 뜻은 아닙니다.
>
> Token Login이 성공했다는 것은 Dashboard가 해당 Token의 신원을 확인했다는 뜻입니다.
>
> **하지만**, 모든 Resource를 조회하거나 변경할 권한이 있다는 뜻은 아닙니다. 실제 허용 범위는 **RBAC**이 결정합니다.

# 2. 정상일 때 어떤 연결이 이어지는가

> 장애를 찾으려면 정상 접속이 어떤 순서로 완성되는지 먼저 알아야 합니다.
>
> `어느 Cluster인가`, `브라우저가 어디까지 가는가`, `누구의 Token인가`, `어떤 권한이 있는가`라는 쉬운 질문으로 나눈 뒤 기술 이름을 붙이겠습니다.

## 2.1 대상 Cluster와 URL을 먼저 고른다

원본 Guide의 Xi'an Dashboard URL은 다음과 같습니다.

| Cluster | 역할 | Dashboard URL |
|---|---|---|
| `prd-host-pa01-xas` | 중앙 관리 Host | `https://dashboard.apps.xaprdpa01.mgmt.dks.samsungds.net` |
| `prd-apps-pa01-xas` | 운영 Application Member | `https://dashboard.apps.xaprdpa01.apps.dks.samsungds.net` |
| `dev-apps-pa01-xas` | 개발 Application Member | `https://dashboard.apps.xadevpa01.apps.dks.samsungds.net` |

> 이 URL들은 서로 바꿔 쓰는 주소가 아닙니다.
>
> Host의 Token을 Member Dashboard에 넣거나 DEV에서 확인해야 할 Workload를 PRD Dashboard에서 찾으면 올바른 결과를 얻을 수 없습니다.
>
> 원본 Guide의 URL은 교육 기준입니다. 실제 장애에서는 현재 승인된 Cluster와 DNS 값이 같은지 다시 확인합니다.

## 2.2 브라우저 요청이 Dashboard까지 간다

> 사용자가 URL을 열면 브라우저 요청은 이름을 IP로 찾고, Network와 HTTPS를 통과해 해당 Cluster의 Dashboard 화면으로 전달됩니다.

```text
사용자 브라우저
→ Dashboard FQDN과 DNS
→ 대상 Cluster VIP-B
→ Ingress
→ Dashboard Service
→ Dashboard Pod
→ Login 화면
```

> 이 연결이 끊기면 Token을 입력할 화면 자체가 나오지 않습니다.
>
> **따라서**, URL이 열리지 않는 문제와 Token Login 실패를 같은 문제로 취급하지 않습니다.

## 2.3 ServiceAccount는 Dashboard가 확인할 신원이다

> 사람이 일반 웹사이트에 ID와 Password를 넣듯이, Kubernetes 안의 작업 주체도 자신의 신원을 나타내는 계정이 필요합니다.
>
> Kubernetes에서 이런 계정을 **ServiceAccount**라고 합니다.
>
> 원본 Guide는 `kubernetes-dashboard` Namespace의 `admin-user` ServiceAccount를 사용합니다.

```text
Namespace: kubernetes-dashboard
ServiceAccount: admin-user
```

> `admin-user`라는 이름만 존재한다고 Login 준비가 끝난 것은 아닙니다. Dashboard에 입력할 인증값이 연결돼 있어야 합니다.

## 2.4 Secret이 Token을 담고 ServiceAccount와 연결된다

> ServiceAccount의 인증값을 담는 Kubernetes Resource가 **Secret**입니다.
>
> 이번 Guide에서 사용하는 Secret Type은 `kubernetes.io/service-account-token`입니다.
>
> Secret의 Annotation에 `admin-user`가 지정되면 Controller가 해당 ServiceAccount용 Token Data를 채웁니다.

```text
admin-user ServiceAccount
→ service-account-token Secret
→ Controller가 Token Data 생성
→ Dashboard에 Token 입력
```

> Token은 Password와 같은 인증정보입니다. 존재와 연결 상태는 확인하되 원문은 교육 화면, 문서, 로그와 채팅에 남기지 않습니다.

## 2.5 RBAC이 실제 조회 범위를 정한다

> Token은 `누구인가`를 확인하는 인증 수단입니다.
>
> 그 신원이 Namespace, Node와 Workload를 어디까지 볼 수 있는지는 **RBAC**, 즉 Kubernetes 권한 설정이 정합니다.

```text
Token 인증 성공
→ ServiceAccount 신원 확인

Resource 조회 성공
→ RBAC 권한까지 확인
```

> Login 성공과 모든 Resource 조회 가능을 같은 의미로 사용하지 않습니다.

## 2.6 정상 경로를 한 줄로 연결한다

```text
대상 Cluster 확정
→ 현재 kubectl Context 확인
→ kubernetes-dashboard Namespace
→ admin-user ServiceAccount
→ service-account-token Secret
→ Token Data 존재
→ 같은 Cluster Dashboard URL
→ Token Login
→ 승인 범위 Resource 조회
```

# 3. URL 성공, Token Login 성공과 Resource 조회 성공은 다르다

```text
Dashboard Login 화면 표시
≠ Token 인증 성공

Token 인증 성공
≠ 모든 Resource 조회 권한

admin-user 존재
≠ Token Secret 정상

Token Secret 존재
≠ 다른 Cluster Dashboard에서도 사용 가능
```

> 이 차이를 모르면 Login 화면이 열리지 않는데 Token을 계속 바꾸거나, Login은 성공했는데 Resource가 보이지 않는 문제를 Token 만료로 잘못 판단하게 됩니다.

---

# 4. 장애를 보기 전에 같은 대상을 고정한다

> 해결 명령보다 먼저 다음 값을 고정합니다.

```text
대상 Cluster
Dashboard 전체 URL
사용자 Source와 발생 시각
화면 자체가 열리는지
Token Login 화면까지 나오는지
Login 뒤 어떤 Resource에서 거부되는지
현재 kubectl Context
admin-user와 Secret 이름
오류 원문
```

> `kubectl` 확인은 대상 Cluster의 승인된 kubeconfig와 접근 권한이 있는 운영자만 수행합니다.

현재 Context 확인:

```console
kubectl config current-context
```

> Context가 대상 Cluster와 다르면 이후의 ServiceAccount와 Secret 조회도 다른 Cluster를 보고 있는 것입니다. 이 상태에서 Token을 새로 만들지 않습니다.

> **하지만**, 읽기 전용 확인에서 원인을 추정했다고 바로 Secret을 만들거나 삭제하는 것은 아닙니다. Token Secret 변경과 삭제는 승인된 대상, 권한과 복구 순서를 확인한 뒤 수행합니다.

# 5. Dashboard URL 자체가 열리지 않는다

> 첫 번째 사용자는 브라우저에서 Dashboard Login 화면까지 도달하지 못합니다.
>
> 이 단계에서는 아직 Token이 사용되지 않았습니다. 따라서 Token Secret을 재생성해도 화면 접근 문제는 해결되지 않습니다.

## 5.1 정확한 Cluster URL인지 확인한다

> 사용자가 입력한 URL을 Cluster별 표와 대조합니다.
>
> 오타, PRD와 DEV 혼용, Host와 Member 혼용이 있으면 먼저 올바른 URL로 다시 확인합니다.

## 5.2 브라우저 경로의 첫 단절을 확인한다

```text
FQDN이 IP로 해석되는가
→ 사용자 Source에서 대상 VIP-B까지 연결되는가
→ HTTPS 응답이 오는가
→ Ingress가 Dashboard Service로 연결되는가
→ Dashboard Pod가 Ready인가
```

> 사용자 Source에서 DNS와 Network가 실패한다면 Dashboard Pod나 Token보다 앞단 문제입니다.
>
> DNS와 Network는 통과하지만 HTTP 응답이 없다면 승인된 운영자가 대상 Cluster의 Ingress, Service와 Pod 상태를 확인합니다.
>
> **따라서**, Login 화면이 나타나기 전에는 `admin-user` Token을 변경하지 않습니다.

## 5.3 Web 접속 복구 기준

> 같은 사용자 Source와 같은 Cluster URL에서 Certificate 오류 없이 Login 화면이 표시돼야 Web 접속 경로가 복구된 것입니다.
>
> **하지만**, Login 화면만으로 Token 인증까지 완료 처리하지 않습니다.

---

# 6. Login 화면은 열리는데 Token이 거부된다

> 두 번째 사용자는 올바른 Cluster의 Login 화면까지 도달했습니다.
>
> 이 상태는 Browser, DNS, Network와 Dashboard Web 경로가 통과했다는 뜻입니다. 이제 대상 Cluster의 `admin-user`, Token Secret과 실제 입력을 구분합니다.

## 6.1 admin-user 존재를 확인한다

```console
kubectl -n kubernetes-dashboard get sa admin-user
```

원본 Guide의 기대 구조:

```text
NAME         SECRETS
admin-user   1
```

> `admin-user`가 없으면 Token 문자열을 다시 복사하는 것으로 해결되지 않습니다.
>
> 원본 6.2는 기존 `admin-user`와 RBAC을 유지한 상태에서 Token Secret을 교체하는 절차입니다. ServiceAccount나 RBAC 자체가 없다면 이 절차를 임의로 확대하지 않고 관련 복구 절차와 승인 담당자에게 연결합니다.

## 6.2 현재 Token Secret을 확인한다

```console
kubectl -n kubernetes-dashboard get secret | grep '^admin-user-token-'
```

기대 Type:

```text
kubernetes.io/service-account-token
```

> Secret 이름의 무작위 접미사와 AGE는 실행 시점마다 달라질 수 있습니다. 원본의 `admin-user-token-jsjxf`를 현재 Secret 이름으로 외우지 않습니다.

> Secret이 존재하면 이름, Namespace, Type과 Data 필드 수를 확인합니다. Token 원문 자체는 출력하지 않습니다.

```console
kubectl -n kubernetes-dashboard get secret <current-token-secret>
```

> 원본 Guide에서는 `DATA=3`을 Token Data가 채워진 기준으로 사용합니다.
>
> **하지만**, `DATA=3`만으로 올바른 Cluster URL에 정확한 Token을 입력했고 RBAC도 정상이라고 증명되지는 않습니다.

## 6.3 Token 입력 과정도 구분한다

> 현재 Secret과 ServiceAccount 연결이 정상이라면 다음을 확인합니다.

```text
대상 Cluster에서 얻은 Token인가
Token 한 줄 전체를 복사했는가
앞뒤 공백이나 줄바꿈이 섞이지 않았는가
다른 Cluster의 Token과 바뀌지 않았는가
Token이 기록·공유되지 않았는가
```

> 원본 Guide에는 Token 출력 명령이 있지만 교육 화면이나 녹화 중에는 실행하지 않습니다. 필요한 운영자가 승인된 보안 경로에서 확인하고 Dashboard에 직접 사용합니다.

## 6.4 기존 Token을 먼저 삭제하지 않는다

> 현재 Token이 실패해도 바로 기존 Secret을 삭제하지 않습니다.
>
> 새 Secret 생성과 Token Data 발급이 실패하면 사용할 수 있는 기존 접근까지 잃을 수 있기 때문입니다.

```text
기존 Secret 유지
→ 새 Secret 생성
→ 새 Token Data 확인
→ 새 Token Login 검증
→ 필요할 때만 기존 Secret 삭제
```

# 7. Token Secret을 안전한 순서로 다시 만든다

> 이 절차는 대상 Cluster, `admin-user`와 RBAC이 정상이고 Token Secret 교체가 승인된 경우에만 수행합니다.
>
> 교육 중에는 실제 Secret을 생성하거나 삭제하지 않고 YAML 구조와 판정 기준만 설명합니다.

## 7.1 새 Secret을 별도 이름으로 생성한다

원본 Guide의 예시:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: admin-user-token-new
  namespace: kubernetes-dashboard
  annotations:
    kubernetes.io/service-account.name: admin-user
type: kubernetes.io/service-account-token
```

적용 명령:

```console
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Secret
metadata:
  name: admin-user-token-new
  namespace: kubernetes-dashboard
  annotations:
    kubernetes.io/service-account.name: admin-user
type: kubernetes.io/service-account-token
EOF
```

> 여기서 중요한 연결은 세 가지입니다.

```text
Namespace = kubernetes-dashboard
ServiceAccount Annotation = admin-user
Type = kubernetes.io/service-account-token
```

> 이름, Namespace, Annotation이나 Type이 틀리면 Controller가 기대한 Token Data를 채우지 못할 수 있습니다.

## 7.2 Controller가 Token Data를 채웠는지 확인한다

```console
kubectl -n kubernetes-dashboard get secret admin-user-token-new
```

원본 Guide의 기대 결과:

```text
NAME                   TYPE                                  DATA
admin-user-token-new   kubernetes.io/service-account-token   3
```

> Secret이 생성됐다는 메시지와 Token 사용 가능 상태는 다릅니다.
>
> `DATA=3`이 될 때까지 연결 상태를 확인합니다. Data가 채워지지 않으면 Secret을 반복 생성하지 않고 Namespace, Annotation, ServiceAccount 이름과 Controller 상태를 확인합니다.

## 7.3 새 Token을 같은 Cluster에서 검증한다

> 승인된 운영자가 새 Token을 보안 경로에서 확인하고, 처음 고정한 같은 Cluster URL의 Dashboard에 입력합니다.

```text
새 Token Login 성공
→ Namespace 조회
→ Node 조회
→ Workload 조회
```

> 실제 승인 범위의 Resource가 조회돼야 새 Token이 사용할 수 있는 상태입니다.

## 7.4 기존 Secret 삭제는 마지막이다

> 새 Token으로 Login과 Resource 조회가 확인된 뒤, 기존 Token 폐기가 운영상 필요한 경우에만 기존 Secret을 삭제합니다.

원본 Guide의 예시:

```console
kubectl -n kubernetes-dashboard delete secret <old-token-secret>
```

> 삭제 전에 삭제 대상이 새 Secret이 아닌지, 기존 Token을 사용하는 다른 운영 경로가 없는지, 새 Token 보관과 전달이 완료됐는지 확인합니다.
>
> 교육 중에는 삭제 명령을 실행하지 않습니다.

---

# 8. Token Login은 성공하지만 일부 Resource가 보이지 않는다

> 세 번째 사용자는 Dashboard Login에는 성공했지만 Namespace, Node 또는 Workload 일부를 조회할 수 없습니다.
>
> 이때 Token을 다시 만드는 것이 항상 맞지는 않습니다.

```text
Login 성공
→ 인증 통과

Resource 조회 거부
→ RBAC 권한 범위 확인
```

> 먼저 사용한 Token이 대상 `admin-user`의 것인지 확인하고, 그다음 승인된 RBAC Binding이 유지되는지 운영 절차로 확인합니다.
>
> 권한이 부족하다는 이유만으로 더 높은 권한을 임의로 부여하지 않습니다. 기대 조회 범위와 승인된 역할을 대조한 뒤 필요한 최소 권한만 적용합니다.

---

# 9. 실제 장애 요청을 하나의 흐름으로 연결한다

> 사용자가 `Kubernetes Dashboard Token Login이 안 됩니다`라고 요청했다고 하겠습니다.
>
> 먼저 Host, PRD Member와 DEV Member 중 어느 Cluster를 보려는지 확인합니다. 입력한 전체 URL, 사용자 Source, 발생 시각과 화면 상태를 고정합니다.
>
> **첫 번째 분기**는 Login 화면이 열리는지입니다.
>
> 화면이 열리지 않으면 URL, DNS, VIP-B, Ingress, Service와 Dashboard Pod 경로를 확인합니다. 아직 Token 단계가 아닙니다.
>
> **두 번째 분기**는 Login 화면은 열리지만 Token이 거부되는 경우입니다.
>
> 대상 Cluster Context, `admin-user`, Token Secret의 Namespace·Type·Data와 Token 입력 상태를 확인합니다. 다른 Cluster Token이나 잘못 복사한 Token이면 Secret을 변경하지 않습니다.
>
> **세 번째 분기**는 현재 Secret을 사용할 수 없어 새 Token Secret이 필요한 경우입니다.
>
> 기존 Secret을 유지한 채 새 Secret을 만들고 Controller가 Data를 채운 것을 확인합니다. 새 Token으로 같은 URL에 Login하고 승인 범위 Resource를 조회한 뒤에만 기존 Secret 폐기를 검토합니다.
>
> **마지막 분기**는 Login은 성공하지만 Resource 조회가 거부되는 경우입니다.
>
> 이것은 인증보다 RBAC 권한 범위 문제일 수 있습니다. Token 재생성을 반복하지 않고 승인된 Binding을 확인합니다.

---

# 10. 오류가 사라진 것과 복구 완료는 다르다

## 10.1 URL 장애

> 같은 사용자 Source에서 처음 고정한 Cluster URL을 열고 Login 화면이 표시되는지 확인합니다.

## 10.2 Token 장애

> 같은 Cluster의 `admin-user`와 연결된 검증된 Token으로 Login이 성공하는지 확인합니다.

## 10.3 권한 장애

> Login 후 승인된 Namespace, Node와 Workload가 기대 범위에서 조회되는지 확인합니다.

## 10.4 Token 교체

> 새 Token Login과 Resource 조회가 먼저 성공해야 합니다. 기존 Secret 삭제가 필요하다면 그 뒤에 수행하고, Token 원문이 자료와 기록에 남지 않았는지 확인합니다.

> **결국**, Login 오류가 사라졌다는 말이 아니라 같은 Cluster URL에서 인증과 승인 범위 조회까지 실제로 완료돼야 복구입니다.

---

# 11. 마무리 — 처음부터 이야기로 다시 말한다

> 사용자는 특정 Kubernetes Cluster의 상태를 Dashboard에서 보려 합니다.
>
> 그래서 먼저 Host, PRD Member와 DEV Member 중 대상 Cluster를 정하고 그 Cluster의 Dashboard URL을 사용합니다.
>
> 브라우저 요청이 DNS, VIP-B, Ingress, Service와 Dashboard Pod를 통과하면 Login 화면이 나타납니다.
>
> 그다음 `kubernetes-dashboard` Namespace의 `admin-user` ServiceAccount와 연결된 Token Secret으로 신원을 확인합니다.
>
> **하지만**, Login 성공이 모든 Resource 권한을 뜻하지는 않습니다. 실제 조회 범위는 RBAC이 정합니다.
>
> **따라서**, 장애가 발생하면 Token부터 다시 만들지 않습니다. `대상 Cluster와 URL → Web 접속 → ServiceAccount → Token Secret → Token 인증 → RBAC 조회` 순서에서 마지막 성공과 첫 실패를 찾습니다.
>
> Token을 교체할 때도 기존 Secret을 먼저 삭제하지 않습니다. 새 Secret과 새 Token을 같은 Cluster에서 검증한 뒤 필요한 경우에만 기존 Secret을 폐기합니다.
