# 6.1 Harbor 접속·로그인 및 Image Push/Pull 오류 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 **수강생이 Harbor와 Docker Registry를 거의 모른다는 전제**로 작성했다. 오전 교육 내용을 기억한다고 가정하지 않는다. 오류 문자열과 명령부터 외우게 하지 말고, 사용자가 Image로 하려던 일과 정상 경로를 쉬운 말로 설명한 뒤 실제 기술 이름과 Xi'an 값을 붙인다. 원본 Guide의 출력에는 Project와 Tag가 이어지지 않는 부분이 있으므로 실제 Xi'an 성공 증적으로 사용하지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
사용자가 하려던 일을 먼저 말한다
→ 정상적으로 필요한 역할을 쉬운 말로 설명한다
→ 그 역할의 기술 이름을 붙인다
→ Xi'an 실제 값을 보여준다
→ 원본 Guide의 절차와 오류로 들어간다
→ 마지막 성공과 첫 실패를 구분한다
→ 같은 사용자 경로로 복구를 확인한다
```

## 0-1. 오늘 전체 한 줄

```text
Harbor에서 Image를 가져오거나 올리려 한다
→ Harbor 주소를 찾아가야 한다
→ Network와 HTTPS를 통과해야 한다
→ Client가 Harbor를 신뢰해야 한다
→ 계정 인증과 대상 Project 권한이 필요하다
→ 정확한 Repository와 Tag로 Pull 또는 Push한다
→ 실제 Image 결과를 확인한다
→ 실패하면 이 흐름에서 처음 끊긴 곳을 찾는다
```

---

# 1. 시작 — 오류 메시지부터 설명하지 않는다

> 오늘은 Harbor 접속, Login, Image Pull과 Push에서 오류가 발생했을 때 무엇부터 확인해야 하는지 보겠습니다.
>
> 그런데 `x509`, `unauthorized`, `manifest unknown`, `denied`부터 외우지는 않겠습니다. 이 단어만 외우면 오류가 조금 다르게 보일 때 어디를 확인해야 하는지 연결할 수 없습니다.
>
> 먼저 사용자가 Harbor에서 무엇을 하려는지부터 다시 보겠습니다. 오전 교육 내용을 기억하고 있다고 가정하지 않겠습니다.

![[harbor-image-container-concept.png]]

*Application 실행 요소를 Container Image로 묶고, 중앙 Registry인 Harbor에 보관해 필요한 사용자가 가져오거나 올리는 흐름*

## 1.1 Harbor에서 사용자가 하려는 일

> Application을 같은 조건으로 실행하려면 프로그램, Library와 실행환경을 하나로 묶은 실행 원본이 필요합니다. 이 실행 원본이 **Container Image**입니다.
>
> 여러 사용자와 서버가 같은 Image를 사용하려면 한곳에 저장하고 공유할 공간이 필요합니다. 이 중앙 Image 저장소를 **Registry**라고 하며 Xi'an에서는 **Harbor**가 이 역할을 담당합니다.
>
> Harbor에서 Image를 사용자 시스템으로 가져오는 동작은 **Pull**, 사용자 시스템의 Image를 Harbor에 올리는 동작은 **Push**입니다.

## 1.2 “Harbor가 안 됩니다”만으로는 아직 알 수 없다

> 사용자가 `Harbor가 안 됩니다`라고 말해도 실제로 실패한 작업은 서로 다를 수 있습니다.
>
> Harbor 화면 자체가 열리지 않을 수도 있고, 화면은 열리지만 Docker Login이 실패할 수도 있습니다. Login은 성공하지만 특정 Image를 Pull하지 못하거나, Pull은 되지만 Push가 거부될 수도 있습니다.
>
> **그래서**, 해결 명령부터 실행하지 않고 사용자가 하려던 작업과 실제 오류를 먼저 구분해야 합니다.

```text
Harbor Web 화면을 열려 했는가
Docker로 Login하려 했는가
Harbor Image를 Pull하려 했는가
로컬 Image를 Harbor에 Push하려 했는가
```

> **하지만**, 이 네 작업은 완전히 따로 떨어져 있지 않습니다. Harbor 주소를 찾고 Network와 HTTPS를 통과하는 공통 기반 위에서 각 작업이 이어집니다.

## 1.3 브라우저와 Docker는 서로 다른 Client다

> Harbor를 사용하는 Client는 하나만 있는 것이 아닙니다.
>
> 사람은 **브라우저**로 Harbor Web 화면을 보고, Image를 Pull하거나 Push할 때는 **Docker daemon**이 Harbor Registry와 통신합니다.
>
> 두 Client는 같은 Harbor 주소를 사용해도 Certificate를 신뢰하는 방식과 실제 요청 경로가 다를 수 있습니다.
>
> **따라서**, 브라우저에서 Harbor 화면이 열린다는 사실만으로 Docker Login과 Pull·Push도 정상이라고 확정할 수 없습니다.

# 2. 정상일 때 어떤 연결이 이어지는가

> 장애를 찾으려면 먼저 정상일 때 무엇이 연결돼야 하는지 알아야 합니다.
>
> 기술 이름부터 외우지 않고 `주소를 어떻게 찾는가`, `Harbor까지 어떻게 가는가`, `HTTPS에서 어떻게 믿는가`, `누구의 요청인지 어떻게 확인하는가`, `어느 Image를 요청했는가`, `실제 결과는 어디에서 확인하는가`라는 질문으로 나누겠습니다.

## 2.1 Harbor 주소를 어떻게 찾는가

> 사용자가 Harbor 서버의 IP를 직접 외우는 대신 서비스 이름으로 접근합니다. 이런 전체 도메인 이름을 **FQDN**이라고 합니다.
>
> 원본 Guide에 기록된 Xi'an Harbor 값은 다음과 같습니다.

```text
FQDN: xa.dcr.dks.samsungds.net
IP: 109.156.22.53
Port: TCP 80, 443
```

> 사용자의 Host는 FQDN을 DNS에 물어 IP를 찾고, 그 IP의 Harbor Port까지 Network와 Firewall을 통과해야 합니다.
>
> **따라서**, `xa.dcr.dks.samsungds.net`을 찾지 못하거나 `109.156.22.53:443`까지 연결하지 못하면 아직 Login이나 Project 권한을 확인할 단계가 아닙니다.
>
> 원본 Guide의 값은 교육 기준이며 실제 운영에서는 현재 승인된 FQDN, IP와 Port가 같은지 다시 확인합니다.

## 2.2 HTTPS에서 Harbor를 어떻게 믿는가

> Network로 Harbor까지 도달해도 Client는 자신이 접속한 서버가 요청한 FQDN의 Harbor가 맞는지 확인해야 합니다.
>
> Harbor가 자신의 신원을 보여주는 것이 **Server Certificate**이고, Client가 그 Certificate를 신뢰할지 판단하는 기준이 **CA**입니다.
>
> Xi'an Guide에서는 Docker를 사용하는 Host가 승인된 `SECDS-2TROOTCA.crt`를 신뢰하도록 적용합니다.
>
> **하지만**, 브라우저와 Docker daemon은 Certificate 신뢰를 서로 다르게 사용할 수 있습니다. 브라우저가 Harbor를 신뢰해도 Docker daemon에 승인된 CA가 반영되지 않았다면 Docker에서는 `x509` 오류가 발생할 수 있습니다.

## 2.3 Docker는 Image 기능의 입구로 요청한다

> Harbor Web 화면은 사람이 Project와 Repository를 확인하는 화면입니다.
>
> Docker가 Image를 Pull하거나 Push할 때는 Harbor의 Image 기능과 통신하는 별도 입구를 사용합니다. 이 입구가 **Registry API**이고 대표 경로가 `/v2/`입니다.
>
> 인증정보 없이 Private Registry의 `/v2/`를 호출하면 `401`이 반환될 수 있습니다. 이것은 Registry 경로가 요청을 받고 인증을 요구한다는 뜻입니다.
>
> **하지만**, 무인증 `401`이 나온 사실만으로 실제 계정 Login과 Pull·Push가 정상이라는 뜻은 아닙니다. Registry 응답과 사용자 인증은 별도로 확인해야 합니다.

## 2.4 누구의 요청인지 확인한다

> Harbor는 조직 내부 Image를 아무나 가져가거나 올리지 못하게 사용자 Account를 확인합니다. 사용자가 Account와 Password로 자신을 증명하는 단계가 **Authentication**, 즉 사용자 인증입니다.
>
> Docker에서는 `docker login`으로 이 단계를 확인하고 정상 결과는 `Login Succeeded`입니다.
>
> **하지만**, Login 성공은 이 Account가 누구인지 확인됐다는 뜻일 뿐 모든 Private Project를 사용할 수 있다는 뜻은 아닙니다.

## 2.5 어느 Project에서 무엇을 할 수 있는지 확인한다

> Harbor는 여러 Team과 Application의 Image가 섞이지 않도록 **Project**로 영역을 나눕니다.
>
> 이 대본에서 다루는 Private Project의 Image를 Pull하거나 Push하려면 사용자가 해당 Project의 Member여야 하고 허용된 Role이 필요합니다. 원본 Guide에서 Image 읽기와 쓰기가 가능한 Role은 `Developer`, `ProjectAdmin`으로 기록돼 있습니다.
>
> **따라서**, Account 인증과 Project 권한은 다음처럼 구분해야 합니다.

```text
Docker Login 성공
→ Account 인증 성공

특정 Project Pull·Push 성공
→ 해당 Project와 작업에 필요한 권한까지 확인
```

## 2.6 어느 Image를 요청했는지 확인한다

> Project 안에서 Image는 **Repository** 단위로 정리되고, 같은 Image의 Version이나 구분값은 **Tag**로 표시합니다.
>
> Docker가 사용하는 전체 Image 주소는 다음 관계로 읽습니다.

```text
<Registry FQDN>/<Project>/<Repository>:<Tag>
```

> 예를 들어 `xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2`라면 Harbor 주소, Project, Repository와 Tag가 모두 포함돼 있습니다.
>
> 이 중 하나만 달라도 다른 Image를 요청하게 됩니다. Login이 성공했더라도 존재하지 않는 Tag를 요청하거나 권한이 없는 Project를 요청하면 Pull은 실패할 수 있습니다.

## 2.7 실제 Image 결과는 어디에서 확인하는가

> Harbor에 저장된 실제 Image 결과를 **Artifact**라고 하며, Image 내용을 식별하는 값으로 **Digest**가 표시됩니다.
>
> Pull이나 Push 명령이 끝났다는 문장만 보지 않습니다. 요청한 Project, Repository와 Tag가 맞는지, Pull한 로컬 Image와 Push한 Harbor Artifact의 Digest가 의도한 결과와 연결되는지 확인해야 합니다.

# 3. Web 성공, Login 성공과 실제 Image 사용 성공은 다르다

> 지금까지의 연결을 두 경로로 나누면 다음과 같습니다.

```text
공통 기반
사용자 Host
→ FQDN과 DNS
→ Harbor IP와 TCP 443
→ HTTPS

Web 확인
→ 브라우저의 Certificate 신뢰
→ Harbor Web 화면
→ Web Login

Image 사용
→ Docker daemon의 CA 신뢰
→ Registry API
→ Docker Login
→ 대상 Project 권한
→ Repository와 Tag
→ Pull 또는 Push
→ Artifact와 Digest
```

> 이 경로는 서로 일부를 공유하지만 하나의 성공이 뒤의 모든 성공을 보장하지는 않습니다.

```text
Harbor Web 화면이 열림
≠ Docker daemon의 CA 신뢰

Registry /v2/가 응답함
≠ Docker Login 성공

Docker Login 성공
≠ 모든 Private Project의 Pull·Push 권한

Pull 성공
≠ Push 권한 보유

Push 명령 종료
≠ 의도한 Harbor Artifact 확인 완료
```

> **결국**, Harbor 장애는 마지막에 보이는 오류 하나만 보는 것이 아니라 이 연결 중 어디까지 성공했고 어디에서 처음 달라졌는지 찾는 작업입니다.

---

# 4. 장애를 볼 때 먼저 같은 대상을 고정한다

> 이제 원본 6.1 Guide의 오류 사례로 들어가겠습니다.
>
> 먼저 현재 보고 있는 결과가 모두 같은 대상의 결과인지 확인해야 합니다. 다른 Host, 다른 Account, 다른 Project와 과거 출력이 섞이면 마지막 성공과 첫 실패를 연결할 수 없습니다.

```text
Harbor FQDN
명령을 실행한 사용자 Host
실제로 사용한 Account
대상 Project
Repository와 Tag
오류 발생 시각
화면이나 명령에 표시된 오류 원문
```

> Password, Docker Credential과 인증서 Private Key는 화면이나 교육 기록에 남기지 않습니다.
>
> 대상을 고정한 뒤 정상 경로와 비교합니다.

```text
사용자가 하려던 작업은 무엇인가
→ 어디까지 실제로 성공했는가
→ 처음 실패한 결과는 무엇인가
→ 어떤 읽기 전용 확인이 다음 행동을 바꾸는가
```

> **하지만**, 읽기 전용 확인에서 원인을 추정했다고 바로 변경하는 것은 아닙니다. CA 배치, Docker 재시작과 Member·Role 변경은 해당 Host와 Project의 승인된 절차와 권한을 확인한 뒤 수행합니다.

# 5. Harbor Web 화면 자체가 열리지 않는다

> 첫 번째 사용자는 브라우저에서 Harbor 화면을 열려고 했지만 Login 화면에도 도달하지 못했습니다.
>
> 이 경우 Account와 Password, Project Role은 아직 확인할 단계가 아닙니다. 요청이 Harbor의 인증과 권한 판단 지점까지 도달했는지부터 알 수 없기 때문입니다.
>
> **그래서**, 이름을 찾는 단계부터 Harbor HTTPS 응답까지 순서대로 확인합니다.

## 5.1 FQDN을 IP로 찾을 수 있는가

```console
getent hosts xa.dcr.dks.samsungds.net
```

> `getent`는 사용자 Host가 Xi'an Harbor FQDN을 어떤 IP로 해석하는지 확인합니다.
>
> 원본 Guide의 기대값은 `109.156.22.53`입니다. 결과가 없거나 다른 IP라면 Password를 변경하지 않고 사용 중인 DNS와 현재 승인된 Harbor 주소를 확인합니다.

## 5.2 Harbor의 HTTPS Port까지 갈 수 있는가

```console
nc -vz -w 3 109.156.22.53 443
```

> `nc`는 현재 사용자 Host에서 `109.156.22.53:443`까지 TCP 연결이 되는지 확인합니다.
>
> DNS는 기대 IP를 반환하지만 이 단계가 timeout이면 이름이 아니라 사용자 Source IP에서 Harbor까지의 Network와 Firewall 경로를 확인합니다.

## 5.3 Harbor가 HTTPS로 응답하는가

```console
curl -skI https://xa.dcr.dks.samsungds.net/
```

> `curl` 결과에 HTTP 응답이 보이면 Harbor의 HTTPS Endpoint가 요청에 응답한 것입니다.
>
> **하지만**, 이 명령의 `-k`는 Certificate 검증을 생략합니다. 따라서 이 결과는 Endpoint 응답을 확인하는 근거이지 Client의 Certificate 신뢰가 정상이라는 근거는 아닙니다.
>
> DNS, TCP 443과 HTTPS Endpoint 응답이 모두 확인되면 Network 전단을 반복하지 않습니다. 같은 사용자 Host의 브라우저에서 승인된 FQDN을 다시 열어 Certificate를 정상적으로 신뢰하는지, Certificate 확인 뒤 Harbor Login 화면까지 표시되는지 구분합니다.
>
> 브라우저에서 Login 화면까지 확인됐다면 Web 접속 경로는 통과했습니다. 그다음 실제 실패한 작업이 Web Login인지 Docker Login인지에 따라 사용자 인증 또는 Docker daemon의 Certificate 신뢰를 확인합니다.

# 6. Web은 열리는데 Docker Login에서 x509가 발생한다

> 두 번째 사용자는 브라우저에서 Harbor 화면을 열 수 있습니다.
>
> 그런데 Docker Login은 다음 오류로 실패합니다.

```text
x509: certificate signed by unknown authority
```

> 이 오류는 Docker daemon이 Harbor의 Certificate 신뢰를 완성하지 못했다는 뜻입니다.
>
> 브라우저가 열린다는 사실은 사용자 Host에서 Harbor HTTPS까지 도달한 경로가 완전히 끊기지는 않았다는 뜻입니다.
>
> **하지만**, 브라우저의 신뢰와 Docker daemon의 신뢰는 같지 않습니다. 이 단계에서 Account나 Password부터 변경하면 원인에 맞지 않습니다.

## 6.1 승인된 CA가 준비돼 있는지 확인한다

원본 Guide의 첫 확인은 다음과 같습니다.

```console
ls -l /etc/pki/ca-trust/source/anchors/SECDS-2TROOTCA.crt
ls -l ./SECDS-2TROOTCA.crt
```

> 첫 번째 명령은 승인된 CA가 OS trust anchor 경로에 배치돼 있는지 확인합니다.
>
> 두 번째 명령은 작업 위치에 원본 CA 파일이 있는지 확인합니다.
>
> **하지만**, 같은 이름의 파일이 존재한다는 사실만으로 승인된 올바른 CA라고 확정할 수는 없습니다. 임의로 내려받은 Certificate나 Harbor Server Certificate로 대체하지 않고 승인된 `SECDS-2TROOTCA.crt`인지 확인해야 합니다.

## 6.2 CA trust를 Docker에 반영한다

원본 Guide의 조치 순서는 다음과 같습니다.

```console
sudo cp ./SECDS-2TROOTCA.crt /etc/pki/ca-trust/source/anchors/
sudo update-ca-trust extract
sudo systemctl restart docker
sudo systemctl is-active docker
```

> CA를 trust anchor에 배치하고 OS CA trust를 갱신한 뒤 Docker daemon을 재시작해야 갱신된 신뢰를 사용합니다.
>
> 이 명령들은 사용자 Host의 trust store와 Docker Service 상태를 변경합니다. 교육 중에는 승인된 테스트 Host와 변경 권한이 확인되지 않았다면 실행하지 않고 절차와 결과만 설명합니다.
>
> `systemctl is-active docker`의 `active`는 Docker daemon이 실행 중이라는 증거입니다.
>
> **하지만**, `active`만으로 Harbor Certificate 신뢰와 Login 성공까지 증명되지는 않습니다. 같은 FQDN으로 Docker Login을 다시 확인해야 합니다.

## 6.3 같은 Docker Login으로 다시 확인한다

```console
sudo docker login xa.dcr.dks.samsungds.net
```

정상 결과:

```text
Login Succeeded
```

> 이 결과가 나오면 Docker daemon의 HTTPS 신뢰와 해당 Account의 Login 경로가 실제로 통과한 것입니다.
>
> Login 과정에서 `/root/.docker/config.json`에 Password가 암호화되지 않은 상태로 저장될 수 있다는 경고가 나타날 수 있습니다. 이 경고는 Login 실패가 아니지만 Password와 Credential을 화면이나 기록에 남겨도 된다는 뜻은 아닙니다.
>
> **하지만**, Login 성공은 특정 Project의 Image를 Pull하거나 Push할 권한까지 증명하지 않습니다.

# 7. HTTPS와 Registry는 응답하지만 Docker Login이 실패한다

> 세 번째 사용자는 Harbor 주소에 도달할 수 있지만 Docker Login에서 `unauthorized`가 발생합니다.
>
> 이때 Harbor 전체가 Down인지, Registry가 응답하지만 Account 인증이 거부된 것인지 구분해야 합니다.

원본 Guide의 확인은 다음과 같습니다.

```console
curl -sk -o /dev/null -w '%{http_code}\n' https://xa.dcr.dks.samsungds.net/
curl -sk -o /dev/null -w '%{http_code}\n' https://xa.dcr.dks.samsungds.net/v2/
```

대표 결과:

```text
Harbor Web / = 200
Registry /v2/ without credentials = 401
```

> `/`의 `200`은 Harbor Web Endpoint가 응답한다는 뜻입니다.
>
> 인증정보가 없는 `/v2/`의 `401`은 Registry API가 인증을 요구하며 응답한다는 뜻입니다. 이 `401`만 보고 Registry 장애라고 판단하지 않습니다.
>
> **하지만**, 두 명령 모두 `-k`로 Certificate 검증을 생략했으며 Account 인증도 수행하지 않았습니다. 실제 사용자 인증 결과는 어떤 명령이 반환한 오류인지와 함께 확인합니다.

원본 Guide에서는 다음 Docker Login 명령의 결과로 `unauthorized`가 기록돼 있습니다.

```console
sudo docker login xa.dcr.dks.samsungds.net
```

```text
unauthorized: unauthorized to access repository
```

> 같은 단어가 Pull이나 Push 오류에도 포함될 수 있으므로 문자열만 보고 실패 단계를 정하지 않습니다. 위 사례는 `docker login`이 반환한 오류이므로 Account 인증 단계에서 확인합니다.

> Network와 Registry 응답이 확인되고 Login만 거부된다면 Account 문자열, Password, AD Account 상태와 Harbor 인증 연동을 확인합니다.
>
> Password 원문을 명령행, 화면 캡처와 장애 기록에 남기지 않습니다.
>
> **하지만**, 이 단계에서 특정 Project의 Member·Role을 임의로 올리는 것은 맞지 않습니다. 먼저 Account 인증을 해결하고 `Login Succeeded`를 확인한 뒤 대상 Project의 Pull·Push 권한을 별도로 확인합니다.

# 8. Login은 성공했지만 Image Pull이 실패한다

> 네 번째 사용자는 `Login Succeeded`까지 확인했습니다.
>
> 이것은 Docker가 Harbor를 신뢰하고 해당 Account 인증이 성공했다는 뜻입니다.
>
> **하지만**, 사용자가 요청한 Project, Repository와 Tag가 실제로 존재하고 그 Account가 접근할 수 있다는 뜻은 아닙니다.
>
> 따라서 Pull 오류에서는 비밀번호를 다시 입력하기 전에 전체 Image 주소를 같은 값으로 고정합니다.

```text
Registry FQDN
/
Project
/
Repository
:
Tag
```

## 8.1 존재하지 않는 Tag를 요청한 경우

원본 Guide의 예시는 다음과 같습니다.

```console
sudo docker pull xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:not-exist
```

오류:

```text
manifest unknown: manifest unknown
```

> 이 오류는 Harbor와 통신하고 Image 요청까지 전달했지만 요청한 Manifest를 찾지 못했다는 뜻입니다.
>
> **그래서**, Account와 Password를 다시 만들기 전에 대상 Project와 Repository가 맞는지, 요청한 Tag가 Harbor Artifact에 실제로 존재하는지 확인합니다.

## 8.2 Project 경로나 권한을 구분해야 하는 경우

원본 Guide의 예시는 다음과 같습니다.

```console
sudo docker pull xa.dcr.dks.samsungds.net/other-private-project/nginx:1.14.2
```

오류:

```text
pull access denied for xa.dcr.dks.samsungds.net/other-private-project/nginx,
repository does not exist or may require 'docker login':
denied: requested access to the resource is denied
```

> 이 오류에는 Repository가 없을 수 있다는 문장과 Login 또는 접근 권한이 필요할 수 있다는 문장이 함께 들어 있습니다.
>
> **따라서**, 오류 문자열 하나만 보고 Repository 부재 또는 권한 문제로 확정하지 않습니다.
>
> 먼저 요청한 Project와 Repository 이름을 확인하고 Harbor 화면에서 실제 Artifact 존재를 확인합니다. 그다음 현재 Docker Login에 사용한 Account가 해당 Private Project의 Member인지, Pull이 허용된 Role인지 확인합니다.
>
> 다른 Account의 성공 결과나 다른 Project의 Artifact를 현재 사용자의 성공 증거로 사용하지 않습니다.

## 8.3 원본 Pull 출력을 성공 증거로 사용하지 않는다

> 원본 Guide의 정상 Pull 예시에는 명령의 Project·Tag와 중간 출력 및 `docker image ls`의 Tag가 서로 이어지지 않는 부분이 있습니다.
>
> **그래서**, 해당 출력은 Pull 구조를 읽는 참고자료로만 사용하고 실제 Xi'an 성공 증적으로 단정하지 않습니다.
>
> 실제 Pull 완료는 자신이 실행한 같은 전체 Image 주소를 기준으로 확인합니다.

```text
요청한 FQDN·Project·Repository·Tag 일치
→ Pull 완료
→ 반환된 Digest 확인
→ 로컬 Image의 Repository와 Tag 확인
```

> Pull이 성공하면 Image를 읽는 경로는 확인됐습니다.
>
> **하지만**, 같은 Account가 Harbor에 Image를 쓸 수 있다는 뜻은 아닙니다.

# 9. Pull은 되지만 Image Push가 실패한다

> 다섯 번째 사용자는 Harbor Image를 Pull할 수 있지만 자신의 Image를 Push할 수 없다고 말합니다.
>
> Pull은 Harbor에서 Image를 읽는 작업이고 Push는 Harbor에 Image를 쓰는 작업입니다. 읽기가 성공해도 쓰기 권한과 저장 조건은 별도로 확인해야 합니다.

## 9.1 Push 전에 로컬 Image와 대상 주소를 연결한다

> Push할 정확한 Source Image가 사용자 Host에 실제로 존재해야 합니다. 원본 Guide의 Source는 `nginx:v1.0`입니다.

```console
sudo docker image ls nginx
```

> 결과에서 Repository가 `nginx`, Tag가 `v1.0`인 행과 해당 Image ID를 확인합니다. 이 Source가 없으면 Harbor 권한을 보기 전에 로컬 Image 단계에서 멈춥니다.
>
> Source Image가 있으면 Harbor의 어느 Project와 Repository에 어떤 Tag로 올릴지 전체 대상 주소를 붙입니다. 이 작업이 `docker tag`입니다.

원본 Guide의 명령 예시:

```console
sudo docker tag nginx:v1.0 \
  xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

```text
Source: nginx:v1.0
Target: xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

> 이 예시는 Source의 `v1.0`을 Target의 `1.14.2`로 연결합니다. 실제 작업에서는 이 Version 매핑이 승인된 의도인지 먼저 확인하며, 임의로 다른 Tag 이름을 붙이지 않습니다.
>
> Tag는 로컬 Image에 Harbor 대상 이름을 추가하는 작업입니다.
>
> **하지만**, Tag를 만들었다고 Harbor에 Image가 올라간 것은 아닙니다. Source와 Target이 같은 Image ID를 가리키는지 확인한 뒤 Target 전체 주소로 Push해야 합니다.

## 9.2 대상 Project에 쓸 수 있는지 확인한다

> Target 주소가 맞다면 현재 Docker Login Account와 대상 Project 권한을 확인합니다.
>
> 원본 Guide 기준으로 Image 읽기와 쓰기가 가능한 Role은 `Developer`, `ProjectAdmin`입니다.
>
> **하지만**, Role 이름만 보고 임의로 권한을 올리지 않습니다. 승인된 사용자가 맞는지, Target Project가 맞는지, 실제 업무에 필요한 Role인지 확인한 뒤 Project 운영 절차를 따릅니다.

## 9.3 denied 오류를 확인한다

```console
sudo docker push xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

대표 오류:

```text
denied: requested access to the resource is denied
```

> 이 오류가 나오면 먼저 실제 Push Target이 승인된 Project와 Repository인지 확인합니다.
>
> Target이 맞다면 현재 Login Account가 그 Project의 Member인지, Push가 가능한 Role인지 확인합니다. 로컬 Source Image와 Target Tag가 잘못됐다면 권한 변경으로 해결하지 않습니다.

## 9.4 Push 명령 종료와 실제 게시 완료를 구분한다

> 원본 Guide의 Push 예시에는 Push 명령의 Tag와 마지막 Digest 출력의 Tag가 서로 일치하지 않는 부분이 있습니다.
>
> 따라서 그 출력은 실제 성공 증거로 사용하지 않습니다.
>
> 실제 완료는 사용자가 의도한 Target과 Harbor 화면을 같은 값으로 대조합니다.

```text
Push한 FQDN·Project·Repository·Tag
=
Harbor Repository의 Artifact·Tag·Digest
```

> 이 값이 일치해야 올바른 Image가 올바른 위치에 게시됐다고 판단할 수 있습니다.

# 10. 실제 장애 요청을 하나의 흐름으로 연결한다

> 실제 사용자가 `Harbor가 안 됩니다`라고 요청했다고 하겠습니다.
>
> 먼저 무엇을 하려 했는지 확인합니다. Web 화면인지, Docker Login인지, Pull인지, Push인지에 따라 확인을 시작할 위치가 달라집니다.
>
> 그다음 현재 사용자 Host, Harbor FQDN, Account, Project, Repository와 Tag, 발생 시각과 오류 원문을 같은 대상으로 고정합니다.
>
> **그래서**, 실제 초동 확인은 다음 이야기로 이어집니다.

```text
사용자가 하려던 작업 확인
→ 같은 대상과 오류 원문 고정
→ 정상 경로와 비교
→ 마지막으로 성공한 연결 확인
→ 처음 실패한 연결 확인
→ 결과에 따라 다음 확인 선택
→ 승인된 조치 또는 담당 영역으로 전달
→ 같은 사용자 경로로 재검증
```

> 다른 담당 영역으로 전달할 때는 `Harbor가 안 됩니다`라고만 쓰지 않습니다.
>
> 예를 들어 Web은 열리고 Docker Login에서 x509가 발생했다면 `브라우저의 Harbor HTTPS 접근은 가능하지만 같은 Host의 Docker Login에서 x509가 발생했으며 승인된 CA의 trust 적용 상태를 확인해야 한다`고 전달합니다.
>
> 확인한 사실과 아직 확인하지 않은 원인을 구분하고 Password, Docker Credential과 Private Key는 전달하지 않습니다.

# 11. 오류가 사라진 것과 복구 완료는 다르다

> 원인을 추정하거나 설정을 수정했다고 장애가 완료된 것은 아닙니다.
>
> 사용자가 실패했던 같은 대상과 같은 작업으로 실제 결과를 다시 확인해야 합니다.

## 11.1 Web 장애

> 같은 사용자 Host에서 승인된 Harbor FQDN으로 Web 화면에 도달하는지 확인합니다.

## 11.2 Docker x509

> Certificate 검증을 생략하지 않은 Docker Login이 `Login Succeeded`로 끝나는지 확인합니다.

## 11.3 Login 장애

> 같은 승인 Account로 Docker Login이 성공하는지 확인합니다. Login 성공만으로 특정 Project 권한까지 완료 처리하지 않습니다.

## 11.4 Pull 장애

> 사용자가 실패했던 같은 Project, Repository와 Tag로 Pull하고 Digest와 로컬 Image를 확인합니다.

## 11.5 Push 장애

> 승인된 같은 Target으로 Push한 뒤 Harbor Repository에서 Artifact, Tag와 Digest가 일치하는지 확인합니다.

> **결국**, 오류 문구가 보이지 않는 것이 아니라 사용자가 원래 하려던 Image 작업이 실제로 완료돼야 복구입니다.

---

# 12. 마무리 — 오류표가 아니라 이야기로 다시 말한다

> 오늘 Harbor 장애에서 가장 중요한 것은 `x509는 CA`, `denied는 권한`처럼 단어와 답을 짝으로 외우는 것이 아닙니다.
>
> 사용자는 Harbor에서 Image를 가져오거나 올리려고 합니다. 그러려면 먼저 FQDN을 통해 Harbor 주소를 찾고 Network와 TCP 443을 통과해야 합니다.
>
> HTTPS로 도달한 뒤에는 브라우저와 Docker daemon이 각각 Harbor Certificate를 신뢰해야 합니다. Docker는 Registry API를 통해 Harbor의 Image 기능과 통신하고 Account 인증을 수행합니다.
>
> **하지만**, Login 성공은 모든 Private Project 권한을 의미하지 않습니다. 대상 Project의 Member와 Role, 정확한 Repository와 Tag가 함께 맞아야 Pull과 Push가 동작합니다.
>
> Pull이나 Push가 끝난 뒤에는 명령의 마지막 줄만 보지 않고 로컬 Image 또는 Harbor의 Artifact, Tag와 Digest를 확인합니다.
>
> **그래서**, 장애가 발생하면 비밀번호 변경이나 Docker 재시작부터 하지 않습니다. 사용자가 하려던 작업을 확인하고 정상 경로 중 마지막 성공과 첫 실패를 찾은 뒤, 그 결과에 맞는 확인과 승인된 조치를 선택합니다.
>
> **결국**, `FQDN과 Network → HTTPS 신뢰 → Registry API → Account 인증 → Project 권한 → Repository와 Tag → Pull·Push → Artifact와 Digest`의 전체 경로를 이해하고 처음 끊긴 연결부터 확인해야 합니다.

# 13. 마지막 확인 질문

기술 이름과 오류 답을 외웠는지 묻지 않고, 정상 경로와 문제의 이유를 설명할 수 있는지 순서대로 확인한다.

1. 사용자는 Harbor에서 Container Image로 어떤 두 가지 작업을 하는가?
2. `Harbor가 안 됩니다`라는 말만으로 원인을 정할 수 없는 이유는 무엇인가?
3. 브라우저와 Docker daemon은 Harbor를 사용할 때 어떤 역할 차이가 있는가?
4. Xi'an Harbor의 FQDN을 사용하면 사용자 Host의 요청은 어떤 경로를 지나 Harbor에 도달하는가?
5. Harbor Web 화면이 열린다고 Docker Login까지 정상이라고 확정할 수 없는 이유는 무엇인가?
6. 인증정보 없이 Registry `/v2/`가 `401`을 반환할 때 무엇을 확인할 수 있고 무엇은 아직 확인할 수 없는가?
7. Docker Login 성공과 특정 Private Project의 Pull·Push 권한은 무엇이 다른가?
8. Image 주소에서 Registry, Project, Repository와 Tag는 각각 어디에 해당하는가?
9. `manifest unknown`이 발생했을 때 Password보다 먼저 무엇을 확인해야 하는가?
10. `pull access denied`와 `repository does not exist`가 함께 보일 때 오류 문자열만으로 원인을 확정하면 안 되는 이유는 무엇인가?
