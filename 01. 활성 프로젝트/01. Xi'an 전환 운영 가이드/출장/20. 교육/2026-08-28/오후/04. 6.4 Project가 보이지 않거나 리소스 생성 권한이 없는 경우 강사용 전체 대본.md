# 6.4 Project가 보이지 않거나 리소스 생성 권한이 없는 경우 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 **수강생이 KubeSphere Workspace, Project와 Kubernetes RBAC을 거의 모른다는 전제**로 작성했다. 오전 교육 내용을 기억한다고 가정하지 않는다. `Project가 안 보인다`와 `Project는 보이지만 Create가 없다`를 같은 권한 장애로 설명하지 않는다. 먼저 Project 존재, Workspace Member, Project Member와 Project Role의 역할을 쉬운 말로 연결하고, 신청 Permission과 현재 Role을 증거로 비교한다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
사용자가 어느 공간에서 어떤 작업을 하려는지 먼저 말한다
→ 공간이 존재하고 사용자를 연결하고 역할을 주는 과정을 쉬운 말로 설명한다
→ Workspace·Project·Namespace·Member·Role·RBAC이라는 이름을 붙인다
→ Xi'an 신청 Permission과 Role 기준을 보여준다
→ 원본 Guide의 Project 존재·멤버십·Role 확인으로 들어간다
→ 안 보이는 문제와 생성할 수 없는 문제의 첫 단절을 구분한다
→ 같은 사용자 재로그인과 승인된 작업으로 복구를 확인한다
```

## 0-1. 오늘 전체 한 줄

```text
사용자는 KubeSphere에서 자신의 Application 공간을 사용하려 한다
→ 대상 Cluster에 Project·Namespace가 존재해야 한다
→ 상위 Workspace의 Member여야 한다
→ 대상 Project의 Member여야 한다
→ 신청 Permission에 맞는 Project Role이 있어야 한다
→ Role이 허용한 조회·생성·수정 작업을 수행한다
→ 실패하면 존재·Workspace·Project·Role 중 처음 끊긴 곳을 찾는다
```

---

# 1. 시작 — Project가 안 보인다는 말부터 나눈다

> 오늘은 KubeSphere에 Login했지만 대상 Project가 보이지 않거나, Project는 보이지만 Deployment, PVC와 Secret을 만들 수 없는 경우를 보겠습니다.
>
> 두 증상은 겉으로는 모두 `권한이 없습니다`처럼 보일 수 있습니다.
>
> **하지만**, Project 자체가 만들어지지 않은 경우, Workspace에만 사용자가 없는 경우, Project Member가 빠진 경우, 조회 전용 Role이 정상 적용된 경우는 서로 다른 상태입니다.

## 1.1 사용자가 하려는 일

> 여러 Team이 같은 Cluster를 사용하면 Application Resource가 섞이지 않도록 작업 공간을 나눠야 합니다.
>
> KubeSphere에서는 상위 관리 범위를 **Workspace**, 실제 Application Resource를 다루는 공간을 **Project**라고 합니다.
>
> KubeSphere Project는 Kubernetes의 **Namespace**와 같습니다.

```text
Workspace
→ 여러 Project를 묶는 상위 관리 범위

Project
= Kubernetes Namespace
→ Deployment·Pod·PVC·Secret 같은 Resource 작업 범위
```

## 1.2 공간이 있어도 사용자가 자동으로 들어가는 것은 아니다

> Workspace와 Project가 존재해도 모든 사용자가 자동으로 볼 수 있는 것은 아닙니다.
>
> 사용자를 Workspace Member로 연결하고, 다시 대상 Project Member로 연결해야 합니다.

```text
사용자 Account
→ Workspace Member
→ Project Member
```

> Workspace가 보인다는 사실과 그 안의 모든 Project가 보인다는 사실은 다릅니다.

## 1.3 Member와 Role은 다르다

> **Member**는 사용자가 그 공간에 연결돼 있는지를 나타냅니다.
>
> **Role**은 연결된 사용자가 무엇을 할 수 있는지를 나타냅니다.

```text
Member 없음
→ 공간을 보거나 들어갈 연결이 없음

Member 있음 + viewer
→ 조회 가능, 생성·수정 불가

Member 있음 + operator
→ 승인된 Resource 생성·수정 가능
```

> 그래서 사용자가 Project를 볼 수 있다고 생성 권한까지 있는 것은 아닙니다.

# 2. 정상일 때 어떤 연결이 이어지는가

## 2.1 신청 내용이 기준이 된다

> 운영팀은 화면의 현재 Role 이름만 보고 권한을 결정하지 않습니다.
>
> 먼저 승인된 신청서에서 대상 환경, Project 이름, 사용자 Account와 Permission을 확인합니다.

```text
대상 PRD 또는 DEV Cluster
Project Name
사용자 Account
신청 Permission
승인된 Role 정책
```

> 사용자가 생성 메뉴가 필요하다고 말해도 승인된 Permission이 `User`라면 임의로 Role을 올리지 않습니다.

## 2.2 대상 Cluster에 Project·Namespace가 존재해야 한다

> Project가 화면에 보이기 전에 대상 Member Cluster에 Kubernetes Namespace로 존재해야 합니다.

```text
KubeSphere Project
=
Kubernetes Namespace
```

> 다른 Cluster의 같은 이름 Namespace를 확인하면 현재 사용자의 Project 존재 증거가 되지 않습니다. 먼저 대상 Cluster Context를 고정합니다.

## 2.3 Workspace Member가 상위 공간을 연결한다

> 사용자는 상위 Workspace의 Member로 등록돼야 Workspace를 보고 그 아래 Project 사용 흐름으로 들어갈 수 있습니다.

원본 Guide의 화면 경로:

```text
Workbench
→ Workspaces
→ 대상 Workspace
→ Workspace Settings
→ Workspace Members
```

> 원본 사례는 Workspace 단계에서 사용자를 `viewer` 성격의 Role로 초대하고 실제 Workload 권한은 Project Role에서 별도로 부여합니다.

## 2.4 Project Member가 실제 Project를 연결한다

원본 Guide의 화면 경로:

```text
Projects
→ 대상 Project
→ Project Settings
→ Project Members
→ Invite
```

> Workspace Member 등록만 하고 Project Member 등록을 빠뜨리면 Workspace는 보이지만 대상 Project는 보이지 않을 수 있습니다.

## 2.5 Project Role이 작업 범위를 정한다

Xi'an 교육 기준의 기본 매핑:

| 신청 Permission | 기본 Project Role | 의미 |
|---|---|---|
| `User` | `project-viewer` | Project Resource 조회 |
| `Admin` | `project-operator` | Workload·PVC·Secret 등 승인 Resource 운영 |
| 별도 운영 승인 | `project-admin` | Project Member와 Role 관리 범위 |

> `project-operator`는 Application Resource를 생성·수정할 수 있지만 Project Member를 관리하는 Role은 아닙니다.
>
> `project-admin`은 이름이 더 높아 보인다는 이유로 자동 부여하지 않고 별도 운영 정책과 승인을 따릅니다.

## 2.6 정상 경로를 한 줄로 연결한다

```text
승인 신청 확인
→ 대상 Cluster Context
→ Project·Namespace 존재
→ Workspace Member
→ Project Member
→ 신청 Permission과 Project Role 일치
→ 사용자 재로그인
→ Project 표시
→ 승인된 조회·생성 작업 성공
```

# 3. Workspace가 보임, Project가 보임과 생성 권한은 다르다

```text
KubeSphere Login 성공
≠ 대상 Workspace Member

Workspace 표시
≠ 대상 Project Member

Project 표시
≠ Create·Edit 권한

project-operator
≠ Project Member 관리 권한

Create 실패
≠ 항상 RBAC 문제
```

> 마지막 구분도 중요합니다. Role이 맞아도 Quota나 Resource 정책 때문에 생성이 거부될 수 있습니다. 실제 오류 원문을 보지 않고 모든 생성 실패를 Role 문제로 판단하지 않습니다.

---

# 4. 장애를 보기 전에 같은 대상과 승인값을 고정한다

```text
대상 PRD 또는 DEV Cluster
Workspace 이름
Project·Namespace 이름
사용자 Account 문자열
신청 Permission
현재 Workspace Member 여부와 Role
현재 Project Member 여부와 Role
사용자가 보지 못하는 화면 또는 실패한 작업
오류 원문과 발생 시각
```

> Account의 점, 하이픈과 철자까지 신청서와 실제 사용자를 같은 값으로 비교합니다. 비슷한 다른 Account를 추가하면 현재 사용자 문제는 해결되지 않습니다.

> 원본 Guide의 `hello-kubesphere-dev`, `dj2.kim`, `dsjl32783.id`는 사례 값입니다. 현재 운영 요청의 승인값으로 다시 확인하지 않고 그대로 사용하지 않습니다.

> `kubectl` 확인과 Member·Role 변경은 승인된 운영자만 수행합니다. 교육 중에는 현재 Project와 Member를 읽기 전용으로 확인하고 `Invite`, `Edit Role`, `OK`와 Resource `Create`를 실행하지 않습니다.

---

# 5. Project 자체가 존재하는지 먼저 확인한다

> 첫 번째 사용자는 Login했지만 대상 Project가 보이지 않는다고 말합니다.
>
> Member와 Role을 바꾸기 전에 Project 자체가 대상 Cluster에 존재하는지 확인합니다.

## 5.1 대상 Cluster Context를 확인한다

```console
kubectl config current-context
```

> PRD와 DEV를 혼용하면 같은 이름의 Project를 잘못 판단할 수 있습니다.

## 5.2 Namespace 존재를 확인한다

원본 Guide의 사례:

```console
kubectl get namespace hello-kubesphere-dev
```

Project가 존재하는 경우:

```text
NAME                   STATUS
hello-kubesphere-dev   Active
```

> `Active`라면 Project 생성 단계는 통과했습니다. 이제 Workspace와 Project 멤버십을 확인합니다.

Project가 없는 경우:

```text
Error from server (NotFound): namespaces "hello-kubesphere-dev" not found
```

> `NotFound`라면 Member Role을 수정하기 전에 Project 이름과 생성 완료 여부를 확인합니다.
>
> 신청서의 이름이 맞지만 Namespace가 없다면 원본 Guide가 연결한 `Creating Workspaces&projects` 절차로 돌아갑니다. 장애 대응 중 임의 이름으로 Project를 새로 만들지 않습니다.

---

# 6. Namespace는 Active인데 사용자 화면에 Project가 없다

> Project가 존재한다면 다음은 사용자를 공간에 연결하는 단계입니다.

## 6.1 Workspace Member를 확인한다

```text
Workbench
→ Workspaces
→ 대상 Workspace
→ Workspace Settings
→ Workspace Members
```

> 신청서의 실제 Account가 목록에 있는지 확인합니다.
>
> Account가 없으면 승인된 요청과 운영 절차에 따라 초대합니다.

원본 Guide의 화면 예시:

```text
Workspace Settings
→ Workspace Members
→ Invite Member
→ 승인된 Account 선택
→ Role: viewer
→ OK
```

> 이 `viewer`는 상위 Workspace를 볼 수 있도록 연결하는 원본 사례의 Role입니다. 이 단계에서 Project Workload 운영 권한까지 부여됐다고 판단하지 않습니다.

## 6.2 Project Member를 확인한다

```text
Projects
→ 대상 Project
→ Project Settings
→ Project Members
```

> Workspace에 사용자가 있어도 Project Members에 없으면 대상 Project가 보이지 않을 수 있습니다.

> **따라서**, Workspace 초대 완료를 전체 권한 작업 완료로 처리하지 않습니다.

## 6.3 원본 사례의 사용자 매핑을 읽는다

원본 Guide의 예시:

```text
dj2.kim        Admin → project-operator
dsjl32783.id   User  → project-viewer
```

> 이 표는 신청 Permission을 Project Role로 연결하는 방법을 보여주는 사례입니다.
>
> 실제 장애에서는 현재 신청서의 Account와 Permission을 다시 확인합니다. 이름이 비슷하거나 역할 의미가 비슷하다는 이유로 원본 Account와 Role을 그대로 적용하지 않습니다.

## 6.4 사용자 재로그인으로 표시를 확인한다

> Workspace와 Project Member를 승인값에 맞게 수정했다면 사용자가 KubeSphere에서 로그아웃했다가 다시 Login합니다.
>
> 같은 Account로 대상 Workspace와 Project가 표시되는지 확인합니다.

> 다른 관리자 화면에서 Member가 보인다는 사실만으로 사용자 화면의 복구를 완료하지 않습니다.

---

# 7. Project는 보이지만 Create·Edit 메뉴가 없다

> 두 번째 사용자는 Project에 들어갈 수 있고 기존 Workload, PVC와 Secret도 볼 수 있습니다.
>
> **하지만**, `Create`, `Edit`, `Delete` 메뉴가 없습니다.
>
> 이 상태는 Project 존재와 멤버십이 통과했다는 뜻입니다. 이제 현재 Role이 신청 Permission과 일치하는지 봅니다.

## 7.1 User 신청자와 project-viewer

```text
신청 Permission = User
Project Role = project-viewer

Workload 조회 = 가능
PVC 조회 = 가능
Secret 조회 = 가능
Create·Edit·Delete = 불가
```

> 이 경우 생성 메뉴가 없는 것은 정상입니다.
>
> 장애로 판단해 `project-operator`나 `project-admin`으로 올리지 않습니다. 생성 권한이 필요하면 Permission 변경과 승인부터 진행합니다.

## 7.2 Admin 신청자인데 project-viewer인 경우

```text
신청 Permission = Admin
Project Role = project-viewer
→ 승인 내용과 현재 Role 불일치 가능
```

> 신청서와 현재 정책에서 `Admin → project-operator`가 승인된 경우에만 Role 수정을 검토합니다.

원본 Guide의 화면 경로:

```text
Project Settings
→ Project Members
→ 대상 Account
→ Edit Role
→ project-operator
→ OK
```

> Role을 수정하기 전에 대상 Account, Project와 승인 Permission을 다시 읽습니다. 다른 사용자의 Role을 바꾸지 않습니다.

## 7.3 project-operator의 정상 범위

원본 Guide 기준으로 다음 영역의 승인 Resource를 생성·수정할 수 있습니다.

```text
Application Workloads → Workloads
Storage → Volumes
Configuration → Secrets
Configuration → ConfigMaps
```

> **하지만**, `project-operator`에게 Project Member 초대 메뉴가 보이지 않는 것은 정상입니다.
>
> Member 관리를 이유로 `project-admin`을 부여하려면 별도 운영 정책과 승인이 필요합니다.

---

# 8. Create 실패를 전부 RBAC으로 판단하지 않는다

> Role이 `project-operator`인데 Resource 생성이 실패하면 실제 오류 원문을 확인합니다.

```text
Forbidden·권한 거부
→ 현재 Role과 RBAC 확인

Quota 초과
→ 승인 Quota와 현재 사용량 확인

입력값·정책 오류
→ Resource Spec과 적용 정책 확인
```

> Quota 오류에 Role을 올려도 해결되지 않습니다.
>
> 반대로 RBAC 오류를 Quota 부족으로 처리해도 해결되지 않습니다.
>
> `Create가 실패했다`는 결과보다 API와 UI의 실제 오류가 다음 확인을 결정합니다.

---

# 9. Role 수정 후 실제 사용자 경로로 검증한다

> 승인된 Role 수정 뒤에는 관리자 화면의 Role 이름만 확인하지 않습니다.

## 9.1 같은 사용자가 다시 Login한다

```text
대상 Account 로그아웃
→ 다시 Login
→ 대상 Workspace 진입
→ 대상 Project 진입
```

## 9.2 Role별 기대 동작을 확인한다

`project-viewer`:

```text
Workload·PVC·Secret 조회 가능
Create·Edit·Delete 불가
```

`project-operator`:

```text
승인된 Workload·PVC·Secret 조회 가능
승인된 Resource 생성·수정 가능
Project Member 관리 불가
```

> viewer에게 Create 메뉴가 없어야 하는 것도 완료 기준입니다. 모든 사용자에게 같은 메뉴가 보이는 것이 정상은 아닙니다.

## 9.3 작은 Resource 생성 검증은 승인된 공간에서만 수행한다

> 원본 Guide는 `Admin → project-operator` 수정 후 작은 Test Deployment를 생성해 실제 권한을 확인할 수 있다고 설명합니다.
>
> 이 검증은 교육 전용 또는 승인된 Project, 이름 충돌이 없는 Test Resource와 정리 계획이 있을 때만 수행합니다. 운영 Application이 있는 Project에 임의 Resource를 만들지 않습니다.

원본 Guide의 기대 결과 구조:

```text
Deployment READY = 1/1
Pod STATUS = Running
```

> 생성이 성공하면 Test Resource를 승인된 정리 절차에 따라 제거합니다.

## 9.4 과도한 권한이 없는지도 확인한다

> 복구는 필요한 작업이 되는 것뿐 아니라 불필요한 권한이 생기지 않는 것도 포함합니다.

```text
viewer는 조회만 가능
operator는 승인 Resource 운영 가능
operator는 Member 관리 불가
불필요한 project-admin 없음
```

# 10. 실제 장애 요청을 하나의 흐름으로 연결한다

> 사용자가 `Login은 되는데 hello-kubesphere-dev가 안 보입니다`라고 요청했다고 하겠습니다.
>
> 먼저 대상 DEV Cluster, Workspace, Project, Account와 신청 Permission을 고정합니다.
>
> **첫 번째 분기**는 대상 Cluster에 Namespace가 존재하는지입니다.
>
> `NotFound`라면 Project 생성 미완료 또는 이름 불일치입니다. 멤버십을 바꾸지 않고 생성 절차로 돌아갑니다.
>
> `Active`라면 Project는 존재합니다. Workspace Members와 Project Members에서 정확한 Account를 확인합니다.
>
> **두 번째 분기**는 Workspace는 보이지만 Project만 보이지 않는 경우입니다.
>
> Project Member 등록이 빠졌는지 확인하고 승인된 Role로 연결합니다. 사용자 재로그인 뒤 같은 Project가 표시되는지 확인합니다.
>
> **세 번째 분기**는 Project는 보이지만 Create 메뉴가 없는 경우입니다.
>
> 신청 Permission이 `User`이고 Role이 `project-viewer`라면 정상입니다. 권한을 올리지 않습니다.
>
> 신청 Permission이 `Admin`인데 `project-viewer`라면 승인된 `project-operator` 매핑과 현재 Role을 대조합니다.
>
> Role 수정 뒤에는 같은 사용자로 다시 Login해 Project 표시와 Role별 기대 동작을 확인합니다. 필요하면 승인된 작은 Resource로 실제 생성 권한을 확인하고 정리합니다.

# 11. 오류가 사라진 것과 복구 완료는 다르다

## 11.1 Project가 보이지 않았던 경우

> 같은 사용자 Account로 재로그인한 뒤 대상 Workspace와 Project가 실제로 표시되는지 확인합니다.

## 11.2 viewer 사용자

> 승인 Resource가 조회되고 Create·Edit·Delete가 허용되지 않는지 확인합니다.

## 11.3 operator 사용자

> 승인된 Resource 조회와 생성이 가능하고 Project Member 관리 권한은 없는지 확인합니다.

## 11.4 전체 완료 기준

```text
대상 Cluster에 Project·Namespace 존재
+ Workspace Member 등록
+ Project Member 등록
+ Role이 신청 Permission과 일치
+ 사용자 재로그인 후 기대 화면 표시
+ Role별 승인 작업 성공
+ 불필요한 project-admin 없음
```

# 12. 마무리 — 처음부터 이야기로 다시 말한다

> 사용자는 KubeSphere에서 자신의 Application을 운영할 Project를 사용하려 합니다.
>
> 먼저 대상 Cluster에 Project, 즉 Kubernetes Namespace가 실제로 존재해야 합니다.
>
> 그다음 사용자가 상위 Workspace Member이고 대상 Project Member여야 합니다.
>
> **하지만**, Member 등록만으로 모든 작업이 허용되는 것은 아닙니다. Project Role이 신청 Permission에 맞아야 합니다.
>
> `project-viewer`는 조회 역할이므로 Create 메뉴가 없는 것이 정상이고, `project-operator`는 승인된 Resource를 운영하지만 Member를 관리하지는 않습니다. `project-admin`은 별도 승인 없이 부여하지 않습니다.
>
> **따라서**, `Project·Namespace 존재 → Workspace Member → Project Member → 신청 Permission과 Role → 사용자 재로그인 → 실제 허용 작업` 순서에서 처음 끊긴 곳을 확인합니다.
>
> 보이지 않는 문제와 생성할 수 없는 문제를 구분하고, 정상적인 최소 권한을 장애로 오해하지 않는 것이 6.4의 핵심입니다.
