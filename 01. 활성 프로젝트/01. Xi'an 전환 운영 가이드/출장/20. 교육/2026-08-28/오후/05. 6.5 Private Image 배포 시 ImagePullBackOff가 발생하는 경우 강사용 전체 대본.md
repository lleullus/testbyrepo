# 6.5 Private Image 배포 시 ImagePullBackOff가 발생하는 경우 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 **수강생이 Container Image, Harbor와 Kubernetes Secret을 거의 모른다는 전제**로 작성했다. `ImagePullBackOff`라는 상태부터 원인으로 외우게 하지 않는다. 사용자가 Private Image로 Pod를 실행하려던 일을 먼저 설명하고, Worker Node가 Image를 가져오는 경로를 이해시킨 뒤 Pod Event의 실제 오류로 첫 단절을 찾는다.

> [!warning] 교육 중 변경 경계
> 본문 교육은 원본 Guide의 Console 출력으로 상세 분기를 진행하며, 잘못된 Tag·Secret 생성, Deployment 저장, Rollout 변경과 Harbor Role 변경을 실행하지 않는다. 단, 하단 `14. 승인된 교육용 간단 실습`은 **별도로 승인된 교육용 Project에서만** 수행하는 격리 실습이다. 이 실습에서는 존재하지 않는 교육용 Tag 하나만 실패 변수로 사용하며 Registry Secret·Harbor Role·CA·Network는 변경하지 않는다. Registry Password와 Secret Data 원문은 화면·명령·교육자료·장애 기록에 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
사용자가 하려던 일을 먼저 말한다
→ Image와 Private Registry의 역할을 쉽게 설명한다
→ 실제 Pull Client가 Worker Node임을 설명한다
→ Secret과 imagePullSecrets라는 이름을 붙인다
→ Xi'an 사례의 전체 Image 주소를 읽는다
→ Pod Event의 실제 오류 문장을 먼저 확인한다
→ Image·Secret·연결·권한 중 첫 단절을 찾는다
→ 수정된 경로를 실제 Pod Event와 Ready 상태로 검증한다
```

## 0-1. 오늘 전체 한 줄

```text
Deployment가 Private Harbor Image를 지정한다
→ Pod가 Worker Node에 배치된다
→ Worker가 같은 Namespace의 Registry Secret을 사용한다
→ Harbor가 Image 주소와 계정의 Pull 권한을 확인한다
→ Worker가 Image를 Pull한다
→ Container가 생성되고 시작된다
→ 실패하면 Pod Event에서 처음 끊긴 연결을 찾는다
```

# 1. 시작 — `ImagePullBackOff`는 답이 아니다

> 오늘은 KubeSphere에서 Private Harbor Image로 Deployment를 만들었는데 Pod가 `ErrImagePull` 또는 `ImagePullBackOff`에 머무는 경우를 보겠습니다.
>
> `ImagePullBackOff`는 원인 이름이 아닙니다. Kubernetes가 Image Pull에 실패했고, 같은 실패를 너무 빠르게 반복하지 않도록 잠시 기다렸다가 다시 시도하는 상태입니다.
>
> 그래서 상태 이름만 보고 Secret을 다시 만들지 않습니다. 실제 원인은 Pod Event의 `Failed to pull image` 뒤에 있는 문장에서 찾습니다.

## 1.1 사용자가 하려던 일

> Pod에서 Application을 실행하려면 프로그램과 실행환경을 묶은 **Container Image**가 필요합니다.
>
> 여러 Worker가 같은 Image를 가져올 수 있도록 Image를 중앙에 보관하는 곳이 **Registry**이고, Xi'an에서는 **Harbor**가 이 역할을 담당합니다.
>
> Harbor의 Private Project에 있는 Image는 정확한 주소뿐 아니라 허용된 계정의 인증정보가 있어야 가져올 수 있습니다.

## 1.2 Image를 실제로 가져오는 Client

> 사용자가 KubeSphere 화면에서 Deployment를 저장하지만 Image를 가져오는 것은 사용자 브라우저가 아닙니다.
>
> Pod가 배치된 Worker Node의 kubelet과 Container Runtime이 Harbor에 요청합니다.

```text
사용자
→ KubeSphere에서 Deployment 정의

Worker Node
→ Harbor에 Image Pull 요청
→ Container 생성·시작
```

> 따라서 사용자 PC의 `docker pull` 성공과 Pod의 Image Pull 성공은 같은 증거가 아닙니다.

## 1.3 Kubernetes가 Private Image 인증정보를 연결하는 방법

> Worker가 사용할 Registry 인증정보를 Kubernetes **Image Registry Secret**에 보관합니다.
>
> 하지만 Secret은 존재하기만 해서는 사용되지 않습니다. Deployment의 Pod Template이 `imagePullSecrets`로 정확한 Secret 이름을 선택해야 합니다.

```text
Secret 존재
≠ 현재 Deployment가 Secret 사용

같은 Namespace의 Secret
+ imagePullSecrets 이름 연결
→ Pod의 Image Pull 인증에 사용
```

# 2. 정상 경로를 하나의 연결로 이해한다

```text
Deployment의 전체 Image 주소
→ Pod가 Worker Node에 배치
→ 같은 Namespace의 Registry Secret
→ Pod Template의 imagePullSecrets 연결
→ Secret Account의 Harbor Project Pull 권한
→ Harbor에서 Image Pull
→ Pulled·Created·Started
→ Pod Running·Ready
```

> 각 단계는 앞 단계의 성공만으로 자동 보장되지 않습니다.
>
> Image 주소가 정확해도 Secret 연결이 빠질 수 있고, Secret이 연결돼도 계정에 대상 Project의 Pull 권한이 없을 수 있습니다.

## 2.1 Image 주소는 네 부분으로 읽는다

```text
<Registry>/<Project>/<Repository>:<Tag>
```

원본 Xi'an 사례:

```text
xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

| 부분 | 원본 사례 값 | 의미 |
|---|---|---|
| Registry | `xa.dcr.dks.samsungds.net` | Harbor 주소 |
| Project | `dspaas-v1.22.10-a` | Harbor Image 영역 |
| Repository | `nginx` | Image Repository |
| Tag | `1.14.2` | 요청한 Image Version |

> 네 부분 중 하나라도 다르면 다른 Image를 요청합니다. 존재하지 않는 Tag는 Secret이나 Password를 바꿔도 생기지 않습니다.

# 3. 같은 장애 대상을 먼저 고정한다

```text
대상 Cluster
KubeSphere Project·Kubernetes Namespace
Deployment 이름
현재 Pod 이름
Pod가 배치된 Worker Node
발생 시각
Pod Event 원문
Deployment의 전체 Image 주소
Registry Secret 이름·Namespace·Type
imagePullSecrets 연결 이름
```

> Pod 이름, ReplicaSet Hash, Node, AGE와 Event 횟수는 실행할 때마다 달라질 수 있습니다. 원본 사례의 동적 값을 현재 장애에 그대로 사용하지 않습니다.

원본 사례값:

```text
Namespace   hello-kubesphere-dev
Deployment  nginx-test
Pod         nginx-test-6f7c8d9b6d-7k2pm
Node        xadkswkmd01 / 109.156.22.82
Secret      harbor-registry-secret
Secret Type kubernetes.io/dockerconfigjson
```

실제 장애에서는 현재 값을 변수로 고정합니다.

```bash
NS='actual-namespace'
DEPLOY='actual-deployment-name'
POD='actual-pod-name'
SECRET='actual-registry-secret-name'
```

# 4. 첫 번째 확인은 Pod Event다

## 4.1 상태와 배치 Node를 확인한다

```bash
kubectl -n "$NS" get pod "$POD" -o wide
```

> `STATUS=ImagePullBackOff`는 Pull 실패가 반복된다는 사실만 보여줍니다. Tag, Secret, 권한 중 무엇이 원인인지는 아직 알 수 없습니다.

## 4.2 같은 Pod의 Event를 읽는다

```bash
kubectl -n "$NS" describe pod "$POD"
```

> 다음 항목을 한 묶음으로 읽습니다.

```text
Pod와 Namespace
배치된 Worker Node
Container가 요청한 전체 Image 주소
Pulling과 Failed Message
실제 오류 문장
ErrImagePull·BackOff의 시각과 반복 횟수
```

원본 사례의 결합 오류:

```text
Failed to pull image "xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2":
pull access denied, repository does not exist or may require authorization
```

> 이 문장에는 Repository 부재와 인증 필요 가능성이 함께 들어 있습니다.
>
> 따라서 `denied` 한 단어만 보고 Harbor Role 문제로 확정하지 않습니다. 실제 Image 주소부터 Secret과 연결, 권한 순서로 대조합니다.

## 4.3 Event가 첫 분기를 결정한다

| Event 핵심 문구                 | 첫 확인                                            |
| --------------------------- | ----------------------------------------------- |
| `manifest unknown`          | Harbor의 Project·Repository·Tag 존재               |
| `pull access denied`        | Image 주소·Secret·imagePullSecrets·Harbor Pull 권한 |
| `repository does not exist` | Project·Repository 이름과 계정 접근 범위                 |

> 원본 6.5 Guide의 핵심 분기는 위 세 문구입니다.
>
> 실제 Event가 `x509`, DNS 또는 timeout이라면 Secret 문제로 억지로 맞추지 않고, Pod가 배치된 Worker와 Harbor 사이의 HTTPS·Network 경로 및 6.1 Guide로 전환합니다.

# 5. Deployment의 실제 Image 주소를 확인한다

```bash
kubectl -n "$NS" get deployment "$DEPLOY" -o yaml
```

확인 위치:

```yaml
spec:
  template:
    spec:
      containers:
        - image: xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

> Deployment YAML의 `image`와 Pod Event의 실제 Image 주소가 같은지 먼저 봅니다.
>
> 그다음 Registry, Project, Repository와 Tag를 분리해 Harbor의 실제 Project·Repository·Artifact에 대조합니다.

## 5.1 `manifest unknown`

원본 오류 사례:

```text
xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:not-exist
manifest unknown: manifest unknown
```

> 이 오류는 Harbor까지 Image 요청이 전달됐지만 요청한 Manifest를 찾지 못했다는 뜻입니다.
>
> Secret을 재생성하거나 Password를 바꾸기 전에 요청한 Project·Repository·Tag가 Harbor에 실제로 존재하는지 확인합니다.

원본 정상 Tag 사례:

```text
nginx:1.14.2
Digest: sha256:f5578142accc4a354c4759f960645f83328ca602a17083e82c873a070a7fd172
```

> 이 Tag와 Digest는 원본 사례의 참조값입니다. 현재 Deployment에서는 승인된 Image Version과 Harbor의 현재 Artifact를 다시 확인합니다.

---

# 6. 같은 Namespace의 Registry Secret을 확인한다

> KubeSphere Project는 이 사용 경로에서 Kubernetes Namespace에 대응합니다.
>
> Deployment가 있는 Namespace와 Registry Secret이 있는 Namespace가 같아야 합니다. 다른 Project에 같은 이름의 Secret이 있어도 현재 Pod는 사용할 수 없습니다.

```bash
kubectl -n "$NS" get secret "$SECRET"
kubectl -n "$NS" describe secret "$SECRET"
```

확인할 값:

```text
Name      = imagePullSecrets에서 참조할 이름
Namespace = Deployment와 같은 Namespace
Type      = kubernetes.io/dockerconfigjson
Data Key  = .dockerconfigjson 존재
```

> Secret의 이름, Namespace, Type과 Data Key 존재까지만 확인합니다.
>
> `.dockerconfigjson`을 출력하거나 Base64를 해제해 Registry Address, Account와 Password를 확인하지 않습니다.

## 6.1 Secret이 있어도 인증정보가 정상이라고 확정할 수 없다

> Secret 객체가 존재하고 Type이 맞아도 저장 당시의 Registry Address나 Credential이 현재 승인값과 다를 수 있습니다.
>
> 하지만 원문을 열어 확인하지 않습니다. Image 주소와 Secret 연결이 모두 맞는데 인증 거부가 계속될 때, 승인된 Account와 Credential로 Secret을 안전하게 다시 준비해야 하는지 판단합니다.

> 교육 중에는 Secret 생성·교체를 실행하지 않습니다.

---

# 7. Deployment가 그 Secret을 실제로 선택하는지 확인한다

같은 Deployment YAML에서 다음 위치를 봅니다.

```yaml
spec:
  template:
    spec:
      imagePullSecrets:
        - name: harbor-registry-secret
```

세 값을 대조합니다.

```text
Deployment Namespace
= Secret Namespace

imagePullSecrets.name
= 실제 Secret 이름

Deployment Image의 Registry
= Secret을 준비할 때 승인된 Harbor Registry
```

> Secret이 올바르게 존재해도 `imagePullSecrets`가 없거나 이름이 다르면 이 Pod Template은 해당 Secret을 사용하지 않습니다.
>
> KubeSphere UI에 Secret이 보였다는 사실만으로 완료하지 않고, 실제 Deployment YAML에 연결이 반영됐는지 확인합니다.

---

# 8. Image·Secret·연결이 맞으면 Harbor Pull 권한을 확인한다

> Image 경로, 같은 Namespace의 Secret과 Type, `imagePullSecrets` 이름 연결이 모두 맞는데 접근 거부가 계속되면 Secret을 준비할 때 승인된 Harbor Account와 대상 Project의 Pull 권한을 확인합니다.

```text
Harbor Login 성공
≠ 모든 Private Project Pull 가능

대상 Project Member
+ Pull 가능한 Role
→ 해당 Project의 Image Pull 가능
```

> 권한 오류로 추정해 일반 사용자를 임의로 ProjectAdmin으로 올리지 않습니다. 승인된 Role 정책에서 필요한 Pull 권한만 확인합니다.

## 8.1 같은 Account의 직접 Login·Pull이 증명하는 범위

원본 Guide의 확인 구조:

```console
sudo docker login xa.dcr.dks.samsungds.net
sudo docker pull xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

> Password는 대화형으로 입력하고 기록하지 않습니다.

```text
같은 Account로 Login 성공
+ 같은 전체 Image 주소 Pull 성공
→ 그 Client에서 Account 인증·Harbor Project·Image Pull 경로 통과
```

> 하지만 사용자 Host에서 성공한 직접 Pull은 Kubernetes Secret이 같은 Credential을 담고 있다는 증거나 Worker Node의 Pull 성공 증거가 아닙니다.
>
> 직접 Login 또는 Pull이 실패하면 6.1 Guide에서 Account 인증, Project·Repository·Tag와 Role을 구분합니다.

# 9. 결과를 보고 수정할 위치를 선택한다

```text
manifest unknown
→ 승인된 Project·Repository·Tag와 Deployment Image 주소 대조

같은 Namespace에 Secret 없음·Type 불일치
→ 승인된 Registry Account로 현재 Project의 Registry Secret 준비

imagePullSecrets 없음·이름 불일치
→ Deployment Pod Template의 Secret 연결 수정

Image·Secret·연결 정상 + denied
→ Harbor Account의 대상 Project Pull 권한 확인

직접 Account Pull 성공 + Pod만 denied
→ Secret Credential·연결과 실제 Pod Event를 다시 대조
```

> 이 표는 확인 결과가 가리키는 수정 위치입니다. 교육 중 실제 수정은 수행하지 않습니다.

## 9.1 먼저 하지 않을 조치

```text
Event를 보기 전에 Secret 반복 재생성
존재하지 않는 Tag를 인증 문제로 처리
Harbor Role을 근거 없이 ProjectAdmin으로 상향
Secret Data·Password 출력
실패 Pod 반복 삭제
```

> 첫 단절과 무관한 변경은 정상 영역을 바꾸고 실제 오류를 숨길 수 있습니다.

# 10. 수정 후에는 실제 Pull 경로를 다시 확인한다

> Deployment의 Image 또는 Pod Template이 바뀌면 새 ReplicaSet과 Pod가 생성될 수 있습니다.
>
> Secret만 갱신한 경우에는 그것만으로 새 ReplicaSet이 생긴다고 가정하지 않습니다. 기존 Pod의 재시도 또는 승인된 재기동 절차에서 실제 Pull 결과를 확인합니다.

## 10.1 Rollout이 발생한 경우

```bash
kubectl -n "$NS" rollout status deployment/"$DEPLOY"
kubectl -n "$NS" get pod -o wide
```

> `rollout status`는 실제로 Deployment Pod Template 변경과 Rollout이 발생한 경우에 확인합니다.

## 10.2 복구된 Pod의 Event를 확인한다

```bash
RECOVERED_POD='actual-recovered-pod-name'
kubectl -n "$NS" describe pod "$RECOVERED_POD"
```

원본 사례의 정상 Event 흐름:

```text
Scheduled
→ Pulling
→ Successfully pulled
→ Created
→ Started
```

> Worker에 같은 Image가 이미 있으면 `Pulled` Event가 기존 Image 사용을 나타낼 수도 있습니다. 중요한 것은 의도한 전체 Image 주소에 대한 새 Pull 실패가 없고 Container가 정상 생성·시작되는 것입니다.

## 10.3 최종 완료 기준

```text
Harbor에 승인된 Project·Repository·Tag 존재
+ Deployment의 전체 Image 주소 일치
+ 같은 Namespace에 올바른 Registry Secret 존재
+ Secret Type = kubernetes.io/dockerconfigjson
+ imagePullSecrets 이름 연결
+ 승인 Account의 대상 Project Pull 권한
+ 의도한 Image에 대한 Pull 실패 해소
+ Container Created·Started
+ Pod Running·Ready
```

> 기존 실패 Pod의 오래된 Event만 보고 완료하지 않습니다. 수정된 설정이 적용된 실제 Pod의 현재 상태와 Event로 판정합니다.

---

# 11. 실제 장애 요청을 하나의 이야기로 연결한다

> 사용자가 `Private Harbor Image로 배포했는데 ImagePullBackOff입니다`라고 요청했다고 하겠습니다.
>
> 먼저 대상 Cluster, Namespace, Deployment, 현재 Pod, Worker Node와 발생 시각을 고정합니다.
>
> 첫 확인은 Secret 화면이 아니라 Pod Event입니다. `ImagePullBackOff`라는 상태가 아니라 실제 `Failed to pull image` 문장과 전체 Image 주소를 읽습니다.
>
> `manifest unknown`이면 승인된 Project·Repository·Tag와 Deployment Image 주소를 먼저 대조합니다.
>
> 접근 거부 문구라면 같은 Namespace에 `kubernetes.io/dockerconfigjson` Type의 Secret이 있는지, Deployment가 `imagePullSecrets`로 정확한 이름을 선택하는지 확인합니다.
>
> Image·Secret·연결이 모두 맞는데 거부되면 승인된 Harbor Account가 대상 Project에서 Pull 가능한지 확인합니다.
>
> **하지만**, 사용자 Host의 직접 Pull 성공만으로 Pod 경로 전체가 정상이라고 판정하지 않습니다.
>
> 수정 후에는 실제 적용 대상 Pod에서 의도한 Image의 Pull 실패가 해소되고 Container가 Created·Started되며 Pod가 Running·Ready인지 확인합니다.

---

# 12. 마무리 — 하나의 연결만 기억한다

> Private Image로 Pod를 실행하려면 Deployment가 정확한 Harbor Image 주소를 지정해야 합니다.
>
> 같은 Namespace에는 Registry Secret이 있어야 하고, Deployment의 Pod Template이 `imagePullSecrets`로 그 Secret을 선택해야 합니다.
>
> Secret을 준비한 Account는 대상 Harbor Project의 Image를 Pull할 수 있어야 합니다.
>
> **결국**, `Pod Event → 전체 Image 주소 → 같은 Namespace의 Secret → imagePullSecrets 연결 → Harbor Pull 권한 → 실제 Pod의 Pulled·Created·Started → Running·Ready` 순서에서 첫 단절과 복구를 확인합니다.
>
> `ImagePullBackOff`는 시작점이지 답이 아닙니다.

1. `ImagePullBackOff`가 원인 이름이 아닌 이유는 무엇인가?
2. KubeSphere에서 Deployment를 저장한 뒤 실제 Image Pull은 어느 Client가 수행하는가?
3. Image 전체 주소의 Registry·Project·Repository·Tag는 각각 무엇인가?

# 14. 승인된 교육용 간단 실습 — 같은 Image, 다른 Tag

> 이 실습은 2.2의 `Pending·Running` 비교와 2.4의 `403·200·403` 비교처럼 **한 가지 차이가 결과를 어떻게 바꾸는지 화면에서 직접 확인**하기 위한 대표 시연이다.
>
> 승인된 교육용 Project에서 같은 Registry·Harbor Project·Repository·Registry Secret을 사용하는 Deployment 두 개를 만든다. 정상 Deployment를 먼저 확인한 뒤, 다른 Deployment의 Tag만 존재하지 않는 교육용 값으로 바꿔 `manifest unknown → ErrImagePull → ImagePullBackOff`를 확인한다.

```text
공통 조건
- 같은 Cluster·Namespace
- 같은 Harbor Registry·Project·Repository
- 같은 Registry Secret
- 같은 Container 설정

Deployment A
- 존재하지 않는 교육용 Tag
→ ErrImagePull / ImagePullBackOff
→ Event: manifest unknown

Deployment B
- Harbor에서 존재를 확인한 정상 Tag
→ Container Created·Started
→ Pod Running·Ready
```

> 실제 실행은 정상 기준을 먼저 확보하기 위해 Deployment B부터 만든다. B가 정상 동작하지 않으면 A를 만들지 않는다. 정상 Image·Secret·권한·Network가 확인되지 않은 상태에서는 Tag 하나만의 비교가 성립하지 않는다.

## 14.1 실행 전 Gate와 공통값을 확정한다

다음 조건을 모두 만족할 때만 진행한다.

```text
별도로 승인된 교육용 Project·Namespace가 있다
+ 현재 kubectl Context가 대상 Cluster와 일치한다
+ Harbor에서 정상 Repository·Tag 존재를 확인했다
+ 같은 Namespace에 기존 Registry Secret이 있다
+ Secret Type이 kubernetes.io/dockerconfigjson이다
+ Registry Secret Data와 Password를 열지 않는다
+ 실패용 Tag가 Harbor에 존재하지 않음을 확인했다
+ 같은 이름의 기존 Deployment가 없다
+ 실습 종료 후 Deployment 두 개를 삭제할 수 있다
= 실행 가능
```

실행할 실제값을 입력한다. Password나 Secret Data는 변수에 넣지 않는다.

```bash
NS='<승인된-교육용-namespace>'
IMAGE_REPO='<registry>/<harbor-project>/<repository>'
GOOD_TAG='<harbor에서-존재를-확인한-tag>'
BAD_TAG='training-not-exist-65-20260828'
PULL_SECRET='<같은-namespace의-기존-registry-secret>'
```

대상과 Secret의 이름·Type만 확인한다.

```bash
kubectl config current-context
kubectl get namespace "$NS"
kubectl -n "$NS" get secret "$PULL_SECRET" \
  -o custom-columns='NAME:.metadata.name,TYPE:.type'
kubectl -n "$NS" get deployment
```

기대하는 Secret Type:

```text
kubernetes.io/dockerconfigjson
```

> `BAD_TAG`는 Harbor에서 존재하지 않음을 다시 확인한다. 교육용 실패를 만들기 위해 Registry Secret을 삭제·변경하거나 Harbor Role을 낮추지 않는다.

## 14.2 Deployment B — 정상 Tag로 기준 결과를 먼저 만든다

다음 Deployment는 정상 Tag와 기존 Registry Secret을 사용한다.

```bash
cat <<EOF | kubectl -n "$NS" apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: imagepull-good-tag
spec:
  replicas: 1
  selector:
    matchLabels:
      app: imagepull-good-tag
  template:
    metadata:
      labels:
        app: imagepull-good-tag
    spec:
      imagePullSecrets:
        - name: ${PULL_SECRET}
      containers:
        - name: nginx
          image: ${IMAGE_REPO}:${GOOD_TAG}
          imagePullPolicy: Always
EOF
```

정상 Rollout과 Pod를 확인한다.

```bash
kubectl -n "$NS" rollout status deployment/imagepull-good-tag --timeout=120s
kubectl -n "$NS" get pod -l app=imagepull-good-tag -o wide
kubectl -n "$NS" describe pod -l app=imagepull-good-tag
```

기대 결과:

```text
의도한 전체 Image 주소에 Pull 실패 없음
→ Container Created·Started
→ Pod Running·Ready
```

> Worker에 Image Layer가 이미 있어 Event 문구가 달라질 수 있다. 정상 기준은 의도한 전체 Image 주소에 대한 Pull 실패가 없고 Container가 생성·시작되어 Pod가 `Running·Ready`인 것이다.

> Deployment B가 `Running·Ready`가 아니면 여기서 중단한다. Event에 따라 정상 Tag, Registry Secret 연결, Harbor Pull 권한, CA 또는 Network를 먼저 확인한다. B가 실패한 상태에서 A를 만들면 Tag 하나만의 비교가 아니다.

## 14.3 Deployment A — Tag만 존재하지 않는 값으로 바꾼다

Deployment B와 동일한 Registry·Project·Repository·Registry Secret을 사용하고 Tag만 `BAD_TAG`로 지정한다.

```bash
cat <<EOF | kubectl -n "$NS" apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: imagepull-bad-tag
spec:
  replicas: 1
  selector:
    matchLabels:
      app: imagepull-bad-tag
  template:
    metadata:
      labels:
        app: imagepull-bad-tag
    spec:
      imagePullSecrets:
        - name: ${PULL_SECRET}
      containers:
        - name: nginx
          image: ${IMAGE_REPO}:${BAD_TAG}
          imagePullPolicy: Always
EOF
```

Pod 상태와 Event를 확인한다.

```bash
kubectl -n "$NS" get pod -l app=imagepull-bad-tag -o wide
kubectl -n "$NS" describe pod -l app=imagepull-bad-tag
```

기대 흐름:

```text
Pulling image "<같은 Repository>:<존재하지 않는 Tag>"
→ Failed to pull image
→ manifest unknown
→ ErrImagePull
→ ImagePullBackOff
```

> `ErrImagePull`이 먼저 보이고 재시도 뒤 `ImagePullBackOff`로 바뀔 수 있다. 두 상태 이름보다 Event의 `manifest unknown`과 실제 전체 Image 주소를 확인한다.
>
> `pull access denied`, `x509`, `timeout`이 나오면 의도한 실습 결과가 아니다. Secret·권한·CA·Network를 변경해 억지로 계속하지 말고 Deployment A를 삭제한 뒤 실행 전 Gate를 다시 확인한다.

## 14.4 두 결과를 나란히 비교한다

```bash
kubectl -n "$NS" get pod \
  -l 'app in (imagepull-good-tag,imagepull-bad-tag)' \
  -o wide
```

| Deployment | Registry·Project·Repository | Registry Secret | Tag | 결과 |
|---|---|---|---|---|
| `imagepull-bad-tag` | 동일 | 동일 | 존재하지 않음 | `ErrImagePull` → `ImagePullBackOff`, Event `manifest unknown` |
| `imagepull-good-tag` | 동일 | 동일 | 존재 확인 | `Running·Ready` |

```text
같은 Registry·Project·Repository
+ 같은 Registry Secret
+ Tag만 다름
= 실패 위치는 인증이 아니라 Image Tag
```

> 이 비교로 `ImagePullBackOff`를 보고 Secret부터 재생성하지 않는 이유를 설명한다. Event가 `manifest unknown`이면 Deployment의 전체 Image 주소와 Harbor의 실제 Tag를 먼저 대조한다.

## 14.5 Deployment A의 Tag만 수정해 복구를 확인한다

실패했던 Deployment A의 Image를 정상 Tag로 변경한다.

```bash
kubectl -n "$NS" set image \
  deployment/imagepull-bad-tag \
  nginx="${IMAGE_REPO}:${GOOD_TAG}"
kubectl -n "$NS" rollout status deployment/imagepull-bad-tag --timeout=120s
kubectl -n "$NS" get pod -l app=imagepull-bad-tag -o wide
kubectl -n "$NS" describe pod -l app=imagepull-bad-tag
```

기대 결과:

```text
정상 Tag로 Pod Template 변경
→ 새 ReplicaSet·Pod 생성
→ 의도한 Image의 Pull 실패 없음
→ Container Created·Started
→ Pod Running·Ready
```

> 기존 실패 Pod의 오래된 Event로 복구를 판정하지 않는다. 정상 Tag가 적용된 새 Pod의 현재 Event와 `Running·Ready` 상태를 확인한다.

## 14.6 실습이 끝나면 Deployment만 삭제한다

```bash
kubectl -n "$NS" delete deployment \
  imagepull-good-tag \
  imagepull-bad-tag
kubectl -n "$NS" wait --for=delete \
  deployment/imagepull-good-tag \
  deployment/imagepull-bad-tag \
  --timeout=120s
kubectl -n "$NS" get pod \
  -l 'app in (imagepull-good-tag,imagepull-bad-tag)'
```

기대 결과:

```text
No resources found
```

> 기존 Registry Secret, Harbor Repository·Tag, Harbor Role과 교육용 Namespace는 삭제하거나 변경하지 않는다. 실습이 만든 Deployment와 Pod만 제거한다.

## 14.7 실습 완료 기준

```text
Deployment B의 정상 Tag → Running·Ready 확인
+ Deployment A의 존재하지 않는 Tag → Event manifest unknown 확인
+ 두 Deployment의 Pull 조건에서 Tag만 다름을 확인
+ Deployment A의 Tag 수정 후 새 Pod Running·Ready 확인
+ 교육용 Deployment·Pod 삭제 확인
+ Registry Secret·Harbor Role·CA·Network 변경 없음
= 6.5 대표 시연 완료
```

> 교육생이 `ImagePullBackOff → Event 확인 → manifest unknown → Repository·Tag 대조 → 정상 Tag 수정 → 새 Pod Running·Ready`를 자신의 말로 설명할 수 있어야 한다.
