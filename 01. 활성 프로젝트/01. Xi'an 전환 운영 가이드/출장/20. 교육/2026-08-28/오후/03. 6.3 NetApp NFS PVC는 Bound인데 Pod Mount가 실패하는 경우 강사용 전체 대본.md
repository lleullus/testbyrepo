# 6.3 NetApp NFS PVC는 Bound인데 Pod Mount가 실패하는 경우 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 **수강생이 Kubernetes Storage와 NFS를 거의 모른다는 전제**로 작성했다. 기술 이름부터 나열하지 말고, 저장공간을 준비하는 일과 준비된 저장공간을 Pod에 붙이는 일이 다르다는 점부터 설명한다. 이번 교육에서는 Guide 선택, 첫 분기, 완료 또는 담당 영역 전환까지만 다룬다. 실제 Route·Export Policy 변경이나 NFS 직접 Mount는 수행하지 않는다.

> [!warning] 원본 사례의 확정 정도
> 원본 Guide는 `draft`, 사례는 `investigating` 상태다. 사례의 Management IP 또는 Route를 확정 원인으로 가르치지 않는다. 현재 장애의 PVC·PV·Pod Event와 대상 Node에서 확인한 증거로 다음 영역을 선택한다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
사용자가 하려던 일부터 말한다
→ 저장공간 준비와 Pod 연결을 쉬운 말로 나눈다
→ PVC·PV·StorageClass·Trident·NFS라는 이름을 붙인다
→ Xi'an 사례값을 보여준다
→ PVC·Pod·Event로 같은 장애를 고정한다
→ 마지막 성공과 첫 실패를 구분한다
→ 다음 확인 또는 담당 영역을 선택한다
→ 같은 PVC의 실제 사용으로 복구를 판정한다
```

## 0-1. 오늘 전체 한 줄

```text
Pod가 영구 저장공간을 요청한다
→ Trident가 NetApp Volume을 준비한다
→ PVC와 PV가 연결돼 Bound가 된다
→ Pod가 Worker Node에 배치된다
→ 그 Node가 NFS Volume을 Container 경로에 붙인다
→ Bound 뒤의 Mount 단계가 끊기면 FailedMount가 발생한다
```

---

# 1. 시작 — `Bound인데 왜 실패합니까?`에서 출발한다

> 오늘 볼 증상은 PVC가 `Bound`인데 그 PVC를 사용하는 Pod가 `ContainerCreating`에 머물고 Event에 `FailedMount`가 나타나는 경우입니다.
>
> 처음 보면 모순처럼 보입니다. `Bound라면 Storage가 정상 아닌가요?`라고 생각할 수 있습니다.
>
> 하지만 `Bound`와 `Mount`는 서로 다른 작업의 결과입니다.

## 1.1 사용자가 하려던 일

> Container는 다시 만들어질 수 있지만 Application Data는 계속 남아야 할 수 있습니다.
>
> 그래서 사용자는 Pod 밖에 유지되는 저장공간을 요청하고, 그 저장공간을 Container의 지정 경로에 연결해 사용합니다.

## 1.2 저장공간을 먼저 준비한다

> 필요한 용량과 사용 방식을 적은 저장공간 요청이 **PVC**입니다.
>
> 준비된 실제 Volume을 Kubernetes에서 나타내는 객체가 **PV**이고, 어떤 방식으로 Volume을 준비할지 정한 기준이 **StorageClass**입니다.
>
> Xi'an 사례에서는 **Trident**가 이 요청을 받아 NetApp NFS Volume과 qtree를 준비합니다.

```text
PVC 요청
→ StorageClass 선택
→ Trident가 NetApp Volume 준비
→ PV 생성·연결
→ PVC Bound
```

## 1.3 준비된 저장공간을 Pod에 붙인다

> PVC가 Bound된 뒤에도 한 단계가 더 남습니다.
>
> Scheduler가 Pod를 실행할 Worker Node를 선택하면, 그 Node의 kubelet과 CSI 구성요소가 NetApp NFS Volume을 Container 경로에 Mount해야 합니다.

```text
Pod 배치
→ 선택된 Worker Node
→ NFS Data LIF와 export path
→ kubelet·CSI Mount
→ Container에서 저장공간 사용
```

> **따라서**, `PVC=Bound`는 Volume 준비와 PV 연결까지 성공했다는 뜻입니다.
>
> **하지만**, 현재 Pod가 배치된 Worker Node의 NFS Mount까지 성공했다는 뜻은 아닙니다.

---

# 2. 이 증상이 정말 6.3 사례인지 먼저 확인한다

> Storage라는 단어가 보인다고 바로 이 Guide를 선택하지 않습니다. 다음 세 상태가 함께 있는지 봅니다.

```text
PVC = Bound
Pod = ContainerCreating
Pod Event = FailedMount와 NFS Mount 오류
```

## 2.1 결과에 따라 Guide가 갈린다

```text
PVC가 Pending 또는 Bound가 아님
→ Volume 준비 단계
→ StorageClass·Provisioning·Quota 영역 확인

PVC는 Bound지만 Event가 Image Pull·Scheduling 오류
→ NFS Mount 사례가 아님
→ 실제 Event에 맞는 Guide 선택

PVC Bound + NFS FailedMount
→ 6.3 Guide로 진행
```

> 상태 이름만 보고 추측하지 않고 Event의 실제 오류 문장으로 사례를 선택합니다.

# 3. Xi'an 원본 사례값은 정답이 아니라 읽기 예시다

```text
PVC                qtree-volume
StorageClass       scs-netapp-qtree-nfs-sc-delete
Pod                tomcat-deployment3-59b6769d74-2znvv
Worker Node        xadkswkmp01
Node Management IP 109.156.22.67
Node Storage IP    109.156.24.67
Data LIF           109.156.24.25, 109.156.24.26
NFS Port           TCP 2049
Container Path     /test
```

> 이 값은 원본 사례의 구조를 읽기 위한 자료입니다. Pod 이름, PV UUID, export path, 시각과 IP를 현재 장애에 그대로 붙여 넣지 않습니다.
>
> 실제 장애에서는 대상 Cluster와 Namespace부터 다시 고정합니다.

---

# 4. 같은 장애 대상을 고정한 뒤 세 가지를 확인한다

> 명령을 여러 개 실행하는 것이 목적이 아닙니다. PVC·Pod·Event가 같은 장애를 가리키는지 확인하는 것이 목적입니다.

```bash
NS='actual-namespace'
PVC='actual-pvc-name'
POD='actual-pod-name'
```

## 4.1 PVC·PV·StorageClass — 무엇이 준비됐는가

```bash
kubectl -n "$NS" get pvc "$PVC" -o wide
PV="$(kubectl -n "$NS" get pvc "$PVC" -o jsonpath='{.spec.volumeName}')"
SC="$(kubectl -n "$NS" get pvc "$PVC" -o jsonpath='{.spec.storageClassName}')"
kubectl get pv "$PV" -o yaml
kubectl get storageclass "$SC" -o yaml
```

> 여기서는 PVC가 실제로 `Bound`인지, 어떤 PV와 StorageClass에 연결됐는지 확인합니다.
>
> PV와 StorageClass에서는 NFS Server·export path 또는 CSI Volume 정보와 `mountOptions`를 읽습니다. 뒤에서 확인할 경로가 실제 Pod Mount 요청과 같은 조건인지 대조하기 위해서입니다.

## 4.2 Pod와 Worker Node — 어디에서 Mount를 시도했는가

```bash
kubectl -n "$NS" get pod "$POD" -o wide
NODE="$(kubectl -n "$NS" get pod "$POD" -o jsonpath='{.spec.nodeName}')"
printf 'NODE=%s\n' "$NODE"
```

> NFS Mount는 모든 Worker가 아니라 Pod가 배치된 정확한 Node에서 수행됩니다.
>
> 따라서 Bastion이나 정상인 다른 Worker의 결과로 현재 Pod의 Mount 경로를 판정하지 않습니다.

## 4.3 Pod Event — 실제로 무엇이 실패했는가

```bash
kubectl -n "$NS" describe pod "$POD"
```

> `exit status 32`라는 숫자만 외우지 않습니다. Event에서 다음 값을 읽습니다.

```text
Reason과 실제 오류 문장
실패가 발생한 시각과 반복 횟수
Volume과 PV 식별자
NFS Server 또는 Data LIF
export path
Mount를 시도한 Worker Node
```

> Event의 Server·Path와 PV·StorageClass 정의가 서로 같은지 확인합니다. 다르면 Network를 확인하기 전에 객체 정의와 실제 요청부터 바로잡아야 합니다.

---

# 5. `Bound` 뒤의 첫 분기를 선택한다

## 5.1 Trident Backend가 Volume 준비 경계를 확인한다

```bash
tridentctl get backend -n trident
```

```text
PVC Bound + Backend online
→ Volume 준비 경로는 통과
→ Pod가 배치된 Node의 Mount 경로로 이동

Backend offline 또는 비정상
→ Node Route를 먼저 변경하지 않음
→ Trident·Storage Backend 연결 영역으로 전환
```

> Backend가 `online`이라는 사실도 모든 Worker Node의 NFS 경로가 정상이라는 뜻은 아닙니다.

## 5.2 Node Mount 경로는 결과에 따라 담당 영역이 갈린다

> 원본 Guide의 후속 확인은 다음 순서입니다. 이번 교육에서는 각 결과가 어느 영역으로 연결되는지만 판단합니다.

```text
대상 Worker에서 Data LIF Route와 Source IP 확인
→ TCP 2049 확인
→ 같은 Server·Path·Mount Option의 직접 Mount 확인
```

| 확인 결과 | 다음 영역 |
|---|---|
| Route의 Device·Source IP가 승인된 Storage 경로와 다름 | Node Routing·Network |
| Route 정상, TCP 2049 Timeout | Storage Network·Firewall·Data LIF |
| TCP 2049 연결, `access denied by server` | 실제 Source IP·Export Policy |
| TCP 2049 연결, `No such file or directory` | PV·Event·qtree·export path |
| 동일 조건의 직접 Mount 실패 | 오류 원문에 해당하는 Network·Storage 영역 |
| 동일 조건의 직접 Mount 성공, Pod만 실패 | kubelet·CSI·Trident Node 영역 |

> TCP 2049 연결은 Port 도달만 증명합니다. export 허용, 정확한 path와 Mount Option까지 증명하지 않습니다.
>
> 직접 Mount도 Event와 다른 Server·Path 또는 다른 NFS Option을 사용하면 현재 Pod 경로의 분기 증거가 되지 않습니다.

## 5.3 원본 사례의 Route를 확정 원인으로 만들지 않는다

> 원본에는 Storage IP 대신 Management IP가 Source로 선택되는 비정상 분기가 설명돼 있습니다.
>
> 하지만 사례 상태가 `investigating`이므로 현재 장애의 `ip route get` 결과와 승인된 Network 설계 없이 Route를 원인으로 확정하지 않습니다.
>
> Route·Default Metric 변경은 Node 전체 통신에 영향을 줄 수 있으므로 교육 중 실행하지 않습니다.

---

# 6. 먼저 하지 않을 조치를 분명히 한다

```text
PVC·StorageClass 즉시 삭제·재생성
Trident 전체 재설치
Pod 반복 삭제
모든 Node Route 일괄 변경
Export Policy 전체 허용
```

> 첫 단절을 확인하지 않은 변경은 정상 영역과 기존 데이터에 영향을 주거나 장애 원인을 숨길 수 있습니다.

---

# 7. 완료와 에스컬레이션 기준을 구분한다

## 7.1 복구 완료

```text
같은 PVC 사용
+ Pod Running·Ready
+ FailedMount Event의 횟수와 최근 시각이 더 이상 증가하지 않음
+ Container의 지정 경로에 실제 Filesystem Mount 확인
+ 승인된 Test Data를 쓰고 같은 값을 다시 읽음
```

> `touch`와 `ls -l`은 빈 파일 생성과 Metadata 조회입니다. 데이터 Write·Read라고 부르지 않습니다.
>
> 실제 Write·Read 검증은 Application 영향과 정리 계획이 승인된 경우에만 고유한 Test File로 수행합니다. 교육 중에는 실행하지 않습니다.

## 7.2 담당 영역으로 넘길 때 함께 전달할 증거

| 확인 결과 | 담당 영역 | 함께 전달할 증거 |
|---|---|---|
| Backend offline | Trident·Storage | Namespace·PVC·PV·StorageClass·Backend 상태 |
| Route·Source IP 불일치 | Node·Network | Pod Node·Data LIF·`ip route get` 원문 |
| TCP 2049 Timeout | Network·Firewall | Source Node·Data LIF·Port·발생 시각 |
| 접근 거부·경로 없음 | Storage | 실제 Source IP·Server·Path·오류 원문 |
| 직접 Mount 성공, Pod 실패 | Kubernetes·CSI | PVC·PV·Pod Event·Node·동일 시간대 로그 |

> Password, Token, kubeconfig, Secret 값과 다른 Application 데이터는 장애 증적에 포함하지 않습니다.

---

# 8. 실제 요청을 하나의 이야기로 연결한다

> 사용자가 `PVC는 Bound인데 Pod가 계속 ContainerCreating입니다`라고 요청했다고 하겠습니다.
>
> 먼저 PVC가 정말 Bound인지 보고, Pod Event가 NFS `FailedMount`인지 확인합니다. PVC가 Pending이거나 Event가 Image Pull 오류라면 6.3 사례가 아닙니다.
>
> 다음으로 Namespace, PVC, 연결된 PV와 StorageClass, Pod, Worker Node와 발생 시각을 하나의 장애 대상으로 고정합니다.
>
> PV·StorageClass의 Server·Path·Mount Option과 Event의 실제 요청을 대조합니다.
>
> Trident Backend가 online이면 Volume 준비 단계는 통과한 것으로 보고, Pod가 배치된 Node의 Route·Source IP와 TCP 2049, 동일 조건의 직접 Mount 결과로 담당 영역을 좁힙니다.
>
> **하지만**, 원본 사례만 보고 Route를 확정 원인으로 정하거나 Node 설정을 바로 바꾸지 않습니다.
>
> 조치 후에는 같은 PVC를 사용하는 Pod가 Running·Ready인지, FailedMount가 더 증가하지 않는지, Container 경로의 실제 Mount와 승인된 데이터 Write·Read가 성공하는지 확인합니다.

---

# 9. 마무리 — 두 단계만 정확히 기억한다

> PVC가 `Bound`라는 것은 저장공간이 준비되고 PV와 연결됐다는 뜻입니다.
>
> Pod가 그 저장공간을 실제로 사용하려면 선택된 Worker Node가 NFS 경로에 도달하고 kubelet과 CSI가 Container 경로에 Mount해야 합니다.
>
> **결국**, `PVC·PV 준비 → Pod가 배치된 Node → Event의 Server·Path → Backend → Route·2049·동일 조건 직접 Mount → kubelet·CSI → Container 사용`에서 마지막 성공과 첫 실패를 구분합니다.
>
> `Bound`는 저장공간 준비의 완료이고, `Running·Ready와 실제 Mount·Write·Read`는 Pod 사용 경로의 완료입니다.
