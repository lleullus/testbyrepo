# Workspace · Project 운영자 실습 진행안

## 실제 진행 순서

| 순서 | 강사가 시연할 내용 | 교육생이 할 일 | 확인 기준 | 권장 시간 |
|---|---|---|---|---:|
| 1 | `admin` 로그인, DEV 대상과 Naming Rule 확인 | 자기 Workspace / Project 이름 확인 | 이름 2개 준비 | 3분 |
| 2 | Workspace 생성 | 자기 Workspace 생성 | Name / Administrator / Cluster 일치 | 5~7분 |
| 3 | Project 생성 | 같은 Workspace 아래 자기 Project 생성 | Project 이름 일치 | 4~5분 |
| 4 | Namespace 조회 | 자기 Project 이름으로 Namespace 조회 | `Active` | 3~5분 |

정상 진행 기준 약 **15~20분**으로 본다.

## 1. 먼저 한 줄로 연결한다

`일단` Kubernetes에서는 Namespace가 Application의 실제 운영 영역이 됨 → `하지만` KubeSphere에서는 사용자와 Project를 묶어 관리하기 위해 그 위에 Workspace를 둠 → `그래서` 먼저 Workspace를 만들고 그 아래 Project를 생성함 → `그리고` Project를 만들면 실제 Kubernetes Namespace가 생성됨 → `DKS에서는` Workspace와 Project를 1:1로 운영함 → `따라서` 이번 실습에서는 `admin`으로 로그인해 각 교육생의 AD 기준 Workspace와 Project를 만들고 → `마지막으로` 해당 Project와 같은 이름의 Namespace가 `Active`인지 확인함

```text
Workspace
= KubeSphere 상위 관리 영역

Project
= Kubernetes Namespace와 연결되는 Application 운영 영역

DKS
= Workspace : Project = 1 : 1
```

### 강사 대본

> 먼저 전체 구조부터 보겠습니다. Kubernetes에서는 Application을 나누는 실제 운영 영역이 Namespace입니다. 그런데 KubeSphere에서는 Namespace를 바로 보여주는 방식이 아니라, 그 위에 Workspace라는 관리 영역을 두고 그 안에 Project를 둡니다. 여기서 Project가 실제 Kubernetes Namespace와 연결됩니다. 그래서 화면에서 보이는 Workspace와 Project가 둘 다 비슷한 이름으로 보여도 같은 객체는 아닙니다. Workspace는 사용자와 Project를 묶어서 관리하는 상위 영역이고, Project가 실제 Application 리소스가 들어가는 Namespace 쪽입니다.
>
> DKS에서는 이 구조를 복잡하게 쓰지 않고 Workspace 하나에 Project 하나, 1:1로 운영합니다. 오늘도 그 기준으로 갑니다. 각자 자기 AD를 기준으로 이름을 만들고, `admin`으로 로그인해서 먼저 Workspace를 만든 다음 그 안에 Project를 만들 겁니다. 실습 대상은 DEV이기 때문에 Cluster는 `dev-apps-pa01-xas`로 고정해서 보시면 됩니다. 이름도 자기 AD를 기준으로 만들되 Kubernetes 리소스 이름에 맞게 점은 하이픈으로 바꿉니다.
>
> 여기서 한 가지 구분할 게 있습니다. 지금 로그인하는 계정은 `admin`이고, Workspace 생성 화면의 Administrator도 `admin(DKS)`입니다. 신청자의 Admin/User Permission하고 이 Administrator는 다른 개념입니다. 신청자 Permission은 뒤에서 Project Role을 줄 때 쓰는 값이고, 지금 1번에서는 Workspace와 Project라는 운영 영역을 먼저 만드는 데 집중합니다.
>
> Workspace를 만들고 나면 바로 Project를 만들고, Project를 만들었다고 KubeSphere 화면만 보고 끝내지는 않습니다. Project가 실제 Kubernetes Namespace와 연결되는 객체이기 때문에 마지막에는 `kubectl get namespace`로 같은 이름의 Namespace가 실제로 존재하고 상태가 `Active`인지 확인할 겁니다. 즉 1번의 완료 기준은 Workspace가 보이는 것 하나가 아니라, Workspace 생성, Project 생성, 그리고 실제 Namespace `Active`까지입니다. 이 상태를 그대로 두고 다음 2번에서 같은 Workspace에 사용자를 연결하겠습니다.

## 2. 실제 진행

### 2.1 생성할 이름 확인

이번 실습 고정값:

```text
로그인 계정
admin

Cluster
dev-apps-pa01-xas
```

AD가 `abcd1234.id`라면:

```text
Project
abcd1234-id-dev

Workspace
ws-dev-apps-pa01-xas-abcd1234-id-dev
```

Naming Rule:

```text
. → -

Project
<AD-normalized>-dev

Workspace
ws-dev-apps-pa01-xas-<AD-normalized>-dev
```

---

### 2.2 Workspace 생성

```text
Workspace
→ Create
```

| 항목 | 값 |
|---|---|
| Name | `ws-dev-apps-pa01-xas-abcd1234-id-dev` |
| Administrator | `admin(DKS)` |
| Cluster | `dev-apps-pa01-xas` |

주의:
- Workspace 이름은 자기 AD 기준으로 만든다.
- Cluster는 `dev-apps-pa01-xas`를 선택한다.

생성 후 바로 확인:

```text
Name
= 자기 Workspace 이름

Administrator
= admin(DKS)

Cluster
= dev-apps-pa01-xas
```

---

### 2.3 Project 생성

방금 만든 Workspace에서 진행한다.

```text
Projects
→ Create
→ Project Name 입력
→ OK
```

예시:

```text
abcd1234-id-dev
```

주의:
- Workspace 이름이 아니라 Project 이름을 입력한다.

---

### 2.4 Namespace 확인

```bash
kubectl get namespace abcd1234-id-dev
```

교육생은 자기 Project 이름으로 실행한다.

정상 예:

```text
NAME                STATUS   AGE
abcd1234-id-dev      Active   ...
```

완료 기준:

```text
Workspace 생성
→ Project 생성
→ 같은 이름 Namespace 존재
→ Status = Active
```

확인 후 Workspace와 Project는 삭제하지 않고 02번에서 그대로 사용한다.
