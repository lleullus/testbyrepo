# KubeSphere CA ConfigMap Mount

> [!summary] 요약
> Harbor 이미지 레지스트리 연동 시 `x509: certificate signed by unknown authority` 오류가 발생하면 Member Cluster의 `ks-apiserver`가 Harbor 인증서 체인을 신뢰할 수 있도록 CA ConfigMap과 Mount 상태를 확인한다. 기존 가이드의 `secds-rootca` 방식과 현재 Xi'an의 T2 CA 적용 계획을 함께 이해한다.

> [!important] 이번 교육에서의 범위
> 6명이 `kubesphere-system`의 공용 ConfigMap이나 `ks-apiserver`를 각각 수정하지 않는다. 이번 교육에서는 **오류 증상 → CA ConfigMap → `ks-apiserver` volume/volumeMount → Pod Ready → 기능 재확인**의 흐름을 설명하고 현재 상태를 조회한다.

---

## 1. 문제 현상

Harbor 이미지 레지스트리 Secret 생성 또는 KubeSphere에서 Harbor 이미지를 조회하는 과정에서 CA 신뢰가 맞지 않으면 다음 오류가 발생할 수 있다.

> `x509: certificate signed by unknown authority`

운영자는 먼저 이 오류가 **TLS 인증서 신뢰 문제**인지 확인하고, 인증 실패(`unauthorized`)와 구분한다.

```text
x509: certificate signed by unknown authority
→ CA Trust 확인

unauthorized
→ Harbor 계정 / Project / 권한 확인
```

---

## 2. 기존 가이드의 기본 구조

기존 1.7 가이드는 각 Member Cluster의 `kubesphere-system` Namespace에 사내 CA를 ConfigMap으로 등록하고 `ks-apiserver`에 Mount하는 구조다.

```text
사내 CA cert
→ ConfigMap
→ kubesphere-system
→ ks-apiserver Volume
→ ks-apiserver VolumeMount
→ ks-apiserver 재기동
→ 기능 재확인
```

기존 문서 예시는 다음과 같다.

- ConfigMap: `secds-rootca`
- Namespace(Project): `kubesphere-system`
- Key: `ca.crt`
- Workload: `ks-apiserver`

이 구조 자체는 현재 Xi'an에서도 CA를 `ks-apiserver`에 추가 Mount하는 기본 메커니즘을 이해하는 데 사용한다.

---

## 3. 현재 Xi'an T2 CA 기준

2026-08-19 작업계획 기준으로 Harbor `xa.dcr.dks.samsungds.net`의 실제 인증서 체인은 T2 CA를 사용한다.

```text
xa.dcr.dks.samsungds.net
→ SECDS-T2IssuingCA
→ SECDS-T2ROOTCA
```

현재 작업계획은 기존 `secds-rootca`를 덮어쓰는 방식이 아니라 **신규 `secds-t2-ca` ConfigMap을 추가**하는 방식이다.

```text
SECDS-T2IssuingCA
+
SECDS-T2ROOTCA
        ↓
secds-t2-ca / ca.crt
        ↓
ks-apiserver 인증서 디렉터리에 추가 Mount
        ↓
DEV 검증
        ↓
PRD 동일 적용
```

### 현재 작업계획 핵심

- 대상: `dev-apps-pa01-xas`, `prd-apps-pa01-xas`
- Host Cluster는 해당 작업 대상에서 제외
- 기존 `secds-rootca` 또는 기존 CA Mount가 있으면 먼저 확인하고 기존 설정은 그대로 둔다.
- 신규 ConfigMap: `secds-t2-ca`
- `ca.crt`: `SECDS-T2IssuingCA` + `SECDS-T2ROOTCA` bundle
- DEV에서 먼저 적용·검증 후 PRD에 동일 적용
- 적용 후 `ks-apiserver` Pod 정상 상태와 Harbor 이미지 입력 기능을 다시 확인

> [!note] 현장 우선
> 실제 교육 당일 ConfigMap 이름과 Mount 상태가 작업계획과 다를 수 있으므로 현재 Console/Cluster 상태를 조회한 결과를 우선한다.

---

## 4. 교육생 상태 조회 절차

### 4.1 대상 Member Cluster 확인

KubeSphere에서 다음 경로로 이동한다.

```text
Platform
→ Cluster Management
→ 대상 Member Cluster
```

이번 교육에서는 `dev-apps-pa01-xas`를 조회 대상으로 사용한다.

### 4.2 CA ConfigMap 확인

```text
Configuration
→ ConfigMaps
→ Project/Namespace: kubesphere-system
```

현재 환경에서 다음을 확인한다.

- `secds-rootca` 존재 여부
- `secds-t2-ca` 존재 여부
- 기타 사내 CA ConfigMap 존재 여부
- 실제 적용 대상으로 확인된 ConfigMap의 Key가 `ca.crt`인지

교육에서는 CA 내용 자체보다 **어떤 ConfigMap이 어떤 Namespace에 있고 `ks-apiserver`와 어떻게 연결되는지**를 확인한다.

### 4.3 ks-apiserver Mount 확인

```text
Application Workloads
→ Workloads
→ ks-apiserver
→ Volumes / Mounts 확인
```

확인 항목:

- CA ConfigMap을 참조하는 Volume이 존재하는가
- Container에 해당 VolumeMount가 존재하는가
- Mount Path가 현재 운영 설정과 일치하는가
- `ks-apiserver` Pod가 정상 상태인가

핵심:

```text
ConfigMap 존재
≠
CA 적용 완료
```

ConfigMap이 있어도 `ks-apiserver`에 Mount되지 않았다면 해당 프로세스가 CA를 사용하지 않는다.

### 4.4 적용 완료 판단 흐름

실제 CA 변경 작업의 완료 판단은 다음 순서다.

```text
ConfigMap 생성/확인
→ ks-apiserver volume 확인
→ volumeMount 확인
→ Rollout/Pod Ready 확인
→ Harbor 이미지 입력 또는 Registry 기능 재확인
```

이번 교육에서는 이미 구성된 상태를 조회하면서 이 순서를 설명한다.

---

## 5. 원본 운영 절차와 현재 작업 절차의 관계

| 구분 | 기존 1.7 가이드 | 현재 Xi'an T2 CA 작업계획 |
|---|---|---|
| 문제 | Harbor x509 | Harbor x509 |
| Namespace | `kubesphere-system` | `kubesphere-system` |
| ConfigMap | `secds-rootca` 예시 | 신규 `secds-t2-ca` |
| CA 내용 | SECDS-ROOT.crt | `SECDS-T2IssuingCA` + `SECDS-T2ROOTCA` |
| 적용 대상 | 각 Member | DEV 먼저, 검증 후 PRD |
| 기존 CA | 명확한 구분 없음 | 기존 `secds-rootca` 등은 먼저 확인하고 유지 |
| 검증 | 자동 재시작 언급 | rollout, Pod 상태, UI/Harbor 기능까지 확인 |
| Rollback | 원본에 없음 | 작업 전 상태 백업 및 rollback 기준 존재 |

따라서 교육에서는 기존 1.7의 **ConfigMap → Mount** 개념을 유지하면서, 실제 Xi'an 운영은 최신 T2 CA 작업계획 기준으로 설명한다.

## 6. 실제 변경 작업이 필요한 경우

이번 교육에서 직접 변경하지 않는다. 실제 x509 조치가 필요한 경우 다음 작업계획을 기준으로 수행한다.

- [[35. 작업 관리/2026-08-19 DEV PRD Member ks-apiserver SECDS T2 CA Bundle 적용 작업계획서|DEV PRD Member ks-apiserver SECDS T2 CA Bundle 적용 작업계획서]]

해당 작업계획에는 다음이 포함되어 있다.

- 승인된 T2 CA 확인
- 작업 전 `ks-apiserver` 상태/Deployment 백업
- 기존 CA Mount 확인
- 실제 인증서 디렉터리 확인
- DEV 적용 및 기능 검증
- PRD 동일 적용
- Rollout 및 Pod 확인
- 실패 시 rollback

## 7. 6명 교육 완료 확인

6명 모두 다음을 설명하거나 화면에서 확인할 수 있으면 완료다.

- [ ] `x509: certificate signed by unknown authority`가 CA 신뢰 문제임을 설명
- [ ] 대상 Member Cluster의 `kubesphere-system`으로 이동
- [ ] 현재 CA ConfigMap 이름 확인
- [ ] `ca.crt` Key 확인
- [ ] `ks-apiserver`의 ConfigMap Volume 확인
- [ ] `ks-apiserver`의 VolumeMount 확인
- [ ] Pod 정상 상태 확인
- [ ] ConfigMap 존재만으로 적용 완료가 아니라는 점 설명
- [ ] 현재 Xi'an에서는 T2 Issuing/Root CA bundle 적용 계획을 사용한다는 점 설명
