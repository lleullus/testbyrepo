# Quota 운영자 실습 진행안

## 실제 진행 순서

| 순서 | 강사가 시연할 내용 | 교육생이 할 일 | 확인 기준 | 권장 시간 |
|---|---|---|---|---:|
| 1 | 당일 확정 CPU·Memory·Storage 값 안내 | 공통 실습값 확인 | 6명 동일 값 | 2분 |
| 2 | Workspace CPU/Memory Quota | 자기 Workspace에 공통값 입력 | Request/Limit 값 일치 | 4~5분 |
| 3 | Project CPU/Memory Quota | 자기 Project에 같은 값 입력 | Workspace와 동일 | 4~5분 |
| 4 | StorageClass 확인과 준비된 ResourceQuota YAML 설명 | 자기 Project명과 Storage 값 확인 | 대상 Namespace / 값 정확 | 3~4분 |
| 5 | Storage ResourceQuota 적용 | 자기 Namespace에 적용 | ResourceQuota 생성 | 3~5분 |
| 6 | ResourceQuota 조회 | `get/describe`로 결과 확인 | Namespace / Storage 값 / SC key 일치 | 3~5분 |

정상 진행 기준 약 **20~25분**으로 본다. Storage YAML을 처음부터 타이핑하지 않고 준비된 파일을 사용한다.

## 1. 먼저 한 줄로 연결한다

`일단` 03번까지 끝나면 사용자는 Project를 운영할 권한을 가지지만 사용할 수 있는 자원량의 경계는 아직 없음 → `그래서` 신청서에서 승인된 CPU·Memory·Storage 값을 Quota로 반영함 → `DKS에서는` Workspace와 Project를 1:1로 운영하므로 CPU·Memory Quota는 두 범위에 같은 승인값을 적용함 → `그리고` Storage는 Namespace 전체 요청 총량뿐 아니라 실제 StorageClass별 요청 총량도 함께 제한함 → `마지막으로` 화면 저장만 보고 끝내지 않고 Kubernetes ResourceQuota가 실제 Namespace에 존재하는지 확인함 → `결국` 04번은 숫자를 입력하는 작업이 아니라 사용자가 사용할 수 있는 자원 경계를 실제 Cluster에 만드는 단계임

### 핵심 구조

```text
신청 CPU / Memory
→ Workspace Quota
→ Project Quota

신청 Storage
→ Namespace 전체 Storage Quota
+ StorageClass별 Storage Quota
```

### 강사 대본

> 3번까지 끝났으면 사용자가 자기 Project에서 Application 리소스를 운영할 권한은 생긴 상태입니다. 그런데 여기서 권한하고 자원량을 분리해서 봐야 합니다. `project-operator`라는 Role은 무엇을 할 수 있느냐를 정하는 거고, CPU를 몇 코어까지 쓸 수 있는지, Memory를 얼마나 쓸 수 있는지, Storage를 얼마나 요청할 수 있는지는 Quota가 정합니다. 권한이 있다고 자원을 무제한 쓸 수 있는 건 아닙니다.
>
> 그래서 4번에서는 신청서에서 승인된 CPU, Memory, Storage 값을 실제 Cluster의 자원 경계로 반영합니다. DKS에서는 Workspace하고 Project를 1:1로 사용하고 있기 때문에 CPU와 Memory는 Workspace Quota와 Project Quota 양쪽에 같은 승인값을 넣습니다. 현재 운영 가이드 기준으로 CPU 승인값은 CPU Request와 Limit에 동일하게, Memory 승인값도 Memory Request와 Limit에 동일하게 넣습니다. 숫자만 보지 말고 단위까지 같이 확인하시면 됩니다.
>
> Storage는 CPU나 Memory처럼 UI 값만 넣고 끝나는 게 아니라 Kubernetes의 ResourceQuota까지 봅니다. Namespace 전체에서 요청할 수 있는 Storage 총량을 `requests.storage`로 잡고, 현재 Xi'an에서 사용하는 StorageClass인 `scs-netapp-qtree-nfs-sc-delete`에 대한 Storage 요청 제한도 같이 둡니다. 오늘은 YAML 문법을 외우는 실습이 아니기 때문에 처음부터 작성하지 않고 준비된 `storagequota.yaml`을 사용합니다.
>
> 준비된 YAML에서 각자 확인할 건 자기 Project 이름, 즉 Namespace가 맞는지, 그리고 당일 확정된 Storage 값이 맞는지입니다. 다른 사람 Project 이름이 남아 있거나 단위가 다르면 그 상태로 적용하면 안 됩니다. 적용 전에는 자기 Namespace가 `Active`인지 한 번 보고, 이상 없으면 ResourceQuota를 생성합니다.
>
> 마지막 확인이 중요합니다. Workspace 화면에 CPU/Memory 숫자가 저장됐다고 4번이 끝난 게 아니고, Project에도 같은 값이 들어가야 하고 Storage ResourceQuota도 실제 Namespace에 존재해야 합니다. 그래서 `kubectl get resourcequota`하고 `kubectl describe resourcequota`로 `requests.storage`, StorageClass key, Namespace가 자기 값과 맞는지 확인합니다. Workspace CPU/Memory, Project CPU/Memory, Storage ResourceQuota 세 가지가 다 맞으면 4번은 끝입니다.

## 2. 실제 진행

### 2.1 오늘 사용할 값 확인

6명 모두 같은 승인값을 사용한다.

| 항목 | 이번 실습 값 |
|---|---|
| CPU | 당일 확정값 |
| Memory | 당일 확정값 |
| Storage | 당일 확정값 |
| StorageClass | `scs-netapp-qtree-nfs-sc-delete` |

CPU 승인값은 CPU Request와 Limit에 동일하게, Memory 승인값은 Memory Request와 Limit에 동일하게 입력한다.

Storage CLI 작업은 06번에서 만드는 사용자 kubeconfig가 아니라 **교육 시작 전에 준비된 기존 운영 kubectl 환경**을 사용한다.

---

### 2.2 Workspace CPU / Memory Quota

```text
Workbench
→ Workspaces
→ 자기 Workspace
→ Workspace Settings
→ Workspace Quotas
→ Edit Quotas
```

입력:

```text
CPU Request = 당일 CPU 값
CPU Limit   = 당일 CPU 값
Memory Request = 당일 Memory 값
Memory Limit   = 당일 Memory 값
```

주의:
- 자기 AD 기반 Workspace가 맞는지 먼저 본다.
- CPU/Memory 숫자와 단위를 같이 확인한다.

저장 후 화면의 Request/Limit 값을 바로 확인한다.

---

### 2.3 Project CPU / Memory Quota

```text
자기 Project
→ Project Overview / Project Settings
→ Edit Quotas
```

Workspace에 입력한 것과 **같은 CPU·Memory 값**을 입력한다.

확인:

```text
Workspace CPU/Memory
= Project CPU/Memory
```

---

### 2.4 Storage ResourceQuota 준비

먼저 실제 StorageClass를 확인한다.

```bash
kubectl get sc
```

이번 DEV 기준:

```text
scs-netapp-qtree-nfs-sc-delete
```

교육생이 YAML을 처음부터 타이핑하지 않는다. 준비된 `storagequota.yaml`에서 **자기 Project 이름과 당일 확정 Storage 값**만 확인한다.

형식:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: abcd1234-id-dev-storage-quota
  namespace: abcd1234-id-dev
spec:
  hard:
    requests.storage: <당일 확정 Storage 값>
    scs-netapp-qtree-nfs-sc-delete.storageclass.storage.k8s.io/requests.storage: <당일 확정 Storage 값>
```

예시 AD가 `abcd1234.id`이면 Project/Namespace는 `abcd1234-id-dev`다.

주의:
- 다른 교육생 Project 이름이 남아 있지 않은지 확인한다.
- Storage 값과 단위를 확인한다.
- StorageClass 이름을 임의로 바꾸지 않는다.

---

### 2.5 Storage ResourceQuota 적용

적용 전에 자기 Namespace가 있는지만 확인한다.

```bash
kubectl get namespace abcd1234-id-dev
```

정상이면:

```bash
kubectl create -f storagequota.yaml
```

이미 같은 ResourceQuota가 존재한다면 `create`를 반복하지 않고 기존 객체를 먼저 확인한다.

---

### 2.6 바로 확인

예시 Project가 `abcd1234-id-dev`라면:

```bash
kubectl get resourcequota -n abcd1234-id-dev
kubectl describe resourcequota abcd1234-id-dev-storage-quota -n abcd1234-id-dev
```

확인할 것:

```text
Namespace
= abcd1234-id-dev

requests.storage
= 당일 확정 Storage 값

StorageClass key
= scs-netapp-qtree-nfs-sc-delete.storageclass.storage.k8s.io/requests.storage
```

04번은 아래 세 가지가 모두 맞으면 끝낸다.

```text
Workspace CPU/Memory
→ Project CPU/Memory
→ Storage ResourceQuota
```
