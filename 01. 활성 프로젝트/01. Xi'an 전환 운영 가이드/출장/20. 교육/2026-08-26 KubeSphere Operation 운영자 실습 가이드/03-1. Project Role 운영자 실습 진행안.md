# Project Role 운영자 실습 진행안

## 실제 진행 순서

| 순서 | 강사가 시연할 내용 | 교육생이 할 일 | 확인 기준 | 권장 시간 |
|---|---|---|---|---:|
| 1 | 대상 Project와 자기 AD 확인 | 01번에서 만든 자기 Project 열기 | Project 이름 일치 | 2분 |
| 2 | Project Member 초대와 Role 선택 | 자기 AD 계정 추가, `project-operator` 선택 | AD + Role 일치 | 4~6분 |
| 3 | Project Members 확인 | 자기 계정/Role 확인 | `project-operator` | 2분 |

정상 진행 기준 약 **10분 내외**로 본다.

## 1. 먼저 한 줄로 연결한다

`일단` Workspace Member가 되면 사용자가 상위 Workspace 범위에는 들어오지만 실제 Project 리소스를 운영할 권한은 아직 없음 → `그래서` 같은 사용자를 Project Member로 추가하고 Project Role을 별도로 부여함 → `DKS에서는` 신청서 Admin을 `project-operator`, User를 `project-viewer`로 매핑함 → `중요` 신청서에 Admin이라고 적혀 있다고 `project-admin`을 주는 것이 아님 → `이번 실습에서는` 6명 모두 운영자 실습이므로 `project-operator`를 동일하게 적용함 → `결국` 03번은 사용자 이름을 Project에 넣는 작업이 아니라 신청 Permission을 실제 Namespace 운영 권한으로 변환하는 단계임

### 핵심 매핑

```text
신청서 Admin
→ project-operator

신청서 User
→ project-viewer

project-admin
→ 별도 더 강한 권한
```

### 강사 대본

> 2번에서는 사용자를 Workspace Member로 넣어서 상위 Workspace 범위에 연결했습니다. 그런데 Workspace Viewer만 가지고는 실제 Project 안의 Application 리소스를 운영하는 권한이 생기지 않습니다. 그래서 3번에서는 같은 사용자를 이번에는 Project Member로 추가하고, 실제 Project 안에서 어떤 작업을 할 수 있는지 Role을 부여합니다.
>
> 여기서 신청서의 Permission하고 KubeSphere Project Role을 연결해서 봐야 합니다. DKS 기준으로 신청서에 Admin이라고 되어 있으면 `project-operator`, User라고 되어 있으면 `project-viewer`로 매핑합니다. 이름만 보면 신청서 Admin이니까 `project-admin`을 줘야 할 것처럼 보일 수 있는데 그렇게 매핑하지 않습니다. 이 부분이 실제 운영에서 가장 헷갈리기 쉬운 지점입니다.
>
> `project-viewer`는 말 그대로 Project 리소스를 조회하는 쪽이고, `project-operator`는 Deployment나 Service 같은 Workload뿐 아니라 PVC, ConfigMap, Secret 같은 Project 내부 리소스를 운영할 수 있습니다. 대신 Project Member를 추가하거나 다른 사람의 Role을 바꾸는 권한까지는 없습니다. 그 Member/Role 관리까지 가능한 권한이 `project-admin`이고, 신청서의 일반 Admin보다 더 강한 권한으로 봐야 합니다.
>
> 이번 실습에서는 6명 모두 운영자 실습이기 때문에 같은 기준으로 `project-operator`를 적용합니다. 1번에서 만든 자기 Project를 열고 Project Members에서 2번에 등록했던 같은 AD를 선택한 다음 `project-operator`를 부여하겠습니다. 여기서도 다른 Project나 비슷한 계정을 선택하지 않는지만 확인하면 됩니다.
>
> 마지막에는 Project Members 목록에서 자기 AD가 있고 Role이 `project-operator`인지 확인합니다. 여기까지 끝나면 Workspace에서는 Viewer, Project에서는 Operator가 각각 존재하게 됩니다. 이 두 Role은 중복되거나 충돌하는 게 아니라 서로 다른 범위의 권한입니다. 다음 4번에서는 이 권한과 별개로 실제로 사용할 수 있는 CPU, Memory, Storage 양을 Quota로 제한하겠습니다.

## 2. 실제 진행

### 2.1 대상 확인

`admin`으로 로그인한 상태에서 자기 AD 기반 Project를 연다.

예시 AD가 `abcd1234.id`라면:

```text
Project
abcd1234-id-dev

추가할 사용자
abcd1234.id

이번 실습 Role
project-operator
```

주의:
- 02번에서 Workspace Member로 추가한 같은 AD를 사용한다.
- 다른 교육생 Project나 비슷한 계정명을 선택하지 않는다.

---

### 2.2 Project Member + Role 적용

```text
Projects
→ 자기 Project
→ Project Settings
→ Project Members
→ Invite
→ 자기 AD 계정 선택
→ project-operator
→ OK
```

주의:
- 신청서 `Admin`은 `project-admin`이 아니라 `project-operator`다.
- `project-admin`은 Project Member/Role 관리까지 가능한 더 강한 권한이다.

Role 차이는 이 정도만 본다.

| Role | Project 리소스 조회 | Workload/PVC/Secret 운영 | Project Member 관리 |
|---|---:|---:|---:|
| `project-viewer` | O | X | X |
| `project-operator` | O | O | X |
| `project-admin` | O | O | O |

---

### 2.3 바로 확인

Project Members 목록에서 다음만 확인한다.

```text
사용자
= 자기 AD 계정

Project Role
= project-operator
```

완료 기준:

```text
자기 Project
→ 자기 AD Project Member 존재
→ Role = project-operator
```

확인 후 같은 Project를 사용해 04번 Quota 실습으로 넘어간다.
