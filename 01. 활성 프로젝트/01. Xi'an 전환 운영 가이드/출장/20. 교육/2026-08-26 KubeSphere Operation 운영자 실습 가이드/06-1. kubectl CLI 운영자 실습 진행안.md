# kubectl CLI 운영자 실습 진행안

`kubeconfig`는 **kubectl이 어느 Kubernetes Cluster에 어떤 사용자 인증정보로 접속할지 알려주는 설정 파일**이다. 안에는 API Server 주소, 사용자 인증서/키, Cluster와 사용자를 연결하는 context 정보 등이 들어 있다. 쉽게 보면 **kubectl 접속정보를 한 파일에 묶어 둔 것**이다.

## 실제 진행 순서

| 순서 | 강사가 시연할 내용 | 교육생이 할 일 | 확인 기준 | 권장 시간 |
|---|---|---|---|---:|
| 1 | VM/Bastion 접속과 사용자별 ConfigMap 위치 | 자기 환경 접속, 자기 ConfigMap 확인 | `kubeconfig-[자기 AD]` 존재 | 3~5분 |
| 2 | ConfigMap의 `config` 추출 | 자기 config 파일 생성 | kubeconfig YAML 추출 | 4~6분 |
| 3 | kubeconfig에서 바꿀 5개 위치 설명 | DEV 값으로 config 수정 | server / cluster / context 값 일치 | 6~8분 |
| 4 | 교육용 kubeconfig 배치 | 파일 복사, `KUBECONFIG` 적용 | 교육용 파일 사용 | 3~5분 |
| 5 | API Server와 자기 Project 접근 확인 | DEV API / 자기 Project 조회 | VIP-A + Project 접근 정상 | 4~6분 |
| 6 | 교육용 파일 정리 | 실습 파일 삭제 | 정리 완료 | 2~3분 |

정상 진행 기준 약 **25~35분**으로 본다. 한 단계씩 6명 모두 끝난 것을 확인하고 다음 단계로 이동한다.

## 1. 먼저 한 줄로 연결한다

`일단` 사용자별 kubectl 접근을 위해서는 자기 AD 계정에 맞는 kubeconfig가 필요함 → `그래서` `kubeconfig-[AD]` ConfigMap에서 사용자 config를 추출함 → `그런데` 추출한 config의 API Server·Cluster·Context가 Xi'an DEV 기준과 맞지 않으면 다른 Cluster를 보거나 정상 접속할 수 없음 → `따라서` API Server VIP-A `109.156.25.72:6443`, Cluster `dev-apps-pa01-xas`, Context `[AD]@dev-apps-pa01-xas` 기준으로 값을 맞추고 해당 kubeconfig를 사용하도록 적용함 → `마지막으로` API Server가 올바른지 확인한 뒤 자기 Project가 정상 조회되는지 확인함 → `결국` 06번은 kubeconfig를 처음부터 작성하는 작업이 아니라 사전 준비된 사용자 config를 Xi'an DEV 접속정보에 맞게 정리하고 실제 kubectl 접근까지 확인하는 절차임

### 전체 경로

```text
자기 AD
→ kubeconfig-[AD] ConfigMap 확인
→ config 추출
→ DEV API Server / Cluster / Context 수정
→ kubeconfig 적용
→ API Server 확인
→ 자기 Project 조회
```

### 강사 대본

> 앞에서는 KubeSphere Web 화면에서 사용자와 권한을 설정했습니다. 6번에서는 같은 사용자가 이번에는 `kubectl`로 Kubernetes API에 접근할 수 있도록 사용자별 kubeconfig를 준비하는 절차를 보겠습니다. kubeconfig는 `kubectl`이 어느 Cluster에 어떤 사용자 인증정보로 접속할지를 알려주는 설정 파일입니다. 쉽게 말하면 사용자별 Kubernetes 접속정보라고 보면 됩니다.
>
> 이 kubeconfig를 오늘 처음부터 만드는 건 아닙니다. 사용자별로 이미 `kubeconfig-[AD]` 형식의 ConfigMap이 준비되어 있고, 그 ConfigMap 안에 `config`라는 데이터가 들어 있습니다. 먼저 자기 AD가 맞는 ConfigMap을 찾고, 그 안의 `config` 값만 파일로 추출합니다. 다른 사용자의 ConfigMap을 가져오면 인증정보 자체가 달라지기 때문에 첫 단계에서 AD를 정확하게 보는 게 중요합니다.
>
> 추출한 config는 그대로 쓰는 게 아니라 Xi'an DEV 환경에 맞게 접속정보를 확인하고 정리합니다. 실제 API Server는 `109.156.25.72:6443`, Cluster 이름은 `dev-apps-pa01-xas`, Context는 자기 AD에 `@dev-apps-pa01-xas`를 붙인 형태로 맞춥니다. 여기서 Cluster 이름은 `clusters[].name`하고 `contexts[].context.cluster`가 서로 연결되고, Context 이름은 `contexts[].name`하고 `current-context`가 서로 연결된다는 정도만 기억하면 됩니다.
>
> 반대로 인증서나 키는 건드리지 않습니다. `certificate-authority-data`, `client-certificate-data`, `client-key-data` 같은 값은 ConfigMap에서 추출한 사용자 인증정보이기 때문에 그대로 유지합니다. Cluster 이름이나 Context를 바꾼다고 인증서까지 새로 만드는 작업이 아닙니다. 접속 대상과 Context 연결정보를 DEV 기준으로 맞추는 작업입니다.
>
> 수정한 뒤에는 기존 기본 kubeconfig를 덮어쓰지 않고 교육용 파일로 따로 배치해서 `KUBECONFIG`로 사용합니다. 그다음 실제로 어떤 API Server를 보고 있는지 확인해서 `https://109.156.25.72:6443`이 나오는지 보고, 자기 Project에서 `kubectl` 명령이 정상 수행되는지 확인합니다. `kubectl get all` 결과가 비어 있어도 오류 없이 조회가 되면 접근 자체는 된 겁니다.
>
> `kubectl auth can-i`도 같이 볼 텐데, 이건 이번 사용자 kubeconfig로 API 접근과 권한 경로가 정상인지 확인하는 용도로 보겠습니다. 교육 계정에 별도 권한이 더 붙어 있다면 결과 하나만 가지고 `project-operator` 단독 권한을 증명한다고 해석하지는 않습니다. 결국 6번의 완료 기준은 자기 AD의 kubeconfig를 사용하고, DEV API Server를 보고 있고, 자기 Project가 정상 조회되는지까지입니다. 실습이 끝나면 교육용 kubeconfig 파일과 실습 중 직접 만든 로컬 OS 계정만 정리합니다.

## 2. 실제 진행

아래 명령은 AD가 `dj2.kim`, Project가 `dj2-kim-dev`인 경우의 예시다. 교육생은 자기 AD와 자기 Project 이름으로 바꿔 실행한다.

공통 DEV 값:

| 항목 | 값 |
|---|---|
| Cluster | `dev-apps-pa01-xas` |
| API Server | `https://109.156.25.72:6443` |
| ConfigMap Namespace | `kubesphere-controls-system` |

---

### 2.1 자기 kubeconfig ConfigMap 확인

ConfigMap 이름:

```text
kubeconfig-dj2.kim
```

교육 시작 전에 준비된 기존 운영 kubectl 환경에서 확인한다.

```bash
kubectl get -n kubesphere-controls-system configmap kubeconfig-dj2.kim
```

주의:
- 반드시 자기 AD의 ConfigMap을 사용한다.
- 여기서는 새 kubeconfig를 생성하는 것이 아니라 이미 준비된 사용자 config를 꺼내는 것이다.

---

### 2.2 config 추출

```bash
mkdir -p "$HOME/ksop-260826/dj2.kim"
cd "$HOME/ksop-260826/dj2.kim"

kubectl get configmap kubeconfig-dj2.kim \
  -n kubesphere-controls-system \
  -o jsonpath='{.data.config}' > config
```

확인:

```bash
ls -l config
```

`kubectl describe ... > config` 출력 전체를 kubeconfig로 사용하지 않는다. `config` key 데이터만 추출한다.

---

### 2.3 kubeconfig 수정

```bash
vi config
```

복사해 온 kubeconfig에서 **아무 `name`이나 바꾸는 것이 아니다.** 아래 위치를 구분해서 수정한다.

| YAML 위치 | 들어갈 값 | 관계 |
|---|---|---|
| `clusters[].cluster.server` | `https://109.156.25.72:6443` | 실제 DEV API |
| `clusters[].name` | `dev-apps-pa01-xas` | 아래 `contexts[].context.cluster`와 같아야 함 |
| `contexts[].context.cluster` | `dev-apps-pa01-xas` | 위 Cluster 이름 참조 |
| `contexts[].name` | `dj2.kim@dev-apps-pa01-xas` | 아래 `current-context`와 같아야 함 |
| `current-context` | `dj2.kim@dev-apps-pa01-xas` | 사용할 context 선택 |

수정하지 않는 값:

```text
certificate-authority-data
client-certificate-data
client-key-data
contexts[].context.user
users[].name
```

이 값들은 ConfigMap에서 추출한 기존 사용자 인증정보를 유지한다.

구조 예:

```yaml
apiVersion: v1
clusters:
- cluster:
    certificate-authority-data: <기존 값 유지>
    server: https://109.156.25.72:6443
  name: dev-apps-pa01-xas
contexts:
- context:
    cluster: dev-apps-pa01-xas
    namespace: default
    user: dj2.kim
  name: dj2.kim@dev-apps-pa01-xas
current-context: dj2.kim@dev-apps-pa01-xas
kind: Config
users:
- name: dj2.kim
  user:
    client-certificate-data: <기존 값 유지>
    client-key-data: <기존 값 유지>
```

여기서 특히 확인할 두 쌍:

```text
clusters[].name
= contexts[].context.cluster

dj2.kim@dev-apps-pa01-xas
= contexts[].name
= current-context
```

---

### 2.4 교육용 kubeconfig 배치

```bash
mkdir -p "$HOME/.kube"
cp config "$HOME/.kube/config-ksop-260826"
chmod 600 "$HOME/.kube/config-ksop-260826"
export KUBECONFIG="$HOME/.kube/config-ksop-260826"
```

기존 기본 kubeconfig를 덮어쓰지 않고 교육용 파일을 별도로 사용한다.

---

### 2.5 API Server와 자기 Project 확인

API Server 확인:

```bash
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}{"\n"}'
```

정상값:

```text
https://109.156.25.72:6443
```

자기 Project 접근 확인:

```bash
kubectl auth can-i get pods -n dj2-kim-dev
kubectl auth can-i create deployments.apps -n dj2-kim-dev
kubectl get all -n dj2-kim-dev
```

확인:

```text
API Server
= https://109.156.25.72:6443

Project
= dj2-kim-dev

kubectl get all
= 명령 정상 수행
```

`kubectl get all` 결과가 비어 있어도 명령 자체가 정상 수행되면 Project 접근은 확인된 것이다.

`auth can-i`는 사용자 kubeconfig 접근 경로 확인용으로 본다. 교육 계정에 추가 권한이 있다면 결과를 `project-operator` 단독 권한 증명으로 해석하지 않는다.

---

### 2.6 실습 종료 후 정리

예시 AD가 `dj2.kim`인 경우:

```bash
unset KUBECONFIG
rm -f "$HOME/.kube/config-ksop-260826"
rm -rf "$HOME/ksop-260826/dj2.kim"
```

실습 중 Bastion/VM에 `dj2.kim` 로컬 OS 계정을 직접 만들었다면 계정과 홈 디렉터리도 삭제한다.

```bash
sudo userdel -r dj2.kim
getent passwd dj2.kim
```

`getent passwd dj2.kim`에서 아무 결과가 나오지 않으면 로컬 OS 계정 삭제가 완료된 것이다.

이 명령은 CyberArk/AD 계정 자체를 삭제하는 것이 아니라 **Bastion/VM에 직접 만든 로컬 OS 계정만 삭제**한다.
