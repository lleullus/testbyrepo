# KubeSphere CA ConfigMap 인수인계 진행안

## 실제 진행 순서

| 순서 | 강사가 시연할 내용 | 교육생이 볼 것 | 확인 기준 | 권장 시간 |
|---|---|---|---|---:|
| 1 | `x509`와 `unauthorized` 구분 | 오류별 확인 대상 구분 | CA / 권한 문제 구분 | 2분 |
| 2 | 현재 Xi'an T2 CA 기준 | `secds-t2-ca`와 CA chain 확인 | Issuing + Root 구성 | 3분 |
| 3 | DEV CA ConfigMap 조회 | `kubesphere-system`의 현재 ConfigMap 확인 | 이름 / `ca.crt` 확인 | 3~5분 |
| 4 | `ks-apiserver` Volume / VolumeMount / Pod 조회 | 현재 Mount 상태 확인 | ConfigMap 참조 + Pod 정상 | 5~7분 |
| 5 | 실제 변경 작업의 완료 순서 설명 | 최신 작업계획과 대조 | DEV 검증 후 PRD | 3분 |

약 **15~20분**으로 진행한다. 교육에서는 공용 `ks-apiserver` 설정을 변경하지 않고 조회만 한다.

Harbor 연동에서 x509 오류가 발생했을 때, ks-apiserver가 Harbor 인증서의 CA 체인을 신뢰할 수 있도록 CA 인증서를 ConfigMap으로 준비해 ks-apiserver에 Volume/VolumeMount로 연결하고, 변경 후 Pod가 정상 기동되는지 확인한 다음 실제 Harbor Image/Registry 기능까지 다시 테스트해서 인증서 신뢰 문제가 해결됐는지 확인하는 절차입니다.
## 1. 먼저 한 줄로 연결한다

`일단` KubeSphere에서 Harbor Image를 조회하거나 입력할 때 `x509: certificate signed by unknown authority`가 발생하면 계정 비밀번호 문제와 같은 오류로 보면 안 됨 → `이 오류는` Member Cluster의 `ks-apiserver`가 Harbor 인증서 체인을 신뢰하지 못하는지 확인하는 출발점임 → `기존 가이드는` 사내 CA를 ConfigMap으로 만들고 `ks-apiserver`에 Mount하는 구조를 사용함 → `현재 Xi'an에서는` Harbor 체인이 `SECDS-T2IssuingCA → SECDS-T2ROOTCA`이므로 신규 `secds-t2-ca` bundle을 추가 Mount하는 계획이 최신 기준임 → `하지만` ConfigMap이 존재하는 것만으로 CA 적용이 끝난 것은 아님 → `Volume → VolumeMount → Pod Ready → Harbor 기능 재검증`까지 이어져야 함 → `결국` 07번은 CA 파일 붙여넣기 절차가 아니라 x509 증상에서 실제 trust 적용과 기능 검증까지 이어지는 운영 경로를 인계하는 단계임

### 강사 대본

> 마지막 7번은 실제로 설정을 바꾸는 실습이라기보다, Harbor 연동에서 인증서 오류가 났을 때 어디를 봐야 하는지 운영 경로를 인계하는 파트입니다. 먼저 `x509: certificate signed by unknown authority`하고 `unauthorized`를 구분해야 합니다. 둘 다 Harbor에서 뭔가 안 되는 것처럼 보이지만 원인이 완전히 다릅니다.
>
> CA는 Certificate Authority, 즉 인증서를 발급하고 서명하는 인증기관입니다. 서버가 자기 인증서를 보여주면 클라이언트는 그 인증서가 내가 신뢰하는 CA까지 정상적으로 이어지는지를 확인합니다. X.509는 이런 서버 인증서와 CA 인증서의 형식과 검증 방식을 정의한 표준입니다. 그래서 `x509: certificate signed by unknown authority`가 나온다는 것은 비밀번호가 틀렸다는 뜻이 아니라, 현재 통신하는 프로세스가 서버 인증서를 서명한 CA를 신뢰하지 못하고 있다는 의미로 먼저 봐야 합니다.
>
> 이번 Xi'an 사례에서는 KubeSphere의 `ks-apiserver`가 Harbor인 `xa.dcr.dks.samsungds.net`의 인증서 체인을 검증할 때 필요한 CA를 신뢰할 수 있어야 합니다. 현재 Harbor 인증서 체인은 `SECDS-T2IssuingCA`를 거쳐 `SECDS-T2ROOTCA`로 이어지고, 최신 작업계획에서는 이 두 CA를 하나의 bundle로 만들어 신규 `secds-t2-ca` ConfigMap의 `ca.crt`에 넣고 `ks-apiserver`에 추가 Mount하는 방식입니다.
>
> 여기서 기존 `secds-rootca`를 새 CA라고 생각해서 덮어쓰면 안 됩니다. 현재 계획은 기존 것을 유지하고 신규 `secds-t2-ca`를 추가하는 겁니다. 적용 대상도 Host가 아니라 Member Cluster이고, DEV에서 먼저 적용하고 기능 검증이 끝난 다음 PRD로 가는 순서입니다. 오늘 교육에서는 공용 `ks-apiserver`를 6명이 직접 수정하지 않고 이 구조가 실제로 어디에 연결돼 있는지만 조회합니다.
>
> 확인 순서는 ConfigMap부터 봅니다. `kubesphere-system` Namespace에서 대상 CA ConfigMap이 있는지, key가 `ca.crt`인지 확인합니다. 그런데 ConfigMap이 존재한다고 끝난 건 아닙니다. 그 ConfigMap을 참조하는 Volume이 있어야 하고, 그 Volume이 `ks-apiserver` Container에 VolumeMount로 실제 연결돼 있어야 합니다. 그리고 변경 작업이었다면 Rollout 이후 새 Pod가 Ready 상태인지도 봐야 합니다.
>
> 마지막은 기능 검증입니다. Pod가 Ready라고 해서 인증서 문제가 해결됐다고 단정하지 않습니다. 실제 Harbor Image 입력이나 Registry 기능을 다시 수행해서 x509가 사라졌는지 봐야 합니다. 만약 x509는 없어졌는데 `unauthorized`가 나온다면 그때는 CA 문제가 아니라 Harbor 계정, Project, Role 같은 인증·권한 문제로 분리해서 봅니다.
>
> 그래서 실제 변경 작업의 완료 순서는 승인된 CA 확인, 기존 설정 백업, `secds-t2-ca` ConfigMap 확인, Volume, VolumeMount, Rollout과 Pod Ready, 마지막 Harbor 기능 재검증까지입니다. 7번에서는 이 전체 연결을 이해하고, 실제 변경이 필요할 때는 교육 문서가 아니라 최신 T2 CA 적용 작업계획서를 기준으로 진행하면 됩니다.

## 2. 실제 확인

### 2.1 오류 구분

`CA(Certificate Authority)`는 서버 인증서가 믿을 수 있는 인증서인지 확인할 때 기준이 되는 **인증서 발급·서명 기관**이다. 클라이언트는 서버 인증서가 자신이 신뢰하는 CA까지 정상적으로 이어지는지 확인한 뒤 인증서를 신뢰한다.

`X.509`는 서버 인증서와 CA 인증서 같은 **디지털 인증서의 형식과 검증 방식을 정의한 표준**이다. Kubernetes나 Harbor 통신에서 `x509` 오류가 보인다는 것은 보통 인증서를 검증하는 과정에서 **신뢰할 수 있는 CA까지 인증서 체인을 연결하지 못했다**는 뜻이다.

```text
x509: certificate signed by unknown authority
→ 서버 인증서를 서명한 CA를 신뢰하지 못함
→ CA Trust 경로 확인

unauthorized
→ 인증서 신뢰 문제가 아니라 인증/권한 문제
→ Harbor 계정 / Project / Role 확인
```

이번 Xi'an 사례에서 보는 대상은 Member Cluster의 `ks-apiserver`가 Harbor 인증서 체인을 신뢰하는지 여부다.

---

### 2.2 현재 Xi'an T2 CA 기준

Harbor:

```text
xa.dcr.dks.samsungds.net
```

CA chain:

```text
Harbor Server Certificate
→ SECDS-T2IssuingCA
→ SECDS-T2ROOTCA
```

현재 작업계획:

```text
SECDS-T2IssuingCA
+ SECDS-T2ROOTCA
        ↓
secds-t2-ca / ca.crt
        ↓
ks-apiserver에 추가 Mount
```

주의:
- 기존 `secds-rootca`를 덮어쓰지 않는다.
- DEV에 먼저 적용·검증한 뒤 PRD에 적용한다.
- Host Cluster는 작업 대상에서 제외한다.

실제 변경이 필요하면 교육 문서가 아니라 최신 작업계획을 기준으로 한다.

### 2.3 CA ConfigMap 확인

조회 대상은 DEV Member `dev-apps-pa01-xas`다.

```text
Platform
→ Cluster Management
→ dev-apps-pa01-xas
→ Configuration
→ ConfigMaps
→ Namespace: kubesphere-system
```

확인:

```text
secds-rootca 존재 여부
secds-t2-ca 존재 여부
대상 ConfigMap의 key = ca.crt
```

ConfigMap이 존재한다고 바로 적용 완료로 보지 않는다. 다음 단계에서 `ks-apiserver`에 실제 연결됐는지 확인한다.

---

### 2.4 ks-apiserver Mount와 Pod 확인

```text
Platform
→ Cluster Management
→ dev-apps-pa01-xas
→ Application Workloads
→ Workloads
→ ks-apiserver
→ Volumes / Mounts
```

확인할 것:

```text
Volume
→ 대상 CA ConfigMap 참조

VolumeMount
→ ks-apiserver Container에 연결

Mount Path
→ 현재 운영 설정과 일치

Pod
→ Ready
```

관계는 이렇게 본다.

```text
ConfigMap 존재
→ Volume 참조
→ VolumeMount 연결
→ ks-apiserver Pod 정상
```

ConfigMap만 있고 VolumeMount가 없으면 `ks-apiserver` trust에 사용되고 있다고 볼 수 없다.

---

### 2.5 실제 변경 작업의 완료 순서

교육에서는 변경하지 않는다. 실제 작업 시 완료 순서만 인계한다.

```text
승인된 CA 확인
→ 기존 ks-apiserver 설정 백업
→ 신규 secds-t2-ca ConfigMap 생성/확인
→ Volume 확인
→ VolumeMount 확인
→ Rollout / 새 Pod Ready
→ Harbor Image 입력 또는 Registry 기능 재검증
```

최종 기능 확인에서:

```text
x509 계속 발생
→ CA trust 경로 재확인

unauthorized 발생
→ CA가 아니라 Harbor 계정 / Project / Role 확인
```

즉 Pod가 Ready인 것만으로 끝내지 않고 Harbor 기능 재검증까지 한다.
