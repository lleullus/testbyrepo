# 오후 교육 전 사고 보조 체크

> [!important] 지금 시점의 목적
> 자료를 더 만드는 것보다, 오후에 실제로 막힐 지점을 먼저 없앤다. 01~05 흐름은 이미 확인했고, 지금 남은 시간은 **교육자료 보강보다 현장에서 안 막히게 만드는 시간**으로 쓴다.

## 1. 지금 상황을 한 줄로 잡는다

```text
오후 교육 내용은 대체로 준비됨
→ 01~05 흐름은 이미 확인
→ 06 kubectl이 실제 실행 변수와 실수 포인트가 가장 많음
→ 지금 남은 시간은 "교육자료 보강"보다 "현장에서 안 막히게 만드는 시간"
```

지금 컴퓨터 앞에서 첫 행동은 문서를 처음부터 다시 읽는 것이 아니다.

---

## 2. 지금 가장 먼저 확인할 질문

오후에 6명이 동시에 06번을 한다고 생각하고 이것만 본다.

> **내가 지금 교육생 자리 하나라고 가정했을 때, 06번을 처음부터 끝까지 실제로 실행할 수 있는가?**

여기에 `YES`가 나오게 만드는 것이 오전 점검의 첫 목표다.

---

## 3. 첫 출발 — 06번을 실제로 한 번 끝까지 돌려본다

[[06-1. kubectl CLI 운영자 실습 진행안]]을 열고, 읽는 데서 끝내지 말고 **실제로 한 사람 분량을 직접 수행**한다.

```text
AD 확인
↓
kubeconfig-[AD] ConfigMap 존재 확인
↓
config 추출
↓
config 내용 확인/수정
↓
교육용 kubeconfig 적용
↓
current-context 확인
↓
API Server 확인
↓
자기 Project 조회
```

여기서 중요한 것은 단순히 성공 여부가 아니라 **각 단계에서 오후에 6명이 어디서 틀릴지를 표시하는 것**이다.

예:

```text
ConfigMap 이름에서 막힘
→ 오후 설명에 "AD 그대로 들어간다" 한 줄 필요

config 추출에서 헷갈림
→ 명령 직후 파일 내용 확인 한 줄 필요

server만 바꾸기 쉬움
→ cluster/context/current-context 같이 보라고 표시

KUBECONFIG 적용 후 헷갈림
→ current-context를 바로 확인하도록 진행

Project 이름 입력에서 실수 가능
→ 자기 AD 기반 Project 이름 확인 후 실행
```

실제로 걸리는 부분만 표시한다.

---

## 4. 그다음은 6명 동시 진행 가능 여부를 본다

혼자 되는 것과 6명이 동시에 되는 것은 다르다.

```text
6명 AD 계정 준비됐나
6명 kubeconfig ConfigMap 있나
6명 VM/Bastion 접근 되나
04에서 사용할 기존 운영 context 준비됐나
06에서 자기 config를 각자 별도로 다룰 수 있나
6명 Project 이름을 바로 알 수 있나
```

특히 오후에 교육생을 앉혀 놓고 확인하면 안 되는 것은 다음과 같다.

- 계정 자체가 없음
- ConfigMap이 없음
- Bastion 접속 안 됨
- 권한 때문에 ConfigMap 조회 안 됨
- API VIP 접근 안 됨

설명 실수는 현장에서 고칠 수 있지만 **환경 미준비는 교육 자체를 멈춘다.**

---

## 5. 그다음 01~05는 재학습하지 말고 연결만 확인한다

06을 한 번 실제로 돌린 다음 01~05를 본다.

각 문서에서는 딱 두 가지만 확인한다.

```text
① 실제 진행 순서가 자연스러운가
② 다음 문서로 무엇을 넘기는가
```

연결은 다음 정도면 충분하다.

```text
01
Workspace / Project 생성
→ 02로 넘김

02
Workspace Member
→ 03로 넘김

03
Project Role
→ 04로 넘김

04
Quota
→ 완료

05
지금 한 Role 관계 정리

06
kubectl 사용자 설정

07
CA ConfigMap 현재 상태 조회 / 인수인계
```

문장을 예쁘게 만들기 위해 다시 손대기 시작하지 않는다. **오후에 이 순서대로 진행할 수 있으면 통과**다.

---

## 6. 강사용 진행 체크 한 장

교육 중에는 다음 체크만 보고 현재 위치를 놓치지 않는다.

```text
01 Workspace / Project
□ 설명
□ 시연
□ 6명 완료

02 Workspace Member
□ 설명
□ 시연
□ 6명 완료

03 Project Role
□ 설명
□ 시연
□ 6명 완료

04 Quota
□ 공통값 확인
□ Workspace
□ Project
□ Storage ResourceQuota
□ 6명 완료

05 RBAC
□ 3계층
□ Admin → operator
□ Role ≠ Quota

06 kubectl
□ AD
□ ConfigMap
□ config 추출
□ DEV 값 수정
□ KUBECONFIG
□ context/server
□ 자기 Project
□ 6명 완료

07 CA
□ 조회/설명만
```

## 7. 지금 당장 실행 순서

```text
1. 06번 문서를 연다.

2. 실제 교육생 1명이라고 생각하고
   처음부터 끝까지 직접 수행한다.

3. 수행하면서
   "여기서 6명이 틀리겠다" 싶은 곳에만 표시한다.

4. 6명 환경 사전조건을 확인한다.

5. 04도 CLI 작업이 있으니
   ResourceQuota 적용 직전까지 한 번 확인한다.

6. 01→02→03→04→05→06→07의
   상단 '실제 진행 순서'만 연속으로 훑는다.

7. 이후에는 내용 추가를 멈춘다.
```

---

## 8. 지금 판단의 핵심

현재 가장 위험한 것은 **교육 설명을 충분히 준비하지 못한 것**이 아니다.

오히려 다음과 같은 실제 환경 문제다.

```text
ConfigMap이 안 보인다
context가 다르다
권한이 없다
Project 이름이 안 맞는다
6명 중 한 명만 진행이 안 된다
```

따라서 오전 점검의 목적은 다음 한 줄로 잡는다.

> **오후 내용을 더 풍부하게 만드는 것보다, 오후에 실제로 멈출 가능성을 하나씩 제거한다.**
