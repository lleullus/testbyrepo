# KubeSphere RBAC 인수인계 진행안

## 실제 진행 순서

| 순서 | 강사가 설명할 내용 | 교육생이 볼 것 | 확인 기준 | 권장 시간 |
|---|---|---|---|---:|
| 1 | Platform / Workspace / Project 3계층 | 앞에서 적용한 Role 위치 확인 | 범위 구분 | 3분 |
| 2 | Workspace Role 핵심 차이 | 자기 Workspace Member의 Viewer 확인 | Viewer 위치 확인 | 2분 |
| 3 | Project Role 핵심 차이 | 자기 Project Member의 operator 확인 | operator 위치 확인 | 3분 |
| 4 | 신청서 Admin/User 매핑 | 03 결과와 대조 | Admin → operator | 2분 |
| 5 | RBAC와 Quota 구분 | 04 결과와 연결 | 권한/자원 제한 구분 | 2분 |

약 **10~15분**으로 진행한다. Role 생성 실습은 하지 않는다.

## 1. 먼저 한 줄로 연결한다

`일단` KubeSphere를 여러 사용자와 팀이 함께 쓰면 모두에게 같은 권한을 줄 수 없음 → `그래서` Platform·Workspace·Project 세 범위로 권한을 나눔 → `02번에서는` 사용자를 Workspace Viewer로 상위 범위에 연결했고 → `03번에서는` 같은 사용자에게 Project Operator를 부여해 실제 Namespace 리소스 운영 권한을 만들었음 → `하지만` Role이 맞아도 Quota가 부족하면 생성이 거부될 수 있음 → `결국` 운영자는 문제가 생겼을 때 어느 범위의 Role인지와 자원 제한 문제인지를 분리해서 봐야 함

### 핵심 구조

```text
Platform Role
→ Workspace Role
→ Project Role
```

이번 교육에서는 Role을 새로 만들지 않고 02·03에서 이미 적용한 Role을 기준으로 본다.

### 강사 대본

> 지금까지 한 작업을 RBAC 관점에서 한 번 정리해보겠습니다. 새로운 Role을 만들거나 권한표를 전부 외우는 시간은 아닙니다. 이미 2번하고 3번에서 실제로 Role을 적용했기 때문에, 그 결과가 어느 범위의 권한이었는지만 연결해서 보면 됩니다.
>
> KubeSphere 권한은 크게 Platform, Workspace, Project 세 범위로 나눠서 보면 됩니다. Platform은 전체 KubeSphere와 Workspace를 관리하는 가장 상위 범위입니다. Workspace는 그 아래에서 Project와 Workspace Member를 관리하는 범위이고, Project는 실제 Kubernetes Namespace 내부의 Workload나 Storage, ConfigMap, Secret 같은 리소스를 다루는 범위입니다. 같은 사용자라도 어느 범위의 Role을 받았느냐에 따라 할 수 있는 일이 달라집니다.
>
> 2번에서 우리는 자기 AD를 Workspace Member로 넣고 Viewer를 줬습니다. 이건 사용자를 Workspace 범위에 포함시키고 그 Workspace를 볼 수 있게 한 겁니다. 3번에서는 같은 AD를 Project Member로 넣고 `project-operator`를 줬습니다. 이건 실제 Namespace 안의 Application 리소스를 운영할 수 있게 한 겁니다. 그러니까 Workspace Viewer와 Project Operator는 둘 중 하나를 고르는 관계가 아니라 각각 다른 범위에서 같이 존재하는 권한입니다.
>
> Project Role은 세 개만 구분하면 됩니다. `project-viewer`는 조회, `project-operator`는 Project 리소스 운영, `project-admin`은 거기에 Project Member와 Role 관리까지 포함합니다. 그래서 신청서 Admin은 `project-admin`이 아니라 `project-operator`로 매핑합니다. 신청서 User는 `project-viewer`입니다. 운영 중에 Operator 계정으로 Member 관리가 안 된다고 해서 권한이 잘못됐다고 보면 안 됩니다. 그건 원래 Admin 범위입니다.
>
> 그리고 RBAC하고 Quota도 반드시 분리해서 봐야 합니다. Role은 '무엇을 할 수 있는가'이고 Quota는 '얼마나 사용할 수 있는가'입니다. 예를 들어 Role은 정상인데 CPU나 Memory Quota가 부족하면 리소스 생성이 거부될 수 있습니다. 반대로 Quota가 충분해도 Role이 없으면 생성이나 수정 자체가 허용되지 않습니다.
>
> 그래서 실제 운영 중 권한 문제처럼 보이는 상황이 나오면 무조건 상위 권한부터 올리는 게 아니라, 먼저 대상 Workspace와 Project가 맞는지 보고, Workspace Member인지, Project Member인지, Project Role이 무엇인지 확인합니다. Role이 신청 내용과 맞다면 그다음 Quota 같은 다른 제한을 보는 식으로 분리해서 확인하면 됩니다. 5번에서 가져갈 건 Role 이름 암기가 아니라 이 범위를 구분해서 보는 방식입니다.

## 2. 실제 확인

### 2.1 세 범위 구분

| 범위 | 무엇을 관리하는가 | 대표 Role |
|---|---|---|
| Platform | 전체 플랫폼 / Workspace 생성·관리 | `platform-admin`, `platform-regular` |
| Workspace | Workspace / Project / Workspace Member | `ws-admin`, `ws-viewer` |
| Project | Namespace 내부 Workload / Storage / Config | `project-admin`, `project-operator`, `project-viewer` |

Workspace 쪽은 이번 교육에서 다음 정도만 본다.

```text
ws-viewer
= Workspace 조회

ws-admin
= Workspace / Project / Member 관리

ws-self-provisioner
= DKS 미사용
```

---

### 2.2 Workspace Role 확인

02번에서 만든 결과를 다시 연다.

```text
Workbench
→ Workspaces
→ 자기 Workspace
→ Workspace Settings
→ Workspace Members
```

확인:

```text
자기 AD
→ Viewer
```

Workspace Viewer 자체가 Project Workload 운영 권한은 아니다.

---

### 2.3 Project Role 확인

03번에서 만든 결과를 연다.

```text
Projects
→ 자기 Project
→ Project Settings
→ Project Members
```

확인:

```text
자기 AD
→ project-operator
```

Project Role 차이는 이것만 본다.

| 기능 | project-viewer | project-operator | project-admin |
|---|---:|---:|---:|
| 조회 | O | O | O |
| Workload / PVC / ConfigMap / Secret 운영 | X | O | O |
| Project Member 관리 | X | X | O |

신청서 매핑:

```text
신청서 Admin
→ project-operator

신청서 User
→ project-viewer

신청서 Admin
≠ project-admin
```

---

### 2.4 RBAC와 Quota 구분

```text
Role
= 무엇을 할 수 있는가

Quota
= 얼마나 사용할 수 있는가
```

문제가 생기면 다음 순서로 본다.

```text
대상 Workspace / Project가 맞는가
→ Workspace Member가 맞는가
→ Project Member / Role이 맞는가
→ Role이 맞으면 Quota 등 다른 제한을 확인
```

`project-operator`인데 Project Member 관리가 안 되는 것은 정상이다. Member 관리는 `project-admin` 범위다.
