# 2.2 Taint와 Node Label 강사용 전체 대본

> [!important] 사용 방법
> 수강생이 Label, Taint, nodeSelector와 Toleration을 처음 본다고 가정한다. YAML부터 읽지 않는다. **왜 전용 Worker가 필요한지 → Node를 어떻게 표시하고 보호하는지 → Pod가 어떻게 선택하고 통과하는지 → 실제 배치를 무엇으로 판단하는지** 순서로 설명한다.

## 0. 강사가 들고 갈 설명 공식

```text
전용 공간이 필요한 이유
→ Node 쪽 표시와 제한
→ Pod 쪽 선택과 허용
→ Kubespray Inventory
→ 실제 Node와 Workload 비교
```

## 0-1. 오늘 전체 한 줄

```text
특정 Team 전용 Worker가 필요하다
→ Label로 Node를 표시한다
→ Taint로 일반 Pod를 막는다
→ nodeSelector로 전용 Node를 선택한다
→ Toleration으로 Taint를 통과한다
```

---

# 1. 시작 — Node 이름만으로는 전용 공간이 되지 않는다

> 앞에서 Kubespray로 일반 Worker를 Cluster에 추가하는 흐름을 봤습니다.
>
> 이번에는 특정 Team만 사용할 Worker가 필요하다고 하겠습니다.
>
> 운영자가 `xadkswkmp03`, `xadkswkmp04`를 DSCMP Team 전용이라고 알고 있어도 Kubernetes Scheduler는 사람의 의도를 읽지 못합니다.
>
> **그래서**, Node에는 어떤 용도의 공간인지 표시하고, 일반 Pod가 함부로 들어오지 못하게 제한해야 합니다.
>
> Pod 쪽에서도 어느 Node를 원하는지와 그 제한을 통과할 자격이 있는지 선언해야 합니다.

## 1.1 선택과 통과를 먼저 구분한다

> 전용 Worker 배치는 두 질문으로 나누면 쉽습니다.
>
> 첫 번째는 **이 Pod가 어느 Node를 선택하는가**입니다.
>
> 두 번째는 **선택한 Node의 제한을 통과할 수 있는가**입니다.

> 선택은 `Node Label ↔ Pod nodeSelector`, 통과는 `Node Taint ↔ Pod Toleration`의 관계로 판단합니다.

> Label과 nodeSelector는 선택 조건입니다.
>
> Taint와 Toleration은 배치 제한과 허용 조건입니다.
>
> 네 요소 중 하나만 보지 않고 Node와 Pod 양쪽을 함께 읽어야 합니다.

---

# 2. 먼저 Node에 용도를 표시한다 — Label

> Kubernetes의 **Label**은 Resource에 붙이는 Key와 Value 형태의 표식입니다.
>
> 오늘 사례에서는 신규 Worker 두 대에 `team=dscmp`를 붙여 DSCMP Team용 Node라는 사실을 표시합니다.

| Label | 의미 |
|---|---|
| `node-type=worker` | 일반 Worker 유형 |
| `team=dscmp` | DSCMP Team용 Node |
| `node-role.kubernetes.io/dscmp` | Node Role 표시에 사용하는 Label |

> Label은 Node를 설명하고 Pod가 선택할 조건을 제공합니다.
>
> **하지만**, Label만 붙였다고 일반 Pod가 자동으로 차단되지는 않습니다.
>
> 일반 Pod를 막으려면 Node 쪽에 별도의 배치 제한이 필요합니다.

---

# 3. 일반 Pod를 막는다 — Taint

> Node가 특정 조건을 허용한 Pod만 받도록 만드는 설정이 **Taint**입니다.
>
> 사례에서 사용할 Taint는 다음과 같습니다.

> 사례의 Taint는 `team=dscmp:NoSchedule`입니다.

> 이 한 줄은 세 부분으로 읽습니다.

| 부분 | 값 | 의미 |
|---|---|---|
| Key | `team` | 어떤 조건인지 |
| Value | `dscmp` | 어느 Team 조건인지 |
| Effect | `NoSchedule` | 일치하는 Toleration이 없는 새 Pod를 배치하지 않음 |

## 3.1 Effect 세 가지를 구분한다

| Effect | 의미 |
|---|---|
| `PreferNoSchedule` | 가능하면 해당 Pod를 배치하지 않는 완화된 조건 |
| `NoSchedule` | 일치하는 Toleration이 없는 새 Pod를 배치하지 않음 |
| `NoExecute` | 일치하는 Toleration이 없는 새 Pod를 배치하지 않고 기존 Pod도 제거 대상이 됨 |

> 오늘 사례는 `NoSchedule`입니다.
>
> **따라서**, 이미 실행 중인 Pod를 제거하는 `NoExecute`와 혼동하지 않습니다.
>
> **하지만**, Taint를 통과할 수 있다는 사실만으로 Pod가 이 Node를 반드시 선택하는 것은 아닙니다. 선택 조건은 Pod의 nodeSelector가 담당합니다.

---

# 4. Pod가 전용 Node를 선택한다 — nodeSelector

> Pod가 `team=dscmp` Label을 가진 Node를 선택하려면 Pod Spec에 **nodeSelector**를 넣습니다.

```yaml
nodeSelector:
  kubernetes.io/os: linux
  team: dscmp
  node-type: worker
```

> Scheduler는 세 Label을 모두 만족하는 Node를 후보로 봅니다.
>
> `team=dscmp`가 빠지면 일반 Worker도 후보가 될 수 있습니다.
>
> **하지만**, nodeSelector가 맞아도 대상 Node에는 `team=dscmp:NoSchedule` Taint가 있습니다.
>
> **따라서**, Pod가 그 제한을 허용한다고 따로 선언해야 합니다.

---

# 5. Pod가 Taint를 통과한다 — Toleration

> Pod가 특정 Taint를 허용한다는 선언이 **Toleration**입니다.

```yaml
tolerations:
  - key: team
    value: dscmp
    effect: NoSchedule
```

> Taint의 Key, Value와 Effect가 Pod의 Toleration과 일치합니다.
>
> 이 조건이 맞으면 Pod는 해당 Taint 때문에 배치 후보에서 제외되지 않습니다.
>
> **하지만**, Toleration은 전용 Node를 선택하는 기능이 아닙니다. Taint를 통과할 자격만 제공합니다.

> nodeSelector만 있으면 전용 Node를 선택해도 Taint를 통과하지 못할 수 있습니다.
>
> Toleration만 있으면 Taint를 통과해도 전용 Node를 반드시 선택하지는 않습니다.
>
> 둘을 함께 사용해야 전용 Node를 선택하고 그 Node의 Taint를 통과합니다.

---

# 6. Kubespray Inventory에 전용 Worker 정책을 기록한다

> Node에 Label과 Taint를 수동으로 한 번 붙이는 것으로 끝내면 Inventory와 실제 Cluster 상태가 달라질 수 있습니다.
>
> **그래서**, `hosts.yaml`의 전용 Worker Group에 Host, Label과 Taint를 함께 기록합니다.

> [!example] `worker1_node` 관련 발췌
> 실제 Inventory의 기존 Master·Router·Infra·etcd와 일반 Worker Group은 그대로 유지한다.

> `all.hosts`에는 `xadkswkmp03`·`109.156.22.69`, `xadkswkmp04`·`109.156.22.70`의 신원과 주소를 유지합니다.

```yaml
all:
  children:
    worker1_node:
      hosts:
        xadkswkmp03:
        xadkswkmp04:
      vars:
        node_labels:
          node-type: "worker"
          node-role.kubernetes.io/worker: ""
          node-role.kubernetes.io/dscmp: ""
          team: "dscmp"
        node_taints:
          - "team=dscmp:NoSchedule"
    kube_node:
      children:
        worker1_node:
```

> `all.hosts`에는 신규 Node의 신원과 주소가 있습니다.
>
> `worker1_node`에는 DSCMP 전용 Label과 Taint가 있습니다.
>
> `kube_node`는 이 Group을 Kubernetes Node 집합에 포함합니다.

> [!warning] Manual 화면 판독
> Manual의 `=====` 표시는 변경 위치를 강조한 설명이며 실제 YAML이 아니다.

---

# 7. scale.yml의 대상도 전용 Group이다

> Inventory가 준비되면 Ansible이 `worker1_node` Group을 대상으로 Kubespray의 `scale.yml`을 실행합니다.

> [!warning] 실행 경계
> 기본 교육에서는 읽기 전용으로 설명한다. 실제 실습을 진행할 때는 아래 `# 11`처럼 PRD Worker 두 대 중 한 대에 교육용 Label·`NoSchedule` Taint를 걸고, 두 Deployment의 Scheduling 결과를 비교한 뒤 바로 원복한다. `NoExecute`, Inventory 변경과 `scale.yml`은 이 실습에서 사용하지 않는다.

```bash
ansible-playbook \
  -e @inventory/dks/dks_vars.yml \
  -i inventory/dks/hosts.yaml \
  --become \
  --become-user=root \
  scale.yml \
  --limit "worker1_node"
```

> 2.1의 일반 Worker 추가와 가장 큰 차이는 `--limit` 대상이 Hostname 두 개가 아니라 전용 정책이 들어 있는 `worker1_node` Group이라는 점입니다.
>
> 승인된 전용 Worker, Inventory Group과 `--limit`이 같은 대상을 가리켜야 합니다.

---

# 8. 실제 Node와 Pod 양쪽을 비교한다
> 이제 Inventory의 선언과 실제 Node·Workload가 같은 정책을 사용하는지 읽기 전용으로 비교하겠습니다.


## 8.1 Node 쪽

```bash
kubectl get nodes
kubectl get nodes --show-labels | grep dscmp
kubectl describe node xadkswkmp03
```

> 먼저 `xadkswkmp03`, `xadkswkmp04`가 `Ready`인지 확인합니다.
>
> Label 목록에서 `team=dscmp`, `node-type=worker`, DSCMP Role Label을 찾습니다.
>
> Node 상세 화면의 Taints에서 `team=dscmp:NoSchedule`을 찾습니다.

## 8.2 Pod 쪽

> Workload YAML에서는 `nodeSelector`와 `tolerations`를 함께 찾습니다.

```yaml
spec:
  template:
    spec:
      nodeSelector:
        kubernetes.io/os: linux
        team: dscmp
        node-type: worker
      tolerations:
        - key: team
          value: dscmp
          effect: NoSchedule
```

> Node의 Label이 Pod nodeSelector와 일치하는지 확인합니다.
>
> Node의 Taint가 Pod Toleration과 일치하는지 확인합니다.
>
> 마지막으로 기존 실행 Pod의 `NODE`가 DSCMP 전용 Worker인지 읽기 전용으로 확인합니다.

```bash
kubectl get pods -o wide
```

---

# 9. 완료 기준 — 선택과 통과를 함께 설명할 수 있는가

> 완료 판단은 `Inventory의 worker1_node → 실제 Node Label·Taint → Workload nodeSelector·Toleration → Pod의 실제 NODE`를 한 흐름으로 연결하는 것입니다.

> `ROLES`에 `dscmp`가 보이는 것만으로 완료하지 않습니다.
>
> Inventory의 정책이 실제 Node에 적용되고, Workload가 같은 조건을 사용하며, Pod가 의도한 전용 Worker에서 실행되는지까지 연결해야 합니다.
>
> **결국**, Label과 nodeSelector가 전용 Node를 선택하고 Taint와 Toleration이 일반 Pod의 진입을 제한하는 관계를 설명할 수 있어야 합니다.

# 11. KubeSphere 3.2.1 간단 실습 — 같은 Selector, 다른 Toleration

> 맞습니다. PRD Worker 두 대 중 한 대만 교육용 전용 Node로 만들고, 같은 `nodeSelector`를 가진 Deployment 두 개 중 하나에만 Toleration을 주면 차이가 바로 보입니다.

```text
PRD Worker A
- Label: training=dscmp
- Taint: training=dscmp:NoSchedule

PRD Worker B
- 변경 없음

Deployment A
- nodeSelector 있음
- toleration 없음
→ Worker A만 선택되지만 Taint를 통과하지 못해 Pending

Deployment B
- 같은 nodeSelector 있음
- toleration 있음
→ Worker A에 Running
```

> `NoSchedule`은 Worker A에 이미 실행 중인 Pod를 제거하지 않습니다. 다만 실습 중 새로 생성되는 일반 Pod의 배치에는 영향을 줄 수 있으므로 승인된 시간에 진행하고 끝나면 바로 원복합니다. `NoExecute`는 사용하지 않습니다.

## 11.1 Worker A에 Label과 Taint를 건다

```text
Platform
→ Cluster Management
→ PRD Cluster
→ Nodes
→ Cluster Nodes
→ 실습할 Worker A
```

Label:

```text
More
→ Edit Labels
→ Key: training
→ Value: dscmp
→ 저장
```

Taint:

```text
More
→ Edit Taints
→ Key: training
→ Value: dscmp
→ Effect: NoSchedule
→ 저장
```

확인할 현재 상태:

```text
Worker A: training=dscmp / training=dscmp:NoSchedule
Worker B: training=dscmp Label 없음
```

> Worker B에는 같은 Label을 붙이지 않습니다. 그래야 두 Deployment의 유일한 Label 후보가 Worker A가 됩니다.

## 11.2 Deployment A — Selector만 넣는다

```text
Workbench
→ 승인된 Workspace
→ 승인된 PRD 교육용 Project
→ Application Workloads
→ Workloads
→ Deployments
→ Create
→ Edit YAML
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taint-selector-only
spec:
  replicas: 1
  selector:
    matchLabels:
      app: taint-selector-only
  template:
    metadata:
      labels:
        app: taint-selector-only
    spec:
      nodeSelector:
        training: dscmp
      containers:
        - name: nginx
          image: xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

예상 결과:

```text
nodeSelector가 Worker A를 선택
→ Worker A의 NoSchedule Taint를 허용하지 못함
→ Pod Pending
```

Deployment 상세에서 확인합니다.

```text
Resource Status
→ Pods
→ Pending Pod
→ Events
```

Event에서 `untolerated taint` 또는 해당 Taint를 허용하지 않았다는 `FailedScheduling` 원인을 찾습니다.

## 11.3 Deployment B — 같은 Selector에 Toleration을 추가한다

같은 Project에서 두 번째 Deployment를 생성합니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taint-selector-toleration
spec:
  replicas: 1
  selector:
    matchLabels:
      app: taint-selector-toleration
  template:
    metadata:
      labels:
        app: taint-selector-toleration
    spec:
      nodeSelector:
        training: dscmp
      tolerations:
        - key: training
          operator: Equal
          value: dscmp
          effect: NoSchedule
      containers:
        - name: nginx
          image: xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

예상 결과:

```text
nodeSelector가 Worker A를 선택
→ Toleration이 Worker A의 Taint와 일치
→ Pod Running
→ Pod의 Node는 Worker A
```

Deployment 상세의 `Resource Status → Pods`에서 다음을 확인합니다.

```text
STATUS: Running
NODE: Worker A
```

## 11.4 두 결과를 나란히 본다

| Deployment | nodeSelector | toleration | 결과 |
|---|---|---|---|
| `taint-selector-only` | `training=dscmp` | 없음 | `Pending` |
| `taint-selector-toleration` | `training=dscmp` | 있음 | Worker A에서 `Running` |

> 두 Deployment는 Image와 Selector가 같습니다. 결과를 바꾼 차이는 Toleration 하나입니다.
>
> 이 화면으로 `Label·nodeSelector는 선택`, `Taint·Toleration은 통과`라는 관계를 확인합니다.

## 11.5 실습이 끝나면 원복한다

```text
1. 두 Deployment 삭제
2. Pod가 모두 사라졌는지 확인
3. Worker A → More → Edit Labels → training=dscmp 제거
4. Worker A → More → Edit Taints → training=dscmp:NoSchedule 제거
5. Worker A가 Ready이고 변경 전 Label·Taint 상태인지 확인
```

> 이 값은 임시 교육용이므로 Kubespray Inventory에는 넣지 않습니다. 실습 종료 후 Node에 `training=dscmp` Label이나 Taint를 남기지 않습니다.

## 11.6 실습 완료 기준

```text
Deployment A Pending과 FailedScheduling 확인
+ Deployment B Running과 Worker A 배치 확인
+ 두 Deployment 삭제
+ Worker A Label·Taint 원복
=
실습 완료
```
