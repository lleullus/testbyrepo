# 2.1 Worker Node 추가 강사용 전체 대본

> [!important] 사용 방법
> 수강생이 Worker Node와 Kubespray를 처음 본다고 가정한다. 명령과 Inventory를 먼저 읽지 않는다. **왜 실행 공간이 필요한지 → VM이 왜 아직 Worker가 아닌지 → Cluster에 어떻게 합류하는지 → 무엇을 확인해야 실제 사용할 수 있는지** 순서로 설명한다.

## 0. 강사가 들고 갈 설명 공식

```text
문제
→ 필요한 역할
→ 기술 이름
→ Xi'an 사례
→ 작업 화면
→ 실제 결과
```

## 0-1. 오늘 전체 한 줄

```text
Application 실행 공간이 부족하다
→ Worker용 VM을 준비한다
→ Kubespray가 읽을 Inventory에 등록한다
→ scale.yml로 Cluster에 합류시킨다
→ 실제 Workload와 PVC Pod가 신규 Worker에서 실행되는지 확인한다
→ 운영 Inventory까지 맞춘다
```

---

# 1. 시작 — Worker 추가는 서버 대수를 늘리는 작업이 아니다

> 오늘은 기존 Kubernetes Cluster에 Worker Node를 추가하는 절차를 보겠습니다.
>
> 먼저 Worker가 왜 필요한지부터 생각하겠습니다.
>
> Kubernetes에서 Application은 Pod와 Container 형태로 실행됩니다. Control Plane은 어느 Pod를 어느 서버에 놓을지 결정하고, Worker Node는 그 Pod를 실제로 실행합니다.
>
> 기존 Worker의 CPU와 Memory가 부족하거나 새로운 Application을 더 수용해야 한다면 Pod를 실행할 공간을 늘려야 합니다.
>
> **그래서**, 새로운 Worker용 VM을 준비합니다.
>
> **하지만**, VM을 만들었다고 Kubernetes가 그 서버를 자동으로 사용하지는 않습니다. 새 VM에는 아직 기존 Cluster가 사용하는 실행환경과 설정이 없고, Cluster도 이 VM의 이름과 역할을 모릅니다.
>
> Worker 추가는 단순히 서버 한 대를 만드는 작업이 아니라 **새 VM을 기존 Cluster와 같은 실행 기준에 연결하는 작업**입니다.

## 1.1 Ansible과 Kubespray의 관계

> 신규 Worker를 준비하려면 사용자, Package, OS와 Kubernetes 설정을 여러 VM에 같은 기준으로 적용해야 합니다.
>
> **하지만**, 운영자가 각 VM에 들어가 같은 명령을 반복하면 작업이 빠지거나 Node마다 설정이 달라질 수 있습니다.
>
> **그래서**, 여러 서버에 정의된 작업을 자동으로 적용하는 도구를 사용합니다. 이 도구가 **Ansible**입니다.
>
> Ansible은 어떤 서버에 작업할지와 어떤 작업을 실행할지 알아야 합니다. 작업 대상 서버를 기록한 것이 **Inventory**이고, 실행할 작업 순서를 기록한 것이 **Playbook**입니다.
>
> **Kubespray**는 Kubernetes 설치와 확장 작업을 위해 준비된 Ansible Playbook과 설정 묶음입니다.
>
> 오늘 사용하는 `hosts.yaml`은 신규 Worker를 기록하는 Inventory이고, `scale.yml`은 기존 Cluster에 Worker를 추가하는 Playbook입니다.

```text
Bastion에서 ansible-playbook 실행
             │
      ┌──────┴──────┐
      ▼             ▼
  hosts.yaml     scale.yml
  작업 대상       수행 작업
      └──────┬──────┘
             ▼
     신규 Worker VM
             ▼
      기존 Cluster 합류
```

> 이제 기존 Worker 두 대가 있는 환경에 신규 Worker 두 대를 추가하는 한 사례를 끝까지 따라가겠습니다.

# 2. 오늘 따라갈 두 대의 신규 VM
> 사례에서는 기존 Worker 두 대가 있는 환경에 신규 Worker 두 대를 추가합니다. 먼저 네 대의 이름과 IP를 한 화면에서 구분하겠습니다.


| 구분 | Hostname | IP |
|---|---|---:|
| 기존 Worker | `xadkswkmp01` | `109.156.22.67` |
| 기존 Worker | `xadkswkmp02` | `109.156.22.68` |
| 신규 Worker | `xadkswkmp03` | `109.156.22.69` |
| 신규 Worker | `xadkswkmp04` | `109.156.22.70` |

> 여기서 계속 볼 대상은 `xadkswkmp03`, `xadkswkmp04` 두 대입니다.
>
> 이 Hostname과 IP는 Manual에 기록된 사례값입니다. 실제 작업에서는 승인서와 현재 VM 정보로 다시 확인합니다.
>
> 두 VM은 생성됐지만 아직 Kubernetes Node 목록에는 없습니다.
>
> 먼저 Kubespray가 이 VM에 들어가 설정할 수 있도록 준비하고, Inventory에 이름과 역할을 등록한 뒤, `scale.yml`로 합류시키겠습니다.

# 3. VM이 Worker가 되기 전에 세 개의 길을 연다

> 앞에서 Ansible은 Bastion에서 신규 VM으로 접속해 작업한다고 설명했습니다.
>
> **그래서**, Kubespray보다 먼저 SSH와 권한 경로, 기존 Worker와 같은 Package·OS 기준, Application이 사용할 Storage 접근을 준비합니다.

## 3.1 Bastion에서 신규 VM으로 들어갈 수 있어야 한다

> 첫 번째는 Ansible이 사용할 접속과 권한 경로입니다.
>
> **그래서**, Bastion이 신규 Hostname을 올바른 IP로 찾을 수 있어야 하고 `dspaas` 계정의 SSH 접속과 sudo 권한이 준비돼야 합니다.
>
> Manual의 Pre-setting 화면에서는 `dspaas` 사용자 Group, Bastion `/etc/hosts`, SSH Key Pair와 Public Key, sudoers `wheel NOPASSWD`를 확인합니다.
>
> 이 항목들은 서로 별개인 Checklist처럼 보이지만 목적은 하나입니다.


> 이 길이 열리지 않으면 Kubespray는 Kubernetes 설정에 들어가기 전에 접속이나 권한 단계에서 멈춥니다.

## 3.2 기존 Worker와 같은 실행 기준을 받을 수 있어야 한다

> 다음은 신규 VM이 필요한 Package와 내부 인증서를 받을 수 있는지 확인합니다.
>
> YUM Repository 또는 Artifactory 접근, 필수 Package, Swap 비활성화, logrotate 설정, `SECDS-ROOTCA`, IPv6 관련 `sysctl.conf`와 VM Resource가 Manual의 Pre-setting 항목입니다.
>
> 여기서 모든 명령을 외우게 하지는 않습니다.
>
> **왜냐하면**, 중요한 것은 신규 VM을 독립된 새 서버로 두는 것이 아니라 기존 Worker와 같은 운영 기준으로 맞추는 것이기 때문입니다.
>
> Package Version이나 OS 설정은 다른 Cluster의 기록값을 복사하지 않고 대상 Cluster의 현재 기준을 사용합니다.

## 3.3 Storage가 신규 Worker를 허용해야 한다

> 마지막은 NetApp Storage ACL입니다.
>
> 신규 Worker에 PVC를 사용하는 Pod가 배치되려면 Storage 측에서도 신규 Worker의 접근을 허용해야 합니다.
>
> **그래서**, NetApp Storage ACL은 Node를 추가한 뒤가 아니라 사전 확인 단계에서 봅니다.

> [!summary] 화면에서 묶어 볼 것
> `접속·권한 → Package·OS 기준 → NetApp Storage ACL` 세 묶음이 준비되면 Kubespray가 신규 VM을 Worker로 구성할 전제가 생긴다.

# 4. Inventory에는 주소와 역할을 등록한다

> 앞에서 Inventory는 Ansible이 작업할 대상을 정한다고 설명했습니다.
>
> 이제 `hosts.yaml`에 신규 Worker 두 대의 이름·주소·역할을 등록합니다.


## 4.1 화면에서 변경할 세 위치

> `inventory/dks/hosts.yaml`을 열고 전체 파일을 처음부터 읽지 않습니다.
>
> 화면에서 다음 세 위치만 찾습니다.
>
> `all.hosts`에 `xadkswkmp03`, `xadkswkmp04`의 주소를 추가합니다.
>
> `worker_node.hosts`에 두 Hostname을 추가합니다.
>
> 기존 `kube_node`가 `worker_node`를 포함하는지 확인합니다.

> [!example] 신규 Worker 관련 발췌
> 아래는 관계를 보기 위한 발췌다. 실제 파일의 기존 Master·Router·Infra·etcd 항목은 그대로 유지한다.

```yaml
all:
  hosts:
    xadkswkmp03:
      ansible_host: 109.156.22.69
      ip: 109.156.22.69
      access_ip: 109.156.22.69
    xadkswkmp04:
      ansible_host: 109.156.22.70
      ip: 109.156.22.70
      access_ip: 109.156.22.70
  children:
    worker_node:
      hosts:
        xadkswkmp03:
        xadkswkmp04:
      vars:
        node_labels:
          node-type: "worker"
          node-role.kubernetes.io/worker: ""
    kube_node:
      children:
        worker_node:
```

> `ansible_host`는 Ansible이 접속할 주소입니다.
>
> `ip`와 `access_ip`는 Kubespray가 Node 통신에 사용할 주소입니다. 사례에서는 세 값이 같지만 실제 Network 설계가 다르면 승인된 값을 각각 사용합니다.
>
> `worker_node`는 일반 Worker 역할과 Label을 적용합니다.
>
> 특정 Team 전용 Taint와 Label은 다음 2.2 절차에서 다룹니다. 여기서는 일반 Worker만 추가합니다.

> [!warning] Manual 화면 판독
> Manual에 보이는 `=====`와 `add new worker node`는 변경 위치를 표시한 설명이다. 실제 YAML이 아니므로 복사하지 않는다.

> 편집이 끝나면 승인된 신규 VM, `all.hosts`의 Hostname·IP, `worker_node`의 Hostname과 다음 `scale.yml --limit` 대상이 모두 같은지 읽습니다.

---

# 5. scale.yml은 신규 두 대만 대상으로 실행한다

> `hosts.yaml`이 작업 대상을 정했다면 `scale.yml`은 수행할 Kubernetes 작업을 정합니다.
>
> 이제 Ansible이 두 파일을 읽어 신규 VM에 Worker 구성을 적용하고 기존 Cluster에 합류시킵니다.

> [!warning] 실행 경계
> `scale.yml`은 실제 Cluster를 변경한다. 승인된 신규 VM, Inventory와 `--limit` 대상이 일치할 때만 실행한다. 별도 승인이 없는 교육에서는 명령과 기존 결과만 확인한다.

```bash
ansible-playbook \
  -e @inventory/dks/dks_vars.yml \
  -i inventory/dks/hosts.yaml \
  --become \
  --become-user=root \
  scale.yml \
  --limit "xadkswkmp03,xadkswkmp04"
```

> 이 명령에서 모든 Option을 외우지 않습니다.
>
> `-e`는 대상 Cluster 변수, `-i`는 대상 Inventory입니다.
>
> 가장 중요한 것은 `--limit`입니다.
>
> `--limit`은 이번 변경을 `xadkswkmp03`, `xadkswkmp04` 두 대로 한정합니다. 잘못된 Hostname이나 기존 Node가 들어가면 의도하지 않은 서버가 작업 대상이 될 수 있습니다.

## 5.1 Play Recap이 말해주는 범위

> 실행이 끝나면 `PLAY RECAP`에서 신규 두 Host를 찾습니다.
>
> 두 Host 모두 `unreachable=0`, `failed=0`이면 Kubespray 작업이 오류 없이 끝난 것입니다.
>
> **하지만**, 이것은 자동화가 끝났다는 뜻이지 Application 실행까지 확인됐다는 뜻은 아닙니다.
>
> 이제 Kubernetes가 두 VM을 Worker로 인식하는지 보겠습니다.

---

# 6. 성공은 Node 목록에서 끝나지 않는다
> 이제 같은 두 Hostname을 네 화면에서 계속 추적하겠습니다. Node 목록, Node별 System Pod, 테스트 Workload, PVC Pod 순서입니다.


## 6.1 첫 화면 — Node 등록

```bash
kubectl get nodes
kubectl get nodes -o wide | egrep 'xadkswkmp03|xadkswkmp04'
kubectl get pod -A -o wide | egrep 'xadkswkmp03|xadkswkmp04'
```

> 화면에서 신규 Hostname 두 개가 보이고 `STATUS`가 `Ready`, `ROLES`가 `worker`인지 확인합니다.
>
> `-o wide`에서는 Internal IP, OS, Kernel과 Container Runtime을 기존 정상 Worker와 비교합니다.
>
> Manual의 출력에는 Kubernetes `v1.22.10`, RHEL `8.10`, Kernel `4.18.0-553.el8.x86_64`, `containerd://1.6.4`가 기록돼 있습니다.
>
> 이 숫자를 외우는 것이 목적은 아닙니다. 신규 Worker가 기존 Worker와 같은 실행 기준을 받았는지 비교하는 것이 목적입니다.

## 6.2 두 번째 화면 — Node별 System Pod


> Worker에는 Application Pod만 실행되는 것이 아닙니다.
>
> `calico-node`는 이 Node의 Pod Network에 필요한 구성이고, `vxflexos-node`는 Storage 연결에 필요한 Node 구성입니다.
>
> 두 신규 Worker에서 해당 System Pod가 `Running`인지 확인합니다.
>
> Node가 `Ready`라는 결과와 Node별 System Pod가 실행된다는 결과를 따로 보는 이유가 여기 있습니다.

## 6.3 세 번째 화면 — 실제 Workload 배치

> 다음은 테스트 Deployment를 신규 Worker 한 대에 배치합니다.
>
> 여기서 확인할 핵심은 Deployment가 생성됐다는 메시지가 아니라 Pod의 실제 `NODE`입니다.

```yaml
containers:
  - image: xa.dcr.dks.samsungds.net/dspaas-testrepo/checker:v5
    name: checker
nodeSelector:
  kubernetes.io/os: linux
  kubernetes.io/hostname: xadkswkmp03
```

> Manual의 테스트 YAML에는 `xadkswkmp01`이 기록돼 있습니다. `xadkswkmp01`은 기존 Worker이므로 그대로 사용하면 신규 Worker를 시험하지 않습니다.
>
> 실제 테스트에서는 `xadkswkmp03` 또는 `xadkswkmp04`로 바꿉니다.

```bash
kubectl apply -f ./test_deploy.yaml
kubectl get pods -o wide
```

> Pod가 `READY 1/1`, `Running`인지 보고 `NODE`가 지정한 신규 Worker인지 확인합니다.

## 6.4 네 번째 화면 — PVC를 사용하는 Pod

> 일반 Workload가 실행되면 Storage를 사용하는 Pod도 확인합니다.
>
> 먼저 대상 Cluster에서 사용할 수 있는 StorageClass를 확인합니다.

```bash
kubectl get storageclass
kubectl get pvc
kubectl get pods -o wide test-pvc-app
```

> Manual에는 `xa-netapp-nfs-sc`, `powerflexos-xfs-sc-300t-sp04`가 Xi'an 예시로 기록돼 있습니다.
>
> 테스트 PVC는 승인된 StorageClass와 용량을 사용합니다. Manual 예시의 핵심값은 `ReadWriteOnce`, `16Gi`, `xa-netapp-nfs-sc`입니다.
>
> 테스트 Pod는 `claimName: test-netapp-deploy`를 `/pvc-test`에 Mount하고, `nginx:latest` Image를 사용합니다.
>
> 이 Pod도 `nodeSelector`를 실제 신규 Worker로 바꿉니다.
>
> PVC가 `Bound`인지, Pod가 `Running`인지, `NODE`가 실제 신규 Worker인지 확인합니다.
>
> **결국**, 검증은 다음 네 장면입니다.

> 네 화면은 `Node Ready → Node별 System Pod Running → 테스트 Workload Running → PVC Pod Running` 순서로 이어집니다.

# 7. 마지막으로 운영 기준본을 맞춘다

> 신규 Worker가 실제로 동작해도 운영 Ansible Inventory가 이전 상태로 남아 있으면 다음 작업에서 Node 목록이 달라집니다.
>
> **그래서**, `app/dspaas/ansible/XiAn_DKS_Kubernetes_Stack-v1.0/ansible`의 `[worker]` Group에도 신규 Node를 추가합니다.

```ini
[worker]
xadkswkmp01
xadkswkmp02
xadkswkmp03
xadkswkmp04
```

> 마지막에는 세 상태가 같아야 합니다.

> 마지막에는 Kubespray `hosts.yaml`, 운영 Ansible Inventory와 `kubectl`의 실제 Worker 목록이 모두 같아야 합니다.

> 다른 Cluster에 적용할 때 운영 Apps 사례의 Hostname과 IP를 복사하지 않습니다. `dev-apps-pa01-xas`처럼 Cluster가 바뀌면 해당 Cluster Catalog에서 Bastion, Node, CIDR과 VIP를 다시 확인합니다.

# 8. 완료 기준 — 신규 VM이 실제 실행 공간이 되었는가

> 처음 질문으로 돌아가겠습니다.
>
> Worker 추가의 목적은 Application을 실행할 공간을 늘리는 것입니다.
>
> **그래서**, 완료도 그 목적에 맞춰 판단합니다.

```text
신규 VM 준비
→ Inventory의 주소·역할 등록
→ scale.yml 신규 Node 한정 실행
→ Play Recap 성공
→ Node Ready와 System Pod Running
→ Workload와 PVC Pod가 신규 Worker에서 Running
→ 운영 Inventory 정리
```

> `scale.yml` 성공만으로 완료하지 않습니다.
>
> Node가 `Ready`라는 사실만으로도 완료하지 않습니다.
>
> 실제 Workload와 PVC Pod가 신규 Worker에 배치되고, 다음 운영 작업에서 사용할 Inventory까지 실제 상태와 같아야 합니다.
>
> **결국**, VM이 Cluster의 이름만 가진 Node가 아니라 Application을 실행할 수 있는 Worker가 되었을 때 작업이 끝납니다.
