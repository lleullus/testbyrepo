# 2.5 API Server 인증서 갱신 강사용 전체 대본

> [!important] 사용 방법
> 수강생이 Control Plane 인증서, Static Pod와 kubeconfig 갱신을 처음 본다고 가정한다. 명령부터 읽지 않는다. **왜 인증서를 만료 전에 갱신해야 하는지 → 어떤 인증서가 언제 만료되고 무엇이 중단되는지 → 잔여기간과 Upgrade 계획으로 작업 시점을 어떻게 정하는지 → 왜 Master를 한 대씩 작업하는지 → 새 파일을 실행 중인 Process와 Client에 어떻게 반영하는지 → 언제 다음 Master로 갈 수 있는지 → KubeSphere 연결까지 왜 다시 반영하는지** 순서로 설명한다.

## 0. 강사가 들고 갈 설명 공식

```text
인증서 유효기간과 만료 영향 확인
→ 잔여기간·Upgrade 계획으로 갱신 필요 여부 결정
→ 신뢰 정보 갱신
→ 실행 중인 Process 반영
→ 한 Node 정상 확인
→ 다음 Node 진행
→ 관리 Client와 KubeSphere 연결 갱신
```

## 0-1. 오늘 전체 한 줄

```text
kubeadm 관리 인증서의 잔여기간을 확인한다
→ 만료 전에 승인된 작업창을 정한다
→ 세 Master를 모두 백업한다
→ ma01 인증서·Static Pod·Health 확인
→ ma02 같은 Gate 반복
→ ma03 같은 Gate 반복
→ Bastion kubeconfig 갱신
→ KubeSphere Unbind·Import·System Pod 재시작
```

---

# 1. 왜 이 작업을 하는가 — 인증서 만료 전에 Control Plane 신뢰를 연장한다

> Kubernetes Control Plane 구성 요소와 관리 Client는 TLS 인증서로 상대의 신원을 확인하고 연결을 허용합니다.
>
> 이 인증서는 영구 자격증명이 아닙니다. 유효기간이 끝나면 올바른 Server와 Client라도 상대가 인증서를 거부할 수 있습니다.
>
> **그래서**, 현재 잔여기간과 다음 Upgrade 일정을 확인하고 만료 전에 인증서를 갱신해야 합니다. 이 작업의 목적은 단순히 파일의 날짜를 바꾸는 것이 아니라 API Server, Control Plane 구성 요소, `kubectl`과 KubeSphere가 계속 서로를 신뢰하며 Cluster를 운영할 수 있게 하는 것입니다.

## 1.1 일반 인증서 약 1년과 CA 약 10년을 구분한다

Kubernetes 공식 kubeadm 기준에서 kubeadm이 생성하는 Client Certificate의 기본 유효기간은 1년이다. Xi'an 구축 문서의 `kubeadm certs check-expiration` 참조 출력에서도 일반 인증서와 kubeconfig 내부 Client Certificate는 `359d`, CA는 `9y`의 잔여기간으로 기록돼 있다.

| Xi'an 참조 출력의 구분 | 예시 대상 | 참조 잔여기간 |
|---|---|---:|
| kubeadm 관리 일반·Client Certificate | `admin.conf`, `apiserver`, `apiserver-kubelet-client`, `controller-manager.conf`, `front-proxy-client`, `scheduler.conf` | `359d` |
| Certificate Authority | `ca`, `front-proxy-ca` | `9y` |

> `359d`와 `9y`는 구축 당시의 **참조 출력**이며 현재 잔여기간이 아닙니다. 현재값은 각 Master에서 `kubeadm certs check-expiration`으로 다시 확인합니다.
>
> “약 1년”은 매년 같은 날짜에 무조건 수동 명령을 실행하라는 뜻이 아닙니다. 만료 전 정기 점검과 Kubernetes Upgrade 계획을 함께 보고 실제 갱신 시점을 결정해야 합니다.

공식 근거: [Kubernetes — Certificate Management with kubeadm](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-certs/)

## 1.2 갱신하지 않으면 어떤 경로가 중단되는가

| 만료 대상 | 사용하는 경로 | 예상 영향 |
|---|---|---|
| `apiserver` | `kubectl`, Scheduler, Controller Manager, KubeSphere 등 API Client → API Server | Client가 API Server의 TLS 인증서를 거부하여 API 연결 실패 |
| `admin.conf` | Master·Bastion 관리자 `kubectl` | 관리자 인증 실패와 Cluster 운영 명령 중단 |
| `controller-manager.conf` | Controller Manager → API Server | Deployment·ReplicaSet·Node 등 상태 조정 기능 장애 |
| `scheduler.conf` | Scheduler → API Server | 새 Pod의 Node 배치 기능 장애 |
| `apiserver-kubelet-client` | API Server → kubelet | Pod Log·Exec 등 kubelet 보안 통신 장애 가능 |
| `front-proxy-client` | API Aggregation Layer | Metrics와 확장 API 연결 장애 가능 |
| KubeSphere가 보관한 이전 kubeconfig | KubeSphere Host → Member Cluster | Member Cluster 조회·관리 연결 장애 |

```text
인증서 만료
→ TLS Server 또는 Client 신원 검증 실패
→ API 요청·Control Plane 구성 요소 간 인증 실패
→ 배포·변경·Scheduling·상태 조정·운영·복구 경로 장애
```

> 인증서가 만료되는 순간 기존 Application Pod가 모두 즉시 종료된다고 설명하지 않습니다. 이미 실행 중인 Pod는 계속 동작할 수 있습니다. 그러나 신규 배포·Scale·장애 복구·상태 조정, `kubectl`, KubeSphere 관리 같은 Control Plane 작업이 실패할 수 있으므로 정상 운영과 복구 능력을 잃기 전에 갱신해야 합니다.

## 1.3 언제 갱신하는가 — 달력이 아니라 잔여기간과 Upgrade 계획으로 정한다

작업 검토는 다음 순서로 시작한다.

```text
모든 Master에서 check-expiration 확인
→ EXPIRES·RESIDUAL TIME·EXTERNALLY MANAGED 확인
→ 다음 Kubernetes Control Plane Upgrade 일정 확인
→ Upgrade의 인증서 자동 갱신 사용 여부 확인
→ 내부 사전 갱신 기준과 작업 승인 확인
→ 백업·작업창·롤백 담당 확보
→ 갱신 실행
```

```bash
for host in ma01 ma02 ma03; do
  echo "===== $host ====="
  ssh "$host" sudo /usr/local/bin/kubeadm certs check-expiration
done
```

> kubeadm은 기본적으로 Control Plane Upgrade 과정에서 인증서를 갱신합니다. 1년 이내에 정기 Upgrade가 예정되어 있고 인증서 자동 갱신을 비활성화하지 않았다면 Upgrade가 갱신 경로가 될 수 있습니다. 정기 Upgrade가 없거나 만료 전에 Upgrade할 수 없다면 이 Manual의 수동 갱신 절차를 계획합니다.
>
> 정확히 “만료 며칠 전” 작업할지는 현재 문서에 운영 정책 근거가 없습니다. 임의로 30일·60일을 정하지 않고 현지 운영 기준과 변경 승인 절차를 확인합니다.
>
> `EXTERNALLY MANAGED=yes`인 인증서는 kubeadm이 직접 갱신할 대상이 아닙니다. 외부 인증서 관리 담당 절차로 전환합니다.

## 1.4 `renew all`이 Cluster의 모든 인증서를 갱신하는 것은 아니다

```text
kubeadm certs renew all
= 해당 Control Plane Node에서 kubeadm이 관리하는 갱신 가능 인증서 전체

아님
- CA 자체의 갱신
- kubelet 자동 회전 Client Certificate의 갱신
- External ETCD 인증서의 갱신
- 외부 CA가 관리하는 인증서의 갱신
- Harbor·Ingress·Application TLS 인증서의 갱신
```

> `all`을 Cluster에 존재하는 모든 인증서라는 뜻으로 해석하지 않습니다. `check-expiration`의 대상과 `EXTERNALLY MANAGED` 값을 먼저 확인하고, External ETCD와 다른 서비스 인증서는 각각의 운영 절차로 분리합니다.

## 1.5 인증서 파일만 바꾸면 끝나는 작업이 아니다

> 오늘 절차는 API Server를 포함한 kubeadm 관리 Control Plane 인증서와 kubeconfig의 Client Certificate를 갱신합니다.
>
> **하지만**, 디스크의 인증서 파일을 갱신했다고 실행 중인 API Server가 새 파일을 자동으로 읽는 것은 아닙니다.
>
> API Server, Scheduler와 Controller Manager는 Static Pod로 실행됩니다. 새 인증서를 사용하게 하려면 해당 Static Pod를 재생성해야 합니다.
>
> Bastion과 KubeSphere도 기존 kubeconfig의 Client Certificate를 계속 참조할 수 있습니다.
>
> **그래서**, 이 작업은 파일 갱신, Process 반영, Client 연결 갱신의 세 층으로 봅니다.

## 1.6 세 층을 구분한다

> 파일 층에는 `/etc/kubernetes/ssl`과 `admin.conf`·`scheduler.conf`·`controller-manager.conf`가 있습니다.
>
> Process 층에는 `kube-apiserver`, `kube-scheduler`, `kube-controller-manager`가 있습니다.
>
> Client 연결 층에는 Master root, Bastion root·`dspaas` kubeconfig와 KubeSphere Member Cluster 등록이 있습니다.

> 어느 한 층만 바뀌면 일부 경로는 새 인증서를 쓰고 다른 경로는 이전 인증서를 계속 사용할 수 있습니다.

> [!warning] 실행 경계
> 교육에서는 만료 영향·작업 시점 판단, Master one-by-one 절차와 중단 Gate를 탁상훈련으로 설명한다. 인증서 갱신, Static Pod 재생성, kubeconfig 교체와 KubeSphere Unbind·Import는 실행하지 않는다.

# 2. 가장 중요한 원칙 — Master를 한 대씩 작업한다

> Xi'an Control Plane은 `ma01`, `ma02`, `ma03` 세 Master가 함께 API 서비스를 제공합니다.
>
> 세 대를 동시에 변경하면 Control Plane 가용성을 잃을 수 있습니다.
>
> **그래서**, 한 번에 한 Master만 갱신하고 그 Node가 정상으로 돌아온 뒤 다음 Master로 이동합니다.

```text
ma01 갱신·재시작·Health 확인
→ 정상일 때만 ma02
→ ma02 갱신·재시작·Health 확인
→ 정상일 때만 ma03
```

> One-by-One은 단순한 작업 순서가 아닙니다.
>
> 각 Master의 정상 확인이 다음 Master 작업을 허용하는 **Gate**입니다.
>
> ma01이 정상으로 복구되지 않았는데 ma02 작업으로 넘어가면 정상 Master를 하나 더 줄일 수 있습니다.

# 3. 첫 변경 전에 모든 Master를 백업한다

> 인증서와 kubeconfig를 변경하기 전에 복구할 원본을 준비합니다.
>
> 백업은 ma01만 하는 것이 아니라 모든 Master에서 먼저 완료합니다.

## 3.1 백업 대상

| 대상 | 이유 |
|---|---|
| `/etc/kubernetes/ssl` | 갱신되는 인증서와 Key 보관 |
| `/etc/kubernetes/admin.conf` | 관리자 Client 인증정보 |
| `/etc/kubernetes/scheduler.conf` | Scheduler의 API 연결정보 |
| `/etc/kubernetes/controller-manager.conf` | Controller Manager의 API 연결정보 |

> 인증서 디렉터리에는 Private Key가 있고 kubeconfig에는 Client 인증정보가 있습니다. 백업 내용을 화면이나 문서에 노출하지 않습니다.

## 3.2 모든 Master에서 백업

```bash
for host in ma01 ma02 ma03; do
  ssh $host mkdir -p /tmp/$(date +%Y%m%d)-apibackup
  ssh $host sudo cp -rp /etc/kubernetes/ssl \
    /tmp/$(date +%Y%m%d)-apibackup/
  ssh $host sudo cp -rp \
    /etc/kubernetes/admin.conf \
    /etc/kubernetes/scheduler.conf \
    /etc/kubernetes/controller-manager.conf \
    /tmp/$(date +%Y%m%d)-apibackup/
done
```

> 백업 명령 종료만 보지 않습니다.

```bash
for host in ma01 ma02 ma03; do
  ssh $host sudo ls -al /tmp/$(date +%Y%m%d)-apibackup/
done
```

> 세 Master 모두에서 `ssl` 디렉터리와 세 kubeconfig 파일이 보이는지 확인합니다.
>
> 복구 위치를 확인하지 못했다면 첫 Master 갱신으로 진행하지 않습니다.

# 4. 한 Master에서 반복할 작업 단위

> 세 Master에서 수행할 작업은 같습니다.
>
> 먼저 ma01 한 대를 기준으로 전체 작업 단위를 보겠습니다.

1. 인증서 갱신과 새 만료일 확인
2. Control Plane Static Pod 재생성과 상태 확인
3. Master root kubeconfig 갱신과 Client Certificate 확인
4. API Server `readyz`·`livez` 확인
5. 다음 Master 진행 여부 결정

---

# 5. ma01 — 첫 번째 Gate를 끝까지 통과한다
> ma01에서는 파일 갱신부터 Process·Client 반영과 Health 확인까지 하나의 작업 단위를 끝까지 수행합니다.


## 5.1 인증서 파일 갱신

```bash
ssh ma01 sudo /usr/local/bin/kubeadm certs renew all
ssh ma01 sudo /usr/local/bin/kubeadm certs check-expiration
```

> `renew all`은 kubeadm이 관리하는 Control Plane 인증서를 갱신합니다.
>
> `check-expiration`으로 새 만료일이 적용됐는지 확인합니다.
>
> 새 만료일이 확인되지 않으면 Static Pod를 재생성하지 않고 원인을 확인합니다.

## 5.2 Static Pod 재생성

> 인증서 파일은 바뀌었지만 실행 중인 Process는 아직 기존 파일을 사용합니다.
>
> **그래서**, ma01의 API Server, Scheduler와 Controller Manager Pod Sandbox를 제거합니다.
>
> kubelet이 Static Pod를 다시 만들면서 갱신된 인증서를 읽습니다.

```bash
ssh ma01 'sudo /usr/local/bin/crictl pods --namespace kube-system \
  | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)" \
  | awk "{print \$1}" \
  | xargs -r sudo /usr/local/bin/crictl rmp -f'
```

> 이 명령은 ma01의 Control Plane Static Pod에만 적용합니다.
>
> 재생성된 Sandbox가 보이는지 확인합니다.

```bash
ssh ma01 'sudo /usr/local/bin/crictl pods --namespace kube-system \
  | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)"'
```

## 5.3 ma01 root kubeconfig 갱신

> ma01에서 실행하는 관리 명령도 갱신된 Client Certificate를 사용해야 합니다.

```bash
ssh ma01 sudo cp /etc/kubernetes/admin.conf /root/.kube/config
```

> kubeconfig의 `client-certificate-data`를 인증서 정보로 확인해 만료일이 갱신됐는지 봅니다. 인증서와 Key 원문을 출력하거나 기록하지 않습니다.

## 5.4 Static Pod와 API Server Health

```bash
kubectl get pod -n kube-system | grep -E \
  'kube-apiserver.*01|kube-controller-manager.*01|kube-scheduler.*01'
ssh ma01 curl -k https://localhost:6443/readyz?verbose
ssh ma01 curl -k https://localhost:6443/livez?verbose
```

> 세 Control Plane Pod가 Running인지 확인합니다.
>
> 필요한 경우 최근 Event를 확인합니다.
>
> `readyz`는 API Server가 요청을 받을 준비가 됐는지, `livez`는 Process가 살아 있는지 확인합니다.
>
> ma01의 새 만료일, Static Pod와 두 Health Endpoint가 모두 정상이어야 다음 Master로 갈 수 있습니다.

> [!important] ma02 진행 Gate
> ma01의 Control Plane Pod와 API Server Health가 정상으로 복구되지 않았다면 ma02 작업을 시작하지 않는다.

---

# 6. ma02와 ma03 — 같은 Gate를 새로 통과한다

> ma01이 정상으로 복구된 뒤 ma02에서 같은 작업 단위를 반복합니다.
>
> ma02가 정상으로 복구된 뒤에만 ma03으로 이동합니다.

| 순서 | 갱신 대상 | 다음 단계 조건 |
|---|---|---|
| 1 | `ma01` | 만료일·Static Pod·kubeconfig·readyz·livez 정상 |
| 2 | `ma02` | 같은 Gate 정상 |
| 3 | `ma03` | 같은 Gate 정상 |

> 각 Node에서도 `renew all → check-expiration → Static Pod 재생성 → root kubeconfig 갱신 → Pod Running → readyz·livez`를 새로 확인합니다.

> 이전 Master가 성공했다는 사실은 현재 Master의 검증을 대신하지 않습니다.
>
> ma01, ma02, ma03가 모두 Gate를 통과하면 Control Plane Node의 인증서 갱신이 끝납니다.

---

# 7. Bastion kubeconfig도 새 Client Certificate로 바꾼다

> 세 Master가 새 인증서를 사용해도 Bastion의 kubeconfig는 자동으로 바뀌지 않습니다.
>
> Manual은 정상 갱신이 끝난 ma01의 `admin.conf`를 Bastion root와 `dspaas` 계정에 반영합니다.

## 7.1 Bastion root

```bash
ssh ma01 'sudo cp /etc/kubernetes/admin.conf /tmp/admin.conf \
  && sudo chown $(whoami):$(whoami) /tmp/admin.conf'
scp ma01:/tmp/admin.conf /tmp/config
sudo cp /tmp/config /root/.kube/config
```

## 7.2 Bastion dspaas

```bash
ssh ma01 sudo cat /etc/kubernetes/admin.conf \
  > /app/dspaas/.kube/config
```

> 두 경로 모두 kubeconfig의 Client Certificate 만료일이 갱신됐는지 확인합니다.
>
> Bastion에서 `kubectl`이 새 kubeconfig로 Cluster에 접근하는지도 확인합니다.

> Bastion 완료 기준은 Master API Server, Bastion root `kubectl`, Bastion `dspaas` `kubectl`이 모두 새 인증정보로 정상 동작하는 것입니다.

# 8. KubeSphere Member Cluster 연결도 갱신한다

> Bastion까지 정상이어도 KubeSphere는 Member Cluster를 등록할 때 사용한 이전 kubeconfig를 참조할 수 있습니다.
>
> **그래서**, 기존 Member Cluster 연결을 해제하고 갱신된 kubeconfig로 다시 Import합니다.

## 8.1 Unbind 전에 기록할 값

> KubeSphere Console에서 대상 Member Cluster를 확인합니다.
>
> Unbind 전에 정확한 Cluster Name과 Tag를 기록합니다. Import할 때 같은 Identity를 사용해야 합니다.

> Console 경로는 `Platform → Cluster Management → 대상 Member Cluster → Cluster Settings → Basic Information → Unbind Cluster`입니다.

> `I understand the risks of this operation`을 확인하고 승인된 작업에서만 Unbind합니다.

## 8.2 새 kubeconfig로 Import

> `Cluster Management → Add Cluster`에서 기록한 Cluster Name과 Tag를 사용하고 갱신된 kubeconfig를 입력합니다.
>
> 이 단계로 KubeSphere의 Member Cluster 연결에 새 Client Certificate가 반영됩니다.

## 8.3 KubeSphere System Deployment 재시작

```bash
kubectl rollout restart deploy \
  -n kubesphere-system \
  ks-apiserver ks-console ks-controller-manager
kubectl get pod -n kubesphere-system
```

> 재시작된 KubeSphere System Pod가 정상 상태로 돌아오는지 확인합니다.
>
> Member Cluster가 KubeSphere에서 다시 연결되고 Resource가 조회되는지 확인합니다.

---

# 9. 완료 기준 — 새 인증서가 모든 사용 경로에 반영됐는가

> 완료하려면 모든 Master 백업 뒤 ma01, ma02, ma03가 각각 Gate를 통과해야 합니다.
>
> Bastion root·`dspaas` kubeconfig를 갱신하고 KubeSphere를 같은 Cluster Name·Tag와 새 kubeconfig로 다시 Import해야 합니다.
>
> 마지막으로 KubeSphere System Pod가 정상으로 돌아와야 합니다.

> `kubeadm certs renew all` 명령 성공만으로 완료하지 않습니다.
>
> 각 Master의 Static Pod와 API Server Health, 관리 Client의 kubeconfig, KubeSphere Member Cluster 연결까지 새 인증정보를 사용해야 합니다.
>
> **결국**, 인증서 파일이 바뀌는 것이 아니라 Control Plane Process와 모든 관리 Client의 실제 연결이 새 인증서를 사용하는 상태가 완료입니다.
