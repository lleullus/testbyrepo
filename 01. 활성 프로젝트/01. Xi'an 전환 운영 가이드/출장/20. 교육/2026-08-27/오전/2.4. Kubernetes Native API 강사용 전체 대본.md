# 2.4 Kubernetes Native API 강사용 전체 대본

> [!important] 사용 방법
> 수강생이 Kubernetes API, Service, Ingress, ServiceAccount와 RBAC을 처음 본다고 가정한다. YAML부터 읽지 않는다. **외부 시스템이 무엇을 요청하는지 → 요청이 어떤 경로로 kube-apiserver에 도달하는지 → 누구의 요청인지 → 무엇을 허용할지 → 어떤 결과로 경계를 확인하는지** 순서로 설명한다.

## 0. 강사가 들고 갈 설명 공식

```text
요청
→ 진입 경로
→ 호출 주체
→ 허용 권한
→ 성공·거부 결과
```

## 0-1. 오늘 전체 한 줄

```text
외부 시스템이 Kubernetes Resource를 조회한다
→ Ingress가 외부 Domain을 받는다
→ Service가 kube-apiserver Static Pod를 찾는다
→ ServiceAccount Token으로 주체를 확인한다
→ RBAC으로 Resource·Verb·Namespace를 제한한다
```

---

# 1. 시작 — Kubernetes API는 Control Plane의 입구다

> 사용자가 `kubectl get pods`를 실행하면 `kubectl`이 직접 Pod를 찾는 것이 아닙니다.
>
> Kubernetes의 **kube-apiserver**에 Pod 목록을 요청합니다.
>
> kube-apiserver는 Kubernetes Resource 조회·생성·변경 요청을 받는 Control Plane의 API 입구입니다.
>
> `GET`, `POST`, `PUT`, `PATCH` 같은 HTTP 동작으로 Resource를 조회하거나 변경합니다.
>
> 오늘은 승인된 외부 시스템이 이 Kubernetes Native API를 호출하는 경로를 보겠습니다.

## 1.1 새 업무 API를 만드는 절차가 아니다

> 이 절차는 외부 시스템 전용 비즈니스 API를 새로 개발하는 작업이 아닙니다.
>
> Kubernetes가 원래 제공하는 API에 승인된 진입 경로와 권한을 부여하는 작업입니다.
>
> DKS 운영 환경에는 Prometheus를 이 방식으로 노출한 선례가 있습니다.
>
> **하지만**, 이 선례가 특정 소비 시스템의 전체 기능을 Kubernetes Native API로 대체할 수 있다는 증거는 아닙니다.
>
> 여기서 다루는 범위는 **API 진입 경로와 인증·RBAC 기반 권한 제공**까지입니다.

## 1.2 길이 열려도 권한이 생기는 것은 아니다

> 외부 시스템이 kube-apiserver를 사용하려면 세 가지가 모두 필요합니다.


> Ingress를 만들었다고 API 권한이 생기지 않습니다.
>
> Token이 있다고 모든 Kubernetes Resource를 사용할 수도 없습니다.
>
> Source 제한, Authentication과 RBAC을 함께 봐야 합니다.

> [!warning] 실행 경계
> 기본 교육은 기존 Service·Ingress·RBAC을 읽기 전용으로 확인한다. 실제 실습을 진행할 때는 아래 `# 10`처럼 PRD의 기존 Native API FQDN을 재사용하고 `nativeapi-lab` Namespace에 Pods `get·list` 전용 ServiceAccount·Role·RoleBinding만 임시 생성한다. 신규 API 노출, Source CIDR 변경, ClusterRoleBinding과 권한 확대는 실행하지 않으며 실습 후 Namespace를 삭제한다.

---

# 2. 하나의 요청 경로를 끝까지 따라간다

> 외부 Client가 운영 Cluster의 `default` Namespace에서 Pod 목록을 조회한다고 하겠습니다.

```text
승인된 Client Source
→ nativeapi.xaprdpa01.apps.dks.samsungds.net
→ kube-apiserver Ingress
→ kube-apiserver Service :443
→ Master의 kube-apiserver :6443
→ ServiceAccount 인증
→ Role의 pods get·list 권한
→ PodList 응답
```

> Master의 kube-apiserver Endpoint는 사례에서 다음 세 주소입니다.

- `109.156.22.58:6443`
- `109.156.22.59:6443`
- `109.156.22.60:6443`

> 이 경로를 내부 연결, 외부 노출, 인증과 권한 순서로 나누겠습니다.

---

# 3. Service가 kube-apiserver Static Pod를 묶는다

> kube-apiserver는 각 Master에서 **Static Pod**로 실행됩니다.
>
> Ingress가 Pod 이름 세 개를 직접 참조하지는 않습니다.
>
> **그래서**, Pod Label을 기준으로 세 kube-apiserver를 하나의 내부 접점으로 묶는 Service를 만듭니다.

## 3.1 Selector와 Port

> Service가 찾을 Label은 kube-apiserver Static Pod의 실제 Label과 같아야 합니다.

```bash
kubectl get pod -n kube-system kube-apiserver-xadksmamp01 -o yaml
```

확인할 Label:


> Service의 `port: 443`은 Service가 제공하는 HTTPS Port입니다.
>
> `targetPort: 6443`은 실제 kube-apiserver가 받는 Port입니다.

> [!example] Service 핵심 발췌

```yaml
apiVersion: v1
kind: Service
metadata:
  name: kube-apiserver
  namespace: kube-system
spec:
  type: ClusterIP
  selector:
    component: kube-apiserver
    tier: control-plane
  ports:
    - port: 443
      protocol: TCP
      targetPort: 6443
```

## 3.2 Service 존재보다 Endpoints가 중요하다

```bash
kubectl get service -n kube-system kube-apiserver
kubectl describe service -n kube-system kube-apiserver
```

> `Service`가 보인다는 것은 객체가 저장됐다는 뜻입니다.
>
> 실제 연결은 `Endpoints`에서 확인합니다.
>
> 사례의 Endpoints가 세 Master의 `109.156.22.58~60:6443`을 가리키는지 봅니다.
>
> Selector가 잘못되면 Service는 존재해도 kube-apiserver로 연결되지 않습니다.

---

# 4. Ingress가 외부 Domain을 Service에 연결한다

> Service는 Cluster 내부 접점을 만들었습니다.
>
> 외부 Client가 승인된 Domain으로 들어오게 하려면 Ingress가 필요합니다.

## 4.1 Host와 Backend

> Ingress Host는 `nativeapi.xaprdpa01.apps.dks.samsungds.net`입니다.
>
> Backend는 앞에서 만든 `kube-apiserver` Service의 Port `443`입니다.

> [!example] Ingress 핵심 발췌

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: kube-apiserver-ingress
  namespace: kube-system
  annotations:
    kubernetes.io/ingress.class: nginx
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
    nginx.ingress.kubernetes.io/ssl-passthrough: "true"
    nginx.ingress.kubernetes.io/whitelist-source-range: "<approved-source-cidr>"
spec:
  rules:
    - host: nativeapi.xaprdpa01.apps.dks.samsungds.net
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: kube-apiserver
                port:
                  number: 443
```

> `ssl-passthrough`는 TLS 연결을 Ingress에서 종료하지 않고 kube-apiserver까지 전달합니다.
>
> `force-ssl-redirect`는 HTTP 요청을 HTTPS로 보냅니다.

## 4.2 Source IP·CIDR 제한은 필수다

> kube-apiserver는 Control Plane API입니다.
>
> 모든 Source에 외부 주소를 열어 두지 않습니다.
>
> 실제 호출 주체가 위치한 승인된 Source IP 또는 CIDR만 허용합니다.
>
> `<approved-source-cidr>`는 Placeholder이며 실제 승인값으로 바꿉니다.
>
> Source CIDR이 확정되지 않았다면 Ingress 구성을 완료로 간주하지 않습니다.

## 4.3 Ingress 연결 확인

```bash
kubectl get ingress -n kube-system kube-apiserver-ingress
kubectl describe ingress -n kube-system kube-apiserver-ingress
```

> Ingress Address가 Router Node 주소를 가리키는지 봅니다.
>
> 사례에서는 `109.156.22.61`, `109.156.22.62`, `109.156.22.63`입니다.
>
> Backend가 `kube-apiserver:443`이고 그 뒤의 Endpoints가 세 Master의 `:6443`인지 확인합니다.

---

# 5. 경로가 열려도 익명 요청은 거부돼야 한다

> 이제 외부 Domain에서 kube-apiserver까지 요청이 도달할 수 있습니다.
>
> **하지만**, 요청 주체가 누구인지 증명하지 않으면 Kubernetes가 Resource 접근을 허용해서는 안 됩니다.

## 5.1 Token 없이 호출한다

```bash
curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods
```

> Manual 사례에서는 `system:anonymous`가 Pod 목록을 조회할 수 없다는 `403 Forbidden`이 반환됩니다.
>
> 이것은 API가 고장 난 결과가 아니라 무인증 요청이 거부되는 정상 경계입니다.


> `curl -k`는 Server Certificate 검증을 생략하는 Manual의 확인 예시입니다. 실제 Client의 인증서 신뢰 정책을 대체하지 않습니다.

---

# 6. ServiceAccount와 RBAC으로 주체와 권한을 연결한다

> 외부 시스템처럼 사람이 직접 로그인하지 않는 호출 주체에는 ServiceAccount를 사용할 수 있습니다.
>
> ServiceAccount는 요청의 이름을 제공합니다.
>
> Role은 그 이름이 어느 Namespace에서 어떤 Resource에 어떤 동작을 할 수 있는지 정합니다.
>
> RoleBinding은 ServiceAccount와 Role을 연결합니다.


## 6.1 Manual의 최소 검증 사례

> 사례는 `default` Namespace의 Pod를 `get`, `list`할 수 있는 최소 검증입니다.

| Resource | 이름 | Namespace | 역할 |
|---|---|---|---|
| ServiceAccount | `test-sa` | `default` | API 요청 주체 |
| Role | `test-role` | `default` | Pods `get`, `list` 허용 |
| RoleBinding | `test-rb` | `default` | `test-sa`와 `test-role` 연결 |

> 세 Resource의 Namespace와 이름이 연결되는지 확인합니다.
>
> 이 `test-sa`, `test-role`, Pod `get/list`는 인증과 인가 흐름을 보여주는 사례입니다.
>
> 실제 소비 시스템의 전체 기능과 필요한 권한을 분석하지 않고 이 Role을 최종 업무 권한으로 복사하지 않습니다.

## 6.2 Resource 상태 확인

```bash
kubectl describe serviceaccount test-sa -n default
kubectl describe role test-role -n default
kubectl describe rolebinding test-rb -n default
```

> ServiceAccount, Role과 RoleBinding 이름·Namespace가 맞는지 확인합니다.
>
> Role에는 Pods의 `get`, `list`만 보여야 합니다.
>
> RoleBinding의 Subject가 `test-sa`, RoleRef가 `test-role`인지 확인합니다.

---

# 7. Token으로 인증된 요청을 보낸다

> ServiceAccount Token은 API 요청에서 주체를 증명하는 Credential입니다.
>
> 화면, 문서와 작업 로그에 실제 Token 값을 기록하지 않습니다.
>
> Manual의 Token 확인 단계에서는 해당 Token이 `test-sa`에 연결되는지 확인합니다.


> 실제 Token 대신 Placeholder만 사용하겠습니다.

```bash
curl -k https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/default/pods -H "Authorization: Bearer <SERVICE_ACCOUNT_TOKEN>"
```

> 유효한 Token이 `test-sa`를 증명하고 Role이 Pods `get/list`를 허용하면 `PodList`가 반환됩니다.


> Token이 있다고 모든 API가 허용되는 것은 아닙니다. Role에 없는 Resource나 Verb는 RBAC 경계에서 거부돼야 합니다.

---

# 8. 완료 기준 — 길과 권한을 함께 확인했는가

> 완료하려면 Service Selector가 세 kube-apiserver Endpoint `:6443`을 가리켜야 합니다.
>
> Ingress Host와 Backend가 맞고 승인된 Source CIDR이 적용돼야 합니다.
>
> Token이 없는 요청은 `system:anonymous`로 거부되고, 유효한 ServiceAccount Token은 Role이 허용한 Pods `get`, `list`에서만 `PodList`를 받아야 합니다.

> Service나 Ingress가 생성됐다는 메시지만으로 완료하지 않습니다.
>
> Service Endpoints가 올바른 Master를 가리키고, Ingress가 승인된 Host·Backend·Source 제한을 가지며, 무인증 요청은 거부되고 승인된 ServiceAccount는 허용된 API만 사용할 수 있어야 합니다.
>
> **결국**, Native API 구성은 URL을 만드는 작업이 아니라 Control Plane 진입 경로와 호출 주체의 권한 경계를 함께 만드는 작업입니다.

# 10. PRD 간단 실습 — 같은 Token으로 403·200·403 비교

> KubeSphere에서는 Namespace·ServiceAccount·RBAC 객체를 확인하고, 실제 Native API 호출은 PRD Bastion `xadksbtmp01`에서 `curl`로 수행합니다.
>
> 기존 `kube-apiserver` Service와 Ingress를 새로 만들지 않습니다. 기존 PRD FQDN `nativeapi.xaprdpa01.apps.dks.samsungds.net`을 그대로 사용합니다.

## 10.1 교육용 Namespace와 Pods 조회 권한을 만든다

`xadksbtmp01`에서 PRD Context인지 먼저 확인합니다.

```bash
kubectl config current-context
```

다음 파일을 만듭니다.

파일명: `nativeapi-lab.yaml`

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: nativeapi-lab
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: nativeapi-lab-sa
  namespace: nativeapi-lab
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: nativeapi-lab-pod-reader
  namespace: nativeapi-lab
rules:
  - apiGroups:
      - ""
    resources:
      - pods
    verbs:
      - get
      - list
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: nativeapi-lab-pod-reader
  namespace: nativeapi-lab
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: nativeapi-lab-pod-reader
subjects:
  - kind: ServiceAccount
    name: nativeapi-lab-sa
    namespace: nativeapi-lab
```

적용하고 확인합니다.

```bash
kubectl apply -f nativeapi-lab.yaml
kubectl -n nativeapi-lab get serviceaccount nativeapi-lab-sa
kubectl -n nativeapi-lab get role nativeapi-lab-pod-reader
kubectl -n nativeapi-lab get rolebinding nativeapi-lab-pod-reader
```

> PRD Kubernetes `v1.22.10`에서는 ServiceAccount의 Token Secret이 자동 생성됩니다. `SECRETS`가 `1`이 될 때까지 ServiceAccount를 다시 확인합니다. Token 원문은 출력하지 않습니다.

```bash
kubectl -n nativeapi-lab get serviceaccount nativeapi-lab-sa
```

```text
NAME                 SECRETS   AGE
nativeapi-lab-sa     1         10s
```

## 10.2 첫 번째 호출 — Token 없이 Pods 조회

```bash
curl -sk -w '\nHTTP %{http_code}\n' https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/nativeapi-lab/pods
```

기대 결과:

```text
reason: Forbidden
user: system:anonymous
HTTP 403
```

> Kubernetes `Status` JSON과 `system:anonymous`가 보이면 FQDN·Ingress·Service·kube-apiserver 경로에는 도달했고 인증 주체가 없어 거부된 것입니다.
>
> NGINX HTML 형태의 `403`이면 Kubernetes RBAC 결과가 아니라 Source 제한에서 거부된 것입니다. 이 경우 다음 호출로 넘어가지 않습니다.

## 10.3 두 번째 호출 — 같은 URL을 ServiceAccount Token으로 조회

> Token을 변수에 저장하거나 화면에 출력하지 않습니다. ServiceAccount가 참조하는 Secret에서 Token을 읽어 요청 Header에 바로 넣습니다.

```bash
curl -sk -w '\nHTTP %{http_code}\n' -H "Authorization: Bearer $(kubectl -n nativeapi-lab get secret "$(kubectl -n nativeapi-lab get serviceaccount nativeapi-lab-sa -o jsonpath='{.secrets[0].name}')" -o jsonpath='{.data.token}' | base64 -d)" https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/nativeapi-lab/pods
```

기대 결과:

```text
kind: PodList
items: []
HTTP 200
```

> `items: []`는 교육용 Namespace에 Pod가 없다는 뜻입니다. `PodList`와 `HTTP 200`이면 ServiceAccount 인증과 Pods `list` 권한이 모두 성공한 것입니다.

## 10.4 세 번째 호출 — 같은 Token으로 Services 조회

> Role에는 Pods `get·list`만 있습니다. 같은 Token으로 권한이 없는 Services를 조회합니다.

```bash
curl -sk -w '\nHTTP %{http_code}\n' -H "Authorization: Bearer $(kubectl -n nativeapi-lab get secret "$(kubectl -n nativeapi-lab get serviceaccount nativeapi-lab-sa -o jsonpath='{.secrets[0].name}')" -o jsonpath='{.data.token}' | base64 -d)" https://nativeapi.xaprdpa01.apps.dks.samsungds.net/api/v1/namespaces/nativeapi-lab/services
```

기대 결과:

```text
user: system:serviceaccount:nativeapi-lab:nativeapi-lab-sa
cannot list resource "services"
reason: Forbidden
HTTP 403
```

## 10.5 세 결과를 한 번에 비교한다

| 호출 | 인증 주체 | Resource | 결과 |
|---|---|---|---|
| Token 없이 조회 | `system:anonymous` | Pods | `403` |
| 교육용 Token 사용 | `nativeapi-lab-sa` | Pods | `200 PodList` |
| 같은 Token 사용 | `nativeapi-lab-sa` | Services | `403` |

```text
첫 번째 403
→ API 경로는 도달했지만 인증되지 않음

200
→ ServiceAccount 인증과 허용된 Pods list 성공

두 번째 403
→ 인증은 성공했지만 Services 권한은 없음
```

> KubeSphere 화면만으로 이 차이를 만들려고 하지 않습니다. KubeSphere는 `nativeapi-lab`의 ServiceAccount·Role·RoleBinding 존재를 확인하는 데 사용하고, 인증·인가 결과는 위 세 HTTP 응답으로 판정합니다.

## 10.6 실습이 끝나면 모두 삭제한다

```bash
kubectl delete -f nativeapi-lab.yaml
kubectl wait --for=delete namespace/nativeapi-lab --timeout=120s
kubectl get namespace nativeapi-lab
```

기대 결과:

```text
Error from server (NotFound): namespaces "nativeapi-lab" not found
```

> Namespace 삭제가 끝나면 ServiceAccount, Role, RoleBinding과 자동 생성된 Token Secret도 함께 사라집니다. 실제 Token 값은 문서·화면·Shell History에 남기지 않습니다.

## 10.7 실습 완료 기준

```text
Token 없음 → 403 system:anonymous
+ Pods get·list Token → 200 PodList
+ 같은 Token으로 Services 조회 → 403 Forbidden
+ nativeapi-lab Namespace 삭제 확인
=
Native API 경로·인증·RBAC 실습 완료
```
