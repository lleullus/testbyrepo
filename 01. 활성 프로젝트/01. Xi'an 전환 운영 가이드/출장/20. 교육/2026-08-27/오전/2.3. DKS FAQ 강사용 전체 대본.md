# 2.3 DKS FAQ 강사용 전체 대본

> [!important] 사용 방법
> 수강생이 DKS를 처음 접한다고 가정한다. 원본 FAQ의 문답부터 읽지 않는다. **사용자가 Application을 실행하려는 이유 → 필요한 공간과 권한 → Image 준비와 실행 → 외부 접속 → 운영 중 변경과 장애** 순서로 하나의 이야기를 만든 뒤, 그 안에서 원본 FAQ의 여덟 항목을 설명한다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
사용자가 하려는 일
→ 왜 필요한가
→ 필요한 역할을 쉬운 말로 설명한다
→ 그 역할의 기술 이름을 붙인다
→ Xi'an 실제 구조에 연결한다
→ 무엇을 보면 사용할 수 있는지 판단한다
→ 실패하면 처음 끊긴 지점을 찾는다
```

## 0-1. 오늘 전체 한 줄

```text
Application을 DKS에서 실행하고 싶다
→ Project와 자원이 필요하다
→ 사용자 권한이 필요하다
→ 실행할 Image가 필요하다
→ Harbor와 Kubernetes를 연결한다
→ 외부 접속 경로를 만든다
→ 운영 중 변경과 장애를 처리한다
```

# 1. 시작 — 사용자는 FAQ가 아니라 Application 실행을 원한다

> 오늘은 DKS FAQ의 질문과 답을 순서대로 읽지 않겠습니다.
>
> 사용자는 FAQ를 읽기 위해 DKS를 사용하는 것이 아닙니다.
>
> 사용자는 자신이 준비한 Application을 DKS에서 실행하고, 필요한 사람에게 서비스를 제공하고 싶어 합니다.
>
> **하지만**, Application 파일 하나만 있다고 Kubernetes에서 바로 실행되는 것은 아닙니다.
>
> Application을 다른 팀과 분리해서 운영할 공간이 필요하고, 사용할 수 있는 CPU·Memory·Storage 범위가 필요하며, 누가 무엇을 할 수 있는지도 정해야 합니다.
>
> 실행할 Container Image를 준비해 Registry에 저장해야 하고, Kubernetes가 그 Image를 가져올 수 있어야 합니다.
>
> Application을 외부 사용자에게 제공하려면 Service, Ingress, DNS와 방화벽 경로도 이어져야 합니다.
>
> **그래서**, 오늘은 DKS를 사용하는 전체 과정을 먼저 따라가겠습니다. 그 과정에서 Project 신청, Harbor 권한, Namespace 변경, `kubectl`, 외부 접속, DevOps, Image 생성과 로그인 질문이 왜 생기는지 연결하겠습니다.

## 1.1 DKS를 네 가지 역할로 먼저 본다

> Xi'an DKS를 처음 볼 때 제품 이름과 Cluster 이름부터 외우지 않겠습니다.
>
> 먼저 네 가지 역할로 나누겠습니다.

| 필요한 역할 | Xi'an DKS의 구성요소 |
|---|---|
| 사용자가 Application Resource와 권한을 관리하는 화면 | KubeSphere Host |
| 실제 Application Pod가 실행되는 환경 | Production·Development Member Cluster |
| Container Image를 저장하고 Push·Pull하는 장소 | Harbor |
| Application이 외부 요청을 받는 입구 | Member Cluster Ingress |

> Xi'an에서는 KubeSphere Host가 사용자 로그인과 Workspace·Project·권한 관리를 담당합니다.
>
> 실제 Application은 Production Member인 `prd-apps-pa01-xas` 또는 Development Member인 `dev-apps-pa01-xas`에서 실행됩니다.
>
> Container Image는 Harbor `prd-harbor-xas`에 저장합니다.
>
> KubeSphere의 관리 영역, Application 실행 영역과 Image 저장 영역은 서로 연결되지만 같은 시스템은 아닙니다.

## 1.2 한 Application의 전체 길을 먼저 본다

```text
AD 계정과 Network 접근 준비
→ DKS 이용 신청
→ Workspace·Project 생성
→ 사용자와 Role 연결
→ CPU·Memory·Storage Quota 설정
→ Source·Binary를 Container Image로 Build
→ Harbor Project에 Image Push
→ Kubernetes가 Private Image Pull
→ Deployment와 Pod 실행
→ Service와 Ingress 연결
→ DNS·VIP-B·Firewall
→ 외부 사용자 접속
```

> 이 흐름을 처음부터 끝까지 모두 한 사람이 처리한다는 뜻은 아닙니다.
>
> 사용자, DKS 운영자, 인증 담당, Network 담당과 Application 담당의 책임이 나뉩니다.
>
> **하지만**, 책임이 나뉜다고 전체 경로가 사라지는 것은 아닙니다. 앞 단계가 준비되지 않으면 뒤 단계는 정상적으로 동작할 수 없습니다.
>
> 따라서 운영자는 메뉴 하나를 처리하는 데 그치지 않고, 지금 요청이 전체 경로의 어느 부분에 있는지 이해해야 합니다.

> [!warning] 교육 실행 경계
> 오늘은 기존 정상 환경과 원본 Manual을 기준으로 구조와 판단 방법을 설명한다. Project·권한·Quota 변경, Namespace 삭제, Credential 발급과 방화벽 신청을 교육용으로 임의 실행하지 않는다. 실제 변경은 대상·승인·현재 상태와 해당 절차가 확인된 경우에만 수행한다.

# 2. Application을 실행할 공간과 자원이 필요하다

> 사용자가 “DKS를 사용하고 싶습니다”라고 요청했다고 하겠습니다.
>
> 이 요청의 실제 목적은 계정을 하나 만드는 것이 아니라, Application을 배포하고 운영할 공간을 준비하는 것입니다.
>
> **하지만**, 여러 Team과 Application이 같은 Kubernetes Cluster를 사용하므로 모든 Resource를 한 공간에 섞을 수는 없습니다.
>
> 한 Team의 사용자가 다른 Team의 Workload를 변경하거나, 한 Application이 Cluster의 CPU와 Memory를 모두 사용하는 상황을 막아야 합니다.
>
> **그래서**, Application별 공간을 만들고, 그 공간을 사용할 사람과 자원 범위를 함께 정합니다.

## 2.1 Workspace, Project와 Namespace를 역할부터 구분한다

> KubeSphere의 **Workspace**는 사용자와 Project를 묶는 관리 단위입니다.
>
> KubeSphere의 **Project**는 Application의 Workload, Service, Secret과 Storage 같은 Resource를 운영하는 공간입니다.
>
> Kubernetes에서 이 공간의 실제 이름은 **Namespace**입니다.
>
> 따라서 KubeSphere Project와 Kubernetes Namespace는 화면과 API에서 부르는 이름이 다르지만 같은 Application 공간을 가리킵니다.

```text
Workspace
→ 사용자와 Project를 묶는 관리 단위

KubeSphere Project
= Kubernetes Namespace
→ Application Resource가 놓이는 실행 공간
```

> Xi'an DKS 정책에서는 Workspace 하나와 Project 하나를 1:1로 구성합니다.
>
> **하지만**, Workspace와 Project가 만들어졌다고 사용자가 자동으로 그 공간을 사용할 수 있는 것은 아닙니다.
>
> 사용자를 Member로 연결하고, 허용할 작업에 맞는 Role을 부여해야 합니다.

## 2.2 대상 환경과 Project를 먼저 결정한다

> Project를 만들기 전에 Application이 Development와 Production 중 어느 환경에서 실행될지 확인합니다.
>
> 환경이 달라지면 대상 Member Cluster와 외부 Application Domain이 달라지기 때문입니다.

| 환경 | Member Cluster | Application Ingress Domain |
|---|---|---|
| Production | `prd-apps-pa01-xas` | `*.xaprdpa01.apps.dks.samsungds.net` |
| Development | `dev-apps-pa01-xas` | `*.xadevpa01.apps.dks.samsungds.net` |

> Project 이름, 대상 환경, CPU·Memory·Storage, 사용자 AD 계정과 필요한 권한을 신청 내용에서 함께 확인합니다.
>
> 사용자가 KubeSphere에 한 번도 로그인하지 않았다면 사용자 객체와 로그인 이력 확인이 선행될 수 있습니다.
>
> Dashboard와 사용할 서비스에 도달할 Network와 방화벽 경로도 별도 전제입니다.

## 2.3 Role은 사용자가 할 수 있는 일을 정한다

> Member로 등록됐다는 것은 사용자가 해당 공간과 연결됐다는 뜻입니다.
>
> **하지만**, 연결됐다는 사실만으로 모든 작업을 할 수 있는 것은 아닙니다.
>
> Role은 사용자가 Project 안에서 조회, 생성, 변경 또는 멤버 관리 중 무엇을 할 수 있는지 정합니다.

| KubeSphere Role | 의미 |
|---|---|
| `project-viewer` | Project Resource 조회 |
| `project-operator` | 멤버·역할·Project 설정을 제외한 Application Resource 운영 |
| `project-admin` | Resource·설정·멤버 관리, 별도 운영 정책에 따라 부여 |

> Xi'an 기준 문서에서는 신청서의 `User`를 `project-viewer`, `Admin`을 `project-operator`에 연결합니다.
>
> 멤버 관리까지 가능한 `project-admin`은 이름이 더 강해 보인다는 이유로 임의 부여하지 않고 별도 운영 정책을 확인합니다.

## 2.4 Quota는 사용할 수 있는 자원의 상한이다

> 여러 Project가 같은 Cluster의 CPU, Memory와 Storage를 사용합니다.
>
> **하지만**, 제한이 없으면 한 Project의 Resource 요청이 다른 Application의 운영 여유까지 소비할 수 있습니다.
>
> **그래서**, 신청한 범위에 따라 **Quota**를 설정합니다.

```text
Workspace Quota
→ Workspace 전체 CPU·Memory 상한

Project Quota
→ Project의 CPU·Memory 상한

Storage ResourceQuota
→ Namespace 전체와 StorageClass별 Storage 요청 상한
```

> Xi'an DKS는 Workspace와 Project가 1:1이므로 Workspace와 Project의 CPU·Memory Quota를 같은 승인값으로 설정합니다.
>
> Storage는 신청서 숫자만 보고 적용하지 않습니다. 대상 Cluster의 현재 StorageClass 이름을 확인하고 Namespace 전체 요청량과 해당 StorageClass 요청량을 함께 제한합니다.

## 2.5 공간 준비의 실제 완료를 판단한다

```text
Workspace와 Project 존재
+ 대상 Member Cluster 일치
+ 사용자 Member 존재
+ Role이 승인 내용과 일치
+ CPU·Memory·Storage Quota 일치
+ 사용자가 자신의 Project를 조회 가능
=
Application 배포를 시작할 수 있는 공간 준비
```

> Project 이름이 화면에 보인다는 사실만으로 준비가 끝난 것은 아닙니다.
>
> 사용자가 보지 못하거나, Role이 다르거나, Quota가 비어 있거나, 다른 Cluster에 연결됐다면 실제 이용 상태가 아닙니다.

# 3. DKS는 Source를 바로 실행하지 않는다

> 이제 Application 공간이 준비됐다고 하겠습니다.
>
> 사용자가 Source Code나 Binary 파일을 가지고 와서 “이 파일을 DKS에 배포해 주세요”라고 요청할 수 있습니다.
>
> **하지만**, Kubernetes는 Source Code를 받아서 자동으로 Build하는 시스템이 아닙니다.
>
> Kubernetes가 실행하는 것은 필요한 파일과 Library, 실행환경을 하나로 묶은 **Container Image**입니다.

## 3.1 Source에서 Pod까지의 경로

```text
Source·Binary
→ Docker·Podman 또는 승인된 Build 시스템
→ Container Image
→ Harbor 또는 승인된 Registry
→ Kubernetes가 Image Pull
→ Container 실행
→ Pod Ready
```

> Source나 Binary를 Container Image로 만드는 작업을 **Build**라고 합니다.
>
> Docker와 Podman은 Image를 만들 수 있는 도구입니다.
>
> DKS의 Kubernetes Runtime은 준비된 Image를 가져와 실행합니다.
>
> Xi'an DKS의 표준 Container Runtime인 ContainerD는 Image 실행과 Pull을 담당하지만 Source Build 도구는 아닙니다.

## 3.2 Image Build의 책임을 구분한다

> Image 생성은 사용자 또는 승인된 Build 시스템의 책임입니다.
>
> DKS 운영팀이 사용자의 Source 구조와 Build Dependency를 대신 해석해 Image를 만드는 서비스가 아닙니다.
>
> **그래서**, 사용자는 Dockerfile과 Build 입력을 준비하고, 승인된 환경에서 Image를 만든 뒤 Registry에 Push해야 합니다.
>
> DKS는 그 Image를 Kubernetes Workload에서 실행할 수 있는 환경을 제공합니다.

```text
DKS에서 Image 실행
≠ DKS에서 Source Build
```

## 3.3 DevOps 요청은 Image 한 번 만드는 요청과 다르다

> “Image를 만들어야 합니다”와 “DevOps를 사용하고 싶습니다”도 같은 요청이 아닙니다.
>
> Image Build는 특정 Source를 실행 가능한 Image로 만드는 작업입니다.
>
> DevOps 또는 CI/CD는 Source 변경을 감지하고 Build, Test, 배포를 반복 자동화하는 더 큰 흐름입니다.

```text
Image Build
≠ CI Pipeline
≠ 배포 자동화
≠ DevOps 플랫폼 전체
```

> 원본 DKS FAQ 기준으로 DKS는 Docker Build와 DevOps 기능을 직접 제공하지 않습니다.
>
> 자동화가 필요하면 P-DEP 또는 사용자 조직에서 승인한 Build·배포 시스템을 확인합니다.
>
> 존재하지 않는 DKS 기능을 약속하거나, 운영 기준이 확인되지 않은 임시 Build 환경을 만들어 안내하지 않습니다.

# 4. 만든 Image를 Harbor에 저장한다

> Image를 만들었다면 Kubernetes Worker가 가져갈 수 있는 장소에 저장해야 합니다.
>
> Worker마다 Image 파일을 직접 복사하면 Node마다 Version이 달라질 수 있고, 새 Worker나 새 Pod가 같은 Image를 안정적으로 받을 수 없습니다.
>
> **그래서**, Image를 중앙 Registry에 저장합니다.
>
> Xi'an DKS에서는 Harbor `prd-harbor-xas`가 이 역할을 담당하며, 접속 FQDN은 `xa.dcr.dks.samsungds.net`입니다.

## 4.1 Harbor Project와 KubeSphere Project는 다르다

```text
KubeSphere Project
→ Kubernetes Application Resource와 Workload 공간

Harbor Project
→ Container Image, Repository와 접근 권한 공간
```

> 이름은 모두 Project이지만 서로 다른 시스템의 객체입니다.
>
> KubeSphere Project를 만들었다고 같은 이름의 Harbor Project가 자동으로 생기지 않습니다.
>
> Application 공간과 Image 공간이 모두 필요하면 각각 승인 내용과 운영 절차에 따라 준비해야 합니다.

## 4.2 Harbor Login과 Project 권한도 다르다

> 사용자가 Harbor Login에 성공했다는 것은 Harbor가 사용자의 인증정보를 확인했다는 뜻입니다.
>
> **하지만**, Login 성공이 모든 Private Project의 Image를 Push하거나 Pull할 수 있다는 뜻은 아닙니다.
>
> 대상 Harbor Project의 Member여야 하고, 필요한 작업에 맞는 Role이 있어야 합니다.

| Harbor Role | 일반적인 역할 의미 |
|---|---|
| `Developer` | Image Push·Pull |
| `ProjectAdmin` | Image Push·Pull과 Project Member 관리 |

> 신청서의 Admin/User 이름만 보고 Harbor Role을 자동으로 확정하지 않습니다.
>
> 사용자가 Image Push·Pull만 필요한지, Member 관리까지 필요한지 확인하고 승인된 Harbor 운영 정책에 따라 Role을 적용합니다.

## 4.3 과거 예시를 Xi'an 현재값으로 사용하지 않는다

> 원본 FAQ에는 AD 보안그룹 `SG1599`와 Harbor Quota `10GB`가 기록돼 있습니다.
>
> **하지만**, 현재 기준 문서에서는 `SG1599`와 신청 경로가 Xi'an 최종 운영값으로 확정되지 않았습니다.
>
> `10GB`도 모든 Project에 적용하는 고정값이 아니라 문서 예시입니다.
>
> **그래서**, 현재 유효한 AD Group, 신청 경로, Project Quota와 Role은 운영팀과 승인 내용을 기준으로 확인합니다.

## 4.4 Harbor의 실제 사용 가능 상태

```text
Harbor 접속 가능
+ 사용자 Login 성공
+ 대상 Project가 Private·Quota 승인값과 일치
+ 사용자 Member와 Role 일치
+ 실제 Image Push 또는 허용된 Pull 성공
=
해당 사용자의 Harbor Project 사용 가능
```

> Harbor 화면이 열린다는 사실, Login이 성공했다는 사실과 Project 이름이 보인다는 사실은 서로 다른 단계의 증거입니다.
>
> 사용 목적이 Image Push라면 실제로 Push 권한이 있어야 하고, Pull만 허용된 사용자라면 허용 범위에서 Pull이 동작해야 합니다.

# 5. Harbor의 Private Image를 Kubernetes에서 실행한다

> Harbor에 Image가 저장됐다고 하겠습니다.
>
> 이제 Deployment에 Image 주소를 지정하면 Worker가 Harbor에서 Image를 Pull해 Container를 실행합니다.
>
> **하지만**, Harbor Project가 Private이면 Worker도 인증 없이 Image를 가져올 수 없습니다.
>
> Kubernetes Project 안에 Registry 인증정보를 저장한 **Image Secret**이 필요하고, Workload가 그 Secret을 사용하도록 연결해야 합니다.

## 5.1 Private Image 실행 경로

```text
Developer·CI가 Harbor Login
→ Image Push
→ Harbor Project·Repository·Tag
→ KubeSphere Project의 Image Secret
→ Deployment의 Image 주소와 imagePullSecrets
→ Worker가 Harbor에서 Image Pull
→ Container 실행
→ Pod Running·Ready
```

> Image 주소는 Harbor FQDN, Harbor Project, Repository와 Tag를 모두 포함합니다.

```text
xa.dcr.dks.samsungds.net/<harbor-project>/<repository>:<tag>
```

> 이 값 중 하나라도 실제 Image와 다르면 Worker는 원하는 Image를 찾지 못합니다.
>
> Secret이 없거나 잘못된 Credential을 담고 있으면 Private Registry 인증에서 실패합니다.

## 5.2 단계별 성공을 구분한다

```text
Image Build 성공
≠ Harbor Push 성공
≠ Worker Image Pull 성공
≠ Container 실행 성공
≠ Pod Ready
```

> Build가 성공했다는 것은 Image가 만들어졌다는 뜻입니다.
>
> Push가 성공했다는 것은 Image가 Harbor에 저장됐다는 뜻입니다.
>
> Worker Pull이 성공했다는 것은 Kubernetes가 Image에 접근할 수 있다는 뜻입니다.
>
> Pod가 Ready가 돼야 Application이 Kubernetes 안에서 요청을 처리할 준비가 됐다고 판단할 수 있습니다.

> [!warning] Credential 경계
> Harbor Password, Docker Credential, Image Secret 원문과 kubeconfig 인증정보를 교육 화면·문서·로그에 노출하지 않는다. 예시는 구조만 설명하고 실제 Secret 값은 사용하지 않는다.

# 6. 실행한 Application을 외부에 공개한다

> Pod가 정상적으로 실행돼도 외부 사용자가 Pod IP로 직접 접속하는 것은 아닙니다.
>
> Pod는 재시작되면서 IP가 바뀔 수 있고, 여러 Pod가 같은 Application을 제공할 수도 있습니다.
>
> **그래서**, Service가 Pod를 하나의 내부 접점으로 묶고, Ingress가 외부 Domain 요청을 Service로 전달합니다.

## 6.1 Pod에서 사용자까지의 전체 경로

```text
사용자 Client
→ DNS에서 Application FQDN 조회
→ Member Cluster Ingress VIP-B
→ Ingress Controller
→ Application Ingress
→ Service
→ Ready Pod Endpoint
→ Container Application
```

> Network 관점에서 사용자 Source IP에서 목적지 VIP와 Port로 방화벽 경로도 열려 있어야 합니다.
>
> 따라서 Application 외부 접속은 Pod나 Ingress 하나만 확인해서 끝나지 않습니다.

## 6.2 환경에 따라 Domain이 달라진다

> Production Application은 `*.xaprdpa01.apps.dks.samsungds.net`, Development Application은 `*.xadevpa01.apps.dks.samsungds.net` 패턴을 사용합니다.
>
> 실제 FQDN의 `*` 부분에는 승인된 Application 이름이 들어갑니다.
>
> FAQ의 `[application-name].ingress-cluster` 같은 표현은 구조를 설명하는 형식이지 실제 접속 URL이 아닙니다.
>
> 대상 Cluster, 실제 Ingress Host와 DNS 등록값을 확인해야 합니다.

## 6.3 해외 사업장 방화벽 신청의 적용 범위를 구분한다

> 해외 사업장에서 국내 GH/HS의 DKS 서비스 URL로 접근하는 경우에는 별도의 GSAMS 방화벽 신청 가이드가 있습니다.
>
> 해당 가이드의 `1.1.1.1`, `80/443` 입력 방식은 그 특정 신청 유형에 대한 안내입니다.
>
> **하지만**, 모든 Xi'an Application 접속 요청에 같은 값을 적용할 수는 없습니다.
>
> 접속 출발지, 실제 대상 서비스, FQDN, 목적지와 현지 승인 절차를 먼저 확인한 뒤 적용 가능한 방화벽 절차를 선택합니다.

## 6.4 외부 접근의 실제 완료를 판단한다

```text
Pod Ready
+ Service에 Ready Endpoint 존재
+ Ingress Host·Backend 일치
+ DNS가 올바른 VIP-B를 가리킴
+ Source에서 목적지 Port까지 Firewall 승인
+ 실제 Client에서 Application 응답 확인
=
외부 Application 접근 가능
```

> Ingress 객체가 존재한다는 사실만으로 외부 접속이 완료된 것은 아닙니다.
>
> Service Endpoint가 없거나, DNS가 다른 VIP를 가리키거나, 방화벽 승인이 끝나지 않았다면 사용자는 Application에 도달하지 못합니다.

# 7. Web 화면과 kubectl 접근은 별도 경로다

> 사용자가 KubeSphere 화면 대신 `kubectl` 명령을 사용하고 싶다고 요청할 수 있습니다.
>
> `kubectl`은 Kubernetes API에 요청을 보내 Resource를 조회하거나 변경하는 CLI입니다.
>
> **하지만**, KubeSphere Web 화면을 사용할 수 있다고 Bastion OS 접근과 `kubectl`이 자동으로 허용되는 것은 아닙니다.
>
> Web UI, Bastion 접근, Kubernetes Client 인증과 RBAC은 서로 다른 경계입니다.

## 7.1 kubectl 사용 경로

```text
사용자 AD 계정
→ Bastion 계정과 Firewall
→ CyberArk 접근 권한
→ 사용자별 kubeconfig
→ 올바른 Cluster Context와 VIP
→ Kubernetes API 인증
→ RBAC
→ 허용된 Project Resource
```

> 각 Cluster는 승인된 Bastion을 통해 CLI 접근을 제공합니다.
>
> Bastion 계정명, CyberArk 권한, 대상 Cluster와 Project가 요청 내용과 일치해야 합니다.
>
> kubeconfig에는 Cluster 주소, CA와 사용자 인증정보, Context가 들어 있습니다.
>
> Context는 지금 명령을 어느 Cluster와 사용자 자격으로 보낼지 결정합니다.

## 7.2 kubeconfig가 있다고 모든 권한이 생기는 것은 아니다

> kubeconfig 파일이 존재한다는 것은 Client 설정이 있다는 뜻입니다.
>
> **하지만**, 잘못된 Cluster VIP를 가리키거나 Context가 다르면 원하는 Cluster에 요청하지 못합니다.
>
> 인증이 성공해도 RBAC이 허용하지 않은 Resource와 Verb는 사용할 수 없습니다.

```text
Bastion Login 성공
≠ Kubernetes API 인증 성공
≠ 대상 Namespace 권한 보유
```

## 7.3 kubectl의 실제 사용 가능 상태

```text
CyberArk를 통한 Bastion 접근
+ 사용자 kubeconfig 파일 권한과 소유자 정상
+ current-context가 대상 Cluster와 일치
+ Kubernetes API 인증 성공
+ 승인된 Project에서 허용된 조회·작업 성공
=
kubectl 사용 가능
```

> [!warning] kubeconfig 경계
> kubeconfig에는 Client Certificate와 Private Key 등 인증정보가 포함될 수 있다. 원문을 교육 자료에 붙여넣거나 다른 사용자와 공유하지 않는다. 화면 시연에서는 사용자명, Token, Certificate와 Key를 마스킹한다.

# 8. 자원을 줄이는 것과 공간을 삭제하는 것은 다르다

> 운영 중에는 처음 신청한 자원을 줄이거나 더 이상 사용하지 않는 Project를 삭제해 달라는 요청이 들어올 수 있습니다.
>
> **하지만**, Quota를 줄이는 작업과 Namespace를 삭제하는 작업은 영향이 전혀 다릅니다.

## 8.1 Quota 축소는 공간을 유지한 채 상한을 바꾼다

> Quota 축소는 Workspace와 Project를 유지하면서 사용할 수 있는 CPU·Memory·Storage 상한을 낮추는 변경입니다.
>
> 신청 변경값만 보고 바로 숫자를 낮추지 않습니다.
>
> 현재 Workload의 Requests와 Limits, 현재 PVC 요청량과 실제 사용 상태를 확인해야 합니다.

```text
승인된 새 Quota
→ 현재 CPU·Memory Requests·Limits
→ 현재 PVC와 Storage 요청량
→ Workspace·Project 1:1 값 일치
→ 영향 확인
→ 승인된 절차로 변경
→ 변경 후 Quota와 Workload 상태 확인
```

> 현재 요청량보다 낮은 Quota를 적용하면 새 Resource 생성이나 확장이 거부될 수 있습니다.
>
> Storage Quota를 낮춘다고 기존 PVC의 데이터가 자동으로 줄어드는 것도 아닙니다.

## 8.2 Namespace 삭제는 Application 공간을 제거한다

> Namespace 삭제는 자원 상한을 바꾸는 작업이 아니라 Application Resource가 놓인 공간을 제거하는 작업입니다.
>
> KubeSphere에서 Workspace와 Project를 1:1로 운영하더라도, 화면의 이름 하나만 지우는 작업으로 보면 안 됩니다.

삭제 전에 확인할 영향:

- Deployment·StatefulSet·DaemonSet·Job 등 Workload
- Service·Ingress
- ConfigMap·Secret
- PVC와 연결된 PV
- PV Reclaim Policy
- 보존해야 할 Application 데이터
- 사용자 Member와 접근 권한
- Backup과 복구 가능성
- 대상 Cluster·Workspace·Project
- 승인자와 작업 시간

> Harbor Image는 Harbor Project에 저장되므로 Kubernetes Namespace와 별도 객체입니다.
>
> Namespace를 삭제했다고 Harbor Image가 자동으로 삭제되는 것도 아니고, Harbor Image가 남아 있다고 Namespace의 Application 데이터가 복구되는 것도 아닙니다.

```text
Quota 축소
≠ Namespace 삭제

Namespace 삭제
≠ Harbor Project 삭제

Project 이름이 사라짐
≠ 데이터 영향과 복구 확인 완료
```

> 현재 운영 자료에는 Namespace 완전 삭제의 영향 확인, 백업, 중단과 복구를 모두 판정하는 충분한 전용 Runbook이 확인되지 않습니다.
>
> **따라서**, 대상 Resource, PVC·PV, Reclaim Policy, Backup, 승인자와 승인된 삭제 절차가 확인되지 않으면 FAQ만 보고 삭제하지 않습니다.

# 9. 문제가 생기면 처음 끊긴 지점을 찾는다

> 지금까지 Application이 DKS에서 실행되고 사용자에게 도달하는 전체 경로를 봤습니다.
>
> 장애가 생기면 보이는 단어 하나만 보고 같은 조치를 반복하지 않습니다.
>
> 요청이 정상 경로의 어디까지 도달했는지 확인하고, 처음 실패한 지점부터 봅니다.

## 9.1 KubeSphere 또는 Harbor 화면이 열리지 않는다

> Login 화면 자체가 열리지 않는다면 Username과 Password보다 앞선 단계에서 실패한 것입니다.

```text
입력한 FQDN
→ Client DNS 조회
→ Network Route
→ Firewall
→ VIP 또는 서비스 Endpoint
→ HTTPS 응답
```

> 먼저 대상 서비스와 URL이 맞는지 확인합니다.
>
> 그다음 DNS가 올바른 주소를 반환하는지, 사용자 Source에서 목적지 80/443 경로가 승인됐는지, 서비스가 응답하는지 순서대로 봅니다.

## 9.2 화면은 열리지만 Login이 실패한다

> Login 화면이 보인다는 것은 적어도 Client가 서비스 앞단까지 도달했다는 뜻입니다.
>
> `Wrong username or password`가 보이면 대상 서비스, AD 계정 상태, 현재 유효한 AD Group, Password와 서비스 인증 연동을 확인합니다.
>
> 원본 FAQ의 `SG1599`를 현재 Xi'an 확정값으로 바로 사용하지 않습니다.
>
> 원인 확인 없이 Password Reset만 반복하지 않습니다.

## 9.3 Login은 되지만 Project가 보이지 않는다

> Login 성공은 사용자 인증 성공입니다.
>
> **하지만**, 특정 Project가 보이고 사용할 수 있다는 뜻은 아닙니다.

```text
대상 KubeSphere Host
→ Workspace Member
→ Project Member
→ Role
→ Project가 연결된 Member Cluster
```

> Harbor에서도 같은 원칙이 적용됩니다. Login은 성공하지만 대상 Harbor Project의 Member가 아니면 해당 Private Project를 사용할 수 없습니다.

## 9.4 Harbor Login은 되지만 Push가 거부된다

```text
Image 주소의 Harbor FQDN
→ 대상 Harbor Project
→ 사용자 Member
→ Role의 Push 권한
→ Repository·Tag
→ Project Quota
```

> 이 증상에서 Password 변경을 첫 조치로 삼지 않습니다.
>
> Login이 이미 성공했다면 Project 권한과 Image 경로를 먼저 구분합니다.

## 9.5 Harbor에는 Image가 있지만 Pod가 Pull하지 못한다

```text
Image 주소와 Tag
→ Harbor Repository 존재
→ KubeSphere Project의 Image Secret
→ Deployment의 imagePullSecrets
→ Worker DNS·Network·CA 신뢰
→ Harbor Pull 권한
→ Pod Event
```

> `ImagePullBackOff`는 최종 증상입니다.
>
> Pod Event의 실제 오류에서 `not found`, `unauthorized`, `x509`, Network Timeout을 구분하고 해당 경계부터 확인합니다.

## 9.6 Pod는 정상인데 Application URL로 접속할 수 없다

```text
Pod Ready
→ Service Selector와 Endpoint
→ Ingress Host·Backend
→ DNS
→ VIP-B
→ Firewall
→ Client 요청
```

> Pod가 Ready라면 Image Build와 Container 시작 단계는 통과했습니다.
>
> 이제 Application 내부 Listen Port부터 외부 접속 경로까지 처음 끊긴 지점을 찾습니다.

## 9.7 kubectl을 사용할 수 없다

```text
CyberArk 권한
→ Bastion Login
→ kubeconfig 파일과 권한
→ current-context
→ API Server 연결
→ 사용자 인증
→ RBAC
```

> `connection refused`, `x509`, `Unauthorized`, `Forbidden`은 같은 장애가 아닙니다.
>
> 연결, 인증서 신뢰, 사용자 인증과 권한 중 어느 단계에서 실패했는지 오류를 기준으로 구분합니다.

# 10. 한 Application을 처음부터 끝까지 다시 따라간다

> 이제 한 사용자가 새로운 Application을 DKS에서 운영하려는 상황으로 전체 내용을 다시 연결하겠습니다.
>
> 사용자는 먼저 Application Source와 실행 조건을 가지고 있습니다.
>
> **하지만**, Kubernetes는 Source를 직접 실행하지 않으므로 사용자는 승인된 Build 환경에서 Container Image를 만듭니다.
>
> 만든 Image를 여러 Worker가 가져갈 수 있도록 Harbor Project에 Push합니다.
>
> Harbor가 Private이므로 사용자는 대상 Project의 Member와 Push 권한이 필요합니다.
>
> Application을 실행할 Production 또는 Development Member Cluster를 정하고, 신청한 CPU·Memory·Storage와 사용자 정보에 따라 Workspace, KubeSphere Project, Role과 Quota를 준비합니다.
>
> KubeSphere Project에는 Harbor 인증정보를 담은 Image Secret을 만들고, Deployment에 정확한 Image 주소와 Secret을 연결합니다.
>
> Worker가 Image를 Pull하고 Pod가 Running과 Ready가 되는지 확인합니다.
>
> 외부 사용자가 접속해야 한다면 Service가 Ready Pod를 찾고, Ingress가 승인된 Application FQDN을 Service에 연결하도록 구성합니다.
>
> DNS가 해당 FQDN을 올바른 VIP-B로 보내고, 사용자 Source에서 목적지까지 방화벽이 승인돼야 합니다.
>
> 실제 Client에서 Application 응답을 확인해야 전체 사용 경로가 완성됩니다.

```text
Source
→ Build
→ Image
→ Harbor Project·권한
→ DKS Project·Role·Quota
→ Image Secret
→ Deployment
→ Worker Pull
→ Pod Ready
→ Service
→ Ingress
→ DNS·VIP-B·Firewall
→ 사용자 접속
```

## 10.1 운영 중 추가 요구도 같은 경로에서 이해한다

> Web UI로 부족해 `kubectl`이 필요하면 Bastion, CyberArk, 사용자 kubeconfig와 RBAC이라는 별도 접근 경로를 준비합니다.
>
> 자원을 줄이려면 현재 사용량과 Workload 영향을 확인하고 Quota를 변경합니다.
>
> 서비스를 종료하려면 Namespace 삭제 전에 Workload, PVC·PV, 데이터, Backup과 복구 가능성을 확인합니다.
>
> 장애가 생기면 전체 경로를 처음부터 무작정 다시 구성하지 않고, 실제로 처음 끊긴 지점부터 확인합니다.

| Namespace 축소 또는 삭제 | 운영 중 자원 변경과 Application 공간 종료 |
| CLI 사용 | Web UI와 별도의 Bastion·kubeconfig·RBAC 경로 |
| 외부 Application 접근 | Pod에서 사용자까지 Service·Ingress·DNS·Firewall 연결 |
| DKS DevOps | DKS 제공 범위와 외부 CI/CD 책임 구분 |
| Image 생성과 Source 배포 | Source→Build→Image→Registry→Pod 흐름 |
| 로그인 오류 | Network·인증·Member·Role 중 첫 실패 지점 확인 |

> FAQ는 이 전체 구조를 대신하는 상세 Runbook이 아닙니다.
>
> **하지만**, 짧은 답만 외우는 문서도 아닙니다.
>
> 각 질문이 전체 DKS 사용 경로의 어느 부분에서 생겼는지 이해하고, 현재 상태와 승인값을 확인한 뒤 해당 Manual의 실제 절차로 들어가야 합니다.

# 12. 완료 기준 — 전체 경로를 설명하고 실제 증거를 구분할 수 있는가

> 오늘 교육의 완료 기준은 FAQ 문장을 외우는 것이 아닙니다.
>
> 사용자가 DKS에서 Application을 실행하려 할 때 필요한 공간, 자원, Image, 권한과 접속 경로를 하나의 이야기로 설명할 수 있어야 합니다.
>
> 또한 화면에 객체가 보이는 것과 실제 사용 가능한 상태를 구분해야 합니다.

```text
Project 존재
≠ 사용자·Role·Quota 정상

Harbor Login 성공
≠ 대상 Project Push·Pull 권한

Image 존재
≠ Worker Pull 성공

Pod Running
≠ Pod Ready

Ingress 존재
≠ 외부 Client 접속 성공

kubeconfig 존재
≠ 인증·RBAC 정상

Quota 변경
≠ 기존 Workload 영향 없음
```

> **결국**, DKS 운영은 메뉴를 하나씩 만드는 작업이 아니라 다음 연결을 실제 증거로 확인하는 일입니다.

```text
사용자와 권한
+ Application 공간과 자원
+ Image 준비와 Registry
+ Kubernetes 실행
+ 외부 접근
+ 변경·장애 경계
=
운영 가능한 Application 경로
```

# 13. 마지막 확인 질문

> 기술 이름만 외웠는지 묻지 않고, 문제와 역할과 연결을 자기 말로 설명할 수 있는지 확인합니다.

1. 사용자가 Source만 가지고 왔을 때 왜 바로 DKS에 배포할 수 없는가?
2. KubeSphere Workspace, KubeSphere Project와 Kubernetes Namespace는 어떻게 연결되는가?
3. Project가 생성돼도 사용 준비가 끝난 것이 아닌 이유는 무엇인가?
4. Workspace·Project Quota와 Storage ResourceQuota는 각각 무엇을 제한하는가?
5. DKS에서 Image 실행과 Image Build는 누가 각각 담당하는가?
6. Image Build와 DevOps·CI/CD는 무엇이 다른가?
7. Harbor Project와 KubeSphere Project는 무엇이 다른가?
8. Harbor Login은 되지만 Image Push가 실패할 때 무엇을 확인하는가?
9. Private Harbor Image가 Pod에서 실행되기까지 어떤 경로를 거치는가?
10. Pod가 Ready여도 외부 Application 접속이 실패할 수 있는 이유는 무엇인가?
11. KubeSphere Web 권한이 있어도 `kubectl`을 바로 사용할 수 없는 이유는 무엇인가?
12. Quota 축소와 Namespace 삭제는 무엇이 다른가?
13. `Wrong username or password`에서 Password 외에 무엇을 구분해야 하는가?
14. `ImagePullBackOff`에서 어떤 오류 경계를 구분해야 하는가?
15. 전체 흐름에서 처음 끊긴 지점을 찾는다는 것은 무엇을 의미하는가?
