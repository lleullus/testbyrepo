# Harbor 교육 교재

> [!summary] 오늘의 목표
> Harbor를 처음 보는 사람도 **왜 필요한지 → 무엇을 하는지 → 어떤 구조인지 → 운영자는 무엇을 하는지** 순서로 이해하는 것이 목표다. 8/25에 들었던 Kubernetes 용어를 기억하고 있다고 가정하지 않는다.

# Part 0. Harbor를 보기 전에 아주 짧게 다시 시작한다

## 1. 프로그램을 실행하려면 무엇이 필요한가

Application을 실행하려면 프로그램뿐 아니라 필요한 파일과 Library, 실행환경도 함께 있어야 한다.

**그래서**, 이 요소들을 하나로 묶어 동일한 형태로 전달할 수 있게 만든 실행 원본이 **Container Image**다.

Image를 실제로 실행한 상태가 **Container**이고, Kubernetes에서는 이 Container가 **Pod 안에서** 실행된다. 여기서는 Pod를 Kubernetes에서 Container가 실행되는 기본 단위로 이해하면 충분하다.

![[harbor-image-container-concept.png]]

*Application 실행 요소를 Container Image로 묶고, Image를 실행해 Pod 안의 Container가 되는 흐름*

**하지만**, Worker가 여러 대라면 같은 Image를 각 Worker에 어떻게 전달할지 정해야 한다.

## 2. Image를 서버마다 직접 복사하면 왜 불편한가

Kubernetes에서 Application Container가 실행되는 서버를 **Worker Node**라고 한다. Worker가 한 대라면 Image를 직접 복사해 사용할 수도 있다.

**하지만**, Worker가 여러 대면 같은 복사를 반복해야 한다.

- 일부 Worker에 이전 Image Version이 남을 수 있다.
- 새 Worker가 추가될 때마다 Image를 다시 전달해야 한다.
- Application이 다른 Worker에 배치됐는데 필요한 Image가 없을 수 있다.
- 어느 Image가 현재 기준 Version인지 관리하기 어려워진다.

**그래서**, Image를 한곳에 보관하고 모든 Worker가 같은 위치에서 필요한 Image를 가져오게 한다.

이 **Container Image 중앙 저장소**를 **Registry**라고 한다.

## 3. Harbor는 무엇인가

Registry는 Container Image 중앙 저장소의 일반적인 이름이다. Xi'an DKS에서는 **Harbor**가 이 역할을 담당한다.

**하지만**, 조직 내부 Image를 아무나 저장하거나 가져가게 할 수는 없다.

**그래서**, Harbor는 사용자 인증과 접근 권한을 확인하는 **Private Registry**로 운영한다.

Harbor를 사용할 때는 Image가 저장소로 들어가는 방향과 저장소에서 나오는 방향을 구분해야 한다.

## 4. Push와 Pull도 먼저 쉬운 말로 본다

Harbor에 Image를 올리는 동작을 **Push**, Harbor에서 Image를 가져오는 동작을 **Pull**이라고 한다.

Developer나 CI가 Image를 Harbor에 Push하고, Kubernetes Worker는 필요한 Image를 Pull해서 Container를 실행한다.

**하지만**, Push와 Pull이 동작하려면 Harbor 자체가 준비되어 있어야 하고, Image를 저장할 Project와 이를 사용할 User 권한도 필요하다.

전체 교육은 다음 인과관계로 이어진다.

`Application 실행 요소 → Container Image → 중앙 Registry → Xi'an Harbor → Harbor 실행·주소·HTTPS 신뢰·저장공간 → Project → Private·Quota → Member·Role → Push·Pull → Kubernetes 인증 → Worker Pull → Pod 실행`

**하지만**, 각 단계의 화면이나 상태 하나가 성공했다고 전체 경로가 정상인 것은 아니다. 이후 절에서는 각 단계의 역할과 완료 기준을 구분한다.

## 7. 현재 Xi'an에서 설치 Manual을 배우는 이유

현재 Xi'an Harbor는 이미 구축되어 있다.

따라서 오늘 Harbor를 다시 설치하지 않는다.

3.1을 배우는 목적은 다음과 같다.

```text
Harbor가 어떤 기반 위에서 동작하는가?
→ 설치/복구 시 무엇이 필요한가?
→ 무엇을 확인해야 실제 정상인가?
```

즉 명령어 암기보다 **구조와 완료 판단**이 먼저다.

## 8. Harbor도 결국 하나의 서비스다

Harbor라고 해서 특별한 마법 상자가 있는 것은 아니다.

Harbor도 어떤 서버 위에서 실행되고, 사용자가 주소를 통해 접속하고, HTTPS로 통신하고, Image 데이터를 Disk에 저장하는 서비스다.

먼저 네 가지 질문으로 본다.

```text
1. 어디에서 실행할 것인가?
2. 사용자가 어떻게 찾아올 것인가?
3. 어떻게 안전하게 HTTPS로 접속할 것인가?
4. Image 데이터를 어디에 계속 보관할 것인가?
```

이 질문에 실제 기술 이름을 붙이면 다음과 같다.

| 쉬운 질문 | 실제 기술 요소 |
|---|---|
| 어디에서 실행하는가? | VM / OS / Docker / docker-compose |
| 어떻게 찾아오는가? | FQDN / DNS / Network / Port |
| HTTPS를 어떻게 신뢰하는가? | Server Certificate / Private Key / CA |
| Image는 어디에 남는가? | Disk / Mount / `data_volume` |
| 설치 설정은 어디에 모으는가? | `harbor.yml` |
| 설치 프로그램은 무엇인가? | Harbor offline installer / `install.sh` |

이 표를 이해한 다음 원본 Manual의 세부 항목을 본다.

## 9. 첫 번째 — 실행할 서버가 필요하다

Harbor도 프로그램이므로 실행할 서버가 필요하다.

원본 Manual에서는 Harbor VM에 Docker를 설치하고 Harbor Container들을 실행한다.

```text
Harbor VM
→ OS
→ Docker
→ Harbor Containers
```

여기서 Docker는 **Container를 실제로 실행하는 소프트웨어**라고 이해하면 된다.

`docker-compose`는 여러 Harbor Container 구성을 함께 실행·관리하기 위한 도구로 보면 된다.

원본 Manual에 특정 Docker와 docker-compose Version이 나오지만, 그 숫자를 외우는 것이 오늘 목표는 아니다.

실제 재설치 시에는 현재 승인 Version과 호환성을 다시 확인한다.

## 10. 두 번째 — 사용자가 찾아올 주소가 필요하다

사용자는 Harbor 서버의 내부 구조를 외우고 접속하지 않는다.

보통 정해진 이름으로 접속한다.

원본 Harbor Manual에 기록된 기준 FQDN은 다음과 같다.

```text
xa.dcr.dks.samsungds.net
```

실제 운영에서는 현재 승인된 값과 현장 조회 결과를 우선한다.

`FQDN`이라는 말이 어려우면 먼저 **서비스의 전체 도메인 주소**라고 이해하면 된다.

그리고 그 이름을 실제 Harbor 위치로 찾게 해주는 것이 DNS다.

```text
사용자 또는 Worker
→ xa.dcr.dks.samsungds.net
→ DNS로 주소 확인
→ Network / Firewall 통과
→ Harbor HTTPS Port
→ Harbor
```

따라서 내 PC에서 Web UI가 열린다고 모든 Kubernetes Worker의 Harbor 접근까지 자동으로 정상인 것은 아니다.

각 Client에서 DNS, Network, Port 접근이 달라질 수 있기 때문이다.

## 11. 세 번째 — HTTPS에서 상대를 믿을 수 있어야 한다

Harbor는 HTTPS로 접속한다.

HTTPS에서는 단순히 연결되는 것뿐 아니라 **내가 접속한 서버가 정말 그 Harbor인지, 그 인증서를 믿을 수 있는지** 확인한다.

여기서 세 가지 이름이 나온다.

### 11.1 Server Certificate

Harbor가 접속한 Client에게 보여주는 서버 인증서다.

쉬운 표현:

> **"나는 xa.dcr.dks.samsungds.net 서버입니다"라고 증명하는 인증서**

확인할 것은 FQDN, 유효기간, 인증서 Chain 등이다.

### 11.2 Private Key

Server Certificate와 한 쌍으로 사용되는 비밀키다.

쉬운 표현:

> **서버만 안전하게 보관해야 하는 비밀 정보**

Private Key는 교육 화면이나 문서에 노출하지 않는다.

### 11.3 Root / Intermediate CA

Client가 Server Certificate를 믿을 수 있는지를 판단할 때 사용하는 신뢰 체인이다.

쉬운 표현:

> **"이 서버 인증서를 믿어도 된다"고 확인할 수 있게 하는 신뢰 기준**

따라서 다음 세 개는 같은 것이 아니다.

```text
Server Certificate
≠ Private Key
≠ Root / Intermediate CA
```

Client가 필요한 CA를 신뢰하지 못하면 Harbor가 정상 실행 중이어도 다음 오류가 날 수 있다.

```text
x509: certificate signed by unknown authority
```

이 경우 바로 비밀번호 문제로 가지 않는다.

```text
접속한 이름이 맞는가
→ Server Certificate가 맞는가
→ 인증서 Chain이 맞는가
→ 그 Client가 CA를 신뢰하는가
```

순서로 본다.

## 12. 네 번째 — Image는 Container가 재시작돼도 남아야 한다

Harbor의 목적은 Image를 저장하는 것이다.

따라서 Harbor Container가 재시작될 때 Image까지 사라지면 안 된다.

그래서 Image 데이터는 별도의 영속적인 저장 위치에 둔다.

원본 Manual에서는 이 위치를 `data_volume`으로 설정한다.

```text
Harbor Container
      ↓
Image / Registry Data
      ↓
data_volume
      ↓
실제 Disk / Mount
```

`data_volume`이라는 이름을 먼저 외우기보다:

> **Harbor를 껐다 켜도 Image가 남아 있어야 하므로 데이터를 보관할 실제 저장공간이 필요하다.**

를 먼저 이해하면 된다.

## 13. harbor.yml은 Harbor의 주요 설정을 모은 파일이다

앞에서 본 요소를 설치 시 어디에 적는가?

원본 Manual에서는 `harbor.yml`에 주요 설정을 넣는다.

| 설정 | 쉬운 의미 |
|---|---|
| `hostname` | Harbor가 사용할 이름 |
| `http.port` / `https.port` | 접속 Port |
| `certificate` | Server Certificate 파일 위치 |
| `private_key` | Private Key 파일 위치 |
| `data_volume` | Image 데이터를 보관할 위치 |

즉 `harbor.yml`은 처음 보는 낯선 파일이 아니라 **앞에서 설명한 주소·HTTPS·저장공간 등의 기준을 모아 둔 설치 설정 파일**이다.

## 14. 원본 Manual의 실제 설치 순서

이제 역할을 이해했으므로 기술 용어로 된 원본 흐름을 본다.

```text
Harbor VM / Disk 확인
→ DNS / FQDN / Network 확인
→ Docker Repository 준비
→ Docker / docker-compose 설치
→ Harbor offline installer 확보
→ Server Certificate / Private Key / CA 준비
→ OS / Docker CA Trust 반영
→ harbor.yml 작성
→ data_volume 확인
→ install.sh 실행
→ Harbor Containers 기동
```

이 순서를 처음부터 외우는 것이 아니라, 각 항목이 앞에서 본 **실행 / 주소 / 신뢰 / 저장** 중 어디에 해당하는지 연결해서 본다.

## 15. 설치 명령 성공과 서비스 정상은 다르다

`install.sh`가 성공하고 Harbor Container가 Running이라고 하자.

그럼 Harbor가 정상일까?

운영에서는 아직 확인이 더 필요하다.

Harbor Web 화면이 열린다는 것과 실제 Image 저장소 기능이 동작한다는 것은 다르다. Docker나 Worker가 Harbor의 Image 저장 기능과 통신하는 실제 입구를 `Registry API`라고 이해하면 된다.

```text
프로세스가 떠 있음
→ Harbor Container Running

사용자가 실제로 쓸 수 있음
→ HTTPS 접근
→ Registry API 응답
→ Login
→ Project 접근
→ Test Image Push
→ Test Image Pull
→ 데이터 저장
→ 재시작 후 Repository 유지
```

### 반드시 기억할 문장

> **Harbor Container Running ≠ Harbor 사용 가능 상태**

예를 들어 Container는 떠 있지만 다음이 실패할 수 있다.

- DNS
- Firewall
- HTTPS Certificate
- Client CA Trust
- Registry API
- 사용자 인증
- Project 권한
- Quota
- Disk / Mount

그래서 **명령 성공보다 실제 기능을 확인한다.**

# Part 3. 3.2 Create a project — 여러 팀의 Image를 나눈다

> [!summary] Part 3 설명 흐름
> 여러 팀이 같은 Harbor를 사용함 → **하지만** Image·권한·Storage를 한 공간에 섞을 수 없음 → **그래서** Harbor Project로 영역을 나눔 → Repository에 Image와 Tag를 저장함 → KubeSphere Project와 구분함 → 승인된 Name·Private·Quota를 적용함 → **하지만** Project만으로 User 권한이 생기지는 않음


## 16. Harbor가 하나인데 왜 Project가 또 필요한가

이제 Harbor 자체는 정상이라고 하자.

회사에 Application 팀이 하나만 있는 것이 아니다.

여러 팀이 같은 Harbor를 사용하면 다음을 나눠야 한다.

- 이 Image가 어느 Application의 것인가?
- 누가 볼 수 있는가?
- 누가 새로운 Image를 올릴 수 있는가?
- 이 팀이 Storage를 얼마나 사용할 수 있는가?

아무 구분 없이 한 공간을 같이 쓰면 Image와 권한이 섞인다.

그래서 Harbor 안에서 팀 또는 Application별 영역을 나눈다.

그 영역의 이름이 **Harbor Project**다.

```text
Harbor
├─ Project A
│  ├─ Image Repository
│  └─ Members / Roles
├─ Project B
│  ├─ Image Repository
│  └─ Members / Roles
└─ Project C
```

> **Harbor Project = 특정 Application/Team의 Image와 접근 권한을 나누는 경계**

## 17. Repository는 무엇인가

Project 안에는 실제 Image가 Repository 형태로 저장된다.

오늘은 복잡하게 생각하지 않는다.

```text
Harbor
→ Project
→ Repository
→ Image / Tag
```

쉬운 말로 보면:

```text
Harbor = 전체 Registry
Project = 팀/Application 영역
Repository = 그 안의 Image 저장 단위
Tag = Image Version 등을 구분하는 이름
```

Repository와 Tag의 실제 사용은 다음 User Manual의 Push/Pull 실습에서 더 자세히 본다.

## 18. KubeSphere Project와 Harbor Project는 다른 물건이다

어제 KubeSphere에서도 `Project`라는 이름을 사용했다.

이름이 같아서 가장 헷갈릴 수 있다.

| 구분 | KubeSphere Project | Harbor Project |
|---|---|---|
| 쉬운 의미 | Application이 Kubernetes Resource를 운영하는 공간 | Application의 Image를 저장하고 권한을 나누는 공간 |
| 연결 대상 | Kubernetes Namespace | Harbor Repository |
| 대표 작업 | Deployment, Pod, PVC 등 | Image Push/Pull, Repository, Member |
| 권한 | KubeSphere Role | Harbor Role |

```text
KubeSphere Project
= Kubernetes Workload 영역

Harbor Project
= Container Image 영역
```

> **KubeSphere Project ≠ Harbor Project**

KubeSphere에 Project가 있다고 Harbor Project가 자동으로 생기는 것으로 이해하지 않는다.

## 19. 실제 Project 요청을 받으면 무엇을 보는가

이제 Manual의 메뉴보다 실제 운영 요청 관점으로 본다.

> [!warning] 오늘 교육의 실행 경계
> 기존 Private Project에서 Private·Quota·Member·Role을 **읽기 전용으로만 확인**한다. New Project 화면은 절차 설명에 사용할 수 있지만 **Create·Save·Role 변경은 실행하지 않는다.** 실제 운영에서는 승인된 작업 절차와 권한을 확인한 뒤 수행한다.


```text
신청/승인 내용 확인
→ 어느 Application인가
→ Project Name은 무엇인가
→ 내부 Private Project인가
→ 승인 Storage Quota는 얼마인가
→ 사용할 AD 계정은 누구인가
→ 관리자 / 일반 사용자 구분은 무엇인가
```

그 다음 Harbor에서 Project를 만든다.

## 20. Project 생성의 핵심 세 값

### 20.1 Project Name

승인된 신청 이름을 사용한다.

비슷한 이름을 임의로 만들지 않는다.

### 20.2 Private

내부 Application Image는 기본적으로 인증된 사용자만 사용하도록 Private 기준으로 본다.

쉬운 의미:

> **아무나 들어와 Image를 가져가는 공간이 아니라, 허용된 사용자만 접근하는 공간**

### 20.3 Storage Quota

Project가 사용할 수 있는 Image 저장공간의 상한이다.

원본 Manual의 `10 GB`는 예시다.

실제 운영에서는 현재 정책과 승인값을 확인한다.

## 21. Project 생성 버튼을 눌렀다고 완료가 아니다

```text
Project가 보임
≠ 운영 요청 완료
```

확인할 것은 다음이다.

```text
승인 이름과 일치
+ 중복 없음
+ Private
+ Quota 승인값 일치
+ 필요한 사용자/관리자 연결 가능
```

# Part 4. 3.3 Managing Users — 공간 다음에는 사람과 권한을 연결한다

> [!summary] Part 4 설명 흐름
> Project가 있어도 User가 자동으로 접근하지 못함 → **그래서** AD User를 Member로 연결하고 Role을 부여함 → Developer와 ProjectAdmin의 작업 범위를 구분함 → **하지만** 신청서 Admin·User와 Harbor Role을 이름만으로 매핑할 수 없음 → 승인 정책을 확인함 → Login 성공과 Project 권한 성공을 구분함


## 22. Project가 있다고 사용자가 자동으로 들어오는 것은 아니다

Harbor Project를 만들었다고 모든 AD 사용자가 그 Project를 사용할 수 있는 것은 아니다.

대상 사용자를 Project Member로 연결하고 Role을 정해야 한다.

```text
Harbor Project
→ Member 추가
→ AD 계정
→ Role
→ 실제 권한 확인
```

## 23. Role은 "이 사람이 여기서 무엇을 할 수 있는가"다

오늘은 두 역할을 중심으로 본다.

### 23.1 Developer

Image를 사용하는 일반 사용자 역할이다.

```text
Image Pull O
Image Push O
Project Member 관리 X
```

### 23.2 ProjectAdmin

Image 사용과 Project Member 관리가 필요한 관리자 역할이다.

```text
Image Pull O
Image Push O
Project Member 관리 O
```

표로 보면:

| 기능 | Developer | ProjectAdmin |
|---|---:|---:|
| Image Pull | O | O |
| Image Push | O | O |
| Member 관리 | X | O |

> [!warning] 다른 제품의 Role과 섞지 않는다
> Harbor `ProjectAdmin`은 Harbor 안의 Role이다. KubeSphere `project-operator`, `project-admin`과는 별개의 권한 체계다.

## 24. 신청서 Permission을 바로 Harbor Role이라고 단정하지 않는다

원본 신청 양식에는 `Admin / User`가 있고 Harbor에는 `ProjectAdmin / Developer`가 있다.

교육생에게는 다음처럼 연결해서 설명한다.

```text
신청서의 사용자 구분 확인
→ 이 사용자가 Project 관리자인가 일반 사용자인가
→ Xi'an 승인된 Harbor Role 정책 확인
→ ProjectAdmin 또는 Developer 선택
```

역할 의미는 다음처럼 이해한다.

```text
관리자 역할이 필요한 대상
→ ProjectAdmin 후보

일반 Image 사용 대상
→ Developer 후보
```

하지만 **신청서 Admin/User와 Harbor Role의 최종 1:1 대응은 Xi'an 승인 운영 정책을 확인한 뒤 적용**한다.

강사가 기억으로 임의 확정하지 않는다.

## 25. Login과 Project 권한은 다른 단계다

사용자가 Harbor 로그인에 성공했다고 하자.

그것은 무엇을 의미할까?

```text
Harbor가 이 사용자가 누구인지 확인함
→ 인증 성공
```

하지만 특정 Private Project에서 Image를 Push/Pull할 수 있다는 뜻은 아니다.

그 Project의 Member인지, 어떤 Role인지가 추가로 맞아야 한다.

```text
Harbor Login 성공
= 사용자 인증 성공

특정 Project Push/Pull 성공
= Project Membership + Role까지 성공
```

### 반드시 기억할 문장

> **Harbor Login 성공 ≠ 특정 Private Project 사용 권한 보유**

## 26. 실제 반복 운영 흐름

3.2와 3.3은 현장에서 다음과 같이 연결해서 본다.

```text
신청/승인 내용
→ Project Name
→ Private
→ Storage Quota
→ AD 사용자
→ 관리자/일반 사용자 구분
→ 승인된 Role 정책 확인
→ Harbor Project 생성
→ Member 추가
→ Role 적용
→ 실제 허용 범위 확인
```

# Part 5. Push/Pull에서 Kubernetes까지 전체 길을 보여준다

> [!summary] Part 5 설명 흐름
> Developer·CI가 Harbor에 Image를 Push함 → **하지만** Private Project의 Image는 Kubernetes도 인증 없이 Pull할 수 없음 → Registry Secret과 `imagePullSecrets`, 정확한 Image 주소가 필요함 → Worker가 Pull함 → Container와 Pod가 실행됨


## 27. Harbor를 왜 운영하는지 다시 연결한다

Project와 User를 만드는 것 자체가 최종 목적은 아니다.

최종 목적은 필요한 Image를 안전하게 저장하고, 필요한 사용자와 Kubernetes가 그 Image를 사용할 수 있게 하는 것이다.

```text
Developer
→ Application Image 준비
→ Harbor Login
→ Harbor Project에 Image Push
→ Repository에 Image 저장
```

그리고 Kubernetes가 그 Private Image를 사용할 때는 **Harbor에 인증할 정보가 필요하다.**

Kubernetes에게 "어떤 Image로 Application을 실행할 것인지" 적어주는 대표 설정을 `Deployment`라고 이해하면 된다.

```text
Kubernetes
→ Private Harbor 인증정보 필요
→ Deployment에서 Image 지정
→ Worker가 Harbor에서 Image Pull
→ Container 실행
→ Pod 실행
```

여기서 인증정보를 Kubernetes에 넣는 실제 방법은 다음 User Manual에서 자세히 본다.

```text
Registry Secret
→ imagePullSecrets
```

오늘은 이름만 알고 전체 길에서 어디에 있는지만 이해한다.

> [!important] 오늘의 경계
> `Registry Secret`과 `imagePullSecrets` 상세 생성·연결은 8/28 User Manual에서 다룬다. 하지만 Private Harbor에서 Kubernetes가 Image를 Pull할 때 인증 단계가 **존재한다는 사실은 숨기지 않는다.**

## 28. 전체 흐름 최종 정리

```text
[기반]
Application 실행 원본 필요
→ Container Image
→ 중앙 Image 저장소 필요
→ Registry
→ Xi'an Harbor

[Harbor 플랫폼]
Server / 주소 / HTTPS 신뢰 / 저장공간
→ Harbor 실행
→ 실제 Registry 기능 검증

[반복 운영]
신청
→ Harbor Project
→ Private / Quota
→ User
→ Role
→ Login / Push / Pull

[다음 사용 단계]
Kubernetes Registry 인증정보
→ Image 지정
→ Worker Pull
→ Container / Pod 실행
```

# Part 6. 문제가 생기면 용어보다 "어디까지 됐는가"를 본다

> [!summary] Part 6 설명 흐름
> 증상부터 확인함 → 화면 접근 실패는 DNS·Network·Port·Container 경로 → x509는 인증서 신뢰 경로 → Login 실패는 사용자 인증 → Push denied는 Project 권한 → Kubernetes Pull 실패는 Secret·Worker 접근·Pod Event → **결국** 처음 끊긴 단계부터 확인함


## 29. Web UI 자체가 안 열린다

먼저 Harbor까지 가는 길을 본다.

```text
이름을 찾을 수 있는가
→ DNS

길이 열려 있는가
→ Network / Firewall

HTTPS Port가 열리는가
→ 443 등 실제 설정

Harbor가 실행 중인가
→ Container 상태
```

## 30. Web은 열리는데 x509가 나온다

Harbor가 Down이라고 바로 판단하지 않는다.

```text
FQDN
→ Server Certificate
→ Certificate Chain
→ Client CA Trust
```

즉 **접속은 갔지만 신뢰 확인에서 막힌 것인지** 본다.

## 31. Login이 실패한다

```text
Harbor까지 접속됨
→ HTTPS도 통과함
→ 그다음 사용자 인증 확인
→ Account / Password / AD / Harbor Auth
```

## 32. Login은 되는데 Push가 거부된다

로그인은 이미 됐으므로 비밀번호만 계속 보지 않는다.

```text
대상 Project가 맞는가
→ 사용자가 Member인가
→ Role이 맞는가
→ Repository / Tag가 맞는가
→ Quota가 남아 있는가
```

## 33. Harbor에서 Image는 보이는데 Kubernetes가 Pull하지 못한다

Harbor 사용자 Push 성공과 Kubernetes Pull은 다른 경로다.

```text
Image 주소 / Tag
→ Private Registry 인증정보
→ Registry Secret
→ imagePullSecrets 연결
→ Worker에서 Harbor 접근
→ Pod Event
```

상세 트러블슈팅은 다음 User Manual과 Troubleshooting Guide에서 다룬다.

# Part 7. 오늘 반드시 기억할 것

## 34. 기술 용어보다 먼저 기억할 열두 문장

1. **Application 실행에 필요한 프로그램·파일·Library·실행환경을 하나로 묶은 원본이 Image다.**
2. **Image를 실제로 실행한 상태가 Container이고 Kubernetes에서는 Pod 안에서 실행된다.**
3. **Registry는 여러 Worker가 같은 Image를 사용할 수 있도록 중앙에서 보관하는 곳이다.**
4. **Xi'an에서는 Harbor를 인증과 권한을 적용하는 Private Registry로 사용한다.**
5. **Harbor에 Image를 넣는 동작은 Push이고 가져오는 동작은 Pull이다.**
6. **3.1은 Harbor 플랫폼 기반이고 3.2~3.3은 Project와 User에 관한 반복 운영이다.**
7. **Harbor 플랫폼은 실행 환경·접속 주소·HTTPS 신뢰·Image 저장공간 위에서 동작한다.**
8. **Harbor Container Running과 Harbor 실제 사용 가능 상태는 다르다.**
9. **Harbor Project는 Image 영역이고 KubeSphere Project는 Kubernetes Workload 영역이다.**
10. **Project의 Name·Private·Quota는 승인 내용과 일치해야 한다.**
11. **Harbor Login 성공과 특정 Private Project 권한 성공은 다르며 Role은 승인 정책으로 결정한다.**
12. **Private Harbor Image를 Kubernetes가 사용할 때는 Registry 인증 단계가 필요하다.**

## 35. 마지막 Teach-back

교육생에게 다음 상황을 준다.

> 새로운 Application 팀이 Xi'an DKS에서 자체 Container Image를 Harbor에 저장하고 나중에 Kubernetes에서 사용하고 싶다고 요청했다.

교육생이 다음 순서로 자기 말로 설명하게 한다.

```text
Image가 왜 필요한지
→ 왜 중앙 Registry가 필요한지
→ Xi'an에서 Harbor가 무슨 역할인지
→ Harbor 자체가 이미 구축된 플랫폼이라는 점
→ 새 Harbor Project가 왜 필요한지
→ Private / Quota
→ 사용자를 왜 Member로 넣는지
→ Developer / ProjectAdmin 차이
→ Push / Pull
→ Kubernetes가 Private Image를 사용할 때 인증 단계가 있다는 점
```

추가 질문:

- Image와 Container는 무엇이 다른가?
- Registry를 왜 Worker마다 따로 두지 않는가?
- Harbor Project와 KubeSphere Project는 무엇이 다른가?
- Harbor Container가 Running인데 왜 아직 완료가 아닐 수 있는가?
- Login은 되는데 Push가 안 되면 왜 계정 비밀번호부터 다시 볼 필요가 없는가?
- Kubernetes가 Private Harbor Image를 가져갈 때 무엇이 하나 더 필요한가?
