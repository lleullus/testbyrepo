# 2026-08-27 오후 Harbor Manual 교육 안내

> [!important] 이 폴더의 교육 원칙
> **수강생이 Kubernetes와 Harbor를 거의 모른다고 가정한다.** 8/25에 설명한 내용을 선수지식으로 요구하지 않는다. 먼저 "이게 왜 필요한 물건인지"를 쉬운 말로 이해시키고, 그다음 역할에 기술 용어를 하나씩 붙인 뒤, Xi'an 실제 환경과 Manual 절차로 연결한다.

## 1. 이 교육의 목적

이 교육의 목적은 Harbor 명령어, 메뉴, 용어를 많이 전달하는 것이 아니다.

수강생이 다음 순서로 이해하도록 만드는 것이 목적이다.

```text
왜 필요한가
→ 무슨 문제를 해결하는가
→ 아주 단순한 구조는 무엇인가
→ 각 역할의 기술 이름은 무엇인가
→ Xi'an에서는 어떻게 구성되어 있는가
→ 운영자는 실제로 무엇을 하는가
→ 무엇을 보면 완료인가
→ 문제가 생기면 어디부터 볼 것인가
```

## 2. 내일 오후의 한 문장

**Application을 실행할 Image를 한곳에서 안전하게 관리하기 위해 Harbor를 사용하고, Harbor 안에서 Project로 Image 영역을 나누고, 사용자와 Role을 연결한 뒤, 실제 Push/Pull이 가능한 상태인지 확인한다.**

## 3. 용어를 먼저 던지지 않는다

강의 시작부터 다음 문장을 연속으로 던지지 않는다.

```text
Container Image
Registry
Repository
Project
Quota
ProjectAdmin
Developer
Push / Pull
```

먼저 역할을 설명하고 나중에 이름을 붙인다.

```text
실행할 프로그램과 필요한 파일을 묶은 원본
→ Container Image

그 원본을 여러 서버가 가져갈 수 있게 한곳에 보관하는 저장소
→ Registry

Xi'an에서 사용하는 Private Registry 제품
→ Harbor

Harbor 안에서 특정 Application/Team의 Image와 권한을 나누는 영역
→ Project

Harbor에 Image를 올림
→ Push

Harbor에서 Image를 가져옴
→ Pull
```

## 4. 3.1과 3.2~3.3은 연결되지만 같은 종류의 업무가 아니다

```text
[플랫폼 기반 이해]
3.1 Harbor Installation
→ Harbor 자체를 처음 구축하거나 복구할 때 필요한 구조
→ 현재 Xi'an Harbor는 이미 구축되어 있음
→ 8/27에는 재설치하지 않고 구조와 정상 판정을 설명

                 ↓ 이 기반 위에서

[반복 운영]
3.2 Create a project
→ Application/Team용 Image 영역 생성

3.3 Managing Users
→ 그 영역을 사용할 사용자와 Role 연결
```

> [!warning] 반드시 구분
> 새로운 Harbor Project 요청을 받을 때마다 Harbor를 다시 설치하는 것이 아니다. 3.1은 **플랫폼 기반**, 3.2~3.3은 **반복 운영 요청**이다.

## 5. 전체 이야기

```text
프로그램을 실행하려면 실행 원본이 필요함
→ 그 원본을 Container Image라고 함
→ 여러 서버가 같은 Image를 사용해야 함
→ 한곳에 보관하는 Registry가 필요함
→ Xi'an에서는 Harbor를 사용함

Harbor 자체가 정상이어야 함
→ 주소·HTTPS·저장공간·실행 기반이 필요함
→ 설치 명령 성공이 아니라 실제 Registry 기능까지 확인

여러 팀이 같은 Harbor를 사용함
→ Image와 권한이 섞이면 안 됨
→ Project로 영역을 나눔
→ Private와 승인 Quota 적용

Project만 만들어서는 사람이 사용할 수 없음
→ AD 사용자를 Member로 연결
→ 역할에 따라 Developer / ProjectAdmin 부여
→ 실제 Login·Push·Pull 범위 확인

Kubernetes가 Private Image를 사용할 때는 Registry 인증정보가 필요함
→ 구체적인 Secret / imagePullSecrets는 다음 User Manual에서 교육
```

## 6. 신청서에서 실제 Harbor 설정으로 연결

3.2~3.3 교육에서는 메뉴보다 **신청 내용이 실제 설정으로 어떻게 바뀌는지**를 보여준다.

```text
신청/승인 내용
→ Project Name
→ Private 여부
→ Storage Quota
→ AD 계정
→ 관리자 / 일반 사용자 구분
→ Xi'an Harbor Role 정책 확인
→ Project 생성
→ Member / Role 적용
→ 실제 사용 권한 확인
```

> [!caution] Role 매핑 Gate
> 원본 문서에는 신청서 `Admin / User`와 Harbor `ProjectAdmin / Developer`가 각각 등장한다. **실제 Xi'an 운영 정책의 최종 매핑을 확인하지 않은 상태에서 강사가 임의로 1:1 규칙으로 확정하지 않는다.** 관리자 대상은 ProjectAdmin, 일반 사용자는 Developer라는 역할 의미를 설명하고, 신청서 Permission과의 최종 대응은 승인된 운영 정책을 우선한다.

## 7. 계속 반복할 핵심 구분

```text
Harbor Container Running
≠ Harbor 사용 가능 상태

Harbor Project
≠ KubeSphere Project

Harbor Login 성공
≠ 특정 Private Project 사용 권한 보유

Project 생성 성공
≠ Private·Quota·Member·Role까지 올바름

Server Certificate
≠ Private Key
≠ Root / Intermediate CA
```

## 8. Xi'an 현장 교육 경계

- 현재 Xi'an Harbor는 이미 구축되어 있다.
- Harbor를 설치·재설치하거나 서비스를 재시작하지 않는다.
- 실제 Private Key와 관리자 Credential을 노출하지 않는다.
- 3.1은 설치 구조와 완료 증거를 이해하는 워크스루로 진행한다.
- 3.2~3.3은 기존 Private Project에서 Private·Quota·Member·Role을 읽기 전용으로 확인한다.
- New Project 화면과 Role 메뉴는 Manual 절차 설명에 사용할 수 있지만 Create/Save/Role 변경은 실행하지 않는다.
- Push/Pull은 설치 완료와 실제 사용 가능 상태를 판단하는 검증 개념으로 설명하고, 실제 실습은 다음 User Manual로 연결한다.
- 원본 Manual의 Version과 10 GB는 예시이며 현재 Xi'an 환경과 승인값을 우선한다.

## 10. 완료 기준

교육생이 자기 말로 다음을 설명할 수 있으면 된다.

1. Image가 무엇인지 아주 간단히 설명할 수 있는가?
2. 왜 Image를 Worker마다 복사하지 않고 Registry에 보관하는가?
3. Harbor가 Registry라는 말이 무슨 뜻인가?
4. Harbor가 설치되어 있다는 것과 실제 사용 가능한 상태는 왜 다른가?
5. Harbor Project와 KubeSphere Project는 왜 다른가?
6. 왜 내부 Project를 Private으로 사용하는가?
7. Developer와 ProjectAdmin의 역할 차이는 무엇인가?
8. Login은 되는데 Push가 안 될 때 왜 비밀번호 문제만 보면 안 되는가?
9. Private Harbor Image를 Kubernetes가 사용하려면 인증 경계가 있다는 것을 아는가?
10. 전체 흐름을 `Image → Harbor → Project → User/Role → Push/Pull → Kubernetes 사용`으로 설명할 수 있는가?
