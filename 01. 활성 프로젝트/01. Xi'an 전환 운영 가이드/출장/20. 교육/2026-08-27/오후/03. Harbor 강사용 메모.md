# Harbor 강사용 메모

> 이 문서는 `[[02. Harbor 강사용 전체 대본]]`의 현재 흐름을 강의 직전에 빠르게 찾기 위한 압축 메모다. 기술 이름이 먼저 나오면 반드시 쉬운 문제와 역할 설명으로 돌아간다.

## 1. 전체 논리 흐름

`일단` Application 실행에는 프로그램·파일·Library·실행환경이 필요함 → `그래서` Container Image로 묶음 → Image를 실행하면 Container가 되고 Kubernetes에서는 Pod 안에서 실행됨 → `하지만` Worker가 여러 대면 Image 전달과 Version 관리가 어려움 → `그래서` 중앙 Registry가 필요함 → Xi'an에서는 Harbor가 이 역할을 담당함 → `하지만` 내부 Image를 아무나 사용할 수 없음 → `그래서` Private Registry로 운영함 → Project로 영역을 나누고 Member와 Role을 연결함 → Push와 Pull을 확인함 → Kubernetes는 별도 Registry 인증으로 Private Image를 Pull함

## 2. 시작 5분

### Image / Container / Pod

```text
Application + 필요한 파일 + Library + 실행환경
→ Container Image
→ 실행된 상태가 Container
→ Kubernetes에서는 Pod 안에서 실행
```

### Worker / Registry / Harbor

```text
Worker 한 대
→ Image 직접 복사 가능

Worker 여러 대
→ 반복 복사 / Version 차이 / 재배치 시 Image 누락
→ 중앙 Container Image 저장소 필요
→ Registry
→ Xi'an Harbor
```

### Private / Push / Pull

```text
조직 내부 Image
→ 인증과 접근 권한 필요
→ Private Registry

Harbor에 Image 넣기 = Push
Harbor에서 Image 가져오기 = Pull
```

## 4. 3.1 Harbor Installation

### 네 질문

```text
1. 어디에서 실행하는가?
2. 사용자와 Worker는 어떻게 찾아오는가?
3. HTTPS에서 어떻게 신뢰하는가?
4. Image 데이터는 어디에 남는가?
```

### 역할과 기술 이름

| 쉬운 역할 | 기술 요소 |
|---|---|
| 실행 환경 | VM / OS / Docker / docker-compose |
| 접속 주소와 경로 | FQDN / DNS / Network / Firewall / HTTPS Port |
| HTTPS 신뢰 | Server Certificate / Private Key / Root·Intermediate CA |
| Image 데이터 유지 | Disk / Mount / `data_volume` |
| 주요 설정 모음 | `harbor.yml` |
| 설치 실행 | Offline Installer / `install.sh` / Harbor Containers |

### Xi'an FQDN

```text
원본 Manual 기록값
= xa.dcr.dks.samsungds.net

실제 운영값
= 현재 승인값과 현장 조회 결과를 다시 확인
```

### 인증서 구분

```text
Server Certificate
→ Harbor가 해당 FQDN의 서버임을 제시

Private Key
→ Server Certificate와 한 쌍인 서버 비밀키

Root / Intermediate CA
→ Client가 인증서 Chain을 신뢰하는 기준
```

```text
Server Certificate
≠ Private Key
≠ CA
```

### x509

```text
x509: certificate signed by unknown authority
→ 비밀번호부터 보지 않음
→ FQDN
→ Server Certificate
→ Certificate Chain
→ Client CA Trust
```

### 설치 순서

```text
VM / Disk
→ FQDN / DNS / Network
→ Docker
→ Offline Installer
→ Certificate / Private Key / CA
→ harbor.yml
→ data_volume
→ install.sh
→ Harbor Containers
```

### 완료 판정

```text
install.sh 성공
≠ Harbor 실제 사용 가능

Container Running
≠ Harbor 실제 사용 가능
```

```text
HTTPS
→ Registry API
→ Login
→ Project 접근
→ Test Push
→ Test Pull
→ Data 저장
→ 재시작 후 Repository 유지
```

## 5. 3.2 Create a project

### 왜 Project인가

`일단` 여러 팀이 같은 Harbor를 사용함 → `하지만` Image·권한·Storage를 한 공간에 섞을 수 없음 → `그래서` Harbor Project로 Application·Team 영역을 나눔

```text
Harbor
→ Project
→ Repository
→ Image / Tag
```

```text
KubeSphere Project
= Kubernetes Workload 영역

Harbor Project
= Container Image / Repository / 권한 영역
```

```text
KubeSphere Project
≠ Harbor Project
```

### 실제 요청에서 확인할 값

```text
승인된 Project Name
→ Private 여부
→ Storage Quota 승인값
→ 사용할 AD 계정
→ 관리자 / 일반 사용자 구분
```

```text
10 GB
= 원본 Manual 예시
≠ 현행 고정값
```

> [!warning] 교육 실행 경계
> 기존 Private Project에서 Private·Quota·Member·Role을 읽기 전용으로 확인한다. New Project 화면은 설명에 사용할 수 있지만 **Create·Save·Role 변경은 실행하지 않는다.**

## 6. 3.3 Managing Users

```text
Project 생성
→ AD User를 Member로 연결
→ Role 부여
→ 허용된 작업 확인
```

### Developer / ProjectAdmin

| 기능 | Developer | ProjectAdmin |
|---|---:|---:|
| Image Pull | O | O |
| Image Push | O | O |
| Member 관리 | X | O |

```text
Harbor ProjectAdmin
≠ KubeSphere project-admin
≠ KubeSphere project-operator
```

### 신청서 Role 매핑 Gate

```text
신청서 Admin / User
→ 실제로 필요한 작업 확인
→ Xi'an 승인 Harbor Role 정책 확인
→ ProjectAdmin / Developer 적용
```

절대 하지 않음:

```text
강사 기억으로 Admin = ProjectAdmin 확정
강사 기억으로 User = Developer 확정
```

### Login과 Project 권한

```text
Harbor Login 성공
= 사용자 인증 성공

특정 Project Push / Pull 성공
= Member + Role + 대상 Repository 조건까지 성공
```

## 7. 실제 반복 운영 흐름

```text
승인 내용 확인
→ Project Name / Private / Quota
→ AD User / 사용자 구분
→ 승인 Role 정책
→ Harbor Project 생성
→ Member 추가
→ Role 적용
→ Login / Push / Pull 권한 확인
```

Project가 화면에 보이거나 Member가 추가됐다는 사실만으로 완료가 아니다. 승인값과 실제 설정이 일치하고 사용자가 허용된 작업을 수행할 수 있어야 한다.

## 8. Kubernetes Private Image 사용

```text
Developer / CI Login
→ Harbor Push
→ Repository 저장

Kubernetes Registry 인증정보
→ 정확한 Image 주소
→ imagePullSecrets
→ Worker Pull
→ Container / Pod 실행
```

> `Registry Secret`과 `imagePullSecrets` 상세 생성·연결은 다음 User Manual에서 다룬다. Private Harbor에는 별도 인증 단계가 있다는 사실만 반드시 설명한다.

## 9. 장애 분류

### Web 자체가 열리지 않음

```text
FQDN / DNS
→ Network / Firewall
→ HTTPS Port
→ Harbor Container
```

### x509

```text
서버에는 도달함
→ FQDN / Server Certificate
→ Certificate Chain
→ Client CA Trust
```

### Login 실패

```text
Network / HTTPS 성공 후
→ Account / Password
→ AD 상태
→ Harbor 인증 연동
```

### Login 성공 + Push denied

```text
대상 Project
→ Member
→ Role
→ Repository / Tag
→ Quota
```

### Harbor Image 존재 + Kubernetes Pull 실패

```text
Image 주소 / Tag
→ Registry Secret / imagePullSecrets
→ Worker DNS / Network / CA Trust / Pull 권한
→ Pod Event
```

## 10. 강의 중 하지 않을 것

- Harbor 설치 / 재설치 / 서비스 재시작
- 운영 Project 신규 생성 / 삭제
- Public / Private 변경
- Quota 변경
- Member Role 변경
- 사용자 제거
- 실제 Private Key / 관리자 Password 노출
- 10 GB를 고정 정책으로 단정
- 신청서 Admin/User와 Harbor Role을 미확인 상태에서 1:1 확정
- KubeSphere Role과 Harbor Role 혼동
- 8/25 내용을 기억한다고 가정하고 설명 생략

## 11. 마지막 1분 대본

> Application을 실행하려면 프로그램과 실행환경을 묶은 Image가 필요합니다. 여러 Worker가 같은 Image를 사용하려면 중앙 Registry가 필요한데, Xi'an에서는 Harbor가 이 역할을 담당합니다. Harbor 플랫폼은 실행 서버, 접속 주소, HTTPS 신뢰, Image 저장공간 위에서 동작합니다. 하지만 플랫폼이 정상이라고 여러 팀의 Image와 권한이 자동으로 나뉘지는 않습니다. 그래서 Harbor Project에 Private와 Quota를 적용하고 AD 사용자를 Member로 연결해 Role을 부여합니다. Image가 Push된 뒤 Kubernetes가 Private Image를 사용하려면 Registry 인증정보가 필요하고 Worker가 Image를 Pull해야 Pod가 실행됩니다. 결국 각 화면이나 상태 하나가 아니라 전체 경로의 실제 성공을 확인해야 합니다.
