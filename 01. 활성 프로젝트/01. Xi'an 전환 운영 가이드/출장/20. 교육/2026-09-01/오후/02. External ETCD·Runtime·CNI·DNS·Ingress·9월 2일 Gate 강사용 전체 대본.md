# External ETCD·Runtime·CNI·DNS·Ingress·9월 2일 Gate 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 앞 블록의 `CONTROL PATH PASS` 뒤에 **실제 Application Pod가 실행되고, Pod Network와 Cluster DNS를 사용하며, 외부 요청이 VIP-B에서 Service·Pod까지 이어질 수 있는지 증명하는 법**을 가르친다. ETCD·containerd·Calico·CoreDNS·Ingress의 긴 설정을 외우게 하지 않는다. 설정 존재와 실제 기능 성공을 분리하고, 9월 2일 Storage를 시작할 Kubernetes 기반이 있는지 `KUBERNETES BASE PASS / BLOCKED`로 판정한다.

## 0. 앞 블록에서 이어받는 것

```text
Cluster Name·Stage
current-context·API Server URL
VIP-A 검증 결과
실제 Kubernetes Version
실제 Pod CIDR·Service CIDR·Domain
Node별 Name·Role·IP·Version·Ready
Role별 Label·Taint
Control Plane Component 상태
CONTROL PATH PASS / BLOCKED
```

> 이 값은 다시 추측하지 않습니다. 같은 Context를 유지한 채 Control Path 뒤의 실제 Application 경로를 검증합니다.

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> ETCD·containerd·Calico·CoreDNS·Ingress Pod가 Running이라는 사실만으로 완료 처리하지 않고, **상태 저장 → Container 실행 → Pod IP·통신 → Service 이름 해석 → Service Endpoint → Router NodePort → VIP-B 사용자 요청**의 실제 기능 경로를 단계별 증거로 확인할 수 있어야 한다.

오늘의 중심 질문:

> **이 Cluster에서 실제 Pod를 실행하고 Network와 DNS를 사용하며 외부 요청을 Application까지 전달할 수 있는가?**

---

# 1. 시작 — Node Ready 뒤에도 Application이 동작한다는 증거는 남아 있다

> 앞 블록에서는 API Server가 응답하고 예상 Node가 올바른 Identity로 등록되며 Control Plane 핵심 Component가 정상임을 확인했습니다.
>
> 이제 `그럼 Application Pod를 하나 만들면 실제로 실행되고 통신하며 사용자가 접근할 수 있는가?`를 묻습니다.
>
> 아직 바로 예라고 할 수 없습니다.

Application 경로에 필요한 역할을 최소 다섯 가지로 본다.

```text
Cluster 상태를 보존
→ External ETCD

Image로 Container를 실행
→ CRI·containerd

Pod에 IP와 통신 경로 제공
→ CNI·Calico

Service 이름을 IP로 해석
→ CoreDNS

외부 HTTP·HTTPS 요청을 Service로 전달
→ Ingress Controller·Router·VIP-B
```

> 이 역할들은 연결되지만 하나의 성공이 뒤의 성공을 대신하지 않습니다.

---

# 2. 같은 신규 Member Context와 기능 테스트 범위를 고정한다

```text
current-context: _________________________________________
Cluster Name·Stage: _____________________________________
Pod CIDR: ________________________________________________
Service CIDR·Domain: _____________________________________
VIP-B·80/443: ____________________________________________
Router Role Node: ________________________________________
Registry FQDN·Project: ___________________________________
External ETCD Endpoint 기준: _____________________________
검증 시작 시각: _________________________________________
```

> 다른 Cluster의 ETCD나 Registry가 정상이어도 오늘 신규 Member의 증거가 아닙니다.

기능 검증에서 사용할 임시 Resource는 승인된 Runbook의 Test Manifest를 사용한다.

원칙:

```text
고유한 Test 이름
승인된 Namespace
승인된 Image
변경 영향 최소
정리 계획 선확정
민감정보 없음
```

> 긴 Test Manifest는 이 대본에 복제하지 않습니다. 무엇을 증명하기 위해 만드는지만 기억합니다.

---

# 3. External ETCD — 상태 저장소가 같은 신규 Member를 보존하는가

> External ETCD는 Kubernetes API가 보존해야 할 Cluster 상태를 저장합니다. Kubernetes Pod 목록에 ETCD Pod가 보이지 않아도 External Node에서 별도로 실행될 수 있습니다.

반드시 구분한다.

```text
kube-system에 ETCD Pod 없음
≠ ETCD 없음

ETCD Process 실행
≠ Member 전체 정상

Member 목록 정상
≠ 모든 Endpoint 상태 정상
```

## 3.1 확인할 최소 질문

```text
현재 신규 Member의 ETCD Endpoint인가
기대 Member 수가 있는가
각 Endpoint가 건강한가
Leader가 존재하는가
Cluster ID가 하나로 연결되는가
```

정확한 `etcdctl` 인증서·Endpoint 옵션은 현재 승인 Runbook을 따른다. Certificate·Private Key 원문은 화면과 증적에 복사하지 않는다.

## 3.2 ETCD가 증명하는 범위

ETCD health가 정상이라면:

```text
Kubernetes 상태 저장 경로의 기본 기능이 성립
```

하지만:

```text
ETCD 정상
≠ Node Container 실행 정상
≠ Pod Network 정상
≠ DNS·Ingress 정상
```

> ETCD가 비정상이면 뒤 기능 테스트를 계속해 원인을 복잡하게 만들지 않습니다.

---

# 4. Runtime — Service가 떠 있는 것과 실제 Container 실행을 분리한다

> Kubernetes가 Pod를 실행하려면 각 Node의 kubelet이 Container Runtime에 Container 생성을 요청합니다. 이 환경에서는 containerd가 그 역할을 담당합니다.

구분:

```text
containerd Service Running
≠ Kubernetes가 실제 Container 생성 성공

containerd Version 출력
≠ 승인 Version·Config 정상

Registry 설정 파일 존재
≠ 실제 Private Image Pull 성공
```

확인할 최소 범위:

```text
대상 Node의 containerd Service 상태
Runtime Version
Kubernetes가 보고한 CONTAINER-RUNTIME
필요한 Registry Trust·Endpoint 기준
실제 Test Pod의 Container Created·Started
```

> Registry Image Pull에 실패하면 Runtime 자체를 재설치하기 전에 Pod Event의 실제 Image 주소, DNS·Network·CA·Credential·Tag 중 처음 끊긴 지점을 봅니다.

---

# 5. Calico — DaemonSet Running보다 실제 Pod Network가 중요하다

> CNI는 Pod가 Network를 사용할 수 있게 연결하는 표준 경계이고, 현재 환경에서는 Calico가 이 역할을 수행합니다.

확인할 개념:

```text
calico-node
→ 각 대상 Kubernetes Node의 Network Agent

Calico Controller
→ Network 상태·정책 관련 Control 기능

IPPool·Backend
→ Pod IP 대역과 Network 동작 기준
```

반드시 구분한다.

```text
calico-node Running
≠ 실제 Pod IP 할당·통신 정상

IPPool 객체 존재
≠ 승인 Pod CIDR와 일치
```

## 5.1 설정과 실제 설계를 대조한다

```text
8/31 승인 Pod CIDR
↔ 실제 Cluster Pod CIDR
↔ Calico IPPool
```

Role별 대상 Node에 필요한 Calico Agent가 존재하는지도 확인한다.

> ETCD 전용 VM처럼 Kubernetes Node가 아닌 Server를 DaemonSet 대상 수에 포함하지 않습니다.

---

# 6. Test Pod — Runtime과 CNI를 실제로 통과한다

> 이제 설정 객체를 보는 데서 멈추지 않고 승인된 임시 Pod를 실제로 실행합니다.

Test Pod가 답해야 할 질문:

```text
Scheduler가 Node를 선택했는가
Image Pull이 성공했는가
Container가 Created·Started됐는가
Pod가 Ready·Running인가
Pod IP가 승인 Pod CIDR에서 할당됐는가
실제 NODE가 기대 역할인가
```

대표 조회:

```bash
kubectl get pod -n <test-namespace> <test-pod> -o wide
kubectl describe pod -n <test-namespace> <test-pod>
```

증거 범위:

```text
Pod Running + Pod IP
→ Scheduler·Runtime·CNI의 중요한 실제 경로가 통과
```

하지만:

```text
Pod Running
≠ Cluster DNS 질의 성공
≠ 외부 Ingress 성공
```

## 6.1 실패 분기

| 상태·Event | 첫 확인 |
|---|---|
| Pending / Unschedulable | Node Label·Taint·Resource·Scheduler Event |
| ImagePullBackOff | Image 주소·Registry·CA·Credential·Network |
| ContainerCreating 장기 지속 | CNI·Mount·Runtime Event |
| CrashLoopBackOff | Container Log·Command·Application 상태 |
| Pod IP 없음 | CNI·Calico Node·IPPool·Node Network |

> 상태 이름을 원인으로 외우지 않고 Event의 실제 문장을 읽습니다.

---

# 7. Service와 Endpoint — Pod가 있다고 Service 경로가 자동으로 생기지 않는다

> Application을 안정적으로 찾기 위해 Kubernetes는 Pod 앞에 Service를 둡니다.

기본 경로:

```text
Service
→ Selector
→ Endpoint 또는 EndpointSlice
→ 실제 Pod IP:Port
```

확인할 질문:

```text
Service가 의도한 Selector를 갖는가
Endpoint가 실제 Test Pod를 가리키는가
Port와 TargetPort가 맞는가
```

구분:

```text
Service 존재
≠ Endpoint 존재

Endpoint 존재
≠ 실제 요청 성공
```

> 이후 DNS와 Ingress가 이 Service를 사용하므로 Service·Endpoint가 잘못된 상태에서 CoreDNS나 VIP-B부터 조사하지 않습니다.

---

# 8. CoreDNS — Pod Running과 실제 이름 해석을 구분한다

> CoreDNS는 Cluster 안에서 Service 이름을 ClusterIP로 찾게 합니다.

정상 경로:

```text
Test Pod
→ Service DNS 이름 질의
→ CoreDNS
→ Service ClusterIP 반환
→ Service Endpoint 접근
```

구분:

```text
CoreDNS Pod Running
≠ 실제 DNS Query 성공

DNS Query 성공
≠ 대상 Service Endpoint 기능 성공
```

## 8.1 실제 질의

승인된 Test Pod에서 현재 Service 이름을 조회한다.

예:

```bash
kubectl exec -n <test-namespace> <test-pod> -- \
  getent hosts <test-service>.<test-namespace>.svc.<current-domain>
```

현재 Image에 `getent`가 없다면 Runbook이 지정한 승인된 DNS Test 도구를 사용한다.

검증:

```text
질의 이름이 현재 Cluster Domain 사용
+ 반환 ClusterIP가 실제 Service와 일치
+ 실제 Service 요청도 성공
```

> 과거 Cluster Domain으로 우연히 질의가 성공하거나 `/etc/hosts`로 우회된 결과를 Cluster DNS 증거로 사용하지 않습니다.

---

# 9. Ingress — Controller Running 뒤의 사용자 경로를 실제로 연결한다

> 외부 사용자가 Application에 접근할 때는 Router Role의 Ingress Controller와 VIP-B가 이어집니다.

전체 경로:

```text
사용자 또는 Test Source
→ DNS / FQDN
→ VIP-B:80 또는 443
→ Router Backend
→ ingress-nginx-controller
→ Ingress Rule
→ Service
→ Endpoint
→ Pod
```

## 9.1 먼저 Controller 배치를 본다

```text
Ingress Controller Pod Ready
+ 실제 NODE가 승인 Router
+ 필요한 Label·Taint·Toleration 일치
```

구분:

```text
Ingress Controller Running
≠ Ingress Rule 정상
≠ Service Endpoint 정상
≠ VIP-B Mapping 정상
```

## 9.2 Router NodePort와 VIP-B를 분리한다

Xi'an 설계의 대표 구조는 현재 승인값을 확인해 다음 관계로 읽는다.

```text
VIP-B:80
→ Router의 승인 HTTP NodePort

VIP-B:443
→ Router의 승인 HTTPS NodePort
```

> 정확한 NodePort는 현재 Service 출력과 승인 설계를 사용합니다. 과거 `30080`, `30443` 값을 자동으로 현재값으로 사용하지 않습니다.

먼저 Router 경로를 확인하고 그다음 VIP-B를 본다.

```text
Service·Endpoint 정상
→ Router NodePort 응답
→ VIP-B Frontend 응답
```

이 순서가 중요한 이유는 VIP-B 실패 시 Cluster 내부와 LB 경계를 분리할 수 있기 때문이다.

---

# 10. HTTP 성공과 HTTPS 성공을 분리한다

```text
VIP-B HTTP 80 성공
≠ HTTPS 443 성공
```

HTTPS에는 추가로 다음이 들어갈 수 있다.

```text
Certificate
TLS 종료 위치
SNI·Host
Ingress TLS 설정
LB 방식
```

> `curl -k`로 응답이 나온다고 Certificate Trust까지 통과한 것은 아닙니다. 검증 목적을 명시하고 승인된 CA를 사용한 정상 TLS 확인을 별도로 판정합니다.

9월 2일 Storage 진입 Gate에서 반드시 외부 Application HTTPS까지 요구하는지는 현재 일정·검증 기준을 따른다. 하지만 Router·Ingress 기본 경로의 미해결 오류는 Storage 이후로 미루지 않는다.

---

# 11. Add-on은 전부 같은 중요도로 보지 않는다

> Kubespray Bundle에는 metrics-server 등 여러 Add-on이 있을 수 있습니다. 모든 Pod를 같은 중요도로 취급하면 핵심 Kubernetes 기반과 부가 기능을 구분하기 어렵습니다.

우선순위:

```text
9/2 Storage를 가능하게 하는 Kubernetes 핵심 기반
→ 반드시 PASS 필요

부가 Add-on
→ 현재 일정상 다음 단계 필수인지 판단
```

다만 다음은 비차단이라고 임의 판단하지 않는다.

```text
CNI
CoreDNS
API·Node 기반
Container Runtime
Storage가 의존하는 Node Network·DNS
```

> 다음 단계 선행조건을 실제로 바꾸는 기능은 반드시 닫습니다.

---

# 12. 임시 Resource 정리도 검증의 일부다

> Test Pod·Service·Ingress를 만들었다면 성공 화면을 확인한 뒤 그대로 두지 않습니다.

정리 전에 기록할 것:

```text
Test Namespace·Resource 이름
생성 목적
성공 증거
문제 조사에 더 필요한지
삭제 영향
```

승인된 Runbook에 따라 Test Resource를 정리하고 다음을 확인한다.

```text
Test Pod·Service·Ingress 제거
+ 의도하지 않은 운영 Resource 영향 없음
+ 잔여 Endpoint 없음
+ Critical Event 없음
```

> 정리 결과를 확인하지 않은 실습은 완료가 아닙니다.

---

# 13. 실패 시 전체 경로에서 첫 단절을 고른다

| 증상 | 먼저 볼 경계 |
|---|---|
| ETCD endpoint unhealthy | 실제 Endpoint·TLS·Network·Member 상태 |
| Test Pod ImagePullBackOff | Image 주소·Registry·CA·Credential·Network |
| Pod IP 없음 | Calico Agent·IPPool·Node Network |
| Pod Running, DNS 실패 | CoreDNS·Service·Cluster Domain·Network |
| DNS 성공, Service 요청 실패 | Service Selector·Endpoint·TargetPort |
| Router NodePort 성공, VIP-B 실패 | LB Frontend·Backend·Health·Network |
| VIP-B HTTP 성공, HTTPS 실패 | TLS·Certificate·443 Mapping·Ingress 설정 |

> 뒤 단계가 실패했다고 앞 단계까지 모두 실패로 되돌리지 않습니다. 마지막 성공과 첫 실패 사이를 좁힙니다.

# 14. 9월 2일 Storage 진입 Gate

9월 1일 종료 판정은 `KUBERNETES BASE PASS / BLOCKED` 두 상태만 사용한다.

## 14.1 KUBERNETES BASE PASS

```text
CONTROL PATH PASS
+ External ETCD 기본 health·member 상태 정상
+ 각 Kubernetes Node의 Runtime 기본 상태 정상
+ 승인 Test Pod 실제 Container 실행
+ Calico 기반 Pod IP 할당·Network 기본 기능 정상
+ Service·Endpoint 정상
+ 실제 Cluster DNS 질의 성공
+ Ingress Controller가 승인 Router에 배치
+ Router NodePort 기본 경로 정상
+ 다음 단계에 필요한 VIP-B 경로 정상
+ 미해결 Critical Event 없음
+ Test Resource 정리 완료
```

> 이 상태는 Kubernetes 기반이 Storage Component를 설치하고 PVC·Pod를 검증할 만큼 성립했다는 뜻입니다.

## 14.2 BLOCKED

다음 중 Storage의 선행조건을 흔드는 문제가 남으면 BLOCKED다.

```text
External ETCD 비정상 원인 미확정
필수 Node Runtime 비정상
Test Pod 실행 실패
CNI·Pod IP·기본 통신 실패
Cluster DNS 실제 질의 실패
Service·Endpoint 기본 경로 실패
Router·Ingress 기본 기능 실패
Storage가 사용할 Node Network 경로의 중대한 이상
Critical Event 미해결
Test Resource 정리 위험 또는 영향 미확정
```

> Storage 설치가 의존하는 Kubernetes 기반이 미해결이면 다음 날짜로 넘기지 않고 먼저 닫습니다.

> 오후 첫 블록에서는 API·전역 설계·Node·Control Plane이라는 Control Path를 증명했습니다.
>
> 마지막으로 External ETCD, Runtime, CNI, DNS와 Ingress를 실제 Test Pod·Service·요청 경로로 확인했습니다.
>
> **결국 9월 1일 완료는 System Pod가 많이 Running인 상태가 아니라, 신규 Member가 상태를 보존하고 Container를 실행하며 Pod Network와 DNS를 사용하고 필요한 외부 요청 경로를 제공할 수 있다는 것을 독립 증거로 확인한 상태입니다.**
