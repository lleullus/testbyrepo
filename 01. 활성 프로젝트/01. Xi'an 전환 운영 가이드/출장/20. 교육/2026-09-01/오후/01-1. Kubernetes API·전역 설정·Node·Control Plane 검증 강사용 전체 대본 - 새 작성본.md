# Kubernetes API·전역 설정·Node·Control Plane 검증 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 오전에는 Kubespray를 실행해 `PLAYBOOK EXECUTION PASS`를 확인했다. 이번 블록은 **자동화 결과가 실제 신규 Member의 API 입구, 전역 설정, Node와 Control Plane으로 만들어졌는지 확인하는 과정**이다.
>
> 조회 명령과 현재값은 승인된 9월 1일 기준 문서를 따른다. kubeconfig·Token·Client Key와 Certificate Key 원문은 화면과 증적에 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
Kubespray 실행이 끝났다
→ 하지만 실제 Kubernetes 제어 기능은 별도다
→ 먼저 kubectl이 어느 Cluster를 보는지 확인한다
→ 승인 VIP-A로 API가 응답하는지 확인한다
→ 실제 Version·CIDR·Domain을 입력값과 대조한다
→ 예상 Node가 올바르게 등록됐는지 확인한다
→ Label·Taint와 Control Plane 상태를 확인한다
→ 이 범위가 정상이어야 다음 기능 검증으로 간다
```

## 0-1. 오늘 전체 한 줄

> 이번 블록은 `kubectl get nodes` 화면을 보는 시간이 아닙니다. **오전에 실행한 설계가 실제 신규 Member의 API·전역값·Node·Control Plane으로 반영됐는지 확인하는 시간**입니다.

---

# 1. 시작 — Playbook 성공과 Kubernetes 제어 가능 상태는 다르다

> 오전의 성공은 Kubespray Task가 미해결 오류 없이 끝났다는 뜻입니다.
>
> **하지만 운영자가 올바른 API에 접속할 수 있는지, 입력한 VIP·CIDR·Domain·Version이 실제로 반영됐는지는 별도입니다.**
>
> 예상 Node가 올바른 Role과 IP로 등록되고 Control Plane이 기능하는지도 확인해야 합니다.
>
> 그래서 오후 첫 블록에서는 Kubernetes의 Control Path를 봅니다.
>
> Control Path는 올바른 Context에서 승인 VIP-A로 API에 접근하고, 그 API에서 실제 설계와 Node·Control Plane 상태를 확인하는 경로입니다.

---

# 2. kubectl 출력보다 먼저 Context를 확인한다

> `kubectl get nodes`가 성공해도 오늘 만든 신규 Member라는 뜻은 아닙니다.
>
> Bastion에 과거 kubeconfig가 남아 있거나 현재 Context가 기존 Host 또는 다른 Member를 가리킬 수 있습니다.
>
> 그래서 현재 Context 이름과 API Server 주소를 확인합니다. 그 Endpoint가 이번 신규 Member의 승인 VIP-A와 연결되는지도 봅니다.
>
> kubeconfig에는 여러 Context와 Cluster 정보가 함께 들어갈 수 있습니다. Context는 어떤 Cluster 정보와 인증 정보를 사용할지 선택하고, 선택된 Cluster의 `server` 값이 실제 `kubectl` 요청이 향하는 API Endpoint가 됩니다.
>
> 그래서 Context 이름만 신규 Member처럼 보이는 것으로 끝내지 않습니다. 현재 Context가 실제로 어느 Cluster Entry를 선택하고 있고, 그 Cluster Entry의 Server Endpoint가 승인 VIP-A를 가리키는지 같이 확인합니다.
>
> 출력된 Node 이름을 오전 기대값과 교차하면 대상 확인에 도움이 됩니다.
>
> 또한 Node 이름은 보조 증거입니다. 과거 Cluster와 Hostname 규칙이 비슷하거나 일부 Node 이름이 겹칠 수 있으므로 Context·Endpoint와 함께 봅니다.
>
> kubeconfig 원문 전체를 보여줄 필요는 없습니다. 어느 Context가 어느 Endpoint로 요청하는지가 중요합니다.
>
> Context가 다르면 이후 출력은 오늘 검증의 증거가 아닙니다.

---

# 3. Master 직접 API와 VIP-A API는 다른 경로다

> Master IP로 API가 응답하면 그 Master의 API Process와 Listener가 동작한다는 것은 알 수 있습니다.
>
> **하지만 운영자가 사용할 공통 입구는 VIP-A입니다.** Master 직접 주소가 성공해도 Load Balancer Frontend·Backend·Health Check·Network·TLS 문제로 VIP-A가 실패할 수 있습니다.
>
> VIP-A는 단순히 Master IP를 다른 이름으로 부르는 값이 아닙니다. 운영자는 하나의 공통 Endpoint로 요청하고, Load Balancer는 현재 정상으로 판단한 Control Plane Backend로 그 요청을 전달합니다.
>
> 그래서 Master 하나의 직접 API가 정상이어도 VIP-A Frontend가 열리지 않았거나 Backend Mapping이 틀리고 Health Check가 실패하면 실제 운영 경로는 정상이라고 할 수 없습니다.
>
> 그래서 승인된 VIP-A 또는 FQDN으로 API Health와 Ready 응답을 확인합니다.
>
> 이때 API Health 응답은 Load Balancer를 거쳐 Kubernetes API Server까지 요청이 도달하고 응답이 돌아오는 경로를 확인하는 것입니다. 단순 Port Open 확인보다 한 단계 더 실제 API 기능에 가깝습니다.
>
> `-k`처럼 Certificate 검증을 생략한 요청이 성공해도 정상 Trust까지 증명한 것은 아닙니다.
>
> 반대로 x509 오류가 보이면 Server 도달과 Certificate 신뢰를 구분합니다.
>
> 예를 들어 TLS Handshake 단계까지 도달한 뒤 Certificate 오류가 발생했다면 Network가 완전히 막힌 경우와 조사 시작점이 다릅니다. 이때 FQDN·SAN·CA Trust와 실제 접속 Endpoint를 확인합니다.
>
> VIP-A가 정상이라면 공통 API 입구가 열린 것입니다. 그다음 실제 Cluster 설정이 입력값과 같은지 확인합니다.

# 4. 입력 파일이 아니라 실제 전역 설정을 본다

> 실행 전에는 Version·VIP·Pod CIDR·Service CIDR·Cluster Domain을 변수 파일에 넣었습니다.
>
> **하지만 파일에 올바른 값이 남아 있다는 사실은 의도를 보여줄 뿐 실제 적용 결과를 대신하지 않습니다.**
>
> 변수 우선순위나 과거 설정 때문에 다른 값이 적용됐을 수 있습니다.
>
> 그래서 API와 실제 Component 설정에서 Kubernetes Version, Control Plane Endpoint, Pod·Service CIDR과 Cluster Domain을 확인합니다.
>
> Kubernetes Version은 API Server와 Node Component가 어떤 Kubernetes 기준으로 동작하는지 보여 줍니다. 따라서 기대 Version과 실제 API·Node Version이 다르면 단순 표시 차이로 보지 않고 현재 Bundle과 설치 결과를 다시 대조합니다.
>
> Pod CIDR은 이후 CNI가 Pod에 배정할 주소 범위의 기준입니다. 이 값이 승인 설계와 다르면 Pod가 생성된 뒤 Network 검증에서도 다른 주소 체계를 보게 됩니다.
>
> Service CIDR은 ClusterIP Service가 사용할 주소 범위의 기준입니다. 그래서 Service 객체가 정상 생성돼도 실제 ClusterIP가 승인 Service CIDR과 다른지 확인할 수 있어야 합니다.
>
> Cluster Domain은 Service 이름을 Kubernetes 내부 DNS 이름으로 해석할 때 사용하는 기준입니다. 따라서 Domain이 다르면 다음 블록의 CoreDNS 검증에서 같은 Service를 다른 이름 체계로 찾게 될 수 있습니다.
>
> Control Plane Endpoint는 운영자와 Kubernetes Component가 공통 API 경로를 어떤 주소로 사용할지와 연결됩니다. 그래서 앞에서 확인한 VIP-A와 실제 설정이 같은 방향을 가리키는지 함께 봅니다.
>
> 그 결과를 8월 31일 승인값과 대조합니다.
>
> 값이 다르면 즉시 숫자를 수정하고 전체 Playbook을 다시 실행하지 않습니다. 승인 Source와 실제 적용 위치를 확인하고 변경 영향과 절차를 판단합니다.
>
> 특히 CIDR과 Domain은 설치 후 가볍게 바꿀 수 있다고 가정하지 않습니다.

# 5. Node 목록은 개수가 아니라 실제 VM을 확인하는 것이다

> 예상한 수의 Node가 보인다고 설계가 모두 맞는 것은 아닙니다.
>
> 빠진 Node와 예상하지 않은 Node가 서로 상쇄돼 개수만 맞을 수도 있습니다.
>
> 그래서 각 Node의 Name·Internal IP·Version을 8월 31일 Role·Hostname·IP와 대조합니다.
>
> Node Name은 kubelet이 어떤 Identity로 Cluster에 등록됐는지 보여 주고, Internal IP는 Control Plane이 그 Node를 어떤 주소로 인식하는지 확인하는 기준입니다.
>
> 그래서 Hostname은 맞지만 Internal IP가 다른 경우나, IP는 맞지만 예상하지 않은 Node Name으로 등록된 경우를 같은 정상으로 보지 않습니다.
>
> OS와 Container Runtime 정보도 현재 Bundle 기준과 맞는지 확인합니다.
>
> 여기서 Container Runtime 정보는 Runtime Service 전체 기능을 검증하는 것이 아니라 kubelet이 어떤 Runtime과 연결된 Node로 등록됐는지 확인하는 자료입니다. 실제 Container 생성은 다음 블록에서 Test Pod로 다시 확인합니다.
>
> Node가 `Ready`이면 kubelet이 Control Plane과 기본 상태를 주고받고 있다는 중요한 증거입니다.
>
> **하지만 Ready가 CNI·DNS·Ingress·Storage까지 정상이라는 뜻은 아닙니다.** 여기서는 Node 등록과 기본 상태까지만 확인합니다.
>
> Ready는 kubelet이 Node 상태를 API Server에 보고하고 Control Plane이 그 Node를 기본적으로 사용할 수 있는 상태로 보고 있다는 의미입니다. 따라서 Ready 하나로 Pod 간 통신이나 Service, DNS 같은 Application 기능까지 확대하지 않습니다.

> ROLES 문자열만으로 이후 Workload 배치까지 확정하지 않습니다.
>
> Master·Router·Infra·Worker에 필요한 Label과 Taint가 승인 배치 기준과 같은지 확인합니다.
>
> Label은 Scheduler나 운영 정책이 Node를 선택하는 기준으로 사용될 수 있고, Taint는 허용되지 않은 Pod가 특정 Node에 배치되는 것을 막는 기준으로 사용됩니다.
>
> 그래서 Router나 Infra Node의 이름이 맞더라도 필요한 Label·Taint가 빠져 있으면 이후 Ingress나 Monitoring Workload가 의도한 Node에 배치된다고 가정할 수 없습니다.
>
> 다만 실제 Ingress·Monitoring·KubeSphere Pod 배치는 해당 기능 블록에서 다시 확인합니다.

---

# 6. Control Plane은 Pod 개수보다 역할과 상태로 본다

> API Server는 요청을 받고, Controller Manager는 원하는 상태와 현재 상태를 맞추며, Scheduler는 Pod 배치 대상을 결정합니다.
>
> 사용자가 Deployment 같은 Resource를 생성하면 먼저 API Server가 요청을 받아 Kubernetes 상태로 기록합니다. 그다음 Controller Manager가 원하는 Replica 수와 현재 상태의 차이를 보고 필요한 Pod 생성을 조정합니다.
>
> 그리고 아직 Node가 정해지지 않은 Pod가 생기면 Scheduler가 Node의 Resource와 배치 조건을 보고 대상 Node를 선택합니다. 선택 결과는 다시 API를 통해 Cluster 상태에 반영되고 각 Node의 kubelet이 실제 실행을 이어받습니다.
>
> 그래서 API Server·Controller Manager·Scheduler는 서로 따로 존재하는 Process가 아니라 Kubernetes의 제어 흐름을 순서대로 이어가는 핵심 Component입니다.
>
> Component가 Running이면 Process가 시작됐다는 것은 알 수 있습니다.
>
> **하지만 API Health·Leader Election·Scheduling·Controller 동작 전체를 자동으로 증명하지는 않습니다.**
>
> API Server Pod가 Running이어도 VIP-A를 통한 실제 API 요청이 실패할 수 있고, Controller Manager나 Scheduler가 Running이어도 반복 재시작하거나 Leader Election을 유지하지 못하면 안정적인 제어 기능을 기대할 수 없습니다.
>
> 반대로 Pod 하나의 Restart가 존재한다는 이유만으로 현재 Control Plane이 비정상이라고 바로 판단하지 않습니다. 현재 Ready 상태와 Restart 증가 여부, Event·Log의 반복 오류를 같이 봅니다.
>
> 그래서 현재 Bundle과 Master 수를 기준으로 실제 배치와 Ready·Restart 상태를 확인합니다.
>
> Event와 Log에 반복되는 Critical Error가 없는지도 봅니다.
>
> 특히 여러 Master를 사용하는 구조에서는 Control Plane Component가 승인된 Master 집합에 배치돼 있는지 확인합니다. 한 Master만 정상인 결과를 전체 Control Plane 정상으로 확대하지 않습니다.
>
> 정확한 Pod 이름과 개수를 외우는 것이 아니라 API, Controller와 Scheduler가 제어 기능을 수행할 상태인지 확인하는 것이 목적입니다.

# 7. 이 블록의 완료는 CONTROL PATH PASS다

> 올바른 Context에서 승인 VIP-A API가 응답해야 합니다.
>
> 실제 Version·CIDR·Domain이 승인 설계와 맞고, 예상 Node가 올바른 Name·IP·Role·Ready 상태로 등록돼야 합니다.
>
> Label·Taint와 Control Plane 핵심 상태도 현재 설계와 맞아야 합니다.
>
> 그래서 `CONTROL PATH PASS`는 단일 명령 하나가 성공한 결과가 아닙니다. 운영자가 올바른 Cluster를 선택했고, 공통 API 입구가 실제로 동작하며, Cluster 전역값과 Node Identity·배치 기준·Control Plane 상태가 같은 신규 Member 설계를 설명하는 결과여야 합니다.
>
> 이 범위가 정상일 때 `CONTROL PATH PASS`라고 합니다.
>
> **하지만 아직 Kubernetes 전체 기반 PASS는 아닙니다.** External ETCD Health, Runtime의 실제 Container 실행, CNI·Service·DNS·Ingress 기능은 다음 블록에서 확인합니다.

---

# 8. 문제가 생기면 Control Path 순서대로 확인한다

> 출력이 예상과 다르면 먼저 Context를 확인합니다. 다른 Cluster를 보고 있다면 Node나 API를 고칠 문제가 아닙니다.
>
> Context는 맞는데 Server Endpoint가 다르면 kubeconfig와 승인 VIP-A 관계를 확인합니다. 이 단계에서 Node Label이나 CNI 설정을 바꾸지 않습니다.
>
> Master 직접 API는 되는데 VIP-A가 실패하면 Control Plane 재설치보다 Load Balancer·DNS·Network·TLS를 봅니다.
>
> VIP-A까지 Network 연결은 되지만 x509 오류가 발생하면 Backend 전체 장애로 확대하지 않고 FQDN·Certificate SAN·CA Trust와 접속 주소를 확인합니다.
>
> VIP-A는 되는데 CIDR·Domain이 다르면 실제 입력과 변수 우선순위를 확인합니다.
>
> 이때 다른 전역값까지 한꺼번에 수정하지 않고, 승인 Source와 실제 Component 설정 사이에서 어느 값이 다르게 적용됐는지 좁힙니다.
>
> 특정 Node만 없거나 NotReady라면 해당 Node의 Identity·kubelet·Network·Runtime을 같은 Role의 정상 Node와 비교합니다.
>
> 여러 Node가 같은 증상이라면 개별 Host보다 공통 설정과 Control Plane 경로를 먼저 볼 수 있습니다. 반대로 한 Node만 다르면 해당 Node의 상태 차이를 우선 확인합니다.
>
> Node는 Ready인데 Label·Taint가 다르면 CNI 문제로 확대하지 않고 배치 기준 적용 위치를 확인합니다.
>
> Control Plane Component가 반복 재시작하면 Pod를 삭제해 다시 띄우는 것부터 하지 않고 Event·Log와 해당 Component의 설정·Certificate·연결 경로를 확인합니다.
>
> 확인 순서는 `Context → VIP-A API → 전역 설정 → Node Identity·Ready → Label·Taint → Control Plane`입니다.

---

# 9. 다음 블록에는 실제 Control Path 결과를 넘긴다

> 다음 블록에서는 External ETCD, Runtime, CNI, DNS와 Ingress를 검증합니다.
>
> 그래서 Cluster Name·Stage·Context와 실제 API Endpoint, VIP-A Health 결과를 넘깁니다.
>
> 실제 Kubernetes Version·Pod CIDR·Service CIDR·Domain과 Node별 Role·Hostname·Internal IP·Version·Ready도 전달합니다.
>
> Label·Taint, Control Plane 상태와 미해결 Event가 있다면 해당 내용도 함께 남깁니다.
>
> kubeconfig와 Key 원문은 제외합니다.

---

# 10. 마무리

> Playbook이 끝나도 실제 Kubernetes 제어 기능은 별도로 확인해야 했습니다.
>
> 그래서 먼저 Context를 확인하고, Master 직접 주소가 아니라 승인 VIP-A로 API를 확인했습니다.
>
> 그다음 입력했던 Version·CIDR·Domain이 실제로 반영됐는지 대조하고, 예상 Node의 Identity·Ready·배치 기준과 Control Plane 상태를 확인했습니다.
>
> **결국 CONTROL PATH PASS는 명령 출력이 보이는 상태가 아니라, 올바른 Context와 VIP-A에서 실제 신규 Member의 설계·Node·Control Plane을 확인할 수 있는 상태입니다.**
