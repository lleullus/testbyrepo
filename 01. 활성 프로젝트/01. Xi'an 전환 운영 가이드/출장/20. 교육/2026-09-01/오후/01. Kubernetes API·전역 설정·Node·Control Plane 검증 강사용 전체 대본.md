# Kubernetes API·전역 설정·Node·Control Plane 검증 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 오전 Kubespray 실행이 미해결 자동화 오류 없이 끝난 뒤, **8월 31일에 입력한 신규 Member 설계가 실제 Kubernetes Control Path로 만들어졌는지 증명하는 법**을 가르친다. `kubectl` 명령을 외우는 것이 목적이 아니다. 같은 신규 Member Context에서 **API → 실제 전역값 → Node Identity·Role·Ready → Control Plane**을 독립 증거로 확인하고 다음 Data Plane 검증으로 넘기는 것이 목적이다.

## 0. 오전에서 이어받는 것

```text
Cluster Name·Stage
Bastion·Bundle 기준
Inventory·주요 변수 Checksum
Kubernetes Version 기대값
VIP-A 기대값
Pod CIDR·Service CIDR·Domain 기대값
Node Role·Hostname·IP 기대표
최종 cluster.yml Return Code·PLAY RECAP
실행 로그
최초 실패·조치·재검증 기록
```

> 오후에는 이 값을 다시 만들어내지 않습니다. **이 값이 실제 Cluster에 어떻게 반영됐는지 확인합니다.**

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> `kubectl get nodes` 한 화면만 보고 설치 완료를 선언하지 않고, **현재 kubeconfig가 신규 Member를 가리키는지 → VIP-A API가 실제 응답하는지 → 전역 설계값이 입력과 같은지 → 예상 Node가 올바른 Role·IP·Version으로 등록되고 Ready인지 → Control Plane 핵심 Component가 기능하는지**를 구분해서 판정할 수 있어야 한다.

오늘의 중심 질문:

> **8월 31일에 입력한 신규 Member 설계가 실제 Kubernetes Control Path로 만들어졌는가?**

---

# 1. 시작 — `kubectl` 성공보다 어느 Cluster에 묻고 있는지가 먼저다

> 오전에는 Kubespray가 신규 Member Node에 Kubernetes를 설치했습니다.
>
> 이제 사람이 Cluster에 질문합니다. `kubectl`은 Node 파일을 직접 읽는 도구가 아니라 Kubernetes API Server에 요청을 보내는 Client입니다.
>
> 따라서 결과가 그럴듯한가보다 **어느 kubeconfig의 어느 Context가 어느 API Server를 가리키는가**가 먼저입니다.

정상 요청 경로:

```text
운영자
→ kubectl
→ kubeconfig
→ current-context
→ 신규 Member API Endpoint
→ kube-apiserver
→ Resource 응답
```

반드시 구분한다.

```text
kubectl Binary 존재
≠ 신규 Member 접근 준비

current-context 표시
≠ 신규 Member Context

Resource 응답 성공
≠ VIP-A 경로까지 정상
```

---

# 2. 검증 대상을 하나로 고정한다

먼저 기록한다.

```text
검증 Cluster Name·Stage: ________________________________
현재 kubeconfig: _________________________________________
current-context: _________________________________________
API Server URL: __________________________________________
VIP-A 기대값: ____________________________________________
Kubernetes Version 기대값: _______________________________
Pod CIDR 기대값: _________________________________________
Service CIDR 기대값: _____________________________________
Domain 기대값: ___________________________________________
Node 기대표 위치: ________________________________________
오전 실행 Log·Recap: _____________________________________
```

기본 확인 예:

```bash
kubectl config current-context
kubectl config view --minify
```

> kubeconfig에는 Credential이 포함될 수 있으므로 원문 전체를 교육 증적에 복사하지 않습니다. Cluster Name, Server URL, Context 같은 판정 정보만 승인된 방식으로 확인합니다.

## 2.1 다른 Cluster에서의 성공은 증거가 아니다

```text
기존 PRD Member kubectl 성공
≠ 신규 Member API 성공

Master 직접 API 성공
≠ VIP-A 경로 성공
```

> 검증 중 Context가 바뀌면 뒤 결과를 같은 증거 묶음으로 사용하지 않습니다.

---

# 3. API는 직접 경로와 VIP-A 경로를 구분한다

> API Server가 Master에서 동작하는 것과 운영자·Bastion이 VIP-A를 통해 접근하는 것은 서로 다른 경로입니다.

개념적으로:

```text
Master 내부 또는 직접 경로
→ kube-apiserver 자체 기능

운영자·Bastion
→ VIP-A:6443
→ Master API Backend
```

## 3.1 API 응답과 준비 상태

대표적인 읽기 전용 확인은 현재 승인 Runbook을 따른다.

예:

```bash
kubectl get --raw='/readyz?verbose'
```

또는 승인된 API health 확인 경로를 사용한다.

증거 범위:

```text
readyz 정상
= 현재 kubeconfig가 가리키는 API가 주요 readiness check를 통과
```

하지만:

```text
readyz 정상
≠ Node 전체 정상
≠ ETCD·CNI·DNS·Ingress 실제 기능 전체 정상
```

## 3.2 VIP-A 자체를 증명한다

> kubeconfig의 Server URL이 VIP-A인지 확인하고, 8월 31일 승인값과 대조합니다. Master 개별 IP를 가리키는 임시 kubeconfig로 성공한 결과를 VIP-A HA 경로의 증거로 확대하지 않습니다.

CONTROL PATH에서 VIP-A가 틀리면 다음 단계로 넘기지 않는다.

---

# 4. 전역 설정 — 입력 파일이 실제 Cluster에 반영됐는가

> 이제 8월 31일에 넣은 설계값이 실제 Cluster 설정으로 만들어졌는지 확인합니다.

최소 대조 항목:

```text
Control Plane Endpoint / VIP-A
Kubernetes Version
Cluster Name 또는 식별 기준
Pod CIDR
Service CIDR
Cluster DNS Domain
필요한 Node CIDR 관련 설정
```

현재 Cluster 설정을 읽는 정확한 위치와 명령은 Kubespray Runbook·검증 기준을 따른다.

대표적으로 kubeadm 관련 ConfigMap 등을 조회할 수 있다.

```bash
kubectl -n kube-system get cm kubeadm-config -o yaml
```

> 출력 전체를 외우는 것이 아니라 **어제 기대값과 오늘 실제값을 한 항목씩 대조**합니다.

## 4.1 반드시 구분할 것

```text
설정 객체 존재
≠ 값이 승인 설계와 일치

Kubernetes Version 출력
≠ Bundle·Registry·Package 기준까지 모두 일치
```

값이 다르면 “설치가 됐으니 나중에 고친다”로 넘기지 않는다. 영향이 큰 Cluster Identity·Network 값은 다음 기능 검증 전에 원인과 범위를 판정한다.

---

# 5. Node — 목록이 아니라 예상 설계와 실제 등록을 대조한다

대표 조회:

```bash
kubectl get nodes -o wide
```

한 Node에서 볼 핵심은 다음 정도다.

```text
NAME
STATUS
ROLES 또는 Label 기반 Role
INTERNAL-IP
VERSION
OS
CONTAINER-RUNTIME
```

## 5.1 Node 목록 표시와 정상 등록을 분리한다

```text
Node 이름이 목록에 있음
≠ 기대한 VM이 맞음

모든 Node가 표시됨
≠ Role이 올바름

Ready
≠ Version·IP·Runtime·Label·Taint가 승인 설계와 일치
```

따라서 각 Node를 8월 31일 기대표와 대조한다.

```text
기대 Hostname
↔ 실제 NAME

기대 Management/Internal IP
↔ 실제 INTERNAL-IP

기대 Role
↔ 실제 Label·Role

기대 Kubernetes Version
↔ 실제 VERSION
```

## 5.2 Node Ready가 증명하는 범위

```text
Ready=True
→ kubelet이 Control Plane과 기본 상태 보고를 주고받는 경로가 성립
```

하지만:

```text
Ready=True
≠ 실제 Pod Network 통신 정상
≠ Cluster DNS 질의 정상
≠ Ingress 사용자 경로 정상
≠ Storage 정상
```

> 이 경계가 다음 블록이 필요한 이유입니다.

---

# 6. Label과 Taint는 Role 이름보다 실제 배치 정책을 만든다

> Master·Router·Infra·Worker 같은 Role은 표시용 이름만이 아니라 뒤 Workload 배치에 영향을 줍니다.

확인 질문:

```text
Master는 Control Plane 역할 Label·Taint가 기대대로 있는가
Router는 Ingress 배치 대상 Label·Taint가 있는가
Infra는 플랫폼 Workload 배치 조건이 있는가
Worker는 사용자 Workload 조건과 맞는가
ETCD는 승인 설계의 Role 경계가 유지되는가
```

정확한 Label·Taint 값은 현재 Bundle과 8월 31일 승인 설계를 따른다.

구분:

```text
Role 문자열 표시
≠ 필요한 Label·Taint 정책 전체 정상
```

> 다음 날 Monitoring·KubeSphere는 Infra 배치 조건을 실제로 사용하므로 지금 잘못된 Role·Label을 “Pod가 뜨면 된다”로 넘기지 않습니다.

---

# 7. Control Plane은 세 역할을 각각 본다

Kubernetes Control Plane의 핵심 역할:

```text
kube-apiserver
→ 모든 Kubernetes API 요청의 입구

kube-controller-manager
→ 원하는 상태와 실제 상태를 맞추는 Controller 실행

kube-scheduler
→ 새 Pod를 어느 Node에 배치할지 결정
```

설치 방식에 따라 Static Pod 등으로 확인할 수 있다. 정확한 조회는 현재 Cluster 구조를 따른다.

대표 조회:

```bash
kubectl -n kube-system get pods -o wide
```

또는 필요한 Label/이름으로 좁혀 본다.

## 7.1 Pod Running과 기능 정상은 다르다

```text
Control Plane Pod Running
≠ Restart·Event·Endpoint까지 정상
```

확인할 최소 항목:

```text
예상 Replica 또는 Node별 배치
Ready 상태
Restart 급증 없음
실제 NODE가 기대 Master인지
Critical Event 없음
```

> Pod 이름 suffix는 외우지 않습니다. **어떤 역할 Component가 어느 Master에서 왜 있어야 하는지**를 이해합니다.

---

# 8. kube-proxy와 System Pod를 전체 성공으로 확대하지 않는다

> `kube-system`에 Pod가 많이 Running이면 좋아 보이지만 하나의 총점으로 판정하지 않습니다.

예:

```text
kube-proxy
→ Node의 Service Network 처리 일부

CoreDNS
→ Cluster DNS

Calico
→ Pod Network
```

이 블록에서는 kube-proxy와 전체 System Pod에 명백한 이상이 없는지 확인하지만, **CoreDNS와 Calico의 실제 기능 성공은 다음 블록에서 별도 검증**한다.

구분:

```text
System Pod Running
≠ Data Plane 실제 기능 정상
```

---

# 9. 비정상이면 같은 대상에서 첫 차이를 찾는다

대표 분기:

| 증상 | 첫 확인 |
|---|---|
| `kubectl` 연결 실패 | kubeconfig Context·Server URL·VIP-A·TLS·Network |
| Master 직접 API는 되나 VIP-A 실패 | LB Frontend·Backend·TLS/API 경로 |
| 기대 Node 누락 | Inventory·kubelet·Network·Join/Bootstrap 상태 |
| 한 Node NotReady | 해당 Node Condition·kubelet·Network·Runtime 차이 |
| Role·IP 다름 | 8/31 Inventory와 실제 Node Identity 대조 |
| Control Plane Pod 비정상 | 해당 Master·Pod Event·Static Pod/Service 상태 |
| Version 불일치 | Bundle·Inventory·Package·설치 로그 |

> 전체 Cluster 재설치로 바로 가지 않습니다. **정상 Node와 실패 Node의 첫 차이**를 먼저 찾습니다.

---

# 10. Control Path PASS를 판정한다

이 블록의 완료 기준:

```text
신규 Member kubeconfig·Context 확인
+ API Server가 승인 VIP-A를 가리킴
+ API readiness 정상
+ 8/31 VIP·CIDR·Domain·Version 기대값과 실제 설정 대조
+ 예상 Node가 모두 등록
+ Node Name·IP·Role·Version 일치
+ 필요한 Node Ready
+ Role별 Label·Taint가 승인 설계와 일치
+ Control Plane 핵심 Component 정상
+ 미해결 Critical Event 없음
```

이를 다음과 같이 부른다.

```text
CONTROL PATH PASS
```

하지만 아직:

```text
External ETCD 상태
실제 Container 실행
Pod Network
실제 DNS 질의
Ingress·VIP-B 사용자 경로
```

를 닫지 않았다.

---

# 11. BLOCKED 기준

다음 중 하나가 미해결이면 다음 Data Plane 검증의 정상 PASS 흐름으로 넘기지 않는다.

```text
대상 Context 불명확
VIP-A API 경로 비정상
전역 Cluster Identity·CIDR·Domain 불일치
예상 Node 누락
Node Identity·Role·Version 중대한 불일치
필수 Node NotReady 원인 미확정
Control Plane 핵심 Component 비정상
Critical Event 미해결
```

> BLOCKED라면 어디까지 성공했고 어느 증거에서 처음 달라졌는지 남깁니다.

---

# 12. 다음 ETCD·Runtime·CNI·DNS·Ingress 블록으로 넘길 것

```text
Cluster Name·Stage
current-context·API Server URL
VIP-A 검증 결과
실제 Kubernetes Version
실제 Pod CIDR·Service CIDR·Domain
Node별 Name·Role·IP·Version·Ready
Role별 Label·Taint 확인 결과
Control Plane Component 상태
Critical Event·미해결 항목
CONTROL PATH PASS / BLOCKED 판정
```

> 다음 블록에서는 같은 Context에서 **Application Pod가 실제로 실행되고 통신하고 이름을 찾으며 외부 요청을 받을 수 있는지** 검증합니다.

---

# 13. 마무리 — Control Path를 한 문장으로 다시 말한다

> 오전 Playbook 성공은 자동화 단계가 끝났다는 뜻이었습니다.
>
> 오후 첫 검증에서는 그 입력이 실제 신규 Member Kubernetes로 만들어졌는지 확인합니다. 먼저 Context와 VIP-A API를 고정하고, 8월 31일의 전역 설계값이 실제 Cluster에 반영됐는지 대조합니다.
>
> 그다음 예상 Node가 올바른 Name·IP·Role·Version으로 등록되고 Ready인지, Control Plane 핵심 Component가 정상인지 확인합니다.
>
> **결국 `kubectl get nodes`가 보기 좋다는 것이 아니라, 우리가 만들기로 한 신규 Member의 Control Path가 실제로 같은 Identity와 설계로 성립했다는 것이 이 블록의 성공입니다.**
