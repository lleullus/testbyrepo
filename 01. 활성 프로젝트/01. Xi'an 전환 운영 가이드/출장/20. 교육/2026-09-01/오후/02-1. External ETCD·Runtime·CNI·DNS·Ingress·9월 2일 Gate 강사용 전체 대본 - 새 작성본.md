# External ETCD·Runtime·CNI·DNS·Ingress·9월 2일 Gate 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 앞 블록에서 API·전역 설정·Node·Control Plane의 `CONTROL PATH PASS`를 확인했다. 이번 블록은 **실제 Pod가 생성되고 통신하며 내부와 외부 요청을 처리할 수 있는지 확인하는 과정**이다.
>
> Test Resource, Ingress와 Cleanup 명령은 승인된 9월 1일 Runbook을 따른다. 과거 NodePort와 다른 Cluster의 ETCD Endpoint를 현재값으로 사용하지 않고 Secret·Certificate Key·Credential 원문을 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
API와 Control Plane을 확인했다
→ 하지만 실제 Application 실행 경로는 별도다
→ External ETCD가 상태를 저장해야 한다
→ Runtime이 실제 Container를 만들어야 한다
→ CNI가 Pod IP와 Network를 만들어야 한다
→ Service와 Endpoint가 Pod를 연결해야 한다
→ DNS가 이름으로 Service를 찾게 해야 한다
→ Ingress와 Router가 외부 요청을 받아야 한다
→ VIP-B와 HTTPS를 확인한다
→ Test Resource를 정리한다
→ 이 범위가 정상이어야 Storage로 넘어간다
```

## 0-1. 오늘 전체 한 줄

> 이번 블록은 System Pod 수를 확인하는 시간이 아닙니다. **신규 Member가 상태를 저장하고, Container를 실행하며, Pod·Service·DNS·Ingress를 거쳐 실제 요청을 처리하는지 확인하는 시간**입니다.

---

# 1. 시작 — Control Path와 Application Path는 다르다

> 앞 블록에서 올바른 Context와 VIP-A API, Node와 Control Plane을 확인했습니다.
>
> **하지만 API에 요청할 수 있다고 실제 Pod가 생성되고 통신하며 외부 사용자에게 응답하는 것은 아닙니다.**
>
> 그래서 작은 Test Pod를 기준으로 `ETCD → Runtime → CNI → Service → DNS → Ingress → VIP-B` 순서로 확인합니다.
>
> 먼저 Kubernetes 상태를 저장하는 External ETCD를 봅니다.

---

# 2. External ETCD — Kubernetes Pod 목록만으로 판단하지 않는다

> Xi'an 신규 Member가 External ETCD를 사용하면 `kube-system`에 ETCD Pod가 보이지 않을 수 있습니다. ETCD가 별도 VM에서 실행되기 때문입니다.
>
> 그래서 API Server가 사용하는 Endpoint가 8월 31일에 확인한 신규 Member ETCD Node와 같은지 확인합니다.
>
> 다른 Host나 과거 Member IP가 섞이지 않았는지도 봅니다.
>
> **하지만 Endpoint 주소가 맞다고 ETCD Cluster가 건강한 것은 아닙니다.**
>
> 승인된 인증 방식으로 Member 목록과 각 Endpoint의 Health·Status를 확인합니다.
>
> 한 Endpoint만 정상인 결과를 전체 정상으로 확대하지 않습니다. Certificate와 Client Key 원문도 출력하지 않습니다.
>
> ETCD 완료 기준은 Process 존재가 아니라 API Server가 현재 Member의 상태를 실제로 저장하고 읽을 수 있는 상태입니다.

---

# 3. Container Runtime — Service 상태보다 실제 Container 실행을 본다

> Kubernetes는 Node의 Container Runtime에 Container 생성을 요청합니다.
>
> Runtime Service가 `active`이면 Process가 실행 중이라는 뜻입니다.
>
> **하지만 Kubernetes가 그 Runtime으로 Image를 가져오고 Container를 만들 수 있다는 뜻은 아닙니다.**
>
> 그래서 Runtime Version과 CRI Endpoint, Registry·CA 설정을 현재 Bundle 기준과 대조합니다.
>
> 그다음 승인 Test Image로 실제 Pod를 만들고 Scheduling, Image Pull, Container Created·Started 상태를 확인합니다.
>
> Image가 이미 Cache돼 있다면 이번 시험이 Registry Pull까지 증명하는지, Runtime 실행만 증명하는지 범위를 구분합니다.
>
> Container가 시작되면 Runtime 경로는 확인됐습니다. 그러나 Pod Network는 아직 별도입니다.

---

# 4. CNI — Calico Pod보다 Test Pod의 실제 IP와 통신을 본다

> CNI는 Pod에 IP와 통신 경로를 만듭니다. Xi'an에서는 현재 승인된 Calico 구성을 사용합니다.
>
> Calico Component가 Running이어도 Test Pod가 승인 Pod CIDR의 IP를 받고 통신한다는 뜻은 아닙니다.
>
> 그래서 Test Pod의 IP와 배치 Node를 확인하고, IP가 승인 Pod CIDR에 속하는지 봅니다.
>
> 필요한 범위에서 같은 Node와 다른 Node 사이의 허용 통신도 확인합니다.
>
> 한 Node의 성공을 전체 Node Network 성공으로 확대하지 않습니다.
>
> Pod IP가 없거나 CIDR이 다르면 DNS·Ingress로 넘어가지 않습니다.
>
> CNI 완료 기준은 Component 이름이 아니라 실제 Pod에 올바른 주소와 통신 경로가 생기는 것입니다.

---

# 5. Service와 Endpoint — 객체와 실제 Backend를 연결한다

> Pod IP는 바뀔 수 있으므로 다른 Application은 Service를 사용합니다.
>
> Service 객체가 존재해도 Ready Pod가 Backend로 연결됐다는 뜻은 아닙니다.
>
> 따라서 Selector와 Pod Label, Service Port·Target Port를 확인합니다.
>
> Endpoint 또는 EndpointSlice에 실제 Ready Pod IP가 있는지도 봅니다.
>
> 그다음 Service 주소로 요청해 실제 응답을 확인합니다.
>
> Service는 있는데 Endpoint가 없다면 Network보다 Selector·Label·Readiness·Target Port를 먼저 봅니다.
>
> **Service 존재, Endpoint 존재, 실제 요청 성공은 각각 다른 결과입니다.**

---

# 6. CoreDNS — Pod Running보다 실제 이름 질의를 확인한다

> Application은 Service IP보다 이름을 사용하는 경우가 많습니다. 이 이름 해석을 CoreDNS가 담당합니다.
>
> CoreDNS Pod가 Running이어도 Test Pod에서 현재 Cluster Domain으로 질의가 성공한다는 뜻은 아닙니다.
>
> 그래서 CoreDNS Service·Endpoint와 Cluster Domain을 확인합니다.
>
> Test Pod 안에서 Service의 짧은 이름과 필요한 전체 이름을 질의하고, 반환 주소가 앞에서 확인한 Service와 같은지 봅니다.
>
> 이어서 이름을 사용한 실제 요청도 확인합니다.
>
> DNS가 실패하면 바로 CoreDNS를 재시작하지 않습니다. Pod Network, DNS Service IP·Endpoint, Domain과 Query 오류를 순서대로 확인합니다.

---

# 7. Ingress와 Router — 내부 Service를 외부 요청 경로로 연결한다

> Cluster 내부 Service가 정상이어도 외부 사용자는 바로 접근할 수 없습니다.
>
> 그래서 Domain과 HTTP·HTTPS 요청을 Service로 전달하는 Ingress 경로가 필요합니다.
>
> Ingress Controller가 Running이어도 승인 Router Node에 배치되고 Rule과 Backend를 실제로 처리한다는 뜻은 아닙니다.
>
> 먼저 Controller의 실제 Node와 Router Role·Label·Taint를 확인합니다.
>
> 그다음 현재 Service 출력에서 승인 NodePort를 확인합니다. 과거 `30080`, `30443` 값을 기억으로 확정하지 않습니다.
>
> Test Ingress의 Host·Path·Class와 Backend Service·Endpoint를 연결한 뒤 Router NodePort에서 실제 응답을 확인합니다.
>
> Router NodePort가 성공하면 Cluster 내부 Ingress 경로는 확인됐습니다. **하지만 실제 외부 요청은 VIP-B를 통하므로 Load Balancer 경로가 남아 있습니다.**

---

# 8. VIP-B와 HTTPS — 외부 요청과 TLS를 따로 확인한다

> 승인 Domain 또는 VIP-B에서 요청하고 DNS가 현재 VIP-B를 반환하는지 확인합니다.
>
> Frontend Port가 현재 Router NodePort로 연결되고 Load Balancer Health와 실제 응답이 정상인지 봅니다.
>
> Router NodePort는 되는데 VIP-B가 실패하면 Kubernetes 전체를 재설치하지 않습니다. DNS, Frontend·Backend Mapping, Health Check와 Network를 확인합니다.
>
> 또한 HTTP 성공은 HTTPS 성공이 아닙니다.
>
> TLS 종료 위치, FQDN과 Certificate, Ingress TLS Secret과 443 Mapping을 별도로 확인합니다.
>
> `curl -k` 응답은 정상 Certificate Trust를 증명하지 않습니다.
>
> VIP-B 완료 기준은 Port 개방이 아니라 외부 요청이 올바른 Ingress·Service·Pod까지 도달하는 것입니다.

---

# 9. Test Resource는 실제 정리 결과까지 확인한다

> Test Pod·Service·Ingress로 기능을 확인한 뒤에는 승인된 순서로 정리합니다.
>
> 삭제 요청만 보내고 끝내지 않습니다. Resource와 Endpoint가 사라졌는지, 운영 Resource에 영향이 없는지 확인합니다.
>
> 삭제 대상이 불명확하거나 장애 조사에 필요하면 강제 삭제하지 않습니다.
>
> Cleanup까지 확인해야 통제된 기능 시험이 끝납니다.

---

# 10. 문제가 생기면 Application Path 순서대로 확인한다

> ETCD Endpoint가 unhealthy라면 CNI부터 바꾸지 않고 Endpoint·TLS·Network·Member 상태를 봅니다.
>
> Test Pod가 `ImagePullBackOff`라면 Pod Network보다 Image 주소·Registry·CA·Credential을 확인합니다.
>
> Pod에 IP가 없으면 CoreDNS를 재설정하지 않고 CNI와 Pod CIDR을 봅니다.
>
> Pod는 Running인데 DNS가 실패하면 Runtime은 통과했습니다. CoreDNS Service·Endpoint·Domain과 Query를 확인합니다.
>
> Router NodePort는 되는데 VIP-B가 실패하면 내부 경로는 통과했습니다. Load Balancer 경계를 봅니다.
>
> HTTP는 되는데 HTTPS만 실패하면 TLS와 Certificate 경로를 확인합니다.
>
> 확인 순서는 `ETCD → Runtime → CNI → Service·Endpoint → DNS → Ingress·Router → VIP-B·HTTPS`입니다.

---

# 11. 9월 2일 Storage 진입 Gate를 판정한다

> `KUBERNETES BASE PASS`는 앞 블록의 `CONTROL PATH PASS`가 유지되는 것에서 시작합니다.
>
> External ETCD가 건강하고 Runtime이 실제 Test Container를 실행해야 합니다.
>
> CNI가 Test Pod에 승인 CIDR의 IP를 주고, Service·Endpoint와 DNS가 실제로 동작해야 합니다.
>
> Ingress Controller가 승인 Router에 배치되고, 다음 단계에 필요한 Router·VIP-B 경로가 정상이어야 합니다.
>
> 미해결 Critical Event와 Test Resource 잔여도 없어야 합니다.
>
> 반면 ETCD·Runtime·Pod Network·DNS·Ingress 핵심 기능이 실패하거나 Storage가 사용할 Node Network가 미확정이면 `BLOCKED`입니다.

---

# 12. Storage에는 실제 Kubernetes 기능 결과를 넘긴다

> 다음 날에는 Cluster·Context와 `KUBERNETES BASE PASS / BLOCKED` 결과를 넘깁니다.
>
> ETCD Member·Health, Runtime과 Test Pod 실행 결과를 전달합니다.
>
> Pod CIDR·실제 Pod IP·Network, Service·Endpoint·DNS 질의, Ingress Controller 배치·NodePort·VIP-B 결과와 Cleanup 상태도 이어갑니다.
>
> Secret과 Key 원문은 제외합니다.
>
> Storage는 이 Kubernetes 기반 위에서 PVC 요청을 실제 Volume과 Node Mount로 연결합니다.

---

# 13. 마무리

> API와 Control Plane이 정상이어도 실제 Application 실행 경로는 별도였습니다.
>
> 그래서 External ETCD Health와 Runtime의 Container 실행을 확인했습니다. 그다음 CNI의 Pod IP, Service·Endpoint와 DNS 질의를 확인했습니다.
>
> 마지막으로 Ingress·Router·VIP-B와 HTTPS를 확인하고 Test Resource를 정리했습니다.
>
> **결국 KUBERNETES BASE PASS는 System Pod가 많이 Running인 상태가 아니라, 현재 신규 Member가 상태를 저장하고 Container를 실행하며 내부와 외부 요청을 실제로 처리할 수 있는 상태입니다.**

---

# 14. 마지막 확인 질문

1. Control Path가 정상이어도 Application Path를 별도로 확인해야 하는 이유는 무엇인가?
2. External ETCD를 Kubernetes Pod 목록만으로 판단하면 안 되는 이유는 무엇인가?
3. Runtime Service Running과 실제 Test Container 실행은 무엇이 다른가?
4. Calico Component Running 뒤에도 Test Pod IP를 확인해야 하는 이유는 무엇인가?
5. Service 존재, Endpoint 존재, 실제 요청 성공은 각각 무엇을 증명하는가?
6. CoreDNS Pod Running과 실제 DNS 질의 성공은 왜 다른가?
7. Ingress Controller Running과 Router NodePort 응답은 무엇이 다른가?
8. Router NodePort를 VIP-B보다 먼저 확인하는 이유는 무엇인가?
9. HTTP 성공이 HTTPS와 정상 Trust까지 증명하지 못하는 이유는 무엇인가?
10. Cleanup 결과까지 확인해야 하는 이유는 무엇인가?
11. 어떤 상태가 남으면 Storage 진입을 BLOCKED해야 하는가?
