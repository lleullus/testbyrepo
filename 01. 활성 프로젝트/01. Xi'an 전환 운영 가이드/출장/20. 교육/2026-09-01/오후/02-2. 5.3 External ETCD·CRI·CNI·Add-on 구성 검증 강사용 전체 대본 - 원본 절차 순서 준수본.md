# 5.3 External ETCD·CRI/containerd·CNI/Calico·Ingress·Metrics·Dashboard 상세 검증 강사용 전체 대본 - 원본 절차 순서 준수본

> [!important] 사용 방법
> 이 대본은 원본 `3. Ansible Playbook 배포 및 클러스터 설정`의 **`3-4-3 → 3-4-4 → 3-4-5 → 3-4-6` 순서와 각 단계 내부의 실제 실행 순서를 그대로 따라가는 강사용 대본**이다.
>
> 앞 블록에서는 원본 `3-4-1~3-4-2`를 따라 전역값, Node, 주요 Component 배치와 각 Node의 OS 상태를 확인했다. 이번 블록은 그 다음 원본 순서 그대로 **External ETCD → CRI/containerd → CNI/Calico → Ingress → Metrics → Dashboard**를 확인한다.
>
> 기술 설명은 **왜 이 명령을 실행하는지, 무엇까지 증명하는지, 실패하면 어디부터 볼지**를 이해시키는 데 사용한다. 원본에 없는 새로운 Test나 진단 명령을 원본 Procedure 사이에 끼워 넣지 않는다.
>
> 정확한 ETCD Endpoint, Certificate 경로, Registry, Calico CIDR, Ingress Domain/NodePort, Dashboard 인증 방식은 현재 신규 Member와 현재 승인 Bundle 기준을 사용한다. 원본의 `10.166.*`, `khdks*`, `dcr.cloud.*`, 과거 `30080/30443`, 과거 Dashboard Token 방식은 현재값으로 가정하지 않는다.
>
> ETCD Private Key, Registry Password, kubeconfig, Dashboard Token 원문은 화면과 증적에 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

> **이 문서의 순서는 딱 하나입니다. `External ETCD → CRI/containerd → CNI/Calico → Ingress → Metrics → Dashboard`입니다.** 설명을 위해 다른 Component를 중간에 끼우거나, 별도의 A/B 분류로 다시 묶지 않습니다.
>
> 검증 방식은 Component마다 다르지만 **순서는 바뀌지 않습니다.** ETCD는 ETCD Node에서 `etcdctl`, Runtime은 Kubernetes Node 내부에서 `containerd/crictl/config dump`, Calico는 Kubernetes Resource, Ingress·Metrics·Dashboard는 실제 기능 결과를 봅니다.

```text
3-4-3 External ETCD
→ ETCD Node / etcdctl
→ ETCD Cluster 자체 상태

3-4-4 CRI / containerd
→ Kubernetes Node 내부
→ Runtime 실제 설정

3-4-5 CNI / Calico
→ kubectl
→ DaemonSet / ConfigMap / IPPool

3-4-6 Ingress
→ Controller / Service / Test Ingress / Browser

3-4-6 Metrics
→ metrics-server / kubectl top nodes

3-4-6 Dashboard
→ Ingress / Browser / ServiceAccount / Token / Login
```

> 앞의 ETCD·Runtime·CNI는 주로 **설계대로 구성됐는지** 확인하고, Ingress·Metrics·Dashboard는 **실제로 기능하는지**까지 확인합니다.

## 0-1. 오늘 전체 한 줄

> 이번 블록은 **External ETCD → CRI/containerd → CNI/Calico → Ingress → Metrics → Dashboard를 원본에 적힌 순서 그대로 검증해 5.3을 끝내는 시간**입니다.

# 2. 원본 3-4-3 — External ETCD 검증

> **이 단계의 핵심은 `External ETCD는 Kubernetes 안에서 보는 것이 아니라 ETCD에게 직접 물어서 Cluster 상태를 검증한다`입니다.**
>
> Xi'an 구조에서 ETCD가 External VM으로 구성되면 `kube-system`의 ETCD Pod 목록만 보고 Cluster 상태를 판단할 수 없습니다. 먼저 Kubernetes가 어느 External ETCD를 바라보도록 구성됐는지 확인하고, 그다음 ETCD Node에 들어가 `etcdctl`로 ETCD Cluster 자체를 직접 조회합니다.
>
> 검증 질문은 네 개입니다.
>
> ```text
> kubeadm-config
> → Kubernetes가 어느 ETCD를 바라보는가?
>
> member list
> → 누가 ETCD Cluster 구성원인가?
>
> endpoint status
> → 각 Member가 실제 정상 상태인가?
>
> Certificate expiration
> → 그 통신에 필요한 인증서가 현재 유효한가?
> ```

## 2.1. 원본 첫 번째 — External ETCD configuration을 확인한다

```bash
kubectl -n kube-system get cm kubeadm-config -o yaml | grep -A8 etcd:
```

> 이 명령은 **Kubernetes API Server가 어느 External ETCD를 사용하도록 구성됐는지** 확인하는 단계입니다. 아직 ETCD 자체 상태를 보는 것이 아니라, Kubernetes 쪽 연결 설정을 먼저 확인합니다.

```yaml
etcd:
  external:
    caFile: <CA 경로>
    certFile: <Client Certificate 경로>
    endpoints:
      - https://<ETCD-1>:2379
      - https://<ETCD-2>:2379
      - https://<ETCD-3>:2379
    keyFile: <Client Key 경로>
```

> `endpoints`가 현재 신규 Member의 ETCD Node와 일치하는지 보고, `caFile`, `certFile`, `keyFile`이 현재 승인된 ETCD TLS 경로를 가리키는지 확인합니다.
>
> 여기까지 정상이라는 것은 **Kubernetes가 올바른 External ETCD를 바라보도록 구성됐다**는 뜻입니다. 실제 ETCD Cluster가 건강한지는 아직 확인하지 않았습니다.

## 2.2. 원본 두 번째 — ETCD Node에 접속한다

```bash
ssh <신규 Member ETCD 1>
```

> External ETCD는 Kubernetes Resource가 아니므로 이제 검증 위치를 Bastion/Kubernetes API에서 **ETCD Node 자체로 옮깁니다.**
>
> 이 단계의 목적은 단순한 SSH 접속 확인이 아니라, 다음 원본 명령부터 ETCD 자체 CLI와 인증 자료를 **ETCD가 실제 동작하는 Host에서 직접 확인할 준비를 하는 것**입니다.

## 2.3. 원본 세 번째 — `etcdctl` Version을 확인한다

```bash
etcdctl version
```

> `etcdctl`은 ETCD Cluster를 직접 조회하는 Client입니다. 여기서는 먼저 Binary가 설치돼 있고 현재 ETCD와 사용할 수 있는 Version인지 확인합니다.
>
> **Version 출력 성공은 ETCD Cluster 정상 증명이 아닙니다.** ETCD를 직접 조회할 도구가 준비됐다는 것까지만 증명합니다.

## 2.4. 원본 네 번째 — Certificate와 Key File 위치를 확인한다

```bash
sudo ls -al /etc/ssl/etcd/ssl/
```

> 다음 `etcdctl` 조회는 TLS 인증이 필요하므로, 원본은 먼저 실제 Certificate와 Key가 어느 경로에 있는지 확인합니다.
>
> 대표 역할은 다음처럼 구분합니다.

```text
CA Certificate
→ ETCD Certificate를 신뢰할 기준

Admin Client Certificate / Key
→ etcdctl로 ETCD Cluster를 관리·조회할 때 사용할 Client 인증 자료

ETCD Member Certificate / Key
→ ETCD Member 간 통신에 사용하는 인증 자료

Kubernetes Node/Client용 Certificate / Key
→ Kubernetes 구성요소와 ETCD 연결에 사용하는 인증 자료
```

> 현재 신규 Member Hostname 기준의 파일이 존재하는지, Owner/Mode가 적절한지 확인합니다. **Private Key 내용 자체는 출력하지 않습니다.**

## 2.5. 원본 다섯 번째 — ETCD Endpoint·Certificate·Key Alias를 만든다

```bash
alias etcd3ctl="ETCDCTL_API=3 sudo /usr/local/bin/etcdctl --endpoints=https://<ETCD-1>:2379,https://<ETCD-2>:2379,https://<ETCD-3>:2379 --cacert=<현재 CA 경로> --cert=<현재 Admin Client Cert 경로> --key=<현재 Admin Client Key 경로>"
```

> 여기서는 이후 ETCD 조회가 **어느 Cluster를, 어떤 CA와 Client Certificate/Key로 조회할지** 한 번에 고정합니다.
>
> 즉 이 Alias는 편의용 단축어이기도 하지만, 더 중요하게는 **검증 대상 ETCD Cluster와 인증 경로를 고정하는 조회 기준**입니다. 다른 Cluster Endpoint나 다른 Host용 Certificate가 섞이지 않았는지 확인합니다.

## 2.6. 원본 여섯 번째 — ETCD Member List를 조회한다

```bash
etcd3ctl -w table member list
```

> 이제 처음으로 **ETCD Cluster 자체에게 누가 구성원인지 직접 묻습니다.**
>
> 신규 Member 설계가 3-Node ETCD라면 예상한 세 Member가 모두 존재하고 `started` 상태인지, `PEER ADDRS`, `CLIENT ADDRS`가 현재 ETCD Node 목록과 일치하는지 확인합니다. Learner 구성이 아니라면 `IS LEARNER=false`인지도 봅니다.
>
> 여기서 확인되는 것은 **Cluster 구성원 목록**입니다. Member가 보인다고 각 Endpoint의 실제 상태와 Leader/Raft 상태까지 정상이라는 뜻은 아닙니다.

## 2.7. 원본 일곱 번째 — ETCD Endpoint Status를 조회한다

```bash
etcd3ctl -w table endpoint status
```

> 이번에는 **각 ETCD Endpoint가 실제로 어떤 상태로 동작하는지** 확인합니다.

```text
ENDPOINT
ID
VERSION
DB SIZE
IS LEADER
IS LEARNER
RAFT TERM
RAFT INDEX
RAFT APPLIED INDEX
ERRORS
```

> ETCD Cluster에는 일반적으로 Leader 하나와 Follower가 존재합니다. 따라서 모든 Member가 Leader여야 하는 것이 아니라, 하나의 Leader와 나머지 정상 Member가 같은 Cluster/Raft 상태로 동작하는지를 봅니다.
>
> `RAFT INDEX`, `RAFT APPLIED INDEX`, `ERRORS`를 통해 특정 Member가 뒤처지거나 오류가 있는지도 확인합니다.
>
> 여기까지 정상이어야 **ETCD Member가 존재한다는 수준을 넘어 실제 Cluster 상태가 정상**이라고 말할 수 있습니다.

## 2.8. 원본 여덟 번째 — ETCD Certificate expiration을 확인한다

```bash
sudo openssl x509 -startdate -enddate -noout -in <현재 ETCD CA Certificate>
sudo openssl x509 -startdate -enddate -noout -in <현재 ETCD Admin Client Certificate>
```

> 마지막으로 ETCD 통신에 사용하는 Certificate의 `notBefore`, `notAfter`를 확인합니다.
>
> 원본 과거 출력의 100년 값을 현재 환경의 절대 정답으로 사용하지 않고, **현재 Kubespray/ETCD Certificate 정책과 실제 생성 결과가 유효한지** 확인합니다.
>
> **3-4-3 PASS는 `Kubernetes가 올바른 External ETCD를 바라보고 있고, ETCD 자체 Cluster도 Member·Endpoint·Certificate 기준으로 정상이다`라는 뜻입니다.**
>
> 여기까지가 원본 `3-4-3`입니다.

# 3. 원본 3-4-4 — CRI 및 containerd 설정 검증

> **이 단계의 핵심은 `각 Kubernetes Node 안에 만들어진 Runtime 설정이 Kubespray 설계대로 생성됐는지 직접 확인한다`입니다.**
>
> Kubernetes는 Pod를 직접 Container Process로 만드는 것이 아니라 kubelet이 CRI를 통해 Runtime에 Container 생성을 요청합니다. Xi'an DKS에서는 containerd를 사용하므로 **Node 내부에서 `containerd`, `crictl`, `containerd config dump`를 직접 확인**합니다.
>
> ETCD처럼 별도 Cluster CLI로 보는 것도 아니고, 뒤의 Calico처럼 Kubernetes Resource만 보는 것도 아닙니다. Runtime은 Node Local Component이므로 실제 Node의 설정이 Source of Truth입니다.
>
> ```text
> Kubernetes Node 접속
> → containerd Version
> → crictl Version
> → containerd config dump
> → 현재 Kubespray 입력/Bundle 기준과 비교
> ```
>
> **여기서 핵심은 SSH 방식이 아니라 `config dump` 비교입니다.** 원본은 대표 Kubernetes Node에 접속해 상세 설정을 확인합니다. 전체 Node 정합성을 확인할 때 같은 명령을 Node별로 반복하거나 SSH Loop로 실행할 수 있지만, Loop 자체가 검증 기준은 아닙니다. **각 Node의 실제 Runtime 설정이 같은 설계 기준과 일치하는지가 판정 본체**입니다.
>
> 직접 입력한 값은 `8/31 Filesystem 설계`와 오전 `3-1`의 `offline.yml`을 기준으로 대조합니다. 직접 지정하지 않은 Runtime·Cgroup·CNI·Snapshotter 값은 **현재 실제로 사용한 Kubespray Bundle의 변수·Template·Default**를 기준으로 확인합니다. 원본의 과거 `containerd config dump` 출력은 출력 형태를 읽는 참고자료이지 현재 신규 Member의 정답표가 아닙니다.

## 3.1. 원본 첫 번째 — Kubernetes Node에 접속한다

```bash
ssh <신규 Member Kubernetes Node>
```

> 원본은 먼저 Runtime을 직접 확인할 Kubernetes Node로 이동합니다. 이 SSH 행위 자체를 다음 Version 확인과 합치지 않습니다.

## 3.2. 원본 두 번째 — containerd Version을 확인한다

```bash
sudo /usr/local/bin/containerd --version
```

> 과거 원본의 Version 문자열을 정답으로 사용하지 않고, **현재 실행한 Kubespray Bundle이 사용하는 containerd Version**과 대조합니다.
>
> Version 문자열 하나만 맞는다고 Registry나 CNI 설정까지 정상이라는 뜻은 아닙니다.

## 3.3. 원본 세 번째 — crictl Version을 확인한다

```bash
sudo /usr/local/bin/crictl --version
```

> `crictl`은 CRI Runtime 상태를 직접 확인하는 Client입니다.
>
> 마찬가지로 과거 원본 출력이 아니라 **현재 Kubernetes/CRI Bundle의 crictl Version 기준**과 대조합니다.

## 3.4. 원본 네 번째 — containerd Configuration을 상세 확인한다

```bash
sudo /usr/local/bin/containerd config dump
```

> [!warning] Registry Credential 화면 노출 주의
> 원본 `config dump` 예시에는 Registry `username`, `password` 영역이 포함됩니다. 실제 교육 화면에서 전체 출력을 무심코 캡처·녹화하면 Credential이 노출될 수 있습니다. Registry Auth 영역은 비공개 화면에서 확인하거나 승인된 방식으로 마스킹하고, 증적에는 Registry Host·TLS·Mirror 등 필요한 설정 결과만 남깁니다.
>
> 여기서 먼저 **무엇과 비교할지**를 고정합니다.
>
> | 실제 확인값 | 비교 기준 |
> |---|---|
> | containerd / crictl Version | 현재 사용 Kubespray Bundle의 Version 기준 |
> | `root` / `state` | 8/31 Filesystem 설계 + 현재 Bundle Runtime 설정 |
> | CRI Plugin / `runc` / Cgroup | 현재 Kubespray containerd 변수·Template·Default |
> | CNI `bin_dir` / `conf_dir` | 현재 Kubespray CNI 설정 |
> | Registry Host / Mirror | 오전 `3-1`에서 적용한 현재 `offline.yml` |
> | Registry TLS / CA | 8/31 CA Trust + 현재 승인 Registry Certificate 정책 |
> | Snapshotter | 현재 Kubespray/containerd 설정 |
>
> 원본 출력은 매우 길기 때문에 대본에서는 전체 TOML을 암기하지 않습니다. **위 비교 기준이 있는 항목을 중심으로 읽습니다.**

```text
containerd root/state 경로
CRI plugin 활성 상태
CNI bin_dir / conf_dir
Runtime = runc
systemdCgroup
Snapshotter
Registry configuration
Registry authentication entry
TLS policy
Registry mirror endpoint
```

> 먼저 `root`와 `state`를 봅니다. 특히 `root`는 **8/31에 확정한 Filesystem 설계**와 비교합니다. 현재 Kubernetes Node가 `/var/lib/containerd`를 사용하도록 준비됐다면 실제 containerd Data 경로도 그 설계와 일치해야 합니다. `state`는 현재 Bundle의 Runtime 설정과 대조합니다.
>
> 그다음 `io.containerd.grpc.v1.cri` Plugin과 CNI `bin_dir`, `conf_dir`를 봅니다. 이 값들은 임의의 과거 출력과 비교하는 것이 아니라 **현재 사용 Kubespray Bundle이 배포하도록 정의한 CRI/CNI 경로**와 맞는지 확인합니다. kubelet은 CRI를 통해 containerd와 통신하고, CNI Directory에는 Calico 같은 Network Plugin의 Binary와 설정이 위치합니다.
>
> 이어서 실제 Runtime과 Cgroup 설정을 **현재 Kubespray Bundle의 containerd 설정**과 비교합니다. `runc`, Runtime Type, Cgroup 설정이 현재 Bundle이 의도한 값과 다르면 Node가 Ready여도 Runtime 구성 정합성이 확인된 것이 아닙니다.
>
> Snapshotter도 현재 Bundle의 containerd 설정과 비교합니다. 여기서 보이는 Snapshotter는 Container Image Layer와 Writable Layer를 관리하는 containerd 내부 기능이며, 9/2 Storage에서 다루는 Kubernetes Volume Snapshotter와는 역할이 다릅니다.
>
> 마지막으로 Offline 구축에서 중요한 Registry 설정을 봅니다. 여기의 정답지는 **오전 `3-1`에서 실제 적용한 `offline.yml`의 현재 승인 Registry**와 **8/31 CA Trust / 현재 Registry Certificate 정책**입니다. `config dump`의 Registry Host·Mirror·TLS가 그 입력과 다르면 Kubespray 입력이 실제 Runtime까지 기대대로 반영되지 않은 것입니다. 원본 예시의 `dcr.cloud.*`, Username, `insecure_skip_verify=true`는 현재값으로 가정하지 않습니다.
>
> Password나 Auth Token은 화면에 노출하지 않습니다. 필요한 것은 Credential 원문이 아니라 **현재 승인 Registry Entry가 존재하고 올바른 Host·TLS·Mirror를 가리키는지** 확인하는 것입니다.
>
> **3-4-4 PASS는 `각 Node의 Runtime 설정이 Kubespray 입력과 Bundle 기준에 맞게 생성됐다`는 뜻입니다.** Filesystem·CRI/Runtime·CNI Path·Registry의 핵심 설정이 기준과 다르면 단순히 `containerd` Service가 실행 중이라는 이유로 통과시키지 않습니다.
>
> 여기까지가 원본 `3-4-4`가 확인하는 범위입니다. 실제 Test Workload가 Container로 실행되는지는 뒤 원본 `3-4-6`의 Test Ingress 배포에서 별도로 증명합니다.

# 4. 원본 3-4-5 — CNI 및 Calico 설정 검증

> **이 단계의 핵심은 `Pod Network 설계가 Kubernetes Resource에 실제로 구현됐는지 확인한다`입니다.**
>
> 오후 1에서는 `calico-node`, `calico-kube-controllers`, `calico-typha` Pod가 기대 Node에 배치되고 Running인지 확인했습니다. 이제는 존재 여부가 아니라 **DaemonSet·ConfigMap·IPPool에 실제 Network 설계가 어떻게 반영됐는지** 봅니다.
>
> containerd는 Node 내부 Runtime 설정을 직접 봤지만, Calico의 실행 방식과 Network Pool은 Kubernetes Resource로 표현됩니다. 따라서 이 단계의 주 검증 도구는 `kubectl`입니다.
>
> ```text
> calico-node DaemonSet
> → 필요한 Node에 CNI Agent가 모두 배치됐는가?
>
> calico-config ConfigMap
> → 어떤 Network Backend로 동작하는가?
>
> Calico IPPool
> → 실제 Pod CIDR과 Encapsulation/NAT 정책이 설계와 맞는가?
> ```
>
> Pod CIDR은 오전 `dks_vars.yml`의 `kube_pods_subnet`을 기준으로 합니다. Backend·IPIP/VXLAN·IP 자동 탐지 같은 Calico 동작값은 **현재 Kubespray Inventory에서 명시적으로 Override한 값이 있으면 그 값을 우선**하고, 별도 Override가 없다면 **현재 실제 사용 Bundle의 Calico Default/Template**을 기준으로 확인합니다. 원본의 과거 Calico 출력은 현재 신규 Member의 정답표가 아닙니다.

## 4.1. `calico-node` DaemonSet Configuration 확인

```bash
kubectl describe ds calico-node -n kube-system
```

> 먼저 DaemonSet의 배치 상태를 다시 확인합니다.

```text
Desired Number of Nodes Scheduled
Current Number of Nodes Scheduled
Up-to-date Pods
Available Pods
Misscheduled
Pods Status
```

> 여기서는 **현재 Kubernetes Node 구성과 실제 `calico-node` Coverage가 일치하는지** 판정합니다. 필요한 Node가 빠져 있거나 Misscheduled가 발생하면 Network 설정값을 보기 전에 배치 상태부터 정상으로 보지 않습니다.
>
> 그다음 Pod Template에서 중요한 설정을 봅니다.

```text
CNI binary/config mount
CALICO_NETWORKING_BACKEND
Typha service name
FELIX VXLAN 관련 값
CALICO_IPV4POOL_IPIP
FELIX_IPV6SUPPORT
IP_AUTODETECTION_METHOD
NODENAME
Readiness/Liveness
```

> 모든 Environment Variable을 외우는 것이 목적은 아닙니다. 확인 대상을 세 묶음으로 읽습니다.
>
> - CNI Mount는 현재 Kubespray가 정의한 CNI Binary/Config 경로와 실제 DaemonSet 연결이 맞는지 봅니다.
> - Backend·VXLAN/IPIP·Typha 값은 현재 Kubespray의 Calico Override 또는 Bundle 기준과 대조합니다.
> - `IP_AUTODETECTION_METHOD`를 별도로 지정했다면 현재 Kubespray 입력과 같은지 확인하고, 별도 지정이 없다면 현재 Bundle이 생성한 기본 동작과 일치하는지 확인합니다.
>
> 즉 이 단계는 Environment Variable을 구경하는 것이 아니라 **현재 Kubespray가 의도한 Calico 실행 방식이 실제 `calico-node` Pod Template에 반영됐는지** 판정하는 단계입니다.

## 4.2. Calico Backend Network 확인

> `calico-node`가 전체 Node에서 Running이어도 실제로 어떤 Network Backend를 사용하도록 구성됐는지는 아직 확인되지 않았습니다. 그래서 원본은 다음으로 `calico-config`를 직접 확인합니다.

```bash
kubectl get cm calico-config -n kube-system -o yaml
```

> 원본은 다음 핵심값을 확인합니다.

```text
calico_backend
cluster_type
typha_service_name
```

> 여기서 `calico_backend`의 정답지는 과거 원본의 `vxlan` 문자열이 아닙니다. **현재 Kubespray Inventory에서 지정한 Calico Backend 값**을 먼저 보고, 별도 Override가 없다면 현재 사용 Bundle의 기본값을 기준으로 실제 `calico-config`와 대조합니다.
>
> `cluster_type`은 현재 Kubespray가 생성한 Cluster 구성과 맞는지 확인합니다.
>
> Typha를 사용하는 현재 구성이라면 `typha_service_name`도 실제 배포된 Service와 맞는지 확인합니다.

## 4.3. Calico IPPool과 Encapsulation Mode 확인

> Backend가 맞는다고 실제 Pod Address Pool과 Encapsulation 정책까지 확인된 것은 아닙니다. 그래서 원본은 마지막으로 Calico IPPool을 확인합니다.

```bash
kubectl get ippools.crd.projectcalico.org -o yaml
```

> 여기서도 먼저 비교 기준을 고정합니다.
>
> | 실제 IPPool 값 | 비교 기준 |
> |---|---|
> | `cidr` | 오전 `dks_vars.yml`의 `kube_pods_subnet`, 또는 현재 Bundle에서 별도로 지정한 Calico Pool CIDR |
> | `ipipMode` | 현재 Kubespray Calico IPIP 설정 |
> | `vxlanMode` | 현재 Kubespray Calico VXLAN 설정 |
> | `blockSize` | 현재 Kubespray Calico IPPool 설정 |
> | `natOutgoing` | 현재 Kubespray Calico IPPool/NAT 설정 |
> | `nodeSelector` | 현재 Kubespray가 생성하도록 정의한 IPPool 대상 Node 정책 |
>
> `cidr`는 특히 중요합니다. 오전에 입력한 `kube_pods_subnet` 또는 현재 Bundle에서 명시적으로 Override한 Calico Pool CIDR과 실제 IPPool이 같은 Network를 가리켜야 합니다.
>
> **원본 참조 출력의 IPPool CIDR은 같은 원본 앞쪽 `kube_pods_subnet` 값과 서로 일치하지 않습니다. 따라서 원본의 과거 CIDR을 현재 정상값으로 사용하지 않고, 이번 구축에서 실제 입력한 Pod CIDR과 실제 IPPool을 직접 대조합니다.**
>
> 입력한 Pod CIDR과 실제 Calico IPPool CIDR이 다르면 Node Ready나 Calico Pod Running만으로 정상이라고 할 수 없습니다.
>
> `blockSize`, `ipipMode`, `vxlanMode`, `natOutgoing`, `nodeSelector`도 값의 의미만 설명하고 끝내지 않고 **현재 Kubespray의 Override/Bundle 기준과 실제 IPPool이 같은지** 확인합니다.
>
> **3-4-5 PASS는 `Pod Network Resource가 이번 구축의 CIDR·Backend·Encapsulation·NAT 설계대로 구현됐다`는 뜻입니다.** 특히 Pod CIDR이나 Encapsulation이 기대값과 다르면 Calico Pod가 Running이어도 정상으로 판정하지 않고, 다음 원본 단계인 Ingress 기능 검증으로 넘어가기 전에 원인을 확인합니다.
>
> 이 단계가 끝나면 **Calico Component가 존재하는지**를 넘어서 **실제 Pod Network가 이번 구축 설계대로 구성됐는지** 판정한 것입니다.
>
> 여기까지가 원본 `3-4-5`입니다. 오후 1에서 Calico Pod의 배치와 기본 상태를 확인했고, 지금은 DaemonSet·Backend·IPPool을 통해 실제 Network 설정을 확인했습니다.

# 5. 원본 3-4-6 첫 번째 — Ingress 기능 검증

> **여기서부터는 `설정이 맞는가`를 넘어서 `실제 기능이 되는가`까지 봅니다. 첫 번째 대상은 Ingress입니다.**
>
> 원본은 Ingress Controller 설정과 Service를 확인한 뒤 Test Deployment·Service·Ingress를 실제로 배포하고 Browser 응답까지 확인합니다. 이 Ingress 절차를 끝낸 뒤에야 다음 원본 대상인 Metrics로 넘어갑니다.

## 5.1. Ingress Controller `--enable-ssl-passthrough` Argument 확인

```bash
kubectl describe deploy -n ingress-nginx ingress-nginx-controller | grep -A9 Args:
```

> 현재 DKS 기준에서 `--enable-ssl-passthrough`가 필요한 설정이면 실제 Controller Argument에 반영됐는지 확인합니다.
>
> Pod가 Running이어도 필요한 Argument가 빠져 있으면 특정 TLS Passthrough 기능은 기대대로 동작하지 않을 수 있습니다.

> 그다음 Ingress Controller Service에서 80/443 Port와 현재 NodePort를 확인합니다.

```bash
kubectl get svc -n ingress-nginx ingress-nginx-controller
```

> Service Type과 80/443 Port의 현재 NodePort를 확인합니다.
>
> 원본 과거 `30080`, `30443`을 기억으로 사용하지 않고 **현재 Service 출력에 보이는 실제 NodePort**를 사용합니다.
>
> 여기서는 원본 목적대로 Ingress Controller Service의 현재 NodePort가 어떤 값으로 구성됐는지 확인합니다. 외부 LB 경로에 대한 추가 진단이 필요하면 뒤 Troubleshooting에서 별도로 확인합니다.

## 5.2. 원본 Test Ingress로 실제 기능을 확인한다

> **Ingress 기능 검증의 핵심은 `Controller가 Running인가?`가 아니라 `실제 외부 요청이 Ingress → Service → Test Pod까지 도달하는가?`입니다.**
>
> 원본은 먼저 Test Manifest 파일을 직접 작성하고, 바로 다시 읽어서 실제 적용할 Deployment·Service·Ingress 내용을 확인합니다. 이 두 행위가 원본에 있으므로 생략하지 않습니다.

```bash
vi ingress-test.yaml
```

```bash
cat ingress-test.yaml
```

> `vi`에서는 현재 승인 Test Image·ImagePullSecret·Test Domain을 반영하고, `cat`에서는 저장된 최종 Manifest가 그 값으로 실제 작성됐는지 다시 확인합니다. 파일을 편집했다는 사실과 저장된 내용이 맞다는 것은 별도 확인입니다.
>
> 원본 Manifest 구조는 다음과 같습니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ing-test
  labels:
    app: ing-test
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ing-test
  template:
    metadata:
      labels:
        app: ing-test
    spec:
      containers:
        - image: <현재 승인 Test Image>
          name: ing-test
      imagePullSecrets:
        - name: <현재 승인 ImagePullSecret>
---
apiVersion: v1
kind: Service
metadata:
  labels:
    app: ing-test
  name: ing-test-svc
spec:
  internalTrafficPolicy: Cluster
  ipFamilies:
    - IPv4
  ipFamilyPolicy: SingleStack
  ports:
    - port: 80
      protocol: TCP
      targetPort: 80
  selector:
    app: ing-test
  sessionAffinity: None
  type: ClusterIP
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    kubernetes.io/ingress.class: nginx
  labels:
    app: ing-test
  name: ing-test-ingress
spec:
  rules:
    - host: <현재 승인 Test Domain>
      http:
        paths:
          - backend:
              service:
                name: ing-test-svc
                port:
                  number: 80
            path: /
            pathType: Prefix
```

> 위 구조는 원본 Manifest의 필드를 보존한 형태입니다. Test Image, ImagePullSecret, Domain은 현재 신규 Member 승인값으로 치환합니다.
>
> [!note] 현재 Kubernetes Version 적용 차이
> 현재 Version/Ingress Controller 기준에서 `spec.ingressClassName: nginx` 사용이 표준이라면, 먼저 원본의 `kubernetes.io/ingress.class` Annotation 방식을 확인한 뒤 **현재 Version에 필요한 변경점을 별도 적용사항으로 기록하고 적용**합니다.

> Manifest를 현재값으로 검수했으면 실제로 적용합니다.

```bash
kubectl apply -f ingress-test.yaml
```

> 여기서 `created`가 출력됐다고 기능 시험이 끝난 것은 아닙니다.
>
> Deployment가 Pod를 만들고, Service가 그 Pod를 Backend로 선택하고, Ingress Controller가 Rule을 읽어야 실제 요청 경로가 만들어집니다.

> 적용이 끝나면 Deployment, Pod, Service 상태를 이어서 확인합니다.

```bash
kubectl get all
```

> 다음을 확인합니다.

```text
Pod READY/STATUS
Deployment READY
Service ClusterIP/Port
ReplicaSet 상태
```

> `kubectl get all`에서는 Test Pod가 `Running/Ready`인지, Deployment가 Available인지, Service가 생성됐는지 확인합니다. Service가 존재한다고 실제 Backend까지 자동으로 증명되는 것은 아니므로, 이 결과를 확인한 뒤 원본 다음 단계인 Ingress 조회로 넘어갑니다.
>
> 그다음 원본 순서대로 Ingress Resource의 Host와 Address를 확인합니다.

```bash
kubectl get ing
```

> 원본은 특정 이름을 바로 조회하지 않고 현재 Namespace의 Ingress 목록을 먼저 봅니다. 여기서 `ing-test-ingress`의 Test Domain이 표시되고, Ingress Address가 현재 신규 Member에서 기대하는 Router Node 집합과 맞는지 확인합니다. 다른 Role Node가 Address로 나타난다면 Router 배치와 Ingress Controller 상태를 다시 봅니다.
>
> 이어서 원본은 Ingress Rule과 Default Backend를 상세히 확인합니다.

```bash
kubectl describe ing ing-test-ingress
```

> 여기서는 Host와 Path가 어떤 Backend Service를 가리키는지 읽고, 그 Service Port 뒤에 실제 Pod IP와 Port가 연결되는지도 확인합니다. 즉 Service와 실제 Backend의 연결을 **원본 `describe ingress` 출력 안에서 직접 확인**합니다.
>
> 원본 환경의 `describe ingress`에는 별도 `default-http-backend`가 표시됩니다. 이것은 **Ingress Rule에 매칭되지 않는 요청을 처리하는 fallback Backend**입니다. 현재 ingress-nginx 구성에서는 별도 `default-http-backend` Pod/Service 없이 Controller가 기본 404를 처리할 수도 있으므로, 현재 환경에서 동일 이름이 반드시 보여야 정상이라고 판정하지 않습니다. 실제 Test에서 볼 핵심은 `ing-test-svc:80` 뒤에 Test Pod Backend가 연결되는지입니다.
>
> 마지막으로 원본 순서대로 Browser에서 Test Domain을 엽니다.
>
> 현재 승인 Test Domain으로 접속해 기대한 Nginx/Test Application 응답이 오는지 확인합니다. 앞의 Kubernetes Object가 모두 정상이어도 실제 사용자 요청이 응답까지 도달하는 것은 별도 결과이므로 Browser Test까지 성공해야 원본 Ingress 기능 시험을 완료한 것입니다.

# 6. 원본 3-4-6 두 번째 — Metrics Server 기능 검증

> **Ingress 기능 확인이 끝난 뒤 원본 다음 대상은 Metrics Server입니다.** 여기서는 별도의 다른 Component 검증을 끼우지 않습니다.
>
> 원본에는 Metrics Server의 배치 참조 결과가 제시되고, 실제 실행 명령으로 `kubectl top nodes`를 사용해 Resource 사용량이 조회되는지 확인합니다.

```bash
kubectl top nodes
```

> `kubectl top nodes`가 실제 CPU/Memory 값을 반환해야 Metrics API가 기능한다고 볼 수 있습니다. Metrics Server Pod가 존재하는 것과 실제 Metrics 값이 조회되는 것은 다른 검증입니다.
>
> `top`이 실패하면 Metrics API, TLS/Certificate, kubelet 연결과 Metrics Server Log를 Troubleshooting에서 확인합니다.

# 7. 원본 3-4-6 세 번째 — Kubernetes Dashboard 기능 검증

> **Dashboard의 핵심은 Ingress나 Pod가 존재하는지가 아니라 실제 사용자가 URL을 열고 인증해서 UI에 들어갈 수 있는지 확인하는 것입니다.**
>
> 원본 사용자 흐름은 다음 순서입니다.
>
> ```text
> Dashboard Ingress 조회
> → Browser에서 URL Open
> → Firefox 사용 권장
> → TLS 경고가 있으면 Advanced 선택
> → 위험을 수락하고 계속 진행
> → admin-user ServiceAccount 확인
> → Secret 목록 확인
> → admin-user Token Secret 확인
> → Token Decode
> → Token 입력
> → Dashboard Login / UI 진입
> ```

원본 순서대로 먼저 Dashboard Ingress를 확인합니다.

```bash
kubectl get ing -n kubernetes-dashboard
```

> Domain과 Address가 현재 신규 Member 기준과 맞는지 확인한 뒤 **Browser에서 현재 Dashboard URL을 먼저 엽니다.** 원본은 Firefox Browser 사용을 권장합니다. 이 시점에는 아직 Token을 준비하기 전이므로 Dashboard 접속 화면과 TLS 경고 여부까지 확인합니다.
>
> 원본처럼 Browser에서 Certificate 경고가 나타나는 환경이라면 `Advanced`를 선택하고 승인된 현장 기준에 따라 위험을 수락해 계속 진행합니다. 이것은 원본의 실제 사용자 절차를 설명하는 것이며, 현재 환경에서 정상 신뢰 Certificate가 적용돼 경고가 없다면 해당 화면은 나타나지 않을 수 있습니다.
>
> 그다음 로그인에 사용할 `admin-user` ServiceAccount와 연결된 Secret을 원본 순서대로 확인합니다.

```bash
kubectl get sa -n kubernetes-dashboard admin-user
```

```bash
kubectl get secrets -n kubernetes-dashboard
```

```bash
kubectl get secrets -n kubernetes-dashboard -o yaml <admin-user-token-secret>
```

> ServiceAccount 존재 → Token Secret 존재 → 해당 Secret의 `data.token` 확인을 순서대로 수행합니다. Secret 이름을 임의로 추정하지 않고 현재 조회 결과의 실제 `admin-user` Token Secret을 사용합니다.
>
> 그다음 원본 순서대로 Token 값을 Base64 Decode합니다.

```bash
echo '<Encoded Token Value>' | base64 -d
```

> Decode한 Token은 앞에서 열어 둔 Dashboard Login 화면에 입력합니다. 로그인 후 실제 Dashboard UI가 열려야 사용자 기능까지 성공한 것입니다.
>
> **Token 원문은 강의 화면 캡처·녹화·증적에 남기지 않습니다.** Decode가 필요한 경우에도 비공개 화면에서 수행하고 결과값을 기록하지 않습니다.
>
> [!warning] 현재 Kubernetes Version 인증 방식 확인
> ServiceAccount Token 동작은 Kubernetes Version과 Dashboard 배포 방식에 따라 원본 v1.22 예시와 달라질 수 있습니다. 현재 환경에서 장기 Token Secret이 자동 생성되지 않는다면 `kubectl create token` 등 현재 승인 방식으로 수행합니다. 이 차이는 원본 절차를 삭제하는 것이 아니라 **현재 Version 적용 차이로 별도 기록**합니다.

> **3-4-6 PASS는 세 가지 실제 기능 증거가 있어야 합니다.** Ingress는 실제 Browser 요청이 `Ingress → Service → Test Pod`까지 도달해야 하고, Metrics는 `kubectl top nodes`가 실제 CPU/Memory 값을 반환해야 하며, Dashboard는 실제 사용자가 URL을 열고 인증해 UI에 진입해야 합니다.
>
> ```text
> Ingress PASS
> → 실제 외부 요청이 Application까지 도달
>
> Metrics PASS
> → 실제 Metrics API가 Resource 값을 제공
>
> Dashboard PASS
> → 실제 사용자가 접속·인증해 UI 진입
> ```
>
> 여기까지 Dashboard Login까지 확인하면 원본 `3-4-6`이 끝납니다. 따라서 원본 `3-4-3`, `3-4-4`, `3-4-5`, `3-4-6` 전체가 완료되고, 오전의 `3-1~3-3`과 오후 1의 `3-4-1~3-4-2`까지 포함해 원본 5.3을 끝까지 수행한 상태가 됩니다.
>
> 오후 1에서 Pod 배치와 기본 상태를 확인하고 이번 블록에서 상세 설정과 기능을 다시 본 것은 중복이 아닙니다. **배치가 맞는가와 실제 구성·기능이 맞는가는 서로 다른 검증 질문**입니다.

# 8. 문제가 생기면 현재 원본 단계에서 처음 어긋난 지점부터 본다

> `3-4-3`에서 Kubernetes의 External ETCD Endpoint가 다르면 Calico나 Ingress부터 수정하지 않습니다. 먼저 `kubeadm-config`와 현재 신규 Member ETCD 목록을 맞추고, Member List는 정상인데 특정 Endpoint Status만 Error라면 해당 Member의 Network, Certificate, Disk와 Process 상태를 비교합니다.
>
> `3-4-4`에서 containerd Version은 맞는데 Registry Entry나 TLS 정책이 다르면 CNI 문제로 확대하지 않습니다. `offline.yml`, 현재 containerd Registry 설정과 8/31 CA Trust를 대조합니다. Test Ingress의 Pod가 `ImagePullBackOff`라면 이 Runtime/Registry 경계로 다시 돌아옵니다.
>
> `3-4-5`에서 Calico Pod는 Running인데 IPPool CIDR이 오전 승인값과 다르면 먼저 Calico IPPool과 Kubespray Network 입력을 맞춥니다. Pod에 IP가 붙지 않거나 Network 기능을 추가 확인해야 할 때만 승인된 Test Pod와 관련 진단을 사용합니다.
>
> `3-4-6`에서 Test Deployment는 정상인데 Service Backend가 비어 있다면 Ingress Controller보다 먼저 Service Selector, Pod Label, Readiness와 Endpoint/EndpointSlice를 확인합니다. Ingress Address나 Controller 배치가 이상하면 Router Role·Label·Taint와 Ingress Controller 상태를 봅니다.
>
> Browser Test만 실패하면 필요에 따라 `curl`로 같은 요청을 재현하고 DNS, Load Balancer, Router Network 경계를 좁힙니다. Router NodePort까지 응답하는데 VIP-B만 실패하면 Kubernetes 내부 전체를 다시 설치하지 않고 Load Balancer Frontend/Backend Mapping과 DNS를 확인합니다. HTTP만 성공한 경우에도 HTTPS와 Certificate Trust까지 자동으로 정상이라고 확대하지 않습니다.
>
> Metrics Server Pod는 정상인데 `kubectl top nodes`가 실패하면 Metrics API와 Metrics Server가 kubelet에서 값을 수집하는 경로를 봅니다. Dashboard 화면은 열리는데 Login만 실패하면 현재 Kubernetes Version의 ServiceAccount Token 방식과 RBAC를 확인합니다.
