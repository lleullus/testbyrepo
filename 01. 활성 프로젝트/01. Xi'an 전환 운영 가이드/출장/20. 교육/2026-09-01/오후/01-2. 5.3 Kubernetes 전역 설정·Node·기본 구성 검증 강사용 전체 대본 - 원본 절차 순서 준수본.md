# 5.3 Kubernetes 전역 설정·Node·기본 구성 검증 강사용 전체 대본 - 원본 절차 순서 준수본

> [!important] 사용 방법
> 이 대본은 원본 `3. Ansible Playbook 배포 및 클러스터 설정`의 **`3-4-1 → 3-4-2` 순서를 그대로 따라가는 강사용 대본**이다.
>
> 오전에는 원본 `3-1 → 3-2 → 3-3`을 따라 Kubespray 입력을 확인하고 `cluster.yml`을 실행한 뒤 kubeconfig·kubectl·ETCD Backup·정리까지 마쳤다. 이번 블록부터는 원본 `3-4. 클러스터 배포 후 구성 검증`을 시작한다.
>
> 필요한 기술 설명은 해당 원본 검증 항목 아래에서 보강하되, 원본 `3-4-1 → 3-4-2`의 작업 순서는 바꾸지 않는다.
>
> 정확한 신규 Member VIP·CIDR·Domain·Hostname·IP·Version·Role·Node 수는 8/31 확정값과 현재 승인 기준을 사용한다. 원본의 `10.166.*`, `khdks*`, 과거 Host/Member 출력은 구조 참고로만 본다.
>
> kubeconfig, Token, Private Key, Certificate Key, Registry Credential 원문은 화면과 증적에 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
오전 3-1~3-3을 완료했다
→ 이제 원본 3-4 검증을 시작한다
→ 3-4-1에서 실제 Cluster 전역값을 본다
→ Node Version·Ready·IP를 확인한다
→ kube-proxy mode와 Role·Label·Taint를 확인한다
→ Kubernetes main component와 Add-on Pod의 위치·상태를 원본 순서대로 본다
→ Kubernetes certificate 만료를 확인한다
→ 3-4-2에서 각 VM의 OS 적용 결과를 확인한다
→ 전체 Host 목록을 기준으로 SELinux를 본다
→ Kubespray가 반영한 /etc/hosts를 본다
→ Swap이 여전히 꺼져 있는지 본다
→ module/sysctl 파일이 Role에 맞게 생성됐는지 본다
→ resolv.conf를 본다
→ NTP와 실제 시간을 확인한다
→ 다음 원본 3-4-3 External ETCD로 넘긴다
```

## 0-1. 오늘 전체 한 줄

> 이번 블록은 오전에 만든 Cluster를 다시 설정하는 시간이 아닙니다. **오전에 넣은 설계값이 실제 Kubernetes에 반영됐는지, 예상 Node와 주요 Component가 올바른 위치와 상태로 올라왔는지, 그리고 각 VM에도 Kubespray의 기본 OS 설정이 맞게 적용됐는지 원본 순서대로 검증하는 시간**입니다.

# 1. 시작 — 이제 설치된 상태를 검증된 상태로 바꾼다

> 오전에는 Kubespray가 읽을 입력을 만들고 `cluster.yml`을 실행했습니다.
>
> 그리고 Master와 Bastion에서 `kubectl`을 사용할 기본 경로까지 준비했습니다.
>
> 하지만 오전의 `kubectl get nodes`는 배포 직후 API가 최소한 응답하고 Node 객체를 읽을 수 있는지를 확인한 Smoke Check였습니다.
>
> 지금부터는 다릅니다.
>
> 원본 `3-4`에서는 **실제 Cluster에 어떤 값이 적용됐는지, Node가 어떤 Identity와 Role로 등록됐는지, 핵심 Kubernetes Component가 어느 Node에 배치됐는지, 그리고 각 Node의 OS 설정이 설치 후에도 기대 상태인지**를 확인합니다.
>
> 따라서 이번 블록의 핵심은 “명령이 성공하는가”가 아니라 **오전에 넣은 설계와 지금 보이는 실제 상태가 같은 Cluster를 설명하는가**입니다.

# A. Cluster가 설계대로 만들어졌는지 판정한다

> 여기서는 오전에 입력한 설계가 실제 Kubernetes Cluster의 전역값, Node Identity·Role, 주요 Component 배치에 그대로 반영됐는지를 판정합니다. 이 구조가 틀리면 상세 Component 검증으로 넘어가기 전에 먼저 설계와 적용 결과의 불일치를 해결합니다.

# 2. 원본 3-4-1 — 전역 변수 및 Kubernetes 기본 설정 검증

> 원본은 먼저 Kubernetes API에서 Cluster 전체에 적용된 전역 설정과 Node·Component 상태를 확인합니다.
>
> 여기서는 입력 파일을 다시 보는 것이 아닙니다. **실제로 만들어진 Cluster가 어떤 값을 사용하고 있는지**를 봅니다.
>
> [!warning] 원본 참조 출력의 과거값 주의
> `03.md`의 참조 출력에는 서로 다른 과거 시점 또는 환경의 VIP, Domain, CIDR, Hostname, Role/Taint 값이 섞여 있습니다. 예를 들어 앞 설정 예시와 뒤 `kubeadm-config` 출력이 같은 값을 보장하지 않습니다. 따라서 참조 출력의 숫자나 문자열 자체를 기대값으로 사용하지 않고, **8/31에 확정한 신규 Member 입력값과 지금 조회한 실제 Cluster 결과를 서로 대조**합니다.

## 2.1. Kubernetes cluster configuration 확인

> 먼저 `kubeadm-config`에서 실제 Cluster 설정을 확인합니다.

```bash
kubectl -n kube-system describe cm kubeadm-config \
  | egrep "controlPlaneEndpoint|node-cidr-mask-size|kubernetesVersion|dnsDomain|podSubnet|serviceSubnet"
```

> 확인할 항목은 다음입니다.

```text
controlPlaneEndpoint
node-cidr-mask-size
kubernetesVersion
dnsDomain
podSubnet
serviceSubnet
```

> `controlPlaneEndpoint`는 운영자와 Kubernetes Component가 공통으로 사용하는 API 진입점입니다.
>
> 신규 Member에서는 8/31과 오전 `dks_vars.yml`에서 확인한 승인 VIP-A와 6443 Port가 실제로 반영됐는지 봅니다.
>
> Master 하나의 직접 IP로 API가 응답한다고 해서 이 값이 올바르다는 뜻은 아닙니다. Cluster 전역 설정이 승인 VIP-A를 가리키는지 별도로 확인합니다.
>
> `kubernetesVersion`은 실제 Cluster가 어떤 Kubernetes Version으로 구성됐는지 보여 줍니다.
>
> 오전 `k8s-cluster.yml`에서 확인한 Version과 실제 `kubeadm-config`의 Version이 같아야 합니다.
>
> `dnsDomain`은 Kubernetes 내부 Service 이름 해석의 기준 Domain입니다.
>
> `podSubnet`은 Pod Network가 사용할 주소 범위이고, `serviceSubnet`은 ClusterIP Service가 사용할 주소 범위입니다.
>
> 두 CIDR은 목적이 다르므로 단순히 “둘 다 /16이다” 같은 식으로 보지 않습니다. 8/31 승인값과 각각 대조합니다.
>
> `node-cidr-mask-size`는 각 Node에 Pod CIDR Block을 어떻게 나눌지와 연결됩니다. 원본 예시의 `26`을 기억으로 적용하지 않고 현재 승인 설계와 실제값을 비교합니다.
>
> 여기서 중요한 판단은 다음입니다.
>
> 오전 변수 파일이 올바른 것은 **의도한 입력**을 증명합니다.
>
> 지금 `kubeadm-config`에서 같은 값이 보이는 것은 **그 입력이 실제 Cluster 구성에 반영됐다는 결과**를 증명합니다.
>
> 그래서 입력 파일만 보고 오후 검증을 생략하지 않습니다.

## 2.2. Kubernetes Version 및 Node 상태 확인

> 다음 원본 순서는 전체 Node 상태입니다.

```bash
kubectl get nodes -o wide
```

> 최소 다음 항목을 읽습니다.

```text
NAME
STATUS
ROLES
VERSION
INTERNAL-IP
OS-IMAGE
KERNEL-VERSION
CONTAINER-RUNTIME
```

> 먼저 Node 개수만 세지 않습니다.
>
> 예상한 수만큼 보이더라도 빠진 Node와 잘못 들어온 Node가 서로 상쇄되면 숫자만 맞을 수 있습니다.
>
> 그래서 각 `NAME`을 8/31 실제 VM 목록과 대조하고, `INTERNAL-IP`도 해당 Hostname의 실제 Management/Node IP와 같은지 확인합니다.
>
> `VERSION`은 앞에서 확인한 Cluster Version과 같은 설치 세트인지 봅니다.
>
> `OS-IMAGE`, `KERNEL-VERSION`, `CONTAINER-RUNTIME`은 현재 Node가 어떤 OS와 Runtime 기준으로 등록됐는지 확인하는 자료입니다.
>
> `STATUS=Ready`는 kubelet이 Control Plane과 기본 상태를 주고받고 있고 Control Plane이 해당 Node를 사용할 수 있는 상태로 판단하고 있다는 중요한 증거입니다.
>
> 하지만 Ready 하나로 CoreDNS, Calico, Ingress, Storage까지 정상이라고 확대하지 않습니다.
>
> 이번 단계에서는 **Node Identity·Version·Internal IP·기본 Ready 상태**까지 확인합니다.

## 2.3. KubeProxy mode 및 Node Label·Role·Taint 확인

> 원본은 다음으로 kube-proxy Mode를 확인합니다.

```bash
kubectl -n kube-system describe cm kube-proxy | grep mode:
```

> 현재 승인 설계가 IPVS를 사용한다면 실제 `mode`가 그 기준과 같은지 확인합니다.
>
> 여기서 ConfigMap에 값이 존재한다는 것만 보고 실제 Node 전체의 kube-proxy 기능까지 완료됐다고 판단하지 않습니다. 먼저 원본 순서대로 설정값을 확인하고, 이어지는 Pod 배치에서 kube-proxy가 모든 Node에 올라왔는지 봅니다.
>
> 그다음 Node의 Role, Label, Taint를 확인합니다.

```bash
kubectl describe nodes | egrep "Name:|Labels:|node-type|Taints:|Role"
```

> `ROLES` 문자열은 Node가 어떤 역할로 보이는지 알려 주지만, 실제 Workload 배치 정책은 Label과 Taint에 영향을 받을 수 있습니다.
>
> Master, Router, Infra, Worker/System 계열 Node가 각각 현재 승인된 `node-type`과 Taint를 갖는지 확인합니다.
>
> 예를 들어 Router Node 이름과 IP가 맞아도 Router Label/Taint가 빠져 있으면 이후 Ingress Controller가 의도한 Node 집합에 배치된다고 장담할 수 없습니다.
>
> Infra도 마찬가지입니다. Dashboard, Metrics 같은 Add-on의 기대 배치와 연결되므로 Node Role과 Label/Taint를 함께 봅니다.

# 3. 원본 3-4-1 — Kubernetes main component 및 Add-on Pod 위치와 상태 확인

> 이제 원본은 Kubernetes 핵심 Component와 기본 Add-on Pod가 어느 Node에 배치되어 있는지 확인합니다.
>
> 여기서 중요한 것은 Pod 이름을 외우는 것이 아닙니다. **각 Component가 어떤 역할을 하고, 어느 Role Node에 배치되어야 하며, 실제 상태가 Ready/Running인지**를 순서대로 읽는 것이 목적입니다.
>
> 먼저 Control Plane 세 Component를 봅니다. API Server는 Kubernetes API 요청을 받고, Controller Manager는 원하는 상태와 현재 상태의 차이를 조정하며, Scheduler는 아직 Node가 정해지지 않은 Pod의 배치 대상을 결정합니다.

```bash
kubectl get pod -A -o wide --no-headers | grep kube-apiserver | sort -k8
kubectl get pod -A -o wide --no-headers | grep kube-controller-manager | sort -k8
kubectl get pod -A -o wide --no-headers | grep kube-scheduler | sort -k8
```

> 세 Component가 현재 신규 Member의 승인 Control Plane Node 집합에 배치되고 Ready/Running인지 확인합니다. `Running`만으로 VIP-A 경로나 모든 제어 기능까지 증명되는 것은 아니지만, 이 단계에서는 원본 목적대로 **기대 Master 집합에 Control Plane 핵심 Component가 정상 상태로 존재하는지**를 봅니다.
>
> 그다음 kube-proxy와 CoreDNS를 확인합니다. 앞에서는 kube-proxy ConfigMap의 Mode를 봤고, 여기서는 실제 kube-proxy Pod가 대상 Kubernetes Node 전체에 존재하는지 확인합니다. CoreDNS는 Kubernetes 내부 DNS를 담당하므로 원본에서 기대하는 Replica 수와 배치 Role이 현재 신규 Member 설계와 같은지 봅니다.

```bash
kubectl get pod -A -o wide --no-headers | grep kube-proxy | sort -k8
kubectl get pod -A -o wide --no-headers | grep coredns | sort -k8
```

> 특정 Node에서 kube-proxy만 빠져 있다면 전체 Network 문제로 확대하기 전에 그 Node의 Pod 상태와 Node 상태를 비교합니다. CoreDNS도 `Running`이면 Pod가 시작됐다는 뜻이지 실제 Service 이름 질의까지 성공했다는 뜻은 아니므로, 지금은 배치와 기본 상태까지만 확인합니다.
>
> 이어서 Calico Component를 원본 순서대로 봅니다. 먼저 Controller가 Router Node 집합에 배치되는지 확인하고, `calico-node`가 대상 Kubernetes Node 전체에 하나씩 배치되는지 확인합니다. 그다음 현재 Bundle에서 Typha를 사용하는 경우 Router Node 집합의 실제 배치도 봅니다.

```bash
kubectl get pod -A -o wide --no-headers | grep calico-kube | sort -k8
kubectl get pod -A -o wide --no-headers | grep calico-node | sort -k8
kubectl get pod -A -o wide --no-headers | grep calico-typha | sort -k8
```

> 여기서는 Calico의 배치와 Running 상태를 확인합니다. 실제 Backend, IPPool, VXLAN 같은 상세 설정은 다음 블록의 원본 `3-4-5`에서 다시 확인합니다. Bundle/Version에 따라 Typha Replica 수는 달라질 수 있으므로 과거 출력의 숫자를 그대로 정답으로 사용하지 않습니다.
>
> 마지막으로 원본에 이어지는 Add-on Pod 배치를 봅니다. Ingress Controller는 승인 Router Node에 배치되는지 확인하고, default-http-backend와 Dashboard, Metrics Scraper, Metrics Server는 현재 신규 Member의 승인 Infra 배치 기준과 실제 Node가 같은지 확인합니다.

```bash
kubectl get pod -A -o wide --no-headers | grep ingress-nginx | sort -k8
kubectl get pod -A -o wide --no-headers | grep default-http | sort -k8
kubectl get pod -A -o wide --no-headers | grep kubernetes-dashboard- | sort -k8
kubectl get pod -A -o wide --no-headers | grep kubernetes-metrics-scraper | sort -k8
kubectl get pod -A -o wide --no-headers | grep metrics-server | sort -k8
```

> Ingress는 지금 배치와 기본 상태까지만 보고, NodePort와 `--enable-ssl-passthrough`, 실제 Test Ingress는 다음 블록의 원본 `3-4-6`에서 확인합니다. Dashboard도 로그인 방식과 Token은 다음 블록에서 확인하고, Metrics Server 역시 실제 `kubectl top nodes`가 값을 반환하는지는 다음 블록에서 확인합니다.
>
> 모든 Component는 단순히 `STATUS=Running`만 보지 않습니다. `READY`, `RESTARTS`, `NODE`, `AGE`를 함께 봅니다. READY가 기대값인지, Restart가 계속 증가하는지, 의도한 Role Node에 배치됐는지 같이 확인합니다. 과거 Restart 한 번이 있다는 이유만으로 현재 장애라고 단정하지 않고, 현재 Ready 상태와 Restart 증가 여부를 함께 판단합니다.

# 4. 원본 3-4-1 마지막 — Kubernetes certificate expiration 확인

> 원본은 주요 Kubernetes Component 배치 확인 뒤 Master에서 Kubernetes Certificate 만료를 확인합니다.

```bash
ssh <신규 Member Master 1>
sudo /usr/local/bin/kubeadm certs check-expiration
```

> 확인할 항목은 다음과 같습니다.

```text
CERTIFICATE
EXPIRES
RESIDUAL TIME
CERTIFICATE AUTHORITY
EXTERNALLY MANAGED
```

> 신규 구축 직후라면 주요 Certificate의 만료기간이 현재 설치 기준에 맞게 충분히 남아 있어야 합니다.
>
> 여기서는 Certificate Renewal 절차를 수행하는 단계가 아닙니다.
>
> **생성된 Certificate가 현재 유효하고 비정상적으로 짧은 만료가 아닌지 검증**하는 단계입니다.
>
> Private Key 내용은 출력하지 않습니다.

# B. 각 Node의 OS 기반이 설치 기준대로 남아 있는지 판정한다

> Kubernetes 객체가 정상으로 보여도 실제 VM의 OS 기반 설정이 잘못되어 있으면 이후 Runtime·Network·Add-on 문제로 이어질 수 있습니다. 여기서는 Kubespray와 Pre-setting이 각 Host에 남긴 SELinux, hosts, Swap, Kernel/sysctl, DNS, 시간 동기화 상태가 현재 Role과 설치 기준에 맞는지를 판정합니다.

# 5. 원본 3-4-2 — 추가 노드 설정 검증

> 이제 원본은 Kubernetes API 객체에서 실제 VM의 OS 상태로 내려갑니다.
>
> 앞에서는 Cluster가 어떤 설정과 Node·Pod 상태를 가지고 있는지 봤습니다.
>
> 이제는 Bastion에서 각 Host에 접속해 **Kubespray와 Pre-setting이 실제 Node OS에 남긴 상태가 기대와 같은지** 확인합니다.

## 5.1. 현재 신규 Member 전체 Host 목록 준비

> 원본은 반복 확인을 위해 전체 Hostname 목록을 사용합니다.
>
> 과거 `all_hosts.list`를 그대로 재사용하지 않고 현재 신규 Member의 실제 Bastion·Master·ETCD·Router·Infra·Worker/System Node 목록으로 작성합니다.

```bash
cat all_hosts.list
```

> 목록에 빠진 Host가 있으면 이후 Loop 결과도 완전하지 않습니다.
>
> 그래서 8/31 VM/Role 목록과 `all_hosts.list`를 먼저 대조합니다.

## 5.2. 각 Node의 SELinux 상태 확인

```bash
for i in $(cat all_hosts.list)
do
  echo ""
  ssh "$i" hostname
  ssh "$i" sudo grep '^SELINUX=' /etc/selinux/config
  sleep 1
done
```

> 원본 기대 상태와 실제 각 Host의 설정을 확인합니다.
>
> 한 Node가 정상이라고 전체 Node가 같은 것은 아닙니다.
>
> Role에 관계없이 현재 승인 기준과 다른 Host가 있는지 Host 단위로 봅니다.

## 5.3. Kubespray가 생성한 `/etc/hosts` Record 확인

```bash
for i in $(cat all_hosts.list)
do
  echo ""
  ssh "$i" hostname
  ssh "$i" sudo cat /etc/hosts
  sleep 2
done
```

> 8/31 Bastion Pre-setting에서 Bastion의 `/etc/hosts`를 준비한 것과 지금 검증은 목적이 다릅니다.
>
> 지금은 **Kubespray가 각 Node에 Inventory Host/IP 정보를 어떤 Record로 반영했는지** 확인합니다.
>
> Hostname, FQDN, Alias와 IP가 현재 신규 Member 목록과 맞는지 봅니다.
>
> 다른 Cluster의 Host나 과거 IP가 섞여 있으면 이름 해석 문제로 이어질 수 있습니다.

## 5.4. Swap 비활성화 확인

```bash
for i in $(cat all_hosts.list)
do
  echo ""
  ssh "$i" hostname
  ssh "$i" sudo cat /proc/swaps
  sleep 2
done
```

> 8/31 Node Pre-setting에서 이미 Swap을 비활성화했습니다.
>
> 지금 다시 보는 이유는 중복 실습이 아니라 **Kubespray 배포 후에도 설치 전 조건이 유지되고 있는지 검증**하기 위해서입니다.
>
> `/proc/swaps`에 실제 사용 중인 Swap이 없어야 합니다.

## 5.5. Kubespray 생성 Module/sysctl Configuration File 확인

> 원본은 `/etc/modules-load.d`와 `/etc/sysctl.d`를 확인합니다.

```bash
for i in $(cat all_hosts.list)
do
  echo ""
  ssh "$i" hostname
  ssh "$i" sudo ls -al /etc/modules-load.d
  ssh "$i" sudo ls -al /etc/sysctl.d
  sleep 2
done
```

> 주요 확인 대상은 원본 기준 다음과 같습니다.

```text
kube_proxy-ipvs.conf
kubespray-br_netfilter.conf
99-sysctl.conf
```

> 하지만 모든 Host에 세 파일이 똑같이 있어야 한다고 단정하지 않습니다.
>
> 원본 자체에서도 Bastion이나 External ETCD Node처럼 Kubernetes Node와 역할이 다른 Host에는 일부 Module File이 없을 수 있습니다.
>
> 따라서 `No such file`이 보이면 바로 장애라고 하지 않고 **그 Host Role이 해당 파일 생성 대상인지** 먼저 확인합니다.

## 5.6. 위 Configuration File 상세 확인

> Kubernetes Node에서는 IPVS Module, `br_netfilter`, IP Forwarding, Bridge Netfilter 등 Kubespray가 요구한 Kernel/Network 설정이 반영됐는지 확인합니다.

```bash
sudo cat /etc/modules-load.d/kube_proxy-ipvs.conf
sudo cat /etc/modules-load.d/kubespray-br_netfilter.conf
sudo cat /etc/sysctl.d/99-sysctl.conf
```

> 원본에서 확인하는 대표 값은 다음 범주입니다.

```text
ip_vs 관련 module
br_netfilter
IPv4 forwarding
bridge-nf-call-iptables
bridge-nf-call-ip6tables
Kubespray가 추가한 kernel/vm/network sysctl
```

> 8/31 Pre-setting에서 일부 sysctl을 준비했더라도, 지금은 **Kubespray 설치 후 생성된 설정이 Role별로 올바르게 존재하는지** 보는 단계입니다.

## 5.7. 각 Node의 `resolv.conf` Nameserver 설정 확인

```bash
for i in $(cat all_hosts.list)
do
  echo ""
  ssh "$i" hostname
  ssh "$i" sudo cat /etc/resolv.conf
  sleep 2
done
```

> Bastion/External ETCD와 Kubernetes Node의 `resolv.conf` 내용은 같지 않을 수 있습니다.
>
> Kubernetes Node에는 Cluster DNS 관련 Search Domain이나 Cluster DNS Service IP가 추가될 수 있고, Bastion/ETCD는 외부/사내 DNS만 사용할 수 있습니다.
>
> 따라서 모든 Host의 파일이 동일한지 보지 않고 **각 Role에서 필요한 DNS 경로가 현재 신규 Member Domain과 Nameserver 기준으로 맞는지** 확인합니다.

## 5.8. 각 Node의 NTP 설정과 실제 시간 확인

```bash
for i in $(cat all_hosts.list)
do
  echo ""
  ssh "$i" hostname
  ssh "$i" sudo chronyc sources -v
  ssh "$i" date
  sleep 2
done
```

> NTP Server 목록이 파일에 있다는 것만으로 시간 동기화가 정상인 것은 아닙니다.
>
> `chronyc sources -v`에서 실제 사용 가능한 Source와 현재 선택 Source를 확인하고, 각 Host의 `date`도 비교합니다.
>
> Kubernetes Certificate, ETCD, Log 상관관계와 분산 시스템 동작에서는 Node 간 시간 차이가 장애 분석을 어렵게 만들 수 있습니다.
>
> 따라서 설정 문자열보다 **실제 동기화 상태와 현재 시간**을 함께 봅니다.

# 7. 문제가 생기면 현재 원본 검증 단계에서 끊긴 지점부터 본다

> `kubeadm-config`의 VIP/CIDR/Domain이 다르면 Pod부터 재시작하지 않습니다. 오전 입력값과 실제 적용값이 어디서 달라졌는지 확인합니다.
>
> 특정 Node만 없거나 NotReady라면 전체 Cluster 재설치보다 해당 Node의 Identity, kubelet, Network, Runtime 상태를 같은 Role의 정상 Node와 비교합니다.
>
> Node는 Ready인데 Label/Taint가 다르면 CNI 문제로 확대하지 않고 Inventory/Group 변수와 적용 결과를 봅니다.
>
> 특정 Control Plane Pod만 반복 재시작하면 Pod 삭제부터 하지 않고 Event·Log와 해당 Component 설정을 확인합니다.
>
> Calico/Ingress Pod 배치만 이상하면 오후 2 상세 설정을 건너뛰지 않고 먼저 현재 Role/Label/Taint와 Deployment/DaemonSet의 Scheduling 조건을 비교합니다.
>
> 어떤 Host에서 Module File이 없으면 다른 Node와 파일 수를 맞추기 전에 그 Host가 Kubernetes Node인지 Bastion/ETCD인지 Role을 확인합니다.
>
> DNS/NTP 결과가 한 Host만 다르면 공통 설정 전체보다 해당 Host의 NetworkManager, resolv.conf, chronyd 상태를 우선 비교합니다.
