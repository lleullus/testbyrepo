# Kubespray 입력 최종 확인·실행·로그 판독 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 8월 31일에 검증한 신규 Member 입력을 실제 Kubespray 실행으로 넘길 때 **무엇을 다시 확인하고, 실행 로그에서 어떤 실패를 먼저 믿으며, 언제 재실행해도 되는지 판단하는 법**을 가르친다. 정확한 Kubespray 옵션·세부 Role·복구 절차는 원본 Runbook을 따른다. 오늘 오전의 목표는 명령 암기가 아니라 **올바른 입력으로 한 번 실행하고, 실패가 있으면 최초 단절을 증거로 좁혀 같은 대상을 다시 검증하는 것**이다.

## 0. 8월 31일에서 이어받는 것

어제 마지막 블록에서 이미 다음을 판정했다.

```text
신규 Member Cluster Identity
+ Bastion Identity
+ Bundle·Kubespray 기준
+ hosts.yaml Host·Group
+ VIP·CIDR·Domain
+ Registry·Version
+ Ansible Graph·Ping·Identity·Become
+ Syntax Check
= GO 또는 BLOCKED
```

> 오늘은 어제의 모든 Preflight를 처음부터 반복하지 않습니다. 대신 **실행을 결정하는 핵심 증거가 지금도 같은 대상과 같은 내용인지** 확인합니다.

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> `cluster.yml`을 실행하기 전에 8월 31일 GO가 현재도 유효한지 확인하고, 실행 중 문제가 생기면 **어느 Host의 어느 Task가 최초로 실패했는지**, 그 실패가 `UNREACHABLE`인지 Task `FAILED`인지, 이후 오류가 연쇄 결과인지 구분한 뒤 재실행 여부를 판단할 수 있어야 한다.

오늘의 중심 질문은 하나다.

> **지금 이 입력으로 이 신규 Member에 Kubespray를 실행해도 되는가? 실패했다면 최초 실패가 정확히 무엇을 증명하는가?**

---

# 1. 시작 — 오늘 만드는 것은 Playbook 성공 화면이 아니다

> 오늘 오전에는 실제 신규 Member Kubernetes Cluster 설치를 시작합니다.
>
> 하지만 목표를 `ansible-playbook` 명령이 끝나는 것으로 잡지 않습니다. Kubespray는 우리가 준 Inventory와 변수 값을 믿고 여러 Node에 빠르게 변경을 적용합니다.
>
> 잘못된 IP가 실제 다른 Server를 가리키고 있다면 연결도 성공하고 많은 Task도 성공할 수 있습니다. 따라서 자동화의 힘은 입력이 맞을 때만 장점입니다.

Kubespray 실행을 다음처럼 이해한다.

```text
8월 31일에 확인한 현실
→ Inventory·변수로 표현
→ Kubespray가 그 입력을 읽음
→ Host별 Task 수행
→ Kubernetes Component 구성
→ 이후 기능 검증이 가능한 상태
```

> **오늘 오전의 완료는 Cluster 정상 완료가 아닙니다.** 실행이 미해결 자동화 오류 없이 끝나고, 오후 기능 검증을 시작할 수 있는 상태가 되는 것입니다.

---

# 2. GO를 다시 실행 허가로 바꾸기 전에 현재성을 확인한다

> 8월 31일에 GO였다는 사실은 어제 그 시점의 증거입니다. 밤사이 VM, 파일, Bundle, Registry, 승인 시간이 바뀌었을 수 있습니다.

다시 확인할 것은 전체 Preflight가 아니라 실행을 바꾸는 항목이다.

```text
현재 Bastion Hostname·IP
현재 작업 Account
현재 Bundle Root·Kubespray Directory
현재 hosts.yaml·주요 변수 파일
현재 Registry·Kubernetes Version
현재 Inventory Graph의 Host·Group
현재 Ansible Ping·Identity·Become
현재 실행 승인·유지보수 시간
```

## 2.1 GO의 의미

```text
8월 31일 GO
= 실행 전 필수 입력과 연결이 당시 증거로 통과
```

하지만:

```text
8월 31일 GO
≠ 9월 1일 현재 파일과 환경이 자동으로 동일
```

따라서 핵심 파일이 변경됐다면 그 변경이 승인된 것인지 확인한다.

> 미확정 VIP, CIDR, ETCD Filesystem, Repository, Registry, Credential 같은 **실행 필수값이 새로 불명확해졌다면 다시 BLOCKED**입니다. 시간을 맞추기 위해 추측값을 넣지 않습니다.

## 2.2 실행 전 마지막 말하기 Gate

강사는 실행 직전 수강생에게 다음을 말하게 한다.

```text
어느 Cluster를 만드는가
어느 Bastion에서 실행하는가
어느 Inventory를 읽는가
어느 Bundle·Kubespray를 사용하는가
VIP·CIDR·Domain·Registry·Version의 근거는 무엇인가
실행 승인 시간은 언제인가
로그는 어디에 남길 것인가
```

> 이 답이 한 신규 Member를 가리키지 않으면 실행하지 않습니다.

---

# 3. 실행 명령은 하나의 canonical 구조로만 본다

오늘 실제 실행 구조는 현재 승인된 Runbook을 따른다.

대표 구조:

```bash
ansible-playbook \
  -e @inventory/dks/dks_vars.yml \
  -i inventory/dks/hosts.yaml \
  --become --become-user=root \
  cluster.yml
```

> 실제 경로·추가 옵션·Ansible Config는 현재 Bundle과 Runbook을 우선합니다. 이 대본에서 임의의 재실행 옵션이나 우회 옵션을 만들지 않습니다.

실행 전 기록할 최소 정보:

```text
Cluster Name·Stage
Bastion Hostname
Bundle Root·Version
Inventory 위치·Checksum
주요 변수 파일 Checksum
실행 시작 시각
실행 Account
승인자·작업 시간
로그 파일 위치
```

> Password, SSH Private Key, Registry Credential, Token은 기록하지 않습니다.

---

# 4. Playbook 로그는 ‘어디에서 처음 달라졌는가’를 찾는 자료다

> 로그가 길다고 처음부터 모든 줄을 분석하지 않습니다. 먼저 **정상 진행이 어디까지 이어졌고 최초 비정상이 어디에서 시작했는지** 찾습니다.

최초로 고정할 네 가지:

```text
어느 Host인가
어느 Task인가
UNREACHABLE인가 FAILED인가
한 Host만인가 여러 Host 공통인가
```

그리고 마지막에 PLAY RECAP을 본다.

```text
ok
changed
unreachable
failed
skipped
rescued
ignored
```

## 4.1 `UNREACHABLE`과 `FAILED`는 조사 시작점이 다르다

```text
UNREACHABLE
→ Ansible이 대상 Host에서 Task 자체를 시작하지 못한 경계
→ Hostname·IP·DNS·Network·SSH·Account를 먼저 봄

FAILED
→ 대상 Host에 도달해 Task를 실행했지만 작업 또는 검증이 실패한 경계
→ 해당 Task 입력·현재 상태·권한·Package·Service·설정 등을 봄
```

> `UNREACHABLE`을 Kubernetes 설치 문제로 바로 부르지 않습니다. 아직 원격 Task를 실행하지 못한 것입니다.

## 4.2 첫 FAILED와 뒤의 FAILED를 구분한다

예를 들어 초기 Package 설치가 실패하면 뒤의 Kubernetes Component Task도 연쇄적으로 실패할 수 있다.

```text
최초 FAILED
→ 다음 정상 경로를 처음 끊은 후보

뒤의 다수 FAILED
→ 최초 실패의 결과일 수 있음
```

> Recap에 `failed=20`이 보인다고 원인이 20개라는 뜻은 아닙니다.

---

# 5. 실패가 나면 먼저 ‘같은 실패’를 증명한다

> 로그 한 줄만 보고 바로 설정을 바꾸지 않습니다.

먼저 대상과 오류를 고정한다.

```text
실패 Host
실패 Task
오류 원문
Task가 사용한 주요 입력
같은 Role의 정상 Host가 있는지
직전 Task까지 성공했는지
```

그다음 다음 질문을 한다.

> **어떤 읽기 전용 확인 하나가 다음 행동을 바꿀 것인가?**

대표 예:

| 실패 | 다음 첫 확인 |
|---|---|
| UNREACHABLE | Inventory Hostname·IP와 실제 DNS·SSH 경로 |
| sudo/become 실패 | 같은 Account의 `sudo -n` 기능 |
| Package 설치 실패 | 승인 Repo·OS Version·Package 존재 |
| Registry/Image 실패 | 실제 Image 주소·Registry 접근·CA Trust |
| kubelet/Service 시작 실패 | Service 상태와 해당 Task가 만든 설정 |
| 특정 Role만 실패 | 정상 Role과의 차이보다 같은 Role 정상 Host와 먼저 비교 |

> 원인과 무관한 영역을 동시에 바꾸지 않습니다. 여러 설정을 한꺼번에 바꾸면 어느 변경이 결과를 만들었는지 증명할 수 없습니다.

---

# 6. 재실행은 ‘처음부터 다시’가 아니라 적용 상태를 이해한 뒤 한다

Ansible과 Kubespray는 많은 Task가 반복 실행 가능한 구조를 갖지만, 이것이 무조건 안전한 재실행을 뜻하지는 않는다.

반드시 구분한다.

```text
Playbook 재실행 가능성
≠ 현재 부분 적용 상태를 무시해도 됨
```

재실행 전에 최소한 다음을 확인한다.

```text
최초 실패 원인이 무엇이었는가
어떤 조치를 했는가
조치 후 좁은 기능 확인이 성공했는가
이미 적용된 변경은 무엇인가
현재 Inventory·변수가 처음 실행과 같은가
재실행 범위와 영향이 Runbook 기준에 맞는가
```

> 첫 실패가 해소됐는지 확인하지 않고 같은 명령을 반복해 로그가 달라지기만 기다리지 않습니다.

## 6.1 좁은 확인이 먼저다

예:

```text
SSH 문제를 고쳤다
→ 해당 Host의 SSH·Ansible Ping 먼저 확인
→ 전체 cluster.yml 재실행은 그 뒤

Repository 문제를 고쳤다
→ 해당 Host에서 Metadata·필수 Package 조회 먼저 확인
→ 전체 재실행은 그 뒤
```

이 원칙은 하루 전체에서 계속 사용한다.

---

# 7. 실행 완료의 증거 범위를 정확히 제한한다

오전 실행 PASS는 다음을 의미한다.

```text
승인된 신규 Member 입력으로 cluster.yml 실행
+ 최종 Return Code 정상
+ PLAY RECAP에 미해결 failed·unreachable 없음
+ 실행 로그와 입력 기준이 보존됨
```

하지만 아직 다음은 증명하지 않았다.

```text
API 기능 정상
Node Identity·Role·Ready 정상
Control Plane 기능 정상
ETCD 상태 정상
실제 Pod Network 정상
Cluster DNS 질의 정상
Ingress·VIP-B 사용자 경로 정상
Storage 정상
```

즉:

```text
PLAYBOOK EXECUTION PASS
≠ KUBERNETES BASE PASS
```

> 오전 성공을 오후 전체 기능 성공으로 확대하지 않습니다.

---

# 8. 실행이 끝나면 ‘어제 입력 → 오늘 결과’ 연결을 남긴다

오후 검증으로 넘길 최소 증거:

```text
Cluster Name·Stage
현재 kubeconfig 후보와 검증 Account
Bastion·Bundle 기준
Inventory·주요 변수 Checksum
Kubernetes Version 기대값
VIP-A·Pod CIDR·Service CIDR·Domain 기대값
Node Role·Hostname·IP 기대표
최종 cluster.yml 실행 시각
Return Code
PLAY RECAP
실행 로그 위치
재실행이 있었다면 최초 실패·조치·재검증 기록
남은 미확정 또는 비차단 관찰사항
```

> 오후에는 이 값을 다시 처음부터 만드는 것이 아니라, **8월 31일에 입력한 설계가 실제 Kubernetes로 만들어졌는지** 대조합니다.

---

# 9. 오전 BLOCKED 기준

다음 중 하나가 남으면 기능 검증을 정상 흐름으로 시작하지 않고 실행 문제부터 닫는다.

```text
현재 대상 Cluster·Bastion·Inventory 불일치
실행 필수값 미확정
실행 승인·작업 시간 없음
미해결 UNREACHABLE 존재
미해결 FAILED 존재
Return Code 비정상
재실행 후에도 최초 실패 원인 미확정
로그와 실제 입력 기준을 연결할 수 없음
```

> BLOCKED를 숨기기 위해 `failed`를 ignore하거나 임의 옵션을 추가하지 않습니다.

---

# 10. 마무리 — Kubespray 실행을 한 문장으로 다시 말한다

> Kubespray는 Cluster가 맞는지 판단해 주는 도구가 아니라, 우리가 제공한 Inventory와 변수에 따라 여러 Node를 자동으로 구성하는 도구입니다.
>
> 그래서 실행 전에는 8월 31일 GO가 현재도 같은 대상인지 확인하고, 실행 중에는 긴 로그에서 최초 실패 Host와 Task를 고정합니다.
>
> 실패가 있으면 원인을 추정해 여러 설정을 바꾸지 않고 다음 행동을 바꾸는 최소 확인부터 합니다. 재실행은 그 원인과 적용 상태를 이해한 뒤 승인된 동일 경로로 수행합니다.
>
> **결국 오전의 성공은 Playbook이 미해결 자동화 오류 없이 끝났다는 뜻이며, 실제 Kubernetes가 정상이라는 판정은 오후 기능 검증에서 별도로 해야 합니다.**

---

# 11. 마지막 Teach-back

1. 8월 31일 GO를 9월 1일 실행 직전에 그대로 믿지 않고 다시 현재성을 확인해야 하는 이유는 무엇인가?
2. `UNREACHABLE`과 Task `FAILED`는 무엇이 다르며 조사 시작점은 어떻게 다른가?
3. PLAY RECAP에 여러 FAILED가 있어도 최초 FAILED를 먼저 찾는 이유는 무엇인가?
4. 실패 후 바로 전체 Playbook을 반복하지 않고 좁은 기능 확인을 먼저 해야 하는 이유는 무엇인가?
5. Return Code 0과 Kubernetes 기능 정상은 왜 다른 증거인가?
6. 오전 실행 PASS가 오후 검증으로 넘겨야 할 최소 증거는 무엇인가?
