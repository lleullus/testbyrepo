# 5.3 Kubespray 배포 환경 설정·Playbook 실행·클러스터 후속 설정 강사용 전체 대본 - 원본 절차 순서 준수본

> [!important] 사용 방법
> 이 대본은 **원본 `3. Ansible Playbook 배포 및 클러스터 설정`의 `3-1 → 3-2 → 3-3` 순서를 그대로 따라가면서 설명하기 위한 강사용 대본**이다.
>
> 원본의 작업 순서를 교육 편의상 `Inventory`, `로그`, `API`, `운영 도구` 같은 새로운 주제 순서로 재배열하지 않는다. 먼저 `3-1`에서 Kubespray가 읽을 입력을 준비하고, 그다음 `3-2`에서 실제 `cluster.yml`을 실행하며, 배포가 끝난 뒤 `3-3` 후속 설정을 수행한다.
>
> 정확한 신규 Member Hostname·IP·VIP·CIDR·Domain·Registry·Kubernetes Version은 8/31에 확인한 실제값과 현재 승인 기준을 사용한다. 원본에 남아 있는 `10.166.*`, `khdks*`, Host Cluster 값과 과거 Taylor/TAS 실행값을 신규 Member 실행값으로 복사하지 않는다.
>
> 이 대본은 원본 명령을 보여주고 바로 이어서 **왜 이 순서에서 실행하는지, 어떤 입력을 읽는지, 무엇을 변경하는지, 결과에서 무엇을 봐야 하는지, 여기까지 성공했다고 어디까지 말할 수 있는지**를 설명한다.
>
> 오후에는 원본 `3-4. 클러스터 배포 후 구성 검증`을 별도로 진행한다. 오전에 `kubectl get nodes`가 성공했다고 오후 검증까지 끝난 것으로 처리하지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

> 직관적으로는 **`3-1 = 무엇을 만들지 확정`, `3-2 = Kubespray로 실제 Cluster 배포`, `3-3 = 배포된 Cluster의 관리 접근·복구·정리 후속 설정`, `3-4 = 제대로 만들어졌는지 정식 검증`**으로 이해하면 됩니다.

```text
8/31에 신규 Member Node와 실행 조건을 준비했다
→ 원본 3-1-1에서 현재 Kubespray Ansible 설정을 확인한다
→ 원본 3-1-2에서 hosts.yaml을 현재 Node/Role/IP로 구성한다
→ dks_vars.yml에 VIP·CIDR·Domain을 넣는다
→ offline.yml에 Registry를 연결한다
→ Kubernetes Version을 재확인한다
→ 실행 직전 8/31 Preflight의 현재성만 다시 확인한다
→ 원본 3-2-1에서 cluster.yml을 실제 실행한다
→ 실행 중 Task와 Host, FAILED/UNREACHABLE, PLAY RECAP을 읽는다
→ Playbook 완료 후 Master에서 최초 kubectl get nodes를 확인한다
→ 원본 3-3-1에서 dspaas kubeconfig를 구성한다
→ 3-3-2에서 root와 dspaas의 API 연결을 확인한다
→ 3-3-3에서 Bastion kubectl과 kubeconfig를 구성한다
→ 3-3-4에서 kubectl alias/completion을 설정한다
→ 3-3-5에서 ETCD Backup과 Bastion Reserve를 구성한다
→ 3-3-6에서 Kubespray가 남긴 불필요 파일을 조회·삭제·재확인한다
→ 오전 후속 설정 완료 결과를 오후 3-4 검증으로 넘긴다
```

## 0-1. 오늘 전체 한 줄

> 오늘 오전은 Kubespray를 시험 삼아 실행하는 시간이 아닙니다. **어제 확인한 신규 Member 실제값을 원본 `3-1` 설정 파일에 최종 반영하고, 그 입력으로 `3-2`의 `cluster.yml`을 실행한 뒤, 원본 `3-3`의 운영 접근과 ETCD Backup·정리 설정까지 순서대로 완료하는 시간**입니다.

# 1. 시작 — 8/31 준비 결과를 오늘 실제 배포 입력으로 연결한다

> 어제는 신규 Member VM의 Role·Hostname·IP와 VIP를 확인했고, Bastion과 Kubernetes Node Pre-setting을 마쳤습니다.
>
> Node에서는 `dspaas` 권한, SSH Public Key, Repository, Package, Swap, logrotate, CA, sysctl과 Role별 Filesystem을 원본 순서대로 준비했습니다.
>
> 하지만 Node를 준비했다고 Kubernetes Cluster가 만들어진 것은 아닙니다.
>
> 이제 Kubespray가 실제로 **어느 Host를 어떤 Role로 구성할지, API Endpoint와 Pod·Service Network를 무엇으로 만들지, 어떤 Registry와 Kubernetes Version을 사용할지** 입력 파일에 표현해야 합니다.
>
> 그래서 오늘 원본은 먼저 `3-1. Ansible Playbook 배포 환경 설정`으로 시작합니다.
>
> `3-1`이 끝나면 `3-2`에서 그 파일을 실제로 읽어 Cluster를 만듭니다. 그리고 Playbook이 끝난 뒤 바로 오후 검증으로 뛰지 않고, 원본 `3-3`의 kubeconfig·kubectl·ETCD Backup·정리 작업을 수행합니다.
>
> 즉 오늘 오전에는 **입력을 먼저 확정하고 실제 배포를 실행한 뒤, 배포 직후 필요한 후속 설정까지 순서대로 완료**합니다.

# 2. 원본 3-1 — Ansible Playbook 배포 환경 설정

> `3-1`에서는 Kubespray 실행 전에 현재 작업 Directory와 Ansible 설정, 그리고 신규 Member Cluster 정보를 담을 설정 파일을 준비합니다.
>
> 여기서 파일이 존재한다는 사실보다 중요한 것은 **지금 실행할 Bundle의 파일이 오늘 신규 Member 실제값을 가리키는지**입니다.

## 2.1. 원본 3-1-1 — Ansible 설정 파일 준비

> 먼저 현재 Kubespray Directory로 이동합니다.

```bash
cd /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/DKS-Kubespray-v2.19/
```

> Directory 이름의 Version은 원본 예시입니다. 신규 Member에서는 현재 승인 Bundle 안의 실제 Kubespray Directory를 사용합니다.
>
> 그다음 `ansible.cfg`의 Host Key Checking 설정을 확인합니다.

```bash
cat ansible.cfg | grep host_key
```

> 원본의 기대 형태는 다음과 같습니다.

```text
host_key_checking=False
```

> Ansible은 기본적으로 SSH Host Key를 확인합니다. 이 기능은 처음 보는 서버나 Host Key가 바뀐 서버에 접속할 때 사람이 확인할 기회를 줘서 잘못된 대상이나 중간자 공격을 막는 보호 장치입니다.
>
> 하지만 Kubespray로 여러 신규 Node를 자동 구성하는 환경에서는 새 Host마다 확인 Prompt가 발생하면 비대화식 자동화가 멈출 수 있습니다.
>
> 그래서 원본은 현재 Kubespray 실행환경에서 `host_key_checking=False`를 사용합니다.
>
> 다만 이 설정이 편리하다고 해서 대상 확인이 필요 없어진 것은 아닙니다. Host Key 확인을 약화시키는 대신 **8/31에 확인한 Hostname·IP와 오늘 `hosts.yaml`의 대상이 같은 신규 Member인지 더 엄격하게 대조**해야 합니다.
>
> 여기서 확인할 것은 시스템 전체의 어떤 `ansible.cfg`가 아니라 **지금 `cluster.yml`을 실행할 Kubespray Directory의 설정**입니다.
>
> Ansible 설정을 확인했으면 이제 원본 `3-1-2`에서 실제 Cluster 입력을 구성합니다.

## 2.2. 원본 3-1-2 — Kubespray 설정 파일 구성

> 원본은 신규 Cluster 정보를 하나의 파일에 전부 몰아넣지 않습니다.
>
> Host와 Role은 `hosts.yaml`, Cluster 공통 Network와 VIP는 `dks_vars.yml`, Offline Registry는 `offline.yml`, Kubernetes Version은 `k8s-cluster.yml`에서 확인합니다.
>
> 따라서 이 네 종류를 하나의 “Inventory 값”으로 뭉뚱그리지 않고 원본 순서대로 확인합니다.

### 2.2.1. 원본 3-1-2의 1 — 노드 Hostname/IP 설정, `hosts.yaml`

> 먼저 Kubespray가 어느 서버를 대상으로 작업할지 정의합니다.

```bash
vi inventory/dks/hosts.yaml
```

> 실행 전에는 바로 수정하기보다 현재 파일을 먼저 읽어 신규 Member 값과 대조합니다.

```bash
cat inventory/dks/hosts.yaml
```

> `hosts.yaml`에는 크게 두 영역이 있습니다.
>
> `all.hosts`는 각 Host의 접속 주소와 Kubernetes 내부에서 사용할 주소를 정의하고, `children`은 그 Host가 어떤 Kubernetes Role Group에 들어가는지를 정의합니다.
>
> 먼저 각 Host에서 주로 확인하는 필드는 다음과 같습니다.

```yaml
<hostname>:
  ansible_host: <Management IP>
  ip: <Node IP>
  access_ip: <접근 IP>
```

> `ansible_host`는 Ansible이 해당 Host에 접속할 때 사용하는 주소입니다.
>
> `ip`와 `access_ip`는 Kubespray Role과 Network 구성에서 참조되는 Node 주소입니다.
>
> Xi'an의 일반적인 구조에서는 같은 Management IP가 들어갈 수 있지만, 값이 같다고 세 필드의 의미가 같은 것은 아닙니다. 현재 Bundle과 신규 Member 설계를 기준으로 확인합니다.
>
> 그다음 `children`에서 Role Group을 봅니다.

```text
kube_control_plane
etcd
router_node
infra_node
worker/system 계열 실제 Group
kube_node
k8s_cluster
```

> Master는 `kube_control_plane`에 들어가고, External ETCD Node는 `etcd` Group에 들어갑니다.
>
> Router와 Infra, Worker 계열 Node도 현재 신규 Member 설계에 맞는 Group에 들어가야 합니다.
>
> 여기서 중요한 것은 Host가 파일 안에 존재하는지가 아닙니다. **같은 Host가 어느 Group에 들어가느냐에 따라 Kubespray가 적용하는 Role과 Task가 달라집니다.**
>
> 예를 들어 Master Hostname과 IP가 정확해도 `kube_control_plane` Group에서 빠지면 Control Plane Role을 기대대로 구성할 수 없습니다.
>
> 반대로 Worker가 잘못된 Role Group에 들어가면 SSH와 Ansible 연결은 성공하면서도 의도하지 않은 Kubernetes Role로 설치될 수 있습니다.
>
> Role Group에 `node_labels`와 `node_taints`가 있다면 이것도 같이 확인합니다.

```yaml
node_labels:
  node-type: "<role>"

node_taints:
  - "node-role.kubernetes.io/<role>:NoSchedule"
```

> Label은 이후 Workload 배치와 Component 배치 기준으로 사용될 수 있고, Taint는 일반 Pod가 해당 Role Node에 임의로 배치되지 않도록 제한하는 데 사용됩니다.
>
> 그래서 `hosts.yaml`은 단순 SSH Host 목록이 아니라 **Node Identity와 Role 설계를 Kubespray가 읽는 형태로 표현한 파일**입니다.
>
> 원본의 `khdks*`, `10.166.*`, Host Cluster `xadks*hm*`은 구조 참고값입니다. 신규 Member에는 8/31에 실제 확인한 Member Hostname과 IP를 넣습니다.
>
> `hosts.yaml`이 현재 신규 Member의 모든 Node와 Role을 정확하게 표현하면 다음 원본 항목인 External LB와 Cluster 공통값으로 넘어갑니다.

### 2.2.2. 원본 3-1-2의 2 — External LB 및 `dks_vars.yml`

> Node와 Role을 정했으면 그다음 Cluster 전체에서 공통으로 사용할 API Endpoint와 Network 값을 구성합니다.

```bash
vi inventory/dks/dks_vars.yml
cat inventory/dks/dks_vars.yml
```

> 원본에서 확인하는 주요 구조는 다음과 같습니다.

```yaml
apiserver_loadbalancer_domain_name: "<신규 Member VIP-A>"

loadbalancer_apiserver:
  address: <신규 Member VIP-A>
  port: 6443
  cluster_name: <신규 Member Cluster Name>

kube_service_addresses: <신규 Member Service CIDR>
kube_pods_subnet: <신규 Member Pod CIDR>
service_domain: <신규 Member Service Domain>
rhel_enable_repos: false
```

> 먼저 `apiserver_loadbalancer_domain_name`과 `loadbalancer_apiserver.address`는 Kubernetes API의 공통 진입점인 VIP-A와 연결됩니다.
>
> Master가 세 대여도 운영자와 Component가 각 Master IP를 따로 기억하는 것이 아니라 승인된 Load Balancer Endpoint를 기준으로 API에 접근할 수 있어야 합니다.
>
> `port: 6443`은 Kubernetes API Server의 HTTPS Port입니다.
>
> `cluster_name`은 이번에 만들 신규 Member Cluster를 식별하는 이름입니다. 기존 Host나 다른 Member Cluster의 이름을 복사하지 않습니다.
>
> 그다음 `kube_service_addresses`는 Kubernetes Service가 사용할 Virtual IP 범위입니다.
>
> `kube_pods_subnet`은 Pod Network가 사용할 주소 범위입니다.
>
> 두 CIDR은 목적이 다르며 현재 신규 Member 설계와 일치해야 합니다. 기존 Cluster CIDR을 복사하거나 서로 겹치는 값을 넣으면 YAML 문법이 정상이어도 잘못된 Network 설계를 가진 Cluster를 만들 수 있습니다.
>
> `service_domain`은 Kubernetes 내부 DNS의 Service 이름 영역과 연결됩니다.
>
> 그래서 이 값은 단순 문자열이 아니라 이후 CoreDNS와 Service Discovery가 사용하는 Cluster DNS 기준입니다.
>
> `rhel_enable_repos: false`는 현재 Offline/내부 Repository 기반 설치 정책과 연결됩니다. Kubespray가 외부 RHEL Repository를 임의로 Enable하지 않도록 현재 승인 정책을 따릅니다.
>
> 이 단계에서는 값이 채워져 있다는 것만 보지 않습니다. **8/31에 확인한 VIP-A·Cluster Name·Service CIDR·Pod CIDR·Domain과 한 항목씩 대조**합니다.
>
> Network와 API 입력이 끝났으면 다음 원본 항목에서 Image 공급 경로를 정합니다.

### 2.2.3. 원본 3-1-2의 3 — DKS Harbor Repository, `offline.yml`

> Xi'an은 Private Registry 기반 Offline 설치 환경입니다.
>
> 그래서 Kubespray가 필요한 Kubernetes Image를 어느 Registry에서 가져올지 `offline.yml`에 설정합니다.

```bash
vi inventory/dks/group_vars/all/offline.yml
cat inventory/dks/group_vars/all/offline.yml | grep registry_host:
```

> 확인할 형태는 다음과 같습니다.

```yaml
registry_host: "<신규 Member 승인 Registry Base>"
```

> 여기서 8/31 Node Pre-setting의 CA 배포와 연결해서 설명합니다.
>
> Node에 승인 CA가 배포됐다는 것은 Registry TLS를 신뢰할 준비를 한 것이고, `offline.yml`의 `registry_host`는 Kubespray가 실제로 **어느 Registry/Image 경로를 사용할지 지정하는 입력**입니다.
>
> 따라서 CA가 정상이어도 `registry_host`가 다른 Project나 과거 Version 경로를 가리키면 설치 중 Image Pull에서 실패하거나 잘못된 Image Set을 사용할 수 있습니다.
>
> 반대로 Registry 주소가 맞아도 Node가 그 Registry의 Certificate를 신뢰하지 못하거나 Network로 접근할 수 없으면 Image Pull은 실패합니다.
>
> 원본의 `xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a`는 과거 확인값이므로 신규 Member의 현재 승인 Registry와 Bundle 기준을 다시 확인합니다.
>
> Registry를 확인했으면 마지막으로 설치할 Kubernetes Version을 재확인합니다.

### 2.2.4. 원본 3-1-2의 4 — Kubernetes Version 재확인

```bash
cat inventory/dks/group_vars/k8s_cluster/k8s-cluster.yml | grep kube_version:
```

> 원본 예시는 다음 형태입니다.

```yaml
kube_version: <현재 승인 Kubernetes Version>
```

> Version은 숫자 하나를 맞추는 문제가 아닙니다.
>
> 현재 Kubespray Bundle, `dks-requirements.txt`의 Ansible 조합, Offline Registry의 Image Set과 설치할 Kubernetes Version이 같은 설치 기준으로 맞아야 합니다.
>
> 예를 들어 Registry는 과거 `v1.22.10` Image Set을 가리키는데 `kube_version`만 다른 Version으로 바꾸면 필요한 Image Tag나 Component Version이 맞지 않을 수 있습니다.
>
> 따라서 Version은 `k8s-cluster.yml` 한 줄만 보고 독립적으로 승인하지 않고 **현재 Bundle과 Registry Image Set의 승인 기준과 함께 확인**합니다.
>
> 여기까지가 원본 `3-1`입니다.

## 2.3. 교육 보강 — 원본 3-2 진입 직전 8/31 Preflight의 현재성만 재확인한다

>
> 그래서 새로 긴 실습을 반복하지 않고 다음만 다시 확인합니다.

```text
현재 Bastion이 어제 작업한 신규 Member Bastion과 같은가
현재 Kubespray Directory와 Bundle이 같은가
hosts.yaml이 오늘 신규 Member Host/Role/IP를 가리키는가
dks_vars.yml의 VIP·CIDR·Domain이 어제 승인값과 같은가
```

>
> Kubespray는 잘못된 입력을 진단만 하는 도구가 아니라 그 입력을 실제 여러 Node의 System 상태로 확대하는 자동화이기 때문입니다.

# 3. 원본 3-2 — Ansible Playbook 배포

> 이제 입력 확인이 끝났으므로 원본 `3-2`에서 실제 Kubernetes Cluster를 배포합니다.
>
> 여기부터는 설정 조회가 아니라 대규모 변경 작업입니다.

## 3.1. 원본 3-2-1 — Ansible Playbook 배포

> 원본 실행 명령은 다음 구조입니다.

```bash
ansible-playbook \
  -e @inventory/dks/dks_vars.yml \
  -i inventory/dks/hosts.yaml \
  --become \
  --become-user=root \
  cluster.yml
```

> `-i inventory/dks/hosts.yaml`은 어느 Host에 접속하고 그 Host가 어떤 Role인지 제공합니다.
>
> `-e @inventory/dks/dks_vars.yml`은 VIP-A, Cluster Name, Pod·Service CIDR, Domain 같은 신규 Member 공통값을 Playbook에 전달합니다.
>
> `cluster.yml`은 이 입력을 Kubespray의 Role과 Task에 연결해서 각 Node의 OS 준비, Container Runtime, Kubernetes Component와 Network 설정을 실제로 적용합니다.
>
> `--become --become-user=root`는 `dspaas`로 접속한 뒤 Package 설치, System File 변경, Service 제어처럼 Root 권한이 필요한 Task를 수행하기 위해 사용합니다.
>
> 같은 `cluster.yml`이라도 `hosts.yaml`과 `dks_vars.yml`이 달라지면 다른 Host와 다른 Network 값으로 Cluster를 만들 수 있습니다.
>
> 따라서 실행 명령 한 줄이 익숙하다는 이유로 안전하다고 판단하지 않습니다. **그 명령이 지금 읽는 파일 전체가 오늘 신규 Member 기준인지 확인한 뒤 실행**합니다.

### 3.1.1. 실행 중에는 Task 이름과 Host를 함께 본다

> Kubespray는 수많은 Role과 Task를 순서대로 실행합니다.
>
> 모든 Task가 모든 Node에서 실행되는 것은 아닙니다. 어떤 Task는 전체 Node에 적용되고, 어떤 Task는 Master나 ETCD, Router 같은 특정 Group에만 적용됩니다.
>
> 그래서 화면에서 단순히 오류 문자열만 찾지 않고 다음처럼 읽습니다.

```text
현재 어느 Role/Task인가
어느 Host에서 실행 중인가
결과가 ok / changed / skipped / failed / unreachable 중 무엇인가
같은 Task에서 다른 Host는 어떤 결과인가
```

> `ok`는 해당 Task가 요구한 상태를 변경 없이 만족했거나 정상 확인했다는 의미입니다.
>
> `changed`는 오류가 아니라 Ansible이 대상 Host 상태를 원하는 상태로 바꿨다는 의미입니다.
>
> `skipped`도 조건에 따라 그 Host에서 실행할 필요가 없어 건너뛴 것일 수 있으므로 그 자체를 실패로 판단하지 않습니다.
>
> 반면 `FAILED`와 `UNREACHABLE`은 원인을 확인해야 합니다.

### 3.1.2. UNREACHABLE이면 Kubernetes보다 연결 단계부터 본다

> `UNREACHABLE`은 Ansible이 원격 Host에서 정상적으로 Task를 시작할 수 없는 상태입니다.
>
> 먼저 `hosts.yaml`의 Hostname과 IP가 현재 신규 Member와 맞는지 확인합니다. 그다음 Bastion에서 해당 IP/Hostname까지 도달 가능한지 보고 SSH 연결을 확인합니다. SSH가 된다면 `dspaas` Account와 Key를 확인하고, 마지막으로 Ansible이 원격 Python을 실행할 수 있는지 봅니다.
>
> 아직 원격 Task 자체를 시작하지 못한 것이므로 Package, kubelet, CNI 같은 Kubernetes 설정부터 수정하지 않습니다.

### 3.1.3. FAILED이면 실패 Task가 하려던 일을 본다

> `FAILED`는 대상 Host에 도달해 Task를 수행하기 시작했지만 해당 작업을 완료하지 못한 것입니다.
>
> Package Task라면 Repository·Package·Dependency를 보고, Registry/Image Task라면 Registry·CA·Image Path를 봅니다.
>
> Service Task라면 해당 Service와 바로 앞 Config·Package·Certificate Task가 정상인지 확인합니다.
>
> Become 실패라면 SSH가 아니라 같은 `dspaas` Session의 sudo/Become 조건을 봅니다.

### 3.1.4. 뒤에 오류가 많아도 최초 실패부터 찾는다

> 한 앞선 실패가 뒤 Task의 연쇄 실패를 만들 수 있습니다.
>
> 먼저 최초 실패 Host를 찾고, 그 Host에서 처음 실패한 Task와 오류 원문을 읽습니다. 그다음 같은 Host의 직전 성공 Task를 확인하고, 같은 Role의 다른 Host 결과와 비교합니다. 이렇게 해서 특정 Host 문제인지 공통 문제인지 범위를 좁힌 뒤 마지막에 `PLAY RECAP`으로 전체 영향 범위를 확인합니다.
>
> `PLAY RECAP`은 Host별 전체 실행 결과를 요약해 줍니다.
>
> 하지만 `failed=10`이라고 원인이 열 개인 것은 아닙니다. 원인은 최초 실패 위치와 오류 원문에서 찾고, RECAP은 영향 범위를 확인하는 데 사용합니다.

### 3.1.5. 재실행은 현재 부분 적용 상태를 확인한 뒤 결정한다

> Kubespray가 중간에 실패하면 그전 Task에서 일부 Node 상태는 이미 변경됐을 수 있습니다.
>
> 그래서 실패했다고 무조건 모든 Node를 Reset하거나, 반대로 `ignore-errors`, `skip-tags`, 임의 `limit`로 오류만 피하지 않습니다.
>
> 먼저 실패 지점과 현재 부분 적용 상태를 확인하고, 원인을 해결한 뒤 승인된 Runbook 범위에서 재실행합니다.
>
> 목표는 Playbook 화면을 끝까지 지나가게 만드는 것이 아니라 **필요한 Kubernetes 상태가 일관되게 적용되도록 하는 것**입니다.

## 3.2. 원본 3-2-1 마지막 — Playbook 완료 후 Master에서 최초 Cluster 상태를 확인한다

> 원본은 Playbook이 성공하면 Master Node 중 하나에 접속해 Kubernetes Cluster가 최소한 응답하는지 확인합니다.
>


>
> Node 목록이 모두 보여도 이것만으로 오후 검증까지 끝난 것은 아닙니다.

>
> 따라서 여기서는 “Kubernetes Cluster 전체 정상”이라고 하지 않고 **Playbook 완료 후 API와 Node 조회가 가능한 초기 상태**라고 기록합니다.

# 4. 원본 3-3 — 클러스터 후속 설정

## A. 관리 접근 및 CLI 환경 준비

> 먼저 Master의 운영 Account와 Bastion에서 Cluster를 관리할 수 있는 경로를 만들고, 그 관리 환경을 실제 운영에 사용할 수 있게 정리합니다.

## 4.1. 원본 3-3-1 — `.kube/config` 설정

> Kubespray 배포 후 Master의 root 계정에는 Kubernetes API에 접근할 kubeconfig가 생성됩니다.
>
> 하지만 실제 운영에서 계속 root Session만 사용할 수는 없습니다.
>
> 그래서 원본은 Master의 `dspaas` 사용자도 자신의 `~/.kube/config`를 사용해 `kubectl`을 실행할 수 있도록 구성합니다.

### 4.1.1. Master의 `dspaas` Home에 `.kube` Directory를 만든다

```bash
mkdir -p ~/.kube
chmod 700 ~/.kube
```

> `.kube`는 사용자별 Kubernetes Client 설정을 저장할 Directory입니다.
>
> Directory Permission을 제한하는 이유는 그 안의 kubeconfig에 Cluster Endpoint와 인증정보가 포함될 수 있기 때문입니다.

### 4.1.2. root kubeconfig를 확인하고 `dspaas`로 복사한다

```bash
sudo ls -al /root/.kube/config
sudo cp /root/.kube/config /app/dspaas/.kube/config
sudo chown dspaas:dspaas /app/dspaas/.kube/config
chmod 600 /app/dspaas/.kube/config
```

> 먼저 Source인 `/root/.kube/config`가 실제로 존재하는지 확인합니다.
>
> 그다음 `dspaas` Home의 `.kube/config`로 복사하고 소유권을 `dspaas`로 변경합니다.
>
> 파일 내용을 화면이나 문서에 그대로 출력해 Credential이나 Client Certificate Data를 노출하지 않습니다.
>
> kubeconfig는 단순 환경 파일이 아니라 **어느 Cluster API에 어떤 Context와 인증정보로 접속할지 정의하는 Client 접속 기준**입니다.

### 4.1.3. `dspaas`로 실제 `kubectl`을 확인한다

```bash
kubectl get nodes
```

> root에서 성공했던 명령이 `dspaas`에서도 성공해야 합니다.
>
> 이것은 root의 kubeconfig와 권한이 정상이라는 결과를 일반 운영 Account의 성공으로 확대하지 않기 위해서입니다.
>
> `dspaas`의 `kubectl get nodes`가 성공하면 해당 Master에서 `dspaas`가 현재 kubeconfig를 사용해 API를 조회할 수 있는 상태입니다.

## 4.2. 원본 3-3-2 — Kubernetes API 연결 확인

> 원본은 Master의 `dspaas`와 root 두 계정에서 각각 `kubectl`을 실행해 API 통신을 확인합니다.

```bash
# dspaas
kubectl get nodes

# root
sudo su - root
kubectl get nodes
```

> 같은 Master에서 두 Account 모두 조회가 가능하면 각자의 kubeconfig와 실행 환경이 정상이라는 것을 확인할 수 있습니다.
>
> 하지만 `kubectl get nodes` 한 번으로 Control Plane 전체, DNS, CNI, ETCD 기능까지 검증된 것은 아닙니다.
>
> 여기서는 **후속 설정에 필요한 API 기본 접근이 성립**했다고 판단하고 다음 Bastion `kubectl` 구성으로 넘어갑니다.

## 4.3. 원본 3-3-3 — Bastion `kubectl` 설치

> 운영자는 매번 Master에 SSH해서만 Cluster를 관리하지 않습니다.
>
> Bastion이 설치와 운영의 기준점이므로 Bastion에서도 `kubectl`을 실행할 수 있도록 구성합니다.

### 4.3.1. 현재 Bundle의 `kubectl` Binary를 확인한다

```bash
cd /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/
ls
```

> Bundle 안에서 현재 Kubernetes Version과 맞는 `kubectl` Directory와 Binary를 확인합니다.
>
> 원본의 `kubectl-v1.22.10`을 신규 Member 현재 Version으로 가정하지 않습니다.

```bash
cd <현재 Bundle의 kubectl Directory>
ls -l kubectl
```

### 4.3.2. Bastion PATH에 Binary를 배치한다

```bash
sudo cp -rp kubectl /usr/local/bin/kubectl
sudo chmod 755 /usr/local/bin/kubectl
```

> Binary를 `/usr/local/bin`에 두면 Bastion의 일반 Shell에서 `kubectl`을 PATH로 실행할 수 있습니다.
>
> 하지만 Binary가 설치됐다고 Cluster에 접속할 수 있는 것은 아닙니다.

### 4.3.3. kubeconfig가 없을 때의 실패를 이해한다

```bash
kubectl get nodes
```

> kubeconfig가 없는 상태에서는 `localhost:8080 refused`와 같은 오류가 발생할 수 있습니다.
>
> 이것은 `kubectl` Binary 설치 실패가 아니라 **Client가 어느 Kubernetes API에 어떤 인증으로 접속해야 하는지 설정되지 않은 상태**라는 의미입니다.
>
> 그래서 다음으로 Bastion의 `dspaas`와 root용 `.kube` Directory를 만들고 Master의 kubeconfig를 가져옵니다.

### 4.3.4. Bastion의 kubeconfig Directory를 준비한다

```bash
mkdir -p /app/dspaas/.kube
chmod 700 /app/dspaas/.kube

sudo mkdir -p /root/.kube
sudo chmod 700 /root/.kube
```

### 4.3.5. 신규 Member Master의 kubeconfig를 Bastion으로 가져온다

> 원본의 `ma01` Alias를 그대로 가정하지 않고 현재 신규 Member Master Hostname을 사용합니다.

```bash
ssh <신규 Member Master 1> cat /app/dspaas/.kube/config > /app/dspaas/.kube/config
chmod 600 /app/dspaas/.kube/config
```

> 필요하면 승인된 방식으로 root용 kubeconfig도 구성합니다.
>
> kubeconfig를 복사할 때 화면에 내용을 출력하거나 교육 증적에 원문을 저장하지 않습니다.

### 4.3.6. Bastion에서 실제 API 조회를 확인한다

```bash
kubectl get nodes
```

> 이제 같은 `kubectl` Binary가 Master가 아니라 Bastion에서 실행되고, Bastion의 kubeconfig를 통해 신규 Member API에 접근합니다.
>
> 이 성공은 **Bastion이 신규 Member Cluster의 기본 관리 Client로 동작할 수 있는 상태**라는 뜻입니다.

## 4.4. 원본 3-3-4 — `kubectl` 자동 완성 및 별칭 설정

> 원본은 반복적인 Kubernetes 운영을 위해 Bash Completion과 Alias를 설정합니다.
>
> 예시는 다음과 같습니다.

```bash
alias k=kubectl
complete -F __start_kubectl k
source <(kubectl completion bash)
alias kc=kubectl
complete -F __start_kubectl kc
source <(kubectl completion bash)
```

> 원본은 `k`와 `kc` 두 Alias를 모두 예시로 구성합니다. 현재 운영 표준에서 실제 사용할 Alias를 확인해 적용하되, 원본에 있는 설정 항목 자체를 생략하지 않습니다.
>
> `.bashrc`에 반영했다면 현재 Shell에도 적용합니다.

```bash
source ~/.bashrc
k get nodes
```

> 여기서는 Alias 자체가 중요한 것이 아니라 **설정 후에도 실제 `kubectl` 기능이 동일하게 동작하는지** 확인합니다.
>
> CLI 기본 환경이 준비됐으면 다음 원본 단계에서 ETCD Backup을 구성합니다.

## B. 장애 복구 준비

> 관리 경로가 준비됐다고 장애 복구 수단까지 생긴 것은 아닙니다. 원본은 다음으로 ETCD Local Snapshot과 Bastion Reserve Copy를 구성해 Cluster 상태를 복구할 수 있는 보호 수단을 마련합니다.

## 4.5. 원본 3-3-5 — ETCD 백업 스크립트 구성

> Kubernetes의 Object와 Cluster 상태는 ETCD에 저장됩니다.
>
> 그래서 Control Plane 전체 장애나 잘못된 상태 변경에 대비하려면 ETCD 데이터를 복구할 수 있는 Snapshot이 필요합니다.
>
> 원본은 각 ETCD Node에서 정기 Snapshot을 만들고, 추가로 Bastion에 Reserve Copy를 보관하는 두 단계 구조를 사용합니다.
>
> **ETCD Node의 Local Snapshot과 Bastion Reserve는 같은 백업이 아닙니다.** Local Snapshot이 생성되는 것과 다른 Node로 별도 복사본을 확보하는 것은 서로 다른 보호 단계입니다.

### 4.5.1. ETCD Node 1에 접속한다

```bash
ssh <신규 Member ETCD 1>
```

> 실제 신규 Member ETCD Hostname을 사용합니다.

### 4.5.2. Backup Directory와 Script를 준비한다

```bash
mkdir -p /app/dspaas/etcd_backup
vi /app/dspaas/etcd_backup/etcd_backup.sh
chmod +x /app/dspaas/etcd_backup/etcd_backup.sh
```

> Script에는 현재 Hostname을 기준으로 Snapshot File 이름을 만들고 `etcdctl snapshot save`를 수행하는 흐름이 들어갑니다.
>
> 원본 구조는 다음과 같습니다.

```bash
#!/bin/bash

Hostname=$(hostname)
backup_file_name=${Hostname}_etcd_backup_$(date +'%Y%m%d%H%M').dump

sudo ETCDCTL_API=3 /usr/local/bin/etcdctl \
  --endpoints=https://${Hostname}:2379 \
  --cacert=/etc/ssl/etcd/ssl/ca.pem \
  --cert=/etc/ssl/etcd/ssl/ca.pem \
  --key=/etc/ssl/etcd/ssl/ca-key.pem \
  snapshot save /app/dspaas/etcd_backup/${backup_file_name}

sudo chown dspaas:dspaas /app/dspaas/etcd_backup/${backup_file_name}
find /app/dspaas/etcd_backup -name '*_etcd_backup_*.dump' -mtime +30 -delete
```

> [!warning] 원본 Certificate 사용 방식 확인 필요
> 원본 `3-3-5`의 Snapshot 예시는 위와 같이 `ca.pem`과 `ca-key.pem`을 `--cert`, `--key`에 사용합니다. 반면 같은 원본의 뒤 `3-4-3` ETCD 상태 검증에서는 `admin-<hostname>.pem`과 `admin-<hostname>-key.pem`을 Client 인증서로 사용합니다.
>
> 따라서 이 차이를 대본에서 임의로 하나의 방식으로 고쳐 쓰지 않습니다. **실행 전 현재 Bundle의 ETCD Backup Script와 신규 Member의 실제 Client 인증서 정책을 확인하고, 승인된 Script를 사용합니다.** 원본 예시를 그대로 실행할지 여부는 이 확인이 끝난 뒤 결정합니다.
>
> Private Key의 내용 자체는 출력하거나 문서에 저장하지 않습니다.
>
> `snapshot save`는 현재 ETCD 데이터를 Snapshot File로 저장합니다.
>
> 그다음 소유권을 `dspaas`로 맞추고, 원본 기준 보존기간을 초과한 오래된 Snapshot을 정리합니다.

### 4.5.3. Script를 수동으로 먼저 실행한다

```bash
sh /app/dspaas/etcd_backup/etcd_backup.sh
ls -al /app/dspaas/etcd_backup/
```

> Cron부터 등록하지 않고 수동 실행을 먼저 하는 이유는 Script 자체와 Endpoint·Certificate가 실제로 동작하는지 먼저 확인하기 위해서입니다.
>
> 완료 기준은 단순 Return Code가 아니라 **실제 `.dump` Snapshot File이 생성되고 파일 크기가 0이 아니며 `etcdctl`이 Snapshot 저장 완료를 반환하는 것**입니다.

### 4.5.4. 매일 06:00 Cron을 등록한다

```bash
crontab -e
```

```cron
0 6 * * * /app/dspaas/etcd_backup/etcd_backup.sh
```

> Cron Line이 등록됐다는 것과 실제 Script가 정상이라는 것은 다릅니다. 그래서 앞에서 반드시 수동 시험을 먼저 했습니다.
>
> 같은 절차를 ETCD Node 2와 3에도 수행합니다.

### 4.5.5. Bastion Reserve Directory와 Script를 준비한다

> 각 ETCD Node에 Snapshot이 있어도 해당 ETCD VM 자체를 잃으면 Local Backup도 함께 잃을 수 있습니다.
>
> 그래서 원본은 Bastion에 Reserve Copy를 추가로 보관합니다.

```bash
# Bastion
mkdir -p /app/dspaas/etcd_backup
vi /app/dspaas/etcd_backup/etcd_backup_reserve.sh
chmod +x /app/dspaas/etcd_backup/etcd_backup_reserve.sh
```

> Reserve Script는 현재 신규 Member의 ETCD Host 목록을 기준으로 각 Node의 최신 Snapshot을 Bastion 하위 Directory로 복사하는 구조입니다.
>
> [!warning] 원본 Reserve Script 예시 주의
> 원본 예시에는 `for etcd in {% for host in groups['etcd'] %}{{ host }} {% endfor %}` 같은 Jinja Template 표현이 Shell Script 안에 그대로 남아 있고, `backup_file_name` 정의도 주석 처리된 상태에서 뒤에서 참조됩니다. 즉 원본 예시 자체가 그대로 실행 가능한 완성 Shell Script라고 단정하면 안 됩니다.
>
> 따라서 원본 예시를 그대로 실행하지 않습니다. **현재 승인 Bundle에 실제 렌더링된 Reserve Script가 있는지 먼저 확인하고, 없다면 현재 신규 Member ETCD 목록과 파일명 규칙을 기준으로 승인된 실행본을 검수한 뒤 사용합니다.**
>
> Script는 먼저 ETCD Node별 Bastion 보관 Directory가 있는지 확인하고 없으면 생성합니다. 그다음 각 ETCD Node의 Snapshot File을 `scp`로 복사하고, 마지막으로 Bastion에 오래 남은 Reserve Snapshot을 보존기간 기준으로 정리합니다.

### 4.5.6. Reserve Script도 수동 시험한다

```bash
sh /app/dspaas/etcd_backup/etcd_backup_reserve.sh
find /app/dspaas/etcd_backup -maxdepth 2 -type f -name '*_etcd_backup_*.dump' -ls
```

> 세 ETCD Node의 Snapshot이 각각 Bastion에 복사됐는지 확인합니다.
>
> 한 Node의 Snapshot만 복사된 상태로 전체 Backup이 완료됐다고 판단하지 않습니다.

### 4.5.7. 매일 06:30 Reserve Cron을 등록한다

```cron
30 6 * * * sh /app/dspaas/etcd_backup/etcd_backup_reserve.sh
```

> 원본은 각 ETCD Node의 06:00 Local Backup 이후 Bastion이 06:30에 Reserve Copy를 수행하도록 순서를 둡니다.
>
> 그래서 Reserve가 실행될 때 먼저 각 ETCD Node에 당일 Snapshot이 존재해야 합니다.
>
> ETCD Backup 구성까지 끝나면 원본 마지막 후속 설정인 불필요 파일 정리로 넘어갑니다.

## C. 설치 후 보안·잔여 파일 정리

> 마지막은 Kubernetes 기능을 추가하는 단계가 아니라, Kubespray 설치 과정에서 남을 수 있는 불필요한 Backup/Temporary 파일을 확인하고 정리해 배포 후 Node 상태를 마감하는 작업입니다.

## 4.6. 원본 3-3-6 — 불필요한 `hosts`/`passwd` 파일 삭제

> Kubespray 실행 중 `/etc` 아래에 Backup/Temporary 형태의 `hosts.<숫자...>` 파일이나 `passwd-` 계열 파일이 생성될 수 있습니다.
>
> 원본은 이 파일들이 불필요하게 남아 있고 Permission이 넓을 경우 보안상 문제가 될 수 있어 조회한 뒤 삭제합니다.
>
> 이 단계는 삭제 작업이므로 Pattern만 보고 바로 지우지 않습니다. 먼저 조회 결과를 확인해 실제 삭제 대상인지 판단하고, 확인된 파일만 삭제한 뒤 같은 조건으로 다시 조회해 정리 결과를 확인합니다.

### 4.6.1. `/etc/hosts` Garbage File을 먼저 조회한다

```bash
cd /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/ansible/

ansible all -i inventory -m shell \
  -a "sudo find /etc/ -type f -name 'hosts.[[:digit:]]*'" \
  --become --become-user=root
```

> 여기서 사용하는 `inventory`는 8/31 Node Pre-setting에서 사용한 SCS Stack의 Ansible Inventory입니다.
>
> 조회 결과가 실제 원본이 말하는 Kubespray 잔여 Backup 파일인지 확인합니다.
>
> 정상 `/etc/hosts` 자체를 삭제 대상으로 취급하지 않습니다.

### 4.6.2. 확인된 Garbage File만 삭제한다

```bash
ansible all -i inventory -m shell \
  -a "sudo find /etc/ -type f -name 'hosts.[[:digit:]]*' -exec rm -f {} \;" \
  --become --become-user=root
```

### 4.6.3. 삭제 후 다시 조회한다

```bash
ansible all -i inventory -m shell \
  -a "sudo find /etc/ -type f -name 'hosts.[[:digit:]]*'" \
  --become --become-user=root
```

> 출력이 없으면 해당 Pattern의 잔여 파일이 정리됐는지 확인할 수 있습니다.

### 4.6.4. `/etc/passwd-` 계열도 같은 순서로 처리한다

> 먼저 조회합니다.

```bash
ansible all -i inventory -m shell \
  -a "sudo find /etc/ -type f -name 'passwd-*'" \
  --become --become-user=root
```

> 여기서 `/etc/passwd` 본 파일과 삭제 대상 Backup/잔여 파일을 반드시 구분합니다.
>
> 원본 Pattern과 현재 실제 출력이 의도한 잔여 파일임을 확인한 뒤 삭제합니다.

```bash
ansible all -i inventory -m shell \
  -a "sudo find /etc/ -type f -name 'passwd-*' -exec rm -f {} \;" \
  --become --become-user=root
```

> 마지막으로 다시 조회합니다.

```bash
ansible all -i inventory -m shell \
  -a "sudo find /etc/ -type f -name 'passwd-*'" \
  --become --become-user=root
```

> 이 단계의 완료 기준은 삭제 명령의 `CHANGED`가 아니라 **삭제 대상으로 확인한 잔여 파일이 실제로 더 이상 조회되지 않는 것**입니다.
>
> 여기까지가 원본 `3-3`의 마지막입니다.

# 6. 문제가 생기면 현재 원본 단계에서 처음 실패한 지점부터 본다

> `3-1-1`에서 현재 Kubespray Directory나 `ansible.cfg`가 다르면 `cluster.yml`을 실행하지 않습니다.
>
> `hosts.yaml`의 Hostname/IP/Role이 실제 VM과 다르면 Ansible Ping 성공 여부보다 먼저 입력을 고칩니다.
>
> `dks_vars.yml`의 VIP·CIDR·Domain이 미확정이면 Playbook 오류로 값을 확인하려 하지 않습니다.
>
> `offline.yml` Registry가 잘못됐으면 Node의 CA부터 다시 만들지 않고 현재 승인 Registry와 파일 입력을 먼저 대조합니다.
>
> `cluster.yml` 실행 중 `UNREACHABLE`이면 Host/Network/SSH/Account를 먼저 보고, `FAILED`이면 해당 Task가 하려던 작업과 직전 성공 Task를 봅니다.
>
> Playbook은 성공했지만 Master의 `kubectl get nodes`가 실패하면 `3-3`으로 넘어가기 전에 root kubeconfig와 API 기본 접근부터 확인합니다.
>
> `3-3-1`에서 root는 되는데 `dspaas`만 실패하면 Cluster 전체 Network보다 `dspaas`의 `.kube/config`, Ownership, Permission과 Context를 먼저 봅니다.
>
> Bastion에서 `kubectl` Binary는 실행되는데 `localhost:8080` 오류가 나면 Binary 재설치보다 Bastion kubeconfig를 확인합니다.
>
> ETCD Backup이 실패하면 Cron부터 수정하지 않고 수동 Script의 Endpoint·Certificate·Permission과 Snapshot File 생성부터 확인합니다.
>
> Garbage File 정리는 조회 결과가 예상 Pattern과 다르면 삭제하지 않습니다. 삭제 대상의 실제 의미를 확인한 뒤 진행합니다.
