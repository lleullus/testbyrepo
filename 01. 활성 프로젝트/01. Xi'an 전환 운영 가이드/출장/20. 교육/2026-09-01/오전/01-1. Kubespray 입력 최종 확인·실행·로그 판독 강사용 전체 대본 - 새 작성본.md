# Kubespray 입력 최종 확인·실행·로그 판독 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 어제 신규 Member 입력과 Ansible Preflight를 확인해 `GO / BLOCKED`를 판정했다. 오늘 오전은 **GO의 현재성을 다시 확인하고 Kubespray를 실행하며, 실패하면 최초 실패 Host와 Task를 찾는 과정**이다.
>
> 실행 명령, 옵션과 재실행 범위는 승인된 Kubespray Runbook을 따른다. 실패를 숨기는 옵션을 사용하지 않고 Password·Private Key·Registry Credential·Token 원문을 화면과 증적에 남기지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
어제 실행 전 GO를 만들었다
→ 하지만 어제 상태가 오늘까지 유지됐다고 가정할 수 없다
→ 그래서 대상·입력·Bundle·연결·승인을 다시 확인한다
→ 현재성이 맞으면 Kubespray를 실행한다
→ Inventory와 변수에 적힌 내용을 Ansible이 Host별 Task로 풀어낸다
→ 로그에서는 각 Task가 어느 Host에서 어떤 결과를 냈는지 본다
→ 실패하면 최초 실패 Host와 Task를 찾는다
→ UNREACHABLE과 FAILED를 구분한다
→ 필요한 확인만 수행하고 최소 범위로 조치한다
→ 조치한 기능을 확인한 뒤 현재 부분 적용 상태를 보고 재실행한다
→ Playbook 성공 뒤에는 Kubernetes 기능을 별도로 검증한다
```

## 0-1. 오늘 전체 한 줄

> 오늘은 `cluster.yml`을 시험 삼아 실행하는 시간이 아닙니다. **검증된 입력으로 자동화를 실행하고, Ansible이 어느 Host에 어떤 작업을 수행했는지 읽으며, 실패하면 정확한 시작점을 찾아 안전하게 다음 판단을 만드는 시간**입니다.

# 1. 시작 — 어제 GO였어도 실행 직전 다시 확인한다

> 어제 Node·Role·IP와 VIP·CIDR·Domain·Registry·Version을 확인했고 Graph·Ping·Identity·Become·Syntax도 통과했습니다.
>
> 그래서 어제 작업 종료 시점에는 `cluster.yml`을 실행할 수 있는 입력과 실행 조건이 준비돼 있었습니다.
>
> **하지만 GO는 어제 시점의 결과입니다.** 밤사이 VM이 재기동되거나 Network 상태가 달라질 수 있고, Inventory나 변수 파일이 수정됐을 수도 있습니다. 작업 Directory나 Bundle이 달라졌거나 Registry의 Image 상태와 작업 승인 시간이 바뀌었을 수도 있습니다.
>
> 특히 Kubespray는 현재 파일에 적힌 값을 실제 Host 변경으로 확대합니다. 사람이 어제 어떤 값을 검증했는지를 기억해서 실행하는 것이 아니라, 실행 시점에 지정된 Inventory와 변수 파일을 읽습니다.
>
> 그래서 실행 직전에 현재 Bastion·Account·Bundle·Kubespray Directory, `hosts.yaml`과 주요 변수, Registry·Version, Ping·Identity·Become과 작업 승인 시간을 다시 확인합니다.
>
> 먼저 지금 접속해 있는 Bastion이 어제 Preflight를 수행한 Bastion과 같은지 확인합니다. 그다음 현재 Directory와 Bundle이 맞는지 보고, Inventory가 실제 신규 Member Node와 Role을 가리키는지 확인합니다.
>
> 또한 VIP-A·Pod CIDR·Service CIDR·Service Domain·Registry·Kubernetes Version처럼 Cluster 전체에 영향을 주는 값은 실행 전에 다시 확인합니다. 이런 값은 Playbook이 성공한 뒤 쉽게 되돌려 확인할 수 있는 단순 표시값이 아니라 실제 Cluster 구성을 만드는 입력입니다.
>
> 하나라도 달라졌다면 어제 GO였다는 이유로 실행하지 않습니다. 승인된 변경인지 확인하고 필수값이 미확정이면 `BLOCKED`로 돌아갑니다.
>
> 그리고 실행 전에 어느 신규 Member를 어느 Bastion·Account·Bundle·Inventory·변수로 설치하는지 다시 말로 설명할 수 있어야 합니다.
>
> `cluster.yml`은 지정한 입력을 검토만 하는 도구가 아니라 실제 변경으로 적용하는 도구이므로 대상과 입력이 다른 Cluster를 가리키면 실행하지 않습니다.

# 2. Kubespray를 승인된 명령으로 실행한다

> Kubespray는 한 개의 설치 Binary가 모든 Node에 동일한 작업을 수행하는 방식이 아닙니다.
>
> Ansible Inventory와 변수, 그리고 Kubespray의 Role과 Task를 이용해 각 Host의 역할에 필요한 상태를 순서대로 만듭니다.
>
> 그래서 같은 `cluster.yml`을 실행해도 Master, ETCD, Router, Infra, Worker에서 실제 수행되는 작업 범위는 서로 다를 수 있습니다.
>
> 먼저 `hosts.yaml`은 Ansible이 **어느 Host에 접속할지와 그 Host가 어떤 Role에 속하는지** 알려 줍니다.
>
> Master가 `kube_control_plane`에 포함되는지, ETCD Host가 `etcd` Group에 들어가는지, Router·Infra·Worker가 승인된 Group에 배치됐는지가 여기서 결정됩니다.
>
> 따라서 Host가 Inventory 안에 존재하는 것만으로 충분하지 않습니다. 실제 Role Group이 잘못되면 Ansible 연결은 성공해도 의도하지 않은 Kubernetes 역할로 구성될 수 있습니다.
>
> 그다음 `dks_vars.yml` 같은 변수 파일은 VIP-A, Cluster Name, Pod·Service CIDR과 Domain처럼 여러 Host가 공통으로 사용해야 하는 환경값을 제공합니다.
>
> 이런 값은 특정 Node 하나의 설정이 아니라 새 Cluster 전체의 기준으로 확대될 수 있습니다.
>
> 그래서 실행 직전에 값이 존재하는지만 보지 않고, 어제 승인한 신규 Member 값과 같은지를 다시 확인합니다.
>
> 또한 `offline.yml`과 Kubernetes Version 설정은 설치할 Software와 Image 공급 경로를 결정합니다.
>
> Node가 Registry에 접속할 수 있어도 현재 Bundle과 맞지 않는 Project나 Tag를 가리키면 설치 중 Image Pull이나 Component 구성에서 실패할 수 있습니다.
>
> 반대로 Registry 경로 하나가 맞아도 Kubespray Bundle과 Kubernetes Version, Image 세트가 서로 다른 기준이라면 같은 설치 세트라고 볼 수 없습니다.
>
> 실제 실행에서는 Inventory와 추가 변수, `cluster.yml`, Become 조건이 하나의 명령으로 연결됩니다.
>
> `-i`로 지정한 Inventory가 대상 Host와 Group을 제공하고, `-e`로 넘기는 변수 파일이 현재 신규 Member의 추가 환경값을 제공합니다.
>
> `cluster.yml`은 이 입력을 Kubespray의 Role과 Task에 연결해서 OS 준비, Package와 Binary 배치, Container Runtime, Kubernetes Component, Network 관련 구성을 각 대상 Host에 적용합니다.
>
> 그리고 `--become`은 일반 `dspaas` Account로 접속한 뒤 Package 설치나 System 파일 변경, Service 제어처럼 Root 권한이 필요한 Task를 수행하기 위해 사용합니다.
>
> 여기서 중요한 것은 `cluster.yml` 자체가 신규 Member를 식별하는 것이 아니라는 점입니다.
>
> 같은 Playbook이라도 다른 Inventory와 변수를 넘기면 다른 Host와 다른 Network 값으로 작업할 수 있습니다.
>
> 그래서 실행 명령 문자열 하나만 보고 안전하다고 판단하지 않고, 그 명령이 실제로 읽는 Inventory·변수·Directory·Bundle을 함께 확인합니다.
>
> 실제 명령과 추가 옵션은 Runbook을 따릅니다.
>
> `limit`, `skip-tags`, `start-at-task`, `ignore-errors` 같은 옵션은 현재 부분 적용 상태와 승인 범위를 확인하지 않고 사용하지 않습니다.
>
> 특히 실패 Task만 피하기 위해 `ignore-errors`나 임의의 Skip 범위를 추가하면 Playbook이 끝났다는 결과는 만들 수 있어도 필요한 Kubernetes 상태가 만들어졌다는 근거는 잃을 수 있습니다.
>
> 실행 전에 대상 Cluster, Bastion, Bundle, Inventory, Account, 시작 시각과 로그 위치를 남깁니다. Credential 원문은 제외합니다.
>
> 그리고 실행이 시작되면 화면에 출력되는 Task를 모두 조치 대상으로 보지 않고, Ansible이 현재 어느 Role과 Task를 수행하고 있는지 흐름을 먼저 봅니다.

# 3. 로그에서는 최초 실패를 찾는다

> Kubespray 로그에는 많은 Role과 Task가 있고 같은 Task가 여러 Host에서 반복됩니다.
>
> 어떤 Task는 모든 Node를 대상으로 하고, 어떤 Task는 Control Plane이나 ETCD 같은 특정 Group에서만 수행됩니다.
>
> 그래서 로그를 읽을 때는 단순히 오류 문자열을 찾는 것이 아니라 **어느 Task가 어느 Host에서 어떤 결과가 됐는지** 같이 봅니다.
>
> Ansible에서 자주 보이는 결과에는 `ok`, `changed`, `skipped`, `failed`, `unreachable`이 있습니다.
>
> `ok`는 해당 Task가 확인한 현재 상태가 이미 원하는 상태이거나 변경 없이 정상적으로 처리됐다는 뜻입니다.
>
> `changed`는 오류가 아니라 Ansible이 대상 Host의 상태를 원하는 상태로 변경했다는 뜻입니다. Package를 설치하거나 설정 파일을 변경하고 Service 상태를 조정하면 정상 실행 중에도 `changed`가 발생할 수 있습니다.
>
> `skipped`도 반드시 문제가 아닙니다. OS 종류, Role, 변수 조건이나 현재 상태에 따라 해당 Host에서 실행할 필요가 없는 Task라면 조건에 의해 건너뛸 수 있습니다.
>
> 그래서 `changed`가 많다는 이유로 불안정하다고 보거나 `skipped`가 있다는 이유로 설치 누락이라고 바로 판단하지 않습니다. 어떤 Task가 왜 해당 결과를 냈는지 문맥을 봅니다.
>
> 반면 `failed`와 `unreachable`은 정상 흐름이 중단된 원인을 확인해야 하는 상태입니다.
>
> **하지만 뒤쪽에 오류가 많이 보여도 앞의 한 실패가 연쇄 결과를 만들었을 수 있습니다.**
>
> 예를 들어 한 Node에서 Package 설치가 실패하면 그 Package를 전제로 하는 뒤 Task도 실패하거나 실행되지 않을 수 있습니다. Registry에서 Image를 받지 못했다면 이후 Service가 시작되지 않는 오류가 추가로 보일 수도 있습니다.
>
> 그래서 모든 오류 줄을 각각 다른 원인으로 보지 않습니다.
>
> 먼저 어느 Host의 어느 Task가 처음 비정상이었는지 확인합니다.
>
> 이때 Task 이름만 보지 않고 오류 원문도 같이 봅니다. 같은 Package Task라도 Repository 연결 실패, Package 미존재, Dependency 문제, 권한 문제는 조사 시작점이 다릅니다.
>
> 그다음 최초 실패 직전에 같은 Host에서 어떤 Task가 성공했는지 확인합니다.
>
> 직전 단계까지 무엇이 정상으로 확인됐는지를 알면 조사 범위를 좁힐 수 있습니다. SSH와 Fact 수집이 이미 성공했다면 처음부터 Network 전체를 의심할 필요가 없을 수 있습니다.
>
> 그리고 한 Host만의 문제인지, 같은 Role의 여러 Host인지, 전체 공통인지 봅니다.
>
> 한 Worker만 실패하고 같은 조건의 다른 Worker가 성공했다면 공통 Bundle보다 해당 Host의 상태 차이를 먼저 봅니다.
>
> 반대로 모든 Node에서 같은 Repository Task가 같은 오류로 실패한다면 Host 하나의 설정보다 공통 Repository·DNS·Network나 입력을 우선 확인할 수 있습니다.
>
> 마지막에는 PLAY RECAP에서 Host별 `ok`, `changed`, `unreachable`, `failed`, `skipped` 결과를 확인합니다.
>
> PLAY RECAP은 전체 실행 결과를 요약하는 화면입니다.
>
> 하지만 PLAY RECAP만으로 최초 원인을 알 수 있는 것은 아닙니다.
>
> `failed=20`이라고 원인이 스무 개인 것은 아니고, 뒤쪽의 여러 실패가 하나의 앞선 원인에서 이어졌을 수 있습니다.
>
> 따라서 전체 결과는 PLAY RECAP에서 보고, 원인은 최초 실패 Host·Task와 오류 원문에서 확인합니다.

# 4. UNREACHABLE과 FAILED는 의미가 다르다

> `UNREACHABLE`은 Ansible이 원격 Host에서 정상적으로 Task를 시작할 수 없었다는 뜻입니다.
>
> Ansible은 먼저 Inventory가 가리키는 Host로 연결하고, 지정된 Account와 인증 방식으로 원격 작업을 시작해야 합니다.
>
> 이 연결 단계가 성립하지 않으면 그 뒤의 Package 설치나 kubelet 설정 같은 Kubernetes 작업까지 가지 못합니다.
>
> 따라서 Inventory의 Hostname·IP, 이름 해석, Network, SSH, Account와 인증 경로를 먼저 확인합니다.
>
> 먼저 Inventory가 올바른 주소를 가리키는지 보고, 그다음 Bastion에서 실제 SSH가 되는지 확인합니다. SSH 자체가 되지 않는다면 Kubernetes 설정부터 변경하지 않습니다.
>
> 어제 Ping이 성공했다는 사실만으로 오늘 연결도 정상이라고 가정하지 않습니다. VM 재기동, Network 변경, SSH Service나 Key 상태가 달라졌을 수 있습니다.
>
> 반면 `FAILED`는 대상 Host에 도달해 Task를 시작했지만 그 Task가 요구한 작업이나 검증을 완료하지 못했다는 뜻입니다.
>
> 그래서 해당 Task가 무엇을 하려 했는지부터 봅니다.
>
> Package Task가 실패했다면 Repository와 Package 조건을 보고, Service Task가 실패했다면 Service와 그 Service가 필요로 하는 설정·파일·Dependency를 확인합니다.
>
> 파일 배치나 Template Task가 실패했다면 Source·Destination·권한·변수 렌더링을 확인하고, Registry 관련 Task라면 Network뿐 아니라 CA Trust와 Registry 경로까지 확인할 수 있습니다.
>
> 예를 들어 Package Task가 `FAILED`라면 Ansible은 해당 Host에 접속해 Package 작업을 시작할 단계까지 왔을 가능성이 큽니다.
>
> 그래서 이때 SSH Key부터 다시 만드는 것보다 Repository Metadata, OS Version, Package 이름이나 Dependency 조건을 먼저 보는 것이 순서에 맞습니다.
>
> 반대로 `UNREACHABLE`인데 Package Repository를 수정해도 Ansible이 Host에 접속하지 못하는 원인은 해결되지 않습니다.
>
> 또한 Become 단계의 실패는 SSH 실패와 다릅니다.
>
> 일반 Account로 접속은 됐지만 Root 권한이 필요한 Task를 수행하지 못한 것일 수 있습니다.
>
> 그래서 같은 `dspaas` Account에서 sudo 정책과 비대화식 Become 상태를 확인합니다. Root Account로 직접 접속한 성공을 같은 조건의 증거로 사용하지 않습니다.
>
> 결국 `UNREACHABLE`과 `FAILED`를 나누는 이유는 이름을 분류하기 위해서가 아니라 **조사 시작점을 잘못 잡지 않기 위해서**입니다.

---

# 5. Playbook 성공과 Kubernetes 정상은 다르다

> Return Code가 정상이고 PLAY RECAP에 미해결 `failed`와 `unreachable`이 없다면, 승인된 입력으로 자동화가 실행 오류 없이 끝났다는 것은 확인할 수 있습니다.
>
> 이것이 `PLAYBOOK EXECUTION PASS`입니다.
>
> 이 결과는 중요합니다.
>
> Inventory에 지정한 Host를 대상으로 Ansible이 필요한 Task 흐름을 끝까지 수행했고, Playbook 관점에서 미해결 실행 오류가 남지 않았다는 뜻입니다.
>
> 또한 정상적인 `changed`나 조건에 따른 `skipped`가 있더라도 그 자체는 실패가 아닙니다.
>
> **하지만 Kubernetes 기능 전체가 정상이라는 뜻은 아닙니다.**
>
> Playbook은 Kubernetes를 구성하기 위한 자동화입니다.
>
> 자동화가 오류 없이 끝났다는 것과 만들어진 Kubernetes Cluster의 실제 기능이 우리가 승인한 설계와 같다는 것은 별도로 확인해야 합니다.
>
> 예를 들어 kube-apiserver 관련 Task가 성공했어도 외부 VIP-A를 통해 실제 API에 접근할 수 있는지는 별도입니다.
>
> Node 관련 Task가 성공했어도 모든 Node가 기대한 Role과 Version으로 `Ready` 상태인지 확인해야 합니다.
>
> Pod CIDR과 Service CIDR 값이 설정 파일에 반영됐어도 실제 Cluster Network가 그 기준으로 동작하는지는 결과를 조회해야 합니다.
>
> 그래서 VIP-A API, 실제 Version·CIDR·Domain, Node Ready·Role과 Control Plane은 오후에 확인합니다.
>
> External ETCD도 별도입니다. Kubespray에서 ETCD 관련 Task가 완료됐다는 것과 실제 Member Control Plane이 승인된 External ETCD와 정상적으로 상태를 주고받는다는 것은 같은 확인이 아닙니다.
>
> Container Runtime, CNI, DNS와 Ingress도 각각 실제 기능 검증이 필요합니다.
>
> 따라서 오전의 성공 범위를 확대하지 않고 실행 입력과 로그를 오후 검증으로 넘깁니다.
>
> 오전에는 `Kubespray 자동화가 미해결 실행 오류 없이 완료됐다`까지 말하고, 오후에 실제 Kubernetes Control Path와 Application Path를 단계별로 확인합니다.

---

# 6. 문제가 생기면 현재 대상부터 순서대로 확인한다

> 실행 직전 대상이나 입력이 달라졌다면 Playbook 장애가 아니라 현재성 확인이 끝나지 않은 것입니다.
>
> 그래서 아직 실행하지 않았다면 입력을 바로잡고 다시 Preflight 기준을 확인합니다. 잘못된 값임을 알면서 Playbook을 실행해 오류 메시지로 설계를 확인하지 않습니다.
>
> 실행 중 문제가 발생했다면 먼저 최초 실패 Host와 Task를 찾습니다.
>
> `UNREACHABLE`이면 Inventory·DNS·Network·SSH를 확인합니다.
>
> Become 실패면 같은 Account의 sudo를 확인하고, Package 실패면 Repository·OS·Package 조건을 봅니다.
>
> Registry 관련 작업이면 Registry 주소뿐 아니라 Node의 DNS·Network·CA Trust와 실제 Image 경로를 확인합니다.
>
> Service가 시작되지 않았다면 Service 자체만 반복 재시작하지 않고 직전 Config·Package·Certificate·Dependency Task가 정상인지 같이 봅니다.
>
> 그리고 최초 실패 Host·Task와 직전 성공 Task를 확인합니다.
>
> 같은 Role의 정상 Host가 있다면 차이를 봅니다.
>
> 예를 들어 Master 세 대 중 한 대만 같은 Task에서 실패한다면 공통 Inventory 값보다 해당 Host의 Package, 파일, Network, 시간, Mount 같은 차이를 먼저 확인할 수 있습니다.
>
> 반대로 같은 Task가 전체 Node에서 같은 오류로 실패한다면 공통 Source와 변수를 우선 확인합니다.
>
> 오류 하나를 보고 여러 설정을 동시에 바꾸지 않습니다.
>
> SSH, Repository, CA, Kernel 설정을 한꺼번에 바꾸면 어떤 변경이 원인을 해결했는지 확인할 수 없고, 새로운 차이를 추가할 수 있습니다.
>
> 필요한 최소 변경만 Runbook에 따라 수행합니다.
>
> SSH를 조정했으면 SSH·Ping·Identity를 다시 확인합니다.
>
> sudo를 조정했으면 같은 Account에서 `sudo -n`이나 승인된 Become 검증을 다시 수행합니다.
>
> Repository를 조정했으면 Playbook부터 바로 다시 돌리지 않고 같은 Node에서 Repository Metadata와 필요한 Package 공급 경로를 먼저 확인합니다.
>
> Registry Trust를 조정했으면 Certificate 검증을 생략하지 않은 HTTPS나 승인된 Registry 확인 경로로 다시 검증합니다.
>
> 이렇게 조치한 기능이 정상으로 돌아왔다는 좁은 증거를 만든 뒤 재실행 여부를 결정합니다.
>
> 여기서 Kubespray가 Ansible 기반이라는 점도 중요합니다.
>
> Ansible Task는 많은 경우 현재 상태를 확인하고 원하는 상태와 다를 때만 변경하는 방식으로 작성됩니다. 그래서 이미 원하는 상태인 항목은 재실행 시 `ok`가 되고, 필요한 변경이 남아 있는 항목만 다시 `changed`가 될 수 있습니다.
>
> **하지만 이것이 원인을 확인하지 않고 `cluster.yml`을 계속 반복 실행해도 된다는 뜻은 아닙니다.**
>
> 실패하기 전까지 일부 Host와 Task는 이미 변경됐을 수 있습니다.
>
> Package가 설치됐거나 설정 파일이 생성되고 Service가 시작된 상태에서 뒤 Task가 실패했을 수 있습니다.
>
> 그래서 재실행 전에는 어디까지 성공했고 어느 Host가 어느 상태까지 적용됐는지 확인해야 합니다.
>
> 그다음 실패 원인을 조치하고, 조치한 기능이 정상이며 현재 부분 적용 상태에서 승인된 재실행이 가능한지를 봅니다.
>
> `--limit`, `--start-at-task`, `--tags`, `--skip-tags` 같은 범위 조정은 편리하지만, 현재 상태를 이해하지 않고 임의로 사용하면 앞에서 필요한 Task를 건너뛸 수 있습니다.
>
> 따라서 재실행 범위와 옵션은 Runbook과 현재 부분 적용 상태를 기준으로 결정합니다.
>
> 확인 순서는 `현재 대상 → 원격 도달 → Task 실행 → 최초 실패 → 직전 성공 → 필요한 확인 → 최소 조치 → 기능 재확인 → 부분 적용 상태 확인 → 승인된 재실행`입니다.

# 7. 오후에는 실행 결과와 입력을 함께 넘긴다

> 오후에는 단순히 "`cluster.yml` 성공했습니다"라고 넘기지 않습니다.
>
> 어느 Cluster·Stage인지, 어느 Bastion·Bundle·Inventory로 실행했는지 함께 넘깁니다.
>
> 그래야 오후에 조회되는 Kubernetes 결과가 오전에 실행한 입력과 같은 Cluster의 결과인지 연결해서 판단할 수 있습니다.
>
> 기대한 Kubernetes Version·VIP-A·Pod CIDR·Service CIDR·Service Domain과 Node Role·Hostname·IP도 전달합니다.
>
> 오후에는 이 값들이 실제 Kubernetes API와 Node·Cluster 설정에 반영됐는지 확인합니다.
>
> 따라서 오전 실행 입력이 없으면 오후에 보이는 값을 무엇과 비교해야 하는지 기준이 없어집니다.
>
> 실행 시각, Return Code, PLAY RECAP과 로그 위치를 함께 남깁니다.
>
> 정상 실행이라면 미해결 `failed`와 `unreachable`이 없었는지 확인할 수 있어야 합니다.
>
> `changed`와 `skipped`가 있었다면 그 자체를 오류로 기록하지 않고, 필요할 경우 어떤 Task에서 왜 발생했는지 로그를 통해 확인할 수 있도록 위치를 남깁니다.
>
> 재실행이 있었다면 최초 실패 Host와 Task, 오류 원문에서 확인한 원인, 수행한 조치와 좁은 재검증 결과를 전달합니다.
>
> 또한 전체 재실행인지 승인된 일부 범위 재실행인지도 남깁니다.
>
> 그래야 오후 검증에서 이상이 발견됐을 때 오전에 어느 단계가 한 번 실패했고 어떤 변경이 있었는지 추적할 수 있습니다.
>
> Password·Private Key·Token·Registry Credential 원문은 제외합니다.
>
> 로그나 화면에 Credential이 포함됐다면 그대로 교육 증적으로 전달하지 않습니다.
>
> 오후 검증은 이 입력과 실행 결과가 실제 Kubernetes 상태로 만들어졌는지 확인하는 단계입니다.

# 8. 마무리

> 어제 GO였어도 오늘 상태가 유지됐는지 다시 확인했습니다.
>
> 그래서 현재 Bastion·Bundle·Inventory·변수·Registry·Version과 연결·권한·승인 상태가 같은 신규 Member를 가리키는지 확인했습니다.
>
> 그다음 검증된 입력으로 Kubespray를 실행하고, Inventory와 변수가 Kubespray Role과 Task를 통해 각 Host의 실제 변경으로 확대되는 과정을 봤습니다.
>
> 로그에서는 `ok`, `changed`, `skipped`, `failed`, `unreachable`의 의미를 구분하고, 오류 개수보다 최초 실패 Host와 Task를 먼저 찾았습니다.
>
> `UNREACHABLE`과 `FAILED`의 조사 시작점을 구분하고, 최초 실패 직전까지 무엇이 성공했는지 확인한 뒤 필요한 사실만 좁혀 봤습니다.
>
> 문제가 있었다면 여러 설정을 동시에 바꾸지 않고 필요한 최소 변경을 수행했습니다.
>
> 그리고 조치한 기능을 먼저 검증하고 현재 부분 적용 상태를 확인한 뒤 승인된 범위로 재실행했습니다.
>
> Playbook이 정상 종료돼도 Kubernetes 전체 기능이 정상이라고 확대하지 않고, 오전에 사용한 입력·PLAY RECAP·로그와 재실행 이력을 오후 검증으로 넘겼습니다.
>
> **결국 오전의 완료는 명령이 끝난 상태가 아니라, 검증된 신규 Member 입력으로 Kubespray 자동화가 미해결 오류 없이 끝났고 그 실행 과정을 설명할 수 있으며, 오후에 실제 Kubernetes 결과를 검증할 수 있는 근거가 준비된 상태입니다.**

16. Ansible이 반복 실행 가능한 구조라는 것과 원인 확인 없이 계속 반복 실행하는 것은 왜 다른가?
17. 부분 적용 상태를 확인하지 않고 `--limit`, `--start-at-task`, `--skip-tags`를 사용하면 어떤 문제가 생길 수 있는가?

20. 오전 Kubespray 실행이 완료됐다고 말하려면 명령 종료 외에 무엇을 설명할 수 있어야 하는가?
