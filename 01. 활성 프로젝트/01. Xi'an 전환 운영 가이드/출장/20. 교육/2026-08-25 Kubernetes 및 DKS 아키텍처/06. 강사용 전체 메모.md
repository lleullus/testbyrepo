# Part 1. Kubernetes를 이해하기 전에

## 말할 순서

1. 서버 직접 운영
   - 적을 때는 가능
   - 많아지면 설치·복구·증설·Network·Storage 관리 증가
2. VM
   - OS 환경 분리·Template·증설 편리
   - Application 배포와 상태 유지 문제는 남음
3. Container
   - Image = 실행 원본
   - Container = 실제 실행
   - Runtime = 실행 소프트웨어
   - Registry = Image 저장소
4. Container 증가
   - 어느 서버?
   - 죽으면 재실행?
   - 몇 개 유지?
   - 통신과 외부 접근?
5. Kubernetes
   - 여러 서버를 Cluster로 관리
   - 배포·배치·연결·복구·확장

## 꼭 말할 핵심

> Container는 애플리케이션의 실행 단위이고, Kubernetes는 여러 서버에서 많은 Container를 원하는 상태로 유지하는 플랫폼입니다.

## 다음 연결

> 그러면 Kubernetes Cluster 안에서 실제로 누가 판단하고 누가 실행하는지 보겠습니다.

# Part 2. Kubernetes의 핵심 동작 원리

## 말할 순서

1. Cluster = 여러 Node와 구성요소를 하나로 관리
2. Control Plane = 요청·판단·조정
3. Worker = 실제 Pod 실행
4. Pod
   - Container 실행 기본 단위
   - 없어졌다 다시 생길 수 있음
   - Pod 하나보다 원하는 상태가 중요
5. API Server = 관리 요청 입구
6. Scheduler = 새 Pod를 실행할 Node 선택
7. Controller Manager
   - Desired 3 / Actual 2
   - 다시 3으로 조정
8. ETCD
   - Cluster 상태 저장
   - Application DB 아님
9. 생성 흐름
   - 요청 → API Server → 원하는 상태 → Scheduler → kubelet → 상태 비교
10. Worker
   - kubelet = Node의 Pod 상태 관리
   - containerd = 실제 Container 실행
11. 용량
   - Node 수만 보지 않음
   - CPU·Memory·Disk·Pod 요구량 같이 확인

## 꼭 말할 핵심

> Kubernetes의 핵심은 특정 Pod 하나를 유지하는 것이 아니라, 원하는 상태와 실제 상태를 계속 맞추는 것입니다.

## 다음 연결

> 이제 Pod를 직접 하나씩 관리하지 않고 Deployment와 Service를 사용하는 이유를 보겠습니다.

# Part 3. Kubernetes 워크로드와 서비스 제공

## 말할 순서

1. Deployment
   - Image와 Pod 수량 관리
   - Pod가 사라지면 필요한 수량 유지
2. Replica
   - 분산·장애 대응·확장
   - 여러 개라고 자동 HA는 아님
3. Label / Selector
   - 바뀌는 Pod를 조건으로 찾음
   - `app=web`
4. Service
   - Pod 앞의 안정적 접근점
   - Selector로 Pod 집합 선택
5. Pod Running 경계
   - Running ≠ Service·Ingress·사용자 정상
6. Namespace
   - Cluster 내부 논리 경계
   - KubeSphere Project와 연결
7. ConfigMap / Secret
   - 일반 설정 / 민감 설정
   - 영속 Data Storage와 다름
   - Secret도 운영 보호 설정 필요

## 꼭 말할 핵심

> Deployment는 원하는 Pod 상태를 관리하고, Service는 바뀌는 Pod 앞에 안정적인 접근점을 제공합니다.

## 다음 연결

> Service는 내부 접근점입니다. 이제 외부 사용자가 어떻게 들어오는지 보겠습니다.

# Part 4. 외부 사용자가 서비스에 접근하는 과정

## 말할 순서

1. Ingress = HTTP/HTTPS Routing 규칙
2. Ingress Controller = 규칙을 실제 Traffic에 적용
3. DKS = Router Node에 Ingress Nginx
4. 사용자 경로
   - Domain / Ingress VIP
   - External LB
   - Router / Ingress Controller
   - Service
   - Pod
   - Application
5. LB와 Router 구분
   - LB = 정상 Router로 분산
   - Router = Kubernetes 내부 연결
6. DNS
   - Domain → Ingress VIP
7. 접속 실패 시 Pod만 보지 않음

## 꼭 말할 핵심

> 사용자 요청은 DNS와 Load Balancer, Router, Ingress, Service를 거쳐 Pod와 Application으로 전달됩니다.

# Part 6. 영속 스토리지

## 말할 순서

1. Pod 수명 ≠ Data 수명
2. PV = 제공된 Volume 표현
3. PVC = Application의 Storage 요청
4. StorageClass = 공급 정책
5. CSI = Kubernetes와 외부 Storage 표준 연결
6. Trident = Kubernetes와 NetApp 연결
7. 경로
   - Pod → PVC → StorageClass → Trident → NetApp
8. 성공 단계 구분
   - PVC Bound
   - Node Mount
   - Pod Mount
   - Container Read/Write

## 꼭 말할 핵심

> PVC Bound는 Volume 연결의 증거지만, 실제 사용 성공은 Mount와 Read/Write까지 확인해야 합니다.

## 다음 연결

4. Project 구분

## 꼭 말할 핵심

> KubeSphere Project와 Harbor Project는 다른 객체이고, ImagePullBackOff는 Image 공급 경로부터 확인합니다.

# Part 10. 왜 이렇게 설계하는가

## 말할 순서

- VM Node = 생성·증설·교체 표준화, 인프라 경계
- 역할별 Node = 제어·Traffic·Platform·Workload 영향 분리
- External ETCD = 상태 저장 영역 분리
- External LB = 여러 Control Plane / Router로 분산
- External Storage = Pod와 Data 수명 분리
- Harbor 분리 = Image와 Kubernetes Resource 운영 분리
- Host / Member = 중앙 관리와 Workload 실행 분리
- API Traffic → Control Plane
- User Traffic → Router → Service / Pod

## 꼭 말할 핵심

> 역할 분리는 장애 영향과 운영 책임을 구분하기 위한 설계입니다.

# Part 11. 고가용성의 기본 개념

## 말할 순서

1. API
   - LB → Control Plane 1/2/3
2. 사용자 Traffic
   - LB → Router 1/2/3
3. 상태 저장
   - ETCD Member 1/2/3
4. Control Plane 1대 Down
   - 다른 Node + LB 정상 필요
5. Router 1대 Down
   - 다른 Router + Health Check 필요
6. Worker 1대 Down
   - Replica·다른 Worker 자원·Storage·Network 필요
7. 3대 ≠ 무조건 HA
   - LB·분산·Storage·DNS·Network·Application 구조 같이 확인

## 꼭 말할 핵심

> 여러 Node는 HA의 조건 중 하나일 뿐이며, 실제 가용성은 전체 의존성 경로로 판단합니다.

# Part 15. Xi'an DKS 아키텍처

## 말할 순서

1. `prd-host-pa01-xas`
   - Host / 중앙 관리
2. `prd-apps-pa01-xas`
   - Production Member / 운영 Workload
3. `dev-apps-pa01-xas`
   - Development Member / 개발 Workload
4. `prd-harbor-xas`
   - Private Registry / Image 공급
5. 중요 경계
   - 신규 Member identity는 8/31 재확정
   - 현장 조회 우선
6. Node 표
   - Host: 13대, Worker 0
   - Prod: 17대, Worker 4
   - Dev: 15대, Worker 2
   - Harbor: Server 1
7. 해석
   - Host는 Node 많아도 일반 Workload 영역 아님
   - Node 총수 ≠ 처리 용량
   - 역할 + CPU·Memory·Disk·Request/Limit 확인

## 꼭 말할 핵심

> Xi'an은 중앙 관리 Host, 운영 Member, 개발 Member, Harbor로 나뉘며, Node 수량은 역할 배치이지 실제 용량 자체가 아닙니다.

## 다음 연결

> 실제 서비스는 이 Cluster들뿐 아니라 Load Balancer, DNS, Storage 같은 외부 시스템과도 연결됩니다.

# Part 17. 정상 상태를 판단하는 방법

   - ≠ Metric
   - ≠ Alert

## 꼭 말할 핵심

# Part 21. 핵심 정리

## 15개를 그대로 다 읽기보다 묶어서 말하기

### Kubernetes 기본

- Kubernetes = 배포·연결·상태 유지
- Control Plane = 제어
- Worker = 실행
- Pod = 교체 가능
- Deployment = 원하는 Pod 상태
- Service = 안정적 접근점
- Ingress/LB/Router = 외부 사용자 경로
- Namespace = 논리 경계

### 주변 기능

- PVC·StorageClass·Trident = 영속 Storage
- Bound ≠ Mount·Read/Write
- Harbor = Image Registry
- Prometheus/Grafana/Alertmanager = 수집·시각화·알림

### DKS와 운영

- DKS = 역할별 표준 구조
- Host = 중앙 관리
- Member = 실제 Workload
- Node 수 ≠ 실제 용량
- 정상 = 전체 경로 확인

## 끝 문장

> 오늘은 세부 명령어보다 각 구성요소의 역할과 연결 경로를 확인했습니다. 실제 환경값은 Cluster 카탈로그와 현장 조회 결과를 기준으로 보겠습니다.
