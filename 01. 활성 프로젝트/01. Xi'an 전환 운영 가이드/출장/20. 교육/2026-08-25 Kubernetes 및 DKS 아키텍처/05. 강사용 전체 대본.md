# 교육 시작

안녕하세요.

오늘은 Kubernetes의 기본 구조와 DKS 아키텍처를 같이 보겠습니다.

오늘 교육의 목적은 Kubernetes 명령어나 모든 기능을 하루 안에 외우는 것이 아닙니다. 앞으로 KubeSphere 운영 교육과 실제 Cluster 구축 과정에서 계속 보게 될 용어들이 어떤 관계로 연결되는지를 먼저 이해하는 것이 목적입니다.

세 번째는 `prd-host-pa01-xas`, `prd-apps-pa01-xas`처럼 Xi'an에 실제로 구성된 환경 정보입니다.

먼저 Kubernetes가 왜 필요한지부터 보겠습니다.

# Part 1. Kubernetes를 이해하기 전에

처음에는 애플리케이션을 한 대의 서버나 VM에 직접 설치해서 운영할 수 있습니다.

서비스가 작고 서버 수가 적으면 이 방식으로도 충분합니다. 어떤 애플리케이션이 어디에서 실행되는지 사람이 알고 있고, 문제가 생기면 직접 확인해서 다시 실행할 수도 있습니다.

그런데 서버와 애플리케이션이 많아지면 상황이 달라집니다.

어떤 서버에서 어떤 애플리케이션이 실행되고 있는지 계속 관리해야 합니다. 서버마다 같은 설치와 설정을 반복해야 하고, 애플리케이션이 중단되면 다시 실행해야 합니다. 트래픽이 늘어나면 실행 수를 늘려야 하고, 서버가 고장 나면 다른 서버에서 다시 구성해야 합니다. Network와 Storage, 외부 접근 경로도 함께 관리해야 합니다.

그래서 규모가 커지면 서버 한 대를 관리하는 문제보다, 여러 서버에서 많은 애플리케이션을 계속 원하는 상태로 유지하는 문제가 더 커집니다.

다음은 VM입니다.

VM은 물리 서버 위에 독립적인 OS 환경을 제공합니다. 하나의 물리 서버에 여러 환경을 나누어 만들 수 있고, Template을 이용해서 비슷한 서버를 반복해서 구성할 수 있습니다. OS 단위로 환경을 분리하고 서버를 증설하거나 교체하는 데에도 도움이 됩니다.

하지만 VM이 애플리케이션 운영 문제를 모두 해결하는 것은 아닙니다.

VM을 준비한 다음에도 애플리케이션을 어떻게 설치할지, 여러 VM에 같은 설정을 어떻게 적용할지, 장애가 생기면 어떻게 다시 실행할지, 필요한 실행 수를 어떻게 유지할지는 별도로 관리해야 합니다.

그다음이 Container입니다.

Container는 애플리케이션과 실행에 필요한 파일을 Image로 묶어서 사용하는 방식입니다.

표에 있는 용어를 간단히 구분하겠습니다.

Container Image는 애플리케이션을 실행하기 위한 원본입니다. Container는 그 Image를 기반으로 실제 실행된 프로세스 환경입니다. Container Runtime은 Container를 실제로 만들고 실행하는 소프트웨어입니다. Registry는 Image를 저장하고 배포하는 장소입니다.

흐름은 화면과 같습니다.

Application Source로 Image를 만들고, 그 Image를 Registry에 저장합니다. 실행할 서버에서는 Registry에서 Image를 가져와 Container로 실행합니다.

이렇게 하면 같은 Image를 개발, 테스트, 운영 환경에서 일관된 형태로 사용할 수 있습니다. 애플리케이션 실행환경을 표준화하기 쉬워지는 것입니다.

하지만 Container가 많아지면 다시 관리 문제가 생깁니다.

어느 서버에서 Container를 실행할지 정해야 합니다. Container가 중단되면 다시 실행해야 합니다. 같은 애플리케이션을 세 개 또는 열 개 유지해야 하면 그 수량도 계속 관리해야 합니다. 서버 한 대가 중단되면 그 서버의 Container를 다른 곳에서 다시 실행해야 할 수 있습니다. Container 간 통신과 외부 사용자 접근도 연결해야 합니다.

이런 문제를 다루는 것이 Kubernetes입니다.

Kubernetes는 여러 Server나 VM을 하나의 Cluster로 묶고, Container 기반 애플리케이션을 배포하고 배치하고 연결하고 복구하고 확장할 수 있는 공통 제어 구조를 제공합니다.

여기서 Kubernetes와 Container의 역할은 구분해야 합니다.

Container는 애플리케이션의 실행 단위입니다. Kubernetes는 여러 서버에서 많은 Container가 원하는 상태로 실행되도록 관리하는 플랫폼입니다.

마지막 비교 그림은 이 변화만 확인하면 됩니다.

처음에는 물리 서버에 애플리케이션을 직접 실행했습니다. VM을 사용하면서 OS 환경을 분리할 수 있게 됐고, Container를 사용하면서 애플리케이션 실행환경을 Image로 표준화할 수 있게 됐습니다. 그리고 많은 Container를 여러 서버에서 운영하기 위해 Kubernetes를 사용합니다.

Part 1은 여기까지입니다.

다음은 Kubernetes Cluster 안에서 Control Plane과 Worker Node, Pod가 어떻게 동작하는지 보겠습니다.

# Part 2. Kubernetes의 핵심 동작 원리

먼저 Cluster, Node, Pod부터 보겠습니다.

Kubernetes Cluster는 여러 Node와 Kubernetes 구성요소를 하나의 운영 단위로 묶은 것입니다. Cluster에 참여하는 각각의 서버나 VM을 Node라고 합니다.

Node의 역할은 크게 Control Plane과 Worker Node로 구분할 수 있습니다.

Control Plane은 Cluster의 요청을 받고 전체 상태를 판단하고 조정하는 영역입니다. Worker Node는 실제 애플리케이션 Pod가 실행되는 영역입니다.

화면의 구성도에서 Control Plane과 Worker Node의 위치만 먼저 확인하면 됩니다. Control Plane은 제어 영역이고, Worker는 실제 Workload 실행 영역입니다.

Pod는 Kubernetes에서 Container가 실행되는 기본 단위입니다.

Container Image를 가져와 Container를 실행하고, Kubernetes에서는 그 Container가 Pod 안에서 실행됩니다. 그리고 Pod가 Worker Node에 배치됩니다.

Pod는 고정된 서버처럼 생각하면 안 됩니다.

배포나 장애, 확장 과정에서 Pod는 삭제되고 새로 만들어질 수 있습니다. 예를 들어 Worker 1에서 실행되던 Web Pod가 Worker 1 장애로 사라졌다고 하겠습니다. 다른 Worker에 필요한 자원과 Network, Storage 조건이 갖춰져 있다면 Kubernetes가 Worker 2에 새로운 Pod를 만들 수 있습니다.

중요한 것은 기존 Pod 하나를 같은 모습으로 계속 살려 두는 것이 아닙니다. 사용자가 정한 애플리케이션의 원하는 상태를 유지하는 것입니다.

이제 Control Plane의 주요 구성요소를 보겠습니다.

첫 번째는 API Server입니다.

API Server는 Kubernetes 관리 요청의 중심 진입점입니다. `kubectl`이나 KubeSphere 같은 관리도구도 결국 Kubernetes API를 사용합니다.

Deployment를 만들거나 Pod를 조회하거나 Service를 변경하는 요청은 API Server를 통해 처리됩니다. 운영자와 관리도구가 Kubernetes에 요청을 전달하는 입구라고 보면 됩니다.

두 번째는 Scheduler입니다.

Scheduler는 새로 실행해야 하는 Pod를 어느 Node에 배치할지 결정합니다.

Worker Node가 여러 대일 때 아무 곳에나 실행하는 것이 아니라, Node 상태와 자원, 배치 조건을 보고 적절한 Node를 선택합니다.

세 번째는 Controller Manager입니다.

여기서 Kubernetes의 중요한 개념인 원하는 상태와 실제 상태가 나옵니다.

예를 들어 Web Pod를 세 개 유지하도록 설정했다고 하겠습니다. 원하는 상태는 세 개인데 실제로 두 개만 실행 중이면 하나가 부족합니다. Controller는 이 차이를 확인하고 다시 세 개가 되도록 조정합니다.

그래서 Kubernetes는 한 번 실행하고 끝나는 도구가 아닙니다. 원하는 상태와 실제 상태를 계속 비교하면서 필요한 조정을 수행하는 플랫폼입니다.

네 번째는 ETCD입니다.

ETCD는 Kubernetes Cluster의 상태를 저장하는 분산 Key-Value Store입니다.

어떤 Node가 Cluster에 있는지, 어떤 Deployment와 Service가 존재하는지, 사용자가 어떤 상태를 원하고 있는지 같은 Cluster의 중요한 정보가 ETCD에 저장됩니다.

ETCD는 일반 애플리케이션의 업무 데이터를 저장하는 DB가 아닙니다. Kubernetes Cluster 자체의 상태를 저장하는 데이터 계층입니다.

지금까지의 내용을 Pod가 만들어지는 흐름으로 연결해 보겠습니다.

먼저 사용자나 관리도구가 요청을 보냅니다. API Server가 요청을 받습니다. 요청한 내용이 Cluster의 원하는 상태로 반영됩니다. Scheduler가 Pod를 실행할 Node를 선택합니다. 선택된 Node의 kubelet이 Pod를 실행하도록 관리합니다. 이후에도 Controller는 원하는 상태와 실제 상태가 같은지 계속 확인합니다.

이제 Worker Node를 보겠습니다.

Worker Node는 실제 애플리케이션 Pod가 실행되는 곳입니다.

각 Worker Node에는 kubelet이 동작합니다. kubelet은 해당 Node에서 어떤 Pod가 실행되어야 하는지 확인하고, 필요한 Pod의 상태를 관리합니다.

실제 Container를 실행하는 것은 Container Runtime입니다. Xi'an DKS에서는 `containerd`를 사용합니다.

흐름은 Kubernetes에서 Node의 kubelet로 전달되고, kubelet이 containerd를 통해 Container를 실행하는 구조입니다.

한 Worker Node에는 여러 Pod가 실행될 수 있습니다. 다만 무한히 실행할 수 있는 것은 아닙니다.

실제 수용량은 CPU, Memory, Disk, Kubernetes가 사용하는 예약 자원, 각 Pod의 요구량과 운영 정책에 따라 달라집니다. 그래서 뒤에서 Cluster별 Node 수량을 보더라도 Node 개수만으로 실제 처리 용량을 판단하면 안 됩니다.

Part 2를 정리하겠습니다.

Control Plane은 Cluster를 제어하고, Worker Node는 실제 Pod를 실행합니다. API Server는 요청을 받고, Scheduler는 실행할 Node를 선택하고, Controller는 원하는 상태와 실제 상태를 맞춥니다. ETCD는 Cluster 상태를 저장합니다. Worker에서는 kubelet과 containerd를 통해 실제 Container가 실행됩니다.

다음은 Pod를 직접 하나씩 관리하지 않고 Deployment와 Service 같은 상위 객체를 사용하는 이유를 보겠습니다.

# Part 3. Kubernetes 워크로드와 서비스 제공

Pod는 삭제되거나 재생성될 수 있기 때문에 운영에서는 Pod를 직접 하나씩 만들고 관리하지 않습니다. 보통 Deployment 같은 상위 객체에 원하는 상태를 정의합니다.

Deployment는 어떤 Image로 몇 개의 Pod를 실행할지 관리합니다.

화면의 예에서는 `web-app:v1` Image로 Web Pod 세 개를 유지하도록 정의했습니다. Deployment가 있으면 Pod 하나가 중단되더라도 다시 필요한 수량이 유지되도록 새로운 Pod가 만들어질 수 있습니다.

여기서 Replica는 동일한 Workload를 몇 개 실행할지를 나타냅니다.

Replica를 여러 개 두면 요청을 여러 Pod에 나눌 수 있고, Pod 하나에 문제가 생겼을 때 나머지 Pod로 서비스를 계속 제공할 가능성이 높아집니다. 배포와 확장에도 유연하게 대응할 수 있습니다.

다만 Replica가 여러 개라고 해서 자동으로 완전한 고가용성이 되는 것은 아닙니다.

여러 Replica가 같은 Node에 몰려 있을 수도 있고, Storage나 Network처럼 공통으로 의존하는 부분에 장애가 생길 수도 있습니다. Replica 수는 중요한 조건이지만 전체 서비스 가용성을 혼자 보장하지는 않습니다.

다음은 Label과 Selector입니다.

Pod는 다시 만들어지면서 이름과 IP가 바뀔 수 있습니다. 그래서 고정된 Pod 하나만 지정해서 연결하면 운영하기 어렵습니다.

Label은 Kubernetes Resource에 붙이는 식별 정보입니다. Selector는 Label을 이용해 필요한 대상을 선택하는 조건입니다.

화면의 예에서는 여러 Pod에 `app=web`이라는 Label이 있고, Service는 `app=web`이라는 Selector로 해당 Pod 집합을 찾습니다.

이렇게 하면 특정 Pod의 IP를 직접 기억하지 않아도 조건에 맞는 Pod들을 하나의 서비스 대상으로 묶을 수 있습니다.

다음은 Service입니다.

Service는 바뀔 수 있는 Pod 앞에 안정적인 접근점을 제공합니다.

Pod가 새로 만들어지면 IP가 달라질 수 있습니다. 사용자가 Pod IP를 직접 사용한다면 Pod가 바뀔 때마다 접속 대상도 바꿔야 합니다. Service는 Selector로 대상 Pod 집합을 찾고 그 앞에서 일관된 접근점을 제공합니다.

Pod와 Service의 역할은 다릅니다.

Pod는 실제 Container가 실행되는 단위입니다. Service는 그 Pod 집합에 접근하기 위한 논리적인 접점입니다.

여기서 중요한 것은 Pod가 `Running`이라고 해서 사용자 서비스 전체가 정상이라는 의미는 아니라는 점입니다.

사용자 요청은 Load Balancer, Ingress, Service, Pod, Application을 차례로 통과할 수 있습니다. Pod Running은 이 전체 경로 중 한 단계가 확인된 것입니다. Service가 올바른 Pod를 선택하는지, Ingress가 올바른 Service로 연결되는지, 실제 Application이 응답하는지까지 별도로 확인해야 합니다.

다음은 Namespace입니다.

Namespace는 하나의 Kubernetes Cluster 안에서 Resource를 논리적으로 구분하는 경계입니다.

Team이나 Application별로 Namespace를 나누고, 각 Namespace 안에 Deployment, Service, PVC 같은 Resource를 배치할 수 있습니다.

Xi'an DKS에서 KubeSphere Project는 Kubernetes Namespace와 연결되는 운영 단위입니다. 이 관계는 다음날 KubeSphere 교육에서 다시 보게 됩니다.

마지막은 ConfigMap과 Secret입니다.

Application Image만으로 모든 환경 설정을 처리하기는 어렵습니다. 환경별 설정값이나 인증 정보가 별도로 필요할 수 있습니다.

ConfigMap은 일반 설정값을 관리하고, Secret은 Password, Token, Certificate 같은 민감정보를 관리하는 Kubernetes 객체입니다. Image를 다시 만들지 않고도 설정을 Pod에 전달할 수 있습니다.

ConfigMap과 Secret은 영속 Application Data를 저장하기 위한 Storage와는 목적이 다릅니다.

또 Secret이라는 이름만으로 값이 자동으로 완전히 보호된다고 판단하면 안 됩니다. 실제 보호 수준은 RBAC, ETCD 암호화, 접근 통제와 출력 통제 같은 운영 설정에 함께 의존합니다.

Part 3을 정리하면 Deployment는 Pod의 원하는 수량과 배포 상태를 관리하고, Label과 Selector는 바뀌는 Pod를 조건으로 찾게 해주며, Service는 그 Pod 집합 앞에 안정적인 접근점을 제공합니다. Namespace는 Resource를 논리적으로 나누고, ConfigMap과 Secret은 Workload와 설정을 분리합니다.

다음은 외부 사용자가 Service와 Pod까지 어떻게 접근하는지 보겠습니다.

# Part 4. 외부 사용자가 서비스에 접근하는 과정

Service는 Kubernetes 내부에서 Pod에 접근할 수 있는 기반을 제공합니다. 하지만 외부 사용자가 Domain으로 HTTP나 HTTPS 서비스에 접근하려면 외부 진입 경로가 추가로 필요합니다.

Ingress는 HTTP와 HTTPS 요청을 적절한 Service로 전달하기 위한 Routing 규칙입니다.

Ingress 규칙만 있다고 실제 Traffic이 처리되는 것은 아닙니다. 그 규칙을 실제로 적용하는 구성요소가 Ingress Controller입니다.

DKS에서는 Ingress Nginx를 사용하고, Router 역할의 Node에 Ingress Controller가 배치됩니다.

Xi'an DKS의 사용자 요청 경로는 화면과 같이 이해하면 됩니다.

사용자가 Service Domain이나 Ingress VIP로 접근합니다. External Load Balancer가 요청을 Router Node로 전달합니다. Router의 Ingress Controller가 Ingress 규칙에 따라 적절한 Kubernetes Service로 요청을 연결합니다. Service가 대상 Pod로 전달하고, Pod 안의 Application이 응답합니다.

External Load Balancer와 Router는 역할이 다릅니다.

Load Balancer는 외부 요청을 여러 Router 중 사용 가능한 대상으로 전달합니다. Router는 Kubernetes 내부에서 Ingress Controller를 통해 Service와 Pod로 요청을 연결합니다.

여러 Router와 Load Balancer를 사용하는 이유는 특정 Router Node 하나에만 전체 요청이 의존하는 위험을 줄이기 위해서입니다.

DNS의 역할도 같이 봐야 합니다.

사용자는 보통 IP 주소가 아니라 Domain으로 접속합니다. DNS는 Application Domain을 Ingress VIP와 연결합니다. 이후 Load Balancer와 Router, Ingress, Service, Pod를 거쳐 Application까지 요청이 전달됩니다.

그래서 사용자가 접속하지 못한다고 해서 Pod만 확인하면 충분하지 않습니다.

DNS가 올바른 주소를 반환하는지, Load Balancer가 정상인지, Router와 Ingress Controller가 정상인지, Ingress Rule이 올바른 Service를 가리키는지, Service가 올바른 Pod를 선택하는지, Application이 실제 Port에서 응답하는지를 순서대로 구분해야 합니다.

Part 4의 핵심은 외부 사용자 요청이 하나의 객체로 바로 Pod에 들어가는 것이 아니라, DNS와 Load Balancer, Router, Ingress, Service를 거쳐 전달된다는 점입니다.

다음은 Kubernetes 내부의 Pod Network, Service Network와 DNS를 보겠습니다.

# Part 5. Kubernetes 네트워크의 기본 개념

Pod는 여러 Worker Node에 나뉘어 실행될 수 있습니다. 서로 다른 Node에 있는 Pod들이 통신하려면 Cluster Network가 필요합니다.

DKS에서는 Pod Network 구현에 Calico를 사용합니다.

오늘은 Calico의 내부 설정이나 세부 동작을 다루지 않습니다. Calico가 Kubernetes Cluster 안에서 Pod 간 통신을 가능하게 하는 Network 기반이라는 점만 확인하면 됩니다.

다음은 Service Network입니다.

Pod Network는 실제 Pod들이 사용하는 주소 영역입니다. Service Network는 Service가 제공하는 논리적인 접근 주소 영역입니다.

두 Network는 역할이 다르며 Cluster를 설계할 때 서로 겹치지 않도록 구성해야 합니다.

다음은 CoreDNS입니다.

Cluster 내부에서도 모든 Service IP를 사람이 기억할 수는 없습니다. CoreDNS는 Kubernetes 내부에서 Service 이름을 주소로 해석합니다.

Application Pod가 `my-service.my-namespace` 같은 이름으로 요청하면 CoreDNS가 해당 Service의 주소를 찾을 수 있도록 지원합니다.

Part 5에서는 세 가지만 기억하면 됩니다. Calico는 Pod 통신 기반을 제공하고, Pod Network와 Service Network는 서로 다른 주소 영역이며, CoreDNS는 Cluster 내부에서 이름 기반 Service 접근을 가능하게 합니다.

다음은 Pod가 교체되더라도 데이터를 유지하기 위한 Storage 구조를 보겠습니다.

# Part 6. 영속 스토리지

Pod와 데이터의 수명은 다릅니다.

Pod는 배포나 장애 처리 과정에서 삭제되고 새로 만들어질 수 있습니다. Application Data가 Pod 내부에만 저장되어 있다면 Pod가 사라질 때 데이터도 함께 사라질 수 있습니다.

그래서 운영 데이터는 Pod의 수명과 분리해서 외부의 영속 Storage에 저장해야 합니다.

먼저 PV와 PVC를 구분하겠습니다.

PV는 Kubernetes에서 사용할 수 있는 Persistent Volume을 표현하는 객체입니다.

PVC는 Application이 필요한 Storage를 요청하는 객체입니다. Application은 특정 Storage 장비를 직접 다루기보다 필요한 조건을 PVC로 요청할 수 있습니다.

StorageClass는 어떤 정책과 방식으로 Volume을 공급할지를 정의합니다.

화면의 흐름은 Application 또는 Pod가 PVC를 요청하고, PVC가 StorageClass를 선택하고, 정의된 정책에 따라 Storage가 Provisioning되어 PV가 연결되는 구조입니다.

Kubernetes는 CSI라는 표준 Interface를 통해 외부 Storage System과 연계합니다.

Xi'an DKS에서는 Kubernetes와 NetApp Storage를 연결하기 위해 NetApp Trident를 사용합니다.

전체 경로는 Pod에서 PVC를 사용하고, PVC가 StorageClass를 통해 Trident와 연결되고, Trident가 NetApp Storage에 Volume을 공급하는 구조입니다.

여기서 `PVC Bound`의 의미를 정확히 구분해야 합니다.

PVC가 Bound 상태가 되면 Kubernetes에서 PVC와 Volume이 연결됐다는 중요한 증거입니다. 하지만 이것만으로 Application이 Storage를 실제로 사용할 수 있다고 확정할 수는 없습니다.

PVC가 생성되고 Bound가 된 다음, Node에서 Volume이 Mount되어야 합니다. Pod에서도 Mount가 정상이어야 하고, Container 안에서 실제 파일 Read와 Write가 가능해야 합니다.

따라서 `PVC Bound`와 `Application Read/Write 정상`은 같은 성공 단계가 아닙니다.

Storage 검증에서는 Volume 공급 단계와 실제 사용 단계를 나누어 확인해야 합니다.

Part 6을 정리하면 Pod와 데이터의 수명을 분리하고, PVC와 StorageClass를 통해 Storage를 요청하며, Trident가 Kubernetes와 NetApp을 연결합니다. 실제 성공은 Bound에서 끝나지 않고 Mount와 Read/Write까지 확인해야 합니다.

다음은 Pod가 실행할 Image를 공급하는 Registry와 Harbor를 보겠습니다.

# Part 7. 컨테이너 레지스트리와 Harbor

Kubernetes가 Pod를 실행하려면 Container Image를 가져올 수 있어야 합니다.

Image를 Build한 다음 Registry에 Push합니다. Kubernetes에서 Workload가 만들어지면 Worker Node의 Container Runtime이 Registry에서 Image를 Pull하고 Pod를 실행합니다.

Harbor는 DKS에서 사용하는 Private Container Registry입니다.

Harbor에서는 Container Image를 저장하고, Project와 Repository를 관리하고, 사용자와 접근 권한을 관리하며, Image Push와 Pull을 처리합니다.

여기서 KubeSphere Project와 Harbor Project를 구분해야 합니다.

KubeSphere Project는 Kubernetes Namespace와 연결되어 Workload와 Kubernetes Resource를 운영하는 단위입니다.

Harbor Project는 Container Image Repository와 접근 권한을 관리하는 Registry 단위입니다.

이름이 같더라도 같은 객체가 아닙니다.

Private Image를 사용하려면 Kubernetes와 Worker Node가 Harbor에 인증하고 접근할 수 있어야 합니다.

Image 이름이나 Tag가 잘못됐거나, Repository가 없거나, 인증과 권한에 문제가 있거나, Registry Certificate를 신뢰하지 못하거나, Worker에서 Harbor로 접근할 수 없으면 `ImagePullBackOff`가 발생할 수 있습니다.

이 상태는 Application이 실행된 뒤의 문제라기보다, Application이 실행되기 전에 Image를 공급받는 경로에서 발생한 문제일 수 있습니다.

Part 7의 핵심은 Harbor가 Image 공급 영역이고, KubeSphere Project와 Harbor Project가 서로 다르며, `ImagePullBackOff`는 Image 공급 경로부터 확인해야 한다는 점입니다.

다음은 Cluster와 Application 상태를 어떻게 관측하는지 보겠습니다.

# Part 8. 모니터링

Cluster와 Application이 정상인지 판단하려면 현재 상태를 관측할 수 있어야 합니다.

운영에서는 Node의 CPU와 Memory가 충분한지, Pod가 정상인지, Application Resource 사용량이 어떻게 변하는지, ETCD와 Kubernetes 주요 구성요소가 정상인지, 장애 징후가 있는지를 확인해야 합니다.

Monitoring은 이런 상태를 Metric으로 수집하고 분석하는 기반을 제공합니다.

주요 구성요소는 Prometheus, Grafana, Alertmanager입니다.

Prometheus는 Metric을 수집하고 Time Series Data로 저장합니다. Grafana는 그 데이터를 시각화합니다. Alertmanager는 Prometheus에서 발생한 Alert를 전달하고 처리합니다.

화면의 구조처럼 Node와 Kubernetes Component, Workload의 Metric을 Prometheus가 수집하고, Grafana가 조회해서 보여주며, Alert는 Alertmanager로 전달됩니다.

여기서 Dashboard가 열린다는 것과 Monitoring 전체가 정상이라는 것은 구분해야 합니다.

Grafana 화면이 열려도 Prometheus가 Target을 실제로 수집하지 못할 수 있습니다. 필요한 Metric이 없을 수 있고, Grafana Datasource가 잘못된 Prometheus를 바라볼 수도 있습니다. Alert Rule이나 Alertmanager 연결에 문제가 있을 수도 있습니다.

그래서 Monitoring에서는 화면의 존재보다 데이터가 실제로 수집되고 올바르게 연결되어 있는지를 확인해야 합니다.

Part 8을 정리하면 Prometheus는 Metric을 수집하고, Grafana는 시각화하며, Alertmanager는 Alert를 전달합니다. 화면이 열린 것만으로 전체 Monitoring이 정상이라고 판단하지 않습니다.

이제 Kubernetes 위에 DKS가 어떤 구조를 적용하는지 보겠습니다.

# Part 9. DKS 아키텍처

DKS는 Kubernetes를 대체하는 별도의 Container Orchestrator가 아닙니다.

Kubernetes를 기반으로 Node 역할, 설치 도구, Network, Storage, Monitoring, Registry, Multi-Cluster 운영 구조를 정해진 방식으로 구성한 표준 아키텍처로 이해하면 됩니다.

Kubernetes가 Container Workload를 실행하고 조정하는 기반이라면, DKS는 그 Kubernetes를 어떤 도구와 Node 역할, Platform 구성으로 배포하고 운영할지를 정한 구조입니다.

표에 DKS에서 사용하는 주요 소프트웨어가 나와 있습니다.

Git은 Cluster 배포 Source와 Configuration을 관리합니다. Python은 Ansible 실행 등에 필요한 기반을 제공합니다. Ansible은 여러 Linux Node의 설정을 자동화하고, Kubespray는 Ansible Playbook을 기반으로 Kubernetes Cluster를 설치합니다.

`kubectl`은 Kubernetes API에 접근하는 CLI이고, Helm은 Kubernetes Application Package를 설치하고 관리하는 도구입니다.

`containerd`는 Container Runtime입니다. Kubernetes는 Workload를 Scheduling하고 조정합니다. ETCD는 Cluster 상태를 저장하고, CoreDNS는 Cluster 내부 DNS를 제공합니다. Calico는 Pod Network를 담당합니다.

Ingress Nginx는 외부 HTTP와 HTTPS 요청을 Routing합니다. Trident는 Kubernetes와 NetApp Storage를 연결합니다. Prometheus와 Grafana는 Monitoring과 시각화를 담당합니다. KubeSphere는 Kubernetes와 Multi-Cluster 운영 계층을 제공하고, Harbor는 Private Container Registry 역할을 합니다.

오늘 이 제품들의 내부 동작을 모두 배우는 것은 아닙니다. 각 구성요소가 전체 구조에서 어느 역할을 담당하는지 구분하는 것이 목적입니다.

다음은 DKS Node 역할입니다.

DKS는 여러 기능을 한 종류의 Node에 모두 배치하지 않고 역할별로 나눕니다.

Bastion은 Cluster 설치와 관리 작업의 진입점입니다. 운영자는 Bastion에서 Ansible, Kubespray, `kubectl`, Git, Helm 같은 도구를 사용합니다. Bastion은 일반 사용자 Application을 실행하는 Worker와 역할이 다릅니다.

Control Plane은 Kubernetes API와 Cluster 제어 기능을 제공합니다. DKS에서는 여러 Control Plane Node와 External Load Balancer를 이용해 API 접근 경로를 구성합니다.

External ETCD는 Kubernetes Cluster 상태를 저장합니다. DKS는 ETCD를 별도 Node 역할로 구성해서 상태 저장 영역을 일반 Workload 실행 영역과 분리합니다.

Router에는 Ingress Controller가 배치되어 외부 HTTP와 HTTPS Traffic을 Kubernetes 내부 Service로 전달합니다. External Load Balancer와 함께 사용자 요청의 진입 영역을 구성합니다.

Infra Node에는 Prometheus, Grafana, Dashboard 등 Platform 운영 성격의 Workload가 배치됩니다. 사용자 Business Workload와 Platform Workload의 자원 영향과 운영 책임을 나누기 위한 역할입니다.

Worker Node는 실제 사용자 Application Workload를 실행합니다.

Worker의 실제 수용량은 Node 수량만으로 결정되지 않습니다. CPU, Memory, Disk, Kubernetes 예약 자원, Application Request와 Limit, Replica 수, Storage와 Network 요구사항, 운영 정책을 같이 봐야 합니다.

Part 9를 정리하면 DKS는 Kubernetes를 기반으로 여러 도구와 Platform을 표준화하고, Bastion, Control Plane, External ETCD, Router, Infra, Worker로 Node 역할을 구분합니다.

다음은 왜 이런 역할 분리와 외부 구성을 선택했는지 보겠습니다.

# Part 10. 왜 이렇게 설계하는가

DKS 구조는 제품을 많이 배치하기 위한 것이 아니라 장애 영향, 관리 영역, 용량과 운영 책임을 나누기 위한 설계입니다.

VM 기반 Node를 사용하면 표준화된 방식으로 Node를 생성하고 증설하고 교체할 수 있고, 물리 인프라와 Kubernetes 운영의 경계를 나눌 수 있습니다. Kubernetes가 물리 인프라 전체를 자동으로 관리하는 것은 아닙니다.

Node 역할을 나누면 제어 영역, 사용자 Traffic 영역, Platform 영역, 사용자 Workload 영역의 영향을 분리할 수 있습니다. 모든 Node를 같은 Worker로 보면 안 됩니다.

External ETCD는 Cluster 상태 저장 영역을 일반 Workload와 분리합니다. ETCD는 Application DB가 아닙니다.

External Load Balancer는 여러 Control Plane과 Router에 요청을 분산합니다. 특정 Node IP 하나를 Cluster의 영구 진입점으로 사용하지 않도록 하는 구조입니다.

External Storage는 Pod의 수명과 Application Data의 수명을 분리합니다.

Harbor를 별도로 두면 Image 공급과 Kubernetes Resource 운영을 구분할 수 있습니다.

Host와 Member를 나누면 중앙 관리 영역과 실제 Workload 실행 영역을 분리할 수 있습니다.

역할 분리의 효과를 Traffic 관점에서도 볼 수 있습니다.

Kubernetes API 요청은 Control Plane으로 들어갑니다. 사용자 HTTP와 HTTPS 요청은 Router를 통해 Service와 Pod로 들어갑니다.

이 두 경로를 나누면 문제가 생겼을 때 Kubernetes 관리 API 문제인지, 사용자 서비스 Traffic 문제인지 먼저 구분할 수 있습니다.

Part 10의 핵심은 DKS의 역할 분리가 장애 범위와 운영 책임을 구분하기 위한 설계라는 점입니다.

다음은 여러 Node를 구성했을 때의 고가용성 개념을 보겠습니다.

# Part 11. 고가용성의 기본 개념

운영 환경에서는 Node 하나의 장애가 전체 기능 중단으로 바로 이어지지 않도록 중요 역할을 여러 Node에 분산합니다.

API 요청은 External Load Balancer를 통해 여러 Control Plane Node로 전달됩니다. 사용자 HTTP와 HTTPS 요청은 External Load Balancer를 통해 여러 Router Node로 전달됩니다. Cluster 상태는 여러 ETCD Member에 저장됩니다.

Control Plane Node 하나가 중단되더라도 다른 Control Plane이 정상이고 Load Balancer가 정상 Node로 요청을 전달할 수 있다면 전체 API 중단으로 이어지지 않도록 구성할 수 있습니다.

Router Node 하나가 중단된 경우에도 다른 Router가 정상이고 Load Balancer Health Check가 올바르게 동작하면 사용 가능한 Router로 Traffic을 전달할 수 있습니다.

Worker Node 하나가 중단되면 그 Node에서 실행되던 Pod가 영향을 받습니다. 다른 Worker에 필요한 자원이 있고, Application이 여러 Replica를 사용하고, Network와 Storage 조건이 갖춰져 있다면 다른 Worker에 새로운 Pod가 Scheduling될 수 있습니다.

다만 Node가 여러 대 있다는 사실만으로 고가용성이 완성되는 것은 아닙니다.

Load Balancer 자체가 정상이어야 합니다. Application Replica가 실제 여러 Node에 분산되어 있어야 합니다. Storage와 DNS, Network가 정상이어야 하고, Application 자체도 여러 Replica로 동작할 수 있어야 합니다.

그래서 “세 대가 있으니 무조건 HA다”라고 판단하면 안 됩니다.

여러 Node는 중요한 조건이지만, 실제 가용성은 Application과 Load Balancer, Network, DNS, Storage를 포함한 전체 의존성 경로로 판단해야 합니다.

Part 11을 정리하면 여러 Node를 배치하는 목적은 단일 Node 장애의 영향을 줄이는 것이지만, HA는 Node 수만이 아니라 전체 경로가 함께 정상일 때 성립합니다.

다음은 지금까지 나온 내용을 다섯 가지 경로로 다시 정리하겠습니다.

---

# Part 12. DKS에서 기억해야 할 다섯 가지 경로

DKS 구조를 제품 이름으로만 외우기보다, 실제 요청과 데이터가 이동하는 다섯 가지 경로로 기억하면 됩니다.

첫 번째는 Kubernetes 관리 요청 경로입니다.

운영자나 `kubectl`, 관리도구의 요청이 API VIP로 들어가고, External Load Balancer를 거쳐 Control Plane과 Kubernetes API로 전달됩니다.

이 경로는 Cluster Resource를 조회하거나 변경하는 관리 요청에 사용됩니다.

두 번째는 사용자 서비스 요청 경로입니다.

사용자가 Domain이나 Ingress VIP로 접근하고, External Load Balancer가 Router와 Ingress Controller로 요청을 전달합니다. 이후 Service, Pod, Application으로 연결됩니다.

사용자 접속 장애는 이 순서를 따라 어디까지 요청이 전달되는지를 확인해야 합니다.

세 번째는 Container Image 공급 경로입니다.

Developer나 CI가 Harbor에 Image를 Push합니다. Kubernetes Workload가 만들어지면 Worker의 containerd가 Harbor에서 Image를 Pull하고 Pod를 실행합니다.

네 번째는 영속 데이터 경로입니다.

Pod가 PVC를 사용하고, PVC가 StorageClass를 통해 Trident와 연결됩니다. Trident가 NetApp Storage를 공급하고, Node와 Container에서 Mount와 Read, Write가 이루어집니다.

다섯 번째는 Monitoring Data 경로입니다.

Node와 Kubernetes, Workload의 Metric을 Prometheus가 수집합니다. Grafana가 이를 시각화하고, Alert는 Alertmanager로 전달됩니다.

이 다섯 가지 경로를 구분하면 문제가 생겼을 때 어느 영역부터 봐야 하는지 정리하기 쉬워집니다.

다음은 KubeSphere가 Kubernetes 위에서 어떤 역할을 하는지 보겠습니다.

---

# Part 13. KubeSphere

KubeSphere는 Kubernetes를 대체하지 않습니다.

Kubernetes API와 Resource를 Web UI와 사용자 관리 구조를 통해 운영할 수 있도록 제공하는 Platform 계층입니다.

KubeSphere에서 보이는 많은 객체는 실제 Kubernetes Resource와 연결됩니다.

KubeSphere Project는 Kubernetes Namespace와 연결됩니다. KubeSphere의 Workload 화면에서는 Deployment, StatefulSet, Pod 같은 Kubernetes Workload를 봅니다. Service는 Kubernetes Service와 연결되고, Storage는 PVC, PV, StorageClass와 연결됩니다. 사용자 Role은 Kubernetes 권한 구조와 연결됩니다.

Xi'an DKS 운영에서는 KubeSphere를 통해 Workspace, Project, User, Role, Quota를 관리합니다.

Workspace는 여러 Project를 관리하는 상위 운영 영역입니다. Project는 Namespace와 연결되는 Application 운영 단위입니다. User는 KubeSphere에 접근하는 사용자이고, Role은 사용자가 할 수 있는 작업 범위를 정합니다. Quota는 사용할 수 있는 CPU와 Memory 등의 Resource 범위를 제한합니다.

오늘은 이 개념들의 관계만 확인합니다. 실제 Workspace와 Project 생성, 사용자 초대, Role과 Quota 설정은 다음날 KubeSphere Operation 교육에서 다룹니다.

Part 13의 핵심은 KubeSphere가 Kubernetes 위의 관리 계층이고, KubeSphere 화면의 객체가 실제 Kubernetes Resource와 연결된다는 점입니다.

다음은 여러 Kubernetes Cluster를 중앙에서 관리하는 Multi-Cluster 구조를 보겠습니다.

---

# Part 14. Multi-Cluster

Kubernetes Cluster가 하나라면 해당 Cluster를 직접 관리할 수 있습니다.

하지만 Production, Development, 중앙 관리 영역처럼 Cluster가 여러 개이면 각 Cluster의 상태와 사용자, Resource를 따로 관리해야 합니다.

Multi-Cluster는 여러 독립 Kubernetes Cluster를 중앙에서 관리하고 관측할 수 있는 기반을 제공합니다.

KubeSphere Multi-Cluster에서는 Host Cluster와 Member Cluster를 구분합니다.

Host Cluster는 중앙 관리 영역입니다. 사용자, Workspace, Project를 여러 Cluster 관점에서 관리하고 Member Cluster를 관측합니다.

Member Cluster는 실제 Application Workload를 실행하고 자체 Kubernetes Resource를 운영하는 독립 Cluster입니다.

Member가 Host에 Join된다는 것은 중앙 관리와 관측 대상에 편입된다는 의미입니다. Member의 Kubernetes가 Host 내부로 합쳐지는 것은 아닙니다. Host와 각 Member는 각각 독립된 Kubernetes Cluster로 존재합니다.

Host와 Member를 분리하면 중앙 관리와 실제 Workload 실행 영역을 나눌 수 있습니다. Production과 Development 같은 환경별 독립성을 유지할 수 있고, 장애 범위와 Resource 영향을 분리할 수 있습니다. 동시에 여러 Cluster를 하나의 관리 화면에서 확인할 수 있습니다.

Part 14의 핵심은 Host가 중앙 관리 역할을 하고, Member가 실제 Workload를 실행하는 독립 Cluster이며, Join은 Cluster의 합병이 아니라 관리 관계의 연결이라는 점입니다.

다음은 이 구조가 Xi'an 환경에 어떻게 적용되어 있는지 보겠습니다.

---

# Part 15. Xi'an DKS 아키텍처

이제 일반 Kubernetes와 DKS 구조를 Xi'an의 실제 환경에 연결해 보겠습니다.

현재 Cluster 카탈로그 기준으로 Xi'an 환경은 네 영역으로 나뉩니다.

`prd-host-pa01-xas`는 KubeSphere Multi-Cluster 중앙 관리를 담당하는 Host Cluster입니다.

`prd-apps-pa01-xas`는 운영 Application Workload가 실행되는 Production Member Cluster입니다.

`dev-apps-pa01-xas`는 개발 Application Workload가 실행되는 Development Member Cluster입니다.

`prd-harbor-xas`는 Container Image를 저장하고 Push와 Pull을 처리하는 Private Registry입니다.

화면의 논리 구성도에서 Host는 Production Member와 Development Member를 관리하고 관측합니다. Harbor는 두 Member에 필요한 Image를 공급합니다.

이 구성은 현재 Cluster 카탈로그에 기록된 Xi'an 기준 아키텍처입니다. 이번 출장에서 신규로 구축할 Member의 실제 identity와 현재 상태는 8월 31일 환경 확인 단계에서 다시 확정해야 합니다. 현장 조회 결과가 이 교재의 예시보다 우선합니다.

다음은 Node 배치 표입니다.

Host Cluster인 `prd-host-pa01-xas`는 Bastion 1대, Control Plane 3대, External ETCD 3대, Router 3대, Infra 3대로 총 13대이며, 카탈로그 기준 사용자 Business Workload용 Worker는 없습니다.

그래서 Host Cluster는 Node 수가 많더라도 Production Member처럼 일반 Application을 실행하는 영역으로 해석하면 안 됩니다.

Production Member인 `prd-apps-pa01-xas`는 Bastion 1대, Control Plane 3대, External ETCD 3대, Router 3대, Infra 3대, Worker 4대로 총 17대입니다. 실제 운영 Application은 이 Cluster의 Worker 영역에서 실행됩니다.

Development Member인 `dev-apps-pa01-xas`는 같은 기본 역할에 Worker 2대를 두고 총 15대로 구성되어 있습니다. Production과 Development는 서로 독립된 Kubernetes Cluster이고, Pod Network와 Service Network, Resource를 각각 관리합니다.

`prd-harbor-xas`는 별도의 Harbor Server 영역입니다. Kubernetes Cluster와는 다른 Registry 영역이며, Production과 Development Member가 필요한 Image를 이곳에서 가져옵니다.

이 표를 볼 때 Node 총수와 Workload 수용량을 같은 의미로 보면 안 됩니다.

Worker가 네 대여도 각 Worker의 CPU와 Memory, Disk, Kubernetes System Resource, Application Request와 Limit, Replica 수, Storage와 Network 요구량, 운영 Reserve 정책에 따라 실제 수용량은 달라집니다.

“17대 Cluster가 13대 Cluster보다 무조건 성능이 좋다”는 식으로 판단할 수 없습니다. Node의 역할과 실제 자원 사양을 같이 봐야 합니다.

Part 15를 정리하면 Xi'an에는 중앙 관리용 Host, 운영용 Production Member, 개발용 Development Member, Image 공급용 Harbor가 있고, Node 수량은 역할 배치를 보여줄 뿐 실제 Workload 용량을 직접 의미하지 않습니다.

다음은 Kubernetes 밖의 Load Balancer, DNS, Storage 같은 외부 시스템과 운영 경계를 보겠습니다.

# Part 16. 외부 시스템과 운영 경계

실제 DKS 서비스는 Kubernetes Cluster만으로 구성되지 않습니다.

External Load Balancer, DNS, Network와 Firewall, NetApp Storage, Harbor Registry, 사용자 인증 System 같은 외부 영역과 연결되어 동작합니다.

그래서 Kubernetes 안의 객체가 정상이라고 해서 전체 서비스가 정상이라고 판단할 수 없습니다. 문제가 어느 영역에 있는지 나누어 확인해야 합니다.

Cluster 설치와 관리 작업은 Bastion을 통해 진행합니다. 여기서는 계정과 Network 접근, Kubespray와 Ansible, kubeconfig 같은 관리 경로를 확인합니다.

Kubernetes 관리 API는 API VIP와 Load Balancer를 거쳐 Control Plane으로 연결됩니다. 여기서는 Load Balancer Health, API Server, 인증과 권한을 구분해서 확인합니다.

사용자 HTTP와 HTTPS 요청은 DNS, Ingress VIP, Load Balancer, Router, Service, Pod로 이어집니다. 여기서는 DNS와 Firewall, Load Balancer, Ingress, Service, Application을 순서대로 봐야 합니다.

KubeSphere Web 운영 문제는 사용자 인증, Workspace, Project, Role, Quota 영역을 확인합니다.

Image Push와 Pull 문제는 Harbor의 인증, Project, Repository, Image, Certificate와 Network 접근을 확인합니다.

Persistent Storage 문제는 PVC와 PV, StorageClass, Trident Backend, Network, Mount, Read와 Write를 확인합니다.

Monitoring 문제는 Prometheus Target, Metric, Grafana Datasource와 Dashboard, Alert 연결을 구분합니다.

운영 책임도 기술 영역별로 나누어 생각할 수 있습니다.

Infrastructure 영역에는 VM, Network, Load Balancer, DNS가 있습니다. Kubernetes Platform 영역에는 Control Plane, Worker, Service, Ingress가 있습니다. Platform Service 영역에는 KubeSphere, Harbor, Storage, Monitoring이 있습니다. 그 위에 Deployment, Pod, Application Process 같은 Application 영역이 있습니다.

문제가 생겼을 때 처음부터 모든 영역을 동시에 확인하기보다, 어느 층까지 정상인지 순서대로 확인하면 원인을 더 빠르게 좁힐 수 있습니다.

Part 16의 핵심은 Kubernetes 내부와 외부 의존성을 나누고, 문제의 첫 확인 영역을 요청 목적에 맞게 선택하는 것입니다.

다음은 한 가지 상태값만으로 전체를 정상이라고 판단하면 안 되는 이유를 정리하겠습니다.

---

# Part 17. 정상 상태를 판단하는 방법

Kubernetes에서는 한 명령이나 한 화면만 보고 전체 서비스가 정상이라고 판단하면 안 됩니다.

먼저 Cluster 구축을 보겠습니다.

Kubespray가 `exit 0`으로 끝났다는 것은 설치 명령이 오류 없이 종료됐다는 중요한 결과입니다. 하지만 Cluster의 모든 기능이 정상이라는 최종 증거는 아닙니다.

추가로 Kubernetes API가 응답하는지, Node가 Ready인지, System Pod가 정상인지, Network와 DNS가 정상인지, 실제 Workload를 실행할 수 있는지 확인해야 합니다.

다음은 Pod Running입니다.

Pod가 Running이어도 Service가 올바른 Endpoint를 가지고 있는지, Ingress가 정상인지, 사용자가 실제로 접속할 수 있는지는 별도입니다.

다음은 PVC Bound입니다.

PVC가 Bound여도 Node Mount와 Pod Mount가 정상인지, Application에서 실제 Read와 Write가 가능한지는 별도로 확인해야 합니다.

다음은 Monitoring Dashboard입니다.

Grafana 화면이 열려도 Prometheus Target과 Metric 수집이 정상인지, Alert가 정상적으로 평가되고 전달되는지는 별도입니다.

이런 구분은 이후 실제 구축과 Troubleshooting에서도 계속 사용합니다.

Part 17을 한 문장으로 정리하면, 한 단계의 성공은 전체 경로의 성공과 같지 않습니다.

다음은 이 기준을 실제 사례에 적용해 보겠습니다.

---

# Part 18. 아키텍처 이해를 위한 사례

첫 번째 사례는 Pod가 Running인데 사용자가 접속하지 못하는 경우입니다.

Pod가 Running이고 Application Process도 실행 중인데 사용자는 접속하지 못한다고 하겠습니다.

이 경우 Pod만 계속 재시작하기보다 전체 사용자 요청 경로를 확인해야 합니다.

DNS가 올바른 Ingress VIP를 반환하는지 확인합니다. External Load Balancer가 정상인지 확인합니다. Router와 Ingress Controller가 요청을 받고 있는지 확인합니다. Ingress가 올바른 Service를 가리키는지, Service가 올바른 Pod Endpoint를 선택하는지, Pod의 Application Port가 실제로 응답하는지 순서대로 봅니다.

Pod Running은 이 경로의 마지막 일부가 확인된 것입니다.

두 번째 사례는 `ImagePullBackOff`입니다.

Deployment를 만들었고 Pod 생성이 시작됐지만 ImagePullBackOff가 발생했다고 하겠습니다.

이 상태에서는 Application Process가 아직 실행되지 않았을 가능성이 큽니다. 그래서 Application 내부보다 Image 공급 경로를 먼저 봅니다.

Image 이름과 Tag가 올바른지, Harbor Repository에 Image가 존재하는지, 인증과 권한이 정상인지, Registry Certificate를 Worker가 신뢰하는지, Worker에서 Harbor로 Network 접근이 가능한지를 확인합니다.

세 번째 사례는 PVC가 Bound인데 Pod가 Storage를 사용하지 못하는 경우입니다.

PVC가 Bound여도 Mount 단계에서 실패할 수 있습니다.

PVC와 PV 연결을 확인하고, StorageClass가 올바른지, Trident 상태와 Storage Backend가 정상인지, Node에서 Storage Network 접근이 가능한지, 실제 Volume Mount가 정상인지 확인합니다.

Bound는 Provisioning의 중요한 단계이지만 실제 사용 성공의 마지막 단계는 아닙니다.

네 번째 사례는 KubeSphere에서 Project가 보이지 않는 경우입니다.

이 문제는 Pod Network나 Storage부터 확인할 문제가 아닙니다.

Project가 실제로 존재하는지, 올바른 Workspace에 있는지, 사용자가 해당 Workspace나 Project에 초대됐는지, User Role과 Project Permission이 올바른지를 확인합니다.

다섯 번째 사례는 Kubernetes API에 접속할 수 없는 경우입니다.

운영자 Network에서 API VIP로 접근할 수 있는지 확인합니다. External Load Balancer가 정상인지, Control Plane Node와 kube-apiserver가 정상인지, 마지막으로 인증과 kubeconfig가 올바른지 확인합니다.

API 문제는 사용자 Application의 Ingress 경로와 다른 경로입니다. 사용자가 Web 서비스에 접속하지 못하는 문제와 `kubectl`이 API에 접속하지 못하는 문제를 같은 경로로 보면 안 됩니다.

여섯 번째 사례는 Worker Node 하나가 중단된 경우입니다.

먼저 해당 Node에 어떤 Pod가 있었는지 확인합니다. Application Replica가 여러 개였는지, 다른 Worker에 충분한 Resource가 있는지 봅니다. 새 Pod가 다른 Worker에 Scheduling되는지 확인합니다. Persistent Storage가 다른 Node에서도 연결 가능한지 확인하고, Service Endpoint가 새로 정상 상태가 된 Pod를 가리키는지도 확인합니다.

이 사례는 HA가 Node 수만으로 결정되지 않는다는 점을 보여줍니다. Application Replica, 다른 Worker의 자원, Storage와 Network, Service Endpoint까지 함께 정상이어야 합니다.

Part 18의 사례들은 모두 같은 기준을 사용합니다.

보이는 상태 하나만 보고 결론을 내리지 않고, 해당 기능의 전체 경로를 따라 첫 번째로 끊긴 구간을 찾습니다.

다음은 오늘 배운 내용이 이후 교육과 실제 구축에 어떻게 이어지는지 보겠습니다.

# Part 20. 전체 구조 다시 보기

Application 하나가 사용자에게 제공되는 전체 흐름을 다시 보겠습니다.

먼저 Application Image를 만듭니다. Image를 Harbor에 저장합니다. KubeSphere나 Kubernetes API를 통해 Deployment를 생성합니다. Scheduler가 Pod를 실행할 Worker Node를 결정합니다. 해당 Worker의 kubelet과 containerd가 Harbor에서 Image를 Pull하고 Pod를 실행합니다.

Service가 Pod 집합 앞에 안정적인 접근점을 제공합니다. Ingress가 HTTP와 HTTPS Routing 규칙을 제공합니다. External Load Balancer가 사용자 요청을 Router로 전달하고, Router의 Ingress Controller가 Service와 Pod로 요청을 연결합니다. 사용자는 Domain을 통해 Application에 접근합니다.

Application에 영속 데이터가 필요하면 Storage 경로가 추가됩니다.

Pod가 PVC를 사용하고, PVC가 StorageClass를 선택합니다. Trident가 NetApp Storage와 연결하고, Node와 Pod에서 Mount와 Read, Write가 이루어집니다.

운영 상태는 Monitoring 경로에서 확인합니다.

Node와 Kubernetes Component, Pod의 Metric을 Prometheus가 수집하고, Grafana가 시각화하며, Alertmanager가 Alert를 전달합니다.

여러 Cluster는 KubeSphere Multi-Cluster 구조로 연결됩니다.

Host Cluster가 Production Member와 Development Member를 중앙에서 관리하고 관측합니다. Harbor는 각 Member가 실행할 Container Image를 공급합니다.

화면의 전체 구성도에서는 이 관계를 한 번에 볼 수 있습니다.

운영자와 KubeSphere, `kubectl`의 관리 요청은 API VIP와 Control Plane으로 들어갑니다. 사용자의 요청은 Domain, Ingress VIP와 Load Balancer, Router, Service를 거쳐 Pod로 들어갑니다. Harbor는 Pod 실행에 필요한 Image를 공급합니다. Pod는 Trident와 NetApp을 통해 Storage를 사용합니다. Prometheus는 상태를 수집합니다. Host는 Member를 관리하고 관측합니다.

Part 20은 새로운 내용을 추가하는 부분이 아니라, 앞에서 따로 본 경로를 하나의 구조로 합치는 부분입니다.

마지막으로 오늘 반드시 기억할 내용을 정리하겠습니다.

# Part 21. 핵심 정리

오늘 내용을 열다섯 가지로 정리하겠습니다.

첫째, Kubernetes는 여러 Node에서 Container 기반 Application을 배포하고 연결하고 원하는 상태로 유지하는 Platform입니다.

둘째, Control Plane은 Cluster를 제어하고 Worker Node는 실제 Pod를 실행합니다.

셋째, Pod는 교체될 수 있는 실행 단위이므로 고정 Server처럼 생각하면 안 됩니다.

넷째, Deployment는 원하는 Pod 수량과 배포 상태를 관리합니다.

다섯째, Service는 바뀔 수 있는 Pod 앞에 안정적인 접근점을 제공합니다.

여섯째, Ingress와 External Load Balancer, Router는 외부 사용자의 요청을 Service와 Pod까지 연결합니다.

일곱째, Namespace는 하나의 Cluster 안에서 Resource를 논리적으로 나누는 경계입니다.

여덟째, Pod의 수명과 Data의 수명은 분리해야 하며, PVC와 StorageClass, Trident를 통해 External Storage와 연결합니다.

아홉째, PVC Bound와 실제 Pod Mount, Application Read와 Write는 서로 다른 성공 단계입니다.

열째, Harbor는 Container Image를 저장하고 공급하는 Private Registry입니다.

열한째, Prometheus는 Metric을 수집하고 Grafana는 데이터를 시각화하며 Alertmanager는 Alert를 전달합니다.

열두째, DKS는 Bastion, Control Plane, External ETCD, Router, Infra, Worker로 역할을 구분합니다.

열셋째, KubeSphere Host는 중앙 관리 영역이고 Member Cluster는 실제 Workload를 실행하는 독립 Cluster입니다.

열넷째, Node 수량만으로 실제 Workload 수용량을 판단할 수 없습니다.

열다섯째, 정상 여부는 Pod 하나나 화면 하나가 아니라 API, Network, Storage, Registry, Monitoring을 포함한 전체 경로로 판단해야 합니다.

오늘 교육은 여기까지입니다.

뒤의 핵심 용어와 구조 비교 표는 지금까지 설명한 내용을 다시 확인하거나 질문이 있을 때 참고하면 됩니다. 실제 IP, VIP, hostname, CPU와 Memory, CIDR 같은 상세값은 Cluster 카탈로그와 승인된 Manual, 현장 조회 결과를 기준으로 확인하겠습니다.

감사합니다.
