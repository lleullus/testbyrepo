# Kubernetes Node Pre-setting 강사용 전체 대본 - 원본 절차 순서 준수본

> [!important] 사용 방법
> 이 대본은 **Cluster Setup 원본 `2. K8S 클러스터 노드 사전 설정`의 항목 순서와 작업 단위를 그대로 따라가면서 설명하기 위한 강사용 대본**이다.
>
> 원본의 `0-1 → 0-2 → 0-3 → 0-4 → 2-1-1 → 2-1-9` 순서를 바꾸지 않는다. 앞 시간에 이미 수행한 항목은 생략하지 않고 **"앞 블록에서 확인한 결과를 이 단계의 진입조건으로 다시 확인한다"**고 연결한다.
>
> 정확한 신규 Member Hostname·IP·Repository URL·Volume Group·인증서와 기타 환경값은 오전에 확인한 실제값과 승인된 Runbook을 사용한다. 원본에 남아 있는 Host/Taylor 값을 신규 Member 값으로 복사하지 않는다.
>
> 이 대본은 명령어를 숨기지 않는다. **원본 명령을 보여주고, 왜 실행하는지, 무엇이 바뀌는지, 결과에서 무엇을 봐야 하는지, 어디까지 성공했다고 말할 수 있는지**를 바로 이어 설명한다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
원본 0. 사전 요구사항을 확인한다
→ 0-1 LB 결과를 확인한다
→ 0-2 ETCD Filesystem과 VM Resource를 확인한다
→ 0-3 dspaas와 passwordless sudo를 확인한다
→ 0-4 Node Pre-setting용 Ansible inventory를 확인한다
→ 2-1 Ansible 작업을 시작한다
→ 2-1-1 sudoers
→ 2-1-2 SSH Public Key
→ 2-1-3 YUM Repository
→ 2-1-4 Package
→ 2-1-5 SWAP
→ 2-1-6 logrotate
→ 2-1-7 SECDS-ROOTCA
→ 2-1-8 sysctl.conf
→ 2-1-9 VM Resource 최종 확인
→ 완료 결과를 다음 Kubespray Inventory·Preflight 블록에 넘긴다
```

## 0-1. 오늘 전체 한 줄

> 오늘은 Kubernetes Node를 일반적인 범주로 다시 분류해서 설명하지 않습니다. **Cluster Setup 원본에서 실제로 하는 순서 그대로 각 Node를 준비하고, 각 명령이 왜 필요한지와 정상 결과를 함께 설명합니다.**

# 1. 시작 — 오늘은 Cluster Setup 2번을 원본 순서대로 따라간다

> 오전에는 신규 Member VM과 Bastion을 확인했습니다.
>
> 이제 Cluster Setup의 `2. K8S 클러스터 노드 사전 설정`으로 들어갑니다.
>
> 이 단계의 목적은 Master·ETCD·Router·Infra·Worker 같은 Kubernetes Node가 **Bastion에서 수행하는 Ansible 자동화와 이후 Kubespray 작업을 받을 수 있는 OS 상태**가 되도록 준비하는 것입니다.
>
> 여기서 중요한 것은 작업을 편하게 설명하기 위해 순서를 새로 만들지 않는 것입니다. 원본은 먼저 진입조건을 확인하고, 그다음 Ansible을 이용해 sudoers, SSH Key, Repository, Package, Swap, logrotate, CA, sysctl을 순서대로 적용한 뒤 마지막에 VM 상태를 다시 확인합니다.
>
> 그래서 오늘도 같은 순서로 갑니다. 앞 단계가 끝났다는 근거가 없으면 뒤 단계의 성공으로 대신하지 않습니다.

# 2. 원본 0. 사전 요구사항 — Ansible 변경 전에 기준부터 확인한다

> 원본은 Node에 바로 변경을 넣지 않습니다.
>
> 먼저 SCS VM Inventory, 계정 접근 권한, Load Balancer, Repository 접근, ETCD Filesystem과 VM Resource가 준비돼 있는지 확인합니다.
>
> 이 확인은 단순한 체크리스트가 아닙니다. 뒤의 Ansible 명령은 Inventory에 적힌 Host를 대상으로 실제 System 파일과 Package 상태를 변경하기 때문에, 대상과 역할이 틀린 상태에서 실행하면 잘못된 VM을 정확하게 변경할 수 있습니다.

## 2.1. 원본 0-1 — Load Balancer 구성 확인

> 이 항목은 오전 환경 확인에서 이미 다뤘습니다.
>
> 그래서 오후에 Load Balancer를 처음부터 다시 구축하지는 않습니다. 다만 **Node Pre-setting에 들어가기 전에 오전에 확인한 VIP-A·VIP-B와 Backend Role이 여전히 오늘 대상 신규 Member 기준인지** 확인합니다.
>
> VIP-A는 Kubernetes API 경로이고 Master가 Backend입니다. VIP-B는 Ingress 경로이고 Router가 Backend입니다.
>
> 오전에 임시 Backend Listener를 사용해 확인했다면 그 결과가 어느 VIP, 어느 Backend, 어느 Port에 대한 결과였는지 다시 연결해서 설명합니다.
>
> 하지만 LB 확인이 성공했다고 각 Kubernetes Node의 sudo·Repository·Package 상태까지 확인된 것은 아닙니다.
>
> 따라서 LB 결과가 현재 신규 Member 기준이라는 것을 확인한 뒤 원본 다음 항목인 ETCD Filesystem과 VM Resource로 넘어갑니다.

## 2.2. 원본 0-2 — ETCD Filesystem 및 VM Resource 확인

> 이제 실제 Node의 Disk와 Mount를 다시 봅니다.
>
> ETCD는 Kubernetes 상태 데이터를 저장하기 때문에 일반 Application Node와 같은 Data 경로로 취급하면 안 됩니다. 원본도 Node Pre-setting을 적용하기 전에 ETCD의 `/var/lib/etcd` 설계를 확인하도록 되어 있습니다.

```bash
hostnamectl
lsblk -f
df -hT
findmnt /var/lib/containerd /var/lib/etcd
```

> 먼저 `hostnamectl`로 현재 접속한 VM이 어느 Node인지 확인합니다.
>
> 그다음 `lsblk -f`로 Block Device와 Filesystem을 보고, `df -hT`로 실제 Mount 상태를 확인합니다.
>
> 마지막으로 `findmnt`를 이용해 `/var/lib/containerd`와 `/var/lib/etcd`가 어떤 Source와 Filesystem에 연결돼 있는지 확인합니다.
>
> Directory가 존재하는 것과 별도 Filesystem이 Mount돼 있는 것은 다릅니다. 또한 현재 Mount가 보이는 것과 재부팅 뒤에도 같은 설계로 올라오는 것도 별도이므로, 오전에 확인한 `/etc/fstab`과 Role별 Disk 설계를 같이 연결해서 봅니다.
>
> 특히 ETCD의 최종 Mount 설계가 아직 승인되지 않았다면 이후 Ansible 변경을 먼저 진행해 완료 처리하지 않습니다. 어떤 Role에서 어떤 Data 경로를 사용할지 확정된 뒤 다음 단계로 넘어갑니다.

## 2.3. 원본 0-3 — `dspaas` 계정 및 비밀번호 없는 sudo 확인

> Node Pre-setting의 Ansible 명령은 `dspaas` Account를 기준으로 실행됩니다.
>
> 따라서 Account가 존재하고 `wheel` Group에 포함돼 있으며, 실제로 비대화식 sudo가 가능한지 먼저 확인합니다.

```bash
id dspaas
getent group wheel
sudo -n true
```

> `id dspaas`는 Account와 Group Membership을 확인합니다.
>
> `getent group wheel`에서는 `dspaas`가 실제 `wheel` Group에 포함돼 있는지 봅니다.
>
> 그리고 `sudo -n true`는 Password 입력을 기다리지 않고 Root 권한을 사용할 수 있는지 확인합니다.
>
> 여기서 `sudo -n`이 이미 성공하면 현재 passwordless sudo 상태를 확인한 것입니다. 반대로 `dspaas`가 `wheel`에 속하고 승인된 sudo Password로 권한 상승은 가능하지만 `sudo -n`만 실패한다면, 원본 `2-1-1`에서 `-K -k -b`로 접속해 `NOPASSWD` 상태를 만드는 대상입니다.
>
> 따라서 `sudo -n` 실패만으로 원본 `2-1-1` 자체를 막지는 않습니다. 다만 승인된 Credential로 sudo 권한 상승조차 불가능하면 그 상태부터 해결해야 합니다. 이미 passwordless sudo가 정상이어도 `2-1-1`은 건너뛰지 않고 원본이 요구하는 sudoers 상태를 Ansible로 적용·확인합니다.

## 2.4. 원본 0-4 — Node Pre-setting용 Ansible Inventory 생성·확인

> 원본 `0-4`는 Node Pre-setting용 Ansible Inventory를 생성하는 단계입니다. 앞 Bastion 블록에서 이미 생성했다면 여기서는 현재 신규 Member 값으로 검수하고, 아직 없다면 이 단계에서 생성한 뒤 뒤의 Ansible 명령이 어느 Node를 대상으로 실행될지 확인합니다.
>
> 여기서 말하는 Inventory는 **다음 블록에서 만드는 Kubespray `hosts.yaml`이 아닙니다.** Bastion의 SCS Stack 아래 `ansible/inventory`에서 사용하는 **Node Pre-setting용 INI Inventory**입니다.

```bash
su - dspaas
cd /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/ansible
cat inventory
```

> 원본 Host 예시에는 `[master]`, `[etcd]`, `[router]`, `[infra]` 같은 Group이 들어 있지만, 신규 Member에서는 오전에 확인한 실제 Member Role과 Hostname을 기준으로 Inventory를 작성하거나 검수해야 합니다.
>
> Host용 Hostname과 Group을 신규 Member에 복사하지 않습니다. Worker가 포함되는 Member라면 실제 승인된 Member Role 구조를 기준으로 반영합니다.
>
> 여기서 확인할 핵심은 파일 형식보다 **Inventory의 Hostname과 Group이 오늘 실제 작업할 신규 Member Node를 정확하게 가리키는지**입니다.
>
> 이 Inventory가 없거나 다른 Cluster를 가리키고 있으면 `2-1-1`을 시작하지 않습니다.
>
> 이제 사전 요구사항이 끝났습니다. 다음부터는 Bastion에서 이 Inventory를 사용해 실제 Node 상태를 변경합니다.

# 3. 원본 2-1 — Ansible을 사용한 모든 노드 구성

> 여기서부터는 읽기 전용 확인이 아니라 실제 변경이 포함됩니다.
>
> 원본 명령의 `-i inventory`는 방금 확인한 Node Pre-setting용 Inventory를 사용한다는 뜻입니다.
>
> `-k`는 대상 Node의 `dspaas` SSH Password를 요청하는 옵션이고, `-K`는 Become Password를 요청합니다. `-b`는 Root 권한이 필요한 작업을 Become으로 수행한다는 뜻입니다.
>
> 초기에는 SSH Public Key가 아직 전체 Node에 배포되지 않았을 수 있기 때문에 원본은 Password 기반 접근을 사용한 뒤, `2-1-2`에서 Bastion Public Key를 배포해 이후 비밀번호 없는 SSH 경로를 만듭니다.
>
> 또한 원본 Inventory에는 `[bastion]` Group도 있으므로 `ansible all -i inventory ...`는 Bastion까지 포함할 수 있습니다. 반면 `2-1-1`은 `k8s,etcd`만 대상으로 합니다. 따라서 각 단계에서 `all`과 `k8s,etcd`의 실제 대상 범위를 구분해서 확인합니다.

## 3.1. 원본 2-1-1 — sudoers 파일 편집

> 첫 번째 실제 변경은 sudoers입니다.
>
> `dspaas`가 `wheel` Group에 있어도 일반 `wheel` 규칙이 Password를 요구하면 자동화 중 권한 상승이 막힐 수 있습니다.
>
> 그래서 원본은 모든 Kubernetes/ETCD 대상 Node에서 `wheel`의 `NOPASSWD` 규칙을 활성화하고 일반 Password 요구 규칙을 비활성화합니다.

```bash
ansible k8s,etcd -i inventory -m lineinfile \
  -a 'path=/etc/sudoers regexp="^# %wheel\s+ALL=\(ALL\)\s+NOPASSWD: ALL" line="%wheel ALL=(ALL) NOPASSWD: ALL" state=present' \
  -K -k -b

ansible k8s,etcd -i inventory -m shell \
  -a "cat /etc/sudoers | grep %wheel" \
  -K -k -b

ansible k8s,etcd -i inventory -m lineinfile \
  -a 'path=/etc/sudoers regexp="^%wheel\s+ALL=\(ALL\)\s+ALL" line="#%wheel ALL=(ALL) ALL" state=present' \
  -K -k -b

ansible k8s,etcd -i inventory -m shell \
  -a "cat /etc/sudoers | grep %wheel" \
  -b
```

> 첫 번째 `lineinfile`은 `NOPASSWD` 규칙을 활성 상태로 맞춥니다.
>
> 그다음 실제 `/etc/sudoers`의 `wheel` 관련 줄을 확인합니다.
>
> 세 번째 작업은 일반 `%wheel ALL=(ALL) ALL` 규칙을 주석 처리해 Password를 요구하는 규칙과 충돌하지 않도록 원본 상태에 맞춥니다.
>
> 마지막 확인에서는 대상 Node에 `NOPASSWD` 규칙이 활성화되고 일반 `wheel` 규칙이 비활성화됐는지 봅니다.
>
> `CHANGED`라는 단어만 보고 끝내지 않습니다. 원하는 sudoers 줄이 실제로 남았는지가 완료 기준입니다.
>
> sudoers가 준비되면 이제 매번 SSH Password를 입력하지 않도록 Bastion의 Public Key를 Node에 배포합니다.

## 3.2. 원본 2-1-2 — SSH 공개키 복사

> 오전 Bastion 단계에서 SSH Key Pair를 준비했습니다.
>
> 하지만 Bastion에 Key가 존재한다고 Node가 그 Key를 신뢰하는 것은 아닙니다. 이번 단계에서 Bastion `dspaas` Public Key를 대상 Node의 `dspaas` `authorized_keys`에 추가합니다.

```bash
su - dspaas
cd /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/ansible

ansible all -i inventory -m authorized_key \
  -a "user=dspaas state=present key='{{ lookup('file', '/app/dspaas/.ssh/id_rsa.pub') }}'" \
  -k
```

> `authorized_key` Module은 Bastion의 Public Key를 대상 Account의 `authorized_keys`에 추가합니다.
>
> 여기서 Private Key 내용을 Node로 복사하는 것이 아닙니다. Private Key는 Bastion에 남고 Public Key만 대상 Node가 신뢰하도록 등록합니다.
>
> 기존 `authorized_keys`를 통째로 덮어쓰는 방식이 아니라 필요한 Key를 추가하는 방식이라는 점도 설명합니다.
>
> 명령 결과에서 대상 Host가 올바른 신규 Member Node인지, 적용 Account가 `dspaas`인지, Key File 경로가 의도한 위치인지 확인합니다.
>
> 이 단계가 끝나면 Bastion에서 Node로 비밀번호 없는 SSH를 사용할 기반이 생깁니다. 다음 단계에서는 각 Node가 실제 Package를 받을 Repository를 구성합니다.

## 3.3. 원본 2-1-3 — YUM Repository 파일 업데이트

> Bastion에서 Repository를 사용할 수 있었더라도 각 Kubernetes Node가 같은 Repository를 사용할 수 있다는 뜻은 아닙니다.
>
> 실제 Package 설치는 대상 Node에서 수행되기 때문에 Node별 Repository 설정이 필요합니다.
>
> 원본은 `yum_repository` Module을 사용해 Docker, AppStream, BaseOS, Kubernetes Repository를 구성하고 Metadata Cache를 정리합니다.

```bash
ansible all -i inventory -m yum_repository \
  -a "name=Artifactory-docker file=docker baseurl=<신규-Member-승인-docker-repository> enabled=yes gpgcheck=false description=Artifactory-docker" \
  -b

ansible all -i inventory -m yum_repository \
  -a "name=appstream file=base baseurl=<신규-Member-승인-appstream-repository> enabled=yes gpgcheck=false description=appstream" \
  -b

ansible all -i inventory -m yum_repository \
  -a "name=base file=base baseurl=<신규-Member-승인-baseos-repository> enabled=yes gpgcheck=false description=base" \
  -b

ansible all -i inventory -m yum_repository \
  -a "name=Artifactory-k8s file=kubernetes baseurl=<신규-Member-승인-kubernetes-repository> enabled=yes gpgcheck=false description=Artifactory-k8s" \
  -b

ansible all -i inventory -m shell -a "dnf clean all" -b
```

> 여기의 Repository URL은 원본 Host/Taylor 값을 복사하지 않고 오늘 확인한 신규 Member 승인값을 사용합니다.
>
> Repository 파일이 생성됐다는 것만으로 실제 사용 가능하다고 판단하지 않습니다. 그래서 원본은 이어서 `dnf repolist`로 활성 Repository를 확인합니다.

```bash
ansible all -i inventory -m shell -a "dnf repolist" -b
```

> 여기서 확인하는 것은 Node가 현재 승인된 Repository를 인식하는지입니다.
>
> 하지만 `repolist`가 보인다고 필요한 Package가 실제로 설치된 것은 아닙니다. 그 검증은 바로 다음 원본 `2-1-4 Package 설치`에서 수행합니다.

## 3.4. 원본 2-1-4 — 필수 Package 설치

> Repository가 준비됐으므로 이제 Node Pre-setting에 필요한 Package를 실제로 설치합니다.
>
> 원본 Package 목록에는 Network 확인, LVM·Storage, SSH·TLS, NFS, 운영 점검에 필요한 도구가 포함됩니다.

```bash
ansible all -i inventory -m dnf \
  -a "name=net-tools,yum-utils,bind-utils,device-mapper-persistent-data,lvm2,nmap,bash,bash-completion,openssh,openssl,nfs-utils,wget,tcpdump,tree,cloud-utils-growpart,sg3_utils,ncurses-compat-libs.x86_64 state=present" \
  -b
```

> `bind-utils`는 DNS 확인에 사용하고, `lvm2`와 `device-mapper-persistent-data`는 LVM/Block Storage 작업에 필요합니다. `nfs-utils`는 이후 NFS Storage 경로를 사용할 때 필요하고, `openssl`은 Certificate 확인에 사용합니다.
>
> 이 단계에서는 Package 이름을 외우게 하는 것이 목적이 아닙니다. **앞에서 만든 승인 Repository를 통해 뒤 단계와 Kubernetes 운영에 필요한 Tool이 실제 Node에 준비되는 과정**이라는 연결을 설명합니다.
>
> Ansible 결과가 `CHANGED`이면 새로 설치된 Package가 있다는 뜻이고, 이미 설치돼 있으면 변경 없이 정상일 수 있습니다.
>
> Package 준비가 끝나면 Kubernetes 설치 전 OS 조건 중 가장 먼저 Swap을 정리합니다.

## 3.5. 원본 2-1-5 — SWAP 비활성화

> Kubernetes 설치 전에 모든 대상 Node에서 Swap을 비활성화합니다.
>
> 여기서 현재 Swap을 끄는 작업과 재부팅 뒤에도 다시 올라오지 않게 만드는 작업을 구분해야 합니다.

```bash
ansible all -i inventory -m shell -a "swapoff -a" -b
ansible all -i inventory -m shell -a "cp /etc/fstab /etc/fstab.bak" -b
ansible all -i inventory -m lineinfile -a 'path=/etc/fstab regexp=swap state=absent' -b
```

> 먼저 `swapoff -a`로 현재 Runtime의 Swap을 비활성화합니다.
>
> 그다음 `/etc/fstab`을 백업하고 Swap 항목을 제거합니다. 이 작업이 필요한 이유는 지금 Swap이 0이어도 `fstab`에 항목이 남아 있으면 다음 Boot에서 다시 활성화될 수 있기 때문입니다.
>
> 원본은 현재 상태와 영속 설정을 각각 확인합니다.

```bash
ansible all -i inventory -m shell -a "free -h | grep -i swap" -b
ansible all -i inventory -m shell -a "cat /etc/fstab | grep swap" -b
```

> `free -h`에서 Swap이 0으로 보이면 현재 Runtime은 비활성 상태입니다.
>
> `grep swap`이 결과 없이 종료되면 `fstab`에 Swap 항목이 남아 있지 않은지 확인할 수 있습니다. 이 경우 `grep`의 반환코드 1은 검색 결과가 없다는 의미일 수 있으므로 Ansible의 `FAILED` 표기만 보고 곧바로 작업 실패로 단정하지 않습니다.
>
> 원본에는 Swap LV 자체를 제거하는 절차도 있지만 **현재 신규 Member의 Volume Group과 Logical Volume 이름이 확정된 경우에만 승인 절차로 수행**합니다.

```bash
ansible all -i inventory -m lvol \
  -a "vg=<신규-Member-승인-volume-group> lv=swap state=absent force=yes" \
  -b
```

> 과거 `vgroot`나 다른 Cluster의 LV 이름을 그대로 사용하지 않습니다.
>
> Swap이 끝나면 원본 다음 항목인 logrotate 설정으로 넘어갑니다.

## 3.6. 원본 2-1-6 — logrotate 압축 설정

> 이 항목은 기존 새 작성본에서 빠져 있었지만 원본 Node Pre-setting의 독립된 단계입니다.
>
> Kubernetes와 Platform 운영에서는 System Log가 지속적으로 쌓입니다. logrotate가 Log를 회전하더라도 압축하지 않으면 제한된 Filesystem을 더 빠르게 사용할 수 있습니다.
>
> 그래서 원본은 `/etc/logrotate.conf`에서 `compress`를 활성화합니다.

```bash
ansible all -i inventory -m lineinfile \
  -a "path=/etc/logrotate.conf regexp='^#compress' line=compress" \
  -b
```

> 환경에 따라 원본 파일에 `#compress` 또는 `# compress`처럼 공백 차이가 있을 수 있으므로 실제 파일 상태를 확인하면서 적용합니다.
>
> 여기서 확인하는 것은 단순히 Ansible이 `CHANGED`를 반환했는지가 아니라 `/etc/logrotate.conf`의 압축 정책이 의도한 상태로 반영됐는지입니다.
>
> logrotate까지 끝나면 Private Registry와 내부 HTTPS 연결에 필요한 CA를 Node에 배포합니다.

## 3.7. 원본 2-1-7 — SECDS-ROOTCA CA 인증서 배포

> Kubernetes Node는 이후 Private Registry와 내부 HTTPS Endpoint를 사용합니다.
>
> 그래서 원본은 Bastion Bundle 안의 승인된 `SECDS-ROOTCA.crt`를 대상 Node의 Container Runtime Certificate 경로와 OS Trust Store에 배포합니다.
>
> 먼저 현재 Bundle 안에 실제 어떤 `SECDS-*.crt` 파일이 있는지 확인합니다.

```bash
find /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0 -maxdepth 2 -name 'SECDS-*.crt' -print
```

> 파일명이 과거 예시와 같다는 이유만으로 같은 인증서라고 가정하지 않습니다. 현재 승인된 Bundle에 포함된 파일을 사용합니다.
>
> 그다음 대상 Node에 Container Runtime용 Certificate Directory를 만들고 CA를 배포합니다.

```bash
ansible all -i inventory -m file \
  -a "path=/etc/containerd/certs.d/ state=directory owner=root group=root mode=0755" \
  -b

ansible all -i inventory -m copy \
  -a "src=/app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/SECDS-ROOTCA.crt dest=/etc/containerd/certs.d/ mode=0644 owner=root group=root" \
  -b
```

> 그리고 같은 CA를 OS Trust Anchor에도 배포한 뒤 Trust Database를 갱신합니다.

```bash
ansible all -i inventory -m copy \
  -a "src=/app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/SECDS-ROOTCA.crt dest=/etc/pki/ca-trust/source/anchors/SECDS-ROOTCA.crt mode=0644 owner=root group=root" \
  -b

ansible all -i inventory -m shell -a "update-ca-trust" -b
```

> `/etc/containerd/certs.d/`에 파일이 있다는 것과 OS Trust Store에 등록됐다는 것은 서로 다른 적용 위치입니다.
>
> 그래서 이 단계에서는 **Bundle의 승인 CA가 대상 Node의 Runtime 관련 Certificate 경로와 OS Trust에 배포되고 `update-ca-trust`까지 수행됐는지** 확인합니다.
>
> 다만 CA 파일 복사 성공만으로 실제 Registry Image Pull까지 검증한 것은 아닙니다. 실제 Registry와 Container Runtime 동작 검증은 이후 단계에서 현재 Registry 설정과 함께 확인합니다.
>
> CA 배포가 끝나면 원본 다음 항목인 `sysctl.conf`를 구성합니다.

## 3.8. 원본 2-1-8 — sysctl.conf 구성

> 이 단계는 막연하게 Kernel Tuning을 전부 수행하는 단계가 아닙니다.
>
> 원본은 **Xi'an VM Image에서 IPv6가 비활성화된 경우 `/etc/sysctl.conf`의 IPv6 관련 설정을 주석 처리해 Kubespray와 충돌하지 않도록 하는 작업**을 명시하고 있습니다.

```bash
ansible all -i inventory -m shell -b \
  -a "sed -i '/ipv6/s/^/#/g' /etc/sysctl.conf"

ansible all -i inventory -m shell -b \
  -a "cat /etc/sysctl.conf"

ansible all -i inventory -m shell -b \
  -a "sysctl -p"
```

> 먼저 실제 VM에서 IPv6가 비활성화된 조건인지 확인한 뒤 이 작업을 적용합니다. 조건을 확인하지 않고 모든 환경에 같은 `sed` 명령을 기계적으로 적용하지 않습니다.
>
> 첫 번째 명령은 `sysctl.conf`의 IPv6 관련 줄을 주석 처리합니다.
>
> 두 번째 명령에서 실제 파일이 의도한 상태로 바뀌었는지 확인합니다.
>
> 마지막 `sysctl -p`는 파일 내용을 현재 Runtime Kernel Parameter에 다시 적용합니다.
>
> 따라서 파일을 수정한 상태와 실제 Runtime에 반영된 상태를 구분해서 설명합니다.
>
> 여기까지 Node 변경이 끝나면 마지막으로 전체 Node의 현재 VM Resource와 주요 설정을 한 번에 확인합니다.

## 3.9. 원본 2-1-9 — VM Resource 최종 확인

> 마지막 단계에서는 지금까지 변경한 결과와 처음 확인한 VM 설계가 서로 맞는지 전체 Node에서 다시 확인합니다.
>
> 원본은 Hostname, IP, OS, CPU, Memory, Filesystem, DNS와 Time Source를 한 번에 조회합니다.

```bash
ansible all -i inventory -m shell \
  -a "hostname && hostname -i && cat /etc/os-release | head -2 && nproc && free -h && df -h && cat /etc/resolv.conf && chronyc sources" \
  -b
```

> `hostname`과 `hostname -i`는 Inventory가 가리킨 대상과 실제 Node Identity를 다시 대조하는 데 사용합니다.
>
> `/etc/os-release`, `nproc`, `free -h`에서는 승인된 OS·CPU·Memory와 맞는지 봅니다. 여기서 Swap도 다시 0인지 확인할 수 있습니다.
>
> `df -h`에서는 Role별 Filesystem을 봅니다. Master·Router·Infra·Worker와 ETCD는 Data 경로의 목적이 다르므로 한 Node의 출력으로 다른 Role을 대신하지 않습니다.
>
> 특히 ETCD는 승인된 `/var/lib/etcd` 설계가 실제로 반영돼 있는지 확인합니다. 신규 Member의 실제 Disk 설계가 원본 Host 표와 다르면 신규 Member 승인 설계를 우선합니다.
>
> `/etc/resolv.conf`에서는 현재 Nameserver가 의도한 값인지 확인하고, `chronyc sources`에서는 설정 파일이 아니라 실제 Time Source와 동기화 상태를 봅니다.
>
> 마지막 출력은 단순한 정보 수집이 아닙니다. **앞에서 수행한 Node Pre-setting이 올바른 Host 전체에 적용됐고, 각 Node가 다음 Kubespray 준비 단계로 넘어갈 기본 상태를 갖췄는지 최종 대조하는 단계**입니다.

# 4. Node Pre-setting 완료 범위를 정리한다

> 여기까지 끝났다고 Kubernetes Cluster가 설치된 것은 아닙니다.
>
> 오늘 확인한 범위는 각 Node가 Kubespray 작업을 받을 수 있도록 사전 조건을 준비한 것입니다.
>
> 먼저 대상 Node와 Role, Filesystem을 확인했습니다. 그다음 `dspaas`와 Node Pre-setting용 Ansible Inventory를 확인했습니다.
>
> 이후 원본 순서대로 sudoers를 맞추고 SSH Public Key를 배포했습니다. Repository를 구성한 뒤 실제 Package를 설치했고, Swap과 logrotate를 정리했습니다.
>
> 그리고 승인 CA를 Runtime/OS Trust 경로에 배포하고, VM 조건에 맞는 `sysctl.conf`를 적용했습니다.
>
> 마지막으로 전체 Node에서 Hostname·IP·OS·CPU·Memory·Filesystem·DNS·Time을 다시 확인했습니다.
>
> 따라서 이 단계의 완료는 **"SSH가 된다"**가 아니라 **"원본 Node Pre-setting의 0번 진입조건과 2-1-1~2-1-9 작업을 현재 신규 Member 기준으로 순서대로 확인·적용했고 마지막 전체 Node 상태까지 대조했다"**는 상태입니다.

# 5. 문제가 생기면 원본의 처음 실패 단계부터 확인한다

> 장애가 발생하면 뒤 단계의 설정을 임의로 바꾸지 않습니다.
>
> `0-2`에서 Filesystem이 다르면 Package나 CA를 먼저 수정하지 않습니다. 현재 Role과 Disk 설계부터 확인합니다.
>
> `0-3`에서 `dspaas` 또는 sudo가 안 되면 Repository로 넘어가지 않습니다.
>
> `2-1-1`에서 Become이 실패하면 SSH 자체가 되는지와 현재 Account·sudoers 규칙을 확인합니다.
>
> `2-1-2`에서 Public Key 배포가 실패하면 대상 Hostname·IP, Account Home, SSH 접근을 확인합니다.
>
> `2-1-3`에서 Repository가 실패하면 공개 인터넷 Repository를 임시로 추가하지 않고 승인 URL, DNS·Network와 현재 OS를 확인합니다.
>
> `2-1-4`에서 Package 설치가 실패하면 앞에서 구성한 Repository와 Package 존재·Dependency를 봅니다.
>
> `2-1-5`에서 Swap이 남으면 Runtime인지 `fstab`인지, 별도 LV인지 구분합니다. LV 삭제는 승인된 VG/LV가 확정된 경우에만 수행합니다.
>
> `2-1-6`에서 logrotate가 예상과 다르면 실제 `/etc/logrotate.conf`의 기존 줄 형태를 확인합니다.
>
> `2-1-7`에서 CA 작업이 실패하면 Source CA 파일, Destination Directory, Permission과 `update-ca-trust` 결과를 순서대로 봅니다.
>
> `2-1-8`에서 `sysctl -p`가 실패하면 어떤 IPv6/Kernel Parameter가 문제인지 오류 원문과 현재 VM의 IPv6 조건을 확인합니다.
>
> 마지막 `2-1-9` 결과가 승인 VM 정보와 다르면 이전 단계가 `CHANGED`였다는 이유로 완료 처리하지 않습니다. 실제 차이를 남기고 해당 원본 단계로 돌아갑니다.

# 7. 마무리

> 오늘은 Node Pre-setting을 새로운 개념 순서로 다시 묶지 않고 Cluster Setup 원본 순서대로 수행했습니다.
>
> 먼저 `0-1`부터 `0-4`까지 진입조건을 확인했습니다. 그다음 `2-1-1 sudoers`부터 `2-1-9 VM Resource 확인`까지 원본 작업을 하나씩 따라갔습니다.
>
> 각 단계에서는 명령 자체보다 **왜 이 순서에서 필요한지, 무엇을 변경하는지, 결과가 어디까지 성공을 의미하는지**를 함께 확인했습니다.
>
> Repository 설정과 Package 설치는 다른 단계였고, 현재 Swap 비활성화와 재부팅 후 유지도 구분했습니다. logrotate도 독립된 원본 단계로 수행했고, CA 배포와 sysctl도 실제 원본 작업 범위를 기준으로 설명했습니다.
>
> **결국 Kubernetes Node Pre-setting의 완료는 원본 Runbook의 작업을 현재 신규 Member 실제값으로 순서대로 수행하고, 마지막에 전체 Node의 실제 상태가 다음 Kubespray 단계로 넘어갈 조건을 만족하는지 확인한 상태입니다.**
