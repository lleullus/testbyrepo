# Kubernetes Node Pre-setting 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 오전에는 Bastion을 설치 기준점으로 준비했다. 이번 블록은 **각 Kubernetes Node가 Bastion의 자동화를 받을 수 있는 상태인지 확인하는 과정**이다.
>
> SSH Key 배포, sudoers, Repository, Package, Swap, Kernel·Network, CA와 Filesystem 변경은 승인된 Node Pre-setting Runbook을 따른다. 파괴적 Storage 변경은 별도 승인 없이 실행하지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
Bastion을 준비했다
→ 하지만 각 Node의 상태는 별도다
→ 먼저 실제 대상 Node가 맞는지 확인한다
→ SSH와 sudo를 확인한다
→ 승인 Repository에서 Package를 받는다
→ Kubernetes가 요구하는 OS 상태를 맞춘다
→ Private Registry 신뢰를 확인한다
→ Role별 Filesystem과 Time을 확인한다
→ 전체 Node 결과를 Inventory에 넘긴다
```

## 0-1. 오늘 전체 한 줄

> Node Pre-setting은 설정을 많이 적용하는 작업이 아닙니다. **올바른 Node가 자동화에 필요한 접근·권한·Package·OS·Registry·Filesystem 조건을 갖췄는지 확인하는 작업**입니다.

---

# 1. 시작 — Bastion이 준비돼도 Node는 별도로 확인해야 한다

> 오전에는 Bastion에서 신규 Member Node 이름을 찾고, `dspaas` 권한과 Repository, Bundle, Toolchain, SSH 인증 재료를 준비했습니다.
>
> 그래서 자동화를 시작할 서버는 준비됐습니다.
>
> **하지만 Master·ETCD·Router·Infra·Worker가 같은 상태라는 뜻은 아닙니다.** SSH는 되지만 sudo가 안 될 수 있고, Package는 있지만 Swap이나 Kernel 상태가 다를 수 있습니다.
>
> 또한 Registry에 도달해도 Certificate를 신뢰하지 못하면 Image Pull이 실패합니다.
>
> 따라서 한 Node에서 `대상 → SSH → sudo → Package → OS → Registry Trust → Filesystem·Time`을 확인한 뒤 같은 방식으로 전체 Node를 봅니다.

---

# 2. 먼저 실제 대상 Node가 맞는지 확인한다

> Bastion에서 어떤 Host에 SSH가 된다고 하겠습니다.
>
> 그러면 그 주소로 접속할 수 있다는 것은 알 수 있습니다. **하지만 그 Host가 승인된 신규 Member Node라는 뜻은 아닙니다.**
>
> 잘못된 IP가 다른 Server를 가리키고 있어도 같은 Credential을 받아주면 접속은 성공할 수 있습니다.
>
> 그래서 Bastion이 사용하는 Hostname·IP와 원격 Node가 보고하는 Hostname·IP를 확인하고, 오전의 Role·Hostname·IP와 대조합니다.
>
> 세 결과가 같은 VM을 가리킬 때 대상 확인이 끝납니다. 다르면 sudo나 Package를 수정하지 않고 대상부터 바로잡습니다.

---

# 3. SSH — Bastion에서 실제 Node에 접속할 수 있어야 한다

> 오전에 SSH Key Pair를 준비했지만 Bastion에 Key가 있다는 것만으로 Node 접근은 완료되지 않습니다.
>
> Public Key가 올바른 Node의 `dspaas`에 배포돼야 하고, Bastion에서 같은 Account로 비대화식 SSH가 성공해야 합니다.
>
> SSH 성공은 Bastion에서 Node까지 Network와 인증 경로가 열렸다는 뜻입니다.
>
> **하지만 System 설정을 바꿀 권한까지 확인한 것은 아닙니다.** 그래서 같은 Session에서 sudo를 확인합니다.

---

# 4. sudo — Login과 Root 작업은 다르다

> Kubespray는 Package를 설치하고 System 설정을 변경하므로 Root 권한이 필요합니다.
>
> sudoers 파일에 설정이 있고 `visudo -c`가 성공해도 실제 `dspaas`가 비대화식 sudo를 사용할 수 있는지는 별도입니다.
>
> 그래서 자동화를 실행할 같은 Account와 Session에서 `sudo -n`을 확인합니다. Root Account의 성공으로 대신하지 않습니다.
>
> 실패하면 Network나 Kubernetes 설정으로 가지 않고 Group, sudo 정책과 Session을 확인합니다.
>
> SSH와 sudo가 준비되면 Node에서 작업할 수 있습니다. **하지만 필요한 Package를 받을 수 있어야 실제 준비가 가능합니다.**

---

# 5. Repository와 Package — 승인된 Source에서 실제 설치 재료를 받는다

> Kubernetes 설치 전에는 Network·Storage·TLS·운영 확인에 필요한 Package가 준비돼야 합니다.
>
> Xi'an에서는 승인된 내부 Repository를 사용합니다.
>
> Bastion에서 Repository를 사용할 수 있었다고 각 Kubernetes Node에서도 같은 Repository를 사용할 수 있다는 뜻은 아닙니다. 실제 Package 설치는 대상 Node에서 수행되므로 Node별 DNS·Network와 Repository 설정이 같이 맞아야 합니다.
>
> `.repo` 파일이나 URL이 있다는 것만으로는 충분하지 않습니다. Node에서 Metadata를 읽고, 필요한 Package를 설치하며, 실제 설치 결과를 확인합니다.
>
> DNS나 Network가 막혀 있으면 URL이 맞아도 사용할 수 없습니다.
>
> 반대로 Package가 이미 설치돼 있다고 현재 Repository 경로가 정상이라고 판단하지 않습니다. 기존 Cache나 과거 설치 결과가 남아 있으면 현재 Repository를 사용하지 않고도 명령이 성공해 보일 수 있습니다.
>
> 따라서 실패했다고 공개 인터넷 Repository를 임시로 추가하지 않습니다. 승인 URL, DNS·Network, OS Version과 Package 상태를 순서대로 확인합니다.
>
> 여기서 확인하는 것은 Package 이름을 외우는 것이 아니라 **현재 Node가 승인된 Source에서 이후 Kubernetes 설치에 필요한 재료를 다시 받을 수 있는 상태인지**입니다.
>
> Package 목록과 정확한 명령은 Runbook을 따릅니다.

---

# 6. OS 상태 — 현재 상태와 재부팅 후 상태를 함께 본다

> Package가 준비돼도 Kubernetes가 기대하는 OS 상태가 아니면 설치가 실패할 수 있습니다.
>
> 대표적인 예가 Swap입니다. `swapoff` 뒤 현재 사용량이 0이면 지금은 비활성 상태입니다.
>
> **하지만 `/etc/fstab`이나 LVM 설정에 Swap이 남아 있으면 다음 Boot에서 다시 활성화될 수 있습니다.**
>
> 그래서 현재 Runtime과 영속 설정을 함께 확인합니다.
>
> Swap LV 제거처럼 Storage 구조를 바꾸는 작업은 단순한 비활성화가 아닙니다. 승인된 Volume 설계와 Runbook을 확인한 뒤 수행합니다.
>
> Kernel과 Network도 같습니다. Kubernetes가 사용하는 Kernel Module이나 `sysctl` 값은 설정 파일에 적혀 있는 것만으로 충분하지 않습니다. 현재 Kernel에 Module이 실제로 Load됐는지, 필요한 Network Parameter가 Runtime에 적용됐는지 확인해야 합니다.
>
> 예를 들어 설정 파일을 수정했어도 아직 Reload되지 않았다면 현재 동작은 이전 값일 수 있습니다. 반대로 Runtime에서만 값을 바꿨다면 재부팅 뒤 다시 원래 상태로 돌아갈 수 있습니다.
>
> 그래서 Swap과 마찬가지로 Kernel·Network도 **현재 동작 상태와 다음 Boot 뒤 유지될 설정을 함께 봅니다.**
>
> OS 조건까지 맞아도 Private Registry 신뢰가 없으면 Image를 받을 수 없습니다.

---

# 7. Registry Trust — CA 파일보다 실제 HTTPS 검증이 중요하다

> Kubernetes Node는 Private Registry에서 설치 Image와 Application Image를 가져옵니다.
>
> 그래서 승인된 CA를 OS와 Container Runtime의 Trust 구조에 연결해야 합니다.
>
> CA 파일 이름이 같다고 같은 Certificate는 아닙니다. 파일이 존재한다고 Trust 갱신이 끝난 것도 아니며, OS Trust와 Runtime Trust가 자동으로 같은 것도 아닙니다.
>
> OS의 `curl`이 Certificate를 신뢰하는 것과 Container Runtime이 Registry를 신뢰하는 것도 구분합니다. 서로 다른 Trust Store나 Registry 설정을 사용하면 OS에서는 HTTPS가 성공해도 실제 Image Pull은 실패할 수 있습니다.
>
> 따라서 승인된 CA Source, 배포 파일, Trust 적용 상태와 Runtime Registry 설정을 확인합니다.
>
> 먼저 CA가 현재 승인된 Registry Certificate Chain과 맞는지 확인하고, 그다음 OS Trust와 Runtime 쪽 설정이 같은 Registry를 대상으로 하고 있는지 봅니다.
>
> 마지막에는 Certificate 검증을 생략하지 않은 HTTPS 경로로 실제 신뢰를 확인합니다.
>
> `curl -k` 성공은 Network와 Server 응답 일부만 보여 줄 뿐 정상 Certificate Trust를 증명하지 않습니다.
>
> 따라서 이 단계의 완료는 CA 파일을 복사한 상태가 아니라 **Node가 현재 승인 Registry를 정상 Certificate 검증으로 사용할 준비가 된 상태**입니다.

---

# 8. 마지막으로 Role별 Filesystem과 Time을 확인한다

> 공통 설정이 모두 성공해도 Role별 Filesystem 차이는 남아 있습니다.
>
> Master·Router·Infra·Worker는 승인된 Container Runtime Data 경로를 사용해야 합니다. Container Image와 Runtime Data가 쌓이는 위치이므로 단순히 Directory가 존재하는 것이 아니라 승인된 Filesystem이 실제로 해당 경로에 Mount돼 있어야 합니다.
>
> 반면 ETCD는 Kubernetes 상태 데이터를 저장하므로 승인된 ETCD Data 경로가 필요합니다. 일반 Node의 Container Runtime 경로를 그대로 적용하지 않습니다.
>
> `/app`도 설치 파일과 작업 기준을 두는 경로이므로 Role별 현재 설계에 맞는 Filesystem을 확인합니다. Directory 이름만 같고 실제 Mount Source가 다르면 같은 구성으로 보지 않습니다.
>
> 그리고 `mount` 결과가 정상이어도 재부팅 뒤 같은 Filesystem이 자동으로 올라오는지는 별도입니다. 따라서 실제 Mount Source·Filesystem과 영속 Mount 설정이 같은 설계를 가리키는지 함께 봅니다.
>
> ETCD Mount 설계가 미확정이면 다음 단계로 넘기지 않습니다.
>
> Time도 설정 파일만 보지 않습니다. 승인 Time Source와 실제 동기화 상태를 확인합니다.
>
> Time Source가 파일에 있어도 실제 동기화가 되지 않으면 Node 시간은 계속 어긋날 수 있습니다. 반대로 현재 시간이 비슷하다는 이유만으로 승인 Time Source와 동기화되고 있다고 판단하지 않습니다.
>
> Node 간 시간이 어긋나면 인증서 유효시간 판단, 로그 비교와 분산 상태 확인에 문제가 생길 수 있습니다.
>
> 그래서 이 단계에서는 **Role에 맞는 Data 경로가 현재와 재부팅 후에도 유지되고, Node 시간이 승인 Source와 실제로 동기화되는지**까지 확인합니다.

---

# 9. 전체 Node에서 같은 기준으로 확인한다

> 대표 Master 하나가 성공했다고 ETCD·Router·Infra·Worker까지 성공한 것은 아닙니다.
>
> 그래서 먼저 대표 Node에서 현재 상태와 승인 변경이 맞는지 확인한 뒤 같은 Role로 확대합니다. 같은 Role로 확대할 때도 원격 Hostname·IP와 최종 상태를 다시 확인합니다.
>
> 그다음 다른 Role을 확인하고, 마지막에는 모든 신규 Member Node의 SSH, sudo, Package, OS, Registry Trust, Filesystem과 Time 결과를 정리합니다.
>
> `SUCCESS`나 `CHANGED` 개수보다 각 Node에서 실제로 확인된 상태가 중요합니다.

---

# 10. 문제가 생기면 처음 실패한 단계부터 확인한다

> `UNREACHABLE`이면 Package나 Swap을 보지 않습니다. Hostname·IP, DNS·Network와 SSH를 확인합니다.
>
> SSH는 되는데 sudo가 실패하면 Network는 통과했습니다. 같은 `dspaas`의 Group과 sudo 정책을 봅니다.
>
> Repository Metadata가 열리지 않으면 승인 URL, DNS·Network와 OS 차이를 확인합니다.
>
> Registry Trust가 실패하면 CA Source, 배포 파일, Trust 적용, Runtime 설정과 실제 HTTPS 순서로 봅니다.
>
> Filesystem이 다르면 sudo나 CA를 다시 수정하지 않고 Role과 승인 Mount 설계, 실제 Mount를 확인합니다.
>
> 확인 순서는 `대상 → SSH → sudo → Repository·Package → OS → Registry Trust → Filesystem·Time`입니다.

---

# 11. Inventory에는 확인된 Node 상태를 넘긴다

> 다음 블록에서는 Node를 Kubespray Inventory와 변수 파일에 표현합니다.
>
> 그래서 각 Node의 Role·Hostname·IP와 SSH·sudo 결과를 넘깁니다. Repository·Package, 현재와 영속 OS 상태, Registry Trust, Filesystem과 Time 결과도 전달합니다.
>
> 실패하거나 미확정인 Node는 첫 실패 단계와 함께 그대로 남깁니다.
>
> **Inventory는 현실을 대신 만드는 파일이 아니라 확인된 Node 상태를 표현하는 파일이어야 합니다.**

---

# 12. 마무리

> Bastion이 준비돼도 각 Node의 상태는 별도로 확인해야 했습니다.
>
> 그래서 대상 Node를 확인하고 SSH와 sudo를 검증했습니다. 그다음 승인 Repository와 Package, 현재와 영속 OS 상태, Registry Trust를 확인했습니다.
>
> 마지막으로 Role별 Filesystem과 Time을 확인하고 전체 Node 결과를 정리했습니다.
>
> **결국 Node Pre-setting의 완료는 올바른 Node가 Kubespray 작업을 받을 수 있는 조건을 실제로 갖춘 상태입니다.**

---

# 13. 마지막 확인 질문

1. Bastion이 준비돼도 각 Kubernetes Node를 따로 확인해야 하는 이유는 무엇인가?
2. SSH 성공 뒤에도 원격 Hostname·IP를 확인해야 하는 이유는 무엇인가?
3. 한 Role의 대표 Node 성공을 다른 Role에 바로 적용하면 안 되는 이유는 무엇인가?
4. SSH와 비대화식 sudo는 각각 무엇을 증명하는가?
5. Repository 파일 존재와 실제 Package 공급 성공은 무엇이 다른가?
6. 현재 Swap 비활성화와 재부팅 후 유지 상태는 왜 다른가?
7. CA 파일 존재와 실제 Registry Trust는 무엇이 다른가?
8. `curl -k` 성공이 정상 Trust를 증명하지 못하는 이유는 무엇인가?
9. ETCD Filesystem을 일반 Node와 별도로 보는 이유는 무엇인가?
10. Inventory 단계에 어떤 Node 상태를 넘겨야 하는가?
