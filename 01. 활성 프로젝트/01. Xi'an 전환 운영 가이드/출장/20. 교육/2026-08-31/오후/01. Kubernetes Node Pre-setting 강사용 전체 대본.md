# Kubernetes Node Pre-setting 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 오전에 검증한 신규 Member와 Bastion을 이용해 **각 Kubernetes Node가 Kubespray 작업을 받을 준비가 됐는지 판단하는 법**을 가르친다. Package 설치, sudoers 변경, Swap·CA·sysctl 수정 같은 정확한 변경 절차는 Node Pre-setting Runbook에서 수행한다. 강의의 핵심은 **연결 성공을 준비 완료로 확대하지 않고, 같은 질문을 모든 Node에 적용하되 Role 차이를 보존하며, Canary에서 검증한 뒤 필요한 범위로만 확대하는 것**이다.

## 0. 앞 블록에서 이어받는 것

오전에는 이미 다음을 확보했다.

```text
신규 Member Node Role·Hostname·IP
Bastion Identity
DNS·hosts 기능 확인
Bastion sudo 기능 확인
승인 Repository
승인 Bundle·Toolchain
SSH Public Key 기준
Disk·Filesystem 확인 결과
미확정값과 중단 항목
```

> 이번 블록에서는 이 값을 다시 추측하지 않습니다. **앞에서 확인한 사실을 Node 작업의 입력으로 사용합니다.**

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> SSH가 된다는 사실만으로 Node 준비 완료라고 판단하지 않고, **Identity → Access → Privilege → Package → OS 조건 → Registry 신뢰 → Filesystem·Time**의 최소 증거를 같은 Node에서 확인하며, 한 Node의 성공 범위를 다른 Role까지 확대하지 않을 수 있어야 한다.

오늘의 중심 질문:

> **Kubespray가 이 Node에서 실제 작업을 수행할 수 있다는 것을 무엇으로 증명하고, 그 증거를 어느 범위까지 확대할 수 있는가?**

---

# 1. 시작 — SSH 성공은 출발점일 뿐이다

> 오전에는 신규 Member의 실제 VM과 Bastion을 확인했습니다.
>
> 이제 Master, ETCD, Router, Infra, Worker가 Kubespray Task를 받을 수 있도록 준비합니다.
>
> Bastion에서 SSH가 된다는 것은 Network와 인증의 일부가 통과했다는 뜻입니다.
>
> **하지만**, Ansible이 Root 권한으로 Package를 설치하고 Kubernetes가 요구하는 OS·Network·Filesystem 조건을 사용할 수 있다는 뜻은 아닙니다.

Node 준비는 다음 질문 하나씩을 닫아가는 과정이다.

```text
이 Node가 맞는가
→ Bastion에서 도달할 수 있는가
→ 자동화 Account가 Root 작업을 할 수 있는가
→ 승인된 Package 공급 경로를 사용할 수 있는가
→ Kubernetes가 요구하는 OS 조건이 맞는가
→ Private Registry를 신뢰할 수 있는가
→ Role에 맞는 Filesystem과 Time 상태인가
```

---

# 2. 한 번에 전체 Node를 바꾸지 않는다

> Ansible의 장점은 같은 작업을 여러 Node에 빠르게 적용하는 것입니다. 대상이나 절차가 틀리면 잘못된 변경도 같은 속도로 퍼집니다.

따라서 변경은 다음 사고 순서로 진행한다.

```text
전체 Node 읽기 전용 비교
→ Role별 대표 Canary 선택
→ Canary에서 승인된 변경
→ 바로 기능 검증
→ 같은 Role에만 확대
→ 전체 Node 재검증
```

## 2.1 Canary가 증명하는 범위

```text
Canary 성공
= 그 대상·그 Role·그 조건에서 변경 방법과 검증이 성립함

Canary 성공
≠ 다른 Role의 Disk·Package·배치 조건까지 같음
```

> Master에서 성공한 절차를 ETCD·Router·Infra·Worker에 자동으로 같은 의미로 확대하지 않습니다. 확대 전에 **무엇이 공통이고 무엇이 Role별 차이인지** 확인합니다.

## 2.2 변경 전 반드시 말할 것

```text
어느 Cluster인가
어느 Host·Role인가
현재 상태는 무엇인가
무엇을 바꾸려는가
성공을 무엇으로 확인할 것인가
실패하면 어디에서 멈출 것인가
```

> 이 질문에 답하지 못하면 Runbook의 변경 명령으로 넘어가지 않습니다.

---

# 3. 첫 증거 — Inventory가 가리킨 Node와 실제 Node가 같은가

> Ansible 명령이 안전해도 Inventory가 틀리면 잘못된 Node에서 정확하게 실행됩니다.

먼저 두 가지를 구분한다.

```text
Inventory Graph 정상
= Host와 Group 관계를 읽을 수 있음

Ansible Ping SUCCESS
= 지정된 대상으로 SSH하고 Python Module을 실행할 수 있음
```

둘 다 아직 다음을 증명하지 않는다.

```text
Root 권한 정상
Repository 정상
Swap 정상
CA 정상
Filesystem 정상
```

그리고 Ping 성공만으로 대상 신원이 맞다고 끝내지 않는다.

```text
Inventory Hostname·IP
→ 원격 Node가 스스로 보고한 Hostname·IP
→ 오전 Role 표와 일치
```

> 다른 Server가 같은 SSH Credential을 받아도 Ping은 성공할 수 있습니다. **연결 성공과 대상 신원 성공은 별도 증거**입니다.

---

# 4. 두 번째 증거 — SSH와 sudo를 분리한다

> Node에 들어갈 수 있다는 것과 Root 권한 Task를 수행할 수 있다는 것은 다른 성공 단계입니다.

```text
Passwordless SSH 성공
= dspaas가 대상 Node에 비대화식으로 접속 가능

sudo -n 성공
= 같은 dspaas Session에서 비대화식 Root 권한 사용 가능
```

즉:

```text
SSH 성공
≠ sudo 성공
```

> Public Key 배포, `authorized_keys` 보존, sudoers 변경의 정확한 방법은 Node Pre-setting Runbook을 따릅니다. 이 대본에서는 **기존 접근을 지우지 않고 추가하고, 같은 Account로 기능을 재검증해야 한다**는 원칙만 기억합니다.

---

# 5. 세 번째 증거 — Repository와 Package는 공급 경로와 결과를 나눈다

> 접속과 권한이 준비돼도 필요한 Package를 받을 수 없으면 Kubespray 전제는 완성되지 않습니다.

다음 세 가지를 분리한다.

```text
Repo 파일 존재
≠ 승인 Repository 사용

Metadata 조회 성공
≠ 필요한 Package 설치 성공

설치 Task CHANGED
≠ 실제 Package 존재 확인
```

성공을 판정할 때는:

```text
승인 Repository
→ Canary에서 Metadata·Package 조회
→ 필요한 Package 설치
→ 실제 Package 상태 확인
```

> 실패했다고 공개 Repository를 임시로 추가하지 않습니다. DNS·Network·승인 URL·OS Version 중 어디가 처음 다른지 확인합니다.

Package 이름을 외우는 것이 아니라 역할을 이해한다.

| 범주 | 왜 필요한가 |
|---|---|
| Network 도구 | DNS·Port·Packet 경로 확인 |
| Storage 도구 | LVM·NFS·Block Device 사용 |
| SSH·TLS 도구 | 접속과 Certificate 확인 |
| 운영 도구 | 구축·운영 과정의 기본 확인 |

정확한 Package 목록과 설치 명령은 원본 Runbook에서 확인한다.

---

# 6. 네 번째 증거 — 현재 상태와 재부팅 후 상태를 구분한다

Swap은 대표적인 예다.

```text
현재 Swap 비활성
≠ 재부팅 후에도 비활성
```

> Kubernetes가 요구하는 OS 조건에는 지금의 Runtime 상태와 재부팅 뒤 영속 설정이 함께 영향을 줄 수 있습니다.

따라서 확인은 두 질문으로 나눈다.

```text
지금 활성화돼 있는가
다음 Boot에서 다시 활성화되는 설정이 남아 있는가
```

> Swap LV 삭제처럼 파괴적인 Storage 변경은 “Swap을 끈다”는 같은 작업으로 취급하지 않습니다. 필요한 경우 별도 승인과 Storage Runbook으로 이동합니다.

같은 원칙은 다른 설정에도 적용한다.

```text
설정 파일에 값이 있음
≠ Runtime에 그 값이 적용됨
```

Kernel·Network 설정은 **정확한 변경 문자열보다 최종 Runtime 값과 전체 적용 성공**을 확인한다.

---

# 7. 다섯 번째 증거 — CA 파일 존재와 Registry 신뢰를 구분한다

> Kubernetes Node는 Private Registry에서 Image를 가져올 수 있어야 합니다. 여기서 필요한 것은 파일 하나를 복사하는 일이 아니라 **Node가 승인된 Registry Certificate Chain을 실제로 신뢰하는 상태**입니다.

구분:

```text
CA 파일 이름이 같음
≠ 같은 CA 파일

OS Trust Store에 파일 존재
≠ Trust 갱신 성공

OS Trust 갱신 성공
≠ Container Runtime의 Registry별 Trust까지 자동 증명
```

따라서 최소 증거는:

```text
승인 Source CA의 기대 Checksum
→ 배포된 파일 Checksum
→ Trust 적용 결과
→ 현재 Runtime 기준의 Registry Trust 구조
→ Certificate 검증을 생략하지 않은 실제 HTTPS 경로
```

> `curl -k` 성공은 Certificate 검증을 생략했기 때문에 정상 Trust의 증거가 아닙니다.

CA 배포와 Container Runtime 설정의 정확한 절차는 원본 Runbook에서 수행한다.

---

# 8. 마지막 증거 — Role에 맞는 Filesystem과 Time이 실제로 보이는가

> Node 준비의 끝에서는 처음 확인했던 VM 설계로 다시 돌아옵니다. 중간 작업이 모두 성공해도 Role별 Filesystem이나 Time 상태가 승인 설계와 다르면 다음 단계로 넘기지 않습니다.

역할 차이를 남긴다.

```text
Master·Router·Infra·Worker
→ 승인된 Container Runtime Data 경로

ETCD
→ 승인된 ETCD Data 경로
```

> ETCD에 일반 Node의 Filesystem 구조를 기본 적용하지 않습니다. 현재 신규 Member의 승인 Mount 설계가 기준입니다.

Time도 같은 원칙이다.

```text
NTP 설정 존재
≠ Node 시간 동기화 정상
```

> 실제 Source와 동기화 상태를 보고, 한 Node만 다르면 전체 정상으로 처리하지 않습니다.

---

# 9. Node 하나의 준비 완료는 ‘증거 묶음’이다

한 Node를 다음처럼 읽는다.

```text
Identity
→ Access
→ Privilege
→ Repository·Package
→ 현재·영속 OS 조건
→ Registry CA Trust
→ Kernel·Network Runtime
→ Role별 Filesystem
→ Time
```

대조표:

```text
Host | Role | Identity | SSH | sudo | Repo·Pkg | OS 조건 | CA | Kernel | Filesystem | Time
     |      |          |     |      |          |         |    |        |            |
```

> `CHANGED`가 많다는 것은 성공의 증거가 아닙니다. **각 Host에서 위 질문이 실제 상태로 닫혔는지**가 중요합니다.

## 9.1 한 Node 성공과 전체 성공

```text
Canary 성공
→ 해당 Role에서 변경 방법 검증

Role Group 성공
→ 같은 Role Node의 일관성 검증

전체 Node 성공
→ 모든 Role의 Kubespray 사전조건 검증
```

---

# 10. 실패하면 ‘첫 단절’만 찾는다

대표적인 첫 분기만 기억한다.

| 증상 | 먼저 볼 경계 |
|---|---|
| UNREACHABLE | 대상 Host·DNS·Network·SSH |
| SSH 성공, sudo 실패 | Account·Group·sudo 정책·Session |
| Repo Metadata 실패 | DNS·Network·승인 URL·Repo 정책 |
| 특정 Node Package 실패 | OS·Repo·Architecture·Disk 차이 |
| Swap·Filesystem 불일치 | 현재 VM 설계·영속 설정·Role 차이 |
| Registry Trust 실패 | CA Source·Checksum·Trust·Runtime 경로 |

> 실패한 항목과 무관한 설정을 같이 바꾸지 않습니다. 정상 Node의 상태를 현재 실패 Node의 증거로 사용하지도 않습니다.

---

# 11. 이 블록의 완료 기준

```text
모든 Node가 오전 Role·Hostname·IP와 일치
+ Ansible이 올바른 Node에 도달
+ dspaas SSH와 sudo 기능 확인
+ 승인 Repository·필수 Package 기능 확인
+ Kubernetes가 요구하는 현재·영속 OS 조건 확인
+ 승인 CA와 Registry Trust 경계 확인
+ Kernel·Network Runtime 확인
+ Role별 Filesystem 확인
+ Node별 Time 상태 확인
+ 실패·미확정 Node가 별도로 기록됨
```

> 여기까지 왔다고 Kubernetes Cluster가 만들어진 것은 아닙니다. **각 Node가 Kubespray 입력을 받아도 되는 상태인지 확인한 것**입니다.

다음 중 하나면 Inventory 작성 완료 단계로 넘기지 않는다.

```text
Node 신원 불일치
SSH 또는 sudo 실패
Repository 미확정
필수 Package 실패
Swap·영속 설정 미확정
Registry CA·Runtime Trust 미확정
ETCD Filesystem 미확정
```

---

# 12. 다음 Inventory·Ansible Preflight 블록으로 넘길 것

```text
최종 Node Role·Hostname·IP
Node별 Identity·SSH·sudo 결과
승인 Repository와 Package 기준
현재·영속 OS 조건 결과
CA Source·Checksum·Trust 결과
Kernel·Network 확인 결과
Filesystem·Mount 결과
Time 결과
실패·미확정 Node와 첫 실패 단계
```

> 다음 블록에서는 이 실제 Node 상태만 Kubespray가 읽을 `hosts.yaml`과 변수 파일로 표현합니다. **파일을 먼저 채운 뒤 현실을 맞추지 않고, 확인된 현실만 파일로 옮기며 미확정 Node는 입력에서 숨기지 않습니다.**

---

# 13. 마무리 — Node Pre-setting을 한 문장으로 다시 말한다

> Node Pre-setting은 Package와 설정을 많이 바꾸는 작업이 아닙니다.
>
> 올바른 Node에 도달하고, 필요한 권한과 공급 경로를 사용하며, Kubernetes가 요구하는 OS·Trust·Filesystem 조건이 실제로 성립하는지 확인하는 과정입니다.
>
> **한 Node의 성공 범위를 다른 Role까지 확대하지 않고, Canary에서 검증한 뒤 필요한 범위로만 확대하며, 마지막에는 모든 Node를 같은 질문으로 다시 비교합니다.**

---

# 14. 마지막 Teach-back

1. SSH 성공과 Node Pre-setting 완료는 무엇이 다른가?
2. Canary 성공을 다른 Role 전체의 성공으로 확대하면 안 되는 이유는 무엇인가?
3. Ansible Ping 성공 뒤에도 원격 Hostname·IP를 확인해야 하는 이유는 무엇인가?
4. `CHANGED`와 실제 Package·설정 성공을 왜 구분해야 하는가?
5. 현재 Swap 비활성화와 재부팅 후 비활성화를 왜 별도 증거로 봐야 하는가?
6. CA 파일 존재와 Registry Trust 성공은 무엇이 다른가?
7. 이 블록에서 다음 Inventory 단계로 넘기는 핵심 증거는 무엇인가?
