# Inventory·Ansible Preflight 강사용 전체 대본

> [!important] 이 대본의 역할
> 이 문서는 앞의 세 블록에서 검증한 **신규 Member의 실제 환경을 Kubespray 입력으로 정확히 표현하고, 실행 전에 그 파일들이 모두 같은 현실을 설명하는지 판정하는 법**을 가르친다. 8월 31일에는 실제 `cluster.yml`을 실행하지 않는다. YAML 편집의 세부 절차와 실제 Playbook 실행은 원본 Kubespray Runbook에서 수행한다.

## 0. 앞 블록에서 이어받는 것

이 블록의 입력은 새로 만드는 값이 아니다.

```text
신규 Member Cluster Identity
Node별 Role·Hostname·IP
VIP-A·VIP-B
Pod·Service CIDR·Domain
Bastion Identity와 Toolchain
Node별 Identity·SSH·sudo 결과
승인 Repository·Package 기준
Registry CA Trust 결과
Filesystem·Time 결과
미확정값과 첫 실패 단계
```

> 지금부터 할 일은 **파일을 완성해 보이게 만드는 것**이 아닙니다. 앞에서 사실로 확인한 것만 파일에 옮기고, 사실이 아닌 값은 빈칸이나 BLOCKED로 남기는 것입니다.

## 0.1 이 블록이 끝난 뒤 수강생이 할 수 있어야 하는 것

> `hosts.yaml`과 변수 파일을 단순 설정 파일이 아니라 **실제 신규 Member 설계의 표현**으로 읽고, YAML Parse·Ping·Syntax 성공의 증거 범위를 제한하면서 **실제 VM ↔ Inventory ↔ 변수 ↔ Ansible 연결**이 일치하는지 확인해 9월 1일 실행을 GO 또는 BLOCKED로 판정할 수 있어야 한다.

오늘의 중심 질문:

> **이 파일들이 문법상 정상인가가 아니라, 실제 신규 Member를 정확히 설명하고 있다는 것을 무엇으로 증명할 것인가?**

---

# 1. 시작 — Inventory는 서버 목록이 아니라 설치 설계도다

> 오전에는 신규 Member의 실제값을 확인했고, Bastion과 Node가 자동화를 받을 조건을 준비했습니다.
>
> 이제 그 현실을 Kubespray가 읽을 수 있는 파일로 표현합니다.
>
> Kubespray는 이 파일이 승인 설계와 맞는지 스스로 판단하지 않습니다. 문법상 완벽한 잘못된 값도 그대로 실행할 수 있습니다.

그래서 가장 먼저 이 구분을 기억한다.

```text
YAML Parse 성공
≠ 실제 설계 정상

Ansible Ping 성공
≠ 올바른 Role·Group

모든 값이 채워짐
≠ 승인된 값

과거 Cluster에서 성공한 파일
≠ 신규 Member에 사용 가능
```

> 잘못된 IP를 적었는데 그 IP의 다른 Server가 응답하면 Ansible은 성공할 수 있습니다. **도구 성공이 오히려 잘못된 대상을 빠르게 바꾸는 통로가 될 수 있기 때문에 현실과의 대조가 먼저**입니다.

---

# 2. 파일을 열기 전에 값의 Source를 고정한다

> 먼저 “무엇을 넣을 것인가”보다 “그 값은 어디에서 왔는가”를 확인합니다.

최소 Source 표:

```text
항목 | 실제값 | 근거 | 확인 시각·확인자
Cluster Name | | |
Master Role·Hostname·IP | | |
ETCD Role·Hostname·IP | | |
Router Role·Hostname·IP | | |
Infra Role·Hostname·IP | | |
Worker Role·Hostname·IP | | |
VIP-A | | |
Pod CIDR | | |
Service CIDR | | |
Service Domain | | |
Registry FQDN·Project | | |
Kubernetes Version | | |
Bundle·Kubespray Version | | |
```

Source 우선순위는 다음 정도면 충분하다.

```text
승인된 신규 Member 설계
+ 8월 31일 실제 VM·LB 결과
+ Node Pre-setting 실제 결과
+ 현재 승인 Bundle·Manifest
```

> 원본 Manual과 기존 Xi'an Cluster는 구조를 이해하는 자료입니다. 신규 Member의 빈 값을 대신하지 않습니다.

미확정값의 의미:

```text
근거 없음
= 아직 실행값 아님
= BLOCKED 후보
```

---

# 3. 각 파일은 ‘무엇을 표현하는가’만 먼저 이해한다

Kubespray 입력을 네 묶음으로 본다.

| 파일 | 쉬운 의미 | 앞에서 가져올 현실 |
|---|---|---|
| `hosts.yaml` | 어떤 Server가 어떤 Role인가 | Node Role·Hostname·IP |
| `dks_vars.yml` | 이 Cluster의 Identity와 Network는 무엇인가 | VIP-A·Cluster Name·CIDR·Domain |
| `offline.yml` | 설치 Image를 어디서 가져오는가 | Registry·Project·Bundle Manifest |
| `k8s-cluster.yml` | 어떤 Kubernetes 기준으로 설치하는가 | 승인 Version·Bundle 지원 범위 |

> 파일이 네 개라고 설계가 네 개인 것이 아닙니다. **네 파일 모두 같은 신규 Member 하나를 설명해야 합니다.**

---

# 4. hosts.yaml — Hostname·IP·Role이 하나의 실제 Node를 가리키는가

> `hosts.yaml`의 핵심은 들여쓰기 문법이 아니라 **한 Host가 실제 어느 VM이고 어떤 역할로 설치되는지**입니다.

한 Host를 다음 순서로 읽는다.

```text
Hostname
→ ansible_host·ip·access_ip
→ 실제 원격 Hostname·IP
→ Role Group
→ 상위 Group 포함 관계
```

## 4.1 IP 필드는 의미를 알고 쓴다

```text
ansible_host
→ Bastion의 Ansible이 접속할 주소

ip
→ Kubernetes Node 내부 통신에 사용할 주소

access_ip
→ Node 접근과 일부 Component 통신에 사용할 주소
```

> 현재 신규 Member 설계에서 세 값이 같다면 같게 적을 수 있습니다. 하지만 “원본이 같았으니까” 복사하지 않습니다.

## 4.2 Host가 목록에 있다는 것과 Role이 맞는 것은 다르다

```text
all.hosts에 Host 존재
≠ 필요한 Role Group에 포함됨

Group 이름이 문법상 정상
≠ 실제 Role 설계와 일치
```

Master·ETCD·Router·Infra·Worker의 실제 수와 Group 관계는 앞 블록의 Role 표와 현재 Bundle Template을 함께 본다.

> 원본 Taylor Hostname, `10.166.*` IP, 과거 `system_node` 같은 값이 실행값으로 남아 있으면 신규 Member 실행을 중단합니다.

---

# 5. dks_vars.yml — Cluster Identity와 Network가 같은 설계를 가리키는가

> Node Role을 표현했으면 이 Node들이 어떤 Cluster로 통신할지 적습니다.

핵심 항목:

```text
VIP-A
Cluster Name
Pod CIDR
Service CIDR
Service Domain
```

쉽게 말하면:

```text
VIP-A
→ Kubernetes API 입구

Pod CIDR
→ Pod 주소 범위

Service CIDR
→ ClusterIP Service 주소 범위

Service Domain
→ Cluster 내부 DNS 이름의 기준
```

반드시 구분한다.

```text
CIDR 문자열 형식 정상
≠ 다른 Network와 중복 없음

VIP-A 값 존재
≠ 오전 승인 LB 값과 일치
```

> 이런 값은 설치 뒤 “조금 고치는” 성격이 아닐 수 있습니다. 실행 전에 승인 설계와 대조합니다.

---

# 6. offline.yml — Registry 주소가 실제 Image 공급 경로인가

> Offline 환경에서 Registry는 단순 Hostname이 아니라 Kubernetes 설치에 필요한 Image 공급 경로입니다.

확인할 최소 연결:

```text
Registry FQDN
→ Harbor Project
→ Bundle Manifest의 Image 경로·Tag
→ Node Network 접근
→ Node CA Trust
```

구분:

```text
FQDN 접근 성공
≠ 올바른 Project·Tag 존재

과거 Registry가 살아 있음
≠ 신규 Member의 승인 Source

CA Trust 성공
≠ 필요한 Image Tag 존재
```

> Credential·Password는 Inventory에 평문으로 넣지 않습니다.

과거값 검색은 중요한 Preflight다.

```text
과거 Hostname
과거 IP 대역
과거 Cluster Name·Domain
과거 Registry Project
```

> 검색 결과가 나왔다고 바로 삭제하지 않습니다. **주석인지 실행값인지 확인하고, 실행값이면 BLOCKED로 판정한 뒤 현재 Source에 맞게 정리**합니다.

---

# 7. Kubernetes Version — 숫자 하나가 아니라 공급 기준 전체를 맞춘다

> `kube_version`은 단순 Version 문자열이 아닙니다. Bundle, Registry Image와 Package 공급 기준이 같은 세트를 이루는지 확인하는 기준입니다.

```text
승인 Kubernetes Version
↔ Kubespray Bundle 지원 Version
↔ Registry Image Tag
↔ Package Repository Version
↔ kubectl 등 Bundle Tool Version
```

> 원본의 `v1.22.10`이 있다는 사실만으로 현재 승인 Version이 되지 않습니다. 한 요소가 다르면 설치 전에 영향과 승인값을 확인합니다.

---

# 8. 파일별로 맞는 것보다 ‘서로 같은 설계’를 가리키는지가 중요하다

여기서 가장 중요한 표를 만든다.

| 의미 | 파일의 위치 | 실제 근거 |
|---|---|---|
| Node Hostname·IP | `hosts.yaml` | VM·Node Pre-setting 결과 |
| Master·ETCD·Router·Infra·Worker Role | `hosts.yaml` Group | 승인 Role 설계 |
| VIP-A | `dks_vars.yml` | 오전 LB 확인 |
| Cluster Name | `dks_vars.yml` | 신규 Member Identity |
| Pod·Service CIDR | `dks_vars.yml` | Network 승인값 |
| Domain | `dks_vars.yml` | DNS 설계 |
| Registry | `offline.yml` | Bundle Manifest·Harbor 실제값 |
| Kubernetes Version | `k8s-cluster.yml` | Bundle·Registry·Package 기준 |

> **한 파일이 맞는 것이 아니라 이 표의 모든 행이 같은 신규 Member를 가리켜야 합니다.**

예:

```text
hosts.yaml = 신규 Member
+ dks_vars.yml = 과거 PRD VIP
= 실행 금지

Registry = 신규 Bundle
+ kube_version = 과거 Version
= 실행 금지
```

# 9. Preflight는 서로 다른 질문을 하는 여러 증거다

편집이 끝났다고 가정해도 바로 실행하지 않는다.

## 9.1 Inventory Graph

무엇을 증명하는가:

```text
Host와 Group 관계를 Ansible이 어떻게 읽는가
```

증명하지 못하는 것:

```text
실제 VM의 신원이 맞는가
```

## 9.2 Host Variable

무엇을 증명하는가:

```text
특정 Host에 최종적으로 어떤 IP·변수가 적용되는가
```

## 9.3 Ansible Ping

무엇을 증명하는가:

```text
지정된 대상으로 SSH·Python Module 실행 가능
```

증명하지 못하는 것:

```text
그 대상이 의도한 실제 Node인가
Root Become이 가능한가
```

## 9.4 원격 Identity

> Inventory Hostname과 원격 Node가 스스로 보고한 Hostname·IP를 대조합니다. **Ping 성공 뒤 이 확인이 필요한 이유가 바로 잘못된 Server에 성공적으로 접속할 수 있기 때문**입니다.

## 9.5 Root Become

```text
Ping 성공
≠ Root Task 실행 가능
```

같은 Host에서 Root Become까지 성공해야 Kubespray 연결 Preflight가 닫힌다.

## 9.6 Diff

```text
Diff가 의도한 줄만 보여줌
≠ 변경값이 옳음
```

> Diff는 무엇이 바뀌었는지 보여줍니다. 그 값의 정당성은 Source 표가 증명합니다.

## 9.7 Syntax Check

```text
--syntax-check 성공
= Ansible이 Playbook·Inventory·변수 구조를 읽을 수 있음

--syntax-check 성공
≠ 실제 Cluster 설치 성공
≠ Registry Image Pull 성공
≠ CIDR 설계 정상
```

# 10. 8월 31일에는 실제 cluster.yml을 실행하지 않는다

> 오늘의 목적은 시험 설치가 아닙니다.
>
> 실제값을 입력으로 옮기고, 그 입력이 현실과 맞으며 Ansible이 같은 실제 Node에서 연결·권한·문법 Preflight를 통과한다는 근거를 만드는 것입니다.

오늘의 경계:

```text
허용
= Inventory·변수 검토
= Graph·Host Variable 확인
= Ping·Identity·Become 확인
= Syntax Check

오늘 범위 아님
= 실제 cluster.yml 실행
```

> Playbook 실행으로 미확정값이나 연결 문제를 발견하려고 하지 않습니다. **실행 전에 발견해야 합니다.**

---

# 11. 9월 1일 Gate는 GO 또는 BLOCKED로만 판정한다

이 작업에서 중간 상태를 늘리지 않는다. 실제 실행 가능 여부를 바꾸는 두 상태면 충분하다.

## 11.1 GO

```text
신규 Member 실제값 모두 확정
+ VM·LB·Bastion·Node Pre-setting 증거가 연결됨
+ Inventory·변수와 실제 설계 일치
+ 과거 Cluster 실행값 없음
+ Ansible Graph·Ping·Identity·Become 통과
+ Syntax Check 통과
+ 실행 승인·담당자·시간 준비
```

## 11.2 BLOCKED

다음 중 하나라도 실행 전 필수조건이면 BLOCKED다.

```text
Cluster Identity 미확정
Node Role·Hostname·IP 불일치
VIP·CIDR·Domain 미확정
ETCD Filesystem 미확정
Repository·Bundle·Registry·Version 미확정
SSH·sudo 실패
Inventory Group·Host 불일치
과거 Cluster 실행값 잔존
Syntax Check 실패
실행 승인·담당자·시간 없음
```

> BLOCKED를 실패처럼 숨기지 않습니다. **왜 멈췄는지와 누가 무엇을 확인해야 GO가 되는지 기록하는 것이 정상적인 Preflight 결과**입니다.

# 13. 마무리 — 8월 31일 전체 이야기를 닫는다

> 오늘은 Cluster를 설치하는 날이 아니라 **잘못된 입력으로 Cluster를 설치하지 않기 위한 근거를 만드는 날**입니다.
>
> 신규 Member VM의 실제 상태를 확인하고, Bastion과 Node가 자동화를 받을 조건을 준비했습니다.
>
> 마지막으로 그 현실을 `hosts.yaml`과 변수 파일에 표현하고, 파일별 값이 모두 같은 신규 Member를 설명하는지 대조합니다.
>
> Graph, Ping, 원격 Identity, Become과 Syntax Check는 서로 다른 범위를 증명합니다. 하나의 성공으로 나머지를 대신하지 않습니다.
>
> **결국 8월 31일 완료는 Playbook을 한번 실행해본 상태가 아니라, 9월 1일 Kubespray를 잘못된 대상과 값으로 실행하지 않아도 된다는 근거가 완성된 상태입니다.**
