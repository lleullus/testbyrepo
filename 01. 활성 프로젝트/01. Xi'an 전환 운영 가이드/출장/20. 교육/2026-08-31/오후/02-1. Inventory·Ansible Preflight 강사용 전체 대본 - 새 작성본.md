# Inventory·Ansible Preflight 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 앞 블록까지 신규 Member의 VM·Bastion·Node 상태를 확인했다. 이번 블록은 **그 상태를 Kubespray 입력으로 옮기고, 실제 변경 전에 Ansible이 올바른 대상과 권한을 사용하는지 확인하는 과정**이다.
>
> 8월 31일에는 `cluster.yml`을 실행하지 않는다. YAML 편집과 검증 명령은 승인된 Kubespray Runbook을 따르며, 과거 Host·Taylor 환경의 Hostname·IP·VIP·Domain·Registry·Version을 현재값으로 사용하지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
신규 Member의 실제 Node 상태를 확인했다
→ 하지만 Kubespray는 사람이 확인한 내용을 직접 알지 못한다
→ 그래서 Inventory와 변수 파일에 표현한다
→ hosts.yaml에 Node와 Role을 넣는다
→ dks_vars.yml에 API·CIDR·Domain을 넣는다
→ offline.yml과 Version을 현재 Bundle·Registry에 맞춘다
→ 여러 파일이 같은 Member를 설명하는지 확인한다
→ Graph·변수·Ping·Identity·Become·Syntax를 확인한다
→ 실행하지 않고 GO 또는 BLOCKED를 판정한다
```

## 0-1. 오늘 전체 한 줄

> 오늘의 결과물은 YAML 파일 자체가 아닙니다. **확인된 신규 Member 상태가 Kubespray 입력에 정확히 반영됐고, 내일 실행 가능한지 판단할 수 있는 근거**입니다.

---

# 1. 시작 — Node가 준비돼도 Kubespray 입력은 별도로 만들어야 한다

> 지금까지 어느 VM이 어떤 Role이고, SSH·sudo·Package·OS·Registry·Filesystem이 어디까지 준비됐는지 확인했습니다.
>
> **하지만 Kubespray는 이 확인 결과를 직접 읽을 수 없습니다.** 어느 Host에 접속하고 어떤 Role을 부여하며, 어떤 VIP·CIDR·Domain·Registry·Version을 사용할지 파일로 알려줘야 합니다.
>
> 그래서 Inventory와 변수 파일이 필요합니다.
>
> 다만 YAML 문법이 정상이라고 설계가 맞는 것은 아닙니다. 잘못된 IP와 다른 Cluster의 VIP도 문법상 정상일 수 있습니다.
>
> 따라서 먼저 현재 Cluster Name, Node Role·Hostname·IP, VIP-A, Pod·Service CIDR·Domain, Registry·Project, Kubernetes Version과 Bundle을 확인합니다. Node Pre-setting의 SSH·sudo·Registry Trust·Filesystem 결과도 이어받습니다.
>
> 미확정값은 과거 Inventory로 채우지 않습니다.
>
> 주요 파일의 역할은 간단합니다. `hosts.yaml`은 Node와 Role, `dks_vars.yml`은 API와 Network, `offline.yml`은 Registry 경로, `k8s-cluster.yml`은 Kubernetes Version을 표현합니다.

---

# 2. hosts.yaml — Node와 Role을 표현한다

> Kubespray가 작업하려면 Hostname·IP와 Role Group을 알아야 합니다.
>
> 그래서 `hosts.yaml`에 앞에서 확인한 Node 상태를 넣습니다.
>
> `ansible_host`, `ip`, `access_ip`가 비슷해 보여도 의미를 확인합니다. 현재 설계에서 같은 Management IP를 사용한다면 값이 같을 수 있지만, 과거 Template이 같았다는 이유로 복사하지 않습니다.
>
> 특히 Inventory의 IP는 단순 표기가 아니라 Ansible이 어느 Node에 접속하고 Kubernetes가 어떤 주소를 Node 기준으로 사용할지에 영향을 줄 수 있습니다. 그래서 값이 서로 같아 보이더라도 현재 설계에서 왜 같은지 설명할 수 있어야 합니다.
>
> 또한 Host가 `all.hosts`에 있는 것과 올바른 Role Group에 속한 것은 다릅니다. Master가 Worker Group에 들어가면 문법은 정상이어도 설계는 틀립니다.
>
> Role Group은 이후 어떤 Task가 어느 Node에 적용되는지를 결정하는 기준이므로 Group 오류를 단순한 분류 실수로 보지 않습니다.
>
> 따라서 각 Host의 Role·Hostname·IP와 Group 관계가 Node Pre-setting 결과와 같은지 확인합니다.
>
> 이제 Kubespray는 작업 대상과 Role을 압니다. **하지만 Cluster의 공통 Network 기준은 아직 모릅니다.**

---

# 3. dks_vars.yml — API와 Cluster Network를 표현한다

> Node와 Role을 정한 뒤에는 API 입구와 Network 기준이 필요합니다.
>
> VIP-A는 Kubernetes API의 공통 입구입니다. Pod CIDR은 Pod 주소 범위, Service CIDR은 ClusterIP 범위, Service Domain은 내부 DNS 이름의 기준입니다.
>
> 이런 값은 특정 Node 하나의 설정이 아니라 Cluster 전체가 공유하는 기준입니다. 그래서 한 번 잘못 들어가면 여러 Node가 같은 잘못된 기준으로 설치될 수 있습니다.
>
> Cluster Name도 이번 설치 대상의 Identity로 사용됩니다.
>
> 값이 파일에 있다는 사실보다 승인된 신규 Member 값과 같은지가 중요합니다. CIDR 형식이 맞아도 다른 Network와 충돌하거나 다른 Member 값일 수 있습니다.
>
> 반대로 과거 Cluster와 숫자 형식이 비슷하다는 이유로 재사용하지 않습니다. VIP·CIDR·Domain은 현재 신규 Member의 Network 설계와 함께 확인해야 합니다.
>
> 따라서 이런 전역값은 실행 전에 승인 설계와 맞춥니다.
>
> Node와 Network를 표현했어도 Offline 설치에 사용할 Image 공급 경로는 별도입니다.

---

# 4. Offline Registry와 Version — 설치 공급 세트를 맞춘다

> Xi'an은 승인된 Private Registry에서 설치 Image를 받습니다.
>
> 그래서 `offline.yml`에는 Registry FQDN뿐 아니라 Project, Image 경로와 현재 Bundle 기준이 반영돼야 합니다.
>
> Node가 Registry에 도달해도 필요한 Project나 Tag가 없으면 설치할 수 없습니다. 반대로 과거 Registry가 정상 응답해도 현재 승인 Source라는 뜻은 아닙니다.
>
> 앞 블록에서 확인한 Node의 CA와 Registry Trust가 이 Registry 경로와 맞는지도 확인합니다. Credential은 Inventory에 평문으로 넣지 않습니다.
>
> Registry FQDN이 맞아도 `offline.yml`의 Project나 Image 경로가 다른 환경을 가리키면 실제 설치 시 필요한 Image를 찾지 못할 수 있습니다. 그래서 Registry 접근 성공과 설치용 Image 공급 준비를 같은 의미로 보지 않습니다.
>
> **또한 Kubernetes Version은 숫자 하나만 맞추는 항목이 아닙니다.** Kubespray Bundle, Registry Image, Package와 Tool이 같은 Version 세트여야 합니다.
>
> Bundle은 특정 Kubernetes Version과 그에 필요한 Image·설정 조합을 전제로 할 수 있습니다. 따라서 `k8s-cluster.yml`의 Version만 임의로 바꿔 다른 Bundle과 섞지 않습니다.
>
> 과거 Manual의 Version은 참고자료이며 현재 승인 Bundle이 실행 Version을 결정합니다.
>
> 마지막으로 `hosts.yaml`, `dks_vars.yml`, `offline.yml`, `k8s-cluster.yml`이 모두 같은 신규 Member의 Node·VIP·CIDR·Domain·Registry·Bundle·Version을 가리키는지 확인한 뒤 Preflight로 넘어갑니다.
>
> 여기서 중요한 것은 파일 네 개가 각각 정상인 것이 아니라 **서로 다른 파일이 하나의 같은 Cluster를 설명하고 있는지**입니다.

# 5. Ansible Preflight — 실제 변경 전에 작은 항목부터 확인한다

## 5.1 Inventory Graph

> 먼저 Graph에서 Ansible이 Host와 Group 구조를 어떻게 읽는지 확인합니다.
>
> 파일을 눈으로 봤을 때 Group이 맞아 보여도 들여쓰기나 Group 위치가 잘못되면 Ansible이 다른 구조로 읽을 수 있습니다. 그래서 실제 연결 시험 전에 Ansible이 해석한 Host·Group 관계부터 확인합니다.
>
> Role Group이 실제 설계와 같은지 봅니다. Master·ETCD·Worker 같은 Group에 어느 Host가 포함됐는지 Node Pre-setting 결과와 대조합니다.
>
> 다만 Graph 성공은 실제 VM 연결까지 증명하지 않습니다. Graph는 **Ansible이 작업 대상을 어떤 구조로 이해하고 있는지**를 확인하는 단계입니다.
>
> 그래서 Group 구조가 틀리면 Ping이나 Become으로 넘어가지 않고 Inventory부터 바로잡습니다.

## 5.2 Host Variable

> 같은 변수가 여러 위치에 있으면 사람이 본 값과 Ansible의 최종값이 다를 수 있습니다.
>
> `hosts.yaml`에 적은 값 외에도 Group Variable이나 다른 변수 파일이 같은 항목을 정의하면 적용 우선순위에 따라 최종값이 달라질 수 있습니다.
>
> 그래서 특정 Host에 적용되는 IP와 주요 변수를 확인합니다. 기준은 파일 위치가 아니라 Ansible이 실제로 읽는 값입니다.
>
> 예를 들어 파일 하나의 IP를 수정했어도 다른 위치의 값이 최종적으로 적용되고 있다면 작업자는 수정이 반영됐다고 생각하지만 Ansible은 여전히 이전 값을 사용할 수 있습니다.
>
> 따라서 이 단계에서는 **작성한 값과 실제 적용될 값이 같은지**를 확인하고, 예상하지 않은 Override가 있으면 연결 시험 전에 정리합니다.

## 5.3 Ping과 원격 Identity

> Graph와 최종 변수가 맞으면 그다음 실제 Node 연결을 확인합니다.
>
> 여기서 Ansible Ping은 일반 ICMP Ping과 다릅니다. 지정한 Host에 SSH로 접속하고 원격 Python을 통해 Ansible Module을 실행할 수 있는지를 확인합니다.
>
> 그래서 Ping이 성공하면 Inventory의 연결 주소, SSH 인증과 기본 Module 실행 경로가 동작한다는 것은 알 수 있습니다.
>
> **하지만 잘못된 Server에도 성공할 수 있습니다.** 같은 Account와 Key를 받아주는 다른 VM을 가리키고 있어도 Ping 결과는 성공으로 나올 수 있습니다.
>
> 그래서 원격 Hostname·IP를 다시 확인해 Inventory와 Node Pre-setting 결과에 맞춥니다.
>
> 연결 성공과 대상 Identity를 함께 확인해야 **접속할 수 있는 Server가 아니라 실제 신규 Member의 올바른 Node에 접속했다**고 판단할 수 있습니다.

## 5.4 Become

> 일반 Module 실행과 Root Task 실행은 다릅니다.
>
> Node Pre-setting에서 `dspaas`의 비대화식 sudo를 확인했지만 여기서는 Kubespray가 실제 사용할 Inventory와 Ansible 경로에서도 같은 권한이 적용되는지 다시 확인합니다.
>
> 그래서 같은 `dspaas` Account에서 Become이 실제로 되는지 확인합니다.
>
> Ping은 성공하는데 Become이 실패한다면 Network와 SSH는 이미 통과한 상태입니다. 이때 Inventory 주소나 Registry를 바꾸지 않고 현재 Account와 sudo 정책, Ansible의 Become 설정을 확인합니다.
>
> 따라서 Become 성공은 **Ansible이 현재 대상 Node에서 Kubespray가 필요한 Root Task를 비대화식으로 실행할 수 있는지**를 보여 주는 근거입니다.

## 5.5 Diff와 Syntax Check

> 연결과 권한까지 확인했으면 실제 실행 전에 입력 내용과 Playbook 구조를 마지막으로 봅니다.
>
> Diff는 무엇이 바뀌었는지 보여 주지만 그 값이 승인값인지 판단하지 않습니다. 값의 근거는 앞 단계 Source에 있습니다.
>
> 그래서 Diff에 신규 Member의 Node·VIP·CIDR·Domain·Registry·Version 변경이 의도한 범위로 들어갔는지 보고, 과거 Cluster 값이 남아 있지 않은지 확인합니다.
>
> 그다음 Syntax Check로 Playbook·Inventory·변수 구조를 Ansible이 오류 없이 읽을 수 있는지 확인합니다.
>
> 하지만 Syntax Check 성공은 실제 Node 변경이 성공한다는 뜻이 아닙니다. Image Pull, Package 설치, Kubernetes Network와 Control Plane 기능은 아직 실행하지 않았기 때문에 확인되지 않았습니다.
>
> 따라서 이 단계의 목적은 설치 성공을 미리 증명하는 것이 아니라 **내일 실행을 시작하기 전에 구조·변수·대상·권한에서 확인할 수 있는 오류를 최대한 제거하는 것**입니다.

# 6. 8월 31일에는 cluster.yml을 실행하지 않는다

> Preflight가 끝나도 오늘은 실제 설치를 시작하지 않습니다.
>
> 오늘의 목적은 내일 실행할 입력이 실제 신규 Member와 맞는지 실행 전에 확인하는 것입니다.
>
> VIP나 Role이 미확정인데 Playbook을 돌려 실패로 찾는 것은 Preflight가 아닙니다.
>
> Kubespray는 입력을 검토하는 도구가 아니라 실제 변경으로 확대하는 도구입니다.
>
> 따라서 오늘은 Graph·최종 변수·Ping·원격 Identity·Become·Diff·Syntax까지 확인하고 멈춥니다.

---

# 7. GO와 BLOCKED를 판정한다

> Node·Role·IP가 실제 환경과 맞고, VIP·CIDR·Domain·Registry·Version이 같은 승인 설계를 가리키며, Ansible Preflight가 같은 대상에서 통과했다면 `GO`입니다.
>
> 여기서 `GO`는 Kubernetes 설치 성공을 미리 보장한다는 뜻이 아닙니다. **현재 시점에서 실행 전에 확인할 수 있는 입력·대상·권한·문법 조건이 충족돼 실제 실행을 시작해도 된다는 판정**입니다.
>
> 실행 시간과 승인 조건도 준비돼 있어야 합니다.
>
> 반면 필수값이 미확정이거나 SSH·sudo·Registry Trust·Filesystem, Group·변수·Identity·Syntax에 문제가 남아 있다면 `BLOCKED`입니다.
>
> 일부 Node만 정상이라고 전체 Cluster를 GO로 판단하지 않습니다. Cluster 전체 실행에 필요한 Node나 전역값 하나가 미확정이면 해당 근거를 남기고 BLOCKED로 유지합니다.
>
> BLOCKED는 실패를 숨기는 이름이 아니라 아직 실행하면 안 되는 이유를 확인한 결과입니다. 값을 추측해서 GO로 만들지 않습니다.

---

# 8. 문제가 생기면 Preflight 순서대로 확인한다

> Graph가 이상하면 Network를 보지 않고 Host·Group 구조를 확인합니다.
>
> Ping이 실패하면 CIDR이나 Registry를 바꾸지 않고 Hostname·IP, 이름 해석, Network와 SSH를 봅니다.
>
> Ping은 되는데 Identity가 다르면 연결은 성공했지만 대상이 틀린 것입니다.
>
> Identity는 맞는데 Become이 실패하면 같은 `dspaas`의 sudo 상태를 확인합니다.
>
> Syntax는 성공하지만 과거값이 남아 있다면 문법 문제가 아닙니다. Cluster Name·Domain·Registry·IP를 현재 Source와 대조합니다.
>
> 확인 순서는 `파일 구조 → 최종 변수 → 연결 → 실제 대상 → 권한 → 문법`입니다.

# 9. 9월 1일에는 파일과 실행 근거를 함께 넘긴다

> 다음 날에는 최종 Node Role·Hostname·IP, VIP-A·CIDR·Domain과 Registry·Project·Version·Bundle 관계를 넘깁니다.
>
> Node Pre-setting의 SSH·sudo·Registry Trust·Filesystem 결과와 Graph·Host Variable·Ping·Identity·Become·Syntax 결과도 함께 전달합니다.
>
> 미확정값과 과거값 제거 여부를 숨기지 않습니다. Password·Private Key·Registry Credential·Token 원문은 넣지 않습니다.
>
> GO라면 같은 대상과 입력의 현재성을 다시 확인한 뒤 실행합니다. BLOCKED라면 남은 항목부터 해결합니다.

---

# 10. 마무리

> 실제 Node가 준비돼도 Kubespray가 그 상태를 자동으로 아는 것은 아닙니다.
>
> 그래서 `hosts.yaml`에 Node와 Role을, `dks_vars.yml`에 API와 Network를 표현했습니다. 또한 `offline.yml`과 Kubernetes Version을 현재 Registry·Bundle과 맞췄습니다.
>
> 그다음 모든 파일이 같은 신규 Member를 가리키는지 확인하고, Ansible이 실제로 읽는 구조·값·대상·권한·문법을 Preflight로 검증했습니다.
>
> **결국 8월 31일의 완료는 Playbook을 시험 실행한 상태가 아니라, 내일 실행 가능 여부를 GO 또는 BLOCKED로 설명할 수 있는 상태입니다.**
