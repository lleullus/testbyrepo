# Bastion Pre-setting 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 앞 블록에서 신규 Member의 Role·Hostname·IP·Disk·VIP를 확인했다. 이번 블록은 **그 값을 실제 설치에 사용할 하나의 실행 기준으로 모으는 과정**이다.
>
> DNS, `/etc/hosts`, sudoers, Repository, Bundle, Python·Ansible·Helm, SSH Key의 실제 변경은 승인된 Bastion Runbook을 따른다. 과거 Xi'an URL과 Version은 현재값으로 추측하지 않는다.
>
> 이번 시간의 목적은 Tool을 설치하는 것보다 **어떤 Bastion에서, 어떤 이름과 권한으로, 어떤 Package·Bundle·Toolchain을 사용해 신규 Member를 구축할지 기준을 하나로 고정하는 것**이다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
신규 Member의 실제값을 확인했다
→ 하지만 값만으로 여러 Node에 작업할 수는 없다
→ 그래서 설치 기준점인 Bastion을 준비한다
→ 먼저 Bastion 자체가 올바른 대상인지 확인한다
→ Node 이름이 승인 IP로 해석돼야 한다
→ 자동화 Account와 sudo 권한이 필요하다
→ 승인 Repository에서 Package를 받아야 한다
→ 현재 Bundle과 Toolchain이 맞아야 한다
→ SSH 인증 재료를 Node 접근으로 연결한다
→ 준비된 기준을 Node Pre-setting에 넘긴다
```

## 0-1. 오늘 전체 한 줄

> Bastion은 Tool을 모아 두는 서버가 아닙니다. **신규 Member의 이름 해석, 권한, Package, Bundle, 실행 Tool과 SSH 인증을 같은 기준으로 관리하고, 이후 여러 Node에 같은 방식으로 작업을 전달하는 서버**입니다.

---

# 1. 시작 — 실제값을 확인해도 설치 기준점은 별도로 필요하다

> 앞 블록에서 어떤 VM이 Bastion·Master·ETCD·Router·Infra·Worker인지 확인했습니다. Hostname과 IP, Disk와 VIP도 확인했습니다.
>
> **하지만 값만 있다고 여러 Node에 Kubernetes를 설치할 수는 없습니다.** 누군가는 그 값을 사용해 Node를 찾고, Package와 Bundle을 준비하고, 자동화를 실행해야 합니다.
>
> 여러 사람이 서로 다른 서버와 파일, Version으로 작업하면 같은 Cluster를 구축해도 기준이 달라질 수 있습니다.
>
> 예를 들어 한 사람은 DNS 이름을 사용하고 다른 사람은 과거 `/etc/hosts` 값을 사용하거나, 서로 다른 Bundle과 Ansible Version으로 작업하면 같은 명령을 실행해도 결과가 달라질 수 있습니다.
>
> 그래서 설치 시작점을 하나로 모읍니다. 그 역할이 Bastion입니다.
>
> Bastion에서 이번 신규 Member의 Hostname·IP·Repository·Bundle·Toolchain·SSH 기준을 하나로 맞추면 이후 Node 작업에서도 같은 입력을 반복해서 사용할 수 있습니다.
>
> 다만 다른 Cluster의 Bastion에서도 Tool 설치는 정상적으로 성공할 수 있습니다. 따라서 Tool보다 먼저 현재 Bastion이 오늘 대상인지 확인합니다.

---

# 2. 먼저 올바른 Bastion인지 확인한다

> 현재 Hostname과 Management IP를 앞 블록에서 확인한 신규 Member Bastion과 대조합니다. 작업 Account도 확인합니다.
>
> Bastion은 이후 모든 Node 작업의 시작점이기 때문에 여기서 대상 서버를 잘못 잡으면 뒤 단계가 정상적으로 실행돼도 잘못된 Cluster에 작업할 수 있습니다.
>
> 기존 작업 Directory나 Bundle이 있다면 어느 Cluster에서 사용하던 것인지 봅니다.
>
> 특히 기존 Inventory, SSH Key, `/etc/hosts`, Repository 설정과 Bundle Directory는 다른 Cluster의 값이 남기 쉬운 영역입니다.
>
> 파일 이름이 익숙하거나 과거에 성공했다는 이유만으로 신규 Member용이라고 판단하지 않습니다.
>
> 따라서 출처를 설명할 수 없는 기존 파일은 현재 실행 기준으로 사용하지 않습니다.
>
> 현재 Bastion의 Hostname·IP·Account와 기존 작업 Directory의 출처까지 설명할 수 있어야 다음 단계로 넘어갑니다.
>
> Bastion 자체를 확인했으면 다음은 Node 이름 해석입니다. **Bastion이 맞아도 Hostname이 잘못된 IP를 가리키면 자동화는 잘못된 서버로 갑니다.**

---

# 3. DNS와 hosts — 이름을 물었을 때 승인된 Node IP가 나와야 한다

> Ansible과 운영자는 Node를 Hostname으로 찾을 수 있습니다.
>
> 그래서 Bastion에서 신규 Member의 Master·ETCD·Router·Infra·Worker 이름을 조회했을 때 승인된 Management IP가 나와야 합니다.
>
> 이 이름 해석에 DNS와 `/etc/hosts`가 사용됩니다.
>
> 여기서 중요한 것은 설정 파일 자체가 아니라 **실제로 Hostname을 조회했을 때 어느 IP가 반환되는지**입니다.
>
> 하지만 설정 파일에 Nameserver나 Host 줄이 있다는 것만으로는 충분하지 않습니다. 실제 Hostname을 조회해 앞 블록의 승인 IP와 비교합니다.
>
> DNS에 올바른 값이 있어도 `/etc/hosts`의 과거 항목이 우선 사용되면 예상과 다른 Node로 접속할 수 있습니다. 반대로 `/etc/hosts`만 맞고 DNS가 잘못돼 있으면 다른 System이나 운영 ㅍㄱ각 Tool에서는 다른 결과를 볼 수 있습니다.
>
> `/etc/hosts`를 사용한다면 다른 Cluster의 Host 목록을 섞지 않습니다. Bastion은 이번 Cluster의 실행 기준점이므로 이름 해석도 같은 범위를 유지해야 합니다.
>
> DNS와 hosts가 다른 답을 주면 접속되는 쪽을 임의로 선택하지 않습니다. 어느 Source가 이번 신규 Member의 승인 기준인지 확인한 뒤 정리합니다.
>
> 따라서 이 단계의 완료 기준은 설정 줄이 존재하는 것이 아니라 **신규 Member의 각 Hostname이 앞에서 확정한 Management IP와 일치하게 해석되는 것**입니다.
>
> 이제 Bastion은 올바른 Node를 찾을 수 있습니다. **하지만 목적지를 찾는 것과 System 변경 권한은 다른 문제입니다.**

---

# 4. dspaas와 sudo — 자동화 Account가 Root 작업을 수행할 수 있어야 한다

> Xi'an 구축에서는 `dspaas` Account를 사용합니다.
>
> Ansible이 실제로 Node에 접속하고 System 설정을 변경할 때도 결국 이 Account와 권한 기준을 사용합니다.
>
> `dspaas`로 Login이 된다고 Kubespray에 필요한 권한까지 확인된 것은 아닙니다. Kubespray는 Package 설치와 System 설정 변경처럼 Root 권한이 필요한 작업을 수행합니다.
>
> 그래서 실제 사용할 `dspaas` Session에서 비대화식 sudo가 가능해야 합니다.
>
> 자동화 도중 Password 입력을 기다리게 되면 동일한 Playbook이라도 비대화식 실행이 중단될 수 있습니다. 따라서 사람이 직접 `sudo`에 성공한 것보다 실제 자동화 방식에서 권한 상승이 가능한지가 중요합니다.
>
> sudoers 문법이 정상인 것과 `dspaas`가 `sudo -n`을 사용할 수 있는 것은 다릅니다. Root Session의 성공도 `dspaas` 권한을 대신하지 않습니다.
>
> 또한 `wheel` Group에 포함됐다는 사실만으로 실제 sudo 정책 전체가 확인된 것도 아닙니다. 적용된 sudoers 규칙과 실제 `dspaas` Session의 결과가 같이 맞아야 합니다.
>
> 따라서 Group과 sudoers 변경은 Runbook을 따르고 기존 권한을 임의로 덮어쓰지 않습니다.
>
> 이 단계에서는 `dspaas`가 현재 Bastion의 작업 Account이고, 이후 자동화에서 필요한 권한 상승을 비대화식으로 수행할 수 있다는 데까지 확인합니다.
>
> 권한까지 확인했으면 설치에 필요한 Package를 받을 경로가 필요합니다.

---

# 5. Repository — 승인된 Source에서 실제 Package를 받을 수 있어야 한다

> Bastion에는 Python·Pip·Ansible·Helm과 여러 의존 Package가 필요합니다.
>
> Xi'an에서는 이를 임의의 인터넷 저장소가 아니라 승인된 내부 Repository에서 받습니다.
>
> 따라서 Repository 준비의 목적은 `.repo` 파일이나 `pip.conf`를 만드는 것이 아닙니다. **승인된 Source에서 Metadata와 Package를 실제로 받을 수 있게 하는 것**입니다.
>
> Repository 설정 파일은 Package Manager가 어디를 조회해야 하는지 알려주는 입력일 뿐이고, 실제 사용 가능 여부는 DNS·Network·인증·Repository Server 상태까지 연결돼야 확인됩니다.
>
> URL이 파일에 있어도 DNS나 Network가 막혀 있으면 사용할 수 없습니다. 그래서 Metadata와 필요한 Package 조회를 확인합니다. Pip Index도 같은 방식으로 봅니다.
>
> Metadata 조회는 되는데 실제 Package 다운로드가 실패할 수도 있습니다. 반대로 특정 Package가 Cache에 남아 있어 설치됐다고 해서 현재 Repository 연결이 정상이라고 판단할 수도 없습니다.
>
> 따라서 기존 Cache나 과거 설치 결과보다 **현재 승인 Repository에서 현재 필요한 Package를 조회하고 받을 수 있는지**를 기준으로 봅니다.
>
> 과거 자료의 URL이나 과거 로그의 성공은 현재 승인값을 대신하지 않습니다.
>
> Repository가 준비되면 Package는 받을 수 있습니다. **하지만 어떤 Kubespray 설치판을 사용할지는 아직 정해지지 않았습니다.**

---

# 6. Bundle과 Toolchain — 설치판과 실행환경을 맞춘다

> 먼저 이번 구축에 사용할 승인 Bundle Source와 Version을 확인합니다. 실제 받은 파일과 작업 Directory도 고정합니다.
>
> Bundle은 단순한 압축파일이 아니라 이번 구축에서 사용할 Kubespray, Manifest, Helm Chart와 관련 설정의 기준이 됩니다.
>
> 그래서 같은 제품 이름이라도 Bundle Version이 달라지면 포함된 Kubespray나 Manifest, 요구 Tool Version이 달라질 수 있습니다.
>
> 과거 Xi'an Bundle 이름은 참고자료일 뿐 현재 실행값은 승인된 Source가 결정합니다.
>
> 제공자가 기대 Checksum을 제공했다면 현재 파일과 비교합니다. 기대값이 없다면 현재 Hash를 추적용으로 남길 수 있지만 승인 검증이 끝났다고 말하지 않습니다.
>
> Checksum은 파일이 현재 기대한 파일과 같은지를 확인하는 근거이고, 파일 이름이 같다는 사실만으로 같은 Bundle이라고 판단하지 않습니다.
>
> **하지만 Bundle을 정했다고 바로 실행할 수 있는 것은 아닙니다.** 그 Bundle이 요구하는 Python·Pip·Ansible·Helm 조합이 실제로 동작해야 합니다.
>
> Python이 설치돼 있어도 Bundle이 기대하는 Interpreter나 Module 조합과 맞지 않을 수 있고, Ansible도 설치 여부보다 현재 Kubespray가 지원하는 Version 범위가 중요합니다.
>
> Tool이 설치돼 있다는 사실과 Version Requirement를 만족한다는 사실은 다릅니다.
>
> Helm도 마찬가지입니다. Binary가 실행된다는 사실보다 이후 사용할 Chart와 Bundle이 기대하는 실행 기준과 맞는지 확인해야 합니다.
>
> 따라서 Version 숫자를 외우는 것이 아니라 현재 Bundle을 실행할 수 있는 조합인지 확인합니다.
>
> 이 단계가 끝나면 **어떤 Bundle을 어느 Directory에서 어떤 Python·Ansible·Helm 조합으로 실행할지** 설명할 수 있어야 합니다.
>
> 이제 Bastion 안의 설치판과 실행환경은 준비됐습니다. 마지막으로 실제 Node에 들어갈 SSH 인증이 필요합니다.

---

# 7. SSH Key — Bastion의 기준을 Node 접근으로 연결한다

> Ansible은 Bastion에서 여러 Node에 접속하므로 `dspaas`가 사용할 SSH 인증 재료가 필요합니다.
>
> Key Pair가 있다고 Node가 그 Key를 신뢰하는 것은 아닙니다. Public Key가 올바른 신규 Member Node의 `dspaas`에 배포돼야 하고, 실제 비대화식 SSH가 성공해야 합니다.
>
> 또한 Key가 어느 Account 소유인지와 어떤 Cluster·Node를 대상으로 만든 것인지 구분해야 합니다. 과거 Cluster의 Key가 남아 있다는 이유만으로 그대로 사용하지 않습니다.
>
> 오전에는 Key Type, Fingerprint, 소유 Account와 Public Key 배포 대상 Node를 확인합니다.
>
> Fingerprint를 남기면 Private Key 본문을 노출하지 않고도 이후 어떤 Key를 사용했는지 식별할 수 있습니다.
>
> 실제 Node별 배포와 SSH 성공은 이어지는 Node Pre-setting에서 확인합니다.
>
> 따라서 Bastion에 Key가 있는 상태와 Node 접근이 성공한 상태를 구분합니다.
>
> Public Key를 배포했다고 해도 대상 Account, Home Directory, `authorized_keys` 권한이나 SSH 정책이 맞지 않으면 실제 접속은 실패할 수 있습니다. 그래서 최종 성공 판정은 실제 Node SSH 확인 단계에서 합니다.
>
> Private Key 본문과 Passphrase는 화면이나 증적에 남기지 않습니다.
>
> 여기까지 확인한 Bastion·이름 해석·sudo·Repository·Bundle·Toolchain·SSH 인증이 모두 같은 신규 Member 기준이어야 합니다. 하나라도 미확정이면 Node 작업으로 넘어가지 않습니다.

---

# 8. 문제가 생기면 처음 실패한 단계부터 확인한다

> Hostname이 다른 IP를 가리키면 Ansible이나 SSH Key부터 바꾸지 않습니다. DNS와 hosts, 승인 Hostname·IP를 확인합니다.
>
> 이름은 맞는데 sudo가 실패하면 Network로 돌아가지 않습니다. 같은 `dspaas` Session의 Group과 sudo 정책을 봅니다.
>
> Package가 조회되지 않으면 임의 Repository를 추가하지 않습니다. 승인 URL, DNS·Network, Metadata 순서로 확인합니다.
>
> Metadata는 조회되는데 Package 다운로드만 실패한다면 Repository 설정 전체를 다시 만드는 것보다 실제 Package 경로와 접근 결과를 먼저 봅니다.
>
> Ansible은 설치돼 있지만 Bundle과 맞지 않으면 Tool 존재 여부보다 Bundle Requirement와 Python·Ansible 조합을 봅니다.
>
> SSH가 실패해도 바로 Key를 다시 만들지 않습니다. 먼저 대상 Hostname·IP와 Account가 맞는지 확인하고, 그다음 Public Key 배포와 SSH 인증 상태를 봅니다.
>
> 즉 뒤 단계의 실패를 앞 단계의 추측으로 덮지 않습니다. **처음 기대 결과와 달라진 지점부터 다시 확인해야 원인 범위를 줄일 수 있습니다.**
>
> 확인 순서는 `대상 Bastion → 이름 해석 → 권한 → Repository → Bundle·Toolchain → SSH 인증`입니다.

---

# 9. 오후에는 준비된 기준만 넘긴다

> 오후에는 실제 Kubernetes Node를 준비합니다.
>
> 그래서 현재 Bastion, Node Role·Hostname·IP와 이름 해석 기준을 넘깁니다. `dspaas` 권한, 승인 Repository, Bundle과 Toolchain도 함께 전달합니다.
>
> 이때 오전에 확인한 값과 오후에 사용할 Inventory·Node 정보가 달라지면 안 됩니다. 오전 확인값은 단순 참고자료가 아니라 이후 Node Pre-setting의 입력 기준입니다.
>
> SSH는 Private Key를 넘기는 것이 아니라 Fingerprint, 소유 Account와 Public Key 배포 대상 Node를 넘깁니다.
>
> 아직 Node에서 SSH를 확인하지 않았다면 `SSH 성공`이라고 기록하지 않습니다.
>
> Repository 역시 Bastion에서 Package를 받을 수 있었다는 결과와 각 Kubernetes Node에서 같은 Repository를 사용할 수 있다는 결과를 구분합니다. Node 쪽 실제 Package 접근은 오후 Pre-setting에서 다시 확인합니다.
>
> 따라서 오전에는 **Bastion에서 사용할 실행 기준을 고정하고, 오후에는 그 기준이 각 Node에서도 실제로 성립하는지 확인하는 흐름**으로 이어집니다.

---

# 10. 마무리

> 신규 Member의 실제값을 확인했지만 설치를 실행할 기준점은 별도로 필요했습니다.
>
> 그래서 Bastion 자체와 이름 해석을 확인하고, `dspaas` sudo와 승인 Repository를 준비했습니다. 그다음 현재 Bundle과 Toolchain을 맞추고 SSH 인증 재료를 확인했습니다.
>
> 이 과정에서 중요한 것은 각각의 설정이 존재하는지가 아니라 **모든 설정이 같은 신규 Member를 가리키고 실제 자동화에서 사용할 수 있는 상태인지 확인하는 것**이었습니다.
>
> Repository 설정 파일이 있는 것과 Package를 받을 수 있는 것은 다르고, Tool이 설치된 것과 Bundle을 실행할 수 있는 것도 다릅니다. SSH Key가 존재하는 것과 실제 Node 접근이 가능한 것도 구분해야 합니다.
>
> **결국 Bastion Pre-setting은 이름 해석, 권한, Package 공급, Bundle, 실행 Tool과 SSH 인증을 같은 신규 Member 기준으로 정리하고, 이후 Node 자동화가 사용할 실행 기준을 만드는 작업입니다.**
>
> 이제 이 기준을 사용해 각 Kubernetes Node를 준비하겠습니다.

4. 기존 Inventory·Bundle·SSH Key가 남아 있을 때 먼저 출처를 확인해야 하는 이유는 무엇인가?
5. Nameserver가 있는 것과 신규 Member 이름이 승인 IP로 해석되는 것은 무엇이 다른가?
6. DNS와 `/etc/hosts`가 다른 답을 주면 무엇을 기준으로 판단해야 하는가?
7. `dspaas` Login과 비대화식 sudo는 무엇이 다른가?
8. `wheel` Group 포함과 실제 자동화 sudo 성공은 무엇이 다른가?
9. Repository URL 존재와 실제 Package 공급 성공은 무엇이 다른가?
10. Repository Metadata 조회 성공과 실제 Package 다운로드 성공은 무엇이 다른가?
11. 과거 Repository URL이나 Bundle Version을 현재값으로 사용하면 안 되는 이유는 무엇인가?
12. Bundle과 Python·Ansible·Helm을 함께 확인해야 하는 이유는 무엇인가?
13. 현재 파일 Hash와 승인된 기대 Checksum은 무엇이 다른가?
14. Tool이 설치돼 있는 것과 현재 Bundle의 Version Requirement를 만족하는 것은 무엇이 다른가?
15. SSH Key Pair 존재와 실제 Node SSH 성공은 무엇이 다른가?
16. SSH Key의 Fingerprint를 확인하는 이유는 무엇인가?
17. 문제가 발생했을 때 뒤 단계 설정부터 바꾸지 않고 처음 실패한 단계부터 확인해야 하는 이유는 무엇인가?
18. 오후 Node Pre-setting에 어떤 기준을 넘겨야 하는가?
