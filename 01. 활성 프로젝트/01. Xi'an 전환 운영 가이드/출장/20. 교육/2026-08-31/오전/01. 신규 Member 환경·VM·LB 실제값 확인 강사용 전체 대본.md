# 신규 Member 환경·VM·LB 실제값 확인 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 **신규 Member 구축을 시작하기 전에 무엇을 먼저 사실로 확인해야 하는지**를 설명한다. 수강생이 기존 Xi'an Cluster의 값과 신규 Member의 값을 섞을 수 있다는 전제로 진행한다.
>
> 정확한 Disk 변경, LVM·Filesystem 생성, LB 실제 테스트 명령은 승인된 Runbook을 따른다. 이 대본에서는 명령을 외우게 하기보다 **왜 확인해야 하는지 → 무엇을 확인하는지 → 어디까지 확인되면 다음 단계로 갈 수 있는지**를 말로 연결한다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
VM을 받았다고 바로 설치하지 않는다
→ 자동화가 믿어도 되는 입력이 먼저 필요하다
→ 그래서 Cluster와 Node Role을 먼저 고정한다
→ 하지만 승인 문서만으로 현재 VM이 그 대상이라고 확정할 수는 없다
→ 그래서 승인값과 현재 출력을 대조한다
→ 그다음 Resource와 Disk를 Role 기준으로 본다
→ 하지만 Node만 맞아도 외부 진입 경로는 아직 미확정이다
→ 그래서 VIP-A와 VIP-B를 따로 확인한다
→ 마지막에는 확인됨·불일치·미확정을 나눈다
→ 근거가 붙은 값만 Bastion 단계로 넘긴다
```

## 0-1. 오늘 전체 한 줄

```text
신규 Member 구축 시작
→ 어느 Cluster의 어떤 VM인지 확인
→ Role별 Hostname·IP·Resource·Disk 확인
→ VIP-A·VIP-B 경로 확인
→ 확인됨·불일치·미확정 구분
→ 근거가 붙은 값만 Bastion Pre-setting에 전달
```

# 1. 시작 — VM이 있다는 사실과 설치할 준비가 됐다는 사실은 다르다

> 오늘부터 신규 Member Cluster 구축을 시작하겠습니다.
>
> VM도 준비돼 있고 Kubespray도 있습니다. 그러면 바로 Inventory를 만들고 설치를 시작하면 될 것처럼 보입니다.
>
> **하지만**, Kubespray는 우리가 입력한 값이 맞는지 대신 판단해 주지 않습니다. Hostname을 잘못 넣으면 잘못된 Hostname을 사용하고, IP를 잘못 넣으면 잘못된 IP를 향하고, Role을 잘못 넣으면 그 잘못된 Role을 기준으로 자동화가 진행됩니다.
>
> **그래서**, 오늘 첫 작업은 설치가 아닙니다. **자동화에 넣어도 되는 사실을 먼저 만드는 것**입니다.

> 여기서 기존 Xi'an Host Cluster나 기존 PRD·DEV Member Cluster를 볼 수는 있습니다. 어떤 Role이 있고, VIP가 어떻게 나뉘고, Disk가 어떤 목적으로 쓰이는지를 이해하는 데는 좋은 참고입니다.
>
> **하지만**, 기존 환경이 정상이라고 해서 신규 Member도 같은 Hostname, IP, VIP, CIDR을 쓰는 것은 아닙니다.
>
> **따라서**, 기존 Xi'an 값은 구조를 이해하는 비교 자료로만 사용하고, 신규 Member의 실행값은 신규 Member 승인 설계와 현재 VM의 실제 출력으로 다시 확인합니다.

## 1.1 오늘부터 값을 세 가지 상태로 본다

> 값을 확인할 때는 단순히 `있다`, `없다`로 끝내지 않겠습니다.
>
> 승인된 설계와 현재 출력이 같은 대상을 가리키면 **확인됨**입니다.
>
> 승인된 설계와 현재 출력이 다르면 **불일치**입니다.
>
> 그리고 승인 근거나 현재 출력이 부족해서 아직 판단할 수 없으면 **미확정**입니다.
>
> **중요한 것은 빈칸을 없애는 것이 아닙니다.** 근거가 없으면 미확정으로 남기는 것이 맞습니다.

```text
확인됨
= 승인 근거와 현재 출력이 같은 대상을 가리킴

불일치
= 승인 근거와 현재 출력이 다름

미확정
= 승인 근거 또는 현재 출력이 부족해 아직 판단 불가
```

> **결국**, 오늘 첫 블록의 목표는 모든 값을 채우는 것이 아니라 **어떤 값은 믿어도 되고 어떤 값은 아직 믿으면 안 되는지 구분하는 것**입니다.

# 2. 먼저 Role을 알아야 무엇을 확인할지 정해진다

> 이제 신규 Member VM들을 보겠습니다.
>
> 여러 VM이 있다고 해서 모두 같은 기준으로 보면 안 됩니다. 어떤 VM은 설치를 시작하는 Bastion이고, 어떤 VM은 Kubernetes API를 담당하는 Master이며, 어떤 VM은 상태 데이터를 저장하는 ETCD입니다.
>
> **그래서**, Hostname과 IP를 확인하기 전에 먼저 각 VM이 어떤 Role인지 승인된 신규 Member 목록과 연결합니다.

## 2.1 Bastion

> Bastion은 구축 명령을 시작하는 실행점입니다.
>
> **하지만**, 단순히 SSH가 되는 서버라고만 보면 부족합니다. 이 Bastion에서 어떤 Node 이름을 찾고, 어떤 Account와 Tool을 사용하고, 어떤 Cluster를 설치할지가 뒤에서 모두 이어집니다.
>
> **그래서**, Bastion이 어느 VM인지 잘못 잡으면 이후 자동화 전체가 다른 Cluster를 향할 수 있습니다.

## 2.2 Master

> Master는 Kubernetes API와 Control Plane 기능을 담당합니다.
>
> 뒤에서 확인할 VIP-A는 Master 쪽 Kubernetes API 경로로 이어집니다.
>
> **따라서**, Master Role을 잘못 연결하면 VIP-A의 Backend 판단도 같이 틀어집니다.

## 2.3 ETCD

> ETCD는 Kubernetes의 상태 데이터를 저장합니다.
>
> **하지만**, 일반 Node의 Container Runtime 데이터와 ETCD 상태 데이터는 같은 용도가 아닙니다.
>
> **그래서**, ETCD는 Disk와 Filesystem을 다른 Node와 똑같이 보지 않습니다. 원본 기준에서는 ETCD 데이터 경로로 `/var/lib/etcd`를 사용합니다.
>
> 다만 신규 Member에서 최종적으로 어떤 Filesystem 구성을 사용할지는 승인된 신규 Member 설계로 다시 확인합니다.

## 2.4 Router

> Router는 외부 Application 요청이 Cluster 안으로 들어오는 경로입니다.
>
> 뒤에서 확인할 VIP-B는 Router를 Backend로 사용합니다.
>
> **그래서**, Router Role이 확인돼야 VIP-B가 어느 Node와 Port로 이어져야 하는지도 판단할 수 있습니다.

## 2.5 Infra와 Worker

> Infra는 KubeSphere나 Monitoring 같은 플랫폼 Workload가 배치되는 영역이고, Worker는 사용자 Application이 실행되는 영역입니다.
>
> 이름만 보면 둘 다 Workload가 올라가는 Node처럼 보일 수 있습니다.
>
> **하지만**, 배치 목적과 Resource 기준이 다를 수 있습니다.
>
> **따라서**, Infra와 Worker를 같은 Node 종류로 묶어서 보지 않고 승인된 Role 기준을 따로 확인합니다.

> 여기서 Role 이름을 외우는 것이 목적은 아닙니다.
>
> **Role을 먼저 알아야 뒤에서 어떤 Resource, Disk, Network 경로를 정상이라고 판단할지 정해진다**는 것이 핵심입니다.

> **하지만**, 승인 문서에서 이 VM이 Worker라고 적혀 있다고 해서 현재 접속한 VM이 정말 그 Worker라는 사실까지 확인된 것은 아닙니다.
>
> **그래서 이제 승인값과 현재 VM의 실제 출력을 서로 대조합니다.**

# 3. 승인값만 봐도 안 되고, 현재 출력만 봐도 안 된다

> 신규 Member 승인 문서에는 Hostname과 IP, Role과 Resource가 적혀 있을 수 있습니다.
>
> **하지만**, 승인 문서의 값만 보고 현재 VM이 그 대상이라고 확정할 수는 없습니다.
>
> 반대로 VM에 접속해서 Hostname과 IP가 보인다고 해도 그 값이 이번 신규 Member의 승인값이라는 뜻은 아닙니다.
>
> **그래서**, 한 값을 실행에 사용하려면 두 쪽을 같이 봅니다.

```text
승인된 신규 Member 설계
+ 현재 대상에서 실제로 읽은 값
→ 같은 VM을 가리키는지 대조
→ 맞으면 이번 구축에 사용할 값으로 확정
```

> 예를 들어 현재 VM의 Hostname이 `worker01`이라고 하겠습니다.
>
> 그것은 현재 VM이 스스로 보고한 Hostname이라는 사실은 증명합니다.
>
> **하지만**, 승인된 신규 Member 목록에서 이 VM의 Role이 Worker인지, 승인 Hostname이 같은지, 승인 IP가 같은지는 별도로 확인해야 합니다.

```text
VM이 존재함
≠ 승인된 Role 확인

Hostname이 보임
≠ 승인 Hostname과 일치 확인

IP가 보임
≠ 신규 Member 승인 IP 확인

Disk가 보임
≠ 변경 가능한 DATA Disk 확인
```

## 3.1 기준표는 기억용 표가 아니라 같은 대상을 계속 보기 위한 기준이다

> 이제 이번 신규 Member의 기준표를 하나 만듭니다.
>
> 이 표를 만드는 이유는 문서를 예쁘게 정리하기 위해서가 아닙니다.
>
> **뒤에서 보는 모든 출력이 계속 같은 신규 Member를 가리키는지 확인하기 위해서입니다.**

```text
Cluster Name: __________________________________________
Stage·용도: ____________________________________________
승인 근거: _____________________________________________
확인 시각·확인자: ______________________________________

Role | Hostname | Management IP | CPU | Memory | DATA Disk | 승인 Mount | 상태
Bastion | | | | | | |
Master  | | | | | | |
ETCD    | | | | | | |
Router  | | | | | | |
Infra   | | | | | | |
Worker  | | | | | | |

VIP-A: __________________  Port: 6443  Backend Role: Master
VIP-B: __________________  Port: 80/443  Backend Role: Router
Pod CIDR: ______________________________________________
Service CIDR: __________________________________________
Domain: ________________________________________________
```

> Storage IP처럼 별도 Network 정보가 필요한 경우도 있을 수 있습니다.
>
> **하지만**, 현재 승인 Source가 그 항목을 제공하지 않는다면 먼저 칸부터 만들고 과거 값을 채우지 않습니다.
>
> **그래서**, 별도 Storage Network가 실제 설계 항목이라면 승인된 Network·Storage Source에서 확인한 뒤 추가합니다.

# 4. 실제 VM에서는 신원부터 보고 Resource를 본다

> 이제 실제 VM에 접속했다고 하겠습니다.
>
> 바로 CPU나 Disk부터 보지 않습니다.
>
> **왜냐하면 다른 VM에서 정확한 명령을 실행해도 오늘 대상의 증거가 아니기 때문입니다.**
>
> **그래서**, 첫 번째는 항상 신원입니다.

## 4.1 먼저 Hostname과 IP를 확인한다

> 현재 Hostname이 무엇인지 확인합니다.
>
> 현재 Management IP가 무엇인지 확인합니다.
>
> 그리고 이 두 값이 기준표의 어느 Role 행과 연결되는지 봅니다.
>
> **하지만**, Hostname만 맞고 IP가 다르거나, IP는 맞는데 승인 Role이 다르면 같은 대상으로 확정할 수 없습니다.
>
> **따라서**, Role·Hostname·IP가 하나의 VM을 가리킬 때까지 다음 판단으로 넘어가지 않습니다.

## 4.2 신원이 맞으면 Resource를 본다

> 이제 어느 VM인지 확인됐습니다.
>
> **그러면** 이 VM이 승인된 Role에 필요한 Resource를 갖고 있는지 볼 수 있습니다.
>
> OS와 Version, CPU, Memory를 현재 대상에서 읽고 승인된 신규 Member 사양과 대조합니다.
>
> **하지만**, 기존 Xi'an Cluster와 숫자가 같다고 해서 신규 Member 승인값이라고 할 수는 없습니다.
>
> **그래서**, 과거 정상 환경은 비교 자료로만 보고 최종 판단은 신규 Member 승인 설계를 기준으로 합니다.

> 여기까지 확인하면 VM의 신원과 기본 Resource는 알 수 있습니다.
>
> **하지만**, Kubernetes가 실제 데이터를 쓸 Disk와 Filesystem이 잘못돼 있으면 설치 이후 더 큰 문제가 생길 수 있습니다.
>
> **그래서 다음으로 Disk를 봅니다.**

---

# 5. Disk는 ‘무엇인지 확인하는 것’과 ‘바꾸는 것’을 분리한다

> Disk는 오늘 가장 조심해서 봐야 하는 항목입니다.
>
> Hostname이나 CPU는 잘못 읽어도 다시 확인할 수 있습니다.
>
> **하지만**, 잘못된 Disk에 Partition이나 Filesystem을 쓰면 기존 데이터를 잃을 수 있습니다.
>
> **그래서**, Disk에서는 먼저 무엇인지 확인하고, 실제 변경은 그다음 별도 절차로 분리합니다.

## 5.1 먼저 이 Disk가 무엇인지 확인한다

> 먼저 Block Device를 봅니다.
>
> Size와 Serial을 확인합니다.
>
> 현재 Partition과 Filesystem, Mount를 확인합니다.
>
> PV·VG·LV로 이미 사용 중인지도 봅니다.
>
> 그리고 보존해야 할 데이터가 있는지 확인합니다.
>
> **이 모든 확인이 필요한 이유는 Device 이름 하나만 보고 DATA Disk라고 단정하면 안 되기 때문입니다.**

```text
대상 Hostname·Role
→ Device·Size·Serial
→ Partition·Filesystem
→ Mount
→ PV·VG·LV
→ 보존 데이터
→ 승인된 DATA Disk와 일치 여부
```

## 5.2 DATA Disk를 찾았다고 바로 변경하지 않는다

> DATA Disk를 식별했다고 하겠습니다.
>
> **하지만**, 그것은 “무슨 Disk인지 알았다”는 뜻이지 “지금 바꿔도 된다”는 뜻은 아닙니다.
>
> **그래서**, 실제 Partition·LVM·Filesystem 변경은 승인된 Runbook의 변경 Gate를 따릅니다.

```text
DATA Disk 식별 완료
≠ 변경 승인 완료

변경 실행 완료
≠ Filesystem 사용 가능 검증 완료
```

## 5.3 ETCD는 한 번 더 나눈다

> ETCD Node에서는 한 가지를 더 봅니다.
>
> 일반 Node의 Container Runtime 데이터와 ETCD 상태 데이터는 다릅니다.
>
> **그래서**, ETCD에 비-ETCD Filesystem 구조를 그대로 적용하면 안 됩니다.
>
> 원본 기준에서는 ETCD가 `/var/lib/etcd`를 사용합니다.
>
> **하지만**, 신규 Member의 최종 ETCD Filesystem 설계가 승인 Source에서 아직 확정되지 않았다면 과거 값을 넣어 진행하지 않습니다.
>
> **따라서**, ETCD 설계가 미확정이면 Disk 변경 단계에서 중단합니다.

> `fdisk`, `pvcreate`, `vgcreate`, `lvcreate`, `mkfs.xfs` 같은 실제 파괴적 명령은 Initial VM Setting Runbook에서 수행합니다.
>
> 이 강의에서는 **왜 지금 바로 실행하면 안 되는지**까지 이해하면 됩니다.

> 이제 Node 자체의 신원과 Resource, Disk를 확인했습니다.
>
> **하지만**, Cluster가 외부에서 사용될 경로가 준비됐다는 뜻은 아직 아닙니다.
>
> **그래서 다음으로 VIP-A와 VIP-B를 봅니다.**

---

# 6. VIP-A와 VIP-B는 서로 다른 입구다

> 신규 Member에는 외부에서 Cluster로 들어오는 두 가지 중요한 LB 경로가 있습니다.
>
> 둘 다 VIP라고 부르기 때문에 하나의 경로처럼 느낄 수 있습니다.
>
> **하지만**, 사용하는 주체와 Backend가 다릅니다.

```text
운영자·Bastion·자동화
→ VIP-A:6443
→ Master
→ Kubernetes API 경로

사용자 Application 요청
→ VIP-B:80/443
→ Router
→ Ingress 경로
```

## 6.1 실제 LB 테스트 전에는 먼저 운영 Gate가 있다

> 여기서 바로 `curl`이나 임시 Listener부터 실행하면 안 됩니다.
>
> 원본 Initial VM Setting에는 LB 테스트 전에 DS Cloud Service Desk에 경고 예외를 요청하고 사전 통보하도록 되어 있습니다.
>
> **왜냐하면 LB 테스트 자체가 운영 감지와 연결될 수 있기 때문입니다.**
>
> **그래서**, 실제 LB 검증을 수행하기 전에 승인된 Runbook에서 경고 예외와 유지보수 시간 조건이 충족됐는지 먼저 확인합니다.
>
> 교육이라고 해서 이 경계를 생략하지 않습니다.

## 6.2 VIP-A는 Kubernetes API 경로다

> VIP-A는 Frontend `6443`을 통해 Master의 Kubernetes API 경로로 이어집니다.
>
> **하지만**, 지금 Kubernetes API가 아직 설치되지 않았다면 최종 `/healthz` 성공까지 증명할 수는 없습니다.
>
> **그래서**, 지금은 현재 존재하는 LB 구성과 연결 준비가 어디까지 확인됐는지만 기록합니다.
>
> Kubernetes API 기능 자체는 설치 후 다시 확인합니다.

```text
VIP-A TCP 경로 확인
≠ Kubernetes API 기능 성공
```

> 그리고 HTTPS 응답을 확인하더라도 Certificate 검증을 생략한 테스트라면 Certificate Trust까지 성공했다고 말하지 않습니다.

## 6.3 VIP-B는 Application Ingress 경로다

> VIP-B는 사용자 Application 요청이 들어오는 경로입니다.
>
> 원본 기준에서는 Frontend `80`이 Router Backend `30080`, Frontend `443`이 Router Backend `30443`으로 이어집니다.

```text
VIP-B:80
→ Router:30080

VIP-B:443
→ Router:30443
```

> 여기서 80 경로가 성공했다고 443 경로도 성공한 것은 아닙니다.
>
> **특히**, 임시 Python HTTP Server로 `30080`을 확인하는 것은 HTTP 경로만 증명합니다. `30443`의 TLS 동작까지 증명하지는 못합니다.
>
> **그래서**, HTTP와 HTTPS 경로는 각각 따로 확인합니다.

```text
VIP-B 80 경로 성공
≠ VIP-B 443 TLS 경로 성공
```

## 6.4 한 테스트의 성공 범위를 다른 경로까지 확대하지 않는다

> LB 확인 결과를 적을 때 `정상`이라고 한 단어만 쓰지 않습니다.
>
> 어느 Cluster의 어느 VIP를, 어느 Frontend Port에서, 어느 Backend Role과 Port까지 확인했는지 적습니다.
>
> **그래야 나중에 장애가 났을 때 마지막으로 어디까지 성공했는지 다시 찾을 수 있습니다.**

```text
Cluster
+ VIP
+ Frontend Port
+ Backend Host·Role
+ Backend Port
+ 실행 시각
+ 관찰 결과
```

> **결국**, VIP-A 성공과 VIP-B 성공은 서로 대신할 수 없고, Frontend 연결 성공과 실제 Application 기능 성공도 같은 증거가 아닙니다.

# 7. 이 블록의 완료는 ‘모든 것이 정상’이 아니다

> 여기까지 오면 모든 항목이 정상이어야 다음으로 갈 수 있다고 생각할 수 있습니다.
>
> **하지만**, 오늘 첫 블록의 목적은 모든 문제를 해결하는 것이 아닙니다.
>
> **목적은 무엇이 확인됐고, 무엇이 불일치하고, 무엇이 아직 미확정인지 정확히 나누는 것입니다.**

> 예를 들어 VIP 승인값이 아직 오지 않았다면 VIP는 미확정입니다.
>
> ETCD Filesystem 설계가 아직 승인되지 않았다면 ETCD Disk 변경은 미확정입니다.
>
> **이 상태 자체가 잘못된 것은 아닙니다.**
>
> **하지만**, 미확정값을 자동화 입력이나 파괴적 변경에 사용하면 안 됩니다.

## 7.1 이 블록에서 확인돼야 하는 것

```text
신규 Member Cluster Identity를 설명할 수 있음
+ Node별 Role·Hostname·Management IP의 근거가 있음
+ OS·CPU·Memory의 현재 상태를 승인 기준과 대조함
+ DATA Disk의 Identity와 현재 사용 상태를 확인함
+ ETCD와 비-ETCD Filesystem 경계를 구분함
+ VIP-A와 VIP-B의 역할과 Backend를 구분함
+ LB 테스트 전 운영 Gate를 알고 있음
+ 지금 확인 가능한 LB 범위와 설치 후 확인할 범위를 나눔
+ 확인됨·불일치·미확정을 구분함
```

## 7.2 다음 조건에서는 중단한다

```text
대상 Cluster가 불명확
Role·Hostname·IP가 서로 일치하지 않음
DATA Disk가 무엇인지 확정되지 않음
보존 데이터 여부가 불명확
ETCD 최종 Filesystem 설계가 미확정
VIP 또는 Backend 승인값이 미확정
LB 테스트 사전 통보·예외 조건이 충족되지 않음
```

> **중단은 실패가 아닙니다.**
>
> 확인되지 않은 값을 다음 자동화나 파괴적 변경으로 넘기지 않았다는 정상적인 판정입니다.

# 8. 다음 Bastion 블록으로 넘기는 것은 값이 아니라 ‘근거가 붙은 값’이다

> 이제 다음 블록에서는 Bastion을 준비합니다.
>
> **하지만**, Bastion 단계에서 다시 과거 Xi'an 문서를 뒤져 값을 새로 채우면 오늘 확인한 의미가 사라집니다.
>
> **그래서**, 지금까지 확인된 값만 다음 입력으로 넘깁니다.

```text
Cluster Name·용도
승인 근거
Node별 Role·Hostname·Management IP
Bastion Hostname·IP
승인 DNS·Domain
VIP-A·VIP-B와 Backend 역할
Pod CIDR·Service CIDR
Disk·Filesystem 확인 결과
미확정값과 영향
각 값의 현재 관찰 근거
확인 시각·확인자
```

> 여기서 중요한 것은 값 자체보다 **왜 그 값을 믿어도 되는지 설명할 수 있는가**입니다.
>
> 확인된 값은 다음 단계의 입력으로 사용합니다.
>
> **하지만**, 미확정값이 Bastion 설정의 필수 입력이라면 그 부분은 진행하지 않습니다.
>
> **따라서**, 필요한 Source를 먼저 확보한 뒤 다시 이어갑니다.

---

# 9. 마무리 — 오늘 첫 블록을 다시 하나의 이야기로 말한다

> 오늘 신규 Member 구축을 시작했지만 설치 명령부터 시작하지 않았습니다.
>
> **왜냐하면** 자동화는 우리가 넣은 값이 맞는지 대신 판단하지 않기 때문입니다.
>
> **그래서** 먼저 어떤 Cluster를 만들고 있는지, 각 VM이 어떤 Role인지 고정했습니다.
>
> **하지만** 승인 문서만으로 현재 VM이 그 대상이라고 확정할 수는 없기 때문에 Hostname과 IP, OS와 Resource를 실제 VM에서 다시 확인했습니다.
>
> **그리고** Disk는 잘못 변경하면 데이터 손실이 생길 수 있기 때문에 무엇인지 확인하는 단계와 실제 변경 단계를 분리했습니다. ETCD는 일반 Node와 데이터 경로도 따로 봤습니다.
>
> **하지만** Node가 모두 맞다고 외부 진입 경로까지 준비된 것은 아니기 때문에 VIP-A와 VIP-B를 각각 확인했습니다. VIP-A는 Master의 Kubernetes API 경로이고, VIP-B는 Router의 Application Ingress 경로입니다.
>
> 실제 LB 테스트 전에는 Service Desk 경고 예외와 사전 통보 같은 운영 Gate도 먼저 확인해야 합니다.
>
> **결국**, 오늘 첫 블록의 목적은 모든 칸을 채우는 것이 아니라 **다음 자동화가 믿어도 되는 사실과 아직 믿으면 안 되는 값을 분리하는 것**입니다.
>
> 그리고 다음 Bastion 단계에는 단순한 값이 아니라 **승인 근거와 현재 출력이 연결된 값**만 넘깁니다.
