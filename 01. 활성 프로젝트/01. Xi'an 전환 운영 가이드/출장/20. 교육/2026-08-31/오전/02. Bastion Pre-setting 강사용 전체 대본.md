# Bastion Pre-setting 강사용 전체 대본

> [!important] 사용 방법
> 이 대본은 앞 블록에서 확인한 신규 Member의 값을 **Bastion이라는 설치 실행점에 연결하는 이유와 판단 흐름**을 설명한다.
>
> DNS·`/etc/hosts`·sudoers·Repository·Python·Pip·Bundle·SSH Key의 정확한 변경 명령은 승인된 Bastion Runbook을 따른다. 여기서는 파일을 만드는 순서를 외우게 하기보다 **왜 필요한지 → 무엇이 실제로 동작해야 하는지 → 무엇을 확인해야 다음 Node 단계로 갈 수 있는지**를 말로 연결한다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
앞 블록에서 신규 Member 값을 확인했다
→ 하지만 그 값만 있어서는 설치를 시작할 실행점이 없다
→ 그래서 Bastion을 이번 Cluster의 설치 기준점으로 준비한다
→ 먼저 이 Bastion이 정말 오늘 대상인지 확인한다
→ 그다음 Node 이름을 올바른 IP로 찾게 한다
→ 하지만 이름만 찾아도 자동화 권한이 없으면 작업할 수 없다
→ 그래서 dspaas와 sudo를 확인한다
→ 하지만 권한만 있어도 Package와 Tool이 없으면 설치할 수 없다
→ 그래서 Repository와 Bundle·Toolchain을 확인한다
→ 마지막으로 Node 접근에 사용할 SSH 인증 재료를 준비한다
→ 각 결과가 같은 신규 Member를 가리키는지 다시 묶는다
→ 오후 Node Pre-setting으로 넘긴다
```

## 0-1. 앞 블록에서 이어받는 것

> 앞 블록에서는 신규 Member의 Cluster Name과 Node Role, Hostname과 IP, VIP와 CIDR, Disk와 Filesystem 상태를 확인했습니다.
>
> 그리고 어떤 값은 확인됐고, 어떤 값은 불일치했고, 어떤 값은 아직 미확정인지 구분했습니다.
>
> **이제 Bastion 단계에서는 그 결과를 다시 추측하지 않습니다.** 확인된 값은 그대로 쓰고, 미확정값은 미확정 상태로 이어받습니다.

```text
신규 Member Cluster Name·용도
Node별 Role·Hostname·Management IP
Bastion Hostname·IP
승인 DNS·Domain
VIP-A·VIP-B
Pod CIDR·Service CIDR
Disk·Filesystem 확인 결과
미확정값과 근거
```

## 0-2. 오늘 전체 한 줄

```text
신규 Member 실제값 확인
→ Bastion Identity 확인
→ DNS·hosts로 올바른 Node 찾기
→ dspaas가 자동화 권한 사용
→ Repository로 Package 공급
→ 승인된 Bundle과 Toolchain 준비
→ SSH Key를 안전하게 준비
→ 같은 신규 Member 기준인지 재확인
→ 오후 Node Pre-setting으로 전달
```

# 1. 시작 — Bastion은 단순히 거쳐 가는 서버가 아니다

> 앞 블록에서 어떤 VM을 사용할지는 확인했습니다.
>
> 그러면 이제 그 VM들을 실제 Kubernetes Cluster로 만드는 명령을 어디에서 시작할지가 필요합니다.
>
> **그래서 Bastion이 필요합니다.**

> Bastion을 단순 Jump Server라고만 생각하면 “다른 서버로 SSH하는 중간 서버” 정도로 보입니다.
>
> **하지만**, 실제 구축에서는 더 많은 것이 Bastion에 모입니다.
>
> 어떤 Node 이름을 어느 IP로 찾는지, 어떤 Account로 자동화를 실행하는지, 어떤 Repository에서 Package를 받는지, 어떤 Kubespray Bundle과 Toolchain을 쓰는지, 어떤 SSH Key를 Node에 배포할지가 Bastion에서 시작됩니다.
>
> **따라서**, Bastion은 단순한 접속 중계점이 아니라 **이번 Cluster 설치의 기준점**입니다.

> 여기서 중요한 것은 각 설정이 따로 정상인지가 아닙니다.
>
> `/etc/hosts`는 신규 Member인데 Bundle은 과거 Host Cluster용일 수도 있고, Account는 맞는데 Repository가 다른 환경을 볼 수도 있습니다.
>
> **그래서**, 오늘은 Bastion의 각 기능을 하나씩 확인한 뒤 마지막에 **전부 같은 신규 Member를 가리키는지** 다시 묶어 보겠습니다.

---

# 2. 설정 전에 먼저 ‘지금 이 Bastion이 맞는가’를 확인한다

> Bastion에 Login이 됐다고 바로 설정을 시작하면 안 됩니다.
>
> **왜냐하면 다른 Bastion에 접속해도 Login 자체는 성공할 수 있기 때문입니다.**
>
> **그래서**, 먼저 지금 이 서버가 앞 블록에서 확인한 신규 Member Bastion인지 봅니다.

> 현재 Hostname과 IP를 확인합니다.
>
> 앞 블록의 Bastion Hostname·IP와 같은지 확인합니다.
>
> 현재 작업 Account도 확인합니다.
>
> 그리고 이미 작업 Directory나 Bundle이 있다면 이것이 어느 Cluster에서 사용하던 것인지 확인합니다.

```text
현재 Bastion Hostname·IP
→ 앞 블록의 신규 Member Bastion과 일치하는가

현재 작업 Account
→ 승인된 자동화 Account인가

현재 Directory·기존 파일
→ 신규 Member용이라고 설명할 근거가 있는가
```

> **하지만**, 파일 이름이 같다는 이유만으로 신규 Member용이라고 판단하지 않습니다.
>
> 다른 Cluster Bastion에서 같은 명령이 성공했다고 오늘 Bastion의 증거가 되는 것도 아닙니다.

```text
다른 Bastion에서 성공
≠ 오늘 Bastion 성공

같은 파일 이름
≠ 같은 Cluster용 파일
```

> **따라서**, Bastion Identity가 맞지 않거나 기존 파일의 출처를 설명할 수 없으면 그 파일을 그대로 사용하지 않습니다.

> 이제 올바른 Bastion에 있다는 것은 확인했습니다.
>
> **하지만**, 이 Bastion이 신규 Member Node를 올바르게 찾아갈 수 있는지는 아직 모릅니다.
>
> **그래서 다음으로 이름 해석을 봅니다.**

---

# 3. DNS와 hosts — 이름이 올바른 Node를 가리켜야 한다

> Ansible과 운영자는 결국 Hostname이나 IP를 이용해 Node를 찾아갑니다.
>
> 그래서 DNS와 `/etc/hosts`의 목적은 파일을 채우는 것이 아닙니다.
>
> **신규 Member Hostname을 요청했을 때 신규 Member의 승인 IP를 돌려주는 것**이 목적입니다.

## 3.1 Nameserver가 적혀 있다고 이름 해석이 성공한 것은 아니다

> `/etc/resolv.conf`에 Nameserver가 들어 있다고 하겠습니다.
>
> 이것은 설정이 존재한다는 뜻입니다.
>
> **하지만**, 실제로 Hostname을 찾을 수 있다는 뜻은 아닙니다.
>
> **그래서**, 변경 뒤에는 신규 Member Hostname을 실제로 조회합니다.

```text
Nameserver 설정 존재
≠ 이름 해석 성공
```

> 그리고 반환된 IP를 앞 블록에서 확인한 Node IP와 비교합니다.
>
> **그래야** “DNS 설정이 있다”가 아니라 “이 Bastion이 올바른 신규 Member Node를 찾는다”고 말할 수 있습니다.

## 3.2 `/etc/hosts`도 파일 존재보다 반환 결과가 중요하다

> `/etc/hosts`에 Hostname이 있다고 끝난 것도 아닙니다.
>
> **하지만**, 그 Hostname이 다른 Cluster IP를 가리키면 오히려 자동화를 잘못된 Node로 보낼 수 있습니다.
>
> **그래서**, `/etc/hosts`는 앞 블록의 신규 Member Role·Hostname·IP 목록과 대조합니다.

> 원본 Bastion Runbook에는 Cluster별 Host 목록을 섞지 말라는 경계가 있습니다.
>
> **따라서**, 기존 Host·PRD·DEV Cluster 목록을 신규 Member Bastion에 합쳐 넣지 않습니다.

```text
hosts 항목 존재
≠ 신규 Member 승인 IP와 일치

한 Node 이름 해석 성공
≠ 전체 대상 Node 목록 확인
```

## 3.3 DNS와 hosts가 서로 다른 답을 주면 먼저 멈춘다

> DNS는 한 IP를 주고 `/etc/hosts`는 다른 IP를 줄 수도 있습니다.
>
> 이런 경우 어느 쪽이 더 그럴듯해 보이는지 보고 맞추면 안 됩니다.
>
> **왜냐하면 지금 필요한 것은 편한 값이 아니라 이번 신규 Member의 승인값이기 때문입니다.**
>
> **그래서**, 어떤 Source가 이번 환경의 기준인지 먼저 확인합니다.

> **결국**, 이름 해석 단계의 완료는 파일을 저장한 것이 아니라 다음 연결입니다.

```text
신규 Member Hostname
→ Bastion에서 실제 반환된 IP
→ 앞 블록의 승인 Role·IP와 일치
```

> 이름을 올바른 Node로 찾게 됐습니다.
>
> **하지만**, Node를 찾아간다고 자동화 작업까지 할 수 있는 것은 아닙니다.
>
> **그래서 다음으로 Account와 sudo를 봅니다.**

---

# 4. dspaas와 sudo — Account가 있다는 것과 자동화 권한은 다르다

> Xi'an 구축에서는 `dspaas` Account를 사용합니다.
>
> Account가 존재하면 Login은 할 수 있습니다.
>
> **하지만**, Ansible이 필요한 Root 작업을 자동으로 수행하려면 Password Prompt 없이 sudo를 사용할 수 있어야 합니다.
>
> **그래서**, Account 존재와 자동화 권한을 따로 확인합니다.

```text
dspaas Account 존재
→ 사용자 존재 확인

승인 Group 연결
→ 권한 정책 적용 대상 확인

실제 dspaas Session에서 sudo -n 성공
→ 비대화식 자동화 권한 확인
```

> sudoers 파일의 문법이 정상이어도 끝이 아닙니다.
>
> **왜냐하면** 문법이 맞아도 `dspaas`가 실제 Session에서 Password 없이 sudo를 못 쓸 수 있기 때문입니다.
>
> **그래서**, 실제 `dspaas` Session에서 기능을 확인합니다.

```text
sudoers 문법 정상
≠ dspaas sudo 기능 성공

Root Session에서 성공
≠ dspaas Session에서 성공
```

> 이 단계에서 중요한 것은 `sudoers` 내용을 외우는 것이 아닙니다.
>
> **자동화가 사람의 Password 입력을 기다리지 않고 필요한 권한을 사용할 수 있는지**가 핵심입니다.

> 정확한 sudoers 편집과 Group 변경은 원본 Runbook을 따릅니다. 기존 보조 Group을 덮어쓰는 파괴적인 방식은 사용하지 않습니다.

> 이제 이름도 찾고 필요한 권한도 사용할 수 있습니다.
>
> **하지만**, 설치에 필요한 Package와 Tool을 받을 수 없다면 Bastion은 아직 실행점 역할을 할 수 없습니다.
>
> **그래서 다음으로 Repository를 봅니다.**

---

# 5. Repository — 설정 파일이 아니라 Package 공급 경로다

> Repository를 보면 URL이나 `.repo` 파일부터 떠올릴 수 있습니다.
>
> **하지만**, Repository의 목적은 설정 파일을 만드는 것이 아닙니다.
>
> **승인된 Source에서 필요한 Metadata와 Package를 실제로 받을 수 있게 하는 것**이 목적입니다.

## 5.1 Repo 파일이 있다고 기능이 성공한 것은 아니다

> Repo 파일이 이미 있다고 하겠습니다.
>
> 먼저 그 파일이 현재 승인된 Source를 바라보는지 확인합니다.
>
> **하지만**, URL이 맞아도 DNS나 Network가 막혀 있으면 Package를 받을 수 없습니다.
>
> **그래서**, 실제 Metadata 조회까지 확인합니다.

```text
Repo 파일 존재
≠ 승인 Source 사용

승인 URL 기재
≠ 실제 접근 성공

Metadata 조회 성공
≠ 필요한 Package 전체 설치 완료
```

> Pip Repository도 같은 방식입니다.
>
> 설정에 Index URL이 들어 있는지만 보지 않고 실제로 그 Index를 사용할 수 있는지 확인합니다.

## 5.2 잘못된 과거 URL을 비슷한 값으로 고치지 않는다

> 원본 Bastion 자료에는 과거 캡처에서 철자가 잘못됐거나 URL 일부가 비어 있는 Repository 항목도 남아 있습니다.
>
> **하지만**, 비슷해 보인다는 이유로 값을 만들어 넣으면 안 됩니다.
>
> **그래서**, 원본 Runbook이 미확정이라고 표시한 Repository는 먼저 현재 승인 Source를 확인합니다.

> 예전 로그에서 Package 설치가 성공했다고 해도 그 Endpoint가 오늘 신규 Member에서 승인된 Endpoint라는 뜻은 아닙니다.
>
> **따라서**, 과거 성공 로그는 참고하고 실제 설정은 현재 승인된 Source와 오늘 Bastion의 기능 결과를 기준으로 합니다.

> 이제 Package 공급 경로를 준비했습니다.
>
> **하지만**, Repository만 준비됐다고 어떤 Kubespray와 어떤 부속 Tool을 사용할지가 정해진 것은 아닙니다.
>
> **그래서 다음으로 Bundle을 봅니다.**

---

# 6. Bundle은 이번 구축에서 사용할 설치 기준 묶음이다

> Bundle은 이번 Kubernetes 구축에 사용할 Kubespray와 부속 Tool을 묶은 설치 자료입니다.
>
> 원본 Bastion Manual에는 과거 `SCS_DKS_Kubernetes_Stack-v1.0`과 `DKS-Kubespray-v2.19`가 기록돼 있습니다.
>
> 이 자료는 Bundle 안에 어떤 구성요소가 들어가는지 이해하는 데는 도움이 됩니다.
>
> **하지만**, 과거에 사용했다는 이유만으로 2026 신규 Member도 같은 Bundle을 사용한다고 확정할 수는 없습니다.
>
> **그래서**, 이번 구축에 사용할 Bundle은 현재 승인된 Source에서 다시 확인합니다.

## 6.1 Bundle은 출처부터 본다

> 먼저 어디에서 받은 Bundle인지 봅니다.
>
> 그다음 파일 이름과 Version을 확인합니다.
>
> 압축을 풀었다면 내부 Kubespray와 Tool Version도 확인합니다.
>
> **이렇게 해야** 단순히 “파일이 있다”가 아니라 “이번 신규 Member에 사용할 설치 묶음이 맞다”고 말할 수 있습니다.

```text
현재 승인 Bundle Source
→ 실제 받은 파일
→ Bundle Version
→ 압축 해제 위치
→ 내부 Kubespray·Tool Version
→ 이번 구축 기준과 일치
```

## 6.2 Checksum은 기대값의 Source가 있을 때 의미가 완성된다

> 파일이 바뀌지 않았는지 확인하려고 Checksum을 사용할 수 있습니다.
>
> **하지만**, 지금 파일에서 Checksum을 한 번 계산했다고 그 값이 공급자가 승인한 기대값이 되는 것은 아닙니다.
>
> **그래서**, 두 종류를 구분합니다.

```text
현재 파일에서 계산한 Checksum
→ 현재 파일을 다시 식별하는 관찰값

제공자·승인 Source가 제시한 기대 Checksum
→ 실제 파일과 대조하는 승인 기준
```

> 현재 승인 Source에 기대 Checksum이 있다면 실제 파일과 대조합니다.
>
> **하지만**, 기대 Checksum Source가 없다면 `승인 Checksum 확인 완료`라고 쓰지 않습니다.
>
> **따라서**, 필요하면 현재 파일의 Checksum은 추적용으로 기록하고 기대값은 미확정으로 남깁니다.

> Bundle이 정해졌습니다.
>
> **하지만**, Bundle 파일만 있어도 실행 환경이 맞지 않으면 Kubespray가 정상적으로 동작하지 않을 수 있습니다.
>
> **그래서 다음으로 Toolchain을 봅니다.**

---

# 7. Toolchain은 숫자를 맞추는 일이 아니라 Bundle을 실행할 조합을 맞추는 일이다

> Bastion에는 Python, Pip, Ansible, Helm 같은 Tool이 필요합니다.
>
> 각 Version 숫자를 따로 외우는 것이 목적은 아닙니다.
>
> **현재 승인된 Bundle이 기대하는 조합으로 실행할 수 있어야 합니다.**

> 예를 들어 `ansible --version`이 출력됐다고 하겠습니다.
>
> 그것은 Ansible이 설치돼 있다는 증거입니다.
>
> **하지만**, 그 Version이 이번 Bundle의 Requirement와 맞는지는 아직 별도 판단입니다.
>
> **그래서**, 실제 Tool Version을 Bundle Requirement와 연결합니다.

```text
Python 실행 가능
≠ Bundle 요구 Python과 일치

Ansible Version 출력
≠ Bundle Requirement와 일치

Helm 파일 존재
≠ 이번 구축 기준과 일치
```

> 원본 Manual의 Python·Pip·Ansible·Helm Version은 당시 환경의 증적입니다.
>
> **하지만**, 지금 신규 Member의 실행값은 현재 승인 Bundle이 결정합니다.
>
> **따라서**, Version을 과거 값에 억지로 맞추기 위해 기존 Symbolic Link를 무조건 덮어쓰거나 임의 변경하지 않습니다.

> 정확한 Python 설치, Pip 업데이트, Requirement 설치, Helm 배치와 Link 변경은 원본 Runbook을 따릅니다.

> 이제 Bastion 자체에서 필요한 도구까지 준비했습니다.
>
> **하지만**, Bastion에서 Node로 들어갈 인증 재료가 준비되지 않으면 다음 Node 설정을 시작할 수 없습니다.
>
> **그래서 마지막으로 SSH Key를 봅니다.**

---

# 8. SSH Key — Key가 있다는 것과 Node 접근이 성공한 것은 다르다

> Bastion에서 각 Node에 접근하려면 `dspaas`가 사용할 SSH Key Pair가 필요합니다.
>
> 그래서 먼저 Key Pair를 준비하고 어떤 Key를 이번 신규 Member에 사용할지 고정합니다.

> **하지만**, Key 파일이 존재한다고 대상 Node가 그 Public Key를 신뢰하는 것은 아닙니다.
>
> Public Key를 배포했다고 모든 Node의 실제 비대화식 SSH가 성공한 것도 아닙니다.

```text
Private/Public Key Pair 존재
≠ Node Public Key 배포 완료

Public Key 배포 완료
≠ 모든 Node 비대화식 SSH 성공
```

> **그래서**, 오전 Bastion 단계에서는 Key의 Identity와 소유 Account, Fingerprint와 배포 대상 Node 목록을 명확히 준비합니다.
>
> 그리고 실제 Public Key 배포와 Node별 SSH 성공은 이어지는 Node Pre-setting에서 같은 Node 목록을 기준으로 확인합니다.

## 8.1 보호정보는 원문을 보여주는 방식으로 증명하지 않는다

> SSH Key를 확인할 때 보안 경계도 중요합니다.
>
> **하지만**, Key가 존재한다는 것을 증명하려고 Private Key 본문을 문서에 복사하면 안 됩니다.
>
> **그래서**, 보호정보의 내용이 아니라 Identity와 사용 가능성을 기록합니다.

```text
기록 가능
= Key Type
+ Fingerprint
+ 소유 Account
+ 생성·확인 시각
+ Public Key 배포 대상

기록 금지
= Private Key 본문
+ Passphrase
+ Password
```

> **결국**, 오전 SSH 단계의 완료는 “SSH가 다 된다”가 아니라 **다음 Node 단계가 사용할 SSH 인증 재료와 대상이 안전하게 준비된 상태**입니다.

---

# 9. Bastion 준비는 각각의 성공이 아니라 하나의 기준으로 묶였을 때 끝난다

> 이제 이름 해석, sudo, Repository, Bundle과 Toolchain, SSH Key를 각각 봤습니다.
>
> 여기서 각 항목이 따로 성공했다고 바로 Bastion 준비 완료라고 하지 않습니다.
>
> **왜냐하면 서로 다른 Cluster의 값이 섞여 있어도 개별 명령은 성공할 수 있기 때문입니다.**
>
> **그래서**, 마지막으로 전부 같은 신규 Member를 가리키는지 다시 연결합니다.

```text
신규 Member Bastion Identity
→ 신규 Member Hostname·IP 해석
→ dspaas 비대화식 sudo
→ 현재 승인 Repository
→ 현재 승인 Bundle·Toolchain
→ 같은 신규 Member Node 목록에 사용할 SSH Public Key
```

> DNS는 신규 Member인데 Bundle은 과거 PRD용이면 준비 완료가 아닙니다.
>
> Repository가 정상이어도 어떤 Bundle을 쓸지 미확정이면 준비 완료가 아닙니다.
>
> Key Pair가 있어도 어느 Node에 배포할지 대상이 확정되지 않았다면 다음 단계 입력이 닫힌 것이 아닙니다.

```text
일부 기능 성공
≠ Bastion 전체 준비 완료
```

---

# 10. 이 블록의 완료 기준과 중단 기준

> Bastion Pre-setting의 완료는 파일을 몇 개 만들었는지가 아닙니다.
>
> **오후 Node Pre-setting을 같은 신규 Member 기준으로 안전하게 시작할 수 있는 상태**가 완료입니다.

## 10.1 완료 기준

```text
현재 Bastion이 신규 Member용임을 확인
+ 대상 Node 이름이 승인 IP와 연결됨
+ dspaas 비대화식 sudo 기능 확인
+ Repository가 현재 승인 Source와 연결되고 실제 접근 범위를 확인
+ 이번 구축에 사용할 Bundle Source·Version·내용 확인
+ 기대 Checksum Source가 있는 경우 실제 파일과 대조
+ 기대 Checksum Source가 없으면 미확정으로 명시
+ Toolchain이 현재 Bundle Requirement와 연결됨
+ SSH Key Identity·Fingerprint·소유 Account 확인
+ Public Key 배포 대상 Node 목록 확정
+ 보호정보 원문 미노출
+ 남은 미확정값과 영향 기록
```

## 10.2 다음 조건에서는 중단한다

```text
현재 Bastion이 신규 Member용인지 불명확
DNS·hosts가 승인 Node IP와 충돌
이름 해석 기준 Source가 미확정
dspaas 비대화식 sudo 실패
필수 Repository URL이 미확정
Repository 기능 확인 실패
이번 구축 Bundle Source·Version이 미확정
Toolchain과 Bundle Requirement 관계가 미확정
기대 Checksum이 필수 승인 조건인데 Source가 없음
SSH Key 소유 Account·배포 대상이 불명확
```

> **하지만**, 중단 항목이 있다고 해서 임의로 다른 Cluster 값을 복사해 채우지 않습니다.
>
> **따라서**, 필요한 Source를 확보하거나 현재 대상을 수정한 뒤 같은 기준으로 다시 확인합니다.

# 11. 오후 Node Pre-setting으로 넘기는 것은 ‘준비된 기능과 아직 준비되지 않은 기능’이다

> 이제 오후에는 각 Kubernetes Node를 준비합니다.
>
> **하지만**, 다음 블록에서 Bastion 설정을 다시 처음부터 조사하면 오전 Handoff의 의미가 없습니다.
>
> **그래서**, 지금 확인한 결과를 그대로 넘깁니다.

```text
Bastion Hostname·IP·확인 시각
신규 Member Node Role·Hostname·Management IP 목록
DNS·hosts 이름 해석 확인 결과
승인 DNS·Domain 근거
dspaas sudo -n 확인 결과
현재 승인 Repository와 실제 확인 범위
미확정 Repository와 필요한 Source
Bundle Source·파일·Version·Root Directory
Bundle 내부 Kubespray·Tool Version
기대 Checksum 존재 여부와 대조 결과
현재 Toolchain과 Bundle Requirement 관계
SSH Public Key Fingerprint·소유 Account
Public Key 배포 대상 Node 목록
미확정·중단 항목과 영향
```

> 여기서 아직 Public Key를 Node에 배포하지 않았다면 `SSH 접근 성공`이라고 넘기지 않습니다.
>
> **왜냐하면 준비한 것과 실제로 성공한 것은 다른 상태이기 때문입니다.**
>
> **그래서**, 다음 Node Pre-setting에서 같은 `dspaas` Account와 같은 Node 목록으로 Public Key 배포와 실제 SSH 기능을 확인합니다.

---

# 12. 마무리 — Bastion을 다시 하나의 이야기로 말한다

> 앞 블록에서는 신규 Member의 실제값을 확인했습니다.
>
> **하지만**, 그 값만 있다고 Kubernetes 설치를 시작할 수 있는 것은 아니었습니다.
>
> **그래서**, 그 값을 기준으로 사용할 Bastion을 준비했습니다.
>
> 먼저 현재 Bastion이 정말 오늘 신규 Member용인지 확인했습니다.
>
> **그리고**, 신규 Member Hostname이 올바른 IP를 반환하도록 DNS와 hosts를 확인했습니다.
>
> **하지만**, 이름만 찾아도 자동화 권한이 없으면 작업할 수 없기 때문에 `dspaas`가 비대화식 sudo를 실제로 사용할 수 있는지 확인했습니다.
>
> **또한**, 권한만 있어도 Package와 Tool이 없으면 설치할 수 없기 때문에 승인된 Repository와 Bundle, Bundle이 요구하는 Toolchain을 확인했습니다.
>
> Bundle의 Checksum은 기대값의 Source가 있을 때 실제 파일과 대조했고, Source가 없으면 승인됐다고 만들지 않았습니다.
>
> 마지막으로 다음 Node 작업에 사용할 SSH Key의 Identity와 배포 대상을 준비했고, Private Key 같은 보호정보는 노출하지 않았습니다.
>
> **결국**, Bastion 준비의 목적은 설정 파일을 많이 만드는 것이 아니라 **이름·권한·Package·Bundle·Toolchain·SSH 인증 재료가 모두 같은 신규 Member를 가리키는 설치 기준점을 만드는 것**입니다.
