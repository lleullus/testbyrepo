# 신규 Member 환경·VM·LB 실제값 확인 강사용 전체 대본 - 새 작성본

> [!important] 사용 방법
> 오늘은 설치 명령을 실행하지 않는다. 먼저 신규 Member의 VM과 Load Balancer가 승인된 설계와 같은지 확인하고, **Kubespray에 넣어도 되는 실제값**을 만든다.
>
> 조회와 변경 명령은 승인된 Runbook을 따른다. 기존 Xi'an Cluster의 값은 구조를 이해하는 참고자료일 뿐 신규 Member의 실행값으로 복사하지 않는다.

## 0. 강사가 머릿속에 들고 갈 설명 공식

```text
새 Member Cluster를 구축한다
→ 하지만 Kubespray는 입력값이 맞는지 판단하지 않는다
→ 그래서 먼저 대상 Cluster와 VM을 확인한다
→ VM마다 역할이 다르므로 Role을 구분한다
→ Role·Hostname·IP가 맞으면 Resource와 Disk를 확인한다
→ Node 확인 뒤에는 VIP-A와 VIP-B를 구분한다
→ 확인된 값만 Bastion 준비에 넘긴다
```

## 0-1. 오늘 전체 한 줄

> 오늘의 결과물은 VM 목록이 아닙니다. **신규 Member를 잘못된 대상에 설치하지 않도록, 다음 자동화가 사용할 값과 그 근거를 확인하는 것**입니다.

---

# 1. 시작 — VM과 Kubespray가 있어도 바로 설치하지 않는다

> 신규 Member용 VM과 Kubespray Bundle이 준비돼 있으면 바로 Inventory를 만들고 싶을 수 있습니다.
>
> **하지만 Kubespray는 Hostname·IP·Role이 오늘 대상의 값인지 확인하지 않습니다.** 입력한 값을 그대로 여러 Node에 적용합니다.
>
> 그래서 설치보다 먼저 대상과 값을 확인합니다.
>
> 기존 Xi'an Host나 Member Cluster는 Role과 VIP 구조를 이해하는 데 도움이 됩니다. 그러나 기존 환경이 정상이라는 사실은 신규 Member의 Hostname·IP·Disk·VIP가 같다는 뜻이 아닙니다.
>
> 따라서 신규 Member의 값은 승인 설계와 현재 VM 출력에서 다시 확인합니다.
>
> 승인 설계와 현재 출력이 다르거나 근거가 없으면 기존 Cluster 값으로 채우지 않고 미확정으로 남깁니다.
>
> 그런데 VM마다 맡은 일이 다르므로 먼저 Role을 구분합니다.

---

# 2. Role을 알아야 확인 기준이 정해진다

> **Bastion**은 설치를 시작하는 서버입니다. Node 이름 해석, 작업 Account, Bundle과 자동화 실행이 여기서 시작됩니다.
>
> **Master**는 Kubernetes API와 Control Plane을 담당합니다. 따라서 API용 VIP-A의 Backend가 됩니다.
>
> **ETCD**는 Kubernetes 상태를 저장합니다. 일반 Node의 Container Runtime 데이터와 목적이 다르며 Xi'an 기준 경로는 `/var/lib/etcd`입니다.
>
> **Router**는 외부 Application 요청을 Ingress로 전달합니다. 따라서 Application용 VIP-B의 Backend가 됩니다.
>
> **Infra**는 Monitoring과 KubeSphere 같은 플랫폼 Workload가 주로 실행되고, **Worker**는 사용자 Application이 주로 실행됩니다.
>
> Role 이름을 외우는 것이 목적은 아닙니다. **Role에 따라 확인할 Disk, Filesystem과 VIP 경로가 달라지기 때문에 먼저 구분하는 것**입니다.
>
> 이제 Role을 알았으므로 실제 접속한 VM이 그 대상인지 확인합니다.

---

# 3. CPU보다 먼저 VM의 신원을 확인한다

> VM에 접속했다고 CPU와 Memory부터 보지 않습니다. 다른 VM에서 정확한 명령을 실행해도 신규 Member의 증거가 아니기 때문입니다.
>
> 먼저 Cluster와 Role을 확인합니다. 그리고 현재 Hostname과 Management IP를 승인된 Role·Hostname·IP와 대조합니다.
>
> Hostname만 맞고 IP가 다르거나, IP는 맞지만 Role이 다르면 다음 단계로 가지 않습니다.
>
> **Role·Hostname·Management IP가 같은 VM을 가리킬 때 대상 확인이 끝납니다.**

## 3.1 대상이 맞으면 Resource를 확인한다

> 그다음 OS와 Version, CPU와 Memory를 확인합니다.
>
> 기존 Node 사양은 참고할 수 있지만 최종 기준은 신규 Member 승인 설계입니다.
>
> Resource까지 맞으면 VM의 기본 사양은 확인됐습니다.
>
> **하지만 Kubernetes는 CPU와 Memory만 사용하지 않습니다.** Image와 상태 데이터를 저장할 Disk와 Filesystem도 필요합니다. 따라서 다음은 Disk입니다.

---

# 4. Disk는 Device 이름보다 현재 용도를 먼저 확인한다

> `/dev/sdb`가 보인다고 바로 DATA Disk라고 판단하지 않습니다.
>
> 이미 Partition이나 Filesystem이 있을 수 있고, 다른 곳에 Mount됐거나 LVM에서 사용 중일 수도 있습니다. 보존해야 할 데이터가 있을 수도 있습니다.
>
> 그래서 Size와 Serial, Partition·Filesystem, Mount, `/etc/fstab`, LVM 상태를 확인하고 승인된 DATA Disk와 대조합니다.
>
> 여기까지 맞으면 **Disk의 신원을 확인한 것**입니다. 아직 변경 승인을 받은 것은 아닙니다.
>
> 따라서 `fdisk`, `pvcreate`, `vgcreate`, `lvcreate`, `mkfs.xfs` 같은 파괴적 작업은 승인된 Initial VM Setting Runbook의 조건을 확인한 뒤 수행합니다.
>
> 또한 변경 명령이 성공해도 끝이 아닙니다. 의도한 Filesystem이 실제로 Mount되고 사용할 수 있어야 합니다.

## 4.1 ETCD Disk는 별도로 본다

> ETCD는 Kubernetes 상태를 저장하므로 일반 Node의 Container Runtime DATA Disk와 목적이 다릅니다.
>
> 따라서 일반 Node Filesystem 구성을 ETCD에 그대로 적용하지 않습니다.
>
> 신규 Member의 ETCD 경로와 크기가 미확정이면 기존값을 복사하지 않고 변경을 멈춥니다.
>
> 이제 VM의 신원과 Resource, Disk까지 확인했습니다.
>
> **하지만 Node가 맞아도 외부에서 Cluster로 들어오는 경로는 별도입니다.** 그래서 VIP-A와 VIP-B를 확인합니다.

---

# 5. VIP-A와 VIP-B는 목적이 다르다

> 여러 Master나 Router 앞에는 고정된 가상 주소를 둘 수 있습니다. 이 주소가 VIP이고 Load Balancer가 요청을 Backend로 전달합니다.
>
> **VIP-A**는 운영자·Bastion·자동화가 Kubernetes API로 들어가는 경로입니다. Frontend `6443`이 Master API로 이어집니다.
>
> **VIP-B**는 사용자 Application 요청이 들어오는 경로입니다. Frontend `80`은 Router `30080`, Frontend `443`은 Router `30443`으로 이어집니다.
>
> 따라서 VIP-A가 정상이라고 VIP-B까지 정상인 것은 아닙니다. 또한 VIP-B의 HTTP가 성공했다고 HTTPS까지 성공한 것도 아닙니다.

## 5.1 시험 전에 운영 조건을 확인한다

> Load Balancer 시험은 운영 감지와 연결될 수 있습니다.
>
> 그래서 임시 Listener나 `curl`을 실행하기 전에 Service Desk 경고 예외, 사전 통보와 작업 시간을 확인합니다.

## 5.2 현재 단계에서 확인할 범위를 구분한다

> Kubernetes API가 아직 설치되지 않았다면 VIP-A의 최종 API Health는 확인할 수 없습니다.
>
> 이 시점에는 승인된 VIP, Backend Role, Load Balancer 구성과 가능한 TCP 경로를 확인하고 API 기능은 설치 후 같은 VIP에서 다시 확인합니다.
>
> 반면 VIP-B의 `80 → 30080`이 성공했다면 HTTP 경로만 확인된 것입니다. `443 → 30443`의 TLS와 Certificate Trust는 별도입니다.
>
> 따라서 결과를 단순히 `VIP 정상`이라고 적지 않습니다. **어느 VIP의 어느 Port가 어느 Backend까지 확인됐는지** 기록합니다.

---

# 6. Bastion에는 확인된 값만 넘긴다

> 다음 블록에서는 Bastion을 설치 기준점으로 준비합니다.
>
> 그래서 승인 설계와 현재 출력이 일치한 Cluster와 Bastion VM, Node Role·Hostname·Management IP를 넘깁니다. DNS·Domain, VIP-A·VIP-B, Pod·Service CIDR도 확인된 근거와 상태를 함께 전달합니다.
>
> VIP 승인값이 없거나 Disk·Filesystem이 미확정이면 추측하지 않고 그대로 남깁니다. DATA Disk의 신원이나 보존 데이터가 불명확한 상태에서 파괴적 작업을 시작하지 않습니다.
>
> 다음 사람이 기존 자료를 보고 빈칸을 추측하지 않아도, 왜 이 값이 신규 Member의 값인지 설명할 수 있어야 합니다.

---

# 7. 문제가 생기면 처음 다른 지점부터 확인한다

> Hostname과 IP가 다르면 Hostname부터 바꾸지 않습니다. 현재 접속한 VM이 맞는지와 승인 Source가 최신인지 먼저 확인합니다.
>
> DATA Disk가 예상과 다르면 강제로 구성을 맞추지 않습니다. Size·Serial, Partition·Filesystem, Mount와 LVM 상태를 다시 봅니다.
>
> VIP-B의 80은 되는데 443이 실패하면 HTTP 성공은 유지하고 TLS 경로만 확인합니다.
>
> VIP-A가 API 응답을 주지 않으면 먼저 Kubernetes API가 설치된 단계인지 구분합니다.
>
> 확인 순서는 `대상 VM → Resource → Disk → VIP 경로`입니다.

---

# 8. 마무리

> Kubespray는 입력값의 진위를 판단하지 않기 때문에 설치 전에 실제값을 확인했습니다.
>
> 먼저 Role·Hostname·IP로 VM을 확인하고, 그다음 Resource와 Disk를 확인했습니다. 또한 Node 확인과 별도로 VIP-A와 VIP-B의 목적과 현재 검증 범위를 구분했습니다.
>
> **결국 오늘의 결과는 신규 Member의 VM·Disk·VIP 중 무엇을 설치 입력으로 사용할 수 있는지 정리한 상태입니다.**
>
> 이제 확인된 값만 사용해 Bastion을 준비하겠습니다.

---

# 9. 마지막 확인 질문

1. VM과 Kubespray가 있어도 바로 설치하면 안 되는 이유는 무엇인가?
2. 기존 Xi'an Cluster 값은 신규 Member 구축에서 어떤 용도로만 사용할 수 있는가?
3. 승인 설계와 현재 VM 출력이 다르면 어떻게 처리해야 하는가?
4. Role을 먼저 구분해야 하는 이유는 무엇인가?
5. Role·Hostname·IP 중 하나가 다르면 왜 다음 단계로 가면 안 되는가?
6. Device 이름만 보고 DATA Disk를 변경하면 안 되는 이유는 무엇인가?
7. Disk 신원 확인, 변경 승인, 변경 후 Filesystem 확인은 무엇이 다른가?
8. ETCD Disk를 일반 Node와 별도로 보는 이유는 무엇인가?
9. VIP-A와 VIP-B는 각각 어떤 요청을 어디로 전달하는가?
10. VIP-B HTTP 성공이 HTTPS 성공까지 증명하지 못하는 이유는 무엇인가?
11. Kubernetes 설치 전에 VIP-A에서 확인할 수 있는 범위는 어디까지인가?
12. Bastion 단계에 어떤 값과 근거를 넘겨야 하는가?
