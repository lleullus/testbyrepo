# 05.1.1.6 Deploying Custom Role Base (Workspace)

> **실행자**: DSPAAS
>
> **원문 기준**: 기존 Host cluster 설치 절차의 `6) Custom Roles for Kubesphere Host` / `Deploying Custom Role Base (Workspace)` 를 Xi'an 문서 형식으로 재구성

KubeSphere는 기본 RBAC role을 제공하지만, 운영에 그대로 쓰기에는 제약이 큽니다. 그래서 DKS는 Kubernetes 일반 `Role` 보다 상위 권한 모델을 담은 KubeSphere `RoleBase` CRD로 Workspace 역할 기반을 배포합니다.

이 단계의 목적은 Host cluster에 아래 4개 Workspace RoleBase를 적용하고, 변경 사항을 반영하기 위해 `ks-apiserver` / `ks-controller-manager` 를 재기동하는 것입니다.

| RoleBase 이름 | WorkspaceRole name | 용도 |
|---------------|--------------------|------|
| `workspace-viewer` | `viewer` | 조회 중심 |
| `workspace-self-provisioner` | `self-provisioner` | self-provisioner |
| `workspace-regular` | `regular` | regular |
| `workspace-admin` | `admin` | workspace 관리 권한 |

> [!summary] 한 줄 요약
> KubeSphere Workspace 권한 템플릿(`RoleBase`) 4종을 Host에 적용하고, IAM 반영을 위해 control plane Deployment를 rollout restart 한다.

## 지금 해야 할 일

1. Host cluster용 KubeSphere 설치 디렉토리로 이동한다.
2. `workspace-*.yaml` 4개 파일이 있는지 확인한다.
3. 4개 RoleBase manifest를 순서대로 apply 한다.
4. `rolebase.iam.kubesphere.io` 리소스가 생성/갱신됐는지 확인한다.
5. `ks-apiserver`, `ks-controller-manager` 를 rollout restart 한다.
6. 재기동 후 pod가 Ready인지 확인한다.

## 사전 확인

- [[05.1.1 Apply kubesphere-installer|05.1.1]] ~ [[05.1.1.4 Re-deployment of Pods according to the DKS Standard|05.1.1.4]] 가 끝난 Host cluster
- `kubectl` context가 Xi'an Host cluster를 가리킴
- 작업 디렉토리: `~/SCS_DKS_Kubernetes_Stack-v1.0/Kubesphere-v3.2.1/host`
- 아래 파일이 존재함

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/Kubesphere-v3.2.1/host
ls workspace-*.yaml
```

예상 출력:

```text
workspace-admin.yaml
workspace-regular.yaml
workspace-self-provisioner.yaml
workspace-viewer.yaml
```

> [!note] Xi'an 기준
> 원본 운영 호스트명은 사이트마다 다르다. Xi'an Host Bastion 예시는 `xadksbthm01` 이며, 설치 bundle 경로는 `SCS_DKS_Kubernetes_Stack-v1.0/Kubesphere-v3.2.1/host` 를 사용한다. RoleBase 내용은 DKS 표준 YAML 그대로 적용한다.

## 배경

### 왜 RoleBase 인가

- KubeSphere 기본 role만으로 운영 요구를 맞추기 어렵다.
- DKS는 Workspace 단위 커스텀 권한 기반이 필요하다.
- `RoleBase` 는 KubeSphere IAM이 사용하는 상위 권한 정의이며, 단순 Kubernetes `Role` 보다 넓은 Workspace 권한 모델을 담는다.

### 적용 대상 API

```text
apiVersion: iam.kubesphere.io/v1alpha2
kind: RoleBase
```

내부 `role` 필드는 `WorkspaceRole` (`iam.kubesphere.io/v1alpha2`) 정의를 포함한다.

## 1. Workspace Viewer RoleBase

파일: `workspace-viewer.yaml`

```yaml
apiVersion: iam.kubesphere.io/v1alpha2
kind: RoleBase
metadata:
  name: workspace-viewer
role:
  apiVersion: iam.kubesphere.io/v1alpha2
  kind: WorkspaceRole
  metadata:
    annotations:
      iam.kubesphere.io/aggregation-roles: '["role-template-view-app-templates","role-template-view-app-repos"]'
      kubesphere.io/creator: system
    name: viewer
  rules:
  - apiGroups:
    - openpitrix.io
    resources:
    - repos
    - repos/events
    verbs:
    - get
    - list
    - watch
  - apiGroups:
    - openpitrix.io
    resources:
    - '*'
    verbs:
    - get
    - list
    - watch
  - apiGroups:
    - '*'
    resources:
    - workspaces
    verbs:
    - get
  - apiGroups:
    - monitoring.kubesphere.io
    - metering.kubesphere.io
    - monitoring.coreos.com
    resources:
    - namespaces
    - workloads
    verbs:
    - get
    - list
  - apiGroups:
    - '*'
    resources:
    - namespaces
    verbs:
    - watch
  - apiGroups:
    - iam.kubesphere.io
    resources:
    - workspacemembers
    verbs:
    - list
```

## 5. Manifest 적용

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/Kubesphere-v3.2.1/host

kubectl apply -f workspace-viewer.yaml
kubectl apply -f workspace-self-provisioner.yaml
kubectl apply -f workspace-regular.yaml
kubectl apply -f workspace-admin.yaml
```

예상 결과:

```text
rolebase.iam.kubesphere.io/workspace-viewer configured
rolebase.iam.kubesphere.io/workspace-self-provisioner configured
rolebase.iam.kubesphere.io/workspace-regular configured
rolebase.iam.kubesphere.io/workspace-admin configured
```

이미 존재하면 `configured`, 최초 적용이면 `created` 가 나올 수 있다. 둘 다 정상이다.

## 7. ks-apiserver / ks-controller-manager 재기동

RoleBase 변경을 KubeSphere IAM control plane에 반영하기 위해 아래 Deployment를 rollout restart 한다.

```bash
kubectl get deploy -n kubesphere-system

kubectl rollout restart deployment ks-apiserver -n kubesphere-system
kubectl rollout restart deployment ks-controller-manager -n kubesphere-system

kubectl rollout status deployment/ks-apiserver -n kubesphere-system
kubectl rollout status deployment/ks-controller-manager -n kubesphere-system
```

재기동 전 예시:

```text
NAME                    READY   UP-TO-DATE   AVAILABLE   AGE
ks-apiserver            3/3     3            3           11d
ks-console              3/3     3            3           11d
ks-controller-manager   3/3     3            3           11d
```

검증:

```bash
kubectl get pod -n kubesphere-system -l app=ks-apiserver -o wide
kubectl get pod -n kubesphere-system -l app=ks-controller-manager -o wide
```

모든 pod가 `Running` / Ready 인지 확인한다.

> [!tip]
> Xi'an Host cluster에서는 이전 단계에서 `ks-apiserver` / `ks-controller-manager` 를 `infra` 노드로 재배치한 상태여야 한다. restart 후에도 `infra` 노드에 올라오는지 함께 확인한다.

- [ ] `ks-apiserver` rollout 완료
- [ ] `ks-controller-manager` rollout 완료

## 운영 메모

| 항목 | 내용 |
|------|------|
| 적용 시점 | Host KubeSphere 설치·재배치 이후, Custom Role 기반 배포 단계 |
| 재적용 | YAML 수정 후 동일 `kubectl apply -f` 로 재적용 가능 |
| 필수 후속 | apply 후 `ks-apiserver`, `ks-controller-manager` restart |
| UI 확인 | KubeSphere Console Workspace Role 목록에 커스텀 역할이 보이는지 확인 |
| 권한 변경 | 문서/원본 YAML 기준으로만 변경. 현장 임의 확장 금지 |

> [!note]
> `viewer` / `self-provisioner` / `regular` 의 rule 본문이 동일하게 보이는 것은 원본 DKS RoleBase 정의 기준이다. 역할 차이는 주로 `metadata.name` 과 상위 aggregation template 사용 맥락에서 구분된다. `admin` 만 aggregation-roles 와 rules 범위가 명확히 넓다.
