# 05.1.1.4 Re-deployment of Pods according to the DKS Standard

> **실행자**: DSPAAS
>
> **원문 기준**: 기존 Host cluster 설치 절차의 `4)` 및 `4-1)` 로그/명령, Ingress 배포, AD-Join(LDAP) 설정을 Xi'an 문서 형식으로 재구성

KubeSphere `v3.2.1` 설치 후 생성된 workload는 `kubesphere-installer.yaml` 의 `nodeSelector`/`tolerations` 가 자동 전파되지 않을 수 있습니다. 따라서 설치 직후 관련 pod가 일단 모두 `Running` 상태가 되었더라도, DKS 표준에 맞게 namespace별 목적 노드로 한 번 더 재배치해야 합니다. 재배치 이후에는 Console/Prometheus/Alertmanager Ingress를 배포하고, `kubesphere-config` 에 AD-Join(LDAP) 설정을 반영합니다.

> [!warning] Xi'an 배치 정책
> 원본 DKS 운영 로그는 `monitoring` 계열을 `infra`, `controls/devops/kubesphere-system` 계열을 `system` 노드로 재배치합니다. Xi'an Host cluster에는 `system` 노드 타입이 없으므로, 관련 namespace workload를 모두 `infra` 노드로 재배치합니다.

## 지금 해야 할 일

1. KubeSphere 관련 namespace pod가 모두 `Running` 또는 `Completed` 인지 확인합니다.
2. `monitoring`, `controls`, `devops`, `kubesphere-system` 계열을 모두 `infra` 로 보냅니다.
3. `ks-installer` Deployment replica를 `0`으로 줄여 재실행을 막습니다.
4. 재배치 후 pod가 `infra` 노드 풀에 올라왔는지 확인합니다.
5. `ks-console` / `prometheus` / `alertmanager` Ingress를 배포하고 host 도메인을 환경에 맞게 수정합니다.
6. `kubesphere-config` 에 LDAP identity provider를 추가한 뒤 `ks-apiserver` 를 rollout restart 합니다.

## 1. 대상 노드 역할 확인

```bash
kubectl get nodes --show-labels | egrep 'node-type=|node-role.kubernetes.io/'
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

운영 해석:

- 재배치 대상은 모두 `node-type=infra`, `node-role.kubernetes.io/infra:NoSchedule`
- Xi'an Host cluster 기준 `system` 노드 타입은 사용하지 않음

## 적용 대상

| Namespace | 리소스 | 대상 노드 | 비고 |
|-----------|--------|-----------|------|
| `kubesphere-monitoring-system` | `alertmanager/main`, `prometheus/k8s`, `prometheus-operator`, `kube-state-metrics`, `notification-manager`, `notification-manager-operator` | `infra` | 원본과 동일 |
| `kubesphere-controls-system` | `default-http-backend`, `kubectl-admin` | `infra` | 원본 `system` → Xi'an `infra` |
| `kubesphere-devops-system` | `devops-apiserver`, `devops-controller`, `devops-jenkins`, `s2ioperator`, `devops` CronJob | `infra` | Job `Pending` 시 CronJob toleration 추가 |
| `kubesphere-system` | `ks-apiserver`, `ks-console`, `ks-controller-manager`, `minio`, `tower`, `redis-ha-haproxy`, `openldap`, `redis-ha-server` | `infra` | 존재하는 리소스만 patch |

> [!note]
> 현재 Xi'an 기본 `cluster-configure.yaml` 에서는 `common.redis.enabled: false`, `common.openldap.enabled: false` 입니다. 따라서 `redis-ha-*`, `openldap` 가 실제로 없을 수 있으니 존재하는 리소스만 patch 합니다.

## 2. `kubesphere-monitoring-system` 재배치

```bash
kubectl -n kubesphere-monitoring-system patch alertmanager main --type=json -p='[{"op":"add","path":"/spec/nodeSelector","value":{"node-type":"infra","kubernetes.io/os":"linux"}}]'
kubectl -n kubesphere-monitoring-system patch alertmanager main --type=json -p='[{"op":"add","path":"/spec/tolerations/0","value":{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}}]'
kubectl -n kubesphere-monitoring-system patch prometheus k8s --type=json -p='[{"op":"add","path":"/spec/nodeSelector","value":{"node-type":"infra","kubernetes.io/os":"linux"}}]'
kubectl -n kubesphere-monitoring-system patch prometheus k8s --type=json -p='[{"op":"add","path":"/spec/tolerations/0","value":{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}}]'
kubectl -n kubesphere-monitoring-system patch deployment prometheus-operator --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
kubectl -n kubesphere-monitoring-system patch deployment kube-state-metrics --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
kubectl -n kubesphere-monitoring-system patch notificationmanagers notification-manager --type=json -p='[{"op":"add","path":"/spec/nodeSelector","value":{"node-type":"infra","kubernetes.io/os":"linux"}}]'
kubectl -n kubesphere-monitoring-system patch notificationmanagers notification-manager --type=json -p='[{"op":"add","path":"/spec/tolerations/0","value":{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}}]'
kubectl -n kubesphere-monitoring-system patch deployment notification-manager-operator --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
```

검증:

```bash
kubectl -n kubesphere-monitoring-system get pod -o wide
```

## 3. `kubesphere-controls-system` 재배치

```bash
kubectl -n kubesphere-controls-system patch deployment default-http-backend --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
kubectl -n kubesphere-controls-system patch deployment kubectl-admin --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
kubectl -n kubesphere-controls-system get pod -o wide
```

## 4. `kubesphere-devops-system` 재배치

```bash
for deploy in devops-apiserver devops-controller devops-jenkins; do
  kubectl -n kubesphere-devops-system patch deployment "$deploy" --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
done
kubectl -n kubesphere-devops-system patch sts s2ioperator --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
```

### 4-1. `devops` CronJob 이 `Pending` 인 경우

```bash
kubectl -n kubesphere-devops-system patch cronjob devops --type merge -p '{"spec":{"jobTemplate":{"spec":{"template":{"spec":{"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}}}'
```

> [!note]
> 원문 운영 로그에도 `devops` CronJob 이 기존 실행 Job 때문에 `Pending` 또는 `JobAlreadyActive` 상태로 남는 사례가 있었으므로, `kubectl describe cronjob devops -n kubesphere-devops-system` 으로 상태를 함께 확인합니다.

## 5. `ks-installer` 중지

> [!danger]
> `ks-installer` 를 다시 실행하면 일부 설정이 공장 초기값 방향으로 되돌아갈 수 있으므로, 설치 완료 후에는 replica를 `0`으로 유지합니다.

```bash
kubectl scale -n kubesphere-system deployment ks-installer --replicas=0
```

## 6. `kubesphere-system` 재배치

### 6-1. Deployment patch

```bash
for deploy in ks-apiserver ks-console ks-controller-manager minio tower redis-ha-haproxy; do
  kubectl -n kubesphere-system patch deployment "$deploy" --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
done
```

### 6-2. StatefulSet patch

```bash
for sts in openldap redis-ha-server; do
  kubectl -n kubesphere-system get sts "$sts" >/dev/null 2>&1 || continue
  kubectl -n kubesphere-system patch sts "$sts" --type merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux","node-type":"infra"},"tolerations":[{"key":"node-role.kubernetes.io/infra","effect":"NoSchedule"}]}}}}'
done
```

## 7. 적용 후 검증

```bash
kubectl -n kubesphere-monitoring-system get pod -o wide
kubectl -n kubesphere-controls-system get pod -o wide
kubectl -n kubesphere-devops-system get pod -o wide
kubectl -n kubesphere-system get pod -o wide
kubectl -n kubesphere-system get deploy,sts -o yaml | egrep 'name: |node-type:|node-role.kubernetes.io/'
kubectl -n kubesphere-devops-system get cronjob devops -o yaml | grep -A5 tolerations
kubectl get events -A --sort-by=.lastTimestamp | egrep 'kubesphere|prometheus|alert|devops'
```

검증 기준:

- `kubesphere-monitoring-system`, `kubesphere-controls-system`, `kubesphere-devops-system`, `kubesphere-system` pod 가 모두 `infra` node 에 올라옴
- patch 대상 workload 의 pod spec 에 `nodeSelector` / `tolerations` 반영됨
- `ks-installer` replica 가 `0` 으로 유지됨
- `devops-*` job pod 가 `Pending` 없이 완료 또는 재생성됨

## 8. 운영 메모

- 동일한 `KubeSphere v3.2.1` 이더라도 설치 직후 상태는 환경별로 다를 수 있습니다.
- 이 단계의 핵심은 `파드가 떴다` 에서 끝내지 않고 `의도한 노드 풀에 올라갔는지` 까지 맞추는 것입니다.
- Xi'an Host cluster는 원본의 `system` 배치를 쓰지 않고, 관련 KubeSphere workload를 모두 `infra` 로 재배치합니다.
- `rt3` 에서 registry/DNS 우회 조치를 했다면, 재배치 중 새 pod pull 시 같은 문제가 재발하지 않는지도 함께 확인합니다.

## 9. Ingress 배포 (Console / Prometheus / Alertmanager)

> [!note] Cluster Domain
> Ingress `host` 값은 환경의 Cluster Domain에 맞게 수정해야 합니다. 아래 예시는 `*.apps.tmtest.cloud.samsungds.net` 기준입니다. Xi'an 환경이면 해당 사이트 도메인으로 교체합니다.
>
> 원문 제목에는 Grafana도 포함되어 있으나, 제공된 `ks-ingress.yaml` 에는 Grafana Ingress가 없습니다. Grafana UI 노출이 필요하면 별도 Ingress를 추가합니다.

### 9-1. `ks-ingress.yaml` 작성

```yaml
############### Deploy Ingress for Kubesphere dashboard, Prometheus UI, Grafana & Alertamanger Web UIs ###########
### Note: Need to edit the Cluster Domain accordingly #####
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  labels:
    k8s-app: ks-console-ingress
  name: ks-console-ingress
  namespace: kubesphere-system
  annotations:
    kubernetes.io/ingress.class: nginx
spec:
  rules:
    - host: ks-console.apps.tmtest.cloud.samsungds.net
      http:
        paths:
          - pathType: Prefix
            path: /
            backend:
              service:
                name: ks-console
                port:
                  number: 80
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: alertmanager-main-ingress
  namespace: kubesphere-monitoring-system
  annotations:
    kubernetes.io/ingress.class: "nginx"
spec:
  rules:
    - host: alertmanager.apps.tmtest.cloud.samsungds.net
      http:
        paths:
          - pathType: Prefix
            path: /
            backend:
              service:
                name: alertmanager-main
                port:
                  number: 9093
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: prometheus-ingress
  namespace: kubesphere-monitoring-system
  annotations:
    kubernetes.io/ingress.class: "nginx"
spec:
  rules:
    - host: prometheus.apps.tmtest.cloud.samsungds.net
      http:
        paths:
          - pathType: Prefix
            path: /
            backend:
              service:
                name: prometheus-k8s
                port:
                  number: 9090
```

### 9-2. 적용 및 확인

```bash
kubectl apply -f ks-ingress.yaml
kubectl get ing -n kubesphere-system
kubectl get ing -n kubesphere-monitoring-system
```

예상 결과 예시:

```text
NAME                  CLASS    HOSTS                                         ADDRESS   PORTS   AGE
ks-console-ingress    <none>   ks-console.apps.tmtest.cloud.samsungds.net              80      11s

NAME                        CLASS    HOSTS                                            ADDRESS   PORTS   AGE
alertmanager-main-ingress   <none>   alertmanager.apps.tmtest.cloud.samsungds.net              80      15s
prometheus-ingress          <none>   prometheus.apps.tmtest.cloud.samsungds.net                80      15s
```

| Ingress | Namespace | Service | Port | Host 예시 |
|---------|-----------|---------|------|-----------|
| `ks-console-ingress` | `kubesphere-system` | `ks-console` | `80` | `ks-console.apps.<cluster-domain>` |
| `alertmanager-main-ingress` | `kubesphere-monitoring-system` | `alertmanager-main` | `9093` | `alertmanager.apps.<cluster-domain>` |
| `prometheus-ingress` | `kubesphere-monitoring-system` | `prometheus-k8s` | `9090` | `prometheus.apps.<cluster-domain>` |

검증 기준:

- 3개 Ingress 가 생성되고 `HOSTS` 가 의도한 도메인과 일치함
- nginx Ingress Controller 가 트래픽을 받을 수 있는 상태임
- 브라우저 또는 curl 로 Console / Prometheus / Alertmanager UI 접속 가능

## 10. AD-Join (LDAP) — `kubesphere-config` 수정

KubeSphere 로그인에 AD/LDAP identity provider를 연결하려면 `kubesphere-system` 의 `kubesphere-config` ConfigMap 을 수정한 뒤 `ks-apiserver` 를 재기동합니다.

> [!note] Xi'an 적용 값
> 아래 값은 **Xi'an Host cluster AD-Join** 기준입니다. 로컬 `admin` 계정은 보통 그대로 사용 가능하고, LDAP는 추가 로그인 수단입니다.

### 10-0. 사전 확인 (권장)

LDAP 서버 포트가 bastion / 클러스터에서 열려 있는지 먼저 확인합니다. 여기가 막히면 로그인 시 **504 Gateway Timeout** 이 날 수 있습니다.

```bash
# 후보 LDAP 서버 (우선순위대로 확인)
for h in 109.150.175.95 109.150.175.96 109.150.175.97 109.150.175.98; do
  echo "=== $h:389 ==="
  nc -vz -w 3 "$h" 389 || true
done
```

| 역할 | 주소 |
|------|------|
| Primary (ConfigMap `host`에 넣을 값) | `109.150.175.95:389` |
| Standby 후보 | `109.150.175.96:389`, `109.150.175.97:389`, `109.150.175.98:389` |

> [!warning] host 필드
> KubeSphere `LDAPIdentityProvider` 의 `provider.host` 는 보통 **단일** `IP:PORT` 만 받습니다. 여러 대를 한 줄에 괄호로 나열하지 말고, 우선 통과한 서버 1대를 `host` 에 넣습니다. Primary 장애 시 standby IP로 바꾼 뒤 `ks-apiserver` 를 다시 restart 합니다.

### 10-1. ConfigMap 편집

```bash
kubectl edit cm -n kubesphere-system kubesphere-config
```

`data.kubesphere.yaml` 의 `authentication` 블록을 아래처럼 맞춥니다.

- 기존 `jwtSecret`, `kubectlImage` 는 **지우지 말고 유지**
- `oauthOptions` 아래에 `identityProviders` 를 추가/수정
- 원문에 `mailSttribute` 로 적힌 경우 → 키 이름은 **`mailAttribute`**

```yaml
authentication:
  authenticateRateLimiterDuration: 10m0s
  authenticateRateLimiterMaxTries: 10
  jwtSecret: <existing-jwtSecret>   # 기존 값 유지
  kubectlImage: <env-registry>/dspaas-cloud/kubesphere/kubectl:v1.22.0  # 기존 값 유지
  loginHistoryRetentionPeriod: 168h
  maximumClockSkew: 10s
  multipleLogin: true
  oauthOptions:
    accessTokenInactivityTimeout: 30m
    accessTokenMaxAge: 1h
    clients:
      - name: kubesphere
        redirectURIs:
          - '*'
        secret: kubesphere
    identityProviders:
      - mappingMethod: auto
        name: ldap
        provider:
          host: 109.150.175.95:389
          loginAttribute: cn
          mailAttribute: mail
          managerDN: cn=scstdksldap.srv,ou=Shared,ou=Users,ou=SCS,ou=Locations,dc=samsungds,dc=net
          managerPassword: K8s@dmin!
          userSearchBase: ou=Locations,dc=samsungds,dc=net
          userSearchFilter: (&(objectclass=user)(memberOf=CN=SG1599,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net))
        type: LDAPIdentityProvider
```

저장 후 에디터 종료 (`:wq`).

### 10-2. Xi'an LDAP 값 요약

| 항목 | Xi'an 값 |
|------|----------|
| host (primary) | `109.150.175.95:389` |
| host (standby) | `109.150.175.96:389` / `97:389` / `98:389` |
| loginAttribute | `cn` |
| mailAttribute | `mail` (`mailSttribute` 오타 주의) |
| managerDN | `cn=scstdksldap.srv,ou=Shared,ou=Users,ou=SCS,ou=Locations,dc=samsungds,dc=net` |
| managerPassword | `K8s@dmin!` |
| userSearchBase | `ou=Locations,dc=samsungds,dc=net` |
| userSearchFilter | `(&(objectclass=user)(memberOf=CN=SG1599,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net))` |
| type | `LDAPIdentityProvider` |
| mappingMethod | `auto` |

### 10-3. 반영 확인 (restart 전)

```bash
kubectl get cm -n kubesphere-system kubesphere-config -o yaml | egrep 'identityProviders|LDAPIdentityProvider|host:|managerDN|userSearchBase|userSearchFilter|mailAttribute|mailSttribute'
```

확인할 것:

- `host: 109.150.175.95:389` (또는 선택한 standby)
- `managerDN` 에 `scstdksldap.srv` / `ou=SCS` 포함
- 키 이름이 `mailAttribute` (오타 `mailSttribute` 아님)
- `type: LDAPIdentityProvider`

### 10-4. `ks-apiserver` rollout restart

```bash
kubectl rollout restart -n kubesphere-system deploy ks-apiserver
kubectl rollout status -n kubesphere-system deploy ks-apiserver
kubectl get pods -n kubesphere-system | grep ks-api
```

예상:

```text
ks-apiserver-xxxxx   1/1     Running   0          14s
ks-apiserver-xxxxx   1/1     Running   0          11s
ks-apiserver-xxxxx   1/1     Running   0          9s
```

### 10-5. 로그인 검증

1. Console 접속 (Ingress host)
2. **로컬 계정** 스모크: `admin` / `P@88w0rd` (환경 비밀번호)
3. **LDAP 계정** (`cn` + SG1599 그룹 멤버) 로그인
4. 그룹 밖 계정은 실패해야 정상

```bash
# 로그인 시도 직후
kubectl -n kubesphere-system logs -l app=ks-apiserver --tail=100 | egrep -i 'ldap|auth|login|timeout|error|fail'
```

| 증상 | 조치 |
|------|------|
| 로그인 504 / 장시간 무응답 | LDAP `host:389` 네트워크 재확인, standby IP로 교체 후 restart |
| invalid username/password | `loginAttribute`/`userSearchFilter`/그룹 멤버십 확인 |
| 로컬 admin 도 504 | `ks-apiserver` Ready/로그 확인, LDAP hang 여부 점검 |
| Config 반영 안 됨 | YAML 들여쓰기/`kubesphere.yaml` 키 위치 재확인 후 restart |

### 10-6. 운영 주의

- `ks-installer` replica 가 `0` 인지 확인 (installer 재기동 시 ConfigMap 덮어쓸 수 있음)
```bash
kubectl -n kubesphere-system get deploy ks-installer
```
- Primary LDAP 장애 시: `host` 를 `109.150.175.96:389` 등으로 바꾼 뒤 `ks-apiserver` restart
- `managerPassword`, `jwtSecret` 은 시크릿 관리 체계에 따라 취급

> [!danger] 보안
> `managerPassword`, `jwtSecret` 평문 장기 보관을 피하고, 사이트 시크릿 관리 체계를 따릅니다.
