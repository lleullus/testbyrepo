# 05.1.1.10 Apply Custom Alertmanager Config

> **실행자**: DSPAAS
>
> **원문 기준**: 기존 Host cluster 설치 절차의 `10) Apply Custom Alertmanager Config` 를 Xi'an 문서 형식으로 재구성

이 단계는 Prometheus 알림 **내용**을 만드는 단계가 아니다.  
Alertmanager 가 알림을 **어디로 보낼지** 적어 둔 설정 Secret 을 적용하는 단계다.

> [!summary] 한 줄 요약
> DKS 커스텀 webhook(`alertfunction`) 으로 알림을 넘기도록 만든 `alertmanager-secret.yaml` 을  
> `kubesphere-monitoring-system` 에 apply 한다.

## 0. 원문이 말하는 것 (의미부터)

원문 흐름을 풀면 아래와 같다.

| 원문 | 의미 |
|------|------|
| DKS uses a custom Webhook known as `alertfunction` | DKS 전용 알림 중계 서비스 이름이 `alertfunction` |
| It receive alerts from alertmanager and passes that to the Internal Chat System's API | Alertmanager → `alertfunction` → 사내 채팅 API |
| Currently, it is not applicable to the Taylor environment as there is no such internal chat notification system | Taylor 당시에는 사내 채팅 연동이 없어 **실제 통지는 안 됨** |
| However, as it will be considered later, alertmanager configuration ... will be applied beforehand | 나중에 채팅 연동할 수 있으니 **Alertmanager 쪽 설정은 미리 넣어 둔다** |
| `k apply -f alertmanager-secret.yaml` → `secret/alertmanager-main configured` | 그 설정이 들어 있는 Secret 을 클러스터에 적용 |

### 그림으로 보면

```text
Prometheus (rule firing)
    ↓
Alertmanager
    ↓  (이 단계가 설정하는 부분)
alertfunction  webhook  ← DKS 커스텀
    ↓
사내 Chat System API   ← 환경에 없으면 실제 메시지는 안 감
```

### 헷갈리기 쉬운 점

- **지금 당장 채팅이 와야 성공** 이 아니다.  
  원문도 “Taylor 에는 채팅 시스템이 없어서 해당 없음. 그래도 설정은 미리 적용” 이다.
- Xi'an 에 사내 채팅/`alertfunction` 엔드포인트가 아직 없으면:
  - Secret apply 자체는 할 수 있음 (원문과 동일 정책)
  - **실제 채팅 통지는 안 될 수 있음**
  - webhook URL·인증값이 잘못된 채 적용하면 Alertmanager 가 webhook 전송 실패 로그를 남길 수 있음 → apply 전 Secret 내용 확인 필요

> [!note] Xi'an 적용 판단
> - bundle 에 `alertmanager-secret.yaml` 이 있고, 운영 표준이 “미리 적용” 이면 **이 단계 수행**
> - webhook 대상이 아직 없고, 실패 로그가 부담이면 **파일 내용 확인 후 적용 여부 결정** (담당/표준에 따름)
> - 원문 기본 입장은 **beforehand apply**

## 1. 지금 해야 할 일

1. DKS prometheus stack 디렉토리로 이동한다.
2. `alertmanager-secret.yaml` 이 있는지 본다.
3. Secret 이 올라갈 namespace 가 `kubesphere-monitoring-system` 인지 확인한다.
4. `kubectl apply -f alertmanager-secret.yaml` 한다.
5. Secret / Alertmanager 상태를 확인한다.

## 2. 작업 경로 (Xi'an)

원문(Taylor) 경로:

```text
/app/dspaas/Taylor_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/2.kube-prometheus-0.11.0/manifests
```

Xi'an 은 설치 bundle 루트가 `SCS_DKS_Kubernetes_Stack-v1.0` 이다.  
동일 상대 경로를 쓴다:

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/2.kube-prometheus-0.11.0/manifests
pwd
ls alertmanager-secret.yaml
```

경로가 조금 다르면 찾는다:

```bash
find ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0 -name 'alertmanager-secret.yaml' 2>/dev/null
```

파일이 없으면 이 단계를 진행할 수 없다. bundle 버전/구성 확인이 먼저다.

## 3. 적용 전 확인

### 3-1. namespace 검증 (원문 강조)

원문이 굳이 `grep namespace` 한 이유:  
Secret 이 **다른 ns** 로 들어가면 Alertmanager 가 설정을 안 읽는다.

```bash
grep -n namespace alertmanager-secret.yaml
```

기대:

```text
namespace: kubesphere-monitoring-system
```

KubeSphere 기본 Alertmanager 가 이 ns 에 있다.

### 3-2. 무엇을 덮어쓰는지

```bash
# 현재 Secret 존재 여부
kubectl get secret alertmanager-main -n kubesphere-monitoring-system

# 파일 상단 구조 확인 (민감정보 주의)
head -50 alertmanager-secret.yaml
```

| 항목 | 내용 |
|------|------|
| 리소스 | `Secret` |
| 이름 | 보통 `alertmanager-main` |
| Namespace | `kubesphere-monitoring-system` |
| 역할 | Alertmanager 설정(`alertmanager.yaml` 등) 저장 |
| apply 결과 예 | `secret/alertmanager-main configured` |

> [!warning]
> Secret 안에는 webhook URL, 라우팅 트리 등이 들어 있을 수 있다.  
> 로그/블로그/티켓에 **전체 내용 붙여넣지 않는다.**  
> 확인은 `namespace`, `metadata.name`, receiver 이름 존재 여부 정도만.

### 3-3. (권장) receiver 에 alertfunction 이 보이는지

민감값 제외하고 key/구조만:

```bash
# Secret manifest 가 stringData/data 인 경우 키가 다름
grep -nE 'alertfunction|webhook_configs|receiver|route:' alertmanager-secret.yaml | head -40
```

- `alertfunction` / webhook 관련 키가 보이면 원문 의도와 맞는 파일
- 아무 것도 없으면 잘못된 파일이거나 다른 버전

### 3-4. Alertmanager 가 이미 떠 있는지

```bash
kubectl get alertmanager -n kubesphere-monitoring-system
kubectl get pod -n kubesphere-monitoring-system -l app.kubernetes.io/name=alertmanager
```

## 4. 적용

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/2.kube-prometheus-0.11.0/manifests

kubectl apply -f alertmanager-secret.yaml
```

성공 예 (원문과 동일 형태):

```text
secret/alertmanager-main configured
```

최초면 `created`, 재적용이면 `configured` / `unchanged`.

## 5. 적용 후 확인

### 5-1. Secret

```bash
kubectl get secret alertmanager-main -n kubesphere-monitoring-system
kubectl get secret alertmanager-main -n kubesphere-monitoring-system -o yaml | grep -E 'name:|namespace:|type:' | head
```

### 5-2. Alertmanager 가 Secret 을 다시 읽었는지

operator/Alertmanager 가 reload 한다. pod 상태 확인:

```bash
kubectl get pod -n kubesphere-monitoring-system -l app.kubernetes.io/name=alertmanager -o wide
kubectl logs -n kubesphere-monitoring-system -l app.kubernetes.io/name=alertmanager --tail=50
```

- pod Ready
- 설정 파싱 에러가 반복되지 않음

### 5-3. (선택) 설정 반영 여부

```bash
kubectl -n kubesphere-monitoring-system port-forward svc/alertmanager-main 9093:9093
# 브라우저: http://127.0.0.1:9093/#/status  또는 /#/config
```

Status/Config 에 적용한 route·receiver 가 보이는지 본다.  
사내 채팅이 없어도 **설정이 로드된 것** 과 **메시지가 전송되는 것** 은 별개다.

## 6. 완료 기준

- [ ] `alertmanager-secret.yaml` 경로 확인
- [ ] `namespace: kubesphere-monitoring-system`
- [ ] `kubectl apply` 성공 (`created` / `configured`)
- [ ] `secret/alertmanager-main` 존재
- [ ] Alertmanager pod Ready
- [ ] (해당 시) 설정 로드 에러 없음

## 7. 자주 하는 실수

| 실수 | 결과 | 방지 |
|------|------|------|
| 다른 namespace 로 apply | Alertmanager 가 설정 무시 | apply 전 `grep namespace` |
| KubeSphere host 경로와 혼동 | 파일 못 찾음 | `dks-prometheus-stack_v2.0/.../manifests` |
| 채팅 안 온다고 실패 판정 | 원문도 “미리 적용” | webhook 대상 유무와 분리 판단 |
| Secret 전문 유출 | 보안 사고 | 민감값 로그 금지 |
| Alertmanager 기동 전 apply | 나중에야 반영되거나 혼란 | monitoring stack Ready 후 적용 권장 |

## 8. 운영 메모

| 항목 | 내용 |
|------|------|
| 목적 | Alertmanager → `alertfunction` webhook 경로 설정 선반영 |
| 대상 파일 | `alertmanager-secret.yaml` |
| 대상 Secret | `alertmanager-main` |
| Namespace | `kubesphere-monitoring-system` |
| 선행 | Host monitoring/Alertmanager 기동, (권장) 5.1.1.7~8 |
| 채팅 연동 | 환경에 `alertfunction`/Chat API 가 있어야 실통지 |
| 원문 환경 | Taylor 는 채팅 없음 → 그래도 설정 미리 적용 |
