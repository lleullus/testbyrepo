# 0. Initial VM Setting

## 0-1. Prerequisites

Before building the Xi'an DKS clusters, verify the VM configuration and required load-balancer routing for every DKS node. Confirm the hostname, IP address, operating system, CPU, memory, block disk, and filesystem layout against the approved VM inventory.

| Check target | Check item | Acceptance criteria |
|---|---|---|
| All DKS nodes | Hostname, IP address, operating system, resources, and filesystem layout | Matches the approved VM inventory and role specification |
| ETCD nodes | VM template filesystem purpose | `/var/lib/etcd` is assigned for ETCD data |
| Load Balancer | VIP-A/VIP-B routing to Master and Router nodes | Backend reachability and the applicable protocol check are recorded |
| All nodes | DATA disk and `dspaas` account | Sections 0-2-1 and 0-2-2 are complete |

Run the following checks on every Bastion, Master, ETCD, Router, Infra, and Worker node, then reconcile the results with the inventory.

```bash
hostnamectl
hostname -I
ip addr
cat /etc/os-release
nproc
free -h
lsblk -f
df -hT
findmnt /var/lib/containerd /var/lib/etcd
```

## 0-1-2. Verify VIP-A/B

Verify that each Load Balancer virtual IP routes to the correct backend role:

- VIP-A exposes frontend port `6443` and routes to Master nodes.
- VIP-B exposes frontend port `80` and routes to Router backend port `30080`.
- VIP-B exposes frontend port `443` and routes to Router backend port `30443`.

The `80` to `30080` mapping can be checked with a temporary Python HTTP server on a Router node.

```bash
# On the Router backend used for the HTTP mapping check
python3 -m http.server 30080 --bind 0.0.0.0

# Through the VIP-B frontend port 80
curl -i http://<VIP-B>/
```

`python3 -m http.server` is suitable for the HTTP mapping check only. It does not prove the TLS behavior of the `443` to `30443` mapping. Use an appropriate TLS-capable listener on the Router backend port `30443`, then perform a TLS-aware connection test through VIP-B.

```bash
# Verify the VIP-B TLS frontend
curl -k -i https://<VIP-B>/

# Use an appropriate TLS-aware test when the backend listener is available
openssl s_client -connect <VIP-B>:443
```

VIP-A port `6443` is a Kubernetes API/TLS endpoint. A plain HTTP server or plain HTTP request is not evidence that the API or TLS path works. Use an appropriate TCP/TLS listener or connection test for the `6443` path.

```bash
# TCP reachability check for VIP-A
nc -vz <VIP-A> 6443

# Kubernetes API/TLS health check, when the API endpoint is available
curl -k -i https://<VIP-A>:6443/healthz
```

Record the following five items for each test execution:

- The cluster, VIP address, frontend port, and backend role under test.
- The backend server hostname/IP and listener port used for the check.
- The command and execution time used for the check.
- The observed result for VIP-A `6443` and VIP-B HTTP `80` to `30080`.
- The observed TLS result for VIP-B `443` to `30443`, including any error or alert message.

### 0-2-1. Destructive Disk Procedure

This is a destructive, root-only procedure. It deletes the partition table entries and filesystem signatures on the approved DATA disk, then creates new LVM and XFS structures. Perform it on one confirmed node at a time. The commands intentionally use `/dev/sdb`; do not select that device from its name alone or replace it with another disk without an approved change to the target.

> [!warning] Confirm the target disk and maintenance approval before any destructive command
> Do not run `fdisk /dev/sdb`, `pvcreate`, or `mkfs.xfs` until every gate below is confirmed:
> - The hostname and role match the approved inventory.
> - `/dev/sdb` is the approved DATA disk, and its size and serial match the VM or storage record.
> - The disposition of all existing data on the disk is approved.
> - The current block-device, PV/VG/LV, mount, and `/etc/fstab` state is recorded in the change evidence.
> - The approved maintenance window is active.
> Stop if any item is unknown or inconsistent.

#### 1. Confirm the node and record the current state

Run these commands on the target node before changing the disk. Save the complete output as pre-change evidence; do not rely on a terminal glance or an assumed empty disk.

```bash
hostnamectl --static
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS,UUID,SERIAL
findmnt -rn
cat /etc/fstab
pvs
vgs
lvs -a -o lv_name,vg_name,lv_size,lv_attr,devices
```

Confirm from the recorded output and the approved inventory that `/dev/sdb` is not the source or backing device for `/`, `/app`, `/var/lib/containerd`, `/var/lib/etcd`, or any other data that must be retained. If a filesystem is mounted, a PV/VG/LV already exists, a filesystem signature is present, or the device identity does not match the approved DATA disk, stop and reconcile the state before continuing. Do not add extra `fdisk` delete commands or force options to work around an unexpected state.

The role determines the required size of the second DATA partition and the logical volume that will use it. The root filesystem is not changed by this procedure.

| Role profile | Block disk | `/dev/sdb1` -> `/app` | `/dev/sdb2` -> filesystem | Logical volume on `vg00disk2` |
|---|---:|---:|---:|---|
| Bastion, Master, Infra, Worker | 315 GB | 50 GB | 100 GB | `containerd_lv` -> `/var/lib/containerd` |
| ETCD | 315 GB | 50 GB | 100 GB | `etcd_lv` -> `/var/lib/etcd` |
| Router | 265 GB | 50 GB | 50 GB | `containerd_lv` -> `/var/lib/containerd` |

The ETCD row is an invariant: an ETCD node uses `/var/lib/etcd`, not `/var/lib/containerd`. [[02. K8S Cluster Nodes Pre-setting]] records an unresolved catalog discrepancy for the ETCD filesystem size. If the final approved ETCD mount design is not confirmed, stop before `fdisk`; do not use the catalog's `0 GB` value or the non-ETCD layout as a default.

#### 2. Delete and recreate the DATA partitions

For Bastion, Master, ETCD, Infra, and Worker nodes, use the 315 GB layout below. This interaction creates a 50 GB first partition and a 100 GB second partition.

Enter the following one input at a time inside the `fdisk` prompt. The comments explain the review points and are not input to `fdisk`. If the local `fdisk` displays separate prompts for a command, partition number, or type, answer those prompts separately with the same values; do not guess different values.

```text
# 1. Delete and recreate partitions
fdisk /dev/sdb
d 1
n
(Enter)
(Enter)
+50G
(Enter)
p    # Confirm partition creation
n
(Enter)
(Enter)
+100G
(Enter)
t 1 31
t 2 31
p    # Confirm that the result matches the approved layout
w
```

For Router nodes only, use the same interaction but create a 50 GB second partition. Do not apply the 100 GB second-partition input to a Router node.

```text
# 1. Delete and recreate partitions for a Router
fdisk /dev/sdb
d 1
n
(Enter)
(Enter)
+50G
(Enter)
p    # Confirm partition creation
n
(Enter)
(Enter)
+50G
(Enter)
t 1 31
t 2 31
p    # Confirm that the result matches the approved layout
w
```

The interactive inputs have these meanings:

- `d 1` deletes partition 1 only. It does not approve deletion of any other partition or data.
- Each `(Enter)` accepts the default partition number, first sector, or other default shown by `fdisk`. Do not replace a displayed partition number or first sector with a guessed value.
- `+50G` and `+100G` request the exact partition capacities defined above. The second value is `+50G` for Router and `+100G` for all other role profiles listed above.
- `t 1 31` and `t 2 31` set both partitions to type code `31` (`Linux LVM` in the approved layout).
- `p` prints the pending in-memory partition table. It does not write changes and is the required review point.
- `w` writes the reviewed partition table. Treat it as the commit point for the destructive partition change.
- `q` exits without writing if the review is not correct.

At either `p` review, stop and enter `q` instead of `w` if `fdisk` shows an unexpected partition number, size, type, disk label, existing signature, mounted or in-use device, or any prompt that is not covered by the approved procedure. If `d 1` reports that partition 1 does not exist, or if another existing partition is present, stop and reconcile the disk state; do not improvise additional deletion input. Never confirm a prompt to remove an existing signature unless that specific data loss is covered by the approval.

After `w` returns, allow the kernel to reread the table and verify it before creating PVs:

```bash
udevadm settle
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS
fdisk -l /dev/sdb
```

Acceptance criteria are `/dev/sdb1` with 50 GB and type code `31` (`Linux LVM`), `/dev/sdb2` with 100 GB and type code `31` for the 315 GB profiles, or `/dev/sdb2` with 50 GB and type code `31` for Router. There must be no unexpected partition or mount. Sector numbers may differ because of disk alignment; the role-approved partition number, capacity, and type must not differ. If the result is wrong, stop before `pvcreate`.

#### 3. Create and verify the common LVM and XFS structures

Run the common commands only after the partition acceptance check passes. If `pvcreate` reports an existing signature or an in-use device, if `vgcreate` reports that a volume group already exists, if `mkfs.xfs` reports an existing signature or asks to overwrite data, or if any command requests an unexpected confirmation, stop. Do not use `-f`, `-ff`, or a different device to bypass the condition.

```bash
# 2. Create the common LVM structures
lsblk
pvcreate /dev/sdb1
pvcreate /dev/sdb2
vgcreate vg00disk1 /dev/sdb1
vgcreate vg00disk2 /dev/sdb2
lvcreate -n app_lv -l 100%free vg00disk1

# 3. Create the common filesystem
mkfs.xfs /dev/vg00disk1/app_lv
```

For non-ETCD roles, including Bastion, Master, Router, Infra, and Worker nodes, create the containerd logical volume and filesystem. The `100%free` allocation uses the approved second-partition size: 100 GB for the 315 GB profiles and 50 GB for Router.

```bash
# Non-ETCD roles only
lvcreate -n containerd_lv -l 100%free vg00disk2
mkfs.xfs /dev/vg00disk2/containerd_lv
```

For ETCD nodes, create the ETCD logical volume and filesystem instead:

```bash
# ETCD roles only
lvcreate -n etcd_lv -l 100%free vg00disk2
mkfs.xfs /dev/vg00disk2/etcd_lv
```

The non-ETCD and ETCD branches are mutually exclusive. On an ETCD node, do not create `containerd_lv` at all, and do not create `containerd_lv` followed by `etcd_lv` in the same volume group. On a non-ETCD node, do not substitute `etcd_lv` for `containerd_lv`.

Verify the newly created structures before proceeding to any mount or `/etc/fstab` change:

```bash
lsblk -f
pvs
vgs
lvs -a -o lv_name,vg_name,lv_size,lv_attr,devices
blkid /dev/vg00disk1/app_lv
```

Run exactly one of the following role-specific checks:

```bash
# Non-ETCD roles only
blkid /dev/vg00disk2/containerd_lv
```

```bash
# ETCD roles only
blkid /dev/vg00disk2/etcd_lv
```

The verification must show XFS on `app_lv` and on the selected second LV, the expected role-specific size, and the expected VG/LV names. An ETCD node must show `etcd_lv` and no `containerd_lv`; a non-ETCD node must show `containerd_lv` and no `etcd_lv`. Record the actual UUID returned by `blkid` in the change evidence. Do not invent or copy a UUID into this guide.

This section ends after the LVM and XFS verification. Do not create mount points, run `mount`, or edit `/etc/fstab` here. When the checks pass, continue with the mount-point and `/etc/fstab` persistence procedure in [[02. K8S Cluster Nodes Pre-setting]], using the actual target-node UUID and the role-appropriate path. If any verification fails, stop and do not hand off to the mount procedure.

### 0-2-2. Verify `dspaas` Wheel Membership

Run the membership and sudo checks on every Bastion and DKS cluster node. Verify the account using both `id` and `groups`:

```bash
id dspaas
groups dspaas
```

If `dspaas` is not a member of `wheel`, append the group without replacing the user’s existing supplementary groups:

```bash
usermod -aG wheel dspaas
```

Do not use the destructive `usermod -G wheel dspaas` form. Verify the membership again and confirm passwordless sudo from the `dspaas` account:

```bash
id dspaas
groups dspaas
sudo -n true
```
