## 0-1-2. VIP-A/B Verification

Verify that each Load Balancer virtual IP is routed to the correct backend role.

- VIP-A exposes frontend port `6443` and routes to Master nodes.
- VIP-B exposes frontend port `80` and routes to Router backend port `30080`.
- VIP-B exposes frontend port `443` and routes to Router backend port `30443`.

The mapping from `80` to `30080` can be verified using a temporary Python HTTP server on a Router node.

```bash
# On the Router backend used to verify the HTTP mapping
python3 -m http.server 30080 --bind 0.0.0.0

# Through VIP-B frontend port 80
curl -i http://<VIP-B>/
```

`python3 -m http.server` is suitable only for verifying the HTTP mapping. It does not demonstrate TLS behavior for the mapping from `443` to `30443`. Use an appropriate TLS-capable listener on Router backend port `30443`, then perform a TLS-aware connection test through VIP-B.

```bash
# Verify the VIP-B TLS frontend
curl -k -i https://<VIP-B>/

# Perform an appropriate TLS-aware test when a backend listener is available
openssl s_client -connect <VIP-B>:443
```

VIP-A port `6443` is a Kubernetes API/TLS endpoint. A generic HTTP server or generic HTTP request is not evidence that the API or TLS path works. Use an appropriate TCP/TLS listener or connection test for the `6443` path.

```bash
# Check VIP-A TCP connectivity
nc -vz <VIP-A> 6443

# Check Kubernetes API/TLS status when available
curl -k -i https://<VIP-A>:6443/healthz
```

Record the following five items for each test execution.

- Target cluster, VIP address, frontend port, and backend role tested.
- Backend server hostname/IP and listener port used for verification.
- Command used for verification and execution time.
- Observed results at VIP-A `6443` and the VIP-B HTTP `80` to `30080` mapping.
- Observed TLS results for VIP-B `443` to `30443`, including error or warning messages.

### 0-2-1. Destructive Disk Procedure

This procedure is destructive and requires root privileges. It deletes partition table entries and filesystem signatures on the approved DATA disk, then creates a new LVM and XFS structure. Perform it on one confirmed node at a time. The commands intentionally use `/dev/sdb`. Do not select this device based only on its device name or replace it with another disk without an approved change for the target.

> [!warning] Confirm the target disk and maintenance approval before executing destructive commands
> Do not execute `fdisk /dev/sdb`, `pvcreate`, or `mkfs.xfs` until all the gates below have been confirmed.
> - The hostname and role match the approved inventory.
> - `/dev/sdb` is the approved DATA disk, and its size and serial match the VM or storage records.
> - Handling of existing data on the disk has been approved.
> - The current block device, PV/VG/LV, mount, and `/etc/fstab` state has been recorded in the change evidence.
> - The approved maintenance window is active.
> Stop if any item is unknown or does not match.

#### 1. Verify the node and record the current state

Before changing the disk, run the following commands on the target node. Save the complete output as pre-change evidence. Do not perform only a brief terminal check or assume that the disk is empty.

```bash
hostnamectl --static
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS,UUID,SERIAL
findmnt -rn
cat /etc/fstab
pvs
vgs
lvs -a -o lv_name,vg_name,lv_size,lv_attr,devices
```

From the recorded output and approved inventory, confirm that `/dev/sdb` is not the source or backing device for `/`, `/app`, `/var/lib/containerd`, `/var/lib/etcd`, or any other data that must be preserved. Stop and reconcile the state before continuing if a filesystem is mounted, a PV/VG/LV already exists, a filesystem signature is present, or the device identifier does not match the approved DATA disk. Do not use additional `fdisk` delete commands or force options to bypass an unexpected state.

The required size of the second DATA partition and the logical volume that uses it is determined by role. This procedure does not change the root filesystem.

| Role profile | Block disk | `/dev/sdb1` -> `/app` | `/dev/sdb2` -> filesystem | Logical volume in `vg00disk2` |
|---|---:|---:|---:|---|
| Bastion, Master, Infra, Worker | 315 GB | 50 GB | 100 GB | `containerd_lv` -> `/var/lib/containerd` |
| ETCD | 315 GB | 50 GB | 100 GB | `etcd_lv` -> `/var/lib/etcd` |
| Router | 265 GB | 50 GB | 50 GB | `containerd_lv` -> `/var/lib/containerd` |

The ETCD row is an invariant. ETCD nodes use `/var/lib/etcd`, not `/var/lib/containerd`. [[02. K8S Cluster Nodes Pre-setting]] records an unresolved catalog discrepancy regarding ETCD filesystem size. Stop before `fdisk` if the final approved ETCD mount design has not been confirmed. Do not use the catalog's `0 GB` value or the non-ETCD layout as the default.

#### 2. Delete and recreate the DATA partitions

Use the 315 GB layout below on Bastion, Master, ETCD, Infra, and Worker nodes. This creates a 50 GB first partition and a 100 GB second partition.

Perform the following inputs one at a time within the `fdisk` prompt. Comments explain review points and are not entered into `fdisk`. If local `fdisk` displays separate prompts for the command, partition number, or type, answer each prompt with the same value. Do not guess other values.

```text
# 1. Delete and recreate partitions
fdisk /dev/sdb
d 1
n
(Enter)
(Enter)
+50G
(Enter)
p    # Confirm partition creation
n
(Enter)
(Enter)
+100G
(Enter)
t 1 31
t 2 31
p    # Confirm that the result matches the approved layout
w
```

On Router nodes only, use the same input flow but create a 50 GB second partition. Do not apply the 100 GB second-partition input to Router nodes.

```text
# 1. Delete and recreate Router partitions
fdisk /dev/sdb
d 1
n
(Enter)
(Enter)
+50G
(Enter)
p    # Confirm partition creation
n
(Enter)
(Enter)
+50G
(Enter)
t 1 31
t 2 31
p    # Confirm that the result matches the approved layout
w
```

The interactive inputs mean the following.

- `d 1` deletes only partition 1. It does not authorize deleting other partitions or data.
- Each `(Enter)` accepts the default partition number, first sector, or other default displayed by `fdisk`. Do not replace the displayed partition number or first sector with a guessed value.
- `+50G` and `+100G` request the exact partition capacities defined above. The second value is `+50G` for Router and `+100G` for all other role profiles listed above.
- `t 1 31` and `t 2 31` set both partitions to type code `31` (`Linux LVM`) in the approved layout.
- `p` prints the pending partition table in memory. It does not record changes and is a required review point.
- `w` writes the reviewed partition table. Treat it as the commit point for destructive partition changes.
- `q` exits without writing when the review result is incorrect.

At any `p` review, if `fdisk` displays an unexpected partition number, size, type, disk label, existing signature, mounted or in-use device, or prompt not covered by the approved procedure, enter `q` instead of `w` and stop. Stop and reconcile the disk state if `d 1` reports that partition 1 does not exist or if other existing partitions are present. Do not invent additional deletion inputs. Never confirm a prompt to remove an existing signature unless the specific data loss is within the approved scope.

After `w` returns, wait for the kernel to reread the table and verify it before creating the PV.

```bash
udevadm settle
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS
fdisk -l /dev/sdb
```

The acceptance criteria are `/dev/sdb1` with 50 GB and type code `31` (`Linux LVM`), `/dev/sdb2` with 100 GB and type code `31` for 315 GB profiles, and `/dev/sdb2` with 50 GB and type code `31` for Router. There must be no unexpected partitions or mounts. Sector numbers may vary due to disk alignment, but the partition number, capacity, and type approved for the role must not vary. Stop before `pvcreate` if the result is incorrect.

#### 3. Create and verify the common LVM and XFS structure

Run the common commands only after partition approval has passed. Stop if `pvcreate` reports an existing signature or a device in use, `vgcreate` reports that the volume group already exists, `mkfs.xfs` reports an existing signature or requests data overwrite, or any command requests an unexpected confirmation. Do not use `-f`, `-ff`, or another device to bypass the condition.

```bash
# 2. Create the common LVM structure
lsblk
pvcreate /dev/sdb1
pvcreate /dev/sdb2
vgcreate vg00disk1 /dev/sdb1
vgcreate vg00disk2 /dev/sdb2
lvcreate -n app_lv -l 100%free vg00disk1

# 3. Create the common filesystem
mkfs.xfs /dev/vg00disk1/app_lv
```

Non-ETCD roles include Bastion, Master, Router, Infra, and Worker nodes; these roles create the containerd logical volume and filesystem. The `100%free` allocation uses the approved second-partition size. It is 100 GB for the 315 GB profile and 50 GB for Router.

```bash
# Run only on non-ETCD roles
lvcreate -n containerd_lv -l 100%free vg00disk2
mkfs.xfs /dev/vg00disk2/containerd_lv
```

On ETCD nodes, create the ETCD logical volume and filesystem instead.

```bash
# Run only on ETCD roles
lvcreate -n etcd_lv -l 100%free vg00disk2
mkfs.xfs /dev/vg00disk2/etcd_lv
```

The non-ETCD and ETCD branches are mutually exclusive. On ETCD nodes, do not create `containerd_lv` at all, and do not create `etcd_lv` in the same volume group after creating `containerd_lv`. On non-ETCD nodes, do not use `etcd_lv` instead of `containerd_lv`.

Verify the newly created structure before proceeding with mounts or `/etc/fstab` changes.

```bash
lsblk -f
pvs
vgs
lvs -a -o lv_name,vg_name,lv_size,lv_attr,devices
blkid /dev/vg00disk1/app_lv
```

Run exactly one of the following role-specific checks.

```bash
# Run only on non-ETCD roles
blkid /dev/vg00disk2/containerd_lv
```

```bash
# Run only on ETCD roles
blkid /dev/vg00disk2/etcd_lv
```

The verification result must show XFS on `app_lv` and the selected second LV, with the expected role-specific sizes and VG/LV names. ETCD nodes must show `etcd_lv` and must not show `containerd_lv`; non-ETCD nodes must show `containerd_lv` and must not show `etcd_lv`. Record the actual UUID returned by `blkid` in the change evidence. Do not create or copy a UUID into this guide.

This section ends after LVM and XFS verification. Do not create mount points, run `mount`, or edit `/etc/fstab` here. If the checks pass, continue with the mount-point and `/etc/fstab` persistence procedure in [[02. K8S Cluster Nodes Pre-setting]], using the actual target node UUID and role-appropriate paths. If verification fails, stop and do not hand off to the mount procedure.

### 0-2-2. Confirm `dspaas` wheel group membership

Run group membership and sudo checks on all Bastion and DKS cluster nodes. Use both `id` and `groups` to verify the account.

```bash
id dspaas
groups dspaas
```

If `dspaas` is not a member of `wheel`, add the group without replacing the user's existing supplementary groups.

```bash
usermod -aG wheel dspaas
```

Do not use the destructive `usermod -G wheel dspaas` form. Recheck group membership and verify passwordless sudo from the `dspaas` account.

```bash
id dspaas
groups dspaas
sudo -n true
```
