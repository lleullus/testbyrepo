# 0. 초기 VM 설정

## 0-1. 사전 요구 사항

Xi'an DKS 클러스터를 구축하기 전에 모든 DKS 노드의 VM 구성과 필요한 로드 밸런서 라우팅을 확인한다. 승인된 VM 인벤토리와 대조하여 호스트명, IP 주소, 운영 체제, CPU, 메모리, 블록 디스크 및 파일시스템 레이아웃을 확인한다.

| 확인 대상 | 확인 항목 | 승인 기준 |
|---|---|---|
| 모든 DKS 노드 | 호스트명, IP 주소, 운영 체제, 리소스 및 파일시스템 레이아웃 | 승인된 VM 인벤토리 및 역할 사양과 일치 |
| ETCD 노드 | VM 템플릿 파일시스템 용도 | `/var/lib/etcd`가 ETCD 데이터용으로 할당됨 |
| Load Balancer | Master 및 Router 노드로의 VIP-A/VIP-B 라우팅 | 백엔드 연결 가능 여부와 해당 프로토콜 확인 결과가 기록됨 |
| 모든 노드 | DATA 디스크 및 `dspaas` 계정 | 0-2-1 및 0-2-2 섹션이 완료됨 |

모든 Bastion, Master, ETCD, Router, Infra 및 Worker 노드에서 다음 확인을 실행한 후 결과를 인벤토리와 대조한다.

```bash
hostnamectl
hostname -I
ip addr
cat /etc/os-release
nproc
free -h
lsblk -f
df -hT
findmnt /var/lib/containerd /var/lib/etcd
```

### ETCD 파일시스템 요구 사항

ETCD 노드는 ETCD 데이터에 `/var/lib/etcd`를 사용해야 한다. VM 템플릿이 ETCD 노드에 `/var/lib/containerd`를 할당한 경우 설치 전에 파일시스템 할당을 `/var/lib/etcd`로 변경한다. ETCD 노드에 비-ETCD containerd 레이아웃을 적용하지 않는다.

Load Balancer 가상 서버를 테스트하기 전에 DS Cloud Service Desk에 경고 예외를 요청한다.

```text

```

> [!warning] 테스트 전에 DS Cloud Service Desk에 알림
> 작업을 시작하기 전에 DS Cloud Service Desk에 알린다. 사전 알림 없이 두 번 이상 브로드캐스트가 발생하면 LB 가상 서버가 서비스 중단 감지 대상에서 제외될 수 있다.

## 0-1-2. VIP-A/B 확인

각 Load Balancer 가상 IP가 올바른 백엔드 역할로 라우팅되는지 확인한다.

- VIP-A는 프런트엔드 포트 `6443`을 노출하고 Master 노드로 라우팅한다.
- VIP-B는 프런트엔드 포트 `80`을 노출하고 Router 백엔드 포트 `30080`으로 라우팅한다.
- VIP-B는 프런트엔드 포트 `443`을 노출하고 Router 백엔드 포트 `30443`으로 라우팅한다.

`80`에서 `30080`으로의 매핑은 Router 노드에서 임시 Python HTTP 서버를 사용하여 확인할 수 있다.

```bash
# HTTP 매핑 확인에 사용하는 Router 백엔드에서
python3 -m http.server 30080 --bind 0.0.0.0

# VIP-B 프런트엔드 포트 80을 통해
curl -i http://<VIP-B>/
```

`python3 -m http.server`는 HTTP 매핑 확인에만 적합하다. `443`에서 `30443`으로의 매핑에 대한 TLS 동작을 입증하지는 않는다. Router 백엔드 포트 `30443`에서 적절한 TLS 지원 리스너를 사용한 후 VIP-B를 통해 TLS 인식 연결 테스트를 수행한다.

```bash
# VIP-B TLS 프런트엔드 확인
curl -k -i https://<VIP-B>/

# 백엔드 리스너를 사용할 수 있을 때 적절한 TLS 인식 테스트 수행
openssl s_client -connect <VIP-B>:443
```

VIP-A 포트 `6443`은 Kubernetes API/TLS 엔드포인트다. 일반 HTTP 서버 또는 일반 HTTP 요청은 API 또는 TLS 경로가 작동한다는 증거가 아니다. `6443` 경로에는 적절한 TCP/TLS 리스너 또는 연결 테스트를 사용한다.

```bash
# VIP-A TCP 연결 가능 여부 확인
nc -vz <VIP-A> 6443

# 사용 가능한 경우 Kubernetes API/TLS 상태 확인
curl -k -i https://<VIP-A>:6443/healthz
```

각 테스트 실행에 대해 다음 다섯 항목을 기록한다.

- 테스트 대상 클러스터, VIP 주소, 프런트엔드 포트 및 백엔드 역할.
- 확인에 사용한 백엔드 서버 호스트명/IP 및 리스너 포트.
- 확인에 사용한 명령어와 실행 시간.
- VIP-A `6443` 및 VIP-B HTTP `80`에서 `30080`으로의 관찰 결과.
- 오류 또는 경고 메시지를 포함한 VIP-B `443`에서 `30443`으로의 관찰된 TLS 결과.

| 프런트엔드 | 백엔드 | 상태 확인 |
|---|---|---|
| `109.156.25.43:6443` | Master 노드 | TCP `6443` |
| `109.156.25.46:80` | Router 노드 `:30080` | TCP `30080` |
| `109.156.25.46:443` | Router 노드 `:30443` | TCP `30443` |
| `109.156.25.57:6443` | Master 노드 | TCP `6443` |
| `109.156.25.60:80` | Router 노드 `:30080` | TCP `30080` |
| `109.156.25.60:443` | Router 노드 `:30443` | TCP `30443` |
| `109.156.25.72:6443` | Master 노드 | TCP `6443` |
| `109.156.25.75:80` | Router 노드 `:30080` | TCP `30080` |
| `109.156.25.75:443` | Router 노드 `:30443` | TCP `30443` |

추정한 성공 결과를 기록하지 않는다. 실행 플레이스홀더를 대상 노드와 Load Balancer에서 수집한 결과로 대체한다.

### 0-2-1. 파괴적 디스크 절차

이 절차는 파괴적이며 root 권한이 필요하다. 승인된 DATA 디스크의 파티션 테이블 항목과 파일시스템 시그니처를 삭제한 다음 새 LVM 및 XFS 구조를 생성한다. 한 번에 하나의 확인된 노드에서 수행한다. 명령은 의도적으로 `/dev/sdb`를 사용한다. 장치 이름만 보고 이 장치를 선택하거나, 대상에 대한 승인된 변경 없이 다른 디스크로 바꾸지 않는다.

> [!warning] 파괴적 명령을 실행하기 전에 대상 디스크와 유지보수 승인을 확인한다
> 아래의 모든 게이트가 확인될 때까지 `fdisk /dev/sdb`, `pvcreate` 또는 `mkfs.xfs`를 실행하지 않는다.
> - 호스트명과 역할이 승인된 인벤토리와 일치한다.
> - `/dev/sdb`가 승인된 DATA 디스크이며, 크기와 시리얼이 VM 또는 스토리지 기록과 일치한다.
> - 디스크에 있는 기존 데이터의 처리 방안이 승인되었다.
> - 현재 블록 장치, PV/VG/LV, 마운트 및 `/etc/fstab` 상태가 변경 증적에 기록되어 있다.
> - 승인된 유지보수 시간이 활성 상태이다.
> 하나라도 알 수 없거나 일치하지 않으면 중지한다.

#### 1. 노드를 확인하고 현재 상태를 기록한다

디스크를 변경하기 전에 대상 노드에서 다음 명령을 실행한다. 전체 출력을 변경 전 증적으로 저장한다. 터미널을 잠깐 확인하거나 디스크가 비어 있다고 가정하지 않는다.

```bash
hostnamectl --static
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS,UUID,SERIAL
findmnt -rn
cat /etc/fstab
pvs
vgs
lvs -a -o lv_name,vg_name,lv_size,lv_attr,devices
```

기록된 출력과 승인된 인벤토리에서 `/dev/sdb`가 `/`, `/app`, `/var/lib/containerd`, `/var/lib/etcd` 또는 보존해야 하는 다른 데이터의 소스나 백킹 장치가 아님을 확인한다. 파일시스템이 마운트되어 있거나, PV/VG/LV가 이미 존재하거나, 파일시스템 시그니처가 있거나, 장치 식별자가 승인된 DATA 디스크와 일치하지 않으면 중지하고 계속하기 전에 상태를 조정한다. 예상하지 못한 상태를 우회하기 위해 추가 `fdisk` 삭제 명령이나 강제 옵션을 사용하지 않는다.

역할에 따라 두 번째 DATA 파티션과 이를 사용할 논리 볼륨의 필수 크기가 결정된다. 이 절차에서는 루트 파일시스템을 변경하지 않는다.

| 역할 프로파일 | 블록 디스크 | `/dev/sdb1` -> `/app` | `/dev/sdb2` -> 파일시스템 | `vg00disk2`의 논리 볼륨 |
|---|---:|---:|---:|---|
| Bastion, Master, Infra, Worker | 315 GB | 50 GB | 100 GB | `containerd_lv` -> `/var/lib/containerd` |
| ETCD | 315 GB | 50 GB | 100 GB | `etcd_lv` -> `/var/lib/etcd` |
| Router | 265 GB | 50 GB | 50 GB | `containerd_lv` -> `/var/lib/containerd` |

ETCD 행은 불변 조건이다. ETCD 노드는 `/var/lib/containerd`가 아니라 `/var/lib/etcd`를 사용한다. [[02. K8S Cluster Nodes Pre-setting]]에는 ETCD 파일시스템 크기에 대한 미해결 카탈로그 불일치가 기록되어 있다. 최종 승인된 ETCD 마운트 설계가 확인되지 않았으면 `fdisk` 전에 중지한다. 카탈로그의 `0 GB` 값이나 비-ETCD 레이아웃을 기본값으로 사용하지 않는다.

#### 2. DATA 파티션을 삭제하고 재생성한다

Bastion, Master, ETCD, Infra 및 Worker 노드에서는 아래의 315 GB 레이아웃을 사용한다. 이 작업은 50 GB의 첫 번째 파티션과 100 GB의 두 번째 파티션을 생성한다.

`fdisk` 프롬프트 안에서 다음 입력을 한 번에 하나씩 수행한다. 주석은 검토 지점을 설명하며 `fdisk`에 입력하지 않는다. 로컬 `fdisk`가 명령, 파티션 번호 또는 타입에 대해 별도의 프롬프트를 표시하면 같은 값으로 해당 프롬프트에 각각 답한다. 다른 값을 추측하지 않는다.

```text
# 1. 파티션 삭제 및 재생성
fdisk /dev/sdb
d 1
n
(Enter)
(Enter)
+50G
(Enter)
p    # 파티션 생성 확인
n
(Enter)
(Enter)
+100G
(Enter)
t 1 31
t 2 31
p    # 결과가 승인된 레이아웃과 일치하는지 확인
w
```

Router 노드에서만 같은 입력 흐름을 사용하되 50 GB의 두 번째 파티션을 생성한다. Router 노드에 100 GB 두 번째 파티션 입력을 적용하지 않는다.

```text
# 1. Router의 파티션 삭제 및 재생성
fdisk /dev/sdb
d 1
n
(Enter)
(Enter)
+50G
(Enter)
p    # 파티션 생성 확인
n
(Enter)
(Enter)
+50G
(Enter)
t 1 31
t 2 31
p    # 결과가 승인된 레이아웃과 일치하는지 확인
w
```

대화형 입력의 의미는 다음과 같다.

- `d 1`은 파티션 1만 삭제한다. 다른 파티션이나 데이터를 삭제하는 것을 승인하는 것이 아니다.
- 각 `(Enter)`는 `fdisk`에 표시된 기본 파티션 번호, 첫 번째 섹터 또는 기타 기본값을 수락한다. 표시된 파티션 번호나 첫 번째 섹터를 추측한 값으로 바꾸지 않는다.
- `+50G`와 `+100G`는 위에 정의된 정확한 파티션 용량을 요청한다. 두 번째 값은 Router의 경우 `+50G`, 위에 나열된 다른 모든 역할 프로파일의 경우 `+100G`이다.
- `t 1 31`과 `t 2 31`은 두 파티션을 타입 코드 `31`(승인된 레이아웃의 `Linux LVM`)으로 설정한다.
- `p`는 메모리에 있는 보류 중인 파티션 테이블을 출력한다. 변경 사항을 기록하지 않으며 필수 검토 지점이다.
- `w`는 검토한 파티션 테이블을 기록한다. 파괴적인 파티션 변경의 커밋 지점으로 취급한다.
- `q`는 검토 결과가 올바르지 않을 때 기록하지 않고 종료한다.

어느 `p` 검토에서든 `fdisk`가 예상하지 못한 파티션 번호, 크기, 타입, 디스크 레이블, 기존 시그니처, 마운트되었거나 사용 중인 장치 또는 승인된 절차에서 다루지 않는 프롬프트를 표시하면 `w` 대신 `q`를 입력하고 중지한다. `d 1`에서 파티션 1이 존재하지 않는다고 보고하거나 다른 기존 파티션이 있으면 중지하고 디스크 상태를 조정한다. 추가 삭제 입력을 임의로 만들지 않는다. 특정 데이터 손실이 승인 범위에 포함된 경우가 아니면 기존 시그니처를 제거하라는 프롬프트를 절대 확인하지 않는다.

`w`가 반환된 후 커널이 테이블을 다시 읽도록 기다리고 PV를 생성하기 전에 검증한다.

```bash
udevadm settle
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,MOUNTPOINTS
fdisk -l /dev/sdb
```

허용 기준은 50 GB 및 타입 코드 `31`(`Linux LVM`)인 `/dev/sdb1`, 315 GB 프로파일에서는 100 GB 및 타입 코드 `31`인 `/dev/sdb2`, Router에서는 50 GB 및 타입 코드 `31`인 `/dev/sdb2`이다. 예상하지 못한 파티션이나 마운트가 없어야 한다. 디스크 정렬 때문에 섹터 번호는 달라질 수 있지만, 역할에 승인된 파티션 번호·용량·타입은 달라지면 안 된다. 결과가 잘못되었으면 `pvcreate` 전에 중지한다.

#### 3. 공통 LVM 및 XFS 구조를 생성하고 검증한다

파티션 승인 확인이 통과한 후에만 공통 명령을 실행한다. `pvcreate`가 기존 시그니처나 사용 중인 장치를 보고하거나, `vgcreate`가 볼륨 그룹이 이미 존재한다고 보고하거나, `mkfs.xfs`가 기존 시그니처를 보고하거나 데이터 덮어쓰기를 요청하거나, 어떤 명령이든 예상하지 못한 확인을 요청하면 중지한다. 조건을 우회하기 위해 `-f`, `-ff` 또는 다른 장치를 사용하지 않는다.

```bash
# 2. 공통 LVM 구조 생성
lsblk
pvcreate /dev/sdb1
pvcreate /dev/sdb2
vgcreate vg00disk1 /dev/sdb1
vgcreate vg00disk2 /dev/sdb2
lvcreate -n app_lv -l 100%free vg00disk1

# 3. 공통 파일시스템 생성
mkfs.xfs /dev/vg00disk1/app_lv
```

비-ETCD 역할에는 Bastion, Master, Router, Infra 및 Worker 노드가 포함되며, 이 역할에서는 containerd 논리 볼륨과 파일시스템을 생성한다. `100%free` 할당은 승인된 두 번째 파티션 크기를 사용한다. 315 GB 프로파일은 100 GB이고 Router는 50 GB이다.

```bash
# 비-ETCD 역할에서만 실행
lvcreate -n containerd_lv -l 100%free vg00disk2
mkfs.xfs /dev/vg00disk2/containerd_lv
```

ETCD 노드에서는 대신 ETCD 논리 볼륨과 파일시스템을 생성한다.

```bash
# ETCD 역할에서만 실행
lvcreate -n etcd_lv -l 100%free vg00disk2
mkfs.xfs /dev/vg00disk2/etcd_lv
```

비-ETCD와 ETCD 분기는 상호 배타적이다. ETCD 노드에서는 `containerd_lv`를 전혀 생성하지 않으며, `containerd_lv`를 생성한 다음 같은 볼륨 그룹에 `etcd_lv`를 생성하지 않는다. 비-ETCD 노드에서는 `etcd_lv`를 `containerd_lv` 대신 사용하지 않는다.

마운트나 `/etc/fstab` 변경을 진행하기 전에 새로 생성한 구조를 검증한다.

```bash
lsblk -f
pvs
vgs
lvs -a -o lv_name,vg_name,lv_size,lv_attr,devices
blkid /dev/vg00disk1/app_lv
```

다음 역할별 검사 중 정확히 하나를 실행한다.

```bash
# 비-ETCD 역할에서만 실행
blkid /dev/vg00disk2/containerd_lv
```

```bash
# ETCD 역할에서만 실행
blkid /dev/vg00disk2/etcd_lv
```

검증 결과에는 `app_lv`와 선택한 두 번째 LV에 XFS가 있고, 예상한 역할별 크기와 VG/LV 이름이 표시되어야 한다. ETCD 노드에는 `etcd_lv`가 표시되고 `containerd_lv`는 없어야 하며, 비-ETCD 노드에는 `containerd_lv`가 표시되고 `etcd_lv`는 없어야 한다. `blkid`가 반환한 실제 UUID를 변경 증적에 기록한다. 이 가이드에 UUID를 만들거나 복사해 넣지 않는다.

이 섹션은 LVM 및 XFS 검증 후 끝난다. 여기에서 마운트 지점을 만들거나 `mount`를 실행하거나 `/etc/fstab`를 편집하지 않는다. 검사가 통과하면 실제 대상 노드의 UUID와 역할에 맞는 경로를 사용하여 [[02. K8S Cluster Nodes Pre-setting]]의 마운트 지점 및 `/etc/fstab` 영속성 절차를 계속 진행한다. 검증에 실패하면 중지하고 마운트 절차로 인계하지 않는다.

### 0-2-2. `dspaas` wheel 그룹 소속 확인

모든 Bastion 및 DKS 클러스터 노드에서 그룹 소속과 sudo 확인을 실행한다. `id`와 `groups`를 모두 사용하여 계정을 확인한다.

```bash
id dspaas
groups dspaas
```

`dspaas`가 `wheel`의 구성원이 아닌 경우 사용자의 기존 보조 그룹을 대체하지 않고 그룹을 추가한다.

```bash
usermod -aG wheel dspaas
```

파괴적인 `usermod -G wheel dspaas` 형식은 사용하지 않는다. 그룹 소속을 다시 확인하고 `dspaas` 계정에서 비밀번호 없는 sudo를 확인한다.

```bash
id dspaas
groups dspaas
sudo -n true
```
