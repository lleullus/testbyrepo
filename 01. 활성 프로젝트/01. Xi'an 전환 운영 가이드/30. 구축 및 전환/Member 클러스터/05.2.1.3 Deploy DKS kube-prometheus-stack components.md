# 05.2.1.3 Deploy DKS kube-prometheus-stack components

> **실행자**: DSPAAS
>
> **대상 클러스터**: `dev-apps-pa01-xas`
>
> **선행 단계**: [[05.2.1.2 Deploy CRDs|5-2-1-2 Deploy CRDs]]

이 단계에서 `monitoring` Namespace에 DKS custom Prometheus stack을 배포합니다. KubeSphere 설치 후 생성되는 `kubesphere-monitoring-system`과 혼동하지 않습니다. Member Cluster의 선행 Monitoring stack은 `monitoring` Namespace를 사용합니다.

## 1. dev 적용값

| 항목 | 적용값 |
|---|---|
| Namespace | `monitoring` |
| Cluster label | `dev-apps-pa01-xas` |
| Stage label | `Dev` |
| Prometheus retention | `30d` |
| Prometheus replicas | `3` |
| Alertmanager replicas | `3` |
| 대상 Infra node | `xadksirmd01`, `xadksirmd02`, `xadksirmd03` |
| Node selector | `node-type: infra`, `kubernetes.io/os: linux` |
| Grafana datasource URL | `http://prometheus-k8s.monitoring.svc:9090` |
| Custom stack image base | `xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/prometheus/...` 후보, 실제 manifest/Harbor 확인 |
| StorageClass | `kubectl get storageclass`로 확인한 값 |

Prometheus와 Alertmanager replica 수는 dev 클러스터의 Infra 3대에 맞춥니다. `node-exporter`는 DaemonSet이므로 모든 대상 노드에 배치되는 것이 정상이며, 이를 Infra 3개 replica와 동일하게 해석하지 않습니다.

## 2. Manifest 경로 확인

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/2.kube-prometheus-0.11.0/manifests
ls -al
```

적용 전에 다른 환경 값이 남아 있는지 확인합니다.

```bash
grep -RniE '^( *image:| *namespace:| *storageClassName:| *replicas:| *retention:| *cluster:| *stage:| *node-type:)' --include='*.yaml' .
grep -RniE 'dcr\.cloud\.samsungds\.net|tmtest|tmdev|dev-ds-kstest|10\.166\.202\.' --include='*.yaml' .
```

Taylor 환경의 registry, domain, cluster name, ETCD IP가 검색되면 그대로 적용하지 않습니다. Xi'an Harbor host는 `xa.dcr.dks.samsungds.net`입니다. 원본 Prometheus image 경로가 `dcr.cloud.samsungds.net/dspaas-v1.22.10-a/prometheus/...`라면 host만 `xa.dcr.dks.samsungds.net`으로 바꾸고 `dspaas-v1.22.10-a/prometheus/...` repository path와 tag는 유지하는 방식이 우선입니다. `dspaas-cloud`는 KubeSphere bundle에서 사용하는 경로이므로 custom Prometheus stack에 일괄 치환하지 않습니다. 실제 image/tag와 imagePullSecret은 manifest와 Harbor에서 확인합니다.

## 3. Manifest별 핵심값 확인

### 3-1. Alertmanager

```bash
grep -nE 'image:|namespace:|node-type:|replicas:|storageClassName:' alertmanager-alertmanager.yaml
grep -n namespace alertmanager-secret.yaml
```

확인 기준:

- `namespace: monitoring`
- `replicas: 3`
- `node-type: infra`
- Alertmanager CR 이름은 `main`이며 생성되는 Service/Pod 이름은 `alertmanager-main` 계열
- Grafana/Alertmanager PVC에 지정된 StorageClass가 현재 dev 클러스터의 확인값과 일치
- `alertmanager-secret.yaml`도 `monitoring` Namespace를 대상으로 함

### 3-2. Prometheus

```bash
grep -nE 'image:|namespace:|retention:|cluster:|stage:|node-type:|replicas:|storageClassName:|secrets:' prometheus-prometheus.yaml
```

`prometheus-prometheus.yaml`의 `Prometheus` 리소스는 다음 값으로 맞춥니다.

```yaml
spec:
  retention: 30d
  externalLabels:
    cluster: dev-apps-pa01-xas
    stage: Dev
  replicas: 3
  nodeSelector:
    node-type: infra
    kubernetes.io/os: linux
```

`storageClassName`은 manifest에 지정된 PVC template에 확인한 dev StorageClass를 반영합니다. `prometheus-k8s` PVC가 생성되기 전 반드시 이름을 다시 확인합니다.

### 3-3. Grafana datasource

```bash
grep -n -A12 -B3 'prometheus-k8s' grafana-dashboardDatasources.yaml
```

datasource 이름은 `prometheus`, URL은 아래 값을 사용합니다.

```text
http://prometheus-k8s.monitoring.svc:9090
```

`kubesphere-monitoring-system` 또는 다른 클러스터의 Service 이름을 사용하지 않습니다.

> [!danger] 2026-07-14 실제 장애
> `dev-apps-pa01-xas`에서 Secret URL이 `http://prometheus-k8s.kubesphere-monitoring-system.svc:9090`으로 들어가 Grafana No data / `no such host`가 발생했다. Prometheus Pod와 `monitoring.svc` 직접 조회는 정상이었다.

잘못 적용된 뒤 고치는 명령:

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/2.kube-prometheus-0.11.0/manifests
# grafana-dashboardDatasources.yaml 의 url을 monitoring.svc:9090 으로 수정
kubectl apply -f grafana-dashboardDatasources.yaml
kubectl -n monitoring rollout restart deploy/grafana
kubectl -n monitoring rollout status deploy/grafana
kubectl get secret grafana-datasources -n monitoring -o jsonpath='{.data.datasources\.yaml}' | base64 -d
```

완료 기준: Grafana UI Save & Test 성공.

## 4. 전체 stack 적용

```bash
kubectl apply -f .
```

Bundle에 `adaptor` 디렉토리가 포함되어 있고 Prometheus Adapter가 생성되지 않았다면 별도로 적용합니다.

```bash
kubectl get deployment prometheus-adapter -n monitoring
kubectl apply -f adaptor/
```

## 5. 배포 확인

```bash
kubectl get pods -n monitoring -o wide
kubectl get pvc -n monitoring -o wide
kubectl get prometheus,alertmanager -n monitoring
kubectl get servicemonitor,prometheusrule -n monitoring
kubectl get svc -n monitoring
```

확인 대상:

- `alertmanager-main`이 3 replica로 Ready
- `prometheus-k8s`가 3 replica로 Ready
- `prometheus-operator`, `kube-state-metrics`, `blackbox-exporter`, Grafana가 정상
- `prometheus-adapter`가 bundle에 포함된 경우 정상
- `node-exporter`가 DaemonSet으로 대상 노드에 배치
- Prometheus/Alertmanager PVC가 `Bound`
- 일반 Monitoring workload가 `node-type=infra`에 배치

문제가 있으면 아래 순서로 확인합니다.

```bash
kubectl get pods -n monitoring -o wide
kubectl get events -n monitoring --sort-by=.lastTimestamp
kubectl describe pod -n monitoring <비정상-pod>
kubectl logs -n monitoring <비정상-pod> --all-containers --tail=100
```

## 6. Grafana 관리자 비밀번호 변경

초기 비밀번호를 운영 비밀번호로 변경할 때는 비밀번호를 문서나 shell history에 남기지 않습니다.

```bash
kubectl get pod -n monitoring | grep grafana
kubectl exec -it -n monitoring <grafana-pod> -- \
  grafana-cli admin reset-admin-password '<새-운영-비밀번호>'
```

성공 메시지가 확인되면 Grafana Ingress 배포 후 로그인 검증을 진행합니다.

## 완료 기준

- [ ] `monitoring` Namespace의 주요 Pod가 `Running`/Ready
- [ ] Prometheus/Alertmanager replica가 각각 3
- [ ] Prometheus `retention=30d`
- [ ] `externalLabels.cluster=dev-apps-pa01-xas`
- [ ] `externalLabels.stage=Dev`
- [ ] Prometheus/Alertmanager PVC가 `Bound`
- [ ] Grafana datasource URL이 `prometheus-k8s.monitoring.svc:9090`
- [ ] KubeSphere 설치 전에 stack이 안정화됨
