# 05.2.1.1 Deploy preliminary components

> **실행자**: DSPAAS
>
> **대상 클러스터**: `dev-apps-pa01-xas`
>
> **목적**: DKS custom Prometheus stack을 배포하기 전에 `monitoring` Namespace, ETCD 인증서 Secret, Grafana PVC를 준비

Member Cluster의 Prometheus stack은 KubeSphere 설치보다 먼저 배포합니다. 이 단계에서 다른 사이트의 Namespace, StorageClass, 인증서 파일을 그대로 복사하지 않습니다.

## 1. dev 기준값

| 항목 | dev-apps-pa01-xas 값 | 확인 방법 |
|---|---|---|
| Bundle 루트 | `~/SCS_DKS_Kubernetes_Stack-v1.0` | Bastion의 실제 경로 확인 |
| Stack 경로 | `dks-prometheus-stack_v2.0` | `ls` |
| Namespace | `monitoring` | `1.namespace.yaml` |
| Grafana PVC | `grafana-pvc`, `16Gi`, `RWO` | `3.grafana-pvc.yaml` |
| StorageClass | **현장 확인 필요** | `kubectl get storageclass` |
| Infra 배치 | `xadksirmd01~03`, `109.156.22.79~81` | `kubectl get nodes -l node-type=infra -o wide` |

현재 Xi'an Storage 문서에는 SCS StorageClass 명이 아직 요청 중으로 기록되어 있습니다. 따라서 `powerflexos-xfs-sc-300t-sp04` 또는 `scs-netapp-qtree-nfs-sc-delete`를 확인 없이 사용하지 않습니다.

## 2. 작업 전 확인

```bash
kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide
kubectl get nodes -l node-type=infra -o wide
kubectl get storageclass
```

확인 기준:

- 현재 context가 `dev-apps-pa01-xas` 대상인지 확인
- Infra node가 `node-type=infra` 라벨로 3대 조회되는지 확인
- PVC에 사용할 StorageClass가 `Available` 목록에 있는지 확인
- StorageClass가 없거나 이름이 불명확하면 이 단계에서 중지하고 SCS/Storage 담당자에게 확정값을 받음

## 3. Bundle 확인

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/1.preliminary
ls -al
```

필수 파일:

```text
1.namespace.yaml
2.secret.sh
3.grafana-pvc.yaml
```

## 4. `monitoring` Namespace 생성

적용 전에 Namespace가 `monitoring`인지 확인합니다.

```bash
grep -nE '^(metadata:|  name:|  namespace:)' 1.namespace.yaml
kubectl apply -f 1.namespace.yaml
kubectl get ns monitoring
```

정상 기준:

```text
monitoring   Active
```

## 5. ETCD 인증서 Secret 생성

`2.secret.sh`는 ETCD 인증서 파일을 읽어 `monitoring/etcd-certs` Secret을 생성하는 스크립트입니다. 실행 전에 스크립트가 참조하는 인증서 경로와 Namespace를 확인합니다.

```bash
grep -nE 'namespace|etcd|pem|crt|kubectl' 2.secret.sh
./2.secret.sh
```

확인:

```bash
kubectl get secret etcd-certs -n monitoring
kubectl describe secret etcd-certs -n monitoring | grep -A3 -E 'ca\.pem|node-'
```

Secret 키 이름은 이후 `ServiceMonitor`의 `certFile`/`keyFile` 경로와 일치해야 합니다. `node-khdksmatmdta01` 등 Taylor 환경의 인증서 이름을 복사하지 말고, 위 출력에서 dev 클러스터용 키 이름을 확인합니다.

> [!warning] Secret 취급
> Secret 전문과 인증서 데이터는 문서, 티켓, 터미널 로그에 붙여넣지 않습니다. Namespace, Secret 이름, 키 이름만 확인합니다.

## 6. Grafana PVC 생성

먼저 현재 사용할 StorageClass의 이름과 provisioner를 확인합니다.

```bash
kubectl get storageclass
kubectl get storageclass <확정한-dev-storageclass> -o yaml
grep -nE 'name:|namespace:|storage:|storageClassName:|accessModes:' 3.grafana-pvc.yaml
```

`3.grafana-pvc.yaml`은 아래 기준으로 수정한 뒤 적용합니다. `<확정한-dev-storageclass>`는 설명용 표기이므로 실제 이름으로 치환해야 합니다.

```yaml
metadata:
  name: grafana-pvc
  namespace: monitoring
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 16Gi
  storageClassName: <확정한-dev-storageclass>
```

```bash
kubectl apply -f 3.grafana-pvc.yaml
kubectl get pvc grafana-pvc -n monitoring -o wide
kubectl describe pvc grafana-pvc -n monitoring
```

정상 기준:

- `STATUS`가 `Bound`
- `CAPACITY`가 `16Gi`
- `ACCESS MODES`가 `RWO`
- `STORAGECLASS`가 방금 확인한 dev StorageClass와 일치
- PVC Events에 provisioner 오류가 없음

## 7. 완료 기준

- [ ] 현재 context가 `dev-apps-pa01-xas`임
- [ ] `monitoring` Namespace가 `Active`
- [ ] `etcd-certs` Secret이 `monitoring`에 생성됨
- [ ] Secret 키 이름을 확인함
- [ ] `grafana-pvc`가 `Bound`
- [ ] Grafana PVC에 적용한 StorageClass를 증적에 기록함
