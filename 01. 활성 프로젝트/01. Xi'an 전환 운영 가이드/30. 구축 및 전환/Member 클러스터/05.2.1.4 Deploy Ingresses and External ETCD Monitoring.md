# 05.2.1.4 Deploy Ingresses and External ETCD Monitoring

> **실행자**: DSPAAS
>
> **대상 클러스터**: `dev-apps-pa01-xas`
>
> **선행 단계**: [[05.2.1.3 Deploy DKS kube-prometheus-stack components|5-2-1-3 Deploy DKS kube-prometheus-stack components]]

이 단계는 Monitoring UI용 Ingress를 배포하고, Member Cluster의 외부 ETCD 3대를 `ServiceMonitor` target으로 등록합니다.

## 2. Monitoring Ingress 배포

### 2-1. Host 값 수정

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/4.Ingress
ls -al
```

dev 클러스터에서는 다음 Host를 사용합니다.

| 파일 | Host |
|---|---|
| `1.prometheus_ingress.yaml` | `prometheus.xadevpa01.apps.dks.samsungds.net` |
| `2.grafana_ingress.yaml` | `grafana.xadevpa01.apps.dks.samsungds.net` |
| `3.alertmanager_ingress.yaml` | `alertmanager.xadevpa01.apps.dks.samsungds.net` |

각 manifest의 Namespace는 `monitoring`이어야 하며 Service는 아래 이름과 일치해야 합니다.

| Ingress | Service | Port |
|---|---|---:|
| Prometheus | `prometheus-k8s` | 9090 |
| Grafana | `grafana` | 3000 |
| Alertmanager | `alertmanager-main` | 9093 |

`tmtest.cloud`, `tmdev.cloud`, `apps.<다른-클러스터-domain>` 값을 그대로 적용하지 않습니다.

### 2-2. 적용 및 확인

```bash
kubectl apply -f .
kubectl get ingress -n monitoring -o wide
kubectl describe ingress -n monitoring prometheus-ingress
kubectl describe ingress -n monitoring grafana-ingress
kubectl describe ingress -n monitoring alertmanager-ingress
```

정상적으로 연결되면 `ADDRESS`에 Router IP `109.156.22.76`, `109.156.22.77`, `109.156.22.78`이 표시될 수 있습니다. 외부 DNS가 `109.156.25.75`를 가리키는지 별도로 확인합니다.

```bash
getent hosts prometheus.xadevpa01.apps.dks.samsungds.net
getent hosts grafana.xadevpa01.apps.dks.samsungds.net
getent hosts alertmanager.xadevpa01.apps.dks.samsungds.net
```

DNS 조회가 필요한 환경에서는 `getent hosts` 결과만 확인하고, DNS 도구가 있으면 `dig +short <host>`를 사용합니다.

> [!warning] TLS/인증서
> 현재 dev 클러스터 상세에는 L4 LB의 80/443 전달만 정의되어 있고 Monitoring Ingress별 TLS Secret은 확정되어 있지 않습니다. `spec.tls`를 임의로 추가하지 말고 현장 인증서 정책과 Ingress Controller 기본 인증서 구조를 확인합니다. `kubectl get ingress`의 PORTS가 `80`으로 보이는 것도 이 구조에서는 가능하지만, 443 외부 접속 여부는 LB와 Controller 설정으로 별도 검증합니다.

## 3. 외부 ETCD Service와 Endpoints 작성

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/3.servicemonitor_etcd
ls -al
```

`1.service.yaml`의 기준:

```yaml
metadata:
  name: etcd-k8s
  namespace: monitoring
spec:
  type: ClusterIP
  clusterIP: None
  ports:
    - name: metrics
      port: 2379
      targetPort: 2379
  selector: null
```

`2.endpoints.yaml`의 `subsets.addresses`는 반드시 dev ETCD IP 3개로 맞춥니다.

```yaml
subsets:
  - addresses:
      - ip: 109.156.22.70
      - ip: 109.156.22.71
      - ip: 109.156.22.72
    ports:
      - name: metrics
        port: 2379
        protocol: TCP
```

```bash
grep -nE 'name:|namespace:|ip:|port:' 1.service.yaml 2.endpoints.yaml
```

## 4. ETCD 인증서 파일명 확인 및 ServiceMonitor 수정

Secret의 키 이름을 먼저 확인합니다.

```bash
kubectl describe secret -n monitoring etcd-certs | grep -A3 -E 'ca\.pem|node-'
```

`3.servicemonitor-metrics.yaml`은 아래 구조를 사용합니다. `<확인한-dev-node-cert>`는 Secret 출력에서 확인한 실제 기본 파일명으로 치환합니다.

```yaml
metadata:
  name: etcd-k8s
  namespace: monitoring
spec:
  jobLabel: k8s-app
  endpoints:
    - port: metrics
      interval: 30s
      scheme: https
      tlsConfig:
        caFile: /etc/prometheus/secrets/etcd-certs/ca.pem
        certFile: /etc/prometheus/secrets/etcd-certs/<확인한-dev-node-cert>.pem
        keyFile: /etc/prometheus/secrets/etcd-certs/<확인한-dev-node-cert>-key.pem
        serverName: etcd-cluster
        insecureSkipVerify: true
  selector:
    matchLabels:
      k8s-app: etcd-k8s
```

`node-khdksmatmdta01.pem`은 Taylor 환경 예시이므로 dev에 사용하지 않습니다. dev ETCD 인증서가 `node-xadksetmd01.pem` 형식이라도 실제 Secret 키가 다르면 Secret 출력값을 우선합니다.

> [!warning] `insecureSkipVerify`
> 위 설정은 원본 DKS 절차를 보존한 값입니다. 인증서 SAN과 `serverName` 검증이 가능한 현장 표준이 있으면 `insecureSkipVerify: false`로 전환하는 것이 안전합니다. 전환 여부는 인증서 발급 정책과 ETCD 운영 담당자 확인 후 결정합니다.

## 5. Prometheus에 ETCD Secret 연결

Prometheus CR 이름은 custom stack 기준 `k8s`입니다.

```bash
kubectl get prometheus -n monitoring
kubectl edit prometheus -n monitoring k8s
```

`spec`에 아래 값이 반영되어야 합니다. 기존 `spec` 항목은 삭제하지 않습니다.

```yaml
spec:
  replicas: 3
  secrets:
    - etcd-certs
```

저장 후 반영을 확인합니다.

```bash
kubectl rollout status statefulset prometheus-k8s -n monitoring --timeout=120s
kubectl get prometheus k8s -n monitoring -o yaml | grep -n -A3 -B2 -E 'replicas:|secrets:'
```

Prometheus Pod에 `/etc/prometheus/secrets/etcd-certs` volume mount가 없으면 ServiceMonitor 적용 전에 Secret 연결을 수정합니다.

## 6. ServiceMonitor 적용

```bash
kubectl apply -f 1.service.yaml
kubectl apply -f 2.endpoints.yaml
kubectl apply -f 3.servicemonitor-metrics.yaml
```

확인:

```bash
kubectl get svc -n monitoring etcd-k8s
kubectl get endpoints -n monitoring etcd-k8s
kubectl get servicemonitor -n monitoring etcd-k8s
kubectl describe servicemonitor -n monitoring etcd-k8s
```

기대 결과:

- `etcd-k8s` Service가 `ClusterIP: None`
- Endpoints에 `109.156.22.70:2379`, `109.156.22.71:2379`, `109.156.22.72:2379`
- `etcd-k8s` ServiceMonitor가 `monitoring`에 생성됨

## 7. Prometheus Target 확인

Prometheus UI의 **Status > Targets**에서 `etcd-k8s` job의 3개 endpoint가 모두 `UP`인지 확인합니다.

필요하면 로컬 port-forward를 사용합니다.

```bash
kubectl -n monitoring port-forward svc/prometheus-k8s 9090:9090
```

브라우저에서 `http://127.0.0.1:9090/targets`를 열어 확인합니다. 리소스가 생성된 것만으로 target 정상이라고 판단하지 않습니다.
