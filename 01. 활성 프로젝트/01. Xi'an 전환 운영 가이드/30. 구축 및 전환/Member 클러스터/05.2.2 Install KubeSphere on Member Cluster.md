# 05.2.2 Install KubeSphere on Member Cluster

> **실행자**: DSPAAS
>
> **대상 클러스터**: `dev-apps-pa01-xas` (DEV Member)
>
> **원문 기준**: DSPAAS `5-2-2. Install Kubesphere - Member cluster` 절차 — StorageClass 생성 및 dks-prometheus-stack 설치 완료 후 Member Cluster에 KubeSphere를 설치하고 Host Join 준비까지 수행

**선행 조건**: [[05.2.1.1 Deploy preliminary components|5-2-1-1]] ~ [[05.2.1.5 Grafana Custom Dashboard Addition|5-2-1-5]] 완료 (StorageClass, DKS Prometheus stack, External ETCD Monitoring, Grafana 대시보드)

**범위**:
- KubeSphere installer manifest 배포
- Cluster configuration 적용 (Member용 `clusterRole: member`)
- 설치 확인 (namespace/pod/installer log)
- DKS 표준 node 재배치 (infra node)
- Member role 배포 (권한 제한)
- Host Join 전 jwtSecret 확인
- **5-2-3 (Host Join)은 이 문서에서 다루지 않음** — Join 준비 확인까지만 포함

Member Cluster의 `kubectl` context가 맞는지 확인하고, 선행 리소스가 정상인지 점검한다.

```bash

kubectl get nodes -l node-type=infra -o wide
kubectl get nodes -l node-role.kubernetes.io/infra -o wide
kubectl describe node xadksirmd01 | grep Taints
```

```bash

# DKS Prometheus stack 상태

# KubeSphere CRD 사전 존재 확인 (없어야 정상)

kubectl get ns | grep kubesphere
```

```bash
# bundle 파일 존재 확인
ls -la ~/SCS_DKS_Kubernetes_Stack-v1.0/Kubesphere-v3.2.1/member/
```

예상 출력:
```text

```

```bash

grep -nE 'dcr\.cloud\.samsungds|powerflexos|10\.166\.202|tmtest|tmdev|dev-ds-kstest|khdks' \
```

### 사전 점검 기준

- [ ] `kubectl config current-context`가 `dev-apps-pa01-xas` 대상
- [ ] Infra node 3대 (`xadksirmd01~03`)에 `node-type=infra` label 존재

- [ ] manifest에 Taylor/PRD 값 잔존 없음

## 3. Deploy KubeSphere installer manifest

원문 기준 Member Cluster 전용 `kubesphere-installer.yaml`을 적용한다. 원문은 아래 리소스를 포함한다:

| 리소스 종류 | 이름 | 네임스페이스 |
|-------------|------|-------------|
| `CustomResourceDefinition` | `clusterconfigurations.installer.kubesphere.io` | - |
| `Namespace` | `kubesphere-system` | - |
| `ServiceAccount` | `ks-installer` | `kubesphere-system` |
| `ClusterRole` | `ks-installer` | - |
| `ClusterRoleBinding` | `ks-installer` | - |
| `Deployment` | `ks-installer` | `kubesphere-system` |

## 4. Deploy cluster configuration manifest

`cluster-configuration.yaml`에 Member Cluster 설정을 정의하고 적용한다. 이 파일이 KubeSphere의 모든 component 활성화/비활성화와 외부 연동을 결정한다.

### 4.1. 원문 설정 검토 및 DEV 치환

> [!danger] 민감값 처리
> - `jwtSecret: "<HOST_JWT_SECRET>"` — 실제 JWT Secret은 **Host Cluster**의 `kubesphere-config` ConfigMap에서 조회한 값으로 치환한다. 이 값을 문서·로그·스크린샷에 기록하지 않는다.
> - 초기 콘솔 비밀번호(`admin`)는 설치 완료 후 콘솔 메시지로 확인한다. 문서에 기본 비밀번호를 기록하지 않는다.

> [!note] External monitoring endpoint 교차검증
> 원문 값 `http://prometheus-operated.monitoring.svc:9090`을 그대로 사용한다. DKS Prometheus CR `k8s`가 생성하는 Service는 `prometheus-operated`이며, Grafana datasource는 `prometheus-k8s.monitoring.svc:9090`을 사용한다. 두 Service는 같은 Prometheus backend를 가리킨다. KubeSphere는 `prometheus-operated` endpoint를 통해 monitoring 메트릭을 읽어온다.

| 구분 | Service | 용도 |
|------|---------|------|
| KubeSphere external monitoring | `prometheus-operated.monitoring.svc:9090` | KubeSphere가 메트릭 조회 |
| Grafana datasource | `prometheus-k8s.monitoring.svc:9090` | Grafana 대시보드용 |

### 4.6. 설치 중 장애 대응

| 증상 | 원인 | 조치 |
|------|------|------|
| `ImagePullBackOff` / `ErrImagePull` | Registry 주소 오류 또는 imagePullSecret 없음 | `local_registry`, image tag 확인. DEV registry `xa.dcr.dks.samsungds.net/dspaas-cloud` 접근 가능 여부 확인 |

| installer log 실패 / task failed | CRD 타이밍, 리소스 부족 | installer pod 삭제 후 재시도 (`kubectl delete pod -n kubesphere-system <pod>`) |
| External monitoring endpoint unreachable | `prometheus-operated` Service 없음 | `kubectl get svc -n monitoring prometheus-operated` 확인. DKS Prometheus CR `k8s`가 정상인지 확인 |
| Console 접속 실패 (30880) | NodePort 방화벽 / LB 미등록 | `kubectl get svc -n kubesphere-system ks-console`, `netstat -tlnp \| grep 30880` |
| Pod Pending (PVC) | StorageClass 미존재 또는 용량 부족 | `kubectl describe pvc -n kubesphere-system`, StorageClass 이름 일치 확인 |

> 아래 patch 명령을 실행하기 전에 DEV infra node label/taint가 일치하는지 확인한다.

## 7. Deploy member role

KubeSphere 기본 role은 과도한 권한을 포함한다. Member Cluster에서는 project/namespace 범위로 권한을 제한하기 위해 RoleBase CRD를 사용하여 `project-admin` role을 생성한다.

### 7.1. RoleBase 개념

`RoleBase`는 KubeSphere의 API object로, role의 최상위 권한을 정의한다. `project-admin` RoleBase는 DevOps scope와 Namespace scope에서만 권한을 부여하고, Cluster scope 권한은 부여하지 않는다.

### 7.2. member-role.yaml 적용

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/Kubesphere-v3.2.1/member
cat member-role.yaml
```

원문 YAML:

```yaml
apiVersion: iam.kubesphere.io/v1alpha2
kind: RoleBase
metadata:
  labels:
    scope.kubesphere.io/devops: ""
    scope.kubesphere.io/namespace: ""
  name: project-admin
role:
  apiVersion: rbac.authorization.k8s.io/v1
  kind: Role
  metadata:
    annotations:
      iam.kubesphere.io/aggregation-roles: '[
        "role-template-view-members",
        "role-template-view-roles",
        "role-template-manage-members",
        "role-template-view-app-workloads",
        "role-template-manage-app-workloads",
        "role-template-view-volumes",
        "role-template-manage-volumes",
        "role-template-view-snapshots",
        "role-template-manage-snapshots",
        "role-template-view-secrets",
        "role-template-manage-secrets",
        "role-template-view-serviceaccount",
        "role-template-manage-serviceaccount",
        "role-template-view-configmaps",
        "role-template-manage-configmaps",
        "role-template-view-alerting-policies",
        "role-template-manage-alerting-policies",
        "role-template-view-alerting-messages",
        "role-template-manage-alerting-messages",
        "role-template-view-custom-monitoring",
        "role-template-manage-custom-monitoring",
        "role-template-view-pipelines",
        "role-template-manage-pipelines",
        "role-template-view-pipelineruns",
        "role-template-manage-pipelineruns",
        "role-template-view-credentials",
        "role-template-manage-credentials"
      ]'
      kubesphere.io/creator: system
    name: admin
  rules:
    - apiGroups: ['*']
      resources: ['*']
      verbs: ['get', 'list', 'watch']
    - apiGroups:
        - ""
        - apps
        - extensions
        - batch
        - logging.kubesphere.io
        - monitoring.kubesphere.io
        - monitoring.coreos.com
        - metering.kubesphere.io
        - notification.kubesphere.io
        - autoscaling
        - alerting.kubesphere.io
        - openpitrix.io
        - app.k8s.io
        - servicemesh.kubesphere.io
        - operations.kubesphere.io
        - devops.kubesphere.io
        - resources.kubesphere.io
        - config.istio.io
        - events.k8s.io
        - events.kubesphere.io
        - snapshot.storage.k8s.io
        - monitoring.coreos.com
        - networking.k8s.io
      resources: ['*']
      verbs: ['*']
    - apiGroups: ['*']
      resources:
        - members
        - rolebindings
      verbs: ['*']
```

> [!note] Role 설계 의도
> - `scope.kubesphere.io/devops: ""` + `scope.kubesphere.io/namespace: ""` — DevOps 및 Namespace scope로 제한
> - 첫 번째 rule: 모든 리소스에 대해 `get/list/watch`만 허용 (읽기 전용)
> - 두 번째 rule: DevOps/Monitoring/App/Network 등 주요 리소스에 대해 `*` (모든 작업) 허용
> - 세 번째 rule: `members`와 `rolebindings`에 대해 `*` 허용 (멤버/롤 관리)
> - Cluster scope role을 생성하지 않으므로 cluster-wide 권한은 부여되지 않음

```bash
kubectl apply -f member-role.yaml
```

예상 출력:
```text
rolebase.iam.kubesphere.io/project-admin created
```

## 8. Join Member Cluster to Host Cluster - 준비 및 확인

이 단계는 Join 전 사전 확인까지 다룬다. 실제 Join 절차는 5-2-3 문서에서 수행한다.

### 8.1. Host Cluster에서 jwtSecret 조회

Host Cluster의 `kubesphere-config` ConfigMap에서 `jwtSecret` 값을 조회한다. **이 값을 문서·로그에 기록하지 않는다.**

```bash
# Host Cluster context로 전환
kubectl config use-context <HOST_CLUSTER_CONTEXT>

# jwtSecret 조회 (출력 확인 후 터미널 기록 즉시 삭제)
kubectl -n kubesphere-system get cm kubesphere-config -o yaml | grep jwtSecret
```

> [!danger] 보안 주의
> 조회한 `jwtSecret` 값을 문서, 티켓, 스크린샷, 공유 채널에 절대 기록하지 않는다. 안전한 방법(예: 암호 관리 도구, 직접 전달)으로 Member Cluster 운영자에게 전달한다.

### 8.2. Member Cluster의 jwtSecret 일치 확인

Member Cluster에서도 `kubesphere-config` ConfigMap을 확인한다. 값 자체를 출력하지 않고 Host와 일치하는지 안전한 방식으로 검증한다.

```bash
# Member Cluster context로 전환
kubectl config use-context <MEMBER_CLUSTER_CONTEXT>

# kubesphere-config 조회 (전문 출력 금지, grep으로 jwtSecret 존재만 확인)
kubectl -n kubesphere-system get cm kubesphere-config -o yaml | grep jwtSecret
```

**안전한 검증 방법:**
- 두 클러스터에서 조회한 `jwtSecret` 값의 길이와 prefix를 눈으로 비교한다
- Hash 기반 검증이 필요한 경우 개별 터미널 세션에서 SHA256 해시를 확인한다
- **절대 두 값을 같은 화면에 동시에 출력하지 않는다**

### 8.3. accessTokenMaxAge 확인

```bash
kubectl -n kubesphere-system get cm kubesphere-config -o yaml | grep accessTokenMaxAge
```

정상 기준: `accessTokenMaxAge: 0` (0이면 토큰 만료 없음)

### 8.4. kubesphere-config 전체 구조 확인 (민감값 마스킹)

```bash
kubectl -n kubesphere-system get cm kubesphere-config -o yaml | grep -v "jwtSecret:\|password:"
```

정상 설정 시 `multipleLogin: True` 확인 및 `kubectlImage` registry가 DEV registry와 일치하는지 확인.

### 8.5. Host Web UI Import를 위한 kubeconfig 준비

> [!warning] 중요
> kubeconfig 파일에는 클러스터 인증 정보가 포함되어 있다. 안전한 경로로 전달한다.

```bash
# Member Cluster의 kubeconfig 생성
kubectl config view --minify --raw
```

출력 결과를 안전하게 저장하여 Host Cluster 운영자에게 전달한다. kubeconfig의 `server`가 DEV API VIP (`109.156.25.72:6443`)를 가리키는지 확인한다.

### 8.6. Host Web UI 절차 (5-2-3 참고)

실제 Join은 5-2-3 문서에서 수행하지만, 사전 절차 구조는 아래와 같다:

## 10. 장애 대응

| 증상 | 원인 | 조치 |
|------|------|------|
| `ImagePullBackOff` | DEV registry 접근 불가 또는 image URL 오류 | `kubectl describe pod -n kubesphere-system <pod>`로 image URL 확인. `xa.dcr.dks.samsungds.net/dspaas-cloud` registry 접근 확인. `imagePullSecret` 필요 시 생성 |
| `ClusterConfiguration` Pending / CC not found | CRD `clusterconfigurations.installer.kubesphere.io` 미등록 | `kubectl get crd \| grep installer` 확인. installer manifest 재적용 |
| `ks-installer` log task `failed` | CRD 타이밍, ServiceMonitor CRD 미준비 | installer pod 삭제로 재시도: `kubectl delete pod -n kubesphere-system <ks-installer-pod>` |
| PVC `Pending` | StorageClass 불일치, 용량 부족 | `kubectl describe pvc <pvc> -n kubesphere-system`. `storageClass` 이름이 `scs-netapp-qtree-nfs-sc-delete`와 일치하는지 확인 |
| External monitoring `prometheus-operated` Service 없음 | DKS Prometheus CR `k8s` 미기동 | `kubectl get prometheus -n monitoring`, `kubectl get svc -n monitoring prometheus-operated` |
| Pod가 infra node에 배치 안 됨 | node label/taint 불일치 | `kubectl get nodes -l node-type=infra` 조회, `kubectl describe node xadksirmd01 \| grep Taints` |
| JSON patch `tolerations/0` 오류 | tolerations 필드 구조 상이 | `kubectl get deploy <name> -n kubesphere-system -o jsonpath='{.spec.template.spec.tolerations}'`로 현재 상태 확인 후 `--type=merge`로 대체 |
| `ks-installer` 재시작으로 재설치 | 실수로 scale up 또는 pod 삭제 | `kubectl scale -n kubesphere-system deploy ks-installer --replicas=0` 즉시 실행. 설정이 초기화되었으면 4번부터 재적용 |
| `jwtSecret` 불일치 / `signature is invalid` | Host/Member JWT 불일치 | `ks-apiserver` rollout restart: `kubectl -n kubesphere-system rollout restart deploy ks-apiserver` |
| Console `30880` 접속 실패 | NodePort 방화벽 차단, LB 미등록 | `kubectl get svc -n kubesphere-system ks-console`, `netstat -tlnp \| grep 30880`, 방화벽/보안그룹 확인 |
| Cluster Agent `Pending` | Join 후 agent 이미지 pull 실패 | Host Cluster Web UI에서 agent Error 확인. 네트워크/registry 접근 확인 |
