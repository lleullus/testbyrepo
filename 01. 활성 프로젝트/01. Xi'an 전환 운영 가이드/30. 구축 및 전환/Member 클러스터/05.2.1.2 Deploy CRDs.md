# 05.2.1.2 Deploy CRDs

> **실행자**: DSPAAS
>
> **대상 클러스터**: `dev-apps-pa01-xas`
>
> **선행 단계**: [[05.2.1.1 Deploy preliminary components|5-2-1-1 Deploy preliminary components]]

DKS custom Prometheus stack이 사용하는 Prometheus Operator CRD를 먼저 등록합니다. KubeSphere 설치 전에 등록해야 이후 `Prometheus`, `Alertmanager`, `ServiceMonitor`, `PrometheusRule` 리소스를 인식할 수 있습니다.

## 1. CRD 파일 확인

```bash
cd ~/SCS_DKS_Kubernetes_Stack-v1.0/dks-prometheus-stack_v2.0/2.kube-prometheus-0.11.0/manifests/setup
ls -al
```

필수 CRD:

```text
0alertmanagerConfigCustomResourceDefinition.yaml
0alertmanagerCustomResourceDefinition.yaml
0podmonitorCustomResourceDefinition.yaml
0probeCustomResourceDefinition.yaml
0prometheusCustomResourceDefinition.yaml
0prometheusruleCustomResourceDefinition.yaml
0servicemonitorCustomResourceDefinition.yaml
0thanosrulerCustomResourceDefinition.yaml
```

## 2. 기존 CRD 확인

```bash
kubectl get crd | grep -E 'alertmanager|podmonitor|probe|prometheus|servicemonitor|thanosruler'
kubectl api-resources | grep monitoring.coreos.com
```

이미 같은 이름의 CRD가 있으면 삭제하지 않습니다. `kubectl apply`로 현재 bundle과의 차이를 확인하고, 다른 Operator가 관리하는 CRD인지 담당자 확인 후 진행합니다.

## 3. CRD 적용

```bash
kubectl apply \
  --server-side \
  --field-manager=prometheus-crd-installer \
  -f .
```

최초 적용에서는 `created`, 재적용에서는 `configured` 또는 `unchanged`가 출력될 수 있습니다. CRD는 OpenAPI 스키마가 커서 일반 Client-Side Apply를 사용하면 `metadata.annotations: Too long: must have at most 262144 bytes` 오류가 발생할 수 있습니다. Server-Side Apply는 전체 manifest를 `kubectl.kubernetes.io/last-applied-configuration` 어노테이션에 저장하지 않으므로 이 제한을 피할 수 있습니다.

`AlreadyExists`를 피하기 위해 운영 문서의 재실행 명령은 `create`가 아닌 Server-Side Apply를 사용합니다.

### 3-1. 필드 충돌 발생 시

이미 다른 field manager가 CRD 필드를 관리하고 있어 충돌이 발생하는 경우, 현재 CRD를 다른 Operator가 관리하는지 먼저 확인합니다.

```bash
kubectl get crd prometheuses.monitoring.coreos.com -o yaml \
  | grep -E 'managedFields|manager:'
```

현재 bundle을 적용하는 것이 맞고 담당자 확인이 끝난 경우에만 충돌 강제 옵션을 사용합니다.

```bash
kubectl apply \
  --server-side \
  --force-conflicts \
  --field-manager=prometheus-crd-installer \
  -f .
```

`kubectl annotate ... kubectl.kubernetes.io/last-applied-configuration-`로 어노테이션만 삭제하는 방식은 재발을 막지 못하므로 해결책으로 사용하지 않습니다.

### 3-2. Server-Side Apply 지원 여부

`kubectl apply --server-side`가 지원되지 않는 오래된 `kubectl`을 사용 중이면, 임의로 CRD를 삭제하지 말고 `kubectl` 버전을 먼저 업그레이드합니다. CRD 삭제는 해당 CRD로 생성된 Custom Resource를 함께 위험에 빠뜨릴 수 있습니다.

## 4. Established 상태 확인

```bash
for crd in \
  alertmanagerconfigs.monitoring.coreos.com \
  alertmanagers.monitoring.coreos.com \
  podmonitors.monitoring.coreos.com \
  probes.monitoring.coreos.com \
  prometheuses.monitoring.coreos.com \
  prometheusrules.monitoring.coreos.com \
  servicemonitors.monitoring.coreos.com \
  thanosrulers.monitoring.coreos.com; do
  kubectl wait --for=condition=Established "crd/$crd" --timeout=60s
done
```

전체 목록과 생성 시간을 확인합니다.

```bash
kubectl get crd | grep -E 'alertmanager|podmonitor|probe|prometheus|servicemonitor|thanosruler'
```

정상 기준:

- 8개 CRD가 모두 조회됨
- `Established=True`
- CRD의 API group이 `monitoring.coreos.com`
- 기존 CRD를 삭제하거나 다른 버전으로 강제 교체하지 않음

## 5. API 등록 검증

```bash
kubectl explain prometheus.spec --api-version=monitoring.coreos.com/v1
kubectl explain servicemonitor.spec --api-version=monitoring.coreos.com/v1
kubectl explain prometheusrule.spec --api-version=monitoring.coreos.com/v1
```

`the server doesn't have a resource type` 또는 `no matches for kind`가 나오면 다음 단계로 진행하지 않습니다. API server의 CRD 상태와 적용 파일을 다시 확인합니다.

## 완료 기준

- [ ] 8개 Prometheus Operator CRD 적용 완료
- [ ] 모든 CRD가 `Established`
- [ ] `monitoring.coreos.com/v1` API가 등록됨
- [ ] 기존 CRD 충돌/삭제 없이 현재 bundle과 호환성 확인
