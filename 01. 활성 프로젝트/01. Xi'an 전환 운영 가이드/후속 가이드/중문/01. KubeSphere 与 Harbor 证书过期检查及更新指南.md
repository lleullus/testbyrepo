## 2. 确认 Harbor 服务器及内部 T2 CA 证书过期时间

### 2-1. 确认 Harbor 服务器证书过期时间

在 Bastion 上查询 Harbor FQDN (`xa.dcr.dks.samsungds.net:443`) 当前对外服务证书的过期时间。

```console
[dspaas@xadksbtmp01 ~]$ openssl s_client -connect xa.dcr.dks.samsungds.net:443 -servername xa.dcr.dks.samsungds.net </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
subject= /CN=xa.dcr.dks.samsungds.net
issuer= /CN=SECDS-T2IssuingCA
notBefore=Aug 20 00:00:00 2025 GMT
notAfter=Aug 20 23:59:59 2027 GMT
```

### 2-2. 确认内部 T2 CA (Issuing CA / Root CA) 有效期

检查安装包目录下存放的内部 T2 CA 证书文件的过期时间。

```console
[dspaas@xadksbtmp01 ~]$ cd /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/
[dspaas@xadksbtmp01 SCS_DKS_Kubernetes_Stack-v1.0]$ openssl x509 -in SECDS-T2IssuingCA.crt -noout -subject -issuer -enddate
subject= /CN=SECDS-T2IssuingCA
issuer= /CN=SECDS-T2ROOTCA
notAfter=Dec 31 23:59:59 2034 GMT

[dspaas@xadksbtmp01 SCS_DKS_Kubernetes_Stack-v1.0]$ openssl x509 -in SECDS-T2ROOTCA.crt -noout -subject -issuer -enddate
subject= /CN=SECDS-T2ROOTCA
issuer= /CN=SECDS-T2ROOTCA
notAfter=Dec 31 23:59:59 2035 GMT
```

### 2-3. 确认 KubeSphere secds-t2-ca ConfigMap 有效期

查询 Member 集群的 `ks-apiserver` 在与 Harbor 通信时所使用的 ConfigMap 中的证书。

```console
[dspaas@xadksbtmp01 ~]$ kubectl get cm secds-t2-ca -n kubesphere-system -o go-template='{{index .data "ca.crt"}}' | openssl x509 -noout -subject -enddate
subject= /CN=SECDS-T2IssuingCA
notAfter=Dec 31 23:59:59 2034 GMT
```

## 3. 更换 Harbor 服务器证书并重启服务

当 Harbor 服务器证书临近过期时，需在内部安全门户重新申请域名 (`xa.dcr.dks.samsungds.net`) 证书。 
若从内部门户接收到 PFX 文件 (`dks.samsungds.net.pfx`)，请使用以下命令提取私钥与证书：

```console
[dspaas@xadksharbor01 ~]$ openssl pkcs12 -in "dks.samsungds.net.pfx" -nocerts -nodes -out "/tmp/xa.dcr.dks.samsungds.net.key"
[dspaas@xadksharbor01 ~]$ openssl pkcs12 -in "dks.samsungds.net.pfx" -clcerts -nokeys -out "/tmp/xa.dcr.dks.samsungds.net.crt"
```

新文件 (`xa.dcr.dks.samsungds.net.crt`, `xa.dcr.dks.samsungds.net.key`) 准备就绪后，应用至 Harbor 服务器 (`xadksharbor01`)。

### 3-1. 验证新证书与私钥

生效前，确认 SAN 域名以及 Modulus 是否一致。

```console
[dspaas@xadksharbor01 ~]$ openssl x509 -in /tmp/xa.dcr.dks.samsungds.net.crt -noout -text | grep -A1 "Subject Alternative Name"
            X509v3 Subject Alternative Name: 
                DNS:xa.dcr.dks.samsungds.net

[dspaas@xadksharbor01 ~]$ openssl x509 -noout -modulus -in /tmp/xa.dcr.dks.samsungds.net.crt | openssl md5
(stdin)= a1b2c3d4e5f60718293a4b5c6d7e8f90

[dspaas@xadksharbor01 ~]$ openssl rsa -noout -modulus -in /tmp/xa.dcr.dks.samsungds.net.key | openssl md5
(stdin)= a1b2c3d4e5f60718293a4b5c6d7e8f90
```

确认两个 MD5 输出值完全一致。

## 4. 内部 CA 变更时同步 Harbor、Worker 节点及 KubeSphere

当内部 CA (Root CA 或 Issuing CA) 更换为新证书时，必须同步更新 Harbor 服务器自身（用于 LDAP/外部通信）的操作系统 CA 信任、各 Worker 节点的操作系统 CA 信任，以及 KubeSphere `ks-apiserver` 的 ConfigMap。

### 4-1. 更新 Harbor 服务器系统 CA 信任

由于 Harbor 需要与内部 Global AD (LDAP) 进行身份验证通信并与上游镜像仓库同步，因此必须在 Harbor 宿主机系统 (`xadksharbor01`) 中注册新 CA。

```console
[dspaas@xadksbtmp01 ~]$ ssh xadksharbor01
[dspaas@xadksharbor01 ~]$ sudo cp /tmp/SECDS-T2IssuingCA.crt /etc/pki/ca-trust/source/anchors/
[dspaas@xadksharbor01 ~]$ sudo cp /tmp/SECDS-T2ROOTCA.crt /etc/pki/ca-trust/source/anchors/
[dspaas@xadksharbor01 ~]$ sudo update-ca-trust extract
[dspaas@xadksharbor01 ~]$ sudo systemctl restart docker
[dspaas@xadksharbor01 ~]$ sudo systemctl is-active docker
active
[dspaas@xadksharbor01 ~]$ exit
```

### 4-2. 更新 Worker 节点系统 CA 信任

将新 CA 复制到各 Worker 节点并更新系统信任库 (Trust Store)。

```console
[dspaas@xadksbtmp01 ~]$ ssh xadkswkmp01
[dspaas@xadkswkmp01 ~]$ sudo cp /tmp/SECDS-T2IssuingCA.crt /etc/pki/ca-trust/source/anchors/
[dspaas@xadkswkmp01 ~]$ sudo cp /tmp/SECDS-T2ROOTCA.crt /etc/pki/ca-trust/source/anchors/
[dspaas@xadkswkmp01 ~]$ sudo update-ca-trust extract
[dspaas@xadkswkmp01 ~]$ sudo systemctl restart containerd
[dspaas@xadkswkmp01 ~]$ sudo systemctl is-active containerd
active
[dspaas@xadkswkmp01 ~]$ exit
```

### 4-3. 更新 KubeSphere ks-apiserver CA ConfigMap

在 Member 集群的 Bastion 上，使用新的 CA Bundle 重新创建 `kubesphere-system` 命名空间下的 `secds-t2-ca` ConfigMap，并重启 `ks-apiserver`。

```console
[dspaas@xadksbtmp01 ~]$ cat SECDS-T2IssuingCA.crt SECDS-T2ROOTCA.crt > /tmp/secds-t2-bundle.crt

[dspaas@xadksbtmp01 ~]$ kubectl create configmap secds-t2-ca \
  --from-file=ca.crt=/tmp/secds-t2-bundle.crt \
  -n kubesphere-system \
  --dry-run=client -o yaml | kubectl apply -f -
configmap/secds-t2-ca configured

[dspaas@xadksbtmp01 ~]$ kubectl rollout restart deployment ks-apiserver -n kubesphere-system
deployment.apps/ks-apiserver restarted

[dspaas@xadksbtmp01 ~]$ kubectl rollout status deployment ks-apiserver -n kubesphere-system
Waiting for deployment "ks-apiserver" rollout to finish: 1 old replicas are pending termination...
Waiting for deployment "ks-apiserver" rollout to finish: 1 old replicas are pending termination...
deployment "ks-apiserver" successfully rolled out
```

## 5. 依次更新 Kubernetes 控制平面证书

为了保证控制平面的高可用性，Master 节点必须按顺序逐台进行更新（`ma01` → `ma02` → `ma03`）。在前一台节点的 Pod 正常启动且健康检查通过之前，严禁进入下一台节点的更新操作。

### 5-1. 备份所有 Master 节点

在 Bastion 上备份 3 台 Master 节点的 `/etc/kubernetes/ssl` 目录及配置文件。

```console
[dspaas@xadksbtmp01 ~]$ for host in xadksmamp01 xadksmamp02 xadksmamp03; do
  echo "===== Backing up $host ====="
  ssh $host "sudo mkdir -p /tmp/$(date +%Y%m%d)-apibackup && \
             sudo cp -rp /etc/kubernetes/ssl /tmp/$(date +%Y%m%d)-apibackup/ && \
             sudo cp -rp /etc/kubernetes/*.conf /tmp/$(date +%Y%m%d)-apibackup/"
done
===== Backing up xadksmamp01 =====
===== Backing up xadksmamp02 =====
===== Backing up xadksmamp03 =====

[dspaas@xadksbtmp01 ~]$ ssh xadksmamp01 sudo ls -l /tmp/$(date +%Y%m%d)-apibackup/
total 24
-rw-------. 1 root root 5621 Sep  7 10:30 admin.conf

-rw-------. 1 root root 5621 Sep  7 10:30 scheduler.conf
drwxr-xr-x. 3 root root 4096 Sep  7 10:30 ssl
```

### 6-2. 重新连接 KubeSphere 成员集群

由于 Kubernetes API Server 的客户端证书已更新，需在 KubeSphere Host 集群中解绑 (Unbind) 原 Member 集群，并使用新 kubeconfig 重新导入 (Import)。

1. **登录 Host 集群 Web 控制台**:
   - 访问 `https://xa.ks.dks.samsungds.net/`
   - 进入 **Platform** → **Cluster Management** 菜单
2. **解绑成员集群 (Member Cluster Unbind)**:
   - 选择目标 Member 集群（`dev-apps-pa01-xas` 或 `prd-apps-pa01-xas`）
   - 点击 **Cluster Settings** → **Basic Information** → **Unbind Cluster**
   - 确认界面显示的 Cluster Name 与 Cluster Tag，勾选确认框后执行 Unbind
3. **重新导入成员集群 (Member Cluster Re-import)**:
   - 在 **Cluster Management** 页面点击 **Add Cluster**
   - 输入相同的 Cluster Name 与 Cluster Tag
   - 复制 Bastion 节点 `~/.kube/config` 的全部内容并粘贴至 kubeconfig 输入框中
   - 点击 **Create** 完成注册
4. **重启 KubeSphere 系统组件**:
   在 Bastion 上重启 Member 集群的系统 Pod：


## 7. 故障时回滚

若证书更新后 API Server 无法启动或静态 Pod 启动失败，使用预先备份的文件进行恢复。

```console
[dspaas@xadksbtmp01 ~]$ ssh xadksmamp01
[dspaas@xadksmamp01 ~]$ sudo rm -rf /etc/kubernetes/ssl
[dspaas@xadksmamp01 ~]$ sudo cp -rp /tmp/20260907-apibackup/ssl /etc/kubernetes/
[dspaas@xadksmamp01 ~]$ sudo cp -p /tmp/20260907-apibackup/*.conf /etc/kubernetes/
[dspaas@xadksmamp01 ~]$ sudo cp -p /etc/kubernetes/admin.conf /root/.kube/config
[dspaas@xadksmamp01 ~]$ sudo /usr/local/bin/crictl pods --namespace kube-system | grep -E "(kube-scheduler|kube-controller-manager|kube-apiserver)" | awk '{print $1}' | xargs -r sudo /usr/local/bin/crictl rmp -f
[dspaas@xadksmamp01 ~]$ curl -sk https://localhost:6443/readyz
ok
[dspaas@xadksmamp01 ~]$ exit
```
