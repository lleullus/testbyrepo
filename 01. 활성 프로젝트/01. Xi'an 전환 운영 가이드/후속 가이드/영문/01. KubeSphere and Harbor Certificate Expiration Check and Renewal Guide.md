# KubeSphere and Harbor Certificate Expiration Check and Renewal Guide

## Index

1. **Check Kubernetes Control Plane certificate expiration**
2. **Check Harbor server and internal T2 CA certificate expiration**
   - 2-1. Check Harbor server certificate expiration
   - 2-2. Check internal T2 CA (Issuing CA / Root CA) validity
   - 2-3. Check KubeSphere secds-t2-ca ConfigMap validity
3. **Replace Harbor server certificate and restart services**
   - 3-1. Validate new certificate and private key
   - 3-2. Replace certificate files and restart Harbor
   - 3-3. Verify normal Harbor operation
4. **Synchronize Harbor, Worker nodes, and KubeSphere upon internal CA change**
   - 4-1. Update Harbor server OS CA trust
   - 4-2. Update Worker node OS CA trust
   - 4-3. Update KubeSphere ks-apiserver CA ConfigMap
5. **Renew Kubernetes Control Plane certificates sequentially**
   - 5-1. Back up all Master nodes
   - 5-2. Renew Master Node 01
   - 5-3. Renew Master Node 02
   - 5-4. Renew Master Node 03
6. **Update Bastion kubeconfig and re-connect KubeSphere**
   - 6-1. Replace Bastion Node kubeconfig
   - 6-2. Re-connect KubeSphere Member Cluster
7. **Rollback upon failure**

## 2. Check Harbor Server and Internal T2 CA Certificate Expiration

### 2-1. Check Harbor Server Certificate Expiration

From the Bastion, establish a TLS connection to the Harbor FQDN (xa.dcr.dks.samsungds.net:443) to check the expiration date of the active service certificate.

```console
[dspaas@xadksbtmp01 ~]$ openssl s_client -connect xa.dcr.dks.samsungds.net:443 -servername xa.dcr.dks.samsungds.net </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
subject= /CN=xa.dcr.dks.samsungds.net
issuer= /CN=SECDS-T2IssuingCA
notBefore=Aug 20 00:00:00 2025 GMT
notAfter=Aug 20 23:59:59 2027 GMT
```

### 2-2. Check Internal T2 CA (Issuing CA / Root CA) Validity

Check the expiration dates of the internal T2 CA certificate files stored in the package directory.

```console
[dspaas@xadksbtmp01 ~]$ cd /app/dspaas/SCS_DKS_Kubernetes_Stack-v1.0/
[dspaas@xadksbtmp01 SCS_DKS_Kubernetes_Stack-v1.0]$ openssl x509 -in SECDS-T2IssuingCA.crt -noout -subject -issuer -enddate
subject= /CN=SECDS-T2IssuingCA
issuer= /CN=SECDS-T2ROOTCA
notAfter=Dec 31 23:59:59 2034 GMT

[dspaas@xadksbtmp01 SCS_DKS_Kubernetes_Stack-v1.0]$ openssl x509 -in SECDS-T2ROOTCA.crt -noout -subject -issuer -enddate
subject= /CN=SECDS-T2ROOTCA
issuer= /CN=SECDS-T2ROOTCA
notAfter=Dec 31 23:59:59 2035 GMT
```

### 2-3. Check KubeSphere secds-t2-ca ConfigMap Validity

Check the certificate contained in the ConfigMap used by ks-apiserver in the Member Cluster when communicating with Harbor.

```console

subject= /CN=SECDS-T2IssuingCA
notAfter=Dec 31 23:59:59 2034 GMT
```

## 3. Replace Harbor Server Certificate and Restart Services

When the Harbor server certificate has been renewed and new files (xa.dcr.dks.samsungds.net.crt, xa.dcr.dks.samsungds.net.key) are provided, apply them to the Harbor server (xadksharbor01).

### 3-1. Validate New Certificate and Private Key

Before applying, verify the SAN domain and ensure the modulus matches between certificate and key.

```console
[dspaas@xadksharbor01 ~]$ openssl x509 -in /tmp/xa.dcr.dks.samsungds.net.crt -noout -text | grep -A1 "Subject Alternative Name"

                DNS:xa.dcr.dks.samsungds.net

[dspaas@xadksharbor01 ~]$ openssl x509 -noout -modulus -in /tmp/xa.dcr.dks.samsungds.net.crt | openssl md5
(stdin)= a1b2c3d4e5f60718293a4b5c6d7e8f90

[dspaas@xadksharbor01 ~]$ openssl rsa -noout -modulus -in /tmp/xa.dcr.dks.samsungds.net.key | openssl md5
(stdin)= a1b2c3d4e5f60718293a4b5c6d7e8f90
```

Verify that both MD5 values match.

## 4. Synchronize Harbor, Worker Nodes, and KubeSphere upon Internal CA Change

When the internal CA (Root CA or Issuing CA) is replaced, update the OS trust on Harbor for LDAP and outbound communication, update the Worker node OS trust, and recreate the ConfigMap for KubeSphere ks-apiserver.

### 4-1. Update Harbor Server OS CA Trust

Because Harbor communicates with Global AD (LDAP) and performs upstream registry synchronization, the Harbor host OS (xadksharbor01) must also register the new CA.

```console
[dspaas@xadksbtmp01 ~]$ ssh xadksharbor01
[dspaas@xadksharbor01 ~]$ sudo cp /tmp/SECDS-T2IssuingCA.crt /etc/pki/ca-trust/source/anchors/
[dspaas@xadksharbor01 ~]$ sudo cp /tmp/SECDS-T2ROOTCA.crt /etc/pki/ca-trust/source/anchors/
[dspaas@xadksharbor01 ~]$ sudo update-ca-trust extract
[dspaas@xadksharbor01 ~]$ sudo systemctl restart docker
[dspaas@xadksharbor01 ~]$ sudo systemctl is-active docker
active
[dspaas@xadksharbor01 ~]$ exit
```

### 4-2. Update Worker Node OS CA Trust

Copy the new CA to each Worker node and update the system trust store.

```console
[dspaas@xadksbtmp01 ~]$ ssh xadkswkmp01
[dspaas@xadkswkmp01 ~]$ sudo cp /tmp/SECDS-T2IssuingCA.crt /etc/pki/ca-trust/source/anchors/
[dspaas@xadkswkmp01 ~]$ sudo cp /tmp/SECDS-T2ROOTCA.crt /etc/pki/ca-trust/source/anchors/
[dspaas@xadkswkmp01 ~]$ sudo update-ca-trust extract
[dspaas@xadkswkmp01 ~]$ sudo systemctl restart containerd
[dspaas@xadkswkmp01 ~]$ sudo systemctl is-active containerd
active
[dspaas@xadkswkmp01 ~]$ exit
```

### 4-3. Update KubeSphere ks-apiserver CA ConfigMap

From the Bastion of the Member Cluster, recreate the secds-t2-ca ConfigMap in the kubesphere-system namespace with the new bundle and restart ks-apiserver.

```console
[dspaas@xadksbtmp01 ~]$ cat SECDS-T2IssuingCA.crt SECDS-T2ROOTCA.crt > /tmp/secds-t2-bundle.crt

[dspaas@xadksbtmp01 ~]$ kubectl create configmap secds-t2-ca \
  --from-file=ca.crt=/tmp/secds-t2-bundle.crt \
  -n kubesphere-system \
  --dry-run=client -o yaml | kubectl apply -f -
configmap/secds-t2-ca configured

[dspaas@xadksbtmp01 ~]$ kubectl rollout restart deployment ks-apiserver -n kubesphere-system
deployment.apps/ks-apiserver restarted

[dspaas@xadksbtmp01 ~]$ kubectl rollout status deployment ks-apiserver -n kubesphere-system
```

## 5. Renew Kubernetes Control Plane Certificates Sequentially

To ensure Control Plane availability, renew Master nodes sequentially one by one (ma01 → ma02 → ma03). Do not proceed to the next node until pods on the current node are running and health checks pass.

### 5-1. Back Up All Master Nodes

From the Bastion, back up the /etc/kubernetes/ssl directory and configuration files on all three Master nodes.

```console
[dspaas@xadksbtmp01 ~]$ for host in xadksmamp01 xadksmamp02 xadksmamp03; do
  echo "===== Backing up $host ====="
  ssh $host "sudo mkdir -p /tmp/$(date +%Y%m%d)-apibackup && \
             sudo cp -rp /etc/kubernetes/ssl /tmp/$(date +%Y%m%d)-apibackup/ && \
             sudo cp -rp /etc/kubernetes/*.conf /tmp/$(date +%Y%m%d)-apibackup/"
done
===== Backing up xadksmamp01 =====
===== Backing up xadksmamp02 =====
===== Backing up xadksmamp03 =====

[dspaas@xadksbtmp01 ~]$ ssh xadksmamp01 sudo ls -l /tmp/$(date +%Y%m%d)-apibackup/
```

### 6-2. Re-connect KubeSphere Member Cluster

Since the Kubernetes API Server client certificate was renewed, unbind the existing Member cluster connection in the KubeSphere Host Cluster and re-import it using the updated kubeconfig.

1. **Log in to Host Cluster Web Console**:
   - Navigate to `https://xa.ks.dks.samsungds.net/`
   - Go to **Platform** → **Cluster Management**
2. **Unbind Member Cluster**:
   - Select the target Member Cluster (dev-apps-pa01-xas or prd-apps-pa01-xas)
   - Click **Cluster Settings** → **Basic Information** → **Unbind Cluster**
   - Check the Cluster Name and Cluster Tag displayed on screen, select the confirmation checkbox, and execute Unbind
3. **Re-import Member Cluster**:
   - Click **Add Cluster** on the **Cluster Management** page
   - Enter the exact same Cluster Name and Cluster Tag
   - Copy the entire contents of Bastion's `~/.kube/config` and paste into the kubeconfig field
   - Click **Create** to complete cluster registration
4. **Restart KubeSphere System Components**:
   From the Bastion, restart the system pods in the Member cluster.

```console
[dspaas@xadksbtmp01 ~]$ kubectl rollout restart deploy -n kubesphere-system ks-apiserver ks-console ks-controller-manager
```

Verify that the target Member Cluster status transitions to Active in the Host Console's Cluster Management.

## 7. Rollback upon Failure

If the API Server fails to start or static pod startup fails after certificate renewal, restore from the backup taken prior to the change.
