# Prometheus and Grafana Usage and Configuration Reference Guide

## Index

The Xi'an DKS environment uses `kube-prometheus-stack` based on the Prometheus Operator to collect and store cluster and application metrics, visualizing them via Grafana dashboards. This guide provides an operational reference for adding metric scrape targets, querying failure indicators with PromQL, and configuring Grafana dashboards and Alertmanager alerting rules.

Procedures and learning paths are structured in the following order:

1. **Verify DKS monitoring stack architecture and status**
2. **Configure new metric collection via `ServiceMonitor`**
3. **Core operational PromQL queries and terminal API lookups**
4. **Inspect Grafana dashboards and configure custom panels**
5. **Set custom alert rules using `PrometheusRule`**
6. **Troubleshooting terminal workflow (Handling Targets Down)**
7. **Official documentation references and learning resources**

---

## 2. Configuring New Metric Collection via ServiceMonitor

In the Prometheus Operator environment, instead of directly editing configuration files, create a `ServiceMonitor` custom resource to dynamically register target services.

### 2-1. Checking Application Service Labels

Verify that matching labels are configured on the Service object exposing metrics.

```console
[dspaas@xadksbtmp01 ~]$ kubectl get svc -n hello-kubesphere-dev nginx-metrics --show-labels
NAME            TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)    AGE   LABELS
nginx-metrics   ClusterIP   10.233.54.120   <none>        9113/TCP   2d    app=nginx,release=dks-kube-prometheus-stack
```

### 2-2. Creating and Deploying ServiceMonitor Manifest

The `release: dks-kube-prometheus-stack` label is required for the Prometheus Operator to discover the ServiceMonitor.

```console
[dspaas@xadksbtmp01 ~]$ cat <<EOF > /tmp/nginx-servicemonitor.yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: nginx-metrics-monitor
  namespace: hello-kubesphere-dev
  labels:
    release: dks-kube-prometheus-stack
spec:
  selector:
    matchLabels:
      app: nginx
  endpoints:
  - port: metrics
    interval: 15s
    path: /metrics
EOF

[dspaas@xadksbtmp01 ~]$ kubectl apply -f /tmp/nginx-servicemonitor.yaml
servicemonitor.monitoring.coreos.com/nginx-metrics-monitor created

[dspaas@xadksbtmp01 ~]$ kubectl get servicemonitor -n hello-kubesphere-dev
NAME                    AGE
nginx-metrics-monitor   10s
```

## 3. Core Operational PromQL Queries and Terminal API Lookups

The following queries represent the most common resource verification queries. From the Bastion, query the local Prometheus service via `curl` to directly check metrics from the terminal.

### 3-1. Core PromQL Cheatsheet

| Monitored Target | PromQL Expression | Description |
|---|---|---|
| **CPU Usage per Node** | `(1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))) * 100` | CPU utilization excluding idle time over the last 5 minutes (%) |
| **Memory Usage per Node** | `(1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) * 100` | Memory usage percentage calculated from available memory (%) |
| **Pod CPU Usage** | `sum by (pod, namespace) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))` | Core consumption per pod and namespace |
| **Pod Memory Usage (Working Set)** | `sum by (pod, namespace) (container_memory_working_set_bytes{container!=""}) / 1024 / 1024` | Working set memory used for OOM-kill decisions (in MB) |
| **Node Disk Usage** | `(1 - (node_filesystem_free_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"})) * 100` | Root mount ('/') filesystem usage (%) |
| **Pod Restarts in Last 1 Hour** | `sum by (pod, namespace) (increase(kube_pod_container_status_restarts_total[1h])) > 0` | Identify pods that experienced restarts within the past hour |

## 4. Inspecting Grafana Dashboards and Configuring Custom Panels

Grafana visualizes collected time-series metrics through web dashboards.

### 4-1. Grafana Access and Credentials

- **Access URL**: `https://xa.grafana.dks.samsungds.net/` (or configured Ingress FQDN)
- **Default Admin Account**: `admin`
- **Retrieve Password**:
  ```console
  [dspaas@xadksbtmp01 ~]$ kubectl get secret -n monitoring dks-kube-prometheus-stack-grafana -o jsonpath='{.data.admin-password}' | base64 -d
  prom-operator-admin
  ```

### 4-2. Importing Standard Dashboards
1. In Grafana left menu, select **Dashboards** → **Import**
2. Enter the official Grafana Dashboard ID and click **Load**:
   - `315`: Kubernetes Cluster Monitoring (Cluster-wide overview)
   - `6417`: Kubernetes Pod Monitoring (Detailed per-namespace/pod view)
   - `1860`: Node Exporter Full (Comprehensive node OS and hardware view)
3. Select the **Prometheus data source** and complete the **Import**

## 5. Setting Custom Alert Rules using PrometheusRule

Declare alert thresholds in a `PrometheusRule` resource for early incident detection.

```console
[dspaas@xadksbtmp01 ~]$ cat <<EOF > /tmp/custom-alert-rules.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: dks-custom-alerts
  namespace: monitoring
  labels:
    release: dks-kube-prometheus-stack
spec:
  groups:
  - name: node-resource-alerts
    rules:
    - alert: HostHighCpuUsage
      expr: (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))) * 100 > 85
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Host CPU usage is above 85% (instance {{ \$labels.instance }})"
        description: "CPU load on instance {{ \$labels.instance }} has exceeded 85% for 5 minutes."
    - alert: HostOutOfMemory
      expr: (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) * 100 > 90
      for: 3m
      labels:
        severity: critical
      annotations:
        summary: "Host out of memory (instance {{ \$labels.instance }})"
        description: "Available memory on {{ \$labels.instance }} is below 10%."
EOF

[dspaas@xadksbtmp01 ~]$ kubectl apply -f /tmp/custom-alert-rules.yaml
prometheusrule.monitoring.coreos.com/dks-custom-alerts created

[dspaas@xadksbtmp01 ~]$ kubectl get prometheusrule -n monitoring dks-custom-alerts
NAME                AGE
dks-custom-alerts   8s
```

## 6. Troubleshooting Terminal Workflow (Handling Targets Down)

Diagnosis sequence when component scraping fails (`up == 0`):

```console
# 1) Identify downed scraping targets
[dspaas@xadksbtmp01 ~]$ curl -s "http://${PROM_IP}:9090/api/v1/query?query=up==0" | jq '.data.result[] | {job: .metric.job, instance: .metric.instance}'
{
  "job": "nginx-metrics",
  "instance": "10.233.112.45:9113"
}

# 2) Test endpoint port and responsiveness of the pod directly
[dspaas@xadksbtmp01 ~]$ curl -s -m 3 http://10.233.112.45:9113/metrics | head -n 5
# HELP nginx_connections_active Active client connections
# TYPE nginx_connections_active gauge
nginx_connections_active 2
# HELP nginx_connections_reading An aggregating gauge of connections where nginx is reading the request header.
# TYPE nginx_connections_reading gauge
nginx_connections_reading 0

# 3) Check port name mismatch between ServiceMonitor and Service definition
[dspaas@xadksbtmp01 ~]$ kubectl get svc -n hello-kubesphere-dev nginx-metrics -o jsonpath='{.spec.ports[*].name}'
metrics
```

If scraping fails due to port naming or label selector mismatch, adjust `spec.endpoints.port` in the `ServiceMonitor` to match `ports[].name` in the target Service.
