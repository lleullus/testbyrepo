# User kubeconfig Handling Guide for KubeSphere Certificate Renewal

## Index

During Kubernetes Control Plane and KubeSphere certificate renewal operations, this procedure determines the impact on and handles the `kubectl` CLI environment (`~/.kube/config`) used by general users on Bastion nodes.

The procedure is performed in the following order:

1. **Verify target kubeconfig types and management principles**
2. **Check user Client Certificate validity**
3. **Assess impact when only Control Plane certificates are renewed**
4. **Reissue and apply when user Client Certificate expires**
5. **Update user kubeconfig upon Kubernetes CA replacement**
6. **Verify `kubectl` authentication and RBAC permissions per user account**

---

## 1. Target kubeconfig Types and Management Principles

In the Xi'an DKS environment, kubeconfig files are strictly separated and managed based on their purpose and issuing authority.

```console
[dspaas@xadksbtmp01 ~]$ ls -l /etc/kubernetes/admin.conf ~/.kube/config /home/*/.kube/config 2>/dev/null
-rw-------. 1 root   root   5621 Sep  7 10:30 /etc/kubernetes/admin.conf
-rw-------. 1 dspaas dspaas 5621 Sep  7 10:45 /app/dspaas/.kube/config
-rw-------. 1 dshl14314.id dshl14314.id 4892 Jun 19 14:20 /home/dshl14314.id/.kube/config
```

### Essential Management Principles
1. **Strictly Prohibit Distributing `admin.conf` to Users**: `admin.conf` contains `system:masters` superuser privileges and must never be provided or overwritten for general users.
2. **Separation of Renewal Scope**: Control Plane certificates renewed via `kubeadm certs renew all` and individual user Client Certificates are distinct authentication credentials.
3. **Principle of Minimal Changes**: When the Kubernetes CA is retained and the user's Client Certificate remains valid, general user kubeconfigs must not be modified or redistributed.

---

## 2. Checking User Client Certificate Validity

Extract `client-certificate-data` from the user account's `~/.kube/config` or the ConfigMap generated by KubeSphere to check the actual expiration date.

### 2-1. Checking Expiration in User Local ~/.kube/config

On the Bastion node, verify the certificate expiration for a specific user (e.g., `dshl14314.id`).

```console
[dspaas@xadksbtmp01 ~]$ sudo cat /home/dshl14314.id/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -subject -issuer -dates
subject= /O=users/CN=dshl14314.id
issuer= /CN=kubernetes
notBefore=Jun 19 05:20:00 2026 GMT
notAfter=Jun 19 05:20:00 2027 GMT
```

### 2-2. Checking Expiration in KubeSphere ConfigMap

Check the expiration date from the user ConfigMap managed by KubeSphere in the `kubesphere-controls-system` namespace.

```console
[dspaas@xadksbtmp01 ~]$ kubectl get configmaps -n kubesphere-controls-system | grep kubeconfig-dshl14314.id
kubeconfig-dshl14314.id   1      80d

[dspaas@xadksbtmp01 ~]$ kubectl get configmap kubeconfig-dshl14314.id -n kubesphere-controls-system -o jsonpath='{.data.config}' \
  | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -subject -enddate
subject= /O=users/CN=dshl14314.id
notAfter=Jun 19 05:20:00 2027 GMT
```

## 3. Assessing Impact when Only Control Plane Certificates are Renewed

When `kubeadm certs renew all` is executed on Master nodes and only API Server certificates are renewed, **if the Kubernetes Root CA (`/etc/kubernetes/ssl/ca.crt`) has not changed, general user kubeconfigs do not need replacement.**

### 3-1. Verifying CA Match

Verify that the API Server CA and the user kubeconfig CA are identical.

```console
[dspaas@xadksbtmp01 ~]$ openssl x509 -in /etc/kubernetes/ssl/ca.crt -noout -serial
serial=00

[dspaas@xadksbtmp01 ~]$ sudo cat /home/dshl14314.id/.kube/config | grep certificate-authority-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -serial
serial=00
```

If both serial numbers match and the user's Client Certificate has remaining validity, keep the user settings as they are.

### 3-2. User Session Normal Communication Test

Switch to the user account and verify that `kubectl` queries operate normally.

```console
[dspaas@xadksbtmp01 ~]$ sudo su - dshl14314.id
[dshl14314.id@xadksbtmp01 ~]$ kubectl get pods
NAME                          READY   STATUS    RESTARTS   AGE
nginx-test-6f7c8d9b6d-7k2pm   1/1     Running   0          5d

[dshl14314.id@xadksbtmp01 ~]$ kubectl auth can-i create deployments
yes
[dshl14314.id@xadksbtmp01 ~]$ exit
```

## 4. Reissuing and Applying when User Client Certificate Expires

When a user's Client Certificate has expired or has been reissued in the KubeSphere console, extract the new kubeconfig and deploy it to the user's directory.

### 4-1. Extracting New kubeconfig from KubeSphere ConfigMap

From the Bastion administrator (`dspaas`) account, extract the configuration from the KubeSphere ConfigMap.

```console
[dspaas@xadksbtmp01 ~]$ mkdir -p /tmp/kubeconfig-renew && cd /tmp/kubeconfig-renew
[dspaas@xadksbtmp01 kubeconfig-renew]$ kubectl get configmap kubeconfig-dshl14314.id -n kubesphere-controls-system -o jsonpath='{.data.config}' > config.raw
[dspaas@xadksbtmp01 kubeconfig-renew]$ head -n 15 config.raw
apiVersion: v1
clusters:
- cluster:
    certificate-authority-data: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0t...
    server: https://109.156.25.57:6443
  name: local
contexts:
- context:
    cluster: local
    namespace: default
    user: dshl14314.id
  name: dshl14314.id@local
current-context: dshl14314.id@local
kind: Config
preferences: {}
users:
- name: dshl14314.id
...
```

### 4-2. Modifying Cluster Endpoint and Context

Replace the default `local` server address generated by KubeSphere with the actual target cluster's VIP-A address and cluster name.

```console
[dspaas@xadksbtmp01 kubeconfig-renew]$ cp config.raw config
[dspaas@xadksbtmp01 kubeconfig-renew]$ sed -i 's|https://109.156.25.57:6443|https://10.166.202.239:6443|g' config
[dspaas@xadksbtmp01 kubeconfig-renew]$ sed -i 's|name: local|name: prd-apps-pa01-xas|g' config
[dspaas@xadksbtmp01 kubeconfig-renew]$ sed -i 's|cluster: local|cluster: prd-apps-pa01-xas|g' config
[dspaas@xadksbtmp01 kubeconfig-renew]$ sed -i 's|name: dshl14314.id@local|name: dshl14314.id@prd-apps-pa01-xas|g' config
[dspaas@xadksbtmp01 kubeconfig-renew]$ sed -i 's|current-context: dshl14314.id@local|current-context: dshl14314.id@prd-apps-pa01-xas|g' config

[dspaas@xadksbtmp01 kubeconfig-renew]$ grep -E "(server:|name:|current-context:)" config
    server: https://10.166.202.239:6443
  name: prd-apps-pa01-xas
  name: dshl14314.id@prd-apps-pa01-xas
current-context: dshl14314.id@prd-apps-pa01-xas
- name: dshl14314.id
```

### 4-3. Deploying New kubeconfig to User Account

Back up the existing configuration, place the new file, and restrict file permissions to `600`.

```console
[dspaas@xadksbtmp01 kubeconfig-renew]$ sudo cp -p /home/dshl14314.id/.kube/config /home/dshl14314.id/.kube/config.bak_$(date +%Y%m%d)
[dspaas@xadksbtmp01 kubeconfig-renew]$ sudo cp config /home/dshl14314.id/.kube/config
[dspaas@xadksbtmp01 kubeconfig-renew]$ sudo chown dshl14314.id:dshl14314.id /home/dshl14314.id/.kube/config
[dspaas@xadksbtmp01 kubeconfig-renew]$ sudo chmod 600 /home/dshl14314.id/.kube/config

[dspaas@xadksbtmp01 kubeconfig-renew]$ sudo ls -l /home/dshl14314.id/.kube/
total 12
-rw-------. 1 dshl14314.id dshl14314.id 4915 Sep  7 11:10 config
-rw-------. 1 dshl14314.id dshl14314.id 4892 Jun 19 14:20 config.bak_20260907
```

## 5. Updating User kubeconfig upon Kubernetes CA Replacement

When the Kubernetes cluster Root CA itself is renewed or reissued, the existing `certificate-authority-data` and `client-certificate-data` of all users become invalid, requiring an update for all users.

### 5-1. Applying New CA Data

In an environment where a new CA has been applied, KubeSphere reconstructs the user ConfigMap based on the new CA.

```console
[dspaas@xadksbtmp01 ~]$ sudo cat /home/dshl14314.id/.kube/config | grep certificate-authority-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -enddate
notAfter=Jun 17 06:12:00 2036 GMT

[dspaas@xadksbtmp01 ~]$ sudo cat /home/dshl14314.id/.kube/config | grep client-certificate-data: | awk '{print $2}' | base64 -d | openssl x509 -noout -enddate
notAfter=Sep  7 11:05:00 2027 GMT
```

## 6. Verifying kubectl Authentication and RBAC Permissions per User Account

After replacing the kubeconfig, verify that API Server authentication and existing RBAC permissions function normally in the user session.

### 6-1. Checking Permissions and Namespace Access

```console
[dspaas@xadksbtmp01 ~]$ sudo su - dshl14314.id
[dshl14314.id@xadksbtmp01 ~]$ kubectl config current-context
dshl14314.id@prd-apps-pa01-xas

[dshl14314.id@xadksbtmp01 ~]$ kubectl auth can-i create pods -n default
yes

[dshl14314.id@xadksbtmp01 ~]$ kubectl auth can-i get nodes
no

[dshl14314.id@xadksbtmp01 ~]$ kubectl get pods -n default
NAME                     READY   STATUS    RESTARTS   AGE
web-app-85f9565b5-4t9lk   1/1     Running   0          3d

[dshl14314.id@xadksbtmp01 ~]$ exit
```

**Verification Criteria**:
- `kubectl config current-context` outputs the target cluster name.
- Resource creation/query permissions for the authorized namespace work normally.
- Cluster-wide permissions (e.g., `get nodes`) correctly return `no` and are restricted, without granting unnecessary access (`yes`).

---

## 7. Rollback Procedure

If authentication fails (`Unauthorized`) or connection errors occur after applying the new kubeconfig, immediately revert to the backup file.

```console
[dspaas@xadksbtmp01 ~]$ sudo cp -p /home/dshl14314.id/.kube/config.bak_20260907 /home/dshl14314.id/.kube/config
[dspaas@xadksbtmp01 ~]$ sudo chown dshl14314.id:dshl14314.id /home/dshl14314.id/.kube/config
[dspaas@xadksbtmp01 ~]$ sudo su - dshl14314.id -c "kubectl get pods"
NAME                     READY   STATUS    RESTARTS   AGE
web-app-85f9565b5-4t9lk   1/1     Running   0          3d
```
