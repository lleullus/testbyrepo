# KubeSphere and Harbor LDAP Security Group Management Guide

## Index

In the Xi'an DKS environment, KubeSphere and Harbor are integrated with the enterprise Global AD (LDAP) for authentication and access control. This guide provides procedures for adding or removing LDAP Security Groups from allowed lists during new project onboarding, organizational changes, or access control reinforcement.

The procedure is performed in the following order:

1. **Verify KubeSphere LDAP configuration and back up ConfigMap**
2. **Add KubeSphere login-allowed security groups (`userSearchFilter` OR conditions)**
3. **Remove KubeSphere security groups and clean up filters**
4. **Restart `ks-apiserver` and verify login per group**
5. **Add Harbor project LDAP groups and assign roles**
6. **Remove Harbor project LDAP groups and verify permission revocation**
7. **Recovery procedure upon configuration errors**

---

## 1. Verifying KubeSphere LDAP Configuration and Backing Up ConfigMap

The LDAP login filter for KubeSphere is managed in the `userSearchFilter` property within the `kubesphere-config` ConfigMap in the `kubesphere-system` namespace.

### 1-1. Backing Up Current Settings

From the Bastion (`xadksbtmp01`), always back up the configuration prior to any changes.

```console
[dspaas@xadksbtmp01 ~]$ mkdir -p /tmp/ldap-backup && cd /tmp/ldap-backup
[dspaas@xadksbtmp01 ldap-backup]$ kubectl get configmap kubesphere-config -n kubesphere-system -o yaml > kubesphere-config-backup-$(date +%Y%m%d).yaml
[dspaas@xadksbtmp01 ldap-backup]$ ls -l
total 16
-rw-r--r--. 1 dspaas dspaas 14210 Sep  7 12:00 kubesphere-config-backup-20260907.yaml
```

### 1-2. Checking Currently Applied userSearchFilter

```console
[dspaas@xadksbtmp01 ldap-backup]$ kubectl get configmap kubesphere-config -n kubesphere-system -o jsonpath='{.data.kubesphere\.yaml}' | grep -A 2 "userSearchFilter:"
      userSearchFilter: (&(objectclass=user)(memberOf=CN=SG1599,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net))
```

Currently, only users belonging to the `SG1599` group are permitted to log in to KubeSphere.

---

## 2. Adding KubeSphere Login-Allowed Security Groups

Add additional security groups (e.g., `SG1600`, `SG1590`, `SG1591`) to the allowed list to permit access for new departments or project teams.

### 2-1. LDAP Filter Syntax Caution
- Because access should be granted if a user belongs to **any** of multiple groups, the `|` (OR) operator must be used.
- Do not connect groups with `&` (AND) such as `(&(memberOf=A)(memberOf=B))`, as this requires users to belong to both groups A and B simultaneously.

### 2-2. Editing ConfigMap and Applying Filters

Edit `kubesphere-config` and update `userSearchFilter` with multi-group OR conditions.

```console
[dspaas@xadksbtmp01 ~]$ kubectl edit configmap kubesphere-config -n kubesphere-system
```

**Before Modification**:
```yaml
userSearchFilter: (&(objectclass=user)(memberOf=CN=SG1599,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net))
```

**After Modification (adding `SG1600`, `SG1590`, `SG1591`)**:
```yaml
userSearchFilter: (&(objectclass=user)(|(memberOf=CN=SG1599,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)(memberOf=CN=SG1600,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)(memberOf=CN=SG1590,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)(memberOf=CN=SG1591,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)))
```

After saving, verify that changes are correctly applied.

```console
[dspaas@xadksbtmp01 ~]$ kubectl get configmap kubesphere-config -n kubesphere-system -o jsonpath='{.data.kubesphere\.yaml}' | grep -A 1 "userSearchFilter:"
      userSearchFilter: (&(objectclass=user)(|(memberOf=CN=SG1599,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)(memberOf=CN=SG1600,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)(memberOf=CN=SG1590,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)(memberOf=CN=SG1591,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)))
```

## 3. Removing KubeSphere Security Groups and Cleaning Up Filters

When a specific security group (e.g., `SG1590`) needs to be excluded due to security audits or project completion:

### 3-1. Deleting Specific Group Entry

```console
[dspaas@xadksbtmp01 ~]$ kubectl edit configmap kubesphere-config -n kubesphere-system
```

Remove only the `SG1590` entry from the line.

**After Modification**:
```yaml
userSearchFilter: (&(objectclass=user)(|(memberOf=CN=SG1599,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)(memberOf=CN=SG1600,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)(memberOf=CN=SG1591,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net)))
```

### 3-2. Clean Up when Only a Single Group Remains

If all additional groups are removed and only one group remains (e.g., `SG1599`), remove the `|` block and simplify to a single condition.

```yaml
userSearchFilter: (&(objectclass=user)(memberOf=CN=SG1599,OU="Security Groups",OU=Groups,OU=KOR,OU=Locations,DC=samsungds,DC=net))
```

## 4. Restarting ks-apiserver and Verifying Group Login

After editing the ConfigMap, restart `ks-apiserver` so that the new filter is loaded into memory.

### 4-1. Rolling Restart of ks-apiserver

```console
[dspaas@xadksbtmp01 ~]$ kubectl rollout restart deployment ks-apiserver -n kubesphere-system
deployment.apps/ks-apiserver restarted

[dspaas@xadksbtmp01 ~]$ kubectl rollout status deployment ks-apiserver -n kubesphere-system
Waiting for deployment "ks-apiserver" rollout to finish: 1 old replicas are pending termination...
deployment "ks-apiserver" successfully rolled out

[dspaas@xadksbtmp01 ~]$ kubectl get pod -n kubesphere-system -l app=ks-apiserver
NAME                            READY   STATUS    RESTARTS   AGE
ks-apiserver-6c4d7b889f-k2l8x   1/1     Running   0          52s
```

### 4-2. Verifying Login

Open a web browser, navigate to `https://xa.ks.dks.samsungds.net/`, and test:

1. **User in newly added group (`SG1600`)**: Login succeeds normally.
2. **User exclusively in removed group (`SG1590`)**: Login fails with `Incorrect username or password` or access denied.
3. **General AD account not in allowed groups**: Access rejected.

## 5. Adding Harbor Project LDAP Groups and Assigning Roles

While Harbor preserves its global LDAP integration, permissions for LDAP security groups are managed per **Project**.

### 5-1. Adding LDAP Group in Harbor Web Console

1. Log in to `https://xa.dcr.dks.samsungds.net/` with a Harbor Administrator or Project Admin account.
2. Navigate to **Projects** → select target project (e.g., `dspaas-v1.22.10-a`).
3. Click the **Members** tab.
4. Click **+ USER** dropdown or **+ GROUP** button.
5. Configure fields:
   - **Group Type**: Select `LDAP Group`
   - **Group Name**: Search and select enterprise AD group (e.g., `SG1600`)
   - **Role**: Select role according to requirements (`Developer`, `Maintainer`, `Project Admin`, `Guest`)
6. Click **Save** or **Add** to apply.

### 5-2. Verifying CLI Image Access Permissions

Check Docker CLI access with a developer account belonging to the LDAP group (`SG1600`).

```console
[root@user-host ~]# sudo docker login xa.dcr.dks.samsungds.net

[root@user-host ~]# sudo docker pull xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
```

## 6. Removing Harbor Project LDAP Groups and Verifying Revocation

### 6-1. Removing LDAP Group in Harbor Web Console

1. Log in to Harbor console → **Projects** → select target project.
2. Go to **Members** tab.
3. Select the LDAP group to remove (e.g., `SG1590`).
4. Click **Delete** or **Remove** button.
5. Confirm in the prompt to remove the group association.

### 6-2. Verifying Permission Revocation

Verify that an account solely belonging to that group (`SG1590`) is blocked from accessing the private repository.

```console
[root@user-host ~]# sudo docker login xa.dcr.dks.samsungds.net
Username: dshl99999.id
Password: 
Login Succeeded

[root@user-host ~]# sudo docker pull xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx:1.14.2
Error response from daemon: pull access denied for xa.dcr.dks.samsungds.net/dspaas-v1.22.10-a/nginx, repository does not exist or may require 'docker login': denied: requested access to the resource is denied
```

## 7. Recovery Procedure upon Configuration Errors

If a syntax error in the LDAP filter prevents all users from logging in to KubeSphere, restore from the backup taken prior to changes.

```console
[dspaas@xadksbtmp01 ~]$ cd /tmp/ldap-backup
[dspaas@xadksbtmp01 ldap-backup]$ kubectl apply -f kubesphere-config-backup-20260907.yaml
configmap/kubesphere-config configured

[dspaas@xadksbtmp01 ldap-backup]$ kubectl rollout restart deployment ks-apiserver -n kubesphere-system
deployment.apps/ks-apiserver restarted

[dspaas@xadksbtmp01 ldap-backup]$ kubectl rollout status deployment ks-apiserver -n kubesphere-system
deployment "ks-apiserver" successfully rolled out
```
