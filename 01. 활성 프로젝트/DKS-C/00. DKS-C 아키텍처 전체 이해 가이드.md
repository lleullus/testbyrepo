# DKS-C 아키텍처 전체 이해 가이드 — 인과와 스토리로 읽는 전체 지도

> [!important] 이 문서의 목적
> DKS-C(DS Cloud Kubernetes Service)의 8개 운영·아키텍처 문서는 내용이 방대하고 다루는 기술 스택(VCF, CCI, CAPI, APISIX, Keycloak, VictoriaMetrics 등)이 파편화되어 있어, 기술 명세부터 읽으면 전체 구조가 머릿속에서 연결되지 않습니다.
> 
> 이 문서는 **"어떤 문제를 해결하기 위해 앞의 기술이 필요했고, 그 기술의 한계 때문에 왜 다음 기술이 도입될 수밖에 없었는가"**라는 필연적 인과 사슬(`문제 → 하지만 → 그래서`)을 통해 DKS-C 전체 시스템을 한눈에 관통하도록 안내합니다.

---

## 0. 전체 인과 한 줄 요약

```text
개발팀마다 컨테이너 애플리케이션을 배포해야 한다.
→ 하지만 단일 K8s 클러스터에 모든 팀을 몰아넣으면 장애 격리와 보안 통제가 불가능하다.
→ 그래서 서비스마다 K8s 클러스터 자체를 통째로 새로 찍어주는 플랫폼을 만든다 (VKS / CAPI).
→ 하지만 클러스터만 쪼개고 네트워크가 같으면 통신 간섭이 생기는데, VCF 인프라에는 Security Group이 없다.
→ 그래서 클러스터마다 독립된 VPC와 외부 SNAT IP를 1:1:1로 통째로 묶어 가상 데이터센터 수준으로 격리한다.
→ 하지만 가상머신, 네트워크, 스토리지를 관리자가 매번 vCenter에서 수동으로 생성할 수 없다.
→ 그래서 K8s 선언적 API(CRD)로 인프라 자원을 다루는 최상위 관리 레이어를 둔다 (Supervisor Cluster & CCI).
→ 하지만 사용자 워크로드와 플랫폼 관리 기능(콘솔, 빌드, 관제)이 섞이면 사용자 장애가 플랫폼으로 전파된다.
→ 그래서 운영 플랫폼 자체를 5개의 독립된 전용 K8s 클러스터로 완전히 떼어낸다.
→ 하지만 물리적으로 파편화된 수많은 클러스터에 외부 트래픽이 직접 들어오면 보안 구멍이 난다.
→ 그래서 모든 외부 트래픽을 단일 관문에서 통제하는 중앙 API 게이트웨이를 둔다 (APISIX).
→ 하지만 수많은 서비스와 운영자, CLI, 배포 파이프라인의 인증을 제각각 관리할 수 없다.
→ 그래서 SSO 기반 OIDC 중앙 인증과 1년 유효 장기 토큰 교환 체계를 구축한다 (Keycloak).
→ 하지만 시스템이 커질수록 수백 개 컴포넌트의 TLS 인증서 만료와 Quota 제약이라는 운영 시한폭탄이 생긴다.
→ 그래서 cert-manager 기반 자동 갱신과 vCenter 직접 제어 우회로를 운영 기준으로 확립한다.
```

## 1. 출발점: 왜 K8s 클러스터 자체를 찍어내야 하는가?

### 1.1 단일 대형 클러스터의 한계
쿠버네티스(Kubernetes)를 도입할 때 가장 먼저 떠올리는 방식은 거대한 클러스터 하나를 만들고, 팀마다 `Namespace`를 나눠주는 멀티테넌시(Multi-tenancy)입니다.

**하지만**, 네임스페이스 격리에는 명확한 한계가 있습니다.
- 특정 팀의 컨테이너가 커널 패닉을 일으키거나 노드 자원을 고갈시키면 같은 노드에 있는 다른 팀의 서비스가 죽습니다.
- K8s 버전 업그레이드나 CNI 플러그인 점검을 하려면 회사 전체 서비스가 함께 중단 위험을 감수해야 합니다.
- 완벽한 권한 분리와 감사가 어려워 사내 보안 규정을 만족하기 힘듭니다.

**그래서**, DKS-C는 "네임스페이스를 나누는 것"을 넘어 **"팀이나 서비스마다 독립된 K8s 클러스터를 통째로 새로 프로비저닝해 제공하는 모델"**을 채택했습니다.

### 1.2 클러스터 생성의 자동화 (CAPI와 ArgoCD)
클러스터를 통째로 준다는 것은 마스터 노드(Control Plane) 3대, 워커 노드(Worker) 수대를 매번 새로 설치해야 한다는 뜻입니다. 이를 사람이 일일이 수작업으로 OS를 깔고 kubeadm을 돌리면 며칠씩 걸립니다.

**그래서**, 클러스터 생성 자체를 쿠버네티스 선언적 방식으로 처리하는 **Cluster-API(CAPI)**와 이를 배포·동기화하는 **ArgoCD**를 도입했습니다.
- `ClusterClass`라는 붕어빵 틀을 정의해 두고,
- "3 CP / 5 Worker 사양으로 클러스터 하나 만들어줘"라고 선언하면,
- 백엔드에서 11단계 파이프라인(CAPI → ArgoCD → VM 프로비저닝 → Helm/Carvel 기본 Addon 주입)이 자동으로 실행되어 수십 분 만에 완제품 클러스터가 완성됩니다.

## 2. 네트워크와 격리: 왜 VPC와 클러스터를 1:1:1로 묶었는가?

클러스터가 소프트웨어적으로 분리되었다고 해서 끝이 아닙니다. 이 클러스터들이 돌아가는 바닥(인프라)은 VMware Cloud Foundation(VCF) 가상화 환경입니다.

### 2.1 VCF 인프라의 결정적 제약
퍼블릭 클라우드(AWS 등)에서는 같은 네트워크 안에서도 인스턴스마다 `Security Group`을 붙여 패킷을 차단할 수 있습니다.

**하지만**, DKS-C의 기반인 VCF 인프라 내부에는 **동일 VPC 내 VM 간 트래픽을 통제하는 Security Group 개념이 없습니다.**
- 만약 A 서비스 클러스터와 B 서비스 클러스터의 노드들이 같은 VPC에 섞여 있다면, 한쪽이 해킹당했을 때 다른 쪽 클러스터의 내부 통신망(etcd, kubelet 등)으로 아무런 제약 없이 접근할 수 있습니다.

### 2.2 1:1:1 강제 결합 모델의 탄생
**그래서**, DKS-C는 네트워크를 인프라 수준에서 완전히 물리적으로 찢어놓는 극단적인 격리 규칙을 설계했습니다.

```text
[ VPC ]  :  [ Supervisor Namespace ]  :  [ User K8s Cluster ]  =  1 : 1 : 1
```

- 클러스터가 하나 생성될 때마다, 오직 그 클러스터만을 위한 **전용 VPC**가 하나 만들어집니다.
- 그 VPC에는 외부와 통신하기 위한 **전용 SNAT IP (External IP)**가 1:1로 할당됩니다.
- 이렇게 함으로써 다른 클러스터와 통신하려면 무조건 사내망 라우팅 및 방화벽을 거쳐야만 하며, 한 VPC 안에는 오직 단 하나의 클러스터 노드들만 존재하게 되므로 Security Group 부재로 인한 보안 위협이 원천 차단됩니다.

## 3. 제어 평면: 이 복잡한 인프라를 누가 조율하는가?

클러스터마다 전용 VM, 전용 VPC, 전용 스토리지를 동적으로 만들어내려면, 가상화 인프라를 제어하는 관리 주체가 있어야 합니다.

### 3.1 Supervisor Cluster와 CCI (Cloud Consumption Interface)
과거에는 인프라를 만들려면 vCenter 화면에 로그인해 마우스로 VM을 만들고, NSX 화면에서 네트워크를 뚫었습니다.

**하지만**, 클라우드 플랫폼에서 사용자 요청이 들어올 때마다 운영자가 GUI를 클릭할 수는 없습니다.

**그래서**, VMware 인프라 자체를 쿠버네티스처럼 다룰 수 있게 해주는 **Supervisor Cluster**를 Workload Domain(WLD)의 중심에 배치했습니다.
- Supervisor는 일반 워크로드를 돌리는 K8s가 아니라, **Compute(CPU/RAM), Network(VPC/Subnet), Storage를 쿠버네티스 커스텀 리소스(CRD)로 관리하는 특수 제어 K8s**입니다.
- 운영자는 `vcf context create --type cci` 명령으로 이 환경에 붙어서, `kubectl get vpc`, `kubectl get svns`처럼 일반 k8s 명령어로 사내 데이터센터 인프라를 조회하고 프로비저닝합니다.

### 3.2 운영자가 부딪히는 제약: Quota 변경 불가
**하지만**, 이 깔끔한 추상화 레이어에도 현장 운영상의 함정이 있습니다.
- Supervisor Namespace는 불변(Immutable) 객체로 설계되어 있어, 한 번 CPU/Memory/Storage Quota를 지정해 생성하면 **VCFA CLI나 일반 API로는 수정(Patch/Update)이 불가능**합니다.
- **따라서**, 운영 중 특정 클러스터의 자원을 긴급히 증설해야 할 때는 상위 추상화(CCI)를 건너뛰고, 하위 백엔드인 **vCenter Automation API를 직접 호출해 우회 수정**하는 특별 운영 절차가 필요합니다.

## 4. 플랫폼 시스템: 관리 기능은 어디에 올려야 하는가?

사용자들에게 K8s 클러스터를 나눠주려면 포털 콘솔, CI/CD 빌드 엔진, 로깅 수집기, 모니터링 대시보드가 상시 떠 있어야 합니다.

### 4.1 플랫폼과 사용자 워크로드의 물리적 분리
이 플랫폼 서비스들을 사용자가 쓰는 K8s 클러스터의 빈 공간에 올려두면 어떻게 될까요?

**하지만**, 특정 사용자 서비스에 트래픽이 폭주하거나 메모리 누수로 OOM이 발생하면, 포털 콘솔이 죽고 전체 클러스터의 관제와 배포가 마비됩니다.

**그래서**, DKS-C는 관리 플랫폼 전용으로 **완전히 독립된 5개의 K8s 클러스터**를 운영 Workload Domain(WLD01)에 별도로 띄웠습니다.

| 플랫폼 클러스터 | 담당 역할 | 주요 기술 스택 |
|---|---|---|
| **Console (`dksc`)** | 사용자 포털 UI, 결재 연동, 인프라 CRUD 명령 하달 | React, Spring Boot, PostgreSQL, Knox API |
| **Gateway (`dksg`)** | 모든 외부 인입 트래픽의 중앙 관문 및 인증 라우팅 | Apache APISIX (Nginx + Lua) |
| **Monitoring (`dksm`)** | 수백 개 노드·파드의 메트릭 중앙 수집 및 알람 전파 | VictoriaMetrics (Active-Active HA), Grafana, vmalert |
| **Logging (`dksl`)** | 전체 클러스터 로그 중앙 수집, 저장, 검색 | OpenSearch, OpenTelemetry Collector |
| **DevOps (`dkso`)** | 사용자 소스 빌드 및 K8s 배포 파이프라인 구동 | DinD (Docker-in-Docker), workflow-runner, Harbor |

이 분리 덕분에 사용자 클러스터 수십 개가 장애로 다운되어도, 운영자는 Console과 Grafana, OpenSearch를 통해 상황을 파악하고 정상 복구 작업을 지휘할 수 있습니다.

## 5. 트래픽 인입: 격리된 클러스터에 어떻게 접속하는가?

모든 클러스터를 VPC로 찢어놓고 외부 직접 접근을 막았더니 새로운 문제가 생깁니다.

### 5.1 APISIX API Gateway
사용자는 웹 브라우저로 자기 애플리케이션을 봐야 하고, 개발자는 `kubectl`로 API 서버에 붙어야 하며, 콘솔은 클러스터 상태를 읽어와야 합니다.

**하지만**, 클러스터마다 공인 IP를 직접 열어주면 방화벽 관리가 불가능해지고 디도스나 비인가 접근에 무방비로 노출됩니다.

**그래서**, 모든 외부 트래픽의 길목에 **`prd-dksg-ic01-khm` (APISIX Gateway)**를 배치했습니다.
- 사용자가 `console.dks...`나 개별 클러스터 엔드포인트로 접근하면, 트래픽은 무조건 먼저 APISIX 게이트웨이로 들어옵니다.
- APISIX는 중앙에서 인증 여부와 라우팅 규칙을 검사한 뒤, 백엔드 내부망을 통해 대상 클러스터의 인그레스나 API 서버로 트래픽을 안전하게 전달합니다.

### 5.2 Two-Arm Load Balancer 구성의 필수성
이 과정에서 로드밸런서(AVI / NSX Advanced Load Balancer)를 거치게 됩니다.

**하지만**, 로드밸런서를 단순하게 단일 인터페이스(Single-Arm)로 구성하면, 외부에서 들어온 트래픽과 내부로 보낸 트래픽이 같은 NIC을 지나면서 **최초 클라이언트의 원본 IP(Source IP)가 지워지고 L/B 자신의 IP로 덮어써지는 심각한 문제**가 발생합니다. 이렇게 되면 감사 로그에 모든 접속자가 L/B IP로 찍혀 보안 추적이 불가능해집니다.

**그래서**, DKS-C의 로드밸런서는 외부 VIP 인입 NIC과 내부 IP Pool 전달 NIC을 물리적으로 분리하는 **Two-Arm Configuration**을 필수로 적용하여 원본 클라이언트 IP를 끝까지 보존합니다.

## 6. 인증과 보안: 사용자 신원을 어떻게 통일하는가?

클러스터가 수십 개고, 플랫폼 시스템(Grafana, OpenSearch, Console, CLI)도 제각각인데, 로그인 계정을 서비스마다 따로 파줄 수는 없습니다.

### 6.1 Keycloak과 ADFS SSO 연동
**그래서**, 사내 계정 체계(ADFS)와 연동되는 중앙 인증 서버인 **Keycloak**을 배치하고 OIDC(OpenID Connect) 표준 프로토콜로 모든 시스템을 묶었습니다.
- 사용자는 사내 SSO로 한 번 로그인하면 콘솔, 모니터링(Grafana), 로깅(OpenSearch)에 모두 접근할 수 있습니다.

### 6.2 장기 토큰(Long-Term Token)이 필요한 이유
일반적인 OIDC Access Token은 보안을 위해 유효기간이 10분~30분으로 매우 짧습니다. 사람이 브라우저를 쓸 때는 세션 갱신으로 문제가 없습니다.

**하지만**, 시스템 백그라운드 데몬(헬스체크 배치, 외부 관제 시스템 P-DEP)이나 야간에 도는 CI/CD 빌드 러너는 브라우저가 없으므로 10분마다 사람이 로그인을 해줄 수 없습니다.

**그래서**, Keycloak의 **Token Exchange** 메커니즘을 이용한 **Long-Term Access Token 체계**를 만들었습니다.
- 사전에 등록된 특수 클라이언트(`dkssol-console-longterm-client` 등)를 통해 최초 1회 인증 코드를 교환하면, **유효기간 365일(1년)**짜리 장기 토큰을 안전하게 발급받아 무인 서비스의 인증 헤더(`Authorization: Bearer ...`)에 주입할 수 있습니다.

## 7. 수명주기와 잠재 위험: 시스템을 무너뜨리는 시한폭탄들

이 방대하고 정교한 아키텍처가 실제로 멈추는 순간은 대개 거창한 버그가 아니라 **"인증서 만료"**와 **"동시 부하"**에서 옵니다.

### 7.1 90일 인증서의 동시 만료 위험
DKS-C 내부의 모든 마이크로서비스와 노드 간 통신은 상호 TLS(mTLS)로 암호화되어 있으며, 이는 `cert-manager`가 관리합니다.

**하지만**, 현황 조사 결과 치명적인 운영 위험이 발견되었습니다.
- OpenSearch 클러스터의 노드 간 통신 인증서 8개, 모니터링 인증서, Addon 에이전트 인증서들이 **2026-03-19에 일제히 생성**되었습니다.
- 이 인증서들의 수명은 **90일**이며, 갱신 창(Renew Window)은 만료 10~15일 전입니다.
- **결국**, 수십 개의 인증서 갱신 시점이 특정 주간에 한꺼번에 도래하면서 cert-manager 큐가 폭주하거나 노드 재시작이 동시에 일어나 클러스터 순단이 발생할 수 있습니다.
- **따라서**, 운영자는 인증서 대시보드를 통해 일괄 자동 갱신 상태를 사전 감시하고 필요시 단계적 선행 갱신을 수행해야 합니다.
