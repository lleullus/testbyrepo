# 05. 외부 트래픽 진입 경로와 APISIX·Two-Arm LB — 어느 연결에서 주소가 바뀌고 누가 원본 Client IP를 신뢰할 수 있는가?

## 문서의 목적

이 문서는 외부 Client가 DKS-C 서비스에 접속할 때 DNS·VIP·Load Balancer·Kubernetes Service·APISIX·Backend를 거치는 동안 연결과 Source Address가 어떻게 달라질 수 있는지, Two-Arm 구성이 무엇을 분리하고 무엇을 보장하지 않는지, 그리고 `X-Forwarded-For`·`real-ip`·PROXY Protocol 같은 원본 IP 전달 방식이 어떤 신뢰 조건에서 성립하는지 설명합니다.

핵심은 **Client가 어느 Entry Point에 도달했는가**, **각 Proxy가 어느 Backend로 새 연결을 만들었는가**, **Network Source와 HTTP Header 중 어느 값을 누가 신뢰했는가**, **그 요청의 User Identity와 권한은 별도로 확인됐는가**를 구분하는 것입니다.

DKS-C 내부 자료에서 확인되는 배치와 일반적인 LB·Kubernetes·APISIX 동작을 구별합니다. 특정 Virtual Service·NAT Mode·Service Policy·TLS 종료 지점은 현재 설정과 Packet·Log로 다시 확인해야 합니다.

## 전체 인과 지도

이 문서는 **물류 터미널**을 하나의 비유 세계로 사용합니다. DNS와 VIP는 배송 접수 주소, Load Balancer는 도착 화물을 Backend로 분배하는 하역장, Two-Arm은 외부 접수 구역과 내부 배송 구역을 나눈 두 출입구, Kubernetes Service와 APISIX는 내부 분류·중계 허브, `X-Forwarded-For`와 PROXY Protocol은 원 발송지 정보를 다음 구간에 전달하는 운송 표식에 대응합니다. 비유는 연결과 주소 변환을 이해하기 위한 것이며 실제 경로는 NAT·Route·Service·APISIX·Log 증거가 기준입니다.

```text
외부 Client 요청이 Backend 기능으로 이어지는 전체 골격

Entry Point 결정
  FQDN ─ DNS ─ VIP / Listener
        ↓
LB가 Backend 구간 선택
  Pool + NAT / Forwarding Mode + Return Path
        ↓
Kubernetes Service가 APISIX Endpoint로 전달
        ↓
APISIX가 Route / Upstream으로 Backend에 새 연결
        ↓
원본 Client 주소를 신뢰 가능한 방식으로 전달·해석
        ↓
Token / Certificate로 Identity 확인 + Authorization
        ↓
Backend 기능 결과와 Client 반환 확인
```

### 블록 1 — Client가 실제로 들어온 Entry Point와 첫 Backend 구간을 확정한다

#### 기술적 목표

FQDN·VIP·Listener·LB Virtual Service·Backend Pool을 연결해 외부 요청이 어느 Network 접점으로 들어왔고 어디로 전달되는지 정합니다.

#### 비유

배송 주소가 맞다고 물건이 최종 창고 선반에 도착한 것은 아닙니다. 주소가 어느 터미널의 어느 접수구를 가리키는지, 그 접수구가 어떤 하역 라인과 내부 창고를 선택하는지까지 확인해야 실제 이동 경로를 알 수 있습니다.

#### 본문

외부 Client는 DNS가 반환한 VIP·Port로 연결합니다. Load Balancer의 Virtual Service는 그 연결을 받아 설정된 Backend Pool을 선택합니다. User Cluster의 kube-apiserver External IP, Application Ingress IP, SNAT External IP는 역할이 다르므로 하나의 주소라고 합치지 않습니다. Gateway Cluster의 Kubernetes API VIP와 APISIX Listener 역시 같은 주소라고 가정하지 않습니다.

따라서 특정 요청의 Entry Point는 `FQDN → DNS Record → VIP/Port → LB Virtual Service → Backend Pool → Kubernetes Service/Node/Pod → APISIX Listener`를 실제 설정으로 연결해 확정합니다. VIP 연결 성공은 이 사슬의 앞부분이 열린 증거일 뿐 APISIX Route나 Backend 기능 성공의 증거가 아닙니다.

#### ASCII

```text
Client
  ↓ FQDN
DNS
  ↓
VIP / Listener
  ↓ LB Virtual Service
Backend Pool
  ↓
Kubernetes Service / Node / Pod
  ↓
APISIX Listener

VIP 도달 ≠ APISIX Route 성공 ≠ Backend 기능 성공
```

### 블록 2 — LB의 NAT·Two-Arm·Return Path가 Backend의 Source Address를 결정한다

#### 기술적 목표

LB가 Backend 방향 Packet의 Source·Destination을 어떻게 처리하고 Return Path가 어떻게 형성되는지 확인해 원본 Client IP 보존 여부를 판단합니다.

#### 비유

터미널이 외부 접수구와 내부 배송구를 따로 운영할 수는 있지만, 화물 라벨을 원래 발송자 이름으로 유지할지 터미널 이름으로 다시 붙일지는 별도 정책입니다. 내부 배송 차량이 돌아오는 길도 같은 운송 체계와 맞아야 왕복 배송이 성립합니다.

#### 본문

LB가 Source NAT를 사용하면 Backend Socket에는 원래 Client 대신 LB 쪽 주소가 보일 수 있습니다. Source Address를 보존하는 방식에서는 Backend의 Return Route가 Client 방향으로 일관되게 형성되어야 합니다. `Two-Arm`은 Client/VIP 측 Network와 Backend Pool 측 Network를 서로 다른 Interface로 나누지만 NAT Policy 자체를 결정하지는 않습니다.

따라서 Front Arm·Back Arm의 연결 Network, Virtual Service의 Source NAT·Forwarding Mode, Backend Return Route, 실제 양방향 Session을 함께 봅니다. 두 Interface가 있다는 사실만으로 원본 Source가 보존된다고 결론내리지 않습니다.

#### ASCII

```text
Client-side Network ── [LB Front Arm]
                              │
                        Virtual Service
                              │ NAT / Forwarding Mode
Backend-side Network ── [LB Back Arm] ── Backend Pool
                              │
                              └─ Return Path도 같은 Session 조건과 맞아야 함

Two-Arm
   ≠ Source NAT 정책 확인
   ≠ 원본 Client IP 보존 확인
```

### 블록 3 — Kubernetes Service와 APISIX를 지나며 연결과 주소 표현이 다시 바뀔 수 있다

#### 기술적 목표

LB 뒤의 Service 전달과 APISIX Reverse Proxy 동작을 구분해 어느 지점의 Direct Peer와 어느 지점의 원본 Client 주소를 말하는지 명확히 합니다.

#### 비유

터미널 안에서 한 번 더 분류 센터를 거치면 외부 발송자와 내부 운송 담당자가 달라집니다. 최종 창고가 직접 본 배송 기사는 내부 분류 센터일 수 있고, 원래 발송자는 운송 표식에 기록해 전달해야 합니다.

#### 본문

LB Backend가 Kubernetes Node나 Service라면 Node→Pod 전달에서도 Source Address가 달라질 수 있습니다. 표준 Kubernetes의 `externalTrafficPolicy`는 외부 Traffic 전달 방식에 영향을 주며 `Local`은 Local Endpoint를 사용하는 대신 Endpoint 배치와 LB Health Check가 맞아야 합니다. 현재 APISIX Service의 실제 값은 Service YAML과 EndpointSlice로 확인해야 합니다.

APISIX가 HTTP Reverse Proxy로 동작하면 Client→APISIX와 APISIX→Backend는 서로 다른 TCP 연결입니다. Backend의 Direct Peer는 보통 APISIX나 그 사이 Proxy가 되므로 최초 Client 주소를 유지하려면 XFF 같은 Header나 다른 전달 메커니즘이 필요합니다. APISIX가 Client IP를 알고 있다는 사실과 Backend가 같은 Client IP를 신뢰한다는 사실은 별도입니다.

#### ASCII

```text
TCP 연결 1
Client / LB ─────────────> APISIX
Direct Peer = 실제 앞단 Network Peer

TCP 연결 2
APISIX ──────────────────> Backend
Backend Direct Peer = APISIX 또는 중간 Proxy

최초 Client 주소
  └─ XFF / X-Real-IP / PROXY Protocol 등으로 별도 전달 가능
```

### 블록 4 — 원본 IP 정보는 신뢰할 Proxy Chain과 TLS 처리 방식 안에서만 의미를 가진다

#### 기술적 목표

Header·Real IP·PROXY Protocol 중 어떤 방식으로 원본 주소를 전달할 수 있는지와 그 값을 신뢰할 수 있는 조건을 정합니다.

#### 비유

배송 상자에 적힌 발송자 이름은 누구나 임의로 써 넣을 수 있습니다. 터미널이 신뢰하는 운송사가 어느 구간에서 어떤 표식을 추가했는지 알아야 원 발송자를 믿을 수 있습니다. 봉인된 상자를 열지 않는 중계소는 내부 문서에 새 정보를 적어 넣을 수 없습니다.

#### 본문

외부 Client도 `X-Forwarded-For` 값을 임의로 넣을 수 있으므로 Header의 한 위치를 무조건 원본 IP로 믿으면 안 됩니다. APISIX `real-ip` 설정의 `source`, `trusted_addresses`, `recursive`는 어느 전달자의 값을 어떻게 재해석할지 결정합니다. Backend Application도 어떤 Proxy와 Header를 신뢰할지 별도로 맞춰야 합니다.

TLS Termination 지점은 HTTP를 복호화하므로 Header를 읽고 수정할 수 있지만 TLS Pass-through 지점은 암호화 Payload를 열 수 없어 XFF를 새로 넣을 수 없습니다. Pass-through에서는 Network Source 보존이나 양쪽이 지원하는 PROXY Protocol 같은 방식이 필요할 수 있습니다. PROXY Protocol은 송신·수신 양쪽 지원이 필요하며 Port 번호만으로 사용 여부를 추정하지 않습니다.

#### ASCII

```text
TLS Termination
Client TLS ──> Proxy 복호화 ──> HTTP Header 확인·수정 가능

TLS Pass-through
Client TLS ──> 암호화 Stream 그대로 전달
                    └─ XFF 신규 삽입 불가

Header 값 신뢰
  = Trusted Proxy 범위 + Header 해석 규칙 + 실제 Proxy Chain
```

### 블록 5 — Network Source와 User Identity·권한을 별도 축으로 검증한다

#### 기술적 목표

원본 Client IP를 정확히 추적하는 문제와 요청 주체의 Authentication·Authorization 문제를 분리해 최종 기능 성공 조건을 완성합니다.

#### 비유

배송 차량의 출발지를 아는 것과 운전자가 어떤 업무 권한을 가진 사람인지 확인하는 것은 다른 검사입니다. 차량 번호가 정확해도 출입 권한이 생기지 않고, 유효한 사원증이 있어도 잘못된 창고로 배송하면 업무는 실패합니다.

#### 본문

Source IP는 요청이 어느 Network 위치에서 왔는지를 설명하는 정보입니다. Identity는 Token·Client Certificate 같은 Credential의 검증 결과로 정하고, 그 Identity가 작업할 수 있는지는 Backend Policy나 Kubernetes Authorization이 별도로 판단합니다.

따라서 외부 요청의 완료는 Entry Point 도달, 올바른 Backend 선택, Client 주소 해석, Authentication, Authorization, Backend 기능 처리, Client까지의 반환을 서로 다른 상태로 봅니다. 원본 IP가 정확해도 권한이 자동으로 생기지 않고 유효한 JWT가 있어도 DNS·Route·Upstream이 잘못되면 기능은 실패합니다.

#### ASCII

```text
Network 경로
DNS / VIP / LB / Service / APISIX / Backend
             │
             ├─ Source IP 해석
             │
             └─ Token / Certificate
                    ↓
              Authentication
                    ↓
              Authorization
                    ↓
              Backend 기능 결과

Source IP 확인 ≠ Identity 확인 ≠ 권한 허용 ≠ 기능 성공
```
## 1. DKS-C 외부 요청의 Entry Point는 어떻게 식별하는가?

내부 운영 현황은 User Cluster의 외부 직접 접근을 제한하고 Gateway Cluster APISIX를 통해 외부 요청을 통제하는 구조를 기록합니다. SW 아키텍처는 APISIX를 DKS-C Backend와 Kubernetes Native API·REST API 중계 Component로 설명합니다.

User Cluster의 External IP 용도는 다음처럼 나뉘어 기록되어 있습니다.

| 용도 | 주소가 맡는 역할 | 이 주소만으로 알 수 없는 것 |
|---|---|---|
| kube-apiserver External IP | Kubernetes API 외부 접점 | APISIX Application Route와 동일한지 |
| Application Ingress IP | 사용자 Application Inbound 접점 | Outbound SNAT 주소 |
| SNAT External IP | VPC Outbound Source 변환 | Inbound Listener·Route |

Gateway Cluster에도 Kubernetes API VIP와 Application VIP가 기록되어 있습니다. 그러나 Gateway Cluster의 API VIP가 곧 모든 User Cluster API를 중계하는 APISIX Listener라는 뜻은 아닙니다.

특정 요청의 Entry Point를 확정하려면 다음 연결을 확인합니다.

```text
FQDN
  ↓ DNS Record
VIP / Port
  ↓ LB Virtual Service
Backend Pool
  ↓ Kubernetes Service / Node / Pod
APISIX Listener
  ↓ Route / Upstream
Target Backend
```

이 사슬에서 하나의 이름이나 IP만 확인하고 전체 경로를 추정하지 않습니다.

## 2. Load Balancer의 NAT와 Return Path는 원본 IP에 어떻게 영향을 주는가?

LB는 VIP·Port에서 연결을 받고 Virtual Service 설정에 따라 Backend Pool을 선택합니다. Source IP 결과를 결정하는 핵심은 LB가 Backend 방향 Packet의 Source Address를 바꾸는지입니다.

| LB 동작 | Backend에서 보일 수 있는 Peer | 추가로 필요한 조건 |
|---|---|---|
| Source NAT 사용 | LB 쪽 Source Address | LB가 Return Traffic을 Session에 맞춰 처리 |
| Source 보존 | 원래 Client Address | Backend Return Route가 Client 방향으로 일관됨 |
| PROXY Protocol 전달 | TCP Peer와 별도로 원본 주소 Metadata | 송신 LB와 수신 Server 모두 Protocol 지원 |
| HTTP Header 전달 | TLS 종료 후 XFF 등 Header | 신뢰할 Proxy와 Header 처리 규칙 |

Source를 보존하는 방식에서 Backend Return Packet이 LB를 우회하면 비대칭 경로가 생길 수 있습니다. 반대로 비대칭처럼 보이는 경로가 Direct Server Return 같은 의도된 구성일 수도 있으므로 Packet과 현재 Forwarding Mode 없이 임의로 Route를 고치지 않습니다.

### Two-Arm은 어떤 조건을 바꾸는가?

Two-Arm은 Client/VIP 측 Network와 Backend Pool 측 Network를 서로 다른 Interface에 연결합니다. 이것은 Traffic 영역과 Route 설계를 분리할 수 있게 하지만 NAT Policy 자체를 결정하지 않습니다.

다음 상태를 따로 확인합니다.

1. Front Arm이 어느 VIP·Client Network를 받는가
2. Back Arm이 어느 Backend Network와 연결되는가
3. Virtual Service의 Source NAT·Forwarding Mode는 무엇인가
4. Backend Default/Return Route는 어디를 향하는가
5. 같은 Session의 양방향 Packet이 실제로 어디를 통과하는가

내부 자료의 “Two-Arm에서 원본 IP 유지”는 그 자료가 전제한 설정 결과로 읽고 모든 Virtual Service에 확대하지 않습니다.

## 3. Kubernetes Service는 APISIX Pod까지의 Source IP에 어떤 영향을 줄 수 있는가?

LB Backend가 Kubernetes Node나 Service인 경우 Node→Pod 전달에서도 Source Address가 달라질 수 있습니다.

표준 Kubernetes Service에서 `externalTrafficPolicy`는 외부 Traffic 처리에 영향을 줍니다.

- `Local`: Traffic을 해당 Node의 Local Endpoint로 전달해 Source IP 보존에 활용할 수 있음
- `Cluster`: 다른 Node의 Endpoint로 전달될 수 있으며 구현 경로에서 Node Address로 SNAT될 수 있음

그러나 `Local`로 바꾸면 원본 IP가 반드시 보존되고 서비스가 항상 정상이라는 결론은 충분하지 않습니다.

```text
externalTrafficPolicy: Local
        ↓
Local Endpoint가 있는 Node만 실제 처리 가능
        ↓
LB Health Check가 Endpoint 배치와 맞아야 함
        ↓
Pod Ready / EndpointSlice 상태가 유지돼야 함
```

현재 내부 자료만으로 모든 APISIX Service의 `externalTrafficPolicy`를 확정하지 않습니다. 실제 Service YAML, EndpointSlice, Node/Pod Packet을 확인합니다.

## 4. APISIX가 결정한 Client IP와 Backend가 결정한 Client IP는 왜 다를 수 있는가?

HTTP Reverse Proxy는 들어온 Request를 읽고 Backend에 새 Request를 만듭니다. 따라서 Backend는 APISIX와의 새 TCP Connection을 받습니다.

Proxy Chain에서 원본 주소를 전달하는 대표 Header는 `X-Forwarded-For`입니다. 문제는 외부 Client도 임의의 XFF 값을 넣을 수 있다는 점입니다.

```text
외부 Client가 보낸 XFF
        +
신뢰 Proxy가 추가한 주소
        +
여러 Proxy Hop
        ↓
주소 목록
```

Backend가 무조건 맨 왼쪽 값을 원본 Client로 믿으면 공격자가 주입한 값을 신뢰할 수 있습니다.

신뢰할 수 있는 해석에는 두 규칙이 필요합니다.

1. 직접 연결한 Peer 중 누구를 Trusted Proxy로 인정할 것인가
2. Trusted Proxy가 추가한 주소 Chain을 어느 방향으로 해석할 것인가

APISIX `real-ip` 설정은 다음 요소로 Client 주소를 재해석할 수 있습니다.

| 설정 | 역할 |
|---|---|
| `source` | 어느 Header·정보에서 주소를 읽을지 지정 |
| `trusted_addresses` | 어느 전달자의 값을 신뢰할지 지정 |
| `recursive` | 여러 주소를 거슬러 해석하는 방식 |

이 설정은 APISIX 내부에서 Client 주소를 정하는 방식입니다. Backend로 전달되는 XFF와 Backend Application의 Trusted Proxy 설정은 별도로 맞춰야 합니다.

### `$remote_addr`는 언제나 최초 TCP Peer인가?

NGINX 계열에서 Real IP 처리가 적용되면 `$remote_addr`가 재해석된 주소를 반영할 수 있습니다. APISIX Log에 Client IP처럼 보이는 값이 있어도 다음을 확인해야 합니다.

- Real IP 처리 전 Direct Peer를 기록한 Variable이 있는가
- Real IP Module/Plugin이 어느 Header를 읽었는가
- 어느 주소 대역을 Trusted Proxy로 지정했는가
- Backend Log는 Direct Peer와 XFF 중 무엇을 사용했는가

Log Variable 이름만 보고 최초 Network Peer를 확정하지 않습니다.

## 5. TLS Termination과 Pass-through는 어떤 IP 전달 방식을 허용하는가?

TLS Termination을 수행하는 Proxy는 HTTP를 복호화하므로 Header를 읽고 수정할 수 있습니다. Pass-through Proxy는 암호화된 TCP Stream을 전달하므로 XFF 같은 HTTP Header를 새로 추가할 수 없습니다.

| TLS 처리 | 중간 장비가 볼 수 있는 것 | 원본 IP 전달 후보 |
|---|---|---|
| TLS Termination | HTTP Method·Path·Header | XFF·X-Real-IP, 새 TLS 연결 |
| TLS Re-encryption | 앞단 HTTP 확인 후 Backend와 새 TLS | Header + Backend TLS |
| TLS Pass-through | TCP·TLS Handshake Metadata 일부 | Source 보존 또는 PROXY Protocol |

PROXY Protocol은 Connection 시작부에 원래 Source/Destination Metadata를 전달합니다. 수신 Server가 이 형식을 지원하지 않으면 원래 Protocol Data로 오해해 연결이 깨질 수 있습니다.

특히 kube-apiserver가 일반적으로 PROXY Protocol을 수신한다고 가정하지 않습니다. Port 443·6443이라는 사실만으로 TLS 종료 지점이나 PROXY Protocol 사용 여부가 결정되지 않습니다.

## 6. 원본 IP와 Authentication·Authorization은 왜 별도 상태인가?

Source IP는 요청이 어느 Network 위치에서 왔는지 보여주는 단서입니다. Identity는 Token·Client Certificate 같은 Credential 검증으로 판단합니다.

| 질문 | 확인할 상태 |
|---|---|
| Network Entry Point에 도달했는가? | DNS, VIP Listener, LB Session, TCP/TLS |
| 올바른 Backend로 전달됐는가? | LB Pool, Service/Endpoint, APISIX Route·Upstream |
| 원본 주소를 어떻게 판단했는가? | NAT Mode, XFF, Real IP, Trusted Proxy |
| 요청 주체는 누구인가? | Token·Certificate의 Issuer·Subject·검증 결과 |
| 그 주체가 작업할 수 있는가? | Backend 또는 Kubernetes Authorization |
| 기능 처리가 성공했는가? | Backend Response·상태 변화 |

원본 Client IP가 정확히 보존돼도 해당 User가 Kubernetes API 작업을 할 권한이 생기지 않습니다. 반대로 유효한 JWT가 있어도 잘못된 DNS·Route·Backend로 요청하면 기능은 실패합니다.

모든 DKS-C 요청에 JWT가 필요하다고 일반화하지도 않습니다. 실제 Route·Plugin·Backend의 인증 요구를 확인합니다.

## 7. 실제 요청을 마지막 확인 상태에서 어떻게 추적하는가?

NAT와 Proxy를 지나면 5-tuple과 HTTP 연결이 바뀔 수 있습니다. 가능한 경우 동일 시각의 Request ID, Source/Destination, NAT Session, Header, Backend Log를 연결합니다.

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 증거 |
|---|---|---|
| DNS가 VIP를 반환 | VIP Listener가 실제 열려 있는가? | LB Virtual Service·Connection Log |
| Client→VIP 연결 성공 | 어느 Backend Pool Member가 선택됐는가? | LB Session, Pool Health, NAT Mode |
| LB가 Node/Service로 전달 | APISIX Pod까지 Source가 어떻게 왔는가? | Service Policy, EndpointSlice, Packet Capture |
| APISIX Listener 도달 | 어느 Route·Upstream이 선택됐는가? | APISIX Route·Access Log·Request ID |
| APISIX가 Client IP를 기록 | Direct Peer인가 Real IP 재해석 값인가? | real-ip 설정, Log Variable, XFF |
| Backend가 Request 수신 | Backend는 어느 Proxy·Header를 신뢰했는가? | App Trusted Proxy 설정·Log |
| TLS Handshake 성공 | HTTP Route·Authentication·Application 중 어디서 실패했는가? | HTTP Status, Auth Log, Backend Log |
| Backend 응답 성공 | Client까지 반환이 완료됐는가? | Reverse Flow, Client Response |

읽기 전용 확인 예시는 다음과 같습니다. 실제 Context·Namespace·Service·Interface를 먼저 확인합니다.

```bash
kubectl --context="$GATEWAY_CONTEXT" -n "$APISIX_NAMESPACE" \
  get service "$APISIX_SERVICE" -o yaml

kubectl --context="$GATEWAY_CONTEXT" -n "$APISIX_NAMESPACE" \
  get endpointslices \
  -l "kubernetes.io/service-name=$APISIX_SERVICE" -o yaml

ip route get "$CLIENT_IP"

tcpdump -nn -i "$IFACE" -c 20 \
  "host $CLIENT_IP and tcp port $PORT"
```

앞 구간에서 Source가 변환됐다면 뒤 구간에서 원래 `CLIENT_IP`가 보이지 않을 수 있습니다. LB·NAT Session에서 변환 주소를 찾아 같은 요청과 연결합니다.

Connection Timeout 하나만으로 SNAT·`externalTrafficPolicy`·Firewall Rule을 바로 바꾸지 않습니다. Listener 미구성, Unhealthy Backend, APISIX Route 오류, TLS Mismatch, Backend Hang도 경쟁 설명입니다.
