# 07. 운영 수명주기와 Certificate·Token·Node 교체 — 새 Resource는 언제 실제 기능을 인계받는가?

## 문서의 목적

이 문서는 DKS-C에서 Certificate·Long-Term Token·Control Plane Node·Worker Node를 교체할 때, 새 Resource가 생성된 상태와 실제 통신·합의·Workload 기능을 인계한 상태를 구별하고, 기존 상태를 언제 제거할 수 있는지 설명합니다.

네 대상은 기술적으로 다르지만 공통적으로 다음 인과 구조를 가집니다.

```text
새 상태 생성
   ↓
소비자 또는 Cluster가 새 상태를 인식
   ↓
실제 기능을 새 상태로 수행
   ↓
기존 상태가 더 이상 필요하지 않음 확인
   ↓
기존 상태 제거·폐기
```

핵심은 **Resource 존재**, **소비자 반영**, **기능 인계**, **옛 상태 폐기**를 하나의 “변경 완료”로 뭉치지 않는 것입니다. DKS-C Certificate·Token 값은 내부 자료를 따르고, Kubernetes·CAPI·etcd 동작은 공식 자료와 연결합니다. 다른 환경의 Tower 사례는 DKS-C에서 실제 발생한 사건으로 확대하지 않습니다.

## 전체 이해 지도

```text
운영 변경 이해 골격
│
├─ Credential 교체
│  ├─ Certificate 발급 / Secret 저장
│  ├─ Application Reload
│  ├─ 실제 TLS Handshake
│  └─ 옛 Certificate·CA 제거
│
├─ Token 교체
│  ├─ 새 Token 발급
│  ├─ 소비자 Secret·Config 반영
│  ├─ 실제 인증·인가 API 호출
│  └─ 옛 Token 폐기·Revocation 확인
│
├─ Control Plane 교체
│  ├─ 새 VM / Node
│  ├─ etcd Member / Learner / Voter
│  ├─ Quorum·API Health
│  └─ 기존 Member 제거
│
└─ Worker 교체
   ├─ 새 VM / Node Ready
   ├─ 기존 Node Drain·Eviction
   ├─ Volume Detach / 대체 Pod Ready
   └─ Service Endpoint·실제 Request
```

- **Certificate는 새 Secret에 저장됐다고 실제 Server가 그 Certificate를 제시하는 것이 아닙니다.** cert-manager는 `Certificate` Resource와 Issuer를 이용해 Certificate·Private Key를 Secret에 준비합니다. 그 뒤 Application이 Secret 변경을 Reload하고 실제 TLS Connection에서 새 Certificate를 제공해야 기능 인계가 확인됩니다. Root CA가 바뀌면 Client Trust Store도 새 CA를 신뢰해야 합니다.

```text
Certificate Request 성공
        ↓
새 Certificate / Key가 Secret에 저장
        ↓
Server가 Secret 변경을 Reload
        ↓
실제 TLS Endpoint가 새 Certificate 제시
        ↓
Client가 Chain·Hostname을 신뢰
```

- **Token도 발급과 사용이 다릅니다.** 새 Long-Term Token의 `exp`를 확인하고 소비자의 Secret·Environment·Config에 넣은 뒤 Process가 새 값을 읽고 인증이 필요한 API를 실제 호출해야 합니다. 옛 Token 문자열을 저장소에서 지우는 것과 Resource Server가 옛 Token을 즉시 거부하는 것도 같은 상태가 아닙니다.

- **Control Plane Node 교체에서는 VM 수보다 etcd Voting Member와 Quorum이 중요합니다.** 새 VM이 켜져도 etcd Member가 아니거나 Learner라면 Voting Member 수에 포함되지 않습니다. 기존 Member를 제거하기 전에 Member List·Learner/Voter 상태·Replication·Endpoint Health·Kubernetes API를 함께 확인해야 합니다.

```text
새 Control Plane VM
        ↓
Kubernetes Node / Static Pod 준비
        ↓
etcd Member 추가
        ↓
Learner Replication
        ↓
Voter Promotion
        ↓
Quorum·API Health 유지
        ↓
기존 Member 제거 가능 판단
```

- **Worker Node 교체에서는 새 Node Ready와 사용자 기능 인계가 다릅니다.** Drain은 기존 Pod의 Eviction을 요청하는 과정이고, PDB·Affinity·Resource·Volume 조건 때문에 대체 Pod가 Ready되지 않을 수 있습니다. 기존 Pod 종료 뒤에도 Volume Detach·Service Endpoint 반영·실제 Request 성공이 남습니다.

```text
새 Worker VM / Node Ready
        ↓
기존 Node Cordon·Drain
        ↓
Pod Eviction 허용
        ↓
대체 Pod Scheduling·Ready
        ↓
Volume·Endpoint 반영
        ↓
실제 사용자 Request 성공
```

## 1. 공통 수명주기에서 “생성”과 “기능 인계”는 어떻게 다른가?

운영 변경 대상이 달라도 완료 판단은 다음 네 층으로 나눌 수 있습니다.

| 층 | 공통 질문 | Certificate 예 | Token 예 | Node 예 |
|---|---|---|---|---|
| 생성 | 새 Resource가 존재하는가? | 새 Secret | 새 Token | 새 VM·Machine |
| 소비자 반영 | 실제 사용 주체가 새 값을 읽는가? | Server Reload | Process Credential 갱신 | kubelet·etcd·Scheduler 인식 |
| 기능 확인 | 새 상태가 요구 기능을 수행하는가? | TLS Handshake | Protected API 호출 | API Quorum·Pod Service |
| 기존 상태 제거 | 옛 상태가 없어도 기능이 유지되는가? | 옛 Cert·CA 제거 | 옛 Token 거부 | 기존 Member·Node 삭제 |

앞 층의 성공은 뒤 층의 충분조건이 아닙니다.

```text
새 Secret 존재
  ≠ Server가 새 Certificate 사용

새 Token 발급
  ≠ 자동 프로그램이 새 Token 사용

새 VM Power On
  ≠ etcd Quorum·Workload 인계 완료
```

따라서 변경 계획에는 생성 작업뿐 아니라 **누가 새 상태를 소비하는지**, **어떤 기능으로 인계를 검증할지**, **기존 상태를 제거해도 되는 조건**을 함께 적습니다.

## 2. Certificate는 어떤 통신을 보호하고 어느 실패 지점을 만드는가?

Certificate는 TLS에서 Server·Client Identity와 Trust를 확인하는 데 사용됩니다. 어느 Certificate가 만료·불일치·미신뢰 상태인지에 따라 실패하는 연결이 다릅니다.

### Kubernetes Control Plane과 Node Certificate

| Certificate·통신 | 역할 | 실패 시 영향을 받을 수 있는 연결 |
|---|---|---|
| API Server Server Certificate | Client가 kube-apiserver Identity 확인 | kubectl·kubelet·Controller API 접속 |
| API Server → etcd Client Certificate | API Server가 etcd에 Client로 인증 | Cluster State Read/Write |
| etcd Server·Peer Certificate | etcd Client·Member 간 TLS | etcd Query·Replication |
| API Server → kubelet Client Certificate | API Server가 kubelet API에 접속 | logs·exec 등 |
| front-proxy Client Certificate | Aggregated API Request 인증 | Extension API |
| kubelet Client Certificate | kubelet이 API Server에 Node Identity로 인증 | Node Status·Lease |
| kubelet Server Certificate | Client가 kubelet Server Identity 확인 | kubelet HTTPS |

“Certificate 하나가 만료되면 Kubernetes 전체 Process가 즉시 정지한다”고 일반화하지 않습니다. 예를 들어 API Server Server Certificate 실패와 etcd Peer Certificate 실패는 다른 연결을 끊습니다. kubelet이 API Server에 상태를 보고하지 못해도 이미 실행 중인 Container가 같은 순간 모두 종료되는 것은 아닙니다.

DKS-C User Cluster가 실제로 어떤 방식으로 Certificate를 생성·회전하는지는 대상 관리형 VKS Version과 운영 절차를 확인해야 합니다.

### DKS-C 플랫폼 Certificate 기록

내부 Certificate 현황은 다음과 같은 설정을 기록합니다.

| 영역·예시 | Issuer | 기록된 Duration | Renew Window |
|---|---|---:|---:|
| Metric Root CA | `selfsigned-root` | 365일 | 3일 |
| Metric `vmauth-server-cert` | `monitoring-hub-issuer` | 90일 | 10일 |
| Log Root CA | `logs-selfsigned-issuer` | 365일 | 3일 |
| OpenSearch API/Admin/Node | `logs-issuer` | 90일 | 15일 |
| OpenTelemetry Gateway | `logs-issuer` | 90일 | 15일 |
| DKS Log/Metric/Event Agent | 영역별 Issuer | 90일 | 10일 |
| `vm-operator-root-ca` | `vm-operator-root` | 2658일 | 표에는 `-` |
| `vm-operator-validation` | `vm-operator-issuer` | 1908일 | 표에는 `-` |

OpenSearch Node 간 Certificate는 Coordinator 2, Master 3, Hot 2, Warm 1로 총 8개가 기록되어 있습니다. 같은 Renew Window에 들어간다는 사실은 갱신 시점이 겹칠 가능성을 보여주지만 Application Restart·서비스 영향이 반드시 동시에 발생한다는 증거는 아닙니다.

내부 자료에는 Created/Renewal Time 누락, 계산 날짜 불일치, Renew `-`와 기본 Renew 설명의 충돌이 있습니다. 따라서 표의 계산값만으로 현재 만료·자동 갱신 상태를 확정하지 않고 실제 `Certificate`·`CertificateRequest`·Secret·Endpoint를 봅니다.

## 3. cert-manager가 새 Certificate를 발급하면 어떤 상태가 이어지는가?

cert-manager `Certificate` Resource는 대상 DNS/SAN, Secret 이름, Issuer 참조, Duration·renewBefore를 선언합니다. cert-manager는 Issuer를 통해 발급을 요청하고 성공한 Certificate와 Private Key를 Secret에 저장합니다.

이 상태가 확인하는 것은 **새 Certificate Material 준비**입니다.

소비자 반영 방식은 Application과 Mount 형태에 따라 다릅니다.

| 전달 방식 | Secret 변경 뒤 남는 조건 |
|---|---|
| Secret Volume File | kubelet이 갱신해도 Application이 File을 다시 읽어야 함 |
| `subPath` Mount | 일반 Secret Volume과 갱신 방식이 다름 |
| Environment Variable | 실행 중 Process에 자동 반영되지 않음 |
| Controller 자동 Reload | Watch·Reload가 실제 성공했는지 확인 |
| Manual Reload/Restart | 새 Process가 새 Secret을 읽는지 확인 |

따라서 `Certificate Ready=True`와 실제 Server가 새 Certificate를 제시하는 것은 별도 상태입니다.

Root CA 교체에서는 Server Secret뿐 아니라 Client Trust Store가 중요합니다.

```text
새 Root CA
  ├─ 새 Server Certificate 서명
  └─ Client Trust Store에 새 CA 추가 필요

Server만 교체
  + Client가 새 CA를 신뢰하지 않음
  → TLS 실패 가능
```

cert-manager가 Server Secret을 바꿔도 외부 Client의 Trust Store는 자동으로 바뀌지 않습니다.

## 4. Certificate 발급 실패와 소비자 반영 실패는 어떻게 구별하는가?

먼저 새 Certificate가 만들어지지 않은 것인지, 만들어졌지만 소비자가 옛 값을 쓰는 것인지 분리합니다.

### 발급 경로

```bash
kubectl --context="$CLUSTER_CONTEXT" -n "$CERT_NAMESPACE" \
  get certificate "$CERT_NAME" -o yaml

kubectl --context="$CLUSTER_CONTEXT" -n "$CERT_NAMESPACE" \
  get certificaterequests -o wide

kubectl --context="$CLUSTER_CONTEXT" -n "$CERT_NAMESPACE" \
  get events
```

`status.notAfter`, `status.renewalTime`, Ready Condition, CertificateRequest 상태를 봅니다. Condition 배열 첫 항목이 항상 Ready라고 가정하지 않습니다. Secret 존재를 확인할 때 Private Key 원문은 출력하지 않습니다.

### 실제 Endpoint

```bash
openssl s_client \
  -connect "$TLS_HOST:$TLS_PORT" \
  -servername "$TLS_HOST" </dev/null 2>/dev/null \
  | openssl x509 -noout -dates -serial -fingerprint -sha256
```

이 출력은 **해당 연결에서 받은 Certificate**를 보여줍니다. 다음을 자동으로 증명하지는 않습니다.

- Hostname Validation 전체 성공
- 전체 Trust Chain 검증
- Application Request 성공
- LB 뒤 모든 Endpoint가 같은 Certificate 사용

Issuer가 Ready하지 않거나 webhook/API 통신이 실패하면 CertificateRequest가 진행되지 않을 수 있습니다. Secret은 새 값인데 Endpoint가 옛 Certificate를 제시하면 Issuer보다 소비자 Reload·Replica별 반영 상태를 조사합니다.

## 5. Long-Term Token 교체는 Certificate 교체와 무엇이 같고 다른가?

공통 수명주기는 다음과 같습니다.

```text
새 Credential 생성
   ↓
소비자 저장소 반영
   ↓
Process가 새 Credential 사용
   ↓
실제 보호 기능 호출 성공
   ↓
옛 Credential 폐기
```

발급 메커니즘은 다릅니다.

- Certificate: cert-manager·Issuer가 Certificate/Key를 Secret에 저장
- Long-Term Token: User Login·단기 Token·Long-Term Client Token Exchange

내부 Long-Term Token 흐름은 다음처럼 기록됩니다.

1. User Login → Authorization Code
2. Code → Short-Lived Access Token
3. Long-Term Client로 Token Exchange
4. 발급 Token의 `exp` 확인
5. 소비자 Credential 저장소 반영
6. Protected API에서 새 Token 사용 확인

Client 이름·설정 기간과 실제 365일 발급 기록이 충돌하므로 교체 일정은 실제 `exp`와 Current Policy를 기준으로 정합니다. JWT Payload Decode는 Claim 확인일 뿐 Signature·Audience·Authorization 검증이 아닙니다.

새 Token을 Secret에 저장해도 Environment Variable을 읽는 Process는 재기동 전 옛 값을 계속 사용할 수 있습니다. File Mount라도 Application이 다시 읽지 않으면 실제 Request는 옛 Token을 사용할 수 있습니다.

## 6. 새 Credential 적용과 옛 Credential 폐기는 왜 다른가?

Certificate 교체에서 옛 Certificate 제거 조건은 다음과 같습니다.

```text
새 Certificate / Key 준비
   ↓
Server가 새 값 Load
   ↓
실제 Client TLS 연결 성공
   ↓
Chain·Hostname·Client Trust 확인
   ↓
옛 Certificate·CA 제거 가능 판단
```

Token 교체에서는 다음을 확인합니다.

```text
새 Token 발급
   ↓
소비자 반영
   ↓
실제 Authentication·Authorization API 성공
   ↓
옛 Token 사용처·복사본 확인
   ↓
Revocation·Session Policy에 따라 폐기
```

Bearer JWT는 저장소에서 문자열을 지웠다고 이미 복사된 Token이 `exp` 전에 반드시 무효화되는 것은 아닙니다. 즉시 거부가 필요하면 Keycloak과 Resource Server의 Revocation·Session·Local Validation 동작을 확인합니다.

## 7. Node 교체는 왜 같은 “기능 인계” 문제인가?

CAPI Rolling Update나 Machine 교체는 새 Machine·VM을 생성하고 기존 Machine을 제거하는 흐름을 사용할 수 있습니다. 그러나 새 VM 존재는 기존 Node의 기능 인계 증거가 아닙니다.

Control Plane과 Worker가 인계해야 할 기능은 다릅니다.

| Node 종류 | 인계해야 할 핵심 기능 |
|---|---|
| Control Plane | kube-apiserver·Controller·Scheduler, etcd Membership·Quorum |
| Worker | Workload Scheduling, Pod Eviction·대체, Volume, Service Endpoint |

Persistent Volume을 사용하는 Worker는 Pod 이동 외에 Detach·Attach 조건이 추가될 수 있습니다.

따라서 Node 교체는 VM 수를 `N→N+1→N`로 맞추는 작업이 아니라 Cluster 기능이 새 Member·Node로 이동했는지 확인하는 작업입니다.

## 8. Control Plane 교체에서 etcd Quorum은 무엇으로 판단하는가?

etcd는 Voting Member의 과반수가 정상적으로 통신해야 합의를 진행합니다.

```text
quorum = floor(voting_members / 2) + 1
```

| etcd 구성 | 필요한 Quorum | 판단 |
|---|---:|---|
| Voter 3 | 2 | 2개 이상 정상이어야 합의 가능 |
| Voter 4 | 3 | 3개 이상 정상이어야 합의 가능 |
| Voter 3 + Learner 1 | 2 | Learner는 Vote하지 않으므로 3 Voter 기준 |

새 Control Plane VM이 생겨 총 VM이 4대가 됐어도 새 etcd Member가 아직 Learner이거나 Member 자체가 아니면 Voting Member 수가 4가 된 것이 아닙니다.

```text
새 VM 존재
   ↓
새 etcd Member 존재 여부
   ↓
Learner Replication 상태
   ↓
Voter Promotion 여부
   ↓
기존 Voter 제거 후에도 Quorum 유지 여부
```

실제 교체에서는 다음을 함께 봅니다.

```bash
etcdctl --endpoints="$ETCD_ENDPOINTS" \
  --cacert="$ETCD_CA" \
  --cert="$ETCD_CLIENT_CERT" \
  --key="$ETCD_CLIENT_KEY" \
  member list -w table

etcdctl --endpoints="$ETCD_ENDPOINTS" \
  --cacert="$ETCD_CA" \
  --cert="$ETCD_CLIENT_CERT" \
  --key="$ETCD_CLIENT_KEY" \
  endpoint status -w table
```

이 명령은 승인된 Endpoint·Credential을 사용하는 읽기 확인 예입니다. CAPI가 관리하는 Member를 사람이 임의로 Add/Remove하라는 절차가 아닙니다.

VM 개수만으로 Quorum Risk를 설명하지 않고 Member ID, Voter/Learner, Replication, Endpoint Health, API 응답을 연결합니다.

## 9. Worker 교체에서 Drain·PDB·대체 Pod는 어떻게 연결되는가?

Machine 삭제 과정은 설정·Version에 따라 Node Drain, Volume Detach 대기, Infrastructure Resource 삭제를 수행할 수 있습니다.

Drain은 기존 Node에 새 Pod가 배치되지 않도록 하고 실행 중 Pod의 Eviction을 요청합니다. PDB는 자발적 중단에서 유지해야 할 Available Pod 수를 보호합니다.

`disruptionsAllowed=0`을 곧바로 잘못된 설정이라고 결론내리지 않습니다. 현재 Replica·Ready 상태에서 더 이상 Eviction하면 가용성 조건을 깨기 때문에 차단하는 것일 수 있습니다.

Worker 교체 상태는 다음처럼 나뉩니다.

| 상태 | 실제 의미 | 아직 남은 조건 |
|---|---|---|
| 새 Worker VM 생성 | 인프라 VM 존재 | Node 등록·Ready |
| 새 Node Ready | kubelet이 Cluster에 참여 | Workload 인계 |
| 기존 Node Drain 시작 | Eviction 요청 진행 | PDB·종료·Volume 처리 |
| 기존 Pod 종료 | Process 종료 | 대체 Pod 생성·Ready |
| Volume Detach 완료 | 기존 Node 연결 정리 | 새 Node Attach·Mount |
| 대체 Pod Ready | Pod Ready Condition 만족 | Service Endpoint·기능 |
| Endpoint 반영 | Traffic 대상에 포함 | 실제 사용자 Request 성공 |

따라서 Eviction이 끝났다는 사실만으로 Service가 복구됐다고 말하지 않습니다.

읽기 예시는 다음과 같습니다.

```bash
kubectl --context="$MANAGEMENT_CONTEXT" -n "$MACHINE_NAMESPACE" \
  get machines,machinedeployments -o wide

kubectl --context="$MANAGEMENT_CONTEXT" -n "$MACHINE_NAMESPACE" \
  get machine "$MACHINE_NAME" -o yaml

kubectl --context="$USER_CONTEXT" \
  get pods -A --field-selector="spec.nodeName=$NODE_NAME"

kubectl --context="$USER_CONTEXT" get pdb -A
```

CAPI Controller의 Drain을 `kubectl drain` CLI와 동일한 Flag로 실행한다고 가정하지 않습니다. Machine Condition·Event에서 Eviction, Pre-drain Hook, Volume Detach 중 무엇을 기다리는지 확인합니다.

## 10. Tower 교착 사례는 어떤 인과 구조만 보여주는가?

별도 Xi'an 운영 자료의 Tower 사례는 다음 두 조건이 서로 기다리는 교착을 기록합니다.

```text
기존 Pod
  └─ Leader Lease를 계속 갱신

새 Pod
  └─ Leader Lease를 얻어야 Ready

Deployment Rolling Update
  └─ 새 Pod가 Ready여야 기존 Pod 종료

결과
기존 Pod가 살아 있어 Lease 유지
→ 새 Pod는 Lease를 못 얻어 NotReady
→ Controller는 기존 Pod를 내리지 않음
```

이 사례의 일반 교훈은 **새 Pod가 존재하는 것과 기존 역할을 인계한 것은 다르며, Application Leader Election 조건이 Kubernetes Rollout 조건과 교착할 수 있다**는 것입니다.

그러나 이 사례는 특정 Deployment Rolling Update입니다.

- 모든 Lease 기반 Workload에 같은 교착이 생긴다는 근거가 아닙니다.
- CAPI Worker Drain에서 같은 순서로 재현된다는 근거가 아닙니다.
- Replica 0→1 복구안을 다른 DKS-C Component에 적용할 근거가 아닙니다.
- 원자료의 시간·업무 영향 수치를 다른 환경에 보장하지 않습니다.

실제 Application의 Lease 소유권, Readiness 조건, Rollout Strategy, 중단 허용, 복구 승인부터 확인합니다.

## 11. 변경 문제를 마지막 확인 상태에서 어떻게 좁히는가?

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 증거 |
|---|---|---|
| `Certificate` Ready 아님 | Issuer·CertificateRequest 중 어디서 막혔는가? | Condition, Request, Event |
| Secret은 새 Certificate 보유 | 소비자가 새 File을 읽었는가? | Pod Mount·Reload·Process Start Time |
| 일부 TLS 연결만 새 Certificate | Replica·LB Endpoint별 반영이 다른가? | 반복 연결, Backend 식별, Fingerprint |
| 새 Token 발급 | 실제 소비자 저장소와 Process가 새 값을 읽는가? | Secret Version, Env/Volume 방식, Restart |
| 새 Token으로 Health 200 | Protected API에서 Authn·Authz가 성공하는가? | 인증 필수 API·Audit Log |
| 옛 Token 저장소 제거 | Resource Server가 옛 Token을 거부하는가? | Revocation·Session·실제 호출 |
| 새 Control Plane VM 생성 | etcd Member인가, Learner인가, Voter인가? | Member List·Endpoint Status |
| 새 Voter 정상 | 기존 Member 제거 후 Quorum이 유지되는가? | Quorum 계산·API Health |
| 새 Worker Node Ready | 기존 Workload를 인계했는가? | Drain·Pod·Volume·Endpoint |
| 대체 Pod Ready | 사용자 Service Path가 정상인가? | 실제 Request·Response |
| Rollout이 멈춤 | Infra 부족인가 PDB인가 App Leader 조건인가? | Event·PDB·Lease·Readiness |

## 12. 변경 완료를 어떤 증거로 판정하는가?

| 변경 대상 | 새 상태 준비 증거 | 기존 상태 제거 전 확인할 기능 |
|---|---|---|
| Server Certificate | 새 Certificate·Key가 Secret에 저장 | 실제 Client TLS에서 새 Certificate·Trust 확인 |
| Client Certificate | 새 Credential이 소비자에 반영 | Server가 새 Client Identity 수용 |
| Long-Term Token | 새 Token과 `exp` 확인 | 소비자가 Protected API를 새 Token으로 호출 |
| Control Plane Node | 새 VM·Node 생성 | etcd Member·Quorum과 API Health |
| Worker Node | 새 VM·Node Ready | Pod Eviction·대체 Pod·Volume·Service Path |

공통 완료 기준은 **새 Resource 존재가 아니라 기능 인계**입니다.
