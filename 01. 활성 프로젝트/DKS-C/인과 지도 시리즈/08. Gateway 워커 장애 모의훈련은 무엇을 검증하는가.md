# 08. Gateway Worker 장애 모의훈련 — VM 손실 뒤 어느 증거까지 있어야 자동 복구와 사용자 기능 복구를 말할 수 있는가?

## 문서의 목적

이 문서는 DKS-C 개발 Gateway Cluster의 Worker VM 한 대를 의도적으로 제거하는 장애 모의훈련에서, **무엇을 변화시키고**, **각 Control Plane이 그 변화를 언제 감지하며**, **어떤 Resource 연결로 대체 Worker와 Gateway 기능이 복구되고**, **어느 Evidence까지 확인해야 사용자 관점의 복구를 말했다고 할 수 있는지** 설명합니다.

핵심은 VM 삭제를 훈련 결과로 보지 않고 다음 상태를 구별하는 것입니다.

```text
장애 주입
  ≠ 장애 감지
  ≠ 인프라 대체 생성
  ≠ Kubernetes Node 복구
  ≠ Gateway Workload 복구
  ≠ 사용자 요청 복구
```

현재 원자료는 실행 전 검토 단계의 계획이며 이 문서는 특정 VM 삭제나 운영 변경을 승인하지 않습니다. 대상 Worker 수와 개발·운영 URL 표기에 자료 간 불일치가 있으므로 실제 실행 전 현행 Cluster·Machine·VM·Route를 다시 확정해야 합니다.

## 전체 이해 지도

```text
Gateway Worker 모의훈련 이해 골격
│
├─ Baseline
│  ├─ 현재 Worker / Machine / VM 대응
│  ├─ Gateway Pod / Endpoint 분산
│  ├─ 대체 VM 생성 자원
│  ├─ Monitoring·Alert 경로
│  └─ 개발계 사용자 Request
│
├─ 단일 장애 주입
│  └─ 승인된 Worker VM 한 대 제거
│
├─ 감지
│  ├─ vCenter VM 상태
│  ├─ CAPI Machine·Infrastructure Condition
│  ├─ Kubernetes Node Condition
│  └─ Alert·운영 Notification
│
├─ 자동 복구
│  ├─ desired replicas 차이
│  ├─ 대체 Machine / VirtualMachine
│  ├─ VM boot / kubelet Join
│  └─ Node Ready
│
└─ 기능 인계
   ├─ Gateway Pod Ready
   ├─ Service Endpoint 반영
   ├─ APISIX·Keycloak 기능
   └─ 개발계 사용자 Request 성공
```

- **훈련 대상은 “Gateway Worker 한 대”라는 이름이 아니라 vCenter VM·CAPI Machine·Kubernetes Node·실행 Pod가 같은 대상을 가리키는지 확인한 뒤 정해집니다.** VM 이름만 보고 선택하면 다른 Revision의 Worker나 Control Plane을 제거할 수 있습니다. 대상 Identity가 닫히기 전에는 장애 주입의 원인과 영향 범위를 해석할 수 없습니다.

```text
vCenter VM ID / Name
        ↕ Provider·Instance 정보
CAPI Machine UID
        ↕ NodeRef
Kubernetes Node UID / Name
        ↕ spec.nodeName
Gateway Pod / Endpoint
```

- **Worker VM 삭제는 장애를 만드는 행위이고 자동 복구는 별도의 인과 사슬입니다.** MachineDeployment가 원하는 replicas를 유지하고, Controller가 VM 손실을 인식하며, Supervisor Namespace·Zone·Storage·Network가 대체 VM을 만들 수 있어야 새 Worker가 생깁니다. VM을 삭제했다는 사실만으로 CAPI가 반드시 복구를 시작하거나 성공한다고 가정하지 않습니다.

```text
Worker VM 상실
   ↓ Controller가 실제 상태 차이 인식
MachineDeployment desired > available
   ↓
Replacement Machine
   ↓ Quota·Compute·Storage·Network
Replacement VirtualMachine
   ↓ Boot·Bootstrap·API 연결
Node 등록 / Ready
```

- **서비스 영향은 Node 개수보다 삭제 대상 Node에 있던 Ready Pod와 살아남은 Endpoint, 대체 Pod가 배치될 조건에 의해 결정됩니다.** APISIX·Keycloak 같은 핵심 Pod가 여러 Worker에 분산되고 살아남은 Ready Endpoint가 있으면 Node 장애 중에도 사용자 기능이 유지될 수 있습니다. 반대로 단일 Replica·Affinity·Resource 부족·Volume 제약이 있으면 Worker Capacity가 남아도 기능이 중단될 수 있습니다.

```text
Worker 한 대 상실
   ├─ 살아남은 Ready Endpoint 있음
   │      └─ 일부 또는 전체 기능 유지 가능
   └─ Ready Endpoint 없음 / 대체 배치 불가
          └─ 사용자 경로 영향 가능
```

- **감지·인프라 복구·Workload 복구·사용자 경로 복구는 서로 다른 시각과 증거를 가집니다.** vCenter에서 VM이 사라진 시각, Machine Condition 변화, Node NotReady, Alert Firing, 대체 VM 생성, 새 Node Ready, Pod·Endpoint 회복, 실제 Request 정상화는 동시에 일어나지 않을 수 있습니다. Timeline을 분리해야 어느 구간이 복구 지연을 만들었는지 알 수 있습니다.

```text
T0 VM 삭제
 → T1 Machine/Infra 감지
 → T2 Node Condition 변화
 → T3 Alert·Notification
 → T4 대체 Machine/VM
 → T5 새 Node Ready
 → T6 Pod·Endpoint Ready
 → T7 실제 사용자 Request 정상
```

## 1. “Gateway Worker 한 대”는 어떤 Resource 연결로 식별하는가?

훈련에서 제거하는 대상은 vCenter의 실제 VM 한 대입니다. CAPI `Machine`·Kubernetes `Node` Resource를 삭제하는 것과 같은 작업이 아닙니다. 각각 다른 Controller 경로를 유발할 수 있으므로 훈련 목적에 없는 Resource 삭제로 대체하지 않습니다.

| 계층 | 확인 대상 | 무엇을 나타내는가 | 잘못 식별했을 때 위험 |
|---|---|---|---|
| vCenter | Worker VM | 실제 Guest OS VM | 다른 VM·Control Plane 제거 |
| CAPI | `MachineDeployment` | 원하는 Worker 수·Update 정책 | 복구 Owner 오판 |
| CAPI | `MachineSet` | 특정 Revision의 Machine 집합 | 다른 Revision 선택 |
| CAPI | `Machine` | Worker 한 대의 Lifecycle | VM·Node 대응 불일치 |
| Kubernetes | `Node` | kubelet이 등록한 Worker | 실제 VM과 다른 Node 관측 |
| Workload | Pod | APISIX·Keycloak 등 실행 Process | 서비스 영향 예측 실패 |
| Service | EndpointSlice | 현재 Traffic 수신 가능 Pod | 사용자 경로 영향 오판 |

삭제 후보를 정할 때 다음을 같은 대상으로 연결합니다.

1. Node Name·UID
2. Node를 소유한 CAPI Machine과 `NodeRef`
3. MachineSet·MachineDeployment 소속
4. Infrastructure Provider ID·vCenter VM ID/Name
5. Zone·ESXi Host 위치
6. 해당 Node의 Gateway 핵심 Pod
7. Service Endpoint에서 그 Pod가 차지하는 역할

이 대응이 끝나야 “이 VM 상실이 어느 Capacity와 Endpoint를 제거하는가?”라는 인과 주장을 만들 수 있습니다.

## 2. 왜 실행 전에 Worker 수와 URL 불일치를 먼저 닫아야 하는가?

훈련 요청서는 개발 Gateway Worker **5대 중 1대** 삭제를 전제로 하지만 운영 현황 스냅샷은 `dev-dksg-ic01-khm` Worker를 **3대**로 기록합니다.

두 자료 중 하나를 추정으로 선택하지 않습니다.

- 운영 현황은 과거 스냅샷일 수 있습니다.
- 훈련 요청서는 이후 증설 상태를 반영했을 수 있습니다.
- 요청서의 수량이 잘못됐을 수도 있습니다.

실행 시점에 다음을 같은 시각으로 대조합니다.

```bash
kubectl --context="$GATEWAY_CONTEXT" get nodes -o wide

kubectl --context="$MANAGEMENT_CONTEXT" -n "$GATEWAY_NAMESPACE" \
  get machinedeployments,machinesets,machines -o wide
```

여기에 vCenter Inventory를 연결해 Control Plane VM이 후보에 섞이지 않았는지 확인합니다.

URL에도 같은 문제가 있습니다. 요청서 일부에는 운영계와 개발계 표기가 섞여 있습니다. 개발 Gateway Worker 장애를 검증하면서 운영 URL만 성공하면 다른 환경의 정상 상태를 본 것일 수 있습니다.

훈련 전 사용자 경로를 다음처럼 닫습니다.

```text
개발계 사용자 FQDN
  ↓ DNS
개발계 VIP / LB Virtual Service
  ↓ Backend Pool
Gateway Kubernetes Service
  ↓ Endpoint
APISIX Listener / Route / Upstream
  ↓
검증 대상 Backend 또는 User Cluster API
  ↓
필요한 Authentication과 기대 Response
```

이 연결이 확인돼야 T7의 Request 결과가 실제 개발 Gateway 복구 증거가 됩니다.

## 3. 이 훈련이 검증하려는 인과 가설은 무엇인가?

장애 모의훈련은 단순 이벤트가 아니라 사전에 정한 가설과 Evidence를 비교하는 실험입니다.

### 가설 A — CAPI가 원하는 Worker 수를 복구한다

```text
Worker VM 한 대 상실
+ MachineDeployment desired replicas 유지
+ Controller와 Infrastructure Provider 정상
+ Quota·Capacity·Network 충족
→ 대체 Machine·VM·Node 생성
```

깨질 수 있는 지점:

- VM 직접 삭제가 Provider 상태와 올바르게 조정되지 않음
- MachineDeployment Owner·Replica 정책이 기대와 다름
- Supervisor Namespace Quota 부족
- Zone Compute·Storage 부족
- VM Image·Bootstrap·API Join 실패

### 가설 B — 핵심 Gateway 기능은 남은 Replica 또는 대체 Pod로 유지·복구된다

```text
Worker 한 대 상실
+ 핵심 Component Replica 분산
+ 살아남은 Ready Endpoint
또는
+ 다른 Worker에 대체 Pod 배치 가능
→ Gateway 기능 유지·복구
```

깨질 수 있는 지점:

- 핵심 Component가 단일 Replica
- 모든 Replica가 같은 Worker에 있음
- Anti-Affinity·Taint·Resource로 대체 배치 불가
- Persistent Volume Attach 제약
- Readiness·Leader Election 교착

### 가설 C — Monitoring과 운영 전파가 장애와 복구를 구분해 관측한다

```text
VM·Machine·Node 상태 변화
+ Alert Rule·Evaluation·Notification 경로 정상
→ 운영자가 장애를 감지하고 복구 Timeline을 재구성
```

깨질 수 있는 지점:

- 해당 Rule 없음
- Evaluation Interval·for-duration 지연
- Notification Route 미구성
- Monitoring 자체 장애
- VM·Machine·Node 식별자 연결 실패

### 가설 D — 사용자 기능 복구는 인프라 복구 뒤 실제 Request로 확인된다

```text
새 Node Ready
+ Gateway Pod Ready
+ Service Endpoint 반영
+ LB/APISIX Route 정상
+ 인증·Backend 정상
→ 개발계 사용자 Request 성공
```

새 Node Ready는 이 결론의 충분조건이 아닙니다.

## 4. 장애 전 Baseline에서는 무엇을 기록해야 하는가?

Baseline 없이 훈련하면 장애 전부터 있던 문제를 장애 주입 결과로 오해할 수 있습니다.

### Worker와 자동 복구 경로

| Baseline | 실제 질문 |
|---|---|
| MachineDeployment desired replicas | Controller가 유지하려는 Worker 수는 몇 대인가? |
| MachineSet·Machine | 어느 Revision·Owner에 속하는가? |
| Node Ready | 모든 Gateway Worker가 현재 Ready인가? |
| vCenter VM | Node와 대응하는 VM이 존재·Power On인가? |
| Supervisor Namespace Quota | 대체 VM·Disk를 허용할 여유가 있는가? |
| Zone·Storage Capacity | 실제 배치 자원이 있는가? |
| VPC·Network | 새 VM이 사용할 Network·IP가 준비돼 있는가? |

“VM을 직접 삭제하면 CAPI가 자동 복구한다”는 것은 Machine Owner·Controller Policy·Provider Reconciliation을 확인한 뒤 훈련 가설로 확정합니다. 이 경로가 확인되지 않으면 단순 파괴 시험이 될 수 있습니다.

### Pod와 Endpoint

```bash
kubectl --context="$GATEWAY_CONTEXT" \
  get pods -A -o wide \
  --field-selector="spec.nodeName=$NODE_NAME"

kubectl --context="$GATEWAY_CONTEXT" get pdb -A
```

핵심 Component별로 다음을 기록합니다.

- Deployment·StatefulSet의 Desired/Ready Replica
- Pod별 Node 배치
- PDB와 `disruptionsAllowed`
- Affinity·Anti-Affinity·Taint/Toleration
- Resource Request와 다른 Worker의 가용량
- Persistent Volume 사용 여부
- Service·EndpointSlice의 Ready Endpoint
- Leader Election·Readiness처럼 기능 인계에 필요한 Application 상태

PDB는 계획된 Eviction을 제한하는 장치이며 갑작스러운 VM 상실 자체를 막지 않습니다. VM 손실 뒤 대체 Pod 배치 과정과 관리자가 수행할 Drain·Eviction에는 별도로 영향을 줄 수 있습니다.

### 사용자 경로

장애 전에도 실제 개발계 Request를 실행해 정상 Baseline을 남깁니다.

- DNS 결과
- TLS·Authentication 성공
- HTTP Status뿐 아니라 기대 Response·상태 변화
- APISIX Request ID·Access Log
- Backend 처리 결과

인증 없는 Health Endpoint만으로 User 기능을 대표하지 않습니다.

### Monitoring·Notification

다음 Alert가 실제 존재하는지와 어디로 전달되는지 확인합니다.

- VM·Machine 상태
- Node NotReady
- Pod·Replica 부족
- APISIX·Service Health
- CAPI Reconciliation 실패
- 대체 VM 생성 실패

Alert 이름이 문서에 있다는 사실만으로 Notification이 운영자에게 전달된다고 보지 않습니다.

## 5. 장애 주입 시 무엇을 한 변수로 유지해야 하는가?

승인된 담당자는 사전에 확정한 개발 Gateway Worker VM 한 대만 장애 대상으로 제거합니다.

원인 분리를 위해 동시에 다음을 변경하지 않습니다.

- MachineDeployment replicas
- CAPI Machine·MachineSet
- PDB·Replica 수
- APISIX Route·Upstream
- LB Pool·Health Check
- Supervisor Namespace Quota
- 다른 Worker·Control Plane VM
- 인증 Credential·Backend 설정

여러 변수를 동시에 바꾸면 복구가 어떤 조건에서 시작되거나 막혔는지 구분할 수 없습니다.

장애 주입 시 기록할 것은 다음입니다.

- 승인된 작업·담당자
- VM ID·Name
- 연결된 Machine·Node UID
- 삭제 시각 T0
- 직전 Pod·Endpoint 상태
- 예상 중단·중지 조건

예상 밖의 다중 Node·Control Plane·운영계 영향이 나타나면 추가 주입을 중단하고 실제 장애 대응으로 전환합니다.

## 6. 장애는 어느 계층에서 어떤 시차로 감지되는가?

VM이 사라져도 모든 계층이 동시에 상태를 바꾸지 않습니다.

### vCenter와 CAPI

- vCenter에서 VM이 사라지거나 Power 상태가 바뀝니다.
- Machine이 참조하는 Infrastructure Resource Condition이 달라질 수 있습니다.
- MachineDeployment·MachineSet Controller가 desired와 actual 차이를 인식합니다.
- 복구 조건이 맞으면 Replacement Machine·VM 요청이 이어집니다.

### Kubernetes Node

VM 상실로 kubelet Heartbeat·Lease가 끊깁니다. Control Plane은 Grace Period 뒤 Node를 NotReady·Unknown 계열로 판단할 수 있습니다.

VM 삭제 시각과 Node Condition 변화 시각은 다릅니다.

### Pod와 Endpoint

Node 상태 변화와 Pod 재배치도 같은 순간이 아닙니다.

- Stateful/Stateless Controller 종류
- Node Failure 처리 시간
- 다른 Worker 가용 Resource
- Affinity·Topology 조건
- Volume Attach 가능 여부
- Pod Readiness·Leader Election

Pod가 Ready를 잃으면 EndpointSlice에서 Traffic 대상이 변경될 수 있습니다. 살아남은 Ready Endpoint가 있으면 Node가 NotReady여도 서비스가 유지될 수 있습니다.

### Monitoring과 운영 전파

Alert Firing은 Rule Evaluation Interval, `for` Duration, Notification Pipeline 때문에 실제 장애보다 늦을 수 있습니다.

따라서 다음 시각을 분리합니다.

| 시각 | 상태 |
|---|---|
| T0 | VM 삭제 |
| T1 | Machine·Infrastructure 이상 감지 |
| T2 | Node Condition 변화 |
| T3 | Alert Firing |
| T4 | 운영 Notification 수신 |
| T5 | Replacement Machine·VM 생성 시작 |
| T6 | 새 Node 등록·Ready |
| T7 | Gateway Pod·Endpoint 회복 |
| T8 | 실제 개발계 Request 정상화 |

이 Timeline으로 감지 지연, 인프라 생성 지연, Node Bootstrap 지연, Workload 인계 지연, 사용자 경로 지연을 구분합니다.

## 7. 자동 복구는 어떤 Resource 연결을 통과해야 하는가?

자동 복구의 출발점은 원하는 Worker 수와 실제 Worker 상태의 차이입니다.

```text
MachineDeployment desired replicas
        ↓
MachineSet이 필요한 Machine 수 조정
        ↓
Replacement Machine 생성
        ↓
Infrastructure Resource / VirtualMachine 요청
        ↓
Supervisor Namespace Quota·Zone·Storage·VPC 통과
        ↓
VM Boot / Bootstrap
        ↓
kubelet Node Registration
        ↓
Node Ready
```

각 연결은 실패할 수 있습니다.

| 마지막 상태 | 다음 Breakpoint 후보 |
|---|---|
| VM 상실 확인 | Controller가 Provider 상태 차이를 인식하지 못함 |
| Machine 상태 이상 | MachineDeployment Owner·Replica 조정 실패 |
| Replacement Machine 생성 | Quota·Compute·Storage·Network 실패 |
| VM Power On | Bootstrap·Cloud-init·API Endpoint 실패 |
| kubelet 실행 | Token·Certificate·DNS·Network Join 실패 |
| Node 등록 | CNI·CSI·Node Condition 문제로 NotReady |

새 Node Ready 뒤에도 Gateway Pod가 반드시 그 Node에 배치되는 것은 아닙니다. Scheduler는 전체 Cluster 상태와 Affinity·Resource 조건에 따라 배치합니다. 복구 목표는 “새 Node에 반드시 같은 Pod가 간다”가 아니라 필요한 Ready Replica와 Endpoint가 회복되는 것입니다.

## 8. Worker 한 대 상실이 사용자 서비스에 영향을 주는 조건은 무엇인가?

서비스 영향은 다음 조건의 결합으로 결정됩니다.

```text
삭제 Node의 핵심 Pod 수
+ 살아남은 Replica·Endpoint
+ 다른 Worker 가용 Resource
+ Scheduling·Affinity 조건
+ Volume·Leader Election 조건
+ LB/APISIX Health·Route
→ 실제 사용자 영향
```

### 영향이 제한될 수 있는 조건

- 핵심 Component가 여러 Ready Replica로 분산됨
- 살아남은 Endpoint가 Traffic을 처리할 Capacity를 가짐
- LB·Service가 NotReady Endpoint를 제외함
- 인증·Backend가 장애 Node와 독립됨

### 영향이 커질 수 있는 조건

- 단일 Replica 또는 Replica가 한 Node에 집중
- 다른 Worker에 Resource 여유 없음
- Hard Affinity·Topology 제약
- Volume Detach·Attach 지연
- Leader Lease·Readiness 교착
- 살아남은 Replica의 Capacity 부족
- LB Health Check와 Endpoint 상태 불일치

Node 수가 N-1이 됐다는 사실만으로 사용자 요청 실패율을 계산하지 않습니다. 실제 Pod·Endpoint·Request Evidence가 필요합니다.

## 9. 인프라 복구·Workload 복구·사용자 경로 복구는 어떻게 구별하는가?

### 인프라 복구

- MachineDeployment desired와 actual Worker 수가 다시 일치
- Replacement Machine·VirtualMachine 생성
- VM Power On·Bootstrap 완료
- 새 Node 등록·Ready

### Workload 복구

- APISIX·Keycloak 등 필요한 Controller의 Ready Replica 회복
- Pod가 정상 Worker에 배치
- 필요한 Volume 연결
- EndpointSlice에 Ready Endpoint 반영
- Leader·Session 등 Application 상태 정상

### 사용자 경로 복구

```text
Client
  ↓
개발계 DNS / VIP / LB
  ↓
Gateway Service / Endpoint
  ↓
APISIX Listener / Route / Upstream
  ↓
Authentication이 필요한 경우 Credential 검증
  ↓
Target Backend
  ↓
기대 Response·기능 결과
```

새 VM·Node가 생겼다는 사실은 Workload 복구 증거가 아니고, Pod Ready는 실제 사용자 경로 복구의 충분조건이 아닙니다.

## 10. 성공·실패 기준은 어떤 증거로 정하는가?

현재 원자료에는 승인된 수치형 RTO·허용 Error Rate가 확정돼 있지 않습니다. “5분 이내”, “완전 무중단” 같은 값을 임의로 넣지 않습니다.

훈련 전 다음 판정 항목과 Evidence를 승인받고 실제 시간을 측정합니다.

| 판정 영역 | 성공을 판단할 실제 Evidence |
|---|---|
| 대상 통제 | 승인된 개발 Gateway Worker VM 한 대만 제거 |
| 장애 감지 | VM·Machine·Node 상태와 Alert가 예상 경로로 관측 |
| Capacity 복구 | desired Worker 수를 Replacement Machine·VM·Node가 충족 |
| Workload 복구 | 필요한 Gateway Pod·Endpoint가 Ready |
| 사용자 경로 | 확정한 개발 URL/API가 필요한 인증 포함 정상 |
| 영향 범위 | Control Plane·다른 Cluster·운영계에 예상 밖 영향 없음 |
| 운영 전파 | 합의한 Notification·Communication 경로 동작 |
| Evidence | 상태 변화와 시각을 Timeline으로 재구성 가능 |

장애 중 Request 실패가 한 건이라도 있었다면 “완전 무중단”이라고 기록하지 않습니다. 반대로 짧은 Request 실패가 있었다고 자동 복구 자체가 실패했다고 합치지도 않습니다.

```text
인프라 자동 복구 성공 여부
        ≠
Workload 기능 복구 결과
        ≠
사용자 가용성 결과
```

## 11. 결과를 어떤 Timeline과 인과 Evidence로 남기는가?

| 시각 | 계층 | Evidence | 이 Evidence가 말하는 것 |
|---|---|---|---|
| T0 | vCenter | 삭제한 VM ID·Name | 실제 장애 주입 대상 |
| T1 | CAPI | Machine·Infrastructure Condition | Controller가 인프라 손실을 인지 |
| T2 | Kubernetes | Node Condition·Lease | kubelet 통신 중단 인지 |
| T3 | Monitoring | Alert Firing·Notification | 관측·전파 경로 동작 |
| T4 | CAPI/vCenter | Replacement Machine·VM | 인프라 대체 생성 시작 |
| T5 | Kubernetes | 새 Node 등록·Ready | Worker Capacity 참여 |
| T6 | Workload | Pod Ready·EndpointSlice | Gateway Traffic 수신 준비 |
| T7 | 사용자 경로 | 개발계 실제 Request | 최종 기능 유지·복구 |

각 행의 Evidence를 연결하면 느린 구간과 원인을 구분할 수 있습니다.

- T0→T1이 길다: Provider·CAPI 감지 경로 후보
- T1→T4가 길다: Reconcile·Quota·Capacity 후보
- T4→T5가 길다: VM Boot·Bootstrap·Join 후보
- T5→T6이 길다: Scheduling·Volume·Readiness 후보
- T6→T7이 길다: LB·APISIX·Authentication·Backend 후보

시간이 길다는 사실만으로 해당 구간의 특정 Component를 원인으로 확정하지 않고 Condition·Event·Log를 연결합니다.

## 12. 마지막 확인 상태에서 다음 검증 질문은 무엇인가?

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 Evidence |
|---|---|---|
| VM 대상만 식별 | 같은 Machine·Node인가? | Provider ID, NodeRef, UID |
| 현재 Worker 수 자료 불일치 | 실제 desired·actual 수는 얼마인가? | Node·Machine·VM 동시 조회 |
| VM 삭제 완료 | CAPI가 손실을 감지했는가? | Machine·Infra Condition |
| Node NotReady | 살아남은 Endpoint와 사용자 요청은 어떤가? | EndpointSlice·Request |
| Alert Firing | Notification이 운영자에게 도달했는가? | Delivery 기록 |
| Replacement Machine 없음 | Owner·Replica·Reconcile이 정상인가? | MachineDeployment·Controller Log |
| Machine은 있으나 VM 없음 | Quota·Compute·Storage·Network 중 어디서 막혔는가? | Event·Condition·Capacity |
| VM Power On | kubelet Join이 왜 안 되는가? | Bootstrap·Network·Credential |
| 새 Node Ready | Gateway Replica·Endpoint가 회복됐는가? | Deployment·Pod·Endpoint |
| Pod Ready | APISIX Route·인증·Backend Request가 성공하는가? | 실제 개발 Request·Log |
| 사용자 Request 성공 | Error Window와 영향 범위를 기록했는가? | Client Probe·Timeline |

## 13. 이 문서가 승인하지 않는 것은 무엇인가?

이 설명 문서는 다음 실행을 자동으로 승인하지 않습니다.

- 특정 VM의 실제 삭제
- Control Plane 또는 운영계 Resource 변경
- CAPI Machine·MachineSet 직접 삭제
- PDB 완화·Replica 변경
- Supervisor Namespace Quota 변경
- APISIX Route·LB Pool 변경
- Alert Rule·Notification Route 임의 변경
- 특정 RTO·SLO·무중단 기준 확정

실제 훈련은 대상·권한·중지 조건·연락 체계·복구 책임자·사후 검토 방식이 확정된 실행 계획과 승인 절차를 따라야 합니다.
