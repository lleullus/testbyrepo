# 06. 통합 신원·인증과 무인 서비스 Token — 누구의 신원을 어떤 Client가 어떤 Credential로 전달하고 언제 권한이 실제로 성립하는가?

## 문서의 목적

이 문서는 DKS-C에서 사람이 Console·Grafana·kubectl에 접속하는 과정과 Monitoring·CI/CD 같은 자동 프로그램이 API를 호출하는 과정을 구분하고, ADFS·Keycloak·OIDC Client·Authorization Code·Access/ID Token·Long-Term Token·Kubernetes RBAC가 어떤 상태를 차례로 만들며 무엇을 보장하지 않는지 설명합니다.

핵심은 **Login 성공**, **Token 발급**, **Token 검증**, **Identity 확인**, **Authorization 허용**, **실제 API 기능 성공**을 하나의 “인증 성공”으로 뭉치지 않는 것입니다. 자동 호출을 위한 Long-Term Token도 발급된 것과 소비자가 실제 사용하기 시작한 것, 옛 Token이 폐기된 것을 각각 나눠 봅니다.

DKS-C 내부 자료의 Client 이름·Lifetime·Token Exchange 흐름은 기록된 환경에 대한 근거입니다. 현재 Keycloak Version·Client Policy·Kubernetes OIDC 설정·P-DEP 연동 Credential은 실제 설정에서 재확인합니다.

## 전체 이해 지도

```text
DKS-C Identity 이해 골격
│
├─ 사람의 Login
│  ├─ Browser / kubectl
│  ├─ ADFS / Keycloak
│  ├─ Client / Redirect URI
│  └─ Authorization Code / Token
│
├─ Token 검증
│  ├─ Signature / Issuer
│  ├─ Audience / Authorized Party
│  ├─ Expiration
│  └─ User / Group Claim
│
├─ 권한 판단
│  ├─ Application Policy
│  └─ Kubernetes RBAC
│
├─ 자동 호출
│  ├─ Short-Lived Token
│  ├─ Long-Term Token Exchange
│  └─ ServiceAccount·다른 Machine Credential과 구분
│
└─ 운영 수명주기
   ├─ 발급
   ├─ 소비자 저장·반영
   ├─ 실제 API 호출
   └─ 교체·폐기
```

- **Keycloak Realm과 Client는 사내 Identity를 서비스별 Login·Token으로 연결하지만, 같은 Realm을 사용한다고 모든 서비스가 같은 Token과 Lifetime을 쓰는 것은 아닙니다.** `DKS` Realm은 User·Group·Client·Token Policy를 묶고, Console·Grafana·OpenSearch Dashboards·kubectl 등은 각각 별도 Client 설정을 가질 수 있습니다. ADFS Login이 성공해도 잘못된 Redirect URI·Audience·Client 설정이면 대상 서비스의 Token 흐름은 실패할 수 있습니다.

```text
사내 User
   ↓ ADFS Login / Federation
Keycloak DKS Realm
   ├─ dkssol-console Client
   ├─ grafana-oauth Client
   ├─ opensearch-dashboard-oauth Client
   ├─ kube-login / k8s-client
   └─ Long-Term Client

같은 Realm
    ≠
같은 Client 설정·Token 목적·Lifetime
```

- **Authorization Code가 Token으로 교환되고 Token이 검증돼도 API 작업 권한까지 자동으로 생기지는 않습니다.** Code는 Token 발급을 위한 일회용 값이고, Token 검증은 Issuer·Signature·Audience·Expiration 등을 확인해 Identity를 받아들이는 과정입니다. 그 Identity가 Pod 조회·Cluster 변경 같은 작업을 할 수 있는지는 Application Policy나 Kubernetes RBAC가 별도로 결정합니다.

```text
Browser Login
   ↓
Authorization Code
   ↓ Token Endpoint
Token 발급
   ↓ Resource Server 검증
Identity 확인
   ↓ RBAC / Application Policy
작업 허용 여부
   ↓
실제 API 처리 결과
```

- **자동 프로그램용 Long-Term Token은 사람의 Login에서 출발한 Token Exchange 경로로 기록되어 있으며 Kubernetes ServiceAccount Token이나 Client Credentials와 같은 것으로 취급할 수 없습니다.** 내부 가이드는 단기 User Access Token을 Long-Term Client로 Exchange하는 흐름을 기록합니다. Token 안에 User와 발급 Client 정보가 함께 남을 수 있으므로 “자동 프로그램이 사용한다”는 이유만으로 Machine Identity가 되는 것은 아닙니다.

```text
User Login
   ↓
Short-Lived User Access Token
   ↓ Token Exchange + Long-Term Client
Long-Term Access Token
   ↓
자동 프로그램의 Bearer Credential

이 경로
  ≠ Kubernetes ServiceAccount Token
  ≠ 독립 Machine Client Credentials라고 자동 판단
```

- **Token 수명은 Client 이름이나 설정표보다 실제 발급 Token의 `exp`와 수신 서비스의 검증 결과로 판단합니다.** 내부 자료에는 30·90·120·180일 Client 설정과 실제 365일 Token 발급 기록이 동시에 있습니다. 이 불일치를 설명할 Keycloak Policy·Version 근거가 없으므로 Client 이름에서 만료 시각을 계산하지 않습니다.

- **새 Token 발급은 교체 시작일 뿐 완료가 아닙니다.** 실제 소비자의 Secret·Environment·Config에 반영하고 Process가 새 값을 읽도록 해야 하며, 인증이 필요한 API에서 기대한 Identity와 권한으로 성공해야 합니다. 저장소에서 옛 Token 문자열을 지웠다고 이미 복사된 Token이 즉시 무효화되는지도 별도 확인해야 합니다.

## 1. ADFS·Keycloak Realm·Client는 각각 무엇을 담당하는가?

내부 SW 자료는 Gateway Cluster의 Keycloak을 사내 ADFS SSO와 연동된 OIDC 중앙 인증 Component로 기록합니다. APISIX는 Routing을, Keycloak은 Identity·Token을 담당하므로 두 기능을 같은 “Gateway 인증”으로 합치지 않습니다.

Keycloak의 `Realm`은 User·Group·Client·Session·Token Policy를 분리하는 관리 범위입니다. DKS-C 자료는 `DKS` Realm을 기록합니다.

`Client`는 Keycloak과 인증을 주고받는 Application 또는 Service 등록입니다. Client마다 다음이 다를 수 있습니다.

- Redirect URI
- Public/Confidential Client 여부와 인증 방식
- Access Token Lifetime
- Session 설정
- Allowed Flow·Scope
- Audience·Protocol Mapper

내부 자료에 기록된 Client는 다음과 같습니다.

| Client | 기록된 목적 | 기록된 주요 수명 설정 |
|---|---|---|
| `dkssol-console` | DKS-C Console OIDC Login | Access Token 30분 |
| `grafana-oauth` | Grafana Login | Realm 기본값 |
| `opensearch-dashboard-oauth` | OpenSearch Dashboards Login | Realm 기본값 |
| `kube-login` | kubectl OIDC Login | Access Token·Offline Session Idle 8시간, Client Session Max 28,900초 |
| `k8s-client` | kube-apiserver OIDC 설정 | Realm 기본값 |
| `dks-cluster-mgmt` | console-vcfa → Console API 시스템 호출 | Realm 기본값 |
| `k8s-cluster-admin` | 관리자 기능용 시스템 계정 | Realm 기본값 |
| `dkssol-console-longterm-client` | Console·Monitoring·OpenSearch 계열 장기 호출 | 365일 기록 |
| `k8s-longterm-client` | Cluster 접속 장기 Token | 365일 기록 |
| `k8s-longterm-client-30/-90/-120/-180` | 기간별 장기 Token 의도 | 30/90/120/180일 설정, 실제 365일 발급 예외 기록 |

Realm 기본값은 내부 자료에 SSO Session Idle 8시간, SSO Session Max 24시간, Access Token Lifespan 10분으로 기록되어 있습니다.

Session Lifetime과 Token Lifetime은 같은 상태가 아닙니다.

```text
SSO Session이 유효
        ≠
기존 Access Token이 아직 유효

Access Token 만료
        ≠
User Session이 끝남
        ≠
Client가 Refresh·재발급할 수 없음
```

## 2. Authorization Code는 어떻게 Token으로 바뀌며 어느 단계에서 실패할 수 있는가?

Authorization Code Flow에서는 User가 Browser에서 Login을 완료한 뒤 Client Redirect URI로 Authorization Code를 돌려받습니다. Code는 API 호출용 장기 Credential이 아니라 Token Endpoint에서 Token을 받기 위한 일회용 값입니다.

내부 Long-Term Token 가이드는 Console Client에 대해 다음 흐름을 기록합니다.

```text
User Browser
   ↓
Keycloak Authorization Endpoint
   ↓ ADFS 연동 Login
Client Redirect URI
   ↓ Authorization Code
Keycloak Token Endpoint
   ↓ Client·Code 검증
Short-Lived Token
```

원자료는 Code를 1회용, 1분 만료로 기록합니다. 이는 해당 DKS-C 설정 근거이며 모든 OIDC 환경의 고정값으로 일반화하지 않습니다.

각 단계의 성공은 다음 단계를 보장하지 않습니다.

| 확인 상태 | 확인되는 것 | 아직 남은 조건 |
|---|---|---|
| ADFS Login 성공 | 사내 Identity Provider가 User를 인증 | Keycloak Federation·Client 흐름 |
| Keycloak Session 생성 | Realm Login 상태 존재 | Client Redirect·Code 발급 |
| Authorization Code 발급 | Client로 돌아갈 일회용 교환값 생성 | Token Endpoint 교환 성공 |
| Token 발급 | Keycloak이 Credential 발행 | Resource Server의 검증·권한 |
| Browser가 Token 보유 | Client가 Token을 받음 | Backend 전달·저장·재발급 방식 |

Code 교환이 성공했다는 사실만으로 Console Frontend·Backend가 Token을 어디에 저장하고 어느 Header에 넣는지까지 알 수 없습니다. 실제 Application 구현을 확인합니다.

## 3. Token 검증과 Authorization은 왜 서로 다른 판단인가?

JWT에는 발급자·Subject·Audience·만료 시각 같은 Claim이 들어갈 수 있습니다.

| Claim | 의미 |
|---|---|
| `iss` | Token Issuer |
| `sub` | Subject/User 식별자 |
| `aud` | Token 대상 Audience |
| `azp` | 발급에 참여한 Authorized Party/Client |
| `preferred_username` | User 이름 |
| `groups` | Group 정보 |
| `exp` | 만료 시각 |

**Authentication**은 Token을 신뢰할 수 있고 누구를 나타내는지 판단합니다.

- Signature가 신뢰 Key로 검증되는가
- `iss`가 기대 Issuer인가
- `aud`가 현재 Resource Server에 맞는가
- `exp`가 지나지 않았는가
- Username·Group Claim Mapping이 기대한 형태인가

**Authorization**은 인증된 Identity가 요청한 작업을 할 수 있는지 판단합니다.

Kubernetes에서는 Role·ClusterRole의 Rule과 RoleBinding·ClusterRoleBinding이 User·Group·ServiceAccount에 권한을 연결합니다.

다음 문장은 각각 별도 상태입니다.

```text
JWT 구조를 decode할 수 있다
        ≠
Signature가 유효하다
        ≠
Audience가 맞다
        ≠
User Identity가 확인됐다
        ≠
그 User가 Pod를 조회할 권한이 있다
        ≠
요청한 API 작업이 실제 성공했다
```

401과 403도 같은 실패가 아닐 수 있습니다. 일반적으로 401은 Authentication 실패 후보, 403은 인증된 Identity의 Authorization 실패 후보지만, 앞단 Proxy·Application이 자체 Status를 반환할 수도 있으므로 실제 응답 주체와 Log를 확인합니다.

## 4. ID Token과 Access Token은 왜 이름이 비슷해도 목적이 다른가?

OIDC의 ID Token은 Authentication 결과로 User Identity를 Client에 전달하는 Token입니다. OAuth Access Token은 Resource Server/API 호출을 위한 Authorization Credential입니다.

둘 다 JWT 형식일 수 있으므로 Payload 모양만으로 목적을 판단하면 안 됩니다.

Kubernetes의 전통적인 OIDC 사용자 인증 문서는 ID Token을 Bearer Token으로 API Server에 제시하는 흐름을 설명합니다. 내부 Keycloak 자료에 `kube-login`의 **Access Token Lifespan**이 기록돼 있다는 사실만으로 kube-login Plugin이 Access Token을 API Server에 보낸다고 확정할 수 없습니다.

실제 kubectl·API Server 흐름에서는 다음을 확인합니다.

- Plugin이 어느 Token Field를 Kubeconfig Credential로 반환하는가
- API Server의 `--oidc-issuer-url`, Client ID/Audience 설정은 무엇인가
- Username·Group Claim은 무엇인가
- Token의 `aud`가 API Server 기대값과 맞는가
- Refresh·Offline Session을 어떻게 사용하는가

## 5. 자동 프로그램의 Long-Term Token은 어떤 연결로 발급되는가?

자동 프로그램은 매 요청마다 Browser Login을 수행하기 어렵습니다. DKS-C 내부 자료는 Monitoring·OpenSearch 등의 자동 호출에 사용할 Long-Term Access Token 발급 경로를 별도로 기록합니다.

```text
1. User가 Console Client로 Login
        ↓
2. Authorization Code 획득
        ↓
3. Code를 Short-Lived User Access Token으로 교환
        ↓
4. Long-Term Client Credential을 사용한 Token Exchange
        ↓
5. Long-Term Access Token 발급
```

이 경로의 출발점은 User Authentication입니다. 따라서 다음과 동일하지 않습니다.

- Kubernetes ServiceAccount Token 발급
- 독립 Machine Identity의 Client Credentials Grant
- 임의의 Refresh Token 연장
- Client Secret 자체를 API Bearer Token으로 사용

Long-Term Token Claim에는 Keycloak Realm Issuer, User Subject, 발급에 참여한 Long-Term Client, Audience가 함께 나타날 수 있습니다.

| Claim | Long-Term Token에서 구별할 대상 |
|---|---|
| `iss` | Token을 발급한 Keycloak Realm |
| `sub`·`preferred_username` | Token이 나타내는 User |
| `azp` | Exchange에 참여한 Client |
| `aud` | 수신 대상으로 지정된 API·Client |

Long-Term Client로 Exchange했다고 Issuer가 Client로 바뀌는 것이 아니고, 자동 프로그램이 사용한다고 User Token이 ServiceAccount Token으로 바뀌는 것도 아닙니다.

한 발급 예시만으로 모든 Token에서 Subject·Audience·Group이 같은 방식으로 유지된다고 일반화하지 않습니다.

## 6. 설정된 Lifetime과 실제 Token 만료가 다르면 무엇을 기준으로 판단하는가?

내부 Client 목록은 `k8s-longterm-client-30/-90/-120/-180`에 각각 기간 설정을 기록합니다. 같은 자료의 예외 항목은 실제 Access Token이 365일로 발급된다고 기록합니다.

현재 자료만으로 다음 경쟁 설명을 구분할 수 없습니다.

- Client Override가 Exchange Token에 적용되지 않음
- Realm·Exchange Policy가 365일을 강제함
- Version·Extension 동작 차이
- 기록 시점이나 대상 Client가 다름

따라서 결론을 다음 범위로 제한합니다.

```text
Client 이름·설정표
  → 의도 또는 설정 기록

실제 발급 Token의 exp
  → 그 Token Payload에 기록된 만료 시각

Resource Server의 응답
  → 현재 시점에 실제로 Token을 수용·거부한 결과
```

JWT Payload를 Base64url Decode하는 것은 Claim을 읽는 작업일 뿐 Signature 검증이 아닙니다.

```python
import base64
import json
import os
from datetime import datetime, timezone

payload = os.environ["LONG_TERM_TOKEN"].split(".")[1]
payload += "=" * (-len(payload) % 4)
claims = json.loads(base64.urlsafe_b64decode(payload))
print(datetime.fromtimestamp(claims["exp"], timezone.utc).isoformat())
```

Token 원문·Client Secret은 Log나 문서에 출력하지 않습니다.

## 7. 새 Token이 실제 소비자에 반영되는 과정은 무엇인가?

새 Token을 발급한 뒤에는 실제 프로그램이 읽는 Credential 저장 위치를 찾아야 합니다.

```text
새 Token 발급
   ↓
Secret / Environment / Config / External Store 갱신
   ↓
Process가 새 값 Reload 또는 Restart
   ↓
새 Token으로 실제 Request 전송
   ↓
Resource Server Authentication
   ↓
Authorization과 기능 성공
```

전달 방식에 따라 반영 조건이 다릅니다.

| 전달 방식 | Resource 변경 후 남는 조건 |
|---|---|
| Environment Variable | 기존 Process는 자동 갱신되지 않으므로 재기동 필요 가능 |
| Secret Volume File | kubelet 갱신 후 Application이 File을 다시 읽어야 함 |
| `subPath` Mount | 일반 Secret Volume과 갱신 동작이 다름 |
| Application Config File | Reload 기능이나 재기동 필요 가능 |
| External Secret Store | Fetch·Cache·Rotation 주기를 확인 |

Health Endpoint가 인증 없이 200을 반환하면 그 응답은 Token 유효성을 구분하지 못합니다. 실제 인증·권한이 필요한 API를 호출해 기대 Identity와 작업 결과를 확인합니다.

## 8. 새 Token을 쓰기 시작하면 옛 Token은 자동으로 폐기되는가?

Bearer Token은 문자열을 가진 주체가 제시할 수 있는 Credential입니다. Kubernetes Secret의 Base64 Encoding도 암호화가 아닙니다.

새 Token을 소비자에 반영하고 저장소에서 옛 문자열을 지워도 다음 위치에 복사본이 남을 수 있습니다.

- 다른 Secret·Config
- Process Memory
- CI/CD Credential Store
- Backup·Artifact
- Log·Shell History에 잘못 노출된 값

또한 수신 서비스가 JWT를 Public Key로 Local Validation하면 Keycloak Logout·Client Secret 변경·원본 저장소 삭제가 이미 발급된 Token을 `exp` 이전 즉시 거부하는지 별도 확인해야 합니다.

즉 다음 상태는 다릅니다.

```text
옛 Token 저장소에서 제거
        ≠
모든 소비자가 새 Token 사용
        ≠
옛 Token이 더 이상 어디에도 존재하지 않음
        ≠
Resource Server가 옛 Token을 즉시 거부
```

즉시 폐기가 요구되면 Keycloak과 수신 서비스의 Revocation·Session·Policy 동작을 확인합니다.

## 9. 인증 문제를 마지막 확인 상태에서 어떻게 좁히는가?

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 증거 |
|---|---|---|
| ADFS Login 성공 | Keycloak Realm Session과 Client Flow가 생성됐는가? | Keycloak Event, Browser Redirect |
| Keycloak Login 성공 | 올바른 Client·Redirect URI로 Code가 발급됐는가? | Authorization Request·Redirect |
| Code 발급 | Token Endpoint 교환이 성공했는가? | Token Endpoint Status·Error |
| Token 발급 | Signature·Issuer·Audience·Expiration이 수신 서비스 기대와 맞는가? | Resource Server Auth Log, Token Metadata |
| Identity 확인 | 필요한 Group·Username Mapping이 맞는가? | Claim과 Server Mapping 설정 |
| Authentication 성공 | 요청 작업 권한이 있는가? | RBAC `can-i`, Authorization Log, 403 주체 |
| 새 Long-Term Token 발급 | 소비자가 실제 새 값을 읽는가? | Pod Spec·Secret Version·Process Reload |
| 새 Token으로 Health 200 | 인증이 필요한 API도 성공하는가? | Protected API Request와 Audit Log |
| 새 Token 사용 확인 | 옛 Token이 실제로 거부되는가? | Revocation/Session 정책과 별도 검증 |
| Client 설정표와 `exp` 불일치 | 어느 Policy·Version이 실제 Lifetime을 결정하는가? | Current Client/Realm/Exchange 설정, 발급 Token 비교 |

이 표는 “인증이 안 된다”는 하나의 증상을 Login·발급·검증·Mapping·권한·소비자 반영으로 분해합니다. 한 단계의 성공을 뒤 단계의 증거로 사용하지 않습니다.
