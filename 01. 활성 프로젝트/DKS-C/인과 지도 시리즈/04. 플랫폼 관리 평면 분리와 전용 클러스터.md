# 04. 플랫폼 관리 평면 분리와 전용 클러스터 — 어떤 고장은 Cluster 경계에 머물고 어떤 의존성은 경계를 넘어 전달되는가?

## 문서의 목적

이 문서는 DKS-C에서 사용자의 애플리케이션을 실행하는 User Cluster와 Console·Gateway·Monitoring·Logging·DevOps 기능을 실행하는 관리 Cluster를 분리하면 무엇이 실제로 독립되는지, 관리 Cluster들이 API·Messaging·Registry를 통해 어떻게 하나의 플랫폼 기능을 구성하는지, 그리고 Kubernetes Cluster가 나뉘어도 어떤 VPC·Storage·ESXi·관리 API를 공유해 공동 장애 원인을 가질 수 있는지 설명합니다.

핵심은 **Kubernetes Resource와 Node의 소유 경계**, **서비스 호출·데이터 의존성**, **물리·가상 인프라 공유 범위**를 각각 나눠 보는 것입니다. Cluster가 다르다는 사실만으로 기능 영향과 물리 장애 영향이 모두 분리됐다고 결론내리지 않습니다.

배치 이름·Worker 수·Storage 용량은 내부 운영 현황의 기록값이며 시점이 있는 스냅샷입니다. 현재 상태를 판단할 때는 실제 Cluster·VM·Storage·Network 인벤토리와 대조합니다.

## 전체 인과 지도

이 문서는 **병원 캠퍼스**를 하나의 비유 세계로 사용합니다. User Cluster와 Console·Gateway·Monitoring·Logging·DevOps Cluster는 역할이 다른 독립 건물, Cluster 내부 Pod·Resource는 각 건물의 인력과 장비, API·Message·Image·Telemetry 흐름은 건물 사이 업무 전달, VPC·Storage·ESXi·vCenter·Identity는 여러 건물이 함께 쓰는 도로·전력·창고·행정 시스템에 대응합니다. 비유는 역할과 의존성을 보여주기 위한 것이며 실제 장애 범위는 호출 경로와 인프라 배치 증거가 기준입니다.

```text
DKS-C 관리 평면이 분리되면서도 하나의 플랫폼으로 동작하는 전체 골격

Kubernetes 실행 경계 분리
  User / Console / Gateway / Monitoring / Logging / DevOps Cluster
        ↓
Cluster 사이 기능 의존성 형성
  API / Proxy / Messaging / Telemetry / Registry
        ↓
배포·변경 관리 경계 분리
  argocd-admin-instance / argocd-vks-instance
        ↓
공유 인프라와 공통 서비스 유지 가능
  VPC / Transit / Storage / ESXi / vCenter / Identity / Registry
        ↓
장애 영향은 Cluster 경계 + 호출 관계 + 공유 기반을 함께 보고 결정
```

### 블록 1 — Kubernetes 실행 상태와 Resource 수명주기를 Cluster별로 분리한다

#### 기술적 목표

User Workload와 플랫폼 관리 기능을 서로 다른 Kubernetes Control Plane·Worker 집합에 배치해 Resource와 Node Lifecycle의 직접 변경 범위를 Cluster별로 나눕니다.

#### 비유

병원의 응급동·검사동·행정동을 별도 건물로 운영하면 한 건물의 내부 설비 공사가 다른 건물의 설비를 직접 바꾸지는 않습니다. 각 건물은 자체 출입구와 시설 관리 체계를 가집니다. 그러나 환자 이송이나 검사 의뢰가 건물 사이를 오가면 한 건물의 장애가 다른 건물의 업무 결과에 나타날 수 있습니다.

#### 본문

DKS-C의 User Cluster와 Console·Gateway·Monitoring·Logging·DevOps Cluster는 각각 별도의 Kubernetes API·etcd·Worker VM 집합을 가질 수 있습니다. 한 Cluster에 만든 Deployment·CRD·ClusterRole·Machine이 다른 Cluster API의 같은 Resource를 자동으로 생성하거나 변경하지 않습니다. Node 교체와 Pod Scheduling도 해당 Cluster의 Worker 집합 안에서 이뤄집니다.

이것이 보장하는 것은 **Kubernetes 실행 경계의 분리**입니다. 서비스 독립성까지 보장하는 것은 아닙니다. Console Backend가 User Cluster API를 호출하거나 DevOps Cluster가 Target Cluster에 배포한다면, Target API·Credential·Network 실패가 다른 Cluster의 기능 실패로 관측될 수 있습니다.

#### ASCII

```text
User Cluster API / etcd / Worker
Console Cluster API / etcd / Worker
Gateway Cluster API / etcd / Worker
Monitoring Cluster API / etcd / Worker
Logging Cluster API / etcd / Worker
DevOps Cluster API / etcd / Worker

각 Cluster의 Resource / Node Lifecycle은 분리
                 │
                 └─ 그러나 API·Proxy·Deploy·Telemetry 호출은 경계를 넘을 수 있음
```

### 블록 2 — 분리된 관리 Cluster를 서비스 호출과 데이터 흐름으로 다시 연결한다

#### 기술적 목표

Console·Gateway·Monitoring·Logging·DevOps가 서로 다른 기능을 맡으면서 API·Message·Telemetry·Image 흐름을 통해 하나의 사용자 경험을 만들도록 연결합니다.

#### 비유

병원 행정동은 접수와 권한을 처리하고, 안내동은 방문자를 올바른 진료실로 보내며, 검사동은 수치를 모으고, 기록보관동은 기록을 저장하고, 수술 준비동은 실제 작업을 수행합니다. 건물이 다르더라도 업무 문서와 환자·검사 결과가 전달되지 않으면 병원 전체 기능은 완성되지 않습니다.

#### 본문

Console Cluster의 Portal API·VCFA MGMT·DevOps API·DKS DB·Nats는 사용자 요청·권한·Cluster Lifecycle·CI/CD 결과를 연결합니다. Gateway Cluster의 APISIX와 Keycloak은 각각 Request Routing과 Identity·Token 흐름에 관여합니다. Monitoring과 Logging은 Metric과 Log를 서로 다른 Pipeline으로 수집하며, DevOps Cluster는 Checkout·Build·Registry Push·Target Cluster Deploy를 수행합니다.

이 흐름에서 한 Component의 상태가 다른 기능의 상태를 대신하지 않습니다. Console 화면이 열린다고 VCFA MGMT 요청이 성공한 것은 아니고, Gateway Listener가 열렸다고 Authentication과 Backend 처리가 끝난 것도 아닙니다. Metric 수집과 Log 수집도 병렬 경로이므로 하나가 정상이라고 다른 하나를 추정하지 않습니다.

#### ASCII

```text
사용자 요청
   ↓
Console / Portal API
   ├─ Cluster lifecycle ──> VCFA MGMT / ArgoCD
   ├─ CI/CD ──────────────> DevOps Cluster / Registry / Target
   ├─ 진입·인증 ──────────> APISIX / Keycloak
   ├─ Metric 조회 ────────> Monitoring
   └─ Log 조회 ───────────> Logging

Cluster가 분리되어도 기능은 호출 관계로 연결됨
```

### 블록 3 — 관리 대상과 변경 책임을 ArgoCD 인스턴스별로 나눈다

#### 기술적 목표

관리 Cluster와 User Cluster의 선언·Addon 변경이 어느 Git 정의와 ArgoCD 인스턴스에서 시작되는지 구별해 변경 책임과 조사 출발점을 분리합니다.

#### 비유

병원 캠퍼스에서 시설관리팀과 임상장비관리팀이 서로 다른 작업지시서를 맡는 것과 같습니다. 어느 팀이 어떤 건물을 관리하는지는 분리할 수 있지만, 두 팀이 같은 전력실·창고·출입 시스템을 쓰면 그 공통 기반 장애까지 분리되는 것은 아닙니다.

#### 본문

내부 SW 자료는 `argocd-admin-instance`가 관리 Cluster·관리용 ClusterClass·Addon을, `argocd-vks-instance`가 User Cluster·User용 ClusterClass·Addon을 관리하는 것으로 기록합니다. 이 분리는 특정 변경이 어느 Application·Git 정의·ArgoCD 인스턴스에서 시작되는지 추적하는 데 중요합니다.

그러나 배포 관리 경계가 나뉘었다고 Supervisor·Storage·Network·Registry·Identity까지 물리적으로 분리됐다고 볼 수 없습니다. ArgoCD 장애도 새 선언 적용과 복구 작업을 막을 수 있지만 이미 실행 중인 모든 VM·Pod가 즉시 정지한다는 뜻은 아닙니다. 실행 중 Data Plane과 새 변경을 만드는 Control Plane을 구별합니다.

#### ASCII

```text
argocd-admin-instance
  └─ 관리 Cluster / 관리용 ClusterClass / Addon

argocd-vks-instance
  └─ User Cluster / User용 ClusterClass / Addon

배포 대상·변경 책임 분리
          ≠
Supervisor / Storage / Network / Registry / Identity의 완전 분리
```

### 블록 4 — 장애 범위를 Cluster 경계, 호출 관계, 공유 인프라의 교집합으로 결정한다

#### 기술적 목표

여러 Cluster가 동시에 또는 선택적으로 영향을 받을 때 논리적 실행 경계와 실제 공통 원인을 연결해 장애 영향 범위를 설명합니다.

#### 비유

병원 건물이 따로 있어도 같은 변전소·산소 공급실·중앙 인증 시스템을 쓰면 공통 기반 장애가 여러 건물에 동시에 영향을 줄 수 있습니다. 반대로 같은 캠퍼스에 있다는 이유만으로 모든 건물이 같은 변압기나 창고를 쓰는 것도 아닙니다. 실제 연결과 배치를 확인해야 합니다.

#### 본문

관리 Cluster들은 같은 관리 VPC나 Transit Gateway를 사용할 수 있고, 여러 Volume이 같은 Storage Policy·DataStore를 사용할 수 있으며, 서로 다른 Cluster VM이 같은 ESXi Host에 배치될 수도 있습니다. vCenter·Supervisor·Identity·Registry 역시 여러 Cluster가 공통으로 의존할 수 있는 관리 서비스입니다.

장애 범위는 먼저 어느 Cluster의 어떤 Component에서 현상이 보였는지 고정하고, 누가 그 Component를 호출·소비하는지 확인한 다음, 실제 Route·Storage·Host·관리 API를 무엇과 공유하는지 봅니다. 마지막으로 새 생성·변경만 실패하는지 이미 실행 중인 Workload까지 실패하는지를 구분합니다. 이 연결 없이 Cluster 이름만으로 영향 범위를 확대하거나 축소하지 않습니다.

#### ASCII

```text
장애 관측
   ↓
어느 Cluster / Component인가?
   ↓
누가 이 기능을 호출·소비하는가?
   ↓
실제 VPC / Storage / ESXi / Identity / Registry를 무엇과 공유하는가?
   ↓
새 생성·변경만 실패하는가?
또는 실행 중 Workload도 실패하는가?
   ↓
증거가 지지하는 실제 영향 범위
```
## 1. User Cluster와 관리 Cluster를 나누면 무엇이 실제로 독립되는가?

Namespace는 한 Kubernetes Cluster 안에서 namespaced Resource의 소속과 일부 권한·Quota 범위를 나눕니다. Namespace가 달라도 API Server·etcd·Worker Node를 공유할 수 있습니다.

DKS-C의 User Cluster와 관리 Cluster는 더 큰 단위로 나뉩니다.

| 분리되는 대상 | Cluster 분리로 확인되는 것 | 아직 별도로 확인할 것 |
|---|---|---|
| Kubernetes API | Cluster별 API Server·etcd | 상위 Identity·Gateway 의존성 |
| Worker VM | Cluster별 Node 집합과 kubelet | 실제 ESXi Host 공동 배치 |
| Cluster-scoped Resource | CRD·ClusterRole·Webhook 범위 분리 | 공통 Addon Image·Registry 의존성 |
| Node OS lifecycle | VM·Node 교체를 Cluster별로 수행 가능 | 공통 Image·vCenter·Supervisor 의존성 |
| Workload Scheduling | Pod는 해당 Cluster Node에만 배치 | Storage·Network의 물리 공동 영향 |

이 경계 때문에 한 User Cluster의 CRD 변경이나 Worker 교체가 관리 Cluster의 같은 Resource를 직접 바꾸지는 않습니다.

그러나 **Resource 독립성과 서비스 독립성은 다릅니다.** 예를 들어:

- Console Backend가 User Cluster API를 호출하면 User Cluster API 장애가 Console 기능 실패로 보일 수 있습니다.
- APISIX가 특정 Backend를 중계하면 Backend 장애가 Gateway 응답으로 나타납니다.
- DevOps Cluster가 Target Cluster에 배포하면 Target API·Credential·Network 실패가 Pipeline 실패로 나타납니다.
- Monitoring Cluster가 Metric을 받지 못하면 Workload는 실행 중이어도 관측은 끊길 수 있습니다.

따라서 “Cluster가 다르므로 영향 없음”과 “호출 관계가 있으므로 모든 기능이 함께 중단”이라는 두 극단을 모두 피합니다.

## 2. Console Cluster는 사용자 요청을 어떤 관리 작업으로 바꾸는가?

Console Cluster에는 화면뿐 아니라 요청·상태·권한·Pipeline 결과를 연결하는 Component가 배치되어 있습니다.

| Component | 기록된 역할 | 이 Component 장애 시 먼저 확인할 기능 |
|---|---|---|
| DKS Console | 사용자 Front 요청과 인증·Kubernetes·Monitoring·외부 연동 API 호출 | 화면·Session·API 호출 |
| Portal API | Project·Cluster·권한 정보와 DKS DB·외부 시스템 연결 | 자원·권한 조회/변경 |
| VCFA MGMT | Cluster lifecycle 요청과 ArgoCD 연계 | 생성·변경·삭제 요청 |
| DevOps API | Pipeline 요청 관리와 DevOps Cluster 연결 | Build·Deploy 요청·상태 |
| DKS DB | Portal·DevOps·CUP·Knox 관련 상태 저장 | 조회·상태 일관성 |
| Nats | CI/CD Log Stream·Event 전달 | 실시간 Log·Event 전파 |

“Console 장애”라는 한 표현 안에서도 실패 지점은 다를 수 있습니다.

```text
Browser가 화면을 열지 못함
        ≠
Portal API가 요청을 처리하지 못함
        ≠
DB 상태가 잘못됨
        ≠
VCFA MGMT가 Cluster 작업을 못함
        ≠
DevOps 실행은 됐지만 Nats Log가 전달되지 않음
```

그러므로 화면 오류만으로 Cluster lifecycle이나 User Cluster 자체가 중단됐다고 결론내리지 않습니다. 반대로 화면은 열려도 Backend·DB·외부 API 실패로 실제 작업이 진행되지 않을 수 있습니다.

## 3. Gateway Cluster에서 Routing과 Authentication은 어떻게 나뉘는가?

Gateway Cluster에는 APISIX와 Keycloak이 기록되어 있습니다.

- APISIX는 Listener·Route·Upstream에 따라 Request를 Backend로 전달합니다.
- Keycloak은 Realm·Client·User·Token 설정과 ADFS SSO 연동에 관여합니다.

두 Component가 같은 Cluster에 있다는 사실은 모든 Request가 같은 인증 흐름을 탄다는 뜻이 아닙니다.

```text
Client Request
   ↓
APISIX Listener / Route
   ├─ 인증 Plugin·Backend Auth 적용 경로
   │      └─ Keycloak Token 검증·발급과 연결 가능
   └─ 인증 없이 공개된 Route 가능
          └─ 실제 Route·Plugin 설정으로 확인
```

따라서 다음 상태를 구별합니다.

| 상태 | 의미 |
|---|---|
| VIP·Listener 연결 성공 | Network Entry Point 도달 |
| APISIX Route Match | Request가 특정 Upstream으로 선택됨 |
| Token 발급 성공 | Identity Credential 발급 |
| Token 검증 성공 | 요청 Identity를 신뢰함 |
| Backend Authorization 성공 | 해당 작업 권한이 허용됨 |
| Backend 응답 성공 | 최종 기능 처리 완료 |

Gateway Cluster의 Kubernetes API VIP가 User Cluster API를 중계하는 APISIX Listener와 같은 주소라고 가정하지 않습니다. DNS·VIP·Kubernetes Service·APISIX Route의 실제 연결은 별도로 확인합니다.

## 4. Monitoring과 Logging은 왜 하나의 직렬 Pipeline이 아닌가?

Monitoring은 Metric을, Logging은 Log를 다루는 병렬 관측 경로입니다.

```text
Target Cluster / Platform
   ├─ Metric ──> vm-write ──> VictoriaMetrics ──> vm-read / vm-alert / Grafana
   └─ Log ─────> OTel Collector ──> OpenSearch ──> OpenSearch Dashboards
```

Monitoring Cluster의 기록된 Component는 다음과 같습니다.

- `vm-write`: Metric 수집 접점
- VictoriaMetrics main/archive: Metric 저장
- `vm-read`: Query
- `vm-record`: 집계·장기 처리
- `vm-alert`: Alert Rule 평가·전파
- Grafana: 시각화
- `alert-dispatcher`: P-DEP 연동 알림 Component로 기록

Logging Cluster에는 OpenTelemetry Collector, OpenSearch, OpenSearch Dashboards, `spoditor`가 기록되어 있습니다.

Metric이 정상이라고 Log도 정상인 것은 아니며, Log가 검색된다고 Alert 전파가 정상인 것도 아닙니다. 내부 자료는 고객 Alert 대상·전송 Pipeline 일부를 미정으로 기록하므로 Component 존재만으로 전체 고객 알림 경로가 완성됐다고 말하지 않습니다.

## 5. DevOps Cluster는 Console 요청을 어떻게 Build·Deploy 실행으로 바꾸는가?

Console의 DevOps API가 작업을 접수하면 DevOps Cluster의 `workflow-runner`가 실행 환경을 준비하고 `workflow-engine`과 Task Component가 실제 Build·Deploy를 수행합니다.

| Component | 기록된 작업 |
|---|---|
| `tenant` | Docker-in-Docker 기반 Task 실행 환경 |
| `ci-git-clone` | Source Code Download |
| `builder` | Image Build와 Registry Push |
| `deploy-k8s` | Kubernetes Resource 배포 |
| `container-logger` | Task Log를 Nats로 전송 |

이 흐름에서 상태는 다음처럼 나뉩니다.

```text
Console에서 Pipeline 요청 접수
        ↓
DevOps API가 작업 생성
        ↓
workflow-runner가 실행 환경 준비
        ↓
Source checkout
        ↓
Image build / Registry push
        ↓
Target Cluster 배포
        ↓
Task Log·결과가 Nats·Console로 전달
```

앞 단계 성공은 뒤 단계 성공의 충분조건이 아닙니다.

- Build 성공 후 Registry Push가 실패할 수 있습니다.
- Image Push 성공 후 Target Cluster API·Credential 문제로 Deploy가 실패할 수 있습니다.
- Deploy는 성공했지만 Log Stream이 끊겨 Console에서 결과가 보이지 않을 수 있습니다.
- Console이 정상이어도 DevOps Worker·Registry 장애로 Pipeline이 실패할 수 있습니다.

## 6. 두 ArgoCD 인스턴스는 어떤 관리 대상을 나누는가?

내부 SW 자료는 Supervisor Service의 두 ArgoCD 인스턴스를 다음처럼 기록합니다.

| ArgoCD Instance | 관리 대상으로 기록된 범위 |
|---|---|
| `argocd-admin-instance` | 관리 Cluster, 관리용 Custom ClusterClass, Addon |
| `argocd-vks-instance` | User Cluster, User용 Custom ClusterClass, Addon |

이 분리는 변경이 어느 Git 정의·Application·ArgoCD 인스턴스에서 시작되는지 추적하는 데 중요합니다.

그러나 다음은 별도 확인 대상입니다.

- 두 ArgoCD가 같은 Supervisor·Registry·Identity를 사용하는가?
- 같은 Storage·Network 경로에 의존하는가?
- 한 인스턴스 장애가 기존 실행 Workload와 새 배포에 각각 어떤 영향을 주는가?

ArgoCD가 실패하면 새로운 선언 적용·복구 작업이 막힐 수 있지만 이미 실행 중인 모든 VM·Pod가 즉시 정지한다고 볼 수는 없습니다.

Image Registry도 용도를 구별합니다. Supervisor Service Harbor `dksharbor01`은 관리자 Image와 Addon Image/Chart 저장소로 기록되고, DevOps·사용자용 Harbor는 별도 서비스로 기록됩니다. `builder`가 Image를 Push한다는 사실만으로 그 Harbor가 DevOps Kubernetes Cluster 내부 Pod라고 추정하지 않습니다.

## 7. 관리 Cluster가 나뉘어도 어떤 Network·Storage·Compute를 공유할 수 있는가?

운영 현황은 관리 Cluster들이 `prod-dks-vpc`를 사용하고 `dkssol-project`의 단일 Transit Gateway를 공유하는 것으로 기록합니다. User Cluster마다 VPC를 1:1로 연결하는 구성과 다릅니다.

같은 관리 VPC에 속한다는 사실은 여러 관리 Cluster VM이 같은 가상 Network 범위를 사용할 수 있음을 뜻합니다. 그러나 같은 VPC 내부 Packet이 모두 Transit Gateway를 통과하는 것은 아닙니다. 실제 장애 경로는 Route Table과 Flow를 확인해야 합니다.

Storage Policy 기록은 다음과 같습니다.

| Storage Policy | 기록된 용도 | 기록된 DataStore·용량 |
|---|---|---|
| `vks-pf-storage-policy-admin` | Supervisor VM OS, Platform Cluster PV | DS001, 50 TB |
| `vks-pf-storage-policy` | User Cluster VM OS | DS002, 60 TB |
| `vks-pf-storage-policy-data` | User 제공 PV | DS003, 15 TB + 추가 예정 기록 |

이 표는 기록 시점의 배치이며 각 Cluster Quota나 현재 Free Space가 아닙니다. 여러 Cluster의 Volume이 같은 Storage Policy·DataStore를 사용한다면 Capacity·I/O 장애가 공동 원인이 될 수 있습니다. 반대로 같은 Workload Domain이라는 사실만으로 모든 Volume이 같은 DataStore에 있다고 단정하지 않습니다.

Compute도 같습니다. 서로 다른 Cluster VM이 실제로 같은 ESXi Host에 배치되어 있으면 Host 장애를 공유할 수 있지만, Cluster 이름만으로 공동 배치를 확정할 수 없습니다.

## 8. 운영 현황 스냅샷은 무엇을 보여주고 무엇을 보여주지 않는가?

운영 자료는 WLD01·WLD02에 Console·Gateway·Monitoring·Logging·DevOps Cluster를 별도로 기록합니다.

| 역할 | WLD01 기록 | Worker | WLD02 기록 | Worker |
|---|---|---:|---|---:|
| Console | `prd-dksc-ic01-khm` | 5 × 16C/32G | `dev-dksc-ic01-khm` | 3 × 8C/16G |
| Gateway | `prd-dksg-ic01-khm` | 5 × 16C/32G | `dev-dksg-ic01-khm` | 3 × 8C/16G |
| Monitoring | `prd-dksm-ic01-khm` | 5 × 16C/32G | `dev-dksm-ic01-khm` | 3 × 8C/16G |
| Logging | `prd-dksl-ic01-khm` | 5 × 16C/64G | `dev-dksl-ic01-khm` | 3 × 8C/16G |
| DevOps | `prd-dkso-ic01-khm` | 10 × 8C/16G | `dev-dkso-ic01-khm` | 3 × 8C/16G |

이 표가 보여주는 것은 기록 시점의 논리적 역할 분리와 배치입니다. 다음을 입증하지는 않습니다.

- 현재도 같은 Node 수·사양이다.
- 왜 해당 수량과 사양을 선택했는가.
- 서로 다른 Cluster VM이 서로 다른 ESXi에 배치됐다.
- 장애가 해당 Cluster에만 제한된다.

원자료에는 Workload Domain 이름의 `ia`·`ai` 혼용과 기준 연도가 없는 구축 예정 문구도 있으므로 현재 인벤토리와 대조합니다.

## 9. 장애 범위를 마지막 확인 상태에서 어떻게 좁히는가?

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 증거 |
|---|---|---|
| 특정 Cluster의 Pod가 실패 | Cluster 내부 Resource 문제인가, 외부 의존성 실패인가? | Pod Event·Log, Dependency Endpoint, Network Flow |
| Console 화면만 실패 | Front 문제인가 Portal API·DB 문제인가? | Browser Network, API Health, DB/Nats 상태 |
| Gateway가 5xx 반환 | APISIX Route인가 Upstream인가 Auth인가? | Route·Upstream·Plugin Log, Backend 응답 |
| Metric만 끊김 | Target가 중단됐나 수집 Pipeline만 끊겼나? | Target Health, Agent, vm-write·Storage Query |
| Log만 검색 안 됨 | Source Log 생성·수집·Index 중 어디서 끊겼나? | OTel Pipeline, OpenSearch Index·Query |
| Pipeline이 실패 | Checkout·Build·Push·Deploy·결과 전파 중 어디까지 성공했나? | Task별 상태, Registry, Target API, Nats |
| 여러 관리 Cluster 동시 영향 | 공통 VPC·Storage·ESXi·Identity·Registry가 있는가? | VM Placement, Route, Storage Policy, Shared Service Health |
| 새 생성·변경만 실패 | 관리 API·ArgoCD·vCenter 문제인가? | Controller·API 상태, 기존 Workload Health |
| 실행 중 Workload도 실패 | Data Plane·Storage·Host 공동 장애인가? | Packet·Volume·Host·Process 상태 |

이 표의 목적은 “Cluster가 분리됐다”는 설명과 “공통 원인으로 함께 실패했다”는 설명 중 무엇이 현재 증거를 더 잘 설명하는지 구분하는 것입니다.
