# 02. 네트워크 격리와 1:1:1 테넌시 경계 — 어떤 주소가 바뀌고 어떤 조건이 있어야 경로가 열리는가?

## 문서의 목적

이 문서는 DKS-C에서 User Cluster와 VPC를 1:1로 연결하면 어떤 Network 범위가 나뉘는지, VPC의 `SNAT External IP`가 어느 Traffic의 어느 주소를 바꾸는지, 그리고 같은 VPC·다른 VPC·외부 Network 사이의 통신이 성립하려면 어떤 Route·정책·반환 경로가 필요한지 설명합니다.

핵심은 VPC·SNAT·Transit Gateway 같은 **설정 Resource가 존재한다는 사실**과, 특정 Packet이 실제로 **NAT·Routing·정책 허용을 거쳐 목적지와 왕복했다는 사실**을 구별하는 것입니다.

## 전체 이해 지도

```text
DKS-C Network 이해 골격
│
├─ 테넌시 Network 경계
│  ├─ User Cluster ── 자체 Control Plane / Worker
│  ├─ Supervisor Namespace ── Compute / Storage 범위
│  └─ VPC ── Private IP / Route 범위
│
├─ 통신 유형
│  ├─ 같은 VPC 내부
│  ├─ VPC → 외부
│  └─ User VPC A → User VPC B
│
├─ 주소와 경로
│  ├─ Private IP
│  ├─ SNAT External IP
│  ├─ ConnectivityProfile / Attachment / TGW
│  └─ Firewall / ACL / 반환 Route
│
└─ 실제 통신 확인
   ├─ 설정·할당 상태
   ├─ 실제 Route 선택
   ├─ NAT / Flow / Session
   └─ 목적지 응답과 반환 Packet
```

- **User Cluster와 VPC의 1:1 대응은 Cluster VM이 사용할 Private IP와 Network 범위를 식별하지만, 물리 Network와 모든 장애 범위까지 전용으로 만든다는 뜻은 아닙니다.** DKS-C 자료는 `User Cluster : Supervisor Namespace : VPC = 1:1:1` 관계를 기록합니다. Supervisor Namespace는 Compute·Storage Quota를, VPC는 IP·Network 범위를 담당합니다. 서로 다른 User Cluster를 기본 배치에서 같은 User VPC에 넣는 구조로 설명하지 않지만, ESXi Host·Storage·상위 Gateway·물리 회선은 계속 공유할 수 있습니다.

```text
User Cluster A ── Supervisor Namespace A ── VPC A
User Cluster B ── Supervisor Namespace B ── VPC B

분리되는 것
- Kubernetes Control Plane / Worker 집합
- VM Private IP와 VPC Route 범위

이 관계만으로 분리됐다고 말할 수 없는 것
- ESXi / DataStore / 물리 Switch
- 상위 Gateway / 공통 DNS·인증 서비스
```

- **VPC 내부 VM의 Outbound Traffic에 SNAT External IP가 적용되면 외부에서 보는 Source Address가 바뀌지만, 주소 변환만으로 목적지 통신이 성립하지는 않습니다.** 목적지로 가는 Route, 실제 경로의 Firewall·ACL 허용, 응답이 돌아오는 반환 Route가 모두 맞아야 합니다. `networkInfos`에 SNAT IP가 보인다는 사실은 Control Plane이 그 할당 정보를 알고 있다는 뜻이지 특정 Session이 실제로 성공했다는 증거는 아닙니다.

```text
VPC VM Private IP
   │ Outbound Packet
   ▼
SNAT 적용 지점
   │ Source = VPC SNAT External IP
   ▼
목적지 Route
   ▼
Firewall / ACL 허용
   ▼
Destination
   │
   └─ 반환 Route와 Session 상태가 맞아야 왕복 성공
```

- **서로 다른 VPC를 연결하는 Resource는 연결 구조의 후보를 정의하지만, 현재 A VPC에서 B VPC로 실제 Packet이 어느 Hop을 지나는지는 별도 증거가 필요합니다.** `VPCConnectivityProfile`, `VPCAttachment`, `TransitGateway`, `Private TGW IPBlock`은 VPC 간 연결을 구성할 때 사용하는 Resource입니다. 그러나 Resource 존재만으로 실제 Route 설치, Tier-0 경유, 중앙 Firewall 통과를 확정할 수 없습니다.

```text
VPC A
  └─ VPCAttachment
       └─ ConnectivityProfile / TransitGateway
            └─ VPCAttachment
                 └─ VPC B

구성 Resource 존재
        ≠
A→B Route가 현재 설치됨
        ≠
Packet이 특정 Gateway·Firewall을 실제 통과함
```

- **Network 장애는 장비 이름부터 추측하지 않고 마지막으로 확인된 Packet 상태에서 다음 미확인 상태로 이동하며 좁힙니다.** 같은 VPC 내부 흐름에 SNAT을 자동으로 끼워 넣거나, VPC 간 통신에 Tier-0와 물리 Firewall을 무조건 추가하지 않습니다. 조사 순서는 Network 장비가 실행되는 고정 워터폴이 아니라 경쟁 설명을 줄이기 위한 관측 순서입니다.

```text
Source에서 Packet 생성
        ↓
Source VPC·주소 확인
        ↓
NAT 필요 여부와 실제 변환 확인
        ↓
Route 선택 확인
        ↓
정책 장비 Session·ACL 확인
        ↓
Destination 수신·응답 확인
        ↓
반환 Packet 확인
```

## 1. 1:1:1 대응에서 VPC는 무엇을 나누는가?

DKS-C CCI 자료는 `VPC : Supervisor Namespace = 1:1`, `Supervisor Namespace : VKS = 1:1`을 기록하고, 이를 `SupervisorNamespace : VPC : Cluster = 1:1:1` 관계로 설명합니다.

세 대상은 같은 경계를 다른 이름으로 부르는 것이 아닙니다.

| 대상 | 실제로 정하는 것 | 이 대상만으로는 알 수 없는 것 |
|---|---|---|
| `Supervisor Namespace` | User Cluster VM에 허용할 CPU·Memory·Storage Quota와 VM Class | Packet의 실제 Route와 NAT 결과 |
| `VPC` | User Cluster VM의 Private IP와 가상 Network 범위 | 특정 목적지까지의 도달 가능 여부 |
| `User Cluster` | 별도 Kubernetes Control Plane과 Worker Node 집합 | 물리 Host·Storage·상위 Network의 전용 여부 |
| `Limit` | External IP 사용량·CIDR 관련 할당 정책 | 특정 Session에 쓰인 주소와 NAT 성공 |
| `IPBlock` | Private·Private TGW·External 주소 Pool | 현재 Packet이 통과한 경로 |

CCI 자료는 IPBlock을 다음 용도로 구분합니다.

- `Private`: VPC 내부 주소
- `Private TGW`: Multiple-VPC 통신에 쓰는 Private Subnet
- `External`: VPC 외부에서 식별되는 주소 범위

이 세 종류를 모두 “Cluster IP”로 부르면 어느 주소가 VM 내부 주소인지, Transit 연결용인지, 외부 NAT·VIP 용도인지 구분할 수 없습니다.

더 상위에서는 `Project : Transit Gateway : VPC = 1:1:N` 관계가 기록되어 있습니다. User Cluster마다 VPC가 하나씩 나뉘어도 여러 VPC가 같은 Project와 Transit Gateway를 사용할 수 있습니다. 따라서 **User VPC 분리**와 **상위 연결 인프라 공유**는 동시에 성립할 수 있습니다.

## 2. SNAT External IP는 어느 주소를 바꾸고 무엇을 보장하지 않는가?

VCFA 인프라 자료는 `VPC : SNAT External IP = 1:1`을 기록하고, VPC 내부 VM의 Outbound Traffic이 해당 VPC의 SNAT External IP로 변환된다고 설명합니다.

SNAT은 Source Address를 바꿉니다. VPC 내부 VM이 외부 서비스에 연결할 때 경계에서 Private Source가 SNAT External IP로 바뀌면 목적지 시스템은 그 SNAT IP를 Source로 봅니다.

이때 다음 상태는 서로 대체되지 않습니다.

| 상태 | 확인되는 것 | 아직 별도로 확인할 것 |
|---|---|---|
| VPC에 SNAT External IP가 할당됨 | 사용 가능한 외부 Source 주소가 Control Plane에 기록됨 | 실제 Packet이 그 주소로 변환됐는가 |
| NAT/Flow에서 변환 Session 확인 | 특정 Packet의 Source가 변환됨 | 목적지 Route·정책 허용 |
| Firewall Allow/Session 확인 | 해당 정책 장비가 흐름을 허용함 | 목적지 Application 수신·응답 |
| 목적지에서 Request 수신 | Forward Path가 목적지까지 도달 | 응답의 반환 Route와 최종 기능 성공 |

Pod Traffic은 한 단계 더 구별해야 합니다. 내부 자료가 직접 확정하는 것은 **VPC 내부 VM의 Outbound NAT**입니다. Pod IP가 CNI·Node에서 먼저 어떤 주소로 바뀌는지, Service나 egress 경로를 거치는지는 대상 User Cluster의 CNI·Routing 설정을 확인해야 합니다.

따라서 다음과 같은 확대는 피합니다.

- 모든 Pod가 VPC Gateway에서 직접 같은 방식으로 SNAT된다고 단정
- SNAT IP가 있으므로 모든 외부 목적지로 통신 가능하다고 단정
- 외부에서 SNAT IP를 허용했으므로 Application까지 성공한다고 단정

## 3. 같은 VPC 내부 통신과 다른 VPC 통신은 왜 같은 경로가 아닌가?

같은 VPC 안의 VM은 같은 가상 Network 범위에 속합니다. VCFA 자료는 동일 VPC의 VM 간 통신에 별도 Security Group 기능이 없다고 기록합니다.

이 사실은 다음 범위에서만 사용합니다.

> VPC 구현이 동일 VPC VM 사이를 Security Group으로 세분화하지 않는 것으로 기록되어 있다.

여기서 다음 결론까지 갈 수는 없습니다.

- Kubernetes NetworkPolicy가 없다.
- CNI Policy가 없다.
- Application Authentication이 없다.
- 상위 Router·Firewall Policy가 없다.
- 모든 Port가 실제로 열려 있다.

다른 VPC로 가는 Packet은 별도의 연결 Topology와 Route가 필요합니다.

| Resource | 자료에서 확인되는 역할 |
|---|---|
| `VPCConnectivityProfile` | VPC가 사용할 연결 Topology 정의 |
| `VPCAttachment` | 특정 VPC를 ConnectivityProfile에 연결 |
| `TransitGateway` | 여러 VPC 연결에 사용하는 구성요소 |
| `Private TGW IPBlock` | Multiple-VPC 통신용 Private Subnet |

이 Resource들이 존재하면 “VPC 간 연결을 어떤 객체로 구성하는가?”에는 답할 수 있습니다. 하지만 현재 A VPC의 특정 Subnet에서 B VPC의 특정 목적지로 Route가 설치됐는지, 어느 Gateway가 Next Hop인지, 정책이 허용하는지는 실제 상태를 더 확인해야 합니다.

## 4. Tier-0 Gateway와 Firewall은 언제 실제 Packet 경로가 되는가?

`Private TGW`라는 이름이나 “중앙 Firewall이 있다”는 아키텍처 설명만으로 모든 VPC 간 Packet이 해당 장비를 통과한다고 결론 내리지 않습니다.

특정 장비가 실제 경로라고 판단하려면 최소한 다음 연결이 필요합니다.

```text
Source / Destination / Protocol / Port / Time
        ↓
Source VPC Route Table의 Next Hop
        ↓
Gateway·Firewall Interface와 Session
        ↓
ACL / Policy Hit
        ↓
다음 Hop과 Destination 수신
```

Route가 Tier-0 또는 Firewall을 선택하고 같은 5-tuple·시각의 Session과 ACL Hit가 확인되면 해당 흐름의 경유 장비라고 강하게 판단할 수 있습니다.

반대로 장비에 Session이 없을 때도 곧바로 “그 장비 앞에서 차단됐다”고 단정하지 않습니다. Route가 다른 경로를 선택했거나, Packet이 Source에서 나오지 않았거나, 관측 시각·NAT 후 주소가 달랐을 수 있습니다.

## 5. Control Plane 정보와 Data Plane 실행 증거는 어떻게 구별하는가?

VPC·Limit·IPBlock·ConnectivityProfile 같은 Resource는 원하는 설정과 할당 상태를 보여주는 Control Plane 정보입니다. Packet Capture·Flow·NAT Session·Firewall Log·Destination Log는 실제 실행을 보여주는 Data Plane 증거입니다.

| 증거 | 강하게 말할 수 있는 것 | 그것만으로는 말할 수 없는 것 |
|---|---|---|
| VPC Ready | VPC Resource가 준비 상태로 보고됨 | 특정 목적지와 왕복 통신 성공 |
| `networkInfos`의 SNAT IP | 관리 평면이 알고 있는 SNAT 주소 | 특정 Session에서 실제 사용된 Source |
| `LimitState.consumed` | 해당 집계 Resource가 보고한 소비량 | 전체 실제 할당과 정확한 잔여량 |
| Route Table | 설정된 Next Hop | Packet이 실제 그 Route를 사용했는가 |
| Firewall Allow Log | 해당 장비가 특정 흐름을 허용 | 목적지 Application 정상 처리 |
| Destination Log | Request가 목적지에 도달 | 반환 Packet과 Client 기능 성공 |

CCI 자료에는 `VPCLimitState`의 consumed 값과 `VPCIPAddressUsage`의 allocated 값이 일치하지 않은 사례도 기록되어 있습니다. 따라서 하나의 집계값만으로 External IP 실제 가용량 전체를 확정하지 않습니다.

특정 Packet을 재구성할 때는 NAT 전후 주소가 달라질 수 있으므로 최초 5-tuple만 모든 구간에서 반복 검색하지 않습니다. NAT/Session 정보로 변환된 주소를 연결합니다.

## 6. Network 장애를 마지막 확인 상태에서 어떻게 좁히는가?

장애를 장비 목록 순서로 훑지 않고, 마지막으로 확인된 상태와 아직 확인되지 않은 다음 상태를 연결합니다.

| 마지막으로 확인된 상태 | 다음 질문 | 구분력 있는 증거 |
|---|---|---|
| Source에서 DNS·Destination을 확정하지 못함 | 실제 목적지 IP·Port는 무엇인가? | DNS 응답, Application 설정, 호출 Log |
| Source가 Packet을 생성함 | 어느 Interface·Route로 나가는가? | Local Route, Packet Capture |
| VPC SNAT 정보는 존재함 | 실제 Session에 NAT가 적용됐는가? | NAT/Flow Table, 변환 전후 5-tuple |
| NAT는 확인됐으나 목적지 도달 안 함 | Route와 정책 중 어디까지 통과했는가? | Route Table, Gateway·Firewall Session/ACL |
| Firewall은 Allow함 | Destination Listener·Application이 받았는가? | Destination Packet·Socket·Application Log |
| Destination은 Request를 받음 | 응답이 어떤 Route로 돌아오는가? | Return Route, Reverse Flow, Client Capture |
| VPC A/B 연결 Resource가 존재함 | 실제 A→B Route가 설치됐는가? | Attachment 상태, Route Advertisement/Table |
| 같은 VPC인데 통신 실패 | VPC 외 어느 계층이 차단하는가? | CNI/NetworkPolicy, Host Route, Application Auth |

이 표는 **경쟁 설명을 줄이는 조사 흐름**입니다. 운영자가 위 순서로 확인해야 Network Controller가 다음 상태를 만드는 것은 아닙니다.
