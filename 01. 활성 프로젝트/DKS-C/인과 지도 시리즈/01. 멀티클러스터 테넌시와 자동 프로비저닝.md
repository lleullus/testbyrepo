# 01. 멀티클러스터 테넌시와 자동 프로비저닝 — 무엇이 분리되고 생성 완료는 어디까지인가?

## 문서의 목적

이 문서는 DKS-C에서 Kubernetes `Namespace`와 독립 `User Cluster`가 무엇을 다르게 나누는지, User Cluster에 `Supervisor Namespace`와 `VPC`를 1:1:1로 연결하면 어떤 인프라 범위가 정해지는지, 그리고 생성 요청이 실제 VM·Kubernetes Node·Addon·접속 정보로 이어질 때 어떤 상태까지 확인해야 하는지 설명합니다.

## 전체 인과 지도

이 문서는 **신도시 개발 사업**을 하나의 비유 세계로 사용합니다. Kubernetes Namespace는 한 건물 안의 구획, 독립 User Cluster는 자체 설비를 가진 별도 건물, Supervisor Namespace는 그 건물에 배정된 자원 허가 범위, VPC는 도로·주소 구역, ArgoCD·CAPI·Supervisor는 각각 설계도 반영·건물 단위 조정·실제 기반시설 시공을 맡는 조직에 대응합니다. 비유는 관계를 직관적으로 보여주기 위한 것이며 실제 작동과 근거는 각 블록의 기술 본문이 기준입니다.

```text
DKS-C User Cluster가 만들어지는 전체 골격

분리 단위 선택
  Namespace ── 한 Kubernetes Cluster 안의 Resource 경계
  User Cluster ── 자체 Control Plane / Worker를 가진 Cluster 경계
        ↓
User Cluster에 인프라 범위 부여
  Supervisor Namespace ── Compute / Storage / VM Class 범위
  VPC                  ── IP / Network 범위
  User Cluster : Supervisor Namespace : VPC = 1 : 1 : 1
        ↓
원하는 상태를 실제 인프라로 조정
  Git / ArgoCD ──> CAPI ──> Supervisor / vSphere
        ↓
사용 가능한 Cluster인지 확인
  Machine ─ VM ─ API / Node ─ Addon ─ kubeconfig·networkInfos·Portal
```

### 블록 1 — 한 Cluster 안의 구획과 독립 Cluster를 다른 경계로 만든다

#### 기술적 목표

한 Kubernetes 안에서 Resource를 나누는 경계와 Control Plane·Worker 자체를 분리하는 경계를 구별해 테넌시의 실제 격리 단위를 정합니다.

#### 비유

한 건물의 층이나 사무실을 나누는 것과 아예 별도 건물을 세우는 것은 다릅니다. 사무실이 달라도 건물의 엘리베이터·전기실·관리실은 공유할 수 있지만, 별도 건물은 자체 설비와 출입 체계를 가질 수 있습니다. 다만 별도 건물이라고 해서 도시의 도로·변전소·상수도까지 전용인 것은 아닙니다.

#### 본문

Kubernetes `Namespace`는 한 Cluster 안에서 Pod·Service 같은 namespaced Resource가 속할 범위를 나눕니다. `ResourceQuota`를 두면 그 Namespace가 요청할 CPU·Memory나 Resource 수에 한도를 둘 수 있고, `Role`·`RoleBinding`은 해당 범위에서 허용할 API 작업을 사용자·Group·ServiceAccount에 연결합니다. 그러나 Namespace가 달라도 API Server·etcd·Worker Node는 같은 Cluster의 것을 공유할 수 있습니다.

DKS-C의 독립 `User Cluster`는 이보다 큰 경계입니다. User Cluster마다 별도의 Control Plane과 Worker VM 집합을 가지므로 한 User Cluster의 Machine·Node 조정이 다른 User Cluster의 같은 Resource를 직접 변경하지 않습니다. 여기서 확인되는 것은 **Kubernetes 실행 경계의 분리**입니다. ESXi Host·Storage·상위 Network까지 물리적으로 전용이라는 결론은 실제 배치를 확인하기 전에는 만들 수 없습니다.

#### ASCII

```text
한 Kubernetes Cluster
├─ Namespace A
│  ├─ Pod / Service
│  ├─ ResourceQuota
│  └─ Role / RoleBinding
├─ Namespace B
└─ API Server / etcd / Worker는 공유 가능

독립 User Cluster A          독립 User Cluster B
├─ 자체 Control Plane       ├─ 자체 Control Plane
└─ 자체 Worker VM           └─ 자체 Worker VM

Cluster 경계 분리
      ≠
ESXi / Storage / 상위 Network까지 전용이라는 보장
```

### 블록 2 — 독립 User Cluster가 사용할 Compute·Storage·Network 범위를 결합한다

#### 기술적 목표

독립 Cluster라는 논리적 경계를 실제 VM이 사용할 Compute·Storage·Network 범위에 연결해 어떤 인프라 안에서 그 Cluster를 만들 수 있는지 정합니다.

#### 비유

별도 건물을 세우려면 건물 이름만 정해서는 부족합니다. 부지에 허용된 연면적·전력·창고 용량 같은 자원 허가와 그 건물에 연결될 도로·주소 구역이 함께 정해져야 합니다. 자원 허가가 있다고 실제 공사 자재가 충분하다는 뜻도 아니고, 도로 구역이 있다고 모든 목적지까지 통행이 허용된다는 뜻도 아닙니다.

#### 본문

DKS-C 자료는 `User Cluster : Supervisor Namespace : VPC = 1 : 1 : 1` 관계를 기록합니다. `Supervisor Namespace`는 User Cluster VM에 허용할 CPU·Memory·Storage Quota와 VM Class를 연결하고, `VPC`는 그 VM이 사용할 Private IP와 가상 Network 범위를 제공합니다.

이 대응은 Cluster가 사용할 **인프라 범위**를 정하지만 실제 생성의 충분조건은 아닙니다. `VirtualMachineClass`는 VM 한 대의 사양이고 Supervisor Namespace Quota는 여러 VM이 사용할 수 있는 전체 허용량이므로 서로 다른 조건입니다. Zone·Region의 실제 Compute·Storage 여유, External IP 할당, 목적지 Route·정책 같은 추가 조건도 남습니다. 따라서 1:1:1은 테넌시와 인프라 범위를 연결하는 규칙이지 물리 Capacity와 통신 성공을 보장하는 규칙이 아닙니다.

#### ASCII

```text
User Cluster A
   ├─ Supervisor Namespace A
   │    ├─ CPU / Memory Quota
   │    ├─ Storage Quota
   │    └─ 허용 VM Class
   └─ VPC A
        ├─ Private IP 범위
        └─ 가상 Network 범위

User Cluster : Supervisor Namespace : VPC
             = 1 : 1 : 1

이 대응이 있어도 별도 확인:
Zone/Region Capacity · Storage 여유 · External IP · Route/Policy
```

### 블록 3 — 선언한 Cluster 상태를 여러 조정기가 실제 VM과 Node로 수렴시킨다

#### 기술적 목표

Git에 기록한 원하는 Cluster 구성을 관리 API·CAPI·Supervisor를 거쳐 실제 VM과 Kubernetes Node로 만들고 각 조정기의 완료 상태를 서로 혼동하지 않게 합니다.

#### 비유

설계도 저장소에 건물 도면을 올리면 설계 관리 부서가 최신 도면을 행정 시스템에 반영하고, 공정 관리자가 필요한 건물·설비 단위를 발주하며, 기반시설 부서가 실제 전기·창고·도로와 건물을 준비합니다. 설계도가 행정 시스템과 일치했다고 공사가 끝난 것은 아니며 여러 부서의 작업은 서로 필요한 상태를 보면서 겹쳐 진행될 수 있습니다.

#### 본문

운영자가 Git에 Node 수·VM 사양·Network·Addon 같은 원하는 정의를 기록하면 ArgoCD가 관리 대상 API의 Resource를 그 정의에 맞춥니다. ArgoCD의 `Synced`는 Git과 관리 대상 Resource가 일치한다는 뜻이며 실제 VM·Node가 준비됐다는 뜻이 아닙니다.

CAPI Controller는 `Cluster`, `MachineDeployment`, `Machine` 같은 Resource를 읽어 필요한 Cluster와 Node 수가 원하는 상태에 수렴하도록 조정합니다. 여기서 `Machine`은 Node 한 대의 생성·교체 Lifecycle을 표현합니다. Machine과 연결된 Infrastructure·Bootstrap 설정을 바탕으로 Supervisor 쪽 Controller가 `VirtualMachine`·Storage·Network 요청을 실제 vSphere 인프라 작업으로 이어갑니다.

이 관계를 단일 직렬 워터폴로 보면 안 됩니다. ArgoCD·CAPI·Supervisor·Addon Controller는 서로 다른 Resource를 지속적으로 reconcile하며 일부 작업은 겹쳐 진행됩니다. 따라서 조사할 때는 몇 번째 단계보다 **마지막으로 확인된 Resource 상태와 다음에 필요한 상태**를 연결합니다.

#### ASCII

```text
Git의 원하는 정의
   │
   ▼
ArgoCD
   └─ 관리 API Resource를 Git과 일치시킴
          │
          ▼
CAPI
   └─ Cluster / MachineDeployment / Machine 조정
          │
          ▼
Supervisor Controller
   └─ VirtualMachine / Storage / Network 준비
          │
          ▼
VM Boot / Bootstrap
          │
          ▼
kubelet Node 등록

※ reconcile은 일부 겹쳐 진행됨
※ ArgoCD Synced ≠ VM Ready ≠ Node Ready
```

### 블록 4 — 생성 완료를 Resource 존재가 아니라 사용 가능한 Cluster 상태로 닫는다

#### 기술적 목표

VM이 생긴 뒤 Kubernetes Control Plane·Worker·Addon·접속 정보까지 이어지는 서로 다른 완료 상태를 확인해 실제 사용 가능한 User Cluster인지 판정합니다.

#### 비유

건물 골조가 완성됐다고 입주 가능한 것은 아닙니다. 전기실과 관리실이 동작하고, 출입 시스템과 내부 통신망이 연결되고, 입주자에게 실제 출입 수단이 전달되어야 합니다. 어느 한 검사 통과가 나머지 검사를 대신하지 않습니다.

#### 본문

Control Plane VM에서는 etcd가 Cluster 상태를 저장하고 API Server가 Kubernetes API를 제공해야 합니다. Worker VM의 kubelet은 이 API에 자신을 Node로 등록하고 상태를 보고해야 합니다. CNI는 Pod Network를 만들고 CSI는 Kubernetes Storage 요청을 인프라 Volume 작업으로 연결하는 등 필요한 Addon도 준비되어야 합니다.

Node 등록·Node Ready·Addon 배포는 서로 다른 Controller가 관여하므로 항상 한 줄의 실행 순서로 진행된다고 가정하지 않습니다. DKS 오케스트레이터는 Cluster health, `kubeconfig`, Addon 상태, `networkInfos`의 SNAT IP 같은 결과를 수집해 Portal 후처리로 연결합니다.

따라서 User Cluster 생성 완료는 최소한 **선언 적용 → Machine 조정 → 실제 VM 준비 → Kubernetes API와 Node 참여 → 필요한 Addon → 사용자가 쓸 접속 정보와 Portal 후처리**를 서로 다른 확인 지점으로 나눠 봐야 합니다. 앞 상태가 보인다는 이유로 뒤 상태를 추정하지 않습니다.

#### ASCII

```text
원하는 Resource 적용
        ↓
CAPI Machine 상태
        ↓
실제 VM 준비
        ↓
Control Plane API 응답
        ↓
Worker Node 등록 / Ready
        ↓
CNI·CSI 등 필요한 Addon
        ↓
kubeconfig / networkInfos / Portal 후처리
        ↓
사용 가능한 User Cluster

각 화살표는 다음 상태의 충분조건이 아님
```
## 1. Namespace와 User Cluster는 무엇을 다르게 나누는가?

Kubernetes Namespace는 **한 Cluster 안에서 namespaced Resource가 속할 범위**를 제공합니다. Pod와 Service처럼 Namespace에 속하는 Resource는 같은 종류·같은 이름이라도 Namespace가 다르면 서로 구별됩니다. 따라서 하나의 Kubernetes Cluster 안에서 여러 팀이나 환경의 Resource 이름을 분리해 운영할 수 있습니다.

CPU·메모리 한도와 API 권한은 Namespace를 만드는 순간 자동으로 생기는 성질이 아닙니다. `ResourceQuota`를 해당 Namespace에 만들면 Pod의 CPU·메모리 request/limit 합계나 특정 Resource 개수 등에 한도를 둘 수 있습니다. `Role`에는 “Pod 조회”, “Deployment 변경”처럼 허용할 API 작업을 적고, `RoleBinding`으로 그 Role을 사용자·그룹·ServiceAccount에 연결합니다.

이 Resource를 저장하고 실행하는 기반은 Namespace별로 새로 생기지 않습니다. API Server는 Resource의 생성·조회·변경 요청을 받고, etcd는 Cluster의 설정과 상태를 저장하며, Worker Node는 Pod를 실행합니다. 여러 Namespace의 Pod가 같은 Worker Node에 배치될 수 있습니다.

DKS-C의 User Cluster는 이 Namespace 경계보다 큽니다. User Cluster마다 별도의 Kubernetes Control Plane과 Worker VM 집합이 있습니다. 따라서 한 User Cluster의 Machine이나 Node를 변경하는 조정이 다른 User Cluster의 Machine을 같은 Resource로 직접 바꾸는 구조는 아닙니다.

그러나 **Kubernetes Cluster가 분리됐다는 것과 물리 인프라가 전용이라는 것은 다른 주장**입니다. User Cluster의 VM은 vSphere Workload Domain의 서버와 Storage를 사용합니다. 실제 ESXi 배치와 상위 Network를 확인하지 않고 한 User Cluster 장애가 다른 Cluster에 물리적으로 아무 영향도 주지 않는다고 확대할 수 없습니다.

## 2. User Cluster : Supervisor Namespace : VPC = 1:1:1은 무엇을 정하는가?

User Cluster의 Control Plane과 Worker가 VM에서 실행되려면, 그 VM이 사용할 Compute·Storage·Network 범위가 필요합니다. DKS-C의 CCI 자료는 User Cluster마다 Supervisor Namespace와 VPC를 하나씩 대응시키는 구성을 기록합니다.

| 대상 | 실제로 정하는 것 | 이 대상만으로는 알 수 없는 것 |
|---|---|---|
| `Project` | 여러 Supervisor Namespace와 Project 권한을 묶는 상위 관리 범위 | User Cluster와 1:1이라는 보장 |
| `Supervisor Namespace` | User Cluster VM에 허용할 CPU·메모리·Storage Quota와 VM Class | Zone·Region의 실제 남은 물리 용량 |
| `VPC` | User Cluster VM이 사용할 IP 대역과 가상 Network 범위 | 특정 목적지의 Route·정책 허용 |
| `Limit`·`IPBlock` | VPC가 사용할 External IP의 할당 정책과 주소 풀 | 특정 패킷의 실제 NAT 성공 |
| `User Cluster` | 별도 Kubernetes Control Plane과 Worker Node 집합 | ESXi·Storage·상위 Network의 전용 배치 |

Supervisor Namespace를 처음 만들 때는 `SupervisorNamespaceClassConfig`에 정의한 기본 Quota와 VM Class 설정을 사용합니다. `VirtualMachineClass`는 **VM 한 대의 CPU·메모리 사양**이고, Supervisor Namespace Quota는 **그 Namespace에 허용된 전체 자원 범위**이므로 같은 값이 아닙니다.

Quota가 충분해 보여도 실제 VM 생성에는 다른 조건이 남습니다. CPU·메모리는 배치 대상 Zone의 한도와 가용 자원이 관련되고, Storage는 Region·Storage Policy의 한도와 사용량이 관련될 수 있습니다. VPC의 External IP도 별도의 Limit·IPBlock 할당을 사용합니다. 이 구조와 기존 Supervisor Namespace의 Quota 변경은 [03. Supervisor·CCI 인프라 Control Plane과 Quota 경계](03.%20Supervisor%C2%B7CCI%20인프라%20제어%20평면과%20Quota%20경계.md)에서 확대합니다.

VPC도 통신 성공의 충분조건은 아닙니다. VPC의 주소·SNAT과 다른 VPC 또는 외부 목적지까지의 Route는 [02. 네트워크 격리와 1:1:1 테넌시 경계](02.%20네트워크%20격리와%201:1:1%20테넌시%20경계.md)에서 설명합니다.

## 3. Git의 생성 설정이 실제 VM과 Node로 어떻게 이어지는가?

DKS-C 운영 현황은 User Cluster 프로비저닝을 **VCF Cluster API + ArgoCD 기반**으로 기록합니다. SW 아키텍처에는 사용자 Cluster 배포를 맡는 `argocd-vks-instance`가 Supervisor Service로 기록되어 있습니다.

운영자가 Git의 생성 설정을 바꾸면 ArgoCD는 관리 대상 API의 Resource 정의를 그 상태에 맞춥니다. 여기서 ArgoCD가 `Synced`라고 표시하는 것은 **Git에 기록된 원하는 정의와 관리 대상 Resource가 동기화됐다는 뜻**입니다. 실제 VM이나 Kubernetes Node의 health를 같은 상태로 취급하지 않습니다.

CAPI에서는 Resource마다 담당 범위가 다릅니다.

| CAPI Resource | 이 문서에서 필요한 역할 |
|---|---|
| `ClusterClass` | 유사한 Cluster를 만들 때 사용할 공통 구성 틀 |
| `Cluster` | 생성할 Cluster의 원하는 상태와 참조 |
| `MachineDeployment` | Worker Machine 집합의 수와 교체를 조정 |
| `Machine` | Node 한 대의 생성·교체 상태를 표현 |
| `BootstrapData` | VM을 Kubernetes Node로 초기화할 설정과 명령 |

Machine이 생성돼도 실제 VM이 즉시 존재하는 것은 아닙니다. Machine과 연결된 인프라 설정에 맞춰 Supervisor 쪽에서 VM·Storage·Network를 준비해야 합니다. 내부 자료의 Supervisor는 Compute·VPC·Storage를 Kubernetes Resource로 관리하는 Kubernetes Cluster이며, VM Operator 같은 컨트롤러가 VirtualMachine Resource를 읽어 vSphere의 VM 작업으로 이어줍니다.

따라서 **CAPI Resource 존재 → VM 존재 → VM 부팅 → Kubernetes Node 등록**은 서로 다른 상태입니다. CPU·메모리·Storage·External IP 같은 조건이 부족하면 원하는 Machine이 있어도 인프라 Resource가 준비되지 않을 수 있습니다. 반대로 VM이 켜져 있어도 초기화가 끝나지 않으면 Kubernetes Node로 사용할 수 없습니다.

## 4. VM이 생긴 뒤 Control Plane·Worker·Addon은 무엇을 더 준비하는가?

Control Plane VM은 부트스트랩 설정을 실행해 etcd와 API Server를 기동해야 합니다. API Server가 접속 가능한 상태가 되면 Worker VM은 가입 정보와 API 주소를 사용해 같은 Cluster에 Node로 등록됩니다. Worker의 kubelet은 Pod 실행을 관리하고 Node 상태를 API Server에 보고합니다.

이 과정에서 확인하는 상태는 서로 대체되지 않습니다.

| 확인 상태 | 확인되는 것 | 아직 별도로 확인할 것 |
|---|---|---|
| VM 존재·전원 ON | 인프라 VM이 생성되어 실행 중 | API Server·kubelet 동작 |
| Control Plane API 응답 | Kubernetes API에 접속 가능 | 모든 Worker·Addon 준비 |
| Worker Node 등록 | kubelet이 Cluster에 Node로 등록 | Pod Network·Storage 기능 |
| Node `Ready` | kubelet이 현재 Node 준비 상태를 보고 | 사용자 애플리케이션 정상 |
| Addon health | 해당 Addon의 배포 상태 | 외부 시스템을 포함한 전체 서비스 경로 |

DKS-C SW 자료는 기본 Addon 13개를 기록하며, Carvel 또는 Helm으로 관리되는 항목이 섞여 있습니다. CNI는 Pod Network를 만들고 CSI 계열은 Kubernetes Storage 요청을 인프라 Storage 작업으로 연결합니다. cert-manager, Monitoring Agent, Logging Agent, Policy, Backup 기능도 대상 Cluster API를 사용합니다.

이 작업을 하나의 고정된 직렬 단계로 만들면 안 됩니다. CNI가 준비되어야 Node가 `Ready`가 되는 환경에서는 “Worker Ready 완료 후 CNI 설치”라는 설명 자체가 순서를 뒤집습니다. Machine 조정과 Addon 배포도 서로 다른 컨트롤러가 진행할 수 있습니다.

## 5. 오케스트레이터의 작업 순서와 컨트롤러의 실행 순서는 왜 다른가?

내부 CCI 가이드는 DKS 오케스트레이션에서 RoleBinding 생성, ArgoCD Application 배포, Carvel Addon 배포, Cluster health polling, `kubeconfig` 조회, ArgoCD 대상 Cluster 등록, etcd Secret 조회, Helm Addon 배포, `networkInfos`에서 SNAT IP 조회, Console 전달을 수행한다고 기록합니다.

이 표는 **오케스트레이터가 무엇을 요청하고 무엇을 확인하는지**를 보여줍니다. CAPI·Supervisor·vSphere·kubelet·Addon 컨트롤러가 정확히 같은 순서로 멈춰 기다린다는 뜻은 아닙니다. 예를 들어 오케스트레이터가 health를 polling하는 동안에도 CAPI와 인프라 컨트롤러는 계속 reconcile할 수 있습니다.

원자료는 이 절을 “11단계”라고 부르지만 표에는 1~10의 작업이 보입니다. 이 숫자를 아키텍처의 고정 state machine으로 사용하지 않고 각 행이 실제로 수행·확인하는 작업을 기준으로 읽습니다.

Console에 Cluster 정보가 전달된 뒤에도 Portal DB 권한, APISIX Upstream·Route, Cluster Role·RoleBinding, 최초 Harbor Registry 같은 후처리가 기록되어 있습니다. 이 후처리 완료와 사용자가 배포한 애플리케이션의 정상 동작도 같은 상태가 아닙니다.

## 6. 프로비저닝이 멈췄을 때 어느 상태에서 막혔는지 어떻게 찾는가?

장애를 “몇 번째 단계가 실패했는가”로만 찾지 않고, **마지막으로 확인된 상태와 아직 만들어지지 않은 다음 상태**를 연결합니다.

| 마지막으로 확인된 상태 | 다음 질문 | 주요 확인 대상 |
|---|---|---|
| ArgoCD가 원하는 revision을 적용하지 못함 | Git 정의가 관리 API에 적용됐는가? | revision, Application sync/health, 적용 오류 |
| CAPI Cluster/Machine은 있으나 Machine이 준비되지 않음 | 어떤 condition에서 Node 생성이 막혔는가? | Cluster·MachineDeployment·Machine condition/event |
| Machine은 있으나 VM·Disk가 준비되지 않음 | 어떤 인프라 조건이 부족한가? | Supervisor Namespace, VirtualMachine, Storage, VPC, Quota |
| VM은 있으나 Control Plane API가 응답하지 않음 | 부트스트랩과 API Server·etcd가 어디까지 기동했는가? | BootstrapData 적용, VM 초기화, API endpoint |
| Control Plane API는 응답하나 Worker가 등록되지 않음 | Worker가 API에 접속하고 가입할 조건을 갖췄는가? | Worker Machine, kubelet, API 연결·가입 상태 |
| Worker가 등록됐으나 Ready/Addon이 불안정함 | Pod Network·Storage·필수 Addon 중 무엇이 남았는가? | Node condition, CNI·CSI·Addon Resource와 Pod |
| Cluster는 동작하나 Portal 결과가 완성되지 않음 | 오케스트레이터 후처리와 접속 정보가 준비됐는가? | kubeconfig, networkInfos, ArgoCD 등록, Console 후처리 |

운영자가 이 표 순서로 조회한다고 해서 컨트롤러도 이 조회를 기다리는 것은 아닙니다. 표는 **관측된 사실로 실패 범위를 좁히는 조사 순서**입니다.
