# 03. Supervisor·CCI 인프라 제어 평면과 Quota 경계 — 원하는 Node 수는 어떤 자원 조건을 통과해야 실제 Worker가 되는가?

## 문서의 목적

이 문서는 DKS-C에서 Worker Node 수를 늘리는 선언이 CAPI `Machine`과 Supervisor `VirtualMachine`으로 어떻게 이어지는지, VM 한 대의 사양과 Supervisor Namespace·Zone·Region의 Quota가 왜 서로 다른 조건인지, 그리고 기존 Supervisor Namespace의 한도를 바꾼 뒤 어느 상태까지 확인해야 실제 증설 완료라고 말할 수 있는지 설명합니다.

핵심은 **원하는 Node 수를 선언한 상태**, **그 Node를 만들 수 있도록 자원 사용이 허용된 상태**, **실제 VM과 Kubernetes Node가 준비된 상태**를 하나의 “증설”로 뭉치지 않는 것입니다.

내부 자료의 `SupervisorNamespace` update/patch 미지원과 vCenter API 변경 경로는 해당 자료가 기록한 환경의 제약입니다. 다른 VCF/VCFA 버전이나 현재 설치 환경에 자동으로 확대하지 않습니다.

## 전체 이해 지도

```text
Worker 증설 이해 골격
│
├─ 원하는 상태
│  └─ MachineDeployment replicas
│
├─ VM 한 대의 크기
│  └─ VirtualMachineClass
│
├─ 자원 사용 허용 범위
│  ├─ Supervisor Namespace Quota
│  ├─ Zone CPU / Memory
│  ├─ Region StorageClass Quota
│  └─ VPC / Limit / IPBlock
│
├─ 실제 인프라
│  └─ VirtualMachine / Disk / Network
│
└─ Kubernetes 사용 준비
   ├─ kubelet Node 등록
   ├─ Node Ready
   └─ 필요한 Addon·Workload 배치
```

- **Worker 수를 늘리는 선언과 그 Worker를 만들 인프라 여유는 서로 다른 축입니다.** `MachineDeployment.replicas`가 늘어나면 CAPI는 추가 `Machine`을 만들 이유를 갖지만 Supervisor Namespace Quota를 자동으로 늘리지는 않습니다. 반대로 Quota만 늘리고 원하는 replicas를 그대로 두면 새 `Machine`을 만들 요구가 생기지 않습니다.

```text
원하는 Node 수 증가
        ↓
MachineDeployment replicas 증가
        ↓
추가 Machine 요구

인프라 한도 증가
        ↓
Supervisor Namespace·Zone·Storage 여유 증가
        ↓
추가 VM을 만들 수 있는 가능성 증가

두 흐름이 모두 맞아야 실제 Worker 생성으로 이어질 수 있음
```

- **`VirtualMachineClass`는 VM 한 대의 크기를, Quota는 여러 VM이 사용할 수 있는 전체 한도를 정합니다.** 8 vCPU·16 GiB VM Class를 선택했다는 사실은 그 VM을 하나 더 만들 CPU·Memory Quota와 실제 물리 여유가 남았다는 뜻이 아닙니다. Supervisor Namespace Quota가 남아 있어도 Zone Compute, Region Storage, VPC 주소 같은 다른 조건에서 막힐 수 있습니다.

```text
새 Worker 한 대의 요구량
├─ VM Class CPU / Memory
├─ OS Disk / Storage Policy
└─ Network / IP

검사되는 범위
├─ Supervisor Namespace 한도
├─ Zone 실제 Compute 범위
├─ Region·StorageClass 범위
└─ VPC·External IP 범위
```

- **CCI·Supervisor·User Cluster는 같은 상태를 다른 화면에서 보는 것이 아니라 서로 다른 Resource와 권한 범위를 다룹니다.** CCI는 Project·Region·Zone·Supervisor Namespace·VPC 같은 Organization 범위 인프라를, Supervisor는 CAPI와 `VirtualMachine` lifecycle을, User Cluster는 실제 Node와 Application Resource를 보여줍니다. 어느 Context에서 무엇을 확인했는지 구분해야 합니다.

```text
CCI Context
  └─ Project / Region / Zone / Supervisor Namespace / VPC

Supervisor Context
  └─ Cluster / MachineDeployment / Machine / VirtualMachine

User Cluster Context
  └─ Node / Pod / Service / Application
```

- **Quota 변경 완료와 Worker 증설 완료도 별도 상태입니다.** vCenter에서 Namespace 설정이 바뀌었다는 사실은 추가 VM 생성이 허용될 수 있다는 뜻입니다. 그 뒤 추가 Machine, 실제 VM·Disk, kubelet Node 등록, Node Ready까지 이어지는지 확인해야 합니다. Quota 문제를 해결한 뒤에도 Image·Bootstrap·Storage·Network 문제가 남을 수 있습니다.

```text
Quota 변경 요청 성공
        ↓
대상 Namespace 설정 재조회·반영 확인
        ↓
추가 Machine 생성
        ↓
VirtualMachine / Disk / Network 준비
        ↓
VM boot / bootstrap
        ↓
Node 등록 / Ready
```

## 1. CCI와 Supervisor, User Cluster는 무엇을 각각 관리하는가?

User Cluster 안에서 Deployment와 Pod를 운영하는 작업과, User Cluster 자체를 실행할 VM·Network·Storage를 준비하는 작업은 서로 다른 API를 대상으로 합니다.

| 역할·Context | 주로 다루는 대상 | 이 Context만으로는 알 수 없는 것 |
|---|---|---|
| Organization Admin / CCI | Project, Region, Zone, Supervisor Namespace Class, Supervisor Namespace, VPC, Limit, IPBlock | 개별 User Cluster Pod의 현재 상태 |
| Organization User / Supervisor | CAPI Cluster·MachineDeployment·Machine, `VirtualMachine` | Application 요청의 최종 정상 여부 |
| Cluster User / User Cluster | Node, Deployment, Pod, Service 등 Application Resource | Region·Zone 전체 Quota와 vCenter Namespace 설정 |

Supervisor는 VM·Storage·VPC 같은 인프라 요청을 Kubernetes Resource로 관리하는 Kubernetes Cluster입니다. `VirtualMachine` Resource를 VM Operator가 읽어 vSphere VM 작업으로 연결합니다.

CCI는 여러 Supervisor에 걸친 인프라 범위를 통합 API로 요청·조회합니다. 같은 `Zone`이라는 이름도 CCI의 `topology.cci.vmware.com` Resource와 Supervisor의 `topology.tanzu.vmware.com` Resource가 다를 수 있습니다. 이름이 같다고 같은 상태를 조회한다고 보면 안 됩니다.

이 구분 때문에 다음 문장은 성립하지 않습니다.

- User Cluster에서 Node를 조회할 수 있으므로 Region Quota도 변경할 수 있다.
- CCI에서 Supervisor Namespace를 조회했으므로 실제 Pod가 Ready다.
- vCenter에 VM이 보이므로 Kubernetes Node가 등록됐다.

## 2. User Cluster에 연결된 Supervisor Namespace와 VPC는 무엇을 배정하는가?

DKS-C 자료는 User Cluster 하나에 Supervisor Namespace 하나와 VPC 하나를 연결합니다.

Supervisor Namespace는 두 질문에 답합니다.

1. **얼마까지 사용할 수 있는가?** — CPU·Memory·Storage Quota
2. **어떤 크기의 VM을 요청할 수 있는가?** — 허용된 VM Class

VPC는 Node VM이 사용할 Private IP와 Network 범위를 제공합니다. External IP가 필요한 작업에는 VPC가 참조하는 `Limit`과 `IPBlock`이 별도로 관여합니다.

| Resource | 실제로 정하는 것 | Worker 증설과의 관계 |
|---|---|---|
| `VirtualMachineClass` | VM 한 대의 CPU·Memory 사양 | 추가 Worker 한 대의 단위 요구량 |
| `SupervisorNamespaceClassConfig` | 새 Namespace의 기본 Quota와 VM Class | 생성 시 기본값 |
| `SupervisorNamespace` | 현재 Namespace의 Compute·Storage 한도와 VM Class 연결 | 추가 VM·Disk 요청 허용 범위 |
| `VPC` | VM이 연결될 Network 범위 | 추가 VM의 Network 접점 |
| `Limit`·`IPBlock` | External IP 할당 정책과 주소 Pool | External IP가 필요한 요청의 별도 Gate |
| `MachineDeployment` | 유지할 Worker Machine 수 | CAPI가 추가 Machine을 만들 이유 |

`SupervisorNamespaceClassConfig`의 기본값을 바꾸는 것과 이미 생성된 Supervisor Namespace의 Quota를 바꾸는 것은 같은 작업이 아닙니다. 전자는 이후 생성되는 Namespace의 기본 설정이고, 후자는 현재 운영 중인 인프라 범위 변경입니다.

## 3. 왜 Supervisor Namespace Quota 하나만으로 증설 가능 여부를 판단할 수 없는가?

Quota는 **자원 사용을 허용하는 한도**입니다. Quota를 늘린다고 물리 CPU·Memory·Disk가 새로 생기지는 않습니다.

```text
Namespace Quota 여유
        ≠
Zone의 실제 배치 가능 Compute
        ≠
Region·Storage Policy의 실제 여유
        ≠
새 VM 생성 성공
```

내부 자료에서 자원 종류별 확인 범위는 다음처럼 나뉩니다.

| 확인하려는 자원 | 주요 Resource | 확인되는 내용 |
|---|---|---|
| Namespace CPU·Memory·Storage 한도 | `SupervisorNamespace` | Zone별 CPU·Memory Limit, StorageClass별 Limit |
| Zone CPU·Memory | CCI `Zone` | Zone 범위의 Limit과 Used |
| Region Storage | `RegionStorageClassQuota` | StorageClass별 Region Limit과 Consumed |
| Namespace Storage 세부 | `StorageQuota`, `StoragePolicyQuota`, `StoragePolicyUsage` | VM·Snapshot·PVC 사용량과 Policy별 한도 |
| External IP | `IPBlock`, `Limit`, `LimitState` | 주소 Pool, 허용량, 소비 집계 |

내부 CCI 자료는 Node OS Disk 참고값으로 Control Plane 한 대당 136 GiB, Worker 한 대당 116 GiB를 기록합니다. 이 값이 적용되는 환경에서는 Worker 수 증가가 CPU·Memory뿐 아니라 OS Disk 수요도 늘립니다. 다만 실제 계산에는 대상 Cluster의 현재 VM·Disk 사양을 사용해야 합니다.

External IP는 더 별개의 Gate입니다. 기존 VPC에 Worker만 추가하는 작업이 항상 새 External IP를 요구한다고 볼 수 없습니다. 반대로 LoadBalancer VIP나 External IP 추가 요청이라면 CPU Quota를 늘려도 IP 부족은 해결되지 않습니다.

따라서 실패한 요청이 **VM**, **Disk**, **External IP**, **Bootstrap** 중 무엇인지 먼저 구분합니다.

## 4. MachineDeployment replicas와 Quota는 어떤 조건에서 실제 Worker로 이어지는가?

`MachineDeployment`는 원하는 Worker Machine 수를 유지합니다. replicas를 3에서 5로 바꾸면 CAPI는 추가 Worker 두 대를 위한 `Machine`을 만들도록 조정합니다.

그러나 다음 연결이 필요합니다.

```text
MachineDeployment desired replicas 증가
        ↓
추가 Machine 생성
        ↓
Machine이 참조하는 Infrastructure·Bootstrap 설정 유효
        ↓
Supervisor Namespace Quota 허용
        ↓
Zone·Storage·Network 실제 자원 준비
        ↓
VirtualMachine 생성·부팅
        ↓
kubelet이 User Cluster API에 Join
        ↓
Node Ready
```

각 화살표는 앞 상태가 뒤 상태의 충분조건이 아닙니다.

- Machine이 있어도 VM 생성이 실패할 수 있습니다.
- VM이 Power On이어도 Bootstrap이 실패할 수 있습니다.
- kubelet이 등록돼도 CNI·CSI 문제로 Node가 Ready가 아닐 수 있습니다.
- Node가 Ready여도 Application이 정상이라는 뜻은 아닙니다.

반대로 Quota만 늘리고 원하는 replicas를 그대로 두면 CAPI가 새 Machine을 만들 이유가 없습니다.

증설 판단은 항상 두 질문으로 나눕니다.

1. 원하는 Node 수가 실제로 바뀌었는가?
2. 그 Node를 만들 자원과 설정이 준비됐는가?

## 5. 기존 Supervisor Namespace의 Quota 변경 경로는 왜 별도로 확인해야 하는가?

내부 CCI 가이드는 해당 환경의 `SupervisorNamespace`가 create/destroy만 지원하고 update/patch를 지원하지 않는다고 기록합니다. 같은 자료는 기존 Namespace Quota 변경에 vSphere Automation API, 즉 vCenter API와 vCenter 권한이 필요하다고 설명합니다.

Broadcom Namespace 변경 자료는 일부 버전에서 다음 PATCH 경로를 제공합니다.

```http
PATCH https://<vcenter>/api/vcenter/namespaces/instances/<namespace_id>
```

여기서 구별해야 할 것은 다음 세 상태입니다.

| 상태 | 의미 |
|---|---|
| vCenter API가 Namespace 변경 기능을 제공 | 특정 vCenter 버전·권한에서 변경 API가 존재 |
| CCI `SupervisorNamespace`가 update를 지원 | CCI Resource 자체를 patch할 수 있음 |
| 실제 DKS-C 설치 환경에서 운영 절차로 지원 | 제품 버전·권한·운영 승인까지 확인됨 |

첫 번째가 확인됐다고 두 번째와 세 번째까지 자동으로 성립하지 않습니다. 내부 자료의 “향후 버전 적용 예정”도 현재 설치 환경의 지원 증거가 아닙니다.

변경 대상 Namespace ID도 Cluster 이름만으로 만들어내지 않습니다. CCI에서 실제 Supervisor Namespace와 대상 Supervisor를 확인하고 vCenter Namespace와 대조해야 합니다.

Storage Policy 제거·교체는 단순 용량 증설보다 영향 범위가 큽니다. 기존 PVC나 User Cluster가 사용하는 Policy를 바꾸는 작업을 필요한 CPU·Memory 증설과 함께 묶지 않습니다.

## 6. Quota를 바꾼 뒤 어느 상태까지 확인해야 하는가?

HTTP 성공 응답은 API 요청이 접수·처리됐다는 증거일 뿐 Worker 증설 완료 증거가 아닙니다.

먼저 vCenter에서 대상 Namespace 설정을 다시 조회해 바꾸려던 값이 실제 반영됐는지 확인합니다. CCI 값도 대조할 수 있지만 vCenter 변경과 CCI 상태 반영의 시점·조정 관계는 실제 환경에서 확인해야 합니다.

이미 Worker 증설을 요청했다면 다음 상태를 이어 봅니다.

| 마지막으로 확인된 상태 | 다음 질문 | 주요 확인 대상 |
|---|---|---|
| MachineDeployment replicas가 바뀌지 않음 | 원하는 Node 수 선언이 실제 적용됐는가? | Git/ArgoCD, MachineDeployment spec |
| replicas는 증가했으나 Machine 없음 | CAPI Controller가 왜 추가 Machine을 만들지 못했는가? | MachineDeployment condition/event |
| Machine은 있으나 VirtualMachine 없음 | 어떤 인프라 Gate가 막혔는가? | Supervisor Namespace, Zone, Storage, VPC, Bootstrap 참조 |
| VirtualMachine 생성 실패 | Compute·Disk·Network 중 무엇이 부족한가? | VM condition, Event, Quota·Capacity |
| VM은 Power On이나 Node 미등록 | Bootstrap·API Join 조건이 충족됐는가? | cloud-init, kubelet, API endpoint, Token/Certificate |
| Node는 등록됐으나 NotReady | CNI·CSI·Node condition 중 무엇이 남았는가? | Node condition, kube-system Addon |
| Node Ready이나 Workload 미배치 | Scheduler·Affinity·Resource 조건이 맞는가? | Pod event, taint/toleration, request |

Quota 문제를 해소했는데도 Node가 생기지 않으면 Quota 변경 실패로 되돌아가기 전에 새로 드러난 Condition과 Event를 확인합니다. Image·Storage·Network·Bootstrap 같은 경쟁 설명이 남아 있을 수 있습니다.

이 표는 운영자의 **검증 흐름**입니다. 사람이 값을 재조회해야 Controller가 다음 reconcile을 시작한다는 뜻은 아닙니다.

## 7. 어느 API에서 무엇을 조회해야 하는가?

조회할 Resource의 Context를 먼저 고정합니다. 아래 명령은 내부 가이드에 기록된 읽기 형태를 정리한 예시이며, 이 문서 작성 과정에서 실제 환경에 실행한 결과가 아닙니다.

```bash
# CCI: Supervisor Namespace와 상위 Quota·Network
kubectl --context="$CCI_CONTEXT" get svns "$SVNS" -n "$PROJECT" -o yaml
kubectl --context="$CCI_CONTEXT" get zones.topology.cci.vmware.com "$ZONE" -o yaml
kubectl --context="$CCI_CONTEXT" get regionstorageclassquota -o yaml
kubectl --context="$CCI_CONTEXT" get vpc "$VPC" -o yaml
kubectl --context="$CCI_CONTEXT" get limit "$LIMIT" -o yaml

# Supervisor: CAPI와 VM lifecycle
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get machinedeployments,machines
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get virtualmachines
kubectl --context="$SUPERVISOR_CONTEXT" -n "$SVNS" get events

# User Cluster: 실제 등록된 Node
kubectl --context="$USER_CONTEXT" get nodes -o wide
```

배열의 첫 항목이 대상 Zone·StorageClass라고 가정하지 않고 실제 이름을 맞춰 조회합니다. Event는 과거 기록이 남아 있을 수 있으므로 현재 Condition, 대상 UID, 발생 시각을 연결합니다.
