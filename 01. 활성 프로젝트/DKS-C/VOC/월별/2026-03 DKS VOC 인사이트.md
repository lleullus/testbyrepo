# 2026-03 DKS VOC 인사이트

> [!important] 이 문서의 역할
> 이 문서는 2026년 3월 VOC에서 확인되는 **DKS의 계층 경계와 진단 습관**을 학습 관점에서 정리한다. 문의 제목이나 HTTP Status만으로 원인을 확정하지 않고, 실제 Resource 연결과 운영 답변이 허용하는 범위까지만 설명한다.
>
> 3월 30·31일 VOC 2건은 `2026-03-29 ~ 2026-04-04` 주차 파일에 들어 있다. 이 문서는 등록일을 기준으로 해당 두 건을 3월 자료에 포함한다. 당시 공용·Namespace형 답변을 현재 DKS-C 전용 환경에 자동 적용하지 않는다.

## 0. 3월 자료에서 두드러진 변화

1~2월에는 주소·권한·자원 신청 같은 기본 사용 경계가 많이 나타났다면, 3월에는 **증상과 실제 실패 계층을 분리하는 사례**가 더 선명해졌다.

- `502 Bad Gateway`가 Ingress 자체 장애가 아니라 Service Selector·Pod 상태·Liveness Probe 문제로 좁혀진 사례
- `404`가 Ingress를 지나 Backend Pod까지 전달된 뒤 애플리케이션에서 반환된 사례
- Pod의 Kernel 정보가 Container Image가 아니라 배치된 Worker Node에 종속된다는 사례
- Project 권한과 Namespace 멤버 권한이 서로 다른 단계라는 사례

따라서 3월의 핵심은 특정 해결 명령보다 **어느 계층에서 무엇이 확인됐는지 구별하는 법**이다.

---

# 1. 이번 달 한눈에

1. **HTTP Status는 실패 계층을 알려주는 단서이지 Root Cause 자체가 아니다.**
2. **Pod는 독립된 VM이 아니며, Kernel 같은 기반 특성은 배치된 Worker Node를 따른다.**
3. **Namespace 이름은 표시 문자열이 아니라 Resource Identity이므로 in-place Rename 대상이 아니다.**
4. **Project 권한과 Namespace 멤버 권한은 별도 단계다.**

추가로 저활용 판정, Operator 사용, ImagePullBackOff 사례는 **화면에 보이는 단일 신호만으로 정책·원인을 확정하면 안 된다**는 관찰 포인트를 제공한다.

# 2. 확인된 인사이트

## 2.1 502·404를 보고 곧바로 Ingress 장애라고 결론내리지 않는다

### VOC에서 확인된 사실 — 502

VOC `2026031118270611712`에서 사용자는 기존에 동작하던 Ingress 주소에서 `502 Bad Gateway`가 발생했다고 문의했다.

운영팀은 처음부터 Ingress 장애로 확정하지 않고, 502는 Pod 문제나 Port 연결 등 여러 원인으로 발생할 수 있으므로 Project·Cluster·Namespace·Ingress 정보가 필요하다고 답했다.

조사 과정에서 한 번은 Service Selector와 일치하는 Pod가 없어 연결할 수 없는 상태가 확인됐다. 대상 정보를 다시 정정한 뒤에는 실제 Pod의 `liveness probe failed` 상태가 확인됐고, 사용자가 원인을 조치하는 것으로 종료됐다.

### VOC에서 확인된 사실 — 404

VOC `2026031118241311694`에서는 P-DEP 배포 후 사이트 접속 시 404 또는 무한 Redirect가 발생했다.

Ingress Access Log를 확인한 결과 요청은 Service를 거쳐 Backend Pod의 `192.223.28.245:8080`까지 전달됐고, 최종 404는 해당 Backend에서 반환된 것으로 확인됐다. 운영팀은 애플리케이션 확인을 요청했다.

### 여기서 읽을 수 있는 진단 구조

같은 “Ingress를 통해 접속했다”는 상황에서도 실패 지점은 다를 수 있다.

~~~text
Client
  ↓
DNS / VIP / Listener
  ↓
Ingress Rule
  ↓
Service
  ↓
Selector / Endpoint
  ↓
Pod Ready·Probe·Port
  ↓
Application Response
~~~

- 502는 Ingress가 고장났다는 뜻이 아니라 Upstream 연결 실패를 포함한 여러 상태에서 나타날 수 있다.
- 404가 Backend Pod까지 전달된 Log와 함께 확인됐다면 Ingress Routing 성공과 애플리케이션 응답을 구분할 수 있다.
- Service가 존재해도 Selector와 일치하는 Ready Pod가 없으면 실제 전달 대상이 없다.
- Pod가 실행 중으로 보여도 Liveness·Readiness·Listen Port 조건이 맞지 않을 수 있다.

따라서 장애 조사의 핵심 질문은 “Ingress가 문제인가?”가 아니라 다음과 같다.

1. 요청이 어느 계층까지 도달했는가?
2. Service가 실제 Ready Endpoint를 가지고 있는가?
3. Backend Port와 Probe가 정상인가?
4. 최종 Status를 어느 계층이 반환했는가?

### 이 인사이트가 말하지 않는 것

- 모든 502는 Backend Pod 문제라는 뜻은 아니다.
- 모든 404는 애플리케이션 문제라는 뜻도 아니다. Ingress Rule·Path가 404를 만들 수도 있다.
- Log 한 줄만으로 전체 요청 경로가 항상 입증된다는 뜻은 아니다.
- 3월 사례의 구체적인 Probe 설정을 다른 Workload에 그대로 적용할 수 없다.

## 2.2 Pod의 Kernel은 Container Image가 아니라 Worker Node에 종속된다

### VOC에서 확인된 사실

VOC `2026032615112215546`에서 사용자는 같은 서비스의 Pod에서 서로 다른 Kernel Version이 보이는 이유와 특정 Kernel Version을 선택할 수 있는지 문의했다.

운영팀은 Pod 안에서 확인되는 Kernel Version은 **Pod가 배치된 Worker Node의 Kernel**이라고 설명했다. 어느 Node에 배치됐는지에 따라 Kernel 정보가 다르게 보일 수 있다는 답변이었다.

당시 Cluster에는 OS Version Label이 구성돼 있지 않아 특정 OS Node에 배치하려면 Node 이름을 확인한 뒤 Deployment의 `nodeName`에 직접 지정해야 했다. 그러나 단일 Node를 강제하면 Replica가 여러 개여도 같은 Node에만 배치되므로 Node 장애 시 서비스 전체가 영향을 받을 수 있어 권장하지 않는다고 안내했다.

### 여기서 읽을 수 있는 Kubernetes 구조

Container는 User Space를 패키징하지만 Kernel까지 포함한 독립 VM은 아니다.

~~~text
Container Image
  └─ Application / Library / User Space

Worker Node
  └─ Linux Kernel
       ↑
       Pod가 실제로 공유
~~~

그래서 Container Image가 같아도 서로 다른 Kernel을 가진 Node에 배치되면 Pod 내부에서 보이는 Kernel Version이 달라질 수 있다.

또한 “특정 Kernel을 써야 한다”는 요구를 단순히 `nodeName`으로 해결하면 다음 Trade-off가 생긴다.

~~~text
특정 Node 선택 성공
        ↕
Scheduler 선택권 축소
Replica 분산 어려움
Node 장애 시 전체 영향 가능
~~~

운영 관점에서는 Node 이름을 고정하기 전에 다음을 확인해야 한다.

- 요구사항이 정말 Kernel Version 의존성인가?
- Node Label·Affinity처럼 다수 Node에 적용 가능한 선택 기준이 있는가?
- 대상 조건을 만족하는 Node가 여러 대인가?
- 해당 Node가 장애나 교체될 때 Workload가 다른 Node로 이동할 수 있는가?

### 이 인사이트가 말하지 않는 것

- Container가 Node의 모든 설정을 그대로 볼 수 있다는 뜻은 아니다.
- `nodeName` 사용이 항상 금지된다는 뜻도 아니다.
- 현재 DKS-C에 OS Label이 없다는 뜻은 아니다. 원문은 당시 특정 Cluster 구성에 대한 답변이다.
- Kernel Version만 같으면 애플리케이션 호환성이 보장된다는 뜻도 아니다.

## 2.3 Namespace 이름 변경은 속성 수정이 아니라 새 Resource로의 이전이다

### VOC에서 확인된 사실

VOC `2026031609361135305`에서 사용자는 기존 Namespace 이름을 다른 이름으로 바꿀 수 있는지 문의했다.

운영팀은 Kubernetes가 기존 Namespace 이름 변경 기능을 제공하지 않으며, 원하는 이름을 사용하려면 현재 Namespace를 삭제한 뒤 새 Namespace를 신청해야 한다고 답변했다.

### 여기서 읽을 수 있는 Resource Identity

Namespace 이름은 화면에 표시되는 Label 수준의 값이 아니라 Namespace Resource의 식별자다. 따라서 Rename이 아니라 새 Resource 생성과 Workload 이전 문제로 바뀐다.

~~~text
기존 Namespace
  ├─ Deployment / Pod
  ├─ Service / Ingress
  ├─ Secret / ConfigMap
  ├─ PVC
  ├─ RoleBinding
  └─ 외부 연동·배포 설정

이름 변경 요구
        ↓
in-place Rename 불가
        ↓
새 Namespace 생성
        ↓
Resource·Data·권한·연동 이전
        ↓
검증 후 기존 Namespace 삭제
~~~

따라서 실제 작업에서는 “삭제 후 새로 신청”이라는 한 문장만으로 충분하지 않다. 이름이 바뀌면 영향을 받는 참조를 먼저 찾아야 한다.

- CI/CD의 Namespace 값
- Secret·ConfigMap과 Workload Manifest
- PVC·데이터 이전 방식
- DNS·Ingress·방화벽 등 외부 연동
- Project·Namespace Membership
- Monitoring·Backup·권한 설정

### 이 인사이트가 말하지 않는 것

- 기존 Namespace를 먼저 삭제해야 한다는 뜻은 아니다. 서비스 이전 순서는 별도 계획이 필요하다.
- 모든 Resource를 자동으로 복제할 수 있다는 뜻도 아니다.
- PVC Data가 Namespace 이름 변경과 함께 자동 이동한다는 뜻은 아니다.
- 현재 Console의 신청·삭제 절차가 당시와 동일하다는 뜻도 아니다.

### 관련 문서

- [[CCL-CON-001 - Namespace 이름은 생성 후 변경할 수 없다]]
- [[CCL-CON-002 - Namespace 이름 교체는 신규 생성과 워크로드 이전으로 처리한다]]

## 2.4 Project 권한과 Namespace 권한은 서로 대체되지 않는다

### VOC에서 확인된 사실

VOC `2026033113293844007`에서 신규 운영자는 신청 현황과 Project 설정에서 Project를 확인할 수 있었지만, 실제 상단 Project 선택에서는 `No Options`가 표시됐다.

운영팀 확인 결과 해당 계정에는 Project 권한은 있었지만 Namespace 권한이 없었다. Namespace 관리자에게 멤버 권한 추가를 요청하도록 안내했다.

### 여기서 읽을 수 있는 권한 구조

Project와 Namespace는 같은 “DKS 접근 권한”이라는 한 단계로 합쳐지지 않는다.

~~~text
Project Membership
  └─ Project 범위에 참여할 수 있는가?

Namespace Membership / Role
  └─ 특정 Namespace에서 무엇을 볼 수 있고 수행할 수 있는가?
~~~

따라서 사용자가 Project는 보지만 실제 Workload Namespace에 접근하지 못하는 상황은 모순이 아니다. 상위 관리 범위와 하위 실행 범위의 권한이 따로 존재할 수 있다.

문제를 확인할 때는 다음을 분리한다.

1. One Cloud 또는 상위 Project 멤버인가?
2. DKS Project에 동기화됐는가?
3. 대상 Namespace의 멤버인가?
4. Namespace 안에서 어떤 Role을 받았는가?

### 이 인사이트가 말하지 않는 것

- 모든 Project 멤버에게 Namespace 권한이 자동 부여되지 않는다는 일반 정책을 현재 모든 환경에 확정하는 것은 아니다.
- Project가 보이지 않는 모든 현상의 원인이 Namespace 권한이라는 뜻도 아니다.
- Console Cache·동기화 지연·계정 최초 로그인 같은 다른 조건을 배제한 결론도 아니다.

### 관련 문서

- [[CCL-AUTH-002 - Project 멤버와 Namespace 멤버 권한은 별도 단계다]]

# 3. 관찰 포인트

## 3.1 ImagePullBackOff는 하나의 원인이 아니라 상태가 겹친 결과일 수 있다

VOC `2026032015044075665`에서는 Pod Pending과 `ImagePullBackOff`가 발생했다. 조사 과정에서 먼저 과거 Image를 계속 참조하는 구버전 ReplicaSet이 남아 있는 상태가 확인됐다. 구버전과 신버전 ReplicaSet을 조정한 뒤에도 신규 Pod에서 403이 계속되자, 운영팀은 `imagePullSecrets`의 Credential 변경 또는 정책 변경 가능성을 제시하고 최신 Credential로 Secret을 갱신하도록 안내했다.

이 사례는 같은 증상 안에 다음 문제가 연속으로 존재할 수 있음을 보여준다.

~~~text
Deployment / ReplicaSet 상태 혼선
        +
삭제된 과거 Image 참조
        +
신규 Image Pull Credential 403
        ↓
Pod Pending / ImagePullBackOff
~~~

따라서 첫 번째 문제를 발견했다고 전체 원인이 닫힌 것으로 보지 않고, 조치 후 새 Event가 무엇으로 바뀌는지 다시 확인해야 한다.

## 3.2 저활용 판정값과 Dashboard 순간값은 같은 의미가 아닐 수 있다

VOC `2026031713412948754`에서 운영팀은 저활용 판정이 Dashboard와 별개로, 수집된 일 평균 사용률 중 판정 기간 내 최고 수치를 기준으로 이뤄진다고 설명했다.

이 사례의 학습 포인트는 “화면에서 본 현재 사용률”과 “정책이 사용하는 판정 집계값”을 구분하는 것이다.

다만 저활용 기간·임계값·회수 절차는 시간에 따라 바뀔 수 있는 정책값이다. 3월 답변만으로 현재 기준을 확정하지 않는다.

---

## 3.3 공용형 환경에서는 Cluster Scope Tool보다 Namespace Scope 대안을 먼저 검토했다

VOC `2026032311350183044`에서 PostgreSQL Operator 문의에 대해 운영팀은 클러스터 전체 권한이 필요한 설정 대신 Namespace 안에서 Prometheus나 Exporter를 직접 구성하는 방안을 권장했다.

이 사례는 사용자의 최종 목적이 “PostgreSQL 운영·모니터링”이라면 특정 Operator 설치 자체를 목표로 고정하지 않고, 현재 권한 경계 안에서 목적을 달성할 대안을 찾는 방식으로 읽을 수 있다.

그러나 Operator가 전혀 필요 없다는 결론이나 현재 DKS-C 전용 클러스터의 지원 여부를 뜻하지는 않는다.

# 4. 3월 VOC만으로 확정하면 안 되는 것

1. **HTTP Status별 단일 Root Cause**
   - 502·404는 계층을 좁히는 단서일 뿐 원인표가 아니다.

2. **특정 Kernel Node 선택 정책**
   - 당시 Cluster의 Label 부재와 `nodeName` 안내를 현재 모든 Cluster에 일반화하지 않는다.

3. **Namespace 이전 절차의 세부 순서**
   - Rename 불가는 확인됐지만 실제 Migration·Data 복제·Cutover 절차는 별도 설계가 필요하다.

4. **현재 저활용 기준**
   - 판정 기간·임계값·회수 정책은 최신 자료를 확인해야 한다.

5. **모든 Project 가시성 문제의 원인**
   - Namespace 멤버 권한 외에도 동기화·로그인·Console Data 오류 가능성이 있다.

6. **ImagePullBackOff의 단일 해결책**
   - ReplicaSet, Image 참조, Credential, Registry 상태가 함께 얽힐 수 있다.

# 5. 3월을 읽고 남겨야 할 판단 습관

~~~text
"502/404가 났다."
→ Status 이름으로 원인을 정하지 않는다.
→ 요청이 DNS·Ingress·Service·Endpoint·Pod·Application 중 어디까지 갔는지 확인한다.

"Pod마다 Kernel이 다르다."
→ Container Image보다 먼저 배치된 Worker Node를 확인한다.
→ 특정 Node 고정이 가용성에 미치는 영향을 같이 본다.

"Namespace 이름만 바꾸고 싶다."
→ 문자열 수정이 아니라 새 Resource로의 Migration으로 해석한다.

"Project 권한을 받았는데 왜 안 보이지?"
→ Project Membership과 Namespace Membership을 따로 확인한다.

"첫 원인을 고쳤는데 증상이 남는다."
→ 조치 후 새 Event·Log를 다시 읽고 다음 실패 계층을 찾는다.
~~~
