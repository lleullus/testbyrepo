# 2026-05 DKS VOC 인사이트

> [!important] 이 문서의 역할
> 이 문서는 2026년 5월 VOC에서 확인되는 **DKS-N과 DKS-C의 서비스 모델 차이, 네트워크 판단 기준, 선언 원본과 관리 책임**을 학습 관점에서 정리한다.
>
> 5월은 DKS-C Beta 관련 문의와 기존 공용형 DKS-N 문의가 함께 존재하던 시점이다. 따라서 같은 “DKS”라는 이름이나 같은 질문만 보고 답을 합치지 않는다. 서비스 모델·망·통신 방향·시점을 확인한 뒤 원문이 허용하는 범위까지만 설명한다.

## 0. 5월 자료를 읽는 가장 중요한 전제

5월 Coverage Ledger 자체가 다음 경계를 명시한다.

> DKS-C와 기존 공용형 DKS의 차이가 답을 갈라놓기 시작하므로 서비스 모델이 불명확한 사례는 일반화하지 않는다.

실제로 같은 “외부 통신 Source IP”, “Node 관리”, “Ingress”, “권한” 질문이라도 DKS-N과 DKS-C의 답이 달랐다.

~~~text
먼저 확인할 것

1. DKS-N인가 DKS-C인가?
2. 공용 Namespace형인가 독립 Cluster형인가?
3. Inbound인가 Outbound인가?
4. 현재 정식 정책인가 Beta 당시 관측인가?
~~~

5월 문서의 모든 인사이트는 이 네 질문을 전제로 한다.

---

# 1. 이번 달 한눈에

1. **DKS-N과 DKS-C는 같은 Kubernetes 사용법의 두 이름이 아니라 운영·권한·네트워크 경계가 다른 서비스 모델이다.**
2. **방화벽 Source 주소는 “DKS 주소” 하나로 정하지 않고 서비스 모델과 통신 방향에 따라 선택한다.**
3. **HTTP Status·TLS Handshake·TCP Reset·Pod 배치 Node는 연결 장애의 실패 계층을 좁히는 증거다.**
4. **P-DEP이 관리하는 환경변수는 Live Deployment가 아니라 Git 또는 CD 설정에 반영해야 지속된다.**
5. **공용 Node의 Label은 사용자 소유 설정이 아니었으며, 요구사항에 맞춰 Workload 구조를 바꾸는 대안이 필요했다.**

# 2. 확인된 인사이트

## 2.1 답변하기 전에 DKS-N과 DKS-C 중 어떤 서비스 모델인지 확인한다

### VOC에서 확인된 사실

VOC `2026052911180605029`에서 사용자는 DKS-N Namespace의 Project 소속 변경과 향후 DKS-C 이전 시 차이를 문의했다.

운영팀은 DKS-N Namespace의 Project 소속은 변경할 수 없어 삭제 후 재신청을 권장했고, DKS-N과 DKS-C 사이에 다음과 같은 당시의 차이를 설명했다.

| 구분 | 5월 답변에서 설명한 DKS-N | 5월 답변에서 설명한 DKS-C |
|---|---|---|
| 서비스 단위 | 공용 Cluster의 Namespace | 독립 Cluster |
| 외부 노출 | Ingress 중심 | LoadBalancer 및 Gateway API |
| Routing Controller | NGINX Ingress | Contour·Envoy Gateway API |
| 권한 경계 | Namespace Scope | Cluster Scope 가능 |
| Storage | 공용형 기본 StorageClass | 독립 StorageClass, 이전 시 Data Migration 필요 |

VOC `2026051108533795058`에서도 공용 DKS-N Node는 공유 자원이므로 사용자 Label 관리를 지원하지 않는다고 설명하고, 독립 대역의 DKS-C 전환을 하나의 대안으로 제시했다.

### 여기서 읽을 수 있는 서비스 모델 경계

DKS-N의 Namespace를 DKS-C의 Cluster로 옮기는 일은 단순히 같은 Manifest를 다른 Endpoint에 배포하는 작업이 아니다.

~~~text
DKS-N
공용 Cluster
  └─ Namespace Scope
      ├─ 공유 Node
      ├─ 제한된 Cluster Scope 권한
      └─ NGINX Ingress 중심

DKS-C
독립 Cluster
  ├─ 전용 Cluster Lifecycle
  ├─ 별도 Network·Egress
  ├─ Cluster Scope 관리 가능성
  ├─ Contour / Gateway API
  └─ 별도 Storage·Data Migration 고려
~~~

따라서 전환이나 설계 검토에서는 “Kubernetes YAML이 있는가?”만 확인하면 부족하다.

- Ingress Resource를 Gateway·HTTPRoute로 다시 구성해야 하는가?
- Cluster Scope Operator·CRD가 새 환경에서 필요한가?
- StorageClass와 기존 Data를 어떻게 옮길 것인가?
- 방화벽 Source·Destination 주소가 바뀌는가?
- LoadBalancer와 Health Check는 어떤 Resource로 구성하는가?
- 권한과 운영 책임이 Namespace 운영에서 Cluster 운영으로 얼마나 넓어지는가?

### 이 인사이트가 말하지 않는 것

- 표의 모든 항목이 현재 정식 DKS-C 정책과 동일하다는 뜻은 아니다. 5월의 Beta 전환기 답변이다.
- DKS-C가 모든 Cluster Scope 작업을 무제한 허용한다는 뜻도 아니다.
- DKS-N에서 사용한 모든 Manifest가 DKS-C에서 동작하지 않는다는 뜻은 아니다.
- 두 서비스 중 어느 것이 절대적으로 더 낫다는 평가도 아니다. 필요한 격리·권한·운영 책임이 다르다.

## 2.2 방화벽 Source 주소는 서비스 모델과 통신 방향으로 결정한다

### VOC에서 확인된 사실 — DKS-C Outbound

VOC `2026051912595354289`에서 DKS-C Pod가 사내 외부 API로 나갈 때 방화벽 Source IP를 무엇으로 해야 하는지 문의했다.

운영팀은 DKS-C Cluster의 외부 Outbound Traffic이 **Egress IP로 SNAT**되므로, Cluster에 할당된 Egress IP를 Source로 하고 목적지 서비스 IP를 Destination으로 신청하도록 안내했다. 별도 Outbound Kubernetes Resource는 필요하지 않다고 답변했다.

### VOC에서 확인된 사실 — 공용형 Node Subnet

VOC `2026052016031464310`에서는 같은 Namespace의 일부 Pod만 외부 DB 연결이 Timeout됐다. 운영팀은 실패한 Pod가 4월에 추가된 신규 Worker Node에 배치됐고, 이 Node의 IP 대역이 기존 방화벽 Source 목록에 포함되지 않았음을 확인했다. 신규 Node 대역을 추가로 Open하도록 안내했다.

5월의 다른 공용형 VOC에서도 외부 서비스 접근 Source로 Worker Node 대역을 안내한 사례가 존재했다.

### 여기서 읽을 수 있는 주소 선택 구조

두 사례는 같은 “Pod에서 외부 시스템으로 통신한다”는 질문에도 Source 주소가 다를 수 있음을 보여준다.

~~~text
Pod → Cluster 외부
        ↓
서비스 모델 확인
        ├─ DKS-C 전용 VPC
        │      └─ Egress SNAT IP
        │
        └─ 당시 공용형 DKS
               └─ 실제 Pod가 배치된 Worker Node / Subnet
~~~

따라서 방화벽 요청 전에 최소한 다음을 확인해야 한다.

1. DKS-N인가 DKS-C인가?
2. Traffic 방향이 Pod → 외부인가, 외부 → Service인가?
3. SNAT이 적용되는 지점은 어디인가?
4. Node 증설·교체로 Source Subnet이 바뀔 수 있는가?
5. 신청된 방화벽 목록이 현재 Cluster 구성과 일치하는가?

특히 공용형 Node Subnet을 Source로 쓰는 환경에서는 Node 증설이 Application Manifest 변경 없이도 외부 연결 실패를 만들 수 있다. 신규 Pod가 새 Node에 Scheduler되면서 기존 Pod와 다른 Source 주소를 사용하기 때문이다.

### 이 인사이트가 말하지 않는 것

- 모든 DKS-C 통신이 하나의 Egress IP만 사용한다는 뜻은 아니다.
- Inbound DNS·LB 주소에도 Egress IP를 사용한다는 뜻은 아니다.
- 모든 DKS-N 환경이 Worker Node 대역을 Source로 사용한다는 현재 정책 확정도 아니다.
- 5월 문서에 나온 개별 Subnet을 다른 Cluster의 방화벽에 사용할 수 있다는 뜻은 아니다.

### 관련 문서

- [[CCL-NET-003 - DKS-C 아웃바운드 방화벽 Source는 Egress IP다]]
- [[CCL-NET-G001 - 주소 선택 전 네트워크 조건을 식별한다]]

## 2.3 연결 장애는 관측된 Protocol 단계로 실패 범위를 좁힌다

### VOC에서 확인된 사실 — HTTP 405

VOC `2026051113313498841`에서 DKS Service URL로 Batch API를 호출했을 때 `405 Method Not Allowed`가 발생해 방화벽 문제인지 문의했다.

운영팀은 405 응답이 방화벽 문제가 아니며, Backend로 가야 할 요청이 Ingress Path Mapping 누락으로 Frontend에 유입된 결과라고 설명했다. `/batch` Path를 Backend에 Mapping하도록 안내했다.

이 사례에서 405를 받았다는 것은 적어도 요청이 단순 Network Drop으로 사라진 것이 아니라 HTTP 응답을 반환할 대상까지 도달했다는 단서다.

### VOC에서 확인된 사실 — Handshake 후 Reset

VOC `2026052817073800402`에서는 Pod가 목적지 서비스와 TLS Handshake를 진행한 직후 `Connection reset by peer`를 받았다.

운영팀은 인증서 자체 문제보다는 TCP Handshake 완료 뒤 목적지 서버 또는 보안장비가 Reset Packet을 보낸 것으로 분석하고, Source Node 대역의 방화벽 허용과 목적지 접근정책을 확인하도록 안내했다.

### VOC에서 확인된 사실 — 특정 Pod만 Timeout

VOC `2026052016031464310`에서는 같은 Namespace의 다른 Pod는 연결되는데 신규 Pod만 DB 연결 Timeout이 발생했다. 실패 여부가 Pod가 배치된 신규 Node Subnet과 일치하면서 방화벽 Source 누락이 확인됐다.

### 여기서 읽을 수 있는 차등 진단법

~~~text
DNS 실패
  → 이름 해석·등록 계층

TCP 연결 자체 실패 / Timeout
  → Route·방화벽·Listener·Source 대역 후보

TLS Handshake 실패
  → Certificate·Protocol·Cipher·Trust 후보

Handshake 후 TCP Reset
  → 목적지 서버·중간 보안정책·Application 종료 후보

HTTP 4xx / 5xx 수신
  → 요청이 HTTP 처리 계층까지 도달했다는 증거
  → Route·Method·Header·Backend·Application을 추가 분리

같은 Workload 중 일부 Pod만 실패
  → Node·Subnet·Zone·배포 위치 차이를 비교
~~~

좋은 진단은 “방화벽인가 아닌가”를 한 번에 맞히는 것이 아니라, 현재 관측으로 제거할 수 있는 가설을 하나씩 줄이는 것이다.

### 이 인사이트가 말하지 않는 것

- HTTP Status가 보이면 방화벽 문제가 절대 아니라는 뜻은 아니다. 중간 Proxy·WAF가 Status를 반환할 수도 있다.
- `Connection reset by peer`의 발신 주체가 원문만으로 완전히 입증됐다는 뜻은 아니다. 운영팀도 목적지 서버·보안장비 측으로 분석했다.
- TLS Handshake 성공이 Application Authorization 성공을 뜻하지 않는다.
- 특정 Node Subnet 문제가 확인됐다고 다른 Timeout도 같은 원인이라는 뜻은 아니다.

## 2.4 지속할 설정은 P-DEP이 읽는 선언 원본에 반영한다

### VOC에서 확인된 사실

VOC `2026051817525049244`에서 사용자는 DKS Console에서 Deployment의 Environment Variable을 수정했지만 P-DEP Build/Deploy 뒤 원래 값으로 초기화되는 문제를 문의했다.

P-DEP 담당자는 Custom CD로 전환하지 않아도 해결할 수 있으며, 지속할 Secret·Environment 설정을 Git의 `deployments.yaml` 또는 P-DEP 실행 화면의 CD 설정 `Environment Value`에 등록하여 배포하도록 안내했다.

### 여기서 읽을 수 있는 Field Ownership

~~~text
Console에서 Live Deployment 수정
        ↓
현재 Resource 값 변경
        ↓
P-DEP 재배포
        ↓
Git / CD 설정에서 원하는 상태 다시 적용
        ↓
Live 수정값 덮어쓰기
~~~

따라서 같은 값이 반복해서 돌아온다면 Cluster가 수정사항을 무시한다고 보기 전에, 그 Field의 Source of Truth를 확인해야 한다.

- Git Manifest에서 관리하는가?
- P-DEP UI의 CD Parameter로 주입하는가?
- Helm Values나 Template에서 생성하는가?
- Secret 또는 ConfigMap Reference로 관리하는가?
- 다른 Controller가 Reconcile하는 Field인가?

### 이 인사이트가 말하지 않는 것

- 모든 Deployment Field를 Git에서만 관리해야 한다는 뜻은 아니다.
- 모든 Console 수정이 즉시 덮어써진다는 뜻도 아니다.
- 현재 P-DEP의 설정 파일 이름과 UI가 동일하다는 뜻은 아니다.
- Secret 값을 평문 Git에 저장하라는 뜻은 아니다. 실제 보안 저장 방식은 별도로 확인해야 한다.

### 관련 문서

- [[CCL-DEP-001 - P-DEP 관리 필드의 콘솔 직접 수정은 재배포 시 덮어써질 수 있다]]
- [[CCL-DEP-002 - P-DEP 지속 설정은 Git 또는 CD 정의에 반영한다]]

## 2.5 공용 Node 관리 요구는 Workload 설계 문제로 다시 번역해야 한다

### VOC에서 확인된 사실

VOC `2026051108533795058`에서 사용자는 특정 IP 대역 Node에 Label을 설정하려 했다. 운영팀은 공용 DKS-N Node가 공유 자원이므로 사용자 Label 관리를 지원하지 않는다고 답변했다.

VOC `2026052214564372597`에서는 DaemonSet이 모든 Node에 배포돼 Pod 수가 과도해지자 Node Label과 NodeSelector를 사용하려 했다. 운영팀은 역시 공용 Node Label 관리를 지원하지 않는다고 답변하고, DaemonSet 대신 Agent Router를 Deployment로 바꿔 적정 Replica 수로 운영하는 대안을 제시했다.

### 여기서 읽을 수 있는 책임 경계

공용 Cluster의 Node는 한 Namespace 사용자의 전용 VM이 아니다. Label 변경은 다른 Scheduler 결정과 다른 Tenant Workload에도 영향을 줄 수 있다.

~~~text
사용자 요구
"특정 Node 집합에만 Agent를 배포하고 싶다"
        ↓
즉시 Node Label 변경 요청
        X
        ↓
현재 서비스 모델의 Node 관리 책임 확인
        ↓
Workload Controller·Replica·Topology 설계 대안 검토
        ├─ DaemonSet이 정말 필요한가?
        ├─ Deployment로 제한된 수만 운영 가능한가?
        ├─ 기존 제공 Label·Affinity를 활용할 수 있는가?
        └─ 전용 Cluster가 필요한 요구인가?
~~~

### 이 인사이트가 말하지 않는 것

- 사용자가 어떤 Node Scheduling 설정도 사용할 수 없다는 뜻은 아니다.
- DaemonSet이 잘못된 Workload Type이라는 뜻도 아니다.
- 현재 DKS-C에서도 Node Label 관리가 무조건 허용된다는 뜻은 아니다.
- 임시 Node 이름을 직접 지정하는 당시 안내를 장기 설계로 일반화해서는 안 된다.

### 관련 문서

- [[CCL-PLT-003 - DKS-N 공용 Node의 사용자 Label 관리는 지원되지 않는다]]

# 3. 관찰 포인트

## 3.1 Namespace·Project 변경 요구는 단순 Rename이 아니라 재구성 문제다

5월에도 Namespace 이름 오타와 Project 소속 변경 문의가 반복됐다.

- Namespace 이름은 in-place 변경할 수 없어 신규 Namespace 생성과 Workload 이전이 필요했다.
- DKS-N Namespace의 Project 소속도 직접 변경하지 못해 삭제·재신청 방식이 안내됐다.

이 사례들은 이름이나 소속이 단순 Metadata처럼 보여도 실제로는 Resource Identity, 권한, Harbor, CI/CD, Storage, 외부 연동과 연결돼 있음을 보여준다.

다만 “먼저 삭제”를 일반 절차로 읽어서는 안 된다. 실제 Migration에서는 신규 환경 구성과 검증을 먼저 한 뒤 Cutover·기존 삭제 순서를 별도로 설계해야 한다.

---

## 3.2 DKS-C Beta 당시 제공 환경·Quota는 현재 정책 근거가 아니다

5월에는 DKS-C Registry 증설, 개발·Staging 신청 비활성화, Beta 전용 대역 등 시점 의존 사례가 존재한다.

이 자료는 DKS-C가 도입되는 과정의 운영 상태를 보여주지만, 당시 수치·제공 환경·신청 가능 범위를 현재 정식 서비스 정책으로 사용하면 안 된다.

# 4. 5월 VOC만으로 확정하면 안 되는 것

1. **현재 DKS-N/C 기능 비교표**
   - 5월 답변은 Beta 전환기 관측이다. 현재 지원 기능은 최신 자료로 다시 확인한다.

2. **모든 환경의 방화벽 Source 주소**
   - DKS-C Egress IP와 공용형 Worker Subnet은 조건이 다른 답이다.

3. **Connection Reset의 최종 발신 주체**
   - Packet·목적지 Log 없이 서버와 보안장비 중 어느 장치인지 완전히 확정하지 않는다.

4. **모든 P-DEP Field의 Source of Truth**
   - 확인된 사례는 Deployment Environment 설정이다. 각 Field의 관리 주체는 별도로 확인한다.

5. **현재 공용 Node Label 정책과 DKS-C 권한**
   - 당시 DKS-N 경계와 현재 전용 Cluster 권한을 구분한다.

6. **Beta 당시 Registry Quota·환경 제공 범위**
   - 개별 수치와 신청 가능 환경은 현재성 검증 없이는 사용하지 않는다.

# 5. 5월을 읽고 남겨야 할 판단 습관

~~~text
"DKS에서는 어떻게 하나?"
→ 먼저 DKS-N인지 DKS-C인지 묻는다.

"방화벽 Source IP는 무엇인가?"
→ 서비스 모델 + Inbound/Outbound + 목적을 확인한다.

"통신이 안 된다."
→ DNS → TCP → TLS → HTTP → Application 중 관측된 마지막 성공 지점을 찾는다.
→ 같은 Workload 중 일부만 실패하면 Node·Subnet·Zone 차이를 비교한다.

"콘솔에서 수정했는데 돌아왔다."
→ P-DEP·Git·Helm·Controller 중 누가 해당 Field를 관리하는지 찾는다.

"Node에 Label을 붙여 달라."
→ Node 소유권과 Tenant 영향을 확인하고 Workload 설계 대안을 먼저 검토한다.
~~~
