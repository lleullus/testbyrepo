# DKS Conditional Claim Layer 운영 설계 v0.2

## 1. 목적

Conditional Claim Layer는 VOC 원문과 FAQ·런북·아키텍처 문서 사이에서 다음 질문에 답한다.

> 이 운영 답변을 다른 사건에도 적용할 수 있는가? 적용할 수 있다면 어떤 조건과 한계 안에서 가능한가?

이 계층은 정답 모음이 아니다. **증거가 허용하는 범위 안에서만 재사용 가능한 주장**을 관리한다.

```text
VOC 원문
   ↓
VOC Coverage Ledger
   ↓
Conditional Claim
   ↓
FAQ / Runbook / 상세 참조 / 인과 지도
```

원본 VOC는 수정하지 않는다. Claim은 기존 가이드나 현재 정책을 자동으로 대체하지 않는다.

---

# 2. 세 계층의 역할

## Evidence Corpus — `VOC/`

발생한 사건, 문의 조건, 공식 답변, 당시 값과 조치를 보존한다.

## Coverage Ledger

모든 VOC가 Claim 프로젝트에서 어떻게 처리됐는지 기록한다. Claim이 생성되지 않은 사건도 누락되지 않게 한다.

## Conditional Claim

여러 사건에 재사용 가능한 주장만 보존한다. 적용 조건, 근거 사슬, 범위 경계, 반례, 현재성을 함께 관리한다.

---

# 3. Coverage Ledger 처분 값

각 VOC는 반드시 하나의 기본 처분을 가진다.

| 처분 | 의미 |
|---|---|
| `supports-claim` | 기존 Claim을 직접 지지함 |
| `bounds-claim` | 다른 조건의 사례로 Claim 범위를 좁힘 |
| `contradicts` | 동일 조건에서 Claim과 양립하지 않음 |
| `candidate-source` | 재사용 가능성이 있지만 범위·근거 검증이 부족함 |
| `case-only` | 사건 사실로는 유효하지만 재사용 Claim으로 일반화할 수 없음 |
| `out-of-scope` | 현재 Claim 정리 범위 밖의 행정·단순 이관·일회성 문의 |

하나의 VOC가 복수 Claim과 관계될 수 있으므로 `related_claims`에는 여러 ID를 기록할 수 있다.

---

# 4. Claim 원자성

Claim 하나에는 **독립적으로 변경 가능한 주장 하나**만 둔다.

다음은 분리한다.

```text
금지: Worker Node NodePort 직접 접근 불가
대안: Two-Arm LB VIP 사용
```

```text
경계: 내부 Cluster IP는 외부 등록 주소가 아님
절차: 대표 도메인을 조회해 VIP 확인
```

함께 나타난 사실이라도 변경 주기가 다르면 별도 Claim이다.

---

# 5. 정식 Frontmatter

```yaml
---
type: conditional-claim
claim_id: CCL-NET-001
claim_kind: guard | boundary | rule | capability | prohibition | procedure | responsibility
domain: network

decision_question: "외부 DNS 등록 주소로 무엇을 선택해야 하는가?"
derivation: direct | repeated | contrastive | boundary

evidence_status: candidate | supported | contested | superseded
currentness: historical | unverified-current | current
operational_use: blocked | advisory | allowed

service_models: [DKS-N]
network_profiles: [unknown]
directions: [inbound]
purposes: [dns-registration]
protocols: [http, https]

evidence_ids:
  - "2026071617520129033"
evidence_first_seen: 2026-07-16
evidence_last_seen: 2026-07-20

source_fidelity_min: full-dialogue
depends_on: [CCL-NET-G001]
supersedes: []
superseded_by: []
last_reviewed: 2026-09-25
---
```

## 필드 해석

- `evidence_status`: 증거와 논리가 Claim을 어느 정도 지지하는가
- `currentness`: 현재 정책으로 재확인됐는가
- `operational_use`: 실제 운영 절차에서 사용할 수 있는가
- `evidence_first_seen/last_seen`: 증거가 관측된 날짜이며 정책 유효기간이 아님
- `unknown`: 자료에 없는 조건을 추정하지 않았음을 의미

배열 필드는 단일 값이어도 항상 배열로 기록한다.

---

# 6. Claim 본문 구조

모든 Claim은 다음 순서를 따른다.

1. `# Claim`
2. `## 판단 질문`
3. `## 적용 조건`
4. `## 적용 전 확인할 미지수`
5. `## 근거 사슬`
6. `## 근거표`
7. `## 이 Claim이 말하지 않는 것`
8. `## 반례·경쟁 설명`
9. `## 무효화 조건`
10. `## 다음 검증`
11. `## 하위 문서 사용 조건`

## 근거표 형식

| 관계 | VOC | 자료 상태 | 직접 확인된 사실 | 근거 파일·행 |
|---|---|---|---|---|
| direct-support | ... | full-dialogue | ... | ... |
| corroboration | ... | partial | ... | ... |
| scope-boundary | ... | full-dialogue | ... | ... |
| contradiction | ... | redacted-dialogue | ... | ... |

---

# 7. 자료 상태

| 값 | 의미 |
|---|---|
| `full-dialogue` | 문의 조건과 공식 답변이 구체적으로 보존됨 |
| `redacted-dialogue` | 사용자나 일부 값이 익명화됨 |
| `summary-only` | 요약 목록만 있고 상세 답변이 없음 |
| `partial` | 일부 대화 또는 근거가 누락됐음이 명시됨 |

근거 수보다 자료 상태와 Claim의 직접성이 우선한다.

---

# 8. Claim 승격 기준

## `candidate`

- 공식 답변 한 건에서 재사용 가능성이 보이지만 적용 범위가 불명확함
- 서비스 모델·망·버전 등 핵심 조건이 `unknown`임
- 요약 자료만 있고 상세 답변을 확인하지 못함

## `supported`

다음 중 하나를 만족한다.

- 공식 답변이 Claim과 적용 범위를 직접 명시함
- 동일 조건의 독립 사례가 반복됨
- 다른 조건의 반례를 포함해도 범위가 논리적으로 닫힘

`지원됨`은 `현재 정책임`을 의미하지 않는다.

## `contested`

동일한 조건과 시점 범위에서 양립할 수 없는 공식 답변이 있고 차이를 설명할 조건을 찾지 못함.

## `superseded`

새 공식 정책 또는 구조가 과거 Claim을 대체함. 과거 VOC 해석을 위해 파일은 삭제하지 않는다.

---

# 9. 현재성과 운영 사용 Gate

VOC 기반 Claim은 기본값을 다음으로 둔다.

```yaml
currentness: unverified-current
operational_use: advisory
```

현재 신청값·명령·절차를 확정하는 문서에서 직접 사용하려면 다음을 모두 만족해야 한다.

```text
evidence_status = supported
currentness = current
operational_use = allowed
```

최신 공식 자료를 확인하지 못했다면 Claim은 역사·설계 분석에는 사용할 수 있지만 현재 절차의 확정값으로 쓰지 않는다.

---

# 10. 적용 조건의 완결성

적용 조건은 답을 모른 상태에서도 판별 가능해야 한다.

잘못된 조건:

> 운영팀이 Egress IP를 사용하라고 답한 경우

올바른 조건:

> 서비스 모델이 DKS-C이고 방향이 Pod → 클러스터 외부이며 목적이 방화벽 Source 지정인 경우

조건 자체에 결론이 포함되면 Claim이 아니라 순환 정의다.

---

# 11. Case-only 규칙

다음은 Claim으로 만들지 않는다.

- 특정 Cluster·Namespace의 단일 IP, 용량, 일회성 조치
- 서비스 모델이나 구조가 확인되지 않아 적용 범위를 판별할 수 없는 답변
- 특정 사용자의 설정 오류만 설명하는 사건
- 현재 자료에서 일반 규칙과 사례값을 분리할 수 없는 사건

이들은 Ledger에서 `case-only` 또는 `candidate-source`로 관리한다.

---

# 12. Guard Claim

Guard Claim은 구체값을 주지 않고 **잘못된 판단을 중지시키는 조건**을 제공한다.

예:

> 주소를 결정하기 전에 서비스 모델 또는 네트워크 프로파일, 통신 방향, 연동 목적을 식별한다. 이 중 하나가 미확인이면 특정 주소 규칙을 일반화하지 않는다.

Guard Claim은 하위 Claim의 `depends_on`에 연결한다.

---

# 13. 완결성 검사

Claim을 `supported`로 승격하기 전에 다음을 확인한다.

1. Claim이 한 문장·한 판단인가?
2. 적용 조건은 답을 모른 상태에서 확인 가능한가?
3. 원문 공식 답변까지 역추적 가능한가?
4. 근거보다 넓게 일반화하지 않았는가?
5. 인접 조건에 대한 오용 한계를 적었는가?
6. 같은 주제의 반례를 검색했는가?
7. 반례가 범위 차이인지 실제 충돌인지 설명했는가?
8. 증거 관측 기간과 정책 유효기간을 구분했는가?
9. 어떤 증거가 나오면 Claim을 버릴지 적었는가?
10. 운영 사용 Gate를 명시했는가?

하나라도 답하지 못하면 범위를 좁히거나 `candidate`/`contested`로 둔다.

---

# 14. 전체 VOC 처리 순서

```text
1. 주차별 요약 목록에서 모든 VOC를 Ledger에 등록
2. 도메인·질문·조건을 1차 분류
3. 기존 Claim과 연결 가능한지 확인
4. 연결 불가 시 candidate-source / case-only / out-of-scope 판정
5. candidate-source가 반복되면 원문 대화 확인
6. 조건 차이와 반례를 검색
7. Claim 생성 또는 기존 Claim 범위 수정
8. Claim 완결성 검사
9. Ledger에 최종 Claim ID와 처분 반영
10. 현재성 검증 전까지 운영 사용은 advisory 이하로 제한
```

# 15. ID 체계

| 도메인 | 코드 |
|---|---|
| 공통 판단·경계 | `GEN` |
| 네트워크·DNS·Ingress | `NET` |
| 인증·권한·Token | `AUTH` |
| 자원·Quota·수요 | `RES` |
| 배포·워크로드 | `DEP` |
| 이미지·Harbor | `IMG` |
| 스토리지 | `STO` |
| 관측성 | `OBS` |
| 플랫폼 정책·지원 범위 | `PLT` |
| 콘솔·신청 프로세스 | `CON` |

Guard Claim은 `G` 접두를 사용한다.

```text
CCL-NET-G001
CCL-NET-001
CCL-AUTH-001
```

---

# 16. 변경 관리

- Claim 내용을 바꿀 때 근거 범위가 달라지면 기존 Claim을 덮어쓰지 말고 새 Claim으로 분기할 수 있다.
- 정책 변경이 확인되면 과거 Claim은 `superseded`로 전환하고 `superseded_by`를 연결한다.
- Claim 삭제는 원칙적으로 하지 않는다.
- 새 VOC는 우선 Ledger에 등록한 뒤 Claim을 변경한다.

---

# 17. 이 설계의 한계

- VOC는 운영팀이 당시 제공한 답변의 증거이지 영구 정책의 유일한 원천이 아니다.
- 기록 누락·요약·익명화 때문에 모든 사건의 조건을 복원할 수 없다.
- 전체 VOC 분류가 완료돼도 현재 정책 검증이 자동으로 완료되는 것은 아니다.
- Claim 수를 늘리는 것이 목표가 아니다. 일반화할 수 없는 사건은 case-only로 남기는 것이 더 정확하다.
