# Conditional Claim Layer 전체 적용 결과 및 잔여 검증 백로그

## 1. 전체 적용 범위

네트워크 파일럿과 완결성 점검을 거친 운영 설계 v0.2를 현재 `VOC/` 폴더에 존재하는 모든 주차 파일에 적용했다.

- 원본 VOC 파일: 27개
- Ledger 등록 VOC: 334건
- 등록 기간: 2026-01-04 ~ 2026-07-18
- 정식 Conditional Claim: 24개
- Claim을 직접 지지하는 VOC: 62건
- Claim 범위를 제한하는 VOC: 18건
- 추가 검증이 필요한 후보: 198건
- 사건 사실로만 유지한 VOC: 41건
- 중복·테스트·타 시스템 등 범위 밖: 15건

`2026-02-15 ~ 2026-02-21` 주차 파일은 현재 VOC 폴더 목록에서 확인되지 않았다. 따라서 334건은 **존재하는 파일 전체**에 대한 Coverage이며, 누락 주차의 실제 VOC가 0건이었다는 증거는 아니다.

## 2. “전체 적용”의 의미

모든 VOC를 Claim으로 바꾸지 않았다.

모든 VOC에는 다음 중 하나의 처분을 부여했다.

```text
supports-claim
bounds-claim
candidate-source
case-only
out-of-scope
```

이 방식으로 모든 사건은 처리됐지만, 반복성·적용 조건·원문 품질이 부족한 사건은 일반 Claim으로 승격하지 않았다. 이는 미처리가 아니라 완결성 프레임워크에 따른 의도적 제한이다.

## 3. 정식 승격 완료 영역

### 네트워크

- 주소 선택 전 서비스 모델·프로파일·방향·목적 확인
- DKS-N 내부 Ingress IP와 외부 등록 주소 구분
- DKS-N DNS VIP 확인 절차
- DKS-C Egress SNAT
- DKS-C 외부 NodePort 접근 제한
- DKS-C ALB Backend의 관측된 LB VIP 사용
- DKS-N Nginx Ingress에서 DKS-C Gateway API로의 전환 경계
- DKS-C Controller와 사용자 Routing Resource 책임 분리

### 콘솔·신청

- Namespace 이름 불변성
- 신규 Namespace 생성·Workload 이전·기존 삭제의 교체 패턴

### 인증·권한

- One Cloud Project Membership 선행조건
- Project 멤버와 Namespace 멤버 권한의 단계 분리
- 사용자 목록 등록을 위한 최초 Console Login 조건

### 플랫폼 정책

- DKS-N 공용형의 사용자 Cluster Scope 권한 제한
- Cluster Scope Operator 직접 설치 제한
- 공용 Worker Node 사용자 Label 관리 제한

### 자원

- 2026-06 관측 Request:Limit 1:3 정책
- Namespace ResourceQuota 초과 시 Pod 생성 거부

### 스토리지

- DKS PVC의 외부 일반 VM 직접 Mount 제한
- 별도 VM NFS·동기화 경로를 이용한 관측 대안

### 배포

- P-DEP 관리 필드의 Live 수정이 재배포 때 덮어써질 수 있는 경계
- 지속 설정을 Git·CD 선언 원본에 반영하는 절차

### 이미지·Harbor

- Credential 변경 시 Pull Secret 갱신 요구

## 4. 잔여 후보가 정식 Claim이 아닌 이유

198건은 하나 이상의 다음 조건 때문에 후보로 남아 있다.

1. 요약 목록만 확인했고 상세 공식 답변을 아직 검토하지 않음
2. 서비스 모델·망·구축 세대가 확인되지 않아 적용 범위를 정할 수 없음
3. 같은 후보 이름 아래 실제로는 독립적인 주장이 여러 개 섞여 있음
4. 특정 Cluster·Namespace·IP·Quota 값에 종속된 일회성 사실임
5. 시간에 따라 바뀌는 정책값인데 현재성을 확인하지 못함
6. 반례처럼 보이는 사례가 조건 차이인지 실제 충돌인지 아직 설명되지 않음
7. 운영팀 답변이 원인 확정이 아니라 가설·권고 수준임

## 5. 잔여 검증 우선순위

### A. 장애·운영 Guard Claim 후보

#### `ephemeral-storage-eviction`

검증할 연결:

```text
Node ephemeral-storage 고갈
→ DiskPressure 또는 Eviction Threshold 도달
→ Pod Eviction·재스케줄링
```

확인할 경쟁 설명:

- Container Log·emptyDir·Image Layer 중 실제 소비 주체
- Node 전체 문제와 개별 Pod Limit 문제의 구분
- 공용 Node에서 타 Namespace 사용량이 미치는 영향

#### `ingress-backend-readiness`

검증할 연결:

```text
Ingress 502·Bad Gateway
→ Ingress 자체 장애인지
→ Backend Endpoint·Port·Probe 실패인지 분리
```

단순히 502가 Backend 문제라는 일반화는 금지한다.

#### `connectivity-layer-differential-diagnosis`

후보 Guard:

- TCP Handshake 전 실패
- TLS Handshake 실패
- Envoy·Ingress까지 정상 도달
- HTTP Status 또는 Application Reset

각 관측 지점이 배제할 수 있는 가설을 원문 대화로 검증한다.

#### `cpu-throttling-timeout`

확인할 연결:

```text
CPU Limit 도달
→ CFS Throttling
→ 처리 지연
→ 504·UI 정지
```

단일 사례의 상관관계를 일반 원인으로 승격하지 않도록 실제 Metric·Event 근거를 확인한다.

### B. 관측성 후보

#### `prometheus-pod-churn-cardinality`

Pod의 대량 생성·삭제가 Series Cardinality와 TSDB Memory를 증가시켜 OOM으로 이어졌는지 원문 근거를 확인한다.

#### `namespace-monitoring-boundary`

기본 Platform Metric, 사용자 Workload Metric, Namespace 전체 관측, Custom Metric 지원 범위를 별도 Claim으로 분리한다.

### C. 자원·수요 후보

- `low-utilization-reclaim-*`
- `unplanned-minimum-resource`
- `resource-change-request`
- `resource-usage-evidence-for-reduction`
- `dksc-unplanned-resource-request`

분리할 주장:

1. 저활용 판정 기준
2. 회수 또는 예외 승인 절차
3. 계획 외 최소자원 생성
4. 실사용 근거 기반 증설
5. DKS-N과 DKS-C의 신청 절차 차이

### D. 인증·Token 후보

- `cicd-serviceaccount-vs-oidc-token`
- `serviceaccount-token-secret-lifecycle`
- `multicluster-deployment-token`
- `dksc-kubeconfig-and-pdep-token`
- `longterm-token-validity`

사람의 CLI Login, Kubernetes ServiceAccount, OIDC Access Token, P-DEP 등록 Token을 하나의 “장기 Token”으로 합치지 않는다.

### E. Harbor·Registry 후보

- `harbor-project-namespace-coupling`
- `harbor-robot-account-pull-secret`
- `registry-retention-user-managed`
- `dksc-registry-management-and-quota`
- `harbor-registry-trust`
- `harbor-vulnerability-scan-policy`

Project 생성, Authentication, Pull Credential, 저장공간, Retention, CA Trust, Vulnerability Policy를 각각 독립 Claim으로 검증한다.

### F. Namespace·삭제 후보

#### `namespace-finalizer-deletion`

일반 삭제 지연과 강제 Finalizer 제거를 구분한다. 강제 제거가 남은 외부 Resource를 고아 상태로 만들 수 있는지 포함해 안전조건을 검증한다.

#### `namespace-project-transfer-unsupported`

Namespace 이름 불변성과 Project 간 이전 불가를 같은 Claim으로 합치지 않는다. 객체 불변성과 DKS 관리관계 제약을 별도로 확인한다.

### G. DKS-N / DKS-C 전환 후보

- Local `kubectl` 접속 가능성
- Tenant·VPC 격리
- StorageClass
- P-DEP Token
- Gateway·Ingress
- Cluster Scope 권한
- 운영계·개발계 제공 정책

“DKS-N 대 DKS-C 차이표”를 먼저 쓰지 않는다. 각 차원을 독립 Claim으로 확정한 뒤 View 문서에서 합친다.

## 6. 현재성 검증 백로그

현재 정식 Claim 대부분은 다음 상태다.

```yaml
currentness: unverified-current
operational_use: advisory
```

다음은 최신 공식 자료와 교차 검증해야 한다.

1. DKS-N/C 네트워크 주소 선택과 Egress 구조
2. DKS-C Two-Arm LB·Gateway 제공 방식
3. Request:Limit 1:3 정책의 현재 적용 범위
4. One Cloud·DKS 사용자 동기화 절차
5. DKS-N Cluster Scope·Operator 지원 목록
6. P-DEP Field Ownership과 Custom CD 제약
7. Registry Robot Account·Token Rotation 정책
8. DKS-N/C Storage ACL과 외부 공유 지원 범위

최신성 확인 전에는 실제 신청값·명령·설계 승인의 확정 근거로 사용하지 않는다.

## 7. 다음 처리 순서

```text
잔여 후보군 선택
→ 관련 VOC 전체 검색
→ 상세 대화 원문 확인
→ 사실과 운영팀 추론 분리
→ 같은 조건의 반복 근거 확인
→ 다른 조건의 반례 검색
→ 원자 Claim으로 분해
→ 완결성 검사
→ Claim 승격 또는 case-only 유지
→ Coverage Ledger 갱신
```

우선순위는 반복 건수가 아니라 **현재 문서의 오판을 가장 많이 줄일 후보**를 먼저 둔다.

1. 장애 원인 분기 Guard
2. Token·권한 책임 경계
3. DKS-N/C Migration 차원
4. 자원 신청·회수 정책
5. Harbor 운영정책
6. 관측성·스토리지 세부 Runbook

## 8. 완료 기준

전체 후보 처리는 Claim 수가 198개가 되는 것이 아니다.

다음 상태가 완료 기준이다.

- 각 후보군의 관련 원문을 확인함
- Claim으로 승격하거나 `case-only` 유지 이유를 기록함
- 동일 조건의 충돌을 설명하거나 `contested`로 남김
- Claim의 현재성을 공식 자료로 확인하거나 `unverified-current`를 유지함
- Ledger와 Claim의 상호 참조가 일치함

논리적으로 일반화할 수 없는 사건을 Claim으로 만들지 않는 것이 이 설계의 정상 동작이다.
