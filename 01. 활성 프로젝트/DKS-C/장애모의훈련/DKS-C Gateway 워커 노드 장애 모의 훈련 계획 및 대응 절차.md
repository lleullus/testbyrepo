# DKS-C Gateway 워커 노드 장애 모의 훈련 계획 및 대응 절차

> 상태: **실행 전 검토안**. 이 문서는 훈련 목표·관측·전파·복구 판정의 작업 초안이지, VM 삭제 승인이나 기존 장애/이슈 관리 절차의 대체 승인이 아니다. 요청 내용은 개발계 `dev-dksg-ic01-khm`을 대상으로 하지만, 현재 인벤토리와 노드 수가 서로 다르다. 아래 선결 사항을 확인하기 전에는 장애를 유발하지 않는다.

## 문서의 목적

Gateway 클러스터 워커 VM 한 대가 사라졌을 때 나머지 노드에서 DKS-C의 접속 경로가 유지되는지, 장애를 어떻게 인지·전파·점검하고 대체 VM과 서비스가 실제로 회복되었는지를 한 번의 훈련으로 확인하기 위한 계획이다. DKS 운영팀의 기술 대응과 운영·개발 유관 조직의 협조 범위를 함께 기록한다.

## 전체 이해 지도

- **이번 훈련은 Gateway 클러스터의 워커 VM 한 대를 잃는 상황을 재현해 실제 접속 결과와 복구 능력을 검증한다.** 요청 대상은 개발계 `dev-dksg-ic01-khm`이며, 의도한 장애는 Control Plane이나 Guest Cluster가 아니라 Gateway Worker 한 대에 한정된다. 노드가 하나 없어졌다는 관측만으로 서비스 영향이나 자동 복구 성공을 판정하지 않는다.
- **Gateway의 APISIX는 콘솔·서비스·클러스터 API로 들어온 요청을 해당 대상으로 중계하고, Keycloak은 로그인에 관여한다.** 같은 워커에서 실행 중인 Pod가 영향을 받을 수 있으므로 노드·Pod 재배치, APISIX 요청 성공, 콘솔 로그인, Guest Cluster API의 실제 인증된 조회를 나누어 관측한다. 어떤 경로가 반드시 이 개발 Gateway를 지나는지는 현행 LB·Route 설정으로 확인한다.
- **인지·전파·점검은 복구 작업과 병행하되, 같은 시간축의 증거로 연결한다.** 모니터링 알림 또는 직접 점검으로 이상을 발견하면 모의 훈련임을 밝히고 공식 메신저로 상황을 공유한다. 서비스 접근이 실패하거나 영향이 확산되면 유선 긴급 공유를 추가하며, 담당자는 노드·Pod·인증·라우팅·Guest API의 실제 실패 지점을 조사한다.
- **VM이 다시 만들어지는 것과 이용자가 서비스를 사용할 수 있는 것은 서로 다른 완료 조건이다.** 대체 Machine/VM과 Kubernetes Node의 정상 등록, 필요한 Pod의 Ready와 endpoint 편입, 동일 경로의 접속 재검증을 각각 확인한다. 정해진 시간 내 대체가 멈추거나 실제 서비스 영향이 나타나면 훈련을 중단하고 운영 장애 대응으로 전환한다.

## 1. 무엇을 대상으로 하며, 무엇을 먼저 확정해야 하는가?

| 항목 | 이번 훈련의 범위·판정 대상 |
|---|---|
| 대상 환경 | 요청서의 개발계 Gateway `dev-dksg-ic01-khm`. 운영계 `prd-dksg-ic01-khm` 및 다른 관리 클러스터는 장애 유발 대상에서 제외 |
| 유발 범위 | Gateway Worker **VM 한 대**만 삭제하는 시나리오. Control Plane, MachineSet 전체, 게스트 클러스터 및 운영계 VM은 삭제 금지 |
| 기대 관측 | 나머지 워커에서 Gateway 서비스가 요청을 처리하는지, CAPI/인프라 조정으로 대체 VM이 생기는지, 신규 Node가 Ready로 등록되는지 각각 별도 확인 |
| 서비스 범위 | 요청서에 기재된 클러스터 API 경로, DKS-C 콘솔·인증·관측 화면. 서비스별 실제 개발계 라우팅과 URL은 사전 대조 후 확정 |
| 훈련 목표 | 원인·영향 분석과 복구 절차의 시간축 재현, 상황 전파 경로 확인, 노드 자동 복구와 서비스 가용성의 구분 검증 |

**실행 전 불일치:** 요청서에는 Gateway 워커 **5대 중 1대**를 삭제한다고 되어 있고 5개 VM 이름이 제시된다. 반면 로컬 운영 인벤토리 `DKS-C 운영 현황 요약.md`의 WLD02 표는 `dev-dksg-ic01-khm`을 **워커 3대**로 기록한다. 해당 인벤토리는 시점 스냅샷이므로 현재 수량을 증명하지도, 요청의 5대를 오류라고 단정하지도 못한다. 현행 `kubectl get nodes -o wide`, 소속 MachineDeployment/MachineSet/Machine, VCFA/vCenter VM 인벤토리로 **클러스터·워커 수·삭제 후보의 UID/소속·Zone·실제 Pod 배치**를 서로 맞추고 훈련 책임자가 한 대를 지정한다. 요청서에 전사된 `az01`/`az02` VM 이름은 대소문자 `I/l` 및 줄바꿈이 불명확해 삭제 명령의 입력값으로 재사용하지 않는다.

**실행 전 경로 불일치:** 요청서의 `https://console.dks.samsungds.net`, `https://keycloak.dks.samsungds.net`, `https://grafana.dks.samsungds.net`, `https://opensearch-dashboard.dks.samsungds.net` 등은 로컬 운영 인벤토리에서 **운영 WLD01 주소**로 기록된다. 로컬 WLD02에는 `https://console-dev.dks.samsungds.net/`, `https://keycloak-dev.dks.samsungds.net/`, `https://grafana-dev.dks.samsungds.net/`, `https://opensearch-dashboard-dev.dks.samsungds.net/`가 따로 기록된다. 운영 URL은 참고·비영향 관측 대상으로 둘 수 있지만 개발 Gateway 훈련의 성공 기준으로 바로 대체할 수 없다. 요청서의 `https://cluster.dks.samsungds.net/cluster/{cluster_name}`, `https://monitoring.dks.samsungds.net`, `https://alert.dks.samsungds.net`, `https://opensearch-api.dks.samsungds.net` 역시 실제 개발 경로·인증 방식·테스트 가능한 Guest Cluster를 운영/개발팀과 대조한다. `{cluster_name}`은 실제 대상명이 아니라 요청서의 자리표시자다.

## 2. 삭제 전 어떤 기준선과 중단 조건을 준비하는가?

DKS 운영팀은 계획·SOP 초안, 사전 점검, 훈련 실행, 감지·전파·조치, 결과 보고를 담당한다. 운영 개발팀에는 Gateway 애플리케이션의 배치·헬스 확인, 개발계 접속 경로와 인증 가능한 테스트 계정·Guest Cluster 확인, 서비스 오류 시 분석 지원을 요청한다. 실제 훈련 담당자·상황 전파 수신자·유선 연락망·인프라 VM 조치 담당자·일시와 승인자는 아직 지정되지 않았다.

| 준비·기준선 | 확보할 증거와 의미 |
|---|---|
| 대상·권한 확정 | 개발계 context, Machine↔VM↔Node 대응, 실제 워커 수와 가용 Zone, 삭제 대상 한 대의 현재 워크로드, 실행 권한·작업 승인 기록. 이름만 일치하는 VM을 삭제하지 않음 |
| 복구 가능성 | MachineDeployment/MachineSet의 의도한 replicas와 현재 상태, 자동 재생성 방식, VM 생성 quota·스토리지·IP/Zone 여유, vCenter/CCI/CAPI 상태. VM을 직접 삭제했을 때 자동 복구가 일어나는지는 관리 객체·조정 정책에 의존하므로 사전 확인 |
| 여유·영향 | 나머지 노드의 자원 및 APISIX Data Plane·Ingress·Keycloak·인증 DB·APISIX Control Plane/etcd 등의 Pod 수·배치·Ready·PDB·endpoint. 특정 단일 Pod가 대상 노드에만 있는 경우 영향이 없다고 가정하지 않음 |
| 사용자 경로 | 개발계 콘솔 접속 및 로그인, APISIX를 통한 정해진 Guest Cluster의 인증된 읽기 전용 API 조회, 대표 서비스 요청의 응답/지연/오류율. 성공 기준은 단순 TCP 연결이나 로그인 화면 표시가 아닌 동작 완료 |
| 관측 경로 | Grafana/모니터링의 대상 노드·Pod·요청 성공률/오류·지연, Alert 수신 여부, 필요시 OpenSearch 로그. 모니터링 화면 자체에 장애가 있으면 직접 API 조회와 서비스 요청으로 별도 확인 |
| 기록 | 훈련 시작·삭제·최초 감지·최초 전파·서비스 영향·대체 VM 생성·Node Ready·서비스 회복 시각을 동일 시간대(KST)로 기록. 시작 전후 동일 요청·계정·경로를 비교 |

**시작 불가:** 대상·환경/권한 또는 위 3대↔5대 불일치가 해소되지 않은 경우, 운영계 경로와 개발계 경로를 분리하지 못한 경우, 남은 워커 용량이나 핵심 단일 Pod 영향이 수용 가능한지 판단할 수 없는 경우, 자동 복구의 조정 주체와 수동 복구 담당자가 불명확한 경우에는 VM을 삭제하지 않는다. 중단 시 연락할 사람과 훈련 종료 시각도 시작 전에 정한다. 여기서 수치형 허용 오류율·RTO는 승인된 운영 기준이 제공되지 않아 임의로 정하지 않는다.

## 3. 장애를 어떻게 유발하고 인지·전파·점검하는가?

아래는 **승인 후 실행할 순서**이며 실제 시스템에 실행한 결과가 아니다. VM 삭제 명령의 구문과 관리 API는 제공된 자료만으로 확정할 수 없다. 특히 `kubectl delete node`, `kubectl delete machine`, `kubectl delete machineset`, 인프라 VM 삭제는 서로 다른 조정 동작을 유발하므로 동등한 방법으로 취급하지 않는다. 인프라 담당자는 현행 VM 식별자와 승인된 작업 방법을 대조하고 **한 대만** 조치한다.

| 단계 | 담당·행동 | 기록·분기 |
|---|---|---|
| 0. 시작 선언 | DKS 운영팀이 공식 메신저에 `모의 훈련`, 개발계 대상·예정 시각·연락 담당·중단 기준을 사전 공지하고 기준선 기록 | 실제 장애와 혼동되지 않도록 훈련 식별자와 시작 시각 기록 |
| 1. 장애 유발 | 승인된 담당자가 확정된 Gateway Worker VM 한 대를 삭제. 동시에 Machine/VM/Node 식별자와 작업 시각 보존 | 다른 객체를 선택했거나 예상 밖 다중 노드 영향이 보이면 추가 조치 중단, 실제 장애 대응으로 전환 |
| 2. 인지·초동 | DKS 운영팀이 Alert/모니터링과 `Node NotReady`/소실, Pod 재스케줄 및 endpoint 변화를 확인. 알림이 없더라도 직접 조회한 발견 시각 기록 | 감지 경로별 시각과 알림 누락 구분. 모니터링 불가 자체를 서비스 정상으로 취급하지 않음 |
| 3. 공식 전파 | 공식 메신저로 대상·발견 시각·현상·확인된 영향·담당·다음 갱신을 전달. 실제 접속 실패·영향 확산·복구 정체 시 유선 긴급 공유 병행 | 추측한 원인을 확정 사실로 쓰지 않고 확인 중인 항목을 구분; 수신 확인과 후속 갱신 기록 |
| 4. 영향 점검 | Gateway 노드/Pod/Service endpoint, LB/APISIX 라우팅과 응답, Keycloak 로그인, 콘솔의 실제 기능, Guest Cluster API 읽기 조회를 **사전 동일 경로**로 점검 | 한 경로가 성공해도 다른 경로의 가용성을 추론하지 않음. Pod Ready와 외부 사용자 성공을 별도로 기록 |
| 5. 복구 추적 | CAPI Machine 상태·이벤트, VM 생성·초기화, 신규 Node Ready, 핵심 Pod 배치·Ready 및 endpoint 편입 순서로 확인 | VM 생성 실패 시 quota/스토리지·인프라 이벤트 등 원인을 조사; 재삭제·무단 스케일 조정으로 증상을 가리지 않음 |
| 6. 종료 판정 | 같은 사용자 경로를 반복 요청해 콘솔·인증·Guest API·대표 서비스 결과가 기준선으로 돌아왔는지 확인하고 상황 종료 전파 | 자동 복구와 서비스 정상화의 마지막 확인 시각을 각각 기록. 불충족 시 실제 장애 대응 유지 |

메신저 공지 예시: `【모의 훈련 / 개발계 Gateway】 [KST 시각] dev-dksg-ic01-khm 워커 VM 1대 장애 유발. 현재 감지: [알림/직접 확인]. 영향: [확인된 경로와 결과 또는 확인 중]. 담당: [이름/연락처]. 다음 공유: [시각]. 실제 서비스 영향이 확인되면 유선으로 즉시 공유하고 훈련을 중단합니다.`

## 4. 복구 완료와 훈련 종료를 어떻게 구분하는가?

워커가 사라진 뒤에도 `apisix-ingress`/APISIX Data Plane, APISIX Control Plane/etcd, Keycloak 및 DB, 인증 서비스와 관련 Pod가 남은 노드에 정상 배치되는지 확인한다. 요청서의 `process list`, `s3-upload-manual`, `apisix-data-plane-x` 등은 현행 배포 이름·namespace·서비스 의존성을 조회해 검증 대상으로 확정한다. 단일 Pod/데이터 볼륨의 재시작이 원래 서비스 중단을 만들 수 있는지 운영 개발팀과 점검한다.

**자동 복구 확인:** 삭제된 VM이 없어진 시점 → 대체 Machine/VM 생성 → Kubernetes Node 등록 및 Ready → 필요한 Pod의 Ready·서비스 endpoint 편입을 기록한다. 새로운 VM이 생성되기만 하면 성공이 아니다. 대체가 생성되지 않거나 Pending/NotReady로 멈추면 담당자가 인프라/CAPI 이벤트와 quota 등 원인을 확인하고, 승인된 복구 절차로 전환한다. 이 문서는 검증되지 않은 수동 VM 생성 명령을 임의로 지정하지 않는다.

**서비스 회복 확인:** 실제 개발계 콘솔 로그인·대표 기능, 인증, 미리 지정한 Guest Cluster의 인증된 API 읽기, APISIX 경유 대표 요청을 훈련 전과 같은 방식으로 반복한다. 응답 성공과 오류율·지연을 비교하고 알림의 해제 여부를 별도로 기록한다. 운영계 공개 URL만 정상인 경우 개발계 회복 판정은 유보한다. 일시적 단절이 있었으면 발생·회복 시간과 사용자 영향 범위를 기록하고 **무중단 성공**이라고 쓰지 않는다.

**중단·에스컬레이션:** 예상하지 않은 운영계/다른 클러스터 영향, 핵심 서비스 요청 실패, 남은 워커 용량 부족, 다중 VM/Pod 장애, 자동 복구 정체, 모니터링 상실로 영향 범위 판단 불가 시 추가 장애 유발을 즉시 멈춘다. 유선 긴급 공유로 실제 운영 장애 대응 담당자를 연결하고, 현행 공식 장애/이슈 관리 절차의 티켓·상황실·보고 규칙을 따른다. 기존 절차가 확보되지 않았다면 임시 문서의 갱신 간격이나 임의의 장애 등급을 공식 규칙처럼 선언하지 않는다.

## 실행 전 협조 요청 및 자료 안내

운영 개발팀과 훈련 책임자에게 다음 사항을 **확인 요청할 초안**이다. 이 문서 작성 과정에서 실제 담당자에게 연락하거나 장애를 유발하지 않았다.

1. `dev-dksg-ic01-khm`의 현재 워커 수는 3대인가 5대인가? 현행 VM↔Machine↔Node 목록과 삭제 후보 한 대의 UID·Zone·Pod 배치, 훈련 일시와 승인자는 누구인가?
2. 개발계 콘솔/Keycloak/모니터링/알림, APISIX 경유 Guest Cluster API의 **실제 URL·Route·테스트 계정·읽기 전용 요청**은 무엇인가? 요청서의 운영계 주소 중 개발 훈련 영향 검증에 유효한 것은 무엇인가?
3. 인프라 VM 직접 삭제가 현행 CAPI/MachineSet에서 대체 생성으로 이어지는가? 승인된 VM 삭제·수동 복구 SOP와 quota/용량 사전 점검 방법, 실제 조치 담당자는 누구인가?
4. 공식 메신저 채널·유선 비상연락망·장애 등급·티켓/상황 전파·업데이트 간격·훈련에서 실제 장애로 전환하는 권한은 무엇인가? [장애/이슈 관리 참고](https://confluence.samsungds.net/spaces/dks/pages/686174896/G.+%EC%9E%A5%EC%95%A0+%EC%9D%B4%EC%8A%88+%EA%B4%80%EB%A6%AC) 원문/접근 권한을 공유해 이 초안을 현행 규정과 대조해 달라. 작성 시 해당 내부 링크는 연결되지 않아 내용을 확인하지 못했다.
