# 2026-06 DKS VOC 인사이트

> [!important] 이 문서의 역할
> 이 문서는 2026년 6월 VOC에서 확인되는 **DKS 주소의 역할 구분, DKS-N→DKS-C 전환 경계, Quota와 Scheduling의 차이, 접속 Credential의 목적 구분**을 학습 관점에서 정리한다.
>
> 6월에는 기존 공용형 DKS와 DKS-C 전용형 문의가 동시에 존재하고, 같은 CI/CD 연동에 대해서도 Kubeconfig·ServiceAccount Token·OIDC Long-Term Token처럼 서로 다른 표현과 절차가 등장한다. 이를 하나의 규칙으로 억지로 합치지 않고, 어떤 행위자와 접속 목적에 대한 답인지 분리한다.

## 0. 6월 자료의 특징

6월은 DKS-C가 단순한 “새 Cluster”가 아니라 별도의 네트워크·Routing·인증·Storage 모델이라는 점이 실제 문의에서 구체화된 시기다.

- API Server, Ingress VIP, Outbound Source 주소가 서로 다른 역할로 등장했다.
- DKS-N의 NGINX Ingress Manifest는 DKS-C의 Contour·Gateway API 모델에 맞춰 수정해야 했다.
- 자원 부족처럼 보이는 실패가 Namespace Quota 초과와 Node 가용자원 부족으로 나뉘었다.
- 사람의 SSO 접속, CLI Kubeconfig, P-DEP·GitOps 자동화 Credential이 서로 다른 문제로 나타났다.

따라서 6월의 핵심은 **이름이 비슷한 대상을 목적과 제어 계층에 따라 분리하는 것**이다.

---

# 1. 이번 달 한눈에

1. **API Server 주소, Ingress VIP, Outbound Source 주소는 같은 “Cluster IP”가 아니다.**
2. **DKS-N에서 DKS-C로의 이전은 Manifest 복사가 아니라 Routing·인증·Storage 의미의 변환이다.**
3. **Namespace Quota 초과와 Worker Node 가용자원 부족은 서로 다른 실패 Gate다.**
4. **Console SSO, 사람의 CLI, CI/CD 배포는 요구하는 Credential과 수명이 다를 수 있다.**
5. **Namespace가 Terminating에 머문다고 Finalizer를 즉시 제거해서는 안 된다.**

# 2. 확인된 인사이트

## 2.1 주소는 이름이 아니라 목적·방향·서비스 모델로 구분한다

### VOC에서 확인된 사실 — 공용형 DKS

VOC `2026060411254332894`에서 외부 사용자가 DKS Web Service에 접근하기 위한 IP·Port를 문의했다.

운영팀은 다음 두 방향을 분리했다.

- 외부 → DKS HTTP/HTTPS: Cluster별 VIP를 Destination으로 사용하고 80·443 및 URL Filtering 절차 적용
- DKS → 외부: Cluster별 Node IP 대역을 Source로 사용

VOC `2026062218271247272`에서는 P-DEP 연동을 위해 필요한 주소를 다시 세 종류로 구분했다.

1. Kubernetes API Server IP:Port
2. 외부 통신용 Cluster Egress Node IP 대역
3. 사용자 Service Inbound용 Ingress LB VIP

### VOC에서 확인된 사실 — DKS-C

VOC `2026063016483603852`에서 DKS-C Pod가 외부 DB로 나갈 때 Source IP를 문의했다.

운영팀은 DKS-C Cluster가 전용 VPC에 구성되고, 외부 통신 시 해당 Cluster 전용 Egress IP로 SNAT되므로 그 Egress IP를 방화벽 Source로 사용한다고 답변했다.

VOC `2026062516184272719`에서도 DKS-C는 Cluster마다 독립 VPC와 외부 통신용 Egress SNAT IP를 연결한 격리 모델로 설명됐다.

### 여기서 읽을 수 있는 주소 역할

~~~text
1. Kubernetes API 관리 접점
   Client / CI/CD → API Server Endpoint

2. 사용자 Service Inbound
   External Client → Ingress·LoadBalancer VIP → Workload

3. Workload Outbound
   Pod → Cluster 외부
      ├─ 당시 공용형 DKS: Worker / Node Subnet Source
      └─ DKS-C 전용 VPC: Egress SNAT IP Source
~~~

따라서 “Cluster IP가 무엇인가?”라는 질문만으로는 주소를 결정할 수 없다. 먼저 다음을 확인해야 한다.

- Kubernetes API에 접속하려는가?
- 사용자 Service에 들어오는 Traffic인가?
- Pod에서 외부로 나가는 Traffic인가?
- DKS-N인가 DKS-C인가?
- 방화벽 Source를 묻는가, Destination을 묻는가?

### 이 인사이트가 말하지 않는 것

- API Server, Ingress, Egress가 항상 각각 하나의 고정 IP만 가진다는 뜻은 아니다.
- 6월에 기록된 Port와 주소 대역을 다른 Cluster에 그대로 적용할 수 있다는 뜻은 아니다.
- DKS-C의 모든 Outbound Traffic이 동일한 Network Profile과 SNAT 정책을 사용한다는 뜻은 아니다.
- 공용형 DKS의 Worker Node 대역 답변을 DKS-C에 적용할 수 있다는 뜻도 아니다.

## 2.2 DKS-N→DKS-C 이전은 Resource 의미를 다시 매핑하는 작업이다

### VOC에서 확인된 사실

VOC `2026061609200507157`에서 기존 DKS-N Workload를 DKS-C로 이전할 때의 차이를 문의했다.

운영팀은 다음 세 영역을 주요 차이로 안내했다.

1. Routing: DKS-N의 NGINX Ingress와 DKS-C의 Contour·Gateway API 기반 Envoy Routing
2. 인증: DKS-C OIDC SSO와 Kubeconfig·Token 발급
3. Storage: DKS-C 전용 StorageClass

VOC `2026062312395352000`에서는 Routing 차이가 더 직접적으로 설명됐다. DKS-N은 Ingress NGINX를 사용하고 DKS-C는 Contour 및 Gateway API를 사용하므로 Annotation과 Resource Spec이 다르며, Migration 시 `Gateway`·`HTTPRoute` Manifest 수정이 필요하다고 안내했다.

PaaS에서 DKS-C로 이전하는 다른 6월 사례에서도 DKS-C Tenant 신청 후 Contour·Gateway API Routing과 vSAN PVC를 구성하도록 안내했다.

### 여기서 읽을 수 있는 Migration 구조

~~~text
기존 Workload Manifest
        ↓
동일 YAML 그대로 적용?
        X
        ↓
기능별 의미 비교
        ├─ Ingress Rule / Annotation
        │      → Gateway / HTTPRoute / Contour 설정
        ├─ Cluster 접속 방식
        │      → OIDC / Kubeconfig / 자동화 Credential
        ├─ StorageClass / PVC
        │      → DKS-C StorageClass 선택 + Data Migration
        ├─ Service Exposure
        │      → LoadBalancer / Gateway / Health Check
        └─ 권한·Operator
               → 전용 Cluster Policy 재확인
~~~

Migration 완료 여부도 “Pod가 Running인가?” 하나로 판단하면 부족하다.

- DNS와 외부 Routing이 새 Endpoint를 바라보는가?
- TLS Secret과 Host 설정이 맞는가?
- 기존 Data가 새 PVC에 존재하는가?
- CI/CD가 새 API Server와 Credential을 사용하는가?
- Monitoring·Backup·Alert 경로가 다시 연결됐는가?

### 이 인사이트가 말하지 않는 것

- 모든 NGINX Ingress 기능을 Gateway API로 일대일 변환할 수 있다는 뜻은 아니다.
- DKS-C의 현재 Storage Backend가 6월 답변과 동일하다는 뜻은 아니다.
- 기존 Manifest를 전부 새로 작성해야 한다는 뜻도 아니다. 변경이 필요한 차원을 식별하는 것이 핵심이다.
- OIDC·Kubeconfig·Token 절차의 현재 구현이 6월과 같다는 뜻은 아니다.

- [[CCL-NET-007 - DKS-C는 Controller를 제공하지만 Gateway와 HTTPRoute는 사용자가 작성한다]]

## 2.3 Namespace Quota와 Node Scheduling Capacity는 서로 다른 Gate다

### VOC에서 확인된 사실 — Request:Limit 정책

VOC `2026060509215539969`에서 CPU·Memory 증설 기준을 문의했다.

운영팀은 당시 Namespace CPU·Memory Quota에 `Request:Limit = 1:3` 비율을 적용하고 있다고 설명했다. Limit 기준의 요구량이 있다면 그 비율을 고려해 Request Quota를 신청하도록 안내했다.

### VOC에서 확인된 사실 — Namespace Quota 초과

VOC `2026063015591003237`에서 Jenkins Agent Pod 생성 시 `exceeded quota: requests.cpu`가 발생했다.

운영팀은 Namespace CPU Request Quota 90 Core 중 87.55 Core가 이미 사용 중인 상태에서 4 Core 요청이 추가돼 Quota를 초과했고, 그 결과 Pod 생성이 거부됐다고 설명했다.

VOC `2026062614334080181`에서도 CPU Limit Quota 합계 초과로 Workload 배포가 진행되지 않은 사례가 기록됐다.

### VOC에서 확인된 사실 — Node 가용자원 부족

VOC `2026061514125201281`에서는 Pod Event에 `0/N nodes are available: insufficient cpu/memory`가 나타났다.

운영팀은 Namespace Quota가 아니라 Worker Node의 실제 여유 자원이 부족해 Pod가 배치되지 못한 것으로 설명하고, Workload Request 조정 또는 Worker Scale-out을 검토하도록 안내했다.

### 여기서 읽을 수 있는 자원 Gate

~~~text
Pod Spec의 Resource Request / Limit
        ↓
1. Namespace ResourceQuota Gate
   - Namespace 전체 합계가 허용 범위 안인가?
   - 초과하면 생성·변경이 거부될 수 있음
        ↓
2. Scheduler / Node Capacity Gate
   - Request를 수용할 Node가 실제로 있는가?
   - 없으면 Pod는 Pending으로 남을 수 있음
        ↓
3. Runtime 사용량
   - 배치된 뒤 CPU Throttling·Memory OOM 등이 발생하는가?
~~~

이 세 질문은 서로 대체되지 않는다.

- Quota를 늘렸다고 실제 Node Capacity가 생기지는 않는다.
- Node에 여유가 있어도 Namespace Quota를 넘으면 생성이 거부될 수 있다.
- Pod가 배치됐다고 Runtime의 Limit·실사용량 문제가 해결된 것은 아니다.

### 이 인사이트가 말하지 않는 것

- `1:3` 비율이 현재 모든 Namespace의 고정 정책이라는 뜻은 아니다.
- Limit의 1/3만 신청하면 언제나 충분하다는 계산식도 아니다.
- `insufficient cpu/memory`가 반드시 Cluster Scale-out만으로 해결된다는 뜻은 아니다. Request 과다 설정도 확인해야 한다.
- Quota 수치가 곧 물리 Cluster의 총 가용자원이라는 뜻은 아니다.

### 관련 문서

- [[CCL-RES-001 - 관측된 Namespace Quota 정책은 Request 대 Limit 1대3이다]]
- [[CCL-RES-002 - Namespace Quota 초과 시 Pod 생성이 거부된다]]

## 2.4 “장기 Token”이라는 이름보다 행위자와 접속 목적을 먼저 구분한다

### 6월 원문에 등장한 서로 다른 접속 방식

6월 VOC에는 다음 안내가 함께 존재한다.

1. **사람의 Console 접속**
   - DKS-C Console은 SSO OIDC로 인증된다고 설명됐다.

2. **외부 CLI 접속**
   - Cluster 접속을 위해 ServiceAccount Token이 포함된 Kubeconfig를 등록하도록 안내된 사례가 있다.

3. **P-DEP Multi Cluster 배포**
   - 각 DKS-C Cluster의 API Server FQDN과 Long-Term ServiceAccount Token을 각각 P-DEP에 등록하도록 안내됐다.

4. **외부 CI/CD 장기 Credential**
   - 다른 6월 30일 VOC에서는 DKS-C 전용 OIDC Long-Term Access Token을 발급받아 CI/CD Credential로 등록하도록 안내됐다.

이 답변들은 표면적으로 모두 “배포용 장기 Token”처럼 보이지만, Token 발급 주체·Credential Type·대상 Tool·권한 Scope가 같은지 원문만으로는 완전히 닫히지 않는다.

### 여기서 읽을 수 있는 Credential 판단법

~~~text
누가 접속하는가?
        ├─ 사람
        │    ├─ Browser Console → SSO OIDC Session
        │    └─ Local CLI → Kubeconfig / 사용자 인증 방식
        │
        └─ 자동화 시스템
             ├─ P-DEP
             ├─ ArgoCD / Flux
             └─ 외부 CI/CD
                    ↓
             대상 Cluster API·필요 권한·Token 수명 확인
~~~

Credential을 선택하기 전에 다음을 확인해야 한다.

- Browser Login용인가, Kubernetes API 호출용인가?
- 사람 계정인가, ServiceAccount인가, OIDC Client인가?
- 단일 Cluster인가, Multi Cluster인가?
- Read-only인가, 배포 권한인가, Cluster Scope 작업인가?
- Token Rotation·만료·폐기 책임은 누구에게 있는가?
- Kubeconfig 안에 포함되는 Credential과 별도 Secret 저장소에 등록하는 Credential이 같은가?

### 완결성 검수 결과

6월 원문만으로는 “P-DEP에는 항상 정확히 이 Token Type을 써야 한다”는 하나의 결론을 정당화할 수 없다. ServiceAccount Token과 OIDC Long-Term Token 안내가 모두 있기 때문이다.

따라서 현재 운영 문서에서는 다음을 재확인해야 한다.

- 대상 P-DEP 기능과 Version
- DKS-C Cluster Generation
- 현재 지원하는 Authentication Flow
- Token 발급 주체와 Rotation 절차
- 필요한 RBAC Scope

### 이 인사이트가 말하지 않는 것

- 사람의 Kubeconfig와 CI/CD Token이 같은 Credential이라는 뜻은 아니다.
- ServiceAccount Token과 OIDC Access Token을 서로 교환해서 사용할 수 있다는 뜻도 아니다.
- “Long-Term”이 무기한이라는 뜻은 아니다.
- 6월의 절차를 현재 자동화에 그대로 사용해도 된다는 뜻은 아니다.

# 3. 관찰 포인트

## 3.1 Namespace Terminating과 Finalizer 제거는 일반 삭제와 다르다

VOC `2026062609203976164`에서 Namespace가 장시간 `Terminating`에 머물렀고, 운영팀은 제거되지 않은 CRD Instance의 Finalizer Block을 수동 정리하여 삭제를 완료했다.

Finalizer는 Resource 삭제 전에 Controller가 수행해야 할 정리 작업이 남았음을 표현할 수 있다. 따라서 삭제가 지연된다는 이유만으로 Finalizer를 즉시 제거하면, 외부 Storage·Network·Cloud Resource 정리가 끝나지 않은 채 Kubernetes Object만 사라질 가능성을 검토해야 한다.

6월 원문은 해당 사건의 수동 정리 결과만 제공하며, 어떤 CRD였는지와 외부 Resource 잔류 여부는 설명하지 않는다. 그러므로 이 사례는 다음 수준의 관찰로만 사용한다.

> Namespace가 Terminating에 머물면 남은 Resource와 Finalizer Owner를 먼저 확인하고, 강제 제거는 영향 범위를 확인한 뒤 수행한다.

---

## 3.2 Pod Trust Store와 Cluster·Node Trust는 같은 계층이 아니다

VOC `2026062217140146565`에서 다른 Cluster Service와 HTTPS 통신할 때 SSL 오류가 발생했다.

운영팀은 Pod 내부의 CA Trust Store는 Cluster·Node와 별도로 관리해야 하며, 상대 CA Certificate를 Secret·ConfigMap으로 Mount하고 Container Trust Store에 등록하도록 안내했다.

이 사례는 Node에 CA가 존재하는지와 Application Runtime이 해당 CA를 신뢰하는지를 구별해야 함을 보여준다. 다만 모든 Image·Runtime의 Trust Store 경로와 갱신 방식이 같다는 뜻은 아니다.

# 4. 6월 VOC만으로 확정하면 안 되는 것

1. **현재 주소·Port 목록**
   - 주소의 역할은 학습할 수 있지만 실제 Endpoint·Port·대역은 대상 Cluster에서 다시 확인한다.

2. **현재 DKS-N→DKS-C Migration 절차 전체**
   - 6월 답변은 핵심 차원을 제시하지만 Cutover·Rollback·Data 검증까지 포함한 완전한 절차는 아니다.

3. **현재 Request:Limit 정책값**
   - `1:3`은 당시 관측된 정책이며 현재 적용 범위가 달라질 수 있다.

4. **CI/CD용 단일 Token 표준**
   - 6월 원문에는 ServiceAccount Token과 OIDC Long-Term Token 안내가 함께 존재한다. 현재 대상 Tool별 절차를 확인해야 한다.

5. **Finalizer 강제 제거의 안전성**
   - 한 사건이 해결됐다는 사실은 일반적인 강제 삭제 승인이 아니다.

6. **DKS-C VPC 격리의 모든 세부 구현**
   - 독립 VPC·Egress 구조는 확인됐지만 Route·Firewall·LB·Network Profile의 모든 세부 조건은 별도 자료가 필요하다.

→ DKS-N과 DKS-C를 구분한다.

"DKS-N Manifest를 DKS-C에 배포하면 되나?"
→ Ingress/Gateway, 인증, Storage, 외부 연동 의미를 각각 다시 매핑한다.

"CPU가 부족해서 Pod가 안 뜬다."
→ exceeded quota인지 insufficient node capacity인지 Event를 먼저 읽는다.

"장기 Token이 필요하다."
→ 사람/자동화, CLI/P-DEP/GitOps, 단일/Multi Cluster, RBAC Scope를 먼저 정한다.

"Namespace 삭제가 멈췄다."
→ 남은 Resource·Controller·Finalizer Owner를 확인하고 강제 제거의 잔류 위험을 본다.
~~~
