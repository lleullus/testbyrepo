# 2026-04 DKS VOC 인사이트

> [!important] 이 문서의 역할
> 이 문서는 2026년 4월 VOC에서 확인되는 **DKS의 권한 흐름, 관리 접점, 인증서 책임, 스토리지 경계**를 학습 관점에서 정리한다. Console 화면에 보이는 현상만으로 플랫폼 전체 기능을 판단하지 않고, 각 기능의 실제 관리 주체와 Resource 경계를 구분한다.
>
> 4월 Coverage Ledger는 `summary-only` 기준의 1차 분류다. 이 문서의 핵심 인사이트는 관련 원문 대화를 다시 확인하여 작성했다. 당시 공용·Namespace형 DKS와 Beta 전환기의 답변을 현재 DKS-C 정책으로 자동 일반화하지 않는다.

## 0. 4월 자료에서 두드러진 변화

4월 VOC에서는 단일 기능의 사용법보다 **한 작업이 여러 관리 계층을 통과하는 방식**이 반복해서 드러났다.

- 사용자를 추가하려면 One Cloud Project, 인사정보 동기화, 최초 Console Login, Namespace Membership이 순서대로 관여했다.
- Console UI에서 입력할 수 없는 Resource도 DKSctl·YAML을 통해 생성할 수 있었다.
- TLS 인증서 발급과 Kubernetes Secret 등록은 서로 다른 주체가 담당했다.
- DKS가 관리하는 PVC를 외부 VM에서 직접 Mount하는 것과, 별도 공유 경로를 구성하는 것은 다른 문제였다.

따라서 4월의 핵심은 **“안 된다”는 현상을 만났을 때 어느 계층의 제약인지 먼저 식별하는 것**이다.

---

# 1. 이번 달 한눈에

1. **DKS 접근 권한은 Project 가입 하나로 끝나지 않고 여러 단계의 선행조건을 가진다.**
2. **Console UI에서 지원하지 않는 입력이 곧 Kubernetes Resource 자체의 미지원은 아니다.**
3. **TLS 인증서 발급, Secret 등록, Ingress 연결은 서로 다른 책임 단계다.**
4. **DKS 관리 Volume과 외부 VM 사이의 파일 공유는 직접 Mount가 아니라 별도 공유 경로로 설계해야 했다.**

추가로 Git 기반 배포와 Harbor 사례는 **현재 화면의 상태보다 선언 원본과 Namespace 결합 관계를 먼저 확인해야 한다**는 관찰 포인트를 제공한다.

# 2. 확인된 인사이트

## 2.1 DKS 사용자 권한은 선행조건이 있는 단계적 흐름이다

### VOC에서 확인된 사실

VOC `2026040119202958138`에서 협력사 사용자의 Namespace 및 Harbor 권한 추가를 요청했다. 운영팀은 먼저 One Cloud에서 Project 권한을 신청하고 승인받아야 DKS 권한 부여가 가능하다고 답변했다. Project 승인 이후 인사정보 동기화에 시간이 걸릴 수 있으며, Harbor 권한도 DKS Console Dashboard가 정상 표시된 뒤 확인하도록 안내했다.

VOC `2026041416130946649`에서는 신규 사용자를 One Cloud Project 멤버로 신청·승인하면 인사정보 동기화 뒤 DKS Project 멤버로 추가되고, 이후 DKS 관리자에게 Namespace 멤버 권한을 요청하도록 안내했다.

VOC `2026040315450674172`에서는 One Cloud Project에 멤버를 추가했지만 일부 계정이 DKS 권한 목록에 나타나지 않았다. 운영팀은 해당 계정이 아직 DKS Console에 로그인하지 않아 AD 권한이 없는 상태라고 설명하고, Console 1회 접속 후 정상화되는 것을 확인했다.

### 여기서 읽을 수 있는 권한 흐름

4월 사례에서 DKS 권한은 하나의 버튼으로 완료되는 단일 상태가 아니었다.

~~~text
One Cloud Project 참여 신청·승인
        ↓
인사정보·계정 정보 동기화
        ↓
DKS Console 최초 Login / 계정 인식
        ↓
DKS Project Membership
        ↓
대상 Namespace Membership·Role
        ↓
Harbor 등 연계 기능 권한 확인
~~~

이 흐름 때문에 상위 Project에 사용자를 추가했다는 사실만으로 다음 단계까지 모두 완료됐다고 판단하면 안 된다.

- 계정이 DKS에 실제 인식됐는가?
- Project Membership이 동기화됐는가?
- 대상 Namespace 멤버로 별도 등록됐는가?
- Namespace 안에서 필요한 Role을 받았는가?
- Harbor처럼 별도 연계 기능에서도 계정이 보이는가?

### 이 인사이트가 말하지 않는 것

- 모든 사용자에게 반드시 같은 수동 절차가 필요하다는 뜻은 아니다.
- 최초 Login이 현재 모든 계정 유형에서 항상 필요한 조건이라는 뜻도 아니다.
- 권한이 보이지 않는 모든 현상의 원인이 동기화나 최초 Login이라는 뜻은 아니다.
- Harbor 권한이 Namespace 권한과 완전히 동일하다는 뜻도 아니다. 4월 사례에서는 상위 선행조건이 연결돼 있었음을 보여준다.

## 2.2 Console UI의 제약과 Kubernetes 기능의 미지원은 구별해야 한다

### VOC에서 확인된 사실 — ConfigMap·Secret

VOC `2026042113280492909`에서 ConfigMap의 `binaryData`, XML 안의 `${}` 문자열, Secret의 특수문자 입력이 Console UI 검증에 막히는 문제가 제기됐다.

운영팀은 Console Web UI의 유효성 검증 제약이 있는 경우 DKSctl 환경에서 YAML을 작성하고 `kubectl apply -f`로 생성하면 정상 등록할 수 있다고 답변했다.

### VOC에서 확인된 사실 — ExternalName Service

VOC `2026042013113883288`에서는 `ExternalName` Service를 만들 때 Console UI가 Label Selector를 필수 입력으로 요구해 생성할 수 없었다.

운영팀은 DKSctl에서 YAML 선언 방식으로 ExternalName Service를 생성하도록 안내했다.

### 여기서 읽을 수 있는 관리 접점

같은 Kubernetes Resource라도 관리 접점은 여러 개일 수 있다.

~~~text
사용자 요구
  ↓
DKS Console Form
  ├─ 지원하는 입력 → UI로 생성
  └─ UI Validation·Form 제약
             ↓
         DKSctl / kubectl / YAML
             ↓
         Kubernetes API Resource 생성
~~~

따라서 “Console 화면에서 만들 수 없다”는 관측은 다음 중 어느 의미인지 구분해야 한다.

1. Console Form이 해당 필드나 Resource Type을 표현하지 못한다.
2. 사용자의 RBAC 권한이 부족하다.
3. Admission Policy가 거부한다.
4. Kubernetes API가 해당 Resource를 지원하지 않는다.
5. 플랫폼 운영정책상 금지된 기능이다.

4월 두 사례는 첫 번째에 해당했고, CLI·YAML이라는 다른 관리 접점으로 해결됐다.

### 이 인사이트가 말하지 않는 것

- Console에서 막힌 모든 입력을 CLI로 우회해도 된다는 뜻은 아니다.
- RBAC·Admission·보안정책을 DKSctl이 우회한다는 뜻도 아니다.
- CLI에서 생성 명령이 성공하면 해당 구성이 운영상 지원된다는 뜻은 아니다.
- 현재 Console에도 같은 UI 제약이 남아 있다는 뜻은 아니다.

## 2.3 인증서 발급과 Kubernetes TLS 적용은 다른 책임 단계다

### VOC에서 확인된 사실

VOC `2026042116145395245`에서 사용자는 Ingress HTTPS를 위한 SSL 인증서를 DKS가 제공하는지 문의했다.

운영팀은 DKS 자체 인증서는 제공하지 않으며 DS IAM에서 발급받아야 한다고 답변했다. 발급받은 뒤 DKS Console의 Secret에서 `TLS information` Type으로 `tls.crt`와 `tls.key`를 입력하거나 DKSctl을 통해 등록할 수 있다고 안내했다.

VOC `2026043015572249189`에서도 Fake 인증서가 보이는 상황에서 같은 흐름이 다시 확인됐다. 인증서는 DS IAM에서 발급받고, 발급 후 DKS Console 또는 DKSctl을 통해 TLS Secret으로 적용하도록 안내했다.

### 여기서 읽을 수 있는 인증서 수명주기

“Ingress HTTPS 설정”이라는 한 작업 안에는 서로 다른 책임이 있다.

~~~text
1. 인증서 발급
   - Domain·조직 검증
   - Certificate / Private Key 획득
   - 담당: 인증서 발급 체계

2. Kubernetes Secret 등록
   - tls.crt / tls.key 저장
   - 담당: Workload·Namespace 운영자

3. Ingress 연결
   - tls.hosts / secretName 연결
   - 담당: Routing Resource 관리

4. 실제 검증
   - 제공 Certificate·SAN·만료일·Chain 확인
~~~

따라서 Fake Certificate가 보인다는 사실만으로 “인증서가 발급되지 않았다”고 결론낼 수 없다. Secret이 없거나, Secret 내용이 잘못됐거나, Ingress가 다른 Secret을 참조하거나, Host가 맞지 않는 경우도 구분해야 한다.

또 VOC `2026043014263448079`에서는 신규 Repository의 Issuing CA가 Cluster에 사전 신뢰 등록돼 있어 별도 CA 추가 없이 Image Path와 Pull Secret만 바꾸도록 안내됐다. 이것은 **Server Certificate 발급·Ingress TLS 적용과 Node/Runtime Trust Store 문제도 서로 다른 층**임을 보여준다.

### 이 인사이트가 말하지 않는 것

- 현재도 DKS가 어떤 인증서도 발급하지 않는다는 일반 정책을 확정하는 것은 아니다.
- TLS Secret만 생성하면 Ingress HTTPS가 자동 완성된다는 뜻은 아니다.
- Repository CA가 모든 Cluster에 현재도 사전 등록돼 있다는 뜻은 아니다.
- `tls.crt`와 `tls.key`의 유효성·쌍 일치·SAN 검증이 불필요하다는 뜻도 아니다.

## 2.4 DKS 관리 Volume과 외부 VM 파일공유 경로는 분리해야 한다

### VOC에서 확인된 사실

VOC `2026040908233608510`에서 사용자는 Pod와 DS Cloud VM 사이에 파일을 공유하기 위해 DKS에서 생성한 PVC를 VM이 직접 Mount할 수 있는지 문의했다.

운영팀은 PVC 직접 공유는 불가하다고 답변하고, VM에 NFS Server를 구축한 뒤 Pod에서 NFS Volume으로 Mount하는 방안을 제시했다.

VOC `2026042810465626401`에서는 DKS Pod에 연결된 NetApp PV를 로그 분석용 외부 개발 VM에 직접 Mount하려 했다. 운영팀은 DKS StorageClass로 Provisioning된 NAS가 ACL·보안정책상 DKS 관리 Worker VM에서만 Mount 가능하므로 사용자 VM의 직접 Mount는 불가하다고 설명했다. 대안으로 사용자 VM에 NFS Server를 구성하고 Pod가 이를 Mount한 뒤 `rsync`로 동기화하는 방식을 권장했다.

### 여기서 읽을 수 있는 스토리지 경계

Kubernetes PVC가 NAS 기반이라는 사실과, 그 NAS Export를 임의의 외부 VM에서도 직접 Mount할 수 있다는 결론은 같지 않다.

~~~text
DKS StorageClass
        ↓
DKS가 관리하는 PVC / PV
        ↓
DKS Worker·Pod를 위한 ACL·관리 경계

외부 사용자 VM
        ↓
직접 같은 PV Mount 불가
        ↓
별도 NFS 공유 또는 동기화 경로 설계
~~~

파일을 공유해야 한다면 “동일 Volume을 양쪽에서 Mount”하는 방식만 고집하지 않고 다음을 구분해야 한다.

- 실시간 공동 Read/Write가 필요한가?
- 단방향 로그 Export나 Batch 동기화면 충분한가?
- 외부 VM이 Server가 되고 Pod가 NFS Client가 되는 구조가 가능한가?
- `rsync`, Object Storage, API 전송 같은 다른 경로가 더 적합한가?
- 권한·UID/GID·ACL·방화벽을 누가 관리하는가?

### 이 인사이트가 말하지 않는 것

- Kubernetes의 모든 PVC를 외부 시스템과 공유할 수 없다는 뜻은 아니다.
- 별도 NFS Server가 항상 최선의 아키텍처라는 뜻도 아니다.
- DKS-C의 모든 StorageClass가 동일한 ACL 정책을 가진다는 뜻은 아니다.
- `rsync`가 실시간 동기화·동시 쓰기 일관성을 보장한다는 뜻은 아니다.

### 관련 문서

- [[CCL-STO-002 - 외부 VM과의 파일 공유는 별도 NFS 또는 동기화 경로를 사용한다]]

# 3. 관찰 포인트

## 3.1 Git 선언 원본과 Live Resource는 양방향 동기화되지 않았다

VOC `2026042119491296949`에서 사용자는 DKS Console에서 Ingress를 수정한 뒤 재배포하면 설정이 초기화되는 이유와 Console 변경이 Git Config Repository로 동기화되는지 문의했다.

운영팀은 P-DEP 사용 시 Git Repository의 선언적 형상이 DKS Cluster로 **단방향 배포·덮어쓰기**되며, Console 수동 수정은 배포 때 Reset된다고 답변했다. 지속할 변경은 Config Repository에서 수행하도록 안내했다.

이 사례의 학습 포인트는 다음과 같다.

~~~text
Git Config Repo
      ↓ 단방향 적용
Cluster Live Resource

Live 수정
      └─ Git으로 역동기화되지 않음
      └─ 다음 배포 때 원본 정의로 복원될 수 있음
~~~

다만 모든 DKS 배포가 P-DEP GitOps 방식이라는 뜻은 아니다. 현재 Workload를 누가 관리하는지 먼저 확인해야 한다.

---

## 3.2 Harbor Project는 당시 Namespace와 결합된 번들로 제공됐다

VOC `2026042211051800439`에서 별도 Harbor Project 생성을 요청했지만, 운영팀은 해당 Namespace에 대응하는 이름의 Project가 이미 생성돼 있으며 ImagePullSecret을 만들어 사용하도록 안내했다.

VOC `2026042814164028971`에서는 여러 Namespace가 공용으로 쓸 Harbor Project를 요청했으나, 운영팀은 당시 DKS Harbor Project가 Namespace에 번들로 제공되며 별도 공용 Project 생성과 Quota 확장을 지원하지 않는다고 답변했다.

이 사례는 “DKS Project”, “Namespace”, “Harbor Project”가 이름은 비슷해도 임의로 자유 조합되는 독립 Object가 아니었음을 보여준다. 그러나 이는 당시 공용형 정책이며 현재 DKS-C Registry 운영 방식으로 일반화하지 않는다.

# 4. 4월 VOC만으로 확정하면 안 되는 것

1. **현재 사용자 동기화 절차**
   - One Cloud 승인, 최초 Login, 인사정보 동기화의 현재 구현과 지연시간은 최신 자료를 확인해야 한다.

2. **Console과 CLI의 모든 기능 차이**
   - 두 사례는 UI 제약이었지만 다른 기능은 RBAC나 Policy로 실제 금지될 수 있다.

3. **현재 인증서 발급·Trust 정책**
   - 발급 주체, CA Trust, 자동화 방식은 Service Model과 시점에 따라 달라질 수 있다.

4. **모든 StorageClass의 외부 Mount 정책**
   - 확인된 사례는 당시 DKS 관리 NetApp/NAS 및 PVC 경계다.

5. **Harbor Project와 Namespace의 현재 결합 관계**
   - 당시 번들 정책과 현재 DKS-C 전용 Registry 정책을 분리해야 한다.

6. **모든 배포의 Git 단방향 관리**
   - P-DEP·Git 관리 대상 Field에 해당하는지 먼저 확인해야 한다.

# 5. 4월을 읽고 남겨야 할 판단 습관

~~~text
"Project에 추가했는데 왜 DKS에서 안 보이지?"
→ Project 승인·동기화·최초 Login·Namespace Membership을 단계별로 본다.

"Console에서 생성이 안 된다."
→ UI Form 제약인지, RBAC인지, Admission인지, API 미지원인지 구분한다.

"HTTPS 인증서를 DKS에서 만들어 주나?"
→ 발급 → Secret 등록 → Ingress 참조 → 실제 검증 책임을 분리한다.

"PVC가 NAS니까 VM에서도 Mount하면 되나?"
→ Storage Backend 이름보다 ACL·관리 경계와 지원 경로를 확인한다.

"콘솔에서 수정했는데 다시 돌아왔다."
→ 다음 배포의 Source of Truth와 Field 관리 주체를 확인한다.
~~~
