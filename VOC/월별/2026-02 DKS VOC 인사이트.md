- DKS-N·공용형 환경의 제약을 현재 DKS-C 전용 클러스터에 그대로 옮기지 않는다.

# 1. 이번 달 한눈에

2월 VOC에서 확인되는 핵심 학습 포인트는 다음 네 가지다.

1. **HTTP Ingress와 임의 TCP 노출은 서로 다른 제공 경로이며, 당시 NodePort는 임시·비권장 경로로 안내됐다.**
2. **자원 증·감설은 요청값 자체보다 실제 사용량과 단계적 검증을 중심으로 판단됐다.**
3. **Image Pull 실패는 인증·경로·Tag·네트워크를 한 덩어리로 보지 않고 단계별로 분리해야 한다.**
4. **공용 클러스터에서는 Namespace가 달라도 Node 로컬 자원과 공통 관측 계층을 통해 영향이 전달될 수 있다.**

추가로 ServiceAccount Token, Ingress Annotation 사례는 **플랫폼 오류처럼 보이는 현상도 Kubernetes 버전이나 Resource 설정 의미부터 확인해야 한다**는 관찰 포인트를 제공한다.

# 2. 확인된 인사이트

## 2.1 HTTP Ingress와 TCP NodePort는 같은 외부 노출 방식이 아니다

### VOC에서 확인된 사실

VOC `2026020613441335043`에서 사용자는 DKS의 Ingress가 HTTP 80·443만 의미하는지, NGINX TCP Proxy처럼 다른 Port도 노출할 수 있는지 문의했다.

운영팀은 당시 HTTP/HTTPS Ingress는 80·443만 지원한다고 답변했다. TCP는 NodePort 사용 자체가 불가능한 것은 아니지만 임시 공개 방식이며 권장하기 어렵다고 설명했다. 특히 다른 사용자에게 Node IP와 Port를 공개해야 하는 구성은 주의가 필요하다고 덧붙였다.

VOC `2026021016230057995`와 `2026021014531656645`에서도 같은 경계가 반복됐다. HTTP Ingress는 80·443으로 안내됐고, FTP 등 TCP 통신은 Worker Node의 NodePort를 사용하는 방식이 제시됐다. 다만 Worker Node는 가변적 자원이라 IP가 바뀔 수 있고, 이에 따른 HA 구성 실패는 사용자 책임이라는 경고가 함께 붙었다.

### 여기서 읽을 수 있는 DKS 구조

외부에서 Pod에 접근한다는 목적이 같아도 Protocol과 진입 경로는 같지 않다.

~~~text
HTTP / HTTPS 서비스
        ↓
Ingress 경로
        ↓
당시 지원 Port: 80 / 443

기타 TCP 서비스
        ↓
임시 NodePort 경로
        ↓
Worker Node IP·Port 직접 의존
        ↓
Node 교체·IP 변경 시 연결·HA 위험
~~~

따라서 외부 노출을 검토할 때는 먼저 다음을 구분해야 한다.

- HTTP 계열인가, 일반 TCP인가?
- 안정된 서비스 진입점이 필요한가, 특정 Node 주소에 의존해도 되는가?
- Node 교체나 IP 변화가 발생해도 외부 연결 구성이 유지되는가?
- 해당 방식의 HA와 변경 관리를 누가 책임지는가?

2월 사례에서 NodePort는 단순히 “기술적으로 열 수 있다”는 가능성과 “운영 서비스 진입점으로 권장된다”는 판단이 다르다는 점을 보여준다.

### 이 인사이트가 말하지 않는 것

- 현재 DKS-C에서도 HTTP가 80·443으로만 제한된다는 뜻은 아니다.
- 모든 TCP 서비스는 NodePort를 사용해야 한다는 뜻이 아니다.
- Kubernetes NodePort 자체가 항상 비가용적이라는 뜻도 아니다.
- 당시 공용형 환경에서 임시 제공된 NodePort 운영 조건을 다른 서비스 모델에 그대로 적용할 수 없다.

## 2.2 자원 변경은 피크 한 번이 아니라 사용 근거와 단계적 검증으로 판단한다

### VOC에서 확인된 사실

VOC `2026020513120725900`에서 사용자는 기존 1 Core 수준의 CPU 할당에서 16 Core로 증설을 요청했다. 운영 답변은 하루 약 4회 80% 이상 사용한 관측을 언급하면서도 한 번에 요청치 전체를 승인하지 않고, 먼저 4 vCore로 점진적으로 늘리는 방식을 안내했다.

VOC `2026020411404115875`에서는 저활용 Namespace의 감설을 위해 CPU·Memory Max 사용량을 요청했다. 운영팀은 우선 Console의 최근 30일 사용량을 안내했고, 그래프에서 확인이 어려운 간헐적 개발 Workload에 대해서는 별도 조회한 최대 사용량을 제공했다.

같은 달 후반의 VOC `2026022311243204451`도 저활용 회수 대응을 위해 AVG와 MAX 사용량을 구분해 다시 확인한 사례로 분류됐다.

### 여기서 읽을 수 있는 DKS 운영 판단

자원 증설과 감설은 서로 반대 방향이지만 공통적으로 **현재 할당량과 실제 사용 특성을 연결하는 근거**가 필요하다.

~~~text
증설
실제 Peak·빈도·동시성 확인
        ↓
필요량 가설
        ↓
단계적 증설
        ↓
변경 후 재관측

감설
AVG만 보지 않음
        ↓
MAX·간헐적 실행·업무 주기 확인
        ↓
여유량 판단
        ↓
감설 후 위험 검토
~~~

특히 간헐적으로만 실행되는 개발·배치 Workload는 평균값이나 화면의 제한된 그래프만 보면 실제 Peak가 가려질 수 있다. 반대로 한 번의 Peak만으로 큰 폭의 증설 필요량 전체가 입증되는 것도 아니다.

따라서 자원 판단에서는 다음 질문이 중요하다.

- Peak는 얼마나 자주 발생하는가?
- 평균과 최대 중 어떤 값이 현재 판단 목적에 필요한가?
- Replica 수와 동시 처리 요구는 무엇인가?
- 먼저 작은 변경을 적용하고 다시 관측할 수 있는가?

### 이 인사이트가 말하지 않는 것

- 모든 증설은 반드시 4 vCore 단위로 해야 한다는 뜻은 아니다.
- Max 사용량 하나만으로 적정 할당량을 계산할 수 있다는 뜻도 아니다.
- 당시 승인 절차와 산출 양식이 현재도 동일하다는 뜻은 아니다.
- 사용량이 낮다는 사실만으로 즉시 감설해도 안전하다는 뜻은 아니다.

## 2.3 Image Pull 실패는 인증·경로·Artifact·네트워크를 분리해서 확인한다

### VOC에서 확인된 사실

VOC `2026020210355795480`에서는 Deployment 생성 문제를 조사하면서 운영팀이 다음 항목을 각각 확인하도록 안내했다.

- Image Pull Secret의 `.dockerconfigjson`에 저장된 ID·Password 또는 Token이 유효한가
- Registry 주소만이 아니라 전체 Image 경로까지 Manifest에 작성했는가
- CAE망에서 사용하는 Registry 주소와 방화벽 경로가 맞는가
- 실제 사용자 Pod가 배치되는 Worker 경로에서 목적지 통신이 가능한가

운영팀은 DKSctl도 Pod이지만 사용자 Workload와 다른 Node에 배치되므로, DKSctl에서 성공한 통신 결과가 사용자 Pod의 통신 성공을 보장하지 않는다고 설명했다. 실제 사용자 Pod에서 테스트해야 한다는 안내가 뒤따랐다.

VOC `2026021109410962159`에서는 `Failed to pull image` 오류에 대해 복잡한 조치보다 먼저 Registry에 해당 Image와 Tag가 실제로 존재하는지 확인하도록 답변했다.

### 여기서 읽을 수 있는 진단 구조

Image Pull 실패는 하나의 증상이지만 실패 지점은 여러 층으로 나뉜다.

~~~text
1. Artifact 존재
   - Repository / Image / Tag가 실제로 있는가?

2. Image 참조
   - Registry 주소와 전체 경로가 정확한가?

3. 인증
   - Pull Secret의 ID·Password·Token이 유효한가?
   - Workload가 그 Secret을 실제 참조하는가?

4. 네트워크
   - 사용자 Pod가 배치된 Worker 경로에서 Registry에 도달하는가?
   - 방화벽과 망별 Registry 주소가 맞는가?

5. Runtime
   - 위 조건이 맞은 뒤에도 kubelet·container runtime 문제가 남는가?
~~~

이 순서의 장점은 첫 단계에서 틀렸는데 Secret을 반복 재생성하거나, 인증 오류인데 Runtime을 재시작하는 식의 불필요한 조치를 줄인다는 데 있다.

### 이 인사이트가 말하지 않는 것

- 모든 Image Pull 장애를 같은 순서로만 조사해야 한다는 뜻은 아니다. 실제 Event 메시지가 우선이다.
- DKSctl이 항상 사용자 Pod와 다른 Network 경로를 쓴다고 모든 환경에 일반화하는 것은 아니다. 2월 원문의 당시 구성 설명이다.
- 특정 Registry 목록과 URL이 현재도 그대로 유효하다는 뜻은 아니다.
- Runtime 재시작이 일반적인 첫 조치라는 뜻도 아니다.

## 2.4 Namespace 격리가 Node·관측 계층의 완전한 영향 격리를 뜻하지 않는다

### VOC에서 확인된 사실 — Node 로컬 디스크

VOC `2026020408343213030`에서 한 Namespace의 Pod가 `DiskPressure`로 Evict됐다. 후속 확인 결과 운영팀은 장애 원인이 문의자의 Namespace가 아니라 다른 Namespace의 Pod가 Node의 ephemeral-storage를 소진한 데 있다고 설명했다.

운영 답변에 따르면 해당 Node를 함께 사용하던 여러 사용자의 Pod가 Evict됐고, ephemeral-storage는 Node Disk를 공유하므로 같은 Node의 모든 Pod가 영향을 주고받을 수 있었다.

VOC `2026020409585514266`도 같은 시간대의 Pod 비정상 종료와 삭제 지연을 Node DiskPressure·Eviction 및 장애 조치 중 kubelet 동기화 문제와 연결했다.

### VOC에서 확인된 사실 — Prometheus TSDB

VOC `2026021217281176273`에서는 한 Namespace가 서로 다른 이름의 Pod를 빠르게 생성·삭제하면서 Prometheus가 매번 새로운 시계열을 저장했고, TSDB 관련 메트릭과 메모리 사용량이 증가한 것으로 분석됐다.

VOC `2026022411561713187`에서는 같은 패턴이 계속되어 Prometheus OOM이 발생했고, 임시 메모리 증설 후 짧은 주기의 Task를 상시 Pod 구조로 바꾸는 방안이 논의됐다.

### 여기서 읽을 수 있는 DKS 구조

Namespace는 Kubernetes Resource와 권한·Quota의 중요한 경계지만, 같은 Cluster의 모든 공유 계층을 물리적으로 분리하지는 않는다.

~~~text
Namespace A의 Workload 동작
        ↓
공유 Node Disk 또는 공통 Monitoring 대상 증가
        ↓
Node DiskPressure / Prometheus Series 증가
        ↓
다른 Namespace의 Pod 또는 Monitoring Workload 영향
~~~

따라서 공용 Cluster에서 영향 범위를 판단할 때는 Namespace 내부만 보지 않고 다음을 함께 확인해야 한다.

- 같은 Node를 공유하는가?
- Node 로컬 디스크·Image 저장소·Log 공간을 함께 쓰는가?
- Cluster 단위로 수집하는 Prometheus가 Pod churn을 모두 관측하는가?
- 한 Workload의 생성·삭제 패턴이 공통 Controller·Network·관측 계층에 추가 작업을 만드는가?

### 이 인사이트가 말하지 않는 것

- Namespace 격리가 무의미하다는 뜻은 아니다.
- 모든 Pod churn이 Prometheus OOM을 일으킨다는 뜻은 아니다.
- 2월 사건의 정확한 Cardinality 증가량과 메모리 인과관계가 모든 세부 단계까지 계측됐다는 뜻은 아니다. 운영 답변은 원인으로 “보인다”고 표현했다.
- 현재 DKS-C 전용 클러스터에도 동일한 이웃 Namespace 영향이 존재한다는 뜻은 아니다.

# 3. 관찰 포인트

## 3.1 ServiceAccount Secret이 보이지 않는 현상은 Kubernetes 버전 동작일 수 있다

VOC `2026022611160529134`에서 ServiceAccount 생성 후 Key가 보이지 않는 현상에 대해 운영팀은 Kubernetes 1.24 이상부터 Secret이 자동 생성되지 않는다고 설명하고 별도의 ServiceAccount Token 생성 가이드를 안내했다.

이 사례의 학습 포인트는 UI나 DKS 장애를 의심하기 전에 **대상 Kubernetes 버전에서 기본 동작이 바뀌었는지** 확인하는 것이다.

다만 이 한 건만으로 다음을 확정해서는 안 된다.

- 모든 Cluster가 동일한 Kubernetes 버전이라는 결론
- 모든 자동화에 장기 Secret Token을 사용해야 한다는 결론
- 현재 DKS-C의 권장 Token 방식

사람의 CLI, Workload ServiceAccount, 외부 CI/CD, OIDC Token은 목적이 다르므로 후속 문서에서 분리해 확인해야 한다.

---

## 3.2 Ingress Annotation은 Controller 설정을 Workload별로 조정하는 접점이었다

2월에는 `413 Content Too Large`와 Body Size 제한 해제 문의가 반복됐다. 운영팀은 당시 DKS가 NGINX Ingress Controller를 사용하며 `nginx.ingress.kubernetes.io/proxy-body-size` Annotation으로 값을 조정할 수 있다고 답변했다.

이 사례는 애플리케이션이 200을 기록했는데 Client가 413을 받는 경우처럼, 요청 경로의 중간 계층인 Ingress에서 응답이 달라질 수 있음을 보여준다.

그러나 특정 Annotation의 지원 여부와 허용값은 Controller 버전·정책에 따라 달라질 수 있으므로 현재 환경에서 다시 확인해야 한다.

# 4. 2월 VOC만으로 확정하면 안 되는 것

1. **2월 전체 문의 분포**
   - `2026-02-15 ~ 2026-02-21` 파일이 없으므로 41건을 2월 전체 모집단으로 취급하지 않는다.

2. **현재 DKS-C의 외부 노출 정책**
   - Ingress 80·443 및 임시 NodePort 답변은 당시 공용형 환경의 운영 답변이다.

3. **자원 산정 공식**
   - 4 vCore 점진 증설은 한 사례의 결정이며 일반 증설 단위가 아니다.

4. **공유 장애의 단일 원인**
   - ephemeral-storage와 Pod churn은 관측된 두 영향 경로다. 모든 공용 Cluster 장애를 이 둘로 설명할 수 없다.

5. **Image Pull 오류의 단일 해결책**
   - Tag 누락, Credential, 경로, 방화벽, Runtime은 서로 다른 실패 지점이다.

6. **현재 ServiceAccount Token 정책**
   - Kubernetes 버전 동작과 플랫폼의 권장 인증 방식을 분리해야 한다.

# 5. 2월을 읽고 남겨야 할 판단 습관

~~~text
"외부에 Port를 열 수 있나?"
→ Protocol과 진입 경로를 먼저 구분한다.
→ 기술적으로 가능함과 운영상 권장됨을 구분한다.

"자원을 얼마나 늘리거나 줄일까?"
→ 평균·최대·빈도·동시성을 분리한다.
→ 큰 변경 전에 단계적 변경과 재관측 가능성을 본다.

"Image Pull이 실패했다."
→ Artifact 존재 → 전체 경로 → 인증 → 실제 Pod Network → Runtime 순으로 실패 층을 좁힌다.

"내 Namespace에는 문제가 없는데 왜 영향받았지?"
→ Node 로컬 자원과 Cluster 공통 관측 계층을 확인한다.

"Secret이 자동으로 안 생긴다."
→ 플랫폼 장애를 결론내리기 전에 Kubernetes 버전의 기본 동작을 확인한다.
~~~
