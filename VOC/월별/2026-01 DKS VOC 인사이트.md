# 2026-01 DKS VOC 인사이트

> [!important] 이 문서의 역할
> 이 문서는 2026년 1월 VOC를 다시 나열하는 문서가 아니라, 당시 실제 문의와 운영 답변에서 **DKS를 이해하는 데 도움이 되는 구조·경계·운영 특성**을 뽑아 정리한 학습용 문서다.
>
> 1월 VOC가 보여주는 당시 환경과 현재 DKS-C를 같은 것으로 간주하지 않는다. 특정 IP·용량·정책값과 단일 장애 사례는 그 시점의 관측으로만 취급하며, 현재 운영 절차의 확정 근거가 필요하면 최신 공식 자료를 다시 확인한다.

## 0. 먼저 알아야 할 1월의 시점 배경

1월 원문에는 당시 제공 중인 DKS가 **Namespace 방식 중심**이었고, 문의자가 말한 IaaS 방식 서비스는 아직 제공하지 않으며 향후 오픈을 목표로 준비 중이라는 운영 답변이 남아 있다.

따라서 이 달의 VOC는 현재 DKS-C의 모든 동작을 설명하는 자료라기보다, **공용·Namespace형 DKS에서 어떤 경계가 실제 사용자 문의로 드러났는지**를 이해하는 자료로 보는 것이 적절하다.

이 시점 배경은 뒤의 여러 VOC를 해석하는 데 중요하다. 예를 들어 Cluster Scope 권한 제한, 공용 Node 자원 영향, Ingress·LB 주소 구분은 당시의 공용형 서비스 모델과 함께 읽어야 한다.

---

# 1. 이번 달 한눈에

1월 VOC에서 비교적 강하게 확인되는 학습 포인트는 다음 네 가지다.

1. **외부 연동에 사용하는 주소와 클러스터 내부에서 보이는 Ingress IP는 같은 것이 아니다.**
2. **공용형 DKS의 사용자 권한 경계는 Namespace Scope였고, Cluster Scope CRD·Operator 요구는 그 경계를 넘는다.**
3. **P-DEP이 관리하는 필드를 Live Resource에서 직접 바꾸면 재배포 때 다시 치환될 수 있다.**
4. **Private Registry 인증 정보가 바뀌면 기존 Pull Secret도 함께 점검해야 한다.**

추가로, 1월 말의 ephemeral-storage 사례는 **공용 Node의 로컬 자원이 워크로드 간 영향 경로가 될 수 있다는 관찰 포인트**를 제공한다. 다만 단일 사례이므로 일반 규칙으로 확정하지 않는다.

# 2. 확인된 인사이트

## 2.1 외부 연동 주소와 내부 Ingress IP를 구분해야 한다

### VOC에서 확인된 사실

VOC 2026011610005492048에서 사용자는 화면에서 확인한 LB/IP를 외부 시스템과의 방화벽 신청에 사용할 수 있는지 문의했다.

운영 답변은 해당 IP를 **내부에서 인식하는 Ingress IP**로 설명하고, 외부에서는 **Cluster의 LB VIP**로 방화벽을 열어야 한다고 안내했다. 또한 Cluster Domain 또는 Ingress 생성 시 만들어지는 hostname을 nslookup하여 클러스터별 VIP를 확인하는 방법을 제시했다.

같은 달에는 DNS 등록 또는 외부 연결을 위해 Cluster VIP를 확인하는 문의가 반복되었다. VOC 2026012611473446983에서도 Ingress hostname 또는 클러스터별 Domain을 조회하여 VIP를 확인하도록 안내했다.

### 여기서 읽을 수 있는 DKS 구조

1월 사례가 보여주는 핵심은 **"클러스터에서 보이는 IP"라는 이름만으로 외부 연동 주소를 결정하면 안 된다는 것**이다.

~~~text
클러스터 내부에서 보이는 Ingress IP
        ≠
외부 시스템이 접근할 때 사용하는 Cluster LB VIP
~~~

따라서 주소를 선택할 때는 최소한 다음 질문을 먼저 분리해서 보는 습관이 필요하다.

- 주소를 어디에 등록하려는가?
- 클러스터 내부 통신인가, 외부에서 들어오는 통신인가?
- DNS 등록·방화벽 신청처럼 외부 진입점을 정하는 작업인가?

1월 인바운드 사례에서는 이 질문의 답에 따라 내부 Ingress IP가 아니라 외부 Cluster LB VIP가 선택되었다.

### 이 인사이트가 말하지 않는 것

- 모든 DKS 서비스 모델에서 동일한 주소 체계를 사용한다는 뜻은 아니다.
- DKS-C의 현재 Egress·Gateway·Load Balancer 구조까지 1월 사례만으로 확정할 수 없다.
- 당시 문서에 등장한 개별 IP 값을 다른 클러스터에 재사용할 수 있다는 뜻이 아니다.
- 아웃바운드 방화벽 Source 주소까지 Cluster LB VIP를 사용한다는 뜻이 아니다.

### 관련 문서

- [[CCL-NET-001 - DKS-N 내부 Ingress IP는 외부 등록 주소가 아니다]]
- [[CCL-NET-002 - DKS-N DNS 등록 VIP는 대표 도메인 조회로 확인한다]]
- [[CCL-NET-G001 - 주소 선택 전 네트워크 조건을 식별한다]]

## 2.2 공용형 DKS에서는 Namespace Scope와 Cluster Scope를 분리해서 봐야 한다

### VOC에서 확인된 사실

VOC 2026011717453599328에서는 CloudNativePG Operator를 사용하기 위해 CRD 등록이 가능한지 문의했다. 운영 답변은 사용자가 **Namespace Scope 내 권한만 제공받고 있으며 Cluster 권한과 Operator 사용은 지원하기 어렵다**고 설명했다.

VOC 2026012311122738890에서도 Kong Gateway 구성에 필요한 CRD 생성 권한을 요청했지만, 운영팀은 공용 클러스터의 안정성과 보안을 이유로 Namespace Scope 권한만 제공하며 Cluster Scope와 CRD 생성을 지원하기 어렵다고 다시 답변했다.

서로 다른 두 문의가 같은 권한 경계를 보여준다.

### 여기서 읽을 수 있는 DKS 구조

공용형 DKS에서 "내 Namespace 안에서만 쓸 예정"이라는 사용 목적과, 실제 Kubernetes Resource가 요구하는 Scope는 별개의 문제다.

예를 들어 어떤 Operator의 Custom Resource를 Namespace 안에서 생성하더라도, 그 Operator 설치 과정에서 **CustomResourceDefinition 자체를 클러스터에 등록해야 한다면 Cluster Scope 작업이 포함될 수 있다.**

따라서 공용형 서비스에서 새로운 도구나 Operator를 도입할 때는 다음 순서로 보는 것이 유용하다.

~~~text
내 Namespace에서 사용할 것인가?
        ↓
그 도구가 Namespace-scoped Resource만 사용하는가?
        ↓
CRD / ClusterRole / Webhook 등 Cluster Scope Resource가 필요한가?
        ↓
현재 서비스 모델의 권한 경계 안에서 가능한가?
~~~

1월 VOC에서 확인된 DKS 정책은 이 마지막 단계에서 Cluster Scope 요구를 허용하지 않는 쪽이었다.

### 이 인사이트가 말하지 않는 것

- 모든 Helm Chart 설치가 불가능하다는 뜻은 아니다.
- 모든 Custom Resource가 Cluster Scope라는 뜻은 아니다.
- 현재 DKS-C 전용 클러스터에서도 같은 권한 제한이 적용된다는 뜻은 아니다.
- "Operator"라는 이름만으로 지원 여부를 결정할 수 있다는 뜻도 아니다. 실제 설치에 필요한 Resource Scope를 확인해야 한다.

### 관련 문서

- [[CCL-PLT-001 - DKS-N 공용 서비스는 사용자 Cluster Scope 권한을 제공하지 않는다]]
- [[CCL-PLT-002 - Cluster Scope Operator는 DKS-N 공용 서비스에 직접 설치할 수 없다]]

## 2.3 P-DEP으로 관리되는 설정은 Live Resource 수정만으로 지속되지 않을 수 있다

### VOC에서 확인된 사실

VOC 2026012612104247173에서 사용자는 Ingress의 /api 경로가 원하는 Backend Service를 바라보도록 수정했지만, Front Product를 재배포하면 Service 이름이 다시 Front Service로 변경되는 문제를 문의했다.

P-DEP 답변은 기본 배포 로직이 **해당 Product 기준으로 Ingress 내부 Service 이름을 치환**한다고 설명했다. 현재 구조에서 이를 강제로 다른 값으로 유지하려면 Custom CD를 사용해야 하며, 그 경우 CI 이후 CD를 수동으로 진행하는 등의 별도 제약이 있다고 안내했다.

### 여기서 읽을 수 있는 DKS 구조

이 사례는 Kubernetes Resource의 현재 화면에 보이는 값과, 다음 배포 때 다시 적용되는 **선언 원본 또는 배포 시스템의 관리값**을 구분해야 한다는 점을 보여준다.

~~~text
Live Ingress 직접 수정
        ↓
현재 상태는 바뀔 수 있음
        ↓
P-DEP 재배포
        ↓
P-DEP 기본 로직이 관리 필드를 다시 계산·치환
        ↓
직접 수정값이 유지되지 않을 수 있음
~~~

따라서 반복 배포가 있는 환경에서는 "지금 Resource가 원하는 값인가?"뿐 아니라 **"다음 배포 시 그 값을 누가 다시 쓰는가?"**를 같이 확인해야 한다.

### 이 인사이트가 말하지 않는 것

- P-DEP이 모든 Kubernetes 필드를 항상 덮어쓴다는 뜻은 아니다.
- 모든 Live 수정이 금지되어 있다는 뜻도 아니다.
- 1월 당시 안내된 Custom CD의 기능·제약이 현재도 그대로라는 뜻은 아니다.
- 이 사례에서 확인된 것은 Product 기준으로 관리되는 Ingress Service 이름 치환이며, 다른 필드의 소유권은 별도로 확인해야 한다.

### 관련 문서

- [[CCL-DEP-001 - P-DEP 관리 필드의 콘솔 직접 수정은 재배포 시 덮어써질 수 있다]]
- [[CCL-DEP-002 - P-DEP 지속 설정은 Git 또는 CD 정의에 반영한다]]

## 2.4 Registry Credential과 Pull Secret은 함께 수명주기를 가진다

### VOC에서 확인된 사실

VOC 2026010508063503895에서는 기존에 정상 동작하던 Harbor Image Pull이 갑자기 실패했다.

운영팀은 **AD 패스워드 변경에 따른 인증 문제로 보인다**고 판단하고, Image Pull에 사용하던 Secret을 수정하거나 삭제 후 재생성하여 확인하도록 안내했다.

### 여기서 읽을 수 있는 DKS 구조

Private Registry에서 Image를 Pull하려면 Registry 인증에 사용할 Credential이 필요하고, Kubernetes에서는 그 Credential을 Secret 형태로 참조할 수 있다.

따라서 Registry 인증에 사용한 원본 Credential이 변경되면 기존 Secret 안의 인증 정보와 실제 Registry Credential이 서로 달라질 수 있다.

~~~text
Registry Credential 변경
        ↓
기존 Pull Secret의 인증 정보가 오래된 값이 될 수 있음
        ↓
Image Pull 인증 실패 가능
        ↓
Secret 갱신 또는 재생성 후 확인
~~~

이 사례에서 배울 포인트는 Image Pull 장애를 단순 네트워크 문제로만 보지 않고 **Registry Credential과 Secret의 수명주기**도 함께 확인해야 한다는 것이다.

### 이 인사이트가 말하지 않는 것

- 1월의 모든 Image Pull 실패 원인이 Credential이었다는 뜻은 아니다.
- AD 패스워드 변경이 모든 Registry 인증 방식에 영향을 준다는 뜻은 아니다.
- ImagePullBackOff가 발생하면 무조건 Secret을 재생성해야 한다는 뜻도 아니다. Image 이름·Tag·Registry 연결·Secret 참조 등 다른 원인도 별도로 확인해야 한다.
- 운영 답변의 표현은 "인증 문제로 보인다"였으므로, 이 VOC 하나만으로 최종 Root Cause가 완전히 입증됐다고 확대하지 않는다.

### 관련 문서

- [[CCL-IMG-002 - Registry Credential 변경 시 Pull Secret을 갱신해야 한다]]

# 3. 관찰 포인트

아래 내용은 학습 가치는 있지만, 1월 자료만으로 DKS의 일반 규칙으로 승격하기에는 근거가 부족하다.

## 3.1 공용 Node의 ephemeral-storage는 Namespace 바깥 영향 경로가 될 수 있다

VOC 2026013017520489751에서는 Pod가 축출된 사건에 대해 운영팀이 Node의 ephemeral-storage Threshold 초과를 설명했다. 운영팀은 해당 Pod의 emptyDir 사용을 축출 후보가 된 원인으로 추정했고, emptyDir이 공용 Node의 디스크 공간을 사용하므로 과도한 사용이 같은 Node의 다른 Pod에도 영향을 줄 수 있다고 안내했다.

이 사례는 Namespace의 CPU·Memory Quota만 보고 워크로드 격리를 전부 이해하면 부족하다는 점을 보여준다. 공용 Node에서 공유되는 로컬 디스크 같은 자원이 별도의 장애 전파 경로가 될 수 있기 때문이다.

다만 이 사건에서 emptyDir이 실제 공간 고갈의 주된 소비자였는지, 다른 Pod의 Log·Image Layer·Writable Layer가 얼마나 기여했는지는 원문만으로 확정되지 않는다. 따라서 다음 정도로만 기억하는 것이 안전하다.

> **Pod Eviction에서 ephemeral-storage 메시지가 보이면 개별 Pod 설정뿐 아니라 Node 전체의 로컬 저장공간 소비를 함께 확인한다.**

이 항목은 현재 candidate-source이며, 후속 월의 유사 사례와 함께 검증해야 한다.

---

## 3.2 같은 "장애"라도 문제 계층을 먼저 확인해야 한다

1월에는 다음처럼 겉보기 증상과 실제 조사 계층이 다른 사례가 함께 나타난다.

- NetworkPolicy 문의로 시작했지만 DNS 설정 문제가 원인으로 분류된 사례
- Pod Pending이 Storage Attach 문제와 연결된 사례
- Image Pull 실패가 Registry 인증 정보와 연결된 사례
- Pod 종료가 Node의 ephemeral-storage 상태와 연결된 사례

이 사례들을 하나의 Root Cause 규칙으로 합칠 수는 없다. 오히려 공통 학습 포인트는 반대다.

~~~text
증상 이름
  ↓
바로 원인 확정 X
  ↓
Network / DNS / Storage / Registry Auth / Node Resource 등
실제 실패 계층을 분리해서 확인
~~~

1월 VOC는 "문제가 Kubernetes에서 보였다"는 사실과 "원인이 Kubernetes 자체에 있다"는 결론이 같지 않다는 점을 여러 사례로 보여준다.

# 4. 1월 VOC만으로 확정하면 안 되는 것

1. **현재 DKS-C 정책**
   - 1월 원문은 Namespace형 공용 DKS가 중심이던 시점의 자료다. 당시 향후 제공 예정이던 IaaS형과 현재 DKS-C를 같은 정책으로 취급하지 않는다.

2. **특정 IP·Subnet·VIP 값**
   - 주소 종류를 구분하는 원리는 학습할 수 있지만, 개별 주소값은 당시 특정 클러스터의 값이다.

3. **모든 Operator의 지원 여부**
   - 1월에서 확인된 것은 공용형 DKS의 Cluster Scope 제한이다. 실제 Chart·Operator가 어떤 Cluster Scope Resource를 요구하는지는 각각 확인해야 한다.

4. **모든 P-DEP 필드의 소유권**
   - 확인된 사례는 Ingress의 Product 기준 Service 이름 치환이다. 다른 Field가 동일하게 관리되는지는 별도 근거가 필요하다.

5. **ephemeral-storage 사건의 단일 원인**
   - Node Threshold 초과와 Pod 축출은 확인됐지만, Node 공간을 어떤 요소가 얼마나 소비했는지는 추가 관측 없이 확정하지 않는다.

# 5. 1월을 읽고 남겨야 할 판단 습관

1월 VOC의 가장 유용한 부분은 개별 답변보다 다음의 구분 습관이다.

~~~text
"무슨 IP를 써야 하나?"
→ 내부 주소와 외부 진입 주소를 먼저 구분한다.

"내 Namespace에서 쓸 건데 설치해도 되나?"
→ 사용 범위보다 먼저 필요한 Kubernetes Resource Scope를 본다.

"콘솔에서 수정했는데 왜 다시 바뀌었지?"
→ 현재 Live 상태와 다음 배포의 선언 원본·관리 주체를 구분한다.

"이미지가 갑자기 안 받아진다."
→ Network뿐 아니라 Registry Credential과 Pull Secret도 확인한다.

"Pod가 죽었다."
→ Pod 자체 설정만 보지 말고 Node 공유 자원과 외부 의존 계층을 함께 본다.
~~~

이 다섯 가지는 1월 VOC를 단순 FAQ가 아니라 DKS 운영 구조를 이해하는 자료로 읽게 해주는 핵심 질문이다.
