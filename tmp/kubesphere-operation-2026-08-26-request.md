# Oracle Browser 요청 — 2026-08-26 Xi'an KubeSphere Operation 운영자 실습 문서 작성

## 요청 목적
Xi'an 현지 출장의 2026-08-26 오후 KubeSphere Operation 교육을 위해, 기존의 방대한 교육 문서를 그대로 반복하지 않는 **현장 실행용 운영자 실습 문서**를 새로 작성해 달라.

이 교육은 일반 사용자 교육이 아니라 **KubeSphere/DKS 운영자 교육**이다. 화면을 설명하는 데 그치지 않고, 운영자가 실제로 수행해야 하는 안전한 작업은 직접 Step-by-Step으로 실습해야 한다.

최종 산출물은 Obsidian의 `01. 활성 프로젝트/01. Xi'an 전환 운영 가이드/출장/20. 교육/` 아래에 새 Markdown 문서로 저장할 수 있는 수준의 완성본이어야 한다. 기존 `2026-08-26 KubeSphere Operation 기술 전수.md`를 대체하기보다는, 실제 오후 실습을 운영하기 위한 간결한 실행 문서/실습 운영안 성격으로 작성한다.

## 현장 조건
- 교육 시간: 2026-08-26 오후 13:00~17:00, 최대 4시간 블록.
- 교육생: 6명 기준.
- 교육생은 전날(8/25) Kubernetes/DKS 아키텍처 기초 교육을 이미 수강했다. 따라서 긴 복습은 필요 없다. 필요하면 시작 연결은 몇 분 수준으로만 둔다.
- 교육생별 AD 계정은 확보됐다.
- AD 실습에 필요한 추가 계정도 준비됐다.
- 각 교육생은 VM/Bastion 쪽에 접속할 수 있을 것으로 보고 있으며 `dspaas` 계정 접근도 가능한 전제다.
- 기존 Xi'an KubeSphere/Member 환경은 공유 운영환경이다. 교육을 위해 불필요하게 공용 관리 컴포넌트를 반복 변경하지 않는다.

## 사용자가 명확히 합의한 교육 원칙
1. **운영자 교육**이다. 사용자 교육처럼 안전을 이유로 실제 운영 작업을 과도하게 시연/설명만으로 빼지 않는다.
2. 진행은 한 번에 큰 시나리오를 던지는 방식이 아니라 **Step-by-Step 동시 실습**이다.
   - 강사가 해당 Step을 설명하고 보여준다.
   - 교육생 6명이 각자 같은 Step을 수행한다.
   - 전원 완료를 확인한다.
   - 다음 Step으로 넘어간다.
3. 신청서/가상 요청 사례는 어디까지나 설명용 예시다. 교육 전체를 복잡한 신청 시나리오/Teach-back 중심으로 재설계하지 않는다.
4. 시간을 억지로 채우기 위한 긴 복습, 과도한 설명, 불필요한 시나리오를 넣지 않는다.
5. 6명이 동시에 실습할 수 있게 **계정, 실습 대상 이름, 충돌 방지, 필요한 사전 권한, cleanup**을 실질적으로 준비해야 한다.
6. Workspace/Project 같은 결과물을 미리 만들어 두어 핵심 실습을 없애지 않는다. 특히 **Workspace 생성 자체가 교육 내용이므로 사전 생성 금지**다.
7. 모든 권한/RBAC 조합을 만들어보는 실습은 하지 않는다. **권한 체계/RBAC 표는 설명으로 끝낸다.**
8. 다만 실제 운영 절차 안에서 필요한 Member 초대와 Role 지정은 직접 실습한다.

## 항목별 확정 방향
### 직접 실습
- Workspace 생성
- Project 생성 (= Kubernetes Namespace 관계 포함)
- Workspace Member 초대
- Project Member 추가 / Role 지정
- CPU / Memory / Storage Quota 설정
- kubectl CLI 접근/구성/확인

### 설명 중심
- KubeSphere RBAC/권한 체계 자체
  - platform-admin / platform-regular
  - ws-admin / ws-viewer
  - project-admin / project-operator / project-viewer
  - DKS 신청서 Admin 요청은 project-admin과 동일하지 않고, 기준상 project-operator로 매핑되는 점
- 권한표를 실제로 하나씩 생성하거나 여러 조합을 실습하는 방식은 하지 않는다.

### 실제 변경 실습 제외
- `SECDS-ROOT.crt` CA ConfigMap Mount
- 이유: `kubesphere-system`, `ks-apiserver` 등 공유 관리 컴포넌트에 영향을 주며 6명이 반복 변경하는 실습으로 적합하지 않다.
- 대신 `x509: certificate signed by unknown authority` 상황, `secds-rootca` ConfigMap, `ks-apiserver` mount 관계, 확인/조치 절차를 설명하고 기존 정상 상태를 조회/확인하는 수준으로 한다.

## Workspace 생성 권한 관련 중요 문제
- 실제 RBAC 문서상 Workspace 생성은 platform-admin 권한과 관련된다.
- 그렇다고 Workspace를 미리 만들어 두면 안 된다. Workspace 생성 자체가 실습이기 때문이다.
- 이 문제를 **교육 내용을 줄이는 방향으로 해결하지 말고**, 6명이 교육 중 각자 Workspace를 생성할 수 있도록 사전에 무엇을 준비해야 하는지 현실적인 방식으로 정리해 달라.
- 단, 이 준비 자체를 RBAC 실습으로 만들지 않는다. 권한은 교육 전 preflight/운영 준비로 처리하고, 수업에서는 필요한 권한 구조를 설명하는 정도로 한다.
- 관리자 Credential 공동 사용은 피해야 한다.

- 6명이 한 Step을 수행할 때 강사가 무엇을 확인하고 다음으로 넘어가야 하는가?
- 실습 종료 후 생성된 Workspace/Project/Member/Quota/kubeconfig 관련 산출물을 무엇을 남기고 무엇을 정리할 것인가?
