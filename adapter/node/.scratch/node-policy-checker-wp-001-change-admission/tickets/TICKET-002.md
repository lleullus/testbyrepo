## Goal

LLM이 사용자 요청을 성급하게 구현하지 못하도록 변경 근거와 사전 테스트 의무를 먼저 확보하고, 안전한 범위가 확인된 뒤에만 제품 코드를 쓰게 한다.

## Acceptance Criteria

- 실제 변경 요청마다 독립적인 사전검사가 수행된다.
- 사용자의 일반 요청에서 원하는 행동, 보존할 행동과 실패 시 관측 결과가 자동 추출된다.
- 필요한 정보가 부족하면 자동 재조사를 먼저 수행하고, 해소되지 않을 때만 기술 용어가 아닌 행동 차이를 사용자에게 질문한다.
- 기존 프로젝트에서는 현재 실행 경로, 책임 소유자, 모듈 및 레이어 경계, 의존 방향, SSOT, 디렉터리 위계와 재사용 후보가 실제 저장소 근거에서 발견된다.
- 기존 구조가 없는 새 프로젝트에서는 요청 행동을 만족하는 가장 단순한 기본 구조가 선택되고 이후 같은 요청의 사전검사 기준으로 유지된다.
- 새 function, helper, type 또는 shape를 허용하기 전에 기존 재사용 후보가 검색되고 새로 만들 필요성이 판정된다.
- 코드 작성 전에 빈 입력, null, 경계값, 동시성, 실패 경로와 side effect에 대한 테스트 의무가 도출된다.
- 사전검사 결과는 하나의 사용자 의도와 변경 범위에 묶이고 같은 범위의 수정 반복에서는 유지된다.
- 사용자 의도, 변경 범위 또는 변경 전 프로젝트 상태가 달라지면 기존 결과가 무효화되고 다시 심사된다.
- 필수 근거가 완전한 `PASS` 전에는 LLM의 제품 코드 쓰기가 실제로 거부된다.
- `FAIL`과 `INCONCLUSIVE`는 모두 코드 쓰기를 차단하며 판단 또는 검사 능력의 부족이 성공으로 정규화되지 않는다.
- 사전검사 자체는 대상 제품 소스를 변경하지 않는다.
- 기본 결과는 통과 여부, 선택된 변경 책임과 주요 위험을 짧게 보여주며 상세 근거와 의미가 일치한다.

## Scope

- 기존 및 새 Node/TypeScript 프로젝트에 대한 사용자 변경 요청별 사전검사
- 일반 요청의 행동, 보존, 실패 결과 추출과 필요한 행동 질문
- 기존 실행 경로, 책임, 경계, SSOT, 디렉터리 위계와 재사용 후보의 근거 기반 판정
- 새 프로젝트의 최소 기본 구조 선택
- 새 function, helper, type, shape의 생성 필요성과 사전 테스트 의무 판정
- 요청 범위에 묶인 `PASS`, `FAIL`, `INCONCLUSIVE` 결과 및 `PASS` 전 제품 코드 쓰기 차단

## Non-Goals

- 변경 요청이 없는 독립적인 현재 구조 진단은 이 Ticket의 범위가 아니다.
- 작성된 코드의 정적 검사 또는 AI 의미 품질 판정은 이 Ticket의 범위가 아니다.
- 테스트 실행, 변이 검사, 생성된 edge case 실행과 side effect 증명은 이 Ticket의 범위가 아니다.
- LLM 자동 수정 반복, CI 결과 소비와 배포 승인은 이 Ticket의 범위가 아니다.
- 사용자가 레이어, SSOT 위치, 에러 경계 또는 mock 경계를 기술 설정으로 직접 작성하게 하지 않는다.
- 사전검사가 제품 기능 코드를 직접 구현하지 않는다.
- Node/TypeScript 이외 언어는 이 Ticket의 범위가 아니다.

## Verification

- 일반적인 사용자 요청이 행동, 보존, 실패 결과로 자동 정리되고 실제 저장소 경로, 책임과 재사용 후보에 연결되는지 확인한다.
- 정보가 모호한 요청에서 자동 재조사가 먼저 수행되고, 남은 질문은 기술 선택이 아닌 행동 차이만 묻는지 확인한다.
- 기존 프로젝트와 구조가 없는 새 프로젝트 모두에서 각각 저장소 근거 또는 최소 기본 구조에 기반한 사전검사 결과가 나오는지 확인한다.
- 새 function, helper, type, shape를 요구하는 변경에서 기존 후보 검색과 생성 필요성 판정이 먼저 수행되는지 확인한다.
- 빈 입력, null, 경계값, 동시성, 실패 경로와 side effect 테스트 의무가 코드 쓰기 전에 도출되는지 확인한다.
- `PASS` 전 제품 코드 쓰기 시도가 실제로 거부되고 `FAIL`과 `INCONCLUSIVE`가 우회되지 않는지 확인한다.
- 같은 요청의 수정 반복에서는 사전검사가 유지되고, 의도, 범위 또는 변경 전 상태가 달라지면 다시 심사되는지 확인한다.
- 사전검사 전후 대상 제품 소스가 동일하고 짧은 결과와 상세 근거가 일치하는지 확인한다.
