# WP-001 자동 변경 입장 심사

Status: approved
Owner: user01

## Problem

코딩 지식이 없는 사용자는 LLM에게 원하는 결과를 설명할 수는 있지만, 변경 전에 레이어, 모듈 경계, SSOT, 디렉터리 위계와 재사용 대상을 직접 판단하기 어렵다. LLM의 자율적인 주의에만 맡기면 기존 구조를 충분히 조사하지 않거나 새 function, helper, type, shape를 성급하게 만들어도 실제 코드 작성이 시작되는 것을 막을 수 없다.

## Desired Outcome

사용자는 평소 방식으로 원하는 행동을 설명하고, LLM은 기존 또는 새 Node/TypeScript 프로젝트를 읽기 전용으로 조사해 안전한 변경 근거와 사전 테스트 의무를 확보한 뒤에만 코드를 작성할 수 있다. 근거가 부족하거나 변경 위치를 확정할 수 없으면 작성은 자동으로 차단된다.

## Requirements

- 변경 요청이 없어도 현재 프로젝트의 구조, 경계, SSOT와 의존 방향을 읽기 전용으로 진단할 수 있어야 한다.
- 실제 변경 요청마다 별도의 사전검사를 수행해야 한다.
- 사용자의 일반 요청에서 원하는 행동, 보존할 행동, 실패 시 관측 결과를 자동으로 추출해야 한다.
- 필요한 정보가 부족하면 먼저 자동으로 재조사하고, 그래도 결정할 수 없을 때만 기술 용어가 아닌 행동 차이를 사용자에게 질문해야 한다.
- 기존 프로젝트에서는 현재 실행 경로, 책임 소유자, 모듈 및 레이어 경계, 의존 방향, SSOT, 디렉터리 위계와 재사용 후보를 실제 저장소 근거에서 발견해야 한다.
- 기존 구조가 없는 새 프로젝트에서는 요청된 행동을 만족하는 가장 단순한 기본 구조를 선택하고 이후 사전검사의 기준으로 고정해야 한다.
- 새 function, helper, type 또는 shape를 허용하기 전에 기존 재사용 후보를 검색하고 새로 만들 필요성을 판정해야 한다.
- 코드 작성 전에 빈 입력, null, 경계값, 동시성, 실패 경로와 side effect에 대한 테스트 의무를 도출해야 한다.
- 사전검사는 하나의 사용자 변경 요청에 묶여야 하며, 같은 의도와 범위의 수정 반복에서는 유지되어야 한다.
- 사용자 의도, 변경 범위 또는 변경 전 프로젝트 상태가 달라지면 기존 사전검사 결과를 재사용하지 않고 다시 심사해야 한다.
- 필수 근거가 모두 갖춰진 `PASS` 상태 전에는 LLM의 제품 코드 쓰기를 실제로 차단해야 한다.
- 결과는 `PASS`, `FAIL`, `INCONCLUSIVE`를 구분해야 하며 `FAIL`과 `INCONCLUSIVE`는 모두 코드 작성을 차단해야 한다.
- LLM의 근거 없는 자기 진술은 증거로 인정하지 않아야 한다.
- 기본 사용자 결과는 통과 여부, 선택된 변경 책임, 주요 위험을 짧게 보여주고 상세 근거는 필요할 때 확인할 수 있어야 한다.

## Non-Goals

- 작성된 코드의 정적 검사 또는 AI 의미 품질 판정은 이 Spec의 범위가 아니다.
- 테스트 실행, 변이 검사, 생성된 edge case 실행과 side effect 증명은 이 Spec의 범위가 아니다.
- LLM의 자동 수정 반복, CI 결과 소비와 배포 승인은 이 Spec의 범위가 아니다.
- Node/TypeScript 이외 언어 지원은 이 Spec의 범위가 아니다.
- 사용자가 레이어, SSOT 위치, 에러 경계 또는 mock 경계를 기술 설정으로 직접 작성하게 하지 않는다.
- 입장 심사가 제품 기능 코드를 직접 구현하지 않는다.

## Implementation Constraints

- 진단과 사전검사는 대상 제품 소스를 변경하지 않는 읽기 전용 작업이어야 한다.
- 프로젝트 고유 정책과 변경 근거는 코드 작성 전에 확보되어야 하며, 작성된 코드에서 다시 추론해 기존 실패를 합법화할 수 없어야 한다.
- 제품 코드 쓰기 차단은 LLM의 자발적인 준수에만 의존해서는 안 된다.
- 판단할 근거나 검사 능력이 부족한 상태를 성공으로 정규화해서는 안 된다.

## Verification Expectations

- 기존 Node/TypeScript 프로젝트에 변경 요청 없이 실행했을 때 제품 소스를 바꾸지 않고 현재 구조와 근거를 진단하는 흐름이 확인되어야 한다.
- 일반적인 사용자 변경 요청에서 행동, 보존, 실패 결과를 자동 추출하고 실제 저장소 근거와 재사용 후보를 연결하는 흐름이 확인되어야 한다.
- 기존 구조가 없는 새 프로젝트에서 가장 단순한 기본 구조와 사전 테스트 의무를 도출하는 흐름이 확인되어야 한다.
- 안전한 변경 위치가 모호할 때 자동 재조사가 먼저 수행되고, 해소되지 않으면 행동 질문 또는 `INCONCLUSIVE`로 코드 쓰기가 차단되는 흐름이 확인되어야 한다.
- 사전검사 `PASS` 전의 제품 코드 쓰기 시도가 실제로 거부되고, `PASS` 뒤에는 승인된 요청 범위에서만 진행 가능한 흐름이 확인되어야 한다.
- 사용자 의도, 범위 또는 변경 전 상태가 달라졌을 때 기존 사전검사가 무효화되고 다시 심사되는 흐름이 확인되어야 한다.
- 필수 근거 누락과 판단 불가가 성공으로 표시되지 않으며 짧은 결과와 상세 근거가 서로 일치하는지 확인되어야 한다.
