# Scope Verification Workflow

## 1. Independent semantic cycle

The caller owns dispatch, completed-result fan-in, Coverage and completion recording. The assigned independent verifier performs this entire core and never delegates. It is a separate invocation from the implementing actor and Main's completion check, not self-verification under another label. Read every bound Thesis source and the exact Scope directly before accepting caller framing. A narrower test suggestion, implementation report or Plan cannot redefine approved meaning.

The verifier owns canonical Scope admission, original-meaning check, every authored Acceptance scenario, product success/failure/preservation conditions, scenario discrimination, current target/effect attribution, runtime/canonical evidence, finding disposition, settlement and cleanup. It never edits product source/config/planning/prior evidence, dispatches Coverage or writes Scope status. It records its own fresh evidence and performs only authorized scenario effects and cleanup.

## 2. Canonical admission and current authority

Before any product/runtime action:

1. Resolve the exact `scope-shaper/tools/validate_scope.py` from the supplied source or installed skills snapshot; never use a global latest pointer or another client home.
2. Run it against the exact absolute Scope path and continue only on exact `VALID`.
3. Require the canonical output to identify the same Project Root, Scope path, `iis-scope/v1`, exact Thesis authorities and current `Status`.
4. Normal delivery requires `Status: ready`; `draft`, `blocked` and `superseded` do not start. `done` is diagnostic only when explicitly authorized.
5. Read every Thesis source named in `Product Authority`, the complete Scope, optional `Transition Authority`, current user instructions and any applicable transition/re-entry constraint. If present, compare each exact project-local baseline path/SHA-256 with validator `transition_authorities` and apply only the Scope's selected approved Block/conditions; an absent section does not require a baseline. A hash is byte identity, not approval or continuation authority. Confirm authority bytes and hashes are current.
6. Enumerate every meaningful authored Acceptance scenario and every product success/failure/preservation condition expressed by the Scope. Preserve authored labels, initial conditions, triggers/inspections, expected results, authoritative readbacks and decision boundaries; do not invent missing conditions or weaken existing ones.
7. Resolve the actual current stable implementation target and declared scenario-effect paths from direct repository/runtime observation. Caller hints and Plan Review paths are navigation only.
8. For a known Verify/Coverage correction in this request, inspect the predecessor, actual product/shared-tooling mutation attribution and completed result from the currently authorized implementation/tooling actor, including applicable admission and self-check. Missing attribution or unauthorized correction is a non-started authority limit, not product FAILED. Later self-check, report labels or relabeling this continuation verification-only do not cure it. A genuine standalone verification-only request has no historical implementation-provenance prerequisite; authorized scenario effects are not repairs.

If validator, Scope, Thesis authority, status, current target or product meaning cannot be established, return the applicable non-started/non-progressing result with no semantic verdict. Do not start product/runtime work to obtain missing admission evidence.

A Scope that omits or contradicts an applicable original obligation returns to Main for the owning Thesis, Baseline or Scope correction under `iis-workflow`'s re-entry rules. Verification does not add a new acceptance obligation, normalize a missing condition or silently expand the work.

## 3. Current source and target attribution

After canonical and semantic preflight, before any scenario action, record in this invocation's report/evidence using ordinary read/search/hash/CLI tools:

- exact canonical Project Root and Scope path, actual Scope bytes/SHA-256 and observed status;
- every bound Thesis and applicable Transition source path with SHA-256 calculated from actual bytes;
- exact stable implementation paths, file bytes/digests and relevant executable/build/config/runtime identities;
- exact declared scenario-effect paths (possibly empty), permitted state changes and authoritative settlement/cleanup readbacks;
- optional exact Plan Review navigation reference, never a prerequisite for verification-only work.

For directories, identify the relevant file set as well as file bytes so additions/removals cannot hide behind unchanged existing-file hashes. Record applicable modes/links or runtime identities where they affect this Scope; a Git revision or source digest alone does not establish which artifact/service actually executed. Attribute new observations to this invocation and any retained prior observation to its original target and invocation under the corrective-re-entry or unchanged-target follow-up rules below; retention never changes that original attribution. Do not create a binding schema, special capture tool, credential or registry.

For a load-bearing verification mechanism, record the actual files, version/bytes, relevant configuration, arguments/selectors/endpoints and their connection to the executed target in the same evidence. Capture only identities that can materially affect the observation, not an entire dependency tree or separate registry. If the mechanism materially changes, do not reinterpret old evidence as observations by the new mechanism: re-establish validity and currentness of affected observations. Invalidate and reacquire every observation dependent on a defective mechanism; widen acquisition when that dependency span is uncertain.

The stable implementation remains unchanged for attribution. Authored scenarios may mutate only declared authorized effect paths, not source/config/planning/authority or prior evidence. Separate stable and effect surfaces explicitly; overlapping declarations cannot authorize protected edits. Recheck the recorded source/target identities after scenarios and cleanup. Drift or an unavailable required check makes affected evidence non-current and prevents progression; do not carry a prior PASS across drift. Plan-only navigation drift need not invalidate product evidence unless the Plan is itself an approved product target.

## 4. Semantic contract and scenario plan

Before execution, compare the Scope's exact `Outcome` and `Acceptance` with Thesis purpose, complete loop, truth boundary, behavior/UI, failure/recovery and preservation rules. Challenge concrete false-success and false-failure paths:

- a displayed result belonging to the wrong identity, revision or cause;
- a local/cache/mock success that does not cross the promised boundary;
- a late or duplicate result destroying a promised preservation condition;
- ordering, interruption, persistence, retry or cleanup changing the result;
- an alternate ordinary entry, writer, reader or external owner bypassing the chosen path;
- a provider/runtime response that is accepted internally but not settled externally.

Do not create a speculative checklist. A derived positive variation or counterexample is justified only by a current implementation-grounded failure path, a concrete false-verdict risk or a necessary attribution distinction, and must remain within approved Scope authority.

Build invocation-local matrices before execution:

```text
Acceptance Coverage Matrix:
Acceptance scenario 1 -> authored/derived observation(s)
Acceptance scenario 2 -> authored/derived observation(s)

Thesis Meaning Coverage Matrix:
Purpose/success condition -> observation(s)
Failure/recovery/preservation condition -> observation(s)
```

These are navigation aids, not a second schema or evidence store. Link each obligation to the scenario block and primary evidence that discriminate it; keep observation limits in that block so Coverage can find what was and was not established without a second matrix. Every authored Acceptance scenario remains in the adjudication denominator. A real artifact/document promise may use canonical inspection; a runtime, state-transition, ordering, persistence, UI or external-effect promise requires its real boundary and authoritative readback.

## 5. Integrated scenario blocks

Treat each authored Acceptance scenario as one normative block. Common setup or cleanup may be shared only when initial state, identity, trigger, observation window, readback and decision boundary remain unchanged. Do not merge materially distinct scenarios or split one scenario around implementation seams.

For each block, record:

```text
Scenario Block:
Acceptance anchor: <exact Scope section/subheading>

Authored contract:
  Initial state:
  Identity:
  Action or inspection:
  Expected observable result:
  Acceptance boundary:
  Authoritative readback:
  Observation window:
  Decision boundary:
  Failure/recovery/preservation condition:

Derived execution:
  Setup:
  Actual runtime/canonical inspection:
  Positive case:
  Material counterexample or nearest nonconforming state:
  Discriminating observation:
  Sensitivity activation:
  Evidence capture:
  Cleanup/settlement:
  SATISFIED condition:
  CONTRADICTED condition:
  INCONCLUSIVE condition:
```

Ground `Nearest nonconforming state` in a real failure of a current implementation assumption. Ground `Discriminating observation` in the result that differs between conforming and failing behavior. Ground `Sensitivity activation` in the initial state and authorized action that exposes that difference. A happy path that would also pass the failing implementation is insufficient.

For a reachable ordering/race failure, activate the relevant competing writer or controlled interleaving within authorized effects and inspect the authoritative final state/invariant; repeated sequential happy paths do not discriminate that failure.

For every material finding supplied by navigation or discovered while grounding/executing, assign one verifier-owned disposition:

```text
Finding Disposition:
- REPRODUCED
- CURRENT_READBACK_CONFIRMED
- OUT_OF_SCOPE
- UNATTRIBUTABLE
- SUPERSEDED_BY_CURRENT_TARGET
```

`REPRODUCED` uses the smallest safe current trigger and fresh authoritative evidence. `CURRENT_READBACK_CONFIRMED` uses a direct canonical/product readback without unsafe repetition. `OUT_OF_SCOPE` is bound to the current Scope, not merely convenient. `UNATTRIBUTABLE` is not a product failure; if the missing attribution is required, the affected scenario stays `INCONCLUSIVE`. `SUPERSEDED_BY_CURRENT_TARGET` never carries an old finding forward.

## 6. Evidence and execution

Obtain the smallest sufficient evidence for every authored Acceptance scenario and product success condition needed by the current-target verdict. Normally acquire fresh current-target observations. A prior primary observation may support the fresh verdict only under the changed-target corrective-re-entry or unchanged-target evidence-only follow-up rules below, after independently establishing its applicability to the exact current obligation and preserving its original target/invocation attribution. Never relabel retained evidence as execution by the current target. Use:

1. actual runtime/canonical acceptance-surface observation;
2. authoritative product/canonical readback;
3. rendered UI interaction/readback where UI is the boundary;
4. real authorized disposable/controlled execution crossing the approved entry, transition/effect, lifecycle and readback;
5. source/diff/unit checks and ancillary doubles only as supporting explanation.

A mock, stub, canned response, seeded terminal state, hand-written event or surrogate readback cannot prove the real boundary it replaces. An ancillary double does not invalidate a separate real boundary; never claim the doubled boundary was verified. Internal success or HTTP acceptance is not proof of an external effect.

Preserve conflicting observations across retries. A later successful run does not erase an attributable product contradiction; an unexplained conflict in mechanism, target or attribution leaves the affected evidence INCONCLUSIVE rather than authorizing retry-until-PASS. Use the smallest observation that separates those causes, retain both raw results and apply the existing verdicts; add no flaky verdict or automatic retry loop.

### Corrective re-entry and evidence breadth

After stable product target change, issue one fresh whole-Scope verdict for that exact target; never combine PASS results from different targets. The fresh verdict re-adjudicates every obligation, but it does not itself require mechanical replay of every prior observation. The verifier independently decides evidence breadth. An implementer impact claim, Main's narrower suggestion, unchanged file/function or noninterference argument does not exempt an obligation or decide observation retention.

For changed-target corrective re-entry, a directly readable prior primary observation may be retained for an obligation only when the verifier independently establishes its current applicability from the actual delta and that obligation's deciding writer/reader, causal/state/effect dependencies, verification mechanism, build/runtime/config identity, external premises, observation window and settlement. Preserve the original target/invocation attribution. Retention is evidence reuse, not PASS carry-forward or current-target execution. Reobserve any time/current-state-dependent premise and any real boundary whose relevant dependency changed or remains uncertain; unchanged file/function/hash alone is insufficient.

For an obligation not fully re-executed, explain in the existing scenario block its exact anchor, relevant deciding writer/reader and causal/state/effect dependencies, current target/mechanism, retained primary observation and original attribution when used, current applicability basis, actual current observations establishing target/mechanism/premise state, and limits. Preserve authored initial state, trigger, transition, identity, ordering, observation window and preservation conditions. A fresh readback of A's existing output proves its current state, not B's ability to create it. If neither fresh current-target execution nor an admissible retained primary observation plus current applicability evidence distinguishes the required behavior from its nearest nonconforming state, broaden acquisition. Static artifact promises may use canonical inspection; runtime promises still require a real-boundary primary observation, whether freshly acquired or conditionally retained under this rule.

When sufficient discrimination or bounded impact cannot be established, broaden acquisition; cross-cutting or unbounded impact defaults to full fresh scenario execution within current authority. Do not blind-replay external effects or reinterpret lack of execution permission as lack of need. Unavailable necessary evidence prevents VERIFIED. This successful-verdict condition does not remove failure-aware continuation below.

For an evidence-only gap on an unchanged product target, a fresh independent invocation may retain directly readable primary evidence from the prior independent invocation only after re-establishing unchanged authority, relevant source/runtime/config identities, valid mechanism and external premises, applicable observation windows and settled effects. Source hashes alone are insufficient; new scenario effects must not invalidate retained conclusions. Reobserve time/current-state-dependent claims as needed. Preserve original observation/invocation attribution, acquire the missing observations and issue a new superseding whole-Scope result referencing, never editing, the predecessor. An unresolved gap prevents completion from the old VERIFIED alone. This unchanged-target path is distinct from changed-target retention above.

### Mechanisms and boundary observations

Reuse existing project launch, readiness/doctor, UI/CLI/E2E drive, raw-evidence and cleanup methods when they exercise the required path under current authority. Inspect what the tool actually does, then connect its actions and raw authoritative readbacks to the existing scenario evidence, distinguishing observed boundaries from substituted or omitted ones. No common command interface or feature-map format is required. PASS or exit status proves only its observed boundary: when the approved Acceptance is the CLI's exit code itself, that code is direct evidence; internal PASS cannot replace storage, identity or external settlement readback.

If selector/route drift or another mechanism limit prevents observation of the required path, identity or readback, return an evidence/mechanism gap with exact owner and allowed next action, not an inferred product failure. Invocation-local argument/selector/route misuse can be corrected in a fresh verifier follow-up, after prior effects settle; shared project tool source repair belongs to its authorized implementation/tooling actor, and IIS-owned validator/helper repair to its authorized maintainer. The verifier does not patch shared tools and manufacture success in the same cycle. Reacquire observations dependent on the defect. An attributable product contradiction remains a product failure even when the harness reports PASS.

Launchers, selectors, CLI commands, provider readbacks and cleanup code belong to the product project, not a generic IIS harness. When an approved product change makes an existing tool stale, update it within that authorized implementation work. A missing tool is not a verification blocker if direct real-path execution/readback is sufficient; create reusable project tooling only when repeated use justifies it, through authorized implementation rather than verifier repair.

For absence or retirement, define the bounded active-surface universe from the Scope, Thesis and current entrypoints/config/package/runtime/storage authority. Directly inspect the relevant identities and suspicious survivors; state the universe and limits. For deletion, observe existence before the trigger and absence after it, plus required preservation. For timing, measure the authored milestone (onset versus settlement). For event delivery, distinguish publisher emission, subscriber receipt and rendered change.

For an uncertain external or non-idempotent effect, do not blind replay. Use the authored readback, settlement and cleanup path. If applied/not-applied is attributable, adjudicate from it. If not, affected scenario evidence is `INCONCLUSIVE`; unknown is not success and not an automatic product failure.

## 7. Failure-aware continuation

A first attributable contradiction is not permission to skip required evidence blindly. After fresh evidence directly contradicts an authored decision boundary and fixes whole Scope FAILED, continue only where the next observation can change validity, target attribution, cause/owner, bounded correction span or mandatory cleanup; finish all started effects' settlement/readback/cleanup. Leave an unrelated expensive scenario unexecuted only when it cannot change those facts, and record its explicit INCONCLUSIVE disposition and reason. This shortcut never applies to VERIFIED: every required authored scenario needs sufficient evidence admissible under the current-target or retention rules above.

If a required scenario is unavailable, preserve `INCONCLUSIVE`. An attributable contradiction is `CONTRADICTED`/`FAILED`; lack of authority/evidence is not a product defect. Do not downgrade the Scope requirement to force success.

## 8. Scenario report and completed result

Before the first product/runtime action, record initial identities in invocation-local evidence. Return one complete report through the ordinary invocation result or exact report path:

```text
SCOPE VERIFICATION RESULT
Project Root: <exact canonical root>
Scope: <exact canonical Scope path and pre-execution SHA256>
Thesis / Transition sources: <all exact bound paths and actual-byte SHA256; transition None when absent>
Independent invocation: <actual verifier identity and result/evidence reference>
Stable Target Paths: <exact paths and observed byte/runtime identities>
Scenario Effect Paths: <exact declared mutable paths and authorized effects>
Currentness before / after: <actual checks, byte/runtime identities and limitations>
Verification Verdict: VERIFIED | FAILED | INCONCLUSIVE
Verifier Scope Progression: PENDING CALLER RECORDING | NOT APPLICABLE
Observed Scope Status: ready | done

Semantic contract check: <result>
Scope Outcome and Thesis success conditions: <meaning and evidence>
Acceptance scenarios: <all scenarios in authored order>
Target stability: <identity/currentness>
Environment and external conditions: <conditions/limits>
Authoritative readbacks: <raw paths/keys/windows>
Known findings and dispositions: <none or exact items>
Cleanup and settlement: <actual state>
Limitations/provenance: <None or exact Decision/Governing authority/Observed condition/Effect/Next allowed action>
```

Progression is `PENDING CALLER RECORDING` for a normal ready Scope and `NOT APPLICABLE` for diagnostic done verification. A non-started preflight result names its exact blocker without manufacturing a verdict. The worker never writes `done`. Main preserves the unchanged completed result and actual invocation/evidence attribution, then applies the Coverage and ordinary status-only recording procedure in `scope-verify/SKILL.md`. No special host terminal schema, handle or authentication is required or claimed. A field set, hash, copied narrative or process exit alone does not prove independent verification.

## 9. Completion boundary

Before returning, confirm every authored Acceptance scenario and applicable Thesis success/failure/preservation condition has an explicit result; every result has sufficient evidence admissible under the current-target or retention rules above, or an exact `INCONCLUSIVE` limit; all started effects settled and were cleaned up; stable target/authority identity stayed current; and all material findings have dispositions. A normal `VERIFIED` requires no unresolved material evidence/attribution gap. `FAILED` is a valid semantic result when an attributable contradiction is established. `INCONCLUSIVE` preserves the exact missing evidence/authority/settlement boundary. No result authorizes implementation, remediation, Scope mutation or finalization.
