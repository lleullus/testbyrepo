# Scope Coverage

## Caller contract

The finalization-owning caller supplies the unchanged original source assignment:

- **Project Root:** exact canonical absolute path.
- **Thesis:** every exact source bound by the Scope, revision and full UTF-8 SHA-256.
- **Scope:** exact canonical `docs/planning/work/<slug>/SCOPE.md` path.
- **Transition Authority:** if the Scope has the optional section, preserve each exact project-local baseline path and full SHA-256 and inspect its selected Block/conditions; if absent, no baseline is required. A digest proves bytes, not approval or continuation authority.
- **Completed verification:** exact unchanged result from the completed independent verifier invocation, its actual identity and primary-evidence locations, including initial state, trigger/order, readbacks, observation windows, cleanup and currentness.
- **Target/source identity:** exact stable target paths and byte/runtime identities, declared scenario-effect paths, bound source paths/digests and verification pre/post currentness observations.
- **Prior Coverage:** exact previous result and correction/new evidence on follow-up, or `None`.
- **User instructions:** current read-only limits and selected model/effort policy.

Tell the worker: **read every bound Thesis source, the exact Scope and primary verifier evidence directly before judgment.** A caller summary, prior success conclusion or latest-file lookup is not a substitute. Original sources define the approved purpose and success boundary; they do not authorize mutation.

### Evidence boundary — copy into every assignment

> **Evidence boundary — apply before role-specific work**
> - Do not use mocks, stubs, canned responses, seeded success states or surrogate readbacks as evidence for a real boundary they replace.
> - When the Scope promises real execution, state transitions or external effects, distinguish actual path/readback evidence from ancillary doubles and internal success.
> - If a required primary observation is unavailable, preserve the exact evidence/authority limit. Do not infer no finding.
> - This role has no product execution, provider, service, source-edit or completion-recording authority.

Forward the block unchanged, followed by exact role document, target, report and ordinary result destination.

## Purpose and ownership

Answer one bounded question: **even if every observation in this exact verification is correct, can a reachable implementation path still violate the same approved Scope outcome or Acceptance condition while passing those observations?**

Coverage owns a separate post-verification counterexample and observation-gap search. It is not a second verifier: the verifier owns semantic preflight, every authored Acceptance scenario, actual execution/readback/cleanup, known-finding disposition and the semantic verdict. Coverage never issues an Acceptance or whole-Scope verdict, changes Thesis/Scope/source/runtime/planning/prior evidence, writes Scope status, executes product/tests/experiments, starts services, calls providers or creates a review database. It records only its own read-only review result.

## Invocation and inputs

Arrange exactly one separate independent Coverage invocation only after the completed independent verifier result has settled with semantic `VERIFIED` on the normal ready-to-done path. Coverage is separate from the verifier, implementer and Main's completion check and uses the caller-selected model/effort. Do not create a second verifier, add consensus or hide a fallback. If an independent invocation is unavailable, return that limitation, not a no-finding result. `FAILED`, `INCONCLUSIVE`, diagnostic done verification, missing/incomplete verifier result or failed settlement skip normal-success Coverage.

Coverage receives the exact Scope, current Thesis/applicable Transition sources, unchanged verifier report, raw primary evidence and target/source identities. The caller must not prescribe a no-finding result. Use ordinary read/search tools; no specific host installation or custom tool is required.

## Read-only bounded investigation

1. Establish the approved Scope `Outcome`, optional `Transition Authority`, every authored `Acceptance` scenario and relevant Thesis purpose/success/failure/preservation boundary. Compare originals directly; do not invent supported conditions or new acceptance requirements.
2. Trace the relevant current implementation from entrypoint through deciding writers/readers, state/effect owner and authoritative readback. Read a dependency boundary further only when a material clue makes it relevant. This is not a repository-wide audit or standing fault checklist.
3. Inspect verifier primary evidence, not only its narrative. For each load-bearing claim follow the raw path/locator, target identity, initial state, action, readback and observation window. Compare what was activated and observed with reachable states the implementation can produce. Check onset versus settlement, pre-existing existence before deletion, publisher versus subscriber/rendered evidence and identity/persistence only when those distinctions govern this Scope claim.
4. Resolve materially supported candidates as an evidence-backed dismissal, a concrete finding, or an exact evidence limit. An unexecuted branch alone is not a finding, but a reachable contract-violating state that would pass the actual observations is material.

A material finding or evidence limit must state:

- exact Thesis/Scope obligation and section;
- relevant implementation/mechanism path or exact unavailable anchor, with observed fact separated from inference;
- reachable condition and materially wrong result for a finding, or the missing observation and unresolved claim for an evidence limit;
- which verifier observation cannot distinguish the violation or is missing;
- narrowest discriminating next observation or exact authority/environment limitation;
- routing class (such as observation, mechanism, product, method, meaning, drift or settlement), required owner and exact current actor when supplied, permitted next action and actions not authorized.

Routing metadata grants no mutation authority and does not determine verification sufficiency. Do not select a missing actor or turn a local classification into permission to omit observations. Coverage may identify exact code paths and failing assumptions, but must not issue an exact patch as an implementation instruction or rewrite the Plan.

Dismiss unrelated risks, unreachable candidates, approved Non-Goals and already-discriminated paths. Do not require a fixed finding count or an executable reproduction from this read-only role. Stop when material candidates are resolved; do not search remote possibilities merely to fill a report.

### Useful distinctions

- A unique key observed in one environment may not distinguish a multi-identity collision; identify the smallest additional source/readback observation without creating product state.
- Disposable accumulated state can be evidence only when it already exists and the Scope authorizes the history/transition; Coverage must not seed a terminal state or run the product to create it.
- A controlled dependency failure may show application failure handling, not the external provider's behavior. Do not exhaust quota or demand unapproved fallback policy.
- Current source/schema inspection can dismiss a reachable hypothesis, but cannot substitute for a verifier-owned real boundary that the Scope requires.
- A verification script may pass while observing an old API route instead of the current UI, or checking display text without distinguishing a wrong identity's persisted result. Follow the actual mechanism, action and raw readback to establish a reachable violation or exact evidence limit; tool presence alone proves neither weakness nor sufficiency. Report the next discriminating observation without executing or repairing the product/tool.

## Terminal result

Return one ordinary review through the completed invocation's result or exact report path, preserving actual reviewer identity and primary-evidence references:

```text
SCOPE COVERAGE REVIEW RESULT
Scope: <exact canonical Scope>
Reviewed verification: <exact report and primary-evidence references>
Target and authority: <existing identity and currentness limits>
Completion: COMPLETE | PARTIAL | BLOCKED
Findings: None | <material causal findings>
Limitations: None | <exact evidence/authority/investigation limits>
```

`COMPLETE` means the bounded search finished; it may contain findings. `COMPLETE` with `None` is not proof that all bugs are absent. Tool failure, missing evidence or an unfinished search is `PARTIAL`/`BLOCKED`, never no-finding. A material limitation that leaves an approved Scope claim unresolved prevents success progression even if Findings is `None`.

## Caller continuation

The caller retains the unchanged completed verifier result and its invocation/evidence attribution while Coverage runs. It must not convert a Coverage summary into a second semantic verdict or discard raw findings/limits.

- `COMPLETE` with no unresolved material finding/evidence gap and no required follow-up permits Main to apply the currentness and status-only recording procedure in `scope-verify/SKILL.md`: confirm actual independent completed results, current ready Scope/source/target and settled effects; change only `Status: ready` to `Status: done` with ordinary file tools; read back the exact result.
- A material reachable path or evidence limit withholds recording and routes the exact finding/limit to the existing verifier, implementation/tooling, Plan, Scope or Thesis owner as appropriate. It is not a product FAILED verdict and does not authorize automatic remediation or Coverage rewriting the Plan. Main forwards the evidence; it neither repairs the product/tool nor decides which obligations are unaffected.
- Coverage failure, missing evidence or target attribution returns `PARTIAL`/`BLOCKED` and exact next owner/action without overwriting verifier `VERIFIED` or fabricating completion.
- A changed stable source/config/authority or unexplained effect drift requires a fresh current-target semantic verifier cycle. The old result is never resumed or patched. An unchanged-target evidence-only gap follows the verifier's evidence-follow-up rules and produces a new whole-Scope result before further normal-success Coverage.

Only Coverage decides whether follow-up search can be targeted. Require an attributable predecessor COMPLETE review with readable primary basis and explicit limits, exactly identified unresolved items, and a new settled VERIFIED result for the current whole Scope. Inspect all relevant changes since that predecessor, including product, runtime/config, mechanisms and verifier observations omitted or replaced. Establish that the previous basis outside the follow-up frontier remains applicable; COMPLETE alone or the verifier's local-impact claim is insufficient.

Targeted follow-up examines the prior finding, corrected causal path, adjacent reachable bypasses, new primary evidence and the basis for reduced execution. If boundedness or retained applicability cannot be established, perform normal Scope-bounded Coverage, not a repository-wide audit. Missing evidence or unfinished search remains PARTIAL/BLOCKED, never no-finding.

Do not create a Coverage verdict store, fingerprint registry, scheduler, approval layer, lifecycle state or new delivery switch. Coverage is an ordinary read-only review between verifier settlement and Main's completion recording, not host-enforced authorization.
