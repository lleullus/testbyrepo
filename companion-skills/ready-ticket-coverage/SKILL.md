## Purpose and ownership

Answer: even if every observation in this exact verification is correct, can a reachable implementation path still violate the same approved outcome while passing those observations?

Coverage owns the separate post-implementation counterexample search, after the verifier has finished its semantic cycle. The verifier still owns semantic preflight, every authored Flow/AC, scenario discrimination, actual execution/readback/cleanup, known finding disposition and the semantic verdict. Do not repeat its whole scenario or issue a second AC/Ticket verdict. Planner/Plan Reviewer retain important pre-implementation assumptions and start sufficiency.

Coverage is read-only: inspect current contract, source/schema and existing primary evidence. Do not run the product, execute experiments or tests, prepare scenario state, call providers, start services, modify product/runtime/source/config/planning/evidence, write Ticket status, capture or amend a verification binding, call `ready_finalize`, or manufacture terminal authority. Return the review through existing host output/artifact delivery, not a new evidence store or registry.

The caller reads Caller: include in every delegated assignment, Purpose, Invocation and inputs, and One terminal result to dispatch and consume this role; the actual reviewer reads the whole skill. The caller does not repeat Bounded investigation.

## Bounded investigation

1. Establish the approved outcome and exact current Ticket/parent anchors. Compare parent meaning with its Ticket projection; do not invent supported conditions or new ACs.
2. Trace the relevant implementation from entrypoint through deciding writers/readers and state/effect to authoritative readback. Read a dependency boundary further only when a material clue makes it relevant. This is not a repository-wide audit or standing fault checklist.
3. Compare that path's load-bearing assumptions with what the verifier actually activated and observed: initial state, entity identity, trigger/order, observation window and readback. Inspect primary evidence, not only the final narrative.
   Primary-evidence inspection is targeted but not conditional on first finding suspicious code. Use the report as an index and bounded evidence-location lookup as needed; an unexecuted branch alone is not a finding. Establish how a reachable contract-violating state could pass this run's actual observations.
   Follow each load-bearing claim to the existing raw file and locator, identity, initial state, action, readback and window. Report/raw disagreement takes the raw observation as evidence and leaves unsupported narrative unproven. Check the milestone actually measured (onset versus settlement), preexisting artifact before deletion, and publisher versus subscriber/rendered evidence only when those distinctions govern this claim. Canonical artifact-only outcomes and ancillary doubles do not automatically require additional runtime work.
4. Resolve materially supported candidates through evidence-backed dismissal, a concrete finding, or an exact evidence limit. Do not discard a material gap merely because the next observation needs unavailable authority/environment.

A material finding concisely connects:

- the approved obligation and exact Ticket/parent anchor;
- the actual implementation path and assumption that can fail, separating observed facts from inference;
- a reachable condition and materially wrong result;
- which actual verification condition/observation cannot distinguish that result;
- the narrowest discriminating next observation, or the exact authority/environment limitation preventing it.

Unrelated generic risks, new feature requests, conditions outside current approval, unreachable candidates and already-discriminated paths are not completion blockers. Do not require a finding count or executable reproduction from this read-only role. Stop when materially supported candidates are resolved as above; do not keep searching without new important evidence or to fill a no-finding report.

### Examples, not mandatory cases

If multi-project use is approved, compare project identity through actual key writers/readers with the recorded verification state. A single-project unique-key run may not distinguish a global-key collision; two projects with the same local key and different results can be the narrow next observation. Do not require a production DB copy or expand a single-project contract.

Fresh evidence need not start empty. Disposable accumulated/multi-entity state may activate a real boundary, but seeding the terminal state cannot replace an approved history/transition claim. Coverage proposes the observation without creating the state.

If approved failure semantics require leaving a progressing state after provider failure, inspect real success/failure writers and returns against recorded provider-success evidence. Distinguish controlled dependency failure exercising the application from proving the provider's external behavior. Do not exhaust quota or demand new retry/fallback behavior. Missing approved failure meaning returns to the contract owner.

## One terminal result

Return one review through the existing host terminal/artifact path. The following is readable content, not a machine schema or prose-string validator:

```text
COVERAGE REVIEW RESULT
Ticket: <exact Ticket>
Reviewed verification: <exact report and primary-evidence references>
Target and authority: <existing identity and currentness limits>
Completion: COMPLETE | PARTIAL | BLOCKED
Findings: None | <material causal finding(s) above>
Limitations: None | <exact investigation/evidence/authority limits>
```

COMPLETE means the bounded investigation finished; it can contain findings. COMPLETE + None is not proof that all bugs are absent. No response, tool failure, PARTIAL or BLOCKED is not no-finding. A limitation that leaves a material approved claim unresolved prevents success progression even when the investigation is COMPLETE.

## Caller continuation

The caller retains the immutable verifier result and exact host-delivered handle while Coverage runs. It does not send that handle to Coverage or reconstruct it from reports.

Do not convert COMPLETE into no-finding or discard Limitations in a success summary. Preserve the original review and deciding raw-file references when returning to the existing contract/evidence owner. A caller must withhold submission for a material evidence limit even when Findings is None; report `Finalization: not called`, not a fabricated finalizer rejection. This is caller behavior, not host-enforced attestation.

- COMPLETE with no unresolved material finding or evidence gap: while target/authority remain current, submit that original handle to existing `ready_finalize` and report its actual progression result.
- A material unverified path under the same obligation: withhold the success handle; route the exact finding to the existing verification/correction owner. A hypothesis is not product FAILED or proof of a completed fix.
- Material parent-to-Ticket projection gap: return to the exact contract owner; neither Coverage nor the verifier approves replacement ACs.
- Coverage failure, missing evidence or target attribution: report PARTIAL/BLOCKED and the exact next owner/action without overwriting the verifier's semantic VERIFIED or fabricating a finalizer return.

The caller may not erase a material finding, vote it away or treat reviewer agreement as evidence. Further execution/adjudication requires a fresh verifier invocation with a fresh binding and terminal, never resumption or mutation of the old terminal. The new verifier adjudicates every applicable obligation; reuse observations only under existing freshness/attribution/flow rules, never carry old PASS automatically. Source/config changes or a changed effect surface cannot be patched into the old binding. Fixes follow existing Implement/Plan Review authority; standalone verification does not authorize automatic remediation.

After a new successful verifier result, follow-up Coverage focuses on prior gap resolution and the scope affected by correction/new evidence. Use current primary evidence for dismissal; do not repeat unrelated investigation or import an old review across changed target, obligations or initial conditions. Do not redispatch the same unresolved finding and same evidence indefinitely; stop with the exact limit and next owner when no material progress is available.

Coverage adds a caller protocol condition, not mechanical enforcement in the finalizer. Opaque handles, verifier terminal schema, immutable stable/effect binding and guarded status writes remain unchanged. Do not create a Coverage verdict store, fingerprint system, lifecycle DB, scheduler, approval layer or new delivery switch.
