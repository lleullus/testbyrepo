## Failure-layer notes

### Mbed TLS 4.2.0

The first Mbed TLS 4 attempt used GitHub's autogenerated tag archive and failed because that archive did not contain the full release framework expected by the build. That was a source-package selection error, not a product incompatibility. The build was corrected to use Mbed TLS's official release asset with its published SHA-256. With the official asset, Mbed TLS itself built successfully, but libwebsockets 4.x compilation then failed because the integration still references public headers removed by Mbed TLS 4. This second failure is the actual compatibility boundary.

### libwebsockets 4.5.x CMake workaround

The historical cross-build contained an OpenSSL-probe `sed` workaround intended for libwebsockets 4.3.x. Applying it unconditionally to 4.5.8 corrupted newer CMake flow-control lines and caused configuration failure. The script now scopes that workaround to `4.3.*`; 4.5.8 then builds normally. The initial parse failure therefore was a build-script migration defect, not evidence against LWS 4.5.8.

### OpenSSL 3.6.1

The first OpenSSL build invocation was interrupted while generating unnecessary documentation/output. The build path was changed to `no-docs` and quiet make; the same OpenSSL 3.6.1 target then built successfully and passed TLS 1.2, TLS 1.3 and WSS checks. It remains a tested alternative, but its LWS 4.5.8 static ttyd was 7,370,664 bytes versus 1,316,984 bytes for the installed production baseline, so it was not selected as the default TLS architecture.

### libwebsockets 5.0.0

LWS 5.0.0 itself compiled, but ttyd's final static link failed to resolve its dependency set. This is a real integration blocker and is intentionally not papered over with additional linker-path hacks in Phase 9.

## Reproducibility

The first two selected-version builds from different build roots produced different binaries. Inspection found absolute Mbed TLS source paths embedded through `__FILE__` strings. `build_mbedtls` now applies:

```text
-ffile-prefix-map=${BUILD_DIR}=.
```

After that change, two independent build roots produced byte-identical ttyd binaries:

```text
/tmp/ttyd-stage-phase9-repro-a/x86_64-linux-musl/bin/ttyd
/tmp/ttyd-stage-phase9-repro-b/x86_64-linux-musl/bin/ttyd
SHA-256: 2e34d0685f08d7b74235d7e656a6d40f008c39b1b77e80843fe5ac3a2c45d9d8
```

A third build using only the new default values in `scripts/cross-build.sh` produced the same SHA-256.
