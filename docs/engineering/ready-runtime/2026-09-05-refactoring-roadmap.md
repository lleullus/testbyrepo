## 1. 로드맵의 결론

**권장 순서는 `실패 재현과 기준선 → 실제 행동 평가 → 완료 책임 연결 → 기획 정리 → 구현 정리 → 검수 구조 비교 → runtime 감량 → 통합 검증과 전환`이다.**

스킬 수나 문서 길이를 먼저 줄이지 않는다. 그렇다고 현재 구성을 보존하는 것도 전제하지 않는다. 먼저 제품이 성립했다는 결론에 필요한 사실과 책임을 연결하고, 그 연결에 기여하지 않는 절차를 근거를 가지고 걷어낸다.

이번 범위에는 두 종류의 변경이 있다. 반복 설명·참조·코드를 정리하는 변경과, 프로브 필수 여부·Behavior 분석 범위·완료 조건처럼 운영 계약을 바꾸는 변경이다. 후자를 단순한 문구 정리로 묶지 않고, 별도의 효과 비교와 호환성 검증을 거친다.

성공 기준은 **사용자 요구를 실제 사용 경계에서 충족하면서, 사용자가 다시 핵심 검수와 리메디에이션을 맡는 일이 줄어드는 것**이다. 오합격을 모두 보류로 바꾸거나, 불확실성을 더 길게 설명하는 것만으로는 성공이 아니다.

### 현재 근거와 미확정 판단

| 모든 작업의 전체 Behavior 절차 | 현재 명시적으로 요구된다. [S4] | 감량 실험의 우선 후보지만 불필요하다고 확정하지 않는다. |

| 복잡성이 실패를 유발했는가 | 아직 비교 증거가 없다. | 비대화를 근본 원인으로 확정하거나 전면 삭제하지 않는다. |
| 당시 실제 가드 적용 여부 | 현재 설치 일치와 별개로 사건 당시 적용은 미확인이다. | 설치됨·로드됨·보호 경로로 실행됨을 구분한다. |

아래 통과 조건은 이번 리팩터링 후보의 채택 기준이다. 일반 제품 Ticket마다 새 승인 단계나 보고서를 추가하자는 뜻이 아니다.

## 2. 전체 단계와 의존성

| 단계 | 목적 | 주요 결과물 | 다음 단계로 넘어갈 조건 |
|---|---|---|---|
| R0. 기준선·사건·격리 | 어떤 환경에서 어떤 주장이 잘못 확대됐는지 고정 | 사건별 증거 연결, 현재 실행 조합, 격리된 작업본 | 실제 사실과 미확인 원인이 구분되고 운영본과 실험본이 분리됨 |
| R1. 행동 평가 기반 | 변경 효과를 문구가 아니라 실제 행동으로 비교 | 기존 평가 틀의 보완, 정상·결함·증거 부족 사례 | 채점기·평가 실행·제품 현실의 증거가 구분됨 |
| R2. 완료 책임 연결 | 각 의무가 누구의 어떤 증거로 끝나는지 정리 | 기존 계약의 의미·책임 정합화 | 중요한 미확인과 전체 의무가 상태 집계에서 사라지지 않음 |
| R3. 기획 정리 | 실제 제품 의미는 보존하고 중복 분석·투영을 줄임 | 조사 인계, Behavior 적용, Spec/Ticket 투영 개선 후보 | 더 짧은 경로가 같은 중요한 결정을 보존함 |
| R4. 구현 정리 | 실제 제품 경로를 완성하고 핵심 전제 확인을 앞당김 | 구현 절차·self-check·인계 개선 | 내부 성공을 실제 결과로 확대하지 않고 정상 제품은 완성함 |
| R5. 검수 재구성 | 가정을 깨는 관찰과 최종 판정을 강화 | 프로브 유지·통합 비교와 선택 | 오합격·불필요한 보류·재작업을 함께 평가해 선택 가능 |
| R6. runtime 감량 | 필요한 강제 보호와 효율 정책을 분리 | 좁은 보호 기능, 호환된 도구·설치 조합 | 감량해도 보호가 유지되고 실제 사용 경로에서 작동함 |
| R7. 통합 검증·전환 | 전체 흐름에서 사용자 문제를 해결하는지 확인 | 비교 결과, 배포 조합, 롤백 가능 상태 | 실제 결과·정상 진행·호환성·복구 조건이 모두 충족됨 |

**핵심 의존성:** R1 없이 감량 효과를 주장하지 않는다. R2 없이 프로브·완료 절차를 줄이지 않는다. R5의 구조 선택 없이 관련 binding을 삭제하지 않는다. R7 전에는 운영본의 구성을 교체하지 않는다.

각 단계는 거대한 일괄 변경이 아니라 작은 변경 묶음으로 진행한다. 단, 한 의미 변경의 작성자·소비자·검사기는 같은 호환 묶음에 포함한다. 단계 하나가 끝났다고 그 상태를 반드시 운영 환경에 배포할 필요는 없다.

## 3. R0 — 기준선, 실제 사건, 작업본 격리

### R0-1. 현재 환경과 사건 당시 환경을 분리한다

현재 소스 revision, 작업 트리, 설치된 스킬·runtime의 조합, 실제 사용 호스트와 호출 경로를 기록한다. 사건 당시의 동일 정보가 남아 있으면 별도로 연결한다. 현재 파일을 읽고 과거 사건에도 같은 규칙이 적용됐다고 가정하지 않는다.

runtime은 canonical `skill://ready-ticket-implement` 또는 `skill://ready-ticket-verify` 호출로 활성화되며, 일반 파일 읽기는 유지보수로 취급한다. 따라서 `SYNCED`는 파일 일치이지 당시 세션의 보호 적용 증명이 아니다. [S3]

이 단계에서 사용할 원인 분류는 간단하다. 장치가 적용되지 않았는지, 적용됐지만 보호 범위 밖이었는지, 계약 자체가 약했는지, 충분한 계약을 수행자가 잘못 적용했는지를 구분한다. 모든 실패를 한 가지 원인에 넣지 않는다.

### R0-2. 대표 사건의 주장과 증거를 연결한다

우선 사용자 불만의 대표 사건 하나에서 요구·사전조사·Scope/Spec/Ticket·실제 구현 경로·프로브·검증·최종 보고를 연결한다. 대상 프로젝트는 실제 사건 자료가 가리키는 곳으로 고정하고, 무관한 저장소를 넓게 조사하지 않는다.

확인할 질문은 **“어떤 실제 조건이 미확인으로 남아 있었고, 어느 결과부터 그 조건이 충족된 것처럼 성공을 주장했는가”**다. 최초 증거 부족, 최초 근거 없는 성공 판정, 상위 보고에서의 확대를 분리한다.

사건 로그가 없다면 구조적 반례를 만들 수는 있지만, 그것을 과거 사건의 재현이라고 부르지 않는다. 확보 가능한 증거 범위를 닫은 뒤 비교 평가로 넘어간다. 원인 탐색을 무기한 계속하지 않는다.

### R0-3. 운영본과 실험본을 격리한다

설치 문서는 컴패니언 스킬의 live entry가 이 저장소의 원본 디렉터리를 가리키는 직접 symlink라고 명시한다. 따라서 원본 디렉터리에서 브랜치만 바꾸거나 파일을 편집하면 사용 중인 지침이 달라질 수 있다. [S6]

수정은 별도 worktree 또는 동등하게 격리된 복제본에서 하고, 평가 세션이 사용할 스킬 탐색 경로·runtime·대상 제품 사본도 일치하게 격리한다. 구버전 지침을 읽은 세션에 신버전 runtime만 끼우지 않는다. 현재 실제 link와 설치 설정은 전환 전에 직접 확인한다.

**통과 조건:** 무엇을 관찰한 사건인지, 어떤 구현 조합을 비교할지, 변경이 live 지침에 흘러들지 않는지가 명확하다. 기록이 없는 역사적 원인은 미확인으로 유지한다.

## 4. R1 — 체계가 실제로 좋아졌는지 판단할 평가 기반

### R1-1. 기존 평가 틀을 확장하되 또 다른 프레임워크를 만들지 않는다

`evaluation/ready-verification/`을 먼저 재사용한다. 이 틀은 실제 Probe → Verify 에이전트 결과와 단위/runtime 테스트의 역할을 구분하고, 정답 정보를 검증자에게 주지 않도록 설계되어 있다. [S7]

평가 범위는 최종 검증자만이 아니라 세 가지로 나눈다. 약한 기획이 생성되는지를 보는 기획 평가, 실제 경로를 만드는지를 보는 구현 평가, 잘못된 증거를 거절하고 정상 제품을 통과시키는지를 보는 검수 평가다. 마지막에는 처음부터 끝까지 연결한 평가를 둔다. 세 분야에 별개의 평가 플랫폼을 만들 필요는 없다.

### R1-2. 채점기의 판별 한계를 먼저 보완한다

현재 `score_result.py`는 오합격, 정상 사례 거절, 잘못된 verdict 형식, 보고된 대상 변경, 누락 사례를 release 조건에 사용한다. 그러나 결함 사례의 `FAILED`와 `INCONCLUSIVE`를 정확히 구분했는지는 그 조건에 직접 들어 있지 않다. 코드상 정상 사례만 `VERIFIED`, 나머지는 모두 `INCONCLUSIVE`로 반환해도 다른 조건을 만족하면 통과할 수 있다. 이는 현재 채점 조건의 논리적 한계이며 실제 에이전트가 그렇게 행동했다는 관찰은 아니다. [S8]

사례마다 허용되는 결론과 그 결론에 필요한 관찰을 평가용 정답으로 정한다. 직접적인 결함 관찰과 증거 부족을 구분하고, 권한 부족만으로 제품 결함을 확정하지 않도록 한다. 모호한 사례는 단일 문자열 정답을 강요하지 않고 정당한 결론의 범위를 정의한다.

기존 기록에 `runtime_trigger_executed: true`가 있다는 것만으로 실제 실행을 증명하지 않는다. 필요한 원시 도구 결과와 대상별 관찰을 표본 확인한다. 이 자료는 리팩터링 실험의 증거이며, 모든 제품에 영구 evidence ledger를 설치할 이유가 아니다.

### R1-3. 사용자 불만을 판별하는 사례를 넣는다

| 사례 | 확인할 행동 | 잘못된 결과 |
|---|---|---|
| Mock 내부는 정상이고 실제 인증은 거절됨 | 실제 실패 또는 접근 불가를 구분하고 전체 성공을 주장하지 않음 | 내부 테스트 통과로 제품 완료 |
| 성공 응답은 왔지만 외부 상태 변화가 없음 | 실제 권위 있는 상태를 확인함 | 응답 코드만으로 효과 완료 |
| 올바른 helper를 실제 진입점이 우회함 | 사용자 진입 경로를 실행함 | source 모양만 보고 합격 |
| 사전조사의 결정적 미확인이 그대로 남음 | 그 조건을 해소하거나 판정을 제한함 | 문서 승인 이후 미확인 소실 |
| 앞 Ticket의 동작을 뒤 Ticket이 깨뜨림 | 변경 영향 범위의 현재 결과를 확인함 | 과거 done 합계로 현재 완료 |
| 제품은 정상이고 실제 경계도 사용 가능함 | 불필요한 보류 없이 완료함 | 무조건 실환경 불확실성을 이유로 중단 |
| 운영자 권한이 필요한 경계 | 승인된 도움·증거 경로를 사용함 | 권한 우회 또는 내부 Mock 대체 |
| 검증 중 소스 변경으로만 결과를 맞출 수 있음 | 원래 대상 판정을 보존하고 수정과 판정을 분리함 | 고친 뒤 원래 대상 VERIFIED |

제어된 평가용 서비스는 검증자의 판단 능력을 시험하는 데 사용할 수 있다. 그러나 그것으로 실제 대상 외부 서비스와의 연동이 성립했다고 주장하지 않는다. 실제 연동 결과를 약속한 후보는 승인된 실제 테스트 대상·환경에서 같은 제품 호출 경로로 확인한다. 운영 환경의 위험한 효과를 강행할 필요는 없다.

### R1-4. 비교 방법과 채택 기준을 결과를 보기 전에 정한다

같은 모델·도구·권한·초기 제품 상태에서 기준선과 후보를 비교한다. 실행마다 상태를 초기화하고 예상 정답이나 결함 설명이 작업자 문맥에 들어가지 않게 한다. 이름·파일 구조가 다른 미공개 변형과 반복 실행을 포함한다. 필요한 반복 수와 허용 편차는 실행 비용·변동성을 확인한 뒤 결과를 보기 전에 고정한다.

핵심 지표는 잘못된 전체 완료, 정상 결과의 부당한 보류, 결함과 증거 부족의 구분, 핵심 현실 경계에 처음 도달하는 시점, 사용자 재검수·재작업이다. 토큰·도구 호출·문서량은 그다음 비용 지표다.

**통과 조건:** 채점기 테스트가 아니라 실제 작업자의 행동을 비교할 수 있다. 알려진 핵심 회귀 사례의 근거 없는 완료는 허용하지 않고, 정상 제품을 막아 오합격 수치만 낮추는 후보도 채택하지 않는다. 유한한 평가의 통과를 일반적인 무오류 보장으로 해석하지 않는다.

## 5. R2 — 완료 의미와 책임 연결부터 바로잡는다

### R2-1. 서로 다른 ‘완료’를 기존 계약 안에서 분리한다

새 lifecycle 상태를 늘리지 않고, 기존 결과가 증명하는 범위를 정리한다. 기획 완료는 요구와 수용 기준의 확정이다. 구현 self-check는 구현자가 확인한 제품 결과다. 프로브 완료는 탐색 종료다. 최종 검증은 해당 범위의 판정이다. 전체 완료는 그 판정들이 현재 사용자 결과를 충분히 덮는 경우에만 가능하다.

`Independent`나 `Operator-assisted`는 증거 획득 주체·경로의 구분이지 실제 성립을 면제하는 분류가 아니다. 실행하지 못한 실제 동작을 `Not independently verifiable`라는 표기로 성공으로 바꾸지 않는다. 반대로 문서·소스·구조 자체가 산출물인 작업에는 불필요한 runtime 실행을 요구하지 않는다.

### R2-2. 중요한 미확인 사항의 해소와 전달을 연결한다

기존 Spec/Ticket의 외부 조건·readback과 기존 인계의 한계를 사용한다. 전체 결과에 필수적인 미확인은 직접 해소되거나, 상위 판정의 범위를 제한해야 한다. 다른 내부 테스트가 더 통과했다고 그 미확인이 소멸하지 않는다.

조사 자료가 제품 정책을 결정할 권한이 없다는 원칙은 유지한다. 다만 관찰된 제약과 미확인이 결론을 제한하는 효력까지 없애지는 않는다. 상위로 돌아가야 하는 것은 사용자 의미를 바꿔야 하는 경우다. 현재 의미 안에서 해결할 구현·검증 방식 선택까지 기획 승인으로 되돌리지 않는다.

### R2-3. Ticket 집계에서 빠질 수 있는 전체 의무를 닫는다

To Tickets에는 한 Ticket이 수용 책임을 갖지 않는 부모 의무를 whole-Goal로 남길 수 있다는 문구가 있고, Adaptive의 현재 Increment 종료에는 done 집계 경로가 있다. [S5]

각 실제 사례에서 모든 중요한 의무가 수용될 자리를 먼저 찾는다. 관련 기존 Ticket의 실제 제품 flow에서 확인할 수 있으면 거기에 둔다. 여러 변경이 결합되어야 드러나는 의무는 기존 검수 책임 안에서 현재 통합 결과를 판단할 위치를 명시한다. 테스트를 위한 별도 제품 기능이나 형식적인 Ticket을 만들어 빈칸을 채우지 않는다.

Outer Main은 판정을 다시 만드는 두 번째 검증자가 되지 않는다. 다만 받은 결과가 전체 완료 주장에 충분한지, 빠진 의무나 미해결 제한이 없는지 확인하는 책임은 가진다. 실제 판정이 필요한 잔여 의무는 기존 검수 책임으로 보낸다. 책임을 지정하지 못한 의무가 있으면 집계만으로 제품 완료를 선언할 수 없다.

뒤의 변경이 앞의 결과를 무효화할 수 있는 범위는 현재 통합 결과로 다시 확인한다. 관련 없는 모든 flow를 매번 처음부터 재실행하지 않는다.

**주요 수정 후보:** `iis-adaptive-planning/references/08-delivery-continuation.md`, `09-run-contract.md`, `07-terminal-report.md`, `matt/skills/to-tickets/SKILL.md`, 검증 결과 계약.

**통과 조건:** Ticket 외부 의무, 뒤 변경으로 깨진 앞 결과, 운영자 증거 누락, 제한적 판정이 전체 성공으로 확대되는 사례를 모두 정확히 구분한다. 이 단계는 단계 수를 줄이기 전에 완료되어야 한다.

## 6. R3 — 기획 파트의 리팩터링

### R3-1. 조사·Scope·Matt의 반복을 ‘서로 다른 결정’으로 정리한다

사전조사는 현재 사실과 미확인을 제공한다. Scope는 지금 만들 하나의 의미 있는 결과를 고른다. Matt는 그 결과의 제품 정책과 확인 조건을 결정한다. 이 구분에 맞지 않는 반복 조사는 줄인다.

현재성에 영향을 주는 변화가 없다면 이미 확인된 사실을 다시 넓게 탐색하지 않는다. 새 결정에 필요한 사실, 달라진 경계, 반례가 생긴 부분만 확인한다. ‘보고서를 믿지 말라’를 매 단계 전체 재조사로 구현하지 않고, 중요한 근거의 귀속과 현재성을 확인하는 데 한정한다.

범위는 작게 하되 결과를 가짜로 축소하지 않는다. 실제 외부 반영이 요청인데 응답 처리 함수만 납품하는 식의 기술 조각을 제품 Increment로 위장하지 않는다. 다만 사용자가 명시적으로 라이브러리·문서·코드 납품을 요청한 경우에는 그 산출물의 올바른 경계를 사용한다.

### R3-2. Behavior는 의미를 유지하면서 분석량을 바꾸는 후보를 비교한다

현재 모든 기획 단위의 동일한 전체 절차를 기준선으로 둔다. 비교 후보는 기존 권위의 재사용을 우선하고, 변경되거나 영향을 받는 행동 의미를 중심으로 분석하는 방식이다. [S4]

이를 ‘쉬운 작업은 대충 한다’는 예외 목록으로 만들지 않는다. identity·소유권·상태 전이·실패 복구·동시성처럼 결과에 영향을 받는 축은 분석하고, 영향을 받지 않는 기존 권위는 재설계하지 않는다. 작은 코드 변경이라도 실제 행동 범위가 넓으면 분석도 넓어져야 한다.

기존 권위 재사용, 제한된 행동 변경, 핵심 lifecycle 변경을 각각 비교한다. 후보가 중요한 정책 누락이나 상충 결과를 더 많이 허용하면 채택하지 않는다. 단순히 짧아졌다는 이유로 성공 처리하지 않는다.

### R3-3. Spec/Ticket은 우선 유지하되 투영 중복부터 줄인다

첫 리팩터링에서 Spec과 Ticket을 합치지 않는다. 기존 소비자와 이력·validator의 영향이 크기 때문이다. 먼저 같은 제품 의미를 여러 곳에서 독립적으로 다시 작성하는 부분을 줄이고, 투영 검토가 실제 누락·왜곡을 잡도록 만든다.

문구 포함 여부만 검사하는 테스트는 용도대로 유지하되 전체 품질 증거로 사용하지 않는다. 부모의 실제 외부 효과가 하위의 내부 응답 처리로 약화되는 예제, 미확인 환경이 Existing으로 바뀌는 예제, 서로 결합되지 않는 Ticket 예제를 추가한다. 구조 validator는 참조·스키마를, 행동 평가는 의미 보존을 검사한다.

**주요 수정 후보:** `scope-shaper/SKILL.md`, `matt/skills/ask-matt/SKILL.md`, `behavior-design-lead/SKILL.md`, `matt/skills/to-spec/SKILL.md`, `matt/skills/to-tickets/SKILL.md`, 관련 계약·validator 테스트.

**통과 조건:** 기획 경로가 줄어도 중요한 제품 결정과 외부 미확인이 보존된다. 새로운 외부 조건을 발견하지 않고 같은 내용을 다시 쓰는 비용은 줄어든다. Behavior 분석량 조정은 비교 결과가 나올 때까지 채택 미정으로 남긴다.

## 7. R4 — 구현 파트의 리팩터링

### R4-1. 핵심 전제를 확인하는 시점을 앞당긴다

제품 성립을 좌우하는 전제가 있는데 내부 코드만 계속 쌓는 패턴을 줄인다. 구현자는 초기 제품 경로를 추적해 자신이 만드는 부분, 이미 존재하는 부분, 외부가 소유하는 부분과 실제 readback을 구분한다.

가능한 경우 위험이 큰 경계를 작은 정상 경로로 일찍 확인한 뒤 나머지를 확장한다. 이는 ‘항상 외부 호출부터 한다’는 규칙이 아니다. 비용·권한·부작용·현재 제품 상태에 맞춰, 뒤늦게 틀리면 작업 전체가 무의미해지는 전제를 우선 다룬다는 방향이다.

자격증명이나 운영자 행동이 필요하다면 정확한 기존 경로를 사용한다. 권한이 없다는 이유로 Mock으로 바꿔 제품 성공을 주장하거나, 권한을 우회하지 않는다. 별도 승인 없이 진행 가능한 내부 구현은 이어갈 수 있지만, 최종 주장 범위는 그 제한을 넘지 않아야 한다.

### R4-2. self-check를 실제 제품 경로에 연결한다

내부 단위 테스트는 분기와 실패 처리를 지원한다. 제품 self-check는 실제 진입점에서 필요한 외부·상태 경계를 거쳐 결과를 확인한다. 성공 응답을 받은 것과 상태 변경이 완료된 것은 구분한다.

기존 handoff에는 실제 확인한 경로, 관련 결과, 남은 한계의 연결을 남긴다. 별도 인증서나 매번 새로운 evidence 문서를 요구하지 않는다. 프로브·검증이 독립적으로 확인할 책임이 있다는 이유로 구현자의 실제 동작 확인을 생략하지 않는다.

실제 경로 없음, 실제 경로의 결함, 환경 때문에 미확인을 구분한다. 요청이 명시적으로 코드 산출물에 한정된 경우와 실제 동작하는 제품을 약속한 경우도 구분한다. 필요한 self-check가 닫히지 않은 제품 작업을 기존 COMPLETE로 과장하지 않는다.

### R4-3. runtime의 ‘성공 관찰’과 제품 증거를 혼동하지 않게 정리한다

현재 성공 observation이 최신 evidence revision을 갱신하고, 구현 종료는 수정 revision과의 일치를 확인한다. 이 조건은 관찰의 존재·현재성이지 해당 제품 의무의 충분성 증명이 아니다. [S9]

우선 이 장치가 제공하는 보장과 이름·보고 해석을 일치시킨다. 단순 조회가 제품 self-check를 대신한 것처럼 보이는 성공 경로를 회귀 사례로 둔다. 제품 의미를 범용 runtime에 모두 집어넣거나, 체크박스 제출만으로 증거가 생기는 새 가드를 만들지 않는다.

이 가드의 수정·유지·제거는 실제로 어떤 관찰 누락을 막는지 확인한 뒤 결정한다. R4에서는 구현 완료의 의미와 인계를 먼저 바로잡고, 넓은 runtime 감량은 R6에서 수행한다.

**주요 수정 후보:** `companion-skills/ready-ticket-implement/SKILL.md`, `references/implement.md`, `delivery-runtime/ready-ticket-implement/src/observation-ledger.js`, `lifecycle.js`의 관련 경계와 테스트.

**통과 조건:** 실제 경로가 빠진 구현을 완료로 넘기지 않는다. 정상 외부 경로가 가능한 사례는 과도하게 중단하지 않고 완성한다. 핵심 경계의 발견이 검증 마지막까지 미뤄지지 않는지 기준선과 비교한다.

## 8. R5 — 검수 파트 재구성과 프로브의 존치 결정

### R5-1. 검수의 중심을 ‘구분 가능한 관찰’에 둔다

기존 verifier가 이미 요구하는 `Nearest nonconforming state`, `Discriminating observation`, `Sensitivity activation`을 또 다른 양식으로 복제하지 않는다. 그 필드가 실제 시나리오를 바꾸고 있는지 평가한다. [S2]

핵심 질문은 ‘정상 제품과 가장 가까운 실제 실패 상태가 현재 관찰에서 다르게 나타나는가’다. 실제 인증을 제거해도 같은 합격이 나오는 테스트는 인증의 증거가 아니다. source에 올바른 분기가 있어도 실제 진입점이 우회하면 제품 증거가 아니다.

검증자는 제품이나 승인된 조건을 바꿔 합격을 만들지 않는다. 관찰된 모순, 증거 부족, 계획 계약의 결함을 구분하고, 이미 있는 수정·재진입 경로로 전달한다. 하나의 판정 사이클에서 수정과 합격 판단을 섞지 않는다.

### R5-2. 프로브는 ‘유지’와 ‘검수 내부 통합’을 비교한다

비교 A는 현재 별도 프로브와 verifier 구조다. 비교 B는 verifier가 탐색과 판정의 기능을 모두 수행하되, 탐색 중 발견한 반례를 버리지 않고 관찰과 판정을 명확히 구분하는 구조다. 처음부터 복잡한 위험 점수 기반 선택기를 추가하지 않는다.

별도 프로브가 어떤 결함군을 추가로 발견하는지, verifier가 같은 경계를 다시 세팅·실행하는 비용이 어느 정도인지, 통합 시 공유 가정과 편향이 늘어나는지를 평가한다. worker 수를 늘려 단순히 투표하게 하지 않는다. 실행 방식은 현재 허용된 DIRECT를 기준으로 비교하고, SUBAGENT는 사용자가 해당 실험에 명시적으로 선택한 경우에만 별도 비교한다.

통합은 비용이 줄고 의미 있는 발견·정상 완료·근거 있는 판정이 보존될 때만 채택한다. 효과가 불명확하면 프로브를 우선 유지하고 중복 설명·인계만 줄인다. 독립 탐색의 효과가 특정 작업에서만 뚜렷하다면 이후에 좁은 선택 기준을 검토한다. 그 기준을 먼저 발명하지 않는다.

### R5-3. 통합한다면 관련 계약을 한 묶음으로 바꾼다

정상 verifier는 현재 terminal Probe result와 machine binding을 필수로 요구한다. 따라서 스킬 삭제만으로는 통합되지 않는다. [S2]

통합을 선택한 경우 `ready-ticket-heuristic-probe`, `ready-ticket-verify`, Adaptive delivery route, runtime의 `probe-handoff.js`와 `begin_verify`, 설치 호환성 검사, 평가 실행 경로, 관련 테스트를 함께 수정한다. 프로브 절차만 끊고 binder를 형식적으로 생성하는 우회는 하지 않는다.

binding에서 제거할 수 있는 것은 폐기한 프로브 단계의 증명이다. 대상·권위의 현재성 보호는 별개이므로 verifier의 자체 binding으로 유지한다. 이 기능이 무슨 보장을 제공하는지에 따라 분리한다.

**주요 수정 후보:** 두 검수 스킬과 reference, `iis-adaptive-planning/references/08-delivery-continuation.md`, `delivery-runtime/ready-ticket-implement/src/probe-handoff.js`, `omp-adapter.js`, 관련 계약·runtime·평가 테스트.

**통과 조건:** 불량 제품을 놓치지 않으면서 정상 제품을 계속 완료할 수 있다. 프로브를 없애도 된다는 결론은 비교 근거가 있을 때만 낸다. 최종 판정의 증거 범위와 R2의 전체 완료 책임이 유지되어야 한다.

## 9. R6 — runtime 감량과 실제 적용 경로 정리

### R6-1. 안전·무결성 보호와 효율 정책을 분리한다

정확한 대상과 권위, 보호 파일의 무단 변경 방지, 검증 중 대상 변경, 중복·불확정 외부 효과, 관리 서비스 정리 같은 기능은 구체적인 실패와 연결된다. 성능이나 코드량 때문에 일괄 제거하지 않는다.

반복 조회 차단, 광범위 조사 제한, 관찰 revision, 다단계 보고와 체크포인트는 각자의 실제 기여를 평가한다. 비용 절감 정책이 필요한 현재 상태 관찰을 막거나, 형식 수행이 제품 증거처럼 해석되면 축소·분리 후보가 된다.

source revision이 같아도 외부 인증·작업 완료·서버 상태는 달라질 수 있다. 따라서 소스 정적 읽기의 재사용 정책을 외부 runtime readback의 현재성으로 확대하지 않는다. 현재 검증 실행에 REFRESH 경로가 있다는 점도 보존하여 일괄 비판하거나 제거하지 않는다. [S10]

### R6-2. 필요한 보호를 작게 검증한다

보호별로 실제 차단해야 할 동작과 정상 허용 동작을 짝으로 시험한다. 예를 들어 잘못된 root 쓰기는 막되 승인된 일회성 제품 상태 변화는 허용해야 한다. 검증 중 source 변경은 막되 정상 제품 flow가 만드는 선언된 출력은 허용해야 한다.

효율 정책을 제거하는 후보도 한 번에 하나의 실패 경로에 연결해 비교한다. 오류나 재시도가 늘었다면 이름을 바꿔 같은 정책을 되살리는 대신 어떤 제한이 필요한지 좁힌다. 일반 조회 성공을 self-check 성공으로 취급하는 모호함을 남기지 않는다.

### R6-3. 지원 호스트에서 실제 호출 경로를 확인한다

스킬 발견 → canonical 진입 → 가드 시작 → 도구 실행 → 최종 결과까지 현재 실제 사용 호스트에서 연결한다. OMP extension이 설치됐다는 사실을 다른 호스트에서도 같은 보호가 있다는 뜻으로 확대하지 않는다.

필요한 호스트만 지원 범위로 정하고, 지원이 부족한 경로는 명시한다. 이를 해결한다는 이유로 범용 어댑터 플랫폼이나 새로운 controller를 만들지 않는다. 보호가 필요한 실행을 아무 설명 없이 비보호 fallback으로 전환하지 않는다.

**주요 수정 후보:** `delivery-runtime/ready-ticket-implement/src/`의 해당 모듈과 테스트, `scripts/sync_installed_ready_runtime.py`, 스킬 진입·설치 문서.

**통과 조건:** 줄인 후보가 실제 보호 동작을 유지하고 정상 작업을 불필요하게 차단하지 않는다. 설치 일치, 세션 로드, 실행 적용을 각각 확인한다.

## 10. R7 — 전체 검증, 호환 전환, 롤백

### R7-1. 단계별 테스트를 넘어 전체 결과를 확인한다

기획에서 약한 요구가 나왔는데 검증자가 뒤늦게 전부 거절하는 후보는 기획 개선으로 통과시키지 않는다. 구현이 계속 잘못된 것을 만들고 검수만 정확해진 후보도 전체 목적을 달성한 것으로 보지 않는다.

사용자 요청부터 기획·구현·검수·최종 보고까지 연결하여 정상 제품 완성, 의도된 외부 경계, 미확인 사항 처리, 수정 재진입, 전체 결과의 현재성을 확인한다. 평가용 도구가 생성한 정답을 제품 증거로 다시 읽는 순환을 막는다.

문서·schema·unit/runtime 회귀, 실제 에이전트 비교, 승인된 실제 제품 경계 확인은 서로 다른 증거로 보고한다. 기존 전체 테스트의 실패가 있다면 기준선과 신규 회귀를 분리한다. 실패한 필수 기능을 unrelated baseline 문제로 감추지 않는다.

### R7-2. 기존 산출물과 호출 호환성을 유지한다

초기 변경에서는 공개 진입 이름·canonical path·Ticket status·기존 Spec/Ticket 형식을 가능하면 유지한다. 꼭 필요한 형식 변경은 확인된 의미적 필요가 있을 때만 수행하고 작성자·reader·validator·설치본을 함께 전환한다.

완료된 Ticket은 역사적 산출물로 보존한다. 신규 규칙에 맞추려고 과거 PASS나 done을 조용히 수정하지 않는다. 진행 중인 산출물이 영향을 받으면 해당 작업의 권위 아래 필요한 범위만 재확인하고, 일괄 승인·일괄 draft 전환으로 상태를 맞추지 않는다.

활성 세션 중간에 스킬·runtime 조합을 교체하지 않는다. 격리된 후보를 검증한 뒤 맞는 묶음으로 전환하고 새 세션에서 실제 진입을 확인한다. 파일 동기화 성공을 제품 검증 성공으로 기록하지 않는다.

### R7-3. 롤백 조건과 대상 묶음을 미리 고정한다

새로운 근거 없는 완료, 정상 사례의 의미 있는 보류 증가, 보호 우회, 지원 호스트의 진입 실패, 기존 산출물 오해석이 나타나면 해당 변경 묶음의 채택을 중단한다.

롤백은 호환되는 스킬·runtime·설치 설정 조합으로 수행한다. 사용자 제품 변경이나 무관한 작업 트리를 강제 초기화하지 않는다. 이미 발생했을 수 있는 외부 효과는 코드 롤백과 별도로 현재 상태를 확인한다. 실험 결과와 실패 기록은 지우지 않는다.

### 최종 채택 기준

| 기준 | 요구하는 증거 |
|---|---|
| 근거 없는 제품 완료 방지 | 핵심 회귀 사례와 변형·반복 평가에서 오합격이 없고 실제 관찰이 뒷받침됨 |
| 정상 제품 완성 | 기준선 대비 부당한 보류·사용자 재검수·불필요한 재작업이 악화되지 않음 |
| 정확한 판단 | 구현 결함·계약 결함·환경/권한 부족·증거 부족을 적절히 구분함 |
| 전체 책임 연결 | 개별 Ticket 완료 밖에 중요한 의무나 현재성 문제가 방치되지 않음 |
| 단순화의 실익 | 의사결정·증거 수집을 보존하면서 반복 분석·인계·통제가 실제로 감소함 |
| 적용과 복구 | 지원 호스트의 실제 경로, 기존 자료 호환성, 롤백 가능성이 확인됨 |

평가 결과가 엇갈리면 ‘리팩터링 완료’로 묶지 않는다. 통과한 변경만 채택하고, 프로브 통합이나 Behavior 감량처럼 근거가 부족한 선택은 보류한다.

## 11. 무엇을 남기고, 무엇을 줄이며, 무엇을 아직 건드리지 않을 것인가

| 분류 | 대상 | 방향 |
|---|---|---|
| 보존할 보장 | 사용자 제품 의미, 실제 확인 경계, 외부 행동 권한, 검증 대상 무결성 | 형태가 바뀌어도 보장 자체는 유지 |
| 우선 정리 | 동일 권위·제품 의미의 반복 서술, 새 사실 없는 인계·재조사, 성공 관찰의 과장된 해석 | 기존 위치에 통합·축소하며 의미를 보존 |
| 비교 후 결정 | 전체 Behavior 절차, 프로브 독립 단계, 일부 체크포인트·효율 가드 | R1 결과로 선택하고 불확실하면 현행 유지 또는 작은 정리만 채택 |

| 만들지 않을 것 | 새 총괄 검증자, 범용 controller, 제품별 영구 evidence DB, 점수 기반 역할 배정 체계 | 기존 문제를 또 다른 운영 계층으로 덮지 않음 |

현재 시스템 전체를 폐기하고 다시 작성하는 방식은 권하지 않는다. 무엇이 효력을 냈는지 모르는 상태에서 모두 바꾸면 인과를 확인할 기준선과 이미 있는 실질 보호를 동시에 잃기 때문이다. 반대로 기존 구성을 보존하는 테스트가 있다는 이유로 불필요한 구조를 남기지도 않는다.

## 12. 실행을 시작할 때의 첫 변경 묶음

첫 묶음은 운영 스킬 대수술이 아니라 **격리·사건 근거·행동 평가**다. 실제 사건의 최초 근거 없는 성공 지점을 정리하고, 정상 제품과 결함·증거 부족을 구분하는 평가를 만든 뒤 현행 조합으로 기준선을 얻는다. 문구 검사와 실제 성능 증거를 분리한다.

두 번째 묶음은 **완료 의미와 전체 의무의 책임 연결**이다. 누가 어느 범위에서 어떤 사실을 확인해야 하는지를 기존 계약 안에서 닫는다. 이 연결이 없는 상태에서 프로브나 보고를 먼저 없애지 않는다.

세 번째부터는 **기획·구현·검수 각각의 작은 후보를 비교**한다. 한 후보가 실패하면 다른 곳에 보완 계층을 추가하기 전에 그 후보의 목적과 인과 경로를 다시 확인한다.

최종 방향은 **‘많은 단계가 서로 완료를 확인하는 체계’에서 ‘필요한 실제 사실을 확보하고, 그 사실이 뒷받침하는 범위에서만 완료를 선언하는 체계’로 이동하는 것**이다. 절차를 줄이는 것은 그 이동의 결과여야 하며, 핵심 사실을 놓친 채 문서만 짧게 만드는 일이 되어서는 안 된다.
