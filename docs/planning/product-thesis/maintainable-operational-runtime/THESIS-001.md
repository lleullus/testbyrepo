## Reason to Exist

Oracle Browser의 효용은 “브라우저가 한 번 답했다”가 아니라, 사용자가 상담을 맡기고 나면 **의도한 실행 환경·대화·턴의 결과를 믿고 회수할 수 있다**는 데 있다. Python 슬롯 래퍼, Node Oracle, Linux Chrome/CDP, 외부 ChatGPT UI가 연결된 시스템에서 한 계층의 성공만으로는 이 효용이 성립하지 않는다.

현재 개인 NVM 경로와 외부 패키지 내부 모듈에 연결된 실행은 설치 위치가 바뀌면 깨질 수 있다. 에이전트가 매번 버전·시간 제한·드라이런을 보완해야 한다면 일반 사용자와 스케줄러는 같은 보호를 받지 못한다. 복구가 이전 완료 턴을 현재 답변으로 반환하면 긴 정상 실행보다 더 나쁜 결과, 즉 신뢰할 수 없는 성공을 만든다. 상태 파일이 여러 곳에 있다는 설명만으로는 급사 직후 중복 제출이나 오염된 슬롯 재사용이 차단되지 않는다.

따라서 제품 존재 이유는 **개인 환경과 숙련자의 간병을 제거하고, 지원 환경에 옮겨도 같은 실행·귀속·실패 계약을 자체적으로 지키는 런타임**을 제공하는 것이다. 의존성 지도와 운영 문서는 보조 수단이다. 완성도는 도구가 책임을 수행하는지로 판정하며 패키징 파일 생성 여부로 판정하지 않는다.

## Core Utility

사용자는 정상적인 설치·필수 설정·로그인을 마친 지원 환경에서 동일한 CLI로 상담을 시작하고 이어가며 중단된 결과를 회수한다. 에이전트 전용 지침을 주입하지 않아도 다음 약속이 유지된다.

- 개인 홈 디렉터리, NVM 버전 폴더, 개발 체크아웃을 복제하지 않아도 제품 실행 단위가 해석되고 작동한다.
- 요청한 모델/Power, 첨부 집합, 대화 및 원 슬롯이 제출과 결과까지 보존된다.
- 현재 요청의 완결된 답변이라는 증거가 있으면 결과를 회수하고, 증거가 없으면 미확정 또는 실패를 받는다. **“100% 신뢰”는 모든 요청의 성공이나 AI 답변 내용의 사실성을 보증한다는 뜻이 아니라, 다른 턴·불완전한 답변·미검증 실행을 성공으로 꾸미지 않는다는 뜻이다.**
- 실패해도 중복 제출, 다른 요청의 점유 해제, 조용한 컨텍스트 이동이 발생하지 않는다. 사용자에게 남은 결과와 필요한 조치가 구별되어 보인다.

“어디서나”의 적용 경계는 우선 Linux/WSL2의 선언된 지원 환경이다. OS·Chrome·계정/로그인·네트워크·외부 ChatGPT 가용성까지 제품 안에 복제한다는 의미가 아니다. 이러한 전제는 명시되고 도구가 실행 전에 판정한다. 지원 전제가 충족된 다른 머신/사용자/설치 경로에서 개인 설정을 복사하지 않고 재현 가능해야 한다.

## Behavior and Product Policy

### 1. 런타임 자기완결성과 설치 계약

- 제품 소유 코드와 파일 선택·첨부·브라우저 실행 구성은 하나의 호환 실행 단위로 공급되고 해석되어야 한다. `CANONICAL_ORACLE_CLI`의 개인 절대 경로와 외부 NVM의 비공개 `dist/src/oracle/files.js` 탐색은 허용되는 영구 정책이 아니라 제거해야 할 결손이다.
- Node/Python/Chrome 같은 선언된 플랫폼 전제는 허용한다. 특정 사용자의 설치 구조나 개발 소스는 전제가 아니다. 필요한 버전/기능이 충족되지 않으면 실행 전에 원인을 보여주고 제출하지 않는다.
- `0.16.1`은 조사 시점의 호환 기준이다. 버전 문자열 하나를 영구 고정하는 것이 아니라 릴리스가 함께 제공·지원하는 구성의 정합성을 도구가 확인해야 한다. 이름이 같은 다른 CLI, 다른 파일 선택기 또는 오래된 실행물로 조용히 대체하지 않는다.
- 설치 위치와 사용자별 데이터 위치를 구별한다. 다른 홈/설치 경로에서 생성한 세션·프로필은 해당 사용자 소유로 유지하며, 배포물에 기존 쿠키·프로필·비밀정보를 포함하지 않는다.

### 2. CLI 내장 보호

- `run`, `submit`, `followup` 및 제품이 제공하는 recovery 진입 경로는 동일한 안전 계약을 적용한다. “SKILL.md를 읽었어야 한다”는 실패 원인을 제품 안전성의 면책으로 삼지 않는다.
- 브라우저 응답 대기의 기본값은 `2h`다. 명시적 사용자 시간 제한은 보존하고 실제 적용값을 드러낸다. 큐 대기·사전 준비·정리를 응답 대기와 혼동하지 않으며, 외부 스케줄러가 프로세스를 먼저 종료하더라도 중복 제출이나 거짓 성공이 발생해서는 안 된다.
- 사전 버전/호환성 확인, 인자/라우팅/첨부 검증은 CLI가 자동 수행한다. 사용자가 별도 dry-run을 한 번 더 호출하는 것이 안전한 실실행의 필요조건이면 안 된다. 별도 preview는 계획을 보여주는 선택적 인터랙션이며 절대로 제출하지 않는다.
- 외부 UI 준비 여부 등 시점에 따라 달라지는 사실은 실제 제출 경계에서 다시 확인한다. 과거 dry-run 성공이 현재 로그인·모델·첨부 완료를 대신하지 않는다.
- 사용자의 파일 선택 의도는 보존하며 파일 요청에 대해서만 단일 압축 ZIP을 만든다. 빈 ZIP, 선택 실패를 빈 성공으로 변환하거나 원본 파일 다중 업로드로 조용히 우회하지 않는다. 첨부가 없는 요청에 인위적인 ZIP을 강제하지 않는다.

### 3. 라우팅·반복·대화 연속성

- 명시 `run`은 지정 슬롯을 즉시 시도하며 점유/사용 불가면 거절한다. `submit`은 요청 capability에 맞는 슬롯 집합에서 기존 FIFO와 상대 우선순위를 유지한다. Pro 세 선택은 `(1,2,10)`, 자동 상대순서는 `1 → 2 → 10`이다. 이 Thesis는 다른 capability의 기존 라우팅을 변경하지 않는다.
- `followup`은 `oracle_browser_slots.originating_slot`의 슬롯·프로필·대화에 고정한다. 다른 슬롯이 비어도 이동하지 않는다. 보관된 대화의 복원이 필요하면 동일 대화임을 확인한 뒤 이어가며 대체 대화를 만들지 않는다.
- `running` 부모 또는 child 종료를 입증하지 못한 부모를 곧바로 새 followup 대상으로 삼지 않는다. 중단 요청의 기존 턴 수거와 다음 턴 제출은 다른 작업이다.
- 같은 `request_id`는 새 외부 실행을 만들지 않는다. 기존 중복 거절 의미를 유지하며 저장 결과 조회와 요청 재실행을 구분한다. 예약을 시간 경과만으로 지워 중복 실행을 허용하지 않는다.

### 4. 원자적 상태와 닫힌 수명주기

- `slot-N.lock`, `slot-N.json`, `allocator.lock`, `allocator-queue.json`, `allocator-requests/`, 세션 `meta.json`은 동일한 사실을 아무 파일이나 대표하는 체계가 아니다. 예약/큐는 접수와 순서, 슬롯 상태는 점유, 브라우저 관찰은 원격 제출/턴, 세션 자료는 결과 및 lineage의 근거다.
- 점유의 승인·해제는 동시 호출에서 원자적이어야 한다. owner는 PID 숫자만이 아니라 재사용을 구분하는 identity를 가져야 한다. 기존 `job_id`, `owner_pid`, `owner_starttime`과 `finish_job`의 소유자 대조가 이 요구의 소스 앵커다.
- 내구 저장이 중간에 실패하면 부분 파일이나 서로 모순된 상태를 성공으로 읽지 않는다. 여러 파일을 하나의 분산 트랜잭션으로 만든다고 가정하지 않고, 충돌/불완전 상태에서는 후속 실행을 승인하지 않는 결과를 보장한다.
- SIGKILL/OOM 등으로 정상 해제가 생략되면 다음 조회/claim 경계에서 소유자 소실을 판정하고 `requires_reprepare=True`, `UNAVAILABLE`로 격리한다. 전용 상시 감시 서비스 없이도 새 작업의 진입은 차단되어야 한다.
- `prepare --slot N`은 격리를 해제하는 명시적 경계다. 기존 활성 실행을 침범하지 않고 브라우저·로그인 및 잔여 실행 상태를 확인한 뒤에만 다시 사용할 수 있다. 일반 사용자가 상태 JSON이나 lock 파일을 수작업으로 고치는 것은 정상 복구 절차가 아니다.
- 결과 완료와 후처리는 구분한다. 답변은 확정됐지만 ZIP 정리/점유 해제가 실패했다면 답변을 보존하고 해당 후처리 실패 및 슬롯 격리를 노출한다. 전체 정상 완료로 위장하거나 답변을 지우고 다시 제출하게 하지 않는다.

### 5. 제출 및 결과 귀속: Zero False Success in Recovery

- `promptSubmitted=true`는 현재 코드상 전송 동작 뒤 기록되는 힌트다. 원격 사용자 턴 커밋의 충분조건이 아니며, `false`/필드 부재도 급사 구간에서 미제출의 증명이 아니다. 전송 직후 기록 직전에 죽을 수 있다는 경계를 제품이 책임진다.
- 확실한 제출 전 거절, 전송되었을 가능성이 있는 미확정, 사용자 턴 커밋 확인을 구별한다. 불확실하면 자동 재제출하지 않는다. exactly-once 원격 전송을 로컬 플래그 하나로 보장한다고 주장하지 않는다.
- 성공에는 동일 conversation, 현재 요청의 고유 사용자 턴, 그 턴의 답변인 고유 어시스턴트 턴, 완결 상태의 결합 증거가 필요하다. `answer.turn_index > prompt.turn_index`만으로는 그 뒤의 다른 사용자 요청 답변을 배제할 수 없으므로 충분하지 않다.
- `reattach`는 비제출 수거다. 기존 Chrome 연결과 새 Chrome 복구 모두 현재 턴 증거를 복원해 적용해야 한다. 짧은 prompt preview, 비슷한 텍스트, 마지막 완료 메시지, copy 버튼 존재만으로 귀속을 대체하지 않는다.
- 증거가 없거나 동일 문구의 복수 턴 때문에 식별이 모호한 오래된 세션은 자동으로 성공 처리하지 않는다. 미확정/실패와 원인을 반환하고 기존 자료를 보존한다. 보수적 거절은 허용하지만 이전 턴 반환은 허용하지 않는다.
- 늦게 도착한 응답이나 복구 호출은 다른 요청의 결과를 덮어쓰거나 다음 턴의 답변을 선점하지 않는다. 동일 세션을 복수 수거자가 다루어도 결과 확정과 슬롯 소유권 계약을 우회하지 않는다.

## UI and Interaction

제품의 주요 인터페이스는 CLI와 저장 결과이며, 외부 ChatGPT 웹 UI는 실제 실행의 관찰 경계다. 자체 대시보드 구축은 필요조건이 아니다.

- CLI는 요청/세션 식별자, 배정 슬롯, 대기·실행·제출 미확정·응답 확정·후처리 실패를 구별해 보여준다. `operator_action`은 실행 가능한 조치이며 안전성을 사용자의 기억에 맡기는 대체 코드가 아니다. 정상 성공 출력과 성공 종료 코드는 미확정/거절/격리를 숨기지 않는다.
- 외부 UI의 로그인 요구나 접근 제한은 중단 사유다. 사용자 인증·수동 로그인이 필요할 수 있지만 인증 장벽 우회나 자동 해결을 제품 약속에 넣지 않는다.
- 명시 Pro 선택은 `Latest`, `GPT-5.6 Sol`, `GPT-5.5`의 정확한 checked row와 Power=`Pro`를 결합해 제출 전에 검증한다. `Latest`의 실제 해석값을 기록하되 영구 GPT-6 alias로 만들지 않는다. `6 Pro` 한 문자열이 모든 모델의 검증을 대신하지 않는다.
- 컴포저 입력, 업로드 완료, 전송 시도, 사용자 턴 커밋은 각각 다른 관찰이다. 버튼 클릭 또는 컴포저 비움만으로 현재 턴 생성 성공을 선언하지 않는다.
- 어시스턴트 식별 게이트와 완료 게이트는 별개다. 올바른 턴이라도 `Pro thinking`, `Answer now`, placeholder 또는 스트리밍 중간 내용은 최종 답변이 아니다. 이전 턴에 있는 action/copy 버튼도 현재 턴의 완료 증명이 아니다.
- `Answer now`를 자동으로 누르거나 낮은 모델/Power로 바꾸어 시간을 단축하지 않는다. 정상 수거와 recovery 모두 현재 귀속 턴의 완결된 Markdown을 보존한다.

## Required Outcomes / Means

### Required Outcomes — 사용자 명시 요구

1. **자기완결적 실행**: 지원되는 다른 머신/홈/설치 경로에서 개인 NVM·개발 체크아웃·외부 패키지 내부 파일 의존 없이 동일 효용을 제공한다.
2. **호출자 독립적 보호**: 일반 사용자·에이전트·스케줄러에 같은 기본값, 사전 검증 및 실패 계약을 적용한다. 수작업 버전 확인/timeout 주입/dry-run 선행이 안전성의 전제가 아니다.
3. **결과 귀속의 원천 보장**: 정상과 복구 모두 현재 요청의 완결된 답변만 성공으로 반환한다. 미확정은 미확정으로 끝나며 과거 답변 성공은 없다.
4. **닫힌 수명주기**: 중복 접수, 슬롯 경쟁, 급사, 저장/정리 실패에서도 실행 소유권과 결과를 보존하고 위험한 재진입을 차단한다.
5. **단일 압축 ZIP 보장**: 파일 첨부 요청의 선택된 원본 집합을 하나의 압축 ZIP으로 전달하며 선택·압축·업로드 실패를 숨기지 않는다.

### Required Means — 명시적으로 요구된 보장 방식

- 제품 자체로 완결된 실행 단위와 CLI 안의 보호를 사용한다. 별도 SKILL.md 규율만으로 대신할 수 없다.
- 슬롯 배타 점유, 중복 요청 차단, 급사 후 안전 격리, 첨부 시 단일 압축 ZIP을 제공한다.
- recovery에서도 현재 요청 턴과 어시스턴트의 귀속 검증을 수행하고 근거가 부족하면 fail-closed한다.

### Derived Necessities — 위 결과에서 파생된 필수 조건

- 요청·세션·conversation·사용자 턴·어시스턴트 턴·원 슬롯의 연결 증거를 복구가 사용할 수 있게 보존해야 한다. 메모리의 `identityScope`만으로 프로세스 급사 후 보장을 충족할 수 없다.
- 전송 시도와 원격 커밋을 분리하고 기록 누락 구간을 미확정으로 다뤄야 한다. 플래그 부재를 재시도 허가로 읽으면 중복 제출이 가능해진다.
- 실제 실행 CLI와 첨부 선택기를 같은 호환 구성으로 해석해야 한다. CLI 경로만 바꾸면 독립성은 성립하지 않는다.
- 상태의 원자적 변경·내구성·소유자 확인이 필요하다. 다만 특정 저장 라이브러리, 번들러, 모든 파일에 동일한 fsync 절차를 적용하는 설계는 여기서 필수 수단으로 승격하지 않는다.
- 설치된 실행물에서 결과를 관찰해야 한다. 소스의 단위 검증만으로 실제 배포 런타임의 정합성을 입증할 수 없다.

## Candidate / Supporting Means

다음은 대체 가능한 방법이다. 채택 여부와 세부 설계는 후속 Plan의 책임이며 해당 도구의 존재 자체는 완료 조건이 아니다.

- `doctor`/헬스체크 CLI로 런타임·Chrome·경로·세션 저장소를 한 번에 진단. 실실행의 내장 검증을 대신하지 않는다.

- 릴리스 manifest, 실행물 fingerprint 또는 다른 provenance 증거로 실제 CLI/선택기 정합성을 확인하는 방법.

## Truth / Causal Invariants

1. **슬롯 배타**: 같은 관리 슬롯을 동시에 조작하도록 승인된 활성 소유자는 최대 하나다. 해제는 현재 owner만 수행하며, owner 소실은 자동 가용화가 아니라 격리로 이어진다. `occupancy=null`만으로 `AVAILABLE`을 증명할 수 없다.
2. **컨텍스트 연속**: followup의 `conversationId`와 원 슬롯/프로필은 부모와 같아야 한다. 현재 턴의 모델/Power 검증은 새로 수행한다. 같은 URL만으로 관리 lineage가 생기거나 다른 프로필이 동등해지지 않는다.
3. **제출 증명**: 전송 시도, 커밋 확인, 결과 완료는 서로 다른 사실이다. `promptSubmitted=true`는 커밋의 충분조건이 아니며 필드 부재는 미제출의 충분조건이 아니다. 제출 가능성이 생긴 요청은 원격 결과를 확인하지 않고 자동 재제출하지 않는다.
4. **결과 귀속**: `success ⇒ same conversation ∧ uniquely identified current user turn ∧ assistant owned by that turn ∧ completed response`. 턴 순서, 텍스트 유사성, 기존 완료 상태 또는 마지막 메시지만으로 이 결합을 대체할 수 없다. 정상·reattach·새 Chrome·늦은 캡처에 예외가 없다.
5. **빌드-바이너리 일체성**: 실제 실행한 CLI와 파일 선택·브라우저 동작 코드는 선언된 동일 호환 릴리스/구성에 속한다. 수정 소스의 결과를 개인 NVM의 오래된 `dist` 실행 결과로 대신 주장하지 않는다. 설치물의 실제 경로와 정체성이 제품 실행의 근거다.

## Success Observation

아래는 **제품 완성도를 판단할 관찰 기준**이다. 이번 문서 작성에서 실행하거나 통과시킨 시나리오가 아니다. stdout의 `completed` 한 줄이 아니라 원격 턴 관찰, 저장된 세션/답변 및 슬롯 종료 상태를 함께 읽어야 한다.

### A. 다른 지원 환경에서 정상 실행

개인 NVM 폴더와 개발 체크아웃이 없는 별도 사용자/설치 경로에서 선언된 플랫폼 전제와 로그인만 준비한다. 에이전트의 버전 확인·timeout 주입·사전 dry-run 없이 CLI를 호출한다. 실행 구성과 기본 `2h`가 해석되고, 파일 요청은 정확한 선택 집합의 단일 ZIP으로 업로드되며, 모델/Power와 현재 턴의 답변이 확인된다. 저장 결과를 다시 읽을 수 있고 정상 해제 뒤 슬롯을 재사용할 수 있다. 첨부 없는 요청도 같은 계약으로 동작한다.

**반례**: CLI만 실행되고 첨부는 원 작성자의 NVM `files.js`가 없어서 실패하는 설치, 경로를 맞추기 위해 개인 홈 symlink를 요구하는 설치, 스킬을 읽은 에이전트만 성공하는 호출은 자기완결성 달성이 아니다.

### B. 다중 턴 중단과 비제출 복구

동일 대화에 완료된 턴 A와 새 요청 턴 B가 있고 B 제출 뒤 연결이 끊어진다. 복구는 B의 커밋/귀속 증거를 사용해 B의 답변만 회수한다. 기존 Chrome과 재개방 경로 모두 같은 조건을 만족한다. B가 아직 없거나 귀속 증거가 유실되면 미확정/실패로 끝나고 원격 prompt 수는 증가하지 않는다.

**강한 반례**: A와 B의 prompt가 같거나 앞 120자가 같음, B가 렌더링되지 않음, A만 copy 버튼을 가짐, 이후 턴 C의 답변이 더 최신임. 이때 A 또는 C를 B의 `completed`로 저장/반환하면 Zero False Success 실패다. 미확정 거절을 오류율 때문에 성공으로 바꾸지 않는다.

### C. 전송과 저장 사이 급사

전송 동작 직후 `onPromptSubmitted` 또는 커밋 증거 저장 전에 프로세스가 죽은 경우, 플래그 부재를 미제출로 판정하지 않는다. 상태는 미확정으로 남고 새 자동 전송은 없다. 확정된 결과가 이미 저장된 뒤 출력 전에 죽었다면 조회로 그 결과를 회수하며 재실행하지 않는다.

### D. 소유자 급사와 슬롯 격리

실행 owner가 SIGKILL/OOM으로 사라지거나 PID가 재사용되면 후속 `status`/claim은 `owner_starttime` 등 identity 불일치를 판정한다. `requires_reprepare=True`가 유지되고 신규 작업은 거절된다. 명시 `prepare --slot N`이 안전한 준비를 완료한 후에만 가용화한다. 외부 관리자가 JSON을 지워야만 보호가 작동하는 구조는 실패다.

### E. 경쟁·중복·후속 대화

같은 request ID를 동시에 호출해도 외부 제출은 중복되지 않는다. 서로 다른 작업의 동일 슬롯 경쟁도 한 소유자만 승인된다. 원 슬롯이 바쁜 followup은 다른 빈 슬롯으로 이동하지 않는다. 지연된 이전 owner의 종료 처리나 복구 결과가 새 owner의 점유/결과를 해제·덮어쓰지 않는다.

### F. 닫힌 실패와 실행물 정합성

비호환 실행물, 사용할 수 없는 모델/Power, 실패한 ZIP 선택/압축/업로드는 해당 제출 전에 거절된다. 메타데이터 저장 충돌, 불확실한 커밋, 귀속 실패는 성공이 아니다. 답변 확정 후 후처리 실패에서는 저장 답변과 별도의 정리 실패/격리를 함께 회수한다. 설치물의 실제 CLI와 선택기 정체성을 대조할 수 있어야 하며 소스 검증만으로 구형 `dist` 실행을 승인하지 않는다.

**완료 판정의 경계**: 위 관찰에 필요한 필수 결과 전체가 제품의 약속이다. 한 시나리오의 성공, 패키지 생성, dry-run 출력, 하위 프로세스 exit 0만으로 전체 완성을 선언하지 않는다. 구체적 구현 순서·현재 Scope·검증 명령과 판정은 후속 역할의 책임이다.

## Open Product Meaning

None

현재 핵심 제품 의미는 자기완결적 실행, CLI 내장 보호, 현재 턴에만 귀속되는 성공, 실패 시 닫히는 수명주기로 확정했다. 번들러·배포 형식·증거 필드 배치·내구 저장 기법은 대체 가능한 구현 선택이며 미해결 제품 의미가 아니다. `CALIBRATED`는 이 의미가 정리되었다는 결과이지 런타임이 이미 구현되었거나 제품 검증을 통과했다는 판정이 아니다.
