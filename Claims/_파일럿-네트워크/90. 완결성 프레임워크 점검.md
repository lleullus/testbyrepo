# 네트워크 파일럿 완결성 점검

## 1. 점검 질문

파일럿을 지지하는 설명을 더 붙이는 대신 다음 질문으로 공격했다.

1. 증거에서 Claim까지 실제로 연결되는가?
2. Claim의 적용 조건은 답을 모른 상태에서도 판별 가능한가?
3. 같은 증거를 설명하는 경쟁 설명이 있는가?
4. 반례가 Claim을 깨뜨리는가, 범위를 좁히는가?
5. 관측 시점과 실제 유효기간을 혼동하지 않았는가?
6. 이 Claim을 운영 절차에 바로 사용해도 되는가?

## 2. 핵심 결론

초기 스키마는 **근거 사슬과 범위 경계를 드러내는 데는 유효**했지만, 그대로 전체 적용하기에는 다음 결함이 있다.

- 과거 VOC의 관측 구간을 정책 유효기간처럼 보이게 한다.
- 증거가 지지되는 정도와 현재 운영에 사용 가능한지를 하나의 `status`로 충분히 구분하지 못한다.
- 일부 적용 조건이 답을 이미 안다는 전제를 포함해 순환적이다.
- 한 Claim에 서로 독립적으로 바뀔 수 있는 복수 주장이 결합돼 있다.
- 파일을 만든 것만으로 모든 VOC가 처리됐는지 확인할 수 없다.
- 원문 전체 대화, 축약 대화, 익명화·요약 자료의 근거 품질 차이를 표현하지 못한다.

따라서 전체 적용 전에 스키마와 처리 흐름을 수정해야 한다.

# 3. Claim별 판정

## PILOT-NET-G001 — 조건 식별 Guard Claim

### 판정: 유지하되 조건 모델을 확장

서비스 모델·통신 방향·목적이 답을 갈라놓는다는 결론은 상반된 공식 답변들로 지지된다.

다만 `서비스 모델`만으로 구조 차이를 모두 설명한다고 단정할 수 없다. 일부 VOC에는 DKS-N/C가 명시되지 않았고, 구축 세대·망·클러스터 프로파일이 실제 분기 조건일 수도 있다.

따라서 최종 Guard Claim은 다음처럼 수정한다.

> 연동 주소를 선택하기 전에 서비스 모델 또는 네트워크 프로파일, 통신 방향, 연동 목적을 식별한다. 자료에서 모델·프로파일이 확인되지 않으면 주소 규칙을 일반화하지 않는다.

### 필요한 변경

- `service_model` 외에 `network_profile`을 허용한다.
- 미확인 값을 빈칸이 아니라 명시적 `unknown`으로 둔다.
- Guard Claim은 실제 주소를 주는 Claim이 아니라 **판단을 중지시키는 안전 규칙**임을 표시한다.

## PILOT-NET-001 — DKS-N DNS·인바운드

### 판정: 두 Claim으로 분리

초기 Claim에는 다음 두 주장이 결합돼 있다.

1. 내부 Cluster IP·Ingress Service IP는 외부 등록 주소가 아니다.
2. 외부 DNS·HTTP/HTTPS에는 대표 도메인 조회로 얻은 Cluster LB VIP를 사용한다.

두 주장은 현재 자료에서는 함께 나타나지만 독립적으로 변경될 수 있다. 예를 들어 조회 절차가 `nslookup`에서 콘솔 조회로 바뀌어도 내부 IP와 외부 VIP의 구분은 유지될 수 있다.

따라서 다음으로 분리한다.

- **경계 Claim**: 내부 Ingress Service IP와 외부 노출 주소를 동일시하지 않는다.
- **절차 Claim**: 관측된 DKS-N DNS 등록에서는 대표 도메인 조회 결과를 사용했다.

### 추가 결함

1월과 3월 VOC는 서비스 모델을 직접 명시하지 않는다. 이 자료는 DKS-N 범위를 직접 확장하는 근거가 아니라 `corroboration`으로만 사용해야 한다.

## PILOT-NET-002 — 기존 DKS Node 대역

### 판정: Claim Layer에서 제외하고 case-only로 이동

초기 적용 조건 중 다음 문장은 순환적이다.

> 운영팀이 그 클러스터의 방화벽 출발지로 Worker Node IP 대역을 지정함

이 조건을 확인하려면 이미 답을 알고 있어야 한다. 따라서 새로운 사건에 적용할 수 있는 조건이 아니다.

또한 두 VOC 모두 DKS-N/C를 명시하지 않으므로, 현재 증거에서 재사용 가능한 범위를 확정할 수 없다.

현재 정당화되는 것은 다음 사건 사실뿐이다.

> 특정 과거 클러스터 사례에서 운영팀이 Worker Node IP 대역을 방화벽 출발지로 안내했다.

이는 Conditional Claim이 아니라 **case-only evidence**다. 전체 적용에서는 Claim 파일을 만들지 않고 VOC Coverage Ledger에서 다음처럼 관리한다.

```yaml
resolution: case-only
reason: service-model-and-network-profile-unresolved
candidate_branch: legacy-dks-outbound-node-subnet
```

향후 공식 자료에서 적용 범위가 확인되면 새 Claim의 Evidence로 승격한다.

---

## PILOT-NET-003 — DKS-C Egress SNAT

### 판정: 유지하되 현재성 Gate 추가

서로 다른 두 사례에서 DKS-C 전용 Egress IP SNAT 구조가 직접 확인되므로, 증거에서 Claim까지의 연결은 성립한다.

하지만 2026-05~07의 공식 답변이 2026-09-25 현재 정책임을 검증하지 않았다. 따라서 다음 상태를 분리해야 한다.

- `evidence_status: supported`
- `currentness: unverified-current`
- `operational_use: advisory`

즉 역사적·설계적 설명에는 사용할 수 있지만, 현재 방화벽 신청서를 작성하는 절차의 확정값으로 사용하려면 최신 공식 자료를 재확인해야 한다.

---

## PILOT-NET-004 — DKS-C ALB 백엔드

### 판정: 금지와 대안을 분리

초기 Claim에는 다음이 결합돼 있다.

1. 외부에서 Worker Node NodePort를 직접 ALB backend로 사용할 수 없다.
2. Two-Arm LB VIP를 backend target으로 사용한다.

첫 번째는 네트워크 경계에 관한 **prohibition/capability Claim**이고, 두 번째는 당시 제공 방식에 관한 **selection Claim**이다. 향후 LB 구현이 바뀌면 두 번째만 폐기될 수 있다.

따라서 최종 Claim을 두 개로 분리한다.

- `DKS-C 전용 VPC 외부에서는 Worker Node NodePort 직접 접근이 지원되지 않는다.`
- `관측된 ALB 연동 방식에서는 클러스터 Two-Arm LB VIP를 backend target으로 사용했다.`

두 번째 Claim은 단일 VOC 근거이므로 `supported`로 둘 수 있으나 `currentness: unverified-current`, `operational_use: advisory`로 제한한다.

# 4. 초기 스키마에서 제거·변경할 항목

## `observed_from` / `observed_to` 제거

이 값은 증거가 나타난 기간이지 Claim의 유효기간이 아니다. 유효기간으로 오독될 수 있으므로 다음으로 바꾼다.

```yaml
evidence_first_seen: 2026-05-19
evidence_last_seen: 2026-07-01
```

정책 유효기간은 공식 자료가 직접 확인할 때만 별도로 기록한다.

## 단일 `status` 분리

```yaml
evidence_status: candidate | supported | contested | superseded
currentness: historical | unverified-current | current
operational_use: blocked | advisory | allowed
```

- `evidence_status`는 증거와 논리의 상태다.
- `currentness`는 시간적 유효성의 확인 상태다.
- `operational_use`는 실제 절차에 사용할 수 있는지를 나타낸다.

세 값을 합치지 않는다.

## 배열 필드 통일

단수·복수 혼용을 없애고 다음 필드는 항상 배열로 쓴다.

```yaml
service_models: []
network_profiles: []
directions: []
purposes: []
protocols: []
```

미확인은 빈 배열이 아니라 `[unknown]`으로 명시한다.

# 5. 새로 필요한 필드

## `decision_question`

Claim이 실제로 어떤 판단 질문에 답하는지 한 문장으로 기록한다.

## `derivation`

```yaml
derivation: direct | repeated | contrastive | boundary
```

- `direct`: 공식 답변이 Claim을 직접 명시
- `repeated`: 같은 조건의 복수 사례에서 반복
- `contrastive`: 서로 다른 답변의 조건 차이로 도출
- `boundary`: 다른 조건의 반례가 범위를 제한

## `evidence_ids`

VOC 번호를 배열로 기록해 Claim ↔ VOC 역추적을 가능하게 한다.

## `source_fidelity`

근거표 각 행에서 자료 상태를 구분한다.

- `full-dialogue`: 문의와 공식 답변이 구체적으로 보존됨
- `redacted-dialogue`: 사용자 정보 일부가 익명화됨
- `summary-only`: 요약만 있고 상세 공식 답변이 없음
- `partial`: 일부 대화가 누락됐음이 명시됨

## `invalidation_conditions`

어떤 증거가 나오면 Claim을 수정 또는 폐기해야 하는지 기록한다.

## `depends_on`

상위 Guard Claim이나 선행 Claim이 필요한 경우 ID로 연결한다.

# 6. Claim 파일만으로는 부족한 이유

Claim 생성만으로 모든 VOC를 처리했다고 증명할 수 없다. 반복성이 없거나 범위가 불명확한 VOC는 Claim이 되지 않기 때문이다.

따라서 전체 적용에는 **VOC Coverage Ledger**가 필수다.

각 VOC는 반드시 다음 중 하나의 처분을 가진다.

```text
supports-claim    기존 Claim을 직접 지지
bounds-claim      Claim의 적용 범위를 좁힘
contradicts       동일 조건에서 충돌
candidate-source  Claim 후보이나 검증 부족
case-only         사건 사실로만 보존
out-of-scope      현재 Claim 프로젝트 범위 밖
```

Ledger가 있어야 Claim이 생성되지 않은 VOC도 누락이 아니라 의도적 처분임을 설명할 수 있다.

---

# 7. 운영 사용 Gate

VOC만을 근거로 만든 Claim은 기본적으로 현재 정책을 보장하지 않는다.

운영 절차나 신청값을 확정하는 문서에서 Claim을 직접 사용하려면 다음을 모두 만족해야 한다.

```text
evidence_status = supported
currentness = current
operational_use = allowed
```

그 외 Claim은 분석·역사·후보 지식으로는 사용할 수 있지만 현재 절차의 확정 근거로 사용하지 않는다.

---

# 8. 파일럿을 거쳐 확정된 설계 원칙

1. Claim이 되지 못한 사건을 억지로 일반화하지 않는다.
2. 적용 조건은 답을 모른 상태에서도 판별 가능해야 한다.
3. 한 Claim에는 독립적으로 변경 가능한 주장을 하나만 둔다.
4. 증거 지지, 현재성, 운영 사용 가능성을 분리한다.
5. 과거 관측 기간을 정책 유효기간으로 쓰지 않는다.
6. 서비스 모델 미확인은 추론으로 채우지 않는다.
7. 모든 VOC의 처분은 Coverage Ledger에 남긴다.
8. Claim을 깨뜨릴 증거를 `invalidation_conditions`로 미리 적는다.
9. LLM은 후보 추출과 반례 탐색에 사용하되 Claim 승격은 근거표와 범위 점검을 통과해야 한다.

## 최종 판단

파일럿은 Conditional Claim Layer의 필요성을 지지했지만, 초기 스키마 그대로의 전체 확장은 기각한다.

다음 단계는 이 점검 결과를 반영한 **정식 운영 설계 v0.2**, **Coverage Ledger**, **분리·수정된 네트워크 Claim**을 만든 뒤 전체 VOC를 순차 분류하는 것이다.
